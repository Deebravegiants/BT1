### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` value used downstream to attribute the webhook to a tenant is read from an unauthenticated HTTP header. `Utils::HmacValidator` never binds that header to the signature, so `Registry.process` authenticates the *bytes* of a webhook but trusts an unauthenticated *shop* label for tenant routing.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no role in that signable string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and compare against the header-supplied `hmac-sha256` value — the shop header is never part of the digest input: [3](#0-2) 

`Registry.process` performs exactly this raw-body-only check and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The equality this breaks is: **shop authenticated by the HMAC (none — HMAC only covers the body) ≠ shop used as the tenant/session key (`request.shop`, taken from an attacker-controllable header)**. Any `(raw_body, hmac)` pair that is valid for *some* shop is valid for *every* shop value an attacker chooses to place in the header, because the header is outside the signed content.

### Impact Explanation
This is a cross-tenant identity confusion at the point where the gem hands validated webhook data to the host application. An unprivileged actor who can obtain one genuinely-signed `(body, hmac)` pair — trivially available to anyone who can install/trigger a webhook on their own store, or who can simply resend a previously observed webhook — can replay it against the target app's public webhook endpoint while swapping the `shop` header to name a victim shop. `Registry.process` will pass HMAC validation and deliver attacker-controlled `body`/topic data labeled with the victim's shop to the app's handler via `WebhookMetadata#shop`. Host apps commonly use this shop value as the tenant key to look up sessions/access tokens or to gate per-tenant business logic (including mandatory topics like `customers/redact`, `shop/redact`), so this can cause cross-tenant data corruption, spoofed mandatory-compliance webhooks, or attacker-controlled data being processed under another merchant's identity.

### Likelihood Explanation
Reaching this requires no `api_secret_key`, no access token, and no privileged account — only the ability to send an HTTP request to the app's public webhook endpoint (which is, by design, internet-reachable) plus one legitimately-observed `(body, hmac)` pair (obtainable from the attacker's own shop/app installation). This is directly reachable through the gem's own documented `Registry.process` entry point with no reliance on the host app deviating from documented usage.

### Recommendation
Include the shop (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed payload before it is trusted — e.g., have `to_signable_string` incorporate the shop header, or require host apps to independently verify that the shop in the webhook belongs to a store with an active, matching session before acting on the payload. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a sole tenant key.

### Proof of Concept
1. Attacker installs the target (public) app on their own store `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it was genuinely computed by Shopify over that body with the app's real secret.
2. Attacker POSTs to the app's public webhook endpoint with the same raw body and same `hmac-sha256` header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body) == header_hmac` — this passes.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, causing the host app to process attacker-supplied data under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
