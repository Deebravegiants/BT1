### Title
Unaccounted ETH drain from Emporium via zero-length `erc20TokenAddresses` + unsigned stateless op - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When a `transact()` call targets the Emporium external action with `circomData.erc20TokenAddresses.length == 0`, both `Hinkal.sol`'s balance-diff loop and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` accounting loop are bounded by that same empty array and never execute. Combined with `verifyWallet` skipping all signature checks when `stack.signerAddress == address(0)`, an attacker can submit an `EmporiumStack` whose stateless op sends `op.value` (up to the full ETH balance of the Emporium contract) to an attacker-controlled `op.endpoint`, and no code path ever measures or constrains that ETH movement.

### Finding Description
The claimed equality is: *tokens leaving an action == -deltaAmountChanges it received*, i.e. `sum(balanceChange_i)` measured over `circomData.erc20TokenAddresses` must equal the net negative of `deltaAmountChanges`. This equality is enforced only by iterating `circomData.erc20TokenAddresses`:

- In `Hinkal.sol`, the pre/post balance snapshot and slippage check loop is `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` [1](#0-0) .
- In `EmporiumUpgradeable.runAction`, `deltaAmountChanges` is sized to `circomData.erc20TokenAddresses.length` in `Hinkal.sol:_externalTransact` [2](#0-1) , and the post-call reconciliation loop in `runAction` is likewise `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)` [3](#0-2) .

When `erc20TokenAddresses.length == 0` (which `CircomDataBuilder.formInputForCircom` explicitly routes to the minimal `formInputEmporiumMin` public-input path for the Emporium action) [4](#0-3) , both of these loops iterate zero times, so no ETH movement performed inside the loop over `stack.ops` is ever captured in `balancesBefore`/`balancesAfter`, `oldBalances`/`newBalances`, or checked against slippage.

Inside `runAction`, the operation loop executes every `stack.ops[i]` unconditionally, and for the "Stateless Interaction" branch performs a raw low-level call carrying `op.value` ETH to an arbitrary `op.endpoint`:
```
(success, err) = op.endpoint.call{value: op.value}(op.callData);
``` [5](#0-4) 

Critically, `verifyWallet` — the only gate on the contents of `stack.ops` — returns immediately without any EIP-712 signature check when `stack.signerAddress == address(0)`:
```
if (stack.signerAddress == address(0)) {
    return;
}
``` [6](#0-5) 

So an attacker who submits their own valid proof (over their own UTXOs, using the minimal Emporium public-input form) can freely choose `stack.signerAddress = address(0)` and a `stack.ops` entry with `invokeWallet = false`, `endpoint = <attacker contract>`, `value = address(Emporium).balance`. That op executes with real ETH leaving the Emporium contract, yet because `erc20TokenAddresses = []`, neither `Hinkal.sol` nor `EmporiumUpgradeable.runAction` ever samples `address(Emporium).balance` before/after, so `balanceChange` for that ETH is never computed and the `BalanceChangeShouldBePositive` revert path (lines 141-144) is never reached because the loop body containing it never runs. Existing guards (`performHinkalChecks`/`dimensionsCheck`, `verifyProof`, `rootHashExists`, `onlyAllowedRecipient`, `nonReentrant`) constrain the *sizes* and consistency of the `circomData` arrays and the validity of the attacker's own UTXO proof, but none of them re-introduce an ETH balance check when the array is deliberately empty — the code's own comment at line 138 ("this equation reads: total change of emporium balance = what was moved to emporium...") confirms the design intent that this loop is the sole ETH/token accounting mechanism, and it is bypassed entirely for the zero-token case.

### Impact Explanation
Any ETH resting in the Emporium contract (e.g. residual balances carried over between transactions, as acknowledged by the code comment "the only case when balanceChange can be < 0, when there were some funds on emporium before the call") can be swept out by an attacker-controlled endpoint with zero on-chain accounting or revert protection. This is a direct, unaccounted theft of ETH held by the protocol's Emporium contract — matching the Critical category ("direct theft of shielded or in-flight user funds" / protocol funds moved without any authorization check). It is repeatable every time the Emporium contract accumulates ETH balance and an attacker can submit a self-generated proof using the zero-token-array path.

### Likelihood Explanation
Preconditions: (1) the attacker must be able to submit a valid ZK proof over their own UTXOs targeting the Emporium external action with `erc20TokenAddresses = []` (fully within an unprivileged user's capability, since they control their own `CircomData` and deposits); (2) the Emporium contract must hold a non-zero ETH balance at call time (an expected, code-acknowledged possibility, and the attacker can also engineer this indirectly through other Emporium ops or by waiting for legitimate residual balances). No privileged role, relay cooperation, or victim key is required — the attacker only needs to construct `EmporiumStack` with `signerAddress = address(0)` and a stateless op, which requires no signature at all.

### Recommendation
Do not allow the "Min" (zero-token) Emporium public-input/accounting path to bypass ETH/ERC20 balance reconciliation. Either (a) always snapshot and reconcile `address(this).balance` (native ETH) in `EmporiumUpgradeable.runAction` and `Hinkal.sol` independent of `erc20TokenAddresses.length`, or (b) forbid non-zero `op.value` / arbitrary `op.endpoint` calls whenever `erc20TokenAddresses.length == 0`, or (c) require `deltaAmountChanges`/`erc20TokenAddresses` to include the native-ETH entry whenever any `op.value > 0` is present in the decoded `EmporiumStack`, so the existing `balanceChange < 0` revert guard actually executes.

### Proof of Concept
Hardhat test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a malicious `AttackerSink` contract with a `receive()` function.
2. Fund the Emporium contract with ETH directly (e.g., via a prior legitimate transaction that leaves residual balance, or by sending ETH directly if `receive()` permits it) to set `address(Emporium).balance = X`.
3. Generate a valid Hinkal proof for the attacker's own UTXO set with `circomData.erc20TokenAddresses = []`, `circomData.amountChanges = []`, `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)`, `ops = [{endpoint: AttackerSink, invokeWallet: false, value: X, callData: ""}]`.
4. Call `Hinkal.transact(...)` with this proof and circomData.
5. Assert: `getBalancesForArray(circomData.erc20TokenAddresses)` returns `[]` both before and after (trivially true since array is empty); `address(Emporium).balance` drops from `X` to `0`; `address(AttackerSink).balance` increases by `X`; and the transaction does not revert with `BalanceChangeShouldBePositive` (confirming the guard never executed).
