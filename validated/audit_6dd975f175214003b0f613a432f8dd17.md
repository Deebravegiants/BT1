## Finding: Webhook shop identity not bound to HMAC signature [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [4](#0-3) , while `#shop` (and `#topic`, `#webhook_id`, `#api_version`) are read verbatim from unauthenticated HTTP headers [5](#0-4) . `Registry.process` only validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, then hands `request.shop` straight to the app's webhook handler as the tenant identifier, with no separate binding check [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop_that_authenticated_the_payload == shop_the_handler_attributes_the_data_to`

Because the app's `api_secret_key` is a single shared secret used to sign webhook bodies for *every* shop that has installed the app (not a per-shop secret), any merchant who installs the app receives genuine `(body, HMAC)` pairs signed with that same secret for their own shop's events. Since the HMAC computation in `HmacValidator.validate_signature` only signs `verifiable_query.to_signable_string`, which for webhooks is just `@raw_body` [6](#0-5) [4](#0-3) , the `x-shopify-shop-domain` header carrying the tenant identity is left completely outside the cryptographic proof.

A merchant who legitimately owns Shop A can therefore capture a real, validly-signed webhook delivery for Shop A, and resend the identical body + HMAC to the app's public webhook endpoint while substituting `x-shopify-shop-domain: shop-b.myshopify.com`. `HmacValidator.validate` will still return `true` because it only re-derives the HMAC from `@raw_body` [7](#0-6) , and `Registry.process` will dispatch to the handler with `shop: request.shop` set to the attacker-chosen value `shop-b.myshopify.com` [8](#0-7) .

### Impact Explanation
This breaks the tenant boundary: the app's business logic (e.g. order/customer sync, `app/uninstalled` cleanup, data deletion, entitlement changes) trusts `WebhookMetadata#shop` as the tenant key while only the body — not the shop — was authenticated. An attacker who is merely a legitimate installer for their own store can inject fabricated events attributed to a victim shop, enabling cross-tenant data corruption or forged lifecycle events (e.g. spoofing `app/uninstalled` or `shop/redact` for a shop they do not own) — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires being an ordinary, unprivileged app installer able to capture their own webhook traffic and replay HTTP requests to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or victim credentials is needed, matching the required unprivileged-attacker profile.

### Recommendation
Bind the shop identity into the signed material, or otherwise cross-check the `x-shopify-shop-domain` header against a shop known/registered independently (e.g. verify it matches a shop with an active, stored session/registration) before dispatching to handlers, rather than trusting the header solely because the body-only HMAC passed.

### Proof of Concept
1. Install the app normally on attacker-owned `shop-a.myshopify.com`; capture a real webhook delivery (raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`).
2. Resend an HTTP POST to the app's webhook endpoint with identical body `B` and header `H`, but `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop that also installed the app).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC from `B` only and matches `H` — validation succeeds.
4. The handler executes with `WebhookMetadata.shop == "shop-b.myshopify.com"`, even though the payload never originated from Shopify for that shop.
