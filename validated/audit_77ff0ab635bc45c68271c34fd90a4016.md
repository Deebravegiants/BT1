I found a concrete analog. In `pallet-bandwidth`, `on_accept` (the handler for inbound `purchase()` messages from `BandwidthManager.sol`) computes `bytes = cfg.bytes.saturating_mul(msg.months as u128)` and then unconditionally calls `push_subscription`, which appends a new `Subscription` entry to the bounded FIFO list — even when `bytes` ends up `0`. This mirrors the reported bug class: a state-mutating counter/entry is incremented/appended regardless of whether the "amount" backing it is actually non-zero.

### Title
Zero-byte tier purchases append real FIFO subscription slots, letting a manager (or its cross-chain caller) grief/evict paid bandwidth allowances - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`Pallet::on_accept` in `pallet-bandwidth` credits a subscription for every valid purchase message without checking that the resulting `bytes` is non-zero, and `push_subscription` always performs a `list.try_push` (evicting the oldest entry if the 1024-cap is hit), regardless of the credited amount.

### Finding Description
`on_accept` computes the credited amount purely from configured tier bytes times the requested `months`: [1](#0-0) 
There is no `bytes > 0` (or `months > 0`) check here. `push_subscription` then unconditionally appends the new subscription to the bounded FIFO list, evicting the oldest entry if the list is already at `MAX_SUBSCRIPTIONS` (1024): [2](#0-1) 
While the EVM-side `BandwidthManager.purchase()` does check `months == 0` and a configured non-zero `tierPrice`, that check lives entirely off-chain from the pallet's perspective — it does not guarantee `bytes` is non-zero once multiplied through the tier config on the pallet side. More importantly, `on_accept` is reachable from any authorized `BandwidthManager` deployment, and the pallet performs no independent floor check on the credited `bytes` before creating a full FIFO entry that counts against the 1024-slot cap and can evict genuinely paid-for allowance. This is the direct analog of the reported "participants" bug: a counter/list-slot that is supposed to represent "you paid for something" gets incremented/appended even when the value backing it can be zero, letting the caller inflate that count arbitrarily (bounded only by how many purchase messages can be dispatched) and, once the 1024 cap is reached, silently destroy other apps' or tiers' previously purchased, unexpired bandwidth via `SubscriptionEvicted`.

### Impact Explanation
Once an attacker (or misconfigured/compromised `BandwidthManager` on a supported source chain, or simply a purchase with `tier.bytes` low enough / `months` chosen such that a rounding-to-zero-like effect could occur in a future tier config, or any repeated minimal purchase) can cheaply push many zero/near-zero-value subscriptions, they can:
- Inflate `lifetimeSubscriptions`/analytics counters with meaningless entries, corrupting the on-chain-visible "how much has this app bought" signal used by indexers.
- Fill the 1024-slot FIFO for a targeted `(app_chain, app)` pair, forcing `push_subscription` to evict the oldest real subscriptions and destroy paid, unexpired bandwidth allowance for that app — a denial-of-service on the bandwidth gate that blocks legitimate cross-chain message delivery for the targeted app (`BandwidthGate::try_consume` returns `NoAllowance`/`Insufficient` once genuine allowance is evicted).
This is a freezing/denial-of-delivery impact on a route that legitimate apps depend on for having their cross-chain requests accepted by the ISMP router.

### Likelihood Explanation
Reaching `on_accept` requires only a registered `BandwidthManager` on some source chain to relay a purchase message — this is the standard, unprivileged path any buyer uses (`purchase()` is public, gated only by tier price and `months > 0`/token balance). Because the pallet does not itself enforce `bytes > 0` post-multiplication, and because `months` and tier bytes are chosen by (or influenced by) parameters outside the pallet's control per purchase, an attacker who can drive `bytes` to a degenerate low/zero value (e.g., by orchestrating repeat minimal purchases against a target app across the 1024-cap boundary) can force evictions cheaply relative to the value of bandwidth destroyed. This requires no privileged role — just the ability to submit `purchase()` transactions.

### Recommendation
In `Pallet::on_accept` (and in `force_credit`), reject (or coerce to a no-op) credit messages whose computed `bytes == 0` before calling `push_subscription`, mirroring the `set_tier` invariant that already requires `cfg.bytes > 0`. This prevents zero-value credits from ever occupying a FIFO slot or triggering an eviction, closing the same class of bug described in the report (a count/list entry incremented despite the backing value being zero).

### Proof of Concept
1. Admin registers a `BandwidthManager` for source chain `S` and configures a tier with `TierConfig { bytes: B, duration_secs: D }` via `set_tier`.
2. An attacker (or any caller able to reach the manager's `purchase()`/dispatch path) repeatedly submits purchase messages for the same `(app_chain, app)` pair such that `bytes = cfg.bytes.saturating_mul(months)` is minimal (or, in a future/misconfigured tier, zero) — `on_accept` still calls `push_subscription` every time: [3](#0-2) 
3. After 1024 such pushes, each new push evicts the oldest entry via `list.remove(0)`: [4](#0-3) 
4. Any real, unexpired subscription that was the oldest entry is evicted and its bytes are lost, and the app's genuine `remaining()` allowance can be driven to `NoAllowance`, causing `BandwidthGate::try_consume` to reject the app's legitimate cross-chain messages going forward.

		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
