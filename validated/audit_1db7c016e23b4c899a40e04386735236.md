### Title
Escrow release/refund permanently reverts and locks funds if the beneficiary is blacklisted by a token like USDC - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` uses `IERC20(token).safeTransfer(beneficiary, amount)` to push escrowed tokens directly to a solver or user address [1](#0-0) . This is invoked both from `onAccept` (settling `RedeemEscrow`/`RefundEscrow` messages delivered by a relayer) and `onGetResponse` (cancellation refunds) in `ExtrinsicIntents.sol` [2](#0-1) , and from the same-chain fill/cancel paths in `IntrinsicIntents.sol`. If the beneficiary address is blacklisted by a compliance-controlled token such as USDC, the `transfer` call reverts, which reverts the entire `onAccept`/`onGetResponse`/`fillOrder`/`cancelOrder` transaction.

### Finding Description
`_withdraw` is the single internal function that releases escrow to a beneficiary for both fills and refunds/cancellations across the IntentGatewayV2 (v2 intents) architecture:
- `IntentsBase._withdraw` iterates `body.tokens`, decrements `_orders[commitment][token]`, and calls `IERC20(token).safeTransfer(beneficiary, amount)` for ERC-20 inputs [3](#0-2) .
- On the cross-chain path, `ExtrinsicIntents.onAccept` is called by the host after a relayer delivers a `RedeemEscrow` or `RefundEscrow` message and unconditionally calls `_withdraw(body, ..., true)` [2](#0-1) .
- `ExtrinsicIntents.onGetResponse` (cancellation from source chain) also calls `_withdraw` to refund the user once the destination fill-status proof comes back empty.
- On the same-chain path, `IntrinsicIntents._fillOrder`/`_cancelSameChain` call `_withdraw` directly to pay the beneficiary (user or solver) inline within the fill/cancel transaction [4](#0-3) [5](#0-4) .

If `beneficiary` (the order's `user` or a filling solver) is on a token's blacklist (e.g., USDC's `isBlacklisted`), `safeTransfer` reverts. Because `_withdraw` is not wrapped in a try/catch and there is no fallback "credit balance for later pull" mechanism, this reverts:
- the relayer's `onAccept`/`onGetResponse` delivery on the source chain, which will fail identically on every resubmission — the escrow can never be released or refunded, permanently freezing the escrowed input tokens for that order;
- or, on same-chain orders, the solver's `fillOrder`/`cancelOrder` transaction, blocking that specific fill/cancellation attempt (any solver attempting to fill an order whose beneficiary is blacklisted will always revert, and the order owner can never cancel to reclaim escrow either).

This is the same bug class as the JOJO report: a protocol-level push-transfer to a potentially blacklisted address in a settlement/liquidation-like path causes an unavoidable, permanent revert instead of degrading gracefully (e.g., by crediting an internal balance the beneficiary can withdraw later via an alternate address).

### Impact Explanation
For cross-chain orders, once a solver has filled an order and the settlement message is in flight, if the source-chain beneficiary (the solver's payout address) is blacklisted for the escrowed token, the `RedeemEscrow` delivery permanently reverts on `onAccept` — the escrowed input tokens become permanently stuck in the gateway contract with no mechanism to redirect or reclaim them, since `_orders[commitment][token]` can never be decremented to zero and the funds cannot be swept by anyone else. The same is true for `RefundEscrow`/cancellation refunds to a blacklisted user: the user permanently loses access to their escrowed collateral. This constitutes a permanent freezing-of-funds condition, which is a valid Medium/High severity finding per the report's impact class.

### Likelihood Explanation
Reaching this requires only that the order's declared beneficiary (user on `placeOrder`, or the filling solver's chosen output address) becomes blacklisted by the underlying stablecoin issuer (e.g., USDC/Circle) at any point before settlement completes — a realistic, externally-triggerable, unprivileged condition that doesn't require any protocol bug beyond the missing fallback. Given USDC is an explicitly supported/expected asset in the intent gateway's test suite and fee/dust flows, this is a practically reachable scenario for any order denominated in a blacklist-capable stablecoin.

### Recommendation
Do not push tokens directly to a potentially blacklisted beneficiary in a context where failure blocks essential protocol state transitions (escrow settlement/refund). Instead:
- Wrap the ERC-20 transfer in `_withdraw` in a try/catch (or use a low-level call and check success without reverting the whole batch), and on failure credit an internal per-user withdrawable balance mapping that the beneficiary (or a designated alternate address) can pull from later.
- Alternatively, allow the beneficiary to specify an escape-hatch/backup address to redirect payouts to if the primary is blacklisted.
- Ensure this fallback applies uniformly across `_withdraw` in `IntentsBase.sol`, and the analogous `withdraw` function in the Tron `IntentGatewayV2.sol` implementation, which has the identical unconditional `transfer` call pattern [6](#0-5) .

### Proof of Concept
1. User places a cross-chain order on chain A with `inputs` = 1000 USDC, escrowed by the gateway (`placeOrder`).
2. Solver fills the order on chain B, delivering the output tokens to the user, and `_fillCrossChain` dispatches a `RedeemEscrow` `WithdrawalRequest{ beneficiary: solver }` back to chain A [7](#0-6) .
3. Before the message is relayed and delivered, Circle blacklists the solver's payout address (e.g., due to unrelated activity) for USDC.
4. The relayer submits the proof; the host calls `onAccept`, which decodes the `RedeemEscrow` body and calls `_withdraw(body, false, true)` [2](#0-1) .
5. Inside `_withdraw`, `IERC20(usdc).safeTransfer(solver, 1000e6)` reverts because `solver` is blacklisted [1](#0-0) .
6. The entire `onAccept` transaction reverts. Every relayer resubmission of the same proof will revert identically. The 1000 USDC remains locked in the gateway contract indefinitely — the solver already delivered output tokens to the user but can never claim the escrowed input, and no other mechanism exists to release or redirect these funds.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
