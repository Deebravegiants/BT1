### Title
Iris-capture signature omits signup context, enabling replay with mismatched signup metadata - (File: `src/plans/enroll_user.rs`)

### Summary
The signature that orb-core attaches to a signup request is computed over only a subset of the data sent to the backend (`orb_id`, `user_id`, and the raw iris/mask codes). It excludes `signup_id`, the operator/`distributorId`, `signup_reason`, `region`, and the GPS coordinates that are submitted in the very same multipart request. Because the signature does not bind to this contextual metadata, a previously-produced signature/iris-code pair can be resubmitted alongside different context fields without invalidating the cryptographic check, mirroring the reported Connext issue where a signature covered only the tx ID instead of the entire digest.

### Finding Description
`make_signature()` builds the digest that is later signed by the Secure Element: [1](#0-0) 

The digest is computed from `ORB_ID`, `user_qr_code.user_id`, and the iris/mask codes and versions only. This signature is then transmitted together with several additional fields that are *not* part of the signed digest: [2](#0-1) 

Specifically, `signup_id` (used in the URL path `/api/v2/signups/{signup_id}`), `distributorId` (operator identity), `reason` (`SignupReason`: `Normal`/`Failure`/`Fraud`), `region`, `latitude`, and `longitude` are all sent unsigned. The backend can only cryptographically confirm that "this `user_id` + these iris codes were produced by this Orb's secure hardware" — it cannot confirm which signup session, which operator, which fraud/failure reason, or which location that attestation is bound to.

This is structurally identical to the reported class of bug: a signature that commits to only part of the meaningful state (tx ID) instead of the complete digest (`hashInvariantTransactionData`) allows old signatures to be replayed with different associated data (e.g., different relayer fee/`preparedBlockNumber`). Here, an iris-code signature can potentially be replayed with a different `signup_id`, operator, or `SignupReason` while still validating against the Secure Element's public key.

### Impact Explanation
If a genuine capture signature for a given `user_id`/iris-code pair is captured and resubmitted with altered context (e.g., a different `signup_id`, a `Fraud`→`Normal` reason swap, or a different operator/`distributorId`), the backend's ability to trust the signature as an attestation of the *entire* signup context is undermined. This can lead to misattributed signups (crediting/associating a genuine biometric capture with a different signup session or operator) or weakened fraud/failure classification if the reason field is not itself independently verifiable against the signed payload — directly matching the "misattributed signup" and "fraud/liveness bypass" impact categories.

### Likelihood Explanation
Exploitation requires the ability to submit or resubmit a signup request carrying a previously produced signature alongside different metadata fields; this does not require breaking the Secure Element or possessing privileged Orb operator keys — it only requires that the unsigned fields (`signup_id`, `reason`, `distributorId`, `region`, coordinates) can be varied independently of the signature that is meant to attest to the capture's authenticity. The likelihood is moderate: it depends on whether/how strictly the backend cross-checks these fields against session state, which is outside this repo, but the client-side signing logic itself provides no binding guarantee.

### Recommendation
Include all security-relevant contextual fields in the signed digest, not just `orb_id`, `user_id`, and iris codes. At minimum, `signup_id`, `distributorId` (operator), and `signup_reason` should be part of the data passed into `make_signature()`/`secure_element::sign()`, analogous to using `hashInvariantTransactionData(txData)` instead of only the transaction ID, so any change to session/operator/reason invalidates the signature and cannot be replayed across mismatched requests.

### Proof of Concept
1. Observe that `make_signature` in `src/plans/enroll_user.rs:290-304` hashes only `ORB_ID`, `user_qr_code.user_id`, and pipeline iris/mask codes.
2. Observe that `signup_post::request` in `src/backend/signup_post.rs:100-139` sends this signature together with `signup_id` (in the URL), `distributorId`, `reason`, `region`, `latitude`, `longitude` — none of which are covered by the signature.
3. A previously valid `(user_id, iris_codes, signature)` triple can therefore be paired with a different `signup_id`, `distributorId`, or `reason` value in a resubmitted request, and the signature verification (bound only to `user_id` + iris codes) would still succeed, since the signed payload never encodes those fields.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
