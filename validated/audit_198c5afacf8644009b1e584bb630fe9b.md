## Title
Race between background config polling and in-flight signup allows `ignore_user_centric_signups` to change mid-signup, bypassing backend enrollment attestation — analog of `InsuranceFund#syncDeps()` (File: `src/plans/mod.rs`)

### Summary
This is the same bug class as the reported `InsuranceFund#syncDeps()` issue: a piece of *shared, mutable global state* can be overwritten asynchronously by a background process while a user-facing operation is mid-flight, and different points in that operation read the shared state at different times, producing an inconsistent outcome. In `InsuranceFund`, `vusd` is read once at deposit and again (possibly with a different value) at withdraw. In orb-core, the shared `Config` object (`Arc<Mutex<Config>>`) is refreshed from the backend every 10 seconds by a background task while a signup is in progress, and `do_signup()` reads the `ignore_user_centric_signups` flag from that shared config a second time, later in the flow, independent of the config snapshot it took at the start of the signup.

### Finding Description
`MasterPlan::do_signup()` takes a snapshot of several config fields at the very beginning of a signup: [1](#0-0) 

Much later in the same function — after QR validation, biometric capture, the biometric pipeline, fraud detection, PCP package building, and PCP tier uploads (all of which can take far longer than a few seconds) — the code re-acquires the config lock independently to decide how to finalize the signup: [2](#0-1) 

This second read, `orb.config.lock().await.ignore_user_centric_signups`, is **not** the same snapshot taken at line 497-506; it's a fresh read of whatever the shared `Config` currently holds. Meanwhile, the `Observer` broker runs a background task that downloads and fully replaces the shared `Config` object every `CONFIG_UPDATE_INTERVAL` (10 seconds), independent of and concurrent with any in-progress signup: [3](#0-2) [4](#0-3) 

The two branches produce materially different verification guarantees:
- If `user_centric_signup && !ignore_user_centric_signups` is true, success is derived purely from the locally-computed `signup_reason` (whether the pipeline/fraud checks passed) with no backend round trip.
- Otherwise, `enroll_user()` is invoked, which performs a real backend signup request and polls the backend until it reports `Completed`/`success == true`, i.e., an actual server-side attestation/dedup check: [5](#0-4) 

Because the flag governing which of these two paths is taken is read fresh at the end of the signup rather than pinned to the value observed when the signup began, a backend-triggered config change delivered mid-signup (within the same 10s polling cadence that overlaps a multi-second-to-multi-minute signup) can flip which path executes — exactly analogous to `Governance` calling `syncDeps()` between a user's deposit and withdrawal in the reported bug.

### Impact Explanation
If `ignore_user_centric_signups` toggles from `true` to `false` mid-signup (or the reverse), the orb can end up crediting a signup as successful (`result.success = true`, later reported via `debug_report.enrollment_status`) without ever completing the backend's authoritative confirmation flow, or it can fail to finalize a signup that the backend would have accepted. The former is a misattributed/unauthorized signup outcome: a signup is locally marked successful based only on on-device fraud-check results, bypassing the backend's own uniqueness/attestation check that `enroll_user()` exists to enforce.

### Likelihood Explanation
The window is realistic: `CONFIG_UPDATE_INTERVAL` is 10 seconds, and a signup routinely spans well beyond that (QR scans, biometric capture, ML pipeline, fraud checks, PCP building, and tiered uploads). Any operator-side or backend-driven config change pushed during this window will race with the in-flight signup's finalization check, with no re-validation or config pinning to prevent it.

### Recommendation
Use the single config snapshot captured at the start of `do_signup()` (the `Config { .. }` destructure at the top of the function) for the `ignore_user_centric_signups` decision instead of re-locking `orb.config` later in the same function. More generally, any decision that spans the lifetime of a signup should be based on a config value captured once at signup start, not re-read from the mutable shared `Config` at arbitrary later points, to avoid different phases of a single signup observing inconsistent configuration state — the same fix pattern recommended for `syncDeps()` (snapshot/validate before allowing a value in flight to be overwritten).

### Proof of Concept
1. Signup begins; `do_signup()` snapshots config, including implicitly relying on `ignore_user_centric_signups == false`. `user_centric_signup` from the user QR data is `true`.
2. Biometric capture, pipeline, and fraud checks run (multiple config-update intervals elapse).
3. Backend pushes a config update where `ignore_user_centric_signups` flips to `true`; the background `Observer::config_update` task in `src/brokers/observer.rs` replaces the whole shared `Config`.
4. `do_signup()` reaches the final check at `src/plans/mod.rs:639`, re-reads `orb.config.lock().await.ignore_user_centric_signups`, now `true`, and takes the local-only success path instead of calling `enroll_user()`.
5. The signup is marked `Success` and reported to the backend as `signup_successful()` without ever going through the backend's real enrollment/dedup confirmation cycle used by `enroll_user()`.
