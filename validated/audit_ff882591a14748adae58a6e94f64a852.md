## Finding: Webhook `shop` identity is not covered by HMAC verification, contradicting the "verified request" guarantee

**Analog to UF-2:** the report's underlying theme is that a value that matters for authorization/attribution isn't actually protected by the check that's supposed to secure it. Here the identity-binding equality that should hold is:

`shop domain used to attribute/process the webhook == shop domain cryptographically bound by the HMAC signature`

That equality does not hold.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, never the `shop`/topic headers: [1](#0-0) 

`shop` is read directly and unauthenticated from the `x-shopify-shop-domain` / `shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC over that same request object, then immediately trusts `request.shop` as the tenant identity handed to the app's handler, with no additional check that the shop is one the HMAC secret could have authenticated: [3](#0-2) 

`HmacValidator.validate` only recomputes and compares the signature over `verifiable_query.to_signable_string` — i.e. the body — never the shop: [4](#0-3) 

For contrast, the OAuth callback's `AuthQuery` (which uses the *same* `VerifiableQuery`/`HmacValidator` machinery) does bind `shop` into the signed string: [5](#0-4) 

So within this same library, one identity-carrying flow (OAuth) binds `shop` to the signature and the other (webhooks) does not.

### Why this matters

The library's own documentation promises stronger guarantees than the code delivers: `Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the handler with `shop`: [6](#0-5) 

But because the app's webhook HMAC secret (`Context.api_secret_key`) is shared across every shop that has the app installed, any merchant who installs the app on their own store legitimately receives valid `(raw_body, hmac)` pairs. They can then replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still passes (it never inspected `shop`), and `Registry.process` forwards `shop: request.shop` (the attacker-chosen value) straight to the app's handler as if Shopify itself vouched for that shop.

This breaks the identity binding an app relying on this gem would reasonably assume holds (`request.shop` is only as trustworthy as the HMAC that's supposed to authenticate it). Since apps commonly key session/database lookups and multi-tenant business logic directly off `WebhookMetadata#shop`/`data.shop`, this enables cross-tenant event injection/spoofing against shops the attacker never installed the app on.

### Recommendation

Bind `shop` (and ideally `topic`) into the value that is HMAC-verified, or have `Registry.process`/`WebhookMetadata` cross-check `request.shop` against a shop-specific verification path (not merely presence of *a* valid HMAC for the app), and update `docs/usage/webhooks.md` to accurately describe what is and is not authenticated by `process`.

### Note on confidence

I want to flag an important caveat: Shopify's platform-level webhook signing scheme is documented across all Shopify SDKs as "HMAC over the raw body only," and shop attribution via header is the platform's inherent design, not something this gem invented incorrectly. Whether this rises to a "new" vulnerability in this gem specifically (versus an inherent limitation of Shopify's webhook architecture that every consuming app must additionally guard against) is a judgment call — the gem does provide the primitive but doesn't overstate its guarantee elsewhere (i.e., `AuthQuery` for OAuth *does* bind `shop`, creating an inconsistency in the library's own hardening, and the docs' phrasing "verify the request did indeed come from Shopify" arguably overstates what `process` protects). I'm surfacing this as the strongest matching analog found in-scope, but you should weigh whether this is treated as a genuine library defect versus an accepted platform-level design limitation before treating it as a confirmed, actionable vulnerability.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
