### Title
Unbacked Reputation Asset mint via cheap self-relayed messages lets an attacker buy collator selection - (File: `modules/pallets/messaging-incentives/src/lib.rs`)

### Summary
`pallet-messaging-incentives` mints `ReputationAsset` to whoever signs the delivered message, scaled purely by the byte-size of the request body, with no linkage to any real economic cost (fee paid, proof cost, or destination value). Because dispatch fees on ISMP are optional (`fee` can be `0`) and the reward is decoupled from any fee actually paid, an attacker can dispatch cheap, large-bodied, self-targeted requests and self-relay them to mint large amounts of `ReputationAsset` for negligible cost, directly buying a higher chance of being selected as a Hyperbridge collator via `pallet-collator-manager`.

### Finding Description
`FeeHandler::on_executed` computes `bytes = max(body_size, 32)` per request in a delivered `Message::Request`/`Message::Response`, multiplies by governance-set `MintPerByte`, and mints that amount of `ReputationAsset` to the account recovered from the message's `signer` field (the relayer) <cite repo="Alyssadaypin/hyperbridge--025" path="modules/pallets/messaging-incentives/src/lib.rs" start="126="135"/> [1](#0-0) . This mint has no relationship to whether the underlying request carried a real relayer fee — dispatch fees on ISMP are explicitly optional and can be `0` (self-relay is an intended, documented use-case) [2](#0-1) [3](#0-2) .

`ReputationAsset` is the sole input to `pallet-collator-manager`'s collator-selection ranking: at every session boundary, candidates are ranked purely by their controller's `ReputationAsset` balance, and the top balances are selected into the collator set [4](#0-3) . The documentation confirms reputation is "the primary factor in Collator selection" and mirrors `$BRIDGE` earnings 1:1 for legitimate relaying/proving work [5](#0-4) .

The pallet's own 32-byte floor is explicitly designed only to stop *splitting* small payloads into many envelopes to abuse the floor — it does nothing to stop an attacker from constructing arbitrarily large, cheap-to-produce request bodies with a zero relayer fee and delivering (relaying) them to themselves, repeatedly, to mint unbounded `ReputationAsset` at will [6](#0-5) . The relayer is recovered purely from a valid sr25519 signature on the `signer` field of the message, with no requirement that this account paid anything for the request nor that the request delivers any real cross-chain value [7](#0-6) . This is structurally the same bug class as the referenced report: a minimal-cost action (dispatch + self-relay of a request with `fee = 0` and a large but cheap-to-produce body) mints a disproportionately large reward asset (`ReputationAsset`), which is then used to seize a privileged, consensus-critical role (collator/block-producer selection) — an unauthorized app action with concrete protocol-level impact, not merely a cosmetic score.

### Impact Explanation
An attacker who controls both the sending application (or simply pays `fee = 0` from any account) and a relayer identity can repeatedly dispatch and self-deliver large-bodied, low-value POST requests. Each delivery mints `bytes × MintPerByte` in `ReputationAsset` to the attacker's controller account at negligible real cost (gas plus, at most, a body-size-independent flat fee, since dispatch fees are optional and not enforced to scale with mint value). Accumulated reputation directly determines the outgoing collator set each session [8](#0-7) , so this lets an attacker cheaply outrank legitimate, economically-active relayers/provers and seize collator slots — a consensus-integrity compromise (unauthorized privileged-role acquisition) on Hyperbridge's own parachain, going well beyond a simple "points" gaming issue since collators produce blocks, run the fisherman/state-commitment veto logic, and are trusted with block production.

### Likelihood Explanation
Any account can dispatch an ISMP POST request with `fee = 0` (a documented, intended feature for self-relaying apps) [3](#0-2) , and any account holding a valid sr25519 key can act as the "relayer" whose signature is recovered and rewarded [9](#0-8) . No staking, permission, or fee-proportionality gate exists between message body size and the mint. Whenever `MintPerByte` is non-zero (which is the pallet's intended operating mode, wired into both the `gargantua` and `nexus` runtimes as the `IncentivesManager`/`FeeHandler` feeding `pallet-collator-manager` [10](#0-9) [11](#0-10) ), this path is exploitable by any unprivileged actor able to dispatch and deliver ISMP messages — a very low bar reachable from a single submitted extrinsic/self-relay loop.

### Recommendation
Tie the `ReputationAsset` mint to actual economic cost rather than raw byte-size: e.g., mint proportional to the real relayer fee paid/collected for the message (or require a non-zero, proportional fee before minting), and/or rate-limit/cap mint accrual per signer per session independent of self-generated traffic volume. At minimum, exclude self-relayed (`payer == signer`) or zero-fee (`fee == 0`) requests from minting, since these carry no real cost that reputation is meant to proxy for.

### Proof of Concept
1. Attacker deploys/uses any app on a connected chain and calls `dispatch()`/`dispatch_request()` with `fee = 0`, `payer = attacker`, and a request body sized as large as the destination/weight limits allow (e.g. tens of KB), targeting itself or a no-op module [2](#0-1) .
2. Attacker runs a relayer using their own controller keypair and delivers the message to Hyperbridge, producing a `Message::Request` signed with that key.
3. `pallet-ismp::execute` calls `FeeHandler::on_executed`, which computes `bytes = max(body.len(), 32)` and mints `bytes × MintPerByte` of `ReputationAsset` to the attacker's controller account, with `pays_fee = Pays::No` so no fee is charged for the extrinsic itself [1](#0-0) ; this is directly demonstrated by `on_executed_mints_reputation_proportional_to_bytes` and `on_executed_mints_accumulate_across_deliveries` in the pallet's own test suite [12](#0-11) [13](#0-12) .
4. Attacker repeats steps 1–3 across many blocks/sessions, accumulating `ReputationAsset` far in excess of legitimate operators' earnings for a fraction of the cost.
5. At the next session boundary, `pallet-collator-manager::new_session` ranks candidates by `ReputationAsset` balance and selects the attacker's controller into the collator set ahead of genuine relayers/provers [14](#0-13) .

	/// Same minimum-byte rule as the bandwidth gate (`max(body, 32)`),
	/// applied **per request** so packing requests into one envelope
	/// vs. splitting them across many produces identical mints.
	/// Applying the floor once per envelope would let a relayer inflate
	/// the mint by splitting (each split picks up its own 32-byte floor).
	fn message_bytes(message: &Message) -> u32 {
		match message {
			Message::Request(req) => req
				.requests
				.iter()
				.map(|p| core::cmp::max(p.body.len() as u32, 32))
				.sum::<u32>(),
			_ => 0,
		}
	}

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		_events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let rate = MintPerByte::<T>::get();
		if !rate.is_zero() {
			for mw in &messages {
				let bytes = Self::message_bytes(&mw.message);
				let bytes_balance: BalanceOf<T> = (bytes as u128).saturated_into();
				let amount = rate.saturating_mul(bytes_balance);
				if amount.is_zero() {
					continue;
				}
				if let Some(relayer) = Self::relayer_for(&mw.message) {
					match T::ReputationAsset::mint_into(&relayer, amount) {
						Ok(_) =>
							Self::deposit_event(Event::ReputationMinted { relayer, bytes, amount }),
						Err(err) => log::warn!(
							target: "messaging-incentives",
							"reputation mint failed for {bytes}b: {err:?}",
						),
					}
				}
			}
		}
		Ok(PostDispatchInfo { actual_weight: None, pays_fee: Pays::No })
	}

## Relayer Fees

The relayer fee is an optional incentive provided by applications initiating cross-chain transactions. It compensates Hyperbridge's decentralized relayers for delivering messages to the destination chain. Apps that prefer to self-relay can leave the fee at zero.

The fee is collected by `pallet-ismp`'s `IsmpDispatcher` from the configured `Currency` (typically a stablecoin). It's escrowed into the `RELAYER_FEE_ACCOUNT` and paid out to the relayer that delivers the message (or refunded to the payer on timeout).

			T::IncentivesManager::reset_incentives();

			let desired_collators = core::cmp::max(
				pallet_collator_selection::DesiredCandidates::<T>::get(),
				<T as pallet_collator_selection::Config>::MinEligibleCollators::get(),
			) as usize;

			// Rank candidate controllers that have session keys by reputation, highest first.
			// We keep every eligible candidate, even those with no reputation, so the set never
			// shrinks below what's needed to keep producing blocks; reputation only orders them.
			let mut candidates = pallet_collator_selection::CandidateList::<T>::get()
				.into_iter()
				.map(|info| info.who)
				.filter(|stash_account| !Unbonding::<T>::contains_key(stash_account))
				.filter_map(|stash_account| Controller::<T>::get(&stash_account))
				.filter(|controller_account| {
					!RemovedValidators::<T>::contains_key(controller_account) &&
						pallet_session::NextKeys::<T>::get(controller_account.clone().into())
							.is_some()
				})
				.map(|controller_account| {
					(T::ReputationAsset::balance(&controller_account), controller_account)
				})
				.collect::<Vec<_>>();

			candidates.sort_by_key(|(balance, _)| *balance);

			// Invulnerables always collate unless root has removed them; the highest reputation
			// candidates fill the rest.
			let mut new_set: Vec<T::AccountId> =
				pallet_collator_selection::Invulnerables::<T>::get()
					.into_iter()
					.filter(|validator| !RemovedValidators::<T>::contains_key(validator))
					.collect();
			for (_, controller) in candidates.into_iter().rev().take(desired_collators) {
				if !new_set.contains(&controller) {
					new_set.push(controller);
