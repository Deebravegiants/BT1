I have enough evidence to confirm the vulnerability class. The webhook HMAC signature covers only the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) fields — which are trusted and passed directly to the app's handler — come from unauthenticated HTTP headers.### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook HMAC over the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values used by the application's webhook handler are read directly from unauthenticated HTTP headers. This breaks the equality "the shop that was cryptographically verified == the shop the app acts on," which is the exact bug class the external report describes (data used for a security-sensitive decision is not the data actually verified).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled straight from HTTP headers, with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature strictly against `to_signable_string`, i.e., the body bytes, using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` then trusts `request.shop` (an unverified header) when building the `WebhookMetadata` passed to the app's handler, after only checking that the HMAC (over the body) is valid: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no relationship to the signature at all: [5](#0-4) 

Because HMAC verification only proves "this body was produced using the app's `client_secret`," it proves nothing about which shop the header claims to be from. The equality that should hold is:
`verified_bytes (raw_body signed by client_secret) == bytes acted on by the handler for tenant attribution (shop header)`
but the gem only enforces `verified_bytes == raw_body`, and separately trusts the `shop` header without binding it into the signed payload. Any request replay or MITM-free header rewrite (e.g., through an intermediary proxy, load balancer misconfiguration, or a malicious actor who has legitimately received one genuine, validly-signed webhook body from Shopify for their own tenant and can reuse that exact body with a different `x-shopify-shop-domain` header) will still pass `Utils::HmacValidator.validate`, since the header is not part of the signed content.

### Impact Explanation
This is a cross-tenant identity confusion: a webhook payload that passes HMAC verification can be attributed to any shop the header claims, not the shop that Shopify actually generated it for. Applications commonly key persistence, authorization and background jobs off `data.shop` (as shown in the gem's own webhook usage docs), so an attacker able to replay or relabel a validly-signed webhook body could cause the receiving application to process/attribute events to another merchant's tenant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation does not require the `client_secret` or a merchant's access token — it only requires the attacker to reuse a webhook body that was already validly signed by Shopify for the app (e.g., from the attacker's own installed shop) and manipulate the "shop-domain" header value delivered to the app's webhook endpoint before this gem's `HmacValidator` sees it. This is more likely if the host application terminates TLS behind a proxy/CDN that forwards headers separately from a fixed body, or if any intermediary component allows header rewriting. Likelihood is Medium: it requires a specific request-forwarding topology, but no secret material.

### Recommendation
Bind the tenant-identifying header (`shop-domain`, and ideally `topic`/`webhook-id`) into the signed payload verification, e.g., by validating the HMAC against a canonical string that includes the shop domain and body rather than the body alone. At minimum, the gem should document that host applications must not trust `shop`/`topic` from headers as tenant-authoritative independent of transport-level guarantees (i.e., that the webhook endpoint is reachable only via Shopify's direct TLS connection with no header-rewriting proxies in between), or the gem could look up the expected shop via the previously registered webhook and compare, rejecting mismatches.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and legitimately receives a webhook body `B` with a valid HMAC `H = HMAC_SHA256(client_secret, B)` and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same raw body `B` and HMAC header `H` to the app's webhook endpoint but rewrites `x-shopify-shop-domain: victim-shop.myshopify.com` (feasible wherever the delivery path allows header modification independent of the signed body, e.g., a misconfigured reverse proxy in front of the Rack app).
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `to_signable_string` (`@raw_body`) against `H`. [4](#0-3) 
4. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the application to attribute a validly-signed webhook event to the wrong tenant.
