### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw HTTP body, while `Request#shop` is read directly from the untrusted `x-shopify-shop-domain` / `shopify-shop-domain` header. `Registry.process` validates the HMAC of the body but then hands the handler a `WebhookMetadata` whose `shop` field was never covered by that signature, so the "authenticated bytes" and the "tenant identity acted on" are two different, independently-controllable inputs.

### Finding Description
`Registry.process` is the entry point host apps call to dispatch an inbound webhook: [1](#0-0) 

It validates the request with `Utils::HmacValidator.validate(request)`, which computes an HMAC over `request.to_signable_string` and compares it to `request.hmac`: [2](#0-1) 

`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

while `Request#shop` is taken verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relation to the HMAC computation: [4](#0-3) 

The library then forwards this unauthenticated `shop` value straight into the handler call as tenant identity: [5](#0-4) 

This breaks the intended binding `HMAC(body, api_secret_key) == received_hmac ⇒ (body, shop) is authentic`. In reality the equality that holds is only `HMAC(body, api_secret_key) == received_hmac`, independent of the `shop` header. Because `api_secret_key` is a single value shared by the app across **all** shops that install it (it is the app's client secret, not a per-shop secret), any tenant that has legitimately installed the app receives real webhook deliveries with valid `(body, hmac)` pairs signed under that same shared secret. That tenant can capture such a delivery and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain, while the body content is attacker-controlled data delivered to their own store's webhook.

This is the direct analog of the reported bug class: the field that is *acted upon* to establish identity (`shop`, used by host apps as the tenant/session key to route to the correct merchant's data) is disjoint from the field that is *cryptographically verified* (the raw body only).

### Impact Explanation
Any host application built on this gem that trusts `WebhookMetadata#shop` (or `Request#shop`) as an authenticated tenant identifier — the intended and documented use, since `Registry.process` passes it straight to the handler — is exposed to cross-tenant data confusion: an attacker who is a legitimate (but unprivileged, non-victim) merchant of the app can cause the app to process attacker-controlled payloads as if they originated from an arbitrary other merchant's shop. Depending on how the host app uses `data.shop` (e.g., as a lookup key to load that shop's session/access token and perform actions, or to write incoming data into that shop's tenant storage), this can lead to cross-tenant access/data corruption or actions being taken against a victim shop using the attacker's payload. This satisfies the "cross-tenant access" Critical impact category, since the tenant boundary (the `shop` domain) that the gem is expected to authenticate is not actually bound to the HMAC it validates.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own shop (an ordinary, unprivileged action available to any merchant) and be able to send an HTTP POST with attacker-chosen headers to the app's public webhook endpoint — no access token, `api_secret_key`, or privileged account is needed. The only "skill" required is capturing one legitimate webhook delivery to obtain a valid `(body, hmac)` pair, then replaying it with a different `shop` header. This is fully within the unprivileged-internet-user threat model.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the signed material, or independently verify that the `shop` header corresponds to a shop for which the app has an active installation/registration before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` / `WebhookMetadata#shop` is NOT authenticated by the HMAC check and must be cross-checked by the host application against its own list of installed/authorized shops before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, permitted action).
2. Shopify sends the attacker a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: HMAC_SHA256(api_secret_key, B)`.
3. Attacker crafts a new POST to the same app endpoint with the identical body `B` and identical HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `HmacValidator.validate` succeeds because it only checks `B` against the HMAC (per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#to_signable_string`), and `Registry.process` invokes the app's handler with `shop == "victim-shop.myshopify.com"`, even though the actual webhook body/content originated from the attacker's own shop context.
