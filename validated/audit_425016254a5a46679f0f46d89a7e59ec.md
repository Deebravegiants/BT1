### Title
Encrypted biometric Personal Custody Package (iris/face data) is uploaded before backend enrollment/fraud verification completes - ([File: src/plans/mod.rs])

### Summary
The reported bug is a Checks-Effects-Interactions violation: `transferFrom()` performs the external-facing effect (`_transfer()`) before completing the check (allowance decrement), which is unsafe ordering. The corresponding pattern in `orb-core` is `MasterPlan::do_signup` in [1](#0-0) , where the biometric encrypted packages (containing iris/face data) are built and queued for upload to cloud storage **before** the authoritative backend enrollment check (`enroll_user`, which performs dedup/fraud/legitimacy verification via `signup_post`/`signup_poll`) completes.

### Finding Description
In `do_signup`, the order of operations is:
1. Biometric pipeline processing and local fraud detection determine `signup_reason` (`Normal`/`Fraud`/`Failure`) at [1](#0-0) .
2. The Personal Custody Package (PCP) is built via `self.build_pcp(...)`, which packages encrypted iris/normalized-iris/face images (see `Package::build` in `personal_custody_package.rs`) [2](#0-1) .
3. Tier 0 upload is gated by a check (`if !self.upload_pcp_tier_0(...).await? { return Ok(result); }`), but tiers 1 and 2 — containing the encrypted iris/face image tars — are sent unconditionally to the `data_uploader` agent queue with no gating check at all [3](#0-2) .
4. Only **after** these uploads have been queued/sent does the code call `enroll_user` (unless `user_centric_signup` is true, in which case the "check" is entirely replaced by trusting the already-computed `signup_reason` value) to determine actual signup success/fraud status with the backend [4](#0-3) .

This is the "effects/interactions before checks complete" pattern: the irreversible interaction (uploading encrypted biometric imagery to the backend/S3 via `data_uploader`, which then calls `upload_personal_custody_package::request` and physically posts the data [5](#0-4) [6](#0-5) ) is performed before the check that determines whether the signup is legitimate, a duplicate, or fraudulent has been finalized with the backend.

### Impact Explanation
If the later `enroll_user` check determines the signup is `Fraud`, a duplicate, or otherwise invalid, the encrypted tier1/tier2 biometric packages (iris and face imagery) have already been dispatched for upload and cannot be un-sent — the `data_uploader` agent operates asynchronously and independently once the `Pcp` input is queued [7](#0-6) . This causes biometric data retention/disclosure for signups that are never confirmed valid by the backend check, i.e., an effect performed before its corresponding check is finalized — directly analogous to the CEI violation described in the report (interaction/effect executed ahead of the check that should gate it).

### Likelihood Explanation
This occurs on every normal signup path that reaches the PCP build step (not just an edge case): fraud/duplicate detection at the backend level happens via `enroll_user`, which runs strictly after the tier1/tier2 upload dispatch. Any signup flagged as fraud or duplicate by the backend (as opposed to the orb-local fraud check, which is largely stubbed out — see `detect_fraud` returning `Ok(false)` always in this FOSS build [8](#0-7) ) will still have had its biometric data uploaded.

### Recommendation
Reorder the signup pipeline so that biometric PCP tier1/tier2 uploads (and tier0, where currently gated only by network-level errors) are only dispatched after the backend-authoritative enrollment/fraud check (`enroll_user`) has confirmed the signup as `SignupReason::Normal` and successful. Alternatively, if upload must be pipelined for performance, add a compensating "delete/retract" mechanism so that if `enroll_user` subsequently reports fraud or failure, the already-uploaded tier1/tier2 packages are proactively purged from the backend/S3.

### Proof of Concept
Not applicable/executable in this ask-only context — the finding is based on the static code path in `do_signup`: `build_pcp` → `data_uploader.send(Pcp{tier:1})` / `data_uploader.send(Pcp{tier:2})` (unconditional, unchecked) at [3](#0-2) , followed only afterward by the enrollment success determination at [4](#0-3) . Reproducing this in a live environment (e.g., forcing `enroll_user`/`signup_post` to report `SignupReason::Fraud` after tier1/tier2 upload) would require a running Devin session with repo access, which is outside the scope of this ask-only analysis.

pub async fn request(
    signup_id: &SignupId,
    session_id: &str,
    checksum: &[u8],
    data: &[u8],
    tier: Option<u8>,
    config: &Arc<Mutex<Config>>,
) -> Result<()> {
    let t0 = Instant::now();
    let presigned_url::Response { url: presigned_url, fields: form_data_params } =
        if let Some(tier) = tier {
            presigned_url::request_tiered_package(
                &DATA_BACKEND_URL,
                signup_id,
                session_id,
                &BASE64.encode(checksum),
                tier,
            )
            .await?
        } else {
            presigned_url::request_package(
                &DATA_BACKEND_URL,
                signup_id,
                session_id,
                &BASE64.encode(checksum),
            )
            .await?
        };
    dd_timing!("main.time.signup.upload_custody_images.presigned", t0);
    tracing::debug!("Images self-custody presigned_url: {presigned_url:?}");
    tracing::debug!("Images self-custody form_data_params: {form_data_params:?}");
    let file = Part::bytes(data.to_vec())
        .file_name("package.tar.gz")
        .mime_str("application/octet-stream")?;
    let form = form_data_params
        .into_iter()
        .flatten()
        .fold(Form::new(), |form, (key, value)| form.text(key, value))
        .part("file", file);
    let Config { backend_http_connect_timeout, backend_http_request_timeout, .. } =
        *config.lock().await;
    let request =
        super::client_with_timeouts(backend_http_connect_timeout, backend_http_request_timeout)?
            .post(presigned_url)
            .multipart(form);
    tracing::debug!("Sending request {request:#?}");
    let t1 = Instant::now();
    let response = request.send().await?;
    dd_timing!("main.time.signup.upload_custody_images.upload", t1);
    tracing::debug!("Received response {response:#?}");
    response.error_for_status()?;
    Ok(())
