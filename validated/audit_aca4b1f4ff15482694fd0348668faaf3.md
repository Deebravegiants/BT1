### Title
Emporium `runAction` balance guard only tracks listed `erc20TokenAddresses`, letting an unprivileged prover drain any other token/ETH balance held by the Emporium via an unchecked op call - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes an arbitrary list of `EmporiumOperation`s (`endpoint.call{value}(callData)`) supplied by the prover inside `circomData.externalActionData.externalActionMetadata`, and only verifies that the Emporium's balance did not decrease for the tokens present in `circomData.erc20TokenAddresses`. Any balance movement in a token that is not included in that array is never checked, so a self-proving user can move/steal tokens the Emporium contract holds without breaking the on-chain invariant the contract relies on.

### Finding Description
`runAction` computes `balancesBefore`/`balancesAfter` strictly over `circomData.erc20TokenAddresses`: [1](#0-0) [2](#0-1) 

But the ops loop calls arbitrary `op.endpoint` with arbitrary `op.callData`/`op.value` without any restriction on which token contracts can be targeted: [3](#0-2) 

Critically, `circomData.externalActionData` (which embeds the whole `EmporiumStack`, including `ops`) is hashed into `getHashedCalldata`/`calldataHash`, which becomes part of `getSignedMessageHash`, a value the prover's own ZK proof commits to: [4](#0-3) [5](#0-4) 

That means an ordinary unprivileged user, acting purely as the prover of their own transaction, fully controls the `ops` array content — no relay, admin, or external signer approval is required for the `signerAddress == address(0)` path, which skips the EIP-712 wallet signature entirely: [6](#0-5) 

Additionally, `formInputForCircom` allows a minimal circuit path when `erc20TokenAddresses.length == 0` for Emporium actions, which does not carry the usual root-hash/nullifier/output-commitment checks at all: [7](#0-6) 

Combining these: a user can submit `circomData.erc20TokenAddresses` that omits (or is empty of) a token the Emporium contract currently holds a balance of (e.g., leftover dust from prior swaps/fee roundings, ETH sitting in the payable `receive()`, or tokens temporarily routed through Emporium in unrelated flows), and include an `EmporiumOperation` whose `endpoint` is that token's contract with `callData` = `transfer(attacker, balance)` (or a native-ETH-transferring call). Because that token/address is absent from `circomData.erc20TokenAddresses`, `balancesBefore`/`balancesAfter` never observe the drop, so `BalanceChangeShouldBePositive` never reverts, and the theft goes through cleanly.

### Impact Explanation
This breaks the balance equation the protocol relies on to guarantee "funds moved by an external action are always accounted for" — value is moved out of the Emporium (a protocol contract holding user/relay/dust balances) without being counted, resulting in theft of protocol/relay-held funds or funds left mid-flight in other operations. This falls under High/Critical impact: theft of protocol/relay fees or funds temporarily held by the contract, and unauthorized asset movement never intended by any wallet owner (since it's outside the tracked equality the contract enforces).

### Likelihood Explanation
No admin, relay, or third-party signature is required — the attacker only needs to be an ordinary Hinkal user capable of generating their own valid ZK proof (which they always can, since the malicious `ops`/`erc20TokenAddresses` selection is fully within the calldata they control and hash into their own proof). The only precondition is that the Emporium contract holds some balance in a token/ETH not listed in the attacker's chosen `erc20TokenAddresses` for that call, which is plausible given dust, fee rounding, and the contract's payable `receive()`.

### Recommendation
Enforce that every token/address touched by `EmporiumOperation.endpoint` (or at minimum, verify the Emporium's balance across the full universe of tokens it could plausibly hold, not just the caller-supplied list) is included in `circomData.erc20TokenAddresses` before execution, or restrict callable `endpoint`s to an explicit allow-list unrelated to arbitrary ERC20 token contracts. At minimum, track and verify balance deltas for any token address appearing in `op.endpoint`/decoded `callData`, not only the tokens the prover chooses to declare.

### Proof of Concept
1. Emporium contract accumulates a balance of `TokenX` (not part of any specific transaction's declared token set) through normal dust/fee residue or via `receive()` ETH.
2. Attacker (regular user) builds `CircomData` with `erc20TokenAddresses` = `[]` or a list that excludes `TokenX`/ETH, and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: TokenX, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, TokenX.balanceOf(emporium))) }`.
3. Attacker generates a valid proof over this `CircomData` (they control all inputs, including `calldataHash`/`getSignedMessageHash`), and submits the transaction through Hinkal's `_externalTransact` → `Emporium.runAction`.
4. `verifyWallet` returns immediately since `signerAddress == address(0)`; the op executes `TokenX.transfer(attacker, ...)`; `balancesBefore`/`balancesAfter` only track the (empty) `erc20TokenAddresses` array, so `balanceChange < 0` never triggers on `TokenX`, and the call succeeds, transferring `TokenX` to the attacker at no cost.
