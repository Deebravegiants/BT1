### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body, not the `shop-domain`/`topic` headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` values taken directly from unauthenticated HTTP headers to build the `WebhookMetadata` handed to the app's handler. None of those header-derived identity fields are bound into the signature, so a party who can obtain one legitimate `(body, hmac)` pair can replay it while attaching a different shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

But `Registry.process` derives the shop and topic identity fields entirely from headers, independent of the body/HMAC, and forwards them unchecked to the caller's handler: [3](#0-2) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from the `shopify-*`/`x-shopify-*` headers: [4](#0-3) 

The equality that should hold is:
`hmac_signed_bytes == (body, shop, topic)` for the fields the handler treats as authenticated.

What actually holds is:
`hmac_signed_bytes == body` only, while `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated header bytes trusted as if they were verified.

### Impact Explanation
Any party capable of triggering a legitimate webhook for **their own** shop (a fully unprivileged action — installing the app on a shop they control and generating an event) obtains a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. Because the `shop-domain` header is not part of the signed bytes, that same `(body, hmac)` pair can be replayed against the app's public webhook endpoint with the `shop-domain` header changed to a victim shop, and `Registry.process` will still pass `Utils::HmacValidator.validate` and dispatch `WebhookMetadata` claiming the victim shop as the source. Depending on the app's webhook handler (e.g., mandatory compliance webhooks, order/customer sync, or any per-shop side effect keyed off `data.shop`), this enables cross-tenant data injection/attribution — an attacker-controlled payload processed under another merchant's identity.

### Likelihood Explanation
Exploitation requires no secrets, no privileged account, and no host application misuse of the documented API — only the ability to generate a webhook for a shop the attacker controls (trivial for anyone able to install a Shopify app) and to POST that captured body/HMAC to the target app's public webhook endpoint with a modified `shop-domain` header. This is fully reachable through the gem's own `Registry.process`/`Request` code path, not through misuse of undocumented behavior.

### Recommendation
Bind the shop (and ideally topic) identity into the authenticated bytes before trusting them: include the `shop-domain` header (and other identity-bearing headers used to construct `WebhookMetadata`) in the value that is HMAC-verified, or independently cross-check the header-derived `shop` against shop-identifying content inside the verified body before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (fully unprivileged, self-service).
2. Attacker triggers any registered webhook topic (e.g. `orders/create`) on their own shop, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` value Shopify sent.
3. Attacker POSTs that identical body and HMAC value to the victim app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body)`, using code at: [5](#0-4) 
   The check passes since the body is unmodified; `WebhookMetadata` is constructed with `shop: "victim-shop.myshopify.com"` and handed to the app's handler, which processes attacker-supplied content as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
