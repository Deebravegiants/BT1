### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant event spoofing via HMAC-valid replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC over the raw body only, then dispatches to the app's handler using the `shop` value taken from an **unsigned** HTTP header. The binding the gem should enforce — "the shop identity used for tenant dispatch == the shop whose secret produced the verified HMAC" — is broken because the HMAC signable string never includes the shop domain (or topic/webhook-id).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers that are **not** part of the signed payload: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` (used by `Registry.process`) only recomputes the signature over `verifiable_query.to_signable_string`, i.e. the raw body: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed to the handler, without any check that binds it to the verified body: [5](#0-4) 

Because the shop-domain header sits entirely outside the HMAC's coverage, any request whose *raw body* + *HMAC* pair is valid for the configured `api_secret_key` will pass `HmacValidator.validate` regardless of what `x-shopify-shop-domain` (or `shopify-shop-domain`) says. An unprivileged internet user does not need the secret to obtain such a pair — a legitimate webhook delivery observed once (e.g., delivered to their own dev/trial store using the same app) already carries a valid `(raw_body, hmac)` pair. Replaying that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value produces a request that still satisfies `Utils::HmacValidator.validate`, yet `WebhookMetadata.new(... shop: request.shop ...)` reports whichever shop the attacker put in the header. The equality the gem should enforce and fails to enforce is:
`shop authenticated by HMAC == shop delivered to handler as tenant key`
but the left side doesn't exist — the HMAC authenticates only the body bytes, never the tenant claim.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` (as the docs instruct: "construct a `ShopifyAPI::Webhooks::Request` ... call `Registry.process`") to select which merchant's records to update/delete/notify is exposed to cross-tenant data corruption: an attacker with access to one legitimate webhook payload (from their own installed instance of the app) can cause the app to process/write that event under a victim shop's identity. This satisfies the "cross-tenant access" Critical impact category, since the identity binding that keeps one tenant's data isolated from another is broken by the gem's own signature scope, not by host misuse.

### Likelihood Explanation
Moderate-to-high: obtaining one valid `(raw_body, hmac)` pair requires only installing the app on the attacker's own shop (a normal, unprivileged action — many apps are free to install on a dev store), and replaying it against the public webhook endpoint with a different shop header requires no secret and no privileged access. The mandatory topics (`shop/redact`, `customers/redact`, `customers/data_request`) and any handler that reads `data.shop` to scope writes are directly reachable this way.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signable payload check, or otherwise cryptographically bind `request.shop` to a value the host app can independently trust (e.g., require the caller to additionally verify the resolved shop against a per-app-installation table using the `webhook_id`/`api_version` GraphQL lookup already used in `Registry.get_webhook_id`), and document that `Registry.process` does not itself guarantee tenant integrity of the `shop` field beyond raw body authenticity.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# captures one legitimate webhook delivery:
raw_body = '{"id":123,"note":"legit payload from attacker shop"}'
hmac     = Base64.encode64(OpenSSL::HMAC.digest("sha256", app_secret, raw_body))
# (app_secret is unknown to the attacker — this pair is captured off the wire,
#  not computed, since Shopify itself signs and delivers it to the attacker's own shop)

spoofed_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => hmac,                     # valid, unmodified
  "x-shopify-shop-domain" => "victim.myshopify.com",   # attacker-controlled, unsigned
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => HmacValidator.validate(req) succeeds (body/hmac untouched)
# => handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", ...))
#    even though the body never originated from victim.myshopify.com
```
