### Title
Webhook Shop/Topic Identity Spoofing via Headers Not Covered by HMAC Signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `ShopifyAPI::Webhooks::Registry.process` are read straight from unauthenticated HTTP headers [2](#0-1) . The binding "HMAC-verified bytes == data acted upon" only holds for the body; the shop/topic identity fields are never included in the signed string, so they can be freely rewritten as long as the attacker possesses one valid `(body, hmac)` pair for their own shop.

### Finding Description
`Registry.process` validates the webhook purely via `Utils::HmacValidator.validate(request)`, then dispatches using `request.topic` for handler lookup and constructs `WebhookMetadata` using `request.shop`, both taken from headers: [3](#0-2) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string` [4](#0-3)  and for `Webhooks::Request` that method returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled from the `shopify-*`/`x-shopify-*` headers with no cryptographic tie to the body: [2](#0-1) 

**Equality that should hold but doesn't:** `hmac_verified(raw_body) == data_used_for_tenant_and_routing_decisions(shop, topic)`. In reality, `hmac_verified(raw_body)` only proves the body is untampered; `shop` and `topic` are independent, attacker-controlled inputs.

**Attack sequence:**
1. Attacker installs the target public app on their own Shopify development/test store (a normal, unprivileged install — no special credential needed beyond being a Shopify merchant).
2. Attacker triggers a legitimate webhook delivery to the app's endpoint (e.g., `orders/create`), capturing the genuine `raw_body` and its correctly computed `x-shopify-hmac-sha256`/`shopify-hmac-sha256` value, both signed with the app's real `api_secret_key` by Shopify.
3. Attacker replays that exact `(raw_body, hmac)` pair to the app's webhook endpoint but rewrites `x-shopify-shop-domain` to a victim shop's domain (and/or `x-shopify-topic` to a different subscribed topic).
4. `HmacValidator.validate` succeeds because the body/hmac pair is genuinely valid; `Registry.process` then invokes the handler with `shop: <victim-domain>` (and/or the wrong topic), even though the body content actually originated from the attacker's own store.

### Impact Explanation
This breaks the tenant identity binding a multi-tenant app relies on: the app's own webhook handler is told (falsely) that data originated from an arbitrary victim shop. Depending on how the hosting app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up the merchant's session/access token, write records, or trigger fulfillment/order logic under that merchant's account), this enables cross-tenant data injection/confusion — a Critical-class "cross-tenant access" impact, achievable by any unprivileged party who can install the app on a shop they control.

### Likelihood Explanation
Any Shopify merchant can install a public app and subscribe to at least one webhook topic without special privileges, then capture and replay their own legitimately-signed payload with modified headers against the app's exposed webhook endpoint — no `api_secret_key`, access token, or credential theft is required, only observation of one's own legitimate webhook traffic.

### Recommendation
Bind the identity/routing fields into the HMAC-covered signable content (e.g., include `shop`, `topic`, `webhook_id`, and `api_version` header values in the canonical string that is signed/verified, mirroring how `Oauth::AuthQuery#to_signable_string` includes all identity fields [5](#0-4) ), or, at minimum, document prominently that `shop`/`topic` in `WebhookMetadata` are unauthenticated and must be independently cross-checked (e.g., against an expected shop list or the delivery's registered topic) by host applications before being trusted for tenant-scoped operations.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# Step 1: capture a real webhook delivery to the app endpoint:
raw_body = '{"id":123,"note":"hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # rewritten, not part of the signed content
  "x-shopify-webhook-id" => "any-value",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes (raw_body/hmac genuinely match),
# handler.handle receives shop: "victim-shop.myshopify.com" though the body
# actually came from "attacker-shop.myshopify.com".
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
