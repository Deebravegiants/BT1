## Analysis

The codebase already hardened the exact bug class from the report: `Bonding`, `Zap`, `FeeVault`, and `LPLock` all inherit `Ownable2StepUpgradeable` rather than single-step `OwnableUpgradeable`, and the accompanying test suite (`OwnershipTransfer.t.sol`) explicitly documents and verifies that owner transfers require a `transferOwnership` + `acceptOwnership` handshake to prevent a fat-fingered address from bricking the proxy. [1](#0-0) [2](#0-1) [3](#0-2) 

However, `Bonding.transferCreator` — an unprivileged-reachable function (any current token creator can call it) explicitly listed as in-scope — implements exactly the single-step, no-confirmation ownership-change pattern the report warns about. It sets `info.creator = newCreator` directly with only a zero-address and same-address check, with no acceptance step from `newCreator`: [4](#0-3) 

This role is not cosmetic: `FeeVault.accrue` credits `creatorBalance[creator]` using the `creator` attribution supplied by the depositor (`Zap`, which reads `Bonding.tokenInfo(token).creator`), and only that exact address can later call `FeeVault.claim()` to withdraw the pooled USDC: [5](#0-4) [6](#0-5) 

A creator who mistypes `newCreator` (or passes a contract address incapable of calling `claim()`) irreversibly and permanently reassigns both the launch-time creator role and all *future* fee-attribution rights on that token — there is no `pendingCreator`/`acceptCreator` step and no recovery path. All future `FeeAccrued` credits, and any already-pooled but unclaimed `creatorBalance`, become permanently unclaimable by the original creator and are instead locked at (or drained by, if reachable) the wrong address, with no owner-level override to reverse it.

### Title
Single-step `Bonding.transferCreator` lacks a two-step handshake, permanently misdirecting creator fee rights - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.transferCreator(tokenAddress, newCreator)` reassigns a token's `creator` role — which controls all future `FeeVault` fee attribution and claim rights for that token — in a single irreversible step, unlike every owner-level role in the same codebase (`Bonding`, `Zap`, `FeeVault`, `LPLock` owners), which was deliberately upgraded to `Ownable2StepUpgradeable` to avoid exactly this class of mistake.

### Finding Description
`transferCreator` only checks that `newCreator != address(0)` and `newCreator != info.creator`, then immediately commits the change: [4](#0-3) 
There is no pending-creator staging slot and no acceptance call required from `newCreator`, unlike the pattern the project itself adopted for owner transfers (`transferOwnership` + `acceptOwnership`), whose rationale is documented directly in `Bonding.sol`'s and `FeeVault.sol`'s NatSpec and enforced by `OwnershipTransfer.t.sol`. [1](#0-0) 

`Bonding.tokenInfo(token).creator` is the sole source of truth used by `Zap` to attribute fees when calling `FeeVault.accrue`, and `FeeVault.claim()` pays out strictly to `msg.sender`'s recorded `creatorBalance`: [7](#0-6) [6](#0-5) 

Because `transferCreator` is callable by the current creator with no verification that `newCreator` can actually operate (e.g., call `claim()`), a mistake instantly and permanently redirects the role.

### Impact Explanation
Any already-accrued but unclaimed `creatorBalance` for the token, plus all future accrual from every subsequent buy/sell fee on that token (0.25% creator share per `docs/contracts-scope.md`), becomes permanently unclaimable by the legitimate creator and is locked at (or, if the typo happens to be a valid, unrelated address, stolen by) the wrong address — a direct, permanent freezing/misdirection of creator funds with no recovery path, since there's no owner override to reset `TokenInfo.creator`.

### Likelihood Explanation
High for a fat-finger mistake: `transferCreator` takes a raw address argument with no ENS/checksum-style secondary confirmation, and is a normal, expected creator action (e.g., handing a token off to a DAO/team wallet). A single incorrect digit or copy-paste error is sufficient to trigger irreversible loss, and the project's own comments/tests show the team is aware this exact pattern is dangerous for owner roles yet left this creator-role transfer single-step.

### Recommendation
- **Short term:** Convert `transferCreator` into a two-step process mirroring `Ownable2StepUpgradeable`: add a `pendingCreator[tokenAddress]` slot set by the current creator, and require `newCreator` to call an `acceptCreator(tokenAddress)` function before `TokenInfo.creator` is updated.
- **Long term:** Audit all other single-step, non-`onlyOwner` privileged-role transitions in the codebase for the same footgun and apply a consistent propose/accept pattern.

### Proof of Concept
1. Creator launches a token via `Zap.createToken`, accruing creator fees in `FeeVault` as trades occur (`FeeVault.accrue` credits `creatorBalance[creator]`). [5](#0-4) 
2. Creator calls `Bonding.transferCreator(tokenAddress, newCreator)` intending to move the role to a new team wallet but mistypes `newCreator` (e.g., transposes two hex characters). [4](#0-3) 
3. `TokenInfo.creator` is updated immediately; the original creator has no further access, and `newCreator` (a random/uncontrolled address) is now the sole address `FeeVault.claim()` will pay for that token's past and future accrued fees. [6](#0-5) 
4. There is no function to revert or re-propose the change from the protocol owner or the original creator — the funds are permanently misdirected.

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```
