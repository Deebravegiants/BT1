Found the identity binding break: `ShopifyAPI::Webhooks::Request` computes `shop` from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC (`to_signable_string`) only ever signs the raw request body, never the shop-domain header.

### Title
Webhook shop identity is read from an unauthenticated header not covered by the HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` trusts the `X-Shopify-Shop-Domain` / `Shopify-Shop-Domain` HTTP header to identify which tenant/store a webhook belongs to, but `to_signable_string` (the data actually protected by the `X-Shopify-Hmac-SHA256` signature) is only the raw request body [1](#0-0) [2](#0-1) .

### Finding Description
`Request#hmac` decodes the `X-Shopify-Hmac-SHA256` header and `to_signable_string` returns `@raw_body` verbatim [3](#0-2) [2](#0-1) . `HmacValidator.validate` computes `HMAC-SHA256(client_secret, to_signable_string)` and compares it to the received value using `OpenSSL.secure_compare` [4](#0-3) . This only proves the body bytes were signed by Shopify — it says nothing about the `shop`, `topic`, `webhook-id`, or `api-version` headers, all of which are read directly from attacker-controllable HTTP headers [5](#0-4) .

The identity binding that should hold is:
`shop-domain header == shop that produced/authorized the signed body`

but the code only checks:
`HMAC(secret, raw_body) == signature`

There is no cryptographic linkage between the `shop` value returned by `Request#shop` and the HMAC. This class only performs `include Utils::VerifiableQuery` (defining `hmac` and `to_signable_string`); the actual "is this request valid" check is left entirely to the host application via `HmacValidator.validate(request)` (mirroring the OAuth path in `lib/shopify_api/auth/oauth.rb:64` which does call it). Nothing in this gem forces or documents that `shop` must be treated as untrusted or cross-checked, and any consumer that reads `Request#shop` to look up per-tenant configuration/session immediately after passing HMAC validation is trusting an unsigned header for tenant routing.

### Impact Explanation
If a host application uses `Request#shop` (post-HMAC-validation) to select which merchant's data/session a webhook payload applies to — which is the documented and intended usage pattern for this class — an attacker who has a valid HMAC for **their own shop's** webhook (e.g., because they registered a webhook on their own free/trial store, which is normal and requires no special access) can replay that legitimately-signed body while forging the `X-Shopify-Shop-Domain` header to name a **different** victim shop. Since `shop` is never part of `to_signable_string`, the signature still validates, and the application will process/store attacker-controlled webhook data (order created, product updated, app-uninstalled, etc.) under the identity of a shop the attacker does not control — a cross-tenant data confusion / cross-tenant access primitive.

### Likelihood Explanation
Exploitability requires: (1) a valid HMAC over *some* body, which is trivial to obtain by installing the app on any store or replaying any previously observed webhook, and (2) the host app relying on `Request#shop` after calling `HmacValidator.validate` for tenant identification instead of independently re-verifying the shop against its own record of registered webhook endpoints/shops. This is a realistic and encouraged usage pattern since the gem exposes `Request#shop` as the canonical accessor for the shop domain and never warns that it is unauthenticated relative to the signature.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise cryptographically link them to the verified body — e.g., include `shop-domain` in `to_signable_string`, or require host apps to independently verify that the `shop` header matches a shop associated with the specific registered webhook subscription (not just a passing HMAC check) before trusting `Request#shop` for tenant routing. At minimum, document prominently that `Request#shop`/`topic`/`webhook_id` are **not** covered by the HMAC and must be independently validated against the app's own webhook registration records.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the app there,
# so Shopify sends them legitimately-signed webhooks.
raw_body = '{"id": 1, "malicious": "payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
encoded_hmac = Base64.strict_encode64(valid_hmac)

# Attacker forges the shop-domain header to point at the victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => encoded_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not part of signed data
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, HMAC only covers raw_body
request.shop # => "victim-shop.myshopify.com"  (attacker-controlled, unauthenticated)
```
A host application that does `if HmacValidator.validate(request); process_for_shop(request.shop, request.parsed_body); end` will process attacker-supplied data under the victim's tenant.
