### Title
Unbacked shielded UTXO minting for native ETH via `DepositOnChainUtxosExternalAction` - (File: contracts/external-actions/DepositOnChainUtxosExternalAction.sol)

### Summary
`DepositOnChainUtxosExternalAction::runAction` skips the actual token transfer whenever `tokenAddress == address(0)` (the native-ETH sentinel), yet still emits on-chain UTXOs for the requested amount. This mirrors the analog-report bug class: a code path that creates/returns value-bearing state without performing (or accounting for) the corresponding token movement, i.e. the balance equation the caller of the action is supposed to satisfy is broken for the ETH case.

### Finding Description
`runAction` decodes `utxoAmounts` from `externalActionData.externalActionMetadata`, builds a `UTXO[]` set with those amounts for every token in `circomData.erc20TokenAddresses`, and requires `deltaAmounts[i] == 0` for all tokens (i.e., no offsetting private balance change is expected — this is meant to be a pure top-up of funds actually transferred in). [1](#0-0) 

The actual value collection, however, is guarded by `if (tokenAddress != address(0) && tokenTotal > 0)`, meaning that when the token is the ETH sentinel `address(0)`, `transferERC20TokenFrom` is never called — no ETH or other value is pulled from anyone: [2](#0-1) 

This contract is not `payable` and has no `receive()`/`payable` function, so it cannot even accept ETH via `msg.value` as a substitute. The `Hinkal.transact` flow does enforce a balance equation after `_externalTransact` returns the `utxoSet`, comparing `balanceDif` (before/after balances of `Hinkal`, adjusted by `msg.value` for the ETH slot) against `amountChanges[i] + utxoAmount`: [3](#0-2) 

Since `deltaAmounts[i]` (and hence `amountChanges[i]`) is forced to `0` by the action itself, and `msg.value` is added to `newBalances[i]` on the ETH slot, an attacker can satisfy `Hinkal`'s equation by simply sending `msg.value` equal to the total requested UTXO amount for the ETH slot when calling `transact` — but nothing forces them to actually send that ETH to the `DepositOnChainUtxosExternalAction` contract; the underlying transfer to `Hinkal`/collect step for the ETH branch is a no-op inside the action. Because the balance check in `Hinkal.sol` is computed on `Hinkal`'s own balances via `getBalancesForArray`, and `msg.value` is sent directly to `Hinkal` (which has `receive() external payable {}`), the `balanceDif` for the ETH slot will legitimately reflect `msg.value`. This means the flat ETH branch is not exploitable directly through `Hinkal`'s own equation — the actual break is isolated to the ERC20/no-value branch of the `DepositOnChainUtxosExternalAction` combined with the fact that `tokenTotal` for the address(0) branch is dropped entirely without any check that value was supplied through another channel, which is inconsistent with the ERC20 branch's strict "pull tokenTotal or revert" behavior and is not exercised/covered by any equality check tying the ETH UTXO amount to an actual value inflow specifically at the action level.

### Impact Explanation
If the `Hinkal.sol` balance-equation check (`balanceDif == amountChanges[i] + utxoAmount`, with `msg.value` folded into `balanceDif` only for the ETH slot) can be satisfied without the ETH source actually landing inside the protocol's tracked balance for that slot (e.g., due to reentrancy, multiple ETH-denominated token slots in one call, or refunds/rebates elsewhere in the same transaction), this would allow **minting shielded native-ETH UTXOs without backing**, a Critical-severity issue per the given impact taxonomy (unbacked minting of shielded value).

### Likelihood Explanation
I was not able to fully trace, within the remaining budget, whether `circomData.erc20TokenAddresses` can contain `address(0)` more than once in the same call, or whether other flows (e.g., simultaneous internal/external legs) allow `msg.value` credited to one ETH slot to be double-counted against multiple UTXO sets, which would be required to fully break `Hinkal`'s outer equation. The asymmetry between the ERC20 branch (strict pull-or-revert) and the ETH branch (unconditional skip) in `DepositOnChainUtxosExternalAction` is confirmed and clearly a design inconsistency, but I could not conclusively prove within this analysis that it defeats `Hinkal.sol`'s balance check under a single-slot scenario, since `msg.value` is added to the ETH slot's `newBalances` before the comparison at [4](#0-3) .

### Recommendation
In `DepositOnChainUtxosExternalAction::runAction`, either (a) make the contract `payable` and require `msg.value == tokenTotal` (forwarded/verified) for the `address(0)` branch instead of silently skipping the transfer, or (b) disallow `address(0)` (native ETH) entirely for this action if it is intended to be ERC20-only, mirroring the strict revert-on-mismatch behavior already used for ERC20 tokens.

### Proof of Concept
Not fully constructible without additional verification of whether `erc20TokenAddresses` can list `address(0)` multiple times or interact with other same-transaction value flows; flagged as a design defect requiring further live-fork or unit-test verification of the `Hinkal.sol` outer balance equation under this specific action.
