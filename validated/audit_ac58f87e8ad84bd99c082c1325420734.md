This is a valid, exploitable analog: the webhook HMAC signature only ever covers the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` identity used by the receiving application is read from the unsigned `X-Shopify-Shop-Domain` header, exactly the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" pattern called out in scope.

### Title
Webhook `shop` identity is read from an HTTP header that is not covered by HMAC verification, allowing shop-impersonation of webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [1](#0-0) , but exposes `shop` (the tenant identifier used by host applications to route/authenticate the webhook) by reading it straight out of the `shop-domain` / `x-shopify-shop-domain` header, unauthenticated [2](#0-1) .

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body` [3](#0-2) . `Utils::HmacValidator.validate` (used the same way for OAuth) computes the signature over `to_signable_string` and compares it to the `hmac` value [4](#0-3) . Because `to_signable_string` for webhooks is just the body bytes, the HMAC only binds the body — it says nothing about which shop sent it. Yet `Request#shop` is derived purely from an HTTP header supplied by the caller, with no cryptographic binding to the signed body [5](#0-4) .

The identity binding that should hold is: `shop-domain header == shop that produced the HMAC-signed body`. This is never enforced anywhere in the reviewed code — `shop` is exposed as a plain accessor for host applications to use for tenant routing (e.g., "which merchant's data does this webhook belong to") with the implicit assumption that verifying the HMAC over the body also authenticates the `shop` header, which is false.

### Impact Explanation
An unprivileged attacker who has captured or replayed one legitimately-signed webhook body for **any** shop (their own store, a webhook sample, a leaked payload, etc.) can resubmit that exact body to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` to a **different, victim** shop's domain. Since the HMAC only covers the body, `HmacValidator.validate` will still return `true`, and the host application — trusting `Request#shop` as the authenticated tenant — will process/store the payload under the victim's tenant. This crosses a tenant boundary using data purportedly verified by HMAC, matching the "Critical - cross-tenant access" impact category, since the shop identity that gates tenant-scoped writes is unauthenticated.

### Likelihood Explanation
Likelihood is meaningful but bounded by two factors: (1) the attacker needs at least one validly-signed body (their own webhook traffic satisfies this, since anyone can register a Shopify dev store and receive real signed webhooks for it), and (2) exploitability depends on the host application trusting `request.shop` without independently confirming it against a session or webhook-registration record. Because this is the sanctioned, documented way to read the shop from this gem's `Webhooks::Request` object, many integrators will rely on it directly. This is a real gap in the binding this gem's own API is supposed to provide, not a host-app misuse of an already-documented safeguard.

### Recommendation
Include the shop-identifying header (and ideally `topic`/`webhook-id`) in the signable content, or independently verify that the header value matches a value derivable from/bound to the signed body before exposing it via `Request#shop`. At minimum, the gem's documentation should explicitly warn that `shop` is unauthenticated and must be cross-checked by the host app against known registered shops before being trusted for tenant routing.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` receives a legitimate webhook; attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value (these are valid, non-secret artifacts available to them for their own shop's real webhook).
2. Attacker POSTs the identical body and `X-Shopify-Hmac-Sha256` value to the target app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `HmacValidator.validate(request)`. `to_signable_string` returns only the (untouched) raw body, so the HMAC check passes [1](#0-0) .
4. The app reads `request.shop` and processes the payload as if it belongs to `victim.myshopify.com`, even though the payload was never signed for that shop [2](#0-1) .
