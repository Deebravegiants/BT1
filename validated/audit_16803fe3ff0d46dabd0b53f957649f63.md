### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC-signed payload. `ShopifyAPI::Webhooks::Registry.process` validates only that the raw body's HMAC matches the app's shared `api_secret_key`, then forwards the caller-supplied `shop` header straight to the app's webhook handler as trusted tenant identity. Any actor who can obtain one validly-signed webhook body (e.g., from their own shop where the app is installed) can replay it with an arbitrary `shop-domain` header value and have it accepted as coming from a different shop.

### Finding Description
The webhook signature is computed over the raw body only: [1](#0-0) 

`shop` is read from an unauthenticated header and is not part of `to_signable_string`: [2](#0-1) 

`Registry.process` verifies the HMAC over the request (i.e., over the body) and, once that passes, hands the unauthenticated `request.shop` value directly to the registered handler as the identity of the tenant that "sent" the webhook: [3](#0-2) 

Because `api_secret_key` is a single, app-wide credential (not per-shop), a valid HMAC only proves "some installation of this app produced this body" — it does not bind the body to the `shop-domain` header. This breaks the identity equality that the gem implicitly promises to handler code: `verified_sender_shop == request.shop`. In reality, `verified_sender_shop` (the shop whose install actually produced a body with a valid HMAC) can differ from `request.shop` (the header value trusted and forwarded to the handler), exactly mirroring the report's pattern of a field (`RubiconMarketAddress`) being acted upon while a different, unsynchronized/unverified copy of the identity is what's actually trusted.

### Impact Explanation
An attacker who has the app installed on their own shop (an "unprivileged" tenant relative to any other merchant) can capture one legitimately-signed webhook delivery (raw body + `X-Shopify-Hmac-Sha256`) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to point at a victim shop. `Registry.process` will accept it (HMAC matches, since the body is untouched) and invoke the handler believing the event originated from the victim shop. Depending on how the host application's handler uses `WebhookMetadata#shop` (e.g., to look up/update per-shop state, trigger `app/uninstalled` cleanup, `shop/redact` data deletion, or GDPR compliance topics), this can be leveraged for cross-tenant state corruption or forged compliance/lifecycle events against a shop the attacker does not own.

### Likelihood Explanation
Likelihood is moderate to high: any user of the vulnerable app who has installed it on at least one shop can obtain a validly-signed webhook body from Shopify for that shop, and crafting/replaying an HTTP request with a different `shop-domain` header requires no special access, secrets, or race conditions — only knowledge of the target app's public webhook endpoint and a victim shop domain (which is often discoverable, e.g., `*.myshopify.com`).

### Recommendation
Do not trust the `shop-domain` header as tenant identity based solely on a body HMAC that is shared across all installations of the app. Options:
- Include the shop domain in the value that is HMAC-verified (e.g., verify against the shop associated with a stored, per-shop webhook secret/session rather than the single app-wide `api_secret_key`), or
- Cross-check `request.shop` against an independently known, previously-registered shop/session record before invoking the handler, rejecting webhooks for shops that have no corresponding registered session/installation, or
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant boundary without additional verification by the host application.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) and capture the raw request body `B` and its `X-Shopify-Hmac-Sha256` header `H` (valid because `HMAC(api_secret_key, B) == H`).
2. Send a new HTTP request to the app's webhook endpoint with the same body `B`, the same `X-Shopify-Hmac-Sha256: H`, and `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present); `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `@raw_body`, ignoring the `shop-domain` header: [4](#0-3) 
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with `shop == "victim-shop.myshopify.com"`, even though the actual signed content originated from `attacker-shop.myshopify.com`.
