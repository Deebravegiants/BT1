## Title
Missing zero-check on launch-time `virtualLtReserve` lets a zero-`k` pair be minted, breaking `Pair`'s re-mint guard and letting the entire curve supply be bought for free - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._deployAndSeed` computes the launch-time virtual LT reserve from the paired LT's live `exchangeRate()` and only guards the *upper* bound. It never rejects the case where the division rounds down to zero, exactly mirroring the kernel bug's asymmetric validation (`num_mon > CEPH_MAX_MON` checked, `num_mon == 0` not). Downstream, `Pair.mint` and `Router._computeBuy`/`_computeSell` both silently treat `k == 0` as valid, and `k == 0` is simultaneously used by `Pair.mint` as the "already initialized" sentinel and as the constant-product invariant.

### Finding Description
In `_deployAndSeed`: [1](#0-0) 

`exchangeRate` is only checked for `== 0`, and `virtualLtReserve` is only checked against an *upper* bound (`type(uint112).max / 4`). There is no check that `virtualLtReserve != 0`. Since `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate`, integer division floors to `0` whenever the paired LT's `exchangeRate()` (an externally, live-read, rebasing value — see `docs/contracts-scope.md` "reserve asset is an external BounceTech LT") is large enough relative to the fixed `VIRTUAL_LIQUIDITY_USD` constant.

This zero value is passed straight into `Router.addInitialLiquidity` → `Pair.mint`: [2](#0-1) 

`_pool.k = tokenReserve * assetReserve` becomes `totalSupply * 0 = 0`. This is the same shape as the kernel's `num_mon == 0`: a count/reserve that the protocol implicitly assumes is always non-zero (used later as a divisor and as a guard sentinel) is never actually validated against zero.

The consequence is severe because `k == 0` collides with `Pair.mint`'s own re-entry guard (`if (_pool.k != 0) revert AlreadyMinted();`) and with the buy math in `Router._computeBuy`: [3](#0-2) 

With `k = 0`, `tokensOut = reserveToken - (k / newReserveAsset) = reserveToken` for *any* `amountIn > 0` — the virtual reserve (`totalSupply`, 1B) always exceeds the real pair balance (`curveSupply`, 750M), so the overflow-cap branch triggers on the very first buy. In that branch, `cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken` also evaluates near zero because `k = 0`, and `amountInUsed = cappedReserveAsset - reserveAsset` collapses to `0` (since the launch-time `reserveAsset` is itself `0`). The net effect: `Router.buy` returns `tokensOut = 750M` (the entire real curve supply) for `amountInUsed ≈ 0`.

### Impact Explanation
Any unprivileged trader calling `Zap.buy` (or its permit variant) on such a token after `Bonding.launch()`/`Zap.createToken` completes for that pair can drain the *entire* 750M real curve-token supply for effectively zero LT. This is concrete theft of the curve's intended fair-launch supply and permanently breaks the bonding curve's price discovery and the graduation math built on the `k`-identity (`_launchTimeVirtualLtReserve = Pair.k() / Token.TOTAL_SUPPLY()`, which also evaluates to `0`), corrupting `canGraduate`'s donation-immune accounting for that token going forward. This satisfies the "unbacked token payouts"/"theft of trader/creator funds" bar.

### Likelihood Explanation
Reachability requires only that some allowlisted LT paired via `Zap.createToken({ltAddress, ...})` have (or later drift to, since `exchangeRate()` is a live, rebasing, leverage-compounding value per the protocol's own design notes) an `exchangeRate()` large enough that `VIRTUAL_LIQUIDITY_USD * 1e18 / exchangeRate` floors to `0`. No privileged role, upgrade, or off-chain component is needed — the creator freely picks the LT at `createToken` time, and the check that exists (`ExchangeRateTooLow`, guarding the *high*-virtual-reserve side) has no zero-guarding counterpart, so the asymmetry is a real, standing gap in the validation rather than a purely theoretical one.

### Recommendation
In `Bonding._deployAndSeed`, add an explicit `if (virtualLtReserve == 0) revert ZeroVirtualLtReserve();` immediately after computing `virtualLtReserve`, mirroring the existing `ExchangeRateTooLow` upper-bound check. Defense in depth: `Pair.mint` should not overload `k == 0` as both "uninitialized" and "valid state" — track initialization with a separate boolean/flag so a degenerate `k = 0` mint cannot be produced or misinterpreted downstream, and `Router._computeBuy`/`_computeSell` should explicitly revert if `pair.k() == 0`.

### Proof of Concept
1. Register/select (or wait for) an LT whose `exchangeRate()` is large enough that `(VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate == 0` (e.g. `exchangeRate > VIRTUAL_LIQUIDITY_USD * 1e18`).
2. Creator calls `Zap.createToken({..., ltAddress: <that LT>, ...}, seedUsdcAmount)`; `Bonding.launch` → `_deployAndSeed` computes `virtualLtReserve == 0`, no revert occurs, and `Pair.mint(totalSupply, 0)` sets `_pool.k = 0`.
3. After the anti-snipe delay elapses, any unprivileged trader calls `Zap.buy(tokenAddress, usdcAmount=1, minTokensOut=0, referrer)` with a minimal amount.
4. `Router._computeBuy` returns `tokensOut = curveSupply (750M)` capped by real balance, with `amountInUsed` computed as `0` (or negligible) due to `k = 0` in the capped-branch formula.
5. Trader receives the full 750M real token supply of the curve for ~0 LT, confirmed by asserting `IPair(pair).tokenBalance() == 0` and the trader's token balance equals `curveSupply` immediately after the single buy, with `IPair(pair).assetBalance()` essentially unchanged.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
