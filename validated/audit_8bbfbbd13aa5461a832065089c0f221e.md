### Title
Unchecked ERC20 `transfer()` return value in Tron `IntentGatewayV2` withdraw/sweep paths permanently freezes escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` handler in the Tron fork of `IntentGatewayV2.sol` release escrowed tokens using a raw low-level `.call()` to `IERC20.transfer.selector` and only check that the call did not revert (`success`), never checking the ABI-decoded boolean return value of `transfer()`. This is the exact bug class flagged in the referenced Sherlock finding ("use safeTransfer() instead of transfer()"), and here it is reachable by the relayer delivering an ISMP `RedeemEscrow`/`RefundEscrow`/`SweepDust` message.

### Finding Description
`withdraw()` is invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` message is delivered by the host after proof verification [1](#0-0) . Inside `withdraw()`, for each escrowed ERC20/TRC20 token, the contract does:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` only reflects whether the external call reverted, not whether the token's `transfer()` returned `true`. Many TRC20/ERC20-like tokens (including some deployed on Tron, where this contract specifically runs) return `false` on failure instead of reverting. When that happens, `success` is `true`, so the code proceeds to decrement internal accounting:

```solidity
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

and marks the order as filled/refunded:

```solidity
_filled[body.commitment] = beneficiary;
``` [4](#0-3) 

Since `_filled` is set unconditionally at the top of `withdraw()` before any transfer occurs, and `_orders[...][token]` is decremented regardless of whether tokens actually moved, the escrowed balance is consumed by accounting while the beneficiary never received the tokens. There is no retry path—`RedeemEscrow`/`RefundEscrow` is a one-shot ISMP message keyed by `commitment`, and once `_filled`/`_orders` are updated the funds cannot be re-claimed. The same unchecked pattern also exists in the `SweepDust` branch of `onAccept()` [5](#0-4)  and in the fee-token payout inside `withdraw()` [6](#0-5) .

By contrast, the EVM (non-Tron) version of the intents code consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which reverts on a `false` return, e.g. in `IntentsBase.sol` and `IntentGatewayV2.sol` (EVM) escrow/fill paths [7](#0-6) . The Tron variant diverges from this safe pattern for the withdrawal/sweep code paths specifically.

### Impact Explanation
This results in permanent freezing/loss of escrowed user funds: the intended beneficiary (the user being refunded, or the solver being paid for filling an order) never receives their tokens if the token contract returns `false` instead of reverting on transfer failure (e.g., due to a blacklist, paused state, or non-standard TRC20 implementation), yet the protocol's internal ledger (`_orders`, `_filled`) is updated as if the transfer succeeded. Because `_filled` is set and `_orders` decremented unconditionally, there is no mechanism to retry or reclaim the escrowed tokens — they remain locked in the `IntentGatewayV2` contract forever while the corresponding commitment is marked as already settled.

### Likelihood Explanation
This path is reached by the relayer delivering a normal, authenticated `RedeemEscrow`/`RefundEscrow`/`SweepDust` ISMP message — no privileged or malicious actor is required. The only precondition is that one of the escrowed tokens is a non-fully-ERC20-compliant token that returns `false` on failure rather than reverting, which is a realistic condition on Tron (TRC20 tokens have known non-standard behaviors) and is exactly the scenario `SafeERC20` is designed to guard against elsewhere in this same codebase.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol`, EVM `IntentGatewayV2.sol`, `WrappedHyperFungibleToken*.sol`), so that a token returning `false` causes a revert instead of silently updating escrow accounting without delivering funds.

### Proof of Concept
1. A user escrows a TRC20 token in `IntentGatewayV2` (Tron) as part of an intent order; `_orders[commitment][token] += amount`.
2. The token is one whose `transfer()` implementation returns `false` on failure instead of reverting (a known category of non-standard ERC20/TRC20 tokens, and something explicitly guarded against by `SafeERC20` used elsewhere in this repo).
3. Hyperbridge relays a `RefundEscrow`/`RedeemEscrow` message; `onAccept()` calls `withdraw()`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; the token internally fails the transfer (e.g., balance changed, blacklist, or some other business-logic failure) and returns `false` in `data`, but the call itself does not revert, so `success == true`.
5. `withdraw()` proceeds to decrement `_orders[commitment][token] -= amount` and has already set `_filled[commitment] = beneficiary`, without the tokens ever reaching `beneficiary`.
6. The commitment is now permanently marked filled/refunded and the escrowed tokens are stuck in the contract with no code path to release them to the rightful owner.
