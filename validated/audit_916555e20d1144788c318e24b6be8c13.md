### Title
`onPostRequestTimeout` refund path is gated by `whenNotPaused`, freezing already-burned user funds - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable.onPostRequestTimeout` — the function that re-mints tokens to a user after their cross-chain `send()` message failed to deliver — is gated by the `whenNotPaused` modifier, just like the `send()`/`onAccept()` mint/burn paths that actually create new economic exposure. This mirrors the Sherlock finding: a pause check meant to stop new risky actions is also applied to a pure fund-recovery/collection path, which can trap users' already-burned tokens.

### Finding Description
`send()` burns the caller's tokens and dispatches a cross-chain POST request. If that request times out (never delivered), `onPostRequestTimeout` is the only path that restores the caller's balance: [1](#0-0) 

Both `onAccept` (which mints new tokens on inbound transfers — a genuine risk-creating action that must be pausable) and `onPostRequestTimeout` (which merely restores tokens the user already owned and already had burned) share the same `whenNotPaused` modifier: [2](#0-1) [3](#0-2) 

As in the reported `LibUbiquityPool.collectRedemption()` bug, pausing is a legitimate control for preventing *new* mint/burn stability-affecting operations (`send()`, `onAccept()`), but there is no reason a user's refund of tokens they already burned in a failed send should be blocked by the same flag. The tokens are no longer part of circulating supply once burned; refusing to re-mint them while paused doesn't protect protocol invariants, it only delays/blocks the user from recovering funds that are rightfully theirs.

### Impact Explanation
If the token contract is paused (by the owner, e.g. during an incident response or governance action unrelated to a specific user's pending timeout) while a user has an in-flight `send()` that subsequently times out, that user's `onPostRequestTimeout` call reverts and their burned tokens cannot be re-minted until the contract is unpaused. Since pausing is an owner-controlled, potentially long-lived state (e.g., during a governance dispute, an upgrade window, or an extended security pause), this can result in a prolonged, unjustified freeze of user funds that have no bearing on the reason the contract was paused. This matches the "Medium" categorization of the original report: unfair, avoidable prevention of users from recovering funds they are entitled to.

### Likelihood Explanation
The relayer-delivery pipeline (BEEFY/consensus proof-driven cross-chain delivery) can produce timeouts under ordinary operating conditions (dropped/slow relayers, destination chain congestion, or intentional pausing by governance during volatile periods) — the same period during which an owner might reasonably pause the token. Any owner-invoked `pause()` that coincides with even one pending cross-chain send timeout is sufficient to trigger the freeze, making this readily reachable without any malicious actor, purely through normal use combined with an ordinary admin pause.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout` (and any equivalent pure fund-recovery/refund path), keeping the pause check only on `onAccept`/`send()` and other functions that create new mint/burn exposure. This ensures pausing halts new cross-chain risk without blocking users from recovering tokens that were already removed from supply via a failed prior transfer.

### Proof of Concept
1. User calls `send()`, burning `amount` tokens and dispatching a POST request cross-chain — see the `HyperFungibleTokenUpgradeable` `send` flow feeding `dispatchWithFeeToken`/`onAccept` counterpart at [4](#0-3) .
2. The request times out on the destination (never delivered).
3. Contract owner calls `pause()` for an unrelated reason (e.g., a security incident on a different chain).
4. User (or the relayer on their behalf) submits the timeout proof to trigger `onPostRequestTimeout`; the call reverts due to `whenNotPaused`, at [5](#0-4) .
5. The user's burned tokens remain unrecoverable until the owner unpauses the contract, which may not happen promptly, resulting in an unjustified, temporary freeze of the user's funds.

```text
    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) external override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
```
