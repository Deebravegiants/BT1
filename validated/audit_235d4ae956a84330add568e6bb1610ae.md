### Title
Missing Sanity Checks in `IntentGatewayV2.setParams()` on TRON Allows Irrecoverable Misconfiguration of Escrow Routing - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The TRON deployment of `IntentGatewayV2` initializes its `Params` struct through `setParams()`, which performs **no validation whatsoever** on the incoming struct before committing it to storage, unlike the mainline EVM `IntentGatewayV2`, whose equivalent initialization/update path always runs `_validateParams` before applying new params.

### Finding Description
`setParams()` in the TRON variant is gated only by an admin check and is a one-shot call (it zeroes `_admin` immediately after use), functioning as this contract's de-facto constructor/initializer for cross-chain intent routing: [1](#0-0) 

It writes `_params = p` directly with no checks on `p.host`, `p.dispatcher`, `p.protocolFeeBps`, or any other field.

Contrast this with the mainline EVM `IntentGatewayV2`/`IntentsBase`, where every path that installs or updates `Params` — `initialize()` and `_updateParams()` — first calls `_validateParams(p)`: [2](#0-1) [3](#0-2) 

`_params.host` and `_params.dispatcher` are load-bearing for every subsequent unprivileged operation: `placeOrder()`, `fillOrder()`, and `cancelOrder()` all resolve `host()` and then call `IDispatcher(hostAddr)` for `.host()`, `.feeToken()`, and `.uniswapV2Router()` to route escrow, compute commitments, and dispatch cross-chain messages, as seen in the shared TRON contract logic: [4](#0-3) [5](#0-4) 

Because `setParams()` skips the invariant checks that `_validateParams` enforces elsewhere in the codebase (valid non-zero `host`/`dispatcher` addresses that are actual deployed contracts, `protocolFeeBps` bounded below 10,000, etc.), an operator can set `_params` to a malformed value — e.g. a zero or non-contract `host`, or a `protocolFeeBps` ≥ 10,000 — during the one-shot initialization. Since `setParams` also unconditionally clears `_admin` to `address(0)` on the same call, there is no recovery path: the misconfiguration becomes permanent.

### Impact Explanation
A malformed `host`/`dispatcher` address makes `host()` return an unusable or wrong address, so every subsequent unprivileged `placeOrder`, `fillOrder`, and `cancelOrder` call either reverts (freezing the escrow logic path entirely on that chain) or, if `host` points to a contract that still passes low-level calls, can misroute fee token transfers and Uniswap swaps. A `protocolFeeBps` at or above 10,000 makes the fee-reduction arithmetic in `placeOrder` underflow/revert (`reducedAmount = originalAmount - protocolFee` with `protocolFee >= originalAmount`), permanently blocking escrow of user funds through this gateway instance. Because `_admin` is zeroed by the same call that sets the bad params, there is no privileged path to correct the mistake — this is a permanent freezing of the intents functionality (and any tokens already escrowed become unroutable) rather than a recoverable operational error.

### Likelihood Explanation
This requires the deployment/init transaction for the TRON gateway to be executed with an incorrect `Params` value — an unvalidated one-time configuration mistake, not attacker-controlled input from unprivileged users. However, unlike the mainline EVM gateway (which enforces `_validateParams` on the exact same initialization step), this TRON variant has zero defense-in-depth against such a mistake, and the self-revoking admin makes any error unrecoverable, which is precisely the missing-sanity-check pattern the reference report flags.

### Recommendation
Route `setParams()` through the same `_validateParams` invariant checks used by `IntentsBase._updateParams`/`initialize` in the mainline gateway (non-zero, contract-code `host`/`dispatcher`, `protocolFeeBps < 10_000`, etc.) before committing `_params` and revoking `_admin`, so a bad configuration reverts instead of bricking the contract.

### Proof of Concept
1. Deploy `IntentGatewayV2` (TRON variant) with `admin = A`.
2. `A` calls `setParams(p)` with `p.protocolFeeBps = 10_000` (or `p.host = address(0)`); the call succeeds since there is no validation, and `_admin` is zeroed in the same transaction.
3. Any subsequent `placeOrder` call from an unprivileged user with `order.fees`/protocol-fee-bearing inputs underflows in the fee-reduction loop (`originalAmount - protocolFee` with `protocolFee >= originalAmount`) and reverts, or `host()`-dependent calls fail because `_params.host` is invalid.
4. Because `_admin == address(0)`, `setParams` can never be called again — the gateway instance on that chain is permanently unusable for intent placement/fill/cancel. [1](#0-0)
