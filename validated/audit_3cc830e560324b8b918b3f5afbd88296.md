This confirms the vulnerability. Comparing `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:33-43`), where `shop` is explicitly included in the HMAC-signed string, against `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`), which only returns `@raw_body` — the `shop` identity is derived from an HTTP header (`shopify-shop-domain`/`x-shopify-shop-domain`) that is never included in the HMAC computation.

### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) identity solely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator.validate` only verifies the raw HTTP body bytes against the app's `client_secret`. Because the header is not part of the signed content, the equality the app relies on — "HMAC-verified bytes == the shop attributed to this webhook" — does not hold, allowing a merchant who legitimately receives a validly-signed webhook for their own store to relabel it as belonging to another shop.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` gates all webhook handling on `Utils::HmacValidator.validate(request)` [1](#0-0) . `HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field using the app's `client_secret` [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the literal request body — and nothing else [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` values used downstream are all pulled from HTTP headers via `shopify_header`, none of which are covered by the signature [4](#0-3) . After signature validation succeeds, `Registry.process` passes `request.shop` directly into the `WebhookMetadata` given to the app's handler as the tenant identifier [1](#0-0) .

This is the same bug class as the reference report: a value the code trusts and acts on (there, the burn-multiplier timestamp; here, the `shop` tenant identity) is not covered by the same integrity check (there, the reset omitted duration tracking; here, the HMAC omits the header). Contrast this with `Auth::Oauth::AuthQuery`, which explicitly folds `shop` into `to_signable_string` so the shop cannot be swapped without invalidating the signature [5](#0-4) . `Webhooks::Request` has no equivalent binding.

Because every shop installing the app shares the same global `Context.api_secret_key` used to compute webhook HMACs, any merchant who is a legitimate recipient of a validly-signed webhook (for their own store, or one they can trigger, e.g. via an order/product/customer action in their own shop) possesses a `(raw_body, hmac)` pair that is valid app-wide. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it never inspects the header), and `Registry.process` dispatches the handler with `shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary the app relies on for webhook processing: an app that scopes storage, side effects, or business logic per `shop` (as `docs/usage/webhooks.md` explicitly instructs handlers to do, using `data.shop`) can be made to attribute attacker-controlled webhook content to a different merchant's tenant. This is a cross-tenant integrity/isolation failure introduced directly by this gem's `Request`/`HmacValidator` design — the impact category is cross-tenant access, since data validated as authentic ("really came from Shopify, HMAC-checked") is delivered under an arbitrary, attacker-chosen shop identity.

### Likelihood Explanation
Exploitation requires only being able to trigger any webhook to yourself (any app-installing merchant can do this trivially, e.g. by placing an order or updating a resource that fires a subscribed topic) and the ability to send an HTTP POST with custom headers to the app's public webhook endpoint — no access to `client_secret`, access tokens, or privileged credentials is needed. This is squarely reachable by an unprivileged, already-installed merchant.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-signed content verified by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the header-derived shop to the signed body (e.g., by including it as an HMAC-covered value the way `AuthQuery` does for `shop`), so that swapping the `shopify-shop-domain` header invalidates the signature.

### Proof of Concept
1. Attacker owns/operates `attacker-shop.myshopify.com`, installed on the target app, and triggers a webhook topic they are subscribed to (e.g. `orders/create`), capturing the legitimate raw body `B` and the `shopify-hmac-sha256` header value `H` that Shopify computed with the app's shared `client_secret`.
2. Attacker sends `POST /webhook` to the app with body `B` unchanged, header `shopify-hmac-sha256: H` unchanged, but `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) and finds it matches `H` [3](#0-2) [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` [7](#0-6) , even though the actual signed payload originated from the attacker's own shop.
