### Title
Excess native-token overpayment on `EvmHost.dispatch`/`fundRequest` is permanently stranded in `EvmHost` and not refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all accept `msg.value` and swap it via `swapETHForExactTokens{value: msg.value}(fee, path, address(this), ...)` to obtain the exact `feeToken` amount required. Unlike the sibling contract `IntentGatewayV2.sol`, which captures the router's returned `amounts[0]` (actual ETH spent) and refunds the unspent portion (`msgValue -= amounts[0]` then `_sendValue(msg.sender, msgValue)`), `EvmHost` discards the return value of `swapETHForExactTokens` entirely and never refunds the difference between `msg.value` and the ETH actually consumed by the swap.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 
the swap call's return value (an array containing `[ethSpent, feeTokenReceived]`) is never captured. Because `swapETHForExactTokens` is called for an *exact-out* amount (`post.fee`), any `msg.value` supplied above what the current AMM price requires is refunded by the Uniswap router — but that refund goes to `msg.sender` of the router call, which is `EvmHost` itself, not the original end user. That leftover native token then sits as a balance on `EvmHost` with no bookkeeping tied to who overpaid.

The same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 
and in `fundRequest`: [3](#0-2) 

Contrast this with `IntentGatewayV2.placeOrder`, which does it correctly by tracking spent amount and refunding the excess to `msg.sender`: [4](#0-3) 

`EvmHost` itself has no owner-only "sweep stuck native ETH" or withdraw-native function reachable via `HostManager` — `HostManager.onAccept`'s `Withdraw` action calls `IHostManager(host).withdraw(withdrawParams)`, which (per docs and the fee-refund logic elsewhere in `EvmHost`) only pays out `feeToken()` ERC20 balances, not the contract's native ETH balance. There is no `receive()`/native-sweep path documented for `EvmHost` analogous to `HostManager`'s `receive() external payable {}`. Any native ETH stranded in `EvmHost` from an overpaid `dispatch`/`fundRequest` call therefore has no on-chain recovery mechanism for the original payer, and, per the report's bug class, could plausibly be captured by anyone able to trigger a subsequent operation that moves the host's native balance (e.g., a governance/relayer withdrawal path or any future function that forwards `address(this).balance`), or simply becomes permanently locked ("freezing of funds").

### Impact Explanation
This is directly analogous to the referenced Code4rena finding: value attached to a cross-chain dispatch call (the "airdrop"/prepaid gas equivalent here is the native-to-feeToken swap overpayment) is left as an untracked balance in a shared, publicly-callable contract (`EvmHost`) rather than returned to the payer. Every `dispatch{value: x}` and `fundRequest{value: x}` call where `x` exceeds the exact AMM-quoted cost for `fee`/`amount` leaks funds into `EvmHost`. Given `EvmHost`'s `quote()` (used for fee estimation) is explicitly documented as vulnerable to sandwiching/staleness and callers are told to add safety margin, overpayment via `msg.value` is the expected common case in production, not an edge case — meaning funds are lost on essentially every dispatch that uses the native-token payment rail. This is a protocol-wide, permanent value leak (freezing/loss of user funds) reachable by any unprivileged dispatcher of a POST/GET request or `fundRequest` caller.

### Likelihood Explanation
High. Every user or app dispatching a POST/GET request or funding a request via the native-token payment rail must estimate `msg.value` off-chain (the docs explicitly warn against on-chain `quote()` due to sandwich risk), so slippage/overpayment is routine, not adversarial. No attacker action is required to trigger the loss; the loss occurs automatically whenever `msg.value` exceeds the swap's actual cost, which is guaranteed to happen frequently given price movement between quote-time and execution-time.

### Recommendation
Capture the return value of `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, compute `msg.value - amounts[0]`, and refund the difference to `_msgSender()` (mirroring `IntentGatewayV2._sendValue`), reverting or requiring the `call` to succeed. Additionally, ensure a governance-only sweep for any pre-existing stranded native balance, and add invariant tests (as already exist in `IntentGatewayV2Test.sol`, e.g. `testPlaceOrder_RefundsExcessNativeToken`) for `EvmHost.dispatch`/`fundRequest` to assert overpaid native tokens are always refunded to the caller.

### Proof of Concept
1. Caller calls `EvmHost.dispatch{value: 5 ether}(DispatchPost{fee: 1e18 feeToken, ...})` when the actual Uniswap cost to acquire `1e18` feeToken is only `0.1 ether`.
2. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: 5 ether}(1e18, path, address(this), block.timestamp)` executes; the router refunds `4.9 ether` to `msg.sender` of the router call, i.e., `EvmHost`.
3. `dispatch` never reads the swap's return value nor forwards any refund to the original caller; the `4.9 ether` remains as `address(this).balance` inside `EvmHost` (compare to `evm/src/core/EvmHost.sol:921-932` vs. the correct handling in `evm/src/apps/IntentGatewayV2.sol:375-397`, and the existing test `testFillCrossChain_RefundsSolverExcessNativeToken`/`testPlaceOrder_RefundsExcessNativeToken` in `IntentGatewayV2Test.sol` which prove this exact refund pattern is expected elsewhere but is absent in `EvmHost`).
4. Repeated for every dispatcher paying with native token, the ether accumulates in `EvmHost` with no code path that returns it to payers.
