### Title
Unregistered gateway instance defaults to `address(this)`, allowing forged `RedeemEscrow`/`RefundEscrow` withdrawals - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` resolves the trusted peer-gateway address for a source state machine via `instance()`, but unlike the mainline EVM implementation, it does **not** revert when no deployment has been registered for that chain — it silently falls back to `address(this)`. This fallback is then used directly as the authorization check in `authenticate()`, which gates the ability to release (`RedeemEscrow`) or refund (`RefundEscrow`) escrowed user funds. This is the same class of bug as the TBTC `requestNewKeep` issue: a privileged, fund-controlling code path trusts an attacker-influenced value (`request.from`, encoded by whoever deployed a contract at a given address on a remote/unregistered chain) instead of enforcing that only a properly provisioned, governance-registered peer can invoke it.

### Finding Description
`instance()` in the Tron `IntentGatewayV2` is defined as: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

Contrast this with the equivalent, correctly-hardened logic in the mainline `IntentsBase`/`ExtrinsicIntents` contracts used elsewhere in the repo: [2](#0-1) 

which reverts with `UnknownInstance()` when no deployment is registered, and [3](#0-2) 

which relies on that revert for its `_authenticate` check.

`authenticate()` gates the fund-moving `onAccept` branch: [4](#0-3) 

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        authenticate(incoming.request);
        WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
        return withdraw(body, kind == RequestKind.RefundEscrow);
    }
    ...
```

Registration of a legitimate peer only happens via governance's `NewDeployment` action, dispatched exclusively by Hyperbridge itself: [5](#0-4) 

Because `_instances[keccak256(stateMachineId)]` defaults to `address(0)` for any state machine that has not yet had an explicit `NewDeployment` registered, `instance()` returns `address(this)` for **every unregistered chain**. The `authenticate()` check then only requires `request.from == address(this)` — i.e., that the message on the source chain claims to originate from a module at the exact same address as this gateway. Since `PostRequest.from` is populated by the remote-chain module dispatching the message (any contract deployed there, e.g. via CREATE2 to that specific address before/instead of the real gateway, or on any chain Hyperbridge later onboards where no `NewDeployment` has yet been issued), an attacker who can deploy a contract at that address on some state machine which Hyperbridge's consensus/relayer pipeline recognizes can dispatch an arbitrary `WithdrawalRequest` body with `RedeemEscrow`/`RefundEscrow`, and it will pass `authenticate()` even though it is not the real, governance-approved peer gateway.

### Impact Explanation
`withdraw()` releases escrowed input tokens (and accumulated fees) to an attacker-chosen beneficiary/solver address based on the forged `WithdrawalRequest`, and marks arbitrary order commitments as filled/refunded. This is a direct path to permanent theft of escrowed user funds in the Intent Gateway, analogous in severity to the TBTC keep-ownership takeover: an unprivileged party who is not the legitimate cross-chain peer can trigger privileged fund-release logic reserved for authenticated instances.

### Likelihood Explanation
Exploitability depends on Hyperbridge's ISMP consensus/relayer layer accepting a message from a state machine for which the Intent Gateway has not yet had a `NewDeployment` registered (e.g., a newly onboarded chain, or a chain where governance has not yet executed the registration step, or any chain where the deterministic CREATE2 gateway address has not actually been deployed there yet). Given that `NewDeployment` registration is a manual/sequenced governance action performed per chain, there is a realistic operational window — every time a new state machine is added to Hyperbridge before its gateway peer is registered — during which this default-to-self fallback is exploitable.

### Recommendation
Change `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g., `UnknownInstance()`) when no deployment is registered for the given `stateMachineId`, matching the hardened behavior already present in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_instance()`. Do not allow `authenticate()` to succeed against an implicit `address(this)` default for unregistered source chains.

### Proof of Concept
1. Hyperbridge onboards a new state machine `X` but has not yet dispatched `NewDeployment` to the Tron `IntentGatewayV2` instance for chain `X` (so `_instances[keccak256(X)] == address(0)`).
2. An attacker deploys (or otherwise controls) a module on chain `X` at the exact address of the destination-chain `IntentGatewayV2` (`address(this)` on the destination), or otherwise gets a message accepted by Hyperbridge's consensus/relayer pipeline with `PostRequest.from = address(this)`.
3. Attacker dispatches a `PostRequest` from chain `X` with body `[RequestKind.RedeemEscrow] || abi.encode(WithdrawalRequest{commitment: <victim order commitment>, tokens: <victim's escrowed inputs>, beneficiary: attacker})`.
4. The host delivers this to `onAccept` on the destination `IntentGatewayV2`; `authenticate()` calls `instance(X)`, which returns `address(this)` (default fallback) since no explicit registration exists, matching `request.from`, so authentication passes.
5. `withdraw()` releases the victim's escrowed tokens to the attacker-controlled beneficiary, completing theft of user funds without ever legitimately filling or refunding the order.
