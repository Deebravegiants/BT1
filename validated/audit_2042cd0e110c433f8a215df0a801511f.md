### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content solely from the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers and never included in the signed payload. `Registry.process` validates only the body's HMAC and then forwards the unauthenticated `shop`/`topic`/`webhook_id` values straight to the app's handler. This breaks the intended identity binding: `HMAC(body) == valid` is treated as proof of `(body, shop, topic) all originated together from Shopify`, when in fact only `body` was authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (the body), so the header fields never enter the signature computation: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then dispatches to the handler keyed by the (unauthenticated) `topic`, passing the (unauthenticated) `shop` value into `WebhookMetadata`: [4](#0-3) 

Because Shopify signs webhooks with the app's single, per-app `client_secret` (not a per-shop key), any shop that installs the app can legitimately receive genuinely-signed `(body, hmac)` pairs for its own webhook events. An attacker who installs the target app on a shop they control (a normal, unprivileged action any Shopify merchant can perform) can capture such a valid `(body, hmac)` pair and then replay it directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with an arbitrary victim value. `HmacValidator.validate` still succeeds because it only checks the (unmodified) body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim's shop.

This is the same class of defect as the audited GroupBuy bug: an invariant the code implicitly relies on (`hmac_valid ⇒ shop/topic bound to body`) is not actually enforced by the arithmetic/logic that's supposed to guarantee it — here, the binding is simply absent from the signed data rather than merely imprecise.

### Impact Explanation
Any app relying on this gem's `Webhooks::Registry`/`Request` to determine "which shop this webhook is about" is exposed to cross-tenant impersonation: an attacker-controlled shop can cause the app to process/store data under an arbitrary victim shop identifier, corrupting per-tenant state, triggering victim-scoped side effects (e.g., data sync, billing, notifications) attributed to a shop the attacker never actually controls. This crosses the tenant boundary that HMAC verification is meant to establish, matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any Shopify store (a low-privilege, self-service action) and send a crafted HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — no access to `api_secret_key`, tokens, or other privileged material is needed. The core weakness (header fields excluded from the signed payload) is intrinsic to `Request#to_signable_string`/`Registry.process`, not a misuse of a documented safety contract by the host app, since the gem itself is the one parsing and forwarding these header-derived, unauthenticated values to handlers.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is authenticated, or explicitly document/require callers to independently verify `shop` against their own known list of installed shops before trusting `WebhookMetadata#shop`/`#topic`. At minimum, `Registry.process` should cross-check `request.shop` against a caller-supplied allow-list/session store before invoking handlers, since the raw-body-only HMAC cannot vouch for header-derived routing fields.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, unprivileged).
2. Attacker triggers a benign event (e.g., creates a product) causing Shopify to deliver a genuinely signed webhook to the app's endpoint, with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: products/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
3. Attacker replays this exact `(raw_body, hmac)` pair directly to the app's public webhook URL, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks `hmac` against `raw_body`, which is unmodified.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "products/create", body: <attacker's body>, ...)`, causing the app to act as if the victim shop produced this event.

          received_signature = verifiable_query.hmac
