### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching webhook data to the app's handler, but the HMAC signature computed by `HmacValidator` only binds the raw request body, not the `shop-domain` header that identifies which tenant the webhook belongs to. An attacker who can obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` can replay it with an arbitrary `x-shopify-shop-domain` header and it will still pass validation, causing the app to process/store data under the wrong shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` gates on this HMAC check and then forwards `request.shop` (parsed straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, with no cross-check against the HMAC-covered body) to the app's handler as the authoritative tenant identifier: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header used by handler == shop bound by the HMAC signature`. In this implementation that equality never holds — the header is fully attacker-controllable independent of the signature. The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` as "The shop domain of the webhook", implying it is a verified value: [5](#0-4) [6](#0-5) 

Critically, `api_secret_key` is a single per-app credential shared across every shop that installs the app — it is not per-tenant. Any legitimate webhook delivered to the app (for any shop using the app) is signed with that same key. An attacker who is able to observe/capture one legitimate `(raw_body, x-shopify-hmac-sha256)` pair (e.g., their own store's webhook, or one leaked in logs/proxies) can resend it to the app's webhook endpoint while swapping only the `x-shopify-shop-domain` header to point at a different, victim shop. `HmacValidator.validate` will still accept it because the header is not part of the signed content, and `Registry.process` will dispatch the (attacker-supplied) body to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the tenant/shop binding at the core trust boundary of webhook processing: the gem does not cryptographically bind the `shop` field it hands to application code, despite documenting the check as authenticating "the request." Any multi-tenant app relying on `data.shop` from `WebhookMetadata` to select which shop's records to create/update/delete (a documented and expected usage pattern shown in the gem's own example handler) is exposed to cross-tenant data injection/corruption: an attacker-controlled payload can be attributed to and processed against a different merchant's data scope. This matches the "cross-tenant access" criterion for Critical severity in this scope.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid signed webhook body/HMAC pair signed by the target app's `api_secret_key` — attainable by any merchant who installs the app themselves (they receive real webhooks for their own shop, signed with the app's shared secret) and can freely modify headers on replay, since headers are never covered by the signature. No access to `api_secret_key`, access tokens, or privileged accounts is needed beyond normal app installation as an ordinary merchant/user, which is the expected unprivileged-attacker capability for this class of finding.

### Recommendation
Bind the tenant identity into the HMAC-verified content, or otherwise cryptographically tie the `shop-domain` header to the signed payload before trusting it. Concretely, `VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the `shop`, `topic`, and `webhook_id` header values (in addition to the raw body) into the signed string used for verification, matching how Shopify actually issues webhooks per-topic/per-shop, and/or the library should document explicitly that only body integrity is verified and that header values (including `shop`) must not be treated as authenticated without additional validation (e.g., cross-referencing against the shop for which the webhook was registered).

### Proof of Concept
1. App is installed by Attacker on `attacker-shop.myshopify.com` and by Victim on `victim-shop.myshopify.com`, both served by the same app instance/`api_secret_key`.
2. Attacker triggers any subscribed webhook topic (e.g., `orders/create`) on their own shop and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid, since `H = HMAC-SHA256(api_secret_key, B)`).
3. Attacker resends a POST to the app's webhook endpoint with the same body `B` and the same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged header, and `Registry.process` calls `Utils::HmacValidator.validate(request)`: [7](#0-6) 
Because validation only re-computes the HMAC over `B` (not the shop header), it succeeds, and the handler is invoked with `data.shop == "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's shop — demonstrating the break in the shop-identity binding.
