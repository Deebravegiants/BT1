### Title
Webhook shop attribution not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the HMAC of an incoming webhook request and then trusts the `x-shopify-shop-domain` header as the tenant identity passed to the app's handler, but the HMAC only ever covers the raw request body, never the shop-domain header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `HmacValidator.validate_signature` computes/compares the HMAC solely against that signable string using `Context.api_secret_key` [3](#0-2) . The `shop` value, however, is read independently from the `x-shopify-shop-domain`/`shopify-shop-domain` header via `Request#shop` [1](#0-0) , a value that is not part of the signed bytes at all.

`Registry.process` calls `Utils::HmacValidator.validate(request)` to authenticate the request, then immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header — and dispatches it to the app's registered handler [4](#0-3) . This breaks the intended identity binding: `HMAC(secret, raw_body) == valid` should imply `shop == the tenant that produced raw_body`, but the equality actually enforced is only "some entity that knows `api_secret_key` produced this exact body"; nothing ties that body to the `shop` field the library reports to the handler.

Because `api_secret_key` is a single, static per-app secret shared by Shopify across *every* merchant that installs the app (it is not merchant-specific), any shop that has installed the app can receive genuinely-signed webhook deliveries from Shopify for its own store, then replay that exact `raw_body` + valid HMAC to the app's webhook endpoint while substituting a different value in the `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched and valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop, per the documented handler contract `data.shop` [5](#0-4) .

### Impact Explanation
Per the gem's own documentation, `data.shop` is the trusted tenant identifier host apps are expected to key their session lookups, background jobs, and data mutations on (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) . Since this value is fully attacker-controlled by any shop owner able to trigger a real webhook against their own install (e.g. `app/uninstalled`, `shop/update`, `customers/redact`, etc.), an attacker can cause the handler to process events attributed to an arbitrary victim shop domain — e.g., forcing deletion of the victim's session/access token on `app/uninstalled`, or injecting attacker-controlled body content associated with the victim tenant. This is a cross-tenant identity confusion rooted in the gem's own webhook-processing code, not merely host-application misuse, since the library is what asserts "HMAC valid" as the trust signal while silently exposing an unbound field as the tenant key.

### Likelihood Explanation
Exploitation requires only that the attacker be an ordinary, unprivileged merchant who has installed the public app (a routine, unprivileged action) and can send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers — no access token, `client_secret`, or privileged account is needed, satisfying the in-scope "unpriveleged internet user" bar.

### Recommendation
Include the shop domain (and other Shopify-supplied metadata) within the HMAC-verified surface, or otherwise cryptographically bind `shop` to the signed body — e.g., by computing/validating the signature over a canonical string that incorporates `topic`, `shop`, and `webhook_id` alongside the raw body, rejecting requests where header-derived identity fields are not covered by the signature. At minimum, document prominently that `data.shop` in `WebhookMetadata` is not authenticated by the HMAC and must not be trusted as a tenant key without independent verification (e.g. cross-checking against the shop tied to the originally-registered webhook subscription).

### Proof of Concept
1. Attacker installs the target app on their own store, `attacker.myshopify.com`, and Shopify sends a legitimately signed webhook (e.g. `app/uninstalled`) to the app's callback URL with body `raw_body` and header `x-shopify-hmac-sha256: <valid HMAC of raw_body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this exact `raw_body` and valid HMAC value.
3. Attacker resends an HTTP POST to the same webhook endpoint with the identical `raw_body`/HMAC but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC using the shared `api_secret_key` [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` [8](#0-7) , causing the host app to act (e.g., delete stored session/token, process fake data) against the victim tenant.
