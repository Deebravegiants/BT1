## Title
Webhook `shop` used for tenant routing is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that gets passed to the application's webhook handler from an unauthenticated HTTP header, while the HMAC signature that `HmacValidator` verifies only covers the raw request body. This breaks the binding `hmac-verified bytes == tenant-identifying bytes`, letting anyone who can obtain one valid `(body, hmac)` pair for the app (e.g. a legitimate merchant using the same app) replay it with a forged `shop-domain` header to make the app believe the webhook belongs to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from client-supplied HTTP headers with no cryptographic binding to that signature: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then dispatches the handler using the *unauthenticated* `request.shop`: [4](#0-3) 

The documented integration pattern encourages exactly this trust model — hand the raw headers straight to `Request.new` and call `process`: [5](#0-4) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app can capture a legitimate, correctly-HMAC'd webhook delivered to their own endpoint (same body+hmac are valid for any shop, since the shop is not part of the signed content). That merchant can then re-send the exact same `raw_body`/`hmac` to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker_body, ...)`.

The broken identity equality is: **HMAC-authenticated bytes (`raw_body`) must equal the bytes that determine which tenant (`shop`) the webhook is attributed to** — but `shop` is taken from an unsigned header, not from the signed payload.

### Impact Explanation
This crosses a tenant boundary: an attacker (any shop that has installed the target app) can make the app process forged/replayed webhook data under a different merchant's identity. Since `WebhookMetadata.shop` is what downstream app code typically uses to look up the merchant's stored session/access token and to route data writes (as shown in the gem's own docs example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this can lead to cross-tenant data corruption/injection in the host application — the app will act on attacker-supplied `body` content believing it came from the victim shop. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to be a legitimate (even trial) installer of the target app in order to receive one genuine webhook with a valid HMAC — no leaked secrets or privileged access are needed beyond installing the app, which is normal for any embedded Shopify app used by many independent merchants. The replay itself only requires sending an HTTP POST with a copied body/HMAC and a modified `shop-domain` header, exactly per the gem's documented integration pattern.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind the shop domain to the signature (e.g., verify the shop against the caller's known/registered shop list per delivery endpoint, or require the host app to additionally check that `request.shop` matches an installed/authorized shop before trusting `WebhookMetadata.shop`). At minimum, document explicitly that `request.shop` is not authenticated by the HMAC and must be cross-checked against the app's own shop registry before use.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target Shopify app and receives a legitimate `orders/create` webhook at the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H` (valid, since `H = HMAC(api_secret_key, B)`).
2. Attacker replays an HTTP POST to the same webhook endpoint with body `B` unchanged, `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the host app exactly as documented.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and succeeds.
5. The registered handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it came from the victim shop.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
