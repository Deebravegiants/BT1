This confirms `onlyAllowedRecipient` restricts `runAction` callers to Hinkal itself (whitelisted at init as `_allowedRecipients` [1](#0-0) ), so the entry path is legitimate: Hinkal.transact -> `_externalTransact` -> `EmporiumUpgradeable.runAction`, reachable by any attacker who submits a valid proof for their own UTXOs with `externalActionId` set to Emporium's registered id [2](#0-1) . The attacker fully controls `circomData.externalActionData.externalActionMetadata` (decoded as `EmporiumStack`/`ops`), since the circuit only binds an opaque `calldataHash` to it, not its semantic content [3](#0-2) .

### Title
Emporium CASE 2 lets attacker forge calls to `Hinkal.prooflessDeposit` using Emporium-held token balances via a self-authorized `approve` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 (stateless) branch only blocks `callHinkalWallet`/`doSendToRelay` selectors but never restricts `op.endpoint` to registered external actions or DEX routers, so an attacker can chain two attacker-crafted ops in the same `EmporiumStack`: one that calls `approve(hinkal, X)` on any ERC20 token (executed with `msg.sender == Emporium`), and a second that calls `Hinkal.prooflessDeposit` (again `msg.sender == Emporium`), pulling `X` tokens from Emporium's own balance via `transferFrom` and minting a UTXO to the attacker's own stealth address.

### Finding Description
Equality broken: tokens leaving Emporium's balance and entering Hinkal via `prooflessDeposit` should be conserved as "tokens contributed by the depositor (`msg.sender`) on their own behalf." Instead, `msg.sender` inside `Hinkal.prooflessDeposit` is `Emporium`'s contract address (because Emporium is the low-level caller), so `_handleTransfersFromProoflessDeposit` -> `transferERC20TokenFrom(token, msg.sender=Emporium, address(this), amount)` pulls `amount` from Emporium's own balance/allowance, not the attacker's [4](#0-3) .

The attack path:
1. Attacker submits a valid `Hinkal.transact` proof for their own (possibly trivial/zero) UTXOs, with `externalActionData.externalActionId` = Emporium's registered id and `externalActionMetadata` = an attacker-crafted `EmporiumStack` with two ops.
2. Since CASE 2 is taken (`op.invokeWallet=false` or `signerAddress==0`), the only guard is a selector blacklist on `op.callData`'s leading bytes4 [5](#0-4) ; `op.endpoint` is never checked against `externalActionMap` or any allowlist.
3. Op #1: `endpoint = VICTIM_TOKEN`, `callData = approve(Hinkal, X)`. Executed as `op.endpoint.call(op.callData)`, so `msg.sender` inside the ERC20's `approve` is Emporium, granting Hinkal an allowance of `X` VICTIM_TOKEN from Emporium's balance.
4. Op #2: `endpoint = Hinkal`, `callData = prooflessDeposit([VICTIM_TOKEN], [X], [ATTACKER_STEALTH], [...], false, '')`. This is a plain untrusted call (no proof, no signature) that only runs `performProoflessDepositChecks` (length/positivity checks) [6](#0-5) , then pulls `X` VICTIM_TOKEN from Emporium via the allowance just granted, and mints a shielded UTXO to the attacker's stealth address.
5. Back in `runAction`, the post-call balance-conservation check in the outer loop only inspects tokens present in `circomData.erc20TokenAddresses` [7](#0-6) ; since the attacker's own `circomData.erc20TokenAddresses` for this `transact` call need not include `VICTIM_TOKEN`, the drained balance is never checked and the call succeeds. Even the outer `Hinkal.transact` balance/slippage checks only iterate `circomData.erc20TokenAddresses`, which the attacker also controls and can exclude `VICTIM_TOKEN` from [8](#0-7) .

No existing guard stops this: `performHinkalChecks`, `dimensionsCheck`, `verifyProof`, and `rootHashExists` only validate the attacker's own inputs/UTXOs, not the semantic safety of `externalActionMetadata`'s embedded calls; the CASE 2 selector blacklist covers only `callHinkalWallet`/`doSendToRelay`, missing `approve`/arbitrary calls entirely.

### Impact Explanation
Any ERC20 balance sitting in `EmporiumUpgradeable` (residual dust from prior swaps/batches, unswept protocol/relay fees, or funds left mid-multi-op-execution) can be stolen by any unprivileged attacker and minted as a shielded UTXO under their control. This is theft of protocol/relay held funds and matches at minimum the High severity bar ("theft ... of protocol/relay fees" / "executing calls ... never authorised"); if Emporium is holding user funds in transit between two legs of a batched operation at the time of the attack, it escalates to Critical (theft of in-flight user funds). The exploit is repeatable for every token/every time Emporium holds a nonzero balance, at near-zero attacker cost (one `transact` call with a trivial proof).

### Likelihood Explanation
Preconditions: (1) Emporium must hold a nonzero balance of the target ERC20 at attack time — plausible given multi-op batches, rounding, dust, or fee accumulation are an expected part of Emporium's design (note the explicit "balance before the call" handling in `runAction`'s comments) [9](#0-8) ; (2) attacker needs a valid ZK proof for their own (possibly zero-value) UTXO transaction — fully within attacker capability per the threat model. No privileged role, relay whitelisting, or victim cooperation is required (relay can be `address(0)`, satisfying `performHinkalChecks`'s `originalSender==sender` branch). This is a low-cost, deterministically repeatable attack whenever the precondition balance exists.

### Recommendation
In `EmporiumUpgradeable.runAction` CASE 2, restrict `op.endpoint` to a governance-controlled allowlist (e.g., registered DEX routers/external actions) instead of only blacklisting two selectors, and/or forbid `op.endpoint == hinkal` (and any ERC20 `approve`/`increaseAllowance` selector targeting `hinkal`/relay-controlled spenders) entirely from the stateless path. Additionally, revoke/reset any token approvals granted during a batch before returning from `runAction`, and track per-token balance deltas for **all** tokens touched by arbitrary calls (not just `circomData.erc20TokenAddresses`) to detect unauthorized outflows.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (registered as an external action), a mock ERC20 `VICTIM_TOKEN`.
2. Fund `EmporiumUpgradeable` directly with `VICTIM_TOKEN` (simulating residual/protocol balance), assert `VICTIM_TOKEN.balanceOf(emporium) == X`.
3. As attacker, build a valid Circom proof for a trivial `Hinkal.transact` call (`erc20TokenAddresses` excluding `VICTIM_TOKEN`, `externalActionId` = Emporium's id) whose `externalActionMetadata` encodes an `EmporiumStack` with two CASE-2 ops: (a) `endpoint=VICTIM_TOKEN, callData=abi.encodeCall(IERC20.approve,(hinkal, X))`; (b) `endpoint=hinkal, callData=abi.encodeCall(IHinkal.prooflessDeposit,([VICTIM_TOKEN],[X],[attackerStealth],[encOutput],false,""))`.
4. Call `Hinkal.transact(...)`.
5. Assert: `VICTIM_TOKEN.balanceOf(emporium) == 0` (drained) and a new on-chain commitment/UTXO exists in Hinkal's tree spendable by the attacker for `X` `VICTIM_TOKEN` — i.e., assert `tokens leaving Emporium (X) != tokens contributed by attacker's own wallet (0)`, proving the value-conservation equality is broken.
