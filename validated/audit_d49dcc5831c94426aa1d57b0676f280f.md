### Title
POA Bridge withdrawal status is matched by `assetId` only, causing wrong tx-hash/status to be reported for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status of a specific withdrawal solely by matching the response list against `withdrawalParams.assetId`, ignoring `destinationAddress`, `amount`, and the caller-supplied `index`. When a batch withdrawal contains two or more entries for the same `assetId` (a supported and tested scenario), the matcher cannot disambiguate between them, and a withdrawal item can end up reporting a `txHash`/`status` that actually belongs to a different withdrawal in the batch.

### Finding Description
`describeWithdrawal` is: [1](#0-0) 

The comment explicitly states the response list is unsorted and matching is done "by assetId instead of index," and the only argument passed into `findMatchingWithdrawal` is `args.withdrawalParams.assetId`: [2](#0-1) 

Nothing in this matching path checks `withdrawalParams.destinationAddress` or `withdrawalParams.amount`, nor does it correlate against the specific `WithdrawalIdentifier.index`. `WithdrawalIdentifier` is created per-batch-item purely from the caller's own `withdrawalParams` and `index`, without embedding any protocol-level correlation id (such as the POA `transfer_tx_hash`/withdrawal-specific memo) that could disambiguate two withdrawals sharing the same asset: [3](#0-2) 

The SDK explicitly supports batching multiple withdrawals of the identical `assetId` in one intent — this is exercised directly in the test suite (two identical `withdrawalParams` entries with the same `assetId` in one `withdrawalParams` array): [4](#0-3) 

The only regression test covering the actual `findMatchingWithdrawal`/`describeWithdrawal` disambiguation logic uses **two different** `assetId`s (`eth.omft.near` vs `btc.omft.near`) to prove index-independent matching works, but there is no test proving correct behavior when two withdrawals in the same batch share the **same** `assetId` with different `destinationAddress`/`amount`: [5](#0-4) 

Since `watchWithdrawal` polls `describeWithdrawal` independently per batch index and simply forwards whatever `txHash`/`status` is returned: [6](#0-5) 

...two different batch indices for the same asset will resolve to the *same* matched POA record (whichever the underlying `findMatchingWithdrawal` selects first), even though they represent distinct withdrawals to distinct destination addresses/amounts.

This breaks the equality that the report's bug class targets: **a status/txHash reported for withdrawal N must be the on-chain outcome for withdrawal N's own destination and amount**, not an unrelated withdrawal's outcome that merely shares the same token.

### Impact Explanation
If a user or integrator submits a batch withdrawal with two entries of the same `assetId` (e.g., withdrawing the same USDC token to two different addresses, or twice to the same address with different amounts), `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` can report the wrong `txHash` (or a premature "completed" status) for one of the withdrawals. An integrator relying on this API to mark a specific withdrawal record as settled and to release/credit the corresponding off-chain balance could:
- Credit/refund the same destination-chain transaction against two different withdrawal records (double credit), or
- Mark a withdrawal that never landed as "completed" using the txHash of a sibling withdrawal, misleading reconciliation and support tooling.

This matches the High-impact category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Batch withdrawals of the same `assetId` are an explicitly supported, tested pattern in the SDK (identical `withdrawalParams` repeated in an array), so this is not a contrived edge case — any integrator batching several withdrawals of the same token (a very common flow, e.g. paying out multiple users in USDC in one intent) can trigger the ambiguous-match condition. No malicious actor input is required; it is triggered by ordinary usage of the documented batch-withdrawal API.

### Recommendation
Extend the POA withdrawal matching to disambiguate same-asset withdrawals within a batch, e.g. by also matching on `destinationAddress` and `amount` (and any withdrawal-specific memo/identifier the POA API returns), or by consuming the POA API's per-request/withdrawal identifier if one exists, instead of relying on `assetId` alone. At minimum, `findMatchingWithdrawal` should be updated to exclude already-consumed entries so that each batch index maps to a distinct POA withdrawal record, and a regression test should be added covering multiple same-`assetId` withdrawals with differing destination addresses/amounts within one batch.

### Proof of Concept
1. Submit a batched withdrawal intent with two `withdrawalParams` entries, both `assetId: "nep141:btc.omft.near"`, but `destinationAddress: A` (amount 100000) and `destinationAddress: B` (amount 50000) respectively.
2. POA bridge processes both, producing two `COMPLETED` records in `getWithdrawalStatus` — record 1 for address A with `transfer_tx_hash: "tx-A"`, record 2 for address B with `transfer_tx_hash: "tx-B"` — both sharing `defuse_asset_identifier`/`near_token_id` equal to `assetId`.
3. `createWithdrawalCompletionPromises` calls `describeWithdrawal` independently for index 0 and index 1, both passing the same `withdrawalParams.assetId` into `findMatchingWithdrawal` (see `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:319-322`).
4. Because matching keys only on `assetId`, both index 0 and index 1 can resolve to the same record (e.g., both report `tx-A`), even though withdrawal index 1 was actually destined for address B, causing the SDK caller to falsely believe the withdrawal to B settled via `tx-A`.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
