### Title
`Auth.setPin()` allows unauthenticated PIN takeover with no proof of existing credential - ([File: features/auth-mobile/module/auth.js])

### Summary
The external report describes `initAuctionLauncher()` allowing anyone to call an initializer and become admin because it lacks a check restricting the call to the legitimate deployer/owner. The equivalent unprivileged-access-control gap in hydra is `Auth.setPin()` in `features/auth-mobile/module/auth.js`, which overwrites the wallet's PIN secret without requiring proof of the currently configured PIN (or any other authentication factor), and is exposed as a public SDK API method (`exodus.auth.setPin`) reachable the same way whether or not a PIN is already configured.

### Finding Description
`Auth.setPin` [1](#0-0)  only validates the *format* of the new PIN (length === 6) and then unconditionally calls `this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_PIN_KEY), value)`, replacing any existing PIN. There is no comparison against the previous PIN, no call to `isCorrectPin`, and no check of wallet lock/auth state before performing the write. Contrast this with `Wallet.changePassphrase` in `features/wallet/module/wallet.js`, which explicitly requires and verifies `currentPassphrase` before allowing `newPassphrase` to be set [2](#0-1)  — showing the project's own pattern for this class of operation is to gate re-authentication changes behind proof of the current secret, a pattern `setPin` does not follow.

The `auth` module is registered with `public: true` [3](#0-2) , meaning it is exposed directly on the SDK surface (as documented: `await exodus.auth.setPin('123456')` [4](#0-3) ). SDK/API methods marked `public: true` are exactly the surface that gets flattened and exposed over the cross-process RPC boundary (e.g. `rpc.exposeMethods(sdk)` deep-traverses `api` nodes and exposes them all [5](#0-4) , and `@exodus/sdk-rpc`'s `flattenObject`/`exposeMethods` walks the whole API object tree exposing every leaf function as an RPC-callable method [6](#0-5) ). Any caller able to reach this RPC surface — the UI process, an injected/compromised webview bridge, or any code sharing the message port — can invoke `auth.setPin` with an attacker-chosen value and immediately overwrite the legitimate user's PIN without ever supplying the old one.

### Impact Explanation
Once an attacker overwrites the PIN via `setPin`, `isCorrectPin` will now validate the attacker's chosen PIN [7](#0-6) , giving the attacker a working authentication factor that unlocks the app UI going forward (or locks the legitimate user out of app-level authentication) — a direct authentication-bypass/account-takeover impact rather than only a wallet-lock scenario. Because `setPin` is exposed unconditionally on the public SDK/API surface, and the SDK explicitly deep-flattens and exposes all `public: true` module methods over the RPC transport with no per-method authorization/reauthentication guard visible in this module, this is a concrete unauthorized-authentication-state-change matching the "auth bypass" acceptance criteria in the validation rules.

### Likelihood Explanation
Likelihood is high in any client wiring that connects this module's methods to a process/message boundary less trusted than the background/core process (e.g., through the RPC/webview bridge patterns present in this repo, such as `@exodus/sdk-rpc` and `@exodus/browser-extension-rpc`), since no additional check (current PIN, biometric confirmation, unlocked-state assertion) gates the call within `Auth` itself — the module trusts its caller entirely for this operation, analogous to `initAuctionLauncher` trusting any caller to self-assign the admin role.

### Recommendation
Require proof of the existing credential before allowing `setPin` to overwrite an existing PIN, mirroring the pattern already used in `Wallet.changePassphrase` (require and verify `currentPin` unless no PIN is currently set, i.e., only allow unauthenticated `setPin` on first-time setup). Additionally, ensure this method is not reachable from any RPC/webview boundary without a corresponding unlocked/authenticated-session check enforced at the transport or API layer.

### Proof of Concept
1. Attacker gains access to the RPC/message channel that exposes the SDK's public API surface to the UI/webview process (the same channel used for `exodus.auth.setPin`, per `features/auth-mobile/README.md`).
2. Attacker calls `exodus.auth.setPin('999999')` without ever knowing or supplying the legitimate user's existing PIN.
3. `Auth.setPin` in `features/auth-mobile/module/auth.js` (lines 115-126) validates only the 6-digit format and overwrites `AUTH_KEYSTORE_PIN_KEY` in the keystore, updates `authAtom` to `hasPin: true`, and records a `pin_auth_set` event — with no verification against the prior PIN.
4. `isCorrectPin('999999')` now returns `true`, giving the attacker a working authentication factor for the app, while the legitimate user's original PIN no longer works.

Note: I was not able to trace, within the indexed portions of this repo, the exact production wiring that connects `exodus.auth.setPin` to a specific untrusted-origin RPC transport (e.g., which client apps expose this specific `public: true` module across a webview/extension boundary versus keeping it same-process). This limits certainty about the concrete attacker vantage point in a specific shipped app, though the module-level lack of re-authentication is clearly reproducible and directly analogous to the reported bug class.

export const flattenObject = <T>(obj: T, path: string[] = []): { [name: string]: Fn } => {
  if (typeof obj === 'function') {
    return { [serializePath(path)]: obj as Fn }
  }

  if (typeof obj !== 'object' || !obj) return {}

  return Object.keys(obj).reduce((acc, key) => {
    return { ...acc, ...flattenObject(obj[key as keyof T], [...path, key]) }
  }, {})
}

type ConstructorParams = {
  transport: Transport
  requestTimeout?: number
  serialize?: JsonRPCParams[0]['stringify']
  deserialize?: JsonRPCParams[0]['parse']
}

class RPC extends JsonRPC {
  _emitter = new EventEmitter()

  constructor({ transport, serialize, deserialize, requestTimeout = ms('5m') }: ConstructorParams) {
    super({
      transport,
      requestTimeout,
      parse: deserialize,
      stringify: serialize,
    })
  }

  // @ts-expect-error this overrides the parent method's signature with TS does not allow but which the original JS code did
  exposeMethods(methods: Methods) {
    const current = Object.fromEntries(this._methods)
    const flattenMethods = flattenObject(methods)

    return super.exposeMethods({ ...current, ...flattenMethods })
  }
