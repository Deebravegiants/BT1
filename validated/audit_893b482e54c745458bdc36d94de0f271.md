### Title
Webhook shop/topic identity fields excluded from HMAC signature enable cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines `to_signable_string` to return only the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` fields, however, are pulled directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) and are **not** part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, and then dispatches the handler using the unverified `request.shop` and `request.topic` values: [3](#0-2) 

The identity binding that should hold is: `HMAC-verified bytes == bytes that determine the tenant (shop) the event is attributed to`. Because `to_signable_string` covers only `@raw_body` while `shop` is read from a separate, unsigned header, the equality breaks: the HMAC only proves the *body* was produced with the app's `api_secret_key`; it proves nothing about which shop header accompanied that body.

### Impact Explanation
An attacker who legitimately owns a store where the vulnerable app is installed (an unprivileged, ordinary merchant/tenant of a multi-tenant app) can capture a real, validly-signed webhook delivery that Shopify sends for their own shop (e.g., `orders/create`). Because the app's `api_secret_key` is shared across all installations, that same body + HMAC pair is valid for *any* shop the app is installed on. The attacker can then replay that exact `raw_body`/`hmac-sha256` header pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header value with a victim shop's domain. `HmacValidator.validate` will still pass (it only checks the body signature), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the attacker-chosen victim domain, with data that actually belongs to the attacker's own store — or, depending on how the host app keys its data model by `data.shop`, this lets an attacker inject/attribute their own webhook payload into a victim tenant's record scope. This crosses a tenant boundary using only the attacker's own legitimate app installation, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (if unprivileged) merchant/tenant of the app — a very low bar, since anyone can install a public Shopify app. No access to `api_secret_key`, access tokens, or any other credential is needed; the attacker leverages a webhook body/HMAC pair that Shopify itself generates and delivers to them. The only tooling required is the ability to send a crafted HTTP POST with modified headers, which is trivial. This makes the likelihood high for any app whose webhook handlers key business logic by `data.shop` without independent confirmation.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signed content, or otherwise cryptographically bind them to the verified body (e.g., by having the host validate that the `shop` extracted from the payload body itself — most webhook bodies for shop-level resources include shop-identifying data — matches the header, or by requiring per-shop shared secrets/verification tied to the shop domain). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated header values and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a shop that is already known to be associated with the delivered `webhook_id` via a prior GraphQL lookup).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., creates an order) which causes Shopify to send a webhook to the app's callback URL with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and body `B`.
3. Attacker captures `B` and the valid `hmac-sha256` value.
4. Attacker sends a new POST to the same webhook endpoint with the identical body `B` and `hmac-sha256` header, but with `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only checks `@raw_body`, so `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) returns `true`.
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's own shop, achieving cross-tenant data attribution.
