This confirms the finding: `Transferer` explicitly implements `onERC721Received` [1](#0-0)  so both `EmporiumUpgradeable` and `HinkalWallet` can freely receive Uniswap V3 NFTs during a stateless `op.endpoint.call` inside `runAction`, but nowhere in the contract's balance/UTXO accounting is ERC721 custody ever considered. `handleOut` only compares ERC20/ETH balances before/after the call and mints a UTXO strictly from `balanceChange`, returning a zero-amount (default) `UTXO` if `balanceChange <= 0` [2](#0-1) , and `runAction` only pushes non-zero-amount UTXOs into the returned set [3](#0-2) .

### Title
Minting a Uniswap V3 LP NFT via Emporium leaves the position custody-less with no shielded UTXO representing it - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`/`handleOut` accounts for value transfer strictly via pre/post ERC20/ETH balance deltas of the tokens listed in `circomData.erc20TokenAddresses`. When a stateless op mints a Uniswap V3 (or any ERC721) position to the Emporium/Wallet, the underlying token0/token1 balances used to mint the LP position simply decrease then stay at Emporium wrapped inside the NFT, so `balanceChange` for those tokens is `<= 0` and `handleOut` returns a zero UTXO, silently dropping the victim's claimed value while the NFT itself sits unprotected in the contract.

### Finding Description
The broken equality is: `UTXO_minted_for_victim(token0, token1) == position_value`. Before the call, Emporium holds `token0`/`token1` balances (deposited via the negative `deltaAmountChanges` path in `_externalTransact`, `contracts/Hinkal.sol:247-256`). During the stateless op (`runAction` CASE 2, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:102-113`), the endpoint (e.g. Uniswap V3 `NonfungiblePositionManager.mint`) consumes those balances and mints an ERC721 to Emporium via `onERC721Received` (accepted unconditionally by `Transferer.onERC721Received`, `contracts/Transferer.sol:19-26`). After the call, `balancesAfter[i]` for token0/token1 is at or near zero (funds are now locked inside the NFT position, not as a free ERC20 balance), so in `handleOut` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:162-184`) `balanceChange <= 0` and the function returns a default zero-amount `UTXO` without reverting. `runAction` then simply skips it (`utxoOut.amount > 0` check, lines 148-151), so the victim's proof-authorized transaction returns fewer/zero UTXOs vs. the value it consumed from their shielded balance. Meanwhile the NFT itself is now owned by Emporium (or the ephemeral `HinkalWallet`) with no linkage to any UTXO, nullifier, or leaf — nothing in the Merkle tree, `nullifiers`, or `roots` state references that ERC721 token ID. Any subsequent, unrelated `runAction` call (attacker-crafted `circomData`/stateless op) that calls `positionManager.safeTransferFrom(emporium, attacker, tokenId)` or `collect()` succeeds because there is no access control tying NFT custody to a specific owner UTXO — this is the same underlying custody gap referenced as "Q1" (ERC721 assets held by Emporium/Wallet are unprotected because the contracts only reason about ERC20/ETH balances). `performHinkalChecks`, `verifyProof`, `insertNullifiers`, and the circuit's `inTotal + amountChanges === outTotal` constraint only constrain the *fungible* ERC20/ETH accounting declared in `circomData.erc20TokenAddresses`/`amountChanges`; they have no signal at all for ERC721 token IDs, so none of these guards detect or prevent the divergence.

### Impact Explanation
Critical: the victim's tokens (token0/token1) are consumed by the mint but the resulting value (the LP position) never appears in the shielded balance (UTXO) — value silently disappears from the victim's provable/shielded holdings — and the NFT itself is left unprotected and stealable by any unprivileged attacker (`positionManager.safeTransferFrom` or `collect`), directly draining the victim's position. This is a double failure: no UTXO minted (loss of shielded record for the victim) AND theft of the actual asset by an unrelated party, matching "minting shielded value without backing" / "direct theft of in-flight user funds."

### Likelihood Explanation
Any unprivileged EOA can independently trigger this by crafting `CircomData` with a stateless `EmporiumOperation` op pointing to a Uniswap V3 `NonfungiblePositionManager.mint` (or any ERC721-minting endpoint) and depositing/proving over token0/token1 through the normal `_externalTransact` flow (no special role needed — attacker can be the "victim" in the PoC, or observe it happen to any other Emporium user, then race a second `runAction` to drain the NFT). It is fully repeatable for every LP-style position minted through Emporium and costs only normal deposit + gas.

### Recommendation
Add explicit ERC721 (and ERC1155) accounting to `EmporiumUpgradeable`: track `IERC721.ownerOf`/token-ID deltas per configured NFT collection analogous to the ERC20 balance-diffing in `handleOut`, mint a UTXO (or an equivalent NFT-position commitment) representing the newly custodied position, and gate any subsequent transfer/collect of that NFT behind ownership of the corresponding shielded UTXO/nullifier so an unrelated caller cannot move it out.

### Proof of Concept
1. Foundry test: deploy `EmporiumUpgradeable`, a mock ERC20 pair, and a mock `NonfungiblePositionManager` that pulls token0/token1 and mints an ERC721 to `msg.sender` (Emporium). Deposit token0/token1 into Emporium via `_externalTransact`-equivalent path, then call `runAction` with a stateless op calling `mint`. Assert `handleOut`'s returned UTXO set contains zero entries (or amount `0`) for token0/token1, and assert Emporium's ERC20 balances for token0/token1 are now ~0 while `positionManager.ownerOf(tokenId) == address(emporium)`.
2. Second test: from a different, unrelated EOA, craft a `circomData`/stateless op calling `positionManager.safeTransferFrom(emporium, attacker, tokenId)` (or `collect`) through `runAction`, and assert it succeeds, transferring the NFT/fees to the attacker with no relationship to the original depositor's proof or nullifiers.
