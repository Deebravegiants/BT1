### Title
Webhook `shop` (and other identity headers) are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying that the raw request body matches the `X-Shopify-Hmac-Sha256` header, then hands the handler a `WebhookMetadata` object built from **unauthenticated** headers, most importantly `shop`. Because the HMAC only signs the body — not the `shop-domain`, `topic`, `webhook-id` or `api-version` headers — an attacker who can obtain any one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own shop and triggering a webhook they control the content of) can replay that exact body/HMAC pair while substituting the `shop-domain` header for an arbitrary victim shop. The gem will treat the forged request as authentic and tell the handler it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract requires `hmac` and `to_signable_string`. Its `to_signable_string` only returns the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers with no cryptographic binding at all: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this body-only check as the sole authentication gate, then forwards the **unauthenticated** `request.shop` (and `topic`) straight into the handler as trusted tenant-identifying metadata: [4](#0-3) 

The binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ body)` (or equivalent), so that the shop the handler trusts is the same shop the signature actually vouches for. Instead the code only proves `hmac == HMAC(secret, body)`, i.e. `shop` is a field acted upon (used to key/scope handler-side state per tenant) but not covered by the signature.

Since Shopify webhooks for a given app all use the same app-level `api_secret_key` regardless of which shop delivered them, any shop that has installed the app — including one an attacker fully controls (e.g. a free development store) — can generate a validly-signed `(body, hmac)` pair by triggering a webhook whose body content the attacker can influence (many webhook topics, e.g. `orders/create`, echo attacker-supplied fields back in the body). The attacker then POSTs that exact body and HMAC to the app's webhook endpoint again, but with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still passes because it never looked at that header, and `Registry.process` invokes the handler with `shop: <victim shop>`.

### Impact Explanation
This breaks the tenant boundary that the whole webhook-authentication design exists to protect: the shop identity is supposed to be as trustworthy as the HMAC, but it is fully attacker-controlled. Any host application that uses `request.shop`/`WebhookMetadata#shop` (the documented and expected way to determine which merchant a webhook is for) to scope database writes, cache invalidation, entitlement checks, or state transitions can be made to act on a victim shop's data using content the attacker controls — a cross-tenant access issue. This meets the Critical bar ("cross-tenant access") in the assessed impact categories.

### Likelihood Explanation
Exploitation requires only an unprivileged internet user with any working installation of the target app (trivial to obtain via a free/development store — no leaked credentials, no access token, no `api_secret_key`, no privileged account required), plus the ability to POST an HTTP request with attacker-chosen headers to the app's public webhook endpoint. Both prerequisites are ordinary, unprivileged capabilities, making this highly likely to be exploitable wherever the shop field is trusted by handler logic.

### Recommendation
Include the identity-binding headers in the signed content used for verification (or otherwise cryptographically bind `shop`/`topic` to the payload) before trusting them in `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id`, and `HmacValidator`/`Registry.process` should reject a request if these header values do not match what was signed, rather than accepting an HMAC that only covers the body.

### Proof of Concept
1. Install the target app on an attacker-owned development store (`attacker-shop.myshopify.com`).
2. Trigger a webhook whose body the attacker can influence (e.g. `orders/create` with attacker-chosen note/line-item text) so Shopify sends `POST /webhooks` with a valid `X-Shopify-Hmac-Sha256` for that exact body, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Capture the raw body + HMAC value.
4. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) succeeds because it only checks the body.
6. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, even though the request never actually came from, nor was authorized by, that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
