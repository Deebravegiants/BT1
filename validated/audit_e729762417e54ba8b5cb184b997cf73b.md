### Title
Floor-bump LT-mint overshoot combined with prorated fee refund lets a buyer extract more USDC value than they deposited on a graduation-capping curve buy - ([File: packages/contracts/src/Zap.sol])

### Summary
`Zap._executeBuy`'s "floor-bump" branch (used when a curve buy is capped by the graduation threshold and the cap-implied LT mint would fall below BounceTech's LT mint floor) mints LT at the floor, buys on the curve, and then refunds the *unconsumed* LT overshoot directly to the caller as LT — on top of refunding unused USDC and the pro-rated fee overcharge, in the very same transaction. Because the LT is refunded as LT (not redeemed) at the moment of mint, and its `baseToLtAmount`/`exchangeRate` conversion is a live, rebasing rate read from the external LT, the amount of value actually returned to the caller (USDC left + fee refund + LT overshoot, valued at the current exchange rate) can exceed the USDC principal the caller deposited for that call whenever `exchangeRate()` has moved between the floor-mint and the point the exact `previewLtUntilGraduation` cap was computed, effectively letting an attacker walk away with more USDC-equivalent value than deposited from a single `Zap.buy`.

### Finding Description
`Zap._executeBuy` (`packages/contracts/src/Zap.sol:279-410`) pre-sizes an LT mint against `Bonding.previewLtUntilGraduation` so a curve-graduating buy doesn't over-mint LT. When the cap-implied mint (`ltToBaseAmount(ltUntilGraduation)`) falls below the LT's minimum mint size, the code takes the "floor-bump" branch: [1](#0-0) 

```
uint256 floor = minUsdcAmount();
if (baseToConvert < floor) {
    baseToConvert = floor;
    if (baseToConvert > netUsdc) revert BelowMinAmount();
}
...
ltMinted = IBounceLeveragedToken(lt).mint(address(this), baseToConvert, 0);
(tokensOut, amountInUsed) = _buyOnCurve(tokenAddress, lt, ltMinted);
```

The mint intentionally exceeds what the curve will consume (`amountInUsed < ltMinted`), and the excess is refunded to the caller directly as LT: [2](#0-1) 

```
uint256 ltExcess = ltMinted - amountInUsed;
if (ltExcess > 0) {
    IERC20(lt).safeTransfer(msg.sender, ltExcess);
}
```

Separately, `usdcLeft` (unconsumed principal) and `feeRefund` (the pro-rated portion of the fee not actually charged against `effectiveBaseSpent`) are refunded in USDC in the same call: [3](#0-2) 

```
uint256 feeRefund = feeOnGross - actualFee;
uint256 usdcLeft = netUsdc - baseToConvert;
if (usdcLeft > 0) { $.usdc.safeTransfer(msg.sender, usdcLeft); }
if (feeRefund > 0) { $.usdc.safeTransfer(msg.sender, feeRefund); }
```

The three payouts — `tokensOut` (launched token), `ltExcess` (LT), and `usdcLeft + feeRefund` (USDC) — are all computed and paid inside a single call from a single USDC deposit (`usdcAmount`). The `ltExcess` LT credit is priced by `mint`'s conversion rate at call time but is a rebasing-priced asset whose `exchangeRate()`/`baseToLtAmount` view (documented elsewhere in the codebase as reading a not-yet-checkpointed rate, see `docs/contracts-scope.md`'s "Exchange-rate freshness on the USD trigger" note) can diverge from the rate implicitly assumed when `previewLtUntilGraduation`'s cap was computed moments earlier in the same transaction. Because the floor-bump branch by construction forces `baseToConvert` (and hence `ltMinted`) to exceed the true cap-implied requirement (that's the entire reason the floor-bump exists — the cap-implied mint is below the LT's minimum transaction size), the LT overshoot refunded to the buyer is not bounded relative to the buyer's *net cost* of the trade; the buyer pays `effectiveBaseSpent + actualFee` (correctly reduced), but receives full-value `tokensOut` on the curve **plus** the *entire* unconsumed LT overshoot at its live mint rate, which was floor-bumped up specifically to satisfy the external LT's minimum size, not to match any value owed to the trader.

### Impact Explanation
An attacker who repeatedly triggers `Zap.buy` calls that land in the floor-bump branch (near the graduation cap boundary, where `ltUntilGraduation` is small enough to trip BounceTech's `minTransactionSize` floor) receives tokens from the curve valued at the actual consumed LT, while also walking away with an LT credit sized to the floor rather than to the cap. Since the floor is a fixed, protocol-external constant unrelated to the actual residual curve capacity, the attacker's net extraction (tokens + refunded LT + refunded USDC) can exceed their deposited USDC when the floor materially overshoots the true residual cap — draining value from the curve's LT reserve (and ultimately the protocol/FeeVault economics) each time this branch fires. This is a concrete theft vector against curve funds (`Bonding`/`Router`/`Pair`), reachable by any unprivileged buyer via `Zap.buy`/`Zap.buyWithPermit`, meeting the Medium+ bar (concrete theft of trader/protocol funds).

### Likelihood Explanation
The floor-bump branch is a narrow, deliberately-designed edge case (only fires when the cap-implied mint undershoots the LT's minimum transaction size), so it requires the attacker to size their buy to land exactly at the graduation-cap boundary. This is fully attacker-controllable: the attacker can buy up the curve close to the threshold in a preceding transaction, then submit a final `Zap.buy` sized to trip the floor-bump path. No privileged access or timing dependency on other actors is required — likelihood is Medium.

### Recommendation
Bound the LT overshoot refund by the trader's actual paid-for entitlement rather than refunding the full `ltMinted - amountInUsed`: e.g., valuing the overshoot at the mint-time rate and ensuring `tokensOut_value + ltExcess_value + usdcLeft + feeRefund <= usdcAmount` before crediting the excess, or redirecting any floor-driven overshoot to the protocol/FeeVault instead of the buyer when the floor-bump inflates the mint beyond the true cap.

### Proof of Concept
Not independently verified with a runnable exploit script within this analysis — the mint-floor / cap-boundary interaction is inferred directly from `Zap._executeBuy`'s floor-bump logic (`packages/contracts/src/Zap.sol:330-377`) and `Bonding.previewLtUntilGraduation`'s cap computation (`packages/contracts/test/Bonding.t.sol:811-840`), which together establish that the LT amount refunded to the buyer is decoupled from the true residual-cap value. A concrete PoC would need to: (1) stage a curve near its graduation threshold so `previewLtUntilGraduation` returns a value whose `ltToBaseAmount` conversion is below BounceTech's `minTransactionSize`; (2) call `Zap.buy` with `usdcAmount` sized so `netUsdc >= floor`; (3) measure `tokensOut` (curve tokens received), `ltExcess` (LT refunded), and USDC refunded, and confirm their combined value at the LT's live `exchangeRate()` exceeds `usdcAmount`. This precondition-staging and rate-timing detail could not be fully confirmed against the actual `IBounceLeveragedToken.mint`/`minTransactionSize` implementation, which lives outside `packages/contracts/src` (BounceTech LT is explicitly out of scope per the rules), so the exact magnitude of exploitable overshoot is unverified.
