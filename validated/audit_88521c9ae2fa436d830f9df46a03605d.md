### Title
Webhook `shop` field is unauthenticated and can be spoofed to trigger cross-tenant webhook processing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator` over that body never covers the `shop-domain` (or `topic`/`webhook-id`/`api-version`) headers. `Registry.process` nevertheless trusts `request.shop`, taken straight from the unauthenticated header, when constructing the `WebhookMetadata` handed to the app's handler. This breaks the intended binding `shop_used_for_tenant_dispatch == shop_bound_by_hmac(secret, payload)`.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop` is read from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, while `to_signable_string` (the data the HMAC actually signs, per `VerifiableQuery`) is only `@raw_body`. `Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts the unauthenticated `shop` header to build the metadata delivered to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The gem's own documentation instructs apps to key their business logic (job queues, per-tenant records, mandatory GDPR redact webhooks such as `shop/redact` and `customers/redact`) directly off `data.shop`:
```ruby
def handle(data:)
  puts "Received webhook! ... shop: #{data.shop} ..."
  perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
end
``` [4](#0-3) 

Because the HMAC only signs the raw body, an attacker who legitimately receives one genuine webhook delivery for their own shop (any unprivileged merchant who installs the app can trigger/observe this, e.g., by creating a product to fire `products/create`) obtains a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. The `hmac` value is verifiable independent of which shop domain header is attached. The attacker can then replay the same `raw_body` and `hmac` to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value naming a different (victim) shop. `HmacValidator.validate` still returns `true` because it only checks the body signature, and `Registry.process` dispatches to the handler with `shop` set to the attacker-chosen victim domain.

### Impact Explanation
This directly crosses the tenant boundary that the gem is supposed to protect: an unprivileged internet user (any merchant who can install the app and receive one legitimate webhook) can cause the host application to process webhook data as if it belonged to an arbitrary victim shop. Depending on how the host app is wired (as shown in the gem's own documented usage pattern), this can lead to writing/altering another tenant's records, or falsely invoking the mandatory `shop/redact`/`customers/redact` GDPR handlers against a victim shop, since neither the `shop` header nor the topic/webhook-id/api-version headers are covered by the signature. This qualifies as Critical cross-tenant access.

### Likelihood Explanation
Likelihood is high: any actor who can install the app on their own store (a normal, unprivileged flow for public Shopify apps) can capture one valid `(body, hmac)` pair from their own genuine webhook delivery and immediately replay it with a forged shop header to the app's public HTTP webhook endpoint. No access token, `client_secret`, or privileged credential is required — only the ability to trigger and observe a single webhook for a shop the attacker legitimately controls.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`/`api-version`) header values in the data covered by the HMAC verification, or otherwise cryptographically bind the `shop` value delivered in `WebhookMetadata` to the same signed payload used for HMAC validation, so that `to_signable_string` cannot be satisfied while spoofing the shop header. At minimum, document prominently that `request.shop`/`data.shop` is unauthenticated and must not be trusted for tenant routing without additional verification (e.g., cross-checking against a known, previously-registered shop for that webhook topic/subscription id).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and performs an action that fires a subscribed webhook (e.g. `orders/create`), causing Shopify to POST to the app's webhook endpoint with:
   - Body: `raw_body`
   - Header `X-Shopify-Hmac-Sha256: hmac` (valid HMAC-SHA256 of `raw_body` using the app's real `api_secret_key`)
   - Header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
2. Attacker captures this exact `(raw_body, hmac)` pair (they control the receiving server for their own install, or can sniff their own traffic).
3. Attacker sends a new HTTP request to the same public webhook endpoint with the identical `raw_body` and `hmac` headers, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` reads the unchanged HMAC header, and `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `raw_body`:
```ruby
def to_signable_string
  @raw_body
end
``` [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the request never originated from Shopify for that shop, causing the host app to process/store data under the wrong tenant.
