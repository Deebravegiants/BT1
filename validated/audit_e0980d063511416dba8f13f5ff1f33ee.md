### Title
`IntentGatewayV2.placeOrder` (Tron variant) escrows the CallDispatcher's entire token balance instead of only the funds produced by the predispatch call - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron deployment of `IntentGatewayV2.sol`, the `placeOrder` predispatch path sweeps whatever balance the shared `CallDispatcher` happens to hold for `order.inputs[i].token`, rather than measuring only the amount actually produced by executing `order.predispatch.call`. This is the same root cause as Sherlock M-1 (`MarginTrading._openTrade` depositing `balanceOf(address(this))` instead of isolating swap-acquired funds): any pre-existing balance in the shared contract gets swept and escrowed to whichever order runs next.

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 389-449) executes the predispatch call through `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` and then, for each required input token, does: [1](#0-0) 

```solidity
for (uint256 i; i < inputsLen;) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    uint256 requiredAmount = order.inputs[i].amount;
    uint256 balance;
    ...
    balance = IERC20(token).balanceOf(dispatcher);
    if (balance < requiredAmount) revert InvalidInput();
    transferCalls[i] = Call({
        to: token, value: 0,
        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
    });
    uint256 dust = balance - requiredAmount;
    if (dust > 0) emit DustCollected(token, dust);
    _orders[commitment][token] += reducedInputs[i].amount;
```

There is no "before" snapshot of the dispatcher's balance taken prior to executing the predispatch call, so `balance` reflects *all* tokens sitting in `dispatcher` at that moment — whether they came from this order's swap, from leftover dust of a previous order's predispatch execution, from fee-on-transfer residue, or from any other party's tokens that were transferred into the shared `CallDispatcher` and not yet fully swept out. As long as `balance >= requiredAmount`, the check passes and the *entire* balance is pulled into the gateway, with `requiredAmount` (minus protocol fee) credited to the caller's own escrowed order.

This is structurally identical to the reported bug class: instead of computing `received = balanceAfter - balanceBefore` to isolate funds actually generated by the operation being performed (a swap in the original report, a predispatch call here), the code uses the raw current balance of a shared contract. Notably, the non-Tron production contract at `evm/src/apps/IntentGatewayV2.sol` was hardened against exactly this pattern by snapshotting `balancesBefore` before the predispatch call and computing `received = balanceOf(address(this)) - balancesBefore[i]` (see the `IntentGatewayV2.sol:260-330` fix), confirming this is a known, addressed vulnerability class in this codebase — but the fix was not carried over to the Tron variant.

### Impact Explanation
An attacker can place an order whose `predispatch.call` is a trivial/no-op call (satisfying `order.predispatch.call.length > 0 && order.predispatch.assets.length > 0` with a minimal, even worthless, predispatch asset), and set `order.inputs[i].token` to a token that the shared `CallDispatcher` happens to be holding for unrelated reasons (dust left by a previous order's incomplete sweep, residue from fee-on-transfer tokens, or funds transiently parked there by another in-flight cross-chain/calldata flow documented as using the same `CallDispatcher` instance across apps). Because the check only verifies `balance >= requiredAmount` without isolating what this specific predispatch call produced, the attacker's order can be escrowed and later filled/withdrawn using tokens that were never actually contributed by the attacker's own predispatch swap — a permanent, unauthorized appropriation of funds sitting in shared bridge/dispatcher infrastructure.

### Likelihood Explanation
`CallDispatcher` is documented as a persistent, address-book-listed contract reused across order flows and other apps (e.g., HyperFungibleToken calldata execution), which increases the chance of residual balances accumulating there (fee-on-transfer overages, partial sweep failures, race conditions between concurrent predispatch flows). Triggering the bug requires only a single `placeOrder` call with attacker-chosen `order.inputs`/`predispatch` fields — no privileged role, no governance, and no multi-step setup beyond crafting the order — placing it squarely in the reachable "unprivileged intent-order" attack surface.

### Recommendation
Snapshot the dispatcher's balance for each input token before invoking `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, and compute the amount to sweep/escrow as `balanceAfter - balanceBefore`, matching the mitigation already applied in `evm/src/apps/IntentGatewayV2.sol`. Any balance in the dispatcher predating the predispatch call must not be swept into the placing order's escrow.

### Proof of Concept
1. Some prior activity (a partially-completed predispatch sweep, fee-on-transfer token residue, or a stray transfer) leaves token `T` with balance `B` sitting in the shared `CallDispatcher` at address `dispatcher`.
2. Attacker calls `placeOrder` with:
   - `order.predispatch.call` set to a harmless/no-op call and `order.predispatch.assets` containing a minimal (e.g., 1 wei) asset transfer, satisfying the `if` branch condition.
   - `order.inputs[0].token = T`, `order.inputs[0].amount = B` (or any amount ≤ `B`).
3. `placeOrder` executes the no-op predispatch call, then reads `balance = IERC20(T).balanceOf(dispatcher) == B`, passes the `balance >= requiredAmount` check, and sweeps the full `B` into the gateway.
4. `_orders[commitment][T] += reducedInputs[0].amount` credits the attacker's order with (up to) `B` worth of `T`, funded almost entirely by tokens the attacker never provided.
5. The attacker (or a colluding solver) later fills/cancels the order to redeem the escrowed `T`, extracting value that originated from unrelated activity in the shared `CallDispatcher`.
