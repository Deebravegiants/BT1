Webhook `shop` and `topic` identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields that `ShopifyAPI::Webhooks::Registry.process` trusts and forwards to the app's handler are read from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the raw body), never against the header-derived fields: [3](#0-2) 

`Registry.process` then uses these *unauthenticated* header values to select the handler (`@registry[request.topic]`) and to construct the metadata (including `shop:`) that is handed to the app's business logic: [4](#0-3) 

This breaks the identity binding `shop_header == shop_authenticated_by_hmac`: the HMAC only proves the *body bytes* originated from a holder of `client_secret` (e.g. Shopify, or a shop where the attacker legitimately installed the app), but it proves nothing about which shop or topic that body is being attributed to. An attacker who can obtain one valid `(raw_body, hmac)` pair — trivially available to them by installing the app on their own shop and receiving a legitimate webhook — can replay that exact body/HMAC pair while substituting arbitrary `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header values. `HmacValidator.validate` will still return `true` because it only checks the untouched body, and `Registry.process` will happily dispatch that forged shop/topic combination to the app's real handler.

### Impact Explanation
This allows cross-tenant identity confusion: a handler that trusts `WebhookMetadata#shop` (as the docs and gem's own `Webhooks::Registry` design intend it to) can be made to process attacker-supplied body content while being told it belongs to an arbitrary victim shop domain, and/or under an arbitrary topic of the attacker's choosing. Depending on how the host app persists or acts on webhook data keyed by `shop`, this enables writing, redacting, or otherwise mutating data attributed to a tenant the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
The prerequisite is modest: the attacker needs any one valid `(raw_body, hmac)` pair for the app's `client_secret`. This is trivially obtainable by any unprivileged internet user who installs the app on a shop they control (a normal, unprivileged flow) and observes a legitimate webhook delivery. No access to the app's `client_secret`, access tokens, or the victim's credentials is required to forge the spoofed shop/topic combination afterward.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signable content, or otherwise cryptographically bind them to the signed body, so that `HmacValidator.validate` fails if any of these attacker-controllable, unauthenticated headers are altered relative to what was actually signed by Shopify.

### Proof of Concept
1. Install the app on an attacker-controlled shop `attacker.myshopify.com` and trigger any subscribed webhook topic (e.g. `products/update`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid for that exact body under the app's `client_secret`.
2. Replay that exact `raw_body` and `hmac` value to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally change `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (`Request#shop` returns `victim.myshopify.com`, `Request#hmac` decodes the untouched, still-valid signature).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)` — validated against `to_signable_string` (`@raw_body`) — passes.
5. The registered handler's `handle` method is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: <attacker-controlled JSON>, ...)`, i.e., attacker-controlled content is processed under a spoofed shop identity, despite a "valid" HMAC signature.
