### Title
Account enumeration via distinguishable "Invalid email" vs "Invalid password" responses in local session authentication - (File: core/sessions/localauth/orm.go)

### Summary
The `CreateSession` login flow returns two distinct, attacker-visible error messages depending on whether the submitted email exists in the `users` table, allowing an unauthenticated caller to enumerate valid Chainlink node operator accounts — the same bug class as CVE-2018-15131 (Zimbra account enumeration via inconsistent authentication responses).

### Finding Description
In `orm.CreateSession`, after looking up the user by email, the code performs two separate checks and returns two different error strings: [1](#0-0) 
- If the email does not correspond to a stored user (or the constant-time comparison fails), it returns `"Invalid email"`.
- If the email is valid but the password is wrong, it returns `"Invalid password"`.

The `SessionsController.Create` handler forwards this raw error text directly to the HTTP client without normalization: [2](#0-1) 

`jsonAPIError` serializes `err.Error()` into the JSON body, so an unauthenticated POST to `/sessions` with a guessed email will receive `"Invalid email"` for non-existent accounts and `"Invalid password"` for existing accounts — a direct oracle for account existence, mirroring the Zimbra "inconsistent responses for specific types of authentication requests" flaw.

The same pattern is duplicated in the LDAP and OIDC local-fallback authenticators: [3](#0-2) [4](#0-3) 

Note that the code comment in `orm.go` claims the ordering exists "to prevent extra database look up for MFA tokens leaking if an account has MFA tokens or not" [5](#0-4) , but this only addresses MFA-status leakage, not the more basic email/password message distinction, which is still present.

### Impact Explanation
This is a low-severity, unprivileged, internet-facing information disclosure: an anonymous attacker hitting `/sessions` can enumerate which email addresses are registered as Chainlink node API users (admin/edit/run/view roles). This aids targeted credential-stuffing, phishing, or brute-force attacks against confirmed accounts and reveals operational information about which operators/administrators exist on a given node — consistent with CVSS 3.0 5.3 (Medium) for the referenced CVE.

### Likelihood Explanation
High likelihood of exploitation if reachable: the `/sessions` endpoint requires no prior authentication, no rate limiting is evident in the reviewed code path, and the distinguishing text appears directly in the JSON response body on every request, making automated enumeration trivial.

### Recommendation
Return a single generic error message (e.g., `"invalid credentials"`) for both the "email not found" and "password mismatch" branches in `orm.CreateSession`, `ldapAuthenticator.localLoginFallback`, and `oidcAuthenticator.localLoginFallback`, and ensure constant-time/constant-work execution paths for both branches (a dummy password hash comparison should still run when the email doesn't exist, as is already partially done) so that timing does not become a secondary oracle.

### Proof of Concept
1. `POST /sessions` with `{"email":"known-admin@node.example","password":"wrong"}` → response body contains `"Invalid password"`.
2. `POST /sessions` with `{"email":"nonexistent@node.example","password":"wrong"}` → response body contains `"Invalid email"`.
3. Iterating step 1/2 against a wordlist of candidate emails lets an attacker enumerate valid Chainlink node user accounts without any authentication.

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
