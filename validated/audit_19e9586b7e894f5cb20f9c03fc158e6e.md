This confirms the design: `WebhookMetadata.shop` (and `topic`, `webhook_id`, `api_version`) are populated directly from HTTP headers via `Registry.process` at `lib/shopify_api/webhooks/registry.rb:189-199`, using `request.shop` which is read straight from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header in `lib/shopify_api/webhooks/request.rb:20-23`. The HMAC validation performed by `Utils::HmacValidator.validate` only covers `to_signable_string`, which is exclusively the raw request body (`lib/shopify_api/webhooks/request.rb:35-38`), never headers. This is the exact bug class described in the report: a value ("shop") that is acted upon downstream is not the value that is cryptographically bound by the authentication check.

### Title
Webhook shop-identity header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's `WebhookHandler` are all read from HTTP headers rather than from the HMAC-covered body [2](#0-1) , and the signable string used for HMAC computation is exclusively the raw body [3](#0-2) . This breaks the identity binding `authenticated_bytes == acted_upon_bytes`: the `shop` field that downstream handler logic uses to attribute the webhook to a tenant is never part of what the HMAC actually authenticates.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it against the `hmac` field using `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from HTTP headers, not from the signed body [5](#0-4) .

`Registry.process` raises only if the HMAC fails, then immediately constructs a `WebhookMetadata` object using `request.shop` (the unauthenticated header) and dispatches it to the registered handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [1](#0-0) . `WebhookMetadata.shop` is a plain `String` field with no cryptographic binding to the verified body [6](#0-5) .

Because the app's `api_secret_key` is shared across all shops that install the app, any user who can install the app on a shop they control (a normal, unprivileged action) can trigger a genuine webhook delivery for that shop, capture the raw body and its valid HMAC, and then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `Utils::HmacValidator.validate` will still succeed, since it never inspected those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the attacker-chosen body belongs to the victim shop.

The equality that should hold but doesn't:
`shop_bound_by_hmac == shop_used_to_attribute_the_event`
In this gem, the left side is undefined (the HMAC binds nothing about `shop`), while the right side is `request.shop` read straight from an attacker-controlled header.

### Impact Explanation
This is a cross-tenant data injection: a host application that uses `ShopifyAPI::Webhooks::Registry.process` to route webhook data by `data.shop` (the intended and documented usage) will accept attacker-controlled body content under the identity of a shop the attacker does not own, since the gem itself provides no verification that the `shop` header matches the shop whose secret validated the HMAC (there is, in fact, only one shared `api_secret_key`, so any shop-header value is accepted). This can be used to inject forged orders, customer data, GDPR-redaction requests, or other webhook payloads attributed to an arbitrary victim shop, violating tenant isolation guarantees the gem appears to provide via `HmacValidator.validate` and `Registry.process`.

### Likelihood Explanation
Exploitation only requires the ability to install the app on an attacker-controlled shop (or otherwise obtain one valid `(raw_body, hmac)` pair for the shared secret) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — both require no privileged credentials, access tokens, or knowledge of `api_secret_key`. This is a realistic, low-effort attack path for any public/multi-tenant Shopify app using this gem's webhook processing.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) identity to the HMAC-authenticated content, or otherwise cryptographically tie header values to the verified payload before constructing `WebhookMetadata`. At minimum, `Registry.process` should cross-check `request.shop` against a shop that is independently known to have installed the app (e.g., an existing session/shop record) rather than trusting the header as-is once HMAC on the body passes. Consider including the shop domain in the signable string used for HMAC validation, or requiring host apps to validate `request.shop` against session storage before acting on webhook data, and documenting explicitly that the header `shop` value is not covered by the HMAC signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop the attacker controls) and configures a webhook subscription for a topic such as `orders/create`.
2. Attacker triggers the event in their own shop with attacker-chosen data in the body (e.g., a forged order), and captures Shopify's genuine POST request, including `X-Shopify-Hmac-Sha256` and the raw JSON body.
3. Attacker replays the identical POST body and `X-Shopify-Hmac-Sha256` header value to the same webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds (`lib/shopify_api/utils/hmac_validator.rb:13-22`) because it only checks the raw body against the shared `api_secret_key`.
5. `ShopifyAPI::Webhooks::Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and calls the registered handler (`lib/shopify_api/webhooks/registry.rb:188-200`), which now processes attacker-controlled data as if it originated from the victim shop.
