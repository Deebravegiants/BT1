### Title
Local Success Determination Bypasses Backend Signup Confirmation for User-Centric Signups - (File: src/plans/mod.rs)

### Summary
For "user-centric" signups, `MasterPlan::do_signup` never calls `enroll_user::Plan::run` (the code path that actually POSTs the signup to the backend at `/api/v2/signups/{signup_id}` and polls `signup_poll::request` for backend-side confirmation). Instead, success is derived purely from a locally computed `signup_reason`, which itself is derived from a fraud-detection routine that has had all fraud checks removed. This mirrors the `BeraBitcoin.transfer()` bug class: a security-relevant check (here, backend confirmation/anti-fraud/duplicate validation) is asymmetrically applied to one code path (non-user-centric signup) but omitted on the other (user-centric signup), letting an unauthorized/misattributed outcome persist unchecked.

### Finding Description
In `do_signup`, after the biometric pipeline runs, `signup_reason` is computed locally: [1](#0-0) 

and `detect_fraud` (which in this FOSS build has "deleted all fraud checks" and unconditionally returns `false`) feeds directly into that determination: [2](#0-1) 

Success is then branched on `user_centric_signup`: [3](#0-2) 

When `user_centric_signup` is true (and `ignore_user_centric_signups` is not set), the orb marks the signup as `Success` purely because `signup_reason == SignupReason::Normal` — it never invokes `self.enroll_user(...)`, which is the only code path that calls `signup_post::request` (submitting the signup to the backend) and then polls `signup_poll::request` for the backend's authoritative completion/duplicate/fraud verdict: [4](#0-3) 

By contrast, for non-user-centric signups, the `else` branch does call `enroll_user`, which performs the full backend round trip before declaring success. This is the same "check applied to one path, omitted on the sibling path" pattern as the external report: the backend-side authorization/validation (analogous to the recipient blacklist check) is skipped entirely for one class of requests (user-centric signups), while it is enforced for the other.

### Impact Explanation
Because the backend is never asked to confirm the signup for the user-centric path, and the local fraud-check routine is a no-op in this build, a signup can be locally marked `Success`, PCP tiers uploaded, and the UI/dbus events fired to declare a completed signup — without the backend having verified duplicate-iris detection, blacklist state, or any other server-side fraud signal for that specific signup. This can lead to unauthorized or misattributed signups being accepted at the orb level and state (UI completion, uploaded custody packages, relay "SignupEnded" success events) persisting as if the backend had validated the signup, even when the backend never confirmed it. This is a concrete instance of "unauthorized signup" / "cross-signup state bleed" impact scoped to unprivileged end-users going through the ordinary user-centric signup flow (not an operator/node-trust scenario).

### Likelihood Explanation
This code path is reachable by any ordinary end user whose QR code presents `user_centric_signup = true` (a field parsed straight from the scanned/authenticated user QR data) and is not gated behind any operator privilege, hardware access, or test-only feature flag — it runs in the normal `do_signup` flow used in production self-serve and operator-assisted signups alike, so likelihood is high whenever this configuration is active.

### Recommendation
Do not let the local, always-false `fraud_detected` / `signup_reason` computation independently declare `Success` for user-centric signups. Route user-centric signups through the same `enroll_user` backend confirmation call (or an equivalent backend acknowledgment) before setting `enrollment_status` to `Success`, so backend-side duplicate/fraud validation is enforced symmetrically regardless of `user_centric_signup`.

### Proof of Concept
1. Configure/scan a user QR code such that `orb_qr_link::UserData.user_centric_signup == true` (reachable via ordinary QR parsing in `backend::user_status`). [5](#0-4) 
2. Proceed through `do_signup`; since `fraud_check::Report::fraud_checks()` returns an empty array, `detect_fraud` always returns `false`, so `signup_reason` becomes `SignupReason::Normal` as long as the pipeline succeeded. [6](#0-5) 
3. In the `user_centric_signup` branch, `enroll_user` (and therefore `signup_post::request` / `signup_poll::request` backend confirmation) is never invoked; `success` is set to `true` solely from the local `signup_reason`. [3](#0-2) 
4. The orb reports the signup as successful (`debug_report.signup_successful()`, UI completion, `SignupEnded{success: true}` over `orb_relay`) without the backend ever confirming the signup was unique/non-fraudulent. [7](#0-6) [8](#0-7)
