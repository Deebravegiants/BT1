### Title
Arbitrary Emporium `runAction` calls can drain ERC20 balances held by the Emporium contract that are excluded from `circomData.erc20TokenAddresses` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction()` reconciles balance changes only for the token list supplied in `circomData.erc20TokenAddresses`. Any caller can submit their own (self-consistent, even net-zero) shielded proof through `Hinkal.transact()` with `externalActionId` pointing at Emporium, `signerAddress == address(0)` (the unauthenticated "stateless" path), and a token array that deliberately omits a token the Emporium contract happens to hold a balance of. The stateless op-execution branch places essentially no restriction on `op.endpoint.call(op.callData)` (it only blocks the `callHinkalWallet`/`doSendToRelay` selectors), so the attacker can direct Emporium to call `token.transfer(attacker, amount)` on the omitted token. Because that token is absent from `circomData.erc20TokenAddresses`, the before/after balance-reconciliation loop in `runAction` never inspects it, so the transfer is invisible to the balance equation that is supposed to gate every value movement.

### Finding Description
`runAction` computes `balancesBefore`/`balancesAfter` and enforces `balanceChange >= 0` (and mints a corresponding UTXO via `handleOut`) strictly for the tokens listed in `circomData.erc20TokenAddresses`: [1](#0-0) [2](#0-1) 

The arbitrary-call loop that actually executes user-supplied `op.endpoint.call{value: op.value}(op.callData)` only rejects two specific selectors and otherwise performs no allow-list or authorization check when `stack.signerAddress == address(0)`: [3](#0-2) 

`verifyWallet` explicitly skips *all* signature/authorization checks whenever `signerAddress == address(0)`, only marking the `emporiumMessage` nonce as used: [4](#0-3) 

`circomData.erc20TokenAddresses` is fully attacker-controlled data bound only by the prover's own ZK proof over their own inputs/outputs — nothing forces it to include every token the shared Emporium contract happens to hold. Since Emporium is a single shared contract across all users (dust from partial swaps, un-swept leftovers from other users' Emporium interactions, or tokens sent by mistake), any ERC20 balance sitting on it for a token not named in the current caller's `erc20TokenAddresses` array is completely outside the accounting loop. The attacker can therefore call, e.g., `IERC20(dustToken).transfer(attacker, amount)` from Emporium's own context, and this movement is never checked against `balancesBefore`/`balancesAfter` for that token because that token index simply doesn't exist in the iterated array — breaking the invariant that every value movement out of the protocol's shared contracts must be captured in the (`balanceChange`, `deltaAmountChanges`, minted-UTXO) equality.

This is the same root-cause pattern as the referenced Circles finding: a "net-zero"/unauthenticated operation path (here, `signerAddress == address(0)` with attacker-chosen, incomplete `erc20TokenAddresses`) is trusted to leave all balances consistent, but the enforced equality only covers a subset of state (the listed tokens) rather than all value that can be moved by the arbitrary call.

### Impact Explanation
This allows an attacker to permanently steal ERC20 tokens held by the shared `Emporium` contract that belong to other users/the protocol (dust, stuck partial-swap remainders, mistakenly-sent tokens) without needing any wallet signature, without depositing anything backing the withdrawal, and without ever touching the token in the checked balance equation. This is theft of protocol/other-user funds sitting in a shared contract, satisfying the High/Critical impact bar (unauthorized asset movement / theft of funds not backed by any equality check).

### Likelihood Explanation
Likelihood depends on Emporium actually holding a non-zero balance of some ERC20 token outside of an in-flight transaction (e.g., leftover dust from prior swaps/ops, tokens sent directly to the contract, or partially-completed multi-hop Emporium operations). Given Emporium is designed to execute arbitrary DeFi call chains (swaps, LPs, etc.) on behalf of many users, and any imperfect sweep-back leaves a nonzero balance, this is a realistic and low-cost condition for an attacker to wait for or even induce (e.g., via a benign-looking op sequence of their own that leaves 1+ wei behind first), then drain in a follow-up call using a token array that omits the target token.

### Recommendation
Do not allow the stateless (`signerAddress == address(0)`) `runAction` path to execute unrestricted arbitrary calls to unrestricted `op.endpoint` addresses. At minimum:
- Require Emporium to only ever hold a balance for tokens listed in the current `circomData.erc20TokenAddresses` for the duration of an action, or track a Emporium-wide is per-token internal ledger so leftover balances cannot be silently reachable by unrelated callers.
- Alternatively, restrict the stateless path's callable endpoints/selectors to a known allow-list (similar to `onlyAllowedRecipient`), rather than only excluding two selectors.
- Enforce that `balancesBefore`/`balancesAfter` reconciliation covers the full set of tokens actually touched by `op.endpoint.call`, not merely the caller-supplied `erc20TokenAddresses` array, e.g. by disallowing calls to arbitrary ERC20 contracts entirely from the stateless path.

### Proof of Concept
1. Emporium contract accumulates a balance of `TokenX` from any prior interaction (dust/leftover from a multi-hop swap, or another user's incomplete Emporium op, or a mistaken transfer).
2. Attacker submits `Hinkal.transact()` with a self-consistent ZK proof for their own (possibly zero) shielded balance, `externalActionId` set to Emporium, `erc20TokenAddresses` containing only tokens irrelevant to `TokenX` (i.e., `TokenX` omitted), and `deltaAmountChanges` net zero for all listed tokens.
3. `circomData.externalActionData.externalActionMetadata` encodes an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation` where `endpoint = TokenX`, `callData = transfer(attacker, amount)`.
4. `verifyWallet` returns immediately with no signature check (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:314-316`).
5. The stateless branch executes `TokenX.call(transfer(attacker, amount))` from Emporium's context — the selector check only blocks `callHinkalWallet`/`doSendToRelay`, so this succeeds (`EmporiumUpgradeable.sol:102-113`).
6. `runAction`'s balance loop only iterates `circomData.erc20TokenAddresses`, which never included `TokenX`, so the drained balance is never checked against any equality and the transaction completes successfully, netting the attacker `amount` of `TokenX` with no corresponding debit anywhere in the protocol's accounting.
