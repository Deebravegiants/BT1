### Title
Donating bought-back tokens to a bonding-curve `Pair` permanently disables the supply-side graduation trigger and freezes curve funds - (File: `packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
`Router._computeBuy`'s overflow-cap logic and `Bonding.canGraduate`'s supply trigger both assume the hard invariant `IPair.tokenBalance() < stored tokenReserve` holds for the life of the curve. That invariant is only maintained because every buy/sell moves both `tokenBalance()` (live `balanceOf`) and `_pool.tokenReserve` (stored) by the same amount. A plain, unprivileged `IERC20.transfer` of the launched `Token` directly into the `Pair` breaks this symmetry: an attacker can buy more than `LP_RESERVE` (250M) tokens off the curve and then donate them straight back to the pair, permanently inverting the gap so that `tokenBalance()` sits above the stored `tokenReserve` for the remainder of the curve's life.

### Finding Description
The virtual-reserve design in `Router.sol`/`Pair.sol` seeds `_pool.tokenReserve = totalSupply` (1B) while only `curveSupply = 750M` real tokens are transferred to the pair, leaving a fixed 250M (`LP_RESERVE`) gap: [1](#0-0) 

Every buy/sell updates `_pool.tokenReserve` and the real `balanceOf` by the identical `tokensOut`/`tokenIn` amount inside `Pair.swap`, so under normal trading the 250M gap between `tokenReserve` and `tokenBalance()` is invariant: [2](#0-1) 

`tokenBalance()` is a live `balanceOf` read, not a stored counter, so it can be inflated independently of `tokenReserve` by any plain ERC20 transfer into the pair: [3](#0-2) 

`Router._computeBuy`'s overflow-cap branch subtracts the (possibly donation-inflated) real balance from the stored reserve, and this subtraction is only safe because of the "virtual reserve always exceeds real balance" invariant that the test suite explicitly documents as being what keeps `cappedReserveToken == 0` (and, in the general case, underflow) unreachable: [4](#0-3) [5](#0-4) 

`Bonding.canGraduate`'s supply-side trigger relies on the same live `tokenBalance()` read reaching exactly zero to fire, and the protocol's own reasoning for this trigger is explicitly to "handle flat/bear markets where $9K [USD trigger] is never reached": [6](#0-5) 

Attack sequence, reachable by any unprivileged trader through public entry points (`Zap.buy` → `Bonding.buy` → `Router.buy`, and a plain `IERC20.transfer` into the `Pair`):
1. Buy `T` tokens off the curve, where `T > LP_RESERVE (250M)`. This is a large but real, self-funded buy - real supply (750M) comfortably allows it. Each buy decrements `_pool.tokenReserve` and `tokenBalance()` by the same `tokensOut`, so the gap `tokenReserve − tokenBalance()` remains `250M` right after the buy.
2. `IERC20(token).transfer(pair, T)` — donate every purchased token straight back to the `Pair`. This restores `tokenBalance()` to its pre-buy level (adding `T` back) while `_pool.tokenReserve` is untouched (it is only mutated by `Pair.mint`/`Pair.swap`, both `onlyRouter`).
3. New gap = `250M − T`, which is **negative** for `T > 250M`, i.e. `tokenBalance()` now permanently exceeds `_pool.tokenReserve`.

Because `Pair.swap` always moves both quantities by the identical amount on every subsequent trade, this inverted gap persists for the rest of the curve's life. The consequence:
- The uncapped buy formula in `_computeBuy` produces `tokensOut` values bounded above by `_pool.tokenReserve` (which asymptotically shrinks toward 0 as `newReserveAsset` grows), while the real `tokenBalance()` is now pinned above that bound by `T − 250M` forever. `tokensOut > realBalance` therefore can never be true again, so the overflow-cap branch is never entered.
- Consequently `IPair.tokenBalance() == 0` (the supply trigger in `canGraduate`) can never be satisfied, because real balance is permanently floored above zero by the donated surplus.
- The token is now permanently unable to graduate via the supply trigger. If the paired LT's `exchangeRate()` never lifts the real raised value above `$9K` (the exact "flat/bear market" scenario the docs say the supply trigger exists for), the token, its curve-raised LT, and the 250M `LP_RESERVE` tokens held in `Bonding` are permanently stuck in `Lifecycle.Curve` — unreachable by `_prepareGraduationLiquidity`/`Router.graduate`, which only run once `canGraduate()` is true.

This is the analog of ALPINE-CVE-2017-7479's class: an unprivileged, in-protocol counter/state manipulation (repeated legitimate operations composed with a "free" side transfer) drives an internal invariant that a security-critical code path assumes to be unbreakable into a state that permanently disables that path, causing denial of service / fund freezing rather than a crash.

### Impact Explanation
Once the gap is inverted, the affected token's curve can never drain via the supply trigger. In market conditions where the LT's `exchangeRate()`-driven USD value of raised LT never crosses the fixed `$9K` threshold, the token is permanently stuck in `Lifecycle.Curve`: the real LT raised on the curve remains locked in the `Pair` (unreachable — only `Router.graduate`, gated behind a successful `canGraduate()`, can drain it), and the 250M `LP_RESERVE` tokens held in `Bonding` for LP seeding can never be released or burned. This is a permanent freeze of trader/creator/LP-bound funds for that token, achievable for the cost of a single large-but-real curve buy plus a free ERC20 transfer.

### Likelihood Explanation
Medium. It requires no privileged role, only standard public calls (`Zap.buy`/`Bonding.buy` and a plain `Token.transfer`), but it does require the attacker to spend real economic value buying more than `LP_RESERVE` (250M, i.e., 1/3 of the curve's real 750M supply) worth of tokens on the curve before donating them back — a non-trivial capital outlay with no direct payout to the attacker other than griefing a specific token's graduation. This bounds it to a griefing/DoS motive (e.g., attacking a competitor's launch, or a paid attack against a project the attacker wants to sabotage) rather than a profit-seeking one, which is consistent with the CVSS 6.5 Medium severity of the source CVE (availability impact, no confidentiality/integrity impact, low privileges, no user interaction).

### Recommendation
Do not rely on the live `IERC20.balanceOf`-derived `tokenBalance()` for both the overflow-cap subtraction in `Router._computeBuy` and the supply-side graduation trigger in `Bonding.canGraduate`. Either:
- Track real curve-token outflow via a stored counter incremented only inside `Pair.swap`/`Pair.transferToken` (mirroring how `_pool.tokenReserve`/`assetReserve` are already tracked), and use that stored counter for both the overflow cap and the supply trigger instead of a live `balanceOf` read, or
- Explicitly sweep/burn any launched-token donations to the pair (symmetric to the existing LT-donation handling) before they can affect `tokenBalance()`, so the "virtual reserve exceeds real balance by exactly `LP_RESERVE`" invariant cannot be inverted mid-curve.

### Proof of Concept
1. `_launchNoSeed()` a token; `_pool.tokenReserve = 1_000_000_000e18`, `Pair.tokenBalance() = 750_000_000e18` (`CURVE_SUPPLY`).
2. Attacker calls `Zap.buy`/`Bonding.buy` with enough LT to buy `T = 260_000_000e18` tokens (`T > LP_RESERVE = 250_000_000e18`, well within the 750M real supply). After the buy: `_pool.tokenReserve = 740,000,000e18`, `Pair.tokenBalance() = 490,000,000e18` — gap still `250,000,000e18`.
3. Attacker calls `IERC20(tokenAddress).transfer(pairAddr, 260_000_000e18)` (a plain, unrestricted ERC20 transfer — no `onlyRouter` gate exists on `IERC20.transfer`). Now `Pair.tokenBalance() = 750,000,000e18` again, but `_pool.tokenReserve` is still `740,000,000e18`. Gap is now `-10,000,000e18` — inverted.
4. From this point on, every subsequent buy moves `tokenReserve` and `tokenBalance()` by the same `tokensOut`, so `tokenBalance()` stays permanently `10,000,000e18` above `tokenReserve`. `Router._computeBuy`'s uncapped `tokensOut` (bounded above by `reserveToken`) can never exceed `realBalance` again, so the `tokensOut > realBalance` branch — and therefore `Bonding.canGraduate`'s `IPair.tokenBalance() == 0` supply trigger — can never fire again for this token.
5. If the paired LT's `exchangeRate()` never drives the USD trigger (`(storedAssetReserve − virtualLtReserve) × exchangeRate ≥ $9K`) above threshold, the token is permanently stuck in `Lifecycle.Curve`, freezing the curve-raised LT in the `Pair` and the 250M `LP_RESERVE` tokens held in `Bonding`.

(Note: I was unable to run this scenario against the actual Foundry test suite in this session — the reasoning is derived from static analysis of `Router.sol`, `Pair.sol`, `Bonding.sol`, and the project's own invariant tests/comments (`GraduationInvariants.t.sol` lines 353-361 explicitly identify the "virtual reserve always exceeds real balance" property as the sole reason the overflow-cap degenerate branch is currently unreachable). A Devin session with repo/test access would be needed to execute this PoC end-to-end and confirm exact numeric behavior, including whether any other guard elsewhere in `Zap.sol`/`Bonding.sol` incidentally blocks this specific buy-then-donate sequence.)

    /// @dev Capped: `amountInUsed` is back-calculated from the K invariant
    ///      (rounded up so the curve never under-charges).
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
