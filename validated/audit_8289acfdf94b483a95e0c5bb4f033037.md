Confirmed: the main EVM `IntentsBase.sol` uses `SafeERC20.safeTransfer` correctly, but the Tron variant `evm/tron/contracts/apps/IntentGatewayV2.sol` uses raw low-level `.call()` with only the boolean success check, ignoring the ABI-decoded return value of `transfer`.

### Title
Unchecked ERC20 return value in escrow withdrawal allows silent transfer failure and permanent fund loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2` contract's `withdraw` function (and its `sweep`-like dust helper) releases escrowed intent tokens using a raw low-level `.call()` to the ERC20 `transfer` function, checking only that the call did not revert (`success`), without decoding/validating the boolean return value the ERC20 standard mandates. Non-conforming or defective ERC20 tokens that return `false` on failure instead of reverting will be silently treated as successful transfers.

### Finding Description
In `withdraw`, escrowed balances are decremented and the order is marked filled regardless of whether the token transfer actually delivered funds: [1](#0-0) 

The pattern `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); if (!success) revert TransferFailed();` only detects a revert; it never inspects the returned `bool` value from `transfer`. Per ERC20, a compliant token can return `false` (without reverting) to signal a failed transfer, and this codebase already acknowledges that class of token elsewhere by using OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the returned boolean, in the equivalent EVM-mainline contract: [2](#0-1) 

The same unchecked pattern also occurs in the fee-redemption path and the dust-sweep path of the Tron contract: [3](#0-2) [4](#0-3) 

`withdraw` is invoked from the relayer-driven fill/refund/`onGetResponse` flows of the intents escrow, so it is reachable by any relayer/solver submitting a valid ISMP proof or GET response for an order commitment, without requiring privileged roles.

### Impact Explanation
Because `_orders[body.commitment][token] -= amount` and `_filled[body.commitment] = beneficiary` execute unconditionally after the (falsely-successful) `call`, the escrow accounting is permanently updated as if funds were paid out even when the token transfer silently failed. This causes:
- Permanent loss/freezing of the escrowed funds — the beneficiary never receives tokens, and the order is marked filled/refunded, so there is no path to retry or reclaim the escrow.
- Loss of protocol fee tokens similarly, since `feeToken.call(...)` is unchecked in the same way.

This matches the "unchecked external call" bug class from the referenced report, but with concrete, high-severity impact (unrecoverable fund loss) specific to Hyperbridge's intents escrow rather than a generic best-practice nit.

### Likelihood Explanation
Likelihood depends on a non-standard ERC20 token being used as an order's input/output/fee asset on the Tron deployment (Tron's TRC20 ecosystem includes several tokens with non-strict-compliant `transfer` implementations that return `false` instead of reverting). Any order settled in such a token will trigger this path during normal `withdraw`/refund processing — no attacker action beyond selecting/using such a token is required, making this readily triggerable in production usage.

### Recommendation
Replace the raw `.call()` + revert-only check with `SafeERC20.safeTransfer` (as already correctly done in `evm/src/apps/intentsv2/IntentsBase.sol`) for all three unchecked transfer call sites: the token loop in `withdraw`, the fee-token transfer in `withdraw`, and the dust-sweep helper, so that both call failure and a `false` return value revert the transaction.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and register a TRC20 token whose `transfer` implementation returns `false` on failure without reverting (e.g., due to insufficient balance/paused state) rather than reverting.
2. A user places an order escrowing that token; escrow amount recorded in `_orders[commitment][token]`.
3. A relayer submits a fill/refund proof; `withdraw` is invoked, calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`.
4. The token's `transfer` returns `false` (e.g., because the gateway's balance is insufficient due to a rounding/state issue) but the low-level call itself does not revert, so `success == true`.
5. `_orders[commitment][token] -= amount` executes, the order is marked filled/refunded, and `EscrowReleased`/`EscrowRefunded` is emitted — but the beneficiary received nothing, and the escrowed tokens remain stuck/unaccounted for in the contract with no recovery path. [5](#0-4)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
