### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop` (tenant identity) directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `to_signable_string` only returns the raw request body. `Utils::HmacValidator.validate` verifies the HMAC over that signable string only, so the `shop` field is never part of what the signature actually authenticates.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
while `shop` is read straight from an attacker-controllable header with no cryptographic binding to it: [2](#0-1) 

`Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates `hmac` against `to_signable_string`, i.e. the body) before dispatching the handler with `request.shop`: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the signature strictly over `verifiable_query.to_signable_string`, never touching header fields such as `shop`: [4](#0-3) 

The resulting `WebhookMetadata.shop` value — which the host app is expected to trust as the tenant identifier to look up shop-scoped data/sessions — is populated directly from this unauthenticated header: [5](#0-4) [6](#0-5) 

Breaking the intended binding as an equality:
`shop used for tenant identification (WebhookMetadata.shop / request.shop)` should equal `shop cryptographically bound by the HMAC`, but the implementation only guarantees `hmac == HMAC(secret, raw_body)`, with no constraint tying `shop` to that HMAC at all. Since the app's `api_secret_key` is shared across every merchant/shop that installs the app, any unprivileged user who is themselves a legitimate installer of the app can observe a genuine `(raw_body, hmac)` pair from a webhook fired for their own shop (e.g., by triggering an order/customer event on their own store) and then POST that identical `raw_body` + `hmac-sha256` header to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim shop's domain). `HmacValidator.validate` will accept it because the body/HMAC pair is genuinely valid — the forged `shop` header is never checked — and the app's registered `WebhookHandler` will be invoked believing the event happened for the victim's tenant.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an attacker-controlled `shop` value, not bound by any authentication, is delivered to the host application as trusted tenant identity. Any app that keys shop-scoped storage, session lookup, or business logic off `WebhookMetadata.shop` (exactly as the gem's own documentation instructs) can be made to write, delete, or process data under a victim shop's identity using an attacker-supplied (but real-webhook-derived) body. This is a cross-tenant confusion vulnerability reachable by any unprivileged user who has (or creates) their own install of the target app — no `api_secret_key`, access token, or privileged access required.

### Likelihood Explanation
Medium-to-High: it requires the attacker to be (or become) a legitimate, low-privilege installer of the same app (trivial for public apps, since installing costs nothing) in order to harvest one valid `(raw_body, hmac)` pair, and then to send a direct HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — both steps require no secrets and are fully within reach of an "unprivileged internet user."

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signable content that `Utils::HmacValidator` verifies for webhook requests, or otherwise cryptographically tie the `shop-domain` header to the HMAC (e.g., compute/verify a signature over `shop-domain + topic + raw_body` rather than `raw_body` alone), so a body/HMAC pair valid for one shop cannot be replayed under another shop's identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (any unprivileged user can do this for a public app).
2. Attacker triggers a normal event (e.g., updates a customer) causing Shopify to deliver a legitimate webhook to the app's callback URL, with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (e.g., via a proxy they control, or by hosting the webhook receiver themselves during testing).
4. Attacker sends a new POST directly to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the HMAC against `raw_body`: [7](#0-6) 
6. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though this event never happened for that shop, causing the host app to act on/against the victim tenant's data.
