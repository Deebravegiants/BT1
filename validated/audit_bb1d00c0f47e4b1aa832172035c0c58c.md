### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature exclusively to the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (tenant identifier), `topic`, `webhook_id`, and `api_version` fields used by `Registry.process` to route and attribute the webhook are all taken unauthenticated from HTTP headers. Because the HMAC never covers these header fields, any party who possesses one validly-signed webhook body/HMAC pair for their own shop can re-submit it with a modified `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header, and the gem will accept it as valid and process it as if it originated from a different shop.

### Finding Description
The intended binding is: **the shop that produced the HMAC-signed bytes == the shop the gem attributes the webhook event to**. The rules in this gem's own logic break that equality:

1. `Request#shop` is `T.cast(shopify_header("shop-domain"), String)` — read straight from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header [4](#0-3) .
2. `Request#to_signable_string` is only `@raw_body` [5](#0-4) , so the shop header, topic header, and webhook-id header are never part of the signed material.
3. `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and does a constant-time comparison against the `hmac` header value [6](#0-5) . This only proves the body bytes were signed by Shopify (or someone possessing the secret) — it says nothing about which shop the header claims to be.
4. `Registry.process` gates entirely on this body-only HMAC check, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and calls the app's registered handler with that unauthenticated `shop` value [7](#0-6) .

Before the request: a legitimate webhook for Shop A arrives with `body=B`, `hmac=HMAC(secret,B)`, `shop-domain=A`. After an attacker's replay: the attacker (any party who has received a legitimate webhook for their own shop, e.g. by installing the app on a shop they control) resends the exact same `body=B` and `hmac=HMAC(secret,B)` but with `shop-domain` header changed to Shop B (`victim`). `HmacValidator.validate` still passes (it only checks the body against the same valid hmac), and `Registry.process` calls the handler with `shop: "victim-shop"` and the attacker-chosen `body`/`topic`. This crosses the tenant boundary: an app that keys any per-shop side effects (e.g., order/inventory updates, redact-request processing, GDPR mandatory topics `shop/redact`, `customers/redact`, `customers/data_request`) off `WebhookMetadata#shop` will act on behalf of, or against, a shop that never sent this data.

### Impact Explanation
This matches the Critical/High "cross-tenant access" impact category: an attacker who is a legitimate merchant/user of the integrating app (i.e., an unprivileged internet user with respect to any other tenant) can cause the app to process fabricated webhook events attributed to an arbitrary other shop domain, without needing that shop's credentials, access token, or `client_secret`. Because the mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) are also routed the same way, this could be leveraged to trigger data-deletion/redaction logic for a victim shop, or corrupt any per-shop state the host app derives from webhook `shop` attribution.

### Likelihood Explanation
Exploitation requires only: (1) being a legitimate app user/merchant capable of generating at least one validly-HMAC-signed webhook body for their own shop (trivial — install the app, trigger any webhook topic), and (2) POSTing that captured body+HMAC to the app's webhook endpoint with a forged `shop-domain` header. No secret key, access token, or privileged access to Shopify is required, and no TLS interception or social engineering is needed — this is a pure unauthenticated-header manipulation against the gem's own header-parsing/HMAC-checking logic.

### Recommendation
Bind the tenant-identifying and routing fields into the signed material, or otherwise require the `shop` used for attribution to be independently authenticated (e.g., verified against session/shop storage the app controls) rather than trusted directly off the header. Concretely:
- Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (mirroring the JSON body the way Shopify's payload commonly already includes `shop_domain`), or
- Have `Registry.process` cross-check `request.shop` against an expected/known shop derived from an authenticated source (e.g., a stored session or an allow-list) before invoking the handler, rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host: "http://example.com",
  scope: "read_products", is_embedded: false, is_private: false, api_version: "2024-01")

body = '{"id":1,"note":"legit webhook for attacker-shop.myshopify.com"}'
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", body)
hmac_b64 = Base64.encode64(hmac_digest)

# Step 1: attacker legitimately receives this webhook for their own shop.
legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: legit_headers)
ShopifyAPI::Utils::HmacValidator.validate(legit_request) # => true (expected)

# Step 2: attacker replays identical body+hmac but claims a different shop.
forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# HMAC check still passes because it only ever validated the body, not the shop header.
ShopifyAPI::Utils::HmacValidator.validate(forged_request) # => true (should be false / shop-bound)
ShopifyAPI::Webhooks::Registry.process(forged_request)
# => handler is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though "victim-shop" never sent this webhook.
```
