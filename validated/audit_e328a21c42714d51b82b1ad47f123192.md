## Title
Escrowed order funds can be permanently locked in `IntentGatewayV2`/`IntentsBase` if the fixed beneficiary is later blocklisted by USDT/USDC - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` (and its Tron-port twin `IntentGatewayV2.withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol`) releases escrowed order tokens to a `beneficiary` address that is fixed at fill/cancel time and baked into the cross-chain `WithdrawalRequest` message. If that fixed beneficiary is later added to the USDT/USDC blocklist before the settlement message is delivered on the source chain, the `safeTransfer` call reverts every time delivery is retried, and the escrowed collateral becomes permanently stuck in the gateway contract, exactly as described in the SolverVault report where a fixed `receiver` cannot be updated once set.

### Finding Description
For a cross-chain order, `ExtrinsicIntents._fill`/`_cancelFromDest` (in `evm/src/apps/intentsv2/ExtrinsicIntents.sol`) stamps the beneficiary of the eventual escrow release as `bytes32(uint256(uint160(msg.sender)))` — the solver that filled the order (or the order's `user` for a refund) — and dispatches a `RedeemEscrow`/`RefundEscrow` POST request carrying that address [1](#0-0) .

When that message is later delivered on the source chain, `IntentsBase._withdraw` transfers the escrowed input tokens directly to this fixed `beneficiary` via `IERC20(token).safeTransfer(beneficiary, amount)`, with no mechanism to substitute an alternate recipient address: [2](#0-1) 

The identical pattern exists in the Tron port's `withdraw()`: [3](#0-2) 

The time between when the beneficiary address is fixed (fill/cancel on the destination chain) and when the message is actually delivered on the source chain can be arbitrarily long — it requires consensus proof generation, challenge-period elapse, and relaying. `EvmHost.dispatchIncoming` is designed to keep failed deliveries retryable rather than reverting the whole batch: [4](#0-3) 

This retry design assumes failures are transient (e.g. temporary pausing, insufficient gas). But if the `beneficiary` address is added to the USDT/USDC blocklist during this window — a real-world event as noted in the referenced report — then `safeTransfer(beneficiary, amount)` will **deterministically revert on every future retry**, because the token issuer itself refuses to move funds to/from a blocklisted address. The message can never be delivered successfully, `_orders[commitment][token]` stays escrowed forever, and there is no `cancelOrder`/refund path once a `RedeemEscrow`/`RefundEscrow` has been dispatched with that beneficiary — the beneficiary field is fixed inside the already-dispatched, immutable cross-chain message body.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged intent solver or user: simply filling/cancelling an order commits an immutable beneficiary address into a cross-chain settlement message. If that solver's or user's address is later blocklisted by the escrowed token's issuer (USDT/USDC — both known to blocklist addresses, e.g. sanctioned or compromised addresses) before the message is delivered, the escrowed principal is locked in the `IntentGatewayV2` contract with no recovery mechanism, matching the Medium severity of the underlying SolverVault report.

### Likelihood Explanation
Requires (a) the escrowed input token to be a blocklist-capable stablecoin (USDT/USDC), and (b) the solver's or order owner's address becoming blocklisted within the settlement delivery window (proof + challenge period + relay time). This is a plausible, externally-triggered event outside the protocol's control (e.g., regulatory/compliance action, an exchange-custodied solver address, or a compromised key later sanctioned), consistent with the "Medium" classification used in the reference report for the same root cause.

### Recommendation
Do not hard-bind token delivery to a single immutable address baked into the cross-chain message. Options:
- Allow the beneficiary (solver/user) to specify or update a fallback receiver, verified by signature, before/at claim time, similar to the reference report's suggested fix of decoupling escrow "ownership" (who is entitled to claim) from the literal transfer destination.
- Provide an explicit recovery/sweep path (permissioned or beneficiary-signed) for orders whose settlement message repeatedly fails to deliver, so escrowed collateral is not stuck indefinitely.

### Proof of Concept
1. User places a cross-chain order on chain A escrowing USDC as input.
2. Solver fills the order on chain B; `ExtrinsicIntents._fill` dispatches a `RedeemEscrow` `WithdrawalRequest` with `beneficiary = solver`.
3. Before the message is relayed/proved and delivered on chain A (during the consensus + challenge-period window), the solver's address is added to Circle's USDC blocklist.
4. A relayer submits `handlePostRequests` → `EvmHost.dispatchIncoming` → `IntentGatewayV2.onAccept` → `IntentsBase._withdraw`, which calls `IERC20(usdc).safeTransfer(solver, amount)`; USDC's `blacklisted` modifier causes the call to revert.
5. `dispatchIncoming` swallows the revert and deletes the receipt so the message stays "retryable" [5](#0-4) , but every future retry hits the same blocklist and reverts identically — the escrowed USDC in `_orders[commitment][usdc]` can never be released.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
