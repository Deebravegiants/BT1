## Title
Webhook shop/topic/webhook-id headers are excluded from HMAC verification, allowing tenant/topic spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` fields that `Registry.process` actually acts on are read straight from unauthenticated HTTP headers. Anyone who can obtain one genuine, HMAC-signed webhook body for their own store (trivial for any merchant who installs the app) can replay that body to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (and/or topic/webhook-id) header. The HMAC check still passes because it never covered those headers, so the dispatched `WebhookMetadata` misreports the shop/topic of an attacker-controlled payload as belonging to a victim tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` against `to_signable_string`. For webhooks, `to_signable_string` is: [1](#0-0) 

which returns only `@raw_body`. Meanwhile the identity-bearing fields consumed later — `shop`, `topic`, `webhook_id`, `api_version` — are parsed from headers that are never mixed into the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields to build `WebhookMetadata`, which is what host applications use to identify which tenant/topic an event belongs to: [3](#0-2) 

The equality the HMAC is supposed to guarantee is "bytes verified == bytes the app acts on for tenant identification." Here that equality is broken: the verified bytes are the body only, but the app acts on `shop`/`topic`/`webhook_id` headers that are entirely outside the signature. This is the same root-cause pattern as the reported bug (a value used for accounting/identification that bypasses the value actually covered by the cryptographic check).

### Impact Explanation
Any party who can trigger a legitimate webhook delivery for their own shop (i.e., any merchant who installs the app — no special privilege required) obtains a `(raw_body, hmac)` pair that is valid forever for that body under the app's `client_secret`. By replaying that exact body to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a different, victim shop, the HMAC check still succeeds (`Registry.process` only checks the body hash), and the handler receives `WebhookMetadata` claiming the event is for the victim shop. Any host application that trusts `data.shop` from a verified webhook to select which tenant's session/records to look up or mutate (the documented and expected usage pattern shown in `docs/usage/webhooks.md`) can be made to apply attacker-controlled event data to another merchant's tenant context — a cross-tenant integrity/confidentiality issue.

### Likelihood Explanation
Exploitation requires no secrets beyond what any installing merchant already legitimately receives (a real webhook body + its HMAC for their own store), and only a header substitution on a replayed HTTP request to the app's public webhook endpoint. This is a low-effort, credential-free attack path from the perspective of the gem's own verification logic.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signable representation used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify shop against the body's own `shop_id`/`shop_domain` where present, or require callers to independently confirm the shop against a known, previously-authenticated tenant list before trusting `WebhookMetadata#shop`). At minimum, document prominently that `Request#shop`, `#topic`, and `#webhook_id` are **not** covered by HMAC validation and must not be trusted for tenant/topic dispatch without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets the app register for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a real webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the identical `(B, H)` pair to the app's webhook endpoint, replacing the shop header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `H` against `B` (`to_signable_string` returns `@raw_body`) — see `lib/shopify_api/webhooks/request.rb` lines 35-38 and `lib/shopify_api/utils/hmac_validator.rb` lines 12-22.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, even though this payload was never produced by, or for, `victim.myshopify.com`.
