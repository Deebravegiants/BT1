### Title
BSC consensus verifier accepts finalization with fewer than the specified (2/3·N)+1 supermajority, weakening the safety threshold below the documented BFT bound - (File: modules/consensus/bsc/verifier/src/lib.rs)

### Summary
`verify_bsc_header` in the BSC consensus client checks participation against `(2 * current_validators.len()) / 3` with no `+1` and a strict `<` comparator, whereas the protocol's own specification (and every other consensus verifier in this codebase: BEEFY, sync-committee, Pharos) requires strictly more than two-thirds, i.e. `floor(2N/3) + 1` participating validators.

### Finding Description
The documented BSC/Parlia finality rule states: "it requires votes from more than two-thirds of the validators... Additionally, at least one more unique validator needs to participate to reach the required threshold of `(2/3 * N) + 1` votes." [1](#0-0) 

Every other on-chain/off-chain consensus verifier in the repo implements exactly this `floor(2N/3)+1` rule:
- BEEFY: `len >= ((2 * total) / 3) + 1` [2](#0-1) 
- Sync-committee: `sync_aggregate_participants < ((2 * committee_size as u64) / 3) + 1` [3](#0-2) 
- Pharos: `required = (self.total_stake * 2 / 3) + 1` [4](#0-3) 

But the BSC verifier omits the `+ 1` term entirely, requiring only:
```rust
if participant_count < ((2 * current_validators.len()) / 3) {
    Err(Error::NotEnoughParticipants)?
}
``` [5](#0-4) 

This is the exact bug class described in the external report: a rounding/threshold quantity that the specification defines with a rounding-up/inclusive adjustment (`+1`) is instead computed with plain integer-division truncation, silently lowering the value below spec. Here the effect is worse than a simple decay-rate error — it directly weakens the Byzantine-fault-tolerance safety margin of the light client that verifies BSC finality for Hyperbridge.

Concretely, for BSC's 21-validator set: the spec requires `floor(2*21/3)+1 = 15` signers; the implementation accepts as few as `14` signers (since the check only rejects `< 14`). For validator-set sizes not evenly divisible by 3 the gap is even larger relative to true supermajority — e.g. for N=4, spec requires `floor(8/3)+1 = 3`, but the implementation only requires `>= 2` (50%), which is not even a majority.

The BFT safety argument for finality (that any two valid quorums must intersect in at least one honest validator, given `f < N/3` byzantine validators) depends on the quorum size exceeding `2N/3`. Removing the `+1` shrinks the pairwise-quorum overlap guarantee and, for validator counts where `2N/3` is not an integer, integer truncation shrinks it again. This lets an adversary controlling (or colluding with) fewer validators than the intended supermajority forge a `VoteAttestationData`/`ExtraData` that this verifier will accept as validly justified/finalized.

### Impact Explanation
`verify_bsc_header` is the core acceptance gate for BSC consensus updates consumed by `ismp-bsc` / the BSC tesseract client and ultimately drives `EvmHost`/`HandlerV2` state-commitment updates for the BSC state machine. [6](#0-5) 
An attacker who can produce BLS signatures from a sub-supermajority subset of BSC validators (below the documented `(2/3)N+1` bound, e.g. only ~66% instead of ~71% for a 21-validator set) can get a forged/premature `StateMachineUpdated` accepted, allowing a bogus BSC state root to be committed on Hyperbridge. Since state commitments are the basis for state-membership/non-membership proofs used to deliver and finalize cross-chain messages, requests, and token mint/burn operations, this can lead to forged message delivery, unauthorized app actions, or unsound state commitments — a High/Critical impact consistent with the rules governing acceptable analogs (unsound state commitment / forged message delivery).

### Likelihood Explanation
Reaching this code only requires submitting a single relayed consensus-update message (an ordinary, unprivileged operation any relayer can perform) containing a `BscClientUpdate` with a bitset of participating validators. No governance or privileged role is needed to submit the update; only the ability to obtain signatures from validators — and the vulnerability lowers the number of colluding/compromised validators required from the intended supermajority down to a materially smaller set, or in the worst case (small `N`) down to a bare majority. Because BSC's own validator set is bounded and known, and because 21 is not evenly divisible by 3, the gap between the spec's `15` and the implementation's `14` is a concrete, exploitable one-signature shortfall today, not merely a theoretical rounding curiosity.

### Recommendation
Change the threshold check in `verify_bsc_header` to match the specification and the pattern used by the other verifiers in this codebase — require strictly more than two-thirds via `floor(2N/3) + 1`:
```rust
if participant_count < ((2 * current_validators.len()) / 3) + 1 {
    Err(Error::NotEnoughParticipants)?
}
```
Add a regression test analogous to the sync-committee `supermajority_tests` module (which asserts that `floor(2N/3)` participants are rejected and `floor(2N/3)+1` are accepted) to lock in the corrected threshold for the BSC validator-set sizes actually in use. [7](#0-6) 

### Proof of Concept
1. Configure/trust a BSC validator set of size `N = 21` (BSC's real validator-set size).
2. Craft a `BscClientUpdate` whose `ExtraData.vote_address_set` bitset has exactly `14` bits set (i.e., 14 out of 21 validators participating) rather than the spec-required `15`.
3. Produce a valid aggregate BLS signature from those 14 validators over the correct `VoteData` (source/target hash) — feasible if an attacker controls or colludes with only 14 of the 21 validators, one fewer than the documented `(2/3)*21+1 = 15` requirement.
4. Submit this update through the standard BSC consensus-update path (`ismp-bsc` client / relayer message) to the runtime/`EvmHost`.
5. `verify_bsc_header` computes `participant_count = 14`, and `(2 * 21) / 3 = 14`; since `14 < 14` is false, the check passes and the update — finalized by one validator short of the documented supermajority — is accepted, updating the trusted BSC state commitment on Hyperbridge. [5](#0-4)

/// Verify that participating validators have more than 2/3 of total stake.
fn verify_stake_threshold(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let participating_stake = validator_set.participating_stake(participants);
	let total_stake = validator_set.total_stake;
	let required = (total_stake * 2 / 3) + 1;

	if participating_stake >= required {
		Ok(())
	} else {
		Err(Error::InsufficientStake {
			participating: participating_stake,
			required,
			total: total_stake,
		})
	}
}
