### Title
Webhook shop-domain header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, but the `shop` (tenant) identity that is handed to the app's webhook handler is read from the unsigned `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header. Because the header is not part of the signed payload, any request whose body+HMAC pair is valid for the app's secret (which an attacker can legitimately obtain by installing the app on their own store and receiving one real webhook) can be replayed with the shop-domain header rewritten to any other shop, and it will still pass `ShopifyAPI::Webhooks::Registry.process`'s authenticity check.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Webhooks::Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from attacker-controllable HTTP headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates authenticity solely via `Utils::HmacValidator.validate(request)`, which computes `HMAC(raw_body, api_secret_key)` and compares it to the `hmac-sha256` header — it does not fold `shop`, `topic`, or `webhook_id` into the signed material: [3](#0-2) 

After that check passes, `Registry.process` immediately builds the `WebhookMetadata` handed to the host application's handler using `request.shop` — the unsigned header value — as the tenant identity: [4](#0-3) 

This is the "field acted on but not covered by the HMAC" identity-binding break: the equality the code should enforce is `shop_bound_by_hmac == shop_acted_on`, but instead it is `hmac_verifies(raw_body) ∧ shop_acted_on := header("shop-domain")`, with no cryptographic link between the two. Since the HMAC secret (`api_secret_key`) is shared across every shop that has installed the app, an unprivileged internet user can:
1. Install the app on their own store (a normal, unprivileged action) and receive one legitimately signed webhook (`raw_body`, `hmac`) for a topic of their choosing.
2. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the (unchanged) body bytes against the (unchanged) HMAC.
4. `WebhookMetadata.shop` now reports the victim's domain, and the host application's handler processes the attacker-crafted body content as if it originated from the victim shop.

### Impact Explanation
This lets an attacker who controls only their own shop cause the gem to deliver attacker-chosen webhook bodies attributed to a shop they do not own or administer — a cross-tenant confusion that any host application relying on `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata#shop` for per-tenant business logic (e.g., updating local shop records, processing GDPR `customers/redact`, `shop/redact`, order/customer mutation topics, deauthorizing access on `app/uninstalled`) will act on believing it is legitimate victim-shop data. This satisfies the Critical bar of cross-tenant access via a credential/tenant boundary crossed entirely within this gem's own verification logic.

### Likelihood Explanation
Likelihood is high for any app that has at least one active install (including the attacker's own dev/trial store) and exposes a webhook endpoint using this gem's `Registry.process`. No access token, `client_secret`, or privileged account is required — only a single genuine webhook delivery to an attacker-controlled shop, which any unprivileged internet user can obtain by installing the app themselves.

### Recommendation
Bind the trusted tenant identity to the HMAC-verified material instead of an unsigned header. Concretely, extend `VerifiableQuery#to_signable_string` for `Webhooks::Request` to include the `shop`, `topic`, and `webhook_id` header values (in a canonical, unambiguous encoding) so the signature covers the full tuple, or require the host application to independently confirm that the shop domain in the webhook belongs to a shop with an active, previously-persisted session/webhook registration before trusting it, and document this requirement clearly in `docs/usage/webhooks.md`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) to receive a legitimate `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `api_secret_key`.
2. Attacker sends a POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, and the host app processes attacker data under the victim's tenant identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
