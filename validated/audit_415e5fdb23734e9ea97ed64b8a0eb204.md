### Title
Emporium `runAction` allows unsigned arbitrary calls draining protocol-held tokens when `signerAddress == address(0)` combined with the empty-`erc20TokenAddresses` "min-circuit" path - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin`) constrains nothing about the `EmporiumStack`/ops/tokens moved. Combined with `EmporiumUpgradeable.verifyWallet` short-circuiting all EIP-712 signature verification when `stack.signerAddress == address(0)`, and `runAction`'s post-call balance/slippage checks being skipped entirely because the loop bound (`circomData.erc20TokenAddresses.length`) is zero, an attacker can execute arbitrary `op.endpoint.call(...)` from Emporium's own context with zero authentication and zero balance accounting anywhere in the call stack.

### Finding Description
The claimed broken equality: `Hinkal.transact`'s balance conservation check
`balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` ( [1](#0-0) )
and `EmporiumUpgradeable.runAction`'s per-token check `balanceChange >= 0` / `handleOut` ( [2](#0-1) )
are both iterated `for (i = 0; i < circomData.erc20TokenAddresses.length; i++)`. If `erc20TokenAddresses = []`, both loops execute zero times, so **no equality is ever evaluated** for any token actually moved by `stack.ops`.

Root cause chain:
1. `formInputForCircom` branches to the trivial `formInputEmporiumMin` (3 public signals: `emporiumMessage`, `timeStamp`, `calldataHash`) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` ( [3](#0-2) ). The corresponding circuit `MainEVMCircuitMin` only proves `message == Poseidon(messageSeed)` and constrains nothing about tokens, amounts, or ops ( [4](#0-3) ). An attacker can freely pick `messageSeed`/`emporiumMessage` and generate a valid proof themselves, with `dimensionsCheck` passing since `dimensions.tokenNumber = 0 == erc20TokenAddresses.length` ( [5](#0-4) ).
2. `_externalTransact` computes `deltaAmountChanges` over the (empty) `erc20TokenAddresses` array and calls `EmporiumUpgradeable.runAction` ( [6](#0-5) ).
3. `runAction` decodes an attacker-supplied `EmporiumStack` from `externalActionMetadata` and calls `verifyWallet`. Critically, `verifyWallet` returns immediately with **no signature check at all** when `stack.signerAddress == address(0)` ( [7](#0-6) ).
4. The ops loop then executes the "Stateless Interaction" branch: `op.endpoint.call{value: op.value}(op.callData)`, executed with `msg.sender == EmporiumUpgradeable` ( [8](#0-7) ). The attacker sets `op.callData = token.transfer(attacker, allBalance)` against any ERC20 held by Emporium — this is not blocked (only `callHinkalWallet`/`doSendToRelay` selectors are blocked).
5. After the ops loop, `runAction`'s balance-check loop and `Hinkal.transact`'s balance-check loop both iterate over the empty `erc20TokenAddresses` array and therefore never observe or reject the balance drop ( [9](#0-8)  and [10](#0-9) ).

`onlyAllowedRecipient` only checks that `msg.sender` (Hinkal) is a pre-approved recipient, which is normal system wiring, not attacker-controlled, and does not gate the malicious `stack.ops` content ( [11](#0-10) ). `rootHashHinkal` can be any historical valid root the attacker knows (e.g. genesis), so `rootHashExists` does not block this path. No other guard (`nullifiers`, `usedMessages`, `dimensionsCheck`, `checkOnchainCreation`) constrains the content of `stack.ops` or ties it to the declared (empty) token list.

### Impact Explanation
Critical — direct theft of protocol/Emporium-held ERC20 tokens by an unprivileged attacker with no authorization (signature bypassed) and no balance accounting anywhere in the call stack. The attack is fully repeatable against any token balance held by the Emporium contract, limited only by the attacker's ability to craft a proof for `MainEVMCircuitMin` (trivial, self-contained) and to pick an unused `emporiumMessage`.

### Likelihood Explanation
Preconditions: the min-circuit verifier for `dimensions = {0,0,0}` and `externalActionId = HINKAL_EMPORIUM_ACTION_ID` must be registered (evidenced by the presence of `contracts/verifiers/mainEVMCircuitMin0v4.sol` in the repo, indicating this configuration is deployed/supported), and Emporium must hold a nonzero ERC20 balance (e.g., from other users' deposits/UTXOs, or residual balances). Attacker cost is a single `Hinkal.transact` call with a self-generated Groth16 proof for the trivial circuit — no dependency on victim keys, relay, or privileged roles. Fully repeatable per attacker-chosen `emporiumMessage` and per token/endpoint until Emporium's balance is exhausted.

### Recommendation
- In `EmporiumUpgradeable.verifyWallet`, do not allow `signerAddress == address(0)` to bypass signature verification for stateless ops that perform arbitrary external calls; require either a valid signature or restrict the "no signer" path to a strictly safe, non-arbitrary-call action set.
- In `EmporiumUpgradeable.runAction`, do not allow `stack.ops` to target arbitrary `endpoint`/`callData` when `circomData.erc20TokenAddresses.length == 0`; either disallow non-empty `stack.ops` entirely for the min-circuit path, or enforce that any token balance touched by `ops` is reflected in `erc20TokenAddresses` so the existing balance-conservation loops actually execute.
- Alternatively, remove/restrict the `formInputEmporiumMin` fast path so it cannot be combined with `EmporiumOperation`s capable of arbitrary calls, or bind the ops hash/target tokens into the min circuit's public signals so the proof actually constrains what is executed.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient of Hinkal), register a mock verifier for `verifierId = buildVerifierId(Dimensions(0,0,0), HINKAL_EMPORIUM_ACTION_ID)` that always returns `true` (simulating a real min-circuit proof, since the circuit itself imposes no real constraint on ops).
2. Fund `EmporiumUpgradeable` with `100e18` of a mock ERC20 (`victimToken`), simulating protocol/user-deposited balance.
3. Attacker (unprivileged EOA) builds `EmporiumStack{signerAddress: address(0), ops: [{endpoint: victimToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 100e18))}], maxFee: 0, deadline: type(uint256).max, v/r/s: 0}`.
4. Craft `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = address(emporium)`, `externalActionData.externalActionMetadata = abi.encode(stack)`, `dimensions = {0,0,0}`, valid `calldataHash`, valid pre-existing `rootHashHinkal`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker.
6. Assert: call succeeds (no revert from `balanceDif == ...` in `Hinkal.transact` nor `BalanceChangeShouldBePositive` in `EmporiumUpgradeable.runAction`), and `victimToken.balanceOf(emporium)` drops from `100e18` to `0` while `victimToken.balanceOf(attacker)` increases by `100e18`, proving both sides of the balance-conservation equality (`balanceDif` vs `amountChanges[i] + utxoAmount`) were never evaluated for the stolen token.

    function formInputEmporiumMin(

        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;

include "../../node_modules/circomlib/circuits/poseidon.circom";

template MainEVMCircuitMin() {
  // Public inputs:
  signal input outTimeStamp;
  signal input calldataHash;

  // Private inputs:
  signal input messageSeed;

  // outputs:
  signal output message;
