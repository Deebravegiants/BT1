### Title
Tron IntentGatewayV2's `setParams` performs zero configuration validation, allowing insolvent/bricked fee parameters that DoS all order placement - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` implements its own admin-gated configuration setter, `setParams()`, which is the functional equivalent of `initialize()`/`_validateParams()` in the mainline EVM `IntentsBase.sol`. Unlike the mainline implementation, this Tron version performs **no validation whatsoever** on the `Params` struct before committing it to storage, matching exactly the M-5 bug class: "Template implementations doesn't validate configurations properly."

### Finding Description
The canonical EVM implementation validates all configuration fields via `_validateParams()` before they are ever committed, both at initialization and at update time: [1](#0-0) 

This function checks that `host`/`dispatcher` are non-zero contract addresses, that `surplusShareBps <= 10_000`, that `protocolFeeBps < 10_000`, and that `priceOracle` (if set) is a contract. It is explicitly documented as existing to prevent values that "would brick the gateway or cause arithmetic errors in fee calculations."

In contrast, the Tron template's `setParams()` — the one-time admin configuration entrypoint (guarded only by `_admin`, which is zeroed out after the first call, functioning as an `initialize()`) — writes the incoming `Params` struct directly to storage with no checks at all: [2](#0-1) 

There is no equivalent of `_validateParams`, no bounds check on `protocolFeeBps`, `surplusShareBps`, and no contract-code check on `host`/`dispatcher`/`priceOracle` anywhere in this file. A search for `_validateParams`/`initialize` confirms these guardrails are entirely absent from the Tron contract, whereas they are present in the shared `IntentsBase.sol` used by the standard EVM deployment.

The unvalidated `protocolFeeBps` is later used directly in unchecked-looking fee-subtraction arithmetic inside `placeOrder`, which is reachable by any unprivileged user placing an order: [3](#0-2) 

Because Solidity 0.8.x reverts on underflow, if `protocolFeeBps` is configured above `10_000` (100%), `protocolFee = originalAmount * protocolFeeBps / 10_000` exceeds `originalAmount`, and `reducedAmount = originalAmount - protocolFee` underflows and reverts on every single call to `placeOrder`, permanently bricking the intent-order pathway for all users on that chain. This is the exact analog of the M-5 root cause — a config field ("royaltiesBps"/"protocolFeeBps") that must be bounded but is checked in the canonical implementation and silently unchecked in this template variant.

### Impact Explanation
Once `setParams()` is called with an out-of-range `protocolFeeBps` (or a non-contract `host`/`dispatcher`), the IntentGateway on Tron becomes permanently unable to process `placeOrder` calls — an unrecoverable route/pathway that "is unable to deliver messages" for cross-chain and same-chain intents. Since `_admin` is zeroed after the single call to `setParams`, there is no way to correct the misconfiguration afterward; the contract is permanently bricked, freezing the intent-gateway functionality on that deployment and any funds routed through it via `placeOrder` prior to discovery.

### Likelihood Explanation
This requires only a single legitimate call to the one-shot `setParams()` function with a value that is not sanity-checked, e.g. an off-by-one-order-of-magnitude configuration error (entering `protocolFeeBps` as `100_000` for "10%" instead of `1_000`, or providing an EOA/incorrect address for `host`/`dispatcher`). This is exactly the scenario the original M-5 report calls out: no malicious intent required, only a configuration mistake by a trusted, non-malicious operator during deployment — a plausible and previously-demonstrated real-world failure mode (as cited in the original report's Nomad/Acala precedents).

### Recommendation
Port the `_validateParams()` checks from `evm/src/apps/intentsv2/IntentsBase.sol` (lines 592-598) into the Tron `IntentGatewayV2.sol`'s `setParams()` function, requiring `host`/`dispatcher` to be non-zero contract addresses, `surplusShareBps <= 10_000`, `protocolFeeBps < 10_000`, and `priceOracle` (if non-zero) to be a contract, reverting with `InvalidInput()` otherwise — mirroring the mainline template exactly.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` contract with `constructor(admin)`.
2. As `admin`, call `setParams(Params{ protocolFeeBps: 20000, ... })` (200%, or any value `> 10_000`). No revert occurs because there is no validation.
3. `_admin` is now `address(0)`, so the misconfiguration can never be corrected via `setParams` again.
4. Any user calls `placeOrder(order, graffiti)` with a non-zero input amount.
5. Inside the fee-reduction loop, `protocolFee = originalAmount * 20000 / 10000 = 2 * originalAmount`, and `reducedAmount = originalAmount - protocolFee` underflows, causing the transaction to revert.
6. Every subsequent `placeOrder` call reverts identically — the gateway is permanently unusable, confirmed by inspecting [4](#0-3) .

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }
