### Title
Unallowlisted route venues let a crafted strategy payload execute arbitrary `require_auth`ed calls as the caller, draining the caller's wallet — (File: contracts/controller/src/strategies/swap.rs)

### Summary
The Shim bug class is "trusted code path processes attacker-controlled wire data and performs a controlled write." The lending analog: `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral`/`flash_position` accept a fully attacker-craftable `swap: Bytes` route, hand it to the configured router, and the route names arbitrary pool/token contracts. Those contracts execute under the caller's authorization tree, so a rogue "pool" can issue a `token.transfer(victim, attacker, amount)` that simulation records as a child of the caller's own `swap_collateral` auth entry. If the caller signs the simulated tree — which honest simulation produces automatically — the rogue contract steals the caller's entire wallet balance of any token, completely outside the measured input/output accounting.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` authorizes only one exact `token_in.transfer(controller → router, amount_in)` invocation and then measures balance deltas (`RouterOverspend`, `NoSwapOutput`). That boundary protects the routed `amount_in`, but it does not bound what the *payload* causes below the caller's root auth. The router keeps no allowlist of venue or token addresses; `execute_strategy` invokes whatever pool addresses the packed program's `assets` registry names (`dispatch_hop`, `contracts/swap-aggregator/src/venues/mod.rs:23-58`). A malicious pool contract running in that call frame may call `token::Client::transfer(victim, attacker, amount)` on any token; because the victim's `require_auth` root is the controller verb, the host records this transfer as a `sub_invocation` of the caller's signed entry and executes it if the caller signs the simulated tree.

The repo's own harness proves the primitive end-to-end: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` shows `RogueHopPool` transferring Alice's unrelated wallet token to the attacker (test at lines 194-227: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while the swap itself pays out normally and passes risk gates). The enforced-auth test at lines 229-269 confirms the theft succeeds exactly when the victim signs the tree that `simulateTransaction` returned — the default wallet/SDK flow. The threat model documents the exposure at `docs/explanation/threat-model.md:154-165` but the loss is unbounded ("the loss is then the caller's wallet, not the routed amount"), which exceeds any slippage/route-quality rejection category.

### Impact Explanation
Theft of user funds: an unprivileged attacker publishes/serves a route payload (or a poisoned `routeXdr` via a compromised/malicious quote path) that routes a hop through an attacker contract. Any user who executes `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or a standalone `execute_strategy` with the simulated auth tree loses every balance the rogue code names — not just the swap input. This mirrors CVE-2023-40547's shape: attacker-controlled data parsed inside a trusted context yields a controlled write (here, an authorized token transfer) far beyond the declared input.

### Likelihood Explanation
Single unprivileged attacker deploys `RogueHopPool` (arbitrary contract), encodes a valid `Program` naming it (the decoder only checks index bounds/opcode shape, `contracts/swap-aggregator/src/program.rs:239-313`), and gets a victim to sign the simulated transaction — the standard flow, since honest simulation embeds the malicious child invocation. No privileged role, oracle manipulation, or MitM of infrastructure is required beyond supplying the route bytes, which are already user-supplied arguments on every strategy verb.

### Recommendation
- Enforce a venue/pool allowlist (or venue-address registry pinned at oracle/listing time) in the router's `dispatch_hop`, so payloads cannot name arbitrary contracts.
- Have the controller verify the caller's authorization surface contains exactly the expected child invocation(s) (e.g., require the route to carry only allowlisted pools, and/or document and enforce a "no extra children" invariant).
- Client-side mitigation already implied by the tests: decode `routeXdr` and reject any signed auth tree with children other than the single input `transfer` — but contract-side enforcement is needed since wallet UX cannot be trusted.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-269`: `UnlistedPoolRouter.execute_strategy` invokes `route.hop_pool`; `RogueHopPool.swap` calls `token::transfer(alice, attacker, WALLET_BALANCE)`; with the simulated (poisoned) auth tree signed, the call succeeds — `wallet(alice)=0`, `wallet(attacker)=WALLET_BALANCE` — while the swap pays `FAIR_OUT_ETH` and all controller risk gates pass.
