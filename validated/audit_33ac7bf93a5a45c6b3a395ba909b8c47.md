### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook solely via `Utils::HmacValidator.validate(request)`, and `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . However, the `shop` value passed to the app's handler is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material [2](#0-1) . `Registry.process` forwards this unauthenticated `shop` value directly into `WebhookMetadata` given to the app's handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: **`shop` value cryptographically bound to the payload == `shop` value the app acts on**. In this gem, the HMAC only authenticates the raw JSON body bytes (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight out of caller-supplied HTTP headers with no cryptographic linkage to the signed body [4](#0-3) . `HmacValidator.validate` only compares `verifiable_query.hmac` against `HMAC(secret, to_signable_string)` [5](#0-4) , so it never validates that the `shop` header actually corresponds to the shop whose data is in the body.

Concretely: a merchant who has legitimately installed the app on their own store (`shop-a.myshopify.com`) receives genuine Shopify-signed webhook POSTs (valid raw body + valid HMAC, since Shopify computes the HMAC using the app's real secret). That merchant, as an unprivileged actor with respect to other tenants, can replay the exact same raw body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header value with a victim's shop domain (`shop-b.myshopify.com`). Because the header is not part of `to_signable_string`, the HMAC still validates successfully [6](#0-5) , and the handler is invoked with `shop: "shop-b.myshopify.com"` even though the body content actually belongs to `shop-a`.

### Impact Explanation
This breaks the tenant isolation guarantee the gem's documented API implies to consuming apps: `docs/usage/webhooks.md` tells developers that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler, and that `data.shop` is "the shop domain of the webhook" [7](#0-6) , implying it is a verified/trustworthy identity field like `topic` and `body`. Any app that follows this documented contract and uses `data.shop` to select which tenant's record to update (a common, encouraged pattern shown in the doc's own example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [8](#0-7) ) can be induced to apply another shop's event body to the wrong tenant, i.e., cross-tenant data corruption/injection.

### Likelihood Explanation
Requires only an app installed on any shop (any unprivileged internet merchant can install a public app), then a trivial replay of one legitimate captured webhook request with a modified header value. No secret key, access token, or privileged account is needed.

### Recommendation
Bind the header-derived identity fields to the signed payload, e.g., require the webhook body itself to carry (or be checked against) the shop identifier, or document/require host apps to cross-check `data.shop` against Shopify's registered webhook shop via an authenticated channel (e.g., verifying the shop against a previously stored session before trusting the header), rather than presenting `data.shop` as an already-verified field in `WebhookMetadata`.

### Proof of Concept
1. Install the app on `shop-a.myshopify.com`; capture a genuine webhook POST (raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`).
2. Replay the same body `B` and `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)` which only checks `HMAC(secret, B) == H` — this still passes [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and `body` from shop-a's event [9](#0-8) , causing the app to act on shop-b's tenant record using shop-a's data.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
