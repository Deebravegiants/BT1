### Title
Webhook shop-domain, topic, and webhook-id headers are not covered by the HMAC signature, enabling cross-tenant spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, which is the only data verified by `HmacValidator.validate` before a webhook is processed: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC (computed only over `@raw_body`) and then dispatches to the registered handler using `request.topic` to select the handler and `request.shop` as the tenant identity passed to the handler's `WebhookMetadata`: [3](#0-2) 

However, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers (`shopify_header`) and are never part of `to_signable_string`: [4](#0-3) [5](#0-4) 

This is the same bug class as the external report: the code verifies one thing (raw body bytes against a shared secret) but acts on another, unauthenticated thing (the `shop` header) as the tenant/authorization boundary. The identity binding that should hold is:

`HMAC-authenticated(shop) == shop used to attribute/act on the webhook`

but here `HMAC covers only (body)`, and `shop` is parsed from an unauthenticated header, so:

`HMAC-authenticated(body) ≠ shop-used-for-tenant-attribution`

Because `api_secret_key` is a single shared secret for the whole app (not per-shop), any tenant that has the app installed on their own store can legitimately receive a validly-signed webhook (a real delivery from Shopify to their own shop, with a real HMAC over the real body). Since the signature never binds the body to the `shop-domain` header, that attacker can replay the same raw body and valid HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header of a victim shop. `HmacValidator.validate` will still succeed because it only recomputes/compares the HMAC over `@raw_body`, and `Registry.process` will hand the (attacker-controlled) `shop` value to the application's handler as if it came from the victim tenant.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to look up or mutate per-tenant state (e.g., look up the victim's stored access token/session, update victim-shop records, trigger tenant-scoped side effects) based on the unauthenticated `shop` field, an attacker who only controls their own (low-privilege) shop installation can forge webhook deliveries that are attributed to a different shop. This is a cross-tenant access primitive achieved purely from an unprivileged internet-facing endpoint (the app's public webhook URL) without needing the victim's or the app's `api_secret_key`/access token — the attacker only needs one legitimately-delivered webhook (signed with the shared app secret) from their own store to replay against arbitrary shop identities.

### Likelihood Explanation
The webhook endpoint is designed to be internet-reachable without prior authentication (that's the whole point of webhook delivery), and `HmacValidator.validate` is the only defense present, so exploitation only requires: (1) installing the app on an attacker-controlled shop (a normal, unprivileged action), (2) capturing one real webhook delivery (raw body + valid HMAC), and (3) resending it to the webhook endpoint with the `shop-domain` header changed. No secrets need to be recovered or brute-forced.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) in the signable content, or otherwise cryptographically bind them to the HMAC — e.g., have `Request#to_signable_string` incorporate `shop`, `topic`, and `webhook_id` in addition to `@raw_body`, and reject requests where these headers don't match a value verified by the HMAC. At minimum, document that `Registry.process`/`WebhookMetadata#shop` is not authenticated for tenant attribution and must be cross-checked by the host application against its own store of known shops, since this gem currently only verifies body integrity, not header/tenant integrity.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (an ordinary, unprivileged onboarding action).
2. Shopify delivers a real webhook to the app's endpoint: body `{"id":1}`, headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over {"id":1}>`.
3. Attacker replays the exact same body and HMAC header to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` recomputes the HMAC only over `@raw_body` (`to_signable_string`) — this matches, since the body is unchanged — and `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the shop header was never part of what the HMAC verified: [2](#0-1) .
