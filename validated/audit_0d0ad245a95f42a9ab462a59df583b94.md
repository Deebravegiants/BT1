Audit Report

## Title
Unauthenticated cross-client request-ID collision enables response hijack / denial-of-service in Gateway ConfidentialRelay handler - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

## Summary
`HandleJSONRPCUserMessage` in the ConfidentialRelay gateway handler performs no authentication, authorization, or per-caller identity binding before registering an attacker-controlled `req.ID` in a single global `activeRequests` map, unlike the sibling `vault` handler, which authenticates callers and prefixes the request ID with an authenticated owner before insertion. This allows an unauthenticated network client to collide with another caller's in-flight request ID, causing that caller's request to be rejected (`"request ID already exists"`) or, if the attacker's own request occupies the slot, causing subsequent DON node responses for that ID to be delivered to the attacker's callback instead of the legitimate caller's.

## Finding Description
`HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 characters before calling `h.newActiveRequest`, with no `Authorizer`, allowlist, or JWT verification anywhere in the file: [1](#0-0) 

`newActiveRequest` stores requests keyed purely by the attacker-supplied `req.ID` in a shared map and rejects insertion if that exact ID is already present: [2](#0-1) 

`HandleNodeMessage` later matches a DON node's response back to a waiting caller purely by `resp.ID`, with no ownership/owner-binding check: [3](#0-2) 

This is directly reachable from `gateway.ProcessRequest`, the internet-facing HTTP entry point, which extracts an optional bearer token but never enforces it — the token is merely forwarded as `auth` into the decoded request and no session/JWT check gates dispatch to `HandleJSONRPCUserMessage`: [4](#0-3) [5](#0-4) 

The comment in the handler itself explicitly documents this as an intentional "dumb relay" design — the gateway does not interpret or validate the caller's params/identity at all, deferring all substantive validation to the relay nodes: [6](#0-5) 

By contrast, the vault handler in the same gateway package explicitly authenticates and stamps requests with an authenticated owner prefix *before* they enter the active-request map, via `authorizeAndStamp`/`GatewayVaultRequestProcessor`: [7](#0-6) 

This asymmetry confirms the ConfidentialRelay handler lacks an equivalent protection that exists elsewhere in the same codebase for a functionally similar flow.

## Impact Explanation
- **Denial of service to the legitimate caller**: An unprivileged party that submits a request with an ID matching another in-flight request causes the second submission of that ID to fail with `"request ID already exists"`, since `newActiveRequest` unconditionally rejects duplicate IDs regardless of caller identity.
- **Cross-caller response delivery**: Because `HandleNodeMessage` resolves the target callback solely via `resp.ID` with no ownership check, whichever caller's insertion won the race to occupy that ID slot receives the DON's response for that ID.

Both fall within an in-scope "cross-user response corruption" / gateway request impersonation category, since they arise purely from gateway-side logic (no malicious node/DON/OCR-peer participation is required) and are reachable by an unprivileged network client hitting the public `/user` gateway endpoint.

## Likelihood Explanation
The requirement is only that an unprivileged attacker knows or guesses another caller's `req.ID` before that caller's own request lands (a race). Request IDs here are caller-chosen strings capped at 200 characters, not server-issued nonces, and there is no evidence in this file that IDs are otherwise namespaced by caller. In practice, exploitation depends heavily on how ID values are actually generated by legitimate ConfidentialRelay clients (e.g., the CRE workflow engine) — if IDs are high-entropy random values not observable by third parties before submission, blind collision is infeasible without some additional information leak; the report does not demonstrate that IDs are predictable or observable in practice, only that the server-side code does not defend against collision if it occurs. This weakens the standalone likelihood of the attack absent a concrete demonstration of ID predictability/observability, but the root-cause code gap (no per-caller binding, unlike vault) is real and verified directly in the code.

## Recommendation
Bind `activeRequests` keys to an authenticated caller identity, mirroring the vault handler's `authorizeAndStamp` pattern (prefixing the request ID with an authenticated owner/session identifier before insertion), and have `HandleNodeMessage` verify that a matched entry belongs to the same authenticated caller who created it before delivering data through its callback.

## Proof of Concept
1. Send an unauthenticated JSON-RPC request to the gateway's public `/user` endpoint targeting the ConfidentialRelay service (`vault.secrets.get` / `capability.exec` methods) with `ID = "X"`.
2. Concurrently or immediately afterward, submit a second request with the same `ID = "X"` (simulating either an attacker colliding with a victim's ID, or a victim retry). The second `newActiveRequest` call returns `"request ID already exists: X"` per `core/services/gateway/handlers/confidentialrelay/handler.go:417-419`, demonstrating the DoS.
3. To demonstrate cross-caller response delivery, have the DON node send a response with `ID = "X"` via `HandleNodeMessage`; verify it is delivered through whichever caller's callback is registered in `h.activeRequests["X"]`, per `core/services/gateway/handlers/confidentialrelay/handler.go:449-459`.

This can be implemented as a Go unit test directly against the `handler` struct (as the existing test file already does for similar scenarios, e.g. `TestConfidentialRelayHandler_DoesNotForwardOnErrorMajority`), calling `HandleJSONRPCUserMessage` twice with the same `req.ID` from two different `Callback` instances and asserting the second call errors, and that `HandleNodeMessage` responses reach only the first-registered callback.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
```

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		l.Debug("global relay rate limit exceeded")
		return nil
	}

	ar := h.getActiveRequest(resp.ID)
	if ar == nil {
		l.Debugw("no pending request found for ID")
		return nil
	}
```

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID
