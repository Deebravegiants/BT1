## Title
Unbounded free computation in `handle_unsigned`'s `validate_unsigned` enables a mempool-flooding Denial of Service - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
The Discourse CVE (BIT-discourse-2021-43850) is a DoS where a costly, unauthenticated/lightly-gated diagnostic path could be triggered repeatedly to exhaust resources. The structural analog in this codebase is `pallet-ismp`'s `handle_unsigned` extrinsic: it is a **permissionless, fee-free** unsigned call whose entire cost — full message execution, including MMR/state-proof cryptographic verification — is paid by every node in `validate_unsigned`, which runs on every peer's mempool validation, not just the block author.

### Finding Description
`handle_unsigned` is documented and implemented as free, permissionless message execution: [1](#0-0) 

Its `ValidateUnsigned::validate_unsigned` implementation does not do a cheap, bounded sanity check — it calls `Self::execute(messages.clone())`, the *same* full execution path (including all proof verification, MMR checks, and state changes attempted) that block execution performs: [2](#0-1) 

`execute()` iterates every submitted message and runs `handle_incoming_message` for each, which performs the full cryptographic proof verification (BEEFY/SP1/MMR multiproof, storage-proof/state-trie verification etc.) for every message in the batch: [3](#0-2) 

Because `handle_unsigned` is `Unsigned`/free-of-charge by design (documented explicitly: "all cross-chain messages received are executed for free as unsigned transactions"), an attacker pays nothing to have every full node on the network run this heavy verification work during **transaction-pool validation** — which happens for every propagated transaction on every peer, independent of whether it is ever included in a block. There is no visible cap in the reviewed code on the number of messages, proof size, or per-message cost inside `Vec<Message>` before `execute()` is invoked; the weight passed to `#[pallet::weight(weight())]` is only used for block-inclusion accounting, not for bounding the work done during `validate_unsigned`.

This mirrors the Discourse bug class: a permissionless (here, literally feeless and unsigned) endpoint triggers expensive backend computation that is not properly rate-limited or bounded, and — because it runs on every node that receives/relays the transaction over p2p — the cost multiplies across the network rather than being confined to a single request handler.

### Impact Explanation
An attacker with no funds and no privileged role (only requires network connectivity to gossip transactions) can submit unsigned transactions carrying large batches of messages with maximal-size (but not necessarily fully valid, since verification happens regardless) proofs. Each such submission forces every full node's mempool validation logic to execute full cryptographic verification (ECDSA recovery over BEEFY signature sets, MMR multiproof verification, parachain header verification, storage trie verification) for every message in the batch, at zero cost to the sender. Because the submission is unsigned, an attacker can also cheaply revise/resubmit variants to defeat naive tx-pool deduplication, repeating the validation cost. This is a network-wide resource-exhaustion vector that can degrade relaying/consensus-message throughput and processing latency for the whole chain, which is a Medium-severity DoS against the message-dispatch path a relayer/unprivileged submitter can reach — directly analogous to the reachable, unprivileged DoS pattern in the Discourse advisory.

### Likelihood Explanation
Likelihood is Medium: submitting `handle_unsigned` extrinsics is fully permissionless (no signature, no fee, "Unsigned" origin only), and the reviewed source shows no explicit message-count or proof-size bound applied before `Self::execute` is invoked in `validate_unsigned`. Exploitation only requires constructing sufficiently large/complex `Message::Request`/`Message::Response`/`Message::Consensus` payloads and broadcasting them repeatedly; no privileged key, admin role, or governance access is needed.

### Recommendation
- Bound the cost of `validate_unsigned` independently of full execution: perform a cheap structural/size check (max messages per call, max proof/leaf-count size) before invoking `Self::execute`, and consider a lighter-weight pre-validation (e.g., verifying only enough to reject clearly malformed/oversized batches) rather than running the entire proof-verification pipeline during mempool validation.
- Enforce an explicit `MaxMessages`/`MaxProofSize` bound on the `messages: Vec<Message>` parameter of `handle_unsigned`, rejected in `validate_unsigned` before any cryptographic work begins.
- Consider making the per-message validation cost proportional to `longevity`/priority so that a single unsigned submission cannot force disproportionate verification work relative to its priority in the pool.

### Proof of Concept
Conceptual PoC (not executed, based on static review of the referenced functions):
1. Construct a `pallet_ismp::Call::handle_unsigned { messages }` where `messages` is a `Vec<Message>` containing many `Message::Request`/`Message::Response` entries, each with a large `MMR` `multiproof`/`leafCount` or many BEEFY signatures in a `Message::Consensus` entry.
2. Submit this as an unsigned transaction to the network (no signature or fee required — origin is `ensure_none`).
3. Every peer's `ValidateUnsigned::validate_unsigned` calls `Self::execute(messages.clone())`, which calls `handle_incoming_message` for each entry and performs full proof verification for each, at no cost to the submitter.
4. Repeat with variant payloads (to avoid tx-pool tag collisions) to sustain load across the network's mempool validation, degrading node responsiveness/relay throughput.

I was unable to confirm from the indexed code whether there is a message-count/size limit enforced elsewhere (e.g. at the transaction pool layer, a `TransactionExtension`, or node-level RPC/gossip limits) that might mitigate this before `validate_unsigned` is reached — the reviewed pallet source itself contains no such bound. If such an external bound exists, it should be verified directly in a full checkout, since the indexed snippets do not show it. [4](#0-3)

	/// Execute the provided ISMP datagrams, this will short circuit if any messages are invalid.
	/// This also charges fee on valid message delivery
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
