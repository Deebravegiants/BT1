### Title
Webhook HMAC covers only the raw body, not the `shop-domain` header — cross-tenant shop-identity spoofing via header replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` verifies the payload bytes but never binds the `shop`, `topic`, `webhook_id`, or `api_version` fields that `Registry.process` subsequently trusts and hands to the app's webhook handler as the tenant identity.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only `@raw_body` is included in the signable string, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` and `request.topic` (both header-derived) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the raw body for webhooks: [4](#0-3) 

The identity binding that should hold is: `hmac_signed_bytes ⊇ {shop, topic, body}`. In this implementation it is only `hmac_signed_bytes == {body}`, so `shop` (and `topic`) are acted upon by the handler without being covered by the signature.

**Exploitation path**: An attacker who controls their own Shopify store can install the victim app (or any app using this gem), trigger a legitimate webhook event (e.g. `orders/create`), and capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair — this is a validly-signed webhook because it was genuinely sent by Shopify to the attacker's own endpoint. The attacker then replays that exact body and HMAC value to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to the victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body bytes against the secret), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: <victim-shop>, ...)`, causing the host application to process attacker-controlled data as though it originated from the victim tenant.

### Impact Explanation
This breaks the tenant/shop authentication boundary the gem is supposed to enforce for webhook delivery: `HMAC-valid == shop-authentic` is assumed by consuming apps, but the shop claim is not part of the signed material. Depending on what the handler does with `data.shop` (e.g., look up a shop's session/access token, apply data to a tenant's records), an attacker can inject spoofed data into another merchant's tenant context — a cross-tenant access primitive.

### Likelihood Explanation
Requires the attacker to be able to install the app / receive at least one legitimate webhook to their own store (achievable by any developer partner account) and to be able to send raw HTTP requests to the app's public webhook endpoint with custom headers — both of which are within reach of an unprivileged internet user with no access to `api_secret_key` or any merchant's access token.

### Recommendation
Include `shop`, `topic`, and any other header fields the handler relies on in the HMAC-signed material, or independently verify that the `shop-domain` header matches an expected/allow-listed shop before dispatching to the handler. At minimum, `Registry.process` should not treat header-derived `shop`/`topic` as trusted tenant identity once only the body has been authenticated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an `orders/create` event, receiving a webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid signature for `B`).
2. Attacker resends `POST /webhooks` with the same body `B`, same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `B` against `H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) dispatches the handler with `shop: "victim-shop.myshopify.com"`, `body: <attacker-controlled parsed body>` — the app now processes attacker data under the victim's tenant identity.
