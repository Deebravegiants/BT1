Webhook `shop` tenant identifier is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` value that identifies which merchant/tenant the webhook belongs to is read from a separate, unsigned HTTP header and is never included in the signed payload. Any party who can obtain one validly-signed webhook delivery (e.g. by installing the app on their own store) can resend that exact body with a forged `shop-domain` header pointing at a different, victim tenant, and the HMAC check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is derived independently from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header: [2](#0-1) 

`Registry.process` validates authenticity purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` accessor (also from a header), then immediately forwards `request.shop` to the app's handler as the trusted tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate_signature` only proves that the *body* bytes were signed by the app's secret — it says nothing about which shop the body belongs to: [4](#0-3) 

This is exactly the binding break described in the reference report: the field the code *acts on* (`shop`, used as the tenant key) is not the field *covered by the HMAC* (only the body is). The equality the gem should guarantee — "the `shop` a handler receives == the `shop` cryptographically bound to this request" — does not hold; instead `shop` is taken from an attacker-controllable, unauthenticated header.

The gem's own documentation instructs host apps to trust `data.shop` as "The shop domain of the webhook": [5](#0-4) 

so apps following the documented contract (e.g. keying storage, tenant scoping, or job dispatch off `data.shop`, as shown in the very same doc's example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) inherit this cross-tenant confusion.

### Impact Explanation
An unprivileged attacker who can install the target app on their own (attacker-controlled) shop — which requires no special privilege, access token, or leaked secret — will receive genuine webhook deliveries, each with a valid `X-Shopify-Hmac-Sha256` computed over the body using the app's real `api_secret_key`. Because the header carrying `shop` is not part of the signed content, the attacker can replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with any victim shop's domain. `HmacValidator.validate` still returns `true` (body+hmac still match), and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-authored) body belongs to the victim shop. Any host application that trusts `data.shop` for tenant scoping — as the gem's docs instruct — will attribute attacker-controlled webhook content to a shop the attacker does not control, i.e. cross-tenant data injection/confusion.

### Likelihood Explanation
High for any app that receives HTTP webhooks and follows the gem's documented usage of `data.shop`. The only prerequisite is that the attacker be able to trigger at least one legitimate webhook to their own shop (trivial for any public/embedded Shopify app, since installing on one's own store requires no elevated privilege) and be able to send an arbitrary HTTP request to the app's public webhook callback endpoint with a modified header — both are standard unprivileged-internet-user capabilities.

### Recommendation
Bind the shop identity cryptographically to the payload before it is trusted, e.g.:
- Include the shop domain (and ideally webhook id / topic) in the HMAC-signed string used by `Utils::HmacValidator`, or
- Cross-check `request.shop` against a shop value embedded in the JSON body (Shopify webhook payloads for most topics include the shop/merchant identifiers), or
- At minimum, document loudly in `docs/usage/webhooks.md` and `WebhookMetadata` that `shop` is derived from an unauthenticated header and must not be used as a sole tenant-scoping key without additional verification (e.g. checking it against a shop already known/installed by the app).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimate webhook to the app with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and the HMAC header identical, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`) — it matches, since only the body is signed.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: B, ...)`.
6. Any handler logic keyed by `data.shop` (as documented/shown in `docs/usage/webhooks.md:26`) now processes attacker-controlled body content under the victim shop's tenant.
