### Title
Unbounded attacker-controlled scrypt cost parameters (n/r/p) in imported container metadata enable CPU/memory DoS during unlock - ([File: libraries/secure-container/src/metadata.js])

### Summary
`metadata.decode()` parses `scrypt.n/r/p` as raw `UInt32BE` fields from an untrusted container/import file with no range validation, and `decryptBlobKey()`/`boxDecrypt()` pass these values straight into `stretchPassphrase()` → `scrypt()` without clamping. Because the container's integrity check (`file.checkContents`) is a plain SHA-256 checksum with no secret/HMAC, an attacker who supplies or tampers with an imported SECO file can set arbitrary extreme values (e.g. `n` near `2^32`) and still produce a self-consistent, "valid" checksum, forcing pathological CPU/memory usage the moment the correct passphrase is used to unlock/import.

### Finding Description
The metadata struct decodes `scrypt.n`, `scrypt.r`, `scrypt.p` as raw 4-byte big-endian integers with no bounds checking: [1](#0-0) 

`decode()` only warns (does not reject) if the blob is larger than expected and otherwise blindly returns the struct-decoded object: [2](#0-1) 

`decryptBlobKey()` forwards `metadata.scrypt` (attacker-controlled) directly to `boxDecrypt()`: [3](#0-2) 

`boxDecrypt()` merges the attacker-supplied params over sane defaults (which does not clamp values — it lets any attacker-specified `n/r/p` override the defaults) and calls `stretchPassphrase()`, which passes `N`, `r`, `p` straight into `scrypt()` with no sanity ceiling: [4](#0-3) [5](#0-4) 

Critically, the only integrity check on the container (`file.checkContents`) is a bare SHA-256 hash over `metadata || blobLength || blob`, not an HMAC or signature tied to a secret the attacker doesn't know: [6](#0-5) 

Since this is a plain hash, an attacker crafting or tampering with an entire import file (e.g., a "restore backup" / QR-imported SECO container) can freely choose `scrypt.n/r/p`, recompute the matching checksum themselves, and the file will still "checkContents" as valid — there is no cryptographic binding between the checksum and passphrase knowledge that would prevent this tampering.

### Impact Explanation
When the legitimate user attempts to import/unlock this crafted container with their correct passphrase, `stretchPassphrase()`/`scrypt()` is invoked with attacker-chosen `N/r/p`. Depending on what limits (if any) the underlying `@exodus/crypto/scrypt` implementation imposes internally (not visible in this repo — it is an external package), this can cause excessive CPU burn and/or memory allocation on the client during the unlock/import flow, hanging or crashing the app before the wallet ever unlocks. This is a liveness/availability issue ("locked means locked" violated in the sense that the correct passphrase cannot complete unlock in reasonable time/resources) rather than a confidentiality or signing-authorization compromise — no secrets are disclosed and no unauthorized signing occurs.

### Likelihood Explanation
Feasible whenever the wallet accepts an attacker-influenced or attacker-crafted SECO container for import/restore (e.g., a malicious backup file, QR payload, or a container the user is tricked into importing) and does not perform out-of-band validation of the scrypt parameters or reject the file before invoking the KDF. Because the checksum is a non-keyed SHA-256, the attacker does not need the passphrase or any secret to produce a "valid" crafted file — they only need to control the imported file's bytes, which matches the "QR/import payloads" attack surface named in scope.

### Recommendation
Add explicit upper/lower bound validation for `scrypt.n`, `scrypt.r`, `scrypt.p` (and ideally the `n*r*p` memory-cost product) in `metadata.decode()` or in `decryptBlobKey()`/`boxDecrypt()` before calling `stretchPassphrase()`, rejecting metadata whose cost parameters deviate from the application's expected/created values (e.g., enforce `n` is a power of two within `[2^10, 2^17]`, `r <= 8`, `p <= 4`, or simply reject any parameters that don't match the values the wallet itself generates via `createScryptParams()`). Additionally, consider binding the metadata's integrity to a value the attacker cannot forge (e.g., verifying scrypt parameters against a fixed policy rather than trusting arbitrary values from the file).

### Proof of Concept
Unit/fuzz test plan for `libraries/secure-container/src/__tests__/metadata.test.js`:
1. Construct a metadata object via `metadata.create()`/`encryptBlobKey()`, then mutate `metadata.scrypt.n` to `0xFFFFFFFF` (and vary `r`/`p` across the full `UInt32BE` range) before calling `metadata.decryptBlobKey(metadata, passphrase)`.
2. Assert that `decryptBlobKey()` throws a validation error (e.g., "scrypt parameters out of bounds") rather than invoking `scrypt()`/hanging or consuming excessive memory.
3. As a fuzz invariant, generate random `(n, r, p)` UInt32BE triples, decode/encode round-trip through `metadata.decode()`/`metadata.encode()`, and assert `decryptBlobKey()`/`boxDecrypt()` reject any triple whose `n*r*p` cost exceeds a defined ceiling before calling the underlying `scrypt()` function (mock `@exodus/crypto/scrypt` to assert it is never invoked with the oversized parameters).
4. (Integration) Build a full SECO file via `file.encode()`/`computeChecksum()` with the malicious `scrypt.n`, confirm `file.checkContents()` returns `true` (proving the checksum does not protect against this tampering), and confirm the unlock path currently proceeds to call `scrypt()` with the attacker-controlled value.

  return { salt: randomBytes(32), n: 16_384, r: 8, p: 1, ...params }

export async function stretchPassphrase(passphrase, { salt, n, r, p } = createScryptParams()) {
  const key = await scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')
  return { key, salt }
}
