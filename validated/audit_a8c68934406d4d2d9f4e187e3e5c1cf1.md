This confirms the test suite explicitly demonstrates that `describeWithdrawal` is called with three identical `withdrawalParams` (same `assetId: "nep141:wrap.near"`) in a batch, and the mock resolves in an order-independent way — the SDK's `createWithdrawalCompletionPromises` correlates results purely by array index/promise position, not by the underlying bridge record's amount or address. This validates the reported mechanism.

### Title
`describeWithdrawal`'s `assetId`-only match returns an unverified `txHash` for a batch withdrawal of the same token, letting an integrator credit a completion against the wrong underlying transfer - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) selects the matching bridge-side withdrawal record solely via `findMatchingWithdrawal` on `assetId` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`), and `WithdrawalStatus` (`packages/intents-sdk/src/shared-types.ts:454-457`) carries only `{status, txHash}`/`{status, reason}` with no `amount`/`destinationAddress`. When a NEAR intents tx contains two or more withdrawals of the same `assetId` (a legitimate, unprivileged scenario — a user simply requests a batch withdrawal with two legs of the same token to two different addresses/amounts), `findMatchingWithdrawal` cannot distinguish between them and may bind the wrong bridge record's `txHash` to a given `WithdrawalIdentifier`.

### Finding Description
The equality that should hold is: for withdrawal *i* in a batch, the `txHash`/completion returned by `describeWithdrawal(wid_i)` must correspond to the bridge-side record whose `data.amount`/`data.address` equals `withdrawalParams_i.amount`/`destinationAddress`. Instead, `findMatchingWithdrawal` only checks `` `nep141:${w.data.near_token_id}` === assetId `` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:426`), with the code's own comment acknowledging: *"multiple withdrawals of the same token in a single transaction are not supported"* (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:412-416`). When two legs share an `assetId`, `Array.prototype.find` deterministically returns the **first** matching entry in the API response array for every call, regardless of which `WithdrawalIdentifier.index` invoked it — so both legs' `describeWithdrawal` calls converge on the same underlying record/`txHash`, and the second leg is reported "completed" using the first leg's `txHash` (and vice versa, depending on array order) with no cross-check against its own `amount`/`destinationAddress`.

`withdrawal-watcher.ts:36-47` and `createWithdrawalCompletionPromises` consume only `status`/`txHash` and surface `{hash}` to the integrator — there is no downstream re-validation against `withdrawalParams.amount` or `destinationAddress` anywhere in the call chain I traced (`core/withdrawal-watcher.ts`, `sdk.createWithdrawalCompletionPromises.test.ts`). The confirmed test at `packages/intents-sdk/src/sdk.createWithdrawalCompletionPromises.test.ts:27-44` shows the SDK invoking `describeWithdrawal` independently per identical-`assetId` withdrawal and trusting whatever `txHash` each call returns, with completion correlated purely by promise/array index — exactly the condition needed for the mismatch to go undetected by the integrator.

`validateWithdrawal`, `compareAddresses`, and `supports()` all execute before signing/estimation, not at status-check time, and do not protect the `describeWithdrawal` read path at all — they cannot prevent the described mismatch.

### Impact Explanation
An integrator polling per-leg withdrawal status (e.g., to mark a customer's specific withdrawal record complete and release an off-chain credit/refund) can mark the **wrong leg** complete: leg B's `txHash` gets attributed to leg A while leg A's real destination/amount is different, and vice versa. This is a status/hash misreport that can cause an integrator to credit or refund a withdrawal that has not actually completed as recorded (or double-report the same underlying transfer for two logically distinct withdrawals) — matching the "High" impact category (status/hash misreport causing credit/refund confusion). It does not itself move funds or forge a signature, so it does not rise to "Critical."

### Likelihood Explanation
Preconditions: a batch withdrawal (`WithdrawalParams[]`) must contain ≥2 entries with the same `assetId` routed through PoA Bridge in a single NEAR intents transaction — an ordinary, permitted use of the public batch-withdrawal API, requiring no privilege beyond normal SDK usage. This is explicitly a known/documented gap in the code (not a new discovery of hidden logic), and the referenced test file demonstrates the SDK's index-based promise resolution for duplicate `assetId` batches, confirming the vulnerable path is exercised in normal operation. Repeatable on every batch withdrawal containing duplicate `assetId` legs.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId`: either (a) reject/guard batches with duplicate `assetId` per PoA-routed leg before submission, or (b) extend the match to also compare `data.amount`/`data.address` (net of fee) against `withdrawalParams.amount`/`destinationAddress`, only falling back to positional/ordering heuristics when uniquely resolvable, and throwing an explicit ambiguity error otherwise instead of silently returning a possibly-swapped `txHash`.
