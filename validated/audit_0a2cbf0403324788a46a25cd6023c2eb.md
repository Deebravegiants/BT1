Confirmed root cause. The docs explicitly state that `Registry.process` "will verify the request did indeed come from Shopify" — implying the entire request, including the `shop` field handed to the handler, is trustworthy. That guarantee is false for the `shop-domain` header.

### Title
Webhook `shop` domain is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` authenticates the payload bytes but never binds the `X-Shopify-Shop-Domain` header to the signature. Any party in possession of one valid `(raw_body, hmac)` pair — which any shop that has installed the app legitimately receives for its own events, since the HMAC is computed with the single shared `Context.api_secret_key` rather than a per-shop secret — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `Registry.process` accepts it, because it only checks `Utils::HmacValidator.validate(request)` and never checks that the `shop` field is consistent with anything cryptographically bound to the body.

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(secret, raw_body + shop)` (or equivalent), but the actual binding implemented is:
`hmac == HMAC(secret, raw_body)` only [1](#0-0) , while `shop` is read directly and unauthenticated from the header [2](#0-1) .

`HmacValidator.validate`/`validate_signature` only ever signs `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) . `Registry.process` gates entirely on this HMAC check and then forwards the request's `shop` header straight into `WebhookMetadata` passed to the app's handler, without any further verification: [4](#0-3) .

Because the API secret (`Context.api_secret_key`) used to sign webhooks is one shared value for the whole app across all installed shops (not shop-specific), a legitimate but malicious merchant who has installed the app can capture a real, validly-signed webhook body for their own shop, then POST that exact body and HMAC to the app's webhook endpoint again with a forged `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header naming a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain [5](#0-4) , while `body` still contains the attacker's own shop's data.

The docs describe `Registry.process` as verifying "the request did indeed come from Shopify" as a whole [6](#0-5) , and explicitly document `shop` as a trusted field of `WebhookMetadata` for host apps to key off of [7](#0-6) , so any host app following the documented API (e.g. persisting `data.body` under `data.shop`, as shown in the docs' own example calling `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [8](#0-7) ) will attribute attacker-controlled data to a shop record chosen entirely by the attacker.

### Impact Explanation
This breaks the tenant isolation boundary the gem is meant to provide: an attacker-controlled shop can cause the app to process/store data under a victim shop's identity, i.e. cross-tenant access/data poisoning purely by manipulating an unauthenticated HTTP header on a request whose payload signature was legitimately obtained from the attacker's own tenant. No access token, `client_secret`, or privileged credential is required — only that the attacker itself is an installed (even free/trial) tenant of the app, which for a self-serve Shopify app is available to any internet user.

### Likelihood Explanation
Likelihood is high wherever the app's webhook endpoint is internet-reachable (a documented requirement for receiving Shopify webhooks) and the handler trusts `WebhookMetadata#shop` as documented. The attacker needs no special access beyond installing the app as any tenant, which is the normal, expected onboarding flow for this class of app.

### Recommendation
Bind the shop identity to the HMAC computation, or otherwise cross-check it against a trusted source, before handing it to the handler. Concretely: extend `to_signable_string` (or add a new signed field) so the `shop` header is included in the value covered by `Utils::HmacValidator.validate`, or require callers of `Registry.process` to compare `request.shop` against the shop for which the webhook topic was registered/known to be installed, rejecting mismatches with `Errors::InvalidWebhookError` before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-serve, no special privilege needed).
2. Shopify sends the attacker a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays `POST /callback/orders/create` to the app's public endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation passes [9](#0-8) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's order data> ...)` [5](#0-4) , causing the host app (following the gem's documented usage) to record/act on attacker data as though it belongs to `victim-shop.myshopify.com`.
