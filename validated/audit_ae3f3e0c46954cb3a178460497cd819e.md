### Title
Webhook shop identity spoofable because `x-shopify-shop-domain` is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw HTTP body only, while the `shop` (tenant identity) is read from an unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then hands the caller-controlled `shop` value straight to the app's handler as the tenant identifier, without binding it to the signature. This mirrors the report's core bug class — a field ("mintRecipient"/sender in the report, "shop" here) that is *acted upon* for identity/authorization purposes but is not the field actually *covered* by the cryptographic check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is pulled from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the body), so it only proves "this body was produced by someone who knows `api_secret_key`" — it says nothing about which shop the request claims to be from: [3](#0-2) 

`Registry.process` raises only if the body HMAC fails, then immediately trusts `request.shop` as the tenant identity forwarded to the app-defined handler: [4](#0-3) 

Because `api_secret_key` is shared across every shop that has installed a given app (it is not per-shop), any merchant who has legitimately installed the app can trigger real Shopify webhooks for their own store and thus obtain body/HMAC pairs that pass `HmacValidator.validate`. Since the `shop` header is outside the signed scope, that merchant (an "unprivileged" party with respect to every *other* tenant of the same app) can replay/craft an HTTP POST to the app's webhook endpoint using a validly-signed body but with the `x-shopify-shop-domain` header set to a different, victim merchant's domain. `Registry.process` will accept it and dispatch `WebhookMetadata` carrying the attacker-chosen `shop` to the handler as if it were an authentic event for the victim's store: [5](#0-4) 

The identity binding that should hold — `HMAC-authenticated sender == shop value the handler acts on` — is broken: the HMAC authenticates only "some installed shop of this app produced this body," while the `shop` value that determines *which tenant's* data the handler mutates is taken from an unauthenticated header.

### Impact Explanation
This allows cross-tenant request/data injection in any host application that uses `WebhookMetadata#shop` (as documented/intended) to key persistence, sync business logic, or trigger side effects for a specific merchant (e.g., writing order/inventory/customer records, revoking access, sending notifications) without an independent, out-of-band verification that the header shop actually owns the signed body. This meets the "cross-tenant access" criterion (Critical) since one tenant can cause the app to process an event under a completely different tenant's identity.

### Likelihood Explanation
Reasonably likely: (1) any legitimate installer of a multi-tenant app can obtain genuinely HMAC-valid webhook bodies for their own shop, since Shopify signs with the app's single shared `api_secret_key`, not a per-shop secret; (2) crafting the HTTP request with a different `shop` header requires no special access — only the ability to send arbitrary HTTP requests to the app's public webhook endpoint; (3) this gem provides no built-in mechanism (e.g., a registered-shop allow-list check, or binding shop into the signed payload) to prevent it, and the library's own documentation/tests treat `request.shop` as trustworthy tenant identification once `HmacValidator.validate` passes.

### Recommendation
Do not treat `request.shop` as authenticated by `HmacValidator.validate` alone. `Registry.process` (or the host app via documentation) should require that the resolved `shop` correspond to a shop that has a known/active session or app installation record before dispatching to the handler, and/or the library should surface a strong warning that the `shop` header is unauthenticated relative to the HMAC. Ideally, expose an API that lets consumers verify the webhook's shop against their own installed-shop registry as a mandatory step, rather than implicitly trusting the header once the body-only HMAC check succeeds.

### Proof of Concept
1. App X is installed on both `victim-shop.myshopify.com` and `attacker-shop.myshopify.com` (attacker legitimately installs the same public app on their own store — no special privilege required).
2. Because `api_secret_key` is shared across installs, Shopify sends attacker-shop a real webhook whose body/HMAC pair validates against `HmacValidator.validate` (as shown in `lib/shopify_api/utils/hmac_validator.rb#L12-L22`, which signs only the body).
3. Attacker captures this valid `(raw_body, x-shopify-hmac-sha256)` pair and re-POSTs it to App X's public webhook endpoint, replacing the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (`lib/shopify_api/webhooks/request.rb#L45-L63`); `Registry.process` validates the (still-valid) body HMAC and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb#L188-L200`).
5. The host app's handler processes attacker-controlled event data as if it originated from `victim-shop`, corrupting or leaking victim-tenant state.
