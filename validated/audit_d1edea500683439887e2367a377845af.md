## Title
Webhook shop identity spoofing — HMAC covers only the raw body, not the `shop-domain` header used for tenant attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the webhook signature check to the raw HTTP body only, while the `shop` value that identifies *which tenant* the webhook belongs to is taken from an unrelated, unsigned HTTP header. Any actor who can obtain one validly-signed webhook delivery (trivially available to any merchant who installs the app on their own store) can replay that exact body/HMAC pair while substituting a different `X-Shopify-Shop-Domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic and hand the forged shop identity to the host app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which in turn calls `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., HMAC over the body alone — and then immediately forwards the unauthenticated `request.shop` value to the app-registered handler: [3](#0-2) 

`HmacValidator.validate_signature` confirms the signature only binds `verifiable_query.to_signable_string` (the body) to the secret — no header, including `shop`, is part of that signed string: [4](#0-3) 

This breaks the intended identity binding: `HMAC(secret, raw_body) == received_hmac` should imply "this exact `(shop, body)` pair was sent by Shopify for `shop`", but the equality actually only proves "this exact `body` was sent by Shopify for *some* shop." The `shop` field is acted upon (passed into `WebhookMetadata` and handed to the host app's business logic) without ever being covered by the cryptographic check.

### Impact Explanation
Any unprivileged user who can install the target app on their own Shopify store (a normal, unprivileged action) receives genuine webhook deliveries addressed to their own shop, complete with a valid HMAC over the body. Since the HMAC never covers the `shop-domain` header, that same attacker can resend the identical raw body and HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a victim shop. `Registry.process` will pass HMAC validation and deliver `WebhookMetadata` claiming the payload originated from the victim shop. Any host app that uses `webhook.shop` (as documented/intended by this gem's API) to scope data writes, trigger per-tenant side effects, or reconcile records will act on forged, cross-tenant data — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any attacker willing to install the app (a normal, unprivileged onboarding flow) since capturing one legitimate webhook body+HMAC pair from their own store is the only prerequisite; no secrets, tokens, or privileged access are required, and the header can be freely set by anyone posting directly to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and other identity-bearing fields such as `topic`/`webhook_id` if used for authorization decisions) into the signed material, or otherwise cryptographically tie the header value to the verified payload — e.g., include the shop domain in `to_signable_string`, or cross-check `request.shop` against a shop value embedded in the verified body/claims before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook delivery with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body.
2. Attacker replays that exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)`.
4. The host app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs shop-scoped actions against the wrong tenant. [3](#0-2)
