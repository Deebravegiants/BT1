### Title
`calc_total_without_take_pnl_no_orderbook()` unnecessarily reverts swap/deposit/withdraw via `checked_sub` instead of saturating on rounding-induced overshoot - (File: program/src/math.rs)

### Summary
`Calculator::calc_total_without_take_pnl_no_orderbook()` computes each pool's usable reserve by subtracting the accrued-but-unwithdrawn protocol PnL (`need_take_pnl_pc` / `need_take_pnl_coin`) from the live vault token balances, using `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?`. This function is called at the very start of every unprivileged, single-transaction entrypoint that a swapper or LP can invoke — `process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`, `process_deposit` and `process_withdraw` — and also in `process_withdrawpnl`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The subtraction `pc_amount.checked_sub(amm.state_data.need_take_pnl_pc)` (and the analogous coin subtraction) is the AMM's counterpart of the reported `repayDebt()` bug class: whenever the "debt-like" quantity being subtracted (`need_take_pnl_pc`/`need_take_pnl_coin`) is equal to or marginally larger than the corresponding live balance (`pc_amount`/`coin_amount`), the strict `checked_sub` fails and every call using it reverts with `AmmError::CheckedSubOverflow`, instead of gracefully clamping to zero the way `get_max_buy_size_at_price`/`get_max_sell_size_at_price` do via `saturating_sub` a few lines below in the same file. [5](#0-4) [6](#0-5) 

`need_take_pnl_pc`/`need_take_pnl_coin` is accrued (`checked_add`) inside `calc_take_pnl`, which is itself invoked from within deposit/withdraw/withdrawpnl paths using integer-square-root and repeated integer division/rounding of `U256`/`U128` values (`x2_power.integer_sqrt()`, multiple `checked_mul`/`checked_div` chains for `delta_x`, `delta_y`, `pc_pnl_amount`, `coin_pnl_amount`). [7](#0-6) [8](#0-7) 

Because these accrual computations pass through multiple decimal-normalization/restoration steps (`normalize_decimal_v2`, `restore_decimal`) with different `pc_decimals`/`coin_decimals`/`sys_decimal_value` scaling for the two legs of the pool, rounding on the pc side and the coin side is not perfectly symmetric. Over repeated deposit/withdraw/swap calls that each re-derive and re-accumulate `need_take_pnl_pc`/`need_take_pnl_coin`, this asymmetry can push the accrued "unwithdrawn PnL" bookkeeping value to be off-by-a-few-units relative to what the live vault balance can actually support at the moment a subsequent unprivileged instruction runs `calc_total_without_take_pnl_no_orderbook`, exactly mirroring the external report's root cause: a downstream accounting value becomes slightly larger than the on-chain balance it is subtracted from, and a strict subtraction (rather than a saturating/clamped one) causes the entire instruction to revert.

### Impact Explanation
Because `calc_total_without_take_pnl_no_orderbook` is called unconditionally at the top of `process_swap_base_in[_v2]`, `process_swap_base_out[_v2]`, `process_deposit`, and `process_withdraw`, a rounding-induced state where `need_take_pnl_pc > amm_pc_vault.amount` (or the coin equivalent) causes **all** subsequent swaps, deposits, and withdrawals on the pool to permanently revert with `CheckedSubOverflow` until `process_withdrawpnl` is invoked by the privileged `pnl_owner` to reset `need_take_pnl_pc`/`need_take_pnl_coin` to zero. This is a pool-wide denial of service for ordinary swappers and LPs, freezing their ability to trade or withdraw liquidity, which can also make LP funds practically inaccessible for arbitrary lengths of time if the `pnl_owner` is inactive. [9](#0-8) 

### Likelihood Explanation
This requires no privileged access or special transaction crafting — the corrupted state accrues purely from normal pool usage (deposit/withdraw/swap sequences that repeatedly invoke `calc_take_pnl`) and any single subsequent unprivileged swap/deposit/withdraw transaction will trip the revert once the drift accumulates to overshoot the live vault balance. The likelihood scales with pool activity and time; it is not attacker-triggerable on demand with certainty, but the same integer-rounding root cause that the external report flags as realistic ("amount could be slightly greater... because of math rounding differences") applies directly to this repeatedly-executed accrual/subtraction pattern.

### Recommendation
Change `calc_total_without_take_pnl_no_orderbook` to saturate instead of hard-failing, consistent with the `saturating_sub` pattern already used elsewhere in `math.rs`:
```rust
let total_pc_without_take_pnl = pc_amount.saturating_sub(amm.state_data.need_take_pnl_pc);
let total_coin_without_take_pnl = coin_amount.saturating_sub(amm.state_data.need_take_pnl_coin);
```
Alternatively, clamp `need_take_pnl_pc`/`need_take_pnl_coin` to the live vault balance at the point of use so a small rounding drift cannot brick swap/deposit/withdraw flows for all users.

### Proof of Concept
A concrete on-chain reproduction (exact input sequence needed to force the multi-step rounding drift across `pc_decimals`/`coin_decimals`/`sys_decimal_value`) could not be fully derived from static analysis alone within the indexed code; the mechanism (accrual via `calc_take_pnl`'s integer-sqrt/decimal-restore chain, followed by strict `checked_sub` consumption in `calc_total_without_take_pnl_no_orderbook`) is verified directly in the cited code, but confirming the exact number of deposit/withdraw/swap cycles required to trigger the overshoot would require running the program's arithmetic with concrete decimal configurations (e.g., via the project's existing Rust unit tests such as `test_swap_base_in`/withdraw tests in `program/src/processor.rs`) — this exceeds what can be confirmed from the indexed excerpts available.     pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

            .checked_mul(U128::from(

            ))
            .unwrap()
            .checked_div(U128::from(amm.fees.trade_fee_denominator))

            .checked_mul(amm.sys_decimal_value.into())
            .unwrap()
            .checked_div(price_with_fee)
            .unwrap();
        max_size = max_size.saturating_sub(y.into());
        Self::to_u64(max_size.as_u128()).unwrap()
    }
