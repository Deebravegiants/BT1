### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header as the tenant identity passed to the handler, without that header ever being covered by the HMAC.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only this body-bound HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature using the app-level `Context.api_secret_key`, which is a single shared secret common to *every* shop that has installed the app — it is not shop-specific: [4](#0-3) 

Because of this, the identity binding the code implicitly assumes — "the shop-domain header equals the shop that produced this HMAC-verified body" — does not hold. The HMAC only proves "this body+signature pair was produced with the app's secret" (i.e., came from some Shopify webhook for this app), not "this body belongs to shop X." Any legitimate, unprivileged merchant who has installed the app can trigger normal store events (e.g., create/update a resource) to obtain their own valid `(raw_body, hmac)` pair from a real Shopify webhook delivery. Since `shop-domain` is never part of the signed content, that same attacker can replay the identical body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header (and any of `topic`/`webhook-id`/`api-version`) with a victim shop's domain. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop: [5](#0-4) 

If the host application's webhook handler uses `WebhookMetadata#shop` to select which tenant's session/data record to update (the intended and only reasonable use of this field), the attacker can inject or attribute forged webhook data into another tenant's records — a cross-tenant integrity/confidentiality breach — using nothing but their own legitimate installation.

### Impact Explanation
This breaks the equality the gem implicitly guarantees to consumers: `shop-domain header == shop that authored the HMAC-signed body`. In reality the equality only holds for `HMAC secret == app's shared secret`, not per-shop. A merchant with no elevated privileges (any shop that installs the app) can leverage their own legitimate webhook traffic to forge cross-tenant webhook deliveries, satisfying the "cross-tenant access" Critical impact category — no `api_secret_key`, access token, or privileged account is required, only normal use of the app as an ordinary merchant.

### Likelihood Explanation
Moderate-to-high: exploitation requires only (1) installing the target app as a normal merchant (a capability every attacker in scope has), (2) triggering any webhook-eligible store event to obtain a valid body+HMAC pair, and (3) replaying it with a different `shop-domain` header value. No secret material, token theft, or race condition is needed — only that the host application (as designed by this gem's API) relies on `WebhookMetadata#shop` for tenant identification, which is the documented/intended field for that purpose.

### Recommendation
Include `shop-domain` (and ideally `topic`/`webhook-id`) in the signed/verified content, or otherwise cryptographically bind the shop identity to the body — e.g., verify the header `shop-domain` against a shop derived independently (from a resolved/looked-up subscription record for that `webhook_id`) rather than trusting the raw header value. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain, or `HmacValidator`/`Registry.process` should require and validate a per-shop-bound signature component so that replaying a valid payload under a different `shop-domain` header fails verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` (a normal, unprivileged app installation).
2. Attacker performs a store action that triggers a subscribed webhook topic (e.g., `orders/create`), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` and `X-Shopify-Shop-Domain: attacker.myshopify.com` to the app's webhook endpoint.
3. Attacker captures `(B, H)` (they legitimately received/observed their own webhook delivery).
4. Attacker crafts a new HTTP request to the same webhook endpoint with the identical body `B` and identical header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (`B`) using the shared `Context.api_secret_key` — the same for both shops — so validation succeeds: [6](#0-5) 
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` and, if it uses `shop` to route/attribute data (as intended), processes the attacker's forged event as if it came from `victim.myshopify.com`.
