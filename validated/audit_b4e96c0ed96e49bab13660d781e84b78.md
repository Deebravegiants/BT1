### Title
Unaccounted token transfers via arbitrary `EmporiumOperation` calls let any user drain stranded/reward balances held by `EmporiumUpgradeable` without passing the balance equation - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes an arbitrary, prover-supplied list of `EmporiumOperation`s (stateless case: `op.endpoint.call{value: op.value}(op.callData)`), then reconciles only the token addresses listed in `circomData.erc20TokenAddresses` against `deltaAmountChanges`/UTXOs. Any ERC20 balance moved by an op whose token is not included in that array is never checked, refunded, or reconciled — mirroring the AuraSpell/WAuraPools bug where reward tokens returned by an external interaction were never accounted for in the refund logic.

### Finding Description
Inside `EmporiumUpgradeable.runAction`, the stateless-interaction branch performs an arbitrary call chosen entirely by the calldata the caller supplies: [1](#0-0) 

The only accounting performed afterward iterates strictly over `circomData.erc20TokenAddresses`, computing `balanceChange` per declared token and forwarding any surplus to `msg.sender` via `handleOut`: [2](#0-1) 

Nothing forces `circomData.erc20TokenAddresses` to include every token an op call can touch. The circuit/`CircomDataBuilder` only hashes `circomData.externalActionData` (which contains the whole `EmporiumStack`, including the `ops` array) into `calldataHash`/`getSignedMessageHash` — it never constrains *what* the ops are allowed to do, nor does it require every ERC20 address touched by an op to appear in `erc20TokenAddresses`: [3](#0-2) [4](#0-3) 

Because `EmporiumUpgradeable` is a shared contract (not a per-user wallet like the `invokeWallet` path that routes through `IHinkalWallet`), any balance it happens to hold — e.g. reward tokens accrued from a prior user's staking/farming op that weren't declared in that prior transaction's `erc20TokenAddresses` (exact analog of WAuraPools sending back multiple reward tokens while `AuraSpell#openPositionFarm` only refunded Aura) — sits there unprotected. An attacker can construct their own `transact()` call with a stateless op such as `IERC20(R).transfer(attacker, strandedBalance)` where `R` is deliberately omitted from `circomData.erc20TokenAddresses`. This transfer:
- happens outside the `Hinkal.sol` balance-equation loop that enforces `balanceDif == amountChanges[i] + utxoAmount` and `slippageValues[i]` for the caller's own transaction: [5](#0-4) 
- happens outside the `EmporiumUpgradeable.runAction` per-token accounting loop shown above,
- consumes no nullifier and creates no output commitment for `R`.

The attacker thus extracts real ERC20 value from the shared Emporium contract without spending any shielded balance and without the moved value ever appearing in `calldataHash`/public-input-vector-checked fields tied to that value.

### Impact Explanation
This is direct theft of funds held by the protocol's shared external-action contract (reward tokens, dust, or in-flight balances belonging to other users or the protocol) by an unprivileged EOA, with no equality in the balance/UTXO system ever being broken in a way the circuit or `Hinkal.sol` checks catch. This matches the Critical category: direct theft of in-flight/shielded funds via a transferFrom-equivalent operation not authorized by the balance equation.

### Likelihood Explanation
Any user who can call `Hinkal.transact()` with a valid proof for their own real nullifiers (a normal, unprivileged capability) can supply an arbitrary `EmporiumStack`/`ops` payload as calldata; nothing in the circuit or `CircomDataBuilder` restricts the semantics of `op.endpoint`/`op.callData`, only their hash consistency. Exploitation requires no special relayer, admin, or victim cooperation — only that the shared `EmporiumUpgradeable` contract at some point holds an ERC20 balance outside the currently-declared `erc20TokenAddresses` set (a normal occurrence whenever a multi-reward-token DeFi protocol is used through a stateless op).

### Recommendation
Require `runAction` to snapshot balances for *every* token address that an op's `callData` could plausibly move (or, more robustly, disallow raw ERC20 `transfer`/`transferFrom`-style selectors as op targets/selectors unless the token is present in `circomData.erc20TokenAddresses`), and extend the balance-equation check so any non-zero balance change of a token not present in `erc20TokenAddresses` causes the transaction to revert rather than silently leaving/moving funds outside accounting. Alternatively, sweep/refund logic should enumerate all tokens actually touched by the executed ops (as recommended for `WAuraPool` in the source report) rather than trusting a caller-supplied token list.

### Proof of Concept
1. A prior user performs a legitimate Emporium stateless op that stakes/farms and only lists the principal token in `circomData.erc20TokenAddresses`; the protocol later emits a second reward token `R` credited to `EmporiumUpgradeable`'s own balance (never withdrawn/tracked, since `R` wasn't part of that tx's `erc20TokenAddresses`).
2. Attacker (any EOA holding some genuine shielded UTXO to produce a valid proof) calls `Hinkal.transact()` with `externalActionData.externalActionId` set to Emporium and `externalActionMetadata` decoding to an `EmporiumStack` containing one stateless op: `{endpoint: R, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedBalance)}`.
3. Attacker sets `circomData.erc20TokenAddresses` to not include `R` (e.g. an unrelated token or the minimal Emporium path with empty array per `formInputEmporiumMin`).
4. `Hinkal._externalTransact` calls `EmporiumUpgradeable.runAction`, which executes the op at line 112, transferring `strandedBalance` of `R` straight to the attacker.
5. Neither `Hinkal.sol`'s balance-diff loop nor `EmporiumUpgradeable.runAction`'s per-token loop ever inspects `R`, so the transaction completes successfully with the attacker having received real tokens while spending/nullifying none of their own shielded value tied to `R`.
