### Title
Arbitrum Consensus Client Trusts Attacker-Chosen, Potentially Stale L1 State Root Without Freshness/Finality Checks - (File: modules/ismp/clients/ismp-arbitrum/src/lib.rs)

### Summary
`ArbitrumConsensusClient::verify_consensus` lets the relayer pick an arbitrary, already-stored L1 `l1_height` to source the L1 `state_root` used to verify Arbitrum rollup-core storage proofs (challenge state, assertion existence). Unlike the tough delegated-metadata bug (missing expiration/hash/length checks on a "child" metadata path), here the "delegated" trust anchor — a previously verified L1 state commitment — is consumed without any recency, latest-height, or finality/confirmation-window check, so an attacker can bind an Arbitrum consensus update to a historically-valid-but-now-superseded L1 view.

### Finding Description
`ArbitrumConsensusClient::verify_consensus` decodes an untrusted `ArbitrumUpdate { l1_height, proof }` from the relayer-supplied `consensus_proof`, then does: [1](#0-0) 

`l1_height` is fully attacker-controlled and is only constrained by `host.state_machine_commitment(l1_state_machine_height)` succeeding — i.e. any L1 height that Hyperbridge has *ever* stored a commitment for is accepted, with no check that it is the *latest* known L1 height, no check on `state_machine_update_time`/challenge period elapsed for that L1 height, and no check that it falls within any Arbitrum confirmation/challenge window.

This `state_root` is then handed to `verify_arbitrum_bold`/`verify_arbitrum_payload`, which check "is this assertion currently unchallenged" purely against that chosen (possibly old) L1 root: [2](#0-1) 

The BoLD path's entire security property ("this assertion is not currently being challenged") is `parent.secondChildBlock == 0` at the *chosen* L1 root. Arbitrum's on-chain rollup allows a rival assertion (and hence a non-zero `secondChildBlock`) to be created *after* an assertion was created with `secondChildBlock == 0`. By picking an L1 height captured before a challenge was raised (but after the assertion in question was created), an attacker with delegated signing/relaying authority can present a proof that appears "unchallenged" even though, at the current L1 head, the assertion is contested or has since lost the challenge game.

This is structurally identical to the tough advisory's root cause: a secondary/child validation path (`load_delegations` there, the L1-anchor lookup here) omits the same "is this input still valid/current" checks (expiration in tough; recency/finality in Hyperbridge) that the top-level path enforces elsewhere (e.g. `is_expired`/`is_consensus_client_frozen` gate the *top-level* consensus state update in `update_client`, but nothing analogous gates the *L1 anchor height* selected inside `verify_consensus`): [3](#0-2) 

### Impact Explanation
If exploited, this allows forging/poisoning the Arbitrum state commitment stored by Hyperbridge: an attacker-controlled or compromised relayer can get Hyperbridge to accept an Arbitrum L2 state root backed by an assertion that has since been (or currently is) successfully challenged on L1, i.e. an invalid/rejected L2 state. Because this state commitment feeds `StateMachineClient::verify_membership`/`verify_non_membership` for all cross-chain messages routed through that Arbitrum state machine, a forged commitment can be used to forge message delivery (fake `PostRequest`/`GetResponse` proofs) or fabricate non-membership for timeouts, i.e. unbacked message delivery / fund-affecting actions for any app relying on Hyperbridge's Arbitrum consensus client. This satisfies "forged message delivery" / "unsound state commitment" impact criteria.

### Likelihood Explanation
Requires an actor with delegated relayer/signing authority for the Arbitrum consensus client (the class explicitly in scope: relayer submitting `ConsensusMessage`s via `handle_unsigned`), and requires timing a submission around a real challenge event on L1 (i.e. an assertion that was briefly unchallenged and later successfully disputed, or picking a height before a later-raised challenge lands). This is a narrower window than a fully free choice, but the code provides no defense at all against it — there is no requirement that `l1_height` be the latest verified L1 height or within any bounded staleness window, so the vulnerability is fully reachable from a single relayed consensus update.

### Recommendation
- Require `l1_height` to equal (or be no older than a small, explicitly configured staleness bound from) the latest verified L1 state machine height known to the host, rather than accepting any historically stored L1 commitment.
- Alternatively/additionally, enforce Arbitrum's actual confirmation/challenge window: only accept an assertion as "final" if the L1 anchor height is at least `challengePeriod` newer than the assertion's creation height, consistent with how `handlePostRequests`/`update_client` enforce challenge periods elsewhere.
- Mirror the freshness enforcement already present in the top-level consensus-update path (`is_expired`) onto this L1-anchor selection, so delegated/nested lookups can't bypass it.

### Proof of Concept
1. Attacker (a permissioned Arbitrum relayer) observes an assertion `A` created on L1 rollup-core with `parent.secondChildBlock == 0` at L1 height `H0`. Hyperbridge has previously stored the L1 state commitment for `H0` (from ordinary L1 consensus updates).
2. A rival assertion is later submitted on L1 at height `H1 > H0`, setting `parent.secondChildBlock != 0` (challenge in progress / assertion `A` ultimately loses).
3. Attacker submits a `ConsensusMessage` to `handle_unsigned` with `ArbitrumUpdate { l1_height: H0, proof: ArbitrumBold(proof_for_A) }`.
4. `ArbitrumConsensusClient::verify_consensus` fetches the L1 commitment at `H0` (still present in storage, no freshness check), and `verify_arbitrum_bold` succeeds because `secondChildBlock == 0` at `H0`, even though assertion `A` is contested/invalid as of the current L1 head `H1`.
5. Hyperbridge stores a state commitment for the Arbitrum state machine derived from the now-invalid assertion `A`, which can subsequently be used to forge membership/non-membership proofs for that state machine.
