### Title
Webhook shop/topic identity spoofing — HMAC only covers the raw body, not the `shop-domain` header used for tenant routing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, but the signature is computed only over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are never part of the signed material, yet they are the fields the handler acts on to decide *which tenant's data this is* and *which handler to dispatch to*.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the identity-carrying fields — `shop`, `topic`, `webhook_id`, `api_version` — are read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only that HMAC, then dispatches using the unauthenticated `shop` header value: [3](#0-2) 

Because `OpenSSL::HMAC.hexdigest(secret, raw_body)` (used identically by `HmacValidator.validate_signature`) depends only on `raw_body` and the shared `api_secret_key`: [4](#0-3) 

any request whose body bytes match a body Shopify has legitimately signed for the app (e.g., the attacker owns a shop with the same app installed and can generate/replay a webhook with identical or attacker-controlled JSON body content, since `hmac` is computed over the raw payload only) will pass validation regardless of the `shop-domain`, `topic`, or `webhook-id` header values supplied. This breaks the equality that should hold: `shop_header == shop_bound_by_signature`. In this gem, that equality never exists — the signature binds `HMAC == f(secret, body)` only, and `shop`, `topic`, `webhook_id` are asserted, not verified.

### Impact Explanation
An attacker who controls a shop with the app installed (an unprivileged, non-merchant-token requirement — they only need their own shop and no elevated credentials) can produce an HMAC-valid webhook body and then deliver it to the app's webhook endpoint with a spoofed `x-shopify-shop-domain`/`shopify-shop-domain` header naming a *different* merchant's shop. Because `Registry.process` trusts `request.shop` when building `WebhookMetadata` passed to the app's handler, the app's own webhook handler code will process data under the wrong tenant identity — a cross-tenant data/action confusion inside the host application, driven entirely by this gem's failure to bind the tenant identity to the signature. This matches the "cross-tenant access" impact class, since the vulnerability's exploitation path goes purely through fields this gem accepts and forwards as trusted (`shop`, `topic`, `webhook_id`) without any binding to the one thing that is actually verified (the raw body bytes).

### Likelihood Explanation
Exploitation requires only: (1) the attacker controls a shop with the target app installed (no privileged credentials, no access to the target's tokens/secrets), and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with attacker-chosen headers — both realistic capabilities for an "unprivileged internet user." The gem provides no additional binding (e.g., no HMAC over headers, no signed shop claim) to prevent this, so likelihood is moderate-to-high wherever a host app trusts `WebhookMetadata#shop` for tenant-scoped logic without independently re-validating shop identity (e.g., against the session/subscription that registered the webhook).

### Recommendation
Include the identity-carrying header fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string, not just the raw body, so the signature binds the full identity tuple rather than only the payload bytes. Alternatively/additionally, document and enforce that consuming applications must cross-check `WebhookMetadata#shop` against an independently known/registered shop for the given webhook subscription before trusting it for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimately signed webhook with raw body `B` and valid `hmac = HMAC(api_secret_key, B)`.
2. Attacker POSTs to the app's webhook endpoint with the same raw body `B` and the same valid `hmac`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (only checks header *presence*, not content binding) — see [5](#0-4) .
4. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B` — see [6](#0-5) .
5. `Registry.process` dispatches to the registered handler with `shop: "victim.myshopify.com"` — see [3](#0-2) , causing the host app's handler to act on/attribute data to the victim shop using attacker-controlled body content.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
