### Title
Permissionless `CallDispatcher.dispatch` lets any order's calldata leave a standing token approval that later drains balances the shared dispatcher temporarily holds for other orders - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, chain-wide shared contract used by `IntentGatewayV2` (predispatch/postdispatch) and the `HyperFungibleToken`/`WrappedHyperFungibleToken` apps to execute arbitrary attacker-supplied calldata while briefly holding user/solver funds. Its `dispatch()` entry point has no access control and no allowance bookkeping. If any single order's calldata grants an ERC-20 approval from the dispatcher to an attacker-controlled address (instead of the single-use router approval documentation recommends), that approval persists on the shared contract indefinitely. Because the dispatcher is reused by every subsequent `placeOrder`/`fillOrder`/HFT `send` that specifies calldata, an attacker can later pull out whatever tokens are transiently routed through the dispatcher by unrelated orders, without needing any additional interaction with those orders.

### Finding Description
`CallDispatcher.dispatch()` decodes an arbitrary `Call[]` and executes each call with itself as `msg.sender`, with zero caller restriction and no tracking of what allowances calldata has created: [1](#0-0) 

`IntentGatewayV2.placeOrder` transfers predispatch input assets to this same shared `dispatcher` address, then invokes `dispatch(order.predispatch.call)` with attacker-fully-controlled calldata before sweeping the dispatcher's resulting balance back into escrow: [2](#0-1) 

The same pattern is used for postdispatch output calldata in `_execute`, and for `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain deliveries, all of which reuse the same `CallDispatcher` instance: [3](#0-2) [4](#0-3) 

The project's own documentation flags the underlying hazard but does not enforce it on-chain: predispatch/postdispatch calldata "should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution." [5](#0-4) 

Because `dispatch()` is fully permissionless and the dispatcher's balance/allowance state is never reset between unrelated top-level transactions, an attacker only needs to place one order whose `predispatch.call` (or `output.call`) contains `IERC20(token).approve(attacker, type(uint256).max)`. This is executed with the dispatcher as `msg.sender`, so the approval is durably recorded against the dispatcher's own token balance. From that point forward, whenever any other user's/solver's order routes the same token through the dispatcher (predispatch swap-then-escrow, or postdispatch fill-then-act), the attacker can front-run or simply wait and call `token.transferFrom(dispatcher, attacker, amount)` directly (bypassing the gateway/`dispatch` entirely) to steal the balance the dispatcher is holding mid-flow or any residual dust before it is swept, since the approval never expires and is reusable across every future user of the shared dispatcher.

This mirrors the LeetSwap root cause: an externally-callable function (`_transferFeesSupportingTaxTokens` there, `dispatch()` here) allows unrestricted manipulation of a pooled/shared balance holder, letting an attacker set up state (fee-token transfer there, standing approval here) that is later exploited to redirect funds intended for legitimate participants.

### Impact Explanation
Any tokens that transiently sit in `CallDispatcher` for the swap-then-escrow (predispatch) or fill-then-act (postdispatch) flows of unrelated `IntentGatewayV2` orders, or that are forwarded during `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata delivery, are at risk of being pulled by an attacker holding a previously-planted `approve` from the dispatcher. This is concrete theft of escrowed/bridged user and solver funds reachable from a single unprivileged, attacker-submitted order — satisfying the Medium/High bar (unauthorized app action / theft of funds routed through a shared, permissionless intermediary).

### Likelihood Explanation
Exploitation requires only: (1) placing one attacker order with malicious predispatch/postdispatch calldata that sets an approval from the dispatcher to the attacker (a single `placeOrder` call, fully unprivileged), and (2) waiting for any other order to route matching tokens through the same shared dispatcher instance, which happens routinely for swap-then-escrow and fill-then-act flows. No governance, admin, relayer, or consensus compromise is needed — only a submitted transaction, matching the scope of reachable attack paths (intents escrow/bids, token bridger calldata delivery).

### Recommendation
- Make `CallDispatcher` non-reusable/ephemeral per call (e.g., deploy a fresh minimal-proxy instance per `dispatch()` invocation, or use `delegatecall`-free single-use contracts) so no approval or balance persists after the calling transaction completes.
- Alternatively, harden `CallDispatcher.dispatch()` to revoke any allowances it granted before returning (scan and zero out approvals created during the batch), or restrict `approve`-type calls entirely from the allowed `Call[]` targets.
- Restrict `dispatch()` callers to the known set of trusted apps (`IntentGatewayV2`, `HyperFungibleToken`, etc.) via `onlyAuthorizedCaller`, and require the dispatcher to end each transaction with a zero balance/zero allowance invariant check for the tokens involved in that call.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with a `predispatch.call` (or `output.call` on `fillOrder`) whose `Call[]` includes:
   `Call({ to: TOKEN, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max) })`, executed via `ICallDispatcher(dispatcher).dispatch(...)` — this executes with `CallDispatcher` as `msg.sender`, so `TOKEN.allowance(dispatcher, attacker) == type(uint256).max` afterward.
2. At any later time, a legitimate user places/fills another order in `TOKEN` whose predispatch or postdispatch flow moves `TOKEN` into the same shared `dispatcher` address (per `IntentGatewayV2.sol:250,274` / `IntentsBase.sol:518`).
3. Attacker calls `TOKEN.transferFrom(dispatcher, attacker, amount)` directly — no interaction with `IntentGatewayV2` or `dispatch()` required — draining the balance the dispatcher is holding for the legitimate order before (or instead of) the gateway's own sweep call executes.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
