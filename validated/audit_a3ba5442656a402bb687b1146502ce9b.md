### Title
Withdraw reverts entirely instead of allowing partial redemption when computed coin/pc amounts are not strictly less than actual vault balances - (File: program/src/processor.rs)

### Summary
`process_withdraw` computes the LP holder's proportional share of the pool's *internal* accounting totals (`total_coin_without_take_pnl` / `total_pc_without_take_pnl`, which exclude protocol PnL that is still sitting in the vaults) and then requires that both derived amounts be **strictly less than** the actual vault token-account balances before any transfer happens. If either derived amount is **not** strictly less than the vault balance, the entire withdrawal is rejected with no partial-payout fallback, mirroring the Unitas `_swapOut`/`withdrawCollateral` DOS pattern where a shortfall between "accounted" reserves and "real" reserves blocks user withdrawals outright.

### Finding Description
In `Processor::process_withdraw` (program/src/processor.rs), the pool's coin/pc entitlement is computed from `total_coin_without_take_pnl`/`total_pc_without_take_pnl`, values obtained via `Calculator::calc_total_without_take_pnl_no_orderbook` and then adjusted by `Self::calc_take_pnl`, which subtracts pending, not-yet-swept protocol PnL (`amm.state_data.need_take_pnl_coin/pc`) from the raw vault balances: [1](#0-0) 

The resulting per-LP amounts are then gated by a strict-inequality check against the *actual* vault balances before any tokens are moved or LP burned: [2](#0-1) 

This is functionally identical to the Unitas bug class: the contract maintains an *internal accounting view* of available reserves (here: vault balance minus pending, unswept protocol PnL) that is used to gate a user-facing withdrawal, and when that internal view diverges unfavorably from what a strict comparison demands (i.e., the computed share is not strictly smaller than the vault's raw balance), the whole withdrawal is aborted with `AmmError::TakePnlError` instead of degrading to a partial/best-effort payout. Unlike Unitas's `_swapOut`, which explicitly tries to pull a shortfall from an external Insurance Pool and reverts on insufficient collateral, Raydium's equivalent failure mode is the `else` branch at processor.rs:1813-1816, which unconditionally reverts rather than paying out `min(coin_amount, amm_coin_vault.amount)` / `min(pc_amount, amm_pc_vault.amount)`.

Note that a full-pool drain scenario (`withdraw.amount == amm.lp_amount`) is already explicitly disallowed earlier: `program/src/processor.rs:1716` (`AmmError::NotAllowZeroLP`), which narrows — but does not eliminate — the situations under which the strict-inequality check at line 1779 can fail, since accumulated pending PnL, decimal-normalization rounding in `calc_take_pnl`/`normalize_decimal_v2`, and the state of `need_take_pnl_coin/pc` at withdrawal time all affect whether `coin_amount`/`pc_amount` remain strictly below the raw vault balances for a given LP redemption size.

### Impact Explanation
If the strict-inequality invariant is violated for a given withdrawal size (e.g., large redemption combined with outstanding unswept protocol PnL that has not yet been reconciled via `WithdrawPnl`), `process_withdraw` reverts with `TakePnlError` for every retry with the same LP amount, and the LP holder has no way to redeem a partial amount instead. This is a freezing-of-user-funds condition analogous to the reported issue, reachable purely through the public `Withdraw` instruction by any LP holder with attacker/user-chosen accounts and data (a valid LP-token amount).

### Likelihood Explanation
Likelihood depends on the pool's pending-PnL state and the size/timing of the withdrawal relative to `need_take_pnl_coin`/`need_take_pnl_pc`, and can be influenced by protocol/admin cadence of calling `WithdrawPnl` as well as by rounding in `Calculator::normalize_decimal_v2`/`restore_decimal`. It is not attacker-controlled in the same directly-triggerable way as an external insurance-pool shortfall, so exploitability is state-dependent rather than trivially reproducible on demand, which is why this should be treated as a caveated analog rather than a confirmed, immediately-triggerable finding without further on-chain state simulation.

### Recommendation
Instead of aborting the entire withdrawal when `coin_amount`/`pc_amount` are not strictly less than the vault balances, cap the payout at `min(coin_amount, amm_coin_vault.amount)` and `min(pc_amount, amm_pc_vault.amount)`, burn LP proportionally to what was actually paid out (or leave the remainder redeemable), and only treat a shortfall as an unrecoverable error if it results in a zero payout. This avoids permanently blocking legitimate LP withdrawals due to a temporary mismatch between internal PnL accounting and raw vault balances.

### Proof of Concept
Not concretely provable from static review alone: reproducing the strict-inequality failure requires simulating `calc_take_pnl`'s interaction with `need_take_pnl_coin/pc`, `target_orders.calc_pnl_x/y`, and `normalize_decimal_v2` rounding across a sequence of deposits/swaps/withdrawals to drive `coin_amount == amm_coin_vault.amount` (or `pc_amount == amm_pc_vault.amount`) for a chosen `withdraw.amount < amm.lp_amount`. This would require an integration/unit test harness (e.g., extending the existing tests around `program/src/processor.rs:3122-3212`) to confirm feasibility; I could not fully verify triggerability within the scope of this review.
