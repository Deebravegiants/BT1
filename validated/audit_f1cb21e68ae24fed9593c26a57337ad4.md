### Title
Missing zero-address validation in `IntentGatewayV2` constructor permanently bricks the Tron intent gateway - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` sets the one-time admin key in its constructor without validating it is non-zero, unlike the canonical EVM `IntentGatewayV2`, which already guards against this. If deployed with a zero (or otherwise unreachable) admin, the contract can never have its `Params` initialized, permanently disabling the intent gateway's dispatch route.

### Finding Description
The constructor simply stores the admin with no validation: [1](#0-0) 

`_admin` is the sole authority allowed to call `setParams`, the only function that sets `_params` (which in turn determines `host()`, the ISMP host address used for every dispatch/receive path): [2](#0-1) [3](#0-2) 

If `admin` is passed as `address(0)` (accidentally, or because the deploy tooling defaults an unset env var to zero), `_admin` stays `address(0)` forever, since `setParams` is the only writer and it requires `msg.sender == _admin`. `msg.sender` can never legitimately be `address(0)`, so `setParams` — and therefore initialization of `_params.host` and all other gateway parameters — becomes permanently unreachable. `host()` then always returns `address(0)`, and every subsequent `placeOrder`/fill/incoming-message path that depends on `host()` or `_params` is broken for the lifetime of the deployed contract, since there is no re-deploy-free recovery path.

This is the exact bug class from the report: a constructor parameter (an authority/owner address) is not checked for the zero address, and a zero value renders the contract permanently unusable. Notably, the sibling production contract `evm/src/apps/IntentGatewayV2.sol` already had this exact fix applied (see the project's own changelog entry noting "The gateway constructor now rejects a zero owner, since a mis-set `ADMIN` would leave no key able to arm a fresh proxy"): [4](#0-3) [5](#0-4) 

The Tron port at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated with the equivalent guard, leaving the same class of bug present on that chain's deployment.

### Impact Explanation
A gateway deployed with a zero admin can never have `_params` set, so `host()` permanently resolves to `address(0)`. This means:
- No order can ever be correctly dispatched or filled through the ISMP host on that chain, since the host address is never bound.
- Any user funds sent to `placeOrder` before this is discovered would interact with a gateway that cannot correctly route to the configured host, risking stuck/frozen funds in escrow with no governance path to fix the params.
- There is no recovery mechanism — the admin gate is permanently one-shot and irreversible, matching the "route unable to deliver messages" / permanent freezing-of-funds impact class.

### Likelihood Explanation
This requires a specific deployment misconfiguration (admin parameter defaulting/being passed as zero), so it is not attacker-triggered on a properly configured deployment. However, deploy scripts reading environment variables (as seen with `GOVERNANCE_RELAYER`/`ADMIN` elsewhere in this codebase) are exactly the kind of input that can silently default to zero, and the project's own changelog shows this exact failure mode was already found and fixed once for the main EVM contract — indicating a real, recurring operational risk for the Tron fork that inherited the same pattern without the fix.

### Recommendation
Add a zero-address check in the Tron `IntentGatewayV2` constructor mirroring the fix already applied in `evm/src/apps/IntentGatewayV2.sol`:
```solidity
constructor(address admin) EIP712("IntentGateway", "2") {
    if (admin == address(0)) revert InvalidInput();
    _admin = admin;
}
```

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with `admin = address(0)` (e.g., via a deploy script that fails to populate the admin env var).
2. Observe `_admin` is `address(0)`.
3. Attempt to call `setParams(params)` from any account — the check `msg.sender != _admin` at [3](#0-2)  always reverts with `Unauthorized`, since no externally-owned or contract account can have `msg.sender == address(0)`.
4. `_params` (and thus `host()`) remains permanently unset/zero, and the gateway is permanently non-functional with no admin-recovery path.
