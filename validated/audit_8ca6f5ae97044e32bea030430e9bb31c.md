### Title
Emporium `runAction` lets unprivileged callers drain any token balance held by the shared Emporium contract by omitting the drained token from `erc20TokenAddresses` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only reconciles balances for the tokens the caller lists in `circomData.erc20TokenAddresses`, an attacker-supplied array, and only reverts on a *negative* change for those listed tokens [1](#0-0) . When `stack.signerAddress == address(0)`, `verifyWallet` performs no signature check at all beyond marking the nonce used [2](#0-1) , so any caller can freely craft `stack.ops` performing arbitrary `op.endpoint.call(op.callData)` as Emporium itself [3](#0-2) . Combining these two facts, an attacker can move any token balance Emporium already holds (stranded refunds, other users' parked funds, or a token to which Emporium/router has a standing `approveUnlimited` allowance from a LI.FI-style op) straight to their own address, while excluding that token from the checked array so the loss is never detected.

### Finding Description
The invariant that should hold is: *tokens leaving the Emporium action in a transaction == `-deltaAmountChanges` that Hinkal sent it in that same transaction, for every token the action touched*. `runAction` only enforces this for tokens present in `circomData.erc20TokenAddresses`, which is fully attacker-controlled per-transaction input (confirmed scope rule: "Attacker controls: ... erc20TokenAddresses ordering").

Root cause chain:
1. `runAction` decodes an `EmporiumStack` from `externalActionMetadata` (attacker-controlled) and executes every `op` in `stack.ops` before any balance checks run [4](#0-3) .
2. For "Stateless Interaction" (`op.invokeWallet == false` or `stack.signerAddress == address(0)`), the only restriction is that the selector cannot be `callHinkalWallet`/`doSendToRelay`; any other endpoint/calldata is permitted [3](#0-2) .
3. `verifyWallet` requires a valid EIP-712 signature only when `stack.signerAddress != address(0)`; if it's `address(0)` it returns immediately after marking the message used — no authorization is required for these unauthenticated stateless ops [2](#0-1) .
4. After the ops run, the contract computes `balancesAfter` only for `circomData.erc20TokenAddresses` and reverts only if the (deltaAmountChanges-adjusted) change for a *listed* token is negative [5](#0-4) . Any token not listed is completely unchecked.
5. `TransfererBase.approveUnlimited` (used by `LifiExternalAction.callRouter` for token-based LI.FI swaps) leaves an unlimited standing allowance from the acting contract to `router` once granted, and is re-used across calls (`allowance < type(uint256).max/2` guard) [6](#0-5) [7](#0-6) .

Exploit flow: the attacker deposits a trivial amount of their own token `Y` into the shielded pool and generates a valid proof calling `Emporium.runAction` with:
- `circomData.erc20TokenAddresses = [Y]` only (excluding the target token `X` that Emporium currently holds a balance of, e.g. dust/stranded funds, or an unswept balance to which a standing `approveUnlimited(X, router)` exists from a prior LI.FI op),
- `stack.signerAddress = address(0)` (no signature required),
- `stack.ops = [{ endpoint: X (or router), invokeWallet:false, value:0, callData: <transfer(attacker, amount)> or <malicious router calldata directing output to attacker> }]`.

`runAction` executes the op as Emporium (moving `X` out to the attacker or through the router to the attacker, exploiting the standing allowance), and since `X` is absent from `erc20TokenAddresses`, its depletion is never measured or checked. Only `Y`'s balance is reconciled and matches the attacker's own legitimate small deposit, so the transaction succeeds and `handleOut` mints the attacker a correct UTXO for `Y` while `X` silently leaves the contract to the attacker's address with zero relation to `deltaAmountChanges`.

Existing guards fail because: `performHinkalChecks`/proof verification only constrain the attacker's own UTXO inputs/outputs and `deltaAmountChanges` for the tokens *they* declare — they do not constrain what `erc20TokenAddresses` must contain, nor what arbitrary `stack.ops` may touch; `verifyWallet` is bypassed entirely for `signerAddress == address(0)`; and the `balanceChange < 0` revert in `runAction` only applies to tokens present in the array.

### Impact Explanation
Direct theft of funds parked in (or in-flight through) the Emporium action — including other users' stranded/refunded balances and any balance reachable via a standing router allowance from a prior LI.FI-style op — by an unprivileged attacker, without needing any signature or role. This is repeatable for every token balance Emporium ever accumulates that isn't included by the attacker in their own `erc20TokenAddresses` array. This matches the Critical category: "direct theft of shielded or in-flight user funds."

### Likelihood Explanation
- No privileged role, signature, or victim cooperation required.
- Attacker only needs to be able to submit a normal `Hinkal.transact` call with a self-crafted `EmporiumStack` (fully attacker-controlled metadata) and a trivial deposit of their own funds to satisfy proof/balance constraints on the declared token.
- Preconditions: Emporium (or a token it has previously `approveUnlimited`'d to a router) must be holding a residual/stranded balance of some other token — plausible given Emporium's design as a shared multi-user pooled contract that can accumulate dust, partial refunds, or amounts left after slippage/partial swaps.
- Cost is a single transaction plus gas; gain scales with whatever balance is currently stranded in Emporium.

### Recommendation
- Require `circomData.erc20TokenAddresses` to be validated/derived from a protocol-controlled or circuit-constrained source rather than trusting attacker-supplied arrays for balance reconciliation, or reconcile balances against a fixed, exhaustive list of tokens the action is permitted to touch.
- For "Stateless Interaction" ops (`stack.signerAddress == address(0)`), do not allow fully unauthenticated arbitrary `endpoint.call(callData)` — at minimum, restrict callable endpoints/selectors to a protocol-defined allowlist (e.g., only the declared router with output constrained back to the Emporium contract), and require any token balance touched by an op to be included in the reconciliation array.
- Avoid unlimited/standing approvals (`approveUnlimited`) to routers from shared, multi-tenant contracts like Emporium; approve only the exact amount needed per call and revoke afterward.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20 `X`, mock ERC20 `Y`, and a mock router.
2. Seed `X` balance directly into the Emporium contract (simulating stranded/refunded funds from a prior session) — this represents the "residual value."
3. Have the attacker EOA deposit a trivial amount of `Y` into the shielded pool and construct a valid Hinkal proof calling `Emporium.runAction` with:
   - `circomData.erc20TokenAddresses = [Y]`,
   - `deltaAmountChanges` matching only the attacker's own trivial `Y` deposit,
   - `externalActionMetadata` encoding `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: X, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount) }] }`.
4. Assert equality before: `X.balanceOf(Emporium) == strandedAmount`, `X.balanceOf(attacker) == 0`.
5. Execute `Hinkal.transact` → `Emporium.runAction`.
6. Assert equality after: transaction succeeds without revert; `X.balanceOf(attacker) == strandedAmount` (funds stolen); `X.balanceOf(Emporium) == 0`; and no `deltaAmountChanges` entry ever accounted for token `X`, proving `tokens_leaving_action(X) != -deltaAmountChanges(X)` (the latter being undefined/absent), confirming the broken invariant.
