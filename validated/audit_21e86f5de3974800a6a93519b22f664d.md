Confirmed: `AuthQuery` (`lib/shopify_api/auth/oauth/auth_query.rb`) does not call `ShopValidator.sanitize!` anywhere, and neither does `Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb`). By contrast, `ClientCredentials`, `RefreshToken`, and `Graphql::Storefront` all invoke `ShopValidator` before using a shop value.

### Title
OAuth authorization-code callback sends `client_secret` to an unvalidated `shop` host, breaking the "signed shop equals trusted Shopify domain" binding - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Oauth.validate_auth_callback` verifies the HMAC over the callback query string, but never validates that `auth_query.shop` is a genuine `*.myshopify.com` (or otherwise trusted) domain before using it as the destination host for the access-token exchange request, which carries the app's `client_id`/`client_secret`.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`, `validate_auth_callback` does: [1](#0-0) 
It only checks `Utils::HmacValidator.validate(auth_query)` and cookie/state equality, then immediately builds `null_session = Auth::Session.new(shop: auth_query.shop)` and POSTs `{client_id, client_secret, code, expiring}` through `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`.

`Auth::Session#initialize` (`lib/shopify_api/auth/session.rb`, lines 70-86) stores `shop` verbatim with no domain validation. `Clients::HttpClient#initialize` then builds the request host directly from that value: [2](#0-1) 
So the POST containing the app's `client_secret` and the OAuth `code` goes to `https://#{auth_query.shop}/admin/oauth/access_token` — wherever `auth_query.shop` says, with no membership check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

Contrast this with other flows in the same gem that do call `Utils::ShopValidator.sanitize!` before using a shop string as a request host — e.g. `ClientCredentials`, `RefreshToken`, and `Clients::Graphql::Storefront` (confirmed via grep: `ShopValidator` is referenced in `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/clients/graphql/storefront.rb`, but not in `lib/shopify_api/auth/oauth.rb` or `lib/shopify_api/auth/oauth/auth_query.rb`).

This maps directly onto the report's bug class: the HMAC/identity check (`hmac` covering `code, host, shop, state, timestamp`) binds those fields to each other, but does **not** bind `shop` to "is a Shopify-owned host." The equality that should hold is:
`shop used to receive client_secret == shop ∈ TRUSTED_SHOPIFY_DOMAINS`
but the code only enforces `hmac(shop, code, state, host, timestamp) == received_hmac`, which says nothing about whether `shop` itself is legitimate. If the host application populates `AuthQuery` from raw request parameters (as the gem's own docs sample shows) without separately sanitizing `shop`, and if there exists any way for `shop`/`state`/`hmac` to be attacker-influenced end to end (e.g., a host app that doesn't independently pin `shop` before calling `begin_auth`, or reuses `begin_auth`'s route construction which also uses the raw `shop` in `auth_base_uri` with no validation — `lib/shopify_api/auth/oauth.rb` lines 117-128), the gem itself provides no defense-in-depth against a non-`myshopify.com` `shop` value reaching the access-token POST.

### Impact Explanation
If a non-Shopify `shop` value reaches this code path, the app's `client_id`/`client_secret` and the victim's one-time `code` are transmitted to an attacker-controlled host, which is functionally equivalent to leaking the app's `client_secret` and enabling theft of the resulting access token for the targeted shop — a Critical-class outcome under the stated impact categories (theft/exfiltration of the app's `client_secret` and an access token via SSRF-with-credentials).

### Likelihood Explanation
Likelihood is limited by the fact that `auth_query.hmac` must be a valid HMAC over the exact `code/host/shop/state/timestamp` tuple computed with the app's own `api_secret_key`, which in the normal flow only Shopify can produce for a given `shop`. I could not find, within the in-scope files, a path where an unprivileged internet user can supply an arbitrary `shop` value AND a matching valid `hmac` without already controlling `api_secret_key` (which is out of scope per the rules). The `begin_auth`/`auth_base_uri` path (lines 117-128) is more directly reachable if a host app forwards a raw `shop` query parameter to `begin_auth`, since that path has no HMAC gate at all, but exploiting it depends on the host application's own routing of untrusted input into `begin_auth`, which is arguably "the host application ignoring documented usage" (out of scope per the rules) rather than a flaw purely internal to this gem.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: ...)` on `auth_query.shop` (and on the `shop:` parameter to `begin_auth`) before it is used to construct `auth_base_uri`/`Session`/`HttpClient` base URIs in `lib/shopify_api/auth/oauth.rb`, mirroring the pattern already used in `client_credentials.rb`, `refresh_token.rb`, and `graphql/storefront.rb`.

### Proof of Concept
Could not be fully constructed and verified within the available read-only access, because it depends on unverified assumptions about how a specific host application wires unvalidated `shop` input into `AuthQuery`/`begin_auth`, and on whether a valid HMAC for an attacker-chosen `shop` can ever be produced without the app's secret. This is a structural gap (missing `ShopValidator` call) rather than a demonstrated exploit chain fully inside gem code; a background Devin session with test-harness access would be needed to attempt to reproduce end-to-end behavior against `Oauth.begin_auth`/`validate_auth_callback`.

        def validate_auth_callback(cookies:, auth_query:)

          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]

          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }
