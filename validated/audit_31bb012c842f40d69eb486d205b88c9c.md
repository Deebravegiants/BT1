### Title
msg.value double-counted across duplicate `address(0)` entries in `erc20TokenAddresses` allows minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
In `Hinkal.transact`, the balance-reconciliation loop recomputes `balanceDif` for the native-ETH branch as `newBalances[i] + msg.value - oldBalances[i]` independently for every index `i` where `erc20TokenAddresses[i] == address(0)`. Because `oldBalances`/`newBalances` are snapshotted once for the whole array (not per-token), every duplicate `address(0)` entry gets the exact same `balanceDif`, letting a single `msg.value` satisfy the balance equation for two (or more) independent token "slots," each of which mints its own shielded UTXO via `amountChanges[i]`.

### Finding Description
The broken equality is: **total shielded value minted for ETH == real ETH received (`msg.value`) exactly once**. The code instead allows: **total shielded value minted for ETH == `msg.value` × (number of duplicate `address(0)` entries)**.

Path: `Hinkal.transact` (contracts/Hinkal.sol lines 78-147) computes: [1](#0-0) 
`oldBalances`/`newBalances` come from `getBalancesForArray`, which for `address(0)` simply returns `address(this).balance` at the time of the call — the same value for every duplicate `address(0)` index in the array: [2](#0-1) 
So if `erc20TokenAddresses = [address(0), address(0)]`, `oldBalances[0]==oldBalances[1]` and `newBalances[0]==newBalances[1]`, hence `balanceDif[0] == balanceDif[1]`, both equal to the same `msg.value`-inflated delta.

For an internal transact (`externalActionId == 0`), `checkOnchainCreation` forces `onChainCreation[i] == false` for every index: [3](#0-2) 
and `utxoSet` stays empty because it is only populated in the `_externalTransact` branch: [4](#0-3) 
So the final balance equation collapses, per index, to `balanceDif[i] == amountChanges[i]`: [5](#0-4) 
Since `balanceDif[0] == balanceDif[1]` by the duplication bug, the attacker simply sets `amountChanges[0] == amountChanges[1] == X == msg.value`, and both checks pass with a single real deposit of `X` ETH.

In `_internalTransact`, both indices independently take the `deltaAmountChange > 0` branch and call `transferERC20TokenFromOrCheckETH(address(0), externalAddress, address(this), X)` twice, which only asserts `msg.value == X` (a check, not a transfer, when `_to == address(this)`): [6](#0-5) [7](#0-6) 
This check trivially passes twice for the same `msg.value` — no additional ETH is required.

Meanwhile, in the proof/circuit inputs, the attacker controls two independent token "slots" (both mapped to `address(0)`), each with its own `inTotal_i + amountChanges_i == outTotal_i` constraint and its own set of output commitments. The attacker can set slot 0: `inTotal=0, amountChanges=X, outTotal=X` (mint UTXO #1 = X ETH) and slot 1: `inTotal=0, amountChanges=X, outTotal=X` (mint UTXO #2 = X ETH) — both fully valid inside the circuit for the attacker's own outputs. On-chain, nothing prevents duplicate token addresses in `erc20TokenAddresses` (`dimensionsCheck` in `HinkalHelper.sol` only checks array-length consistency, never uniqueness of `erc20TokenAddresses` entries), so both slots pass the (bugged) balance equation with only one real ETH deposit of `X`.

Net effect: attacker deposits `X` ETH once and mints two shielded UTXOs each worth `X` ETH (total `2X`), i.e., unbacked shielded value equal to the extra duplicated `msg.value`.

Existing guards that fail to catch this: `performHinkalChecks`/`dimensionsCheck` (no address-uniqueness check), `checkOnchainCreation` (irrelevant to this path, only blocks `onChainCreation`), the slippage check (trivially satisfied since `balanceDif == amountChanges`), and the balance-equation `require` itself (defeated exactly because it re-derives the same inflated `balanceDif` per duplicate index instead of tracking `msg.value` consumption once globally).

### Impact Explanation
The attacker mints `(N-1)·X` extra unbacked shielded ETH for every `N` duplicate `address(0)` entries used with a real deposit of `X`, directly causing protocol insolvency (the pool's tracked shielded liabilities exceed the actual ETH held by the contract). This matches the Critical category: "minting shielded value without backing (protocol insolvency)." The attack is repeatable per transaction and scales with the number of duplicated `address(0)` slots (bounded only by dimension/array-size limits), so an attacker can drain the entire protocol's ETH reserves over repeated calls by redeeming the extra minted UTXOs.

### Likelihood Explanation
No privileged role is required — any unprivileged EOA can call `Hinkal.transact` directly with `externalActionId == 0`, craft `erc20TokenAddresses` with duplicate `address(0)` entries, generate a valid proof for their own UTXOs (since they fully control the circuit's public inputs and their own output commitments), and send `msg.value = X`. The only "cost" is `X` (which is fully recoverable since the attacker also receives corresponding legitimate shielded value at index 0), so the marginal cost to mint the extra unbacked UTXO(s) is effectively zero beyond gas and proof generation. This is a straightforward, repeatable exploit requiring only self-controlled inputs.

### Recommendation
Aggregate the `msg.value` credit once per unique token address rather than once per array index. Specifically, before the per-index loop, deduct `msg.value` from `oldBalances`/`newBalances` accounting a single time (e.g., add `msg.value` to `balanceDif` only for the *first* occurrence of `address(0)` in `erc20TokenAddresses`, or reject/require that `erc20TokenAddresses` contains at most one `address(0)` entry, or better, require all entries in `erc20TokenAddresses` to be unique). Enforce this uniqueness check inside `dimensionsCheck` or directly in `Hinkal.transact` before the balance loop.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with a mocked/whitelisted `HinkalHelper` and verifier that accepts a locally-generated proof for an internal transact (`externalActionId == 0`).
2. Build `circomData` with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, `slippageValues = [0, 0]`, and craft the accompanying nullifiers/commitments so the circuit constraint `inTotal_i + amountChanges_i == outTotal_i` holds independently for both slots, producing two output UTXOs each of value `X` ETH.
3. Call `hinkal.transact{value: X}(...)` from an attacker EOA (`externalActionData.externalAddress == attacker`).
4. Assert the call succeeds (does not revert on the balance-equation `require`).
5. Assert the equality violation: `address(this).balance` increased by exactly `X`, but the two newly inserted commitments decode/represent a total shielded ETH value of `2X` (i.e., `sum(mintedUTXOs.amount) > address(this).balance - balanceBefore`).
6. Optionally show redemption: withdraw both UTXOs via a subsequent internal transact and observe the contract's ETH balance goes negative relative to tracked shielded liabilities (or the second withdrawal reverts due to insufficient contract balance — demonstrating insolvency/DoS for other depositors' funds).

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }
