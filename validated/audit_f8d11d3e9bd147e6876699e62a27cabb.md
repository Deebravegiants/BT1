Based on my investigation, I found an analogous unsafe-downcast pattern in the Hyperbridge codebase, reachable from an unprivileged user placing an order through `IntentGatewayV2.placeOrder`.

### Title
Unsafe downcast of user-controlled `order.fees` from `uint256` to `uint128` in `UniV4UniswapV2Wrapper.swapETHForExactTokens` silently truncates the fee-swap amount, decoupling the escrowed fee record from actual tokens purchased - ([File: evm/src/utils/uniswapv2/UniV4UniswapV2Wrapper.sol])

### Summary
`IntentGatewayV2.placeOrder` lets any user set an arbitrary `order.fees` (a `uint256`) and pay it in native token, in which case the gateway calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` [1](#0-0) . That router call is serviced by `UniV4UniswapV2Wrapper.swapETHForExactTokens`, which narrows the `uint256 amountOut` parameter to `uint128` before encoding it into the Uniswap V4 swap params: `params[0] = abi.encode(poolKey, true, uint128(amountOut), uint128(msg.value), bytes(""));` and `params[2] = abi.encode(poolKey.currency1, recipient, amountOut);` [2](#0-1) . If `order.fees` (i.e. `amountOut`) exceeds `type(uint128).max`, the swap's `SWAP_EXACT_OUT_SINGLE` action silently truncates to the low 128 bits, while the `TAKE` action in `params[2]` still uses the full, un-truncated `amountOut`.

### Finding Description
The root cause mirrors the reported bug class: an unchecked/implicit narrowing cast (`uint256` → `uint128`) on a value that is fully attacker/user-controlled, with no `require`/`SafeCast` bounds check anywhere in the call path (`IntentGatewayV2.placeOrder` → `IUniswapV2Router02.swapETHForExactTokens` → `UniV4UniswapV2Wrapper.swapETHForExactTokens`) [1](#0-0) [2](#0-1) .

After the swap returns, `IntentGatewayV2.placeOrder` records the escrow entry `_orders[commitment][TRANSACTION_FEES] = order.fees;` using the full, un-truncated `order.fees` value — not the amount that was actually delivered by the truncated swap [3](#0-2) . Since `params[0]`'s `uint128(amountOut)` and `params[2]`'s full `amountOut` diverge whenever `order.fees > type(uint128).max`, the two Universal Router actions (`SWAP_EXACT_OUT_SINGLE` targeting the truncated amount, and `TAKE` demanding the full amount) become inconsistent, and the accounting invariant "escrowed fee amount == actual fee token balance moved into the gateway" is broken.

### Impact Explanation
This breaks the accounting invariant that underlies fee release to solvers/relayers. `withdraw()` later releases the exact `_orders[commitment][TRANSACTION_FEES]` amount of fee token to the filler/relayer on `RedeemEscrow`/`RefundEscrow` [4](#0-3) . If the escrowed record is larger than what the truncated swap actually produced and deposited into the contract, the contract can attempt to pay out more fee tokens than it actually holds for that order, drawing down other users' escrowed balances (a shared pool of stored fee-token balances) — a fund-freezing/fund-corruption condition that could permanently break withdrawal for other unrelated orders once the pool is depleted. Because `order.fees` values large enough to exceed `2^128` (≈3.4×10^38) are astronomically outside realistic fee ranges, the *practical* exploitability is limited (an attacker would need to be motivated purely to corrupt internal accounting/griefing rather than direct realistic profit), which tempers the severity relative to a directly profitable exploit.

### Likelihood Explanation
Low-to-medium likelihood: exploiting the truncation requires the placer to deliberately set `order.fees` above `2^128 - 1` while paying with native ETH (`msgValue > 0` branch) [5](#0-4) . There is no upper-bound check on `order.fees` anywhere in `placeOrder`, so nothing prevents this input from an unprivileged caller. The main friction is that it requires intentional misuse (an attacker willing to grief/corrupt the fee-escrow bookkeeping), rather than being triggerable by ordinary usage.

### Recommendation
Add an explicit bounds check before down-casting: `require(order.fees <= type(uint128).max, "fee amount too large")`, or replace the raw cast with OpenZeppelin's `SafeCast.toUint128()` in `UniV4UniswapV2Wrapper.swapETHForExactTokens`/`swapExactTokensForETH`/`getAmountsIn`/`getAmountsOut`, so it reverts instead of silently truncating. Additionally, `_orders[commitment][TRANSACTION_FEES]` should be set from the *actual* amount received/spent by the swap (e.g., the wrapper's returned `amounts` array), not from the raw `order.fees` input, to keep escrow accounting consistent with real balances regardless of any future truncation-adjacent bugs.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder(order, graffiti)` with `order.fees = type(uint128).max + 1` and sends `msg.value` sufficient to cover the (mis-costed) swap, with `order.inputs`/`order.output` set minimally to pass validation.
2. `placeOrder` takes the `msgValue > 0` branch and calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` [6](#0-5) .
3. Inside `UniV4UniswapV2Wrapper.swapETHForExactTokens`, `uint128(amountOut)` truncates `order.fees` to a small value for the `SWAP_EXACT_OUT_SINGLE` params while `params[2]` still encodes the full `amountOut` for `TAKE` [7](#0-6) , causing the Universal Router call to behave inconsistently with the true intended amount (either reverting on `TAKE`'s excess demand or, depending on downstream router semantics, producing a mismatched output amount).
4. `placeOrder` nevertheless persists `_orders[commitment][TRANSACTION_FEES] = order.fees` (the full, untruncated value) as the amount owed to whichever party redeems the escrow, independent of what the swap actually delivered [8](#0-7) .

Note: I was not able to fully trace whether the Universal Router's internal `SETTLE`/`TAKE` handling reverts cleanly on this mismatch in all cases (that depends on external Uniswap V4 core/periphery contract behavior not indexed in this repo), so the exact failure mode (revert vs. successful-but-inconsistent completion) could not be verified with certainty from the available code.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory amounts)
    {
        PoolKey memory poolKey = _createPoolKey(path[1]);

        bytes[] memory params = new bytes[](3);
        params[0] = abi.encode(poolKey, true, uint128(amountOut), uint128(msg.value), bytes(""));
        params[1] = abi.encode(poolKey.currency0, uint256(0), false);
        params[2] = abi.encode(poolKey.currency1, recipient, amountOut);

        bytes[] memory inputs = new bytes[](1);
        inputs[0] = abi.encode(
            abi.encodePacked(uint8(Actions.SWAP_EXACT_OUT_SINGLE), uint8(Actions.SETTLE), uint8(Actions.TAKE)), params
        );

        // Snapshot standing balance (excluding inbound msg.value) so the refund is the swap-call delta only,
        // immune to any ETH that lands on the wrapper from outside the router (e.g., selfdestruct, coinbase).
        uint256 balanceBefore = address(this).balance - msg.value;

        IUniversalRouter(_params.universalRouter).execute{value: msg.value}(
            abi.encodePacked(bytes1(uint8(Commands.V4_SWAP))), inputs, deadline
        );

        uint256 refundETH = address(this).balance - balanceBefore;

        if (refundETH > 0) {
            (bool success,) = msg.sender.call{value: refundETH}("");
            require(success, "ETH refund failed");
        }

        amounts = new uint256[](2);
        amounts[0] = msg.value - refundETH;
        amounts[1] = amountOut;
    }
