`lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb` show that the webhook HMAC signs only the raw body, while the shop identity handed to the app's handler comes from an unauthenticated header. This breaks the same "field acted on but not covered by the HMAC" identity binding referenced in the report's admin-role analogy.

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never part of the HMAC-signed payload. `Registry.process` validates the HMAC and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, so the shop identity delivered to the app is not bound to the signature that "proves" the request is genuine.

### Finding Description
`Registry.process` does: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which validates against `request.to_signable_string`: [2](#0-1) 

That signable string is the raw body only — `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are completely outside the signature: [3](#0-2) 

The binding the gem implicitly claims is:
`hmac_valid(raw_body) == request_is_authentic_for(shop_header)`

but the actual binding enforced is only:
`hmac_valid(raw_body) == raw_body_is_authentic`

The `shop` value passed to the handler is never verified as belonging to the shop that actually generated the signed body: [4](#0-3) 

Because a valid `(raw_body, hmac)` pair can be obtained by any party that legitimately receives a real webhook for their own shop (e.g., a merchant who has installed the app), that party can then replay the identical body+HMAC to the app's webhook endpoint while swapping only the `shop-domain` header to a victim shop. The HMAC check still passes (it never looked at the header), and the app's handler is invoked believing the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the shop that a webhook is attributed to is attacker-controlled while the cryptographic proof only covers the body. Any host application logic keyed on `WebhookMetadata#shop` (session lookup/invalidation on `app/uninstalled`, per-shop data writes, billing state changes, etc.) can be triggered against a shop the attacker doesn't control, using a body the attacker does control (their own shop's webhook). This matches the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Medium: it requires the attacker to have received at least one legitimate webhook for a shop they control (trivial — install the app once) and to be able to POST to the app's public webhook endpoint with a forged `shop-domain`/`x-shopify-shop-domain` header, which any unprivileged internet user can do since webhook endpoints are unauthenticated by design and rely solely on the HMAC.

### Recommendation
Include the shop domain (and topic, api_version, webhook_id) in the HMAC-signed payload, or otherwise cryptographically bind the `shop` header to the request — e.g., verify it matches a shop looked up via a signed/trusted channel, not the raw header. At minimum, `Utils::HmacValidator.validate` should incorporate the headers relied upon by `WebhookMetadata`, not just the raw body.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app registers webhooks and Shopify sends a real webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker captures this exact `(B, hmac)` pair (own outbound listener, proxy, etc.).
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body = B` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — passes, since `B` and the HMAC are unchanged. [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and performs whatever shop-scoped action the app implements, now misattributed to the victim shop. [4](#0-3)
