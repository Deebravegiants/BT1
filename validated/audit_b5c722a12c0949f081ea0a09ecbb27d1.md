### Title
Signup signature omits `signup_id`, permitting replay of a valid attestation across different signup sessions - (File: src/plans/enroll_user.rs)

### Summary
`make_signature` in `src/plans/enroll_user.rs:290-304` computes a SHA-256 digest over `ORB_ID`, `user_qr_code.user_id`, and the iris/mask codes/versions only, then signs it via `secure_element::sign`. Because `signup_id` (and any timestamp/nonce) is never part of the signed payload, an attacker who can trigger two signup sessions with the same `user_id` and reproducible iris capture output (e.g. photo/contact-lens replay) obtains two identical signatures that are interchangeable across the two distinct `signup_id`s.

### Finding Description
`enroll_user::Plan::run` (src/plans/enroll_user.rs:72-88) computes `signature = make_signature(&user_qr_code, &pipeline)` and separately passes `signup_id` as an independent parameter to `signup_post::request(signature.as_ref(), &signup_id, ...)` (src/plans/enroll_user.rs:90-102). The signature itself is derived only from: [1](#0-0) 
`ORB_ID`, `user_qr_code.user_id`, and the pipeline's iris/mask codes and versions — `signup_id` is concatenated nowhere into the hashed context. Since the secure-element signs only this hash, the resulting signature is a function purely of `(ORB_ID, user_id, iris_pipeline_output)` and is otherwise independent of which `signup_id` it is eventually submitted with in `signup_post::request`.

### Impact Explanation
This breaks the intended invariant that the secure-element attestation authenticates a specific signup transaction. If an attacker can reproduce the same iris capture output (feasible if the pipeline output is deterministic for a fixed physical/photographic input, which is the premise of this question) across two signup attempts sharing the same claimed `user_id`, the orb will produce byte-identical signatures for both attempts. The signature carries no binding to `signup_id`, so it cannot itself prove that the biometric attestation was produced for the specific enrollment session it accompanies in the backend request; the anti-replay burden is placed entirely outside the signed payload, on backend-side session/dedup logic that this code path does not implement or enforce.

### Likelihood Explanation
Exploitability depends entirely on the ability to reproduce identical iris-pipeline output across attempts, which is the stated precondition and is a strong assumption not established as reachable within this file/function's own logic (the iris capture and pipeline stages contain their own liveness/fraud/uniqueness checks elsewhere in the codebase that are out of scope for this function). Within the scope of `make_signature` alone, the missing `signup_id` binding is a real design gap, but whether it is practically exploitable depends on unaudited upstream capture/pipeline determinism and backend-side signup deduplication, neither of which is verifiable from this function in isolation.

### Recommendation
Include `signup_id` (and ideally a freshness value such as a server-issued nonce or timestamp) in the `Context` hashed before calling `secure_element::sign`, so the attestation is cryptographically bound to the specific signup session it is submitted for.

### Proof of Concept
Unit test in `src/plans/enroll_user.rs`:
1. Construct a fixed `qr_scan::user::Data` (`user_id = "same-user"`) and a fixed `Pipeline` with deterministic `iris_code`/`mask_code`/version fields.
2. Call `make_signature(&user_qr_code, &pipeline)` twice — treat these as belonging to `signup_id_a` and `signup_id_b` (two different `SignupId` values used later by `Plan::run`).
3. Assert `signature_a == signature_b`.
4. This demonstrates the signature does not incorporate `signup_id`, i.e., the same secure-element attestation would be accepted (from the orb's perspective) for two different signup submissions, contingent on the backend not independently rejecting the reuse.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
