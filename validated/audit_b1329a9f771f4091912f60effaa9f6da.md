### Title
`IntentGatewayV2.setParams` on Tron has no zero-address/validation check, and it is one-shot and admin-only, so a bad `p.host` or `p.dispatcher` permanently bricks the gateway - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` initializes its critical `Params` (`host`, `dispatcher`, fee/oracle settings) through `setParams`, which is admin-gated exactly like `RubiconFeeController.setGladiusReactor` in the referenced report, but performs no validation on the supplied struct before storing it and burns the admin role in the same call.

### Finding Description
`setParams` is guarded only by `msg.sender == _admin`, then unconditionally overwrites `_params` and zeroes `_admin`, with no check that `p.host` or `p.dispatcher` are non-zero or contain code: [1](#0-0) 

Compare this with the mainline EVM `IntentsBase._validateParams`, which is the analogous config setter and explicitly rejects a zero/uncoded `host` or `dispatcher`: [2](#0-1) 

The Tron contract's `host()` reads directly from `_params.host`: [3](#0-2) 

Because `_admin` is reset to `address(0)` unconditionally inside `setParams` (line 309) regardless of whether the supplied params are sane, this call is strictly one-shot: there is no recovery path if `host` or `dispatcher` is set to `address(0)` (or any wrong/non-contract address) by mistake. Every subsequent ISMP dispatch (`placeOrder`, order fills, escrow releases, refunds, dust sweeps) that depends on `IDispatcher(_params.host)`/`_params.dispatcher` would then fail permanently, and no governance action can reach the contract again since `onAccept`/dispatch routes all run through `host()`.

### Impact Explanation
This is a High-severity availability/fund-freezing bug for the Tron token/intents bridge: escrowed user funds placed via `placeOrder` before or shortly after a misconfigured `setParams` call would become permanently stuck, since the module can no longer dispatch or receive any ISMP message (redemption, refund, cross-chain governance) once `host`/`dispatcher` is zero/wrong and `_admin` is burned. This matches the class of "trusted actor sets a critical address with no zero check" from the referenced report, but the impact here is more severe because the setter is also one-shot (no re-arming path exists, unlike `RubiconFeeController.setGladiusReactor`, which can simply be called again).

### Likelihood Explanation
Likelihood is low-to-moderate since it requires an admin operational mistake (deployment misconfiguration), but the consequence is unrecoverable and the code path is a first-class initialization step every Tron deployment must execute exactly once.

### Recommendation
In `setParams`, validate `p.host` and `p.dispatcher` are non-zero and contain code (mirroring `IntentsBase._validateParams` on the EVM side) before committing the struct and clearing `_admin`:
```solidity
function setParams(Params memory p) public {
    if (msg.sender != _admin) revert Unauthorized();
    if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
    if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
    _admin = address(0);
    _params = p;
}
```

### Proof of Concept
1. Deploy `IntentGatewayV2(admin)` on Tron; `_admin` is set, `_params` is unset (`host == address(0)`).
2. Admin calls `setParams(p)` with `p.host` accidentally left as `address(0)` (or any EOA/non-ISMP-host address) — no revert occurs. [4](#0-3) 
3. `_admin` is now `address(0)`, so `setParams` can never be called again.
4. Users call `placeOrder`, escrowing tokens into the gateway; any later call requiring `host()`/`_params.dispatcher` (fills, refunds, governance `onAccept`) fails because `host()` returns the bad address, permanently locking escrowed user funds with no admin recovery path.
