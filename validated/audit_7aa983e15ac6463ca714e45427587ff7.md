### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated headers and are not covered by the HMAC signature - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook delivery solely by HMAC-verifying the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from HTTP headers that are never included in the signed content. An attacker who can replay a genuinely-signed webhook body (e.g. one their own shop received after installing the app) can rewrite these headers — most importantly `shop-domain` — while keeping the body and its valid HMAC intact, causing the app's handler to process the payload under an arbitrary, attacker-chosen shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read straight from request headers, which are entirely outside the HMAC computation: [2](#0-1) 

`HmacValidator.validate` verifies the received HMAC against `verifiable_query.to_signable_string` (i.e., only the body), never touching the headers: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The intended identity binding is: `shop asserted to the handler == shop that Shopify actually signed the payload for`. Because `shop` is carried in a header untouched by the signature, this binding does not hold. An attacker who legitimately installs the app on their own store (an ordinary, unprivileged action) will receive real webhook deliveries with a valid HMAC computed over the JSON body using the app's real secret. They can capture such a request, change only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to reference a different, victim shop, and resend it to the app's webhook endpoint. `HmacValidator.validate` still passes because the body and HMAC are unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
Most webhook handlers use `data.shop` to decide which tenant's records to create, update, or delete (order/product/customer sync, GDPR data-request/erasure handlers, billing state, etc.). Forging this field lets an attacker who controls one legitimate installation inject attacker-controlled webhook payloads that are processed as if they belong to a different merchant's shop, i.e., cross-tenant data corruption/injection with a cryptographically "valid" signature. This satisfies the cross-tenant access impact category.

### Likelihood Explanation
Exploitation requires only that the attacker install the app on a shop they control (or capture/replay any webhook delivery addressed to any store) and modify plain HTTP headers before forwarding the request to the app's public webhook endpoint — no secret, token, or privileged access is needed. The only prerequisite is intercepting/relaying an HTTP request they can already legitimately receive, which is well within "unprivileged internet user" capability.

### Recommendation
Include the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the verified body, rather than trusting header values that sit outside `to_signable_string`. At minimum, `Registry.process` should not treat `request.shop` as authenticated after only validating the body's HMAC — the gem should compute/verify the signature over a canonical representation that includes these fields (mirroring Shopify's server-side signing behavior once confirmed), or document that host applications must independently re-validate `shop` against their own known installation records before trusting it.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving a POST with body `B`, and headers including `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the real `api_secret_key`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends this exact request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B` [5](#0-4) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, where `shop` is now `"victim-shop.myshopify.com"` even though the payload was never signed for that shop [6](#0-5) .
