### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the request body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw body bytes, while the tenant identity (`shop`) is read separately from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is never included in the signed material.

### Finding Description
`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [1](#0-0) . For webhook requests, `to_signable_string` is defined as `@raw_body` only [2](#0-1) , whereas the identity field `shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signed payload [3](#0-2) .

`Registry.process` uses this unauthenticated `request.shop` value directly to construct `WebhookMetadata` that is handed to the app's handler as the tenant identifier for the event: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . The only integrity check performed is `raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)` — no field ties the verified body to the claimed `shop`.

This exactly matches the report's bug class: a field that is acted upon (`shop`, used as the tenant key for routing/authorizing webhook handling) is not covered by the cryptographic proof (`hmac`, which only covers the raw body bytes). The equality that should hold — `shop-header-authenticated == shop-bound-in-signed-bytes` — does not, because the HMAC computation never consumes the `shop` header at all.

### Impact Explanation
A holder of one valid `(body, hmac)` pair for their own shop (i.e., any merchant with an app installed, an "unprivileged" actor relative to other tenants) can resend that exact HTTP request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. Because that header is not part of the signed bytes, `HmacValidator.validate` still succeeds, and the app-level handler receives `WebhookMetadata` claiming the payload originated from the victim shop. Any handler logic that trusts `data.shop` to select which tenant's records to create/update/delete (a common pattern, since this is literally the field this gem exposes for that purpose) can be tricked into cross-tenant data manipulation using only a webhook payload the attacker legitimately received for their own store. This is a cross-tenant integrity/confidentiality violation reachable without any credentials beyond a standard, legitimately-installed merchant account, which meets the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that (a) trusts `WebhookMetadata#shop` for tenant scoping (the intended and only reasonable use of this field, since this gem provides no alternative shop-verification mechanism) and (b) does not independently cross-check the shop against session/installation records before acting on webhook data. No secret key or privileged access is required — only a legitimate webhook delivery for the attacker's own store, which every installed merchant naturally receives, and the ability to replay an HTTP request with a modified header, which is trivial (curl/replay tooling).

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) header values in the HMAC-signed material verified by `HmacValidator`, or otherwise cryptographically bind the header-derived identity to the verified body before it is exposed via `WebhookMetadata`. Short term, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC check and must not be trusted for tenant selection without corroborating it against the app's own session/shop records (e.g., an existing installation record for that shop). Long term, consider changing `to_signable_string` to a canonical representation that includes the shop-domain header, or add a dedicated `verified_shop` accessor that fails closed unless header-shop consistency can be proven.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has the app installed,
# so Shopify legitimately sends them a signed webhook:
raw_body = '{"id": 1, "note": "legit order update for attacker-shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  # Attacker swaps this header only; body+hmac are untouched and still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  "x-shopify-webhook-id" => "attacker-controlled",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (it only checks raw_body),
#    and the app's handler receives WebhookMetadata with shop: "victim-shop.myshopify.com",
#    even though this payload was never sent by/about victim-shop.

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
