### Title
Escrow accounting trusts the pre-transfer input amount instead of the actually-received token balance, causing insolvent/under-collateralized escrow for fee-on-transfer/rebasing tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` in the Tron deployment records the escrowed amount for an order using the user-declared, fee-reduced input amount (`reducedInputs[i].amount`, derived from `order.inputs[i].amount`) rather than the amount of tokens the contract actually received via `safeTransferFrom`. This is the same root-cause pattern as the reported Convex `Booster.deposit` bug: the accounting quantity used downstream (minted/escrowed amount) is decoupled from the quantity actually custodied by the contract.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` was computed earlier purely from the caller-supplied `order.inputs[i].amount` minus the protocol fee: [2](#0-1) 
There is no post-transfer balance check (no `balanceOf` delta measurement), so for any fee-on-transfer, rebasing, or otherwise non-1:1-transfer ERC20 token, the amount actually held by the gateway will be less than the amount recorded in `_orders[commitment][token]`.

This mirrors the reported Convex issue exactly: `bal != _amount` because the recorded/committed quantity is derived from an a-priori declared amount rather than the measured, actually-received balance.

By contrast, the current (non-Tron) `evm/src/apps/IntentGatewayV2.sol` implementation was hardened against precisely this class of bug: it measures `balBefore`/`balanceOf` deltas and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment and fee reduction: [3](#0-2) 
The Tron variant lacks this fix.

### Impact Explanation
`_orders[commitment][token]` is the ledger the protocol relies on for `withdraw` during `cancelOrder`/`RefundEscrow` and (per `IntentsBase`/`IntrinsicIntents`) for solver settlement (`RedeemEscrow`), i.e., it represents a promise that the contract holds that many tokens for that order: [4](#0-3) 
If the ledgered amount exceeds the actual token balance, later withdrawals/refunds for that or other orders can revert due to insufficient balance (denial of service / freezing of other users' funds sharing the same token), or — depending on withdraw's internal accounting across orders — allow one order's under-collateralization to consume tokens escrowed for another order, causing loss of funds for legitimate depositors. This satisfies "permanent freezing of funds" / insolvent-escrow criteria.

### Likelihood Explanation
Reachable by any single unprivileged `placeOrder` transaction that specifies a fee-on-transfer, deflationary, or rebasing ERC20 as an input token — no privileged role or governance action required. The likelihood depends on whether such tokens are permitted as inputs by protocol configuration; if any non-standard ERC20 is accepted as an intent input, this is directly and trivially triggerable.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after `safeTransferFrom`, use the actual delta as `order.inputs[i].amount`, and compute `reducedInputs`/`commitment`/`_orders[commitment][token]` from that measured amount rather than the caller-declared amount.

### Proof of Concept
1. Protocol configuration permits a fee-on-transfer ERC20 token (e.g., a token that takes 5% fee on `transferFrom`) as an intent input token.
2. User calls `placeOrder` with `order.inputs[0].amount = 100` for that token.
3. `reducedInputs[0].amount` is computed as `100 - protocolFee` (e.g., 99 with a 1% protocol fee).
4. `safeTransferFrom(msg.sender, address(this), 100)` executes, but due to the 5% transfer fee the contract only receives 95 tokens.
5. `_orders[commitment][token] += 99` is recorded, but the contract's actual token balance increase is only 95 — a 4-token shortfall is now ledgered as escrowed but not actually held.
6. When this or a co-mingled order is later settled/refunded via `withdraw`, the shortfall causes either a revert (freezing legitimate withdrawals sharing the token) or depletion of tokens escrowed for other orders. [1](#0-0)
