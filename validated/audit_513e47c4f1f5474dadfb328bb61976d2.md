### Title
Missing re-initialization guard in `LockupContract::new` allows any unprivileged account to reinitialize a deployed, funded lockup contract and steal all locked/vested NEAR - (File: `lockup/src/lib.rs`)

### Summary
The `#[init]` constructor of `LockupContract` never checks `env::state_exists()`, unlike every other production contract in this repository. Because NEAR's `near-sdk` (v3.1.0, as pinned in `lockup/Cargo.toml`) does not itself prevent re-invocation of `#[init]` methods once state exists, this omission means `new` remains a public, callable-any-time entrypoint on an already-deployed and funded lockup contract. Any unprivileged account can call `new` again to overwrite `owner_account_id`, `vesting_information`, `lockup_information`, `staking_information` and `foundation_account_id`, then drain the account's NEAR balance via the (now attacker-owned) `transfer` method.

### Finding Description
Compare the `new` constructors across the in-scope contracts:

- `staking-pool/src/lib.rs` guards initialization: [1](#0-0) 
- `whitelist/src/lib.rs` guards initialization: [2](#0-1) 
- `staking-pool-factory/src/lib.rs` guards initialization: [3](#0-2) 

`multisig` and `voting` also contain a `state_exists` guard, confirmed by grep matches in `multisig/src/lib.rs` and `voting/src/lib.rs`.

However, `lockup/src/lib.rs::new` has **no** such guard at all: [4](#0-3) 

The function only checks:
- `address(this) != codeOrigin`-style self-check is absent (irrelevant here, NEAR contracts don't have that concept),
- validity of the account IDs passed in,
- consistency between `vesting_schedule` and `foundation_account_id`.

It never asserts that the contract has not already been initialized. Since `new` is a plain public method compiled into the contract's ABI (not gated behind `assert_owner()`, which itself depends on `owner_account_id` already being set correctly — and an attacker fully controls that value on the re-init call), **any account** can send a `FunctionCall` transaction invoking `new` on an already-deployed `lockup1`-style account at any point after initial deployment, exactly as the external report's attacker called `initialize` on `JBTiered721Delegate` a second time.

An attacker can call `new` with:
- `owner_account_id` = attacker's own account,
- `transfers_information` = `TransfersEnabled` with a past timestamp,
- `vesting_schedule` = `None`,
- `foundation_account_id` = `None`,
- `lockup_duration` = 0, `lockup_timestamp` = None, `release_duration` = None,
- any valid `staking_pool_whitelist_account_id`.

This overwrite fully replaces `LockupContract`'s Borsh-serialized state (`owner_account_id`, `lockup_information`, `vesting_information`, `staking_information`, `foundation_account_id`), wiping out the legitimate owner's rights and any pending vesting/lockup schedule/termination status, and instantly unlocking all funds (since `lockup_duration`/`release_duration`/`vesting_schedule` are all empty and transfers are marked enabled).

`assert_owner()` in `lockup/src/internal.rs` simply compares `predecessor_account_id` to whatever `owner_account_id` currently is: [5](#0-4) 
Since the attacker just set `owner_account_id` to themselves via the unguarded `new` call, they now pass `assert_owner()` trivially.

The attacker then calls the owner-only `transfer` method to drain the contract's liquid balance to any account: [6](#0-5) 
Because `get_liquid_owners_balance` is computed against the now-empty vesting/lockup information, the attacker can withdraw essentially the entire account balance (down to `MIN_BALANCE_FOR_STORAGE`).

If the original contract had funds delegated to a staking pool, the attacker (as the new "owner") could also call staking-pool-facing owner methods (`unstake_all`, `withdraw_all_from_staking_pool`) to eventually pull those funds back to the lockup account and then `transfer` them out.

### Impact Explanation
This is a **Critical** finding under the "Unauthorized transfer, withdrawal, spending, or release of locked, vested, pooled NEAR through public-call... accounting failure reachable by an unprivileged user" and "Permanent freezing/irrevocable loss of user or protocol funds in lockup release... flows" categories. An unprivileged attacker can seize full ownership of a deployed, funded `LockupContract` and drain essentially its entire NEAR balance, permanently defeating the vesting/lockup guarantees the contract is designed to enforce for the legitimate owner and the NEAR Foundation.

### Likelihood Explanation
Likelihood is high and does not require any privileged role, key compromise, or trusted assumption — it only requires knowledge of the lockup contract's account ID (which is deterministic/public, being derived from `sha256(owner_account_id)` in `lockup-factory/src/lib.rs`) and the ability to send a signed transaction from any account, which every NEAR user has. The `new` method is a completely public entrypoint with no re-initialization guard, unlike every sibling contract in this repository (`staking-pool`, `staking-pool-factory`, `whitelist`, `multisig`, `voting`), strongly indicating this is an accidental omission rather than an intentional design choice.

### Recommendation
Add a `state_exists` guard to `LockupContract::new`, matching the pattern used elsewhere in the repository:
```rust
#[init]
pub fn new(...) -> Self {
    assert!(!env::state_exists(), "The contract has already been initialized");
    ...
}
```
This is the standard mitigation for NEAR's `#[init]` methods (near-sdk 3.x does not auto-guard against re-invocation of already-initialized contracts) and directly closes the re-initialization/ownership-hijack path.

### Proof of Concept
1. Deploy `LockupContract` (via `lockup-factory` or directly) with `owner_account_id = "owner1"`, a non-trivial `vesting_schedule`, and a non-zero `lockup_duration`, funded with N NEAR.
2. From an arbitrary attacker account `attacker.near` (no relation to `owner1` or the NEAR Foundation), call:
```bash
near call lockup1 new '{
  "owner_account_id": "attacker.near",
  "lockup_duration": "0",
  "transfers_information": {"TransfersEnabled": {"transfers_timestamp": "1"}},
  "vesting_schedule": null,
  "release_duration": null,
  "staking_pool_whitelist_account_id": "staking-pool-whitelist"
}' --accountId=attacker.near --gas=25000000000000
```
This succeeds because `LockupContract::new` has no `state_exists` check, overwriting all prior state.
3. Call, as `attacker.near`:
```bash
near call lockup1 transfer '{"amount": "<near_full_liquid_balance>", "receiver_id": "attacker.near"}' --accountId=attacker.near --gas=50000000000000
```
This succeeds because `assert_owner()` now matches `attacker.near`, and `get_liquid_owners_balance` reflects the attacker-controlled (empty) vesting/lockup state, allowing the attacker to withdraw the account's NEAR balance down to `MIN_BALANCE_FOR_STORAGE`.
