### Title
Admin `update_token`/`register_token` calls in `pallet-hyper-fungible-token` can desynchronize in-flight cross-chain transfers from the custody/precision config used to settle them - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
This is the same bug class as the AvailBridge finding: a message dispatched cross-chain only carries an `asset_id`, while the custody model, contract address, and decimal precision needed to correctly settle that message later are looked up from mutable admin-controlled storage at settlement time, not snapshotted at dispatch time. In `pallet-hyper-fungible-token`, `send()` escrows/burns funds based on the *current* `NativeAssets`/`Precisions`/`TokenContracts` state, but the resulting `on_accept`/`on_timeout` processing re-reads that same mutable state later, after `CreateOrigin` may have changed it via `register_token`/`update_token`.

### Finding Description
`send()` decides whether to lock (`native = true`, transfer into escrow) or burn (`native = false`) the sender's asset using `NativeAssets::<T>::get(params.asset_id)`, and resolves precision via `Precisions::<T>::get(asset_id, destination)`, at the moment of dispatch: [1](#0-0) 

The dispatched ISMP `DispatchPost` request/commitment itself only encodes the `Message` (from/to/amount/data) - it does not encode or pin the custody model (`native`), the token contract address, or the decimals used for conversion: [2](#0-1) 

`register_token`/`update_token` are gated only by `CreateOrigin` and can be called at any time to rewrite `TokenContracts`, `ContractToAsset`, `NativeAssets`, and `Precisions` for an `asset_id`, with no check for outstanding in-flight requests for that asset: [3](#0-2) 

Per the pallet's documented ISMP callbacks, `on_accept` maps the incoming counterpart contract back to a local asset via `ContractToAsset` and scales the amount via `Precisions`, then mints or releases escrow depending on custody model; `on_timeout` refunds "from escrow or by re-minting" - both of these necessarily consult the *current* value of `NativeAssets`/`Precisions`/`ContractToAsset`, since no snapshot of the config used at `send()` time is stored per-request: [4](#0-3) 

If governance flips `native` for an asset (e.g. `true → false`) or removes/re-points a chain's `token_contract`/decimals via `update_token` while a `send()` request dispatched under the old configuration is still in flight (undelivered, awaiting response, or awaiting timeout), the later settlement path (`on_accept`/`on_timeout`) will apply the *new* custody model or precision to an amount that was escrowed/burned under the *old* one. This can cause:
- Escrowed funds to remain permanently locked because `on_timeout` now treats the asset as non-native and attempts to re-mint instead of releasing the escrow (funds never returned to the sender), or
- Unbacked minting if the reverse happens (funds were burned under the old `native=false` model, but the timeout/refund path re-mints under a stale/incorrect precision or asset mapping), and
- Silent mis-scaling of settled amounts if `Precisions` for the `(asset, chain)` pair is changed/removed between dispatch and settlement (`update_token`'s `remove_chains` path deletes the `Precisions` entry entirely), which would make in-flight `on_accept` conversions fail or reduce/inflate amounts erroneously.

This exactly parallels the AvailBridge issue: the queued/in-flight message references only the `asset_id`, and admin's ability to freely rewrite the id→contract/custody/precision mapping can break correct processing of already-committed messages.

### Impact Explanation
Funds that were escrowed or burned under one configuration can be settled under a different configuration once admin retargets the asset via `update_token`, resulting in permanent freezing of escrowed user funds (if the custody model flips to non-native at settlement time) or incorrect mint/refund amounts due to stale/removed precision data. This is a concrete freezing-of-funds / mis-settlement risk on the token bridge mint/burn path, reachable by any user who submits a `send()` transaction shortly before a routine admin `register_token`/`update_token` reconfiguration.

### Likelihood Explanation
`register_token`/`update_token` are normal, expected maintenance operations (e.g. re-pointing a contract address, correcting decimals, or migrating a wrapped-token deployment) rather than adversarial admin actions, so this can be triggered unintentionally during ordinary asset lifecycle management. Any `send()` request with a non-trivial cross-chain timeout window is exposed to a race with such an update, since there is no in-flight-request check or timelock in `register_token`/`update_token`.

### Recommendation
Snapshot the settlement-relevant configuration (custody model `native`, ERC decimals, and/or contract address) into the outgoing request/commitment itself, or into a per-commitment storage entry recorded at `send()` time, and have `on_accept`/`on_timeout` use that snapshot rather than re-reading the live `NativeAssets`/`Precisions`/`TokenContracts` maps. Alternatively, require `update_token`/`register_token` to only apply to newly dispatched requests (e.g. via asset-id versioning) so pending requests always settle against the configuration that was active when they were created.

### Proof of Concept
1. Governance registers asset `X` with `native = true` (escrow custody) for chain `Evm(1)` via `register_token`. [5](#0-4) 
2. A user calls `send()` for asset `X`; the pallet transfers the user's balance into the pallet's escrow account and dispatches a Post request. [6](#0-5) 
3. Before the request is delivered/times out, governance calls `update_token` for asset `X`, flipping custody semantics is not directly exposed by `update_token` (only `register_token` sets `NativeAssets`), but governance can call `register_token` again for the same `local_id` to overwrite `NativeAssets::<T>::insert(registration.local_id, registration.native)` with `native = false`. [7](#0-6) 
4. The in-flight request from step 2 eventually times out; `on_timeout` reads the now-updated `NativeAssets` value (`false`) and refunds by re-minting instead of releasing the escrow, leaving the originally escrowed balance permanently stuck in the pallet account while the user simultaneously receives freshly minted tokens - an unbacked mint plus a frozen escrow balance.

		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}

		pub fn update_token(
			origin: OriginFor<T>,
			update: TokenUpdate<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}

			for chain in update.remove_chains {
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}
				TokenContracts::<T>::remove(chain, update.asset_id.clone());
				Precisions::<T>::remove(update.asset_id.clone(), chain);
			}

			Ok(())
		}

## ISMP module behaviour

- `on_accept` — receives `Send` messages from the paired EVM contract. Maps
  the source contract back to a local asset via `ContractToAsset`, scales the
  amount using `Precisions`, then mints (non-native) or releases from escrow
  (native) to the beneficiary. Emits `TokenReceived`.
- `on_timeout` — refunds the original sender's balance from escrow or by
  re-minting. Emits `TokenRefunded`.
- `on_response` — unused; this pallet uses post-only messaging.
