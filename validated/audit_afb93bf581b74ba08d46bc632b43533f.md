### Title
Asymmetric decimal-scaling math in `convert_to_balance`/`convert_to_erc20` mishandles one direction of the decimals relationship, causing wrong mint/refund and outbound amounts - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet converts amounts between the local Substrate asset's decimals and the paired EVM ERC20 contract's decimals using `saturating_sub` on the decimals difference. This only produces correct results when `erc_decimals >= local_decimals`; when the relationship is reversed, the scaling factor collapses to `10^0 = 1` and the function silently returns the raw unscaled value instead of applying the (missing) multiplication/division, mirroring the y2k PegOracle bug where the decimal-handling math only worked for one specific decimals configuration and silently produced wrong/incorrect data for any other.

### Finding Description
`convert_to_balance` is documented as "Divides by `10^(erc_decimals - local_decimals)`" but implements this with `erc_decimals.saturating_sub(local_decimals)`: [1](#0-0) 

When `erc_decimals < local_decimals` (e.g. a USDC-style 6-decimal ERC20 paired with an 18-decimal local asset), `erc_decimals.saturating_sub(local_decimals)` evaluates to `0`, so the divisor is `10^0 = 1`. The function returns the raw ERC20 `U256` amount **unscaled** and parses it directly as the local balance, instead of correctly multiplying by `10^(local_decimals - erc_decimals)` to preserve value. This under-credits the beneficiary by a factor of `10^(local_decimals - erc_decimals)`.

The companion function `convert_to_erc20` has the mirror-image bug: it is documented as "Multiplies by `10^(erc_decimals - local_decimals)`" but again uses `erc_decimals.saturating_sub(local_decimals)`: [2](#0-1) 

When `local_decimals > erc_decimals` (local asset has more precision than the paired ERC20), the scaling factor is again `10^0 = 1` — no division is applied where one is required — so the value dispatched to the remote EVM contract is **inflated** by `10^(local_decimals - erc_decimals)`.

Both helpers are invoked on the direct fund-movement paths of `on_accept` (mint/transfer to beneficiary for an inbound cross-chain transfer) and `on_timeout` (refund of escrowed/burned funds back to the original sender) in the ISMP module handler: [3](#0-2) [4](#0-3) 

These are triggered by an unprivileged, relayed ISMP `PostRequest` (a message dispatched by any user via the paired contract's `send()`), meaning the vulnerable arithmetic sits directly in the reachable minting/refund path from a single relayed message.

### Impact Explanation
Because `Precisions` decimals are per-`(asset, chain)` configuration entries set by governance (`register_token`/`update_token`), any token pair where the local asset's configured decimals exceed the remote ERC20's decimals (or vice versa for outbound `send()`/`convert_to_erc20`) will silently mint/refund/dispatch amounts off by many orders of magnitude rather than reverting. This is a concrete freezing/loss-of-funds and unbacked-mint class of bug:
- Inbound (`on_accept`): a user sending real ERC20 value can receive a beneficiary credit that is `10^n` times smaller than intended (funds effectively lost/frozen), or in principle credited with wildly wrong precision depending on which decimals pairing is misconfigured.
- Timeout refunds (`on_timeout`): the same wrong scaling means escrowed/burned funds are refunded at the wrong magnitude — a definite fund-loss for the original sender.
- Outbound (`send`/`convert_to_erc20`, used elsewhere in the pallet to build the message body dispatched to the peer EVM contract): the destination chain could receive a message claiming an amount inflated by `10^n`, which — depending on the peer contract's own minting logic — could result in an unbacked mint of tokens on the destination chain, breaking the 1:1 backing invariant between the locked/burned supply on one side and the minted supply on the other.

This exactly matches the required impact bar: concrete theft/freezing of funds or unbacked mint arising from unsound decimal handling reachable by a normal cross-chain token transfer.

### Likelihood Explanation
This does not require any privileged or malicious actor — it is triggered purely by the *legitimate configuration* of a token pair whose local and remote decimals differ in the unhandled direction (which is a very common real-world scenario, since ERC20 tokens commonly use 6, 8, or 18 decimals while native Substrate assets are frequently registered at 12 or 18 decimals). Any ordinary user performing a `send()` or having a normal inbound transfer processed via `on_accept`/`on_timeout` on such a misconfigured-relative-decimals pair will trigger the bug on every single transfer, with no attacker interaction needed beyond normal usage.

### Recommendation
Replace the one-directional `saturating_sub`-based scaling with an explicit branch that multiplies when `local_decimals > erc_decimals` and divides when `erc_decimals > local_decimals`, mirroring the correct pattern already used elsewhere in the codebase (e.g. `VWAPOracle._normalizeAmount`): [5](#0-4) 

Concretely, for `convert_to_balance`: if `erc_decimals > local_decimals`, divide by `10^(erc_decimals - local_decimals)`; if `erc_decimals < local_decimals`, multiply by `10^(local_decimals - erc_decimals)`; if equal, pass through unchanged. Apply the symmetric fix to `convert_to_erc20`. Add regression tests covering both directions of the decimals relationship (erc > local and erc < local), not just the currently-tested direction.

### Proof of Concept
1. Register a token pair via `register_token`/`update_token` where the local Substrate asset has 18 decimals and the paired remote ERC20 has 6 decimals (a realistic USDC-style token), populating `Precisions` accordingly.
2. Have a user call `send()` on the peer EVM contract for `1_000_000` (i.e., `1.0` token at 6 decimals), which dispatches a `PostRequest` to the pallet.
3. In `on_accept`, `erc_decimals = 6`, `decimals (local) = 18`. `convert_to_balance` computes divisor `10^(6u8.saturating_sub(18u8)) = 10^0 = 1`, so `amount = 1_000_000` is minted/transferred as-is — i.e., `0.000000000000001` of the intended `1.0` token in 18-decimal terms — a `10^12` undervaluation of the credited amount, silently succeeding rather than reverting.
4. Symmetrically, reversing the decimals configuration (local 6, erc 18) and exercising the `send()` path that builds the outbound message via `convert_to_erc20` shows the dispatched ERC20 amount inflated by `10^12` relative to the local balance actually burned/escrowed. [6](#0-5)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}

    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
