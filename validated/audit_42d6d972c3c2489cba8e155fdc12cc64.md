## Title
Native ETH refunded/left over by LI.FI router during a swap is never tracked or returned, permanently trapping shielded user funds - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
When a shielded swap uses native ETH as `inputToken`, `LifiExternalAction.callRouter` forwards the *entire* `inputAmount` pulled from the user's shielded balance to the LI.FI router as `msg.value`, but only measures the swap's success by the change in `outputToken` balance. Any native ETH that the router does not consume (and returns to the caller, as many aggregated DEX routers do for partial fills / exact-output swaps) is left sitting in the `LifiExternalAction` contract with no code path to detect, account for, or return it to the depositor.

### Finding Description
`ExternalActionSwap.swap()` computes `inputAmount` from the circuit-verified `deltaAmounts[0]` and calls `callRouter(inputToken, inputAmount, outputToken, ...)`: [1](#0-0) 

`LifiExternalAction.callRouter` then sends the full `inputAmount` as `msg.value` to the LI.FI router along with opaque, off-chain-constructed `externalActionMetadata`, and computes `swappedAmount` purely from the delta in `outputToken` balance: [2](#0-1) 

The `externalActionMetadata` bytes are never cross-checked on-chain against `inputAmount` — nothing in `MainEVMCircuit.circom` or `ExternalActionSwap`/`LifiExternalAction` enforces that the amount the router will actually consume equals the ETH sent as `msg.value`. If the router's encoded call consumes less than `inputAmount` and refunds the difference (a common pattern for aggregator/DEX routers, e.g. exact-output swaps or partial fills), that refunded native ETH lands back in the `LifiExternalAction` contract itself (since it is the direct caller of `router.call`).

Because `swappedAmount` in `callRouter` is only derived from `outputToken`'s balance delta, this leftover native ETH (when `outputToken != address(0)`) is invisible to the accounting: it is not part of `swappedAmount`, not sent to `msg.sender`, and not folded into any UTXO. It simply accumulates in `LifiExternalAction`. `ExternalActionBaseV2` and `ExternalActionSwap` expose no rescue/sweep/withdraw function for stray ETH, so the funds are unrecoverable.

This breaks the intended balance equality: the ETH debited from the user's shielded balance (verified via the ZK proof and moved into `LifiExternalAction` by `Hinkal._externalTransact`) should be fully converted into `outputToken` value returned to the depositor, but a portion of it can leak out of the equation entirely and become permanently stuck.

### Impact Explanation
This causes permanent freezing of user (depositor) funds: real shielded value that was debited from the user's Merkle-tree balance (backed by a valid nullifier spend and ZK proof) is partially lost to the `LifiExternalAction` contract with no recovery mechanism, `onlyOwner`/admin path, or later transaction able to claim it. This matches the "permanent freezing of user funds" High-severity impact criterion.

### Likelihood Explanation
Likelihood is moderate: it requires only an ordinary user (no special privileges) to trigger a shielded swap via `transact()` with `inputToken == address(0)` where the LI.FI-encoded route (constructed off-chain and simply hashed/passed through, never validated against `inputAmount` on-chain) results in the router consuming less native ETH than `inputAmount` and returning the difference to the caller — a realistic scenario whenever the underlying aggregated route performs an exact-output swap or a partial fill.

### Recommendation
- In `LifiExternalAction.callRouter`, additionally snapshot the native ETH balance before/after the router call (when `inputToken == address(0)`) and refund any leftover ETH to `msg.sender`/the depositor instead of leaving it in the contract.
- Alternatively/also, require that the router call consumes exactly `inputAmount` (e.g., verify balance before/after equals `inputAmount` was spent, reverting otherwise), and expose an owner-independent sweep that routes any residual native balance back to the entitled depositor via the standard UTXO/commitment flow rather than losing it.

### Proof of Concept
1. User deposits ETH into Hinkal and later initiates a shielded swap through `Hinkal.transact` with `externalActionData.externalActionId` pointing to `LifiExternalAction`, `erc20TokenAddresses = [address(0), USDC]`, and `deltaAmounts[0] = -1 ETH` (verified by proof).
2. `Hinkal._externalTransact` transfers 1 ETH to `LifiExternalAction`, then calls `runAction` → `swap` → `callRouter(address(0), 1 ETH, USDC, metadata)`. [3](#0-2) 
3. `metadata` encodes a LI.FI route that only needs 0.9 ETH to complete the USDC swap (e.g., an exact-output style route); the router consumes 0.9 ETH and returns 0.1 ETH to the caller (`LifiExternalAction`).
4. `callRouter` computes `swappedAmount` solely from the USDC balance delta; the 0.1 ETH refund is never observed, never sent to `msg.sender`, and never included in any UTXO. [4](#0-3) 
5. The 0.1 ETH remains permanently locked in `LifiExternalAction`, with no function available to withdraw it back to the user.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
