This confirms the finding: the gem's own documentation at `docs/usage/webhooks.md:125` states the library "will verify the request did indeed come from Shopify" via `Registry.process`, and explicitly documents `data.shop` as trusted, verified webhook metadata (`docs/usage/webhooks.md:14`). The library itself claims to authenticate the request, but the identity binding is broken internally, so this is a genuine defect in the gem, not a case of the host app ignoring documented API.

### Title
Webhook shop-domain/topic/webhook-id headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate` succeeds, then hands the caller-supplied `shop`, `topic`, `webhook_id`, and `api_version` headers straight to the app's handler as trusted metadata. But the HMAC only signs the raw body — none of those headers are part of the signed payload — so an attacker who owns a *single* valid (body, HMAC) pair signed with the app's shared `api_secret_key` can replay it with an arbitrary `X-Shopify-Shop-Domain` header and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers with no cross-check against the signed body: [2](#0-1) 

`HmacValidator.validate` only compares the HMAC against `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` accepts the request as soon as this body-only HMAC check passes, and then forwards `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` — none of which are bound to the signature — directly into `WebhookMetadata` given to the app's handler: [4](#0-3) 

The equality being broken is: `hmac_signed_bytes == bytes_the_app_trusts_as_the_shop_identity`. The gem verifies `hmac(body) == received_hmac`, but then treats `header["shop-domain"]` as if it were also covered by that check, exactly the same class of gap as `currentDelegate` never being checked against `delegatee` before being trusted downstream. The documentation reinforces that this header is supposed to be verified information: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any unprivileged merchant who has the app installed on their own store (a normal, unprivileged action for any public app) can trigger a legitimate webhook event on their own shop, capturing a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's single, shared `api_secret_key` (the same secret is used for all shops using the same app — nothing shop-specific is mixed into the HMAC). They can then replay that exact body+signature to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with a victim shop's domain. Because the signature never covered these headers, `HmacValidator.validate` still returns `true`, and the app's handler receives `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop. Any app that uses `data.shop` to look up shop-scoped state, write to a shop's records, or drive shop-scoped side effects (exactly what the documented usage pattern in `docs/usage/webhooks.md` shows — `shop_domain: data.shop`) is vulnerable to cross-tenant data injection/corruption attributed to another merchant's store.

### Likelihood Explanation
High likelihood for any app that follows the gem's documented pattern of trusting `data.shop`/`data.topic` for tenant identification (which is the pattern the gem itself documents). The only prerequisite is installing the target public app on an attacker-controlled store — no leaked credentials, no access token, and no privileged account are required, satisfying the unprivileged-internet-user bar.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` values in the signable string used by `HmacValidator`, or otherwise cryptographically bind them to the HMAC (e.g., construct the signable string from headers + body rather than body alone), so that `Utils::HmacValidator.validate` fails if any of these fields are altered post-signing.

### Proof of Concept
1. Install the target public app on attacker-owned store `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) to receive a legitimate request with body `B` and header `X-Shopify-Hmac-Sha256: H` (`H = HMAC-SHA256(api_secret_key, B)`).
2. Replay to the app's webhook endpoint:
   ```
   POST /callback/orders/create
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim.myshopify.com
   X-Shopify-Webhook-Id: <any>
   X-Shopify-Api-Version: 2024-01

   B
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — it matches because the signature never covered the shop header.
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: B, ...)`, i.e., attacker-controlled body content processed as if it originated from the victim's store.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
