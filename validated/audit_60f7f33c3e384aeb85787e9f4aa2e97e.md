GRANDPA justification verification performs unbounded, attacker-scaled ancestry-chain traversal on a free unsigned extrinsic — CPU-exhaustion DoS analogous to pyasn1's unbounded tag-ID loop - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`GrandpaJustification::verify_with_voter_set` and its helper `AncestryChain::ancestry` walk a parent-hash chain built entirely from attacker-supplied `votes_ancestries: Vec<H>` and `commit.precommits`, with no cap on either vector's length and no bound on the number of hops walked per precommit. Just like the pyasn1 BER decoder that accumulated an unbounded tag ID in a loop driven purely by attacker-chosen input length, this code performs an attacker-controlled amount of work (up to `O(precommits × ancestry_length)` `BTreeMap` lookups) before any signature or size validation limits the cost, and it is reachable via `pallet_ismp::Pallet::handle_unsigned`, an **unsigned, fee-free extrinsic** that any relayer can submit repeatedly.

### Finding Description
`AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs:180-197` walks backwards from a `block` hash to a `base` hash by repeatedly looking up `current_header.parent_hash()` in a `BTreeMap` built from the untrusted `votes_ancestries` field of the justification: [1](#0-0) 

This loop has no upper bound on hop count other than the size of the `ancestry` map itself, which is populated directly from `self.votes_ancestries` — an SCALE-decoded `Vec<H>` field with no length limit: [2](#0-1) 

`verify_with_voter_set` calls `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)` **once per precommit** in `self.commit.precommits`: [3](#0-2) 

Because both the precommit count and the ancestry-header count are attacker-controlled (bounded only by the overall extrinsic/block-length limit, not by any semantic cap tied to real authority-set size or actual chain depth), the total work is quadratic in the size of the submitted justification: `O(|precommits| × |votes_ancestries|)`. A relay-chain header chain can be constructed as a long, degenerate linked list (each header's `parent_hash` pointing to the next), forcing the maximum number of hops for every precommit that doesn't already reference the base.

This verification path is reachable from `pallet_ismp::Pallet::handle_unsigned`, which is an **unsigned, no-fee extrinsic** explicitly documented as executing "for free": [4](#0-3) 

Crucially, `validate_unsigned` for this call also fully executes `Self::execute(messages.clone())` (which drives consensus-message verification, including `verify_grandpa_finality_proof` → `GrandpaJustification::verify`) at the **transaction-pool validation stage**, before the transaction is even included in a block: [5](#0-4) [6](#0-5) 

This means every full node validating the mempool — not just the block author — must pay the full quadratic verification cost for every submitted `handle_unsigned` call carrying a crafted GRANDPA consensus message, with no fee charged to the submitter, and this can be resubmitted repeatedly with cosmetic variations to bypass the mempool's `provides`-tag de-duplication.

### Impact Explanation
This matches the reported bug class precisely: an unbounded loop whose cost scales with attacker-chosen input size, executed in an unmetered/free-of-charge code path reachable by any unprivileged party. Because `handle_unsigned` is validated (and its consensus-verification logic fully executed) at transaction-pool admission for every peer node, a flood of maximal-size crafted GRANDPA justifications can consume CPU on every relaying/validating node in the network for free, degrading or halting the timely processing of legitimate cross-chain messages — i.e., a "route unable to deliver messages" condition, which is one of the explicitly accepted impacts for this scan.

### Likelihood Explanation
Any unprivileged relayer can construct and submit a `ConsensusMessage::Relaychain`/`Polkadot`/`StandaloneChain` variant wrapped in `handle_unsigned` with a `GrandpaJustification` whose `commit.precommits` and `votes_ancestries` are sized up to the network's extrinsic/block-length limits, and whose ancestry headers form a maximally-degenerate parent-hash chain. No signature over the ancestry headers themselves is required for the quadratic-cost ancestry walk to be triggered — the expensive traversal happens as part of `finality_grandpa::validate_commit`/`verify_with_voter_set`, prior to the point where an invalid signature or non-existent header short-circuits with an error. The attack requires only crafting SCALE-encoded data and no possession of valid keys, consensus state, or elevated privileges, making it straightforward for a single malicious relayer to attempt at scale.

### Recommendation
- Bound `votes_ancestries.len()` and `commit.precommits.len()` to a sane multiple of the known/trusted authority-set size before running `verify_with_voter_set`.
- Bound the maximum number of hops `AncestryChain::ancestry` may traverse (e.g., to `votes_ancestries.len() + 1`) and reject with an error once exceeded, rather than allowing it to walk the full map.
- Consider charging weight/fees proportional to the size of `votes_ancestries` and `precommits` for consensus-update extrinsics even though `handle_unsigned` is fee-free, or introduce a pre-validation cheap size/sanity check in `validate_unsigned` before invoking the full verification pipeline, so pool-validation cost cannot be forced arbitrarily high by unauthenticated data.

### Proof of Concept
1. Construct a `GrandpaJustification<H>` where:
   - `commit.precommits` contains `N` precommits (up to the maximum permitted by extrinsic size), each targeting a distinct header hash.
   - `votes_ancestries` contains `M` headers forming one long linked chain (`header_i.parent_hash == header_{i-1}.hash()`), engineered so that from each precommit's target hash back to `base_hash` requires traversing nearly the entire `M`-length chain.
2. Wrap this justification in a `FinalityProof`/`ConsensusMessage::Relaychain` (or `StandaloneChain`) and submit it via `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(...)] }` as an unsigned extrinsic.
3. Every node performing `validate_unsigned` for this transaction executes `verify_grandpa_finality_proof` → `GrandpaJustification::verify_with_voter_set`, which calls `AncestryChain::ancestry` up to `N` times, each potentially walking up to `M` hops — `O(N×M)` `BTreeMap` lookups — for free, before the transaction is rejected (e.g., due to invalid signatures once actual authority verification fails).
4. Repeating this submission (with cosmetic nonce/content changes to avoid `provides`-tag dedup) at volume forces sustained CPU cost on every relaying/validating node, without any fee being charged to the attacker.

Note: I was unable to directly determine the exact maximum extrinsic/PoV size enforced by the runtime configuration (varies by deployment), so the precise practical bound on `N`/`M` achievable in one transaction is uncertain and would need on-chain configuration inspection to quantify precisely — but the vulnerability's root cause (absence of any explicit cap on precommit/ancestry counts in the verification logic itself) is confirmed directly from the source.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}

	mut consensus_state: ConsensusState,
	finality_proof: FinalityProof<H>,
) -> Result<(ConsensusState, H, Vec<H256>, AncestryChain<H>), Error>
where
	H: Header<Hash = H256, Number = u32>,
	H::Number: finality_grandpa::BlockNumberOps + Into<u32>,
{
	// First validate unknown headers.
	let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);

	let target = finality_proof
		.unknown_headers
		.iter()
		.max_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	// this is illegal
	if target.hash() != finality_proof.block {
		Err(Error::LatestBlockMismatch)?;
	}

	let justification =
		GrandpaJustification::<H>::decode_all(&mut &finality_proof.justification[..])
			.map_err(|e| Error::DecodeJustification(alloc::format!("{e:?}")))?;

	if justification.commit.target_hash != finality_proof.block {
		Err(Error::JustificationTargetMismatch)?;
	}

	let from = consensus_state.latest_hash;

	let base = finality_proof
		.unknown_headers
		.iter()
		.min_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	if base.number() < &consensus_state.latest_height {
		headers
			.ancestry(base.hash(), consensus_state.latest_hash)
			.map_err(|_| Error::InvalidAncestry)?;
	}

	let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

	// 2. verify justification.
	justification
		.verify(consensus_state.current_set_id, &consensus_state.current_authorities)
		.map_err(|e| Error::JustificationVerify(e.to_string()))?;
