### Title
OAuth callback `shop` value is HMAC-signed but never validated as a Shopify domain before the `client_secret` is sent to it - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`Oauth.validate_auth_callback` builds the access-token request host directly from `auth_query.shop` without ever checking that the value is a legitimate `*.myshopify.com` (or dev-shop) domain. The equality that should hold is `shop value trusted for HMAC-signing == shop value safe to use as the destination host for the client_secret`, but the code only enforces the first half.

### Finding Description
In `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-113`), the HMAC check only proves that `auth_query.shop` (along with `code`, `host`, `state`, `timestamp`) was signed with `Context.api_secret_key` — it says nothing about the shop being a real, in-scope `myshopify.com` store:
```ruby
raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
...
null_session = Auth::Session.new(shop: auth_query.shop)
body = {
  client_id: Context.api_key,
  client_secret: Context.api_secret_key,
  code: auth_query.code,
  expiring: Context.expiring_offline_access_tokens ? 1 : 0,
}
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
```
`HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:12-19`) then builds the destination host directly from `session.shop`:
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
```
There is no allowlist/regex anywhere in `lib/shopify_api/**` restricting `shop` to `*.myshopify.com` (confirmed by search — the only `myshopify`/domain-validation hits are in generated `test/rest/**` fixtures, not library code). Because `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`) simply includes whatever `shop` string is passed in as a signable field, an app that (per Shopify's own recommended flow) reflects the incoming `shop`/`host` request parameters into the callback URL and lets Shopify redirect back is trusting Shopify's HMAC to vouch for the *value*, not for the *domain space* it belongs to. If the host application's redirect/callback wiring allows an attacker-influenced `shop` to reach `AuthQuery` (e.g., through parameter pass-through prior to the signed redirect, or through a permissive host implementation matching the library's own documented Rails example in `docs/usage/oauth.md`), the library will happily POST `client_id`, `client_secret`, and the authorization `code` to that attacker-controlled host — nothing in this gem stops it.

### Impact Explanation
This meets the Critical bar: theft/exfiltration of the app's `client_secret` and the authorization `code` (which is exchangeable for a merchant access token) to an SSRF target chosen by the request, because the library performs no domain-space validation before dispatching the credential-bearing POST request. This is exactly the pattern the external report highlights generically ("host validated versus the host that receives the... `client_secret`") — here the check that exists (HMAC) is orthogonal to the check that's missing (domain safety).

### Likelihood Explanation
Likelihood depends entirely on whether a caller's routing/controller (outside this gem) can be induced to construct an `AuthQuery` whose `shop` value is non-Shopify while still being signable — which requires either Shopify itself producing the signature (not attacker-controlled) or the host app skipping the HMAC path. Given the library performs no defense-in-depth here and documents direct construction of `AuthQuery` from raw request parameters (`docs/usage/oauth.md:242-260`), the residual risk surface is real but contingent on host-app behavior at the margin, which the rules ask us to still flag if the missing check is inside this gem's own logic (it is: `validate_auth_callback`/`HttpClient` never independently constrain `shop`).

### Recommendation
Add explicit shop-domain validation (e.g., a `myshopify.com`/dev-shop allowlist regex, matching what `@shopify/shopify-api` JS and other official SDKs implement as `sanitizeShop`) in `Auth::Session` or `Oauth.validate_auth_callback`/`Oauth.begin_auth` before using `shop` to construct any outbound URL, independent of and in addition to the HMAC check.

### Proof of Concept
1. Construct (or have a permissive host app forward) an `AuthQuery` with `shop: "attacker.example.com"`, plus a valid `hmac` computed over the exact same field set with the app's `api_secret_key` (this is possible if the host app itself computes/forwards the HMAC, or if any component upstream of this gem trusts and re-signs attacker-supplied fields).
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies: valid_cookies, auth_query: auth_query)`.
3. Observe `HttpClient` in `lib/shopify_api/clients/http_client.rb:18` build `@base_uri = "https://attacker.example.com"` and POST the body containing `client_secret` and `code` to that host — the library performs no domain check to prevent this. [1](#0-0) [2](#0-1) [3](#0-2)

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]

          raise Errors::InvalidOauthError,
