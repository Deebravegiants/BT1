## Analog Found

### Title
SimplexPaymaster uses a single `maxOracleAge` staleness threshold for both the native/USD and token/USD Chainlink feeds - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` prices every ERC-4337 UserOperation by combining two independent Chainlink feeds — `nativeOracle` (e.g. BNB/USD, ETH/USD) and a per-token `tokenOracle` (token/USD) — but validates both feeds' freshness against the exact same `maxOracleAge` value, just as `ChainLinkOraclePivot._getLatestRoundData` checked `priceFeedA` and `priceFeedB` against the same `outdated` value.

### Finding Description
`_getOraclePrice` is the single staleness gate used for both feeds: [1](#0-0) 

It is invoked twice per pricing call, once for `nativeOracle` and once for `cfg.tokenOracle`, with the same `maxOracleAge` bound each time: [2](#0-1) 

The contract's own documentation acknowledges these feeds have very different real-world heartbeat cadences: [3](#0-2) 

Despite this, only a single `maxOracleAge` field exists in `Params`/`TokenConfig`, applied uniformly: [4](#0-3) 

Governance can only tighten or loosen one shared bound via `_setParams`, never set independent thresholds per feed: [5](#0-4) 

This is the same root cause as the external report: a shared staleness parameter cannot correctly bound two feeds whose actual update frequencies diverge (e.g. a fast-updating native/USD feed at ~27s vs. a slow-updating stablecoin feed with a 24h heartbeat, or vice versa per chain). If `maxOracleAge` is set loose enough to accommodate the slower feed's legitimate heartbeat, the faster feed's staleness check becomes ineffective and a genuinely stale/broken fast feed can silently be treated as fresh.

### Impact Explanation
`_tokenPrice`/`_getOraclePrice` is on the direct, permissionless path of `_fetchDetails`, which executes during **every** UserOperation validation for any bandwidth purchaser using this paymaster: [6](#0-5) 

and also gates the swap execution price in `swapAndDeposit`: [7](#0-6) 

An unbounded/stale price on either leg directly determines `tokenPrice`, hence `prefundAmount` pulled from the user (mode 0x00 `transferFrom` or mode 0x02 Permit2), and the `amountOutMin` used to guard the treasury's stablecoin-to-native swap. A stale-but-accepted feed can cause users to be over/undercharged in ERC-20 stablecoins relative to actual gas cost, or let `swapAndDeposit` execute against a stale price, both of which are direct fund-accounting/loss issues for either the paymaster treasury or its users.

### Likelihood Explanation
No privileged action is required — any address that submits a UserOperation through the EntryPoint against this paymaster reaches `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` on the hot path. The condition is deterministic: whenever one configured feed's real heartbeat differs meaningfully from `maxOracleAge` relative to the other feed (a normal, expected chain-dependent configuration per the contract's own comments), the single shared bound cannot correctly protect both legs simultaneously.

### Recommendation
Track and enforce staleness independently per feed, e.g. add a `nativeOracleMaxAge` alongside the existing per-token `tokenOracle` staleness bound (or a `maxAge` field inside `TokenConfig`), and pass the appropriate bound into `_getOraclePrice` for each feed instead of reusing the single global `maxOracleAge` for both `nativeOracle` and every `cfg.tokenOracle`.

### Proof of Concept
1. Governance registers a token whose Chainlink feed has a 24h heartbeat and configures `maxOracleAge` = 24h + buffer so that token feed passes the staleness check under normal operation.
2. The `nativeOracle` (e.g., BNB/USD) has an actual heartbeat of ~27s, but because `_getOraclePrice(nativeOracle, ...)` reuses the same 24h `maxOracleAge`, the native feed can go stale (e.g., due to an aggregator outage) for hours without the paymaster detecting it.
3. Any user submits a UserOperation; `_fetchDetails` → `_tokenPrice` accepts the stale native price and computes an incorrect `tokenPrice`.
4. The user is charged (or the treasury receives) an ERC-20 amount computed from a stale native/USD price, and/or `swapAndDeposit` executes with `amountOutMin` derived from the stale rate, causing a mispriced swap. In both cases, the single shared `maxOracleAge` fails to catch the staleness of the feed with the tighter real heartbeat.

        if (mode != 0x00 && mode != 0x02) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
