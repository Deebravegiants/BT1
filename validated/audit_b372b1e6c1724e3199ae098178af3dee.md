### Title
Webhook shop tenant identity is not bound to the HMAC signature, enabling cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC over only the raw request body [1](#0-0) , but the `shop` value that is passed downstream to the app's handler as the tenant identity is read from an unauthenticated header and is never included in the signed payload [2](#0-1) . This breaks the equality `bytes_verified_by_hmac == bytes_used_to_identify_the_tenant`, matching the reported bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` field [3](#0-2) . For webhook requests, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header without being covered by the signature at all [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before dispatching to the app's handler with `request.shop` as the tenant identifier: [4](#0-3) . There is no check anywhere in this call path that ties the `shop` header to the signed bytes or to any known/expected shop.

Because Shopify webhook HMACs are computed with the app's single `client_secret` and only over the JSON body — never the shop domain — any two webhook deliveries with identical body content (which is common, e.g., empty-body compliance webhooks, or webhooks whose payload an attacker can influence by taking equivalent actions in their own store) will produce an *identical* valid HMAC regardless of which shop sent it. An attacker who has installed the app on their own shop can capture one of these valid `(body, hmac)` pairs from their own legitimate webhook deliveries, then replay the same body and HMAC while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop [5](#0-4) .

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem authenticates the *bytes of the body* but not the *tenant attribution* of those bytes. Any host application that trusts `WebhookMetadata#shop` (as the library's own documentation and API imply it should, since it's the only tenant-identifying field the gem hands to `WebhookHandler#handle`) can be made to process attacker-controlled webhook data under a victim shop's identity — e.g., triggering shop-scoped side effects, writing/altering per-shop state, or acting on behalf of a shop the attacker does not control. This falls under the "cross-tenant access" Critical impact category, since the exploit crosses a tenant boundary using only body/HMAC pairs an unprivileged (but app-installing) attacker can legitimately obtain for their own shop.

### Likelihood Explanation
Exploitability requires the attacker to install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer using a public or custom app) and to find or engineer a webhook body that is byte-identical between their own deliveries and ones plausible for a victim (trivially true for topics with empty/near-empty bodies, e.g., app/uninstalled-style events, or by crafting resource fields to match). No access to the app's `client_secret`, access tokens, or the victim's credentials is required — only observation of the attacker's own valid webhook traffic and the ability to POST a forged request with a different `shop-domain` header to the app's public webhook endpoint. This is a realistic, unprivileged-internet-user attack path.

### Recommendation
Bind the shop identity into the value verified by the HMAC path, e.g., either (a) require host applications to look up and validate the shop against a known/installed-shop list before trusting `request.shop`, or (b) have the gem itself reject/flag webhook requests whose `shop` cannot be independently corroborated (for example, cross-checking against `Context`-registered shops or requiring the caller to pass an expected shop to `Registry.process`). At minimum, the gem's documentation and `WebhookMetadata` should make explicit that `shop` is unauthenticated header data, not something covered by the HMAC guarantee, so host apps do not treat it as trusted tenant identity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or waits for) a webhook delivery with body `B` (e.g., `{}` for a topic with an empty payload) and captures the valid `x-shopify-hmac-sha256` header value `H` computed by Shopify over `B` with the app's `client_secret`.
3. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - `x-shopify-topic`: the real topic
   - `x-shopify-hmac-sha256`: `H` (unchanged, still valid for body `B`)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - body: `B` (unchanged)
4. `ShopifyAPI::Webhooks::Request.new` parses these headers and body without error [6](#0-5) .
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B`/`H` [7](#0-6) .
6. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: {}, ...)` [5](#0-4) , causing the host app to act as if the victim shop sent this webhook.

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
