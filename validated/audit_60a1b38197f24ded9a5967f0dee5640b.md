### Title
Overflow in market accrual permanently freezes a large high-utilization market - ([File: contracts/pool/src/interest.rs])

### Summary
An unprivileged user can trigger a persistent `MathOverflow` in the pool’s mandatory interest-accrual path by creating a very large, highly utilized market and then calling `update_indexes` after sufficient elapsed time. [1](#0-0) [2](#0-1)  Accrual computes the old and new aggregate debt as `borrowed * borrow_index` with panicking `Ray::mul`, before the intended borrow-index cap can safely bound the resulting value. [3](#0-2)  Once this bound is crossed, every operation that first synchronizes the market—including repayment, withdrawal, liquidation, and further `update_indexes` calls—reverts on the same arithmetic overflow. [4](#0-3) [5](#0-4) 

### Finding Description
`LiquidityPool::update_indexes` calls `ops::market::accrue`, which loads each requested market and invokes `interest::global_sync`. [1](#0-0) [2](#0-1)  `global_sync` divides elapsed time into bounded accrual windows and calls `accrue_step` for every window. [6](#0-5)  Accrual evaluates utilization through `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`, and reward accounting separately computes `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`. [7](#0-6) [3](#0-2) 

`Ray::mul` is backed by `mul_div_half_up`, which only uses an `I256` intermediate and still requires the final RAY value to fit in `i128`; otherwise it panics with `GenericError::MathOverflow`. [8](#0-7) [9](#0-8)  `update_borrow_index` caps the *index* at `MAX_BORROW_INDEX_RAY`, but this does not cap the aggregate RAY-denominated debt value `borrowed * borrow_index`. [10](#0-9)  The existing protocol test demonstrates that a one-billion-token, 18-decimal market at approximately 98% utilization reaches this aggregate-value ceiling before the borrow-index cap, after which `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW`. [11](#0-10) 

The public path is `controller.update_indexes(...)` for the affected `(hub, asset)` market; an attacker can create the required state using ordinary `supply` and `borrow` calls, allow interest to accumulate, and invoke index synchronization. [1](#0-0) [12](#0-11)  No privileged pool call is required because user-facing controller actions delegate to the owner-gated pool methods. [13](#0-12) [14](#0-13) 

### Impact Explanation
The affected market becomes unable to accrue interest, which blocks all user-facing actions that begin by loading a synced market. [4](#0-3)  Suppliers cannot withdraw, borrowers cannot repay or reduce liquidatable positions, liquidations that require accrual cannot proceed, and explicit index updates also fail. [15](#0-14)  This is at least temporary freezing of user funds and market operation; absent a separate remediation path, the math condition makes the freeze persistent. [16](#0-15) 

### Likelihood Explanation
The exploit requires a whale-sized market and sustained high utilization, so ordinary market balances are unlikely to reach the `i128` aggregate-value bound immediately. [12](#0-11)  However, the repository’s directed test shows the condition is deterministic for supported parameters: approximately one billion 18-decimal tokens supplied and about 98% borrowed eventually cross the bound under the configured rate curve. [17](#0-16)  Once crossed, a single unprivileged `update_indexes` call is sufficient to trigger the denial of service. [1](#0-0) 

### Recommendation
Do not compute unbounded aggregate debt solely as `borrowed * borrow_index` in the accrual path. [3](#0-2)  Before `accrue_step`, detect whether `borrowed * new_borrow_index` would exceed the RAY value domain and clamp the growth to the largest index whose aggregate value remains representable, or perform utilization and interest calculations with saturating/wide arithmetic that cannot revert after state is committed. [18](#0-17) [10](#0-9)  The index cap should be applied consistently to the aggregate-value ceiling, not only to the scalar index. [19](#0-18) 

### Proof of Concept
The repository’s directed test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` establishes the issue:

1. Create a normal collateral market and a large 18-decimal borrow market.
2. Deposit `1_000_000_000 * 10^18` base units into the large market.
3. Borrow approximately 98% of that liquidity against sufficient collateral.
4. Advance ledger time in one-year intervals while calling `update_indexes`.
5. `update_indexes` eventually returns `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
6. Subsequent `withdraw` and `repay` calls also fail with `MATH_OVERFLOW` because they must sync the same market first. [11](#0-10)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Computes `floor(x * y / d)`, saturating to `i128::MAX` (or `i128::MIN` for a negative
/// quotient) instead of panicking if the result does not fit in `i128`. Panics with
/// `GenericError::DivisionByZero` if `d == 0`.
pub fn mul_div_floor_saturating(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    require_nonzero_divisor(env, d);
    if let Some(quotient) = x
        .checked_mul(y)
        .and_then(|product| div_floor_i128(product, d))
    {
        return quotient;
    }
    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    div_floor_i256(
        env,
        &x256.mul(&y256),
        &d256,
        quotient_is_nonnegative(x, y, d),
    )
    .to_i128()
    .unwrap_or(if quotient_is_negative(x, y, d) {
        i128::MIN
    } else {
        i128::MAX
    })
