### Title
Same-transaction price manipulation of `calc_take_pnl` lets an unprivileged LP bias the persistent PnL baseline stored in `TargetOrders` - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` derives the pool's persistent "PnL baseline" (`target_orders.calc_pnl_x` / `calc_pnl_y`) and the amount skimmed into `amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin` from the *instantaneous* vault reserves at the moment `Deposit` or `Withdraw` executes. Because Solana lets any signer bundle arbitrary instructions into one atomic transaction, an unprivileged user can sandwich a `Deposit`/`Withdraw` call between a self-executed swap and its reversal, feeding `calc_take_pnl` an attacker-chosen spot price. This is the same root cause as the reported bug: an economically important, persistent parameter is derived from a value that is trivially manipulable within a single attacker-controlled transaction, with no time-weighting or admin gate protecting it.

### Finding Description
`calc_take_pnl` (called from `process_deposit` at [1](#0-0) ) and from `process_withdraw` ( [2](#0-1) ) computes `x1`/`y1` directly from the current `amm_coin_vault` / `amm_pc_vault` token balances via `Calculator::calc_total_without_take_pnl_no_orderbook`: [3](#0-2) 

Inside `calc_take_pnl`, the "current price" implied by these live balances is used to project a new baseline point `(x2, y2)` on the invariant curve and to split the accrued profit into `delta_x` / `delta_y`: [4](#0-3) 

The resulting `delta_x`/`delta_y` are added to `amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin` (locking that amount out of the swappable pool) and the *persistent* baseline `target_orders.calc_pnl_x` / `calc_pnl_y` is rewritten using the same spot-priced `x1`/`y1`: [5](#0-4) [6](#0-5) 

There is no check that the vault balances used for `x1`/`y1` reflect anything other than the exact state at the instant the instruction runs, and no restriction on what other instructions may precede/follow it in the same transaction. Any holder of LP tokens can therefore construct a single transaction that:
1. Executes a large `SwapBaseIn`/`SwapBaseOut` to push the pool to an extreme, attacker-chosen price ratio (still paying only the swap fee).
2. Calls `Deposit` or `Withdraw` in the same transaction, so `calc_take_pnl` computes `x1`/`y1` (and hence `delta_x`, `delta_y`, and the rewritten `calc_pnl_x`/`calc_pnl_y` baseline) at that attacker-chosen ratio instead of the pool's steady-state price.
3. Reverses the initial swap in the same transaction, restoring the vault balances and paying only the two swap fees.

This is functionally identical to the reported bug class: a value (`totalBorrows` there, spot vault reserves here) that only needs to be true for the duration of one attacker-composed transaction is used to permanently update state (`refreshCompSpeeds`'s reward speed there, `TargetOrders.calc_pnl_x/y` and `need_take_pnl_pc/coin` here) that other, unrelated users continue to be economically affected by afterwards.

### Impact Explanation
`need_take_pnl_pc`/`need_take_pnl_coin` are amounts that are permanently removed from the swappable/withdrawable pool until an admin-only `WithdrawPnl` call clears them, and `calc_pnl_x`/`calc_pnl_y` is the baseline every future `Deposit`/`Withdraw`/`WithdrawPnl` call compares against. Because the split between `delta_x` and `delta_y` (i.e., how much of the skim is denominated in coin vs. pc) is a function of the price ratio at call time, an attacker who freely chooses that ratio controls the composition (and, since decimals/normalization differ per token, the effective value) of what gets locked away from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` versus what remains available to the withdrawing/depositing LP in the very same instruction. This directly misstates the pool's PnL accounting - the persisted baseline no longer reflects the pool's true, unmanipulated reserve ratio - which is exactly the "insolvent/incorrect pool accounting" class of impact: value is shifted between ordinary LPs and the protocol's PnL reserve based on an artificial, attacker-chosen spot price rather than genuine trading activity.

### Likelihood Explanation
Any LP token holder can trigger this without needing a privileged signer, leaked key, or malicious validator - a single self-signed transaction with a swap instruction followed by a `Deposit`/`Withdraw` instruction followed by a reversing swap is sufficient, exactly analogous to the flash-loan-in-one-block pattern described in the source report but easier here since Solana atomically executes all instructions of one transaction with no separate "EOA-only" gate at all on the affected code path.

### Recommendation
Do not derive `calc_take_pnl`'s baseline/skim amounts from the instantaneous vault balances read within the same instruction that a caller can precede with an arbitrary swap. Options:
- Use a time-weighted or previous-slot snapshot of reserves for the PnL baseline calculation instead of the live balances read in the same transaction.
- Reject `Deposit`/`Withdraw` calls that follow a swap touching the same AMM within the same transaction (e.g., by tracking a per-block/per-slot "touched" flag on the `AmmInfo`), similar to reentrancy-style protections used elsewhere in the codebase.
- Bound how much the price ratio may move between the last recorded baseline and the current call before allowing a PnL-affecting instruction to proceed, rejecting instructions during that reversion window.

### Proof of Concept
1. Attacker holds LP tokens for pool `P` and has enough capital to move `P`'s price meaningfully (can also be funded within the same transaction from another liquidity source).
2. Build a single transaction with:
   - Ix 1: `SwapBaseIn` on pool `P`, sending a large amount of coin→pc (or vice versa), skewing `amm_coin_vault`/`amm_pc_vault` balances to an attacker-chosen ratio - reachable via `process_swap_base_in` ( [7](#0-6) ).
   - Ix 2: `Withdraw` (or `Deposit`) on pool `P`, which invokes `calc_total_without_take_pnl_no_orderbook` and `calc_take_pnl` using the just-skewed balances ( [2](#0-1) ), permanently rewriting `target_orders.calc_pnl_x`/`calc_pnl_y` and `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` at the attacker-chosen price.
   - Ix 3: A reversing `SwapBaseIn`/`SwapBaseOut` restoring the original vault ratio.
3. All three instructions execute atomically in one transaction signed only by the attacker; the attacker pays only the swap fees from Ix 1 and Ix 3, while the persistent `TargetOrders`/`need_take_pnl_*` state is left biased toward the composition the attacker chose, misallocating pool value between LPs and the protocol's PnL reserve for all subsequent interactions until the next `WithdrawPnl`/`Deposit`/`Withdraw` call recalculates it.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
