### Title
Reentrancy via untrusted-token callback before escrow-balance decrement in `IntentGatewayV2.withdraw()` (Tron variant) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-specific `IntentGatewayV2.sol` implements escrow settlement (`withdraw()`) using raw `.call()` token transfers that execute **before** the corresponding `_orders[commitment][token]` accounting is decremented — the same checks-effects-interactions (CEI) violation flagged in the SHER `_sendSherRewardsToOwner()` finding, where `sher.safeTransfer()` ran before `delete sherRewards_[_id]`. The already-hardened EVM path (`IntentsBase.sol::_withdraw`) fixes this exact class of bug by decrementing escrow before transferring, but the Tron contract still contains the vulnerable ordering.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` performs, for each escrowed token: [1](#0-0) 
```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```
The external call (`token.call(...transfer...)`) happens **before** the state variable `_orders[body.commitment][token]` is decremented — an unambiguous CEI violation, structurally identical to the reported SHER bug where the transfer preceded `delete sherRewards_[_id]`. The same pattern repeats for the transaction-fee payout, though there the fee mapping is (correctly) deleted before the transfer [2](#0-1) .

`withdraw()` is only reachable through `onAccept()`, gated by `onlyHost` [3](#0-2) , and no `nonReentrant` guard is present anywhere in this contract (confirmed absent by search). `token` in `body.tokens` originates from `order.inputs`, which is attacker-controlled at `placeOrder()` time — an attacker can register an order whose input token is a malicious ERC-777/hook-style contract. When `withdraw()` iterates a multi-token `body.tokens` array and reaches the malicious token entry, the malicious token's `transfer` hook gains full control of execution while `_orders[commitment][token]` for *subsequent, legitimate* tokens in the same array is still fully populated (unmodified). If the attacker can trigger a second delivery of an incoming message for the same `IntentGatewayV2` module during that callback window (e.g., a permissionless handler call carrying a valid state/consensus proof for another queued request), the reentrant `onAccept → withdraw` invocation re-reads the still-unmodified `_orders[commitment][token]` entries for the remaining tokens and pays them out a second time before the original call resumes and pays them out again through the normal loop continuation — a straightforward double-spend of the escrow.

This directly parallels the reported bug class: an external call to an implementation the app does not fully control (there, the SHER token; here, an attacker-supplied escrow input token) executes before the bookkeeping state (`sherRewards_` / `_orders[commitment][token]`) is updated, allowing repeated draining of the same accounted balance.

### Impact Explanation
A successful reentrant call sequence drains legitimate escrowed input tokens (e.g., USDC/DAI) held for one commitment by paying them out more than once, directly stealing funds from the `IntentGatewayV2` escrow — concrete theft of user/solver funds, consistent with the High/Critical impact bar for unbacked payout / fund drain in the intents escrow. Because the vulnerable ordering sits in the *settlement* path shared by both `RedeemEscrow` and `RefundEscrow` request kinds, both solver payouts and user refunds are exposed.

### Likelihood Explanation
Exploitability is Medium: it requires (a) an attacker to register an order whose input token is a malicious/hook-capable contract, and (b) a mechanism to reenter the module's `onAccept` (or otherwise trigger `withdraw()` for the same commitment) during the malicious token's transfer callback before the loop proceeds to the next, legitimate token. Item (a) is trivially attacker-controlled since order inputs are user-supplied at `placeOrder`. Item (b) depends on the reachability of a second `onAccept` delivery mid-callback, which is plausible given `onAccept` is only gated by `onlyHost` and the surrounding message-handling/relayer flow is otherwise permissionless with proof verification — this reentry path could not be fully confirmed from the available context and would need dedicated verification of the handler/host call graph. Regardless of the exact reentry vector, the core CEI violation (`_orders[...] -= amount` after the external `.call`) is a defect present unconditionally in the code and mirrors an already-acknowledged and fixed defect class in the sibling EVM contract.

### Recommendation
Apply the checks-effects-interactions fix already used in `IntentsBase.sol::_withdraw` (decrement before transfer) to the Tron variant:
```solidity
_orders[body.commitment][token] -= amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
```
Additionally, add an explicit `nonReentrant` guard to `withdraw()`/`onAccept()` in this contract (as is done for `fillOrder` in the main EVM `IntentGatewayV2.sol` [4](#0-3) ) so that even a successful reentry into the module cannot recurse through `withdraw()` for the same or related commitments.

### Proof of Concept
1. Attacker calls `placeOrder()` on the source chain with `order.inputs` containing two tokens: `[MaliciousHookToken, LegitimateToken (e.g. USDC)]`, escrowing both.
2. Attacker (as solver) fills/cancels the order on the destination side so that a `RedeemEscrow`/`RefundEscrow` `WithdrawalRequest` is dispatched back to the source chain, listing both tokens in `body.tokens`.
3. On delivery, `onAccept()` → `withdraw()` processes `body.tokens[0] = MaliciousHookToken` first: the `.call(...transfer...)` triggers the malicious token's callback before `_orders[commitment][MaliciousHookToken] -= amount` executes.
4. From inside the callback, the attacker triggers a second delivery of the same (or a duplicate) incoming request to the module (e.g., by submitting a second valid proof for another queued message targeting this gateway), causing a second `onAccept → withdraw` call for the same `commitment`.
5. This nested call re-reads `_orders[commitment][LegitimateToken]`, which is still fully escrowed (untouched, since the outer loop hasn't reached index 1 yet), and transfers it out — a first payout of `LegitimateToken`.
6. The nested call returns, the malicious token's transfer completes, the outer loop resumes, decrements `_orders[commitment][MaliciousHookToken]`, then proceeds to index 1 (`LegitimateToken`) and pays it out a *second* time, since the decrement from step 5 was applied to a value that the outer call's local loop state does not re-check beyond the stale in-memory iteration guard — resulting in a double payout of `LegitimateToken` from a single escrowed amount.

(Note: step 4's exact re-entry vector — i.e., whether a second `onAccept` delivery for the same module can be triggered mid-callback via the permissionless handler/relayer flow — was not independently confirmed against the handler/host call graph in this review and should be verified; the underlying CEI defect in `withdraw()`, however, is confirmed directly from the source.)
