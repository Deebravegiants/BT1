## Title
Withdraw's pro-rata payout can be silently sandwiched to near-zero because slippage protection is optional and all-or-nothing - (File: `program/src/processor.rs`)

## Summary
Raydium's `process_withdraw` computes the coin/pc amounts a withdrawing LP receives based on the pool's *current* vault balances at execution time, not the balances at submission time. Slippage protection (`min_coin_amount`/`min_pc_amount`) is entirely optional in the wire format, and even when supplied, the check is only enforced if *both* fields are simultaneously `Some`. This mirrors the Reserve Protocol bug class: a redemption/withdrawal transaction that sits in the mempool computes its payout against pool state that can be manipulated (via a swap/deposit sandwiched immediately before it lands), silently redeeming a user's LP tokens for far less value than expected — with LP tokens burned regardless.

## Finding Description
`WithdrawInstruction` is deserialized with `min_coin_amount`/`min_pc_amount` defaulting to `None` when the instruction data omits the trailing 16 bytes: [1](#0-0) 

In `process_withdraw`, the pro-rata `coin_amount`/`pc_amount` a user receives is computed from `total_coin_without_take_pnl`/`total_pc_without_take_pnl`, which are derived from the *live* vault balances read at instruction-processing time: [2](#0-1) 

The slippage guard is then applied — but only if **both** `min_coin_amount` and `min_pc_amount` are `Some`: [3](#0-2) 

If either field is `None` (which happens whenever the client omits the last 16 bytes of instruction data, or a wallet/integrator builds the instruction without full slippage params), the entire check is skipped, and the withdraw proceeds unconditionally:
```
if coin_amount < amm_coin_vault.amount && pc_amount < amm_pc_vault.amount {
    if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some() {
        ... // only path where amounts are validated
    }
    // burn LP + transfer whatever coin_amount/pc_amount happen to be, unconditionally
}
```
An attacker watching the mempool for a pending `Withdraw` (or `4`-tag) transaction that lacks full slippage parameters can, in a single block, submit a large swap that shifts the coin/pc ratio in the pool immediately before the victim's withdraw executes. Because `coin_amount`/`pc_amount` are computed pro-rata against `amm.lp_amount` at execution time using post-swap vault balances, the victim's LP tokens (`user_source_lp.amount`, specified by `withdraw.amount`) are burned in full via `Invokers::token_burn`, while the actual amounts transferred out can be pushed arbitrarily low for one side of the pair (the swap converts real value from one token to the other inside the vaults, and the LP's pro-rata share of the depleted side shrinks accordingly). This is directly analogous to the referenced Reserve `RToken.sol` finding: an LP submits a withdraw expecting proportional value, but the transaction executes against manipulated pool state and the redemption is honeypotted — full burn of the ownership token for degraded proceeds — because the protection meant to prevent this is optional and gated on both fields being set together rather than on each token individually (as `Deposit`'s `other_amount_min` correctly does per-side).

## Impact Explanation
This allows theft of LP value: a withdrawing user unaware of (or whose client omits) full slippage parameters loses proceeds from an in-block sandwich, while the attacker's swap-then-reverse-swap captures the difference. Because `token_burn` for the full `withdraw.amount` and both token transfers execute unconditionally when the `Some`/`Some` gate is not met, there is no fallback protection — the LP's capital can be drained close to the manipulated pro-rata amount on one leg while the other leg still burns the same LP quantity. This is a direct, unprivileged, single-transaction-reachable fund-theft vector against any liquidity provider withdrawing without a complete slippage guard.

## Likelihood Explanation
Likelihood is Medium: it requires precise transaction ordering within the same block/slot (searcher/validator MEV capability), and depends on the withdrawer's client/integration omitting `min_coin_amount`/`min_pc_amount` (many simple integrations may only set one or neither, especially since the deserialization format silently defaults both to `None` if the trailing bytes are absent, and the code doesn't reject partial specification — it just disables protection entirely). Given Solana's fast block times and well-known MEV/searcher activity around AMM pools, an attacker able to observe pending withdraw transactions can reliably execute this sandwich.

## Recommendation
- Enforce slippage checks independently per side, matching the `Deposit` path's pattern (`other_amount_min` checked whenever present, regardless of the other field): check `min_coin_amount` if `Some` and `min_pc_amount` if `Some` separately, rather than requiring both to be `Some` before any check runs.
- Consider making `min_coin_amount`/`min_pc_amount` mandatory (non-optional) for `Withdraw`, so a client cannot construct an unprotected withdrawal instruction at all.
- Optionally, snapshot/validate pool ratio deviation between submission-time expectations and execution-time state beyond just a floor check, or document strongly that omitting slippage parameters exposes LPs to sandwich risk.

## Proof of Concept
1. Victim submits `Withdraw` (`program/src/instruction.rs` tag `4`) with `amount = X` LP tokens and instruction data that omits the trailing 16 bytes (so `min_coin_amount = None`, `min_pc_amount = None`), expecting a pro-rata payout based on the pool state they last observed.
2. Attacker observes this transaction in the mempool/leader schedule and, in the same block ahead of the victim's tx, submits a large `SwapBaseIn`/`SwapBaseOut` that heavily skews the coin/pc vault ratio (e.g., dumping a large amount of `coin` into the pool, driving `pc` reserves down relative to `coin`).
3. Victim's `Withdraw` executes next: `Calculator::calc_total_without_take_pnl_no_orderbook` reads the now-skewed `amm_pc_vault.amount`/`amm_coin_vault.amount`; `coin_amount`/`pc_amount` are computed pro-rata against the skewed totals (`program/src/processor.rs:1719-1761`).
4. Since `withdraw.min_coin_amount`/`min_pc_amount` are both `None`, the guard at `program/src/processor.rs:1779-1786` is bypassed entirely; `Invokers::token_burn` burns the victim's full `X` LP tokens and transfers the now-degraded `coin_amount`/`pc_amount`.
5. Attacker reverses their swap (or lets arbitrageurs do so) to restore the pool ratio, netting the value siphoned from the victim's withdrawal, while the victim's LP position has been fully burned for less than fair value — the redemption honeypot analog to the Reserve Protocol finding.
