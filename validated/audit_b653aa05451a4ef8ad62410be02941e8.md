### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-attribution forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` value that is later trusted as the tenant identity is read from an HTTP header that is not part of that signed content. `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC/body pair and then hands the header-derived `shop` straight to the app's webhook handler as the authoritative tenant, breaking the intended binding of `HMAC-verified bytes == identity used for authorization`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived independently from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) against the HMAC header, and never checks `request.shop`: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirms only that `verifiable_query.to_signable_string` (body) matches the HMAC, with no reference to `shop`: [4](#0-3) 

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` *is* explicitly included in `to_signable_string` and therefore covered by the HMAC: [5](#0-4) 

Because the webhook's `shop` header is never part of the signed payload, the equality the library implicitly relies on — "the shop attributed to a validated webhook equals the shop whose secret produced the HMAC" — does not hold. An unprivileged actor who legitimately controls their own Shopify store will receive real webhooks for that store, each with a valid HMAC computed only over the body. Nothing in the raw body itself needs to reference the shop domain (most webhook payloads are resource data, not shop identity). That attacker can capture one such legitimate (body, HMAC) pair from their own store and replay it to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because it never looks at the header, and `Registry.process` passes the forged `shop` straight into `WebhookMetadata`, which host applications use to select the tenant/session for processing the event: [6](#0-5) 

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` from a `Registry`-validated webhook as the tenant identifier (the intended and documented usage pattern) can be made to process attacker-controlled webhook bodies under a victim shop's identity. Depending on the handler, this enables cross-tenant data injection/confusion — e.g., an app that updates local per-shop state (order status, inventory, GDPR/compliance flags, install status) keyed by `data.shop` from a webhook it believes is authentic for that shop. This matches the "cross-tenant access" class of Critical impact called out in scope.

### Likelihood Explanation
The attacker only needs their own installed shop (unprivileged, no special credentials, access tokens, or knowledge of `api_secret_key` required) to obtain one legitimate `(raw_body, hmac)` pair, then replay it against the app's public webhook endpoint with a modified `shop-domain` header — an operation entirely under the attacker's control via a normal HTTP client. No secrets are needed because the HMAC never covers the header being forged.

### Recommendation
Include `shop` in `Webhooks::Request#to_signable_string` is not possible (Shopify signs only the body), so instead the gem should not expose an unauthenticated `shop` accessor as trustworthy without a caveat, or should require callers to cross-check `request.shop` against the shop of the session/tenant they expect for that endpoint (e.g., document that `WebhookMetadata#shop` must be treated as untrusted webhook-header input and be revalidated against out-of-band tenant context, such as the URL route or a registered shop list) rather than treated as verified. Alternatively, since Shopify does not sign the shop header, the library should clearly document this gap and/or provide a stricter validation path that requires callers to supply the expected shop and reject mismatches before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker resends that exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only checks the (unchanged) raw body against the (unchanged) HMAC: [3](#0-2) 
4. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the payload actually originated from the attacker's own store.

          received_signature = verifiable_query.hmac
