### Title
Webhook `shop-domain` / `topic` / `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant handler confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler are read straight from unauthenticated HTTP headers. This breaks the identity binding: *the bytes that are HMAC-verified* (`raw_body` only) ≠ *the bytes that are trusted as the tenant identity* (`shop-domain` header). This is exactly the bug class described in the report ("a field acted on but not covered by the HMAC").

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never included in the signable string and thus are never covered by the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (unauthenticated headers) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated string field consumed by the handler as the tenant identifier: [5](#0-4) 

Because the HMAC is computed with the app's single, shared `client_secret` across all shops installed on the app (not a per-shop secret), any shop that has installed the app can legitimately receive a real Shopify webhook for its own store — i.e., a valid `(raw_body, hmac)` pair. That merchant (an "unprivileged internet user" with respect to other tenants of the same app) can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a *different* shop. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will happily construct `WebhookMetadata` attributing that (unauthenticated) shop identity, topic and webhook id to the request. The equality this breaks is:

`shop authenticated by HMAC (none — HMAC binds only raw_body)` ≠ `shop trusted as the tenant key handed to the app handler (request.shop from an unauthenticated header)`.

### Impact Explanation
If the hosting application uses `data.shop` (or `data.topic`/`data.webhook_id`) from `WebhookMetadata` as a lookup/storage key without independently verifying it belongs to the shop that actually owns the webhook subscription (which is exactly what this gem's own documented usage pattern in `docs/usage/webhooks.md` encourages — trust `Registry.process`'s output directly), a malicious merchant can cause the app to process or persist another merchant's data under the attacker-chosen shop, or vice versa. This is a cross-tenant confusion vector: data intended for shop A gets attributed to attacker-controlled shop B (or an arbitrary, non-installed shop string), potentially leading the app to act on/store attacker-supplied body content under a different tenant's session/data namespace. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker is a legitimate (even free/trial) merchant who has installed the target app — no special privilege, no access to `client_secret`, no token theft. They only need to capture one real webhook delivery for their own store (trivial — they control the store and can trigger events like `orders/create`) and replay it with a modified `shop-domain` header to the app's public webhook endpoint. The HMAC check as implemented in this gem cannot detect this because it was never designed to bind the header set to the signature; likelihood is Medium-High given the attacker-accessible prerequisite (installing the app) is trivial for any internet user.

### Recommendation
Do not use header-derived `shop`, `topic`, or `webhook_id` values as trusted identity without further verification. Either:
1. Extend `VerifiableQuery`/`to_signable_string` for webhooks to include the relevant headers (`shop-domain`, `topic`, `webhook-id`) in the signed content if Shopify's webhook signature scheme supports it, or
2. Document explicitly (and ideally enforce in `Registry.process`) that `WebhookMetadata.shop` must be cross-checked by the consuming app against a known/registered shop for that specific webhook subscription (e.g., verify the shop is one that currently has an active session/installation) before trusting it as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and legitimately receives a real webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body using the app's shared client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {"id": 123, ...}
   ```
2. Attacker replays the exact same request to the app's webhook endpoint, but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (and optionally `x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, per `lib/shopify_api/utils/hmac_validator.rb:12-31`, which only re-computes the HMAC over `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`) — validation still succeeds because the body is unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) using the attacker-controlled `shop-domain` header value `victim-shop.myshopify.com`.
5. The app's `WebhookHandler#handle` receives `data.shop == "victim-shop.myshopify.com"` together with the attacker's forged/replayed body, even though this webhook never originated from Shopify for that shop — demonstrating that the HMAC does not bind the `shop` field, enabling cross-tenant handler confusion.
