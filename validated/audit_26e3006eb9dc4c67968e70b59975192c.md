## Title
Escrow accounting assumes static ERC-20 balances; a rebasing (balance-decreasing) input or output token can freeze other users' escrowed funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

## Summary
`IntentGatewayV2`/`IntentsBase` escrow multiple orders' tokens together in one pooled contract balance, using a per-`(commitment, token)` accounting mapping (`_orders`) that is only updated on deposit/withdraw calls. Withdrawal transfers the *recorded* escrowed amount, not a value derived from the contract's live balance. This is the same class of bug the Curve report describes: code that assumes "balances only change via a transfer the contract itself observes" breaks once a token can change every holder's balance out-of-band (a rebase), because bookkeeping and actual balance diverge.

## Finding Description
`placeOrder` already defends against tokens that reduce the amount *during* a single transfer (fee-on-transfer) by diffing `balanceOf` before/after the transfer and storing the *actual received* amount in escrow: [1](#0-0) 

However, once tokens are escrowed, the contract's belief about how much of a token it holds for a given order is frozen in the `_orders[commitment][token]` mapping and is never reconciled against the token's live `balanceOf(address(this))`. Withdrawal simply decrements that stored value and transfers it out: [2](#0-1) 

Because the gateway holds many orders' escrow for the same token in one pooled balance (there is no per-order token segregation at the ERC-20 level — only the internal mapping distinguishes orders), the invariant `sum(_orders[*][token]) <= IERC20(token).balanceOf(address(this))` must hold at all times for every escrowed order to be redeemable. A rebasing token that can reduce holder balances without a `transfer` call (the exact limitation Curve's docs cite, and the same class flagged in the referenced report) silently breaks this invariant: the sum of outstanding escrow entries can exceed the actual token balance the contract holds, with no code path re-syncing the mapping to reality.

There is no allowlist, denylist, or rebasing-token check anywhere in `IntentGatewayV2`/`IntentsBase` restricting which ERC-20s can be used as `order.inputs`/`order.output.assets` tokens — any address is accepted as long as `safeTransferFrom`/`safeTransfer` succeed.

## Impact Explanation
When a negative-rebasing token is used as an input or output asset:
- Multiple orders' escrow entries for that token share one contract-held balance.
- After a downward rebase, the contract's actual balance for that token is less than the sum of the `_orders` entries still outstanding for it.
- The orders that attempt to withdraw *after* the rebase will have their `IERC20(token).safeTransfer(beneficiary, amount)` call revert (insufficient balance), since `amount` reflects the pre-rebase committed value, not the shrunk supply.
- This permanently freezes those users' funds (or forces the last order(s) to be undercollateralized/unfillable), since no function reconciles or partially satisfies an escrow whose backing balance has shrunk.

This matches the "permanent freezing of funds" acceptance criterion, reachable purely from unprivileged, ordinary `placeOrder`/`fillOrder`/`cancelOrder` calls with an attacker-chosen (or later-listed) rebasing token — no privileged action required.

## Likelihood Explanation
Likelihood is Medium-High for any deployment where `IntentGatewayV2` is not restricted to a known-safe token allowlist: intent-based systems are commonly extended to arbitrary ERC-20 pairs across chains, and a malicious/compromised token contract (or a legitimate but rebasing/deflationary token later escrowed by unaware users) is enough to trigger the freeze — the same "no restriction on token properties" gap that has repeatedly bitten Curve-style pools and other balance-diffing DeFi contracts.

## Recommendation
Either (a) explicitly disallow rebasing/elastic-supply tokens via a maintained allowlist for `order.inputs`/`order.output.assets`, or (b) change escrow withdrawal to cap the transferred amount at `min(recordedAmount, currentBalanceOf(token))` and account for any shortfall explicitly (e.g., pro-rata reduction across pending claims or an explicit "shortfall" event) rather than assuming the recorded amount is always fully backed. Segregating per-order balances is not generally practical for ERC-20 pooled custody, so an allowlist of vetted, non-rebasing tokens is the more robust fix, consistent with the Curve documentation's own recommendation to avoid rebasing tokens entirely in balance-sensitive pooled accounting.

## Proof of Concept
1. Gateway operator (or a user) allows a token `RBT` that rebases balances downward globally (e.g., an elastic-supply/rebasing stablecoin) to be used in `order.inputs`.
2. User A places `orderA` with `1000 RBT` input; gateway records `_orders[commitmentA][RBT] = 1000` and holds `1000 RBT` (balance-diffed at deposit, per `IntentGatewayV2.sol:313-329`).
3. User B places `orderB` with `1000 RBT` input; gateway now holds `2000 RBT`, `_orders[commitmentB][RBT] = 1000`.
4. `RBT` undergoes a 20% negative rebase; gateway's actual balance drops to `1600 RBT`, while `_orders` still totals `2000`.
5. Order A is filled/cancelled first and successfully withdraws `1000 RBT` (`IntentsBase.sol:451-470`), leaving `600 RBT` actual balance.
6. Order B's `_withdraw` call attempts `safeTransfer(beneficiary, 1000)` against the gateway's remaining `600 RBT` balance and reverts — order B's escrow is permanently stuck, with no function available to reconcile or partially release it.
