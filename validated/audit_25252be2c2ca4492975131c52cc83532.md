### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but the `shop` domain (along with `topic`, `webhook_id`, and `api_version`) is read directly from unauthenticated HTTP headers and passed straight into the handler as trusted metadata.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for a `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [4](#0-3) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from the `x-shopify-shop-domain`/`shopify-shop-domain` (and sibling) headers with no cryptographic binding to the signed body: [5](#0-4) [6](#0-5) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (body-only) before trusting `request.shop` to build `WebhookMetadata`, which is handed to the host application's `WebhookHandler#handle`: [2](#0-1) 

The identity-binding equality this breaks is: *bytes verified by HMAC (body only) ≠ bytes acted on to determine tenant identity (`shop` header)*. Because the HMAC key (`Context.api_secret_key`, i.e., the app's `client_secret`) is shared across every shop/tenant that has installed the app, any store that has legitimately installed the app can capture one of its own genuine webhook deliveries (valid signature over that body) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC still validates (it only covers the body), so `Registry.process` accepts the request and invokes the handler with `WebhookMetadata#shop` set to the victim's domain rather than the attacker's.

### Impact Explanation
This is a cross-tenant identity confusion at the library layer: the one piece of data (`shop`) that host applications rely on to select per-tenant session/data context is delivered to the handler without being covered by the authentication check. A host application following this gem's documented API (using `request.shop`/`data.shop` from `Registry.process` as the tenant key, as shown in the gem's own test suite) can be led to write, redact, or act on data under the wrong shop, corresponding to the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker's own store has the app installed (an "unprivileged" but legitimate multi-tenant SaaS customer of the app) — no access token, `api_secret_key`, or victim credentials are needed. The attacker simply replays a webhook body they legitimately received (with its valid HMAC) to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header. This is a realistic and inexpensive attack for any app serving more than one shop with a shared `client_secret`.

### Recommendation
Bind the tenant-identifying fields to the authenticated payload instead of trusting headers verbatim:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (e.g., verify against Shopify's per-webhook signature scheme that covers these fields), or
- Cross-check `request.shop` against an independently established tenant context (e.g., the session/shop the webhook subscription was registered for) before dispatching to the handler, rejecting mismatches.
- At minimum, document prominently that `request.shop` is unauthenticated header data and must not be used as the sole tenant selector without additional verification.

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and `victim.myshopify.com`, both signed with the same `Context.api_secret_key`.
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker replays this exact HTTP request to the app's webhook endpoint, only changing `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, since the signature never covered the shop header.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and invokes the app's handler, which acts as if the (attacker-supplied) body legitimately belongs to `victim.myshopify.com`. [2](#0-1)
