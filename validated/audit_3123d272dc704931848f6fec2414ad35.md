### Title
Accrued debt-value overflow permanently freezes a high-balance market - (File: common/src/rates/index.rs)

### Summary
A single unprivileged user can create a large borrow market and later call `update_indexes` to trigger an `i128` overflow while calculating `borrowed * borrow_index`. Because every pool mutation synchronizes interest before acting, the overflow permanently blocks repayment, withdrawal, liquidation, bad-debt cleanup, and further index updates for that market.

### Finding Description
`Controller::update_indexes(caller, assets)` is permissionless apart from caller authorization and forwards the provided `HubAssetKey` list to the pool. [1](#0-0) 

Pool accrual computes old and new total debt as `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)` in `calculate_supplier_rewards`. [2](#0-1)  These products are RAY-scaled values: a market with `1e18`-decimal token supply of `1e27` base units already stores approximately `1e36` scaled debt, and the representable `i128` ceiling is only about `1.70e38`. Once the borrow index exceeds roughly 170×, the multiplication can no longer fit in `i128`.

The panic occurs before `update_borrow_index` reaches its `MAX_BORROW_INDEX_RAY` cap because the cap is applied after the product is evaluated. [3](#0-2) 

The market is then unrecoverable through its normal paths: `update_indexes`, `supply`, `borrow`, `withdraw`, and `repay` all load an interest-synced market. [4](#0-3)  `global_sync` runs `accrue_chunk`, which invokes the shared `accrue_step` calculation before committing the timestamp. [5](#0-4) 

### Impact Explanation
Permanent freezing of user funds and protocol insolvency.

Once `borrowed * borrow_index` exceeds `i128::MAX`, no transaction can advance `last_timestamp`, because accrual panics before `mark_accrued` or `commit`. Every later state-changing operation repeats the same overflowing accrual. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot process the account, and governance/admin paths that first synchronize the market also fail. Token cash remains in the pool while the corresponding positions are frozen.

The repository contains a regression-style test demonstrating the condition: a one-billion-token, 18-decimal market at 98% utilization eventually returns `MathOverflow`; subsequent withdrawal and repayment attempts fail with the same error while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [6](#0-5) 

### Likelihood Explanation
High once a listed market and its configured spoke caps permit a book approaching the raw RAY-value domain.

An unprivileged attacker can:

1. Call `supply(caller, 0, spoke_id, [(BIG, 1_000_000_000 * 10^18)])` to create the pool claim. The controller measures the token transfer and submits the corresponding `PoolSupplyEntry`. [7](#0-6) 
2. Supply sufficient collateral and call `borrow(caller, account_id, [(BIG, 980_000_000 * 10^18)], Some(caller))`. The public controller entrypoint requires only owner/delegate authorization and post-borrow solvency. [8](#0-7) 
3. Wait for interest to increase `borrow_index`.
4. Call `update_indexes(caller, [BIG])`; the call is permissionless and forces accrual. [1](#0-0) 

No privileged call is required to trigger the overflow. The economic prerequisite is a very large market and enough collateral to pass borrowing checks; configured caps and actual token supply determine whether a particular deployment exposes it. Caps are configuration-dependent rather than an intrinsic arithmetic bound: the documented maximum token input is approximately `i128::MAX / 10^(27-d)`, which permits the demonstrated billion-token, 18-decimal book.

### Recommendation
Bound index valuation before multiplying, rather than allowing an unrecoverable `i128` panic.

- Before each accrual step, reduce the compounding interval so `borrowed * projected_borrow_index`, `supplied * projected_supply_index`, and their additions remain below `i128::MAX`.
- Alternatively, enforce a market-level invariant such as `max(supplied, borrowed) <= i128::MAX / MAX_BORROW_INDEX_RAY` on every debt/supply mint, ensuring all later index products remain representable.
- Prefer saturating or capped debt-value projections during accrual, then set `borrow_index` directly to `MAX_BORROW_INDEX_RAY` when the exact product cannot fit. This preserves repayment, withdrawal, liquidation, and cleanup paths.
- Add a production-level regression test that reaches the boundary without test-only cap changes and proves `repay`, `withdraw`, `liquidate`, and `clean_bad_debt` remain executable.

### Proof of Concept
The repository’s test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the sequence:

```text
supply(BOB, BIG18, 1_000_000_000 * 10^18)
supply(ALICE, COL, 3_000_000_000 * 10^7)
borrow(ALICE, BIG18, 980_000_000 * 10^18)

repeat:
    advance ledger by one year
    update_indexes([BIG18])
until update_indexes returns MathOverflow

withdraw(BOB, BIG18, 1) -> MathOverflow
repay(ALICE, BIG18, 1 unit) -> MathOverflow
borrow_index < MAX_BORROW_INDEX_RAY
```

The failure occurs inside the scaled-value multiplication used by accrual, before the borrow-index ceiling can engage, and repeats for all later operations because each operation calls `global_sync` first. [2](#0-1)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
