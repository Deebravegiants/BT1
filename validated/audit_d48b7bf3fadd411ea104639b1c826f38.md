This confirms the finding: `ShopifyAPI::Webhooks::Registry.process` explicitly documents that it "will verify the request did indeed come from Shopify" [1](#0-0)  and hands the host app a `WebhookMetadata` object whose `shop` field is presented as trustworthy, tenant-identifying data for the handler to act on (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [2](#0-1) . However, the HMAC computed by `HmacValidator.validate` is only ever checked against `Request#to_signable_string`, which returns just `@raw_body` — none of the `shop`, `topic`, or `webhook_id` headers are part of the signed material [3](#0-2) [4](#0-3) . `Registry.process` then trusts `request.shop` unconditionally to build the metadata passed to the handler [5](#0-4) .

### Title
Webhook tenant identity (`shop` header) not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so the `X-Shopify-Shop-Domain` header — the sole tenant identifier passed to app webhook handlers via `WebhookMetadata#shop` — is never authenticated by `HmacValidator.validate`. Any party capable of producing one valid `(body, hmac)` pair for the shared app `client_secret` can attach an arbitrary `shop` value to it and have `Registry.process` treat the payload as if it originated from that other shop.

### Finding Description
`Registry.process` gates on `Utils::HmacValidator.validate(request)` alone before dispatching to the registered handler [5](#0-4) . `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [4](#0-3) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [6](#0-5) , while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated headers [7](#0-6) . The identity binding the gem's own webhook documentation promises — "this will verify the request did indeed come from Shopify" for the given `shop` in `WebhookMetadata` [8](#0-7)  — does not actually hold for the `shop` field: `hmac(secret, body) == hmac(secret, body)` is verified, but `shop_header == shop_that_produced_this_body` is never checked. Because the `client_secret` (and thus the HMAC key) is identical for every shop that installs a given public app, an attacker who installs the app on their own store legitimately receives real `(body, hmac)` pairs signed with that shared secret. They can then replay the same body/hmac while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain; `HmacValidator.validate` still succeeds because it never inspects that header.

### Impact Explanation
This breaks the cross-tenant boundary the gem is documented to enforce for webhook processing: a handler built per the documented pattern will act on `data.shop` for a shop that never actually sent the event, e.g. enqueuing background jobs, updating per-shop records, or triggering shop-scoped side effects (including mandatory compliance topics like `shop/redact`) under a victim's identity. This is a Critical-class cross-tenant access issue in a multi-tenant app built on this gem.

### Likelihood Explanation
Any user of a public app that also installs it on a shop they control can obtain a validly-signed webhook body/HMAC pair using the app's shared `client_secret` (no leaked credentials, access token, or privileged account required — just normal app installation), then replay it with a forged `shop` header against the app's public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) header values in the material that is HMAC-verified, or otherwise cryptographically bind the verified body to the claimed shop before constructing `WebhookMetadata`, so `Registry.process` cannot dispatch data under an unauthenticated `shop` value.

### Proof of Concept
1. Attacker installs the target public app on `attacker.myshopify.com`, triggering a real webhook (e.g. `orders/create`) with a valid `X-Shopify-Hmac-Sha256` computed over the raw body with the app's shared `client_secret`.
2. Attacker captures `raw_body` and its valid `hmac`.
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body`/`hmac` but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers as-is; `HmacValidator.validate` succeeds because it only checks the body [6](#0-5) .
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim.myshopify.com"` [9](#0-8) , causing the app to process attacker-controlled data as though it belonged to the victim shop.
