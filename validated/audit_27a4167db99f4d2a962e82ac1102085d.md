### Title
Keychain's `addExternalPrivateKey` stores the caller-supplied private key buffer by reference, allowing later external mutation to corrupt signing key material - (File: features/keychain/module/keychain.js)

### Summary
This is a direct analog of the BigNumber bug class: a security-relevant library stores an externally-provided buffer directly in its internal state instead of copying it, so a later external mutation of that buffer silently corrupts the value the library relies on for cryptographic operations.

### Finding Description
`Keychain.addExternalPrivateKey` accepts a caller-supplied `privateKey` (a `Uint8Array`/`Buffer`) and stores the exact same object reference into its internal `#masters[seedId]` map without cloning it: [1](#0-0) 

Specifically, the `master.derive` closure captures and returns the identical `privateKey` reference every time it's called: `return { privateKey, publicKey, toJSON: () => ({ xpriv: null, xpub: null }) }`. This object is what `#getPrivateHDKey` hands out to every downstream signing routine (`secp256k1.signBuffer`, `ed25519.signBuffer`, `sodium.sign`, `cardanoEd25519.signBuffer`), all of which consume `hdkey.privateKey` directly without copying it themselves: [2](#0-1) [3](#0-2) 

This mirrors the reported BigNumber issue precisely: an object that accepts a buffer either allocates its own copy (for the derived/native BIP32 seed path via `bip32FromMasterSeed`, which is safe) or, in the "external private key" path, aliases the caller's buffer directly. Any code in the same JS realm that retains a reference to the buffer it passed into `addExternalPrivateKey` — for example, code that wipes/zeroes sensitive buffers after use (a common, and encouraged, security hygiene practice elsewhere in this codebase, e.g. `randomFill(databuffer)` patterns in `libraries/secure-container/src/compressed.js`) — will silently corrupt the keychain's stored key material with no validation, exception, or integrity check performed on subsequent use. [4](#0-3) 

By contrast, the same file's `bip32/hdkey.js` module partially defends against exactly this class of bug in some places (e.g. `#setPublicKey` does `this.#publicKey = Buffer.from(publicKey)` to force a copy) but not others (`set privateKey`, `get privateKey` return/store the raw reference): [5](#0-4) 

### Impact Explanation
If the private key buffer stored by `addExternalPrivateKey` is mutated after registration (intentionally by careless caller-side cleanup code, or by any other code sharing the reference), all subsequent `signBuffer`/`getPublicKey`/`exportKey` calls for that `seedId` will operate on corrupted key material. This can produce signatures derived from a different (attacker-influenced or garbage) private key, or expose intermediate key state to any code holding the aliased reference — a direct violation of the confidentiality/integrity guarantees expected of a keychain trust boundary responsible for wallet signing.

### Likelihood Explanation
Exploitability depends on some in-process caller retaining and later mutating the buffer object it handed to `addExternalPrivateKey`. This is plausible for internal features that import external private keys and then perform standard secure-buffer hygiene (zeroing sensitive buffers post-use), and is a realistic engineering foot-gun rather than a purely theoretical concern, matching the report's characterization ("a user of the library could definitely modify the buffer... doesn't represent an attack against the system" but "should be fixed"). I was not able to fully trace every caller of `addExternalPrivateKey` beyond `create-signer.js` and its test file within the available index, so I cannot confirm whether any current caller actually keeps and mutates the reference in production code today — this should be verified with a full-repo grep in a live Devin session.

### Recommendation
In `addExternalPrivateKey` (and anywhere else a `Uint8Array`/`Buffer` secret is accepted from a caller), defensively copy the buffer before storing it internally (e.g., `privateKey = Buffer.from(privateKey)`), and likewise ensure any getter that returns internal secret buffers (`HDKey.get privateKey`, `master.derive().privateKey`) returns a copy rather than the live reference, consistent with the pattern already used for `#publicKey` in `libraries/bip32/src/hdkey.js`.

### Proof of Concept
```js
import keychainDefinition, { KeyIdentifier } from 'features/keychain/module/index.js'

const keychain = keychainDefinition.factory({ logger: console, legacyPrivToPub: {} })
const privateKey = Buffer.from('bb42809079e6564ec7e45af4d6a8fb8c5edc9373d8585b86f62f46ec7aa4172', 'hex')
const keyId = new KeyIdentifier({
  derivationPath: "m/44'/60'/0'/0/0",
  derivationAlgorithm: 'BIP32',
  keyType: 'nacl',
})

const seedId = await keychain.addExternalPrivateKey({ privateKey, keyId })

// Caller performs "secure cleanup" of the buffer it passed in,
// unaware the keychain stored the same reference internally:
privateKey.fill(0)

// All subsequent signing for this seedId now silently uses a zeroed/corrupted key:
const sig = await keychain.signBuffer({ seedId, keyId, signatureType: 'ed25519', data: Buffer.alloc(32) })
// sig is now derived from the corrupted (zeroed) key, not the original imported key
```

    throwIfInvalidKeyIdentifier(keyId)

    let publicKey

    if (keyId.derivationAlgorithm === 'SLIP10' && keyId.keyType === 'nacl') {
      publicKey = await edwardsToPublic({ privateKey, format: 'buffer' })
    }

    if (keyId.derivationAlgorithm === 'BIP32' && keyId.keyType === 'secp256k1') {
      publicKey = await privateKeyToPublicKey({ privateKey, format: 'buffer' })
    }

    const seedId = await this.#createExternalSeedId({ privateKey, publicKey, keyId })
    const master = {
      __proto__: null,
      privateKey,
      keyId,
      derive: (path) => {
