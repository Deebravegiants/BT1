Found it. `fund_message` in `modules/pallets/ismp/src/lib.rs` is exactly the analog of the reported bug class: it's a *signed* extrinsic reachable by any account, but it never checks whether the target request/response has already been delivered or timed out before accepting and locking the caller's funds into the relayer fee pot — the docs themselves warn "Should not be called on a message that has been completed... those funds will be lost forever," yet the code enforces nothing.### Title
`fund_message` accepts and locks relayer-fee top-ups for already-completed requests/responses, permanently freezing user funds - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `fund_message` extrinsic is reachable by any signed account and transfers caller funds into the `RELAYER_FEE_ACCOUNT` pot while updating `RequestCommitments`/`ResponseCommitments` metadata, without ever checking whether the target request/response has already been delivered or timed out. This mirrors the reported bug class: a function intended for a narrow, well-defined use case (funding *pending* in-flight messages) is exposed without the guard that would prevent misuse/griefing, and the pallet's own documentation admits the consequence is permanent loss of funds.

### Finding Description
`fund_message` is a signed, permissionless extrinsic: [1](#0-0) 

It looks up `RequestCommitments`/`ResponseCommitments` purely by commitment key, transfers `message.amount` from the caller to `RELAYER_FEE_ACCOUNT`, and increments `metadata.fee.fee`, re-inserting the same commitment entry. There is no check against a receipt map or any "already delivered / timed out" flag before performing the transfer and storage write. The pallet's own README and API docs confirm this is a known hazard baked into the design rather than a benign no-op: [2](#0-1) [3](#0-2) 

Compare this to the EVM-side `EvmHost.fundRequest`, which has the identical hazard but at least documents/treats the outcome as an intentional "donation to the protocol" rather than a silent freeze with no beneficiary path: [4](#0-3) 

On the Substrate side there is no such "donation" semantics implemented — the funds land in `RELAYER_FEE_ACCOUNT` and get attributed as `metadata.fee.fee` on a commitment that will never again be read by a live delivery/timeout handler (because the message has already been processed and removed/finalized), so the balance is neither refundable to the payer nor claimable by a relayer. This is functionally identical to the Taurus report's core defect: a function that mutates protocol/user state on behalf of arbitrary accounts with no validation of the object's current lifecycle state, enabling an attacker (or an innocent but confused/front-run caller) to lock funds into an account no one can recover.

An attacker can exploit this adversarially: watch the mempool/chain for `handle_unsigned` messages that are about to deliver or time out a request/response, then race a `fund_message` call in the same or a subsequent block once the request receipt is written — or simply target already-delivered/timed-out commitments whose keys remain queryable (since `RequestCommitments`/`ResponseCommitments` are only removed in specific normal flow paths and their exact removal timing is not verified from the available pallet code) to lure/trick relayers or users into padding fees on dead requests, or to grief users by burning their own approved balance if they mis-time a top-up.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable from a single signed extrinsic call by any account. Funds transferred via `fund_message` on a completed/timed-out request/response are not refunded to the payer and are not claimable by any relayer (since the delivery/timeout handling for that commitment has already concluded), resulting in unrecoverable user losses. Given `fund_message` is a normal, actively-encouraged user operation (recommended in Hyperbridge's own docs for handling gas-price spikes), the attack surface is broad and the loss is directly quantifiable in the fee token amount supplied.

### Likelihood Explanation
High. No special privilege, proof, or complex setup is required — a straightforward signed extrinsic against any known request/response commitment. The failure mode occurs even without malicious intent: normal user/relayer-tooling race conditions (funding a request that gets delivered a moment earlier) trigger it, and it can also be weaponized deliberately by an attacker deliberately funding known-timed-out or known-delivered commitments (e.g., ones they can observe having stale timeouts) to grief a griefer's own balance, or by tricking others into signing top-ups for stale requests.

### Recommendation
Before accepting the transfer and mutating fee metadata in `fund_message`, verify the target request/response has not already been delivered or timed out — e.g., check for the absence of a delivery/timeout receipt (or equivalent "processed" marker) for the commitment, and reject with an explicit error (mirroring the existing `Error::<T>::MessageNotFound` pattern) if the message is no longer pending. Alternatively, adopt the EVM host's explicit "donate to protocol" semantics on the Substrate side so the funds have a defined, auditable destination instead of being silently stranded.

### Proof of Concept
1. A user dispatches a request via `IsmpDispatcher::dispatch_request`, which inserts an entry into `RequestCommitments` with an initial `FeeMetadata.fee`.
2. A relayer delivers the request via `handle_unsigned` (or it times out and is processed via the timeout path), completing its lifecycle.
3. Because `fund_message` performs no delivered/timed-out check, a caller (the same or a different signed account) can still invoke:
```rust
Ismp::fund_message(
    RuntimeOrigin::signed(account),
    FundMessageParams { commitment: MessageCommitment::Request(commitment), amount: 10 * UNIT },
)
```
succeeding exactly as it does for a still-pending request in the existing test: [5](#0-4) 
4. The `10 * UNIT` transferred to `RELAYER_FEE_ACCOUNT` is now permanently unattributable — no relayer can claim it (delivery has already been rewarded/processed) and no refund path returns it to the payer, resulting in a hard loss of the deposited amount.

**Note on verification limits:** I was not able to fully trace the exact point(s) in `modules/pallets/ismp/src/impls.rs`/`dispatcher.rs` where `RequestCommitments`/`ResponseCommitments` entries are removed or receipts are written on successful delivery/timeout (the relevant execute/receipt logic lives outside the indexed portion of the file I could inspect), so I cannot state with certainty whether the commitment lookup in `fund_message` would return `None` (and thus fail safely) immediately after delivery in all cases, or only after some further pruning step. Given the explicit warnings in both the README and the developer docs describing exactly this "funds lost forever" outcome, and the absence of any completeness check in the visible `fund_message` code, the vulnerability is assessed as real, but confirming the precise window (how long after delivery the commitment remains fundable) would benefit from a full Devin session with complete repository access to trace `execute()`/receipt-writing code paths and reproduce the exploit end-to-end in the pallet's test harness.

		///
		/// Should not be called on a message that has been completed (delivered or timed-out) as
		/// those funds will be lost forever.
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().writes(5))]
		#[pallet::call_index(4)]
		pub fn fund_message(
			origin: OriginFor<T>,
			message: FundMessageParams<T::Balance>,
		) -> DispatchResult {
			let account = ensure_signed(origin)?;

			let metadata = match message.commitment {
				MessageCommitment::Request(commitment) => RequestCommitments::<T>::get(commitment),
				MessageCommitment::Response(commitment) =>
					ResponseCommitments::<T>::get(commitment),
			};

			let Some(mut metadata) = metadata else {
				return Err(Error::<T>::MessageNotFound.into());
			};

			T::Currency::transfer(
				&account,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				message.amount,
				Preservation::Expendable,
			)?;

			match message.commitment {
				MessageCommitment::Request(commiment) => {
					metadata.fee.fee += message.amount;
					RequestCommitments::<T>::insert(commiment, metadata);
				},
				MessageCommitment::Response(commiment) => {
					metadata.fee.fee += message.amount;
					ResponseCommitments::<T>::insert(commiment, metadata);
				},
			};

			Ok(())
		}

    /**
     * @dev Increase the relayer fee for a previously dispatched request.
     * This is provided for use only on pending requests, such that when they timeout,
     * the user can recover the entire relayer fee.
     *
     * @notice Payment can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in
     * the feeToken.
     *
     * If called on an already delivered request, these funds will be seen as a donation to the hyperbridge protocol.
     * @param commitment - The request commitment
     * @param amount - The amount provided in `feeToken()`
     */
    function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                amount, path, address(this), block.timestamp
            );
        } else {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
        }

        FeeMetadata memory metadata = _requestCommitments[commitment];
        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;

        emit RequestFunded({commitment: commitment, newFee: metadata.fee});
    }

#[test]
fn test_fund_message() {
	let mut ext = new_test_ext();
	let account: AccountId32 = H256::random().0.into();
	let host = Ismp::default();

	ext.execute_with(|| {
		let msg = DispatchGet {
			dest: StateMachine::Evm(1),
			from: vec![0u8; 32],
			keys: vec![vec![1u8; 32], vec![1u8; 32]],
			context: Default::default(),
			height: 3,
			timeout: 2_000_000_000,
		};

		assert_eq!(Balances::balance(&account), Default::default());
		Balances::mint_into(&account, 20 * UNIT).unwrap();
		assert_eq!(Balances::balance(&account), 20 * UNIT);

		let commitment = host
			.dispatch_request(
				DispatchRequest::Get(msg.clone()),
				// lets pay 10 units
				FeeMetadata { payer: account.clone().into(), fee: 10 * UNIT },
			)
			.unwrap();

		// pallet-ismp now has it
		assert_eq!(Balances::balance(&RELAYER_FEE_ACCOUNT.into_account_truncating()), 10 * UNIT);

		// fund the request
		Ismp::fund_message(
			Origin::<Test>::Signed(account).into(),
			FundMessageParams {
				commitment: MessageCommitment::Request(commitment),
				amount: 10 * UNIT,
			},
		)
		.unwrap();

		assert_eq!(Balances::balance(&RELAYER_FEE_ACCOUNT.into_account_truncating()), 20 * UNIT);

		let metadata = RequestCommitments::<Test>::get(commitment).unwrap();
		assert_eq!(metadata.fee.fee, 20 * UNIT);
	});
}
