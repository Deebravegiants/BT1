### Title
Excess native-token fee payment on `EvmHost.dispatch`/`fundRequest` is permanently trapped, not refunded to caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and swap it through `swapETHForExactTokens` to obtain an exact amount of `feeToken()`. Any leftover ETH from that swap is refunded by the Uniswap router — but to the wrong recipient. The router refunds unspent ETH to its immediate caller (`msg.sender` from the router's perspective), which is `EvmHost` itself, not the original transaction sender who supplied the `msg.value`. The excess ETH is therefore stranded inside `EvmHost`'s own balance with no code path to return it to the payer.

### Finding Description
In all three functions, the pattern is identical: [1](#0-0) [2](#0-1) [3](#0-2) 

`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called directly by `EvmHost`. In the standard `UniswapV2Router02` implementation, `swapETHForExactTokens` computes the exact input required, performs the swap, and then refunds `msg.value - amountIn` back to `msg.sender` of the call — here that is `address(EvmHost)`, not `_msgSender()` (the dispatching application/user who actually funded the call). Unlike `IntentGatewayV2`/`ExtrinsicIntents`, which explicitly track `msgValue` locally and call `_sendValue(msg.sender, msgValue)` to refund any leftover native token after their own `swapETHForExactTokens` calls (see `evm/src/apps/IntentGatewayV2.sol:375-397` and `evm/src/apps/intentsv2/ExtrinsicIntents.sol:203-217`), `EvmHost` has no such refund step and no `receive()`/sweep mechanism was found to reclaim the ETH that lands on it from the router's refund.

Consequently, any overestimation of the ETH amount needed to cover `post.fee`/`get.fee`/`amount` (which is easy, since the exact swap-in amount depends on live AMM reserves at execution time and callers must send `msg.value` in advance) results in the excess being irrecoverably absorbed into `EvmHost`'s balance.

### Impact Explanation
This is directly reachable by any unprivileged message dispatcher (any application calling `IDispatcher(host).dispatch()` for a POST or GET request, or calling `fundRequest()` to top up a relayer fee) — exactly the class of "unprivileged message dispatcher... bandwidth purchaser" actors in scope. Every native-token payer of dispatch/relayer fees permanently loses any overpayment above the exact swap cost, which for volatile AMM pricing can be substantial and is impossible to predict precisely off-chain. This is a permanent loss of user/application funds with no recovery path, meeting the "permanent freezing/loss of funds" bar.

### Likelihood Explanation
High likelihood: `msg.value` sizing for a Uniswap `swapETHForExactTokens` call is inherently imprecise (slippage buffers are standard practice — callers routinely overpay to guard against price movement between quote and execution), so virtually every native-token dispatch/fundRequest transaction will produce some excess ETH that becomes stuck. This occurs on the base ISMP dispatch path used pervasively across all IApp integrations, not an edge case.

### Recommendation
Track the actual ETH consumed by the swap and refund the difference to `_msgSender()` (not rely on the router's own refund, which targets the wrong address), e.g.:
```solidity
uint256 balanceBefore = address(this).balance - msg.value;
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 refund = address(this).balance - balanceBefore;
if (refund > 0) {
    (bool sent, ) = _msgSender().call{value: refund}("");
    require(sent, "refund failed");
}
```
Apply the same fix to `dispatch(DispatchGet)` and `fundRequest`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost)` (or `dispatch(DispatchGet)` / `fundRequest`) with `msg.value = X`, intending to cover `post.fee` fee-tokens via swap.
2. `swapETHForExactTokens{value: X}(post.fee, path, address(this), ...)` executes; suppose the actual ETH needed is `Y < X`.
3. The Uniswap router refunds `X - Y` ETH to `msg.sender` of the router call, which is `EvmHost`'s own address (since `EvmHost` itself invoked the router).
4. `EvmHost`'s ETH balance increases by `X - Y`, but no code path exists in `EvmHost` to send this back to the original caller — it is permanently stuck in the contract, benefiting neither the caller nor the protocol treasury.
