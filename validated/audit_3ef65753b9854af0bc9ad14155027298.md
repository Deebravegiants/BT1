### Title
`CallDispatcher.dispatch()` has no access control, allowing anyone to drain any tokens or ETH sitting in the shared dispatcher contract - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is `external` with no caller restriction (no `onlyOwner`, no `onlyGateway`/`onlyHost` check), yet it executes arbitrary attacker-supplied `Call[]` (`to`, `value`, `data`) using the CallDispatcher's own ETH/token balance. This is the same bug class as the Napier `PeripheryPayments` sweep functions: a periphery/utility contract that temporarily holds funds sent to it by users/apps, but exposes an unauthenticated function that lets anyone move those funds wherever they like.

### Finding Description
`CallDispatcher` is a shared execution helper used by both `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` (`onAccept`, via `ICallDispatcher(_dispatcher).dispatch(message.data)`) and `IntentGatewayV2`/`IntentsBase` (`_execute`, predispatch/postdispatch calldata execution) to run arbitrary calldata on behalf of orders/messages. [1](#0-0) 

The contract:
- Has a `receive() external payable {}` so it accepts native ETH.
- Has `dispatch(bytes memory encoded)` marked `external` with **no `msg.sender` check at all** — any account can call it directly.
- For each decoded `Call`, it does `to.call{value: call.value}(call.data)` — using the contract's *own* ETH balance (`call.value` is paid from `address(this).balance`, not `msg.value` of the caller) and can target any contract with code, including ERC20 tokens (`transfer(attacker, amount)`), because the only guard is `extcodesize(to) != 0`.

Because `CallDispatcher` is invoked by the intents/token-bridge flows to hold and route funds mid-execution (e.g., `IntentsBase._execute` transfers order-output assets into the dispatcher, runs `order.output.call`, then sweeps residual balances back; the `WrappedHyperFungibleToken` variants pass `message.data` for post-receipt execution), any ETH or ERC20 balance that ends up sitting on the `CallDispatcher` address — whether from a partially-swept postdispatch leftover, a stray direct transfer, or funds in flight between steps — can be swept out by literally anyone by simply calling `dispatch()` themselves with a `Call` that transfers the balance to their own address, before or instead of the legitimate caller's dispatch.

This mirrors the Napier report exactly: a periphery contract holds funds on behalf of users temporarily, and a public function (`dispatch`, analogous to `sweepToken`) lets any third party redirect those funds.

### Impact Explanation
Any token or native ETH balance held by `CallDispatcher` at any point (dust left from `_execute`'s output-token routing, ETH sent via its unrestricted `receive()`, or approvals/tokens transferred to it as part of predispatch/postdispatch flows) can be permanently stolen by any unprivileged address. Since `CallDispatcher` is shared infrastructure wired into both the intents gateway and the wrapped fungible token apps, this is a direct theft-of-funds vector reachable from a single unprivileged transaction — satisfying the "concrete theft of funds" bar.

### Likelihood Explanation
High. `dispatch()` requires zero authorization and is a `public`/`external` entrypoint on a contract address that is documented to receive tokens/ETH as part of normal order execution (`_execute` transfers assets to the dispatcher before running calldata). Any attacker monitoring the dispatcher's balance (or racing a pending transaction that will leave dust) can call `dispatch()` directly to redirect funds to themselves — no special conditions, proofs, or governance actions are required.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the authorized apps that are configured to use it (e.g., an `onlyAuthorized` modifier checking `msg.sender` against a set of approved gateway/token contract addresses set at deployment/configuration time), analogous to adding access control to Napier's `sweepToken`/`refundETH`/`unwrapWETH9`. Alternatively, make `CallDispatcher` non-custodial by design: never let funds rest on its balance across transaction boundaries, and add a `nonReentrant`/single-use guard so `dispatch()` cannot be invoked out-of-band by third parties.

### Proof of Concept
1. In the normal flow, `IntentsBase._execute` or `WrappedHyperFungibleToken.onAccept` transfers ERC20 tokens (or ETH) to the `CallDispatcher` address and then calls `ICallDispatcher(dispatcher).dispatch(...)` to run the order's/message's calldata, expecting any leftover balance to be swept back to the gateway.
2. Because `CallDispatcher.dispatch()` has no access control, an attacker can independently call:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({
    to: address(token),
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, token.balanceOf(address(dispatcher)))
});
callDispatcher.dispatch(abi.encode(calls));
```
3. If executed after tokens have been transferred into `CallDispatcher` but before the legitimate sweep-back call executes (e.g., dust left after a failed/partial postdispatch execution, or ETH sitting from its permissive `receive()`), the attacker's call succeeds because `dispatch()` performs no caller check — draining the dispatcher's balance to the attacker.

```text
    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
