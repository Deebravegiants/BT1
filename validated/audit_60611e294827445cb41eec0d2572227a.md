## Finding: Stale `TombStone.original_owner` in `object::burn`/`unburn` allows theft of transferred objects

### Title
Object `burn`/`unburn` custody bypass via stale `TombStone` after ordinary ownership transfer - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
This is the same bug class as the Gitcoin `QVBaseStrategy` issue: a per-entity status/record (`reviewsByStatus`, here `TombStone.original_owner`) is written once and is not cleared when the entity's controlling relationship changes through a different code path than the one the designers expected to reset it. In Aptos' `object.move`, `TombStone{ original_owner }` is only cleared inside `transfer_with_ref` (the `LinearTransferRef` path), but not inside the plain `transfer`/`transfer_raw` path [1](#0-0) . This lets a stale `original_owner` field be used later by `unburn` to redirect an object away from its legitimate current owner.

### Finding Description
`burn` creates a `TombStone{ original_owner }` recording whoever is the object's owner *at the moment of the call*, without changing actual ownership: [2](#0-1) 

`unburn` later has two recovery paths:
- If the *current* owner calls it, the `TombStone` is simply discarded without checking `original_owner` at all.
- If the object's current owner is the special `BURN_ADDRESS`, `unburn` transfers the object back to whatever address is stored as `original_owner_addr` in the (stale) `TombStone`, as long as the caller matches that stored address: [3](#0-2) 

Ordinary ungated transfers (`transfer`, `transfer_call`, `transfer_raw`) go through `transfer_raw_inner`, which updates `ObjectCore.owner` but does **not** touch or clear any existing `TombStone`: [4](#0-3) 

Only the `TransferRef`/`LinearTransferRef` path (`transfer_with_ref`) explicitly clears a pre-existing `TombStone` "so we don't want the original owner to be able to reclaim by calling unburn later": [1](#0-0) 

This mirrors exactly the reported bug pattern: one mutation path (`vote_transanction`/here `transfer_with_ref`) resets the stale record, but the other legitimate mutation path (`_registerRecipient`/here `transfer`/`transfer_raw`) does not, leaving an authority-relevant field (`reviewsByStatus`/`original_owner`) pointing at a party that no longer has the corresponding relationship.

### Impact Explanation
Concretely:
1. Owner A calls `object::burn(A, obj)` while A owns `obj`. This creates `TombStone{ original_owner: A }`, but `obj` is still owned by A (burn is a "soft," metadata-only tombstone; ownership doesn't move).
2. A then transfers `obj` to B via the ordinary `object::transfer`/`transfer_call` entry function (a ungated, non-`TransferRef` transfer). `transfer_raw_inner` updates `owner` to B but does not clear the `TombStone`, so the stale `TombStone{ original_owner: A }` persists.
3. B — now the legitimate owner — is unaware the object still carries a tombstone. B cannot burn it themselves (`burn` aborts with `EOBJECT_ALREADY_BURNT` since a `TombStone` already exists), and if B later moves the object to `BURN_ADDRESS` (e.g., following whatever application-level "burn" workflow expects a two-step burn-then-send-to-burn-address), `unburn`'s second branch fires: since `object_core.owner == BURN_ADDRESS` and `original_owner_addr == A`, **A** (not B) can call `unburn` and have `transfer_raw_inner` send the object back to themselves — reclaiming ownership of an object that B, not A, actually held and burned.

This is a custody-grade issue: object ownership (and therefore any value or resources gated by ownership of that object, e.g. tokens/NFTs implemented as objects) can be redirected to a stale, unprivileged former owner rather than the party who actually controlled/burned it — a form of unauthorized owner reassignment/theft of object-held value.

### Likelihood Explanation
Exploitation requires: (a) an object owner to call `burn` and later transfer the object away via a plain (non-`TransferRef`) transfer rather than `transfer_with_ref`, and (b) the new owner to eventually move the object to `BURN_ADDRESS`. Both `burn` and ordinary `transfer` are public entry functions usable by any object owner without special permissions, so the preconditions are fully attacker/former-owner controlled once such a transfer sequence occurs. The likelihood in practice depends on how common it is for applications to combine `object::burn` with ordinary transfers (rather than exclusively with `TransferRef`-based flows) before eventually routing to `BURN_ADDRESS`; I was not able to fully confirm from the indexed code how/whether any first-party module (token/NFT burn helpers) actually chains `burn()` + plain `transfer()` + move-to-`BURN_ADDRESS`, so real-world triggering conditions in first-party flows remain uncertain from the available index.

### Recommendation
Clear (or invalidate) an existing `TombStone` whenever the object's owner changes through any path, not just `transfer_with_ref`. The most robust fix is to check/clear `TombStone` inside `transfer_raw_inner` (the single low-level function through which all owner reassignments funnel), analogous to resetting `reviewsByStatus` inside `_registerRecipient` for every status-changing path rather than only some of them.

### Proof of Concept
Conceptual PoC (Move test) exercising the described sequence:
```move
// A owns obj
object::burn(&A, obj);                       // TombStone{ original_owner: A } created, A still owner
object::transfer(&A, obj, address_of(&B));   // ownership -> B, TombStone NOT cleared (bug)
// B is unaware obj is tomb-stoned; B later "burns" via app-level flow that sends to BURN_ADDRESS
object::transfer_call(&B, object_address, BURN_ADDRESS);
// A can now reclaim an object they no longer legitimately own:
object::unburn(&A, obj);                     // succeeds: owner==BURN_ADDRESS && original_owner_addr==A
// obj is transferred back to A, even though B was the real owner/burner
```
I could not fully verify within index limits whether any in-repo module actually performs this `burn` + plain-`transfer` + `BURN_ADDRESS` sequence end-to-end (e.g., via `is_burnt`/burn UX helpers referenced in `primary_fungible_store.move`); confirming a concrete first-party trigger path would require a full checkout/Devin session to inspect all call sites of `object::burn`, `object::transfer`, and `BURN_ADDRESS` across the framework and token-objects packages.

    public fun transfer_with_ref(self: LinearTransferRef, to: address) {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));

        // Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later.
        if (exists<TombStone>(self.self)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(self.self);
        };

        let object = borrow_global_mut<ObjectCore>(self.self);
        assert!(
            object.owner == self.owner,
            error::permission_denied(ENOT_OBJECT_OWNER),
        );
        event::emit(
            Transfer {
                object: self.self,
                from: object.owner,
                to,
            },
        );
        object.owner = to;
    }

    /// This only works for objects directly owned and for simplicity does not apply to indirectly owned objects.

    /// Please use the test only [`object::burn_object_with_transfer`] for testing with previously burned objects.

        let object_addr = object.inner;

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
