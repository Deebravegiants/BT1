### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` built from the `shop-domain` and `topic` HTTP headers — fields that are never included in the signed material. This breaks the intended binding: `hmac == HMAC(body)` should imply `shop == the tenant that produced this body`, but the gem only proves the former.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic linkage to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the body) and then immediately trusts `request.shop` and `request.topic` (both header-derived) to build the metadata passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it to the `hmac` header — again, this only proves the body was produced with knowledge of `api_secret_key`, and says nothing about which shop's header value accompanies it: [4](#0-3) 

Because Shopify apps share a single `client_secret` across every installing merchant, any merchant who installs the app receives genuine webhook deliveries whose body+HMAC pair is valid under that shared secret. That merchant (an ordinary, unprivileged internet user with respect to other tenants of the app) can capture one such delivery and replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different, victim shop's domain. `HmacValidator.validate` still succeeds because the signable string (the body) is untouched, yet `Registry.process` reports the event as belonging to the victim shop to the handler.

The equality the library should enforce but does not:
`shop_bound_by_hmac == shop_used_for_tenant_routing`
What actually holds is only:
`hmac == HMAC(api_secret_key, body)`, independent of `shop`.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which merchant's tenant record to update (the documented and expected usage pattern for `ShopifyAPI::Webhooks::WebhookHandler#handle`), an attacker who is a legitimate installer of the app on their own store can inject webhook events that are attributed to an arbitrary victim shop domain. This is a cross-tenant data-integrity/confusion issue: attacker-controlled data (their own store's order/customer/etc. payload) is applied to another tenant's record purely because the unauthenticated header claims a different shop. This falls under the in-scope "Critical - cross-tenant access" impact category, since the tenant boundary (`shop`) that the gem is supposed to enforce as authenticated is not actually bound to the authenticated payload.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker must (a) be able to install the target app on a shop they control (a normal, low-privilege action any Shopify merchant/developer can perform) to obtain one genuine, HMAC-valid webhook delivery, and (b) be able to send arbitrary HTTP requests with forged headers directly to the app's public webhook endpoint (trivial for an internet-facing HTTP endpoint). No access to `api_secret_key`, access tokens, or the victim's credentials is required — only reuse of a legitimately obtained body+HMAC pair with a substituted header.

### Recommendation
Bind the shop identity to the authenticated content instead of trusting an unauthenticated header for tenant routing:
- Extend `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` (or a companion check) so the `shop-domain` (and ideally `topic`) header value is included in what's verified — e.g., derive/cross-check the shop from a source that Shopify's signature actually covers, or require the payload body itself to carry an authenticated shop identifier that is cross-checked against the header before trusting it.
- Alternatively/additionally, verify that the `shop-domain` header for the incoming request matches an actively registered session/shop for which this specific webhook subscription was created, rather than accepting any shop string that arrives with a validly-signed body.
- Document explicitly (and enforce in code, not just in comments) that `request.shop`/`WebhookMetadata#shop` must not be trusted for tenant-scoped side effects without an additional binding check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/test store (`attacker-shop.myshopify.com`), which is granted access using the app's shared `client_secret`.
2. Shopify delivers a genuine webhook to the app's endpoint for a topic such as `orders/create`, with a body `B` and header `x-shopify-hmac-sha256: HMAC(client_secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then re-sends it directly to the same public webhook endpoint, keeping body `B` and the HMAC header unchanged, but rewriting `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or changing `x-shopify-topic` if desired).
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(client_secret, B)` — matches, since `B` is untouched — and `Registry.process` proceeds to build `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, confirmed by: [5](#0-4) 
5. Any host application logic that uses `data.shop` to look up/update per-tenant state now attributes attacker-supplied content to the victim shop, without the app or the gem ever detecting the header was forged.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
