### Title
`deposit` can mint `u0` shares while pulling the full `amount` into vault `assets`, permanently freezing the depositor's principal - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`deposit` computes `inkind` via `convert-to-shares-preview` (rounds down) but, unlike `redeem`, never asserts `inkind > u0`. When the vault's exchange rate has `ta > ts` (assets-per-share > 1, which naturally occurs after any interest accrual), a small enough `amount` truncates to `0` shares. The transaction still succeeds: the full `amount` is pulled from the depositor and added to `assets`, but `ft-mint?` mints `0` zft, leaving the depositor with no shares and no way to reclaim the value.

### Finding Description
The intended round-trip identity for a deposit is:
`shares = convert-to-shares-preview(amount) = mul-div-down(amount, ts, ta)`, and the depositor must end up owning claims worth `~amount` (bounded rounding loss), i.e. `convert-to-assets-preview(shares) <= amount` **and** `shares > u0` whenever `amount > u0`.

In `deposit` (mainnet/contracts/vault/v0-vault-ststx.clar): [1](#0-0) 
the only output-related check is `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`. If the caller supplies `min-out = u0` (the default, permissible value), `inkind = u0` satisfies `0 >= 0` and the function proceeds to `receive-underlying`, `ft-mint? zft u0 recipient`, and `(var-set assets (+ current-assets amount))` — i.e. the vault takes the tokens and increases `assets` without minting any compensating shares.

Contrast this with `redeem`, which explicitly guards the symmetric case: [2](#0-1) 
`(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` — `redeem` refuses to burn shares for zero underlying, but `deposit` has no equivalent guard against minting zero shares for nonzero underlying. This is exactly the asymmetry the question identifies.

`convert-to-shares-preview` performs the floor division: [3](#0-2) 
`mul-div-down(amount, ts, ta) = floor(amount * ts / ta)`. Whenever `ta > ts` (which happens as soon as the vault has accrued any interest, since `total-assets-preview` grows while `total-supply-preview` does not for that accrual), there exists a nonzero `amount` (in the smallest units of `ststx`, 6 decimals) small enough that this floors to `0`.

Attacker flow:
1. Attacker (or even an unaware normal user) waits until `ta > ts` (naturally true after interest accrues, no privileged action needed).
2. Calls `deposit(amount, u0, attacker)` with `amount` chosen so `mul-div-down(amount, ts, ta) = 0`.
3. Deposit succeeds: `assets` increases by `amount`, `ft-mint? zft u0 attacker` mints nothing.
4. Attacker now holds `0` zft and cannot call `redeem` — any `redeem(u0, ...)` reverts immediately at `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` in `redeem`. There is no other withdrawal path for the lost `amount`.

Existing guards do not prevent this: `min-out` is attacker-supplied and defaults to `u0`; `ERR-SLIPPAGE` only fires if the attacker explicitly demands more shares than they'll get; there is no floor check independent of `min-out`, and no cap/pause state addresses this. Clarity's overflow checks are irrelevant since no arithmetic overflows.

### Impact Explanation
Each triggering deposit permanently transfers `amount` (the truncated dust amount, bounded by roughly `ceil(ta/ts) - 1` underlying units per call, small in absolute terms but nonzero and repeatable) from the depositor to the vault's `assets` pool with zero shares minted in return. Because zft supply is unchanged while `assets` (and thus `total-assets-preview`) increases, the value is absorbed pro-rata by all existing zft holders — a direct, permanent, unrecoverable loss of principal for whoever calls `deposit` this way, and a repeatable vector for anyone to grief themselves or be griefed by a poorly configured integrator/UI that always passes `min-out = u0`. This matches "permanent freezing of funds" (Critical), since the deposited principal cannot ever be recovered by the depositor once shares round to zero.

### Likelihood Explanation
- No privileged access needed; any Stacks principal can call `deposit` directly.
- Precondition `ta > ts` is a normal vault state reached passively once any interest has accrued (via `accrue`), not an artificial state the attacker must create maliciously.
- The attacker/victim must pass `min-out = u0` (or a bound low enough to still allow `0`), which is the SDK/most naive integration default.
- Capital cost is minimal — the attacker only loses the small `amount` (dust-sized deposit) that rounds to zero; repeatable at will since the exchange rate condition persists.

### Recommendation
Add a symmetric zero-check to `deposit`, mirroring `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other `deposit` assertions in `mainnet/contracts/vault/v0-vault-ststx.clar` (and the equivalent `v0-vault-ststxbtc.clar`), so that a deposit which would mint zero shares always reverts instead of silently swallowing the depositor's underlying tokens.

### Proof of Concept
Clarinet simnet test outline:
1. Deploy/initialize the vault; call `initialize` (mints `MINIMUM-LIQUIDITY` shares to `NULL-ADDRESS`, so `ts = ta = MINIMUM-LIQUIDITY` initially).
2. Simulate interest accrual (e.g., `system-borrow` + time advance + `accrue`, or directly manipulate state via available lending functions) until `total-assets-preview() = ta > total-supply-preview() = ts`, e.g. `ta = 2*ts`.
3. Record attacker's `UNDERLYING` balance `B0` and `(ft-get-balance zft attacker)` (`= u0`).
4. Call `deposit(u1, u0, attacker)` (amount = `u1`, chosen so `mul-div-down(1, ts, ta) = 0` given `ta >= 2*ts`).
5. Assert:
   - `(is-ok result)` — the call succeeds (does NOT revert).
   - `(ft-get-balance zft attacker) == u0` — no shares minted.
   - `(- B0 (get-balance UNDERLYING attacker)) == u1` — the underlying was pulled from attacker.
   - `(get-assets) == old-assets + u1` — vault `assets` increased with no offsetting share issuance.
6. Attempt `redeem(u0, u0, attacker)` and assert it returns `(err u802009)` (`ERR-AMOUNT-ZERO`), proving there is no recovery path — the `u1` is permanently lost to the attacker and pro-rata gifted to remaining zft holders.

```text
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

```text
(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    (states (var-get pause-states))
    (u (try! (accrue)))
    (account contract-caller)
    (current-assets (var-get assets))
    (balance (get-balance-internal account))
    (balance-check (asserts! (>= balance amount) ERR-INSUFFICIENT-BALANCE))
    (available-assets (get-available-assets))
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  (asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)
```
