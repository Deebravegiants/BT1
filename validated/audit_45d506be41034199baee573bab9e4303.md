## Title
Webhook `shop` (and `topic`/`api_version`) values are trusted from unauthenticated headers while the HMAC only covers the raw body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, but the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are read from unauthenticated HTTP headers that are never included in the signed bytes. Any party who can obtain one validly-signed webhook body/HMAC pair (e.g. by installing the app on their own store and receiving a legitimate webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header to point at a different (victim) shop, and the library will report the request as validly authenticated for the attacker-chosen shop.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`. [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers that are not part of the signed bytes at all: [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then trusts `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the app's handler, without any additional binding between the signed body and the shop/topic headers: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the library implicitly claims is `hmac == HMAC(secret, raw_body)` ⟺ "this webhook belongs to `shop` header", but the actual signed scope is `raw_body` alone, so `shop` (and `topic`) can be swapped freely on any request that carries a validly-signed body.

### Impact Explanation
An app's `api_secret_key` is shared across every shop that has the app installed (Shopify does not use a per-shop signing secret for webhooks in this library's model — the same `Context.api_secret_key` validates all shops' webhooks). Consequently, a user who installs the app on their own store (an ordinary, unprivileged action requiring no special credentials) receives genuinely-signed webhooks for their own shop, whose body+HMAC pair is valid under the app's shared secret. Because `shop` is not part of the signed bytes, that same body+HMAC pair can be replayed with the `X-Shopify-Shop-Domain` header changed to a victim shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. If the host application uses `data.shop` to select the tenant's session/store record (the documented and expected pattern), this results in cross-tenant data being written or processed under another merchant's identity — a cross-tenant access violation.

### Likelihood Explanation
Likelihood is high for any app that: (1) allows self-service installation (i.e., the attacker can become a legitimate, if minor, tenant), and (2) exposes a single shared webhook endpoint keyed by the `shop` header, which is the standard integration pattern documented for this library. No access to `api_secret_key`, no TLS interception, and no privileged account is required — only ordinary installation of the app by the attacker on their own shop.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the signed payload verification, e.g., by including them in `to_signable_string`, or by requiring the host application to independently verify that the `shop` header belongs to a shop for which a session/webhook was actually registered before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` is unauthenticated header data and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (ordinary self-service install).
2. Attacker triggers/receives a legitimate webhook for their shop; captures the exact raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `H == HMAC(api_secret_key, B)`).
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body is unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`. [5](#0-4) 
5. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, and any app logic that keys off `data.shop` now processes/stores the attacker's payload under the victim's tenant. [4](#0-3)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
