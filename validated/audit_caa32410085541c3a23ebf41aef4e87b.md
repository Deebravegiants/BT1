### Title
Error in Chainlink oracle call not handled, leading to potential protocol instability - ([Project: listadao] [File: lista-dao-contracts/contracts/oracle/ResilientOracle.sol])

### Summary
The `listadao` project's `ResilientOracle.sol` contract, specifically the `getPriceFromOracle` function, does not handle potential errors from Chainlink's `latestRoundData()` call. While it uses a `try-catch` block, it only returns `INVALID_PRICE` on any error, without distinguishing between a temporary oracle outage and a negative price. This can lead to the protocol using a stale or manipulated price, potentially causing financial loss or protocol instability.

### Finding Description
The `getPriceFromOracle` function in `ResilientOracle.sol` attempts to fetch price data from a Chainlink oracle using `latestRoundData()` . Although a `try-catch` block is present, it broadly catches all errors and returns `INVALID_PRICE` . This means that if the Chainlink oracle is offline or experiences an error, the function will return `INVALID_PRICE` (which is 0) , potentially leading to incorrect price reporting or protocol halts if not handled appropriately by the calling functions. More critically, the function also lacks a positivity check for the `answer` received from the oracle, meaning a negative price from the oracle would be cast to a large `uint256` value, leading to an astronomically high price .

### Impact Explanation
If the Chainlink oracle experiences an outage or returns an error, the `getPriceFromOracle` function will return `INVALID_PRICE` (0) . This could lead to rebalancing and minting functionalities being broken, as the protocol would be operating with an invalid price, potentially causing the USSD to lose its peg, similar to the impact described in the external report. Furthermore, the lack of a positivity check on the `int256 answer` from Chainlink means a negative price would be interpreted as a very large positive `uint256` value . In configurations where only a main oracle is used (`!pivotEnabled`), this inflated price would be returned without further validation, leading to overvalued collateral and potential protocol drain .

### Likelihood Explanation
The likelihood of this vulnerability is medium. While Chainlink oracles are generally robust, temporary outages or unexpected errors can occur. The external report highlights that `priceFeed.latestRoundData()` can revert for various reasons, including the oracle being taken offline. The `listadao` project's `ResilientOracle` contract explicitly demonstrates this vulnerability by not properly handling the `int256` to `uint256` cast for negative values and by broadly catching all errors without specific handling . The fact that a single-oracle configuration is explicitly permitted increases the likelihood of this impact .

### Recommendation
Implement specific error handling within the `try-catch` block to differentiate between temporary oracle issues and other errors. Additionally, a positivity check should be added for the `int256 answer` received from the Chainlink oracle before casting it to `uint256` . This would prevent negative prices from being misinterpreted as large positive values.

### Proof of Concept
The `getPriceFromOracle` function in `lista-dao-contracts/contracts/oracle/ResilientOracle.sol` demonstrates the issue :

```solidity
function getPriceFromOracle(address oracle, uint256 tolerance) external view returns (uint256) {
    try AggregatorV3Interface(oracle).latestRoundData() returns (
        uint80, int256 answer, uint256, uint256 updatedAt, uint80
    ) {
        if (tolerance != 0 && block.timestamp - updatedAt > tolerance) return INVALID_PRICE;
        return uint256(answer);                      // <-- unchecked int256 -> uint256
    } catch {
        return INVALID_PRICE;
    }
}
```
If `AggregatorV3Interface(oracle).latestRoundData()` reverts, the `catch` block is executed, returning `INVALID_PRICE` (0). If `answer` is negative, `uint256(answer)` will result in a very large number. This large number is then used without further validation if `pivotEnabled` is false :

```solidity
// _getMainOraclePrice
try this.getPriceFromOracle(mainOracle, tokenConfigs[asset].timeDeltaTolerance) returns (uint256 mainOraclePrice) {
    if (!pivotEnabled) {
        return (mainOraclePrice, true);          // <-- "validated = true" with NO comparison
    }
    ...
}
```
This allows a negative oracle price to be treated as a valid, astronomically high price, leading to potential protocol drain .
