### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (and `topic`, `webhook_id`, `api_version`) values are taken directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body HMAC and then dispatches to the registered handler using the unauthenticated `shop` value read from headers. This breaks the identity binding `hmac_signed_bytes == bytes_the_handler_trusts_as_the_tenant_identifier`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then immediately trusts `request.shop` (and `request.topic`) as the tenant identity when constructing the metadata passed to the app's handler: [3](#0-2) 

Because the `Utils::HmacValidator.validate` call only signs/verifies `to_signable_string` (the raw body) against `Context.api_secret_key`: [4](#0-3) 

...an attacker who has legitimately received one valid webhook delivery for their own shop (i.e., installed the app on shop A, which is a completely unprivileged action available to any internet user who can create a Shopify dev/trial store) possesses a raw body + valid HMAC pair signed with the app's secret. Because the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not part of the signed content, the attacker can resend the exact same body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header (or `x-shopify-shop-domain`) with a victim shop's domain. `Registry.process` will pass HMAC validation (since it only checks the body) and will invoke the handler with `WebhookMetadata` claiming the event originated from the victim shop.

This satisfies the rule's identity-binding pattern directly: *"a field acted on but not covered by the HMAC"* — here, `shop` is the field acted upon (used to attribute/act on the event) but is excluded from the signed bytes.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as provided by this gem) to determine which merchant/tenant a webhook event pertains to — e.g., to update that shop's data, decrement inventory, mark an order fulfilled, or trigger `shop/redact`/`customers/redact`-adjacent data-handling logic for a shop the attacker does not own — an attacker can trigger tenant-scoped side effects attributed to a shop they do not control, using only a webhook body they legitimately received from their own installation. This is a cross-tenant/spoofing vector directly enabled by a gap in this gem's authenticity binding, meeting the "cross-tenant access" bar in the rules since the shop identity is exactly the boundary the HMAC is supposed to protect but doesn't cover.

### Likelihood Explanation
Likelihood is dependent on shared/generic webhook payload shapes across shops (e.g., `app/uninstalled`, `shop/update`, or any webhook topic whose payload is not shop-specific in content but only via header) so that a replayed body remains semantically valid/exploitable for a different shop. Any developer using an app can become the "attacker" by installing the app and capturing legitimate webhook deliveries, meeting the unprivileged-internet-user bar. However, exploitation requires the host application to trust `WebhookMetadata#shop` from this gem as the sole tenant-identity signal without any additional server-side verification (e.g., checking that shop exists in its own session store) — which is exactly how the gem's own documented `Registry.process` API is intended to be consumed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered signable string, or otherwise cryptographically bind the header-derived identity fields to the signed body before trusting them in `WebhookMetadata`. At minimum, document loudly that `shop` from `WebhookMetadata` is not authenticated by the body HMAC and must be independently verified by the host application against its own session/shop registry before use.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `app/uninstalled`) and capture the raw body and the valid `x-shopify-hmac-sha256` value computed by Shopify with the app's `client_secret`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and `x-shopify-topic` to a topic registered by the app).
3. `ShopifyAPI::Webhooks::Request#hmac` decodes the header, `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only, and it matches (since the body is unmodified) — `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., the handler executes as if the event came from the victim shop.
