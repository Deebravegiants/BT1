### Title
Webhook shop/topic identity spoofing via unsigned headers — cross-tenant webhook delivery ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` and `topic` values that `Registry.process` uses to route and label the webhook are read from unauthenticated HTTP headers that are never covered by the signature.

### Finding Description
`Request#to_signable_string` returns exclusively `@raw_body`: [1](#0-0) 

But `topic` and `shop` — the fields that determine *which handler runs* and *which merchant the data is attributed to* — are pulled straight from HTTP headers, entirely outside that signed string: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the body) against the `hmac` header value: [3](#0-2) 

`Registry.process` performs the HMAC check and then unconditionally trusts `request.shop` and `request.topic` for dispatch and for constructing the metadata handed to the app's handler: [4](#0-3) 

Shopify apps share one static `client_secret`/`api_secret_key` across every merchant that installs them — it is not per-shop. Consequently, any unprivileged actor who installs the app on their own attacker-controlled store legitimately receives webhook requests with a valid HMAC signature computed from that shared secret and the JSON body. Because the signature never covers `X-Shopify-Shop-Domain` or `X-Shopify-Topic`, the attacker can replay that same body/HMAC pair to the app's webhook endpoint while swapping those two headers to name a different (victim) shop and/or a different topic. `HmacValidator.validate` will still return `true` because it only re-derives the HMAC from the untouched body, so `Registry.process` accepts the forged request and calls the host handler with `WebhookMetadata` claiming the victim's `shop` (and/or the swapped `topic`), even though the payload actually originated from — and was only ever signed for — the attacker's own shop.

This breaks the intended identity binding: `hmac ⟺ (shop, topic, body)` — the gem enforces `hmac ⟺ body` only, letting `shop` and `topic` be forged independently of the signature that is supposed to authenticate the webhook's origin.

### Impact Explanation
This is a High-severity issue: it lets an unprivileged app-installer forge the apparent tenant (`shop`) and/or event type (`topic`) of a cryptographically "valid" webhook, causing the app's own webhook-processing pipeline to attribute attacker-supplied data to another merchant's tenant record, or to route attacker data into a handler meant for a different topic (e.g., turning a benign event into a privileged one like `app/uninstalled` handling, or injecting fabricated `orders/create` data under a victim's shop identity). Any host application that trusts `WebhookMetadata#shop`/`#topic` as the origin of record — which is exactly what this gem documents and returns — inherits a cross-tenant data-integrity break.

### Likelihood Explanation
Any actor can freely create a development/trial store and install the target app, which is the only prerequisite (no special access, no leaked secrets, no privileged account needed). Capturing one's own legitimately signed webhook and replaying it with modified headers is trivial and entirely within the reach of an "unprivileged internet user."

### Recommendation
Bind `shop` and `topic` into the signed material, or otherwise cryptographically tie them to the body before trusting them for dispatch/attribution — e.g., include the `shop-domain` and `topic` header values in `to_signable_string` (matching Shopify's actual signing scheme if it covers them), or independently verify the `shop` domain against the session/shop the webhook was registered for before invoking the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real event so Shopify sends a legitimately HMAC-signed webhook to the app's endpoint, e.g. body `{"id":1}"` with headers `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker captures this request and replays it to the same endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` to another registered topic), leaving the body and `X-Shopify-Hmac-Sha256` untouched.
4. `Utils::HmacValidator.validate` recomputes the HMAC solely from the unchanged body and matches it, so `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)`, i.e., attacker-controlled data attributed to the victim shop.         def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
