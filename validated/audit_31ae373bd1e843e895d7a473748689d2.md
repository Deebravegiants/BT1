I have sufficient evidence now to construct the analog.### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing tenant impersonation in `Registry.process` - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request by checking only the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` and `topic` HTTP headers to route and label the payload via `WebhookMetadata`. Because the HMAC binds only the body bytes and not the header bytes, an attacker who legitimately receives one valid, signed webhook can replay it to the same endpoint with a forged `shop-domain`/`topic` header while the signature still validates, causing the host application to process the payload as belonging to a different shop/topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` and `topic` accessors, however, are derived purely from request headers that are not part of the signed material: [2](#0-1) 

`Registry.process` uses `Utils::HmacValidator.validate(request)` — which calls `to_signable_string` (body only) — as the sole authenticity check, then immediately trusts `request.topic` and `request.shop` to select the handler and populate `WebhookMetadata`, which is what the host application receives and typically uses to identify the tenant (shop) the event belongs to: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` computes and compares only `verifiable_query.to_signable_string` against the HMAC — it never incorporates `shop` or `topic`: [5](#0-4) 

The equality this breaks: **bytes verified (raw body signed with `api_secret_key`) ≠ bytes/identity parsed and trusted (`shop-domain`/`topic` headers)**. The `api_secret_key` is a single, app-wide secret shared across every shop that has installed the app (it is not shop-specific), so a genuine HMAC produced for a webhook delivered to Shop A is cryptographically indistinguishable from one that would be produced for Shop B carrying the same body — the signature carries no shop-binding information at all.

### Impact Explanation
Any unprivileged actor who is a merchant/owner of a real installed shop (or who otherwise obtains one legitimate `(raw_body, hmac)` pair, e.g. via their own store's webhook log or a captured request) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) for a different, victim shop. `Registry.process` will accept the request as valid (HMAC checks out) and hand `WebhookMetadata` with the attacker-chosen `shop`/`topic` to the host application's handler. Applications built on this gem generally use `data.shop` to look up/update the corresponding tenant record (e.g., to mark orders paid, update inventory, or trigger business logic), so this allows cross-tenant data injection/corruption — the handler executes tenant-specific side effects attributed to a shop the attacker does not own. This matches the Critical "cross-tenant access" impact category, since the tenant identity binding is broken.

### Likelihood Explanation
The precondition — obtaining one legitimately signed webhook body/HMAC pair — is trivial: any merchant with the app installed on their own store receives webhooks and can inspect the raw POST body and headers Shopify sends. Crafting the replayed request with modified `shop-domain`/`topic` headers requires only basic HTTP tooling; no access to `api_secret_key`, access tokens, or any privileged account is needed. The vulnerability is entirely within this gem's own trust boundary (`Registry.process`/`HmacValidator`), not a host-application misuse issue.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header values into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the shop identity to the signature (e.g., verify the header values against a known/registered shop-token pairing before dispatching to a handler), rather than trusting them as raw, unauthenticated headers in `Registry.process` and `Webhooks::Request`.

### Proof of Concept
1. Attacker installs the app on their own store (`attacker-shop.myshopify.com`) and receives a legitimate webhook: raw body `B`, with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — validation succeeds because `B` and `H` are unchanged (confirmed by `Request#to_signable_string` returning only `@raw_body`, `lib/shopify_api/webhooks/request.rb:35-38`, and `HmacValidator#validate_signature`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` dispatches to the registered handler for the (forged) topic with `WebhookMetadata.new(topic: forged_topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host application to process attacker-supplied event data as if it originated from `victim-shop.myshopify.com`.
