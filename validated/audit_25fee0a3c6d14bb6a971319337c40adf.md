### Title
`recapitalize` refunds the declared amount even when the payer's deposit never arrived, draining pool custody - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
`Pool::recapitalize` is a permissionless entrypoint (controller::recapitalize forwards to it; `scripts/permissionless_entrypoints.txt` line 73 declares it caller-auth). It is meant to let anyone donate to cover a market's backing shortfall, applying the measured receipt and refunding the excess. The refund leg pays out the *declared* `amount`, not the *measured received* amount, so a caller can pass a large `amount` while transferring nothing and receive a refund of tokens that were never deposited. The pool's own regression test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` demonstrates this end-to-end: custody drains to zero while the `cash` book is untouched. The Linux analog (accessing registers after the device is suspended / doing work after `dwc3_core_exit` tore the device down) maps onto using pool custody that was never actually received — the settlement precondition is assumed rather than measured before the payout leg runs.

### Finding Description
The recapitalize flow (1) measures the receipt, (2) credits `cash` only up to the shortfall, and (3) refunds the payer. Step (3) uses the declared `amount` minus what was applied, rather than the actual balance delta received in step (1). With `amount = custody` and a zero-value receipt, the refund equals the full declared amount and leaves the pool holding zero tokens while `cash` still reports all prior deposits as backed. Per the documented test at `contracts/pool/tests/flows.rs:3408-3476`, `require_reserves` reads the book — not the balance — so subsequent supplier withdrawals pass the pool's own liquidity and solvency guards and then revert inside the SAC transfer with `BalanceError = 10`. This is a checks-effects-interactions inversion analogous to the kernel bug: a state-changing action (register access / custody payout) is performed after the precondition that made it valid (device powered / tokens received) is no longer or never was true.

### Impact Explanation
Theft of user funds followed by freezing of remaining funds. An unprivileged attacker calls `recapitalize(hub_asset, payer, pool_balance)` with a payer they control and transfers nothing; the contract pays `pool_balance` worth of tokens to `payer`. Every legitimate supplier/borrower exit thereafter fails in the token transfer — suppliers' claims are recorded but unpayable, a permanent loss for early victims and a temporary/permanent freeze for everyone else.

### Likelihood Explanation
`controller::recapitalize` requires only `payer.require_auth()` on a caller-supplied address — no owner, role, or governance gate (permissionless list, caller-auth, INV-AUTH-03). No timing, price manipulation, or multi-step setup is needed; any EOA can trigger it on any live market with positive custody.

### Recommendation
Refund only the measured excess: compute `refund = measured_receipt − applied` and transfer that, never `declared_amount − applied`. Assert `measured_receipt ≥ applied` and make the refund a no-op when the receipt is zero. Alternatively, pull the donation via `transfer` into the pool first and measure `balance_after − balance_before` before any outbound leg.

### Proof of Concept
See `contracts/pool/tests/flows.rs:3408-3476`: mint `10_000_000_000` to the pool, call `recapitalize(&hub, &payer, &custody)` — `token.balance(&pool)` becomes `0`, `payer` holds the full declared amount, `state.cash` is unchanged, and `try_withdraw` then fails inside the SAC transfer with `BalanceError = 10` rather than any pool guard.
