### Title
Webhook shop-domain and topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while `ShopifyAPI::Webhooks::Registry.process` trusts the unsigned `shop-domain` and `topic` headers to build the `WebhookMetadata` passed to app handlers. This breaks the identity binding `shop authenticated == shop acted upon`, letting an attacker who legitimately receives one signed webhook (e.g. for their own shop) replay it against the app's webhook endpoint while claiming to be a different ("victim") shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers, none of which participate in the signature: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` accepts any request whose body HMAC validates, then forwards the unauthenticated `shop` (and `topic`) straight to the app's handler as trusted metadata: [4](#0-3) 

This is precisely the documented, expected usage pattern — the gem's own docs tell app authors to key their processing on `data.shop`: [5](#0-4) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is a single value shared across *every* shop that installs the app, any unprivileged merchant who installs the app on their own store receives genuinely-signed webhooks for their own shop. That merchant can capture the raw body + valid `x-shopify-hmac-sha256` value from one of their own webhooks, then POST that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while setting an arbitrary `x-shopify-shop-domain` header (e.g. a victim's shop domain) and/or arbitrary `x-shopify-topic`. `HmacValidator.validate` still succeeds (it only checks the body), so `Registry.process` looks up a handler for the attacker-chosen topic and calls it with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain.

This equality that should hold is:
`shop the HMAC authenticates == shop the handler acts upon`
but the gem allows:
`shop the HMAC authenticates (attacker's own shop, via body) != shop passed to handler.handle (arbitrary, via unsigned header)`

### Impact Explanation
Any app built on this gem that uses `data.shop` (as documented) to key persistence, cache invalidation, entitlement checks, or trigger tenant-scoped side effects can be tricked into attributing attacker-supplied webhook data to a victim shop it does not control — a cross-tenant boundary violation achievable by an unprivileged internet user who only needs a free/trial installation of the target app on their own store. No `api_secret_key`, access token, or other privileged credential is required from the attacker; they only need the ability to receive one legitimate webhook for a shop they control.

### Likelihood Explanation
Likelihood is high in any multi-tenant Shopify app: installing the app on an attacker-controlled shop is trivial (self-serve app install), capturing a webhook delivery is trivial (any documented topic, e.g. `app/uninstalled` or a custom one the merchant can trigger), and forging the replay request is a simple HTTP POST with a modified header, since neither `shop-domain` nor `topic` is bound to the signature.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them in `WebhookMetadata`. At minimum, document loudly that `data.shop`/`data.topic` are NOT covered by the HMAC and must not be used for authorization or tenant-keyed writes without independent verification (e.g., cross-checking against a shop that is known to have this exact webhook subscription registered).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a legitimate webhook, capturing the raw body `B` and the valid header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's shared `client_secret`).
2. Attacker sends a forged HTTP request directly to the app's public webhook endpoint with:
   - body = `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs the body)
   - `x-shopify-shop-domain: victim.myshopify.com` (attacker-chosen)
   - `x-shopify-topic:` any topic the app has a handler for.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only the body is checked: [6](#0-5) 
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes/persists attacker-controlled data as if it originated from the victim tenant.

          received_signature = verifiable_query.hmac
