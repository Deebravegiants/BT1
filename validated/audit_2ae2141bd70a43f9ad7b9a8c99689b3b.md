### Title
Webhook shop identity spoofing via HMAC that only binds the request body, not the `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity with an HMAC that is computed exclusively over the raw request body, while the shop identity that is handed to application handlers is read from an unauthenticated, unsigned header. This breaks the binding: `shop used by handler == shop covered by HMAC`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body, using the app's shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates only that overall HMAC and then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` that is passed to the app's handler as the authenticated tenant identity: [4](#0-3) 

Because the same `api_secret_key` is shared across **every shop that has installed the app** (it is the app's client secret, not a per-shop secret), and the HMAC signs only the body bytes, any two webhook deliveries with identical body content will carry an identical, valid signature regardless of which shop header is attached. This means the `shop-domain` header — the very field the handler uses to determine "which tenant does this event belong to" — is not part of what the HMAC authenticates. The library treats a validated body as proof of the header's shop value, which is not something the signature actually establishes.

This matches the flagged binding-break pattern: *a field acted on (the shop used to route/attribute the webhook event) but not covered by the HMAC (which signs only the body).*

### Impact Explanation
An app that trusts `WebhookMetadata#shop` (as the documented usage pattern instructs — `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`) to select which merchant's data the payload applies to can be made to process a validly-HMAC'd payload under an attacker-chosen shop identity. Any party able to relay (or induce delivery of) a body+signature pair from one installation while substituting the `shop-domain` header causes cross-tenant data confusion in the receiving app — e.g., an order/fulfillment/customer webhook event could be attributed to a victim shop it did not originate from, since the library provides no mechanism to bind the two together and no documentation warns that the shop header is unauthenticated. This falls under cross-tenant access/data confusion.

### Likelihood Explanation
Exploitation requires the attacker to control or observe a body+HMAC pair produced by Shopify (for example, from their own store's installation of the app, using a self-crafted resource payload) and to be able to relay it to the app's public webhook endpoint with a modified shop header — something an unprivileged internet user who can install the app on a store they control can accomplish without needing the app's `client_secret`, an access token, or any victim credentials. The likelihood is moderate: it depends on the receiving application accepting the identity claimed by the header (which is exactly what `Registry.process`/`WebhookMetadata` encourages), and on the attacker being able to interpose between Shopify and the app's endpoint (e.g. via a proxy/relay they control) to swap the header while preserving the body bytes.

### Recommendation
Bind the shop identity into the verified material instead of trusting an unsigned header:
- Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or
- Cross-check the header-derived shop against an application-maintained allowlist of shops known to have this webhook subscription/topic combination before constructing `WebhookMetadata`, and document clearly that `request.shop` is not itself authenticated by the HMAC.

### Proof of Concept
1. App installs on attacker's own shop `attacker.myshopify.com`; Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(api_secret_key, B)`.
2. Attacker intercepts/relays this request to the app's public webhook endpoint but rewrites the header to `X-Shopify-Shop-Domain: victim.myshopify.com`, leaving body `B` and `X-Shopify-Hmac-Sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and finds it equals `H` — validation passes at [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the event never originated from that shop, because `shop` in `Request` (`lib/shopify_api/webhooks/request.rb:20-23`) is never part of `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`).
