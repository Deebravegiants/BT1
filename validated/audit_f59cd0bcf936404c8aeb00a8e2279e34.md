Confirmed: `WebhookMetadata.shop` (and `topic`, `webhook_id`, `api_version`) are populated directly from unauthenticated HTTP headers, while `Utils::HmacValidator.validate(request)` only verifies `request.to_signable_string`, which returns `@raw_body` alone.

### Title
Webhook shop/topic identity spoofing via headers not covered by HMAC - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are covered by that signature — to build the `WebhookMetadata` passed to the host app's handler.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC only against `request.to_signable_string`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from headers:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

The equality the gem implicitly claims to enforce is: *`shop` field the handler receives == the shop that produced/signed this webhook*. In reality, the HMAC only proves *body integrity*, not *header integrity* — the same mismatch pattern as `CoiinMinter.sol`'s `mint` requiring one thing (`_amount` bounds) while `lastMintAmount` accounting silently drifts from what was actually checked. Here, the field the app *acts on* (`request.shop`, `request.topic`) is not the field the HMAC *covers* (`@raw_body`).

Since any merchant can install the app on their own store and thereby legitimately receive genuine, correctly-HMAC-signed webhooks for that store, they can capture such a webhook and replay it to the app's public webhook endpoint after rewriting only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a different, victim shop. `Utils::HmacValidator.validate` still succeeds (it only checks the untouched body), and `Registry.process` hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the shop-identity binding relied on by any host application built on this gem: a handler that persists webhook payloads keyed by `data.shop` (e.g., to sync orders/customers/inventory per tenant) can be made to write attacker-controlled body content under a victim shop's identity — cross-tenant data injection/confusion using data that was never actually sent by, or intended for, the victim shop.

### Likelihood Explanation
Requires only that the attacker be able to install/operate the app on a shop they control (a normal, low-privilege capability for any Shopify merchant using a public app) and be able to send an HTTP request to the app's public webhook endpoint with a modified header — no access to the app's `client_secret`, access tokens, or the victim's credentials is needed.

### Recommendation
Do not trust `shop`, `topic`, or `webhook_id` header values as authenticated identity for routing/attribution unless they are also covered by the signature, or unless the caller independently correlates the header shop against a known, previously-authorized shop record (e.g., verifying the shop has an active session with a matching webhook subscription id fetched via API) before processing. At minimum, document this gap prominently since `Registry.process` currently presents `request.shop` as if it were as trustworthy as the HMAC-checked body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving a POST with a valid `X-Shopify-Hmac-Sha256` for the raw body and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the identical body/HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body`. [4](#0-3) 
4. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled>)` and processes/persists it as if it were genuine data from the victim shop.
