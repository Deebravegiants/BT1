### Title
Passphrase cache `maxTtl` hard cap bypass via repeated `restartAutoLockTimer` calls keeps stale unlock material alive indefinitely - (File: features/application/src/modules/passphrase-cache.ts)

### Summary
`PassphraseCache.get()` in `features/application/src/modules/passphrase-cache.ts` enforces the configured `maxTtl` cap only via the `addedAt` branch, but once `inactiveAt` is set the check permanently switches to `inactiveAt + ttl > Date.now()` and never re-validates against `addedAt + maxTtl`. Because `scheduleClear()`/`restartAutoLockTimer` can be invoked repeatedly and unconditionally (no lock/auth gate) whenever a passphrase is already cached, an attacker with access to the app's public API surface can keep resetting `inactiveAt` forever, causing the cached passphrase to remain valid far beyond the configured `maxTtl` hard cap.

### Finding Description
`get()` decides whether to return the cached passphrase using two mutually exclusive branches: [1](#0-0) 

Once any activity has occurred (`inactiveAt` set via `scheduleClear()`), the `addedAt + this.#maxTtl` bound is bypassed entirely — subsequent checks rely solely on `inactiveAt + ttl`, which is refreshed every time `scheduleClear()` runs: [2](#0-1) 

`scheduleClear()` is reachable from the public application API through `restartAutoLockTimer`, which has no lock, auth, or applicationStarted gate of its own: [3](#0-2) 

This method is exposed directly on the headless/RPC `applicationApi`/SDK surface (`exodus.application.restartAutoLockTimer()`), reachable by any caller of the wallet's API/dapp bridge: [4](#0-3) [5](#0-4) 

Since the only precondition inside `scheduleClear()` is that a passphrase is currently cached (true any time `cachePassphrase` is enabled and the user has unlocked at least once), repeatedly calling `restartAutoLockTimer()` before each `ttl` window expires resets `inactiveAt` indefinitely, so the passphrase never expires via the intended `maxTtl` bound. Later, when the wallet is locked/killed and restarted, `Application#start` calls `#autoUnlock`, which reads the cache and silently unlocks the wallet with no PIN/biometric prompt as long as `inactiveAt + ttl > now`: [6](#0-5) 

This defeats the `maxTtl` invariant — the fallback (cache-based) auto-unlock path is supposed to be strictly bounded by `config.maxTtl`, but that bound can be nullified as long as the attacker (or any code with API access, e.g. a malicious dapp/website integrated via the SDK) keeps invoking the unauthenticated `restartAutoLockTimer` endpoint.

### Impact Explanation
This allows old unlocked/session material (the plaintext passphrase) to survive far past the operator-configured maximum caching window, silently re-unlocking the wallet (and thus the keychain/seed) without any PIN/biometric check on subsequent app starts. This matches "Private key or private key generation leakage leading to unauthorized access to user funds" because the auto-unlock path directly feeds the cached passphrase into `wallet.unlock({ passphrase })`, restoring full private-key/seed access to whoever controls the device or app process at that later point, well beyond the intended session bound.

### Likelihood Explanation
Preconditions: `cachePassphrase` feature must be enabled (config-dependent) and the user must have unlocked at least once with a passphrase so a value exists in the cache. Given those, exploitation only requires repeatedly calling the public, unauthenticated `restartAutoLockTimer` API (or any hook that triggers `passphraseCache.scheduleClear()`) before each `ttl` window lapses — no credentials or privileged state needed. This is straightforward and repeatable via ordinary dapp/API/RPC access.

### Recommendation
In `PassphraseCache.get()`, always additionally enforce `addedAt + this.#maxTtl > Date.now()` regardless of whether `inactiveAt` is set, so the hard cap cannot be bypassed by activity-based renewal. Additionally, gate `scheduleClear`/`restartAutoLockTimer` behind the same "wallet unlocked" state checks used elsewhere (e.g., require `!wallet.isLocked()`) so it cannot be invoked to keep a stale cache alive indefinitely.

### Proof of Concept
Unit test for `features/application/src/modules/passphrase-cache.ts`:
1. Construct `PassphraseCache` with `config.maxTtl = 1` (1 minute) and a fake `autoLockTimerAtom` returning `ttl = 1 minute`.
2. Call `set('secret')`.
3. Repeatedly (every 30s of mocked time, before `ttl` elapses) call `scheduleClear()` for, say, 5 minutes of mocked elapsed time (well past `maxTtl`).
4. Call `get()` and assert it still returns `'secret'` — demonstrating the passphrase survives beyond `maxTtl`, violating the intended hard cap.
5. Integration variant: with `Application`, call `unlock({ passphrase })` (caches passphrase), then loop calling `application.restartAutoLockTimer()` at intervals under `ttl` for a duration exceeding `config.maxTtl`, then simulate app restart (`application.start()`); assert `wallet.isLocked()` is `false` without any PIN/passphrase provided at restart.
