## Finding

### Title
Webhook `shop`/`topic`/`webhook-id`/`api-version` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), routing key (`topic`), and other metadata directly from HTTP headers, but `Registry.process` only HMAC-validates the raw request **body**. Any attacker who can obtain one genuinely-signed webhook body for their own shop (trivial: install the app on a free dev/trial store they control) can replay that exact body to the app's webhook endpoint while substituting arbitrary values for `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version`. The HMAC still validates because it only ever covered the body bytes, letting the attacker impersonate any other shop/topic to the host application's webhook handler.

### Finding Description
The equality that should hold is: `shop header used to identify the tenant == shop bound by the HMAC signature`. In this gem it does not.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the identity-bearing fields (`shop`, `topic`, `webhook_id`, `api_version`) come straight from attacker-suppliable headers with no cryptographic binding to them: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then trusts `request.topic` and `request.shop` to route and to build `WebhookMetadata` that is handed to the host application's handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, confirming the HMAC only ever covers what `to_signable_string` returns (the body for webhooks), never the headers: [4](#0-3) 

Because `Context.api_secret_key` is the single app-wide client secret (not a per-shop secret), any store that has ever installed the app can generate a body+HMAC pair that is valid for *any* shop identity claim, since the shop identity is never part of what's signed. This is exactly the bug-class pattern described in the report: "a field acted on but not covered by the HMAC."

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce for webhook delivery. A host application that (reasonably, per this gem's documented API) trusts `WebhookMetadata#shop` as the authenticated tenant for the delivered payload can be made to apply another merchant's webhook body under a different `shop` value, or to dispatch a body under an arbitrary `topic` it wasn't actually emitted for. This is a cross-tenant confusion issue: an unprivileged owner of Shop A can cause the app to process/attribute webhook data as if it came from Shop B, without ever needing Shop B's or the app's `client_secret`.

### Likelihood Explanation
High likelihood of exploitability given: (1) any unprivileged internet user can install the target app on a shop they control and receive genuinely-signed webhook deliveries; (2) capturing and replaying an HTTP POST with modified headers is trivial; (3) no secret material beyond what the attacker already legitimately possesses (their own webhook deliveries) is required.

### Recommendation
Bind the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-signed material, or otherwise cryptographically verify them (e.g., by including them in `to_signable_string`, or requiring the host app to independently confirm `shop` against a known session/store before trusting `WebhookMetadata`). At minimum, document prominently that headers are unauthenticated and must not be used as a tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery with body `{"id":123}` and header `x-shopify-hmac-sha256: <valid HMAC over the body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical raw body and HMAC header to the same webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC — validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {...}, ...)`, and the host application processes/stores data as if it legitimately originated from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
