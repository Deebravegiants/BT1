### Title
`describeWithdrawal` misreports withdrawal status/txHash when a batch contains multiple withdrawals of the same asset - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` and `waitForWithdrawalCompletion`'s helper both call `findMatchingWithdrawal`, which matches a POA bridge status-API record to a requested withdrawal purely by `nep141:{near_token_id} === assetId`, ignoring `amount`, `address`, and the `WithdrawalIdentifier.index`. When a caller submits a batch (`processWithdrawal`/`signAndSendWithdrawalIntent` with `withdrawalParams: WithdrawalParams[]`) containing two or more withdrawals of the same `assetId` but different `amount`/`destinationAddress`, `Array.prototype.find` always returns the *first* matching record in the (explicitly documented as "unsorted") API response for every index queried, so `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` can both resolve to the same record, or index 0 can resolve to the record that actually belongs to index 1's withdrawal.

### Finding Description
The claimed equality — "(amount,address) reported completed == (amount,address) signed" — is not enforced anywhere in the match path.

- `findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427` and its twin in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153` both do:
```
return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
```
Neither function looks at `withdrawal.data.amount`, `withdrawal.data.address`, or any withdrawal `index`/nonce to disambiguate between multiple withdrawals of the same asset in one NEAR transaction. The in-repo comment on both copies explicitly acknowledges this: *"Currently only matches by assetId... multiple withdrawals of the same token in a single transaction are not supported."*
- `describeWithdrawal` (`poa-bridge.ts:313-343`) is called once per index by `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` (see `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`), each call passing the same `args.tx.hash` (the shared NEAR settlement tx) but a different `args.withdrawalParams` (and thus a different intended amount/address). Since the POA status endpoint is queried by `withdrawal_hash` only and returns the full unsorted list of withdrawals for that tx, and the match key (`assetId`) is identical across same-asset withdrawals, `Array.find` deterministically returns the array's first same-asset element for every call, regardless of which index/amount/address was actually requested.
- Nothing upstream (`supports()`, `validateWithdrawal`, `createWithdrawalIdentifier`, or the intents-contract signing path) rejects or deduplicates a batch containing two same-asset withdrawals with different amounts/destinations; there is no invariant check tying the returned `withdrawal.data.amount`/`address` back to `args.withdrawalParams.amount`/`destinationAddress` before reporting `{status:'completed', txHash}`.

Attacker/user input: a `withdrawalParams` array such as `[{assetId:'nep141:X', amount:100n, destinationAddress:'A'}, {assetId:'nep141:X', amount:200n, destinationAddress:'B'}]` passed to `processWithdrawal`. No malicious relayer or API is required — the bug triggers purely from the ordinary "unsorted list, match-by-assetId-only" logic on a legitimate multi-withdrawal batch.

### Impact Explanation
An integrator (or the SDK's own `waitForWithdrawalCompletion`) can be told withdrawal index 0 is `{status:'completed', txHash: H}` where `H` is actually the destination transaction for withdrawal index 1 (different amount and/or address), or vice versa. This is a status/hash misreport that can cause an integrator to mark/credit a user's withdrawal as complete based on the wrong on-chain transfer, matching the "status or hash misreport making an integrator credit or refund twice" High-impact category. It is repeatable on every batch containing ≥2 same-asset withdrawals with differing amount/address, for as long as the POA bridge API returns an unsorted list (per the code's own comment).

### Likelihood Explanation
Precondition: the withdrawal batch must contain two or more withdrawals of the same `assetId` (this is not blocked anywhere in the SDK — batches are freely composed by the caller). Attacker cost is zero beyond constructing such a batch; no privileged access, no compromised relayer, and no reliance on a malicious API — only on the acknowledged fact that the POA bridge's `getWithdrawalStatus` response ordering doesn't guarantee correspondence to request order. This is a normal, legitimate usage pattern (multiple same-token withdrawals in one intent), not an edge case requiring adversarial setup, so it is realistically triggerable by an ordinary integrator or user.

### Recommendation
Extend `findMatchingWithdrawal` (both copies) to disambiguate same-asset withdrawals by additionally matching on `amount` and destination `address` (and consuming matched records so they aren't reused across indices), or track per-index consumption using a stable ordering (e.g., sort both the API response and the local `withdrawalParams` list by amount, as suggested in the existing code comment) before reporting `completed` status/txHash. Add an explicit runtime assertion that the reported `withdrawal.data.amount`/`address` match `args.withdrawalParams.amount`/`destinationAddress`, throwing/treating as pending instead of reporting `completed` on mismatch.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
