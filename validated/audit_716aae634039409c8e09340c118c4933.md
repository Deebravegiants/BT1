### Title
Non-embedded session cookie value is trusted as a session id without any HMAC/signature verification - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`SessionUtils.current_session_id` falls back to `cookie_session_id`, which returns the raw value of the `shopify_app_session` cookie verbatim as the session id used to load a `Session` from storage [1](#0-0) . Because session ids generated by this gem are deterministic and derivable from public information (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`), and the cookie carrying that id is set with no HMAC/signature attached to it, any client can forge the cookie value to request another tenant's session id.

### Finding Description
The claimed binding is: `session_id_returned_to_host_app == HMAC_or_signature_verified_value_under(Context.api_secret_key)`. Tracing the code shows this is false.

- `current_session_id` requires only that the cookie key be present, not that its value be validated in any way, before calling `cookie_session_id` for both the embedded-without-JWT and non-embedded branches [2](#0-1) .
- `cookie_session_id` simply returns `cookies[SESSION_COOKIE_NAME]` — no HMAC check, no signature, no `Context.api_secret_key` involvement of any kind [1](#0-0) .
- Confirmed by the gem's own test, which sets an arbitrary literal `"cookie_value"` as the cookie and asserts it is returned unmodified as the session id [3](#0-2) .
- The cookie is originally set by `Oauth.validate_auth_callback` to literally `session.id` for non-embedded apps, with no signature attached to the cookie value itself [4](#0-3) .
- Session ids produced elsewhere in this same class are deterministic and guessable from public data: `"offline_#{shop}"` and `"#{shop}_#{user_id}"` [5](#0-4) . A shop's `myshopify.com` domain is typically public/discoverable, and a user_id may leak via storefront pages, app listings, etc.

None of the existing guards (`HmacValidator.validate`, `ShopValidator.sanitize!`, the OAuth `state` check, `JwtPayload`'s `aud` check) apply on this path at all — those guards only run during the initial OAuth callback (`Oauth.validate_auth_callback`), not on this session-lookup path, which is reached on every subsequent authenticated request from the host app once OAuth has completed. `HttpRequest#verify` and Sorbet runtime typing only check types (`String`), not authenticity of the value.

Exploit flow: an attacker who has installed the app themselves (or simply knows/guesses a victim shop's domain, e.g. `victim-shop.myshopify.com`) sends a request to the non-embedded host app with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. `current_session_id(nil, {"shopify_app_session" => "offline_victim-shop.myshopify.com"}, false)` returns that exact string unmodified. The host app (per this gem's documented usage pattern) then uses this returned id to look up a `Session` object in its session storage keyed by session id, potentially returning the victim's offline session (and its access token) to the attacker.

### Impact Explanation
If exploited, the attacker's request causes the host app to load and act with another tenant's stored `Session` (including its access token) purely because the session-id lookup key was accepted from an unauthenticated, unsigned cookie value. This is cross-tenant access / session fixation: one tenant's identifier is trusted as if it belonged to the requester. Blast radius depends on the host app's session storage semantics (whether it's keyed exactly by this session id string across all installs), but the gem provides no cryptographic binding at all between the returned session id and the requester, which is the root defect regardless of storage backend.

### Likelihood Explanation
Preconditions: `Context.embedded? == false` (a common, documented, supported app mode), OR embedded with no `shopify_id_token` header sent. No secrets are required — the attacker only needs to know or guess a shop domain (public) and, for online sessions, a user id (potentially discoverable). No TLS interception or physical access needed; the attacker fully controls the cookie header of their own requests. This is repeatable against any victim shop/session id string the attacker can guess.

### Recommendation
Sign the session-cookie value (e.g., HMAC it with `Context.api_secret_key`, or store an opaque, unguessable server-generated value in the cookie mapped server-side to the session id) and verify that signature/mapping in `cookie_session_id` before trusting the cookie as a session identifier, mirroring the HMAC validation already used for OAuth callbacks.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_session_id_accepts_unsigned_attacker_chosen_value
  ShopifyAPI::Context.stubs(:embedded?).returns(false)
  attacker_value = "offline_victim-shop.myshopify.com"
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => attacker_value }

  # No HMAC secret, signature, or api_secret_key involved anywhere in this call.
  result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  assert_equal(attacker_value, result) # returned verbatim, unverified
end
```
This demonstrates the equality `session_id_returned == attacker_supplied_cookie_value` holds unconditionally, with no dependency on `Context.api_secret_key` or any signature, confirming the missing binding.
