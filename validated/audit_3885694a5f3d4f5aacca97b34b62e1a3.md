## Analysis

The external report's bug class — a value that is *used* to make a security decision is not actually the value that gets *verified* — has a direct analog in this gem's webhook processing path.

### The mismatched binding

`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only the raw HTTP body: [1](#0-0) [2](#0-1) 

`hmac` and `shop` are both simply read off HTTP headers (`x-shopify-hmac-sha256`/`shopify-hmac-sha256` and `x-shopify-shop-domain`/`shopify-shop-domain`), and neither header is included in `to_signable_string`. `Utils::HmacValidator.validate` only checks that the HMAC matches the raw body: [3](#0-2) 

`Registry.process` trusts `request.shop` after this check passes, and hands it straight to the app's webhook handler as the tenant identifier: [4](#0-3) 

So the equality the code implicitly assumes — `shop attributed to the webhook == shop that produced the HMAC-signed body` — does not hold, because `shop` is never part of the signed content. The HMAC secret (`Context.api_secret_key`) is a single app-wide secret shared across every shop that installs the app, not a per-shop secret. Any shop that installs the app can receive a legitimately-signed webhook (with body content it can influence, e.g. via a resource's editable fields), and since `shop-domain` is not covered by the signature, that same signed body/HMAC pair remains valid if replayed to the app's webhook endpoint with the `shop-domain` header changed to a different, victim shop's domain. `Registry.process` will accept it and dispatch the forged event to the handler under the victim shop's identity.

This is precisely the report's underlying class of bug — the gem authenticates one thing (the body bytes) but the consuming code acts on a different, unauthenticated field (the shop) as if it had been verified.

### Title
Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw webhook body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from separate, unsigned HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body only and then trusts `request.shop` as the tenant for dispatch, without any binding between the two.

### Finding Description
`Request#hmac` and `Request#shop` both come from independent HTTP headers, while `Request#to_signable_string` returns just `@raw_body`. Because the app-wide `api_secret_key` used for HMAC verification is identical for every shop that installs the app, a party that controls any shop where the app is installed can obtain a body+HMAC pair that is valid for that shop, then submit the identical body/HMAC to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will accept it because it never inspects the shop header, and `Registry.process`/`WebhookMetadata` will hand the forged event to the app's handler as if it originated from the spoofed shop.

### Impact Explanation
This breaks the tenant isolation boundary: an attacker who is a legitimate (but unprivileged, relative to other merchants) installer of the app can inject fabricated webhook events attributed to any other shop using the app, without needing that shop's credentials. Depending on what the host app does with webhook data (e.g. updating stored order/product/customer records keyed by `shop`), this can lead to cross-tenant data corruption or unauthorized state changes attributed to a victim's store — a cross-tenant access violation.

### Likelihood Explanation
Exploitation requires: (1) the attacker be a shop that installs the app (a normal, unprivileged action, no special access needed), (2) the attacker be able to influence some editable field value in a webhook body they receive, and (3) resubmit the intercepted request to the app's own public webhook endpoint with a modified shop header. No secrets, tokens, or elevated access are required beyond normal app installation.

### Recommendation
Bind the shop (and other identifying headers) into the signed content verified by `Utils::HmacValidator`, or otherwise cryptographically tie the `shop-domain` header to the signature (e.g., by having `to_signable_string` include the shop domain, or by cross-checking `request.shop` against a separately-authenticated value) before trusting it in `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook whose body contains attacker-controlled content (e.g. rename a product to include a crafted value), and capture the resulting HTTP request, including its valid `x-shopify-hmac-sha256` value (computed with the app's shared `api_secret_key`).
3. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:12-22) succeeds because it only checks the body signature; `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data as belonging to the victim shop.
