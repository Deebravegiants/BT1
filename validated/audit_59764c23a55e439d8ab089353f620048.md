### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` field used to attribute the webhook to a tenant is read from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` trusts this header value and forwards it to the app's handler as the tenant identity, without it ever being part of the signed data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` value and dispatches it to the app-provided handler: [3](#0-2) 

`WebhookMetadata.shop` is a `T::Struct` field with no further validation, consumed directly by the handler to key data by tenant: [4](#0-3) 

This breaks the identity binding that should hold: `hmac-verified bytes (raw_body)` should equal `bytes used to determine tenant identity (shop header)`. Because the `client_secret`/`api_secret_key` used to compute the webhook HMAC is shared across all shops that install a given app, a person who legitimately installs the app on their own shop can capture a genuine `raw_body` + valid `hmac-sha256` pair delivered to their own webhook endpoint (which they control, since they own that installation), then replay that identical body and signature to the app's webhook endpoint while substituting a different, victim shop's domain in the `x-shopify-shop-domain` header. `HmacValidator.validate` verifies against `Context.api_secret_key`: [5](#0-4) 
Since only the body is checked, the forged/spoofed shop header passes through untouched, and the handler processes the payload as if it originated from the victim's shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged party who can install the app (or otherwise obtain one valid body+HMAC pair from any tenant using the same app credentials) can make the host application believe a webhook event (order data, `app/uninstalled`, `shop/redact`, `customers/data_request`, etc.) originated from an arbitrary victim shop domain of their choosing. Since host applications commonly key sessions, data records, and business logic off `WebhookMetadata#shop`, this can lead to cross-tenant data corruption, spoofed lifecycle events (e.g., faking an uninstall or redaction event for a shop the attacker doesn't own), or injection of attacker-influenced data attributed to another merchant.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimate `(raw_body, hmac)` pair produced under the app's shared `api_secret_key` — trivially obtainable by installing the app on any shop (including a shop the attacker controls) and capturing a delivered webhook at their own endpoint, or from any shop with which the attacker interacts. Forging the `shop-domain` header requires only crafting an HTTP request; no cryptographic material is needed for that part since the header sits entirely outside the HMAC's protected data.

### Recommendation
Bind the tenant identity into the same trust boundary as the payload: either include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-signed string in `Request#to_signable_string`, or otherwise verify that the `shop` header value is consistent with a shop-specific secret/session context maintained by the host app before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated on its own and must not be used as a sole tenant key without additional verification (e.g., cross-checking against an existing stored session for that shop).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same raw body and `hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature only covers `raw_body`: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, and the host application processes the event as belonging to `victim.myshopify.com`.
