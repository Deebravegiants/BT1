Found a valid analog in the webhook processing pipeline: the shop identity used for tenant dispatch is never covered by the HMAC that authenticates the request.

### Title
Webhook `shop` field is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates nothing but the bytes of the JSON payload. The `shop` value, read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, is never included in the signed content, yet `Registry.process` passes it straight through as the tenant identifier delivered to the app's webhook handler.

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` only: [1](#0-0) 

`Request#shop` is read from an unauthenticated header with no cross-check against the signed body: [2](#0-1) 

`Registry.process` verifies the HMAC (which only covers `@raw_body`) and then immediately uses `request.shop` — the header value — to build the `WebhookMetadata` handed to the registered handler: [3](#0-2) 

`HmacValidator.validate` performs a straightforward HMAC compare against `verifiable_query.to_signable_string`, i.e. only the body: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used to route/attribute the webhook payload`. Because `to_signable_string` excludes the `shop-domain` header, this equality is never enforced — the HMAC only proves "this body byte-string was produced with the app's secret", not "this body belongs to shop X". Any party who can obtain one valid `(raw_body, hmac)` pair for the app's shared secret (e.g. by installing the app, which is public, on a shop they control, since Shopify webhook bodies frequently contain no shop-identifying content, such as `app/uninstalled` or many resource webhooks with generic payload shapes) can replay that exact body+HMAC pair directly to the app's own webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still pass (the body is genuinely HMAC-valid), and `Registry.process` will hand the attacker-chosen `shop` value to the handler as if it were authentic.

### Impact Explanation
This breaks the tenant boundary: the handler receives `WebhookMetadata#shop` (used by host applications to select the target tenant's session/access token/database record) without any cryptographic guarantee that the payload actually originated for that shop. A malicious app installer can cause data belonging to their own shop's webhook body to be processed and attributed to a victim shop identifier, corrupting or triggering unintended actions against another tenant's records — cross-tenant access/contamination.

### Likelihood Explanation
Medium: exploitation requires the attacker to (1) install the target app on any shop they control (public apps allow this trivially) to obtain a validly-signed `(body, hmac)` pair, and (2) directly POST to the app's public webhook endpoint with a forged `shopify-shop-domain` header — both of which are reachable by an unprivileged internet user with no credentials, tokens, or TLS interception required. The main constraint is finding/crafting a webhook body that is shop-agnostic or otherwise useful when attributed to another tenant, which is plausible for several standard webhook topics.

### Recommendation
Bind the `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cross-check the header-derived `shop`/`topic` against the payload/registration context before dispatch, rather than trusting `shopify-shop-domain` purely from an unauthenticated header. At minimum, document/require that consuming apps independently verify the `shop` belongs to a shop that has an active installation before trusting webhook metadata for tenant-sensitive operations.

### Proof of Concept
1. As an ordinary developer, create a free/dev Shopify store and install the target Shopify app (assume it uses this gem's `Webhooks::Registry` to process webhooks for a topic with a fixed/generic body, e.g. `app/uninstalled`).
2. Trigger the webhook (e.g., uninstall the app) and capture the exact raw request the app's webhook endpoint receives, including the `X-Shopify-Hmac-Sha256` header and body.
3. Replay this exact HTTP request to the app's public webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with a victim shop's domain (e.g., `victim-shop.myshopify.com`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only signs `@raw_body`, unaffected by the header change: [5](#0-4) 
5. The handler receives `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content under the victim's tenant identity, with no verification that the two ever agreed with each other.

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
