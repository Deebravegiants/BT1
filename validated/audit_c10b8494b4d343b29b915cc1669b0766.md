### Title
Unrestricted `CallDispatcher.dispatch()` lets any caller plant persistent ERC20 approvals that drain funds transiently routed through the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, unowned contract used as the temporary custodian for every predispatch/postdispatch calldata execution across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken`. Its `dispatch()` entrypoint has no access control, so any unprivileged account can invoke it directly to execute arbitrary calls in the dispatcher's own context — including granting itself an unlimited ERC20 `approve()` from the dispatcher. Because the dispatcher's sweep logic in intent fills only recovers the specific tokens declared in `order.output.assets`, any output calldata that produces a *different* token (via a swap, fee-on-transfer token, or rounding) leaves a genuine, standing balance on the shared dispatcher that is never reclaimed. Combined with the self-granted infinite approval, an attacker can later call the ERC20's `transferFrom()` directly to steal that stranded balance, which economically belongs to a legitimate order/beneficiary.

### Finding Description
`CallDispatcher.dispatch()` is declared as a bare `external` function with no modifier restricting the caller: [1](#0-0) 

Any address can call this function to make the dispatcher execute `to.call{value}(data)` for arbitrary `to`/`data` pairs, including `IERC20(token).approve(attacker, type(uint256).max)`, which sets `allowance[dispatcher][attacker]` permanently, since ERC20 allowances persist independently of any transaction boundary.

The same dispatcher instance is reused as the trusted, temporary holder of funds for unrelated users' operations: `IntentGatewayV2` transfers predispatch assets to it and invokes `dispatch()` before sweeping tokens back, and `IntentsBase._execute` does the same for postdispatch output calldata: [2](#0-1) 

The sweep in `_execute` only recovers balances for the tokens explicitly listed in `order.output.assets` (`outputsLen`), snapshotting `IERC20(token).balanceOf(dispatcher)` for just those tokens. If `order.output.call` performs a swap or any operation that leaves the dispatcher holding a token *not* in `order.output.assets` (e.g., a DEX swap that overshoots into a different asset, or leftover from fee-on-transfer semantics), that balance is never swept and remains standing on the dispatcher indefinitely — a real, persistent balance rather than transient escrow.

The `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` flows likewise route to the same shared dispatcher and are documented as depending on manual approval hygiene from callers rather than any dispatcher-side protection: [3](#0-2) 

Since `dispatch()` is unrestricted, an attacker does not need to participate in any order or transfer at all to plant the approval — they simply call the dispatcher directly at any time, for any ERC20, well in advance of exploiting a future standing balance left by any other flow.

### Impact Explanation
This allows theft of funds that transiently or persistently reside on the shared `CallDispatcher`: any residual token balance left behind by a mismatched output swap, fee-on-transfer token, or rounding in intent fills (or HFT calldata execution) can be permanently drained by an attacker who pre-planted an infinite approval via the unrestricted `dispatch()` call. This is a concrete theft-of-funds vector reachable by any unprivileged intent solver/order placer/caller, matching High severity per the in-scope validation criteria (unauthorized app action / theft of escrowed or in-flight funds).

### Likelihood Explanation
Likelihood is high for the approval-planting step (trivial, permissionless, one transaction, no cost beyond gas) but depends on a standing dispatcher balance existing, which requires either a token-mismatched output/predispatch swap, a fee-on-transfer token, or rounding dust to accumulate. Given `IntentGatewayV2` explicitly supports arbitrary DEX/DeFi routing calldata in `order.output.call`/`order.predispatch.call` (swap-then-escrow / fill-then-act patterns are the advertised use case), such mismatches are a realistic and even likely outcome in normal usage, not merely a contrived edge case.

### Recommendation
Restrict `CallDispatcher.dispatch()` to an allowlist of trusted callers (e.g., the registered `IntentGatewayV2` and HFT/WrappedHFT contracts) via an `onlyAuthorized` modifier, and/or make the dispatcher revoke approvals it grants at the end of each `dispatch()` call. Additionally, harden the sweep logic in `IntentsBase._execute` (and the predispatch sweep in `IntentGatewayV2`) to reconcile *all* token balances the dispatcher ends up holding after arbitrary calldata execution, not just the tokens declared in `order.output.assets`/`order.inputs`, so no value can silently strand on the shared contract.

### Proof of Concept
1. Attacker (no prior relationship to any order) calls `CallDispatcher.dispatch(abi.encode([Call({to: TOKEN, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})]))` directly. This succeeds because `dispatch()` has no access control, granting `allowance[dispatcher][attacker] = max` for `TOKEN`.
2. At any later point, a legitimate user places/fills an intent order whose `output.call`/`predispatch.call` swaps into `TOKEN` but does not declare `TOKEN` in `order.output.assets`/`order.inputs` (e.g., slippage or an intermediate hop token), leaving a nonzero `TOKEN` balance on `CallDispatcher` that `_execute`'s sweep loop does not recover.
3. Attacker calls `TOKEN.transferFrom(dispatcher, attacker, TOKEN.balanceOf(dispatcher))` directly on the token contract, draining the stranded balance that belonged to the victim's order/beneficiary.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }

                uint256 balance = IERC20(token).balanceOf(dispatcher);

                    });

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
