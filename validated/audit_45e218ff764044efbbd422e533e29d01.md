### Title
Token Exchange accepts non-admin (checkout UI extension) session tokens to mint Admin API access tokens - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` trusts the `dest` claim of *any* validly-signed Shopify ID token to determine which shop receives a token-exchange request for a full Admin API access token, without checking that the token is an **admin** session token (`iss` ending in `/admin`). The gem itself defines and uses an `admin_session_token?` predicate elsewhere (`JwtPayload#shopify_user_id`), proving that admin-vs-non-admin token type is a claim that must be checked before granting admin-level trust — but `exchange_token` never checks it.

### Finding Description
`ShopifyAPI::Auth::JwtPayload` decodes and signature-verifies a Shopify ID token, exposing `iss`, `dest`, `aud`, `sub`, etc. [1](#0-0) 

The class explicitly distinguishes an "admin session token" from other session tokens (such as those issued to checkout UI extensions) via: [2](#0-1) 

This predicate is exercised in the gem's own tests, which show that a checkout UI extension token (`iss: ".../checkouts"`) is signed with, and successfully decodes using, the very same `Context.api_secret_key` as an admin token: [3](#0-2) 

`admin_session_token?` is consumed by `shopify_user_id`, but `TokenExchange.exchange_token` never calls it. It only validates the signature/`aud` (via `JwtPayload.new`) and then unconditionally uses `dest` to build the shop the app trusts with its `client_secret`: [4](#0-3) 

Compare this to the sibling method `migrate_to_expiring_token`, which validates the shop it is given via `Utils::ShopValidator.sanitize!` before using it — showing the library authors do apply extra binding checks in some privileged flows but omitted the equivalent "is this really an admin session token" check in `exchange_token`. [5](#0-4) 

The identity binding that should hold is:
`token type (iss == admin session) == token trusted for Admin API token exchange`

Because this binding is never checked, any signed-by-the-app ID token — including a checkout UI extension token, which is available to a much lower-privileged identity (a storefront customer/checkout context) than a merchant/admin session — is accepted, and its `dest` claim is used to request a full Admin API access token from Shopify using the app's `client_id`/`client_secret`.

### Impact Explanation
This breaks the trust boundary between "app installed and authenticated in Shopify Admin" (has `iss` ending `/admin`) and "checkout extension context" (has `iss` ending `/checkouts`). A party who can only obtain a checkout-context session token (a much weaker capability than an authenticated Admin embedded session) can call `exchange_token` and receive a legitimate Admin API access/refresh token for the shop, i.e., privilege escalation / scope-check bypass — matching the "scope or expiry check bypass" High-impact category, and depending on the requested token type (offline, with broad configured scopes), it can amount to full merchant data compromise (Critical-adjacent).

### Likelihood Explanation
Any host application that calls `ShopifyAPI::Auth::TokenExchange.exchange_token` and (as is common for embedded apps using checkout UI extensions or App Bridge in multiple surfaces) also handles session tokens originating from non-admin surfaces is exposed. Since the library performs no `admin_session_token?` check itself, the vulnerability lives entirely in this gem's exchange_token implementation and requires no credentials or privileged access beyond obtaining any validly signed session token for the app (e.g., from checkout).

### Recommendation
In `TokenExchange.exchange_token`, after constructing `jwt_payload`, require `jwt_payload` to be an admin session token before proceeding (e.g., expose and check `jwt_payload.admin_session_token?`), raising `ShopifyAPI::Errors::InvalidJwtTokenError` otherwise — mirroring the deliberate shop-domain validation already performed in `migrate_to_expiring_token`.

### Proof of Concept
1. Attacker (a storefront customer, not a merchant) obtains a checkout UI extension session token for the shop (issued by Shopify to the checkout extension context, signed with the app's `api_secret_key`), e.g. payload `{ iss: "https://shop.myshopify.io/checkouts", dest: "shop.myshopify.io", aud: <api_key>, sub: "gid://shopify/Customer/123", ... }` as shown in `test/auth/jwt_payload_test.rb` lines 23-32 and 154-174.
2. Attacker calls:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: checkout_extension_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `JwtPayload.new` successfully validates the token (signature + `aud` match) since `exchange_token` never checks `iss`/`admin_session_token?`.
4. `exchange_token` proceeds to POST `client_id` + `client_secret` + the checkout token to `https://shop.myshopify.io/admin/oauth/access_token` and returns a full Admin API `Session` with a merchant-privileged `access_token`, despite the attacker never having had an authenticated Admin session.
