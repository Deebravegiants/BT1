## Answer

Based on the code I reviewed, this is a real gap in the accounting model, but it needs careful scoping.

### Title
Storage-proof recording margin for trie removals only covers `TrieKey::ContractData`, leaving `AccessKey`/`GasKeyNonce`/`ReceivedData`/`PromiseYield` removals unaccounted for restructuring cost - (File: core/store/src/trie/update.rs)

### Summary
`TrieUpdate::remove` only calls `TrieRecorder::record_key_removal()` — which adds a flat 2000-byte safety margin to `upper_bound_size` — when `trie_key` matches `TrieKey::ContractData`. All other trie-key removals performed on behalf of the runtime/user actions (e.g. `remove_access_key`, `remove_gas_key_nonce` in `runtime/runtime/src/access_keys.rs`) bypass this margin entirely, even though the actual restructuring cost recorded later in `Trie::update`/`finalize` (extension merges, branch collapses requiring sibling reads) is identical in kind to what ContractData removal can trigger.

### Finding Description [1](#0-0) 
The comment explicitly states the rationale: "removals performed by the runtime are assumed to be non-malicious and we don't charge extra for them." `remove_access_key` and `remove_gas_key_nonce`, invoked from `delete_gas_key`/`delete_regular_key` in `runtime/runtime/src/access_keys.rs`, are exactly such "runtime" removals — but they are directly reachable by an unprivileged attacker via `AddKey`/`DeleteKey` transactions, and gas-key deletion loops over `remove_gas_key_nonce` once per nonce (`for i in 0..gas_key_info.num_nonces { remove_gas_key_nonce(...) }`), [2](#0-1)  meaning an attacker fully controls the number of removal calls per transaction via `num_nonces` when creating a gas key, then deleting it.

The design intent behind `record_key_removal`'s flat 2000-byte charge (per `core/store/src/trie/trie_recording.rs` lines 140-146, referencing near/nearcore#10890) is to bound the *unaccounted* proof growth that a single removal can cause due to trie restructuring discovered only at `finalize()` time (after `check_proof_size_limit_exceed()` has already been evaluated during execution). Because that safety margin is gated on `TrieKey::ContractData` only, `AccessKey`/`GasKeyNonce` deletions get zero margin, meaning any restructuring-induced proof growth from those removals is invisible to `upper_bound_size` and thus to `check_proof_size_limit_exceed()`.

However, unlike `ContractData`, whose keys are attacker-chosen and can be crafted to specific trie positions to maximize sibling/branch reads on removal, `AccessKey`/`GasKeyNonce` keys are structured (`account_id + column + public_key [+ nonce_index]`) and their prefixes are the account's own key subtree, which is comparatively less exploitable for adversarial worst-case fan-out than a fully attacker-controlled `ContractData` key namespace under an attacker-owned contract account. I was not able to fully verify, from the code available, the actual worst-case magnitude of trie-restructuring proof growth achievable through crafted `AccessKey`/`GasKeyNonce` sequences versus the compute already charged via `storage_removes_compute` (`runtime/runtime/src/access_keys.rs` lines 118-125), nor whether the `main_storage_proof_size_soft_limit` check semantics (soft limit that stops processing further receipts, rather than a hard consensus-breaking limit) would actually be violated in a way that causes protocol-level harm as opposed to merely degraded chunk-production efficiency. This requires empirical fuzzing (as the question itself proposes) against the actual `storage_proof_size_soft_limit` enforcement path in `runtime/runtime/src/lib.rs`, which I was not able to fully trace to conclusive limit-bypass instrumentation within the available tool budget.

### Impact Explanation
If exploitable, the impact would be: the runtime's soft proof-size limit could be silently exceeded due to unaccounted trie-restructuring during `AccessKey`/`GasKeyNonce` deletion, producing an oversized state witness. Since `main_storage_proof_size_soft_limit` is enforced as a *soft* limit (chunk producers stop admitting further receipts once exceeded, not a hard consensus failure), the worst-case protocol impact is likely reduced block/chunk throughput or witness-size stress on validators rather than a direct fund-loss, consensus-divergence, or authorization-bypass bug. This is a weaker impact class than the analogous documented `ContractData` issue (#10890), which was itself mitigated with a flat margin rather than exact accounting.

### Likelihood Explanation
Preconditions are low: any unprivileged account holder can submit `AddKey`/`DeleteKey` transactions or create/delete gas keys with a chosen `num_nonces`, requiring no special privilege. Repeatability is high (can be looped across many transactions/receipts). However, feasibility of actually producing *significant* unaccounted trie-restructuring proof growth per removal (comparable to or exceeding the 2000-byte margin ContractData removals get) via `AccessKey`/`GasKeyNonce`/`ReceivedData`/`PromiseYield` deletions is unverified — the trie subtree under these keys is generally much shallower/narrower per-account than an attacker-controlled `ContractData` namespace, and I could not confirm the actual per-removal amplification factor from static analysis alone.

### Recommendation
Extend `record_key_removal()` accounting (or an equivalent, possibly smaller, margin) to cover all trie-key removals reachable from unprivileged user actions — not only `TrieKey::ContractData` — including `AccessKey`, `GasKeyNonce`, `ReceivedData`, and `PromiseYield`, or empirically bound and document why these key types cannot produce meaningful unaccounted restructuring cost relative to the compute already charged in `storage_removes_compute`.

### Proof of Concept
Fuzz/integration test plan (not yet executed, provided as guidance since this could not be conclusively validated with static analysis alone):
1. Build a chunk-execution test harness (`runtime/runtime/src/tests/apply.rs` already has `main_storage_proof_size_soft_limit`/`check_proof_size_limit_exceed` test scaffolding) that creates an account with a gas key having a large `num_nonces`, populates surrounding trie state to maximize branch/extension restructuring on deletion, then issues a `DeleteKeyAction`.
2. Record `TrieRecorder::recorded_storage_size()` (actual) vs `recorded_storage_size_upper_bound()` (accounted) before and after `finalize()`, and compare the actual post-finalize proof growth against `result.compute_usage` charged via `storage_removes_compute`.
3. Assert that `recorded_storage_size() - recorded_storage_size_upper_bound()` remains bounded (e.g., under some safety multiple of compute charged); a failing assertion where actual proof size measurably exceeds the accounted upper bound by an amount not explained by margin would substantiate the finding quantitatively.

```rust
    pub fn remove(&mut self, trie_key: TrieKey) {
        // We count removals performed by the contracts and charge extra for them.
        // A malicious contract could generate a lot of storage proof by a removal,
        // charging extra provides a safe upper bound. (https://github.com/near/nearcore/issues/10890)
        // This only applies to removals performed by the contracts. Removals performed
        // by the runtime are assumed to be non-malicious and we don't charge extra for them.
        if let Some(recorder) = &self.trie.recorder {
            if matches!(trie_key, TrieKey::ContractData { .. }) {
                recorder.record_key_removal();
            }
        }

        self.prospective.insert(trie_key.to_vec(), TrieKeyValueUpdate { trie_key, value: None });
    }
```
