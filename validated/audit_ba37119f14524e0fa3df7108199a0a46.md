## Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop` (tenant) identifier used by `ShopifyAPI::Webhooks::Registry.process` to dispatch webhook data is read from an unauthenticated HTTP header that is never included in the signed bytes. Any party that can obtain one valid `(raw_body, hmac)` pair for a shop can replay it against the app's webhook endpoint with a different `shop-domain` header and have it processed as belonging to a different tenant, because the signature check succeeds regardless of the `shop` value.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all sourced from HTTP headers and are excluded from the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `to_signable_string` (i.e., the raw body) against `hmac`: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once `HmacValidator.validate` succeeds, and then passes the *unverified* `request.shop` header straight into `WebhookMetadata`, which the app's handler uses as the tenant identifier for processing the event: [4](#0-3) 

The identity binding that should hold is:
`shop_used_for_dispatch == shop_covered_by_hmac`

In this code, `shop_used_for_dispatch` is `request.shop` (an unauthenticated header value), while `shop_covered_by_hmac` is effectively "nothing" — the HMAC only covers `@raw_body`. Because the two are decoupled, an attacker who can produce or capture one legitimate `(body, hmac)` pair (e.g., by installing the app on their own shop and receiving Shopify's real webhook callback, which is trivially available to any merchant/developer) can resend that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still passes because it never inspected the shop header, and `Registry.process` dispatches the payload to the handler tagged with the attacker-supplied `shop` value.

## Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for inbound webhooks: an unprivileged actor (any merchant with an app install, or anyone who can capture a single valid webhook delivery) can inject arbitrary webhook payloads that are processed as if they belong to a different, victim shop. Since host applications rely on `WebhookMetadata#shop` from this library as the trusted tenant key when persisting/acting on webhook data, this can lead to cross-tenant data corruption or state confusion (e.g., orders/products/customers or app-uninstall events being attributed to the wrong shop). This matches the "Critical - cross-tenant access" impact category, because the vulnerability is in the gem's own identity-binding logic, not a misuse of a documented API by the host app.

## Likelihood Explanation
Medium-to-high. No secrets, tokens, or privileged access are required — only a legitimate `(raw_body, hmac)` pair for *some* shop, which is trivially obtainable by any developer/merchant who installs the target app and captures Shopify's own webhook call to their endpoint (or any environment where webhook payloads are logged/replayable). The attacker only needs to alter the `shop-domain` header on replay; the body and HMAC remain byte-for-byte identical and thus still validate.

## Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered material, or otherwise cryptographically bind the `shop` header to the verified payload before it is trusted — e.g., derive the tenant strictly from a value that is itself covered by the signature, or require the host application to separately confirm the shop against its own webhook subscription registry (keyed by webhook id) rather than trusting the header verbatim.

## Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# captures a legitimate Shopify webhook delivery for topic "orders/create":
raw_body = '{"id":1,"note":"attacker-controlled"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
valid_hmac_b64 = Base64.encode64(hmac)

# Attacker replays the same body/hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation succeeds because it only checks raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process dispatches attacker-controlled data tagged as "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
```
