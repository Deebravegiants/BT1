### Title
Deflationary/fee-on-transfer underlying tokens break the lock/mint invariant in `WrappedHyperFungibleToken(Upgradeable).send()` - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol])

### Summary
`WrappedHyperFungibleTokenUpgradeable.send()` (and its non-upgradeable twin `WrappedHyperFungibleToken.sol`) locks `params.amount` of the underlying ERC20 via `safeTransferFrom` and then dispatches a cross-chain message that commits to unlocking/minting exactly `params.amount` on the destination side. It never checks the actual balance received by the contract before/after the transfer, unlike `IntentGatewayV2`, which explicitly measures `balanceOf` deltas to remain safe against fee-on-transfer tokens.

### Finding Description
`send()` performs:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
bytes memory body = abi.encode(HyperFungibleTokenUpgradeable.Message({..., amount: params.amount, ...}));
``` [1](#0-0) 

If `_underlying` is a deflationary/fee-on-transfer/rebasing token, the contract's actual received balance is strictly less than `params.amount`, yet the dispatched `Message.amount` (the amount committed to the peer contract on the destination chain, which will be unlocked/transferred there via `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` in `onAccept`) still equals the full, unreduced `params.amount`. [2](#0-1) 

This directly contradicts the escrow/lock-unlock invariant this contract is designed around ("Locks the underlying token on the source chain and mints/unlocks on the destination chain" / "no shared custody pool"), because the amount actually escrowed on the source chain is now permanently less than the amount promised for release on the destination chain. [3](#0-2) 

By contrast, the codebase already demonstrates awareness of and a fix for this exact bug class in `IntentGatewayV2.placeOrder`, which snapshots `balanceOf` before and after `safeTransferFrom` and mutates the escrowed/committed amount to the actual received value:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [4](#0-3) 

`WrappedHyperFungibleTokenUpgradeable.send()` has no equivalent check, so it is a direct analog where the mitigation pattern used elsewhere in the same protocol was not applied.

### Impact Explanation
Each transfer of a fee-on-transfer/deflationary underlying through `send()` skims the escrow pool by the token's fee percentage while still instructing the destination-chain peer to release the full nominal amount from its own escrow. Over repeated transfers, the aggregate amount locked on the source chain falls short of the aggregate amount that peers across all connected chains are obligated to release. Because this is a lock/unlock (not mint/burn) bridge design with no shared custody pool, the shortfall directly reduces the collateral backing all outstanding wrapped balances, meaning some legitimate holders will be unable to redeem their full amount on the destination chain (`safeTransfer` insufficient balance revert), i.e. permanent freezing/loss of user funds. This is reachable by any unprivileged user simply calling `send()` with a supported deflationary ERC20 configured as `_underlying` — no privileged role or governance action is required to trigger the loss.

### Likelihood Explanation
Likelihood is contingent on the owner configuring a deflationary/fee-on-transfer/rebasing token as `_underlying` via `configure()`; for a standard, non-deflationary ERC20 this bug class does not manifest. However, nothing in `configure()` restricts `_underlying` to non-deflationary tokens, and the wrapper is a generic "wrap any existing ERC20" primitive, so deployment against a fee-on-transfer token is a realistic and foreseeable configuration, especially since the sibling `IntentGatewayV2` contract in the same repo was explicitly hardened against this exact scenario, indicating the protocol authors consider such tokens in-scope.

### Recommendation
In `send()`, measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual received delta as `params.amount` in the dispatched `Message`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`. Apply the same fix to `onAccept`/`onPostRequestTimeout`'s outgoing `safeTransfer` paths if `_underlying` can also be deflationary on the outbound leg (verify actual balance decrease matches `message.amount`, or use `safeTransfer` and accept that recipient may receive less, but ensure the emitted event and downstream calldata reflect the true received amount).

### Proof of Concept
1. Owner configures `WrappedHyperFungibleTokenUpgradeable` with `_underlying = FeeOnTransferToken` (e.g., 1% fee on transfer), analogous to the `FeeOnTransferToken` test double already used in `IntentGatewayV2SameChainTest.sol`. [5](#0-4) 
2. User A calls `send({amount: 1000e18, to: userA_on_dest, dest: ..., ...})`. `safeTransferFrom` pulls 1000e18 but, due to the 1% fee, the contract's balance only increases by 990e18.
3. The dispatched `Message.amount` is still `1000e18`, so the peer contract on the destination chain will later execute `safeTransfer(beneficiary, 1000e18)` out of its own escrow when the message is delivered via `onAccept`.
4. Repeating this pulls progressively more value out of the aggregate escrow than was ever locked, so eventually a legitimate `onAccept` call on some chain will `safeTransfer` more than the contract's actual underlying balance, reverting and freezing the users who did not withdraw first (last-in, no-payout), demonstrating fund loss/freezing caused by the unhandled deflationary token.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(request.body, (HyperFungibleTokenUpgradeable.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
