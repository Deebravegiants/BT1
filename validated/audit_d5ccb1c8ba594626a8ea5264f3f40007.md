## Title
Webhook shop attribution relies on an unauthenticated header not covered by the HMAC signature - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` verifies solely that the body bytes are signed by the app's shared `client_secret`. The `shop`, `topic`, `webhook_id`, and `api_version` fields — read straight from request headers — are never included in the signed content, yet `Registry.process` uses `request.shop` as the trusted tenant identity when dispatching the payload to the host app's handler.

### Finding Description
`Request#to_signable_string` binds the HMAC to `@raw_body` only: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are outside that signed string: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` (and the other unverified header values) to build the metadata handed to the host app's handler: [3](#0-2) 

Because Shopify signs webhooks with the app's single shared `client_secret` (the same secret used for every shop that has the app installed, not a per-shop secret), any merchant/tenant that has the app installed can trigger an action on their own store to obtain a body + valid HMAC pair from Shopify. The equality this gem should be enforcing but doesn't is:

`shop asserted in header == shop bound inside the HMAC-covered bytes`

Since the right-hand side doesn't exist (the header is outside the signed content), an attacker who controls Tenant A can replay/forge an HTTP request to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to Tenant B, while keeping Tenant A's genuine raw body and its valid HMAC. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will hand the host app a `WebhookMetadata` claiming the data came from Tenant B.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to route webhook data (e.g., to update the correct merchant's records, trigger per-shop side effects, or authorize based on `shop`). An attacker with any single shop installation of the app can inject data that is misattributed to a different shop, i.e., cross-tenant data injection through a spoofed identity binding — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even trial/free) merchant with the app installed and the ability to POST an HTTP request with custom headers to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed. This is a low-friction, unprivileged-internet-user path once one real signed body is captured.

### Recommendation
Include the security-relevant header values (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable content, or otherwise cryptographically bind the shop identity to the payload (e.g., look up the expected shop for the webhook subscription server-side rather than trusting the header), so a body signed for one shop cannot be replayed and reattributed to another shop.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., updates a product) to receive a legitimate `raw_body` and its correctly computed `X-Shopify-Hmac-Sha256`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint using that same `raw_body`/HMAC pair but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only validates `@raw_body` against the HMAC. [4](#0-3) 
4. The host app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-supplied data as if it originated from the victim shop.
