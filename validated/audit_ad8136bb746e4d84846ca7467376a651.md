### Title
Unbounded-length `message.from` in `HyperFungibleToken::on_accept` panics on `copy_from_slice`, allowing a relayed cross-chain transfer to halt request processing - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::<T>::on_accept` decodes an attacker/user-controlled ABI `bytes` field (`message.from`) from an incoming `PostRequest` body and, in the non-EVM-source calldata-execution branch, copies it directly into a fixed 32-byte buffer without checking its length first, unlike the sibling code paths in the same file that do validate length before copying.

### Finding Description
`Message` is an ABI struct with unconstrained `bytes` fields (`from`, `to`, `amount`, `data`), decoded via `Message::abi_decode(&body)` [1](#0-0) . The `to` field is properly length-checked before being copied into a fixed buffer:

```
if to_bytes.len() == 32 { ... } else if to_bytes.len() == 20 { ... } else { Err(...)? }
``` [2](#0-1) 

But in the optional-calldata-execution branch of `on_accept`, when the request originates from a non-EVM chain, `message.from` is copied straight into a fixed `[u8; 32]` with **no length check at all**:

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [3](#0-2) 

`Vec::copy_from_slice`/`<[u8;32]>::copy_from_slice` panics if the source slice length does not exactly equal 32. Since `message.from` is an arbitrary-length ABI `bytes` value fully controlled by whoever initiates the transfer on the source chain, a crafted transfer whose `from` field is not exactly 32 bytes (e.g. 0, 31, 33 bytes) will panic when this code path executes — reached whenever `!message.data.is_empty()` and the signature-less branch is taken (`substrate_data.signature` is `None`) for a request coming from a non-EVM `source`.

This is the exact same bug class as CVE-2015-8728: an untrusted, length-driven field is copied into a fixed-size buffer without validating that the declared/observed length matches the buffer, causing a crash. Notably, the codebase itself documents having fixed this precise pattern elsewhere (`modules/ismp/core/src/host.rs` and `modules/utils/serde/src/lib.rs`, both with explicit regression tests noting "runs on untrusted input … panic … wasm trap"), confirming this is a recognized, previously-remediated bug class in this repository that was missed here. The `on_timeout` handler in the very same file (lines 224-232) applies the correct length check for the analogous `from_bytes`, showing the intended, but here-missing, guard.

### Impact Explanation
A panic during `IsmpModule::on_accept`, invoked from the pallet-ismp message-execution pipeline (`handle_incoming_message` / `Pallet::execute`) [4](#0-3) , is a runtime panic reachable from a relayed, dispatched ISMP request — i.e., attacker-controlled data reaches unguarded fixed-buffer arithmetic through a single relayed message. In a Substrate/FRAME context, an unguarded panic while executing an extrinsic's dispatch logic is a denial-of-service: it can abort block execution/traps the wasm runtime for that message, preventing legitimate token-bridge messages (and potentially other unrelated messages processed in the same batch, since `Pallet::execute` iterates over all messages in a call and maps over the whole batch) from being delivered, i.e. "a route unable to deliver messages."

### Likelihood Explanation
Reaching the vulnerable branch requires: (1) `ContractToAsset` authentication of `(source, from)` for the ISMP-level sender, which authenticates the source *contract*, not the length of the embedded ABI `message.from`; (2) `message.data` non-empty; (3) no substrate signature attached (`substrate_data.signature == None`); (4) `source` not EVM. All of these are ordinary, attacker-selectable parameters of a self-initiated cross-chain transfer with calldata — no privileged relayer, governance, or consensus proof forgery needed, just a malformed `from` field length in the ABI payload the user encodes when initiating the transfer. This makes the trigger straightforward for any user of a non-EVM-source hyper-fungible-token bridge deployment.

### Recommendation
Add an explicit length check (mirroring the `to_bytes`/`on_timeout` handling) before copying `message.from` into `[0u8; 32]`:
```rust
let mut account = [0u8; 32];
if from_bytes.len() != 32 {
    Err(HftError::InvalidSenderLength(from_bytes.len()))?
}
account.copy_from_slice(from_bytes);
```
and return a proper `HftError` variant instead of panicking, consistent with the rest of the file and with the previously-fixed instances of this same bug class in `host.rs` and `serde/src/lib.rs`.

### Proof of Concept
1. On a non-EVM source chain, initiate a hyper-fungible-token transfer whose emitted ISMP `PostRequest.body` ABI-encodes a `Message` with `data` non-empty, `data`'s decoded `SubstrateCalldata.signature == None`, and `from` set to any byte string whose length ≠ 32 (e.g., empty bytes or 31/33 bytes) — attacker fully controls this field since it is simply an ABI `bytes` value in the payload they construct.
2. Relay this request as normal to the destination chain running the `hyper-fungible-token` pallet.
3. `Pallet::on_accept` executes; `substrate_data.signature` is `None`; since `source.is_evm() == false`, the code executes `account.copy_from_slice(from_bytes)` on a `from_bytes` slice whose length is not 32, causing an immediate panic/trap during message execution instead of returning a decode/validation error.
