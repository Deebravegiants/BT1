### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats the `shopify-shop-domain` HTTP header as the authenticated tenant identifier for an incoming webhook, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from unauthenticated headers and handed to the app's handler as trusted data, breaking the binding `hmac-verified bytes == identity used downstream`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it to the `hmac` header: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from separate, unsigned headers: [3](#0-2) 

`Registry.process` validates only the HMAC, then forwards `request.shop` unchanged to the app's webhook handler as the tenant identifier: [4](#0-3) 

The binding the gem is supposed to enforce is:
`shop_used_by_handler == shop_that_Shopify_actually_sent_the_signed_body_for`

In reality the gem enforces only:
`hmac_over(raw_body) == valid`

`shop` is never part of the signed material, so the two sides of the equality can diverge: any request whose body+HMAC pair is valid for the app's secret (e.g. a genuinely received webhook, including from a shop the attacker legitimately controls and installed the app on) can be replayed with the `shopify-shop-domain` header rewritten to any other shop domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` passes the attacker-chosen `shop` straight into `WebhookMetadata`, which host applications use to scope the corresponding tenant action (e.g. uninstall/deauthorize, subscription changes, data deletion, session/shop record lookups).

### Impact Explanation
This is a cross-tenant identity-binding break: a value (`shop`) that host apps rely on as the authenticated tenant for a webhook is not covered by the cryptographic check that gates webhook processing. An attacker who can obtain any one valid (body, hmac) pair for the app (trivially available to any merchant who installs the app, since many webhook topics carry generic/predictable bodies) can cause `Registry.process` to execute the handler with an arbitrary `shop` value of the attacker's choosing, i.e., impersonate another shop's webhook to the app. Depending on how the host app's handler uses `data.shop` (record lookup key, deauthorization trigger, billing state, etc.), this enables cross-tenant interference — matching the Critical "cross-tenant access" impact category, since the tenant boundary itself is what's being broken here.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that installs the gem's webhook processing as documented: the attacker only needs network access to the app's public webhook endpoint plus one legitimately-signed (body, hmac) pair from their own shop's webhook deliveries (no access token, `client_secret`, or privileged credentials required), then replay the body/HMAC while substituting the `x-shopify-shop-domain` header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content that is cryptographically bound to the HMAC check, or otherwise cryptographically bind the header-derived `shop` to the verified body (e.g., require the shop domain to appear inside the signed JSON body and cross-check it against the header before trusting either). At minimum, document that `request.shop` is unauthenticated header data and must not be treated as verified tenant identity by consuming applications until it is bound to the signed payload.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery for a topic with a static/predictable body (e.g. `{}`), together with its valid `x-shopify-hmac-sha256` value computed with the app's `client_secret`.
2. Attacker POSTs to the app's public webhook endpoint, reusing the exact `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body; `HmacValidator.validate` recomputes the HMAC over `@raw_body` only and it matches, so `Registry.process` proceeds: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, even though Shopify never sent this body for that shop — the app now performs whatever tenant-scoped action the handler takes, keyed off an attacker-controlled `shop`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
