Based on my investigation, this finding does not hold up.

**The claimed equality:** "signed payload executes ≤ 1 time, only on `envConfig.contractID`, never after invalidation" is broken by nonce predictability from a 15-byte `randomBytes` value with no entropy check.

**Why it doesn't break:**

1. **Contract binding is not nonce-derived.** `verifying_contract` is a separate signed field set by `IntentPayloadBuilder` to `this.envConfig.contractID` [1](#0-0)  — it is never derived from or influenced by the nonce bytes. A counterparty predicting nonce bytes gains no ability to redirect execution to a different contract, since the NEP-413 payload's `verifying_contract` is fixed by the SDK/integrator's own `envConfig`, not by nonce entropy.

2. **Single-execution guarantee is enforced on-chain, not by nonce entropy.** `encodeNonce` merely serializes salt + deadline + 15 bytes into a nonce string [2](#0-1) . Whether those bytes are predictable or fully random, the actual "used-once" guarantee is enforced by the `intents.near` contract's own nonce-consumption check when a payload is submitted — a signed payload with an already-consumed nonce is rejected by the contract, not executed twice. This is explicitly excluded as an out-of-scope trust assumption ("defects inside intents.near ... with no path through this repo").

3. **Predicting a nonce does not let a counterparty forge a valid signature.** Even if an attacker predicts the exact 27-byte nonce a victim will use, they cannot produce a validly signed `MultiPayload` for the victim's intent without the victim's private key — signature validity, not nonce secrecy, is what the contract checks to authorize execution.

4. **The "attacker-controlled data feeding nonce bytes" scenario requires integrator misuse.** The only way a counterparty's data enters nonce generation is via the documented escape hatches `setNonceRandomBytes` / `VersionedNonceBuilder.encodeNonce(randomBytes)` [3](#0-2) , which per the rules is an excluded scenario ("requiring the integrator to deliberately misuse a documented escape hatch").

5. **`invalidateNonces` race is not exploitable via nonce prediction.** `invalidateNonces` signs an empty intent using the exact same nonce string supplied by the caller [4](#0-3) ; the only way a third party could pre-empt or race this is again by controlling the original nonce bytes, which requires the same integrator-misuse precondition ruled out above. Whichever payload (the original intent or the invalidation) reaches the contract first consumes the nonce; the second is rejected by the contract's own nonce check, not "executed" — consistent with the invariant, not a break of it.

`withSaltRetry`'s handling of `INVALID_SALT` [5](#0-4)  and `SaltManager`'s TTL-based caching [6](#0-5)  only affect which salt is embedded in future nonces; they don't weaken the contract-side single-use nonce check either.

	export function encodeNonce(
		salt: Salt,
		deadline: Date,
		randomBytes: Uint8Array<ArrayBufferLike> = crypto.getRandomValues(
			new Uint8Array(RANDOM_BYTES_LENGTH),
		),
	): string {
		if (salt.length !== 4) {
			throw new Error(`Invalid salt length: ${salt.length}, expected 4`);
		}
		if (randomBytes.length !== RANDOM_BYTES_LENGTH) {
			throw new Error(
				`Invalid randomBytes length: ${randomBytes.length}, expected ${RANDOM_BYTES_LENGTH}`,
			);
		}

		const deadlineBigInt = BigInt(deadline.getTime()) * 1_000_000n;

		// Manual serialization of SaltedNonce
		// salt (4) + deadline (8) + nonce (15) = 27 bytes
		const borshBytes = new Uint8Array(27);

		// Salt
		borshBytes.set(salt, 0);

		// Deadline (u64 little endian)
		const view = new DataView(
			borshBytes.buffer,
			borshBytes.byteOffset,
			borshBytes.byteLength,
		);
		view.setBigUint64(4, deadlineBigInt, true);

		// Random bytes
		borshBytes.set(randomBytes, 12);

		// Serializing in full format: MAGIC_PREFIX (4) | VERSION (1) | NONCE_BYTES (27)
		const result = new Uint8Array(4 + 1 + borshBytes.length);
		result.set(VERSIONED_MAGIC_PREFIX, 0);
		result.set([LATEST_VERSION], 4);
		result.set(borshBytes, 5);

		return base64.encode(result);
	}

				// 1. Nonce's deadline (can't exceed this)

						const oneMinuteFromNow = new Date(Date.now() + DEFAULT_DEADLINE_MS);

export class SaltManager implements ISaltManager {
	protected intentsContract: string;
	protected nearProvider: providers.Provider;
	protected currentSalt: Salt | null = null;
	private fetchPromise: Promise<Salt> | null = null;
	private lastFetchTime = 0;

	constructor({
		envConfig,
		nearProvider,
	}: {
		envConfig: EnvConfig;
		nearProvider: providers.Provider;
	}) {
		this.intentsContract = envConfig.contractID;
		this.nearProvider = nearProvider;
	}

	/**
	 * Returns the cached salt if it's valid, otherwise fetches a new one
	 * Deduplicates concurrent requests so only one fetch runs at a time
	 */
	async getCachedSalt(): Promise<Salt> {
		if (this.isCacheValid()) {
			// biome-ignore lint/style/noNonNullAssertion: isCacheValid ensures currentSalt is set
			return this.currentSalt!;
		}

		if (this.fetchPromise) {
			return this.fetchPromise;
		}

		this.fetchPromise = this.fetchAndCache().finally(() => {
			this.fetchPromise = null;
		});

		return this.fetchPromise;
	}

	/**
	 * Fetches a new salt from the contract and updates the cache
	 */
	async refresh(): Promise<Salt> {
		this.invalidateCache();

		return this.getCachedSalt();
	}

	async fetchAndCache(): Promise<Salt> {
		try {
			const salt = await fetchSalt(this.nearProvider, this.intentsContract);

			this.currentSalt = salt;
			this.lastFetchTime = Date.now();

			return this.currentSalt;
		} catch (err) {
			this.fetchPromise = null;

			throw new Error(`Failed to fetch salt`, { cause: err });
		}
	}

	private isCacheValid(): boolean {
		return (
			this.currentSalt != null && Date.now() - this.lastFetchTime < SALT_TTL_MS
		);
	}

	private invalidateCache(): void {
		this.currentSalt = null;
		this.lastFetchTime = 0;
	}
