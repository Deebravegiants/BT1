### Title
Supply index accrual panics on `MathOverflow` once `supplied * supply_index` exceeds `i128`, permanently bricking the market and freezing all deposits - (File: common/src/rates/index.rs)

### Summary
Every state-changing pool entrypoint refreshes the market through `global_sync` → `accrue_step` → `update_supply_index`, which computes `supplied.mul(env, old_index)` — a checked `mul_div` that reverts with `GenericError::MathOverflow` when the total supplied RAY value no longer fits `i128`. A single unprivileged depositor can push the market's scaled `supplied` shares close to the `i128` boundary (the admitted cap domain allows RAY-scaled supply up to ~`i128::MAX`), after which the next tick of interest accrual overflows and every subsequent call on that market — including `withdraw`, `repay`, `liquidate`-driven `seize`, and `recapitalize` — reverts forever.

### Finding Description
`update_supply_index` computes the total supplied value before applying rewards:

```rust
// common/src/rates/index.rs:34
let total_supplied_value = supplied.mul(env, old_index);
```

`Ray::mul` resolves to `mul_div_floor`/`half_up` in `fp_core`, which widens to `I256` only for intermediates and still panics with `MathOverflow` when the *result* exceeds `i128` (`common/src/math/fp_core.rs:148-159`). There is no cap on `supplied` shares themselves: the only admission bound is `require_cap_within_asset_domain`, which permits caps up to `i128::MAX / 10^(27-d)` base units — i.e. a RAY-scaled supplied amount of roughly `i128::MAX` (`common/src/validation.rs:48-56`, `docs/reference/formulas.md:429-437` explicitly notes "value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first").

`accrue_chunk`/`accrue_step` is invoked unconditionally by `renewed_market` inside `Cache::renewed_market`/`ops::renewed_market`, which every pool op (`supply`, `withdraw`, `borrow`, `repay`, `seize`, `net_settle`, `flash_loan`, `claim_revenue`, `recapitalize`) calls before touching state (`contracts/pool/src/interest.rs:20-33`, `contracts/pool/src/ops/strategy.rs:66` uses the same `renewed_market`). Once `supplied * supply_index / RAY > i128::MAX`, `global_sync` panics before any logic runs — for all callers, permanently, since `supplied` cannot be reduced (withdrawal itself requires the same accrual).

Reachable path for a single unprivileged address:
- `Controller::supply(account, payments)` with a near-maximum deposit on a market whose cap admits it → scaled `supplied` ≈ `i128::MAX / RAY`-scaled near the boundary.
- One millisecond of accrual (any later caller's op, or the attacker's own `update_indexes`/`supply` dust call) pushes `supply_index` up by one tick via `accrue_step`.
- The product `supplied * new_index` now overflows → `MathOverflow` panic inside `global_sync` → the market is bricked; no supplier can withdraw, no borrower can repay, no liquidator can seize, and `recapitalize` cannot rescue it because it too goes through `renewed_market`.

Analog to CVE-2024-50305: a *valid* input (an in-domain deposit amount) drives the server/contract into a crash path that was not guarded on that path.

### Impact Explanation
Permanent freezing of funds for every supplier on the affected market, plus permanent insolvency of all outstanding borrows on it: interest accrual is a precondition of every exit, so no path reduces `supplied` after the overflow boundary is crossed. This satisfies "permanent freezing of funds" and "contract unable to operate."

### Likelihood Explanation
Reachable by any unprivileged address holding sufficient token balance — no governance action, oracle manipulation, or privileged call is required. The deposit must merely be within the admitted cap domain (`max_cap_for_decimals`), which is an explicitly "valid" parameter range. Accrual crossing the boundary is then guaranteed on the very next market interaction. The practical cost is large token value, but the vulnerability is deterministic once funded; markets with large caps and high-decimals assets are exposed.

### Recommendation
Clamp `total_supplied_value` in `update_supply_index` with a saturating multiply (e.g. `mul_div_floor_saturating`) or explicitly clamp `supplied` growth: enforce a global scaled-supply ceiling at supply time (`require_nonneg_amount`/`calculate_scaled_supply` site) so `supplied * MAX_SUPPLY_INDEX_RAY` always fits `i128`. Alternatively, make `global_sync` degrade gracefully (skip accrual / pin index) when the product would overflow instead of reverting, so exits remain possible.

### Proof of Concept
```rust
// 1. Attacker supplies near-cap amount on a high-cap market:
//    amount just below i128::MAX / 10^(27 - asset_decimals) base units.
//    After calculate_scaled_supply, supplied ≈ amount * 10^(27-d) * RAY / supply_index
//    ≈ i128::MAX-scaled RAY value.
//
// 2. Any later call that touches the market runs global_sync first:
//    accrue_step -> update_supply_index(supplied, supply_index', rewards)
//    -> supplied.mul(env, supply_index')
//       = mul_div(supplied_raw, supply_index'_raw, RAY)
//    With supplied_raw * supply_index'_raw / RAY > i128::MAX this panics
//    with GenericError::MathOverflow inside fp_core::mul_div_*.
//
// 3. Every subsequent controller/pool call on that (hub, token) book
//    (withdraw, repay, seize, flash_loan, claim_revenue, recapitalize)
//    invokes ops::renewed_market -> global_sync -> same panic.
//    No code path can reduce `supplied` anymore → permanent freeze.
```
