### Title
Unbounded swap routes can attach an unrelated wallet-token transfer beneath a user's signed controller authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary

`swap_collateral` accepts caller-supplied `swap` bytes after authorizing the account owner or delegate, then forwards those bytes to the configured router without restricting the route's venue addresses. [1](#0-0) [2](#0-1) 

The router decodes the payload-selected pool and invokes it through a venue adapter; a malicious venue implementation can perform an unrelated `token.transfer(victim, attacker, amount)` while still returning sufficient swap output. [3](#0-2) [4](#0-3) 

Simulation records that unrelated transfer as a child invocation under the victim's `swap_collateral` authorization, and enforcement accepts it if the victim signs the poisoned authorization tree. [5](#0-4) [6](#0-5) 

### Finding Description

The reachable entrypoint is `Controller::swap_collateral(caller, account_id, current, amount, new, swap)`, where `caller` is the victim account owner or delegate and `swap` is attacker-crafted route data. [7](#0-6) 

The controller authorizes only its own exact input-token transfer to the router, but that controller-side grant does not constrain unrelated user-authorization children introduced by code deeper in the route. [8](#0-7) [9](#0-8) 

The router derives each hop's `pool`, `token_in`, and `token_out` from the decoded route and dispatches the pool through the selected venue adapter. [10](#0-9) 

A malicious pool can therefore execute a `token.transfer` from the original caller to the attacker during its swap callback; the regression test demonstrates that this transfer becomes a sub-invocation beneath the caller's `swap_collateral` authorization. [11](#0-10) [12](#0-11) 

The measured-output and final-risk checks do not prevent this loss because they validate only the router's token input and output, not unrelated authorization children signed under the user's root invocation. [13](#0-12) [14](#0-13) 

### Impact Explanation

A victim who signs the simulated authorization tree can lose any unrelated wallet token selected by the malicious venue, while the lending collateral swap itself can still complete normally and pass all controller accounting checks. [15](#0-14) 

The exploit transfers assets already in the victim's wallet and is therefore theft of user funds, bounded by the amount and token chosen by the malicious route contract and the victim's available balance. [16](#0-15) [17](#0-16) 

### Likelihood Explanation

An unprivileged attacker can deploy a venue-compatible pool contract, embed its address in a route, prefund or otherwise arrange sufficient output, and convince a victim to submit the resulting `swap_collateral` transaction. [10](#0-9) [4](#0-3) 

The attack requires the victim to sign an authorization tree containing the hidden transfer, so it depends on spoofed or poorly presented transaction authorization rather than being a purely permissionless theft. [18](#0-17) [6](#0-5) 

### Recommendation

Restrict route venue contracts to governance-approved implementations or otherwise prevent arbitrary third-party contract code from executing below a user-authorized lending operation. [19](#0-18) [14](#0-13) 

Clients should additionally decode and display every authorization sub-invocation and reject a swap authorization containing any token transfer unrelated to the declared route, but this UI check should not be the protocol's only defense. [14](#0-13) 

### Proof of Concept

The test deploys a route whose `hop_pool` is an attacker-controlled contract configured with the victim, an unrelated wallet token, the attacker recipient, and the amount to steal. [20](#0-19) [21](#0-20) 

The victim invokes `try_swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)`, causing the router to invoke the malicious pool during the swap. [22](#0-21) 

Inside the pool's `swap` function, `token.transfer(victim, attacker, amount)` moves the victim's unrelated wallet token. [11](#0-10) 

Simulation records the malicious transfer as a sub-invocation under Alice's `swap_collateral` root, and signing that tree results in Alice's wallet balance becoming zero and the attacker receiving `WALLET_BALANCE`. [5](#0-4) 

The enforcing-auth test confirms that the same transaction succeeds when the signed tree includes the rogue transfer, while the collateral swap still deposits the expected ETH output. [6](#0-5)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
