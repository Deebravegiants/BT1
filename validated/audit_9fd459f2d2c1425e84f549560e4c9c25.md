## Title
CORS wildcard-origin bypass via naive suffix matching in Gateway HTTP server allowlist - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` matches wildcard CORS entries (e.g., `*.ethereum.org`) using `strings.HasSuffix(originHost, allowedHost)` without verifying a label/subdomain boundary. This lets an attacker-controlled domain such as `evilethereum.org` satisfy an allowlist entry intended only for genuine subdomains of `ethereum.org`.

## Finding Description
The relevant code is: [2](#0-1) 

`allowedHost` is derived by stripping the literal `*.` prefix, and matching is done via raw suffix comparison rather than checking for a `.` boundary. An attacker who registers `evilethereum.org` produces an `originHost` that ends with the literal string `ethereum.org`, satisfying `HasSuffix` despite not being a subdomain.

This is invoked from `handleRequest`, which reflects the origin verbatim into `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true: [3](#0-2) 

Wildcard CORS entries are a documented, supported configuration option (not test-only), as shown by sample configs and integration tests referencing `CORSAllowedOrigins`. Existing unit tests (`TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`) only check rejection of an origin that shares no suffix at all, never the boundary-less bypass case, so the flaw is untested and unguarded.

## Impact Explanation
When an operator uses the supported wildcard CORS feature (e.g., `*.ethereum.org`), an attacker registering a lookalike domain (`evilethereum.org`) can obtain a reflected `Access-Control-Allow-Origin` header from the gateway's internet-facing `UserServerConfig` endpoint. This allows a browser on the attacker's page to read cross-origin JSON-RPC responses from the gateway that were meant to be restricted to genuine subdomains, constituting an allowlist bypass / cross-origin response exposure in the gateway's request-handling path.

## Likelihood Explanation
Exploitation requires the operator to have configured a wildcard `CORSAllowedOrigins` entry — a documented, intended usage mode of the feature rather than a misuse — plus registration of a domain string that shares the allowed suffix, which is trivial and unrestricted. The victim need only visit the attacker's page while interacting with the gateway, consistent with the reference CVE-2017-14460 CORS-bypass vector. No node/operator credentials or privileged access are needed by the attacker.

## Recommendation
Enforce a proper label boundary in the wildcard branch, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
Add regression tests asserting domains like `evilethereum.org` are rejected against an `*.ethereum.org` allowlist entry.

## Proof of Concept
1. Configure `UserServerConfig` with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send a request to the gateway's user-facing endpoint with header `Origin: https://evilethereum.org`.
3. Observe `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilethereum.org", "ethereum.org")` is `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, allowing the attacker's page to read the cross-origin JSON-RPC response via browser JavaScript.
