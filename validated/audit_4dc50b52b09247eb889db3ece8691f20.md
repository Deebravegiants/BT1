### Title
Webhook shop identity spoofing via replay — HMAC covers only the raw body, not the `shopify-shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over that body alone before dispatching the webhook handler with `request.shop` taken from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a value that is never covered by the signature.

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` only [1](#0-0) , and `shop` is read straight from an HTTP header with no cryptographic binding to the signature [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body signature) and then immediately trusts `request.shop` as the tenant identity passed to the app's handler via `WebhookMetadata` [3](#0-2) . `HmacValidator.validate` / `validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string`, i.e. the body, and compare it to the received `hmac` field — the shop-domain header plays no role in that computation [4](#0-3) .

This breaks the intended binding `hmac_signed_bytes == tenant_identity_bytes`: the signature only proves "this body was produced by Shopify for *some* shop using this app's secret," not "this body belongs to shop X." Because a merchant that has installed the app is a legitimate recipient of correctly-HMAC'd webhooks for their own shop, that merchant (an otherwise unprivileged actor with respect to other tenants) can capture one of their own genuine webhook deliveries (raw body + valid `hmac`) and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. The signature still validates because it never inspected the shop header, and the app-provided handler will process the payload attributing it to the victim tenant (`WebhookMetadata#shop` used for tenant-scoped session/session-storage lookups, order/customer record writes, GDPR redaction flows, etc., depending on the app).

### Impact Explanation
This is a cross-tenant boundary break: an actor authorized only for their own shop's webhook traffic can cause the receiving application to process attacker-controlled bytes under a different, victim shop's identity. Any app that uses `request.shop` (or `WebhookMetadata#shop`) to select the tenant session, look up stored access tokens, or perform tenant-scoped writes (this is the documented usage pattern for `ShopifyAPI::Webhooks::Registry.process`) is exposed to cross-tenant data pollution or actions being misattributed to the wrong merchant's account.

### Likelihood Explanation
Reasonably likely: replay of an intercepted-by-design (the merchant is the intended recipient) webhook plus a header rewrite requires no possession of `api_secret_key` or any credential beyond having their own app installation generate one legitimate webhook delivery — something any merchant using the app can obtain trivially. No TLS interception, social engineering, or privileged access is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the bytes covered by the HMAC signature, or have `Registry.process` cross-check the header-derived `shop` against a value independently confirmed via an authenticated channel (e.g., correlate against the webhook id/subscription registered for that specific shop) before invoking the handler. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` must not be trusted as an authenticated tenant identifier without additional verification (e.g., binding processed webhook ids or event correlation to the originating shop through a side channel).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, capturing the raw body `B` and the resulting valid header `shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's real `api_secret_key`, which the attacker never sees but received a validly-signed message).
2. Attacker resends an HTTP request to the app's webhook endpoint with the same body `B`, the same `shopify-hmac-sha256: H`, `shopify-topic` unchanged, but `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Request.new` builds successfully since only the *presence* of headers is checked [5](#0-4) .
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and the app processes attacker-supplied payload `B` under the victim's tenant identity [7](#0-6) .

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
