### Title
Unchecked zero-length index into `incoming.request.body[0]` permanently blocks ISMP message delivery - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`ExtrinsicIntents.onAccept` reads the `RequestKind` discriminator by indexing `incoming.request.body[0]` without first checking that `body` is non-empty [1](#0-0) . Any counterparty-chain sender that can get a POST request routed to this contract (source authentication happens only *after* this line for the `NewDeployment`/`UpdateParams`/`SweepDust`/`Execute` branches, and the `RedeemEscrow`/`RefundEscrow` branch is authenticated even later) can submit a body of length 0 and force a Solidity array-bounds panic.

### Finding Description
The CVE describes an out-of-bounds read in PDFium caused by insufficiently validated length/offset handling when parsing an untrusted, attacker-supplied byte buffer. The analogous bug class here is unchecked indexing into attacker-controlled `bytes` before any length validation. In `onAccept`:

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    _checkRelayer(incoming.relayer);
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    ...
    // source is checked only here, AFTER the indexing above
    if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
``` [2](#0-1) 

`incoming.request.body` is fully attacker-controlled content originating from the source chain's dispatcher/application that targets this contract's address as `dest`; the host only verifies the message's inclusion in the finalized MMR/state commitment (`HandlerV2.handlePostRequests`), not that its body is well-formed [3](#0-2) . If `body.length == 0`, `body[0]` triggers Solidity's built-in array-out-of-bounds panic (`Panic(0x32)`), reverting the call before any authentication/authorization check can even run.

### Impact Explanation
`HandlerV2.handlePostRequests` iterates every leaf in the batch and calls `host.dispatchIncoming(leaf.request, ...)` in a plain loop with no per-leaf try/catch [4](#0-3) . A single malformed request targeting `ExtrinsicIntents` with an empty body will always revert `onAccept`, and therefore:
- Any batch that includes this poisoned leaf reverts entirely, blocking delivery of every other legitimate request/response bundled in the same MMR proof.
- Because the message is already committed in the finalized MMR leaf set on the source side, a relayer cannot skip it — every future delivery attempt (alone or batched) reverts identically, permanently freezing that request's processing and consuming relayer gas with no way to clear the receipt.

This matches the rule's "route unable to deliver messages" impact class: an unprivileged party can permanently deny delivery of ISMP messages destined for this contract (and any messages batched alongside them).

### Likelihood Explanation
High. No signature, proof forgery, or privileged role is required — any account or contract on a supported source chain that can dispatch an ISMP POST request with `dest` set to the `ExtrinsicIntents` address (the standard, permissionless cross-chain dispatch path) can set `body` to an empty byte string. The check ordering makes this trivially exploitable: `_checkRelayer` only validates the delivering relayer, not the request's own well-formedness, and the `source` authenticity check happens strictly after the vulnerable index.

### Recommendation
Validate `incoming.request.body.length > 0` (and, ideally, that the leading byte decodes to a defined `RequestKind`) before indexing, returning a clean revert/no-op rather than an uncontrolled panic; and/or wrap `host.dispatchIncoming` calls in `HandlerV2` batch loops with a try/catch so a single malformed leaf cannot revert delivery of the rest of the batch or permanently strand its own delivery.

### Proof of Concept
1. On a supported source chain, call the standard ISMP dispatch entry point (e.g., a `Dispatcher.dispatch`/equivalent POST) with `dest` = the `ExtrinsicIntents` contract address on the destination chain and `body = ""` (zero length).
2. Once finalized/committed into the source chain's state/MMR, a relayer submits `HandlerV2.handlePostRequests` with this leaf (alone or batched with others).
3. `EvmHost` calls `ExtrinsicIntents.onAccept`, which executes `RequestKind(uint8(incoming.request.body[0]))` on an empty `body`, causing a Solidity array-out-of-bounds panic that reverts the entire `handlePostRequests` transaction.
4. Every subsequent attempt to deliver this leaf (or any batch containing it) reverts identically — the message can never be delivered.
