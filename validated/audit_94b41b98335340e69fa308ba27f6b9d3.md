### Title
Unbounded debt-index accrual can permanently freeze a market before `MAX_BORROW_INDEX_RAY` - (`contracts/pool/src/cache/shares.rs`)

### Summary
An unprivileged borrower can create a sufficiently large debt position and leave it at sustained high utilization until `scaled_to_original` overflows `i128` during index accrual. Because pool operations accrue before processing the requested action, the market then rejects `update_indexes`, `repay`, `withdraw`, and liquidation with `MathOverflow`; the stored index remains below the intended `MAX_BORROW_INDEX_RAY` cap. [1](#0-0) [2](#0-1) 

### Finding Description
Scaled debt is converted back to token units through fixed-point multiplication by the accrued borrow index. The generic multiply-divide helper explicitly panics on division by zero, while other fixed-point paths panic on overflow rather than allowing a recoverable bounded result. [3](#0-2) [4](#0-3) 

The repository already demonstrates a reachable condition where a `1e18`-decimal market holding a `1e9`-unit principal and 98% debt utilization reaches the RAY-value ceiling before `MAX_BORROW_INDEX_RAY`. [5](#0-4)  The test advances `update_indexes` until the next accrual fails with `MATH_OVERFLOW`, then confirms that the committed borrow index remains below `MAX_BORROW_INDEX_RAY`. [6](#0-5) 

This is analogous to the incomplete-validation class because entry validation bounds the represented debt against caps at creation time, but does not establish that the debt remains representable after all permitted future index growth. The existing regression test notes that the index cap never engages before the value overflow. [7](#0-6) 

### Impact Explanation
The overflow is persistent rather than a single rejected transaction: each affected user action performs accrual first and therefore hits the same failure. The committed test explicitly observes that withdrawal and repayment fail after `update_indexes` begins failing. [8](#0-7) 

Once this state is reached, borrowers cannot reduce debt, suppliers cannot exit through that market, and liquidators cannot complete a path that needs the market’s accrued debt value. This is permanent freezing of the affected market’s funds absent an owner upgrade or other out-of-band recovery. [1](#0-0) [8](#0-7) 

### Likelihood Explanation
The attack path is permissionless but economically demanding: it requires creating an extremely large market, obtaining enough separate collateral to borrow near the tested 98% utilization, and waiting for accrual to grow the represented debt beyond `i128`. [5](#0-4) [9](#0-8) 

The tested setup disables ordinary utilization limits and lifts caps, so deployment parameters determine whether a listed market can actually reach this boundary. [10](#0-9)  Still, no privileged parameter mutation is required after market configuration, and `supply`, `borrow`, and `update_indexes` are callable by ordinary addresses. [11](#0-10) [12](#0-11) 

### Recommendation
Enforce a debt-cap invariant based on the maximum representable post-accrual value, not only the current scaled value. In practice:

- Compute the largest scaled debt `D` for which `D * MAX_BORROW_INDEX_RAY` remains within the protocol’s `i128`/`RAY` domain.
- Apply that bound in supply/borrow cap validation and whenever position or market debt grows.
- Before multiplying a scaled position by an accrued index, use a checked bound or clamp the index to the largest value that preserves representability.
- Ensure `MAX_BORROW_INDEX_RAY` is applied before attempting the overflowing `scaled_to_original` conversion, so capped markets remain serviceable instead of trapping all future calls.
