## Analog Vulnerability Found

### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its "signable string" from the raw request body only, while the shop identity (`shop-domain` header) and other routing fields (`topic`, `webhook-id`, `api-version`) are read directly from unauthenticated HTTP headers. `Registry.process` verifies only that the body's HMAC matches, then forwards the attacker-controllable `shop` header value straight to the app's webhook handler as the tenant identity. This reproduces the report's bug class: a field that is *acted on* (the shop the data is attributed to) is not actually covered by the cryptographic check that is supposed to bind it, exactly as `stake.left_ == key` in the OrchidDirectory report could never validate what it appeared to validate.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled from headers that are never included in that signable string: [2](#0-1) 

`HmacValidator.validate` only checks the HMAC of `to_signable_string` (the body) against the `hmac` header: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC check, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` object passed to the app-provided handler — with no additional binding between the verified body and the shop the app is told it belongs to: [4](#0-3) 

So the equality the code implicitly assumes — "HMAC-valid body" ⇔ "authenticated for the shop named in `shop-domain`" — does not hold, because `shop-domain` is not part of what the HMAC covers. Compare this to the OrchidDirectory bug: the condition looked like it validated a binding (`stake.left_ == key`) but structurally could never do so, letting an attacker-controlled state persist without the expected integrity link.

### Impact Explanation
Since the app's `api_secret_key` (client secret) is shared across every shop that installs the app, any merchant who has installed the app can trigger a legitimate webhook delivery to obtain a real `(body, hmac)` pair for their own shop, then POST that exact body/HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim shop). Because the header is never covered by the signature, `Registry.process` accepts it and hands the handler data tagged with the victim's shop domain. Any app logic keyed off `WebhookMetadata#shop` (e.g., writing/deleting per-tenant records, invalidating a victim's cache, triggering tenant-scoped side effects) is thus attributable to and executed for the wrong tenant — a cross-tenant impact reachable by an unprivileged internet user with no token or secret required.

### Likelihood Explanation
Any user who can install the target app on a Shopify development/trial store (freely available) can generate an arbitrary number of valid `(body, hmac)` pairs, then replay them directly to the app's webhook HTTP endpoint (which is public by definition, since Shopify itself must reach it over the internet) with a forged `shop-domain` header. No credentials, TLS interception, or privileged access are required — only network reachability to the app's webhook route, which this gem exposes to be reachable from Shopify's IPs but which enforces no additional source/tenant validation.

### Recommendation
Include the identity fields (`shop-domain`, `topic`, `webhook-id`) in the HMAC-signed payload verification, or independently verify that the `shop-domain` header corresponds to a shop with a currently valid, stored session/access token before dispatching to the handler, rather than trusting the header purely because the body's HMAC validated. At minimum, document and enforce that `WebhookMetadata#shop` must be cross-checked by the host app against its own tenant/session store — but the safer fix is for the gem itself to bind the shop to the verified request the same way `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` and `host` into its own signable string.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on their own shop "attacker.myshopify.com"
# and captures a real webhook delivery for a topic they control, e.g. "orders/create":
raw_body = '{"id":1,"note":"hi"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker now POSTs the exact same body/hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop they do not control:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # unchanged, still valid because body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, NOT covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Registry.process passes HMAC validation (body unchanged) and invokes the
#    registered handler with WebhookMetadata(shop: "victim-shop.myshopify.com", ...),
#    even though the request never actually originated from that shop.
```
