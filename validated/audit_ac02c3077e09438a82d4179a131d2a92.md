### Title
Emporium `EmporiumStack` signature never binds `circomData.relay` / fee token, letting an attacker redirect the wallet owner's signed `flatFee` to an arbitrary relay - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`verifyWallet` in `EmporiumUpgradeable.sol` only checks that `circomData.feeStructure.flatFee <= stack.maxFee`, and the EIP‑712 hash it recovers (`EMPORIUM_SIGNATURE_TYPEHASH`) only commits to `emporiumMessage`, the hash of `ops`, `maxFee`, and `deadline` — it never commits to `circomData.relay` or `circomData.feeStructure.feeToken/variableRate`. Since `circomData` is supplied fresh by whoever calls `Hinkal.transact` (not the wallet owner who only signed the `EmporiumStack`), an unprivileged attacker can submit the owner's valid signature together with an arbitrary `circomData.relay`, causing the wallet's fee (up to the signed `maxFee`) to be paid to the attacker's own address instead of any relay the owner intended.

### Finding Description
The invariant the question requires is: **(fee amount, fee destination)** paid out of the wallet must equal what the owner's EIP‑712 signature authorized. The signature only authorizes the fee **amount** (bounded by `maxFee`), never the **destination**.

- `EMPORIUM_SIGNATURE_TYPEHASH` = `EmporiumSignature(uint256 message, EmporiumOperation[] ops, uint256 maxFee, uint256 deadline)` [1](#0-0) 
- `verifyWallet` recovers the signer strictly over `(emporiumMessage, hash(ops), maxFee, deadline)` and only enforces `circomData.feeStructure.flatFee <= stack.maxFee` — it never reads or hashes `circomData.relay` or `circomData.feeStructure.feeToken`: [2](#0-1) 
- `runAction` calls `verifyWallet(stack, circomData)` and then `payRelayFees(circomData, stack.signerAddress, deltaAmountChanges)`, both driven by the **attacker-supplied** `circomData`, not anything the signature binds: [3](#0-2) 
- In `payRelayFees`, when `stack.signerAddress != address(0)` (the "Stateful Interaction"/wallet case), `relayFee = flatFee` (fixed, exactly the owner-approved amount) and is routed to `circomData.relay` via `payRelay` → `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)`: [4](#0-3) [5](#0-4) 
- `doSendToRelay` on the wallet has no restriction on `relay` beyond `onlyEmporium`, and unconditionally forwards funds to whatever `relay` address it's told: [6](#0-5) 
- There is no on-chain allow-list check for `circomData.relay` anywhere in this call path (no `isRelayInList` check inside `EmporiumUpgradeable.sol` or `Hinkal.sol`'s external-action path); `RelayStore.isRelayInList` exists but is not invoked by `payRelay`/`sendToRelayFromWallet`.

Because `circomData` (including `relay` and `feeStructure.feeToken`) is never part of the signed payload, and the ZK proof only constrains internal UTXO/amount arithmetic (not who ultimately receives `flatFee` from the wallet), an attacker who obtains/observes a valid, unexpired `EmporiumStack` signature (e.g., relayed off-chain, or the owner's own transaction they can front-run/resubmit before the legitimate relay does) can call `Hinkal.transact` themselves, supplying the identical `stack` (same `v,r,s`, `ops`, `maxFee`, `deadline`) but a `circomData.relay` set to their own address. `verifyWallet` still recovers the correct signer and passes because nothing about `relay` is checked against the signature. The wallet's `flatFee` (up to `maxFee`) is then sent to the attacker instead of the intended relay.

This is distinct from, and does not require, any Merkle-tree edge case; the "tree has exactly one prior leaf" condition from the question is not what enables this specific fee-destination diversion — the vulnerability exists independent of tree size, since `verifyWallet`/`payRelayFees` never touch `roots`/tree state at all.

### Impact Explanation
An attacker can permanently steal the relay fee (`feeStructure.flatFee`, bounded by the owner-signed `maxFee`) that was meant for a legitimate relay, by resubmitting/racing a valid `EmporiumStack` signature with `circomData.relay` pointed at themselves. This is theft of protocol/relay fees redirected to an unauthorized third party — matching the "High" category ("theft ... of protocol/relay fees ... executing calls or moving assets a wallet owner or prover never authorised"). It is repeatable for every `EmporiumStack` signature the attacker can observe or race before the intended relay consumes it (each `emporiumMessage` can only be used once due to `usedMessages`, so per-message it's a one-shot race, but it is repeatable across every new message/signature the owner produces).

### Likelihood Explanation
- Preconditions: attacker needs visibility into a valid, not-yet-used `EmporiumStack` (v,r,s, ops, maxFee, deadline) and the associated `emporiumMessage`/`circomData` fields that are not fee-destination-sensitive (these may be observable in the mempool, from a relay's public API, or from any front-end that shows pending fee-carrying actions before submission).
- No privileged role is required; any EOA can call `Hinkal.transact` with the intercepted `stack` and their own `circomData.relay`.
- Cost is only gas plus winning a race against the legitimate relay/owner submission (front-running), which is a well-known reproducible pattern.
- Repeatable per signed message: the `usedMessages[circomData.emporiumMessage]` guard only prevents replay of the *same* message, not redirection on first use.

### Recommendation
Bind `circomData.relay` (and ideally `feeStructure.feeToken`/`variableRate`, or at minimum the fee token) into the `EMPORIUM_SIGNATURE_TYPEHASH` that the wallet owner signs, so the owner explicitly authorizes both the fee amount and its destination/token. Alternatively/additionally, enforce that `circomData.relay` is a whitelisted relay (via `RelayStore.isRelayInList`) before `payRelay` forwards any wallet funds, so an arbitrary attacker address can never be a valid fee destination even without altering the signed payload.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, `HinkalWallet`, `RelayStore`/`HinkalHelper`, and a minimal `Hinkal` external-action wiring so `runAction` is reachable via `onlyAllowedRecipient`.
2. Have `owner` sign a valid `EmporiumStack` (`ops` = trivial no-op or single ETH transfer op, `maxFee = X`, `deadline` in future) via `vm.sign` using the `EMPORIUM_SIGNATURE_TYPEHASH` domain separator, with `signerAddress = ownerWallet`.
3. Construct `circomData` with `feeStructure.flatFee = X`, `feeStructure.feeToken = someToken`, and `relay = legitimateRelay`. Confirm via a "happy path" call that `runAction` sends `flatFee` to `legitimateRelay`.
4. Reset state (fresh `emporiumMessage`), rebuild an identical `EmporiumStack`/signature, but this time invoke `Hinkal.transact` → `EmporiumUpgradeable.runAction` with `circomData.relay = attacker`, everything else (`stack.v,r,s`, `maxFee`, `ops`, `deadline`) unchanged.
5. Assert:
   - Equality claimed by owner: `(fee amount, fee destination)` should equal `(flatFee, ownerIntendedRelay)`.
   - After step 4: `token.balanceOf(attacker)` increased by `flatFee`, `token.balanceOf(legitimateRelay)` unchanged, and `verifyWallet` did not revert (`InvalidSignature`/`FeeExceedsSignedMax` not thrown) — demonstrating the equality is broken: the destination the attacker chose was never part of what the owner signed, yet the transaction succeeded and moved owner funds to it.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
