### Title
Webhook `shop` field used for tenant identification is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used to route and identify webhook data purely from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` validates covers only the raw request body. `Webhooks::Registry.process` trusts this header-derived `shop` value when constructing `WebhookMetadata` passed to the app's handler, breaking the binding between "bytes verified by HMAC" and "the shop identity acted upon."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the host application's handler, with no cross-check that the shop value is consistent with anything cryptographically bound to the signed body: [4](#0-3) 

The identity binding that should hold is: `shop header == shop bound inside the HMAC-signed payload`. In this gem's implementation that equality never holds — the HMAC only proves "this body byte sequence was produced by someone holding `api_secret_key`," it proves nothing about which shop the header claims to represent.

### Impact Explanation
An attacker who owns any shop that has the app installed (an "unprivileged internet user" from the perspective of other tenants) legitimately receives real webhook deliveries — bodies with valid HMAC signatures — for their own shop's data. Because the `shop-domain` header is not part of the signed content, the attacker can capture one such genuine `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to a victim shop the attacker does not control. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that uses this gem's documented `shop` field to select the tenant record, session, or datastore to write into will process/attribute data under the wrong tenant — a cross-tenant integrity/confidentiality break rooted entirely in this gem's own `Request`/`Registry` implementation, not in host misuse.

### Likelihood Explanation
Any developer or malicious actor can install the app on their own store (a normal, unprivileged flow), capture the resulting genuine webhook HTTP request, and replay it with a modified `shop-domain` header against the app's public webhook endpoint. No access token, `client_secret`, or elevated privilege is needed — only an app installation, which is the standard entry point for any third-party developer.

### Recommendation
Bind the `shop` identity to the signed content rather than trusting an out-of-band header:
- Include the shop domain in the value that is HMAC-verified (e.g., verify it against the shop encoded in the JSON body, or require the host app to independently re-derive/verify the shop against a per-shop secret when multiple shops share one endpoint), or
- At minimum, document/enforce that `Registry.process` must be called per-shop with the expected shop pre-bound (e.g., pass an expected shop and raise if `request.shop` doesn't match), so the unauthenticated header can never silently override tenant identity.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST body plus its `X-Shopify-Hmac-Sha256` header — both are valid because Shopify itself signed them for the attacker's own shop.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:13-22) succeeds because it only checks `raw_body` against the HMAC.
4. `Webhooks::Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) invokes the handler with `WebhookMetadata` where `shop == "victim.myshopify.com"`, even though the payload actually originated from `attacker.myshopify.com`'s data — demonstrating the broken `shop`-to-signed-content binding.
