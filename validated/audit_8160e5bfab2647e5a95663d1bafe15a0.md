This confirms the vulnerability: the webhook handler's documented contract (`docs/usage/webhooks.md` line 14: `shop`, `String` - The shop domain of the webhook`) tells app developers to trust `data.shop` for tenant identification, but this field is sourced from an HTTP header that is never covered by the HMAC signature.

### Title
Webhook `shop` domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while the `shop` value returned to the handler is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, independent of the signed body [2](#0-1) . The HMAC is verified against `Context.api_secret_key`, which is the same shared secret for every shop/tenant using the app [3](#0-2) . The `Registry.process` method passes this unauthenticated `shop` value straight into `WebhookMetadata` for the app's handler to consume [4](#0-3) .

### Finding Description
The equality the gem is supposed to guarantee is:
`shop domain used by the app to attribute/act on webhook data == shop domain cryptographically bound to the HMAC-signed payload`

This equality does not hold. The HMAC only proves that `@raw_body` bytes were signed by an app holding `api_secret_key`; it says nothing about which header values accompanied that body. Because `api_secret_key` is shared across all shops installing the app (it is not a per-shop secret), any unprivileged actor who controls one shop installation of the app can:
1. Trigger a legitimate webhook from their own (attacker-controlled) shop, capturing a valid `(raw_body, hmac)` pair signed with the app's shared secret.
2. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. `Utils::HmacValidator.validate` still returns `true`, because the header is not part of `to_signable_string` [1](#0-0) [5](#0-4) .
4. `Registry.process` proceeds to call the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is the attacker-chosen victim domain [4](#0-3) .

The gem's own documentation instructs integrators to key their business logic (e.g., job enqueueing, DB lookups) directly off `data.shop` [6](#0-5) , so this unauthenticated field is the documented, intended tenant-identity binding — yet it is never cryptographically tied to the signed content.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker who is a legitimate (unprivileged) merchant/tenant of a multi-tenant Shopify app can forge webhook deliveries that the app attributes to a different, victim shop. Depending on how the host application uses `data.shop` (e.g., to look up which merchant record to update, uninstall, or process order/customer data for), this can lead to cross-tenant data corruption or processing of attacker-controlled payloads under a victim's identity — matching the "cross-tenant access" Critical impact category, since the gem's own contract exposes `shop` as the trusted tenant discriminator without binding it to the HMAC.

### Likelihood Explanation
Likelihood is high for any actor with a legitimate low-privilege app installation: no special credentials, no `api_secret_key` knowledge, no TLS interception, and no social engineering are required — only the ability to trigger one real webhook to their own shop and then send a modified HTTP request with a swapped header value.

### Recommendation
Include the `shop` domain (and ideally `topic`) as part of the signed payload/context that `Utils::HmacValidator` verifies, or otherwise cryptographically bind the `x-shopify-shop-domain` header to the signature (e.g., by having `to_signable_string` incorporate the header value, or by cross-checking `request.shop` against a shop stored/derived independently, such as a value embedded in the parsed body or a previously established session). Document clearly, or enforce in code, that `data.shop` cannot be trusted unless it is itself covered by the same HMAC that authenticates the body.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a real webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header value.
2. Attacker sends a POST to the app's webhook endpoint reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present) [7](#0-6) .
4. `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` never includes the `shop` header [1](#0-0) .
5. `Registry.process` invokes the app's handler with `data.shop == "victim-shop.myshopify.com"`, even though the request never originated from Shopify on behalf of that shop [4](#0-3) .

        end
