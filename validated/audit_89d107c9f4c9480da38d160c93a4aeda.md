Audit Report

## Title
Wildcard CORS `Access-Control-Allow-Origin` allowlist matching lacks a domain-boundary check, allowing attacker-controlled origins to receive credentialed gateway responses - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` strips the `*.` prefix from wildcard allowlist entries and then uses `strings.HasSuffix` on the raw host string without requiring a `.` label boundary. An attacker who registers a domain that merely ends with the configured suffix (e.g., `evil-ethereum.org` when `*.ethereum.org` is allowlisted) — without actually being a subdomain — will pass the check and have their `Origin` reflected into `Access-Control-Allow-Origin` by `handleRequest`.

## Finding Description
The vulnerable logic is: [1](#0-0) 

```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```

`strings.HasSuffix(originHost, allowedHost)` matches any string ending in the substring `"ethereum.org"`, including non-subdomains like `evil-ethereum.org` or `notethereum.org`. This result is consumed directly by `handleRequest`, which reflects the attacker-controlled `Origin` header into the `Access-Control-Allow-Origin` response header when `isAllowedOrigin` returns true: [2](#0-1) 

No other validation, allowlist normalization, or domain-boundary enforcement occurs elsewhere in the request pipeline for this check.

## Impact Explanation
This is a genuine CORS allowlist-bypass: an operator using a wildcard entry (a documented and tested configuration pattern, confirmed by `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`) unintentionally grants cross-origin read access to any domain sharing the suffix string, not just genuine subdomains. This maps to the in-scope "allowlist or subscription bypass" impact category and can expose gateway JSON-RPC response content to an attacker-controlled webpage via credentialed cross-origin reads.

## Likelihood Explanation
Exploitation requires: (1) the gateway operator to configure a wildcard CORS entry (supported, non-default, documented feature), and (2) the attacker to register a domain string that satisfies the naive suffix match but is not a true subdomain (e.g., `evil-ethereum.org`). Domain registration is trivial and requires no privileged access to the gateway itself; the existing test suite's negative-case tests (`TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`) do not cover this specific boundary-violation scenario, confirming the gap is untested and unmitigated in the current code.

## Recommendation
Change the suffix check to require a dot-boundary:
```go
if strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost {
    return true
}
```
Add negative test cases such as `evil-ethereum.org` and `notethereum.org` against `*.ethereum.org` to `core/services/gateway/network/httpserver_test.go` to lock in the corrected behavior.

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` (as in `startNewServer` in `core/services/gateway/network/httpserver_test.go`).
2. Send a POST request to the server with header `Origin: https://evil-ethereum.org`.
3. Observe the response contains `Access-Control-Allow-Origin: https://evil-ethereum.org`, even though `evil-ethereum.org` is not a subdomain of `ethereum.org`.
4. This can be added as a Go unit test modeled directly on the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`/`FromNotAllowedOriginWildcards` tests, asserting the header is empty (which it currently is not).
