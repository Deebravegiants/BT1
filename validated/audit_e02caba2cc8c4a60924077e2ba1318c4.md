### Title
Webhook HMAC Does Not Bind `Shop-Domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value straight from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` checks covers only the raw request body. Because the shop header is never mixed into the signed bytes, a previously captured valid `(body, hmac)` pair can be replayed against the app's webhook endpoint with an attacker-chosen `Shop-Domain` header and will still pass HMAC verification, letting an attacker attribute fabricated webhook data to an arbitrary victim shop.

### Finding Description
`Request#shop` reads the shop identifier directly from the header without any cryptographic binding: [1](#0-0) 

The signable string used for HMAC verification is only the raw body — it does not include the shop, topic, webhook id, or api version headers: [2](#0-1) 

`Registry.process` validates the HMAC over the request, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata passed to the app's handler, without any additional verification that these header values were what Shopify actually intended for this particular signed body: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. the body, and compares it to the `hmac` header — it has no visibility into `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The equality that should hold is:
`shop_header_used_for_attribution == shop_the_HMAC_was_computed_for`

but the gem only enforces:
`hmac(raw_body, secret) == received_hmac`

leaving `shop_header` completely outside the trust boundary established by the signature. Any request whose body+hmac pair is valid for *some* shop is accepted and re-attributed to whatever shop the attacker names in the header.

### Impact Explanation
This is a cross-tenant vulnerability: an attacker who obtains any single legitimate `(raw_body, hmac)` pair — trivially available by installing the app on a free/dev store they control and triggering any webhook (or a "send test notification") — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `ShopifyAPI::Webhooks::Registry.process` will pass HMAC validation and deliver the handler a `WebhookMetadata` claiming the data belongs to the victim shop, even though it never originated from that shop. Any host application logic that trusts `request.shop`/`WebhookMetadata#shop` for tenant-scoped writes (e.g. updating per-shop state, creating orders/customers records, redact processing) can be poisoned with attacker-controlled data attributed to an arbitrary victim tenant — a cross-tenant data-integrity/confusion attack requiring no credentials for the victim shop or the app.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is unauthenticated by design (protected only by HMAC), the attacker only needs one signed sample from any shop they can freely provision (a dev store), and replaying the request with a modified header is trivial for any unprivileged internet user with HTTP access to the app's public webhook URL.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload, or otherwise cryptographically bind them to the request (e.g., re-derive/confirm the shop from a value that is itself authenticated, or require the caller to separately verify the shop against a known session/registration before trusting the header). At minimum, `Request#to_signable_string` should incorporate the shop-domain header so that `HmacValidator.validate` fails if the header is altered independently of the body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they fully control) and triggers/receives any webhook, capturing the raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify using the app's real `client_secret`, which the attacker never needs to know).
2. Attacker sends a new POST request to the app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` (`Request#to_signable_string`) — the check passes because `B` and `H` are unchanged.
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to process attacker-controlled webhook data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
