### Title
Webhook shop-domain identity spoofing due to `shop` header not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop` value that the gem hands to the application's webhook handler is read from the `shopify-shop-domain` HTTP header, which is never included in the signed content. Any request bytes an attacker can freely choose (the shop-domain header) are trusted for tenant attribution while only a disjoint set of bytes (the body) is cryptographically verified — breaking the required equality `verified_bytes == shop_identity_bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def to_signable_string
  @raw_body
end
``` [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` recomputes and compares the signature exclusively over the body:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` gates on this HMAC check alone, then forwards the **unverified** `request.shop` straight to the app's handler as the tenant identity for the event:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that has installed the app, any unprivileged user can install the app on a store they control and legitimately trigger Shopify to send them webhooks with a **valid HMAC signature** for that body. Since the `shopify-shop-domain` header is not part of the signed material, that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to name a different (victim) shop. `Registry.process` will accept it as authentic (the HMAC still validates) and hand the handler a `WebhookMetadata` claiming the event originated from the victim shop — an identity binding that was never cryptographically established.

The binding that is violated, stated as an equality:
`shop attributed to the event by the gem (request.shop, unauthenticated header) == shop that produced/authorized the event (implied by the caller, cryptographically unverifiable)` — this equality does **not** hold, because only `hmac(raw_body)` is checked, not `hmac(raw_body ‖ shop)`.

### Impact Explanation
This crosses a tenant boundary: an attacker who only needs to install the target app on a store they legitimately control (an ordinary internet-user action, no credential leakage or privileged access needed) can forge webhook deliveries that the receiving application will process as if they came from an arbitrary victim shop. Any downstream logic that uses `WebhookMetadata#shop` to select which merchant's data/session/state to read or mutate (a common and expected usage per the gem's own webhook example) is exposed to cross-tenant data confusion/manipulation — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is installing the app once (or otherwise obtaining one genuine webhook body+HMAC pair for the attacker's own shop), which is trivial for any public/embeddable app and requires no secrets, tokens, or social engineering. The replay itself is a simple HTTP request with a modified header, fully within the unprivileged-internet-user threat model.

### Recommendation
Bind the shop identity into the verified material instead of trusting an unauthenticated header:
- Include the `shopify-shop-domain` (and ideally `webhook-id`/`api-version`) values in the string that is HMAC-verified (`to_signable_string`), matching them against the header-derived values before use, or
- Cross-check `request.shop` against an application-maintained record of shops that are expected to be able to send that `topic`/`webhook_id` (e.g., verify the webhook subscription belongs to the claimed shop) before invoking the handler, and
- Document/enforce that `Webhooks::Registry.process` must not expose `shop` to handlers without this additional binding.

### Proof of Concept
1. Attacker installs the target Shopify app on their own test store (`attacker-shop.myshopify.com`), a fully unprivileged, self-service action.
2. Attacker triggers any webhook-eligible event (e.g., updates a product) on their own store; Shopify sends the app's webhook endpoint a POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and resends the exact same request to the app's public webhook endpoint, but rewrites the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-derives the signature from `request.to_signable_string` (`= @raw_body = B`), so it validates successfully — the shop-domain header played no part in the check. [5](#0-4) 
5. The app's handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and processes/attributes the event to the victim shop, even though the victim never sent this webhook. [6](#0-5)
