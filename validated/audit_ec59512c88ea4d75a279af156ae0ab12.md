## Finding

### Title
Webhook shop/topic/webhook-id identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and identify the webhook are read straight from HTTP headers that are never included in that signed content. This breaks the identity binding `hmac(raw_body) == hmac(raw_body)` while `shop_header != authenticated_shop`, letting a value the app treats as an authenticated tenant identifier travel completely outside the cryptographic check.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it against the `hmac` reader with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from HTTP headers that play no role whatsoever in the HMAC computation: [3](#0-2) 

`Registry.process` validates the HMAC (i.e., proves the body bytes are Shopify-signed), then unconditionally trusts these unsigned header-derived fields to select the handler and to build the metadata delivered to app code: [4](#0-3) 

So the equality actually enforced is `hmac_header == HMAC(raw_body, api_secret_key)`, not `hmac_header == HMAC(raw_body ‖ shop ‖ topic, api_secret_key)`. Any request whose body/HMAC pair is a validly-signed pair for the shared `api_secret_key` will pass `validate()` regardless of what `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers say. In a multi-tenant app (one endpoint, one `api_secret_key`, many shops), an attacker who controls their own shop can subscribe to a webhook, receive a genuine Shopify-signed `(body, hmac)` pair for their own store, and then resend that exact body/HMAC pair to the app's shared webhook endpoint with the `shopify-shop-domain` header changed to a victim shop and/or the `shopify-topic`/`shopify-webhook-id` headers changed to target a different registered handler. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` then hands the handler a `WebhookMetadata` claiming the victim shop as the source: [5](#0-4) 

This is the same bug class as the reference report: a value that the code treats as authoritative (there, `max_loans_value` inside the per-collateral loop; here, the `shop`/`topic` identity used for routing and tenant attribution) is not actually covered/bound by the mechanism meant to protect it (there, the running accumulation; here, the HMAC signature), so downstream logic silently operates on the wrong value.

### Impact Explanation
Any app using this gem's webhook module for more than one shop under a single `api_secret_key` (the standard architecture for a public Shopify app) can have webhook payloads attributed to the wrong shop. Depending on the handler, this enables cross-tenant data injection or corruption (e.g., a victim shop's records get updated with attacker-controlled `orders/create`, `app/uninstalled`, or GDPR webhook content), satisfying the "cross-tenant access" Critical impact category, since the identity boundary between shops is enforced only by these unsigned, attacker-controllable headers.

### Likelihood Explanation
The attacker needs no credentials, tokens, or access to `api_secret_key`: they only need their own (or any) shop's webhook subscription to obtain one legitimately signed `(body, hmac)` pair, then can replay it with modified plain-text headers to the app's public webhook endpoint. This requires only unprivileged internet access to the endpoint and standard webhook subscription capability on an attacker-owned store.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed content checked against the HMAC, or otherwise cryptographically bind them (e.g., verify `shop` against a value looked up independently and trusted, such as validating the shop against pre-registered webhook subscriptions rather than trusting the header verbatim). At minimum, document that `Request#shop`/`#topic` are unauthenticated and must not be used as a tenant key without an independent verification step, and update `Registry.process` to cross-check the header-derived shop against server-side state (e.g., the shop that is known to have an active session/webhook registration) before dispatching to handlers.

### Proof of Concept
1. App `X` registers webhook handlers for `orders/create` and serves one shared endpoint for all installed shops, using `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker installs app `X` on their own store `attacker.myshopify.com` and triggers a real `orders/create` webhook, capturing the raw POST: headers (including a valid `x-shopify-hmac-sha256`) and body `B`.
3. Attacker resends the identical body `B` and `x-shopify-hmac-sha256` value to app `X`'s webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only hashes `B`, exactly as computed in [2](#0-1) .
5. `Registry.process` dispatches the attacker's order payload to the handler tagged with `shop: "victim.myshopify.com"`, as read directly from the spoofed header in [5](#0-4) , causing the app to act on victim-shop data using attacker-controlled content.
