### Title
Webhook shop/topic/webhook_id headers are trusted by the handler despite being outside the HMAC signature scope - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming HTTP webhook as fully authenticated once `Utils::HmacValidator.validate` succeeds, and then forwards `request.shop`, `request.topic`, and `request.webhook_id` — all values taken from unauthenticated HTTP headers — to the app's handler as trusted, verified metadata. The HMAC computed by `HmacValidator` only covers `request.to_signable_string`, which is defined as the raw JSON body, not the headers. This breaks the intended binding: "HMAC-verified bytes" == "the shop/topic this webhook is attributed to."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the signature strictly over `verifiable_query.to_signable_string`: [2](#0-1) 

Meanwhile, `Registry.process` uses `request.topic` to look up the handler and passes `request.shop`, `request.parsed_body`, `request.api_version`, and `request.webhook_id` — all read straight from HTTP headers via `shopify_header` — into `WebhookMetadata`, right after the single HMAC gate: [3](#0-2) 

`shop`, `topic`, `webhook_id`, and `api_version` are all sourced from headers, not the signed body: [4](#0-3) [5](#0-4) 

The equality that the code implicitly assumes is:
`bytes_verified_by_HMAC == bytes_the_handler_attributes_to(shop, topic, webhook_id)`

But in reality:
`bytes_verified_by_HMAC == raw_body_only`, while `shop`/`topic`/`webhook_id` come from headers that carry no cryptographic binding to that body or to each other.

Since the HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, any legitimately obtained `(raw_body, hmac)` pair — trivially obtainable by an unprivileged user who installs the app on their own store and captures one webhook delivery to their own publicly reachable endpoint — remains a **valid** signature for that exact body regardless of which shop, topic, or webhook id headers accompany it. An attacker can therefore replay that captured body+HMAC to the target app's public webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because only the byte-identical raw body is checked, and `Registry.process` hands the handler a `WebhookMetadata` object claiming the (attacker-chosen) victim shop as the source.

### Impact Explanation
Any application handler that keys its side effects (e.g., loading/updating a shop's stored session or business data, triggering merchant-specific state changes, or reconciling per-shop billing/inventory records) off `WebhookMetadata#shop` will process attacker-supplied body content under a victim shop's identity. This is a cross-tenant data-integrity/confusion vulnerability: the "verified" HMAC gives false assurance that both the payload and its attributed tenant are authentic, when only the payload bytes are actually authenticated. Depending on the handler's use of `shop`, this can escalate to cross-tenant data corruption or unauthorized state changes performed "as" another merchant — meeting the Critical, cross-tenant-access bar.

### Likelihood Explanation
Exploitation requires only:
1. The attacker installs the target app on their own store (a normal, unprivileged action any developer/merchant can take), or otherwise legitimately receives one webhook delivery.
2. The attacker captures the raw body and `X-Shopify-Hmac-Sha256` value of that delivery — trivial, since it is delivered in plaintext HTTPS to an endpoint the attacker controls.
3. The attacker replays that exact body + HMAC to the same app's public webhook endpoint with a forged `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header.

No access token, `api_secret_key`, or privileged account is needed — the HMAC secret used is the app-wide webhook secret, and knowledge of it is not required since the attacker replays a signature they already legitimately possess for their own data. Likelihood is high wherever the host application relies on `WebhookMetadata#shop`/`#topic` for tenant or business-logic routing, which is the documented, expected usage pattern shown in the gem's own webhook processing example.

### Recommendation
Include the header-derived identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., derive/verify the shop from an already-authenticated source such as an existing session lookup rather than trusting the header verbatim). At minimum, document that `Registry.process`'s HMAC check does not authenticate `request.shop`/`request.topic`/`request.webhook_id`, and require handlers to independently verify that the claimed shop is one that is actually expected/registered for that webhook subscription before acting on the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and configures/receives one HTTP webhook (e.g., `orders/create`) at an endpoint they control, capturing:
   - raw body `B`
   - header `X-Shopify-Hmac-Sha256: H` (valid because it's computed by Shopify using the app's shared `api_secret_key` over `B`)
2. Attacker sends a forged POST directly to the target app's real webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   Host: victim-app.example.com
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <any-id>

   B
   ```
3. `Webhooks::Request.new` parses the headers/body successfully (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `B` and `H` are a genuinely matching pair for the app's shared secret — the shop-domain header is never included in the signed string. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, and any logic keyed on `shop` operates as though `victim-shop.myshopify.com` genuinely sent payload `B`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
