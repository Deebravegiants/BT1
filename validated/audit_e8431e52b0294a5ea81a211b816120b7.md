### Title
Unbounded cyclic ancestry-chain traversal in GRANDPA finality verification can hang consensus processing - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`AncestryChain::ancestry` walks a linked list of relayer-supplied headers from a target block hash back to a base hash by repeatedly dereferencing each header's `parent_hash` field, with no cycle detection, no visited-set, and no depth bound. This is structurally the same bug class as CVE-2017-6505 (QEMU OHCI `ohci_service_ed_list`): an attacker-controlled linked list (there, USB endpoint descriptors; here, a set of headers keyed by their own hash but whose `parent_hash` pointers are fully attacker-chosen) can be crafted into a cycle that the traversal loop can never escape.

### Finding Description
`AncestryChain::new` builds a `BTreeMap<H::Hash, H>` from an arbitrary `Vec<H>` of headers supplied inside a GRANDPA `FinalityProof` (`unknown_headers`) or a justification's `votes_ancestries`, both of which are decoded directly from relayer-submitted consensus/fraud-proof messages. [1](#0-0) 

Each header is keyed by its own computed hash, but its `parent_hash` field is an attacker-controlled value inside that same decoded struct. `ancestry()` then walks:
```
let mut current_hash = block;
while current_hash != base {
    match self.ancestry.get(&current_hash) {
        Some(current_header) => {
            current_hash = *current_header.parent_hash();
            route.push(current_hash);
        },
        _ => return Err(finality_grandpa::Error::NotDescendent),
    };
}
``` [2](#0-1) 

If two or more submitted headers' `parent_hash` fields point at each other's hashes (forming a cycle within the attacker-chosen header set) and neither hash equals `base`, the loop never terminates: every lookup succeeds (the cycle members are all present in the map) so the `NotDescendent` error path is never reached, and `route` grows without bound while `current_hash` cycles forever. This mirrors the OHCI bug exactly: a linked structure walked by pointer without cycle detection, driven entirely by attacker-supplied "next" pointers.

This function is called from the core GRANDPA verification paths used to accept consensus updates and adjudicate fraud proofs — `verify_grandpa_finality_proof` and `verify_parachain_headers_with_grandpa_finality_proof`, which any relayer can trigger by submitting a consensus message: [3](#0-2) [4](#0-3) 

and also from `verify_fraud_proof`, reachable by anyone submitting two conflicting finality proofs: [5](#0-4) 

### Impact Explanation
Both `verify_grandpa_finality_proof` and `verify_fraud_proof` are invoked on-chain from pallet-ismp's consensus-message handling path, which is reachable by any unprivileged relayer submitting a GRANDPA consensus update or fraud proof. Because the loop has no depth cap and no cycle guard, a crafted `unknown_headers`/`votes_ancestries` set can make block execution hang inside this call for the duration of the transaction, consuming unbounded CPU within a single block's execution — a state-machine-halting condition for the affected route, since the relay/parachain consensus client for that chain can no longer make progress until the runtime is patched or the extrinsic is otherwise prevented from executing. This blocks all subsequent message delivery over the affected GRANDPA route.

### Likelihood Explanation
Constructing two or more headers whose `parent_hash` fields reference each other's hashes only requires crafting arbitrary header structs with attacker-chosen `parent_hash` values — this is trivial since `unknown_headers` and `votes_ancestries` are not otherwise validated to form a real chain before this traversal runs (that validation is effectively what `ancestry()` itself is trying to perform). No signatures over these specific header structs are required to build the cycle itself. Likelihood is high given a single relayer-submitted message can trigger it.

### Recommendation
Bound the traversal: track visited hashes in a `BTreeSet` and return `Err(NotDescendent)` (or a dedicated cycle error) if a hash is revisited, and/or cap `route.len()` at the number of entries in `self.ancestry` (since a valid, cycle-free ancestry path can never exceed the number of supplied headers). Reject the proof immediately once the cap is exceeded, similar to the `MAX_PROOF_DEPTH` guard already used in the Pharos SPV verifier.

### Proof of Concept
1. Craft `header_A` with `parent_hash = hash(header_B)`.
2. Craft `header_B` with `parent_hash = hash(header_A)`.
3. Submit a `FinalityProof` (or fraud-proof pair) with `unknown_headers = [header_A, header_B, ...]` such that `target = header_A` (or `header_B`) and `base` is any hash not equal to `hash(header_A)` or `hash(header_B)`.
4. Call into `verify_grandpa_finality_proof` (via the standard consensus-update extrinsic) or `verify_fraud_proof`; `AncestryChain::ancestry(base, target.hash())` enters `while current_hash != base` and cycles between `hash(header_A)` and `hash(header_B)` forever, since both are always found in the map and neither equals `base`.

Note: I could not fully trace every call site that invokes `verify_grandpa_finality_proof`/`verify_fraud_proof` from the runtime extrinsic dispatch layer (e.g., exact weight-metering behavior of the enclosing `pallet-ismp` unsigned extrinsic) due to tool-call limits reached before completing that trace — this should be confirmed by inspecting `modules/pallets/ismp` consensus-message dispatch and its extrinsic weight annotations to fully confirm whether block-level weight limits would truncate execution before the loop can cause a full hang, or whether this executes in an unmetered/off-chain-worker context.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;

				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
