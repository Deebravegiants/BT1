### Title
Repeated `hrmp_init_open_channel` + `hrmp_cancel_open_request` cycles bypass the intended per-session HRMP request cap and spam a target para's DMP queue - (File: polkadot/runtime/parachains/src/hrmp.rs)

### Summary
`Hrmp::init_open_channel` unconditionally enqueues an `HrmpNewChannelOpenRequest` downward message to the `recipient` para and increments `HrmpOpenChannelRequestCount` for the sender, while `Hrmp::cancel_open_request` only decrements that counter and unreserves the sender deposit — it does not, and cannot, retract the downward message that was already queued. Because cancellation frees the counter slot, `hrmp_max_parachain_outbound_channels` only limits the number of *concurrently pending* requests, not the cumulative number of open+cancel cycles (and therefore DMP notifications) a parachain origin can perform within a session. 

### Finding Description
`hrmp_init_open_channel` is dispatched with `ensure_parachain` origin (reachable by any live parachain via UMP `Transact`, the normal path parachains use to manage HRMP channels), and on success it (a) checks `HrmpOpenChannelRequestCount::<T>::get(&origin) < config.hrmp_max_parachain_outbound_channels`, (b) reserves `hrmp_sender_deposit` from the sender, (c) stores the pending request, (d) increments the sender's open-request counter, and (e) queues an `HrmpNewChannelOpenRequest` downward message to `recipient` via the DMP queuing path (`Dmp::queue_downward_message`). `hrmp_cancel_open_request` validates the caller is the sender or recipient of an unconfirmed pending request, then decrements the sender's (and possibly recipient's) open-request counter, removes the pending-request storage entry, and unreserves the deposit — it performs no compensating action against the downward message queue of `recipient`, because that message was already delivered/queued at step (e) above and is immutable relay-chain state once queued. 

Because the per-sender counter is decremented on cancellation, the "cap" `hrmp_max_parachain_outbound_channels` only bounds the number of simultaneously-open (unconfirmed) requests a parachain can have at any instant — it does not bound the total number of times a parachain can execute the init→cancel cycle within a single session/block window. An attacker-controlled parachain can therefore loop `init_open_channel(recipient) -> cancel_open_request(channel_id)` many more times than `hrmp_max_parachain_outbound_channels` within the same session, each iteration producing one additional `HrmpNewChannelOpenRequest` downward message into `recipient`'s DMQ, while the sender's own deposit is reserved and immediately unreserved each time (no net cost beyond transaction/weight fees). No channel is ever actually established (`process_hrmp_open_channel_requests`, run at session boundary, never sees a confirmed request because it's cancelled first), so the notifications are pure spam. 

### Impact Explanation
The scoped impact is queue-capacity consumption on the `recipient` para's downward message queue: each spam cycle inserts one message that the target para's runtime must process (or explicitly ignore) on its next block, consuming PoV/weight budget attributable to `recipient`, not to the attacker. This is a griefing/DoS vector against a specific target parachain's DMP processing, achievable purely through normal signed extrinsic/XCM `Transact` calls from any onboarded parachain, without ever forming a channel or losing the reserved deposit. 

### Likelihood Explanation
Preconditions are modest: the attacker needs control of any live, onboarded parachain (which can be obtained cheaply via on-demand coretime) capable of dispatching `Transact` XCM to the relay chain with `pallet-hrmp` calls — this is the exact mechanism parachains normally use to manage channels, so no special privilege beyond "being a parachain" is required. The attack is repeatable every block/session subject only to relay-chain block weight and transaction fee limits, which do not scale with the number of distinct spam messages sent to a single victim, so it is fully feasible and repeatable. 

### Recommendation
Track a separate, non-decrementing counter (or a time/session-windowed rate limiter) for the number of `init_open_channel` calls a parachain origin has made toward the same or any `recipient` within a session, independent of `HrmpOpenChannelRequestCount`, and reject further `hrmp_init_open_channel` calls once that limit is hit even if prior requests were cancelled. Alternatively, charge a non-refundable fee/deposit slice per notification sent (rather than a fully cancel-refundable deposit) so repeated cycles have a real economic cost proportional to DMQ load imposed on the victim. 

### Proof of Concept
Rust integration test in `polkadot/runtime/parachains/src/hrmp/tests.rs` style, or an `xcm-simulator` test:
1. Onboard attacker para `A` and victim para `B`; set `hrmp_max_parachain_outbound_channels = K` in config.
2. In a single session, loop `N > K` times: call `Hrmp::init_open_channel(A, B, ...)` then `Hrmp::cancel_open_request(A_or_B_origin, channel_id)`.
3. Assert after each iteration `HrmpOpenChannelRequestCount::<T>::get(&A) == 0` and the reserved deposit balance for `A` returns to its pre-call value (confirming no accounting drift).
4. Assert that `Dmp::DownwardMessageQueues::<T>::get(&B).len()` grows monotonically and reaches `N` (not bounded by `K`) after the loop, proving the notification count exceeds the nominal `hrmp_max_parachain_outbound_channels` cap.
5. Run `Initializer` session rotation and confirm `process_hrmp_open_channel_requests` establishes zero actual channels between `A` and `B`, confirming the spam is "channel-less."
