### Title
Webhook shop-domain and topic headers are unauthenticated — HMAC only signs `raw_body`, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Registry.process` validates covers exclusively the request body. The `shop`, `topic`, `api_version`, and `webhook_id` values, however, are all read straight from unauthenticated HTTP headers and are then trusted downstream to select the webhook handler and to identify which shop/tenant the event belongs to.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC over the raw body only, then immediately uses the unauthenticated `request.topic` to pick the handler and the unauthenticated `request.shop` to construct the `WebhookMetadata` passed to the handler: [3](#0-2) 

The equality that should hold is: `shop-that-signed-the-body == shop-attributed-to-the-event`. Because the signable string is `raw_body` alone, and the app's HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app (it is the app's `client_secret`, not a per-shop secret), any merchant who has installed the app can capture one of their own legitimate, correctly-signed webhook deliveries and replay it to the app's webhook endpoint after swapping only the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers. `HmacValidator.validate` still succeeds because it only recomputes over `raw_body`: [4](#0-3) 

The app then processes the (attacker-supplied-header) event as if it belonged to a different shop, or as if it were a different topic — for example forging a `shop/redact` / `customers/redact` mandatory-compliance event with a `shop-domain` header pointing at a victim tenant, causing the app's handler to redact/act on the victim shop's data using attacker-controlled headers and a body the attacker fully controls the framing of (only the raw bytes need to be a validly-signed body from *any* webhook the attacker previously received).

### Impact Explanation
This breaks the tenant boundary between two independent installs of the same app: an unprivileged merchant (any user who can install the app on their own store, which requires no special privilege) can cause the app to attribute webhook data/actions to a different shop. Depending on how the host app implements handlers (e.g., mandatory `shop/redact`, `customers/redact`, order/customer data handlers keyed off `WebhookMetadata#shop`), this can cause cross-tenant data corruption, unauthorized redaction, or processing of another merchant's data — matching the Critical cross-tenant access category.

### Likelihood Explanation
The attacker only needs to be a legitimate (but unprivileged, from the app's perspective) installer of the app to receive one genuine signed webhook, then can freely forge the `shop-domain`/`topic` headers on replay since those are not covered by `to_signable_string`. No access token, `client_secret`, or privileged access is required — this is directly reachable through this gem's own `HmacValidator`/`Registry.process` logic as implemented.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for verification (or otherwise cryptographically bind the headers used for routing/tenant-attribution to the same value the HMAC covers), so `Registry.process` cannot be tricked into attributing a validly-signed body to an arbitrary shop or topic via header manipulation.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify sends a webhook to the app with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: customers/redact`.
4. `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checked `raw_body`, per `lib/shopify_api/webhooks/request.rb` line 36-38.
5. `Registry.process` dispatches to the handler for the attacker-chosen topic with `shop: "victim-shop.myshopify.com"`, per `lib/shopify_api/webhooks/registry.rb` lines 188-199, letting the attacker act as/against `victim-shop` without ever compromising `victim-shop`'s credentials.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
