### Title
Division by zero in `IntrinsicIntents.sol` partial-fill escrow release reverts `fillOrder` when an order's output amount is zero - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The same-chain intent-fill path in `IntrinsicIntents.sol` computes the proportional escrow release for a partially-filled output pair as `(order.inputs[i].amount * fillAmount) / totalRequired`, where `totalRequired` is `order.output.assets[i].amount` — a value fully controlled by the order-placing user, with no non-zero validation at `placeOrder` time. If `totalRequired == 0` for any output asset entry and a solver supplies a non-zero `fillAmount` for that entry, `amountFilled` (`= alreadyFilled + fillAmount`) is not equal to `totalRequired` (`0`), so execution falls into the `else` branch and divides by zero, reverting the entire `fillOrder` transaction. This directly parallels the reported bug class ("Div by 0 can lead to accidentally revert" in an internal helper reachable from public functions) applied to Hyperbridge's IntentGateway fill path.

### Finding Description [1](#0-0) 

`amountFilled` is computed from the solver-supplied `fillAmount` and prior fills, and is compared against `totalRequired` (the order's declared required output amount for that token). When `amountFilled == totalRequired` the code uses the pre-recorded escrow balance directly (no division). Otherwise it computes a proportional release via integer division by `totalRequired`. There is no check anywhere in the fill path (or at order placement) guaranteeing `totalRequired > 0` — a user can construct an `Order` whose `output.assets[i].amount` is `0` for one of the token pairs, since only the input side and overall structure are validated at placement. A solver filling that specific pair with any non-zero amount forces the code down the division branch with a zero denominator, causing an EVM revert (division by zero causes a `Panic(0x12)`).

### Impact Explanation
This causes an unconditional revert of `fillOrder` for that order/token-pair, denying settlement/withdrawal of the escrowed input tokens tied to it. Because escrow release and downstream withdrawal (`_withdraw`) are blocked, the input tokens for that pair remain stuck in escrow until the order is separately cancelled via `cancelOrder`. This is a griefing/DoS vector against the fill mechanism of the intents contract, analogous to the C4 medium-severity finding: a division-by-zero causing accidental reverts in a path reachable from a public, unprivileged entry point (`fillOrder`), without requiring any privileged actor.

### Likelihood Explanation
Likelihood is limited to orders that intentionally or accidentally set a zero required output amount for one of multiple output token entries (multi-asset orders) — a single-asset order with `amount == 0` would be economically pointless and likely rejected by other invariants, but a multi-output order with one legitimate asset and one zero-amount decoy asset is plausible and not explicitly disallowed by `placeOrder`. As with the original C4 report, the judge's own assessment ("unlikely to be triggered in practice" but still real) applies here — the same reasoning that kept the original finding at Medium.

### Recommendation
Add an explicit zero-check before performing the division in the escrow-release branch (revert with a clear error, or fall back to the full-escrow-release path when `totalRequired == 0`), and/or validate at `placeOrder` that every `output.assets[i].amount` is non-zero, consistent with the recommendation given for the original Volt `Deviation.sol` div-by-zero.

### Proof of Concept
1. User calls `placeOrder` with an `Order` whose `output.assets` contains two entries: `{tokenA, amount: 1000e18}` and `{tokenB, amount: 0}`.
2. A solver calls `fillOrder` supplying a non-zero output amount for the `tokenB` entry (e.g., `1` wei), satisfying the "amount >= required" check since required is `0`.
3. Inside the fill loop, for that `tokenB` entry: `totalRequired = 0`, `fillAmount = 1`, so `amountFilled = 1 != totalRequired (0)`, forcing the `else` branch: `escrowedAmount = (order.inputs[i].amount * fillAmount) / 0` → reverts with a division-by-zero panic, aborting the whole `fillOrder` call (including any other legitimately-fillable output entries in the same transaction).
