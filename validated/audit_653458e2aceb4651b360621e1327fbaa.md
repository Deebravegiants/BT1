Based on my research, the bandwidth quota enforcement in `pallet-bandwidth` is intentionally, deliberately compiled out via the `no-bandwidth` feature flag on production (testnet) release builds of the Gargantua runtime.

#### Title
No-op bandwidth quota enforcement on production Gargantua release builds allows unmetered resource consumption - ([File: parachain/runtimes/gargantua/Cargo.toml])

#### Summary
The `pallet-bandwidth` gate is Hyperbridge's disk/bandwidth-quota analog: it meters per-`(source chain, app)` byte consumption on every non-purchase POST/GET request delivered through the router, rejecting messages once the prepaid allowance is exhausted [1](#0-0) . However, the `gargantua-runtime`'s `no-bandwidth` Cargo feature strips the `Bandwidth` pallet from `construct_runtime!` entirely and swaps the enforcement hook for a no-op `BandwidthGate`, and this feature is turned **on** by the project's own release build script for deployed (testnet) runtimes [2](#0-1) [3](#0-2) .

#### Finding Description
CVE-2016-0780 describes disk-quota enforcement that could be bypassed in certain code paths, letting an attacker consume unbounded DEA/CELL disk and starve other tenants. The Hyperbridge analog is the `pallet-bandwidth` gate, which is meant to be the sole rate-limiting mechanism standing between an unprivileged message dispatcher and unbounded free message delivery on a "managed" source chain — `BandwidthGate::try_consume` is consulted on **every** non-purchase POST request `on_accept` and on every GET response delivered through `pallet-state-coprocessor::handle_get_requests`, gating actual encoded-message-size consumption against a prepaid FIFO subscription ledger [4](#0-3) [5](#0-4) .

The `no-bandwidth` feature comment states plainly: "Turning this flag ON strips the pallet from the runtime: the `Bandwidth` entry is dropped, the gate becomes a no-op `BandwidthGate`, and none of the pallet's extrinsics are exposed. Release builds for testnet deployments enable this" [6](#0-5) . `scripts/build_release_runtime.sh` unconditionally sets this feature for `gargantua-runtime` release builds [7](#0-6) . With the flag active, `ProxyModule::on_accept` compiles out the entire gate-check block via `#[cfg(not(feature = "no-bandwidth"))]` [8](#0-7) , meaning any application/dispatcher on a managed source chain can flood the deployed runtime with arbitrarily large POST bodies with zero enforced byte budget.

#### Impact Explanation
This is a resource-exhaustion vector matching the CVE's bug class: an unprivileged actor (any app dispatching a message on a source chain routed through the affected runtime) can bypass the intended per-app metering entirely and dispatch unlimited message volume/size, consuming unbounded chain storage (request receipts, offchain MMR leaves, block proof space) and CPU for proof verification, at no cost — a route-level resource-exhaustion/DoS against other tenants sharing the runtime, consistent with "a route unable to deliver messages" for congested/starved apps.

#### Likelihood Explanation
This is not a hypothetical or attacker-forced misconfiguration — it is the project's documented, checked-in default behavior for release/testnet deployments (`scripts/build_release_runtime.sh` always passes `no-bandwidth` for `gargantua-runtime`). Any transaction reaching that deployed runtime automatically travels the unmetered path; no privileged action or governance error is required to trigger it.

#### Recommendation
Do not gate bandwidth enforcement behind a build-time feature that is force-enabled for release/production builds. If bandwidth metering is intended to be the production DoS control for Gargantua, remove `no-bandwidth` from the release build invocation (or invert the feature's default so enforcement is on unless explicitly and consciously disabled per-deployment), and add a CI/runtime assertion that production WASM artifacts are built without `no-bandwidth`.

#### Proof of Concept
1. Build the Gargantua runtime using the shipped script: `scripts/build_release_runtime.sh gargantua-runtime`, which passes `--features=metadata-hash,no-bandwidth`.
2. Deploy/observe that `construct_runtime!` omits the `Bandwidth` pallet and `ProxyModule::on_accept`'s bandwidth block is compiled out (`#[cfg(not(feature = "no-bandwidth"))]`).
3. From any unprivileged application on a managed source chain, dispatch repeated large POST messages via `IDispatcher.dispatch(...)`.
4. Observe none of these dispatches are checked against `BandwidthGate::try_consume`, and no `GateError::Insufficient`/`NoAllowance` is ever raised regardless of volume — unbounded free message throughput to the deployed runtime.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}

#!/bin/bash

set -euo pipefail

PACKAGE="$1"

# Gargantua release builds turn on the negatively-biased `no-bandwidth`
# flag so the `pallet-bandwidth` pallet is stripped from the deployed
# testnet runtime. The runtime keeps bandwidth on by default for local
# development; only release builds opt out.
if [ "$PACKAGE" = "gargantua-runtime" ]; then
    cargo build -p "$PACKAGE" --features=metadata-hash,no-bandwidth --release
else
    cargo build -p "$PACKAGE" --features=metadata-hash --release
fi
