### Title
Unchecked duplicate cosigner public keys in `#getMultisigAddress` allow a single cosigner to unilaterally satisfy the multisig signing threshold - (File: features/address-provider/module/address-provider.js)

### Summary
`AddressProvider#getMultisigAddress` builds the multisig spending script directly from the `cosigners` array stored in `multisigAtom`, with no check that the public keys derived from cosigners are distinct. Just like the Convergence `manageOwnedAndDelegated` bug where duplicate `tokenId`s let a delegatee multiply their voting share, a duplicate public key inserted into the `cosigners` list lets one keyholder occupy multiple "signer slots" in the resulting multisig/Taproot script, letting them satisfy the threshold alone.

### Finding Description
`#getMultisigAddress` reads the wallet's on-chain multisig configuration and, without deduplication, maps every cosigner with the `SIGNER_ROLE` to a raw public key that is fed straight into `asset.encodeMultisigContract(publicKeys, { threshold, ... })`: [1](#0-0) 

There is no assertion that the resulting `publicKeys` array contains unique keys before it is handed to `encodeMultisigContract`. If the `cosigners` list (which is populated from configuration data, e.g. via the referenced treasury-wallet cosigner-invite flow) contains the same `assetPublicKeys` entry more than once — for instance because a participant re-submits/duplicates their own key when the multisig wallet is being set up or a cosigner is re-added — the derived script will contain that one public key in two (or more) of the `threshold` signer slots.

This mirrors the referenced Sherlock report precisely: in the original bug, `manageOwnedAndDelegated` accepted an unchecked array of `tokenId`s and let a delegatee multiply their `_toPercentage` share by repeating the same id; here, the analogous unchecked array (`cosigners` → `publicKeys`) lets one signer occupy multiple slots of the `threshold`-of-`N` policy that other cosigners believe requires `threshold` *independent* approvals.

For Taproot `sortedmulti_a`/legacy multisig scripts, `OP_CHECKSIGADD`/`OP_CHECKMULTISIG` count one valid signature per listed public key slot. If the same public key appears in two slots, a single signature from that keyholder satisfies both slots, since the same signature verifies successfully against the same pubkey in each slot check.

### Impact Explanation
A multisig wallet is meant to require `threshold` independent cosigner approvals before funds move — this is the entire trust model of a shared/treasury wallet where no single participant is supposed to have unilateral custody. If duplicate public keys reach the `cosigners` array (e.g., a cosigner is added twice, or a participant supplies the same key for two different cosigner roles during setup), that single keyholder can single-handedly reach `threshold` and spend funds without any of the other cosigners' involvement. This is a direct, concrete unauthorized-signing / wallet-compromise impact matching the required bar: unauthorized movement of shared assets by an otherwise unprivileged cosigner.

### Likelihood Explanation
Reaching this requires only that the same public key end up twice in the `cosigners`/`assetPublicKeys` list that feeds `#getMultisigAddress` — no admin/owner privilege is needed, only participation as one of the (unprivileged) cosigners in a shared wallet setup/invite flow that populates `multisigAtom`. Because `#getMultisigAddress` never validates the derived `publicKeys` for duplicates before calling `encodeMultisigContract`, nothing in this code path prevents such a configuration from being accepted and used to derive real spending addresses.

### Recommendation
Before calling `asset.encodeMultisigContract`, assert that the derived `publicKeys` array (post role-filter, and preferably the whole `cosigners` list) contains only unique entries — e.g. compare `publicKeys.length` against `new Set(publicKeys.map(k => k.toString('hex'))).size` and throw if they differ. This should be enforced both when the multisig configuration is first written/updated and defensively inside `#getMultisigAddress` prior to script construction.

### Proof of Concept
1. Set up a 2-of-3 multisig wallet account with `multisigAtom` populated with `cosigners = [{ roles: [2], assetPublicKeys: A }, { roles: [2], assetPublicKeys: A }, { roles: [2], assetPublicKeys: B }]` (cosigner "A" listed twice, e.g. via a cosigner-invite flow that doesn't verify key uniqueness), `threshold: 2`, matching the test fixture pattern shown in [2](#0-1) .
2. Call `addressProvider.getAddress(...)` for that `walletAccount`; `#getMultisigAddress` produces `publicKeys = [A, A, B]` and derives a real spending address via `encodeMultisigContract([A, A, B], { threshold: 2, ... })`.
3. Keyholder "A" alone produces one signature; because the resulting script contains A's public key in two of the three signer slots, that single signature is valid for both A-slots, satisfying the `threshold: 2` requirement without any cooperation from cosigner "B" — allowing A to unilaterally spend funds from what was intended to be a 2-of-3 shared wallet.
