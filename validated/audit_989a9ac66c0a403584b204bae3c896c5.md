## Finding

This confirms an important asymmetry: `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before using the `shop` value to build the request host, but `Auth::Oauth.begin_auth` does **not** validate its `shop:` parameter at all before using it to construct the authorization redirect host.

### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` allows redirecting the OAuth authorization flow (and `client_id`/`redirect_uri`/`state`) to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth "authorize" URL by directly interpolating the caller-supplied `shop` into `auth_base_uri(shop)` (`"https://#{shop}/admin"`), with no call to `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing entry point in the same module tree (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, both of which call `Utils::ShopValidator.sanitize!(shop)` first). ### Finding Description
The gem's documented usage pattern for starting OAuth takes the shop identifier straight from an unauthenticated, attacker-influenced request value (e.g. a header), as shown in the gem's own docs (`shop = request.headers["Shop"]`), and passes it directly into `begin_auth`: [5](#0-4) 

Inside `begin_auth`, this raw `shop` is used, unsanitized, as the host of the OAuth authorize redirect: [6](#0-5) [7](#0-6) 

The equality that should hold is: `shop` used to build the OAuth "authorize" redirect host == a value validated to be a trusted Shopify domain (`Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`). Instead, `begin_auth`'s `shop` == raw, unvalidated caller input, breaking that binding. By contrast, `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` — which also build request hosts from a `shop:` argument and also embed `Context.api_secret_key` in the request body sent to that host — both enforce the equality via `Utils::ShopValidator.sanitize!(shop)` before use: [8](#0-7) [9](#0-8) 

`begin_auth` does not send `client_secret` (so this particular call site is not a `client_secret` leak), but it does place the app's `client_id`, `redirect_uri`, and freshly-generated CSRF `state` nonce into a URL whose host is entirely attacker-controlled, and that URL is the one the app instructs the browser to navigate to (`head 307` / `Location` in the docs' example): [10](#0-9) 

Because the resulting `state` cookie is set on the app's own domain and its value is echoed in the plaintext URL query string sent to the attacker's host, an attacker who supplies their own `shop` value learns the CSRF `state` nonce the victim's browser is about to carry, and controls where the "OAuth authorize" step is actually served from. `validate_auth_callback` does not bind `state` to a specific shop — it only compares the cookie value to `auth_query.state`: [11](#0-10) 

### Impact Explanation
This falls under "session fixation or forced OAuth completion" (High severity per the scope's impact list): an unvalidated `shop` in `begin_auth` lets an unprivileged caller/attacker redirect a victim's OAuth-initiation step to a host they control while the legitimate app still issues and stores a real CSRF `state` and cookie tied to its own domain. Because that `state` value is transmitted in cleartext to the attacker-chosen host, and the callback validation logic never re-associates `state` with the specific `shop` it was minted for, the primary CSRF protection the library relies on for `validate_auth_callback` (`state == auth_query.state`) is weakened to a bare token-known-to-attacker comparison in this flow. This does not by itself leak `client_secret` or an access token, but it directly undermines the state/nonce binding the library provides for other consumers (`ClientCredentials`, `RefreshToken`) via `ShopValidator`, and is inconsistent with the trust model the rest of the gem enforces.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the host application to pass a caller-influenced value into `begin_auth`'s `shop:` argument without its own validation — which is exactly the pattern shown in this gem's own documentation example (`shop = request.headers["Shop"]`), so a host app following the documented usage is directly exposed. No credentials, tokens, or privileged access are required to trigger it; a completely unauthenticated request can supply an arbitrary `shop` value.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain` with an explicit myshopify_domain check) inside `Oauth.begin_auth` before using `shop` to construct `auth_base_uri`, exactly as already done in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`. This restores the invariant that any host receiving the app's OAuth authorize request (and by extension the CSRF `state`) must be a member of `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Host app implements the documented pattern: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. Attacker sends a request with `Shop: attacker.evil-tld.com`.
3. `begin_auth` returns `auth_route = "https://attacker.evil-tld.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://legit-app.com/auth/callback&state=<nonce>&grant_options[]=..."`, and the app redirects the victim's browser there while setting the `state` cookie on `legit-app.com`.
4. `attacker.evil-tld.com` (controlled by the attacker) observes `client_id`, `redirect_uri`, and `state` in the incoming request.
5. Attacker leverages the captured `state` and `redirect_uri` to attempt forced OAuth completion / CSRF against `legit-app.com/auth/callback`, since the library's callback validation only checks `state == auth_query.state` without any binding to which host actually served the authorize step.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
