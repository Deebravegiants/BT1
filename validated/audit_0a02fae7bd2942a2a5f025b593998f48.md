### Title
PoA Bridge withdrawal status misattribution for batched same-asset withdrawals in a single transaction - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` looks up the withdrawal status by matching on `assetId` alone via `findMatchingWithdrawal()`, ignoring the caller-provided `index`. When a single NEAR transaction contains two or more `ft_withdraw` intents for the *same* `assetId` (e.g., two withdrawals of `nep141:btc.omft.near` to two different destination addresses/amounts in one batched intent), both `WithdrawalIdentifier` entries (`index: 0` and `index: 1`) resolve to the exact same status record from the POA bridge API.

### Finding Description
`createWithdrawalIdentifiers()` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` assigns a per-bridge-route `index` to each withdrawal in a batch [1](#0-0) . This `WithdrawalIdentifier` (with its `index`) is later passed to `bridge.describeWithdrawal()` to determine on-chain completion status and destination tx hash.

For the PoA bridge, however, `describeWithdrawal()` does not use `index` to disambiguate between multiple withdrawals returned by the bridge API for the same NEAR transaction hash. Instead it calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does a plain `.find()` by `assetId` only [2](#0-1) :

```
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
```

The function itself documents this exact limitation:
```
/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 ...
 */
``` [3](#0-2) 

Because `.find()` returns only the first array element matching `assetId`, if a batch contains two withdrawals of the same token to two different destination addresses/amounts, **both** `describeWithdrawal({index:0, ...})` and `describeWithdrawal({index:1, ...})` will resolve to the same underlying withdrawal record — same `status`, same `transfer_tx_hash`. There is no validation anywhere (`createWithdrawalIntents`, `validateWithdrawal`, `createWithdrawalIdentifiers`) that rejects or warns about duplicate `assetId` withdrawals routed through the PoA bridge in the same call.

This breaks the equality: *the withdrawal record reported as the outcome for withdrawal index N* should equal *the on-chain outcome for withdrawal N specifically*, but instead both withdrawals report the outcome of whichever record the API returns first.

### Impact Explanation
`watchWithdrawal()` (`packages/intents-sdk/src/core/withdrawal-watcher.ts`) resolves an integrator-facing promise with `{ hash: status.txHash }` based on this status [4](#0-3) . An integrator calling the SDK's batch withdrawal completion API (`sdk.createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion`, per `sdk.ts`) for two same-asset withdrawals in one transaction would receive:
- The same `txHash` reported as the destination transaction for both withdrawals, even though only one of them actually landed under that hash.
- If one withdrawal has completed and the other is still pending/failed on the bridge side, both will be reported with the completed one's status — i.e., a `"completed"` status is reported for a withdrawal that has not actually settled on-chain.

This matches the "status or hash misreport making an integrator credit or refund twice" impact class: an integrator (exchange, custodian, backend service) that credits a user's balance or marks a withdrawal request "done" based on this SDK status would incorrectly credit/close out the second withdrawal using the first withdrawal's transaction hash and completion status, potentially before the second withdrawal has actually landed, or attribute the wrong destination hash to the wrong withdrawal record entirely.

### Likelihood Explanation
This requires an ordinary (non-malicious) integrator use case: batching multiple withdrawal intents of the same asset in a single `signAndSendIntent` call, which the SDK's `createWithdrawalIntents`/`WithdrawalParams[]` batch API explicitly supports (see `withdrawal-watcher.ts`'s `createWithdrawalIdentifiers` accepting `withdrawalParams: WithdrawalParams[]`). No malicious actor or admin action is required — it is a normal batching pattern (e.g., processing a queue of pending BTC withdrawals together for gas efficiency) that silently produces incorrect status attribution. The code comment shows the authors were aware of the gap but did not add a guard to prevent or detect the unsupported case.

### Recommendation
- In `PoaBridge.describeWithdrawal()` / `findMatchingWithdrawal()`, detect when more than one withdrawal in the batch shares the same `assetId` for a given `tx.hash` and either: (a) disambiguate deterministically (e.g., sort both the API response and the withdrawal params by amount, as the existing comment suggests) and pick by relative position, or (b) throw an explicit unsupported-batch error at `createWithdrawalIntents`/`validateWithdrawal` time so integrators cannot silently trigger the misattribution.
- At minimum, add a runtime assertion in `createWithdrawalIdentifiers` (or in `PoaBridge.supports`/`validateWithdrawal`) that rejects batches containing duplicate `assetId` values routed to the PoA bridge, failing fast instead of returning ambiguous/incorrect status later.

### Proof of Concept
1. Call `sdk.signAndSendIntent` (or the withdrawal batching API) with two `WithdrawalParams` both using `assetId: "nep141:btc.omft.near"`, but different `destinationAddress`/`amount`, both routed to the PoA bridge, in the same NEAR transaction.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two withdrawals for route `RouteEnum.PoaBridge` [5](#0-4) .
3. Once the POA bridge indexes the tx, `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: tx.hash })` returns a `withdrawals` array containing (at least) two entries, both with `near_token_id: "btc.omft.near"`.
4. Call `bridge.describeWithdrawal({ ...wid0 })` and `bridge.describeWithdrawal({ ...wid1 })` — both invoke `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which `.find()`s the **first** matching element in both calls [6](#0-5) .
5. Both calls return the identical `{ status: "completed", txHash: withdrawal.data.transfer_tx_hash }`, even though the two withdrawals are for different destination addresses/amounts and only one of them may have actually settled to that `transfer_tx_hash`.

Note: I was not able to fully trace whether a higher-level guard in `sdk.ts` (e.g., in `createWithdrawalIntents`/`processWithdrawal`) rejects duplicate same-asset PoA withdrawals in one call — the grep results show `createWithdrawalIntents`/related methods in `sdk.ts` but I did not get to read the full method bodies before running out of iterations. If such a guard exists, it would need to be confirmed to fully close this gap; based on the code and comment reviewed, no such guard is currently present in the `PoaBridge` class itself.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
