## Analysis

The GitLab CVE describes a webhook feature that could be abused to trigger denial-of-service by having the server perform expensive external calls on attacker-controlled targets without adequate resource bounds. The closest analog in Hyperbridge is the fully permissionless external-call fan-out performed by `EvmHost.dispatchIncoming` when relayers batch-deliver POST requests via `HandlerV2.handlePostRequests`.

### Title
Unbounded gas forwarding to attacker-chosen `IApp.onAccept` destinations enables batch-delivery griefing/DoS - (File: `evm/src/core/EvmHost.sol`)

### Summary
Any account on any connected source chain can permissionlessly dispatch a POST request (via `IDispatcher.dispatch`) whose `to` field points at an attacker-deployed contract on the destination chain. When a relayer batches and delivers this request together with legitimate requests through `HandlerV2.handlePostRequests`, `EvmHost.dispatchIncoming` performs a raw `.call` to the attacker's contract forwarding essentially all remaining transaction gas, with no gas stipend/limit applied.

### Finding Description
`EvmHost.dispatchIncoming` executes: [1](#0-0) 

The call does not pass a bounded `gas:` value, so the callee (an arbitrary, attacker-controlled destination contract named in the original `PostRequest.to`, which is fully attacker-chosen since dispatch is permissionless) receives essentially all of the remaining gas of the relayer's transaction. Because `HandlerV2.handlePostRequests` processes a whole batch of requests in a single loop before returning: [2](#0-1) 

an attacker can dispatch a message destined for a malicious contract that consumes an unpredictable/near-maximal amount of gas inside `onAccept` (or reverts only after burning gas). Because the exact gas cost of `onAccept` is not knowable/boundable by the relayer ahead of time, and no per-call gas cap is enforced by the host, this can starve the gas budget for the remainder of the batch, causing the relayer's whole `handlePostRequests` transaction to run out of gas and revert — reverting the delivery of every other, unrelated, legitimate request bundled in the same batch. The same unbounded-gas pattern exists for `onGetResponse`, `onGetTimeout`, and `onPostRequestTimeout` dispatch paths in the same contract.

### Impact Explanation
This falls under "a route unable to deliver messages": a single attacker, at the cost of one cheap outgoing dispatch plus deploying a gas-griefing contract, can force relayers to either (a) fail entire batches (reverting legitimate deliveries and wasting relayer gas), or (b) stop batching multiple requests together to protect themselves, degrading throughput and increasing relaying cost for all users of the route. Because delivery is economically relayer-driven, repeated griefing can render a corridor practically undeliverable, which is a Medium/High-severity availability impact within the accepted impact classes.

### Likelihood Explanation
Likelihood is high: dispatching a POST request is a fully permissionless, single-transaction action available to any unprivileged user; no proof forgery, governance compromise, or privileged role is required. The attacker only needs to deploy a destination contract implementing `IApp.onAccept` with a gas-burning body and dispatch one request to it from any connected source chain, then wait for it to be batched by relayer software that batches multiple pending requests for gas efficiency.

### Recommendation
Bound the gas forwarded to `IApp` callbacks in `EvmHost.dispatchIncoming` (and the sibling `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` dispatch functions) with an explicit `gas:` stipend (e.g., a configurable `_hostParams.perByteFee`-like max callback gas parameter), so that a single malicious destination cannot consume more than its bounded share of the batch's gas, and failures beyond the stipend are treated the same as any other execution failure (receipt cleared, delivery retryable) without threatening the rest of the batch.

### Proof of Concept
1. Deploy `MaliciousApp` implementing `IApp.onAccept` that runs a gas-burning loop consuming close to the block gas limit before returning.
2. From any source chain, call `IDispatcher(_host).dispatch(DispatchPost{ dest: destChain, to: abi.encode(maliciousApp), body: "", timeout: 0, fee: 0, payer: attacker })`.
3. Wait until a relayer batches this request together with N legitimate pending POST requests and submits `HandlerV2.handlePostRequests` with a gas limit sized for the legitimate batch.
4. `EvmHost.dispatchIncoming` for the malicious leaf forwards nearly all remaining gas to `MaliciousApp.onAccept`, exhausting the gas budget before the loop can process the remaining legitimate leaves, causing the whole transaction to run out of gas and revert — none of the batched legitimate requests are delivered.     function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
