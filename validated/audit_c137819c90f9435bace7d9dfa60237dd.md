### Title
Unfiltered parachain state-commitment acceptance in `EcdsaBeefy.verifyParachainHeaderProof` — (File: `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
The Solidity BEEFY consensus client (`EcdsaBeefy.sol`) accepts and returns an `IntermediateState` for **every** parachain header included in a submitted MMR-leaf proof, keyed by the untrusted `para.id` field taken directly from proof calldata, with no allow-list check against the set of state machines this particular consensus client/host is meant to track. This mirrors the CVE-2015-1612 bug class: genuine, validly-signed protocol data (a real parachain's finalized header, correctly proven via merkle-multi-proof against the relay chain's authenticated parachain-heads root) is accepted and attributed to an identity/context (`stateMachineId`) the verifier never validated belongs to the trusted topology — exactly as reused/relayed LLDP frames let an attacker assert false adjacency using authentic-looking data taken out of its intended context.

### Finding Description
`EcdsaBeefy.verifyParachainHeaderProof` iterates over every `Parachain` entry supplied in `ParachainProof.parachains`, verifies each `(para.id, para.header)` pair's membership in the relay chain's `headsRoot` via `MerkleMultiProof.VerifyProof`, and unconditionally emits: [1](#0-0) 

There is no check equivalent to the Rust BEEFY client's `C::is_parachain_tracked(para_header.para_id)` filter, which explicitly restricts which `para_id`s are allowed to produce state-machine commitments for a given consensus client: [2](#0-1) 

Because the merkle-multi-proof only proves that `(para.id, para.header)` is a genuine leaf of the relay chain's authenticated parachain-heads tree — it says nothing about whether `para.id` is a state machine the deploying host/consensus-client configuration intends to trust — any caller can submit a proof containing an arbitrary *live, real* parachain's finalized header (data anyone can freely obtain from the relay chain, no privilege or compromise needed) and have `EcdsaBeefy.verify` return a completely valid `IntermediateState` for that parachain's id. Whatever the router/`EvmHost` layer does with that returned array (typically storing it as `_stateCommitments[stateMachineId][height]` for later state-proof verification via `HandlerV2`), the identity binding of "which foreign chains are legitimately reachable from this host" is only as strong as filtering that the codebase itself already recognizes is necessary elsewhere (see the GRANDPA client's `envelope_matches_state_machine`, added specifically to stop a "genuine ... proof submitted under [wrong] ... state machine [passing] verification and its ... state root [being] recorded under [the wrong] identity"): [3](#0-2) 

`EcdsaBeefy.sol`, unlike its Rust counterpart, contains no analogous per-`para.id` allow-list, so it is the one BEEFY verification path in this codebase missing the "is this state machine actually one we track" check that the rest of the protocol treats as mandatory hardening against exactly this bug class.

### Impact Explanation
If the calling host (`EvmHost` via `HandlerV2`/consensus router) does not itself re-filter the returned `IntermediateState[]` against a configured set of trusted/tracked state machine ids before persisting `_stateCommitments`, this allows state commitments for parachains the deployer never intended to bridge to be written into host storage. Once stored, `HandlerV2.handlePostRequests`/`handleGetResponses` trust `host.stateMachineCommitment(...)` as the root of truth for message-inclusion proofs: [4](#0-3) 
An attacker able to get an arbitrary tracked-relay-chain parachain's real state root accepted as a trusted commitment for a state-machine id the application logic (token bridge, intents, etc.) treats as authorized could forge message delivery (mint, intent fulfillment, etc.) by proving inclusion against that foreign chain's genuine trie, i.e. unbacked mint / forged message delivery — the class of impact this analog scan requires.

### Likelihood Explanation
Exploitability requires only a permissionless call submitting a genuine merkle-multi-proof of *any* live parachain's finalized header under the same relay chain BEEFY authority set already trusted by the consensus client — no signature forgery, no privileged role, no protocol compromise; this data is publicly obtainable from the relay chain. The only open question (which I could not fully confirm from the retrieved code) is whether `EvmHost`/the consensus router applies its own independent allow-list filter on `stateMachineId` before persisting commitments returned by `IConsensusV2.verify`; I found evidence of such filtering only on the Rust side (`is_parachain_tracked`), not in the Solidity `EvmHost`/`HandlerV2` consensus-update path I was able to inspect.

### Recommendation
Add an explicit allow-list check inside `EcdsaBeefy.verifyParachainHeaderProof` (or in the caller immediately after `IConsensusV2.verify` returns), mirroring `is_parachain_tracked` in the Rust BEEFY client, so that `IntermediateState`s are only emitted/persisted for `para.id`s the host/consensus client is explicitly configured to trust. Confirm and, if absent, add the same filtering on the `EvmHost`/`HandlerV2` side before writing to `_stateCommitments`.

### Proof of Concept
1. Identify any parachain `P` (with `para.id = X`) finalized under the same relay-chain BEEFY authority set that a target `EcdsaBeefy` instance trusts, where `X` is *not* one of the state machines the deploying protocol intends to support.
2. Fetch `P`'s finalized header and its merkle-multi-proof of inclusion in the current MMR leaf's parachain-heads root (public relay-chain RPC data — same construction as `verifyParachainHeaderProof`, `evm/src/consensus/EcdsaBeefy.sol:199-229`).
3. Submit this as `ParachainProof.parachains[0] = Parachain({index, id: X, header})` alongside a valid, unrelated `RelayChainProof` (any legitimately signed recent commitment) to `EcdsaBeefy.verify`.
4. Observe `verify` returns `IntermediateState{stateMachineId: X, height, commitment}` with `commitment.stateRoot` matching `P`'s real state root — despite the deploying protocol never configuring state machine `X` as trusted.
5. If the caller persists this without its own `X`-allow-list check, `X`'s state root is now usable to satisfy `HandlerV2.handlePostRequests`/`handleGetResponses` inclusion proofs, enabling forged/unauthorized message delivery purportedly "from" state machine `X`.

/// Whether the proof envelope a submitter chose is valid for the class of state
/// machine the trusted consensus state tracks.
///
/// The envelope is attacker-selected; the state machine is trusted. Every arm of
/// `verify_consensus` labels the header it just verified with that trusted identity, so
/// an unchecked pairing is a type confusion rather than a mere decoding quirk: a
/// parachain tracker's authority set *is* the relay's GRANDPA set, so a genuine
/// relay-chain finality proof submitted under `StandaloneChain` passes signature
/// verification and its **global** state root is then recorded under the parachain's
/// identity, at a relay height.
///
/// The accepted pairings mirror the mapping the honest producer already uses in
/// `tesseract/consensus/grandpa/src/host.rs`.
pub(crate) fn envelope_matches_state_machine(
	state_machine: &StateMachine,
	message: &ConsensusMessage,
) -> bool {
	matches!(
		(state_machine, message),
		(StateMachine::Polkadot(_) | StateMachine::Kusama(_), ConsensusMessage::Polkadot(_)) |
			(StateMachine::Relay { .. }, ConsensusMessage::Relaychain(_)) |
			(StateMachine::Substrate(_), ConsensusMessage::StandaloneChain(_))
	)
}
