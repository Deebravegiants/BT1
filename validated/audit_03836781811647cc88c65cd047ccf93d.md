### Title
Blacklisted creators can never claim their accrued USDC fees, permanently freezing funds in `FeeVault.claim()` - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` transfers a creator's entire pooled USDC balance to `msg.sender` with no way to redirect the payout to an alternate address. Because the accrued asset is real USDC — which enforces Circle's on-chain blocklist — any creator whose address becomes blacklisted can never receive the transfer, and there is no other path to extract the balance. The funds remain permanently locked in the vault.

### Finding Description
`claim()` computes the creator's balance and unconditionally transfers it to `msg.sender`: [1](#0-0) 

There is no parameter allowing the creator to specify a different recipient, unlike the pattern the original report recommends (separating the "rights holder" check from the "transfer destination"). The vault explicitly holds USDC: [2](#0-1) 

`Bonding.transferCreator()` lets a creator reassign the *creator* role for future fee attribution, but it only mutates `TokenInfo.creator` on `Bonding` — it does not move the already-accrued `creatorBalance[oldCreator]` inside `FeeVault`: [3](#0-2) 

So once fees have accrued to a creator address via `Zap`'s buy/sell flow calling `FeeVault.accrue(token, creator, ...)`: [4](#0-3) 

that balance is permanently keyed to the original creator address. If USDC's issuer later blocklists that address, `safeTransfer(msg.sender, amount)` inside `claim()` reverts every time it is attempted — the creator can never receive the funds, and no other address (including a new creator set via `transferCreator`) is authorized to pull the pre-existing `creatorBalance[oldCreator]`.

### Impact Explanation
This is a permanent freezing of creator funds: real, accrued USDC fees become forever unclaimable once the creator's address is blocklisted by the reserve asset's issuer, with no recovery path on-chain (no owner sweep for stuck creator balances, and `transferCreator` doesn't migrate the pooled balance). This matches the Medium-severity impact bar for permanent freezing of legitimate funds.

### Likelihood Explanation
Any token creator earns fees automatically on every buy/sell of their launched token via `Zap`'s 0.25% creator split, so simply creating a token and having it trade accrues USDC into `FeeVault.creatorBalance[creator]` — no special action required. The only additional condition is that the creator's specific address gets added to USDC's blocklist at some point before they call `claim()`, which is outside the protocol's control but a documented, real risk of using centrally-blocklistable stablecoins as the fee-settlement asset.

### Recommendation
Add an explicit "pay to" parameter to `claim()` (and analogously consider it for `claimProtocol()`), verifying authorization against `msg.sender` (or the accrued balance owner) but transferring to a caller-supplied destination address, e.g.:

```solidity
function claim(address to) external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(to, amount);
    emit CreatorFeesClaimed(msg.sender, to, amount);
}
```

Alternatively, add an owner-gated (or self-service) balance-migration function that lets a creator move their pooled `creatorBalance` to a new address before the old one becomes unusable.

### Proof of Concept
1. Address `C` launches a token via `Zap.createToken`, becoming `Bonding.tokenInfo(token).creator`.
2. Traders `buy`/`sell` the token; `Zap._executeBuy`/`_executeSell` route 0.25% of the fee to `FeeVault.accrue(token, C, creatorAmount, protocolAmount, isBuy)`, growing `creatorBalance[C]`.
3. USDC's issuer blocklists `C` (e.g., due to unrelated sanctions/compliance action).
4. `C` calls `FeeVault.claim()`. `$.usdc.safeTransfer(C, amount)` reverts because `C` is blocklisted; the whole transaction reverts, so `creatorBalance[C]` is never cleared but also never payable.
5. `C` calls `Bonding.transferCreator(token, newAddress)` to reassign future attribution — this has no effect on the existing `creatorBalance[C]` in `FeeVault`; `newAddress` cannot call `claim()` to retrieve it since `claim()` reads `creatorBalance[msg.sender]`, not `creatorBalance[oldCreator]`.
6. The USDC held for `C` in `FeeVault` (`creatorBalance[C]`) is permanently stranded with no recovery path.

        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }

All fees are charged by `Zap` in USDC and forwarded into `FeeVault`. The router holds no fee state — the vault is where balances live and where creators and the protocol claim.

- **Rate:** 0.75% on every buy/sell (curve **and** post-grad), split 0.5% protocol / 0.25% creator.
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
