### Title
TON Connect intent hash uses UTF-16 code-unit length instead of UTF-8 byte length for `domain_len`, causing `computeIntentHash` to diverge from the contract's hash for non-ASCII domains - (File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts)

### Summary
`computeTonConnectHash` builds the length-prefixed `domain` field using `domain.length` (JavaScript UTF-16 code-unit count) as the 4-byte big-endian length prefix, while the actual domain bytes appended are `TextEncoder().encode(domain)` (UTF-8 byte count). Per the TON Connect sign-data spec documented in the same file's comment, `domain_len` must equal the UTF-8 byte length of `domain`. For any domain containing non-ASCII characters (CJK, emoji, accented Latin, etc.), the two counts diverge, producing a different SHA-256 hash than the one the wallet/contract actually computes over the true byte layout.

### Finding Description
The broken equality is:

`computeIntentHash(multiPayload)` (locally computed via `computeSignedTonConnectHash` → `computeTonConnectHash`) **==** the `intent_hash` returned by the relayer/contract for the exact same `multiPayload`.

Code path:
- `computeIntentHash` (`packages/intents-sdk/src/intents/intent-hash.ts:68-73`) dispatches on `standard === "ton_connect"` to `computeSignedTonConnectHash`, which is a pass-through to `computeTonConnectHash` [1](#0-0) .
- Inside `computeTonConnectHash`, the message is built as: `0xffff + "ton-connect/sign-data/" + workchain(4) + address(32) + domain_len(4) + domain_bytes + timestamp(8) + type + payload_len(4) + payload_bytes`, matching the documented spec comment [2](#0-1) .
- The length prefix is computed from `domain.length` (UTF-16 code units), but the bytes actually appended are `new TextEncoder().encode(domain)` (UTF-8 bytes) [3](#0-2) .

For an ASCII-only domain (e.g. `"near.com"` in the existing test [4](#0-3) ), `domain.length === TextEncoder().encode(domain).length`, so the bug is invisible. As soon as `domain` contains any multi-byte UTF-8 character (2-4 bytes per code point, or a surrogate pair for characters outside the Basic Multilingual Plane), `domain.length` (code units) no longer equals the UTF-8 byte count, so the 4-byte length prefix baked into the hashed message is wrong relative to the actual byte stream that follows it. This shifts every subsequent field (`timestamp`, `payload_type`, `payload_len`, `payload`) in the conceptual byte layout that a correct implementation/verifier would reconstruct, producing a SHA-256 digest that differs from the one computed by a spec-compliant implementation (e.g. the actual near-intents contract or TON wallet) over the same logical payload.

The `domain` field flows into this function via `MultiPayloadTonConnect.domain: string` [5](#0-4) , with no ASCII-only or byte-length constraint in the JSON schema [6](#0-5) , and is populated straight from `signature.signatureData.domain` in `prepareSwapSignedData` with no sanitization [7](#0-6) . `computeIntentHash` is called on the freshly signed `multiPayload` right before publishing, specifically to hand to `onBeforePublishIntent` so integrators can persist the intent hash ahead of the relayer response [8](#0-7) . No validation, `assert`, or `supports()` gate anywhere in this path checks that `domain` is ASCII-only or re-derives the length correctly, so nothing prevents the divergence.

### Impact Explanation
An integrator that persists `intentHash` from `onBeforePublishIntent` and later reconciles it against the `intent_hash` returned by `publishIntent`/`waitForSettlement` for a `ton_connect`-signed intent with a non-ASCII `domain` will compute two different hash strings for what is actually the same signed intent. This is a hash/status misreport: the integrator's bookkeeping key (locally computed hash) will not match the protocol's real intent hash, which can cause the integrator to treat the intent as "unknown"/never-settled and resubmit it, or fail to detect settlement and hold/duplicate a user credit or refund — matching the High-severity category "a status or hash misreport making an integrator credit or refund twice" / "a withdrawal stuck until manual intervention." The bug is deterministic and repeatable on every `ton_connect` intent whose `domain` contains any non-ASCII character; it does not require a malicious relayer, RPC, or contract — it is a pure client-side computation defect.

### Likelihood Explanation
Preconditions are narrow but realistic: the intent must use `standard: "ton_connect"` and the `domain` string must contain at least one character outside the ASCII range (very plausible for internationalized dApp domains, e.g. IDN domains with non-Latin scripts, or any domain string containing non-ASCII text passed through by a counterparty/solver payload). No special privilege or cost is required — any caller providing such a `MultiPayload` (directly, or via a counterparty-supplied payload an integrator forwards through `signIntent`/`onBeforePublishIntent`) triggers the mismatch on every affected call, making it fully repeatable.

### Recommendation
Compute the length prefix from the actual encoded byte array rather than the JS string length:

```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```

Apply the same fix pattern check to any other length-prefixed string field to ensure byte-length (not UTF-16 code-unit length) is always used, and add a regression test with a non-ASCII domain.

### Proof of Concept
Vitest test in `packages/intents-sdk/src/intents/intent-hashes/ton-connect.test.ts`:

```ts
import { describe, expect, it } from "vitest";
import type { MultiPayload } from "@defuse-protocol/contract-types";
import { computeTonConnectHash } from "./ton-connect";
import { sha256 } from "@noble/hashes/sha2";

function numberToBigEndian(num: number, bytes: number): Uint8Array {
  const result = new Uint8Array(bytes);
  for (let i = bytes - 1; i >= 0; i--) {
    result[i] = num & 0xff;
    num >>= 8;
  }
  return result;
}

it("diverges from a spec-correct UTF-8-byte-length hash for non-ASCII domain", () => {
  const domain = "近.com"; // contains multi-byte UTF-8 chars; domain.length (2) !== UTF-8 byte length (5)
  const payload = {
    standard: "ton_connect",
    address: "UQBkxBWE4Gf9gd2sNbm1SJ6zXWnbA6ywoBvpAUQhBXJY_YiM",
    domain,
    timestamp: 1778685374,
    payload: { type: "text", text: "hello world" },
    public_key: "ed25519:99q8mY2bNRik43niUSKrXWsHGgmp9S6iG6VKmyta2Znj",
    signature: "ed25519:not-checked-by-hash-fn",
  } satisfies Extract<MultiPayload, { standard: "ton_connect" }>;

  const localHash = computeTonConnectHash(payload);

  // Reference hash built with the spec-correct UTF-8 byte length prefix
  const domainBytes = new TextEncoder().encode(domain);
  const addressBytes = /* parsed 32-byte workchain-0 address from parseTonAddress */ new Uint8Array(32); // filled via tryParseTonAddress in real test
  const payloadBytes = new TextEncoder().encode("hello world");
  const parts = [
    new Uint8Array([0xff, 0xff]),
    new TextEncoder().encode("ton-connect/sign-data/"),
    numberToBigEndian(0, 4),
    addressBytes,
    numberToBigEndian(domainBytes.length, 4), // correct: byte length, not domain.length
    domainBytes,
    numberToBigEndian(1778685374, 8),
    new TextEncoder().encode("txt"),
    numberToBigEndian(payloadBytes.length, 4),
    payloadBytes,
  ];
  const total = parts.reduce((s, p) => s + p.length, 0);
  const msg = new Uint8Array(total);
  let off = 0;
  for (const p of parts) { msg.set(p, off); off += p.length; }
  const referenceHash = sha256(msg);

  expect(localHash).not.toEqual(referenceHash); // proves computeIntentHash != contract-side/spec hash for this payload
});
```

This assertion demonstrates that for a domain with non-ASCII characters, `computeIntentHash(multiPayload)` (via `computeTonConnectHash`) does not equal the hash a spec-compliant implementation (or the contract) would compute over the same signed bytes, confirming the equality breaks exactly as described.
