### Title
`placeOrder`'s native-fee-to-token swap uses `block.timestamp` as the Uniswap deadline, providing no real deadline protection against stale/sandwiched execution - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
When a user calls `placeOrder` with `order.fees > 0` and pays the fee in native token, `IntentGatewayV2` swaps the supplied ETH into the fee token via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` (evaluated at execution time) as the deadline. Because `block.timestamp` is always "now" whenever the transaction is finally mined, this argument imposes no actual expiry — it is functionally equivalent to having no deadline at all, exactly the anti-pattern described in the referenced report. [1](#0-0) 

### Finding Description
`placeOrder` is a public, unprivileged entry point that any user can call while attaching native value to cover `order.fees`. In that code path: [2](#0-1) 

the router call is:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
```
`swapETHForExactTokens` requires exactly `order.fees` output tokens and consumes up to `msgValue` ETH as input, refunding any leftover ETH implicitly to `address(this)` (`msgValue -= amounts[0]`). No `amountInMax` bound is enforced beyond the attached `msg.value`, and — critically — the "deadline" parameter is `block.timestamp`, computed inside the transaction itself rather than a value chosen by the user ahead of time with a bounded window. This means:

- The deadline check inside Uniswap's router (`require(deadline >= block.timestamp)`) can never fail, since the deadline supplied is always equal to the block's own timestamp at execution.
- A transaction that sits in the mempool (or is deliberately delayed by a block builder/relayer) for an arbitrary period will still pass the deadline check when eventually included, no matter how stale the price expectations were when the user signed/submitted the transaction.
- This directly mirrors the reported bug class: a swap call lacking meaningful deadline enforcement is trivially sandwichable, and pending transactions can be executed long after intended, at an attacker-manipulated price.

Because the swap is exact-output (fee amount is fixed) and bounded only by `msg.value`, the practical impact of holding/sandwiching the transaction is that an attacker can manipulate the pool price to make `amounts[0]` (ETH spent) approach the full `msgValue`, extracting the difference from the user as MEV, before the swap executes. The lack of a caller-supplied, bounded deadline removes the last line of defense a legitimate deadline is meant to provide.

### Impact Explanation
This is reachable by any unprivileged user submitting a normal `placeOrder` transaction with `order.fees > 0` paid in native ETH — no special privileges required. A searcher/validator/relayer can:
1. Observe the pending `placeOrder` transaction in the mempool.
2. Manipulate the Uniswap V2 pool (front-run to move WETH→feeToken price unfavorably, back-run to restore it) or simply delay inclusion until the price is unfavorable.
3. Because the deadline is always satisfied (`block.timestamp == block.timestamp`), the swap still executes, consuming a larger share of the user's attached ETH (`amounts[0]`) than expected, reducing the ETH refunded to the user (`msgValue -= amounts[0]`), extracting value from the order placer.

This results in direct loss of user funds (excess ETH spent to acquire the fixed fee-token amount) on every `placeOrder` call that pays fees in native token, satisfying the "concrete theft ... of funds" criterion.

### Likelihood Explanation
High. `placeOrder` is a normal, permissionless user-facing entrypoint of the Intent Gateway, and paying fees with native ETH (triggering this swap) is a standard supported flow, not an edge case. No governance or privileged role is needed to trigger it — any user or bot repeatedly places orders with `msg.value` fee payment, and MEV searchers routinely monitor mempools for exactly this class of swap call.

### Recommendation
Replace `block.timestamp` with a genuine, bounded deadline supplied by the caller (or derived from a short, fixed window configured by governance, e.g., `block.timestamp + MAX_SWAP_WINDOW`) that is committed to before submission, not computed at execution time. Additionally, consider adding an explicit `amountInMax` slippage bound (rather than only relying on `msg.value`) so a manipulated pool price cannot silently consume the user's entire attached value.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` with `order.fees = X` (fee-token units) and attaches `msgValue` ETH sufficient to comfortably cover the current market price of `X` fee tokens.
2. The transaction enters the mempool; `IntentGatewayV2.placeOrder` will eventually call:
   ```solidity
   IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
       order.fees, path, address(this), block.timestamp
   );
   ``` [3](#0-2) 
3. An attacker sees the pending transaction and front-runs the WETH/feeToken pool to raise the feeToken price relative to ETH, then lets the victim's transaction execute (or is the block producer and simply delays inclusion), and back-runs to restore price.
4. Because `deadline == block.timestamp` at execution, the router's deadline check trivially passes regardless of when the transaction is actually mined, so the swap proceeds at the manipulated price.
5. `amounts[0]` (ETH spent) is now much larger than it would have been at the honest price, so `msgValue -= amounts[0]` leaves the user with a smaller ETH refund than expected — the difference is extracted by the attacker via the sandwich, with no deadline protection preventing the stale/manipulated execution.
