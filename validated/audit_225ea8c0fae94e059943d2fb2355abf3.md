### Title
Webhook `shop` identity is not covered by HMAC, allowing cross-tenant attribution of a validly-signed webhook body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop` (`X-Shopify-Shop-Domain`) header is read and trusted as the tenant identifier without being part of the signed material. Since the HMAC secret (`Context.api_secret_key`, the app's client secret) is the same for every shop that installs the app, any party who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on their own store and triggering a webhook) can replay that exact body to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` will report the request as valid, and `WebhookMetadata#shop` will carry the attacker-chosen shop domain into the host application's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` header and is never checked against, or folded into, the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the body alone: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to hand `request.shop` straight to the app's handler as the authenticated tenant: [4](#0-3) 

`WebhookMetadata#shop` is a plain, unauthenticated `String` field consumed by the host application's `WebhookHandler#handle`: [5](#0-4) 

The identity binding that should hold is: `shop reported in WebhookMetadata == shop that actually produced/owns the signed body`. Because `shop` is excluded from `to_signable_string`, this equality is never enforced by the gem. Any unprivileged internet user who can install the target app on their own shop (or otherwise capture one legitimate webhook delivery for any shop using the same app credentials) obtains a `(raw_body, hmac)` pair that remains valid under `HmacValidator.validate` regardless of which `shop-domain` header value is sent with it, because the secret (`api_secret_key`) is shared across every shop installation and the body is unrelated to the shop header. The attacker can then submit that captured body with a forged `shopify-shop-domain` header naming a victim shop; the gem will report the HMAC as valid and pass the victim shop's identifier plus the attacker's body content to the app's handler.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC check is meant to provide: a host application relying on this gem's "HMAC valid ⇒ shop and body are trustworthy together" guarantee will process attacker-supplied body content under a victim shop's identity. Depending on the webhook topic (e.g., `app/uninstalled`, `shop/update`, `customers/redact`, order/customer topics), this enables cross-tenant data corruption or triggering privileged per-shop side effects (e.g., app data deletion, entitlement changes) against a shop the attacker does not control, using only a webhook delivery they legitimately received for their own store. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is meaningfully high for an unprivileged actor: installing the target app on a free/dev store and triggering any webhook (many topics fire automatically on install, e.g. `app/uninstalled`, `shop/update`) is sufficient to obtain a valid `(body, hmac)` pair, since the client secret is identical for all installs of the same app. No access token, leaked credential, or privileged account is required — only the ability to send an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the material that is HMAC-verified, or otherwise cryptographically tie the claimed shop to the signed body before constructing `WebhookMetadata`. At minimum, `Request#to_signable_string` should not omit fields that downstream code (`WebhookMetadata#shop`) treats as authenticated, and `Registry.process` should not implicitly present `request.shop` as verified when only the body was checked.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, using the same app `client_id`/`client_secret` as any other merchant of this app.
2. Shopify delivers a webhook (e.g. `app/uninstalled`) to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw body>`, and a JSON body.
3. Attacker captures the raw body and HMAC value from this legitimate delivery.
4. Attacker sends a new POST to the same app endpoint, reusing the identical raw body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a request whose `hmac` method still reads the (still-valid) HMAC header, and `to_signable_string` returns the unchanged raw body: [6](#0-5) 
6. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the same raw body and secret and finds it matches — validation passes: [7](#0-6) 
7. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., the app's business logic processes attacker-controlled body content while believing it originated from `victim-shop.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
