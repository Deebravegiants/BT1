Confirmed. `WebhookMetadata.shop` is passed straight from `Request#shop` (the `x-shopify-shop-domain` header) into the handler with no cross-check against the HMAC-covered content.### Title
Webhook shop-domain spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, while the `shop` identity delivered to the app's handler is taken from an HTTP header that is never included in that HMAC. This breaks the equality the docs promise (`hmac == "request came from Shopify"` is treated as `shop == "the shop the webhook is about"`), letting an attacker splice a validly-signed body from one tenant with an arbitrary `shop-domain` header for another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then forwards `request.shop` unchanged into `WebhookMetadata`, which is handed to the app's handler as the tenant identity: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` const with no relation to the HMAC-verified bytes: [4](#0-3) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`/`old_api_secret_key`: [5](#0-4) 

The identity binding that should hold is: `shop header delivered to handler == shop that the HMAC-signed body actually pertains to`. Because the HMAC never covers the shop header, this equality is not enforced by the gem.

Critically, `api_secret_key` is the app's single client secret shared across **every** shop that has installed the app — it is not a per-tenant secret. An unprivileged attacker can install the target app on their own (attacker-controlled) shop, which is a normal, unprivileged action requiring no special credentials. Shopify will then send that attacker legitimately-signed webhooks (valid HMAC using the same shared `api_secret_key`) for events on the attacker's own shop. The attacker can take that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), and the handler receives `WebhookMetadata` claiming the event is for the victim shop while containing attacker-chosen body content, satisfying whatever fields the attacker wants inside the body (since the attacker fully controls the payload of webhooks fired against their own shop, e.g. `orders/create` custom note fields, product fields, etc., up to what Shopify includes for that topic).

The gem's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md, "Process a Webhook" section) with no caveat that the `shop` field is unauthenticated, so a reasonable app author would treat `data.shop` as a trustworthy tenant key for lookups such as "find the session/store for this shop and apply this webhook payload," which is exactly the field this vulnerability lets an attacker forge.

### Impact Explanation
This enables cross-tenant data confusion/spoofing: an attacker who has legitimately installed the app on their own shop can forge webhook deliveries that are attributed to a victim shop while carrying attacker-controlled body content (within the constraints of the topic's schema). If the host application uses `data.shop` to scope side effects (updating cached order/product data, triggering downstream automation, invalidating caches, writing audit logs, etc. keyed by shop), those side effects can be misattributed to or executed against the victim tenant. This matches the "cross-tenant access" class of Critical impact described in the rules, since the security boundary broken is the binding between the cryptographically-verified payload and the tenant it is delivered to.

### Likelihood Explanation
Likelihood is realistic but not universal: it requires (1) that the app be installable by arbitrary parties (true for public/marketplace apps), and (2) that the receiving application trust `data.shop` from `WebhookMetadata` for tenant-scoped logic without independently re-validating shop identity via, e.g., signed webhook subscription addresses or per-shop webhook IDs registered through `Registry`. Because the gem's own docs describe `process` as verifying the request "did indeed come from Shopify" without qualifying that `shop` is unauthenticated, many integrators are likely to rely on it directly, as shown by the sample handler in the docs which prints and forwards `data.shop` unquestioned.

### Recommendation
- Document explicitly (and ideally enforce) that `shop` in `WebhookMetadata` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier by itself.
- Where possible, bind webhook authenticity to a specific shop, e.g., by requiring the caller to pass the expected shop (from the session that registered the webhook) and comparing it against `request.shop`, or by including the shop domain in the signable string used for HMAC verification if/when a shop-scoped secret or webhook-specific token is available.
- At minimum, surface a warning/error path in `Registry.process` when a caller expects a specific shop but the header-derived shop diverges from any registered expectation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing normal OAuth (no privileged access needed).
2. Attacker triggers an event that causes Shopify to send a legitimate webhook to the app's endpoint, e.g. `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over raw body, computed by Shopify with the app's shared api_secret_key>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
   raw body: attacker-controlled order JSON (attacker created this order themselves).
3. Attacker captures `(raw_body, x-shopify-hmac-sha256)` and re-sends an HTTP POST directly to the app's webhook endpoint, keeping `raw_body` and the HMAC header identical, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds, since the body and secret are unchanged: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled order JSON>, ...)`, and any tenant-scoped logic in the host app now believes this attacker-crafted event pertains to the victim shop.
