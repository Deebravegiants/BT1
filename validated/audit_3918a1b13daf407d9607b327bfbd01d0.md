### Title
Withdraw slippage protection is silently bypassed unless both `min_coin_amount` and `min_pc_amount` are set, exposing LPs to sandwich attacks - (File: `program/src/processor.rs`)

### Summary
The `Withdraw` instruction lets a liquidity provider redeem LP tokens for pool coin/pc tokens, optionally specifying `min_coin_amount` and `min_pc_amount` to protect against price movement (i.e., a "minimum-amount-out" equivalent for LP withdrawals). The check that enforces this protection is only executed when **both** values are `Some`; if either one is `None`, the check is skipped entirely and the withdrawal proceeds with no slippage protection, mirroring the "hard-coded zero minimum-amount-out" flaw described in the external report.

### Finding Description
`WithdrawInstruction` carries `min_coin_amount: Option<u64>` and `min_pc_amount: Option<u64>` [1](#0-0) . During unpacking, if the instruction payload is short (fewer than 16 extra bytes), both fields default to `None` rather than failing [2](#0-1) .

In `process_withdraw`, the slippage check is guarded by a logical AND over `is_some()` for both fields:
```rust
if coin_amount < amm_coin_vault.amount && pc_amount < amm_pc_vault.amount {
    if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some() {
        if withdraw.min_coin_amount.unwrap() > coin_amount
            || withdraw.min_pc_amount.unwrap() > pc_amount
        {
            return Err(AmmError::ExceededSlippage.into());
        }
    }
    Invokers::token_transfer_with_authority(...); // coin payout, no check applied
    Invokers::token_transfer_with_authority(...); // pc payout, no check applied
    ...
}
``` [3](#0-2) 

This means an attacker-visible transaction supplying only one of the two minimums (e.g. `min_coin_amount = Some(x)`, `min_pc_amount = None`) — or an SDK/client that only populates one side — causes the entire slippage guard to be skipped, exactly as if both had been hard-coded to `None`/zero. There is no other minimum-out enforcement anywhere else in the withdrawal path before tokens are transferred out via `Invokers::token_transfer_with_authority`.

### Impact Explanation
Because the withdrawal payout amounts (`coin_amount`, `pc_amount`) are derived from the pool's live `total_pc_without_take_pnl`/`total_coin_without_take_pnl` at execution time [4](#0-3) , an attacker can sandwich a victim's `Withdraw` transaction: front-run with a swap that skews the coin/pc ratio, let the victim's withdrawal execute at the skewed ratio (silently unprotected because the min-amount AND-gate is bypassed), then back-run to restore the ratio and pocket the difference. This results in concrete loss of LP funds during redemption, matching the theft-of-user-funds impact bar.

### Likelihood Explanation
The `Withdraw` instruction is reachable by any unprivileged LP in a single transaction with attacker/user-chosen instruction data; the only requirement to trigger the bypass is supplying `None` for one of the two `Option<u64>` fields (or using a short/legacy-format instruction payload), which is a normal, low-effort client behavior, not an edge case requiring special access.

### Recommendation
Change the guard so slippage is enforced independently per side (or require both to be present, rejecting the instruction otherwise), e.g.:
```rust
if let Some(min_coin) = withdraw.min_coin_amount {
    if min_coin > coin_amount { return Err(AmmError::ExceededSlippage.into()); }
}
if let Some(min_pc) = withdraw.min_pc_amount {
    if min_pc > pc_amount { return Err(AmmError::ExceededSlippage.into()); }
}
```
This ensures that specifying only one minimum still provides protection for that side, removing the silent full-bypass condition.

### Proof of Concept
1. LP holds LP tokens for pool `P` (coin/pc reserves `Rc`, `Rp`).
2. LP submits `Withdraw { amount, min_coin_amount: Some(expected_coin), min_pc_amount: None }` expecting partial protection.
3. Attacker front-runs with a large swap that shifts `Rc`/`Rp` unfavorably for the LP’s payout ratio.
4. `process_withdraw` computes `coin_amount`/`pc_amount` from the skewed reserves; since `min_pc_amount.is_some()` is `false`, the entire `if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` block is skipped — no revert occurs even though `coin_amount` may still satisfy `min_coin_amount` while `pc_amount` is far below fair value.
5. Tokens are transferred at the unfavorable rate [5](#0-4) , LP tokens are burned, and the attacker back-runs to restore the pool ratio, capturing the LP's loss as arbitrage profit.
