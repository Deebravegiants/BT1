Confirmed: `ValidateOwnerReferences` in `staging/src/k8s.io/apimachinery/pkg/api/validation/objectmeta.go` (lines 97-114) does not check for duplicate UIDs across owner references — it only validates individual field presence and that at most one `Controller: true` ref exists. Nothing prevents an object from persisting two `ownerReferences` entries with identical `UID` but different `Kind`/`Name`/`APIVersion`.

### Title
`indexByUID` collapses duplicate-UID ownerReferences, allowing bypass of blockOwnerDeletion finalizers authorization check - (File: plugin/pkg/admission/gc/gc_admission.go)

### Summary
`indexByUID` builds a `map[types.UID]metav1.OwnerReference` from the old object's owner references, silently overwriting entries that share a UID. Since `ValidateOwnerReferences` never rejects duplicate UIDs, an attacker can construct an object with two owner references sharing one UID — one already legitimately blocking (`blockOwnerDeletion: true`) and one not — then flip the non-blocking ref to `blockOwnerDeletion: true` in a later update. `newBlockingOwnerDeletionRefs` looks up the old state by UID, finds the *other* duplicate's already-blocking state, and incorrectly treats the transition as "already blocking", skipping the delete/finalizers authorization check entirely.

### Finding Description
- `indexByUID` (`plugin/pkg/admission/gc/gc_admission.go:248-254`) indexes `oldMeta.GetOwnerReferences()` by `ref.UID` into a plain map, so if two owner refs share a UID, only the last one survives.
- `newBlockingOwnerDeletionRefs` (lines 258-294) uses this map to decide, for each new blocking ref, whether it is *newly* blocking: `oldRef, ok := indexedOldRefs[ref.UID]; wasNotBlocking := oldRef.BlockOwnerDeletion == nil || *oldRef.BlockOwnerDeletion == false`.
- Attack flow:
  1. Attacker (who has delete permission on their own dependent object, and legitimately obtained finalizers/delete permission on some object B) creates the dependent object with two owner references sharing the same UID `X`: ref A (owner resource the attacker does NOT have delete/finalizers permission on, `blockOwnerDeletion: false`) and ref B (owner resource attacker DOES have permission on, `blockOwnerDeletion: true`), ordered so B appears after A in the slice. This create passes `ValidateOwnerReferences` (no UID-uniqueness check) and passes admission because on `Create`, `newBlockingOwnerDeletionRefs` returns `blockingNewRefs` directly (oldObj is nil, `indexByUID` not on the code path) and only ref B is blocking, for which the attacker legitimately has permission.
  2. Attacker later sends an `Update` that leaves ref B (UID X, blocking) unchanged, but flips ref A's `blockOwnerDeletion` from `false`/`nil` to `true`.
  3. In `Validate`, `isChangingOwnerReference` detects the diff, `newBlockingOwnerDeletionRefs` is invoked with old/new metadata. `blockingOwnerRefs(newRefs)` returns both A and B (both now blocking). `indexByUID(oldMeta.GetOwnerReferences())` collapses to `map[X] = B` (B overwrote A because it came later in the old slice).
  4. Looping over `blockingNewRefs`: for ref B, `indexedOldRefs[X] == B`, already blocking → correctly skipped. For ref A, `indexedOldRefs[X]` **also resolves to B** (not A), whose `BlockOwnerDeletion == true` → `wasNotBlocking` is `false` → ref A is wrongly excluded from `ret`.
  5. Because ref A never appears in `newBlockingRefs`, the subsequent authorization loop (lines 138-152, `ownerRefToDeleteAttributeRecords` + `a.authorizer.Authorize` on the `finalizers` subresource) is never invoked for ref A. The attacker's update — setting `blockOwnerDeletion: true` on a reference to a resource they cannot delete/finalize — is admitted without the required authorization check.

### Impact Explanation
This breaks the `OwnerReferencesPermissionEnforcement` admission plugin's core invariant that setting `blockOwnerDeletion: true` requires delete/finalizers permission on the referenced owner (Kubernetes bounty class: authorization bypass / privilege escalation via admission-plugin logic error). The concrete effect is that an unprivileged user can attach an unauthorized, deletion-blocking ownerReference to an arbitrary object (e.g., a serviceaccount- or namespace-owned resource they cannot otherwise touch), letting them block foreground deletion of that owner object without holding the required finalizers permission — a cross-tenant integrity/availability violation of `AUTHORIZATION_EXACTNESS`.

### Likelihood Explanation
Requires only namespace-scoped RBAC to: (1) create/update the attacker's own dependent object with arbitrary `ownerReferences` (no special permission needed to *set* an ownerReference on create, since Create is exempt from the delete-permission gate); and (2) have legitimately obtained finalizers/delete permission on some unrelated "helper" resource B, which is common (e.g., the attacker's own namespaced resource). No cluster-admin, webhook, or node access needed. The exploit is fully reproducible via unit test of `indexByUID`/`newBlockingOwnerDeletionRefs` with crafted duplicate-UID slices, and via an admission-plugin `Validate` integration test.

### Recommendation
Change `indexByUID` to index by a composite key that uniquely identifies an owner reference (e.g., `(APIVersion, Kind, Name, UID)`) instead of `UID` alone, or change it to `map[types.UID][]metav1.OwnerReference` and check *all* candidates for a given UID before concluding "already blocking". Additionally, consider rejecting duplicate UIDs in `ValidateOwnerReferences`.

### Proof of Concept
Unit test in `plugin/pkg/admission/gc/gc_admission_test.go` (or a new test file):
```go
uid := types.UID("dup-uid")
blockTrue := true
blockFalse := false

oldRefs := []metav1.OwnerReference{
    {APIVersion: "v1", Kind: "ConfigMap", Name: "a", UID: uid, BlockOwnerDeletion: &blockFalse}, // attacker lacks permission on this
    {APIVersion: "v1", Kind: "Secret", Name: "b", UID: uid, BlockOwnerDeletion: &blockTrue},      // attacker has permission on this
}
newRefs := []metav1.OwnerReference{
    {APIVersion: "v1", Kind: "ConfigMap", Name: "a", UID: uid, BlockOwnerDeletion: &blockTrue}, // flipped to blocking
    {APIVersion: "v1", Kind: "Secret", Name: "b", UID: uid, BlockOwnerDeletion: &blockTrue},
}

oldObj := &v1.Pod{ObjectMeta: metav1.ObjectMeta{OwnerReferences: oldRefs}}
newObj := &v1.Pod{ObjectMeta: metav1.ObjectMeta{OwnerReferences: newRefs}}

result := newBlockingOwnerDeletionRefs(newObj, oldObj)
// BUG: result does not contain the ConfigMap/a ref, so its authorization check is skipped.
// Expected (fixed) behavior: result must contain the ConfigMap "a" ref since it
// transitioned from non-blocking to blocking, regardless of the colliding UID.
assert.Contains(t, refNames(result), "a")
```
A complementary admission-level integration test should call `gcPermissionsEnforcement.Validate` with an authorizer that denies `update`/`finalizers` on the ConfigMap resource but allows it on the Secret, and assert that the request is currently (incorrectly) allowed, demonstrating the bypass.
