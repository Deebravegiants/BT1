### Title
Direct token donation to a curve `Pair` permanently bricks the overflow-buy-cap safety net in `Router._computeBuy`, causing a persistent DoS on the last/large buys of the curve and blocking the supply-based graduation trigger - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's live `tokenBalance()` and back-calculates `amountInUsed` from the K-invariant whenever a buy would otherwise exceed the real (non-virtual) token balance held by the `Pair`. This "overflow buy cap" is the mechanism that lets any oversized buy safely complete against the last remaining real supply instead of reverting. The back-calculation subtracts `tokensOut` (== `realBalance`) from the stored `reserveToken`: [1](#0-0) 

`reserveToken` and `realBalance` are supposed to differ by a constant 250M-token virtual gap, but `realBalance` is a live `IERC20.balanceOf(pair)` read, while `reserveToken` is only mutated by `Router.swap`. An unrelated wallet can permissionlessly call `IERC20(launchedToken).transfer(pair, X)` to inflate `realBalance` above `reserveToken` (the codebase's own regression test drives exactly this state, `_stageDonationAttack` in `test/Zap.t.sol`, confirming `realBalance > reserveToken` is reachable): [2](#0-1) [3](#0-2) 

Once poisoned, `cappedReserveToken = reserveToken - tokensOut` (= `reserveToken - realBalance`) underflows and reverts with a Solidity arithmetic panic instead of `OverflowCapDegenerate`, for **any** buy whose uncapped `tokensOut` exceeds `realBalance` — i.e. exactly the class of buy this cap exists to protect (large buys, and the final buy that would otherwise drain the curve).

### Finding Description
The protocol previously suffered the identical underflow in `Bonding.previewLtUntilGraduation`'s supply leg and shipped a guard for it — `if (realBalance >= reserveToken) return ltUntilThreshold;` — documented as fixing a "TOKEN donation that drives realBalance > reserveToken … cascading into a Zap.buy DoS": [4](#0-3) 

That guard only protects the *preview/sizing* helper used by `Zap._executeBuy` to avoid oversizing an LT mint; it does not touch `Router._computeBuy`, which contains the exact same unguarded subtraction and is the code that actually executes every `Bonding.buy` / `Zap.buy`: [5](#0-4) 

The existing regression coverage (`test_donation_zapBuyStillSucceeds`, `test_donation_sellsStillWork`) only exercises **small** buys/sells after the donation, which never reach the capped branch, so the panic in `_computeBuy` is not covered: [6](#0-5) 

Because `reserveToken` and `realBalance` decrease in lockstep on every ordinary buy (both drop by `tokensOut`), the gap introduced by a one-time donation is permanent for the life of the curve — there is no operation that lets the gap heal. From that point on, `Router._computeBuy`'s capped branch will always underflow-revert instead of completing the buy, exactly mirroring the CVE-2023-31615 pattern of a crafted input state causing an unhandled arithmetic fault in a core data-structure operation, producing a Denial of Service.

### Impact Explanation
- Any trader (including an unrelated wallet with no privileges) submitting a buy large enough to exceed the (attacker-inflated) `realBalance` gets a reverted transaction instead of the intended graceful cap-and-refund; this is the exact mechanism `_computeBuy`/`test_inv_overflowCap_refundsLt` exists to guarantee.
- The AGENTS.md documents that the supply trigger (`IPair.tokenBalance() == 0`) is the *only* graduation path for flat/bear-market LTs where the USD trigger never fires. Since the gap is permanent, no buy can ever legitimately reduce `tokenBalance()` to `0` via the cap path (any buy attempting to do so panics), permanently blocking graduation for such tokens.
- This freezes the LT already raised by the curve inside `Bonding`/`Pair` (no graduation → no LP creation → no exit path other than sells, which are also constrained by the LT's redemption buffer), and permanently DoSes legitimate large buyers — satisfying the "permanent freezing of trader/creator funds" and "concrete DoS" bars required by the validation rules.
- Reachable entirely through in-scope, unprivileged actions: buying some Token off the curve, then a plain `IERC20.transfer` of that Token into the `Pair` — no privileged role, no upgrade, no off-chain component.

### Likelihood Explanation
High. The donation itself costs only the price of acquiring ~250M+ tokens' worth of curve exposure (which the attacker can immediately re-sell back, since transferring tokens to `Pair` outside of `Router.sell` doesn't consume the attacker's economic position beyond the tokens donated), and the codebase's own test suite (`_stageDonationAttack`) shows this is a simple, cheap, two-step sequence usable by any wallet against any freshly-launched or actively-trading curve before graduation.

### Recommendation
Add the same `realBalance >= reserveToken` guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy` (and any other caller of the capped-branch formula, e.g. `getAmountOut`/`previewBuy`), routing to a defined behavior (e.g. treat the curve as effectively capped at `tokensOut = 0`/revert with `OverflowCapDegenerate`, or clamp `cappedReserveToken` to a minimum of `1`) instead of allowing the unguarded subtraction to underflow. Alternatively, make `tokenBalance()`-based donation immune everywhere by tracking sellable supply via the stored pool state rather than a live `balanceOf` read.

### Proof of Concept
Using the repository's own test scaffolding (`test/Zap.t.sol`):
1. Launch a token (`_createToken(0)`), producing `Pair` with `reserveToken = 1B` (virtual) and `tokenBalance() = 750M` (real, `curveSupply`).
2. Call `_stageDonationAttack(tokenAddr)`: drain enough LT through the curve to acquire `> 250M` real Token, then `Token(tokenAddr).transfer(pairAddr, donatedTokens)` — this is exactly the helper already in the codebase, and `test_donation_realBalanceExceedsReserveToken` confirms `realBalance > reserveToken` afterward: [3](#0-2) 
3. Have any trader submit a buy through `Zap.buy`/`Bonding.buy` large enough that the uncapped `_computeBuy` calculation yields `tokensOut > realBalance` (e.g. the same `1_000_000_000 ether`-scale oversized buy used in `test_inv_overflowCap_refundsLt`): [7](#0-6) 
4. Because `realBalance > reserveToken` post-donation, `cappedReserveToken = reserveToken - realBalance` underflows in `Router._computeBuy`, reverting the transaction with an arithmetic panic instead of returning a capped `tokensOut`/`amountInUsed` — a DoS that persists for every subsequent large buy against that token.

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```

```text
    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }
```

```text
        address pair = info.pair;
        uint256 realBalance = IPair(pair).tokenBalance();
        if (realBalance == 0) return 0;

        (uint256 reserveToken, uint256 reserveAsset) = IPair(pair).getReserves();

        uint256 ltUntilThreshold = type(uint256).max;
        uint256 exchangeRate = IBounceLeveragedToken(info.ltAddress).exchangeRate();
        if (exchangeRate > 0) {
            uint256 realLtRaised = reserveAsset - _launchTimeVirtualLtReserve(token_, pair);
            uint256 thresholdRealLt = ($.graduationThresholdUsd * 1e18 + exchangeRate - 1) / exchangeRate;
            if (realLtRaised >= thresholdRealLt) return 0;
            ltUntilThreshold = thresholdRealLt - realLtRaised;
        }

        // Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
        if (realBalance >= reserveToken) return ltUntilThreshold;

        uint256 cappedReserveToken = reserveToken - realBalance;
        uint256 cappedReserveAsset = (IPair(pair).k() + cappedReserveToken - 1) / cappedReserveToken;
        uint256 ltUntilSupply = cappedReserveAsset - reserveAsset;

        return ltUntilSupply < ltUntilThreshold ? ltUntilSupply : ltUntilThreshold;
    }
```

```text
    function test_inv_overflowCap_refundsLt() public {
        (address tokenAddr,) = _launchNoSeed();
        // Crash exchange rate so USD trigger never fires and we can isolate the supply
        // trigger & overflow-cap path.
        lt.setExchangeRate(0.0001 ether);

        uint256 balancePre = lt.balanceOf(trader2);
        // Grossly oversized buy that would attempt to absorb >1B tokens on the curve.
        // Real balance is 750M, so `Router.buy` must cap at 750M and back-calc the LT used.
        uint256 oversizedBuy = 1_000_000_000 ether;

        (uint256 tokensOut, uint256 amountInUsed) = _buy(tokenAddr, trader2, oversizedBuy);

        assertTrue(bonding.isGraduated(tokenAddr), "graduated on capped buy");
        assertTrue(amountInUsed < oversizedBuy, "buy must be capped below oversized request");
        assertEq(tokensOut, CURVE_SUPPLY, "tokensOut must equal remaining real supply");

        // `bonding.buy` pulls only `amountInUsed` from trader2 (via Router → pair + fees).
        uint256 balancePost = lt.balanceOf(trader2);
        uint256 ltConsumed = balancePre + oversizedBuy - balancePost;
        assertEq(ltConsumed, amountInUsed, "trader should only pay `amountInUsed`, not the requested amount");
    }
```
