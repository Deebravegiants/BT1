### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`/`webhook_id`) values are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` verifies only that the HMAC matches the body, then hands the header-derived `shop` value to the app's webhook handler as trusted tenant identity. This breaks the equality `shop authenticated by HMAC == shop acted on by the handler`, allowing a webhook whose body/HMAC pair is legitimately obtainable for one shop to be replayed with a forged `shop` header pointing at a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the signable string (i.e., the body) via `Utils::HmacValidator.validate`, then immediately trusts `request.shop` when constructing the data passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever compares the HMAC against `verifiable_query.to_signable_string` (the body for webhooks) and `Context.api_secret_key` — it never incorporates the `shop` header: [4](#0-3) 

Because `api_secret_key` is a single app-wide secret shared across every shop that installs the app (not per-tenant), any unprivileged internet user who can install the app on their own shop (or otherwise capture one legitimate webhook delivery) obtains a `(raw_body, hmac)` pair that is valid under the app's key regardless of which shop the body nominally describes. Since the `shop` header is outside the signed content, that same `(raw_body, hmac)` pair can be replayed to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to target a different, victim shop. `HmacValidator.validate` still returns `true` (the body and secret match), and `Registry.process` forwards the attacker-chosen `shop` to `WebhookMetadata`/the handler as if it were authentic: [5](#0-4) 

Any app logic that uses `WebhookMetadata#shop` to look up/act on a merchant's stored session, data, or state will act on the attacker-forged tenant instead of the tenant that actually produced the webhook body.

### Impact Explanation
This is a cross-tenant access primitive: an attacker who legitimately receives (or can otherwise obtain) one valid webhook body+HMAC pair for the app (e.g., by installing the app themselves) can forge the `shop` identity associated with that payload and cause the host application to process/act on it under an arbitrary victim shop's identity. Depending on how the host app's webhook handlers use `data.shop` (e.g., to fetch the victim's stored session/access token, update the victim's stored records, or trigger side effects "on behalf of" the victim shop), this can lead to cross-tenant data manipulation — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker does not need the app's `client_secret`/`api_secret_key`, only a legitimate webhook delivery from Shopify for a shop they control (installing a public app is unprivileged). Because `api_secret_key` is shared across all shops for a given app, one such captured `(body, hmac)` pair is valid for replay against any shop header. The main precondition is that the host application relies on the gem's `WebhookMetadata#shop` for tenant-sensitive decisions — which is the intended and documented use of this field.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook-id`) header values into the HMAC-signable content, or otherwise cryptographically verify that the `shop` header matches the tenant the webhook body was actually generated for, before exposing it to handlers. At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` is derived from an unauthenticated header and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against a shop known to have a currently valid stored session/registration for that specific webhook `webhook_id`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook, capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` (valid because `H = HMAC_SHA256(api_secret_key, B)`, and `api_secret_key` is the same for every shop using the app).
2. Attacker sends a forged HTTP request directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic`: unchanged/attacker-chosen
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `request.to_signable_string` (`= B`) and succeeds since `B`/`H` still match under `api_secret_key`. [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop == "victim-shop.myshopify.com"`, even though that body never originated from Shopify for the victim shop. [5](#0-4)
