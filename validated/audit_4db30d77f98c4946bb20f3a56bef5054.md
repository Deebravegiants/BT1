### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Webhooks::Registry.process` binds *only* the body bytes to the app's secret. The `x-shopify-shop-domain` (and `shopify-shop-domain`) header, which is read directly off the unauthenticated request and forwarded to the host application as the tenant identifier, is never included in the signed material. This breaks the intended binding: `hmac == HMAC(secret, body)` while `shop == header value`, with no cryptographic tie between the two.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` straight from request headers: [1](#0-0) 

The signable string used for HMAC verification is defined as just the raw body, excluding all headers: [2](#0-1) 

`Webhooks::Registry.process` validates that HMAC against the app's `api_secret_key`, then immediately trusts `request.shop` (header-derived) as the tenant identity passed to the handler, without any check that `shop` corresponds to whatever entity actually produced the signed body: [3](#0-2) 

The HMAC is computed and verified purely over `@raw_body`: [4](#0-3) 

This is exactly the identity-binding-break pattern called out in scope: "a field acted on but not covered by the HMAC." The equality the code implicitly assumes is `shop_header == originating_shop_of(body)`, but nothing enforces it — the check only proves `hmac == HMAC(secret, body)`. Since `shop` is not part of the signed string, any request carrying a *previously valid* `(body, hmac)` pair will pass validation regardless of what `x-shopify-shop-domain` value accompanies it.

### Impact Explanation
An unprivileged party who can obtain one legitimately-signed `(raw_body, hmac)` pair for any topic (e.g., by installing the app on their own store and triggering an event, or intercepting one delivery) can replay that exact body/HMAC to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` header value naming a victim shop. `Registry.process` will accept the HMAC (it only checks the body) and hand the handler a `WebhookMetadata` whose `shop` is the attacker-chosen victim domain. Any host application that uses `data.shop` to route persistence, look up the tenant's session/access token, or otherwise scope the write will process attacker-supplied body content under another tenant's identity — a cross-tenant data-integrity/confusion vulnerability using only the app's own valid webhook traffic, no `access_token` or `client_secret` needed by the attacker.

### Likelihood Explanation
Webhook endpoints are, by design, publicly reachable to accept unauthenticated POSTs from Shopify, so the attacker does not need network privilege beyond the endpoint's normal exposure. Obtaining one valid `(body, hmac)` sample only requires installing the app on an attacker-controlled store (a low bar for many app models) or capturing one legitimate delivery, then replaying it with a modified header — no cryptographic secret is required. Likelihood is moderate: it depends on the host app trusting `data.shop` for tenant-scoping logic (a common and expected usage pattern per this gem's own `WebhookMetadata` design) and on topics whose body content is attacker-influenceable or replayable across shops.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string bound to the HMAC, or otherwise cryptographically tie the header-derived `shop` value to the verified body before constructing `WebhookMetadata`. At minimum, `Registry.process` should not treat `request.shop` as trusted tenant context based solely on a body-only HMAC check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST: body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because the shop header is not part of `to_signable_string`.
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes/stores data as belonging to `victim-shop`, even though it never originated from that shop.
