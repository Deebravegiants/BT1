## Title
Cross-chain order escrow becomes permanently unrecoverable when `placeOrder` targets a `destination` state machine with no registered `IntentGateway` instance - ([File: evm/src/apps/intentsv2/IntentsBase.sol], [File: evm/src/apps/intentsv2/ExtrinsicIntents.sol], [File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` escrows a user's input tokens for a cross-chain order without validating that `order.destination` corresponds to a state machine with a registered peer gateway (`_instances[keccak256(destination)]`). Both cross-chain cancellation paths (`_cancelFromSource` and `_cancelFromDest`) internally require a registered instance to construct the Hyperbridge message, so if the destination was never registered (or is mistyped/unsupported), the order can neither be filled nor cancelled - the escrowed tokens are permanently frozen with no available recovery function, mirroring the "arbiter never set → dispute/refund path unreachable" bug class from the referenced report.

### Finding Description
`placeOrder` escrows `order.inputs` for any `order.destination` bytes value supplied by the caller, with no check against the `_instances` registry: [1](#0-0) 

The only way to recover escrow on a cross-chain order once placed is through `cancelOrder`, which routes to `_cancelFromSource` (on the source chain) or `_cancelFromDest` (on the destination chain) depending on which chain the call executes on: [2](#0-1) 

`_cancelFromSource` unconditionally calls `_instance(order.destination)` to build the storage-proof key for the Hyperbridge `DispatchGet` request. `_instance` reverts with `UnknownInstance` if no peer gateway is registered for that state machine: [3](#0-2) [4](#0-3) 

`_cancelFromDest` can only be invoked by calling `cancelOrder` while `currentChain == orderDest`. If `order.destination` refers to a chain identifier for which no `IntentGatewayV2` was ever deployed/registered (a typo, an unsupported chain, or a chain governance has not yet onboarded), there is no gateway contract at that address/chain to call `cancelOrder` on in the first place, and even if there were, `fillOrder` there would also be unreachable because the order's `destination` field would not match that gateway's registered peer relationship back to the source (peer registration/`_instances` are populated only by governance via `NewDeployment`, gated to `Hyperbridge` itself): [5](#0-4) [6](#0-5) 

As a result, a single unprivileged `placeOrder` transaction with a destination that lacks a registered gateway instance escrows the user's tokens with **no reachable withdraw, cancel, or timeout path**: `_cancelFromSource` reverts `UnknownInstance` immediately, and `_cancelFromDest`/`fillOrder` are unreachable because no correctly-configured counterpart gateway exists. This is functionally identical to the referenced report's root cause: a critical recovery function (`resolveDispute`/`initiateDispute` there, `cancelOrder`'s cross-chain routes here) is guarded by a precondition (arbiter set / registered peer instance) that the depositing party does not control and that, once left unmet, can never be satisfied by that party, permanently freezing escrowed funds.

### Impact Explanation
Any user who places a cross-chain order (mistyped destination chain id, destination not yet onboarded by governance, or a destination that is later deregistered/never registered) permanently loses access to their escrowed `order.inputs`. There is no permissionless emergency-withdraw or same-chain fallback for cross-chain orders once escrowed — the funds are locked until/unless Hyperbridge governance separately deploys and registers the missing peer (an action entirely outside the depositor's control and not guaranteed to ever happen for arbitrary/invalid chain identifiers). This satisfies "permanent freezing of funds" from a single submitted transaction reachable by any ordinary user.

### Likelihood Explanation
Likelihood is non-trivial: `placeOrder` performs no on-chain validation that `order.destination` is a supported/registered state machine, so any user-facing frontend bug, off-chain misconfiguration, stale peer list, or a user directly interacting with the contract (or a chain governance has since deregistered/never registered) can trigger this. Because escrow happens unconditionally at `placeOrder` time before any cross-chain confirmation of destination validity, the failure mode requires no attacker — it can occur from ordinary use whenever the destination registry and order destination diverge.

### Recommendation
Add a guard in `placeOrder` requiring `order.destination` to already have a registered instance for cross-chain orders (`_instances[keccak256(order.destination)] != address(0)`) before escrowing tokens, so invalid/unregistered destinations revert at placement time instead of after funds are locked. Additionally, consider a same-chain-style emergency withdrawal path (e.g., permissionless withdrawal after a long grace period, analogous to the destination-side "after deadline anyone can cancel" mechanic) that does not depend on a registered peer instance, so that misconfigured cross-chain orders can still be recovered without requiring a fresh governance `NewDeployment` action.

### Proof of Concept
1. Governance/relayer has registered `IntentGatewayV2` peers for chains A and B only; chain C has no registered instance (`_instances[keccak256(C)] == address(0)`).
2. A user on chain A calls `placeOrder(order, graffiti)` with `order.destination = C` (typo, unsupported chain, or chain not yet onboarded). `placeOrder` escrows `order.inputs` from the user with no destination-registration check, as shown in `evm/src/apps/IntentGatewayV2.sol` lines 194-213.
3. The user calls `cancelOrder(order, options)` from chain A. Since `orderSource == currentChain`, `_cancelFromSource` executes and calls `_instance(order.destination)` → reverts with `UnknownInstance` (`evm/src/apps/intentsv2/IntentsBase.sol` lines 401-405).
4. No `IntentGatewayV2` deployment exists on chain C to call `cancelOrder`/`fillOrder` from the destination side, so `_cancelFromDest` and `fillOrder` are unreachable.
5. The user's escrowed tokens in the chain-A gateway remain locked indefinitely, with no available function to reclaim them short of Hyperbridge governance later deploying and registering a gateway on chain C purely coincidentally matching the order (which does not resolve an already-mistyped/nonexistent chain id).

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    /**
     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }
