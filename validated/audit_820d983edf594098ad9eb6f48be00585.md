### Title
Webhook shop attribution not covered by HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by `ShopifyAPI::Webhooks::Registry.process` to attribute and route the webhook come from unauthenticated HTTP headers. This breaks the identity binding `shop_verified_by_hmac == shop_used_by_handler`, letting an attacker who controls one legitimately-signed webhook body/HMAC pair relabel it as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `to_signable_string` against the secret-derived HMAC: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once the HMAC over the body passes, then forwards `request.shop` (the unauthenticated header) straight to the app's handler without any further binding check: [4](#0-3) 

Because the signature never covers `shop`, any HTTP client that possesses one valid `(raw_body, hmac)` pair — for example, an attacker's own shop that legitimately installed the app and received a real webhook delivery — can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only re-derives the HMAC from the (unchanged) body, and `Registry.process` will hand the handler a `WebhookMetadata` object claiming the victim shop as the source: [5](#0-4) 

### Impact Explanation
Applications built on this gem commonly key persistence, session lookup, or business logic (e.g. order processing, GDPR "shop redact"/"app uninstalled" handling) off `WebhookMetadata#shop`. Since that value is not bound to the HMAC, an attacker owning any shop (including a free/trial install) can forge webhooks attributed to a victim merchant, causing the host application to process attacker-controlled data under another tenant's identity — a cross-tenant access/integrity violation.

### Likelihood Explanation
Exploitation requires only an unprivileged actor to install the app on their own shop (or otherwise obtain one legitimately-signed `(body, hmac)` pair) and send a crafted HTTP POST directly to the app's public webhook endpoint with a different `shop-domain` header — no access token, `client_secret`, or privileged access is required.

### Recommendation
Do not treat header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) as authenticated. Either include them in the signed payload construction used for HMAC verification, or require the host application to independently verify that the `shop` value corresponds to a shop that actually has an active session/installation before trusting webhook content, rejecting the webhook if the header-derived shop cannot otherwise be corroborated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook delivery (e.g. `orders/create`) with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, and `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B` (`to_signable_string` in `lib/shopify_api/webhooks/request.rb:36-38`).
4. `Registry.process` dispatches to the handler with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload actually originated from and was signed for the attacker's own shop.
