## Title
Webhook `shop` (and `topic`) identity is not bound to the HMAC signature, enabling cross‑tenant webhook spoofing — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when computing/validating the webhook HMAC. The `shop-domain` (and `topic`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the host application's webhook handler are taken from unauthenticated HTTP headers that are never included in the signed material. Anyone who can obtain one valid `(body, hmac)` pair for the shared app secret (e.g. from their own store's legitimate webhook, which they fully control as an app installer) can replay that exact body/hmac while substituting an arbitrary `shop-domain` header, and the gem will accept it as authentic and dispatch it to the app's handler as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `#shop`, `#topic`, `#api_version`, and `#webhook_id` are pulled straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., HMAC(body) == header) and then forwards `request.shop` and `request.topic` — both unauthenticated — directly to the app-registered handler: [3](#0-2) 

The identity binding that should hold is:
`shop_bound_by_hmac == shop_delivered_to_handler`

but in this implementation:
`shop_bound_by_hmac` (nothing — the signature only covers the body) `!= shop_delivered_to_handler` (`request.shop`, an attacker-controllable header).

Because the HMAC is computed with the single shared `api_secret_key` for the whole app (not per-shop), the signature for a given raw body is identical regardless of which shop the webhook is "for." An app owner who installs their own copy of the app on their own store legitimately receives real `(body, hmac)` pairs signed with the app's secret. Nothing in `Request` or `Registry.process` stops that same attacker from POSTing that exact body and hmac to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) to a different, victim shop's domain. `HmacValidator.validate_signature` will still pass because it only recomputes HMAC over `@raw_body`: [4](#0-3) 

The forged request is then indistinguishable from a legitimate webhook and is dispatched with `shop: request.shop` set to the victim tenant: [5](#0-4) 

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (as the gem's own registry does, and as apps are expected to) to determine which tenant's data to update, look up, or expose can be tricked into acting on attacker-chosen data under a victim shop's identity — a cross-tenant access/data-confusion vulnerability that stems from this gem's failure to bind the `shop` field to the cryptographic proof it exposes as "verified." This satisfies the Critical impact criterion of cross-tenant access.

### Likelihood Explanation
Any user can install the target app on their own store (a normal, unprivileged action), causing Shopify to deliver real webhooks with valid `(body, hmac)` pairs for their shop. They need no special credentials, no leaked secrets, and no access to `api_secret_key`; they only need to control the headers of their own forged HTTP request to the app's public webhook endpoint, replaying a body/hmac they legitimately received. This is straightforward to reproduce.

### Recommendation
Bind the `shop` (and ideally `topic`) to the verified material — e.g., include `shop-domain` and `topic` header values in the signable string used for the webhook HMAC check, or otherwise cryptographically tie the claimed shop to the specific webhook delivery before it is handed to `WebhookMetadata`/the app handler. At minimum, document and enforce that `Registry.process` must verify the delivered `shop` against session/installation state the app already trusts for that endpoint, rather than trusting the header outright once the body hash matches.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook (e.g. `orders/create`), capturing the exact raw JSON body and the `X-Shopify-Hmac-Sha256` header value sent by Shopify.
2. Attacker crafts a new HTTP POST to the same app webhook endpoint using the identical raw body and HMAC header, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - (optionally) a different `X-Shopify-Topic`
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only, which still matches the replayed `hmac` header — validation succeeds.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-controlled data as if it came from the victim shop.

          received_signature = verifiable_query.hmac
