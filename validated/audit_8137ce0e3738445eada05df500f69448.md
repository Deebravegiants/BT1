### Title
Unbounded ancestry-walk loop in GRANDPA `AncestryChain::ancestry` allows a relayer-submitted circular header proof to hang block execution (DoS) - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`AncestryChain::ancestry` walks backward from a target block hash to a base hash by repeatedly following `parent_hash` pointers taken from attacker-supplied header data (`votes_ancestries` / `unknown_headers` in a GRANDPA consensus proof). The loop condition is only `while current_hash != base`, with no cycle detection and no iteration bound. A relayer can submit a consensus proof containing two (or more) headers whose `parent_hash` fields point at each other, forming a cycle that never reaches `base`. This drives the loop into an unbounded/infinite traversal — the same bug class as CVE-2017-9122 (an unbounded parsing loop over attacker-controlled linked structures causing CPU exhaustion / hang), except here the "file" being parsed is a submitted consensus proof processed inside on-chain runtime execution.

### Finding Description
`AncestryChain` is built directly from attacker-controlled data with no validation that the supplied headers form an acyclic chain: [1](#0-0) 

```rust

	ancestry: BTreeMap<H::Hash, H>,

		AncestryChain { ancestry }
	}
	...

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H> {
	fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
}
```

The `ancestry` map is keyed by each header's own computed hash, but nothing constrains the *content* of a header's `parent_hash` field, and nothing prevents two attacker-supplied headers in the same proof from forming a cycle (header A's `parent_hash` = hash(B), header B's `parent_hash` = hash(A)). Once `current_hash` enters such a cycle and `base` is not one of the cycle members, the `while` loop never terminates and `route` grows without bound.

This is directly reachable from the GRANDPA consensus verification entry point, which any relayer can invoke by submitting a consensus proof: [2](#0-1) 

`verify_grandpa_finality_proof` calls `headers.ancestry(base.hash(), consensus_state.latest_hash)` and `headers.ancestry(from, target.hash())` using an `AncestryChain` built from `finality_proof.unknown_headers`, which comes straight from the submitted proof bytes. It is also reached via `GrandpaJustification::verify_with_voter_set`: [3](#0-2) 

which builds `AncestryChain::<H>::new(&self.votes_ancestries)` (also attacker-supplied) and calls `.ancestry(base_hash, signed.precommit.target_hash)` for each precommit.

Both entry points are exercised from `ConsensusClient::verify_consensus` for GRANDPA, which decodes an unsigned/unauthenticated `ConsensusMessage` proof supplied by any relayer: [4](#0-3) 

This code path runs inside on-chain runtime execution (`no_std` pallet code), so an infinite loop here blocks block-production/extrinsic execution rather than merely a long-running off-chain process.

### Impact Explanation
An unprivileged relayer can craft a GRANDPA consensus proof (`ConsensusMessage::Polkadot`/`Relaychain`/`StandaloneChain`) whose `unknown_headers`/`votes_ancestries` contain two or more headers with circular `parent_hash` references. When submitted, `verify_grandpa_finality_proof` (or `GrandpaJustification::verify`) enters an infinite loop inside `AncestryChain::ancestry`, hanging execution of the extrinsic/consensus-update call. Because this executes as part of on-chain state-transition logic, this can stall block execution for the chain hosting the GRANDPA light client, halting all consensus updates and therefore all message delivery that depends on that consensus client (a "route unable to deliver messages" condition), and potentially exhausting node resources chain-wide.

### Likelihood Explanation
The attack requires no special privilege: any relayer able to submit a consensus proof (permissionless in Hyperbridge's design) can construct two dummy headers whose `parent_hash` fields point at each other and place them in `votes_ancestries`/`unknown_headers`. Producing a valid header hash and pointing another header's `parent_hash` field at it requires no cryptographic break — header fields (parent_hash, number, state_root, extrinsics_root, digest) are attacker-controlled inputs to this code path since these headers are only checked for internal hash self-consistency in the `BTreeMap` construction, not against a real finalized chain before this traversal runs. This makes the likelihood high once such a proof reaches `verify_consensus`.

### Recommendation
Add cycle detection / an iteration bound to `AncestryChain::ancestry`, e.g. track visited hashes in a `BTreeSet` and return `Err(finality_grandpa::Error::NotDescendent)` (or a new error) if a hash is revisited, or cap the number of hops to `votes_ancestries.len() + 1` (since a legitimate route can never contain more hops than headers supplied). Apply the same bound to any other traversal over attacker-controlled header sets (e.g., `unknown_headers` in fraud-proof verification) that calls into `AncestryChain::ancestry`.

### Proof of Concept
1. Construct header `A` with arbitrary fields and `parent_hash = hash(B)`.
2. Construct header `B` with arbitrary fields and `parent_hash = hash(A)`.
3. Submit a `GrandpaJustification`/`FinalityProof` whose `votes_ancestries`/`unknown_headers` includes `[A, B]`, with a precommit `target_hash = hash(A)` and a `base_hash`/`consensus_state.latest_hash` that is neither `hash(A)` nor `hash(B)`.
4. Call `verify_grandpa_finality_proof` (or `GrandpaJustification::verify`) with this proof: `AncestryChain::ancestry(base, hash(A))` enters `current_hash = hash(A) -> hash(B) -> hash(A) -> ...` forever, matching the existing test harness pattern in `modules/consensus/grandpa/primitives/src/justification.rs` (`test_ancestry_route`) but with a cyclic `headers` vector instead of a linear one.
