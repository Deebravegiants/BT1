### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` HTTP header (unauthenticated) as the tenant identity passed to the app's handler. Because the HMAC signature only covers the body and not the shop header, a party who can obtain one valid `(body, hmac)` pair for the shared app secret can replay it while substituting an arbitrary `shop-domain` value, causing the app to attribute attacker-controlled data to a different (victim) tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body) and then forwards the header-derived `shop` straight to the handler as the tenant identity, without any independent binding between the shop and the signed body: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Because `HmacValidator.validate` only proves `HMAC(body, api_secret_key)` is correct — it says nothing about which shop the body came from — the equality is broken: any request with a previously-valid `(body, hmac)` pair combined with an arbitrary `shop-domain` header passes validation and is delivered to the handler under that arbitrary shop identity. [4](#0-3) 

Critically, `api_secret_key` is the app's single client secret, shared across every shop that installs the app — it is not shop-specific. Any merchant who installs the app is a legitimate recipient of real webhook deliveries (body + valid HMAC) for their own store. That merchant can capture one such delivery and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. The HMAC still validates (it never covered the header), and `Registry.process` calls the handler with `shop: request.shop` set to the victim's domain, injecting attacker-controlled data into the victim tenant's processing path.

### Impact Explanation
This breaks tenant isolation for any app relying on `ShopifyAPI::Webhooks::Registry` to route webhook data by shop: an unprivileged app-installer (who needs no elevated access, no `api_secret_key`, and no token) can make the host application process arbitrary attacker-chosen webhook bodies under another merchant's shop identity — a cross-tenant data-integrity/confidentiality issue (e.g., poisoning another shop's cached data, triggering redact/data-request workflows against the wrong tenant, or corrupting per-shop business state), matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that has more than one merchant installed (a very common condition): obtaining one legitimately-signed webhook body/HMAC pair only requires installing the app as an ordinary merchant, and replaying it with a modified header requires no cryptographic secret at all.

### Recommendation
Bind the tenant identity into the verified material. Either:
- Include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (this requires a Shopify-side change to the webhook signing scheme), or
- Do not trust the header-derived `shop` for authorization/tenant-scoping purposes; instead require the host application to cross-check `request.shop` against an independently known, already-authenticated relationship (e.g., a session/shop record that was created via OAuth/token exchange) before acting on the payload, and document this requirement prominently since the gem's own signature verification does not protect the shop field.

### Proof of Concept
1. App merchant M installs the target app; Shopify sends a real webhook to the app: body `B`, header `X-Shopify-Shop-Domain: m-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)`.
2. M captures `(B, H)` (trivial — M is the legitimate recipient / can proxy their own endpoint).
3. M sends a forged request to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B, secret) == H`, per `lib/shopify_api/utils/hmac_validator.rb`.
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, per `lib/shopify_api/webhooks/registry.rb` lines 198-199, causing the app to process attacker-controlled data as if it originated from `victim-shop`.
