Audit Report

## Title
JWT replay-cache check-then-act race condition allows single-use token to authorize multiple concurrent requests - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` enforces single-use JWTs by checking `isReplay` and later calling `recordUsage`, but these are two independently-locked operations rather than a single atomic critical section. An unprivileged attacker can send two (or more) concurrent HTTP trigger requests bearing the identical valid JWT, and both can pass the replay check before either records usage, bypassing the single-use guarantee.

## Finding Description
`Authorize` calls `h.jwtCache.isReplay(claims.ID)` which acquires and releases `cache.mu.RLock()` internally, then performs unrelated workflow/signer authorization lookups, and only afterward calls `h.jwtCache.recordUsage(claims.ID)`, which separately acquires `cache.mu.Lock()`. No lock spans the whole "check-then-record" sequence in `Authorize`, so between the `isReplay` read-unlock and the `recordUsage` write-lock, a second concurrent request with the same `jti` can also observe "not replayed" and pass. This defeats the anti-replay invariant the code comment claims to provide ("prevent replay attacks"). The existing signature verification (`utils.VerifyRequestJWT`) and authorized-key checks are unaffected by this bug and do not mitigate it, since the race is purely in the cache bookkeeping layer.

## Impact Explanation
This allows a single-use, time-bound JWT to authorize more than one workflow-trigger execution, undermining the intended one-time-use authorization control on the gateway's HTTP trigger path. This maps to an in-scope "unauthorized job run" / authorization-control-bypass category, since a credential meant to authorize exactly one trigger can be used to launch multiple concurrent workflow executions.

## Likelihood Explanation
Exploitation requires only replaying the same signed JWT concurrently against the gateway's `HandleUserTriggerRequest` endpoint — no special privileges, no key compromise, and no unusual tooling beyond issuing parallel HTTP requests with the same `Authorization` token. The race window, while narrow, is trivially reproducible by any client capable of firing concurrent requests, making this a low-effort, repeatable bypass.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic operation performed under one lock acquisition (e.g., a `checkAndRecord`/`LoadOrStore`-style method) so only one concurrent caller can successfully claim a given `jti`; reject all others as already used.

## Proof of Concept
1. Generate a valid JWT with authorized signer/workflow claims and a fixed `jti`.
2. Fire two goroutines concurrently, each invoking `WorkflowMetadataHandler.Authorize` (via `HandleUserTriggerRequest` → `authorizeRequest`) with the identical token.
3. Observe that both calls to `isReplay` return `false` before either `recordUsage` call completes, so both `Authorize` calls succeed and both trigger workflow executions from the single JWT — demonstrable via a Go unit test invoking `Authorize` from two goroutines with a `sync.WaitGroup` and a small artificial delay between `isReplay` and `recordUsage` (or simply high iteration count) to reliably hit the race, confirmed under `go test -race`.
