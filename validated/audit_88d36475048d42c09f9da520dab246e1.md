### Title
Webhook `shop` field is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant) value is read from an unrelated header that is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates only that signature and then hands the unauthenticated `shop` value straight to the app's webhook handler as if it had been verified.

### Finding Description
`Request#to_signable_string` returns `@raw_body` verbatim: [1](#0-0) 
`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside that signed string: [2](#0-1) 
`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 
`HmacValidator.validate`/`validate_signature` confirm the same: the comparison is solely between the received HMAC and a signature computed over `verifiable_query.to_signable_string` (the body), never the shop header: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body)` **and** `shop` is the tenant that produced that signed body. In this gem, only the first half holds — the equality `hmac == HMAC(secret, body)` is checked, but `shop` is never included in the material the HMAC certifies. As documented, `Registry.process` is advertised to the app author as verifying "the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), which developers reasonably interpret as covering the `shop` value handed to their handler via `data.shop` (`docs/usage/webhooks.md:12-17,25-26`).

### Impact Explanation
Any party who can obtain one genuine, validly-signed webhook body+HMAC pair (trivial for an attacker who installs the app on their own free/dev store and triggers any webhook-eligible event, e.g. `orders/create`) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. Because the header is not part of the signed content, `HmacValidator.validate` still returns `true`, and the handler receives `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop. Any host application that uses `data.shop` from the gem's webhook handler as a trusted tenant key (session lookup, per-shop data mutation, cache invalidation, mandatory `shop/redact`/`customers/redact` compliance actions, etc.) can be tricked into acting on the victim tenant with attacker-supplied content — a cross-tenant data integrity/confidentiality breach.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on any shop the attacker controls (self-serve for public apps) and to send one HTTP POST with attacker-chosen headers to the app's public webhook route — no possession of `api_secret_key`, access tokens, or privileged credentials is required, satisfying the unprivileged-internet-user threat model.

### Recommendation
Bind the tenant identity to the signature: either include the shop domain (and other trust-sensitive headers) inside the HMAC-signed material, or have `Registry.process`/`HmacValidator` independently verify that the shop header matches an id embedded in the signed payload, so that `shop` cannot be altered without invalidating the HMAC.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., create an order) so Shopify delivers a validly-signed webhook: body `B`, header `shopify-hmac-sha256: H` where `H = Base64(HMAC-SHA256(secret, B))`.
2. Capture the raw POST.
3. Replay the identical body `B` and header `shopify-hmac-sha256: H` to the same endpoint, but change `shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and succeeds.
5. The app's handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, i.e., attacker-controlled body accepted as belonging to the victim tenant. [5](#0-4) [6](#0-5) [7](#0-6)

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end
