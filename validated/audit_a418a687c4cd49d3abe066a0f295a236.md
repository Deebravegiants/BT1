### Title
Unvalidated `shop` parameter in OAuth begin/callback flow enables forced-OAuth-completion / session-fixation via attacker-redirected authorization request - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from a caller-supplied `shop` string with no domain-format validation, unlike the other OAuth entry points in this gem (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, `clients/graphql/storefront.rb`) which all invoke `Utils::ShopValidator` before using the `shop` value. This lets an unprivileged user who can influence the `shop` param sent to `begin_auth` (the normal, documented entry point that host apps feed with `params[:shop]`) cause the victim's browser to be redirected to an attacker-chosen host instead of Shopify, while the CSRF `state` nonce — the exact value later checked against the session cookie in `validate_auth_callback` — is carried in that redirect's query string and thus disclosed to the attacker-controlled host.

### Finding Description
`begin_auth` computes the authorization URL as: [1](#0-0) 

`auth_base_uri(shop)` performs no format check on `shop` and simply interpolates it into `https://#{shop}/admin`: [2](#0-1) 

The resulting `auth_route` (containing `client_id`, `scope`, `redirect_uri`, and the newly generated `state`) is returned for the host app to redirect the merchant's browser to. Because `shop` is never checked to be a `*.myshopify.com` (or partner-approved) domain, a `shop` value pointing at an attacker-controlled host makes the victim's browser navigate there instead of to Shopify, handing the attacker the `state` value in the query string.

That same `state` is simultaneously placed into a cookie set on the victim's browser (`cookie = SessionCookie.new(value: state, ...)`), and later `validate_auth_callback` only checks equality between the cookie and the query-string `state` — it never checks that the `shop` used in step one matches the `shop` in the completed callback, nor is there any binding that the authorization attempt actually reached Shopify: [3](#0-2) 

The identity binding broken is: `state(cookie set for shop_A's begin_auth) == state(auth_query for shop_B's callback)` is treated as sufficient proof of a single continuous flow, when in fact `state` was leaked out-of-band because `shop_A` was never validated to be a real Shopify host during `begin_auth`. An attacker who owns a legitimate store can complete a genuine OAuth grant for their own shop (obtaining a real, Shopify-issued `code` and `hmac`), then submit the callback with the leaked `state` value that matches the victim's cookie, causing `validate_auth_callback` to accept it and drive the victim's session to be fixed to the attacker's shop/session — a forced OAuth completion / session-fixation, without ever needing the app's `api_secret_key`.

By contrast, other flows in this gem explicitly guard the `shop` value: [4](#0-3) [5](#0-4) [6](#0-5) 

`Auth::Oauth.begin_auth`/`auth_base_uri` has no such guard, which is the inconsistency exploited here.

### Impact Explanation
This matches the "High" category "session fixation or forced OAuth completion" from the impact taxonomy: an attacker can hijack the CSRF `state` binding that `validate_auth_callback` relies on to prove a single coherent OAuth transaction, letting them fix a victim's app session/cookie to a shop/session of the attacker's choosing without needing the app's `client_secret` or any leaked credential.

### Likelihood Explanation
Likelihood is Medium: it requires (1) the host application to pass an unvalidated, attacker-influenced `shop` value into `begin_auth` (a common integration pattern, since `shop` is typically taken from a query parameter on the app's own `/auth` endpoint), and (2) the attacker to lure the victim into visiting that endpoint and to also complete a real OAuth grant on a shop they control. No secrets or privileged access are required — only a normal Shopify store account (attacker's own) and the ability to get the victim to click a link.

### Recommendation
Validate `shop` with `Utils::ShopValidator` (the same guard already used in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, and `clients/graphql/storefront.rb`) inside `Auth::Oauth.begin_auth` before constructing `auth_base_uri`, rejecting any `shop` that is not a valid `*.myshopify.com` (or explicitly allow-listed) domain. Additionally, bind the `state` cookie/query check to the `shop` domain that initiated the flow (e.g., store `shop` alongside `state` in the cookie and compare both in `validate_auth_callback`) so a leaked `state` cannot be replayed against a different shop's callback.

### Proof of Concept
1. Host app exposes `GET /auth?shop=<params>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` — a typical integration.
2. Attacker sends victim a link to `https://merchantapp.example.com/auth?shop=evil.attacker.example`.
3. `begin_auth` builds `auth_route = "https://evil.attacker.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=<STATE>"` (per `lib/shopify_api/auth/oauth.rb:40-51`) and the host app sets a `shopify_per_user_grant` cookie with `value: <STATE>` on the victim's browser, then redirects.
4. Victim's browser lands on the attacker's server with `state=<STATE>` in the URL; attacker's server logs it. The victim's browser still carries the `<STATE>` cookie for `merchantapp.example.com`.
5. Attacker separately performs a real Shopify OAuth install on their own store `attacker-shop.myshopify.com`, obtaining a genuine `code` and Shopify-computed `hmac` for a callback query of their choosing (they control the `redirect_uri` target/params during their own real install).
6. Attacker gets the victim's browser (or replays victim's cookie) to hit `https://merchantapp.example.com/auth/callback?shop=attacker-shop.myshopify.com&code=<real_code>&state=<STATE>&hmac=<real_hmac>&timestamp=...&host=...`.
7. `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-73`) verifies the real Shopify HMAC (valid, since Shopify signed it for the attacker's own shop) and checks `state == auth_query.state`, which passes because `<STATE>` matches the cookie set in step 3 — completing OAuth and fixing the victim's session/cookie to the attacker's shop.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
