### Title
`AuroraEngineBridge.describeWithdrawal` unconditionally reports `completed`/`txHash: null`, regardless of on-chain outcome - (File: `packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts`)

### Summary
`AuroraEngineBridge.describeWithdrawal()` takes no arguments and always returns `{ status: "completed", txHash: null }`, no matter which withdrawal, index, or NEAR transaction it is asked about. `watchWithdrawal` treats this as a final, successful result and immediately resolves the completion promise for that withdrawal index.

### Finding Description
The claimed invariant is: `(status, txHash)` returned by `watchWithdrawal` for index *i* must correspond to the actual outcome of the *i*-th withdrawal the user signed for that route, and `completed` should only be reported once the destination transfer is final.

`AuroraEngineBridge.describeWithdrawal` in `packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts` lines 220-222:
```ts
async describeWithdrawal(): Promise<WithdrawalStatus> {
    return { status: "completed", txHash: null };
}
```
This method ignores its `WithdrawalIdentifier` argument entirely (index, tx hash, withdrawal params - nothing is read). It performs no RPC call, no receipt inspection, and no check on whether the underlying `ft_withdraw` intent's cross-contract call to the Aurora Engine contract (or proxy token contract, per `createWithdrawIntentPrimitive` in `aurora-engine-bridge-utils.ts`) actually succeeded, versus being refunded through NEP-141's standard `ft_resolve_transfer` refund path.

`watchWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts` lines 33-47) treats any `status === "completed"` as terminal success and immediately returns `{ hash: status.txHash }` (`null` here), short-circuiting the poll loop on the very first call - it never even reaches a second poll attempt.

Root cause: the bridge implementation is a stub that assumes the `ft_withdraw` intent's cross-contract deposit call to Aurora Engine always succeeds once the NEAR intent transaction settles, and never verifies the destination-side (Aurora Engine chain) transfer that the invariant explicitly requires ("`completed` is returned only after the destination transfer is final"). Because NEP-141 `ft_transfer_call` failures on the receiver's callback are resolved asynchronously after intent settlement (and can be rejected/refunded by Aurora Engine due to malformed `msg`, insufficient `min_gas`, insufficient `storage_deposit`, or destination-side rejection), it's entirely possible for the transfer to fail/refund while the SDK still reports `completed`.

This is independent of batch composition, ordering, or per-route vs per-tx indexing - the function does not consult `index`, `tx`, or `withdrawalParams` at all, so no amount of batch shaping is even needed to trigger the misreport; it is unconditional for every Aurora Engine/VirtualChain withdrawal. None of the existing guards (`validateAddress`, `validateWithdrawal`, `supports()` ordering, `FeeExceedsAmountError`, `assert` sanity checks) intercept this, because they all execute before intent signing/settlement and have no bearing on the post-settlement destination-transfer outcome that `describeWithdrawal` is supposed to check. ### Impact Explanation
Any integrator relying on `waitForWithdrawalCompletion` / `watchWithdrawal` (via `IntentsSDK`) to decide whether to credit a user, release custody, or refund on failure will always see `{ status: "completed", txHash: null }` for Aurora Engine (VirtualChain) route withdrawals, even if the underlying `ft_withdraw` cross-contract deposit was rejected/refunded by the Aurora Engine (or proxy token) contract. This matches the "High" impact category: a status/hash misreport that can cause an integrator to credit or refund based on a false completion signal, since `txHash: null` combined with `completed` provides no way to verify the on-chain transfer independently, and this is repeatable for every Aurora Engine withdrawal (single or batched, not just mixed-route batches).

### Likelihood Explanation
No special batch shaping, route mixing, or privileged access is required - a single ordinary VirtualChain/Aurora Engine withdrawal is sufficient. The precondition is simply: the destination-side `ft_transfer_call` to the Aurora Engine (or proxy) contract fails/refunds after the NEAR intent transaction settles (e.g., malformed deposit `msg`, insufficient `min_gas`/`storage_deposit`, or the target contract rejecting the deposit) — situations plausible in normal operation, not requiring attacker-crafted inputs beyond a routine VirtualChain withdrawal. Cost to the attacker/tester is essentially zero; this is fully deterministic and reproducible on every call.

### Recommendation
Implement real status checking in `AuroraEngineBridge.describeWithdrawal`: inspect the NEAR transaction's receipts for the `ft_withdraw` intent to determine whether the cross-contract call to the Aurora Engine (or proxy token) contract succeeded or was refunded (e.g., check for a `ft_resolve_transfer` refund receipt vs. a successful deposit event), and only return `completed` once the destination-side transfer is confirmed final; return `failed` if a refund is detected, and `pending` otherwise.

```ts
// packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.test.ts
import { describe, expect, it } from "vitest";
import { AuroraEngineBridge } from "./aurora-engine-bridge";
import { configsByEnvironment } from "@defuse-protocol/internal-utils";

describe("AuroraEngineBridge.describeWithdrawal", () => {
  it("always reports completed/null hash regardless of withdrawal identifier or on-chain outcome", async () => {
    const bridge = new AuroraEngineBridge({
      envConfig: configsByEnvironment.production,
      nearProvider: {} as any,
    });

    // Simulate a withdrawal whose ft_withdraw cross-contract call to Aurora Engine
    // was actually refunded on NEAR (no way to pass that info in, since the
    // function ignores its argument entirely).
    const refundedWid = {
      landingChain: "near:mainnet",
      index: 0,
      withdrawalParams: {} as any,
      tx: { hash: "refunded-tx", accountId: "attacker.near" },
    };

    const result = await bridge.describeWithdrawal(refundedWid as any);

    // BROKEN EQUALITY: expected {status: "failed"} or {status:"pending"} for a
    // refunded/unexecuted transfer, but SDK always claims success:
    expect(result).toEqual({ status: "completed", txHash: null });
  });
});
```
This demonstrates the equality break: `describeWithdrawal(wid)` for a refunded/never-executed withdrawal equals `describeWithdrawal(wid)` for a genuinely completed one — both return the identical `{status:"completed", txHash:null}` — violating "status/hash reflects actual destination-transfer finality."
