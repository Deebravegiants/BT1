### Title
Escrow withdrawals in IntentGatewayV2/IntentsBase trust stale recorded balances, causing fund freezing for rebasing/elastic-supply escrowed tokens - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` escrows a `TokenInfo[]` list into `_orders[commitment][token]` [3](#0-2)  and, notably, goes out of its way to measure the *actual* balance change on deposit to correctly support fee-on-transfer tokens [1](#0-0) . However, `_withdraw` in `IntentsBase.sol`, which is invoked for every fill, refund, and cancellation path (`RedeemEscrow`, `RefundEscrow`, same-chain `fillOrder`/`cancelOrder`), releases funds using only the recorded `_orders[commitment][token]` bookkeeping value, never re-validating against the token's actual `balanceOf(this)` [4](#0-3) . If the escrowed token is a rebasing/elastic-supply ERC20 (e.g. Ampleforth-style tokens whose balances mutate via periodic mint/burn without transfers), the sum of all `_orders[...]` entries recorded at deposit time can exceed the gateway's real token balance after a negative rebase.

### Finding Description
The escrow accounting model records a fixed `amount` per `(commitment, token)` pair at deposit time in `placeOrder` [3](#0-2) . This value is treated as an IOU that is redeemed later via `_withdraw`:

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
``` [5](#0-4) 

Unlike `placeOrder`, which snapshots `balanceOf` before/after transfers specifically to handle non-standard token transfer semantics [6](#0-5) , no equivalent check exists on the withdrawal side. For a rebasing token, the gateway's actual balance drifts independently of the sum of all `_orders[...][token]` bookkeeping entries across all pending orders — a negative rebase (burn-style supply contraction, e.g. AMPL) shrinks the real balance below what is collectively owed. Because withdrawals are processed on a first-come/first-served basis against a shared, undifferentiated token balance, whichever order is redeemed first (`RedeemEscrow` on solver fill, `RefundEscrow`/`cancelOrder` on timeout/cancellation) drains real tokens irrespective of other outstanding orders' claims, and later orders' `safeTransfer` calls revert once the real balance is insufficient, permanently reverting `onAccept`/`cancelOrder` for those beneficiaries since their recorded escrow entry never gets corrected to reflect the shortfall.

This same static-bookkeeping pattern is repeated in the partial-fill path of `IntrinsicIntents.sol`, where `escrowedAmount` is taken directly from `_orders[commitment][token]` [7](#0-6)  rather than the contract's live balance.

### Impact Explanation
This is a Medium-severity permanent freezing-of-funds bug: for any order whose input token undergoes negative rebases while escrowed (a normal daily occurrence for tokens like AMPL), some subset of legitimately entitled beneficiaries — solvers awaiting `RedeemEscrow` fill payouts or users awaiting `RefundEscrow`/`cancelOrder` refunds — can have their `safeTransfer` calls in `_withdraw` revert indefinitely because the gateway's actual token balance is lower than the sum of outstanding bookkeeping claims. Since the escrow ledger is never reconciled against real balance, these funds become permanently unrecoverable through the intended withdrawal path.

### Likelihood Explanation
Reaching this path requires no special privilege — any unprivileged user calling `placeOrder` with a rebasing ERC20 as an input token triggers the vulnerable accounting, and any relayer delivering a legitimate `RedeemEscrow`/`RefundEscrow` post request, or the user itself calling `cancelOrder`, exercises the flawed `_withdraw` release logic. The likelihood scales with how commonly rebasing tokens are accepted as intent inputs; the protocol's own fee-on-transfer handling in `placeOrder` [8](#0-7)  shows non-standard ERC20 support is an explicit design goal, making this a realistic configuration rather than a contrived edge case.

### Recommendation
Either (a) explicitly disallow rebasing/elastic-supply tokens as intent input assets (e.g. via an allowlist enforced in `placeOrder`), or (b) mirror the deposit-side `balanceOf` delta accounting at withdrawal time in `_withdraw`, capping the transferred `amount` to `min(recordedAmount, actualContractBalanceAttributableToThisOrder)` and reconciling any shortfall pro-rata across outstanding claims rather than allowing a race where the first withdrawer takes real tokens on behalf of the ledger's promised (but unbacked) totals.

### Proof of Concept
1. Deploy `IntentGatewayV2` with a mock rebasing ERC20 `RBT` (simulate via a `rebase(int256 delta)` function that mints/burns proportionally across all holders, similar to AMPL).
2. User A calls `placeOrder` with `inputs = [{token: RBT, amount: 1000}]`; gateway records `_orders[commitmentA][RBT] = 1000` and physically holds `1000 RBT`.
3. User B calls `placeOrder` with the same token, recording `_orders[commitmentB][RBT] = 1000`; gateway now holds `2000 RBT`, bookkeeping sum = `2000`.
4. Trigger a negative rebase on `RBT` reducing the gateway's real balance to `1200 RBT` (40% contraction), while `_orders[commitmentA][RBT] + _orders[commitmentB][RBT]` bookkeeping remains `2000`.
5. Relayer delivers a `RedeemEscrow`/`RefundEscrow` request for commitmentA; `_withdraw` calls `IERC20(RBT).safeTransfer(beneficiaryA, 1000)`, succeeding and draining `1000` of the remaining `1200 RBT`.
6. Relayer delivers the corresponding request for commitmentB; `_withdraw` attempts `safeTransfer(beneficiaryB, 1000)` against a real balance of only `200 RBT`, which reverts — permanently freezing User B's escrowed funds since `_orders[commitmentB][RBT]` still shows `1000` owed but the gateway can never restore that balance.
