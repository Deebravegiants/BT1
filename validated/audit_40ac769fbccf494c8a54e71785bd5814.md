### Title
Deflationary/fee-on-transfer token support missing in Tron `IntentGatewayV2.placeOrder` causes escrow over-crediting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` escrows the *requested* input amount (minus protocol fee) rather than the amount actually received from `safeTransferFrom`, unlike the EVM mainline `IntentGatewayV2.sol`, which was explicitly hardened against fee-on-transfer/deflationary tokens by measuring balance deltas.

### Finding Description
In the Tron contract's `placeOrder`, tokens are pulled with a plain `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and the contract immediately credits the ledger with the pre-computed `reducedInputs[i].amount` (`order.inputs[i].amount` minus protocol fee), with no verification of the actual balance change: [1](#0-0) 

The same unconditional credit pattern is used in the predispatch branch, which sweeps the dispatcher's balance and still credits `reducedInputs[i].amount` rather than the swept `balance` (only "dust" surplus is emitted, no deficit handling): [2](#0-1) 

Additionally, the commitment hash is computed from `order.inputs` (the pre-fee, requested amounts) before any transfer occurs, at lines [3](#0-2) , so there is no mechanism anywhere in this function to reconcile the ledger with what the gateway actually holds.

This is exactly the bug class from the external report: the contract "increases `user.amount` by `_amountToStake`" (here, `_orders[commitment][token]`) without verifying the real received amount, which breaks accounting for deflationary/fee-on-transfer ERC20 tokens.

By contrast, the canonical EVM `IntentGatewayV2.sol` fixes this by snapshotting balances before/after each transfer and mutating `order.inputs[i].amount` to the actual received amount before computing fees, the commitment, and escrow credits: [4](#0-3) 
This fix is explicitly covered by regression tests for fee-on-transfer tokens: [5](#0-4) . The Tron deployment lacks this protection entirely.

### Impact Explanation
If a pool/order is created using a deflationary or fee-on-transfer ERC20 on the Tron deployment, the gateway will hold strictly less of that token than the amount recorded in `_orders[commitment][token]`. Because `_orders` is a global per-token ledger shared across all commitments/orders, this creates a shortfall: the gateway's real token balance can no longer back the sum of all outstanding escrow entitlements. When a solver later fills/settles an order (or a user cancels and expects a full refund) and the withdrawal path attempts to transfer the escrowed amount, either (a) the transfer for that order fails once the aggregate shortfall exhausts the actual balance — freezing funds/reverting settlement for other legitimate orders sharing that token — or (b) an earlier order's withdrawal consumes tokens balance-wise that were nominally allocated to a different, later order, effectively socializing losses across users of the same token. This is a fund-freezing/fund-loss condition reachable by any unprivileged user simply by placing an order with a deflationary token.

### Likelihood Explanation
Likelihood is straightforward to trigger: any user can call `placeOrder` with an arbitrary ERC20 token address, including a deflationary/fee-on-transfer token, with no on-chain guard rejecting such tokens. No privileged role or special conditions are required — a single `placeOrder` transaction is sufficient to desynchronize the ledger from actual balances.

### Recommendation
Mirror the fix already present in the canonical EVM `IntentGatewayV2.sol`: measure the gateway's actual token balance before and after each `safeTransferFrom` (and after the predispatch sweep), mutate `order.inputs[i].amount` to the actually-received amount, and derive the protocol fee, commitment hash, and `_orders[commitment][token]` credit from that verified amount rather than the caller-supplied `amount`. Alternatively, explicitly reject non-standard tokens (e.g., via a pre-registered token allowlist) if fee-on-transfer support is not intended for the Tron deployment.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% burn on transfer, as in the `FeeOnTransferToken` test helper: [6](#0-5) ).
2. On the Tron `IntentGatewayV2`, call `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`. `safeTransferFrom` moves only 990e18 to the gateway, but `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount` (≈1000e18 minus protocol fee), i.e., more than the gateway actually received.
3. Repeat with a second order for the same token. The sum of `_orders[...][FOT]` entitlements now exceeds the gateway's real `FOT` balance.
4. When solvers attempt to fill/withdraw against these commitments (or users cancel), the total ERC20 transfers required exceed the gateway's holdings; the last withdrawal(s) revert due to insufficient balance, freezing that user's funds, or an earlier withdrawal drains balance that belonged to a different order's escrow.

Note: Full withdrawal/cancel-path code (`withdraw`/`cancelOrder` internals) for the Tron contract could not be retrieved in this session due to index limits; the accounting mismatch at the point of escrow crediting was verified directly, and the downstream impact on shared-balance settlement is inferred from the ledger design (`_orders[commitment][token]` as a per-token map on a contract holding real ERC20 balances) confirmed in the `placeOrder` code shown above. A Devin session with full repo access is recommended to trace the exact withdraw path in this file for final confirmation of the exact reversion/loss mechanics.

            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),

            output: output
        });

        assertEq(
            intentGateway._orders(commitment, address(fot)),

            "Escrow should equal actual received amount"
        );

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
