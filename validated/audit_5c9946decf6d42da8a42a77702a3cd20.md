### Title
Webhook `shop` (and other identity fields) are read from unauthenticated headers and never covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw JSON body via `to_signable_string` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from HTTP headers with no cryptographic binding to that body [2](#0-1) . `Registry.process` validates only this body-only HMAC and then forwards the unauthenticated `request.shop` value to the app's handler as the tenant identifier [3](#0-2) .

### Finding Description
The equality the library implicitly claims to guarantee is: `shop_header == shop_that_produced(signed_body)`. In reality the HMAC only proves `HMAC(api_secret_key, raw_body) == received_signature`; it says nothing about which shop the body came from, since `api_secret_key` is the same for every shop connected to a given app. An attacker (or a compromised intermediary) who possesses one valid `(raw_body, hmac)` pair for topic X — trivial to obtain since bodies for many topics are static or attacker-influenced JSON, and the HMAC is deterministic per body — can replay that exact body with an arbitrary `x-shopify-shop-domain` / `shopify-shop-domain` header. `HmacValidator.validate` still passes because it only recomputes the digest over `@raw_body` [4](#0-3) , and `Request#shop` simply returns the caller-supplied header verbatim [5](#0-4) . The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [6](#0-5) , which is misleading: it verifies the body's origin, not the shop attribution, yet `data.shop` is passed to the host application's handler as if it were verified, and the docs' own example uses it directly as a tenant key (`shop_domain: data.shop`) [7](#0-6) .

### Impact Explanation
This breaks the cross-tenant boundary: a webhook payload legitimately generated for Shop A can be relabeled to appear as if it belongs to Shop B, causing the host application to attribute Shop A's order/customer/app-uninstall data to Shop B's session/tenant record. Depending on how the host app uses `data.shop` (e.g., to look up the session for making follow-up API calls, or to update per-shop records), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to already have obtained one valid `(body, hmac)` pair for the target app (e.g., from a shop they control, or from a previously observed delivery), which is plausible since app developers commonly test webhooks on their own store or log deliveries. Once obtained, replaying it with a forged shop header requires no knowledge of `api_secret_key` and no privileged access, satisfying the "unprivileged internet user" threat model.

### Recommendation
Do not treat header-derived `shop`/`topic`/`webhook_id` as trusted without additional verification. At minimum, cross-check the header-provided shop against the shop embedded in `body["shop_domain"]`/webhook payload where available, or require host applications to independently authorize the shop via a stored, previously-registered webhook subscription id/shop mapping before acting on `data.shop`. Consider including the identity headers in the signed payload used for HMAC comparison, or documenting explicitly that `data.shop` is unauthenticated and must be revalidated by the consuming application before being used as a tenant key.

### Proof of Concept
1. App registers webhook, Shopify delivers `POST /callback` with body `{"id":123}"`, headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
2. Attacker (or malicious middlebox) resends the identical raw body and HMAC, changing only `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged header [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the untouched body [9](#0-8) .
4. The registered handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the payload was never generated for shop-b, and acts on it as if verified.

            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
