### Title
Vault `SecretsDelete` gateway handler executes deletion using unvalidated client-supplied owner instead of the authorized owner - ([File: core/capabilities/vault/gw_handler.go])

### Summary
The Vault gateway handler's delete-secrets path authorizes the *request envelope* (its digest/JWT identity) but then executes the deletion using the `Owner` field taken verbatim from the client-controlled request body, without rebinding it to the authorized owner. This is architecturally inconsistent with the sibling `list` path, which explicitly overwrites the owner with the authorized value before calling the backing service, confirming that the `Owner` field in these methods is not otherwise cryptographically bound to the authorized identity.

### Finding Description
`GatewayHandler.HandleGatewayMessage` routes `MethodSecretsDelete` and `MethodSecretsList` through the same authorization pipeline, `GatewayVaultRequestProcessor.ProcessRequest` → `processDeleteSecretsRequest` / `processListSecretIdentifiersRequest` → `authorizeAndStamp`, which calls `Authorizer.AuthorizeRequest` and, on success, only rewrites the JSON-RPC envelope ID (prefixing it with the authorized owner) and stamps the `RequestId` field into params. [1](#0-0) 

Critically, `authorizeAndStamp` never rewrites the `Owner`/`Ids[].Owner` fields inside the request body itself for delete or list requests — it only stamps the request ID. For **create/update** requests, this is safe because `EnsureRightLabelOnSecret` cryptographically verifies that each `EncryptedSecret.Id.Owner` matches the TDH2 ciphertext label, so the owner cannot be spoofed independently of the actual encrypted payload: [2](#0-1) 

For **list**, the handler compensates for the lack of binding by explicitly overwriting the client-supplied owner with the authorized owner right before calling the backing service: [3](#0-2) 

For **delete**, however, no equivalent rebind exists. `handleSecretsDelete` unmarshals the (already "authorized") request params directly and passes the client-supplied `Ids` — including each `Id.Owner` — straight to `h.secretsService.DeleteSecrets`, with no check that `id.Owner` equals `authResult.AuthorizedOwner()`: [4](#0-3) 

The corresponding validator, `ValidateDeleteSecretsRequest`, only checks structural well-formedness of each `SecretIdentifier` (non-empty, valid characters, length limits) — it never compares `id.Owner` against any authorized identity: [5](#0-4) 

This is precisely the "access control check implemented after asset is accessed" bug class described in the report: the request is authenticated/authorized as *a* legitimate request (a specific digest is on the allowlist, or a JWT is valid), but the specific asset targeted by the privileged operation (secrets belonging to `id.Owner`) is never re-validated against the identity that was actually authorized before the delete is executed against the backing `secretsService`.

Whether this is exploitable in the allowlist-based auth path depends on how tightly the on-chain allowlist digest binds to the full request body (including `Owner`) versus the JWT-based auth path, where authorization derives from token identity rather than a whole-body digest — the very asymmetry that made the `handleSecretsList` explicit-overwrite necessary in the first place implies the same gap exists for delete.

### Impact Explanation
If an attacker can get a `SecretsDelete` request authorized (e.g., via a validly signed/allowlisted envelope for their own identity, or via JWT-based auth that binds identity but not the full payload) while supplying `Ids[].Owner` values belonging to a different, victim owner, the vault node will delete that victim's secrets. This is an unauthorized cross-tenant destructive operation (fund/config/credential loss for another workflow owner) triggered by an unprivileged client request through the internet-facing gateway pipeline.

### Likelihood Explanation
Likelihood depends on the exact binding strength of the specific `Authorizer` implementation in use (`allowListBasedAuth` binds by whole-request digest against on-chain allowlisted requests, which may make owner spoofing hard since digest changes on any params tampering; but `jwtBasedAuth`, referenced in `NewGatewayHandler`, authorizes based on token-derived identity separate from arbitrary request body fields). The explicit `r.Owner = authResult.AuthorizedOwner()` rebind present only in the `list` handler strongly suggests the codebase authors were aware this binding is not universal across auth strategies, making the missing equivalent check in `handleSecretsDelete` a real gap rather than defense-in-depth.

### Recommendation
In `handleSecretsDelete` (`core/capabilities/vault/gw_handler.go`), reject or overwrite any `Ids[].Owner` that does not equal `authResult.AuthorizedOwner()` before calling `h.secretsService.DeleteSecrets`, mirroring the pattern already used in `handleSecretsList`. More generally, move ownership-scoping enforcement into `ValidateDeleteSecretsRequest`/`processDeleteSecretsRequest` so it is structurally guaranteed for every auth backend, rather than relying on each handler to remember to apply it.

### Proof of Concept
1. Obtain valid authorization for a `SecretsDelete` request as owner A (e.g., a validly signed/allowlisted envelope, or a JWT identifying owner A) sent to the gateway/node.
2. Craft the JSON-RPC `DeleteSecretsRequest` params with `Ids: [{Key: "victim_secret", Owner: "<owner B>"}]`.
3. Because `authorizeAndStamp` only authorizes the envelope/digest and stamps the request ID (not the `Owner` fields), and `ValidateDeleteSecretsRequest`/`handleSecretsDelete` never compare `Ids[].Owner` to `authResult.AuthorizedOwner()`, the request proceeds to `secretsService.DeleteSecrets` with owner B's identifier, deleting owner B's secret despite the request only ever being authorized for owner A.

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil

func (r *RequestValidator) ValidateDeleteSecretsRequest(ctx context.Context, request *vaultcommon.DeleteSecretsRequest) error {
	if request.RequestId == "" {
		return errors.New("request ID must not be empty")
	}
	if err := r.MaxRequestBatchSizeLimiter.Check(ctx, len(request.Ids)); err != nil {
		if errBoundLimited, ok := errors.AsType[limits.ErrorBoundLimited[int]](err); ok {
			return fmt.Errorf("request batch size exceeds maximum of %d: %w", errBoundLimited.Limit, err)
		}
		return fmt.Errorf("failed to check request batch size limit: %w", err)
	}
	if len(request.Ids) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}

	uniqueIDs := map[string]bool{}
	for idx, id := range request.Ids {
		if id == nil {
			return errors.New("secret ID must not be nil at index " + strconv.Itoa(idx))
		}
		if err := r.ValidateSecretIdentifier(ctx, id.Key, id.Owner, id.Namespace); err != nil {
			return fmt.Errorf("invalid secret identifier at index %d: %w", idx, err)
		}

		_, ok := uniqueIDs[vaulttypes.KeyFor(id)]
		if ok {
			return errors.New("duplicate secret ID found at index " + strconv.Itoa(idx) + ": " + id.String())
		}

		uniqueIDs[vaulttypes.KeyFor(id)] = true
	}
	return nil
}

func (h *GatewayHandler) handleSecretsDelete(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.DeleteSecretsRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized delete secrets request", "request", r.String())
	resp, err := h.secretsService.DeleteSecrets(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to delete secrets: %w", err))
	}

	resultBytes, err := resp.ToJSONRPCResult()
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&resultBytes),
	}
}
