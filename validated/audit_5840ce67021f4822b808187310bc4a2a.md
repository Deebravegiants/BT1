### Title
Vault request digest can be griefed via replay guard front-running to cause permanent denial of service - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
The Vault gateway authorization pipeline computes a deterministic `digest` from the JSON-RPC request body (method + params) and uses it both as the on-chain allowlist key [1](#0-0)  and as the key for a single-use `RequestReplayGuard` that rejects any request whose digest was already seen [2](#0-1) . Because the digest is derived purely from the (unencrypted/deterministic) request content rather than any secret unique to the actual submitter, any party who can observe or reconstruct an allowlisted request's exact JSON-RPC body can compute the same digest and submit it to the gateway ahead of the legitimate owner.

### Finding Description
This mirrors the `CardTopupPermit` griefing pattern: a privileged action is gated by a value (the ERC20 permit signature / here, the request digest) that must match exactly, and once "consumed," a legitimate resubmission by the rightful actor fails permanently. In `allow_list_based_auth.go`, `AuthorizeRequest` computes `req.Digest()` and looks it up against on-chain allowlisted entries recorded via `AllowlistRequest(owner, digest, expiry)` [1](#0-0) . Successful authorization is then recorded in the shared `RequestReplayGuard`, and any later request with the identical digest is rejected with `ErrRequestAlreadySeen` [3](#0-2) ; this is explicitly reused for both `AllowListBasedAuth` and `JWTBasedAuth` [4](#0-3) . Because the digest is a hash of request content and is publicly known once the owner allowlists it on-chain (`AllowlistRequest` is an on-chain transaction, visible in the mempool/logs, as shown in the system test helper) [5](#0-4) , an attacker who observes the allowlisting transaction (which necessarily reveals the exact `RequestDigest`) can reconstruct or intercept the exact JSON-RPC request and race it to the gateway before the legitimate owner does. Once the malicious duplicate is processed, the replay guard permanently marks that digest as seen, and the real owner's subsequent submission is rejected with "request was already authorized previously" — exactly analogous to the attacker calling `permit()` first to consume the nonce before `CardTopupPermit` can use it.

### Impact Explanation
If the exact request body (and thus digest) can be reconstructed or observed off-chain before the legitimate owner submits it to the gateway, an attacker can permanently deny that specific vault operation (secrets create/list/delete) for the legitimate owner, since the on-chain allowlist entry is single-use per digest and the replay guard enforces exactly one acceptance. This is a Medium-severity availability/DoS impact consistent with the reported bug class, not a fund-theft or authentication bypass.

### Likelihood Explanation
Exploitability depends on how easily an attacker can learn/reconstruct the exact digest-producing request body before the real owner submits it. The digest itself is not secret — it is published on-chain via `AllowlistRequest` — but reconstructing the exact underlying request bytes (which must hash to that digest) from just the digest is not generally feasible unless the attacker also observes the actual JSON-RPC payload (e.g., via network interception, a malicious/observing gateway, or if the client publishes the payload alongside the on-chain allowlisting). This significantly limits likelihood compared to the original ERC20 permit case, where the signature (which is directly reusable) is visible in the mempool.

### Recommendation
Bind the replay-guard/allowlist consumption to the authenticated submitter identity (e.g., require that the caller's derived owner from a companion signature matches `allowlistedRequest.Owner` before treating the digest as consumed), or make the on-chain allowlist entry track "claimed" state tied to a nonce/session controlled by the legitimate owner instead of solely a content digest, so that an attacker submitting a copy of the request without the right to claim it does not consume the single-use allowlist slot.

### Proof of Concept
1. Workflow owner calls `AllowlistRequest(requestDigest, expiryTimestamp)` on-chain for a specific vault JSON-RPC request body (visible in the `AllowlistRequest` transaction/logs) [5](#0-4) .
2. Attacker, having learned/reconstructed the exact request body that hashes to `requestDigest` (e.g., through log/traffic observation), sends that identical JSON-RPC request to the gateway before the real owner does.
3. `allowListBasedAuth.AuthorizeRequest` finds the allowlisted digest and succeeds, and `RequestReplayGuard.CheckAndRecord` records the digest as seen [2](#0-1) .
4. The legitimate owner then submits the same request; the replay guard rejects it with `ErrRequestAlreadySeen`, denying the intended operation, as reproduced in `TestVaultHandler_HandleJSONRPCUserMessage`'s "duplicate requestId" case [6](#0-5) .

var ErrRequestAlreadySeen = errors.New("request was already authorized previously")

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
