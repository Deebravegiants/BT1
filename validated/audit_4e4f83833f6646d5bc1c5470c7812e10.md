Audit Report

## Title
View-role users can read bridge adapter outgoing authentication tokens via unrestricted `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` - (File: core/web/router.go)

## Summary
The bridge type read endpoints (`Index`/`Show`) are registered without `auth.RequiresEditRole`, so any authenticated user with the lowest-privilege `view` role can retrieve the `OutgoingToken` secret used to authenticate the node to external bridge adapters. Mutation endpoints on the same resource correctly require the `edit` role, confirming this is an inconsistency in the intended RBAC design rather than an accepted behavior.

## Finding Description
In `core/web/router.go`, `GET /bridge_types` and `GET /bridge_types/:BridgeName` are wrapped only by the generic `authv2` session/token authentication group, while `Create`, `Update`, and `Destroy` are wrapped with `auth.RequiresEditRole`. `RequiresEditRole` rejects requests from users whose role is `view` or `run`, but since it's absent on the GET routes, `view`-role users pass through to the handlers. The `Index` and `Show` handlers in `core/web/bridge_types_controller.go` build responses via `presenters.NewBridgeResource`, which copies `b.OutgoingToken` into the `BridgeResource.OutgoingToken` field. That field is tagged `json:"outgoingToken"` (no `omitempty`), so it is always serialized in the response — unlike `IncomingToken`, which is intentionally tagged `omitempty` and left blank after creation specifically to avoid leaking it on subsequent reads. This asymmetry (protecting `IncomingToken` from being re-exposed, but not `OutgoingToken`) combined with the missing role check on GET routes is the root cause. The RBAC test suite in `core/web/auth/auth_test.go` explicitly encodes `viewOnlyAllowed: true` for both bridge GET routes, confirming the current (missing) restriction is by design/test expectation rather than a bug in test coverage — but this contradicts the treatment of `IncomingToken` and of write operations on the identical resource, indicating the read endpoints were not intended to leak node-to-adapter secrets to read-only accounts.

## Impact Explanation
Any user provisioned with only the `view` role (e.g. auditor/read-only dashboard account) can retrieve the `OutgoingToken` for any configured bridge via a single unauthenticated-role-elevation-free GET request. This token is used by the node to authenticate itself when calling out to external bridge/adapter services; possessing it could allow an attacker to impersonate the node to the adapter or replay/correlate authorized traffic, which is a legitimate secret-exfiltration impact for a lower-privileged role than intended.

## Likelihood Explanation
Exploitation requires only a valid `view`-role session or API token and a single `GET` request — no bypass, timing, or additional access is needed. The RBAC test table itself proves this is reachable in the current codebase for `view` accounts.

## Recommendation
Add `auth.RequiresEditRole` to the `GET /bridge_types` and `GET /bridge_types/:BridgeName` routes, or strip/redact `OutgoingToken` from `BridgeResource` responses when the requesting user's role is below `edit`, mirroring the existing `omitempty` treatment given to `IncomingToken`.

## Proof of Concept
1. Create a bridge with `POST /v2/bridge_types` as an `edit`/`admin` user, noting the returned `outgoingToken`.
2. Provision a session/API token for a user with `Role: view`.
3. Send `GET /v2/bridge_types/<bridgeName>` using the `view` credentials.
4. Observe the JSON:API response's `attributes.outgoingToken` field contains the secret, despite the requester having only `view` privileges — reproducible via a Go test extending `TestAuth_RBAC` (or similar) in `core/web/auth/auth_test.go`, or via `bridge_types_controller_test.go` asserting response body content under a `view`-role client.

```go
// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
