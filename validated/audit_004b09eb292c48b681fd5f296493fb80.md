### Title
Webhook shop-domain identity spoofing due to HMAC binding only the raw body, not the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` field from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body via `Request#to_signable_string`. The webhook signing secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app — it is not shop-specific. This breaks the intended identity binding `hmac == HMAC(secret, body)` from also covering `shop`, so `Registry.process` trusts `request.shop` without it ever being authenticated by the signature it just validated.

### Finding Description
`HmacValidator.validate` verifies only that `computed_signature == received_signature` where `computed_signature` is derived exclusively from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`, while `shop` is read straight from a header that is never included in the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` — the unauthenticated field — to the app's handler as trusted tenant identity: [4](#0-3) 

Because `Context.api_secret_key` is the app's single `client_secret` and is identical for every shop that installs the app (this is how Shopify signs all webhooks for a given app), any actor who has installed the app on a shop they control (e.g. a free development store, which anyone can create) will legitimately receive real webhooks with valid `hmac-sha256` values for bodies of their choosing. Because the `shop` field is not part of the signed string, that same valid `(raw_body, hmac)` pair can be replayed with an altered `x-shopify-shop-domain` header claiming to be a different, victim shop, and `HmacValidator.validate` will still return `true`.

Equality that should hold but does not: `shop_authenticated_by_hmac == shop_delivered_to_handler`. Before the request: Shopify sends `(body_A, hmac_A, shop=A)` to the app for tenant A, where `hmac_A = HMAC(secret, body_A)` (secret is app-wide). After the attacker's crafted request: `(body_A, hmac_A, shop=B)` is delivered to the same endpoint. `Utils::HmacValidator.validate` still passes because it only checks `hmac_A` against `body_A`; `WebhookMetadata` is then built with `shop: "B"`, `body: parsed_body_of_A`, and forwarded to the host application's handler as an authenticated event for shop B.

### Impact Explanation
This is a cross-tenant identity-binding failure: the library asserts webhook authenticity via `Utils::HmacValidator.validate` but hands the host application a `shop` value that was never bound to that authenticity check. Host applications that use `WebhookMetadata#shop` (built directly from `request.shop`) to select the merchant/session context to act on — the documented and expected usage pattern for this gem's webhook handling — can be made to process attacker-supplied webhook content (including for topics like `app/uninstalled`, `shop/redact`, or order/customer data topics) under the identity of an arbitrary victim shop, leading to cross-tenant data confusion or state corruption.

### Likelihood Explanation
Any user can register as a Shopify Partner and install a public/development app on a store they control at no privileged cost, which is enough to legitimately receive real, validly-signed webhooks for that app. Replaying the same body/HMAC pair with a substituted `shop-domain` header requires no secret material — `client_secret`, tokens, and TLS interception are not needed. The only requirement is the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers, which is standard unauthenticated internet access.

### Recommendation
Bind the shop identity into the authenticated material before trusting it: either include the `shop-domain` header value in the signed string checked by `HmacValidator` (mirroring the OAuth `AuthQuery#to_signable_string` pattern, which does sign `shop`), or cross-validate `request.shop` against an independently-trusted source (e.g., the shop associated with the resolved webhook subscription/session) before constructing `WebhookMetadata` and invoking the handler in `Registry.process`.

### Proof of Concept
1. Install the target public app on an attacker-controlled development store `attacker.myshopify.com`.
2. Trigger any webhook topic the app subscribes to; Shopify delivers `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256 = HMAC-SHA256(client_secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture `(B, hmac)` and replay it to the same endpoint, changing only `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only rehashes `raw_body`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, i.e., attacker-controlled content attributed to the victim tenant.
