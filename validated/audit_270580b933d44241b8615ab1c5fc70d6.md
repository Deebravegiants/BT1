## Analog Found: Unchecked-length `from` field causes slice/arithmetic panic in `HyperFungibleToken::on_accept`

### Title
Unvalidated `message.from` length in `on_accept` causes subtraction underflow and out-of-bounds slice panic - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The QNET6 dissector bug mishandled a variable-length MAC address field without validating it before deriving an offset into the packet, producing an out-of-bounds read and a crash on a crafted packet. The direct analog is in the Hyper Fungible Token (HFT) ISMP module handler: `message.from` (an ABI-decoded, attacker-influenced dynamic `bytes` field, not a source-checked ISMP header) is consumed with `from_bytes.len() - 20` without any prior length check, unlike its sibling field `message.to`, which is explicitly validated to be exactly 20 or 32 bytes a few lines earlier.

### Finding Description
In `on_accept`, the recipient field is defensively validated: [1](#0-0) 

But when calldata execution requires deriving an origin from the sender (no signature supplied), the sender field is used unchecked: [2](#0-1) 

`message` is produced by `Message::abi_decode(&body)` where `body` is the raw ISMP `PostRequest` payload: [3](#0-2) 

`Message.from` is ABI type `bytes` (dynamic), as shown by the sending-side encoder which wraps an arbitrary-length vector into it: [4](#0-3) 

Because `Message.from` is a dynamic `bytes` field inside the ABI-encoded body (not the ISMP-level dispatcher `from`/module-id, which is separately authenticated via `ContractToAsset::get(source, &from)`), its length is not constrained by protocol framing — it is only as trustworthy as whatever logic assembled the request body on the source chain. The destination-side handler makes no length assertion on it before computing `from_bytes.len() - 20` when `source.is_evm()` is true. If `from_bytes.len() < 20`, this integer subtraction underflows (`usize` wraps to a near-`usize::MAX` value in release/wasm builds where overflow checks are typically disabled), and the subsequent slice expression `&from_bytes[from_bytes.len() - 20..]` panics with an out-of-bounds range, exactly mirroring the QNX6 MAC-address mishandling that caused Wireshark's OOB read/crash on a crafted packet.

### Impact Explanation
A panic inside `on_accept`, which runs during ISMP message-dispatch execution on-chain (reachable from `pallet-ismp`'s `handle_unsigned` / message delivery path that a relayer drives), aborts execution of that extrinsic/block-processing path. Because Substrate does not gracefully catch panics from arbitrary logic inside dispatchable execution the same way it catches `Result::Err`, a reachable panic in a widely-used token-bridge module is a denial-of-service vector against block production/import for every node executing that message, i.e. any unprivileged relayer delivering a mis-formed cross-chain message can bring the chain to a halt.

### Likelihood Explanation
The `to` field's careful validation (`InvalidRecipientLength`) right next to the unchecked `from` usage indicates the omission is unintentional, not an intended trust boundary. Any code path that reaches `on_accept` with `source.is_evm()`, a non-empty `message.data` that decodes to `SubstrateCalldata` with `signature: None`, and a `message.from` shorter than 20 bytes will trigger the underflow. Exploitability, however, still depends on whether an untrusted party can influence the raw `Message.from` bytes independently of the honest EVM contract's encoding (which always ABI-encodes the 20-byte `msg.sender`); the code as-is provides no independent guarantee against this, unlike the `to` field. This uncertainty (whether the ABI encoding path can be forced to emit a sub-20-byte `from`) is the outstanding item to confirm to fully weaponize this finding — the index-panic mechanism itself is verifiable and concrete.

### Recommendation
Validate `from_bytes.len()` before use, mirroring the existing pattern used for `to_bytes` (accept only 20 or 32 bytes, return `HftError::InvalidSenderLength` otherwise) rather than performing an unchecked subtraction and slice.

### Proof of Concept
1. Craft (or have a source-chain contract emit) a `PostRequest` whose ABI-encoded `body` decodes to a `Message` with `from` set to fewer than 20 bytes (e.g., 1 byte), `data` non-empty and decodable as `SubstrateCalldata { signature: None, runtime_call: <any valid encoded call> }`.
2. Deliver this request through the standard ISMP delivery path so `on_accept` executes with `source.is_evm() == true`.
3. Execution reaches `from_bytes.len() - 20` with `from_bytes.len() == 1`, underflowing to `usize::MAX - 18`; the following slice `&from_bytes[from_bytes.len()-20..]` panics with an out-of-bounds range error, aborting extrinsic/block execution. [2](#0-1)
