## Analysis

The reported bug class (raw `transferFrom`/`transfer` calls that mishandle ERC-20 return-value semantics) has been fixed in the primary EVM contracts — `evm/src/apps/intentsv2/IntentsBase.sol` now uses `SafeERC20.safeTransfer`/`safeTransferFrom` throughout [1](#0-0) , and `evm/src/apps/IntentGatewayV2.sol` escrows inputs with `safeTransferFrom` [2](#0-1) .

However, the Tron port of the intent gateway, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still contains the vulnerable pattern in its escrow-release paths (`withdraw()` and the `SweepDust` handler), which use a raw low-level `.call` and only check the call's `success` boolean without decoding/validating the returned data: [3](#0-2) 

and [4](#0-3) 

### Title
Escrow release in Tron `IntentGatewayV2.withdraw()`/`SweepDust` accepts non-reverting token transfers that return `false`, permanently freezing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed input tokens to solvers/beneficiaries (`withdraw`, called from `onAccept` for `RedeemEscrow`/`RefundEscrow`) and sweeps protocol dust (`SweepDust`) using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, checking only that the call itself did not revert (`success`), never inspecting or requiring the ABI-decoded boolean return value.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`_orders[body.commitment][token] -= amount;` and `_filled[body.commitment] = beneficiary;` are set unconditionally based only on the call not reverting [3](#0-2) . A low-level `.call` returns `success = true` whenever the callee does not revert, regardless of what boolean value (if any) is returned in the payload. Legacy/non-standard ERC-20 tokens that signal failure by returning `false` instead of reverting (e.g., due to a paused state, blacklist, or insufficient balance edge case) will cause `success` to be `true` even though no tokens actually moved. The same unchecked pattern is used for the `SweepDust` request handler [4](#0-3)  and for the transaction-fee payout that follows `withdraw` [5](#0-4) .

This is the same root cause class as the reported `TrailsIntentEntrypoint` bug — ERC-20 return-value handling that assumes non-standard behavior can't occur — but manifests as silently accepting a failed transfer rather than reverting a valid one.

### Impact Explanation
Because escrow accounting (`_orders[...]` decrement, `_filled[...]` marking) is finalized before/alongside a transfer whose actual success is never verified, a failed-but-non-reverting token transfer leaves the escrowed tokens permanently trapped in the contract: the order is marked filled/refunded (so it can never be retried through the normal `RedeemEscrow`/`RefundEscrow` path since `_filled` is already set) while the beneficiary never receives the tokens and the escrow bookkeeping shows the balance already released. This is a permanent freezing-of-funds condition reachable via the standard cross-chain fill/refund flow (`onAccept` handling relayed proofs) and via governance `SweepDust`.

### Likelihood Explanation
This requires the input/output token used in an order to be a non-standard ERC-20 that returns `false` on failure instead of reverting (a known real-world token behavior class, same category as the USDT-style tokens cited in the original report, just the inverse failure mode). Any solver or user selecting such a token for an order, or hitting a transient failure condition on such a token (e.g., paused/blacklist), can trigger the loss without any privileged actor involved — reachable directly from a normal intent fill/refund flow.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check pattern in `withdraw()` and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the fix already applied to `evm/src/apps/intentsv2/IntentsBase.sol`. `safeTransfer` decodes the return data when present and requires it to be `true`, correctly handling both standard-compliant and non-standard (no-return-value) tokens without accepting a silent `false`.

### Proof of Concept
1. Deploy a token whose `transfer` function returns `false` on failure instead of reverting (e.g., mimicking legacy tokens like ZRX or a paused/blacklist-gated token), and use it as an order's input/output token in the Tron `IntentGatewayV2`.
2. Trigger a condition where the transfer would fail (e.g., beneficiary blacklisted or token paused) while an escrow release (`withdraw`) or `SweepDust` request is processed.
3. Observe `token.call(...)` returns `success = true` (no revert) even though the encoded return data is `false`/empty-of-tokens-moved; the code proceeds to decrement `_orders[...]` and set `_filled[body.commitment] = beneficiary`, finalizing the order.
4. The beneficiary's token balance is unchanged, but the order can never be reprocessed (`_filled` is already set), permanently locking the escrowed tokens in the contract.
