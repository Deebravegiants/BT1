### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the verifiable HMAC over the raw request body only, while the `shop` value used downstream to attribute the webhook to a tenant is read from the `shopify-shop-domain` HTTP header, which is completely outside the signed byte range.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header` [2](#0-1) . `Utils::HmacValidator.validate` verifies the HMAC only against `to_signable_string` (the body) using the app's `api_secret_key` [3](#0-2) . `Registry.process` raises only if this body-HMAC check fails, then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) and hands it to the app's `WebhookHandler#handle` [4](#0-3) . `WebhookMetadata.shop` is a plain `String` field with no cross-check against any signed content [5](#0-4) .

The broken identity binding is:
`shop used by the handler for tenant scoping == shop bytes covered by the HMAC`
is actually:
`shop used by the handler for tenant scoping == attacker-settable HTTP header value`, and
`bytes verified by HMAC == raw_body only (never includes shop-domain)`.

Because Shopify signs webhooks for a given app with the single app-level `api_secret_key` (not a per-shop secret), any legitimate, unprivileged merchant who has installed the app can generate their own genuine webhook deliveries (valid body + valid HMAC) for their own shop. That attacker-controlled merchant can then replay the exact same raw body and HMAC to the app's public webhook endpoint while substituting a different `shopify-shop-domain` header value pointing at a victim shop. `HmacValidator.validate` still passes (it never looked at the header), and `Registry.process` will invoke the app's handler with `WebhookMetadata(shop: <victim-shop>, body: <attacker's own body>)`, causing the app to attribute attacker-supplied data to another tenant.

### Impact Explanation
This crosses the tenant boundary without needing the app's `client_secret`/access token to be leaked and without any privileged account — only an ordinary install of the app on the attacker's own (free/dev) shop is required, which is achievable by any unprivileged internet user who can install the target app. Depending on the handler's logic (e.g., updating per-shop cached data, triggering shop-scoped side effects, `shop/redact` / `customers/data_request` compliance flows, order/product sync), this enables cross-tenant data confusion or injection — matching the "cross-tenant access" Critical impact bucket, since the tenant-scoping value is unauthenticated relative to the cryptographic proof the library relies on.

### Likelihood Explanation
Likelihood is realistic but not trivial: it requires (1) the attacker to be an installed merchant of the target app (any unprivileged actor can achieve this for public/free apps), and (2) the app's webhook handler to trust `WebhookMetadata#shop` for authorization or data-scoping decisions rather than independently verifying it (e.g., cross-checking against a shop id embedded in the signed body, which most Shopify webhook payloads do include as `X-Shopify-Shop-Domain` is conventionally trusted exactly because apps assume the whole request, not just the body, is authenticated). The gem's own API design invites this trust by exposing `shop` as a normal, unqualified field on `WebhookMetadata` right next to the verified `body`.

### Recommendation
Include the shop-domain (and other identity-relevant headers such as topic/api-version/webhook-id) in the HMAC-covered signable string, or otherwise cryptographically bind `shop` to the signed body (e.g., require handlers to verify the shop against a value contained inside the signed body payload). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (no privileged access needed).
2. Attacker triggers a real webhook event (e.g., edits a product) and captures the raw POST body `B` together with the valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)` that Shopify sent to the app's public webhook endpoint.
3. Attacker resends `B` and `H` unmodified to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` [6](#0-5)  — it matches `H` because the header was never part of the signed input, so validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [7](#0-6)  and invokes the app's handler as if the data legitimately originated from the victim shop.
