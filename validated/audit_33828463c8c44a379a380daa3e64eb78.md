### Title
Unbacked mint via one-sided decimals truncation in `hyper-fungible-token` cross-chain amount conversion - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet converts amounts between local Substrate balance decimals and remote EVM ERC20 decimals using `saturating_sub` when computing the scaling exponent in both directions. Because `saturating_sub` clamps to zero instead of scaling in the opposite direction, a decimals mismatch where the local asset has *more* decimals than the remote ERC20 contract causes `convert_to_erc20` to skip scaling entirely on `send`, and the symmetric case in `convert_to_balance` on `on_accept`/`on_timeout` under-scales instead of scaling up — producing amounts that are off by a power of ten. This mirrors the reported analog: a collateral-ratio check performed without normalizing decimals between two tokens of differing precision, letting the math silently produce values with the wrong magnitude and letting an attacker mint or receive far more value than what was locked.

### Finding Description
`convert_to_erc20` (used in `send`, `modules/pallets/hyper-fungible-token/src/impls.rs:57-59`) and `convert_to_balance` (used in `on_accept`/`on_timeout`, same file, lines 43-52) both compute the decimal-scaling exponent as:

```rust
erc_decimals.saturating_sub(local_decimals)   // convert_to_erc20 multiplies by 10^this
erc_decimals.saturating_sub(local_decimals)   // convert_to_balance divides by 10^this
``` [1](#0-0) 

`saturating_sub` returns `0` whenever `local_decimals > erc_decimals` (for `convert_to_erc20`) or whenever `local_decimals > erc_decimals` (for `convert_to_balance`, same subtraction order). In both functions the subtraction is only ever applied in one direction (`erc_decimals - local_decimals`), so whenever the *local* Substrate asset decimals exceed the *remote* EVM token decimals, the scaling factor silently becomes `10^0 = 1` instead of scaling in the other direction (dividing/multiplying by `10^(local_decimals - erc_decimals)`).

Concretely, in `send()` (`modules/pallets/hyper-fungible-token/src/lib.rs:294-300`), the pallet burns/locks `params.amount` in local decimals, then computes:

```rust
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
``` [2](#0-1) 

If the local asset has 18 decimals and the destination EVM contract is registered with 6 decimals (`erc_decimals = 6`, `local_decimals = 18`), `erc_decimals.saturating_sub(local_decimals) = 0`, so `erc20_amount = amount` unscaled. The dispatched `Message.amount` field is then interpreted by the destination contract as a 6-decimal quantity. The raw 18-decimal integer sent is 10^12 times larger in real value than what was actually locked — an unbacked over-mint on the destination chain equal to the difference. The symmetric failure applies to `convert_to_balance` on the inbound path (`modules/pallets/hyper-fungible-token/src/module.rs:82-91` and the `on_timeout` handler at lines 246-255), where an incoming ERC20 amount from a lower-decimals remote contract is credited without the necessary upscaling when `local_decimals > erc_decimals`.

### Impact Explanation
This is a direct unbacked-mint / value-forging bug reachable by any unprivileged user calling the public `send` extrinsic (`modules/pallets/hyper-fungible-token/src/lib.rs:241`) once governance has registered (via `register_token`/`update_token`) any asset pair where the local asset's decimals exceed the paired EVM contract's configured `Precisions` decimals. The user locks/burns a small real-world amount locally but the destination-chain contract mints/releases an amount inflated by `10^(local_decimals - erc_decimals)`, letting an attacker drain value from the bridge's custody/escrow on the destination side — a concrete theft of funds analogous to the "undercollateralized loan" root cause (decimals not normalized before comparing/moving amounts between two differently-scaled units).

### Likelihood Explanation
Exploitability depends entirely on whether any registered asset-chain pair in `Precisions` has `local_decimals > erc_decimals` (e.g., a locally-registered 18-decimal wrapped asset paired against a 6-decimal USDC-style EVM contract) — this is plausible/likely for stablecoin or cross-decimals asset listings, and requires no privileged action from the caller, only an ordinary `send()` call once such a pair exists.

### Recommendation
Replace the one-directional `saturating_sub` scaling in `convert_to_balance` and `convert_to_erc20` with a signed/bidirectional scale that multiplies when the target has more decimals and divides when it has fewer, e.g.:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the mirrored fix for `convert_to_balance`, with an explicit check/test covering `local_decimals > erc_decimals` in both `send` and `on_accept`/`on_timeout` paths.

### Proof of Concept
1. Governance registers asset `X` as native with `local_decimals = 18` and calls `update_token`/`register_token` setting `Precisions::<T>::insert(X, DestChain, 6)` (i.e., the paired EVM contract for `X` on `DestChain` uses 6 decimals).
2. User calls `send(SendParams { asset_id: X, destination: DestChain, amount: 1_000_000_000_000_000_000 /* 1 token, 18 dec */, recipient, .. })`.
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, so `erc20_amount = 1e18`.
4. The dispatched `Message.amount = 1e18` is delivered to the destination EVM contract expecting a 6-decimal amount — the equivalent of `1e18 / 1e6 = 1,000,000,000,000` "real" tokens minted/released, versus the 1 token actually locked, an unbacked mint of value 10^12x the input.
