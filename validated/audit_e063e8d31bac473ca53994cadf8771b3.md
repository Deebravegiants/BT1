### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` header, but the HMAC signature computed by `HmacValidator` only covers the raw request body, never the shop header. This breaks the binding: `hmac_verified_bytes != shop_used_for_tenant_routing`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate` computes and compares the signature strictly against `verifiable_query.to_signable_string`, i.e. the body alone: [2](#0-1) .

Meanwhile `Request#shop` is read straight from an HTTP header that is never mixed into the HMAC input: [3](#0-2) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` and then trusts `request.shop` as the tenant identity when constructing the data passed to the app's webhook handler: [4](#0-3) .

Because `hmac` only binds `raw_body`, the `shop` header can be swapped to any value without invalidating the signature check, as long as the body and HMAC pair remain internally consistent (i.e., the HMAC was legitimately produced by Shopify for that exact body under the app's `client_secret`). This is the exact "field acted on but not covered by HMAC" identity-binding break called out in the task rules — here, `shop` is the tenant key used by downstream handler logic, yet it sits outside the authenticated envelope.

### Impact Explanation
This enables cross-tenant confusion: a party who legitimately receives a valid Shopify webhook for their own store (with a valid HMAC over the body) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header of a different, victim shop. `Registry.process` will pass HMAC validation (since it doesn't check `shop`) and hand the handler a `WebhookMetadata` object claiming the data belongs to the victim shop, corrupting per-tenant data association, potentially triggering victim-store side effects (e.g., data deletion for `customers/redact`/`shop/redact`, inventory or order state changes) attributed to the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one legitimately-signed webhook body/HMAC pair for the shared app's `client_secret` (e.g., from their own store's webhook traffic, or by influencing controllable fields such as order notes/line items to shape the body) and the ability to send an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — no access token or `client_secret` is needed. This is realistically reachable by any merchant/user of a multi-tenant app that shares a single webhook processing endpoint.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed payload validation, or independently verify that the shop claimed in the header corresponds to a shop with a known, provisioned session/installation before trusting it for tenant routing in `Registry.process`. At minimum, cross-check `request.shop` against an authoritative, already-verified installation record rather than trusting the header value once the body HMAC passes.

### Proof of Concept
1. Attacker owns/operates a Shopify store (`attacker-shop.myshopify.com`) with the target app installed, so Shopify sends them legitimately-HMAC-signed webhooks for that shop.
2. Attacker captures a legitimate `orders/create` webhook: raw body `B` and header `x-shopify-hmac-sha256: HMAC(B, client_secret)`.
3. Attacker resends this exact `raw_body`/HMAC pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks the body against the HMAC [2](#0-1) ; `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to process attacker-controlled body content under the victim tenant's identity.
