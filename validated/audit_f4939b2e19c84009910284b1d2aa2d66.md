### Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted as-is and passed straight into the webhook handler. Because the `shop` attribute that identifies the tenant is never part of the signed material, any Shopify merchant who has installed the app on their own store can capture a legitimately-signed webhook delivered to them, replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop, and have the app process attacker-controlled data under the victim's identity — an HMAC-valid but tenant-spoofed webhook.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (unsigned) `shop-domain` header: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` verifies only this body-only HMAC, then immediately dispatches the handler using the unauthenticated `request.shop` value: [4](#0-3) 

The identity binding that should hold is:
`shop_that_signed_the_payload == shop_attributed_to_the_handler`

but the code only enforces:
`HMAC(secret, raw_body) == received_hmac`

with no cryptographic link between `raw_body` and `shop-domain`. Since the app's `api_secret_key` is a single, app-wide secret shared across every shop that has the app installed (this is standard Shopify webhook design — Shopify signs with the client secret, not a per-shop key), any merchant who installs the app can legitimately receive a validly-signed webhook for their own store, then replay that exact body/HMAC pair to the app's endpoint with the `shop-domain` header swapped to a different shop. `HmacValidator.validate` still returns `true` (body and secret are unchanged), so `Registry.process` accepts the request and calls the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is fully attacker-controlled.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to preserve for webhook consumers: any app relying on `WebhookMetadata#shop` (returned by `Registry.process`) to route/store data per-merchant will attribute attacker-supplied data to a shop the attacker does not control. Depending on how the host app uses webhook payloads (e.g., updating cached order/customer/product records, feeding automation, billing state), this is a cross-tenant data-injection/spoofing vector — Critical-adjacent cross-tenant access achieved purely by an unprivileged internet user who merely installs the app on their own store and replays a request.

### Likelihood Explanation
Likelihood is high: no secret material is needed. The attacker only needs the app installed on a store they control (a normal unprivileged action), captures a real webhook delivery (raw body + `x-shopify-hmac-sha256`), and resends it to the app's public webhook endpoint with the `shop-domain` header changed. Nothing in `Request` or `Registry` cross-checks the header against the signed body.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the verified payload — e.g., include the shop domain (and topic/webhook-id) in the value passed to `HmacValidator.validate`, or require the host application to cross-check `request.shop` against a shop it already expects/owns before dispatching to the handler. At minimum, document that `Registry.process`'s `shop` value is unauthenticated and must not be trusted for tenant routing without additional verification (e.g., confirming the shop has an active, previously-established session/installation record).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`) with attacker-controlled order data.
2. Shopify delivers the webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, and the JSON body.
3. Attacker intercepts/replays this exact HTTP request to the same endpoint, only changing `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — this still matches because body and secret are unchanged. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's body, even though `victim.myshopify.com` never sent this webhook.
