### Title
Permanent loss of funds via `DeleteAccount` action with a syntactically valid but non-existent `beneficiary_id` - (File: `runtime/runtime/src/actions.rs`)

### Summary
The `DeleteAccount` action lets an account holder redirect their remaining balance to a `beneficiary_id` when the account is deleted. This `beneficiary_id` is only checked for well-formedness (regex-style account-id syntax), never for whether the target account actually exists. If it does not exist, the balance-refund receipt spawned by the deletion fails to apply and, per nearcore's refund semantics, failed refunds are burned rather than returned to the sender — an unrecoverable, permanent loss of tokens, directly analogous to `transferPosition`'s missing recipient-validity check in the audited contract.

### Finding Description
`action_delete_account` computes the account's remaining balance and unconditionally enqueues a refund receipt to `delete_account.beneficiary_id` without verifying the beneficiary account exists: [1](#0-0) 

The only validation performed on `beneficiary_id`, at action-validation time, is a syntax check (`validate_action_account_id`) — it never checks account existence: [2](#0-1) 

The `DeleteAccountAction` schema itself has no invariant enforcing that `beneficiary_id` corresponds to a live account: [3](#0-2) 

The docs explicitly acknowledge that ordinary balance transfers to non-existent accounts fail (`AccountDoesNotExist`) unless the target is implicit-account-eligible, and that this deliberately does **not** apply to refunds: "Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse. Account deletion with beneficiary creates a refund, so it'll not create a new account." [4](#0-3) 

Because the delete-account payout is implemented as a refund receipt (system-predecessor, free-of-gas) rather than a normal `Transfer` action, it bypasses the `check_transfer_to_nonexisting_account` guard that protects ordinary transfers, and per the protocol-execution invariants a refund that fails to apply is burned instead of being returned: [5](#0-4) 

### Impact Explanation
Any account holder who deletes their own account and mistypes, misconfigures, or otherwise supplies a `beneficiary_id` for an account that does not currently exist on chain (but is syntactically valid, e.g. a never-registered subaccount) will have their entire remaining balance permanently burned instead of transferred. This is concrete, unrecoverable token loss triggered purely by an unprivileged user's own transaction — no attacker or privileged actor is required, matching the "position permanently lost" impact class of the source finding (loss of value due to missing validation of a transfer recipient).

### Likelihood Explanation
This is trivially reachable by any account: submitting a `DeleteAccount` action (directly via a transaction, via a contract's `promise_batch_action_delete_account`, or via a meta-transaction/delegate action) with a `beneficiary_id` that is well-formed but does not exist as a real account requires no special privileges, no race condition, and no unusual configuration — only a typo or use of a not-yet-created account is needed. The tests in the repository only cover the case where `beneficiary_id` exists (e.g. `meta_tx_delete_account`), and none validate existence of the beneficiary before allowing deletion: [6](#0-5) 

### Recommendation
Before executing `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account in state (similar to the existence check already performed for ordinary `Transfer` actions in `check_transfer_to_nonexisting_account`), and reject the action (e.g. with an `AccountDoesNotExist`-style validation error) if the beneficiary does not exist, rather than silently burning the funds via a failed refund.

### Proof of Concept
1. Create account `alice.near` with a nonzero balance.
2. Submit a transaction from `alice.near` containing a single `DeleteAccount { beneficiary_id: "nonexistent123.near" }` action, where `nonexistent123.near` is a syntactically valid account id that has never been created on chain.
3. `action_delete_account` computes `account_balance` and pushes `Receipt::new_balance_refund(&"nonexistent123.near", account_balance)` [1](#0-0) , then deletes `alice.near`.
4. The refund receipt targets a non-existent account; since refund receipts do not trigger implicit-account creation and a failed refund is burned rather than returned (per `runtime-execution.md:151-152`), `alice.near`'s entire balance is permanently destroyed with no path to recovery.
