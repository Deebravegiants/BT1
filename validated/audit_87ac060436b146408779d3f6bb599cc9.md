### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the application's handler are read from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature exclusively from `to_signable_string`, i.e. the body: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof of authenticity for the *whole request*, then extracts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all sourced from headers — and forwards them unchanged into `WebhookMetadata`, which is delivered to the app-defined handler as trusted tenant identity: [3](#0-2) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body: [4](#0-3) [5](#0-4) 

`WebhookMetadata.shop` is a plain `String` field with no further validation, consumed as the tenant key by host applications: [6](#0-5) 

This breaks the identity binding: `HMAC-authenticated bytes (raw_body) == bytes acted on as the tenant identity (shop header)`. The HMAC only proves "this body was signed with our `client_secret`" — it says nothing about which shop the header claims to be. Since the `client_secret` used to compute the webhook HMAC is a single secret shared across *all* merchants of the app (not per-shop), any party who can obtain one valid `(body, hmac)` pair for their own shop can replay that exact body/hmac to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The signature still validates (it never covered the header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to a different, victim shop.

### Impact Explanation
Host applications built on this gem are documented to key their business logic (session lookup, GDPR mandatory-webhook processing, order/customer state updates, `shop/redact` and `customers/redact` handling) off `WebhookMetadata#shop`. An attacker who legitimately installs the app on their own store (no special privilege required) can capture a body + HMAC pair from their own real webhook deliveries and replay it against the shared webhook endpoint with a forged `shop-domain` header naming a different merchant. This is a cross-tenant data-injection / spoofing primitive: fabricated events (e.g., fake `customers/redact`, `app/uninstalled`, or order-mutation triggers) can be attributed to a shop the attacker does not control, since the gem provides no binding between the signed bytes and the shop the handler is told the event came from.

### Likelihood Explanation
The prerequisite — being able to legitimately trigger at least one real webhook for your own installed shop — is trivially available to any unprivileged merchant/developer who installs the app; it requires no `api_secret_key`, no stolen token, and no TLS interception. The only extra step is delivering a crafted HTTP request with an attacker-chosen header to the app's public webhook receiver endpoint, which is by design internet-reachable.

### Recommendation
Bind the shop (and other trust-relevant metadata such as `topic`/`webhook_id`) to the signed material, or otherwise assert the signed payload actually originated for the claimed shop before constructing `WebhookMetadata`. For example, include the `shop-domain`/`topic` values in `to_signable_string` (matching what Shopify actually signs for the delivery) rather than relying on the header being trustworthy purely because the body's HMAC matches, and document/require that any consumer independently confirms `WebhookMetadata#shop` corresponds to a shop with an existing installed session for the app before acting on the payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action) and triggers a real webhook delivery, capturing `raw_body` and the valid `shopify-hmac-sha256` value the app's shared `client_secret` produced for it.
2. Attacker sends a POST to the app's public webhook endpoint reusing the identical `raw_body` and `hmac` header, but replaces `shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) — validation succeeds because the body/HMAC pair is genuinely valid. [3](#0-2) 
4. `WebhookMetadata.shop` is populated from the attacker-controlled header value `victim-shop.myshopify.com`, and the app-defined handler processes the event as though it legitimately originated from the victim's store.
