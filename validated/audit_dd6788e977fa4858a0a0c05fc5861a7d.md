### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing in `ShopifyAPI::Webhooks::Request` - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` value that is subsequently handed to the app's handler as the tenant identifier is read directly from the unauthenticated `shopify-shop-domain` HTTP header [2](#0-1)  and is never included in the signable string that is HMAC-verified [3](#0-2) .

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ body)` (i.e., the identity of the shop the webhook claims to be from should be bound to the signature), but the actual implementation only enforces `hmac == HMAC(secret, body)`.

- `Request#to_signable_string` returns only `@raw_body` [3](#0-2) .
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload [2](#0-1) .
- `HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., against the body only, using `OpenSSL.secure_compare` [4](#0-3) .
- `Registry.process` calls `Utils::HmacValidator.validate(request)` and, once it passes, forwards `request.shop` (the unauthenticated header value) straight into `WebhookMetadata` that is delivered to the app's handler [1](#0-0) .

Because the app's HMAC secret (`Context.api_secret_key`) is shared across every shop that has the app installed, any actor who controls one legitimately-installed shop can capture a real webhook delivery (body + valid HMAC) triggered on their own store, then replay that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header for a different merchant. `HmacValidator.validate` will still return `true` because the signature only covers the body, so `Registry.process` will treat the forged request as authentic and dispatch it to the handler tagged with the attacker-chosen `shop` value.

This maps directly to the report's bug class: a field ("shop", the tenant identity) is acted upon by downstream logic but is not covered by the cryptographic authentication check ("HMAC"), exactly mirroring how `subtraction_result_unchecked` in the `div` circuit was used to satisfy a constraint (`remainder_is_less_than_divisor`) without being range-checked itself.

### Impact Explanation
Applications built on this gem's documented webhook API (`ShopifyAPI::Webhooks::Registry.process`) rely on `WebhookMetadata#shop` to know which merchant/tenant a webhook event belongs to (e.g., to look up that shop's session/access token or to update shop-scoped state). Because `shop` is not authenticated, an attacker who has legitimate access to one shop's webhook traffic can forge events attributed to a different, victim shop, causing cross-tenant data confusion/corruption in any host application that trusts `data.shop` for tenant routing — matching the "cross-tenant access" Critical-impact category defined in the rules.

### Likelihood Explanation
Exploitation requires the attacker to possess a valid `(raw_body, hmac)` pair for the shared `api_secret_key`. This is realistically obtainable by any actor who runs their own store with the app installed (a normal, unprivileged capability, not requiring theft of `api_secret_key` itself) and simply replays the intercepted body/HMAC to the webhook endpoint with a modified `shop-domain` header, since nothing in this gem binds the header to the signature. Likelihood is moderate: it requires the attacker to be an app user with a real installation, and the effectiveness of the attack depends on the host app's handler using the shop value directly (which is exactly what the gem's documented `WebhookMetadata` contract encourages).

### Recommendation
Bind the `shop` (and ideally `topic`) values into the signature verification, or otherwise pin the accepted shop identity to a value the app already trusts (e.g., cross-check `request.shop` against the recipient/handler-registered shop or the session store) before dispatching to handlers. At minimum, document prominently that `shop`/`topic` headers are not authenticated by `HmacValidator`, and require handlers to independently verify tenant identity (e.g., against known installed-shop records) rather than trusting `WebhookMetadata#shop` outright.

### Proof of Concept
1. App has two shops installed: `attacker-shop.myshopify.com` (attacker-controlled) and `victim-shop.myshopify.com`.
2. Attacker triggers any webhook event on their own shop and captures the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
3. Attacker sends a new POST request to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` (body only, per `Request#to_signable_string`) [3](#0-2)  — this matches `H`, so validation succeeds.
5. `Registry.process` proceeds to call the handler with `WebhookMetadata.new(... , shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , even though the event actually originated from the attacker's own shop — a forged, cross-tenant webhook accepted as authentic.
