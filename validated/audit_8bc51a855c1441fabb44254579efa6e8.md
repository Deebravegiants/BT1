### Title
Webhook tenant attribution (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body [1](#0-0) , while the tenant-identifying `shop` value is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed bytes [2](#0-1) . `Registry.process` accepts the request as long as `Utils::HmacValidator.validate(request)` succeeds against the raw body [3](#0-2) , then passes the unauthenticated `request.shop` straight into `WebhookMetadata` and on to the app's `handler.handle` [4](#0-3)  and `WebhookMetadata` struct [5](#0-4) . This is precisely the reported bug class: a field that is *acted upon* (the tenant/`shop`) is not bound by the same authenticator (HMAC) that is supposed to guarantee the integrity of the whole message, just as the withdrawal's eligibility time was not correctly re-derived per request in the analog report.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it, in constant time, to the `hmac` value taken from the request [6](#0-5) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) ; none of the headers (`shopify-topic`, `shopify-shop-domain`, `shopify-api-version`, `shopify-webhook-id`) participate in the signature. The equality the HMAC is supposed to enforce is:

`HMAC(secret, raw_body) == received_hmac` → "this body came from Shopify unmodified"

but the code actually *acts on* a broader claim that is never verified:

`(raw_body, shop_header) came from Shopify for shop_header`

The `shop` binding is broken: any two HTTP requests with the same signed body but different `shop-domain` headers pass validation identically, because the header is parsed but never verified.

### Impact Explanation
Because the app's client secret is shared across every shop that installs the app, an attacker can freely become a legitimate tenant by installing the app on a shop they control, and trigger a real Shopify webhook delivery (e.g. `products/create`, `orders/create`, `customers/data_request`) to the app's webhook endpoint. That delivery carries a body and an HMAC that Shopify computed and that will validate successfully. The attacker can then replay this exact `(raw_body, hmac)` pair to the same endpoint while substituting the `shopify-shop-domain` header for any other shop's `myshopify.com` domain. `HmacValidator.validate` still passes (it never inspected the header), so `Registry.process` invokes the app's webhook handler with `WebhookMetadata.shop` set to the victim shop [7](#0-6) . Any app logic keyed on `data.shop` (looking up/creating tenant records, honoring `customers/redact`/`shop/redact` compliance actions, updating per-shop state, etc.) is then executed against the wrong tenant — a cross-tenant access/data-integrity break, which matches the report's "Critical – cross-tenant access" impact bucket.

### Likelihood Explanation
The only prerequisite is the ability to install the app on an attacker-controlled shop (or otherwise obtain one legitimately signed webhook body/HMAC pair for that app) and the ability to send arbitrary HTTP headers to the app's public webhook endpoint — both are available to any unprivileged internet user and require no access token, `client_secret`, or credential theft. Nothing about this requires exploiting the host framework's misuse of the gem; the gem's own `Request`/`HmacValidator`/`Registry` code is what parses and trusts the unauthenticated header.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`/`webhook-id`) claim to the HMAC-verified content instead of trusting the raw header value in isolation — e.g., have `to_signable_string` incorporate the relevant headers, or, at minimum, document/enforce that consumers must cross check `request.shop` against an out-of-band trusted store (installed-shop list) before using it for tenant routing, since the header itself carries no cryptographic guarantee.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` (a shop they control) and registers a webhook (e.g. `products/create`).
2. Attacker triggers the webhook by creating a product in their own shop; Shopify POSTs to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker captures this request and replays it to the same endpoint, keeping `B` and `H` unchanged but rewriting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)`, which still equals `H`, so validation succeeds [8](#0-7) .
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` [4](#0-3) , causing the app to perform shop-scoped actions against `victim-shop` using attacker-supplied body content.
