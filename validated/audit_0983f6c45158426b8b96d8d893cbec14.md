### Title
Naive string equality in `compareAddresses()` fails to detect equivalent XRPL classic/X-Address encodings, bypassing the token-self-address withdrawal guard - (File: `packages/intents-sdk/src/lib/compareAddresses.ts`)

### Summary
`compareAddresses()` is used by every bridge's `validateWithdrawal()` to block withdrawals where the destination address is actually the token's own contract/issuer address (which would otherwise strand funds permanently). For XRPL it falls into the generic `a === b` branch, but `validateAddress()`/`validateXrpAddress()` accepts two textual encodings of the *same* underlying XRPL account — classic addresses and X-Addresses (`ripple-address-codec`'s `isValidClassicAddress` / `isValidXAddress`). An attacker who supplies the destination in the alternate encoding of the token's own account defeats the equality check.

### Finding Description
`validateAddress()` explicitly accepts both encodings for XRPL: [1](#0-0) 
```
function validateXrpAddress(address: string) {
	return xrp_isValidClassicAddress(address) || xrp_isValidXAddress(address);
}
```
X-Addresses (`X...`) are not an unrelated address type — they are a lossless re-encoding of the *same* classic `AccountID`, optionally carrying an embedded destination tag. A classic address and an X-Address (with no/matching tag) refer to the identical on-ledger account.

`compareAddresses()`, however, groups XRPL with chains that only have one canonical textual form and does plain string equality: [2](#0-1) 
```
case Chains.TON:
    return compareTonAddress(a, b);
case Chains.Tron:
    return compareTronAddress(a, b);
case Chains.Stellar:
    return a.toUpperCase() === b.toUpperCase();
case Chains.Near:
case Chains.Bitcoin:
...
case Chains.XRPL:
case Chains.Cardano:
case Chains.Aleo:
case Chains.Dash:
    return a === b;
```
Unlike TON and Tron — which get dedicated decode-then-compare helpers because they also have multiple valid encodings (`compareTonAddress`, `compareTronAddress`) — XRPL was left in the naive `a === b` bucket even though it has the same "multiple encodings, one account" property. This is structurally the same class of bug as the PySpector `resolve_name()` gap: the validator (`validateAddress`) accepts an alternate representation, but the downstream equality/security check (`compareAddresses`) does not canonicalize before comparing, silently letting the alternate form slip past the check it is supposed to enforce.

### Impact Explanation
`compareAddresses(tokenAccountId, args.destinationAddress, blockchain)` is called in every bridge's `validateWithdrawal()` specifically to reject withdrawals to the token's own address: [3](#0-2) 
```
const nativeAsset = "native" in assetInfo;
const token = nativeAsset ? "native" : assetInfo.address;
if (
    !nativeAsset &&
    compareAddresses(token, args.destinationAddress, assetInfo.blockchain)
) {
    throw new DestinationAddressMatchesTokenAddressError(token, args.assetId);
}
```
The same pattern exists in `direct-bridge.ts`, `omni-bridge.ts`, and `poa-bridge.ts`. If the token's canonical address (`token`/`tokenAccountId`/`destTokenAddress`) is stored/returned in one XRPL encoding (classic) while the attacker-controlled `destinationAddress` is supplied in the other encoding (X-Address) of the very same account, `compareAddresses` returns `false` even though the two strings denote the same account. The guard is bypassed, the withdrawal is approved by the SDK, and funds are sent to what is effectively the token's issuer/contract account — funds delivered to a wrong/self-referential address with no recovery path. This matches the "funds delivered to a wrong address/contract with no recovery" Critical impact category, since the destination check is the only in-SDK safeguard against this class of self-address misdelivery.

### Likelihood Explanation
Exploitation only requires the attacker (the party specifying the withdrawal destination) to encode a known token/issuer XRPL account as an X-Address instead of its classic form — no privileged access, relayer collusion, or admin action is needed, only crafting an equivalent address string. `ripple-address-codec`, already a dependency, provides the encode function needed to produce a valid X-Address for any classic account. The requirement is that an XRPL-denominated asset's canonical account representation differs in form from the caller-supplied destination; whether this is currently reachable end-to-end depends on how the bridges source XRPL token addresses (`assetInfo.address` / `tokenAccountId`), which was not fully inspectable within this pass — confirming which exact chain/bridge configuration surfaces this specific comparison for XRPL assets would require further review.

### Recommendation
Add an XRPL-specific comparator to `compareAddresses()` (parallel to `compareTonAddress`/`compareTronAddress`) that decodes both inputs to their canonical `AccountID` (using `ripple-address-codec`'s X-Address decoding to recover the classic address) before comparing, rather than relying on raw string equality for a chain whose `validateAddress()` explicitly accepts multiple equivalent encodings.

### Proof of Concept
1. Take a token/issuer's XRPL classic address, e.g. `rTokenIssuerAddress...`.
2. Encode the same account as an X-Address using `ripple-address-codec`'s `classicAddressToXAddress` (with no/omitted tag), producing `XTokenIssuerAddress...`.
3. Call the SDK withdrawal flow with `destinationAddress = "XTokenIssuerAddress..."` while the bridge's resolved token address is the classic form.
4. Observe `compareAddresses(tokenAccountId, destinationAddress, Chains.XRPL)` returns `false` (naive `a === b`), so `validateWithdrawal()` does not throw `DestinationAddressMatchesTokenAddressError`, and the withdrawal proceeds to the token's own account.
