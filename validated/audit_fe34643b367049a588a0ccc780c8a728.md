## Title
Unbounded error_handler/appendix ping-pong loop in `XcmExecutor::execute` allows a single XCM message to consume unbounded computation while reporting bounded weight - (File: polkadot/xcm/xcm-executor/src/lib.rs)

### Summary
`XcmExecutor::execute` drives a `while !message.0.is_empty()` loop that alternates between the top-level message, the `error_handler`, and the `appendix` registers, with **no iteration counter, no runtime weight ceiling, and no re-application of `RECURSION_LIMIT`** across loop iterations. An attacker can construct a small, finite XCM whose `error_handler` re-installs an identical copy of itself via `SetErrorHandler` and then immediately faults via `Trap`, causing `take_error_handler()`/`take_appendix()` to feed the *same* handler back into the loop indefinitely, while `prepare()` only charges weight for the handler body once.

### Finding Description
`XcmExecutor::execute` at [1](#0-0)  implements:
```
while !message.0.is_empty() {
    let result = vm.process(message);
    message = match result {
        Err(error) => { ...; vm.take_error_handler().or_else(|| vm.take_appendix()) },
        Ok(()) => { vm.drop_error_handler(); vm.take_appendix() }
    }
}
```
Each call to `vm.process(message)` establishes its own fresh `recursion_count::using_once` scope inside `process()` ( [2](#0-1) ), so `RECURSION_LIMIT` only bounds nesting *within* a single `process()` invocation (e.g. instructions that recursively call `process_instruction`/`process` for nested XCM such as `ExecuteWithOrigin`). It does **not** bound how many times the outer `while` loop in `execute()` can re-invoke `process()` via the error-handler/appendix hand-off.

`SetErrorHandler`/`SetAppendix` processing ( [3](#0-2) ) simply stores the supplied `Xcm` value into `self.error_handler`/`self.appendix` — no bound on how many times that same stored value can be taken and re-processed. `take_error_handler()` moves the value out by value ( [4](#0-3) ), so an attacker can encode (once, statically) a handler body `H = [SetErrorHandler(H'), Trap(0)]` where `H'` is a literal copy of `H`'s instructions. When `H` is executed as the error handler: `SetErrorHandler(H')` succeeds and re-installs an identical handler, then `Trap(0)` immediately errors; back in `execute()`, `take_error_handler()` retrieves `H'` and the `while` loop calls `vm.process(H')` again — repeating forever. This requires only a small, finite, statically-encoded message (well below `MAX_INSTRUCTIONS`/`RECURSION_LIMIT` as measured during `prepare()`), yet produces unbounded runtime iterations.

Weight accounting does not catch this: `prepare()` (via `FixedWeightBounds::weight_with_limit`, [5](#0-4) ) sums the weight of the handler body **once**, statically, with no notion that it can be re-executed. At runtime, `execute()`'s only weight bookkeeping is `total_surplus`/`total_refunded`, purely additive/subtractive against the single `xcm_weight` computed by `prepare()` — there is no live weight meter inside `execute()` that aborts once real consumption exceeds the declared budget.

Critically, `ProcessXcmMessage::process_message` ( [6](#0-5) ) calls `prepare()` once to get `required` weight, checks `meter.can_consume(required)`, and then calls `XcmExecutor::execute(...)` to completion in a single, non-preemptible call — the message-queue pallet's `WeightMeter` has no visibility into, or ability to interrupt, work happening inside that single `execute()` call. `DenyRecursively` ( [7](#0-6)  and start="648" end="683") only inspects the message *before* execution for statically-nested `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin`, and its `RECURSION_LIMIT` counter bounds only *static nesting depth in the encoded message*, not the number of *runtime* loop iterations induced by an error-handler that reinstalls itself.

### Impact Explanation
A single UMP/DMP/HRMP/XCM message from an unprivileged sender, once admitted past the barrier as a normal top-level XCM (SetErrorHandler/SetAppendix are ordinary, commonly-permitted instructions), can cause the single blocking call to `XcmExecutor::execute` inside `ProcessXcmMessage::process_message` to loop far longer than the weight charged against `meter`/`WeightMeter`. Because `pallet-message-queue`'s `service_queues`/`on_initialize` budget (`ServiceWeight`) is enforced only *between* messages (via `WeightMeter::can_consume`/`try_consume`, e.g. [8](#0-7) ), not *within* a single `process_message` call, this single crafted message can monopolize the on-chain XCM processing time for the block (or effectively hang execution), starving all other queued messages sharing the same `ServiceWeight` budget — matching the scoped "single message halts other queue processing" impact.

### Likelihood Explanation
Feasible and repeatable by any account able to have a message enqueued into the runtime's incoming XCM/UMP/HRMP queue with a locally-executed XCM (e.g. via `pallet-xcm::execute`, or a parachain sending a message that ends up locally executed on another chain permitted by that chain's barrier for `SetErrorHandler`/`SetAppendix`/`Trap`). No governance/privileged origin is required; only a barrier that allows top-level `SetErrorHandler`/`SetAppendix`/`Trap` instructions, which is standard for permissive XCM configurations (these are ordinary, benchmarked instructions, not filtered by common barriers like `AllowTopLevelPaidExecutionFrom`/`WithComputedOrigin`).

### Recommendation
Add a runtime-tracked bound in `XcmExecutor::execute`'s outer `while` loop — e.g., an explicit iteration counter or a live weight meter that is decremented as each `vm.process(...)` call runs and that aborts (returning `Outcome::Incomplete`) once accumulated real work exceeds the `xcm_weight`/`weight_credit` budget, independent of the static `prepare()`-computed weight. Additionally, consider re-applying `RECURSION_LIMIT` (or a similar counter) across error-handler/appendix hand-offs in `execute()`, not just within a single `process()` call, and/or disallowing `SetErrorHandler` from re-installing a handler while that same handler is being executed (detect and reject self-reinstallation cycles).

impl<T: Get<Weight>, C: Decode + GetDispatchInfo, M> FixedWeightBounds<T, C, M> {
	fn weight_with_limit(
		message: &mut Xcm<C>,
		instructions_left: &mut u32,
		weight_limit: Weight,
	) -> Result<Weight, InstructionError> {
		let mut total_weight: Weight = Weight::zero();
		for (index, instruction) in message.0.iter_mut().enumerate() {
			let index = index.try_into().unwrap_or(InstructionIndex::MAX);
			*instructions_left = instructions_left
				.checked_sub(1)
				.ok_or_else(|| InstructionError { index, error: XcmError::ExceedsStackLimit })?;
			let instruction_weight =
				&Self::instr_weight_with_limit(instruction, instructions_left, weight_limit)
					.map_err(|error| InstructionError { index, error })?;
			total_weight = total_weight
				.checked_add(instruction_weight)
				.ok_or(InstructionError { index, error: XcmError::Overflow })?;
			if total_weight.any_gt(weight_limit) {
				return Err(InstructionError {
					index,
					error: XcmError::WeightLimitReached(total_weight),
				});
			}
		}
		Ok(total_weight)
	}

	fn instr_weight_with_limit(
		instruction: &mut Instruction<C>,
		instructions_left: &mut u32,
		weight_limit: Weight,
	) -> Result<Weight, XcmError> {
		let instruction_weight = match instruction {
			Transact { ref mut call, .. } => {
				call.ensure_decoded()
					.map_err(|_| XcmError::FailedToDecode)?
					.get_dispatch_info()
					.call_weight
			},
			SetErrorHandler(xcm) | SetAppendix(xcm) | ExecuteWithOrigin { xcm, .. } => {
				Self::weight_with_limit(xcm, instructions_left, weight_limit)
					.map_err(|outcome_error| outcome_error.error)?
			},
			_ => Weight::zero(),
		};
		let total_weight = T::get().checked_add(&instruction_weight).ok_or(XcmError::Overflow)?;
		Ok(total_weight)
	}

pub struct DenyRecursively<Inner>(PhantomData<Inner>);

impl<Inner: DenyExecution> DenyRecursively<Inner> {
	/// Recursively applies the deny filter to a nested XCM.
	///
	/// Ensures that restricted instructions are blocked at any depth within the XCM.
	/// Uses a **recursion counter** to prevent stack overflows from deep nesting.
	fn deny_recursively<RuntimeCall>(
		origin: &Location,
		xcm: &mut Xcm<RuntimeCall>,
		max_weight: Weight,
		properties: &mut Properties,
	) -> Result<ControlFlow<()>, ProcessMessageError> {
		// Initialise recursion counter for this execution context.
		recursion_count::using_once(&mut 1, || {
			// Prevent stack overflow by enforcing a recursion depth limit.
			recursion_count::with(|count| {
				if *count > xcm_executor::RECURSION_LIMIT {
					tracing::debug!(
                    	target: "xcm::barriers",
                    	"Recursion limit exceeded (count: {count}), origin: {:?}, xcm: {:?}, max_weight: {:?}, properties: {:?}",
                    	origin, xcm, max_weight, properties
                	);
					return None;
				}
				*count = count.saturating_add(1);
				Some(())
			}).flatten().ok_or(ProcessMessageError::StackLimitReached)?;

			// Ensure the counter is decremented even if an early return occurs.
			sp_core::defer! {
				recursion_count::with(|count| {
					*count = count.saturating_sub(1);
				});
			}

			// Recursively check the nested XCM instructions.
			Self::deny_execution(origin, xcm.inner_mut(), max_weight, properties)
		})?;

		Ok(ControlFlow::Continue(()))
	}
}
