### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw` — escrow debit happens after the external token transfer, enabling double-release of escrowed funds via a malicious token/reentrant beneficiary - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds in `withdraw()` by making the external token/native transfer *before* decrementing the corresponding `_orders[commitment][token]` escrow balance. This is the same class of bug described in the external report (ERC20Pods): a function assumes that state read/checked early in a loop (`_orders[...] == 0`) remains valid for the rest of that iteration, but the external call embedded in the same iteration can be used to re-enter the contract before the effect (`-= amount`) is committed, so the escrow accounting lags behind the actual transfer.

### Finding Description
In `withdraw()`:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");        // INTERACTION
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); // INTERACTION
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;                    // EFFECT (too late)
        unchecked { ++i; }
    }
    ...
}
``` [1](#0-0) 

The check on line 700 (`_orders[...] == 0`) only guards against a *zero* balance, not an *insufficient* one, and the effect that actually protects against reuse (the `-= amount`) executes only after the interaction returns. This is the opposite order of the already-hardened sibling implementation `IntentsBase._withdraw`, which decrements escrow *before* transferring:
```solidity
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [2](#0-1) 

This CEI-safe pattern, plus setting `_filled[commitment]` at the very top of the fill/withdraw path, is exactly the remediation the ISMP/Intents codebase already applied for the analogous reentrancy class documented in `IntrinsicIntentsReentrancyTest.sol` (the `_filled[commitment] = msg.sender` fix for `_fillSameChain`/`_fillCrossChain`). [3](#0-2) 

The Tron `IntentGatewayV2.withdraw()` was not brought in line with that fix for the per-token transfer loop: `_filled[commitment]` blocks a second top-level call to `withdraw`/`cancelOrder` for the *same* commitment, but it does nothing to protect the per-token `_orders[commitment][token]` decrement that happens inside the loop, after each individual external transfer. Any of the reachable callers of `withdraw` — `onAccept` (RedeemEscrow/RefundEscrow) and the public, unprivileged same-chain branch of `cancelOrder` — can hit this path: [4](#0-3) [5](#0-4) 

Because `order.inputs[i].token` is fully attacker-controlled at `placeOrder` time (any intent placer can pick any ERC20 address as an escrowed input), an attacker can escrow a self-deployed malicious ERC20 whose `transfer()` implementation calls back into the gateway during the token-transfer interaction, before the escrow decrement for that same token executes.

### Impact Explanation
An attacker who controls the escrowed token contract (or, on native-token legs, controls the `beneficiary` contract that receives ETH via the raw `.call`) can re-enter mid-loop, before `_orders[commitment][token] -= amount` commits. Depending on how the host's receipt bookkeeping for the relevant delivery path is ordered relative to the `onAccept`/`onGetResponse` external call into the app (verified CEI-safe for the GET-response path in `EvmHost.sol`, but not conclusively verified for the POST/`onAccept` delivery path within the available investigation budget), this can translate into the escrow for a given token being paid out more than once for the same order, i.e., unbacked release of escrowed funds — a direct loss for whichever party ultimately funds the escrow (the order placer / protocol), which is a Critical-class impact per the report's own bug class (double mint / double release of value).

### Likelihood Explanation
Reachability is realistic: `withdraw()` is invoked from `onAccept` (post-fill escrow redemption, and cross-chain refund) and directly from the *unprivileged*, publicly callable same-chain branch of `cancelOrder`. The attacker fully controls the token contract used as an escrowed input at order-placement time, which is the standard "malicious ERC20 with reentrant transfer hook" pattern common to intents/bridge escrow systems. The remaining uncertainty is whether other layers (host receipt bookkeeping on the POST path, `_filled` guard on the containing call) fully close the window before the loop's own per-token decrement executes; this was not fully confirmed due to investigation-time limits.

### Recommendation
Apply the same CEI ordering already used in `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` (and the fee escrow) *before* performing the native/ERC20 transfer in the Tron `withdraw()` implementation, and prefer `SafeERC20.safeTransfer` over raw `.call(...)` to also get revert-on-failure semantics instead of silently swallowing return values.

### Proof of Concept
Not independently reproduced in this pass — this requires deploying a malicious ERC20 whose `transfer()` re-enters `IntentGatewayV2` mid-`withdraw()` loop and confirming whether the containing entry point (`cancelOrder` same-chain path, unprivileged) or the host's request-receipt bookkeeping (unverified for the POST/`onAccept` delivery path) prevents a second successful transfer for the same `(commitment, token)` pair before the decrement at line 710 executes. The concrete, provable defect is the code-order divergence between `evm/tron/contracts/apps/IntentGatewayV2.sol#L691-714` (interaction-before-effect) and the hardened `evm/src/apps/intentsv2/IntentsBase.sol#L451-469` (effect-before-interaction).
