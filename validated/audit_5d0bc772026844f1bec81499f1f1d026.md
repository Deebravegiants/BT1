### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant `shop` spoofing in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the webhook HMAC only over the raw body, then passes the unauthenticated `shop-domain` header straight to the app's handler as the tenant identifier, breaking the binding: `hmac(secret, body) == valid` should imply `shop header == tenant that produced body`, but the gem never ties the header to the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` verifies the HMAC via `Utils::HmacValidator.validate(request)`, which only checks `request.hmac` against `compute_signature(request.to_signable_string, secret)` i.e. the body [3](#0-2) [4](#0-3) . After that single check, `request.shop` (the header value) is forwarded unchanged into `WebhookMetadata` and handed to the app's `handler.handle` as the trusted tenant identity [5](#0-4) .

Because the shop header is never part of the signed payload, the identity binding the gem is supposed to guarantee — "bytes verified == bytes the tenant field is derived from" — is broken: `hmac` binds only `raw_body`, while `shop` is an independent, attacker-influenceable header value.

### Impact Explanation
Any attacker who can get a validly HMAC-signed webhook body for **any** shop (e.g., their own shop, which they fully control and receive Shopify webhooks for) can replay that exact signed body to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still pass because it only checks the body against the secret, and the gem will then report `WebhookMetadata#shop` as the victim's domain to the host application's handler. If the host application uses this gem-provided `shop` value (as documented/intended) to select per-tenant state, credentials, or trigger tenant-scoped actions (e.g. GDPR redaction, data deletion, session invalidation) keyed off `data.shop`, the attacker can inject the forged tenant id and cause cross-tenant data operations or corruption using only their own legitimate app installation — no access token or `client_secret` compromise required. This matches "cross-tenant access" impact.

### Likelihood Explanation
Likelihood is high in relative terms: any merchant/attacker who has legitimately installed the app on their own shop already receives correctly-signed webhook deliveries for that shop and can capture/replay the raw body with a modified `shop-domain` header to the same public webhook endpoint. No secret material is needed — only the ability to intercept/replay one's own webhook traffic, which is achievable by any unprivileged internet user who installs the app on a shop they control.

### Recommendation
Include the shop/tenant identity in the HMAC-covered payload (or otherwise cryptographically bind the `shop-domain` header to the signed body), or require the caller to cross-check the header-derived shop against a shop the app already trusts for that specific webhook subscription/session before acting on `WebhookMetadata#shop`. Document explicitly that `shop-domain` is unauthenticated and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and enables a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook with a correctly computed `X-Shopify-Hmac-Sha256` over the JSON body, and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this raw body + valid HMAC header, then re-sends the identical body/HMAC to the app's webhook endpoint but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only validates the unchanged body against the shared secret [6](#0-5) .
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [5](#0-4) , and any tenant-scoped logic keyed on this value now operates against `victim-shop`, not the attacker's own shop.
