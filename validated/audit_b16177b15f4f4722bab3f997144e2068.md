### Title
Unvalidated `host` parameter in `ShopifyAPI::Auth.embedded_app_url` enables open redirect / forced OAuth completion to an attacker-controlled domain - (File: lib/shopify_api/auth.rb)

### Summary
`ShopifyAPI::Auth.embedded_app_url` base64-decodes the caller-supplied `host` parameter and splices it directly into a URL, with no check that the decoded value is a trusted Shopify domain. Elsewhere in the same gem, `ShopifyAPI::Utils::ShopValidator` exists specifically to sanitize/validate shop and host values (including the "unified admin" `admin.shopify.com/store/<shop>` form) against a `TRUSTED_SHOPIFY_DOMAINS` allowlist before they are trusted [1](#0-0) , but `embedded_app_url` never calls it.

### Finding Description
`embedded_app_url` is:

```ruby
def embedded_app_url(host)
  ...
  decoded_host = Base64.decode64(host)
  "https://#{decoded_host}/apps/#{Context.api_key}"
end
``` [2](#0-1) 

The `host` argument is the well-known Shopify Admin `host` query parameter that embedded apps receive on every load; it is attacker-influenceable client-side data (it travels in the URL and is not HMAC-covered like the OAuth callback `AuthQuery`, whose `shop` field *is* signed via `to_signable_string`) [3](#0-2) . The library itself demonstrates elsewhere that this exact value needs domain validation: `ShopValidator.sanitize_shop_domain` explicitly decodes/parses `host`-style unified-admin URLs (`admin.shopify.com/store/<shop>`) and only trusts them if they resolve to one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [4](#0-3) . `embedded_app_url`, however, performs no such check — the equality that should hold is `decoded_host == ShopValidator.sanitize!(decoded_host)`, but the method never enforces it, so any base64 string decodes straight into the returned URL.

Because the returned URL embeds `Context.api_key` (the app's client id) and is intended to be used by consumer applications to build the Shopify Admin redirect/link for completing or continuing the embedded app session, an attacker who can supply an arbitrary `host` value can produce a URL of the form `https://attacker.example/apps/<api_key>` that superficially looks like a legitimate Shopify link output by the gem, since it is generated by the trusted library function.

### Impact Explanation
This matches the "session fixation or forced OAuth completion" bucket for High severity: an application that trusts `embedded_app_url`'s output to redirect the merchant back into the embedded app (a common integration pattern for OAuth completion / bounce pages) can be tricked into redirecting the merchant's browser, along with any subsequent OAuth completion navigation, to an attacker-controlled host instead of a genuine `*.myshopify.com`/`admin.shopify.com` domain — this is an open-redirect primitive rooted in the gem's own trust boundary, not merely the host app ignoring documented behavior, because the gem provides no validation hook at all here despite having exactly this validation logic (`ShopValidator`) available and used for the analogous `shop`/`host` value in other flows.

### Likelihood Explanation
`host` is fully attacker-controlled in the URL of any embedded-app page load and is not covered by any HMAC or signature the gem checks before being passed to `embedded_app_url` (unlike `AuthQuery#shop`, which is HMAC-bound) [5](#0-4) . No secret or privileged access is required to trigger it — an unprivileged internet user simply needs to get a victim to open a crafted app URL with a manipulated `host` parameter, which is the standard entry point for embedded Shopify apps.

### Recommendation
Route the decoded `host` value through `ShopifyAPI::Utils::ShopValidator.sanitize!` (or an equivalent trusted-domain check) inside `embedded_app_url` before constructing the URL, raising `Errors::InvalidShopError` (mirroring the existing behavior in `ShopValidator`) when the decoded host is not one of `TRUSTED_SHOPIFY_DOMAINS`. This aligns `embedded_app_url` with the validation already performed for shop/host values elsewhere in the codebase and closes the gap between "host validated" and "host actually embedded in the generated URL."

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "my_api_key", api_secret_key: "secret", ...)

malicious_host = Base64.strict_encode64("attacker.example/phish")
url = ShopifyAPI::Auth.embedded_app_url(malicious_host)
# => "https://attacker.example/phish/apps/my_api_key"
```
No signature, secret, or trusted context is checked on `malicious_host`; any base64 string is accepted and reflected into the returned URL, in contrast to `ShopValidator.sanitize!("attacker.example")`, which correctly raises `ShopifyAPI::Errors::InvalidShopError` for the same untrusted domain [6](#0-5) .
