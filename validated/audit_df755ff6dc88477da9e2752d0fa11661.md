### Title
Emporium's shared-custody design lets any attacker steal assets held under Emporium's address (e.g., another user's Uniswap V3 LP NFT fees) via arbitrary stateless op calldata - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 "stateless" branch executes `op.endpoint.call{value: op.value}(op.callData)` with `address(this)` == Emporium as `msg.sender`, and the only content restriction is blocking two specific selectors. Any unprivileged attacker submitting their own valid proof can craft an `EmporiumStack` whose op calls `positionManager.collect(CollectParams{tokenId: victimTokenId, recipient: attacker})`, and because Emporium is the on-chain owner/approved caller of any NFT minted with `recipient=address(this)` by a prior (victim) transaction, Uniswap authorizes the call — redirecting the victim's accrued LP fees to the attacker.

### Finding Description
The broken equality is: `owner(LP_NFT)` before the attacker's tx is `address(Emporium)` (set by the victim's earlier `runAction` mint with `recipient=address(this)`), not tied to any specific user identity, yet the code assumes/relies on this shared owner correctly gating access — it does not. `EmporiumUpgradeable.runAction` decodes an attacker-fully-controlled `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` [2](#0-1) , and for CASE 2 (`op.invokeWallet=false` or `stack.signerAddress=address(0)`) it directly does `op.endpoint.call{value: op.value}(op.callData)` from the Emporium contract itself, with the only content check being a selector blocklist for `callHinkalWallet`/`doSendToRelay` [3](#0-2) . When `stack.signerAddress == address(0)`, `verifyWallet` performs no EIP-712 signature check on the ops content at all, only marking `emporiumMessage` as used [4](#0-3) . The attacker constructs their own `circomData`/proof, so this metadata is entirely self-chosen — `performHinkalChecks` only checks that `getHashedCalldata(circomData) == circomData.calldataHash` (an internal-consistency hash, not an authorization check) [5](#0-4) . Critically, the post-call balance-diff/UTXO accounting in `runAction` only tracks tokens listed in `circomData.erc20TokenAddresses` via `getBalancesForArray` [6](#0-5) [7](#0-6) ; because `positionManager.collect` sends fee tokens directly to `recipient=attacker` (not to Emporium), Emporium's own balance never decreases, so `balanceChange` stays `>= 0` and the `BalanceChangeShouldBePositive` guard [8](#0-7)  never fires — the theft is entirely invisible to Hinkal's accounting. `ExternalActionBaseUpgradeable.onlyAllowedRecipient` only checks that `msg.sender == Hinkal`, not the op's `endpoint`/`callData` [1](#0-0) .

### Impact Explanation
Critical — direct theft of another user's in-flight assets/fees. Any prior interaction that leaves an asset owned by or approved to the shared Emporium contract address (LP NFTs, ERC20 approvals, staked positions, etc. left with `recipient=address(this)`) becomes stealable by any subsequent unprivileged attacker who submits their own valid proof, because Emporium's identity — not the depositing user's identity — is the on-chain authority recognized by the external protocol (Uniswap here).

### Likelihood Explanation
Requires only that some prior transaction (victim) left state owned by Emporium itself (e.g., minted an NFT to `recipient=address(this)`) and that the `tokenId`/relevant identifier is discoverable on-chain (trivial via public mint events). The attacker needs no special role — just their own funds, their own proof generation, and knowledge of standard ABI encoding for `EmporiumStack`. This is fully repeatable for every victim position left under Emporium's ownership.

### Recommendation
Do not let Emporium act as a shared owner/approved party for externally-tracked assets like NFTs across unrelated users. Either (a) require CASE 2 stateless ops to target only a strict allowlist of endpoints/selectors set by the contract owner, disallowing arbitrary `op.endpoint.call(op.callData)`, or (b) always mint/route positions and approvals to the actual per-user stealth address/wallet rather than to `address(this)`, or (c) bind the specific op parameters (e.g., `tokenId`, `recipient`) cryptographically to the depositing user's proof/session so no other user's proof can reference them.

### Proof of Concept
Foundry test: deploy a mock `INonfungiblePositionManager`; have "victim" call `Hinkal.transact` → `EmporiumUpgradeable.runAction` with a CASE 2 op that calls `mint(...)` with `recipient=address(Emporium)`, capturing `tokenId`; assert `IERC721(positionManager).ownerOf(tokenId) == address(Emporium)`. Then have "attacker" (unrelated funds/proof) call `Hinkal.transact` → `runAction` with a CASE 2 op calling `collect(CollectParams{tokenId: tokenId, recipient: attacker, ...})`; assert the call succeeds and `attacker`'s token balance increases by the victim's accrued fees while Emporium's tracked `erc20TokenAddresses` balance is unchanged, demonstrating the equality `owner(LP_NFT)==victim's stealth address` never held and fees flow to attacker without any Hinkal-level check catching it.
