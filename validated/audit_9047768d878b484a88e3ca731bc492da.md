### Title
`enroll_user::Plan::run` proceeds to sign and upload biometric data without inspecting `pipeline.occlusion` / `pipeline.face_identifier_fraud_checks`, and the only upstream fraud gate is stubbed out - ([File: src/plans/enroll_user.rs])

### Summary
`enroll_user::Plan::run` calculates a signature and calls `signup_post::request` using the pipeline's iris/mask codes without ever checking `pipeline.occlusion` or `pipeline.face_identifier_fraud_checks` for `Err`/fraud results. The only place these fields are supposed to gate the signup, `Plan::detect_fraud` in `src/plans/mod.rs`, is a no-op stub that always returns `false` in this build.

### Finding Description
`Plan::run` in `src/plans/enroll_user.rs` takes `self.pipeline: Option<&Pipeline>` and, if present, only uses it to compute `make_signature` (based on `pipeline.v2` iris/mask codes) before calling `signup_post::request(..., self.pipeline, self.signup_reason)`: [1](#0-0) 
Neither `Plan::run` nor `make_signature` reads `pipeline.occlusion` or `pipeline.face_identifier_fraud_checks`: [2](#0-1) 

The `signup_reason` passed in is computed upstream in `Master::do_signup`: [3](#0-2) 
which relies on `detect_fraud`. That function is explicitly stubbed to always return `Ok(false)`, with the comment "FOSS: WE HAVE DELETED ALL FRAUD CHECKS": [4](#0-3) 
and the underlying `fraud_check::Report` type has `N_FRAUD_CHECKS = 0` and an empty check list, also commented "we manually deleted all fraud checks": [5](#0-4) 

`biometric_pipeline::Plan::run` itself does not fail the overall pipeline construction when `occlusion` or `face_identifier_fraud_checks` resolve to `Err` — it just stores the `Err` variant into the `Pipeline` struct and still returns `Ok(Pipeline{...})`: [6](#0-5) [7](#0-6) 
This propagates as `Ok(Some(pipeline))` from `Master::biometric_pipeline` in `src/plans/mod.rs`, so `pipeline.is_some()` remains true even with `occlusion: Err(_)` and `face_identifier_fraud_checks: Err(_)`, meaning `signup_reason` becomes `SignupReason::Normal` (since `fraud_detected` is always `false` and `pipeline.is_none()` is false): [8](#0-7) [9](#0-8) 

Thus `enroll_user::Plan{ signup_reason: SignupReason::Normal, pipeline: Some(&Pipeline{occlusion: Err(_), face_identifier_fraud_checks: Err(_), ..}) }` is exactly what gets constructed and passed to `run()`, which proceeds to `make_signature` + `signup_post::request` without any client-side check of the occlusion/fraud fields.

### Impact Explanation
No client-side (orb-core) enforcement exists to fail-close a signup when occlusion detection errors out or the face-identifier fraud model reports failure/fraud. The `signup_reason` sent to the backend will read `Normal` even though the biometric pipeline flagged occlusion/fraud errors, and enrollment proceeds through signature calculation and upload. Whether this results in a completed fraudulent enrollment ultimately depends on backend-side validation of `pipeline.occlusion`/`face_identifier_fraud_checks` inside `signup_post::request`'s payload (not verifiable from this repository), so the orb-core code path itself provides no fail-closed guarantee — the gating logic that should exist (`detect_fraud`) is present only as dead/stubbed code in this FOSS build.

### Likelihood Explanation
This is not an attacker-triggered logic bug but a deliberate removal of fraud-check enforcement in the released/open-source build, explicitly documented with "FOSS: WE HAVE DELETED ALL FRAUD CHECKS" comments in both `src/plans/mod.rs` and `src/plans/fraud_check.rs`. Reaching this code path only requires a normal signup session with a degraded/occluded capture (no privileged access needed), and every occlusion/fraud-error outcome flows into `signup_reason::Normal` and `enroll_user::Plan::run()` without additional gating, so it is trivially and repeatably reachable in this codebase.

### Recommendation
Reinstate a fail-closed check either in `Plan::detect_fraud` (`src/plans/mod.rs`) or directly in `enroll_user::Plan::run` (`src/plans/enroll_user.rs`): if `pipeline.occlusion.is_err()` or `pipeline.face_identifier_fraud_checks` is `Err(_)`/indicates fraud, set `signup_reason = SignupReason::Fraud` (or `Failure`) and short-circuit `enroll_user::Plan::run` before calling `make_signature`/`signup_post::request`, returning a failure `Status` instead.

### Proof of Concept
Unit test in `src/plans/enroll_user.rs` (or a new test module):
1. Build a `biometric_pipeline::Pipeline` fixture via `Pipeline::default_with_ok()` but override `occlusion` to `Err(<PyError variant>)` and `face_identifier_fraud_checks` to `Err(<PyError variant>)`.
2. Construct `enroll_user::Plan { signup_reason: SignupReason::Normal, pipeline: Some(&pipeline), .. }` with a stub `Capture` and QR data.
3. Call `Plan::run(orb).await` against a mocked/stub `Orb` and backend.
4. Assert that `signup_post::request` is never invoked (e.g., via a mock/spy) or that `Plan::run` returns a failure `Status` (e.g., a new `Status::FraudOrOcclusionDetected`) instead of proceeding to `Status::Success`/`SignupVerificationNotSuccessful` via the network path — demonstrating the current code fails this assertion because it calls `signup_post::request` regardless of the `Err` fields.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
