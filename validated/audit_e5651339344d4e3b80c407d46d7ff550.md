### Title
Stale delegate grant re-arms on NFT return, replaying a previously revoked-by-transfer authorization - (File: contracts/controller/src/storage/account.rs)

### Summary
The LinOTP bug class is a replay: a credential recorded at an earlier time is accepted again after a resynchronization resets state. XOXNO Lending has the same shape in its delegate-grant storage. `DelegateGrant` is stamped only with `granted_by` (the owner's address), with no ownership epoch or nonce. When the position NFT is transferred, the grant goes dormant because `get_delegates` filters on `granted_by == current_owner`, but the entry is **not deleted**. If the NFT later returns to the original owner — an ordinary event for a freely transferable position token — the stale grant becomes live again with no fresh authorization, replaying a delegation the owner may believe lapsed on transfer.

### Finding Description
`get_delegates` returns the stored delegate list whenever `grant.granted_by == *owner`, and nothing clears `ControllerKey::Delegates(account_id)` on NFT transfer:

- `contracts/controller/src/storage/account.rs:176-181` — filter by `granted_by`, stale entry persists.
- `contracts/position-nft/README.md:174-179` — documents: "The stale grant stays in storage and re-arms if the token returns to `granted_by`."
- `docs/reference/invariants.md:36-38` — "A grant records the owner's address, without a transfer epoch. It is inactive under another owner but can reactivate if the NFT returns."

The dormant grant confers full economic control: `is_owner_or_delegate` (`contracts/controller/src/account.rs:114-127`) authorizes any listed delegate that is an active position manager to reach `borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `migrate_from_blend` (per `scripts/permissionless_entrypoints.txt:49-56`), and delegates may pick arbitrary payout recipients (`docs/explanation/threat-model.md:86-87`).

The only cleanup paths are voluntary: an intervening owner's `add_delegate`/`remove_delegate` overwrites or deletes the entry (`account.rs:203-247`). A buyer who never touches delegation — the common case — leaves the stale grant intact for whoever held it before.

Attack path (all unprivileged):
1. Alice owns account `A` with collateral; she calls `add_delegate` granting manager contract `M`.
2. Alice sells/transfers the position NFT to Bob. `M`'s grant goes dormant.
3. Bob does not call `add_delegate`/`remove_delegate` (nothing requires him to).
4. Bob sells/transfers the NFT back to Alice (or to any address Alice controls — e.g., she repurchases her own position on a marketplace, or Bob is bribed/cooperating).
5. `granted_by == owner` holds again; `M`'s grant is live with no new auth from Alice.
6. `M` calls `withdraw`/`borrow` on `A` with itself as recipient and drains the collateral up to the account gates.

### Impact Explanation
Theft of user funds. A previously recorded delegate authorization is replayed against the original owner after an ownership round-trip, letting a stale position manager withdraw collateral or borrow against it to an arbitrary recipient, without any fresh consent. Loss is bounded only by the account's LTV gates — i.e., effectively all withdrawable collateral plus maximum borrowable debt.

### Likelihood Explanation
Medium. It requires the account to round-trip back to the granting owner while no intervening owner modifies delegates, and the delegate must be an active registered position manager. Both conditions are realistic: positions are marketed as ordinary transferable NFTs (`contracts/position-nft/README.md:39-41`), sellers have no incentive or UI prompt to write delegate state for an account they are exiting, and the trigger (return of the token) is outside the victim's control once the position trades. The delegate needs no extra privilege beyond the grant it was given in the past — precisely the replay property.

### Recommendation
Bind the grant to an ownership epoch rather than the owner address. For example, have the controller maintain a per-account `transfer_epoch` (or store the `granted_at` owner plus an NFT-side generation counter incremented on every `transfer`/`transfer_from`/`burn`), and have `get_delegates` require `grant.epoch == current_epoch`. Alternatively, emit a hook the NFT can call on transfer — or provide a cheap permissionless `purge_delegates(account_id)` — so a stale `DelegateGrant` is deleted the first time an ownership change is observed, rather than silently re-arming.

### Proof of Concept
```text
// Precondition: M is an active position manager (governance-approved).
1. alice: controller.add_delegate(caller=alice, account_id=A, delegate=M)
   // storage: Delegates(A) = DelegateGrant { granted_by: alice, delegates: [M] }
2. alice: position_nft.transfer(from=alice, to=bob, token_id=A)
   // get_delegates(A, bob) -> [] (grant dormant, NOT deleted)
3. // bob never calls add_delegate or remove_delegate
4. bob:   position_nft.transfer(from=bob, to=alice, token_id=A)
   // get_delegates(A, alice) -> [M]  — stale grant re-armed, no auth from alice
5. M:     controller.withdraw(caller=M, account_id=A, withdrawals=[...], to=M)
   // is_owner_or_delegate(A, M, alice) == true -> drains alice's collateral
```
Supporting code: `contracts/controller/src/storage/account.rs:176-181` (`get_delegates`), `:185-199` (`set_delegates` — keyed only by `account_id`, no epoch), `contracts/controller/src/account.rs:114-127` (`is_owner_or_delegate`). The dormant/re-arm semantics are confirmed in `contracts/position-nft/README.md:174-179` and `docs/reference/invariants.md:36-38`; the test `transfer_revokes_prior_owner_and_delegates` (`contracts/controller/tests/helpers/account.rs:387-432`) verifies the grant dies on transfer but never tests the NFT returning, leaving the replay window uncovered.

Caveat: the re-arm behavior is documented in the README and invariants as a known property of the design. If the prompt's "documented ADR choices" exclusion is read to cover it, this should be downgraded; however, the docs describe the mechanism without a stated justification, and the replay-into-theft path stands on the code as written.
