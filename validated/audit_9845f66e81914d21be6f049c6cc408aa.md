### Title
Webhook Shop Attribution Spoofing — HMAC Covers Only the Raw Body, Not the `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. An attacker who legitimately receives one authentic, correctly-signed webhook (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the signature check still passes.

### Finding Description
`Request#shop` reads directly from an unauthenticated header: [1](#0-0) 

But `to_signable_string`, which is the only material fed into the HMAC comparison, is just the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e. the body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` trusts this validation result and then constructs the `WebhookMetadata` passed to the app's handler using `request.shop`, the unauthenticated header value: [4](#0-3) 

Because the app's webhook secret (`Context.api_secret_key`) is a single, global per-app secret shared across every merchant/shop that has installed the app — not a per-shop secret — any unprivileged user who installs the app on their own (potentially free/dev) store can capture a legitimately-signed webhook body + HMAC for their own shop. They can then replay that same body and HMAC to the app's webhook endpoint while setting `x-shopify-shop-domain` to an arbitrary victim shop domain. `HmacValidator.validate` will still return `true` because the body/HMAC pair is authentic — the forged `shop` header is simply never checked.

The gem's own documentation instructs host apps to trust `data.shop` as the tenant identifier without qualification: [5](#0-4) 

This breaks the intended binding: `authenticated_shop == shop_used_for_tenant_routing`. In reality, `authenticated_shop` is "whichever merchant happens to share the app's secret and sent a validly-shaped body," while `shop_used_for_tenant_routing` is "whatever the attacker put in an HTTP header."

### Impact Explanation
This is a cross-tenant identity-confusion primitive at the library layer: the one piece of tenant-identifying data (`shop`) that host applications are told to key their session/data lookups on is not authenticated by the HMAC the gem itself verifies. An attacker (any developer who can install the target app on a shop they control) can forge the `shop` attribution of an otherwise-genuine, validly-signed webhook payload and have the app process it as though it originated from an arbitrary other shop. Depending on how the host app uses `data.shop` (e.g., to fetch a session/access token, mark installation/uninstallation state, or persist data keyed by shop), this enables cross-tenant data corruption or misattribution.

### Likelihood Explanation
Any user capable of installing the app on a shop they control (a very low bar — free Shopify dev/partner stores are trivially obtainable) can capture at least one authentic body+HMAC pair for a webhook topic of their choosing, then replay it with a forged shop-domain header against the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only an unprivileged installer role and network access to the webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`) into the material that is authenticated, rather than trusting the raw header value independently of the signature. Options:
- Include the `shop-domain` and `topic` headers in the signed payload used for signature verification (this would require coordination with Shopify's webhook signing scheme, since Shopify currently signs only the body), or
- At minimum, document/enforce that host applications must cross-check `request.shop` against an app-side registry of shops that are expected to be sending webhooks for the given `webhook_id`/topic combination, and reject webhooks whose `shop` doesn't match an existing, verified installation.
- Consider exposing a combined verification helper that ties `webhook_id` + `shop` + HMAC together so library consumers aren't left to trust an unauthenticated header directly.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, with body `B` and a valid `hmac-sha256` header `H = HMAC(secret, B)` (secret is the app's single global `client_secret`).
2. Attacker captures `B` and `H` from the request their own endpoint received (or from any endpoint they control).
3. Attacker sends a new HTTP POST to the victim app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: `H` (unchanged)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`: unchanged
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this succeeds since `B` and `H` are unmodified: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the payload/body actually originated from the attacker's own shop, causing the host app to misattribute the webhook to the victim tenant.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

    def handle(data:)

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
