### Title
Webhook `shop` identity is taken from an unauthenticated HTTP header not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
This is the same bug class as the Biconomy report: a value that drives security-relevant behavior is taken from a source that is disjoint from the source that is actually authenticated. In Biconomy, the module address used for validation came from `nonce`, but the enable-mode payload that got installed was a *different* module signed in `signature` — the two were not the same authenticated artifact. In this gem, `ShopifyAPI::Webhooks::Request#shop` is read from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature verified by `HmacValidator`/`to_signable_string` only covers the raw request body. The header carrying the tenant identity is never part of what is cryptographically verified.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with no further validation: [2](#0-1) 

But `to_signable_string`, which is what actually gets HMAC-verified via `HmacValidator.validate`, is defined as only the raw request body: [3](#0-2) [4](#0-3) 

So the equality the system is implicitly relying on is:

`shop used for tenant identification (from header)` == `shop cryptographically bound by hmac (from to_signable_string == raw_body only)`

This equality does not hold: `shop` is derived from a header that is not part of `to_signable_string`, so `HmacValidator.validate(request)` returning `true` proves only that the *body* was signed by Shopify with the app's secret — it says nothing about which shop the header claims to be from, because Shopify's `hmac-sha256` header, per Shopify's documented webhook validation scheme, is computed over the raw body alone, not over headers. This is consistent with Shopify's own signing scheme, but it means any downstream consumer that trusts `request.shop` as an authenticated tenant identifier is trusting an unauthenticated value that an attacker fully controls if they can otherwise get a validly-signed body accepted (e.g., replay of a body signed for shop A, replayed with a forged `shop-domain` header claiming shop B, or a raw body whose HMAC happens to validate for reasons outside this gem's control such as body reuse across shops using the same secret).

### Impact Explanation
If a host application uses `request.shop` (as returned by this gem) to select which merchant's session/access token to load or which tenant's data to mutate in response to a webhook, and only checks `HmacValidator.validate(request)` as the authentication gate, then the `shop` value used for that tenant lookup is not bound by the signature at all. This is a cross-tenant boundary issue: the field that determines *whose* data is affected (`shop`) is disjoint from the field verified by the cryptographic proof (`raw_body`). This maps to the report's core class of bug — validation performed on one artifact, action performed using a different, un-bound artifate.

### Likelihood Explanation
This requires the host application to rely on `ShopifyAPI::Webhooks::Request#shop` as an authenticated tenant identifier without any additional binding — which is exactly the documented/intended use of this class (`Registry.process` style consumers key work off `request.shop` for the correct merchant). Because this behavior is inherent to how `Request#to_signable_string` and `Request#shop` are implemented in this gem, it is not a hypothetical or purely host-side misuse; it is a structural property of the class that any consumer of this gem's webhook-verification API inherits, matching the report's binding-break criteria (field acted on but not covered by the HMAC).

### Recommendation
Bind the shop identity into the value that is actually verified, or explicitly document/require that `shop` must never be used as a trust boundary in isolation from an independently verified session/shop record. Concretely, consider including the `shop-domain` header (and other Shopify-controlled headers such as `webhook-id`) into the HMAC-verified signable string, or cross-check `request.shop` against a shop already known/authenticated via an existing, verified session before acting on the webhook.

### Proof of Concept
1. Host app receives two webhooks in sequence, both with a validly-signed body under the app's shared secret (e.g., legitimately signed bodies from two different topics/times can be valid for different shops if body content doesn't encode the shop).
2. Attacker captures a validly-signed webhook body/HMAC pair (e.g., via a public-facing proxy log, or replay window) and re-sends it with an altered `shopify-shop-domain` header pointing at a different tenant.
3. `HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks `@raw_body`, which is unchanged. `request.shop` now returns the attacker-chosen shop domain.
4. If the host handler trusts `request.shop` to select the merchant context (a common, documented pattern for this gem), it processes the webhook payload against the wrong tenant's data — a cross-tenant action performed under a shop identity that was never covered by the signature.
