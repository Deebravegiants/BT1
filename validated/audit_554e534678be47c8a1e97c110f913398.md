### Title
Accrual RAY-value overflow panics before the borrow-index cap engages, permanently freezing all activity in a market - (File: common/src/rates/scaling.rs)

### Summary
The interest-accrual path multiplies scaled debt (`borrowed`, in RAY-scaled shares) by the `borrow_index` (also RAY) inside `scaled_to_original`, and the resulting RAY product can exceed `i128::MAX` while the index is still below `MAX_BORROW_INDEX_RAY` (10^36). Because the index cap only clamps the *index* and not the *value product*, the cap never engages: accrual panics with `GenericError::MathOverflow` first. Every state-changing pool operation accrues before acting, so once this point is crossed the market is bricked — no `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `seize_positions`, `recapitalize`, or `update_indexes` can ever execute again for that `(hub, asset)` book. This is the direct analog of CVE-2019-2914: a low-privilege-reachable condition that produces a complete, permanent denial of service rather than a transient fault.

### Finding Description
`scaled_to_original` is a bare `scaled.mul(env, index)` with no saturation or recovery path: [1](#0-0) 

`accrue_step` calls it unconditionally on both the debt and supply books at the start of every compounding chunk: [2](#0-1) 

`global_sync` runs `accrue_step` before every mutating op via `ops::renewed_market`-style cache loading, in chunks of at most `MAX_COMPOUND_DELTA_MS`: [3](#0-2) [4](#0-3) 

The `MAX_BORROW_INDEX_RAY` ceiling is applied to `new_borrow_index` inside `update_borrow_index` — *after* `scaled_to_original(borrowed, borrow_index)` has already been computed for utilization. So the value product `borrowed_raw × borrow_index_raw / RAY` overflows `i128` while `borrow_index < 10^36`, and the panic occurs before any cap or guard can clamp. The harness test demonstrates this concretely: a market with ~10^27-raw-unit debt at ~98% utilization on a steep rate curve reaches the overflow within decades, and the test pins that `borrow_index < MAX_BORROW_INDEX_RAY` at the failure and that subsequent `withdraw` and `repay` both revert with `MATH_OVERFLOW`: [5](#0-4) 

The panic is permanent: accrual is monotone (`borrow_index` never decreases, `last_timestamp` never moves backward), so the overflowing multiplication overflows on every subsequent call. There is no admin escape hatch either — `update_params` and `force_socialize_bad_debt` also accrue first.

### Impact Explanation
Permanent freezing of funds and a market unable to operate. Once the RAY-value product overflows, all supplier principal and all outstanding debt in that `(hub, asset)` market are frozen forever: suppliers cannot `withdraw`, borrowers cannot `repay`, liquidators cannot `liquidate` bad debt in other legs that touch this market, `clean_bad_debt` cannot socialize it, and permissionless `recapitalize` cannot rescue it (it calls `renewed_market`, which accrues). This maps exactly onto the CVE class — complete loss of availability of the affected component — and onto the accepted impact categories (permanent freezing of funds; contract unable to operate for that book). Other markets on the same pool contract are unaffected because state is keyed per `HubAssetKey`.

### Likelihood Explanation
Medium-low, commensurate with the Medium severity of the source CVE. The attacker path is fully unprivileged: `controller::borrow` (or `flash_position`/`multiply`) holds utilization near the steep end of the rate curve, and passive time does the rest — no governance, oracle, or privileged action is required, and no one can *stop* accrual once the book exists. However, reaching the cliff requires a very large book (scaled debt on the order of `i128::MAX / index`) sustained at high utilization for an extended period, which demands substantial capital and a market whose governance-set caps and collateral universe permit that scale — the harness test had to lift caps to reach it. For large-cap, high-utilization markets on steep curves this is a reachable end-state of ordinary usage rather than an exotic input, which is what keeps it in scope; the capital and time requirements are what keep it Medium rather than High.

### Recommendation
Bound the *value product*, not just the index. Concretely:

- Make `scaled_to_original` (or the accrual-side unscaling used by `accrue_step`) saturate or cap against a protocol constant such that `borrowed_raw × borrow_index_raw` can never exceed `i128::MAX` — e.g., cap `borrow_index` at `min(MAX_BORROW_INDEX_RAY, i128::MAX / borrowed_raw)` inside `update_borrow_index`, so the index cap engages *before* the multiplication overflows rather than after.
- Alternatively, perform the utilization numerator in `I256` (as `compound_interest` already does for `rate × delta_ms` in `common/src/rates/compound.rs:36-42`) and clamp the result, so a saturated debt book accrues at its ceiling instead of panicking.
- Add a regression assertion mirroring `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` that requires the index cap to engage and the market to remain operable, rather than asserting the current frozen-state behavior.

### Proof of Concept
Reachable sequence for a single unprivileged actor (the harness test is an executable version of it):

1. `controller::supply(caller, 0, spoke_id, [(hub_asset, huge_principal)])` — seed a large book (also `supply` by other accounts).
2. `controller::borrow(caller, account_id, [(hub_asset, ~98% of principal)], None)` — push utilization onto the steep slope of the rate curve so the borrow index compounds near `MAX_BORROW_RATE_RAY`.
3. Wait. No further action is needed; accrual is time-driven.
4. Any caller invokes `controller::update_indexes(caller, [hub_asset])` → `pool::update_indexes` → `interest::global_sync` → `accrue_step` → `scaled_to_original(borrowed, borrow_index)` → `Ray::mul` overflows `i128` → `panic_with_error!(env, GenericError::MathOverflow)`.
5. From this ledger forward, `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `flash_position`, and `update_indexes` on that market all revert with `MATH_OVERFLOW` at step 4 of their own accrual preamble. `borrow_index` remains strictly below `MAX_BORROW_INDEX_RAY`, proving the ceiling never fires.

Witnessed by `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356`, which asserts exactly `errors::MATH_OVERFLOW` from `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` with `last.borrow_index < MAX_BORROW_INDEX_RAY`.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```
