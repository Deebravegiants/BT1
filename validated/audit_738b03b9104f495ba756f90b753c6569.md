### Title
Hidden native-fee debit for `prefundedNativeFeeTokens` — `estimateWithdrawalFee` reports `amount = 0` while a `storage_deposit` intent still drains `nativeFee` from the user's wrap.near - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
When a token is listed in `bridgeConfigs[OmniBridge].prefundedNativeFeeTokens`, `estimateWithdrawalFee` skips the fee-conversion quote and can return `feeEstimation.amount = 0` (or an amount that omits the relayer's native fee) even though `fee.native_token_fee > 0`. `deriveOmniWithdrawIntentParams`/`createWithdrawIntentsPrimitive` still unconditionally emit a `storage_deposit` intent for `nativeFee` whenever `nativeFee > 0`, and per the NEP-141 `storage_deposit` semantics that amount is subtracted from the caller's own wrap.near balance. This creates a real, uncompensated debit that the displayed `feeEstimation.amount` does not reflect.

### Finding Description
The invariant claimed by the SDK is: `feeEstimation.amount == total value leaving the user's balance beyond amount, across all assets`.

Trace:
1. `estimateWithdrawalFee` (`omni-bridge.ts:559-660`) fetches `fee.native_token_fee` and `storageDepositFee`, sums them into `totalAmountToQuote`.
2. `if (totalAmountToQuote > 0n && !this.bridgeConfig.prefundedNativeFeeTokens.includes(assetId))` — the quote (which converts the wrap.near-denominated relayer/storage costs into an equivalent amount of the withdrawal token) is only requested when the token is **not** in `prefundedNativeFeeTokens` [1](#0-0) . For a prefunded token this branch is skipped entirely, so `amount` stays `0n` and is never increased by the native fee's asset-equivalent value.
3. `underlyingFees.relayerFee = fee.native_token_fee` is still populated regardless [2](#0-1) , so the fee estimation object internally "knows" the relayer fee is non-zero even while the externally visible `amount` field is `0`.
4. `validateWithdrawal` explicitly permits `feeEstimation.amount == 0` for prefunded/subsidized tokens, bypassing the normal `assert(args.feeEstimation.amount > 0n, ...)` guard [3](#0-2) .
5. `deriveOmniWithdrawIntentParams` reads `nativeFee = getUnderlyingFee(..., "relayerFee")` (still `fee.native_token_fee`, unaffected by the quote skip) and, whenever `nativeFee > 0n`, computes a `storageDepositAccountId` and returns it, independent of whether `feeEstimation.amount` is zero [4](#0-3) .
6. `createWithdrawIntentsPrimitive` unconditionally emits a `storage_deposit` intent with `amount: nativeFee.toString()` whenever `storageDepositAccountId !== null` [5](#0-4) .
7. Per the intents contract schema, the `storage_deposit` intent's `amount` "will be subtracted from user's NEP-141 `wNEAR` balance" directly, not sourced from any token_diff/quote conversion [6](#0-5) .

So for a `prefundedNativeFeeTokens` withdrawal with `nativeFee > 0`, the produced intent set moves `nativeFee` wrap.near out of the user's own balance via `storage_deposit`, while `feeEstimation.amount` (what `estimateWithdrawalFee` reports to the caller/UI and what a `feeInclusive: true` caller subtracts from the requested amount) is `0` (or omits this component). The two sides of the invariant diverge: `feeEstimation.amount = 0` but `total value leaving the user's balance beyond amount = nativeFee (wrap.near)`.

None of the existing guards catch this: `validateWithdrawal`'s `assert(feeEstimation.amount > 0n, ...)` is explicitly bypassed for `isPrefundedWithdrawal`, and there is no cross-check comparing `feeEstimation.amount` against the actually-generated `storage_deposit`/`nativeFee` amount before signing.

### Impact Explanation
A user withdrawing a `prefundedNativeFeeTokens`-listed token (e.g. `nep141:zec.omft.near`, a UTXO chain where `native_token_fee` is normally non-zero) is shown `feeEstimation.amount = 0` (or a value missing the relayer-fee component). If they use `feeInclusive: true`, the SDK does not deduct anything for this hidden cost from the requested withdrawal amount, yet the signed intent batch still contains a `storage_deposit` intent that debits `nativeFee` of wrap.near from the user's own intents balance. This is an uncompensated fee overcharge — NEAR silently leaves the user's balance beyond what was quoted and beyond `amount`, which matches the "fee overcharge... beyond the displayed fee" High-severity category. It is repeatable on every withdrawal of a prefunded token as long as the user holds sufficient wrap.near balance in the intents contract (if they don't, the withdrawal signature would still be produced but the storage_deposit could fail at execution time without refund, per the schema's own "NOTE: the wNEAR will not be refunded in case of fail").

### Likelihood Explanation
Preconditions: the integrator must have configured `prefundedNativeFeeTokens` to include the asset (an ordinary, expected integrator configuration, not a malicious escape hatch), and the Omni Bridge API must return `native_token_fee > 0` for that route (true for most non-subsidized tokens, including UTXO withdrawals like ZEC). No special attacker privilege is required beyond being a normal user calling `estimateWithdrawalFee`/`processWithdrawal` with `feeInclusive: true` on such a token — this is squarely within the "ordinary NEAR Intents user" threat model. It is deterministic and reproducible on every call, not a race condition.

### Recommendation
When a token is in `prefundedNativeFeeTokens`, either (a) also skip creating the `storage_deposit`/`nativeFee` charge (i.e., treat the token as truly fee-free, setting `nativeFee` to 0 for the withdrawal-intent derivation, consistent with `FEE_SUBSIDIZED_TOKENS`), or (b) if the `storage_deposit` debit is intentional, include `nativeFee` (or its NEAR-denominated value) in `feeEstimation.amount`/`underlyingFees` so the displayed fee equals the real total debited, and enforce this equality with an assertion before signing (e.g., compare `feeEstimation.amount + relayerFee-in-native-terms` against what `createWithdrawIntentsPrimitive` actually emits).

### Proof of Concept
Vitest plan (mock only `omniBridgeAPI.getFee`, no other HTTP):
1. Instantiate `OmniBridge` with `bridgeConfig: { prefundedNativeFeeTokens: ["nep141:zec.omft.near"] }`.
2. Mock `getFee` to return `{ native_token_fee: 1000000000000000000000n /* 0.001 NEAR */, gas_fee: null, protocol_fee: null, min_amount: null, insufficient_utxo: false }` and mock storage-balance helpers so `storageDepositFee = 0n`.
3. Call `estimateWithdrawalFee({ withdrawalParams: { assetId: "nep141:zec.omft.near", amount: 100000n, destinationAddress: "<valid zcash address>" } })`.
   - Assert `feeEstimation.amount === 0n` (or whatever value excludes the native fee) and `feeEstimation.underlyingFees[RouteEnum.OmniBridge].relayerFee === 1000000000000000000000n`.
4. Call `createWithdrawalIntents({ withdrawalParams: {...same, feeInclusive: true}, feeEstimation })`.
   - Assert the produced intents array contains a `storage_deposit` intent with `amount === "1000000000000000000000"`.
5. Assert the broken equality directly: `feeEstimation.amount (0n) !== relayerFeeAmountActuallyDebited (1000000000000000000000n)`, proving `feeEstimation.amount` does not equal the total value leaving the user's balance beyond `amount`.
