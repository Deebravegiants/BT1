### Title
Webhook shop domain and topic are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate` succeeds, then dispatches to a handler and builds `WebhookMetadata` using the request's `topic` and `shop` fields. However, the HMAC signature only ever covers the raw request body — never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that the gem (and its documentation) treats as trusted identity fields. An attacker who legitimately installs the app on their own low-value shop can capture one genuinely Shopify-signed webhook delivery and replay it to the app's webhook endpoint with a forged `shop-domain`/`topic` header, and the gem will still report the request as HMAC-valid.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e. the raw body in the webhook case: [3](#0-2) 

`Registry.process` uses the unauthenticated `request.topic` to select the handler and forwards the unauthenticated `request.shop` (plus `webhook_id`/`api_version`) into `WebhookMetadata`, which is exactly what the handler code is documented to trust: [4](#0-3) 

The gem's own documentation instructs host apps to key their business logic off `data.shop` and `data.topic` without any caveat that these are unauthenticated: [5](#0-4) 

The identity-binding equality that should hold is:
`shop/topic used to route and attribute the webhook == shop/topic verified by the HMAC`

In this gem, that equality never holds — the HMAC only proves "this body byte-string was produced with the shop's secret at some point in the past for some webhook," not "this body belongs to shop `X` and topic `Y`." An unprivileged party who installs the app on any shop they control receives genuine Shopify-signed webhook bodies for their own shop. They can then replay that same raw body + `hmac-sha256` header to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (e.g. a victim shop) and/or `x-shopify-topic` header. `HmacValidator.validate` still returns `true` because it never inspected those headers, and `Registry.process` will happily route the request to the handler registered for the forged topic, passing the forged shop domain through to the handler.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on (per this gem's own documented contract) to attribute webhook events to the correct merchant. An attacker with no credentials beyond a self-service app install can inject a "Shopify-verified" event that the host app will process under an arbitrary victim shop id, e.g. triggering `app/uninstalled` cleanup logic, GDPR data-request/erasure handlers, or any per-shop state update keyed by `data.shop`, for a shop they do not control. This is a cross-tenant confusion vulnerability enabled purely by this gem's verification logic.

### Likelihood Explanation
Likelihood is high for any app built on the documented pattern: capturing one legitimate webhook (from the attacker's own trial/dev shop) is trivial, no `api_secret_key`, access token, or victim credentials are required, and the replay only requires modifying two HTTP headers that the gem never validates.

### Recommendation
Include `shop-domain`, `topic`, `webhook-id`, and `api-version` in the signable string used for webhook HMAC validation (or otherwise cryptographically bind them to the body before computing/verifying the signature), so that `HmacValidator.validate` fails if any of these attribution fields are altered, matching the equality: fields trusted by the handler == fields covered by the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker-shop.myshopify.com` and registers for topic `orders/create`.
2. Shopify delivers a legitimately signed webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC over `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker resends the exact same body `B` and the same `x-shopify-hmac-sha256: H` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: app/uninstalled`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb#L13-31`) recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-200`) looks up the handler for the forged topic and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the host app to run victim-shop logic (e.g., delete stored victim data) triggered entirely by the attacker.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
