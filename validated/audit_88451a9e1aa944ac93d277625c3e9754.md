### Title
Webhook shop and topic headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches to the app's handler using the `shop` and `topic` values taken directly from unauthenticated HTTP headers. Because those identity-carrying fields are never included in the signed data, an attacker who can obtain any one genuinely-signed webhook body/HMAC pair (e.g., from a shop they themselves control) can replay it to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` and/or `shopify-topic` header. The HMAC check still passes, and the app's handler executes believing the event originated from, and pertains to, the spoofed shop/topic.

### Finding Description
The signable representation of a webhook request is defined as just the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the request: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against the `hmac` header: [3](#0-2) 

`Registry.process` performs this body-only check and then unconditionally trusts the header-derived `topic` and `shop` to select the handler and construct the metadata handed to app code: [4](#0-3) 

The identity binding that should hold is:
`shop/topic asserted in the processed event == shop/topic that actually produced the HMAC-signed bytes`

Because `to_signable_string` excludes `shop` and `topic`, this equality is never enforced. Any HMAC that is valid for a given body remains valid for that same body no matter what `shop-domain`/`topic` headers accompany it. An attacker who legitimately receives one valid `(body, hmac)` pair — trivially obtainable by installing the app on a shop they control and capturing a real webhook delivery — can resend that exact body/hmac to the app's public webhook endpoint with the `shop-domain` header changed to any victim shop and/or the `topic` header changed to any registered topic. `Registry.process` will accept it as authentic, look up the corresponding handler for the (now attacker-chosen) topic, and invoke it with `WebhookMetadata.shop` set to the (attacker-chosen) victim shop domain.

### Impact Explanation
This crosses the tenant boundary the webhook API is meant to enforce: an unprivileged party who only controls their own shop can cause the app to process forged events attributed to a different merchant's shop, or forged events under a different topic than what was actually signed (e.g., turning a low-sensitivity real event into a spoofed `shop/redact`, `app/uninstalled`, or other mandatory-compliance topic targeting a victim shop). Any host application that relies on `WebhookMetadata.shop`/`topic` — as the gem's own API documents and expects — to take shop-scoped action (deleting data, revoking access, updating billing state, etc.) can be manipulated into acting on the wrong tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no secrets, tokens, or privileged access — only the ability to install the app on an attacker-controlled shop (to harvest one legitimately signed body/HMAC pair) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers. Both are available to any unprivileged internet user/merchant, making this straightforward and repeatable.

### Recommendation
Bind `shop` and `topic` (and ideally `webhook_id`/`api_version`) into the HMAC-signable representation, or otherwise cryptographically authenticate them, so that a signature valid for one shop/topic cannot be replayed under a different one. At minimum, `Registry.process` should reject requests where the header-asserted shop does not match a shop the app has an active, expected installation/session for, rather than trusting `request.shop` purely from an unauthenticated header.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; capture a real webhook delivery, e.g. `orders/create`, recording the raw body `B` and its `x-shopify-hmac-sha256` header `H` (valid because `H = HMAC(secret, B)`).
2. Craft a POST to the app's webhook endpoint with:
   - body `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-topic: shop/redact` (or any topic registered by the app)
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and succeeds regardless of the spoofed `topic`/`shop` headers, per [1](#0-0)  and [3](#0-2) .
4. The app's registered handler for `shop/redact` is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, per [4](#0-3) , causing the app to act on the victim shop despite the event never having been produced by or for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
