### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw request body only. The shop identity (`shop-domain` header) that `ShopifyAPI::Webhooks::Registry.process` hands to the app's webhook handler is never included in the signed material, so a valid HMAC proves only "Shopify produced this body for *some* shop," not "this body belongs to the shop named in this header." An attacker who legitimately receives one Shopify-signed webhook (e.g., by installing the app on their own store) can replay that exact body to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header, and the gem will hand the attacker's payload to the app's handler labeled as belonging to the victim shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; the `shop` accessor is a completely separate, unsigned header read: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string`: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unsigned header) as the tenant identity passed to the app's handler: [5](#0-4) 

The documented, expected usage pattern for consumers of this gem is to key business logic off `data.shop` directly, exactly as shown in the gem's own docs: [6](#0-5) 

The identity binding that should hold is: `shop asserted in the WebhookMetadata handed to the app == shop that Shopify actually cryptographically vouched for`. Because the HMAC only covers `@raw_body`, this equality is never enforced by the gem — the `shop` value is taken from a header that travels completely outside the signed envelope.

### Impact Explanation
This breaks the cross-tenant isolation guarantee the gem is supposed to provide via `Utils::HmacValidator`/`Webhooks::Registry.process`: an app following the gem's documented API (`docs/usage/webhooks.md`) receives attacker-controlled body content tagged with an arbitrary, attacker-chosen shop identity, while `Registry.process` reports the webhook as HMAC-valid. Any app that uses `data.shop` to look up/update the corresponding merchant's records (the exact pattern the docs recommend) can have another merchant's data corrupted or overwritten by an attacker who merely operates their own store with the app installed — a cross-tenant access impact, without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
The only precondition is that the attacker installs the app on a store they control (a completely unprivileged, self-service action any internet user can perform) and captures one legitimate Shopify-signed webhook body for that store. They can then replay that identical body to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header naming any other shop. `Utils::HmacValidator.validate` will pass because the HMAC only ever covered the body, and `Registry.process` performs no additional check that the header's shop matches an already-authorized/installed shop for that webhook.

### Recommendation
Bind the shop identity into the material that is authenticated before it is trusted:
- Do not accept `request.shop` as authoritative for tenant routing based solely on `HmacValidator.validate(request)` succeeding; require the consuming app to cross-check the header shop against a shop that has an existing, previously-established OAuth session/access token (i.e., "is this shop known to us at all") before dispatching to a handler, and document this requirement prominently, or
- Have `Registry.process` require/accept a caller-supplied set of expected/authorized shop domains and reject processing when `request.shop` is not in that set, so a replayed body cannot be relabeled under an arbitrary shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures a webhook subscription (e.g., `products/update`) whose body they can influence (e.g., by editing a product title with malicious content).
2. Shopify sends the webhook to the app's endpoint with headers `X-Shopify-Hmac-Sha256: <hmac over body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures the raw body and its valid HMAC, then replays the exact same body/HMAC pair to the app's webhook endpoint again, this time supplying `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` using `to_signable_string == @raw_body`; the HMAC still matches because the body is unmodified.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, causing the app's handler to process attacker-controlled content as if it originated from the victim shop.
