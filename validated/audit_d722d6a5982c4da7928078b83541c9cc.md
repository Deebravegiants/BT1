### Title
Webhook `shop` (tenant identity) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the `shop-domain` HTTP header as the tenant identity handed to the app's handler. The `shop` field is never part of the HMAC-signed payload, so the equality the library implicitly assumes — "HMAC-authenticated request" == "request legitimately originating from `request.shop`" — does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes/compares the HMAC exclusively against that signable string (the body), never against headers: [2](#0-1) 

`Request#shop` is read directly, unauthenticated, from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [3](#0-2) 

`Registry.process` validates the HMAC of the body, then immediately forwards `request.shop` to the app's handler as the trusted tenant for that webhook, without the header ever having been covered by the signature check: [4](#0-3) 

Because Shopify computes the webhook HMAC using the app's `api_secret_key` — which is shared across every shop that installs the app, not per-shop — the same `(raw_body, hmac)` pair that Shopify legitimately sent for one shop's webhook remains a **valid** signature no matter what `shop-domain` header accompanies it. A user who installs the app on their own store receives a genuinely-signed webhook (any topic they can trigger, e.g. `orders/create` or `app/uninstalled`) with a valid `hmac`. They can then replay that exact body and hmac value directly to the app's public webhook endpoint while substituting an arbitrary victim shop's domain in the `shop-domain` header. `HmacValidator.validate` still returns `true` (it never inspected the header), and `Registry.process` passes the attacker-chosen `shop` value into `WebhookMetadata` as if Shopify itself asserted that identity.

This is the direct analog of the referenced Tigris finding: there, an unauthenticated default (`0x0` referral hash) was treated as an implicitly-trusted binding; here, an unauthenticated header (`shop-domain`) is treated as an implicitly-trusted tenant binding, while the actual cryptographic check only covers a field (`body`) that has no linkage to it.

### Impact Explanation
Any app built on this gem that keys per-tenant behavior off `WebhookMetadata#shop` (e.g., looking up/updating the victim shop's stored records, firing `shop/redact`-style side effects, or writing attacker-controlled body content attributed to the victim's shop) is exposed to cross-tenant webhook forgery: an attacker-controlled payload gets processed as if it were sent by a shop the attacker does not own. This matches the Critical "cross-tenant access" impact category, since the vulnerable identity binding (shop) is exactly the tenant boundary the app is meant to trust.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate but unprivileged merchant of the target app on their own store (no credentials, tokens, or `client_secret` needed) — they simply install the app, capture one webhook delivery's body+HMAC, and POST it to the app's public webhook endpoint with a forged `shop-domain` header. This is fully reachable through the gem's documented `Registry.process` API using only unauthenticated internet requests.

### Recommendation
Do not treat the `shop-domain` header as authenticated tenant identity on its own. Either bind the shop into the signed payload verification (e.g., require and verify against a per-shop secret or a previously-registered webhook shop/session), or require the app to independently confirm that `request.shop` corresponds to an existing, previously-authorized installation/session before acting on the payload, rather than relying on `HmacValidator.validate` (which only proves body integrity/authenticity of the *bytes*, not of the `shop` header) as an implicit tenant check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, a shop they legitimately control.
2. Shopify sends a real webhook, e.g. `POST /webhooks` with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac>`, and some JSON body `B`.
3. Attacker captures `B` and `<valid_hmac>`.
4. Attacker resends `POST /webhooks` to the same app endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: <valid_hmac>`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body fine (`lib/shopify_api/webhooks/request.rb:45-63`), `Utils::HmacValidator.validate` returns `true` because it only checked `B` against the shared `api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:13-22`), and `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:188-199`) even though Shopify never sent this webhook on behalf of `victim-shop`.
