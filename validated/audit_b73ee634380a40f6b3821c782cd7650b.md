## Title
Permissionless `CallDispatcher.dispatch()` combined with persistent approvals enables theft of tokens routed through the shared dispatcher (ERC-777/callback-token hook reentrancy) — (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a shared, singleton contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute arbitrary attacker-supplied `Call[]` batches "in its own context." Its `dispatch()` entrypoint has no access control, and multiple product flows transfer tokens directly into the dispatcher's custody *before* the calls that are supposed to consume/sweep them execute. This reproduces the exact bug class from the external report: arbitrary-call execution inside a shared execution context lets an attacker plant a persistent ERC-20 approval and/or an ERC-777 `tokensReceived` hook on the dispatcher, then drain tokens belonging to another user's in-flight order or bridge transfer.

### Finding Description
`CallDispatcher.dispatch()` decodes an ABI-encoded `Call[]` and executes each call `to.call{value: call.value}(call.data)` from the dispatcher's own address, with **no caller restriction whatsoever**: [1](#0-0) 

Any address — not just `IntentGatewayV2` or the HFT contracts — can invoke `dispatch()` directly and make the dispatcher execute:
- `IERC20(token).approve(attacker, type(uint256).max)`
- `IERC1820Registry.setInterfaceImplementer(address(this), TOKENS_RECIPIENT_HASH, attackerHookContract)` (registering the dispatcher itself for ERC-777 `tokensReceived` callbacks)

These effects persist in the dispatcher's storage/registry state across unrelated future transactions, because the dispatcher is a long-lived shared contract, not an ephemeral per-call proxy.

Multiple legitimate flows then move tokens *into* this same dispatcher before the flow's own calls run:
- `IntentGatewayV2.placeOrder` transfers `order.predispatch.assets` straight to `dispatcher` via `safeTransferFrom(msg.sender, dispatcher, amount)` before `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` is invoked: [2](#0-1) 
- `IntentsBase._execute` (postdispatch/fill path) dispatches `order.output.call` then sweeps whatever balance remains on the dispatcher back to the gateway: [3](#0-2) 
- `HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept` mint or unlock tokens to an arbitrary `to` address (documented pattern: set `to` to the `CallDispatcher` so bridged funds land there) and only afterward run `ICallDispatcher(_dispatcher).dispatch(message.data)`: [4](#0-3) 

If the token involved is ERC-777 (or any hook-bearing/callback token), the `_mint`/`transferFrom`/`transfer` call that lands funds on the dispatcher invokes the attacker-registered `tokensReceived` hook *mid-transaction*, before the victim's own predispatch/postdispatch calls or dust-sweep logic execute. Inside that hook the attacker's contract calls `token.transferFrom(dispatcher, attacker, amount)` using the allowance it pre-planted via a prior, completely independent call to the same permissionless `dispatch()`. This lets the attacker drain the victim's escrowed input tokens, bridged funds, or fill outputs before the protocol's own logic can consume or sweep them — the same "arbitrary call execution in shared context + ERC-777 hook" theft primitive described in the external report, but with the added defect that `dispatch()` itself is unauthenticated.

### Impact Explanation
This allows concrete theft of user funds routed through the shared `CallDispatcher`: order-input tokens escrowed via `placeOrder`'s predispatch path, solver-delivered output tokens swept via `_execute`, and bridged tokens minted/unlocked to the dispatcher by `HyperFungibleToken`/`WrappedHyperFungibleToken`. Because the dispatcher is shared across all consumers of the protocol, a single attacker-planted approval/hook can be reused to attack any subsequent user whose flow happens to route a compatible (hookable) token through the dispatcher. This meets the "concrete theft of funds" bar for reachable paths via an unprivileged intent solver/order-placer and token bridger.

### Likelihood Explanation
Exploitability depends on the involved token supporting a transfer hook (ERC-777, ERC-1363, or similar callback-token) or another reentrancy vector into the dispatcher's token-holding window; for plain non-hook ERC-20s the attack requires exact transaction ordering that isn't available mid-transaction. However, the root defect — a fully permissionless `dispatch()` on a persistent, shared contract that legitimate flows use as temporary custody — is present regardless of token type, and any pool/order/bridge configuration that permits hook-bearing tokens is directly exploitable. This is a realistic risk given the protocol explicitly documents routing arbitrary destination tokens (including third-party ERC-20/possibly ERC-777 compatible tokens) through the dispatcher.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., only `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` instances), removing the fully public entrypoint.
- Avoid using a single long-lived shared dispatcher instance for custody; deploy an ephemeral dispatcher (e.g., via `CREATE2`/minimal proxy) per call-batch so no approval or hook registration can outlive the single transaction it was created for.
- Additionally allowlist call targets/selectors reachable from `Call[]` (mirroring the report's recommendation for `GenericCrossChainFacet`), and explicitly reject ERC-777-style/hookable tokens in flows that stage funds on the dispatcher before executing dependent calls.

### Proof of Concept
1. Attacker calls `CallDispatcher.dispatch()` directly (no access control) with:
   - `Call{ to: victimToken, data: approve(attackerContract, type(uint256).max) }`
   - `Call{ to: ERC1820_REGISTRY, data: setInterfaceImplementer(address(CallDispatcher), TOKENS_RECIPIENT_INTERFACE_HASH, attackerHook) }`
2. A victim calls `IntentGatewayV2.placeOrder` with `order.predispatch.assets` denominated in `victimToken` (an ERC-777-compatible token); the gateway executes `IERC20(victimToken).safeTransferFrom(victim, dispatcher, amount)`.
3. The ERC-777 hook fires mid-transfer, invoking `attackerHook.tokensReceived(...)` in the dispatcher's context.
4. `attackerHook` calls `victimToken.transferFrom(dispatcher, attackerContract, amount)` using the approval from step 1, draining the victim's funds before `placeOrder`'s own `dispatch(order.predispatch.call)`/sweep logic runs.
5. `placeOrder` continues with an insufficient dispatcher balance, either reverting (griefing) or, depending on balance-diff accounting, recording an incorrect escrowed amount while the tokens are gone.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
