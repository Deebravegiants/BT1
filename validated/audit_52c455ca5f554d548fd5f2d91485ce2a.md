### Title
Webhook shop-tenant spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw request body, but the `shop` value used to dispatch the payload to the host application's handler is taken from an HTTP header that is never included in the signed content. This breaks the identity binding `shop authenticated == shop used as tenant key`, letting an attacker who legitimately installs the app on their own store replay a genuine, validly-signed webhook body while relabeling it as belonging to any other shop.

### Finding Description
`Webhooks::Registry.process` accepts a `Request` and validates it with: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` is defined to be **only the raw body**: [3](#0-2) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers that are **not part of the signed string at all**: [4](#0-3) 

The verified `request` is then dispatched to the registered handler carrying that unauthenticated `shop` value as the tenant identifier: [5](#0-4) 

Because a single app uses **one shared `api_secret_key` for HMAC across all shops** that install it, any attacker who installs the app on their own store (an ordinary, unprivileged action) will legitimately receive real Shopify webhooks with a valid `(body, hmac)` pair for their own shop. Since `shop` is not covered by the signature, that attacker can replay the same `body`/`hmac` to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop domain. `HmacValidator.validate` will still return `true` (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop: [5](#0-4) 

Any host application logic that trusts `data.shop` to select which tenant's records to create/update/delete (the intended and documented use of `WebhookMetadata#shop`) will act on the victim tenant using attacker-supplied body content — a cross-tenant data-integrity break achieved purely through this gem's own verification logic, without needing the app's secret, an access token, or any privileged access.

### Impact Explanation
This is a cross-tenant access/confusion vulnerability: an attacker with only an ordinary app installation on their own shop can cause the host application to process attacker-chosen webhook payloads as though they originated from a shop they do not control. Depending on how the host app's webhook handler uses `shop` (e.g., to look up which merchant's data to mutate), this can result in unauthorized cross-tenant writes or data corruption — satisfying the "Critical - cross-tenant access" impact bar without requiring `api_secret_key`, tokens, or privileged accounts.

### Likelihood Explanation
The prerequisite is trivial and available to any internet user: install the target app on a store they control (free, self-service on Shopify), capture one legitimate webhook `(body, hmac)` pair, and replay it against the app's public webhook endpoint with a forged shop-domain header. No secrets, tokens, or elevated access are required, and the gem's own `HmacValidator`/`Webhooks::Request`/`Registry.process` code path is exactly what performs this insufficient binding.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, or require the caller to independently verify that the `shop` header corresponds to a shop that has actually installed the app (e.g., cross-check against a known/stored session for that shop) before trusting `WebhookMetadata#shop`. At minimum, `Utils::HmacValidator.validate` should be documented as only proving body integrity, and `Webhooks::Registry.process`/`WebhookMetadata` should not be treated by callers as proof that the webhook belongs to the named shop unless that shop is cross-checked against a trusted store of installed shops.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook event (e.g., `orders/create`) that the app receives; captures the raw request body `B` and its `X-Shopify-Hmac-Sha256` header `H` (a genuine signature computed with the app's shared `client_secret`).
3. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body is unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic: orders/create`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` is only `B`.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and the host application processes attacker-controlled data as belonging to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
