### Title
Unbounded memory allocation from unauthenticated network length prefix in livestream `Upstream` - ([File: src/agents/livestream/upstream.rs])

### Summary
The `livestream` agent's `Upstream` component binds a TCP listener on `0.0.0.0:9201` and accepts any incoming connection without authentication. [1](#0-0)  Once connected, `EventReader::poll_stream` reads a 4-byte length prefix from the untrusted stream and immediately allocates a `Vec<u8>` of that exact size before any of the payload bytes have been validated or received. [2](#0-1)  This is the same bug class as the reported `EnclaveCall`/`visit_seq` issue: an attacker-controlled size value is used to pre-allocate a buffer with no upper bound, unlike `serde`'s `size_hint::cautious` pattern that caps allocations at 4096 bytes.

### Finding Description
`Upstream::new` opens a `TcpListener` on all interfaces (`0.0.0.0:{PORT}`), meaning any host that can reach the orb on port 9201 can connect without proof of identity. [3](#0-2)  For each connection, `EventReader::poll_stream` first reads exactly 4 bytes into `self.len`, then does:

```rust
if self.len_read == 4 {
    self.buf = vec![0; u32::from_be_bytes(self.len) as usize];
}
``` [4](#0-3) 

The value `u32::from_be_bytes(self.len)` is taken directly from the network with no upper-bound check, so a remote peer can request an allocation up to `u32::MAX` (~4 GiB) per connection simply by sending a 4-byte prefix, before ever having to supply the corresponding payload bytes. This mirrors the pattern criticized in the external report: `visit_seq` in `impl_sgx_wrapper_reqs` allocated `Vec::with_capacity(seq.size_hint())` based on an untrusted size hint with no bound, whereas `serde` caps this at 4096. Here the situation is worse because the "size hint" is not even a hint but an attacker-supplied exact allocation request, and repeated connections/requests can each trigger a fresh multi-gigabyte allocation.

After the buffer fills, it is deserialized via `rkyv::from_bytes` and fed into the `livestream` agent pipeline that drives on-orb GPU rendering. [5](#0-4) [6](#0-5) 

### Impact Explanation
An unauthenticated network peer able to reach port 9201 on the orb can repeatedly open TCP connections and send a 4-byte length header claiming a near-4 GiB payload, forcing the orb process to allocate large buffers it will never receive data for. Repeated or concurrent connections can exhaust available memory on the orb, causing the process (and with it in-progress or upcoming signups, biometric capture, and other orb-core functionality sharing the same address space) to crash or become unresponsive — a denial-of-service condition analogous to the memory-exhaustion impact described in the report.

### Likelihood Explanation
Likelihood is moderate to high wherever the `livestream` feature is enabled and the port is reachable: the listener binds `0.0.0.0` and performs no authentication or handshake before allocating memory based on client-supplied length, so exploitation requires only network access and a trivial 4-byte payload. [7](#0-6) 

### Recommendation
Bound the size of the allocation derived from the untrusted length prefix (e.g., cap it to a small sane maximum consistent with expected livestream event message sizes, similar to `serde`'s `size_hint::cautious`), and/or allocate incrementally (grow the buffer as bytes actually arrive rather than pre-allocating the full claimed size up front) in `EventReader::poll_stream`. [4](#0-3)  Additionally, require authentication/authorization before accepting data on this listener, since it currently accepts any TCP client on all interfaces. [3](#0-2) 

### Proof of Concept
1. Ensure the `livestream` feature is enabled and the orb process is running with the livestream agent active (listener on `0.0.0.0:9201`).
2. From any host that can reach the orb, open a TCP connection to port 9201.
3. Send a 4-byte big-endian value of `0xFFFFFFFF` (or another very large value) and then stop sending further data.
4. Observe that `EventReader::poll_stream` executes `self.buf = vec![0; u32::from_be_bytes(self.len) as usize];`, allocating close to 4 GiB of memory for that single connection. [4](#0-3) 
5. Repeat with multiple concurrent connections to amplify memory pressure and induce process termination or system-wide memory exhaustion.
