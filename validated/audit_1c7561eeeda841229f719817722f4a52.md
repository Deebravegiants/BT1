### Title
Attacker-controlled swap venue can piggyback a victim’s authorization to steal unrelated wallet tokens - (contracts/controller/src/strategies/swap.rs)

### Summary
A malicious venue address embedded in a `StrategySwap` can invoke `token.transfer(victim, attacker, amount)` while it is executing beneath a victim-signed controller strategy call. Soroban records that nested token transfer under the victim’s authorization tree; if the victim signs the simulated tree, the arbitrary transfer succeeds independently of the routed amount. The controller only bounds the controller’s own input transfer and measured output, not additional children authorized under the victim’s `require_auth` invocation. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` accepts a caller-selected `swap: StrategySwap`, requires only caller authorization and account ownership or delegation, then routes the withdrawn collateral through `withdraw_and_swap_from_supply`. [3](#0-2) 

`swap_tokens` snapshots the controller’s input and output balances, authorizes exactly one controller-to-router input transfer, and calls the configured router with the caller-controlled `swap` payload. [4](#0-3)  These checks only bound `actual_spent`, refund unused input, and require a positive measured output; they do not constrain other contract calls or token transfers performed by the route’s venue while the victim’s authorization context is active. [5](#0-4) 

A harness model demonstrates the behavior: a route-selected pool calls `token.transfer(victim, attacker, amount)` for a token unrelated to the lending markets. Simulation records that transfer as a child of the victim’s `swap_collateral` authorization, and enforcing mode executes it when that simulated tree is signed. [6](#0-5) [7](#0-6) 

### Impact Explanation
The attacker can steal any token balance that the victim authorizes through the poisoned simulation tree, including assets that are not listed by XOXNO Lending and are unrelated to the strategy’s input or output. [8](#0-7) 

The theft is not limited to the collateral being swapped. A malicious venue can return a valid output so the controller’s balance-delta, overspend, and final account-risk checks all pass while the unrelated wallet transfer has already executed. [5](#0-4) 

### Likelihood Explanation
The victim must submit or sign a transaction containing the malicious route and the additional authorization child. This is feasible when users consume attacker-provided routes or sign simulated authorization trees without decoding every nested invocation, but it is not fully unilateral because the victim’s signature is required. [9](#0-8) 

The same authorization-tree exposure applies to controller strategies that accept caller-selected route payloads, including `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral`. [10](#0-9) 

### Recommendation
Constrain route execution so route-selected code cannot add a victim-address child authorization beneath the controller call. At minimum, controller clients and any official integrator SDK must present the complete simulated authorization tree for explicit approval and reject children other than the expected strategy token movement. For stronger protocol-level mitigation, isolate route execution behind a contract-held sender context that cannot inherit a user’s `require_auth` authorization tree, or restrict route venues to reviewed contracts whose venue entrypoints cannot perform unrelated `require_auth` calls.

### Proof of Concept
1. Alice owns a lending account with USDC collateral and holds an unrelated `WALLET` token.
2. The attacker deploys a venue contract implementing the pool interface expected by the selected route. Its venue handler calls:
   ```rust
   token::Client::new(&env, &wallet_token).transfer(&alice, &attacker, &amount);
   ```
   while still returning enough output for the swap to pass the controller checks.
3. The attacker supplies a `StrategySwap` route naming that venue.
4. Alice calls:
   ```text
   controller.swap_collateral(
       caller = alice,
       account_id = alice_account,
       current = usdc_hub_asset,
       from_amount = swap_amount,
       new = eth_hub_asset,
       swap = malicious_route,
   )
   ```
5. Simulation records the unrelated `WALLET.transfer(alice -> attacker)` as a child under Alice’s `swap_collateral` authorization.
6. If Alice signs that returned tree, the venue steals `WALLET`; the router can still deliver the declared `ETH` output, leaving Alice’s final position valid.

The repository’s focused test demonstrates the authorization mechanism: recording mode places the unrelated transfer under the caller’s `swap_collateral` entry, and enforcing mode executes it only when that child is present in the signed tree. [2](#0-1) [11](#0-10)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
