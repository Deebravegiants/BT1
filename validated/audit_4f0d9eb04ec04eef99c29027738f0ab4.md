Based on my investigation, I found where nearcore's runtime translates an invariant/consistency failure detected while applying a chunk into a hard node panic, rather than handling it gracefully. This is the closest analog to the Cosmos SDK `x/crisis` issue, but with the opposite (and more severe) characteristic: instead of *failing to halt*, an unprivileged, attacker-triggerable condition causes the validator/node process itself to crash (`panic!`), which is a concrete, reachable DoS.

### Title
Chunk-apply invariant failures triggered by attacker-supplied receipts cause node panic (chain halt) - (File: `chain/chain/src/runtime/mod.rs`)

### Summary
`RuntimeShardHost::apply_chunk` converts several `RuntimeError`/`Error` cases returned from `Runtime::apply`/`process_state_update` directly into `panic!`, instead of returning a recoverable error. Because these errors (`RuntimeError::UnexpectedIntegerOverflow`, `RuntimeError::ReceiptValidationError`, and generic `StorageError` other than the two allow-listed variants) can be produced deep inside receipt/action processing while executing an ordinary incoming receipt that ultimately originates from a submitted transaction, a specially crafted transaction can crash every node that applies the resulting chunk.

### Finding Description
`chain/chain/src/runtime/mod.rs` maps errors from `self.runtime.apply(...)` as: [1](#0-0) 
- `RuntimeError::UnexpectedIntegerOverflow(reason) => panic!(...)`
- `RuntimeError::ReceiptValidationError(e) => panic!(...)`

and separately, `apply_chunk` maps any `Error::StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue` to `panic!`: [2](#0-1) 

These are marked `// TODO(#2152): process gracefully` in the code, i.e., the developers themselves acknowledge these are not meant to be permanent unrecoverable aborts. `UnexpectedIntegerOverflow` is produced widely throughout `runtime/runtime/src/lib.rs` (e.g., in `update_validator_accounts`, gas/balance arithmetic in receipt processing) — several of these overflow paths are reachable from ordinary receipt/action execution, not just validator-only bookkeeping. [3](#0-2) 

Likewise, `StorageError::StorageInconsistentState` invariant violations (e.g. the staking invariant check) are converted to a hard `panic!` rather than being handled as a recoverable/logged condition: [4](#0-3) 

This mirrors the reported Cosmos SDK `x/crisis` bug class exactly: an invariant/consistency check failure encountered while processing a transaction-derived state transition results in the network being unable to make progress — in nearcore's case via an outright crash (`panic!`) of every node applying the chunk, rather than Cosmos's silent "does not halt" failure mode. Both stem from the same root design flaw: treating rare invariant violations as fatal, chain-affecting events instead of contained, gracefully-handled errors.

### Impact Explanation
If an attacker can construct a transaction/receipt (through parameters that are attacker-controlled, e.g. crafted balances, gas, or stake values feeding into checked-arithmetic sequences, or a malformed receipt that fails post-hoc validation via `ReceiptValidationError` after being accepted by an earlier code path) that reaches one of these `panic!` sites during `apply_chunk`, every validator/RPC node tracking that shard will crash processing that chunk. Since `apply_chunk` runs identically on every node validating/tracking the shard, this is a deterministic, network-wide chain-halting DoS — arguably more severe than the Cosmos report, which only describes the chain failing to *proactively* halt (not a live crash of running nodes).

### Likelihood Explanation
Moderate: reaching most of these panics requires finding a specific combination of balances/gas/stake parameters or receipt shapes that slip past earlier stateless validation (`validate_transaction`, `verify_and_charge_*_ephemeral`, `validate_receipt`) but still trip an arithmetic overflow or invariant check deeper in `apply_action_receipt`/`update_validator_accounts`. This requires code-level analysis of the exact arithmetic/validation gaps, similar to the "moderate... requires specific knowledge" likelihood rating given in the original report.

### Recommendation
Replace the `panic!` calls at `chain/chain/src/runtime/mod.rs:367`, `:371`, and `:1285` with graceful error propagation (return `Error::StorageError`/a new dedicated error variant) that causes the specific chunk/transaction to be rejected or the shard state to be marked for investigation, without crashing the node process. At minimum, follow the existing `TODO(#2152)` to implement graceful handling, and audit all checked-arithmetic call sites feeding `RuntimeError::UnexpectedIntegerOverflow` to ensure attacker-controlled inputs cannot reach them.

### Proof of Concept
A concrete end-to-end PoC (a specific transaction payload that reaches one of these overflow/invariant panics) could not be fully constructed from the available indexed code — the exact reachable overflow site and the missing bounds check would need deeper tracing through `apply_action_receipt`/`apply_action` (`runtime/runtime/src/lib.rs:776`, `:523`) and the various `checked_add`/`checked_sub` sites for a specific attacker-controlled value that both passes stateless `validate_transaction`/`verify_and_charge_*_ephemeral` and later overflows or fails `validate_receipt`. This would require a live Devin session with full-repo access to trace and construct/test such a payload.

    fn update_validator_accounts(
        &self,
        state_update: &mut TrieUpdate,
        validator_accounts_update: &ValidatorAccountsUpdate,
    ) -> Result<(), RuntimeError> {
        for (account_id, max_of_stakes) in &validator_accounts_update.stake_info {
            if let Some(mut account) = get_account(state_update, account_id)? {
                if let Some(reward) = validator_accounts_update.validator_rewards.get(account_id) {
                    tracing::debug!(target: "runtime", %account_id, %reward, locked = %account.locked(), "account adding reward to stake");
                    let locked = account.locked().checked_add(*reward).ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow("update_validator_accounts".into())
                    })?;
                    account.set_locked(locked).or_inconsistent_state(account_id)?;
                }

                tracing::debug!(target: "runtime",
                       %account_id, locked = %account.locked(), %max_of_stakes,
                       "account stake and max of stakes"
                );
                if account.locked() < *max_of_stakes {
                    return Err(StorageError::StorageInconsistentState(format!(
                        "FATAL: staking invariant does not hold. \
                         Account stake {} is less than maximum of stakes {} in the past three epochs",
                        account.locked(),
                        max_of_stakes)).into());
                }
                let last_proposal = *validator_accounts_update
                    .last_proposals
                    .get(account_id)
                    .unwrap_or(&Balance::ZERO);
                let return_stake = account
                    .locked()
                    .checked_sub(max(*max_of_stakes, last_proposal))
                    .ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - return stake".into(),
                        )
                    })?;
                tracing::debug!(target: "runtime", %account_id, %return_stake, "account return stake");
                let locked = account.locked().checked_sub(return_stake).ok_or_else(|| {
                    RuntimeError::UnexpectedIntegerOverflow(
                        "update_validator_accounts - set_locked".into(),
                    )
                })?;
                account.set_locked(locked).or_inconsistent_state(account_id)?;
                account.set_amount(account.amount().checked_add(return_stake).ok_or_else(
                    || {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - set_amount".into(),
                        )
                    },
                )?);
