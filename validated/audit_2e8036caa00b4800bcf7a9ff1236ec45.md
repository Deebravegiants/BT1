### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` used for tenant routing from the `X-Shopify-Shop-Domain` header, but `to_signable_string` — the value that `HmacValidator` authenticates — is only the raw request body. The `shop` field is therefore never bound to the HMAC that `Registry.process` checks before dispatching to the host app's handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only, and `Request#shop` is read straight from an unauthenticated header: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely against `verifiable_query.to_signable_string` (i.e., the body), never mixing in the `shop` header: [2](#0-1) 

`Registry.process` accepts the request once that body-only HMAC check passes, then forwards the *header-derived* `shop` value straight to the app's webhook handler as the tenant identifier: [3](#0-2) 

This breaks the identity binding `shop authenticated by HMAC == shop used as tenant key`. Concretely: `hmac == HMAC(body)`, but the tenant-selecting value is `request.shop = header["x-shopify-shop-domain"]`, which is disjoint from what was signed. Because the client secret used to compute the webhook HMAC (`Context.api_secret_key`) is a single app-level secret shared across *every* merchant who installs the app — not a per-shop secret — any merchant who receives a legitimate webhook for their own shop possesses a raw body + valid HMAC pair that remains cryptographically valid for the app's shared secret regardless of which shop domain is asserted. That merchant can therefore replay the exact same `raw_body`/`hmac-sha256` pair while substituting a different `X-Shopify-Shop-Domain` header value, and `Utils::HmacValidator.validate` will still return `true` because the header is never part of `to_signable_string`.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (populated directly from `request.shop`) to select which merchant's session/tenant record the webhook body should be applied to — the documented and expected pattern for a per-shop webhook handler — an attacker who is a legitimate installer of the app for Shop A can forge a webhook that the gem validates as authentic for Shop B, causing cross-tenant data to be attributed to the wrong shop. This is a cross-tenant boundary crossing achieved purely by an app-installing merchant (not requiring `api_secret_key`, an access token, or any privileged account), matching the report's underlying bug class (a field acted upon — the shop identity — that is not covered by the integrity check) applied to this gem's own webhook verification path rather than the BGT/staking scenario in the source report.

### Likelihood Explanation
Medium. It requires the attacker to be, or control, at least one shop that has installed the target app (to obtain one valid raw_body/HMAC pair signed with the app's shared secret), and it requires the host application to trust `request.shop` for tenant selection without independently cross-checking shop identity embedded in the payload — which is exactly the API surface this gem exposes (`WebhookMetadata.shop`), so most integrations using the documented `Registry.process` flow are exposed.

### Recommendation
Bind the shop domain into the value that is HMAC-verified, or otherwise require callers to cross-check `request.shop` against a shop id/domain embedded in the parsed body (where available) before trusting it for tenant routing. At minimum, document that `request.shop` is unauthenticated header data and must not be used as a sole tenant key without additional verification, and consider having `Utils::HmacValidator` include the shop-domain header as part of `to_signable_string` for `Webhooks::Request`, or reject/flag mismatches between `shop` header and previously-known shop-to-secret bindings when per-shop secrets are configurable.

### Proof of Concept
1. Merchant M installs the target app on `shop-m.myshopify.com`; the app's shared `Context.api_secret_key` is used by Shopify to sign all webhooks for the app, for every installed shop.
2. Shopify sends M a legitimate webhook: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`, header `X-Shopify-Shop-Domain: shop-m.myshopify.com`.
3. M replays the exact same `B` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` — identical to the original — and returns `true` per `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` proceeds and calls the host handler with `WebhookMetadata.new(... shop: "shop-victim.myshopify.com" ...)` per `lib/shopify_api/webhooks/registry.rb:198-199`, causing the app to process M's forged data as if it originated from `shop-victim`.
