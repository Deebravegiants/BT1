### Title
Webhook `shop` identity is never covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch and attribute the webhook are read from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then trusts `request.shop` as the tenant identity forwarded to the app's handler, without that value ever being part of the signed material.

### Finding Description
`HmacValidator.validate` verifies a `VerifiableQuery` by computing an HMAC over `to_signable_string` and comparing it to the supplied `hmac`. [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from attacker-controllable HTTP headers, completely outside the signed payload: [3](#0-2) [4](#0-3) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before handing `request.shop` (and `request.topic`, `request.webhook_id`) straight to the host application's handler as the trusted tenant/event identity: [5](#0-4) 

The resulting `WebhookMetadata.shop` is exactly the field host applications are documented to rely on to determine which merchant/tenant the payload belongs to: [6](#0-5) 

This breaks the intended binding: `shop header value == shop that produced/authorized the signed body`. Because the header is not part of the signed bytes, the equality the gem is supposed to enforce (`hmac verifies (body, shop)` ⇒ `shop is authentic`) actually only holds for `hmac verifies (body)`; `shop` is unauthenticated free text.

### Impact Explanation
Any unprivileged internet user who can obtain one legitimate webhook delivery from Shopify — trivially available by installing/registering the app on their own store, including a free development store — captures a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's `client_secret`/`api_secret_key`. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g., a victim merchant's domain). `HmacValidator.validate` still succeeds because it only checks the untouched body bytes, and `Registry.process` forwards `WebhookMetadata.shop` = attacker-chosen domain to the host app's handler together with the attacker's own (but validly-signed) body content. Any host application that uses `data.shop` to select the tenant record to update (a documented, expected usage pattern) will attribute attacker-supplied data to a different merchant's tenant — a cross-tenant data injection / identity-confusion issue rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation, not in host misuse of an undocumented API.

### Likelihood Explanation
Requires only: (1) ability to receive one genuine webhook from Shopify to any store the attacker controls (free to obtain), and (2) ability to send an HTTP POST with attacker-chosen headers to the target app's public webhook endpoint (webhook endpoints are, by design, unauthenticated public endpoints). No access token, `client_secret`, or privileged account is needed. This is a low-effort, reliably reproducible attack path once a webhook sample has been captured.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) in the signed material verified against the app's own registered/expected shop list, or otherwise bind the header-derived `shop` value to the signature — e.g., independently validate that the `shop-domain` header matches a shop known to have this webhook `webhook_id`/subscription registered before trusting it, rather than relying on HMAC validity of the body alone as proof of the shop's identity. At minimum, document prominently that `WebhookMetadata#shop` is NOT authenticated by the HMAC check and must be independently verified by the host application against its own tenant list before use.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store "attacker.myshopify.com"
#    and triggers a real webhook (e.g. orders/create). Shopify sends:
#      body: '{"id":1,"note":"hello"}'
#      headers: {
#        "x-shopify-hmac-sha256" => "<valid-hmac-for-body>",
#        "x-shopify-shop-domain" => "attacker.myshopify.com",
#        "x-shopify-topic" => "orders/create",
#        ...
#      }
#    Attacker captures body + hmac header (still valid, unchanged).

# 2. Attacker replays the exact same body+hmac to the app's public
#    webhook endpoint, but swaps the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<valid-hmac-for-body>",   # unchanged, still verifies
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id":1,"note":"hello"}', headers: headers)

# 3. HMAC check passes because it only verifies the (unchanged) body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches to the handler with
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>1,"note"=>"hello"}, ...)
#    even though the payload actually originated from the attacker's own store.
ShopifyAPI::Webhooks::Registry.process(request)
```
