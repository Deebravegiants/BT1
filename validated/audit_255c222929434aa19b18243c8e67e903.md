### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `api-version`, and `webhook_id` fields — all of which are trusted and handed to the host application's webhook handler — are read directly from unauthenticated HTTP headers. This breaks the equality that should hold between "bytes verified by HMAC" and "bytes the application acts on to identify the tenant."

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively against that signable string [2](#0-1) . However, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never included in the signed payload [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` to dispatch to the registered handler, constructing a `WebhookMetadata` object with the unauthenticated `request.shop` value [4](#0-3) .

This means: `HMAC-verified(body)` ≠ `shop identity acted on (header)`. An attacker who can obtain any single valid `(body, hmac)` pair signed by the app's client secret for shop A (e.g., a webhook payload the attacker's own store received, or any leaked/replayed body+HMAC pair) can resend that exact body/HMAC combination to the app's webhook endpoint while substituting the `shopify-shop-domain` header for shop B. The HMAC validation in `HmacValidator.validate` will still pass because it never inspects the header, yet the host application will process the request as if it originated from shop B.

### Impact Explanation
This is a cross-tenant confusion vector: the webhook consumer (host application built on this gem) is told — via a value the gem asserts to be authentic ("HMAC verified this request") — that a payload belongs to a shop it does not belong to. Any host logic that keys off `WebhookMetadata#shop` (e.g., looking up the session/access token for the named shop, applying the payload to that shop's local records) can be tricked into associating attacker-controlled or cross-store data with a victim shop, since the gem provides no binding between the verified bytes and the shop identifier it exposes as trustworthy.

### Likelihood Explanation
The attacker needs at least one valid `(raw_body, hmac)` pair produced by the app's own secret — obtainable simply by being a merchant/store owner who has installed the app and thus legitimately receives webhooks for their own shop, or a webhook payload with a body that doesn't itself change (e.g., a shop-independent value). No access to `client_secret`, `api_secret_key`, or any privileged credential is required. Because `Registry.process` only checks `Utils::HmacValidator.validate(request)` [5](#0-4)  and never re-derives or verifies the `shop-domain` header against the signed content, exploitation only requires forging/replaying HTTP headers on an otherwise-valid signed body.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api-version`) header values in the string that is HMAC-verified (`to_signable_string`), or otherwise cryptographically bind them to the body before dispatch, so that `HmacValidator.validate` fails if any of these header values are altered relative to what Shopify originally signed.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `{}` and header `shopify-hmac-sha256: <valid HMAC of "{}">`.
2. Attacker (who owns/controls `shop-a` and thus legitimately received this webhook) resends the exact same body and HMAC header to the app's webhook endpoint, but changes `shopify-shop-domain` to `shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb#L13-L22` recomputes the HMAC over `to_signable_string` (`@raw_body` only) and it matches, so validation succeeds.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb#L188-L200` dispatches to the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now returns `"shop-b.myshopify.com"` — a value never covered by the HMAC — even though the signed payload was never sent by or for shop B.
