### Title
`findMatchingWithdrawal` misattributes withdrawal status/txHash across same-asset batch withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status for a specific `WithdrawalIdentifier` by calling `findMatchingWithdrawal`, which selects the **first** entry in the bridge's response whose `nep141:${near_token_id}` equals `args.withdrawalParams.assetId`. When a single `processWithdrawal` batch contains two withdrawals of the same `assetId` to different `destinationAddress`es, both `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` query the same `withdrawal_hash` (the batch tx hash), receive the same withdrawal list, and both resolve to the identical first match — so index 1's true `COMPLETED`/`txHash` can be reported for index 0 (or vice versa).

### Finding Description
The broken equality: `(status, txHash) reported for describeWithdrawal(index=i)` should equal `outcome of withdrawal i`. Instead, both `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` call `getWithdrawalStatusWithRetry` with `{ withdrawal_hash: args.tx.hash }` [1](#0-0) . For withdrawals originating from the same batch transaction, `args.tx.hash` is identical for both indices, so the HTTP response `response.withdrawals` is the same list for both calls.

`findMatchingWithdrawal` then does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [2](#0-1) , matching purely on `assetId`, with no use of `index`, `destinationAddress`, or `amount` to disambiguate. Because `Array.prototype.find` always returns the first matching element, calling this function with the same `withdrawals` array and same `assetId` for index 0 and index 1 returns the exact same record both times.

The code's own comment acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported" and that the POA API doesn't support this case either [3](#0-2) . `describeWithdrawal` passes this record straight through without any check against `index`, `destinationAddress`, or `amount` before returning `{ status: "completed", txHash: withdrawal.data.transfer_tx_hash }` [4](#0-3) .

No existing guard (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()`) runs in this read path — those only run at withdrawal-creation time, not at status-lookup time — so nothing prevents the divergence.

Attacker's exact input: an ordinary user (or integrator on their behalf) submits a single `processWithdrawal`/batch call with two withdrawal legs for the same `assetId` (e.g. `nep141:usdc.omft.near`) to two different `destinationAddress` values. No special privilege is needed — this is a normal same-token multi-recipient withdrawal batch, a supported, unprivileged usage pattern.

### Impact Explanation
An integrator that tracks completion per-index (e.g., to credit or refund a specific user) can receive withdrawal j's `txHash`/`COMPLETED` status for withdrawal i's lookup. This can cause the integrator to mark User A's transfer as completed using User B's transaction hash, or refund/credit the wrong destination address, while the real state of each individual withdrawal is misreported. This matches the "status or hash misreport making an integrator credit or refund twice/wrongly" High-severity category, and is repeatable for every batch that mixes same-asset multi-destination withdrawals as long as the bridge/API returns multiple records under one `withdrawal_hash`.

### Likelihood Explanation
Preconditions: the integrator (or the withdrawing user) must construct a batch containing ≥2 withdrawals of the same `assetId` with different destinations within one NEAR transaction — a normal, permissionless usage pattern requiring no elevated privilege, just ordinary funds/keys. The attacker's cost is a single transaction; the divergence occurs automatically whenever an integrator later calls `describeWithdrawal` per index for such a batch, so it is fully repeatable, not fees-related, and doesn't require timing races — it is deterministic given the array-based `.find()` and identical batch `tx.hash`.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId`, e.g. by also matching on `destinationAddress` and/or sorting both the API response and the local withdrawal params by `amount` (as the code comment suggests) before pairing them by position, or by requesting/using a withdrawal-specific identifier from the POA API if available. At minimum, `describeWithdrawal` should refuse to report a definitive status when multiple withdrawals in the response share the same `assetId`, rather than silently returning the first match.

### Proof of Concept
```ts
// vitest, mocking only poaBridge.httpClient.getWithdrawalStatus
import { describe, it, expect, vi } from "vitest";
import { poaBridge } from "@defuse-protocol/internal-utils";
import { PoaBridge } from "../poa-bridge";

it("misattributes status across same-assetId batch withdrawals", async () => {
  const sameTxHash = "batch-tx-hash";
  const withdrawals = [
    { status: "COMPLETED", data: { near_token_id: "usdc.omft.near", transfer_tx_hash: "tx-for-user-A", address: "addressA" } },
    { status: "COMPLETED", data: { near_token_id: "usdc.omft.near", transfer_tx_hash: "tx-for-user-B", address: "addressB" } },
  ];
  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({ withdrawals });

  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  const idA = bridge.createWithdrawalIdentifier({
    withdrawalParams: { assetId: "nep141:usdc.omft.near", destinationAddress: "addressA", amount: 100n } as any,
    index: 0,
    tx: { hash: sameTxHash } as any,
  });
  const idB = bridge.createWithdrawalIdentifier({
    withdrawalParams: { assetId: "nep141:usdc.omft.near", destinationAddress: "addressB", amount: 200n } as any,
    index: 1,
    tx: { hash: sameTxHash } as any,
  });

  const resultA = await bridge.describeWithdrawal(idA);
  const resultB = await bridge.describeWithdrawal(idB);

  // Broken equality demonstrated: both resolve to the SAME record (index 0's),
  // rather than resultA -> "tx-for-user-A" and resultB -> "tx-for-user-B".
  expect(resultA).toEqual({ status: "completed", txHash: "tx-for-user-A" });
  expect(resultB).toEqual({ status: "completed", txHash: "tx-for-user-A" }); // should be "tx-for-user-B" but isn't
});
```

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
