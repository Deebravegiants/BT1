### Title
Free "Emporium-min" proof lets anyone drain pooled Emporium funds via unrestricted `op.endpoint.call` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`Hinkal.transact` accepts a "minimal" public-input path for the Emporium external action whenever `circomData.erc20TokenAddresses.length == 0` [1](#0-0) , which routes proof verification through `MainEVMCircuitMin`, a circuit that only proves knowledge of a Poseidon preimage and does not constrain any UTXO ownership, nullifier spend, or token balance at all [2](#0-1) . Because `erc20TokenAddresses` is empty, `EmporiumUpgradeable.runAction`'s before/after balance-accounting loop never executes (it iterates over `circomData.erc20TokenAddresses`) [3](#0-2) [4](#0-3) , yet `stack.ops` is still executed with completely unrestricted `endpoint`/`callData`/`value` in the "stateless" branch, blocking only two specific selectors [5](#0-4) . This mirrors the reported bug class (a raw, unfiltered "request"/action forwarded to an external target with no validation of path/method/payload) but here the analog is an unauthenticated arbitrary external call executed from the Emporium contract's own context/balance.

### Finding Description
`formInputForCircom` chooses `formInputEmporiumMin` when the external action is the Emporium action and no ERC20 tokens are declared [6](#0-5) . The resulting public-input vector for the ZK proof is only `[emporiumMessage, timeStamp, calldataHash]`, and the underlying circuit `MainEVMCircuitMin` computes `message <== Poseidon(1)([messageSeed])` from a self-chosen private `messageSeed` with no linkage to any spendable UTXO, nullifier, or balance [2](#0-1) . Any party can therefore construct a trivially valid proof for this circuit without controlling or spending any real shielded value.

`Hinkal.transact` verifies this proof and a Merkle root inclusion check (`rootHashExists`) that is independent of `dimensions`/token count, then dispatches to `_externalTransact`, which calls `IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges)` [7](#0-6) [8](#0-7) . Inside `EmporiumUpgradeable.runAction`, an attacker-controlled `EmporiumStack` (decoded straight from `externalActionData.externalActionMetadata`, an opaque bytes blob only integrity-checked via `calldataHash`, never semantically validated by the circuit) is executed op-by-op [9](#0-8) . When `signerAddress == address(0)` (no EIP-712 signature required — `verifyWallet` just returns early) [10](#0-9) , each op runs as `op.endpoint.call{value: op.value}(op.callData)` with the Emporium contract as `msg.sender`, restricted only against two specific function selectors [5](#0-4) .

Because `circomData.erc20TokenAddresses` is empty in this path, the pre/post balance-diff safety loop that would normally revert on unexpected balance loss (`BalanceChangeShouldBePositive`) never runs at all [11](#0-10) . An attacker can therefore call `IERC20(anyTokenHeldByEmporium).transfer(attacker, fullBalance)` (or drain native ETH) directly, with zero real proof of ownership and zero balance-equation enforcement.

This breaks the equality the protocol relies on: real value moved out of the Emporium contract is never reflected in, or checked against, the balance/UTXO equation for that transaction (`erc20TokenAddresses` / `amountChanges` / nullifiers are all empty), and the "proof" backing the action carries no actual spend authorization.

### Impact Explanation
Critical — this allows unauthenticated, unbacked theft of all pooled ERC20/ETH balances held by the `EmporiumUpgradeable` contract (funds belonging to other users awaiting multi-step Emporium operations), with no valid ZK proof of ownership, no EIP-712 signer authorization, and no balance-equation check to catch the loss.

### Likelihood Explanation
High/Medium — exploitation only requires: (1) generating a proof for the public `MainEVMCircuitMin` circuit, which needs no secret/private user data (any `messageSeed` works), (2) supplying an already-existing Merkle root (e.g., the initial/empty root, which trivially exists), and (3) crafting an `EmporiumStack` with `signerAddress = address(0)` and one malicious op. No admin, relayer, or victim cooperation is needed.

### Recommendation
- Do not allow the zero-token "Emporium-min" circuit/public-input path to authorize arbitrary `stack.ops` execution; require `signerAddress != address(0)` (i.e., a valid EIP-712 signature covering the exact `ops`) whenever any external call is being made, regardless of `erc20TokenAddresses.length`.
- Constrain `op.endpoint` to an allow-list (or to addresses present in `circomData.erc20TokenAddresses`) and forbid arbitrary calldata to arbitrary targets in the "stateless" branch.
- Ensure the balance-accounting safety check in `runAction` cannot be bypassed by declaring an empty `erc20TokenAddresses` array — e.g., always verify the Emporium contract's aggregate balance invariant regardless of which/whether tokens were declared, or disallow calling `runAction` with an empty token set when `stack.ops` is non-empty.

### Proof of Concept
1. Off-chain, compile/use the existing `MainEVMCircuitMin` proving key and generate a proof with a self-chosen `messageSeed`; set `outTimeStamp` and `calldataHash` to match a crafted `CircomData` (no real UTXOs needed).
2. Build `CircomData` with: `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `rootHashHinkal` = a known-existing root (e.g. genesis root) with matching `rootHashHinkalIndex`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = <EmporiumUpgradeable address>`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({v,r,s: arbitrary, signerAddress: address(0), ops: [EmporiumOperation({endpoint: <victim ERC20>, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, victimTokenEmporiumBalance))})], maxFee: 0, deadline: 0}))`.
3. Compute `calldataHash` per `CircomDataBuilder.getHashedCalldata` and embed it consistently in both the public inputs and `circomData.calldataHash`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)`. Proof verification passes (trivial circuit), root check passes, `_externalTransact` calls `EmporiumUpgradeable.runAction`, which executes the malicious `transfer` op with no signature check and no balance-diff enforcement, sending the target ERC20's entire Emporium-held balance to the attacker.
