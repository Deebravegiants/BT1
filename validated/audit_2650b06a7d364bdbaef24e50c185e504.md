### Title
Webhook `shop`/`topic` identity is not bound by the HMAC, allowing cross-tenant data attribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw body via `Utils::HmacValidator.validate(request)` [4](#0-3) . However, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`; the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read directly from HTTP headers and are never part of the signed data [5](#0-4) . This breaks the intended identity binding: `shop actually attested by Shopify's signature != shop asserted by the unauthenticated header the handler trusts`.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [6](#0-5) 

`Utils::HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` (also attacker-controlled input, taken from a header) [7](#0-6) . For `Request`, `to_signable_string` is defined as just the raw body bytes [1](#0-0) , and `shop`, `topic`, `webhook_id`, `api_version` are simple header reads with no cryptographic tie to that body [2](#0-1) .

Consequently, any `(body, hmac)` pair that is valid for the app's secret — for example genuinely generated by Shopify for one shop's webhook — remains a byte-for-byte valid signature no matter which `shop-domain` or `topic` header is attached to it. The library's own `process` method will accept it and hand the handler a `WebhookMetadata` whose `shop` field is fully attacker-controlled while still reporting `HmacValidator.validate` as `true`. This is directly analogous to the referenced report's root cause: a downstream action (`exercise`/webhook processing) trusts an identifier (`token owner`/`shop`) that was never actually checked against the cryptographically verified subject.

### Impact Explanation
This allows cross-tenant misattribution of webhook payloads: an attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the app's secret (e.g., from webhooks legitimately delivered to their own installed shop) can replay that exact body with a forged `shop-domain`/`topic` header pointing at a different, victim shop. Because the gem's own `Registry.process` reports the HMAC as valid and passes the forged `shop` straight to the handler, any host application that trusts `WebhookMetadata#shop` as an authenticated tenant key (the officially documented usage pattern) will process/store data under the wrong tenant — a cross-tenant integrity violation rooted entirely in this gem's verification logic.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one legitimately-signed `(body, hmac)` pair for the target app's secret. This is realistically obtainable by any account that can install the target app on their own shop (webhooks for `shop/redact`, `orders/create`, etc. are then delivered with a real HMAC for that body) if they can capture that raw request (e.g., by pointing a custom/dev app's webhook endpoint they control at their own infrastructure). No access to `api_secret_key`, access tokens, or privileged accounts is required — the attacker just needs their own app installation, which is available to any unprivileged developer/merchant account.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC validation, or independently verify `request.shop`/`request.topic` against values embedded in the signed body/payload before constructing `WebhookMetadata`. At minimum, document prominently that `HmacValidator.validate` only authenticates the byte content of the body and that header-derived fields (`shop`, `topic`) must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
```ruby
# Attacker installs TargetApp on their own shop "attacker.myshopify.com" and,
# via a custom app pointing the webhook URL at infrastructure they control,
# captures one legitimately Shopify-signed delivery:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac_b64 = "<hmac captured from Shopify's real delivery to attacker's shop>"

# Attacker replays the exact same body+hmac to the target app's webhook
# endpoint, but swaps the shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body+hmac match),
#    and the handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though that shop never sent this payload.
```
