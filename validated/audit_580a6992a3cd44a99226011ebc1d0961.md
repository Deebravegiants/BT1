### Title
Webhook `shop-domain` header is trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`, so `ShopifyAPI::Utils::HmacValidator.validate` (which computes `HMAC-SHA256(api_secret_key, to_signable_string)`) authenticates nothing but the raw JSON body bytes. The `shop` value used to route the webhook to a specific merchant/tenant is read from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, which is never included in the signed material. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as the analog report: a value that is *acted upon* (here, the tenant/shop identity used to dispatch webhook data) is not bound by the cryptographic check that is supposed to authenticate the request (here, the HMAC), exactly like the WatchPug finding where ERC20 leftover amounts were handled outside the code path that actually returns value to the user.

`Registry.process` validates the HMAC purely over the request, then immediately trusts `request.shop` (sourced only from the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because `to_signable_string` is just `@raw_body`, the HMAC is valid for *any* combination of headers as long as the body bytes match a message that was genuinely HMAC-signed by Shopify for the app's `client_secret`/`api_secret_key`. An unprivileged internet user who is able to observe (or trigger, e.g. by installing the app on their own free/dev store and receiving one legitimate webhook delivery with a given topic and body) one valid `(raw_body, hmac)` pair can replay that exact body and signature to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` for an arbitrary victim shop. `HmacValidator.validate` will report the request as authentic because it only checks `raw_body` against the signature; it has no dependency on the `shop-domain` header at all.

The identity binding that should hold and does not:
- `shop` authenticated (bytes actually covered by the HMAC) == `shop` used as the tenant key handed to the app's webhook handler
- Actual binding: `shop` authenticated = ∅ (not present in `to_signable_string`) ≠ `shop` used for routing = `request.shop` (header value)

### Impact Explanation
This crosses a tenant boundary: an app built on this gem cannot distinguish "webhook body B for shop A" from "webhook body B replayed while claiming to be shop V" using the primitives the gem provides, since `Utils::HmacValidator.validate(request)` returns `true` in both cases. Any app logic keyed off `WebhookMetadata#shop` (e.g., looking up the merchant's session/access token by shop, updating per-shop billing/subscription state, redacting/creating data scoped by shop, cache invalidation per shop) can be corrupted with attacker-supplied shop identity while still passing the gem's own signature check. This matches the "Cross-tenant access" / "shop authenticated versus the shop stored as a session key" impact class called out in scope.

### Likelihood Explanation
Reachable entirely through the gem's own documented webhook-processing API (`ShopifyAPI::Webhooks::Request.new` + `Registry.process`), with no dependency on `api_secret_key`, access tokens, or any privileged credential — the attacker only needs one legitimate `(body, hmac)` pair, which is trivial to obtain by receiving a real webhook on a shop the attacker legitimately controls (e.g., a free dev store installing the app), then replaying it against the app's public webhook endpoint with a forged shop header. No TLS interception or social engineering required.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values into the signed material that `HmacValidator` checks, or otherwise cryptographically bind them to the body before trusting them for routing — e.g. include the shop domain in `to_signable_string`, or require the caller/gem to independently verify that `shop` corresponds to a shop with an active, previously-established session/installation before invoking the handler, rather than trusting the header as-is once the body-only HMAC passes.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook `POST` with body `B` and headers including `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)`.
3. Attacker crafts a new request to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (== `B`) only, matches `H`, and returns `true`. [5](#0-4) 
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, i.e., attacker-controlled body content is processed by the app as authentic data belonging to `victim-shop`.
