## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing tenant confusion in `WebhookMetadata` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then passes the unauthenticated `shop-domain` header value to the app's handler as the trusted tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` verifies the signature against `request.to_signable_string`, which for `Webhooks::Request` is defined as `@raw_body` only [1](#0-0) . The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signable string and therefore is not covered by the HMAC at all [2](#0-1) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` and then forwards `request.shop` unchanged into `WebhookMetadata`, which is handed to the app's webhook handler as the shop the event belongs to [3](#0-2) .

This breaks the intended identity binding: `shop authenticated == shop the app acts on`. In this gem's design, only the request body bytes are proven genuine (i.e., produced with knowledge of `Context.api_secret_key`); the `shop-domain` header is asserted, not authenticated. An attacker who can replay or forward a validly-signed webhook body (for example, one they received for their own store, or one leaked/observed in transit) can change only the `shop-domain` header to any other shop's domain, and `HmacValidator.validate` will still return `true` because the signature check never inspects headers.

### Impact Explanation
This enables cross-tenant confusion: a webhook payload cryptographically valid for shop A can be delivered to the host application's endpoint labeled as belonging to shop B, and the gem will report it as authenticated for shop B via `WebhookMetadata#shop`. Any host application that uses `data.shop` from the handler to select which tenant's data/session to update (a extremely common pattern for mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics and general webhook processing) can be tricked into applying shop-A's payload against shop-B's tenant record, i.e. cross-tenant access/write. Severity: High, per the rubric's "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires the attacker to obtain a validly HMAC-signed webhook body for some shop's topic (e.g. by being a merchant/collaborator on any shop using the app, or intercepting/replaying a delivered webhook) and to control the headers of the request delivered to the app's webhook endpoint. Since `hmac_validator` and `Request#initialize` place no constraint tying the `shop-domain` header to the signed body, likelihood is moderate — it does not require the app's `client_secret` or any privileged credential, only the ability to send an HTTP request with a previously-observed valid `(body, hmac)` pair and an arbitrary `shop-domain` header value.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signable content, or otherwise cryptographically bind the `shop-domain` header to the request before trusting `request.shop`. At minimum, `Webhooks::Registry.process` should independently verify that the shop asserted in the header matches the shop associated with the merchant that legitimately owns the signed payload (e.g., look up the session/shop by an authenticated channel rather than trusting the header), and reject requests where this cannot be established.

### Proof of Concept
1. Attacker (a Shopify merchant using the vulnerable app on shop `attacker.myshopify.com`) triggers a real webhook (e.g. `orders/create`) and captures the exact raw body and the resulting `x-shopify-hmac-sha256` header value delivered by Shopify — this is a validly-signed `(body, hmac)` pair.
2. Attacker sends a POST request directly to the app's webhook endpoint with the same `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [4](#0-3) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only signs/verifies `@raw_body` [5](#0-4) .
4. The registered handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"`, even though the payload actually originated from `attacker.myshopify.com`'s webhook stream [6](#0-5) .
5. Any host application logic that trusts `data.shop` to select the tenant record to modify (e.g., processing `customers/redact` or storing order data) now operates on the wrong tenant, driven entirely by an unauthenticated header value.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
