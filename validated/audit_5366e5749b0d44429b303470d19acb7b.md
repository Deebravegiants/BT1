# Analysis: Forced Wrapped-Token Delivery on Native Transfer Failure

## Title
Unconditional WETH re-wrap fallback in `WrappedHyperFungibleToken` can permanently strand funds at beneficiaries that cannot handle ERC-20 tokens - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

## Summary
`WrappedHyperFungibleToken.onAccept` and `onPostRequestTimeout` (also duplicated in `WrappedHyperFungibleTokenUpgradeable.sol`) implement the exact bug class described in the GMX report: when a native-ETH push to the beneficiary fails, the contract automatically re-wraps the ETH into WETH and force-delivers it as an ERC-20 transfer, with no way for the sender/beneficiary to opt out of this fallback or to have the transaction revert instead.

## Finding Description
In `isWeth` mode, both delivery paths follow the identical pattern: [1](#0-0) 

```solidity
IWETH(_underlying).withdraw(message.amount);
(bool sent,) = beneficiary.call{value: message.amount}("");
if (!sent) {
    IWETH(_underlying).deposit{value: message.amount}();
    IERC20(_underlying).safeTransfer(beneficiary, message.amount);
}
```

The same logic is repeated for the timeout/refund path: [2](#0-1) 

and again in the upgradeable variant's `onAccept`/`onPostRequestTimeout`: [3](#0-2) [4](#0-3) 

`beneficiary`/`refundee` is derived from cross-chain message data (`message.to` / `message.from`) that the *sender on the source chain* supplies via `SendParams.to` when calling `send()`: [5](#0-4) 

There is no field in `SendParams`, nor any configuration option in `WrappedConfigOptions`, that lets the sender specify "native-only, revert if undeliverable." Whenever the beneficiary address is a contract without a payable `receive()`/`fallback()` (common for many multisigs, vaults, and deposit-only contract wallets), the native push at line 317/346 fails, and the contract silently substitutes an ERC-20 WETH transfer instead — exactly the anti-pattern flagged in the referenced GMX finding (`TokenUtils.withdrawAndSendNativeToken` re-wrapping on failure rather than reverting or deferring).

## Impact Explanation
If the beneficiary contract has no mechanism to sweep or otherwise use ERC-20 tokens (e.g., it is a native-ETH-only vault, exchange hot-wallet contract, or intentionally rejects payable calls to enforce a specific accounting flow), the WETH delivered via the fallback path can become permanently stranded — the exact impact the original report describes ("once sent, the wrapped version will be lost forever"). This affects both successful deliveries (`onAccept`) and timeout refunds (`onPostRequestTimeout`), so both the destination-chain recipient and the original source-chain sender (on refund) are exposed.

## Likelihood Explanation
The condition is trivially reachable by any unprivileged user: any sender can pick an arbitrary `to`/beneficiary address when calling `send()`, including a contract they do not control (e.g., bridging to an exchange deposit address or a third-party vault that only accepts native ETH). No special privileges or race conditions are required — a single `send()` call with a beneficiary lacking a payable fallback is sufficient to trigger the substitution.

## Recommendation
Do not silently substitute an ERC-20 transfer for a failed native push. Either (a) revert the delivery/timeout call so the message can be retried or handled via a manual claim step, or (b) add an explicit flag in `SendParams`/message encoding that lets the sender declare native-only delivery, and revert (rather than re-wrap) when that flag is set and the native push fails — mirroring the GMX report's recommendation of a two-step claim process instead of an implicit re-wrap.

## Proof of Concept
1. Sender calls `send()` on the source-chain `WrappedHyperFungibleToken` with `isWeth = true`, setting `params.to` to the address of `VaultC`, a contract with no `receive()`/payable `fallback()` (e.g., a Gnosis-Safe-style contract without the ETH-receiving module enabled).
2. Message is relayed and delivered; `onAccept` executes on the destination chain: `IWETH(_underlying).withdraw(message.amount)` succeeds, then `beneficiary.call{value: message.amount}("")` reverts because `VaultC` has no payable entry point.
3. The `if (!sent)` branch re-wraps the ETH and calls `IERC20(_underlying).safeTransfer(beneficiary, message.amount)`, delivering WETH to `VaultC`.
4. `VaultC` has no ERC-20 sweep/withdraw function for arbitrary tokens, so the WETH is permanently stuck in `VaultC`, unrecoverable by the intended recipient or the original sender.

        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
