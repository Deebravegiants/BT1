### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant impersonation via replayed webhook body - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` in `Registry.process` only authenticates the *body bytes*, not the `shop-domain` header that the handler uses to attribute the event to a tenant. This breaks the identity binding: `shop authenticated` != `shop acted on`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns `@raw_body` only — the `shopify-shop-domain` header is completely excluded from the signed material. `Registry.process` then does: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the body) and compares against the `hmac-sha256` header: [3](#0-2) 

Because the signature only covers the body, any request with a body+HMAC pair that was legitimately generated by Shopify for *any* shop remains valid regardless of what value is placed in the `shopify-shop-domain` / `x-shopify-shop-domain` header. `Registry.process` passes `request.shop` (i.e., the unauthenticated header value) straight into `WebhookMetadata` and to the app's handler: [2](#0-1) 

This is directly analogous to the reported bug class: a value that is *acted upon* (the vault ID / here, the tenant identity used to route and process the event) is not the value that was *authenticated* (the build caller / here, the HMAC-signed body). Just as the Cauldron report shows the protocol trusting an unauthenticated `vaultID` supplied by the caller, this gem trusts an unauthenticated `shop-domain` header supplied by the caller of the webhook endpoint, while only the body is bound by the HMAC.

### Impact Explanation
An unprivileged internet user who operates their own Shopify store with the target app installed can receive a legitimate webhook from Shopify for their own shop (valid body + valid HMAC for that body). They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different value in the `shop-domain` header (e.g., a victim shop's domain). Since the signature check never inspects the header, the forged request passes HMAC validation, and the app's webhook handler will process the event as if it originated from the victim's shop — i.e., cross-tenant data/event injection using another merchant's identity. Depending on how the host application uses `WebhookMetadata#shop` (e.g. to look up a session/access token and act on the victim's store, or to write data keyed by shop), this can lead to cross-tenant access or data corruption attributed to the wrong tenant.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the attacker to control at least one shop that has the app installed (to legitimately receive a signed webhook body of a type they want to spoof), and it requires the host application to trust `WebhookMetadata#shop` for tenant-sensitive actions without independently re-validating it — which is the intended/documented usage pattern of this gem's webhook processing API (`Registry.process` → handler receives `shop:` as authenticated-looking metadata). Given how the gem's public API surfaces `shop` as part of the "verified" `WebhookMetadata`, most integrators would reasonably trust it, similar to how Yield's front-end trusted vault ownership by ID without expecting front-running.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers in the HMAC-signed material, or independently bind/verify the `shop-domain` header against a value derived from a trusted source (e.g., cross-check with the session/shop the webhook was registered for) before handing it to the handler as authenticated `WebhookMetadata`. At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-sensitive decisions without further verification.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and the valid HMAC value.
3. Attacker crafts a new HTTP request to the app's webhook endpoint with the same body `B`, the same valid HMAC header, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` against the header value — the forged `shop-domain` is never part of the signed data: [2](#0-1) 
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and processes/acts on data attributed to the victim shop, even though the event never originated from Shopify for that shop.
