### Title
Tron IntentGatewayV2.placeOrder omits duplicate-output-token and fee-on-transfer input validation present in the audited EVM version, allowing escrow corruption / fund theft - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of the intent gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reimplements `placeOrder` but drops two input-validation checks that the canonical EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) enforces: (1) rejection of duplicate output tokens in `order.output.assets`, and (2) balance-delta-based accounting of actually-received input tokens (fee-on-transfer protection) instead of trusting the caller-declared `amount`. This mirrors the OmniEstate root cause: a user-controlled quantity/parameter is accepted without validating it against what actually happened on-chain (actual token receipt / uniqueness of accounting buckets), letting an unprivileged caller corrupt escrow accounting reachable by a single `placeOrder` transaction.

### Finding Description
`Order.output.assets` in the Tron contract is used later (in `fillOrder`/partial-fill logic, not shown in this file but shared via the common `IntentGatewayV2.sol` interface/library in `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`) to key per-output-token partial-fill state. In the canonical EVM contract, `placeOrder` explicitly guards against two duplicate-token classes: [1](#0-0) 

and equivalently rejects duplicate **input** tokens (regression tests confirm this was a fixed vulnerability class: "same-chain partial fills over-release repeated input escrow" / "prematurely finalize repeated output legs"): [2](#0-1) [3](#0-2) 

The Tron `placeOrder`, however, contains **no duplicate-token check at all** — neither for `order.inputs` nor `order.output.assets` — before computing the commitment and escrowing tokens: [4](#0-3) 

Additionally, the canonical EVM contract measures *actual* balance received after `safeTransferFrom` (protecting against fee-on-transfer / deflationary tokens) and mutates `order.inputs` to the real received amount before it is escrowed or committed to: [5](#0-4) 

The Tron version's non-predispatch escrow path instead trusts the caller-declared `order.inputs[i].amount` outright and stores that (fee-reduced) amount directly into `_orders[commitment][token]` without ever checking the gateway's actual token balance delta: [6](#0-5) 

This is functionally identical in spirit to `OmniEstate.invest(end_date, qty_ort)` accepting an attacker-supplied quantity without validating it against the amount actually transferred/at-stake, letting the accounting diverge from real custody.

### Impact Explanation
- **Duplicate output tokens**: because the fills/partial-fill bookkeeping (per the same struct used by the shared `IntentGatewayV2.sol` fill logic) buckets state by output token, two output legs for the same token collapse into one bucket. As demonstrated by the sibling regression tests on the audited EVM contract, this class of bug allows a partial fill to be marked "fully filled" prematurely or causes over-release of escrowed input tokens to a solver — i.e., concrete theft of escrowed user funds or a filler being paid for delivering less than what was ordered.
- **No fee-on-transfer / balance-delta check**: for any ERC20 with a transfer fee, burn-on-transfer, or rebasing behavior, the gateway will escrow (i.e., account for in `_orders[...]`) more than it actually holds. When the order is later filled and `withdraw()` pays the solver/beneficiary from `_orders[commitment][token]`, the contract's actual token balance is insufficient, causing either (a) a permanent freeze of a portion of every other user's escrowed funds in the same token (the shortfall must be siphoned from someone else's escrow to make a transfer succeed), or (b) a failing/reverting delivery that blocks legitimate withdrawal (freezing of funds) since `withdraw()` on Tron does not use `SafeERC20`/receipt-checking and instead just calls `token.call(...)` and treats success flag alone as proof of full payment.

Both conditions meet the "concrete theft or permanent freezing of funds" bar for the token-bridge/intents-escrow bug class defined in scope.

### Likelihood Explanation
- Reachable directly by any unprivileged caller via a single `placeOrder(order, graffiti)` transaction — no relayer, proof, or governance action required.
- Duplicate output tokens require no unusual token behavior — just crafting `order.output.assets` with a repeated `token` field, which nothing in the Tron contract rejects.
- Fee-on-transfer exploitation requires the deployment to support (or a governance-added) a token with non-standard transfer semantics; likelihood is contingent on the token set enabled on the Tron deployment, but the contract itself provides zero defense whereas the reference implementation explicitly hardened this exact scenario (see the fee-on-transfer test suite cited above), strongly suggesting this was a known, fixed issue in the primary contract that the Tron port failed to backport.

### Recommendation
Port the following protections from `evm/src/apps/IntentGatewayV2.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`:
1. Add the duplicate-token rejection loop for both `order.inputs` and `order.output.assets` (transient-storage or a simple in-memory nested loop, since Tron/TVM support may differ from `tstore`/`tload` — verify TVM opcode support and fall back to an O(n²) comparison if transient storage isn't available) before computing the commitment.
2. Replace the direct `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` + trust-based escrow bookkeeping with balance-before/after measurement, mutate `order.inputs[i].amount` (or the `reducedInputs[i].amount`) to the actual received amount, and use that value both for the commitment hash and for `_orders[commitment][token]`.
3. Add regression tests mirroring `testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateOutputTokens`, and the fee-on-transfer suite in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, adapted to the Tron contract.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and initialize with two ERC20 tokens (or one being fee-on-transfer).
2. Call `placeOrder` with `order.output.assets` containing two entries for the same `token` (e.g., DAI amounts 400 and 600), analogous to `testRevert_PlaceOrder_DuplicateOutputTokens` in the reference test file — the Tron contract accepts this order without reverting, unlike the audited EVM version.
3. Have a solver perform a partial fill against one of the duplicate output legs; because fill/partial-fill state is keyed by output token, the second leg's remaining amount is miscounted, letting the solver claim escrow disproportionate to what was actually delivered (mirrors the exact "over-release repeated input/output escrow" regression the reference contract patches — see `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2115-2148,2238-2272`).
4. Separately, place an order whose `order.inputs` token is a fee-on-transfer ERC20; the Tron contract escrows the full pre-fee `amount` in `_orders[commitment][token]` even though it only received `amount - fee` tokens, exactly as characterized by `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2441-2494`) for the reference contract that *does* guard against this — the Tron contract has no equivalent guard, so a later `withdraw()` for that token will pay out more than the gateway actually holds, drawing down other users' escrow.

    function placeOrder(Order memory order, bytes32 graffiti) public payable nonReentrant {
        if (order.inputs.length == 0) revert InvalidInput();

        // Reject duplicate output tokens
        uint256 outputsLen_ = order.output.assets.length;
        for (uint256 i; i < outputsLen_;) {
            bytes32 token = order.output.assets[i].token;
            assembly ("memory-safe") {
                if tload(token) {
                    mstore(0, 0xb4fa3fb3) // InvalidInput.selector
                    revert(0x1c, 0x04)
                }
                tstore(token, 1)
            }
            unchecked {
                ++i;
            }
        }
        // Clean up transient storage so repeated placeOrder calls in the same tx don't false-positive.
        for (uint256 i; i < outputsLen_;) {
            bytes32 token = order.output.assets[i].token;
            assembly ("memory-safe") {
                tstore(token, 0)
            }
            unchecked {
                ++i;
            }
        }

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);

        assertEq(

    function placeOrder(Order memory order, bytes32 graffiti) public payable {
        // Validate that order has inputs
        if (order.inputs.length == 0) revert InvalidInput();

        address hostAddr = host();
        // fill out the order preludes
        order.user = bytes32(uint256(uint160(msg.sender)));
        order.source = IDispatcher(hostAddr).host();
        order.nonce = _nonce++;

        // Calculate reduced inputs (after protocol fees) for commitment and escrow
        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                uint256 originalAmount = order.inputs[i].amount;
                uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
                uint256 reducedAmount = originalAmount - protocolFee;
                address token = address(uint160(uint256(order.inputs[i].token)));

                // Emit DustCollected for protocol fee if non-zero
                if (protocolFee > 0) emit DustCollected(token, protocolFee);

                reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
                unchecked {
                    ++i;
                }
            }

            // Temporarily swap inputs to calculate commitment with reduced amounts
            TokenInfo[] memory originalInputs = order.inputs;
            order.inputs = reducedInputs;
            commitment = keccak256(abi.encode(order));
            order.inputs = originalInputs;
        } else {
            // No protocol fees, use order.inputs directly
            reducedInputs = order.inputs;
            commitment = keccak256(abi.encode(order));
        }
