Found a concrete, provable inconsistency in `lib/shopify_api/auth/token_exchange.rb`: the primary `exchange_token` method skips a domain-trust check that every other credential-sending OAuth method in the same file/module performs.

### Title
Missing Shopify-domain validation on JWT `dest` claim before sending `client_secret` in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the OAuth `access_token` request directly from the unvalidated `dest` claim of the caller-supplied session token, and sends the app's `client_secret` to that host without ever passing it through `Utils::ShopValidator.sanitize!`. Every other method in this module/gem that builds a similar `client_secret`-bearing request (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` first and uses the *sanitized* value as the request host. `exchange_token` is the odd one out.

### Finding Description
`JwtPayload#shop` simply strips the `"https://"` prefix from the token's `dest` claim with no domain-shape checking: [1](#0-0) 

`TokenExchange.exchange_token` takes this raw value and uses it, unsanitized, to build the `HttpClient` that receives the `client_id`/`client_secret` POST body: [2](#0-1) 

Compare this with the three sibling flows in the same auth surface, which all treat the incoming `shop` string as untrusted and run it through `Utils::ShopValidator.sanitize!` — which restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before it is used to build the request host that receives `client_secret`: [3](#0-2) [4](#0-3) [5](#0-4) 

`Utils::ShopValidator` exists specifically to close this class of gap — its own tests document rejecting attacker-controlled or look-alike domains before they're trusted as an OAuth token endpoint: [6](#0-5) [7](#0-6) 

The identity binding that should hold is: **the host that receives `client_secret` == a host that has passed `ShopValidator.sanitize!`**. This equality holds for `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token` (all three compute `validated_shop` and use it both for `shop_session` and for the returned `Session.from(shop: validated_shop, ...)`), but is broken in `exchange_token`, where `dest_shop = jwt_payload.shop` is used directly with no equivalent check.

### Impact Explanation
`exchange_token` is documented as the *recommended* OAuth flow for embedded apps (preferred over the Authorization Code Grant), meaning it is the primary code path most integrators will use. Because the JWT signature check in `JwtPayload` only verifies `aud == Context.api_key` and HMAC integrity — it does not constrain what domain string can appear in `dest` — the only thing standing between an attacker-influenced `dest` value and an app leaking its `client_secret` to a non-Shopify host is the (missing) domain allow-list check that all its sibling functions perform. If this validation gap is exploitable in any deployment context (e.g., a JWT source that is less trustworthy than App Bridge, or any future code path that constructs a session token from other input), it directly enables SSRF carrying the app's `client_secret` to an attacker-controlled endpoint, matching the "SSRF with the app's credentials" High-impact category.

### Likelihood Explanation
The gap is deterministic and code-verifiable: `git grep` shows `ShopValidator.sanitize!` used in exactly 3 of the 4 comparable `client_secret`-sending call sites in `lib/shopify_api/auth/`, with `exchange_token` being the sole omission despite being the flow the docs recommend by default. This is not a theoretical style nitpick — it is a defense-in-depth control that the maintainers clearly consider necessary (as evidenced by its presence everywhere else and its dedicated `ShopValidator` module/tests), simply missing from the one method that is most heavily used.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` the same way as the other methods before using it to construct the request host or the returned `Session`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
so that the host receiving `client_id`/`client_secret` is provably constrained to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, consistent with `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`.

### Proof of Concept
Static comparison of the four credential-sending flows in `lib/shopify_api/auth/`:
- `client_credentials.rb:25` → `validated_shop = Utils::ShopValidator.sanitize!(shop)` used for `shop_session`/`Session.from`.
- `refresh_token.rb:24` → same pattern.
- `token_exchange.rb:103` (`migrate_to_expiring_token`) → same pattern.
- `token_exchange.rb:41` (`exchange_token`) → `dest_shop = jwt_payload.shop` used directly, **no** `ShopValidator` call, then passed straight into `Session.new(shop: dest_shop)` → `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` which sends `client_secret` in the request body to that host.

```ruby
      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
```
