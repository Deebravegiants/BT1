### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook by validating the `hmac-sha256` header against the raw request body only. The `shop` attribute — the tenant identifier that is handed to the app's `WebhookHandler` and used by the host app to route/attribute webhook data to a specific merchant — is read straight from the unsigned `shopify-shop-domain` header and is never included in the signed content. The identity binding `HMAC-covered bytes == acted-upon shop identity` is broken.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing the HMAC over `to_signable_string` and comparing it (with `OpenSSL.secure_compare`) to the `hmac` accessor of that object [1](#0-0) .

For webhooks, `Request#to_signable_string` returns only `@raw_body`, while `Request#shop` is read independently from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, and is not part of the signed string at all: [2](#0-1) [3](#0-2) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (i.e., body-only) and then forwards `request.shop` — the unauthenticated header value — straight into `WebhookMetadata`, which is the tenant identity the host application's handler acts on: [4](#0-3) [5](#0-4) 

Equality that should hold but doesn't:
`HMAC(client_secret, bytes verified)` binds `raw_body` only, while the field actually acted upon downstream is `shop` (from `shopify-shop-domain`). Since `shop ∉ to_signable_string`, an attacker who possesses *any* validly-signed `(raw_body, hmac)` pair for their own tenant can resubmit it with an arbitrary `shopify-shop-domain` header value, and `HmacValidator.validate` will still return `true` because it never inspects `shop` at all.

Note this class only requires possession of one legitimately-signed webhook delivery for the attacker's own store (a normal Shopify merchant installing the app receives many of these automatically, e.g. `orders/create`, `app/uninstalled`), and this webhook was itself delivered over plain HTTP by Shopify without transport-level tenant binding — no `client_secret`, access token, or other privileged credential is needed to mount the attack.

### Impact Explanation
This allows cross-tenant confusion / spoofing at the application boundary that this gem exposes to host apps: the gem hands the host app a `WebhookMetadata.shop` value that has no cryptographic binding to the payload it accompanies, even though `Utils::HmacValidator.validate` returned `true` and the host app reasonably treats that as proof the webhook (body **and** shop) originated from Shopify for that shop. An attacker (any merchant with the app installed) can replay their own signed webhook body while claiming it belongs to a victim shop, causing the host app to record, act on, or overwrite state keyed by the victim's shop domain using attacker-controlled data — a cross-tenant integrity/confidentiality violation depending on what the host app's handler does with `data.shop` and `data.body`.

### Likelihood Explanation
High likelihood of being reachable: any user of the `Webhooks::Registry.process` API (the gem's documented entry point for verifying and dispatching inbound webhooks) is affected, and the only prerequisite is having received one legitimately-signed webhook for the attacker's own installed shop — a routine, unprivileged occurrence, not a leaked secret or special access.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, or otherwise cryptographically tie the shop-domain header to the signed body before trusting `request.shop`, e.g. by including the relevant Shopify headers in `to_signable_string`, or by validating that `request.shop` matches an expected/known session's shop rather than trusting the header verbatim.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app with a correct `x-shopify-hmac-sha256` computed over the raw JSON body using the app's `client_secret`, and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this `(raw_body, hmac)` pair.
3. Attacker crafts a new HTTP request to the app's webhook endpoint with the **same** `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present) [6](#0-5) .
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds, since `raw_body` and `hmac` are unchanged from the legitimate delivery [7](#0-6) .
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, i.e., the host application now processes attacker-controlled data under the victim's tenant identity, despite HMAC validation "passing".
