### Title
Webhook Shop-Domain Header Spoofing via HMAC Scope Gap — Cross-Tenant Webhook Attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (`X-Shopify-Shop-Domain`) header used to attribute the event to a tenant is never included in the signed material. An attacker who can obtain one legitimately-signed webhook payload (trivial for a public app, since anyone can install it on their own store) can replay that exact body/HMAC pair while substituting the `shop-domain` header for a victim shop, and the gem will accept it as authentic and hand it to the app's handler as if it originated from the victim.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is read directly from an unauthenticated header with no binding to the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, with no cross-check that the shop asserted in the header matches the tenant the signed body was actually generated for: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely over `verifiable_query.to_signable_string`, which for webhooks is `@raw_body` — the shop header never enters the computation: [4](#0-3) 

The identity binding broken is: `HMAC-covered-bytes (raw_body) != authenticated-attribution-fields (shop header)`. Since Shopify's app `api_secret_key` is a single secret shared across **every** shop that installs the app (it is not per-installation), any attacker can install the target app on their own dev/test store, capture a legitimately Shopify-signed webhook (valid `hmac` + `raw_body` pair for a chosen topic, e.g. `orders/create`), and replay that exact HTTP request to the app's webhook endpoint while only changing the `X-Shopify-Shop-Domain` header to a victim shop's domain. The HMAC check still passes because the body is unchanged, and `Registry.process` dispatches the handler with `shop: request.shop` set to the attacker-chosen victim domain.

### Impact Explanation
Any app built on this gem that uses the webhook `shop` field to scope database writes, cache keys, feature flags, or trigger tenant-specific side effects (the intended and documented use of `WebhookMetadata#shop`) can be made to apply attacker-controlled webhook data (order, product, customer payloads the attacker fully controls from their own test store) under a victim shop's identity. This is a cross-tenant data-integrity/confusion vulnerability meeting the "cross-tenant access" Critical impact bar, because it lets an unprivileged internet user who merely installs the same public app inject events attributed to a merchant they do not control.

### Likelihood Explanation
Likelihood is high: exploitation requires only the ability to install the target (public) app on an attacker-owned store — no privileged credentials, no access token theft, and no interception of the merchant's traffic. Capturing one valid signed webhook and replaying it with a modified header is a straightforward HTTP replay, fully reachable through this gem's own `Registry.process`/`Request` API as documented.

### Recommendation
Bind the asserted `shop` (and other attribution headers such as `topic`/`webhook-id`) into the HMAC-signable material, or require the host application to independently verify that the `shop-domain` header corresponds to a shop with an active, known installation/session before trusting it — i.e., extend `Request#to_signable_string` to include the shop domain, or have `Registry.process` cross-check `request.shop` against session/installation state rather than trusting the header on its own.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. `orders/create`) and captures the raw POST body plus the `X-Shopify-Hmac-Sha256` header Shopify computed for it — this HMAC is valid because it's signed with the app's single shared `api_secret_key`.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the (unchanged, valid) HMAC: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload originated from the attacker's own store, allowing the attacker to inject attacker-controlled data attributed to the victim tenant.

        end

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
