### Title
Predictable, Unsigned Session Cookie Enables Cross-Tenant Session Hijacking - (File: `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/session.rb`)

### Summary
For non-embedded (and embedded-fallback) OAuth flows, the gem sets a plaintext, **unsigned** session cookie whose value is the session's `id`. That `id` is not a random secret — for offline sessions it is the fully predictable string `"offline_#{shop}"`, derived only from the merchant's public `.myshopify.com` domain. `SessionUtils.cookie_session_id` later trusts this raw cookie value verbatim as the session identifier to look up and activate a session. Because the cookie carries no HMAC/signature and the ID is guessable from public information, any unprivileged internet user can forge the cookie for a victim shop and have the host application resolve and use that shop's stored (offline) access token on their behalf.

### Finding Description
The intended binding is: *the session id in the client's cookie must be an unforgeable token, unpredictable, and cryptographically bound to the identity that legitimately completed the OAuth handshake for that specific shop*. In practice this gem breaks that binding on two fronts simultaneously:

1. **Predictable identifier.** `Session.from` builds the id purely from the shop domain with no random or secret component: [1](#0-0) 
and `SessionUtils.offline_session_id`/`jwt_session_id` reproduce the same deterministic scheme: [2](#0-1) 

2. **Unsigned cookie carrying that identifier.** `Oauth.validate_auth_callback` sets the cookie's `value` to this predictable `session.id` with no MAC/signature protecting it: [3](#0-2) 

3. **Blind trust on read.** `SessionUtils.current_session_id`/`cookie_session_id` take whatever value is present in the `shopify_app_session` cookie and hand it back as *the* session id, with zero cryptographic verification: [4](#0-3) [5](#0-4) 

Contrast this with the two identity-binding mechanisms that *are* correctly protected elsewhere in the gem: the OAuth callback query is HMAC-verified via `Utils::HmacValidator` before `shop`/`state` are trusted [6](#0-5) , and the App Bridge session token is cryptographically signed and decoded with `Context.api_secret_key` before its `dest`/`shop` claim is trusted [7](#0-6) . The plain session cookie has no equivalent protection — it is raw, attacker-controllable bytes that get parsed directly into a trusted session id, exactly the "session id derived from unauthenticated bytes" bug class.

The `getting_started.md` documentation confirms this cookie/id is meant to be handed straight to the host app's session store for retrieval, i.e. this is the gem's documented, intended flow, not host-app misuse: [8](#0-7) 

### Impact Explanation
An unprivileged internet user who merely knows (or guesses) a merchant's `.myshopify.com` domain — public information routinely exposed in storefront URLs, app listings, or simple enumeration — can construct the cookie value `offline_{victim-shop}.myshopify.com` (or `{victim-shop}.myshopify.com_{user_id}` for online sessions, where `user_id` is often a small sequential integer) and present it as their own session cookie. Any host application following this gem's documented pattern (`SessionUtils.current_session_id` → `SessionRepository.retrieve`) will resolve and activate the victim merchant's stored session, including its offline **access token**. The attacker can then make authenticated Admin API calls against the victim's shop through the host app's server-side session activation (`Context.activate_session`), achieving cross-tenant access without ever presenting a valid credential of their own. This qualifies as Critical impact under the given rubric (cross-tenant access / theft-equivalent use of a merchant access token).

### Likelihood Explanation
Likelihood is high for offline sessions: the id is a deterministic function of only the shop's domain name, which is not a secret. For online sessions, the attacker additionally needs the target user's numeric Shopify user id, which is often low-entropy/sequential and may be discoverable, reducing but not eliminating exploitability. No TLS interception, leaked secrets, or privileged access is required — only the ability to set an arbitrary `Cookie` header, which any HTTP client can do.

### Recommendation
Do not use a deterministic, guessable value as the session cookie payload, and do not trust raw cookie bytes as an authoritative session id. Sign/MAC the cookie value (e.g., HMAC with `api_secret_key`, verified on read in `SessionUtils.cookie_session_id`) or replace the predictable `"offline_#{shop}"` / `"#{shop}_#{user_id}"` scheme with a high-entropy random session identifier that is opaque and unguessable, mapping to the shop/user only server-side.

### Proof of Concept
1. Merchant `victim-shop.myshopify.com` installs the host app; the app completes OAuth via `ShopifyAPI::Auth::Oauth.validate_auth_callback`, producing `session.id == "offline_victim-shop.myshopify.com"` and setting cookie `shopify_app_session=offline_victim-shop.myshopify.com` (non-embedded flow) — [3](#0-2) .
2. Attacker, with no account and no credentials, sends a request to the host app with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged — [4](#0-3) .
4. The host app's `SessionRepository.retrieve(id)` (the exact pattern this gem's own docs recommend) looks up and returns the victim's stored `Session`, including its real `access_token`.
5. The attacker's request is now served using the victim shop's session/access token — cross-tenant compromise achieved purely by guessing a public domain name.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
