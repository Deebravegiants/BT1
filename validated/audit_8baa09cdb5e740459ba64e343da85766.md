### Title
Webhook `shop`/`topic` headers are trusted for tenant routing without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw JSON body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are handed to the app's handler as the authoritative tenant/topic identifiers — come from HTTP headers that are entirely outside the signed content.

### Finding Description
`Request#hmac` and `Request#to_signable_string` derive the signature check exclusively from `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). `Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which recomputes the HMAC over that same `to_signable_string` and compares it to the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header. Once that check passes, `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all read from separate, unsigned headers via `shopify_header` — are placed into `WebhookMetadata` and forwarded to the app's `handle` callback unchanged (`lib/shopify_api/webhooks/registry.rb:198-199`). The equality the gem is implicitly asserting is: `hmac(body) valid` ⇒ `(shop header, topic header) can be trusted`. That equality does not hold, because `shop`/`topic`/`webhook_id`/`api_version` are never part of the signed bytes.

Any holder of a valid `(body, hmac)` pair for the shared app secret — e.g., a merchant who has installed the app on their own store and therefore legitimately receives real webhooks signed with the app's `client_secret` — can replay that exact `body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and `shopify-topic`) header. `HmacValidator.validate` still returns `true` because it only checks the body bytes, so `Registry.process` proceeds and calls the handler with attacker-chosen `shop`/`topic` values alongside the original, HMAC-covered body content.

### Impact Explanation
Per the documented usage pattern (`docs/usage/webhooks.md:10-29`), host apps use `data.shop` from `WebhookMetadata` as the tenant key to load the shop's session/data and persist or act on `data.body`. Because `data.shop` is unauthenticated, an attacker-controlled value can be substituted for the real tenant while a validly-signed body is delivered, letting one tenant's webhook event be attributed to (and processed as) a different tenant — a cross-tenant confusion inside the app that trusts this gem's stated authentication guarantee ("this will verify the request did indeed come from Shopify", per the same doc). This matches the Critical "cross-tenant access" category, since the boundary crossed is exactly the shop/tenant identity the app relies on this gem to authenticate.

### Likelihood Explanation
Exploitation requires only: (1) attacker has (or creates) their own installation of the target app on a shop they control, so they receive real, validly-HMAC'd webhooks for their own shop, and (2) attacker can send an arbitrary HTTP request with custom headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is required — the attacker only needs a body/HMAC pair they legitimately received as a normal (even free-trial) merchant of the target app.

### Recommendation
Include `shop-domain`, `topic`, and `webhook_id` in the signed content the HMAC is computed over (or otherwise cryptographically bind them to the body), or have `Registry.process`/`Request` reject the request unless these header values are corroborated against Shopify-controlled data (e.g., verifying the webhook subscription/topic against the shop that owns it) rather than trusting them as bare headers.

### Proof of Concept
1. App "TargetApp" registers an HTTP webhook handler for topic `orders/create` that, per the documented pattern, loads/updates data keyed by `data.shop`.
2. Attacker installs TargetApp on `attacker-shop.myshopify.com` and triggers an `orders/create` event, capturing the raw POST: `raw_body = B`, header `shopify-hmac-sha256 = H = HMAC-SHA256(client_secret, B)`, `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical request to the same webhook endpoint, keeping `raw_body = B` and `shopify-hmac-sha256 = H` unchanged, but replacing the header `shopify-shop-domain: attacker-shop.myshopify.com` with `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`); the handler is invoked with `data.shop == "victim-shop.myshopify.com"` even though the body content and cryptographic proof only ever came from `attacker-shop.myshopify.com`.
