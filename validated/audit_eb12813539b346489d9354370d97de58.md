### Title
Webhook Shop Attribution Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC computed only over the raw request body, while the `shop` identity used to route and process the webhook is read from an unauthenticated HTTP header. This breaks the identity binding `shop_verified_by_hmac == shop_used_by_handler`, allowing any party who can obtain one genuinely-signed webhook payload (e.g. by installing the app on their own store) to relabel it as belonging to a different, victim shop.

### Finding Description
`Request#hmac` reads the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` method used elsewhere for identity attribution is derived from the `shop-domain` header, which is completely outside the signed content: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body signature) and then dispatches to the handler using `request.shop` taken straight from the unauthenticated header: [3](#0-2) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, which for webhooks is just the raw body — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never part of the signed material: [4](#0-3) 

Because the app's `client_secret` is shared across all shops that install the app (it's the same secret Shopify uses to sign every merchant's webhook deliveries to that app), an attacker who installs the app on their own store receives genuinely-signed webhook bodies for arbitrary topics/content they control (e.g., by editing their own store data to control body content). They can then replay that valid `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still succeed, since only the body is checked, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop: [5](#0-4) 

This is the same class of bug as the referenced report: a value acted upon (`credit`/here, `shop`) is not the same value that was actually verified/authenticated (`rewardOf`/here, the HMAC-signed body), letting an attacker desynchronize the two.

### Impact Explanation
This is a cross-tenant identity confusion in a multi-tenant app built on this gem: an unprivileged user (any merchant who can install the app on their own store) can cause the app to process attacker-supplied webhook data attributed to a victim shop of their choosing. Depending on what the host application does with `WebhookMetadata.shop` (session lookup, data mutation scoped by shop, job enqueuing per shop as shown in the gem's own documented usage pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this can lead to cross-tenant data corruption or processing of forged events as if they came from another merchant's store — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any developer following the gem's documented pattern verbatim (`docs/usage/webhooks.md`), since the API surface (`Request#shop`, `WebhookMetadata#shop`) implies the shop value is trustworthy once `Registry.process` succeeds, when in fact it is not covered by the cryptographic check. The only prerequisite is the ability to install the app on an attacker-controlled store to obtain one valid `(body, hmac)` pair — no privileged credentials, leaked secrets, or social engineering are required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the request (e.g., incorporate them into `to_signable_string`), so that `HmacValidator.validate` fails if any of these attributed fields are altered relative to what Shopify actually sent.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends (this HMAC is valid because it's computed with the app's real `client_secret`).
2. Replay that captured `(raw_body, hmac)` pair to the app's registered webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC — the forged `shop-domain` header is never validated: [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own store.
