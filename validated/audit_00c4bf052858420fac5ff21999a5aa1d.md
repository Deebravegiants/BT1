### Title
Unbounded `reserveIn * reserveOut * targetN` discriminant in `_noFeeSwapInput` can revert and permanently brick `finalizeGraduation` - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding._noFeeSwapInput` (the closed-form rebalance-swap-size calculation used by the hostile-pre-seed defense in `_pairRebalance` / `_seedRebalancing`) computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` [1](#0-0) . `reserveIn`/`reserveOut` are the live, attacker-influenceable HyperSwap V2 pair reserves (up to `uint112.max` each, per the pre-seed front-run described in the "HyperSwap Pre-Seed Defense" doc) while `targetN`/`targetD` are the protocol's cached `tokensForLP`/`ltFromPair`. The protocol's own test suite proves the discriminant can exceed `type(uint256).max` at realistic (uint112 reserve, token-supply-scale target) magnitudes [2](#0-1) , at which point `Math.mulDiv` reverts rather than truncating. That is exactly the CVE-2016-9586 bug class: a value whose magnitude was assumed to stay inside a bound is fed straight into a fixed-capacity computation without a defensive cap, so an unexpectedly large input blows past the assumed limit.

### Finding Description
`finalizeGraduation` is the sole, permissionless path that completes a two-phase graduation and unfreezes trading; phase 1 has already parked all curve-raised LT and the 250M reserve tokens on `Bonding` and frozen the curve [3](#0-2) . When the HyperSwap pair has been front-run with a mint pre-seed, phase 2 runs `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput` to compute the rebalance-swap size before depositing the protocol's inventory [4](#0-3) .

`_noFeeSwapInput`'s own natspec explicitly documents the risk: "the final result `.../targetD` must still fit in uint256. Call sites must keep that invariant ... Constructed adversarial inputs that violate this would `revert` rather than silently truncate" [5](#0-4) . The team's own overflow-safety test demonstrates the discriminant `reserveIn * reserveOut * targetN / targetD` reaches `2^314` at uint112-max reserves combined with a token-supply-scale `targetN`, and only avoids reverting because the test deliberately picks `targetD` large enough to cancel it out [2](#0-1) . In production, `targetD = ltFromPair` is not attacker- or protocol-bounded to be "large" — it is simply the real LT raised by a given curve, which can be small in raw LT units (e.g., a token that graduates via the supply trigger, or one paired against a high-value/low-supply LT, where the $9K/$-equivalent threshold is met with comparatively few raw LT units) while `targetN = tokensForLP` scales toward the 250M-token cap. Meanwhile `reserveIn`/`reserveOut` are fully attacker-controlled: any address can front-run the HyperSwap pair creation, `transfer` in large balances of the launched Token and the shared LT, and call `pair.mint(attacker)` to set `getReserves()` to whatever ratio and magnitude they can fund (bounded only by `uint112`, i.e. up to ~5.19e33 per side) [6](#0-5) . Because the LT is a shared reserve asset traded across every bonding curve on the platform, an attacker does not need to fund this from a single curve — they can accumulate large LT balances across the whole protocol's LT supply and any Token balance they can buy/hold, then dump both into the fresh pair right before `finalizeGraduation` runs.

No caller in `_pairRebalance`/`_seedRebalancing`/`_seedUniswapV2Direct`/`finalizeGraduation` wraps this call in a try/catch or pre-validates the discriminant magnitude before invoking `_noFeeSwapInput` [4](#0-3) . A revert inside `_noFeeSwapInput` therefore propagates unhandled all the way up through `finalizeGraduation`, causing the entire graduation transaction to revert. This directly contradicts the protocol's own stated invariant that "`_seedUniswapV2Direct` MUST never revert under any pre-seed shape" because "a brick locks every holder in `Graduating` forever" [7](#0-6) .

### Impact Explanation
If the discriminant overflow is reachable in practice (see Likelihood), the effect is a permanent freeze of protocol funds: every buyer's tokens, every LP-bound token/LT reserve parked on `Bonding` during phase 1, and the entire curve's raised LT become permanently stuck — `finalizeGraduation` can never succeed for that token (no retry path changes the attacker's pre-seeded reserves), `LPLock` never receives LP, and `LPLock` has no rescue/withdraw path in v1 [8](#0-7) . This matches the "permanent freezing of trader, creator or LP funds" impact class explicitly accepted by the validation rules.

### Likelihood Explanation
This requires an attacker to (a) front-run the HyperSwap pair for a specific graduating token, (b) fund a mint pre-seed whose `reserveIn`/`reserveOut` combined with the token's specific `tokensForLP`/`ltFromPair` ratio pushes `reserveIn * reserveOut * targetN / targetD` past `2^256`. Because `targetD = ltFromPair` is protocol/market-determined per token and not attacker-controlled to be "small" on demand, and because funding uint112-scale reserves requires substantial capital, this is a real but capital- and setup-intensive attack rather than a trivial one-line exploit — the team's own comments assert "no real call site can construct such inputs because `tokensForLP` and `ltFromPair` are bounded by token supply," which is a claim about the *cached* values, not a hard on-chain bound on the *pre-seeded reserves* that `_pairRebalance` reads. I was not able to fully verify, within the given tool budget, the exact numeric ranges of `ltFromPair` across all possible LT/threshold combinations that would make the overflow condition satisfiable with a realistically fundable pre-seed size — this would need to be confirmed with a targeted fuzz/PoC against the real bounds (`graduationThresholdUsd`, LT `exchangeRate` ranges, `uint112` max) before treating this as conclusively exploitable at low cost.

### Recommendation
Add an explicit, defensive upper bound inside `_noFeeSwapInput` (or in `_pairRebalance` before calling it) that caps `reserveIn`/`reserveOut` read from the live HyperSwap pair to a safe ceiling relative to `targetN`/`targetD`, and fall back to the existing `_seedDirectMint` path (the same fallback already used when the swap rounds to zero) whenever the discriminant would not fit safely in `uint256`, instead of letting the unbounded `Math.mulDiv` call revert and propagate out of `finalizeGraduation`.

### Proof of Concept
A concrete, fully-parameterized PoC (specific `exchangeRate`, `graduationThresholdUsd`, and pre-seed token/LT amounts that satisfy both "fundable by a single attacker" and "discriminant > `type(uint256).max`") could not be completed within the current investigation; the protocol's own `test_overflowSafety_atRealisticMax` test in `packages/contracts/test/NoFeeSwapInput.t.sol` already demonstrates the mathematical mechanism (uint112-scale reserves × token-supply-scale `targetN` overflows `uint256` unless `targetD` is chosen large enough to cancel it) [9](#0-8) , but a full end-to-end reproduction through `Bonding.finalizeGraduation` with attacker-fundable amounts is recommended as a follow-up before treating this as a confirmed, exploitable finding rather than a plausible root-cause hypothesis.

```text
    ///
    ///      `Math.mulDiv` keeps the intermediate product
    ///      `reserveIn * reserveOut * targetN` inside its 512-bit working
    ///      space, but the final result `... / targetD` must still fit in
    ///      uint256. Call sites must keep that invariant — in practice
    ///      both the V2 uint112 reserve cap and the bound that
    ///      `tokensForLP` ≤ `LP_RESERVE` and `ltFromPair` ≤ raised LT
    ///      are well inside the safe envelope. Constructed adversarial
    ///      inputs that violate this would `revert` rather than silently
    ///      truncate, which is the correct failure mode.
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```

```markdown
A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.
```

```markdown
### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`. (truncated)
```
