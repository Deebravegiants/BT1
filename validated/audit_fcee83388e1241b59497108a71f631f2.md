## Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header is not covered by the HMAC signature, allowing cross-tenant webhook forgery via body replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies solely that body against the HMAC header. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers—which the library uses to attribute the webhook to a tenant and dispatch a handler—are never included in the signed data. Anyone who has captured one genuine, HMAC-valid webhook delivery (e.g. a merchant who installed the app on their own shop and inspects its own webhook traffic) can resend that same body+HMAC pair to the app's webhook endpoint with the `shop-domain` header changed to a different (victim) shop, and `Registry.process` will accept it as valid and hand `WebhookMetadata` with the attacker-chosen `shop` to the handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are completely outside of the signed payload: [2](#0-1) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

This breaks the identity binding: `shop authenticated (bytes covered by HMAC) != shop attributed to the event (header value)`. Because the HMAC only proves "this body was signed by Shopify with our secret at some point," and the header carrying the tenant identity is unauthenticated, a body+HMAC pair legitimately generated for shop A's webhook remains valid when replayed with shop B's domain in the header. The library provides no mechanism (e.g., binding `shop` into the signed string, or requiring the caller to independently verify shop/topic against out-of-band data) to prevent this cross-tenant substitution.

### Impact Explanation
This allows an attacker who has legitimate access to one shop (their own, or a shop where they can intercept/replay a webhook delivery) to inject webhook events attributed to any other shop the app also serves, since the `shop` value is not part of the authenticated payload. This is a cross-tenant boundary violation: application logic keyed on `WebhookMetadata#shop` (e.g., updating tenant-specific data, triggering per-shop side effects) can be manipulated to act on behalf of a shop the attacker doesn't control.

### Likelihood Explanation
Exploitation requires possession of one valid `(raw_body, hmac)` pair, which is realistically obtainable by any merchant who installs the app (webhooks are delivered to a URL the merchant/attacker may be able to observe, or via topics like `app/uninstalled` whose bodies are predictable/attacker-influenced) and the ability to send an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No access to the app's `api_secret_key` or any credential is required.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`) header values in the HMAC-signed material used by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the tenant identity to the verified body (e.g., derive `shop` only from a value that Shopify includes inside the signed body/payload, not from a separate unauthenticated header). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant attribution without additional verification (such as confirming the shop against an existing, previously-established session/webhook registration for that topic).

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and registers a webhook handler for `orders/create`.
2. Shopify delivers a legitimate webhook to the app:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B>
   x-shopify-shop-domain: shop-a.myshopify.com
   Body: B
   ```
   Using `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)` and `Registry.process`, this passes `HmacValidator.validate` because it only checks `B` against the HMAC.
3. Attacker captures `(B, hmac)` and resends:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same HMAC>
   x-shopify-shop-domain: shop-b.myshopify.com   # victim shop, unmodified body
   Body: B
   ```
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still succeeds (it only recomputes HMAC over `B`), and `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "shop-b.myshopify.com"`, even though the payload was never actually generated for `shop-b`.
