### Title
Webhook HMAC verification does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC-covered content. `ShopifyAPI::Webhooks::Registry.process` uses `Utils::HmacValidator.validate` to check the signature, then unconditionally trusts `request.shop` (from the untrusted header) as the tenant identity handed to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop` accessor, however, is read straight from an attacker/network-supplied header with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (i.e., the body) and compares it against the `hmac-sha256` header using the app's single `api_secret_key`, which is shared across every shop that has installed the app: [3](#0-2) 

`Registry.process` checks only that HMAC, then dispatches to the handler with `shop: request.shop` taken from the unauthenticated header: [4](#0-3) 

The identity equality that should hold is: `shop-domain header == shop that produced/authorized this body`. Because the HMAC only certifies "this body was signed with this app's secret" and not "this body belongs to this shop," any party that can obtain one valid `(body, hmac)` pair signed with the app's secret can replay it with an arbitrary `shop-domain` header, and the check in `registry.rb:190` will still pass.

The gem's own documentation asserts a security guarantee that the code doesn't provide: `docs/usage/webhooks.md:125` states processing "will verify the request did indeed come from Shopify," when in fact it only verifies the body bytes were signed by the app's secret — not that the claimed shop is the one that produced them.

### Impact Explanation
This is a cross-tenant identity-binding break: `api_secret_key` is a single per-app secret shared by every merchant that installs the app, not a per-shop secret. An unprivileged internet user who installs the public app on their own shop (normal onboarding, no special privilege, no leaked credential, no access token needed) receives real webhooks from Shopify for their own shop, each with a valid `(raw_body, hmac)` pair. They can replay that exact `raw_body`/`hmac` pair to the app's registered webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will accept the HMAC (it never changed) and invoke the handler believing the payload is data belonging to the victim shop — `WebhookMetadata#shop` is exactly the forged value. Any host application that uses `data.shop` to select which tenant's records to update (the very use shown in the gem's own documented example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will write attacker-controlled data into another tenant's records: cross-tenant data injection/corruption.

### Likelihood Explanation
High. No secret material, TLS interception, or elevated privilege is required — only a normal app installation to obtain a legitimately-signed payload, then a single forged HTTP request with a different `shop-domain` header value to the app's public webhook endpoint.

### Recommendation
Bind the tenant identity into the signed content, or otherwise cryptographically verify the shop asserted by the header:
- Extend `to_signable_string` (or add a separate check in `Registry.process`) to bind the `shop-domain`, `topic`, and `webhook-id` headers into the HMAC-verified material, rather than the body alone.
- If Shopify's actual webhook signature spec only signs the body (matching Shopify's real-world webhook behavior), the gem should not claim in `docs/usage/webhooks.md` that this verifies the request "came from Shopify" for a specific shop; instead the library (or host app guidance) must require confirming `request.shop` against a known/registered shop for that specific `webhook_id`/subscription before trusting it for tenant-scoped writes.
- At minimum, update the documentation to explicitly warn that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated header values and must be independently validated by the host application (e.g., cross-checked against the shop that owns the registered `webhook_id`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (ordinary, unprivileged installation flow).
2. Shopify sends a legitimate webhook to the app's endpoint, e.g. body `{"id":123,...}` with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of body, signed with the app's shared api_secret_key>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
3. Attacker captures this `(raw_body, hmac)` pair (e.g., via their own server logs, since it was destined for them).
4. Attacker replays an HTTP POST to the same webhook endpoint URL with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — it still matches.
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, and any host application logic keyed off `data.shop` (as documented in `docs/usage/webhooks.md:26`) processes the attacker's payload under the victim's tenant identity.
