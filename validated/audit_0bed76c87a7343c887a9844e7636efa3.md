### Title
Webhook `shop` identity is taken from an unauthenticated header while only the raw body is covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. The header carrying the shop identity is never included in the signed bytes, so the binding "HMAC-verified bytes == shop identity handed to the app" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is completely independent of the HMAC computation: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the raw body for webhooks): [3](#0-2) 

`Registry.process` validates that HMAC and then immediately hands the handler the header-derived, unauthenticated `request.shop` value as the tenant identity for the webhook payload: [4](#0-3) 

The gem's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is simply "The shop domain of the webhook," with no caveat that this field is unauthenticated: [5](#0-4) [6](#0-5) 

Because the app-level `api_secret_key` is shared across every shop that installs the app, any merchant that legitimately installs the app receives correctly-HMAC-signed webhook deliveries for their own shop. That merchant can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a different (victim) shop's domain that also uses the same app. `HmacValidator.validate` recomputes the signature over the same `raw_body` with the same shared secret and still returns `true`, since the header is not part of the signed string. The handler then processes the payload under the attacker-chosen `shop`, breaking the equality: `shop bound by HMAC` (nonexistent) ≠ `shop trusted by the handler` (attacker-controlled header).

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is a legitimate customer of the app (an unprivileged shop owner, not requiring `api_secret_key`, an access token, or any privileged account) can cause the app to attribute webhook data/events to an arbitrary victim shop of their choosing. Depending on how the host app uses `data.shop` (e.g., to look up/update per-shop records, queue jobs "for" that shop, or make decisions gated on shop identity), this enables cross-tenant data injection or corruption — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that installs on multiple/many shops: any one paying/legitimate merchant using the app can obtain a validly-signed webhook body for their own shop (they receive these constantly), then simply resend the same body with a modified shop header to the app's webhook endpoint — no cryptographic secret is needed, only a body/HMAC pair that they legitimately possess. The library provides no built-in binding of the shop header to the signature, and none of the documented usage warns integrators to independently verify `data.shop` against a shop known to have installed the app or to bind it cryptographically.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or the new-format `shopify-shop-domain`) header as an authenticated identity. Either:
- Include the shop domain in the HMAC-signed input (`to_signable_string`) so header tampering invalidates the signature, or
- Require host applications to cross-check the resolved `shop` against a known/installed shop record (e.g., an existing session for that shop with a still-valid access token) before trusting `data.shop`, and document this requirement clearly in `docs/usage/webhooks.md`.

### Proof of Concept
1. App `AppX` is installed by `attacker-shop.myshopify.com` and by `victim-shop.myshopify.com`, both under the same `api_secret_key`.
2. Shopify sends `AppX` a legitimate webhook for `attacker-shop.myshopify.com`:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
   - Body: `raw_body`
3. Attacker captures `raw_body` and `X-Shopify-Hmac-Sha256` from this delivery (e.g., via a logging proxy they control since it is their own shop's traffic).
4. Attacker POSTs the same `raw_body` and the same `X-Shopify-Hmac-Sha256` value to `AppX`'s webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches, since neither the header nor `to_signable_string` changed.
6. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's original body> ...)`, causing `AppX` to process attacker-controlled webhook content as if it belonged to `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
