## Title
Webhook HMAC only authenticates the request body, not the `shop` header — allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` dispatches webhook payloads to app handlers keyed by `request.shop`, but the HMAC signature that is verified before dispatch only covers the raw request body — it never covers the `shop` value. An attacker who can obtain any single valid `(body, hmac)` pair for the target app (e.g. from their own installed shop) can replay that exact body/HMAC to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop. The library will treat the payload as authentic and attribute it to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an HTTP header with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely against `to_signable_string` (i.e. the raw body): [3](#0-2) 

`Registry.process` gates purely on this body-only HMAC and then forwards the **unauthenticated** `request.shop` value straight to the app's handler: [4](#0-3) 

This is the exact bug class from the report, translated to this gem: the pool-manager bug let an unordered field (asset denom order) diverge from a value assumed to be canonically bound (sorted deposits), corrupting a downstream equality check. Here, `shop` is a field that is *acted upon* (used to attribute/tenant-scope the webhook) but is *not covered* by the authentication primitive (HMAC over body only). The equality the code implicitly assumes — "the shop that receives this HMAC-authenticated payload == the shop the payload is really for" — does not hold, because `shop` is parsed from headers that sit entirely outside the signed bytes.

### Impact Explanation
Any actor who can produce or capture one legitimately-signed `(raw_body, hmac)` pair for the target app (trivially available to them if they run their own shop with the app installed, since Shopify sends them real signed webhooks) can replay it against the app's public webhook endpoint with a forged `shop-domain` header pointing at an arbitrary victim shop. Since the library performs no binding between the verified bytes and the shop attribution, the host application's handler executes believing the event genuinely originated from the victim tenant. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the victim's session/store record and writing order/customer/inventory data, or triggering business logic scoped to that shop), this enables cross-tenant data injection/confusion — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no access to the app's `client_secret`, no privileged account, and no TLS interception — only a single genuine webhook body+HMAC (obtainable by installing/using the app on the attacker's own store, which is normal, unprivileged access) and knowledge of the app's public webhook URL. The replay itself is a simple HTTP POST with a modified header.

### Recommendation
Bind `shop` (and other routing-relevant headers such as `topic`/`webhook-id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the verified body (e.g., include it in `to_signable_string`, or require the host app to independently verify `request.shop` against a known/installed-shop registry before trusting it). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without an out-of-band check.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` computed with the app's secret).
2. Attacker replays the same request to the app's public webhook endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`: [5](#0-4) 
4. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` (from the forged header) even though the payload never actually came from that shop, causing the host app to process/store the event as if it belonged to the victim tenant.
