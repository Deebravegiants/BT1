### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, while the shop, topic, webhook id, and API version used to route and process the webhook are read from unsigned HTTP headers. This breaks the binding between the verified bytes and the tenant (`shop`) the data is attributed to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers that are never included in the HMAC computation: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e. the raw body) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) verbatim to build the `WebhookMetadata` handed to the app's handler, after only checking that the HMAC over the body is valid: [4](#0-3) 

The identity binding that is broken is: `hmac == HMAC(secret, raw_body)` is verified, but the value that downstream code treats as "the shop this payload belongs to" (`shop == request.shop` header) is never included in what's signed. Any attacker capable of sending an HTTP POST to the app's public webhook endpoint with a raw body/HMAC pair they know to be valid (e.g. a webhook body+signature pair for their own shop, since Shopify signs each unique body per delivery, or any captured/replayed valid `(body, hmac)` pair) can freely set `shopify-shop-domain` (or the legacy `x-shopify-shop-domain` header) to an arbitrary victim shop domain, and the header check in `HmacValidator` will still pass because it only checks the body against the same secret — the header is completely outside the signed data.

### Impact Explanation
Any host application built on this gem that uses the `shop` field of `WebhookMetadata` to select which merchant/tenant record to update (the intended and documented use of `WebhookMetadata#shop`) can be made to apply attacker-influenced webhook body data under a victim shop's identity, i.e. cross-tenant data confusion/injection, without possessing that victim's access token or the app's `client_secret`. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) is not part of the cryptographic binding that the library provides and claims to validate (`Errors::InvalidWebhookError, "Invalid webhook HMAC."`).

### Likelihood Explanation
Exploitation requires a valid `(raw_body, hmac)` pair for the shared `api_secret_key`. Since webhook signing uses a single per-app secret (not a per-shop secret), and delivered webhooks for the attacker's own shop are also signed with this same app-wide secret, the attacker can source a valid pair from a webhook delivered to their own shop's install (e.g. a shop they legitimately install the app on), then replay/forge the HTTP request against the app's public webhook endpoint with a different `shopify-shop-domain` header. Likelihood is moderate: it depends on the app exposing a reachable webhook endpoint and using `shop` for tenant routing, which is the standard/documented pattern for this library.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of `to_signable_string`/the value verified against the HMAC, or independently validate that the `shopify-shop-domain` header value matches a shop identifier embedded in the (signed) body/topic before constructing `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is not itself authenticated by the HMAC and must not be trusted for tenant routing without additional verification (e.g. cross-checking against an active session for that shop).

### Proof of Concept
1. App receives a legitimate Shopify webhook for `attacker-shop.myshopify.com` with raw body `B` and header `shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker resends `POST /webhooks` with the same body `B` and same `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` (called in `Registry.process`) only recomputes `HMAC-SHA256(secret, B)` and compares to `H` — it never looks at the `shop` header — so validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and invokes the app's handler, which now processes attacker-supplied body content believing it belongs to `victim-shop.myshopify.com`. [4](#0-3)
