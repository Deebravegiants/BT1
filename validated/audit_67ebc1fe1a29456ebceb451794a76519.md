[1](#0-0) ### Title
Unvalidated route venues can execute attacker contracts under the caller's authorization and steal unrelated wallet assets - (File: `contracts/controller/src/strategies/swap.rs`) [2](#0-1) 

### Summary
The controller accepts an opaque attacker-supplied `swap` payload and forwards it to the configured router without validating which pool or venue contract the route invokes. [3](#0-2) [4](#0-3)  A malicious pool embedded in that route can perform an unauthorized-looking token transfer that is nevertheless included as a child of the victim's signed authorization tree, allowing theft of assets unrelated to the lending position. [5](#0-4) 

### Finding Description
`swap_collateral` takes the raw `swap: Bytes` argument from the caller, authorizes the caller, and passes the payload into `withdraw_and_swap_from_supply`. [6](#0-5) [7](#0-6)  The shared swap boundary only checks that the payload is nonempty, loads the configured router, authorizes one exact input-token transfer, and calls `router.execute_strategy`; it does not decode or constrain pool addresses inside the route. [8](#0-7)  Afterward, the controller checks only measured input spend, positive output, refund of unused input, and final account risk; none of these checks proves that every contract reached by the route was a legitimate venue. [9](#0-8)  Because `StrategySwap` is only opaque bytes, no type-level or controller-level allowlist prevents an attacker from encoding a malicious pool address. [3](#0-2) 

### Impact Explanation
This is theft of user funds rather than merely bad routing or MEV: during the route call, the malicious venue can invoke `wallet_token.transfer(victim, attacker, amount)` for a token that the lending protocol does not list and that was not part of the requested swap. [10](#0-9)  Simulation records that transfer as a child of the victim's controller authorization, and enforcement succeeds if the victim signs the returned tree. [11](#0-10)  The malicious route can still return a positive output and preserve account solvency, so the controller's `NoSwapOutput`, overspend, and final-risk checks do not bound the stolen wallet assets. [9](#0-8) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue, construct a route containing it, and supply that route through a compromised quote provider, phishing flow, wallet integration, or copied transaction payload. [4](#0-3)  Exploitation requires the victim to sign an authorization tree containing the malicious child transfer, which reduces likelihood because an inspecting wallet can reject it. [12](#0-11)  The opaque `Bytes` representation makes the embedded destination contracts difficult for callers and clients to meaningfully review before signing. [3](#0-2) 

### Recommendation
Do not treat arbitrary route-selected contract addresses as trusted venue implementations. Decode and validate the route on-chain or restrict hop destinations to a governance-managed venue/pool registry before calling `execute_strategy`; alternatively, change the router API to accept structured venue identifiers resolved against such a registry rather than caller-supplied pool addresses. [13](#0-12)  Clients should also reject authorization trees containing any child invocation other than the expected input transfer, but protocol-side destination validation is required because signed opaque routes otherwise remain exploitable. [11](#0-10) 

### Proof of Concept
1. The attacker deploys a contract exposing the expected pool call interface for a supported venue and pre-funds it with enough `token_out` to satisfy a positive measured output.
2. The attacker encodes that contract as a hop destination inside a `swap` payload for a route from the victim's supplied collateral to a listed destination asset.
3. The victim invokes:

```text
Controller::swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = HubAssetKey { hub_id, asset = USDC },
    amount = collateral_amount,
    new = HubAssetKey { hub_id, asset = ETH },
    swap = attacker_payload,
)
```

The public entrypoint forwards that opaque payload into the strategy path. [14](#0-13) [7](#0-6) 

4. The controller authorizes only the legitimate collateral input transfer to the router, but the route invocation reaches the attacker's pool contract. [2](#0-1) 
5. Inside that call, the malicious pool pays a valid `token_out` amount and additionally calls `wallet_token.transfer(victim, attacker, victim_balance)` for an unrelated wallet token.
6. Simulation records the extra transfer beneath the victim's authorization root; signing that tree makes the transfer execute, while the swap still produces positive output and can pass the controller's final account checks. [5](#0-4) [15](#0-14)
