### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but the `shop`, `topic`, and `webhook_id` fields consumed by `ShopifyAPI::Webhooks::Registry.process` and handed to app handlers are read from unauthenticated HTTP headers that are never part of the signed data. An attacker who possesses one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own shop and receiving a legitimate webhook — can replay that exact body/HMAC to the app's webhook endpoint while forging the `shop-domain` header to claim it belongs to a different shop, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from headers that are not part of the signable string: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)` — i.e., against the body bytes alone: [3](#0-2) 

`Registry.process` accepts the request once this body-only signature validates, then constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, and dispatches it to the app's handler: [4](#0-3) 

The binding broken is: **shop verified by the HMAC (none — the body only) ≠ shop acted upon (`request.shop`, taken from the unauthenticated header and passed to the handler as the tenant identifier)**. Because the body itself does not always encode the shop, and because the header is excluded from the signed payload, the digest that authenticates "this payload came from Shopify for the api_secret_key holder" says nothing about which shop the payload is for.

### Impact Explanation
An attacker who has (or creates) their own shop installation of the victim's app receives a real webhook: a valid `raw_body` + matching `hmac` for a topic of their choosing (e.g. `app/uninstalled`, `orders/create`, `customers/data_request`). They can then replay that identical body and HMAC to the same public webhook endpoint while setting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a *different* shop. `HmacValidator.validate` still succeeds because it never inspected the header, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any handler logic that uses `shop` from the webhook metadata as the tenant key (to look up sessions, gate access, trigger data deletion/export flows, or update per-shop state) is now acting on attacker-controlled tenant identity while believing it passed HMAC authentication — a cross-tenant boundary crossing.

### Likelihood Explanation
Any developer using an app is entitled to install it on their own store and thus obtain at least one legitimate `(raw_body, hmac)` pair for a topic they choose to trigger (e.g. simply installing/uninstalling the app, placing a test order). Replaying that pair with a modified `shop-domain` header against the app's public webhook endpoint requires no secrets beyond what a legitimate merchant already has access to, so this is trivially reachable by any unprivileged internet user who has installed the app once.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the signable payload verified by the HMAC (or otherwise cryptographically bind them, e.g. by re-deriving/cross-checking `shop` against a value embedded and signed in the body), so that `HmacValidator.validate` fails if any of these header-derived fields are altered relative to what Shopify actually signed for that specific shop/topic/delivery. At minimum, document that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com` and trigger a webhook (e.g. `app/uninstalled`) to capture a legitimate `raw_body` and its `x-shopify-hmac-sha256` header — both computed with the real `api_secret_key`, unknown to the attacker but not needed since they are reused verbatim.
2. Send a forged HTTP request to the same app's webhook endpoint with:
   - the captured `raw_body` unchanged,
   - the captured `x-shopify-hmac-sha256` unchanged,
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (arbitrary),
   - `x-shopify-topic` and `x-shopify-webhook-id` optionally altered.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from and pertains to `attacker.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
