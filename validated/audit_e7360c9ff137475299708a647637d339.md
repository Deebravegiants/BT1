### Title
Rounding drift from `Pair.swap`'s `+1` K-slack can push a curve's stored `assetReserve` below the recovered launch-time virtual LT reserve, causing a permanent underflow-revert DoS in `Bonding.canGraduate` — ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding` recovers the launch-time virtual LT reserve on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` and unconditionally subtracts it from the pair's *stored* `assetReserve` in three places (`canGraduate`, `previewLtUntilGraduation`, `_prepareGraduationLiquidity`) to get the "real LT raised." [1](#0-0) [2](#0-1)  This subtraction implicitly assumes `assetReserve >= virtualLtReserve` always holds. That assumption relies on `Pair`'s constant-product invariant being conserved exactly, but `Pair.swap` only enforces the invariant with a `+1` slack per side, `(newTokenReserve + 1) * (newAssetReserve + 1) >= _pool.k`, rather than requiring the exact product `>= k`. [3](#0-2)  `Router._computeSell` computes `assetOut = reserveAsset - (k / newReserveToken)` using floor division, which rounds `k/newReserveToken` down and therefore rounds `assetOut` up (in favor of the seller) exactly within the tolerance this slack permits. [4](#0-3)  An unprivileged trader who repeatedly round-trips small buy/sell cycles through `Zap.buy`/`Zap.sell` can accumulate this one-directional rounding drift, incrementally reducing the pair's stored `assetReserve` relative to the true, K-conserving value, until it falls below the immutable `virtualLtReserve` recovered from `Pair.k() / TOTAL_SUPPLY()`.

### Finding Description
`Bonding` never stores its own copy of the launch-time virtual LT reserve; instead it re-derives it on every call via `_launchTimeVirtualLtReserve`, trusting the identity `Pair.k() == TOTAL_SUPPLY * virtualLtReserve_init` to hold forever because `Pair.mint` sets `_pool.k` once and `Pair.swap` "never modifies" it. [5](#0-4)  That part is true — `k` itself is untouched by `swap`. What is not guaranteed is that `assetReserve` can never drop below this recovered value, because `swap`'s invariant check tolerates a small violation of the exact constant-product rule:

```solidity
uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
``` [6](#0-5) 

`Router._computeSell` passes `assetOut` computed by floor-dividing `k` by the post-trade token reserve and subtracting from the current `reserveAsset`:

```solidity
uint256 newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
``` [4](#0-3) 

Because `k / newReserveToken` is floor-rounded, the trader is paid an `assetOut` that is at or slightly above the exact K-conserving amount — this is precisely what the `+1` slack in `swap` was added to tolerate. Every completed sell can therefore extract marginally more LT from the pair than a pure constant-product AMM would allow, monotonically eroding `assetReserve` relative to the true invariant. Repeating buy/sell round trips (each individually harmless and within the `KInvariantViolated` check) accumulates this drift in one direction only, with no counteracting mechanism, until `assetReserve` — which started life equal to `virtualLtReserve` at `Pair.mint` time — falls below `virtualLtReserve` itself.

Once that happens, the checked-arithmetic subtraction

```solidity
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [7](#0-6) 

underflows and reverts. `canGraduate()` is documented as being checked "at the end of every buy inside `_executeBuy`", so this permanently breaks `Zap.buy`/`Bonding.buy` for the affected token going forward. [8](#0-7)  The same subtraction pattern exists in `previewLtUntilGraduation` and `_prepareGraduationLiquidity`, so `Zap.sell`'s already-graduatable path (which calls `canGraduate`/`triggerGraduation`) and the final graduation itself are also permanently blocked, trapping the pair's remaining tokens and any already-raised LT (LT sitting in `Pair`, unreachable once trading and graduation are both bricked). [9](#0-8) [10](#0-9) 

### Impact Explanation
This is a permanent, unrecoverable freeze of a token's bonding curve: no admin function exists to reset `assetReserve` or the recovered `virtualLtReserve` once the drift crosses the threshold. Trading (`buy`) is blocked outright by the revert in the post-buy `canGraduate` check, `sell`-triggered graduation reverts the same way, and the token can never reach the supply or USD graduation trigger because every code path that would decide graduation first performs the same unguarded subtraction. This freezes the LT already raised inside `Pair` (unreachable — `Router.graduate` is only invoked from `_prepareGraduationLiquidity`, which itself reverts) as well as any creator/protocol fee flow tied to further trading of that token.

### Likelihood Explanation
The drift is strictly one-directional (always shrinks `assetReserve` relative to the exact invariant, never grows it back), is triggerable purely through `Zap.buy`/`Zap.sell` calls available to any unprivileged wallet, and requires no special preconditions beyond enough round trips. The per-transaction drift is bounded by the rounding slack (on the order of a few wei per trade given `k`'s scale), so the number of transactions required to exhaust the gap between `assetReserve` and `virtualLtReserve` on a freshly-launched, thinly-traded pair could be large but is not bounded by any protocol-level circuit breaker or minimum-drift protection — it is purely a function of gas cost and time, both of which are attacker-controlled on HyperEVM.

### Recommendation
- Tighten `Pair.swap`'s invariant check to require the exact (non-slack) constant-product relation, or clamp `Router._computeSell`/`_computeBuy` to always round strictly against the trader (ceil for LT owed, floor for LT paid out) so no rounding path can ever extract more than the exact K-conserving amount.
- In `Bonding._launchTimeVirtualLtReserve`/`canGraduate`/`previewLtUntilGraduation`/`_prepareGraduationLiquidity`, replace the raw subtraction with a saturating subtraction (`assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0`) so drift cannot brick graduation logic or buy/sell flows, and add an invariant test that fuzzes many round-trip buy/sell sequences to assert `assetReserve` never falls below the recovered `virtualLtReserve`.

### Proof of Concept
1. Launch a token via `Bonding.launch(...)`, recording `virtualLtReserve0 = Pair.k() / Token.TOTAL_SUPPLY()` immediately after `_deployAndSeed`.
2. As an unprivileged trader, repeatedly call `Zap.buy(token, smallUsdcAmount, 0, address(0))` immediately followed by `Zap.sell(token, tokensReceived, 0)` for a large number of iterations (sized to the rounding slack observed in `Router._computeSell`/`swap`'s `+1` tolerance).
3. After each round trip, read `(reserveToken, reserveAsset) = IPair(pair).getReserves()` and compare `reserveAsset` against the constant `virtualLtReserve0`; confirm it strictly decreases over iterations even though `tokenReserve` returns to its pre-round-trip value.
4. Continue iterating until `reserveAsset < virtualLtReserve0`, then call `Bonding.canGraduate(token)` (or perform one more buy through `Zap.buy`) and observe the transaction revert with an arithmetic underflow inside `_launchTimeVirtualLtReserve`'s consumer, permanently blocking further buys/sells and graduation for that token.

    function previewLtUntilGraduation(
        address token_
    ) external view returns (uint256) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return 0;
        if (info.lifecycle != Lifecycle.Curve) return 0;

        address pair = info.pair;
        uint256 realBalance = IPair(pair).tokenBalance();
        if (realBalance == 0) return 0;

        (uint256 reserveToken, uint256 reserveAsset) = IPair(pair).getReserves();

        uint256 ltUntilThreshold = type(uint256).max;
        uint256 exchangeRate = IBounceLeveragedToken(info.ltAddress).exchangeRate();
        if (exchangeRate > 0) {
            uint256 realLtRaised = reserveAsset - _launchTimeVirtualLtReserve(token_, pair);
            uint256 thresholdRealLt = ($.graduationThresholdUsd * 1e18 + exchangeRate - 1) / exchangeRate;
            if (realLtRaised >= thresholdRealLt) return 0;
            ltUntilThreshold = thresholdRealLt - realLtRaised;
        }

        // Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
        if (realBalance >= reserveToken) return ltUntilThreshold;

        uint256 cappedReserveToken = reserveToken - realBalance;
        uint256 cappedReserveAsset = (IPair(pair).k() + cappedReserveToken - 1) / cappedReserveToken;
        uint256 ltUntilSupply = cappedReserveAsset - reserveAsset;

        return ltUntilSupply < ltUntilThreshold ? ltUntilSupply : ltUntilThreshold;
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    /// @dev Recovers the launch-time virtual LT reserve from immutable
    ///      identities: `Pair._pool.k = tokenReserve_init * assetReserve_init
    ///      = TOTAL_SUPPLY * virtualLtReserve_init` is set ONCE in
    ///      `Pair.mint` and never modified by `Pair.swap` (swap only
    ///      mutates `tokenReserve` / `assetReserve` and asserts K-floor).
    ///      So `Pair.k() / Token.TOTAL_SUPPLY()` returns the exact
    ///      `virtualLtReserve` that was passed to `addInitialLiquidity` at
    ///      launch — for any pair, in any phase, with no storage of our own.
    ///
    ///      Going through this derivation rather than a stored mirror
    ///      eliminates an admin-writable economic-state slot and makes the
    ///      donation-immunity property a pure consequence of the pair's
    ///      already-immutable accounting. The `TOTAL_SUPPLY`-equality check
    ///      in `setTokenImplementation` keeps the divisor consistent across
    ///      impl rotations, so tokens launched under different
    ///      `tokenImplementation` versions still derive the same way.
    function _launchTimeVirtualLtReserve(
        address token_,
        address pair_
    ) internal view returns (uint256) {
        return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
    }
