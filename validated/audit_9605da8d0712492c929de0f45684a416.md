### Title
Emporium's zero-token "message-only" proof path lets an unprivileged EOA drain any dust balance held by the Emporium contract with no signature check and no balance accounting - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` switches to the minimal input builder `formInputEmporiumMin`, which produces only `[emporiumMessage, timeStamp, calldataHash]` as public signals [1](#0-0) . Because `erc20TokenAddresses` is empty, `Hinkal.transact()`'s per-token balance/slippage equation loop never executes for this call [2](#0-1) , and `EmporiumUpgradeable.runAction`'s own before/after balance accounting loop is likewise driven by the same empty `circomData.erc20TokenAddresses` array [3](#0-2) . Additionally, `verifyWallet` only marks the `emporiumMessage` as used and returns immediately, skipping the EIP-712 signature check entirely, whenever `stack.signerAddress == address(0)` [4](#0-3) . In that combination (`erc20TokenAddresses = []`, `signerAddress = address(0)`), any caller who can obtain a valid Groth16 proof for the zero-token-dimension circuit variant can push `stack.ops` through `runAction`'s "CASE 2: Stateless Interaction" branch, which executes arbitrary `op.endpoint.call{value: op.value}(op.callData)` [5](#0-4) , with zero accounting of what balance is spent.

### Finding Description
The balance equation Hinkal is supposed to enforce is: `balanceDif == amountChanges[i] (or 0 if onChainCreation) + sum(utxoAmount for token i)`, checked per-token inside the `for` loop over `circomData.erc20TokenAddresses` in `Hinkal.transact()` [6](#0-5) . This equality is the on-chain guarantee that whatever ETH/ERC20 balance change happens during `_externalTransact` is fully backed by proven shielded amount changes and/or freshly created out-UTXOs.

When `erc20TokenAddresses.length == 0` (the "Emporium message-only" mode), this loop's iteration count is zero, so the equality is never evaluated at all for this call - not "trivially satisfied", but literally skipped. The public-input vector fed to the verifier for this mode is only `[emporiumMessage, timeStamp, calldataHash]` [7](#0-6) , none of which encode a specific token, amount, nullifier, or root-hash constraint tying the proof to spending any particular shielded balance owned by the caller. This satisfies the rule-defined analog class: "a `CircomData` field acted on but outside `calldataHash`/`signedMessageHash`/the public-input vector" and "value moved ... but not counted in the balance equation."

Inside `EmporiumUpgradeable.runAction`, the same empty `circomData.erc20TokenAddresses` array is used to compute `balancesBefore`/`balancesAfter` and to build `utxoSet`, so the entire post-call reconciliation (`balanceChange < 0` revert, `handleOut`) is likewise a no-op for zero-length arrays [8](#0-7) . Yet the `stack.ops` loop still runs unconditionally and unconditionally executes `op.endpoint.call{value: op.value}(op.callData)` for any op that is not `invokeWallet` (or is `invokeWallet` with `signerAddress == address(0)`, which the code explicitly permits as "CASE 2") [9](#0-8) .

Because `signerAddress == address(0)` also makes `verifyWallet` skip the EIP-712 signature check completely [10](#0-9) , the only remaining gate is `onlyAllowedRecipient` on `runAction` (which is satisfied automatically because `Hinkal.sol` itself, the only allowed recipient, calls it) and a valid ZK proof over the minimal 3-signal public input, which carries no per-user secret binding. This is the "transferFrom / wallet op not authorised by the prover or signer" analog: the `op.endpoint.call` moving Emporium's existing token/ETH balance is authorised by neither a wallet signature nor a proof that ties it to any specific depositor's shielded funds.

The Emporium contract is explicitly documented to sometimes hold a residual balance across calls ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call" [11](#0-10) ), i.e. dust/in-flight funds are expected to accumulate there. Any such balance is drainable by an attacker using the zero-token message path.

### Impact Explanation
Funds sitting in the Emporium contract (dust left from prior swaps/calls, or value in-flight during a multi-op sequence) can be moved to an attacker-chosen address via an arbitrary `call`, with no balance equation enforced by either `Hinkal.transact()` or `EmporiumUpgradeable.runAction`, and no signer authorization required. This is theft of protocol/user funds held in the Emporium contract without the wallet owner's or prover's authorization, matching the High/Critical impact bar ("executing calls or moving assets a wallet owner or prover never authorised" / "theft ... of protocol/relay fees" / "temporary freezing of user funds").

### Likelihood Explanation
Exploitation requires only: (1) obtaining a valid Groth16 proof for the zero-token-dimension circuit variant whose public signals are just `emporiumMessage`, `timeStamp`, `calldataHash` - values fully controlled by the caller, not secret witness data tied to a specific user's shielded UTXOs, and (2) crafting an `EmporiumStack` with `signerAddress = address(0)` and one or more `ops` targeting `op.endpoint.call`. No admin, relayer, or victim key is needed. The main uncertainty is whether the corresponding Circom circuit for this zero-token dimension enforces some additional ownership constraint not visible in the indexed circuit files (no `circuits/**` file matching "Emporium"/"emporiumMessage" was found in this repo's indexed content, so this could not be fully confirmed from circuit code, only inferred from the Solidity-side public-input construction).

### Recommendation
For the `erc20TokenAddresses.length == 0` Emporium path, either (a) forbid `signerAddress == address(0)` entirely (always require an EIP-712-signed message from a specific wallet before allowing `stack.ops` execution), or (b) require `runAction`/`Hinkal.transact()` to still enforce a balance-conservation check on any token/ETH balance the Emporium contract holds before and after the call regardless of `erc20TokenAddresses` length, so that no un-owned value can leave the contract without being attributed to a specific depositor's proof or signature.

### Proof of Concept
Conceptual sequence (Solidity-level, since circuit-level proof generation for the zero-token dimension could not be verified in-repo):
1. Some ETH/ERC20 balance accumulates in the deployed `EmporiumUpgradeable` proxy (acknowledged as a normal occurrence per the code comment at `EmporiumUpgradeable.sol:141-144`).
2. Attacker (any EOA) builds `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: <attacker-controlled/ERC20>, invokeWallet: false, value: <drain amount>, callData: <transfer to attacker> }], ... })`.
3. Attacker computes `calldataHash` per `CircomDataBuilder.getHashedCalldata` and obtains/derives a Groth16 proof matching `formInputEmporiumMin`'s 3-signal public input for the zero-token verifier variant.
4. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)`.
5. `Hinkal.transact()`'s balance-equation loop (`Hinkal.sol:97-147`) does not execute because `erc20TokenAddresses.length == 0`.
6. `_externalTransact` calls `EmporiumUpgradeable.runAction`, which skips the EIP-712 check (`verifyWallet` early-returns for `signerAddress == address(0)`), executes `op.endpoint.call{value: op.value}(op.callData)` transferring Emporium's balance to the attacker, and its own post-call balance loop is also a no-op due to the empty token array.
7. Attacker keeps the drained funds; no nullifier, root check, or signature ever constrained this specific value transfer.

        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
