### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that raw body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are pulled straight from unauthenticated HTTP headers and are never included in the signable string [2](#0-1) . `Registry.process` validates only the HMAC of the body and then dispatches the handler using the untrusted `request.shop` value as the tenant identity [3](#0-2) . This is the same class of bug as the reported `node.extend` issue: a value that downstream code treats as trusted/bound to an identity (there, `Object.prototype`; here, the `shop` tenant) is actually derived from data that was never covered by the integrity check that "proved" the message was legitimate.

### Finding Description
The identity binding that should hold is:
`hmac_verified_body == body_attributed_to(shop)`

In `HmacValidator.validate_signature`, the only bytes verified are `verifiable_query.to_signable_string`, which for `Webhooks::Request` is `@raw_body` alone [4](#0-3) . The `shop` accessor used by `Registry.process` to build `WebhookMetadata` (and thus route the payload into the host app's per-tenant logic) comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed data [5](#0-4) .

Because the header is never authenticated, an attacker who can obtain any one valid `(raw_body, hmac)` pair for the configured `api_secret_key` — trivially achievable by installing the app on their own store and capturing a real webhook Shopify sends them — can replay that exact body/HMAC pair while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` will invoke the app's handler believing the event originated from the victim tenant [3](#0-2) .

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select which tenant's data/session to update (the documented and expected usage pattern shown in the gem's own webhook docs) can be made to apply attacker-controlled webhook content under another merchant's identity — a cross-tenant integrity violation. This matches the "Critical - cross-tenant access" impact category, since the library's own API for identifying "which shop this webhook is for" is not authenticated even though the API promises the request "did indeed come from Shopify" once `Registry.process`/`HmacValidator.validate` succeeds.

### Likelihood Explanation
Exploitation requires only unprivileged actions: create/install the app on an attacker-owned store (no credentials, access tokens, or `api_secret_key` needed), capture one legitimate webhook delivery for that store, then resend it to the app's webhook endpoint with a forged `shop-domain` header. No secret material or elevated access is required from the attacker.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the data that is authenticated before they are trusted — e.g., have `Registry.process` compare `request.shop` against the shop associated with the currently active/stored session for this delivery, or otherwise document/enforce that host apps must not treat the `shop` header as authenticated without independently verifying it against a known, previously-registered shop for that webhook subscription.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and waits for (or triggers) a real webhook, e.g. `orders/create`, capturing the raw POST body `B` and the `X-Shopify-Hmac-SHA256` header `H` that Shopify sent.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with the identical raw body `B` and identical `X-Shopify-Hmac-SHA256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `B` only, matches `H`, and returns `true` [6](#0-5) .
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, and invokes the app's handler as if the event legitimately came from the victim shop [7](#0-6) .
