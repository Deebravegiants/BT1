This confirms the vulnerability: `WrappedHyperFungibleToken.send()` (and its upgradeable variant) locks the underlying token via `safeTransferFrom(msg.sender, address(this), params.amount)` but never checks the actual amount received — it always dispatches `params.amount` as the message body. In stark contrast, the `IntentGatewayV2.sol` intents contracts in this same repo explicitly compute `received = balanceAfter - balanceBefore` to defend against exactly this class of bug (see the `FeeOnTransferToken` tests). This gap was clearly known to the team elsewhere in the codebase but was not applied to `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`.

### Title
Fee-on-transfer underlying tokens cause escrow under-collateralization and repeated cross-chain over-minting/unlocking in `WrappedHyperFungibleToken` - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom` for `params.amount`, but dispatches the cross-chain message using the requested `params.amount` rather than the amount actually received by the contract. For fee-on-transfer or deflationary tokens, the contract's locked balance is smaller than the amount credited on the destination chain, permanently under-collateralizing the bridge.

### Finding Description
In `send()`: [1](#0-0) 
the ERC20 branch calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` without measuring the contract's actual balance delta. The `_buildDispatchPost` function then encodes `params.amount` (the pre-fee, requested amount) into the cross-chain `Message`: [2](#0-1) 

If the underlying ERC20 token charges a transfer fee (deducts a percentage on `transferFrom`), the wrapper contract receives less than `params.amount`, yet the destination-chain peer (either another `WrappedHyperFungibleToken` unlocking underlying, or a `HyperFungibleToken` minting synthetic supply) will unlock/mint the full, unreduced `params.amount` on `onAccept`: [3](#0-2) 

This is the identical bug class as the referenced Teller `CollateralEscrowV1` finding: the contract stores/uses a caller-specified `_amount` instead of verifying actual tokens held, so post-fee reality diverges from accounted state. Here the consequence is amplified because the model is a cross-chain lock/mint(-or-unlock) bridge — the divergence directly creates unbacked value on the destination chain rather than merely a local shortfall.

The same pattern also exists in `WrappedHyperFungibleTokenUpgradeable.send()`: [4](#0-3) 

Notably, the sibling `IntentGatewayV2.sol` contracts in this same repository already defend against this exact issue by measuring `balanceAfter - balanceBefore` around every `transferFrom`/sweep (`evm/src/apps/IntentGatewayV2.sol` lines 291-323), and the project has explicit fee-on-transfer regression tests (`FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`). No equivalent protection exists for `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`.

### Impact Explanation
Each `send()` call with a fee-on-transfer underlying token locks `received < params.amount` on the source chain but authorizes `params.amount` to be released (unlocked or minted) on the destination chain. Repeated use permanently drains the source-chain escrow relative to circulating claims on other chains: the first users to withdraw/unlock on the destination side can fully redeem, while later legitimate holders find the source-chain contract insolvent (unable to unlock the promised amount), or in the burn/mint (`HyperFungibleToken`) direction, the amount minted permanently exceeds the underlying actually locked, creating unbacked synthetic supply. This is a direct, unbacked-mint / permanent-fund-freezing class issue reachable by any unprivileged user simply calling `send()` with such a token configured as `_underlying`.

### Likelihood Explanation
Triggering the bug requires only that the deployment's `_underlying` token (configured once via `configure()`, an owner action, but the vulnerability is exploitable by any ordinary user thereafter) applies a transfer fee — a well-known and common ERC20 pattern. Any user calling the permissionless `send()` function with such a token immediately creates the discrepancy; no special privileges or race conditions are needed to trigger it, only to have such a token configured as the wrapped underlying.

### Recommendation
Measure the actual amount received by comparing `_underlying` balance before and after the `safeTransferFrom` call in `send()`, and use that measured amount (not `params.amount`) both for the encoded cross-chain `Message.amount` and the `Sent` event — mirroring the balance-delta pattern already used in `IntentGatewayV2.sol`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a token that deducts a 1% fee on `transferFrom` (e.g., the `FeeOnTransferToken` test contract already present in this repo at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2690-2735).
2. User calls `send({dest, to, amount: 1000e18, timeout, relayerFee, data: ""})`.
3. `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), 1000e18)` executes; due to the 1% fee, the contract's actual underlying balance increases by only 990e18.
4. `_buildDispatchPost` encodes `Message.amount = 1000e18` (the requested amount, not the 990e18 received) and dispatches the cross-chain POST request.
5. On the destination chain, the peer's `onAccept` unlocks/mints `1000e18` to the beneficiary — 10e18 more than was ever actually locked on the source chain.
6. Repeating this leaves the source-chain contract holding strictly less underlying than the sum of amounts it has promised across all destination chains, so a later legitimate unlock/withdrawal reverts due to insufficient balance (funds frozen) or, in the mint direction, permanently un-backed synthetic supply exists.
