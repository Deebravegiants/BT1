### Title
Webhook shop identity not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw request body only. The `shop` (and `topic`, `api_version`, `webhook_id`) values are taken from HTTP headers that are never included in the signed content. `Webhooks::Registry.process` trusts `request.shop` as the tenant identity when dispatching to the app's handler, without any additional verification that the signed body actually originated for that shop. This mirrors the reported bug class: "a field acted on but not covered by the HMAC."

### Finding Description
`HmacValidator.validate` verifies a `VerifiableQuery` by recomputing `OpenSSL::HMAC.hexdigest` over `to_signable_string` and comparing it to the supplied `hmac`. [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw HTTP body (`@raw_body`), while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers (`x-shopify-shop-domain`, etc.) with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unauthenticated header value) to the app's handler as the tenant identity, with no separate check that this shop matches the shop the body was actually signed for: [3](#0-2) 

The identity binding this breaks, stated as an equality that should hold but doesn't:
`shop_the_body_was_signed_for == shop_header_value_trusted_by_the_app`

Because the HMAC only proves "this body was produced using our `api_secret_key`," and any merchant who installs the app can legitimately trigger webhooks for their own shop (e.g. `orders/create`, `app/uninstalled`, or mandatory compliance topics), an attacker-merchant can capture one of their own validly-signed webhook deliveries (valid body + valid HMAC, since Shopify itself signed it with the real secret for the attacker's own shop) and replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it never inspected the header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop as the source of attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity confusion: the application's webhook handler (which typically looks up the victim's stored session/access token by `shop`, updates the victim's records, or — for mandatory topics like `customers/redact`/`shop/redact` — performs destructive actions) executes using a shop identity that was never actually validated against the signed payload. An attacker who legitimately controls one shop can inject data/events attributed to any other merchant using the app, without needing that merchant's access token or secrets. This qualifies as cross-tenant access per the impact criteria.

### Likelihood Explanation
Requires only: (1) the attacker installs the target app on a shop they control (a normal, low-privilege action any Shopify merchant can take), (2) they capture one legitimately-signed webhook delivery for their shop (via their own server logs/proxy), and (3) they resend it to the app's public webhook endpoint with a modified shop header. No secret key, access token, or victim credentials are needed — this is exploitable by an ordinary internet-facing attacker who can register a dev/trial shop.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-validated, or independently verify that the header-supplied `shop` corresponds to a shop for which this exact signed body/webhook-id combination was issued (e.g., cross-check against `webhook_id` uniqueness plus a shop-scoped secret, or bind shop into the signable string if Shopify's webhook contract allows it). At minimum, document that `Webhooks::Request#shop` is unauthenticated and must not be trusted as a tenant boundary without additional server-side verification (e.g., confirming the shop has an active installation/session before acting on webhook content).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g. updates an order) causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint; attacker captures the raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC(api_secret_key, B)`).
3. Attacker replays the identical `B`/`H` to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only and succeeds.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, causing the app to process/store attacker data under the victim tenant's identity.
