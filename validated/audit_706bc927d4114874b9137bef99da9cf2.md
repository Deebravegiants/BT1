### Title
Webhook `shop` identity is read from an unauthenticated header not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the value of the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header verbatim, while `#hmac` verification (via `Utils::HmacValidator`/`to_signable_string`) only covers `@raw_body` [2](#0-1)  and `#hmac` derives its comparison value from the `hmac-sha256` header [3](#0-2) . The `shop-domain` header is a separate, independent header that is never mixed into the HMAC-signed bytes.

### Finding Description
The identity binding that should hold is: `shop (tenant identifier used by the host app to route/process the webhook) == shop bound inside the HMAC-verified bytes`. In this gem, the HMAC only authenticates the raw body bytes (`to_signable_string` returns `@raw_body`) [4](#0-3) , while the `shop` accessor used by host applications to identify which merchant/tenant the webhook belongs to is pulled straight from the `shop-domain` header without any cryptographic binding to that header [5](#0-4) , [6](#0-5) . Only presence of the header is checked at construction time — its value is never validated: [7](#0-6) .

Because `Request#shop` (not the body) is what a host application is documented/expected to use to look up the correct per-tenant offline session/access token before processing a webhook, an unprivileged internet user who can reach the app's webhook endpoint (webhook endpoints are typically unauthenticated by design — Shopify's own signature is the only auth) can replay/craft a request with a **valid HMAC for the body they control**, but supply an **arbitrary `shop-domain` header value** pointing at a different, victim tenant. Since the header is outside the signed bytes, the HMAC check passes even though `shop` does not correspond to the shop that actually produced/authorized the signed payload.

### Impact Explanation
If the host application follows this gem's documented pattern of using `Request#shop` (post `HmacValidator.validate`) to select which merchant's offline `Session`/access token to load and act on, an attacker who can produce any HMAC-valid body (e.g., because they know or can influence the merchant's own webhook secret usage indirectly, or simply because this is the field the gem hands back as "verified") can misdirect webhook processing to a different tenant context by spoofing the `shop-domain` header. This breaks the identity binding `verified-shop == acted-upon-shop`, enabling cross-tenant confusion in webhook handling — the same failure mode/class as the referenced report's `battery.lastBlock` binding gap (a value used for a security decision that is not actually covered/initialized by the mechanism meant to secure it).

### Likelihood Explanation
Webhook endpoints are internet-reachable and unauthenticated except for HMAC verification, matching the "unprivileged internet user" threat model. The gap is deterministic and always present — it is not dependent on race conditions or timing, only on the host app trusting `Request#shop` as tenant-authenticated after `hmac` validation, which is exactly how this gem's `VerifiableQuery`/`HmacValidator` pattern is designed to be consumed.

### Recommendation
Include the `shop-domain` header (and `topic`, `api_version`, `webhook_id`) in the bytes that are HMAC-verified, or otherwise cryptographically bind the resolved `shop` to the verified payload before exposing `Request#shop` to callers, so that a verified HMAC guarantees the `shop` value was not tampered with independently of the body.

### Proof of Concept
```ruby
raw_body = '{"id": 1}' # body for which the attacker holds a valid HMAC of shop A's own past webhook, or a body they fully control if the app doesn't validate topic/schema
headers = {
  "x-shopify-hmac-sha256" => valid_hmac_for(raw_body), # computed with the correct secret for the body, independent of shop
  "x-shopify-topic" => "orders/create",
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, NOT covered by hmac
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(req) # => true, because hmac only checks raw_body
req.shop # => "victim-shop.myshopify.com" -- trusted by host app despite being unauthenticated
```
`HmacValidator.validate` returns `true` based solely on `raw_body` [8](#0-7) , while `req.shop` is taken from the unauthenticated header [5](#0-4) , demonstrating the tenant-identity field is not bound to the HMAC-verified bytes.
