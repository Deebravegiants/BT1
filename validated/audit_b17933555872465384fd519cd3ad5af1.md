### Title
Escrow withdrawal reverts entirely if any single escrowed token blocks the beneficiary, permanently freezing the whole order - ([File: evm/src/apps/intentsv2/IntentsBase.sol], [File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentsBase._withdraw` and `IntentGatewayV2.withdraw` both release an order's escrowed tokens to a single beneficiary by looping over `body.tokens` and transferring each one in turn. Because the loop performs the transfers unconditionally and reverts the whole function on any single transfer failure, a beneficiary who is blocklisted, paused, or otherwise reverted by just one of the escrowed tokens can never redeem (or be refunded) any of the tokens in that order — including tokens they are perfectly able to receive.

### Finding Description
`IntentsBase._withdraw` iterates the withdrawal request's token list and calls `IERC20(token).safeTransfer(beneficiary, amount)` for every non-zero entry, reverting the entire call (and thus the whole withdrawal, including unrelated tokens and the final `finalize`/`fee` payout) if any single transfer reverts: [1](#0-0) 

The same pattern exists in the Tron `IntentGatewayV2.withdraw`, which performs a low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and explicitly reverts with `TransferFailed()` if any single transfer in the loop fails: [2](#0-1) 

This `withdraw`/`_withdraw` path is reached from message-driven entry points that are triggered by a single relayed ISMP message or proof — e.g. `onGetResponse` for a cross-chain refund: [3](#0-2) 

and from the `RedeemEscrow`/`RefundEscrow` request kinds processed in `onAccept`, which decode a `WithdrawalRequest` (a beneficiary plus an arbitrary array of escrowed tokens, some of which may be attacker-controlled ERC20s that the order filler/solver has no control over) and hand it straight to `withdraw`/`_withdraw`.

Because escrow orders can list multiple output tokens and any one of them can be a token that blocklists, pauses, or otherwise reverts transfers to the beneficiary (e.g. USDT/USDC-style blocklists, a paused custom token, or a token deliberately crafted to revert for a specific address), a single bad token in the order's token list is enough to permanently DoS redemption of the *entire* order, including tokens the beneficiary could otherwise freely receive, and including the transaction-fee payout bundled into the same call. Since `_filled[commitment]`/`_orders[...]` accounting is only mutated as part of this same reverting call, there is no fallback path to redeem the remaining good tokens individually — the same bug class as the ClaimManagerV1 issue (`ClaimManagerV1._claimAtomicBounty` looping over `bounty.getTokenAddresses()` and reverting the entire claim if any single token transfer fails).

### Impact Explanation
Any attacker (or the intent creator/filler themselves via order construction) who causes one token in a multi-token order to be non-transferable to the designated beneficiary can permanently freeze the beneficiary's entire escrowed reward/refund for that order — a fill this address should have received (or a refund it is entitled to) is locked forever with no code path to selectively withdraw the unaffected tokens. This is a permanent freezing-of-funds condition reachable from a single relayed message/response, which the scan rules classify as a valid Medium/High-severity analog.

### Likelihood Explanation
Likelihood is moderate to high: intent orders can legitimately include multiple output tokens, and USDT-style blocklisting or a paused token is a realistic real-world condition outside the protocol's control. An adversary does not need special privileges — they only need the targeted beneficiary address to be blocked by (or the token paused for) any one of the tokens named in the order's `tokens` array, which is attacker/solver-influenced order data, not access-controlled.

### Recommendation
Do not let one token's failed transfer block the release of the others. Options:
- Wrap each per-token transfer in a try/catch (or low-level call check) and, on failure, credit the amount to a per-user/per-token "pull" balance the beneficiary can withdraw later instead of reverting the whole batch.
- Process each token transfer independently and continue the loop on failure, emitting a `TransferSkipped`/`TransferFailed` event and leaving the escrow balance for that specific token available for a later retry/pull, while still finalizing the order and paying out the remaining tokens and fees.
- Alternatively, allow a permissionless "claim single token" function so a stuck token doesn't block redemption of the rest of the order.

### Proof of Concept
1. A solver fills a cross-chain order whose output/escrow token list includes a legitimate reward token plus a small amount of a blocklisting stablecoin (e.g., USDT) that the intended beneficiary happens to be blocked on.
2. The order is finalized and a `WithdrawalRequest` for the beneficiary is dispatched/received, hitting `IntentGatewayV2.withdraw` (or `IntentsBase._withdraw`).
3. The loop reaches the blocklisting token, `token.call(...transfer...)` (or `safeTransfer`) reverts because the beneficiary is blocked.
4. The entire `withdraw`/`_withdraw` call reverts — `_filled`/`_orders` state is not updated, the legitimate reward token is not released, and the transaction fee payout is skipped — with no way to retry withdrawal of only the good tokens, permanently freezing the beneficiary's funds for that order.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
