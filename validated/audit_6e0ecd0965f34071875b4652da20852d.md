### Title
Webhook `shop-domain` Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never part of the HMAC-signed material. `Registry.process` trusts `request.shop` for downstream handler dispatch without any binding to the HMAC signature that was actually verified, breaking the identity binding: `hmac_verified(bytes) == identity_used(shop)`.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over exactly the string returned by `to_signable_string`: [1](#0-0) 

For webhooks, that signable string is only the raw body: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from HTTP headers and are **not** included in `to_signable_string`, so they are never authenticated by the HMAC check: [3](#0-2) 

`Registry.process` only validates the HMAC over the body, then unconditionally forwards `request.shop` (an unauthenticated header value) to the app's handler as the tenant identity for the event: [4](#0-3) 

Because an app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not per-shop), any party who can trigger a legitimate webhook for their own installed shop possesses a body + HMAC pair that is valid under the app's single shared secret. That same `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header rewritten to name a different, victim shop. `HmacValidator.validate` still passes because it only checks the body bytes, and `Registry.process` then dispatches the handler with `WebhookMetadata.new(shop: request.shop, ...)` carrying the attacker-chosen shop value, even though that value was never covered by the signature that was actually checked.

### Impact Explanation
This breaks the tenant-identity binding at the core of webhook processing: the bytes that are cryptographically verified (`raw_body`) are not the bytes that are used to determine which merchant/tenant the event belongs to (`shop` header). An application built on top of this gem that keys any per-tenant logic (data storage, authorization, side effects) off `WebhookMetadata#shop` can be tricked into attributing attacker-controlled webhook content to an arbitrary victim shop, i.e., cross-tenant data/event injection — a Critical-impact class per the rules (cross-tenant access).

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (common for public/embedded apps) to obtain a validly HMAC-signed webhook body under the shared `api_secret_key`, and (2) sending an HTTP POST to the app's public webhook endpoint with the `shop-domain` header changed to the victim's shop domain. No access to the victim's credentials, session, or access token is required, making this readily reachable by an unprivileged internet user who can install the app once.

### Recommendation
Bind the tenant/topic identity to the authenticated payload instead of trusting unauthenticated headers: include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (mirroring the OAuth `AuthQuery#to_signable_string` pattern, which signs `code`, `host`, `shop`, `state`, and `timestamp` together), or otherwise cryptographically bind the header values to the signed body before they are used for dispatch/authorization decisions in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; the app registers a webhook (e.g., `orders/create`) and Shopify sends a POST with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and a JSON body.
2. Attacker captures this exact `raw_body` and `hmac` header value.
3. Attacker crafts a new POST to the app's webhook endpoint reusing the same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) recomputes the HMAC over `to_signable_string` (the raw body only) and it matches, since the body is unchanged — the forged `shop-domain` header is never checked.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the app to process attacker-controlled webhook content under the victim shop's identity.
