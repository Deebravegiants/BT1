Confirmed: the webhook `shop` field is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header [1](#0-0) , while the HMAC that `Registry.process` validates is computed only over the raw body bytes [2](#0-1) , and `HmacValidator.validate`/`validate_signature` only ever signs `to_signable_string`, never any header value [3](#0-2) . `Registry.process` validates the HMAC and then unconditionally forwards `request.shop` (the header value) into the handler's `WebhookMetadata` without any additional binding [4](#0-3) .

### Title
Webhook shop identity is not bound by the HMAC, allowing shop-domain spoofing via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` verifies only the raw request body, while `#shop` is read from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, a value never included in the HMAC signature. `Registry.process` treats a passing HMAC check as proof of both body authenticity and shop identity, then hands the unauthenticated `shop` value to the app's webhook handler.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(..., verifiable_query.to_signable_string)` and compares it to the supplied `hmac` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) ; the `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled straight from HTTP headers with no cryptographic binding to the body or the signature [6](#0-5) .

`Registry.process` raises `Errors::InvalidWebhookError` if the HMAC check fails, but once it passes, it immediately builds `WebhookMetadata` using `request.shop` from the header, with no separate verification that this shop is the one that actually produced the signed body [4](#0-3) .

Because the signature covers `raw_body` alone, the identity binding "shop authenticated" ≠ "shop delivered to the handler" is broken: `HMAC-valid(raw_body, secret) == true` does not imply `shop_header == originating_shop`. Any principal who can obtain one valid `(raw_body, hmac)` pair for topic `X` (e.g. by triggering that webhook on their own shop, which is a legitimate action for any merchant/unprivileged app installer) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The HMAC check still passes (it never looked at the header), and `Registry.process` calls the handler with attacker-chosen `data.shop` alongside the original signed body content.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the app's own webhook-processing primitive lets a caller decouple "whose data this is" from "who is cryptographically authenticated to have sent it." Any host application that uses `data.shop` from `WebhookMetadata` (as the docs instruct — see the `process` webhook example keyed on shop) to select which merchant's records to update, tag, or notify will attribute attacker-controlled/replayed content to a victim shop chosen by the attacker, without needing the app's `client_secret`. This falls into the "cross-tenant access" category of Critical impact for this gem, because it stems entirely from the gem's own `Webhooks::Request`/`Registry` verification contract, not host misuse.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on their own store (or otherwise trigger one legitimate webhook delivery for a topic they control) obtains a valid `(raw_body, hmac)` pair signed with the app's real secret. Replaying it against the same public webhook endpoint with a forged `shop-domain` header requires no secret knowledge and no TLS interception — only reachable, publicly documented behavior of `ShopifyAPI::Webhooks::Registry.process`.

### Recommendation
Bind the shop identity into the verified signable payload, or otherwise independently confirm that `request.shop` corresponds to a shop that has legitimately installed/registered for that webhook subscription (e.g. cross-check `webhook_id`/`shop` against records stored at registration time) before dispatching to handlers. At minimum, `to_signable_string` should incorporate the `shop-domain` and `topic` headers so the HMAC covers the values the handler ultimately trusts.

### Proof of Concept
1. App merchant M installs the target Shopify app; Shopify legitimately delivers a webhook `POST` with body `B` and headers `x-shopify-hmac-sha256: H(B)`, `x-shopify-shop-domain: m.myshopify.com`, `x-shopify-topic: orders/create`.
2. M (an unprivileged actor from the app's perspective) captures `B` and `H(B)` from this genuine delivery.
3. M crafts a new request to the app's public webhook endpoint reusing the exact same body `B` and `x-shopify-hmac-sha256: H(B)`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (i.e. `B` only) and it matches, so `Registry.process` proceeds [4](#0-3) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, letting M inject/replay data attributed to a shop M does not control.
