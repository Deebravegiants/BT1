### Title
Webhook shop/topic identity fields are trusted from unauthenticated headers while only the raw body is HMAC-covered, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers that are never included in the HMAC-verified content. `Utils::HmacValidator.validate` only checks the value returned by `to_signable_string`, which for webhook requests is `@raw_body` alone. The gem then hands `request.shop` (and the other header-derived fields) straight to the app's `WebhookHandler` as trusted, verified metadata.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the request using only this signable string, then constructs `WebhookMetadata` from the unverified header fields and dispatches it to the app's handler as if it were a Shopify-attested fact: [3](#0-2) 

The `WebhookMetadata` struct and the documented handler contract explicitly instruct integrators to treat `data.shop` as the authoritative shop domain of the webhook: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop header value == shop that produced/authorized this body`. Because the HMAC only covers `@raw_body`, this equality is never enforced — the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header can be swapped for any value without invalidating the HMAC, since Shopify's webhook HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has the app installed. Any shop that installs the app receives real, validly-signed webhook deliveries (body + HMAC) for its own store. That merchant — an unprivileged actor relative to other tenants of the same app — can replay the exact same body/HMAC pair to the app's public webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header (and forging `topic`/`webhook_id` similarly). `HmacValidator.validate` still succeeds because it never inspects the shop-domain header, and the app's handler receives `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This breaks the cross-tenant boundary the gem's webhook API is supposed to enforce: the shop identity delivered to app code is not authenticated, only the body is. Any downstream logic that keys off `data.shop` (e.g., looking up the victim's stored session/access token, updating the victim's local records, or triggering business logic scoped to the victim tenant, as shown in the documented handler example calling `perform_later(shop_domain: data.shop, ...)`) can be manipulated by a different, unrelated tenant. This matches the "cross-tenant access" Critical impact category, since one merchant can inject fabricated webhook events attributed to another merchant's shop.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must control at least one shop that has the target app installed (to obtain a genuine, validly-HMAC-signed body), and the impact depends on the host application trusting `data.shop` for tenant-scoped actions without any secondary shop verification (e.g. cross-checking against an already-known session). No secret, access token, or privileged account is required beyond normal app installation, which is available to any unprivileged merchant/internet user who installs the app.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop domain to the request before trusting it. Concretely, `Utils::HmacValidator.validate` (or `Webhooks::Request#to_signable_string`) should incorporate the `shop-domain` header into the signed content it checks — matching Shopify's actual webhook verification recommendation of comparing the resulting shop only after confirming it corresponds to a shop with a known/stored session — and the documentation/handler contract should make clear that `data.shop` is not itself HMAC-authenticated and must be cross-validated against stored session state before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the app's shared `client_secret`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same body `B` and same `x-shopify-hmac-sha256: H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally forges `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B` [6](#0-5) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, and the app acts on data it believes is attested for `victim-shop.myshopify.com`.
