### Title
Tokens held by the controller outside declared `refund_assets` / collateral lists are permanently unrecoverable — no sweep or rescue path exists - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
Analogous to the `BoringBatchable.batch` payable-ETH trap, the XOXNO Lending controller can hold user tokens that no endpoint can ever return. Any token balance the controller holds that is not (a) a declared `collaterals` receipt during `flash_position`, or (b) a listed `refund_assets` delta, is stranded forever: the protocol exposes no sweep, rescue, or arbitrary-withdraw entrypoint. This is confirmed by the protocol's own documentation: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (docs/reference/endpoints.md, "Strategy payments and callbacks").

### Finding Description
In `process_flash_position`, the receiver callback may push arbitrary tokens to the controller. The function only accounts for two sets of assets:

1. Declared collateral tokens — measured via `balance_delta_since` and deposited (`collect_collateral_deposits`, lines 325-352).
2. Declared `refund_assets` — positive balance deltas since the pre-callback snapshot are returned to `caller` (`refund_listed_assets` → `refund_controller_balance_delta`, lines 372-384).

Any other token transferred to the controller — inside the callback, or simply by a direct `token.transfer` to the controller address at any time — is never credited, never refunded, and cannot be reclaimed:

- The controller has no public function that transfers out arbitrary token balances. Token transfers out occur only inside measured, leg-scoped flows (`withdraw`, liquidation seizure, refunds) that are bound to declared `HubAssetKey`s and account state.
- `validate_refund_assets` (lines 217-256) even restricts refund eligibility to assets listed in the same hub and account spoke and disjoint from collaterals, so a user cannot retroactively rescue tokens that don't meet these constraints (e.g., an unlisted token, or a token listed only under a different hub/spoke).
- The pool side behaves the same way: a direct `token.transfer` to the pool silently inflates market backing (effectively a forced `recapitalize`-like donation) with no way for the sender to claim shares or a refund, since `supply` credits only measured receipts pulled through the controller.

The strongest unprivileged path: a user calls `flash_position` (or `multiply`/`swap_*` strategies) with a receiver/route that ends up pushing a token to the controller that is neither a declared collateral nor in `refund_assets` — or a token that is listed but only under a different `hub_id` than `debt.hub_id`, so `cache.require_listed_active_config` makes it ineligible for refund declaration. Those tokens sit on the controller balance with zero accounting entries and zero exits.

### Impact Explanation
Permanent freezing/loss of user funds. Tokens stranded on the controller (or donated to the pool) are inaccessible to the sender and to the protocol's own accounting — exactly the "ETH stuck in the contract" impact of the reference report, generalized to arbitrary Stellar tokens. Any user can trigger this against themselves via a direct transfer, and strategy users can trigger it accidentally via callback outputs for undeclared/ineligible assets.

### Likelihood Explanation
Medium-low. It requires a user mistake (direct transfer) or a receiver/swap route that delivers an undeclared or hub-ineligible token to the controller. However, `refund_assets` eligibility is narrower than "any token the callback might send" (must be listed in the debt hub and account spoke, disjoint from collaterals), so a callback emitting a valid token listed under a different hub guarantees a stuck balance rather than a refund — a realistic outcome for multi-asset routers.

### Recommendation
Add a permissionless or admin-mediated recovery path for unaccounted controller token balances — e.g., a `rescue(asset, to, amount)` governance/execute operation, or let `flash_position` treat any positive controller balance delta of a listed token as refundable regardless of hub. At minimum, document the stuck-funds behavior in endpoint docs and consider allowing `refund_assets` to include tokens listed under any hub of an active spoke so callback leftovers can always be declared.

### Proof of Concept
1. User deploys a Wasm receiver and calls `controller.flash_position(caller, 0, spoke_id, PositionMode::Multiply, debt=(hub_id, USDC), amount, receiver, data, collaterals=[(hub_id, XLM, min)], refund_assets=[])` where `XLM` and `USDC` are listed.
2. Inside `execute_flash_position`, the receiver delivers the declared XLM collateral and additionally transfers some amount of a third token `AQUA` (or XLM listed only under a different hub) to the controller address.
3. `refund_listed_assets` iterates only `refund_assets` (lines 378-383); the extra token's delta is never measured or returned, and it matches no collateral key.
4. The transaction succeeds; the extra tokens remain on the controller balance. No controller endpoint can move them — there is no sweep function, and every outbound transfer path requires an account position or a declared leg. The user's tokens are permanently frozen.
