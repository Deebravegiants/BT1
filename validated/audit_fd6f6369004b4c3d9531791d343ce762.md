### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers that are never included in the HMAC-verified content. `Registry.process` validates the HMAC over the body only, then trusts the unauthenticated `shop` header to attribute the webhook payload to a tenant. Any actor who can obtain one legitimately HMAC-signed webhook body (e.g. a merchant who installed the app and receives real webhooks for their own store) can replay that exact body to the app's webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header changed to point at a different shop. The HMAC check still passes (body is unmodified and correctly signed), but the app's handler now believes the data belongs to another tenant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which only signs `@raw_body`. The `shop` accessor, however, is derived purely from an HTTP header with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only ever compares the computed HMAC of `to_signable_string` (the body) against the received signature — it has no knowledge of, and cannot bind, the `shop` header: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

The resulting `WebhookMetadata.shop` field is exactly what the documented handler pattern uses to route/attribute data per-tenant (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

This breaks the intended binding: `shop header == tenant that produced the HMAC-signed body`. In reality the equality enforced by this code is only `HMAC(body) == received_hmac`; `shop` is unauthenticated and can be swapped independently of the signed body, exactly matching the "field acted on but not covered by the HMAC" analog class.

### Impact Explanation
An attacker who is a legitimate merchant/installer of the app (thus able to receive real, correctly-signed webhooks for their own shop from Shopify) can capture one such signed request and replay it to the app's public webhook endpoint with only the `shop-domain` header rewritten to target a victim shop. Because the gem never binds `shop` into the HMAC-verified payload, the forged request passes `Registry.process`'s HMAC check and is delivered to the app's handler labeled as belonging to the victim tenant. Depending on how the host app uses `data.shop` (e.g. to key database records, trigger `app/uninstalled` cleanup, or write order/product data), this enables cross-tenant data corruption or spoofed lifecycle events — satisfying the "cross-tenant access" criterion without requiring the app's `client_secret`, an access token, or any credential theft.

### Likelihood Explanation
Any app on the platform necessarily has multiple installing shops, each of which is an "unprivileged" actor relative to other tenants but a legitimate, HMAC-capable webhook sender for their own shop. Capturing a self-owned signed webhook (body + valid HMAC) requires no special access — it is simply a normal event the attacker's own store already receives. Replaying it with a modified header to the same public endpoint is trivial. The only barrier is that the endpoint's raw body must be identical to a real payload the attacker already possesses, which is easy for events with generic/attacker-influenceable shapes (e.g. `app/uninstalled`, `shop/update`, `customers/create` triggered by the attacker's own actions in their store).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) header values into the HMAC-verified signable content, or otherwise cryptographically tie the header-derived tenant identity to the signed body (e.g. include the shop domain in the string used for signature verification, matching how Shopify computes the header in its own webhook delivery, or require the app to additionally verify `request.shop` against session/shop records it already trusts before processing).

### Proof of Concept
1. App installed on `attacker-shop.myshopify.com`; attacker triggers a webhook event on their own store (e.g. updates their shop settings to fire `shop/update`).
2. Attacker's endpoint (or a proxy they control) captures the raw POST body and the `x-shopify-hmac-sha256` header — both valid and correctly computed by Shopify using the app's real secret.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers normally; `Utils::HmacValidator.validate` succeeds because it only checks `@raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` calls the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host app to process attacker-controlled data under the victim tenant's identity.
