### Title
Webhook `shop-domain`/`topic` headers are trusted as tenant identity but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed only over the raw request body, then hands the handler a `shop` value taken directly from an unauthenticated HTTP header. The HMAC binding therefore covers the body but not the header the app uses to identify which tenant (shop) the webhook belongs to - the exact class of bug the external report describes (a value the code depends on for a security decision that is not actually covered by the check that is supposed to authenticate it).

### Finding Description
`Webhooks::Request` implements `VerifiableQuery` by defining: [1](#0-0) 

so the HMAC signature is validated against `@raw_body` only. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately uses the unauthenticated `request.shop` (and `request.topic`) to route and identify the tenant for the handler: [3](#0-2) 

`Utils::HmacValidator.validate` only ever checks `to_signable_string` (the raw body) against the `hmac` field of the `VerifiableQuery`; it has no knowledge of, and does not cover, the `shop-domain` header: [4](#0-3) 

The identity binding that should hold is: `shop header used for tenant attribution == shop bytes covered by the HMAC`. Because the HMAC only signs the body, this equality does not hold - the `shop-domain` header (and `topic`/`webhook_id`) can be swapped freely without invalidating the signature, exactly analogous to the ERC20 report's core defect: a value the caller depends on (there, the boolean return; here, the shop header) is not actually enforced/covered by the mechanism relied upon to guarantee its integrity (there, the ABI-encoded return data; here, the HMAC digest).

### Impact Explanation
An attacker who operates their own Shopify store receives genuine, correctly-HMAC-signed webhooks from Shopify for their own shop (this requires no privileged credentials - any merchant can install a public app and trigger webhooks on their own tenant, e.g. `orders/create`). Because the signature covers only the raw body, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain (and/or the `shopify-topic` header). The HMAC check in `Registry.process` still passes since `to_signable_string` is unchanged, but the handler executes with `WebhookMetadata` claiming the wrong tenant. Depending on the handler, this crosses a tenant boundary: it can be used to inject or mutate data under the wrong shop's session/records, or to trigger tenant-scoped side effects (e.g. GDPR redact handlers, order/customer sync jobs) attributed to a shop the attacker does not control. This matches the "cross-tenant access" criterion for Critical severity.

### Likelihood Explanation
Exploitation requires only an unprivileged Shopify merchant account (to obtain one valid signed webhook payload for any topic the target app subscribes to) and the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint - no `api_secret_key`, access token, or other privileged credential is needed. The gem provides no protection against this because `Webhooks::Request#hmac`/`#to_signable_string` deliberately exclude the shop/topic headers from the signed material, and `Registry.process` never re-derives or cross-checks the header values against anything covered by the signature.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook_id`) header values into the HMAC-signed material, or otherwise validate the `shop-domain` header against Shopify-issued, tenant-scoped state (e.g., a session previously established via OAuth for that exact shop) before dispatching to the handler. At minimum, document/require that consumers of `Webhooks::Request` never trust `request.shop` as an authenticated tenant identifier from HMAC validation alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers an `orders/create` webhook, capturing the legitimate request: headers include `x-shopify-hmac-sha256: <validHmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and body `raw_body`.
2. Attacker replays this exact request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed; `hmac` is computed from the unchanged `raw_body`, so `Utils::HmacValidator.validate(request)` returns `true` (see `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: request.shop` equal to `"victim.myshopify.com"`, even though the signed body originated from the attacker's own shop - demonstrating the header/HMAC binding failure.
