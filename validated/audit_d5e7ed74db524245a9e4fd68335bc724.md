### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the `shop` value straight from an unauthenticated HTTP header to the application's handler. Because the `shop-domain` header is never included in the signed payload, an attacker who legitimately owns one Shopify store (and can therefore receive a validly-signed webhook for that store) can replay that same signed body against the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and the signature check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the (unsigned) header: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature over `to_signable_string` only: [3](#0-2) 

`Registry.process` trusts this validation, then forwards `request.shop` directly into the handler's `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is: `shop that produced the HMAC-signed payload == shop attributed to the processed webhook`. Because the header carrying the shop is excluded from the signed bytes, that equality is not enforced by the gem — only the body bytes are authenticated, while the shop attribution is taken on faith from an attacker-controllable header.

### Impact Explanation
Any user can install the app on a store they control and receive a legitimately-signed webhook for that store (e.g., `orders/create`). By replaying that exact signed body to the app's webhook endpoint with the `shop-domain` (or `x-shopify-shop-domain`) header changed to a victim's `myshopify.com` domain, the forged request still passes `HmacValidator.validate`, and `Registry.process` will invoke the host app's handler believing the payload originated from the victim shop. Any host application that persists or acts on `WebhookMetadata#shop` (nearly universal, since this is the field apps use to resolve the tenant/session) will attribute attacker-controlled data to another tenant — a cross-tenant data injection/corruption primitive.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned development/trial store to receive one genuinely signed webhook, and (2) replaying it with a modified header to the app's public webhook endpoint. No access token, secret, or privileged account is needed — this is achievable by any unprivileged internet user who can install the app once, which is a low bar for most public Shopify apps.

### Recommendation
Bind the shop identity into the authenticated payload instead of trusting a header excluded from the HMAC. Concretely, `Webhooks::Request#to_signable_string` (and/or `HmacValidator.validate`) should incorporate the `shop-domain` header (and other identity-bearing headers such as `topic`/`webhook-id`) into the signed material it checks, or the library should require the host application to cross-check the header-derived shop against a shop already bound to an existing, trusted session/tenant record before acting on `WebhookMetadata#shop`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-resolution key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. creates an order), capturing the raw POST body and its valid `X-Shopify-Hmac-Sha256` header sent to the app's webhook endpoint.
2. Attacker resends the identical raw body and HMAC header to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the secret — matching the header spoof is invisible to the check: [5](#0-4) 
4. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and the host app processes attacker-controlled data as if it belongs to the victim tenant.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
