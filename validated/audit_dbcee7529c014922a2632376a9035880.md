### Title
Standing `approveUnlimited` allowance plus unchecked router calldata lets an attacker sweep stranded input-token balance from `ExternalActionSwap`/`LifiExternalAction` as their own output - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`, `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`LifiExternalAction.callRouter` grants the LI.FI router an unlimited, persistent ERC-20 allowance via `approveUnlimited` and then blindly executes attacker-controlled `externalActionMetadata` against that allowance, only measuring the resulting delta on the **output** token. Because the action never verifies that the router actually consumed the full `inputAmount` transferred to it, and never refunds unconsumed input tokens, any input token left stranded in the action from an earlier transaction can later be pulled by the router (using the still-standing approval) inside a subsequent, unrelated attacker transaction and converted into extra output that is attributed entirely to that attacker's own UTXO.

### Finding Description
The invariant that should hold is: *tokens leaving `LifiExternalAction` in a transaction == `-deltaAmountChanges` that `Hinkal.transact` sent to it for that same transaction* [1](#0-0) .

In `swap()`, `inputAmount` is computed strictly from the circuit-verified `deltaAmounts[0]` [2](#0-1) , but this value is only *passed* to `callRouter`; the LI.FI implementation never checks that the router's calldata actually consumes that exact amount: [3](#0-2) 

`callRouter` approves the router for `type(uint256).max` on the input token (only re-approving when allowance drops below half of max, so the approval persists across transactions) [4](#0-3) , then executes `externalActionMetadata` verbatim, and derives `swappedAmount` purely from the **output**-token balance delta observed around that single call. Nothing constrains the router's calldata to pull exactly `inputAmount` of the input token — if it pulls less (partial fill, multi-hop dust, or a deliberately crafted metadata by a prior caller), the unconsumed input token remains stuck in the action contract, since `swap()` never sweeps or refunds leftover input token back to `Hinkal` or the depositor.

`Hinkal.transact`'s own balance-diff invariant does not catch this, because it only checks Hinkal's own balance change against `amountChanges`/UTXO totals, not what happens to the action's internal balance [5](#0-4) . For the transaction that stranded the dust, the input-token balance-diff check at the Hinkal level is satisfied purely by the pre-call transfer from Hinkal to the action [6](#0-5) ; it never verifies the action actually consumed 100% of it in the router call.

An attacker can then submit their own transaction to the same `LifiExternalAction` (same block or later), depositing their own small `inputAmount`, but craft `externalActionMetadata` (fully attacker-controlled bytes bound only by `calldataHash`, which the attacker themselves computes when generating their own proof) so that the router pulls the attacker's declared amount **plus** the stranded dust sitting in the action from the prior transaction — made possible only because the standing `approveUnlimited` allowance never expires or is scoped to a single call. The resulting `swappedAmount` (and thus `amountToSendToHinkal`) is inflated by the stolen dust, and this whole amount is packaged into the attacker's own output UTXO [7](#0-6) . Hinkal's checks for the attacker's transaction pass unchanged, because they only verify Hinkal's own balance-vs-declared-amounts consistency, which is self-consistent regardless of where the action's swap input actually came from.

### Impact Explanation
Funds that legitimately belonged to an earlier (potentially unrelated) user — value that was already debited from that user's shielded balance and transferred into the action contract as part of their swap, but never fully consumed/refunded — can be diverted into an unrelated attacker's output UTXO. This is direct theft of in-flight user funds via a repeatable mechanism (any time the router under-consumes the approved input token, which is plausible with real DEX aggregator calldata), matching Critical severity.

### Likelihood Explanation
Preconditions: (1) at least one prior transaction through `LifiExternalAction` leaves unconsumed input-token balance in the action (a normal risk with attacker- or SDK-crafted LI.FI calldata since nothing on-chain enforces full consumption), and (2) the attacker then submits a follow-up transaction to the same action for the same input token, crafting `externalActionMetadata` to sweep the extra balance. The attacker only needs to be able to deposit their own funds, generate their own proof, and control the swap calldata for their own transaction — all within the stated unprivileged attacker capabilities. No special role or timing beyond ordinary transaction submission is required, making this cheaply and repeatably exploitable whenever dust exists.

### Recommendation
- After the router call, verify the input token balance of the action has decreased by exactly the declared `inputAmount` (or refund the delta back to `msg.sender`/Hinkal rather than leaving it in the contract).
- Replace `approveUnlimited` with a per-call approval scoped to `inputAmount`, reset to zero after the swap completes, so no standing allowance survives across transactions.
- Alternatively, sweep and force-refund any leftover input-token dust to the depositor's own output UTXO within the same transaction so it can never be claimed by a different caller.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `LifiExternalAction` with a mock LI.FI router that supports partial fills (consumes less than the full approved/transferred amount when instructed by calldata).
2. **Tx 1 (victim)**: Victim deposits `X` of `inputToken`, crafts (or the SDK produces) `externalActionMetadata` that only swaps `0.9 * X`, leaving `0.1 * X` stranded in `LifiExternalAction`. Assert `IERC20(inputToken).balanceOf(action) == 0.1 * X` after the tx, and assert Hinkal's balance-diff checks still passed (tx succeeded).
3. **Tx 2 (attacker)**: Attacker deposits a small `Y` of `inputToken`, crafts `externalActionMetadata` that instructs the mock router to `transferFrom(action, router, Y + 0.1*X)` using the still-standing unlimited allowance, then returns proportional output.
4. Assert the equality that should hold breaks: input token leaving the action in Tx 2 (`Y + 0.1*X`) != `-deltaAmountChanges` Hinkal sent it in Tx 2 (`Y`).
5. Assert attacker's output UTXO amount in Tx 2 is `> amount justified by Y alone`, and `IERC20(inputToken).balanceOf(action) == 0` (dust fully drained), proving the victim's stranded `0.1*X` was captured entirely by the attacker's output.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
