Audit Report

## Title
Missing upper-bound timestamp validation in gateway web-api-trigger staleness check allows permanent bypass of message freshness/replay protection - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` decodes a caller-supplied `TriggerRequestPayload.Timestamp` and checks only that the message is not too old, never that it is not implausibly far in the future. [1](#0-0)  This one-sided check lets an authorized sender craft a signed message with an inflated future `Timestamp` that will forever satisfy the freshness check, defeating the intended anti-staleness/replay protection for that message.

## Finding Description
The staleness check is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // reject as stale
}
```
This is confirmed verbatim in the code. [2](#0-1)  The condition only fails (rejects) when `payload.Timestamp` is smaller than `now - maxAge`; there is no complementary check rejecting `payload.Timestamp` values set far in the future. The JSON schema for the trigger payload documents an intended freshness *window* (not just a lower bound), showing this is a design gap rather than an intended restriction to only-past checking. [3](#0-2) 

The `Timestamp` field is part of the signed message body's `Payload`, which is covered by the signature (`GetRawMessageBody` includes `msgBody.Payload` in the signed data), so it cannot be tampered with post-signature by third parties — but the *legitimate signer* fully controls its value and can pick any value they like, including one far in the future, and the message will still pass `Message.Validate()`/signature checks and this staleness check indefinitely. [4](#0-3)  After passing this check, the message is dispatched to DON nodes and its callback is unconditionally recorded/overwritten in `h.savedCallbacks` keyed only by the client-supplied `MessageID`. [5](#0-4) 

## Impact Explanation
This is a genuine logic bug: the freshness check is asymmetric and does not bound `Timestamp` from above, matching the code exactly as claimed. However, the practical security impact is weak:
- The signer of the message is, by construction, the entity that chose the `Timestamp` value in the first place — an "attacker" self-issuing a message with a future timestamp only defeats a staleness check that was protecting *that same signer's own message* from being replayed by others later. It does not let an attacker forge or impersonate another party's message, since the payload is signed and the signature covers the timestamp.
- Actual exploitation requires a *separate* precondition: that a validly-signed message (with an inflated timestamp) is later captured and replayed by an unauthorized third party. The claim itself acknowledges this ("if the signed message is later captured... via logging, an insecure transport hop..."), which is an external capture/leak scenario outside the code under audit, not something this handler's logic can prevent regardless of timestamp validation.
- The `savedCallbacks` collision concern requires a `MessageID` collision between two different callers, which is an independent precondition unrelated to the timestamp check; a missing upper bound only marginally lengthens a message's validity window rather than being the root cause of any callback-overwrite exploit.

Given this, while the code defect is real, the concrete unprivileged-attacker-triggerable impact (unauthorized job/workflow execution, response misdelivery) described in the report is speculative and depends on additional unproven assumptions (message capture/leak, ID collision) rather than a direct, self-contained exploit path.

## Likelihood Explanation
Low-to-moderate. An "attacker" would need to be an already-authorized signer choosing to self-inflate their own message's timestamp — this only affects replay risk on their own message if it's later leaked through a channel outside this code's control. No mechanism in this handler alone lets a third party forge or extend the freshness of someone else's message.

## Recommendation
Add a symmetric upper-bound check for defense-in-depth:
```go
now := time.Now().Unix()
maxAge := int64(h.config.MaxAllowedMessageAgeSec)
if payload.Timestamp < now-maxAge || payload.Timestamp > now+maxAge {
    // reject
}
```
This is a reasonable hardening recommendation, though it addresses a secondary/defense-in-depth gap rather than a directly exploitable unprivileged vulnerability.

## Proof of Concept
As described in the report: sign a `TriggerRequestPayload` with `Timestamp = now + 10_000_000` using an authorized key, submit via the gateway trigger endpoint using the same flow as `triggerRequest` in `handler_test.go`, and observe the staleness check never rejects it. [6](#0-5)  This confirms the code-level defect but does not by itself demonstrate unauthorized access, impersonation, or fund/job impact without the additional external capture/replay or ID-collision preconditions noted above.

				"ask": "102",

		payloadJSON, err = json.Marshal(reqPayload)
		require.NoError(t, err)
	} else {

	msg := &api.Message{

		},
