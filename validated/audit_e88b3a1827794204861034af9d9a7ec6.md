### Title
`describeWithdrawal` reports `completed` for withdrawals to chains not covered by its EVM/Sol/Fogo/Strk/Aptos/UTXO branches without checking transfer finalization - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
`OmniBridge.describeWithdrawal` (packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:691-731) branches on `destinationChain` derived from the transfer's `recipient`, but chains such as `ChainKind.Bnb`, `ChainKind.Abs`, `ChainKind.Pol`, and `ChainKind.HlEvm` — all real, supported chains listed in `CHAIN_MAPPINGS` (omni-bridge-utils.ts:82-96) — are checked with `isEvmChain(destinationChain)` at line 707, so their fate depends entirely on whether `@omni-bridge/core`'s `isEvmChain` classifies them as EVM. Any destination chain that is neither caught by `isEvmChain`, nor equals `Sol`/`Fogo`/`Strk`/`Aptos`, nor `isUtxoChain` (only `Btc`/`Zcash`), falls into the final `else` at line 722-724 and unconditionally returns `{ status: "completed", txHash: null }` regardless of `transfer.finalised` state.

### Finding Description
The claimed equality is: **reported status `completed` == actual on-chain execution confirmed by `omniBridgeAPI.getTransfer`**. The code path:

```
packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:704-724
const destinationChain = getChain(transfer.recipient as OmniAddress);
let txHash = null;
if (isEvmChain(destinationChain) || destinationChain === ChainKind.Sol || ... Fogo/Strk/Aptos) {
  txHash = transfer.finalised?.transaction_hash;
} else if (isUtxoChain(destinationChain)) {
  txHash = ...;
} else {
  return { status: "completed", txHash: null };   // <-- no check of transfer.finalised at all
}
```

For any `destinationChain` reaching the final `else`, `transfer.finalised` (the only field that indicates on-chain execution occurred) is never inspected. The function returns `completed` purely because the chain kind didn't match any recognized bucket — not because the API confirmed completion. This is reachable without any privileged action: the destination chain is set by the *withdrawing user themselves* via `routeConfig.chain`/`destinationAddress` when constructing the withdrawal (`OmniBridge.createWithdrawalIntents` → `deriveOmniWithdrawIntentParams`), for any chain accepted by `supports()`/`CHAIN_MAPPINGS`. If `@omni-bridge/core`'s `isEvmChain` does not classify a given `CHAIN_MAPPINGS` entry (e.g., a newly added chain, or one whose classification lags library updates) as EVM, that legitimate withdrawal's status query falls to the unconditional `completed` branch on the very first poll, potentially while the transfer is still pending or failed on the destination chain.

No other guard in the file prevents this: `validateWithdrawal`, `estimateWithdrawalFee`, and `supports()` only gate whether a withdrawal can be *created*, not how its *status* is later reported; there is no assertion inside `describeWithdrawal` that checks `transfer.finalised` before the else-branch return.

### Impact Explanation
An integrator polling `describeWithdrawal`/`waitForWithdrawalCompletion` receives `status: "completed"` with `txHash: null` for a withdrawal whose destination-chain payout was never confirmed by the bridge API. If the integrator treats `completed` as proof of delivery (e.g., releasing counterpart funds, marking an order fulfilled, crediting a ledger), it can do so before or even if the destination-chain transfer never lands — a fund-misreporting bug matching the "status or hash misreport making an integrator credit or refund twice" category (High/Critical depending on chain coverage gaps). Since `txHash` is `null`, there is no way for the integrator to independently verify the reported completion.

### Likelihood Explanation
This triggers whenever `getChain(transfer.recipient)` returns a `ChainKind` that (a) is a legitimate, currently-supported Omni Bridge chain per `CHAIN_MAPPINGS`, and (b) is not classified as EVM by `isEvmChain` from `@omni-bridge/core`, and is not `Sol`/`Fogo`/`Strk`/`Aptos`/`Btc`/`Zcash`. Whether such a gap currently exists depends on the exact implementation of `isEvmChain` in the `@omni-bridge/core` dependency, which is outside this repo and was not fully verifiable with available tools — `Bnb`, `Abs`, `Pol`, `HlEvm` are all plausible EVM chains that `isEvmChain` likely covers today, but the code has no fallback/assertion for unrecognized chain kinds, so any future chain addition to `CHAIN_MAPPINGS` without a corresponding update to this if/else chain (or a lag/mismatch versus `@omni-bridge/core`'s internal `isEvmChain` list) reproduces the bug immediately and on every poll for that chain. The attacker (an ordinary user withdrawing to such a chain) needs no special access — just choosing a route/chain combination that lands in the uncovered branch.

### Recommendation
Replace the final `else` with an explicit exhaustive check or a safe default that reflects "unknown/unverified" rather than "completed", e.g., only return `completed` when `transfer.finalised?.transaction_hash` is present, and return `pending` (or throw/log an "unsupported chain kind" error) otherwise for any chain kind not explicitly and correctly matched. Ideally, unify the EVM/Sol/Fogo/Strk/Aptos and UTXO branches with the fallback, so the completion decision always keys off `transfer.finalised` rather than being satisfied merely by chain-kind mismatch.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
