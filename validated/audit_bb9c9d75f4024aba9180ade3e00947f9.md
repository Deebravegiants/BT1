## Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `HmacValidator` authenticates the *body bytes* but never binds them to the `shop-domain` (or `x-shopify-shop-domain`) header. `Registry.process` trusts `request.shop` — taken straight from that unauthenticated header — to build the `WebhookMetadata` handed to the app's handler. The identity binding the gem should enforce (`hmac_signed_content == shop_the_handler_believes_it_is_processing_for`) is broken because the shop identity is never part of what's signed.

### Finding Description
`Request#to_signable_string` is:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e. the body) and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header value:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

The `shop` accessor, however, is read from a separate, unsigned header:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`Registry.process` only checks the body's HMAC, then forwards the unauthenticated `request.shop` value to the handler as the tenant identity:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Because the shop-domain header is not part of the signed content, any two requests whose bodies are identical (or any request the attacker can obtain a valid HMAC for from their own tenant) remain HMAC-valid no matter what `shop-domain` value is sent. An unprivileged app user (e.g. a merchant who installs the app on their own dev/test shop) can capture one legitimately Shopify-signed webhook (valid `raw_body` + `hmac-sha256`) and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still passes (it never looks at the shop header), and the handler executes believing the event, and any lookups keyed by `WebhookMetadata#shop`, belong to the victim tenant — a cross-tenant identity confusion inside the host application driven entirely by this gem's verification gap.

### Impact Explanation
This breaks the binding `hmac_authenticated_bytes == shop_identity_trusted_by_handler`. Any host application that uses `WebhookMetadata#shop` returned by `Registry.process` to select a per-shop session, database record, or access token (the intended/documented usage) can be made to act on/for the wrong shop by an attacker who only needs one valid Shopify webhook capture from any shop (including their own). This is a cross-tenant access vector, matching the Critical-impact category (cross-tenant access) defined for this scan.

### Likelihood Explanation
Likelihood is moderate-to-high: no access to `api_secret_key` is required. The attacker only needs a single genuine webhook delivery (obtainable by installing the app on their own shop, a normal unprivileged action) and the ability to POST an HTTP request with a forged `shop-domain`/`x-shopify-shop-domain` header to the app's public webhook route — something entirely within reach of an unprivileged internet user, since this gem performs no additional binding check.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or explicitly cross-check that the `shop-domain` header matches shop-scoped context (e.g., an expected/registered shop) before trusting `request.shop`. At minimum, document and/or enforce in `Registry.process` that `request.shop` must not be used as an authenticated tenant identifier unless corroborated by out-of-band means, since the current HMAC only covers the raw body.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any webhook topic the app is registered for. Capture the raw body `B` and the valid `x-shopify-hmac-sha256` signature `H` Shopify sends (computed over `B` with the app's `client_secret`).
2. Build a new request to the app's webhook endpoint reusing the exact same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-topic`-compatible body content is not required since only body bytes are checked).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — unchanged from step 1 — so it matches `H` and validation succeeds:
`lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` even though the event content and signature were never associated with `victim-shop.myshopify.com`, demonstrating the identity-binding break.
