Based on investigation of the webhook handling code, I found a genuine identity-binding break matching the report's bug class (a value trusted by downstream logic but not actually covered by the cryptographic check).### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *body bytes* but never binds the `shop-domain` header to that signature. `ShopifyAPI::Webhooks::Registry.process` nonetheless trusts `request.shop` (parsed straight from the unauthenticated header) as the tenant identifier passed to the host application's handler. This is a direct analog of the report's root cause class: a field ("shop") that is acted upon (tenant attribution) is not covered by the cryptographic check (HMAC), breaking the equality `shop authenticated == shop used for tenant identity`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` exclusively — no headers, and specifically not `shop-domain`, are part of the signed material.

`HmacValidator.validate` computes the HMAC solely over `to_signable_string`: [2](#0-1) 

`Registry.process` then validates only this body-bound HMAC before trusting `request.shop` (read from `shopify-shop-domain`/`x-shopify-shop-domain` header, untouched by the signature) and forwarding it as the tenant key to the handler: [3](#0-2) [4](#0-3) 

Because the app's `client_secret` (the HMAC key) is shared across **all** merchants that install the app, a valid `(body, hmac)` pair generated for one shop's webhook delivery is byte-for-byte identical and still passes `OpenSSL.secure_compare` regardless of which `shop-domain` header accompanies it. An attacker who can obtain one legitimate webhook body+HMAC pair (e.g., by installing the app on their own store and capturing a delivered webhook, or by triggering an event whose payload content they control, such as `app/uninstalled` or a custom order with attacker-controlled fields) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value pointing at a victim shop. `HmacValidator.validate` will report success because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) data belongs to the victim shop: [5](#0-4) 

### Impact Explanation
Any host application that uses `request.shop` / `WebhookMetadata#shop` to key persistence, authorization, or business logic (the documented and expected usage pattern of this gem) can be made to attribute attacker-controlled webhook data to a shop the attacker does not own — a cross-tenant integrity violation. Depending on the handler, this can corrupt another merchant's stored state (e.g., inventory, order records, mandatory GDPR webhooks like `customers/redact`) or trigger tenant-scoped side effects using data the attacker fully controls. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The only precondition is possession of one legitimate `(raw_body, hmac)` pair for the target app — obtainable without any privileged credentials by installing the same app on an attacker-owned store, since the app's `client_secret` is identical for every installation and the signature never binds to the originating shop. No access token, `api_secret_key` leak, or TLS interception is required, keeping this within the unprivileged-internet-user threat model.

### Recommendation
Include the shop domain (and ideally other identifying headers such as `topic` and `webhook-id`) in the material that is authenticated, or independently verify that `request.shop` corresponds to a shop with an active installation/session before trusting it for tenant attribution, so the HMAC binds `shop == identity used downstream` rather than only the body bytes.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a webhook whose payload fields the attacker can influence (or capture any delivered webhook's raw JSON body and its `X-Shopify-Hmac-Sha256` value).
2. Replay an HTTP POST to the app's webhook endpoint with:
   - Body: the captured raw body (unmodified, so HMAC stays valid)
   - Header `X-Shopify-Hmac-Sha256`: the captured HMAC (unmodified)
   - Header `X-Shopify-Shop-Domain`: `victim.myshopify.com` (spoofed)
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` since it only checks the body against the HMAC: [6](#0-5) 
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"` and the attacker-controlled body, even though the data never originated from the victim's store.
