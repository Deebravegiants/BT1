### Title
Webhook shop/topic/webhook-id identity is not bound by HMAC, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC over the body only and then dispatches the handler using these unauthenticated header values as the tenant/topic identity, so anyone who can obtain one validly-signed webhook body (e.g. by installing the app themselves) can replay it with forged `shop-domain`/`topic` headers to impersonate any other shop.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`hmac` is computed from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are **not** included in `to_signable_string`, so they are never covered by the HMAC.

`Webhooks::Registry.process` validates only this body-only HMAC and then trusts the header-derived `shop`/`topic` to build `WebhookMetadata` for the handler: [2](#0-1) 

The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app — it is not shop-specific: [3](#0-2) 

The breaks the intended identity binding `shop authenticated == shop acted on`. In reality the equality holds only for `hmac(raw_body) == valid`, while `shop`/`topic`/`webhook_id` are taken from bytes that were never part of the signed input.

### Impact Explanation
Any merchant who installs the app receives real, correctly-signed webhooks for their own shop (topic, body, HMAC all valid, using the app's shared `client_secret`). Because the header fields identifying the tenant and topic are outside the HMAC, that same attacker can replay the captured `(raw_body, hmac-sha256 header)` pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain and/or `x-shopify-topic` with any registered topic. `Registry.process` will accept the forged request (HMAC still validates) and invoke the app's handler believing the event genuinely originated from the victim shop, causing cross-tenant data corruption/injection (e.g. forged `orders/create`, `app/uninstalled`, `customers/data_request`, `shop/redact` events being attributed to another merchant's store). This crosses a tenant boundary using only the app's own shared secret, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any user who can install the app (an ordinary, unprivileged merchant/internet user relative to other tenants) can trivially capture one legitimately-signed webhook body for their own store and issue a forged HTTP POST with different headers to the same publicly reachable webhook endpoint. No secret material beyond what the attacker already legitimately possesses (their own webhook deliveries) is required, and no mistakes by other parties are needed — this is a structural gap in what the gem signs versus what it trusts, not a rare operational error.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified, or otherwise cryptographically tie the header values to the signed body (e.g., include them in `to_signable_string`, or require the host application to look up/verify the shop domain against a known/installed-shop list rather than trusting the header verbatim). At minimum, document and enforce that `Webhooks::Request#shop`/`#topic`/`#webhook_id` must never be trusted as authenticated data — only the raw body is guaranteed authentic by `HmacValidator.validate`.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it's computed with the app's single shared `client_secret`.
2. Send a new HTTP request to the app's webhook endpoint with the *same* raw body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and, if desired, a different `X-Shopify-Topic`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `OpenSSL::HMAC.hexdigest(..., request.to_signable_string)` i.e. the body — validation succeeds.
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `victim.myshopify.com`/topic, so the app processes an event as if it legitimately came from the victim shop.
