### Title
Permanent freeze of escrowed funds and paymaster governance when the sole authorised relayer becomes unavailable, since the relayer-rotation path itself requires delivery by that same relayer - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
Several Hyperbridge apps (`IntentGatewayV2`/`ExtrinsicIntents`, `SimplexPaymaster`, `HostManager`) gate **every** `onAccept`/`onGetResponse` delivery — including the governance action that rotates the authorised relayer — behind a single-address check, `_checkRelayer`. If that one relayer address becomes unavailable (lost key, hardware failure, sanctions, or simple abandonment), no other account, not even Hyperbridge governance, can ever submit a transaction that passes the gate, because the very message that would rotate the relayer must itself be delivered by the now-unreachable relayer. This mirrors the Holograph C4 finding: a single designated executor becomes the only party who can unstick a protocol, and its unavailability (innocent or not) permanently freezes user funds with no fallback path.

### Finding Description
`ExtrinsicIntents._checkRelayer` runs first, before the request body is even decoded, on every `onAccept` and `onGetResponse` call: [1](#0-0) 

This check is applied uniformly to `onAccept`, covering both user-facing actions (`RedeemEscrow`, `RefundEscrow`) and Hyperbridge-governance-only actions (`NewDeployment`, `UpdateParams`, `SweepDust`, and `Execute`, which delegatecalls `setRelayer`/`upgradeToAndCall`): [2](#0-1) 

Crucially, `setRelayer` — the only writer of `_relayer` besides `initialize`/`migrate` — is `onlyHost`, reachable solely via the `Execute` request kind delegatecalled from inside `onAccept`: [3](#0-2) 

Because the `Execute`/`SetRelayer` message must pass through the same `onAccept` entry point, it is also gated by `_checkRelayer`. The documented design explicitly confirms this: "a delivery from anyone but the authorised relayer never decodes the body... The authorised relayer submitting the same message later takes the normal path", with no bypass for governance messages: [4](#0-3) 

The same architecture is used by `SimplexPaymaster`, whose own documentation acknowledges the exact single-point-of-failure risk: "Losing that key loses governance over the deposit, stake and surplus for good: there is no second key": [5](#0-4) 
And its `onAccept` applies `_checkRelayer` uniformly to all `RequestKind`s including `SetRelayer` itself: [6](#0-5) [7](#0-6) 

By contrast, `BridgeToken`'s relayer gate does *not* create this trap, because its `setRelayer` is `onlyOwner`, an independent escape hatch not routed through the relayer-gated `onAccept`: [8](#0-7) 
This asymmetry underscores that `IntentGatewayV2`/`ExtrinsicIntents` and `SimplexPaymaster` lack any equivalent independent recovery mechanism.

### Impact Explanation
For `IntentGatewayV2`, user funds are escrowed on the source chain pending a `RedeemEscrow` or `RefundEscrow` delivery gated by the same relayer check as governance. If the sole relayer becomes unavailable:
- Solvers who filled cross-chain orders can never have their escrow released (`RedeemEscrow` blocked).
- Users who cancelled orders can never get refunds (`RefundEscrow` blocked).
- Governance cannot rotate the relayer (`Execute`/`setRelayer` blocked by the same gate), cannot register new deployments, update params, or sweep dust.

This is a **permanent freezing of funds** with no recovery path — worse than the Holograph analog, where governance eventually proposed a fallback (force-fail after `EXPIRY_NUM` blocks). Here there is no timeout, no alternate submitter, and no owner-level override for the gateway.

For `SimplexPaymaster`, losing the relayer key permanently locks the EntryPoint deposit, stake, and accumulated markup surplus, and blocks any future upgrade or parameter change — as the code comments themselves warn.

### Likelihood Explanation
The relayer here is described as "a plain EOA" whose key is the sole trust anchor: [9](#0-8) 
EOA key loss, operational turnover, infrastructure failure, or regulatory/sanction risk against a single operational address are realistic, non-malicious events — directly analogous to the "innocent" scenario in the Holograph report (hardware failure causing loss of wallet access). Given that this is an intentional design accepted as a documented tradeoff ("Losing that key loses governance... for good: there is no second key"), it is a known but unmitigated single point of failure reachable by ordinary relayer downtime, not by any admin/governance misbehavior.

### Recommendation
Introduce an independent recovery path for the relayer-rotation message that does not depend on the very relayer being rotated, mirroring the Holograph reviewers' accepted mitigation of allowing a fallback path after some condition elapses:
- Allow a `setRelayer`/`Execute` governance message to be delivered by *any* submitter once a configurable timeout has elapsed without delivery by the authorised relayer (analogous to Holograph's suggested "force-fail after EXPIRY_NUM blocks").
- Alternatively, gate only user-facing actions (`RedeemEscrow`/`RefundEscrow`) behind `_checkRelayer`, while keeping governance actions (`Execute`, `SetRelayer`, `UpdateParams`, upgrades) reachable by any relayer as long as the `Hyperbridge` source check passes (the `keccak256(incoming.request.source)` check already authenticates that the message content originated from real Hyperbridge governance, independent of relayer identity).
- Add a secondary/owner-level recovery mechanism (as already exists for `BridgeToken.setRelayer`, which is `onlyOwner`) for `IntentGatewayV2` and `SimplexPaymaster`.

### Proof of Concept
Conceptual sequence, following the tested flow in `evm/tests/foundry/IntentGatewayV2Test.sol`:
1. Governance arms the relayer gate on `IntentGatewayV2` via `migrate(relayerA)`, as exercised by `testFreshProxyIsOpenUntilGovernanceArmsIt`: [10](#0-9) 
2. `relayerA`'s key is lost (analogous to Holograph's "hardware failure that caused a loss of access to the wallet").
3. A solver fills a cross-chain order; the resulting `RedeemEscrow` message can only be delivered by `relayerA` — confirmed by `testOnAcceptRejectsUnlistedRelayer`, which shows any other submitter reverts with `Unauthorized` and escrow stays untouched: [11](#0-10) 
4. Governance attempts to rotate away from the lost relayer by dispatching an `Execute`/`setRelayer` message. This message is also delivered through `onAccept`, and per `testOnAcceptGovernanceRejectsUnlistedRelayer` an upgrade/governance delivery from anyone but the authorised relayer reverts with `Unauthorized`: [12](#0-11) 
5. Since `relayerA`'s key is permanently lost, step 4 can never succeed, and the escrowed funds from step 3 (and all future orders) remain frozen indefinitely.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) {
            revert UnauthorizedCall();
        }

        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        bytes calldata payload = incoming.request.body[1:];

        if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(payload, (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        } else if (kind == RequestKind.UpdateParams) {
            _setParams(abi.decode(payload, (Params)));
        } else if (kind == RequestKind.RegisterToken) {
            (address token, address oracle) = abi.decode(payload, (address, address));
            _registerToken(token, AggregatorV3Interface(oracle));
        } else if (kind == RequestKind.DeactivateToken) {
            _deactivateToken(abi.decode(payload, (address)));
        } else if (kind == RequestKind.WithdrawAssets) {
            (address token, uint256 amount) = abi.decode(payload, (address, uint256));
            _withdrawAssets(token, amount);
        } else if (kind == RequestKind.UnlockStake) {
            entryPoint().unlockStake();
        } else if (kind == RequestKind.WithdrawStake) {
            entryPoint().withdrawStake(payable(treasury));
        } else if (kind == RequestKind.SetRelayer) {
            address newRelayer = abi.decode(payload, (address));
            if (newRelayer == address(0)) revert ZeroAddress();
            _setRelayer(newRelayer);
        }
    }

    function testOnAcceptGovernanceRejectsUnlistedRelayer() public {
        // UpgradeContract: a forged upgrade cannot land unless the relayer submits it.
        address implBefore = _implementationOf(address(intentGateway));
        IntentGatewayV2Upgraded newImpl = new IntentGatewayV2Upgraded(address(this));
        PostRequest memory upgrade = _upgradeRequest(host.hyperbridge(), address(newImpl), "");

        vm.prank(address(host));
        vm.expectRevert(IntentsBase.Unauthorized.selector);
        intentGateway.onAccept(IncomingPostRequest({relayer: filler, request: upgrade}));
        assertEq(_implementationOf(address(intentGateway)), implBefore, "implementation unchanged");

        // NewDeployment: the gate runs before the body is decoded, so every kind is covered.
        PostRequest memory deployment = _newDeploymentRequest(bytes("NEW_CHAIN"), address(0xBEEF));
        vm.prank(address(host));
        vm.expectRevert(IntentsBase.Unauthorized.selector);
        intentGateway.onAccept(IncomingPostRequest({relayer: filler, request: deployment}));
        vm.expectRevert(IntentsBase.UnknownInstance.selector);
        intentGateway.instance(bytes("NEW_CHAIN"));

        vm.prank(address(host));
        intentGateway.onAccept(IncomingPostRequest({relayer: relayer, request: deployment}));
        assertEq(intentGateway.instance(bytes("NEW_CHAIN")), address(0xBEEF), "relayer-submitted governance applies");
    }

    function testFreshProxyIsOpenUntilGovernanceArmsIt() public {
        IntentGatewayV2 gateway = _freshInitializedGateway();
        assertEq(gateway.relayer(), address(0), "no relayer after initialize");

        PostRequest memory deployment = _newDeploymentRequest(bytes("NEW_CHAIN"), address(0xBEEF));
        deployment.from = abi.encodePacked(address(gateway));
        deployment.to = abi.encodePacked(address(gateway));

        // Open: an arbitrary relayer's delivery is applied.
        vm.prank(address(host));
        gateway.onAccept(IncomingPostRequest({relayer: filler, request: deployment}));
        assertEq(gateway.instance(bytes("NEW_CHAIN")), address(0xBEEF), "open gate applies governance");

        // Armed by a rotation: only `relayer` from now on, version unchanged.
        vm.prank(address(host));
        gateway.setRelayer(relayer);
        assertEq(gateway.version(), 2, "a rotation leaves the version alone");
        PostRequest memory another = _newDeploymentRequest(bytes("OTHER_CHAIN"), address(0xCAFE));
        another.from = abi.encodePacked(address(gateway));
        another.to = abi.encodePacked(address(gateway));

        vm.prank(address(host));
        vm.expectRevert(IntentsBase.Unauthorized.selector);
        gateway.onAccept(IncomingPostRequest({relayer: filler, request: another}));
        vm.expectRevert(IntentsBase.UnknownInstance.selector);
        gateway.instance(bytes("OTHER_CHAIN"));

        vm.prank(address(host));
        gateway.onAccept(IncomingPostRequest({relayer: relayer, request: another}));
        assertEq(gateway.instance(bytes("OTHER_CHAIN")), address(0xCAFE));
    }
