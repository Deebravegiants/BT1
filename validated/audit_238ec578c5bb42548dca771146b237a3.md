## Analysis

The strongest structural analog to the Knox `Auction.sol` bug (an unguarded subtraction that assumes an amount already "consumed" is still available, causing every subsequent user operation that hits the same code path to revert) is the pnl-accounting subtraction pattern used by every reachable AMM instruction — `Initialize2`-created pools going through `Deposit`, `Withdraw`, and both swap instructions.

### Title
Unwrap-based subtraction in PnL bookkeeping can permanently freeze `Deposit`/`Withdraw`/swap paths - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
Every reachable liquidity instruction (`process_deposit`, `process_withdraw`, `process_swap_base_in(_v2)`, `process_swap_base_out(_v2)`, `process_withdrawpnl`) first calls `Calculator::calc_total_without_take_pnl_no_orderbook`, which subtracts the accrued `state_data.need_take_pnl_pc` / `need_take_pnl_coin` from the vault balances: [1](#0-0) 

and then `Processor::calc_take_pnl`, which further mutates those already-subtracted totals with a *second*, unrelated `.unwrap()`-guarded `checked_sub`: [2](#0-1) 

Finally, `process_withdraw` performs a third, compounded subtraction to update `target_orders.calc_pnl_x` / `calc_pnl_y`, again via `.unwrap()` on `checked_sub`, mixing a pre-pnl normalized total (`x1`/`y1`) with a post-pnl-derived withdrawal share (`pc_amount`/`coin_amount`) and the pnl delta (`delta_x`/`delta_y`): [3](#0-2) 

### Finding Description
`calc_take_pnl` is invoked from every deposit, withdraw and `withdrawpnl` call, and increments `amm.state_data.need_take_pnl_pc/coin` (a value only ever decremented by the privileged `process_withdrawpnl` caller) while decrementing a **local, in-memory** `total_pc_without_take_pnl`/`total_coin_without_take_pnl` with a raw `.unwrap()`: [4](#0-3) 

Any unprivileged caller can drive this code path repeatedly (every swap/deposit/withdraw re-invokes it), and its correctness depends on the invariant `pool_pc*pool_coin ≥ calc_pc*calc_coin` holding exactly and on `x1/y1` (computed **before** `calc_take_pnl` mutates the totals) staying perfectly consistent with the later-derived `pc_amount`/`coin_amount`/`delta_x`/`delta_y` used in `process_withdraw`'s final bookkeeping update: [5](#0-4) [6](#0-5) 

Because `target_orders.calc_pnl_x`/`calc_pnl_y` are updated using `x1 - normalize(pc_amount) - delta_x` rather than the mathematically defined `x2 = sqrt(last_k * current_price)` that `calc_take_pnl`'s own doc-comment specifies, any accumulated rounding drift from repeated decimal-normalization (`normalize_decimal_v2`/`restore_decimal`) across many `Deposit`/`Withdraw` cycles — all reachable by ordinary LPs choosing attacker-controlled `deposit`/`withdraw` amounts — can make the second `checked_sub` in this chain fail. Since this happens inside `.unwrap()`, the transaction panics/aborts instead of returning a graceful `ProgramError`, and because the underlying state (`need_take_pnl_pc/coin`, `calc_pnl_x/calc_pnl_y`) is a function of the persisted `AmmInfo`/`TargetOrders` accounts rather than of the caller's specific input, the failure is deterministic for the *next* caller as well — mirroring exactly the Knox pattern where a stale/incorrectly-tracked running total causes a `checked_sub` to underflow for every subsequent withdrawer, not just the one who triggered the imbalance.

### Impact Explanation
If the bookkeeping subtraction fails, `process_withdraw` (and by the same code path, `process_deposit`/swap, all of which call `calc_total_without_take_pnl_no_orderbook`) reverts for every caller touching that pool, since the divergence lives in on-chain `AmmInfo.state_data`/`TargetOrders` and is not undone by a failed transaction. This constitutes permanent freezing of LP principal and pending swap liquidity in the affected pool — no legitimate `Withdraw`, `Deposit`, `SwapBaseIn`, or `SwapBaseOut` can succeed until/unless the imbalance is externally corrected (which, per code, only the privileged `pnl_owner` via `process_withdrawpnl` can influence, and only in the `need_take_pnl_*` half of the equation, not the `calc_pnl_x/y` half touched by `process_withdraw`).

### Likelihood Explanation
Reaching the vulnerable code only requires ordinary, permission-less `Deposit`/`Withdraw` calls with attacker-chosen amounts against a pool that has accrued any positive `pnl` (i.e., any pool where trading fees have made `k` grow, which is the normal, expected state of an active AMM pool). No privileged signer, off-chain component, or non-default build is needed — every step is exercised through the standard `Initialize2` → `Deposit`/`Withdraw`/swap instruction flow described in the audit scope. The exact numerical conditions that trigger the underflow depend on decimal-normalization rounding across repeated pnl-taking cycles, so likelihood is tied to pool age/volume rather than a single crafted transaction, which is consistent with a Medium-High likelihood rather than trivially reproducible in one call.

### Recommendation
- Replace the ad-hoc `x1 - normalize(pc_amount) - delta_x` recomputation of `target_orders.calc_pnl_x`/`calc_pnl_y` in `process_withdraw` (and the analogous computation in `process_withdrawpnl`) with the `x2`/`y2` values already computed inside `calc_take_pnl`, which are the values the function's own doc-comment defines as the correct post-pnl baseline.
- Replace `.unwrap()` on the `checked_sub` calls in `calc_take_pnl` (`program/src/processor.rs:257-262`) and in the `process_withdraw` pnl-baseline update (`program/src/processor.rs:1819-1838`) with `.ok_or(AmmError::CheckedSubOverflow)?` (as already done in `calc_total_without_take_pnl_no_orderbook`) so any residual mismatch surfaces as a recoverable program error rather than a deterministic, unrecoverable panic that can be replayed by any future caller.
- Add an explicit invariant check/test verifying that `need_take_pnl_pc/coin` can never be updated in a way that makes a future `calc_total_without_take_pnl_no_orderbook` or `process_withdraw` bookkeeping step underflow, across many sequential deposit/withdraw/swap cycles with mismatched `coin_decimals`/`pc_decimals`.

### Proof of Concept
1. Create a pool via `process_initialize2` with `coin_decimals != pc_decimals` (common for real token pairs) so `normalize_decimal_v2`/`restore_decimal` introduce rounding.
2. Perform a sequence of ordinary `SwapBaseIn`/`SwapBaseOut` calls to grow `k`, causing `calc_take_pnl` to repeatedly trigger inside `process_deposit`/`process_withdraw`, incrementing `need_take_pnl_pc/coin` and updating `target_orders.calc_pnl_x/calc_pnl_y` via `x1 - normalize(pc_amount) - delta_x` each time.
3. Perform interleaved `Deposit`/`Withdraw` calls with amounts chosen (by the caller, unprivileged) to maximize rounding divergence between `x1` (computed pre-pnl) and the later `normalize(pc_amount) + delta_x` sum.
4. Once accumulated rounding pushes `normalize(pc_amount) + delta_x > x1` (or the coin-side equivalent) for some legitimate withdrawal request, `process_withdraw`'s `.unwrap()` at `program/src/processor.rs:1819-1838` panics, aborting the transaction.
5. Because the on-chain `TargetOrders`/`AmmInfo` state that produced the mismatch persists (only the failing transaction's writes are rolled back, not the pre-existing stored `calc_pnl_x/y`/`need_take_pnl_*`), every subsequent `Withdraw` (and any `Deposit`/swap that re-enters the same pnl computation) against this pool continues to hit the same underflow, freezing all LP funds in the pool.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
