## Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the shop domain, topic, and webhook id are taken from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only verifies the body against the HMAC, so a valid `(body, hmac)` pair proves the request came from *some* shop that has this app installed, but it says nothing about which shop the attached `shop-domain`/`topic`/`webhook-id` headers describe.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by checking the body's HMAC: [1](#0-0) [1](#0-0) 

It then builds the metadata that is handed to the app's handler directly from unauthenticated headers: [2](#0-1) 

`Request#to_signable_string` is the value that is actually HMAC-verified, and it is only `@raw_body`: [3](#0-2) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic binding to the body or to the HMAC: [4](#0-3) 

The HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, and `HmacValidator.validate` performs no per-shop keying: [5](#0-4) 

The intended binding is: `hmac_valid(body) ⇒ (shop, topic, webhook_id) attached to that body are the ones Shopify actually sent for that shop/topic`. That binding does not hold, because the signature covers only the body bytes, not the headers that identify the tenant and event type.

### Impact Explanation
Any merchant who has installed the app on their own store (an "unprivileged" outsider relative to any other tenant of the same app) receives genuine webhook deliveries with a valid `x-shopify-hmac-sha256` for their own event bodies, since the same `client_secret` is used to sign webhooks for all shops of the app. That attacker can capture one such `(raw_body, hmac)` pair from their own shop and replay it to the app's webhook endpoint while freely rewriting `x-shopify-shop-domain` to a victim shop's domain (and/or `x-shopify-topic`/`x-shopify-webhook-id` to any registered topic they choose, as long as a body with that valid-looking shape passed the earlier HMAC check for the topic dispatch to succeed). `Registry.process` will accept the request (HMAC checks out) and invoke the registered handler with `WebhookMetadata.shop` set to the victim's domain and the attacker-originated body. Any host application that trusts `WebhookMetadata#shop` to select/scope the tenant record to update (which is the entire documented purpose of this field, and the standard usage pattern shown in `docs/`) will apply attacker-controlled webhook data to the wrong tenant's records — a cross-tenant data-confusion/injection primitive rooted entirely in this gem's own webhook authentication code.

### Likelihood Explanation
The only precondition is that the attacker can install the app on any shop and trigger any webhook event on it (e.g., `orders/create`) — no elevated privileges, no leaked credentials, and no dependency on host misuse of the API are required. This is a normal, unprivileged interaction with a public webhook endpoint that every embedded/public Shopify app exposes.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or independently verify `request.shop` against the shop the webhook subscription was registered for/known offline session before dispatch, e.g., include the `x-shopify-shop-domain` header in `to_signable_string`, or require callers of `Registry.process` to supply an expected shop and reject mismatches before invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers `orders/create`. Shopify sends a webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker resends the same `B` and `hmac` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against the shared `client_secret`: [6](#0-5) 
4. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's body, even though that body never originated from the victim's shop.
