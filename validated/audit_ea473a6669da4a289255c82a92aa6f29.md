### Title
Webhook tenant identity (`shop-domain`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's `WebhookHandler#handle` from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies covers only the raw request body. Because the same `client_secret` (`Context.api_secret_key`) signs webhooks for *every* shop that has installed the app, any merchant who has installed the app can capture a validly-signed `(body, hmac)` pair delivered to their own store and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The library reports this forged `shop` value to the handler as trusted, authenticated data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `to_signable_string` (the body) and compares it to the `hmac` field, never incorporating `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate` passes, and then forwards `request.shop` — the unverified header — directly into `WebhookMetadata`, which is passed to the app-defined handler as the authoritative tenant identity: [4](#0-3) [5](#0-4) 

**Broken binding:** `verified_bytes = {raw_body}` but `acted_upon_bytes = {raw_body, shop_domain_header}`. The identity field (`shop`) that determines *which tenant's data/session* the app will act on is not included in the signed payload, so `verify(hmac, body) == true` does not imply `shop_header` is authentic.

Because Shopify webhooks for a given app are signed with the app's single, shop-agnostic `client_secret` (not a per-shop secret), a `(body, hmac)` pair that is valid for shop A's own webhook delivery remains a byte-for-byte valid signature regardless of which shop's data it is claimed to represent. An attacker who is a legitimate merchant of the app (i.e., has installed it and receives webhooks for their own store) can:
1. Capture a webhook delivered to their own endpoint (valid `body` + `hmac-sha256` header, signed with the shared `client_secret`).
2. Replay that exact `body` and `hmac` header to the app's webhook endpoint, but substitute `x-shopify-shop-domain` with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never looked at the domain), and `Registry.process` invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`.

If the host application (as documented/intended by this gem's API) uses `data.shop` to select which merchant's session/access-token/database record to act on — which is exactly the purpose this field serves in `WebhookMetadata` — the attacker can inject attacker-controlled, "verified" webhook data into the victim tenant's processing path, achieving cross-tenant data injection/cross-tenant access without ever needing the victim's credentials.

### Impact Explanation
This breaks the tenant isolation guarantee the gem is supposed to provide via HMAC verification: a request that fails to prove which shop it came from is nonetheless treated as authenticated for that shop. This falls under the "Critical - cross-tenant access" impact category, since it lets one tenant's (attacker's) data be injected into another tenant's (victim's) processing pipeline while passing the library's own signature check.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must be (or control) an app-installing merchant so they can obtain at least one genuinely-signed `(body, hmac)` pair from the shared `client_secret` — no leaked/privileged credentials or access tokens are required, only ordinary use of the app as an unprivileged internet-accessible merchant. Any topic can be reused (e.g., `orders/create`, `app/uninstalled`), and the header is trivially spoofable by any client posting to the public webhook endpoint. This makes the attack readily achievable by any unprivileged internet user who can install the target app on a store they control.

### Recommendation
Do not treat header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) as authenticated merely because the body's HMAC validates. Options:
- Bind the shop domain into the signed material the library checks (e.g., require and cryptographically verify shop identity via a separate authenticated channel, such as comparing against session/shop records established during OAuth, rather than trusting the header verbatim), or
- At minimum, document/expose that `Request#shop` (and other headers) are NOT covered by `HmacValidator.validate`, and require host applications to cross-check `request.shop` against an independently established, per-shop session before acting on the payload.
- Consider incorporating the shop domain into the signable string used for HMAC comparison if Shopify's delivery signature ever supports it, or require host apps to look up the destination by webhook subscription/address rather than trusting the header.

### Proof of Concept
```ruby
# Attacker controls "attacker-shop.myshopify.com" (a real install of the target app)
# and captures a legitimate webhook delivery to their own endpoint:

raw_body = '{"id":123,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key,   # shared client_secret, same for all shops
  raw_body,
)

# Attacker replays the exact same body+hmac, but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- forged, not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes verification because HmacValidator only checks raw_body against the shared secret:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily hands this to the handler as if it came from victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
``` [4](#0-3) [6](#0-5)
