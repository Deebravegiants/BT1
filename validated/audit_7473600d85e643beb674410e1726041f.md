### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values consumed by the handler come from unauthenticated HTTP headers. Any user who can obtain one genuine, validly-signed webhook for an app (e.g. by installing the app on their own store) can replay that body/signature pair while rewriting the `x-shopify-shop-domain` header to name a different (victim) shop, and the gem will report the webhook as valid and hand the forged shop identity to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines its `to_signable_string` as just the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers, none of which are included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, unconditionally trusts `request.shop` (and the other header-derived fields) when building the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only compares the HMAC against `to_signable_string`, i.e., the raw body — never the headers: [4](#0-3) 

Because an app's `api_secret_key` (the HMAC key) is shared across every shop that has the app installed, any user who installs the app on a store they control receives real, validly-signed webhooks for that store. Since the signature never binds to the `shop-domain` header, that attacker can capture a legitimate `(raw_body, hmac)` pair and POST it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The library still reports the HMAC as valid (the body/signature pair is genuine) and forwards `shop: <victim>` with the attacker's own body content to the handler, breaking the identity binding: shop authenticated by HMAC (none) versus shop asserted to the handler (attacker-controlled header). The library's own documentation states that `process` "will verify the request did indeed come from Shopify," which overstates the actual guarantee and encourages downstream apps (e.g., via `shopify_app`) to trust `data.shop` without independently re-validating it: [5](#0-4) 

### Impact Explanation
This lets any attacker who has legitimately installed the target app on their own tenant forge webhooks that are attributed to an arbitrary other shop. Downstream handlers that key off `data.shop` (as the shipped example handler and the documented usage pattern do) to look up sessions, update per-tenant records, or trigger tenant-scoped side effects can be tricked into applying attacker-supplied webhook payloads to a victim shop's account — a cross-tenant integrity/confusion issue.

### Likelihood Explanation
Exploitation only requires the attacker to have (or create) their own Shopify store and install the target app to receive one legitimately signed webhook — no access to the app's `client_secret`, no privileged account, and no interaction with the victim is required. The webhook endpoint is a normal public HTTP endpoint that must accept unauthenticated requests from "Shopify," making this reachable directly from the internet.

### Recommendation
Bind the identity-relevant headers (`shop`, `topic`, `api_version`, `webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie them to the signed body, so a captured signature cannot be replayed against a different shop/topic. At minimum, document and/or enforce that `process` only guarantees the body's authenticity and that callers must independently verify `shop` against their own known set of installed shops before trusting it.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` — both computed with the app's shared `api_secret_key`.
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B` [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's data>, ...)`, so the app processes attacker-controlled data as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
