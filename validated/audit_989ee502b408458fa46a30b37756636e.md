### Title
Soft `MAX_VIEW_STATE_PAGE_BYTES` cap in `view_state` pagination can be bypassed by a single oversized value, causing unbounded response size for a free RPC call - (File: runtime/runtime/src/state_viewer/mod.rs)

### Finding Description
`TrieViewer::view_state` paginates contract storage by accumulating `StateItem`s into a page and checking the running byte size against `MAX_VIEW_STATE_PAGE_BYTES` **before** appending each item, per the code's own comment that "a page can run one item over." [1](#0-0) . Because the size check happens before, not after, appending an item, the enforcement only bounds the size of the page *excluding* the last item added — it never caps the size of that last item itself. An unprivileged account can deploy a contract that, via a normal contract call, writes a single storage value close to the protocol's maximum value-size limit (on the order of megabytes, far above the 50,000-byte page target) under its own account's contract-data trie-key prefix. When any client then issues a paginated `view_state` query (e.g., `limit=Some(1)` or landing on that key as the first item of a page), the pre-append check passes (page is still empty/small), the oversized value is appended, and only then does the page exceed the cap — but by that point the value has already been read from the trie, deserialized, and included in the RPC response.

### Impact Explanation
This allows an attacker-controlled account to force the RPC node to allocate, serialize, and return payloads far larger than the documented/intended 50,000-byte page cap for a free, unauthenticated `view_state` query. Since `view_state` is a read-only RPC call typically not gated by gas or fees, this is a free/underpriced-execution style resource-exhaustion vector: repeated calls against such an account amplify memory/CPU/bandwidth usage on RPC nodes disproportionately to the cost paid by the attacker, matching the "node panic or unbounded resource use" bounty impact class.

### Likelihood Explanation
Preconditions are minimal and fully within reach of an ordinary account holder: deploy/own a contract, issue a normal function call that writes one large value to storage (bounded only by the runtime's max value-size parameter, which is set well above 50,000 bytes), and then trigger (or wait for a client to trigger) a paginated `view_state` request against that account. No privileged role, node compromise, or network-layer control is required, making this readily and repeatably exploitable.

### Recommendation
Change the pagination check in `view_state` to enforce the byte cap strictly, e.g. check the size **after** tentatively adding the candidate item and, if it would exceed `MAX_VIEW_STATE_PAGE_BYTES`, stop the page before including that item (unless the page is currently empty, in which case cap the single oversized item's inclusion separately or return an explicit "value too large to page" error). Additionally, consider enforcing a hard per-item size ceiling independent of the page-level soft cap so a single value can never dominate a response.

### Proof of Concept
Unit test in `runtime/runtime/src/state_viewer/mod.rs` (or its test module):
1. Seed a `TrieUpdate` with an account and a single contract-data key under that account's prefix whose value is significantly larger than `MAX_VIEW_STATE_PAGE_BYTES` (e.g. several MB, staying under the protocol's max value-size limit).
2. Call `TrieViewer::view_state` with `limit=Some(1)` (or without a `from_key` such that this item is the first candidate for the page).
3. Assert that the returned `ViewStateResult` page's serialized/total byte size does not scale with the attacker-chosen value size and stays within a fixed hard bound (e.g. `MAX_VIEW_STATE_PAGE_BYTES` plus a small fixed slack), failing today because the returned page instead grows to the full multi-megabyte value size.
