Found a genuine analog: `AncestryChain::ancestry` in the GRANDPA justification verifier walks a `while` loop over an attacker-supplied `votes_ancestries` map, and can loop indefinitely (or panic) on crafted, cyclic input — directly analogous to the Exiv2 infinite-loop bug, and reachable from a single relayed consensus proof.

### Title
Infinite loop / unbounded walk in GRANDPA `AncestryChain::ancestry` on cyclic or malicious ancestry proof - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`GrandpaJustification::verify_with_voter_set` builds an `AncestryChain` directly from the untrusted, relayer-submitted `votes_ancestries: Vec<H>` field of a GRANDPA justification, then calls `ancestry.ancestry(base_hash, target_hash)` for every precommit to reconstruct the route to the finalized base block.

### Finding Description
`AncestryChain::new` indexes `votes_ancestries` into a `BTreeMap<H::Hash, H>` keyed by each header's own hash, with **no validation that `parent_hash` pointers form an acyclic chain terminating at `base`**: [1](#0-0) 

The `ancestry()` walk then follows `parent_hash` pointers via a `while current_hash != base` loop: [2](#0-1) 

Because the map is built from attacker-controlled header structs (each header's `hash()` and `parent_hash()` are both attacker-chosen fields inside the encoded justification, not independently verified against a real chain), an attacker can craft two or more headers whose `parent_hash` pointers form a cycle that never reaches `base_hash`. On each iteration `self.ancestry.get(&current_hash)` will succeed (since the cyclic headers are present in the map) and `route.push(current_hash)` will keep growing, so the loop never hits the `Err(NotDescendent)` branch and never terminates — an unbounded loop with an ever-growing `Vec<H::Hash>`, i.e. a memory-exhaustion/CPU-exhaustion condition, exactly mirroring the Exiv2 infinite-loop-on-crafted-input bug class.

This function is called for **every precommit** in the commit from `verify_with_voter_set`: [3](#0-2) 

`verify`/`verify_with_voter_set` is the standard entry point used by GRANDPA/BEEFY-relay consensus clients when a relayer submits a justification-bearing proof to the chain (e.g. via `ismp-grandpa`'s consensus update extrinsic). A single malicious relayer-submitted proof containing a crafted `votes_ancestries` list with cyclic parent pointers is thus enough to trigger the unbounded loop during on-chain proof verification.

### Impact Explanation
An unbounded loop reached during on-chain consensus-proof verification causes the extrinsic to consume unbounded weight/gas until it exhausts the block's execution budget or hits an OOM from the ever-growing `route` vector, effectively hanging block execution for that transaction. Because GRANDPA-relay clients gate delivery of every cross-chain message routed through that consensus client, a stuck/failing verification path denies message delivery for the whole route — a "route unable to deliver messages" condition, which is explicitly in-scope as Medium/High impact per the validation rules.

### Likelihood Explanation
The `votes_ancestries` vector and each header's `parent_hash` are fully attacker-controlled fields within the SCALE-encoded justification that a relayer submits. No relaychain-consensus-independent validation (e.g., verifying real header hashes/PoW/consensus digests) is performed before the headers are indexed and walked — the function trusts the caller-supplied header set completely for routing purposes. Crafting two headers `A -> B -> A` (or any cycle not containing `base`) is trivial and deterministic, requiring no cryptographic break, only correct construction of the header fields consumed by `ancestry()`. This makes the bug reliably triggerable by any single malicious/relayed proof.

### Recommendation
Bound the ancestry walk with a maximum hop count (e.g., derived from `votes_ancestries.len() + 1`) and/or track visited hashes during the walk, returning `Err(NotDescendent)` immediately if a hash is revisited before reaching `base`. This closes the cycle regardless of how the attacker links `parent_hash` fields, mirroring the fix pattern used for the Exiv2 bug (bounding the loop / detecting non-progress before deleting/walking further).

### Proof of Concept
1. Construct two headers `A` and `B` such that `A.parent_hash = B.hash()` and `B.parent_hash = A.hash()`, with a `target_hash` (precommit) equal to `A.hash()` and `base_hash` equal to some unrelated hash `C` not present in either header.
2. Build a `Commit` whose precommits target `A`'s hash, with valid signatures from a legitimate-looking authority set (attacker still needs some valid-looking commit structure to pass earlier checks, but the ancestry cycle itself requires no cryptographic material beyond hash consistency).
3. Set `votes_ancestries = vec![A, B]`.
4. Call `GrandpaJustification::verify_with_voter_set`; internally `ancestry.ancestry(base_hash=C, block=A.hash())` enters the `while current_hash != base` loop in [4](#0-3) , oscillating between `A` and `B` forever since `C` is never reached, growing `route` without bound and never returning.

	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
