## Finding

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by checking the raw HTTP body against the `X-Shopify-Hmac-Sha256` header, but the `shop` value it hands to application handlers is read from the unauthenticated `X-Shopify-Shop-Domain` header, which is never part of the signed bytes. An attacker who controls one shop can therefore replay a genuine (validly-signed) webhook body from their own shop while swapping the shop-domain header to impersonate a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is completely outside that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC` over `verifiable_query.to_signable_string` (i.e., only the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate, then immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header — and forwards it to the app-supplied handler: [4](#0-3) 

The identity binding the library is supposed to enforce is: *"shop that produced/authorized this payload" == "shop used to attribute/store this payload."* Instead, the equality actually enforced is only *"body bytes" == "HMAC(body bytes, secret)"*, with `shop` entirely decoupled from that proof. Because the HMAC secret (`api_secret_key`) is shared across all shops installed on a given app (it's the app's secret, not a per-shop secret), any shop that has this app installed can obtain a validly-signed webhook body (e.g., from any webhook Shopify sends them) and resend it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` will still return `true` because it never looks at the header, and `Registry.process` will hand the forged `shop` value straight to `WebhookHandler#handle`.

### Impact Explanation
This breaks the tenant boundary the gem is documented to protect: `docs/usage/webhooks.md` instructs developers to trust `Registry.process`'s HMAC check as proof the webhook "did indeed come from Shopify," and to use the resulting `WebhookMetadata#shop` to route/attribute data per shop: [5](#0-4) 

An unprivileged attacker who is merely a merchant using the app (no access token, no `api_secret_key`, no privileged account) can forge a webhook that is validated as authentic for a victim shop while carrying attacker-controlled body content. Applications that key their per-shop side effects (order/inventory writes, cache invalidation, session/state lookups) off `WebhookMetadata#shop` — the pattern this library's own documentation recommends — will process attacker data under the victim shop's identity, i.e. cross-tenant data injection/corruption.

### Likelihood Explanation
Any shop that installs the app can trivially capture one legitimate signed webhook body/HMAC pair addressed to itself (webhooks fire routinely, e.g. `orders/create`), then replay that exact body + HMAC header to the app's public webhook URL while substituting the shop-domain header. No secret material, TLS interception, or social engineering is required — only network access to the app's already-public webhook endpoint, which by design accepts unauthenticated POSTs.

### Recommendation
Bind the trusted `shop` identity to something that is actually covered by the signature/authentication proof, not to an attacker-controllable header:
- Include the shop-domain (and ideally topic) in the signable string used for HMAC verification, or
- Cross-check `request.shop` against an out-of-band trusted source (e.g., the shop associated with the webhook subscription/session that was registered), rejecting the webhook if they don't match, before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. App has two merchants installed: `attacker.myshopify.com` and `victim.myshopify.com`, both sharing the same app `api_secret_key`.
2. Attacker's shop triggers/receives a legitimate webhook, e.g. body `{"id":1,...}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `raw_body` vs the HMAC header) — see `lib/shopify_api/webhooks/request.rb:35-43` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`) and invokes the app's handler, which processes attacker-supplied data as if it belongs to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
