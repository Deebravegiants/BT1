### Title
Webhook shop identity spoofing via HMAC that only covers the raw body, not the `shop-domain`/`topic`/`webhook-id` headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop`, `topic`, `webhook_id`, and `api_version` fields entirely from HTTP headers, while its HMAC signature (`to_signable_string`) only covers the raw request body. `Webhooks::Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields to dispatch the webhook to the merchant-supplied handler, breaking the binding: `HMAC-authenticated bytes == identity fields acted upon`.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers: [2](#0-1) 

But `to_signable_string`, the value that is HMAC-verified, is only the raw body: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC over the body, then immediately trusts the header-derived `request.shop`, `request.topic`, and `request.webhook_id` to route and label the webhook to the app's handler: [4](#0-3) 

Because the same `api_secret_key` is shared by an app across every shop that installs it, any user who installs the app on their own store (an ordinary, unprivileged action) receives legitimately-signed webhook deliveries (body + valid `X-Shopify-Hmac-Sha256`). That attacker can capture one such valid `(raw_body, hmac)` pair — trivial for topics like `app/uninstalled`, `orders/create` with attacker-controlled content, or any predictable-body webhook — and replay it to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) to reference a victim shop. `Utils::HmacValidator.validate` only checks the body against the secret: [5](#0-4) 

so the forged request passes validation, and the handler executes believing the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: the shop identity that is *acted upon* (used to attribute webhook data, trigger mandatory compliance flows like `customers/redact`/`shop/redact`, or drive per-tenant business logic in the host app's handler) is not covered by the cryptographic signature that is *verified*. This is a direct cross-tenant confusion vector — the attacker (who only needs their own, unprivileged app installation) can cause the app to process/attribute data under another merchant's identity.

### Likelihood Explanation
Requires only an unprivileged install of the target app (or knowledge of one predictable/replayable signed webhook body) plus the ability to send a crafted HTTP request with forged headers to the app's own public webhook endpoint — no access token, `api_secret_key`, or privileged account is needed. This mirrors the class of finding in the reference report: a check (`HmacValidator.validate`) that verifies one thing (body bytes) while the code downstream acts on a different, unauthenticated thing (header-derived shop/topic).

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable content (or otherwise cryptographically bind the header values to the signed payload), or require the host application to independently validate `request.shop` against the session/shop that installed the app before trusting it in `Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers/receives a webhook (e.g., `app/uninstalled`) and captures the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed with the app's shared `api_secret_key`).
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since body unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic: <any registered topic>`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against `H`.
5. `Webhooks::Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"`, causing the app to process/attribute data as if it came from the victim shop.
