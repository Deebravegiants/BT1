Based on my investigation, this is exactly the analog bug class the report describes: **HTTP response caching that leaks a cross-user/cross-session response**. The chainlink gateway's `responseCache` for HTTP capability actions is scoped to include `WorkflowOwner` (verified by the tests confirming different `WorkflowOwner` produces different hashes), but the test suite explicitly confirms `WorkflowID` is *not* part of the cache key at all — meaning the isolation claimed in the README ("Cache Key: Generated from workflow ID and request hash" / "scoped by workflow ID to prevent cross-workflow data leakage") does not match the actual implementation.

### Title
Outbound HTTP response cache is not scoped by WorkflowID, causing cross-workflow response confusion within the same owner - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's `responseCache` used for HTTP Action capability requests caches responses keyed only by a hash of method, URL, headers, body, and `WorkflowOwner`. `WorkflowID` is explicitly excluded from the hash. Two different workflows belonging to the same owner that issue an outbound HTTP action with identical method/URL/headers/body will read/write the same cache entry, resulting in one workflow receiving a cached HTTP response that was actually fetched/authorized in the context of a different workflow.

### Finding Description
`responseCache.Fetch`/`Set` key the cache exclusively on `req.Hash()` [1](#0-0) [2](#0-1) . The doc comment states the hash is built from "method, URL, headers, body, workflowOwner" [3](#0-2) , and the test suite explicitly proves `WorkflowID` has no effect on the hash while `WorkflowOwner` does: [4](#0-3) [5](#0-4) 

This directly contradicts the module's own documented design intent, which claims workflow-level isolation: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [6](#0-5) .

The cache is consulted from `makeOutgoingRequest`, which is triggered per node's outbound HTTP action request without any additional per-workflow key discrimination beyond what `Hash()` provides [7](#0-6) .

### Impact Explanation
Any two workflows owned by the same address (a common scenario for a multi-workflow operator, or a single account running many independent CRE workflows) that make outbound HTTP action requests to the same URL/method/headers/body will transparently share cached response bodies across workflow boundaries — this is the Shopware analog of "guest session shared between customers when cache is enabled": here it's "workflow B's HTTP response shared with workflow A" because the cache key omits the entity (`WorkflowID`) that should partition the data. If different workflows are meant to have independently-scoped credentials/data embedded in cached headers/bodies (e.g., per-workflow API tokens, personalized responses, or workflow-specific dynamic content), this causes a confidentiality/integrity confusion: one workflow's execution can silently consume another workflow's cached HTTP action result. Combined with the default cache TTL of 10 minutes and `Store: true`/`MaxAgeMs > 0` cache settings, this is a realistic contamination window [8](#0-7) .

### Likelihood Explanation
Reachable purely from unprivileged workflow-node-originated HTTP action requests — no operator or malicious-peer access required. Any workflow that sets `CacheSettings.Store=true` and `MaxAgeMs>0` and targets a URL/method/body identical to another workflow under the same owner will trigger this cache collision during normal operation, since request parameters (URL, headers, body) are workflow/developer controlled and easily made identical across two workflows deployed by the same owner.

### Recommendation
Include `WorkflowID` in the cache key hash (`req.Hash()`) so that cache entries are strictly partitioned per workflow, matching the documented design intent in the README. Add regression tests asserting that identical requests with different `WorkflowID` (same owner) produce different cache entries/hashes, mirroring the existing `WorkflowOwner` differentiation tests.

### Proof of Concept
1. Workflow A (WorkflowOwner=`0xabc`, WorkflowID=`wf-A`) issues an `OutboundHTTPRequest{Method: "GET", URL: "https://api.example.com/data", CacheSettings:{Store:true, MaxAgeMs:600000}}` and receives response R1, which gets cached under `Hash()`.
2. Workflow B (same WorkflowOwner=`0xabc`, WorkflowID=`wf-B`) issues an identical `OutboundHTTPRequest` (same Method/URL/Headers/Body/CacheSettings) within the TTL window.
3. Because `Hash()` does not include `WorkflowID` [4](#0-3) , workflow B's `Fetch` call returns the cached response R1 that was originally fetched in workflow A's execution context, without ever making a fresh outbound request or checking workflow-level authorization/context [2](#0-1) .

func (rc *responseCache) isExpiredOrNotCached(req gateway.OutboundHTTPRequest) bool {
	cachedResp, exists := rc.cache[req.Hash()]

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)

		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
