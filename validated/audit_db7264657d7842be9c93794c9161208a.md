## Finding: Webhook shop/topic identity not bound to the HMAC signature, enabling cross‑tenant webhook spoofing

### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw request **body**. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are taken from HTTP headers and handed to the app's handler as the identity of the tenant/event — are never included in the signed bytes. This breaks the identity binding `hmac_covered_bytes == identity_used_by_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is computed from the `hmac-sha256` header: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no relationship to the signed content: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (i.e., the body): [4](#0-3) 

`Registry.process` checks that HMAC and, once it passes, unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` handed to the app's handler: [5](#0-4) 

Critically, Shopify signs webhooks with the **app's** `api_secret_key`, which is the same secret for every shop that installs the app — it is not a per-shop secret. Any merchant can install the app on their own store and thereby legitimately receive webhooks whose bodies carry a valid HMAC signed with that shared secret. Because the signature covers only the body and not the headers, that same merchant can resend an intercepted (valid-body, valid-signature) webhook to the app's public webhook endpoint while altering the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to impersonate a different shop or event. `Utils::HmacValidator.validate` will still pass because the body bytes and signature are untouched, and `Registry.process` will dispatch the forged `shop`/`topic` values straight to the developer's handler as if genuinely verified.

The gem's own documentation reinforces the false sense of complete verification: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," without noting that only the body — not the shop/topic identity — is actually authenticated: [6](#0-5) 

This is the direct analog of the reported bug class: a value (`params.path`/here, the shop/topic identity) is *acted upon* by downstream logic but is not checked/covered by the validation step (`_extractTokens`/`HmacValidator.validate`) that is supposed to guarantee its integrity.

### Impact Explanation
An attacker who is simply a legitimate (even free-tier) installer of the target app on their own shop can forge webhook events attributed to any other shop domain and any topic, feeding fabricated identity/event data into the app's webhook processing pipeline. Any app whose handler uses `data.shop` to route data into per-tenant storage, trigger per-tenant side effects, or make decisions about a *different* merchant's data is exposed to cross-tenant data injection/confusion — this satisfies the "cross-tenant access" Critical impact bucket, since the merchant identity boundary is exactly what is broken.

### Likelihood Explanation
Likelihood is high for any app that only relies on `ShopifyAPI::Webhooks::Registry.process`/`Request` as documented: no additional per-shop credential or session lookup is required by this gem to pass validation, and the only prerequisite is the ability to install the target app once (trivial for any public app) to obtain a validly-signed body, then resend a modified HTTP request to the app's public webhook endpoint with edited headers.

### Recommendation
Bind the webhook's claimed identity to the verified bytes. At minimum:
- Include `topic`, `shop`, `api_version`, and `webhook_id` in the HMAC-covered signable string (matching what Shopify actually delivers, or otherwise deriving these from a source that can be cryptographically verified), or
- Cross-check the `shop` header against a known/installed-shop store before dispatching to handlers, and document clearly that `Registry.process` only authenticates the body, not the header-derived shop/topic identity, so integrators are not misled into skipping their own shop validation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, completing OAuth normally.
2. Attacker triggers a real event (e.g., `orders/create`) on their own shop, capturing the raw webhook POST: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid, since it's signed with the app's `api_secret_key`).
3. Attacker resends this exact request to the app's public webhook endpoint, but with header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate` computes HMAC over body `B` only — matches `H` — validation passes (see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38).
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb lines 188-200) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches to the app's handler, which now processes attacker-supplied data as if it originated from `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
