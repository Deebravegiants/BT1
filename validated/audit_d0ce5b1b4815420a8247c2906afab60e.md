Confirmed: `Registry.process` validates HMAC via `Utils::HmacValidator.validate(request)` which signs only `request.to_signable_string` (i.e., `@raw_body`), then dispatches to the handler using `request.topic` and `request.shop` — both read straight from HTTP headers that are **not** part of the signed bytes.### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant handler dispatch with a validly-signed body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook only after `Utils::HmacValidator.validate(request)` passes, but the signed payload (`Request#to_signable_string`) is exclusively the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values used to route and label the webhook are read from HTTP headers that are never included in the HMAC computation, breaking the intended binding between "bytes the app cryptographically verified" and "identity fields the app acts on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . Meanwhile `Request#shop`, `Request#topic`, `Request#api_version`, and `Request#webhook_id` are all pulled from headers via `shopify_header`, independent of the signed body: [2](#0-1)  and [3](#0-2) .

`Registry.process` validates the HMAC and then dispatches strictly on `request.topic`, passing `request.shop`, `request.api_version`, and `request.webhook_id` straight into the handler's `WebhookMetadata` without any cross-check against the signed body: [4](#0-3) .

The identity binding that should hold is: `HMAC-verified bytes == bytes the app trusts to select tenant/topic`. Here, `HMAC(secret, raw_body) == valid` says nothing about `shop-domain`/`topic` headers, so:

- Before request: attacker (any party who can obtain one genuine signed webhook body+HMAC pair — e.g. an app's own merchant install, which is an unprivileged party relative to *other* tenants of the same multi-tenant app) has `(body, hmac, shop=A, topic=T)`.
- After request: attacker resends the identical `(body, hmac)` but swaps `shop-domain` to shop `B` and/or `topic` to another registered topic. `HmacValidator.validate` still returns true because it only checks `hmac == HMAC(secret, raw_body)`, and `raw_body` is unchanged. `Registry.process` then calls the handler with `shop: "B"`, `topic: T'` for host-application code, which typically uses these to look up/act on tenant `B`'s data.

This lets an attacker who is not authorized for shop `B` cause the host application's webhook handler to execute logic attributed to shop `B` (cross-tenant confusion), without needing the app's `api_secret_key` — they only need one legitimate signed webhook of their own to replay with a different declared identity.

### Impact Explanation
This matches the Critical bucket "cross-tenant access": the gem's own webhook-processing logic passes an unauthenticated `shop` (and `topic`) value to the host handler as if it were verified, because the gem couples HMAC-body-verification with header-derived identity fields without binding them together. Any application that uses `WebhookMetadata#shop` (or `#topic`) to select which tenant's data to mutate/read is exposed to cross-tenant writes/reads driven entirely by header spoofing, once an attacker possesses one valid `(body, hmac)` pair for the shared app secret.

### Likelihood Explanation
Likelihood is realistic in any multi-tenant app: all installs of a given app share one `client_secret`/webhook-signing key, so any single tenant that has received one legitimate webhook can compute or replay a valid `(body, hmac)` and then freely forge the `shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, and `shopify-webhook-id` headers on a replay to the app's public webhook endpoint, since none of the required-header checks in the constructor verify header authenticity — they only check presence: [5](#0-4) .

### Recommendation
Bind the identity headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, `api_version`, and `webhook_id` to the verified payload before they are trusted:
- Include the relevant headers (at minimum `shop-domain` and `topic`) in `to_signable_string`, or
- Require the host application to independently confirm `request.shop` against a known/expected shop for the webhook subscription (e.g., validate against the shop that owns the specific `webhook_id`) before acting, and document this requirement clearly, or
- Reject processing when header-derived `shop`/`topic` cannot be corroborated by data embedded in the (signed) body.

### Proof of Concept
1. App merchant for shop `A` triggers (or is sent) a legitimate webhook: body `{"id":123}`, headers `shopify-shop-domain: a.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid HMAC of body>`.
2. Attacker (the same merchant, or anyone able to capture this request) resends the exact same body and HMAC header to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim-b.myshopify.com` (and optionally `shopify-topic` to another registered topic handled by the same code path).
3. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes `HMAC(secret, raw_body)` and the body is unmodified: [6](#0-5) .
4. `Registry.process` finds the handler for the (possibly attacker-chosen) topic and invokes it with `shop: "victim-b.myshopify.com"`, `body: {"id":123}` as if Shopify itself had verified this attribution: [7](#0-6) .
5. Any host application logic keyed on `WebhookMetadata#shop` now operates against tenant B using attacker-supplied data, even though only the body bytes — not the tenant attribution — were ever cryptographically verified.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
