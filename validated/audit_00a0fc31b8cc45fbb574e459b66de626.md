### Title
IntentGatewayV2 escrow sweep drains the shared CallDispatcher by live balance instead of owed amount, and CallDispatcher itself is permissionless — dust/residual funds are stealable by anyone - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` and `IntentsBase._execute` route predispatch/postdispatch calldata through a single shared `CallDispatcher` singleton, then "sweep" it back by reading the dispatcher's live `balanceOf`/`.balance` and transferring that entire balance — not the amount actually owed to the order — while `CallDispatcher.dispatch()` itself has no caller restriction whatsoever. This is the same bug class as the FAPEN report: the code uses a raw balance read as the operative transfer amount instead of an amount tracked/owed to the specific caller, and here it is compounded by a completely permissionless withdrawal primitive sitting on top of it.

### Finding Description
In `placeOrder`, predispatch assets are sent to `_params.dispatcher`, an arbitrary `order.predispatch.call` is executed there, and then the gateway sweeps back only the tokens explicitly listed in `order.inputs`, using the dispatcher's *full* balance of that token as the transfer amount: [1](#0-0) 

The same full-balance sweep pattern recurs for postdispatch execution in `_execute`, which sweeps `dispatcher.balance` / `IERC20(token).balanceOf(dispatcher)` for each output token as "dust": [2](#0-1) 

Both sweep loops only iterate over the token set the *order* declares (`order.inputs` or `order.output.assets`). Any token or native value that ends up on the dispatcher as a side effect of the attacker-supplied `order.predispatch.call` / `order.output.call` — but that is not one of the enumerated tokens — is never swept by the gateway and simply remains parked on the dispatcher indefinitely.

Critically, `CallDispatcher.dispatch()` has no access control at all — any address can call it directly with an arbitrary `Call[]`: [3](#0-2) 

Since the dispatcher is a single shared, permissionless contract used across all orders (and documented as a shared deployment on the contract-addresses page), any value it is holding — whether transient dust from an order whose predispatch/postdispatch calldata produced an off-list token, or protocol "dust" the docs say is meant to be swept to treasury only via governance — is directly withdrawable by anyone who simply calls `dispatch()` with a `Call` transferring that balance to themselves. The gateway's use of "live balance" as the swept/transferred amount (rather than a tracked, owed amount) is exactly the wrong-balance-check pattern from the FAPEN report; layered on a dispatcher with zero caller gating, it becomes directly exploitable rather than merely an accounting inconsistency.

The identical pattern is duplicated in the Tron fork of the contract: [4](#0-3) 

### Impact Explanation
Any value left on the shared `CallDispatcher` — protocol dust intended for governance-controlled treasury sweeps, or off-list token residue produced by a solver's/user's own predispatch/postdispatch calldata — can be permissionlessly drained by any third party racing to call `dispatch()` before the legitimate sweep or before governance collects it. This defeats the documented invariant that "protocol fees are retained as dust in the gateway and can be swept to a treasury via Hyperbridge governance," and constitutes concrete unauthorized withdrawal of protocol/order-related funds from a contract in the direct message-dispatch path of the intent gateway.

### Likelihood Explanation
`CallDispatcher.dispatch` is externally callable with no restriction, so exploitation requires only a single unprivileged transaction once any balance is sitting on the dispatcher. An attacker can also deliberately engineer such a balance by crafting `order.predispatch.call` to swap into a token not present in `order.inputs`, then immediately call `dispatch()` in a follow-up transaction to claim it (or race anyone else attempting to do so), making this reachable via a single submitted order and a subsequent direct call — no privileged role or protocol misconfiguration needed.

### Recommendation
Restrict `CallDispatcher.dispatch()` to authorized callers (e.g., the registered `IntentGatewayV2`/app contracts) rather than leaving it fully permissionless, and change the sweep logic in `placeOrder` / `_execute` to move exactly the amount the order is owed rather than the dispatcher's live balance; additionally sweep or explicitly account for *all* tokens the predispatch/postdispatch calldata could produce, not only the ones declared in `order.inputs`/`order.output.assets`, so no residual value is ever left addressable by an outside caller.

### Proof of Concept
1. Attacker submits `placeOrder` with `order.predispatch.call` that swaps the escrowed native/token input partially into an off-list token `X` not present in `order.inputs` (the sweep loop at `evm/src/apps/IntentGatewayV2.sol:263-287` only iterates declared input tokens, so `X` is left on the dispatcher).
2. In a subsequent transaction, attacker (or any third party) calls `CallDispatcher.dispatch(abi.encode([Call({to: X, value: 0, data: transfer(attacker, balanceOfX)})]))` directly — this succeeds because `dispatch()` performs no caller check (`evm/src/utils/CallDispatcher.sol:44-61`).
3. The token `X` balance parked on the shared dispatcher is transferred to the attacker, bypassing the gateway's dust/fee accounting entirely.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
