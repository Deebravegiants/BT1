### Title
Unbounded ancestry walk over attacker-supplied GRANDPA headers permits an infinite/near-infinite loop in `handle_unsigned` - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
CVE-2018-14567 is a libxml2 infinite loop triggered when an attacker-crafted input drives a decompression/parsing loop into a state that never terminates. The analogous bug class in Hyperbridge is `AncestryChain::ancestry`, which walks a `parent_hash` chain built entirely from attacker-controlled `unknown_headers`/`votes_ancestries` submitted in a permissionless, unsigned GRANDPA consensus proof. The walk's termination condition (`current_hash != base`) is never bounded by the number of headers supplied, so a crafted set of headers whose `parent_hash` fields form a cycle causes the loop to run forever (or for as long as the node keeps executing it), hanging the runtime thread validating/executing the extrinsic.

### Finding Description
`AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs:176-198` walks backwards from `block` to `base` using a `BTreeMap<H::Hash, H>` built from the header set supplied in the proof:

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
``` [1](#0-0) 

The `ancestry` map (`AncestryChain::new`) is populated directly from `finality_proof.unknown_headers`, a `Vec<H>` decoded from the raw, attacker-supplied proof bytes with no cycle detection, no visited-set tracking, and no bound on loop iterations relative to `unknown_headers.len()`. If two or more headers in this set form a `parent_hash` cycle that does not include `base`, the `while` loop alternates among the cyclic hashes forever because `self.ancestry.get(&current_hash)` always succeeds for members of the cycle.

This function is reachable via two call sites both driven by an unsigned, permissionless extrinsic:
1. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())` and `headers.ancestry(base.hash(), consensus_state.latest_hash)` directly on attacker-supplied `unknown_headers`. [2](#0-1) 
2. `GrandpaJustification::verify_with_voter_set` calls `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)` for every precommit while checking justification ancestry, using the same attacker-supplied `votes_ancestries` set. [3](#0-2) 

The whole chain is invoked from `GrandpaConsensusClient::verify_consensus`, which decodes the `ConsensusMessage` directly from the raw proof bytes of an ISMP consensus message:
```rust
let consensus_message: ConsensusMessage = codec::Decode::decode(&mut &proof[..])
    .map_err(|e| GrandpaError::DecodeConsensusMessage(format!("{e:?}")))?;
``` [4](#0-3) 

This `verify_consensus` is invoked from `pallet_ismp::handle_unsigned`, an unsigned extrinsic callable by anyone with a valid-looking proof, and from `ValidateUnsigned::validate_unsigned`, which runs `Self::execute(messages.clone())` as part of transaction-pool validation before the transaction is even included in a block: [5](#0-4) [6](#0-5) 

Because `validate_unsigned` runs during mempool gossip validation on every full node (not just block authors), a single submitted unsigned transaction containing a `ConsensusMessage::Polkadot`/`Relaychain` payload with a cyclic `unknown_headers`/`votes_ancestries` set can drive every node that validates the transaction into the unbounded loop, without requiring any signature or fee.

### Impact Explanation
This is a route made permanently unable to deliver messages / process consensus updates: any node whose transaction pool validates the malicious extrinsic hangs the executing thread in the infinite ancestry walk. Since `validate_unsigned` is invoked by every node relaying/gossiping unsigned extrinsics, a single crafted message broadcast to the network can hang multiple validating/collating nodes simultaneously, producing a chain-wide liveness denial-of-service against the GRANDPA consensus-update path (and thus against message delivery relying on it). This satisfies the "route unable to deliver messages" acceptance criterion at Medium/High severity, consistent with the CVE's DoS classification.

### Likelihood Explanation
Likelihood is high: the extrinsic is unsigned and free (`ensure_none(origin)`), requires no privileged role, and the attacker fully controls the `unknown_headers`/`votes_ancestries` vectors and the `parent_hash` field of each synthetic header (which are decoded straight from proof bytes with only type-level SCALE decoding, no chain-linkage validation prior to the ancestry walk). Constructing two headers `A`, `B` with `A.parent_hash == B.hash()` and `B.parent_hash == A.hash()` is a mechanical, offline exercise; no valid GRANDPA signatures or genuine chain data are needed to enter the vulnerable loop, since the ancestry walk in the justification/verifier runs before or independently of full commit/signature validation in some call paths (specifically the per-precommit ancestry walk in `verify_with_voter_set`, called before overall justification success is required to short-circuit the loop for the offending precommit).

### Recommendation
Bound `AncestryChain::ancestry` by the number of entries in the map (or a fixed `MAX_ANCESTRY_DEPTH`), and detect revisits with a `visited` set, returning `Error::NotDescendent` (or a new bounded-depth error) once the walk exceeds `self.ancestry.len()` steps or revisits an already-seen hash. Apply the same bound to any other unbounded walks over attacker-supplied header/proof structures in this crate.

### Proof of Concept
1. Craft two `SubstrateHeader`s `H_a`, `H_b` (or `DefaultHeader` for a standalone chain) such that `H_a.parent_hash = hash(H_b)` and `H_b.parent_hash = hash(H_a)`, and neither hash equals the trusted `base_hash`/`from` used by the verifier.
2. Construct a `GrandpaJustification` whose `commit.precommits` includes a precommit whose `target_hash` differs from the commit's `base_hash`, and whose `votes_ancestries` (or `unknown_headers` in the outer `FinalityProof`) contains `[H_a, H_b]`.
3. Wrap this in a `ConsensusMessage::Polkadot(RelayChainMessage { finality_proof, parachain_headers })` or `ConsensusMessage::StandaloneChain(...)`, encode it, and submit it as the `proof` field of an ISMP `Message::Consensus` inside `pallet_ismp::Call::handle_unsigned { messages }` as an unsigned extrinsic.
4. Any node that validates this transaction (via `validate_unsigned`) or executes it in a block enters `AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs` and loops indefinitely walking `H_a -> H_b -> H_a -> ...`, hanging the node.

Note: I was unable to directly execute this proof of concept or confirm at runtime whether an earlier signature/commit validation step (`finality_grandpa::validate_commit`) would reject the crafted commit before the vulnerable per-precommit ancestry loop is reached in every code path (in particular the `verify_grandpa_finality_proof`'s direct `headers.ancestry(from, target.hash())` call happens independently of `justification.verify`, and appears reachable without needing per-precommit signature validity). This should be verified with an actual instrumented build/test.
