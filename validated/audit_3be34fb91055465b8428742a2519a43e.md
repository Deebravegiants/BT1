### Title
Emporium Min-proof path lets an unprivileged caller execute arbitrary calls from Emporium's identity with zero token accounting - (File: contracts/CircomDataBuilder.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `emporiumMessage`, `timeStamp` and `calldataHash` — a proof any attacker can trivially generate for a self-chosen `messageSeed`. `EmporiumUpgradeable.runAction` then executes `EmporiumStack.ops` (decoded independently from `externalActionMetadata`, unconstrained by the "Min" proof) with `signerAddress == address(0)`, skipping ECDSA verification in `verifyWallet` and issuing raw `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own address, while every balance/accounting loop (in `Hinkal.transact` and `EmporiumUpgradeable.runAction`) iterates the empty `erc20TokenAddresses` array and checks nothing.

### Finding Description
The invariant that should hold is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`*. This is broken as soon as `erc20TokenAddresses.length == 0`.

- `CircomDataBuilder.formInputForCircom` (contracts/CircomDataBuilder.sol:134-148) selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and the token array is empty.
- `formInputEmporiumMin` (contracts/CircomDataBuilder.sol:150-161) builds public inputs consisting only of `emporiumMessage`, `timeStamp`, `calldataHash`. None of `amountChanges`, `inputNullifiers`, `outCommitments`, `rootHashHinkal`, or `erc20TokenAddresses` are constrained by this circuit, unlike `formInputNormal`/`formBasicInput` (contracts/CircomDataBuilder.sol:163-240).
- `HinkalHelper.performHinkalChecks` (contracts/HinkalHelper.sol:208-236) only checks `calldataHash` integrity, relay validity, `dimensionsCheck`, and `checkOnchainCreation` — all of which pass trivially with empty arrays (`dimensions.tokenNumber == 0`).
- `Hinkal.transact` (contracts/Hinkal.sol:30-130) computes `oldBalances`/`newBalances` via `getBalancesForArray(circomData.erc20TokenAddresses)` and loops `balanceDif`/slippage checks only over `circomData.erc20TokenAddresses` — with length 0, this loop never executes, so nothing is verified about actual asset movement.
- `_externalTransact` (contracts/Hinkal.sol:234-261) calls `EmporiumUpgradeable.runAction` with `deltaAmountChanges` sized to the (empty) token array.
- Inside `EmporiumUpgradeable.runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160), `EmporiumStack` is decoded independently from `circomData.externalActionData.externalActionMetadata` — its `ops` array is fully attacker-controlled and not tied to `erc20TokenAddresses` at all. `verifyWallet` (lines 302-349) returns immediately without any signature check when `stack.signerAddress == address(0)` (lines 314-316). The op loop's "CASE 2: Stateless Interaction" branch (lines 102-113) then performs `op.endpoint.call{value: op.value}(op.callData)` directly as `msg.sender == Emporium`, restricted only from calling `callHinkalWallet`/`doSendToRelay` selectors — any other call, including calls into token contracts holding Emporium's residual balance, or into `HinkalHelper`/routers that trust Emporium as an authorized caller, is permitted.
- `balancesBefore`/`balancesAfter` (lines 85-87, 122-124) and the subsequent `BalanceChangeShouldBePositive` check (lines 132-151) are computed over `circomData.erc20TokenAddresses`, which is empty — so any balance change caused by the ops is never observed or reverted on.

Attacker flow: craft `messageSeed`, compute `emporiumMessage = Poseidon(messageSeed)`, generate a valid Min-circuit proof for `(emporiumMessage, timeStamp, calldataHash)`, set `erc20TokenAddresses = []`, and encode `externalActionMetadata` as `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: <target token or trusting router>, invokeWallet: false, value: 0, callData: <e.g. transfer(attacker, amount) or a privileged call the router accepts from Emporium>}] }`. Call `Hinkal.transact` with this data. `verifyProof` succeeds (it only checks the 3 unconstrained public signals), `rootHashExists` passes with any historical root, and `runAction` executes the call from Emporium's identity, moving out whatever ETH/ERC20 balance Emporium holds, with zero accounting anywhere in the call stack.

Note: the `prooflessDeposit` function (contracts/Hinkal.sol:263-295) is a separate, unrelated code path — it never touches `externalActionData`, never calls `IExternalActionV2.runAction`, and includes its own strict balance-delta check (`balanceAfter - balanceBefore == amount`, contracts/Hinkal.sol:376-379). It does not connect to or enable this vulnerability; the actual exploitable entrypoint is `Hinkal.transact`.

### Impact Explanation
An attacker can drain any ETH/ERC20 balance sitting in the `EmporiumUpgradeable` contract (residual funds from partially-executed multi-step Emporium strategies, funds left by `handleOut`'s `balanceChange <= 0` branch, or ETH received via `receive()`), or trigger arbitrary privileged calls into any downstream contract that authorizes actions based on `msg.sender == Emporium`. This is direct theft of shielded/in-flight user funds routed through Emporium, matching the Critical severity category. The attack is repeatable for as long as Emporium holds exploitable balance or trust relationships exist.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: any EOA can deposit/withdraw via Emporium normally, self-generate a Min-circuit proof for a self-chosen message, and craft an `EmporiumStack` with `signerAddress == address(0)`. No privileged role, no other user's key, and no forged signature is required. The only external dependency is that Emporium holds an exploitable balance or that some contract trusts `msg.sender == Emporium` — a realistic condition given Emporium's designed use as a stateless call relay/smart-account executor.

### Recommendation
Do not allow the Min-proof/empty-token-array path to authorize arbitrary stateless calls with no accounting. Either (a) require `erc20TokenAddresses.length > 0` (or otherwise force use of `formInputNormal`) whenever `stack.ops` contains any non-empty `callData`/`value`, or (b) compute `balancesBefore`/`balancesAfter` over the full set of tokens actually touched by `op.endpoint`/`op.callData` rather than only `circomData.erc20TokenAddresses`, or (c) disallow `signerAddress == address(0)` combined with stateless external calls in the Min path, requiring a real signed authorization for any op execution regardless of token-array length.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register the Min verifier for `verifierId = buildVerifierId(Dimensions{tokenNumber:0,...}, HINKAL_EMPORIUM_ACTION_ID)`.
2. Fund `EmporiumUpgradeable` directly with e.g. 100 test ERC20 tokens (simulating residual balance from prior legitimate use).
3. Generate a real Min-circuit proof for `emporiumMessage = Poseidon(attackerSeed)`, arbitrary `timeStamp`, and `calldataHash` matching a `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: address(testToken), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 100e18))}], maxFee:0, deadline: block.timestamp+1})`.
4. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker EOA.
5. Assert: `testToken.balanceOf(attacker)` increased by 100e18 and `testToken.balanceOf(Emporium)` decreased by the same, while `oldBalances`/`newBalances`/`balancesBefore`/`balancesAfter` arrays computed inside `Hinkal.transact`/`EmporiumUpgradeable.runAction` were empty (length 0) and no `require` in either function reverted — demonstrating the broken equality "assets moved == assets accounted".
