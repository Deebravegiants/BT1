## Title
View-role users can read External Initiator `AccessKey` and `OutgoingToken` via unauthenticated-role `GET /v2/external_initiators` - (File: core/web/external_initiators_controller.go)

## Summary
`GET /v2/external_initiators` is registered behind only session/token authentication (no `RequiresEditRole`/`RequiresRunRole` wrapper), while `POST`/`DELETE` on the same resource require `auth.RequiresEditRole`. `Index` returns each initiator's `AccessKey` and `OutgoingToken` to any authenticated caller, including `view`-role users, whereas the actual authentication `Secret` (needed to authenticate as the initiator via `AuthenticateExternalInitiator`) and `OutgoingSecret` are never exposed by `Index`.

## Finding Description
The route wiring in `core/web/router.go` confirms `eia.Index` has no role wrapper: `authv2.GET("/external_initiators", paginatedRequest(eia.Index))`, contrasted with `authv2.POST(...auth.RequiresEditRole(eia.Create))` and `authv2.DELETE(...auth.RequiresEditRole(eia.Destroy))`. `Index` (`core/web/external_initiators_controller.go` L50-59) builds `presenters.ExternalInitiatorResource` for every stored initiator, and that struct (`core/web/presenters/external_initiators.go` L57-65) includes `AccessKey` and `OutgoingToken` in the JSON response. This is verified end-to-end by `TestExternalInitiatorsController_Index` (`core/web/external_initiators_controller_test.go` L104-109, L121-126), which explicitly asserts `AccessKey` and `OutgoingToken` equal the stored values in the `Index` response, and by the RBAC test table in `core/web/auth/auth_test.go` L224, which sets `viewOnlyAllowed: true` for this route.

Critically, however, the `Secret` field (paired with `AccessKey` for `AuthenticateExternalInitiator`, `core/bridges/external_initiator.go` L59-67) and `OutgoingSecret` are deliberately excluded from `ExternalInitiatorResource` — only the non-secret-hash `HashedSecret`/`Salt` are stored server-side and never returned by `Index` at all, and `OutgoingSecret` is likewise omitted from this presenter (only present in `ExternalInitiatorAuthentication`, returned once at `Create` time, per `core/web/presenters/external_initiators.go` L12-20 vs L57-65). Authentication against `AuthenticateExternalInitiator` requires the `Secret`, which is never disclosed by `Index` — a view-role user obtaining `AccessKey` and `OutgoingToken` alone cannot pass `bridges.AuthenticateExternalInitiator` (constant-time comparison against a salted hash, `core/bridges/external_initiator.go` L61-67), since the hashed secret cannot be derived from `AccessKey`/`OutgoingToken`.

## Impact Explanation
The finding is real: exposing `AccessKey` and `OutgoingToken` to `view`-role users is a least-privilege violation and unnecessary information disclosure, and does deviate from the pattern where `Create`/`Destroy` require `edit` role. However, it is not sufficient on its own to authenticate as the external initiator (the `Secret` is never returned by `Index`) or to bypass the node's own authentication of `view` role — it does not provide fund movement, job-run triggering, or authentication/role bypass capability by itself. `OutgoingToken`'s actual use (outgoing webhook callback verification) was not conclusively traceable in the indexed code; no `core/services/webhook` consumer of `OutgoingToken` was found in the search, so its downstream exploitability beyond raw disclosure is unconfirmed. This limits the impact to a sensitive-metadata disclosure to an already-authenticated, lower-privilege internal user rather than a concrete authentication/role bypass or fund-impacting event.

## Likelihood Explanation
Requires an authenticated `view`-role account (already provisioned credential in the RBAC model) — not a zero-privilege external attacker. This matches the report's own framing: the "attacker" already holds valid session/API-token credentials, just at the lowest privilege tier. The behavior is deterministically reproducible via the cited test (`TestExternalInitiatorsController_Index`) and is explicitly encoded as intended in the project's own RBAC test suite (`viewOnlyAllowed: true`), which strongly suggests this was a deliberate design decision rather than an oversight bug — the same test suite treats `Create`/`Destroy` (mutating, higher-risk operations) as requiring `edit`, while treating `Index` (read-only) as `view`-accessible, consistent with common RBAC patterns of restricting mutation more tightly than read access.

## Recommendation
If disclosure of `AccessKey`/`OutgoingToken` to `view`-role users is not intended, wrap `GET /v2/external_initiators` with `auth.RequiresEditRole` (or at minimum `RequiresRunRole`), and/or strip `AccessKey`/`OutgoingToken` from `ExternalInitiatorResource` for roles below `edit`. Given `OutgoingSecret` and the initiator's authentication `Secret` are already correctly withheld from `Index`, applying the same withholding pattern to `AccessKey`/`OutgoingToken` for low-privilege roles would close the gap without breaking existing intended `view`-role read access to non-sensitive fields (`Name`, `URL`, timestamps).

## Proof of Concept
1. Provision a `view`-role user (`sessions.UserRoleView`) and authenticate via session or API token.
2. `GET /v2/external_initiators` — reproduced deterministically by `TestExternalInitiatorsController_Index` (`core/web/external_initiators_controller_test.go` L63-127), which confirms the response body contains `accessKey` and `outgoingToken` for each configured initiator regardless of caller role, since the route itself performs no role check.
3. Confirm `Secret`/`OutgoingSecret` are absent from this response (only visible once, at `Create`, per `presenters.ExternalInitiatorAuthentication`), meaning disclosure is limited to `AccessKey` and `OutgoingToken`, not full authentication credentials. type ExternalInitiator struct {

// NewExternalInitiator generates an ExternalInitiator from an
// auth.Token, hashing the password for storage
func NewExternalInitiator(
	eia *auth.Token,
	eir *ExternalInitiatorRequest,
) (*ExternalInitiator, error) {
	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(eia, salt)
	if err != nil {
		return nil, pkgerrors.Wrap(err, "error hashing secret for external initiator")
	}

	return &ExternalInitiator{
		Name:           strings.ToLower(eir.Name),
		URL:            eir.URL,
		AccessKey:      eia.AccessKey,
		HashedSecret:   hashedSecret,
		Salt:           salt,
		OutgoingToken:  utils.NewSecret(utils.DefaultSecretSize),
		OutgoingSecret: utils.NewSecret(utils.DefaultSecretSize),
	}, nil
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
