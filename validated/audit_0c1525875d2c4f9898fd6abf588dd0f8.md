### Title
`socialize-debt` zeroes `lindex` (total-wipeout signal) while `assets` retains a residual, untracked balance - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`socialize-debt` computes the write-down to `lindex` from `debt-reduction` (a term proportional to `total-debt`, i.e. principal + accrued interest) but writes down `assets` using `principal-reduction` (a term proportional only to `total-borrowed`, i.e. raw principal, excluding accrued interest). Because `total-debt >= total-borrowed` whenever interest has accrued, `principal-reduction < debt-reduction` for any given `scaled-amount`, so the exact `scaled-amount` that drives `new-lindex` to the `u0` "total wipeout" floor leaves `assets` strictly positive whenever `current-assets > total-borrowed` (i.e., whenever the vault is not 100% utilized), breaking the loss-accounting invariant.

### Finding Description
Identity that should hold: **if `new-lindex == u0` (total wipeout of share value), then `assets_after` should be driven to `u0`** — a wipeout of the index should correspond to full consumption of `assets`.

Relevant code, `mainnet/contracts/vault/v0-vault-stx.clar` lines 944-966: [1](#0-0) 

- `debt-reduction = scaled-amount * idx / INDEX-PRECISION`, and since `idx/INDEX-PRECISION == total-debt/scaled-principal` at call time [2](#0-1) , this means `debt-reduction ∝ total-debt`.
- `principal-reduction = scaled-amount * borrowed / scaled-principal`, so `principal-reduction ∝ total-borrowed`.
- `new-lindex` floors to `u0` when `debt-reduction >= old-total-assets`, where `old-total-assets = current-assets + (total-debt - total-borrowed)` (the unrealized-interest-inclusive total) via `total-assets()` [3](#0-2) .
- `assets_after = current-assets - principal-reduction` (floored at `u0`) [4](#0-3) .

Since `principal-reduction / debt-reduction = total-borrowed / total-debt < 1` whenever interest has accrued (`total-borrowed < total-debt`, achievable purely by letting time pass after a borrow — `next-index` compounds `idx` over `stacks-block-time` deltas, see lines 379-390), it can be shown algebraically that at the exact `scaled-amount` threshold where `debt-reduction == old-total-assets` (the boundary that zeroes `lindex`), `principal-reduction < current-assets` strictly whenever `current-assets > total-borrowed` — i.e., whenever the vault is not fully utilized (which is the normal healthy state, since deposits routinely exceed borrows). In that case `assets_after > u0` while `lindex == u0`, the exact divergence the question describes.

`socialize-debt` is gated by `check-caller-auth`, restricting direct calls to `authorized-contracts` (the market contract) [5](#0-4) [6](#0-5) . An unprivileged attacker cannot call `vault.socialize-debt` with an arbitrary `scaled-amount` directly; it is only reachable through the market's bad-debt/liquidation flow, which computes `scaled-amount` from an actual borrower's outstanding debt. I was not able to fully trace `mainnet/contracts/market/v0-4-market.clar`'s exact call site and argument derivation for `socialize-debt` within the available iterations, so I cannot confirm the precise numeric conditions (e.g., whether the market caps `scaled-amount` to a single position's real remaining debt, and whether an attacker can engineer a position whose bad-debt write-off naturally lands in the divergence window). This is a gap that would need to be closed by reading that contract's liquidation/bad-debt logic.

### Impact Explanation
Within the vault contract itself, the arithmetic inconsistency is real: any socialize-debt event sized to cross the `lindex -> 0` threshold, on a vault with unaccrued interest and utilization below 100%, leaves a positive `assets` residue that is no longer backed by any accounted debt or supply logic consistent with a "total wipeout" signal. This residue becomes an accounting artifact: downstream code (`redeem`, `convert-to-assets-preview`) still reads `assets` and computes share value from it despite `lindex` telling integrators/liquidity index consumers that value is fully gone, producing inconsistent internal state that could manifest as insolvency/frozen-value bookkeping errors. However, confirming this is *directly and repeatably triggerable by an unprivileged attacker with attacker-controlled economic benefit* requires validating the market-side bad-debt/liquidation code path that supplies `scaled-amount`, which I could not complete.

### Likelihood Explanation
Preconditions are cheap to satisfy on the vault side alone (deposit, borrow, let time pass to decouple `total-debt` from `total-borrowed`, trigger a socialize-debt-sized event), but reachability depends entirely on whether the market's liquidation/bad-debt logic lets a caller size the resulting `scaled-amount` to land in the identified divergence window. That dependency is unverified.

### Recommendation
Compute the `assets` write-down using the same debt-proportional basis as `lindex`'s write-down (i.e., derive `principal-reduction` consistently with `debt-reduction`, or explicitly force `assets` to `u0` whenever `new-lindex` floors to `u0`), so a total-wipeout signal in `lindex` always corresponds to full consumption of `assets`.

### Proof of Concept
Not confirmed end-to-end due to inability to fully trace the market contract's `socialize-debt` invocation within this session; the arithmetic divergence within `v0-vault-stx.clar::socialize-debt` itself is demonstrable via a Clarinet unit test directly calling `socialize-debt` (as an authorized caller) with: deposit 1,000,000 units, borrow 100,000, warp time so `index` grows (`total-debt` > `total-borrowed`), then call `socialize-debt` with `scaled-amount` set to the computed threshold (`old-total-assets * scaled-principal / total-debt`), and assert `(get-liquidity-index)` returns `u0` while `(get-assets)` returns a value `> u0`. This isolates the vault-level bug, but does not establish unprivileged-attacker reachability through the market's authorized call path, which remains unverified.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
