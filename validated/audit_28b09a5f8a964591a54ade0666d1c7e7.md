### Title
Gas exhaustion in a wallet-contract callback permanently locks `has_in_flight_tx`, bricking the ETH-implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (used to emulate Ethereum accounts on NEAR) guards re-entrancy with a `has_in_flight_tx` boolean that is supposed to be reset to `false` at the very start of every callback. Because NEAR reverts **all** state writes made during a function-call execution that fails/panics (including out-of-gas), any panic inside a callback after the flag reset but before completion discards that reset together with everything else, leaving `has_in_flight_tx` permanently `true`. This is directly analogous to the Salty DAO bug where an unhandled external-call revert left `_userHasActiveProposal` stuck `true`, permanently blocking the user from creating new proposals.

### Finding Description
`rlp_execute` is the sole entry point of the contract and immediately rejects any call while `has_in_flight_tx` is `true`: [1](#0-0) 

The struct's own doc comment states the invariant that must hold for correctness: [2](#0-1) 

Each callback resets the flag as its very first statement, and only then performs further work (deserializing external results, building new promises, etc.): [3](#0-2) [4](#0-3) [5](#0-4) 

Each of these callbacks is allocated a small, fixed static gas budget: [6](#0-5) 

If the callback runs out of the allotted gas (or panics for any other reason, e.g. malformed/oversized JSON from a cross-contract call such as `storage_balance_of` or the address registrar's `lookup`) anywhere after the `self.has_in_flight_tx = false;` line, the entire function-call execution fails. On NEAR, a failed/panicking function call causes **all** of its state changes to be rolled back — the earlier reset to `false` is discarded along with the rest of the execution, so the persisted value of `has_in_flight_tx` remains `true` (the value set by the prior call before scheduling the promise). Because `rlp_execute` unconditionally rejects further calls whenever `has_in_flight_tx == true`, this leaves the account permanently unable to process any further Ethereum-emulated transaction — there is no other method that resets the flag.

This is the same bug class as the `2024-01-salty` `DAO._executeApproval` finding: an external call/cross-contract response is trusted to always complete cheaply and successfully; when it doesn't, a "busy"/"active" flag is left permanently set with no recovery path other than abandoning the account (in Salty's case, moving to a new staking account; here, abandoning the eth-implicit account since accounts on NEAR have no code-replacement/reset mechanism visible to the user).

### Impact Explanation
Any account using the `near-wallet-contract` (an ETH-implicit account, part of NEAR's Chain Signatures/EVM-compatibility feature) can become permanently unusable if a single callback exceeds its hardcoded 5 TGas budget or otherwise panics after the reset line. This is a real, protocol-shipped contract (not a mock or third-party dependency), and the failure is triggerable through an ordinary flow: a relayer/user submitting an `rlp_execute` transaction whose target is a NEP-141 token or the address registrar that returns a larger-than-expected/malformed successful response, causing `serde_json::from_slice` or subsequent logic to exceed the fixed gas ceiling. The affected account then permanently rejects all future `rlp_execute` calls ("transaction already in progress"), a persistent denial-of-service against that specific account with no on-chain recovery — matching "unauthorized state" lock / inability to transact impact, analogous to the original report's permanent proposal-lock.

### Likelihood Explanation
Likelihood is moderate: it requires interacting with an untrusted or misbehaving cross-contract target (a NEP-141 token or the address registrar) whose response is large/complex enough, or gas-price/execution variance large enough, to blow the tight fixed 5 TGas callback budgets. Since `target`/token accounts in Ethereum-emulated transactions are attacker- or third-party-controlled (any NEP-141 contract the user's ETH tx references), a malicious or buggy token contract can reliably trigger this by returning an oversized or expensive-to-parse response, deterministically bricking the calling account.

### Recommendation
- Do not rely on state mutations made earlier in the same execution to "protect" against later panics/gas exhaustion in the same call; instead separate the re-entrancy-flag reset into its own minimal, first, unconditionally-committed action, or store/clear the flag via a mechanism that survives a subsequent panic (e.g., clear it in a dedicated cheap promise/receipt executed before any potentially expensive parsing).
- Increase/parameterize callback gas budgets with headroom, and bound/validate the size of external responses (`storage_balance_of`, registrar `lookup`) before attempting to deserialize them, rejecting oversized payloads early and cheaply.
- Provide an explicit, permissioned recovery path (e.g., a privileged or time-locked `reset_in_flight` method) to un-stick `has_in_flight_tx` if a callback ever fails unexpectedly, analogous to allowing the ballot to always finalize.

### Proof of Concept
1. Deploy/own an ETH-implicit account backed by `WalletContract`.
2. Craft an RLP-encoded ERC-20-style transfer transaction (`EthEmulationKind::ERC20Transfer`) whose `target` token contract is attacker-controlled and whose `storage_balance_of` method returns a large/deeply-nested JSON blob (still within receipt size limits) instead of the expected small `Option<StorageBalance>`.
3. Submit this via `rlp_execute`; `inner_rlp_execute` schedules `storage_balance_of` and chains `nep_141_storage_balance_callback` with the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget: [7](#0-6) 
4. In `nep_141_storage_balance_callback`, `self.has_in_flight_tx = false;` executes first, then `serde_json::from_slice(&value)` deserializes the oversized payload, exhausting the callback's remaining gas and causing the whole receipt execution to panic.
5. Because the panic reverts all state changes made by this receipt, `has_in_flight_tx` reverts to `true` (as set before scheduling the promise chain in `rlp_execute`/`inner_rlp_execute`).
6. Any subsequent call to `rlp_execute` now immediately returns `"Error: transaction already in progress, please try again later."` forever, since no other method resets the flag — the account is permanently bricked.
