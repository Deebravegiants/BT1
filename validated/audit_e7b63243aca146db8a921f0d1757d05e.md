### Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`/`webhook_id`) fields consumed by `Registry.process` and handed to the app's `WebhookHandler` come from unsigned HTTP headers. Any party capable of obtaining one valid `(raw_body, hmac)` pair for the app's shared `api_secret_key` can replay it with a forged `x-shopify-shop-domain` header and pass HMAC validation while impersonating a different shop.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhook requests that method only returns the raw body: [1](#0-0) [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers and are never included in the bytes that are HMAC-verified: [3](#0-2) 

`Registry.process` only checks the HMAC of the body, then constructs `WebhookMetadata` (including the unauthenticated `shop` field) and dispatches it directly to the host app's handler as trusted tenant identity: [4](#0-3) [5](#0-4) 

This is precisely the pattern called out in the rules: "a field acted on but not covered by the HMAC." Since one `api_secret_key` (the app's client secret) is shared across every shop that installs that app, any merchant that installs the app can capture a legitimate `(body, hmac)` pair from a real Shopify webhook delivered to their own shop, then replay that exact body/HMAC to the app's webhook endpoint while substituting a different value in the `x-shopify-shop-domain` header. Because the header is not part of the signed content, `HmacValidator.validate` still returns `true`, and the forged request is delivered to the handler labeled as coming from an arbitrary victim shop.

**Equality that should hold but doesn't:** `shop-identity used by the app (WebhookMetadata#shop)` should equal `shop-identity cryptographically bound into the verified bytes`. Instead: `bytes verified (raw_body only)` ≠ `bytes/headers acted on (raw_body + shop + topic + webhook_id)`.

### Impact Explanation
Any downstream app logic that trusts `WebhookMetadata#shop` as the tenant identifier (e.g., to look up/update per-shop records, credit orders, or gate access) can be tricked into acting on attacker-controlled data while attributing it to a shop the attacker does not control — a cross-tenant data-integrity/confusion issue. This matches the "cross-tenant access" Critical impact category, since the attacker crosses the tenant boundary using only their own legitimate installation of the shared app (no access token, secret, or privileged account required).

### Likelihood Explanation
Exploitation requires only: (1) being a legitimate, unprivileged merchant who has installed the same app (so the attacker naturally receives real webhooks signed with the shared `api_secret_key`), and (2) the ability to replay an HTTP request with a modified header, which is trivial. No credentials, tokens, or elevated access are needed, making this practically likely for any multi-tenant app built on this gem's webhook registry.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material, or — since Shopify does not sign headers this way — have `Registry.process`/`WebhookMetadata` cross-check the `shop` header against session/shop data already known to the app for that specific `webhook_id`/topic combination before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must not be used as the sole tenant boundary without additional verification (e.g., confirming the shop has an active, matching session/installation).

### Proof of Concept
1. App `X` is installed by both `Attacker Shop` and `Victim Shop`, sharing the same `api_secret_key`.
2. Shopify sends a legitimate webhook to `App X` for `Attacker Shop`: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this exact `(B, HMAC)` pair (e.g., via their own server logs, since it was delivered to them).
4. Attacker replays a request to the same webhook endpoint with the identical body `B` and identical `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` verifies only `B` against the HMAC and returns `true`. [6](#0-5) 
6. `Registry.process` dispatches to the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the app processes attacker-controlled data as if it originated from `Victim Shop`.
