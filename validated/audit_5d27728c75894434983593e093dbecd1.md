Confirmed: `handle<H>` checks `host.request_receipt(&req).is_some()` for duplicate detection **before** `store_request_receipt`, so a delivery is idempotent — a second submission of the same request is rejected as `DuplicateRequest` regardless of what `signer` value it carries. This closes off the "steal an existing relayer's credit by resubmitting the same request" scenario. However, the underlying design flaw remains real: `extract_signer` treats any `signer` field ≤32 bytes as an already-authenticated account identifier, with no cryptographic binding to the entity that actually produced the delivery or possesses that key.

### Title
Self-Declared, Unverified `signer` Field Lets Any Deliverer Impersonate an Arbitrary Relayer Address for Fee Accounting - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is permissionless (`ensure_none`) and processes any batch of ISMP messages that carries a valid state/consensus membership proof for the payloads themselves. Each message also carries a `signer: Vec<u8>` field described only as "Ideally should be their account identifier" [1](#0-0) . This field is never cryptographically verified when it is ≤32 bytes — `extract_signer` just echoes the bytes back verbatim as the "relayer" identity [2](#0-1) . That unverified value is stored on-chain as the address credited with delivering the request/response [3](#0-2) , and it is this same commitment (`RequestReceipts`/`ResponseReceipts`) that downstream fee/reward logic (`pallet-ismp-relayer`'s `accumulate_fees` and the outbound-request-delivery reward claim) later reads via state/child-trie proofs to determine who gets paid [4](#0-3) .

### Finding Description
The bug-class analog to CVE-2025-55301 is: a value that functions as an identity/permission claim is accepted from an untrusted, client-controlled input with no proof of ownership, and the receiving system persists and later trusts that value as authoritative. Here, `signer` in `RequestMessage`/`ResponseMessage` is exactly such a field — for byte-strings ≤32 bytes, `extract_signer` performs no signature check at all, it just returns the raw bytes [2](#0-1) . Because `handle_unsigned` requires only `ensure_none` and a valid inclusion/state proof for the *requests themselves* (not for the `signer` field), any address on the network can submit a batch with `signer` set to any 32-byte value of their choosing (e.g. a well-known relayer's public key/account, or their own address), and that value is what gets written into `RequestReceipts`/`ResponseReceipts` as "the relayer who delivered this" [5](#0-4) .

The relayer/fee-accumulation path treats this stored value as proof of who did the delivery work: `decode_receipt_relayer` decodes substrate receipts either as a raw ≤32-byte address or a signature (only recovering a real signer when the stored value happens to exceed 32 bytes) [6](#0-5) , and `accumulate_fees`/the outbound reward claim pay out to whatever address is recovered from that receipt, without any additional cryptographic check tying it to the actual message deliverer [7](#0-6) .

Note: the up-front and re-check `request_receipt(...).is_some()` guards in `handlers/request.rs` and `handlers/response.rs` do provide idempotency, preventing a second party from *overwriting* an already-delivered request's receipt with a different `signer` [8](#0-7) [9](#0-8) . That means the "steal a specific relayer's already-earned credit via resubmission" variant is blocked. What remains exploitable is that the *original* submitter of a not-yet-delivered message can set `signer` to any account they like — including an address they do not control — and that address becomes the on-chain "relayer of record" eligible for the fee, with no proof the named account authorized or participated in the delivery.

### Impact Explanation
This breaks the intended economic/authentication model of relayer fee accounting: fee/reward payouts are meant to compensate the party whose key/account actually performed message delivery, but the substrate-side attribution (`signer` ≤ 32 bytes) requires no signature at all. An attacker who races to be first to deliver a message (which anyone can do once a valid proof exists, since delivery is permissionless and free via `handle_unsigned`) can attribute the delivery to any account they choose, diverting `accumulate_fees` credit and `OutboundRequestDeliveryReward` payouts intended for a legitimate relaying party to an address they control, or falsely crediting an uninvolved account. This is a fund-diversion/fee-theft issue in the relayer economic layer, reachable by any unprivileged party submitting a normal unsigned ISMP message.

### Likelihood Explanation
High reachability: `handle_unsigned` is explicitly designed to be callable by anyone with a valid state proof, and the `signer` field is entirely separate from that proof — nothing in the membership/consensus verification touches it. Any relayer racing to be first to submit a legitimate, provably-deliverable message can simply substitute their own (or any) address in `signer` at no extra cost, since delivery is free ("Pallet ISMP uses unsigned transactions for executing cross-chain messages ... executed for free" [10](#0-9) ).

### Recommendation
Require and verify a genuine cryptographic signature over the delivered batch for the substrate `signer` field in all cases (not only when the byte length happens to exceed 32), analogous to what `pallet-messaging-incentives::relayer_for` already does by recovering a real sr25519 signer from a signature over the encoded requests [11](#0-10) . `extract_signer` in `pallet-ismp`'s host implementation should be aligned with that stricter model so that `RequestReceipts`/`ResponseReceipts` can never be populated with a bare, unverified address.

### Proof of Concept
1. Observe a `PostRequest` on the source chain with a valid, publicly-derivable membership proof for the destination chain (any such proof is public once the state commitment is finalized).
2. Before the honest relayer submits it, submit `handle_unsigned` yourself with `Message::Request(RequestMessage { requests, proof, signer: <32 bytes of your choice, e.g. an address you control> })` — see `extract_signer`'s ≤32-byte passthrough at [2](#0-1) .
3. `RequestReceipts[commitment]` is now set to your chosen address [12](#0-11) , with no signature ever checked.
4. Later, submit an `accumulate_fees`/`claim_outbound_request_delivery_reward` withdrawal proof referencing that receipt; `decode_receipt_relayer` recovers your chosen address as the "relayer" and pays out to it [13](#0-12) , even though the named account never signed anything proving it performed the delivery.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. 	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {

				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),

			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
