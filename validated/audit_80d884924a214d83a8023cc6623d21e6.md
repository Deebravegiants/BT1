### Title
Sustained high-utilization borrowing overflows `i128` total-debt inside accrual and permanently freezes the market before the borrow-index cap can engage - (File: common/src/rates/index.rs)

### Summary
The CVE class is "a crafted input crashes a parser, producing denial of service." The analog in XOXNO Lending is an unprivileged-reachable arithmetic trap inside interest accrual: `calculate_supplier_rewards` multiplies total scaled debt by the new borrow index in `i128` before the `MAX_BORROW_INDEX_RAY` clamp can take effect. Once scaled debt `borrowed` and the index are large enough that `borrowed * new_borrow_index > i128::MAX`, `Ray::mul` panics with `MathOverflow` inside `global_sync`, which runs before every pool verb — so the market permanently rejects withdraw, repay, supply, liquidate, `clean_bad_debt`, and `recapitalize`.

### Finding Description
`accrue_step` (invoked per chunk by `global_sync` in `contracts/pool/src/interest.rs:20-53`) calls `calculate_supplier_rewards`, which computes `borrowed.mul(env, new_borrow_index)` at `common/src/rates/index.rs:81`. `Ray::mul` uses `mul_div_floor`/half-up helpers in `common/src/math/fp_core.rs`, which widen to `I256` but panic with `GenericError::MathOverflow` when the result cannot fit `i128` (`fp_core.rs:117`, `to_i128` at `:300-303`). The borrow index itself is capped by `update_borrow_index` at `MAX_BORROW_INDEX_RAY` (`index.rs:13-19`), but the cap is applied to the index, not to the debt×index product — the product overflows first when `borrowed` is large. The same panic exists in `update_supply_index` via `supplied.mul(env, old_index)` (`index.rs:34`) and `supply_index_reward_shortfall` (`index.rs:60-62`).

Because `Cache::load → interest::global_sync` precedes every mutation and most views on a market (pool README flow), the panic bricks the `(hub, token)` book entirely. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates this end-to-end: accrual fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw` and `repay` both revert with the same error.

An unprivileged attacker path: `supply` a large amount of the target asset, `borrow` near-maximum utilization (only bounded by governance caps and `max_utilization`, which can be disabled/high), then hold the position at high utilization while calling `update_indexes` periodically. Once `borrowed * index` crosses `i128::MAX`, every subsequent `update_indexes`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `recapitalize` on that market panics.

### Impact Explanation
Permanent freezing of funds: all supplier principal and unclaimed yield in the market become unreachable, borrower repayments and liquidations cannot execute, and bad debt cannot be cleaned or recapitalized (all accrue first). This maps to the accepted "permanent freezing of funds" and "contract unable to operate" impacts, not mere fail-closed rejection of malformed input.

### Likelihood Explanation
Medium. It requires whale-scale capital (the test uses ~10^27 base units) and years of sustained ~98% utilization on a steep rate curve, plus caps large enough to permit the position. No privileged action, oracle manipulation, or leaked key is needed — only public `supply`/`borrow`/`update_indexes` calls. Governance-set borrow caps and `max_utilization` are the only mitigations, and they do not bound the `borrowed × index` product, so a sufficiently large market freezes deterministically rather than by chance. The in-repo test confirms the panic path exists and that the index cap never engages.

### Recommendation
Bound the value product, not just the index. Concretely:
- In `calculate_supplier_rewards`, clamp `new_borrow_index` so that `borrowed * new_index` fits `i128` (e.g., `new_index = min(new_index, i128::MAX / borrowed * RAY)`) instead of letting `mul` panic.
- Apply the same saturation in `update_supply_index` for `supplied * old_index` and in `supply_index_reward_shortfall`.
- Alternatively, enforce a global scaled-debt ceiling at borrow time (`borrow` rejects amounts that would let `borrowed * MAX_BORROW_INDEX_RAY` approach `i128::MAX`), so the accrual math stays in-domain for the market's whole lifetime.
- `recapitalize`/`clean_bad_debt` should also have an accrual-free fallback path so governance can recover a frozen market.

### Proof of Concept
The existing harness test demonstrates the freeze: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`. Conceptual reproduction:

```rust
// 18-decimal market, steep XLM-like curve, caps lifted, max_utilization disabled
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);            // unprivileged supply
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization, unprivileged borrow

loop {                                            // keep calling update_indexes (public)
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; }
}
// borrow_index < MAX_BORROW_INDEX_RAY, yet accrual panics with MathOverflow
// at common/src/rates/index.rs:81 (borrowed.mul(env, new_borrow_index))

// Market is permanently frozen — all of these revert with MathOverflow:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
// likewise liquidate, clean_bad_debt, recapitalize, claim_revenue
```

Root cause: `common/src/rates/index.rs:81` (`borrowed.mul(env, new_borrow_index)` overflows `i128` before the `MAX_BORROW_INDEX_RAY` clamp at `:15` can bound the damage), reached unconditionally via `global_sync` in `contracts/pool/src/interest.rs:26-30`.
