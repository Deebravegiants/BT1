### Title
Removing a chain from a token's configuration permanently blocks refunds for in-flight cross-chain transfers - (File: modules/pallets/hyper-fungible-token/src/lib.rs, modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`update_token`'s `remove_chains` branch deletes `TokenContracts`, `ContractToAsset`, and `Precisions` entries for a chain immediately, with no check for outstanding (in-flight) `send()` requests targeting that chain. `on_timeout` for those in-flight requests depends on exactly this configuration to compute and issue the refund, so timeouts that fire after the removal permanently fail, and the user's escrowed/burned funds cannot be reclaimed.

### Finding Description
An unprivileged user calls `send` [1](#0-0) , which escrows (native asset) or burns (non-native asset) the user's tokens and dispatches an ISMP `PostRequest` to the destination chain, relying on `TokenContracts` and `Precisions` at dispatch time only for the outgoing amount conversion.

If the request later times out (relayer never delivers it, or it's not accepted before its timeout), `on_timeout` is invoked to refund the original sender. Crucially, refund computation looks up the *current* state of `ContractToAsset` and `Precisions` for the destination chain, not a value captured at dispatch time: [2](#0-1) 

If between `send()` and the timeout firing, `update_token` is called with that chain in `remove_chains`, these entries are deleted: [3](#0-2) 

`update_token` performs no check for any pending/in-flight ISMP requests referencing the chain being removed — there is no borrowed/outstanding-amount style guard analogous to the `removeAsset` report. When `on_timeout` subsequently executes for the affected request, `ContractToAsset::<T>::get(dest, &to)` returns `None`, so it errors out with `HftError::UnknownContractOnTimeout` before any refund transfer/mint occurs.

### Impact Explanation
The tokens taken from the user in `send()` (escrowed to the pallet's custodial account, or burned entirely) are never returned: the timeout handler that is supposed to release them reverts deterministically because the asset/precision lookup it depends on has been removed. This is a permanent freezing of user funds — for burned (non-native) assets, this is unbacked destruction with no way to reissue since the mint side of the flow never occurred; for escrowed (native) assets, the funds sit unreachable in the pallet's custodial account with no code path to release them once the chain config is gone.

### Likelihood Explanation
This does not require a malicious operator — the report's own template scenario describes an operator making a routine reconfiguration (e.g., migrating a token contract to a new address, deprecating a stale chain, or reacting to an incident on one destination chain) while ordinary users have transfers in flight to that chain. Given that ISMP requests can be timed out well after being dispatched (bounded only by the request's configured timeout), any window between a `send()` and its expiry that overlaps an `update_token` reconfiguration removing that chain will trigger the bug. Both `send` (attacker/any user-reachable) and `update_token` (governance-reachable, not attacker-controlled but easily triggered unintentionally) are real, exercised entry points in the pallet.

### Recommendation
- Short term: Before removing a chain entry (or reject) in `update_token`, ensure there are no outstanding dispatched requests referencing that `(chain, asset_id)` pair, or alternatively retain the historical `ContractToAsset`/`Precisions` mapping (e.g. keyed by request commitment or an append-only history) so `on_timeout` can always resolve the asset/precision that was active at dispatch time, independent of later configuration changes.
- Long term: Snapshot the asset/precision/contract data used for conversion into the outgoing request body (or into per-commitment storage) at `send()` time, so refund and receipt logic never depend on live, mutable configuration state that can be changed out from under an in-flight message.

### Proof of Concept
1. Admin registers asset `A` for chain `Evm(1)` via `register_token`, setting `TokenContracts`, `ContractToAsset`, and `Precisions` for `(Evm(1), A)`.
2. User calls `send()` with `destination = Evm(1)`, `asset_id = A`, burning (or escrowing) `amount` tokens and dispatching a `PostRequest` with a timeout `T`. [4](#0-3) 
3. Before the relayer delivers the request and before timeout `T` elapses, admin calls `update_token` with `remove_chains = [Evm(1)]`, deleting `ContractToAsset`, `TokenContracts`, and `Precisions` entries for `(Evm(1), A)`. [3](#0-2) 
4. Relayer never delivers the request (or delivery is skipped); timeout `T` elapses, and a timeout proof is submitted through the standard ISMP timeout-handling flow, invoking `on_timeout` for the pallet's request.
5. `ContractToAsset::<T>::get(dest, &to)` returns `None`, causing `on_timeout` to error with `HftError::UnknownContractOnTimeout` and abort before refunding. [5](#0-4) 
6. The user's burned/escrowed tokens are permanently unrecoverable — no code path re-attempts or otherwise unlocks the refund once the configuration is gone.

		pub fn send(
			origin: OriginFor<T>,
			params: SendParams<
				AssetId<T>,
				<<T as Config>::NativeCurrency as Currency<T::AccountId>>::Balance,
			>,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			let dispatcher = <T as Config>::Dispatcher::default();

			let token_contract =
				TokenContracts::<T>::get(params.destination, params.asset_id.clone())
					.ok_or(Error::<T>::TokenContractNotFound)?;
			let erc_decimals = Precisions::<T>::get(params.asset_id.clone(), params.destination)
				.ok_or(Error::<T>::DecimalsNotFound)?;

			// Lock or burn the local asset
			let decimals = if params.asset_id == T::NativeAssetId::get() {
				// escrow the native asset
				<T as Config>::NativeCurrency::transfer(
					&who,
					&Self::pallet_account(),
					params.amount,
					ExistenceRequirement::AllowDeath,
				)?;
				T::Decimals::get()
			} else {
				let is_native = NativeAssets::<T>::get(params.asset_id.clone());
				if is_native {
					<T as Config>::Assets::transfer(
						params.asset_id.clone(),
						&who,
						&Self::pallet_account(),
						params.amount.into(),
						Preservation::Expendable,
					)?;
				} else {
					<T as Config>::Assets::burn_from(
						params.asset_id.clone(),
						&who,
						params.amount.into(),
						Preservation::Expendable,
						Precision::Exact,
						Fortitude::Polite,
					)?;
				}
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					params.asset_id.clone(),
				)
			};

			// Encode the Message body
			let sender: [u8; 32] = who.clone().into();
			let amount: u128 = params.amount.into();
			let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);

			let token_message = Message {
				from: sender.to_vec().into(),
				to: params.recipient.to_vec().into(),
				amount: alloy_primitives::U256::from_be_bytes(erc20_amount.to_big_endian()),
				data: params.call_data.unwrap_or_default().into(),
			};

			let dispatch_post = DispatchPost {
				dest: params.destination,
				from: PALLET_ID.to_bytes(),
				to: token_contract,
				timeout: params.timeout,
				body: Message::abi_encode(&token_message),
			};

			let metadata = FeeMetadata { payer: who.clone(), fee: params.relayer_fee.into() };
			let commitment = dispatcher
				.dispatch_request(DispatchRequest::Post(dispatch_post), metadata)
				.map_err(|_| Error::<T>::DispatchError)?;

			Self::deposit_event(Event::<T>::TokenSent {
				from: who,
				to: params.recipient,
				dest: params.destination,
				amount: params.amount,
				commitment,
			});
			Ok(())
		}
