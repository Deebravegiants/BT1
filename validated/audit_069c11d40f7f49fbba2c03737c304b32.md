### Title
Webhook Tenant (Shop) Attribution Is Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (tenant) attribute is read from an HTTP header that is never included in that signature. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then forwards the unauthenticated `shop` header straight into `WebhookMetadata`, which the gem's own documentation tells developers to use as the tenant identifier for storing/dispatching webhook data.

### Finding Description
The identity binding that should hold is: `shop attributed to a webhook == shop whose secret produced the HMAC over the body`. In this gem that equality is never enforced.

- `Request#hmac` reads `shopify-hmac-sha256` and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) , [2](#0-1) .
- `Request#shop` is read from the `shopify-shop-domain` header, which is not part of `to_signable_string`, so it is never covered by the HMAC: [3](#0-2) .
- `Registry.process` verifies only `Utils::HmacValidator.validate(request)` (i.e. the body/secret binding), then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., without any additional binding check: [4](#0-3) .
- `HmacValidator.validate` only ever signs/verifies `verifiable_query.to_signable_string`, so any header outside that string is unauthenticated: [5](#0-4) .
- The gem's documented usage explicitly tells developers to trust `data.shop` as the shop/tenant key for storing and dispatching the webhook body: [6](#0-5) , and `WebhookMetadata.shop` is defined as a plain `String` field with no cryptographic binding to the payload's origin: [7](#0-6) .

Because Shopify signs webhooks with the app's single shared `client_secret` (not a per-shop key) via `X-Shopify-Hmac-SHA256`, the HMAC only proves "this body was produced by our app's secret" — it proves nothing about which shop the body belongs to. An unprivileged internet user who controls any shop that has installed the app (e.g., a free/dev store) receives real, validly-signed webhooks for their own shop. They can capture one such request (raw body + valid `hmac-sha256` header) and replay it to the target app's webhook endpoint while swapping only the `shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the raw body against the secret, and `Registry.process` happily attributes the (attacker-controlled) body to the victim shop.

### Impact Explanation
This breaks the tenant boundary the report's bug class targets ("shop authenticated versus the shop stored/used as the tenant key"). A host application following the gem's documented pattern (persisting/dispatching webhook data keyed by `data.shop`) can be made to associate attacker-supplied webhook content (order data, GDPR redaction requests, mandatory compliance topics, product/customer payloads, etc.) with a victim merchant's tenant record, corrupting per-tenant state or triggering tenant-scoped side effects (e.g., a mandatory `customers/redact` or `shop/redact` webhook forged against a victim shop) — this is a cross-tenant integrity/isolation break directly caused by the gem's signature scope, not by host misuse of an undocumented API.

### Likelihood Explanation
The attacker only needs their own legitimately installed shop (trivial to obtain — free/dev store) to harvest one valid signed webhook, then replay it with a modified `shop-domain` header to any app using this gem's `Registry.process`/`WebhookMetadata.shop` as documented. No access to `api_secret_key`, tokens, or TLS interception is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header bytes in the HMAC-signed string, or otherwise cryptographically bind the shop to the payload before exposing it through `WebhookMetadata`, so `Registry.process` can reject requests whose shop attribution isn't provably tied to the signed body.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker POSTs to the victim app's webhook endpoint with the same raw body `B` and the same `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and matches `H` — validation passes [8](#0-7) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "victim-shop.myshopify.com"` even though the body actually originated from the attacker's shop [9](#0-8) .
5. The host app's handler, following the documented pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`, stores/acts on attacker-controlled data under the victim shop's tenant record.
