## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook processing validates authenticity by computing an HMAC over the raw request body only. The `shop` (tenant) attribute that is handed to the application's webhook handler is taken from an HTTP header that is never included in the signed content, so it can be freely substituted without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC against the body via `HmacValidator.validate`, then dispatches the handler using `request.shop` taken straight from the unauthenticated header: [3](#0-2) 

`HmacValidator.validate_signature` confirms the check is computed purely from `to_signable_string` (the raw body) and the app's shared `api_secret_key`: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == tenant attributed by the signed payload`. Instead, the code enforces only `HMAC(raw_body, api_secret_key) == received_hmac`, leaving `shop` completely outside the cryptographic binding — directly analogous to the report's pattern of checking a limit against a value that isn't the one actually bound to the protected action.

Because `api_secret_key` is a single shared app-level secret used to sign webhooks for *every* shop that installs the app (not a per-tenant secret), any merchant/attacker who installs the app on their own store receives genuine webhooks with valid HMACs computed over bodies they can fully control indirectly (e.g. by creating orders/products with attacker-chosen data). That attacker can then replay the identical `raw_body` + `hmac-sha256` header to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop. The HMAC check still passes since it never looked at the shop header, and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to host applications: any app relying on `WebhookMetadata#shop` from `Registry.process` to select tenant-scoped resources (DB rows, feature flags, cached sessions, etc.) can be made to process attacker-supplied webhook data under a victim shop's identity — a cross-tenant access issue, which is explicitly called out as Critical impact.

### Likelihood Explanation
No privileged credentials, `client_secret`, or leaked tokens are required. Any unprivileged internet user who can install (or already has installed) the app on their own store obtains legitimate, correctly-signed webhook bodies and can replay them against the app's public webhook endpoint with a forged `shop-domain` header. This requires only normal HTTP access to the app's webhook endpoint.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the signed material verified by `HmacValidator`, or otherwise cross-check the `shop-domain` header against an independently-authenticated value (e.g. compare against the shop context derived from the destination URL path/route the app registered per-shop) before dispatching to a handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a body they control, e.g. `{"id":1}`.
2. Shopify sends the webhook with headers including a valid `x-shopify-hmac-sha256` computed with the app's real `api_secret_key` over that exact raw body, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this raw body and HMAC, then POSTs it directly to the app's webhook endpoint, replacing only the header: `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because it only checks `raw_body` against the (unchanged, still-valid) HMAC: [5](#0-4) 
5. The handler executes with `shop: "victim.myshopify.com"`, causing the host app to attribute attacker-controlled webhook data to the victim tenant.
