### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Registry.process` verifies a webhook by validating only the HMAC over the raw request body, then hands the caller a `WebhookMetadata` struct whose `shop` field is read from the `x-shopify-shop-domain` HTTP header, which is not covered by the signature at all.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . The `shop` attribute exposed by `Request`, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed body [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` when building the `WebhookMetadata` passed to the host application's handler: [4](#0-3) 

This breaks the intended identity binding: `verified_bytes (raw_body) == acted_on_bytes (shop header)` does not hold. An attacker who can produce a validly-HMAC'd webhook body for shop A (e.g., by replaying a legitimate webhook payload captured for their own store, which they legitimately received and can sign-verify since the HMAC only covers the body) can pair that same body with an arbitrary `x-shopify-shop-domain` header value for shop B. The gem will report the webhook as valid (`HmacValidator.validate` passes because the body/HMAC pair is genuine) and will hand the host app a `WebhookMetadata` claiming the event belongs to shop B, even though the signed content says nothing about which shop it belongs to.

### Impact Explanation
If the shared secret is the same across all shops for the app (or if the body content is otherwise attacker-influenced/replayable), this allows a webhook whose signature was computed for one tenant to be presented as originating from a different tenant, since the header carrying the tenant identity is never covered by the signature. Host applications commonly key their per-shop side effects (e.g., which merchant's data to update, uninstall, or redact) directly off `WebhookMetadata#shop`, per the library's own webhook contract [5](#0-4) . Spoofing this field enables cross-tenant action within the app relying on this gem's verification guarantee, without needing the app's `client_secret` beyond having obtained one validly-signed body (e.g. from the attacker's own shop or a leaked/replayed webhook).

### Likelihood Explanation
Medium. This does not require the app's secret directly, only a genuinely-signed HMAC/body pair (which any shop with the app installed can legitimately obtain by having the app produce a webhook for their own store), plus the ability to send a crafted HTTP request to the app's webhook endpoint with a modified `x-shopify-shop-domain` header. Whether this is exploitable end-to-end depends on the host app's endpoint accepting raw headers/body from the internet and forwarding them to `Registry.process` unmodified, which is the documented integration pattern for this gem.

### Recommendation
Include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in the signed representation of the webhook request, or otherwise cryptographically bind the shop identity into the HMAC-verified content, so `to_signable_string` cannot be satisfied by a body/HMAC pair whose associated headers were altered independently. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-scoping decisions unless cross-checked against another out-of-band verified value.

### Proof of Concept
1. Attacker (as a legitimate merchant "attacker-shop.myshopify.com") installs the app and receives a genuine webhook: body `B` with header `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`, and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and HMAC `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unmodified [6](#0-5) .
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-controlled header value `victim-shop.myshopify.com` [7](#0-6) .
5. The host app's `WebhookHandler#handle` receives `data.shop == "victim-shop.myshopify.com"` with a payload body that was never actually signed for that shop, potentially triggering cross-tenant side effects.
