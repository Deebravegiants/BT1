### Title
`fiatBalancesReport.export()` ignores `isLocked`, disclosing per-wallet-account fiat balances via `exodus.reporting.export()` while the wallet is locked - ([File: features/fiat-balances/report/index.js])

### Summary
`createReporting`/`getReports` in `sdks/headless/src/api/reporting.js` passes `isLocked` to every registered report's `export()` as a hint only, trusting each report module to self-enforce the lock state. `features/fiat-balances/report/index.js` destructures only `{ walletExists }` from the export options and never checks `isLocked`, so once a wallet exists (has ever been created/imported), its fiat balances are returned regardless of lock state.

### Finding Description
`getReports` in [1](#0-0)  computes `exists` and `locked` once and forwards both as a hint object `{ walletExists, isLocked }` to every report node's `export()`, with no central enforcement — each report is individually responsible for honoring `isLocked`. Most report modules correctly follow this convention, e.g. `features/balances/report/index.js` [2](#0-1)  and `features/wallet-accounts/src/report/index.ts` [3](#0-2)  both short-circuit with `if (!walletExists || isLocked) return null`.

However, `features/fiat-balances/report/index.js` only checks `walletExists` and completely omits the `isLocked` check: [4](#0-3) 
This means that once `exodus.wallet.exists()` is `true` (i.e., the wallet has been created/imported at least once, independent of the current unlock state), a call to `exodus.reporting.export()` while the wallet is locked will still include the `fiatBalances` namespace with the full per-wallet-account fiat balance map (`walletAccountName -> "X USD"`), derived from `walletAccountsAtom` and `fiatBalancesAtom`.

An unprivileged caller of the headless SDK API (e.g., a dapp/extension host consuming `exodus.reporting.export()`) does not need to unlock or authenticate to obtain this data — it only requires the wallet to exist. This breaks the same "secrets/unlocked-only data stays hidden while locked" invariant that every other report module in the codebase enforces, confirming that `isLocked` is treated only as an advisory hint rather than an enforced guard at the `getReports` aggregation layer.

### Impact Explanation
An unprivileged caller can invoke `exodus.reporting.export()` while the wallet is locked and receive the `fiatBalances` report containing wallet account names mapped to fiat balance amounts — financial account data that should only be available when unlocked, consistent with how the sibling `balances` report treats crypto balances. This is a genuine confidentiality violation of the wallet's lock boundary, though scoped to fiat balance amounts and wallet-account identifiers rather than keys/addresses/xpubs (no other report module was confirmed to leak those under this exact precondition — `addressProvider`, `balances`, `blockchainMetadata`, `walletAccounts`, `enabledAssets`, `restoringAssets`, `application`, `analytics`, and `auth` reports all correctly gate on `isLocked`).

### Likelihood Explanation
Fully reproducible with no special preconditions beyond the wallet having been created at some point and then locked — no privileged state, keys, or social engineering required. Any caller with access to the headless SDK's `reporting.export()` API (e.g., embedding host, dapp bridge, or RPC client) can trigger this deterministically every time.

### Recommendation
Add an `isLocked` guard to `features/fiat-balances/report/index.js`'s `export()` function, mirroring the pattern used in `features/balances/report/index.js`: `if (!walletExists || isLocked) return null`. Additionally, consider enforcing the `isLocked`/`walletExists` gating centrally in `getReports` (`sdks/headless/src/api/reporting.js`) via an explicit per-report allow-list/schema declaration of which fields are safe while locked, rather than relying purely on each report module to self-police, to prevent future regressions of this kind.

### Proof of Concept
Integration test (extend `sdks/headless/__tests__/reporting.test.js` style, alongside `features/fiat-balances/report/__tests__/index.test.js`):
1. Register `fiatRamp`/`fiatBalances` definitions as done in `sdks/headless/__tests__/fiat-ramp.test.js`.
2. `exodus.application.create({ passphrase })`, `exodus.application.unlock({ passphrase })`, set non-zero fiat balances via `fiatBalancesAtom`/`walletAccountsAtom`.
3. `await exodus.application.lock()`.
4. `await expect(exodus.wallet.isLocked()).resolves.toBe(true)`.
5. `const result = await exodus.reporting.export()`.
6. Assert `result.fiatBalances` is **not** `null`/empty and instead contains the wallet-account fiat balance data — proving disclosure while locked (this should fail after the fix, where `result.fiatBalances` must equal `null`).
