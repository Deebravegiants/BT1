### Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, and `webhook_id` values that identify *which tenant and event* the webhook belongs to are taken straight from unauthenticated HTTP headers and are never included in the signed payload [2](#0-1) .

### Finding Description
`Request#hmac` decodes the `X-Shopify-Hmac-Sha256` (or `shopify-hmac-sha256`) header, and `Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the received value with `OpenSSL.secure_compare` [4](#0-3) . Note that `Context.api_secret_key` is a single, static, **app-wide** secret — the same key is used to authenticate webhooks for every shop that has the app installed, not a per-shop secret.

`Registry.process` then trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from headers that are outside the HMAC's coverage — and hands them to the developer's handler as `WebhookMetadata`: [5](#0-4) [6](#0-5) 

The equality that should hold is:
`(body, hmac)` authenticates ⇒ `(shop, topic, webhook_id)` are the values Shopify actually associated with that signed body.

But because `to_signable_string` only returns `@raw_body`, the binding actually enforced is only:
`hmac == HMAC(secret, body)`,
with **no cryptographic binding between `body` and the header-derived `shop`/`topic`/`webhook_id`**.

An unprivileged attacker who legitimately installs the app on their own store (a normal, unprivileged action any merchant can take) will receive genuine webhooks from Shopify — real `(raw_body, hmac)` pairs signed with the app's single shared `api_secret_key`. Because that same secret authenticates webhooks for every shop, the attacker can take one of their own legitimately-received `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with a victim shop's domain / a different topic. `HmacValidator.validate` will still succeed because the body and hmac are unmodified and match, and `Registry.process` will dispatch the handler believing the data belongs to the victim shop/topic.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a handler that trusts `WebhookMetadata#shop` (as the doc/API explicitly provides it for that purpose) to select which merchant's data/session to act on can be fed attacker-controlled body content while the header claims it originates from a different, victim shop. Depending on how the host app uses `shop`/`topic`/`body`, this enables cross-tenant data confusion/injection (e.g., processing an `orders/create` payload the attacker controls under the identity of a mandatory topic like `shop/redact` or `customers/data_request`, or under a different shop's session) — a cross-tenant access primitive per the impact criteria. It does not require the app's `client_secret`, an access token, or any privileged capability; the only prerequisite is that the attacker has legitimately installed the app once (a normal unprivileged interaction), which the current code does not defend against because it deliberately does not sign the routing headers.

### Likelihood Explanation
Medium: the attacker needs the app to be installed at least once (normal unprivileged flow) and needs their own webhook deliveries to capture a valid `(body, hmac)`, then must be able to control/forge the HTTP headers reaching the app's endpoint (something they fully control since they choose the request they send to the app's public webhook URL). No credential leakage, TLS interception, or api_secret_key is required.

### Recommendation
Bind the routing identity to the signed payload rather than trusting the raw headers as-is:
- Change `Request#to_signable_string` to incorporate `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (this requires Shopify's signing scheme to support it, so at minimum this should be flagged/mitigated in the gem), or
- Require the host application to independently verify, using an authoritative source (e.g., an existing stored session/shop record), that the shop reported in `X-Shopify-Shop-Domain` is a shop that is actually installed and matches the tenant context expected for that endpoint before trusting `WebhookMetadata#shop`, and document this requirement prominently since the gem does not enforce it itself.
- At minimum, document in `docs/usage/webhooks.md` that `shop`/`topic`/`webhook_id` headers are unauthenticated relative to the HMAC and must not be treated as tenant-verified without additional application-level checks.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving a legitimate webhook delivery, e.g.:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...attacker-controlled order fields...}`
2. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the same app endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or changes `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, raw_body)` [7](#0-6)  — this passes because body/hmac are untouched.
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's JSON>, ...)` [8](#0-7) , i.e., attacker-controlled content is processed under the victim's shop identity.
