### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` binds solely to the byte content of the payload. The `shop` (and `topic`, `webhook_id`, `api_version`) attributes are read directly from HTTP headers and are never part of the signed material, yet `Registry.process` trusts `request.shop` as the authenticated tenant identity when dispatching to the handler.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) [2](#0-1) 

`shop` is pulled straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, while `to_signable_string` (the value actually HMAC-verified) returns only `@raw_body`. In `lib/shopify_api/webhooks/registry.rb`: [3](#0-2) 

`process` validates the HMAC over the body only (`Utils::HmacValidator.validate(request)`), then unconditionally forwards `request.shop` (an unauthenticated header) to the handler as the webhook's tenant identity via `WebhookMetadata`.

The equality the library implicitly assumes is:
`shop_used_by_handler == shop_that_the_HMAC_actually_authenticates`

But the HMAC only authenticates "this body byte-string was produced with our app's shared `api_secret_key`" — it says nothing about which shop the body was intended for. Since the same `api_secret_key` is shared across every shop that has installed the app, any shop that legitimately receives a real Shopify-signed webhook for itself can capture that `raw_body` + `hmac-sha256` header pair (both valid, since it truly came from Shopify), and replay the exact same body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still succeed (it only recomputes/verifies the digest of `@raw_body`), and `Registry.process` will hand the handler `WebhookMetadata` claiming the spoofed shop, not the actual originating shop.

### Impact Explanation
This breaks the tenant-identity binding used by any webhook handler that relies on `WebhookMetadata#shop` to scope actions/data (e.g., updating orders/products/settings for "the shop in the webhook"). A shop that is a legitimate, unprivileged customer of the app can trick the host application into processing attacker-supplied webhook content under a different, victim shop's identity — a cross-tenant access/data-integrity issue that requires no leaked credentials, no access token, and no privileged account; it only requires normal use of the app by any installed shop and observation of one legitimate webhook delivery.

### Likelihood Explanation
Any merchant installing the app receives real webhooks addressed to their own shop; capturing one webhook's raw body and its `hmac-sha256`/`shop-domain` headers requires only normal network visibility into the app's own inbound endpoint (e.g., via a proxy/log they control) or timing side channels. Re-sending that payload with a modified `shop-domain` header is trivial and passes `HmacValidator.validate` unchanged since the signature never covered the shop header.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `api_version`, `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., validate against a known/allow-listed shop for the current install, or require the app to independently confirm the shop via an authenticated channel before trusting `WebhookMetadata#shop`). At minimum, document prominently that `request.shop` is unauthenticated and must not be used for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Shop A (attacker, an installed/paying customer of the app) receives a real webhook from Shopify: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `api_secret_key`), `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and successfully matches `H`.
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host application to process attacker-controlled webhook content attributed to `victim-shop`.
