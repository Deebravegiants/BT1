## Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook entirely from an unauthenticated header, while the HMAC signature that is supposed to prove authenticity only covers the raw request body. This mirrors the reported `trade_proof` bypass pattern: a security check exists and is enforced, but a critical field that downstream code trusts as authoritative (`shop`) is never actually bound to that check.

## Finding Description
`ShopifyAPI::Webhooks::Registry.process` gates all webhook handling on HMAC validation: [1](#0-0) 

The HMAC check is performed by `Utils::HmacValidator.validate`, which computes the signature over whatever `to_signable_string` returns for the object: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

However, the `shop` value used to attribute the webhook to a tenant is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is completely outside the signed content: [4](#0-3) 

`Registry.process` then forwards this unauthenticated `shop` value straight to the app's handler as the tenant key, with no further verification: [1](#0-0) 

This is the identity-binding break: the equality that should hold is
`shop verified by HMAC == shop used to route/attribute webhook data`,
but since `shop-domain` is not part of `to_signable_string`, the actual equality enforced is only `hmac(body) == received_hmac`, with `shop` left completely unauthenticated. The `api_secret_key` used to sign webhooks is shared across *all* shops that install a given app (it's the app's client secret, not a per-shop secret), so any shop that legitimately installs the app can obtain a validly-signed `(body, hmac)` pair for its own data, then resend that exact pair to the app's public webhook endpoint while forging the `x-shopify-shop-domain` header to name a different, victim shop. The signature still validates because it never covered the shop header, and `WebhookMetadata.shop` is set to the attacker-chosen value.

## Impact Explanation
This directly enables cross-tenant data injection into apps built on this gem: an unprivileged party who merely has their own shop install the target app can forge webhook events (e.g. `app/uninstalled`, `customers/data_request`, `orders/create`) attributed to any other merchant using the same app, without ever needing that merchant's credentials, access token, or the app's `client_secret`. Depending on how the host app's handler consumes `data.shop` (e.g. as a lookup/foreign key to update or delete merchant records, trigger data erasure, or ingest order/customer data), this can corrupt or exfiltrate data belonging to unrelated tenants — a cross-tenant access impact.

## Likelihood Explanation
Any developer/merchant account can install the target Shopify app on a shop they control, deliberately trigger a webhook event to obtain a validly HMAC-signed body, and replay it with a substituted `shop-domain` header — no special access, leaked secrets, or privileged account required beyond ordinary app installation, which is the intended unprivileged usage of the gem/apps built on it.

## Recommendation
Bind the shop identity into the value that is cryptographically verified. Options:
- Include the `shop-domain` header in `to_signable_string` for `ShopifyAPI::Webhooks::Request` so the HMAC covers it, if Shopify's signing scheme is changed to support this, or
- Independently verify that the `shop` claimed in the webhook belongs to a shop that has an active, previously-established session/installation record for this app before trusting it as a tenant key, rather than passing the raw header value straight into `WebhookMetadata`.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against its own installed-shop records before being used as a tenant identifier.

## Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control).
2. Attacker triggers a webhook topic the app subscribes to (e.g. updates a product), causing Shopify to send a POST to the app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(B, app_secret)`.
3. Attacker captures `(B, HMAC(B, app_secret))` and resends it to the same endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` computes the HMAC over `B` only (`lib/shopify_api/webhooks/request.rb`, `to_signable_string`), which still matches — validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, and the handler acts on data as if it legitimately originated from the victim shop.
