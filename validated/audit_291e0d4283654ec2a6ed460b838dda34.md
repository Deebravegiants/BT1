### Title
Interest accrual overflow permanently freezes an oversized high-utilization market - (File: `common/src/rates/scaling.rs`)

### Summary
The interest accrual path multiplies scaled debt shares by the borrow index before enforcing the configured `MAX_BORROW_INDEX_RAY` ceiling. At sufficiently large market scale and sustained utilization, `scaled * index / RAY` exceeds `i128::MAX` even though the index itself remains below the cap. Accrual therefore panics with `MathOverflow`.

Because every pool mutation accrues before changing positions, the failed calculation permanently blocks repayment, withdrawal, borrowing, liquidation, revenue claiming, bad-debt handling, and later index synchronization for that market.

### Finding Description
`accrue_step` computes utilization by unscaling the stored share amounts:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
let util = utilization(env, borrowed_original, supplied_original);
```

From `common/src/rates/simulate.rs`, these calls execute before `update_borrow_index` and therefore before any index bound can apply.

`scaled_to_original` uses fixed-point multiplication over `i128` intermediates. The stored `borrowed` value is already normalized into RAY shares. Once its product with `borrow_index` exceeds the `i128` domain, the multiply-divide panics. The index cap is only relevant to the newly calculated index and does not constrain this pre-accrual unscale operation.

`global_sync` in `contracts/pool/src/interest.rs` calls `accrue_step` for each accrual chunk and only calls `mark_accrued` after all chunks complete. Thus a panic rolls back the entire accrual and leaves `last_timestamp` behind. Every subsequent call reaches the same calculation and fails again.

The controller-reachable path is:

1. `supply(spoke_id, payments)` for the target asset.
2. `supply` for collateral.
3. `borrow(spoke_id, payments)` to establish high utilization.
4. Allow interest to accumulate until the scaled-debt unscale exceeds `i128::MAX`.
5. Invoke `update_indexes(hub_assets)` with the affected `HubAssetKey`.
6. The pool calls `Cache::load`, `global_sync`, `accrue_step`, and `scaled_to_original`, then panics.
7. Subsequent `withdraw`, `repay`, `borrow`, liquidation, `claim_revenue`, `recapitalize`, or another `update_indexes` touching that market repeats the same failing accrual.

A test already demonstrates the state transition in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`: a very large 18-decimal market is opened at 98% utilization, yearly `update_indexes` calls eventually fail with `MathOverflow`, the stored index remains below `MAX_BORROW_INDEX_RAY`, and both withdrawal and repayment subsequently fail.

### Impact Explanation
This causes permanent freezing of funds and can leave the protocol insolvent.

After the overflow threshold is reached:

- Suppliers cannot withdraw.
- Borrowers cannot repay.
- Liquidators cannot reduce unhealthy debt because liquidation flows require market accrual.
- Keepers cannot advance the indexes.
- Governance cannot fix the market through normal pool mutations because those paths also accrue first.
- Fees cannot be claimed and bad debt cannot be settled normally.

The overflow is not a one-call transaction failure. Since `last_timestamp` is not stamped until after all accrual chunks complete, the failure is stable and repeats forever. Unless an extraordinary administrative or upgrade path exists to rewrite state, all user claims represented by the affected market remain locked.

### Likelihood Explanation
The attack requires an unusually large market and enough elapsed accrual for the borrow index to grow, but it does not require privileged protocol access.

A single unprivileged attacker can create the state by:

- supplying the borrowed asset to create liquidity;
- supplying a different collateral asset;
- borrowing the first asset at high utilization;
- waiting for accrual and invoking the permissionless index synchronization path.

The main prerequisites are market limits that permit the required principal, enough token liquidity to fund it, a collateral asset with sufficient USD value, and an interest-rate curve capable of growing the index past the overflow threshold before the stored index reaches its configured cap. Large-cap or high-decimal markets with loose caps are the relevant targets. Once the required scale is established, ordinary passage of time and a permissionless `update_indexes` call trigger the condition.

This is more severe than a malformed-input crash: the caller does not need invalid data, and no external venue or oracle misbehavior is required.

### Recommendation
Prevent scaled balances from overflowing before index bounds are applied.

Recommended changes:

- Bound `borrow_index` based on the stored `borrowed` share amount before calling `scaled_to_original`.
- Detect `borrowed.raw() * borrow_index.raw() / RAY > i128::MAX` before multiplication and clamp or otherwise resolve the index instead of panicking.
- Apply the same protection to `supplied * supply_index`.
- Make each accrual chunk commit or otherwise preserve progress so one oversized final step cannot roll back all prior accrual.
- Add a regression test proving that `update_indexes`, `repay`, `withdraw`, and liquidation remain executable at the configured maximum market scale and maximum permitted index.
- Consider representing unscaled debt and supply values in `I256` throughout utilization/rate calculation, then checking the reduced utilization ratio rather than requiring the absolute unscaled amount to fit `i128`.

### Proof of Concept
The deterministic regression is present at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`, function `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`.

The test performs the relevant flow:

1. Creates a large 18-decimal market and a separate collateral market.
2. Supplies approximately `1e9` whole 18-decimal units to the target market.
3. Supplies sufficient collateral and borrows approximately 98% of that market.
4. Advances time and repeatedly invokes `update_indexes` on the affected `HubAssetKey`.
5. The synchronization eventually returns `MathOverflow`.
6. The stored `borrow_index` is still below `MAX_BORROW_INDEX_RAY`.
7. Both `withdraw` on the supplier and `repay` on the borrower also return `MathOverflow`.

The observed failure confirms that the unchecked-domain multiplication happens before the index ceiling can protect the calculation, and that the market cannot recover through ordinary user, liquidation, or keeper flows.
