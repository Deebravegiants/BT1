### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [5](#0-4) . The `shop` value dispatched to the app's `WebhookHandler` comes from `request.shop`, which reads the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header directly, with no cryptographic binding to the signed body [3](#0-2) . This breaks the equality that should hold: `shop authenticated by HMAC == shop the handler acts on`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` is required to produce the string that gets HMAC-verified [6](#0-5) . For webhook requests this is implemented as simply `@raw_body` [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are entirely outside the signed material [7](#0-6) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC using `OpenSSL.secure_compare` [2](#0-1) ; because `to_signable_string` never includes the shop header, a request whose body+HMAC pair was legitimately generated for shop A can be replayed with the `shop-domain` header rewritten to shop B, and it will still pass `HmacValidator.validate`. `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and invokes `handler.handle(data: ...)` with that spoofed shop [8](#0-7) .

An attacker who legitimately installs the app on their own shop (an unprivileged action requiring no credentials beyond being a Shopify merchant) will receive real webhook deliveries to the app's shared webhook endpoint, each with a valid `hmac-sha256` value for their own shop's body. Because the gem never binds the shop header into the HMAC digest, the attacker can capture one such body+HMAC pair and resend it directly to the endpoint with an arbitrary `shopify-shop-domain` header value (e.g. a victim merchant's domain). `HmacValidator.validate` still succeeds since only the body is checked, and the merchant-supplied handler receives `WebhookMetadata` claiming the event belongs to the victim's shop.

### Impact Explanation
This is a cross-tenant identity-binding failure directly analogous to the reported analog class: a field the code acts on (`shop`) is not covered by the authentication mechanism (HMAC over body only). Depending on how the host application's webhook handler uses `data.shop` (e.g., to key data store writes, trigger per-shop side effects, or attribute billing/usage events), an attacker can inject events attributed to a victim shop, achieving cross-tenant access/data poisoning without ever needing the app's `client_secret`, an access token, or the victim's credentials.

### Likelihood Explanation
Likelihood is realistic: any unprivileged party can install the app on their own store to obtain a legitimately-HMAC'd payload, then replay it against the shared webhook endpoint with a forged shop header using a normal HTTP client. No secrets, tokens, or elevated access are required — only the ability to receive one webhook for a shop they control and to send an HTTP request with modified headers to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-verified signable material, or independently cross-check the shop header against a value the app already trusts for that endpoint (e.g., match against the installed session's shop) before dispatching to the handler. At minimum, document that `request.shop` is unauthenticated header data and must be re-validated by the host app against its own session/shop registry before use.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and configures/observes a webhook delivery to the app's shared endpoint; captures `raw_body` and the corresponding `shopify-hmac-sha256` header (both valid for their own shop).
2. Attacker resends the identical `raw_body` and `shopify-hmac-sha256` to the same endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the digest only ever covered `raw_body` [5](#0-4) .
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` and processes/persists data under the victim shop's identity [8](#0-7) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
