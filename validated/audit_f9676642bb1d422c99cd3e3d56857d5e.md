## Title
Webhook HMAC signs only the raw body, not the `shop-domain` header — the `shop` field used for tenant attribution is unauthenticated - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` for webhook HMAC verification, but its `to_signable_string` only returns the raw request body, while `shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never part of the signed content.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC-SHA256 over `to_signable_string` and comparing it to the value returned by `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just `@raw_body`: [2](#0-1) 

Meanwhile `shop` (the tenant identity used downstream) is pulled straight from an HTTP header supplied by the caller of `Registry.process`, and is not included in the signed bytes at all: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

This breaks the intended binding `hmac == HMAC(body ‖ shop)`; in reality the gem only enforces `hmac == HMAC(body)`, and `shop` is asserted, not authenticated. Any entity capable of resending a request with a body+HMAC pair (e.g., because they own a separate shop that installed the same app and therefore legitimately receives Shopify-signed webhooks whose HMAC only covers the body) can swap the `shop-domain` header on replay: the HMAC check still passes (it never covered that header), but the app-facing handler receives an attacker-chosen `shop` value paired with a validated-looking payload.

### Impact Explanation
This is a tenant-identity confusion / cross-tenant access primitive: an app's webhook handler is invoked with `WebhookMetadata.shop` claiming a different, victim merchant while the signature check reports success. Any app logic that keys off `request.shop` to select which merchant's session/store/data to update or invalidate can be tricked into acting on the wrong tenant using a signature the app believed authenticated shop+body together. This lands in the Critical "cross-tenant access" bucket defined by the scan rules, because a boundary the gem is expected to enforce (which shop a verified webhook belongs to) is not actually covered by the cryptographic check it performs.

### Likelihood Explanation
Exploitation requires the attacker to have at least one legitimate app installation of their own (to obtain a body+HMAC pair that validates under the app's real `client_secret`), which is realistic for any public/multi-tenant Shopify app since installation is self-service. No access token, `client_secret`, or privileged account is required — only receipt of one webhook the attacker's own store triggers, after which the header can be freely rewritten before replay to the app's webhook endpoint.

### Recommendation
Include the tenant-identifying header (`shop-domain`) — and ideally `topic`/`webhook-id`/`api-version` — as part of the signed material checked in `to_signable_string`, or perform an out-of-band binding (e.g., look up the session/store solely by an identifier that is itself cryptographically tied to the signed body, and reject any header/body shop mismatch) before invoking `handler.handle`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving genuine webhooks with valid `x-shopify-hmac-sha256` computed only over the JSON body.
2. Attacker captures one such `(raw_body, hmac)` pair.
3. Attacker POSTs the same `raw_body` and `hmac` header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`to_signable_string`) — validation succeeds.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, so the app processes attacker-supplied data as if it belonged to the victim shop. [5](#0-4) [6](#0-5)

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
