### Title
Webhook shop/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values consumed by the handler are all read directly from HTTP headers that are never part of the signed content [2](#0-1) . `Registry.process` validates the HMAC and then builds `WebhookMetadata` straight from those unauthenticated header values before dispatching to the app's handler [3](#0-2) .

### Finding Description
The gem's `HmacValidator.compute_signature`/`validate_signature` binds the signature to `verifiable_query.to_signable_string` using the single app-level `Context.api_secret_key` (and optionally `old_api_secret_key`) [4](#0-3) . This secret is the same for every merchant shop that installs the app — it is not shop-specific. Because `to_signable_string` for webhooks equals only the raw body, a valid `hmac-sha256` signature only proves "this body was produced by Shopify (or someone holding the app secret) for *some* webhook," not "this body belongs to *this* shop/topic/webhook-id."

The identity binding that should hold is:
`shop asserted by the HMAC-covered content == shop the app attributes the event to (WebhookMetadata#shop)`

That equality is never checked. `WebhookMetadata.shop`, `.topic`, and `.webhook_id` come from `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers, none of which are included in `to_signable_string` [5](#0-4) . Given the shared secret across shops, a genuine webhook delivery received by the app for one shop (e.g. an attacker's own installed shop) carries a raw body + HMAC pair that remains valid under the same secret if replayed to the app's public webhook endpoint with a substituted `x-shopify-shop-domain`/`x-shopify-webhook-id` header pointing at a different, victim shop that has also installed the same app. `Utils::HmacValidator.validate` will still return `true` since it only recomputes the signature over `@raw_body` [6](#0-5) , and `Registry.process` will then hand `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` — now pointing at the victim shop — to the handler as if Shopify itself attested it for that shop [7](#0-6) .

### Impact Explanation
Any app-supplied `WebhookHandler#handle` implementation that uses `data.shop` to key persistence/authorization decisions (a documented and expected usage pattern) can be made to apply attacker-controlled body content under a victim shop's identity — a cross-tenant confusion crossing the tenant boundary this gem is responsible for enforcing at the webhook ingress point.

### Likelihood Explanation
The attacker needs: (1) their own store to install the same app (a normal, unprivileged action any merchant can take), which lets them receive a legitimately-signed webhook body/HMAC pair from Shopify for topics they can trigger themselves (e.g. `products/update`), and (2) the ability to POST to the app's public webhook endpoint with modified headers, which any internet client can do. No access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the value that is HMAC-verified, or otherwise cryptographically bind the shop/topic to the signed payload, so that `Utils::HmacValidator.validate` fails whenever any of the header-derived fields are inconsistent with what Shopify actually signed for that specific delivery.

### Proof of Concept
1. Attacker creates their own dev store and installs the target app; the app registers a webhook (e.g. `products/update`).
2. Attacker triggers the webhook on their own store, causing the app's endpoint to receive a legitimate request with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid signature over raw_body>`.
3. Attacker replays the exact same `raw_body` (and thus the exact same valid `hmac-sha256`) to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` and/or `x-shopify-webhook-id`/`x-shopify-topic` to target a different registered handler.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the signature over `@raw_body` only and returns `true` [6](#0-5) .
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches to the app's handler as an authenticated event for the victim shop [7](#0-6) .
