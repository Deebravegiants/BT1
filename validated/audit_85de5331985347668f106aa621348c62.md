## Title
Unprivileged donation-based griefing of `SystemInstruction::CreateAccount` permanently blocks legitimate account initialization - (`programs/system/src/system_processor.rs`)

### Summary
`SystemInstruction::CreateAccount` (and `CreateAccountWithSeed`) reject account creation whenever the destination account already holds any lamports, regardless of who put them there. Because any unprivileged actor can transfer lamports to an arbitrary, not-yet-created address via a plain `SystemInstruction::Transfer`, an attacker can pre-fund a target address before its intended owner submits the legitimate `CreateAccount` transaction, permanently causing that transaction to fail. This mirrors the PartyDAO analog: an unprivileged donation corrupts a state assumption ("account starts uninitialized/zero balance") that a subsequent, otherwise-correct operation depends on, resulting in denial of service for the legitimate flow.

### Finding Description
In `create_account`, the very first check bails out if the destination account already has a nonzero lamport balance: [1](#0-0) 

```
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ...
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
```

This check exists to stop legitimate initialization from clobbering an account someone else already funded/owns, but it treats "has lamports" as a proxy for "in use," even though lamports can be deposited by *anyone*, including a malicious third party who is not a signer on the transaction and has no relationship to the intended account owner. `SystemInstruction::Transfer` requires no permission on the *destination* — only the sender must sign — so an attacker can move a minimal amount of lamports into any target pubkey (a derived PDA, a `create_with_seed` address, a vanity keypair address that hasn't landed on-chain yet, etc.) before the intended owner's `CreateAccount` transaction executes. Any subsequent `CreateAccount` call for that address will now unconditionally hit `SystemError::AccountAlreadyInUse`, since the check only looks at lamports and does not distinguish a legitimately pre-funded account from a griefed one.

The project's own recent work acknowledges this exact defect class: it added a new, feature-gated instruction, `CreateAccountAllowPrefund`, whose comment explicitly states it is "intended for use where account has already had rent paid in whole or in part before creation," and which skips the `lamports > 0` rejection entirely: [2](#0-1) 

However, this new instruction is opt-in per caller/program and gated behind `feature_set.create_account_allow_prefund`: [3](#0-2) 

The original `CreateAccount`/`CreateAccountWithSeed` paths — which remain the default and most widely used instructions across wallets, CLIs, and on-chain programs — are unmodified and still vulnerable to the donation-griefing pattern.

### Impact Explanation
An attacker with no special privileges can permanently deny initialization of a specific target account by depositing a nominal amount of lamports to it before the legitimate creator's `CreateAccount` transaction lands. Because the check only requires `lamports > 0`, the attack cost is negligible (a single lamport). Any protocol or user flow that depends on deterministically creating an account at a known address (e.g., PDAs pre-computed off-chain, `create_with_seed` derived addresses, or freshly generated keypairs whose pubkey is published before the creation transaction is submitted) can be blocked indefinitely, forcing a costly recovery path (manual reclaim via `Assign`/`Allocate` on the pre-funded account, or abandoning the intended address) — directly analogous to the softlocking described in the PartyDAO report, where an unprivileged donation broke an implicit "balance starts as expected" invariant and denied the intended state transition.

### Likelihood Explanation
High. The precondition (target address publicly known ahead of the `CreateAccount` transaction, e.g., due to network propagation delay, deterministic derivation, or off-chain coordination) is common in real usage. The attack requires only a standard `Transfer` instruction and no elevated permissions, no gatekeeper bypass, and no race beyond normal transaction ordering.

### Recommendation
Do not treat "any nonzero lamports" as equivalent to "account in use" for the purpose of rejecting `CreateAccount`. Either:
- Make `CreateAccountAllowPrefund` semantics (or equivalent leniency) the default behavior for `CreateAccount`/`CreateAccountWithSeed` once the surrounding invariants (owner is system program, data is empty) are confirmed, rather than gating the fix behind an opt-in instruction that most callers won't use, or
- Update tooling/documentation broadly to require migration to `CreateAccountAllowPrefund` and treat plain `CreateAccount` as deprecated for any flow where the destination address is disclosed before the creation transaction executes.

### Proof of Concept
1. Attacker observes a not-yet-created target pubkey `T` (e.g., a `create_with_seed` derived address published by a dApp, or a fresh keypair whose pubkey is known before its `CreateAccount` transaction is confirmed).
2. Attacker submits `SystemInstruction::Transfer` sending 1 lamport from an attacker-controlled account to `T`. No signature from `T` is required.
3. Victim submits `SystemInstruction::CreateAccount` naming `T` as the `to` account.
4. In `create_account`, `to.get_lamports() > 0` is now true (set to 1 by the attacker), so the instruction fails with `SystemError::AccountAlreadyInUse`, matching the check and existing test `test_create_already_in_use` (`owned_account = AccountSharedData::new(1, 0, &Pubkey::default())`): [4](#0-3) 
5. The victim's intended account can never be created at address `T` through the standard `CreateAccount` path; it is permanently griefed unless the victim happens to use the feature-gated `CreateAccountAllowPrefund` instruction instead.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
