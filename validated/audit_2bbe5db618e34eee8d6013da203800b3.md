### Title
Webhook HMAC only signs the raw body, letting a replayed valid webhook be attributed to any shop - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [1](#0-0) . `Registry.process` trusts `request.shop`/`request.topic` unconditionally once the body HMAC checks out, and forwards them straight to the app's handler as authoritative tenant/topic identity [2](#0-1) .

### Finding Description
The documented processing flow is: construct a `Request` from the raw body and headers, then call `Registry.process`, which does `raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)` and then dispatches to the handler using `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` [2](#0-1) . `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header value [3](#0-2) . For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated headers (`shopify-shop-domain`, `shopify-topic`, etc.) [4](#0-3) .

This breaks the identity binding the gem's own documentation assumes: `shop`, "The shop domain of the webhook", is presented to the handler as trustworthy metadata derived from a request that "did indeed come from Shopify" (per the doc's description of `Registry.process`) [5](#0-4) [6](#0-5) . In reality the HMAC only proves the *body bytes* were signed by the holder of `api_secret_key`; it proves nothing about which shop or topic that body is being claimed to belong to. Because the app's shared `api_secret_key` is the same across every shop that installs the app, any actor who can obtain one genuine `(raw_body, hmac)` pair for any topic/shop (e.g. from their own installed test shop, from a proxy/log capture of their own webhook traffic, or from a shop they legitimately control) can resubmit that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Registry.process` will pass HMAC validation (it never re-checks the header) and hand the handler a `WebhookMetadata` claiming the payload belongs to a different, victim shop [7](#0-6) .

This is exactly the bug class flagged in the report: an equality the gem should enforce — "shop the HMAC secret vouches for" == "shop the handler is told the data belongs to" — is never checked; the second value comes from bytes the HMAC does not cover.

### Impact Explanation
If the host app uses `data.shop` to select which merchant's records to update, queue a job for, or use for authorization/routing (exactly as shown in the gem's own example handler, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [8](#0-7) , an attacker can inject forged/replayed webhook payloads that are processed under another tenant's identity — a cross-tenant data-integrity/confusion issue. This satisfies the "cross-tenant access" High-impact criterion, since the tenant boundary (`shop`) that the app relies on from this gem's verified webhook object is not actually authenticated.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine `(raw_body, hmac)` pair signed with the app's real `api_secret_key`. This is realistic without any leaked credential: any unprivileged party who installs the target app on their own shop will receive genuinely-signed webhooks for that shop and can capture the exact bytes and HMAC header from their own traffic (e.g. via their own reverse proxy/logging in front of the app, or any shop they control that has network visibility into requests destined to the app). They then replay the identical body+hmac to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No `api_secret_key`, access token, or victim credential is required — only observation of one's own legitimately-received webhook traffic, which is not a privileged action.

### Recommendation
Bind the authenticated identity fields into the signed payload check rather than trusting bare headers:
- Extend `to_signable_string` (or add a separate verification step in `Registry.process`) to incorporate `shop-domain`, `topic`, and `webhook-id` into what is authenticated, or
- Cross-validate `request.shop` against an independently-known, already-authenticated identifier for the expected tenant (e.g. the shop associated with the webhook subscription/registration that the topic+webhook_id maps to) before dispatching to the handler, and
- Document explicitly that `data.shop`/`data.topic` are unauthenticated header values and must not be used as an authorization boundary without additional verification, since Shopify's own HMAC scheme signs only the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for secret `S`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`. The attacker captures `B` and `H` from their own outbound traffic (e.g., via their own proxy in front of the endpoint, or by re-using a payload sample they received while testing).
3. Attacker sends a POST to the app's public webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H})` is built; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string == B` and matches `H` — validation passes [9](#0-8) [1](#0-0) .
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)`, and the app processes/attributes attacker-controlled order data as belonging to `victim.myshopify.com` [10](#0-9) .

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
