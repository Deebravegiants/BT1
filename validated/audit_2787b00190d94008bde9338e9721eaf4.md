This confirms the abstract interface: `VerifiableQuery` requires only `hmac` and `to_signable_string`, and for webhooks, `to_signable_string` returns just the raw body — no header data (including `shop`) is part of the signed payload.

### Title
Webhook shop-domain header is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then uses the unauthenticated `X-Shopify-Shop-Domain` header value as the tenant identifier (`shop`) passed to the app's webhook handler. Because the shop domain is not part of the signed bytes, an attacker who can obtain one validly-signed webhook body (e.g., by installing the app on their own shop, which shares the same `api_secret_key` across all shops for a given app) can replay that body with a forged `shop-domain` header pointing at a victim shop, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is not included anywhere in the signable string: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the raw body for webhooks) using the app's shared `api_secret_key`: [4](#0-3) 

`Registry.process` treats a passing HMAC check as sufficient authentication, then forwards `request.shop` — the unauthenticated header value — directly to the handler as the tenant identity, with no secondary binding to the shop that actually produced the signature: [5](#0-4) 

The identity binding that should hold is: `shop asserted by the HMAC-signed payload == shop the handler treats as the source of the webhook`. Since the signed bytes never include the shop domain, and the app's `api_secret_key` is the same for every shop that installs the app, this equality does not hold — the HMAC only proves "some shop with this app installed sent this body," not "this specific shop sent this body." A malicious but otherwise unprivileged merchant who installs the app on their own store can capture a genuine `(raw_body, hmac)` pair from their own webhook deliveries and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop that also has the app installed. `HmacValidator.validate` will still return `true` because it only checks the body against the shared secret, and `Registry.process` will invoke the handler with `shop: <victim shop>`, `body: <attacker-controlled body content, subject to the topic's schema>`.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: consuming applications rely on `WebhookMetadata#shop` from `Registry.process` as the authenticated identity of the webhook's origin store, in order to route/apply the event to the correct tenant's data (e.g., orders, products, app data for that shop). Because the shop is unauthenticated relative to the HMAC, an attacker with only the unprivileged ability to install the target app on their own store can forge webhook deliveries that are processed as if they originated from any other shop with the app installed, corrupting or exfiltrating tenant data cross-shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app built on this gem: an attacker only needs to be a normal Shopify merchant who installs the target app on their own store (no special credentials, no access token theft, no TLS interception). They can capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair from a webhook delivered to their own endpoint for a topic whose body they can influence (e.g., a resource they create/update themselves), then replay it against the same endpoint with a different `x-shopify-shop-domain` header value naming a victim shop that also has the app installed. Nothing in `Request` or `Registry.process` rejects this.

### Recommendation
Bind the shop identity into the authenticated bytes, or otherwise verify it out-of-band before trusting it:
- Prefer per-shop verification: after HMAC validation succeeds, cross-check `request.shop` against the shop associated with the session/access token or webhook subscription that is expected to be receiving this callback, rather than trusting the header value unconditionally.
- At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a tenant key without additional verification (e.g., confirming an active, stored session/installation exists for that shop before applying the event), since the HMAC does not bind the shop domain.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (a normal unprivileged action).
2. Attacker triggers a webhook topic they control the body of (e.g. `orders/create` for an order they place), and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this signature is computed the same way for every shop that installed this app, since `api_secret_key` is shared per-app, not per-shop:
```ruby
# lib/shopify_api/utils/hmac_validator.rb
computed_signature = compute_signature(verifiable_query.to_signable_string, secret) # = body only
```
3. Attacker replays the exact same body `B` and hmac `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a shop that also has the app installed).
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`:
```ruby
# lib/shopify_api/webhooks/registry.rb
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
5. The handler receives `shop: "victim-shop.myshopify.com"` alongside attacker-controlled body content `B`, and the host application applies/stores this event as if it legitimately originated from the victim shop.
