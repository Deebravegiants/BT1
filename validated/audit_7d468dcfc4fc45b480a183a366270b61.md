### Title
`findMatchingWithdrawal` in POA bridge ignores `index`/`amount`, causing misreported `txHash` for same-token multi-leg withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain `txHash` for a given `WithdrawalIdentifier` by calling `findMatchingWithdrawal`, which matches purely on `nep141:${w.data.near_token_id} === assetId` and never consults `args.index` or `args.withdrawalParams.amount`. When a single NEAR transaction contains two withdrawal legs for the same token (e.g. a user submits `withdrawalParams` with two entries of the same `assetId` but different `amount`), both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` query the same `withdrawal_hash` and the same unsorted `withdrawals` array, and `.find()` returns whichever entry appears first for both calls.

### Finding Description
The claimed invariant is: `txHash_reported_for_index_1 == outcome_on_chain_of_index_1` (i.e., the `txHash` returned for the leg identified by `index:1` and `amount:500` must be the transfer that actually settled that 500-unit leg).

Code path:
- `describeWithdrawal` (poa-bridge.ts lines 313-343) calls `getWithdrawalStatusWithRetry` keyed only by `args.tx.hash` [1](#0-0) , then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`.
- `findMatchingWithdrawal` (lines 409-427) does `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)` — no use of `index` or `amount` at all [2](#0-1) .
- The code's own comment acknowledges this: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) .
- `index` values for same-route withdrawals are assigned sequentially per bridge route (confirmed by `withdrawal-watcher.test.ts`: "maintains separate index counters per bridge route") [4](#0-3) , and both legs share the same `tx.hash` used as `withdrawal_hash` in the query.

An ordinary user who submits a single signed intent with two withdrawal legs of the same POA-bridged token (different amounts, e.g. 100 and 500) causes the PoA indexer to return an unsorted list containing two `COMPLETED` entries with identical `near_token_id` but different `amount`/`transfer_tx_hash`. Calling `describeWithdrawal` for `index:0` and `index:1` both invoke `findMatchingWithdrawal` with the same `assetId`, and `Array.prototype.find` returns the same first match for both calls — so at least one of the two `describeWithdrawal` results reports the wrong `transfer_tx_hash` for its `index`/`amount`.

None of the existing guards prevent this: `validateWithdrawal`, `supports()`, `compareAddresses`, and the min-amount check operate on withdrawal creation, not on status matching; `getWithdrawalStatusWithRetry` only keys by `tx.hash`, not by amount or index; there is no sorting/pairing logic despite the comment mentioning a possible future fix ("matching could be done by sorting both API results and withdrawal params by amount").

### Impact Explanation
An integrator (or the SDK's own `watchWithdrawal`/`waitForWithdrawalCompletion`, see poa-bridge.ts lines 313-343 and withdrawal-watcher.ts lines 20-77) relies on the `txHash` returned by `describeWithdrawal` to determine "this specific withdrawal leg landed on-chain with this hash," and will typically release/credit funds, mark orders complete, or trigger downstream accounting keyed by that per-leg hash. Because both legs can resolve to the same (wrong) `txHash`, an integrator can end up crediting/refunding the same on-chain transfer twice for two logically distinct withdrawal legs, or attribute the wrong transfer hash to the wrong leg — a misreport causing double-credit, matching the stated "status or hash misreport making an integrator credit or refund twice" category. This is repeatable on every multi-leg same-token withdrawal a user submits.

### Likelihood Explanation
Precondition: the attacker (an ordinary user with their own funds) must submit a withdrawal request containing two or more legs for the same POA-bridged `assetId` in a single NEAR transaction — something the public `WithdrawalParams[]`/multi-withdrawal API path permits without any special privilege. No malicious relayer, RPC, or bridge API misbehavior is required — the POA indexer legitimately returns multiple completed withdrawals for the same token under the same `tx.hash`, and the SDK's own matching logic (not the indexer) fails to disambiguate them. This is low-cost and fully reproducible by any user who withdraws the same token twice in one call.

### Recommendation
Fix `findMatchingWithdrawal` to also disambiguate by amount and/or ordinal position: sort both the API's `withdrawals` array and the local per-route withdrawal params by `amount` (as the existing comment suggests, since relayer fees are equal for the same token) and match the `index`-th entry in each sorted list, or track and consume matched withdrawals so the same entry cannot satisfy two different indices in one `describeWithdrawal` batch.

```ts
// poa-bridge.test.ts style vitest test
it("misreports txHash for two same-token withdrawals in one tx", async () => {
  vi.mocked(poaBridge.httpClient.getWithdrawalStatus).mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "zec.omft.near", amount: 100, transfer_tx_hash: "tx-for-100", /* ... */ } },
      { status: "COMPLETED", data: { near_token_id: "zec.omft.near", amount: 500, transfer_tx_hash: "tx-for-500", /* ... */ } },
    ],
  });

  const bridge = new PoaBridge({ envConfig: configsByEnvironment.production, xrplRpcUrls: [] });

  const resultIndex0 = await bridge.describeWithdrawal({
    landingChain: Chains.Zcash, index: 0,
    withdrawalParams: { assetId: "nep141:zec.omft.near", amount: 100n, destinationAddress: "...", feeInclusive: false },
    tx: { hash: "near-tx-hash", accountId: "test.near" },
  });

  const resultIndex1 = await bridge.describeWithdrawal({
    landingChain: Chains.Zcash, index: 1,
    withdrawalParams: { assetId: "nep141:zec.omft.near", amount: 500n, destinationAddress: "...", feeInclusive: false },
    tx: { hash: "near-tx-hash", accountId: "test.near" },
  });

  // Both resolve to the same first match ("tx-for-100"), violating
  // txHash_reported_for_index_1 == outcome_on_chain_of_index_1 (should be "tx-for-500")
  expect(resultIndex1.txHash).toBe("tx-for-100"); // demonstrates the bug
  expect(resultIndex1.txHash).not.toBe("tx-for-500"); // the amount-500 leg's actual hash
  expect(resultIndex0.txHash).toBe(resultIndex1.txHash); // both indices collapse to same hash
});
```

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
