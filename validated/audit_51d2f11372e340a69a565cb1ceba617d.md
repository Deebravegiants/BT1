### Title
Unguarded subtraction in `canGraduate` can underflow and permanently brick trading on a curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` computes the USD-graduation leg as `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with no floor/guard [1](#0-0) . This is called unconditionally at the end of every buy inside `Bonding._executeBuy` [2](#0-1) . If the pair's stored `assetReserve` is ever pushed below the immutable launch-time virtual LT reserve (`Pair.k() / TOTAL_SUPPLY`), the subtraction underflows under Solidity 0.8 checked arithmetic and reverts — and because every future buy re-executes this same check, the revert becomes permanent, freezing the curve.

### Finding Description
`Pair.swap` enforces the K-invariant with a `+1` rounding slack on both sides: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts [3](#0-2) . This slack exists because `Router._computeBuy` / `Router._computeSell` both derive the new reserve via a floored division of `k`:

- Buy: `tokensOut = reserveToken - (k / newReserveAsset)` [4](#0-3) 
- Sell: `assetOut = reserveAsset - (k / newReserveToken)` [5](#0-4) 

On the sell leg, the floored division always rounds the resulting `assetReserve` down (i.e. gives the seller marginally more LT than the exact continuous curve would), so each sell can shave a fraction of a wei off the stored `assetReserve` relative to the ideal curve value, while `tokenReserve` on that leg is updated exactly (no rounding). Repeated round-trip buy/sell cycles by an unprivileged trader accumulate this sub-wei asset-side drift, tolerated by the `+1` K slack in `Pair.swap`, and can in principle push the pair's stored `assetReserve` below the immutable `virtualLtReserve` baseline set at launch (`Pair.k() / Token.TOTAL_SUPPLY()`), which `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity` all treat as a hard floor with unguarded subtraction [6](#0-5) .

Once `assetReserve < virtualLtReserve`, `canGraduate` underflows and reverts on every call. Since `Bonding._executeBuy` calls `canGraduate(tokenAddress)` unconditionally at the tail of every buy [7](#0-6) , this turns every subsequent buy through `Zap.buy` / `Bonding.buy` into a guaranteed revert, and `Bonding.triggerGraduation` (which also calls `canGraduate`) becomes permanently unusable as well [8](#0-7) . The curve is left stuck in `Lifecycle.Curve` with no path to trade further or graduate — a permanent freeze reachable purely through unprivileged `Zap.buy` / `Zap.sell` calls.

This is the closest reachable analog to CVE-2021-32135's class (an unguarded/degenerate arithmetic condition, reachable via crafted-but-permitted input, that permanently crashes/DoSes a core code path): here, a crafted sequence of ordinary buy/sell transactions plays the role of the "crafted file," and the unguarded `assetReserve - virtualLtReserve` subtraction plays the role of the null-pointer-style unchecked access.

### Impact Explanation
If reachable, this permanently freezes a specific token's curve: no further buys are possible (every `_executeBuy` reverts on the trailing `canGraduate` call), and the curve can never reach graduation via `triggerGraduation` either. Trader capital already committed to that curve becomes stuck (no exit via a curve sell either, since `Zap.sell`'s graduatable-check path also depends on `canGraduate`, per the documented dual-trigger design). This matches the "permanent freezing of trader funds" bar.

### Likelihood Explanation
Low-to-uncertain. The per-transaction drift on `assetReserve` from the floor-rounding described is bounded by well under 1 wei of LT (18-decimal token) per sell, tolerated by the pair's `+1` K-slack. Reaching a full-wei accumulated deficit large enough to underflow `assetReserve - virtualLtReserve` (a value typically on the order of thousands of LT wei-equivalents for the `$3K` virtual liquidity design) would require an very large number of round-trip transactions, each paying real gas and real curve trading costs for essentially zero economic return. I was not able to fully derive, within the scope of this review, the exact number of round trips or whether the rounding direction is strictly monotonic in the attacker's favor across a full buy+sell cycle (the buy leg's rounding hits `tokenReserve`, not `assetReserve`, which complicates the accumulation argument) — this needs a targeted fuzz/invariant test (extending `test/GraduationInvariants.t.sol`) to confirm whether `assetReserve` can ever be driven below `virtualLtReserve` under any adversarial sequence of buys/sells, or whether it is provably infeasible.

### Recommendation
- Add an explicit guard in `canGraduate` (and `previewLtUntilGraduation`, `_prepareGraduationLiquidity`) so that `assetReserve < virtualLtReserve` is treated as "not graduatable yet" / `ltFromPair = 0` rather than an unguarded subtraction, e.g. `uint256 realLtRaised = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0;`.
- Add a fuzz/invariant test that specifically drives long sequences of small buy/sell round trips against a single curve and asserts `assetReserve >= virtualLtReserve` holds at every step, to determine conclusively whether the drift described above is reachable in practice.

### Proof of Concept
Conceptual reproduction (not verified against the exact numeric bound in this review):
1. Launch a token via `Zap.createToken` with a minimal seed, giving pair `assetReserve == virtualLtReserve` initially.
2. Have an unprivileged trader repeatedly call `Zap.buy(token, small amount, 0, referrer)` followed immediately by `Zap.sell(token, all tokens received, 0)`, many times, exploiting the sub-wei rounding favor on the sell leg's `assetOut` computation in `Router._computeSell`.
3. After a sufficiently large number of iterations (count unconfirmed), check whether `IPair(pair).getReserves()`'s `assetReserve` drops below `IPair(pair).k() / Token(token).TOTAL_SUPPLY()`.
4. If so, the next call to `Bonding.canGraduate(token)` (and hence any subsequent `Zap.buy`) reverts with an arithmetic underflow panic, permanently freezing the curve.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
