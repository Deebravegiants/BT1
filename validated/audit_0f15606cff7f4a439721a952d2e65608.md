### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain`, `topic`, and `webhook-id` headers to route and label the payload for the receiving application. Because these identity-binding fields are not part of the signed content, they can be swapped on a request whose body+HMAC pair the attacker legitimately possesses (e.g., from webhooks delivered to their own shop), causing the payload to be attributed to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from HTTP headers and are never included in the signable string: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)` (which, via `VerifiableQuery`, checks `hmac` against `to_signable_string`, i.e., the body only), and then immediately uses the unauthenticated `request.topic` to look up a handler and the unauthenticated `request.shop` to construct the metadata passed to that handler: [3](#0-2) 

This mirrors the report's root cause pattern: an identity/attribution field (`shop-domain`, akin to the NFT `_id` in the analog) is *acted upon* by the consuming logic (`handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`) but is *not covered* by the cryptographic binding (`HmacValidator` only signs `@raw_body`). The equality that should hold — "the shop bound by the signature" == "the shop the handler acts on" — is broken: the HMAC binds `secret ⊕ raw_body`, while the handler consumes `header['shop-domain']`, an entirely separate, unauthenticated channel.

### Impact Explanation
An unprivileged internet user who has legitimately received any signed webhook for a shop they control (e.g., by installing the app on their own free/dev store) possesses a valid `(raw_body, hmac)` pair. Because `shop-domain`, `topic`, and `webhook-id` are outside the signed content, that same valid pair can be resent directly to the app's webhook endpoint with those headers altered to reference a different, victim tenant. Downstream host applications that key their per-shop side effects (order/customer updates, GDPR redaction flags, uninstall handling, etc.) off `WebhookMetadata#shop`/`#topic` as returned by this gem will process attacker-supplied data under the victim's tenant identity — this is a cross-tenant confusion inside the trust boundary this gem is responsible for enforcing (HMAC-based webhook authenticity), even though it operates within the gem's documented API.

### Likelihood Explanation
Moderate. The prerequisite is only possession of one valid signed webhook (trivially obtainable by installing the app on an attacker-owned store, since HMAC uses the single global `client_secret` shared for all shops) and a raw HTTP client — no leaked credentials, TLS interception, or privileged access are required. This is exactly the kind of "unprivileged internet user" scenario described in scope.

### Recommendation
Include the identity/routing fields — at minimum `shop-domain` and `topic` — in the signed content checked by `HmacValidator`, or otherwise cryptographically bind them to the verified body (e.g., derive/verify `shop` from a signed claim rather than a bare header) before they are used to construct `WebhookMetadata` or select a handler.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture a legitimate webhook POST, e.g. `orders/create` with `raw_body` B and header `shopify-hmac-sha256: H` (valid because `HmacValidator.validate` only checks `H` against `B`) — see `lib/shopify_api/webhooks/request.rb` lines 10-13, 35-38.
2. Replay the exact same `raw_body` B and `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`) to the app's webhook endpoint.
3. `Utils::HmacValidator.validate(request)` returns `true` because validation only covers `B` (`lib/shopify_api/webhooks/registry.rb` line 190).
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the attacker-controlled `shop`/`topic` headers (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host application to act on attacker-supplied content as if it belonged to `victim.myshopify.com`.
