### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing shop-spoofing on an otherwise "verified" webhook - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate` succeeds, then blindly trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — none of which are covered by the HMAC that was just validated.

### Finding Description
`Registry.process` gates handler execution purely on HMAC validation, then forwards `request.shop` (and other header-derived fields) to the handler as trusted, authenticated data: [1](#0-0) 

`Request#hmac` and `Request#to_signable_string` show that the HMAC signature is computed and verified against `@raw_body` only: [2](#0-1) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers, which are completely outside the signed payload: [3](#0-2) 

`HmacValidator.validate_signature` confirms the check is scoped only to `verifiable_query.to_signable_string` (the body) versus the `hmac` header value — the `shop-domain` header plays no role in the comparison: [4](#0-3) 

This mirrors the report's bug class directly: the pool-balance report's root cause is that a value used for a critical downstream decision (TVL/fee correctness) is derived from a source (`balanceOf`) that is not bound to the mechanism meant to guarantee its integrity (the deposit accounting). Here, the `shop` identity value used for a critical downstream decision (which tenant's data the webhook is attributed to) is derived from a source (HTTP header) that is not bound to the mechanism meant to guarantee its integrity (the HMAC signature). The equality that should hold — "shop value verified by HMAC" == "shop value the handler acts on" — is broken because the HMAC only ever covers `@raw_body`, never the `shop-domain` header.

### Impact Explanation
Any party who can get one legitimate, HMAC-signed webhook delivered to an app's endpoint (e.g., an attacker's own shop installs the app and triggers a webhook for a topic the app handles) can replay that exact request body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. `Utils::HmacValidator.validate` still returns `true` because only the body is hashed, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)` reporting the attacker-chosen shop as the verified tenant. Any host application that trusts `data.shop` from a processed webhook as the authenticated tenant identifier (which is the gem's own documented usage pattern, per `docs/usage/webhooks.md`) will attribute/act on the payload for the wrong tenant — a cross-tenant data confusion/injection primitive.

### Likelihood Explanation
The only requirement is possession of one valid signed webhook body+HMAC pair for any topic the target app registers, which any merchant installing the app can trivially obtain by triggering their own webhook and capturing the raw request. No secret key, access token, or privileged access is required — only control over the HTTP request delivered to the app's public webhook endpoint.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed payload used for comparison, or otherwise cryptographically bind them to the signed body, so that `HmacValidator.validate` fails if any of these fields are altered independently of the signed content. At minimum, `Registry.process` and the documentation should make explicit that `request.shop`/`request.topic` are unauthenticated metadata and must not be trusted as tenant identifiers without additional verification (e.g., cross-checking against a known session/shop record).

### Proof of Concept
1. Attacker (a legitimate merchant with the app installed) triggers a webhook for a subscribed topic, capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify.
2. Attacker replays this exact body and HMAC header to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `OpenSSL.secure_compare(computed_signature, received_signature)` against `request.to_signable_string` (`@raw_body`), per [5](#0-4)  and [4](#0-3) .
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` as if Shopify had verified that shop, per [1](#0-0) , even though the shop value was never covered by the HMAC.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
