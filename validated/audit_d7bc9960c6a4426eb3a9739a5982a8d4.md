## Analog Found

### Title
Missing return-value validation on `IERC20.transfer` in Tron `IntentGatewayV2.withdraw()`/`sweepDust()` permanently locks escrowed and fee funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) escrows tokens via `SafeERC20.safeTransferFrom` on `placeOrder`, but releases them on settlement using a raw low-level `.call` that only checks the boolean *call success*, never the ERC20 return data. This is the inverse case of the reported `UXDGovernor`/`UXDTimelockController` bug class ("don't support non-standard ERC20 implementations that don't return `true`"): here, a token that returns `false` on failure instead of reverting is silently treated as a successful transfer, while `_orders` escrow accounting is unconditionally decremented.

### Finding Description
`withdraw()` releases escrowed input tokens and accumulated transaction fees to the beneficiary/solver using: [1](#0-0) [2](#0-1) 

and `sweepDust()` (protocol dust withdrawal) has the identical pattern: [3](#0-2) 

In all three spots, only `success` from the raw `.call` is checked — the code never decodes/verifies the boolean encoded in the ERC20 `transfer` return data (as `SafeERC20.safeTransfer` would). Standard OpenZeppelin `SafeERC20` is imported and used elsewhere in the same file for the deposit side (`safeTransferFrom` on `placeOrder`), so this is an inconsistency specific to the release path: [4](#0-3) 

The escrow decrement happens unconditionally right after the unchecked `.call`: [5](#0-4) 

For any ERC20 token (or TRC20 token on Tron, which frequently deviates from strict boolean-return semantics) that returns `false` rather than reverting on a failed transfer (e.g. insufficient contract balance edge cases, blacklist checks, paused states, or non-standard implementations), the low-level `.call` itself succeeds (no revert), `success == true`, `TransferFailed` is never raised, yet no tokens actually move to the beneficiary. The `_orders[body.commitment][token]` escrow is nonetheless decremented (or fully deleted for the fee slot), so the order is marked filled/refunded and the escrow record is destroyed while the underlying tokens remain stuck in the contract with no accounting path left to reclaim them.

### Impact Explanation
This causes permanent loss/freezing of escrowed user or fee funds: once `withdraw()` runs (called from `onAccept` on a relayed `RedeemEscrow`/refund message, or from `onGetResponse` for the cancellation path) and the escrow row is zeroed/deleted, there is no other function that can re-derive or re-release those tokens — the commitment's escrow state is gone even though the beneficiary never received the tokens. Both users (order refunds) and solvers (order fills) are exposed, and the protocol's own fee slot funds can be lost the same way. This satisfies the "permanent freezing/loss of funds" bar for Medium-severity classification.

### Likelihood Explanation
Reachable by any unprivileged actor: a solver filling a cross-chain order, a relayer delivering the settlement `PostRequest` that triggers `onAccept` → `withdraw()`, or a user's cancellation GET response triggering `onGetResponse` → `withdraw()`. It only requires that one of the escrowed tokens is a non-strictly-compliant ERC20/TRC20 that returns `false` instead of reverting on transfer failure — a realistic occurrence given TRC20 tokens on Tron are known to have non-standard implementations, and this is the exact chain (`evm/tron/...`) this contract targets.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` in this same file) instead of the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and `sweepDust()`, so that both call failure and a `false` boolean return value revert the transaction and the escrow state is not corrupted.

### Proof of Concept
1. Deploy a non-standard ERC20/TRC20 token `T` whose `transfer` function returns `false` (instead of reverting) when e.g. the recipient is blacklisted or an internal condition fails, without reverting.
2. A user calls `placeOrder` with `T` as an input token; `safeTransferFrom` succeeds, escrow `_orders[commitment][T] = amount` is set.
3. A solver fills the order cross-chain; the settlement message is relayed and `onAccept` invokes `withdraw()` for token `T`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, <return data encoding false>)` — `success` is `true` because the call itself did not revert.
5. `TransferFailed` is never triggered; `_orders[commitment][T]` is decremented to zero and `EscrowReleased` is emitted, but `beneficiary` never received tokens `T`; the tokens remain stranded in the `IntentGatewayV2` contract with no remaining accounting path to recover them.
