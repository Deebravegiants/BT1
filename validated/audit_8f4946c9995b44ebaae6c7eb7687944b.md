### Title
Webhook Shop Domain and Topic Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers [2](#0-1) . `Webhooks::Registry.process` verifies only that the body's HMAC is valid and then forwards the header-derived `shop` value straight to the application handler as the tenant identifier [3](#0-2) . Because the HMAC binds only the body bytes and not the shop/topic/webhook-id headers, any previously captured, validly-signed webhook body can be replayed with a different `X-Shopify-Shop-Domain` header to make the app process attacker-controlled data under a victim shop's identity.

### Finding Description
The identity binding that should hold is:

`HMAC-verified bytes == bytes the handler trusts for tenant identity (shop)`

In this gem that equality is broken. `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [4](#0-3) . For webhook requests, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors pull straight from HTTP headers with no cryptographic binding to that signature [2](#0-1) .

`Registry.process` uses exactly this unauthenticated `request.shop` as the tenant key passed to the application's webhook handler:
```
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [3](#0-2) 

Since the gem's own `api_secret_key` is shared by Shopify and the app across every shop that installs the app (it is not shop-specific), the only cryptographic material that ties a webhook body to a specific tenant is the body content itself plus whatever the app chooses to log/echo back to the merchant. Any body+HMAC pair that was legitimately delivered by Shopify for one shop (e.g. captured via a debug/log view the app exposes to its own merchant, or via Shopify's "resend webhook" sample payload tooling) remains fully valid when replayed to the same public webhook endpoint with the `shop-domain` header swapped to any other shop. `HmacValidator.validate` will pass because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` object claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an unprivileged app user (a shop that has the app installed, with no special access token or `client_secret`) can cause the application to process attacker-supplied data under a different shop's identity. Most webhook handlers use `shop` to select which merchant's records to create/update/delete, so this enables cross-tenant data injection/corruption without ever needing the app's secret, an access token, or a refresh token — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite (an attacker legitimately installs the app on their own shop and can observe one validly-signed webhook body, e.g. through debug logging that echoes raw payloads, or through Shopify's own webhook resend/testing features) is realistic for many real-world app deployments and requires no compromise of secrets or infrastructure. The exploit itself is a single crafted HTTP request with a substituted header, so once the pre-condition is met, exploitation is trivial and repeatable for any topic the app subscribes to.

### Recommendation
Include the `shop-domain`, `topic`, `api-version`, and `webhook-id` header values in the signable string used for HMAC computation (or otherwise cryptographically bind them to the body, e.g. by hashing them together before comparison), so a body signed for one shop/topic/webhook cannot be replayed under different header values. At minimum, `Webhooks::Request#to_signable_string` should incorporate these header fields rather than only `@raw_body`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers an event (e.g., `orders/create`) so Shopify delivers a legitimately HMAC-signed webhook to the app's public endpoint. Attacker obtains the exact `raw_body` and `X-Shopify-Hmac-Sha256` value (e.g., via a debug/log feature the app exposes, or a tunneling/inspection tool sitting in front of their own installation).
2. Attacker resends this exact `raw_body` and `X-Shopify-Hmac-Sha256` to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the untouched `raw_body` against the untouched HMAC — validation succeeds [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-originated body, and the application performs tenant-scoped side effects (e.g., DB writes) attributed to the victim shop.
