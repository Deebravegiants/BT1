### Title
Webhook shop identity spoofing due to HMAC covering only the request body, not the shop-domain header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body. The `shop` (tenant identity), `topic`, and `webhook_id` values are read straight from HTTP headers that are not covered by the HMAC. `Registry.process` trusts `request.shop` for routing/tenant attribution after only validating the body's HMAC.

### Finding Description
`Utils::HmacValidator.validate` verifies `computed_signature == hmac` where `computed_signature` is computed over `verifiable_query.to_signable_string` [1](#0-0) 
and for webhooks that signable string is defined as just `@raw_body` [2](#0-1) 
while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from the `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id`/`shopify-api-version` headers, none of which are part of the signed bytes [3](#0-2) 
`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using `request.shop` and `request.topic` for dispatch, with no additional binding check [4](#0-3) 

The identity binding broken is: `verified_bytes (raw_body signed with HMAC(api_secret_key)) == tenant_identity (shop header used for dispatch)`. Because the app's `api_secret_key` is shared across every shop that installs the app (it's the app-level client secret, not per-shop), any party who can obtain one validly-signed `(raw_body, hmac)` pair — e.g., by installing the app on their own development/test store and receiving a legitimately signed webhook for a topic whose body they can influence — can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while swapping only the `shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This crosses the tenant boundary: an attacker with no relationship to the victim shop can cause the app to process attacker-controlled webhook data (whatever body content Shopify would sign for the attacker's own store/topic) as if it originated from the victim's shop. Depending on how the host application's webhook handler uses `data.shop` (e.g., looking up the corresponding merchant session, writing to per-shop storage, triggering side effects keyed by `shop`), this enables cross-tenant data injection/corruption attributed to the victim's session — matching the report's "Critical: cross-tenant access" category, since tenant isolation for webhook-derived state is broken purely through this gem's verification logic.

### Likelihood Explanation
Moderate-to-High. The attacker needs only: (1) their own installed instance of the target app (self-serve, unprivileged — any developer can install a public/free app on a dev store, or trigger a mandatory topic like `app/uninstalled` which carries almost no attacker-influenced body but is still a valid replay target), and (2) the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which is trivial. No access token, `client_secret`, or leaked credential is required — the HMAC used is legitimately produced by Shopify itself for the attacker's own store.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the verified data before trusting it: either include the `shopify-shop-domain` (and `shopify-webhook-id`) header value in the HMAC-signed payload used by `to_signable_string`, or independently verify that the shop asserted in the webhook actually has an active, matching webhook subscription (e.g., cross-check `webhook_id` against a per-shop record created at registration time) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (self-serve, no privilege needed) and registers/receives a webhook for a topic whose body content is attacker-influenced or predictable (e.g., `app/uninstalled`, or any topic with body they can shape via their own store actions).
2. Shopify sends the attacker's app endpoint a legitimately HMAC-signed request: headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: <topic>`, `X-Shopify-Hmac-Sha256: <valid hmac of raw_body>`, plus `raw_body`.
3. Attacker captures this exact `(raw_body, hmac header)` pair.
4. Attacker crafts a new POST to the same app endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4) 
which recomputes the HMAC over `raw_body` only and finds it matches (since `raw_body` and the secret are unchanged), so validation succeeds despite the shop header being forged.
6. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the app to process attacker-supplied data under the victim shop's identity.
