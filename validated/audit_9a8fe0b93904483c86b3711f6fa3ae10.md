### Title
Webhook `shop`/`topic` Identity Is Not Bound by the HMAC Signature, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the **raw body**, then dispatches the handler using the `shop` and `topic` values taken directly from unauthenticated HTTP headers. Because the api_secret_key is shared by the app across every shop that installs it, any shop merchant who receives a legitimately-signed webhook for their own tenant can replay that exact `(body, hmac)` pair while substituting the `x-shopify-shop-domain` header for a different victim shop. The HMAC check still passes because it never covers the header, breaking the intended binding of `shop` to the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` verifies only the body's HMAC and then trusts `request.topic`/`request.shop` to dispatch and construct `WebhookMetadata`: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and secret, with no shop/topic binding: [4](#0-3) 

The broken identity equality is:
`shop_used_for_dispatch (header, unauthenticated)` ≠ `shop_bound_by_hmac (none — HMAC covers body only)`

Since the app's `api_secret_key` is the same for all shops that install the app (it is not per-tenant), any shop that has installed the app receives genuinely HMAC-signed webhook deliveries for its own tenant. That merchant can capture one such `(raw_body, hmac-sha256 header)` pair and resend it to the app's public webhook endpoint with an altered `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header pointing at a different shop. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` will happily call the handler with `shop: <victim-shop>` and the attacker-chosen topic/body.

### Impact Explanation
This is a cross-tenant identity-binding failure: the `shop` value handed to application webhook handlers — which apps typically use as the tenant key to look up sessions, update records, or trigger tenant-scoped side effects — is not authenticated at all. Any shop installing the app can forge webhook events "on behalf of" any other shop known to the attacker (e.g., by domain guessing/enumeration), causing the app to process attacker-controlled webhook data under another merchant's identity. This falls under the "cross-tenant access" Critical impact bucket defined in scope.

### Likelihood Explanation
Requires only an unprivileged internet user who has installed the app on their own store (a normal, unprivileged merchant/tenant — no leaked credentials, no `api_secret_key`, no TLS interception needed) and can send arbitrary HTTP requests to the app's public webhook endpoint. Capturing one legitimate signed webhook for their own shop is trivial (they own that endpoint's traffic/logs), and replaying it with a modified header requires no cryptographic secret.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed material verified by `Utils::HmacValidator`, or otherwise cryptographically/contextually validate that the `shop-domain` header corresponds to the tenant the request was actually delivered for (e.g., cross-check against a known/registered shop and webhook id via the Admin API, or verify webhook uniqueness/replay via `webhook_id` tracking) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a topic they've registered (e.g. `orders/create`), receiving a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret `S`).
2. Attacker resends `POST /webhook` with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in [5](#0-4) 
returns `true` (only body `B` is checked).
4. `Registry.process` in [6](#0-5) 
dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to act as if the event originated from the victim's tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

        end
