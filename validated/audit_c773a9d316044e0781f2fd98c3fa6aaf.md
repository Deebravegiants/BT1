### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook verification only HMACs the raw request body, but the tenant-identifying metadata (`shop`, `topic`, `webhook_id`, `api_version`) that the host application relies on to route and attribute the webhook is taken from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `HmacValidator.validate_signature` computes/compares the HMAC over exactly that signable string [4](#0-3) . Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the body or to each other [1](#0-0) .

`Registry.process` validates only the body HMAC, then dispatches to the handler using `request.shop` and `request.topic` taken straight from those unsigned headers [3](#0-2) , constructing a `WebhookMetadata` whose `shop` field carries the (unsigned) header value into the host application's business logic [5](#0-4) .

This is exactly the class of bug the report hints at: a value that is *acted on* (`shop`, used by the app to attribute/persist the webhook to a tenant) is not covered by the HMAC that is actually verified (only the body bytes are). The equality that should hold — "shop whose secret produced this HMAC" == "shop the app attributes this webhook to" — does not, because the HMAC computation is entirely independent of the `shop`/`topic` headers.

### Impact Explanation
Since the app's `api_secret_key` is shared across every shop that installs the app, any merchant/attacker who has installed the app can receive a legitimate webhook for their own store (valid body + valid HMAC, computed by Shopify with the shared secret). They can then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and the host application receives a `WebhookMetadata` claiming to originate from the victim shop with attacker-controlled body content. Depending on how the host app trusts `data.shop` (e.g. to load/update per-tenant state, dispatch GDPR "customers/redact" logic, or select which merchant's session/token to act on), this enables cross-tenant data confusion.

### Likelihood Explanation
The webhook endpoint is by design internet-reachable and unauthenticated beyond the HMAC check, and the only prerequisite is that the attacker be a genuine (even trial) installer of the app, so they can harvest a valid (body, HMAC) pair from their own shop's webhook traffic. No access to `client_secret`, access tokens, or the victim's credentials is required.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed content used by `HmacValidator`, or otherwise have `Request#to_signable_string` include them so that the signature verifies the specific shop/topic combination rather than the body alone. At minimum, downstream consumers of `WebhookMetadata#shop` should be documented as receiving an unauthenticated value.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate webhook, e.g. `POST /webhooks` with body `{"id": 123}` and header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical body and HMAC header to the same endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body bytes [6](#0-5) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: {...}, ...)` [7](#0-6) , and any app logic keyed on `data.shop` operates as if this attacker-controlled payload genuinely originated from `victim.myshopify.com`.
