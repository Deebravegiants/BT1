Both `HyperFungibleToken` and `WrappedHyperFungibleToken` (and their upgradeable variants) confirm the same root cause: they are `Ownable`, expose `pause()`/`unpause()` as `onlyOwner`, and `send`, `onAccept`, and `onPostRequestTimeout` are all gated by `whenNotPaused`. Since `unpause()` has no alternative caller and `renounceOwnership()` (inherited from OZ `Ownable`) is unrestricted, a paused state becomes permanent and irreversible once ownership is renounced, freezing all in-flight and future cross-chain token transfers/refunds.

### Title
Renouncing ownership permanently freezes in-transit and future funds in `HyperFungibleToken`/`WrappedHyperFungibleToken` due to unrecoverable pause state - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`HyperFungibleToken` and `WrappedHyperFungibleToken` (and their upgradeable counterparts) inherit OpenZeppelin's `Ownable`, which exposes an unguarded `renounceOwnership()`. The `pause()`/`unpause()` functions are `onlyOwner`, and critically, the core message-handling functions `send`, `onAccept`, and `onPostRequestTimeout` are all gated with `whenNotPaused`. If ownership is ever renounced (accidentally, via a scripted deployment step, or through loss of the owner key) while the contract is paused, there is no address left capable of calling `unpause()`, permanently freezing all cross-chain sends, incoming mints/unlocks, and timeout refunds.

### Finding Description
`HyperFungibleToken` is declared as `contract HyperFungibleToken is ERC20, ERC165, HyperApp, Ownable, Pausable` [1](#0-0) , with `pause()`/`unpause()` restricted to `onlyOwner`: [2](#0-1) 

The three functions that move value across chains are all conditioned on the pause flag:
- `send()`, which burns tokens and dispatches the outgoing ISMP request, is `whenNotPaused` [3](#0-2) 
- `onAccept()`, which mints tokens on receipt of an incoming message, is `onlyHost whenNotPaused` [4](#0-3) 
- `onPostRequestTimeout()`, which re-mints (refunds) previously burned tokens after a timeout, is also `onlyHost whenNotPaused` [5](#0-4) 

Because `unpause()` is the only way to clear the `Pausable` state and it is restricted to `onlyOwner`, and `Ownable.renounceOwnership()` allows the owner to set the owner to `address(0)` with no restrictions or safeguards, once ownership is renounced while paused there is no account able to call `unpause()` ever again. This is not merely a loss of admin configurability (as in the referenced Footium report's `addChain`/`removeChain`/`configure`) — it directly and permanently blocks `onPostRequestTimeout`, meaning tokens already burned via `send()` for an in-flight transfer that later times out can never be refunded, and blocks `onAccept`, meaning any pending or future incoming transfer can never mint/deliver tokens to the recipient.

The exact same pattern exists in `WrappedHyperFungibleToken`, where the underlying ERC20/WETH is locked (not burned) on `send()` [6](#0-5)  and `onAccept`/`onPostRequestTimeout` are the only paths that unlock/refund it, both gated by `whenNotPaused` [7](#0-6) [8](#0-7) , and `pause()`/`unpause()` are `onlyOwner` with the same `Ownable` renunciation exposure [9](#0-8) . In this variant the funds are locked ERC20/native tokens held by the contract, so a permanent pause with no owner directly traps user-deposited collateral in the contract with no recovery function.

### Impact Explanation
This is a concrete, permanent freezing-of-funds bug reachable by any unprivileged token bridger who has an in-flight transfer at the moment the contract becomes paused-and-ownerless: their burned/locked tokens can never be refunded via timeout, and any recipient's incoming transfer can never be delivered via `onAccept`. Since these are cross-chain bridge applications meant to be deployed and configured once per chain, `renounceOwnership()` being callable at any time (e.g., mistakenly during a deployment/config script, matching the pattern already seen for `BandwidthManager.renounceOwnership()` in `evm/script/DeployHostUpdates.s.sol`) turns an otherwise-recoverable operational pause into an irreversible, contract-wide fund freeze.

### Likelihood Explanation
Likelihood is moderate: it requires the contract to be paused while ownership has been renounced (or the owner key is otherwise permanently lost) — a state achievable by a single owner-controlled transaction sequence (`pause()` then `renounceOwnership()`), with no code-level safeguard preventing it. Deployment scripts in this codebase already demonstrate a habit of calling `renounceOwnership()` post-deployment (see the commented `bandwidthManager.renounceOwnership()` call), showing this is an anticipated operational pattern that could be applied to these token contracts as well.

### Recommendation
Either remove/override `renounceOwnership()` to always revert (as is common practice for contracts whose `onlyOwner` functions are load-bearing for fund recovery), or decouple `unpause()` from `onlyOwner` by introducing a separate non-revocable guardian/timelock role, or ensure `onPostRequestTimeout` (refund path) is never blocked by the pause flag so that funds already in transit can always be recovered regardless of the paused/ownerless state.

### Proof of Concept
1. Owner deploys `HyperFungibleToken`, calls `configure()` and `addChain()` to set up cross-chain routes.
2. A user calls `send()`, burning tokens and dispatching an ISMP POST request to a destination chain.
3. Owner calls `pause()` (e.g., in response to some detected issue), then calls `renounceOwnership()` (inherited unrestricted from OZ `Ownable`), setting `owner()` to `address(0)`.
4. The destination chain's dispatch times out; the ISMP host attempts to call `onPostRequestTimeout()` to refund the user — this reverts because `whenNotPaused` fails and there is no address that can call `unpause()` to lift it. The user's burned tokens are permanently unrecoverable.
5. Similarly, any pending incoming request destined for `onAccept()` can never be minted/delivered while the contract remains permanently paused.
