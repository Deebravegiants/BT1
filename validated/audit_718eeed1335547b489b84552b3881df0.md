### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which HMACs only the raw request body. The `shop` value passed to the app's handler is read from the `X-Shopify-Shop-Domain` header and is never included in the signed material, so it can be freely substituted by anyone who can produce (or capture) one validly-signed webhook body for the shared app secret.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is a separate accessor that just reads the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside the signed string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it authenticates the body bytes, not the shop header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the request "did indeed come from Shopify" for this specific shop, then forwards the unauthenticated `request.shop` straight to the developer's handler: [4](#0-3) 

Because the webhook HMAC key (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app, the signature over a given body is identical no matter which shop it "belongs" to. Any shop that has installed the app can trigger a genuine event, capture the Shopify-issued `(body, HMAC)` pair for their own store, and replay that exact pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still succeeds because it never inspects the header, so `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: <victim-shop>, body: <attacker-controlled-but-signed body>, ...)`.

The gem's own documentation reinforces the false assumption that this flow authenticates the shop identity: it advertises that `Registry.process` "will verify the request did indeed come from Shopify" and describes `data.shop` as simply "The shop domain of the webhook," which the sample handler code uses directly (e.g., `shop_domain: data.shop`) without any caveat that it is unauthenticated. [5](#0-4) [6](#0-5) 

This breaks the identity binding: `shop verified by HMAC == shop acted upon by the handler`. In reality, `shop verified by HMAC` is undefined (HMAC verifies nothing about shop), while `shop acted upon` is taken from an attacker-controlled header.

### Impact Explanation
This is a cross-tenant data-attribution vulnerability inherent to the gem's own webhook-processing API: an app built strictly per this gem's documented usage will process an attacker-supplied `shop` value as if it were verified alongside the payload, letting one tenant (a merchant who installed the app) inject data, trigger job processing, or corrupt state that the host app associates with a different tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires being a legitimate, unprivileged installer of the target app (no access to `api_secret_key`, no TLS interception, no social engineering) — the attacker simply captures one of their own genuine webhook deliveries and replays it with a modified `Shop-Domain` header to the app's public webhook endpoint. This is fully reachable through the gem's documented `Registry.process`/`Request` API exactly as shown in `docs/usage/webhooks.md`, so it does not depend on the host app deviating from documented usage.

### Recommendation
Bind `shop` to the verified material, or verify it independently of the raw-body HMAC:
- Cross-check `request.shop` against the shop(s) with an active/registered subscription for that `webhook_id`/topic before invoking the handler, or
- Reject/flag webhooks whose header `shop` does not match a shop known to have installed the app for that specific webhook subscription id, or
- At minimum, update `docs/usage/webhooks.md` to explicitly state that `shop` is not covered by the HMAC and must be independently validated by the host application before being trusted for tenant-scoped operations.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify.
2. Attacker POSTs to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (changed)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as needed
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H`, since `to_signable_string` never includes the shop header. [7](#0-6) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, processing/storing it as if it legitimately originated from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
