## Title
Unprotected UniswapV2 fee-swap during `placeOrder` enables sandwich extraction — ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` swaps the user's native token into the protocol fee token via UniswapV2's `swapETHForExactTokens` whenever an order carries a non-zero `order.fees` and native token was sent. The swap has no slippage bound beyond the caller's own `msg.value`, no minimum-output guard, and no price-impact check tied to a trusted reference price. This mirrors the reported "no slippage protection for UniswapV2 swaps" bug class: the swap's cost is entirely dependent on the pool's current reserves at execution time, so an attacker who sandwiches the `placeOrder` transaction can inflate the WETH→feeToken price and extract the difference from the user as MEV, up to the full amount of native token the user attached.

### Finding Description
In `placeOrder`, when `order.fees > 0` and `msgValue > 0`: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = feeToken;
        uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
        msgValue -= amounts[0];
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```

`swapETHForExactTokens` fixes the output (`order.fees` fee-token units) and treats `msgValue` (the full amount of native token attached to the call) as the maximum allowable input. The actual `amountIn` charged is computed on-chain from the pool's live reserves at execution time — exactly the same root cause identified in the original report (`amount0In`/`amount1In` dependent on current pool balance with no independent slippage bound). Because the only ceiling is the caller's own `msg.value` rather than a price derived from a trusted/external reference (oracle, quoted-and-bounded amount, etc.), an attacker can sandwich the `placeOrder` transaction: front-run to skew the WETH/feeToken reserves so the required `amountIn` for `order.fees` rises close to `msgValue`, let the victim's swap execute at the inflated price, then back-run to restore the pool and capture the price-impact difference as profit. The exact same swap pattern (fixed output, `msgValue` as implicit slippage bound, no oracle/quote check) is duplicated in the Tron port of the contract. [2](#0-1) 

This differs from the intentionally slippage-protected paths elsewhere in the codebase — the predispatch swap calldata is fully user-authored (the user picks their own `amountOutMin`), and `SimplexPaymaster.swapAndDeposit` derives `amountOutMin` from a Chainlink oracle bound by `swapSlippageBps`: [3](#0-2) 

The fee-collection swap inside `placeOrder`, however, has no such user-chosen or oracle-derived bound; it relies solely on the ambient `msg.value` sent for other purposes (predispatch assets + fee).

### Impact Explanation
Any unprivileged user calling `placeOrder` with a native-token order that has `order.fees > 0` is exposed to sandwich-attack value extraction on the fee-collection swap. The attacker's profit is bounded by the price impact they can create within the victim's `msg.value` headroom, and is drawn directly from the order-placer's funds — a direct loss of user funds via unsound/unbounded swap execution, matching the High severity classification given to the original UniswapV2 slippage report.

### Likelihood Explanation
`placeOrder` is a fully permissionless, frequently-used entry point (every cross-chain or same-chain intent order goes through it), and native-token orders with a fee component are a normal/expected usage pattern per the documented fee table (`Fill fee (order.fees) | At order placement | User`). Sandwiching a public mempool transaction against a UniswapV2 pool is a well-established, low-cost MEV technique, so likelihood is high whenever the WETH/feeToken pool has exploitable liquidity depth relative to the order size. [4](#0-3) 

### Recommendation
Bound the fee-collection swap with a real slippage/price check instead of relying on `msg.value` as an implicit ceiling: derive `amountInMax` from a trusted price oracle (as `SimplexPaymaster.swapAndDeposit` already does) or expose a caller-supplied `maxFeeInNative`/slippage parameter on `Order`/`placeOrder` that is validated against a quote taken outside of the same transaction (e.g., TWAP or oracle), and revert if the pool price has moved beyond the tolerated bound. At minimum, document the lack of protection so integrators size `msg.value` tightly and are aware of the sandwich risk.

### Proof of Concept
1. User calls `placeOrder{value: msgValue}(order, graffiti)` where `order.fees > 0`, `order.predispatch` is empty/zero for native assets, and `msgValue` is the amount the user is willing to pay in native token to cover `order.fees` in `feeToken`.
2. Attacker observes the pending transaction in the mempool and front-runs it with a large WETH→feeToken swap on the same UniswapV2 pool used by `IDispatcher(hostAddr).uniswapV2Router()`, driving up the feeToken price in terms of WETH.
3. The victim's `placeOrder` transaction executes `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)`; because the pool is skewed, `amounts[0]` (ETH spent) rises much closer to `msgValue` than it would under normal market conditions, so the victim's refund (`msgValue -= amounts[0]`) shrinks correspondingly.
4. Attacker back-runs with a feeToken→WETH swap to restore the pool and realize the price-impact profit, extracted at the victim's expense — funds the victim would otherwise have gotten refunded via `_sendValue(msg.sender, msgValue)`. [5](#0-4)
