### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing tenant-identity spoofing via forged headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts unauthenticated HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) to build the `WebhookMetadata` that is handed to the host application's handler. The binding the code implicitly assumes — "HMAC-valid request" == "headers are from Shopify for this exact shop/topic" — does not hold, because the signable string never includes those headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

So the HMAC check only proves the *body bytes* were signed by Shopify with the app's secret at some point — it says nothing about which shop, topic, or webhook the signature was originally issued for. Yet `Registry.process` uses the unauthenticated `request.shop` and `request.topic` (parsed straight from headers) to dispatch and tag the event: [3](#0-2) 

and `Request#shop` / `Request#topic` are read directly from headers with no cross-check against the signed body: [4](#0-3) 

This exactly matches the analog class in scope: "a field acted on but not covered by the HMAC." The equality the code should enforce is `signed(shop, topic, body) == (shop_header, topic_header, body)`, but what is actually enforced is only `signed(body) == body`; `shop_header` and `topic_header` are free variables an attacker controls.

### Impact Explanation
An unprivileged internet user who has legitimate access to at least one real, HMAC-signed webhook payload (e.g., because they run their own shop/app installation and receive Shopify webhooks for it, or capture one via a public test endpoint) can replay that exact `raw_body` + valid `hmac-sha256` header to the victim app's webhook endpoint while substituting arbitrary `x-shopify-shop-domain` / `x-shopify-topic` / `x-shopify-webhook-id` header values. The HMAC check still passes because it only covers the body. The host application's handler then processes the replayed payload under a spoofed shop identity (`WebhookMetadata#shop`) and/or spoofed topic, causing cross-tenant data confusion in any app that keys its webhook processing/storage off `WebhookMetadata#shop` — e.g., writing another shop's order/customer payload into the wrong tenant's records, or triggering `shop/redact`-style mandatory-topic handling for a shop that never requested it. This lands squarely in the in-scope "cross-tenant access" (Critical) impact category, since it breaks the shop-identity binding using only internet-reachable, unauthenticated header manipulation plus a legitimately obtained signed body.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining one valid `(body, hmac)` pair only requires the attacker to be a legitimate merchant/developer of the target app (a normal, unprivileged capability — install the app on your own store and capture your own webhook), no `api_secret_key` or access token is needed, and the replay is a trivial HTTP POST with modified headers. It does not depend on the host application ignoring documented behavior — the gem itself never binds `shop`/`topic` into the signature, so any app relying on `Registry.process`/`WebhookMetadata` for tenant routing is exposed by design of this gem's verification logic.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them in `WebhookMetadata`. At minimum, document/enforce that `Registry.process` must reject webhooks whose header-derived `shop`/`topic` cannot be independently corroborated (e.g., against an app's expected shop list or a topic allow-list tied to the specific signature), rather than trusting raw headers alongside a body-only HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise legitimately triggers a webhook to their own controlled endpoint) and captures a real webhook request, e.g. topic `customers/create`, body `{"id":1,"email":"a@a.com"}`, with its valid `x-shopify-hmac-sha256` value computed by Shopify using the app's `api_secret_key`.
2. Attacker resends the identical body and `x-shopify-hmac-sha256` to the same app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only presence, not correctness, is checked): [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body`: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: "customers/create", shop: "victim-shop.myshopify.com", body: {...}, ...)`, causing the host app to associate attacker-controlled body data with `victim-shop.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
