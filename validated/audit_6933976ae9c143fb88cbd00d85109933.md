## Finding: Missing validation of `VestingSchedule` ordering in `LockupContract::new()`

### Title
Lockup contract fails to validate `VestingSchedule` timestamp ordering at initialization, allowing malformed schedules that cause reverts or premature full-vesting — (File: `lockup/src/lib.rs`)

### Summary
The Merit Circle report flagged that curve points were never validated to be monotonically increasing before being used in subtraction (`curve[n+1] - curve[n]`), causing `deposit()`/`extendLock()` to revert. The NEAR `lockup` contract has an analogous structure: `VestingSchedule` has three timestamps (`start_timestamp <= cliff_timestamp <= end_timestamp`) that downstream logic (`get_unvested_amount`) assumes are correctly ordered when doing `end_timestamp - block_timestamp` / `end_timestamp - start_timestamp` subtractions [1](#0-0) . The contract even defines a validation helper, `VestingSchedule::assert_valid()`, that checks exactly this ordering [2](#0-1) , but this method is **never invoked** anywhere in the production code path that actually sets the vesting schedule.

### Finding Description
`LockupContract::new()` accepts an optional `VestingScheduleOrHash`, and for the explicit (public) variant stores it directly into `vesting_information` without ever calling `assert_valid()`: [3](#0-2) 

A repo-wide search confirms `assert_valid` is only referenced inside its own definition in `lockup/src/types.rs` (and a duplicate copy in `lockup-factory/src/types.rs`) — it is dead code, never called from `new()`, `terminate_vesting()`, or anywhere else in `lockup/src/foundation.rs` [4](#0-3) .

Because of this, a `VestingSchedule` can be initialized with `cliff_timestamp > end_timestamp` or `start_timestamp > end_timestamp`, violating the ordering that `get_unvested_amount()` assumes: [5](#0-4) 

### Impact Explanation
Two concrete misbehaviors follow from an unordered schedule:
1. If `end_timestamp` is set earlier than the intended `cliff_timestamp`, then once `block_timestamp >= end_timestamp` the function returns `0` (fully vested) even though the cliff was never logically reached — this prematurely unlocks/over-credits vested tokens to the owner, an accounting divergence.
2. If `start_timestamp > end_timestamp`, the subtraction `end_timestamp.0 - vesting_schedule.start_timestamp.0` at getters.rs:143 underflows (both are `u64`), causing a panic. Since `get_unvested_amount` is relied upon by owner-facing balance/transfer/staking logic, this can make the affected balance calculations revert, effectively freezing the owner's ability to interact with locked funds during that period.

This mirrors the reported bug class: unchecked, non-monotonic schedule/curve points that downstream arithmetic assumes are ordered, leading to either underflow-driven reverts (freezing) or, here additionally, incorrect early unlock (accounting divergence).

### Likelihood Explanation
The vesting schedule is set once, at contract initialization time (`new()`), typically by the party creating the lockup (e.g., via `lockup-factory`) on behalf of a distinct beneficiary (`owner_account_id`). Because there is no on-chain enforcement of correct ordering, any accidental or deliberate misconfiguration by the deploying party — a normal, expected operational input, not a privileged/trusted-role bypass — will silently produce a contract whose vesting math is either exploitably lenient (early full vesting) or permanently broken (revert/freeze) for the actual (different) owner of the funds. This is analogous to why the Sherlock report was accepted despite the curve-setter also being an authorized caller: the missing guard turns an ordinary misconfiguration into a fund-safety issue for the account beneficiary.

### Recommendation
Call `vesting_schedule.assert_valid()` (which already correctly implements the required monotonic ordering checks) inside `LockupContract::new()` whenever an explicit `VestingScheduleOrHash::VestingSchedule` is provided, and equivalently validate the revealed schedule in `terminate_vesting()` / `assert_vesting()` before using it in `get_unvested_amount()`. The same check should also be applied wherever `lockup-factory` accepts vesting-schedule parameters before forwarding them to `new()`.

### Proof of Concept
1. Deploy a `LockupContract` via `new()` with `vesting_schedule = VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T0, cliff_timestamp: T0+100, end_timestamp: T0+50 })` (i.e., `end_timestamp < cliff_timestamp`, violating monotonicity). No assertion fires because `assert_valid()` is never called.
2. Advance `block_timestamp` to `T0+60` (past `end_timestamp` but before intended `cliff_timestamp`). Calling `get_unvested_amount()` hits the `block_timestamp >= vesting_schedule.end_timestamp.0` branch at getters.rs:135-137 and returns `0`, meaning all tokens are reported as vested even though the cliff (T0+100) was never reached — an unintended full early release of otherwise-locked/unvested tokens.
3. Alternatively, construct `start_timestamp > end_timestamp`; any `block_timestamp` value strictly between `cliff_timestamp` and `end_timestamp` triggers the underflow at `getters.rs:143`, panicking the view call and any owner method relying on it.

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }

impl VestingSchedule {
    pub fn assert_valid(&self) {
        assert!(
            self.start_timestamp.0 <= self.cliff_timestamp.0,
            "Cliff timestamp can't be earlier than vesting start timestamp"
        );
        assert!(
            self.cliff_timestamp.0 <= self.end_timestamp.0,
            "Cliff timestamp can't be later than vesting end timestamp"
        );
        assert!(
            self.start_timestamp.0 < self.end_timestamp.0,
            "The total vesting time should be positive"
        );
    }
}

    pub fn terminate_vesting(
        &mut self,
        vesting_schedule_with_salt: Option<VestingScheduleWithSalt>,
    ) {
        self.assert_called_by_foundation();
        let vesting_schedule = self.assert_vesting(vesting_schedule_with_salt);
        let unvested_amount = self.get_unvested_amount(vesting_schedule);
        assert!(unvested_amount.0 > 0, "The account is fully vested");

        env::log(
            format!(
                "Terminating vesting. The remaining unvested balance is {}",
                unvested_amount.0
            )
            .as_bytes(),
        );

        let deficit = unvested_amount
            .0
            .saturating_sub(self.get_account_balance().0);
        // If there is deficit of liquid balance and also there is a staking pool selected, then the
        // contract will try to withdraw everything from this staking pool to cover deficit.
        let status = if deficit > 0 && self.staking_information.is_some() {
            TerminationStatus::VestingTerminatedWithDeficit
        } else {
            TerminationStatus::ReadyToWithdraw
        };

        self.vesting_information = VestingInformation::Terminating(TerminationInformation {
            unvested_amount,
            status,
        });
    }
