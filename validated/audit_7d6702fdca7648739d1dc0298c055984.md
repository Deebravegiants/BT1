### Title
Order creator can pick a hostile ERC20 as an order input to permanently block escrow release via `IntentsBase._withdraw`, stealing solver-delivered outputs — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
This mirrors the Astaria M-21 pattern: a party who controls one leg of an atomic exchange (there, the private-vault owner receiving ERC777 repayment; here, the order creator who selects the order's input tokens) can make that token's transfer to the counterparty revert on demand. In Hyperbridge's cross-chain Intent Gateway, the escrow release/refund path (`_withdraw`) loops over all `order.inputs` tokens and calls `safeTransfer` on each; if any single token transfer reverts, the whole call reverts. Combined with `EvmHost.dispatchIncoming`'s failure handling (a failed `onAccept` just deletes the receipt "so it can be retried" rather than reverting the batch), a token the attacker fully controls can be made to revert forever, permanently blocking delivery of the `RedeemEscrow`/`RefundEscrow` message and freezing the escrow — after the honest solver has already, in good faith, delivered real output tokens on the destination chain.

### Finding Description
`IntentGatewayV2.placeOrder` lets the order creator specify arbitrary ERC20 addresses as `order.inputs` with no allowlist [1](#0-0) . For cross-chain orders, once a solver fills the order on the destination chain (delivering real output tokens to the order's `beneficiary`, which the order creator also controls) [2](#0-1) , a `RedeemEscrow` message is dispatched back to the source chain to release the escrowed input tokens to the solver.

On the source chain, `ExtrinsicIntents.onAccept` handles `RedeemEscrow`/`RefundEscrow` by calling `_withdraw`, which iterates every escrowed token for the commitment and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each in a single atomic loop: [3](#0-2) 

Because Solidity calls revert atomically, if the order creator chose one of the escrowed `order.inputs` tokens to be a contract they fully control (e.g., a custom ERC20 with a transfer hook/blacklist that they can toggle to always revert once the corresponding order is filled — the same "malicious owner-controlled callback" trick as an ERC777 hook), every call to `_withdraw` for that commitment will revert, regardless of who calls it or how many times.

Critically, `EvmHost.dispatchIncoming` treats a reverting `onAccept` as "retryable" rather than fatal — it deletes the request receipt and returns without reverting the relayer's batch: [4](#0-3) 

Since the attacker's token will revert on every retry attempt (it is fully within their control), the message can never be successfully delivered — the escrowed input tokens are permanently locked in the gateway, and the `RedeemEscrow`/`RefundEscrow` finalize step (`_filled[commitment] = beneficiary`) never completes.

The same `_withdraw` function is also reached from the same-chain fill path (`IntrinsicIntents._fillSameChain`) [5](#0-4)  and from `onGetResponse` during source-chain cancellation [6](#0-5) , so the same hostile-token trick blocks refunds too.

### Impact Explanation
For cross-chain orders this is a direct theft vector: the solver irreversibly delivers real output tokens to the attacker's beneficiary on the destination chain [7](#0-6) , but the attacker (as order creator, who picked the poisoned input token) ensures the compensating escrow release on the source chain can never finalize. The solver's payment is permanently frozen/unrecoverable, and the attacker keeps the solver's tokens for free. For same-chain fills and cancellations, the same mechanism causes permanent freezing of escrowed funds for all tokens bundled in that commitment (not just the poisoned one, since `_withdraw`'s loop is atomic), denying legitimate solvers/users their funds indefinitely.

### Likelihood Explanation
Any user can place an order with an arbitrary self-deployed ERC20 as one of the `order.inputs` — there's no token allowlist in `placeOrder`. A solver evaluating cross-chain orders for profitable fills may not always simulate the full round-trip release before filling (especially with multiple input tokens per order), and the malicious token can behave normally at fill-quote/simulation time and only start reverting after the destination-side fill has already been delivered (e.g., gated by an owner-controlled flag or a check on the caller/context). This requires no privileged access, only deploying an ordinary-looking ERC20 and creating an order.

### Recommendation
Do not let a single failing token block the release of the others: iterate and transfer each token independently and continue on a per-token failure (e.g., using low-level calls and recording residual claims instead of using `safeTransfer` inside a loop that reverts all-or-nothing), or offer a pull-based claim per token. Alternatively, restrict `order.inputs`/`order.output.assets` to an allowlist of vetted tokens, and/or require solvers to simulate the full atomic release path (not just the fill) before committing to a cross-chain fill.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer`/`transferFrom` always succeeds except when called from the specific `IntentGatewayV2` address for a specific commitment (e.g., toggled by an owner-controlled boolean or triggered after a specific block/condition the attacker controls).
2. Attacker calls `placeOrder` with `order.inputs = [EvilToken, ...]` and `order.output.beneficiary = attacker`, requesting real, valuable output tokens (e.g., USDC) on the destination chain [1](#0-0) .
3. A solver calls `fillOrder` on the destination chain and delivers USDC to the attacker's beneficiary address [8](#0-7) ; a `RedeemEscrow` message is dispatched toward the source chain.
4. Before the message is delivered, the attacker flips `EvilToken` to always revert on transfer.
5. When a relayer delivers the `RedeemEscrow` message, `ExtrinsicIntents.onAccept` → `_withdraw` reverts on `EvilToken.safeTransfer(...)` [9](#0-8) ; `EvmHost.dispatchIncoming` swallows the revert and deletes the receipt, marking it retryable [4](#0-3) .
6. Every subsequent retry hits the same permanently-reverting token, so the escrowed inputs (including any legitimate tokens bundled in the same order) are frozen forever while the attacker has already received the solver's USDC on the destination chain.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
