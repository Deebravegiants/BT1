### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the caller knows a valid HMAC over the JSON body [2](#0-1) . The `shop` attribute, however, is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2)  and is then propagated as the tenant identifier into `WebhookMetadata` that is handed to the app's webhook handler [4](#0-3) [5](#0-4) .

### Finding Description
The equality the gem is supposed to enforce is:

`shop attributed to the webhook == shop that produced the HMAC-signed bytes`

`Registry.process` only checks `Utils::HmacValidator.validate(request)` [6](#0-5) , which recomputes `HMAC(api_secret_key, request.to_signable_string)` and compares it to the `hmac` header via `OpenSSL.secure_compare` [2](#0-1) . `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers with no cryptographic binding to that HMAC [7](#0-6) .

Because the app's endpoint is a normal public HTTP endpoint, any unprivileged internet user can send it a POST request. If that user can obtain (or brute force at low cost, e.g. an empty/`"{}"` body, or a body whose HMAC they already know from one of their own legitimate test-store webhooks) a `(raw_body, hmac)` pair that validates against the app's `api_secret_key`, they can freely set the `shop-domain` header to any victim shop and the `hmac` check will still pass, since the header is not part of the signed bytes. `Registry.process` then dispatches to the app's handler with `shop: request.shop` set to the attacker-chosen value [8](#0-7) , i.e. the "before" state (attacker's own shop, whose body/HMAC pair was legitimately obtained) is swapped for an arbitrary "after" state (any victim shop) without breaking signature validation.

This is the direct structural analog of the Hats.uri report's underlying bug class: a value that is *used* to make a security-relevant decision (tenant/shop attribution) is not covered by the same integrity check (HMAC) that gates the rest of the payload — i.e. "a field acted on but not covered by the HMAC."

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` to determine which tenant's local records to look up, mutate, or delete (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, `customers/redact`) can be tricked into acting on a different merchant's tenant data because the gem hands the handler a shop value that was never authenticated. This is a cross-tenant data-integrity/access issue driven entirely by this gem's `Webhooks::Request`/`Registry` design, not by host-application misuse of a documented API — the gem's own public `process` contract is "HMAC valid ⇒ trust all fields on `request`," which is false for `shop`, `topic`, `api_version`, and `webhook_id`.

### Likelihood Explanation
Moderate-to-low. The attacker needs at least one `(raw_body, hmac)` pair that the target app's `api_secret_key` validates. This is trivially obtainable for any developer/attacker who has their own test/development store installed on the target app (a completely unprivileged action) — they simply capture a real webhook Shopify sends them, then replay it with a modified `shop-domain` header pointed at a victim shop. No access to `api_secret_key`, tokens, or the victim's credentials is required.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-covered material (or otherwise cryptographically bind them to the signed body), or explicitly document/enforce that the `shop` used for tenant dispatch must be independently corroborated (e.g. against an existing stored session for that shop) before being trusted, rather than passed through unauthenticated from the header directly into `WebhookMetadata`.

### Proof of Concept
```ruby
# Attacker legitimately owns a dev store and captures one real webhook delivery,
# e.g. body: "{}" with a valid HMAC computed by Shopify using the app's api_secret_key.
captured_body = "{}"
captured_hmac_b64 = "..." # from the legitimate x-shopify-hmac-sha256 header Shopify sent

# Attacker replays the same body+hmac but swaps the shop-domain header to a victim shop
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => captured_hmac_b64,   # still validates: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (only raw_body is checked, see request.rb:35-38)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)) is invoked,
#    causing the app to act as if the webhook came from the victim's shop.
``` [4](#0-3)
