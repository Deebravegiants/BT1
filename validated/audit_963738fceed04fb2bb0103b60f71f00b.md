### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Webhooks::Registry.process` validates only covers the raw request body. An attacker who owns a legitimate Shopify store can receive a genuine, correctly-signed webhook for their own shop and then replay that exact body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. The signature will still validate, and the host application's webhook handler will receive `WebhookMetadata` claiming the event belongs to the victim shop.

### Finding Description
The identity binding that should hold is: `bytes verified by HMAC == bytes the application trusts for tenant identity`. In `to_signable_string`, only `@raw_body` is signed [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled unauthenticated from headers [4](#0-3) , none of which participate in the HMAC computation performed by `Utils::HmacValidator.validate` [5](#0-4) .

`Registry.process` validates only that the HMAC matches the (headers-excluded) signable string, then immediately trusts `request.shop` as the identity forwarded to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [3](#0-2) . Because `shop` is not bound to the signature, `request.shop` can be set to any arbitrary value independent of which merchant/secret actually produced the signed body.

This differs from the OAuth callback flow, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters [6](#0-5) , correctly binding shop identity to the signature there. The webhook path lacks this binding.

### Impact Explanation
This breaks the tenant boundary: an unprivileged internet user who controls one shop (which anyone can create for free, or which could be a low-trust/dev store) can generate a validly-HMAC'd webhook body using their own store's genuine webhook delivery, then forge the `shop-domain` header to impersonate any other merchant when POSTing to the host application's webhook receiver endpoint. Since `Utils::HmacValidator.validate` only checks the raw body against the app's shared `client_secret`, and the shared secret is the same for every shop calling the same app, the signature stays valid regardless of which shop domain is claimed. If the host application uses `WebhookMetadata#shop` to select or scope the tenant record to update (a documented, expected use per the gem's design), the attacker can inject data attributed to, or trigger tenant-scoped side effects for, a shop they do not control — a cross-tenant access issue.

### Likelihood Explanation
An attacker needs only to install/create a Shopify app-connected store (something any internet user can do without special privileges) and let it receive one legitimate webhook, then replay the same signed HTTP request body with an altered `shop-domain` header to the target app's public webhook endpoint. No secrets, tokens, or elevated access are required beyond what an ordinary shop owner already has for webhooks addressed to their own store.

### Recommendation
Include the `shop` (and ideally `topic`/`api_version`) header values as part of the signable string used for HMAC verification of webhooks, or otherwise cryptographically bind the claimed shop identity to the signed payload before trusting `request.shop` in `Registry.process`. At minimum, document/require that host applications cross-check `request.shop` against an independently verified session/store record rather than trusting it outright — but the safer fix is inside the gem, in `Webhooks::Request#to_signable_string` and `Webhooks::Registry.process`.

### Proof of Concept
1. Attacker creates their own development store `attacker-shop.myshopify.com` and installs the target app, receiving a legitimate webhook `POST` with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the identical body `B` and header `H` to the app's webhook endpoint, but replaces the header `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `hmac` decodes to `H` and whose `to_signable_string` is still `B` [2](#0-1) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and finds it matches `H`, so validation passes [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , despite the payload never having originated from, nor been signed with knowledge of, `victim-shop.myshopify.com`.
