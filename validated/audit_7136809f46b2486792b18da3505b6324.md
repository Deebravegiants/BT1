Confirmed. The webhook `shop` identity is not covered by the HMAC signature, which validates only the raw body against the app's shared secret.

### Title
Webhook shop-domain identity not bound to HMAC allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` verifies that HMAC against the app's single, app-wide `api_secret_key`. The `shop` (tenant identity), taken unauthenticated from the `X-Shopify-Shop-Domain` header, is never part of the signed bytes, so a webhook payload's origin shop can be swapped without invalidating the HMAC.

### Finding Description
`Registry.process` performs exactly one authenticity check: [1](#0-0) 

```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the caller-supplied `hmac` field: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body, and `shop` is read directly from an attacker-controllable header with no cryptographic tie to the signature: [3](#0-2) 

Because the `api_secret_key` used to sign webhooks is a single per-app secret shared across every shop that installs the app (it is not shop-specific), the HMAC over a given raw body is identical no matter which shop it was originally delivered for. This breaks the intended identity binding:

`HMAC-verified-shop == acting-shop`

In reality the equality only holds for `HMAC-verified-bytes == raw_body`; the `shop` value that the handler acts on (`request.shop` / `WebhookMetadata#shop`) is completely outside the signed data.

### Impact Explanation
Any entity that can obtain one genuinely Shopify-signed `(raw_body, hmac)` pair for the app — trivially available to any merchant who installs the app on their own store and triggers a webhook event — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it never inspected `shop`, and the handler will process the (attacker-chosen, replayed) payload as if it originated from the victim tenant. For mandatory compliance topics such as `shop/redact`, `customers/redact`, `customers/data_request`, or normal topics like `app/uninstalled`, this lets an unprivileged app installer force the host application to execute cross-tenant side effects (e.g. data deletion, access revocation, order/customer state changes) against a shop the attacker does not control — a cross-tenant access/integrity violation.

### Likelihood Explanation
High. Getting one valid signed webhook only requires installing the (often public/free) app once and triggering any webhook-emitting action — no privileged credentials, `client_secret`, or access token needed. The `shop` header is then trivially edited on replay since it is never covered by the signature.

### Recommendation
Bind the shop identity to the verified request: either include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed payload comparison the gem performs (e.g., signing/verifying `shop-domain + raw_body`), or require callers/handlers to cross-check `request.shop` against an independently known, previously-provisioned shop record before trusting it, rather than treating "HMAC valid" as proof that "shop is authentic."

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed with the app's shared secret.
2. Send a new HTTP request to the app's webhook endpoint with the identical body `B` and header `H`, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `B`.
4. The registered handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host app to act on the victim tenant using attacker-supplied data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)

            secret,
            signable_string,
          )
        end
