This confirms the analog clearly. For OAuth's `AuthQuery`, the `shop`, `code`, `host`, `state`, `timestamp` fields are all included in `to_signable_string` and thus covered by the HMAC [1](#0-0) . By contrast, for the webhook `Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and are not included in the signed content [2](#0-1) . `Registry.process` validates only that HMAC, then dispatches the handler with `shop: request.shop` taken straight from the unauthenticated header [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively over that body [4](#0-3) [5](#0-4) . However, `Registry.process` uses `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all read from the `x-shopify-*` HTTP headers — to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . None of these header-derived fields are bound by the HMAC signature, so the "authenticated shop" the handler is told about does not equal the shop whose secret actually produced the signature.

### Finding Description
This mirrors the report's bug class: a field that is *acted on* (the `shop` used to attribute/process webhook data) is not *covered by the cryptographic binding* (the HMAC), producing an equality break: `shop_used_by_handler != shop_that_signed_the_payload`.

Concretely:
- `Request#hmac` decodes the `x-shopify-hmac-sha256` header [6](#0-5) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read straight from headers with no cross-check against the signed body [7](#0-6) .
- `Request#to_signable_string` is only `@raw_body` [4](#0-3) .
- `HmacValidator.validate_signature` computes/compares the HMAC solely against `verifiable_query.to_signable_string`, i.e., the body [5](#0-4) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` returns true, then immediately trusts `request.shop`/`request.topic` to build `WebhookMetadata` for the handler [3](#0-2) .

Compare this with `Auth::Oauth::AuthQuery`, where `shop` is explicitly included inside `to_signable_string` and is therefore cryptographically bound to the HMAC [1](#0-0) . The webhook path lacks this equivalent binding.

Because a merchant/attacker who operates their own shop legitimately receives genuinely-signed webhooks from Shopify for their own store (body + valid HMAC computed with the app's `client_secret`, which the attacker never needs to know), they can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different, victim shop. The HMAC check still passes because it never inspected the header, and the host application — which relies on `WebhookMetadata#shop` (or `#topic`) as the authenticated tenant identity — will process, store, or act on the payload under the wrong shop's identity.

### Impact Explanation
This breaks the tenant boundary: an unprivileged party with access to genuinely-signed webhook traffic for their own shop can spoof the `shop`/`topic` identity attached to that payload, causing cross-tenant data processing. This matches the Critical category "cross-tenant access" since the shop identity that the application acts upon is not the shop that actually produced the signed payload.

### Likelihood Explanation
Any developer/merchant with a Shopify Partner account can install the app on their own store to legitimately receive real signed webhooks, then replay the body with a modified `shop-domain`/`topic` header to the app's public webhook endpoint. No access to `api_secret_key` or another tenant's credentials is required — only the ability to intercept/replay their own already-valid webhook request, and knowledge that the header is unauthenticated.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the signed content verified by `HmacValidator`, or otherwise validate that the shop domain in the header matches an expected/pinned value tied to the session/topic the webhook is registered for, similar to how `AuthQuery#to_signable_string` incorporates `shop` into what is HMAC-verified.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g., `orders/create`) so Shopify sends a request with a correct `x-shopify-hmac-sha256` for the JSON body.
2. Capture the raw body and the `x-shopify-hmac-sha256` value.
3. Resend the same raw body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
4. `HmacValidator.validate` returns `true` because it only checks the body [8](#0-7) ; `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` [3](#0-2) , causing the app to process attacker-supplied data as if it originated from the victim shop.
