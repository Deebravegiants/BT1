### Title
Venue-priced fills trust an unguarded, single-block Uniswap V4 spot price, letting an order-placer flash-manipulate the pool to drain solver funds - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
For "curveless" trading pairs configured with `[vault.uniswapV4]` positions instead of static bid/ask curves, the Simplex filler prices the exotic token directly off the target Uniswap V4 pool's current tick (`sqrtPriceX96` mid), with no TWAP and no execution-cost/size term. `checkPriceGuard` is the *only* defense, and it is entirely optional per-chain configuration (`referencePrice`/`maxDeviationBps`) that the operator may leave unset ("unguarded"). This is the same bug class as the reported IchiLpOracle issue: a price derived from a single AMM's instantaneous reserve/tick composition, which is trivially moved within one transaction via a flashloan, then used to value an asset for a downstream financial decision.

### Finding Description
`resolveLegRates` prices any curveless pair whose `token0` is a USD stablecoin by calling `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which returns `sdkPool.token0Price`/`token1Price` computed straight from the pool's live `sqrtPriceX96`, as documented: "`computeDirectPoolPriceUsd` returns the raw pool mid derived from `sqrtPriceX96` ... there is no size or impact term ... `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost." [3](#0-2) [4](#0-3) 

Crucially, the guard is optional and per-chain: `referencePrice`/`maxDeviationBps` must both be set together, or "neither" is required, leaving the chain "unguarded" by design. [5](#0-4) [6](#0-5) 

An unprivileged user placing an order via `placeOrder`/`fillOrder` on `IntentGatewayV2` fully controls when and how the destination-chain fill happens (the solver reacts to the `OrderPlaced` event and prices at fill time). Because the on-chain gateway itself performs no price validation — `_fillCrossChain`/`_fillSameChain` simply requires `solverAmount >= totalRequired` from whatever the solver signs — nothing on-chain prevents a solver from being tricked by an off-chain price read that was manipulated moments before. [7](#0-6) [8](#0-7) 

An attacker can: (1) flashloan into the configured Uniswap V4 pool to skew `sqrtPriceX96` far from fair value in the direction that makes the exotic token look cheap in USD terms, (2) within the same block/transaction sequence place (or already have queued) an order sized so that the solver's `resolveLegRates`/`sizeOrder` reads the manipulated mid before it reverts, and (3) collect an output amount far above fair value, extracting solver funds — exactly the Warp-Finance-style single-block reserve manipulation the referenced report describes, just applied to the venue-pricing path instead of an LP-token oracle. On any chain where the operator has not (or cannot practically) configure `referencePrice`/`maxDeviationBps` tightly enough, or where the position's pool is thin enough that even a guarded band can be straddled by a flashloan, the fill still executes at the manipulated rate.

### Impact Explanation
A successful manipulation directly drains solver-held funds at a favorable, briefly-manipulated rate — a concrete theft of funds from the party funding IntentGateway fills, analogous to the bad debt caused by the IchiLpOracle-style manipulation in the reference report. Because `side`/one-sided venue pricing and no bid/ask spread mean the manipulated single price is used for both sizing (`referenceRate`, feeding confirmation-depth sizing) and the actual payout (`resolveLegRates`), the same manipulated read compounds through the whole fill path.

### Likelihood Explanation
Medium-High: this requires (a) a venue-priced (curveless) pair configured with Uniswap V4 positions, and (b) either no `referencePrice`/`maxDeviationBps` guard configured for that chain, or a guard band wide enough / a pool thin enough that a flashloan can move price within the allowed deviation. Both configurations are explicitly documented as supported and are not enforced as mandatory by the filler-config validator, so any operator relying purely on pool-based pricing without a guard (or with a loose one) is exposed, and the attack requires only a single flashloan-funded transaction plus an order placement — both fully reachable by an unprivileged actor.

### Recommendation
- Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory whenever `[vault.uniswapV4]` pool-based pricing is used with no static curves, rather than optional.
- Replace or supplement the raw `sqrtPriceX96` spot read with a TWAP (e.g., Uniswap V4's built-in oracle observations) so a single-block manipulation cannot move the price used for fills.
- Add an execution-size/impact term so the quoted rate reflects the cost of actually sourcing liquidity from the pool, closing the gap the flow docs note ("A venue-priced pair that has to swap through its own pool to source inventory pays a fee tier it never quoted against").

### Proof of Concept
1. Operator configures a curveless USDC/EXOTIC pair priced from a Uniswap V4 pool with no `referencePrice`/`maxDeviationBps` guard (a fully valid, documented configuration).
2. Attacker flashloans a large amount of EXOTIC or USDC into that pool, shifting `sqrtPriceX96` so `computeDirectPoolPriceUsd` returns a USD price for EXOTIC far below fair value.
3. In the same block (or with a queued fill ready to execute), the attacker (as order user) has the solver fill a large EXOTIC→USDC or USDC→EXOTIC order; `resolveLegRates`/`sizeOrder`/`computeLegPolicyOutput` all price off the manipulated mid via `venueUsdPrice`, so `fillOrder`'s on-chain check (`solverAmount >= totalRequired`) is satisfied by a solver-signed output computed from the bad price.
4. Attacker reverses the flashloan swap, restoring the pool, and pockets the difference at the solver's expense.

			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {

					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}

	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.
