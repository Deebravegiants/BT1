### Title
Malicious/paused escrow token can permanently DoS `IntentsBase._withdraw`, freezing all other escrowed funds for an order - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` releases every escrowed token of an order in a single `for` loop, using `IERC20.safeTransfer` for each `body.tokens[i]` entry [1](#0-0) . This is the same bug class as the reported `MultiRewards.getRewardForUser` issue: a single token in the loop that reverts or is externally paused causes the *entire* transfer loop to revert, blocking release of every other (well-behaved) token and the escrowed transaction fees for that order, since `_withdraw` is invoked atomically from the cross-chain `RedeemEscrow`/`RefundEscrow` message-handling path.

### Finding Description
`_withdraw` iterates `body.tokens`, decrements `_orders[commitment][token]`, and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each token in the order's input/output set [2](#0-1) . `safeTransfer` reverts the whole transaction if the underlying token reverts (e.g., a paused, blacklisting, or malicious ERC-20), or if it consumes excessive gas / performs a return-bomb, causing the surrounding call to run out of gas.

Because `_withdraw` is called from the message-driven `RedeemEscrow`/`RefundEscrow` handling in `ExtrinsicIntents` (reached via a relayed Hyperbridge `PostRequest` delivered through `onAccept`), any user who places a multi-token order with one legitimate token and one token that later becomes non-transferable (paused by its issuer, blacklists the gateway or beneficiary, or is deliberately malicious) makes the entire withdrawal atomic-fail. Since the escrow accounting (`_orders[commitment][token] -= amount`) and the transfer happen in the same loop iteration, there is no partial-success path: the whole call — and thus the release of the *other* legitimate tokens and the transaction fee (`TRANSACTION_FEES`) — reverts every time it's retried, because retries hit the exact same failing token again.

Unlike a purely "malicious token added by governance" scenario, this path is reachable by an ordinary, unprivileged order-placer: any address calling the intents' `placeOrder`/order-fill flow can include any arbitrary ERC-20 as one of the order's input/output tokens (subject to normal token acceptance at deposit time, which does not guarantee the token stays transferable at withdrawal/redemption time). A token that is transferable at order-placement time but becomes paused, blacklists the contract, or is rugged before the cross-chain redeem message is delivered will permanently brick that order's escrow release.

### Impact Explanation
High. All escrowed value for the affected order — including any other, healthy tokens and the escrowed protocol/relayer fee (`TRANSACTION_FEES`) bundled in the same `WithdrawalRequest` — becomes permanently unretrievable, since `_withdraw` has no per-token skip/failure isolation and both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) share this code path [3](#0-2) . This is a permanent freezing of funds, not merely a delay, because retries execute the identical failing transfer.

### Likelihood Explanation
Medium. It does not require a privileged/malicious governance actor — any user/solver constructing a multi-token order can include a token that is later paused or turns malicious (rug/blacklist) before the settlement message executes, which is a realistic and unprivileged trigger path, matching the report's underlying bug class (an unconditional loop over external token transfers with no failure isolation) but with a stronger reachability profile than the whitelisted-reward-token case in the original report.

### Recommendation
- Isolate per-token transfer failures in `_withdraw` (e.g., low-level `call` with a bounded gas stipend and continue-on-failure, similar to the fix adopted in PR 401 referenced in the external report) so one bad token cannot block release of the others.
- Track and allow retry/claim of individual failed token legs separately (e.g., a `pendingWithdrawal[commitment][token]` that can be swept later) rather than reverting the whole batch.
- Consider using a return-bomb-safe call wrapper (e.g., `ExcessivelySafeCall`) for the token transfer.

### Proof of Concept
1. Attacker/user places a cross-chain order whose `inputs`/`outputs` include token A (well-behaved) and token B (an ERC-20 the attacker controls, or any real token they anticipate will later pause transfers/blacklist the gateway).
2. Order is filled/escrowed normally; `_orders[commitment][A]` and `_orders[commitment][B]` are both credited.
3. Before the cross-chain redeem/refund message settles, token B's contract is paused, or the attacker's token is configured to revert on `transfer` to the beneficiary/gateway (or performs a gas-griefing return-bomb).
4. The relayed `RedeemEscrow`/`RefundEscrow` request calls `_withdraw`, which iterates `body.tokens`; the call to `IERC20(B).safeTransfer(...)` reverts.
5. The entire `_withdraw` call reverts — token A's transfer and the escrowed `TRANSACTION_FEES` payout, which would otherwise have succeeded, never execute. Because `_orders` state was not decremented (revert rolls back state), every future retry re-hits the same reverting token B transfer, permanently freezing token A and the fees along with token B.

    /**
     * @dev Releases escrowed tokens to a beneficiary. Iterates over the withdrawal request's
     * token list, decrements the escrow balance for each, and transfers tokens out.
     *
     * When `finalize` is true, the order is marked as filled in the `_filled` mapping,
     * any accumulated transaction fees (in the protocol fee token) are forwarded to the
     * beneficiary, and the appropriate event (EscrowReleased or EscrowRefunded) is emitted.
     *
     * When `finalize` is false (partial fills), only the proportional token amounts are
     * released without finalizing the order.
     *
     * @param body The withdrawal request containing the commitment, token amounts, and beneficiary.
     * @param isRefund If true, emits EscrowRefunded instead of EscrowReleased on finalization.
     * @param finalize If true, marks the order as complete and releases accumulated fees.
     */
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
