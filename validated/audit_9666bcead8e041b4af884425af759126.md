### Title
Unspent input tokens left unaccounted after LI.FI/router swap allow value to be stranded and later drained by any allowed caller - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap()` and `LifiExternalAction.callRouter()` never verify that the router actually consumed the full `inputAmount` that was debited from the shielded pool. Only the *output*-token balance delta is measured and returned to the user; the input token's balance is never re-checked after the router call. This mirrors the reported Lombard bug class: no validation that the "unspent" portion of a moved asset is accounted for and returned as change.

### Finding Description
`ExternalActionSwap.swap()` computes `inputAmount = uint256(-deltaAmounts[0])` [1](#0-0) , which corresponds to the amount that was already transferred out of `Hinkal` into this contract by `_externalTransact` before `runAction` is invoked [2](#0-1) . It then calls `callRouter(...)`, whose only bookkeeping is the *output* token balance before/after the router call:

```
uint256 balanceBefore = getERC20OrETHBalance(outputToken);
...
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
``` [3](#0-2) 

There is no corresponding check that the *input* token balance of `ExternalActionSwap`/`LifiExternalAction` dropped by `inputAmount`. The router is invoked with `externalActionMetadata` (opaque calldata) via `approveUnlimited(inputToken, router); router.call(externalActionMetadata)` [4](#0-3) , and the amount the router actually pulls is determined entirely by the calldata, not by `inputAmount`. If the router consumes less than `inputAmount` (e.g., because the encoded swap amount in `externalActionMetadata` is smaller than the amount transferred in), the leftover input tokens simply remain as an ERC20 balance sitting in the `ExternalActionSwap`/`LifiExternalAction` contract, with an already-standing unlimited approval to the router.

Back in `Hinkal.transact()`, the balance-equation check only validates the Hinkal contract's own balance delta against `amountChanges[i]` and the returned `utxoSet` amounts [5](#0-4) . Because the full `inputAmount` was transferred out of Hinkal in `_externalTransact` regardless of how much the router actually consumed, this check passes even when the swap only partially executes — the shielded pool correctly reflects "-inputAmount" nullified with no compensating UTXO for the leftover, and that leftover is not tracked or returned anywhere.

This breaks the same equality the report describes for Lombard's BTC change: *value removed from the accounted balance (nullified shielded input) must equal value re-issued as output/change*. Here, `inputAmount_spent_by_router + leftover != inputAmount_debited`, and `leftover` is silently dropped rather than validated or returned.

### Impact Explanation
Funds equal to the unswapped leftover become permanently stuck in the `ExternalActionSwap`/`LifiExternalAction` contract — not backed by any UTXO, not returned to the depositor's shielded balance, and not swept by protocol logic. Because the router already holds an unlimited approval over that contract's balance of `inputToken` [4](#0-3) , any subsequent caller of `runAction`/`swap` for the same `inputToken` can craft `externalActionMetadata` that instructs the router to pull an amount larger than their own declared/deposited `inputAmount`, sweeping the stranded balance from prior transactions and crediting the resulting output entirely to their own new UTXO via `transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal)` [6](#0-5) . This is unauthorized movement of value that was never accounted for in that later caller's own balance equation — value effectively minted for the attacker at the expense of whichever party's swap originally under-consumed. This qualifies as (a) temporary/permanent freezing of user funds while stranded, and (b) theft once a subsequent caller drains it via an unauthorized asset movement not backed by their own debited shielded input.

### Likelihood Explanation
Triggering the stranding condition requires the entity constructing `externalActionMetadata` (the user or relay building the LI.FI calldata alongside the proof/`amountChanges`) to submit calldata that swaps less than the declared `inputAmount` — this can happen accidentally (quote staleness, partial-fill router behavior) or be deliberately engineered by a malicious relay/user. Draining the stranded balance requires only that an attacker be an `isAllowedRecipient` caller of the swap action for the same input token, i.e., any user routing a swap of that token through the shared `LifiExternalAction`/`ExternalActionSwap` contract — no admin/relay privilege is needed for the drain step, only for possibly causing the initial stranding.

### Recommendation
After the router call, verify that `inputToken` balance decreased by exactly `inputAmount` (or explicitly compute the leftover and return it to the caller as change / additional UTXO / revert if leftover > 0), mirroring the Lombard fix of summing UTXO inputs/outputs to compute and return unspent value. Concretely: capture `inputToken` balance before/after the router call in `callRouter`, and require `balanceBefore - balanceAfter == inputAmount` (or route the leftover back into the shielded pool as an additional output UTXO for the same depositor) before proceeding.

### Proof of Concept
1. Attacker (or malicious relay) submits a `transact()` call routed through `LifiExternalAction` with `deltaAmountChanges[0] = -100` (100 units of `inputToken` nullified from the shielded pool and transferred to `LifiExternalAction`) [7](#0-6) .
2. `externalActionMetadata` is crafted so the LI.FI router call only actually pulls 1 unit of `inputToken` via the pre-existing unlimited allowance, swapping it for `outputToken`; `swappedAmount` measured is correct for that 1 unit [3](#0-2) ; Hinkal's balance equation still passes because 100 units were transferred out of Hinkal and none returned as UTXO for token 0 (only an outputToken UTXO is created) [5](#0-4) . 99 units of `inputToken` now sit in `LifiExternalAction`, unbacked by any UTXO.
3. A later `transact()` (potentially the same attacker, or anyone) routes another swap of `inputToken` through the same `LifiExternalAction`, declaring only a small `deltaAmountChanges[0]` but crafting `externalActionMetadata` that directs the router to pull the full current balance of `inputToken` from `LifiExternalAction` (99 + their own deposit), using the standing unlimited approval [4](#0-3) .
4. `swappedAmount` is measured purely by `outputToken` balance delta and is entirely credited to the attacker's new UTXO via `transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal)` [6](#0-5) , even though the attacker's own declared `deltaAmountChanges[0]` only accounted for a fraction of the tokens actually swapped — the stranded 99 units are absorbed into the attacker's shielded output without any corresponding debit from the attacker's own balance equation.

Note: I was unable to fully inspect `TransfererBase.approveUnlimited` (only its existence was located, not read) to confirm whether re-approval happens fresh each call or reuses/accumulates allowance; this doesn't change the core issue since the unlimited approval to the router already grants access to the contract's full token balance including any stranded leftovers, but I could not verify additional nuances (e.g., allowance reset logic) within the available iterations.
