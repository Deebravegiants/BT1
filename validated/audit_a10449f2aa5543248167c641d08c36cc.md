### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw webhook body [1](#0-0) , while the `shop` value used to attribute the webhook to a tenant is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) . `Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the HMAC, never the shop header [4](#0-3) . `Registry.process` then trusts this unauthenticated header value directly when building `WebhookMetadata` and dispatching to the host app's handler [2](#0-1) .

### Finding Description
The identity binding that should hold is:
`shop` value trusted by the handler (`WebhookMetadata#shop`) == `shop` value cryptographically bound to the HMAC-signed payload.

In this gem it does not hold. `hmac`, and by extension the value verified in `validate_signature`, is computed only from `@raw_body` [5](#0-4) . The `shop` accessor is a completely separate, unauthenticated header read (`shopify-shop-domain`) [3](#0-2) , and there is no code path anywhere in `Registry.process` or `HmacValidator` that ties this header's value into the HMAC computation or checks it against anything else [6](#0-5) . `WebhookMetadata.shop` (passed straight to the app-supplied `handler.handle`) is populated from this same unauthenticated header [7](#0-6) .

Since the app's `client_secret` (`api_secret_key`) used for signing is shared across every shop that has installed the app, any shop that installed the app can legitimately receive a genuine `(body, hmac)` pair from Shopify for its own store. That merchant can then resend the exact same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still pass (it never looks at the shop header), and `Registry.process` will dispatch the attacker-supplied body to the handler tagged with an arbitrary victim shop domain.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on `WebhookMetadata#shop` to enforce data isolation between merchants. A malicious merchant can forge webhook deliveries that appear to originate from a different, victim shop, causing the host application to write, process, or act on attacker-controlled data under another tenant's identity — a cross-tenant integrity violation. This matches the High-severity criterion of scope/binding-check bypass across a tenant boundary.

### Likelihood Explanation
Any unprivileged user of a Shopify store with the app installed can trigger this: they only need one legitimately-received webhook body+HMAC pair from their own store (no `api_secret_key` or other privileged material needed) and the ability to POST to the app's public webhook endpoint with a modified header. No interaction with Shopify's servers is required for the replay itself.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`) header values into the signable string used for HMAC verification, or independently authenticate/authorize the shop domain against the session/shop the webhook subscription was registered for, before constructing `WebhookMetadata` and dispatching to the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` using the app's shared secret), header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the same `B`/`H` to the app's webhook endpoint, replacing the header with `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Request#hmac` still decodes to `H`; `Request#shop` now returns `victim-shop.myshopify.com` [8](#0-7) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [9](#0-8) .
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [10](#0-9) , causing the host app to process attacker-controlled data under the victim's tenant identity.
