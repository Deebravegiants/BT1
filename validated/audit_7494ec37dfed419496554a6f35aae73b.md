## Finding: Webhook HMAC signature does not bind the shop domain, topic, or webhook id — allowing cross-tenant webhook spoofing

### Title
Webhook Signature Verification Does Not Bind `shop`/`topic` Headers — Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body against the app's `api_secret_key`. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never included in the signed payload, so they can be freely altered by anyone who can produce one genuinely-signed `(raw_body, hmac)` pair.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` checks nothing but that signable string against the computed HMAC: [2](#0-1) 

`Registry.process` gates entirely on that body-only HMAC check, then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all pulled directly from attacker-controllable headers — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The `shop`/`topic`/`webhook_id`/`api_version` accessors simply read the corresponding `x-shopify-*` (or `shopify-*`) header with no cross-check against the signed content: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is shared across all shops that install the app, any merchant who installs the app can legitimately receive a webhook delivery for their own store, obtain a valid `(raw_body, hmac)` pair, and then replay it to the app's webhook endpoint with the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers rewritten to claim the event belongs to a different (victim) shop or a different topic entirely. `Utils::HmacValidator.validate` will still pass because it only verifies the untouched body bytes, and `Registry.process` will happily dispatch the handler with forged `shop`/`topic` metadata.

This breaks the identity binding: `hmac-signed bytes == raw_body` but `data trusted by the handler == {shop, topic, webhook_id, api_version}`, none of which equal or are derived from the signed bytes.

### Impact Explanation
This is a cross-tenant boundary break (Critical): a party with access to any one tenant's legitimately-delivered webhook can impersonate webhook traffic "from" any other tenant/shop and any topic (e.g., relabeling an `orders/create` payload as `app/uninstalled` for a victim shop, or claiming attacker-supplied JSON originated from a specific victim `shop` domain). Any host application relying on `WebhookMetadata#shop`/`#topic` to authorize per-tenant side effects (updating the victim's stored data, triggering uninstall cleanup, etc.) can be manipulated into acting on behalf of a shop the attacker doesn't own.

### Likelihood Explanation
Any user able to install the app on a store (a normal, unprivileged capability for public/dev/trial installs) can capture one legitimate webhook delivery from their own store and immediately replay it with rewritten headers against the shared webhook endpoint — no access to `api_secret_key`, access tokens, or privileged accounts is required.

### Recommendation
Bind the identity-critical fields into the signed content, or otherwise independently verify them: e.g., verify the `shop` header against a registered/expected shop for the given topic/webhook subscription id (looked up server-side, not trusted from the header) before dispatching to handlers, and/or require the app to cross-check the `webhook_id`/`shop` pair against Shopify via API before trusting the payload's claimed origin. At minimum, document that `Request#shop`/`#topic` are unauthenticated and must not be used as an authorization boundary by the host application without an additional server-side lookup.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for topic `orders/create`.
2. Shopify delivers a webhook to the app's endpoint with a real `raw_body` and a genuinely computed `x-shopify-hmac-sha256` (signed with the app's shared `api_secret_key`).
3. Attacker captures this `(raw_body, hmac)` pair and replays it directly to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any registered topic)
4. `Utils::HmacValidator.validate` recomputes HMAC over the unchanged `raw_body` and it matches — validation succeeds (`lib/shopify_api/webhooks/registry.rb:190`).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host app to act as though the event genuinely originated from the victim shop.
