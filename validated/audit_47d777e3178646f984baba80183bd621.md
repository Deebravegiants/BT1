### Title
`transact()` skips the balance-equation check entirely when `erc20TokenAddresses.length == 0` (Emporium "Min" mode) - ([File: contracts/Hinkal.sol])

### Summary
This is the same access-control class as the BPool report: an unprivileged loop bound (`_tokens.length` / `circomData.erc20TokenAddresses.length`) can legitimately be zero, and every safety check inside that loop is silently skipped rather than rejected. In Hinkal, the balance-equation and slippage checks that guarantee "on-chain balance change == off-chain UTXO change + on-chain UTXO change" for every `transact()` call are executed inside a `for` loop over `circomData.erc20TokenAddresses.length`. The contract itself has a dedicated code path, `formInputEmporiumMin`, that is selected precisely when `erc20TokenAddresses.length == 0` for Emporium external actions, so a zero-length array is not an edge case but an intended, reachable branch.

### Finding Description
`Hinkal.transact()` computes `oldBalances`/`newBalances` and then loops: [1](#0-0) 

Inside this loop the contract enforces two invariants per token: the slippage bound and the core balance equation: [2](#0-1) 

It is also this loop, keyed by `circomData.erc20TokenAddresses[i]`, that populates `onChainCommitments[]` from the `utxoSet` returned by the external action: [3](#0-2) 

When `circomData.erc20TokenAddresses.length == 0`, this whole loop body never executes. `HinkalHelper.dimensionsCheck` does not reject `tokenNumber == 0` — it only requires that all the other arrays' lengths equal `tokenNumber`, which they trivially do when it's zero: [4](#0-3) 

Critically, `CircomDataBuilder.formInputForCircom` explicitly branches to a minimal public-input builder, `formInputEmporiumMin`, exactly when `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`: [5](#0-4) 

That minimal input only binds `emporiumMessage`, `timeStamp`, and `calldataHash` into the proof's public signals — it does not bind `rootHashHinkal`, `amountChanges`, `inputNullifiers`, `outCommitments`, or the stealth-address components, because in normal mode these are folded into the proof through `formInputNormal`/`getSignedMessageHash` (see `formBasicInput`, `contracts/CircomDataBuilder.sol:180-240`). So this mode exists specifically to let a `transact()` call proceed with `erc20TokenAddresses.length == 0` while still invoking an external action (`_externalTransact`, `contracts/Hinkal.sol:234-261`) that can call arbitrary registered `IExternalActionV2.runAction` logic (e.g., the Emporium/HinkalWallet action) and return a non-empty `utxoSet`.

Following the BPool analog exactly:
- The **outer join-equivalent** (the balance/slippage-check loop, `contracts/Hinkal.sol:97-147`) is bypassed entirely because it is bound to `erc20TokenAddresses.length`, not to anything that reflects the actual value moved by the external action.
- Any UTXOs in `utxoSet` returned by the external action are never validated against a real balance delta, and `onChainCommitments` is never populated with real commitments for those UTXOs (since population also happens inside the same skipped loop) — yet `insertCommitments()`/`insertNullifiers()` at the end of `transact()` still run unconditionally regardless of whether the equation was ever checked: [6](#0-5) 

This breaks the documented balance equation ("CHANGE IN BALANCE SHOULD EQUAL TO 1) change in off-chain utxos 2) change in on-chain utxos") for the entire class of calls that use the Emporium-min zero-token path, since that check simply never runs.

### Impact Explanation
This maps to the "Critical" bucket: it is a proof/verification-equation bypass that allows an unprivileged EOA to route a `transact()` call through an external action while skipping the on-chain enforcement that ties balance changes to nullifier/commitment changes. Depending on what the registered external action does when invoked with an empty `erc20TokenAddresses` array and attacker-supplied `deltaAmountChanges = []`, this can permit unauthorized asset movement or unbacked UTXO creation without the balance-equation and slippage guarantees the rest of the protocol relies on for every other code path.

### Likelihood Explanation
Reachable by any unprivileged caller: `transact()` has no access control beyond `nonReentrant`, and `dimensionsCheck` does not forbid `tokenNumber == 0`. The `formInputEmporiumMin` branch is explicit, first-class logic in `CircomDataBuilder.sol`, meaning this configuration is an intended, documented mode of operation, not an obscure edge case — increasing the likelihood that it is actually exercised in production via the Emporium external action.

### Recommendation
- Short term: require `dimensions.tokenNumber >= 1` (or explicitly reject `erc20TokenAddresses.length == 0`) unless the "Min" Emporium mode is proven not to bypass balance accounting — i.e., ensure the balance-equation/slippage loop and `onChainCommitments` population cannot be skipped whenever an external action can return a non-empty `utxoSet` or otherwise move value.
- Long term: decouple the balance-equation enforcement from `circomData.erc20TokenAddresses.length` so it is driven by the actual `utxoSet`/value moved by `runAction`, and add fuzz/property tests (e.g., analogous to Echidna/Manticore testing for `joinPool`/`exitPool`) asserting that `transact()` cannot succeed with `utxoSet.length > 0` while `erc20TokenAddresses.length == 0`.

### Proof of Concept
1. Attacker (any EOA) registers/uses an existing Emporium `externalActionId` (`HINKAL_EMPORIUM_ACTION_ID`) via `registerExternalAction` mapping already set by admin.
2. Attacker calls `Hinkal.transact()` with `dimensions.tokenNumber = 0` and `circomData.erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `inputNullifiers = []`, `outCommitments = []`, `encryptedOutputs = []`, and `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`.
3. `dimensionsCheck` passes trivially (all lengths are 0 == tokenNumber).
4. `performHinkalChecks` returns `formInputEmporiumMin(circomData)` — a proof can be generated that only needs to satisfy `emporiumMessage`, `timeStamp`, `calldataHash`, none of which constrain balances/nullifiers/commitments.
5. `_externalTransact` runs the Emporium action's `runAction(circomData, [])`, returning some `utxoSet`.
6. Back in `transact()`, the `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` loop (length 0) never executes, so neither the slippage/balance-equation `require`s nor the `onChainCommitments` population run.
7. `insertNullifiers`/`insertCommitments` still execute unconditionally at the end, so whatever state changes the external action performed are finalized without ever having been checked against the balance equation. [7](#0-6)

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
