### Title
`EvmHost.dispatch()` charges `_msgSender()` for the relayer fee instead of the documented `payer`, breaking payer-based fee accounting and fee refunds - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` / `dispatch(DispatchGet)` accept a `payer` field that the interface explicitly documents as the account responsible for paying fees ("If different from `msg.sender`, must have approved the Host contract"), but the implementation always pulls the fee token from `_msgSender()`, never from `post.payer`/`get.payer`. The `payer` value is only used afterwards to key `FeeMetadata.sender`, which controls where the relayer-fee refund is sent on timeout. This is the same class of bug as the referenced report: a designated "payer" address is documented/assumed to fund a payment, but the code silently substitutes `msg.sender` as the actual payer, while other logic (refunds) still keys off the documented `payer`.

### Finding Description
The `DispatchPost`/`DispatchGet` structs document the `payer` field as: [1](#0-0) [2](#0-1) 

i.e., callers may set `payer != msg.sender`, provided that `payer` has approved the Host to pull the fee.

However, `EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)` never touch `post.payer`/`get.payer` when collecting payment — they always call `safeTransferFrom(_msgSender(), ...)`: [3](#0-2) [4](#0-3) 

Note line 948 stores `FeeMetadata({sender: post.payer, fee: post.fee})` for the POST path — i.e., the metadata used for later refunds is keyed on the *documented* payer, while the *actual* debit happened against `_msgSender()`. Contrast this with the GET path at line 1001, which correctly stores `_msgSender()` as `sender` — showing the POST path is inconsistent even internally.

This stored `FeeMetadata.sender` is later used to route relayer-fee refunds on timeout: [5](#0-4) 

and to gate `fundRequest` top-ups: [6](#0-5) 

So the party that actually funds the fee (`_msgSender()`) and the party the protocol believes funded it / will be refunded (`post.payer`) can diverge completely, exactly mirroring the external report's root cause ("the protocol assumes the passed address pays, but `_msgSender()` always pays").

### Impact Explanation
- Any integrator or application that follows the documented `IDispatcher` contract literally — setting `payer` to an end-user address who has approved the Host directly, while the calling contract itself holds no fee-token balance/allowance — will have its `dispatch()` call revert (insufficient allowance/balance on `_msgSender()`), a **route unable to deliver messages** for that integration pattern.
- Where the call does not revert (the caller happens to hold funds), the actual fee is silently debited from `_msgSender()` while `FeeMetadata.sender` records an unrelated `payer`. On timeout, `dispatchTimeOut` refunds `meta.sender` (the documented payer), not the address that was actually charged — permanently misdirecting refunded relayer fees away from whoever paid them. This corrupts the fee-accounting invariant relied on by every downstream app built on top of `EvmHost`/`HyperApp`, since the whole point of the `payer` field is to make refunds/accounting correct for third-party fee sponsorship.
- Because `dispatch()` is a public, unprivileged entry point (`external payable`, gated only by `notFrozen`), any unprivileged caller can trigger this mismatch at will, for arbitrary `payer` values, on every outbound POST/GET request.

### Likelihood Explanation
High for any integration that relies on the documented `payer` semantics (sponsor pays on behalf of the app/user) instead of going through the `HyperApp.dispatchWithFeeToken` wrapper (which happens to work around the bug by pre-funding itself from `payer` before calling `dispatch`). Since `EvmHost.dispatch()` is public and reachable directly by any contract or EOA, exploitation requires no special privileges — only a call with a `payer` different from `msg.sender`.

### Recommendation
Make `EvmHost.dispatch(DispatchPost)`/`dispatch(DispatchGet)` pull the fee from `post.payer`/`get.payer` (falling back to `_msgSender()` when `payer == address(0)` or `payer == msg.sender`), consistent with the NatSpec. Ensure `FeeMetadata.sender` always matches whichever address the tokens were actually pulled from, so refunds in `dispatchTimeOut` and `dispatchIncoming` go to the party that truly funded the fee.

### Proof of Concept
1. Contract `A` (which holds fee-token balance/allowance to `EvmHost`) calls `EvmHost.dispatch(DispatchPost{..., payer: userX, fee: F})` where `userX` is an arbitrary address with no relation to `A`.
2. `EvmHost.dispatch` executes `feeToken().safeTransferFrom(A, host, F)` — `A` is charged, not `userX`.
3. `_requestCommitments[commitment] = FeeMetadata({sender: userX, fee: F})` is stored.
4. The request times out; `dispatchTimeOut` calls `feeToken().safeTransfer(userX, F)` — the fee `A` paid is sent to `userX`, an address that never funded anything and never approved `A`'s funds to be spent on its behalf.
5. Conversely, an integrator that assumes the documented behavior (setting `payer = userX` because `userX` approved the Host, while the integrator contract `A` itself holds zero fee-token balance) will have every `dispatch()` call revert with an ERC20 transfer failure, since `_msgSender()` (contract `A`) — not `userX` — is what gets debited.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});

    function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                amount, path, address(this), block.timestamp
            );
        } else {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
        }

        FeeMetadata memory metadata = _requestCommitments[commitment];
        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;

        emit RequestFunded({commitment: commitment, newFee: metadata.fee});
    }
