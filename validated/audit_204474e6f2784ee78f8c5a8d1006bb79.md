### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, but `Registry.process` uses the unauthenticated `shop-domain` header as the tenant identity passed to the app's webhook handler. This breaks the identity binding `hmac_verified_content == data_used_for_tenant_attribution`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` checks the received `hmac` header against `OpenSSL::HMAC.hexdigest` of that signable string using the app's secret [2](#0-1) . The `shop` accessor, however, reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed content [3](#0-2) .

`Registry.process` validates only the HMAC of the request and then hands `request.shop` straight to the handler as the trusted tenant identity, alongside the (HMAC-verified) body: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . The equality the gem implicitly asserts is:

`hmac_verified_bytes (raw_body) == tenant_binding_bytes (shop-domain header)`

but this equality does not hold — the header is never covered by the MAC, so the gem's own HMAC check gives no assurance about which shop the payload belongs to.

Because the HMAC only covers the JSON body, any `(body, hmac)` pair that is valid for one webhook delivery from the merchant's own shop (webhook bodies are not secret — they are delivered over plain HTTP POST to the app's public endpoint and can be captured by the shop owner who received them, or replayed by any party who intercepts them) remains a *cryptographically valid* pair regardless of which `shop-domain` header value accompanies it. An unprivileged caller who has captured one legitimate `(raw_body, hmac)` pair for their own installed shop can resend it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header (e.g. a victim's shop domain) and it will pass `Registry.process`'s only check, `HmacValidator.validate(request)` [5](#0-4) , since that check never looks at the shop header at all.

### Impact Explanation
Because host applications built on this gem receive `WebhookMetadata#shop` as an already-"verified" tenant identifier (the gem's own `Registry.process` gate is the thing that is supposed to establish trust before invoking the handler), a caller who controls the `shop-domain` header can cause the handler to process attacker-supplied or replayed body data under a victim shop's identity. Depending on how the host app persists or acts on webhook data keyed by `data.shop` (order/product/customer updates, uninstall/GDPR webhooks, etc.), this enables cross-tenant data confusion/injection — writing or triggering actions attributed to a shop the caller does not control, using only a body+HMAC pair the caller legitimately obtained for a different (their own) shop. This matches the "Critical – cross-tenant access" impact class, since the tenant boundary (`shop`) that the rest of the gem and typical host integrations treat as authenticated is not actually bound by the cryptographic check performed by `HmacValidator`.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must possess at least one valid `(raw_body, hmac)` pair, which requires having received a genuine webhook (e.g., from their own installed/legitimate shop) — this is realistic for any merchant who installs the app, since webhook deliveries are plaintext POSTs to a public endpoint. No possession of `api_secret_key`, access tokens, or other credentials is required; only header manipulation on replay. This is a design gap in `Webhooks::Request`/`Registry`, not a misuse of a documented safety contract by the host app, because the class's own `shop` field is exposed as a first-class, seemingly-trusted attribute right next to the HMAC-gated body.

### Recommendation
Bind the `shop-domain` header (and ideally `topic`/`webhook-id`) into the HMAC-signable content, or otherwise cryptographically tie the header values to the verified body (e.g., require the host app to separately confirm the shop against a known/installed shop list before trusting `WebhookMetadata#shop`). At minimum, document in `Webhooks::Request`/`Registry.process` that `shop`, `topic`, and `webhook_id` are **not** covered by the HMAC and must not be treated as authenticated tenant identifiers.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's secret).
2. Attacker (who owns/installed the app on `shop-a`) replays the exact same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `H` against `to_signable_string == B` and succeeds, because the shop header was never part of the signed content [5](#0-4) [1](#0-0) .
4. The handler receives `WebhookMetadata` with `shop: "shop-victim.myshopify.com"` and the body from `shop-a`, despite the HMAC never authenticating that association [6](#0-5) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
