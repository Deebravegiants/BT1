I investigated whether the Android binder use-after-free bug class (a resource freed/released while still referenced and later reused) has a reachable analog in Hyperbridge's message-dispatch and delivery paths. I did not find a conclusively provable, fully-reachable analog before exhausting my search budget — I'll lay out exactly what I found and what remains unverified.

**Relevant observation (not fully validated as exploitable):**

In `EvmHost.dispatchIncoming(GetResponse memory response, address relayer)`, the request's fee-escrow entry `_requestCommitments[commitment]` is read (and paid out) after a successful delivery, but it is **never deleted**: [1](#0-0) 

Compare this to `dispatchTimeOut(GetRequestTimeout, ...)`, which explicitly deletes `_requestCommitments[commitment]` *before* the external call as "replay protection", and only restores it if the callback fails: [2](#0-1) 

So after a GET request is successfully answered via `dispatchIncoming`, the `FeeMetadata` for that request (sender + fee) is left dangling in storage indefinitely — the state that models "this request is still pending/fundable" is not torn down when the request's lifecycle actually ends. `fundRequest` even documents that calling it post-delivery just "donates" funds rather than reverting, since it only checks `metadata.sender != address(0)`: [3](#0-2) 

**Why I can't confirm a concrete, reachable fund-theft/double-payment path:**

The only way this stale `_requestCommitments` entry becomes a real "use of a freed resource" bug (e.g., double payment: once to the relayer via `dispatchIncoming(GetResponse)`, and again via a later `dispatchTimeOut(GetRequestTimeout)` refunding the original sender) is if `HandlerV2` does **not** independently check `_responseReceipts[commitment]` before accepting a timeout proof and calling `EvmHost.dispatchTimeOut`. I located the relevant call sites in `evm/src/core/HandlerV2.sol` (references to `GetRequestTimeout`, `requestCommitments(...)`, and response-receipt checks) but ran out of tool iterations before I could read that function body to confirm whether such a check exists. Given that GET-timeout proofs are normally validated against destination-chain state independent of this host's local receipts, it's plausible (but unconfirmed) that this path is already gated elsewhere.

**Conclusion:** I have a real code observation (missing cleanup of `_requestCommitments` on successful `GetResponse` delivery, asymmetric with the cleanup done on timeout), but I cannot prove root cause with the exact file/function support the validation bar here requires, because I could not verify `HandlerV2`'s timeout-acceptance logic in the time available. I'm not going to assert a Critical/High finding I can't back with a confirmed reachable trigger — that would be fabricating an unverified claim. If you want this pursued further, the next concrete step is to read `evm/src/core/HandlerV2.sol`'s GET-timeout handling function in full to check whether it independently guards against timing out an already-responded-to request.

```text
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

```text
    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
