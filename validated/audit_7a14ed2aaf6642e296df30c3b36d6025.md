Audit Report

## Title
Unprivileged Gateway callers can collide legacy `MessageID`s to overwrite and silently drop another user's in-flight callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` stores each request's completion callback in `h.savedCallbacks`, a map keyed only by the caller-controlled `MessageID`, with no uniqueness/ownership check before the write. Since `MessageID` is copied directly from the untrusted JSON-RPC request `ID` field (no server-side dedup, no allowlist enforced at this stage — the code even has a `// TODO: apply allowlist and rate-limiting here` comment), any client able to reach this DON's legacy gateway endpoint can submit a request with the same `MessageID` as a still-pending legitimate request, silently overwriting the victim's saved callback and causing either response misdelivery to the attacker or a forced timeout for the victim.

## Finding Description
The exploit path is confirmed in the code:

1. `gateway.ProcessRequest` decodes the request and, for legacy DON messages, calls `h.HandleLegacyUserMessage(ctx, msg, callback)`, then blocks on `callback.Wait(ctx)`. [1](#0-0) 

2. `common.ValidatedMessageFromReq` sets `m.Body.MessageID = req.ID` directly from the caller-supplied JSON-RPC request ID with no uniqueness enforcement — `Message.Validate()` only checks length/format, not collision. [2](#0-1) 

3. `HandleLegacyUserMessage` stores the callback unconditionally, with no existence check on the key, unlike `httpTriggerHandler.setupCallback` in the v2 handler which explicitly rejects a duplicate/in-flight `requestID`: [3](#0-2) 
There is also an explicit acknowledgment in the same function that allowlisting is not yet applied at this stage: [4](#0-3) 

4. When any DON node later responds for that `MessageID`, `handleWebAPITriggerMessage` looks up and deletes whatever callback currently occupies that slot and delivers the response to it — "first response wins" regardless of which caller originally owns that slot: [5](#0-4) 

The only sender-related check present, `msg.Body.Sender != nodeAddr` in `HandleNodeMessage`, validates that the *node* responding matches the addressed node — it does nothing to bind the `savedCallbacks` entry to the original requester's identity, so it does not prevent this overwrite. [6](#0-5) 

This matches the described root cause: an untrusted, caller-controlled value (`MessageID`) governs a shared, first-come-first-served resolution slot with no per-caller isolation (e.g., no `(Sender, MessageID)` composite key as used elsewhere in `requestcache.go`'s `globalID{sender, id}`).

## Impact Explanation
- **Denial of service against a targeted request**: an attacker who wins the `MessageID` race causes the victim's `callback.Wait(ctx)` to time out (`RequestTimeoutError`) even though the DON actually processed and responded to the request.
- **Cross-user response corruption**: the DON's response intended for the victim is delivered to the attacker's callback instead, since `handleWebAPITriggerMessage` resolves purely by `MessageID` with no sender binding. This can leak response payload contents to an unintended party.
- This maps to an in-scope Chainlink impact class (cross-user response corruption / gateway response misdelivery) and is a legitimate design gap, not merely theoretical — it's demonstrated by the fact that the newer v2 handler (`httpTriggerHandler.setupCallback`) had to add an explicit duplicate-ID rejection that this legacy handler lacks.

## Likelihood Explanation
No special privilege or node/operator access is required — any client able to submit legacy JSON-RPC requests to this gateway/DON endpoint controls its own `MessageID` (the JSON-RPC `id`) and can pick one matching or racing a target's ID. The comment `// TODO: apply allowlist and rate-limiting here` confirms no allowlist currently gates this handler, and `Message.Validate()` does not enforce ID uniqueness. Exploitability depends on the attacker knowing or guessing/racing a victim's `MessageID`, which is plausible for predictable/sequential client ID schemes or same-origin racing scenarios, making likelihood moderate.

## Recommendation
- Before storing into `h.savedCallbacks` in `HandleLegacyUserMessage`, check for an existing entry under `msg.Body.MessageID` and reject the new request (return a conflict error) rather than silently overwriting.
- Key `savedCallbacks` by `(Sender, MessageID)` instead of `MessageID` alone (mirroring `requestcache.go`'s `globalID{sender, id}` pattern) so that one caller's ID cannot collide with another's, and validate that `handleWebAPITriggerMessage` resolves back to the correct sender's callback.
- Apply the allowlist/rate-limiting noted in the existing `TODO` comment.

## Proof of Concept
1. Client A sends a legacy JSON-RPC request to the gateway with `id = "req-1"` targeting a slow-responding DON method; `HandleLegacyUserMessage` stores `savedCallbacks["req-1"] = A's callback` and forwards the request to all DON members.
2. Before the DON responds, attacker B sends another legacy JSON-RPC request with the same `id = "req-1"`; this passes `Message.Validate()` (only length/format checked) and overwrites `savedCallbacks["req-1"]` with B's callback.
3. When a DON node responds for `MessageID = "req-1"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["req-1"]`, finds B's callback, deletes the entry, and delivers the response to B.
4. Client A's `ProcessRequest` call blocks on its now-orphaned callback until timeout, returning `RequestTimeoutError` despite the underlying request having succeeded.

This can be reproduced as a Go unit/integration test against `handler.HandleLegacyUserMessage` + `handleWebAPITriggerMessage`, asserting that after two `HandleLegacyUserMessage` calls with identical `MessageID`s, only the second caller's callback receives the DON's response and the first caller's callback never fires.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
