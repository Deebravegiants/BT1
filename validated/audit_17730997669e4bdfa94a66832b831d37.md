### Title
Escrow withdrawal accepts no-revert-on-failure ERC20/TRC20 tokens as successful transfers, permanently burning user/solver escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2`, the `withdraw()` function (reached via `onAccept()` handling `RedeemEscrow`/`RefundEscrow` requests, and via `onGetResponse()`) releases escrowed order tokens using a raw low-level `.call` to the token's `transfer` selector and only checks whether the *call itself* reverted, never decoding the ERC20 boolean return value. For a no-revert-on-failure token, the call succeeds (`success == true`) even though zero tokens were actually transferred, yet the code still deducts the escrow and marks the order as filled/refunded.

### Finding Description
`withdraw()` transfers each escrowed token to the beneficiary like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the external call reverted, not whether the token's `transfer()` returned `true`. Contracts using OpenZeppelin's `SafeERC20.safeTransfer` correctly decode and require the boolean return value (or absence of it) as this repo does elsewhere, e.g. in the main EVM `IntentsBase._withdraw`: [2](#0-1) 

But the Tron contract deliberately bypasses `SafeERC20` for these transfers and instead performs a raw call that treats any non-reverting response — including one that returns `false` — as success. Any no-revert-on-failure token (a known-common pattern on Tron/TRC20, where many TRC20 tokens do not throw on failed transfers but instead return `false`) will cause the beneficiary to receive nothing while:
- `_filled[body.commitment]` is set to the beneficiary, permanently marking the order as settled and preventing any retry/cancel path, and
- `_orders[body.commitment][token] -= amount` permanently deletes the escrow accounting for that token.

The same unchecked-success pattern is also used for the transaction-fee payout in the same function: [3](#0-2) 

and for dust sweeping in `onAccept`'s `SweepDust` branch: [4](#0-3) 

This is directly analogous to the reported `FootiumPrizeDistributor.claimERC20Prize()` bug: an unchecked/naively-checked `transfer()` call lets bookkeeping advance as if the transfer succeeded even though the recipient received nothing.

### Impact Explanation
This is reachable in the core intents escrow flow: any user places a cross-chain order with ERC20/TRC20 inputs escrowed in the `IntentGatewayV2` contract on Tron; once a solver fills the order (or the order is cancelled/times out), a relayer delivers the corresponding `RedeemEscrow`/`RefundEscrow` ISMP message which triggers `onAccept -> withdraw`. If the escrowed token exhibits no-revert-on-failure behavior (e.g., due to blacklist checks, paused state, insufficient balance edge cases handled via boolean return instead of revert — a real, documented behavior for several TRC20 tokens), the beneficiary (order owner or solver) permanently loses their escrowed funds: the tokens remain locked in the contract, the order is marked filled/refunded so it can never be retried, and the escrow ledger is decremented as if paid out. This is a direct, permanent loss/freezing of user funds with no recovery path.

### Likelihood Explanation
Likelihood is moderate-to-high in practice on Tron: TRC20 tokens are well known for non-standard, non-reverting transfer semantics in various failure conditions (e.g., blacklists, paused contracts, insufficient contract balance due to fee-on-transfer interactions elsewhere in the same codebase, which the tests already anticipate as a supported token category). No attacker action is required beyond normal use of a non-standard token as the order's input/output asset — this can be triggered unintentionally by ordinary escrow settlement, or intentionally targeted by a malicious token author who lists their no-revert token as an intent asset to strand user escrow.

### Recommendation
Replace the raw `.call(...)` + `success`-only checks in `withdraw()` (and in the `SweepDust` branch of `onAccept`) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (e.g. `IntentsBase._withdraw`, `EvmHost.dispatchIncoming`). This library is already imported and aliased (`using SafeERC20 for IERC20;`) in this same file, so the fix is a drop-in replacement:

```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```

for each of the token transfer sites in `withdraw()`, the fee payout, and `SweepDust` handling.

### Proof of Concept
1. Deploy a mock TRC20/ERC20 token whose `transfer()` returns `false` (instead of reverting) when the contract's balance is insufficient or the recipient is blacklisted — modeled after real-world TRC20 tokens.
2. User creates a cross-chain order on the Tron `IntentGatewayV2` with this token as an input asset; tokens are escrowed via `safeTransferFrom` on order creation.
3. Solver fills the order on the destination chain, or the order times out and the user cancels it, triggering a `RedeemEscrow`/`RefundEscrow` POST request back to the Tron gateway.
4. Relayer delivers the proof; `onAccept` calls `withdraw(body, ...)`.
5. Inside `withdraw`, if the mock token's `transfer` returns `false` (e.g., simulate a blacklisted beneficiary or contract balance drained via a reentrant/parallel path), `token.call(...)` still returns `success == true` since the call itself doesn't revert.
6. `withdraw` proceeds: `_orders[body.commitment][token] -= amount` and `_filled[body.commitment] = beneficiary` are set, `EscrowReleased`/`EscrowRefunded` is emitted — yet `beneficiary`'s token balance is unchanged, and the tokens remain stuck in the `IntentGatewayV2` contract with no path to reclaim them.
