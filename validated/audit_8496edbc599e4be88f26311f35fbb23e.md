This confirms the design intent: `create()` is explicitly meant to be callable by **any account** ("Lockups can be funded from any account", "No need to have access to the foundation keys to create lockup") [1](#0-0) , and the resulting lockup account ID is auto-derived purely from `owner_account_id`, independent of who calls or funds it [2](#0-1) .

### Title
Front-Runnable Lockup Account Creation Allows Attacker to Dictate Vesting/Lockup Terms for a Victim Owner - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the deterministic lockup `AccountId` solely from `sha256(owner_account_id)`, with no binding to `predecessor_account_id` (the caller/funder) or any other caller-specific value [3](#0-2) . Because the function is intentionally public and callable by anyone with the minimum deposit, an attacker can observe a pending, legitimate `create()` transaction for a given `owner_account_id` in the mempool and front-run it with the same `owner_account_id` but attacker-chosen `lockup_duration`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` [4](#0-3) .

### Finding Description
Since NEAR account creation is a one-time, name-unique operation, whichever `create()` call executes first wins the deterministic account name `sha256(owner_account_id)[..20].<factory>`. The legitimate transaction that lands second will fail during `create_account()` (the account already exists), and its callback `on_lockup_create` will detect the failure via `is_promise_success()` and simply refund the deposit to that caller [5](#0-4) . There is no uniqueness reservation, commit-reveal, or binding of the resulting account to the transaction's `predecessor_account_id`/salt, and no permission check restricting who may call `create` for a given `owner_account_id` [6](#0-5) .

This mirrors the root cause in the external report: an identifier that should be scoped/bound to the legitimate initiator (here, effectively bound to the intended funder/terms) is instead derived only from public, attacker-observable parameters, letting a backrunning/front-running attacker permanently claim the slot with parameters of their choosing.

### Impact Explanation
The victim `owner_account_id`'s lockup account is permanently occupied by a contract created with the attacker's chosen lockup terms (e.g., an extreme `lockup_duration`, a malicious `vesting_schedule`, or a `foundation_account_id` under attacker influence such as a rogue `whitelist_account_id`). Since account names on NEAR cannot be reused after creation, this is an irrecoverable state: the legitimate funder can never create the intended, correctly parameterized lockup for that owner at that address. Any subsequent NEAR transferred to that address (assuming it is the "real" lockup) would be governed by attacker-dictated release/vesting terms, matching the in-scope "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release, vesting termination" impact category.

### Likelihood Explanation
The attack requires only observing a pending `create()` call in the mempool (the `owner_account_id` and other args are visible in plaintext) and submitting a competing transaction with a higher/faster inclusion before the legitimate one, paying only the `MIN_ATTACHED_BALANCE` (3.5 NEAR) themselves [7](#0-6) . No privileged role, key compromise, or validator collusion is needed — purely an unprivileged, public-entrypoint front-run, identical in nature to the reported analog.

### Recommendation
Bind the derived lockup `AccountId` to more than just `owner_account_id` — e.g., require the call to be restricted (e.g., only the `owner_account_id` itself, or the `foundation_account_id`, may create a lockup for that owner), or incorporate `predecessor_account_id`/a caller-supplied salt into the address derivation combined with an explicit reservation/allow-list step, so that an unrelated third party cannot preempt lockup creation for an owner they don't control.

### Proof of Concept
1. Foundation/funder broadcasts `create({owner_account_id: "alice.near", lockup_duration: X, vesting_schedule: correct_schedule})` from `funder.near` with the correct deposit.
2. Attacker observes this pending transaction and immediately submits `create({owner_account_id: "alice.near", lockup_duration: u64::MAX, vesting_schedule: None})` from `attacker.near` with just `MIN_ATTACHED_BALANCE`, using a higher gas price/priority so it lands first in the same or an earlier block.
3. Attacker's transaction succeeds: account `sha256("alice.near")[..20].lockup-factory.near` is created with attacker's malicious terms and `owner_account_id = "alice.near"`.
4. The foundation's original transaction now fails at `create_account()` (account already exists); `on_lockup_create` refunds `funder.near`'s deposit [5](#0-4) , but the address is permanently squatted with the attacker's chosen lockup/vesting configuration, and the legitimate lockup for Alice can never be created at that deterministic address again.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
