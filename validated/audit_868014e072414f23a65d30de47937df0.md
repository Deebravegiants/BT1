### Title
User-centric signup success determination bypasses backend identity/duplicate verification - ([File: src/plans/mod.rs])

### Summary
The `do_signup` flow contains a branch that, for "user-centric" signups, decides signup success/failure purely from locally-computed state (`signup_reason`) instead of relying on the backend enrollment round-trip (`enroll_user`) that normally performs duplicate/uniqueness verification. This mirrors the reported bug class: a check meant to gate an outcome silently falls through, and the system proceeds as if the "normal" case held, misattributing state that should have depended on external verification.

### Finding Description
In the reported smart-contract bug, `balance >= COLLATERAL` was meant to distinguish a "reward" state from a "slashed" state; when the check failed to catch the slashed case, execution fell through and treated the withdrawal as a normal reward, splitting funds among unintended parties.

The structurally analogous pattern in `do_signup` (`src/plans/mod.rs`) is:

```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason))
        .await
        .is_success()
};
``` [1](#0-0) 

When `user_centric_signup` is true (a value read from backend-supplied QR data, `UserData::user_centric_signup`) [2](#0-1) , the orb never performs the normal `enroll_user::Plan::run` handshake with the backend — a loop that posts the signup and polls `signup_poll` for backend-side results such as duplicate detection, backend fraud checks, and in-flight match resolution [3](#0-2) . Instead, success is derived solely from the *local* `signup_reason` value computed from the on-device biometric pipeline and on-device fraud detection.

In this FOSS build the on-device fraud engine is stubbed out entirely (`detect_fraud` always returns `Ok(false)`, and `N_FRAUD_CHECKS = 0`) [4](#0-3) [5](#0-4) . Consequently, `signup_reason` becomes `SignupReason::Normal` whenever the biometric pipeline merely completes without a hard failure (`pipeline.is_some()`), regardless of whether the backend would have flagged the signup as a duplicate/fraud/already-enrolled identity [6](#0-5) .

This is the same root-cause shape as the reported issue: a condition (`balance >= COLLATERAL` / "did the backend actually verify uniqueness") that is supposed to gate a critical outcome is bypassed, and the code falls through to the "normal/success" branch based on an incomplete local signal, silently skipping the authoritative check that should have been consulted.

### Impact Explanation
If the local pipeline/fraud state is treated as sufficient proof of a valid, non-duplicate signup, a user-centric signup can be marked `Success` and proceed to enrollment/credential issuance without the backend's uniqueness/duplicate-signup verification round trip ever running. Under the report's severity rubric this is a cross-signup/identity-binding integrity issue: a signup could be attributed as "Normal"/successful state locally while the authoritative anti-duplicate check that the rest of the system relies on (`enroll_user`'s `signup_poll` loop, which explicitly enumerates "Backend duplicates", "Backend inflight matches", "Backend detected fraud" as failure causes [7](#0-6) ) is never invoked for this signup path.

### Likelihood Explanation
Reachability depends entirely on the backend setting `user_centric_signup: true` for a given user QR-code session and `ignore_user_centric_signups` being false in device config — both are backend/config-controlled, not attacker-controlled from the orb's perspective. I could not fully verify from the indexed files whether the backend independently re-validates uniqueness out-of-band for user-centric signups (which would mitigate this), because `src/config.rs` (which defines `ignore_user_centric_signups`) and the broader backend semantics of `user_centric_signup` were not fully retrievable within the available context/index. This uncertainty limits confidence in the real-world exploitability of this analog.

### Recommendation
Do not derive signup success purely from local `signup_reason` for user-centric signups. If a lighter-weight backend confirmation is required, still call an authoritative backend uniqueness/duplicate check equivalent to the `signup_poll` verification before marking `enroll_user::Status::Success`, mirroring the report's recommendation of introducing an explicit, backend-approved gate rather than relying on an implicit/locally-computed condition.

### Proof of Concept
Not directly demonstrable via static analysis alone: reproducing this requires backend control to set `user_centric_signup: true` on a QR-code session and confirming that no backend duplicate/fraud check occurs before local success is reported — access to a running backend/device would be needed to confirm exploitability, which is outside the scope of the indexed code review performed here.
