## Analog Found

### Title
Filling an order with zero output assets bypasses escrow-release `safeTransfer`, permanently freezing the user's input tokens - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` derives the escrow-release list `escrowedInputs`/`outputFills` and the fully-filled flag from `order.output.assets.length`. When this length is `0`, the entire per-output loop is skipped, so the code that would normally populate the arrays and flip `isFullyFilled` to `false` for a legitimate but incomplete fill never runs — `isFullyFilled` stays at its initial `true`. This causes `_withdraw` to be invoked with an **empty `tokens[]` array** while `finalize=true`, exactly mirroring the reported Telcoin bug class where a zero-length input array silently bypasses the intended `safeTransfer`/validation branch.

### Finding Description
`_fillSameChain` builds the arrays sized to `outputsLen = order.output.assets.length`: [1](#0-0) 

The core release logic lives entirely inside the `for` loop over `outputsLen`: [2](#0-1) 

If `outputsLen == 0`, this loop body never executes, so `isFullyFilled` (initialized to `true`) is never set to `false`, and `escrowedInputs`/`outputFills` remain zero-length arrays: [3](#0-2) 

Execution then proceeds to finalize the order and release escrow via `_withdraw`, passing the empty `escrowedInputs` array with `finalize=true`: [4](#0-3) 

`_withdraw` gates both the `UnknownOrder()` sanity check and the actual `safeTransfer`/native-send entirely inside a loop over `body.tokens`: [5](#0-4) 

When `body.tokens.length == 0`, this loop is skipped completely — no escrow validation, no token transfer — yet because `finalize == true`, `_filled[body.commitment]` is unconditionally set to the beneficiary just before the loop: [6](#0-5) 

This is the exact bug class from the external report: a zero-length input array causes the code to skip the branch that performs `safeTransfer`, while the surrounding logic proceeds as though the operation succeeded.

### Impact Explanation
Any user who places an order with `order.output.assets.length == 0` (nothing prevents this at `placeOrder` time — that code only iterates and validates non-zero amounts *if* the array is non-empty) has their escrowed `order.inputs` tokens locked in `_orders[commitment][token]`. Any solver calling `fillOrder`/`_fillSameChain` on such an order (trivially, since there is nothing to fill) causes:
- `_filled[commitment]` to be set to the solver's address, permanently marking the order as settled.
- Zero tokens transferred out of escrow, because `body.tokens` is empty.
- The escrow balance in `_orders[commitment][token]` remains non-zero but is now unreachable: `cancelOrder` reverts once `_filled[commitment] != address(0)` (per the documented `cancelOrder` guard `if (_filled[commitment] != address(0)) revert Filled();`), and there is no other path back to `_withdraw` for an already-`_filled` commitment.

This results in a permanent freeze of the user's escrowed input funds — a concrete, high-severity fund-freezing bug reachable via a single `placeOrder` + `fillOrder` pair from an unprivileged user and solver, matching the "Accept only concrete theft or permanent freezing of funds" validation bar.

### Likelihood Explanation
High: this requires no special privilege, no consensus/relayer manipulation, and no crafted cross-chain proof — it is triggerable purely with same-chain `IntrinsicIntents` calls (`placeOrder` with an empty `output.assets` array, then `fillOrder` by any solver, even the same account). No existing check rejects an order with zero output assets at placement or at fill time.

### Recommendation
- At order placement (`placeOrder`), reject orders where `order.output.assets.length == 0` unless `order.inputs.length == 0` as well (i.e., disallow escrowing tokens for an order that requires no output).
- In `_fillSameChain`, explicitly guard against `outputsLen == 0` by reverting (e.g., `if (outputsLen == 0) revert InvalidInput();`) rather than silently treating it as a no-op "fully filled" fill.
- In `IntentsBase._withdraw`, add an explicit `require(body.tokens.length > 0)` (or equivalent) when `finalize == true`, so that marking `_filled[commitment]` can never happen without releasing/validating at least one escrowed token.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [{token: USDC, amount: 100e6}]` and `order.output.assets = []` (empty), `order.output.beneficiary = user`. Placement succeeds — the `predispatch`/`inputs` loops run fine, escrow is recorded: `_orders[commitment][USDC] = 100e6`.
2. Any account (including the user themself, or a bystander) calls `fillOrder(order, options)` with `options.outputs = []`.
3. In `_fillSameChain`: `outputsLen = 0` ⇒ the `for` loop body never executes ⇒ `isFullyFilled` stays `true`, `escrowedInputs = []`.
4. `_withdraw(body={commitment, tokens: [], beneficiary: filler}, false, true)` is called: `_filled[commitment] = filler` is set; the `for` loop over `body.tokens` (empty) does nothing — no `safeTransfer` of the escrowed 100e6 USDC occurs.
5. `OrderFilled` is emitted with empty `inputs`/`outputs` arrays; the order is now permanently `_filled`.
6. User calls `cancelOrder` — reverts with `Filled()` since `_filled[commitment] != address(0)`.
7. Result: the 100e6 USDC remains stuck in `_orders[commitment][USDC]` inside the `IntrinsicIntents`/`IntentGatewayV2` contract with no code path left to release it.

**Note on verification limits:** I was unable to fully trace whether `ExtrinsicIntents.sol` (the cross-chain sibling contract, also calling `_withdraw`) has an equivalent unguarded path, since I did not have remaining tool calls to read its full body — the PoC above is confirmed only for the same-chain `IntrinsicIntents._fillSameChain` path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
