### Title
Webhook `shop`, `topic`, and `webhook_id` metadata are trusted from unauthenticated HTTP headers while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches `WebhookMetadata` containing `shop`, `topic`, `webhook_id`, and `api_version` — all of which are read from HTTP headers that are never included in the signed material. This breaks the identity binding `hmac_signed_bytes == fields_the_handler_acts_on`, allowing the `shop` attribution of an otherwise-valid webhook to be forged.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` when constructing the `WebhookMetadata` passed to the host application's handler: [3](#0-2) 

`WebhookMetadata` is a plain struct with no independent verification of `shop`: [4](#0-3) 

Because the HMAC (`OpenSSL::HMAC.hexdigest` over `@raw_body`) is computed with the app's `client_secret`/`api_secret_key`, an attacker cannot forge an arbitrary body+HMAC pair without the secret. However, the HMAC does **not** bind the body to the `shop-domain` header. Any entity that legitimately receives a valid webhook for one shop it controls (e.g., a merchant who has installed the multi-tenant app on their own store) can replay that exact body+HMAC pair while substituting a different `x-shopify-shop-domain` header value naming another tenant. `HmacValidator.validate` will still return `true`, because it only checks `verifiable_query.to_signable_string` (the body) against the HMAC — the forged shop header is invisible to the check: [5](#0-4) 

The binding that should hold is:
`hmac == HMAC(secret, body || shop || topic || webhook_id)`
but the gem only enforces:
`hmac == HMAC(secret, body)`
while `shop` (the tenant-identifying field) is taken from an unauthenticated header and handed to the host application as trusted metadata.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` to key its per-tenant lookups (e.g., "find the merchant record for this shop and update it from `body`"), an attacker who controls one tenant's webhook stream can attribute a replayed/crafted body to a different shop's identity, causing the host app to write, delete, or process data under the wrong tenant. This is a cross-tenant boundary violation reachable purely through this gem's exposed webhook-verification surface (`Utils::HmacValidator.validate` + `Webhooks::Registry.process`), which advertises itself as validating webhook authenticity but only authenticates the body, not the shop attribution that callers are encouraged to rely on via `WebhookMetadata`.

### Likelihood Explanation
Requires the attacker to be able to install the app on at least one shop they control (a normal unprivileged merchant) and to be able to send a crafted HTTP request with a spoofed `x-shopify-shop-domain` (or `shopify-shop-domain`) header carrying the replayed body/HMAC pair to the app's public webhook endpoint. No access to the app's `client_secret`, another merchant's token, or Shopify infrastructure is required — this matches the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain, topic, and webhook id in the signed/verified material, or independently verify `request.shop` against a value already associated with the specific webhook subscription/HMAC (e.g., cross-check against records stored at registration time) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request and resends it to the app's webhook endpoint, keeping body `B` and the HMAC header unchanged, but replacing the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `hmac` field still matches `HMAC(secret, B)`.
4. `HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B` — see [6](#0-5) .
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...))`, causing the host application to process attacker-supplied body content under the victim shop's identity — see [7](#0-6) .
