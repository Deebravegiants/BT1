Audit Report

## Title
Cross-user response confusion via attacker-controlled `MessageID` collision in gateway `WebAPIHandler` callback map - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
The legacy `web_api_trigger` path stores each pending caller's callback in `h.savedCallbacks`, keyed solely by the client-supplied `MessageID`, with no binding to sender identity and no collision check on insert. Since `MessageID` is fully attacker-controlled (only length/null-byte validated), an unprivileged client can pick a `MessageID` matching another client's in-flight request, causing the map entry — and the eventual node response — to be misattributed.

## Finding Description
`gateway.ProcessRequest` decodes the raw JSON-RPC request and forwards the client-chosen `jsonRequest.ID` unmodified: [1](#0-0) . `ValidatedMessageFromReq` sets `m.Body.MessageID = req.ID` directly from client input, and `Message.Validate` only enforces length (≤200/some max) and non-null-terminator constraints — no uniqueness or sender-binding check: [2](#0-1) [3](#0-2) .

`HandleLegacyUserMessage` then stores the caller's callback in `h.savedCallbacks[msg.Body.MessageID]` via an unconditional map assignment — no existence check, no sender/session tie-in: [4](#0-3) . This was independently confirmed by reading the function in full; `msg.Body.Sender` (derived from the signature in `ExtractSigner`) is computed during validation but never incorporated into the `savedCallbacks` key. When a DON node responds, `handleWebAPITriggerMessage` looks up and deletes whatever entry currently sits at that key and forwards the payload to it, with no verification that the retrieved callback matches the original requester: [5](#0-4) .

I was unable to find any deduplication, uniqueness enforcement, or per-sender scoping logic elsewhere in the gateway package for this legacy path (searched for `pendingRequest`, `requestCache`, `dedup`, `duplicate` across `core/services/gateway/**`; the only `requestcache.go` hits relate to a separate v2 component, not the legacy `WebAPIHandler`). This confirms the described root cause: state (the callback) is tracked only by a caller-supplied, non-unique, non-sender-scoped key, and a second unrelated request using the same key silently overwrites the first.

## Impact Explanation
An unprivileged HTTP client can cause another concurrent client's Web API trigger response (potentially containing capability/job execution results or other payload data meant only for the original caller) to be delivered to the attacker instead of the legitimate requester, while the legitimate requester's own request silently fails and eventually times out via `callback.Wait(ctx)` in `gateway.ProcessRequest`. This is a genuine cross-user response corruption/impersonation issue reachable via the internet-facing gateway JSON-RPC endpoint without any privilege or role beyond being able to send an HTTP request, matching the in-scope "gateway request impersonation / cross-user response corruption" category.

## Likelihood Explanation
Exploitation requires no authentication bypass — only submitting a JSON-RPC request with a `MessageID` chosen to collide with another client's currently-outstanding request, and winning a benign race on the unsynchronized-by-design `savedCallbacks` map (protected by a mutex for concurrency-safety but not for collision-prevention). While winning the race against an unknown victim's exact timing/ID in practice requires either predictable/sequential IDs used by some client implementations or an attacker running enough concurrent requests to increase collision odds, the underlying code defect — unconditional overwrite of a security-relevant map entry keyed by fully attacker-controlled input — is real and directly verifiable in the code, not speculative.

## Recommendation
Scope `savedCallbacks` entries by more than the caller-supplied `MessageID`: derive a gateway-side unique key (e.g., combine `MessageID` with the validated `msg.Body.Sender` and/or a gateway-generated nonce) before storing/looking up callbacks, and reject insertion attempts in `HandleLegacyUserMessage` when a still-pending entry already exists for the derived key instead of silently overwriting it.

## Proof of Concept
1. Client A sends a `web_api_trigger` JSON-RPC request to the gateway with `MessageID = "X"`; `HandleLegacyUserMessage` stores A's callback in `savedCallbacks["X"]` (`core/services/gateway/handlers/capabilities/handler.go:412`) and forwards the request to all DON nodes.
2. Before any node responds, client B sends its own `web_api_trigger` request also using `MessageID = "X"`, overwriting `savedCallbacks["X"]` with B's callback via the same unconditional assignment.
3. A DON node later replies to A's original trigger using `MessageID = "X"`; `handleWebAPITriggerMessage` (`handler.go:148-162`) retrieves whatever callback currently occupies `"X"` (now B's) and delivers A's response to B.
4. Client A's `callback.Wait(ctx)` in `gateway.ProcessRequest` never resolves for A's actual response and eventually returns a `handler timeout` error, while B has received response data intended for A.

A Go integration test constructing two `HandleLegacyUserMessage` calls with identical `MessageID` values from distinct callback instances, followed by a single `handleWebAPITriggerMessage` invocation, would concretely demonstrate the misattributed delivery.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageID = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

func (m *Message) Validate() error {
	if m == nil {

	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}

		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
