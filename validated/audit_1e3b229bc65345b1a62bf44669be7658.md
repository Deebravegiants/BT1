## Analysis

This maps to a concrete unchecked-ERC20-return-value bug in the Tron variant of `IntentGatewayV2`, not in the main EVM contracts (which consistently use OpenZeppelin's `SafeERC20`). [1](#0-0) 

### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` (Tron) can silently fail while marking escrow as delivered - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron port of `IntentGatewayV2` replaces the `SafeERC20`-based transfers used elsewhere in the codebase with raw low-level `.call` invocations of the `transfer` selector, checking only that the call did not revert (`success`) but never decoding/validating the returned `bool` value.

### Finding Description
`withdraw()` releases escrowed tokens to a beneficiary after a `RedeemEscrow`/`RefundEscrow` request is delivered by the host: [2](#0-1) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

The same pattern is repeated for the transaction-fee payout and for `SweepDust`: [3](#0-2) [4](#0-3) 

Only the low-level `success` (i.e. "the call didn't revert") is checked. If the token returns `false` from `transfer` instead of reverting on failure — a well-known non-standard ERC20/TRC20 behavior — `success` is still `true` (the call executed and returned data without reverting), so the `if (!success) revert TransferFailed();` guard never fires. The code proceeds to decrement `_orders[body.commitment][token]`, mark `_filled[body.commitment] = beneficiary`, and emit `EscrowReleased`/`EscrowRefunded`, even though the beneficiary received nothing.

This is exactly the bug class from the referenced report: code that assumes a "call succeeded" implies "ERC20 semantics succeeded" without validating the ABI-encoded boolean return value, which for tokens that signal failure via `false` (rather than reverting) leads to state being finalized as if funds moved when they did not.

Note the same file elsewhere correctly uses `SafeERC20.safeTransferFrom` for inbound escrow transfers (`evm/tron/contracts/apps/IntentGatewayV2.sol:405`), showing the outbound `withdraw`/`SweepDust` paths were implemented with a weaker, unchecked pattern.

### Impact Explanation
For any input/output token used in the intent flow that returns `false` on failed transfer (rather than reverting), the escrowed tokens become permanently stuck in the `IntentGatewayV2` contract: the commitment is marked filled/refunded and the internal `_orders` accounting is decremented, so the beneficiary can never re-claim the funds (their entitlement is deleted) while the tokens remain locked in the contract. This is a fund-freezing/loss condition reachable by any relayer delivering a `RedeemEscrow`/`RefundEscrow` request or a `GET` response for tokens with this transfer semantics, or via `SweepDust` requests dispatched from Hyperbridge.

### Likelihood Explanation
Likelihood depends on the specific tokens configured for intents on the Tron deployment. Historically, several widely-used tokens (including certain TRC20/ERC20 deployments) do not strictly follow the standard and can return `false` under specific failure conditions (e.g. paused state, blacklist, insufficient balance edge cases) instead of reverting. Because `withdraw` is invoked as part of the normal, permissionless-to-trigger cross-chain delivery flow (`onAccept`/`onGetResponse`), no privileged actor is required to hit this path — it triggers automatically whenever such a token's transfer call returns `false`.

### Recommendation
Use `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used elsewhere in this same file) for all outbound token movements in `withdraw` and `SweepDust`, or explicitly decode and check the returned boolean when non-zero-length return data is present, consistent with the pattern used for `IERC20(token).safeTransferFrom` at line 405 of the same contract.

### Proof of Concept
1. Configure/whitelist an input or fee token whose `transfer` implementation returns `false` on failure (e.g., transfer to a blacklisted/paused beneficiary) instead of reverting.
2. A solver fills an order; escrow is recorded via `_orders[commitment][token]`.
3. Hyperbridge relays a `RedeemEscrow` request targeting a beneficiary for which the token's `transfer` returns `false` (call itself doesn't revert).
4. `withdraw()` at [2](#0-1)  sees `success == true`, does not revert, decrements `_orders`, sets `_filled[commitment] = beneficiary`, and emits `EscrowReleased`.
5. The beneficiary never received tokens (transfer silently failed), but the escrow is now marked filled and the underlying tokens remain stuck in the `IntentGatewayV2` contract with no way to reclaim them.
