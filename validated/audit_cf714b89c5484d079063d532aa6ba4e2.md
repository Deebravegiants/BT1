### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant shop spoofing at `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` authenticates the body bytes but never the `shop`, `topic`, or `webhook_id` values that `Registry.process` passes on to the app's `WebhookHandler`. This breaks the equality "shop authenticated by the HMAC == shop delivered to the handler as the tenant identifier."

### Finding Description
`ShopifyAPI::Webhooks::Request` parses the `x-shopify-hmac-sha256`, `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers independently, but only the request body participates in the signature: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC strictly over `to_signable_string` (the raw body): [2](#0-1) 

`Registry.process` only checks this body HMAC, then immediately trusts `request.shop` (taken straight from the unauthenticated header) as the tenant identity handed to the application's handler: [3](#0-2) 

The library's own documentation tells integrators that calling `Registry.process` "will verify the request did indeed come from Shopify," and that `data.shop` is simply "The shop domain of the webhook," implying it is trustworthy: [4](#0-3) [5](#0-4) 

Because headers are excluded from the signable string, any party that can obtain one legitimate `(body, hmac)` pair for the shared `api_secret_key` (e.g., from their own installed/dev shop's webhook deliveries, which every merchant/developer legitimately receives) can replay that exact body+HMAC to the app's public webhook endpoint while substituting arbitrary `shop-domain`, `topic`, and `webhook-id` header values. `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler to act on.

### Impact Explanation
This is a cross-tenant identity-binding failure entirely inside this gem's own webhook-processing code path (`Request` + `Registry.process` + `HmacValidator`), requiring no knowledge of `api_secret_key`, no access token, and no privileged account — only possession of one legitimately-received webhook payload for any shop that uses the app (attacker can generate this for their own store). Any host application that relies on `data.shop` from `WebhookMetadata` to select which tenant's records to update (a pattern explicitly encouraged by the gem's own example, which forwards `data.shop` as `shop_domain` into a background job) can be made to apply attacker-supplied webhook bodies against a different shop's data, i.e., cross-tenant access/write.

### Likelihood Explanation
Moderate-to-high for any app that exposes its webhook HTTP endpoint publicly (as documented) and follows the gem's documented `data.shop` usage pattern. An attacker only needs to be a legitimate (even free/trial) user of the app to capture one valid `(body, hmac)` pair from their own webhook deliveries, then can replay it directly to the public endpoint with a forged shop header — no HMAC forgery or secret compromise required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind `shop` to the verified body (e.g., verify shop membership against the session/shop that requested/owns the specific `webhook_id` before dispatching to the handler). At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` so `HmacValidator` authenticates the full identity tuple, not just the JSON payload bytes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify legitimately delivers a webhook to the attacker's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, and body `B`.
3. Attacker captures `(B, valid_hmac)` and crafts a new HTTP POST directly to the app's public webhook route (same route the app registered, e.g. `/callback/orders/create`), setting:
   - body = `B` (unchanged)
   - `x-shopify-hmac-sha256` = `valid_hmac` (unchanged)
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com`
   - `x-shopify-topic`, `x-shopify-webhook-id` = attacker's choice
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches, so `Registry.process` does not raise `InvalidWebhookError` [6](#0-5) .
5. The app's `WebhookHandler#handle` receives `data.shop == "victim-shop.myshopify.com"` together with attacker-controlled `data.body`, and (per the gem's documented usage pattern) processes/persists it as if it were genuine data belonging to `victim-shop`.
