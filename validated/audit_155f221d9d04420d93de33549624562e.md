## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop` value used to identify the tenant for the delivered webhook is taken from an unsigned HTTP header. Since a single app's `client_secret` (and thus HMAC key) is shared across every shop that installs the app, any user who installs the app on their own (attacker-controlled) store can forge the `X-Shopify-Shop-Domain` header to any other shop while keeping a validly-signed body, breaking the binding between "HMAC-authenticated request" and "shop the request is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body — it never incorporates `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, with no additional check that the shop matches the body's signature scope: [4](#0-3) 

Because a Shopify app uses one `client_secret` for HMAC validation across all of its installed shops, an attacker who installs the app on their own store can capture a genuine, validly-signed webhook (body + `X-Shopify-Hmac-SHA256`) generated from their own store's data, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `HmacValidator.validate` will still return `true` (the body and HMAC are untouched and were legitimately produced with the shared secret), and `Registry.process` will pass `shop: "victim-shop.myshopify.com"` to the handler even though the payload content actually originates from the attacker's own store.

This is the exact identity-binding break called out in the review rules: "a shop authenticated versus the shop stored as a session key" — here, the shop that produced/authenticated the HMAC-signed bytes (attacker's shop) differs from the shop value the gem hands to the application (forgeable header value), and the gem provides no mechanism to detect the mismatch.

### Impact Explanation
If a host application relies on `WebhookMetadata#shop` (as returned by this gem) to select which tenant's session/data to act on — which is exactly the documented/intended usage of `Registry.process` and `Webhooks::Request#shop` — an attacker can inject attacker-controlled webhook content attributed to an arbitrary victim shop of their choosing, despite passing this gem's own HMAC check. Depending on how the host processes the webhook body (e.g., updating inventory, order, or customer records "for" the victim shop, or triggering shop-scoped side effects), this results in cross-tenant data injection/corruption, which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the target app on their own (or any) Shopify development/trial store — a capability available to any unprivileged internet user for public apps — and to replay an HTTP POST with a modified header. No access to the app's `client_secret`, access tokens, or any privileged account is needed, since the HMAC secret is shared across all tenants of the app by Shopify's design and the vulnerability lies in this gem never binding `shop` to that secret.

### Recommendation
Do not treat the `shop` header as trusted solely because the body HMAC validates. Options:
- Extend the webhook envelope validated against the secret to include the shop domain (e.g., require the host app to independently confirm `request.shop` corresponds to a shop with an active, previously-established session/webhook registration before trusting it), or
- At minimum, clearly document in `Webhooks::Request`/`Registry.process` that `shop` is not authenticated by the HMAC and that callers must independently verify shop identity (e.g., against known installed shops) before using it as a tenant key.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker-shop.myshopify.com`.
2. Trigger a webhook (e.g., `products/update`) so Shopify sends a POST with body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Capture `B` and `H`.
4. Replay a POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-SHA256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B`/`H`: [5](#0-4) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, despite the request never having been produced by or for the victim shop.
