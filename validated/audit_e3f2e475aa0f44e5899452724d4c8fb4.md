## Title
Pharos consensus client accepts non-ancestrally-connected finalized headers, enabling a 51%-style forked-finality double-spend - (File: `modules/consensus/pharos/verifier/src/lib.rs`)

### Summary
The Pharos light-client verifier `verify_pharos_block` (called from `PharosClient::verify_consensus` in `modules/ismp/clients/pharos/src/lib.rs`) validates a submitted header solely on: (1) block number greater than the currently trusted finalized height, (2) a matching `block_proof_hash`, (3) legal epoch progression, and (4) a BLS aggregate signature from ≥2/3+1 of the trusted validator set's stake. It never checks that `update.header.parent_hash` (or any ancestry chain) links back to `trusted_state.finalized_hash`. Any header at a higher block number that a validator supermajority signs is accepted as the new canonical finalized state, regardless of whether it actually extends the previously trusted chain.

### Finding Description
`verify_pharos_block` in `modules/consensus/pharos/verifier/src/lib.rs:45-129` performs these checks, in order:
- `update_block_number <= current_block_number` → `StaleUpdate` [1](#0-0) 
- `computed_hash == update.block_proof.block_proof_hash` (self-consistency of the header with its own signed hash, not a link to the *previous* finalized header) [2](#0-1) 
- Epoch monotonicity / rotation rules [3](#0-2) 
- BLS signature by ≥2/3+1 stake of `current_validator_set` over `block_proof_hash` [4](#0-3) 

At no point does the function compare `update.header.parent_hash` to `trusted_state.finalized_hash`, nor does it walk an ancestry chain from the trusted header to the new one (unlike the GRANDPA verifier, which explicitly requires `headers.ancestry(from, target.hash())` [5](#0-4) , or the BSC verifier, which at least binds two adjacent justified blocks together via `NonConsecutiveFinalization` [6](#0-5) ). The `BlockProof` in Pharos only signs `block_proof_hash` — the hash of the new header alone — with no reference to any parent/ancestor commitment [7](#0-6) .

Consequently, a supermajority of the current Pharos validator set (i.e., a "51%" collusion or compromise, exactly the bug class in the referenced OKEx/ETC report where a majority of block-producing power finalizes a competing chain) can sign *any* header at a higher block number — including one that forks off an earlier, already-finalized ancestor rather than the one actually recorded in `trusted_state.finalized_hash` — and the light client will accept it as canonical. This lets the attacker retroactively rewrite the observed Pharos chain history that Hyperbridge relies on for state commitments.

### Impact Explanation
The Pharos consensus client's `verify_consensus` is reachable through the unpermissioned `pallet_ismp::handle_unsigned` extrinsic, which "permits anyone execute ISMP messages for free, provided they have valid proofs" [8](#0-7)  and routes `Message::Consensus` messages straight to `consensus::update_client` → the registered `ConsensusClient::verify_consensus` implementation [9](#0-8) . Once the forged/forked header is accepted, its `state_root` is committed as a `StateCommitment` for the Pharos EVM state machine [10](#0-9) , which downstream state-proof verification (message delivery, token bridge mint/burn, intents) treats as trusted, finalized truth. A validator-majority collusion (or leaked/compromised keys reaching 2/3+1 stake) can therefore forge cross-chain message delivery or unbacked state proofs — directly mirroring the OKEx/ETC incident where a hashpower/validator majority finalized a competing chain to double-spend already-"confirmed" deposits.

### Likelihood Explanation
This requires the same "hard problem" acknowledged by the project's own documentation on consensus proofs: a supermajority of the tracked chain's validator set colluding or being compromised to finalize two competing histories, described there as a "51% Attack" against consensus-verifying bridges [11](#0-10) . That is a real, non-trivial threat model the docs explicitly identify — but unlike GRANDPA (which enforces cryptographic ancestry) and BSC (which enforces adjacency of the two justified blocks), the Pharos verifier has no defense at all against a signed fork that doesn't build on the previously trusted header, making this specific client strictly weaker than the others already in the codebase.

### Recommendation
Require `update.header.parent_hash == trusted_state.finalized_hash` (or provide and verify a full ancestry chain from the trusted finalized header to the new one, as GRANDPA does) before accepting a Pharos block proof, in addition to the existing signature/epoch checks in `verify_pharos_block`.

### Proof of Concept
1. Attacker (or colluding validator supermajority holding ≥2/3+1 stake of the current Pharos `ValidatorSet`) produces two headers `H_a` and `H_b`, both children of an old common ancestor `P` (older than `trusted_state.finalized_hash`), at the same or different block numbers greater than `trusted_state.finalized_block_number`.
2. Both `H_a` and `H_b` are independently signed by the validator supermajority via `debug_getBlockProof`-style aggregation, each producing a valid `BlockProof` over its own `block_proof_hash`.
3. Attacker submits `H_a` (containing a state root that credits the attacker with bridged funds) via `handle_unsigned` as a `Message::Consensus` proof; `PharosClient::verify_consensus` calls `verify_pharos_block`, which passes since `update_block_number > current_block_number`, the hash matches, the epoch is consistent, and the BLS signature verifies — no parent/ancestry check is performed.
4. The state commitment for `H_a` is now trusted; the attacker relays a request/response proven against this forged state root, causing Hyperbridge to mint/release funds.
5. Attacker later submits `H_b` (or reverts to the original canonical fork), which is also accepted, since verification never checks that it descends from the header just committed — completing a double-spend/rewrite analogous to the OKEx ETC 51%-attack loss.

### 51% Attacks

This is an attack that occurs when the supermajority of the validator set finalizes two competing chains at the same height. This situation can be devastating for consensus-verifying  bridges because both chains are valid for its consensus verification algorithm and can be used to double-spend incoming assets.

Although 51% attacks are relatively rare, they can be extremely devastating in a fully networked blockchain ecosystem where the weakest link in the chain can be exploited with a cascading effect across all its connected chains, similar to the Terra-Luna collapse. [Vitalik himself expressed this concern in a Reddit post.](https://www.reddit.com/r/ethereum/comments/rwojtk/ama_we_are_the_efs_research_team_pt_7_07_january/hrngyk8/)


> *Even if there’s a perfect ZK-SNARK-based bridge that fully validates consensus, it’s still vulnerable to theft through 51% attacks.*
>

This is a hard problem to solve and there have been no papers published addressing this major issue with consensus-verifying bridges. In order to build a **truly secure consensus-verifying bridge**, on-chain consensus clients must be resilient to 51% attacks.
