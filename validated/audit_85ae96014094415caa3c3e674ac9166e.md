### Title
Preimage reference-count is not incremented on duplicate `note()` calls, causing scheduler-driven premature preimage deletion and a `debug_assert!`-guarded panic path on the second `unrequest` - (File: substrate/frame/preimage/src/lib.rs)

### Summary
`Pallet::note_bytes` does not increment the `RequestStatus::Requested { count, .. }` counter when a preimage hash is already `Requested`, so two independent `StorePreimage::bound()`/`note()` calls for identical call bytes (e.g. from two scheduled tasks with identical `call` data) collapse into a single reference with `count == 1`. Cancelling both tasks then calls `Preimages::drop`/`unnote` twice for what the storage believes is a single reference: the first cancel fully removes the preimage and its `RequestStatusFor` entry, and the second cancel hits the `NotRequested` error path, which is guarded only by `debug_assert!` in `QueryPreimage::unrequest`/`StorePreimage::unnote`.

### Finding Description
`note_bytes` at [1](#0-0)  only inserts a `RequestStatus::Requested { count, .. }` entry with count carried over unchanged when the hash is already `Requested` — it never calls `count.saturating_inc()`. Reference counting is only incremented in `do_request_preimage` (`count.saturating_inc()`), a separate code path.

`StorePreimage::bound()` calls `Self::note(unbounded.into())` (i.e. `note_bytes`) whenever a call doesn't fit inline [2](#0-1) . If the scheduler pallet bounds two scheduled tasks whose call bytes are byte-for-byte identical, both calls hash to the same `T::Hash` and both go through `note_bytes`; the second call hits the `(Some(RequestStatus::Requested{...}), _)` arm and leaves `count` untouched at `1`, even though there are now two independent `Bounded::Lookup{hash, len}` references held by two scheduler agenda entries.

When either scheduled task is cancelled, the scheduler calls `T::Preimages::drop(&s.call)` → `QueryPreimage::unrequest(hash)` → `Pallet::do_unrequest_preimage` [3](#0-2) . Since `count == 1`, the very first cancellation takes the `count == 1` branch, which fully removes the preimage bytes (`Self::remove`) and the `RequestStatusFor` entry — even though the second scheduled task is still pending and still references the same hash. The second cancellation (or, worse, the scheduler trying to execute/peek the still-scheduled second task) now finds `RequestStatusFor::get(hash)` is `None`, producing `Err(Error::NotRequested)` from `do_unrequest_preimage`, which surfaces through:
- `QueryPreimage::unrequest`: `debug_assert!(res.is_ok(), "do_unrequest_preimage failed - counter underflow?")` [4](#0-3) 
- `StorePreimage::unnote`: `debug_assert!(res.is_ok(), "unnote_preimage failed - request outstanding?")` [5](#0-4) 

This is the exact `debug_assert!` panic path referenced in the question.

Two important corrections to the question's framing:
1. There is no true "race": Substrate/FRAME extrinsics execute sequentially within a block, so `cancel_named(id1)` and `cancel_named(id2)` execute deterministically one after the other, not concurrently. The bug is a deterministic sequential double-drop, not a race condition.
2. `debug_assert!` is compiled out entirely when `debug_assertions` is disabled (the default for `--release`/`production` profiles typically used for real validator/collator node binaries). In such builds the `Err` is silently discarded, the `debug_assert!` line is a no-op, and no panic occurs — but the underlying data corruption (preimage prematurely deleted while still referenced) persists regardless of build profile, which is a distinct, always-present bug: the second scheduled task's preimage becomes unavailable and it will fail to be looked up/executed by the scheduler.

### Impact Explanation
- In builds with `debug-assertions = true`, an unprivileged user who can schedule two tasks (via `pallet_scheduler::schedule`/`schedule_named` where `ScheduleOrigin` permits signed callers, or via any pallet exposing scheduling to end users) with byte-identical call payloads, then cancels both, deterministically triggers the `debug_assert!` panic in `Preimage::unnote`/`unrequest`, panicking the runtime/node executing that block — a scoped chain-halt condition triggered by valid unprivileged extrinsics.
- Independent of the debug-assert, in all builds this causes broken reference accounting: cancelling the first of two identical scheduled tasks silently deletes the shared preimage data that the second, still-active task depends on, causing that task to become unexecutable (its call bytes can no longer be resolved) — a queue/data-integrity violation of the stated invariant that preimage reference counting must correctly handle `N>1` references.

### Likelihood Explanation
The precondition set is narrow and permission-dependent: it requires a `ScheduleOrigin`/similar configuration that allows unprivileged (signed) accounts to schedule arbitrary or attacker-chosen calls, and requires those calls' encoded bytes to exceed the 128-byte inline threshold so `StorePreimage::bound` routes through `note()`/`Bounded::Lookup` rather than `Bounded::Inline`. In most production runtimes, `ScheduleOrigin` for `pallet_scheduler` is restricted to governance/root, which would remove the "purely unprivileged" reachability; but any pallet that internally calls the scheduler on behalf of signed users with attacker-controlled call payloads (or a permissive `ScheduleOrigin` configuration) would satisfy the precondition. Given those preconditions, the double-note/double-drop sequence is 100% reproducible and deterministic — not probabilistic.

### Recommendation
Fix the root cause in `substrate/frame/preimage/src/lib.rs::note_bytes`: increment `count` (via `saturating_inc`) when inserting a `RequestStatus::Requested` for a hash that is already `Requested`, mirroring the increment logic in `do_request_preimage`, so that each independent `bound()`/`note()` call for the same hash is tracked as a separate reference that must be matched by a corresponding `unrequest`/`drop`. Alternatively/additionally, harden `do_unrequest_preimage`'s callers (`QueryPreimage::unrequest`, `StorePreimage::unnote`) to handle `Err(NotRequested)` gracefully instead of relying on `debug_assert!`, since it is reachable from legitimate sequential user-triggered flows, not just internal logic errors.

### Proof of Concept
Rust unit test in `substrate/frame/preimage/src/tests.rs` (or a scheduler integration test):
1. Build call bytes `C` exceeding 128 bytes (so it is not `Bounded::Inline`).
2. Call `Preimage::note_bytes(C, None)` twice directly (simulating two `StorePreimage::bound()` calls from two scheduled tasks with identical call data) — or use scheduler integration test: `Scheduler::schedule_named(id1, ..., call_with_bytes(C))`, `Scheduler::schedule_named(id2, ..., call_with_bytes(C))`.
3. Assert `RequestStatusFor::<T>::get(hash)` is `Requested { count: 1, .. }` after both notes (demonstrating the missing increment — expected/fixed behavior would be `count: 2`).
4. Call `Scheduler::cancel_named(id1)` — assert preimage removed (`RequestStatusFor::get(hash).is_none()`), `Cleared` event emitted.
5. Call `Scheduler::cancel_named(id2)` — assert this call either panics under `debug_assertions` (proving the panic path) or, in release mode, returns without proper accounting while task `id2`'s underlying data has already vanished before its own cancellation processed it — demonstrating the broken reference count invariant across both build configurations.

	fn do_unrequest_preimage(hash: &T::Hash) -> DispatchResult {
		Self::do_ensure_updated(&hash);
		match RequestStatusFor::<T>::get(hash).ok_or(Error::<T>::NotRequested)? {
			RequestStatus::Requested { mut count, maybe_len, maybe_ticket } if count > 1 => {
				count.saturating_dec();
				RequestStatusFor::<T>::insert(
					hash,
					RequestStatus::Requested { maybe_ticket, count, maybe_len },
				);
			},
			RequestStatus::Requested { count, maybe_len, maybe_ticket } => {
				debug_assert!(count == 1, "preimage request counter at zero?");
				match (maybe_len, maybe_ticket) {
					// Preimage was never noted.
					(None, _) => RequestStatusFor::<T>::remove(hash),
					// Preimage was noted without owner - just remove it.
					(Some(len), None) => {
						Self::remove(hash, len);
						RequestStatusFor::<T>::remove(hash);
						Self::deposit_event(Event::Cleared { hash: *hash });
					},
					// Preimage was noted with owner - move to unrequested so they can get refund.
					(Some(len), Some(ticket)) => {
						RequestStatusFor::<T>::insert(
							hash,
							RequestStatus::Unrequested { ticket, len },
						);
					},
				}
			},
			RequestStatus::Unrequested { .. } => return Err(Error::<T>::NotRequested.into()),
		}
		Ok(())
	}
