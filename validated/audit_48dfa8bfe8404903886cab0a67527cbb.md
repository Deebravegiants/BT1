### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers. `Registry.process` nonetheless uses `request.shop` as the tenant identity and `request.topic` to pick the handler, breaking the binding `HMAC-covered-bytes == data acted upon`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the body is signable. `Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 
Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-controlled HTTP headers with no cryptographic tie to the body or to each other: [3](#0-2) 
`Registry.process` validates the HMAC and then immediately trusts `request.topic` (to select the handler) and `request.shop` (as the tenant identity passed into the handler) without any check that these headers were ever part of what Shopify signed: [4](#0-3) 

Because the app's webhook secret (`Context.api_secret_key`) is shared across every shop that installs the app — it is not per-shop — any merchant who installs the app (including an attacker who installs it on their own store) receives genuinely-signed webhook deliveries for their own shop. That attacker can capture one such `(raw_body, hmac)` pair from their own store's webhook traffic, then replay the identical body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header. `HmacValidator.validate` still returns `true` because the signature only ever covered the body, and `Registry.process` will happily dispatch the handler with `data.shop` set to the attacker-chosen shop domain.

### Impact Explanation
This is a High-severity scope/identity-binding bypass: the equality the code should enforce — "HMAC-verified bytes == the shop/topic this webhook is attributed to" — does not hold. An app that keys any tenant-scoped side effect (writing data, invalidating caches, updating internal records, revoking access, etc.) off `WebhookMetadata#shop` inside its handler can be made to perform that action against a victim shop's identity using a signature the attacker legitimately obtained for their own shop, i.e. cross-tenant confusion driven entirely by this gem's webhook verification contract.

### Likelihood Explanation
Requires only that the attacker install the target app on a shop they control (a normal, low-privilege action for any public/unlisted Shopify app) and be able to POST arbitrary headers to the app's public webhook endpoint — no access token, `client_secret`, or privileged credentials needed. The bug is deterministic and requires no timing tricks, since `to_signable_string` never includes the headers at all.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them to the body/signature) in the material verified in `Utils::HmacValidator.validate`, or have `Registry.process` independently verify that the `shop-domain` header matches an expected/allow-listed shop for the topic before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimately HMAC-signed webhook (e.g. `orders/create`) to the app's endpoint, with body `B` and header `X-Shopify-Hmac-Sha256: H`, computed with the app's shared `client_secret`.
3. Attacker intercepts/replays this exact request to the same endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to perform the webhook side effect under the victim's tenant identity despite the payload originating from the attacker's own shop.
