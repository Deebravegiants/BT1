### Title
Webhook HMAC validation covers only the raw body, allowing shop and topic header spoofing to cause cross-tenant webhook processing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then blindly trusts the `shop-domain` and `topic` HTTP headers — which are not covered by that signature — to decide which shop and which handler receive the payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is derived purely from the `x-shopify-hmac-sha256` header: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`, i.e., the raw body — it never incorporates `shop`, `topic`, `webhook_id`, or `api_version`: [2](#0-1) 

`Registry.process` uses the *unverified* `request.topic` to select a handler and the *unverified* `request.shop` as the tenant identity handed to the handler, immediately after the body-only HMAC check succeeds: [3](#0-2) 

The identity binding this breaks is: `shop authenticated by Shopify's signature` should equal `shop the handler is told the data belongs to`. Here, the signature only proves "this raw body was produced with the app's `api_secret_key`" — it says nothing about which shop or topic the body is associated with. An attacker who legitimately controls any shop with the app installed can capture a valid `(raw_body, hmac)` pair from one of their own real webhook deliveries (Shopify signs it with the app's real secret), then replay that exact body/HMAC to the app's public webhook endpoint while substituting arbitrary `x-shopify-shop-domain` and `x-shopify-topic` headers. Because those headers are outside the signed material, the replay still passes `HmacValidator.validate`, and `Registry.process` dispatches the attacker-supplied body to any registered handler under a victim shop's identity.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem allows an unprivileged app-installer (who only needs their own webhook subscription, not the victim's credentials or the app's secret) to make the host application believe attacker-controlled data originated from an arbitrary other shop. Depending on how host apps use `WebhookMetadata#shop`/`#topic` (e.g., `app/uninstalled` to deactivate a shop's session, `customers/redact`/`shop/redact` GDPR handlers to delete data, or order/product sync logic keyed by `shop`), this can be leveraged to trigger destructive or data-corrupting actions against a shop the attacker does not own — a cross-tenant access impact.

### Likelihood Explanation
Any developer or bad-actor merchant can install the target app on a shop they control, capture one legitimate webhook delivery (a valid raw-body/HMAC pair signed with the app's real `api_secret_key`), and replay it with forged `shop-domain`/`topic` headers to the app's public webhook endpoint. No access to the victim's credentials, the app's `client_secret`, or any privileged position is required — only the ability to send an HTTP POST, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Bind the shop (and ideally the topic) into the material that is cryptographically verified, or otherwise re-derive shop identity from a source outside attacker control. Concretely, `Registry.process` (and any downstream host-application logic) should treat `request.shop` and `request.topic` as untrusted unless cross-checked against an independent authoritative record (e.g., confirm the shop has an active, matching session/installation, and that the specific `webhook_id` hasn't already been processed for a different shop). At minimum, document prominently that `shop`/`topic` headers are unauthenticated and must never be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `app/uninstalled`) and capture the raw POST body plus the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because Shopify signed it with the real `api_secret_key`.
2. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
3. `Utils::HmacValidator.validate` succeeds because it only recomputes the signature over the raw body (`lib/shopify_api/utils/hmac_validator.rb#L27-L31`, `lib/shopify_api/webhooks/request.rb#L36-L38`).
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: <attacker body>, ...)` (`lib/shopify_api/webhooks/registry.rb#L188-L199`), causing the host app to act on victim-shop's tenant record using attacker-supplied data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
