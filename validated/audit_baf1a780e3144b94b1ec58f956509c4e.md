## Title
Webhook shop/topic identity spoofing due to unsigned headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` only includes the raw request body in the HMAC-signed payload used for authentication, while the `shop` (tenant identity) and `topic` (dispatch routing) values are read from HTTP headers that are never covered by that signature. Because a single app-level `client_secret`/`api_secret_key` is used to sign webhooks for *every* shop that has the app installed, any shop owner who receives a legitimately-signed webhook for their own store can replay that exact body with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header, and the validator will still accept it as authentic — even though it's now attributed to a different tenant.

which delegates to `Utils::HmacValidator.validate(request)`. The signable string used for computing/verifying the HMAC is defined as: [2](#0-1) 

That is, only `@raw_body` is signed. However, the tenant identity (`shop`) and dispatch key (`topic`) that the app relies on to route and attribute the webhook are pulled straight from unauthenticated headers: [3](#0-2) 

`Registry.process` then uses `request.topic` to select the handler and passes `request.shop` directly into `WebhookMetadata`, which the documented usage pattern uses as the tenant key for downstream processing (e.g. enqueuing per-shop jobs): [4](#0-3) 

`HmacValidator.validate` computes the signature using `Context.api_secret_key`, which is the **app's single, shared client secret**, not a shop-specific key: [5](#0-4) 

This breaks the intended identity binding: `hmac_valid(body) == true` should imply `shop == the shop that actually sent this event`, but because `shop` (and `topic`) are excluded from `to_signable_string`, the equality `authenticated_bytes == bytes_used_for_tenant_attribution` does not hold. Since the same secret validates webhooks for all shops on the app, a value of `shop` header is fully attacker-controllable while `hmac_valid` still returns true.

### Impact Explanation
This is a cross-tenant identity confusion: a user who runs their own store and has installed the vulnerable app (an ordinary, unprivileged action — no special credentials required) can capture one of their own legitimately-signed webhook deliveries and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop (and/or the `topic` header rewritten to another registered topic). The HMAC check still passes because it only verifies `raw_body`, so the app processes attacker-supplied body content as if it originated from — and belongs to — the victim tenant. Depending on how the host app's `WebhookHandler#handle` uses `data.shop`/`data.topic` (as documented, e.g. `shop_domain: data.shop` for job queuing or record lookups), this can lead to data being written under, deleted from, or otherwise associated with a shop the attacker does not control, which is a cross-tenant boundary violation.

### Likelihood Explanation
Any developer using this gem exactly as documented (single endpoint dispatching by `data.topic`/`data.shop`, per the example in `docs/usage/webhooks.md`) is affected. Any user who can install the target app on any shop (which is normal, unprivileged app-installation flow) can generate an arbitrary number of validly-HMAC-signed request bodies at will and replay them with modified shop/topic headers. No secret material, session, or elevated privilege is needed beyond ordinary app installation.

### Recommendation
Bind the `shop` and `topic` values into the signed payload (or otherwise cryptographically bind them to the signature) instead of trusting the corresponding HTTP headers unconditionally. At minimum, `to_signable_string` should incorporate the shop domain and topic so that `HmacValidator.validate` fails if either is tampered with, restoring the equality between the authenticated bytes and the bytes used to determine tenant/topic dispatch. Alternatively, apps should be made to verify that the resolved `shop` corresponds to a shop with an active session/installation for the specific webhook `webhook_id`, rather than trusting the header value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - Body: `{"id": 123, ...}`
3. Attacker captures this request and replays it to the same endpoint, changing only the headers:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - (optionally) `X-Shopify-Topic: customers/data_request`
   - Body and `X-Shopify-Hmac-Sha256` unchanged.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only — identical to step 2 — and returns `true`.
5. `Registry.process` dispatches to the handler for the (possibly attacker-chosen) topic with `shop: "victim-shop.myshopify.com"`, even though the request never originated from Shopify for that shop, resulting in the app processing forged data under the victim's tenant identity.
