### Title
Front-runnable `Initialize2` pool creation via market-only PDA derivation permanently blocks legitimate AMM pool creation - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives every pool-defining PDA (`target_orders`, `lp_mint`, `coin_vault`, `pc_vault`, `amm_info`) solely from `program_id` and the caller-supplied `market` account key plus a fixed literal seed, with no dependency on the coin/pc mints, the initializer's wallet, or any other value chosen by the legitimate pool creator. Because the `market` account of an OpenBook/Serum market is public knowledge before a Raydium pool is created for it, any unprivileged party can front-run a legitimate `Initialize2` transaction by submitting their own `Initialize2` for the same `market` account first (using arbitrary/attacker-chosen mint accounts and dust amounts), permanently occupying those deterministic addresses and causing every subsequent legitimate attempt to create the intended pool for that market to revert.

### Finding Description
The address of each pool-critical account is computed by `get_associated_address_and_bump_seed`, seeded only by `program_id` and `market_address`: [1](#0-0) 

`process_initialize2` uses this helper to create `amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`, and `amm_info` all keyed by the `market_info` account and a hard-coded seed suffix: [2](#0-1) 

The three account-creation helpers only reject re-use of these accounts with `AmmError::RepeatCreateAmm` if the account is not still owned by the system program - i.e., once *any* caller has successfully created these accounts for a given `market`, no other caller (including the intended, legitimate pool creator) can ever create them again: [3](#0-2) [4](#0-3) 

Because the derivation includes neither the `coin_mint`/`pc_mint` nor the `user_wallet_info` submitting the transaction, an attacker only needs to know the public `market` pubkey (visible on-chain or in the legitimate creator's pending transaction) to compute identical addresses and beat the legitimate transaction to the chain with their own `Initialize2` call using different (even worthless) mints and a tiny `init_coin_amount`/`init_pc_amount` (only constrained by `InitLpAmountTooLess` and non-zero vault balance checks): [5](#0-4) [6](#0-5) 

This is the same bug class as the reported `DKIMRecoverySigValidator` issue: a state-changing call keyed by attacker-guessable/public parameters (there, the `recoveries` mapping keyed by `accountAddress`; here, the deterministic PDA set keyed only by `market`) can be pre-empted by any party observing the pending transaction, causing the legitimate caller's transaction to permanently fail a "already done"/"already in use" style check (`RepeatCreateAmm`, `AlreadyInUse`).

### Impact Explanation
Once an attacker's `Initialize2` lands first for a given `market`, the legitimate project/LP can never create the intended Raydium pool for that market again — the PDAs are permanently owned/initialized and every future `Initialize2` attempt for that market reverts with `RepeatCreateAmm`/`AlreadyInUse`. This is a permanent denial of the pool-creation functionality for that market (mirroring the "recovery functionality won't be usable" impact of the source report), and in practice results in an attacker-controlled pool (arbitrary, potentially worthless mints, arbitrary initial price ratio, attacker as sole first LP) permanently squatting the address space that legitimate liquidity would have used, which can also be leveraged to mislead users who trust the on-chain market-to-pool binding.

### Likelihood Explanation
Likelihood is high: no privileged role or precondition is required. Any party monitoring the mempool/pending transactions (or simply front-running any known upcoming pool launch for a known market) can construct and submit their own `Initialize2` instruction with the same `market` account and higher priority fee, requiring only ownership of two mint accounts and negligible token amounts.

### Recommendation
Bind the derived pool PDAs (and/or add an explicit check) to values that only the legitimate initializer controls and that cannot be pre-empted — e.g., include the `user_wallet_info` (creator) or a creator-chosen nonce/salt in the seed derivation instead of relying solely on the publicly known `market` key, or require the `market`-to-pool binding to be reserved/whitelisted via a privileged/config-gated instruction before permissionless `Initialize2` calls are accepted for it.

### Proof of Concept
1. Legitimate creator prepares an `Initialize2` transaction for `market M` with real mints `A`/`B` and real initial liquidity amounts, and broadcasts it.
2. Attacker observes the pending transaction (or simply knows `market M` will be used, since it is public before pool creation), reads `market_info.key = M`, and computes the same PDAs via `get_associated_address_and_bump_seed(program_id, M, <seed>, program_id)` as done in `program/src/processor.rs:747-814`.
3. Attacker submits their own `Initialize2` for `market M` with attacker-owned dummy mints and minimal `init_coin_amount`/`init_pc_amount` satisfying only `amm_coin_vault.amount != 0` and the `InitLpAmountTooLess` check, with higher priority fee so it lands first.
4. Attacker's transaction succeeds: `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` see the target addresses still owned by the system program and create them, permanently assigning `amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`, `amm_info` to the program for `market M`.
5. The legitimate creator's original transaction subsequently executes (or is resubmitted) and reverts with `AmmError::RepeatCreateAmm` at `program/src/processor.rs:380` / `program/src/processor.rs:543`, permanently preventing the intended pool for `market M` from ever being created through this program.
