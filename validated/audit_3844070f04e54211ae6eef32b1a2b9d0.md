## Analysis: Multisig Timelock Bypass via Pre-existing Stale `creation_time_secs`

The external report's core custody invariant is: **a freshness/liveness gate must be evaluated against the true elapsed time since the last authoritative update, not against timestamps that predate the introduction of the gate itself.** I traced this invariant into the custom `MultisigAccountTimeLock` feature added to `multisig_account.move`, which is not present in stock Aptos framework and controls execution authority over a multisig-held custody account (APT, FAs, resource-account/code-object control can all be routed through a multisig).

### Title
Multisig timelock provides no protection for pending transactions predating its configuration - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`MultisigAccountTimeLock` is meant to force a waiting period between reaching quorum approvals and actual execution of a multisig transaction, giving other owners time to detect and reject a malicious/compromised-owner-proposed transaction. However, the elapsed-time check is computed from `MultisigTransaction.creation_time_secs`, which is fixed at transaction-creation time and never re-baselined. If a timelock is added (or its period shortened) *after* a transaction has already been pending long enough, the transaction is treated as if it had already "served" the lock period and can execute immediately once quorum is met — defeating the very protection the timelock was added to provide.

### Finding Description
`MultisigTransaction` stores an immutable `creation_time_secs` set once at proposal time: [1](#0-0) 

The timelock config is a separate, independently-addable resource: [2](#0-1) 

The gate itself: [3](#0-2) 

and it is invoked directly in the VM-called validation path that authorizes execution of the underlying transaction against the multisig-controlled account: [4](#0-3) 

Because `elapsed = now_seconds() - pending_transaction.creation_time_secs` uses a timestamp fixed before the timelock existed (or before it was tightened), any transaction whose age already exceeds the newly configured `timelock_period` is granted `elapsed >= timelock == true` on the very next check — with zero additional waiting. There is no mechanism visible in the code I inspected that re-baselines `creation_time_secs`, rejects/flushes pending transactions, or otherwise excludes already-pending transactions when a `MultisigAccountTimeLock` is added or shortened.

### Impact Explanation
A multisig can hold arbitrary custody-grade value: APT, fungible-asset stores, resource-account signer capabilities, and code-object upgrade authority. The intended security model is: if owners suspect a signer is compromised or a proposed transaction is malicious, they add/shorten a timelock to buy time to reject it via `reject_transaction`/`execute_rejected_transaction`. This finding shows that safety measure is silently inert for any transaction older than the configured period — the compromised-owner transaction can be pushed through by gathering quorum immediately after the timelock is installed, with no delay at all. This is a direct authority/asset-control bypass on a live custody mechanism (Impact: High/Critical, since it defeats the sole recovery/reaction window against a malicious pending multisig transaction).

### Likelihood Explanation
Likelihood is Medium-High: `MAX_PENDING_TRANSACTIONS = 20` and no time bound on how long a transaction may sit pending means an attacker (or attacker-influenced owner) can create a malicious transaction early and simply wait/slow-walk approvals until honest owners react by adding a timelock — at which point the "protection" has already expired for that specific transaction. This does not require any privileged access beyond normal owner rights already assumed for multisig participation, and the timing condition (transaction age > configured timelock period) is easily engineered by an owner controlling proposal timing. [5](#0-4) 

### Recommendation
When a `MultisigAccountTimeLock` is added or its `timelock_period` is decreased, re-baseline `creation_time_secs` for all currently pending transactions (e.g. set to `now_seconds()`), or track a separate "timelock effective from" timestamp and require `elapsed = now_seconds() - max(creation_time_secs, timelock_installed_at)`. Alternatively, disallow enabling/shortening a timelock while pending transactions exist, forcing them to be resolved (executed or rejected) under the old rules first.

### Proof of Concept
1. Owner A (malicious or compromised) creates a multisig transaction (`create_transaction`) that would drain the multisig's APT/FA balance or reassign resource-account/code-object control, at time `T0`. No timelock exists yet, so it can sit pending indefinitely without alarming other owners (only 1 of `num_signatures_required` votes so far).
2. Days later (`T0 + timelock_period + 1`), honest owners notice suspicious activity and add a `MultisigAccountTimeLock` with `timelock_period` (e.g. 24h) specifically intending to force a cooling-off window on any future execution attempts.
3. Owner A quickly gathers the remaining approvals to reach quorum on the still-pending transaction from step 1.
4. `validate_multisig_transaction` invokes `can_execute_with_timelock`, computing `elapsed = now_seconds() - creation_time_secs`, which is already `>= timelock_period` because `creation_time_secs = T0` predates the timelock's installation. Execution proceeds immediately — the intended 24h delay never applies.

```text
    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
```
