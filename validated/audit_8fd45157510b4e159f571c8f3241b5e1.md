### Title
Webhook shop/topic identity is unauthenticated even though `HmacValidator.validate` passes — object verified ≠ object acted on - (File: `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`HmacValidator.compute_signature` only ever signs the string returned by `to_signable_string`. For `ShopifyAPI::Auth::Oauth::AuthQuery` this string includes every field later used (`code`, `host`, `shop`, `state`, `timestamp`), so the OAuth path has no coverage gap. For `ShopifyAPI::Webhooks::Request`, however, `to_signable_string` returns only `@raw_body`, while `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are read straight from unauthenticated HTTP headers and are handed to the webhook handler as if they were verified.

### Finding Description
The invariant the question asks to check is: *every value acted on downstream must be inside the string handed to `HmacValidator` via `to_signable_string`.* This holds for `AuthQuery#to_signable_string` [1](#0-0)  but is broken for `Webhooks::Request#to_signable_string`, which returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from `@headers` [3](#0-2) .

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received hmac [4](#0-3) . It never touches `shop`, `topic`, or `webhook_id`. `Registry.process` calls `Utils::HmacValidator.validate(request)`, and immediately afterward trusts `request.shop` and `request.topic` to build `WebhookMetadata` dispatched to the app's handler [5](#0-4) .

Exploit flow:
1. Attacker installs the target app on their own (free/dev) shop. Because the app's `api_secret_key` is a single per-app secret shared across every installing shop, the attacker legitimately receives a webhook: raw body `B` and a valid `X-Shopify-Hmac-Sha256` header `H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays `B`/`H` unchanged to the app's webhook endpoint, but forges `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`, `X-Shopify-Webhook-Id`).
3. `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and compares it to `H` — this still matches, because `to_signable_string` never includes the shop/topic headers.
4. `Registry.process` treats the request as authentic and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: parsed(B), ...)`.

No existing guard closes this gap: `ShopValidator.sanitize!`, `state` comparison, `JwtPayload`'s `aud` check, and `Context.setup?/private?/embedded?` are all specific to the OAuth/session-token paths and are never invoked on webhook `shop`/`topic`. The webhook signature check only proves "this body was HMAC'd with the app secret at some point," not "this body belongs to this shop/topic."

### Impact Explanation
Any handler logic keyed on `WebhookMetadata#shop` or `#topic` (e.g., looking up/updating per-merchant state, deciding what data to expose or delete) can be triggered for an arbitrary victim shop domain chosen entirely by the attacker, using only a webhook body the attacker legitimately obtained for their own shop. This is a cross-tenant authentication bypass: the app believes it received an authentic message from "victim-shop.myshopify.com" when it did not. It is fully repeatable — the attacker can pick any shop domain string per request and is not limited to shops they have any relationship with.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: create a free development store, install the target app (standard, unprivileged action), trigger any webhook topic the app subscribes to, capture the resulting `(raw_body, hmac)` pair, then send it directly to the app's public webhook endpoint with a forged `shop-domain`/`topic` header. No secret, access token, or victim interaction is required. This is a Critical-class, low-cost, highly repeatable path.

### Recommendation
Include the values that are subsequently trusted/acted upon inside the signed material, or otherwise bind them cryptographically to the verified body — e.g., require `Webhooks::Request#to_signable_string` (or a new verification step) to incorporate `shop`, `topic`, and `webhook_id`, or independently validate that the `shop-domain` header corresponds to a session known to have installed the app before dispatching to the handler.

### Proof of Concept
```ruby
# test/webhooks/request_test.rb (additional case)
def test_hmac_does_not_cover_shop_or_topic_headers
  raw_body = '{"id":1}'
  hmac = Base64.encode64(
    OpenSSL::HMAC.digest("sha256", ShopifyAPI::Context.api_secret_key, raw_body)
  ).strip

  legit_headers = {
    "x-shopify-hmac-sha256" => hmac,
    "x-shopify-topic" => "orders/create",
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
    "x-shopify-api-version" => "2023-10",
    "x-shopify-webhook-id" => "abc",
  }
  forged_headers = legit_headers.merge(
    "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  )

  legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: legit_headers)
  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

  # Same body + same hmac => validator can't tell them apart
  assert(ShopifyAPI::Utils::HmacValidator.validate(legit_request))
  assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))

  # But downstream identity diverges from what was verified
  refute_equal(legit_request.shop, forged_request.shop)
  assert_equal("victim-shop.myshopify.com", forged_request.shop)
end

def test_validate_rejects_malformed_hmac
  refute(ShopifyAPI::Utils::HmacValidator.validate_signature_stub_with_empty_hmac) # false for empty-string hmac
  refute(ShopifyAPI::Utils::HmacValidator.validate_signature_stub_with_wrong_length_hmac) # false for wrong-length digest
end
```
This demonstrates the broken binding directly: `to_signable_string` (the object verified) is identical for both requests, while `request.shop` (the object subsequently acted on via `Registry.process` → `WebhookMetadata`) differs and is fully attacker-controlled.
