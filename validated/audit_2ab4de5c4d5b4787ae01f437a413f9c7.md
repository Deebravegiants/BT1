Audit Report

## Title
CORS wildcard origin allowlist bypass via unanchored hostname suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
The gateway's user-facing HTTP server reflects the request's `Origin` header into `Access-Control-Allow-Origin` whenever `isAllowedOrigin` returns true. For wildcard-configured entries (`*.example.com`), the match is performed with `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, with no check that the character preceding the suffix in `originHost` is a dot, allowing suffix-colliding domains like `evilremix.com` to match `remix.com`.

## Finding Description
`isAllowedOrigin` splits both the incoming `Origin` header and each configured `CORSAllowedOrigins` entry into scheme/host/port. For a wildcard allowlist entry such as `https://*.remix.com`, the code strips `*.` to get `remix.com` and then performs a bare suffix comparison: `strings.HasSuffix(originHost, allowedHost)`. This lacks dot-boundary anchoring (it should check `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)`), so any domain that merely ends with the allowed suffix (e.g., `evilremix.com`, `notremix.com`) incorrectly satisfies the wildcard match despite not being a true subdomain of the allowed host. No other check in `handleRequest` compensates for this before the origin is reflected into the CORS header.

## Impact Explanation
When `CORSEnabled = true` and a wildcard entry is configured — a documented, supported pattern exercised in the test suite — an attacker who registers a domain ending in the same suffix can host a malicious page there. A victim visiting that page causes their browser to send a cross-origin request to the gateway; `isAllowedOrigin` incorrectly returns true, and the server reflects `Access-Control-Allow-Origin` for the attacker's origin. This allows the attacker-controlled origin to read cross-origin JSON-RPC responses from the gateway's user-facing endpoint (which forwards JWT-bearer requests to `ProcessRequest`), constituting an allowlist bypass leading to cross-origin response disclosure.

## Likelihood Explanation
Exploitation requires only a normal supported configuration (`CORSEnabled = true` with a wildcard entry in `CORSAllowedOrigins`) and an attacker capable of registering a suffix-colliding domain and luring a victim's browser to it. No privileged, host, or peer-level access is needed on the attacker's side; this is a purely client/browser-triggerable CORS logic flaw.

## Recommendation
Anchor the wildcard suffix check on a dot boundary:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```

## Proof of Concept
1. Configure the gateway user server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. Send a request to the gateway user endpoint with header `Origin: https://evilremix.com`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilremix.com`, confirming `strings.HasSuffix("evilremix.com", "remix.com")` incorrectly returns `true` at `core/services/gateway/network/httpserver.go:187`.
4. This can be codified as a Go unit test extending `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` with origin `https://evilremix.com` against allowed origin `https://*.remix.com`, asserting the header is (incorrectly) set.
