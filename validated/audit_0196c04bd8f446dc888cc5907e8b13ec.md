## Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing via HMAC replay — (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies nothing but the raw JSON payload bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers are read directly from attacker-controllable request headers and are never mixed into the signed string, yet `Registry.process` trusts `request.shop` as the tenant identity passed to the app's handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` implement `Utils::VerifiableQuery`: [1](#0-0) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all values pulled straight from headers — as authoritative for dispatch and for the metadata handed to the app's webhook handler: [2](#0-1) 

`Utils::HmacValidator.validate` only computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`: [3](#0-2) 

Because `to_signable_string` is just `@raw_body`, the equality the gem actually proves is:
`HMAC(client_secret, raw_body) == received_hmac`

but the equality the code *treats as proven* (and hands to the host app) is:
`(raw_body, shop, topic, webhook_id) came together from Shopify for this shop`

These are not the same binding. The `client_secret` is shared across every shop that installs the app (it is not per-tenant), so any two webhook deliveries for the same app — regardless of which shop triggered them — that happen to carry identical `raw_body` bytes will carry the *same valid HMAC*. An attacker does not need the `client_secret` at all: they only need to be an unprivileged merchant who can install the app on their own shop and trigger a webhook whose body is attacker-controlled or predictable (e.g. a `products/create` webhook where the JSON body reflects fields the merchant fully controls, or any webhook topic with a small/fixed body shape). They capture the genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sent for their own shop, then replay that exact body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header set to a victim shop. `HmacValidator.validate` still passes (it never looked at the shop header), and `Registry.process` calls the handler with `shop: <victim-shop>`, causing the host application to attribute/store/act on that data as if it originated from the victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to the host application: “HMAC valid” is documented/used as the signal that the *entire webhook request* (including which shop it's for) is authentic. Any host app that keys per-tenant side effects (creating/updating records, firing tenant-scoped business logic, writing audit logs, invalidating caches, etc.) off `WebhookMetadata#shop` as returned by this gem is exposed to cross-tenant data injection/attribution from a single unprivileged merchant account — no `api_secret_key`, access token, or victim credentials are required. This matches the Critical "cross-tenant access" impact category, since one tenant can force the app to process fabricated data under another tenant's identity.

### Likelihood Explanation
Reaching this requires only: (1) being any merchant capable of installing the app (a normal, unprivileged install flow), (2) triggering at least one webhook delivery whose body content is attacker-influenced or foreseeable, and (3) sending a raw HTTP POST with a forged shop header to the app's public webhook endpoint. No secret material, no interception, no privileged access is needed — this is a pure identity-binding gap in `Request#to_signable_string`, so likelihood is high for any topic where body content is attacker-controlled or has low entropy/duplicated shape across shops (e.g. minimal payload topics, or topics where the merchant fully controls the created resource's fields).

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the signed material (or otherwise validate them out-of-band, e.g. by cross-checking `request.shop` against a known/registered shop for the delivered `webhook_id`/subscription before dispatch), instead of relying solely on `HMAC(raw_body)`. At minimum, `to_signable_string` should incorporate the shop-domain header so a valid HMAC cannot be replayed across different `X-Shopify-Shop-Domain` values, closing the gap between what is cryptographically proven and what `Registry.process` treats as authenticated.

### Proof of Concept
1. App installs on `attacker.myshopify.com` and `victim.myshopify.com` (same `client_secret` used for both, as is standard for public Shopify apps).
2. Attacker triggers a webhook (e.g., `products/create`) on their own shop with a body they fully control/predict, and captures the legitimate `raw_body` and `X-Shopify-Hmac-Sha256` header Shopify sends to the app's webhook endpoint.
3. Attacker replays an HTTP POST to the same webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` at [4](#0-3) 
returns `true` because only `raw_body` is signed/verified.
5. `Registry.process` dispatches `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"`, even though Shopify never sent this payload for that shop — demonstrating the cross-tenant identity-binding break.
