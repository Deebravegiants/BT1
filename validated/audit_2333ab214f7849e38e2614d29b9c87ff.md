## Custody Pivot Analysis

The external BendDAO finding reduces to one invariant: **a forced, bot/permissionless-triggered repayment or distribution flow must not depend on a step that the counterparty can unilaterally and irrevocably block, because Move-style atomic execution means one party's blocked step reverts value-transfer for everyone else in the same call.**

I evaluated several Aptos-native candidates:
1. `dispatchable_fungible_asset` withdraw/deposit hooks blocking forced transfers — discarded: the hook is registered by the **metadata creator** at FA-creation time via `ConstructorRef`, not by the store owner/borrower, and protocols hold a `TransferRef` that is designed to bypass frozen/dispatch checks entirely [1](#0-0) . A borrower cannot install or revoke a hook on someone else's FA metadata, so this doesn't reproduce the "counterparty revokes approval" pattern.
2. `object::transfer_with_ref`/`LinearTransferRef` escrow (marketplace listing) — discarded: object transfer via `TransferRef` only checks the object's *owner field* at generation time, it does not depend on a revocable external approval from the current owner.
3. **`staking_contract::distribute_internal` / `vesting::distribute` permissionless batch payout loop** — kept as strongest candidate below.

### Title
Unprivileged shareholder can permanently block `distribute()`/`distribute_internal()` payouts to all other shareholders in a staking/vesting pool - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute` (and the analogous `vesting::distribute`) is a permissionless, bot-callable function that iterates over **all** shareholders of a distribution pool and pays each of them via `aptos_account::deposit_coins` in a single atomic transaction. Any account can unilaterally set `DirectTransferConfig.allow_arbitrary_coin_transfers = false` on itself (via `aptos_account::set_allow_direct_coin_transfers`) and avoid registering a `CoinStore<AptosCoin>`. If that account is (or becomes) one of the shareholders in a staking contract or vesting contract, every future call to `distribute`/`distribute_internal` will abort at that shareholder's `deposit_coins` call, reverting the whole transaction and blocking distribution of unlocked stake/rewards to **every other legitimate shareholder** of that pool, not just the malicious one.

### Finding Description
`distribute_internal` withdraws the pool's total withdrawable coins in one shot, then loops with `while (distribution_pool.shareholders_count() > 0)`, redeeming shares and calling `aptos_account::deposit_coins(recipient, ...)` for each shareholder until the pool is empty [2](#0-1) .

`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the recipient is not registered for the coin type and has opted out of direct transfers: [3](#0-2) .

Whether an account accepts direct transfers is controlled entirely by that account's own, unprivileged `DirectTransferConfig`, which any signer can flip at will [4](#0-3) .

Because the withdrawal of the pool's total inactive+pending_inactive stake happens **before** the payout loop (`stake::withdraw_with_cap`), and because Move aborts are atomic (no partial-success/skip-on-failure semantics), a single malicious/uncooperative shareholder converts an unrecoverable revert into a permanent inability to call `distribute` for the entire pool — there is no code path in `distribute_internal`/`update_distribution_pool` that removes, skips, or force-settles an individual shareholder independently of the others. The identical pattern exists in `vesting::distribute`, which loops `shareholders.for_each_ref` calling `aptos_account::deposit_coins` per shareholder within one atomic transaction [5](#0-4) .

### Impact Explanation
This blocks custody-relevant value: unlocked APT stake and accrued rewards held by the resource-account-controlled stake pool (`staking_contract`) or vesting grant pool become permanently non-distributable to all honest shareholders once one shareholder grief-configures their own account. Since the withdraw-from-stake-pool step already executed before the loop, the withdrawn coins are stuck mid-flight inside the aborted transaction context each time `distribute` is retried, and there is no alternate recovery function that bypasses the shareholder loop to rescue the other parties' funds. This matches "permanent lock or non-recoverable loss of resource-account-held value" for the non-malicious shareholders.

### Likelihood Explanation
High feasibility: `set_allow_direct_coin_transfers(false)` is a normal, public, unprivileged entry function usable by any account at any time, and not registering a `CoinStore<AptosCoin>` requires no special permission either. Any staker, delegator, or vesting beneficiary can set this up in advance of being owed a distribution, and `distribute`/`vest_many`/`distribute_many` being permissionless bot-callable functions means the DoS surfaces the very first time anyone (including an automated "bot") attempts to trigger payout.

### Recommendation
Do not let one shareholder's failed deposit abort the whole distribution batch. Wrap each `aptos_account::deposit_coins` call so a failure is caught/isolated (e.g., check `coin::is_account_registered` / `can_receive_direct_coin_transfers` first and, if the recipient cannot accept a direct transfer, credit their share to an escrow/claimable balance they can pull later) rather than performing an unconditional push-transfer inside a loop that services all other shareholders atomically.

### Proof of Concept
1. Account `M` becomes (or already is) a shareholder of a `staking_contract` (staker/operator pair) or a `vesting_contract`.
2. `M` calls `aptos_account::set_allow_direct_coin_transfers(&M, false)` and never calls `coin::register<AptosCoin>`.
3. Anyone calls `staking_contract::distribute(staker, operator)` (or `vesting::distribute(contract_address)`) once unlocked stake/vested rewards exist.
4. `distribute_internal` withdraws the pool's coins, then in the payout loop reaches `M` and calls `aptos_account::deposit_coins(M, ...)`; since `M` is not registered and has disabled arbitrary transfers, this call asserts `error::permission_denied(EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS)`, aborting the entire transaction.
5. Every subsequent call to `distribute` for that same `(staker, operator)`/`vesting_contract` fails identically, permanently blocking payouts for all other shareholders as long as `M` remains a shareholder in that pool.
