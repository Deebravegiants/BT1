## Title
Unbounded-index revert on empty `body` in `onAccept` panics the ISMP module callback and can strand an in-flight request — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

## Summary
`onAccept` in `ExtrinsicIntents.sol` (and the same pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol`, `evm/src/utils/SimplexPaymaster.sol`, `evm/src/utils/VWAPOracle.sol`) reads `RequestKind(uint8(incoming.request.body[0]))` before validating that `body` is non-empty: [1](#0-0) 

If `body.length == 0`, indexing `body[0]` on a `bytes calldata` triggers a Solidity out-of-bounds panic (`0x32`), aborting the call the same way the yasm bug aborts the process on unchecked `nasm-pp.c` buffer indexing — an untrusted, attacker-influenced input drives an out-of-bounds memory access that the process cannot recover from cleanly.

## Finding Description
`onAccept` is invoked by `EvmHost`/`HandlerV2` for every incoming `PostRequest` whose `to` module id resolves to this contract, prior to any `_checkRelayer`/`_authenticate`/source check: [2](#0-1) 

`incoming.request.body` is attacker-controlled data that travels end-to-end from a relayed message: `HandlerV2.handlePostRequests` verifies the MMR membership proof of the leaf and then calls `host.dispatchIncoming(leaf.request, _msgSender())` for every request in the batch, which ultimately calls the target module's `onAccept`: [3](#0-2) 

There is no floor length check on `body` before decoding `RequestKind`. Any relayer that submits a validly-proven request (i.e., one that was genuinely dispatched on the source chain, or — depending on how liberally `to` module resolution and cross-chain dispatch permissions are enforced upstream — a request an attacker can get dispatched with an empty body) whose body is empty causes `uint8(incoming.request.body[0])` to revert with an array-index panic instead of a handled error.

This mirrors the CVE-2023-31723 class of bug: unchecked indexing into attacker-influenced buffer content causes the parser/handler to crash rather than fail gracefully.

## Impact Explanation
`HandlerV2.handlePostRequests` iterates the batch and calls `dispatchIncoming` per leaf without a try/catch visible at this call site: [4](#0-3) 

If `dispatchIncoming` does not itself wrap the module callback in a try/catch (this could not be fully confirmed from the retrieved `EvmHost.sol` excerpts — see Uncertainty below), a single malformed/empty-body leaf reverts the entire batch transaction, reverting delivery for every other (legitimate) request bundled in the same MMR-multiproof batch. This is a "route unable to deliver messages" condition for the whole batch: relayers are incentivized to keep resubmitting, but the same panic recurs deterministically, effectively bricking delivery of that batch until it is manually split — a real liveness/DoS impact on the message-delivery path, consistent with Medium severity (matching the CVE's own CVSS 5.5, "Medium").

## Likelihood Explanation
Reaching `onAccept` requires only that a request destined for this module id be included in a verified proof; the crashing input (`body.length == 0`) requires no signature forgery, no compromised keys, and no special privilege — any party able to get a zero-length-body `PostRequest` proven and delivered (whether a misbehaving/buggy source dispatcher, a cross-chain relay bug, or a scenario where `to`-module-id collision routes an unrelated empty-body request here) triggers it. The check is missing uniformly across four separate contracts using the identical unguarded pattern, indicating a systemic gap rather than an isolated oversight.

## Recommendation
Add an explicit length guard before indexing `body[0]` in every occurrence of this pattern (`ExtrinsicIntents.sol`, `IntentGatewayV2.sol`, `SimplexPaymaster.sol`, `VWAPOracle.sol`):
```solidity
if (incoming.request.body.length == 0) revert InvalidRequestBody();
RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
```
Additionally verify (or add, if absent) that `HandlerV2.handlePostRequests`/`dispatchIncoming` isolates each module's `onAccept` call in a try/catch so that one module's malformed input cannot revert delivery of unrelated requests in the same batch — mirroring the isolation pattern already used for cross-chain callback delivery in `HyperbridgeLzEndpoint.sol`'s `onAccept` (`try ILayerZeroReceiver(...).lzReceive(...)`), which explicitly documents *"does not revert `onAccept`"* as the design goal: [5](#0-4) 

## Proof of Concept
1. Craft (or obtain via a legitimate-looking but empty-body dispatch on the source chain) a `PostRequest` whose `to` resolves to `ExtrinsicIntentsV2`'s module id and whose `body` is empty (`0x`).
2. Get this request included and proven in a `PostRequestMessage` batch delivered to `HandlerV2.handlePostRequests`.
3. `handlePostRequests` verifies the MMR multiproof successfully (proof validity is independent of `body` content) and calls `host.dispatchIncoming(leaf.request, _msgSender())`.
4. `ExtrinsicIntentsV2.onAccept` executes `RequestKind(uint8(incoming.request.body[0]))` on the empty `body`, causing a Solidity array-out-of-bounds panic.
5. If `dispatchIncoming` does not isolate module reverts (unverified from indexed code), the panic propagates up through `handlePostRequests`, reverting the whole batch transaction and denying delivery to every other request bundled with it.

**Uncertainty**: I could not confirm from the retrieved code whether `EvmHost.dispatchIncoming` wraps the module's `onAccept` call in a try/catch (only its declaration/call sites were surfaced, not its body). If it does isolate per-request failures, the impact is reduced to "this single request can never be delivered" (a permanent freeze of that specific in-flight request/its associated fee) rather than a whole-batch DoS — still a valid, if narrower, "route unable to deliver messages" finding for the affected request. Confirming `dispatchIncoming`'s exact error-handling requires reading its full body in `evm/src/core/EvmHost.sol`, which was not available in the indexed excerpts.
