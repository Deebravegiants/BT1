### Title
Missing minimum LP-token (shares) output slippage check in `process_deposit` - (File: `program/src/processor.rs`)

### Summary
The `Deposit` instruction lets a depositor bound the input token amounts (`max_coin_amount`, `max_pc_amount`) and optionally bound the *other-side* input amount via `other_amount_min`, but there is no field, and no check anywhere in `process_deposit`, that bounds the number of LP tokens (`mint_lp_amount`) the depositor actually receives. This is the exact analog of the C4 finding for `ERC4626DepositOnly`: a caller can specify inputs but has no way to guarantee a minimum "shares" output, so the on-chain state at execution time (which can be moved by an intervening swap in the same slot/leader window) can silently give the depositor fewer LP tokens than they intended for the tokens they deposit.

### Finding Description
`DepositInstruction` only carries: [1](#0-0) 

`other_amount_min` is only ever compared against `deduct_pc_amount`/`deduct_coin_amount` (the *other input token* amount), never against `mint_lp_amount`: [2](#0-1) [3](#0-2) 

`mint_lp_amount` is computed from the live pool reserves (`total_coin_without_take_pnl` / `total_pc_without_take_pnl`, themselves derived from vault balances and PnL) via `InvariantPool::exchange_token_to_pool`, and is minted to the user with no lower bound check whatsoever before `Invokers::token_transfer`/mint calls at the end of `process_deposit`. Because the pool reserves used for this ratio are read at instruction-execution time (not locked to values the client observed when building the transaction), any transaction landing before the deposit in the same block/slot that changes `amm_coin_vault.amount`/`amm_pc_vault.amount` (e.g., a large swap via `SwapBaseIn`/`SwapBaseOut`, which is unprivileged and reachable by any account) changes the coin/pc-to-LP ratio and therefore `mint_lp_amount`, with no on-chain mechanism for the depositor to revert if the resulting LP amount is less than expected.

This contrasts with `process_withdraw`, which does support optional `min_coin_amount`/`min_pc_amount` bounds on the assets returned for burned LP: [4](#0-3) 

and with the swap instructions, which enforce `minimum_amount_out` / `max_amount_in` unconditionally. `Deposit` is the only unprivileged, fund-moving instruction in the program lacking any way to bound its "shares" (LP) output — directly mirroring the reported `ERC4626DepositOnly.deposit`/`mint` gap where `shares`/`assets` outputs could differ from what the caller expected with no revert path.

### Impact Explanation
A depositor (LP) can receive materially fewer LP tokens than expected for the coin/pc tokens they transfer in, if pool reserves shift between transaction construction and execution (e.g., due to a sandwiching swap or natural trading activity in the same slot). Because minting is irreversible within the instruction and there is no minimum-LP check, the depositor's capital is diluted/misallocated with no recourse — a direct value-loss to an unprivileged liquidity provider, matching the "Medium" severity class used for the original finding (loss of expected token amount, no protocol insolvency).

### Likelihood Explanation
`Deposit` accounts and data are fully attacker/user chosen in a single transaction; no privileged signer is required. Any party (including a searcher) can submit a swap that shifts `amm_coin_vault`/`amm_pc_vault` balances immediately before a pending deposit lands, or reserves can simply move due to ordinary concurrent trading, both of which are realistic and require no special access — the same low-friction precondition noted as valid ("acknowledged") in the original report.

### Recommendation
Add an explicit minimum LP-output field (e.g., `min_lp_amount: Option<u64>`) to `DepositInstruction`, and after computing `mint_lp_amount` in `process_deposit`, revert with `AmmError::ExceededSlippage` if `mint_lp_amount < min_lp_amount` (analogous to the existing `other_amount_min` and the `Withdraw` instruction's `min_coin_amount`/`min_pc_amount` checks). This closes the gap without changing behavior for callers that don't need the extra guard (field can remain optional, mirroring existing instruction design).

### Proof of Concept
1. Pool has reserves `total_coin`, `total_pc`, and `lp_amount` LP supply.
2. Alice builds a `Deposit` instruction with `base_side = 0`, `max_coin_amount = C`, `max_pc_amount = P`, expecting `mint_lp_amount ≈ C / total_coin * lp_amount`.
3. Before Alice's transaction lands, a swap (`SwapBaseIn`/`SwapBaseOut`) executes against the same pool, changing `amm_coin_vault.amount`/`amm_pc_vault.amount` and thus `total_coin_without_take_pnl` used in `process_deposit`'s `InvariantPool` calculation at lines 1244-1250.
4. Alice's deposit still succeeds (her `other_amount_min`, if set, only bounds `deduct_pc_amount`, not `mint_lp_amount`), but `mint_lp_amount` is now computed against the shifted reserves and is lower than what Alice expected when she built the transaction.
5. Alice has no on-chain mechanism to have the instruction revert on this outcome, and permanently receives fewer LP tokens for the same coin/pc contribution.
