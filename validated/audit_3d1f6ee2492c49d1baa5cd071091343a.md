Confirmed: `WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches the cross-chain message using the **user-supplied `params.amount`**, without measuring the actual balance change received by the contract. This is the exact bug class from the report — the same repo's `IntentGatewayV2.placeOrder()` was explicitly hardened against fee-on-transfer tokens (measuring `balanceOf` before/after and mutating the recorded amount), but `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` were not.

### Title
Fee-on-transfer/deflationary ERC20 underlying causes reserve depletion in `WrappedHyperFungibleToken` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` and the upgradeable variant both lock the `_underlying` ERC20 via `safeTransferFrom` using the caller-supplied `params.amount`, but never verify how much the contract actually received. The full user-specified `params.amount` is then encoded into the cross-chain `Message` and dispatched, so the destination chain will unlock/mint that same nominal amount regardless of any transfer fee taken by the underlying token.

### Finding Description
In `send()`, tokens are pulled with `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` [1](#0-0) , and the dispatched `Message.amount` is set directly to `params.amount` in `_buildDispatchPost` [2](#0-1) . There is no `balanceOf` before/after check, unlike `IntentGatewayV2.placeOrder()` in the same codebase, which explicitly guards against this by recording `balBefore`/`balAfter` and mutating the accounted amount to the actual received value for exactly this reason [3](#0-2) . On `onAccept`, the destination-chain contract releases the underlying token to the beneficiary using `message.amount` (the full nominal amount) via `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` [4](#0-3) . If `_underlying` is a fee-on-transfer or rebasing/deflationary token, the source-chain contract's actual reserve increases by less than `params.amount` while the corresponding destination-chain deployment is instructed to release the full `params.amount`. The identical pattern exists in `WrappedHyperFungibleTokenUpgradeable.send()`/`onAccept()` [5](#0-4) .

### Impact Explanation
Each such transfer under-collateralizes the wrapper's locked reserve relative to what is claimed for release across all chains where this token is registered. Because the wrapper is a shared multi-chain locking contract (any user can call `send()` for arbitrary registered destinations), repeated use with a fee-on-transfer underlying progressively drains the aggregate locked balance until legitimate `onAccept`/`onPostRequestTimeout` unlocks on other chains cannot be fully honored — i.e. permanent freezing/loss of funds for other users of the same wrapped-token deployment, reachable by any unprivileged caller who simply calls `send()`.

### Likelihood Explanation
Likelihood depends on whether an underlying token registered via `configure()` charges a transfer fee. This is plausible in practice: `_underlying` is any owner-configured ERC20 (deflationary/fee-on-transfer/rebasing tokens exist and are commonly wrapped by bridges), and no validation prevents such tokens from being configured. The same repository's `IntentGatewayV2` contract was specifically fixed and tested for this exact scenario (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, etc.) [6](#0-5) , confirming the project treats fee-on-transfer tokens as an in-scope threat model, yet the fix was not applied to `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`.

### Recommendation
In `send()`, measure `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call, and use the actual delta as the amount encoded into the dispatched `Message` (and emitted in `Sent`), mirroring the pattern already used in `IntentGatewayV2.placeOrder()` [3](#0-2) . Apply the same fix to `WrappedHyperFungibleTokenUpgradeable`.

### Proof of Concept
1. Owner calls `configure()` on `WrappedHyperFungibleToken` with `_underlying` set to a token that charges e.g. a 1% fee on `transferFrom` (fee burned or redirected elsewhere), such as the `FeeOnTransferToken` test helper already present in the repo's test suite [7](#0-6) .
2. User A calls `send({amount: 1000e18, ...})`. The contract's actual balance increases by only `990e18`, but the dispatched `Message.amount` is `1000e18`.
3. On the destination chain, `onAccept` releases `1000e18` of the underlying to the beneficiary (or credits mint of equivalent value) — 10e18 more than was actually locked on the source chain.
4. Repeating this drains the source-chain reserve relative to outstanding destination-chain claims, so a later legitimate `onAccept`/`onPostRequestTimeout` unlock for a different user reverts or cannot be fully paid out due to insufficient underlying balance.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
