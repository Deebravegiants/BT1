### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the unauthenticated `shop`, `topic`, `api_version`, and `webhook_id` header values to build the `WebhookMetadata` that is handed to the app's `WebhookHandler`. Because the `shop` field the handler acts on is never part of the signed payload, any actor who can obtain one validly-signed webhook body (e.g., by installing the app on their own store and receiving a legitimate webhook) can replay that exact body to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to a victim shop. The HMAC check still passes because it never examined the shop header, so the app processes attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, independent of the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and the app's single, shared `api_secret_key` — the same secret used for every shop that has installed the app: [3](#0-2) 

`Registry.process` then relies on this HMAC check as the sole authentication gate, and immediately trusts `request.shop` (the unauthenticated header) to construct the `WebhookMetadata` passed to the app-supplied handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated string that the handler is expected to use as the tenant identifier for any subsequent lookup, write, or authorization decision: [5](#0-4) 

**Root cause / broken binding:** the identity binding the gem is supposed to enforce is *"shop claimed in the request == shop that was actually authenticated by the signature."* Here the equality that actually holds is only `HMAC(body, api_secret_key) == received_hmac`; the `shop` header is disjoint from that equation. Since `api_secret_key` is a single app-wide secret (not per-shop), any tenant that has legitimately installed the app can obtain a validly-signed body/HMAC pair for their own webhooks, then re-send that exact body with a different `shop` header value. `Registry.process` cannot distinguish this from a genuine webhook for the spoofed shop, because the field it uses to select the tenant (`shop`) was never bound into the signature it verified. This is the same bug class as the HackerOne report: a boundary/identity check (`remove_symlinks!`'s regex, there; the shop-domain header here) that looks like a completeness guarantee but does not actually bind the field that downstream code trusts, allowing an attacker with limited/legitimate access (their own store's webhook feed, there their own tarball import) to make the system act on data attributed to a different tenant.

### Impact Explanation
This breaks the tenant isolation boundary: a malicious merchant/attacker who has installed the target app on their own Shopify store can forge webhook deliveries that the application will process as belonging to any other shop of their choosing (since `shop` is attacker-controlled and not authenticated). Depending on how the host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up a database row, update a subscription, revoke access, or trigger mandatory GDPR redaction flows for `shop/redact`/`customers/redact`), this can lead to cross-tenant data corruption, cross-tenant deletion/redaction of another merchant's data, or other actions being performed against a victim tenant that the attacker does not control. This qualifies as Critical — cross-tenant access, per the specified impact categories.

### Likelihood Explanation
Likelihood is high for any unprivileged party who can install the app (a normal, unprivileged flow for any public/embedded Shopify app) — no `api_secret_key`, access token, or privileged account is required. The attacker only needs to receive one webhook for their own store (trivial — install the app, trigger the relevant business event) and replay its body with a modified shop-domain header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the authenticated payload rather than trusting an unauthenticated header:
- Extract the shop domain from the signed webhook body payload (Shopify webhook JSON payloads typically include shop-identifying fields inside the body, e.g. via GraphQL ID or the `X-Shopify-Shop-Domain` value corroborated against body content) instead of (or in addition to) the header, and reject the request if the header-derived shop does not match a shop-scoped value verifiable within the signed body.
- At minimum, document/require host applications to independently verify that the shop present in `WebhookMetadata` corresponds to a shop that has an active, previously-established installation/session before performing any tenant-scoped action, and provide the gem-level primitive to do so rather than leaving `shop` fully unauthenticated.
- Longer term, incorporate the shop domain into the HMAC signable content (as `AuthQuery#to_signable_string` does for the OAuth callback) if/when the Shopify webhook signature scheme supports it, so `HmacValidator.validate` can enforce shop-binding directly.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store, `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one webhook HTTP request, e.g. for `customers/redact`, with body `B` and header `x-shopify-hmac-sha256` = `HMAC-SHA256(api_secret_key, B)` (valid, matches `HmacValidator.compute_signature` at `lib/shopify_api/utils/hmac_validator.rb:34-40`).
3. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header successfully (`lib/shopify_api/webhooks/request.rb:45-63`); `HmacValidator.validate` succeeds because it only checks the (unchanged) body against the (unchanged, valid) HMAC (`lib/shopify_api/utils/hmac_validator.rb:13-22`).
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler, which performs shop-scoped work (e.g., redaction/deletion) against the victim tenant, even though no authenticated evidence ties this request to that shop.
