Confirmed: the `Request#shop` field is passed through to the app's `WebhookHandler` as an authoritative tenant identifier, but `Request#to_signable_string` only covers `@raw_body` — the `shopify-shop-domain` / `x-shopify-shop-domain` header is never part of the HMAC-signed material.

### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from an HTTP header that is excluded from the HMAC signature computation. `Registry.process` validates only the HMAC over the raw body and then hands the handler a `WebhookMetadata` struct whose `shop` field comes straight from that unauthenticated header, breaking the binding: `shop delivered to handler == shop covered by HMAC`.

### Finding Description
`Utils::HmacValidator.validate` computes/verifies the signature using `verifiable_query.to_signable_string`, and for webhooks that method returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` unchanged to the app's handler as the trusted tenant identity: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further verification, and `WebhookHandler#handle` receives it as-is: [4](#0-3) 

Because the app's per-secret HMAC (`Context.api_secret_key`) is shared across all shops installing the app, and only the body bytes are authenticated, an attacker who legitimately installs the app on their own shop can obtain a validly-signed webhook (valid `hmac` over a chosen/predictable `@raw_body`), then replay that exact request while rewriting only the unauthenticated `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds because the header is not part of `to_signable_string`, and the handler will process the request believing it originates from the victim's shop — an equality break of `shop authenticated-by-HMAC == shop trusted-by-handler`.

### Impact Explanation
This crosses a tenant boundary: any handler logic that keys persistence, authorization, or side effects (e.g., updating a merchant record, triggering redaction/data actions, associating body content with `data.shop`) off `WebhookMetadata#shop` can be tricked into operating on a shop the attacker does not control, using only a validly-signed webhook body they legitimately obtained for their own store. This matches the Critical bucket of cross-tenant access, since the shop-scoping identity used to route/attribute webhook effects is forgeable by an unprivileged app-installing user.

### Likelihood Explanation
Any developer using this gem can install the app on a shop they control, capture one legitimately-delivered, validly-HMAC'd webhook, and replay it with a modified shop-domain header — no access to `api_secret_key` is required. The attack only requires the ability to send arbitrary HTTP requests to the app's webhook endpoint, which is inherent to how `Registry.process` is invoked from host frameworks.

### Recommendation
Do not trust `Request#shop` as an authenticated value on its own. Bind the shop identity into the verified material — e.g., have `Utils::HmacValidator` (or a new signable representation) validate the header-derived tuple `(shop, topic, webhook_id, raw_body)` rather than `raw_body` alone, or require callers to independently confirm `request.shop` against a shop-scoped webhook registration/session before acting on `WebhookMetadata#shop`. At minimum, document prominently that `shop` is unauthenticated and callers must verify shop identity out-of-band (e.g., via the app's own multi-tenant session store) before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers a webhook handler for a topic the attacker can trigger, e.g. `orders/create`.
2. Shopify delivers the webhook to the app's endpoint with real headers including `x-shopify-hmac-sha256` (valid for the raw body) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this full HTTP request (headers + raw body).
4. Attacker replays the identical raw body and `x-shopify-hmac-sha256` value, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `shop` is `"victim.myshopify.com"`.
6. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) — this matches, since the body and HMAC were untouched.
7. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` and performs shop-scoped effects for `victim.myshopify.com`, even though the request never actually originated from Shopify for that shop.
