### Title
Tron `IntentGatewayV2.placeOrder` Permanently Locks Overpaid Native Tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` collects `msg.value` to fund native-token order inputs and, when `order.fees > 0`, to swap for the fee token via Uniswap V2. Unlike the canonical EVM implementation, it never returns leftover `msgValue` to the caller after these debits, so any native token sent in excess of what is actually consumed by the order inputs/fee-swap is silently retained by the contract with no recovery path.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol`, `placeOrder` tracks a running `msgValue` local variable as it debits native-token inputs and fee-swap costs, and explicitly refunds any remainder at the end: [1](#0-0) 

The Tron port, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the identical flow — debiting `msgValue` for native inputs and for the Uniswap fee swap — but the function ends immediately after crediting escrow and emitting `OrderPlaced`, with no equivalent refund step: [2](#0-1) 

Compare the native-input debit logic, which only checks `msgValue >= order.inputs[i].amount` (an inequality, analogous to the audited `paidOnly()`/`paymentProvided()` pattern) and decrements the tracked remainder without ever paying it back: [3](#0-2) 

and the fee-swap branch, which spends only what the swap needs (`swapETHForExactTokens`) but keeps whatever ETH remains sitting on the contract instead of returning it to `msg.sender`: [4](#0-3) 

This is a structural regression relative to `evm/src/apps/IntentGatewayV2.sol`, which was specifically hardened against this class of bug (see the dedicated `NATIVE TOKEN OVERPAYMENT REFUND TESTS` in the EVM test suite): [5](#0-4) 

### Impact Explanation
Any user who calls `placeOrder` on the Tron gateway with `msg.value` greater than the exact sum required for native-token inputs plus the fee-swap cost has the excess permanently trapped in the contract. There is no `sweepDust`/withdrawal path reachable by the depositor for this stranded native balance from within `placeOrder`, `fillOrder`, or `cancelOrder` — it is not tracked against any order commitment, so it can never be attributed back to the user. This constitutes a concrete, permanent loss of user funds (a single unprivileged transaction is sufficient to trigger it), matching the severity bar for "permanent freezing of funds."

### Likelihood Explanation
Overpayment is a common, plausible user/integrator error: dApps quoting native gas plus a buffer, wallets rounding up `msg.value`, or fee estimates changing between quote and execution (e.g., the Uniswap swap consuming less than the full `msg.value` sent) will all trigger this path. Because the check is `msgValue >= requiredAmount` rather than an exact match with refund, no revert protects the user — the transaction succeeds and silently forfeits the excess.

### Recommendation
Mirror the EVM implementation: after all native-token debits (input escrow and the fee-token swap), refund any remaining `msgValue` to `msg.sender`, e.g.
```solidity
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```
placed at the end of `placeOrder` right before `emit OrderPlaced`, consistent with `evm/src/apps/IntentGatewayV2.sol#L394-397`. Audit `fillOrder`/other payable entry points in the Tron contract for the same missing-refund pattern.

### Proof of Concept
1. User calls `placeOrder{value: inputAmount + overpayment}(order, graffiti)` on the Tron `IntentGatewayV2`, where `order.inputs[0]` is a native-token (`address(0)`) input of `inputAmount` and `order.fees == 0` (or fees consuming less than the extra sent).
2. Inside `placeOrder`, the native-input loop at `evm/tron/contracts/apps/IntentGatewayV2.sol#L450-469` checks `msgValue >= order.inputs[i].amount`, passes, and decrements `msgValue -= order.inputs[i].amount`, leaving `msgValue == overpayment`.
3. No fee branch is entered (or the Uniswap swap consumes less than the leftover), so `msgValue` remains `> 0`.
4. Execution reaches the end of the function and emits `OrderPlaced` without ever transferring the leftover `overpayment` back to `msg.sender` — contrast with the refund step present in the EVM analog at `evm/src/apps/IntentGatewayV2.sol#L394-397`.
5. `overpayment` is now stuck in the contract's native balance, not credited to `_orders[commitment]` for any token, and unrecoverable by the user through any subsequent `fillOrder`/`cancelOrder` call.

    function testPlaceOrder_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1 ether;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(0), amount: inputAmount}); // native ETH

        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userBalBefore = user.balance;

        vm.prank(user);
        intentGateway.placeOrder{value: inputAmount + overpayment}(order, bytes32(0));
