## Title
Webhook shop-domain spoofing enables cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop` value taken from an **unsigned** header to identify which tenant the webhook belongs to. Because the `shop-domain` header is never included in the HMAC-signed material, any party who can obtain one validly-signed `(body, hmac)` pair for the app (e.g. by installing the app on their own, freely-created development store) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header, and the library will accept it as an authentic webhook "from" the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines the signable material as only the raw HTTP body: [1](#0-0) 

The `shop` accessor, by contrast, is read straight from an HTTP header with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` (i.e. the raw body for webhooks) and compares it to the supplied `hmac`: [3](#0-2) 

`Registry.process` performs authentication and tenant identification as two separate, unlinked steps: it validates the HMAC of the body, then immediately trusts `request.shop` (the unsigned header) to build the `WebhookMetadata` that is handed to the app's own webhook handler: [4](#0-3) 

The equality the library implicitly promises to the host application is:
`hmac_valid(body, hmac) == true` implies `(body, shop)` genuinely originated from `shop`.

In reality the library only proves `hmac_valid(body, hmac) == true` implies `body` was signed by the app's `api_secret_key` at some point, for **some** shop that has the app installed — it says nothing about which shop. Since the app's `api_secret_key`/webhook-signing secret is shared across every shop that installs the app, and the signature never includes the shop domain, `shop` is a value an attacker can freely choose independent of the signature check.

### Impact Explanation
Any unprivileged internet user can install the target app on a store they control (e.g., a free Shopify development/partner store) and thereby receive genuinely HMAC-signed webhook deliveries for arbitrary topics/bodies of their choosing (they control their own store's data, e.g. product/order content, and can create/update/delete records to shape the webhook body). They can then capture a `(raw_body, x-shopify-hmac-sha256)` pair and replay it to the app's webhook endpoint with `x-shopify-shop-domain` set to any victim shop domain. `Registry.process` will accept it, because `HmacValidator.validate` only checks the body signature, and will invoke the app's webhook handler believing the event came from the victim shop. Depending on how the host application uses `WebhookMetadata#shop` (commonly used to look up the tenant record, update per-shop state, or process GDPR-type events), this breaks the shop-to-request identity binding and enables cross-tenant impersonation/data corruption without ever needing the victim's or the app's credentials.

### Likelihood Explanation
Exploitation requires no privileged access, no leaked secrets, and no interaction with the app's `api_secret_key`: an attacker only needs the ability to install the app on their own store (which is generally self-service for any Shopify user/developer) and the ability to send an arbitrary HTTP request with attacker-controlled headers to the app's public webhook endpoint. This is squarely an "unprivileged internet user" scenario as scoped by the analog rules.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) values in the HMAC-signable string for `ShopifyAPI::Webhooks::Request`, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted in `Registry.process`/`WebhookMetadata`. At minimum, document prominently that `request.shop` is unauthenticated and must not be used by consuming applications to resolve tenant-specific secrets or authorization without additional verification (e.g., cross-checking against a shop that is known to have this webhook subscription registered).

### Proof of Concept
1. Attacker registers/installs the target Shopify app on their own store `attacker.myshopify.com` (freely obtainable).
2. Attacker triggers a webhook topic they control the payload for, e.g. `products/update`, and captures the resulting HTTP request Shopify sends to the app, including the raw body and the `x-shopify-hmac-sha256` header. This HMAC is valid because it was computed by Shopify using the app's shared `api_secret_key` over that exact body.
3. Attacker resends that exact captured request to the app's webhook endpoint, but changes `x-shopify-shop-domain` (or `shopify-shop-domain`) to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-derives the signature from `@raw_body` — unaffected by the header change:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
5. The app's handler executes believing the event is authentically from `victim-shop.myshopify.com`, using attacker-controlled body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
