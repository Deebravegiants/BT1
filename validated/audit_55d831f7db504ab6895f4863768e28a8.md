### Title
Unbounded per-owner limiter tenant creation via unauthenticated vault secret identifier fields - ([File: core/capabilities/vault/validator.go])

### Summary
`GatewayVaultRequestProcessor.ProcessRequest` explicitly runs `ValidateStructureBeforeAuth` (via `RequestValidator.ValidateEncryptedSecretsStructure`) *before* `AuthorizeRequest` [1](#0-0) . That pre-auth path calls `validateWriteRequest`, which unconditionally invokes `r.ValidateSecretIdentifier(ctx, req.Id.Key, req.Id.Owner, req.Id.Namespace)` for every item in the batch, regardless of the `includeCiphertextSize` flag that gates the (already-fixed) ciphertext check [2](#0-1) . `MaxIdentifierKeyLengthLimiter`, `MaxIdentifierOwnerLengthLimiter`, and `MaxIdentifierNamespaceLengthLimiter` are owner-scoped `BoundLimiter`s that key off `contexts.CREValue(ctx).Owner`, as proven by the owner-override tests [3](#0-2) . This is the identical owner-scoped-limiter tenant-registration pattern that the codebase explicitly says "spawns a persistent background updater" and must never be reached pre-auth, per the comment and regression tests protecting the ciphertext limiter [4](#0-3) [5](#0-4) .

### Finding Description
The ciphertext-size limiter was deliberately excluded from the pre-auth structure-validation path (`ValidateEncryptedSecretsStructure`) specifically because checking an owner-scoped `BoundLimiter` registers a persistent per-owner tenant (with its own background updater goroutine) the first time that owner is seen — and an unauthenticated caller can supply an arbitrary, attacker-chosen `owner` string in the request body [6](#0-5) . However, `validateWriteRequest` still unconditionally calls `ValidateSecretIdentifier` for every secret in the batch before this exclusion takes effect, and that function checks the identifier length against `MaxIdentifierKeyLengthLimiter`, `MaxIdentifierOwnerLengthLimiter`, and `MaxIdentifierNamespaceLengthLimiter` — limiters of the exact same owner-scoped, tenant-spawning class, as demonstrated by `ownerOverrideLimiter` tests that key on `contexts.CREValue(ctx).Owner` [7](#0-6) [8](#0-7) .

Because `ValidateEncryptedSecretsStructure` runs prior to `AuthorizeRequest` in the gateway pipeline [1](#0-0) , any unauthenticated client can submit a `CreateSecrets`/`UpdateSecrets` JSON-RPC request with a batch of secrets whose `Id.Owner`, `Id.Key`, and `Id.Namespace` fields are unique, attacker-chosen strings. Each unique owner value reaching `ValidateSecretIdentifier` causes the scoped identifier limiters to register a brand-new tenant (and spawn its background updater goroutine) — this is functionally the same "unbounded resource growth through a normal, reachable API operation, not properly torn down/deduplicated" bug class as the ic-stable-structures BTreeMap node leak, except the "leaked node" here is a per-owner limiter tenant plus its goroutine, and the API surface reachable by an unprivileged/unauthenticated actor is the gateway vault write RPC.

### Impact Explanation
An unauthenticated actor able to reach the vault gateway RPC endpoint can drive unbounded creation of per-owner limiter tenants and their background updater goroutines by varying the `owner` (and `key`/`namespace`) fields on failed/pending `CreateSecrets`/`UpdateSecrets` requests, since these are checked before authorization succeeds or fails. Sustained abuse can exhaust node memory and goroutines, resulting in degraded availability or crash of the vault-processing node — a resource exhaustion impact consistent with CWE-401 and the CVSS availability-impact-only vector of the referenced advisory.

### Likelihood Explanation
The request only needs to be well-formed enough to pass basic structural checks (non-nil ID, non-empty encrypted value, valid identifier length) — it does not need to be a valid or authorized owner, nor to pass signature/label checks (which occur later/independently in `validateWriteRequest`). An attacker can automate large numbers of distinct owner/key/namespace combinations at scale with no privileged credentials, making this readily reachable and repeatable.

### Recommendation
Apply the same mitigation used for `MaxCiphertextLengthLimiter` to the identifier length limiters: split `ValidateSecretIdentifier`'s owner-scoped bound checks out of the pre-auth `ValidateEncryptedSecretsStructure` path, and only invoke them after `AuthorizeRequest` succeeds (analogous to how `ValidateCiphertextSizes` is now called post-authorization). Alternatively, make `ValidateSecretIdentifier`'s length checks non-owner-scoped (global bound) for the pre-auth structural pass, deferring owner-tenant creation entirely until the caller is authenticated.

### Proof of Concept
1. Send a `CreateSecrets`/`UpdateSecrets` JSON-RPC request to the gateway public handler (unauthenticated) containing a batch of `EncryptedSecret` entries, each with a distinct `Id.Owner` value (e.g., `owner-0001`, `owner-0002`, …), valid enough hex `EncryptedValue` and identifier lengths to pass structural checks.
2. `GatewayVaultRequestProcessor.ProcessRequest` calls `ValidateEncryptedSecretsStructure` → `validateWriteRequest` → `ValidateSecretIdentifier` for each entry before `AuthorizeRequest` is invoked [9](#0-8) .
3. Each new, unique owner value causes the owner-scoped identifier limiters to register a new tenant (and background updater goroutine), matching the behavior proven for the ciphertext limiter in `TestGatewayVaultRequestProcessor_ProcessRequest_UnauthorizedWriteNeverTouchesCiphertextLimiter` [10](#0-9)  — except no equivalent regression test exists guarding the identifier limiters from this same pre-auth exposure.
4. Repeat with a large number of distinct owners to accumulate unbounded limiter tenants/goroutines over time, since authorization is expected to (and will) fail for these bogus owners, so no cleanup/authorized-path logic runs.

		return errors.New("request ID must not be empty")
	}
	if err := r.MaxRequestBatchSizeLimiter.Check(ctx, len(encryptedSecrets)); err != nil {
		if errBoundLimited, ok := errors.AsType[limits.ErrorBoundLimited[int]](err); ok {
			return fmt.Errorf("request batch size exceeds maximum of %d: %w", errBoundLimited.Limit, err)
		}
		return fmt.Errorf("failed to check request batch size limit: %w", err)
	}
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}

		if req == nil {
			return errors.New("encrypted secret must not be nil at index " + strconv.Itoa(idx))

			return errors.New("secret ID must not be nil at index " + strconv.Itoa(idx))
