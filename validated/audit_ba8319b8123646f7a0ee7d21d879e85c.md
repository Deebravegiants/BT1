## Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, allowing tenant-spoofed webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` purely from HTTP headers, while the HMAC signature that `Registry.process` verifies is computed only over the raw request body. Because the tenant-identifying `shop` value is never part of the signed material, an attacker who can obtain any one validly-signed webhook body/HMAC pair (e.g. by triggering a webhook on their own, attacker-controlled shop) can replay it with a different `x-shopify-shop-domain` header and have the host application attribute the event to a victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from unauthenticated headers: [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e. the body only) before dispatching the handler with the header-derived `shop`: [3](#0-2) . `HmacValidator.validate_signature` computes the digest solely from `verifiable_query.to_signable_string`: [4](#0-3) .

This breaks the intended identity binding:
`HMAC-verified bytes (raw body)` **≠** `bytes used to determine the tenant (shop-domain header)`

Compare this to `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` and `host` *are* included in `to_signable_string` and therefore covered by the signature: [5](#0-4) . The webhook path lacks this equivalent protection: the `shop` header that `WebhookMetadata` (and hence the host app's handler) trusts as the tenant identifier is never authenticated by the HMAC.

### Impact Explanation
Since the tenant-scoping `shop` value handed to `handler.handle` is unauthenticated, a host application that (as documented/intended) uses `WebhookMetadata#shop` to select which tenant's data to update will process an attacker-controlled shop value under a signature that only proves "this body came from Shopify for *some* shop," not "this body came from Shopify for *this* shop." An attacker who owns a shop that has this app installed can capture a legitimately-signed webhook for their own shop and resend it with the `x-shopify-shop-domain`/`shopify-shop-domain` header swapped to a victim's shop domain, causing the host app to apply the (attacker-controlled) body's effects to the victim's tenant record — a cross-tenant access/write.

### Likelihood Explanation
The attacker only needs: (1) the app installed on a shop they control, so they can legitimately trigger a webhook and obtain a valid `(raw_body, hmac)` pair, and (2) a way to POST to the app's webhook endpoint with modified headers (trivial, since the endpoint is a public HTTP callback and the vulnerable comparison never inspects headers as part of the signed payload). No knowledge of `api_secret_key` or any credential is required — the attacker reuses a signature Shopify itself already computed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the material verified by the HMAC, or otherwise independently authenticate the `shop` header (e.g. cross-check it against the shop that owns the currently active session/credentials in the host app) before dispatching `handler.handle`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant scoping without an additional check.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers any subscribed webhook topic (e.g. `orders/create`) on their own shop and captures the raw request: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker POSTs to the host app's webhook endpoint with the same body `B` and same header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` re-computes `HMAC(secret, B)` (the signable string is only the body) and it matches `H`, so validation passes: [6](#0-5) .
4. `Registry.process` dispatches the handler with `shop: request.shop` set to `victim-shop.myshopify.com`: [7](#0-6) , causing the host app's handler to act on the victim tenant using attacker-controlled body content.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
