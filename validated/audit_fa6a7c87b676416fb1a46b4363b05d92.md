### Title
Zero-token Emporium path (`formInputEmporiumMin`) lets an attacker execute arbitrary calls from `EmporiumUpgradeable` with no balance accounting, draining any token/ETH held by the contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When a `transact()` call targets the Emporium external action with an **empty** `erc20TokenAddresses` array, `CircomDataBuilder.formInputForCircom` routes the proof through `formInputEmporiumMin`, which only requires `emporiumMessage`, `timeStamp` and `calldataHash` as public inputs [1](#0-0) . This bypasses every token/nullifier/amount check that normally binds a transaction's `deltaAmountChanges` to a real balance movement. However, `EmporiumUpgradeable.runAction` still executes the full, attacker-supplied `EmporiumOperation[]` list, including the fully unrestricted "stateless" branch that lets the Emporium contract itself call any `endpoint` with any `callData` and any `value` [2](#0-1) . Because `circomData.erc20TokenAddresses.length == 0`, the balance-equality loop that would normally detect and revert on any unaccounted-for balance change never executes at all [3](#0-2) .

### Finding Description
The balance invariant that Emporium is supposed to enforce is:
```
totalChange(token_i) = amountDepositedByHinkal(token_i) + balanceChangeFromOps(token_i)  ≥ 0
```
This is only checked for tokens present in `circomData.erc20TokenAddresses` [4](#0-3) . `HinkalHelper.dimensionsCheck` only requires `circomData.erc20TokenAddresses.length == dimensions.tokenNumber` — nothing forbids `tokenNumber == 0` [5](#0-4) , and the dedicated `formInputEmporiumMin` code path in `CircomDataBuilder` exists specifically to support `tokenNumber == 0` Emporium transactions [1](#0-0) .

An attacker who generates their own spending/nullifying key pair (no pre-existing UTXO is required for a 0-token/0-input/0-output proof) can:
1. Call `Hinkal.transact` with `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` whose `ops` array contains a stateless operation (`invokeWallet = false` or `signerAddress = address(0)`) targeting any ERC20 token the Emporium contract currently holds, with `callData = transfer(attacker, balance)`.
2. Because `circomData.erc20TokenAddresses` is empty, `runAction`'s balance-check loop at lines 132–151 never runs — there is no `balancesBefore`/`balancesAfter` comparison for that token, so any transfer performed by the op is completely unaccounted for.
3. The `bytes4(op.callData)` selector check only blocks `callHinkalWallet`/`doSendToRelay` selectors, not arbitrary ERC20 `transfer`/`approve` selectors [6](#0-5) .
4. `op.endpoint.call{value: op.value}(op.callData)` executes with `msg.sender == EmporiumUpgradeable`, so a `transfer`/`approve`+`transferFrom` call moves the Emporium contract's own held funds directly to the attacker, in the clear, with zero shielded value ever debited from the attacker.

This breaks the equality the rules describe: "value moved by ... an external action but not counted in the balance equation." Any ERC20 balance or ETH balance that legitimately or transiently ends up on the shared `EmporiumUpgradeable` contract (e.g., native ETH sent via its `receive()` [7](#0-6) , relay-fee remnants, or dust) can be drained by any unprivileged EOA capable of constructing a valid zero-token proof and a forged `EmporiumStack`.

### Impact Explanation
This is theft of protocol/relay/user funds sitting on the Emporium contract, executed without the attacker providing or spending any real backing value, and without any wallet owner or prover authorization for the actual asset movement (the token being drained is never referenced anywhere in the calldata/signed-message hash that the zk proof and EIP-712 signature commit to, since `erc20TokenAddresses` is empty). This matches the High/Critical bar: "executing calls or moving assets a wallet owner or prover never authorised" / theft of protocol funds.

### Likelihood Explanation
Likelihood is high for any funds that transiently or persistently sit on `EmporiumUpgradeable`'s own balance: the attacker only needs (a) the ability to submit a self-generated valid zk proof for the 0-token Emporium circuit variant (no pre-existing deposit needed) and (b) knowledge of a token the Emporium contract holds a balance of. Both are attacker-controlled and require no relayer, admin, or other user's key.

### Recommendation
- Reject Emporium transactions with `erc20TokenAddresses.length == 0` unless the `EmporiumOperation[]` is provably read-only / value-neutral, or
- Perform the balance snapshot/diff check over the full set of tokens actually touched by `ops` (not just `circomData.erc20TokenAddresses`), or simplest: disallow the "Stateless Interaction" branch (`op.endpoint.call` executed with `EmporiumUpgradeable` as `msg.sender`) from targeting arbitrary endpoints when `erc20TokenAddresses` is empty, and/or require `circomData.erc20TokenAddresses` to include every token referenced by `stack.ops[i].endpoint` so the balance-equation loop always covers it.
- Ensure `EmporiumUpgradeable` never accumulates any leftover balance between transactions (sweep/forbid direct transfers via `receive()`), since any resting value is now provably drainable via this path.

### Proof of Concept
1. Attacker generates an arbitrary EdDSA spending key pair (no funds needed).
2. Attacker crafts `circomData` with: `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData = { externalAddress: EmporiumUpgradeable, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{ signerAddress: address(0), ops: [ EmporiumOperation{ endpoint: VICTIM_ERC20, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, EmporiumBalanceOfVictimToken)) } ], maxFee: 0, deadline: type(uint256).max }) }`.
3. Attacker computes `calldataHash` per `CircomDataBuilder.getHashedCalldata` and generates a valid proof for the `tokenNumber = 0` circuit variant (`formInputEmporiumMin`).
4. Attacker calls `Hinkal.transact(a, b, c, dimensions{tokenNumber:0,...}, circomData)`.
5. `_externalTransact` sees `deltaAmountChanges` is an empty array (no tokens to transfer in), calls `EmporiumUpgradeable.runAction`.
6. `runAction` decodes the `EmporiumStack`, calls `verifyWallet` (trivially passes since `signerAddress == address(0)`, just marks `emporiumMessage` used), then executes the stateless op: `VICTIM_ERC20.call(transfer(attacker, amount))` directly draining the Emporium contract's token balance to the attacker.
7. The trailing loop over `circomData.erc20TokenAddresses` (length 0) never runs, so no revert occurs and no accounting objects to the drained balance.

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
