### Title
Webhook `shop-domain` identity used by handlers is not covered by the HMAC signature, allowing shop-spoofed webhook delivery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies its HMAC only over the raw request body, while the `shop` (and `topic`/`webhook_id`) values consumed by the registered `WebhookHandler` are taken directly from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` and compares it to the received `hmac` header. [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are not part of the signed string at all: [3](#0-2) [4](#0-3) 

After HMAC validation succeeds, `Registry.process` builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's handler: [1](#0-0) [5](#0-4) 

The documented usage pattern shows host applications trusting `data.shop` as the tenant identifier to dispatch/attribute webhook data (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [6](#0-5) 

The identity binding that should hold is: `shop header used by handler == shop bound by the HMAC signature`. Because `to_signable_string` only returns the raw body, this equality does not hold — the HMAC covers zero bytes of the `shop-domain`, `topic`, or `webhook-id` headers. Compare this to `Auth::Oauth::AuthQuery`, where `to_signable_string` explicitly includes `shop`, `host`, `code`, `state`, and `timestamp`, so the HMAC does bind the shop value there: [7](#0-6) 

An attacker who has legitimate access to the app's webhook secret validation pathway — i.e., any merchant who has installed the app and can therefore trigger Shopify to deliver a validly-signed webhook (signed with the app's single `api_secret_key`, which is shared across all shops/tenants using the app) — can capture a genuine signed webhook body for their own shop and replay it to the app's webhook endpoint with a forged `shop-domain` header (and/or `topic`/`webhook_id`) pointing at a different, victim shop. Since `HmacValidator.validate` never inspects headers, the forged request passes validation, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen (victim) shop domain while the body is the attacker's genuine content.

### Impact Explanation
This breaks the shop/tenant identity binding at the point the webhook payload is handed to the host application: the `shop` value handlers treat as authenticated (because it arrived after "HMAC validated" processing) is actually attacker-controlled. Any host application logic that keys per-tenant behavior off `data.shop` — looking up sessions/access tokens for that shop, writing to that shop's records, or dispatching background jobs scoped to `shop_domain` as the documented example does — can be made to act on/for the wrong tenant using data supplied by a different, potentially malicious merchant. This is a cross-tenant identity-confusion vector consistent with the "Critical - cross-tenant access" impact category, since it lets one tenant's webhook traffic impersonate another tenant's `shop` identity within the app's own webhook pipeline.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must be able to generate at least one genuinely HMAC-signed webhook body for the shared `api_secret_key` — achievable by any merchant that has installed the app (a fully unprivileged action, not requiring credential theft), since they can trigger real webhook events and capture the signed request Shopify sends to the app's endpoint. From there, replaying the same body/HMAC pair to the app's webhook URL with a modified `shop-domain` header is trivial and requires no additional secrets.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` headers into the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the payload before it is treated as trusted (e.g., include them in `to_signable_string`, or independently verify `shop-domain` against a shop the app has an active session/webhook registration for before dispatching to the handler).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and receives a legitimately signed webhook: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body computed with the app's api_secret_key>`, body `{"id":123}`.
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (both are attacker's own legitimate traffic, no secret material needed).
3. Attacker sends a new HTTP request directly to the app's webhook endpoint with the same body and same `hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only (per `to_signable_string`) — it matches, since the body was untouched. Validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` from the forged header and invokes the handler, which now processes attacker-supplied data under the victim shop's identity. [1](#0-0) [2](#0-1)
