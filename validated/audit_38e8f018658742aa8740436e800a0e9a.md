### Title
`PoaBridge.describeWithdrawal` misreports withdrawal status/txHash for multi-leg intents sharing the same PoA `assetId` - (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` matches the POA bridge's withdrawal-status response purely by `assetId`, ignoring the caller-supplied `args.index`. When an intent contains two POA withdrawal legs for the same token (e.g. `nep141:btc.omft.near`) to different `destinationAddress`/`amount`, both `describeWithdrawal({..., index: 0})` and `describeWithdrawal({..., index: 1})` resolve against the *same* array element, so both indices report identical `(status, txHash)`.

### Finding Description
The broken equality: for two withdrawal legs `w0` (index 0) and `w1` (index 1) of identical `assetId`, the expected invariant is `describeWithdrawal(w0) != describeWithdrawal(w1)` when their underlying on-chain outcomes differ, but the code makes `describeWithdrawal(w0) === describeWithdrawal(w1)`.

Root cause: `findMatchingWithdrawal` filters the POA API's `withdrawals` array only on `nep141:${w.data.near_token_id} === assetId`, and returns the first match, completely disregarding `args.index`: [1](#0-0) [2](#0-1) 

The code path is reachable by an ordinary, unprivileged NEAR Intents user: `createWithdrawalIdentifiers` assigns per-bridge-route sequential `index` values to each element of `withdrawalParams`, with no restriction preventing two elements from sharing the same `assetId`: [3](#0-2) 

`watchWithdrawal` (used by `createWithdrawalCompletionPromises`) then calls `bridge.describeWithdrawal` per leg with the assigned `index`, trusting the returned `status`/`txHash` as authoritative for that specific leg: [4](#0-3) 

Exploit flow: an attacker (or any legitimate user) builds a single intent with two POA withdrawal legs, both `assetId="nep141:btc.omft.near"`, but different `destinationAddress`/`amount` (e.g. index 0 → address A amount X, index 1 → address B amount Y). Once both complete on the POA bridge, `getWithdrawalStatus` returns two `COMPLETED` entries with distinct `transfer_tx_hash` values for the same `near_token_id`. Calling `describeWithdrawal` with `index: 0` and again with `index: 1` both invoke `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the *first* array entry both times — an integrator polling per-index (as `createWithdrawalCompletionPromises`/`watchWithdrawal` does) receives the same `(status, txHash)` for both legs, even though they are physically distinct withdrawals with distinct destinations/amounts.

None of the existing guards prevent this: `validateWithdrawal`, `compareAddresses`, and `supports()` operate per-leg on `assetId`/`destinationAddress` and do not check for duplicate `assetId` across legs of the same intent; the intents contract's own signature/nonce checks are unrelated to this off-chain status-reporting logic. The code even documents the limitation explicitly in the comment above `findMatchingWithdrawal`, confirming it is a known, unaddressed gap rather than an incidental oversight.

### Impact Explanation
The affected value is the `WithdrawalStatus` (`status`, `txHash`) returned to the integrator for a specific `WithdrawalIdentifier.index`. This is a status/hash misreport: an integrator relying on `sdk.createWithdrawalCompletionPromises`/`watchWithdrawal` to correlate a specific leg's completion with its own bookkeeping (e.g., to release/credit funds per leg) will attribute the wrong leg's `txHash` to a given index, or perceive two distinct completed withdrawals as one. This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice," and is repeatable for every intent containing 2+ legs of the same POA `assetId`.

### Likelihood Explanation
Precondition is simply constructing an intent with two (or more) withdrawal legs using the same PoA-bridge `assetId` but distinct destinations/amounts — a completely ordinary, permissionless action requiring no privileged access, special routeConfig misuse, or third-party compromise. Cost to the attacker/integrator-triggering user is a single intent with an extra leg; the divergence is deterministic once both legs are `COMPLETED` by the bridge, and it is reproducible on every poll while both legs remain in a matching state.

### Recommendation
Disambiguate withdrawals of the same `assetId` within a single NEAR tx by additional criteria available in the response (e.g., `amount`, `address`/`destinationAddress`, and stable ordering by `created`/amount as already hinted in the code comment), or track consumed matches so that each API-side withdrawal entry can only satisfy one `index` per `describeWithdrawal` call (e.g., pass already-claimed entries and exclude them from subsequent lookups for the same `tx.hash`).

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
