### Title
Webhook `shop-domain` header is trusted for tenant identification but is excluded from the HMAC-signed payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, then hands `request.shop` straight to the host application's handler as the tenant identifier. The HMAC signature, however, is computed only over the raw request body (`to_signable_string` returns `@raw_body`), never over the `X-Shopify-Shop-Domain` header that carries the tenant identity used downstream. This reproduces the report's bug class: a field that is *acted on* (used to route/identify the tenant) is not *covered by* the authentication check (the HMAC).

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; it does not include the `shop` (nor `topic`, `webhook_id`, `api_version`) header values in the signed content. Meanwhile `shop` is read straight from an attacker-controllable HTTP header: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string`: [3](#0-2) 

`Registry.process` gates on that HMAC check and then forwards `request.shop` (the unauthenticated header) directly into `WebhookMetadata` given to the host app's handler: [4](#0-3) 

Because `X-Shopify-Shop-Domain` is not bound into the HMAC, an attacker who has captured (or replays/relays) one legitimately-signed webhook body for **any** shop — e.g. from their own store, from a public webhook payload, or from a shop they control — can resend that same body with an arbitrary `X-Shopify-Shop-Domain` header (any victim's `*.myshopify.com` domain) to the app's webhook endpoint. The signature check passes because it never inspects the header, yet `data.shop` delivered to the handler is fully attacker-controlled. This breaks the binding `hmac-signed-shop == data.shop-used-by-app` (equality across authentication vs. action), analogous to the `removeCollateral`/`marketHelper` field never validated against the signed payload in the original finding.

The `docs/usage/webhooks.md` guidance and `WebhookHandler` interface confirm that host apps are expected to trust `data.shop` as the tenant key (used e.g. to route jobs "perform_later(topic: data.topic, shop_domain: data.shop, ...)"): [5](#0-4) 

Since a real HMAC signature is only ever produced by Shopify (secret is never exposed), true forgery of the body content is not possible without the app secret. But the attacker doesn't need to forge the body — they only need a validly-signed body (which they can obtain from a webhook to their own shop, or any publicly-known/replayed payload) and can pair it with a forged `shop-domain` header, since that header plays no part in the signature.

### Impact Explanation
This is a cross-tenant confusion: the app processes/attributes webhook data to a shop identity it never verified. Combined with an app that relies on `data.shop` for authorization decisions or to select the tenant's stored session/access token (as `docs/usage/webhooks.md` explicitly recommends), an attacker can cause the app to associate attacker-supplied webhook body content with a victim shop's identifier, or trigger tenant-scoped side effects (queued jobs, database writes, cache invalidation) keyed to a shop they do not own. This matches "cross-tenant access" impact criteria.

### Likelihood Explanation
Likelihood is moderate: the attacker needs one validly HMAC-signed webhook payload (trivially obtainable by installing a free/trial version of the same app on their own shop and capturing its own legitimate webhook deliveries), then simply resends the same raw body to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header value. No access token, `client_secret`, or privileged account is required — the endpoint is an unauthenticated internet-reachable POST route by design.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`/`api_version`) header values in the HMAC-signed content that `to_signable_string` returns, or otherwise cryptographically bind the shop-domain header to the signed body before trusting `request.shop` in `Registry.process`. At minimum, document that host applications must independently re-validate `data.shop` against a known/installed-shop list rather than trusting it as authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the attacker's endpoint with a valid `X-Shopify-Hmac-Sha256` for body `B` and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures raw body `B` and its valid HMAC signature (both unchanged).
4. Attacker POSTs the exact same body `B` and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `to_signable_string` (`@raw_body` only) and it matches, since the body/HMAC pair is untouched — validation succeeds.
6. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's original body>, ...)` and calls the app's handler, which now believes attacker-controlled data belongs to `victim-shop.myshopify.com`.
