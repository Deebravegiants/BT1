Webhook shop identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` fields that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler are taken unauthenticated from HTTP headers. Any party who can obtain one legitimately-signed `(body, hmac)` pair for their own shop (e.g. by installing the app on their own store and receiving a real webhook) can replay that exact pair while altering only the `shop-domain` header to name a different, victim shop. The gem's HMAC check passes because the body is unchanged, and the handler is invoked believing the body belongs to the victim shop — breaking the binding `authenticated(body) == authenticated(shop)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from (attacker-controllable, in the sense that they are just transport-layer headers not covered by cryptographic proof) headers with no binding to the signed body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the raw body, and never incorporates `shop`: [3](#0-2) 

`Registry.process` validates that HMAC and then constructs `WebhookMetadata` using the unauthenticated `request.shop`, handing it directly to the app's handler as the tenant identifier: [4](#0-3) 

`WebhookMetadata.shop` is documented and expected by consuming apps to be the trusted identifier of which merchant/tenant the webhook body belongs to: [5](#0-4) 

The binding that should hold is: `hmac_valid(body) ⇒ shop_header_is_authentic`. In reality, `hmac_valid(body)` only proves the body was signed by Shopify for *some* shop that received it (including the attacker's own shop if they've installed the app), not that it was signed for the `shop` value present in the current request's header. An attacker who legitimately receives their own signed webhook can resend the identical body+signature to the app's webhook endpoint with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header naming a victim shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): the receiving application will process attacker-controlled webhook body content while attributing it to a victim's shop, since the gem provides no way for the host app to detect the mismatch — the shop value it hands to the handler passed HMAC validation, but the HMAC didn't actually cover the shop. Depending on how the host app uses `data.shop` (e.g., looking up records, updating per-shop state, feeding data pipelines keyed by shop), this allows an unprivileged party (any merchant who can install the app) to inject data into another tenant's context.

### Likelihood Explanation
Any user able to install the app on their own Shopify store (a normal, unprivileged action) can trigger a real webhook for a topic they control (e.g. `orders/create`) and capture the resulting `(raw_body, hmac)` pair from their own endpoint. Replaying it against the app's public webhook URL with a modified shop header requires no secret knowledge and no privileged access — only the ability to install the app once and control the destination header of a replayed HTTP request.

### Recommendation
Bind the shop identity to the signed content, or otherwise cryptographically tie the header-derived `shop` to the authenticated webhook. Options:
- Include `shop-domain`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (this would require Shopify's own signing scheme to change, so as a mitigation within the gem, at minimum document/expose that these header values are unauthenticated), or
- Have `Registry.process` cross-check `request.shop` against an out-of-band trusted source before invoking handlers, or
- Warn/require host apps to independently verify shop ownership (e.g., against their own session/token store) before trusting `WebhookMetadata#shop` for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers for `orders/create`.
2. Shopify sends a legitimately HMAC-signed webhook to the app's callback endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-for-body>`, `x-shopify-topic: orders/create`
   - Body: `{"id":1,"note":"attacker payload"}`
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker resends an HTTP request to the same webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only, matches successfully.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id":1,"note":"attacker payload"}, ...)`, causing the host app to process attacker-controlled data as if it belonged to the victim shop.
