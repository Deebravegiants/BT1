### Title
Signup-extension QR code bypasses backend identity verification, allowing unauthorized/misattributed signup - (File: src/plans/mod.rs)

### Summary
The Rubicon `tailOff`/`rebalance` bug is a class of "missing validation on attacker-influenced parameters lets a normally-lower-trust actor skip a critical safety check." The reachable analog in `orb-core` is in `MasterPlan::handle_user_qr_code`, where a `signup_extension` flag/config parsed directly out of a scanned QR code (either the operator's or the user's) causes the orb to skip the mandatory backend user-identity verification path entirely and instead proceed with a `UserData::default()`.

### Finding Description
User and operator QR codes are parsed via `qr_scan::user::Data::try_parse`, which recognizes a `signup_extension` mode and an arbitrary `parameters` string encoded directly in the scanned code text (`QR_CODE_SIGNUP_EXTENSION` regex, `mode` and `parameters` fields fully attacker/operator controlled) [1](#0-0) [2](#0-1) .

In `handle_user_qr_code`, if either the operator's or the user's QR code sets `signup_extension()` and a `signup_extension_config` is present, the function short-circuits and returns success with `backend::user_status::UserData::default()` — **without ever calling `verify_user_qr_code`**, which is the function that hits the backend `/status` endpoint and performs the cryptographic `user_data.verify(user_data_hash)` check binding the QR code to a backend-issued identity commitment and public keys: [3](#0-2) 

Compare this to the normal path, which always calls `verify_user_qr_code` → `backend::user_status::request`, which requires `user_data.verify(user_data_hash)` to succeed before any `UserData` (containing `id_commitment`, `self_custody_user_public_key`, backend encryption keys) is returned: [4](#0-3) [5](#0-4) 

Just as `BathPair.tailOff` accepted an unchecked `_stratUtil` address and `BathToken.rebalance` accepted an unchecked `filledAssetToRebalance` token — letting a strategist redirect the "trusted" underlying-token transfer path — here an unchecked, QR-code-supplied `signup_extension`/`signup_extension_config` value redirects the "trusted" identity-verification path, letting the flow skip the one check (`verify_user_qr_code`/`user_data.verify`) designed to bind the physical signup session to a specific backend-validated identity.

### Impact Explanation
If this code path is reachable in a production build (i.e., the `internal-data-acquisition` feature is compiled in and enabled at runtime), any actor able to present a QR code with a `signup_extension` marker can force the orb to bypass the identity-commitment/self-custody-key verification, associating the biometric capture with `UserData::default()` (empty identity commitment, no public keys) instead of a backend-verified identity. This breaks the identity-binding guarantee the signup protocol relies on — the same class of impact as the Rubicon finding (a security-critical binding check being skippable via unchecked, caller-supplied parameters) — though the concrete blast radius here is misattributed/unauthenticated signup data rather than direct fund theft.

### Likelihood Explanation
Reachability depends entirely on whether `internal-data-acquisition` is compiled into and enabled in the production orb binary; the code is gated by `#[cfg(feature = "internal-data-acquisition")]` at the `Data::from_signup_extension`/`QR_CODE_SIGNUP_EXTENSION` level. I was not able to fully confirm from the index whether this feature ships in the production build or is dev/test-only (the tool budget ran out before I could inspect the full `Cargo.toml` feature-default list). If it is a default/production feature, likelihood is High because QR content is fully attacker-observable/craftable input at the physical scanning step; if it is strictly a developer/test-only build feature, this would fall under the "test-only paths" exclusion and the finding would not qualify.

### Recommendation
- Never skip `verify_user_qr_code`/backend validation based solely on a value parsed from the scanned QR code content. If a signup-extension mode legitimately needs to bypass full user identity verification (e.g., internal data-acquisition-only builds), gate that bypass behind a build-time-only flag that cannot be toggled by QR-code content, and never ship it in the production identity-verification code path.
- At minimum, require that `signup_extension_config`/`mode`/`parameters` be cryptographically attested by the backend (similar to `user_data_hash` verification) rather than trusted directly from unauthenticated QR text, mirroring the Rubicon fix of adding an explicit whitelist/equality check instead of trusting caller-supplied identifiers.

### Proof of Concept
1. Confirm the orb binary is built with `internal-data-acquisition` enabled.
2. Present an operator QR code (or user QR code) matching `QR_CODE_SIGNUP_EXTENSION`, e.g. `userid:<any-id>:1::0::` (mode `Basic`, no parameters), as both/either operator and user code so that `operator_data.qr_code.signup_extension()` and `user_qr_code.signup_extension()` both evaluate true, with `signup_extension_config` present on at least one side.
3. Observe in `handle_user_qr_code` [3](#0-2)  that the flow returns `Ok(Some(Some((user_qr_code, backend::user_status::UserData::default(), ...))))` immediately, never calling `verify_user_qr_code`/`backend::user_status::request`, thereby completing signup setup without the backend-issued/verified identity commitment or public keys that `UserData::verify` would normally enforce.
