### Title
Webhook `shop` field is excluded from the HMAC signature, allowing cross-tenant shop-domain spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then trusts the `shop` value taken from an unauthenticated HTTP header as the tenant identifier passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` straight to the app's handler as the tenant/`shop` field with no additional binding check: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature using the single app-wide `Context.api_secret_key` — the same secret is used to sign/verify webhooks for *every* shop that has installed the app, since a Shopify app has one `client_secret`, not one per shop: [4](#0-3) 

The identity-binding equality that should hold is: `shop_that_produced_this_valid_HMAC == shop_field_used_for_tenant_routing`. Because the signature only covers `raw_body` and the app secret is shared across all installs, this equality is never enforced. A user who is a legitimate (if malicious) merchant with the app installed on their own store can:
1. Trigger a subscribed webhook topic (e.g. `products/update`) on their own store, with body content fully under their control (e.g. product title/description fields), receiving a genuinely valid `(body, hmac)` pair signed with the app's shared secret.
2. Replay that exact `(raw_body, hmac-sha256)` pair to the app's webhook endpoint, but substitute the `shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` succeeds (it only checks that `raw_body` was signed with the app secret — true, since Shopify actually generated that signature for the attacker's own event). `Registry.process` then invokes the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled body>, ...)`.

For any host app that uses `data.shop` from `WebhookMetadata` to select the tenant record to update (the documented and expected usage pattern, exactly as shown in the gem's own webhook docs example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this results in attacker-controlled data being written into, or an action being performed against, a completely different (victim) tenant's records — a cross-tenant write/action using only the attacker's own valid, unmodified webhook body.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): an attacker with a normal, unprivileged merchant account for the app can cause the app to process a webhook body they fully control as if it belongs to a shop they do not own or operate, without ever obtaining the victim's credentials or session. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be a merchant who has installed the app (an unprivileged, self-service action for any public app) and that they can send an HTTP request directly to the app's public webhook endpoint with a modified `shop-domain` header while replaying a genuine `(body, hmac)` pair they legitimately received. No secrets, tokens, or victim interaction are needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the data that is authenticated, or independently verify that the `shop` header corresponds to a shop with an active, previously-established session/installation known to the app before dispatching to the handler, rather than trusting the header value implicitly once only body-HMAC validation has passed. At minimum, document prominently that `data.shop` from `WebhookMetadata` is not cryptographically bound to the HMAC and must be cross-checked by the host application against its own list of installed/authorized shops before being used for tenant routing.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has the app installed.
# Step 1: Attacker triggers a products/update webhook on their own shop with
# attacker-controlled body content, e.g. {"id":1,"title":"payload"} and receives
# the genuine hmac Shopify computed with the shared app secret.

attacker_body = '{"id":1,"title":"payload"}'
attacker_hmac = shopify_generated_hmac_for(attacker_body) # valid, signed by Shopify for attacker's own event

# Step 2: Attacker replays this to the app's webhook endpoint, only changing
# the shop-domain header to the victim's shop.
headers = {
  "shopify-topic" => "products/update",
  "shopify-hmac-sha256" => attacker_hmac,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: attacker_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds because it only checks attacker_body against the
#    app's shared secret. Handler receives WebhookMetadata(shop: "victim-shop...", body: attacker_body),
#    and (per documented usage) will act on "victim-shop" using attacker-controlled data.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
