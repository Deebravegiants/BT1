I found a strong analog of this readonly-reentrancy pattern in `EvmHost.sol`'s GET-response dispatch path, where a public getter (`requestCommitments`, generated from the `_requestCommitments` mapping) is relied on by relayers/off-chain tooling (`tesseract/messaging/evm/src/provider.rs::query_request_fee_metadata`) to read the pending fee for a commitment, while that same storage slot is only read/paid *after* an external call into attacker-controlled application code.

### Title
Readonly-reentrancy in `EvmHost.dispatchIncoming(GetResponse)` allows a malicious app to manipulate `requestCommitments[commitment].fee` during the `onGetResponse` callback window — (File: evm/src/core/EvmHost.sol)

### Summary
`dispatchIncoming(GetResponse, address relayer)` writes `_responseReceipts[commitment]` for replay tracking, then makes an untrusted external call to `IApp.onGetResponse` on `_bytesToAddress(response.request.from)` — an address fully controlled by whoever dispatched the original GET request — and only *after* that call returns does it read `_requestCommitments[commitment].fee` and pay it out via `safeTransfer`. [1](#0-0) 

### Finding Description
The fee metadata for a request lives in `_requestCommitments`, exposed publicly through the auto-generated `requestCommitments(bytes32)` getter, which relayer infrastructure explicitly relies on to know how much fee is owed for a commitment. [2](#0-1) 

`fundRequest` is a public, unrestricted, non-reentrancy-guarded function that increases `_requestCommitments[commitment].fee` for any known commitment, funded by pulling `feeToken` from the caller. [3](#0-2) 

In `dispatchIncoming(GetResponse memory response, address relayer)`, the call sequence is: (1) write `_responseReceipts[commitment]`, (2) external call to the attacker-supplied app (`response.request.from`), (3) *then* read `_requestCommitments[commitment].fee` and transfer it. Because the external call happens before the fee is read/paid, the callee's `onGetResponse` handler executes while the host is mid-transaction and can re-enter `fundRequest(commitment, amount)` to mutate `_requestCommitments[commitment].fee` before control returns to `dispatchIncoming`. This is the same root-cause class as the Sherlock finding: a value used for accounting is read after an external call, during which the value can be altered by the very party the call handed control to — except here the mutation is possible directly (via `fundRequest`) rather than merely "read-only," making it strictly worse than the classic readonly-reentrancy case, since the state is both mutable and load-bearing for a token payout. [4](#0-3) 

Unlike the sibling timeout-handling functions, which explicitly `delete _requestCommitments[commitment]` for replay protection before the external call, `dispatchIncoming(GetResponse,...)` never clears or snapshots `_requestCommitments[commitment]` at all — it is read fresh, post-callback, every time. [5](#0-4) 

### Impact Explanation
An app that dispatched a GET request (any contract can do this via `dispatch(DispatchGet)`) controls the `onGetResponse` callback target and thus the reentrant call. During that callback it can call `fundRequest` to top up its own commitment's fee using externally supplied `feeToken`, inflating the amount `dispatchIncoming` transfers out immediately afterward, or interleave calls that desynchronize the relayer's view of "correct fee to expect" (as read via the public `requestCommitments` getter used by relayer tooling) from what actually gets paid at settlement time. This breaks the accounting invariant that fee metadata read by external actors (relayers, indexers) accurately reflects state at the time of use, and creates a path for a malicious app to manipulate protocol fee-token balances/payouts through crafted reentrant calls into `fundRequest` from within its own callback — a fund-accounting integrity issue tied directly to relayer fee/reward accounting, which is explicitly in scope.

### Likelihood Explanation
Likelihood is High for a motivated app deployer: dispatching a GET request and implementing `onGetResponse` as a reentrant callback is fully permissionless and requires no privileged role — any of "an unprivileged message dispatcher" reachable path. `fundRequest` has no reentrancy guard and no restriction on caller, so nothing prevents it being invoked mid-callback from `dispatchIncoming`.

### Recommendation
Follow the Checks-Effects-Interactions pattern already used in the timeout functions: read (and clear/finalize) `_requestCommitments[commitment]` into a local variable *before* making the external call to the app, and use that cached value for the fee payout, e.g.:
```solidity
FeeMetadata memory meta = _requestCommitments[commitment];
delete _requestCommitments[commitment];
(bool success,) = _bytesToAddress(response.request.from).call(
    abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer))
);
if (!success) {
    delete _responseReceipts[commitment];
    _requestCommitments[commitment] = meta; // restore for retry
    return;
}
if (meta.fee != 0) {
    IERC20(feeToken()).safeTransfer(relayer, meta.fee);
}
```
Additionally, add a `nonReentrant` guard to `fundRequest` and/or to the dispatch/incoming entry points to eliminate the cross-function reentrancy vector entirely.

### Proof of Concept
1. Attacker deploys `MaliciousApp` and calls `EvmHost.dispatch(DispatchGet{...})` from it, becoming `response.request.from` for a subsequent GET response, paying an initial small `fee`.
2. Handler eventually calls `dispatchIncoming(GetResponse, relayer)`. Inside, `MaliciousApp.onGetResponse` is invoked as the external call at [6](#0-5) .
3. `onGetResponse` re-enters `EvmHost.fundRequest(commitment, largeAmount)`, pulling `largeAmount` of `feeToken` from itself (attacker-supplied) and increasing `_requestCommitments[commitment].fee` as shown at [7](#0-6) .
4. Control returns to `dispatchIncoming`, which reads the now-inflated `_requestCommitments[commitment].fee` and pays it to `relayer` at [8](#0-7) , while any off-chain component that had earlier read `requestCommitments(commitment)` (per the relayer's `query_request_fee_metadata`) observed a stale/different fee than what was ultimately charged/paid, demonstrating the read-after-external-call inconsistency.

**Note on confidence**: I could not fully trace whether `HandlerV2.sol` imposes any additional reentrancy guard at the entry point that would block step 2–3 (an outer `nonReentrant` modifier on the batch handler could mitigate this); this should be verified against `evm/src/core/HandlerV2.sol` before treating this as fully unmitigated, since indexing limits prevented me from reading its full body in this session.

        _responseReceipts[commitment] = ResponseReceipt({
