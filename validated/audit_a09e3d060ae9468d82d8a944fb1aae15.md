### Title
POA Bridge misreports withdrawal status/txHash for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
The SDK explicitly supports batch withdrawals — multiple withdrawal intents settled in one NEAR transaction, tracked individually via a `WithdrawalIdentifier.index` [1](#0-0) . For the POA bridge route, `describeWithdrawal` ignores `index` entirely and resolves the on-chain outcome purely by `assetId` via `findMatchingWithdrawal`, which returns the *first* API record whose `near_token_id` matches [2](#0-1) . If a user batches two withdrawals of the same NEP-141 token to two different destinations in a single intent, both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` calls resolve to the same underlying record, so the second withdrawal is reported with the status/`txHash` that actually belongs to the first.

### Finding Description
`PoaBridge.describeWithdrawal` fetches all withdrawals tied to the NEAR tx hash and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` [3](#0-2) . Because `.find()` returns only the first match and the lookup key is `assetId` alone (no `index`, no destination address, no amount), two batched withdrawals of the same asset in one intent are indistinguishable to this function — both resolve to whichever withdrawal record appears first in the array.

This is a known, explicitly-documented gap in the code itself:
```
NOTE: Currently only matches by assetId. This means multiple withdrawals
of the same token in a single transaction are not supported.
``` [4](#0-3) 

The same defect exists in the internal-utils helper used by `waitForWithdrawalCompletion` for the same bridge [5](#0-4) .

The equality that is broken: the `status`/`txHash` returned for withdrawal at `index=N` must equal the on-chain outcome of the transfer created for `index=N`'s specific `(destinationAddress, amount)` pair. Instead, the code substitutes the outcome of whichever same-asset withdrawal happens to be first in the API's (explicitly documented as "unsorted") response list [6](#0-5) .

This is directly reachable through the SDK's supported and documented batch-withdrawal feature — no attacker privilege is required, just a normal user (or an integrator building on the SDK) submitting two withdrawals of the same token to two different destinations in one intent via `processWithdrawal`/`signAndSendWithdrawalIntent` with an array of `WithdrawalParams` [1](#0-0) , and both legs happening to route through the POA bridge.

### Impact Explanation
Any caller (an exchange, custodial service, or other integrator using this SDK) that watches multiple same-token withdrawals in a batch via `watchWithdrawal`/`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` [7](#0-6)  can be told that withdrawal B (to destination address B) is `"completed"` with `txHash` X, where X is actually the destination transaction for withdrawal A (to destination address A). This is a status/hash misreport that can cause an integrator to:
- Credit/mark-as-settled a withdrawal to address B using a transaction that never paid address B, or
- Release funds/complete downstream accounting for two distinct withdrawal legs based on one real on-chain transfer, effectively double-crediting.

This matches the "status or hash misreport making an integrator credit or refund twice" impact category (High).

### Likelihood Explanation
This requires no adversarial input — only the ordinary, SDK-documented usage pattern of batching two withdrawals of the same asset to different destinations in one intent, and having both legs served by the POA bridge route. The bug is deterministic (not probabilistic): it triggers on every occurrence of this batch shape, and the code comments confirm the authors are aware the case is unhandled.

### Recommendation
Match withdrawals using a unique per-leg identifier instead of `assetId` alone — e.g., have the POA bridge indexer return (or the SDK correlate via) `destinationAddress` + `amount` + ordinal position, or fail closed (throw / return "pending" indefinitely) when multiple same-asset withdrawals are detected in one batch rather than silently returning a possibly-wrong match. At minimum, `findMatchingWithdrawal` should detect ambiguous matches (more than one candidate withdrawal with the same assetId in the response) and refuse to resolve rather than returning the first one via `.find()`.

### Proof of Concept
1. Submit a batch withdrawal intent with two `WithdrawalParams` entries for the same `assetId` (e.g., `nep141:usdc.omft.near`) but different `destinationAddress` values (A and B), both routed via `PoaBridge`.
2. After settlement, call `describeWithdrawal` for `index=0` (destination A) and `index=1` (destination B).
3. `findMatchingWithdrawal` looks up by `assetId` only in both calls and returns the same array entry (the first withdrawal returned by the POA API for that token) for both indices.
4. Both calls report `{status: "completed", txHash: <A's transfer hash>}`, even though B's actual transfer (with a different `transfer_tx_hash`) is never surfaced for index 1 — an integrator tracking index 1 will record the wrong destination transaction as B's completion evidence.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}
