## Title
Webhook shop-domain (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies its HMAC only over the raw request body, while the `shop` (tenant identifier), `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers and passed straight to the app's `WebhookHandler`. This breaks the equality `shop authenticated by HMAC == shop acted on by handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or the HMAC [2](#0-1) . `HmacValidator.validate` and `validate_signature` only ever check `verifiable_query.to_signable_string` against `Context.api_secret_key`/`old_api_secret_key` [3](#0-2) , so the signature check never touches the `shop`, `topic`, `webhook-id`, or `api-version` headers.

`Registry.process` raises only if the HMAC over the body is invalid [4](#0-3) ; it otherwise builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., and forwards it to the app's handler, which typically uses `data.shop` as the tenant key to persist or act on data [5](#0-4) . The gem's own documentation confirms the intended usage: `data.shop` is used as `shop_domain` when enqueuing tenant-scoped work [6](#0-5) .

Because the HMAC only signs the body, an unprivileged internet user who legitimately receives one authentic, HMAC-signed webhook for their own shop (e.g. by installing the app on a shop they control, or by intercepting any publicly-observable webhook delivery with a fixed/guessable body) can replay that exact body/HMAC pair while substituting an arbitrary value in the `shop-domain` header. `Registry.process` will still consider the HMAC valid (since the header isn't part of the signed content) and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain instead of the shop that actually produced the signature. This lets an attacker inject data attributed to a victim tenant into the host app's per-shop processing pipeline — a cross-tenant identity-binding break, matching the "field acted on but not covered by the HMAC" analog class.

### Impact Explanation
This is a cross-tenant data-integrity/identity issue: the app processes webhook payloads keyed by an unauthenticated `shop` field while believing it has cryptographically verified the whole request. Any host application that uses `data.shop` (as the shipped documentation instructs) to select the tenant record, session, or storage bucket to write to is vulnerable to cross-tenant data injection/confusion, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one validly-signed body/HMAC pair — trivially available to any developer/attacker who installs the app on their own shop (a normal, unprivileged action), since Shopify sends the same webhook types to every shop that installs the app. No access to `api_secret_key`, tokens, or victim credentials is needed; only header manipulation on a replayed HTTP request to the app's own public webhook endpoint. This is a realistic, low-effort attack path.

### Recommendation
Bind the tenant/`shop` (and ideally `topic`, `webhook_id`) to the signed content, or independently verify that the `shop` header corresponds to a shop for which this exact webhook payload/HMAC was expected (e.g., cross-check against Shopify's webhook `X-Shopify-Webhook-Id` uniqueness store per shop, or require the caller to supply/verify the shop out-of-band via a per-shop webhook secret if using per-shop secrets). At minimum, document prominently in `docs/usage/webhooks.md` that `data.shop` is derived from an unauthenticated header and must not be trusted as authenticated tenant context without additional verification (e.g., checking it against an existing installed-shop record before using it as a storage key).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a body they control/observe, receiving a valid `x-shopify-hmac-sha256` for that exact `raw_body`.
2. Attacker replays the same HTTP request to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged but rewriting `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged `shop` header [2](#0-1) ; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the HMAC [7](#0-6) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [8](#0-7)  and processes/stores the attacker's data as if it belonged to `victim.myshopify.com`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
