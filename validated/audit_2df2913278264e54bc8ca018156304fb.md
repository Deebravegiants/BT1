### Title
Webhook shop-domain and topic identity spoofing due to HMAC covering only the request body - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the `X-Shopify-Hmac-Sha256` header against the raw request **body**. The `shop-domain` and `topic` headers — which are then handed directly to the app's webhook handler as trusted identity fields — are never included in the signed material. Any user who can obtain one genuine, validly-signed webhook body (e.g. by installing the app on their own store and triggering an event) can replay that body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will report it as an authentic webhook for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely against that signable string (i.e. the body) using the app's `api_secret_key`: [2](#0-1) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then immediately forwards the *unverified* `shop` (and `topic`, `webhook_id`) headers to the registered handler as trusted metadata: [3](#0-2) 

`Request#shop` simply reads the `shop-domain` header with no cross-check against the HMAC or against `ShopValidator`: [4](#0-3) 

The identity binding that should hold is:
`shop asserted in the "shop-domain" header == shop that Shopify actually signed the webhook for`

Because the HMAC only covers the body, this equality is never enforced. Since a single app has one `api_secret_key` shared across *every* installing shop, any shop that has installed the app can generate a legitimately-signed webhook (e.g. by causing an `orders/create`-style event on their own store) and observe both the body and its valid `X-Shopify-Hmac-Sha256` value. That attacker-controlled tenant can then POST the same body/HMAC pair to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain (and/or the `topic` header changed to a more sensitive topic sharing a compatible body shape, e.g. `customers/redact` or `app/uninstalled`). `HmacValidator.validate` still returns `true` because it never inspects the headers, and `Registry.process` dispatches the forged event to the handler tagged with the victim's shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), which is explicitly listed as a Critical-severity outcome. A host application that keys its per-merchant state, deletion routines, GDPR redaction, or subscription/uninstall bookkeeping off of `WebhookMetadata#shop` can be tricked into applying another merchant's data/events to the wrong tenant, or triggering privileged lifecycle actions (like uninstall/redact handling) for a shop that never actually sent that event.

### Likelihood Explanation
Exploitation only requires the attacker to be an ordinary, unprivileged user of the app on their own shop (no access to the app's `api_secret_key`, no privileged account, no leaked credentials) — they can legitimately trigger and capture a validly HMAC-signed webhook for themselves, then replay it against the app's public webhook endpoint with a forged `shop-domain` (and/or `topic`) header. All of the "OUT OF SCOPE" exclusions requiring credentials, leaked secrets, or social engineering do not apply here.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the HMAC-signed material used by `VerifiableQuery`/`Request#to_signable_string`, or otherwise require the gem to independently verify that the `shop-domain` header corresponds to the same tenant the signature was generated for (e.g. via a per-shop secret, or by validating the header against a known/allow-listed shop before trusting it in `WebhookMetadata`). At minimum, document prominently that `Registry.process` does not authenticate `shop`/`topic`/`webhook_id`, so host applications are not misled into trusting these fields as verified.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook event (e.g. `orders/create`), capturing the raw JSON body `B` and the resulting valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared `api_secret_key`).
2. Attacker sends a POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it was never bound to a shop)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic: orders/create` (or any topic compatible with body `B`)
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`: [5](#0-4) 
4. Validation succeeds since it only checks `B` against `H`. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, `topic: "orders/create"`, and body `B`, believing it originated from the victim's store.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
