This confirms the key finding: `ShopifyAPI::Webhooks::Registry.process` (docs explicitly state it "will verify the request did indeed come from Shopify") only validates the HMAC over the raw body, then hands the header-derived `shop`, `topic`, `webhook_id`, and `api_version` straight to the app's handler as trusted `WebhookMetadata`, with no cryptographic binding between those header values and the signature.

### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers [2](#0-1) . `Registry.process` validates only that the body's HMAC is authentic and then trusts these unauthenticated header values when building `WebhookMetadata` for the handler [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop value cryptographically bound to the signed payload == shop value the handler uses to identify the tenant`. Here that equality is broken. `Utils::HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is only the raw JSON body — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never part of the signed data [1](#0-0) .

Anyone who can obtain one genuine, HMAC-valid webhook delivery for a shop they legitimately control (e.g., installing the app on their own free/dev store) can capture that exact `(raw_body, hmac)` pair — which is valid for any headers, since the headers are excluded from the signed string — and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header naming a different, victim shop. `HmacValidator.validate` will still pass because the body and HMAC match [5](#0-4) , and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain [6](#0-5) .

Per the gem's own documented pattern, host applications are expected to key off `data.shop` to identify which tenant a webhook belongs to and to dispatch shop-specific work (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) , and the docs describe `Registry.process` as verifying "the request did indeed come from Shopify" [8](#0-7)  — which is only true for the body, not for the tenant-identifying `shop` header that the API contract hands to every handler as trusted metadata.

### Impact Explanation
This is a cross-tenant confusion primitive that satisfies the "cross-tenant access" impact bar: an app following the gem's documented `WebhookHandler` contract will process attacker-supplied payload content under a victim shop's identity (e.g., queue "victim shop received this order/product update" jobs, or trigger shop-scoped business logic keyed on `data.shop`), because the gem asserts the request is verified while silently leaving the tenant-identifying field unauthenticated.

### Likelihood Explanation
Any party who can install the target app on a shop they control (a normal, unprivileged step for any Shopify merchant/developer) can capture a real `(body, hmac)` pair from their own legitimate webhook deliveries and replay it with a spoofed shop header, since no nonce, timestamp, or shop binding ties the signature to the header values that the gem hands to handlers as trusted.

### Recommendation
Include the tenant/topic-identifying headers (`shop-domain`, `topic`, at minimum) in the signed string that `HmacValidator` verifies, or independently authenticate `request.shop` against the recipient endpoint/shop registration before constructing `WebhookMetadata`, so the value trusted by handlers is cryptographically bound to the same signature that authenticates the body.

### Proof of Concept
1. Install the target app on a shop you control (`shop-a.myshopify.com`) and capture a genuine webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H` is valid because `to_signable_string` only covers `B` [1](#0-0) .
2. Send a request to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a victim shop that also has the app installed).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `B`/`H` match [9](#0-8) .
4. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)` [10](#0-9)  and, following the gem's documented usage pattern, processes attacker-controlled body content as if it were an authentic event for `shop-b`.
