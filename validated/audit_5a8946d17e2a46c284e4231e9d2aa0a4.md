This confirms the vulnerability. `Utils::HmacValidator.validate` for a `Webhooks::Request` only signs `to_signable_string`, which returns `@raw_body` [1](#0-0) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` — the fields that identify *which tenant* the webhook belongs to and route it to a handler — are all read straight from unauthenticated HTTP headers, never included in the HMAC-signed bytes [2](#0-1) . `Registry.process` validates the HMAC over the request, then passes `request.shop` (header-derived) straight into the handler as the tenant identity `WebhookMetadata.shop` [3](#0-2) . Apps are documented to treat this `shop` field as the authoritative tenant identifier for enqueuing/processing work [4](#0-3) .

### Title
Webhook tenant identity (`shop`, `topic`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw JSON body, but reports `shop`, `topic`, `webhook_id`, and `api_version` — the values host applications use to route and attribute the webhook to a specific merchant — straight from HTTP headers that are excluded from the signed bytes. An attacker who owns a legitimate installation of the app can obtain a genuinely-signed webhook (valid HMAC over a real body) and then replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header, successfully passing `HmacValidator.validate` while attributing the payload to a victim shop of the attacker's choosing.

### Finding Description
`HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns solely `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors read from `shopify_header(...)`, which pulls from the `@headers` hash built directly from caller-supplied HTTP headers with no cryptographic binding to the HMAC [2](#0-1) [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, and forwards the unauthenticated `request.shop` directly into `WebhookMetadata` given to the app's handler [3](#0-2) . The identity equality that should hold — `bytes_covered_by_hmac == bytes_used_to_attribute_tenant` — is broken: the HMAC covers only the body, while shop/tenant attribution comes from headers outside that signature.

Documented usage confirms apps treat `data.shop` as trustworthy tenant identity for downstream actions (e.g., enqueuing background jobs keyed by `shop_domain`) [7](#0-6) .

### Impact Explanation
This is a cross-tenant confusion vector: an unprivileged internet user who controls a genuine (even trial/free) installation of the app can generate a validly-HMAC-signed webhook body from their own shop's traffic, then submit it directly to the app's public webhook endpoint with header values (`shop-domain`, `topic`, etc.) rewritten to name a different, victim shop. Because these header values are never covered by the signature, `HmacValidator.validate` still succeeds, and the handler processes attacker-controlled body content while believing it originates from the victim's shop, potentially corrupting per-tenant state, triggering GDPR/compliance handlers (`shop/redact`, `customers/redact`, `customers/data_request`) for the wrong shop, or causing data to be written into the wrong tenant's records if the host app trusts `data.shop` for identity/session lookups. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that (a) has at least one real installed shop able to generate valid signed webhook traffic, or (b) any attacker who can compute an HMAC is blocked without the secret — however, the attacker does not need the secret at all: any genuine merchant installation naturally receives correctly signed webhooks from Shopify for its own store, and the attacker (as that merchant) can capture and replay them with modified headers against the app's public endpoint, since no additional secret knowledge is required to alter headers post-capture.

### Recommendation
Bind the tenant/routing identity to the HMAC-verified bytes: include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (or otherwise cryptographically bind them, e.g. by validating that the body's own embedded shop/domain data matches the header-derived shop before trusting it), so that any header tampering invalidates the signature. At minimum, cross-check `request.shop` against an out-of-band, already-authenticated source (e.g., the session/shop record the webhook subscription was registered under) rather than trusting the header value verbatim.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify send a legitimate webhook (e.g. `orders/create`) to the app's registered callback URL, capturing the raw body `B` and the genuine `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(secret, B)`.
2. Attacker resends a POST to the same webhook endpoint with body `B` unchanged (so `HmacValidator.validate` still succeeds because it only checks `H` against `B`), but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and optionally other headers).
3. `Webhooks::Registry.process` calls `HmacValidator.validate(request)` — passes, since only `B` is checked [8](#0-7) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [9](#0-8) , and if the host app uses `data.shop` to key persistence, background jobs, or compliance actions, it processes attacker-controlled content under the victim tenant's identity.
