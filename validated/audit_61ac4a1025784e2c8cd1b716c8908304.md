## Confirmed: SSRF/credential-leak analog found

### Title
`ShopifyAPI::Auth::TokenExchange.exchange_token` sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
The `initialize`-style unsafe-parameter-trust bug class in the report (accepting an unvalidated input that gates a sensitive resource) maps to `exchange_token`'s handling of the shop host it uses to build the token-exchange request. Unlike every sibling method in this gem that builds a request carrying `client_secret`, `exchange_token` skips `Utils::ShopValidator.sanitize!` on the shop value before using it to construct the destination host that receives the request containing `client_id`/`client_secret`.

### Finding Description
`exchange_token` derives `dest_shop` directly from the session token's `dest` JWT claim and passes it straight into `Session.new(shop: dest_shop)`: [1](#0-0) 

That session is then handed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, and `HttpClient#initialize` builds the request's base URI directly from `session.shop` (unless `Context.api_host` is set): [2](#0-1) 

The POST body sent to that host includes `client_secret`: [3](#0-2) 

Compare this to `migrate_to_expiring_token` in the same file, and `ClientCredentials.client_credentials`, both of which call `Utils::ShopValidator.sanitize!(shop)` before building the session used for the credential-bearing request: [4](#0-3) [5](#0-4) 

`ShopValidator.sanitize!`/`sanitize_shop_domain` restricts the resulting host to Shopify's trusted domain suffixes (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`): [6](#0-5) 

`exchange_token` has no equivalent check. The only constraint on `dest` is that `JwtPayload#initialize` validated the JWT's HMAC signature and that `aud == Context.api_key`: [7](#0-6) 

The equality this code is implicitly (and correctly, for the signature check) enforcing is: *"the host that receives `client_secret`" == "the host authenticated by the signed JWT's `dest` claim"*. What is missing is a second, independent equality that every other credential-bearing call in this module enforces: *"the host that receives `client_secret`" == "a trusted Shopify domain"* (via `ShopValidator`). Because `exchange_token` skips that second check, the trust boundary collapses to "whatever string appears in `dest`, as long as the token was validly signed."

### Impact Explanation
This is High severity per the rules' SSRF-with-credentials category. If Shopify (or an intermediary such as a spoofed/roaming session token issuer, custom-domain configuration, or a future format change to `dest`) ever produces a `dest` value that is not a real Shopify admin host, this code will POST the app's `client_id`/`client_secret` and the raw `subject_token` (the session token) to that host. Given the deliberate asymmetry with `migrate_to_expiring_token`/`client_credentials` — which the gem's own authors clearly treat as needing `ShopValidator.sanitize!` — this is a genuine missing invariant, not merely a style inconsistency: it is the same class of "trust the field but never re-verify against a domain allowlist" bug the report describes for unvalidated `initialize` parameters.

### Likelihood Explanation
Exploitation depends on the attacker's ability to influence the `dest` value inside a JWT that still passes signature and `aud` verification — something out of this gem's control (it depends on Shopify's session-token issuance and any custom/dev-domain forwarding). This gem's contribution to the exposure is the missing defense-in-depth check that its sibling functions already apply. This is a real, reachable code-path gap even though the population of exploitable inputs is currently limited by Shopify's token issuance guarantees.

### Recommendation
Route `dest_shop` through `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) before constructing `shop_session`/`HttpClient`, mirroring `migrate_to_expiring_token` and `ClientCredentials.client_credentials`, so that the host receiving `client_secret` is always constrained to a trusted Shopify domain regardless of what the `dest` claim contains.

### Proof of Concept
1. Obtain (or otherwise arrange to be issued) a validly-signed session token whose `dest` claim is not a genuine `*.myshopify.com`/`*.myshopify.io`/`*.spin.dev` admin host (e.g., an attacker-controlled domain), while `aud` still matches the app's `api_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `HttpClient` builds `@base_uri = "https://#{dest_shop}"` from the unvalidated `dest` value and issues `POST https://{dest_shop}/admin/oauth/access_token` with body containing `client_id` and `client_secret`, exfiltrating the app's credentials to the attacker-controlled host — unlike `migrate_to_expiring_token`, which would reject the same non-trusted host via `ShopValidator.sanitize!` before ever building the request.
