### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the webhook payload using `Utils::HmacValidator.validate(request)`, but the HMAC signature only covers the raw request body. The `shop` value that identifies which tenant the webhook belongs to is taken directly from an unauthenticated HTTP header and handed to the app's handler unchecked.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read straight out of the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signature: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` (and body) directly to the app's handler as the tenant identifier, without re-deriving or verifying it against anything cryptographically bound to the body: [3](#0-2) 

`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac`: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that installs the app, and only the `raw_body` is bound to that signature, the equality the code actually enforces is:

`HMAC(secret, raw_body)` == `HMAC(secret, raw_body)` (regardless of shop)

instead of the equality that matters for a multi-tenant app:

`shop_claimed_in_header` == `shop_that_this_body_actually_belongs_to`

Any request carrying a body/HMAC pair that is valid for *some* delivery under the app's secret will pass `HmacValidator.validate`, no matter what value is placed in the `shop-domain` header, because that header plays no part in the signed material.

### Impact Explanation
This breaks the identity binding between an authenticated webhook payload and the tenant (`shop`) the host application attributes it to. `WebhookMetadata.shop` is the only tenant-scoping signal the library passes to the app's handler: [5](#0-4) 

A host application that (reasonably, per this gem's documented contract) trusts `data.shop` after `Registry.process` returns without raising can be made to process, store, or act on webhook data under the wrong shop's identity — e.g., writing order/customer data into another tenant's records, or triggering shop-specific business logic (uninstall/GDPR/billing webhooks) against a shop that never sent that event. This is a cross-tenant data/attribution confusion in a multi-tenant app built on this gem, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only a single genuine (raw_body, hmac) pair obtained from any real delivery to the app's shared webhook endpoint — a routine event any merchant using the app will generate for their own shop. The unprivileged actor then resends that exact body/HMAC to the same public endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header swapped to a different shop's domain. Since `HmacValidator` never inspects the header, and `Request#shop` is read verbatim, `Registry.process` will happily invoke the handler with the attacker-chosen `shop` value. No secrets, tokens, or privileged access are required — only the ability to POST to the app's public webhook URL, which is unprivileged internet-reachable by design.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the material that is verified, or otherwise independently authenticate the shop claim before it is trusted:
- Include the `shop-domain` header value in the signed/verified material (e.g., verify a value that Shopify itself would need to have signed together with the body), or
- Cross-check the shop domain against a known, previously-registered installation record (e.g., a session/store lookup) before dispatching to the handler, rejecting webhooks whose claimed shop does not correspond to a shop actually subscribed to that topic, or
- At minimum, document loudly that `WebhookMetadata.shop` is unauthenticated header data and must never be trusted for tenant-scoping decisions without independent verification by the host app.

### Proof of Concept
1. App has two installs: `shop-a.myshopify.com` and `shop-b.myshopify.com`, sharing one `api_secret_key`.
2. Shopify delivers a genuine `orders/create` webhook for `shop-a.myshopify.com`; the unprivileged holder of that HTTP request (e.g. anyone who can observe traffic reaching the app's public endpoint, or the shop-a merchant themself) captures `raw_body` and the `x-shopify-hmac-sha256` value.
3. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint again, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared secret: [6](#0-5) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ..., ...))`, causing the host app to treat shop-a's order data as belonging to shop-b.
