### Title
Venue-priced pairs trust a raw, un-guarded Uniswap V4 pool mid to size fills and LP withdrawals, letting a flashloan attacker drain solver funds - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
For curveless (venue-priced) pairs, Simplex derives the exotic token's USD price directly from a Uniswap V4 pool's current `sqrtPriceX96` and uses it, unadjusted for size or execution cost, to size order fills and to compute how much liquidity to remove from the solver's own V4 position. The only mitigation, `checkPriceGuard`, is optional per-chain configuration — when a position's `referencePrice`/`maxDeviationBps` are not set, the chain is explicitly documented as "unguarded." This mirrors the Zivoe `OCL_ZVE.fetchBasis` bug class: a single, spot AMM read (manipulable in one transaction via flashloan) feeds directly into a value the protocol/solver uses to release funds, with no TWAP, no impact/depth check, and an easily-omitted guard.

### Finding Description
`resolveLegRates`/`referenceRate` in `sdk/packages/simplex/src/strategies/fx.ts` price a curveless pair (token0 a USD stable) by calling `venueUsdPrice`, which resolves to `UniswapV4FundingPlanner.getExoticTokenPrice`: [1](#0-0) 

`getExoticTokenPrice` picks the most-liquid qualifying position and calls `computeDirectPoolPriceUsd`, which returns the pool's raw mid price straight from `sdkPool.token0Price`/`token1Price` (derived from the live `sqrtPriceX96`), with no size/impact term and no averaging: [2](#0-1) 

The only defense is `checkPriceGuard`, applied in `resolveLegRates` and `referenceRate` in `fx.ts`, comparing the quote against a static `referencePrice`/`maxDeviationBps`: [3](#0-2) [4](#0-3) 

This guard is optional at boot: it is only populated into the `priceGuard` map when a position's TOML entry sets `referencePrice`, otherwise the chain is priced with no guard at all: [5](#0-4) 

Documentation confirms this is a known, accepted gap: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool" and "omit both to leave the chain unguarded": [6](#0-5) [7](#0-6) 

The mispriced mid then drives two fund-moving actions from a single manipulated block: (1) `computeLegPolicyOutput` extends this mid linearly to size the exotic tokens the solver must deliver for the user's stable input, and (2) `UniswapV4FundingPlanner.planWithdrawalForToken` removes liquidity from the solver's own NFT position sized off the same (attacker-controlled) pool state to cover the deficit. Because the price is read fresh on each fill (`state.refresh()` inside `getExoticTokenPrice`), an attacker who moves the pool immediately before submitting/filling an order gets both effects for free within one atomic sequence, exactly as the Zivoe report describes reserves being manipulable to distort a value that immediately drives a fund-affecting decision.

### Impact Explanation
An attacker can flashloan-swap in the solver's own V4 pool to push the mid price so that, from the solver's perspective, the exotic token appears cheap in USD terms (or expensive, whichever direction extracts value). The solver then either delivers an inflated amount of the exotic token for the user's stable input, or over-withdraws liquidity from its own concentrated position, both computed off the manipulated mid. Because the fee tier is never applied to the price and there is no size/impact term (per the flow doc), the loss is not bounded by the pool's own trading fee, and repeated cycles across configured chains that omit `referencePrice`/`maxDeviationBps` compound the drain. This is direct loss of solver-held funds — comparable in mechanism (single manipulable AMM read directly gating a fund release) and severity (Medium, in-scope, protocol/solver capital) to the referenced Zivoe finding.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (a) a venue-priced pair configured without `referencePrice`/`maxDeviationBps` (explicitly supported and documented as a valid, "unguarded" configuration) and (b) sufficient capital/flashloan access to move the specific V4 pool the solver holds a position in. Both are realistic — operators may reasonably omit the optional guard for pairs where no natural reference price exists, and V4 pools for exotic/thin pairs (the primary use case for pool-based pricing per the docs, e.g. cNGN) are typically thinner and cheaper to move than a major pair. An unprivileged order submitter is the reachable actor: submitting/filling an order triggers the pricing read on the manipulated pool.

### Recommendation
- Make the price guard mandatory (not optional) for all venue-priced pairs, or fail closed (reject the fill) if no `referencePrice`/`maxDeviationBps` is configured for a chain using pool pricing.
- Replace or supplement the raw spot `sqrtPriceX96` mid with a TWAP/multi-block observation, and incorporate the pool's own fee tier and a size/impact term in `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` so quoted output is bounded by actual executable liquidity depth.
- Bound the LP withdrawal sizing (`planWithdrawalForToken`) independently against a sanity/reference price, rather than solely against the same live pool read used for fill pricing, so a single manipulated read cannot simultaneously inflate both the fill output and the withdrawal amount.

### Proof of Concept
1. Operator configures `[vault.uniswapV4]` for a curveless pair (e.g., USDC/EXOTIC) without `referencePrice`/`maxDeviationBps` — a supported, documented configuration (`docs/content/developers/evm/simplex/pricing.mdx` L64-66, L72).
2. Attacker takes a flashloan and swaps heavily in the EXOTIC/USDC V4 pool that backs the solver's configured position, moving `sqrtPriceX96` so the pool momentarily reports EXOTIC as cheap in USD.
3. Attacker (or an accomplice) submits/fills an order matching this pair; `resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` reads the manipulated `sqrtPriceX96` live (`state.refresh()`), returning the skewed price with no guard to reject it.
4. `computeLegPolicyOutput` sizes an inflated EXOTIC payout for the attacker's stable input; `planWithdrawalForToken` removes a correspondingly inflated amount of liquidity from the solver's V4 position, sized off the same manipulated pool state.
5. Attacker reverses the flashloan swap in the same transaction bundle, restoring the pool price and pocketing the value difference extracted from the solver's position.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

**File:** docs/content/developers/evm/simplex/pricing.mdx (L68-72)
```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
