## Title
JWT Replay-Protection Check-Then-Act Race Allows Concurrent Reuse of the Same JWT for Repeated Unauthorized Trigger Requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` calls `h.jwtCache.isReplay(claims.ID)` early to check whether a JWT `jti` has been used, but only calls `h.jwtCache.recordUsage(claims.ID)` at the very end of the function, after signer/authorized-key validation completes. Because these are two independent, separately-locked operations on the same map rather than one atomic "check-and-set," two requests bearing the identical signed JWT can both pass the replay check concurrently before either records usage, allowing the same JWT to authorize more than one trigger request.

## Finding Description
The vulnerable code is exactly as described: [1](#0-0)  performs `isReplay` at line 87 and defers `recordUsage` to line 105, with unrelated authorized-key lookup logic executing in between. The underlying cache implementation confirms the check and the record are two distinct, non-atomic critical sections: [2](#0-1)  — `isReplay` acquires and releases an `RLock`, and `recordUsage` separately acquires and releases a `Lock`, with no lock held across the full `Authorize` call.

This is a genuine TOCTOU (check-then-act) race: if two goroutines process the same signed JWT concurrently (e.g., an attacker firing the same signed HTTP-trigger request twice in parallel), both can read `isReplay` as `false` before either writes to `recordUsage`, allowing both to pass through the authorized-key checks and be treated as validly authorized. The `Authorize` function is reachable from `HandleUserTriggerRequest` on the HTTP trigger path [3](#0-2) , which is exposed to external, unprivileged callers submitting signed JWT-authenticated trigger requests. No other lock, middleware, or serialization exists between the two calls to close this gap.

## Impact Explanation
The JWT `jti` replay cache is the sole mechanism preventing a signed HTTP-trigger request from being processed more than once. A successful race allows an external, unprivileged caller who already possesses one valid signed JWT to cause the gateway to authorize and dispatch the same trigger request twice (or more, depending on the race window and concurrency), producing duplicate workflow execution instead of the intended single-use, single-execution guarantee. This maps to the in-scope "gateway request impersonation / allowlist bypass" category, since the caller effectively defeats a one-time-use control that is meant to bound how many times a specific signed authorization artifact can be consumed. The impact is bounded to duplicate triggering of the caller's own workflow request — it does not grant access to other tenants' workflows or escalate privileges beyond what the caller's key already authorizes — but it is a concrete integrity bypass of a stated security control.

## Likelihood Explanation
Exploitability requires only an unprivileged external actor sending two copies of an already-obtained, validly signed request concurrently to the gateway's HTTP-trigger endpoint — no privileged role, no cryptographic weakness, and no interaction with other tenants is required. The race window is narrow (the span between an `RLock`/`RUnlock` in `isReplay` and a `Lock`/`Unlock` in `recordUsage`, with signer/key-lookup work happening in between), but it is a real, reachable window under concurrent request dispatch on a busy gateway, and the attacker fully controls both timing and repetition of their own signed request, making the race practically winnable with a small number of attempts.

## Recommendation
Make the replay check-and-mark atomic: acquire a single write lock (or use `sync.Map.LoadOrStore` / an equivalent "insert-if-absent" primitive) so that testing for existence and inserting the `jti` happen as one indivisible operation, and reject the request if the entry already existed. This atomic check-and-set should occur as early as possible in `Authorize` — immediately after JWT signature/claims verification — rather than deferring `recordUsage` until after the signer/authorized-key checks complete.

## Proof of Concept
1. Sign one valid JWT for a JSON-RPC trigger request with a valid `jti`, `iss`, `exp`, and digest matching the request payload.
2. Submit this exact signed request twice, concurrently (e.g., two parallel goroutines/HTTP clients), to the gateway's HTTP-trigger endpoint.
3. Both requests reach `WorkflowMetadataHandler.Authorize` at nearly the same time.
4. Goroutine A calls `isReplay(claims.ID)` (workflow_metadata_handler.go:87) → cache empty → proceeds through authorized-key checks (lines 92–104).
5. Before goroutine A reaches `recordUsage` (line 105), goroutine B calls `isReplay(claims.ID)` → also finds no entry → also proceeds.
6. Both goroutines complete authorization successfully and each eventually calls `recordUsage`, demonstrating that a single JWT was accepted twice — a Go unit test spawning two concurrent calls to `Authorize` with the same token/claims (mocking `authorizedKeys`) and asserting both return `nil` error would deterministically reproduce this under a small number of iterations or with an artificial delay inserted between `isReplay` and `recordUsage`.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
