## Title
Duplicate-output-token guard in `IntentGatewayV2.placeOrder` is bypassable via bytes32/address id aliasing - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder()` enforces "no duplicate output tokens" by comparing the raw 32-byte `token` field of each output asset, but every downstream consumer of that same field (escrow debiting, transfers, dust sweeps) truncates it to a 20-byte address with `address(uint160(uint256(token)))`. Because many distinct `bytes32` values collapse to the same `address`, an unprivileged caller can submit an order whose output assets are, in reality, the same ERC-20 token wearing two different `bytes32` "ids" (upper 12 bytes differ, lower 20 bytes — the real address — are identical), completely defeating the duplicate-token check. This mirrors the reported `LibHelpers._getAddressFromId()` id-aliasing bug class: an N-to-1 mapping between id and address is used inconsistently by an equality/uniqueness check versus the code that actually resolves the id to an address.

### Finding Description
In `placeOrder`, the duplicate check operates on the untouched `bytes32`: [1](#0-0) 

```
bytes32 token = order.output.assets[i].token;
assembly ("memory-safe") {
    if tload(token) { revert InvalidInput }
    tstore(token, 1)
}
```

Every other place that resolves an output/input token to the entity actually transferred does so by downcasting to `address`: [2](#0-1) [3](#0-2) [4](#0-3) 

Since `bytes32(uint256(uint160(addr)))` is a many-to-one mapping of ids onto the same 20-byte address, a caller can pick `token_a = bytes32(uint256(uint160(daiAddr)))` and `token_b = token_a | (uint256(1) << 160)` (any non-zero upper 12 bytes) for two different `output.assets[]` entries. `tload/tstore` treats these as distinct 32-byte keys, so the "reject duplicate output tokens" loop passes, even though both entries reference the identical real ERC-20 `dai`. All later consumers of `order.output.assets[i].token` — `_execute`'s dust sweep, `_withdraw`'s escrow debit/credit, and `fillOrder`'s per-index output validation — will resolve both entries to the same `address`, because they all apply the same truncation. This is the exact aliasing pattern described in the external report: a check performed on the full id disagrees with the address the rest of the system actually operates on.

### Impact Explanation
The `placeOrder` function has an explicit, purpose-built invariant ("Reject duplicate output tokens") intended to guarantee that each index of `order.output.assets` corresponds to a distinct real token. Bypassing it via id aliasing means the contract's own security control can be defeated by any unprivileged user in a single `placeOrder` transaction, producing orders that violate an invariant the rest of the fill/withdraw/dust-sweep pipeline (indexer VWAP tracking, `_execute`'s per-token dust accounting, `_withdraw`'s escrow bookkeeping keyed by the *address*, not the id) was written to rely on. This is analogous to the original report's outcome where entities/policies could be created with `id != _getIdForAddress(_getAddressFromId(id))`, later causing unexpected behavior in downstream logic that assumes the invariant holds.

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged, single-transaction entry point reachable by any user constructing an `Order` struct — no special role or multi-step setup is required, only crafting a `bytes32` token id whose lower 20 bytes match a real token address while the upper 12 bytes are non-zero.

### Recommendation
Perform the duplicate-token check on the downcast `address(uint160(uint256(token)))` value instead of the raw `bytes32`, and/or reject any `token` value whose upper 12 bytes are non-zero when it is meant to represent a native/ERC-20 address (mirroring the report's recommended fix of validating that the discarded bytes are zero).

### Proof of Concept
1. Attacker calls `placeOrder` with two output assets:
   - `assets[0].token = bytes32(uint256(uint160(address(dai))))`
   - `assets[1].token = bytes32(uint256(uint160(address(dai))) | (1 << 200))`
2. Both values differ as `bytes32`, so the `tload`/`tstore` dedup loop at [1](#0-0)  does not flag them as duplicates and the order is accepted.
3. Every downstream function that processes `order.output.assets[i].token` (e.g., `_execute` at [3](#0-2) ) resolves both entries to the identical `address(dai)`, confirming the intended per-index token-uniqueness guarantee has been silently broken.
