## Title
Secure-Element signup signature omits `signup_id`, `signup_reason`, and QR-code identifiers, allowing biometric-attestation data to be replayed/misattributed across signup contexts - (File: `src/plans/enroll_user.rs`)

### Summary
The external report describes a formula that combines several similar fee components (`protocol_fee`, `swap_fee`, `burn_fee`) but forgets to include a newer, structurally-similar component (`extra_fees`), producing an incorrect result that is trusted downstream. The analogous root cause in orb-core is `make_signature` in `src/plans/enroll_user.rs`, which builds the buffer that the Secure Element signs to attest a signup's biometric data, but the buffer is composed from a hand-picked, incomplete list of fields rather than all the context that binds the signature to a specific signup session.

### Finding Description
`make_signature` constructs the signed payload as: [1](#0-0) 

It only hashes: `ORB_ID`, `user_qr_code.user_id`, `ir_net_version`, `iris_version`, and the iris/mask codes (+ versions) for both eyes. It is called from `run()`: [2](#0-1) 

Notably absent from the signed buffer are:
- `self.signup_id` (the `SignupId` used to correlate this signup end-to-end, passed into `Plan` but never fed into `make_signature`) [3](#0-2) 
- `self.signup_reason` (`SignupReason`, distinguishing e.g. normal signup vs. other reasons)
- `self.operator_qr_code` (the operator/session context)
- the full `user_qr_code` string/content (only `user_id` is hashed, not the rest of the QR payload such as `pcp_version`, `data_policy`, or extension parameters)

This mirrors the Mantra bug pattern exactly: the function combines several fixed, "same-category" inputs (a whitelist of fields) while a categorically-similar but separately-introduced piece of context (`signup_id`/`signup_reason`/full QR data — analogous to `extra_fees` being added alongside `protocol_fee`/`swap_fee`/`burn_fee`) is silently excluded from the calculation that produces a security-relevant artifact (here, a cryptographic attestation signature, there, a fee-adjusted swap amount).

The signature is sent to the backend as part of `signup_post::request` alongside separately-transmitted `signup_id`, `operator_qr_code`, `user_qr_code`, and `signup_reason` values: [4](#0-3) 
Because the signature itself does not bind to those separately-sent values, nothing cryptographically ties the Secure-Element-signed iris/mask codes to the specific `signup_id`, `signup_reason`, or full QR-code context of the request that carries them.

### Impact Explanation
The Secure Element signature is meant to provide an unforgeable attestation that a specific iris/mask code pair originated from a genuine capture on this Orb for this user QR code. Because the signed buffer omits `signup_id` and `signup_reason`, a previously-produced valid signature over the same `(user_id, iris/mask codes, versions)` tuple is not bound to the specific signup session under which it is submitted. This creates a risk of cross-signup replay/misattribution: a signature computed for one enrollment attempt could be resubmitted under a different `signup_id` or `signup_reason` value without invalidating the attestation, since the omitted fields play no role in what was actually signed. This falls under the "cross-signup state bleed" / "misattributed signup" impact category — a signature intended to bind biometric data to a unique signup transaction fails to do so completely.

### Likelihood Explanation
The gap is deterministic and always present — it is not a probabilistic or edge-case issue but a structural omission in the hashed buffer, verifiable directly from the source. Exploitability depends on backend-side validation (not visible in this repo) potentially re-checking that the signature was produced for the current `signup_id`, which would be a secondary control; however, on the orb-core side alone, there is no cryptographic binding, so orb-core cannot itself guarantee session-uniqueness of the attestation the way the code comment/naming ("Iris code signature") implies.

### Recommendation
Include `signup_id`, `signup_reason`, and the full `user_qr_code` (and ideally `operator_qr_code`) content in the buffer hashed by `make_signature`, e.g.:
```rust
fn make_signature(
    signup_id: &SignupId,
    signup_reason: SignupReason,
    operator_qr_code: &qr_scan::user::Data,
    user_qr_code: &qr_scan::user::Data,
    pipeline: &Pipeline,
) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(signup_id.to_string().as_bytes());
    ctx.update(signup_reason.to_string().as_bytes());
    ctx.update(operator_qr_code.user_id.as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    // ... existing iris/mask code fields ...
    secure_element::sign(ctx.finish())
}
```
This ensures the Secure-Element-signed attestation is cryptographically bound to the exact signup session it is submitted for, matching the same completeness principle the Mantra fix applied (accounting for every relevant "component," not just a fixed subset).

### Proof of Concept
Not independently verifiable without backend source (the `signup_post`/`signup_poll` verification logic that consumes this signature is not in scope of this repo), so exploitability cannot be fully confirmed from orb-core alone. What is concretely provable from this repo:
1. `make_signature`'s hashed inputs are limited to `ORB_ID`, `user_qr_code.user_id`, and iris/mask code fields [1](#0-0) .
2. `Plan` carries `signup_id`, `operator_qr_code`, and `signup_reason` as fields that are never passed into `make_signature` [5](#0-4) .
3. These omitted fields are instead sent unsigned/separately in the same request [4](#0-3) , meaning the request layer — not the signature — is the only thing associating the attestation with a particular `signup_id`/`signup_reason`.

I could not verify from this repo whether backend-side controls compensate for this gap; a Devin session with backend source access would be needed to confirm actual exploitability end-to-end.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
