### Title
Webhook `shop-domain` Header Not Covered by HMAC Verification Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as verified once its HMAC passes, and then trusts the `shop-domain` header as the authoritative tenant identity for the event. However, the HMAC signature computed by this gem covers only the raw request body — none of the Shopify-supplied headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed material. This is the same class of bug as the reported issue: a value that is acted upon (the multiplier/decimals in the external report; here, the `shop` identity) is derived from data that sits outside the cryptographic binding (HMAC) meant to guarantee its authenticity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (the body, in this case) against the secret, and never touches headers: [3](#0-2) 

`Registry.process` performs exactly one check — HMAC validity — and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop` header, handing it to the app-supplied handler as if it were verified tenant identity: [4](#0-3) 

The gem's own documentation reinforces that `Registry.process` is expected to fully authenticate the request ("This will verify the request did indeed come from Shopify") and describes `shop` in `WebhookMetadata` simply as "The shop domain of the webhook," with no caveat that it is unauthenticated: [5](#0-4) [6](#0-5) 

By contrast, in the OAuth callback flow, the equivalent field (`shop`) *is* included in the signable string, so it is properly bound to the HMAC: [7](#0-6) 

This asymmetry confirms the webhook path is the outlier: the binding "authenticated shop == shop acted upon" holds for OAuth but is broken for webhooks.

### Impact Explanation
Because `shop` is not part of the signed payload, an attacker who can obtain any one legitimately-signed webhook body+HMAC pair (trivially available to any unprivileged internet user who installs the target app on their own shop/dev store and triggers a subscribed event) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application that follows the gem's documented contract — trusting `data.shop` as the verified tenant for a "verified" webhook — will process or persist data under the wrong tenant, resulting in cross-tenant data confusion/write (e.g., writing attacker-supplied event data into a victim shop's record, or triggering shop-scoped side effects for a shop the attacker doesn't control).

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own valid webhook subscription and shop (freely obtainable by installing the app on a shop they control), and (2) the ability to POST an HTTP request with custom headers to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or any privileged credential is required — the vulnerable identity value is the header itself, and the HMAC secret is never involved in producing or validating it.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used for HMAC verification in `Webhooks::Request#to_signable_string`, or otherwise cryptographically/structurally bind the header-derived `shop` to the verified body before constructing `WebhookMetadata`. At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not covered by the HMAC check and must be independently corroborated (e.g., against a known list of installed shops) by the host application before being trusted as tenant identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   - Headers: `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: `{...attacker-controlled order payload...}`
3. Attacker captures this request and replays it directly to the app's public webhook endpoint, only changing the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - HMAC and body left untouched.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — this still matches, so validation passes: [8](#0-7) 
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker payload>, ...)`, i.e., attacker-controlled data attributed to a shop the attacker does not control.
