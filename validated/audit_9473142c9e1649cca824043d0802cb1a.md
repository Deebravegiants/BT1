### Title
Webhook shop-domain/topic header spoofing bypasses HMAC binding, enabling cross-tenant webhook data confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers to that signature. Any actor who possesses one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own store and receiving a legitimate webhook signed with the app's shared `api_secret_key` — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header for a victim shop. `ShopifyAPI::Webhooks::Registry.process` accepts the request as valid (since only the body is HMAC-checked) and hands the attacker-chosen `shop` straight to the app's webhook handler as trusted metadata.

### Finding Description
The identity binding that should hold is: `shop reported in the request == shop authenticated by the HMAC signature`. In this gem it does not:

- `HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` header [4](#0-3) .
- For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) ; `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated headers [2](#0-1) .
- `Registry.process` uses only `Utils::HmacValidator.validate(request)` as its trust gate, then dispatches `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) .

Because all merchants that install the same app share the same `api_secret_key`/`client_secret` for HMAC signing, an attacker can install the target app on their own (attacker-controlled) shop, capture any legitimate webhook delivery (a genuine `(raw_body, hmac)` pair signed by Shopify with that shared secret), and replay it directly to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim merchant's domain (and/or the `shopify-topic`/`shopify-webhook-id` headers altered). The HMAC still validates because it only ever covered the body, so `Registry.process` proceeds and calls the handler with `shop: <victim-shop>`. This is a direct violation of the tenant-binding contract this gem is supposed to enforce for webhook authenticity.

### Impact Explanation
This is a Critical-adjacent cross-tenant issue: an app relying on this gem's webhook verification to attribute incoming data to the correct merchant (e.g., updating per-shop records, triggering per-shop side effects, or feeding data into per-tenant storage keyed by `shop`) can be made to process data under the identity of a different, victim shop, since the gem asserts the request is "valid" while the only field it actually authenticates (the raw body) is decoupled from the field the app trusts for tenant attribution (`shop`).

### Likelihood Explanation
Likelihood is high for any attacker who can become a legitimate (even trial/free) installer of the target app — a standard unprivileged internet user action — since that yields a real, validly-signed webhook body/HMAC pair they can replay with modified headers against the same app's webhook endpoint. No access token, `client_secret`, or privileged account is required beyond ordinary app installation, which this gem's OAuth flow is designed to allow to any shop.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for webhook HMAC verification (or otherwise cryptographically bind them to the body signature), and document/require that consuming applications not trust `Request#shop`/`Request#topic` unless they are covered by the verified signature.

### Proof of Concept
1. Attacker creates their own Shopify dev/free store and installs the target app, completing OAuth normally (no special privilege needed).
2. The app's webhook subscription delivers a real webhook to the attacker's registered endpoint, e.g. `raw_body = "{}"` with a valid `shopify-hmac-sha256` computed by Shopify using the app's shared `api_secret_key`, and header `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same `raw_body` and `shopify-hmac-sha256` to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the (unchanged) HMAC [6](#0-5) .
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload/HMAC never originated from or was authorized by that shop, causing the host application to process/act on data under the wrong tenant's identity [7](#0-6) .
