Found a genuine analog: `IntentGatewayV2`'s relayer gate has the exact same "fail-open until armed" design that `HyperFungibleToken` explicitly rejected as unsafe. This directly mirrors SharedStake's root cause — an authorization gate whose default/unset state permits unauthorized action — but here it's reachable by any relayer submitting a message through the standard delivery path, not an insider.

### Title
IntentGatewayV2's relayer gate defaults open, letting any relayer release escrow before governance arms it - (File: evm/src/apps/intentsv2/IntentsBase.sol / evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.onAccept` gates delivery on `_checkRelayer(incoming.relayer)`, but with `_relayer == address(0)` the check matches nothing and therefore accepts every relayer's delivery — the same "opt-in" gate design that `HyperFungibleToken` uses for third-party tokens. The test suite documents this explicitly: `testFreshProxyIsOpenUntilGovernanceArmsIt` shows a freshly initialized proxy has `relayer() == address(0)` and accepts an arbitrary relayer's delivery of a `NewDeployment` governance message, and `testSetRelayerToZeroReopensTheGate` shows that resetting the relayer to zero reopens the gate for escrow release. [1](#0-0) [2](#0-1) 

### Finding Description
`BridgeToken` (the value-bearing production deployment of `HyperFungibleToken`) was deliberately hardened to fail closed specifically because "a forged mint is exactly the attack the gate exists for" for a token whose supply must be backed by escrow. [3](#0-2) 
`BridgeToken._checkRelayer` reverts unless `incomingRelayer == _relayer`, and with `_relayer` unset (zero), nobody matches — a deliberate fail-closed design. [4](#0-3) 

`IntentGatewayV2`, however, retains the opposite ("fail-open") semantics for its own relayer gate over escrow release and governance application: with no relayer configured, `onAccept` accepts messages from any relayer for both `RedeemEscrow`/`RefundEscrow` withdrawals and governance actions like `NewDeployment`/`UpgradeContract`. [5](#0-4) 
This means the entire window between proxy deployment/initialization and the governance transaction that calls `setRelayer` is a window where escrow release, deployment registration, and even contract upgrades can be triggered by an arbitrary, unauthorized relayer that merely delivers a crafted (but otherwise validly-sourced, e.g., self-referential) ISMP message. This is structurally identical to the SharedStake root cause: a privileged/administrative gate whose un-configured or default state fails permissive rather than restrictive, allowing an actor with no special privilege beyond message delivery to trigger value-moving or governance-level actions before the intended "official launch" configuration is complete.

### Impact Explanation
If a gateway proxy is deployed/initialized and, for any reason (redeployment, migration, a delayed governance transaction, or a `setRelayer(0)` reset performed for legitimate maintenance), the relayer is unset or reset to zero, any relayer can submit an `onAccept` delivery that:
- Releases escrowed user funds via `RedeemEscrow`/`RefundEscrow` (`_orders[commitment][token]` payouts) to an address of the attacker's choosing, or
- Registers a malicious `NewDeployment` instance or drives an `UpgradeContract` governance action, redirecting all future settlement/escrow logic to attacker-controlled code, leading to a full and permanent loss of escrowed funds across the gateway.

### Likelihood Explanation
This is exploitable by any actor who can act as (or spoof) an ISMP relayer for a single delivered message once the relayer allowlist is unset — no insider or admin access is required, matching the "unprivileged message dispatcher/relayer" reachability the review scope targets. The `setRelayer(address(0))` reset path and the fresh-proxy-open-by-default path are both explicitly exercised in the test suite as expected/intended behavior rather than defenses, indicating the window is a real, reachable operational state rather than a purely theoretical one. [1](#0-0) 

### Recommendation
Apply the same "fail closed" pattern used by `BridgeToken._checkRelayer` to `IntentGatewayV2`/`IntentsBase`'s relayer gate: treat `_relayer == address(0)` as "nobody authorized" rather than "everybody authorized," for both escrow-release (`onAccept`, `onGetResponse`) and governance-application code paths. If an open bootstrap window is required operationally, restrict it to a narrowly scoped initialization method that cannot be reached after the first `setRelayer` call, and require `setRelayer` to be invoked atomically as part of `initialize`/deployment rather than left as a separate, delayable step.

### Proof of Concept
1. Deploy and initialize a fresh `IntentGatewayV2` proxy without immediately calling `setRelayer` (as shown in `_freshInitializedGateway()`/`testFreshProxyIsOpenUntilGovernanceArmsIt`). [2](#0-1) 
2. An arbitrary relayer (`filler` in the test, standing in for any unauthorized third party) submits an `IncomingPostRequest` such as a `NewDeployment` message or a `RedeemEscrow`/`RefundEscrow` withdrawal request through `onAccept`.
3. The gate's `_checkRelayer` accepts it because `_relayer == address(0)` matches every caller, so the malicious governance action is applied or escrow is paid out to the attacker-controlled address before legitimate governance ever configures a relayer — mirroring SharedStake's insider exploiting a gap between deployment and official launch, except here reachable by any unprivileged relayer. # 2026-09-03 — `HyperFungibleToken` opts in to the relayer gate; `BridgeToken` fails closed

Chosen: the base token's `_checkRelayer` only rejects when a relayer has been set, and
`BridgeToken` overrides it so that an unset relayer matches nobody.

`HyperFungibleToken` is a library contract that third parties deploy from this package. Failing
closed there would leave every token deployed without a `setRelayer` call unable to receive
anything, with no compile-time signal. The BRIDGE token is ours, its supply is backed by the nexus
escrow, and a forged mint is exactly the attack the gate exists for, so it takes the strict
semantics of the intent gateway. The two behaviours live in one virtual function so the difference
is visible in one place rather than spread through the callbacks.
