### Title
Creator attribution bound to `msg.sender` of `Zap.createToken` lets a shared intermediary contract permanently hijack creator fee rewards - ([File: packages/contracts/src/Zap.sol], [File: packages/contracts/src/Bonding.sol], [File: packages/contracts/src/FeeVault.sol])

### Summary
`Zap._createTokenInternal` forwards `msg.sender` directly as the `creator_` argument to `Bonding.launch`, exactly mirroring the reported `g8keepBondingCurveFactory` pattern where `DEPLOYER: msg.sender`. If `Zap.createToken` is invoked through any intermediate contract (a batching/multicall relay, a smart-contract wallet forwarder that doesn't preserve the original caller, or any proxy that performs the call itself rather than via `delegatecall`), that intermediary — not the real user — becomes the permanently recorded `creator` for the token, and consequently the perpetual recipient of the 0.25% creator fee share on every subsequent buy/sell of that token.

### Finding Description
`Zap.createToken` is fully permissionless and calls `_createTokenInternal`, which does: [1](#0-0) 

`(tokenAddr,) = _s().bonding.launch(params, msg.sender);` uses `msg.sender` as seen by `Zap`, which is the calling contract if the call is routed through an intermediary rather than directly from the user's EOA. `Bonding.launch` stores this value verbatim as the token's `creator` in `TokenInfo`: [2](#0-1) 

This `creator` is subsequently used by `Zap` on every buy/sell to attribute the creator-share of the 0.75% fee via `FeeVault.accrue`, and by `FeeVault.claim()` which pays out `creatorBalance[msg.sender]`: [3](#0-2) [4](#0-3) 

Unlike the referenced report's `DEPLOYER` (a one-time ETH reward + LP position), this misattribution is worse in shape: it is a **standing, perpetual entitlement**. Every future trade of the launched token accrues creator fees to whatever address got recorded as `creator` at launch time — for the lifetime of the token. The only escape hatch, `Bonding.transferCreator`, is gated to `msg.sender == info.creator`: [5](#0-4) 

If the recorded `creator` is a shared contract the real user does not control (e.g., a public multicall/batching relay used by many different launchers, or a forwarder that calls out rather than `delegatecall`s), the actual user can never call `transferCreator` to reclaim the role — only whoever can drive a call from that intermediary's address can, and that operator can also call `FeeVault.claim()` directly to walk off with the accrued creator balance for every token launched by every user who routed through that same intermediary.

### Impact Explanation
Impact is High: creator-fee earnings (0.25% of every buy/sell, unbounded in duration since curve trading never expires and fees continue post-graduation) become permanently redirected to and claimable by an address the actual creator does not control, with no recovery path since `transferCreator` requires being the very address that was wrongly recorded. Multiple distinct users routed through the same faulty/malicious intermediary would all have their creator-fee streams pooled under one attacker-controlled address in `FeeVault.creatorBalance`.

### Likelihood Explanation
Likelihood is Low: it requires end users (or a wallet/aggregator integration) to call `Zap.createToken` through an intermediary contract that does not preserve `msg.sender` semantics for the underlying user (e.g., a naive multicall/batcher, or a compromised/malicious "convenience" relay), rather than calling `Zap` directly from an EOA. This is not a normal, expected interaction path for a single unprivileged trader acting alone, but it is fully reachable by any third party who builds and gets users to route `createToken` calls through such a contract.

### Recommendation
Add an explicit `creator` parameter to `Zap.createToken`/`createTokenWithPermit` (and the corresponding `Bonding.launch` call) instead of implicitly trusting `msg.sender`, with the option to default it to `msg.sender` when called directly. This lets integrators (multicallers, smart-account relayers) pass through the true end-user address explicitly, closing the misattribution window that currently mirrors the `g8keepBondingCurveFactory` `DEPLOYER` bug class.

### Proof of Concept
1. Deploy a trivial `Relay` contract with a function `relayCreate(Bonding.LaunchParams calldata params, uint256 seed) external { usdc.transferFrom(msg.sender, address(this), seed); usdc.approve(zap, seed); zap.createToken(params, seed); }` — a stand-in for any shared batching/multicall contract that forwards the call itself (does not `delegatecall`).
2. User A approves `Relay` and calls `relayCreate(...)`. Inside `Zap.createToken`, `msg.sender == address(Relay)`, so `Bonding.launch(params, address(Relay))` records `creator = address(Relay)`.
3. User B does the same for a different token through the same `Relay`; `creator` for that token is also `address(Relay)`.
4. As both tokens trade, `Zap._accrueFee` → `FeeVault.accrue(token, creator=address(Relay), ...)` pools both users' creator-fee shares under `creatorBalance[address(Relay)]`.
5. Whoever can trigger `Relay` to call `FeeVault.claim()` (e.g., the relay operator, or anyone if `Relay` exposes an unguarded passthrough) drains both users' entire creator fee balance; neither user A nor B can call `Bonding.transferCreator` since `msg.sender != info.creator` for them.

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }

        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
