### Title
Webhook `shop` and `topic` headers are trusted by the handler dispatch despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/registry.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers—none of which are covered by that signature—when building the `WebhookMetadata` passed to the app's handler. This breaks the intended identity binding: `hmac_valid(body) == authentic(shop, topic, body)`, when in reality `hmac_valid(body)` only proves the body was produced with the app's shared `client_secret`, not that it is bound to the shop or topic asserted in the headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates only the body HMAC via `Utils::HmacValidator.validate`, then looks up the handler by `request.topic` (not scoped by shop) and constructs `WebhookMetadata` directly from the unauthenticated headers: [3](#0-2) 

`HmacValidator.validate` in turn only ever hashes `verifiable_query.to_signable_string`, i.e. the body, using the app's `Context.api_secret_key` (the same secret shared across every shop that has installed the app): [4](#0-3) 

Because the app's `client_secret` is shared across all merchants that install the app, any merchant (an "unprivileged" party relative to other tenants of the same app) can legitimately receive a validly-signed `(body, hmac)` pair from Shopify for their own shop's webhook deliveries. That pair can then be replayed to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header claiming to belong to a different shop. Verification still succeeds, because the signature never covered those headers, and the handler receives `WebhookMetadata` with an attacker-chosen `shop`/`topic` alongside a body that is cryptographically "valid" but was never actually associated with that shop or topic by Shopify.

This mirrors the reported bug class exactly: the verifier confirms a subset of the claimed structure (body integrity) and then treats that success as if it proved the full statement (this body belongs to this shop/topic), just as the MerkleDB exclusion-proof bug verified only the upper part of a path yet treated it as proof of a full exclusion claim.

### Impact Explanation
This crosses the "cross-tenant access" boundary called out in scope: a merchant using an app can forge webhook events that the host application will attribute to a different merchant's shop, using a body they legitimately obtained from their own account. Depending on how the host application's handler uses `shop` (e.g., to load/create/update records, sync inventory, or trigger billing-relevant side effects), this can lead to data corruption or unauthorized actions performed against another tenant's records.

### Likelihood Explanation
Any party who has installed the app on at least one shop can capture a valid `(body, hmac)` pair from their own webhook deliveries (no special privilege, secret, or interception required) and immediately replay it against the same public webhook endpoint with a different `shop-domain`/`topic` header. No access to `api_secret_key`, access tokens, or TLS interception is required.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` in the value that is authenticated (or independently verify that the shop asserted in the header actually corresponds to a shop with an active installation/registration for that specific topic/webhook id before dispatching to a handler), so that the signature check binds the payload to the specific tenant and topic it was issued for, not just to the app's shared secret.

### Proof of Concept
1. App merchant "Shop A" installs the app and legitimately receives a webhook: 
   - Headers: `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body B>`
   - Body: `B`
2. Attacker (also Shop A, or anyone who intercepted this legitimate delivery to their own endpoint) resends the exact same body `B` and HMAC to the app's public webhook URL, but changes the header:
   - `x-shopify-shop-domain: shop-b.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because it only checks `body` against `hmac` [5](#0-4) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop = "shop-b.myshopify.com"` and passed to the app's handler [6](#0-5) , even though body `B` was never issued by Shopify for `shop-b`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
