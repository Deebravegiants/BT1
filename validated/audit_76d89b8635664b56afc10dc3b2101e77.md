### Title
Tokens sent directly to the pool contract are permanently locked with no recovery path - ([File: contracts/pool/src/lib.rs])

### Summary
The "ETH locked in a payable contract" class maps onto XOXNO Lending as the permanent stranding of tokens transferred directly to the pool contract. The pool tracks `cash` as a bookkeeping number separate from the physical `token.balance()`; every inbound entrypoint (`supply`, `repay`, `recapitalize`, `flash_loan` repayment) credits only measured receipt tied to a protocol action and refunds any excess. A direct `token.transfer` to the pool address therefore raises the physical balance without raising any book, and no entrypoint — owner or permissionless — exists to sweep, rescue, or absorb the surplus. The donated tokens are locked in the contract forever.

### Finding Description
The pool holds physical custody of all market tokens, but its reserve check uses tracked `cash`, which "incidental token donations do not increase" (docs/reference/formulas.md, cash/supply/debt section). The full entrypoint surface (contracts/pool/README.md, "Surface" table) contains only `create_market`, `update_params`, `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `claim_revenue`, `recapitalize`, `flash_loan`, `create_strategy`, and `upgrade` — there is no skim, sweep, or rescue function, and the owner is fixed at deploy with no transfer path.

Each candidate exit for stranded funds is closed:

- `claim_revenue` burns revenue shares and is capped by tracked `cash` and the floored revenue claim (INV-ACCT-06), so it cannot touch donations.
- `recapitalize` credits cash only up to the backing shortfall and refunds the excess to `payer`; the surplus from a prior donation is already excluded from the shortfall calculation and simply stays locked (contracts/pool/tests/flows.rs:732-751 shows the refund-whole-input behavior).
- `flash_loan` computes expected balances as deltas from the live `asset.balance(&pool)` rather than `cash` (contracts/pool/src/ops/flash.rs:53-58, 107-121), so donations neither break nor are absorbed by flash loans.
- `supply`/`repay` credit only the measured balance delta attributable to the payer's own transfer (INV-ACCT-03), so a later supplier cannot claim the stranded amount.

The money-flow audit test confirms the state explicitly: after `token.transfer(&payer, &market.pool, &(7 * UNIT))`, `token.balance(&market.pool)` exceeds the sum of all markets' `cash` by exactly the donation, and every subsequent operation leaves that gap intact (tests/test-harness/tests/pool_money_flow_audit.rs:86-103).

An unprivileged address can reach this by simply calling `token.transfer(their_address, pool_address, amount)` — one of the in-scope entrypoints.

### Impact Explanation
Permanent freezing of funds: any tokens sent directly to the pool contract become permanently unrecoverable. Unlike EVM's ETH analogue, which the vendor could dismiss as "equivalent to burning," the stranded balance here sits inside an active custody contract shared by all markets for that token — it inflates the physical balance while belonging to no book, no share, and no reachable code path. Since one physical pool balance is shared across all hubs for the same token, the lock is also permanent across every hub market of that asset.

### Likelihood Explanation
Requires user error (or a third party) transferring tokens directly to the pool address instead of going through `controller::supply`/`repay`. This is the same low-likelihood, self-inflicted profile as the source report; there is no way for an attacker to force funds into the pool on behalf of a victim. However, there is also no mitigation available after the fact — not even an administrative one — and the error mode is realistic because integrators routinely send tokens to pool/router addresses (e.g., pre-funding a liquidation repayment "directly to the pool," which the liquidator skill itself warns "is a donation").

### Recommendation
Add a `sweep`/`recover` entrypoint that transfers `token.balance(pool) - Σ tracked obligations` (or a governance-clamped amount) to a designated address, or at minimum an owner-only `claim_excess` capped at `balance - total_booked_cash`. Alternatively, document the lock explicitly in the pool README's entrypoint table so integrators know direct transfers are unrecoverable burns, not deferred credit.

### Proof of Concept
```rust
// Any unprivileged address; pool_address is the deployed LiquidityPool contract.
let pool_balance_before = token.balance(&pool);
let cash_before = pool.get_reserves(&hub_asset); // tracked cash

// Direct donation — no protocol call needed.
token.transfer(&user, &pool, &amount);

// Physical balance rises, no book does.
assert_eq!(token.balance(&pool), pool_balance_before + amount);
assert_eq!(pool.get_reserves(&hub_asset), cash_before);

// No entrypoint can release `amount`:
// - recapitalize refunds its own input, ignores the donation (flows.rs:732-751)
// - claim_revenue is capped by tracked cash / revenue shares (INV-ACCT-06)
// - flash_loan balances are deltas from live balance (flash.rs:53-58)
// - supply/repay credit only the caller's own measured delta (INV-ACCT-03)
// `amount` is permanently locked.

#[test]
fn test_recapitalize_refunds_everything_when_market_is_already_backed() {
    let t = TestSetup::new();
    let payer = Address::generate(&t.env);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let token = token::Client::new(&t.env, &t.asset);
    let offered = 250_000_000i128;

    token_admin.mint(&payer, &offered);
    token.transfer(&payer, &t.pool, &offered);
    let before = t.state_snapshot();
    let pool_balance_before_call = token.balance(&t.pool);

    let result = t.client().recapitalize(&hub(&t.asset), &payer, &offered);
    let after = t.state_snapshot();

    assert_eq!(result.actual_amount, 0);
    assert_pool_state_eq(&after, &before);
    assert_eq!(token.balance(&payer), offered);
    assert_eq!(token.balance(&t.pool), pool_balance_before_call - offered);
```
