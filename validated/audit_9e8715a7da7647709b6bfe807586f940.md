### Title
Permissionless `update_account_threshold` lets anyone force a victim's stored LTV down to the new listed value, bricking their `withdraw`/`borrow` solvency check — ([File: contracts/controller/src/risk/params.rs])

### Summary
`controller::update_account_threshold(caller, has_risks, account_ids)` is callable by any authenticated address for arbitrary `account_ids`. With `has_risks = false` (`RiskRefreshScope::LtvOnly`) it restamps each supply position's stored `loan_to_value` to the currently listed config with **no health-factor or owner gate at all**. The borrow/withdraw solvency gate `require_post_pool_risk_gates` reads `ltv_collateral`, which is computed as `min(loan_to_value, liquidation_threshold)` × collateral value. After governance lowers an asset's LTV, a third party can front-run a victim's `withdraw` and force-apply the lower LTV onto the victim's stored positions, making `ltv_collateral < total_debt` (or below `min_borrow_collateral_usd`) so the withdrawal reverts — direct analog of forcing a member's weight down before their `voteProposal`.

### Finding Description
In `sync_account_thresholds` (contracts/controller/src/risk/params.rs:149-237), any caller can list any `account_id`. For each listed supply position, `refresh_supply_risk_params` unconditionally writes `position.loan_to_value = effective_config.loan_to_value` (params.rs:35). The `FullTuple` scope gates liquidation-parameter changes behind `clears_min_hf` (HF ≥ 1.05) and a final HF assertion (params.rs:229-233), but `LtvOnly` applies the LTV change with no gate whatsoever — the HF floor at line 231 only runs `if full_tuple`.

The damage lands in `calculate_ltv_collateral_wad` (contracts/controller/src/risk/totals.rs:76-99) and `calculate_account_risk_totals_body` (totals.rs:190-192): the borrow-limit weight is `position.loan_to_value.min(position.liquidation_threshold)`. `require_post_pool_risk_gates` (contracts/controller/src/risk/validation.rs:29-61) then requires `ltv_collateral >= total_debt` and `ltv_collateral >= min_borrow_collateral_usd` for any account with debt — a check enforced on `withdraw`, `borrow`, and all six strategy entrypoints.

### Impact Explanation
Temporary freezing of user funds / griefing: an attacker can choose the exact moment a victim's borrow capacity shrinks. Example: governance lists an asset's LTV from 8000 to 5000 bps. A victim holding that collateral with `ltv_collateral/debt ≈ 1.2` under the old weight wants to withdraw. The attacker calls `update_account_threshold(attacker, false, [victim_id])`, dropping the victim's stored LTV; the victim's `withdraw` now fails `ltv_collateral >= total_debt` and reverts with `InsufficientCollateral`. The victim must repay debt or add collateral to exit — collateral they may not have. This mirrors M-03's "reduce the member's weight to block their action" pattern, and likewise loses no funds directly.

### Likelihood Explanation
Requires a prior governance LTV decrease (config change is timelocked, so the window between listing change and organic restamping is predictable) and a victim whose margin sits between the old and new effective LTV. Any unprivileged address can trigger it; the only cost is `caller.require_auth()`. Medium likelihood during parameter-change events, which are publicly announced and thus front-runnable.

### Recommendation
Require the account owner (or delegate) to authorize `update_account_threshold` when it lowers a stored LTV, or extend the `FullTuple` safety model to `LtvOnly` — e.g., skip positions where the new `min(LTV, threshold)` weighting would push `ltv_collateral` below debt or the min-borrow floor, rather than only gating liquidation-parameter changes.

### Proof of Concept
1. Governance lowers collateral asset X's `loan_to_value` config via the timelocked listing edit.
2. Victim account supplies X and has debt such that `ltv_collateral(old LTV) >= debt` but `ltv_collateral(new LTV) < debt`. No account op has run yet, so the stored position still carries the old LTV.
3. Attacker calls `controller::update_account_threshold(attacker, false, [victim_id])` — permissionless per contracts/controller/src/lib.rs:386-388 and scripts/permissionless_entrypoints.txt:76.
4. `refresh_supply_risk_params` overwrites the victim's stored `loan_to_value` (params.rs:35) and `set_supply_positions` persists it (params.rs:218).
5. Victim calls `withdraw`; `require_post_pool_risk_gates` computes `ltv_collateral` with `min(new_ltv, lt)` (totals.rs:190) and reverts `InsufficientCollateral` (validation.rs:43), freezing the victim's collateral exit until they deleverage.

Caveat: this is partially bounded — once an LTV change is listed, the victim's own next `supply` would restamp LTV anyway (supply.rs calls the same refresh), and `withdraw` on a `debt_free` account skips the gates entirely (validation.rs:30-32). The exploit value is timing control: forcing the degraded weighting at a moment the victim expected the old one, analogous to front-running `claimAllForMember`.
