### Title
Borrow-index accrual overflows `i128` before `MAX_BORROW_INDEX_RAY` cap engages, permanently freezing the market — ([File: common/src/rates/scaling.rs])

### Summary
The external report is a crash bug: crafted input causes an incorrectly initialized type and a NULL pointer dereference, i.e. attacker-reachable termination (DoS). The direct analog in XOXNO Lending is an unprivileged-reachable arithmetic panic inside interest accrual. `scaled_to_original` multiplies scaled debt by the borrow index with a panicking `Ray::mul`. On a large, high-utilization market, `borrowed * borrow_index` exceeds `i128::MAX` before the `MAX_BORROW_INDEX_RAY` clamp can engage, so every entrypoint that accrues (supply, borrow, withdraw, repay, liquidate, update_indexes) reverts forever. Funds in that market are permanently frozen.

### Finding Description
- `update_borrow_index` caps the *index* at `MAX_BORROW_INDEX_RAY`, but the cap is applied to the index value itself, not to `borrowed * index` products computed during accrual [1](#0-0) .
- Accrual computes total debt via `calculate_supplier_rewards`, which calls `borrowed.mul(env, new_borrow_index)` — `Ray::mul` panics with `MathOverflow` on `i128` overflow [2](#0-1) .
- `scaled_to_original` is the same panicking multiply used everywhere position values are unscaled [3](#0-2) .
- Scaled amounts are denominated in RAY (1e27). A market holding ~1e36 raw units of scaled debt (≈1 billion 18-decimal tokens) hits the `i128::MAX` value ceiling (~1.7e38) once `borrow_index` exceeds ~170× — well below `MAX_BORROW_INDEX_RAY`, which therefore never engages.

The protocol's own harness test documents the failure: after accrual panics, "no repay, no withdraw, no liquidation" succeed because every verb accrues first [4](#0-3) .

### Impact Explanation
Permanent freezing of user funds in the affected market. Once `borrowed * borrow_index` overflows, `update_indexes`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `claim_revenue` all panic on the same multiply before mutating state. Suppliers cannot exit, borrowers cannot repay, and liquidators cannot clear positions — the market is bricked. The in-repo test asserts exactly this: `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` after the cliff [5](#0-4) .

### Likelihood Explanation
Reachable by unprivileged addresses through ordinary `supply` and `borrow` — no privileged call is needed at trigger time; `update_indexes` itself is permissionless. Two preconditions reduce likelihood:

1. The market must hold an enormous scaled book (on the order of 1e36 raw units; the test uses 1 billion 18-decimal tokens with governance-raised caps, so governance must have configured caps that admit such size — a plausible configuration for a legitimate high-cap market rather than something the attacker sets).
2. Utilization must stay high (~98%) for a sustained period so the steep end of the rate curve pushes `borrow_index` past ~170× — the test shows this occurs within the simulated horizon and, per its comment, earlier than the bound claimed in `docs/reference/formulas.md` [6](#0-5) .

An attacker with sufficient capital can accelerate this deliberately by supplying the liquidity and driving utilization to the steep segment; the victim suppliers' funds are then frozen regardless of the attacker's subsequent actions.

### Recommendation
Make accrual saturate instead of panic:
- Bound `borrow_index` (and `supply_index`) so that `borrowed * index` cannot overflow, e.g. clamp `new_borrow_index` to `min(MAX_BORROW_INDEX_RAY, i128::MAX / borrowed)` inside `update_borrow_index` — the cap must account for book size, not just the index constant.
- Alternatively, use saturating/`I256` intermediate math in `calculate_supplier_rewards` and `scaled_to_original` call sites on the accrual path, capping `new_total_debt` at `i128::MAX` rather than reverting.
- Add an index-growth guard driven by `max_utilization`/`caps` validation so configured caps cannot admit a book whose scaled value can reach the `i128` ceiling before the index cap.

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
