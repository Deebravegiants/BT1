This confirms a direct analog to the Eywa-CLP report. `IntentGatewayV2.placeOrder()` reads `_params.protocolFeeBps` (or a per-destination override in `_destinationProtocolFees`) at execution time and deducts it from the user's escrowed input with no user-supplied maximum-fee bound, exactly mirroring `PortalV2.unlock()` reading the mutable `Whitelist` fee at execution time.

### Title
Users cannot cap the IntentGateway protocol fee applied at order placement, exposing already-broadcast orders to a fee increase - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder()` computes the protocol fee to deduct from a user's escrowed input tokens by reading the live, governance-mutable `_params.protocolFeeBps` (or `_destinationProtocolFees[destinationHash]` override) at the moment the transaction executes, not at the time the user signed/quoted the order. There is no field on `Order` or `placeOrder()` allowing the caller to specify a maximum acceptable fee, so a fee increase that lands on-chain between quoting and mining silently changes the economics of an already-submitted order, exactly the class of issue described in the external report for `PortalV2.unlock()`.

### Finding Description
`placeOrder()` looks up the fee to charge only after the inputs have already been pulled from the user: [1](#0-0) 

`protocolFeeBps` comes from `_params` (or a destination-specific override), both of which are mutable via cross-chain governance through `_updateParams`, and are bounded only by `< 10_000` (i.e., up to 99.99%): [2](#0-1) 

The `Order` struct and `placeOrder(Order,bytes32)` signature carry no user-specified fee ceiling; the fee actually applied is whatever `_params.protocolFeeBps`/`_destinationProtocolFees[...]` happen to be when the transaction is mined, not what the user observed off-chain (e.g., via `quoteIntent()`/`readProtocolFeeBps()`) when constructing the order: [3](#0-2) 

The docs explicitly confirm the fee is deducted at placement based on the value in effect at execution, and is non-refundable even on cancellation: [4](#0-3) 

This is structurally identical to the reported `PortalV2.unlock()` issue: a fee that can be legitimately raised (not necessarily maliciously) by the controlling party, applied against a transaction that is already in flight, with no mechanism for the submitter to bound the maximum fee they are willing to pay.

### Impact Explanation
Because `protocolFeeBps` (up to 9,999 bps / 99.99%) and per-destination overrides can change between order construction and mining, a user's escrowed input can be reduced by far more than the amount they agreed to when signing the transaction. The reduced (fee-deducted) `order.inputs` become the actual escrow amount used both for the order commitment and for what a solver is paid on fulfillment, and the fee itself is retained by the protocol as non-refundable "dust" even if the order later expires or is cancelled. A user has no way to enforce "do not execute if the fee exceeds X," so any fee update that races an in-flight `placeOrder()` transaction directly and irreversibly reduces the value the user receives, without any recourse (the deducted fee is not part of the refundable escrow on cancellation).

### Likelihood Explanation
Fee parameters are changed only through cross-chain governance (`onAccept` → `UpdateParams` → `_updateParams`), so triggering this requires a legitimate fee-parameter update to be in flight while a user's `placeOrder()` transaction is pending — a routine, foreseeable event (protocol fee adjustments are an expected operational action, as shown by the multiple governance tests exercising `protocolFeeBps` changes), not a hypothetical or purely adversarial scenario. Any user submitting an order during or shortly before a scheduled/announced fee change is exposed, and there is no timelock, notice period, or per-order fee ceiling to prevent it.

### Recommendation
Add a user-supplied maximum acceptable protocol fee (in bps or absolute amount) to the `Order`/`placeOrder()` call, and revert if the effective `protocolFeeBps` (default or destination-specific) at execution time exceeds that bound. Alternatively, enforce a mandatory notice/timelock period between a `ParamsUpdate`/`DestinationFee` change being received via `onAccept` and it taking effect, so in-flight orders are unaffected by a fee change that was not visible when they were signed.

### Proof of Concept
1. Governance sets `_params.protocolFeeBps = 5` (0.05%) as documented for current deployments.
2. A user calls `quoteIntent()`/reads `protocolFeeBps` off-chain, expecting a 0.05% deduction, and constructs/signs a `placeOrder(order, graffiti)` transaction reducing `order.inputs` by 0.05%.
3. Before the transaction is mined, governance dispatches an `UpdateParams` request via `IntentsBase.onAccept` → `_updateParams`, raising `_params.protocolFeeBps` to, e.g., 5000 (50%) — a value well within the allowed range (`< 10_000`), as exercised by `testProtocolFeeWith10Percent`/similar tests: [5](#0-4) 
4. The user's `placeOrder()` transaction is then mined and reads the now-updated `protocolFeeBps`, deducting 50% of the escrowed input instead of the expected 0.05%, with the excess retained permanently as protocol dust and no way for the user to have capped or rejected this outcome.

     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }

export async function readProtocolFeeBps(
	chainConfigService: ChainConfigService,
	source: IntentQuoteChainContext,

	const gatewayAddress = chainConfigService.getIntentGatewayAddress(source.stateMachineId)
	if (!gatewayAddress || gatewayAddress === "0x" || gatewayAddress === zeroAddress) {

		address: gatewayAddress,
		abi: IntentGatewayV2.ABI,
		functionName: "params",
	})) as GatewayParams

	const protocolFeeBps = Array.isArray(gatewayParams)
		? BigInt(gatewayParams[4] as bigint | number | string)
		: BigInt((gatewayParams as GatewayParamsObject).protocolFeeBps ?? 0)
	if (protocolFeeBps < 0n || protocolFeeBps >= BPS_DENOMINATOR) {
		throw new Error(`Invalid IntentGateway protocol fee: ${protocolFeeBps} bps`)
	}
	return protocolFeeBps
}

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

<Callout type="warn">
Do not build an order by reducing the input yourself to account for the protocol fee. Send the gross input amount and use the amounts returned by `quoteIntent()`. The quote prices the fee-reduced escrow amount; reducing it again would make the order smaller than intended.
</Callout>
```
