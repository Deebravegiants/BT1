### Title
Gateway instance re-registration permanently strands escrowed order funds in-flight - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` trusts a single, mutable mapping (`_instances[keccak256(chain)]`) to authenticate cross-chain settlement messages (`RedeemEscrow`/`RefundEscrow`) for a given destination gateway. Hyperbridge governance can repoint this mapping to a new gateway address at any time via a `NewDeployment` request, exactly analogous to Skale's `ValidatorService.disableValidator`: a legitimate, non-malicious admin action that revokes trust in an entity while funds already committed against that entity (escrow tied to already-dispatched settlement messages from the *old* gateway) are left with no recovery path.

### Finding Description
`_addDeployment` unconditionally overwrites the instance mapping with no regard for orders that are already in flight against the previous address: [1](#0-0) 

Every incoming settlement (`RedeemEscrow` after a solver fills an order, `RefundEscrow` after a destination-side cancellation) is authenticated against whatever is *currently* stored in that mapping: [2](#0-1) 

The request kinds and the mapping semantics are documented here: [3](#0-2) [4](#0-3) 

Sequence that traps funds:
1. A user places a cross-chain order on the source chain; input tokens are escrowed under `_orders[commitment][token]`.
2. A solver fills the order on the destination chain (the gateway instance registered at that time), and the destination gateway dispatches a `RedeemEscrow`/`RefundEscrow` message back to the source chain identifying itself as `from = <old destination gateway address>`.
3. Before that message is relayed/delivered, Hyperbridge governance issues a `NewDeployment` for that same destination state machine — e.g., to migrate/upgrade the destination gateway to a new address — overwriting `_instances[keccak256(destination)]`.
4. When the pending message is finally delivered, `_authenticate` compares `_instance(request.source)` (now the *new* address) against `request.from` (the *old* address) and reverts with `Unauthorized`.
5. The host records the delivery as undelivered/reverted. There is no other function that can release that specific escrow: `_filled[commitment]` was never set, `withdraw()` is only reachable through the same authenticated `onAccept`/`onGetResponse` path, and the user cannot re-trigger a same-chain cancel because the order is cross-chain and its cancellation route also depends on this same `_instances` state being consistent with what was true when the order was placed.

This mirrors the SKALE report precisely: revoking trust in an entity (validator / gateway instance) that already has funds committed to it (delegations / escrow) leaves those funds effectively locked, because no code path accounts for orders/delegations that predate the revocation.

### Impact Explanation
Escrowed user funds (input tokens for cross-chain orders whose settlement message races a legitimate governance `NewDeployment` update) become permanently undeliverable and unrecoverable through the gateway's normal flows — this is a High severity freezing-of-funds condition triggered by a routine, non-malicious governance action combined with ordinary in-flight order traffic, not an attacker-controlled admin.

### Likelihood Explanation
Instance migrations are an expected part of gateway upgrades/redeployments (the `NewDeployment` request kind exists specifically for this). Any order filled or cancelled shortly before such a migration is redeployed and whose settlement message has not yet been delivered will race the mapping update. Given that gateway redeployments are a normal operational event and orders are constantly in flight, the likelihood of hitting this window in practice is non-trivial, though it requires the specific timing coincidence rather than being trivially reproducible by an attacker at will.

### Recommendation
Version the gateway instance mapping (e.g., accept messages from either the current or the immediately-previous registered instance for a grace period), or require governance to drain/settle all in-flight messages for a destination before rotating its instance, or add an explicit emergency-recovery path (analogous to "release delegations" in the SKALE recommendation) that lets the source-chain owner reclaim escrow for a commitment whose destination instance was superseded before delivery.

### Proof of Concept
Not independently reproduced in this analysis; the reasoning is based on static code paths (`_addDeployment` overwrite plus `_authenticate`'s equality check against the live `_instances` entry) and the corresponding governance-driven test flow (`testOnAcceptGovernanceRejectsUnlistedRelayer` / `testInstance` in `evm/tests/foundry/IntentGatewayV2Test.sol`) showing that `NewDeployment` immediately and unconditionally replaces the trusted instance address used for authentication. I was unable to fully verify, within available tool calls, whether any secondary recovery mechanism (e.g., an owner-only rescue function) exists elsewhere in the current `IntentGatewayV2.sol`/`IntentsBase.sol` that would mitigate this — this should be confirmed against the full file contents before treating the finding as conclusive.

     * Called when Hyperbridge governance adds support for a new chain. The gateway
     * address is stored in `_instances` keyed by the hash of the state machine ID.
     *
     * @param body The deployment info containing the state machine ID and gateway address.

    function _addDeployment(Deployment memory body) internal {
        _instances[keccak256(body.chain)] = body.gateway;
        emit DeploymentAdded({chain: string(body.chain), gateway: body.gateway});
