### Title
Unauthenticated stateless Emporium operations allow theft of stranded token residue - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes stateless `EmporiumOperation`s as raw calls from the Emporium contract itself with zero authorization when `stack.signerAddress == address(0)`, and `verifyWallet` explicitly returns early in that case without checking anything about who is entitled to any balance already sitting in the Emporium contract. Any ERC20/NFT balance left in Emporium after a prior action (because it wasn't listed in that action's `circomData.erc20TokenAddresses`) is therefore a shared, unauthenticated pool that any unrelated caller can drain with their own unrelated proof.

### Finding Description
Broken equality: the `from` of an ERC20/ERC721 transfer executed via a stateless `EmporiumOperation` should be authorized by whoever caused those tokens to accrue at Emporium; in practice it is authorized by nobody, since stateless ops bypass both the EIP-712 wallet signature check and any check against `circomData.erc20TokenAddresses`/`deltaAmountChanges` for tokens outside that array.

Code path:
- `runAction` decodes `EmporiumStack` from `externalActionMetadata` and calls `verifyWallet(stack, circomData)` [1](#0-0) .
- `verifyWallet` marks the message used and returns immediately with no signature check at all when `stack.signerAddress == address(0)` [2](#0-1) .
- In the ops loop, CASE 2 (stateless) executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, only rejecting the wallet-only selectors, with no constraint tying `op.endpoint`/`op.callData` to tokens the caller actually deposited [3](#0-2) .
- The post-execution accounting only inspects balances for tokens explicitly listed in `circomData.erc20TokenAddresses` (`balancesBefore`/`balancesAfter` loop), so any token not in that array — e.g., an LP token minted to Emporium by a prior action that only listed the deposit token — is never checked or swept and simply remains at the Emporium contract's own balance indefinitely [4](#0-3) .
- For the Emporium "Min" proof path (`HINKAL_EMPORIUM_ACTION_ID` with `erc20TokenAddresses.length == 0`), the public input is reduced to `emporiumMessage`, `timeStamp`, `calldataHash` only [5](#0-4) , meaning an attacker needs no real deposited value at all to submit a valid proof for an arbitrary `EmporiumStack`.

Exploit flow: a victim's earlier action performs a stateless deposit-like call (CASE 2) into a vault whose LP-token output is not included in that action's `erc20TokenAddresses`; the LP tokens stay held at the Emporium contract. An unprivileged attacker then submits their own `transact` call using the Min-circuit Emporium path with `stack.signerAddress = address(0)` and an ops array containing `{endpoint: lpToken, invokeWallet: false, value: 0, callData: transfer(attacker, bal)}`. `verifyWallet` short-circuits (no signature required), the call executes as `lpToken.transfer(attacker, bal)` with `msg.sender == Emporium`, succeeding because Emporium holds the balance, and since `lpToken` is absent from `circomData.erc20TokenAddresses` in the attacker's own action, no balance-accounting check ever fires to prevent or detect the drain.

### Impact Explanation
Any token balance stranded at Emporium — whether from a genuine token-list omission, a partially-completed multi-step DeFi flow, dust, refunds, or reward accrual from a stateless call — is stealable in full by any unrelated party with a single transaction and no signature or ownership check. This is direct theft of another user's funds residing in a protocol contract, matching Critical severity (direct theft of funds).

### Likelihood Explanation
The only precondition is that some token balance accrues at the Emporium contract's address outside of what a given transaction's `circomData.erc20TokenAddresses` tracks — plausible any time a stateless external call (deposit/mint/swap into an LP or reward token) is performed and the token list omits the resulting asset, whether by design of a multi-step flow or by a mistake in how `erc20TokenAddresses` is constructed off-chain. The attacker's cost is minimal (one Min-circuit proof, no real deposit required), and the attack is fully repeatable against every future occurrence of stranded balance.

### Recommendation
Do not allow stateless (`signerAddress == address(0)`) `EmporiumOperation`s to target arbitrary endpoints/calldata without binding them to funds the caller actually contributes in the same transaction. At minimum: require that every token touched by a stateless op appear in `circomData.erc20TokenAddresses` for that same call (so any inflow triggers the existing balance-accounting/UTXO-out logic), or maintain a per-message/per-depositor claim on any Emporium-held balance and require CASE 2 ops to be constrained to endpoints agreed upon by that specific depositor's own signed action rather than being fully attacker-controlled and unauthenticated.

### Proof of Concept
Hardhat test:
1. Deploy Emporium, a mock LP-vault ERC20 (`deposit()` mints LP tokens to `msg.sender`), and a mock underlying deposit token.
2. Victim performs a `transact` call whose `EmporiumStack` (stateless, `signerAddress = address(0)`) has ops `[{endpoint: vault, callData: deposit(amount)}]`, with `circomData.erc20TokenAddresses` containing only the deposit token (not the LP token) and matching `deltaAmountChanges`. Assert this succeeds and `lpToken.balanceOf(emporium) == bal > 0`.
3. Attacker generates their own valid Min-circuit Emporium proof (`erc20TokenAddresses.length == 0`), builds `EmporiumStack` with `signerAddress = address(0)` and ops `[{endpoint: lpToken, invokeWallet: false, value: 0, callData: transfer(attacker, bal)}]`, and calls `Hinkal.transact`.
4. Assert the call succeeds and `lpToken.balanceOf(attacker) == bal` while `lpToken.balanceOf(emporium) == 0`, proving theft of the victim's residue with no signature or ownership check at any point.
