### Title
Webhook Shop-Domain Spoofing via HMAC Scope Mismatch Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` authenticates the JSON body bytes only. The `shop` value — read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — is never part of the signed content, yet it is passed straight through to the app's webhook handler as the trusted tenant identifier.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `Request#shop` simply reads a header with no cross-check against the HMAC: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC purely over `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a successful HMAC check as proof the whole request — including `request.shop` — is authentic, and forwards it unchanged into `WebhookMetadata`, which apps use as the tenant key: [4](#0-3) [5](#0-4) 

The identity binding broken is: `HMAC-verified bytes (raw_body) ≠ bytes acted upon (shop header used as tenant key)`. This is the same bug class as the report — a value ("shop") that downstream logic treats as authenticated/trusted, but that is not actually covered by the cryptographic check that's supposed to authenticate the request.

Documentation confirms host apps are expected to key their logic off `data.shop` for the tenant, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [6](#0-5) 

### Impact Explanation
An attacker who controls their own Shopify store (a legitimate, unprivileged merchant install of the app) can capture a genuine webhook Shopify sends them — which has a body and HMAC signed with the app's real `api_secret_key` — and replay that exact `(raw_body, hmac-sha256)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because `to_signable_string` never includes `shop`, the signature still validates, and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain while the body content is actually the attacker's own store data. Any host app that uses `data.shop` to look up per-tenant state (install records, feature flags, order/customer sync, GDPR redaction routing, billing) can be tricked into associating attacker-controlled data with another merchant's tenant, resulting in cross-tenant data confusion/corruption in the host application. This matches the Critical "cross-tenant access" impact category — the credential boundary between shops is broken using only a legitimately-installed unprivileged merchant account.

### Likelihood Explanation
Requires only: (1) being a merchant who has installed the app (no special privilege), (2) capturing one legitimate webhook payload+HMAC from their own store (visible in their own webhook endpoint logs or via a personal receiving endpoint), and (3) sending a crafted HTTP request with a modified shop header to the app's known public webhook callback URL. No knowledge of `api_secret_key` or access tokens for other shops is needed — the exploit reuses a valid signature under the attacker's own domain and just swaps the shop-identifying header, since that header sits entirely outside the signed content.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable content, or otherwise cryptographically bind them to the payload before trusting `request.shop` in `Registry.process`. If Shopify's actual webhook signing scheme only signs the raw body (matching Shopify's documented behavior), the gem should document this explicitly and/or require host apps to independently verify `shop` against their own webhook subscription/shop record before trusting it, since as currently written `ShopifyAPI::Webhooks::Registry.process` implies a fully-authenticated `WebhookMetadata`, including `shop`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a legitimate webhook (e.g. `orders/create`), capturing the exact `raw_body` and `x-shopify-hmac-sha256` header value Shopify sent (both valid, signed with the real `api_secret_key`).
2. Attacker sends a POST request to the app's public webhook endpoint (the same route configured via `Registry.add_registration`) with:
   - Body: the captured `raw_body` (unchanged)
   - Header `x-shopify-hmac-sha256`: the captured, still-valid signature
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic`: unchanged
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only — passes, since the body/HMAC pair is untouched.
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`, i.e., a forged webhook that the host app will process as though it genuinely originated from the victim shop.
