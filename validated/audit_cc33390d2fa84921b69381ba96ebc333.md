### Title
Webhook `shop-domain` header is trusted but not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only authenticates the raw JSON body, never the `shop-domain` header [2](#0-1) . Yet `Registry.process` passes `request.shop` straight into `WebhookMetadata`, which the host app's handler treats as the authenticated tenant identifier [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`bytes verified by HMAC == bytes the app relies on to identify the shop`

In this gem that equality is broken: `hmac` is computed over `@raw_body` only [4](#0-3) , and `shop` is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never included in `to_signable_string` [5](#0-4) . `HmacValidator.validate` verifies `verifiable_query.to_signable_string` against the secret-keyed HMAC, and for `Webhooks::Request` that string is exactly the raw body, excluding all headers [6](#0-5) . After validation passes, `Registry.process` builds `WebhookMetadata` using `request.shop` — the unauthenticated header — and hands it to the app's handler as the shop for that webhook [7](#0-6) . The gem's own documentation reinforces the false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify" and describing `data.shop` simply as "The shop domain of the webhook" with no caveat that it is unauthenticated [8](#0-7) [9](#0-8) .

### Impact Explanation
If a multi-tenant app trusts `data.shop` (as the gem's docs instruct) to key session lookups, per-shop data storage, or webhook deduplication, an attacker who can obtain any single valid `(body, hmac)` pair for a topic — e.g., from their own installed shop, which they legitimately control — can replay that request to the shared webhook endpoint while substituting the `shop-domain` header for a victim shop. The HMAC still validates because it never covered the header, letting the attacker inject events under a false tenant identity (cross-tenant data confusion).

### Likelihood Explanation
Exploitation requires the attacker to already possess a legitimate `(raw_body, hmac)` pair, which in practice is delivered directly from Shopify to the app's backend server-to-server, not exposed to the merchant/attacker's browser or any channel they control. Reliably capturing that pair generally requires visibility into the app's own server-side traffic (interception of server-to-server delivery), which falls into the excluded categories of this analog set (no credential/access-token requirement is at play, but the practical capture step depends on network-level access the attacker does not have as an ordinary internet user). This significantly limits real-world likelihood despite the root-cause binding gap being real and present in the gem's own code.

### Recommendation
Include the `shop-domain` (and other identifying headers such as `topic`, `webhook-id`) in the HMAC-signable material, or otherwise have `Registry.process` cryptographically bind the shop identity to the verified payload before constructing `WebhookMetadata`; at minimum, update documentation to explicitly state that `data.shop` is not covered by the HMAC and must not be used as an authentication boundary without additional verification (e.g., confirming the shop has an active, previously-established session).

### Proof of Concept
1. Attacker has a legitimate webhook delivery for topic `orders/create` for their own shop `attacker.myshopify.com`, with raw body `B` and valid `hmac-sha256` header `H` computed by Shopify using the app's `client_secret`.
2. Attacker POSTs the same `B`/`H` to the app's shared webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request#hmac` returns `H`; `to_signable_string` returns `B` [10](#0-9) .
4. `HmacValidator.validate` succeeds because the signature check only depends on `B` and `H`, ignoring headers [2](#0-1) .
5. `Registry.process` invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` [3](#0-2) , causing the app to process attacker-controlled order data under the victim's tenant identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
