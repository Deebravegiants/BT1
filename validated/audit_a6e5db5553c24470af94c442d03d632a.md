## Analog Found

### Title
`placeOrder` swaps native ETH for the protocol fee token using `block.timestamp` as the Uniswap V2 deadline, exposing users to unbounded-latency MEV sandwiching - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
When a user calls the permissionless `placeOrder` function and pays the protocol's transaction fee in native ETH, `IntentGatewayV2` swaps that ETH for the exact fee-token amount via Uniswap V2, passing `block.timestamp` as the swap's `deadline` argument. This mirrors the reported Tokemak bug class: a `block.timestamp` deadline is not a real deadline — it is re-evaluated at whatever block eventually includes the transaction, so the swap never actually expires while sitting unconfirmed.

### Finding Description
In `placeOrder`, when `order.fees > 0` and the caller supplied native token value (`msgValue > 0`), the contract calls Uniswap V2 directly: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = feeToken;
        uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
        msgValue -= amounts[0];
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }
    ...
```

This is directly reachable by any unprivileged caller submitting a `placeOrder` transaction with `msg.value` and a nonzero `order.fees` — no special privilege is required, matching the same code path exercised in `evm/tests/foundry/IntentGatewayV2Test.sol` (e.g. the predispatch swap tests use `block.timestamp + 3600` for their own user-supplied calls, but the protocol's own internal fee-swap hardcodes `block.timestamp`).

`swapETHForExactTokens`'s `deadline` parameter is meant to bound how long a signed/submitted transaction remains valid before a pool-state check should cause it to revert (protecting against stale execution in adverse price conditions). Passing `block.timestamp` defeats this: the EVM evaluates `block.timestamp` against the block the transaction is *actually mined in*, not the block it was signed/submitted in. Consequently, a block builder, searcher, or colluding validator can hold the `placeOrder` transaction in the mempool/private order flow for as long as it wishes and choose the most opportune moment (e.g., after manipulating the WETH/feeToken pool price via a sandwich) to include it — the deadline check will always pass because it is compared against the current, not the original, timestamp.

### Impact Explanation
Because the swap is `swapETHForExactTokens` with `amountInMaximum` implicitly bounded by `msgValue`, worst case for a given user is either (a) the transaction reverts if the manipulated price makes the exact fee amount unaffordable, or (b) the swap succeeds at a worse rate, spending more of `msgValue` on the swap and refunding less unspent ETH back to `msg.sender` via `_sendValue`. The delta between the fair-market cost and the sandwiched cost is value directly extracted from the user's escrowed native tokens on every fee-paying `placeOrder` call — a systemic value-leakage vector on IntentGateway's core order-placement flow, not a one-off griefing bug. This satisfies "concrete theft ... of funds" at Medium severity since the loss is bounded per-transaction but is a native, repeatable arbitrage opening enabled purely by the missing real deadline.

### Likelihood Explanation
`placeOrder` is the primary, permissionless entry point of the IntentGateway and is expected to be called constantly by ordinary users; any order with `order.fees > 0` paid in native ETH triggers this code path. MEV searchers/builders routinely watch for exactly these swap-then-refund patterns since profit is essentially guaranteed via sandwiching whenever a deadline check is non-binding. Likelihood is therefore high whenever this fee-payment path is used in production with a live Uniswap V2 fee-token pool.

### Recommendation
Do not use `block.timestamp` as the AMM deadline. Accept a caller-supplied, sensible deadline (e.g., pass a `deadline` parameter through `placeOrder`/order struct, or a short protocol-defined `block.timestamp + MAX_SWAP_WINDOW` computed and enforced at submission time by requiring a signed intent with an expiry) so the transaction becomes provably stale and reverts if not included within a bounded window. Combine this with an explicit `amountInMaximum`/slippage bound already partially present, and consider using a TWAP-based or oracle-sanity check on the WETH→feeToken rate before performing the swap.

### Proof of Concept
1. Attacker monitors the mempool for `IntentGatewayV2.placeOrder` calls with `msg.value > 0` and `order.fees > 0`.
2. Attacker (as a searcher/builder) delays inclusion of the victim's transaction while sandwiching the WETH/feeToken pool: front-run buy of `feeToken` to raise its price in WETH terms, then let the victim's `swapETHForExactTokens` execute (paying near-`msgValue` ETH for `order.fees` tokens because `block.timestamp` deadline never expires), then back-run sell to realize profit.
3. The victim receives less unspent-ETH refund via `_sendValue` (`evm/src/apps/IntentGatewayV2.sol` line 396) than they would have under fair pricing, while the attacker profits — replicated on every such fee-paying order.
