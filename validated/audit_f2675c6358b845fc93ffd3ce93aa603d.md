### Title
Panic (chunk-apply crash / chain stall) from `.unwrap()` on `receiver_shard_id()` in the delayed-receipt queue filter after multiple reshardings - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The Rubicon bug is a "poison item stuck at the head of a strictly-ordered FIFO/priority queue" DoS: one malformed offer can never be processed, but the processing loop insists on handling it first, so it reverts every call that touches the queue. The structurally identical pattern exists in nearcore's delayed-receipt queue: `DelayedReceiptQueueWrapper::pop` must pop items strictly in FIFO order and calls `receipt_filter_fn`, which does an unchecked `.unwrap()` on a `Result` that can legitimately be `Err` for a `GlobalContractDistribution` receipt whose `target_shard` can no longer be mapped into the current shard layout after repeated resharding. Instead of an EVM `revert`, the nearcore analog is a Rust panic during chunk application, which halts the affected shard.

### Finding Description
`Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) special-cases `GlobalContractDistribution` receipts: if the receipt's `target_shard` is not part of the current `ShardLayout`, it tries `shard_layout.resolve_to_current_shard(target_shard)` and, if that also fails, explicitly returns `Err(EpochError::ShardingError(...))` — i.e. the function is designed to be fallible for exactly this receipt kind: [1](#0-0) 

However, the only caller inside the delayed-receipt pop path discards that `Result` with `.unwrap()`: [2](#0-1) 

`DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn` on every item it dequeues from the FIFO trie-backed queue, in strict order (`core/store/src/trie/receipts_column_helper.rs` `TrieQueue`), so a single bad entry cannot be skipped without panicking first: [3](#0-2) 

`process_delayed_receipts` drives this pop in a loop each chunk, so the same doomed receipt is retried until the shard's compute/proof budget frees enough headroom to reach it, at which point the panic occurs deterministically: [4](#0-3) 

The repository already contains a regression test that documents this exact scenario: a `GlobalContractDistribution` receipt is intentionally kept in the delayed queue while the shard undergoes **two** consecutive dynamic-resharding splits, after which draining the queue is expected to either panic in `receipt_filter_fn()` (if unfixed) or otherwise stall the chain: [5](#0-4) 

The trigger requires no privileged role: any account can (1) deploy a global contract, which creates a `GlobalContractDistribution` receipt targeting the deployer's current shard, and (2) is a normal, unprivileged transaction — the receipt just needs to sit in the delayed queue across two resharding boundaries (e.g., because the shard is saturated with ordinary `FunctionCall` gas-burning transactions, which is itself achievable by an unprivileged account paying gas).

### Impact Explanation
If `resolve_to_current_shard` cannot map an old `target_shard` through the split history (e.g., because two or more resharding generations occurred, or the split-history metadata does not retain the needed ancestor), `receiver_shard_id()` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics inside `Runtime::apply` while draining the delayed queue. Because the queue is strictly FIFO and the panic recurs every time the shard tries to reach that receipt, this is a **chain-halting DoS**: the shard can no longer produce valid chunks past that point without operator intervention (matching the "node panic / chain stall" impact criterion), directly analogous to Rubicon's "single unfillable head-of-queue offer blocks all subsequent order-book operations."

### Likelihood Explanation
Reaching the vulnerable path requires: (a) an account deploying a global contract (ordinary, permissionless transaction), (b) the resulting `GlobalContractDistribution` receipt remaining in the delayed queue while the network performs two or more resharding events that change the shard containing the original `target_shard`. Dynamic/automatic resharding (`DynamicReshardingConfig`) is a live protocol feature, so this is achievable under normal network operation over time, not merely a contrived test setup — the existing test only forces determinism (via `force_split_shards` and compute-saturating transactions) to make the race reliable in a short time window, but the same conditions can occur naturally as shards grow and split repeatedly while a distribution receipt is congestion-delayed.

### Recommendation
Do not `.unwrap()` the `Result` from `receiver_shard_id()` in `receipt_filter_fn`. Propagate the error as a `RuntimeError`/`StorageInconsistentState` (consistent with how other delayed-receipt inconsistencies are already handled, e.g. `runtime/runtime/src/lib.rs:2522-2534`) so it can be handled by validators, or — better — make `resolve_to_current_shard` retain enough shard-split ancestry to always resolve any historical `target_shard`, guaranteeing `receiver_shard_id` never fails for receipts that were valid when enqueued.

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs` (lines 30-186) is a working PoC: it deploys a global contract, saturates the shard's compute budget with ordinary transactions to force the resulting `GlobalContractDistribution` receipt into the delayed queue, forces two sequential shard splits via `DynamicReshardingConfig`, then stops saturating and lets the delayed queue drain — asserting that the chain height keeps advancing (i.e., failing/panicking if `receipt_filter_fn`'s `.unwrap()` on a now-unresolvable `target_shard` triggers a chunk-apply panic).     pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }
