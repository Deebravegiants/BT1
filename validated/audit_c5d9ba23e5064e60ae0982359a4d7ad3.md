### Title
Front-Running of Nonce Account Initialization Due to Missing Signer Check in `InitializeNonceAccount` - (File: `programs/system/src/system_instruction.rs`)

### Summary
`initialize_nonce_account()` in `programs/system/src/system_instruction.rs` sets the nonce authority on a system-owned, correctly-sized-but-uninitialized account without requiring any signature from the account itself or from any signer tied to the account's creation. If account creation (`Allocate`/`CreateAccount`) and `InitializeNonceAccount` are submitted as separate transactions rather than atomically combined (as the SDK helper `create_nonce_account` normally does), any unprivileged party can observe the pending account and race to submit `InitializeNonceAccount` first, seizing the nonce authority — the exact "deploy vs. initialize is not atomic" front-running pattern described in the external report for `EthFoxVault`.

Note that unlike `allocate()`, which explicitly enforces `address.is_signer(signers)` before mutating the account: [2](#0-1) 

`initialize_nonce_account()` performs no signer check at all — it only verifies the account is writable and in the `Uninitialized` state, then unconditionally writes the caller-supplied `nonce_authority` into the account: [3](#0-2) 

The processor dispatch for `SystemInstruction::InitializeNonceAccount` confirms only a single account (the nonce account itself) plus sysvars are required — no signature requirement is layered on top: [4](#0-3) 

The SDK-level safety net is that `create_nonce_account()` bundles `CreateAccount` + `InitializeNonceAccount` into one atomic message/transaction, and the CLI's `process_create_nonce_account` follows this pattern: [5](#0-4) 

However, this atomicity is a convention enforced only by client tooling, not by the program itself. Any caller (script, integrator, custom tooling analogous to the report's task scripts that bypass the factory pattern) that allocates a system-owned account sized for `nonce::State` in one transaction and initializes it in a later, separate transaction exposes a window where an unrelated party can submit `InitializeNonceAccount(attacker_pubkey)` against that account first — winning the race purely by fee/priority, with no signature over the nonce account or its intended owner required.

### Impact Explanation
A successful front-run allows an attacker to become the nonce authority of an account funded and sized by the victim, without paying the account's rent-exempt deposit. This grants the attacker durable-nonce authority: control over advancing/withdrawing/authorizing the account (subject to further authority checks), effectively hijacking the account's intended durable-transaction/replay-protection role and the victim's locked rent-exempt lamports, mirroring the "gain control over the contract" impact in the original report.

### Likelihood Explanation
This requires an integrator to deviate from the safe, SDK-provided atomic `create_nonce_account` pattern by splitting account creation and `InitializeNonceAccount` across separate transactions — exactly the anti-pattern flagged in the external report (task/deploy scripts not combining creation and initialization atomically). Given `InitializeNonceAccount` imposes no signer requirement, any transaction observer can win this race with ordinary fee bidding; no privileged or validator role is needed.

### Recommendation
Require that `InitializeNonceAccount` be signed by the nonce account itself (or by the account originally designated during creation), mirroring the signer check already present in `allocate()`. Alternatively/additionally, document and enforce (e.g., via a lint or wrapper) that all nonce-account creation flows must use the atomic `create_nonce_account`/`create_nonce_account_with_seed` builders so creation and initialization occur in the same transaction.

### Proof of Concept
1. Victim submits Transaction A: `Allocate`/`CreateAccount` sized to `nonce::state::State::size()`, owned by `system_program`, for pubkey `N` (funded to rent-exempt minimum), intending to follow up with `InitializeNonceAccount(victim_authority)` in a later transaction.
2. Attacker observes Transaction A land (or observes it in-flight) and submits Transaction B containing `SystemInstruction::InitializeNonceAccount(attacker_authority)` targeting account `N`, without needing to sign as `N` or provide any authorization tied to the account's creator.
3. Because `initialize_nonce_account()` in `programs/system/src/system_instruction.rs:163-211` only checks `account.is_writable()` and `State::Uninitialized`, Transaction B succeeds if it lands before the victim's intended initialize transaction, setting `attacker_authority` as the nonce authority — [6](#0-5) .
4. The victim's subsequent `InitializeNonceAccount(victim_authority)` now fails with `InstructionError::InvalidAccountData` since the state is already `Initialized`, per the guard at [7](#0-6) , leaving the attacker in control of the account and its rent-exempt lamports.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
