### Title
Fraud-check engine silently defaults to "no fraud detected" when checks are unconfigured, masking fraud/liveness enforcement - (File: src/plans/fraud_check.rs)

### Summary
The Frax report describes a pricing function (`collatDolarValue`) that silently substitutes a safe-looking default ($1) when an oracle is not configured, causing the protocol to misjudge collateralization instead of failing safe or flagging the missing configuration. The analogous pattern in orb-core is the fraud-check engine wrapper in `src/plans/fraud_check.rs`, where the number of fraud checks is hard-coded to zero (`N_FRAUD_CHECKS: usize = 0`) and the check arrays used to compute `fraud_detected()` are all empty, so the function that is supposed to gate a signup on fraud/liveness signals always evaluates over an empty set and returns a default "not fraudulent" result rather than failing safe or surfacing that no fraud checks are actually configured.

### Finding Description
`src/plans/fraud_check.rs` defines: [1](#0-0) 
and the corresponding `Report::fraud_checks()`, `enabled_checks_from_config()`, and `feedback_messages()` all return empty arrays sized by `N_FRAUD_CHECKS`: [2](#0-1) 

`fraud_detected()` and `fraud_detected_with_config()` iterate over these empty, statically-sized arrays: [3](#0-2) 

Because the arrays are empty, `.any(|&v| v)` and the `filter_map` over zipped iterators trivially return `false` / an empty feedback vector — structurally identical to the AMO's `collatDolarValue` returning the raw balance (a stand-in "safe" value) whenever `oracle` is unset, instead of surfacing/erroring on the missing validation source. In both cases, a defensive/fallback code path silently substitutes a value that looks legitimate to callers (a dollar price of $1, or a fraud verdict of "not fraudulent") rather than failing closed or making the missing configuration visible to the caller.

The `FraudChecks` plan wrapper that is actually invoked during a signup is similarly a no-op: [4](#0-3) 
`run()` unconditionally returns an empty `Report {}` for every signup, regardless of what the pipeline observed.

### Impact Explanation
Any caller (e.g., `debug_report.rs`, `plans/mod.rs`, `plans/biometric_pipeline/mod.rs`) that calls `Report::fraud_detected()` / `fraud_detected_with_config()` to decide whether to block or flag a signup for fraud will always receive a "no fraud" result, because the underlying check array is compiled to zero length. This mirrors the Frax finding's impact: the system reports "adequately collateralized" (here, "no fraud") even when the real underlying condition (price below $1 / actual fraud signal) would indicate otherwise. If any code path in orb-core were to rely on `fraud_check::Report::fraud_detected()` as a gating condition for enrollment, it would provide a false assurance of fraud-check enforcement.

### Likelihood Explanation
I could not fully verify from the available index whether `fraud_check::Report::fraud_detected()`/`fraud_detected_with_config()` is actually called anywhere in the enrollment-gating path in this build — my searches found the file defines these methods but I was not able to confirm a live call site invoking them to block a signup within the tool budget available. The code comments ("FOSS: This is set to 0 because we manually deleted all fraud checks") strongly suggest this is an intentional, disclosed stripping of proprietary fraud-detection logic for the open-source release, not an unintentional defect — which is a material difference from the Frax bug (an unintentional/undocumented default). This uncertainty affects confidence in "unauthorized signup" impact classification.

### Recommendation
- Short term: If `fraud_check::Report` is still wired into any enrollment-gating decision in the production (non-FOSS) build, ensure the FOSS stub cannot be mistaken for/deployed as the enforcement path; add an explicit compile-time or runtime assertion that a zero-check configuration is never used as a substitute for real fraud/liveness enforcement in a signup-approving build.
- Long term: Where any validation dependency (oracle, fraud engine, liveness score) is unset/misconfigured, prefer failing closed (block signup / raise error) over silently defaulting to a benign-looking result, and add telemetry to detect when the fraud-check engine is running with zero active checks in a production signup flow.

### Proof of Concept
Not applicable as a standalone exploit — this is a structural/config-defaulting issue analogous to the reported bug class, contingent on whether `Report::fraud_detected()` is used to gate signups in the production build, which I was unable to conclusively confirm.

    pub fn fraud_detected_with_config(
        &self,
        config: &BackendConfig,
    ) -> (bool, Vec<PipelineFailureFeedbackMessage>) {
        let enabled_checks = Self::enabled_checks_from_config(config);
        let fraud_results = self.fraud_checks_strict();
        let feedback_msgs = Self::feedback_messages();

        let feedback: Vec<PipelineFailureFeedbackMessage> = enabled_checks
            .iter()
            .zip(fraud_results.iter())
            .zip(feedback_msgs.iter())
            .filter_map(
                |((&enabled, &result), feedback_msg)| {
                    if enabled && result { feedback_msg.clone() } else { None }
                },
            )
            .collect();

        (!feedback.is_empty(), feedback)
    }

    /// If any fraud check fails or is missing data, fraud is reported.
    #[must_use]
    pub fn fraud_detected(&self) -> bool {
        self.fraud_checks_strict().iter().any(|&v| v)
    }
