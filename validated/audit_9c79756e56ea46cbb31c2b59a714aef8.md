## Analog Found

### Title
`HyperFungibleToken` cross-chain amount is transmitted without any decimal normalization, causing value-mismatched mint/burn for non-18-decimal tokens - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
The original finding concerns ZC Tokens being deployed with the wrong number of decimals so an amount minted/withdrawn does not represent the value the user expects. The same bug class exists in Hyperbridge's `HyperFungibleToken`/`WrappedHyperFungibleToken` bridge: the EVM contracts pass the raw `uint256 amount` cross-chain with **no decimals field and no scaling logic whatsoever**, while `decimals()` on each deployment is whatever the inherited OpenZeppelin `ERC20` default resolves to (18, unless a deployer manually overrides it) [1](#0-0) . This is inconsistent with how the sibling Substrate pallet handles the exact same problem, which explicitly tracks and scales by a per-chain `Precisions` map [2](#0-1) [3](#0-2) .

### Finding Description
`HyperFungibleToken.send()` burns `params.amount` from the caller and encodes that exact raw integer into the cross-chain `Message.amount` field with no decimals conversion: [4](#0-3) . On the destination chain, `onAccept()` decodes the same raw integer and mints it 1:1 via `_mint(beneficiary, message.amount)`: [5](#0-4) .

The topology intended by the docs is: a `WrappedHyperFungibleToken` locks the canonical ERC20 supply on its home chain, and a plain `HyperFungibleToken` mints/burns on every remote chain [6](#0-5) . Nothing in `HyperFungibleToken.sol` reads or negotiates the decimals of the underlying locked asset — the contract simply inherits ERC20's constructor-set metadata and never overrides `decimals()`. Contrast this with `BridgeToken.sol`, which explicitly documents that its own `decimals()` (18, the ERC20 default) diverges from the native asset's real precision (12 on nexus), and that the *only* place this divergence is corrected is in the Substrate pallet's `register_token` call, which must declare the EVM side's decimals so `convert_to_erc20`/`convert_to_balance` can scale correctly [7](#0-6) [8](#0-7) .

The Solidity `Message` struct carries no decimals metadata at all: [9](#0-8) . For any EVM↔EVM deployment (e.g. `WrappedHyperFungibleToken` locking 6-decimal USDC on Ethereum against a `HyperFungibleToken` minting on a remote EVM chain), there is no on-chain or protocol-enforced mechanism ensuring the remote contract's `decimals()` matches the locked asset's decimals, nor any scaling of `amount` if they differ. This is architecturally the same root cause QuantStamp flagged for ZC Tokens — a deployed token's decimal precision silently diverging from the asset it is supposed to represent, with raw integer amounts carried across the mismatch unscaled.

### Impact Explanation
If a `WrappedHyperFungibleToken` is deployed for an asset with decimals ≠ 18 (e.g. 6-decimal USDC, or 8-decimal WBTC) and the corresponding remote `HyperFungibleToken` deployment is left at the ERC20 default of 18 decimals (as the constructor does nothing to prevent this), every cross-chain transfer will mint/burn the wrong magnitude of value: a user locking 1 USDC (1e6 raw units) on the home chain would have only `0.000000000001` "wUSDC" minted on the remote chain if interpreted as 18 decimals, or conversely a malicious/misconfigured deployment could mint 1e12× too many tokens relative to the locked collateral, permanently under-collateralizing the wrapped supply. This is a direct path to unbacked mint / permanent fund freezing for ordinary users who call `send()`, satisfying the "unbacked mint" / "permanent freezing of funds" bar.

### Likelihood Explanation
Reachable by any unprivileged user simply calling `HyperFungibleToken.send()` / triggering an `onAccept()` delivery — no governance or admin action is required to trigger the mismatch once a pair of contracts with divergent decimals is deployed and configured as peers via `addChain`. The likelihood of such a mismatch occurring is non-trivial because the contracts provide zero defense-in-depth against it (no decimals field in the message, no decimals check in `addChain`/`configure`), unlike the Substrate pallet-side design which enforces `config.decimals >= local_decimals` at registration time [10](#0-9) . The EVM-to-EVM path has no equivalent safeguard.

### Recommendation
Add an explicit decimals field to the cross-chain `Message`/registration flow for `HyperFungibleToken`/`WrappedHyperFungibleToken`, or enforce (at `addChain`/`configure` time) that peer decimals are recorded and `send`/`onAccept` scale `amount` accordingly — mirroring the `Precisions` map and `convert_to_erc20`/`convert_to_balance` scaling already implemented in `pallet-hyper-fungible-token`. At minimum, require `decimals()` overrides to be verified against the locked/underlying asset for every deployed pair, and add invariant checks so a peer registration with mismatched decimals reverts rather than silently allowing under/over-scaled mint and burn.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on Ethereum wrapping USDC (6 decimals) — see `send`/lock flow.
2. Deploy `HyperFungibleToken` on a remote EVM chain via `new HyperFungibleToken{salt}("Wrapped USDC", "wUSDC", owner)` — `decimals()` resolves to the OpenZeppelin ERC20 default of 18, since the constructor never overrides it (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:151`).
3. Register both as peers via `addChain` on each side (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:196-198`).
4. A user locks `1_000_000` raw units (1 USDC, 6 decimals) via `send({amount: 1_000_000, ...})`.
5. On the remote chain, `onAccept` mints `message.amount == 1_000_000` raw units of an 18-decimal token — i.e., `0.000000000001 wUSDC` — versus the `1 wUSDC` a user would expect, an effective 1e12x value loss on withdrawal (or the inverse over-mint depending on which side is misconfigured relative to the other), with no code path in either contract to detect or prevent the mismatch.

            from: abi.encodePacked(msg.sender),
            to: params.to,

     * @dev Burns `params.amount` from the caller and sends an ISMP POST request to the
     * destination chain. Fees can be paid in native tokens (via msg.value) or in the
     * host's fee token (pulled from msg.sender).
     * @param params The send parameters including destination, recipient, amount, and optional calldata
     */
    function send(SendParams calldata params) external payable whenNotPaused {
        _burn(msg.sender, params.amount);
        DispatchPost memory request = _buildDispatchPost(params);

        bytes32 commitment;
        if (msg.value > 0) {
            commitment = IDispatcher(_host).dispatch{value: msg.value}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
