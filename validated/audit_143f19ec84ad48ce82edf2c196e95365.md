### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, then trusts the `shop` value taken from an unauthenticated HTTP header as the tenant identity passed to the host app's handler. This breaks the intended binding: `hmac == HMAC(raw_body)` while `shop` (the tenant identifier) is never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed payload: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e., the raw body) against the computed HMAC — it never touches `shop`: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — as the tenant identifier passed to the app's handler: [4](#0-3) 

The documented usage pattern explicitly instructs host apps to treat `data.shop` as the authoritative shop/tenant for the webhook, e.g. enqueuing tenant-scoped work keyed by `data.shop`: [5](#0-4) 

The identity binding that should hold is `hmac == HMAC(raw_body || shop)` (or equivalent), but the actual binding enforced is only `hmac == HMAC(raw_body)`, with `shop` supplied out-of-band and unauthenticated. An attacker who operates their own (unprivileged) Shopify development shop can legitimately receive a valid `(raw_body, hmac)` pair from Shopify for their own tenant, then replay that exact body/HMAC pair to the victim host application's webhook endpoint while substituting the `shopify-shop-domain` header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` forwards the attacker-chosen `shop` value to the app's handler as if it came from Shopify for that shop.

### Impact Explanation
This is a cross-tenant identity-confusion vector: the host application's webhook handler receives attacker-controlled `shop`/tenant identity alongside a Shopify-signed (but tenant-agnostic) body. Depending on how the host app uses `data.shop` (e.g., to look up per-shop settings/tokens, write into shop-scoped tables, or trigger shop-scoped side effects), this can result in cross-tenant data corruption or disclosure attributed to the wrong shop — satisfying the "cross-tenant access" criterion, since the gem's own documented contract (`data.shop`) is the field being confused, not a misuse of an undocumented API.

### Likelihood Explanation
Requires only an unprivileged Shopify developer/store account to obtain one legitimate `(raw_body, hmac)` webhook pair (trivial and free to obtain by creating a dev store and triggering any registered topic), plus the ability to POST directly to the target app's public webhook endpoint with custom headers, which is exactly how `Registry.process`/`Request.new` expects input to arrive per the documented integration.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically verify the shop header against a value tied to the signature (e.g., derive/verify the shop from a signed webhook property, or require verification that the `shop` header matches an active, HMAC-confirmed subscription/session for the topic+webhook_id) before passing `request.shop` to handlers. At minimum, document that `data.shop` from `Registry.process` is not itself authenticated by the same HMAC that guards the body, and require host apps to cross-check it against known registered shops before using it as a trust boundary.

### Proof of Concept
1. Attacker creates their own Shopify development store and registers the target app's webhook endpoint for that store (or intercepts one legitimate webhook call to their own shop, e.g. `orders/create`).
2. Shopify sends: `POST /webhook` with headers `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and some `raw_body`.
3. Attacker replays the exact same request to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the (now attacker-modified) header; `HmacValidator.validate` in `Registry.process` only checks `raw_body` against the HMAC — still valid — so `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, even though the payload never originated from that shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
