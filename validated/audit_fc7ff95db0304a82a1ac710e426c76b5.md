### Title
Webhook `shop` (and `topic`) identity is trusted from unauthenticated headers while only the raw body is HMAC-covered, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature Shopify sends only ever proves the integrity of the JSON body. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values are all read straight from HTTP headers and are never part of the signed material, yet `Registry.process` unconditionally forwards `request.shop` and `request.topic` into `WebhookMetadata`, which the gem's own documentation tells host apps to trust as "the shop domain of the webhook."

### Finding Description
`Registry.process` validates the request with `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` and only ever hashes `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from attacker-controllable HTTP headers via `shopify_header`, none of which participate in the HMAC computation: [3](#0-2) 

`Registry.process` then dispatches purely on `request.topic` and builds `WebhookMetadata` (handed to the host app's handler) directly from these unauthenticated fields, after only checking that the body's HMAC is valid: [4](#0-3) 

The equality that should hold is: **`shop` claimed in the header == the tenant whose secret actually produced the HMAC over this exact body**. Because the HMAC never covers the `shop-domain` header, that binding does not exist — any request with a valid `(body, hmac)` pair computed with the app's shared `client_secret` will be accepted for whatever `shop-domain` header the attacker supplies, regardless of which shop actually generated that body/HMAC pair.

An unprivileged attacker who installs the target app on their own store (a normal, unprivileged action any Shopify merchant can perform) legitimately receives real webhook deliveries — bodies and HMACs computed with the app's single shared `api_secret_key`. The attacker can capture one such `(raw_body, hmac)` pair from their own shop's traffic, then replay it to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) with a victim shop that also has the app installed. `HmacValidator.validate` accepts it because the body/HMAC is genuinely valid, and `WebhookMetadata.shop` ends up carrying the attacker-chosen victim domain — exactly matching the documented, trusted contract: [5](#0-4) 

Host applications built per this gem's documented usage (e.g., using `data.shop` to select which tenant's records to update, as shown in the docs' own example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process the replayed webhook as if it originated from the victim shop, achieving cross-tenant action attribution without ever needing the victim's or the app's credentials.

### Impact Explanation
This breaks the tenant-identity binding between the cryptographically-verified request and the shop it is attributed to, letting one tenant (attacker's own shop, obtained through normal unprivileged app installation) forge webhook events "from" another tenant that also uses the app. Any host logic keyed on `WebhookMetadata#shop` — order/customer/inventory sync, GDPR/compliance webhooks, billing events, etc. — can be poisoned with cross-tenant data or trigger cross-tenant side effects, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be a legitimate (even trial) installer of the target Shopify app on their own store to receive real signed webhook traffic — no `api_secret_key`, access token, or victim credentials are required. Capturing and replaying one's own webhook HTTP request (headers + body) to the same public endpoint with a modified `shop-domain` header is trivial, and the gem performs no additional binding check between the header and the signed body.

### Recommendation
Bind the `shop` (and ideally `topic`) claim to the HMAC-verified data instead of trusting raw headers:
- Extend `to_signable_string` (or add a companion verification) that incorporates the `shop-domain` header (and other identity-bearing headers) into the signed material, matching what Shopify actually computes/allows, or
- Require host applications to cross-check `request.shop` against an independently known, previously-stored shop for the webhook subscription (e.g., matched by `webhook_id`) rather than presenting it as a trusted field in `WebhookMetadata`, and update `docs/usage/webhooks.md` to no longer describe `shop` as authoritative without such a check.
- At minimum, document clearly in `Registry.process`/`WebhookMetadata` that `shop`/`topic`/`webhook_id`/`api_version` are NOT covered by the HMAC and must not be used for tenant-authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (unprivileged, normal flow).
2. Shopify delivers a legitimate webhook to the app's endpoint, e.g.:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-SHA256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id":123, ...}
   ```
3. Attacker captures this exact `(Body, X-Shopify-Hmac-SHA256)` pair.
4. Attacker replays the same body/HMAC to the same endpoint, replacing only the shop header:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-SHA256: <same-valid-hmac-of-same-body>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {"id":123, ...}   (unchanged)
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only hashes the (unchanged) body: [1](#0-0) 
6. `WebhookMetadata.shop` is set to `"victim-shop.myshopify.com"` and passed to the host's handler as if it were an authentic event for that shop: [6](#0-5) 
7. Any host logic trusting `data.shop` (as the gem's own docs recommend) performs cross-tenant actions/updates based on attacker-controlled body content misattributed to the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
