### Title
Lockup contract's `new()` initializer lacks a state-exists guard, allowing reinitialization and takeover of a funded lockup - (File: lockup/src/lib.rs)

### Summary
The external report's root cause class is "an initializer that can be invoked/reached more than once, letting an untrusted caller overwrite trusted state set at construction time" (Holograph's reentrant `init` overwriting `_holographSlot`/`_adminSlot`). The reachable analog in this NEAR core-contracts codebase is **missing double-initialization protection** in the lockup contract's `#[init] pub fn new(...)` function, in contrast to every other contract in the same repo (`staking-pool`, `staking-pool-factory`, `whitelist`, `voting`, `multisig`) which all explicitly guard their initializers with `assert!(!env::state_exists(), ...)`.

### Finding Description
`LockupContract::new` at [1](#0-0)  initializes `owner_account_id`, `lockup_information`, `vesting_information`, `staking_pool_whitelist_account_id`, and `foundation_account_id` directly from caller-supplied arguments, but does **not** call `assert!(!env::state_exists(), ...)` before doing so.

By contrast, every sibling contract in this repository explicitly performs this check as the first statement of its initializer:
- `staking-pool/src/lib.rs`: `assert!(!env::state_exists(), "Already initialized");` [2](#0-1) 
- `staking-pool-factory/src/lib.rs`: `assert!(!env::state_exists(), "The contract is already initialized");` [3](#0-2) 

This is not something the `#[init]` macro on the near-sdk version used here inserts automatically — it must be added by the contract author, as evidenced by the fact that only some contracts in the repo include it. Since `lockup/src/lib.rs` never calls `env::state_exists()` anywhere (confirmed absent by repo-wide grep, unlike lockup-factory, multisig, staking-pool-factory, staking-pool, voting, and whitelist which all contain it), the lockup contract's `new` function can be called again after the contract has already been funded and initialized.

`new` is a plain public contract method with no access-control check tied to the existing `owner_account_id` — it is only guarded (in every other contract) by the state-exists assertion, which is the sole mechanism preventing an unprivileged account from calling it again. Because the lockup contract intentionally holds no access keys (per its design, see README: "the staking pool contract should not have any access keys"), the only defense against a public re-init call is the state-existence check — which is absent here.

### Impact Explanation
If reachable, this allows an unprivileged attacker to call `new` on an already-initialized, already-funded lockup contract account and overwrite `owner_account_id` to their own account (and rewrite `lockup_information`/`vesting_information`/`foundation_account_id` to remove lockup and vesting restrictions entirely). This would let the attacker immediately call owner-only methods such as `transfer` (`lockup/src/owner.rs`) to drain the entire NEAR balance held by the lockup contract — a Critical unauthorized-withdrawal impact directly reachable by an unprivileged user through a public-call accounting/state-machine failure, matching the report's "reinitialization overwrites trusted state" pattern.

### Likelihood Explanation
This is uncertain and requires verification that could not be completed within available tools:
- It is unknown which exact version of `near-sdk-rs` this repo vendors, and in some historical near-sdk-rs versions the `#[init]` macro itself injects an implicit `state_exists`/re-init check at the macro-expansion level (this behavior changed across SDK versions). If the version used here does perform that check automatically, this finding is a false positive/non-issue, since the generated wrapper would reject any second `new` call regardless of the missing explicit assertion in the source.
- I was unable to locate the `near-sdk` dependency/version pin for the `lockup` crate to confirm which behavior applies (the `Cargo.toml` search matched but content wasn't retrievable in this session).

Given that this repo's own sibling contracts explicitly add the manual check, that strongly suggests the SDK version in use does NOT enforce it automatically (otherwise the explicit checks in `staking-pool`/`staking-pool-factory` would be redundant boilerplate) — which would make the missing check in `lockup` a genuine gap rather than defense-in-depth.

### Recommendation
Add `assert!(!env::state_exists(), "The contract has already been initialized");` as the first line of `LockupContract::new` in `lockup/src/lib.rs`, matching the pattern used in `staking-pool/src/lib.rs` and `staking-pool-factory/src/lib.rs`. Before treating this as confirmed, verify the exact `near-sdk-rs` version pinned for the `lockup` crate and confirm experimentally (e.g., via a unit/simulation test that calls `new` twice against a deployed contract) whether the generated `#[init]` wrapper already rejects re-initialization independent of the explicit source-level assertion.

### Proof of Concept
Not able to be produced with certainty in this session — a definitive PoC requires either:
1. Deploying the compiled `lockup_contract.wasm` in a `near-sdk-sim`/`near-workspaces` test harness, calling `new` once to fund/initialize it (as done in `lockup/tests/spec.rs`), then calling `new` again from a different (attacker) account with different `owner_account_id`, and observing whether the call succeeds and the attacker can subsequently call `transfer`; or
2. Confirming via near-sdk-rs source (matching the version in this repo's lockfile) whether `#[init]` auto-generates a state-exists check.

Given the tool limitations in this session (no access to `Cargo.lock`/exact dependency graph, no wasm build/execution), this should be verified with a running/buildable checkout before being reported with full confidence.
