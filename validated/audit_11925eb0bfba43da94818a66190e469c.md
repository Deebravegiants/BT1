### Title
Unbounded `headers` array in `SP1Beefy.verifyConsensus` allows gas-exhaustion DoS on consensus updates before proof verification - (File: `evm/src/consensus/SP1Beefy.sol`)

### Summary
`SP1Beefy.verify()` is the `IConsensusV2` entry point invoked by `ConsensusRouter`/`HandlerV2` when any unprivileged relayer submits a consensus update [1](#0-0) . The function ABI-decodes an attacker-supplied `ParachainHeader[] headers` array from calldata with no length cap, then iterates it twice — first hashing each header with `keccak256` to build `PublicInputs.headers`, and again with `Codec.DecodeHeader` to build `IntermediateState[]` — with the first loop executing *before* `verifier.verifyProof()` is ever called [2](#0-1) .

### Finding Description
The wire format allows `headers.length` to be arbitrarily large since it is just `abi.decode`d from calldata with no bound check anywhere in the contract or in `Types.sol` [3](#0-2) . Crucially, the first loop that computes `keccak256(proof.headers[i].header)` for every entry runs *before* `verifier.verifyProof(verificationKey, publicInputs, proof.proof)` is invoked [4](#0-3) . This means the cost of processing the oversized array is paid unconditionally by the caller/network regardless of whether the SP1 proof itself is valid — an attacker does not need a genuine SP1 proof to trigger the expensive iteration; they only need calldata that ABI-decodes successfully into the tuple `(MiniCommitment, PartialBeefyMmrLeaf, ParachainHeader[], bytes, bytes32)`, with `headers` padded to an arbitrarily large size (each entry can be a minimal-size header, e.g. a few bytes, keeping calldata cost proportional while the per-entry `keccak256` + memory-array-write loop scales with `headers.length`). No file in the repo enforces a `MAX_HEADERS`-style cap on this array (confirmed no matches for such a bound in the codebase), unlike the analogous Rust-side proof-depth bound seen in the Pharos SPV verifier (`MAX_PROOF_DEPTH`) or the beefy-consensus-proofs pallet's `MaxProofSize` `BoundedVec` gate on the `submit_proof` extrinsic [5](#0-4) . The EVM contract has no equivalent size gate before the expensive per-header loop.

This is analogous to CVE-2019-9371 (libvpx resource exhaustion via improper input validation): a message that is not fully validated up front drives an unbounded amount of processing work per single submitted call.

### Impact Explanation
Any unprivileged relayer can submit a consensus-update transaction (via `ConsensusRouter`/`HandlerV2`, which calls into `SP1Beefy.verify`) carrying a crafted proof payload with a very large `headers` array. The contract will perform `O(headers.length)` `keccak256` hashing and memory allocation work before it ever reaches the point of rejecting the (missing/invalid) SP1 proof. A sufficiently large array can push the transaction's gas consumption toward or past the block gas limit, causing legitimate consensus-update transactions to revert or become prohibitively expensive, and can be used to grief relayers who pay gas for reverted transactions, degrading the liveness of the BEEFY consensus update path (a route unable to reliably deliver/settle messages).

### Likelihood Explanation
The `verify()` function is externally reachable through the standard consensus-update dispatch path used by any relayer (`ConsensusRouter`/`HandlerV2` call sites) with no permission gate, and requires only correctly-shaped ABI-encoded calldata — no valid cryptographic proof is needed to trigger the expensive first loop. This makes the likelihood of triggering the wasted-work path high for any adversary willing to pay calldata gas.

### Recommendation
Add an explicit upper bound on `proof.headers.length` (mirroring the `MAX_PROOF_DEPTH`/`MAX_VALIDATORS`-style caps used elsewhere in the codebase, e.g. `modules/consensus/pharos/verifier/src/state_proof.rs`) and enforce it immediately after decoding, before either loop in `verifyConsensus` executes. Consider also checking the array bound in the `ConsensusRouter`/`HandlerV2` dispatch layer for defense in depth.

### Proof of Concept
1. An attacker crafts calldata for `SP1Beefy.verify(previousState, proof)` where `proof` ABI-encodes a valid `MiniCommitment`/`PartialBeefyMmrLeaf`, but `headers` is a `ParachainHeader[]` with, e.g., tens of thousands of minimal entries (`id: 0, header: <few bytes>`), and `proofBytes`/`nonce` are arbitrary/garbage.
2. Submit this via the relayer-facing consensus-update path into `ConsensusRouter`/`HandlerV2`, which forwards to `SP1Beefy.verify`.
3. Execution reaches `verifyConsensus` and runs the first `for` loop over `headers_len` entries computing `keccak256` for each before `verifier.verifyProof` is called [4](#0-3) , consuming gas proportional to the attacker-chosen array length even though the proof will ultimately fail verification.         external
        view
        returns (bytes memory, IntermediateState[] memory, uint256)

        BeefyConsensusState memory consensusState = abi.decode(previousState, (BeefyConsensusState));
        (
            MiniCommitment memory commitment,
            PartialBeefyMmrLeaf memory leaf,
            ParachainHeader[] memory headers,
            bytes memory proofBytes,
            bytes32 nonce

            mmrLeaf: leaf,
            headers: headers,
            proof: proofBytes,
            nonce: nonce
        });

        (BeefyConsensusState memory newState, IntermediateState[] memory intermediates) =
            verifyConsensus(consensusState, sp1Proof);

        return (abi.encode(newState), intermediates, newState.nextAuthoritySet.id);
    }
