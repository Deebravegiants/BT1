### Title
Unauthenticated arbitrary external call in `EmporiumUpgradeable.runAction` CASE 2 lets an unprivileged prover move tokens the ZK proof never constrains - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes `EmporiumOperation.ops` where CASE 2 (`stack.signerAddress == address(0)`) performs a completely attacker-controlled `op.endpoint.call{value: op.value}(op.callData)` [1](#0-0) , and `verifyWallet` skips *all* signature verification whenever `signerAddress == address(0)` [2](#0-1) . Combined with the fact that `_externalTransact`'s pre-loop and the post-loop UTXO accounting in `runAction`/`handleOut` only ever look at `circomData.erc20TokenAddresses[i]` [3](#0-2) [4](#0-3) , an attacker can list a benign token `T` in `circomData.erc20TokenAddresses` (with a small real deposit to satisfy `deltaAmountChanges[i] < 0`/`>0` bookkeeping) while embedding a CASE 2 op whose `op.endpoint`/`op.callData` target an entirely different, unlisted token `T2` (or any contract) that Emporium can act on (e.g. via a standing ERC20 approval a prior legitimate user left for the Emporium contract as spender, which is the mechanism CASE 2 relies on for token deposits into Emporium).

### Finding Description
The broken equality is **PROOF COVERAGE**: every value moved by a `runAction` op should be represented in `circomData.erc20TokenAddresses` / the public-input vector that the Groth16 circuit constrains. In practice:

1. `_externalTransact` only transfers tokens for indices present in `circomData.erc20TokenAddresses`, and only inspects `deltaAmountChanges[i] < 0` per listed token [3](#0-2) . It never inspects what the external action's `ops` (an opaque `bytes callData`, decoded from `externalActionData.externalActionMetadata`) actually touch.
2. `EmporiumUpgradeable.runAction` decodes `stack` from unconstrained metadata and, for CASE 2 (`op.invokeWallet == false` or `signerAddress == address(0)`), performs a raw low-level call to `op.endpoint` with attacker-supplied `op.callData` [1](#0-0) . The only restriction is blocking the `callHinkalWallet`/`doSendToRelay` selectors — there is no check that `op.endpoint` is one of `circomData.erc20TokenAddresses`, nor that the call's effect is limited to those tokens.
3. `verifyWallet` returns immediately with **no signature check at all** when `stack.signerAddress == address(0)` [2](#0-1) , so the entire `ops` array in this mode is fully unauthenticated by anyone — the calling EOA (the attacker themselves, an "allowed recipient" caller of Hinkal) fully controls it.
4. The post-loop accounting in `runAction` computes `balancesAfter - balancesBefore` **only for indices in `circomData.erc20TokenAddresses`** and emits UTXOs only for those [5](#0-4) . Any effect on `T2` (an unlisted token) is invisible to this loop and to `handleOut`.

Exploit flow: attacker lists `erc20TokenAddresses = [T]`, deposits a small real amount of `T` (satisfying the arithmetic in `_calculateDeltaAmount`/`_externalTransact` so `require` checks pass), and crafts a CASE 2 op with `endpoint = T2`, `callData = transferFrom(victim, attacker, amount)`. Because Emporium is the caller (`msg.sender` as seen by `T2`), if `victim` had ever left an ERC20 allowance for the Emporium contract (a pattern the design relies on for CASE 2 stateless deposits), the call succeeds and moves `victim`'s `T2` tokens out — entirely outside `circomData.erc20TokenAddresses`, `calldataHash`, and thus outside every public signal the `MainEVMCircuit` constrains. Existing guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, `balanceDif` slippage checks in `Hinkal._internalTransact`/`transact`) all operate strictly per-index over `circomData.erc20TokenAddresses` and never see `T2`, so none of them catch this.

### Impact Explanation
Direct theft of a third party's ("victim") ERC20 tokens with zero representation in the submitted zk proof's public inputs — value moves through the system entirely outside the Groth16 constraint set, satisfying the Critical bar ("direct theft of shielded or in-flight user funds ... proof or nullifier verification bypass"). This is repeatable for every victim with a residual/standing allowance to the Emporium contract, and each exploit is a normal, self-authorized `transact` call requiring no privileged role and no cooperation from the victim or any signer.

### Likelihood Explanation
The precondition is that some victim's ERC20 allowance to the Emporium contract remains non-zero at the time of attack (e.g., an infinite/generous approval, a partially-consumed approval, or any approval left standing between the approve step and the CASE 2 pull step of the intended deposit flow). Given CASE 2 is explicitly the documented "Stateless Interaction" path used for arbitrary endpoint calls, and `signerAddress == address(0)` deliberately skips authentication (intended for the caller's own funds), the attacker only needs to observe or predict such an allowance and construct one crafted `op`. Cost is a single gas-paying `transact` call plus one legitimate small deposit; no special privileges are required.

### Recommendation
Restrict CASE 2 (`signerAddress == address(0)`) so `op.endpoint` and any token contract touched must belong to `circomData.erc20TokenAddresses`, or require ops in this mode to only pull funds `from == msg.sender` (never a third-party `from`), and/or eliminate the fully-unauthenticated stateless path entirely by requiring `verifyWallet` to always validate a signature bound to `msg.sender` even when `signerAddress == address(0)`. Additionally, bind the `MainEVMCircuit`'s public inputs to a hash of the full `externalActionMetadata` (including every `op.endpoint`/`op.callData`), and reject metadata whose ops reference any token/endpoint not present in `circomData.erc20TokenAddresses`.

### Proof of Concept
Foundry fork test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, mock ERC20 `T` and `T2`.
2. Have `victim` `T2.approve(emporium, LARGE_AMOUNT)` (simulating a leftover/standing allowance from prior legitimate Emporium usage).
3. As `attacker`, generate a real snarkjs proof for `transact` with `circomData.erc20TokenAddresses = [T]`, `amountChanges[0] > 0` (small real deposit of `T`), `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one CASE 2 op: `endpoint = T2`, `callData = abi.encodeCall(IERC20.transferFrom, (victim, attacker, LARGE_AMOUNT))`.
4. Call `Hinkal.transact(...)`.
5. Assert: (a) proof verifies and tx succeeds; (b) `T2.balanceOf(attacker)` increases by `LARGE_AMOUNT` and `T2.balanceOf(victim)` decreases by the same; (c) the proof's public signals / `circomData.erc20TokenAddresses` contain only `T`, never `T2`; (d) no `require` in `Hinkal.sol` or `EmporiumUpgradeable.sol` reverts, confirming `T2`'s movement is unconstrained by the circuit and unchecked by on-chain accounting.
