### Title
Permanent, Unrecoverable Freezing of LT Donated Directly to a Bonding-Curve `Pair` — ([File: packages/contracts/src/Pair.sol])

### Summary
Any unrelated wallet can `IERC20(lt).transfer` LT tokens directly to a bonding-curve `Pair`, either while the token is still trading or after it has already graduated. That LT balance is never recoverable by anyone — not the depositor, not the protocol owner, not through any upgrade path — because the only function capable of moving asset tokens out of a `Pair` (`transferAsset`) is gated to a single-use, lifecycle-bounded caller.

### Finding Description
`Pair.transferAsset` is the sole withdrawal path for the asset (LT) side of a pair and is restricted to `onlyRouter`: [1](#0-0) 

`Router` exposes `transferAsset` to callers in exactly two places, both gated by `onlyRole(BONDING_ROLE)`: `sell` (bounded by curve accounting for the trading amount) and `graduate` (which drains only `assetReserve - virtualLtReserve`, i.e. the LT actually tracked by the curve's stored reserves, deliberately excluding any donated LT): [2](#0-1) 

`Bonding` calls `Router.graduate` exactly once per token, from `_prepareGraduationLiquidity`, during phase 1 of graduation, and that function is unreachable once the token's lifecycle has advanced past `Curve`: [3](#0-2) [4](#0-3) 

Consequently, any LT sent directly to the pair — via a plain ERC20 `transfer` — that exceeds the curve's stored `assetReserve` accounting is permanently excluded from every code path that can move it. This holds whether the donation happens:
- **Before graduation**, while the token is still `Curve` (documented and tested: donated LT is excluded from `ltFromPair` and stays behind after `graduate` drains only the tracked reserve), or
- **After graduation**, once `Lifecycle` has advanced to `Graduating`/`Graduated` and `Router.graduate` for that token can never be called again.

The project's own comments acknowledge this is enforced purely by a trust assumption, not an on-chain guarantee, and depends on `BONDING_ROLE` never being granted elsewhere and future upgrades preserving the lifecycle gate: [5](#0-4) 

Unlike `FeeVault`, which has a permissionless `sweepDonations()` for stray USDC, or `Bonding`, which has `_sweepLTToOwner` for stray LT sitting in `Bonding` itself, **`Pair` has no equivalent sweep/rescue function for stray asset-token balances at all** — there is no code path, privileged or not, that can ever move a pair's excess LT balance anywhere.

This is directly analogous to CVE-2017-8345's underlying bug class: a resource (there, allocated memory; here, transferred LT) is taken in by the system but the code path that is supposed to eventually release/account for it is architecturally unreachable for a subset of inputs, so the resource is permanently stranded — a "leak" that never gets reclaimed.

### Impact Explanation
Any address — trader, creator, or a completely unrelated wallet — that sends LT directly to a `Pair` contract (a publicly known, deterministically derivable address via `Factory.getPair`) permanently loses that LT with zero recovery path for anyone, including the protocol owner. This is a permanent freezing of funds meeting the "Validate" bar (concrete permanent freezing of funds reachable via a direct ERC20 transfer of an LT into `Pair`), and the amount at risk is unbounded — it grows every time this occurs and is never reclaimed, mirroring the unbounded/leaked-resource nature of the referenced CVE.

### Likelihood Explanation
Trivial to trigger: a single unprivileged `IERC20(lt).transfer(pairAddress, amount)` call, requiring no special permissions, timing, or protocol interaction. It can happen accidentally (a wallet mistakenly sending LT to the pair address instead of `Zap`) or deliberately. The project's own test suite exercises and asserts this exact stuck state as expected behavior (`assetBalance() == donation` after graduation), confirming the pattern is real and currently unmitigated at the `Pair` level. [6](#0-5) [7](#0-6) 

### Recommendation
Add an owner-gated or permissionless sweep function on `Pair` (or routed through `Router`/`Bonding`) analogous to `FeeVault.sweepDonations()`, that can compute `assetBalance() - assetReserve` (and `tokenBalance() - tokenReserve` for the token side, post-`unsoldBurned` accounting) and forward the excess to a safe recipient (e.g., the depositor via a claim registry, or the protocol owner) for both pre-graduation and post-graduation states. Ensure this sweep cannot interfere with the K-invariant or reserve accounting used by `swap`/`graduate`.

### Proof of Concept
1. Launch a token via `Bonding.launch`, obtaining `pairAddr`.
2. As an unrelated wallet, call `IERC20(lt).transfer(pairAddr, X)` — this is picked up by `Pair.assetBalance()` but not `Pair.getReserves()`'s stored `assetReserve`.
3. Drive the token through graduation normally (buys crossing the USD/supply trigger, then `finalizeGraduation`). `_prepareGraduationLiquidity`'s `ltFromPair = assetReserve - virtualLtReserve` excludes the donation, and `Router.graduate` drains only that tracked amount — confirmed by `test_graduate_leavesDonationBehind` (packages/contracts/test/Router.t.sol:345-357) and `test_inv_donation_zeroGapPreserved` (packages/contracts/test/GraduationInvariants.t.sol:512-534), both of which assert the donated LT remains in the pair after the graduation flow completes.
4. Post-graduation, attempt to recover the donated LT: no function exists anywhere in `Pair`, `Router`, or `Bonding` that is reachable (lifecycle has passed `Curve`, `Router.graduate` for this token can never be called again). The donated LT is permanently stuck in `Pair` with no owner, keeper, or upgrade-accessible recovery path.

```text
    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
```
