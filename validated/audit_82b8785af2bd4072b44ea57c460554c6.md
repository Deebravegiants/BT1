### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator` validates the HMAC exclusively against that body. The `shop-domain` (and `topic`, `webhook-id`) headers are never part of the signed payload, yet `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier and hands it directly to the app's webhook handler without any additional binding check.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The HMAC validation logic in `HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and the app's single, shop-independent `api_secret_key`: [2](#0-1) 

`Request#shop` is read straight from the (unsigned) `shop-domain` header: [3](#0-2) 

`Registry.process` only checks the HMAC against the body, then dispatches the handler using `request.shop` and `request.parsed_body` without verifying that the shop header is consistent with anything cryptographically bound to that body: [4](#0-3) 

Because the app's `api_secret_key` is a single shared secret used for every installed shop (not a per-shop secret), `HMAC(secret, body)` is identical regardless of which shop the body originated from. An attacker who has legitimate access to a real, valid webhook delivery for their own shop (any store that installs the app receives real webhooks with valid HMACs) can capture a `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` header. The `HmacValidator` check still passes because it only checks the body/secret, and `Registry.process` passes the attacker-chosen `shop` value on to the app's handler as if it were an authentic message from that shop.

This breaks the identity binding: `shop asserted in the unsigned header == shop that the HMAC-covered body actually originated from`. The signature verifies "this body came from an app installation using this app's secret," not "this body came from shop X."

### Impact Explanation
This is a cross-tenant confusion vulnerability: the app processes webhook payloads under the identity of a shop the data did not come from. Any webhook handler logic that trusts `WebhookMetadata#shop` (constructed from `request.shop`) to select/update per-tenant records (customer data requests/redactions, order data, `app/uninstalled` cleanup, etc.) can be tricked by any user who can install the app on any shop into writing, deleting, or leaking data associated with a different, victim tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires normal, unprivileged access to install the target app on any shop (e.g., a free/dev store) to obtain a genuinely signed `(body, hmac)` pair, and the ability to send an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — both of which are available to any internet user with no special credentials, tokens, or MITM position. The likelihood is high for any app whose webhook handlers make tenant-scoped decisions based on `data.shop`.

### Recommendation
Bind the shop identity into the verified signature material, or independently verify it out-of-band:
- Include the shop domain (and topic) as part of the signed/verified data, similar to how AuthQuery signs `shop`, `host`, `state`, etc. together, or
- After HMAC validation, cross-check `request.shop` against an authoritative source (e.g., a previously stored, per-shop webhook secret, or reconcile against the session/shop record the webhook claims to target) before dispatching to handlers.
- At minimum, document/require that `WebhookHandler` implementations must not treat `request.shop`/`WebhookMetadata#shop` as a trusted tenant key on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`.
2. Attacker triggers any webhook topic that is registered (e.g., `orders/create`) on their own shop and captures the raw HTTP request Shopify sends to the app's webhook endpoint, including `X-Shopify-Hmac-Sha256` and the raw body.
3. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` — identical to what was already valid — and returns `true`, since the shop header is never part of `to_signable_string`.
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, causing the app to act on attacker-controlled data under the victim shop's identity.
