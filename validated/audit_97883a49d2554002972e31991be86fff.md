### Title
Unbounded POST/GET request payload size can render a dispatched message permanently undeliverable on the destination chain - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `body`, `to`, `dest`, `keys`, and `context` fields of arbitrary caller-controlled length with no maximum-size enforcement before committing the request and emitting it in `PostRequestEvent`/`GetRequestEvent`.

### Finding Description
`dispatch(DispatchPost)` builds a `PostRequest` directly from caller-supplied `post.body`/`post.to`/`post.dest` and commits/emits it with no bound on payload size: [1](#0-0) 

Likewise `dispatch(DispatchGet)` takes unbounded `keys`/`context` arrays. Neither dispatch path validates a maximum body/array length, and no `MaxRequestBodySize`-style guard exists anywhere in the EVM host or in the analogous pallet-ismp dispatcher path either: [2](#0-1) 

This request is only ever consumed later on the destination chain via `HandlerV2.handlePostRequests`, which decodes it into an MMR leaf and dispatches it with `host.dispatchIncoming`: [3](#0-2) 

Because the request body is embedded verbatim in the destination-chain calldata (`PostRequestLeaf.request.body`), an arbitrarily large body inflates the calldata size and thus the gas required to submit `handlePostRequests`/`batchCall` to the destination chain. Every EVM destination chain has a hard per-transaction block gas limit that the relayer already tracks per-chain (e.g. 16M–32M gas): [4](#0-3) 

If a caller dispatches a POST request with `timeout = 0` (the documented "never expires" option) and a body large enough that the resulting `handlePostRequests` calldata exceeds the destination chain's block gas limit, the message can never be successfully delivered by any relayer or self-relayer, and — because `timeout == 0` — it can also never be timed out and refunded: [5](#0-4) 

This is the same bug class as the unpoly-rails DoS: a single unprivileged, low-cost input (URL length / request body length) is echoed downstream (HTTP response header / cross-chain delivery calldata) into a component with a hard external size limit (load balancer header buffer / destination-chain block gas limit) that the origin service does not itself enforce, causing legitimate use of that downstream mechanism (health-checked upstream / message delivery route) to fail.

### Impact Explanation
A commitment for the oversized request is written to `_requestCommitments` on the source `EvmHost` and can never be cleared:
- It cannot be delivered (`handlePostRequests` calldata exceeds every EVM chain's block gas limit).
- With `timeout = 0` it cannot be timed out either, so any relayer fee attached (`post.fee`) is permanently locked.
- The route between the two state machines becomes unable to deliver that message, satisfying the "route unable to deliver messages" impact criterion. This is reachable by any unprivileged caller of `IDispatcher.dispatch`, i.e. any application contract or EOA-driven app on the source chain.

### Likelihood Explanation
High for a determined attacker: dispatch is fully permissionless, `fee` can be set to zero (no incentive cost beyond gas to submit the oversized calldata on the source chain, which typically has a higher gas limit than some destination chains, e.g. SEI at 4,000,000 or the general EVM default 16,000,000), and `timeout = 0` is a documented, normal usage pattern (not a misuse). No governance or privileged role involvement is required.

### Recommendation
Enforce a maximum serialized size for `DispatchPost.body`/`to`/`dest` and `DispatchGet.keys`/`context` in `EvmHost.dispatch(...)` (and the equivalent `pallet-ismp` `dispatch_request`) sized so that the worst-case `handlePostRequests`/`handleGetResponses`/`batchCall` calldata for the smallest supported destination-chain gas limit still fits comfortably within that chain's block gas limit. Reject dispatches that exceed the bound at the source, mirroring the `BandwidthManager.MAX_APP_LENGTH` pattern already used elsewhere in the codebase: [6](#0-5) 

### Proof of Concept
1. Attacker's contract calls `IDispatcher(host).dispatch(DispatchPost({dest: <low-gas-limit chain>, to: <arbitrary>, body: <bytes sized so ABI-encoded handlePostRequests calldata exceeds that chain's block gas limit, e.g. several MB>, timeout: 0, fee: 0, payer: attacker}))`.
2. `EvmHost.dispatch` commits the request and emits `PostRequestEvent` with the oversized `body` with no size check: [7](#0-6) 
3. Any relayer or self-relayer attempts `HandlerV2.handlePostRequests`/`batchCall` on the destination chain; the transaction's gas requirement (dominated by calldata cost of `body`) exceeds `get_chain_gas_limit(dest)`, so it can never be included in a block.
4. Since `timeoutTimestamp == 0`, `handlePostRequestTimeouts` can never trigger either, leaving the commitment (and any locked fee) permanently stuck and the message permanently undeliverable.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }

	match state_machine {
		StateMachine::Evm(ARBITRUM_CHAIN_ID) | StateMachine::Evm(ARBITRUM_SEPOLIA_CHAIN_ID) =>

## Dispatch Parameters

| Parameter | Description |
|-----------|-------------|
| `dest` | Destination chain, for this you'll use the `StateMachine` library eg `StateMachine.evm(1)` for Ethereum Mainnet. |
| `to` | Receiving module/contract address on the destination chain. |
| `body` | Serialized byte representation of the message (to be decoded by the receiving contract). |
| `timeout` | Time in seconds for message validity eg 3600 for a timeout of 1 hour, or 0 for no timeout. ie Messages will never expire. If the timeout is set to a non-zero value, messages that have exceeded this timeout will be rejected on the destination and require user action (timeout message) to revert changes. |
| `fee` | Optional relayer fees in the fee token, this can also be set to zero if the application developers prefer to self-relay. |
