### Title
Missing Role-Based Authorization on Debug/Profiling Endpoints Allows Any Authenticated Non-Admin User to Access Runtime Memory, Goroutine, and Heap Data - (File: core/web/router.go)

### Summary
The Chainlink node's `/v2/debug/pprof/*` and `/debug/vars` routes are registered behind session/token authentication only, with no role check (`RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole`). Any authenticated user — including one with the lowest privilege `view` role — can pull heap dumps, goroutine stacks, and other runtime introspection data that other equally or less sensitive endpoints (e.g. `PATCH /v2/log`, key export endpoints) correctly gate behind `RequiresAdminRole`.

### Finding Description
`v2Routes` wraps all `/v2/*` endpoints in a group (`authv2`) that only requires session/token authentication (`auth.Authenticate(...)`), not any specific role: [1](#0-0) 

Within that group, `metricRoutes(authv2)` is invoked directly with no additional role middleware: [2](#0-1) 

`metricRoutes` registers pprof endpoints (`heap`, `goroutine`, `allocs`, `block`, `mutex`, `threadcreate`, `profile`, `trace`, `cmdline`, `symbol`) with **no** wrapping in `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole`, unlike almost every other sensitive route in the same file: [3](#0-2) 

Similarly, `debugRoutes` exposes Go's `expvar.Handler()` (process command-line args, memory stats, and any custom published vars) behind only session authentication, again with no role restriction: [4](#0-3) 

For comparison, the codebase's established pattern is to gate operationally sensitive but far less dangerous data behind `RequiresAdminRole`, e.g. the log-level/SQL-logging PATCH endpoint: [5](#0-4) 

and every key-management/export endpoint uses `auth.RequiresAdminRole`: [6](#0-5) 

The role-check middleware itself confirms these are the only gates available and that `view`-role users are otherwise fully authenticated but low-privileged: [7](#0-6) 

Because `metricRoutes` and `debugRoutes` omit any of these role checks, a user provisioned with the minimal `view` role (the lowest tier, used for read-only dashboards per `RequiresRunRole`/`RequiresEditRole` checks) can reach `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/allocs`, and `/debug/vars` with nothing more than a valid session cookie or API token.

### Impact Explanation
Heap and goroutine profiles from a running Chainlink node can contain in-memory secrets (private keys, API tokens, database credentials, decrypted job specs, RPC responses) as well as internal file paths, function/module names, and stack traces of currently-executing goroutines. This is a strict superset of the "reconnaissance" impact described in the analogous report (internal file paths, stack traces, module names) and, in the worst case, can leak live cryptographic key material or credentials residing in process memory — elevating this beyond pure information disclosure to potential secret exposure and further attack-chain enablement (CWE-862, missing authorization).

### Likelihood Explanation
Any user who can authenticate to the node's HMI/API with a `view`-level account (the lowest privilege tier, intended for read-only access) can trivially hit these endpoints with a simple authenticated `GET` request — no additional exploitation steps, timing, or race conditions are required. The bug is directly reachable from the standard authenticated HTTP surface.

### Recommendation
Wrap `metricRoutes` and `debugRoutes` registrations with `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`), consistent with other sensitive routes such as the key-export and log-patch endpoints:
```go
func metricRoutes(r *gin.RouterGroup) {
    pprofGroup := r.Group("/debug/pprof", ... /* add RequiresAdminRole gate */)
    ...
}
```
and call sites should pass the role-guarded handler, e.g. `authv2.Group("", auth.RequiresAdminRole(...))` before invoking `metricRoutes(authv2)`, and similarly restrict `debugRoutes`'s `/vars` endpoint.

### Proof of Concept
```bash
# 1. Create/obtain a view-role session (lowest privilege) for the node
curl -c cookies.txt -X POST http://localhost:6688/sessions \
  -H 'Content-Type: application/json' \
  -d '{"email":"viewer@example.com","password":"ViewerPass123"}'

# 2. Access heap profile (potential secret material) with only a view-role session
curl -b cookies.txt http://localhost:6688/v2/debug/pprof/heap -o heap.pprof

# 3. Access goroutine stack traces revealing internal file paths and execution state
curl -b cookies.txt "http://localhost:6688/v2/debug/pprof/goroutine?debug=2"

# 4. Access expvar runtime state (no role check either)
curl -b cookies.txt http://localhost:6688/debug/vars
```
None of these requests should succeed for a `view`-role user given the sensitivity of the data, but the router places no role-based `RequireX` middleware in front of them.

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
