Confirmed: `circomData.originalSender` is included only in `calldataHash` (via `getHashedCalldata2`) [1](#0-0)  — it is **not** part of `getSignedMessageHash` and not a standalone entry in `formBasicInput`'s public-input vector [2](#0-1) . The only on-chain constraint tying `originalSender` to the caller is in `performHinkalChecks`, and it is skipped entirely whenever a relay is used.

### Title
Unauthorized ERC20 pull from arbitrary `originalSender` via relay path in `DepositOnChainUtxosExternalAction` - (File: contracts/HinkalHelper.sol, contracts/external-actions/DepositOnChainUtxosExternalAction.sol)

### Summary
`HinkalHelper::performHinkalChecks` only forces `circomData.originalSender == sender` when no relay is used; when a relay is set, `originalSender` is unconstrained on-chain and not bound to any signature or ZK secret [3](#0-2) . `DepositOnChainUtxosExternalAction::runAction` then calls `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` using that same unconstrained `originalSender` as the token source [4](#0-3) .

### Finding Description
This mirrors the report's root cause — an address field used to move funds/authorize an action that is not actually the entity that authorized the call. Here, `originalSender` is hashed into `calldataHash` [1](#0-0)  but never appears in `getSignedMessageHash` or the circuit's public-input vector built by `formBasicInput` [5](#0-4) . Because `onChainCreation` deposits require zero input nullifiers (`checkOnchainCreation` mandates `inputNullifiers[i][j] == 0`) [6](#0-5) , the proof for this path proves nothing about ownership of `originalSender`'s funds — no private key/secret tied to that address is consumed. The only place `originalSender` is checked against the actual caller is `require((originalSender==0 && relay!=0) || (originalSender==sender && relay==0))` [7](#0-6) ; once `relay != address(0)`, this constraint is dropped entirely, and `originalSender` can be set to any address that has an outstanding ERC20 approval to the Hinkal contract from a prior legitimate deposit. `DepositOnChainUtxosExternalAction` then pulls `tokenTotal` from that arbitrary `userAddress` and mints an on-chain UTXO under an attacker-controlled `stealthAddressStructure` [8](#0-7) .

### Impact Explanation
If exploitable, this is direct theft of a user's approved ERC20 balance, converted into a shielded UTXO controlled by the attacker — matching the "Critical: direct theft of shielded or in-flight user funds" / "unauthorised asset movement" categories.

### Likelihood Explanation
Low/uncertain. The `relay` path additionally requires `tx.origin == relay` and `isRelayInList(relay)` [9](#0-8) , i.e., the caller must be a whitelisted relay. Exploiting this specific gap therefore depends on a relay (or `tx.origin`-controlling entity) supplying an arbitrary `originalSender`, which falls under the ruleset's explicit exclusion of "malicious relayer/node assumptions." I could not verify from the available index whether any additional off-chain/relay-admission control or circuit-side constraint (outside the files reviewed) further restricts `originalSender`, since circuit template files for this action were not found in the indexed content.

### Recommendation
Bind `originalSender` into the signed/circuit-verified data (e.g., include it in `getSignedMessageHash`/public inputs) or require `originalSender == sender` unconditionally in `performHinkalChecks`, removing the relay-only exemption, so that `transferERC20TokenFrom` in `DepositOnChainUtxosExternalAction` can never pull funds from an address that did not authorize the specific transaction.

### Proof of Concept
1. Victim previously calls `transact`/deposit flow, leaving an ERC20 `approve(Hinkal, large_amount)` allowance outstanding (common UX for repeated shielded deposits).
2. A whitelisted relay (or attacker controlling `tx.origin` as a relay) submits `transact` with `circomData.relay != address(0)`, `circomData.originalSender = victim`, `externalActionId` pointing to `DepositOnChainUtxosExternalAction`, `onChainCreation[i] = true`, `inputNullifiers` all zero, and `stealthAddressStructure` controlled by the attacker.
3. `performHinkalChecks` skips the `originalSender == sender` check because `relay != address(0)` [7](#0-6) .
4. `runAction` executes `transferERC20TokenFrom(token, victim, address(Hinkal), tokenTotal)`, pulling victim funds, and mints a UTXO under the attacker's stealth address [10](#0-9) .

Given the dependency on a "trusted" relay to actually differ `originalSender` from `sender`, this finding sits at the boundary of the "malicious relayer" exclusion in the rules — flagged here for completeness, but its validity as an in-scope unprivileged-EOA analog is uncertain without confirming whether relay admission itself can be attacker-influenced.

    function formBasicInput(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData,
        uint256[] memory input,
        uint256 index,
        uint256 emporiumMessage
    ) internal pure returns (uint256[] memory) {
        // 1) First we list public inputs as in the body of the main template (not the one with exact dimensions)
        input[index++] = circomData.stealthAddressStructure.H1x;
        input[index++] = circomData.stealthAddressStructure.H1y;
        input[index++] = circomData.stealthAddressStructure.stealthAddress;
        input[index++] = emporiumMessage; // this is for Emporium message signature verification

        // 2) Then we list the private inputs as in the body of the main template
        input[index++] = circomData.rootHashHinkal;
        input[index++] = getSignedMessageHash(
            chainId,
            verifyingContract,
            circomData,
            emporiumMessage
        );

        for (uint16 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            input[index++] = uint256(
                uint160(circomData.erc20TokenAddresses[i])
            );
        }

        for (uint16 i = 0; i < circomData.amountChanges.length; i++) {
            require(
                circomData.amountChanges[i] < MAX_AMOUNT &&
                    circomData.amountChanges[i] > -1 * MAX_AMOUNT,
                "amount changed is too large"
            );

            input[index++] = circomData.amountChanges[i] >= 0
                ? uint256(circomData.amountChanges[i])
                : CIRCOM_P - uint256(-circomData.amountChanges[i]);
        }

        for (uint16 i = 0; i < circomData.inputNullifiers.length; i++) {
            for (uint16 j = 0; j < circomData.inputNullifiers[i].length; j++) {
                input[index++] = circomData.inputNullifiers[i][j];
            }
        }

        input[index++] = circomData.timeStamp;

        for (uint16 i = 0; i < circomData.outCommitments.length; i++) {
            for (uint16 j = 0; j < circomData.outCommitments[i].length; j++) {
                input[index++] = circomData.outCommitments[i][j];
            }
        }
        input[index++] = circomData.calldataHash;

        input[index++] = circomData.stealthAddressStructure.H0x;
        input[index++] = circomData.stealthAddressStructure.H0y;

        return input;
    }
