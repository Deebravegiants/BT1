### Title
Per-variant fraud feedback disclosure via self-serve SignupEnded contradicts stated non-disclosure intent - (File: src/debug_report.rs)

### Summary
`Builder::failure_feedback_after_capture_proto` maps each individual `PipelineFailureFeedbackMessage` variant (`ContactLenses`, `EyeGlasses`, `Mask`, `FaceOcclusion`, `MultipleFaces`, `EyesOcclusion`, `HeadPose`, `Underaged`, `LowImageQuality`) to its own distinct `self_serve::orb::v1::signup_ended::FailureFeedbackType` i32 value, all of which are sent unmodified to the attacker's own app via `SignupEnded.failure_feedback` in `after_signup`. Despite the inline comment stating the code intentionally collapses fraud-related reasons into "a high level reason," the implementation does not actually collapse anything — every variant remains distinguishable.

### Finding Description
`failure_feedback_after_capture_proto` (`src/debug_report.rs:745-791`) performs a 1:1 match arm for every `PipelineFailureFeedbackMessage` variant, producing a distinct i32 for each. `PipelineFailureFeedbackMessage` is defined in `src/plans/fraud_check.rs:42-62` and its doc comment explicitly says it is "not an exhaustive list of the true failure modes... This list doesn't include the actual fraud based failure modes" — implying the intended design is to expose only coarse-grained/generic reasons, not liveness/fraud-specific categories like `Mask`, `MultipleFaces`, or `ContactLenses`. However, those exact fraud-adjacent variants are present in the enum and are mapped 1:1 to equally fraud-specific proto values (`Mask`, `MultipleFaces`, `ContactLenses`) in the emission function, with no aggregation/bucketing logic applied.

The result is fed into `after_signup` (`src/plans/mod.rs:1463-1498`): `failure_feedback_after_capture_proto()` is called at line 1478, and if `orb.config.lock().await.self_serve` is true, the vector of i32 codes is sent directly to the attacker's own client app over Orb Relay via `SignupEnded { success, failure_feedback }` (lines 1485-1494). Because the attacker is running their own self-serve signup session, they directly observe this response.

`fraud_check_feedback_messages` (`src/debug_report.rs:576-583`) is the entry point that populates `failure_feedback_after_capture` with these `PipelineFailureFeedbackMessage` values from fraud/liveness checks during the pipeline, and `iris_model_error` similarly pushes `PipelineFailureFeedbackMessage::EyesOcclusion` directly (`src/debug_report.rs:610-616`).

### Impact Explanation
An attacker performing repeated self-serve signup attempts can distinguish exactly which fraud/liveness heuristic caused rejection (e.g., differentiate a `Mask` detection from a `LowImageQuality` failure, or `MultipleFaces` from `HeadPose`), because each maps to a unique, always-emitted i32 in `SignupEnded.failure_feedback`. This enables iterative tuning of a physical presentation attack (e.g., adjusting mask material until the `Mask` code stops appearing, or adjusting contact lenses until `ContactLenses` stops appearing) to defeat specific fraud/liveness detectors one at a time — a fraud-signal oracle. This matches the Worldcoin/Orb bounty category of biometric/fraud-signal disclosure enabling liveness bypass tuning, though it is a disclosure/oracle issue rather than a direct unauthorized-signup or identity-binding compromise; actual bypass still requires the attacker to defeat other independent checks.

### Likelihood Explanation
Highly feasible and fully repeatable: it only requires unprivileged access to the self-serve signup flow (a presented QR code and control over the physical scene shown to the cameras), which the attacker already has by definition of being screened. No credentials, tampering, or operator access are needed — an attacker just runs many `do_signup` attempts, varying facial occlusion/props, and reads back the `failure_feedback` codes from their own `SignupEnded` message.

### Recommendation
Collapse all fraud/liveness-specific `PipelineFailureFeedbackMessage` variants into a small set of generic, non-diagnostic buckets before proto conversion in `failure_feedback_after_capture_proto` (e.g., group `ContactLenses`, `Mask`, `MultipleFaces`, `Underaged` into a single `GenericFailure`/`FraudSuspected` code), matching the stated design intent in the `PipelineFailureFeedbackMessage` doc comment, and only pass through genuinely benign/user-actionable codes (e.g., `LowImageQuality`, `HeadPose`, `FaceOcclusion` due to lighting) at full granularity.
