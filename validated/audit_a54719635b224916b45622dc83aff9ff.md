Audit Report

## Title
CORS wildcard origin matching allows domain-suffix spoofing without dot-boundary check - (`core/services/gateway/network/httpserver.go`)

## Summary
The gateway's `isAllowedOrigin` function implements wildcard CORS matching (`*.domain.com`) using `strings.HasSuffix(originHost, allowedHost)` without verifying that a `.` boundary precedes the matched suffix. This allows an attacker who registers any domain literally ending in the configured suffix (e.g., `notethereum.org` for a `*.ethereum.org` rule) to be treated as an allowed origin, even though it is not an actual subdomain. [1](#0-0) 

## Finding Description
For each configured `CORSAllowedOrigins` entry, `isAllowedOrigin` splits scheme/host/port and, after checking scheme and port equality, performs an exact-host check followed by a wildcard check when `allowedHost` begins with `*.`. [2](#0-1)  In the wildcard branch, the `*.` prefix is stripped and the remaining string is compared via `strings.HasSuffix(originHost, allowedHost)`, which matches any string ending with that substring — not just true subdomains separated by a dot. [3](#0-2)  For a configured rule `*.ethereum.org`, this incorrectly matches `evil-ethereum.org` or `notethereum.org`, domains not owned by or subordinate to `ethereum.org`. The resulting boolean directly gates reflection of the caller-supplied `Origin` header into the `Access-Control-Allow-Origin` response header in `handleRequest`, with no additional boundary validation performed afterward. [4](#0-3) 

## Impact Explanation
This is a CORS allowlist bypass: an attacker who registers an inexpensive domain ending in the configured trusted suffix can have their web page granted cross-origin access (via reflected `Access-Control-Allow-Origin`) to the gateway's HTTP JSON-RPC endpoint, as if it were a legitimate trusted subdomain such as `remix.ethereum.org`. This maps to the in-scope "allowlist bypass" / "gateway request impersonation" category, since it undermines the operator-configured CORS trust boundary intended to restrict which web origins can interact with the gateway.

## Likelihood Explanation
Exploitation requires only registering a domain name and hosting a page there — no privileged access, credentials, or compromise of the legitimate domain is needed. Any deployment using a wildcard `CORSAllowedOrigins` entry (a documented, tested configuration pattern per `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`) is affected, making this a realistic and repeatable bypass for an unprivileged internet-based actor.

## Recommendation
Require a dot boundary before the matched suffix, e.g.:
```go
if strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost {
    return true
}
```
This ensures `remix.ethereum.org` still matches `*.ethereum.org` while `notethereum.org` does not.

## Proof of Concept
1. Configure gateway with `CORSAllowedOrigins: ["https://*.ethereum.org"]`.
2. Send a request to the gateway's HTTP endpoint with header `Origin: https://notethereum.org`.
3. Observe `isAllowedOrigin` computing `allowedHost = "ethereum.org"` and `strings.HasSuffix("notethereum.org", "ethereum.org")` returning `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://notethereum.org`, confirming the bypass — this can be added as a unit test alongside the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, asserting failure (i.e., that the header should NOT be set for `notethereum.org`) to demonstrate the current incorrect behavior.
