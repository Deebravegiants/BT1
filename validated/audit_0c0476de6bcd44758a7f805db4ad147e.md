### Title
Zeroization of sensitive buffers is skipped on exception paths in `encryptCompressed`/`decryptCompressed` - ([File: libraries/secure-container/src/compressed.js])

### Summary
`encryptCompressed` and `decryptCompressed` copy secret/plaintext-bearing buffers (`databuffer`, `gzipped`, `expanded`) and only call `randomFill()` to wipe them *after* the `gzip()`/`encrypt()`/`decrypt()`/`gunzip()` calls succeed. There is no `try/finally`, so any exception thrown by those async calls (e.g. from attacker-crafted malformed compressed or encrypted input) causes the function to exit before the wipe calls run, leaving copies of plaintext/derived data un-zeroed in memory.

### Finding Description
In `decryptCompressed` [1](#0-0) , `databuffer` is a raw copy of the attacker-supplied encrypted blob, and `expanded`/`gzipped` hold the decrypted plaintext returned from `decrypt()` before it is gunzipped. The wipe calls `randomFill(databuffer)`, `randomFill(expanded)`, `randomFill(gzipped)` execute only on the line *after* `await gunzip(gzipped, ...)` returns successfully. If `decrypt()` throws (e.g. checksum mismatch in `conFile.decode`/`computeChecksum` per [2](#0-1) ) or `gunzip()` throws on a malformed/corrupted gzip stream, the function unwinds via exception before any `randomFill` line is reached, so `databuffer` and (if already produced) `expanded` remain populated with copied ciphertext/plaintext bytes with no wiping.

The symmetric issue exists in `encryptCompressed` [3](#0-2) : `databuffer` (a copy of caller-supplied plaintext) and `gzipped`/`expanded` are only wiped after `encrypt()` succeeds; if `gzip()` or `encrypt()` throws, these copies are left un-wiped.

Since these calls are not wrapped in `try/finally`, the invariant "secrets stay secret even on error paths" is violated: an attacker who can supply malformed compressed/encrypted data to `decryptCompressed` (e.g. via a crafted backup/import blob or deeplink payload processed by wallet import/restore flows) can force an exception in `decrypt()`/`gunzip()` and leave a decrypted plaintext copy resident in the process heap indefinitely, extending the exploitable memory-disclosure window beyond normal GC timing.

### Impact Explanation
The affected buffers may contain decrypted seed/secret plaintext (`expanded`) or raw ciphertext copies (`databuffer`). Failure to wipe them on error paths increases the window in which a subsequent memory-disclosure primitive (heap dump, crash reporter, swap, or another vulnerability granting memory read) could recover this data. This is a defense-in-depth/secret-hygiene weakness rather than a direct signing/auth bypass; it does not by itself grant unauthorized signing or unlock the wallet, but it materially increases exposure of decrypted secret material.

### Likelihood Explanation
Triggering the missing-wipe condition only requires supplying a malformed/corrupted encrypted or gzip-compressed container to `decryptCompressed` (or invalid plaintext leading to gzip failure in `encryptCompressed`), which is trivial for any caller that controls import/restore data (e.g. a crafted backup file or deeplink payload). No privileged access is needed to trigger the code path; however, actually reading the un-wiped memory requires a separate memory-disclosure capability, which is outside this specific function's control.

### Recommendation
Wrap the compress/encrypt/decrypt/gunzip calls and the corresponding `randomFill` cleanup in `try/finally` blocks so the buffers are wiped regardless of whether the operation throws, e.g.:
```js
export async function decryptCompressed(encryptedData, passphrase, { expandTo32k = false } = {}) {
  const databuffer = Buffer.from(encryptedData)
  let expanded, gzipped
  try {
    ;({ data: expanded, blobKey, metadata, header } = await decrypt(databuffer, passphrase))
    gzipped = expandTo32k ? shrink32k(expanded) : expanded
    const result = await gunzip(gzipped, { format: 'buffer' })
    return { data: result, blobKey, metadata, header }
  } finally {
    randomFill(databuffer)
    if (expanded) randomFill(expanded)
    if (gzipped && expanded !== gzipped) randomFill(gzipped)
  }
}
```
Apply the analogous pattern to `encryptCompressed`.

### Proof of Concept
Unit test plan:
1. Mock `@exodus/crypto/compress`'s `gunzip` to throw (simulating a corrupted/malformed gzip stream) when called with a controlled buffer.
2. Call `decryptCompressed(malformedEncryptedBlob, passphrase)` and catch the rejection.
3. Spy on `randomFill` (from `@exodus/crypto/randomBytes`) via module mock, assert it was never called with `databuffer`/`expanded` after the exception — demonstrating the buffers remain un-wiped.
4. Alternatively, keep references to `databuffer`/`expanded` outside the function scope (by mocking `decrypt` to return a buffer captured in a test-level variable) and after the rejection, assert `buffer.equals(originalPlaintextBytes)` is still `true`, proving the plaintext copy was not zeroed.
5. Repeat symmetric test for `encryptCompressed` by forcing `gzip()` or `encrypt()` to throw and asserting `databuffer`/`gzipped` retain original plaintext bytes.
