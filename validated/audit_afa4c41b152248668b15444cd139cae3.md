Based on my review, I found a legitimate identity-binding flaw in the webhook processing path.This confirms the vulnerability. The `VerifiableQuery` interface (`to_signable_string`) is the only input to HMAC verification, and for webhooks that method returns solely the raw body, leaving the `shop-domain` and `topic` headers completely outside the signature's protection.

### Title
Webhook `shop` and `topic` identifiers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`) values from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator.validate` checks is computed only over the raw request body. Because the identity binding `shop header == HMAC-covered bytes` does not hold, any holder of a genuine `(body, hmac)` pair from Shopify (i.e., any merchant who installs the app on their own store) can resubmit that same body/hmac pair to the app's public webhook endpoint with a different `shop-domain` header value, and the gem will accept it as an authentic webhook for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string`, which is body-only: [4](#0-3) 

`Registry.process` trusts `request.shop` (and `request.topic`) after this body-only HMAC check succeeds, and passes them directly to the handler as the identity of the event's owning tenant: [5](#0-4) 

The broken identity binding is: `shop (used to attribute the event) == shop (covered by the HMAC signature)`. In fact `shop` (and `topic`) are never inputs to `compute_signature`, so the equality never has to hold for a request to pass verification.

### Impact Explanation
This is a cross-tenant identity bypass. Any external party who can install the app on a shop they control (a routine, unprivileged action any merchant can perform) receives genuine Shopify-signed webhooks addressed to their own shop. They can capture one such `(raw_body, X-Shopify-Hmac-Sha256)` pair and replay it against the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`). `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` calls the registered handler with `WebhookMetadata#shop` set to the attacker-chosen value. Any host application that uses `data.shop` to look up records, apply the payload, or make authorization decisions for "the shop that owns this event" will now act on behalf of, or attribute activity to, a shop the attacker does not control — a direct cross-tenant data/action confusion. This aligns with the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High. No secrets, tokens, or privileged access are required beyond the ability to install the app on a shop the attacker owns and to send an HTTP POST to the app's public webhook URL — both are attacker-reachable prerequisites for any unprivileged Shopify merchant/developer. The only skill required is capturing one legitimate webhook delivery (e.g., via their own store's webhook logs or a simple network capture) and replaying it with a modified header.

### Recommendation
Bind the tenant/event identity into the verified signable content instead of trusting bare headers. Concretely, change `Request#to_signable_string` (and `HmacValidator`) so that verification incorporates `shop`, `topic`, and any other routing-critical header, or require host applications/this gem to independently cross-check `request.shop` against a known/registered shop domain (e.g., via `Utils::ShopValidator`) and reject webhooks whose header-derived shop is not the one your app installed for at the corresponding access token/session — the gem currently provides no such check itself.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`; Shopify sends a genuine webhook, e.g. `orders/create`, to the app's webhook endpoint with body `B`, headers including `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)`.
3. Attacker sends a new POST to the same public webhook endpoint with the identical body `B` and identical header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the header [6](#0-5) ; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation passes [7](#0-6) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [8](#0-7) , causing the host application to process the attacker's order data as if it belonged to the victim's shop.
