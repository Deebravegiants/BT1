### Title
Accrual `scaled_to_original` i128 overflow permanently freezes a whale market before the borrow-index cap engages - ([File: common/src/rates/simulate.rs])

### Summary
`accrue_step` computes `borrowed_original = scaled_to_original(borrowed, borrow_index)` and `supplied_original = scaled_to_original(supplied, supply_index)` via `Ray::mul` → `mul_div_half_up`, which panics with `MathOverflow` when the scaled-value product exceeds `i128::MAX`. The borrow index is capped at `MAX_BORROW_INDEX_RAY = 1e36` inside `update_borrow_index`, but the cap is applied *after* the value computation in the next step — so a large market can reach a state where `borrowed * borrow_index / RAY` no longer fits `i128` while `borrow_index < MAX_BORROW_INDEX_RAY`. Since `global_sync` runs accrual before every mutating verb (`contracts/pool/src/interest.rs:20-33`), once a market crosses this RAY-value ceiling, every subsequent call that accrues — `update_indexes`, `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt` — reverts with `MathOverflow`. No verb can skip accrual, so the market and all funds in it are frozen permanently. This is already demonstrated by the checked-in harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which shows withdraw and repay both reverting with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and notes that the headroom bound stated in `docs/reference/formulas.md` is wrong. ### Finding Description
- `update_borrow_index` (`common/src/rates/index.rs:13`) clamps the index at `MAX_BORROW_INDEX_RAY`, but `accrue_step` (`common/src/rates/simulate.rs:60-61`) first unscales `borrowed` and `supplied` at the *previous* indexes through `scaled_to_original`, which uses non-saturating `mul_div_half_up` (`common/src/math/fp_core.rs:108-118`) and panics on unrepresentable results.
- The panic is therefore a function of `shares × index`, not of the index alone. For a very large book (the test uses a 1e9-token, 18-decimal market at 98% utilization on the steep XLM-rate curve), `borrowed * borrow_index` overflows `i128` at an index far below `1e36`, so the ceiling that is supposed to stop index growth never engages.
- `global_sync` (`contracts/pool/src/interest.rs:20`) is invoked at the head of every state-changing pool entrypoint, and `accrue_step` recomputes the overflowing product every step. The panic is permanent and unrecoverable — no unprivileged or privileged path skips accrual for that market.
- Analogous to CVE-2021-32491 (integer overflow in `render()` crashing on crafted input): here a reachable market state drives the fixed-point pipeline into an unrecoverable overflow panic, but instead of a crash the consequence is a permanently bricked market holding user funds.

### Impact Explanation
Permanent freezing of all funds in the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and bad debt cannot be cleaned. Every position denominated in that market's book is stuck, and collateral positions in other markets that must pass through accrual of the frozen book (e.g., `update_indexes` batches) are also blocked. Because the pool totals are monotonic share counts, there is no recovery path — the panic occurs before any state write each time.

### Likelihood Explanation
Reachable by a single unprivileged address in principle — `supply`/`borrow`/`update_indexes` are permissionless — but requires an extremely large book (≈1e9 whole tokens at 18 decimals) pushed to ~98% utilization and years of sustained high-rate accrual, per the harness test (cliff reached within tens of years, before the documented bound). It also depends on governance listing a high-decimal asset with lifted caps and a steep rate curve, and on utilization staying near the steep segment. The overflow is deterministic once the state is reached and cannot be undone, so severity is High impact with Low–Medium likelihood.

### Recommendation
- Compute the utilization inputs with `mul_div_floor_saturating` (or clamp `borrowed`/`supplied` to the largest share count whose unscaled value fits `i128`), so accrual can proceed to the `MAX_BORROW_INDEX_RAY` sticky cap instead of panicking.
- Alternatively, in `update_borrow_index`, clamp proactively: if `borrowed` or `supplied` unscaled value would overflow at the new index, pin the index at the largest representable value and mark the market accrual-frozen-but-exitable, e.g., allow `withdraw`/`repay`/`liquidate` against the last stored indexes when accrual cannot proceed.
- Fix the headroom bound in `docs/reference/formulas.md`, which the harness test flags as incorrect.

### Proof of Concept
The repo's own harness test demonstrates it end-to-end (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
// list a BIG18 market (18 decimals) with the steep XLM rate curve, lift caps
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);              // whale supply
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // 98% utilization

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// -> MATH_OVERFLOW while book.borrow_index < MAX_BORROW_INDEX_RAY
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Root cause chain: `global_sync` → `accrue_chunk` → `accrue_step` → `scaled_to_original(borrowed, borrow_index)` → `mul_div_half_up` → `MathOverflow` panic, repeated identically on every subsequent entrypoint.

```rust
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
