### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` identity used downstream to attribute the webhook to a tenant is taken from an unauthenticated HTTP header that is never included in the signed material. This breaks the binding `shop-header-used-for-attribution == shop-bound-by-signature`, allowing an attacker who can obtain one validly-signed payload (e.g., by triggering a webhook on their own store, which uses the same app-wide `client_secret`) to replay it against the app's webhook endpoint with an arbitrary `shop-domain` header, causing the app to process it as though it originated from a different (victim) tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the HMAC — it never touches `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to attribute the event to a tenant, passing it into the handler as authoritative metadata: [4](#0-3) 

Because the app's `client_secret` is shared across all shops that installed the app (it is not per-shop), any merchant/attacker who has the app installed on their own store can receive a legitimately-signed webhook body+HMAC for an event they themselves triggered (e.g., by pointing a custom webhook subscription at infrastructure they control), then re-POST that exact body/HMAC pair to the target application's webhook endpoint with the `shop-domain` header rewritten to a victim shop. Since the signature never covers `shop`, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the forged event to the app's handler tagged with the victim's shop — a direct cross-tenant identity-binding break: `shop attributed to event ≠ shop actually authenticated by the HMAC`.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker-controlled webhook body can be attributed to any shop of the attacker's choosing. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to select a session/access token, update shop-scoped records, or trigger business logic like `customers/redact` or `shop/redact` mandatory compliance topics), this can lead to processing forged mutations against another tenant's data using the attacker's own crafted body content, satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any application built on this gem's webhook dispatch, because: (1) obtaining a validly-signed webhook is trivial for any attacker who is a legitimate (even free/trial) merchant of the app, since they can trigger events on their own store; (2) the `shop` header is fully attacker-controllable once they replay the captured payload to the app's endpoint directly (no TLS interception or secret needed); (3) nothing in `Request` or `Registry` cross-checks the header against any signed value.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified data, e.g., by including the shop domain in the signable string, or by requiring the caller to independently authenticate the source (mTLS/IP allowlist to Shopify, or verifying the shop against a known/expected value for the delivery channel) before trusting `request.shop` for attribution in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and creates a custom webhook subscription (e.g., via the Admin GraphQL API, which they can do with their own access token) with callback address pointing to infrastructure they control.
2. Shopify delivers a webhook to the attacker's endpoint, signed with the app's `client_secret`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-topic: orders/create`
   - Body: attacker-crafted JSON payload (attacker controls their own store's order data).
3. Attacker re-sends the exact same body and `x-shopify-hmac-sha256` value to the target app's real webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (matches, since body/HMAC are unchanged) — [5](#0-4)  and [6](#0-5) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's forged payload>, ...)` — [7](#0-6) , causing the application to process attacker-controlled data as belonging to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
