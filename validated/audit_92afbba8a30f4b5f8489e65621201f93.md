### Title
Webhook `topic` and `shop-domain` headers are not covered by the HMAC signature, allowing a replayed body to be dispatched under an attacker-chosen topic/shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` verifies the HMAC over that raw body alone. `Webhooks::Registry.process` then uses the completely unsigned `topic` and `shop-domain` headers to select the handler and to construct `WebhookMetadata#shop`, which host apps use as the authenticated shop identity. Because none of the header values participate in the signature, an attacker who owns a legitimate development shop and receives one validly signed webhook body can replay that exact `(raw_body, hmac)` pair to any app's webhook endpoint with forged `x-shopify-topic` / `x-shopify-shop-domain` headers, and the gem will accept it as authentic.

### Finding Description
The binding the gem is expected to hold is:
`request.shop (used by the handler as "the" authenticated tenant) == the shop whose secret and event actually produced (raw_body, hmac)`.

Trace:
- `Webhooks::Request#hmac` reads `shopify_header("hmac-sha256")` [1](#0-0)  — an unsigned header value.
- `Webhooks::Request#shop` and `#topic` read `shopify_header("shop-domain")` / `shopify_header("topic")` directly from attacker-controlled headers, with no cryptographic tie to the body [2](#0-1) .
- `to_signable_string` returns only `@raw_body`, excluding topic, shop-domain, webhook-id, and api-version from the signed content [3](#0-2) .
- `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac`; it never touches headers [4](#0-3) .
- `Registry.process` raises only if the HMAC check fails, then picks the handler purely from the unsigned `request.topic`, and forwards the unsigned `request.shop` straight into `WebhookMetadata` as the tenant identity consumed by the app's handler [5](#0-4) .

Exploit flow: the attacker (per the rules, an unprivileged user who may create their own dev shop, install their own app, and register their own webhook endpoint) receives a legitimately Shopify-signed `(raw_body, hmac)` pair for an event on their own shop. They then POST that identical body and hmac to the target app's webhook endpoint, substituting `x-shopify-shop-domain` with a victim merchant's domain and/or `x-shopify-topic` with any topic the app has registered a handler for. `HmacValidator.validate` still succeeds because it only checks the body bytes against the shared app secret; `Registry.process` dispatches to the handler for the forged topic with `data.shop` set to the forged victim domain. Any host app that (as documented) uses `data.shop` to look up a session/access token and acts on `data.body` will now execute an authenticated Admin API action for the victim merchant driven by attacker-controlled body content — this is a cross-tenant identity break, not merely a duplicate-delivery issue.

None of the existing guards prevent this: `ShopValidator.sanitize!` is not invoked in the webhook path, there is no `state`/JWT check here, and Sorbet's `T.cast` only enforces types, not provenance. The core cause is the omission of `topic` and `shop-domain` from `to_signable_string`.

### Impact Explanation
The shop identity (`request.shop`) and dispatch topic (`request.topic`) that downstream handler code trusts as authenticated are not actually bound to the signature. An app following the gem's own documented pattern (using `data.shop` to resolve a session/access token, and `data.topic`/`data.body` to decide what action to take) can be made to perform an authenticated Admin API action against an arbitrary victim merchant's store using attacker-chosen body content and topic, purely from a body the attacker legitimately received for their own shop. This is repeatable against any number of victim merchants of the same app, for as long as the attacker can obtain one valid signed webhook body (trivially available by registering their own app installation). It falls into "cross-tenant access" — one tenant's webhook payload is attributed to another tenant's identity.

### Likelihood Explanation
Preconditions: the target app must use this gem's `Webhooks::Registry`/`Webhooks::Request` for webhook processing (documented, default usage) and must use `data.shop`/`data.topic` to select the shop/session and action (also the documented pattern). Attacker cost is low: create a dev shop, install the app or any app using this gem, subscribe to a webhook, capture one `(raw_body, hmac)` pair, then replay it against the target endpoint with forged headers — no secrets, no TLS interception, and fully repeatable.

### Recommendation
Include `topic`, `shop-domain` (and ideally `webhook-id`, `api-version`) in the signed material, or otherwise cryptographically bind them to the HMAC-verified payload before they are used for dispatch or handed to the handler as the shop identity. At minimum, `Registry.process` should refuse to trust `request.shop`/`request.topic` unless they can be independently corroborated (e.g., against the registered shop's known domain or the body's own shop reference).

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (added test)
def test_replayed_signed_body_dispatches_under_forged_topic_and_shop
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
  signed_hmac_header = Base64.encode64(hmac)

  legit_topic  = "orders/create"
  forged_topic = "app/uninstalled"
  victim_shop  = "victim-shop.myshopify.com"

  seen = { legit: false, forged: false }

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: legit_topic, path: "p1", delivery_method: :http,
    handler: TestHelpers::FakeWebhookHandler.new(->(data) { seen[:legit] = data.shop }),
  )
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: forged_topic, path: "p2", delivery_method: :http,
    handler: TestHelpers::FakeWebhookHandler.new(->(data) { seen[:forged] = data.shop }),
  )

  # Attacker replays the SAME (body, hmac) pair with forged topic/shop headers.
  forged_request = ShopifyAPI::Webhooks::Request.new(
    raw_body: body,
    headers: {
      "x-shopify-topic" => forged_topic,
      "x-shopify-hmac-sha256" => signed_hmac_header,
      "x-shopify-shop-domain" => victim_shop,
    },
  )

  ShopifyAPI::Webhooks::Registry.process(forged_request)

  # Binding under test: shop identity handed to handler should be tied to the
  # authenticated source of (body, hmac), not an arbitrary header.
  # This assertion FAILS today because process() accepts the forged topic/shop.
  assert_nil(seen[:forged], "forged topic/shop dispatched despite unsigned headers")
end
```
This demonstrates that `HmacValidator.validate` and `Registry.process` accept a signed body under any attacker-chosen `topic`/`shop-domain`, confirming the header/signature binding is absent.
