### Title
Pausing HyperFungibleToken/WrappedHyperFungibleToken blocks the timeout-refund path, freezing already-burned/locked user funds - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleTokenUpgradeable` gate `onPostRequestTimeout` (the refund/unlock path for a cross-chain transfer that failed to deliver) behind the same `whenNotPaused` modifier used for `send()` and `onAccept()`. This mirrors the reported bug class: an emergency `pause()` doesn't just stop new sends, it also blocks users from recovering funds already committed (burned/locked) for a transfer that has timed out.

### Finding Description
`send()` burns (or locks, in the wrapped variant) the user's tokens up-front and dispatches an ISMP `PostRequest` to the destination chain: [1](#0-0) 

If that request is not delivered before its timeout, the only path to make the sender whole is `onPostRequestTimeout`, which re-mints (or unlocks) the burned/locked amount back to the sender: [2](#0-1) 

That function — the functional analog of "withdraw/redeem" for funds already committed to the bridge — is guarded by `onlyHost whenNotPaused`, exactly as in the original finding where a vault's withdraw/redeem was blocked by `whenNotPaused`: [3](#0-2) 

The same pattern exists in the upgradeable ERC20 variant: [4](#0-3) 

and in the wrapped (lock/unlock) variant, whose timeout handler is responsible for returning locked ERC20/native collateral to the refundee: [5](#0-4) 

Because the relayer calling `onPostRequestTimeout` cannot bypass `whenNotPaused`, any relayer submitting a timeout proof while the token contract is paused will have the refund transaction revert. The user's tokens remain burned/locked with no way to reclaim them until an owner calls `unpause()`.

### Impact Explanation
While the pause is active, users whose transfers time out cannot recover already-burned/locked funds via the only refund mechanism (`onPostRequestTimeout`); their principal is temporarily but completely frozen since `transfer`/`transferFrom` are also `whenNotPaused`, so they cannot even move the (nonexistent, already-burned) tokens elsewhere. This is a direct fund-freezing bug reachable by an ordinary relayer/user in the normal ISMP timeout-relay flow — no privileged or malicious actor is required to trigger the freeze; the pause itself is a legitimate emergency-response action, but its side effect of blocking the refund path is unintended and matches the reported "pause blocks withdraw, locking user funds" bug class. Severity is Medium, consistent with the original Sherlock finding, since resolution (owner unpausing) restores access, but the freeze duration is fully under third-party/admin discretion, and during a legitimate incident-response pause (the exact scenario pausing is meant for) this is precisely when users most need the refund path to work.

### Likelihood Explanation
This is highly likely to occur in practice: pausing is the designed incident-response tool for exactly the scenarios (e.g., a bug discovered in `onAccept`) where in-flight requests are most likely to time out, meaning the freeze condition co-occurs with the pause's most probable use case. Any relayer attempting to deliver a legitimate timeout proof during that window will find the call reverting, and must simply retry after unpause, but there is no code path enabling recovery while paused.

### Recommendation
Remove `whenNotPaused` from `onPostRequestTimeout` in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol` (and `WrappedHyperFungibleToken.sol` if it follows the same pattern), so that refunds for already-committed funds remain available regardless of pause state, mirroring the recommendation from the original finding to exempt withdraw/redeem-equivalent functions from the pause guard.

### Proof of Concept
1. Alice calls `send()` on `HyperFungibleToken`, burning `amount` tokens and dispatching a `PostRequest` to chain B.
2. Before the request is delivered, the token owner calls `pause()` (e.g., in response to an unrelated incident).
3. The request times out on-chain (per ISMP timeout rules), and a relayer submits a valid timeout proof, triggering the host to call `onAccept`'s sibling `onPostRequestTimeout(incoming)` on `HyperFungibleToken`.
4. The call reverts because the contract is paused (`whenNotPaused`), even though `onlyHost` and all other checks pass — Alice's burned tokens are not re-minted.
5. Alice's principal remains frozen (she holds neither the original tokens nor a refund) until the owner calls `unpause()`, which the affected user has no ability to trigger and no guarantee of timing. [6](#0-5) [2](#0-1)

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(incoming.request.body, (HyperFungibleTokenUpgradeable.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
