### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` never authenticates the `shop`, `topic`, or `webhook_id` headers. Any request carrying a body + HMAC pair generated for one shop passes validation unchanged if the `x-shopify-shop-domain` header is swapped to a different (victim) shop, letting an attacker who controls their own installed shop feed arbitrary webhook data into the app under a victim shop's identity.

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the received signature: [1](#0-0) 

For webhook requests, `to_signable_string` is defined to return only the raw body: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors all read directly from HTTP headers that are never part of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (an unauthenticated header) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

This is precisely the "field acted on but not covered by the HMAC" pattern: the equality that should hold is `shop_header == shop_bound_by_signature`, but the signature binds only the body, so `shop_header` can be freely substituted while the signature remains valid. Contrast this with `Auth::Oauth::AuthQuery`, where `shop` (and `host`, `state`, `code`, `timestamp`) is explicitly included in `to_signable_string` and therefore is bound to the HMAC: [5](#0-4) 

The gem's own documentation instructs apps to trust `data.shop` directly for tenant-scoped work (e.g., enqueuing per-shop jobs), so a host app that follows the documented API as-is inherits this gap: [6](#0-5) 

### Impact Explanation
An attacker who has installed the app on any shop they control (a free, unprivileged action available to any internet user, e.g., via a Shopify Partner dev store) can trigger a genuine webhook for their own shop, capturing a valid `(raw_body, HMAC)` pair signed with the app's `client_secret`. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never checked the shop header, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled `body`. Any app that scopes actions/storage by `data.shop` (as the docs instruct) will apply attacker-supplied data to the victim tenant's records — a cross-tenant data-integrity/access issue satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on any shop (self-service, unprivileged), (2) knowledge of the app's public webhook path (visible via registration or app configuration), and (3) capturing one legitimate webhook body/HMAC pair from the attacker's own shop, which is trivial (e.g., triggering `orders/create`). No access token, `api_secret_key`, or victim credentials are needed, making this highly reachable by any unprivileged internet user who is a merchant of the target app.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the material that is HMAC-verified, or otherwise authenticate the shop domain independently of the header value — for example, by having `HmacValidator`/`Request` incorporate the shop domain into the signable string, or by requiring `Registry.process` to cross-check `request.shop` against an installed-shop registry/session store keyed by an already-authenticated identifier before invoking the handler. At minimum, update `docs/usage/webhooks.md` to warn that `data.shop` is not authenticated by the HMAC and must be independently verified (e.g., against known installed shops) before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - header `x-shopify-topic: orders/create` (unchanged or forged, also unsigned)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC-SHA256(client_secret, B) == H`.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
