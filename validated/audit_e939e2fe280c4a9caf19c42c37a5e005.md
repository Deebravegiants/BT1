Confirmed: `approveUnlimited` grants `type(uint256).max` allowance to the router, persistent across calls. This confirms the exploit primitive is real and fully controlled by the attacker's `externalActionMetadata`.

### Title
Uncapped router calldata + persistent max-allowance lets attacker mint UTXOs backed by stranded/unaccounted tokens - (`contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`LifiExternalAction.callRouter` executes attacker-controlled `externalActionMetadata` via `router.call(...)` after granting the router unlimited (`type(uint256).max`) allowance over the action contract's `inputToken` balance, without ever checking that the input token amount consumed equals the `inputAmount`/`-deltaAmountChanges[0]` that Hinkal actually transferred in and accounted for. Because any unprivileged party can strand extra `inputToken` balance in the `LifiExternalAction` contract (e.g. a plain ERC-20 `transfer` directly to its address) and the router pulls tokens based on the amount encoded in the attacker's own calldata (not on Hinkal's accounted `inputAmount`), an attacker can prove/deposit only `1` wei while causing the router to swap `S+1`, and receive a single output UTXO backed by the full `S+1` swap result.

### Finding Description
Equality that should hold: tokens leaving `LifiExternalAction` into the router for the swap == `-deltaAmountChanges[0]` (the amount Hinkal actually transferred into the action and that the proof/circuit accounted for). Trace:

- `Hinkal.transact` → `_externalTransact` (`contracts/Hinkal.sol:234-261`) computes `deltaAmountChanges[0] = circomData.amountChanges[0]` and transfers exactly `uint256(-deltaAmountChanges[0])` (`1` wei in the scenario) of `inputToken` from Hinkal to `LifiExternalAction`, then calls `runAction(circomData, deltaAmountChanges)`.
- `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-68`) computes `inputAmount = uint256(-deltaAmounts[0])` and forwards it to `callRouter`, along with `circomData.externalActionData.externalActionMetadata` — raw calldata that is entirely attacker-authored (it is part of `CircomData`, and the attacker generates their own proof, so they choose every byte of it).
- `LifiExternalAction.callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`) calls `approveUnlimited(inputToken, router)` (which sets allowance to `type(uint256).max` when below half-max, see `contracts/TransfererBase.sol:32-43`), then executes `router.call(externalActionMetadata)`. Notice `inputAmount` is **never used** in the ERC-20 branch — it plays no role in constraining what the router pulls. The only accounting done afterward is `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore`, i.e. purely the *output* side; there is no check on the input token's balance before/after the call.
- The attacker can freely encode `externalActionMetadata` to instruct the router to pull an arbitrary amount `S+1` of `inputToken` via `transferFrom(LifiExternalAction, router, S+1)` (the router already holds max allowance thanks to `approveUnlimited`), as long as `LifiExternalAction`'s ERC-20 balance covers it. That balance can be inflated beforehand by simply transferring `S` tokens directly to the public `LifiExternalAction` contract address (any EOA can do this — no privileged role needed), stranding them there.
- `swappedAmount` (computed purely from output-token balance diff) is fully converted into `amountToSendToHinkal` and wrapped into a single output `UTXO` (`ExternalActionSwap.sol:89-101`) sent to `msg.sender`, which from Hinkal's perspective is Hinkal itself (since `runAction` is called by Hinkal). Back in `Hinkal.transact`, the balance-consistency check (`contracts/Hinkal.sol:96-146`) is tautological for the output token — `utxoAmount` is derived from the very same balance diff it's compared against — so it can never fail, regardless of whether the swap input was `1` or `S+1`.
- `HinkalHelper.performHinkalChecks`/`getHashedCalldata` (`contracts/HinkalHelper.sol:208-236`, `contracts/CircomDataBuilder.sol:10-54`) only bind `calldataHash` to the exact bytes of `externalActionMetadata` used in the transaction (proof-of-integrity against tampering after proof generation) — they never validate what those bytes actually instruct the router to move, nor tie an amount inside the calldata to `amountChanges[0]`.

None of the existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, the `balanceDif` requires, `insertNullifiers`) constrain the semantic amount encoded in `externalActionMetadata`, nor do they check that `LifiExternalAction`'s own input-token balance change matches `inputAmount`. The root cause is entirely in Hinkal's own contracts (unconditional `approveUnlimited` + unchecked pass-through of attacker calldata + no input-side balance accounting), not a LI.FI router defect.

### Impact Explanation
An attacker mints a shielded output UTXO backed by `S` tokens they never deposited nor proved — this is a Critical finding: it lets an attacker mint shielded value without backing, directly stealing/diluting the pool's real assets and creating insolvency risk for other depositors who legitimately own tokens equal to `S` (whether those tokens are the attacker's own prior stranded deposit or, more severely, dust/residual balances left behind by other users' swaps). The attack is repeatable any time excess `inputToken` balance can be made to sit in `LifiExternalAction` before a swap call.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: they can (1) send any amount `S` of an ERC-20 they choose directly to the public `LifiExternalAction` address (a normal `transfer`, no Hinkal interaction needed), (2) craft `externalActionMetadata` themselves since they generate their own proof and control every `CircomData` field, and (3) call `transact` with `amountChanges[0] = -1`. The only cost is `S` (which the attacker can choose to be a token they already fully control, then simply refuse to "deposit" it through the proven path) plus gas. No relayer, admin, or third party involvement is required, and the flow is repeatable for every subsequent `transact` swap call.

### Recommendation
In `LifiExternalAction.callRouter` (and any other external-action router integration using this pattern), measure and enforce the input-token balance delta consumed by the router call against the accounted `inputAmount`: record `inputBalanceBefore = getERC20OrETHBalance(inputToken)` before `router.call`, and after the call `require(inputBalanceBefore - getERC20OrETHBalance(inputToken) == inputAmount, "input amount mismatch")`. Additionally, avoid granting `type(uint256).max` allowance persistently — approve only for the exact `inputAmount` needed per call (`approveERC20Token(inputToken, router, inputAmount)`) and reset to zero afterward, so stranded/extra balance cannot be pulled by a single crafted calldata even if the balance-diff check were bypassed.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `LifiExternalAction` with a mock router that, on a specific selector, executes `token.transferFrom(msg.sender_context==LifiExternalAction, router, amountEncodedInCalldata)` then mints/transfers back `amountEncodedInCalldata` (1:1) of a mock output token to `LifiExternalAction`.
2. "Stranding" step: from an attacker EOA, call `mockInputToken.transfer(address(lifiExternalAction), S)` directly (no Hinkal call), confirming `mockInputToken.balanceOf(address(lifiExternalAction)) == S`.
3. Attacker builds `CircomData` for a swap transaction with `amountChanges[0] = -1` (so `deltaAmountChanges[0] == -1`), `erc20TokenAddresses = [inputToken, outputToken]`, and `externalActionData.externalActionMetadata` encoding a mock-router call that pulls `amountIn = S + 1` (not `1`) from `LifiExternalAction`. Generate a valid proof locally for this `CircomData` (calldataHash binds to this exact metadata, so it's provable).
4. Call `Hinkal.transact(...)`. Assert:
   - Only `1` wei of `inputToken` ever left Hinkal's own balance (`deltaAmountChanges[0] == -1`).
   - `mockRouter` pulled `S+1` from `LifiExternalAction` (`inputToken.balanceOf(lifiExternalAction)` drops by `S+1`, to `0`).
   - `swappedAmount`/`amountToSendToHinkal` in `ExternalActionSwap.swap` equals `S+1` (minus fees), and the resulting `UTXO.amount` reflects `S+1`-based value.
   - The attacker ends up with a spendable UTXO worth `S+1` while `deltaAmountChanges` / the proven `amountChanges[0]` only ever recorded `-1`, proving the equality `tokens sent to router (S+1) != -deltaAmountChanges[0] (1)` is broken and unconstrained by any Hinkal check.     function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
