### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed to the app's webhook handler. This breaks the binding between the verified bytes (HMAC-covered raw body) and the tenant identifier (`shop`) that the host application relies on to attribute a webhook to a specific merchant, matching the report's "field acted on but not covered by the HMAC" bug class.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC secret, never binding it to any header value: [3](#0-2) 

`Registry.process` checks only `Utils::HmacValidator.validate(request)` and then forwards `request.shop` (the unauthenticated header) straight into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The documented handler contract explicitly tells app developers that `data.shop` is "The shop domain of the webhook" and to use it for tenant identification (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

**Binding that should hold:** `HMAC-verified(raw_body) == HMAC-verified(raw_body, shop, topic, webhook_id, api_version)`. In reality: `HMAC-verified(raw_body)` while `shop` (and topic/webhook_id/api_version) are trusted unverified. Because the HMAC is computed purely over the JSON body and the api secret, any request whose body byte-for-byte matches a body the attacker has previously received a valid signature for (e.g., a webhook delivered to the attacker's own shop after installing the app) will pass `HmacValidator.validate` regardless of the `X-Shopify-Shop-Domain` header value sent with it. An attacker who operates their own Shopify store with the app installed can:
1. Install the target app on their own store and capture a legitimate webhook delivery (raw body + valid `X-Shopify-Hmac-Sha256`).
2. Replay that exact raw body and HMAC to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `shop: <victim-domain>` and the attacker's `body`.

### Impact Explanation
If the host application follows the gem's own documented pattern — using `data.shop` from a "verified" webhook to select the tenant record to update (a documented, expected usage pattern) — an attacker can inject or forge webhook events attributed to a shop they do not own, since the "verification" performed by this gem does not actually bind the shop identity to the signed content. This is a cross-tenant identity-binding break rooted in this gem's `Request`/`HmacValidator`/`Registry` implementation, not merely a downstream misuse, because the gem markets `Registry.process` as verifying "the request did indeed come from Shopify" for the tuple `(topic, shop, body, webhook_id, api_version)` while its HMAC computation covers only `body`.

### Likelihood Explanation
Exploitation requires the attacker to be able to obtain at least one valid `(body, hmac)` pair signed with the target app's `api_secret_key`. The most realistic path is installing the app on an attacker-controlled store (public apps that can be installed by anyone) and capturing a real webhook for that store, then replaying it with a modified `shop` header, or for topics whose body content is attacker-influenced (e.g., a webhook triggered by attacker's own store actions), crafting a body of choice. Bodies must be byte-identical for the given HMAC, so an attacker is limited to shop-independent content already sent by Shopify for their own store or to submitting a body they can shape and get Shopify to sign via their own store's webhook triggers — this constrains but does not eliminate exploitability, especially for topics where the body is otherwise near-static or attacker-influenced (e.g., `app/uninstalled`, `shop/update`).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-verified surface, or otherwise cryptographically or out-of-band verify that the `X-Shopify-Shop-Domain` header matches the shop that the app expects for that delivery (e.g., cross-check against a known/installed-shops list before invoking the handler), rather than trusting the header solely because the raw body's HMAC validates.

### Proof of Concept
Conceptual PoC (cannot be executed here, but demonstrates the code path):
```ruby
# Attacker has app installed on attacker-shop.myshopify.com and captured
# a legitimately-signed webhook body+hmac from Shopify for their own store.
captured_body = '{"id": 1, "note": "hello"}'
captured_hmac = "..." # valid HMAC Shopify computed using the app's api_secret_key

# Attacker resends the same body/hmac but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds because it only checks captured_body's HMAC
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...))
```
This matches the library's own unit test structure that constructs headers and HMAC independently: [6](#0-5)
