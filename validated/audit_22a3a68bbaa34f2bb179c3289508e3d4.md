### Title
Fraud Detection Is Permanently Disabled, Allowing All Fraudulent Signups To Bypass Fraud Enforcement - ([File: src/plans/mod.rs])

### Summary
### Finding Description
The reported bug class describes a security-relevant check/counter that exists structurally in the code but is never actually enforced, allowing unlimited abuse (spins never decremented despite `getAvailableSpinsOf()` existing). The direct analog in `orb-core` is the `detect_fraud` function in the `MasterPlan` signup state machine. It is invoked on every signup as part of `do_signup`, but its implementation unconditionally returns `Ok(false)` regardless of the actual biometric pipeline results, with the fraud-detection logic explicitly removed: [1](#0-0) 

This mirrors the `fraud_check.rs` module, whose `Report` struct is hardcoded to zero checks (`N_FRAUD_CHECKS: usize = 0`), so `fraud_detected()` and `fraud_detected_with_config()` can never report fraud regardless of what the pipeline observed: [2](#0-1) [3](#0-2) 

The call site in `do_signup` treats `detect_fraud`'s return value as authoritative for classifying the signup as fraudulent: [4](#0-3) 

Because `detect_fraud` always returns `false`, `fraud_detected` is always `false`, so `signup_reason` can never become `SignupReason::Fraud` through this path — it is limited to `Normal` or `Failure`. Just like the wheel-of-fortune report where `getAvailableSpinsOf()` existed but was never wired into the decrement logic, here the fraud-detection function/report structures exist and are called, but their outcome is structurally incapable of ever flagging fraud.

### Impact Explanation
Any biometric signup that should be flagged as fraudulent by the on-orb fraud-detection stage (e.g. contact lenses, face occlusion, multiple faces, underage detection — the very categories enumerated in `PipelineFailureFeedbackMessage`) will instead be reported to the backend as `SignupReason::Normal` (assuming pipeline processing succeeds), i.e. a legitimate signup: [5](#0-4) 

This allows unauthorized/misattributed enrollment and fraud/liveness bypass at the orb level: an attacker or malfunctioning capture that should be rejected by orb-side fraud checks is instead enrolled/uploaded as a normal signup, undermining the identity-binding guarantee that only a single legitimate human is enrolled per signup and increasing the chance of biometric data being stored/uploaded for a fraudulently-obtained signup.

### Likelihood Explanation
This triggers on every single signup performed by the orb, deterministically — `detect_fraud` is unconditionally called in `do_signup` and unconditionally returns `false`. No attacker action beyond attempting a signup that would otherwise be caught by fraud checks is required.

### Recommendation
Restore and wire in the fraud-detection logic in `detect_fraud` (`src/plans/mod.rs`) and populate `Report::fraud_checks()` / `N_FRAUD_CHECKS` in `src/plans/fraud_check.rs` so that pipeline-derived fraud signals are actually evaluated and can set `signup_reason = SignupReason::Fraud`, consistent with how `report_signup_reason` expects to consume that value.

### Proof of Concept
1. Run a signup where the biometric pipeline would produce fraud indicators (e.g., contact lenses, multiple faces, mask/occlusion) that map to `PipelineFailureFeedbackMessage` variants defined in `src/plans/fraud_check.rs`.
2. Observe that `do_signup` calls `self.detect_fraud(orb, debug_report, pipeline.as_ref())` at `src/plans/mod.rs:564`.
3. Inspect `detect_fraud`'s body at `src/plans/mod.rs:1390-1406`: it returns `Ok(false)` unconditionally (comment: "FOSS: WE HAVE DELETED ALL FRAUD CHECKS"), independent of `pipeline` contents.
4. As a result `fraud_detected` is always `false`, `signup_reason` is computed as `Normal` (or `Failure` only if `pipeline.is_none()`), and the enrollment proceeds through `enroll_user` with `SignupReason::Normal`, exactly as if no fraud had occurred — confirming fraud enforcement is never actually applied, matching the analog of a check/counter existing in code but never being consulted to gate the sensitive operation.
