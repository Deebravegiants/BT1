## Title
Webhook shop/topic identity not covered by HMAC signature, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook signature verification in this gem only authenticates the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which `ShopifyAPI::Webhooks::Registry.process` trusts and forwards to the app's handler as the tenant identity — are read from unauthenticated HTTP headers that are never included in the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. All the identity fields the library exposes to callers — `shop`, `topic`, `webhook_id`, `api_version` — come from `shopify_header(...)`, i.e. plain HTTP headers with no cryptographic binding: ` [2](#0-1) `.

`Registry.process` validates the HMAC against the request and then, on success, unconditionally trusts `request.topic` and `request.shop` to build the `WebhookMetadata` passed to the app's handler: ` [3](#0-2) `. `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the secret: ` [4](#0-3) `.

The identity-binding equality that should hold is:
`shop_bound_by_hmac == shop_delivered_to_handler`

In this implementation that equality does not hold — the HMAC binds only the body bytes, while the "shop" (and "topic") that the handler receives and typically uses to scope tenant data/session lookup is taken from headers outside the signature.

This is functionally the same class of bug as the reported "wrong amount stored" issue: a value that is used to make a security/business decision (`stake.amount` / here, `shop` and `topic`) is not the value that was actually verified (`stakedAmount after fee` / here, the HMAC-signed body).

By contrast, the OAuth callback's `AuthQuery` does correctly bind `shop`, `host`, `code`, `state`, and `timestamp` into the signable string: ` [5](#0-4) `. The webhook path lacks this equivalent binding.

### Impact Explanation
An unprivileged user who can install the target app on their own development/test store (a normal, unprivileged action available to anyone for a public app) can capture one legitimate webhook delivery — a valid `(raw_body, hmac)` pair for their own shop. Because the `shop-domain`/`topic`/`webhook-id` headers are not covered by the HMAC, that same `(raw_body, hmac)` pair remains valid when replayed with an arbitrary attacker-chosen `shop-domain` header. `Registry.process` will accept it (HMAC check passes) and deliver a `WebhookMetadata` claiming to be from a different, victim shop, with attacker-controlled `topic` as well. Any host application that uses the delivered `shop` value to determine which tenant's data/session to act on (the documented and expected use of `WebhookMetadata#shop`, since the gem provides no other way to identify the originating shop) can be tricked into cross-tenant data operations. This crosses a tenant boundary based on forged, unauthenticated header data, matching the High severity bar (identity/tenant-binding bypass carrying the gem's own authenticated channel).

### Likelihood Explanation
Requires only the ability to install/operate one's own instance of the app (trivial for public apps) plus basic HTTP tooling to replay a captured request with modified headers — no access to `api_secret_key`, access tokens, or privileged accounts is needed. The `Registry.process` code path only checks `Utils::HmacValidator.validate(request)`, which is body-only, so a replayed body/HMAC with forged headers passes validation as shown: ` [6](#0-5) `.

### Recommendation
Bind the identity fields (`shop`, `topic`, and ideally `webhook_id`) into the signable material used for HMAC verification, or otherwise cryptographically tie them to the verified body (e.g., include them in `to_signable_string`, or require the host app to separately corroborate `shop` against a known/authorized shop list before trusting it). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be used for tenant/session resolution without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers a webhook handler.
2. Shopify sends a legitimate webhook: body `B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's secret) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the same `B` and `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this still passes since `B`/`H` are unchanged: ` [7](#0-6) `.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` — the host app now processes attacker-supplied data under a spoofed shop identity: ` [8](#0-7) `.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
