## Title
Fixed flat-weight for `state-coprocessor::handle_unsigned` massively underestimates the cost of unbounded batched state-proof verification, enabling a weight-based block-time DoS — (File: `modules/pallets/state-coprocessor/src/lib.rs`)

### Summary
`pallet-state-coprocessor`'s `handle_unsigned` extrinsic is declared with a fixed, trivial weight of `DbWeight::get().reads_writes(1, 2)` [1](#0-0) , yet the call actually performs cryptographic membership/state-proof verification over an attacker-controlled, unbounded `requests: Vec<GetRequest>` list [2](#0-1) . This is directly analogous to the wasmvm advisory: declared/benchmarked cost diverges by orders of magnitude from actual execution cost, allowing a submitter to force execution far beyond what the runtime believes it reserved, temporarily DoSing block production.

### Finding Description
`handle_unsigned` is reachable by anyone (it's dispatched with `ensure_none(origin)` and accepted through `ValidateUnsigned::validate_unsigned`, which only checks structural/dedup validity, not proof cost) [3](#0-2) . Its declared weight is a flat `reads_writes(1, 2)` — a constant, tiny DB-I/O estimate that does not scale with the size of `message.requests` or the number of `keys` per `GetRequest` [4](#0-3) .

The actual work performed in `handle_get_requests` includes:
- `dedup_requests` over the full `requests` vector [5](#0-4) 
- one membership-proof verification (`verify_membership`) covering commitments for *all* requests in the batch [6](#0-5) 
- a `verify_state_proof` call *per request*, each covering an arbitrary number of `req.keys` [7](#0-6) 

None of these costs are bounded by any `Max*` type in the pallet's `Config`, and none feed into the extrinsic's declared weight. Substrate schedules and reserves block execution capacity based on the *declared* weight (`#[pallet::weight(...)]`), not the actual measured cost. Since the declared weight here is a near-zero constant, the block-authoring/import logic will admit many of these extrinsics (or a single one with a large `requests`/`keys` payload, up to the max extrinsic/block length) believing they cost almost nothing, while actual execution performs a multiple/batch of expensive Merkle/state-proof verifications — exactly the "operations take significantly more [gas/weight] than benchmarks indicated" pattern from the cited wasmvm advisory (CWE: Improper Restriction of Power Consumption).

### Impact Explanation
An attacker can submit `handle_unsigned` extrinsics (unsigned, permissionless, gated only by structural mempool checks) with large `requests` vectors and/or requests with many `keys`, forcing the node to perform disproportionate cryptographic proof-verification work per unit of charged/reserved weight. Because block weight accounting is based on the fixed declared weight rather than actual cost, this can cause blocks to take far longer to produce/import than the runtime's weight limit assumes, stalling block production/finality — a temporary chain-wide DoS, matching the Medium-severity classification of the analog report.

### Likelihood Explanation
High likelihood: the extrinsic is unsigned/permissionless (`ensure_none`), requires no special privilege or fee, and `validate_unsigned` only performs structural/dedup checks — it does not bound batch size or reject oversized `requests`/`keys` before admitting the transaction into the pool [8](#0-7) . Any relayer-class actor with network access can construct such a message.

### Recommendation
Replace the flat `DbWeight::get().reads_writes(1, 2)` with a properly benchmarked, size-dependent weight function (e.g., `WeightInfo::handle_unsigned(requests.len(), max_keys)`), following the pattern already used elsewhere in the codebase (e.g., `pallet_beefy_consensus_proofs`'s benchmarked `WeightInfo`) [9](#0-8) . Additionally, enforce hard bounds (`BoundedVec`) on `requests` and per-request `keys` so worst-case weight is boundable and benchmarkable, and reject batches exceeding those bounds in `validate_unsigned` before admission to the pool.

### Proof of Concept
1. Construct a `GetRequestsWithProof` with a large `requests: Vec<GetRequest>` (bounded only by max extrinsic/block length), each `GetRequest` carrying many `keys`.
2. Craft (or reuse) valid source/response proofs covering this batch (the proof structure allows arbitrarily large leaf/key sets).
3. Submit as unsigned extrinsic; `validate_unsigned` accepts it after only dedup/timestamp/height checks, without weighing proof-verification cost [8](#0-7) .
4. On execution, `handle_get_requests` runs one `verify_membership` over all requests plus `verify_state_proof` per request/key [10](#0-9) , consuming far more real CPU time than the declared `reads_writes(1, 2)` weight reserved, while the runtime believes the block still has ample remaining weight budget — repeat across a block to degrade block production time.

				return Err(TransactionValidityError::Invalid(InvalidTransaction::Call));
			};

			if let Err(err) = Self::handle_get_requests(message.clone()) {

				priority: 100,
				requires: vec![],
				provides: vec![msg_hash],
				longevity: 25,
				propagate: true,
			})
		}
