### Title
Webhook `shop` attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies only ever covers the raw request body. This breaks the equality that the framework's own security model implies: `authenticated(payload) == attributed(shop)`. Any attacker who can produce one validly-signed webhook (e.g., because they install the target app on their own shop and receive legitimate webhooks for it) can replay that same body with a forged `shop-domain` header claiming to be a different, victim shop, and the HMAC check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

Note that `to_signable_string` returns only `@raw_body` — it does not include `shop`, `topic`, `webhook_id`, or any header value. `shop` is read directly from the header with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC over the body and, on success, unconditionally forwards `request.shop` (taken straight from the header) to the app's handler as the tenant identifier, with no relation to what was signed: [3](#0-2) 

`HmacValidator.validate` confirms the signature check is only against `to_signable_string` (the body), never against the shop header: [4](#0-3) 

Since Shopify signs every webhook for an app installation with the same app-wide `client_secret` (`api_secret_key`) — not a per-shop secret — a payload+HMAC pair that is valid for Shop A's webhook is *also a valid HMAC for the exact same bytes delivered under a different claimed shop header*, because the signature is a pure function of `(body, api_secret_key)` and does not depend on `shop` at all. The library's own documentation confirms host apps are expected to trust `data.shop` directly as the per-tenant routing key without any additional validation: [5](#0-4) 

This is the "field acted on but not covered by the HMAC" pattern: the byte range that is authenticated (raw body) does not include the field (`shop`) that downstream code uses to select which tenant's data/session/queue the webhook is applied to.

### Impact Explanation
An attacker who operates (or compromises) any single shop that has the vulnerable app installed can capture one of their own legitimately-signed webhooks (same `api_secret_key` is used for every shop of the app) and resubmit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different, victim shop's domain. Because the HMAC only covers the raw body, the forged request still passes `HmacValidator.validate`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop. Downstream host applications that use `data.shop` as documented (to key session/token lookups, update tenant records, enqueue background jobs tagged by shop, etc., as shown in the gem's own webhook doc example) will process attacker-controlled data under a victim tenant's identity — a cross-tenant data-integrity/confusion vulnerability satisfying the "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the target app on their own store (a routine, low-privilege action for any Shopify merchant/developer), since no elevated credential beyond a normal shop install is required to obtain a validly-HMAC'd payload. The only additional step is replaying that payload to the app's public webhook endpoint with a modified header, which requires no secret knowledge at all.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the signed payload before trusting it (e.g., have `Request#to_signable_string` incorporate the shop/topic headers, or require the caller to compare `request.shop` against an expected shop obtained through an already-authenticated channel before invoking the handler). At minimum, the gem should document explicitly and loudly that `data.shop` is not authenticated by the HMAC and must not be used as a sole tenant key without independent verification (e.g., checking against a shop that is already known to have this webhook subscription/session).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving legitimate webhooks signed with the app's shared `client_secret`.
2. Attacker captures one such webhook: `raw_body = B`, `X-Shopify-Hmac-Sha256 = HMAC(client_secret, B)` (valid, since it was really sent by Shopify for the attacker's own shop).
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and successfully matches the received signature — the shop header played no role in this check. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and the host application processes/attributes attacker-controlled webhook data as if it came from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
