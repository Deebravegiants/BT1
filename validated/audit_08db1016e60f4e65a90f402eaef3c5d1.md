### Title
Permissionless `CallDispatcher.dispatch()` allows theft of any assets transiting the shared dispatcher via reentrant hijack - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with no caller restriction whatsoever [1](#0-0) . It is a single shared, permissionless singleton reused across `IntentGatewayV2`, `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken`, and other apps to execute arbitrary attacker/order-controlled `Call[]` batches against any contract with code [2](#0-1) . Because any address can call `dispatch()` directly at any time, and because the dispatcher transiently holds real user/solver funds while `IntentsBase._execute`/predispatch flows run (transferring assets in, invoking attacker-supplied calldata, then sweeping the remaining balance back) [3](#0-2) [4](#0-3) , this is functionally the same bug class as Laravel Pulse's unauthenticated `remember(callable)`: a publicly reachable entry point that executes attacker-influenced logic against state (fund balances) the caller was never meant to control.

### Finding Description
`CallDispatcher.dispatch()` decodes a `Call[]` and, for every entry, `extcodesize`-checks the target and then does `to.call{value: call.value}(call.data)`, reverting the whole batch on any failure [1](#0-0) . There is no `onlyGateway`/`onlyIntentGateway` modifier, no allow-list of callers, and no reentrancy guard on this function or on the interface it implements [5](#0-4) .

The dispatcher is deployed once and shared: the same `CALL_DISPATCHER` address is wired into `IntentGatewayV2` and used by `HyperFungibleTokenUpgradeable.onAccept`/`WrappedHFT` to run cross-chain calldata after mint/unlock [6](#0-5) , and by `IntentsBase._execute`/predispatch flows to run order calldata after assets are moved to it [7](#0-6) , [8](#0-7) . None of these call sites hold a lock/reentrancy guard around the window in which the dispatcher holds funds (`nonReentrant` is absent from `IntentsBase`/`IntentGatewayV2`/`CallDispatcher`).

In every one of these flows, the pattern is: (1) transfer real tokens/ETH to the dispatcher, (2) call `dispatch()` with attacker- or order-creator-controlled `Call[]` (the `to` address just needs to have code — it can be a contract the attacker fully controls), (3) only afterward sweep/verify the dispatcher's balance. Because `dispatch()` is public, the target invoked in step (2) can, in its own execution, call back into the same `CallDispatcher.dispatch()` (reentrancy) and instruct it to send out whatever balance is *currently* sitting on the dispatcher (funds belonging to that same in-flight order/message, or dust left behind from any other imperfectly swept flow) to an address of the attacker's choosing — before the legitimate step (3) sweep/verification runs. Since `dispatch()` has no notion of "whose turn it is" or "which order this call belongs to," it will happily move out any balance it currently holds for anyone who calls it, at any time, including mid-reentrancy.

This is structurally identical to the Pulse vulnerability: a public method meant to be invoked only from a trusted internal flow (Livewire component wiring vs. `IntentsBase`/`HyperFungibleToken` internal orchestration) is instead directly reachable and callable by any unprivileged actor with attacker-chosen parameters, letting them execute arbitrary logic/asset movement outside the intended access boundary.

### Impact Explanation
Any user, solver, or order creator who can get `order.output.call`, `order.predispatch.call`, or an HFT/WrappedHFT `message.data` payload to target a contract they control gets that contract invoked by the shared `CallDispatcher` while it is holding real escrowed/solver/bridged funds. From inside that invocation, the attacker can re-enter `CallDispatcher.dispatch()` (itself unauthenticated) and redirect the dispatcher's current balance to themselves before the caller's own sweep/verification logic executes, resulting in outright theft of solver output funds, escrowed order inputs, or minted/bridged tokens intended for a legitimate beneficiary. Because the dispatcher is a single shared contract used across multiple apps (`IntentGatewayV2`, HFT, WrappedHFT), any transient balance it holds for *any* in-flight cross-app operation is exposed to *any* caller, not only the party that put the funds there. This meets the "concrete theft of funds" bar.

### Likelihood Explanation
High. `dispatch()` requires zero privilege to call — it is a plain external function with no modifier. The only engineering effort required from an attacker is placing an order (or bridging a message) whose calldata targets a contract they control, which is a first-class, explicitly supported feature ("swap-then-escrow"/"fill-then-act" calldata execution) rather than an edge case, so the attacker fully controls the reentrant callback without needing to find a coincidental hook in a third-party token/DEX.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the specific app contracts that are expected to use it (e.g. an `onlyAuthorizedCaller` allow-list of `IntentGatewayV2`/HFT/WrappedHFT addresses set at construction/governance), and add a reentrancy guard so `dispatch()` cannot be re-entered while a prior `dispatch()` call from the same or another authorized caller is still executing. Additionally, each app should verify its expected post-call balance/effects using a per-call escrow/lock (e.g., transient-storage "in-use" flag) rather than trusting `balanceOf(dispatcher)` read after an untrusted external call, since that pattern is inherently vulnerable to any actor draining the dispatcher mid-flow.

### Proof of Concept
1. Attacker deploys `Evil` contract with a function `hook()` that calls `CallDispatcher(dispatcher).dispatch(abi.encode([Call({to: victimToken, value: 0, data: abi.encodeCall(IERC20.transfer, (attacker, victimToken.balanceOf(dispatcher)))})]))`.
2. Attacker places (or fills) an order whose `output.call` (or `predispatch.call`) is `abi.encode([Call({to: address(Evil), value: 0, data: abi.encodeCall(Evil.hook, ())})])`.
3. A solver fills the order, transferring real output tokens to `dispatcher`, then `IntentsBase._execute` calls `ICallDispatcher(dispatcher).dispatch(order.output.call)` [9](#0-8) .
4. This invokes `Evil.hook()`, which re-enters `CallDispatcher.dispatch()` directly (no access control stops it) and transfers out the solver's output tokens currently sitting on the dispatcher to the attacker.
5. `_execute`'s subsequent sweep loop reads `IERC20(token).balanceOf(dispatcher)` as zero/reduced [10](#0-9) , so the solver's funds are gone with no revert, completing the theft.

Note: I was unable to fully trace `evm/src/apps/IntentGatewayV2.sol`'s exact `fillOrder` line numbers before running out of tool iterations, so the precise ordering of token transfer vs. `_execute` invocation in that specific file is inferred from the equivalent, verified `tron` variant and `IntentsBase._execute`; a Devin session with full repo access should confirm the exact call ordering in `evm/src/apps/IntentGatewayV2.sol` before remediation.

        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
