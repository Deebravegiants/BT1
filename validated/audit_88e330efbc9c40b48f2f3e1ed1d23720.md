### Title
`EmporiumStack` EIP-712 signature omits `feeStructure.feeToken`, letting an unauthorized submitter drain arbitrary ERC20 balances from a signer's `HinkalWallet` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The Emporium flow lets a `HinkalWallet` owner (`stack.signerAddress`) pre-authorize a batch of operations off-chain via an EIP-712 signature. That signature, however, only commits to `(emporiumMessage, opsHash, maxFee, deadline)` — it never binds the fee **token**. The contract nonetheless uses `feeStructure.feeToken`, an unsigned field of `CircomData` chosen by whoever assembles the transaction, to pull up to `maxFee` units directly out of the signer's wallet balance. Since `Hinkal.transact` has no access control (any address can submit a valid proof), whoever builds the final `circomData`/proof for a signed `EmporiumStack` can redirect the "relay fee" extraction to any ERC20 the wallet holds, not the token the signer intended.

### Finding Description
`verifyWallet` recovers the signer from a hash that excludes the fee token entirely: [1](#0-0) 

The typehash itself confirms only `ops`, `maxFee`, `deadline`, and the emporium `message` are signed: [2](#0-1) 

Despite that, `payRelayFees` uses the unsigned `circomData.feeStructure.feeToken` to pull funds straight from the signer's wallet, including the explicit branch that fires even when `feeToken` is not one of the tokens touched by the signed operations at all: [3](#0-2) 

The actual wallet debit is unconditional once the (unprivileged) Emporium contract calls it — `HinkalWallet.doSendToRelay` performs the ERC20 transfer with no additional check that the token was part of what the signer approved: [4](#0-3) 

`Hinkal.transact` is public with no caller restriction — anyone holding a valid proof and matching `calldataHash` may submit it: [5](#0-4) 

Because `feeStructure` (including `feeToken`) is part of `calldataHash` (`getHashedCalldata2`), it is bound to whatever proof the *submitter* generates for their own `circomData` — but that only proves internal self-consistency of the submitted calldata, not that the wallet-owner's EIP-712 signature (a separate, narrower authorization) approved that specific token: [6](#0-5) 

Thus a party that possesses a valid off-chain `(v, r, s)` signature for a set of ops/maxFee/deadline (obtained through the normal user flow, e.g. a compromised or malicious front-end/aggregator that collects the signature before finishing the transaction) can build a `CircomData` payload that reuses that signature verbatim while substituting an arbitrary `feeStructure.feeToken` — any ERC20 the wallet holds — and set `flatFee` up to the signed `maxFee` number. `verifyWallet` will accept it because the signature check never inspects `feeToken`.

### Impact Explanation
This breaks the "wallet op authorized by the prover or signer" invariant: `HinkalWallet.doSendToRelay` moves real (non-shielded) ERC20 balance out of the user's wallet to an attacker-chosen `circomData.relay` address, in a token the signer never approved for spending as a fee. This is theft of protocol/relay-fee-labeled funds from the wallet, bounded per transaction by the numeric value of `maxFee` but unbounded in which token it applies to — allowing extraction of a high-value token (e.g., WBTC) using a `maxFee` figure the user only intended to apply to a low-value/stable token. Repeated across multiple legitimately-signed `EmporiumStack` messages, this can drain a meaningful portion of the wallet's held assets.

### Likelihood Explanation
Requires only an unprivileged intermediary (front-end, aggregator/relay-as-a-service, or any actor that receives the user's raw EIP-712 signature before final on-chain submission) to assemble the final `circomData`/proof — it does not require compromising the wallet owner's key, nor any admin/owner/relay-registry privilege, since `Hinkal.transact` itself is callable by any address. The only constraint is obtaining the already-signed `(v, r, s)` blob, which is inherent to how the signature is meant to be handed off for relayed submission.

### Recommendation
Include `feeStructure.feeToken` (and ideally the full `feeStructure`) in the `EMPORIUM_SIGNATURE_TYPEHASH` payload that `stack.signerAddress` signs, so the signer explicitly authorizes which token can be pulled as a fee, in addition to the numeric cap already enforced by `maxFee`.

### Proof of Concept
1. User signs an `EmporiumStack` for a swap on tokenA with `maxFee = 1000` intending 1000 units of tokenA (a stable, low-decimal token) as the fee cap.
2. Signature only commits to `(message, opsHash(tokenA ops), maxFee=1000, deadline)` — see `_hashEmporiumOps`/`EMPORIUM_SIGNATURE_TYPEHASH`.
3. An untrusted party assembling the final `circomData` sets `feeStructure = {feeToken: WBTC, flatFee: 1000, variableRate: 0}` and a valid `deltaAmountChanges` set so `foundToken` stays false, triggering the unconditional branch in `payRelayFees` (lines 247-259) that calls `sendToRelayFromWallet` regardless of whether WBTC was part of the signed ops.
4. `verifyWallet` passes because `flatFee (1000) <= stack.maxFee (1000)`, and the signature recovers correctly since `feeToken` was never part of the signed hash.
5. `HinkalWallet.doSendToRelay` transfers 1000 units of WBTC (a far larger value than the user intended) from the wallet to `circomData.relay`, an address the attacker/submitter controls.
