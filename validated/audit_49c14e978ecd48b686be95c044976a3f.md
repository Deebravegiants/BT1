### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only that the *raw request body* is HMAC-authentic; the `shop` (and `topic`/`webhook_id`) values that identify which tenant the webhook belongs to are read from unauthenticated HTTP headers and are never cryptographically bound to the signature. This mirrors the report's root cause exactly: an operation is invariant-checked/authenticated on one representation of the data (the raw body) while a different, unauthenticated field (the shop header) is what actually gets acted upon downstream, breaking the intended 1:1 binding between "authenticated sender" and "tenant identity."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are pulled straight from HTTP headers with no cryptographic linkage to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` as the tenant identity handed to the application's handler: [3](#0-2) 

Because the HMAC secret (`api_secret_key`) is a single per-app secret shared across every shop that installs the app — not a per-shop secret — any merchant who installs the app on their own store receives genuinely-signed webhook deliveries. Since the signature covers only the body, that merchant can replay the same signed body while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `Utils::HmacValidator.validate` will pass (the body byte-string it signs is unchanged), and `Registry.process` will invoke the registered handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim tenant, even though the signed bytes were never associated with that tenant.

This is the same class of bug as the report: the equality that should hold — "the shop the signature authenticates" == "the shop the code acts on" — is broken because one side (the header-derived shop) is never covered by the authentication primitive (the HMAC), just as the report's second fee-on-transfer conversion silently diverges from the invariant the first conversion established.

### Impact Explanation
An application built on this gem that uses `WebhookMetadata#shop` to scope any per-tenant side effect (writing to a shop record, triggering GraphQL calls with a session looked up by `shop`, updating billing/subscription state, etc.) can be made to act on a shop it did not actually receive the event for. This is a cross-tenant confusion primitive: attacker-controlled but genuinely-signed traffic can be redirected to a different tenant's identity purely by changing an unauthenticated header, which the gem does nothing to prevent or even flag.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on their own Shopify store (an unprivileged, self-service action) to obtain one legitimate, HMAC-signed webhook body, and the ability to send arbitrary HTTP requests with modified headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Do not treat header-derived `shop` (or `topic`/`webhook_id`) as trustworthy tenant identity on its own. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated, and/or have `Registry.process` cross-check the header shop against the shop implied by the resource IDs in the parsed body, or against a per-webhook-subscription registry keyed by `webhook_id` obtained from Shopify's Admin API, before invoking the handler.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a body `B` with a valid `X-Shopify-Hmac-Sha256` signature `H` computed over `B` using the app's shared `api_secret_key`.
2. Replay the exact same request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` (`lib/shopify_api/webhooks/request.rb` `to_signable_string`), and `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), even though the signed body never legitimately corresponded to that shop.
