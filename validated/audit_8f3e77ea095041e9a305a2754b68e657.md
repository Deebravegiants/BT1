### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw body only, while the `shop`, `topic`, and `webhook_id` values that `Registry.process` trusts and forwards to the host app's handler are read straight from unauthenticated HTTP headers. Because the `api_secret_key` used to compute the webhook HMAC is a single app-level secret shared across *every* shop that installs the app, any merchant who legitimately receives a signed webhook for their own store can replay that exact body/HMAC pair while substituting a different `shop-domain` header, and the signature will still validate.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` decodes the `hmac-sha256` header — neither includes `shop`, `topic`, or `webhook_id`: [1](#0-0) 

`shop` is parsed independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then blindly trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed into the host application's handler: [3](#0-2) 

The equality this breaks is: **shop cryptographically proven by the HMAC** (in reality, "some shop installed under this `api_secret_key`") **≠ shop asserted in the unauthenticated header and handed to the app as the acting tenant**. Because `Context.api_secret_key` is one value for the entire app (not per-shop, as confirmed in `HmacValidator.validate` / `JwtPayload`, which use the same singular `Context.api_secret_key` for all tenants): [4](#0-3) 

a valid `(body, hmac)` pair generated for shop A's webhook remains valid for any other `shop-domain` value an attacker chooses to attach, since the header is never covered by the signature.

### Impact Explanation
This is a cross-tenant confusion: a low-privilege actor who is simply a merchant/user of a multi-tenant app (no special access, no leaked `api_secret_key`, no token) can capture one of their own legitimately delivered webhooks (body + valid HMAC, both readily observable from their own store's traffic) and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop. `Registry.process` will accept it as authentic (HMAC check passes because it only checks the body) and dispatch it to the app's handler labeled with the victim's shop, causing the host application to act on/against the wrong tenant's data — satisfying the "cross-tenant access" Critical impact category, since the gem itself supplies no mechanism binding the asserted shop identity to the verified bytes.

### Likelihood Explanation
Any merchant using a shared multi-tenant Shopify app receives real webhooks with valid signatures for their own shop, so obtaining a valid `(body, hmac)` pair requires no special access — this is normal usage, not credential theft or TLS interception. The only additional step is re-issuing that captured POST with one header value swapped, which is trivial for anyone who can reach the app's public webhook endpoint.

### Recommendation
Bind shop identity into what's actually verified: either (a) require the webhook body itself to carry the shop identifier and validate it against the header inside `Webhooks::Request`, rejecting mismatches, or (b) extend `VerifiableQuery`/`to_signable_string` for webhooks to incorporate `shop`, `topic`, and `webhook_id` into the signed material (mirroring how `Oauth::AuthQuery#to_signable_string` already includes `shop` in its signable string), so a valid signature can only be produced/replayed for the specific shop and topic it was issued for. At minimum, document and enforce that `Registry.process` callers must independently confirm `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting the value.

### Proof of Concept
1. App `X` is installed by shop `attacker.myshopify.com` and shop `victim.myshopify.com`; both share the same `Context.api_secret_key` for app `X`.
2. Attacker's own store triggers a webhook (e.g. `orders/create`) delivered to the app with headers:
   `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `B`.
3. Attacker intercepts/logs this request from their own infrastructure (fully within their rights as the receiving endpoint owner, or via a debugging proxy on their own server) and replays it to the app's webhook endpoint, changing only the header:
   `x-shopify-shop-domain: victim.myshopify.com`, keeping body `B` and `x-shopify-hmac-sha256` identical.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which only recomputes HMAC over `@raw_body` and matches — passes.
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: B.parsed, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and the host application processes attacker-controlled order data attributed to the victim shop.
