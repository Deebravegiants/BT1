### Title
Missing gas/compute accounting in `resolve_promise_yield_timeouts` allows unmetered per-chunk work bounded only by proof-size, not compute budget - (File: `runtime/runtime/src/lib.rs`)

### Summary
`resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) walks the `PromiseYieldTimeout` queue and performs trie reads, receipt construction, and `forward_or_buffer_receipt` calls for every expired entry, but unlike every other receipt-processing stage in `process_receipts`, it never calls `total.add(gas, compute)` for the work it does. The loop's only exit conditions are `total.compute >= compute_limit` (using compute accumulated by *earlier* stages, not incremented here) and `state_update.trie.check_proof_size_limit_exceed()`, so the per-entry work in this function is effectively free from the chunk's gas/compute budget.

### Finding Description
`process_receipts` (`runtime/runtime/src/lib.rs:2681-2737`) runs local, delayed, and incoming receipts first, each of which routes execution through `process_receipt_with_metrics` → `total.add(gas_burnt, compute_usage)` (`lib.rs:2359-2371`), correctly charging `processing_state.total.compute` for real work performed. `resolve_promise_yield_timeouts` is called last (`lib.rs:2718-2719`) with the same `compute_limit`, but inside its `while` loop (`lib.rs:3025-3104`) it only checks `total.compute >= compute_limit` — it never calls `total.add(...)` for the trie reads (`get::<PromiseYieldTimeout>`, `contains_key`, optional `get_pure`), receipt construction, or the `receipt_sink.forward_or_buffer_receipt` congestion/buffer bookkeeping it performs per entry.

Because `promise_yield_create` costs no congestion gas (`compute_receipt_congestion_gas`, `runtime/runtime/src/congestion_control.rs:696-703`, "The congestion control MVP does not account for yielding a promise"), and because `yield_create_*` fees only cover the *creation* transaction's own gas budget (not the eventual timeout-resolution work), the resolution work performed later, in a different chunk, is not charged to anyone: it doesn't consume `total.compute` at all, so it cannot even trigger the compute_limit exit condition. The loop only stops once either all due entries are drained or `state_update.trie.check_proof_size_limit_exceed()` trips — a storage-proof-size safety net, not the intended gas/compute budget.

If `total.compute` at the time `resolve_promise_yield_timeouts` runs is well below `compute_limit` (e.g., a chunk with light prior receipt traffic), the function will drain the *entire* backlog of currently-expiring `PromiseYieldTimeout` entries in one pass with zero contribution to `total.compute`, so the chunk's actual completion time is not reflected in (and not bounded by) the gas-derived compute budget that the rest of the runtime relies on as its processing-cost proxy.

### Impact Explanation
This is a gas/compute metering completeness gap (unmetered/underpriced execution), matching NEAR's "gas or storage metering bypass" / "unbounded resource use" bounty class. The immediate effect is degraded chunk-apply throughput for a shard: unaccounted trie reads and buffer/congestion bookkeeping performed by `resolve_promise_yield_timeouts` add real wall-clock cost that is not reflected in `total.compute`, so the fixed gas envelope no longer accurately bounds a chunk's processing time. This can starve or delay processing of other receipts (local/delayed/incoming) on that shard for later chunks, since the timeout resolution runs unmetered on top of already-approved work.

However, the amplification is limited: the number of `PromiseYieldTimeout` entries expiring at any single `block_height` is exactly the number of yields created at `block_height - yield_timeout_length_in_blocks`, and yield creation itself does cost real gas via `yield_create_base`/`yield_create_byte`/`pay_gas_for_new_receipt`/`function_call_base` fees (`runtime/near-vm-runner/src/logic/logic.rs:3660-3718`), so the total batch size is bounded by that single origin chunk's gas limit divided by the minimal per-yield creation cost — not by literally unbounded queue growth across many chunks as the question's framing (per-chunk queue growing "unbounded until timeout") implies. The real defect is narrower than described: it is a missing-charge/metering-completeness bug for the resolution step, not an unbounded-queue-growth bug, since new yield creation is otherwise gas-limited per chunk like any other receipt.

### Likelihood Explanation
Feasible and repeatable by any unprivileged account: deploy a contract, call `promise_yield_create` (or `promise_yield_create_with_id`) many times within a single chunk up to that chunk's gas limit, using minimal `gas`/`gas_weight` and small `method_name`/`arguments` to maximize the count of yields per unit of gas. All those yields expire simultaneously `yield_timeout_length_in_blocks` later, and if the future chunk in which they resolve happens to have low compute usage from other traffic, `resolve_promise_yield_timeouts` will process the whole batch with zero gas/compute charged, until the trie proof-size limit (not the compute budget) eventually halts it. No special privileges, protocol-version gating bypass, or race conditions are required.

### Recommendation
Charge `total.add(gas, compute)` inside `resolve_promise_yield_timeouts` for the trie reads and `forward_or_buffer_receipt` work performed per queue entry (e.g., a fixed per-entry compute/gas cost similar to how other zero-congestion-gas receipt kinds are still charged real execution compute elsewhere), so the loop's `total.compute >= compute_limit` check can actually bound the amount of work done per chunk, independent of the storage-proof-size safety net.

### Proof of Concept
Integration test plan (extending `test-loop-tests/src/tests/yield_timeouts.rs`):
1. Deploy a test contract that calls `promise_yield_create` in a tight loop with minimal `gas`/`gas_weight`/empty-ish arguments, from many transactions in the same chunk, to create N ≈ `chunk_gas_limit / min_yield_create_cost` outstanding yields, all created in the same block height H.
2. Advance the chain to block height `H + yield_timeout_length_in_blocks`, ensuring no other significant receipts are queued for that chunk (so `total.compute` entering `resolve_promise_yield_timeouts` is near zero).
3. Instrument/measure: assert that `ApplyResult.metrics`/`ApplyMetrics::yield_timeouts_done` reports `total.compute` unchanged (or negligibly changed) despite N entries processed, and measure wall-clock apply time for that chunk versus a baseline chunk with equivalent N synthetic local receipts that do consume `total.compute` proportionally.
4. Assert (currently failing) that `total.compute` recorded after `resolve_promise_yield_timeouts` is `>= f(N)` for some non-trivial per-entry cost `f`, i.e., that the compute-limit mechanism — not the proof-size limit — is what bounds the number of timeouts resolved per chunk.
