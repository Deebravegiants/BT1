Audit Report

## Title
CORS wildcard origin matching in gateway UserServer lacks subdomain boundary check, allowing untrusted origins - (File: core/services/gateway/network/httpserver.go)

## Summary
The `isAllowedOrigin` function in the Chainlink Gateway's HTTP server implements wildcard CORS origin matching (`*.domain.com`) using a plain `strings.HasSuffix(originHost, allowedHost)` check with no dot-boundary enforcement. This allows an attacker-registered domain that merely ends with the same character sequence as the trusted suffix (e.g. `evilethereum.org` vs. allowed `*.ethereum.org`) to be treated as an allowed CORS origin.

## Finding Description
The vulnerable logic is confirmed verbatim in the repository: [1](#0-0) 
When an allowed origin entry starts with `*.`, the code strips the prefix and checks only that `originHost` ends with the remaining string — it does not verify that the preceding character is a `.` or that `originHost` equals `allowedHost`. This is invoked directly from the CORS-handling path in `handleRequest`: [2](#0-1) 
`handleRequest` is the handler wired into the mux for the configured request `Path` (the Gateway's user-facing endpoint), reachable by any unauthenticated/unprivileged client that can send an HTTP request with an `Origin` header — no credential or role is required to trigger this code path: [3](#0-2) 
The wildcard feature is a documented, first-class, operator-configurable option (`CORSAllowedOrigins`), and its intended semantics (matching genuine subdomains) are explicitly tested, but the existing test suite only exercises correctly-formed subdomains and does not cover the suffix-collision case, so the flaw is not caught by existing tests: [4](#0-3) 

## Impact Explanation
If a Gateway operator configures `CORSAllowedOrigins` with a wildcard entry such as `https://*.ethereum.org` intending to trust only genuine subdomains, the flawed suffix check also matches unrelated, attacker-controlled domains like `evilethereum.org`. Because the server reflects `Access-Control-Allow-Origin: <origin>` for any origin passing `isAllowedOrigin`, and also exposes JWT-based `Authorization` header handling on the same endpoint, a malicious page hosted on such an attacker-registered domain can issue cross-origin requests to the Gateway's user API and read the JSON responses in the browser — a concrete cross-origin allowlist bypass / cross-user response exposure against the Gateway API, consistent with the "allowlist bypass" and "gateway request impersonation / cross-user response corruption" impact classes.

## Likelihood Explanation
Exploitation only requires (1) an operator to enable the documented wildcard CORS feature (not a misconfiguration outside intended use — it's a supported config option) and (2) an attacker to register or control any domain that lexically ends with the trusted suffix (e.g., `evilethereum.org`, `notethereum.org`), which is inexpensive and requires no special access to the Gateway itself. The victim is simply an unprivileged browser client visiting the attacker's page while it makes requests to the Gateway; no operator or admin access is needed for the exploit trigger itself.

## Recommendation
Enforce a proper subdomain boundary in the wildcard match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This preserves matching of genuine subdomains (`foo.ethereum.org`) while rejecting suffix-only collisions (`evilethereum.org`).

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`, per `httpserver_test.go`'s `startNewServer` pattern.
2. Send a `POST` request to the server's configured `Path` with header `Origin: https://evilethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` (since `strings.HasSuffix("evilethereum.org", "ethereum.org")` is `true`), and the response includes `Access-Control-Allow-Origin: https://evilethereum.org`.
4. Add a Go test (mirroring `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`) asserting that origin `https://evilethereum.org` is currently (incorrectly) accepted, demonstrating the boundary bypass.
