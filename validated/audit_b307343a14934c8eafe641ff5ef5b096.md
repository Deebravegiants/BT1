## Title
`IntentGatewayV2.withdraw` on Tron transfers escrowed tokens before decrementing escrow state, violating CEI - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` implements escrow release in `withdraw()`, called from `onAccept` (RedeemEscrow/RefundEscrow) and `onGetResponse`. Unlike the canonical EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol`, which decrements `_orders[commitment][token]` *before* performing the external transfer, the Tron `withdraw()` performs the external token/native transfer first and only decrements `_orders[commitment][token]` afterward — the exact anti-pattern described in the external report (transfer before state update, i.e., not following CEI).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` iterates over the tokens in a `WithdrawalRequest` and, for each token, performs a low-level `.call` (either a native ETH send or an ERC-20 `transfer` low-level call) and only *after* that external interaction subtracts the amount from `_orders[body.commitment][token]`: [1](#0-0) 

This is a direct Checks-Effects-Interactions violation: the escrow ledger (`_orders`) is only updated *after* the external call returns. Compare with the source-of-truth EVM implementation in `IntentsBase.sol`, which decrements escrow state *before* transferring: [2](#0-1) 

Additionally, no `nonReentrant`/`ReentrancyGuard` protection exists anywhere in the Tron contract file, confirmed by an empty search for those terms across `evm/tron/contracts/**`, whereas the canonical `evm/src/apps/IntentGatewayV2.sol` does use `nonReentrant` in 9 places. Because the Tron contract both (a) leaves state mutation until after the external interaction and (b) has no reentrancy guard on any of its public entry points (`placeOrder`, `fillOrder`, `cancelOrder`, `onAccept`, `onGetResponse`), a beneficiary address controlled by an attacker (either a malicious ERC-20 token contract with a callback, or a Tron/EVM-style contract receiving native value with a fallback) can reenter the gateway during the transfer inside `withdraw()` while `_orders[commitment][token]` (and the transaction-fee balance) still reflects the pre-withdrawal amount.

### Impact Explanation
If reentrancy into a path that re-triggers `withdraw()` (or reads `_orders` to authorize a further withdrawal) is reachable before `_orders[commitment][token]` is decremented, an attacker-controlled beneficiary can drain more of the escrowed input/output tokens and the accumulated `TRANSACTION_FEES` balance than they are entitled to, directly resulting in theft of user/solver escrowed funds — a concrete "theft of funds" outcome for a token-bridging/intents contract in scope.

### Likelihood Explanation
Reachability depends on whether the host's `onAccept`/`onGetResponse` dispatch path can be re-entered before the first call completes (i.e., whether `IsmpHost`'s message-handling call stack is itself reentrancy-guarded) and whether a malicious token/beneficiary address can be placed into a `WithdrawalRequest.beneficiary`/token list. The order's `output.beneficiary`/escrow beneficiary is attacker-influenced when the attacker controls the order or is the filler, and the token loop already supports arbitrary ERC-20 addresses (which can be a malicious token contract that reenters on `transfer`). Given the absence of any `nonReentrant` guard in this file (unlike the audited canonical implementation, which explicitly guards these same functions), the missing check-effects-interactions ordering is a real, exploitable weakness rather than a purely theoretical one.

### Recommendation
Follow CEI: in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, move `_orders[body.commitment][token] -= amount;` (and the `delete _orders[body.commitment][TRANSACTION_FEES];`) to occur *before* the native/ERC-20 transfer calls, mirroring the ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, add a reentrancy guard (`nonReentrant`) consistent with the canonical `evm/src/apps/IntentGatewayV2.sol` to all state-mutating external entry points in the Tron contract.

### Proof of Concept
1. Attacker places (or fills) an order whose escrow token is a malicious ERC-20 contract that, inside its `transfer` function, calls back into a path that reads/consumes `_orders[commitment][token]` (or triggers another `withdraw` for the same commitment) — or uses `address(0)`/native value with a beneficiary contract whose `receive()`/fallback reenters.
2. When Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` post request (or a GET response for cancellation) and `onAccept`/`onGetResponse` invokes `withdraw()`: [3](#0-2) 
   the external `.call` triggers the attacker's reentrant logic while `_orders[commitment][token]` still holds the pre-withdrawal balance (line 710 hasn't executed yet).
3. The reentrant call, if it can reach `withdraw` again (directly, or via a second `onAccept` delivered by a compromised/reentrant host call stack) for the same commitment, would pass the `_orders[body.commitment][token] == 0` check (line 700) again since the decrement has not yet occurred, and receive a second unauthorized payout before the first call's decrement finally executes.

Note: full confirmation that the host's message-handling call stack allows reentrant `onAccept` calls (rather than being itself guarded) was not verified within available context — the host/dispatcher's own reentrancy protections were not located in the indexed portion of the repo. The CEI-ordering flaw itself, however, is confirmed directly from the code cited above and is a clear deviation from the safer pattern used in the canonical EVM contract.
