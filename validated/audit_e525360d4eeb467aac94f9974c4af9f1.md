### Title
Attacker can pre-approve themselves on the shared `CallDispatcher` and later drain any token stranded there by a legitimate order's calldata - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`IntentGatewayV2` routes every order's `predispatch.call` (in `placeOrder`) and `output.call` (in `_execute`, used by both same-chain and cross-chain fills) through a single, shared `CallDispatcher` instance held in `_params.dispatcher`. `CallDispatcher.dispatch()` executes fully attacker-controlled `Call[]` arrays against arbitrary targets with no allow-list. This mirrors the Locke `arbitraryCall()` bug class: a low-cost, unprivileged call can pre-set an ERC-20 allowance from the shared contract to an attacker-chosen spender *before* the contract ever holds a real balance of that token, and a later, unrelated deposit into the same shared contract is then stealable through the standing approval.

### Finding Description
`CallDispatcher.dispatch()` places no restriction on `to` or `data` beyond `to` being a contract: [1](#0-0) 

In `IntentGatewayV2.placeOrder`, the predispatch branch only requires `predispatch.call.length > 0 && predispatch.assets.length > 0`; the `Call[]` in `predispatch.call` is independent of which assets were actually transferred, so an attacker can satisfy the length check with a trivial (e.g., 1-wei) asset while embedding an `approve(attacker, type(uint256).max)` call against any arbitrary token `X`, executed with the dispatcher as `msg.sender`: [2](#0-1) 

The same shared dispatcher is used again at fill time via `_execute`, which dispatches `order.output.call` (again fully attacker/solver controlled) and afterwards sweeps back **only the tokens explicitly listed in `order.output.assets`**: [3](#0-2) 

The predispatch sweep in `placeOrder` has the same limitation — it sweeps only the tokens listed in `order.inputs`: [4](#0-3) 

Because `predispatch.call`/`output.call` are meant to support arbitrary DeFi composition ("unwrapping LP tokens," multi-hop swaps, etc.), a legitimate order's calldata can produce a byproduct token that is not part of the order's declared `inputs`/`output.assets` list (e.g., burning an LP token yields two underlying assets but the order only lists one as an input, or a swap route leaves an intermediate-hop token as dust). That byproduct is never included in the sweep loop and is left stranded as a persistent ERC-20 balance owned by the `CallDispatcher` contract, indefinitely, across transactions.

Combined, these two facts reproduce the Locke bug class exactly: (1) an attacker can cheaply pre-approve themselves for unlimited allowance from the shared contract on any token, before that contract ever holds a real balance of it, and (2) a later, unrelated legitimate transaction can leave a real balance of that exact token on the same shared contract. The attacker then calls `token.transferFrom(dispatcher, attacker, balance)` directly on the ERC-20, bypassing `IntentGatewayV2` entirely, to steal the stranded funds — no interaction with `IntentGatewayV2`'s escrow accounting (`_orders` mapping) is required or checked.

### Impact Explanation
This is a direct theft-of-funds vector against the `CallDispatcher`, a contract shared across every `placeOrder`/`fillOrder` call on the Intent Gateway. Any token balance that ever becomes stranded there (a realistic occurrence given the composable, arbitrary-calldata nature of predispatch/output execution) is permanently exposed to any attacker who front-positioned an approval — at essentially zero cost, since the approval-setting order can use a dust-value predispatch asset to pass the length check. Unlike ordinary escrow theft, this does not require compromising the solver-selection, settlement, or ISMP delivery logic at all; it only requires an unprivileged `placeOrder` call.

### Likelihood Explanation
The prerequisite (attacker pre-approving themselves on the shared dispatcher) is trivially and cheaply reachable by any unprivileged user in a single `placeOrder` transaction, with no special conditions. The second prerequisite (a legitimate order stranding a byproduct token on the dispatcher) depends on real usage of composable predispatch/output calldata (LP unwrapping, multi-hop swaps), which the protocol's own documentation explicitly promotes as a supported use case. Given that many orders over time will exercise this composable path, and that the sweep logic only accounts for tokens explicitly declared in the order, some stranded balance is a plausible, likely-to-eventually-occur outcome, at which point the pre-positioned attacker can drain it immediately and non-atomically (a separate `transferFrom` call, not requiring reentrancy or tight transaction bundling).

### Recommendation
1. Do not allow a persistent standing `CallDispatcher` to accumulate any residual ERC-20 balance across transactions: after every `dispatch()` invoked from `placeOrder`/`_execute`, sweep the *full* balance of every token touched by the arbitrary calldata (not just the tokens declared in `inputs`/`output.assets`), or restrict `Call[]` targets/selectors so `approve`-style state changes cannot be issued to arbitrary spender addresses.
2. Alternatively, deploy a fresh, single-use `CallDispatcher` (e.g., via `CREATE2`/minimal proxy) per order/fill instead of a single shared, long-lived instance, so no allowance or balance can ever outlive one order's execution.
3. As defense in depth, revoke any allowances the dispatcher may have granted during a call (e.g., `approve(spender, 0)` after the composed call) as part of the same `dispatch()` transaction, and verify no non-zero token balances remain on the dispatcher for any ERC-20 it interacted with before returning control to `IntentGatewayV2`.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with:
   - `predispatch.assets = [{token: cheapToken, amount: 1}]` (satisfies the `length > 0` / `amount != 0` checks cheaply).
   - `predispatch.call` encoding a `Call[]` with a single entry: `{to: X, value: 0, data: approve(attacker, type(uint256).max)}`, where `X` is any ERC-20 the attacker wants to target.
   - This is dispatched via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` at [5](#0-4) , with `msg.sender` on `X` being the shared `dispatcher`, so `X.allowance(dispatcher, attacker) = type(uint256).max` is now permanently set.
2. At some later time, any user places or fills an order whose `predispatch.call`/`output.call` performs a composed DeFi operation (e.g., unwrapping an LP token or routing a multi-hop swap) that, as a byproduct, leaves a nonzero balance of `X` on the dispatcher that is not part of that order's `inputs`/`output.assets` list, so it is skipped by the sweep loops at [6](#0-5)  and [7](#0-6) .
3. Attacker calls `X.transferFrom(dispatcher, attacker, X.balanceOf(dispatcher))` directly on the ERC-20 contract, draining the stranded tokens using the allowance set in step 1 — with no involvement of `IntentGatewayV2`'s access control or escrow accounting.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
