### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Shop Spoofing in `Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value it hands to the app's registered handler is read from an HTTP header that is never included in the HMAC-signed content. This breaks the identity binding `hmac-verified bytes == bytes the app trusts as the tenant identity`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which only checks `request.to_signable_string`, i.e. the body, against `request.hmac`), and then immediately forwards the header-derived, unverified `request.shop` to the app's handler as the authoritative tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body only for webhooks) and compares it to the supplied `hmac`: [4](#0-3) 

Because the HMAC only binds the request body, an attacker who possesses one legitimately-signed webhook (e.g. a webhook delivered by Shopify to their own store, where they are a legitimate merchant who installed the app) can replay that exact body/HMAC pair while substituting an arbitrary value in the `shop-domain` header. The gem will still report `Utils::HmacValidator.validate(request) == true` (since the body and secret are unchanged), yet `request.shop` — and therefore `WebhookMetadata#shop` passed to the app's handler — can be set to any victim shop domain the attacker chooses. The equality the code implicitly assumes, `hmac_verified_bytes == identity_bytes_trusted_by_handler`, does not hold: the HMAC verifies `raw_body`, but the identity acted upon (`shop`) comes from unauthenticated header bytes.

### Impact Explanation
This is a cross-tenant identity-binding failure: the shop identity that host applications rely on (to route data, scope database writes, or bypass idempotency/ownership checks in per-shop webhook handlers) is attacker-controllable independent of the cryptographic verification the gem performs. An application built on this gem that trusts `WebhookMetadata#shop` for tenant scoping (a documented, intended use per `docs/usage/webhooks.md`) can be tricked into attributing another merchant's data/events to an attacker-chosen shop, or vice versa — a cross-tenant access primitive achieved without possessing any merchant's access token or the app's `client_secret`.

### Likelihood Explanation
Requires the attacker to have legitimately received at least one webhook with a valid HMAC (trivial — install the target app on a shop they control, or observe delivery to any endpoint they own) and then replay the identical body with a forged `shop-domain` header value to the app's public webhook endpoint. No secret material, TLS interception, or privileged account is needed.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers into the HMAC-signed material, or otherwise cryptographically verify the header-sourced `shop` value before it's surfaced to handlers — e.g., extend `Request#to_signable_string` to include the normalized headers concatenated with the raw body, and have `HmacValidator` validate against that combined value instead of body-only content.

### Proof of Concept
1. Attacker installs the target Shopify app on a shop they control (`attacker-shop.myshopify.com`) and captures a real webhook delivery, e.g. `orders/create`, with body `B` and valid header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's real `client_secret` over `B`).
2. Attacker sends a request to the app's webhook endpoint with the same raw body `B` and the same `hmac-sha256` header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`B`) and matches `H` — validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload/HMAC actually originated from the attacker's own shop, demonstrating the broken binding between the HMAC-verified content and the shop identity trusted by the application.
