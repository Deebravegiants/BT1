### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by the HMAC signature, allowing tenant spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook HMAC against the raw body only, but the `shop`, `topic`, and `webhook_id` values that the host application relies on for tenant/topic identification are taken from unauthenticated HTTP headers that are never part of the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers, with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — i.e., it recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac-sha256` header — before dispatching to the app's handler using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

This is the exact bug class from the report: a field that is *acted on* (`shop`, used by the host app to route data into per-tenant storage) is not covered by the value that is cryptographically *verified* (the raw body HMAC, computed with the app's shared `client_secret`/`api_secret_key`). Compare with the OAuth `AuthQuery`, where `shop` **is** included in `to_signable_string` and therefore is bound by the HMAC: [4](#0-3) 

Because the webhook signing secret is the app's single `client_secret` shared across every shop that installs the app (not a per-shop secret), an attacker who operates their own store and installs the app receives legitimately-signed webhook deliveries (`raw_body` + valid `hmac-sha256`) from Shopify for their own store. Since the `shop-domain`, `topic`, and `webhook-id` headers are not part of the signed bytes, the attacker can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) for a victim shop. `HmacValidator.validate` will still succeed because it only checks the body against the secret: [5](#0-4) 

The handler then receives data tagged with the spoofed `shop`, `topic`, and `webhook_id`, letting the attacker inject data (or trigger topic-specific business logic) attributed to a tenant they do not control.

### Impact Explanation
This breaks the identity binding `shop (verified by HMAC) == shop (used by handler)`, allowing cross-tenant data injection/confusion in any application built on `ShopifyAPI::Webhooks::Registry`: an unprivileged user who can install the app in their own shop (or otherwise obtain one valid signed webhook payload) can make the host app process/store data under an arbitrary victim shop id, and can also relabel the `topic` to trigger different handler logic than what was actually signed. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to obtain at least one legitimately-signed `(body, hmac)` pair for the target app — trivially achievable by installing a public app in an attacker-controlled store and capturing the resulting webhook delivery — then replaying it to the app's publicly reachable webhook endpoint with modified `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers. No access token, `api_secret_key`, or privileged account is needed. Exploitability further depends on how the downstream host application uses `WebhookMetadata#shop`/`#topic` (e.g., to key per-tenant records), which is outside this gem but is the gem's documented contract for host apps.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (all Shopify-supplied identifying headers) in the signed content verified by `Utils::HmacValidator`, or otherwise cryptographically bind them to the HMAC (e.g., by validating them against a signature scheme that covers headers, similar to how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop`). At minimum, document that host applications must not trust `WebhookMetadata#shop`/`#topic` beyond what Shopify's delivery mechanism provides, and warn that these values are not covered by HMAC verification in this gem.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker-shop.myshopify.com`; the app registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the app: body `B`, headers include `x-shopify-hmac-sha256: H` (valid, signed with the app's shared `client_secret`), `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker captures `(B, H)` and replays a new HTTP POST to the same webhook endpoint with the same body `B` and `hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H`, so validation succeeds: [6](#0-5) 
5. The handler executes with `shop: "victim-shop.myshopify.com"`, even though that shop never sent or authorized this webhook, demonstrating the cross-tenant identity break.
