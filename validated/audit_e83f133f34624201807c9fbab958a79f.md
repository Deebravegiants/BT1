### Title
Webhook `shop` domain used for tenant identification is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor (read from the `X-Shopify-Shop-Domain` header) that the webhook registry hands to app-provided handlers as the tenant identifier for the incoming event, but the HMAC signature computed by `HmacValidator` only covers the raw request body. Any party who can obtain one valid `(body, HMAC)` pair for their own shop can replay it with a different `Shop-Domain` header and have it accepted as authentic for an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the received `hmac` using `OpenSSL.secure_compare`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw JSON body — none of the Shopify headers, including the shop domain, are part of the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates only that HMAC-over-body check, then forwards `request.shop` unmodified into `WebhookMetadata`, which is the value the app's handler is expected to trust as the tenant the event belongs to: [4](#0-3) 

The identity binding the HMAC is supposed to guarantee is: `shop domain trusted by handler == shop domain authenticated by Shopify's signature`. Because the signature only binds the body bytes, this equality does not hold — the `shop` header can be swapped for any string while keeping a previously-valid `(body, hmac)` pair, and validation still succeeds.

### Impact Explanation
An attacker who legitimately installs the app on their own shop (any public app installation is available to an unprivileged internet user) can capture one authentic `(raw_body, X-Shopify-Hmac-Sha256)` pair emitted for a webhook topic on their own store, then resend an HTTP request to the app's public webhook endpoint with that same body/HMAC but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`, which are also unsigned) set to a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, and the handler receives `WebhookMetadata` claiming the event is for the victim shop. Any app logic that uses `data.shop` to select which tenant's session/access token/data record to act on (a common and gem-documented pattern, see `docs/usage/webhooks.md`) will act on the wrong tenant, resulting in cross-tenant data confusion/corruption using data an attacker fully controls (their own shop's webhook body). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: no privileged credentials are required beyond installing the app on an attacker-owned shop (a normal, unprivileged action), and the header manipulation requires only a basic HTTP client capable of setting arbitrary headers. The vulnerable code path (`Registry.process` → `HmacValidator.validate` → `WebhookMetadata.new(shop: request.shop, ...)`) is on the primary, documented webhook-processing flow of the gem, and the gem's own webhook documentation instructs developers to trust `data.shop` for tenant-scoped work (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the value that is HMAC-verified, or independently verify that the resolved `shop` corresponds to a shop with an active/installed session for this app before dispatching to handlers. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked by consumers against their own installed-shop registry before being trusted, and consider validating it with `ShopifyAPI::Utils::ShopValidator.sanitize!` combined with a session lookup so a request for a shop with no matching stored session/access token is rejected outright rather than forwarded to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g., creates an order) to receive a legitimate webhook, capturing:
   - `raw_body` (e.g. `{"id":1,...}`)
   - `X-Shopify-Hmac-Sha256: <valid hmac for that body>`
2. Attacker sends a new POST request to the app's public webhook endpoint with:
   - Same `raw_body`
   - Same `X-Shopify-Hmac-Sha256`
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds (matches step 1's HMAC): [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` and performs tenant-scoped work under the victim shop's identity, even though the request originated entirely from the attacker.
