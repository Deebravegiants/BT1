Based on my research, I found a genuine analog to the Boot Finance rounding-to-zero bug in `pallet-hyper-fungible-token`'s decimal-conversion helpers.

### Title
`convert_to_erc20`/`convert_to_balance` silently drop decimal scaling when local decimals exceed remote decimals, causing incorrect cross-chain amounts - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The H-07 report describes a precision-scaling factor computed via multiplication then division that rounds to zero (or otherwise miscalculates) when the two precisions being reconciled are on the "wrong side" of each other, permanently corrupting every subsequent calculation that depends on it. The Hyperbridge `hyper-fungible-token` pallet has an analogous decimal-reconciliation routine, `convert_to_erc20`/`convert_to_balance`, that uses `saturating_sub` between `erc_decimals` and `local_decimals` to compute a scaling exponent. This one-directional subtraction silently collapses to a no-op scale factor of `10^0 = 1` whenever the subtraction underflows, meaning the function fails to scale the amount at all in one of the two directions instead of correctly scaling in the opposite direction.

### Finding Description
`convert_to_erc20` and `convert_to_balance` are used in `send()` (`modules/pallets/hyper-fungible-token/src/lib.rs:294-295`) to translate a local balance into the ERC20-side `U256` amount dispatched to the paired EVM contract, and presumably symmetrically in `on_accept`: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions only handle the case where `erc_decimals >= local_decimals` correctly — they divide/multiply by `10^(erc_decimals - local_decimals)`. When `local_decimals > erc_decimals` (e.g. a local asset registered with 18 decimals sent to an EVM contract configured at 12 decimals, as is explicitly the case for the `BridgeToken` contract documented at [2](#0-1)  — "`decimals()` is the inherited ERC20 default of 18 while BRIDGE is 12 decimals on nexus"), `saturating_sub` clamps the exponent to `0`, so the scale factor becomes `1` and **no scaling is applied at all**, in either `convert_to_erc20` or `convert_to_balance`. This is structurally the same class of bug as `customPrecisionMultipliers` collapsing when the multiplier arithmetic hits the wrong side of the ratio — the function is only sound for a scaling factor ≥ 1 in one specific direction, and any input that requires scaling in the other direction is silently treated as if it required no scaling, rather than correctly dividing/multiplying by the reciprocal.

Concretely, for BRIDGE (local 12 decimals, ERC20-side 18 decimals as documented), calling `convert_to_erc20(value, erc_decimals=18, local_decimals=12)` correctly computes `value * 10^6`. But if the roles were reversed for any other registered asset where the local pallet-assets decimals exceed the registered remote `Precisions` value (e.g. local 18-decimal asset bridged to a 6-decimal remote token), `convert_to_erc20(value, erc_decimals=6, local_decimals=18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, sending the raw 18-decimal-scaled amount to the destination contract as if it were already in 6-decimal terms — a 10^12 amplification of the credited amount on the destination side (or the mirror-image massive under-crediting via `convert_to_balance` on the return leg).

### Impact Explanation
Because `send()` is reachable by any signed account calling the `send` extrinsic with attacker-controlled `asset_id`/`destination` combinations for any locally registered asset, and because `Precisions`/local asset decimals are governance-configured independently per asset/chain pair, any registration where local decimals exceed the destination's registered ERC20 decimals turns this into either:
- Unbacked minting on the destination EVM contract (funds conjured from nothing, `convert_to_erc20` under-scales the outgoing message so it mints far more ERC20 tokens than were locked/burned locally), or
- Silent massive loss of value for users converting back (`convert_to_balance` under-scales incoming amounts, crediting users a small fraction of what should be unlocked/minted, with the difference stuck/lost).

This matches the "unbacked mint" and "permanent freezing of funds" categories called out as acceptable analog outcomes.

### Likelihood Explanation
The bug requires only a governance/config combination where local asset decimals exceed the registered remote `Precisions` entry — this is asset-registration data, not attacker-controlled per-transaction, but any user can trigger the exploitable path once such an asset exists, since `send()` is a permissionless signed extrinsic. The `BridgeToken.sol` documentation shows the pallet's own reference deployment intentionally uses mismatched decimals (12 local vs 18 remote) in the currently-safe direction, indicating decimals mismatches across the two sides are an expected, supported configuration in this system — increasing the plausibility that some future or existing asset registration hits the unhandled direction.

### Recommendation
Replace the one-directional `saturating_sub` scaling with an explicit branch that scales in the correct direction regardless of which side has more decimals, mirroring `adjustDecimals` in `sdk/packages/sdk/src/utils.ts:985-994`, which correctly branches on `fromDecimals < toDecimals` vs `>`:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the symmetric fix for `convert_to_balance`. Additionally add a test asserting correct behavior for both directions (`erc_decimals > local_decimals` and `erc_decimals < local_decimals`), since the current test suite (`benchmarking.rs`) apparently only exercises the direction that happens to work.

### Proof of Concept
1. Governance registers an asset locally with `local_decimals = 18` (e.g. via `pallet-assets`).
2. Governance sets `Precisions::<T>::insert(asset_id, dest_chain, 6)` for a destination EVM chain (a 6-decimal ERC20 representation).
3. A user calls `send()` with `amount = 1_000_000_000_000_000_000` (1 whole token, 18 decimals).
4. `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18) = 0`, so `convert_to_erc20` returns `U256::from(1_000_000_000_000_000_000) * 10^0 = 1_000_000_000_000_000_000`, dispatched to the destination contract.
5. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, expecting 6-decimal amounts, mints `1_000_000_000_000_000_000` raw units — i.e., `10^12` times the intended 1 token — while only 1 token's worth was locked/burned on the source chain, resulting in unbacked mint of destination tokens.
