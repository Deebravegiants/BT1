### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body. The `shop-domain` header that identifies which tenant the webhook belongs to (and the `topic`/`webhook-id` headers) are never included in the signed payload, so the "shop that was cryptographically authenticated" and "the shop value the library hands to the app's handler as the tenant identity" are not bound together.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `HmacValidator.validate` computes/compares the signature purely against that signable string [5](#0-4) . Meanwhile `request.shop`, `request.topic`, and `request.webhook_id` are read straight from unauthenticated HTTP headers [3](#0-2) .

`Registry.process` treats a passing HMAC check as authorization to trust all of these header-derived values and forwards them to the host app's handler as the authoritative tenant/topic identity: [1](#0-0) 

Crucially, the HMAC key is the app's single shared `api_secret_key` [6](#0-5)  — the same secret is used to sign webhooks for **every** shop that has installed the app. That means:
- equality that should hold: `shop_bound_by_hmac == shop_trusted_by_handler`
- equality that actually holds: `shop_trusted_by_handler` is an arbitrary attacker-supplied header value, unconstrained by the HMAC, which only proves "this body was signed with the app's shared secret at some point for some shop."

An attacker who controls any shop that has installed the target app (trivial for an unprivileged internet user — e.g. a free/dev install) receives real, validly-signed webhooks for their own shop. They can capture one `(raw_body, hmac)` pair and replay it directly to the app's public webhook endpoint while substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body signature, and `Registry.process` passes the attacker-chosen `shop` value through to the handler unchanged.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is supposed to provide via `Registry.process`: a webhook that was never actually issued by Shopify for shop B can be made to appear, to the host application's handler, as an authentic webhook for shop B, using only a signature that was legitimately generated for shop A (the attacker's own shop). Any host app that uses `data.shop` from `WebhookMetadata` to select which tenant's session/data to act on (the documented and expected usage pattern, see `docs/usage/webhooks.md`) can be tricked into cross-tenant actions (e.g., processing an order-created/customer-redact event under the wrong shop, corrupting per-tenant data or triggering the mandatory GDPR redact/data-request webhook flow for a shop the attacker doesn't control). This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitability only requires: (1) the attacker has (or creates) any shop that installs the target app and can receive a legitimate webhook — no privileged Shopify credentials, `client_secret`, or access tokens are needed — and (2) network access to POST to the app's public webhook receiving endpoint, which is inherently internet-reachable by design. No secret material needs to be leaked; the attacker only ever needs data legitimately delivered to their own tenant.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise bind them to the signature (e.g., verify the `shop-domain` header against the list of shops known to have valid webhook subscriptions/sessions before dispatching to the handler), so that the signature actually authenticates *which* shop and topic the payload belongs to, not just the raw body bytes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (any unprivileged install).
2. Shopify sends attacker a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — signed with the app's single shared secret.
3. Attacker crafts a new HTTP POST directly to the app's public webhook route with the same body `B` and same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally changes `x-shopify-topic`).
4. `Utils::HmacValidator.validate(request)` returns `true` because the body `B` and HMAC `H` still match (see [7](#0-6)  and [8](#0-7) ).
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` [4](#0-3) , causing the app to act on the attacker's data as if it belonged to `victim-shop.myshopify.com`.
