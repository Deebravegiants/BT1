### Title
Webhook shop/topic identity spoofing via HMAC that only covers the body, not headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Utils::HmacValidator.validate` authenticates a webhook solely by recomputing the HMAC over `to_signable_string`, which for `Webhooks::Request` is defined as the raw request body only [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values consumed by the application are pulled straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the HMAC at all [2](#0-1) . `Registry.process` trusts these header-derived values once the body HMAC checks out: it looks up the handler by `request.topic` and forwards `request.shop` into `WebhookMetadata` [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop-domain header == shop that produced/authorized this exact byte sequence`. Because Shopify computes the webhook HMAC using the app's single `client_secret` for every shop that has installed the app (not a per-shop secret), and because the HMAC covers only `@raw_body`, any party who has legitimately received one real webhook delivery (e.g., by installing the app themselves) possesses a `(raw_body, valid_hmac)` pair. That pair remains a valid HMAC pair for the *same bytes* regardless of which `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` header values accompany it, because none of these are part of `to_signable_string`. An attacker can therefore replay the identical body+hmac while substituting the `shopify-shop-domain` header with an arbitrary victim shop's domain (or any topic registered in the app's `@registry`), and `HmacValidator.validate` will still return `true` [5](#0-4) , causing the handler to run under an attacker-chosen `shop` identity that was never actually verified.

### Impact Explanation
This crosses a tenant boundary: an app that keys any state, authorization decision, or data write off of `WebhookMetadata#shop` (the standard, documented way to identify which merchant a webhook belongs to) can be made to process attacker-controlled shop identity with data the attacker fully controls (subject to needing one valid signed body). This matches the "Critical - cross-tenant access" category, since the gem provides no way for the host application to distinguish a genuinely-scoped webhook from one delivered under a forged shop/topic header.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own store (or otherwise obtain one legitimate webhook body+hmac pair) and be able to submit arbitrary HTTP requests to the app's webhook endpoint with attacker-chosen headers — both are unprivileged-internet-user-level capabilities, not privileged access, leaked secrets, or TLS interception.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signed payload used for HMAC verification (or otherwise cryptographically bind them, e.g., by validating the shop domain against the caller's own record of expected shop(s) before trusting it), rather than relying on the header values being merely "close to" the HMAC-covered body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`) that the app handles.
2. Shopify delivers a real webhook to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>` and some JSON `raw_body`.
3. Attacker captures `raw_body` and `x-shopify-hmac-sha256` verbatim.
4. Attacker (or a compromised network position they control, e.g., their own server) re-sends a request to the app's webhook endpoint with the same `raw_body`/`hmac` but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` [1](#0-0)  — validation succeeds — and the handler executes with `shop: "victim-shop.myshopify.com"` [6](#0-5) , despite the payload never having been produced by or for that shop.
