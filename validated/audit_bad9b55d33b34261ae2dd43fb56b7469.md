### Title
Unbounded `GetRequestsWithProof` batch causes excessive CPU consumption in unauthenticated `validate_unsigned` — ([File: modules/pallets/state-coprocessor/src/lib.rs])

### Summary
`pallet_state_coprocessor::Pallet::validate_unsigned` runs the *entire* request/proof-verification pipeline (`handle_get_requests`) for every unsigned extrinsic that reaches a node's transaction pool, before any fee, weight, or size limit is applied. `GetRequestsWithProof.requests: Vec<GetRequest>` and each `GetRequest.keys: Vec<Vec<u8>>` have no enforced maximum length, so an unauthenticated peer can gossip a single crafted unsigned extrinsic containing a very large batch of `GetRequest`s (and/or keys per request) that forces every full node's mempool validation logic to perform expensive trie/EVM proof decoding and verification work, analogous to CVE-2018-14648's "crafted search query causing excessive CPU in `do_search()`" pattern (an unauthenticated request triggers disproportionate server-side compute before any authorization/weight gate).

### Finding Description
`validate_unsigned` is invoked by every node (not just the block author) whenever this unsigned call propagates through the network — this is standard Substrate transaction-pool behavior for `ValidateUnsigned` pallets. Here it directly calls the same code path that a block-author would use to actually execute the request: [1](#0-0) 

That path, `handle_get_requests`, decodes and verifies proofs and iterates over the full `requests` vector without any upper bound check, invoking per-request state proof verification (`dest_state_machine.verify_state_proof`) which in turn (for EVM/Substrate/Pharos backends) rebuilds tries / walks Merkle proofs per key: [2](#0-1) [3](#0-2) 

The message type itself places no cap on batch size or per-request key count: [4](#0-3) [5](#0-4) 

Bandwidth/fee accounting (`BandwidthGate::try_consume`) is only applied *after* proof verification succeeds for each response, so it cannot gate the CPU cost incurred while attempting (and ultimately failing/succeeding) verification of an oversized or malicious batch: [6](#0-5) 

Because this is `ensure_none` (unsigned, permissionless) dispatch, and `validate_unsigned` executes on every node that merely receives the extrinsic via gossip, there is no authentication or staking requirement gating the CPU expenditure — matching the CVE's "unauthenticated attacker … provoke a denial of service" profile. [7](#0-6) 

### Impact Explanation
An attacker can craft a `Call::handle_unsigned` extrinsic with a `GetRequestsWithProof` containing an unbounded number of `GetRequest`s and/or an unbounded number of `keys` per request, paired with syntactically valid (or partially valid) proof bytes. Every node that receives this extrinsic via the network — before it is ever included in a block — will execute `validate_unsigned`, which fully replays proof decoding/verification for the whole batch. Repeated broadcast of such extrinsics (which are never actually included, since they will ultimately fail some check) can degrade or halt block production and RPC responsiveness network-wide, constituting a denial-of-service against the relaying/messaging path that is reachable from a single relayed message — matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High. The call is fully permissionless (`ensure_none`), requires no token stake or prior state, and the attack payload is just a large `Vec<GetRequest>`/`Vec<Vec<u8>>` with proof bytes — trivially constructible without any privileged access. The `longevity: 25` / `propagate: true` transaction-validity result means the mempool keeps re-validating and rebroadcasting resubmissions, amplifying the cost.

### Recommendation
- Enforce a hard cap on `GetRequestsWithProof.requests.len()` and on each `GetRequest.keys.len()` (e.g., via a `BoundedVec` or an explicit length check) rejected early in `validate_unsigned`, before any proof decoding/verification is attempted.
- Perform cheap, size-based rejection (batch/key/proof byte-length checks) as the very first step of `validate_unsigned`/`handle_get_requests`, ahead of any trie construction or cryptographic verification.
- Consider charging or estimating weight proportional to declared batch size in `validate_unsigned` itself (mirroring `pre_dispatch`/weight-annotation patterns already used for `pallet::weight`) so oversized batches are rejected without doing the expensive work.

### Proof of Concept
1. Construct a `GetRequestsWithProof` with `requests` containing, e.g., tens of thousands of synthetic `GetRequest` entries, each with a large `keys: Vec<Vec<u8>>` (e.g., hundreds of 52-byte EVM keys), and arbitrary/garbage `source`/`response` proof bytes.
2. Wrap it in `Call::handle_unsigned { message }` and submit as an unsigned extrinsic to any RPC node, or directly gossip via the network's unsigned-transaction relay.
3. Observe that every node receiving this extrinsic executes `Pallet::validate_unsigned`, which calls `handle_get_requests`, which iterates the full request/key set and performs trie/EVM proof-verification work for each key (via `verify_state_proof`/`verify_membership`) before any error is returned — consuming CPU proportional to attacker-chosen batch size, with no size cap in place to short-circuit this work.

	pub fn handle_get_requests(
		GetRequestsWithProof { requests, source, response, address }: GetRequestsWithProof,
	) -> Result<(), Error> {
		// 1. Verify source proofs
		// 2. Extract fees
		// 3. Verify response proof
		// 4. insert GetResponse into mmr and request receipts
		// 5. emit Response events
		let host = <<T as Config>::IsmpHost>::default();

		// Reject duplicate requests within the batch.
		let wrapped: Vec<Request> = requests.iter().cloned().map(Request::Get).collect();
		dedup_requests::<<T as Config>::IsmpHost>(&wrapped)?;

		for req in requests.iter() {
			let full = Request::Get(req.clone());

			// Get requests time out are relative to Hyperbridge
			if full.timed_out(host.timestamp()) {
				Err(Error::RequestTimeout { meta: full.clone().into() })?
			}

			// Source of the request must match the proof
			if full.source_chain() != source.height.id.state_id {
				Err(Error::RequestProofMetadataNotValid { meta: full.clone().into() })?
			}

			// Proof must come from the requested chain
			if full.dest_chain() != response.height.id.state_id {
				Err(Error::RequestProofMetadataNotValid { meta: full.clone().into() })?
			}

			// This request has already been responded to. Mirror `handlers/response.rs:61`:
			// dedup against `response_receipt`, which the dispatch path writes for this exact
			// GetRequest hash after producing a response. The receipt also binds the response
			// commitment, so external auditors can attest "Hyperbridge produced response X for
			// request Y" from one map.
			let probe = GetResponse { get: req.clone(), values: Default::default() };
			if host.response_receipt(&probe).is_some() {
				Err(Error::DuplicateResponse { meta: (&probe).into() })?
			}
		}

		// Ensure the proof height is equal to each retrieval height specified in the Get
		// requests
		if !requests.iter().all(|get| get.height == response.height.height) {
			Err(Error::InsufficientProofHeight)?
		}

		// Verify source proof
		let source_state_machine = validate_state_machine(&host, source.height)?;
		let state_root = host.state_machine_commitment(source.height)?;

		// Verify membership proof to ensure that requests where committed on source chain
		let commitments = requests
			.iter()
			.map(|get| hash_request::<<T as Config>::IsmpHost>(&Request::Get(get.clone())))
			.collect();
		source_state_machine.verify_membership(&host, commitments, state_root, &source)?;
