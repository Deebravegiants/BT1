### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator` validates the HMAC exclusively against that body. The `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in the signed material, yet `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the authoritative tenant identity and passes it straight into the `WebhookMetadata` handed to the host app's handler.

### Finding Description
The binding that should hold is: `shop asserted in the "shop-domain" header == shop cryptographically bound by the HMAC`. This equality is broken:

- `Request#to_signable_string` [1](#0-0)  returns `@raw_body` only.
- `HmacValidator.validate` / `validate_signature` compute and compare the signature purely from `verifiable_query.to_signable_string` [2](#0-1) , i.e. only the body is authenticated — the `shop`, `topic`, `api-version`, and `webhook-id` headers are parsed but never bound into the signed bytes.
- `Registry.process` validates the HMAC and then unconditionally uses `request.shop` to construct the `WebhookMetadata` delivered to the app: [3](#0-2) .
- `WebhookMetadata` treats `shop` as a plain, trusted field with no further verification: [4](#0-3) .

Because the api_secret_key used to sign webhooks is shared by the app across **all** installed shops (it is the app's secret, not a per-shop secret), any unprivileged user who can get the app installed on a shop they control (a normal, unprivileged self-service action on Shopify) will legitimately receive real webhook deliveries with valid `hmac`+`body` pairs for their own shop. Since the `shop-domain` header is not part of the signed bytes, that attacker can take a legitimately-signed `(body, hmac)` pair from their own shop and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still return true (the body/hmac pair is valid), and `Registry.process` will pass `shop: "<victim-shop>.myshopify.com"` to the handler, `hmac unchanged`, `body unchanged`.

Before attacker's forged request: `hmac` was computed for `(body_A, shop_A)` and is only meant to authenticate `body_A`.
After attacker's forged request: `hmac` still validates for `body_A`, but the app processes it as `(body_A, shop_victim)` — the shop identity has been substituted without invalidating the signature, breaking the equality `authenticated_body == authenticated_shop`.

### Impact Explanation
This directly enables cross-tenant data injection/confusion: any host application that keys persistence, side effects, or business logic off `WebhookMetadata#shop` (e.g., "update this shop's order/inventory/customer record", "mark this shop as uninstalled", "sync data for this shop") can be made to apply attacker-controlled webhook bodies to a victim shop's tenant data, without needing the app's `api_secret_key`, TLS interception, or the victim's credentials. This matches the "cross-tenant access" Critical-impact category, since the attacker crosses the tenant boundary by manipulating an identity field that this gem does not bind to the cryptographic proof it relies on.

### Likelihood Explanation
Likelihood is high for any unprivileged attacker: obtaining at least one legitimately-signed webhook (body+HMAC) requires only installing the app on a shop the attacker controls, which is by design unprivileged/self-service in the Shopify app ecosystem. Sending an HTTP POST to the app's public webhook endpoint with modified headers requires no special access. The gem itself performs no defense against this because `to_signable_string` deliberately/accidentally excludes the shop header from the signed payload.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind the shop-domain header to the payload before trusting `request.shop`. At minimum, `Request#to_signable_string` should combine the raw body with the shop-domain (and topic) header values so that tampering with those headers invalidates the signature, matching the way `AuthQuery#to_signable_string` already binds `shop` into its signable string.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id": 123, ...}`
3. Attacker replays the exact same request to the same endpoint but changes only the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - HMAC and body left untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the (unchanged) HMAC [5](#0-4) .
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id": 123, ...}, ...)` [6](#0-5)  and applies attacker-controlled data to the victim shop's tenant.
