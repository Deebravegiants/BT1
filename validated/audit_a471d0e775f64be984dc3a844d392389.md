### Title
Live re-read of `operator_qr_expiration_time` config lets a backend value change retroactively alter the validity window of an already-scanned operator QR code - (File: src/plans/mod.rs)

### Summary
`MasterPlan::idle_scan_user_qr_code` computes the remaining validity of an operator QR scan by combining a fixed start timestamp (`operator_data.timestamp`) with the *current* value of `operator_qr_expiration_time` pulled from the live, periodically-refreshed `Config`, instead of computing and storing a fixed expiration deadline at scan time. This mirrors the BendDAO auction-duration bug class: a duration parameter that can change mid-session is applied against an old start time, changing the effective end time for sessions already in progress.

### Finding Description
The operator QR-code scan establishes `operator_data.timestamp` at the moment the operator's QR is validated [1](#0-0) . Every time the loop re-enters the user QR scanning idle plan, it recomputes the remaining time window like this:

```rust
Some(operator_qr_expiration_time.saturating_sub(operator_data.timestamp.elapsed())),
``` [2](#0-1) 

`operator_qr_expiration_time` is not captured once and frozen for the duration of the operator session; it is read as an argument passed in from the live `Config` object, which is periodically replaced by `Config::download_and_store` as the backend config poller runs (governed by `CONFIG_UPDATE_INTERVAL`) [3](#0-2) [4](#0-3) . The default/backend-configurable value is defined as `Duration::from_secs(60 * 60 * 23)` and is explicitly deserialized from the backend config response as `operator_qr_expiration_time` [5](#0-4) [6](#0-5) , and the field exists in the backend wire struct as an operator-controlled, remotely settable parameter [7](#0-6) .

Because the "duration" (`operator_qr_expiration_time`) rather than a computed "end timestamp" is what's stored and re-applied on every loop iteration, any backend-side change to this parameter is retroactively applied to a session whose operator QR was already scanned under the *old* expiration policy — exactly the root cause described in the referenced BendDAO auction-duration report, where `bidStartTimestamp + auctionDuration` is recomputed with the live `auctionDuration` instead of a stored, immutable end time.

### Impact Explanation
This is a signup-authorization/identity-binding timing boundary: the operator QR establishes the operator/location context that authorizes and scopes the signup flow that follows. If the backend increases `operator_qr_expiration_time` while an operator session is already open, an operator QR-derived authorization window that should have expired continues to be treated as valid, letting a signup proceed under a stale operator context longer than intended by policy at scan time. Conversely, a decrease can prematurely invalidate an in-progress, legitimately-authorized signup flow, causing operator/user confusion and needless signup failures. The security-relevant direction (unintended extension of authorization validity) is the more serious case, since the QR expiration acts as a boundary limiting how long a validated operator context can be reused for authorizing signups.

### Likelihood Explanation
Likelihood is limited to scenarios where the backend operator changes `operator_qr_expiration_time` while sessions are already mid-flow, which requires backend/config-server action, not attacker input, consistent with the "medium severity/timing" classification given to the analogous BendDAO finding. The Orb's config refresh cadence (`CONFIG_UPDATE_INTERVAL`) means the new value can propagate to an active orb within a short window, so a live parameter change reliably affects concurrently-running signup sessions.

### Recommendation
Compute and store an absolute expiration timestamp (`operator_qr_expiration_at = Instant::now() + operator_qr_expiration_time`) once, at the moment the operator QR is validated, and persist it alongside `operator_data`. Subsequent checks should compare `Instant::now()` against this stored deadline rather than re-deriving the remaining time from the current (possibly changed) `operator_qr_expiration_time` config value, so that in-flight sessions are unaffected by later config changes.

### Proof of Concept
1. Operator scans their QR code; `operator_data.timestamp = now`, established with the currently configured `operator_qr_expiration_time` (e.g. 23h).
2. Backend config poller (`CONFIG_UPDATE_INTERVAL`) fetches an updated config in which `operator_qr_expiration_time` has been increased (e.g. to 48h) [3](#0-2) .
3. `idle_scan_user_qr_code` loops back and recomputes the remaining time using the new, larger `operator_qr_expiration_time` value against the old `operator_data.timestamp` [2](#0-1) , allowing the operator session to remain "valid" well past the 23h window that was in effect when the operator QR was originally scanned.

    /// Downloads the latest configuration from the backend and updates the
    /// shared configuration object.
    pub async fn download() -> Result<Config> {
        let res = backend::config::request().await.map_err(|e| {
            tracing::error!("Config request failed: {:?}", e);
            dd_incr!("main.count.http.config_update.error");
            e
        })?;

        if let Some(config) = Config::from_backend(res) {
            dd_incr!("main.count.http.config_update.success");
            Ok(config)
        } else {
            dd_incr!("main.count.http.config_parse.error");
            Err(eyre!("invalid config"))
        }
    }

    /// Downloads the latest configuration from the backend, updates the shared
    /// configuration object, and stores the updated configuration to the file
    /// system.
    pub async fn download_and_store(config: Arc<Mutex<Config>>) -> Result<()> {
        *config.lock().await = Self::download().await.map_err(|e| {
            tracing::error!("Failed to download config: {:?}", e);
            e
        })?;
        let config_to_store = config.lock().await;
        tracing::info!("Downloaded latest config: {:?}", config_to_store);
        config_to_store.store().await.map_err(|e| {
            tracing::error!("Config downloaded but failed to be stored: {:?}", e);
            e
        })
    }
