### Title
Exact-out `getFeeQuote` accepts unbounded solver `amount_in` with no sanity check, draining up to the full withdrawal amount - ([File: packages/intents-sdk/src/lib/estimate-fee.ts])

### Summary
`getFeeQuote`'s primary exact-out branch (`packages/intents-sdk/src/lib/estimate-fee.ts:64-80`) sends `exact_amount_out: feeAmount` to `solverRelay.getQuote` and returns the raw solver response with no upper bound on `amount_in`. `solverRelay.getQuote`'s `matchesRequest` (`packages/internal-utils/src/solverRelay/getQuote.ts:119-138`) for the exact-out case only asserts `amount_out === exact_amount_out`; `amount_in` is unconstrained by design ("the other side is what the solver competes on ... min amount_in for exact_out"). Only the exact-in QuoteError-fallback path (lines 139-159 of `estimate-fee.ts`) applies a 1.2x/1.5x sanity ratio — the primary exact-out path has none.

### Finding Description
The broken equality: `feeEstimation.amount` (from `BigInt(feeQuote.amount_in)`, set in `hot-bridge.ts:349`, `omni-bridge.ts:631`, `direct-bridge.ts:260`, `aurora-engine-bridge.ts:197`) is supposed to approximate the real relayer/storage cost `feeAmount`, but nothing in the exact-out path enforces `amount_in ≈ f(feeAmount)`. A single malicious/permissionless solver answering the relay's `quote` RPC can return `amount_out = feeAmount` (satisfying `matchesRequest`) together with an arbitrarily large `amount_in`. Since `sortQuotes` for exact-out picks the *minimum* `amount_in` among valid quotes (`getQuote.ts:96-113`), if that malicious quote is the only valid quote returned (attacker controls the relay response set in this proof), it becomes `bestQuote` unconditionally — there is no absolute ceiling comparing `amount_in` to `feeAmount`'s expected fiat value in this path, unlike the exact-in fallback which explicitly rejects `actualRatio > 1500n` (i.e., > 1.5x `feeAmount` value in `amount_out` terms).

Downstream, `sdk.ts:_estimateWithdrawalFee` (`packages/intents-sdk/src/sdk.ts:421-425`) only throws `FeeExceedsAmountError` when `fee.amount >= withdrawalParams.amount`. Any `feeQuote.amount_in` strictly less than `withdrawalParams.amount` (e.g., `withdrawalParams.amount - 1`) passes this check untouched, and `actualAmount = withdrawalParams.amount - fee.amount` becomes negligible while the "fee" silently consumes almost the entire withdrawal.

### Impact Explanation
For a user withdrawing via `HotBridge`, `OmniBridge`, `DirectBridge`, or `AuroraEngineBridge` (all four route through `getFeeQuote`'s exact-out branch), a colluding/malicious solver participating in the public solver-relay auction can force `feeEstimation.amount` up to `withdrawalParams.amount - 1`, i.e., the withdrawing user is charged nearly the entire amount as a "fee," and `actualAmount` (real tokens delivered) collapses to a negligible residual. This is a fee error draining a material share of the amount against the withdrawing user, matching the Critical impact category. It is repeatable per withdrawal call since the attacker only needs to control (or be selected as) the sole/best-ranked solver response for that specific token pair/fee-asset pair at quote time.

### Likelihood Explanation
Requires the attacker to operate a permissionless solver reachable by the relay's quote aggregation for the `(tokenAssetId, feeAssetId)` pair being fee-quoted, and to either be the only responder or to otherwise become `bestQuote` via `sortQuotes`'s min-`amount_in` ordering — feasible for niche/thin-liquidity fee-asset pairs where few solvers quote. No special access is needed beyond being an ordinary participant in the solver-relay auction (explicitly in-scope per the prompt's attacker model: "a permissionless solver answering a quote").

### Recommendation
Add a sanity bound to the exact-out branch of `getFeeQuote` analogous to the exact-in fallback's 1.2x/1.5x ratio check — e.g., fetch USD prices for `feeAssetId`/`tokenAssetId` and reject the exact-out quote if `amount_in` implies an ratio far above the expected fiat-equivalent of `feeAmount` (mirroring lines 139-159), before returning the quote from the primary branch.

### Proof of Concept
```ts
// vitest, mocking only the solverRelay HTTP quote endpoint
it("accepts an oversized amount_in for exact-out fee quote with no sanity bound", async () => {
  using solverRelay = await useMockedSolverRelay();
  const { IntentsSDK } = await import("./sdk");
  const sdk = new IntentsSDK({ referral: "", intentSigner });

  const withdrawalAmount = 1_000_000n;
  const feeAmount = 100n; // real relayer/storage cost expectation, small
  const maliciousQuote = {
    amount_in: (withdrawalAmount - 1n).toString(), // huge, near full amount
    amount_out: feeAmount.toString(), // matches exact_amount_out => passes matchesRequest
    defuse_asset_identifier_in: "nep141:btc.omft.near",
    defuse_asset_identifier_out: "nep141:wrap.near",
    expiration_time: "",
    quote_hash: "malicious",
  };
  solverRelay.getQuote.mockResolvedValue(maliciousQuote); // sole responder -> becomes bestQuote

  const fee = await sdk.estimateWithdrawalFee({
    withdrawalParams: {
      assetId: "nep141:btc.omft.near",
      amount: withdrawalAmount,
      destinationAddress: zeroAddress,
      feeInclusive: false,
    },
  });

  // Left side of broken equality: no bound relative to real cost baseline (feeAmount-derived expectation)
  expect(fee.amount).toBe(withdrawalAmount - 1n);
  // Right side: sanity check would require fee.amount to stay close to feeAmount's value;
  // it does not, and no error/clamp is thrown despite fee.amount being ~99.9999% of withdrawalAmount
  expect(fee.amount).toBeGreaterThan(feeAmount * 1000n); // grossly exceeds any real-cost multiple
});
```
