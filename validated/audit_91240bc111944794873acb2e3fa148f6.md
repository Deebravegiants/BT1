### Title
PoA Bridge withdrawal status misreport due to matching by `assetId` instead of `index` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the status/destination-tx-hash of a specific withdrawal by matching the POA indexer response solely on `assetId`, ignoring the `index` field that every other bridge implementation uses to disambiguate multiple withdrawals batched inside the same NEAR transaction. When a single NEAR transaction contains two or more withdrawals of the same asset (e.g. two `ft_withdraw` intents for the same token to different destination addresses, executed in one batch), the wrong withdrawal's status and `transfer_tx_hash` can be reported for the queried `index`.

### Finding Description
`describeWithdrawal` fetches the withdrawal list for the NEAR transaction and then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching purely by `assetId`: [1](#0-0) 

The matching criteria type carries only `assetId`, with no `index`, `destinationAddress`, or per-item ordinal disambiguator: [2](#0-1) 

This is confirmed as intentional current behavior by a regression test explicitly titled "matches withdrawal by assetId, not by index," which only exercises the case of two *different* assetIds in the same tx and passes because they don't collide: [3](#0-2) 

However, `WithdrawalIdentifier` explicitly models `index` as the disambiguator for multiple withdrawals inside one NEAR tx, and other bridges (`HotBridge`, `OmniBridge`) correctly use `args.index` to select the right entry out of an array of withdrawals for the same tx hash: [4](#0-3) [5](#0-4) 

`PoaBridge` breaks this equality: when a single NEAR transaction contains two withdrawals of the **same** `assetId` (e.g. same token withdrawn to two different destination addresses in one batched intent execution — supported by NEAR intents batching and by the very existence of the `index` field), `findMatchingWithdrawal` returns the *first* array element whose `defuse_asset_identifier`/`near_token_id` matches, regardless of which element actually corresponds to the caller's `index`/destination. If that first match is `COMPLETED`, `describeWithdrawal({index: 0, ...})` will report `{status: "completed", txHash: <hash belonging to the OTHER withdrawal>}` even though the withdrawal the caller actually cares about (to a different destination address) may still be `PENDING` or have a different (or no) hash.

### Impact Explanation
This is a status/hash misreport: the reported on-chain outcome (destination tx hash and completion status) does not correspond to the specific withdrawal identified by `index`/destination address that the caller queried. An integrator polling per-withdrawal status to decide when to credit/settle a user's off-chain balance, mark an order fulfilled, or release funds could:
- Mark withdrawal A (to address A) as completed using a tx hash that actually paid out withdrawal B (to address B), causing incorrect confirmation to the wrong recipient/order.
- Potentially trigger a double credit if the integrator later also processes the correct completion event for the same underlying hash under a different withdrawal record.

This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Requires only that a single NEAR transaction batches two or more withdrawal intents for the same underlying asset (`assetId`) to different destinations — a state reachable by any ordinary user/integrator constructing a batched withdrawal transaction, no privileged or malicious actor needed. No mitigating check on `index`/destination exists in `findMatchingWithdrawal`'s only consumer path in `poa-bridge.ts`.

### Recommendation
Extend `WithdrawalCriteria`/`findMatchingWithdrawal` to disambiguate using the withdrawal's position/`index` within the transaction (or destination address/amount) in addition to `assetId`, matching the pattern already used by `HotBridge` and `OmniBridge`. At minimum, when multiple withdrawals share the same `assetId` within one NEAR tx, cross-check `destinationAddress`/`amount` before returning a match.

### Proof of Concept
1. Submit one NEAR transaction containing two `ft_withdraw` intents for the same `assetId` (e.g. `nep141:usdt.tether-token.near`) — one to `destinationAddress = A`, `index = 0`, one to `destinationAddress = B`, `index = 1`.
2. POA indexer returns `withdrawals: [{assetId, status: "COMPLETED", transfer_tx_hash: "hash-for-B", address: B}, {assetId, status: "PENDING", address: A}]` (order not guaranteed, per the code comment "Response list is unsorted").
3. Call `describeWithdrawal({index: 0, withdrawalParams: {assetId, destinationAddress: A, ...}, tx})`.
4. `findMatchingWithdrawal` matches the first element by `assetId` alone (the `COMPLETED` one for B) and returns `{status: "completed", txHash: "hash-for-B"}` for the withdrawal that was actually meant for A — a caller polling index 0 sees a false "completed" status with a hash that never paid address A.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}
