### Title
Missing session-binding check for `self_serve::app::v1::RequestState` messages allows unauthorized state disclosure across signup sessions - (File: `orb-relay-client/src/client.rs`)

### Summary
The `PollerAgent::main_loop` in the orb-relay client enforces a per-message-type authorization check that binds every inbound message's source entity to the currently paired session (`src.id == self.config.dst_id`) before it is buffered/acted upon. However, this check is explicitly bypassed for `self_serve::app::v1::RequestState` messages, which are answered unconditionally with the orb's `last_message` (the last signup-state payload sent to the app), regardless of whether the sender is the entity paired to the active signup session. This mirrors the `MapleLoan.makePayment()` pattern where a state-affecting/state-disclosing action lacked the access-control check applied to all other paths, letting an unauthorized caller invoke privileged behavior meant only for the paired counterparty.

### Finding Description
In `orb-relay-client/src/client.rs`, `PollerAgent::main_loop` processes inbound `RelayPayload`s from the relay backend: [1](#0-0) 

Every payload other than `RequestState` is subject to `else if src.id != self.config.dst_id { ...skip... }`, which enforces that only the entity paired for this specific signup/app session (`dst_id`, derived from the QR-code-bound `orb_relay_app_id`) may have its messages processed via `handle_message` and buffered for consumption by the signup plan logic (e.g. `wait_for_msg::<self_serve::app::v1::StartCapture>` in `src/plans/mod.rs`).

The `RequestState` branch is checked first and unconditionally re-sends `self.last_message` — the most recent state payload sent on the connection (e.g., `SignupEnded`, `CaptureStarted`, `AnnounceOrbId`, or other signup lifecycle events) — without verifying `src.id == self.config.dst_id`. This creates a distinct, unauthenticated/unauthorized code path that any entity able to reach the orb's relay queue can exploit to solicit the orb's last signup-related state message, sidestepping the session-binding invariant relied upon everywhere else in the same function.

This is analogous to the reported `makePayment()` bug: a function/branch that should be restricted to the authorized counterparty (the paired app/session, analogous to the `borrower`) instead allows any caller to trigger it, because the authorization check present on the "normal" code path was omitted for this one branch.

### Impact Explanation
An unauthorized entity that is not bound to the active signup session can force the orb to re-emit its last signup-state message on the connection. Depending on timing, this last message can be `SignupEnded` (containing `success`/`failure_feedback`) or other self-serve lifecycle signals such as `CaptureStarted`/`CaptureTriggerTimeout`. This breaks the session/identity-binding trust boundary that the rest of `main_loop` enforces, enabling cross-session state disclosure/replay of signup progress/result information to a caller that was never authorized to observe or interact with that specific signup session — a concrete violation of the "identity binding" and "cross-signup state bleed" categories.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate, authenticated relay client (holding a valid token/ZKP auth per `Client::new_as_app`/`new_as_app_zkp`) but not the entity paired to the target signup session, and to be able to have a `RequestState` message routed into the orb's connection/queue. Given the check is coded to explicitly bypass the `dst_id` binding only for this message type, this is a deterministic code-level omission rather than a speculative race — any caller reaching the orb's relay endpoint with a `RequestState` payload triggers it, independent of the backend's own queue-routing assumptions.

### Recommendation
Apply the same `src.id == self.config.dst_id` (session-binding) check to `RequestState` messages as is applied to every other inbound payload type before replying with `last_message`. If proactive resync must be supported for reconnecting legitimate clients, validate that the reconnecting entity is cryptographically/session-bound to the current `dst_id` prior to responding, consistent with the rest of `main_loop`'s trust model.

### Proof of Concept
1. An attacker authenticates to the orb-relay backend as an `App` entity with a valid token/ZKP proof, but with a `src_id`/session that is not the `orb_relay_app_id` paired to the target orb's active signup (i.e., `src.id != dst_id`).
2. The attacker sends a `self_serve::app::v1::RequestState {}` payload targeting the orb's relay queue.
3. In `PollerAgent::main_loop`, the branch `if self_serve::app::v1::RequestState::matches(&payload).is_some()` matches first and unconditionally executes `sender_tx.send(self.last_message.clone())`, bypassing the `src.id != self.config.dst_id` check that would otherwise reject this message.
4. The orb's last signup-state payload (e.g., `SignupEnded`) is sent out, even though the requester was never the entity bound to that session. [2](#0-1)
