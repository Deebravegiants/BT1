Audit Report

## Title
Staking after pool expiry can permanently brick a pool via arithmetic underflow in `reward_per_token` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `stake` extrinsic performs no check against `pool_info.expiry_block`, allowing any signed account to stake into a pool that has already expired and whose `total_tokens_staked` is currently zero. This silently updates `last_update_block` to a block number past `expiry_block`, and once `total_tokens_staked` becomes non-zero, every subsequent `reward_per_token` calculation branch underflows via `ensure_sub`, permanently breaking `unstake`, `harvest_rewards`, and `cleanup_pool` for that pool.

## Finding Description
`stake` at [1](#0-0)  has no expiry check, unlike `unstake` and `harvest_rewards` which check `now > pool_info.expiry_block || caller == staker` [2](#0-1) [3](#0-2)  — but note this check only gates *who* can act on behalf of another staker; it does not block staking after expiry for the staker's own account either.

`reward_per_token` takes a zero-stake fast path when `total_tokens_staked.is_zero()`, otherwise computes `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)` [4](#0-3) . `last_block_reward_applicable` clamps "now" to `expiry_block` once expired [5](#0-4) , but `update_pool_rewards` unconditionally stamps `last_update_block` with the real current block, never clamped to `expiry_block` [6](#0-5) .

Verified exploit sequence:
1. Pool expires at block `E` with `total_tokens_staked == 0` (no active stakers).
2. At block `E+k`, attacker calls `stake`. Since `total_tokens_staked` is still 0 at the time `reward_per_token` runs, the fast path returns unchanged; `update_pool_rewards` then sets `last_update_block = E+k` (unclamped), and `total_tokens_staked` becomes non-zero after the deposit.
3. Any subsequent call touching the pool (`unstake`, `harvest_rewards`, or another `stake`) re-invokes `reward_per_token`. Now `total_tokens_staked > 0`, triggering the calculation branch: `last_block_reward_applicable(E)` clamps to `E`, then `E.ensure_sub(E+k)` underflows, and `ensure_sub` (from `EnsureSub`, checked arithmetic) returns `Err`, aborting the call.
4. The attacker's `PoolStakers` entry can never be removed (every `unstake` call fails identically), so `PoolStakers::iter_key_prefix(pool_id).next()` never returns `None`, permanently blocking `cleanup_pool`'s guard [7](#0-6) .

I confirmed this exact code exists in the repository as cited, and traced the arithmetic manually: with `total_tokens_staked = 0` at `E+k` fast-path taken, `last_update_block` set to `E+k`, then on the next call `total_tokens_staked = 1` forces the calculation branch, and `E.ensure_sub(E+k)` is indeed a subtraction of a larger value from a smaller one, which underflows under `EnsureSub`'s checked (non-saturating) semantics.

## Impact Explanation
Once triggered, the pool's reward-asset balance held in `pool_info.account` and the `PoolCost` storage deposit become permanently unrecoverable: `cleanup_pool` can never succeed (stakers list never empties) and `unstake`/`harvest_rewards` permanently revert for that pool. This is a genuine, unprivileged, and permanent denial-of-service that locks funds indefinitely — a concrete in-scope impact (permanent fund lock / broken invariant) rather than a purely theoretical issue.

## Likelihood Explanation
The precondition is realistic: a pool that has passed its `expiry_block` while `total_tokens_staked == 0` (either nobody ever staked, or all stakers fully exited before expiry) is a normal, unprivileged state that can occur for any pool. Triggering requires only a single signed `stake` call with a minimal amount — no elevated privilege, no race condition, and no unrealistic assumption. This is a low-cost, repeatable griefing vector against any admin who has created a pool and is waiting to reclaim leftover rewards via `cleanup_pool`.

## Recommendation
- Reject `stake` when `now >= pool_info.expiry_block`, mirroring the intent of the expiry checks already present in `unstake`/`harvest_rewards`.
- Clamp `last_update_block` to `min(now, expiry_block)` in `update_pool_rewards` so `reward_per_token`'s subtraction can never underflow regardless of when `stake` is called, as a defense-in-depth measure.
- Consider allowing `cleanup_pool` (or a dedicated admin-only sweep) to force-remove zero/near-zero residual stakers after expiry so a poisoned pool state cannot permanently block fund recovery.

## Proof of Concept
1. Admin calls `create_pool` with `expiry_block = E`; ensure no one stakes, or all stakers fully `unstake` before/at block `E`, so `Pools::<T>::get(pool_id).total_tokens_staked == 0` at block `E`.
2. Advance to block `E + k` (`k > 0`). Attacker (any signed account) calls `stake(pool_id, amount=1)`. This succeeds: `reward_per_token` takes the `total_tokens_staked.is_zero()` fast path (`substrate/frame/asset-rewards/src/lib.rs:790-792`), `update_pool_rewards` sets `last_update_block = E+k` (`substrate/frame/asset-rewards/src/lib.rs:780`), and `total_tokens_staked` becomes `1`.
3. Call `unstake(pool_id, 1, Some(attacker))` (permissionless post-expiry per `substrate/frame/asset-rewards/src/lib.rs:526`). `reward_per_token` now takes the calculation branch: `last_block_reward_applicable(E) = E`, then `E.ensure_sub(E+k)` underflows, propagating `Err(ArithmeticError::Underflow)` and failing the extrinsic.
4. Confirm every subsequent `stake`/`unstake`/`harvest_rewards` call on this `pool_id` fails identically, and `cleanup_pool`'s `ensure!(stakers.is_none(), Error::<T>::NonEmptyPool)` (`substrate/frame/asset-rewards/src/lib.rs:703-704`) permanently reverts, proving the pool's reward-asset balance and `PoolCost` deposit are stuck. This should be added as a unit test in `substrate/frame/asset-rewards/src/tests.rs`.

				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.

			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}
