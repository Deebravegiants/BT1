### Title
Webhook `shop`, `topic`, and `webhook-id` fields are trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by validating the HMAC over the raw request body, then hands the caller-supplied `shop`, `topic`, and `webhook_id` header values to the app's handler as trusted tenant metadata, even though none of those fields are part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are read directly from unauthenticated HTTP headers [3](#0-2) .

`Registry.process` validates only the body HMAC, then dispatches `request.shop` (and `topic`/`webhook_id`) straight to the app's handler as the identity of the merchant/tenant the payload belongs to: [4](#0-3) .

The binding that should hold is: `hmac == HMAC(secret, raw_body ++ shop ++ topic ++ webhook_id)`. In reality it is only `hmac == HMAC(secret, raw_body)`, i.e. `shop` (the value used downstream as the tenant key) is never part of what is verified. Since every shop that installs the same app shares the same `client_secret`/webhook signing secret, any merchant using the app can capture one legitimately-signed webhook body+HMAC delivered to their own shop, then replay it to the app's webhook endpoint with the `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header swapped to a different merchant's shop domain. The HMAC still validates because it never covered those headers, and `WebhookMetadata.new(shop: request.shop, ...)` hands the forged shop identity to the handler as if it were authentic [5](#0-4) .

### Impact Explanation
Any app built on this gem that uses `request.shop` from a processed webhook to select/update per-tenant records (the documented and expected usage pattern) can be made to attribute or apply another merchant's webhook data/actions under an attacker-chosen shop domain — a cross-tenant confusion/impersonation primitive, since the identity field the handler relies on for tenant scoping is not bound by the cryptographic check that is supposed to authenticate the message.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free/trial) installer of the same app so they receive at least one real webhook with a valid HMAC for their own shop — no access token, `client_secret`, or privileged account is needed. This satisfies the "unprivileged internet user" bar: the attacker just replays an HTTP POST with a modified header value.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them to the HMAC-covered payload), or have `Registry.process` independently verify that the `shop`/`topic` values match what the app expects/has on record for that installation before trusting them, rather than deriving tenant identity purely from unauthenticated headers.

### Proof of Concept
1. App installs on Shop A and Shop B, both served by the same app/`client_secret`.
2. Shop A's owner (attacker) receives a legitimate webhook: raw body `B`, headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`, where `H = HMAC(secret, B)`.
3. Attacker POSTs the same body `B` and same `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `HmacValidator.validate` passes because it only checks `HMAC(secret, B) == H` [6](#0-5) .
5. `Registry.process` calls the handler with `shop: "shop-b.myshopify.com"` and body `B`, even though `B` was never actually sent by/for Shop B [5](#0-4) .
