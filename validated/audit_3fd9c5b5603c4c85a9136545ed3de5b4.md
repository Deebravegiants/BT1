Audit Report

## Title
Unprivileged users can hijack another user's WebAPI trigger response via `MessageID` collision in the gateway's legacy handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` stores each pending callback in a handler-wide `savedCallbacks` map keyed solely by the caller-supplied `msg.Body.MessageID`, without checking for an existing/in-flight entry before overwriting it. Because `MessageID` is only length/format-validated (not checked for uniqueness) in `Message.Validate()`, and any client can sign a message with their own key to reach this handler, an attacker can choose a `MessageID` that collides with another concurrently in-flight request and capture or clobber that request's callback slot.

## Finding Description
`HandleLegacyUserMessage` unconditionally writes to the shared map: [1](#0-0) 

There is no existence/duplicate check prior to this write, unlike the sibling handlers that explicitly guard against ID collisions/replays: `confidentialrelay`'s `HandleJSONRPCUserMessage`/`newActiveRequest` rejects empty/oversized IDs and (per the claim) duplicate in-flight IDs, and `v2/http_trigger_handler.go`'s `setupCallback` explicitly rejects a duplicate `requestID`: [2](#0-1) 

The node-response dispatch path matches purely on `MessageID` and delivers to whatever callback currently occupies that slot: [3](#0-2) 

Crucially, `Message.Validate()` — the only validation function applied to inbound `api.Message` values — checks `MessageID` for length and null-suffix only; it never checks uniqueness or binds `MessageID` to sender identity beyond extracting `Sender` from the signature for informational/audit purposes: [4](#0-3) 

The code even contains an explicit `TODO: apply allowlist and rate-limiting here` at the point `HandleLegacyUserMessage` processes the method, confirming that, in the current codebase, this legacy trigger path performs no allowlist gating before accepting and storing the callback under the attacker-chosen `MessageID`: [5](#0-4) 

This confirms the reported root cause: the map key is attacker-controlled, uniqueness is never enforced, and the existing signature check only proves who signed the message — it does not prevent one legitimately-signed sender from choosing a `MessageID` that collides with a different, concurrently in-flight sender's `MessageID`.

## Impact Explanation
An attacker who can submit a validly signed legacy WebAPI trigger request (a standard, unprivileged capability — signing only proves the attacker's own identity, not any special role) can overwrite `h.savedCallbacks[MessageID]` for an in-flight `MessageID` belonging to another user. The next node response for that `MessageID` is delivered to whichever callback is currently registered, per `handleWebAPITriggerMessage`. This yields cross-user response confusion: the attacker can potentially receive a victim's trigger response payload, or cause the victim's expected callback to be dropped/overwritten — matching the "gateway request impersonation / cross-user response corruption" impact class.

## Likelihood Explanation
Exploitation requires only that the attacker's own signed request use a `MessageID` equal to another concurrently in-flight request's `MessageID`, within the `defaultCallbackMaxAgeSec` (120s) window. Since `MessageID` is entirely caller-chosen and only length-validated, and no per-sender/session namespacing or duplicate-ID rejection exists in this handler (unlike its sibling handlers), this is straightforward to trigger deliberately by an attacker who can predict or coordinate a victim's `MessageID` (e.g., if `MessageID`s are timestamps, sequence numbers, or otherwise predictable client-side values), or simply by racing many requests with the same `MessageID` guess against a target DON.

## Recommendation
- In `HandleLegacyUserMessage`, reject the request if `h.savedCallbacks[msg.Body.MessageID]` already exists, mirroring `httpTriggerHandler.setupCallback`'s duplicate-ID rejection.
- Bind saved callback entries to sender identity (e.g., key on `(Sender, MessageID)` rather than `MessageID` alone) so that only the original signer's response can satisfy an in-flight callback.
- Implement the allowlist/rate-limiting noted in the existing `TODO` to reduce the attack surface for unprivileged submission.

## Proof of Concept
1. Victim submits a signed `HandleLegacyUserMessage` request with `MessageID = "X"`, which is stored at `h.savedCallbacks["X"]` (`handler.go:411-414`).
2. Before the DON responds, attacker submits their own validly signed request also using `MessageID = "X"`, overwriting `h.savedCallbacks["X"]` with the attacker's callback.
3. When a node response for `MessageID = "X"` arrives, `handleWebAPITriggerMessage` (`handler.go:148-162`) delivers it to whichever callback currently occupies the map slot — the attacker's — rather than the victim's, regardless of which request the node was actually answering.
4. A Go unit test extending `handler_test.go` can simulate two concurrent `HandleLegacyUserMessage` calls with identical `MessageID` values followed by one `HandleNodeMessage` response, and assert that the wrong callback receives the payload.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
