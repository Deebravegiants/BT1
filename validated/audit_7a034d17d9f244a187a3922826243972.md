### Title
Non-standard ERC20 tokens returning `false` instead of reverting bypass escrow-release checks in `IntentGatewayV2.withdraw()` and `SweepDust`, causing permanent loss of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron `IntentGatewayV2` contract uses a raw low-level `.call()` with `IERC20.transfer.selector` to pay out escrowed tokens in `withdraw()` and `onAccept`'s `SweepDust` branch, checking only that the call did not revert (`success`), without decoding and validating the ERC20's returned boolean. Tokens that signal failure by returning `false` rather than reverting will pass this check, causing the gateway to mark escrow as redeemed/refunded and permanently write off the balance, while the beneficiary never receives the tokens.

### Finding Description
In `withdraw()`, escrowed token payouts are performed as: [1](#0-0) 

and transaction fees are paid out the same way: [2](#0-1) 

The identical pattern is used for dust sweeping in `onAccept`: [3](#0-2) 

In all three cases, only the outer `success` flag of the low-level `.call()` is checked. Per EVM semantics, `success` is `true` as long as the call itself does not revert — it says nothing about the returned `bool` value that ERC20's `transfer` is supposed to return. Standard-compliant tokens that follow OpenZeppelin's convention will revert on failure, so the check happens to work for them, but any ERC20 (or ERC20-like token deployed on Tron, which is what this contract explicitly targets — `@dev Implements the IntentGatewayV2 contract for Tron` [4](#0-3) ) that instead returns `false` on failure (e.g., insufficient balance in a non-reverting implementation, paused/blacklisted transfers, or a token contract with a bug) will make the `.call()` succeed while the actual transfer fails silently.

This is precisely the bug class described in the referenced report: use of raw `transfer`/`transferFrom` (or, here, a raw `call` wrapping it) without validating the ERC20 return value, instead of `safeTransfer`/`safeTransferFrom`. Notably, the sibling EVM contract `evm/src/apps/IntentGatewayV2.sol` and the Tron contract's own input-collection path both correctly use OpenZeppelin's `SafeERC20.safeTransferFrom` [5](#0-4) , and the file even imports `SafeERC20` [6](#0-5) , but the payout paths in `withdraw()` and `SweepDust` were written with a bespoke unchecked raw call instead.

### Impact Explanation
`withdraw()` is invoked from `onAccept` when Hyperbridge delivers an authenticated `RedeemEscrow` or `RefundEscrow` request — a normal part of the cross-chain intent settlement flow driven by a relayer delivering a legitimately dispatched ISMP message: [7](#0-6) 

If the escrowed token silently fails the payout, `withdraw()` still proceeds to decrement `_orders[body.commitment][token]` to zero and mark `_filled[body.commitment] = beneficiary`, emitting `EscrowReleased`/`EscrowRefunded` [8](#0-7) . The order is now considered settled and can never be retried, while the tokens remain stuck in the gateway contract and the beneficiary/solver/user permanently loses the funds they were owed. This is a concrete, permanent freezing/loss of escrowed user funds reachable without any privileged action — only a standard intent fill/refund settlement using a non-standard token.

### Likelihood Explanation
Exploitability depends on the specific ERC20 token used as an order input/fee token being one that returns `false` instead of reverting on failure — a known and common pattern among real-world tokens (especially relevant here since the contract is explicitly built to interoperate with Tron-style token semantics). Any market maker/solver/user selecting such a token as an escrow asset, or a token entering a failure state (paused, blacklisted address, insufficient balance edge case) during the settlement window, triggers the bug without any attacker action.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()` (lines ~706, ~720) and in the `SweepDust` handler (line ~674) with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the `SafeERC20` usage already present elsewhere in this same file (`safeTransferFrom` at line 459) and in the main EVM `IntentGatewayV2.sol`. `safeTransfer` correctly reverts on both a failing call and a call that succeeds but returns `false`.

### Proof of Concept
1. A user places an order via `placeOrder` with an ERC20 input token whose `transfer` implementation returns `false` on failure instead of reverting (or the token later enters a state — e.g., paused/blacklisted recipient — where it does so).
2. Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` POST request to `onAccept`, which calls `withdraw(body, isRefund)`.
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call itself doesn't revert) but the token internally returns `false` and does not move any balance.
4. Because only `success` is checked, execution continues: `_orders[body.commitment][token] -= amount` zeroes the escrow entry, `_filled[body.commitment] = beneficiary` is set, and `EscrowReleased`/`EscrowRefunded` is emitted.
5. The beneficiary never receives the tokens, the order can never be retried (marked filled), and the tokens remain permanently locked in the `IntentGatewayV2` contract.
