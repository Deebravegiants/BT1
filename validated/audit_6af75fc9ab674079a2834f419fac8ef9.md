### Title
Webhook shop-domain (and topic) header is trusted for tenant identification without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the `shop` (and `topic`) values taken from unauthenticated HTTP headers to build the `WebhookMetadata` passed to the app's handler. Since the HMAC only binds the body, any party capable of obtaining one genuinely-signed webhook body+HMAC pair from Shopify (e.g., by installing the app on their own store and receiving a real webhook) can replay that same body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the handler to process the payload as if it originated from a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` includes `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body` — headers such as `shop-domain`, `topic`, `webhook-id`, and `api-version` are explicitly excluded from the signable content: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac-sha256` header value: [4](#0-3) 

`Registry.process` gates only on this body HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unauthenticated fields) to construct the metadata delivered to the app's handler: [5](#0-4) 

`WebhookMetadata.shop` is a plain `String` field with no cross-check against the HMAC-covered body: [6](#0-5) 

The equality being broken: the gem treats **"HMAC-verified sender" == "shop identified in the `shop-domain` header"**, but the HMAC only proves the *body* bytes were produced by holder of `api_secret_key` for *some* webhook delivery — it proves nothing about which shop that delivery was for, since `shop-domain` is never included in `to_signable_string`. All webhooks for a given app share the same `client_secret`/`api_secret_key`, so a valid HMAC from shop A's webhook does not bind to shop A specifically.

### Impact Explanation
Because merchant tenant attribution (`data.shop` in `WebhookMetadata`) is derived entirely from an unauthenticated header while only the body is cryptographically verified, an attacker who operates their own store with the vulnerable app installed can:
1. Receive a legitimately HMAC-signed webhook from Shopify for their own shop (body + `x-shopify-hmac-sha256` + `x-shopify-topic`).
2. Replay that exact body and HMAC to the app's webhook endpoint, changing only the `x-shopify-shop-domain` header to a victim shop's domain (and optionally `x-shopify-topic` to trigger a different registered handler, since `topic` is also unauthenticated).
3. `Registry.process` passes HMAC validation (body/HMAC pair is genuine) and invokes the app's handler with `shop: <victim-shop>`, causing the app to perform shop-scoped side effects (e.g., data writes, GDPR compliance actions such as `customers/redact`/`shop/redact`, order/customer state changes) attributed to the wrong tenant.

This is a cross-tenant identity-binding break: it lets an unprivileged party (any merchant who installs the app) inject data or trigger business logic under the identity of a different shop, without ever obtaining that shop's access token or the app's `client_secret`. This matches the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Requires only that the attacker install the app on their own shop (a normal, unprivileged action for any merchant) to obtain a legitimate body+HMAC pair, and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with forged headers — no access token, `client_secret`, or privileged access is needed. Actual exploitability depends on whether the receiving application (via `Registry.process`) trusts `WebhookMetadata.shop`/`topic` for authorization or tenant-scoped writes without independent cross-validation, which is the documented and expected usage pattern of this API (`handler.handle(data: WebhookMetadata.new(...))`).

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the payload), so that the HMAC proves both the payload contents and the shop/topic association together, rather than only the raw body. At minimum, document that consuming applications must not trust the header-derived `shop`/`topic` fields as authoritative tenant identifiers unless they are also present and verified inside the signed body.

### Proof of Concept
1. App has webhooks registered; attacker installs the app on `attacker-shop.myshopify.com` and Shopify sends a real webhook: body `{"id":123,...}`, header `x-shopify-hmac-sha256: <valid-hmac-for-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: customers/redact`.
2. Attacker POSTs the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally (headers aren't validated for consistency with body) — see constructor at [7](#0-6) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds because the body is unmodified: [8](#0-7) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to act as though the (attacker-controlled) payload came from `victim-shop.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
