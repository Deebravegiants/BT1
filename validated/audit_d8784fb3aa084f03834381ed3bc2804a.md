### Title
Missing shop-domain format validation in OAuth callback allows the app's `client_secret` to be POSTed to an attacker-influenced host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` and `ShopifyAPI::Auth::Oauth.begin_auth` use the raw `shop` value to build the host that later receives the app's `client_id`/`client_secret` during the access-token exchange, without ever passing it through `Utils::ShopValidator`. Every other credential-bearing flow in this gem (`RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using `shop` to build the request host. `Oauth` is the odd one out, breaking the intended identity binding: *"the shop verified by HMAC" should equal "the shop whose domain format is confirmed safe to receive client_secret."*

### Finding Description
`Utils::HmacValidator.validate` only proves that the query parameters (including `shop`) match a signature computed with `api_secret_key`; it performs no validation of the `shop` value's format: [1](#0-0) 

`AuthQuery#to_signable_string` simply serializes `shop` as one of the signed fields — it never constrains `shop` to a `*.myshopify.com` pattern: [2](#0-1) 

In `Oauth.validate_auth_callback`, after the HMAC check passes, the unsanitized `auth_query.shop` is used directly to build a `null_session` whose `shop` determines the host that the HTTP client posts the app's `client_id`/`client_secret`/authorization `code` to: [3](#0-2) 

`auth_base_uri` builds the request URL straight from that `shop` string with no domain-format check: [4](#0-3) 

`Oauth.begin_auth` has the same gap — the caller-supplied `shop` is used unchecked to build the authorize redirect URL: [5](#0-4) 

By contrast, the other two credential-exchange call sites in this gem explicitly enforce that `shop` is a real Shopify domain before it is used to construct the request host: [6](#0-5) 
and this is verified by an explicit rejection test: [7](#0-6) 

No equivalent test or check exists for `Oauth.begin_auth` / `Oauth.validate_auth_callback` — the full `oauth_test.rb` suite covers HMAC/state/session behaviour but never asserts a non-Shopify `shop` is rejected: [8](#0-7) 

This is analogous to the reported bug class: a field (`shop`) is *acted upon* (used to choose the host that receives the secret) but the enforcement that binds it to a legitimate identity (a real `*.myshopify.com` domain) is missing, exactly as the `selectedApplications` arrays were checked for signature/format validity but never actually enforced against the applications acted upon.

### Impact Explanation
If a value for `shop`/`auth_query.shop` that is not a genuine `*.myshopify.com` domain reaches `validate_auth_callback` (e.g., because the host application passes through query parameters it received, or because Shopify's HMAC only certifies parameter integrity but not domain shape), the gem will POST the app's `client_id` and `client_secret` — its most sensitive credential — to whatever host string ends up in `shop`. This matches the report's High-impact category: "SSRF with the app's credentials" / "credential leakage." Because the destination host is entirely attacker-influenced text with no allowlist/regex enforcement inside this gem, this is a root-cause gap in the library itself, not a host-application misuse of the documented API.

### Likelihood Explanation
Reaching this code path still requires a query that passes the `Utils::HmacValidator.validate` check, which normally means it was signed by Shopify. However, the HMAC only certifies that the parameter *values* were not tampered with — it says nothing about whether `shop` conforms to the expected domain shape. Any legitimate flow that can cause Shopify (or a compromised/malicious partner integration) to sign a callback containing a non-standard `shop` value — or any host application forwarding attacker-controlled `shop` into `begin_auth`/`validate_auth_callback` without pre-validation, which the library does nothing to prevent or even document as required — will trigger the credential exfiltration. The gem's own inconsistency (validating `shop` in `RefreshToken`/`TokenExchange.migrate_to_expiring_token` but not in `Oauth`) shows the maintainers recognize this is a required control that was simply omitted for the OAuth callback/begin flows.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or equivalent strict `*.myshopify.com` format validation) on `shop` in `Oauth.begin_auth` before constructing `auth_route`, and on `auth_query.shop` in `Oauth.validate_auth_callback` before it is used to build `null_session`/`auth_base_uri`, mirroring the existing checks in `RefreshToken.refresh_access_token` and `TokenExchange.migrate_to_expiring_token`. Reject the request with `Errors::InvalidShopError` if validation fails, before any network call carrying `client_secret` is made.

### Proof of Concept
1. A host application calls `ShopifyAPI::Auth::Oauth.validate_auth_callback` with an `AuthQuery` whose `shop` field is set to a non-Shopify host that still HMAC-validates (e.g., because the application constructs/re-signs the query internally, or forwards an externally supplied callback without additional checks — behavior the gem neither prevents nor validates against).
2. `Utils::HmacValidator.validate(auth_query)` succeeds because it only checks the signature over the given fields, including the attacker-influenced `shop` string — see [1](#0-0) .
3. `auth_base_uri(shop)` returns `"https://#{shop}/admin"` unchanged — see [4](#0-3) .
4. `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` then POSTs `{client_id, client_secret, code, expiring}` to `https://#{shop}/admin/oauth/access_token`, sending the app's `client_secret` to the attacker-influenced host — see [9](#0-8) .

Note: I was unable to fully trace whether current versions of Shopify's own `/admin/oauth/authorize` endpoint would ever sign a callback with a non-`myshopify.com` `shop` value (that would require behavior outside this repository/gem to confirm), so likelihood should be validated by testing against the live OAuth flow; the root-cause gap (missing `ShopValidator` call inside this gem, unlike its sibling flows) is confirmed directly from the source.

            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)

          unless Context.setup?

          end

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
