### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" [1](#0-0)  before invoking the app's handler with a `WebhookMetadata` object whose `shop` field is documented as "The shop domain of the webhook" [2](#0-1) . In reality, the only cryptographic check performed is `Utils::HmacValidator.validate(request)`, and the `shop` value is taken directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never part of the signed material.

### Finding Description
`Registry.process` validates a webhook exclusively via HMAC over the raw body, then immediately trusts `request.shop`, `request.topic`, etc., when constructing `WebhookMetadata` for the app's handler: [3](#0-2) 

`Webhooks::Request#hmac` and `#to_signable_string` only ever reference `@raw_body`; `#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from unauthenticated headers: [4](#0-3) [5](#0-4) 

`Utils::HmacValidator.validate` computes the HMAC using `Context.api_secret_key`, which is a single **app-wide** secret shared across every shop that installs the app — it is not shop-specific: [6](#0-5) 

The identity binding that should hold is:
`shop asserted to the handler == shop that actually generated/authorized the signed body`

Because the header carrying `shop` is entirely outside the HMAC's signable string, and the HMAC secret is shared across all tenants of the app, this equality is never enforced. Any actor who can obtain one genuine, HMAC-valid webhook body from the app (e.g., by installing the app on their own store — an action available to any unprivileged internet user/merchant) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different (victim) shop. `HmacValidator.validate` will still succeed, because it only checks `raw_body` against the shared secret — it never checks that `shop` matches whichever shop actually owns that payload. The registered handler then receives `WebhookMetadata` with `shop` set to the attacker-chosen victim domain and `body` set to attacker-controlled content, breaking the shop/tenant identity guarantee the docs imply ("verify the request did indeed come from Shopify").

### Impact Explanation
Apps built on this gem commonly key persistence, background jobs, and business logic off `data.shop` (as shown in the gem's own documented handler example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [7](#0-6) ). An attacker who legitimately installs the app on their own store can generate a valid HMAC for a body of their choosing (subject to what Shopify sends, but content like order fields is attacker-influenced) and then relabel it as belonging to any other shop domain string, causing the target app to write, process, or act on forged data under a victim tenant's identity — a cross-tenant integrity/isolation break with no dependency on the victim's credentials, matching the Critical "cross-tenant access" bucket.

### Likelihood Explanation
Exploitation requires only: (1) becoming a merchant/app-installer (trivial, unprivileged), (2) capturing one legitimate webhook delivery and its `x-shopify-hmac-sha256` header, and (3) POSTing the identical raw body to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. No secrets, tokens, or elevated access are needed, making this practically reachable by any internet user who can install the target app.

### Recommendation
Do not treat `shop` (or `topic`/`webhook_id`) sourced purely from headers as trusted merely because the body's HMAC validated. Options: bind `shop` into the signature verification (e.g., cross-check against a shop-specific secret/session, or require the caller to supply an expected shop and reject mismatches against server-side webhook registration records), or explicitly document that `data.shop` is unauthenticated and must be independently verified by the host app before use in tenant-sensitive operations.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store (`attacker-shop.myshopify.com`), triggering a legitimate webhook (e.g., `orders/create`) to the app's public webhook endpoint.
2. Capture the raw POST body and the `x-shopify-hmac-sha256` header value from that legitimate delivery.
3. Replay an HTTP POST to the same endpoint with the identical raw body and HMAC header, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` against the shared `Context.api_secret_key` — validation succeeds. `Registry.process` then invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...)` [3](#0-2) , causing the victim shop's data/workflow to be manipulated using attacker-controlled webhook content.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
