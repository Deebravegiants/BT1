### Title
Webhook Shop Attribution Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant) attribute used downstream for all business logic is taken from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` when constructing the `WebhookMetadata` passed to the app's handler. This breaks the identity binding: `shop covered by HMAC == shop used to process the webhook`. An attacker who owns any Shopify development/test store can capture a genuinely-signed webhook for their own shop and replay it to the victim app's endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop, and the library will accept it as valid and hand the (attacker-controlled) body to the handler under the victim's shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relation to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`, i.e. only the body, and knows nothing about the shop header: [3](#0-2) 

`Registry.process` checks only that HMAC validation passes, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because the HMAC only proves the *body bytes* were signed with the app's shared `api_secret_key` (i.e., they came from Shopify for *some* shop using this app), it does not prove that the accompanying `shop-domain` header is the shop that body actually pertains to. The equality the code implicitly (and incorrectly) assumes is:

```
shop bound by HMAC signature == shop used for handler dispatch (request.shop)
```

In reality:
```
shop bound by HMAC signature = <nothing, HMAC only signs body>
shop used for handler dispatch = unauthenticated header value
```

### Impact Explanation
This is a cross-tenant confusion vector: an unprivileged internet user who has installed the app on their own (attacker-controlled) shop can receive a legitimately Shopify-signed webhook for their own store, then replay the identical body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header to a victim's shop domain. `Registry.process` will accept the request as authentic (HMAC still validates, since it never covered the header) and invoke the app's registered handler with `WebhookMetadata(shop: <victim shop>, body: <attacker's own webhook body>)`. Depending on how the host application implements its handler (e.g., updating per-shop order/customer records, triggering per-shop side effects, looking up sessions/tokens keyed by `shop`), this can let an attacker inject fabricated events attributed to a shop they do not control — a cross-tenant integrity violation attributable directly to a gap in this library's identity binding, not to host misuse of a documented API.

### Likelihood Explanation
The only capability an attacker needs is the ability to install/operate their own Shopify development store and trigger any webhook topic the target app subscribes to (this is default, low-privilege, unauthenticated-relative-to-the-victim tenant access). No access to the app's `client_secret`, no compromised account, and no victim credentials are required — only the ability to intercept/replay their own legitimately-received webhook HTTP request with one header value changed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-covered signable string, or otherwise cryptographically tie the shop attribution to the verified payload — e.g., include the `shop-domain` header value as part of `to_signable_string` in `ShopifyAPI::Webhooks::Request`, so `HmacValidator.validate` fails if the header is altered relative to the value Shopify actually signed for. At minimum, document/enforce that host applications must independently correlate `request.shop` against a shop the app knows to have this specific webhook subscription/session before trusting the payload.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g., `orders/create`), receiving a POST with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared `client_secret`.
2. Attacker replays the exact same body/HMAC to the same app endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(body, secret)` — unaffected by the header change. [5](#0-4) 
   - `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` is built with `shop = "victim-shop.myshopify.com"` even though the body content and signature originate from the attacker's own shop.
4. The app's handler processes attacker-controlled data as if it were sent by `victim-shop.myshopify.com`, producing cross-tenant data confusion.

          received_signature = verifiable_query.hmac
