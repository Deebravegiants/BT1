### Title
Accrued debt valuation can permanently freeze a market after `i128` overflow - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
Interest accrual computes `borrowed_scaled * borrow_index` and panics when the resulting RAY-denominated debt exceeds `i128::MAX`. Because every state-changing pool operation synchronizes interest before executing, an attacker who creates sufficiently large scaled debt can trigger one accrual that leaves the market permanently unable to repay, withdraw, liquidate, or clean bad debt. [1](#0-0) 

### Finding Description
Pool positions store debt as scaled `Ray` shares, while their current value is recovered by multiplying those shares by the borrow index. During accrual, `calculate_supplier_rewards` evaluates both `borrowed * old_borrow_index` and `borrowed * new_borrow_index`; the fixed-point multiplication widens intermediate multiplication to `I256`, but still rejects any quotient that cannot fit back into `i128`. [2](#0-1) [3](#0-2) 

`update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, but it does not cap the paired `borrowed * index` result. A market can therefore contain debt shares that fit `i128` individually while the debt's RAY value no longer fits once the index grows. The documented numeric boundary also confirms that accrued market values can overflow before the index ceiling and block repayment or withdrawal because those operations accrue first. [4](#0-3) [5](#0-4) 

The unprivileged trigger is:

```text
controller.update_indexes(caller, assets = [hub_asset])
```

`update_indexes` only requires caller authorization and then invokes the pool's index update. [6](#0-5)  The pool's `global_sync` calls `accrue_chunk`, which calls the overflowing `accrue_step` calculation before committing new indexes. [7](#0-6) 

### Impact Explanation
This can permanently freeze a market's user funds. Once `borrowed_scaled * borrow_index` exceeds `i128::MAX`, accrual panics before any later operation-specific logic runs. Consequently, borrowers cannot repay, suppliers cannot withdraw, liquidations and bad-debt cleanup cannot proceed through their normal pool paths, and cash already held by the market remains inaccessible. Debt can become frozen even though every stored field remains a valid `i128`, because the overflow occurs only in their product.

This is not merely a transaction-level bounds check rejecting malicious input: the protocol admits scaled positions and indexes that are individually representable, then makes future operation dependent on a product that is not representable.

### Likelihood Explanation
The condition requires a very large market near the protocol's arithmetic boundary. For an index near `1e9 * RAY`, scaled debt only needs to exceed approximately `i128::MAX / 1e9` before the next valuation overflows. The protocol explicitly allows asset-unit inputs up to roughly `i128::MAX / 10^(27-d)`, and valid caps plus bounded indexes do not prevent accrued values from crossing the `i128` boundary. [8](#0-7) 

A single unprivileged account can attempt to create the required debt through ordinary `borrow` when configured caps, collateral value, and pool liquidity permit a position near that boundary. After the debt exists, any address can trigger the fatal accrual through `update_indexes`. Liquidity and collateral requirements reduce practical likelihood, but the accepted impact is permanent freezing rather than a short-lived denial of service.

### Recommendation
Do not represent total accrued debt or supplied value in a type narrower than the intermediate valuation domain when the index ceiling permits overflow. At minimum:

- bound admitted scaled supply and debt to `i128::MAX / MAX_*_INDEX_RAY`, not merely to the token input domain;
- keep accrued totals in `I256` or another wider representation until they are scaled down;
- reject or cap the position before `scaled * index` can exceed `i128::MAX`;
- make the cap and risk checks evaluate the same widened debt value used by accrual;
- add regression tests for `borrowed_scaled > i128::MAX / MAX_BORROW_INDEX_RAY` and prove that repay, withdraw, liquidation, and bad-debt paths remain executable.

If the intended protocol limit is lower, enforce it directly at borrow and supply admission rather than relying on checked arithmetic to panic after accrual.

### Proof of Concept
Conceptually, use an 18-decimal asset and a market whose borrow index is already above one `RAY`:

```text
borrowed_scaled > i128::MAX / borrow_index
```

1. Supply enough collateral through the normal `supply` path.
2. Borrow the asset through `borrow` until its scaled debt exceeds `i128::MAX / new_borrow_index`. The scaled debt itself still fits `i128`.
3. Advance ledger time so the next accrual raises the borrow index.
4. Call:

```text
controller.update_indexes(attacker, [hub_asset])
```

5. `global_sync` reaches `calculate_supplier_rewards`; `borrowed * new_borrow_index` returns no representable `i128` and panics with `MathOverflow`.
6. Repeat `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, or `update_indexes`. Each path performs the same accrual precondition and panics before users can change the oversized scaled debt.

The exact amount depends on the asset's decimals and current index. With `MAX_BORROW_INDEX_RAY = 1e9 * RAY`, the unsafe scaled-debt threshold is approximately `1.7014e29` RAY shares; any larger scaled debt can fail valuation at the index ceiling.

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
