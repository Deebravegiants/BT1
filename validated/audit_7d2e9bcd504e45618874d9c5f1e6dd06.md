Look at `ShopifyAPI::Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`):

- `to_signable_string` returns only `@raw_body` [1](#0-0) .
- `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, completely outside the HMAC-covered bytes [2](#0-1) .
- `Registry.process` validates `Utils::HmacValidator.validate(request)` (which only checks the HMAC over `raw_body`) and then hands `request.shop` directly to the app's handler as `WebhookMetadata.shop`, with no additional check that the header matches any signed value [3](#0-2) .

Since the HMAC is computed only over the raw body (this matches Shopify's real webhook HMAC scheme — the shop domain is never part of the signed payload), an attacker who can produce *any* valid HMAC for a chosen body (e.g., by replaying/forwarding a legitimate webhook delivery, or if the raw body is attacker-influenced/predictable, e.g. an empty-body webhook like `app/uninstalled` with no meaningful content) can freely set the `shop-domain` header to any value while `Utils::HmacValidator.validate` still passes, since it never binds `shop` to the signature.

However, I want to flag a caveat before finalizing: exploiting this still requires possession of a validly-signed `(topic, hmac, body)` tuple for *some* shop — the attacker cannot forge the HMAC without the `api_secret_key`. The realistic risk is **webhook shop-spoofing via replay**: an attacker who captures/replays one legitimate webhook delivery (e.g., their own store's `app/uninstalled` or any webhook with a fixed/predictable empty body `{}`) can resend it with an arbitrary `x-shopify-shop-domain` header, since the HMAC never binds to the shop. This is a genuine identity-binding gap in the gem's own `Utils::HmacValidator`/`Webhooks::Request` design (`to_signable_string` excludes shop), not a host-application misuse issue — this is exactly analogous to H-6's root cause (a field acted upon that isn't part of the verified/bound set).

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling shop spoofing on replayed/predictable-body webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `#shop` is read from the unauthenticated `shop-domain` header. `Webhooks::Registry.process` validates the HMAC over the body only and then passes the header-derived `shop` straight through to the app's webhook handler, so the identity binding "HMAC signature ⇔ shop that generated it" does not hold — the shop value is never covered by the signature.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it (constant-time) to the received HMAC [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , and `shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) .

`Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)` (body-only HMAC) before dispatching to the handler with `request.shop` taken verbatim from the header [3](#0-2) . There is no check that binds the `shop-domain` header value to anything cryptographically verified. Concretely, the equality that should hold — `shop bound in signature == shop delivered to handler` — is broken because the signature binds only `raw_body`, not `shop`.

This means any request whose body an attacker can reproduce with a matching, previously-observed valid HMAC (e.g., a captured/replayed webhook delivery with a fixed or empty body such as `{}`, or any two shops emitting byte-identical payloads) can be resent with an arbitrary `shop-domain` header and will pass HMAC validation, causing the handler to process it as if it originated from a different, attacker-chosen tenant.

### Impact Explanation
This crosses the "cross-tenant access" boundary called out as Critical impact: an app's webhook handler that trusts `WebhookMetadata#shop` (very common — used to look up the correct merchant record/session before acting on `body`) can be tricked into attributing a replayed/crafted webhook to any `shop` value chosen by the attacker, since the gem provides no verification linking the header-derived `shop` to the HMAC-verified bytes.

### Likelihood Explanation
Exploitation requires the attacker to already have a validly HMAC-signed payload for the exact same `raw_body` (obtained via capture of any legitimate delivery, e.g. their own store's webhook, or a shopify webhook with a fixed/predictable body). This is a moderate bar — no `api_secret_key` needs to be known or guessed, only a body/HMAC pair that was legitimately produced once — and Shopify does emit large numbers of small/near-fixed-body webhooks (e.g., `app/uninstalled`, some compliance topics) that make this practical for at least those payload shapes.

### Recommendation
Bind `shop` (and ideally `topic`) into the verified signable representation, or independently verify that the `shop-domain` header corresponds to a shop known to have installed the app (e.g., cross-check against stored sessions) before trusting `WebhookMetadata#shop`. At minimum, document that `Webhooks::Request#shop` is unauthenticated and must not be trusted for tenant identification without additional verification.

### Proof of Concept
1. Attacker's own development store receives a legitimate webhook delivery with body `{}` (e.g. `app/uninstalled`) and header `x-shopify-hmac-sha256: <valid HMAC of "{}">`.
2. Attacker resends this exact request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, "{}")` — identical to the original, valid signature — and passes [5](#0-4) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5)  and, if it trusts `shop` to select which merchant's data/session to act on, performs the action against the victim's tenant instead of the attacker's own.
