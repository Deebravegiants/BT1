## Title
Webhook `shop` (and `topic`) identity fields are trusted despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop` (and `topic`) values used downstream to attribute a webhook to a tenant are read from unauthenticated HTTP headers.

### Finding Description
`Utils::HmacValidator.validate` checks a `VerifiableQuery`'s HMAC against `to_signable_string`. For webhook requests, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are pulled straight out of the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the HMAC-signed material: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair, then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

This is exactly the identity-binding gap called out in the report class: a field (`shop`) that is *acted on* (used to attribute/route the webhook payload to a tenant) is *not covered by* the cryptographic check (`HMAC` over raw body only). Because the same `client_secret` signs webhooks for every shop installed on an app, the HMAC over the body alone does not bind the signature to a specific shop. An attacker who controls (or can capture) any validly-signed webhook body/HMAC pair for the app (e.g., from their own store's webhook deliveries, which they fully control as an unprivileged merchant/tester of the app) can resend that exact body+HMAC while substituting a different `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate(request)` will still pass because the check only re-derives the HMAC from `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop: [4](#0-3) 

If the host application (as documented/intended, using this gem's own `WebhookMetadata.shop`) uses that `shop` value to look up per-tenant records or index data, this breaks the equality `shop authenticated via HMAC == shop attributed to the payload`, letting one tenant's genuine, replayable webhook be relabeled as belonging to another tenant.

### Impact Explanation
This breaks the identity binding between a cryptographically-verified webhook body and the shop it is attributed to, enabling cross-tenant data injection/attribution through the gem's own webhook-processing API (`ShopifyAPI::Webhooks::Registry.process`) — not a host-application misuse of undocumented behavior. This matches the Critical "cross-tenant access" category since a validly-authenticated payload can be relabeled to a different tenant.

### Likelihood Explanation
Any user who can operate/install the app on their own store can capture a legitimately-signed webhook body/HMAC pair from Shopify (since the signature depends only on the body and the app's shared `client_secret`, not on shop/topic), and replay that exact HTTP body with a forged `x-shopify-shop-domain` header value to any endpoint that calls `Registry.process`. No access token or `api_secret_key` leakage is required — only observing one's own genuine webhook traffic.

### Recommendation
Include `shop` (and `topic`) in the HMAC-signed material — or otherwise independently verify the `x-shopify-shop-domain` header against a trusted, out-of-band source (e.g., matching it to the session used to look up the installation) before trusting `request.shop`/`WebhookMetadata#shop` for tenant attribution — instead of relying solely on the unauthenticated header value.

### Proof of Concept
1. Install the app on shop A (attacker-controlled) and receive a real webhook delivery, e.g. body `{"id":123}` with headers `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Replay the identical raw body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `shop-b.myshopify.com` (the victim tenant).
3. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `@raw_body`, per `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: {"id"=>123}, ...)`, causing shop A's payload to be processed as if it belonged to shop B.
