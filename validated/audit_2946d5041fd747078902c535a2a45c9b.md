## Title
`IntentGatewayV2.placeOrder` predispatch sweep credits caller based on `dispatcher`'s raw token balance instead of the amount actually deposited for that order, permanently trapping any residual/other-caller funds on the shared, permissionless `CallDispatcher` - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
This is the same root-cause pattern as the referenced Phuture `IndexLogic.mint` finding: crediting a user based on a contract's *observed token balance* rather than the *exact amount actually attributable to that user's own transfer*. In `IntentGatewayV2.placeOrder`'s predispatch branch, the gateway sweeps the entire ERC20 balance currently sitting on the shared `_params.dispatcher` contract, rather than only the amount the caller's own predispatch transfer produced.

### Finding Description
When an order carries `predispatch.call`/`predispatch.assets`, `placeOrder` first moves the caller's declared predispatch assets to the shared `dispatcher` contract, runs the caller-supplied `predispatch.call` via `ICallDispatcher(dispatcher).dispatch(...)`, and then sweeps input tokens off the dispatcher using its *live balance*, not the amount deposited in this call: [1](#0-0) 

```
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({
    to: token, value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
```

The full swept amount is transferred to the gateway; anything above the caller's own `order.inputs[i].amount` is emitted only as `DustCollected` and left stranded in the gateway's contract balance with no owner accounting: [2](#0-1) 

`_params.dispatcher` is `CallDispatcher`, a shared, stateless, **permissionless** relay with no access control on `dispatch`, no per-order isolation, and no reentrancy guard: [3](#0-2) 

Because the sweep is keyed off `balanceOf(dispatcher)` rather than a value returned/attributable strictly to the current transaction's transfer, any tokens left on the dispatcher from a different flow — e.g. a predispatch step that intentionally leaves tokens "just sitting" on the dispatcher (as the test suite itself demonstrates is a supported no-op pattern), or a partially-consumed unwrap call, or tokens sent to the dispatcher directly by any third party since `dispatch()` has no caller restriction — get swept into whichever `placeOrder` call happens to run next for that token. The excess is not credited to any commitment (only logged as dust), so the original owner of those funds permanently loses access to them, while the specific attacker who triggers this sweep with a same-token predispatch order pays no compensating transfer for that surplus.

### Impact Explanation
This is a permanent freezing/loss-of-funds bug reachable by a single unprivileged `placeOrder` call. Any residual balance sitting on the shared, permissionless `dispatcher` (belonging to another user, or accidentally left by an incomplete predispatch unwrap) is swept and becomes unrecoverable "dust" inside the gateway with no accounting or owner-recovery path in the reviewed contract, matching the report's "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood is moderate: it does not require any privileged role, only (a) a predispatch order routed through the shared `dispatcher`, and (b) any residual token balance existing on `dispatcher` at sweep time — a condition the codebase's own fee-on-transfer/no-op predispatch tests show is a normal, supported state ("the tokens just sit on the dispatcher"), and one that any third party can also create directly since `CallDispatcher.dispatch` and plain ERC20 `transfer` to the dispatcher are both unrestricted.

### Recommendation
Do not size the sweep off `IERC20(token).balanceOf(dispatcher)`. Instead, snapshot the dispatcher's balance for each input token immediately before the caller's own predispatch transfer/dispatch and take only the delta produced by this specific call (mirroring the pattern already used correctly in the non-predispatch branch, which measures `balanceOf(address(this))` before/after the caller's own `safeTransferFrom`). Any true residual/dust should be swept exclusively by a privileged, accounted-for admin function rather than opportunistically by the next caller.

### Proof of Concept
1. Token `T` ends up sitting on the shared `dispatcher` outside of the current caller's own predispatch transfer (e.g., a prior order's predispatch call intentionally left `T` unconsumed, as shown by `testPlaceOrder_FeeOnTransferToken_Predispatch`'s no-op predispatch pattern, or a third party sends `T` to `dispatcher` directly since `CallDispatcher.dispatch`/ERC20 transfers to it are unrestricted).
2. Attacker calls `placeOrder` with `predispatch.assets` containing a tiny amount of `T`, `predispatch.call` a no-op `Call[]`, and `order.inputs[0] = {token: T, amount: <small>}`.
3. In the sweep phase, `balance = IERC20(T).balanceOf(dispatcher)` includes the stray funds; `balance >= requiredAmount` passes trivially, and the *entire* balance is transferred to the gateway.
4. `received > order.inputs[0].amount` triggers the `DustCollected` branch: `order.inputs[0].amount` (and thus the escrow credited under the attacker's own commitment) stays at the small value the attacker chose, while the surplus (the stray funds) is now stuck in the gateway's own balance with no commitment or owner tracking it, permanently unavailable to whoever it belonged to. [4](#0-3)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
