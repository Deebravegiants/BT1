### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable bytes from the raw request body alone, while the `shop` (and `topic`) it exposes to the application come from separate, unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC validates and then unconditionally trusts `request.shop` when building `WebhookMetadata` for the handler. Because the tenant identity (`shop`) is never bound into the value that is cryptographically verified, an attacker who can obtain one genuine, HMAC-signed webhook body (trivially available by installing the app on their own shop) can replay that exact body to the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop. The signature still validates (it only ever checked the body), so the host application processes attacker-controlled data as if it belonged to another tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers that are never part of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and compares it against the `hmac` header using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` only checks this body-only HMAC, then immediately trusts `request.shop` (and `request.topic`) to build the metadata handed to the app's handler: [4](#0-3) 

This is the same class of defect described in the external report: an identity/authorization key (`shop`, analogous to `poolId`) is used by downstream logic (`WebhookMetadata`/handler dispatch, analogous to `Sleeves.adminSyncPools`) without being bound to the value that was actually verified (the HMAC, analogous to `tokenIdsToPoolIds`). The equality that should hold — `verified_bytes == bytes_the_application_acts_on` — is broken because `verified_bytes = raw_body` but `bytes_the_application_acts_on ⊇ {raw_body, shop_header, topic_header}`.

Notably, elsewhere in the same gem the OAuth callback path does bind `shop` into the signed content — `Auth::Oauth::AuthQuery` includes `shop` in the query hash that is HMAC-verified (see `test/auth/oauth_test.rb` construction of `@callback_hmac` over a hash that includes `shop:`) — showing the gem is capable of, and elsewhere does, bind tenant identity into the signature. The webhook path is the outlier that omits this binding.

### Impact Explanation
Any application that uses `ShopifyAPI::Webhooks::Registry.process` to route/attribute incoming webhook data per-shop (the intended and documented usage, since `WebhookMetadata#shop` is the field host apps use to attribute webhook data to a tenant) is exposed to cross-tenant data injection: an attacker with access to only their own shop's app installation can forge webhooks that the app will process as originating from a different, victim shop. This satisfies the Critical "cross-tenant access" impact category, since no credentials or access belonging to the victim shop are required — only a previously captured, legitimately-signed body from the attacker's own shop.

### Likelihood Explanation
Exploitation requires: (1) the attacker installs the target Shopify app on a shop they control (an ordinary, unprivileged action for any public app), (2) they trigger an event to receive one genuine webhook (body + HMAC) signed with the app's `client_secret`, and (3) they replay that exact body to the app's public webhook endpoint with a modified `shop-domain` header. All three steps require no privileged access, secrets, or social engineering — only the ability to install the app once and know the app's public webhook URL, which is standard for public/embedded Shopify apps.

### Recommendation
Bind the tenant identity into the cryptographic verification, mirroring the fix pattern in the report (do not let a downstream lookup/attribution rely on unverified data). Concretely, either:
- Reject/flag processing when the `shop-domain` header cannot be independently confirmed against session/install-state fetched via a value that is bound to the HMAC (e.g., include `shop` and `topic` headers in the signed payload construction if Shopify's channel allows it), or
- At minimum, require host applications (and document this loudly) to cross-check `request.shop` against an already-known, previously-registered shop/session before trusting `WebhookMetadata#shop`, since the current API surface implies the `shop` field is trustworthy once `Registry.process` succeeds.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event (e.g., updates an order) so Shopify sends a webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(client_secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` (they own the receiving endpoint's traffic path or the app echoes data back).
4. Attacker sends a new POST to the same webhook endpoint with the identical body `B` and identical header `H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and finds it equal to `H` — validation passes, since the shop header is not part of `to_signable_string` — see: [1](#0-0) 
6. `Registry.process` dispatches the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com`, even though the body content and true origin belong to the attacker's own shop: [5](#0-4) 
7. The host application persists/acts on this attacker-controlled payload under the victim tenant's identity.
