## Title
Webhook `shop-domain` (and topic/api-version) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are excluded from the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct, then blindly trusts the `shop` header when dispatching to the app's handler. Since the same `api_secret_key` is used to sign webhooks for every shop installed on the app, a body+HMAC pair that is valid for one (attacker-controlled) shop remains cryptographically valid when replayed with a different shop's identity in the header.

### Finding Description
`ShopifyAPI::Webhooks::Request` binds only the raw bytes of the body to the HMAC: [1](#0-0) 

`shop`, `topic`, `api_version` and `webhook_id` are pulled straight from attacker-controllable HTTP headers and are never part of `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` (the raw body) and compares it with the supplied `hmac`: [3](#0-2) 

`Registry.process` uses this same validator, and after a successful check it forwards the **unverified** `request.shop` value straight to the app's webhook handler as the tenant identity: [4](#0-3) 

The identity binding that should hold is:

`shop that receives credentials/actions == shop whose signature was actually verified`

But what is actually verified is only:

`hmac(raw_body, api_secret_key) == received_hmac`

`shop` is a completely independent, unauthenticated field. Because `api_secret_key` is a single shared per-app secret (not per-shop), any shop that has the app installed can obtain a body+HMAC pair that is valid under the app's secret (e.g., by triggering a webhook for their own store, whose body content they control to varying degrees depending on topic — e.g. `app/uninstalled`, `customers/update`, `shop/redact`, etc.). That attacker can then replay the exact same body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with any victim shop's domain. The HMAC check still passes because it never examined the shop header, and `Registry.process` dispatches the handler with `shop: <victim-shop>`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an unprivileged party (any merchant who can install the public app on their own store, or anyone who can replay a captured webhook) can make the app process attacker-supplied webhook data under a false shop identity. Depending on how the consuming app implements handlers (a normal, documented usage pattern per `docs/usage/webhooks.md`), this can lead to actions being taken against a different tenant's data/session (e.g. spoofing `app/uninstalled` to trigger revocation/deletion logic for a victim shop, or `shop/redact`/`customers/redact` compliance webhooks executing data deletion against the wrong shop, or generic webhook bodies being attributed to a shop that never sent them). This is a cross-tenant identity-binding bypass consistent with the Critical "cross-tenant access" impact category, since it lets one tenant impersonate another purely by exploiting the fact that the identity field is transmitted outside the authenticated payload.

### Likelihood Explanation
Likelihood is high for any app that installs the gem's stock `Webhooks::Request`/`Registry.process` flow as documented: obtaining a valid signed body for one's own shop is trivial (install the app, trigger any webhook topic), and replaying it with a different `shop-domain` header requires nothing more than a normal HTTP client capable of setting arbitrary headers when POSTing to the app's public webhook endpoint — no leaked credentials, TLS interception, or privileged access is required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signed material, or otherwise cryptographically bind the shop to the payload before dispatch — e.g., compute/verify the HMAC over a canonical string that concatenates body and headers, or require that `request.shop` be cross-checked against a stored, previously-authenticated session/shop record before invoking the handler, mirroring the equality that should hold: `verified(shop) == acted_on(shop)`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining an app-level shared `api_secret_key` used for all shops.
2. Attacker triggers/captures a webhook delivery for their own shop, capturing the raw body `B` and the corresponding `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends `POST <app-webhook-endpoint>` with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(B, api_secret_key)`, per [5](#0-4) .
5. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` per [6](#0-5) , causing the app to act on `victim-shop` using attacker-controlled body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
