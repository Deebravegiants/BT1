### Title
Non-primary FungibleStore objects remain ungated-transferable, letting owners bypass dispatchable withdraw/deposit hooks (transfer restrictions) via `object::transfer` - (File: `aptos-move/framework/aptos-framework/sources/fungible_asset.move`, `aptos-move/framework/aptos-framework/sources/primary_fungible_store.move`)

### Summary
The external report's root custody invariant is: *value-affecting logic that is supposed to run atomically with a transfer must not be avoidable by using an alternate transfer path.* In Aptos, `fungible_asset`/`dispatchable_fungible_asset` implement custody-relevant logic (allowlists, deflation/fees, predicated transfer) as withdraw/deposit dispatch hooks tied to a `FungibleStore` object [1](#0-0) . But a `FungibleStore` is itself an Aptos `Object`, and object ownership transfer (`object::transfer`/`transfer_raw`) is governed independently by `ObjectCore.allow_ungated_transfer`, not by the fungible-asset module [2](#0-1) . `primary_fungible_store::create_primary_store` explicitly calls `disable_ungated_transfer()` "since deterministic stores shouldn't be transferrable" [3](#0-2) , which strongly implies that regular/secondary stores created via `fungible_asset::create_store` do **not** get this protection by default.

### Finding Description
If a non-primary `FungibleStore` object is left with `allow_ungated_transfer == true` (the default for newly constructed objects), its owner can call `object::transfer<FungibleStore>` (or `transfer_raw`) directly on the store's address. This only flips the `owner` field on `ObjectCore` [4](#0-3)  — it never calls `fungible_asset::withdraw`/`deposit`, and therefore never invokes `dispatchable_fungible_asset::withdraw`/`deposit`, which is where issuers place custody-relevant enforcement: allowlists, deflationary burns, predicated transfer conditions, or loyalty payouts [5](#0-4) . The entire store balance (and its custody state) moves to the new owner while completely skipping issuer-defined transfer control logic, since that logic only runs inside `withdraw`/`deposit`, not inside `object::transfer`.

### Impact Explanation
For any fungible asset that relies on dispatch hooks for custody controls (e.g., regulatory allowlists, freeze-adjacent business logic, fee-on-transfer economics), a holder of a non-primary store can move the full balance to any address by transferring the store object, bypassing those controls entirely. This matches the "dispatch hooks... tied to live assets" and "supply or custody accounting corruption that moves value to the wrong holder" categories in the custody impact gate, because it lets value move to unauthorized holders (e.g., outside an allowlist) or evade fees/burns that are part of the custody design.

### Likelihood Explanation
Likelihood depends heavily on whether `fungible_asset::create_store` disables ungated transfer by default — I could not confirm this from the function body directly due to tool-call limits, only inferred it from the contrasting explicit call in `primary_fungible_store::create_primary_store`. If `create_store` does not disable ungated transfer, likelihood is high: any FA project using non-primary stores (common for wrapped positions, vault shares, escrow, or NFT-adjacent object composition) with dispatch-hook-based restrictions is affected with no special privilege required — only ordinary ownership of the store object.

### Recommendation
Verify `fungible_asset::create_store`'s implementation. If it does not disable ungated transfer, either (a) have `create_store` call `transfer_ref.disable_ungated_transfer()` by default (mirroring `create_primary_store`), forcing all store movement through `fungible_asset`/`dispatchable_fungible_asset` transfer paths, or (b) explicitly document this as a known limitation and require FA issuers relying on dispatch hooks to disable ungated transfer on stores themselves, and audit `object::transfer_raw`'s interaction with `FungibleStore` to ensure hook-based custody logic can't be bypassed.

### Proof of Concept
1. Issuer creates a dispatchable FA with a withdraw hook enforcing an allowlist via `dispatchable_fungible_asset::register_dispatch_functions` [6](#0-5) .
2. User A creates (or is given) a non-primary `FungibleStore` object holding balance of that FA via `fungible_asset::create_store` (not `primary_fungible_store::create_primary_store`).
3. User A calls `object::transfer<FungibleStore>(a_signer, store_object, addr_not_on_allowlist)` per `object.move` lines 558-566 [7](#0-6) .
4. Ownership of the store (and its entire balance) transfers to `addr_not_on_allowlist` without ever calling `dispatchable_fungible_asset::withdraw`/`deposit`, so the allowlist/fee logic in the registered hooks never executes.

**Caveat**: This conclusion depends on confirming `fungible_asset::create_store` does not call `disable_ungated_transfer`. I was unable to view that function's body before the iteration budget was exhausted; a Devin session with full repo access should verify this directly before treating this as confirmed.

    /// Transfers ownership of the object (and all associated resources) at the specified address
    /// for Object<T> to the "to" address.
    public entry fun transfer<T: key>(
        owner: &signer,
        object: Object<T>,
        to: address,
    ) {
        transfer_raw(owner, object.inner, to)
    }

    /// Attempts to transfer using addresses only. Transfers the given object if
    /// allow_ungated_transfer is set true. Note, that this allows the owner of a nested object to
    /// transfer that object, so long as allow_ungated_transfer is enabled at each stage in the
    /// hierarchy.
    public fun transfer_raw(
        owner: &signer,
        object: address,
        to: address,
    ) {
        let owner_address = signer::address_of(owner);
        verify_ungated_and_descendant(owner_address, object);
        transfer_raw_inner(object, to);
    }

    inline fun transfer_raw_inner(object: address, to: address) {
        let object_core = borrow_global_mut<ObjectCore>(object);
        if (object_core.owner != to) {
            event::emit(
                Transfer {
                    object,
                    from: object_core.owner,
                    to,
                },
            );
            object_core.owner = to;
        };
    }
