### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `X-Shopify-Shop-Domain` header, but its `to_signable_string` (the data that is actually HMAC-verified) is only the raw request body. `Registry.process` validates the HMAC and then forwards `request.shop` to the app's handler as trusted tenant identity, even though that header was never part of the signed material.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; the `shop-domain` header used by `#shop` is not part of it. `Registry.process` validates only the body's HMAC, then passes the unauthenticated `shop` header straight into the handler's trusted metadata: [2](#0-1) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop attributed to the webhook payload`

But the actual binding enforced by the gem is:
`raw_body authenticated by HMAC != shop header used for tenant dispatch`

Since only the raw body bytes are covered by the HMAC (`Utils::HmacValidator.validate(request)` calls `compute_signature(verifiable_query.to_signable_string, secret)` where `to_signable_string == @raw_body`), the `shop-domain` header can be swapped without invalidating the signature, as long as the body itself is untouched: [3](#0-2) 

This is precisely the M-10 bug class: a field the code *acts on* (here, `shop`, used as the tenant/session key that the handler will use to look up state, correlate data, or act on behalf of a shop) is not covered by the equality check (HMAC) that is supposed to bind the whole request to a legitimate shop. It mirrors the reported bug's pattern of "a field acted on but not covered by the [signature]."

### Impact Explanation
An app that receives a webhook and uses `WebhookMetadata#shop` (`request.shop`) to decide which merchant/tenant the payload belongs to — e.g., to fetch that shop's session/access token, write data attributed to that shop, or make authorization decisions — can be made to associate a genuinely-signed payload (from the attacker's own store, whose HMAC the attacker legitimately possesses because Shopify computed it with the merchant's own valid webhook for their own shop) with an arbitrary victim shop, simply by changing the `X-Shopify-Shop-Domain` header when delivering it to the app's endpoint. This is a cross-tenant identity confusion: data is verified with a valid signature but is misattributed to the wrong tenant. This matches the "cross-tenant access" Critical-impact category in the rules, since it breaks the tenant isolation the HMAC is meant to enforce.

### Likelihood Explanation
Any merchant who installs the app on their own store is an "unprivileged internet user" relative to other tenants of the app, per the scoping rules. They can:
1. Legitimately receive real webhooks from Shopify for their own store (with valid HMAC over the body, computed with the app's shared secret).
2. Replay that request directly to the app's webhook endpoint (bypassing Shopify) with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain.

The HMAC will still validate because it only covers the raw body. No access token, `client_secret`, or credential theft is required — only the merchant's own genuine outbound webhook, which they always have access to. The severity of exploitation depends on how the host application further correlates `request.shop` (e.g., does it also validate this shop has ever installed the app, or that a session exists), but the gem itself provides no binding between the verified bytes and the shop attribution, which is the root cause resting entirely inside `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Recommendation
Bind the shop identity to the verified request instead of only trusting an unauthenticated header:
- Where feasible, require callers to independently confirm the `shop` value corresponds to a shop with an active session/installation before trusting `WebhookMetadata#shop` for any privileged action.
- Document explicitly in `Webhooks::Request` that `shop` is not covered by the HMAC and must not be used as the sole tenant-binding key without additional verification (e.g., cross-checking against a known/installed-shop list, or requiring TLS-terminated direct delivery from Shopify's IP ranges).
- Consider including shop/topic/webhook-id in the value that's compared/logged as "verified" so downstream consumers don't conflate "signature valid" with "shop attribution trustworthy."

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com" and has app installed there.
# Shopify sends a genuine webhook to the attacker's own endpoint for their shop:
raw_body = '{"id": 123, "note": "some order data"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker relays the exact same (still validly-signed) body directly to the
# app's public webhook endpoint, but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation passes because it only checks raw_body, not shop-domain:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily hands this to the handler attributed to the victim shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
