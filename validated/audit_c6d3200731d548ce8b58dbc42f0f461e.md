### Title
i128 overflow in scaled Ray totals during accrual permanently freezes a high-decimal market — (`common/src/rates/index.rs`, `common/src/rates/scaling.rs`)

### Summary
CVE-2022-2831 is an integer-overflow → crash class. Its analog in XOXNO Lending is an `i128` overflow when index-scaled `Ray` totals (`scaled * index`) are recomputed during interest accrual. Every mutating entrypoint accrues first, so once a market's `borrowed_scaled_ray × borrow_index` product exceeds `i128::MAX`, every subsequent call on that market reverts with `GenericError::MathOverflow` — permanently freezing all supplied funds and debt in that market. The `MAX_BORROW_INDEX_RAY` cap does not help: `update_borrow_index` multiplies before it clamps, and `calculate_supplier_rewards`/`scaled_to_original` multiply the unclamped value anyway. The repo's own harness proves the freeze end-to-end.

### Finding Description
Accrual runs inside `global_sync`, which every pool operation triggers before touching positions:

- `contracts/pool/src/interest.rs:20-33` — `global_sync` chunks elapsed time and calls `accrue_chunk`, which invokes `accrue_step` and only afterwards `cache.mark_accrued()`. A panic inside the step leaves `last_timestamp` un-updated, so the next call re-runs the same (now longer) accrual and panics again.
- `common/src/rates/index.rs:80-81` — `calculate_supplier_rewards` computes `borrowed.mul(env, old_borrow_index)` and `borrowed.mul(env, new_borrow_index)` via `Ray::mul` → `fp_core::mul_div_half_up`, which panics with `MathOverflow` when the result exceeds `i128` (`common/src/math/fp_core.rs:108-118`).
- `contracts/pool/src/cache/scale.rs:23-24` — `calculate_utilization` calls `scaled_to_original(borrowed, borrow_index)` / `scaled_to_original(supplied, supply_index)`, which are the same `scaled.mul(index)` product (`common/src/rates/scaling.rs:14-16`).

The overflow site is therefore not the index itself but the *value* `scaled_shares × index`. Scaled shares for an `d`-decimal asset are `units × 10^(27-d) / index`, so total debt value in raw `i128` is roughly `units × 10^(27-d) × index / RAY`. Caps are bounded only by `max_cap_for_decimals` (`common/src/validation.rs:48-56`), which requires the *unscaled* ray form to fit `i128` — i.e. `units ≤ i128::MAX / 10^(27-d)`. For an 18-decimal asset that bound is ~`1.7e11` whole tokens, but the debt *value* overflows at roughly `i128::MAX` raw, i.e. index × ~`1.7e11` tokens-worth of scaled supply — reachable whenever the borrow index exceeds ~1× on a fully-utilized whale market, and guaranteed long before the `MAX_BORROW_INDEX_RAY` cap at high utilization. The harness test demonstrates exactly this: a 1-billion-unit, 18-decimal market at ~98% utilization on the XLM rate curve overflows `scaled_to_original` at index ≈ ×170, while `borrow_index < MAX_BORROW_INDEX_RAY` (`tests/test-harness/tests/controller/extreme_amount_inputs.rs`-adjacent test at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-362`).

### Impact Explanation
Permanent freezing of funds — a listed acceptance impact. Once the product exceeds `i128::MAX`:

- `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, flash paths, and revenue claims all route through `global_sync` → `accrue_step`/`calculate_utilization` and revert with `MathOverflow` before any state changes.
- Because `mark_accrued` is never reached, elapsed time only grows; there is no input a user or admin can pass to skip accrual. The test explicitly asserts `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` after the cliff.
- Suppliers' deposits and borrowers' collateral backing this market are frozen indefinitely, and the debt can never be repaid or liquidated, which also strands collateral value accounted against the position NFT.

### Likelihood Explanation
No privileged action is required: `supply`, `borrow`, and `update_indexes` are permissionless entrypoints. The requirements are (a) a listed market whose `asset_decimals` makes `max_cap_for_decimals` admit enough units that `scaled × index` can exceed `i128` (high-decimal assets qualify — cap validation only bounds the unscaled form), and (b) sustained borrow utilization large enough to grow the index. The capital requirement is whale-scale (real tokens must be supplied and borrowed), but it is a single unprivileged address using only `supply`/`borrow`; alternatively, organic growth of any sufficiently large high-decimal market reaches the same cliff without an attacker, since accrual is automatic. Severity is bounded below Critical because the freeze is per-market and requires extreme-but-permitted scale.

### Recommendation
Bound the value domain, not just the index:

1. In `update_borrow_index` / `accrue_step`, compute the new index against a headroom check derived from `borrowed`/`supplied`: clamp the index to `min(cap, i128::MAX / borrowed_scaled_ray)` so `scaled_to_original` can never overflow. Apply the symmetric bound for the supply index inside `update_supply_index` (it already uses `mul_div_floor_saturating` for the quotient but `supplied.mul(old_index)` at `common/src/rates/index.rs:34` still panics).
2. Alternatively, make `calculate_supplier_rewards`, `scaled_to_original`, and `calculate_utilization` use saturating `mul_div` variants and clamp accrued interest to representable values, so accrual degrades gracefully instead of bricking the market.
3. Tighten `require_cap_within_asset_domain` to also require `cap × MAX_SUPPLY_INDEX_RAY / RAY` (and the borrow equivalent) to fit `i128`, so listed caps cannot outgrow the value domain.

### Proof of Concept
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361` is an executable PoC:

```rust
// 18-decimal market, caps lifted to the validation maximum (still ≤
// max_cap_for_decimals(18)), XLM-style rate curve, max utilization disabled.
let principal = BILLION * 10i128.pow(18);          // 1e9 tokens × 1e18
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;                    // ~98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// Advance time; each try_update_indexes accrues. At index ≈ ×170:
//   borrowed_scaled * borrow_index > i128::MAX  →  MathOverflow panic
t.advance_time(YEAR_SECS);
t.try_update_indexes_for(&["BIG18"])               // → Error(Contract, #33)

// Permanent: every verb accrues first and hits the same panic.
t.try_withdraw_raw(BOB, "BIG18", 1)                // → MATH_OVERFLOW
t.try_repay(ALICE, "BIG18", 1.0)                   // → MATH_OVERFLOW
// last.borrow_index < MAX_BORROW_INDEX_RAY: the index cap never engaged.
```

In production terms: an attacker supplies a large position in a high-decimal market (under `max_cap_for_decimals`), borrows to high utilization against collateral in another spoke, and lets permissionless `update_indexes` (or any user action) accrue interest until `borrowed_scaled_ray × borrow_index` exceeds `i128::MAX`. From that point all withdrawals, repayments, and liquidations on the market revert with `MathOverflow` forever.

**Caveat:** I verified the overflow site, the accrual-first ordering, the cap bound, and the repo's own freeze-demonstrating test, but did not trace every entrypoint's call into `global_sync`; the conclusion that verbs freeze market-wide rests on the test's asserted `withdraw`/`repay` failures plus the shared accrual path.
