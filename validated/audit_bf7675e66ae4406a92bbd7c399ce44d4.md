### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` binds only the body bytes. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values — all taken from unauthenticated HTTP headers — are never included in the signed data, yet they are trusted and forwarded to the host application's webhook handler as authoritative shop/topic identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns `@raw_body` exclusively. The `shop`, `topic`, `api_version`, and `webhook_id` accessors all read straight from HTTP headers (`shopify_header(...)`), which are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then constructs the `WebhookMetadata` passed to the handler using the unauthenticated `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id`: [3](#0-2) 

The broken identity binding is:
`hmac == HMAC(secret, raw_body)` is checked, but the code treats it as if `hmac == HMAC(secret, raw_body ‖ shop ‖ topic ‖ webhook_id)`. Since the app's `client_secret`/`api_secret_key` is shared across every installed shop, any merchant who has installed the app can obtain a genuinely-signed `(raw_body, hmac)` pair for their own shop (Shopify sends real webhooks to the app's registered endpoint for every installed shop), then replay that exact body and HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the handler believing the event originated from the spoofed shop/topic.

### Impact Explanation
This breaks the identity binding between the cryptographically-verified payload and the shop/topic the host application acts on, allowing a merchant that installed the app (an unprivileged, non-victim tenant) to make the app process webhook data attributed to a different shop or a different topic than what was actually delivered and signed for. Since host applications commonly key persistence, authorization, and side effects (e.g., updating shop-specific records, deleting shop data on `shop/redact`, etc.) off `WebhookMetadata#shop`, this is a cross-tenant confusion vector at the API boundary the gem exposes, meeting the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation requires no special credentials beyond installing the app to one's own shop (or capturing any legitimately delivered webhook), which is available to any ordinary merchant/unprivileged internet user. No access token, `client_secret`, or privileged access is needed — only the ability to trigger or intercept a real webhook delivery to the app and replay it with modified headers. This is a "field acted on but not covered by the HMAC" defect, directly matching the described bug class of an identity-binding gap.

### Recommendation
Include the `shop-domain`, `topic`, `api-version`, and `webhook-id` values (or equivalently the full raw header/body context Shopify signs) in the string used to compute/verify the HMAC in `Request#to_signable_string`, or otherwise cryptographically bind these header values to the signed payload before trusting them in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the app normally on `attacker-shop.myshopify.com`; trigger any webhook event so Shopify delivers a genuine `(raw_body, x-shopify-hmac-sha256)` pair to the app's webhook endpoint.
2. Capture that request.
3. Replay the identical `raw_body` and `x-shopify-hmac-sha256` header to the same endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or `x-shopify-topic`/`x-shopify-webhook-id` to a more sensitive topic if desired).
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only re-computes the HMAC over `raw_body`, per `to_signable_string` in `lib/shopify_api/webhooks/request.rb:36-38`.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the host application to act on the attacker's payload as if it belonged to the victim shop.
