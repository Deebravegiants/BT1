This is a confirmed finding. `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` [1](#0-0) , and `Oauth.validate_auth_callback` constructs `null_session = Auth::Session.new(shop: auth_query.shop)` and then POSTs a body containing `client_secret` and `code` to that host via `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [2](#0-1) . Neither `Session#initialize` nor `HttpClient#initialize` validates that `shop` matches Shopify's `*.myshopify.com` (or partner-dev) domain format [3](#0-2) . The only gate on `auth_query.shop` before it is used to build this request URL is `HmacValidator.validate`, which computes the HMAC over `code/host/shop/state/timestamp` using the app's own `api_secret_key` [4](#0-3) [5](#0-4) . That HMAC proves the value came from a request the app's own secret would sign correctly (i.e., a value Shopify's real OAuth endpoint signed), but it does not constrain `shop` to be a valid `*.myshopify.com` hostname — the gem trusts the field's *format* implicitly rather than checking it. Note: it is uncertain from the code inspected whether Shopify's own authorize/callback flow could ever be tricked into HMAC-signing a non-`myshopify.com` shop value; that determination depends on Shopify's server-side behavior, not this gem, and I could not verify it from this repository alone.

### Title
Missing shop-domain format validation before sending OAuth `client_secret` — potential SSRF/credential exfiltration if a non-`myshopify.com` `shop` value reaches the token exchange - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` and `ShopifyAPI::Auth::TokenExchange.exchange_token` build the outbound `/admin/oauth/access_token` request host directly from an externally supplied `shop` string (`auth_query.shop` / JWT `dest` claim) without validating it is a well-formed `*.myshopify.com` domain, then attach the app's `client_secret` to the POST body sent to that host.

### Finding Description
`validate_auth_callback` creates `null_session = Auth::Session.new(shop: auth_query.shop)` [6](#0-5) , then issues a POST containing `client_id`, `client_secret`, and `code` through `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [7](#0-6) . `HttpClient#initialize` builds the request's `@base_uri` as `"https://#{api_host || session.shop}"` with no regex/format check on `session.shop` [1](#0-0) . `Session#initialize` likewise accepts an arbitrary `String` for `shop` with no validation [8](#0-7) . The equality this bug class breaks is: **the shop value authenticated by the HMAC ≠ the shop value validated to be a genuine `*.myshopify.com` host that is safe to receive the `client_secret`.** The gem's HMAC check (`Utils::HmacValidator.validate`) proves `shop` was part of a signed query, but it enforces *authenticity of the byte string*, not that the byte string is a syntactically valid Shopify store domain — the same class of gap described in the analog report, where a value that passes one check (signature presence) is treated as fully trustworthy for a separate, unchecked purpose (host used for a credentialed request). The same pattern recurs in `TokenExchange.exchange_token`, which takes `dest_shop = jwt_payload.shop` from the JWT `dest` claim and uses it to build the session sent to the token endpoint with `client_secret` in the body, again with no domain-format validation [9](#0-8) .

### Impact Explanation
If any path allows a `shop` value that is not a genuine `myshopify.com` (or partner sandbox) hostname to reach `validate_auth_callback` or `exchange_token` with a signature/JWT that still validates (e.g., a shop domain containing an unexpected suffix, a subdomain trick, or a host header/URI injection surviving into the `shop` string), the app's `client_secret` would be sent via HTTPS POST to an attacker-influenced host — meeting the High-severity bar of "SSRF with the app's credentials" / credential leakage.

### Likelihood Explanation
Exploitability is not fully confirmed from this repository alone: the primary control is Shopify's own signature on the OAuth callback, and this gem cannot independently confirm whether Shopify's authorization server ever signs a `shop` value outside `*.myshopify.com`. Without a live OAuth flow or additional verification against Shopify's server-side behavior, likelihood is speculative rather than demonstrated purely from this gem's code.

### Recommendation
Add explicit shop-domain format validation (e.g., a `myshopify.com`/allowed-partner-domain regex) in `Session#initialize` or immediately before constructing `null_session` in `Oauth.validate_auth_callback` and `TokenExchange.exchange_token`, rejecting any `shop` value that does not match the expected pattern before it can be used to build a request host that carries `client_secret`.

### Proof of Concept
Not independently reproducible from static analysis of this repository — a concrete PoC would require confirming whether Shopify's real OAuth server can be induced to sign a callback for a non-`myshopify.com` `shop` value, which requires live testing against Shopify's authorization endpoint (outside the scope of this gem's code).
