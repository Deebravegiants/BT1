### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — all of which are handed to the app's webhook handler as trusted, authenticated data — are never included in the signed material. Any actor who can obtain one valid `(body, hmac)` pair for any shop can replay that exact body with a different `shop-domain` header and have it accepted as an authentic webhook for an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using: [1](#0-0) 

```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` is defined as just the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from separate, unsigned headers: [3](#0-2) 

The equality that should hold is:
`bytes(shop header) ⊆ bytes(HMAC-verified content)`

but in fact:
`bytes(HMAC-verified content) = raw_body` and `shop header ∉ raw_body`'s protected scope.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the gem authenticates the body but then trusts an out-of-band, unauthenticated header (`shop-domain`) to decide which tenant the webhook belongs to, and hands that unauthenticated value to the app as `WebhookMetadata#shop`, which apps use to route data into the correct shop's records.

### Impact Explanation
Because the HMAC only proves "this body was produced by someone possessing `api_secret_key`" and not "this body belongs to shop X," an attacker who has legitimate access to one tenant/shop that has the app installed (e.g., a competitor merchant, or anyone able to observe a real webhook delivery from their own store) can capture a valid `(raw_body, hmac)` pair and resend it with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to any other shop's domain. `ShopifyAPI::Webhooks::Registry.process` will still consider the request valid (`Utils::HmacValidator.validate` only checks the body) and will invoke the handler with `shop: <attacker-chosen shop>`, causing the host application to process/persist attacker-controlled webhook content under a different tenant's identity — a cross-tenant data-integrity/spoofing issue that meets the Critical "cross-tenant access" bar since the tenant boundary (`shop`) is the exact value asserted without cryptographic binding.

### Likelihood Explanation
Exploitation requires no privileged credentials, no `api_secret_key`, and no TLS interception: any party that can see one legitimate webhook delivery (their own shop's webhook, which many apps log or expose to developers) obtains a reusable `(body, hmac)` pair valid for any `shop-domain` header value, since the header is never mixed into the signed content. The gem provides no cross-check between the header-derived shop and the authenticated payload, so any host application built directly on the documented `ShopifyAPI::Webhooks::Request` / `Registry.process` API is affected by construction, not by misuse.

### Recommendation
Include the identity-binding fields (`shop-domain`, and ideally `topic`, `webhook-id`) in the material that is cryptographically verified, or otherwise cryptographically bind them to the body (e.g., verify the tuple as Shopify does by trusting `X-Shopify-Shop-Domain` only after confirming it matches a shop already known to have generated the current webhook subscription/registration, and/or by re-deriving the shop from a signed source). At minimum, `Utils::HmacValidator` should be extended so `Webhooks::Request#to_signable_string` incorporates the shop/topic headers, restoring the property that everything acted upon (`shop`) is covered by the HMAC that authenticates the request.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; attacker controls that shop and observes one legitimate webhook delivery:
   - Headers: `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-for-body>`, body: `{"id":1,...}`.
2. Attacker resends the identical body and hmac header, only changing:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — unchanged — so validation succeeds: [4](#0-3) 
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and the host app processes/stores this as authentic data for `victim-shop`, even though `victim-shop` never sent this webhook.
