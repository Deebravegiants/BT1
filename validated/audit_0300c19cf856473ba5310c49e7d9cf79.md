Audit Report

## Title
DMP inbound messages bypass the "advancement rule" size check, enabling collator censorship of downward XCM/DMP messages - (File: cumulus/pallets/parachain-system/src/lib.rs / cumulus/pallets/parachain-system/src/parachain_inherent.rs)

## Summary
`enqueue_inbound_downward_messages` only invokes `check_enough_messages_included_basic`, which merely requires at least one full DMP message be present whenever hashed messages exist, but never invokes the stricter `check_enough_messages_included_advanced` that verifies the size budget was actually exhausted before hashing. In contrast, `enqueue_inbound_horizontal_messages` invokes the advanced check for HRMP. This asymmetry lets a malicious collator hash (censor) arbitrary downward messages every block, as long as one small full DMP message remains, without triggering any panic.

## Finding Description
`enqueue_inbound_downward_messages` calls only `downward_messages.check_enough_messages_included_basic("DMQ")` [1](#0-0) , while `enqueue_inbound_horizontal_messages` additionally calls `check_enough_messages_included_advanced` with `max_full_messages_size` set to `Self::messages_collection_size_limit()` and `first_hashed_msg_max_size` set to the ingress channel's `max_message_size` [2](#0-1) .

`check_enough_messages_included_basic` only asserts `full_messages.len() >= 1` and says nothing about whether the size budget could have accommodated more full messages [3](#0-2) . `check_enough_messages_included_advanced` is the only check that actually verifies hashing was necessary given the size budget, comparing `full_messages_size + first_hashed_msg_max_size` against `max_full_messages_size` [4](#0-3) .

The collator freely controls the abridging via `into_abridged`, which splits a message collection into full and hashed parts purely based on a `size_limit` parameter supplied by the collator itself [5](#0-4) . The runtime-side MQC head equality check in `enqueue_inbound_downward_messages` only validates that the hashed representation is consistent with the relay-provided MQC head — it does not validate that hashing was justified by the size budget [6](#0-5) .

This confirms the code behaves exactly as claimed: the "advancement rule" hardening was applied only to HRMP, as corroborated by `prdoc/stable2603/pr_9086.prdoc`, titled "Make HRMP advancement rule more restrictive," which explicitly scopes the improvement to HRMP only [7](#0-6) . No equivalent DMP-specific hardening exists anywhere in the codebase.

## Impact Explanation
A block-producing collator for a parachain can deterministically censor/delay downward XCM messages (e.g., relay-chain-originated reserve transfers, teleports, or other DMP-carried instructions affecting user funds) every block, by keeping only one small full DMP message and hashing the rest, regardless of whether the size budget (`messages_collection_size_limit()`, 1/6 of block PoV) would allow including more messages in full. This passes `check_enough_messages_included_basic` and produces a validly verifiable inherent, since no advanced check exists for the DMP path. This matches an in-scope censorship/DoS-style impact against user-submitted DMP messages, without requiring any privileged key or governance action — only the ordinary (if adversarial) role of block-producing collator, which is a realistic, permissionless-adjacent actor in the parachain consensus model.

## Likelihood Explanation
This is fully reproducible and deterministic: the collator simply crafts `AbridgedInboundDownwardMessages` with a small effective `size_limit` for the DMP portion (or directly constructs the hashed/full split) while still producing an MQC head matching the relay chain's DMQ head — a mechanical operation entirely within the collator's control at inherent-construction time. There is no probabilistic race and no additional runtime invariant blocks it, since the only relevant check (`check_enough_messages_included_advanced`) is never invoked for DMP.

## Recommendation
Invoke `check_enough_messages_included_advanced` inside `enqueue_inbound_downward_messages`, mirroring the HRMP path in `enqueue_inbound_horizontal_messages`, using `Self::messages_collection_size_limit()` for `max_full_messages_size` and the configured maximum DMP message length (e.g., the pallet's `Config::MaxDmpMessageLenOf` or equivalent bound) for `first_hashed_msg_max_size`, so the advancement rule is enforced symmetrically for both DMP and HRMP inbound paths.

## Proof of Concept
Add a unit test near the existing `check_enough_messages_included_advanced_works` test in `parachain_inherent.rs`/`lib.rs` tests:
1. Build a `InboundDownwardMessages` collection of 4 messages of size 100 each (400 bytes total).
2. Call `into_abridged` with an artificially tiny `size_limit` (e.g., 100), producing 1 full message and 3 hashed messages, even though the real on-chain `messages_collection_size_limit()` would have permitted all 4 to remain full.
3. Call `check_enough_messages_included_basic("DMQ")` on the result — it does not panic (only requires `full_messages.len() >= 1`).
4. Observe that `enqueue_inbound_downward_messages` in `lib.rs` has no call to `check_enough_messages_included_advanced`, so this censorship path passes on-chain, whereas an equivalent HRMP scenario under `check_enough_messages_included_advanced_works`-style assertions with the same size ratios would panic.
A full integration-level PoC would additionally fix `BlockWeights::max_block` to compute a known `messages_collection_size_limit()`, submit `set_validation_data` with a crafted `AbridgedInboundDownwardMessages` (1 full message + N hashed messages that would collectively still fit under the size budget) and a correctly-matching MQC head, and assert the extrinsic succeeds — demonstrating the runtime accepts unnecessary DMP message censorship.

	pub fn into_abridged(
		self,
		size_limit: &mut usize,
	) -> AbridgedInboundMessagesCollection<Message> {
		let mut messages = self.messages;

		let mut split_off_pos = messages.len();
		for (idx, message) in messages.iter().enumerate() {
			if *size_limit < message.data().len() {
				break;
			}
			*size_limit -= message.data().len();

			split_off_pos = idx + 1;
		}

		let extra_messages = messages.split_off(split_off_pos);
		let hashed_messages = extra_messages.iter().map(|msg| msg.to_compressed()).collect();

		AbridgedInboundMessagesCollection { full_messages: messages, hashed_messages }
	}

	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

		let mut full_messages_size = 0usize;
		for msg in &self.full_messages {
			full_messages_size = full_messages_size.saturating_add(msg.data().len());
		}

		// The worst case scenario is that were the first message that had to be hashed
		// is a max size message.
		assert!(
			full_messages_size.saturating_add(first_hashed_msg_max_size) > max_full_messages_size,
			"[{}] Advancement rule violation: full messages size smaller than expected. \
			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",
			collection_name,
			full_messages_size,
			first_hashed_msg_max_size,
			max_full_messages_size
		);
	}
