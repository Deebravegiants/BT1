### Title
Webhook `shop` identity used by app handlers is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is read from an HTTP header which is *not* included in the signed material. Any party that can produce one genuinely-signed webhook body/HMAC pair (e.g. by owning a legitimate Shopify dev store that receives real webhooks for the subscribed topic) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process the payload as if it belonged to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) , and `#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding: [2](#0-1) .

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header [3](#0-2)  — i.e. the signature proves only that the *body bytes* were produced with knowledge of the app's secret, not that the accompanying `shop-domain` header is authentic or bound to that body.

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no additional check tying `shop` to the signed content: [4](#0-3) .

This is exactly the "field acted on but not covered by the HMAC" pattern: the identity binding that should hold is `shop_authenticated == shop_used_as_tenant_key`, but here `shop_used_as_tenant_key` (the header) is disjoint from what the HMAC covers (the body only).

### Impact Explanation
Apps built on this gem commonly use `data.shop` from `WebhookMetadata` to select which merchant/tenant record to create, update, or delete (as shown in the gem's own documented handler pattern using `data.shop`). Because the shop identity is not bound to the signature, an attacker who can obtain any one legitimately HMAC-signed webhook body (from their own store, a trial/dev store, or a previously observed webhook) can resubmit that body with a forged `x-shopify-shop-domain` header pointing at a victim shop domain. The app then attributes attacker-supplied data to the victim tenant — a cross-tenant data-integrity/confusion issue reachable by an unprivileged external actor without needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Medium: the attacker needs at least one genuine `(raw_body, hmac)` pair for the target app (obtainable by installing the app on any store they control and capturing a real webhook delivery for the topic they want to spoof), and the app's public webhook endpoint must be reachable, which it always is by design. No secret key, access token, or insider access is required — only a standard HTTP POST with modified headers.

### Recommendation
Bind the shop identity to the signed material before trusting it for tenant-scoped processing:
- Extend `VerifiableQuery`/`Request#to_signable_string` (or a dedicated check in `Registry.process`) to require that the `shop` (and ideally `topic`/`webhook_id`) values are cryptographically tied to the payload, e.g. by validating the shop against the caller-registered session/shop for that webhook subscription rather than trusting the header value outright.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must be cross-checked by the host app against a known/registered shop before being used as a tenant key, since the current API surface does not enforce this itself.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`) via the app's normal registration flow, using `Registry.add_registration`.
2. Shopify delivers a real webhook to the app's HTTP endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`.
3. Attacker captures the raw POST body and HMAC header from step 2, then re-sends an identical POST directly to the app's public webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only recomputes the HMAC over `@raw_body` [5](#0-4) ; `request.shop` returns `"victim-shop.myshopify.com"` [2](#0-1) , and the handler is invoked with `WebhookMetadata` claiming the data belongs to the victim shop [6](#0-5) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
