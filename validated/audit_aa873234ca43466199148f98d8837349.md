### Title
`AuroraEngineBridge.describeWithdrawal()` unconditionally reports `completed` without checking the Aurora Engine cross-contract sub-call outcome - ([File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts])

### Summary
`AuroraEngineBridge.describeWithdrawal()` is a hard-coded constant that always returns `{ status: "completed", txHash: null }` regardless of whether the underlying NEAR `ft_transfer_call` from the token contract into `auroraEngineContractId`/`proxyTokenContractId` actually succeeded. Because `watchWithdrawal()` and `waitForWithdrawalCompletion()` treat `status: "completed"` as the ground truth for downstream integrator logic, a failed Aurora Engine deposit (e.g., due to missing storage deposit on the proxy) is silently reported as successful.

### Finding Description
The broken equality is: **SDK-reported withdrawal status (`"completed"`) must equal the actual outcome of the Aurora Engine cross-contract deposit on the virtual chain.**

`createWithdrawalIntents()` builds an `ft_withdraw` intent whose execution causes `intents.near` to call `ft_transfer_call` on the token contract, which in turn invokes `ft_on_transfer` on `auroraEngineContractId` (or `proxyTokenContractId` for non-standard-decimal base tokens), passing a `msg` encoding the destination address [1](#0-0) . This is a genuine asynchronous cross-contract call that can fail independently of the top-level `intents.near` transaction succeeding (e.g., insufficient storage on the proxy account, engine-side revert, etc.).

Despite this, `describeWithdrawal()` takes no arguments beyond satisfying the `Bridge` interface and performs zero lookups against NEAR receipts, indexers, or the virtual chain state: [2](#0-1) 

Contrast this with sibling bridges that actually verify the destination-chain outcome — `PoaBridge.describeWithdrawal()` polls an indexer and only returns `completed` when the indexer confirms `COMPLETED`, otherwise `pending` or `failed` [3](#0-2) , and `HotBridge.describeWithdrawal()` checks nonce-based gasless withdraw status including a `Canceled` failure path [4](#0-3) .

This constant status feeds directly into `watchWithdrawal()`, which treats `status === "completed"` as terminal success and resolves immediately with `{ hash: txHash }` (here `null`) without ever entering the `pending` retry loop or the `failed` error path [5](#0-4) , which in turn is consumed by `IntentsSDK.waitForWithdrawalCompletion()` [6](#0-5) .

No existing guard (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()` ordering, `FeeExceedsAmountError`, `getUnderlyingFee`) inspects the sub-call outcome — `validateWithdrawal()` for this bridge is explicitly a no-op beyond address format checking [7](#0-6) , and none of these checks run post-execution to confirm the Aurora Engine leg landed.

### Impact Explanation
An integrator relying on `waitForWithdrawalCompletion()`/`describeWithdrawal()` to gate a second-leg action (releasing an off-chain settlement, crediting a user's balance elsewhere, or marking a withdrawal record as final) will do so even when the Aurora Engine deposit silently failed and the tokens remain stuck in the proxy/engine contract on NEAR rather than landing on the virtual chain. This is a status misreport that causes an integrator to treat an unrealized transfer as final and release funds it does not have, matching the **Critical** ("funds delivered to a wrong address/chain/contract with no recovery") / **High** ("a status or hash misreport making an integrator credit or refund twice") impact categories. This affects every withdrawal routed through `RouteEnum.VirtualChain`, not a one-off edge case — it is a permanent characteristic of the code path.

### Likelihood Explanation
No attacker action beyond initiating a normal withdrawal through the `VirtualChain` route is required; the only precondition is that the Aurora Engine/proxy sub-call fails asynchronously (e.g., proxy storage deposit insufficient, engine-side rejection), which is a realistic operational condition already anticipated by `estimateWithdrawalFee()`'s storage-deposit logic [8](#0-7) . There is no cost to trigger and it is fully repeatable for every withdrawal on this route.

### Recommendation
Implement `describeWithdrawal()` for `AuroraEngineBridge` to actually verify the outcome of the cross-contract call — e.g., fetch the NEAR transaction receipt/execution outcomes for `args.tx.hash`, locate the receipt corresponding to the `ft_transfer_call` into `auroraEngineContractId`/`proxyTokenContractId`, and only return `status: "completed"` when that receipt succeeded; return `status: "failed"` with the failure reason otherwise (mirroring the pattern used by `PoaBridge`/`HotBridge`).

it("BUG: reports completed even when the Aurora Engine sub-call failed", async () => {
  const bridge = new AuroraEngineBridge({ envConfig, nearProvider });

  // Mock: nearProvider.txStatus / receipt lookup for args.tx.hash returns a receipt
  // where the ft_on_transfer call into auroraEngineContractId has a Failure outcome
  // (e.g., "insufficient storage deposit on proxy").
  vi.spyOn(nearProvider, "txStatus").mockResolvedValue({
    receipts_outcome: [
      { outcome: { status: { SuccessValue: "" } } }, // intents.near top-level call
      { outcome: { status: { Failure: { ActionError: { kind: "FunctionCallError" } } } } }, // aurora sub-call
    ],
  } as any);

  const result = await bridge.describeWithdrawal({
    landingChain: Chains.Near,
    index: 0,
    withdrawalParams: { /* ... VirtualChain routeConfig ... */ },
    tx: { hash: "near-tx-hash", accountId: "user.near" },
  });

  // BROKEN EQUALITY: SDK says "completed" while destination-chain outcome is "failed"
  expect(result.status).not.toBe("completed"); // currently fails — bridge always returns "completed"
  expect(result).toEqual({ status: "failed", reason: expect.any(String) });
});

		if (withdrawal == null) {
			return { status: "pending" };

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};

	public async waitForWithdrawalCompletion(args: {
		withdrawalParams: WithdrawalParams | WithdrawalParams[];
		intentTx: NearTxInfo;
		signal?: AbortSignal;
		logger?: ILogger;
	}): Promise<(TxInfo | TxNoInfo) | Array<TxInfo | TxNoInfo>> {
		const withdrawalParamsArray = Array.isArray(args.withdrawalParams)
			? args.withdrawalParams
			: [args.withdrawalParams];

		const promises = this.createWithdrawalCompletionPromises({
			withdrawalParams: withdrawalParamsArray,
			intentTx: args.intentTx,
			signal: args.signal,
			logger: args.logger,
		});

		const result = await Promise.all(promises);

		if (Array.isArray(args.withdrawalParams)) {
			return result;
		}

		assert(result.length === 1, "Unexpected result length");
		// biome-ignore lint/style/noNonNullAssertion: length asserted above
		return result[0]!;
	}
