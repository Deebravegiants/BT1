### Title
Update-path validation gap allows arbitrary `spec.Priority`/`spec.PriorityClassName` mutation on `CompositePodGroup`, bypassing priority-class admission checks - (File: `plugin/pkg/admission/priority/admission.go`)

### Summary
`Plugin.Admit` only invokes `admitCompositePodGroup` for `Create` operations, and the corresponding validation strategy for `Update` (`ValidateCompositePodGroupUpdate`) checks only `ObjectMeta`, never `Spec.Priority` or `Spec.PriorityClassName`. As a result, a namespace-scoped user who is allowed to `update`/`patch` a `CompositePodGroup` can set `spec.Priority` to an arbitrary value or repoint `spec.PriorityClassName` to a different `PriorityClass`, bypassing the priority-class resolution/consistency check that is enforced on create.

### Finding Description
`Plugin.Admit` in `plugin/pkg/admission/priority/admission.go` routes `compositePodGroupResource` requests only for `admission.Create`; any other operation (including `Update`) falls through to `return nil` with no admission logic applied at all: [1](#0-0) 

`admitCompositePodGroup` (the create-only guard) is the only place that: (1) resolves `PriorityClassName` to a `PriorityClass`, (2) rejects the request if a caller-supplied `Spec.Priority` does not match the value computed from the resolved class, and (3) writes the computed `Priority`/`PreemptionPolicy` back onto the object: [2](#0-1) 

For `Update`, the only server-side check is `ValidateCompositePodGroupUpdate`, which validates `ObjectMeta` only and never re-derives or re-checks `Spec.Priority`/`Spec.PriorityClassName` against the referenced `PriorityClass`: [3](#0-2) 

The registry strategy's `PrepareForUpdate`/`ValidateUpdate` similarly do nothing to protect `Spec.Priority`/`Spec.PriorityClassName`, only preserving `Status` and dropping disabled preemption-policy fields: [4](#0-3) 

This is in contrast to the `Pod` path, where `admitPod` is explicitly invoked on both `Create` and `Update` (`Admit` calls `p.admitPod(a)` for both operations) and re-copies the previously-established `Priority`/`PreemptionPolicy` forward, relying on core Pod API validation to reject any attempted mutation: [5](#0-4) [6](#0-5) 

No equivalent "priority is immutable on update" check exists for `CompositePodGroup` (or `PodGroup`, which has the identical gap): `Admit` skips `admitPodGroup`/`admitCompositePodGroup` for updates, and `ValidatePodGroupUpdate`/`ValidateCompositePodGroupUpdate` don't enforce immutability of these fields either.

Consequently, a user permitted to `update`/`patch` an existing `CompositePodGroup` object can submit an update that sets `spec.Priority` to any integer (e.g. `2147483647`, exceeding `scheduling.HighestUserDefinablePriority`), or changes `spec.PriorityClassName` to reference a higher-privilege `PriorityClass` (including cluster-critical classes) without the value being re-validated against the class, and without going through the same consistency check enforced at create time. Neither the admission plugin nor object validation catches this because both are wired to run only on `Create`.

### Impact Explanation
This breaks the core invariant of the priority-class subsystem: that `spec.Priority` is derived exclusively from an admission-resolved `PriorityClass` and can never be set directly by a caller. An attacker with only namespace-scoped update rights on `compositepodgroups` can grant a workload an arbitrary, unbounded scheduling priority/preemption capability post-creation, which the scheduler and preemption logic will honor as if it were legitimately derived from a `PriorityClass`. This matches the Kubernetes bounty impact class "Admission bypass leading to control of a protected field" and can lead to unfair preemption of other tenants' pods / denial-of-service against co-located workloads, i.e. privilege escalation within the scheduling subsystem.

### Likelihood Explanation
Exploitation only requires standard RBAC `update` (or `patch`) verb on the `compositepodgroups` resource in a namespace the attacker already has access to — a permission level plausible for ordinary workload owners who are expected to manage their own `CompositePodGroup` objects, and does not require `create` on `priorityclasses` or any elevated cluster role. The feature is gated behind the `CompositePodGroup` feature flag but requires no other precondition; the attack is a single API `PATCH`/`PUT` call and is fully repeatable.

### Recommendation
Extend `Plugin.Admit` to also invoke `admitCompositePodGroup` (and `admitPodGroup`) on `admission.Update`, mirroring the `admitPod` pattern: on update, reject any attempt to change `Spec.Priority`/`Spec.PriorityClassName`/`Spec.PreemptionPolicy` from the previously admitted values (or re-run priority-class resolution and enforce consistency). Additionally, add explicit immutability checks for these fields in `ValidateCompositePodGroupUpdate` and `ValidatePodGroupUpdate` in `pkg/apis/scheduling/validation/validation.go`, analogous to `ValidatePriorityClassUpdate`'s immutable-field checks.

### Proof of Concept
Unit test plan (add to `plugin/pkg/admission/priority/admission_test.go`):
1. Enable `CompositePodGroup` feature gate; create a `PriorityClass` "low" (value 100) and "high" (value 900 or system-cluster-critical-equivalent).
2. Admit-create a `CompositePodGroup` with `PriorityClassName: "low"`; assert `Spec.Priority == 100`.
3. Submit an `Update` attributes call (via `p.Admit`) on the same object changing `Spec.PriorityClassName` to `"high"` and/or directly setting `Spec.Priority = 2147483647` with no consistency check.
4. Assert current (vulnerable) behavior: `Admit` returns `nil` (no error) and the object passed to storage still has attacker-supplied `Spec.Priority`/`Spec.PriorityClassName` unchanged/unvalidated — i.e., `Admit` never called `admitCompositePodGroup`, and `ValidateCompositePodGroupUpdate` returns no errors for the changed spec fields.
5. Expected assertion after fix: the update request is rejected (`admission.NewForbidden`) or the field is forcibly overwritten back to the original value, and `field.ErrorList` from `ValidateCompositePodGroupUpdate` contains a "may not be changed in an update" error for `spec.priority`/`spec.priorityClassName`.
