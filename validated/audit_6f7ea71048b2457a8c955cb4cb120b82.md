Confirmed: `WebhookMetadata` is constructed directly from `request.shop` (the `x-shopify-shop-domain`/`shopify-shop-domain` header) with no cross-check against the signed body, as shown in `lib/shopify_api/webhooks/registry.rb:198-199`.

### Title
Webhook shop identity spoofing via HMAC that only covers the raw body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable content from the raw request body only, while the `shop` value handed to application webhook handlers is read from an unauthenticated HTTP header. This breaks the intended binding `hmac_signed_bytes == bytes_the_app_trusts_for_tenant_identity`, allowing a valid webhook payload/HMAC pair (signed with the app's shared secret) to be replayed with a different `shop-domain` header, causing the app to attribute an event to the wrong shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`request.shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, then dispatches to the handler using the unauthenticated `request.shop`, with no comparison between the header-derived shop and anything cryptographically bound to it: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`, i.e., the raw body for webhooks, and compares against the `hmac-sha256` header, again without incorporating `shop`: [4](#0-3) 

Because a Shopify app uses **one shared `api_secret_key`** to sign webhooks for **every shop** that has the app installed, a valid `(raw_body, hmac)` pair obtained from a webhook delivered for one shop (e.g. a merchant's own store where the attacker is an installed/unprivileged user of a multi-tenant app) remains a cryptographically valid HMAC no matter what `shop-domain` header accompanies it. The identity binding this code should enforce is:
```
shop_the_HMAC_was_computed_for == shop_the_handler_believes_it_is_processing_for
```
but the implementation only enforces:
```
hmac(raw_body) == received_hmac
```
with `shop` supplied out-of-band and unverified.

### Impact Explanation
An attacker who can obtain any one valid `(raw_body, hmac)` pair signed by the app's secret (e.g., by triggering a webhook on their own tenant, which is an unprivileged, self-service action for any merchant/store owner using a multi-tenant app) can resubmit that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The application will treat the event as authentic and originating from the victim shop named in the header, since `Registry.process` never cross-checks the header-derived `shop` against anything covered by the signature. Depending on the webhook handler's logic (e.g., `customers/redact`, `shop/redact`, `app/uninstalled`, or business-logic handlers keyed by `shop`), this enables cross-tenant confusion: state changes, redaction, or data attributed to the wrong tenant, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
The attack requires only: (1) being an installed/unprivileged user of the app on any one shop to legitimately receive one signed webhook, and (2) the ability to POST to the app's public webhook endpoint with modified headers — both trivially available to an "unprivileged internet user" with no access to `api_secret_key`, tokens, or TLS interception. The victim shop identifier is guessable/enumerable (`*.myshopify.com` domains are often known or discoverable), making this practically exploitable wherever the host application relies on `WebhookMetadata#shop` for tenant scoping without independent verification.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified content, or otherwise ensure the shop domain used for tenant dispatch is not solely header-derived. At minimum, document/require host applications to independently verify that `request.shop` corresponds to a shop with an active, matching session/installation before trusting it, and consider incorporating the `shop-domain` header into `to_signable_string` (mirroring how Shopify's own webhook signature does NOT cover headers—so the library must not treat the header shop as authenticated by that signature).

### Proof of Concept
1. App has two installed shops: `attacker-shop.myshopify.com` (attacker-controlled/unprivileged) and `victim-shop.myshopify.com`, both signed with the same `api_secret_key`.
2. Attacker triggers any webhook-emitting action on their own shop (e.g., updates a product), causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: H` and `x-shopify-shop-domain: attacker-shop.myshopify.com` to the app's webhook endpoint. Attacker captures `B` and `H` (e.g., via their own reverse proxy/logging, which is unprivileged since it's their own traffic).
3. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `hmac(B)`. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:190-199` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to act on victim-shop's tenant context using attacker-supplied body content.
