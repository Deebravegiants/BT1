### Title
Unbounded `Vec<Message>` batch size with flat static weight in `pallet_ismp::handle_unsigned` enables free, unbounded-cost DoS on block execution and mempool validation - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::handle_unsigned` accepts an arbitrary-length `Vec<Message>` from an unsigned, feeless extrinsic and executes every message in the batch via `Self::execute(messages.clone())` [1](#0-0)  both at dispatch time and — critically — again inside `validate_unsigned`, which every node runs during mempool/gossip validation before the extrinsic is even included in a block [2](#0-1) . The call's declared weight is a flat constant, independent of `messages.len()`:
```rust
fn weight() -> Weight {
    Weight::from_parts(300_000_000, 0)
}
``` [3](#0-2) 

This is the same bug class as the reported `WalletImpl.execCalls` issue: an externally-controlled array whose length can "grow indefinitely" is iterated over in full inside a single state transition, with no cap and no cost scaling to the attacker.

### Finding Description
`handle_unsigned` is an unsigned extrinsic — "This allows users execute ISMP datagrams for free" [4](#0-3)  — so submitting it costs the caller nothing, no transaction fee is charged, and `ensure_none(origin)?` is the only origin check [5](#0-4) .

Each `Message` in the request/response handlers performs real cryptographic work per element — Merkle-Mountain-Range / state-trie membership or non-membership proof verification, request hashing, receipt lookups, dispatch to modules — as seen in the analogous EVM handler loops over `requests`/`timeouts` arrays [6](#0-5)  and the Substrate request handler's per-request loop [7](#0-6) .

Because:
1. `messages: Vec<Message>` has no `BoundedVec`/length cap enforced before `Self::execute` runs, and
2. the extrinsic's declared `#[pallet::weight(weight())]` does not scale with `messages.len()`,

an attacker can submit a single `handle_unsigned` call carrying a very large `Vec<Message>` (e.g., many `RequestMessage`/`GetResponseMessage`/`PostRequestTimeoutMessage` entries with syntactically well-formed but ultimately-invalid proofs, or many nearly-valid ones), and the runtime will fully iterate/verify all of them before rejecting. Since `Self::execute` is invoked again inside `validate_unsigned`, **every peer node in the network** performs this unbounded verification work merely to validate the transaction for gossip, before any block-weight accounting or fee deduction applies. This is a mempool-level, network-wide, zero-cost amplification DoS — strictly worse than the reported analog because the attacker doesn't even need the transaction to be included in a block to inflict the cost.

### Impact Explanation
An attacker can force every collator/full node validating the unsigned extrinsic pool to spend CPU time proportional to an attacker-chosen array length doing full ISMP message verification (proof checks, hashing, storage reads) for free, repeatedly and in parallel across many such extrinsics. This can degrade block production time, delay legitimate relayed messages (funds/settlement in flight via requests/responses), and in aggregate constitutes a resource-exhaustion DoS against the routing/consensus-verification path that Hyperbridge depends on for cross-chain message delivery — directly affecting the "EvmHost/HandlerV2 dispatch and delivery" and "pallet-ismp handle_unsigned" paths named in scope. It does not directly cause theft, but it can starve message delivery / block production, which is the qualifying "route unable to deliver messages" impact category.

### Likelihood Explanation
High feasibility: the extrinsic is permissionless, unsigned, and fee-free by design, needing only syntactically valid (not necessarily provably-correct) `Message` structures to reach the verification loops. No additional privilege, timing, or race condition is required — a single crafted extrinsic with a large `Vec<Message>` suffices, and it can be resubmitted continuously at zero cost.

### Recommendation
- Enforce a hard cap on `messages.len()` for `handle_unsigned` (e.g., via `BoundedVec` with a `MaxMessagesPerBatch` config constant), rejecting oversized batches in `pre_dispatch`/`validate_unsigned` before any verification work begins.
- Make the declared weight for `handle_unsigned` scale with `messages.len()` (linear component) rather than a flat constant, so `frame_system::CheckWeight` can correctly bound per-block inclusion.
- Consider adding a lightweight, cheap-to-evaluate pre-check (e.g., cap on encoded length, or per-message-type minimal well-formedness check) inside `validate_unsigned` before invoking the full `Self::execute` path, to avoid doing expensive proof verification during pool validation for batches that are trivially oversized or malformed.

### Proof of Concept
1. Craft `messages: Vec<Message>` containing N (e.g., 10,000+) `Message::Request(RequestMessage { requests: [...], proof: ..., signer: [] })` entries, each with a syntactically valid but bogus/invalid proof, sized just under any implicit extrinsic-length limits.
2. Submit as an unsigned extrinsic `Ismp::handle_unsigned(messages)`.
3. Every node performing `validate_unsigned` executes `Self::execute(messages.clone())` [2](#0-1) , which iterates and verifies membership proofs / hashes for all N entries before failing — consuming CPU proportional to N for free, network-wide, with declared weight fixed at `Weight::from_parts(300_000_000, 0)` regardless of N [3](#0-2) .
4. Repeat with many concurrent such extrinsics to amplify load across the network's mempool validators.
