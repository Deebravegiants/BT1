### Title
Unprivileged UMP-queue flooding can starve the mandatory `UMPSignal::SelectCore` scheduling tail via `check_upward_messages` capacity/size checks - (File: polkadot/runtime/parachains/src/inclusion/mod.rs)

### Summary
`check_upward_messages` enforces `max_upward_queue_count`/`max_upward_queue_size` against the combined footprint of a parachain's UMP queue (`T::MessageQueue::footprint(UmpQueueId::Para(_))`), rejecting an entire candidate's UMP batch—including any appended `UMPSignal::SelectCore`—if the limits would be exceeded. Because ordinary user/collator-submitted UMP messages and the protocol-mandated `SelectCore` signal share the same per-para queue/footprint and the same capacity check, an attacker who can keep the queue saturated (e.g., by exploiting a stuck overweight head message, or simply by sustained flooding while relay-side dequeue lags) can cause legitimate candidates carrying `SelectCore` to be rejected outright.

### Finding Description
`check_upward_messages` in `polkadot/runtime/parachains/src/inclusion/mod.rs` computes the para's current queue count/size from `T::MessageQueue::footprint(UmpQueueId::Para(para))` and compares `count + upward_messages.len()` / `size + total_bytes` against `config.max_upward_queue_count` / `config.max_upward_queue_size`, returning `Error::CapacityExceeded` / `Error::TotalSizeExceeded` if breached. This check is applied to the whole `upward_messages` vector of a candidate commitment as a unit—there is no separation of "protocol signal" messages (the UMP separator + `UMPSignal::SelectCore`) from ordinary application-level UMP messages in terms of queue admission priority. If a candidate's batch (user messages + trailing `SelectCore` signal) does not fit under the configured limits because the queue is already saturated with prior (possibly attacker-driven) messages, the entire candidate is rejected, and the `SelectCore` signal never reaches processing, meaning core assignment/elastic-scaling scheduling for that para stalls.

The precondition that makes this attacker-triggerable at meaningful cost is that the relay-side dequeue of the para's UMP `MessageQueue` is stalled or slow relative to enqueue rate—most concretely via a stuck overweight message at the head of the para's message queue (a known message-queue scenario), or otherwise by an attacker being able to enqueue messages faster than they drain. Once the queue sits at or near `max_upward_queue_count`/`max_upward_queue_size`, any subsequent candidate—whether it carries ordinary messages or the mandatory `SelectCore` tail—fails the same capacity check and is rejected with `CapacityExceeded`/`TotalSizeExceeded`.

However, I was not able to fully verify, within available search results, the precise mechanics of (a) whether an unprivileged para-side actor (a normal user on the parachain, not the collator/runtime) can force parachain-runtime-level UMP message submission at high enough rate independent of collator cooperation, and (b) whether `SelectCore` is queued through the exact same `UmpQueueId::Para` footprint check path or is exempted/prioritized elsewhere (e.g. in `paras_inherent` before calling into `process_candidates`/`check_upward_messages`). The grep evidence shows `SelectCore` is referenced in `paras_inherent/mod.rs`, `builder.rs`, and `inclusion/tests.rs`, and `UMPSignal`/separator constants exist in `inclusion/mod.rs`, but I could not confirm from the available context whether there's an explicit reservation/carve-out of queue capacity for the signal message distinct from the general capacity check, which would materially change the validity of this finding.

### Impact Explanation
If confirmed as described, the impact is a denial-of-service on a specific parachain's V3 elastic-scaling core-selection mechanism: `SelectCore` signals get rejected alongside ordinary messages when the queue is saturated, so the affected para cannot get core assignment via that signal until the queue drains, i.e., until the overweight/stuck message is dealt with or the flood stops. This is scoped to core-selection/scheduling starvation for the targeted para rather than fund loss or cross-para bypass.

### Likelihood Explanation
Feasibility hinges entirely on the unverified precondition: a normal unprivileged extrinsic path must be able to (1) enqueue UMP messages cheaply and repeatedly and (2) cause or exploit a stuck-overweight-at-head condition in the relay-side `MessageQueue` for that para, since without a stalled dequeue, the relay chain would simply keep processing/dequeuing messages, freeing capacity between blocks, making sustained saturation costly/unlikely under normal throughput. Whether ordinary users (not the collator, which controls what goes into a candidate's `upward_messages`) can trigger this from a signed extrinsic/XCM path without collator cooperation was not established in the available context.

### Recommendation
If validated, decouple `SelectCore`/protocol UMP signal admission from the ordinary-message capacity check—e.g., reserve queue capacity/count/size headroom in `check_upward_messages` (and the underlying `max_upward_queue_count`/`max_upward_queue_size` accounting) specifically for the mandatory signal message, or check/enqueue the signal message before applying capacity limits to user messages, ensuring `SelectCore` can never be starved by application-level UMP congestion. Additionally, ensure relay-side overweight-message handling cannot indefinitely block dequeue of a para's UMP queue.

### Proof of Concept
Integration test plan (in `polkadot/runtime/parachains/src/inclusion/tests.rs` or `ump_tests.rs`):
1. Configure a test para with small `max_upward_queue_count`/`max_upward_queue_size`.
2. Enqueue an overweight message at the head of the para's `MessageQueue` (via `UmpQueueId::Para`) so it cannot be serviced/dequeued (simulate stuck-overweight scenario).
3. Submit consecutive candidates with ordinary UMP messages until `footprint(UmpQueueId::Para(para))` count/size reaches `max_upward_queue_count`/`max_upward_queue_size`.
4. Submit one more candidate whose `upward_messages` includes a valid `UMPSignal::SelectCore` signal (with correct separator) plus minimal/no additional payload.
5. Assert `check_upward_messages` (via `process_candidates`/inherent processing) returns `Error::CapacityExceeded` or `Error::TotalSizeExceeded`, and that `SelectCore` is never processed/observed by the scheduler for that para in the resulting block, i.e., no core assignment/rotation happens even though a valid signal was included.

Given the unresolved questions about (a) whether unprivileged users (versus collators) directly control what's placed in `upward_messages`, and (b) whether `SelectCore` has a separate reservation/admission path bypassing this exact capacity check, I cannot state with full confidence that this is a real, currently-exploitable bug as opposed to a described-but-unconfirmed interaction. Based on available evidence, the queue-capacity/DoS mechanism as described in `check_upward_messages` is real, but the attacker-controlled entry path (unprivileged user, not collator/node) driving it was not conclusively verified in the retrieved code.
