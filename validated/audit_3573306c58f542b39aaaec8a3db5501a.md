### Title
Escrow withdrawal in IntentGatewayV2/`IntentsBase._withdraw` bundles multiple, independently chosen tokens into a single atomic transfer, so a paused/blacklist-capable input or output token permanently blocks release of all co-escrowed (otherwise healthy) tokens — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`Order.inputs` and `Order.output.assets` let a user/solver freely pick any set of ERC20 addresses to escrow together in one order. Settlement (`_withdraw`) and same-chain fill/cancel iterate over that token list and perform a `safeTransfer`/`safeTransferFrom` for each entry inside a single, all-or-nothing loop. If any one of those tokens becomes non-transferable — e.g. an ERC20 with an owner-side `pause()`/blacklist function unrelated to Hyperbridge (USDC-style blacklist, a pausable token, a rebasing/fee token that reverts) — the whole withdrawal reverts, and none of the other, perfectly healthy tokens in that same order can be released either. This is directly analogous to the CryptoKitty/CryptoFighter report, where a single pausable collateral asset blocked an otherwise-completable repay/liquidate action and locked funds that had nothing to do with the paused asset itself.

### Finding Description
`IntentsBase._withdraw` releases every token in `body.tokens` in one loop, decrementing escrow and calling `IERC20(token).safeTransfer(beneficiary, amount)` per token: [1](#0-0) 

This function is the single choke point for both:
- Cross-chain settlement via `onAccept` → `RedeemEscrow`/`RefundEscrow` (`ExtrinsicIntents.sol`), and
- Same-chain fill/cancel (`IntrinsicIntents._fillSameChain`, `_cancelSameChain`), [2](#0-1) [3](#0-2) 

There is no per-token isolation (e.g. try/catch, or splitting the withdrawal into independent calls) — a revert on any single token aborts the entire withdrawal, including the `_filled[commitment]` finalization and the release of every other, unaffected token in the order.

For the cross-chain path, `EvmHost.dispatchIncoming` does catch the outer `onAccept` revert and marks the request as retryable rather than permanently discarding it: [4](#0-3) 

but that only means the *entire* settlement message keeps failing and can be resubmitted indefinitely — it does not let the healthy tokens in the bundle be released while the problematic one stays blocked. As long as the offending token remains paused/blacklisted for the gateway address (which, for real-world tokens such as USDC-style blacklists, can be indefinite/permanent, not a bounded "pause window"), the entire order's escrow — every token in it — is frozen. For the same-chain path (`_fillSameChain`/`_cancelSameChain`), there is no host-level retry semantics at all: the transaction simply reverts, and no partial release of the safe tokens is possible until the bad token becomes transferable again.

Because `order.inputs`/`order.output.assets` are arbitrary, attacker-or-user-chosen token lists with no allowlist, any unprivileged order creator (or a solver picking output tokens) can — deliberately or accidentally — mix a reputable token with one that is pausable/blacklistable by its own issuer, permanently freezing the whole bundle for both the user and the solver who already performed their side of the exchange.

### Impact Explanation
- On the cross-chain fill flow (`_fillCrossChain`), the solver already delivers the required output tokens to the beneficiary *before* the `RedeemEscrow` message is dispatched. If the settlement message can never successfully execute `_withdraw` (because one of several escrowed input tokens is frozen), the solver's already-paid-out capital is stuck: escrow release for the healthy tokens in that same order is bundled with the frozen one and permanently blocked.
- On cancellation (`_cancelFromDest`/`_cancelFromSource`/`_cancelSameChain`), the user's refund is similarly all-or-nothing across the input token list — a single frozen input token in a multi-asset order blocks the user from ever getting back the other, unaffected tokens.
- This is a genuine freezing-of-funds condition reachable purely from unprivileged order placement/filling, with no admin or governance action involved, matching the accepted impact class (permanent freezing of funds via a route unable to deliver messages / release escrow).

### Likelihood Explanation
Likelihood is moderate to high: any user can construct an order with multiple input/output tokens, and there is no validation restricting `order.inputs`/`order.output.assets` to a vetted allowlist of "safe" tokens. Malicious or careless combination of a normal token with a pausable/blacklistable one is trivial to construct, and many widely used tokens (USDC, USDT, and various compliance-gated tokens) support address-level freezing that is realistically permanent from the protocol's perspective.

### Recommendation
- Release/refund each token in `body.tokens` independently (e.g., wrap each transfer in a low-level call with its own success tracking and let unaffected tokens settle immediately), rather than reverting the whole withdrawal on a single token failure.
- Track partial settlement per-token so that once a previously-frozen token becomes transferable again, only its escrow needs to be retried, instead of leaving the whole order un-finalized.
- Consider an explicit allowlist/registry of tokens permitted as order inputs/outputs, or a documented risk disclosure that mixing tokens with frozen bundling risk is unsupported.

### Proof of Concept
1. User places a cross-chain order with `order.inputs = [GOOD_TOKEN, BAD_TOKEN]` where `BAD_TOKEN` is a standard ERC20 with an owner-controlled `pause()`/blacklist hook (evm/src/apps/intentsv2/ExtrinsicIntents.sol `placeOrder`/escrow credit loop).
2. A solver fills the order on the destination chain, delivering `order.output.assets` to the beneficiary and dispatching `RedeemEscrow` (`_fillCrossChain`, evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220).
3. `BAD_TOKEN`'s issuer pauses/blacklists the gateway address before the settlement message is delivered.
4. The relayer submits the `RedeemEscrow` message; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw`, which loops over `[GOOD_TOKEN, BAD_TOKEN]`; the `BAD_TOKEN` `safeTransfer` reverts, the whole call reverts, and `EvmHost.dispatchIncoming` deletes the receipt so it "can be retried" (evm/src/core/EvmHost.sol:809-817).
5. As long as `BAD_TOKEN` stays paused/blacklisted, `GOOD_TOKEN` also cannot be released to the solver — despite `GOOD_TOKEN` being fully transferable — because both tokens are bundled in the same `_withdraw` call. [1](#0-0) [5](#0-4)

        address beneficiary = address(uint160(uint256(body.beneficiary)));

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
