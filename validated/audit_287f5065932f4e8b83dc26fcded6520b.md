## Analog Found

### Title
Stale cached `UserData` (backend authorization/identity keys) reused for signup because freshness is checked against the operator QR-code timestamp, not the user validation itself - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::scan_remaining_qr_codes` and its underlying `QrCodes::Both` state cache a backend-validated `backend::user_status::UserData` (self-custody keys, backend encryption keys, `id_commitment`, `user_centric_signup`, `pcp_version`) together with an `OperatorData` struct. When resuming a signup, the code decides whether the *entire cached tuple* — including the user data — is still usable by checking only `operator_data.timestamp.elapsed() < operator_qr_expiration_time`. There is no independent freshness/re-validation check on the user data itself, mirroring the reported bug class where a critical authorization decision relies on a stale cached value instead of re-fetching the current state from the source of truth.

### Finding Description
`QrCodes` is an enum holding either just operator data, or both operator and user data: [1](#0-0) 

`scan_remaining_qr_codes` decides how to proceed with a pending signup: [2](#0-1) 

For the `QrCodes::Both { operator_data, user_qr_code, user_data, user_qr_code_string }` arm, the *only* guard is `operator_data.timestamp.elapsed() < operator_qr_expiration_time`. If that holds, the code immediately proceeds to build a `ResolvedQrCodes` using the already-cached `user_data` — the backend keys, `self_custody_user_public_key`, `id_commitment`, and `user_centric_signup`/`pcp_version` flags that were fetched and validated by `backend::user_status::request` at some earlier point in time (potentially up to `operator_qr_expiration_time`, whose default is 23 hours): [3](#0-2) 

This cached `user_data` is then used directly to build the identity-binding credentials for the Personal Custody Package (PCP) and to decide the enrollment path: [4](#0-3) [5](#0-4) [6](#0-5) 

The `UserData` returned by the backend encodes identity-relevant claims (`id_commitment`, `self_custody_user_public_key`, `user_centric_signup`, `pcp_version`) that are meant to reflect the current backend state of that user's session: [7](#0-6) 

Just like the Morpho `_isLiquidatable` bug — where a critical solvency decision used a possibly-stale P2P index instead of re-deriving current state — here the critical identity-binding/enrollment decision reuses a possibly-stale `UserData` snapshot, gated only by a proxy timestamp (the *operator's* QR freshness) that has no logical connection to whether the *user's* backend-side session/authorization state is still valid. Nothing re-invokes `backend::user_status::request` (the actual freshness/authorization check, analogous to `updateP2PIndexes`) before this cached data is used to build cryptographic identity-binding credentials and decide enrollment routing.

### Impact Explanation
If the backend has since invalidated, revoked, or altered the user's session (e.g., the user status changed, keys were rotated, or the session was otherwise finalized/cancelled on the backend) after the initial `verify_user_qr_code` call but before `scan_remaining_qr_codes` re-uses the cached tuple, the orb will still build and upload the personal-custody package and drive enrollment using the outdated `self_custody_user_public_key`/`id_commitment`/`pcp_version`. This can result in identity-binding credentials being issued/uploaded for a user session the backend no longer considers current or valid — a misattributed-signup-state risk directly analogous to the reported staleness class, since the freshness check used (`operator_data.timestamp`) is not the same entity whose staleness matters (`user_data`).

### Likelihood Explanation
This code path is reached in the normal self-serve idle flow whenever a signup is resumed with previously-cached QR data (`QrCodes::Both`), and the guard window is the full `operator_qr_expiration_time` (23 hours by default) — a long window during which backend-side user state can change without the orb re-checking it. No special privileges or malicious actor are required; it's a logic/state-management gap in the ordinary unprivileged signup flow.

### Recommendation
Track a separate timestamp/freshness marker for `user_data` (not just `operator_data.timestamp`), and re-invoke `backend::user_status::request` (or otherwise re-validate) whenever the cached `user_data` is older than an appropriate freshness threshold, before using it to build PCP credentials or decide enrollment routing — analogous to always calling an "update" step before any downstream critical decision that depends on that state.

### Proof of Concept
Not applicable in the strict PoC sense (this is a logic/state-caching gap, not an exploit primitive) — the reachable path is:
1. Orb performs `scan_initial_qr_codes` + `idle_scan_user_qr_code` in self-serve mode, obtaining `user_data` via `backend::user_status::request`, forming `QrCodes::Both { operator_data, user_data, .. }`. [8](#0-7) 
2. Time passes (up to `operator_qr_expiration_time`, default 23h) — backend-side user state may change.
3. `do_signup` → `scan_remaining_qr_codes` is entered with the stale `QrCodes::Both`; guard only checks `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, so the stale `user_data` is used as-is with no backend re-validation. [9](#0-8)

impl QrCodes {
    fn with_user_qr_code(
        &self,
        user_qr_code: qr_scan::user::Data,
        user_data: backend::user_status::UserData,
        user_qr_code_string: String,
    ) -> Self {
        match self {
            QrCodes::Operator { operator_data } => QrCodes::Both {
                operator_data: operator_data.clone(),
                user_qr_code,
                user_data,
                user_qr_code_string,
            },
            QrCodes::Both { .. } => panic!("user QR code is already present"),
            QrCodes::None => panic!("no operator QR code"),
        }
    }

    fn operator_timestamp(&self) -> Option<Instant> {
        match self {
            QrCodes::Operator { operator_data } | QrCodes::Both { operator_data, .. } => {
                Some(operator_data.timestamp)
            }
            QrCodes::None => None,
        }
    }
}
