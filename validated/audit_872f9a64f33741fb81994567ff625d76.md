### Title
Cache key collision in `DirectBridge.getCachedStorageDepositValue` causes storage-deposit fee to be skipped for the wrong NEAR account, leading to stuck withdrawals - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge` caches whether a destination NEAR account already has sufficient NEP-141 storage balance on a given token contract, to avoid a fee-estimation RPC round trip on every call. The cache key is built by naive string concatenation of `contractId` and `accountId` with no separator: [1](#0-0) 

Because two different `(contractId, accountId)` pairs can produce the identical concatenated string (e.g. `"aaa.near" + "bbbb.near"` == `"aaa.nearb" + "bbb.near"`), the cache can return a stale "storage is sufficient" result for a completely different token/destination pair. This causes `estimateWithdrawalFee` to omit the required `storageDepositFee`, and `createWithdrawalIntents` to build a withdrawal intent without the storage deposit the destination account actually needs.

### Finding Description
`estimateWithdrawalFee` decides whether a `storage_deposit`-equivalent fee must be charged by comparing `minStorageBalance` vs. `userStorageBalance`, fetched (and cached) per `(contractId, accountId)` pair: [2](#0-1) 

The cache lookup/store key is `` `${contractId}${accountId}` `` — a plain string concatenation with no delimiter, so the mapping from key back to `(contractId, accountId)` is not injective. If a caller (or a shared multi-tenant SDK instance serving many users) first triggers a fee estimation for `(contractId=T', accountId=D')` where `D'` already has sufficient storage on `T'` (only such "sufficient" results get cached, per line 295-297: `if (result[1] >= result[0]) { this.storageDepositCache.set(key, result); }`), and `T' + D'` happens to equal `T + D` for a different, real target token/destination pair, then a later legitimate call for `(T, D)` will hit the poisoned cache entry and be told storage is sufficient — even though the real destination `D` on token `T` has no registered storage.

Since `contractId` is fully attacker-controlled in NEAR (an attacker can deploy an arbitrary NEP-141-compatible contract at any account name they choose, including engineered names), an attacker can deliberately construct a colliding `T'`/`D'` pair whose concatenation matches any target `(T, D)` combination, register storage for their own `D'` on their own `T'`, call `estimateWithdrawalFee` to seed the cache, and then have any subsequent (their own or another concurrent user's) withdrawal for `(T, D)` silently skip the storage deposit fee.

`createWithdrawalIntents` then builds the withdrawal intent using the (wrongly) zeroed `storageDepositFee`: [3](#0-2) 

The equality broken is: *the fee charged for a withdrawal must correspond exactly to the storage state of the actual `(token, destination)` pair being withdrawn to* — instead it is keyed by an ambiguous, collidable cache key that can bind the wrong pair's cached state to the transaction being built.

### Impact Explanation
When the storage deposit fee is wrongly omitted, the on-chain `ft_transfer`/`ft_withdraw` to an unregistered destination account fails at the NEP-141 contract level (receiver not registered for the token). The funds have already been debited from the user's intents balance (via the `ft_withdraw`/`token_diff` intents), but the receiving leg fails, leaving the withdrawal stuck and requiring manual intervention/recovery — this matches the High-severity class "a withdrawal stuck until manual intervention" / fee undercharge. In a shared/multi-tenant deployment of the SDK (a single `IntentsSDK`/`DirectBridge` instance serving multiple users, e.g. a backend service), one user can poison the cache to affect another user's withdrawal, not just their own.

### Likelihood Explanation
Exploitability requires: (1) an in-memory `DirectBridge` instance shared across multiple withdrawal requests (the normal server-side usage pattern for this SDK, since the cache is an instance-level `LRUCache`), and (2) the ability to deploy/control a NEAR account/contract whose name, concatenated with a chosen registered account name, matches the victim's `contractId + destinationAddress` string. Both are achievable by an unprivileged NEAR user without needing the relayer, bridge operator, or any admin to act maliciously — deploying subaccounts and NEP-141-like contracts on NEAR is permissionless.

### Recommendation
Use a delimiter that cannot appear ambiguously in either component (or a structured key, e.g. an array/tuple, or `JSON.stringify([contractId, accountId])`, or a hash of both fields) when building `storageDepositCache` keys, e.g.:
```ts
const key = `${contractId}:${accountId}`;
```
is still not fully safe if `:` can appear in NEAR account IDs’ crafted contract names combined with attacker-chosen structure — prefer length-prefixed or JSON-encoded keys to guarantee injectivity. Apply the same audit to any other cache in the bridges directory that concatenates two independent identifiers into a single string key.

### Proof of Concept
1. Attacker deploys/controls a NEP-141-compatible contract at NEAR account `T'` and registers storage for account `D'`, chosen such that `T' + D' === T + D`, where `T` is a real supported token contract and `D` is the real destination address of a pending or future legitimate withdrawal (the attacker's own, or — if the SDK instance is shared — another user's).
2. Attacker calls `sdk.estimateWithdrawalFee({ withdrawalParams: { assetId: "nep141:"+T', destinationAddress: D', ... } })`. Because `D'` has sufficient storage on `T'`, `DirectBridge.getCachedStorageDepositValue` caches `[minStorageBalance, userStorageBalance]` under key `T' + D'` (`direct-bridge.ts` lines 273-300).
3. A legitimate (or the attacker's own) call to `sdk.estimateWithdrawalFee({ withdrawalParams: { assetId: "nep141:"+T, destinationAddress: D, ... } })` computes the same cache key `T + D` and hits the poisoned entry, returning `storageDepositFee: 0`.
4. `sdk.createWithdrawalIntents` builds the `ft_withdraw` intent with `storageDeposit` derived from this zero fee (`direct-bridge.ts` lines 133-144), omitting the needed storage registration for `D` on `T`.
5. On execution, the receiving leg fails on-chain because `D` is not registered on `T`, leaving the withdrawal stuck without the deducted funds being delivered — requiring manual recovery.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
