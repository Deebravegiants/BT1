### Title
ALCX-rewards-style permanent freezing: outbound-request delivery reward becomes unclaimable if the request's `RequestCommitments` entry is deleted by a timeout race before the relayer submits its claim - (File: `modules/pallets/relayer/src/outbound_request.rs`)

### Summary
`pallet-relayer`'s outbound-request delivery reward claim (`claim_outbound_request_delivery_reward`) requires the request's commitment to still be present in `pallet_ismp::child_trie::RequestCommitments` at claim time. That same commitment entry is unconditionally deleted the moment anyone processes a timeout for the same request via `handle_timeouts`, with no check for whether the request was already delivered to its destination. A relayer that legitimately delivers a hyperbridge-originated request and earns a reward can therefore have that reward permanently and irrecoverably destroyed if a timeout for that same request lands on hyperbridge before the relayer's claim does — exactly the same "reward tied to a destroyable identifier" bug class as the reported ALCX/VotingEscrow issue, where merging (burning) `token_1` permanently orphans its unclaimed ALCX because `RewardsDistributor::claim` requires the token to still exist.

### Finding Description
`process_outbound_request_delivery_claim` gates every claim on local presence of the commitment: [1](#0-0) 

This mirrors the report's `require(approvedOrOwner || isVotingEscrow, "not approved")` gate in `RewardsDistributor::claim`, which reverts once the underlying token (identifier) is gone.

The commitment is removed from storage by the timeout pipeline, independent of whether the request was actually delivered to its destination: [2](#0-1) 

The concrete storage removal happens in the pallet-ismp host implementation: [3](#0-2) 

and the underlying child-trie primitive used for that removal: [4](#0-3) 

Crucially, the timeout handler on the source chain (hyperbridge) only checks that the *destination's* observed timestamp has passed `timeout_timestamp` — it has no way of knowing whether the destination already processed and delivered the request: [5](#0-4) 

So the full race is:
1. A hyperbridge-originated `PostRequest` (module reward-eligible, e.g. host-executive, intents-coprocessor, token-governor, relayer withdrawal) is dispatched and recorded in `RequestCommitments`.
2. Relayer A delivers it to the destination before the destination's clock crosses `timeout_timestamp`, earning delivery-reward eligibility (a `RequestReceipts[commitment]` entry now exists on the destination).
3. Before Relayer A's proof of that delivery lands back on hyperbridge and its `claim_outbound_request_delivery_reward` extrinsic is included, the destination's timestamp state (as observed on hyperbridge) advances past `timeout_timestamp`. Anyone (a different relayer, or even Relayer A itself in a race) submits `handle_timeouts` for the same commitment.
4. `handlers::timeout::handle` deletes `RequestCommitments[commitment]` unconditionally as part of processing the timeout, with no cross-check against the destination's actual delivery state.
5. Relayer A's later `claim_outbound_request_delivery_reward` now fails permanently at `RequestCommitments::<T>::get(commitment).is_some()` with `Error::OutboundRequestNotKnown` — this is not retryable, because the commitment can never be re-inserted.

This is structurally identical to the reported bug: an entitlement (ALCX rewards / relayer delivery reward) is gated on the continued existence of an identifier (veALCX tokenId / `RequestCommitments[commitment]`) that a separate, legitimate protocol action (merge / timeout) can destroy without regard for outstanding claims against it.

### Impact Explanation
The relayer's already-earned `OutboundRequestDeliveryReward` (paid from the Hyperbridge treasury) becomes permanently unclaimable — the funds are not stolen, but the promised reward can never be delivered to the party that did the work, matching "Permanent freezing of unclaimed yield" / "Contract fails to deliver promised returns." Because timeouts are a routine, expected part of ISMP operation (delays, congestion, slow relayers) and are submittable by anyone, this is not a contrived edge case — it can occur under ordinary network delay conditions whenever delivery and claim-proof propagation are slower than the timeout window.

### Likelihood Explanation
Medium-to-High. No privileged action is required on either side of the race: delivering a request and submitting a timeout are both unprivileged, permissionless operations reachable by any relayer or third party. The claim pipeline itself already waits for a challenge period and destination state-commitment propagation before it can be submitted (`observe_challenge_period`, waiting for hyperbridge to see the destination), which widens the window during which a timeout for the same commitment can be submitted by someone else.

### Recommendation
Before deleting `RequestCommitments[commitment]` in the timeout handler, or before rejecting a claim for a missing commitment, check whether a delivery receipt/reward-claim already exists for that commitment (e.g. consult `OutboundRequestsClaimed`/an equivalent "already delivered" record, or defer commitment deletion until any pending reward claim window has closed). Alternatively, decouple the reward-eligibility check from `RequestCommitments` existence entirely — record delivery-claim eligibility in its own persistent map at dispatch time that is never pruned by the timeout path, so a later timeout cannot retroactively invalidate a reward for work already completed.

### Proof of Concept
Conceptual reproduction against the pallet-relayer / pallet-ismp code paths:
1. Dispatch a hyperbridge-originated `PostRequest` from an allowlisted module (`OutboundRequestDeliveryReward[module_id] > 0`) with a short `timeout_timestamp`, so it is recorded in `RequestCommitments` (`modules/pallets/ismp/src/child_trie.rs`).
2. Have Relayer A deliver the request to the destination chain, producing a `RequestReceipts[commitment]` entry there (satisfying the delivery-reward claim's later state-proof check).
3. Advance the destination's observed timestamp on hyperbridge past `timeout_timestamp` (e.g. via a subsequent consensus update), and submit `Message::Timeout(TimeoutMessage::Post { requests: vec![post], timeout_proof })` through `pallet_ismp::Pallet::execute` — this succeeds and calls `host.delete_request_commitment(&request)`, removing `RequestCommitments[commitment]` (as already exercised in `modules/pallets/testsuite/src/tests/pallet_ismp.rs::should_handle_get_request_timeouts_correctly` and `test_dispatch_fees_and_refunds`, which assert the commitment is gone after timeout processing).
4. Relayer A now submits `claim_outbound_request_delivery_reward` with a valid destination delivery proof. The call reaches `ensure!(RequestCommitments::<T>::get(commitment).is_some(), Error::<T>::OutboundRequestNotKnown)` in `modules/pallets/relayer/src/outbound_request.rs` and reverts — permanently, since the commitment can never be restored and the claim can never be resubmitted successfully.

	fn delete_request_commitment(&self, req: &Request) -> Result<Vec<u8>, Error> {
		let hash = hash_request::<Self>(req);
		// We can't delete actual leaves in the mmr so this serves as a replacement for that
		let meta = child_trie::RequestCommitments::<T>::get(hash)
			.ok_or_else(|| Error::Custom("Request Commitment not found".to_string()))?;
		child_trie::RequestCommitments::<T>::remove(hash);
		Ok(meta.encode())
	}
