## Finding

### Title
Unchecked ERC-20 return value in `IntentGatewayV2.withdraw` permanently marks intent orders settled/refunded even when the token transfer silently fails - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` hand-rolls ERC-20 transfers with a low-level `.call()` instead of using the already-imported `SafeERC20` helper used everywhere else in the contract. The success check only verifies that the low-level call did not revert; it never decodes/validates the boolean value the ERC-20 `transfer` function returns. For any token that returns `false` on failure instead of reverting (a common, spec-compliant pattern), the escrow bookkeeping is finalized as if the transfer succeeded, permanently losing the beneficiary's funds inside the contract — the exact same "check exists but doesn't verify actual transfer success" class of bug as the reported `Cooler.rescind` finding.

### Finding Description
`withdraw()` is the internal settlement routine invoked from `onAccept` (for `RedeemEscrow`/`RefundEscrow` cross-chain messages) and `onGetResponse` (for source-chain cancellations) — both reachable by ordinary users who filled or cancelled an intent order: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```

`success` here only reflects whether the external call reverted — it says nothing about the ABI-encoded boolean the ERC-20 returned. Many tokens (older/legacy ERC-20s, tokens with blacklist/pause logic, some bridged/wrapped assets) return `false` on failure rather than reverting. In that case `success == true`, the `if (!success) revert` never fires, `_orders[commitment][token]` is decremented, and (on `SweepDust`, further down in the same file) the same unchecked pattern repeats: [2](#0-1) 

The contract already imports and uses `SafeERC20` for every other ERC-20 movement (`safeTransferFrom` in the fill/place paths), which correctly reverts on both a failed call *and* a `false` return value: [3](#0-2) [4](#0-3) 

`withdraw()` deliberately deviates from that safe pattern for the payout leg, reproducing exactly the `Cooler.rescind` bug class: a guard (`if (!success) revert`) exists but does not actually validate the outcome of the transfer, so escrow state is finalized as complete/settled despite the beneficiary never receiving funds.

### Impact Explanation
Once `_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set, the commitment is considered fully settled. There is no other path to re-trigger payout for that commitment/token pair (any retry would fail `UnknownOrder`/`Filled` checks). Escrowed user or solver funds for that token become permanently stuck in the `IntentGatewayV2` contract with no recovery mechanism, i.e. a direct freezing/loss of user funds triggered by a normal, single-transaction order fill/cancel/refund flow.

### Likelihood Explanation
Reachable by any ordinary intents user: placing and then cancelling/filling an order with a token that returns `false` instead of reverting on failure (e.g., due to a blacklist, pause, or edge-case balance/allowance condition) is enough to trigger the finalize-without-transfer state. No privileged role is required — only a token whose `transfer` implementation is non-conforming in this specific, commonly-seen way.

### Recommendation
Replace the raw `.call()` + `success`-only check in `withdraw()` (and the identical pattern in the `SweepDust` handler) with `SafeERC20.safeTransfer`, mirroring the rest of the contract, so that both call failure and a `false` boolean return revert the transaction and prevent escrow state from being finalized without the funds actually moving.

### Proof of Concept
1. An order escrows a non-standard ERC-20 token (`transfer` returns `false` on failure rather than reverting) as an input.
2. The order is cancelled/refunded such that Hyperbridge delivers a `RefundEscrow` message and `onAccept` → `withdraw()` executes, or the cross-chain `onGetResponse` cancellation path is used.
3. The token's `transfer(beneficiary, amount)` call returns `false` (e.g., due to a blacklist or an internal invariant failure) but does not revert; `token.call(...)` therefore returns `success = true`.
4. `if (!success) revert TransferFailed();` does not trigger, `_orders[commitment][token] -= amount` executes, `_filled[commitment]` is set, and `EscrowRefunded`/`EscrowReleased` is emitted.
5. The beneficiary never receives the tokens, and the escrowed amount can never be withdrawn again for that commitment — funds are permanently lost in the contract.
