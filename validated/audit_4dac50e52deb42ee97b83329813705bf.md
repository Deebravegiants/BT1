### Title
Protocol/relay fees permanently stranded in `ExternalActionSwap`/`LifiExternalAction` balance during self-relay swaps - (`contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
The specific mechanism alleged in the question — `sendToRelay` transferring fees to `address(0)` and "burning" them — does not occur, because `sendToRelay` explicitly no-ops when `relay == address(0)` [1](#0-0) . However, a related and real fee-freezing bug exists: in `ExternalActionSwap.swap`, `hinkalFee` (and `relayFee` when the fee token matches the flat fee) is unconditionally computed and subtracted from `amountToSendToHinkal`, but is only actually paid out via `sendToRelay` when `circomData.relay != address(0)` [2](#0-1) . When a user legitimately self-relays (a path explicitly allowed by `performHinkalChecks`, which requires `originalSender == sender && relay == address(0)`) [3](#0-2) , the fee amount is deducted from the user's credited swap output but never transferred anywhere — it remains as the external action contract's own token balance with no sweep/rescue function anywhere in the codebase.

### Finding Description
Claimed equality (as stated in the question): tokens routed to `relay` by `sendToRelay` == fee amount the signed calldataHash committed the relay to receive, and that `relay == address(0)` causes `sendToRelay` to burn funds to the zero address.

This is false as literally stated: `sendToRelay` in `Transferer.sol` guards `if (relay != address(0) && actualAmount > 0)` before calling `transferERC20TokenOrETH` [1](#0-0) . No transfer to `address(0)` ever happens — the call is simply skipped.

The real broken equality is: `amountToSendToHinkal (credited to user) + totalFee (fee deducted)` should equal `swappedAmount`, and `totalFee` should always reach some recipient (relay or, if self-relayed, some other party such as the protocol treasury or back to the user). Instead:
- `swap()` always computes `relayFee = circomData.feeStructure.flatFee` and `hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, variableRate)` regardless of whether `circomData.relay` is zero [4](#0-3) .
- `totalFee` is subtracted from `amountToSendToHinkal`, which is what gets credited into the user's new UTXO and transferred to `msg.sender` (the Hinkal contract) [5](#0-4) .
- When `circomData.relay == address(0)`, both `sendToRelay` calls are no-ops, so `totalFee` worth of `outputToken` is never sent out of `LifiExternalAction`/`ExternalActionSwap` — it just accumulates as the contract's own balance.
- There is no owner/rescue/withdraw function anywhere in `ExternalActionBaseV2.sol`, `OwnerHinkal.sol`, or the swap contracts to recover this stranded balance; the only sweep-adjacent functions in the whole repo are unrelated to `IWrapper`.

Unlike `_internalTransact` in `Hinkal.sol`, which explicitly skips fee computation entirely when `circomData.relay == address(0)` (fee is only computed inside the `if (circomData.relay != address(0))` branch) [6](#0-5) , `ExternalActionSwap.swap` fails to mirror this behavior — it still charges the fee even for the legitimate self-relay path, and that charged amount becomes permanently unreachable.

`performHinkalChecks`, `dimensionsCheck`, and the calldata-hash integrity check do not prevent this, because `relay == address(0)` combined with `originalSender == sender` is an explicitly valid, non-privileged case [7](#0-6) .

### Impact Explanation
Every self-relayed LI.FI (or any `ExternalActionSwap`-based) swap silently strands `hinkalFee` (and `relayFee` if the fee token equals the output token) worth of the output ERC20/ETH in the external action contract, unrecoverable by anyone (owner included, since no sweep function exists). This is a permanent freezing of protocol fee value — funds simply leave circulation. It does not constitute theft of another user's shielded funds and does not break nullifier/proof/tree invariants; the affected value is only the vig that should have flowed to the relay/protocol. This matches the "High — permanent freezing of protocol/relay fees" category.

### Likelihood Explanation
This triggers on every self-relay swap transaction — no special preconditions beyond `circomData.relay == address(0)` and `circomData.originalSender == msg.sender`, both fully attacker-controlled and part of a documented, intended usage mode (self-relaying to avoid paying a third-party relay). It is fully repeatable on every such swap and requires no privileged role, proof forgery, or exotic setup — only a valid self-generated proof for the swap circuit.

### Recommendation
In `ExternalActionSwap.swap`, mirror the pattern used in `Hinkal._internalTransact`: skip fee computation/deduction entirely (or route it to a designated protocol treasury address instead of `circomData.relay`) when `circomData.relay == address(0)`, so that `totalFee` is either zero or actually reaches a recipient. Alternatively, add a rescue/sweep function restricted to `onlyOwner` on `ExternalActionBaseV2` to recover stranded balances, though the preferred fix is to prevent the balance from becoming stranded in the first place.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock LI.FI router that performs a 1:1 token swap.
2. Craft a valid `CircomData` for a swap with `relay = address(0)`, `originalSender = attacker`, non-zero `feeStructure.flatFee` and `variableRate`, and a locally generated valid proof satisfying `performHinkalChecks`.
3. Call the swap path through `Hinkal` as the attacker (self-relay).
4. Assert: `LifiExternalAction`'s post-swap balance of `outputToken` increases by exactly `totalFee` (i.e., `hinkalFee + relayFee` computed in `swap()`), and this balance is never transferred anywhere in the same or a later independent transaction.
5. Assert there is no function callable by anyone (owner or otherwise) that empties this stranded balance, confirming the freeze is permanent.
