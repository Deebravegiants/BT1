## Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are not covered by the HMAC signature, allowing shop-attribution spoofing on webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC over the raw body only, while the `shop` (and other identity-relevant) values used by webhook handlers come from unauthenticated HTTP headers that are never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#hmac` is computed from the `hmac-sha256` header: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string`, i.e. the raw body only: [3](#0-2) [4](#0-3) 

The `shop` value that `Registry.process` hands to the app's handler, however, is read directly from the `shop-domain` header, with no binding to the signed body: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`. What actually holds is: `hmac == HMAC(secret, body)`, with `shop` (the tenant identifier the app will act on) taken verbatim from an attacker-controllable header that is completely outside the signed data.

### Impact Explanation
Because `shop` is not part of the signed payload, a genuine webhook delivery (with a valid HMAC, obtained e.g. from a webhook that Shopify legitimately sent to the attacker's own store) can be replayed to the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to any victim shop, while keeping the same body and HMAC. The signature still validates because it never covered the header. The app's webhook handler then processes attacker-controlled body content attributed to the victim's tenant, corrupting or cross-polluting tenant-scoped state - i.e., cross-tenant access/confusion, without ever needing the app's `client_secret` or any access token.

### Likelihood Explanation
Any user who can install the app on their own shop (or otherwise trigger a webhook delivery to themselves) can capture one legitimately-signed webhook (body + `hmac-sha256`) and replay it to the target app's webhook receiver with a forged `shop-domain` header. No credentials, TLS interception, or privileged access are required - only the ability to send an HTTP POST to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or independently bind the verified request to the shop by cross-checking `shop-domain` against a signed claim (e.g. embed shop in a signed field, or require the shop to already be a known/enrolled tenant with an existing offline session before trusting the header). At minimum, document that `Request#shop` is not authenticated by `HmacValidator.validate` and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. by editing a product) so Shopify delivers a legitimately signed webhook to the app's registered endpoint; attacker captures `raw_body` and the `X-Shopify-Hmac-Sha256` header value from that delivery (they control the receiving server or a proxy in front of it).
2. Attacker POSTs the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint again, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) validates successfully because it only checks `raw_body` against the HMAC - the `shop-domain` header substitution is invisible to the check.
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, processing it as if it were a legitimate webhook for the victim tenant.
