## Title
Protocol fee calculation in `IntentGatewayV2.placeOrder` rounds down, systematically under-collecting protocol fees - (File: `evm/src/apps/IntentGatewayV2.sol`)

## Summary
`IntentGatewayV2` (and its Tron port) deducts a "protocol fee" from every order's input amount before escrowing, using plain Solidity integer division: `protocolFee = (originalAmount * protocolFeeBps) / 10_000`. Integer division in Solidity always truncates towards zero, so any non-exact division under-collects the fee and correspondingly over-credits the user's escrowed (and thus solver-fillable) amount. This is exactly the rounding-direction bug class from the external report: fees must round up in favor of the protocol/treasury, not down in favor of the counterparty, to avoid continuous value leakage.

## Finding Description
In `IntentGatewayV2.placeOrder`, after the user's tokens are pulled in, the contract computes the protocol fee and the reduced (escrowed) amount: [1](#0-0) 

```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
```

`protocolFee` is floored, so `reducedAmount` (the amount actually escrowed, committed to in the order hash, and ultimately paid out to the filling solver / refunded to the user) is rounded up relative to the mathematically exact `originalAmount * (10_000 - protocolFeeBps) / 10_000`. This means the protocol/treasury (which only ever collects the emitted `DustCollected(token, protocolFee)` amount) systematically collects less than the intended bps rate, and the difference is left in the escrowed/reduced amount that flows to users/solvers instead of the treasury.

The identical pattern (`(amount * bps) / 10_000`, floor) is duplicated in the Tron contract's `placeOrder`: [2](#0-1) 

The SDK's own fee helper documents this floor behavior explicitly as the "gateway's floored fee deduction": [3](#0-2) 

Every `placeOrder` call across every order, on every supported chain, at every configured `protocolFeeBps` (including per-destination overrides), leaks a small amount of value from the protocol's fee-collection mechanism to whichever party ends up with the reduced/escrowed amount. Since orders are placed continuously by any unprivileged user, this compounds exactly the way the original report describes: "value will effectively constantly be leaking out from the treasury... the more the system is used, the greater the cumulative value leak will be."

## Impact Explanation
This does not enable outright theft of a specific victim's funds nor freeze funds, but it causes the protocol to permanently under-collect its configured fee revenue on essentially every order that does not divide evenly by `10_000`. Because this is dispatched by a single, ordinary `placeOrder` call from any unprivileged user/solver, and the fee-reduced amount is exactly what gets committed to the order hash, escrowed, and eventually paid to the filling solver, the shortfall is not merely a rounding artifact confined to internal accounting — it directly reduces the amount the protocol actually retains as `DustCollected` versus the bps rate advertised/configured by governance. Over the lifetime of the protocol and at scale (many orders, many chains, many fee tiers), this is a continuous, unrecoverable value leak from the protocol fee-collection mechanism, which matches a Medium-severity finding under the same rationale as the referenced Dinari OrderFees report.

## Likelihood Explanation
Likelihood is very high: this triggers on essentially every single `placeOrder` transaction where `protocolFeeBps > 0` and `originalAmount * protocolFeeBps` is not an exact multiple of `10,000`, which is true for the overwhelming majority of amounts. No malicious actor is required — it is a systematic, deterministic effect of ordinary, permissionless usage of `IntentGatewayV2.placeOrder`.

## Recommendation
Round the protocol fee up (in the protocol's favor) rather than down, e.g. using a ceiling-division helper analogous to the SDK's own `divCeil`:

```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps + 9_999) / 10_000;
```

Apply this consistently in both `evm/src/apps/IntentGatewayV2.sol` and the Tron port `evm/tron/contracts/apps/IntentGatewayV2.sol`, and update the SDK quoting logic (`sdk/packages/sdk/src/protocols/intents/quote/shared.ts`) and any documentation (`docs/content/developers/evm/intent-gateway/placing-orders.mdx`) that currently mirrors the floored calculation, so client-side fee previews stay consistent with the on-chain result.

## Proof of Concept
1. Configure `protocolFeeBps = 33` (0.33%) on `IntentGatewayV2`.
2. User places an order with `input.amount = 1000` (a raw token unit amount chosen so `1000 * 33 = 33,000`, which is not an exact multiple of `10,000`): `protocolFee = 33,000 / 10,000 = 3` (floor of 3.3), `reducedAmount = 997`.
3. The mathematically "fair" fee at exactly 0.33% would be `3.3`; the protocol only collects `3`, i.e., 0.3 units less than intended per such order.
4. Repeat over a high volume of orders with amounts that don't divide evenly by `10_000/gcd(protocolFeeBps,10_000)` — this rounding loss recurs on nearly every order and is not refunded or reconciled anywhere else in the contract (see `DustCollected` emission at [4](#0-3) ), confirming a permanent, compounding shortfall in protocol fee revenue.

/** Mirrors the gateway's floored fee deduction. */
export function deductProtocolFee(amount: bigint, protocolFeeBps: bigint): bigint {
	if (protocolFeeBps <= 0n) return amount
	const fee = (amount * protocolFeeBps) / BPS_DENOMINATOR
	return amount - fee
}
