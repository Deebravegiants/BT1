### Title
Webhook `shop` domain is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (tenant) identity it later hands to the app's handler is read from an HTTP header that is completely outside the scope of that signature. Any party capable of sending a request to the app's webhook endpoint with a *previously valid* `(raw_body, hmac)` pair — for example a merchant who has this app installed on their own store and can see the webhooks Shopify delivers to their configured endpoint — can freely rewrite the `x-shopify-shop-domain` header to any other shop's domain and have the app process the payload as if it came from that other shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares a signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw body, and `Request#hmac` reads the `hmac-sha256` header: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from separate, un-signed headers: [3](#0-2) 

`Registry.process` validates only the HMAC/body binding, then forwards the unauthenticated `request.shop` value straight to the app's handler as the authoritative tenant identity: [4](#0-3) 

The identity binding that should hold is:
`HMAC(api_secret_key, signable_string)` should equal a signature that is bound to `(shop, raw_body)` as a pair — instead it equals a signature bound to `raw_body` alone, while `shop` is asserted independently by an unauthenticated header. Because the app's `api_secret_key` is shared across every shop that has the app installed (it is not shop-specific), a valid `(raw_body, hmac)` pair generated by Shopify for **any** shop using the app remains cryptographically valid for **any other** shop's domain the attacker chooses to place in the `x-shopify-shop-domain` header. This breaks the equality `authenticated_shop == header_shop` that `WebhookHandler#handle` implicitly relies on when it trusts `WebhookMetadata#shop`.

### Impact Explanation
This crosses the "cross-tenant access" bar: an unprivileged user of the app (a merchant on one tenant/shop) can cause the host application to process attacker-supplied webhook payloads under a different, victim tenant's identity, since nothing in this gem's `Registry.process`/`Request` path binds the `shop` value to the cryptographically verified body. Any app logic that trusts `WebhookMetadata#shop` for tenant-scoped writes (e.g., updating orders/customers/settings for "the shop from this webhook") can be tricked into applying attacker-controlled data to a victim tenant's records — a cross-tenant data integrity/confidentiality issue traceable directly to this gem's validation logic, not to any misuse of a documented API by the host app.

### Likelihood Explanation
High. No secrets beyond what a legitimate, low-privilege app user already possesses are required: any shop that installs the app receives genuine `(raw_body, hmac)` pairs at its configured webhook endpoint, and the attacker only needs to replay that pair to the same endpoint with the `shop` header swapped. No `api_secret_key`, access token, or TLS interception is needed — the attacker is simply crafting a new HTTP request to the app's public webhook URL.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) values into the signed material, or otherwise require the host application to cross-check `request.shop` against an independently trusted source (e.g., the shop associated with the target endpoint/session) before trusting it, rather than treating the unauthenticated header as ground truth once the body HMAC passes. At minimum, document/enforce that `WebhookMetadata#shop` must not be treated as authenticated on its own.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop, `attacker-shop.myshopify.com`, and configures (or captures) a webhook delivery, obtaining a genuine `raw_body` and its `x-shopify-hmac-sha256` value as computed by Shopify using the app's shared `api_secret_key`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint, reusing the exact `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against `hmac` — this still passes because neither value was altered. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and processes the attacker's payload as if `victim-shop` had sent it, even though `victim-shop` never sent this webhook.
