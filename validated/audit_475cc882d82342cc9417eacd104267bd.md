## Analog Found

### Title
Reentrancy via external call before state update in `withdraw()` may enable double-spend/loss of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of the Hyperbridge intents contract, `IntentGatewayV2.withdraw()`, performs external calls (native-value transfer and ERC20 `transfer` via low-level `.call`) to an attacker-influenced `beneficiary` address *before* decrementing the corresponding escrow accounting (`_orders[body.commitment][token]`). This is the same checks-effects-interactions (CEI) violation pattern as the reported H-4 bug (`withdrawToken()` in BvbProtocol updating `withdrawableCollectionTokenId` only after the external transfer completes).

### Finding Description
`withdraw()` is reachable from `onAccept()` for `RequestKind.RedeemEscrow`/`RequestKind.RefundEscrow` messages, and from `onGetResponse()` for cross-chain cancellation queries: [1](#0-0) 

Inside `withdraw()`, for each token in the withdrawal request, the contract only checks that the escrow slot is non-zero (not that it covers `amount`), performs the external transfer, and only *afterward* subtracts `amount` from the escrow balance: [2](#0-1) 

This is the exact anti-pattern described in the report: an external call to a `beneficiary`-controlled address (`beneficiary.call{value: amount}("")` for native transfers, or `token.call(...)` for ERC20 transfers using a raw `.call` rather than `SafeERC20.safeTransfer`) happens first, handing execution control to untrusted code, and the state effect (`_orders[...][token] -= amount`) that should have already been applied per CEI is deferred until after the call returns.

By contrast, the mainline EVM `IntentsBase._withdraw()` implementation already applies the correct CEI ordering — the escrow is decremented *before* the external transfer: [3](#0-2) 

This confirms the Tron variant is a regression relative to the fixed pattern used elsewhere in the codebase, mirroring how the original BvbProtocol bug was fixed by moving the state-clearing write before the external `safeTransferFrom` call.

### Impact Explanation
Because the escrow balance for `(commitment, token)` is not zeroed/decremented until after the external transfer completes, a malicious `beneficiary` (attacker-controlled order `user`/refund recipient, or a malicious ERC20 token contract) that receives control during the `.call` can attempt to re-trigger withdrawal logic for the same commitment/token while the escrow accounting still reflects the pre-withdrawal (full) balance, enabling a double-transfer of the same escrowed funds or leaving escrow bookkeeping permanently inconsistent with actual balances. This can result in loss/drain of escrowed user funds or permanently locked/unspendable escrow accounting, matching the "theft or permanent freezing of funds" impact bar.

### Likelihood Explanation
The `beneficiary` address is user-supplied (via `order.user` for refunds, or the destination beneficiary for redemptions), so an attacker fully controls the code executed during the external call. The only mitigating factor is the Host-level replay protection (`_requestReceipts`/`_responseReceipts` written before `onAccept`/`onGetResponse` are invoked), which blocks *literal* replay of the same inbound message; however, that protection does not address the missing check that escrow amount is sufficient, nor guarantee no other code path re-enters `withdraw()`/reads escrow state for the same commitment during the callback window before the decrement executes. The unsafe raw `.call` used for ERC20 transfers (instead of `SafeERC20.safeTransfer`) also removes revert-on-failure guarantees for non-standard tokens, compounding the risk.

### Recommendation
Apply the same fix pattern already used in `IntentsBase._withdraw()`:
1. Move `_orders[body.commitment][token] -= amount;` (and the `TRANSACTION_FEES` delete) to occur **before** the external `.call`/token transfer.
2. Validate `_orders[body.commitment][token] >= amount` explicitly rather than only checking non-zero.
3. Use `SafeERC20.safeTransfer` instead of raw `.call` with `IERC20.transfer.selector` for ERC20 transfers.

### Proof of Concept
1. Attacker places/cancels an order with `order.user` (or destination beneficiary) set to a malicious contract with a `receive()`/fallback that re-enters relevant Hyperbridge entry points for the same escrow commitment.
2. A `RedeemEscrow`/`RefundEscrow` message is delivered via `onAccept`, invoking `withdraw()`.
3. During the native-token `beneficiary.call{value: amount}("")` in `withdraw()` (`evm/tron/contracts/apps/IntentGatewayV2.sol:703-704`), the escrow slot `_orders[body.commitment][token]` has **not yet** been decremented.
4. The malicious beneficiary's callback attempts to trigger another withdrawal/read path against the same commitment/token while the stale (full) escrow value is still stored, before the loop reaches `_orders[body.commitment][token] -= amount;` at line 710 — enabling inconsistent accounting or double payout depending on which other entry points are reachable during the reentrant window.

Note: I was unable to fully confirm from the indexed code whether an additional guard (e.g., an explicit `Filled()`-style check gating `authenticate()`/`onAccept()` re-entry) fully blocks all reentrant paths back into `withdraw()` for the same commitment, since I ran out of tool iterations before inspecting the `authenticate()` function body and full `_filled` guard logic in this file. The CEI violation itself (external call before escrow state update) is confirmed directly from the code and is the root-cause pattern matching the reported bug class.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
