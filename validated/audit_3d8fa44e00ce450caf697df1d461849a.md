### Title
Insufficient treasury balance causes `settle_uncle_proof` to revert, permanently losing a valid relayer's proof-of-delivery submission and slot - ([File: modules/pallets/beefy-consensus-proofs/src/lib.rs])

### Summary
`settle_uncle_proof` propagates any error from `pay_position_reward` with the `?` operator before recording the submitter's accepted proof. If the pallet's treasury account balance is insufficient to pay the position-scaled reward, the entire extrinsic reverts, discarding an otherwise fully-verified SP1 consensus proof and denying the submitting relayer their uncle slot — the exact "insufficient pool balance reverts and the [later] claimant loses everything" bug class from the referenced report, just with a BEEFY/SP1 uncle-proof reward pool instead of a CVG token supply cap.

### Finding Description
`settle_uncle_proof` verifies an SP1 consensus proof cryptographically, then pays a position-scaled reward from the treasury, and only afterward records the submitter into `AcceptedProvers`/`ProverCount`: [1](#0-0) 

The reward call is unconditionally propagated with `?`:

```
let reward_paid = Self::pay_position_reward(&submitter, position)?;

AcceptedProvers::<T>::try_mutate(parachain_height, |vec| vec.try_push(account))
    .map_err(|_| Error::<T>::UncleSlotsFull)?;
ProverCount::<T>::insert(parachain_height, position.saturating_add(1));
``` [2](#0-1) 

`pay_position_reward` transfers from the treasury `PalletId` account using `Preservation::Preserve`, and returns `Err(Error::<T>::RewardTransferFailed)` whenever that transfer fails (e.g., treasury balance too low to cover the reward, or preservation of the existential deposit would be violated): [3](#0-2) 

The codebase's own test `an_unpayable_reward_cannot_block_a_rotation` documents that the `settle_first_proof`/rotation path deliberately swallows this error to avoid blocking consensus state advancement, while explicitly stating "Messaging proofs deliberately keep the hard error" (and, by the same code structure, so does the uncle path used by `settle_uncle_proof`): [4](#0-3) 

and the corresponding inline comment at the rotation-reward call site confirms the asymmetric design intent: [5](#0-4) 

Because `ProofReward` scales per uncle position via `position_reward(base, position)`, a later (higher-position) uncle prover in a race is paid whatever the curve dictates from the same treasury pool that earlier positions already drew down. If the treasury balance runs low enough that a later position's reward transfer fails `Preservation::Preserve`, that specific submitter's entire `settle_uncle_proof` call reverts — losing both the reward and the recorded uncle slot for a cryptographically valid proof they already computed and submitted, exactly analogous to the reported CVG issue where the last claimer's transaction reverts once the shared reward pool is insufficient for their share.

### Impact Explanation
An uncle prover who did legitimate, costly work (SP1 proof generation) and would otherwise occupy a valid slot (`position <= MaxUncleProvers`) gets their entire submission reverted purely because of insufficient treasury funds at the moment of *their* transaction, with no fallback to "pay less" or "skip the reward and still record the proof" the way the rotation path does. This is inconsistent within the same pallet (rotation-reward failures are tolerated; uncle-reward failures are not) and results in the relayer/prover permanently losing both the reward and their accepted-uncle-proof record for that height — a definite loss of expected funds/state for an honest, unprivileged proof submitter, reachable purely by treasury depletion (which naturally occurs as more provers are paid across successive heights/positions).

### Likelihood Explanation
Likelihood is moderate-to-high in practice: the treasury is a shared, governance-topped-up pool that pays out continuously across BEEFY consensus rotations and uncle proofs; any period where inflow lags reward payouts (e.g., heavy prover competition, governance delay in topping up) causes exactly this state. No attacker action is required — it is a natural resource-exhaustion condition on a permissionless path (any account can submit SP1 uncle proofs), matching the "unprivileged... consensus verification (BEEFY, SP1...)" reachability the rules call out.

### Recommendation
Mirror the rotation-path's fail-open behavior in `settle_uncle_proof`: catch the `Err` from `pay_position_reward`, log a warning, treat `reward_paid` as `0`, and still record the submitter into `AcceptedProvers`/`ProverCount` so the valid proof and slot are not lost merely because the treasury reward transfer failed. Alternatively, cap the transferred amount to the treasury's available balance instead of an all-or-nothing transfer, consistent with the report's suggested fix of clamping to the remaining pool rather than reverting entirely.

### Proof of Concept
1. Configure `ProofReward` and the position-reward curve such that later positions still require a non-trivial payout.
2. Drain the treasury (via prior rotation/uncle payouts across several heights) until its balance is below what `position_reward(base, position)` demands for an upcoming uncle at some `position`.
3. Have a legitimate relayer submit a correctly formed SP1 uncle proof for that height/position (as in `settle_uncle_proof`).
4. Observe: `pay_position_reward` returns `Err(RewardTransferFailed)` at [6](#0-5) , the `?` propagates, and the whole extrinsic reverts — `AcceptedProvers`/`ProverCount` are never updated for that submitter, discarding their verified proof and reward, unlike the tolerant behavior demonstrated for the rotation path in `an_unpayable_reward_cannot_block_a_rotation`.

		/// Apply the curve at `position` to [`ProofReward`], transfer from the treasury,
		/// and mint reputation 1:1.
		fn pay_position_reward(
			submitter: &T::AccountId,
			position: u32,
		) -> Result<BalanceOf<T>, Error<T>> {
			let zero = BalanceOf::<T>::default();
			let base = ProofReward::<T>::get();
			if base == zero {
				return Ok(zero);
			}

			let reward = Self::position_reward(base, position);
			if reward == zero {
				return Ok(zero);
			}

			let treasury: T::AccountId =
				<T as Config>::TreasuryPalletId::get().into_account_truncating();
			<T as Config>::Currency::transfer(&treasury, submitter, reward, Preservation::Preserve)
				.map_err(|e| {
					log::warn!(
						target: "ismp",
						"[beefy-consensus-proofs] treasury reward transfer failed: {e:?}",
					);
					Error::<T>::RewardTransferFailed
				})?;

/// Same hazard, different source: an unpayable reward. `pay_position_reward` runs after the
/// caller has applied the rotation, so propagating `RewardTransferFailed` rolls it back — and
/// since the mandatory justification is the only one obtainable for that session, every retry
/// fails identically until the treasury is topped up, leaving consensus on the old set. The
/// reward is the cheaper thing to drop. Messaging proofs deliberately keep the hard error.
#[test]
fn an_unpayable_reward_cannot_block_a_rotation() {
	let mut ext = new_test_ext();
	let height = 800u64;

	ext.execute_with(|| {
		// The BEEFY proofs treasury holds nothing in genesis, so any non-zero reward makes the
		// transfer fail with `RewardTransferFailed`.
		ProofReward::<Test>::put(1_000_000u128);

		pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
			submitter(11),
			vec![PROOF_TYPE_SP1, 0xab],
			Some(H256::repeat_byte(11)),
			PROOF_TYPE_SP1,
			Vec::new(),
			rotation_outcome(height, 30),
		)
		.expect("an unpayable reward must not reject the rotation");

		assert_eq!(
			RotationProofs::<Test>::get().get(&30).copied(),
			Some(height),
			"the rotation must be recorded even though the reward could not be paid",
		);

		// The asymmetry is deliberate: reverting a messaging proof is recoverable, because the
		// next proof re-attempts the same work once the treasury can pay.
		assert!(
			pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
				submitter(12),
				vec![PROOF_TYPE_SP1, 0xac],
				Some(H256::repeat_byte(12)),
				PROOF_TYPE_SP1,
				Vec::new(),
				messaging_outcome(height + 1, 30),
			)
			.is_err(),
			"a messaging proof must still fail hard when the reward cannot be paid",
		);
