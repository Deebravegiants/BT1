### Title
Webhook `shop-domain` header is trusted for tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) it exposes to webhook handlers is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material. This breaks the identity binding `hmac_verified_bytes == bytes_that_determine_tenant`, allowing a party who can produce one validly-signed webhook (e.g. a merchant receiving webhooks for their own installed app) to relabel that request as originating from a different shop before it reaches the host application's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it against the `hmac-sha256` header value: [2](#0-1) 

Meanwhile, `Request#shop` — the value the gem treats as the authenticated tenant for the webhook — is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a value that is not part of the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC and then hands the (unsigned) `shop` header straight to the application's handler as authenticated tenant metadata: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` const with no further validation: [5](#0-4) 

The identity binding that should hold is:
`hmac_verified_bytes(raw_body) == bytes_that_determine_tenant(shop header)`

but in this implementation the two are disjoint: the HMAC only proves the request body is intact and was produced with `api_secret_key`; it proves nothing about which shop the header claims to be from. Any entity capable of obtaining one validly-HMAC-signed webhook payload for topic X — most straightforwardly a merchant who has installed the app and thus legitimately receives webhooks for their own store — can replay that exact body while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g. a victim's `myshopify.com` domain). `HmacValidator.validate` still succeeds because the body (the only signed content) is unchanged, and `Registry.process` will pass the attacker-chosen `shop` value into the handler untouched.

### Impact Explanation
Because host applications built on this gem are documented to key session/tenant lookups and data writes off `WebhookMetadata#shop` (see `docs/usage/webhooks.md` usage patterns and `RegistryTest` assertions on `data.shop`), an application that trusts this field for tenant routing can be made to process one shop's webhook payload as if it belonged to a different shop. This is a cross-tenant confusion vector: attacker-controlled body content (already legitimately signed for the attacker's own shop) gets attributed to and merged into a victim tenant's data/state in the host app, which is a cross-tenant integrity impact directly caused by a gap in this gem's `HmacValidator`/`Webhooks::Request` binding.

### Likelihood Explanation
Any unprivileged internet user who can install the app on their own store (or otherwise trigger a webhook delivery addressed to themselves) automatically receives properly HMAC-signed webhook deliveries for their own shop. Forging the `shop-domain` header on a replayed/relayed request requires no cryptographic secret — only control over which headers reach the app's ingestion endpoint, which is trivial for a party operating their own webhook receiver/proxy in front of the app. No access token, `api_secret_key`, or privileged account is required beyond ordinary app installation.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signed material verified by `HmacValidator`, or otherwise cryptographically bind the shop domain to the payload before trusting it, rather than computing the HMAC over `raw_body` alone in `Request#to_signable_string`. At minimum, document prominently that `Webhooks::Request#shop` is unauthenticated relative to the HMAC and must not be used by host applications for tenant identification without independent verification (e.g., cross-checking against a known/registered shop for the given webhook subscription).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker relays this exact request to the app's webhook endpoint, only replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (body `B` and the HMAC header are left untouched).
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (= `B`) and it matches the untouched HMAC header, so `Registry.process` accepts the request: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body B>, ...)` — content controlled by the attacker, now labeled and processed as belonging to the victim shop.
