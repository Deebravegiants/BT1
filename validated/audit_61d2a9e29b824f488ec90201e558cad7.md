### Title
Unmetered resource depletion via unbounded, statically-weighted `handle_unsigned` message batches - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic accepts an arbitrary-length `Vec<Message>` and is charged a fixed, size-independent weight, yet the transaction-pool validation path fully executes the entire batch (proof verification, membership/non-membership checks, module dispatch) before a block is even produced. This mirrors the GitLab CVE-2023-1072 pattern of "improper filtering for number of requests" leading to a resource-depletion attack.

### Finding Description
`handle_unsigned` is declared as an unsigned, feeless extrinsic reachable by anyone: [1](#0-0) 

Its dispatch weight is a static constant that does **not** scale with the number or size of messages in the batch: [2](#0-1) 

Critically, `ValidateUnsigned::validate_unsigned` for this pallet does not merely inspect the call — it calls `Self::execute(messages.clone())`, which fully runs the ISMP message handler pipeline (state-machine validation, membership/non-membership proof verification via `verify_membership`/`verify_state_proof`, and `on_accept`/`on_response` module dispatch for every request/response in the batch) as part of transaction-pool admission, before the transaction is even included in a block: [3](#0-2) [4](#0-3) 

The per-request handler itself iterates over `msg.requests` with no cap on batch size, performs a `dedup_requests` pass, a membership-proof verification over all commitments, and then dispatches each request to its destination module: [5](#0-4) 

Because (a) there is no bound on `Vec<Message>` / `Vec<PostRequest>` / `Vec<GetRequest>` length enforced before this expensive verification work runs, and (b) the weight annotated on the call (`weight()` = fixed `300_000_000`) does not reflect the true cost of a large batch, an attacker can submit `handle_unsigned` calls carrying very large numbers of requests (each requiring signature/membership-proof verification and full module dispatch) that are executed in full by every node's transaction pool at essentially zero cost, and — if valid — again at block execution/`on_finalize` time. This is directly analogous to the referenced GitLab issue where a lack of request-count filtering during read-commits processing permitted resource-depletion DoS.

### Impact Explanation
This can be triggered by any unprivileged party as a raw unsigned extrinsic (no signed origin, no fee) directly against the message dispatch path called out in scope (`pallet-ismp handle_unsigned`). Repeated submission of maximally-sized batches forces expensive cryptographic verification and module dispatch work onto every collator/full node during mempool validation (which happens on every peer, independent of block inclusion), degrading network throughput and potentially causing legitimate `handle_unsigned` messages (real cross-chain request/response delivery) to be starved out of blocks — a denial-of-service against message delivery, which can manifest as inability to deliver messages (a "route unable to deliver messages" condition) during sustained attack windows.

### Likelihood Explanation
Likelihood is high: `handle_unsigned` is explicitly designed to be permissionless and free (documented as "This allows users execute ISMP datagrams for free. Use with caution."), requires no stake or fee, and the only gates before full execution during validation are proof validity checks that are satisfiable by anyone who can produce a valid (even minimal-value) request/response batch with a legitimate but arbitrarily large `requests` vector against a real, already-finalized state commitment.

### Recommendation
- Enforce an explicit maximum number of messages/requests/responses per `handle_unsigned` call (e.g., a `BoundedVec` with a `MaxMessagesPerBatch` config constant) checked before any proof verification or dispatch is attempted, both in `validate_unsigned` and in `execute`.
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` a function of `messages.len()` (and ideally of nested request/key counts) rather than a fixed constant, so `frame_system::CheckWeight` can reject oversized batches pre-execution.
- Consider adding a lightweight, cheap pre-check (e.g., message count and total encoded size against `T::MaxCallSize`-like bound) inside `validate_unsigned` prior to invoking `Self::execute`, to avoid running the full verification pipeline against attacker-controlled batch sizes during mempool admission.

### Proof of Concept
1. Construct a `RequestMessage` (or `ResponseMessage`) whose `proof.height` references an already-known, valid `state_machine_commitment` and whose `requests` vector contains a very large number of `PostRequest`/`GetRequest` entries (or submit many `Message::Request` items inside one `handle_unsigned` batch), each requiring only a valid Merkle multiproof leaf.
2. Submit `pallet_ismp::Call::handle_unsigned { messages }` as an unsigned transaction to the network (as demonstrated by the test harness pattern used for legitimate submissions): [6](#0-5) 
3. Because `validate_unsigned` runs `Self::execute(messages.clone())` fully (membership proof verification + module dispatch for every request) with only a static `weight()` guard, submitting many such transactions concurrently forces disproportionate computational work in every node's mempool validation relative to the near-zero cost to the attacker, independent of whether the transactions are ultimately included in a block.

	if msg.requests.is_empty() {
		Err(Error::EmptyBatch)?
	}

	let state_machine = validate_state_machine(host, msg.proof.height)?;
	let consensus_clients = host.consensus_clients();
	let check_state_machine_client = |state_machine: StateMachine| {
		consensus_clients
			.iter()
			.find_map(|client| client.state_machine(state_machine).ok())
			.is_none()
	};

	let router = host.ismp_router();

	// Reject duplicate requests within the batch. Wire format is `Vec`,
	// so this is the line of defence against an attacker padding a
	// batch with identical requests.
	let wrapped: Vec<Request> = msg.requests.iter().cloned().map(Request::Post).collect();
	dedup_requests::<H>(&wrapped)?;

	for req in msg.requests.iter() {
		let req = Request::Post(req.clone());
		// If a receipt exists for any request then it's a duplicate and it is not dispatched
		if host.request_receipt(&req).is_some() {
			Err(Error::DuplicateRequest { meta: req.clone().into() })?
		}

		// can't dispatch timed out requests
		if req.timed_out(host.timestamp()) {
			Err(Error::RequestTimeout { meta: req.clone().into() })?
		}

		// either the host is a router and can accept requests on behalf of any chain
		// or the request must be intended for this chain
		if req.dest_chain() != host.host_state_machine() && !host.is_router() {
			Err(Error::InvalidRequestDestination { meta: req.clone().into() })?
		}

		let source_chain = req.source_chain();

		// in order to allow proxies, the host must configure the given state machine
		// as it's proxy and must not have a state machine client for the source chain
		let allow_proxy = host.is_allowed_proxy(&msg.proof.height.id.state_id) &&
			check_state_machine_client(source_chain);

		// check if the request is allowed to be proxied
		if source_chain != msg.proof.height.id.state_id && !allow_proxy {
			Err(Error::RequestProxyProhibited { meta: req.clone().into() })?
		}
	}

	// Verify membership proof
	let state = host.state_machine_commitment(msg.proof.height)?;
	let commitments = msg
		.requests
		.iter()
		.map(|post| hash_request::<H>(&Request::Post(post.clone())))
		.collect();
	state_machine.verify_membership(host, commitments, state, &msg.proof)?;
