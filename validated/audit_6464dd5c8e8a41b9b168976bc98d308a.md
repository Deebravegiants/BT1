### Title
V1 Transaction Format Decouples `priority_fee` From `compute_unit_limit`, Enabling Underpriced Compute-Budget Reservation - ([File: runtime-transaction/src/transaction_meta.rs])

### Summary
In the legacy/v0 transaction path, the prioritization fee a user pays is always mathematically derived from `compute_unit_price * compute_unit_limit` via `ComputeBudgetLimits::get_prioritization_fee()`. In the new V1 transaction message format, `priority_fee` and `compute_unit_limit` are independent, directly user-supplied fields with no cross-validation between them, breaking the invariant that the resource reservation (`compute_unit_limit`) is priced proportionally to the fee paid (`priority_fee`).

### Finding Description
`ComputeBudgetInstructionDetails::sanitize_and_convert_to_compute_budget_limits` (legacy/v0 path) computes the compute unit limit and price from instructions, and the resulting prioritization fee is *always* `compute_unit_price * compute_unit_limit`: [1](#0-0) 

That derived value is what feeds `TransactionConfiguration::priority_fee_lamports` for legacy/v0 transactions: [2](#0-1) 

For the V1 message format, however, `priority_fee` and `compute_unit_limit` are independent optional fields taken directly from the transaction's `TransactionConfig`, with zero relationship enforced between them — only individual clamping to `MAX_COMPUTE_UNIT_LIMIT` / `MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES` is applied: [3](#0-2) 

The same unchecked, independent fields are defined in the base struct: [4](#0-3) 

This `priority_fee_lamports` is fed directly (unmodified) into `calculate_fee_details` as the `prioritization_fee` parameter, which is simply added to the signature fee with no relation to `compute_unit_limit`: [5](#0-4) 

and it also feeds directly into the executed compute-budget/cost accounting used by the bank when validating and charging the transaction: [6](#0-5) 

The result: an attacker submitting a V1 transaction can set `compute_unit_limit` to (up to) `MAX_COMPUTE_UNIT_LIMIT` (1.4M CU) while setting `priority_fee` to `0` (or any arbitrarily small value). The transaction is fully valid — there is no check analogous to the legacy path's `price * limit` derivation to ensure the fee paid scales with the compute budget reserved. This is the direct analog of the reported bug class: two economically linked parameters (the "cost" driver `compute_unit_limit` and the "price paid" driver `priority_fee`) can be chosen independently, letting the user obtain the benefit (a large block-cost/compute reservation, prioritized scheduling weight) associated with a high-fee transaction while paying a fee associated with a low one.

### Impact Explanation
`compute_unit_limit` is the resource that is reserved against the block's compute budget by the cost model/scheduler (a real, finite, per-block resource), while `priority_fee_lamports` is the amount actually paid to obtain that reservation and priority. Because V1 transactions can set these independently and unvalidated, a user can consume large compute-unit block capacity while paying a fee disproportionate to (or completely decoupled from) that consumption — a materially underpriced allocation of a scarce validator/protocol resource, i.e., a fee/compute-budget accounting inconsistency reachable by any unprivileged user submitting ordinary V1 transactions.

### Likelihood Explanation
High for any node/cluster with `enable_tx_v1` feature active: crafting such a V1 transaction requires only building an ordinary `solana_message::v1::Message` with `TransactionConfig { compute_unit_limit: Some(MAX), priority_fee: Some(0), .. }`, no special privileges, and no additional preconditions.

### Recommendation
Enforce a cross-validation in `VersionedTransactionConfiguration::try_into_config`'s `V1` branch analogous to the legacy path's coupling — e.g., require `priority_fee_lamports` to be consistent with (or derived from) an explicit `compute_unit_price` and `compute_unit_limit`, or otherwise reject/clamp V1 configurations where the requested `compute_unit_limit` is disproportionate to the supplied `priority_fee_lamports`.

### Proof of Concept
Construct a V1 `VersionedMessage` with:
```rust
v1::TransactionConfig {
    priority_fee: Some(0),
    compute_unit_limit: Some(MAX_COMPUTE_UNIT_LIMIT),
    ..v1::TransactionConfig::empty()
}
```
as demonstrated by the existing test harness pattern used for `getFeeForMessage`: [7](#0-6) 
and by `VersionedTransactionConfiguration::V1(...).try_into_config(...)`, which accepts arbitrary independent `compute_unit_limit`/`priority_fee_lamports` combinations without error: [8](#0-7)

fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}
