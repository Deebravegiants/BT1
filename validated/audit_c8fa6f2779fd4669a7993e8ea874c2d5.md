### Title
Webhook shop identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id` and `api_version` are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` (used by `Registry.process`) verifies only that the body's HMAC matches the app's shared `api_secret_key`; it never binds the `shop` header into that signature. Since the `api_secret_key` is shared across every shop that has installed the app, any shop owner can capture a legitimate `(body, hmac)` pair from their own webhook traffic and replay it against the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, producing a webhook that passes HMAC validation but is attributed to a tenant the attacker does not control.

### Finding Description
The relevant binding is: `hmac == HMAC(api_secret_key, signable_string)` should imply `signable_string` (and everything the app trusts as a result of a valid signature) came from the shop named in the request. In this gem that equality only covers `raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (the body) using the app's `api_secret_key`, which is identical for every shop that installs this app — it is not a per-shop secret: [3](#0-2) 

`Registry.process` trusts a passing HMAC check and then forwards the header-derived `shop` (and `topic`) straight to the app's webhook handler as authoritative tenant/topic identity: [4](#0-3) 

Because the signature never covers the `shop` (or `topic`) value, "HMAC verified" and "headers describe the true origin of this request" are not the same statement — exactly the class of binding break called out in the rules (a field acted on but not covered by the HMAC).

### Impact Explanation
Any unprivileged internet user who can install the app on their own (even free/dev) store receives legitimate webhook deliveries containing a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's shared `api_secret_key`. They can replay that exact body/HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body against the shared secret, and `Registry.process` will invoke the app's handler with `shop: <victim-shop>` and attacker-chosen body content. This is a cross-tenant boundary break: the attacker injects data/events into the victim tenant's processing path (e.g., forging `orders/paid`, `app/uninstalled`, or mandatory `customers/data_request` / `customers/redact` / `shop/redact` payloads) without ever having credentials for or access to the victim shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High likelihood: exploitation requires no secrets beyond what any app installer already legitimately receives (their own shop's webhook body + HMAC), no social engineering, and no TLS interception. The only prerequisite is that the attacker can install the app themselves (a normal, unprivileged flow) and can send arbitrary HTTP requests to the app's public webhook endpoint — both trivially available to any internet user.

### Recommendation
Bind the shop (and topic) into the value that is actually signed, or otherwise cryptographically authenticate the header before trusting it:
- Include `shop-domain` (and ideally `topic`, `webhook-id`) in `to_signable_string`, matching them against a signature computed the same way Shopify signs webhooks, or
- Independently verify that the `shop` header corresponds to a shop session/installation known to the app before processing, rather than trusting it solely because the body's HMAC validated
- At minimum, document/enforce that consumers of `ShopifyAPI::Webhooks::Registry.process` must not treat `WebhookMetadata#shop` as authenticated by the HMAC check alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets it receive a normal webhook, e.g. `orders/paid`, capturing:
   - `raw_body` (JSON payload)
   - `X-Shopify-Hmac-Sha256: <hmac>` (valid signature over `raw_body` using the app's shared `api_secret_key`)
2. Attacker sends a POST to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: orders/paid` (or any topic the attacker chooses)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present) and `Registry.process` calls `Utils::HmacValidator.validate(request)`:
   ```ruby
   Utils::HmacValidator.validate(request) # => true, because it only checks raw_body against api_secret_key
   ```
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/paid", shop: "victim-shop.myshopify.com", body: JSON.parse(raw_body), ...)`, causing the app to process attacker-controlled data as if it were an authentic event from `victim-shop.myshopify.com`, despite the attacker having no access to that shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
