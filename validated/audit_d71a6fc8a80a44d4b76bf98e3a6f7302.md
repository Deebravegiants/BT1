### Title
Webhook `shop-domain` header is dispatched to handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw body, then dispatches the handler using the shop identity taken from an HTTP header that is never included in that HMAC computation. This breaks the intended binding: `shop authenticated by HMAC == shop passed to handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC using this signable string and, if valid, immediately builds `WebhookMetadata` using `request.shop`, which is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) [3](#0-2) 

Because `api_secret_key` is a single shared secret across every shop/tenant that has installed the app (not a per-shop secret), any merchant that installs the app receives legitimate `(body, hmac)` pairs signed with that same shared secret for their own store's events. Since the header carrying the shop identity (`shop-domain`) is not part of the signed payload, an attacker who controls one installation can replay a body+HMAC pair they legitimately received while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` recomputes the HMAC only over `raw_body`, so the signature still checks out: [4](#0-3) 

The library documents that `data.shop` is "The shop domain of the webhook" and expects host apps to use it directly for tenant-scoped work (e.g., looking up the shop's session/access token, attributing the event, enqueuing per-shop jobs): [5](#0-4) 

There is no code path in the gem that cryptographically binds the `shop` value to the HMAC-verified body, so the "authenticated request" and "tenant the event is attributed to" are two independently-controlled values once past the boundary of a single legitimate secret holder.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate installer of the app (an unprivileged internet user relative to other merchants) can forge webhook deliveries that the host application will process as if they originated from a different shop, since `WebhookMetadata#shop` is trusted downstream without any additional verification. Depending on how the host app uses `data.shop` (commonly to fetch that shop's session/access token and act on their store, per the documented usage pattern), this can lead to cross-tenant data manipulation or actions being taken against another merchant's store using the attacker-supplied payload. This matches the "Critical - cross-tenant access" impact category, since the identity binding the gem is supposed to guarantee (that the shop shown in `WebhookMetadata` is the shop that actually produced the HMAC-signed payload) does not hold.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker needs to be, or briefly become, a legitimate installer of the target app to capture a valid `(body, hmac)` pair signed by the shared secret, and (2) the impact is fully dependent on the host application trusting `data.shop` for privileged, tenant-scoped operations exactly as the gem's own documentation instructs it to. Given that becoming an app installer merely requires installing a public Shopify app (an unprivileged action), and the gem explicitly documents `shop` as the field to key tenant logic on, this is a realistic, low-effort exploitation path within the scope of this gem's own contract.

### Recommendation
Do not treat `request.shop` as authenticated. Either:
- Extend `HmacValidator`/`Request#to_signable_string` to fold the `shop-domain` header (and `topic`/`webhook_id`) into the signed material so any header tampering invalidates the HMAC, or
- Have `Registry.process` cross-check `request.shop` against an out-of-band trusted source (e.g., a known/registered shop list, or reject if the recomputed HMAC context doesn't match a shop-specific secret) before constructing `WebhookMetadata`, or
- At minimum, prominently document in `docs/usage/webhooks.md` that `data.shop` is not covered by the HMAC and must not be trusted for authorization decisions without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(secret, B)`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker re-sends the exact same `B`/`H` to the app's webhook endpoint but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= @raw_body = B`) and finds it matches `H` — validation passes. [2](#0-1) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop == "victim-shop.myshopify.com"`, even though that shop never sent this event and the payload was never signed with knowledge of that shop's identity.
5. Any host-app logic that uses `data.shop` to select which merchant's access token/session to act on (the pattern shown in the gem's own docs) now operates cross-tenant, attributing attacker-controlled data/actions to the victim shop.
