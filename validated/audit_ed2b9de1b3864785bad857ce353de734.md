Audit Report

## Title
CORS Allowlist Bypass via Improper Suffix Matching in Gateway Wildcard Origin Validation - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function performs wildcard subdomain matching using a bare `strings.HasSuffix(originHost, allowedHost)` check without requiring a `.` label boundary before the match. This allows an attacker-registered domain that merely ends with the allowed suffix (e.g., `evilethereum.org` matching allowlist `*.ethereum.org`) to be treated as a trusted subdomain, causing the Gateway to echo the attacker's origin into `Access-Control-Allow-Origin`.

## Finding Description
In the wildcard branch of `isAllowedOrigin`, the code strips the `*.` prefix and then checks `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) . This check does not verify that the character preceding the matched suffix in `originHost` is a `.`, so any host string that literally ends with the allowed suffix's characters (not just a true subdomain) satisfies the condition — e.g., `evilethereum.org` ends with `ethereum.org` despite not being a subdomain of it.

This function is called directly from `handleRequest`, the internet-facing request handler, which sets `Access-Control-Allow-Origin` to the raw `Origin` header value whenever `isAllowedOrigin` returns true: [2](#0-1) . No other validation layer (scheme/port checks in `isAllowedOrigin` at lines 172-179, or auth/JWT extraction later in `handleRequest`) mitigates this, since scheme and port matching pass trivially and are independent of the flawed host suffix check. The existing test suite confirms the intended safe behavior for non-matching suffixes (`ethereum.remix.org` correctly rejected because it does not end with `ethereum.org`) but does not cover the boundary-less bypass case where the malicious host's suffix literally matches without a dot separator.

## Impact Explanation
This is a genuine CORS allowlist bypass in the Gateway's `network/httpserver.go`, reachable by any unprivileged external client capable of sending an HTTP request with a crafted `Origin` header and, in a real-world browser-based exploitation scenario, hosting content on an attacker-registrable domain ending with the victim's configured wildcard suffix. This maps to the in-scope "allowlist or subscription bypass" / "cross-user response corruption" impact category, since it can result in the Gateway granting CORS trust (and thus credentialed cross-origin read access to Gateway responses) to an untrusted origin that was never intended to be covered by the wildcard.

## Likelihood Explanation
Exploitation requires only registering a domain whose name ends with the allowed suffix (e.g., `evilethereum.org` for `*.ethereum.org`) and hosting a page there to trigger a CORS request — no node compromise, no operator/admin access, and no special network position are required. This is fully triggerable by an unprivileged remote attacker against any Gateway operator using wildcard `CORSAllowedOrigins` entries, which is a supported and documented configuration pattern.

## Recommendation
Enforce a proper label boundary in the wildcard match:
```go
if strings.HasSuffix(originHost, allowedHost) &&
    (originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)) {
    return true
}
```
This ensures `originHost` is either exactly `allowedHost` or a true subdomain (immediately preceded by a `.`), preventing suffix-only spoofing.

## Proof of Concept
1. Configure Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send a request to the Gateway's configured path with header `Origin: https://evilethereum.org`.
3. Trace through `isAllowedOrigin`: `allowedHost` becomes `"ethereum.org"` after stripping `*.`; `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, so the function returns `true`.
4. `handleRequest` sets `Access-Control-Allow-Origin: https://evilethereum.org` in the response, despite `evilethereum.org` not being a legitimate subdomain of `ethereum.org`.
5. This can be codified as a Go unit test analogous to the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but asserting that `https://evilethereum.org` is (incorrectly) accepted, demonstrating the bypass.
