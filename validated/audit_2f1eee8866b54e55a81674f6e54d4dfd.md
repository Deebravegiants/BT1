### Title
`update_token` repointing a chain's `TokenContracts` address strands both in-flight incoming messages and in-flight timeout refunds tied to the old contract - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`pallet-hyper-fungible-token::update_token` lets `CreateOrigin` repoint the EVM counterpart contract address for a `(chain, asset)` pair. When it does, it deletes the `ContractToAsset` reverse-mapping entry for the *old* contract address in the same call that installs the new one [1](#0-0) . Both `on_accept` and `on_timeout` authenticate/route incoming ISMP messages solely by looking up `ContractToAsset::<T>::get(source/dest, &from/&to)` [2](#0-1) [3](#0-2) . Any message already dispatched by the old contract (inbound `Send`) or already in flight to it (outbound `Send` awaiting timeout) before the rotation, but delivered/timed-out after it, is now unroutable and reverts permanently, exactly mirroring the audited Airdrop/AirdropFactory bug where a locker-address change was propagated in the "factory" registry but stranded funds tied to the previous locker.

### Finding Description
`TokenContracts` maps `(StateMachine, AssetId) -> Vec<u8>` (the EVM counterpart address used as `to` on outgoing dispatch), and `ContractToAsset` is the reverse map used to authenticate/route incoming messages [4](#0-3) .

`update_token`'s `add_chains` path unconditionally removes the reverse mapping for whatever contract was previously configured, before inserting the new one:
```
if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone()) {
    ContractToAsset::<T>::remove(chain, old_contract);
}
...
TokenContracts::<T>::insert(chain, update.asset_id.clone(), token_contract.clone());
ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
``` [1](#0-0) 

There is no draining/quarantine step and no way to keep the old mapping "claimable" — the old contract's authentication entry is destroyed atomically with the swap, unlike the fixed HostManager-rotation pattern elsewhere in this codebase, which keeps routing to the previous manager valid until governance itself walks through it (see `evm/src/core/HostManager.sol` / `modules/pallets/host-executive/src/lib.rs`) [5](#0-4) .

Two independent unprivileged-user flows are broken by this deletion:

1. **Incoming transfer from the old contract, delivered late.** A user calls `send` on the *old* EVM `HyperFungibleToken` contract (locking/burning funds there) before the rotation is dispatched. If the corresponding ISMP `PostRequest` is delivered to this pallet's `on_accept` after `update_token` executes, `ContractToAsset::<T>::get(source, &from)` no longer resolves and the message reverts with `UnknownSourceContract` [2](#0-1) . The user's funds, already consumed on the source chain, can never be minted/released here — permanent loss, since ISMP relayers cannot retry `on_accept` in a way that changes `from`.

2. **Outbound `send` from this pallet, later timed out against the old contract.** A local user calls `send`, which escrows/burns their local balance and dispatches a `DispatchPost` addressed `to: token_contract` (the contract on record at dispatch time) [6](#0-5) . If governance rotates `TokenContracts`/`ContractToAsset` for that `(chain, asset)` before the request either lands or times out, and the request later times out, `on_timeout` looks up `ContractToAsset::<T>::get(dest, &to)` using the message's original `to` (the now-deregistered old contract) to find `local_asset_id` for the refund [7](#0-6) . That lookup fails with `UnknownContractOnTimeout`, so the refund path reverts and the user's escrowed/burned funds are permanently stuck (escrowed and never released, or burned and never re-minted).

This is functionally identical to the reported bug class: a governance/admin action that legitimately re-points a "locker"/counterpart address is applied by overwriting rather than layering the mapping, silently orphaning funds already committed against the address that is being replaced.

### Impact Explanation
This is a High-severity permanent-freezing-of-funds bug reachable by an ordinary token bridger: any user whose cross-chain transfer straddles a legitimate, non-malicious `update_token` governance call has their funds (already escrowed or burned on one side) become permanently unrecoverable — no on-chain code path exists to re-establish the old `ContractToAsset` entry once it is removed by `update_token`. Because ISMP delivery/timeout is asynchronous and can be delayed relative to when governance dispatches a routine contract rotation (e.g. migrating to a new `HyperFungibleToken` deployment), this is not a contrived edge case but the direct, expected outcome of a normal token-gateway migration performed while transfers are in flight.

### Likelihood Explanation
`update_token` is a routine, expected operational call (analogous to changing a locker/vault address) that maintainers will invoke whenever a token's counterpart contract needs to be redeployed or migrated to a new chain, and the pallet provides no pause/drain mechanism to guarantee no in-flight `send` exists for the affected `(chain, asset)` pair at call time. Given ISMP's asynchronous relay/timeout model, in-flight messages are a normal, non-adversarial occurrence, making the likelihood of triggering stranded funds during any live rotation moderate-to-high, matching the "High" rating of the original report for the same bug class.

### Recommendation
Do not destructively overwrite `ContractToAsset` for the previous contract inside `update_token`. Instead:
1. Keep the old `(chain, old_contract) -> asset_id` entry resolvable for `on_accept`/`on_timeout` purposes (e.g. maintain a bounded history / additional "legacy" reverse-map keyed by contract, or simply never delete an old entry that could still service an in-flight request) until it is safe to prune (e.g. after a configurable grace period longer than any live request's timeout).
2. Alternatively, require operators to first drain/settle all in-flight requests for a `(chain, asset)` pair (a "pause new sends, wait for outstanding round-trips to clear" flow) before calling `update_token`'s `add_chains`/`remove_chains` for that pair.
3. Emit a distinct event when an old mapping is retired so indexers/relays can flag any request still outstanding against it before final cleanup.

### Proof of Concept
1. `CreateOrigin` registers asset `X` with `TokenContracts[Evm(1)][X] = ContractA` via `register_token` [8](#0-7) .
2. A user calls `send(destination = Evm(1), asset_id = X, amount, timeout)`, which escrows/burns locally and dispatches a `PostRequest` addressed `to = ContractA` [9](#0-8) .
3. Before the request is delivered or times out, `CreateOrigin` calls `update_token` with `add_chains = { Evm(1): ContractB }`. This removes `ContractToAsset[Evm(1)][ContractA]` and installs `ContractToAsset[Evm(1)][ContractB] = X` [1](#0-0) .
4. The original request from step 2 later times out; `on_timeout` calls `ContractToAsset::<T>::get(dest, &to)` with `to = ContractA`, which now returns `None`, causing `UnknownContractOnTimeout` and reverting the refund [7](#0-6) . The user's escrowed/burned funds from step 2 are permanently stuck with no code path to recover them.
5. Symmetrically, if a user had already called the EVM `send` on `ContractA` (locking/burning on the EVM side) and the corresponding `PostRequest` arrives at `on_accept` after step 3, `ContractToAsset::<T>::get(source, &from)` with `from = ContractA` returns `None`, and `UnknownSourceContract` is raised, permanently stranding the funds already consumed on the EVM side [2](#0-1) .

		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}

			Self::deposit_event(Event::<T>::TokenRegistered {
				asset_id: registration.local_id,
				native: registration.native,
				chains,
			});
			Ok(())
		}
