## Title
Topic/shop header confusion via body-only HMAC in webhook processing - (File: lib/shopify_api/webhooks/registry.rb)

## Summary
`ShopifyAPI::Utils::HmacValidator.validate` verifies only the raw request body against the HMAC secret; the `topic`, `shop`, `webhook-id`, and `api-version` header values are never included in the signed string. `Registry.process` then uses the unauthenticated `request.topic` header to select the handler and passes the unauthenticated `request.shop` header straight into `WebhookMetadata`, so any request carrying a body/HMAC pair that was genuinely signed for one topic/shop can be relabeled to any other registered topic and shop.

## Finding Description
The claimed binding — "topic committed to by the HMAC-covered payload's originating registration == topic key used to select the handler" — is false. `to_signable_string` in `lib/shopify_api/webhooks/request.rb` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC solely over that signable string [2](#0-1) . `Registry.process` then does `handler = @registry[request.topic]&.handler`, where `request.topic` is read straight from the `x-shopify-topic`/`shopify-topic` header with no cryptographic tie to the body [3](#0-2) , and `request.shop` (also header-only, `x-shopify-shop-domain`) is forwarded unchanged into `WebhookMetadata` [4](#0-3) .

Exploit flow: the attacker installs the app on their own development shop (as permitted by the threat model) and receives a genuine webhook delivery for some topic (e.g. `app/uninstalled`) with body `B` and a valid `X-Shopify-Hmac-Sha256` header `H` computed by Shopify using the real `api_secret_key`. The attacker then replays a POST directly to the app's webhook endpoint with the same body `B` and hmac `H`, but sets `X-Shopify-Topic: shop/update` and `X-Shopify-Shop-Domain: <victim-shop>.myshopify.com`. Because `HmacValidator.validate` only checks `B` against `H`, it still passes. `Registry.process` looks up the handler registered for `shop/update`, and invokes it with `WebhookMetadata` claiming `shop: <victim-shop>`, `topic: shop/update`, and a `body` that was never actually produced for that topic/shop.

No existing guard prevents this: `HmacValidator.validate` only proves the body was signed by the correct secret at some point, not which topic/shop it was signed for; `Registry.process` has no secondary check that ties `topic`/`shop` headers to the signed payload; there is no `Context.setup?`/`private?` check relevant here, and Sorbet typing only enforces types, not header authenticity.

## Impact Explanation
This lets an attacker force a completely mismatched handler (potentially a higher-trust or destructive one) to run with attacker-chosen `topic` and, critically, attacker-chosen `shop` domain, while the `body` content is whatever was actually signed for the attacker's own original webhook. Any host app that trusts `WebhookMetadata#shop` or `#topic` to select tenant context, deletion behavior (e.g. `customers/redact`, `shop/redact` semantics elsewhere), or business logic can be tricked into acting "on behalf of" an arbitrary victim shop, or running the wrong handler's logic against attacker-supplied data. This is repeatable against arbitrary victim shop domains and arbitrary registered topics, using a single genuine webhook delivery the attacker received for their own shop.

## Likelihood Explanation
Preconditions are met by the stated threat model: the attacker only needs to install the target app on a shop they control and passively receive one real webhook to obtain a valid `(body, hmac)` pair. No credential, secret, or privileged access is required — this is a low-cost, fully repeatable attack limited only by the attacker's ability to capture one legitimate webhook delivery and directly POST to the app's public webhook endpoint with forged headers.

## Recommendation
Bind the `topic`, `shop`, `webhook_id`, and `api_version` headers into the HMAC-verified signable string (or otherwise cryptographically tie them to the payload), rather than relying on the raw body alone in `Request#to_signable_string`. At minimum, `Registry.process` should not trust `request.topic`/`request.shop` for handler dispatch or metadata unless those values are proven to correspond to the same delivery whose body was HMAC-verified.

## Proof of Concept
Minitest under `test/webhooks/registry_test.rb` (WebMock/Mocha not required, no live shop):
1. Register two distinct `TestHelpers::FakeWebhookHandler` instances for `topic: "app/uninstalled"` and `topic: "shop/update"` via `ShopifyAPI::Webhooks::Registry.add_registration`.
2. Compute a valid HMAC over body `"{}"` using `ShopifyAPI::Context.api_secret_key` (as in existing `setup`), simulating a genuine delivery for `app/uninstalled`.
3. Build a `ShopifyAPI::Webhooks::Request` with that same body/hmac but `"x-shopify-topic" => "shop/update"` and an attacker-chosen `"x-shopify-shop-domain"`.
4. Call `ShopifyAPI::Webhooks::Registry.process(request)`.
5. Assert that the `shop/update` handler fired (not the `app/uninstalled` handler) and that `data.shop` equals the attacker-chosen victim domain, proving `handler_selected != handler_intended_for_signed_payload` while `HmacValidator.validate` returned `true`.
