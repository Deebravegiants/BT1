### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC-verified payload from **only** the raw request body, while the `shop` (tenant identifier), `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers and forwarded to the app's webhook handler as trusted metadata. This breaks the identity binding `HMAC(signed_bytes) == HMAC(bytes_that_determine_the_tenant)`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` and compares it to the `hmac` header value using `OpenSSL.secure_compare`: [1](#0-0) 

`to_signable_string` for a webhook `Request` returns only `@raw_body`: [2](#0-1) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight out of HTTP headers, none of which are covered by the signable string: [3](#0-2) 

`Registry.process` verifies only the HMAC of the body, then immediately trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` passed to the host app's handler: [4](#0-3) 

`WebhookMetadata.shop` is documented and intended to be used by host applications as the tenant key for routing/storing webhook data (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) [6](#0-5) 

This mirrors exactly the report's bug class: a value the code trusts and acts on (`shop`) is not covered by the integrity check (HMAC) that is supposed to bind the whole request together — analogous to the un-overflow-checked fee field in the external report being used without the protection the design assumed. Here, the equality that should hold is:
`authenticated_bytes (HMAC input) == bytes used to select the tenant (shop header)`
but in this implementation `authenticated_bytes = raw_body` while `tenant_selector = header["x-shopify-shop-domain"]`, and these are independent of each other.

Because Shopify's app secret (`api_secret_key`) is shared across every shop that installs a given app, any valid `(body, hmac)` pair produced for one installation remains valid for any other value of the `shop` header. An attacker who controls a shop with the app installed can obtain a genuine `(body, hmac)` pair for events on their own store, then submit that exact body/HMAC to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still passes because it only checks the body, and the app processes the forged event as if it originated from the victim's tenant.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an attacker-controlled payload, legitimately signed for their own installation, can be attributed to a different merchant's shop, letting the attacker inject fabricated webhook events (e.g. fake order/product/customer events, mandatory-webhook events like `customers/redact`) into another tenant's data pipeline. This is a cross-tenant access vulnerability against the identity binding the HMAC check is meant to provide.

### Likelihood Explanation
Exploitability only requires operating a normal, unprivileged install of the target app on an attacker-owned shop (no `api_secret_key`, access token, or privileged account needed) plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-controlled headers, which is exactly the transport this gem is designed to accept.

### Recommendation
Include the tenant-identifying and dispatch-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the body (e.g., derive/verify them from a separately authenticated channel per shop) before they are handed to `WebhookMetadata` and the caller's handler in `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
1. Attacker installs the target app on shop `attacker.myshopify.com` and triggers an event so Shopify sends a webhook `(raw_body B, x-shopify-hmac-sha256 H)` to the app's shared endpoint, where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)` from their own delivery (no interception of others' traffic needed—it is delivered to them).
3. Attacker crafts a new HTTP request to the same public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `HMAC(B)` against `H` — this still validates.
5. `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` is passed to the app's handler, which processes/attributes the (attacker-chosen) body as belonging to the victim's tenant.
