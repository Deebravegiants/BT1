### Title
Fee accounting mismatch when `actual_fee` exceeds reserved PGAS credit causes over-reported burn in `PGASFeePaid` event - (File: substrate/frame/transaction-payment/pgas-allowance/src/lib.rs)

### Summary
In `ChargePGAS::post_dispatch_details`, the `Pre::PGAS` branch computes `actual_fee` from `compute_actual_fee` and calls `credit.split(actual_fee)` on the reserved `credit`. Because `fungibles::Imbalance::split` clamps its first output to `min(amount, self.peek())`, if `actual_fee` is ever larger than the reserved `credit.peek()`, `fee_refund` will be zero-valued, and the code takes the "happy path" branch that reports `burned = actual_fee` (the inflated value) in `Event::PGASFeePaid`, even though only `reserved` (a smaller amount) was actually withdrawn from the user and burned.

### Finding Description
The relevant code: [1](#0-0) 

```
Pre::PGAS { who, credit, weight_refund } => {
    let mut actual_post_info = *post_info;
    actual_post_info.refund(weight_refund);
    let actual_fee = pallet_transaction_payment::Pallet::<T>::compute_actual_fee(...);
    let reserved = credit.peek();
    let (consumed, fee_refund) = credit.split(actual_fee);
    let burned = if fee_refund.peek().is_zero() {
        actual_fee
    } else {
        match ...resolve(&who, fee_refund) {
            Ok(()) => actual_fee,
            Err(fee_refund) => { ... reserved },
        }
    };
    Pallet::<T>::deposit_event(Event::PGASFeePaid { who, actual_fee: burned });

}
```

`credit.split(actual_fee)` uses the generic `fungibles::Imbalance::split` implementation: [2](#0-1) 

```
pub fn split(self, amount: B) -> (Self, Self) {
    let first = self.amount.min(amount);
    let second = self.amount - first;
    ...
    (Imbalance::new(asset.clone(), first), Imbalance::new(asset, second))

```

This clamps: if `actual_fee > reserved`, `consumed = reserved` (all of `credit`) and `fee_refund = reserved - reserved = 0`. Since `fee_refund.peek().is_zero()` is true, the code takes the `actual_fee` branch (not the `reserved` fallback), so the emitted event reports `burned = actual_fee`, which can be strictly greater than `reserved` — i.e., greater than the amount of PGAS actually withdrawn from the user and actually burned. This directly violates the documented invariant that events must match real balances moved.

However, whether `actual_fee` can genuinely exceed `reserved` under attacker control depends on `pallet_transaction_payment::Pallet::<T>::compute_actual_fee`. That function computes the fee from `post_info.actual_weight`, and the standard implementation in `pallet_transaction_payment` clamps `actual_weight` to `min(info.weight, actual_weight)` before computing the fee (via `PostDispatchInfo::calc_actual_weight`/`Weight::min`), specifically to prevent a dispatchable from reporting more weight than was declared pre-dispatch. I was not able to fully re-verify the exact clamping logic of `compute_actual_fee` in this session (tool budget exhausted), but this clamp is the standard, long-standing behavior of `pallet_transaction_payment` across polkadot-sdk, and it exists precisely to prevent the "attacker inflates `actual_weight`" scenario described in the question. `info.weight` here is fixed by the extrinsic's declared `DispatchInfo` (`weight()` at prepare-time reserved `charge_pgas` fee based on `compute_fee(len, info, 0)`, and `fee` was withdrawn exactly at prepare time using that pre-dispatch fee, i.e. `reserved == fee == compute_fee(info.weight, ...)`). Because `compute_actual_fee` clamps `actual_weight ≤ info.weight`, `actual_fee` cannot legitimately exceed `reserved` through a nested call reporting an inflated `post_info.actual_weight` — the call's own `PostDispatchInfo` cannot report more weight than `info.weight` without being clamped by the transaction-payment fee calculation, and the extension's own `weight_refund` subtraction only reduces, never increases, the compared post-info weight.

Given this, the described attack path — a normal user manipulating a nested dispatchable to report higher-than-prepared `actual_weight` and thereby inflate `actual_fee` beyond `reserved` — is not realizable through the standard `compute_actual_fee` weight-clamping guard that `pallet_transaction_payment` applies. The code path for `fee_refund.peek().is_zero()` in the happy case is simply `actual_fee == reserved` (i.e., no unused weight to refund), which is a normal, correct case, not an exploit.

### Impact Explanation
No concrete, attacker-reachable impact is established. The theoretical accounting bug (event reporting `actual_fee` instead of the true burned amount when `fee_refund` clamps to zero due to `actual_fee > reserved`) would be a real defensive-in-depth issue if `compute_actual_fee` could ever return a value greater than the pre-dispatch reserved fee, but the standard transaction-payment weight-clamping (`actual_weight.min(dispatch_info.weight)`) prevents this under normal call paths, and the question requires only unprivileged, real extrinsic-path exploitation.

### Likelihood Explanation
Low/not reproducible via a normal user. Reaching `actual_fee > reserved` would require bypassing `pallet_transaction_payment`'s standard weight-clamp, which is not something an unprivileged signed caller, proxy, multisig, or contract caller can influence through legitimate `PostDispatchInfo::actual_weight` reporting from a nested dispatchable — such reporting only lowers the weight used for fee computation, never raises it above `info.weight`.

### Recommendation
As a defense-in-depth measure (not because the current attack path is provably reachable), the code should not infer "no refund needed" purely from `fee_refund.peek().is_zero()`. Instead it should explicitly compare `actual_fee` against `reserved` and clamp/assert `actual_fee <= reserved` before reporting `burned`, e.g.:
```rust
let capped_fee = actual_fee.min(reserved);
let burned = if fee_refund.peek().is_zero() { capped_fee } else { ... };
```
This removes any latent risk if `compute_actual_fee`'s clamping guarantee is ever weakened or changed in a way this pallet does not defensively re-check.

### Proof of Concept
Not applicable as a demonstrable exploit — an integration test attempting to set `post_info.actual_weight` above `info.weight` (the pre-dispatch claimed weight) would find `compute_actual_fee` clamps the weight back down to `info.weight` before fee calculation, so `actual_fee` would equal `reserved` at most, and `Assets::balance` deltas would match the emitted `Event::PGASFeePaid.actual_fee` exactly in that scenario. No test can drive `actual_fee` above `reserved` via legitimate `post_info` manipulation from a nested call under attacker control.
