### Title
Escrowed intent funds can be permanently frozen when the beneficiary is blacklisted by the token - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The `IntentsBase._withdraw` function (used by `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents`) pushes escrowed ERC20 tokens directly to a `beneficiary` address via `IERC20(token).safeTransfer(beneficiary, amount)`. If the token is a blacklist-capable stablecoin (e.g., USDC) and the beneficiary (the solver on fill, or the user on refund/cancel) is blacklisted, this transfer permanently reverts, and there is no alternate pull-based recovery mechanism — mirroring the root cause pattern of `PredictDotLoan.repay()`'s direct `LOAN_TOKEN.safeTransferFrom(msg.sender, loan.lender, debt)`.

### Finding Description
`_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol` (lines 451-485) is the settlement primitive for cross-chain intent orders: [1](#0-0) 

It is invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` message is delivered by a relayer over ISMP: [2](#0-1) 

`onAccept` on the source-chain `IntentGatewayV2`/`ExtrinsicIntents` contract is called by `EvmHost.dispatchIncoming` on behalf of the ISMP host, which is itself triggered by an unprivileged relayer submitting a state proof of the destination-chain fill/cancel event. There is no way for the relayer, solver, or user to alter the `beneficiary` embedded in the already-committed `WithdrawalRequest` (it is fixed by whoever filled the order on the destination chain, or by the user's own account on refund).

If `token` is USDC-like and `beneficiary` becomes blacklisted (e.g., a solver address gets blacklisted between filling the destination side and settlement, or a user's own address gets blacklisted), `IERC20(token).safeTransfer(beneficiary, amount)` reverts. Because `EvmHost.dispatchIncoming` treats a failed `onAccept` call as "retryable" by deleting the request receipt: [3](#0-2) 

the message can be resubmitted indefinitely, but every retry hits the exact same `safeTransfer` revert against the same fixed beneficiary — the escrow can never be released. The same push-to-arbitrary-address pattern also exists in the same-chain fill path (`IntrinsicIntents.sol`, `ExtrinsicIntents.sol`) via `safeTransferFrom(msg.sender, beneficiary, ...)`, and in the Tron port's `withdraw()` (`evm/tron/contracts/apps/IntentGatewayV2.sol`), all of which push tokens directly to a beneficiary chosen at order-fill/cancel time rather than crediting an internal claimable balance.

### Impact Explanation
Once a beneficiary address is blacklisted by the escrowed input token:
- On the fill/redeem path: the solver's earned input tokens become permanently stuck in escrow inside the gateway contract — the solver already delivered output tokens to the user but can never claim payment.
- On the cancel/refund path: the user's own escrowed input tokens (e.g., USDC) become permanently frozen if the user's address is blacklisted, with no alternative recovery function to redirect the transfer to another address.

This is a permanent freezing-of-funds condition reachable from a normal, unprivileged intent lifecycle (place → fill → relay settlement), matching the accepted analog class in the source report.

### Likelihood Explanation
Requires the escrowed token to be a centrally-blacklistable stablecoin (USDC, USDT, etc. — which are exactly the assets intents protocols are built to bridge) and the beneficiary address to become blacklisted after order placement/fill but before settlement completes. This is a realistic, externally-triggered event (as acknowledged in the referenced Sherlock report) rather than a contrived attack, and it does not require any malicious actor — a single blacklist action by the token issuer against a solver or user is sufficient.

### Recommendation
Replace the direct push transfer in `_withdraw` (and the equivalent flows in `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`, and the Tron `IntentGatewayV2.withdraw`) with a pull-based claim mechanism: on settlement, credit an internal `claimable[beneficiary][token] += amount` balance instead of transferring immediately, and expose a separate `claim(token)` function the beneficiary (or a delegate/alternate recipient they designate) can call to withdraw. This decouples message delivery/finality from the beneficiary's ability to receive tokens and prevents a blacklist event from permanently freezing escrowed funds or blocking the relay of subsequent legitimate settlement messages.

### Proof of Concept
1. User places a cross-chain order escrowing USDC as input, expecting DAI as output (`placeOrder`).
2. Solver fills the order on the destination chain, delivering DAI to the user (`fillOrder` → `_fillCrossChain`), and a `RedeemEscrow` message is dispatched back to the source chain naming the solver as `beneficiary`.
3. Before the relayer delivers the settlement proof, the solver's address is added to USDC's blacklist (external event, as in the original report).
4. A relayer submits the proof; `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept` → `_withdraw`, which calls `IERC20(USDC).safeTransfer(solver, amount)` — this reverts because the solver is blacklisted.
5. `dispatchIncoming` swallows the failure and deletes the request receipt "so it can be retried" — but every future retry with the same `beneficiary` fails identically.
6. The escrowed USDC remains permanently locked in the `IntentGatewayV2` contract; the solver already gave up the DAI output and cannot recover the USDC, and no other address can be substituted to receive it. [1](#0-0) [2](#0-1) [3](#0-2)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
