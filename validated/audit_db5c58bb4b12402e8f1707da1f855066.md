### Title
Webhook HMAC signature does not bind the `shop-domain`/`topic`/`webhook-id` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used by `ShopifyAPI::Webhooks::Registry.process` are read straight from unauthenticated HTTP headers. Any party who legitimately receives one validly HMAC-signed webhook (e.g., a developer who installed the app on their own store) can replay that same body/HMAC pair while substituting the `shop-domain` header to impersonate a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are parsed directly from the incoming headers and are never included in the signed material: [2](#0-1) 

`Utils::HmacValidator.validate_signature` only verifies `verifiable_query.to_signable_string` (the body) against the app's secret — it never incorporates the headers into the signable string: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop` and `request.topic`, both of which are unauthenticated header values: [4](#0-3) 

This breaks the intended identity binding: **bytes verified (body) ≠ bytes acted on (shop/topic/webhook_id headers)**. Since the same `api_secret_key` is shared across every shop that has installed a given app, any actor who controls a shop that has installed the app can legitimately receive a validly-signed webhook for their own shop, then resend the identical body and HMAC value to the app's webhook endpoint with a different `shopify-shop-domain` header. The HMAC will still validate (it only proves the body was signed with the app's secret, which Shopify did), but the app will process the payload as if it originated from the victim shop.

### Impact Explanation
This directly enables cross-tenant access: an attacker with legitimate access to one tenant (their own shop installation) can forge webhook events attributed to any other shop that uses the same app, causing the host application to create, update, or act on data under the wrong tenant's identity. This matches the "Critical - cross-tenant access" category since no credentials belonging to the victim are needed — only a genuine webhook obtained from the attacker's own, legitimately-installed shop.

### Likelihood Explanation
Medium-to-High: the attacker only needs to install the target app on any shop they control (a normal, unprivileged action for a public app) to obtain one genuine signed webhook body, then replay it with a modified header value using any HTTP client. No secret leakage, TLS interception, or privileged account is required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signable string used for HMAC computation and validation, or otherwise cryptographically bind the shop/topic to the signature so that a valid body signature cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g., `orders/create`) so Shopify sends a genuine webhook: headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid hmac of body>`, body `B`.
2. Attacker captures this HTTP request.
3. Attacker resends the identical body `B` and `shopify-hmac-sha256` value to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against the secret — this passes because `B` is unchanged.
5. `request.shop` returns `"victim-shop.myshopify.com"` from the forged header, and the handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to treat attacker-controlled data as belonging to the victim shop.
