This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` (used by `HmacValidator.validate`) signs only `@raw_body`, while `shop` is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the HMAC-covered payload.

### Title
Webhook `shop` field is unauthenticated, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is not covered by the HMAC signature verified in `ShopifyAPI::Utils::HmacValidator.validate`. Only the raw request body is signed, so an attacker who controls a legitimately signed webhook body (e.g., from their own shop's installation of the app) can replay it while substituting an arbitrary `shop-domain` header value, and the gem will accept it as authentic for that arbitrary shop.

### Finding Description
`Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is parsed from the `hmac-sha256` header — neither includes the `shop` value: [3](#0-2) [4](#0-3) 

`shop` is read verbatim from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the signed body: [5](#0-4) 

After HMAC validation succeeds, `Registry.process` hands the handler a `WebhookMetadata` object built directly from `request.shop`, which the host application typically uses as the tenant key to look up records/credentials: [1](#0-0) 

Because all shops that install the same app share one `api_secret_key` (the app's client secret, not a per-shop secret), any merchant who installs the app receives legitimately-signed webhook deliveries for their own shop. That merchant can capture a valid `(raw_body, hmac)` pair and re-POST it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop that also uses the app. `HmacValidator.validate` will still return `true` because it never verifies that the `shop` header is bound to the signed bytes — it only checks the raw body against the shared secret. This breaks the equality that should hold: *the shop identified as authenticated by the HMAC check* == *the shop attributed to the record being acted on (`request.shop` used as the tenant key)*.

### Impact Explanation
This allows cross-tenant confusion in webhook processing: an attacker-controlled (but validly-signed-for-a-different-shop) payload can be attributed to an arbitrary victim shop known to use the same app. Depending on the host application's webhook handler logic (e.g., updating shop-scoped configuration, revoking access, marking uninstall/redact flags, updating cached tokens or settings keyed by `shop`), this can lead to cross-tenant state corruption or data leakage attributed to the wrong shop — i.e., a cross-tenant access primitive achieved purely through this gem's webhook verification logic.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even low-privilege) merchant who has installed the target app themselves, so they can capture a validly-signed webhook body/HMAC pair. No access to the app's `api_secret_key`, access tokens, or any victim credentials is needed — only the ability to send a crafted HTTP request with a forged header to the app's public webhook endpoint. This is reachable purely through documented gem usage (`ShopifyAPI::Webhooks::Registry.process`) as shown in the gem's own tests.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value verified by the HMAC, not just the raw body — e.g., include these header values in `to_signable_string`, or independently verify that the `shop` header matches an expected/registered shop domain for the given app installation before dispatching to handlers. At minimum, document that host applications must not trust `request.shop` unless corroborated by an independent, tenant-bound record lookup.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g. for `orders/create`:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id": 1, "note": "..."}`
2. Attacker resends the exact same body and `hmac-sha256` value to the app's webhook endpoint, but changes the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. In the app:
   ```ruby
   request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
   ShopifyAPI::Webhooks::Registry.process(request)
   ```
   `Utils::HmacValidator.validate(request)` passes because it only re-computes HMAC over `@raw_body` using the shared `api_secret_key`, ignoring the `shop-domain` header entirely (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from, and was only ever signed for, `attacker-shop.myshopify.com`, causing the host app to act on victim-shop data/state using attacker-controlled content.
