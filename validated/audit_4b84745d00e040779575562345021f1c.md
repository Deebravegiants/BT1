### Title
Cross-chain messages can be replayed across EVM chain forks due to `block.chainid`-derived state machine identifiers with no fork/replay protection - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.host()` derives the destination chain's ISMP identity purely from `block.chainid` via `StateMachine.evm(block.chainid)`. If any EVM chain hosting the bridge (or its counterparty) undergoes a contentious hard fork that preserves the same chain ID on both resulting chains (the common case, absent an explicit EIP-155 chain ID bump on one side), a single relayed message/proof becomes valid and independently deliverable on both post-fork chains, since each fork inherits identical pre-fork `EvmHost` state/bytecode but thereafter maintains fully independent, non-communicating storage (including `_requestReceipts`).

### Finding Description
`EvmHost.host()` returns `StateMachine.evm(block.chainid)` [1](#0-0)  and this is the value checked against every incoming request's `dest` field in `HandlerV2.handlePostRequests`: `if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();` [2](#0-1) .

The commitment used for replay protection is `keccak256(abi.encode(req))` over the `PostRequest` struct (`source`, `dest`, `nonce`, `from`, `to`, `timeoutTimestamp`, `body`) [3](#0-2) , and delivery is tracked in `_requestReceipts[commitment]`, a mapping local to each deployed `EvmHost` instance [4](#0-3) .

None of these values (`chainid`, the `dest`/`source` state-machine identifiers, or the receipt mapping) carry any fork-distinguishing salt (e.g., a genesis hash, a fork-block marker, or a monotonically-bumped chain ID). Consequently:
- If the **destination** EVM chain hard-forks into Chain A and Chain B, both retaining the same `chainid`, both forks deploy from identical pre-fork state, so both run an `EvmHost` at the same address returning the same `host()` value and holding an *independent copy* of `_requestReceipts` (empty for messages not yet delivered before the fork, or diverging afterwards).
- Any relayer (an unprivileged actor — anyone may call `HandlerV2.handlePostRequests`, per the "Access: Permissionless" note [5](#0-4) ) can submit the *same* consensus-verified `PostRequestMessage` (source-chain MMR proof, unaffected by a destination-side fork) separately to Chain A's `EvmHost` and to Chain B's `EvmHost`. Each host independently verifies the proof against its stored (identical, since both forks share the same source-chain state prior to the fork) state commitment, finds no local receipt, and dispatches to `onAccept`.
- For `HyperFungibleToken`/`BridgeToken`, `onAccept` unconditionally mints: `_mint(beneficiary, message.amount);` [6](#0-5) . The relayer thus obtains a second, unbacked mint of the bridged asset on the second fork, at no additional cost (the source-side burn/lock happened only once).

This is the direct structural analog of the reported Avail issue: identifiers used to gate/replay-protect cross-chain messages are derived solely from a value (`chainid`/domain constant) that is *identical across a chain fork*, so the protocol cannot distinguish "the same message replayed on a sibling fork" from "a new legitimate message," enabling unbacked duplication of bridged value.

### Impact Explanation
A contentious hard fork of any EVM chain integrated with Hyperbridge (source or destination) allows replay of previously-dispatched cross-chain messages onto the forked chain that never received them, resulting in double-minting of bridged tokens (`HyperFungibleToken`, `BridgeToken`, wrapped variants) or double-execution of any other `onAccept` side effect (e.g., `IntentGatewayV2` order fills, calldata execution via `CallDispatcher`) on the newly diverged chain. This is an unbacked-mint / value-duplication bug reachable by any relayer without special privileges, satisfying the Medium/High bar for "unbacked mint" impact.

### Likelihood Explanation
Likelihood is contingent on an external event (a chain fork) rather than being purely a function of attacker capability, which limits routine exploitability; however, once such a fork occurs, exploitation requires only resubmitting an already-relayed, already-proven message to the second fork's `EvmHost` — a permissionless, low-cost action requiring no special access, consistent with how the original Avail finding was scored (Medium).

### Recommendation
Bind the chain identity used in `host()`/`StateMachine.evm(...)` and in message commitments to something that provably diverges across a fork (e.g., include the deployment's genesis block hash or a governance-set, monotonically-incrementing "epoch"/fork id alongside `block.chainid`), and require that identifier to be included in the `PostRequest`/commitment hash so that a message valid on the pre-fork chain cannot be replayed as-is on either post-fork branch. Alternatively/additionally, provide an admin-governed mechanism to freeze/re-key the host's chain identity immediately upon detecting a fork event.

### Proof of Concept
1. Chain `C` (chainid `X`) hosts `EvmHost` at address `H`; a relayer submits `handlePostRequests` for message `M` with `dest = StateMachine.evm(X)`, delivering it and minting via `HyperFungibleToken.onAccept` — `_requestReceipts[hash(M)]` is now set on `C`.
2. Chain `C` undergoes a contentious hard fork at block `B`, producing `C_A` and `C_B`, both with chainid `X`, both containing the pre-fork deployed bytecode/storage of `EvmHost` at `H` (except any state written strictly after the fork diverges).
3. Suppose message `M2` was proven/committed on the source chain before block `B` but only delivered on `C_A` after the fork (i.e., `_requestReceipts[hash(M2)]` is set on `C_A` but not on `C_B`, because delivery is a post-fork transaction independently executed per chain).
4. The relayer resubmits the identical `PostRequestMessage` for `M2` (same MMR proof, since the source chain's history up to the proven height is unaffected by the destination's fork) to `EvmHost` on `C_B`. `HandlerV2.handlePostRequests` on `C_B` finds `host.requestReceipts(hash(M2)) == address(0)` [7](#0-6)  and dispatches again, causing `HyperFungibleToken.onAccept` to mint `message.amount` a second time on `C_B` for the same source-chain burn/lock event.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
