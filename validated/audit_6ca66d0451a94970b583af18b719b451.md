### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` only signs and verifies the raw HTTP body via HMAC, while the `shop` (from `X-Shopify-Shop-Domain`) and `topic` (from `X-Shopify-Topic`) headers used to route and attribute the webhook are read directly from unauthenticated headers and never bound into the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` and `topic` are derived purely from HTTP headers with no cryptographic binding to those values: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then forwards the unauthenticated `request.shop`/`request.topic` values straight to the app's webhook handler as trusted tenant/routing identifiers: [3](#0-2) 

The intended binding is: `HMAC(body, client_secret) == received_hmac` should authenticate **all** fields the handler relies on for tenant identification (shop) and dispatch (topic). Instead only `body` is covered, so `shop` (and `topic`) can be swapped after the HMAC was computed by Shopify, and validation still passes because `OpenSSL.secure_compare` only re-derives the signature from the body: [4](#0-3) 

Exploit path: an unprivileged attacker who is a legitimate merchant using the target app receives real, correctly-HMAC-signed webhooks from Shopify for their own store (this is normal, not privileged access). Because the app's `client_secret` is shared across every shop that installs the app, the same HMAC secret authenticates webhooks for all tenants. The attacker can capture one of their own legitimate `(body, hmac)` pairs and replay it to the app's public webhook endpoint while altering only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the secret; `Registry.process` then invokes the handler with `shop: request.shop` set to the victim's domain, injecting attacker-controlled webhook data under another tenant's identity.

### Impact Explanation
This breaks the equality `authenticated_shop == acted_upon_shop` that the HMAC is meant to guarantee, allowing cross-tenant data injection: a handler that keys off `WebhookMetadata#shop` (e.g., to look up the victim's stored session/access token, update per-shop settings, or process the payload as belonging to the victim) will act on forged data attributed to a shop the attacker does not control. This matches the "Critical - cross-tenant access" impact category, since it lets one tenant's requests be misattributed to and processed under a different tenant's identity purely through data crossing the app's own trust boundary.

### Likelihood Explanation
Any merchant who installs the app can trivially capture a valid `(body, hmac)` pair from webhooks sent to their own shop (no privileged access, no credential theft, no TLS interception needed — they are the legitimate recipient). Replaying it with a modified header is a simple unauthenticated HTTP request to the app's public webhook endpoint. The only host-app dependency is that the handler uses `shop`/`topic` from `WebhookMetadata` to make tenant/routing decisions, which is exactly the documented and intended use of these fields per `docs/usage/webhooks.md` and `WebhookHandler`.

### Recommendation
Include `shop-domain` and `topic` (and any other header fields the handler relies on) in the HMAC-signed payload construction, or independently verify that `request.shop` matches the shop associated with the session/access token that ultimately triggered the webhook subscription, before trusting it in `Registry.process`. At minimum, document prominently that `shop` and `topic` are unauthenticated and must not be used as sole tenant-identification without additional server-side verification (e.g., cross-checking against the app's own webhook subscription records per shop).

### Proof of Concept
1. App has installed the gem's webhook registry and a handler that trusts `WebhookMetadata#shop` for tenant lookups.
2. Attacker (a legitimate merchant, `attacker.myshopify.com`) receives a real Shopify webhook: body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: H = HMAC(client_secret, B)`.
3. Attacker resends the same body `B` and same `H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. In `lib/shopify_api/webhooks/request.rb`, `to_signable_string` returns `B` unchanged, so
```ruby
ShopifyAPI::Utils::HmacValidator.validate(request) # => true
```
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-199) passes validation and calls the handler with `shop: "victim.myshopify.com"`, even though the HMAC never covered that header value — the app processes attacker-supplied data as if it originated from the victim's shop.
