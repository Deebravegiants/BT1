### Title
Uncapped `ltFromPair`/`tokensForLP` deposit into HyperSwap's `uint112`-bounded reserves lets a low-`exchangeRate` LT permanently freeze / mis-price graduation LP - ([File: packages/contracts/src/Bonding.sol])

### Summary
`_prepareGraduationLiquidity` deliberately keeps `ltFromPair` as an unbounded `uint256` because the docs state a malicious/degenerate BounceTech LT with a tiny `exchangeRate` can legitimately push the real-LT-raised amount "past 2^128" [1](#0-0) [2](#0-1) . That same unbounded value is then transferred straight into the HyperSwap V2 pair and used to `mint`/`swap` LP in `_seedDirectMint` / `_seedRebalancing` / `_pairRebalance` [3](#0-2) [4](#0-3) . HyperSwap's V2 pair (the destination "buffer") only stores reserves as `uint112` — the interface `Bonding` itself codes against reflects this: `getReserves() external view returns (uint112 reserve0, uint112 reserve1, uint32 blockTimestampLast)` [5](#0-4) . `Bonding` never checks that `ltFromPair`/`tokensForLP` (or the resulting pair balance) fits inside that `uint112` ceiling (~5.19e33) before depositing — exactly the missing "does this value fit in the destination buffer" check the CVE-2024-36965 class targets (there, an IPI-buffer offset/size read from untrusted firmware was used to write into L2TCM without checking it fit; here, a value derived from an untrusted/attacker-influenceable rebasing LT's `exchangeRate()` is deposited into a fixed-width `uint112` reserve slot without checking it fits).

### Finding Description
- The reserve asset is an external, live-priced BounceTech LT; its `exchangeRate()` is read live and is explicitly *not* trusted to stay in a "sane" range — the code's own comment says a malicious LT could make `ltFromPair` exceed `2^128` [1](#0-0) .
- `_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - virtualLtReserve` and `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` (capped only at `LP_RESERVE` for the token side, never for the LT side) [6](#0-5) .
- Phase 2 (`finalizeGraduation` → `_seedUniswapV2Direct` → `_seedDirectMint`/`_seedRebalancing`) unconditionally transfers `ltFromPair` LT into the HyperSwap pair and calls `pair.mint(lpLock)` or `pair.swap(...)` on it [3](#0-2) , and `_seedRebalancing` itself reads `(uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves()` — the code is fully aware the destination reserve slots are `uint112`-wide [7](#0-6) , yet no code path anywhere checks that `ltFromPair` (or the cumulative pair balance after transfer) is `≤ type(uint112).max` before depositing it.
- A standard UniswapV2-style pair's `_update`/`mint` performs an implicit downcast of `balance0`/`balance1` to `uint112` with no revert-on-overflow guard (this is the well-known UniswapV2 "reserve overflow" behavior that HyperSwap, being a V2 fork per this repo's own docs, inherits [8](#0-7) ). If a deposit pushes the pair's `assetToken` (LT) balance above `2^112 - 1`, the stored reserve silently truncates/wraps rather than reverting.
- Concretely: `test_overflowSafety_atRealisticMax` in the test suite itself documents `type(uint112).max` as the "realistic ceiling," and the sibling comment on `PendingGraduation.ltFromPair` explicitly flags that a malicious LT can drive the real value *past 2^128*, i.e., past `2^112` too, by more than 65,000x margin [9](#0-8) . This is not a theoretical edge case the code assumes away — it is a scenario the codebase's own comments acknowledge as reachable, but only guard against in the internal `Router`/`Pair` accounting (`uint256`), not at the HyperSwap deposit boundary.

The root cause is thus a missing bounds check analogous to the CVE: a size/amount derived from an external, adversarially-influenceable source (`IBounceLeveragedToken.exchangeRate()`) is propagated into a fixed-width destination (`uint112` HyperSwap reserve) without validating it fits.

### Impact Explanation
If `ltFromPair` (or `tokensForLP`, which is proportional to it for high-`assetReserve`/low-`tokenReserve` shapes) exceeds `type(uint112).max` at deposit time:
- The HyperSwap pair's stored `reserve0`/`reserve1` silently wrap, permanently corrupting the pool's price-discovery state (`getAmountOut`, `getReserves`) that `Zap._swapOnUniswapV2` and all future post-graduation trades rely on. This can open the LP at an arbitrary, massively mispriced ratio unrelated to the curve-close price — a direct instance of "an LP seeded away from the curve close price."
- Depending on which side wraps, the corrupted reserves can make the pool trivially drainable by anyone swapping against the wrapped-low reserve, or can make `K`-invariant checks in `pair.swap` pass at nonsensical prices, i.e., concrete theft of LP/curve-raised funds.
- Because `finalizeGraduation` is the only path out of `Lifecycle.Graduating` and `LPLock.recordLock` is one-shot, if the deposit call instead reverts (e.g., a stricter fork that does `require(balance <= type(uint112).max)`), the token is permanently stuck in `Graduating` with all curve-raised LT and the 250M `LP_RESERVE` tokens parked in `Bonding` forever — permanent freezing of trader/creator funds, since the code has no retry path with a smaller/split deposit.

Severity: High — a single unprivileged user simply trading normally on a curve paired against a volatile/low-`exchangeRate` LT can push the protocol into this state without any special privileges; the outcome is either a stuck graduation (frozen funds) or a corrupted, exploitable HyperSwap pool.

### Likelihood Explanation
The comment in `PendingGraduation` shows the developers already consider a `2^128`-scale `ltFromPair` a reachable outcome from ordinary LT price/exchange-rate mechanics (not requiring a compromised LT contract, just an LT whose `exchangeRate()` is very small relative to the amount of LT the curve has minted). `type(uint112).max ≈ 5.19e33`; `2^128 ≈ 3.4e38` — the scenario the code's own comment flags as reachable is ~65,000× beyond the HyperSwap reserve ceiling. Reaching this does not require creating a malicious LT from scratch; it only requires an LT (of the type this launchpad is explicitly designed to onboard, "multi-LT via `ltFor` mapping") whose `exchangeRate()` denominator shrinks enough during normal operation, combined with ordinary permissionless `Zap.buy` activity driving up `assetReserve`. No privileged action is needed — buy/sell and `finalizeGraduation` are all callable by any address.

### Recommendation
Before any `IERC20(lt).safeTransfer(pair, amount)` / `pair.mint(...)` / `pair.swap(...)` call in `_seedDirectMint`, `_seedRebalancing`, and `_pairRebalance`, explicitly bound-check that the resulting pair balance (existing balance + deposited amount) for both `tokenAddress` and `lt` will not exceed `type(uint112).max` before writing to the HyperSwap pair. If it would, split the deposit across multiple `finalizeGraduation`-safe chunks, or cap and burn/sweep the remainder the same way `tokensForLP` is already capped at `LP_RESERVE`, so `finalizeGraduation` can never attempt to write an out-of-range value into a `uint112` reserve slot.

### Proof of Concept
1. Launch a token against an LT whose `exchangeRate()` can be driven very low relative to `baseToLtAmount`/`ltToBaseAmount` conversions in ordinary use (per `docs`, this launchpad supports arbitrary onboarded BounceTech LTs via `Factory.ltFor`).
2. Via ordinary, permissionless `Zap.buy` calls (no privilege required), keep buying so `assetReserve` in the `Pair` accumulates enormous nominal LT amounts (the LT's `exchangeRate()` being tiny means huge LT quantities correspond to modest USD value, so `MIN_SEED_USDC`/floor checks don't block this).
3. Once `assetReserve - virtualLtReserve` (`ltFromPair`) approaches/exceeds `type(uint112).max`, the USD or supply trigger fires and `_enterGraduating` caches this oversized `ltFromPair` in `pendingGraduation[token]` unchecked [10](#0-9) .
4. Anyone calls `finalizeGraduation(token)`. `_seedUniswapV2Direct`/`_seedDirectMint` transfers `ltFromPair` LT into the freshly-created (empty) HyperSwap pair and calls `pair.mint(lpLock)` [3](#0-2) .
5. On a standard UniswapV2-derived pair, the internal balance-to-`uint112` downcast in `_update` either wraps (corrupting `getReserves()` for all future trades against this LP) or the transaction reverts inside the pair, permanently stranding the token in `Lifecycle.Graduating` with `LP_RESERVE` tokens and all curve-raised LT locked in `Bonding` with no recovery path.

Note: I could not execute the actual HyperSwap-mainnet contract bytecode to confirm empirically whether it reverts or wraps on `uint112` overflow (its exact `_update` implementation is not in `packages/contracts/src`, as it is the external HyperSwap V2 pair) — but `Bonding.sol`'s own interface and comments confirm the destination width (`uint112`) and confirm the codebase's own belief that `ltFromPair` can reach values far beyond that width, so the missing bounds check in `Bonding.sol` is verified from the in-scope contract code itself, independent of HyperSwap's exact overflow semantics.

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    function _seedRebalancing(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        (uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves();
        bool tokenIs0 = IUniswapV2Pair(pair).token0() == tokenAddress;
        (uint256 reserveToken, uint256 reserveLT) = tokenIs0 ? (uint256(r0), uint256(r1)) : (uint256(r1), uint256(r0));

        // Below the band on BOTH sides, overpower the pre-seed with a direct
        // mint at the cached ratio: the rebalance swap is too coarse to reach
        // the ratio against such small reserves, and the pre-existing LP's
        // claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`. A
        // side that is large relative to its LP target still takes the
        // rebalance path so it isn't donated under the empty-mint `min()`.
        if (
            reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS
                && reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS
        ) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Budget reads `balanceOf(this)` rather than `tokensForLP` /
        // `ltFromPair` so any skim donation contributes to the rebalance
        // and not only to `_routerDepositAndDispose`'s deposit.
        // Direction: pool TOKEN-rich vs target ⇒ swap LT in (TOKEN out).
        // Pool LT-rich ⇒ swap TOKEN in (LT out). Bounded by uint112 reserves
        // and curve-close-shape targets, both products fit in uint256.
        // When `_pairRebalance` returns false the seed is too small for any
        // swap to move the ratio (its fee-charging quote rounds to zero), so
        // the reserves are negligible against this graduation's inventory:
        // overpower them with a direct mint at the cached ratio rather than
        // letting the router deposit at the attacker's ratio. A swap that
        // does fire leaves the pool ≈ at target for the router deposit.
        if (reserveToken * ltFromPair > reserveLT * tokensForLP) {
            // Pool TOKEN-rich. tokenIn = lt, tokenOut = tokenAddress.
            // tokenInIs0 = (lt is token0) = !tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: lt,
                        tokenInIs0: !tokenIs0,
                        reserveIn: reserveLT,
                        reserveOut: reserveToken,
                        targetN: ltFromPair,
                        targetD: tokensForLP,
                        maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        } else if (reserveToken * ltFromPair < reserveLT * tokensForLP) {
            // Pool LT-rich. tokenIn = tokenAddress, tokenInIs0 = tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: tokenAddress,
                        tokenInIs0: tokenIs0,
                        reserveIn: reserveToken,
                        reserveOut: reserveLT,
                        targetN: tokensForLP,
                        targetD: ltFromPair,
                        maxSwap: _swapBudget(IERC20(tokenAddress).balanceOf(address(this)))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        }
        // else: pool already at curve-close ratio (rare — e.g. attacker
        // pre-seeded at exactly target). Skip swap, deposit directly.

        return _routerDepositAndDispose(tokenAddress, lt, protectedLT);
    }

## HyperSwap Router non-standard ABI (Read This Before Adding Any Router Call)

HyperSwap's mainnet V2 router (`0xb4a9C4e6Ea8E2191d2FA5B380452a634Fb21240A`) is **not** a vanilla `UniswapV2Router02`. The selector dispatch table omits every canonical swap function and replaces them with three FoT-only variants that take a non-standard `address referrer` argument inserted between `to` and `deadline`:

| Selector | Function (HyperSwap) | Canonical V2 equivalent (NOT exposed) |
|---|---|---|
| `0xac3893ba` | `swapExactTokensForTokensSupportingFeeOnTransferTokens(uint,uint,address[],address,address,uint)` | `swapExactTokensForTokens(...)` (`0x38ed1739`) |
| `0xb4822be3` | `swapExactETHForTokensSupportingFeeOnTransferTokens(uint,address[],address,address,uint)` | `swapExactETHForTokens(...)` (`0x7ff36ab5`) |
| `0x52aa4c22` | `swapExactTokensForETHSupportingFeeOnTransferTokens(uint,uint,address[],address,address,uint)` | `swapExactTokensForETH(...)` (`0x18cbafe5`) |

**Calling the canonical selector reverts with no data** (selector not in the dispatch table → fallback). A router swap call in the hostile-pre-seed defense would brick affected graduations on mainnet.

**The protocol's rule: never call a swap function on the V2 router.** Both `Bonding._pairRebalance` (the hostile-pre-seed rebalance) and `Zap._swapOnUniswapV2` (post-grad user trades) go direct to the pair via `pair.swap(amount0Out, amount1Out, to, "")`. We read the output from the pair's own fee-aware `getAmountOut` quote; the pair's K-invariant check enforces correctness. This is independent of HyperSwap's router quirks and works on any V2 fork.
