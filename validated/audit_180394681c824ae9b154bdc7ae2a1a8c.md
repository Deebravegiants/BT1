### Title
Unauthenticated arbitrary external calls via Emporium's `signerAddress == address(0)` path combined with a balance-check bypass when `erc20TokenAddresses` is empty - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol, contracts/Hinkal.sol, contracts/CircomDataBuilder.sol)

### Summary
The MakerDAO report's core bug class is that a value-accounting mechanism (the `pot`/`jug` rate accrual) can be manipulated within a single transaction because the check enforcing economic consistency is not actually tied to the real state that matters. The Hinkal analog is structural rather than rate-based: when an Emporium transaction is built with `erc20TokenAddresses.length == 0` (the "Emporium-min" circuit variant), Hinkal's balance-conservation loop is skipped entirely, and `EmporiumUpgradeable.verifyWallet()` skips the EdDSA/ECDSA authorization check whenever `stack.signerAddress == address(0)`. Combined with the fact that the Emporium-min circuit only exposes 3 public signals and never runs the per-token loop that binds the prover's EdDSA signature to real UTXO ownership, an attacker can submit a self-consistent (trivially satisfiable) proof and cause the Emporium contract to execute arbitrary, unaccounted `call{value: ...}(...)` operations.

### Finding Description
`Hinkal.sol`'s balance-conservation check only iterates over `circomData.erc20TokenAddresses`: [1](#0-0) 

If `erc20TokenAddresses.length == 0`, this loop never executes, so **no balance equation is enforced at all** for that `transact()` call, regardless of what the external action does with ETH/tokens.

`CircomDataBuilder.formInputForCircom` explicitly routes to a minimal input builder precisely when the action is Emporium and `erc20TokenAddresses.length == 0`: [2](#0-1) 

That builder exposes only 3 public signals (`emporiumMessage`, `timeStamp`, `calldataHash`) — it never computes or exposes `signedMessageHash`, `rootHashHinkal`, or any nullifier/commitment data as public inputs.

In the circuit, the per-token loop that binds `spendingPublicKey`/`eddsaSignature` to a real Merkle-tree UTXO (nullifier check, root-hash equality, commitment checks) is guarded by `for (var i = 0; i < tokenCount; i++)`, so with `tokenCount == 0` it is entirely skipped: [3](#0-2) 

Only the unconditional `sigVerifier` constraint remains: [4](#0-3) 

Since `spendingPublicKey`, `eddsaSignature`, and `signedMessageHash` are private witnesses that are not exposed publicly in the Emporium-min variant and are not tied to any real leaf/nullifier (the loop that would tie them to the tree is skipped), a prover can pick a self-generated keypair and self-signed message that trivially satisfies `sigVerifier` — this proof does not require possession of any real shielded balance.

On the Solidity side, `EmporiumUpgradeable.verifyWallet()` skips signature verification entirely when `stack.signerAddress == address(0)`: [5](#0-4) 

And `runAction()`'s "stateless" branch, taken whenever `!op.invokeWallet || stack.signerAddress == address(0)`, executes attacker-supplied `endpoint`/`callData`/`value` directly as the Emporium contract, blocking only two specific selectors: [6](#0-5) 

With `erc20TokenAddresses` empty, `payRelayFees` and the balance-change loop that follows also operate over zero-length arrays, so nothing is checked or accounted: [7](#0-6) 

### Impact Explanation
This breaks the equality the whole system is supposed to enforce: "every value movement Hinkal or an external action performs must be counted in the balance equation and authorized by a real spender/signer." Here, value can move (arbitrary `call{value}` from the Emporium contract, arbitrary external call side effects) with (a) no balance equation enforced in `Hinkal.sol` and (b) no authorization check in `verifyWallet` when `signerAddress == address(0)`, and (c) a circuit proof that does not actually prove ownership of any real UTXO for this variant. This matches the rule's "value moved by Hinkal or an external action but not counted in the balance equation" and "wallet op not authorised by the prover or signer" categories — it can be used to drain any ETH/token balance the Emporium contract holds (protocol fee balances or funds transiently parked there during multi-step/stateful Emporium flows) to an attacker-controlled address, or to perform unauthorized calls on Emporium's behalf.

### Likelihood Explanation
Reachable by any unprivileged EOA: it only requires generating a proof for the zero-token-count Emporium dimension and crafting an `EmporiumStack` with `signerAddress = address(0)` and attacker-chosen `ops`. No relayer/admin privilege, price oracle, or third-party defect is needed — the only outside dependency is being able to produce a valid Groth16 proof for the degenerate (`tokenCount = 0`) circuit instance, which the circuit's own structure makes trivially satisfiable since the authenticating constraints are skipped for that dimension.

### Recommendation
- Never allow the balance-conservation loop in `Hinkal.sol` (and the analogous logic in external actions) to be entirely skippable — require `erc20TokenAddresses.length > 0` for any action that can perform external calls, or otherwise enforce balance/value accounting independent of token-array length (e.g., check that Emporium's own ETH/token balances are unchanged when `erc20TokenAddresses` is empty).
- Do not allow `signerAddress == address(0)` (i.e., no signature check) to be combined with the "stateless" branch that performs unrestricted `call{value}`. Either forbid empty `erc20TokenAddresses` + `signerAddress == address(0)` combinations, or require that stateless calls with no signer are restricted to a safe allow-list of endpoints/selectors.
- For the Emporium-min circuit variant, either remove the unconditional `sigVerifier` constraint when `tokenCount == 0` (since it provides no real security there) or, better, prohibit deploying/using a `tokenCount == 0` variant for Emporium calls that also permit direct value-bearing calls.

### Proof of Concept
1. Attacker crafts a `Dimensions` with `tokenNumber = 0`, and a `CircomData` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: <target>, invokeWallet:false, value: <ETH held by Emporium>, callData: <arbitrary>}], maxFee:0, deadline:<future> }`.
2. Attacker generates a Groth16 proof for the `MainEVMCircuit(tokenCount=0, ...)` instantiation, self-choosing `spendingPublicKey`, `eddsaSignature`, `signedMessageHash`, and `messageSeed` so that `sigVerifier` and `message <== Poseidon(1)([messageSeed])` are self-consistently satisfied (no real UTXO/nullifier/root-hash binding exists for this dimension).
3. Attacker calls `Hinkal.transact()` with this proof and `CircomData`; `HinkalHelper.performHinkalChecks` accepts it (calldata-hash matches, dimensions match, `formInputEmporiumMin` produces the 3-signal public input), the proof verifies against the degenerate circuit, and `rootHashExists`/nullifier insertion trivially pass since the relevant arrays are empty.
4. `EmporiumUpgradeable.runAction()` is invoked; `verifyWallet` returns early (no signature check) since `signerAddress == address(0)`; the stateless branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract.
5. Back in `Hinkal.sol`, the balance-conservation loop (lines 96-147) has zero iterations since `erc20TokenAddresses` is empty, so no check ever fires to catch the value movement performed in step 4. [1](#0-0) [8](#0-7) [9](#0-8) [6](#0-5) [5](#0-4) 

**Note on uncertainty:** I could not locate the exact "public signal" declaration (e.g., a `component main {public [...]}` line, likely in a generated/wrapper circuit file for each `Dimensions` combination) that would give 100% certainty about exactly which signals are public for the `tokenCount = 0` instantiation, nor did I fully trace `_externalTransact`'s ETH-forwarding logic or confirm what balances the deployed `Emporium` contract typically holds in practice. These files may be excluded from the in-scope index (generated circuits) or simply outside what I could retrieve. The finding is based on the visible `MainEVMCircuit.circom` template logic and the Solidity code paths cited above, which are consistent and mutually reinforcing, but a full circuit-artifact review would be needed to close out any remaining doubt.
