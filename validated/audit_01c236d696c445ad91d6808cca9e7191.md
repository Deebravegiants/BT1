### Title
`createWithdrawalIntents` skips the `FeeExceedsAmountError` bounds check, allowing `amount - fee` to go negative - (File: `packages/intents-sdk/src/sdk.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount = withdrawalParams.amount - feeEstimation.amount` when `feeInclusive` is true, but — unlike `_estimateWithdrawalFee` — it never validates that `feeEstimation.amount < withdrawalParams.amount` before subtracting.

### Finding Description
In `_estimateWithdrawalFee`, before computing `actualAmount`, the SDK explicitly guards against the fee exceeding the amount: [1](#0-0) 

However, `createWithdrawalIntents` — the method that actually builds and signs the on-chain intents — performs the identical subtraction with **no equivalent check**: [2](#0-1) 

`feeEstimation` is a caller-supplied parameter (it is explicitly designed to be reusable/precomputed — see `ProcessWithdrawalArgs.feeEstimation` and `signAndSendWithdrawalIntent`, which pass through whatever `feeEstimation` object the integrator provides without re-deriving it from `estimateWithdrawalFee`). If an integrator (or any code path) calls `createWithdrawalIntents`/`signAndSendWithdrawalIntent` with a `feeEstimation.amount` that is greater than or equal to `withdrawalParams.amount` (e.g., a stale quote fetched earlier for a larger fee, or a quote for a different/more volatile asset), `actualAmount` becomes zero or a negative `bigint`. This negative/zero amount is then forwarded unchecked into `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents`, which build the `ft_withdraw` intent amount field via `actualAmount.toString()` (as seen in the equivalent bridge-level construction, e.g. `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`), producing an invalid/negative withdrawal amount embedded in a signed intent.

This is the direct analog of the Vyper `int128` bounds bug: an externally-influenced numeric value (`feeEstimation.amount`, akin to the unchecked external-call return value) is used in an arithmetic operation without validating it stays within the expected bound (`fee < amount`) in one code path, while a sibling code path (`_estimateWithdrawalFee`) proves the bound check is required and expected. The equality that breaks is "amount debited on-chain equals user-intended amount minus fee **exactly once, non-negative**" — here it can become negative/inconsistent, undermining the finalized signed intent.

### Impact Explanation
If `actualAmount` goes negative, the resulting `ft_withdraw`/`token_diff` intents encode an inconsistent or invalid on-chain amount. Depending on how the destination bridge/contract parses this value (BigInt-to-string serialization of a negative number is not valid NEP-141 `U128`), this can cause the signed intent to be rejected on-chain (funds stuck/undeliverable) or — more seriously if any downstream consumer coerces the signed negative-looking string differently — create a mismatch between the amount the user authorized and the amount embedded in the cryptographically signed payload. This matches the "signature bound to wrong amount / stuck withdrawal" class of High severity issues.

### Likelihood Explanation
This is only reachable when `createWithdrawalIntents` (or `signAndSendWithdrawalIntent`/`processWithdrawal` with an explicit `feeEstimation` argument) is called with a fee estimation that was not freshly derived from `estimateWithdrawalFee` for the same `withdrawalParams.amount` — a realistic integration pattern is caching/reusing a `FeeEstimation` across a slightly changed withdrawal amount, or race conditions between quote generation and user-adjusted amounts. It requires no malicious actor, only a normal integrator usage pattern the SDK's public API explicitly allows (both `feeEstimation` and `withdrawalParams` are independent, unvalidated inputs to `createWithdrawalIntents`).

### Recommendation
Add the same `FeeExceedsAmountError` guard used in `_estimateWithdrawalFee` to `createWithdrawalIntents` before computing `actualAmount`, ensuring `withdrawalParams.amount > feeEstimation.amount` whenever `feeInclusive` is true, regardless of entry point.

### Proof of Concept
```ts
const sdk = new IntentsSDK({ referral: "", intentSigner });

// Attacker/integrator supplies a feeEstimation.amount >= withdrawalParams.amount,
// bypassing _estimateWithdrawalFee entirely.
const feeEstimation = {
  amount: 5000n, // >= amount below
  quote: null,
  underlyingFees: { /* ... */ },
};

const intents = await sdk.createWithdrawalIntents({
  withdrawalParams: {
    assetId: "nep141:eth.bridge.near",
    amount: 1000n,
    destinationAddress: "0x...",
    feeInclusive: true,
  },
  feeEstimation,
});
// actualAmount = 1000n - 5000n = -4000n
// No FeeExceedsAmountError is thrown here, unlike estimateWithdrawalFee's path,
// and -4000n propagates into bridge.createWithdrawalIntents/ft_withdraw amount.
