### Title
Webhook `shop` attribution is unauthenticated, enabling cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#shop` returns the raw `X-Shopify-Shop-Domain` header value, but `HmacValidator.validate` only signs `@raw_body` via `to_signable_string`, never the shop-domain header. Since a single app's `api_secret_key` is shared across every merchant that installs the app, any developer who installs their own app instance can capture a genuinely-signed webhook and replay its body with an arbitrary `shop-domain` header, producing a request that passes HMAC validation while claiming to originate from a victim shop.

### Finding Description
The broken binding is: `HmacValidator.validate(request) == true` should imply `request.shop` is authentic, i.e. `signed_bytes ⊇ {raw_body, shop}`. In fact:

- `to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body: [2](#0-1) 
- `HmacValidator.validate_signature` computes HMAC over `verifiable_query.to_signable_string` (i.e. `@raw_body` only) and compares it to the received header: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the handler, without any additional binding check: [4](#0-3) 
- The gem's own `SessionUtils.offline_session_id(shop)` pattern (used elsewhere to derive a session key from an unauthenticated-looking `shop` string) demonstrates the shape of the intended, gem-documented usage that host apps follow to fetch a merchant's stored token by shop domain: [5](#0-4) 

Exploit flow: the app's `api_secret_key` is a single per-app secret shared by all merchant installations, not per-shop. An attacker installs the app on their own shop, registers their own HTTP webhook endpoint, and receives a webhook with body `B` and a valid `X-Shopify-Hmac-Sha256` computed over `B` with the app's secret. The attacker's server then forwards (or the attacker directly crafts) a POST to the app's webhook endpoint with the same body `B`, the same valid HMAC, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. `HmacValidator.validate` returns `true` because it only checks `B` against the secret — the shop header is outside the signed bytes — yet `request.shop` now reports the victim's domain. If the host app's handler (following the gem's documented pattern) calls something like `SessionUtils.offline_session_id(request.shop)` to fetch the stored access token for processing, it will act using the victim merchant's token against attacker-controlled payload data.

None of the existing guards catch this: `HmacValidator.validate` only proves the body is genuinely signed by *some* installation of the same app, not which shop; there is no `ShopValidator.sanitize!` call on `request.shop` in `Registry.process`; and there is no comparison between `request.shop` and any shop identifier embedded in the signed body.

### Impact Explanation
This is a cross-tenant authentication/attribution bypass: an attacker can make the host app process an attacker-controlled webhook payload while attributing it to (and using the stored access token of) an arbitrary victim shop, as long as they know or guess the victim's `.myshopify.com` domain (which is often public/guessable). This matches "Critical - cross-tenant access" since one tenant's forged request touches another tenant's data/credentials/processing.

### Likelihood Explanation
Preconditions are modest and match the given attacker model: the attacker needs only to be an unprivileged developer who can install the app on their own dev store (standard, always available) and can craft arbitrary HTTP requests to the app's webhook endpoint. No secrets, no privileged access, and no interaction with the victim are required. The exploit is trivially repeatable against any victim shop domain per request.

### Recommendation
Bind the shop domain into the signed material, or otherwise cross-verify it before trusting it. Concretely: reject/ignore `request.shop` for authorization decisions unless it is corroborated by information that is actually inside `@raw_body` (most webhook payloads embed shop-identifying fields), or require the host app/gem to compare `request.shop` against the shop associated with the OAuth-registered webhook subscription for that topic, and document/enforce this in `Webhooks::Registry.process`.

### Proof of Concept
```ruby
# test/shopify_api/webhooks/request_shop_spoof_test.rb
require "test_helper"

class RequestShopSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_secret_key: "attacker_shared_secret", ...)
  end

  def test_hmac_valid_even_with_spoofed_shop_domain
    body = '{"id": 1, "malicious": "payload"}'
    valid_hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "attacker_shared_secret", body)
    )

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "X-Shopify-Topic" => "orders/create",
        "X-Shopify-Hmac-Sha256" => valid_hmac,
        "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com",
        "X-Shopify-Api-Version" => "2023-10",
        "X-Shopify-Webhook-Id" => "123",
      },
    )

    # Signature validates using the attacker's own app-wide secret over raw_body only
    assert ShopifyAPI::Utils::HmacValidator.validate(request)

    # But shop is fully attacker-controlled/spoofed and not covered by the signature
    assert_equal "victim-shop.myshopify.com", request.shop
  end
end
```
This proves the equality `HmacValidator.validate(request) == true` holds while `request.shop` is an attacker-chosen value never included in `to_signable_string`, confirming the shop attribution is unsigned.
