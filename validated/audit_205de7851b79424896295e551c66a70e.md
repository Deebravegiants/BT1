### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by validating the HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values that the handler actually acts on come from HTTP headers that are excluded from the signed content, so they can be swapped freely on any request that carries a valid `(body, hmac)` pair.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `raw_body`) and then dispatches the handler using `request.shop`, i.e. the unauthenticated header value: [3](#0-2) 

`HmacValidator.validate` confirms this — it only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, and for the webhook `Request` that signable string is just the raw body: [4](#0-3) 

This breaks the equality the HMAC is supposed to enforce: `bytes verified (raw_body) == bytes acted on (raw_body + shop + topic + webhook_id)`. Any party who can obtain one valid `(raw_body, hmac)` pair for the app's shared `api_secret_key` — trivially done by installing the app on a store they control and triggering any subscribed webhook topic — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header pointing at a victim shop. `Registry.process` will accept it as authentic and hand the host application a `WebhookMetadata` object claiming to originate from the victim shop: [5](#0-4) 

Any host application that keys its business logic (order/customer sync, per-tenant state updates, uninstall handling, etc.) off `WebhookMetadata#shop` as returned by this gem is thereby exposed to cross-tenant data confusion, using only data the attacker legitimately received from their own installation.

### Impact Explanation
This crosses the tenant boundary the HMAC is meant to enforce: it lets an attacker who legitimately controls one shop's installation forge webhook deliveries that appear to originate from any other shop, without needing the app's `client_secret` or any privileged credential — they only need the identical body+HMAC bytes from their own, self-service install. This matches the "Critical - cross-tenant access" impact category, since the shop identity binding that downstream code relies on is not authenticated.

### Likelihood Explanation
Moderate-to-high. The attacker prerequisites are self-service: install the target app on a store they own (or a dev/trial store), trigger any webhook topic the app subscribes to, capture the raw body and `X-Shopify-Hmac-Sha256` value from the delivered request, then POST the identical body/HMAC pair to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header. No secret material, no interception of TLS, and no access to the victim's data is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content used for HMAC verification (or otherwise cryptographically bind them to the body), so that `HmacValidator.validate` fails if any of these header-derived identity fields are altered relative to what was actually signed by Shopify. At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are not covered by the HMAC and must not be trusted as tenant identifiers without additional verification (e.g., cross-checking against a known list of installed shops) by the host application.

### Proof of Concept
1. Install the target app (as an unprivileged user) on `attacker-shop.myshopify.com`; trigger a subscribed webhook topic (e.g. `orders/create`) to receive a legitimate webhook POST with raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`, per `HmacValidator.validate_signature`/`compute_signature`).
2. Replay the same request to the app's webhook endpoint but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally keep the same or a different `X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers (`lib/shopify_api/webhooks/request.rb:45-63`); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `raw_body` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `Request#to_signable_string` at line 36-38) — validation succeeds because `B`/`H` are unchanged.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`) with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
