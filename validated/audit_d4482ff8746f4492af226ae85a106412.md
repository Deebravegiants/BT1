### Title
Flash-position callbacks can apply oracle governance behind stale cached prices - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
Medium severity. `flash_position` permits a caller-controlled contract callback after debt is minted and before final solvency checks, while the controller continues using prices fetched before that callback. [1](#0-0) 

### Finding Description
`process_flash_position` accepts any deployed WASM receiver other than the controller and pool. [2](#0-1) 

Before invoking the receiver, the controller calls `prefetch_strategy_prices`, which populates the invocation-local `Context::token_prices` map. [3](#0-2) [4](#0-3) 

Later risk evaluation uses `cached_price`, which returns the pre-callback `PriceFeedRaw` without querying the aggregator again. [5](#0-4) 

The callback is deliberately executed while the flash guard is set. [6](#0-5) 

That guard is only a temporary controller-storage flag and does not prevent the receiver from calling the separate governance contract. [7](#0-6) 

Governance `execute` accepts `executor = None`, allowing any address or contract to execute an already-ready scheduled operation. [8](#0-7) 

`execute` verifies the scheduled operation, invokes its target, and clears the scheduled state only after the invocation returns. [9](#0-8) 

A scheduled `AdminOperation::ConfigureAssetOracle` resolves to `price_aggregator.set_oracle(key, resolved_oracle)`. [10](#0-9) 

Consequently, the callback can atomically replace a collateral oracle after the controller has fetched the old price but before `strategy_finalize` performs collateral coverage, health-factor, and collateral-floor checks. [11](#0-10) [12](#0-11) [13](#0-12) 

This is the same unsafe ordering as the reported bug class: the protocol retains a protected snapshot while synchronously allowing an external callback to mutate the dependency on which final validation relies.

### Impact Explanation
An attacker can time a ready oracle reconfiguration that lowers the true valuation of the declared collateral.

The receiver first obtains the minted debt tokens through `mint_and_forward`, then applies the governance operation and returns inexpensive collateral to the controller. [14](#0-13) 

The controller measures the token amount correctly, but prices it with the stale pre-callback oracle result, so an account that is insolvent under the newly activated oracle can pass the final health checks. [5](#0-4) 

The attacker can retain the forwarded borrowed assets and abandon the undercollateralized account, leaving lenders with bad debt and potentially causing protocol insolvency.

### Likelihood Explanation
Exploitation requires a suitable oracle operation, such as `ConfigureAssetOracle`, to already be scheduled and in the `Ready` state; an unprivileged attacker cannot create that owner-gated proposal alone. [15](#0-14) 

Once ready, however, the attacker can execute it permissionlessly from inside their own flash-position callback by passing `executor = None`. [8](#0-7) 

The receiver needs only implement `execute_flash_position`, invoke governance with the scheduled operation's exact target, function, resolved arguments, predecessor, and salt, and then transfer the declared collateral amount to the controller. [16](#0-15) 

### Recommendation
Re-query all risk-relevant price feeds after the callback and before `strategy_finalize`, or compare a post-callback oracle/configuration epoch against the pre-callback epoch and revert on any change.

At minimum, `Context::cached_price` entries used for post-callback solvency must be invalidated when the aggregator configuration changes during the guarded callback window.

The same ordering should be reviewed for router-mediated strategies, where an external route execution can similarly occur between price prefetch and final risk checks. [17](#0-16) 

### Proof of Concept
1. Assume governance has a ready `ConfigureAssetOracle` operation that changes collateral token `C` from the current higher-priced oracle configuration to a lower-priced configuration. [10](#0-9) 
2. The attacker deploys a receiver implementing `execute_flash_position` and calls `controller.flash_position(caller=attacker, account_id=0, spoke_id=S, mode=Multiply, debt=D, amount=A, receiver=receiver, data=plan, collaterals=[(C, min_c)], refund_assets=[])`. [18](#0-17) 
3. The controller prefetches the old prices for `D` and `C`, mints `A` of debt to itself, forwards the measured amount to the receiver, and invokes the callback. [19](#0-18) 
4. Inside `execute_flash_position`, the receiver calls `governance.execute(None, price_aggregator, "set_oracle", [PriceKey::Token(C), resolved_oracle], zero_predecessor, operation_salt)`. [9](#0-8) 
5. The receiver then transfers `min_c` units of `C` to the controller and returns normally.
6. The controller deposits the measured `C`, but evaluates final health using the stale higher `C` price still present in `Context::token_prices`. [5](#0-4) 
7. The transaction commits with the receiver retaining borrowed asset `D`, while the new oracle configuration makes the created account undercollateralized, leaving a liquidation shortfall for suppliers.

/// Runs `f` with the flash-loan flag set; preserves an already-active outer guard.
pub(crate) fn with_flash_guard<T>(env: &Env, f: impl FnOnce() -> T) -> T {
    let prev = is_flash_loan_ongoing(env);
    set_flash_loan_ongoing(env, true);
    let out = f();
    if !prev {
        set_flash_loan_ongoing(env, false);
    }
