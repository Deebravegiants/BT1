### Title
POA Bridge withdrawal status is matched by `assetId` only, causing status/tx-hash misreport for multiple same-asset withdrawals in one intent - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts)

### Summary
`PoaBridge.describeWithdrawal` and `waitForWithdrawalCompletion` resolve the on-chain withdrawal status for a specific withdrawal by looking up `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching purely on `assetId` (i.e. `near_token_id`) and ignoring the `index`/amount/destination address that uniquely identifies *which* withdrawal within a NEAR transaction is being queried.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  returns the *first* withdrawal record whose `near_token_id` matches `nep141:${assetId}` — it does not disambiguate by index, amount, or destination address. The same pattern is used in `PoaBridge.describeWithdrawal` at [2](#0-1)  via the same `findMatchingWithdrawal` helper, which is explicitly documented as matching "by assetId instead of index" because "Response list is unsorted."

The code comment on `findMatchingWithdrawal` itself acknowledges the gap: [3](#0-2)  states "Currently only matches by assetId (near_token_id). This means multiple withdrawals of the same token in a single transaction are not supported." This breaks the equality that the withdrawal status/tx-hash reported for withdrawal index N corresponds to the on-chain outcome of withdrawal N specifically — instead it can report the completion status/hash of a different withdrawal of the same asset within the same batch.

### Impact Explanation
If a single NEAR intents transaction contains two or more withdrawals of the same underlying asset (e.g. two USDC withdrawals to different destination addresses in one `ft_withdraw` batch, which `createWithdrawalIdentifiers` in [4](#0-3)  explicitly supports by assigning per-bridge `index` values), `PoaBridge.describeWithdrawal` / `waitForWithdrawalCompletion` can report withdrawal #2's status/`transfer_tx_hash` for withdrawal #1's query (or vice-versa), because both share the same `assetId` and the lookup only keys off `assetId`. An integrator polling per-withdrawal completion (via `watchWithdrawal` in `withdrawal-watcher.ts`) could be told withdrawal #1 is "completed" with a tx hash that actually belongs to withdrawal #2, while the real withdrawal #1 is still pending or failed. This is a status/hash misreport that can cause an integrator to credit or mark complete the wrong withdrawal, matching the High-impact category ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires no malicious actor — it is triggered by an ordinary user/integrator action: withdrawing the same token to two different destinations (or amounts) within a single signed intent/transaction, which is a normal, supported use case of the SDK (multiple `WithdrawalParams` per transaction, tracked by `index`). The bug is deterministic whenever the POA bridge returns more than one withdrawal record for the same `near_token_id` in a batch, which the code's own inline comment confirms is an unhandled scenario.

### Recommendation
Update `findMatchingWithdrawal` (and its usage in `PoaBridge.describeWithdrawal`) to disambiguate withdrawals of the same asset within a batch — e.g., by additionally matching on `amount`, `destinationAddress`, and/or preserving order via a stable sort combined with `index`, rather than returning the first `assetId` match. Until fixed, the SDK should surface an explicit error/limitation when multiple same-asset withdrawals are present in one call, rather than silently returning a possibly-wrong status.

### Proof of Concept
1. Submit a single NEAR intents transaction containing two `ft_withdraw` intents for the same token (e.g. `usdc.omft.near`) to two different destination addresses A and B — creating withdrawal identifiers with `index: 0` and `index: 1` via `createWithdrawalIdentifiers` (`withdrawal-watcher.ts`).
2. Call `sdk`'s withdrawal-completion tracking for `index: 0` and `index: 1` separately, each invoking `PoaBridge.describeWithdrawal` / `waitForWithdrawalCompletion` with the same `assetId`.
3. Because the POA Bridge API response list is unsorted and `findMatchingWithdrawal` matches solely on `assetId`, both calls can resolve to the same underlying withdrawal record — e.g., both report `status: "completed"` with the `transfer_tx_hash` belonging to only one of the two withdrawals.
4. An integrator relying on this per-index status to confirm/credit withdrawal B may incorrectly conclude it completed (using A's hash) while B is actually still pending, or double-count a single completed transfer against two logical withdrawals.

Note: I was unable to fully trace how the SDK's higher-level `waitForWithdrawalCompletion`/multi-withdrawal-tracking APIs consume `describeWithdrawal` per-index results end-to-end (e.g., whether any caller adds extra disambiguation before this point), since I could not inspect the complete call chain within the given iteration budget. The root-cause defect in the matching function itself and its documented limitation, however, are directly confirmed in the cited files.

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
