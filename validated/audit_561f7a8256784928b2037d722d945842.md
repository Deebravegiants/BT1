### Title
Webhook shop identity is unauthenticated and can be spoofed independently of the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches to the app's handler using a `shop` value read from an HTTP header that is never covered by that HMAC. Any party capable of producing one validly-signed webhook payload (e.g. a merchant who has installed the app and receives their own genuine webhooks) can replay that body+HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process the payload as though it originated from a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies authenticity like this: [1](#0-0) 

The HMAC check is `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` — the shop identity is not part of the signed material: [3](#0-2) 

Meanwhile `shop` is read from a separate, unauthenticated HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`): [4](#0-3) 

That unverified value is what gets handed to the app's handler as the tenant identity for the event: [5](#0-4) 

Contrast this with the OAuth query path in the same library, where `shop` *is* included in the HMAC-signed string, correctly binding tenant identity to the signature: [6](#0-5) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop authenticated by HMAC` ≠ `shop used by handler (request.shop, from header)`.

Because a single app-level `api_secret_key` is shared across all shops that install the app, a valid `(raw_body, hmac)` pair generated from one shop's genuine webhook delivery remains cryptographically valid for that body regardless of which `shop-domain` header accompanies it. An attacker who controls (or has installed) the app on any shop can capture one authentic webhook delivery, then replay the identical body/HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will pass because it never inspects the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant data/action confusion: any handler logic that trusts `WebhookMetadata#shop` (or `Request#shop`) to select which merchant's session, database row, or business logic to act on can be tricked into applying a payload's contents to the wrong tenant, using nothing but a body/signature pair the attacker legitimately received for their own shop. This falls under the Critical "cross-tenant access" impact category since the gem's own webhook-processing API provides no protection against shop spoofing beyond body integrity.

### Likelihood Explanation
Likelihood is high for any app that installs webhooks for more than one shop (the common case for a public/multi-tenant Shopify app): an attacker only needs to install the app once, capture one of their own valid webhook deliveries (trivial, since it's delivered to their own endpoint), and resend it with a modified header. No access token, secret, or privileged account is required — only participation as an ordinary merchant using the app, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity into the value that is actually authenticated. Options: 
1. Prior to invoking the handler, cross-check `request.shop` against the shop associated with the webhook subscription/session expected for that endpoint (i.e., look up the session by the resource ids in the body rather than trusting the header blindly), or 
2. Include the `shop-domain` header (and other identity-bearing headers such as `webhook-id`) in the value validated by `HmacValidator`, analogous to how `AuthQuery#to_signable_string` binds `shop` into its OAuth HMAC computation.

### Proof of Concept
1. App has two shops installed: `attacker.myshopify.com` and `victim.myshopify.com`, sharing the same `api_secret_key`.
2. Shopify delivers a genuine webhook to the app for `attacker.myshopify.com`:
   - headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-for-body>`
   - body: `{"id": 123, ...}`
3. Attacker captures this exact `(body, hmac)` pair (it was delivered to their own endpoint/app instance) and resends it to the app's webhook controller, changing only the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only (`Request#to_signable_string`) and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: {"id":123,...}, ...)`, as shown in: [7](#0-6) 
5. Any handler that keys tenant-specific behavior off `data.shop` now performs that action attributed to `victim.myshopify.com` using attacker-supplied body content.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
