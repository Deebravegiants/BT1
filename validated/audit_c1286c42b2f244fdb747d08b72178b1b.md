### Title
Attacker-controlled overcapture QR wavelength parameter triggers a panic/DoS via invalid octal-to-3-bit assumption - (File: src/plans/biometric_capture/overcapture.rs)

### Finding Description
The signup-extension QR code's `parameters` field is fully attacker-controlled: `qr_scan::user::Data::from_signup_extension` copies the raw regex-captured string into `SignupExtensionConfig.parameters` without further validation [1](#0-0) . When the mode is `Overcapture`, `overcapture::Plan::from` splits this string on `':'` and feeds the wavelength portion into `parse_u8_octal`, defined as `u8::from_str_radix(src, 8).unwrap_or(default)` [2](#0-1) [3](#0-2) .

`u8::from_str_radix(_, 8)` only rejects strings containing digits outside `0-7`; it does not restrict the *value* of the parsed number to a single octal digit (0-7). A multi-digit octal string like `"10"` (decimal 8), `"20"` (decimal 16), up to `"377"` (decimal 255) all parse successfully to `u8` values ≥ 8. This value is then passed into `Configuration::new` → `Configuration::parse_wavelength_configuration`, which assumes the value fits in exactly 3 bits:

```rust
let binary_repr = format!("{configuration_value:0>3b}");
assert_eq!(binary_repr.chars().count(), 3, "Overcapture wavelength parameter needs to be octal (<=3 bit)!");
``` [4](#0-3) 

For any `configuration_value >= 8`, `format!("{:0>3b}", value)` produces 4 or more characters (e.g. `8` → `"1000"`), so the `assert_eq!` fails and the thread panics with the message `"Overcapture wavelength parameter needs to be octal (<=3 bit)!"`. There is no validation earlier in the pipeline (QR regex, `from_signup_extension`, or `parse_u8_octal`) that rejects values above 7, and no `catch_unwind` wraps this conversion path.

### Impact Explanation
This is a reachable, unauthenticated panic (Denial of Service) triggerable purely by presenting a crafted signup-extension QR code containing an out-of-range octal wavelength parameter (e.g. `"10"`, decimal 8, or up to `"377"`) for the `Overcapture` signup mode. The panic occurs inside `Configuration::parse_wavelength_configuration`, called synchronously from `Plan::from` during construction of the overcapture extension plan for a signup session. Because this runs on the orb's control/signup thread with no panic isolation visible in this path, it crashes the current signup flow and likely the `orb-core` process, disrupting signup availability for legitimate users until the process is restarted. This matches a service-disruption / signup-availability bounty impact rather than a biometric compromise.

### Likelihood Explanation
- Requires the `internal-data-acquisition` feature to be compiled in and the `Overcapture` `SignupMode` reachable via `QR_CODE_SIGNUP_EXTENSION` regex matching [5](#0-4) .
- No operator privileges, keys, or MCU access are needed — only the ability to present a QR code to the orb's camera during signup, which is within the stated unprivileged-attacker threat model.
- The trigger is deterministic and trivially reproducible: any octal string parsing to a `u8 >= 8` (e.g. `"10"`) causes the panic every time.

### Recommendation
In `parse_u8_octal`/`Configuration::new`, explicitly validate that the parsed value is within `0..=7` (reject or clamp otherwise) instead of only checking that `from_str_radix` succeeds. Replace the `assert_eq!` inside `parse_wavelength_configuration` (which panics on attacker input) with a graceful fallback (e.g., default configuration) or return a `Result` that is handled without crashing the process, so malformed/out-of-range QR-supplied parameters cannot induce a panic.

### Proof of Concept
Unit test to add to `src/plans/biometric_capture/overcapture.rs` tests module (or standalone):
```rust
#[test]
#[should_panic(expected = "Overcapture wavelength parameter needs to be octal (<=3 bit)!")]
fn test_overcapture_wavelength_out_of_range_octal_panics() {
    // "10" is valid octal digits but parses to decimal 8, exceeding the 3-bit assumption
    let value = parse_u8_octal("10", 1);
    assert_eq!(value, 8);
    let _ = Configuration::parse_wavelength_configuration(value); // panics here
}
```
Expected result: the assertion inside `parse_wavelength_configuration` panics, demonstrating that a QR-supplied string such as `userid:<uuid>:1::5:10::` (mode `5` = Overcapture, parameter `10`) crashes the overcapture extension construction path during signup.
