## Finding [1](#0-0) [2](#0-1) 

### Title
`SessionUtils.cookie_session_id`/`current_session_id` trust a deterministic, unsigned client-supplied value as the session-store key - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
`session_id_from_shopify_id_token` itself is safe: it only derives `"#{shop}_#{sub}"` from a JWT that `Auth::JwtPayload.new` verifies with HS256 against `Context.api_secret_key` and checks `aud == Context.api_key`, so an attacker cannot mint an arbitrary id token. The real break is the sibling `cookie_session_id` path inside the same class and its call site in `current_session_id`, which returns the raw `Cookie` value as the trusted session id with no MAC, no signature, and no shop binding — and this path is reachable for embedded apps too whenever the request simply omits the id token.

### Finding Description
The invariant that should hold is: `session_id == f(secret_proof_of_identity)`, i.e. the string used to key session storage must only be producible by someone who already holds a cryptographic proof of the shop/user's identity (a Shopify-signed JWT, or a server-issued unguessable token). Instead:

- `jwt_session_id(shop, user_id)` returns `"#{shop}_#{user_id}"` [3](#0-2)  and `offline_session_id(shop)` returns `"offline_#{shop}"` [4](#0-3)  — both fully deterministic from public information (the `myshopify.com` domain, and a user id that is often guessable/enumerable).
- `cookie_session_id(cookies)` just does `cookies[SESSION_COOKIE_NAME]` [5](#0-4)  — it returns whatever value is in the `Cookie` header verbatim, with no MAC/signature check.
- `current_session_id` calls this cookie path in two situations: always for non-embedded apps, and — critically — for **embedded** apps whenever the caller doesn't supply a `shopify_id_token` [6](#0-5) . Nothing in this method rejects a request that has no `Authorization`/id-token; it silently falls back to the cookie instead of failing closed, even though the gem's own docs state cookie-based auth "is not supported for embedded apps."

Because the attacker is assumed to be able to send raw HTTP requests (not constrained to a real browser), they can send `Cookie: shopify_app_session=offline_<shop>.myshopify.com` (or `<shop>_<user_id>` for online) with no `Authorization` header at all. `current_session_id` returns that string unchanged as "the session id." If the host's session storage is naively keyed by this id (which is exactly how the documented `Session.from` / `shopify_app` integration works — the `id` is literally `"#{shop}_#{associated_user.id}"` / `"offline_#{shop}"`, see `lib/shopify_api/auth/session.rb` lines 107-140), the lookup returns the real, previously-persisted `Session` (with its `access_token`) for a shop the attacker never authenticated against.

None of the mitigations listed in the audit's "Validate" checklist intervene here: `HmacValidator.validate` and the OAuth `state` comparison only protect the OAuth callback step (`lib/shopify_api/auth/oauth.rb` lines 60-71), not this later per-request session lookup; `JwtPayload`'s `aud`/signature check only applies to the JWT branch, which the attacker simply avoids by not sending a token; `Context.embedded?` only chooses which branch runs, it doesn't block the cookie fallback. `Session#covers?`/`expired?` operate on whatever `Session` object storage hands back — they cannot detect that the *key* used to fetch it was forged, because by the time those checks run, the attacker's untrusted string has already become the trusted id.

### Impact Explanation
An attacker who can guess or already knows a target's `myshopify.com` domain (public) and, for online sessions, a user id, can construct the exact string this gem would have produced from a legitimate signed JWT, and inject it directly as a cookie on their own raw HTTP request — no secret, no valid JWT, no CSRF needed. If the host's session store resolves that string to a real session (the pattern the gem's own `Session.from` encourages), the attacker's request is treated as an authenticated request for the victim shop, exposing that shop's `access_token` and letting the attacker read/mutate the victim's data. This is repeatable against any shop/user whose id can be guessed and is not limited to one victim - it's a systemic cross-tenant break, matching Critical - cross-tenant access.

### Likelihood Explanation
Preconditions: the host app must key its session storage by the id string produced by this gem (the common/documented pattern) and must actually read incoming cookies via `SessionUtils.current_session_id` (or equivalent) without imposing an independent cryptographic binding of its own. Attacker cost is trivial — one crafted HTTP request with a guessed `Cookie` header, no credentials required. The `offline_#{shop}` case needs no secret at all beyond the shop domain; the online case additionally needs a user id, which is often enumerable (sequential integers) or learnable via the attacker's own trial installs/staff access patterns.

### Recommendation
Do not use a deterministic, attacker-computable string as the sole session-lookup key trusted from an unauthenticated cookie. Either (a) require `current_session_id` to fail closed for embedded apps when no id token is present instead of silently falling back to the cookie, and/or (b) bind the cookie value to a cryptographically random, unguessable session identifier (or HMAC the deterministic id with a server secret) so that knowledge of `shop`/`user_id` alone is insufficient, and verify that MAC in `cookie_session_id` before returning it.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_embedded_app_falls_back_to_unverified_cookie_without_authorization_header
  ShopifyAPI::Context.stubs(:embedded?).returns(true)

  # Attacker never presents an id token (no Authorization header, no JWT param),
  # but guesses the deterministic id format an online JWT session would produce.
  forged_session_id = "victim-shop.myshopify.com_12345"
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

  # EXPECTED (secure) behavior: embedded app should reject a request with
  # no Authorization header rather than trusting an unsigned cookie.
  assert_raises(ShopifyAPI::Errors::CookieNotFoundError) do
    ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)
  end

  # ACTUAL behavior: the forged cookie value is returned verbatim as the
  # trusted session id, identical to what a real signed JWT would mint.
  actual = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)
  assert_equal(forged_session_id, actual)
end
```
This demonstrates that `cookie_session_id`/`current_session_id` return `"victim-shop.myshopify.com_12345"` — the exact key `jwt_session_id` would have derived from a genuine, HMAC-verified JWT for that shop/user — despite the attacker never possessing `api_secret_key` or a valid signature, confirming the binding `session_id == proof_of_identity` does not hold in this branch.

        end
