## Title
Improper CORS origin-suffix matching allows subdomain-impersonation bypass of the allowlist - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in the Gateway's HTTP server implements wildcard CORS origin matching (`*.example.com`) using an unanchored `strings.HasSuffix(originHost, allowedHost)` check after stripping the `*.` prefix. Because this suffix check doesn't verify a label/dot boundary, a hostname such as `notexample.com` incorrectly satisfies the wildcard rule intended for legitimate subdomains of `example.com`, letting an attacker-registered look-alike domain receive `Access-Control-Allow-Origin` trust it should not have.

## Finding Description
The vulnerable logic is confirmed in the code:

```go
// check for wildcard host match (e.g., *.remix.com)
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [1](#0-0) 

This function is invoked directly from `handleRequest`, the single entry point for all Gateway HTTP traffic, and its return value is used to reflect the client-supplied `Origin` header back into the `Access-Control-Allow-Origin` response header:

```go
if s.config.CORSEnabled {
    origin := r.Header.Get("Origin")
    if s.isAllowedOrigin(origin) {
        w.Header().Set("Access-Control-Allow-Origin", origin)
        ...
``` [2](#0-1) 

`strings.HasSuffix` performs a raw textual suffix comparison with no boundary check, so `HasSuffix("notexample.com", "example.com")` evaluates to `true` even though `notexample.com` is an entirely unrelated domain, not a subdomain of `example.com`. Existing unit tests only exercise correctly-anchored subdomains (`remix.ethereum.org`, `another.valid.domain.com`, `example.gov`) and do not cover the boundary-less collision case, confirming the gap is untested: [3](#0-2) 

The scheme and port checks preceding this logic do not mitigate the flaw, since they only narrow scheme/port equality, not host boundary correctness.

## Impact Explanation
When an operator enables CORS and configures a wildcard allowed origin (a supported, documented feature), any attacker who registers a domain that merely ends with the configured suffix string (without a preceding dot) can have their origin reflected into `Access-Control-Allow-Origin`. A browser visiting the attacker's page can then issue cross-origin requests to the Gateway and read responses that should be restricted to the legitimate allowlisted domain family, i.e., gateway request/response impersonation and cross-user response exposure to an unauthorized origin (CWE-346/CWE-384 class). This is a genuine logic bug in Chainlink's own CORS enforcement code, not a misconfiguration of unrelated systems — the wildcard matching feature itself is implemented incorrectly.

## Likelihood Explanation
Exploitation requires only that `CORSEnabled` is true and a wildcard entry is present in `CORSAllowedOrigins` — a supported gateway configuration, not an unsafe default. Given that precondition, any unprivileged external attacker can trivially register a cheap look-alike domain (e.g., `notexample.com`) and serve a page from it; no credentials, node access, or victim interaction beyond visiting the attacker's page are required. The bug is deterministic and repeatable given the flawed string comparison.

## Recommendation
Anchor the wildcard suffix match to a label boundary, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
This preserves legitimate subdomain matching while rejecting unrelated domains that merely share a trailing substring.

## Proof of Concept
1. Configure Gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.example.com"]`.
2. Send an HTTP POST to the gateway endpoint with header `Origin: https://notexample.com`.
3. `isAllowedOrigin` strips `*.` to get `allowedHost = "example.com"` and evaluates `strings.HasSuffix("notexample.com", "example.com")`, returning `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://notexample.com`, confirming the origin-suffix bypass.
5. A Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` [4](#0-3)  but using origin `https://notexample.com` against allowed origin `https://*.example.com` would demonstrate the incorrect `true` result and reflected header.
