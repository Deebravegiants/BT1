### Title
Unsafe ERC20 transfer handling in Tron `IntentGatewayV2.withdraw()`/`onGetResponse`/`SweepDust` checks only call success, not the returned boolean — silent transfer failures corrupt escrow accounting - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports and uses `SafeERC20` (`using SafeERC20 for IERC20;`, and `safeTransferFrom` in `placeOrder`), but the escrow-release path (`withdraw()`), the GET-response refund path (`onGetResponse`), and the `SweepDust` handler perform raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the low-level `success` flag, never decoding/validating the ERC20 boolean return value.

### Finding Description
In `withdraw()`: [1](#0-0) 
tokens are sent with a raw `.call`, and `_orders[body.commitment][token] -= amount` is decremented (escrow accounting finalized) as soon as `success == true`. The same pattern repeats for transaction fees: [2](#0-1) 
and for `SweepDust`: [3](#0-2) 

For an ERC20/TRC20 token that returns `false` instead of reverting on a failed transfer (e.g. due to a paused/blacklisted recipient, or any non-compliant token that follows the "return bool" convention without reverting), the low-level `call` still succeeds (`success == true`) because the call itself did not revert — only the encoded return data (`false`) signals the failure. Since the code never decodes that return data (unlike `SafeERC20.safeTransfer`, which explicitly checks `returndata.length == 0 || abi.decode(returndata, (bool))`), the failure is invisible to the contract.

Because `_filled[body.commitment] = beneficiary` is set unconditionally at the top of `withdraw()` and escrow is decremented after the no-op "successful" call, the order is marked filled/refunded and its escrow balance is wiped even though the beneficiary never received the tokens.

### Impact Explanation
This is a fund-freezing/loss bug reachable through the normal cross-chain settlement flow: `withdraw()` is invoked from `onAccept` (ISMP POST delivery after a relayed proof settles a `RedeemEscrow`/refund request) and from `onGetResponse` (after a relayed GET response proof for cancellation). Both are triggered by a relayer submitting a proof for a message that ultimately stems from a solver filling or a user cancelling an order — an unprivileged path. If the escrowed token misbehaves this way, the beneficiary (solver or user) permanently loses the escrowed funds: the order is marked filled/refunded (so it can never be retried) and the escrow record is zeroed, while the tokens remain stuck in the `IntentGatewayV2` contract with no accounting path left to recover them. This is a permanent freezing/loss of user funds impacting the intents escrow held by this contract.

### Likelihood Explanation
Likelihood depends on a configured input/output/fee token behaving as "return `false` rather than revert" on failure. This is a known ERC20 edge case (and the same underlying token-compatibility rationale that apparently motivated using raw `.call` here instead of `SafeERC20.safeTransfer`, ironically dropping the return-value check that `SafeERC20` provides). Given the contract is deployed for Tron/TRC20 tokens, where non-standard return-value semantics are common, the likelihood of encountering such a token in a supported input/output/fee-token list is realistic, and the same contract already handles `SafeERC20.safeTransferFrom` (which does check returns) for the inbound leg, making the omission on the outbound `withdraw`/`SweepDust`/`onGetResponse` legs an inconsistency rather than an intentional design choice.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()`, the fee payout, and `SweepDust` with `IERC20(token).safeTransfer(beneficiary, amount)` (the contract already has `using SafeERC20 for IERC20;` in scope), so that both call-level reverts and false boolean returns are treated as failures before escrow state is mutated or the order is marked filled.

### Proof of Concept
1. Register/support an ERC20-like token that returns `false` (does not revert) on a failed `transfer`, e.g. when the recipient is blacklisted or a global pause is set.
2. A user places an order with this token as input; escrow is credited via `placeOrder` using `safeTransferFrom` (correctly reverts if failed, so escrow gets funded).
3. A solver fills the order; the settlement message reaches the source chain, `onAccept` decodes a `WithdrawalRequest` and calls `withdraw()`.
4. If the token's `transfer(beneficiary, amount)` call returns `false` (e.g., beneficiary temporarily blacklisted) instead of reverting, `token.call(...)` returns `success == true` with `abi.decode(data,(bool)) == false`, which is never checked.
5. `withdraw()` proceeds to decrement `_orders[commitment][token]` and mark `_filled[commitment] = beneficiary`, emitting `EscrowReleased`, even though the beneficiary received nothing.
6. The escrow is now zero and the order finalized — the tokens are permanently stuck in `IntentGatewayV2` with no order state left to trigger a retry or refund.
