### Title
Webhook shop-domain header is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) exclusively from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while `ShopifyAPI::Utils::HmacValidator` (invoked from `ShopifyAPI::Webhooks::Registry.process`) verifies the HMAC only over the raw request body. The shop header is never part of the signed material, so an attacker who possesses one authentic, validly-signed webhook can replay it with a forged shop header and have it processed under a different tenant's identity.

### Finding Description
`Request#shop` reads the shop identity straight from request headers: [1](#0-0) 

The HMAC that authenticates the webhook is computed over `to_signable_string`, which returns only the raw body — the shop header is not included: [2](#0-1) 

`Registry.process` validates that HMAC against the body and, once it passes, forwards `request.shop` unmodified to the app's handler as the authoritative tenant identity: [3](#0-2) 

`HmacValidator.validate_signature` only ever hashes `verifiable_query.to_signable_string` (the body) against the app's shared `api_secret_key`; the shop header plays no role in the comparison: [4](#0-3) 

Because `api_secret_key` is a single secret shared by the app across *all* installing shops, any webhook body signed for shop A carries a signature that is equally valid regardless of which shop header accompanies it. The identity binding the library implicitly promises to the host app — "the HMAC-verified request came from `request.shop`" — does not actually hold, because:

`HMAC-verified(body) == true` does **not** imply `shop_header == originating_shop`.

The equality the code needs, but never establishes, is:
`shop bound by HMAC == shop delivered to handler (request.shop)`

### Impact Explanation
A merchant who has legitimately installed the app (and can therefore observe genuine webhook deliveries — valid body + valid HMAC — for their own shop) can capture one such webhook and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to point at a different, victim shop that also uses the same app. Because `Registry.process` only re-verifies the HMAC of the (unchanged) body, the forged request passes validation, and `WebhookMetadata.shop` handed to the app's handler is the attacker-controlled header value. Any app logic that uses this `shop` value to select which tenant's records to create/update/delete (e.g., order sync, GDPR/redact handlers, uninstall cleanup) will act on the victim's tenant using attacker-supplied body content — a cross-tenant data integrity/confidentiality break.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on their own shop (an ordinary, unprivileged action for any merchant) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — both trivially available to any internet user who becomes an app user. No access token, `client_secret`, or leaked credential is required.

### Recommendation
Bind the shop identity to the signed payload instead of trusting the header in isolation: e.g. verify that `request.shop` corresponds to a shop for which the app currently holds an active session/installation, and/or require the topic-specific body payload's own shop-identifying fields to match the header before dispatching to the handler. At minimum, document prominently that `request.shop` is not authenticated by the HMAC and must be cross-checked by the host application against its own installation records before being trusted as a tenant identifier.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with an empty/generic body `{}`.
2. Attacker captures the genuine delivery: body `{}`, header `x-shopify-hmac-sha256: <valid HMAC of "{}" under the app's api_secret_key>`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), `Utils::HmacValidator.validate` succeeds (body/HMAC pair is genuinely valid), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` — as shown at [5](#0-4) , even though the request never originated from Shopify on behalf of `victim-shop`.
