### Title
Malicious ERC20 as an order input permanently freezes a solver's entire escrowed bundle after cross-chain fill - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`ExtrinsicIntents` lets any user place an order with an arbitrary set of input tokens (`order.inputs`), with no allowlist. On a cross-chain fill, the solver sends real output tokens to the order's beneficiary *before* the escrowed inputs are released, and release only happens later via a `RedeemEscrow` message processed by `_withdraw`. Because `_withdraw` iterates over all escrowed tokens for a commitment in one loop and reverts the whole call if any single token's `transfer` reverts, a user can bundle one legitimate valuable input token with one adversarial ERC20 that can be made to permanently revert transfers (e.g., a pausable/blacklist token the order-creator controls). Once the solver has filled the order and delivered real assets, the order-creator flips the malicious token to always revert, which permanently blocks `withdraw()` from ever succeeding — freezing the solver's entire escrowed inputs, including the legitimate token bundled alongside the malicious one.

### Finding Description
`placeOrder` accepts arbitrary ERC20 addresses for `order.inputs` with no whitelist or safety check, only recording escrow amounts: [1](#0-0) 

On a cross-chain fill, `_fillCrossChain` transfers the solver's real output tokens directly to the beneficiary immediately, *before* the escrow is ever released to the solver: [2](#0-1) 

The `RedeemEscrow` message dispatched here is later delivered on the source chain and processed by `_withdraw`, which loops over every escrowed token for the commitment and performs a `safeTransfer` for each one, with no isolation between tokens — if any single transfer reverts, the whole function (and hence `onAccept`) reverts: [3](#0-2) 

Delivery failures are not fatal to the protocol state machine but are fatal to the order: `EvmHost.dispatchIncoming` swallows the revert, deletes the request receipt, and returns, leaving the message retryable indefinitely: [4](#0-3) 

Because the failing token's owner can choose to make transfers permanently revert (rather than transiently), retrying delivery is pointless — `_withdraw` will keep reverting forever, so the entire escrowed bundle (the malicious token plus any legitimate tokens escrowed in the same order) is permanently unrecoverable. There is no per-token try/catch or partial-success path in `_withdraw`, and no token allowlist anywhere in `IntentGatewayV2`/`IntentsBase`/`ExtrinsicIntents`.

### Impact Explanation
This is a permanent freezing-of-funds vulnerability reachable by a single unprivileged `placeOrder` call. An attacker (the order creator) crafts an order whose `inputs` array mixes a real, valuable token (e.g., USDC) with a malicious ERC20 they control that can be flipped to always revert on transfer. A solver, evaluating the order, fills it in good faith by sending real output tokens to the beneficiary via `fillOrder`/`_fillCrossChain`. The attacker then flips the malicious token to permanently block transfers. When the `RedeemEscrow` message arrives on the source chain, `_withdraw` will always revert while attempting to pay out the malicious token, so the solver can never claim any of the escrowed inputs — including the legitimate, valuable token bundled in the same order — even though the solver already delivered real value. This directly mirrors the cited report's bug class (a self-controlled malicious ERC20 that becomes non-transferable after the counterparty has committed real value), but here the loss is a permanent freeze of the solver's earned escrow rather than an NFT.

### Likelihood Explanation
High. `placeOrder` is fully permissionless with respect to token selection, requires no allowlist, and deploying a token that starts transferable and later becomes permanently non-transferable (pausable/blacklistable, owner-controlled) is trivial and standard practice for scam tokens. Solvers competing for order fills across many chains and many tokens cannot realistically vet every input token in a bundle before committing to fill, especially since fills must be all-or-nothing for cross-chain orders and outputs are paid before the escrow redemption succeeds.

### Recommendation
Make `_withdraw` resilient to individual token transfer failures instead of reverting the entire withdrawal: use a low-level call with a try/catch (or `.call` + return-value check) per token, and if a transfer fails, keep the failed token's escrow balance recorded (or route it to a separate claimable/sweep mechanism) rather than reverting and blocking payout of every other token in the same order. Additionally, consider isolating per-token release so one bad-token failure cannot block the whole batch, and/or introduce a governance-controlled token denylist/allowlist for `IntentGatewayV2` inputs to reduce exposure to adversarial tokens.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 with an owner-controlled `frozen` flag; `transfer`/`transferFrom` succeed normally but revert unconditionally once `frozen` is set.
2. Attacker calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 1000} , {token: EvilToken, amount: 1} ]`, requesting some output on another chain. `placeOrder` escrows both, per [1](#0-0) .
3. A solver calls `fillOrder`, which routes into `_fillCrossChain`, sending real output tokens to `beneficiary` and dispatching `RedeemEscrow` back to the source chain, per [5](#0-4) .
4. Attacker calls `EvilToken.setFrozen(true)`.
5. When the `RedeemEscrow` message is delivered on the source chain, `_withdraw` attempts to `safeTransfer` both USDC and `EvilToken` to the solver; the `EvilToken` transfer reverts, reverting the whole `_withdraw` call and thus `onAccept`, per [3](#0-2) .
6. `EvmHost.dispatchIncoming` deletes the receipt and leaves the message retryable, per [4](#0-3) , but every retry fails identically since `EvilToken` stays frozen forever — the solver's USDC escrow is permanently locked despite having already delivered real output tokens to the beneficiary.
