### Title
Unbounded, instantaneous-balance-weighted selection in phantom bid price aggregation lets a solver flash-manipulate the published `medianPrice` used to quote real intents - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` weights each solver's phantom-order quote by that solver's *current* on-chain balance of the leg's output token (`getTotalSolverBalance`, default `blockTag = "latest"`), then feeds the weights into `weightedMedian`, which is a **selection** function that returns one bidder's exact quoted integer verbatim as `medianPrice` whenever that bidder holds over half the leg's weight. This mirrors the root cause of the referenced governance report: influence over an outcome (there, vote weight; here, price-setting weight) is derived from an unprotected, instantaneous balance read rather than a balance checkpointed before the action began, so temporarily inflating the balance lets an attacker dictate the outcome.

### Finding Description
- `runAggregation` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1356-1357`, `1506-1513`) builds a `getBalance`/liquidity-sweep reader via `memoizedSolverBalance(yieldVaults)` which calls `getTotalSolverBalance(..., blockTag)` defaulting to `"latest"` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1009-1022`, `1161-1187`). [1](#0-0) 
- Each bid's weight is exactly this instantaneous balance (`quotes.push({ price, weight })`), and a zero-weight quote is dropped, but any nonzero balance counts fully with no minimum holding period, no historical/finalized-block check, and no protection against a balance that only exists for the duration of the read. [2](#0-1) 
- `weightedMedian` is documented and tested as a **selection, not a blend**: "a solver holding over half the leg's weight sets the published price verbatim" (confirmed in `sdk/packages/indexer/docs/ai/flows/phantom-price-snapshot-to-pool-rates-phantombidwindowexhausted.md:13` and `sdk/packages/simplex/docs/ai/flows/phantom-probe-curve-value-published-price.md:40-42`). [3](#0-2) 
- This published `medianPrice`/`standardAmount` is not merely informational: `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot` derives real, executable `amountOut`/`amountIn` for actual intent quotes directly from it (`(netAmountIn * snapshot.medianPrice) / snapshot.standardAmount`), and `updateLiquidityPools`/`poolRateFromQuote` republish it as the pool's `sellRate`/`buyRate` consumed by other quoting paths. [4](#0-3) [5](#0-4) 

The governance analog: `GovernorBravoDelegate.castVoteInternal` takes `min(getPriorVotes(startBlock), getPriorVotes(block.number))` — still vulnerable per the report because neither endpoint is a properly finalized (`block.number - 1`) read. Here the weighting is strictly weaker: there is no "prior" checkpoint reference at all — the *only* input to the weight is the live/`"latest"` balance read at aggregation time, with no comparison against any earlier balance (e.g. balance at bid-submission time or bid-window-open time). A solver can inflate its balance for the (short, largely predictable) window between bid submission and the indexer's aggregation run — which is triggered deterministically by `PhantomBidWindowExhausted`, a pallet-controlled, non-secret timing — to dominate the weighted-median selection and force its own (mispriced) quote to become the network-published rate.

### Impact Explanation
A solver that temporarily boosts its balance of a leg's output token (e.g., via a short-term loan, a same-block token transfer, or coordinated timing around the deterministic bid-window-close event) can:
1. Force `weightedMedian` to select its own bid verbatim as `medianPrice`, overriding genuinely liquidity-backed quotes from other solvers.
2. Have that manipulated price consumed as an executable rate by `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot`, causing real users' intents to be quoted (and potentially filled) at an attacker-chosen, non-market rate.
3. Have the same manipulated rate republished into `LiquidityPool.sellRate/buyRate` via `updateLiquidityPools`, propagating the bad price to any other consumer of pool rates.

This can cause real economic loss to users relying on the quote (over/under-paying versus the true market rate) and lets a single actor manufacture artificial "liquidity-weighted" credibility for a price with only transient backing — the same class of unfair amplification described in the source report, but applied to price-setting weight instead of voting weight, with a direct path to fund-losing trades rather than governance outcomes.

### Likelihood Explanation
Medium-to-High for a determined solver: the balance read happens at `"latest"` with no snapshot-based resistance, the bid-window-close trigger (`PhantomBidWindowExhausted`) timing is protocol-determined (not attacker-secret but predictable/near-deterministic per configured window), and the weighting mechanism explicitly documents (and tests confirm) that "a solver holding over half the leg's weight sets the published price verbatim" — i.e., the code is designed to hand full pricing power to whoever has the largest instantaneous balance, with no minimum dwell time or historical check. The main mitigating factor is the indexer's read timing is not perfectly attacker-controlled to the single block, so a genuine zero-cost atomic flash loan is not guaranteed to land exactly on the balance-read block; the attacker would need to hold the inflated balance across the plausible window between window-close and indexer processing, which raises cost/risk somewhat but does not eliminate the manipulation vector.

### Recommendation
Do not weight (or select verbatim on) a purely instantaneous balance. Require the weighting balance to be checkpointed at (or before) the start of the bid window, e.g., record `SolverBalanceAtWindowOpen` (or `getTotalSolverBalance` pinned to a `blockTag` fixed before/at window open) and require it to be compared against the balance at aggregation time, using `min(balanceAtOpen, balanceAtClose)` analogous to the recommended `GovernorBravoDelegate` fix. Additionally, consider requiring balances to be sustained for a minimum number of blocks before counting toward weight, and/or blending (rather than verbatim-selecting) the median across multiple non-trivial-weight bidders to avoid single-bidder dictatorship of the published price.

### Proof of Concept
1. Solver A holds a negligible balance of `tokenB` on the destination chain and submits a lowball/attacker-favorable bid for a phantom order leg (bid submission requires only a valid signed `UserOperation`, no balance check at submission time — see `isVerifiedSolverBid` in `runAggregation`).
2. Immediately before the `PhantomBidWindowExhausted` event fires (a deterministic, protocol-configured window), Solver A temporarily acquires (e.g., via loan, internal transfer, or coordinated capital movement) a large balance of `tokenB`.
3. When `handlePhantomOrderPrices` triggers `aggregatePhantomBids`, `getTotalSolverBalance(..., "latest")` reads Solver A's inflated balance, giving its bid the largest weight (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1161-1187`, `1506-1513`).
4. `weightedMedian` selects Solver A's quoted price verbatim as `medianPrice` because Solver A's weight exceeds half the leg's total weight (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1551`).
5. Solver A returns the inflated/borrowed balance immediately after the read.
6. `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot` (`sdk/packages/sdk/src/protocols/intents/quote/phantomSnapshot.ts:83-101`) and `updateLiquidityPools`/pool `sellRate`/`buyRate` now quote real users against Solver A's manipulated, unbacked price. [6](#0-5)

export function memoizedSolverBalance(
	yieldVaults: YieldVaultMap,
	/**
	 * Block to read each chain at, keyed by state machine id; anything absent reads the head. Block
	 * numbers are per chain, so a caller handling an event on one chain can pin that chain to the
	 * event's block while the rest of its sweep stays at the head, where the numbers would mean
	 * nothing.
	 */
	blockTags: Record<string, string> = {},
): SolverBalanceReader {
	const cache = new Map<string, Promise<bigint>>()
	return (evmRpcUrl: string, chain: string, token: string, solver: string): Promise<bigint> => {
		const key = `${chain}|${token.toLowerCase()}|${solver.toLowerCase()}`
		let pending = cache.get(key)
		if (!pending) {
			// Evict on rejection. Caching a failure would make it permanent for the memo's lifetime —
			// every retry would replay the same failed read, and a block-scoped memo would carry one
			// blip across every order closing on that block.
			pending = getTotalSolverBalance(evmRpcUrl, chain, token, solver, yieldVaults, blockTags[chain]).catch((err) => {
				cache.delete(key)
				throw err
			})
			cache.set(key, pending)
		}
		return pending
	}
}

export function poolRateFromQuote(
	medianPrice: bigint,
	resolved: Pick<ResolvedPoolLeg, "inDecimals" | "outDecimals">,
	standardAmount: bigint,
): bigint {
	const scale = 10n ** BigInt(POOL_RATE_DECIMALS - resolved.outDecimals)
	const inputUnit = 10n ** BigInt(resolved.inDecimals)
	return (medianPrice * scale * inputUnit) / standardAmount
}
