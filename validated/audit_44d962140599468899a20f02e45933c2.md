### Title
Stale delegate grant re-arms when the position NFT returns to the granting owner — a previous delegate silently regains full account authority - (File: contracts/controller/src/storage/account.rs)

### Summary
The controller's delegate mechanism is the on-chain analogue of a session grant: an account owner stamps a `DelegateGrant { granted_by, delegates }` under `ControllerKey::Delegates(account_id)`. On NFT transfer the grant is *not* invalidated — it is merely filtered out while `granted_by != current owner`. The stale entry persists in storage and automatically re-activates if the token ever returns to the original owner, restoring the old delegate's authority without any fresh consent — the same defect class as CVE-2025-48061 (sessions surviving logout and re-authenticating the user on return).

### Finding Description
`get_delegates` returns the stored delegate list only when `grant.granted_by == *owner`; otherwise it returns empty but **leaves the entry in persistent storage** (`account.rs:176-181`). `account.rs:174-181` explicitly comments: "Ownership changes invalidate a previous owner's grants without deleting them."

Because the grant is keyed only by `account_id` and `granted_by`, if the position NFT is transferred out and later transferred back to `granted_by` (sale and repurchase, marketplace round-trip, accidental return, or deliberate attacker engineering), the stale `DelegateGrant` matches again and the old delegate list becomes live. Nothing in `position-nft`'s `transfer`/`transfer_from` notifies the controller, and the controller never caches ownership (per the README: "the owner is never cached in controller storage"), so no path scrubs the stale grant.

The code shows the authors were aware of the re-arming hazard in exactly one direction: `remove_delegate` deletes a mismatched (`granted_by != owner`) grant specifically "preventing those grants from reactivating if the NFT returns to their original owner" (`account.rs:223-238`). But this cleanup only runs if the *current* owner proactively calls `remove_delegate` for each stale entry — and under the documented design the stale grant is invisible to the new owner as an active list, so there is no reliable trigger to purge it. `add_delegate` (`account.rs:203-221`) also overwrites stale grants, but again only when invoked.

Concretely:
1. Alice owns account NFT `id`, calls `add_delegate(id, alice, mallory)` — e.g., Mallory is a keeper/operator contract.
2. Alice transfers the NFT to Bob (sells the position). The grant becomes dormant but remains in storage.
3. Bob later sells/transfers the NFT back to Alice (or Alice buys an identical-looking position back on a marketplace — `account_id == token_id`, so the same account returns with its history).
4. The instant `owner_of(id) == alice` again, `get_delegates` returns `[mallory]` and Mallory is once again an authorized caller on the account — able to act on the position (withdraw collateral within LTV, borrow, swap collateral/debt, etc., wherever `require_authorized_caller` accepts owner-or-delegate) with no re-consent from Alice.

### Impact Explanation
Theft of user funds: a formerly-trusted delegate (or any address that ever obtained a delegation from a previous holder of that token id) silently regains account authority and can extract collateral value — withdraw freely if debt-free, or borrow up to LTV and withdraw the proceeds — the moment the NFT returns to the original owner. Since positions are transferable NFTs intended to circulate on marketplaces, owner round-trips are a realistic occurrence rather than an edge case. Severity: Medium — requires a prior delegation and a return transfer, but the re-arming is automatic, invisible, and needs no signature from the victim.

### Likelihood Explanation
- Delegation is a supported, in-scope feature; a user who delegates to a router/keeper contract once creates a persistent dormant grant.
- NFT positions are designed to be traded; buying back a previously-owned position (same `account_id`) is plausible, and an attacker who held a delegation can even engineer the return by acquiring the token and transferring it back to the victim unsolicited — NFT `transfer` requires only `from` auth, so anyone holding the token can send it to `granted_by`.
- Notably, an attacker can *buy* an underwater-or-marginal position specifically to gift it back to its prior owner in order to reactivate their own stale grant.
- Mitigating: the stale grant is destroyed if any intervening owner calls `remove_delegate` or `add_delegate` (which overwrite the entry), so the window depends on intermediate holders not touching delegates.

### Recommendation
Delete or epoch-bind stale grants on ownership change rather than leaving them dormant:
- Key `DelegateGrant` by an ownership epoch (e.g., store the owner's address plus a nonce, or store grants under `Delegates(account_id, owner)` so a returning owner maps to a fresh, empty list), or
- Clear `ControllerKey::Delegates(account_id)` on every detected ownership transition (cheap check inside `try_account_owner`/`get_account` via a cached last-owner entry), or
- At minimum, include the NFT token's transfer path in controller awareness (a `renew`-style hook or an owner-version counter bumped on `owner_of` change) and wipe mismatched grants eagerly rather than relying on the new owner to call `remove_delegate`.

### Proof of Concept
```rust
// Harness sketch (soroban testutils):
let token_id = nft.mint(&alice);               // account created via supply(account_id=0)
// alice delegates to mallory
controller.add_delegate(&alice, &token_id, &mallory);      // DelegateGrant{granted_by: alice}

// alice sells/transfers the position to bob
nft.transfer(&alice, &bob, &token_id);
// dormant: get_delegates(token_id, bob) == []  but entry still in storage

// token returns to alice (sale, gift, or attacker sends it back)
nft.transfer(&bob, &alice, &token_id);         // or attacker-held -> alice

// stale grant re-arms:
assert_eq!(get_delegates(token_id, alice), vec![mallory]);

// mallory is again an authorized caller on alice's account:
controller.withdraw(&mallory, &token_id, collateral_legs, None); // succeeds
// or borrow(...) up to LTV and withdraw, draining account equity
```

Note: I could not fully re-verify within this iteration the exact scope of delegate powers inside `require_authorized_caller` (i.e., which entrypoints accept a delegate vs. strictly the owner); the finding assumes delegates are authorized callers for account mutators, consistent with the README's "delegate grant" / "Delegates lapse on transfer" security notes and the `add_delegate`/`remove_delegate` plumbing. If delegates are only permitted on a subset of endpoints, the impact reduces accordingly but the re-arming defect itself is confirmed by `account.rs:174-181` and `223-238`.
