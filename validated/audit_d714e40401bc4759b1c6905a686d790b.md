This confirms the vulnerability. The `Request#hmac` validation only signs `@raw_body` [1](#0-0)  while `shop`, `topic`, and other identity fields come from unauthenticated HTTP headers [2](#0-1) , and `Registry.process` passes that unverified `shop` straight into the handler that apps use for tenant lookups [3](#0-2) .

### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) fields are not covered by the HMAC signature, allowing cross-tenant spoofing via header manipulation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then trusts the `shop` field taken from an unrelated, unsigned HTTP header to identify which tenant the webhook belongs to. Because the header is not covered by the HMAC, anyone who can produce one valid signed `(raw_body, hmac)` pair (e.g., from their own shop/app instance) can freely swap the `x-shopify-shop-domain` header to any other value while keeping the same valid HMAC, causing the app's webhook handler to process/attribute the payload to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Its `hmac`, `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers, none of which are included in the signed bytes: [4](#0-3) 

`Registry.process` validates the request using only this body-derived HMAC, then immediately builds `WebhookMetadata` from the header-derived, unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` and hands it to the app-registered handler as trusted data: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compare it to the `hmac` header value using `Context.api_secret_key`: [5](#0-4) 

This reproduces the report's bug class exactly: a field (`shop`) that the application logic *acts on* (tenant identification/session lookup) is not covered by the cryptographic binding (`hmac`) that is supposed to authenticate the whole request. The equality the gem should enforce — `shop_header == shop_that_the_app_secret_actually_signed_for` — is never checked. Any two requests that share the same `raw_body` will produce the same valid `hmac`, regardless of what `shop`, `topic`, `webhook-id`, or `api-version` headers are attached.

### Impact Explanation
An attacker who can obtain even one legitimately-signed webhook body+HMAC pair (trivially available: install the app on their own free/dev shop and trigger any subscribed webhook topic with a body they control, e.g. a metafield/product update with attacker-chosen content) can replay that exact `raw_body`/`hmac` pair while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers to impersonate an arbitrary victim shop. `Registry.process` will accept it as authentic (HMAC matches) and dispatch `WebhookMetadata` claiming the payload originated from the victim tenant. Any host application that keys off `data.shop` from this gem's webhook processing (the documented pattern, see `docs/usage/webhooks.md`) to look up/update per-tenant records will act on attacker-controlled data under a victim's tenant identity — a cross-tenant data integrity/confidentiality issue.

### Likelihood Explanation
High likelihood for any developer using this gem's webhook feature exactly as documented, since the gem's own API design (`Request`, `Registry.process`, `WebhookMetadata`) presents `shop` as a verified, trustworthy field once `HmacValidator.validate` passes — there is nothing in the public API surface suggesting the shop header is unauthenticated. An attacker needs only network access to the app's webhook endpoint and the ability to generate one valid webhook for any shop (including their own).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signature verification, e.g., by cross-checking the header-provided `shop` against the shop embedded in the raw JSON body where available, or better, by including the relevant headers in the signable string used for validation. At minimum, document/require host apps to independently verify that `data.shop` corresponds to a shop with an active, known session before trusting it — and update `Registry.process` to reject requests when the header-provided identity can't be reconciled with any signed material.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers (or fabricates, if given a raw endpoint to their own dev store) a webhook with topic `X`, causing Shopify to POST `raw_body` with a valid `x-shopify-hmac-sha256` computed using the app's real `client_secret`.
2. Attacker intercepts/replays this request to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`), keeping `raw_body` and `x-shopify-hmac-sha256` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this succeeds because `raw_body` and `hmac` are still the legitimately-signed pair.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and invokes the app's handler, which processes/updates data under the victim shop's tenant using attacker-controlled `body`.
