Confirmed: the shop identity is bound to the wrong bytes in the webhook path. I have enough evidence to finalize.

### Title
Webhook shop-domain header is not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed only over the raw request body, then passes the unauthenticated `shop-domain` header value to the app's handler as the tenant identifier. Because the header is not part of the signed bytes, any party who can obtain one validly-signed webhook body (e.g., from their own store) can replay it with an arbitrary `shop-domain` header and have it accepted as coming from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shop-domain` header, which is excluded from that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only) and, once that check passes, forwards `request.shop` unchanged into `WebhookMetadata`, which is delivered to the app's registered handler as the trusted tenant/shop identity: [3](#0-2) 

The equality that should hold is: *the shop value the handler acts on* == *the shop value cryptographically bound by the HMAC*. Here, the HMAC only binds the JSON body bytes; it never binds the `shop-domain` header. So `request.shop` (header, attacker-controlled) is trusted while `request.hmac` verifies a completely disjoint value (the body). An attacker who is themselves a legitimate Shopify merchant/developer will receive their own genuinely-signed webhook deliveries (identical body content is easy to reproduce, e.g. an `orders/create` payload with attacker-controlled shop data) and can then POST that same body/HMAC pair to the target app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. The signature still validates because it never covered the header, and the handler receives `data.shop` equal to the victim's domain.

### Impact Explanation
This crosses a tenant boundary without any credential belonging to the victim shop or knowledge of the app's `client_secret`/API secret: an unprivileged attacker (any developer/merchant able to generate their own signed webhook traffic) can make the app process events under an arbitrary other shop's identity. Depending on how the host application uses `WebhookMetadata#shop` (data-scoping, session lookup, triggering shop-specific side effects), this enables cross-tenant data manipulation/visibility. This maps to "Critical - cross-tenant access."

### Likelihood Explanation
No secret material is required. The attacker needs only: (1) their own Shopify store to receive at least one legitimately-HMAC-signed webhook of the topic they want to spoof, and (2) network access to POST to the target app's public webhook endpoint. Swapping the `shop-domain` header while keeping body and `hmac-sha256` header untouched is trivial and the gem performs no cross-check between the two.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise independently bind the header value to the signature before trusting `request.shop`/`WebhookMetadata#shop` — e.g., mirror Shopify's actual verification contract if it differs, or require the host application to additionally verify that `request.shop` corresponds to a shop with a known/active session before processing. At minimum, document loudly that `Registry.process`'s `shop` field is not authenticated by the HMAC and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and receives a real webhook there,
# capturing raw_body and the x-shopify-hmac-sha256 header Shopify sent.
raw_body = '{"id":1,"note":"hi"}' # exact bytes Shopify sent to attacker's endpoint
valid_hmac_header = "<value captured from Shopify's legitimate delivery>"

forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_header, # still valid: HMAC only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (Utils::HmacValidator.validate(request) checks raw_body only)
# => handler.handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
