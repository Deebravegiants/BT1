### Title
Webhook `shop-domain` header is not covered by HMAC signature, allowing tenant-spoofed webhook delivery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body via `to_signable_string`, while `topic`, `shop`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the app's handler as the tenant identity, without that value ever being part of the cryptographic proof.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates only that `Utils::HmacValidator.validate(request)` passes (i.e., that the body's HMAC matches the app's secret), then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., and forwards it to the app-supplied handler: [3](#0-2) 

The equality the gem should guarantee but does not is: `shop-domain header == shop bound by the HMAC signature`. Instead the binding actually enforced is only `raw_body == HMAC(raw_body, api_secret_key)`; the shop, topic, webhook-id, and api-version headers are fully attacker-controllable while the request's HMAC still validates as long as the body bytes are unchanged.

Any merchant can install the target app on their own store (unprivileged — this requires no special access, just the OAuth flow the gem itself performs). Shopify will then send that merchant real, validly-HMAC-signed webhooks for their own shop. The merchant/attacker can capture one such request (body + valid `hmac-sha256` header) and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` recomputes the signature over the unchanged raw body and still succeeds, so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain and the attacker's chosen body content — exactly the "field acted on but not covered by the HMAC" identity-binding break.

### Impact Explanation
Per the gem's own documented usage, apps built on this library are expected to route business logic (job dispatch, per-shop data mutation/deletion, uninstall handling, cache invalidation, etc.) using `data.shop` as the trusted tenant identifier, e.g., the doc's own example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. Because the gem's `process` method presents `shop` as a validated, trustworthy field, downstream apps have no signal to re-check it — the HMAC check gives false assurance that the entire webhook (including shop) is authentic. An attacker with a legitimate low-privilege install can trigger cross-tenant state changes for victim shops (e.g. forcing "app/uninstalled" or "customers/redact" processing for a shop that never sent that event), a cross-tenant impact directly in-scope.

### Likelihood Explanation
Requires only: (1) attacker installs the free/public app on their own shop (no privilege beyond being any Shopify merchant), (2) captures one webhook delivery, (3) replays it with a modified shop header to the app's public webhook endpoint. No access to `api_secret_key` or any merchant's access token is needed since the HMAC is recomputed over the same, unmodified body bytes.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signable payload, or require the app's webhook processing code to independently verify that the header `shop` matches a shop-scoped signing input from Shopify (Shopify's official webhook payloads do not expose the shop within the signed body, so the gem should instead document/require binding the `X-Shopify-Shop-Domain` header value against the receiving `session`/subscription record established during registration rather than trusting it outright), and update `docs/usage/webhooks.md` to stop recommending direct use of `data.shop` as an authenticated tenant identifier without such a check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` via the app's normal OAuth flow (unprivileged, self-service).
2. Attacker registers for a low-noise webhook topic (e.g. `app/uninstalled`) and waits for Shopify to POST it to the app's webhook endpoint; attacker captures the raw body `B` and header `shopify-hmac-sha256: H` (`H = HMAC-SHA256(api_secret_key, B)`), which is valid because Shopify's own signature is over the raw body.
3. Attacker replays the exact same `B`/`H` pair to the same webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` instead of their own domain.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` exposes `shop == "victim-shop.myshopify.com"`; `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, B)` which still equals `H`, so validation passes.
5. `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and any app logic keyed off `data.shop` (per the gem's documented pattern) now acts on the victim tenant using attacker-controlled topic/body semantics.
