### Title
Untrusted swap routes can inject unauthorized token transfers into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy swaps forward caller-supplied `StrategySwap` data to the configured router after authorizing only the controller’s exact input transfer, while the swap route itself can direct execution through attacker-selected pool contracts. [1](#0-0)  Because route pool addresses are payload-controlled and invoked as venue contracts, a malicious hop can execute arbitrary contract code during the swap and request additional `token.transfer` authorization from the account that signed the outer controller call. [2](#0-1) [3](#0-2)  If the caller signs the authorization tree produced by simulation without rejecting the injected child invocation, the malicious pool can transfer unrelated wallet tokens to an attacker while still returning a valid swap output. [4](#0-3) 

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and other strategy paths reach `swap_tokens`, which snapshots input and output balances, grants the router a narrow controller-token transfer authorization, and passes the caller-provided swap payload into `execute_strategy`. [1](#0-0)  The router payload contains an attacker-controlled address registry in which pool addresses are selected by instruction indices rather than constrained to trusted pool contracts. [5](#0-4)  Venue dispatch then invokes the selected address as a pool, so the route data functions as an instruction stream capable of placing attacker code inside the caller’s authorization context. [3](#0-2)  The measured-output checks only bound the routed input and require a positive output; they do not prevent the invoked pool from requesting an unrelated transfer from the transaction signer. [6](#0-5) [7](#0-6) 

### Impact Explanation
A malicious route can steal tokens from the user initiating a collateral or debt swap, including assets that are not listed by the protocol and were never intended to be part of the swap. [8](#0-7)  The repository’s regression test demonstrates that a rogue hop can transfer the caller’s unrelated wallet balance to an attacker while the controller still receives and deposits the expected swap output. [4](#0-3)  This is theft of user funds rather than merely poor execution quality because the stolen transfer is separate from the routed amount and the final account risk checks. [9](#0-8) 

### Likelihood Explanation
Exploitation requires convincing a user to submit a crafted route and sign the simulation-produced authorization tree containing the malicious child transfer, so it is not executable by an attacker entirely without user interaction. [10](#0-9)  However, simulation records the rogue transfer under the caller’s normal controller authorization entry, meaning ordinary signing flows can present the poisoned tree as part of the intended swap. [11](#0-10)  Since routes are externally constructed and venue pool addresses are not allowlisted by the payload format, attackers can deploy a malicious contract and encode it as a hop. [5](#0-4) [12](#0-11) 

### Recommendation
Constrain route-selected pool contracts to governance-approved venue addresses or route-specific trusted pool registries so payload bytes cannot introduce arbitrary contract code into the authorization context. [13](#0-12)  At the controller boundary, clients should require the signed authorization tree to contain only the expected controller input-transfer child and reject any additional `token.transfer` invocation involving the caller. [9](#0-8)  The router should also provide an auth-isolated execution mode or venue adapters that cannot inherit unintended signer authorization for arbitrary callee behavior. [14](#0-13) 

### Proof of Concept
1. Deploy a contract exposing the expected pool `swap` interface, but inside `swap` call `token.transfer(victim, attacker, wallet_balance)` on an unrelated token held by the victim. [15](#0-14) 
2. Construct a valid route whose selected pool address is that contract and whose output still satisfies the route minimum through a fair payout. [16](#0-15) 
3. Have the victim invoke `swap_collateral` with that route; simulation records the rogue `transfer` as a child beneath the victim’s controller authorization. [11](#0-10) 
4. If the victim signs the recorded tree, the call succeeds, the attacker receives the victim’s unrelated wallet tokens, and the victim still receives the expected swapped collateral. [17](#0-16)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

/// Builds one invoker-auth entry for `contract.fn_name(args)`, wrapping the given sub-invocations.
pub(crate) fn auth_entry(
    env: &Env,
    contract: &Address,
    fn_name: &str,
    args: Vec<Val>,
    sub_invocations: Vec<InvokerContractAuthEntry>,
) -> InvokerContractAuthEntry {
    InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: contract.clone(),
            fn_name: Symbol::new(env, fn_name),
            args,
        },
        sub_invocations,
    })
}

/// Registers a single top-level invoker auth entry, with no sub-invocations,
/// for `contract.fn_name(args)`.
pub(crate) fn authorize_as_current(env: &Env, contract: &Address, fn_name: &str, args: Vec<Val>) {
    env.authorize_as_current_contract(vec![
        env,
        auth_entry(env, contract, fn_name, args, vec![env]),
    ]);
}
