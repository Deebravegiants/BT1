### Title
Missing bounds validation on `protocolFeeBps` / destination fee in Tron `IntentGatewayV2.setParams` and `onAccept(UpdateParams)` can permanently brick `placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` sets its fee parameters (`_params.protocolFeeBps` via `setParams`, and `_destinationProtocolFees[...]` via the cross-chain `UpdateParams` governance message handled in `onAccept`) with no upper-bound validation, unlike the canonical EVM implementation (`IntentsBase._validateParams`) which enforces `protocolFeeBps < 10_000` and each `destinationFeeBps < 10_000`. If a fee value `>= 10_000` bps is ever configured, every subsequent `placeOrder` call for that fee context reverts with an arithmetic underflow, permanently freezing intent placement — the same "unvalidated bound causes a mandatory-path function to revert forever" defect as the reported `OracleStrikeOTLM.minStrikePrice` issue.

### Finding Description
In the reference contracts (`evm/src/apps/intentsv2/IntentsBase.sol`), both `setParams`/initialization and governance `UpdateParams` handling run through `_validateParams`, which explicitly rejects `protocolFeeBps >= 10_000` and, in `_updateParams`, rejects any `destinationFeeBps >= 10_000`: [1](#0-0) 

The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, omits this validation entirely in both places:

- `setParams` blindly assigns `_params = p` with only an admin-authorization check, no field validation: [2](#0-1) 

- The `onAccept` handler for `RequestKind.UpdateParams` (a cross-chain governance message from Hyperbridge) likewise assigns `_params = update.params` and writes `_destinationProtocolFees[stateMachineId] = feeBps` without any bound check: [3](#0-2) 

`placeOrder` then uses whichever fee value is configured to compute a reduced, escrowed input amount: [4](#0-3) 

`reducedAmount = originalAmount - protocolFee` is performed with Solidity 0.8 checked arithmetic (only the loop index increment is `unchecked`). If `protocolFeeBps` (or the destination-specific override) is ever `> 10_000`, `protocolFee > originalAmount` and this subtraction reverts on every single order for that fee context. Because there is no in-contract mechanism to detect or reject the value before it is written, the only remedy is another governance/admin update — exactly the "invalid strike price... preventing starting a new epoch" pattern from the report: a missing bound on an owner/governance-set parameter silently bricks the core unprivileged user path (`placeOrder`).

### Impact Explanation
Once an out-of-range `protocolFeeBps` (default fee) or `destinationFeeBps` (per-destination override) is set — whether by an honest governance mistake during a `UpdateParams` dispatch, a bad decimal/unit assumption, or a first-time `setParams` call by the admin — `placeOrder` reverts unconditionally for every order using that fee, freezing the intents pipeline for the Tron deployment (or for a specific destination chain). This is a denial-of-service on a core unprivileged path (any user/solver submitting an intent), matching the "route unable to deliver messages" criterion: users cannot create escrow orders, so cross-chain intent fulfillment for that route stops until another correct config is pushed. Because the value only needs to reach `>= 10_000` (a 27-bit vs 14-bit boundary — trivially exceeded, e.g. by mixing up bps with a different fee unit, or supplying a raw percentage like `10000` meaning "no discount"/edge value), this is a realistic operational misconfiguration, not a contrived edge case.

### Likelihood Explanation
Medium likelihood: it requires a governance/admin action to set the fee, but no code path prevents a value at or above 10,000 bps from being written, so the safety net that exists in the mainline EVM contract (`IntentsBase._validateParams`) is simply absent here. Any single incorrect `UpdateParams` message or `setParams` call — accidental, not malicious — bricks the contract's primary function permanently until corrected, mirroring exactly the reported bug class (unvalidated minimum/bound parameter blocking a mandatory downstream operation).

### Recommendation
Port the same validation used in `evm/src/apps/intentsv2/IntentsBase.sol::_validateParams` / `_updateParams` into the Tron `IntentGatewayV2.setParams` and the `UpdateParams` branch of `onAccept`: reject `p.protocolFeeBps >= 10_000` and reject any `update.destinationFees[i].destinationFeeBps >= 10_000` before writing state, so an invalid fee can never be persisted and `placeOrder`'s reduction arithmetic can never underflow.

### Proof of Concept
1. Admin calls `setParams` (or Hyperbridge governance dispatches `UpdateParams`) with `protocolFeeBps = 10_500` (or any value `> 10_000`) — no revert occurs because `evm/tron/contracts/apps/IntentGatewayV2.sol:306-311` / `644-660` perform no bounds check.
2. Any user calls `placeOrder` with a non-zero `order.inputs[i].amount`.
3. Inside the fee-reduction loop, `protocolFee = (originalAmount * 10_500) / 10_000 > originalAmount`, so `reducedAmount = originalAmount - protocolFee` underflows and reverts under Solidity 0.8 checked arithmetic (`evm/tron/contracts/apps/IntentGatewayV2.sol:362-364`).
4. Every subsequent `placeOrder` call using this fee context reverts identically, permanently blocking new intent creation until governance issues a corrective `UpdateParams` message.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
