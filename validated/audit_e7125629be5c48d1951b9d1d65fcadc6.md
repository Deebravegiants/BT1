### Title
Unbounded BEEFY signature count causes computational denial-of-service during consensus proof verification - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
`verify_mmr_update_proof` in the BEEFY consensus verifier iterates over every signature supplied in an attacker-relayed `MmrProof` and calls the expensive `secp256k1_recover` cryptographic primitive once per signature, with no upper bound on the number of signatures accepted. This is analogous to the `net-imap` SCRAM issue: an untrusted, attacker-controlled iteration count (here, the number of `Vote`/signature entries in a relayed consensus proof) directly drives the number of expensive cryptographic operations performed synchronously by the verifier, with only a lower-bound (supermajority) check and no upper bound.

### Finding Description
`check_participation_threshold` only enforces `signatures_length >= (2*total/3)+1` — a floor, not a ceiling: [1](#0-0) 

Immediately after this check passes, the verifier loops over `mmr.signed_commitment.signatures.iter()` and performs an ECDSA public-key recovery (`H::secp256k1_recover`) for every entry, unconditionally: [2](#0-1) 

Because `signatures_length` is read directly off attacker-supplied proof data (`mmr.signed_commitment.signatures.len()`) and is never capped against `authority_set.len` (the real, trusted validator-set size) or any hard maximum, a relayer/submitter can pad the `signatures` vector with an arbitrarily large number of entries (duplicates or junk entries with bogus indices — the merkle multi-proof step that would reject bogus authority indices runs *after* the entire recovery loop completes) to force the verifier to perform an unbounded number of expensive `secp256k1_recover` calls before any validity check on those extra entries fails.

This consensus proof is delivered as an ISMP `Message::Consensus` through the permissionless, unsigned `handle_unsigned` extrinsic of `pallet-ismp` — reachable by any relayer/network peer submitting a single extrinsic, with no signer, no fee, and no stake requirement: [3](#0-2) 

The identical unbounded-loop pattern also exists in the EVM ECDSA BEEFY light client, where `checkParticipationThreshold` is likewise a floor-only check before the `for (uint256 i = 0; i < sigLen; i++) { ECDSA.recover(...) }` loop: [4](#0-3) 

The EVM path is bounded by gas metering (the caller pays and the transaction simply reverts on out-of-gas), which limits — though does not eliminate — the impact there. On the Substrate side, however, `handle_unsigned` is free (unsigned) and, unlike other calls in the pallet that use benchmarked, content-scaled weights (e.g., `DbWeight::get().reads_writes(...)`), it uses a distinct `weight()` helper function whose scaling behavior with respect to proof/signature-array size could not be fully confirmed in this review. If that weight does not scale with the number of signatures actually present in the submitted consensus proof, execution (and, more importantly, `ValidateUnsigned` mempool validation, which every full node performs on every gossiped unsigned extrinsic before it is ever included in a block) could take substantially longer than its declared/benchmarked cost, stalling block production or transaction-pool processing across the network — the direct Substrate analog of the net-imap PBKDF2 DoS (blocking the executor with attacker-controlled iteration counts of an expensive cryptographic primitive).

### Impact Explanation
An attacker who controls only the content of a single unsigned `Message::Consensus` payload (no privileged role required — anyone can submit `handle_unsigned`) can force the node's consensus verifier to perform an attacker-chosen, effectively unbounded number of `secp256k1_recover` operations. Because this happens both during `ValidateUnsigned` (mempool admission, run by every peer on every gossip hop) and during block execution, it can degrade or stall block production/transaction processing across the network — a route-unable-to-deliver-messages / liveness-DoS impact, which is explicitly in scope per the validation rules (message dispatcher / relayer-reachable consensus verification path).

### Likelihood Explanation
Likelihood is high in terms of reachability: any relayer or arbitrary network peer can construct and submit a single `Message::Consensus` extrinsic with a bloated `signatures` vector; no signature threshold, size cap, or fee gates the size of that vector before the recovery loop runs. The main open question — and the reason this can't be graded Critical with full confidence — is whether the pallet's benchmarked `weight()` for `handle_unsigned` already scales sufficiently with the encoded proof size to make the resulting weight-fee/weight-limit reject oversized proofs before execution; this could not be fully verified from the available code in this session.

### Recommendation
Add an explicit upper bound on the number of signatures/votes accepted in a BEEFY (and equivalent EVM) consensus proof — e.g., reject `signatures_length > authority_set.len` (or some small constant multiple accounting for legitimate duplicate submission patterns) before entering the `secp256k1_recover` loop, mirroring the `MAX_PROOF_DEPTH` bound already used for Pharos SPV proofs. Additionally, confirm that `pallet-ismp`'s `handle_unsigned` weight (and its `ValidateUnsigned::validate_unsigned` cost) scales with the actual number of embedded signatures/votes in the consensus proof, so oversized proofs are rejected/priced correctly by both the weight system and the transaction pool before any cryptographic verification work is performed.

### Proof of Concept
1. Construct a `ConsensusMessage`/`MmrProof` whose `signed_commitment.signatures` vector contains, say, 100,000 `Signature { index: 0, signature: <same 65 bytes> }` entries (duplicates are fine — `check_participation_threshold` only checks length, not distinctness).
2. Set `signatures_length` to exceed the supermajority floor so the threshold check passes.
3. Submit this as `Message::Consensus(...)` via `handle_unsigned` (or let it propagate through gossip, triggering `ValidateUnsigned` on every receiving node).
4. Observe that `verify_mmr_update_proof` performs 100,000 `secp256k1_recover` calls before reaching the merkle multi-proof check that would ultimately reject the bogus authority indices — consuming disproportionate CPU time relative to the extrinsic's declared/paid cost.
