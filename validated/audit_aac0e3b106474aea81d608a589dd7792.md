## Title
Incorrect decimal scaling in `convert_to_erc20`/`convert_to_balance` causes unbacked mint or permanent loss of bridged funds - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `hyper-fungible-token` pallet's decimal-conversion helpers only implement the "scale down" direction of ERC20 ↔ local-balance conversion. Whenever the local asset has *more* decimals than the registered EVM/ERC20 representation (or vice versa, depending on direction), `saturating_sub` silently clamps the scaling exponent to zero instead of applying the compensating multiplication, corrupting the cross-chain amount exactly like the SolverVault `amountLockedUp` bug referenced in the external report.

### Finding Description
`convert_to_balance` and `convert_to_erc20` compute a single-directional scale factor using `erc_decimals.saturating_sub(local_decimals)` (and the reverse), which only ever divides/multiplies — never both: [1](#0-0) 

This is used in two reachable paths that any ordinary user can trigger with a single `send` extrinsic or an incoming cross-chain delivery:

1. **Outbound (`send`)** — `Pallet::send` burns/escrows `params.amount` in local decimals, then computes the ERC20 amount to embed in the dispatched message via `convert_to_erc20(amount, erc_decimals, decimals)`: [2](#0-1) 

   If the registered `erc_decimals` (destination chain's token precision) is *less* than the local asset's `decimals`, `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so `convert_to_erc20` returns the raw local-balance value **unscaled** instead of dividing it down by `10^(decimals - erc_decimals)`. The destination `HyperFungibleToken`/`BridgeToken` contract then mints an amount that is `10^(decimals - erc_decimals)` times larger than what was actually escrowed/burned — an unbacked mint.

2. **Inbound (`on_accept`/`on_timeout`)** — the reverse function `convert_to_balance` is used to credit or refund a beneficiary: [3](#0-2) [4](#0-3) 

   If `erc_decimals` (source chain precision) is *less* than the local `decimals`, the exponent again saturates to `0`, so the raw ERC20 value is credited as-is instead of being scaled **up** by `10^(local_decimals - erc_decimals)` — the beneficiary receives far less than the value that was actually locked/burned on the source chain, permanently losing the difference.

This mirrors the report's root cause precisely: the conversion logic assumes one decimal ordering (source ≥ destination, or vice versa) and has no branch for the opposite case, so any token pair registered with the "wrong" relative decimals (a very common real-world case, e.g. an 18-decimal EVM token bridged against a 6-decimal Substrate asset) breaks amount fidelity in one direction or the other.

### Impact Explanation
Depending on which side has more decimals for a given registered token/chain pair, this causes either:
- **Unbacked mint** on the EVM side (`send` path) — recipients receive vastly more tokens than were actually escrowed/burned on the Substrate side, directly threatening the backing/solvency of the bridged asset, or
- **Permanent freezing/loss of user funds** on the receive/refund path — users are credited or refunded drastically less than what was locked, with the difference stuck in the pallet's custodial account with no recovery path for the user.

Both outcomes are High severity: forged/incorrect message delivery value and unbacked mint (or fund loss) reachable from a single ordinary user transaction (`send`) or from ordinary relayed message delivery (`on_accept`/`on_timeout`), not requiring any privileged/malicious actor.

### Likelihood Explanation
Triggering requires only that a token be registered (via governance's `CreateOrigin`) with `Precisions` values where the local asset decimals and the destination/source ERC20 decimals are in the "unsupported" relative order for either helper — a routine configuration choice, not an attack requiring compromise. Once such a token pair exists, every ordinary `send()` call or every inbound delivery for it is corrupted, so the likelihood of triggering, once a mismatched-decimal token is registered, is effectively certain.

### Recommendation
Rewrite `convert_to_erc20` and `convert_to_balance` to handle both directions of decimal difference explicitly (analogous to `VWAPOracle::_normalizeAmount` in `evm/src/utils/VWAPOracle.sol`, which correctly branches on `decimals < 18` vs `decimals > 18`):
- If `erc_decimals > local_decimals`: divide by `10^(erc_decimals - local_decimals)`.
- If `erc_decimals < local_decimals`: multiply by `10^(local_decimals - erc_decimals)`.
- If equal: no scaling.

Apply this fix symmetrically to both `convert_to_balance` and `convert_to_erc20`, and add regression tests covering both decimal orderings for `send`, `on_accept`, and `on_timeout`.

### Proof of Concept
1. Register a token via the pallet's registration call with `local_decimals = 18` (e.g. an Assets pallet asset with 18 decimals) and `erc_decimals = 6` for a given destination `StateMachine` in `Precisions`.
2. Call `Pallet::send` with `params.amount = 1_000_000_000_000_000_000` (1 token, 18 decimals). The pallet burns/escrows this full amount.
3. `convert_to_erc20(amount, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so `erc20_amount = amount = 1_000_000_000_000_000_000` is dispatched unchanged, instead of the correct `1_000_000` (scaled down by `10^12`).
4. The destination `HyperFungibleToken` contract mints `1_000_000_000_000_000_000` units (in its 6-decimal ERC20) to the recipient — `10^12` times more than the value actually escrowed on the Substrate side, an unbacked mint. [5](#0-4) [6](#0-5)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
