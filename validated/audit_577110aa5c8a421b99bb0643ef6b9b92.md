### Title
Unbounded protocol-fee front-run on `IntentGatewayV2.placeOrder` lets a fee update steal escrowed user funds - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder` reads `_params.protocolFeeBps` (or a per-destination override) *at execution time* and immediately deducts that percentage from the user's escrowed input as an unrecoverable "protocol fee" (`DustCollected`). Because the fee is applied atomically inside `placeOrder` with no user-supplied maximum, a `ParamsUpdate` (or `DestinationFee` override) delivered via `onAccept` between the time a user signs/broadcasts `placeOrder` and the time it is mined can silently raise the fee up to 99.99% (9999 bps), causing the user to escrow nearly all of their input as an irrecoverable fee. This is the same "unbounded, front-runnable fee applied at execution time with no user-specified cap" pattern as the referenced Teller `lenderAcceptBid`/`setMarketFeePercent` finding.

### Finding Description
`placeOrder` computes the fee to charge inline, immediately before escrowing funds: [1](#0-0) 

The fee source, `_params.protocolFeeBps` / `_destinationProtocolFees`, is mutated by governance via `_updateParams`, whose only bound is `< 10_000` (i.e., up to 99.99%): [2](#0-1) 

This update is applied by `onAccept` as soon as a cross-chain governance `UpdateParams` message is verified and delivered — with no timelock or delay between the update landing and it taking effect on the very next `placeOrder` transaction in the mempool: [3](#0-2) 

The protocol's own documentation confirms the deducted fee is **not refundable**, even if the order later expires, receives no bids, or is cancelled: [4](#0-3) 

There is no user-supplied "max acceptable fee" parameter anywhere in `placeOrder`, `Order`, or the SDK's order-building path (`grep` for `maxFee`/`slippage`/`expectedFee` across `evm/src/apps/**` returns no results), so a placer has no way to bound or revert on an unexpected fee at execution time — mirroring exactly the missing protection that the Teller `lenderAcceptBid` report flagged and that was fixed by letting callers specify their expected/max fee.

### Impact Explanation
A user broadcasting `placeOrder` with a large input amount can have up to ~99.99% of that input siphoned into protocol "dust" if a `ParamsUpdate`/`DestinationFee` change lands in the same or an earlier block, with no way to detect or prevent it beforehand. Because the deduction happens unconditionally inside `placeOrder` (not a separate opt-in step) and the fee is never refunded, this is direct, permanent loss of user funds - the same theft-of-funds class as the referenced M-15 finding, reachable from a single ordinary `placeOrder` transaction colliding with a routine (not necessarily malicious) governance parameter change.

### Likelihood Explanation
The only actor that can move `protocolFeeBps` is cross-chain Hyperbridge governance via `onAccept`, and fee changes are an expected, periodic administrative operation (the docs describe "current deployments charge 5 bps," implying the value is expected to be tuned over time). Any legitimate fee adjustment that happens to be in-flight when a user submits `placeOrder` — or an attacker who can influence/observe pending governance messages and time their own `placeOrder`-adjacent transactions — triggers the loss without needing to compromise any keys, exactly as in the original Teller report where the "malicious owner" framing was accepted as a valid design gap rather than a pure privileged-key compromise.

### Recommendation
Add a `maxProtocolFeeBps` (or equivalent minimum-received) parameter to `Order`/`placeOrder` that the placer signs off on, and revert `placeOrder` if the currently effective `protocolFeeBps` (global or destination-specific) exceeds that caller-supplied bound. Optionally also introduce a timelock/delay between `_updateParams` taking effect and its application to new orders, so in-flight `placeOrder` transactions cannot be front-run by a fee change.

### Proof of Concept
1. User submits `placeOrder` escrowing 10,000 USDC, expecting the currently published `protocolFeeBps` (e.g. 5 bps ≈ 5 USDC fee), per [5](#0-4) .
2. Before the user's transaction is mined, a `ParamsUpdate` cross-chain message setting `protocolFeeBps = 9999` is delivered via `onAccept` → `_updateParams`, which only enforces `< 10_000` per [6](#0-5) .
3. The user's `placeOrder` now executes against the new `_params.protocolFeeBps = 9999`, deducting 9,999 USDC (99.99%) as `DustCollected` and escrowing only 1 USDC as the order's real input, per [7](#0-6) .
4. Per the documented behavior, this deducted fee is never refunded even if the order is subsequently cancelled or expires, per [8](#0-7) , resulting in permanent loss of ~9,999 USDC for the user.

```text
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();

        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
```

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

<Callout type="warn">
Do not build an order by reducing the input yourself to account for the protocol fee. Send the gross input amount and use the amounts returned by `quoteIntent()`. The quote prices the fee-reduced escrow amount; reducing it again would make the order smaller than intended.
</Callout>
```
