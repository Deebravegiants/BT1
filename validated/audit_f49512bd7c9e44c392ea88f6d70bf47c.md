### Title
Account authority is bound to the stale `Account.owner` recorded at mint, not to the current position-NFT owner — a sold/transferred account stays under the seller's control while the buyer is frozen out - ([File: contracts/controller/src/account.rs])

### Summary
CVE-2021-22244 is an improper-authorization bug: a permission check read the wrong identity, so an unprivileged user reached data/actions belonging to someone else. The analog lives in the controller's account-authorization model. Every fund-moving entrypoint (`withdraw`, `borrow`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, liquidation `SeizeMode::Credit` receiver check) resolves authorization via `require_owner_or_delegate`, which compares the caller against `account.owner` — the `owner` field written once inside `Account` at `create_account` time [1](#0-0) . But actual account ownership is the position-NFT holder, read from NFT storage via `storage::account_owner` in `require_account_owner` [2](#0-1) . These two identity sources diverge the moment the NFT is transferred or sold.

### Finding Description
`is_owner_or_delegate` returns `true` when `caller == owner`, where `owner` is the `Account.owner` field persisted at account creation [3](#0-2) . `require_owner_or_delegate` panics otherwise [4](#0-3) . `process_withdraw` gates on exactly this check before releasing collateral [5](#0-4) .

Meanwhile, `position-nft` exposes `transfer`/`approve`, and the controller itself uses NFT ownership (`storage::account_owner`, i.e. the live NFT owner) for `require_account_owner` in `renew_account`, `add_delegate`, and `remove_delegate` [6](#0-5) . No code path rewrites `Account.owner` when the NFT moves: the field is set once in `create_account_with` and the only writers of `Account` are position merges that never touch `owner` [7](#0-6) .

So after `nft.transfer(seller → buyer)`:

- The buyer (NFT owner) passes `require_account_owner` but fails `require_owner_or_delegate`, so they cannot `withdraw`, `borrow`, `multiply`, or run any strategy on the account they own.
- The seller — whose address is still baked into `Account.owner` — retains full `require_owner_or_delegate` authority and can `withdraw` all collateral and `borrow` against it to the account's threshold, then walk away.

The delegate list is also keyed to the stale `owner` (`storage::get_delegates(env, account_id, owner)`), so any managers the buyer grants via `add_delegate` are recorded under the buyer's key but the spending check consults the seller's key — grants the buyer makes are inert, and grants the seller made survive the sale.

### Impact Explanation
Theft of user funds / permanent freezing of funds. A seller can list or gift an account NFT, let the buyer pay for it (or inherit it via contract custody, e.g. the defindex strategy vault pattern where accounts are keyed by `from`), then call `withdraw(account_id, withdrawals, to = seller)` — `require_owner_or_delegate` accepts the stale owner, `require_external_recipient` only checks the recipient isn't a protocol contract, and the pool pays out the buyer's collateral to the seller. Conversely, a buyer who acquired the NFT in good faith finds every collateral-moving entrypoint permanently gated to the previous owner; their funds are frozen unless the seller cooperates. Both theft and permanent freezing are in-scope impacts.

### Likelihood Explanation
The triggering action — transferring a position NFT — is an explicitly in-scope unprivileged path (position-nft `transfer`/`approve`). No privileged action, oracle manipulation, or market condition is required: the divergence exists the instant any account NFT changes hands. The only assumption is that NFT transferability is intended (it ships as a public entrypoint and the controller reads live NFT ownership in `require_account_owner`, confirming transfers are a supported flow). Likelihood is high that any secondary sale or custody move triggers it; whether the seller exploits it is adversarial.

### Recommendation
Pick one source of truth for account ownership and use it consistently:

- In `is_owner_or_delegate`/`require_owner_or_delegate`, resolve the owner via `storage::account_owner(env, account_id)` (the live NFT owner) instead of `account.owner`, and key `get_delegates` to that resolved owner.
- Alternatively, drop the redundant `Account.owner` field entirely so no code path can read a stale copy; where the struct needs an owner for events, resolve it at emission time.
- Add a regression test: mint account, supply, `nft.transfer` to a new address, assert (a) the old owner can no longer `withdraw`/`borrow`, (b) the new owner can, and (c) `add_delegate` by the new owner produces an effective delegate for `require_owner_or_delegate`.

### Proof of Concept
```rust
// Setup: pool/controller deployed, asset listed, oracle priced.
let seller = Address::generate(&env);
let buyer  = Address::generate(&env);

// 1. Seller supplies; receives account NFT id N.
let account_id = controller.supply(&seller, &0, &spoke_id,
    &vec![&env, HubPayment { hub_asset, amount: 1_000e7 as i128 }]);

// 2. Seller transfers the account NFT to buyer (e.g., after a sale).
position_nft.transfer(&seller, &buyer, &account_id);

// 3. Buyer tries to withdraw their own collateral.
//    process_withdraw -> require_owner_or_delegate(caller=buyer,
//    account.owner=seller) -> panic GenericError::NotAuthorized.
controller.withdraw(&buyer, &account_id,
    &vec![&env, HubPayment { hub_asset, amount: 0 }], &None);
//    => reverts: buyer's funds are frozen.

// 4. Seller (NFT no longer held) withdraws everything to self.
//    require_owner_or_delegate(caller=seller, account.owner=seller) passes;
//    pool pays `recipient = seller`.
controller.withdraw(&seller, &account_id,
    &vec![&env, HubPayment { hub_asset, amount: 0 }], &None);
//    => succeeds: buyer's collateral is paid out to the seller.
```

Conceptually verified against `contracts/controller/src/account.rs` (`create_account_with`, `is_owner_or_delegate`, `require_owner_or_delegate`, `require_account_owner`) and `contracts/controller/src/positions/supply.rs` (`process_withdraw`). One uncertainty: I did not enumerate every `Account` write site in `storage/account.rs`, so if an NFT-transfer hook exists that resyncs `Account.owner`, this finding would reduce to the inverse inconsistency (delegates keyed under a moved owner). The grep found no `account.owner` mutation outside account creation, so no such resync appears to exist.

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
