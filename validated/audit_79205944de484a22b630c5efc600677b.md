### Title
Bad-debt write-down clamps `supply_index` to a nonzero floor, resurrecting wiped suppliers' claims that drain fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary
Analogous to CVE-2022-23002 — where a computation produces an invalid, improperly reduced output that corrupts downstream operations — `apply_bad_debt_to_supply_index` computes a `reduction_factor` of zero on a full bad-debt wipeout, which should zero the supply index (and all supplier claims), but instead the result is clamped up to `SUPPLY_INDEX_FLOOR_RAW`. The clamped index is an invalid state value: suppliers whose claims were fully written down retain scaled shares that unscale to a positive phantom claim, which later withdraws real tokens belonging to fresh suppliers.

### Finding Description
When unpaid debt is socialized, the function computes:

- `total_supplied_value = supplied * supply_index` (line 74)
- `capped = min(bad_debt, total_supplied_value)` (line 80)
- `reduction_factor = (total - capped) / total` (line 83)
- `new_supply_index = supply_index * reduction_factor`, then `max(SUPPLY_INDEX_FLOOR_RAW)` (lines 84–88)

When `bad_debt >= total_supplied_value` (a complete wipeout reachable through the liquidation/bad-debt seize path, e.g. `contracts/pool/src/ops/seize.rs` invoked from controller `liquidate`/`clean_bad_debt`), `remaining` is zero, `reduction_factor` is zero, and the mathematically correct new index is `0`. The floor clamp instead sets it to `SUPPLY_INDEX_FLOOR_RAW` (`RAY / SUPPLY_INDEX_MIN_DIVISOR`, i.e. ~RAY/1000).

Existing suppliers' scaled shares are unchanged, so `unscale_supply_floor(scaled)` now returns a positive amount even though the entire supplied value was written off — a phantom claim. `require_reserves` only masks this while the pool is empty; once any new deposit lands, the phantom claimant can withdraw real cash. The behavior is demonstrated by the codebase's own tests `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` and `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard` in `contracts/pool/tests/interest.rs` (lines 316–428), which show the wiped position draining exactly a fresh supplier's deposit and leaving the honest claim uncovered.

### Impact Explanation
Theft of user funds / protocol insolvency: an old supplier whose position was fully written down to zero value retains scaled shares backed by the clamped index and can drain subsequent deposits pro-rata ahead of honest suppliers. New suppliers' principal becomes unbacked the moment it is deposited.

### Likelihood Explanation
Reachable by a single unprivileged address: any liquidator can call `liquidate`/`clean_bad_debt` on an underwater position whose residual debt exceeds the collateral seized, invoking the seize path that calls `apply_bad_debt_to_supply_index` with `bad_debt >= total_supplied_value`. This occurs in small/low-liquidity markets or sharp price moves where collateral is insufficient. No privileged role is required. The attacker (the written-down supplier) need only wait for one fresh deposit, or supply into the market themselves and withdraw first to capture the fresh cash.

### Recommendation
On a full wipeout, zero out `supplied` (all scaled shares) along with the index rather than clamping the index to a nonzero floor — e.g., when `capped == total_supplied_value`, set `supplied = 0`, `revenue = 0`, and reset `supply_index` to RAY (or a documented reset base) so old shares are extinguished and cannot unscale to phantom claims. Alternatively, enforce the write-down at the share level: burn `supplied` proportional to the written-down fraction so the floor clamp can never resurrect claims.

### Proof of Concept
Executed in-contract (mirrors `contracts/pool/tests/interest.rs:316-428`):

1. Attacker supplies `1,000,000e7` units into a market → `scaled_A` shares, `supply_index = RAY`.
2. Market accrues bad debt ≥ total supplied value (liquidate an undercollateralized position so the seize path calls `apply_bad_debt_to_supply_index` with `bad_debt = 2,000,000` RAY-scaled units).
3. `reduction_factor = 0`, but `set_supply_index` clamps to `SUPPLY_INDEX_FLOOR_RAW`. `scaled_A` shares still exist.
4. `cache.unscale_supply_floor(scaled_A)` returns a positive `stranded` amount — invalid output from the supposedly zeroed index.
5. Victim deposits `stranded` units (`calculate_scaled_supply` mints `scaled_B` honestly).
6. Attacker calls `controller.withdraw` → `resolve_withdrawal(i128::MAX, scaled_A)` returns `gross == stranded`; `require_reserves` passes because cash now covers it; attacker receives the victim's entire deposit. Victim's `b_claim` can no longer be covered (`cash < b_claim`).
