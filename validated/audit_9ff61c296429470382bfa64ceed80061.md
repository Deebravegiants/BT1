### Title
Webhook `X-Shopify-Shop-Domain` header is unauthenticated, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the webhook HMAC only over the raw request body, then trusts the unsigned `shop-domain` header value when building `WebhookMetadata` and dispatching to the handler. Because the HMAC covers only `@raw_body` and the app's `client_secret` is shared across every shop that installs the app, an attacker who legitimately receives one signed webhook on their own store can replay that unmodified body to the shared webhook endpoint with the `shop-domain` header changed to any victim shop, and the signature check still passes.

### Finding Description
Broken binding: `Utils::HmacValidator.validate(request) == true` should imply `request.shop == <the shop that Shopify actually generated this payload for>`. In this code, that implication does not hold.

- `Request#hmac` reads `X-Shopify-Hmac-Sha256` [1](#0-0) .
- `Request#shop` reads `X-Shopify-Shop-Domain` directly from headers with no cryptographic tie to the signature [2](#0-1) .
- `Request#to_signable_string` returns only `@raw_body` [3](#0-2) .
- `HmacValidator.validate_signature` recomputes the HMAC over `to_signable_string` (i.e., body only) and compares it to the received HMAC [4](#0-3) .
- `Registry.process` gates purely on this body-only HMAC check, then forwards `request.shop` straight into `WebhookMetadata` for the handler to act on [5](#0-4) .

Root cause: the app's `client_secret` (`Context.api_secret_key`) is a single, app-wide secret shared by every shop that installs the app — it is not shop-specific. Since the signature covers only the body and not the shop-domain header, any two requests with the same body and the same app secret produce the same valid HMAC regardless of which shop's header is attached.

Exact attacker flow:
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook subscription (permitted under attacker capabilities).
2. Shopify sends the attacker a legitimately signed POST: body `B`, header `X-Shopify-Hmac-Sha256` = HMAC-SHA256(`B`, app_secret), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays `B` unmodified to the app's shared webhook endpoint, only changing `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `B` with the same app secret and it matches, since headers are not part of the signed content.
5. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, i.e., the handler acts on behalf of the victim shop using data that was never generated for that shop.

No existing guard in this repo closes the gap: `HmacValidator.validate` only checks body integrity/authenticity against the app secret, not shop binding [6](#0-5) ; there is no additional check in `Registry.process` that cross-references `request.shop` against any session or installation record before dispatch [7](#0-6) .

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` to attribute webhook data to a tenant (e.g., updating shop-scoped records, processing `customers/redact`/`shop/redact` payloads, syncing order/product data) can be made to process attacker-controlled, validly-signed content under a victim shop's identity. This is a cross-tenant integrity issue: one tenant's signed data is accepted as another tenant's data, matching the Critical/cross-tenant category. It is fully repeatable against arbitrary victim shop domains (the attacker only needs to know or guess the victim's `.myshopify.com` domain, which is often public) and costs the attacker only one legitimate webhook capture per body/topic they want to forge.

### Likelihood Explanation
Preconditions are the ones explicitly given as in-scope by the attacker model: attacker can create their own development/store install and receive genuinely signed webhooks, and the app exposes a single shared webhook endpoint for all merchants (the documented pattern for this gem). No secrets, tokens, or privileged access are required — only observing headers/body of the attacker's own legitimate webhook traffic and replaying with a modified header. This is low-cost and fully repeatable.

### Recommendation
Do not trust the `shop-domain` header as an authenticated tenant identifier from HMAC validation alone. Either:
- Include the shop domain (and other relevant headers) in the signable content used for a supplementary integrity check performed by the app (not possible to retrofit onto Shopify's own signature scheme), or
- Require `Registry.process` (or documentation/handler contract) to cross-check `request.shop` against an existing, independently-authenticated installation/session record (e.g., a known offline session for that shop) before trusting the payload as belonging to that shop, rather than treating header-derived `shop` as trusted solely because the body HMAC matched.

### Proof of Concept
```ruby
# test/shopify_api/webhooks/cross_tenant_forgery_test.rb
require "test_helper"

class CrossTenantForgeryTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host: "localhost",
      scope: "read_products", is_private: false, api_version: "unstable",
      is_embedded: true, session_storage: ShopifyAPI::Auth::FileSessionStorage.new,
    )
    ShopifyAPI::Webhooks::Registry.clear
  end

  def test_hmac_valid_body_replayed_under_different_shop_header
    body = '{"id":1,"note":"attacker-controlled-data"}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", "secret", body)
    )

    handler = mock
    handler.expects(:handle).with(
      data: kind_of(ShopifyAPI::Webhooks::WebhookMetadata)
    ) do |args|
      # This assertion demonstrates the forged shop is accepted downstream
      assert_equal "victim-shop.myshopify.com", args[:data].shop
      true
    end

    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http,
      path: "/webhooks", handler: handler,
    )

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped from attacker.myshopify.com
        "x-shopify-api-version" => "unstable",
        "x-shopify-webhook-id" => "1",
      },
    )

    # Passes because HMAC only covers `body`; shop header is unauthenticated
    ShopifyAPI::Webhooks::Registry.process(request)
  end
end
```
Both sides of the binding diverge: `HmacValidator.validate(request)` returns `true` (body-only check passes), while `request.shop` (`"victim-shop.myshopify.com"`) is not the shop that Shopify actually generated the payload for (`"attacker.myshopify.com"`) — proving the signature coverage gap.
