### Title
Front-runnable, permissionless `Initialize2` allows permanent blocking of pool creation for a chosen market/account seed - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives the AMM state PDA (and its associated vault/mint/target-orders accounts) from a `market_info` account that the instruction's own comments state can be **any account**, not necessarily a legitimate, market-program-owned account. Any unprivileged caller can invoke `Initialize2` with an arbitrary set of otherwise-valid accounts (mints, vaults, config) but supply the `market_info` key belonging to a market that a legitimate party intends to use later, permanently occupying the deterministic AMM PDA for that seed.

### Finding Description
`process_initialize2` accepts `market_info` and documents it as just a seed: `// Just a seed for AMM account. // Can be any account.` [1](#0-0) [2](#0-1) . This account key is fed into `generate_amm_associated_account`, which derives the AMM account's address deterministically via `get_associated_address_and_bump_seed(program_id, &market_account.key, associated_seed, program_id)` and creates/assigns it only if it is still owned by the system program; otherwise it hard-fails with `RepeatCreateAmm` [3](#0-2) . The same seed-derivation pattern is used to create the LP mint, coin vault, pc vault, and target-orders accounts [4](#0-3) .

Because `market_info` is not validated to be owned by (or created through) any market/order-book program, and there is no requirement that the caller control or be authorized for that market, any unprivileged user can call `initialize2` first using a `market_info` key that a legitimate project intends to use for their pool (e.g., the pubkey of a specific OpenBook market they plan to use, which is public/predictable once the market is created). Once the attacker successfully creates a (possibly worthless/dummy) pool bound to that market key, the PDAs derived from `(program_id, market_key, seed)` are permanently owned by the AMM program, so any subsequent, legitimate `Initialize2` call using the same `market_info` account will hit `AmmError::RepeatCreateAmm` in `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` and revert forever [5](#0-4) [6](#0-5) [7](#0-6) .

This mirrors the reported bug class: a state-registering action (`addQuest`) reachable by more than the intended caller (`owner` or `questBoard`) can be triggered by the "wrong" party first, permanently occupying an ID/slot that the legitimate flow can never reuse (`nextID` collision in `createQuest`). Here, the "registration" is the AMM PDA keyed by an arbitrary market account, and the missing constraint is that `Initialize2` does not verify `market_info` is genuinely tied to/controlled by the caller or a real market program before consuming the seed slot permanently.

### Impact Explanation
Any unprivileged actor can permanently deny a specific market/pool-seed combination from ever being initialized as a legitimate Raydium pool, since the PDA collision is irreversible (no delete/reset path for `RepeatCreateAmm`). This is a permanent denial-of-service against pool creators and, by extension, LPs and traders who would have used that market, satisfying the "permanent freezing" bar (freezing the *ability to create* the pool, and any lamports/rent the attacker spends get locked in a griefing pool). Severity is Medium given the report's own framing: high impact (permanent block), effort required is low (single transaction, attacker-chosen accounts/data).

### Likelihood Explanation
The attack is reachable from a single submitted transaction with attacker-chosen accounts and data (`Initialize2` requires only a signer wallet with funds for mints/vaults/fees and does not require special privileges) [8](#0-7) . The main precondition is that the attacker must front-run the legitimate creator's `Initialize2` call using the same `market_info` pubkey, which is feasible once that market/account key is publicly known (e.g., visible in a not-yet-confirmed transaction, or a market created ahead of time by the legitimate team).

### Recommendation
Require that `market_info` be a genuine, program-owned market account (as documented in the `AmmInstruction::Initialize2` doc comment listing "Market Account. Market program is the owner.") and validate its owner against the expected market program id, rather than accepting "any account" as a bare seed. Alternatively, bind pool creation authorization to a permissioned allow-list or require a signer-derived component in the seed so that arbitrary third parties cannot pre-empt a specific market's pool PDA.

### Proof of Concept
1. Legitimate project creates (or is about to use) OpenBook market `M` and plans to call `initialize2` with `market_info = M`.
2. Attacker observes `M` (e.g., publicly known market address) and, before the legitimate `Initialize2` transaction lands, submits their own `Initialize2` transaction with `market_info = M`, arbitrary (even worthless) mints, and minimal `init_pc_amount`/`init_coin_amount`.
3. `generate_amm_associated_account`/`generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` succeed for the attacker because the PDAs derived from `(program_id, M, seed)` are still system-owned, and get permanently assigned/initialized to the attacker's dummy pool.
4. The legitimate project's subsequent `Initialize2` call using `market_info = M` now fails at the ownership check in `generate_amm_associated_account` (`associated_token_account.owner == system_program_account.key` is false) and returns `AmmError::RepeatCreateAmm`, permanently blocking pool creation for market `M` [9](#0-8) .

    fn generate_amm_associated_account<'a, 'b: 'a>(
        program_id: &Pubkey,
        assign_to: &Pubkey,
        market_account: &'a AccountInfo<'b>,
        associated_token_account: &'a AccountInfo<'b>,
        user_wallet_account: &'a AccountInfo<'b>,
        system_program_account: &'a AccountInfo<'b>,
        _rent_sysvar_account: &'a AccountInfo<'b>,
        associated_seed: &[u8],
        data_size: usize,
    ) -> ProgramResult {
        let (associated_token_address, bump_seed) = get_associated_address_and_bump_seed(
            &program_id,
            &market_account.key,
            associated_seed,
            program_id,
        );
        if associated_token_address != *associated_token_account.key {
            msg!("Error: Associated token address does not match seed derivation");
            return Err(AmmError::ExpectedAccount.into());
        }
        if associated_token_account.owner == system_program_account.key {
            let associated_account_signer_seeds: &[&[_]] = &[
                &program_id.to_bytes(),
                &market_account.key.to_bytes(),
                associated_seed,
                &[bump_seed],
            ];
            let rent = Rent::get()?;
            let required_lamports = rent
                .minimum_balance(data_size)
                .max(1)
                .saturating_sub(associated_token_account.lamports());
            if required_lamports > 0 {
                invoke(
                    &system_instruction::transfer(
                        user_wallet_account.key,
                        associated_token_account.key,
                        required_lamports,
                    ),
                    &[
                        user_wallet_account.clone(),
                        associated_token_account.clone(),
                        system_program_account.clone(),
                    ],
                )?;
            }
            invoke_signed(
                &system_instruction::allocate(associated_token_account.key, data_size as u64),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
            invoke_signed(
                &system_instruction::assign(associated_token_account.key, assign_to),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
        } else {
            associated_token_address.log();
            return Err(AmmError::RepeatCreateAmm.into());
        }
        Ok(())
    }
