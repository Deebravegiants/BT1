### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant/shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC over the raw body only, then trusts the `shop-domain` header (unauthenticated) to identify which merchant the webhook belongs to. This breaks the binding `hmac(payload) == hmac_signed_fields`, because `shop` is acted upon (passed to the app's handler as the tenant identifier) but is not one of the signed fields.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` value, handing it directly to the host application's handler as the trusted tenant identifier: [4](#0-3) 

The gem's own documentation instructs integrators to use `data.shop` as the shop identity for post-processing (e.g., enqueuing a job keyed by `shop_domain: data.shop`), reinforcing that this field is treated as authenticated: [5](#0-4) 

**Attack sequence:**
1. An unprivileged attacker installs the target app on their own store (a normal, legitimate installation) and triggers any webhook topic the app subscribes to (e.g. `orders/create`). Shopify sends a correctly HMAC-signed webhook to the app's callback endpoint, with the correct `shop-domain: attacker-shop.myshopify.com` header and a valid `hmac-sha256` header computed only over the raw body.
2. The attacker captures this legitimate request (body + valid HMAC) and replays it to the app's webhook endpoint, changing only the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to a victim shop's domain, leaving the body and HMAC header untouched.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` — unchanged — so `OpenSSL.secure_compare` succeeds even though the shop header was tampered with.
4. `WebhookMetadata.new(... shop: request.shop ...)` is now built with the victim's shop domain, and the app's handler processes the attacker's payload as if it originated from the victim tenant.

Before the request: `hmac` binds only to `raw_body`; `shop` is an independent, attacker-controlled header. After validation: the app treats `(raw_body, shop=victim)` as an authenticated tuple, even though Shopify never signed that pairing — Shopify only vouches for `(raw_body, shop=attacker)`.

### Impact Explanation
This breaks the tenant/shop identity binding that the whole webhook-processing API is built on: `Registry.process` is the gem's advertised mechanism for verifying "the request did indeed come from Shopify" for a given shop, per its own documentation. Because the shop attribution isn't authenticated, an attacker who can obtain one validly-signed webhook (trivially available to any app installer) can make the host app act on arbitrary payload data while attributing it to any other shop the app has installed on. Depending on the host application's use of `data.shop` (e.g., writing data, invalidating caches, updating billing/subscription state, triggering redaction flows for `customers/redact`/`shop/redact`), this enables cross-tenant data corruption or cross-tenant action under a victim's identity — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High. No secrets are required — HMAC validation still passes because only the body is signed. The attacker only needs the ability to trigger one legitimate webhook for their own (or any) store, which is a routine unprivileged action (installing a free/dev app), and then to replay the captured request with one header changed. This is trivially scriptable/automatable, analogous to the "easy to automate with a bot" characteristic noted in the source report.

### Recommendation
Extend the HMAC-signable payload (or add a secondary integrity check) to bind the `shop-domain` header — and ideally `topic`, `webhook_id`, and `api_version` — into the signature verification, so any tampering with these headers invalidates the HMAC. At minimum, `Request#to_signable_string` should incorporate the shop domain header alongside the raw body, and `Registry.process` should re-derive or cross-check the shop identity against a value that is cryptographically bound to the request rather than trusting a bare header.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop and Shopify sends a legitimately
#    signed webhook, e.g.:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_for_body,   # correctly signed over raw_body
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
raw_body = '{"id":1,"note":"hello"}'

# 2. Attacker replays the same body/hmac but swaps only the shop header:
tampered_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: tampered_headers)

# 3. HMAC validation still succeeds because to_signable_string only returns raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches to the handler with shop: "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#   shop: "victim-shop.myshopify.com", body: {...}, ...))
```
