### Title
Signature computed by `make_signature` is not bound to `signup_id`, allowing attestation replay across signup sessions - ([File: src/plans/enroll_user.rs])

### Summary
`make_signature` in `src/plans/enroll_user.rs` hashes `ORB_ID`, `user_qr_code.user_id`, and the iris/mask codes/versions from `Pipeline`, but never includes the `signup_id`, before calling `secure_element::sign`. Because the signing operation is deterministic (ECDSA over the exact digest, no per-signup nonce or session binding baked into the signed bytes), two signups performed with the same user QR code and identical biometric pipeline output produce byte-identical signatures regardless of `signup_id`.

### Finding Description
`make_signature` builds a SHA-256 context from `ORB_ID`, `user_qr_code.user_id`, and the `v2` pipeline's `ir_net_version`, `iris_version`, and per-eye `iris_code`/`mask_code`/`iris_code_version` [1](#0-0) . The resulting digest is passed to `secure_element::sign`, which only signs the bytes it is given — it has no knowledge of `signup_id` and adds no additional entropy binding the signature to a session [2](#0-1) .

`signup_id` is generated by the caller (`Plan.signup_id: SignupId`) and used only for the HTTP path in `signup_post::request` (`/api/v2/signups/{signup_id}`) and for polling — it is never mixed into the signed payload [3](#0-2) [4](#0-3) .

If an attacker (in control of their own signup flow, e.g. by aborting/restarting a signup with the same user QR code) can trigger two signups where the Orb's iris pipeline output is identical (same `user_id`, same iris/mask codes/versions — plausible for the same eyes captured in close succession, or if the pipeline output is otherwise reproducible), `make_signature` yields the exact same digest, and thus the exact same signature bytes, for both signup attempts. The signature computed under `signup_id` A is therefore also a valid signature to submit under `signup_id` B, since nothing in the signed bytes differs.

### Impact Explanation
This breaks the invariant that a secure-element attestation should be scoped to a specific signup session. It enables cross-signup replay of the Orb's cryptographic attestation of "these iris codes were captured by this Orb for this user," without any binding to the particular `signup_id`/session under which the backend expects it. Depending on backend-side validation (not visible in this repo, since it lives server-side), this could allow a signature legitimately produced for one signup attempt to be replayed to authorize/validate a distinct signup POST, undermining exact signup-to-attestation binding. This matches an attestation-forgery / cross-signup state bleed class of impact under the bounty categories, though whether it results in unauthorized signup depends on additional backend-side session/nonce checks that are outside `orb-core`'s scope.

### Likelihood Explanation
Preconditions are realistic for an unprivileged attacker: only the ability to run their own signup, abort/retry it with the same user QR code, and have the Orb re-derive the same iris/mask codes (plausible for the same eyes across closely-spaced retries) are required — no operator privilege, key leakage, or hardware tampering is needed. The `RETRIES_COUNT` retry loop already resends the same signature to the same `signup_id` on transient failures [5](#0-4) , showing the code path is reachable and signature reuse across POSTs is already an accepted client-side pattern; extending this to different `signup_id`s under attacker control is a straightforward reachability argument once `signup_id` generation/session semantics are attacker-influenced.

### Recommendation
Include `signup_id` (and ideally a per-attempt nonce/timestamp) as part of the bytes hashed in `make_signature` before calling `secure_element::sign`, e.g. `ctx.update(signup_id.as_bytes())`, and thread `signup_id` into the function signature. This ensures the secure-element signature cryptographically commits to the specific signup session and cannot be replayed across different `signup_id` values.

### Proof of Concept
Unit test in `src/plans/enroll_user.rs` (or a new test module) that:
1. Constructs an identical `qr_scan::user::Data` and `Pipeline` (same `user_id`, same `v2` eye codes/versions) twice.
2. Calls `make_signature(&user_qr_code, &pipeline)` twice with the same inputs but conceptually different `signup_id`s (currently not passed into the function at all).
3. Asserts the two returned signature strings are **identical**, demonstrating the digest — and thus the signature — has no dependency on `signup_id`.
4. As a secondary check, calls `make_signature` after modifying only `pipeline.v2.eye_left.iris_code` and asserts the signature *changes*, confirming iris data is bound but the session identifier is not.

Expected assertions:
- `sig_for_attempt_A == sig_for_attempt_B` when only `signup_id` differs (bug demonstrated).
- Signature changes when iris code changes (shows partial correctness of the digest, contrasted with the missing `signup_id` binding).

Note: whether `signup_post::request`/backend-side validation actually rejects a replayed signature across different `signup_id`s cannot be verified from this repository, since backend validation logic is server-side and not present in `orb-core`; this PoC only demonstrates the client-side attestation is not session-bound, which is the scoped root cause identified in the question.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}

/// Signs this buffer with Secure Element and returns the output.
#[cfg(not(test))]
pub fn sign<T: AsRef<[u8]>>(data: T) -> Result<Vec<u8>> {
    fn inner(data: &[u8]) -> Result<Vec<u8>> {
        let encoded = BASE64.encode(data);

        tracing::info!("Running orb-sign-iris-code");
        let mut command = Command::new("/usr/bin/orb-sign-iris-code");
        command.stdin(Stdio::piped());
        command.stdout(Stdio::piped());
        command.stderr(Stdio::piped());
        let mut child = command.spawn().wrap_err("running orb-sign-iris-code")?;

        let mut stdin = child.stdin.take().unwrap();
        stdin.write_all(encoded.as_bytes())?;
        drop(stdin);

        let output = child.wait_with_output().wrap_err("waiting for orb-sign-iris-code")?;
        let success = output.status.success();
        for line in String::from_utf8_lossy(&output.stderr).lines() {
            if success {
                tracing::trace!("orb-sign-iris-code {}", line);
            } else {
                tracing::error!("orb-sign-iris-code {}", line);
            }
        }
        if !success {
            if let Some(code) = output.status.code() {
                bail!("orb-sign-iris-code exited with non-zero exit code: {code}");
            } else {
                bail!("orb-sign-iris-code terminated by signal");
            }
        }
        BASE64.decode(&output.stdout).wrap_err("decoding orb-sign-iris-code output")
    }

    inner(data.as_ref())
}
