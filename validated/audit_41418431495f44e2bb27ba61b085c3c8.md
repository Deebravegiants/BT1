### Title
`fractionalize` non-atomicity permanently locks the caller's NFT and held deposit when `do_create_asset` fails after `do_lock_nft` succeeds - (File: substrate/frame/nft-fractionalization/src/lib.rs)

### Summary
`Pallet::<T>::fractionalize` performs `T::Currency::hold`, `Self::do_lock_nft`, `Self::do_create_asset`, `Self::do_mint_asset`, `Self::do_set_metadata`, and the `NftToAsset` insert as a sequence of independently-fallible operations without `#[transactional]`. If `do_create_asset` fails (e.g. the caller pre-creates an asset with the chosen `asset_id` via the permissionless `pallet_assets::create` extrinsic), `do_lock_nft` and the currency `hold` have already mutated storage and are not rolled back, leaving the NFT permanently transfer-locked and the deposit permanently held with no `NftToAsset` entry to ever `unify` it back.

### Finding Description
`fractionalize` (substrate/frame/nft-fractionalization/src/lib.rs:220-263) executes, in order:
1. `T::Currency::hold(...)` on `nft_owner` [1](#0-0) 
2. `Self::do_lock_nft(nft_collection_id, nft_id)`, which calls `T::Nfts::disable_transfer` — an actual storage write in `pallet-nfts` marking the item's `Locked` attribute [2](#0-1) 
3. `Self::do_create_asset(asset_id, pallet_account)`, which calls `T::Assets::create(...)` [3](#0-2) 
4. Only after all of the above succeed is `NftToAsset` populated [4](#0-3) 

None of these steps, nor the enclosing extrinsic, are wrapped in `#[transactional]` (contrast with the entire call body — no such macro appears on `fractionalize`). In FRAME, an individual dispatchable's storage writes are only automatically rolled back on `Err` if explicitly wrapped in a transactional storage layer (`frame_support::storage::transactional` / `#[transactional]`); by default, storage mutations that occurred before the failing operation persist even though the extrinsic as a whole returns `Err`.

`asset_id` is fully attacker-controlled and `pallet_assets::create` is a normal, permissionless public extrinsic, so any account (including the NFT owner) can create an asset with an ID of their choosing beforehand. When that same owner later calls `fractionalize` with the colliding `asset_id`:
- The `hold` succeeds (deposit reserved).
- `do_lock_nft` succeeds, setting the item's transfer-disabled/`Locked` state in `pallet-nfts`.
- `do_create_asset` fails because the asset ID is already in use, and `fractionalize` returns `Err` at that point.
- Because there is no transactional wrapper, the NFT stays locked (transfer disabled) and the deposit stays held, but `NftToAsset` was never populated.

`unify` (lib.rs:283-317) is the only path that unlocks the NFT and releases the deposit, and it requires a pre-existing `NftToAsset` entry (`NftToAsset::<T>::try_mutate_exists(...).ok_or(Error::<T>::NftNotFractionalized)?`) [5](#0-4) . Since that entry was never created, `unify` will always fail with `NftNotFractionalized`, and there is no other pallet extrinsic that can unlock the NFT or release the hold.

### Impact Explanation
An unprivileged user can permanently freeze their own NFT (its transfer becomes disabled indefinitely in `pallet-nfts` with no unlock path) and permanently lose access to the deposited funds (held via `HoldReason::Fractionalized` with no way to trigger `T::Currency::release`). This violates the "user-controlled assets... cannot be... permanently frozen" invariant. While the specific reachable trigger only harms the caller's own NFT (since `fractionalize` requires `nft_owner == who`), it is a genuine, deterministic, non-privileged, non-mocked logic bug reachable purely through two standard signed extrinsics (`pallet_assets::create` then `nft_fractionalization::fractionalize`), and could also be triggered unintentionally by any ordinary user racing against another asset creator for the same `asset_id`, or by griefing another party who is duped/tricked (e.g. via a UI/tool) into calling `fractionalize` with an `asset_id` the attacker has front-run with `pallet_assets::create`.

### Likelihood Explanation
High feasibility and full repeatability: `pallet_assets::create` is permissionless and asset IDs are chosen by the caller; no special privileges, races against block producers, or leaked keys are needed. The bug triggers deterministically every time `do_create_asset` fails after `do_lock_nft`/`hold` succeed (asset-ID collision is the simplest trigger, but any failure in `do_create_asset`, `do_mint_asset`, `do_set_metadata` after the lock/hold would have the same effect).

### Recommendation
Wrap the entire `fractionalize` (and `unify`, for symmetry) body in `#[transactional]`, or otherwise ensure that `do_lock_nft` and `T::Currency::hold` are only committed once all of `do_create_asset`, `do_mint_asset`, `do_set_metadata`, and the `NftToAsset::insert` have succeeded, so a failure anywhere in the sequence fully reverts the NFT lock and the currency hold.

### Proof of Concept
Rust integration test in `substrate/frame/nft-fractionalization/src/tests.rs` (test setup mirrors existing `fractionalize` tests):
1. Mint an NFT collection/item to `account(1)` via mock `Nfts`.
2. As `account(1)`, call `Assets::create(asset_id, account(1), 1)` to pre-occupy `asset_id`.
3. As `account(1)`, call `NftFractionalization::fractionalize(collection, item, asset_id, account(1), 100)`.
4. Assert the call returns `Err` (e.g. `pallet_assets::Error::InUse`).
5. Assert `NftToAsset::<Test>::get((collection, item))` is `None`.
6. Assert the NFT's transfer-disabled/`Locked` state in the mock `Nfts` pallet is **not** set (expected to fail with current code — this demonstrates the bug: the item remains locked).
7. Assert `Balances::balance_on_hold(&HoldReason::Fractionalized.into(), &account(1))` is `0` (expected to fail with current code — demonstrates the deposit remains held).
8. Additionally show there's no recovery: calling `unify(collection, item, asset_id, account(1))` returns `Error::NftNotFractionalized`, proving the NFT/deposit are stuck permanently.
