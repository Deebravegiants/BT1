### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, but the `shop-domain` header — which the gem treats as the authoritative tenant identifier passed to webhook handlers — is never included in the signed payload. Any party able to obtain one validly-signed webhook payload (e.g., by installing the app on their own store) can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will accept it as authentic, delivering forged tenant identity to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads the `shop-domain` header directly, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the body) and secure-compares it to the received `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates on this HMAC check and then forwards `request.shop` — unauthenticated with respect to the signature — straight into the handler's tenant-identifying metadata: [4](#0-3) 

The broken binding is: `HMAC(api_secret_key, body) == received_hmac` is verified, but `shop-domain header == the shop the body actually belongs to` is never checked. Because Shopify computes webhook HMACs using the app's single `client_secret`, shared across every merchant that installs the app, any unprivileged internet user can install the target app on their own store, capture one legitimately-signed webhook delivery, and replay it with the `shop-domain` header swapped to a victim shop while keeping body and `hmac-sha256` unchanged. `Utils::HmacValidator.validate` still returns `true` because it never looked at the header, and `Registry.process` hands the attacker-chosen `shop` value to the app's handler as if it were authenticated.

### Impact Explanation
Apps built on this gem are expected to key persistence, authorization, and business logic in webhook handlers off `WebhookMetadata#shop` — it is the only tenant identifier the gem exposes for webhook processing. Because that field is outside the HMAC's protection, an attacker who has no relationship to the victim shop can inject fabricated event data (order data, GDPR/customer data payloads, etc.) attributed to the victim's `shop` value, corrupting cross-tenant state or triggering tenant-scoped side effects (e.g., writes keyed by shop domain) under a victim's identity. This is a cross-tenant identity-binding bypass.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target public/embedded app on an attacker-controlled store (ordinary self-serve action, no special privilege), and (2) capturing one webhook delivery from that store to reuse its body+HMAC pair with a substituted `shop-domain` header. No access to the victim's credentials, access token, or the app's `client_secret` is needed, since the secret is shared across all installations of the app and the attacker only needs a signed payload of their own.

### Recommendation
Include the tenant-identifying headers (`shop-domain` at minimum, ideally `topic`, `webhook-id`, `api-version`) in the signable content verified by `Utils::HmacValidator`, or otherwise cryptographically bind the shop domain to the signed body (e.g., HMAC over `"#{shop}\n#{raw_body}"` or an application-level check that the resolved shop matches a shop the HMAC-verified session already expects) before exposing `request.shop` to `WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-owned store `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the raw HTTP request, including `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, and the raw body.
2. Replay the exact same request to the app's webhook endpoint, only changing `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which HMACs only `@raw_body` — unchanged — so validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never touched Shopify's servers for that shop, demonstrating the cross-tenant identity spoof.
