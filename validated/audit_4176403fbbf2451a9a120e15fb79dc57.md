### Title
`Pool::recapitalize` refunds `amount - applied` from pool custody without verifying any tokens were actually received — unfunded "recapitalization" drains supplier cash and leaves the cash book overstating custody - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
`recapitalize` trusts the declared `amount`: it credits `min(amount, shortfall)` to the tracked cash book and then unconditionally transfers `amount - applied` back to the `payer`. No balance delta, allowance pull, or receipt check ties the refund to tokens actually delivered. An unprivileged caller can pass a large `amount`, receive a refund paid out of real pool custody, while the cash book still claims the full `applied` credit. This is the direct analog of CVE-2021-47071's "allocated resource never acquired is still released" shape: the pool releases custody for a receipt it never verified.

### Finding Description
In `accounting` (contracts/pool/src/ops/recapitalize.rs:44-66), the function computes `applied = amount.min(backing_shortfall)` and `refund = amount - applied`, calls `cache.credit_cash(applied)` and `cache.commit()` — committing the book credit before any token movement is validated. `apply` (lines 26-38) then executes `outcome.cache.transfer_out(&payer, outcome.refund)`. The doc comment states "The controller transfers `amount` into the pool before this call," but the pool never measures its token balance, so nothing enforces that contract.

The repository's own regression test demonstrates the primitive: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (contracts/pool/tests/flows.rs:3405-3483) calls `client.recapitalize(&hub(&t.asset), &payer, &custody)` with no transfer-in, observes `token.balance(&t.pool) == 0` ("custody is gone"), while `state.cash` still covers a legitimate supplier's deposit. The supplier's `withdraw` then passes the pool's `require_reserves`/solvency guards (which read the book, not the balance) and fails inside the SAC transfer with `BalanceError = 10` — "The market reports itself solvent and cannot pay."

This contrasts with the flash-loan path, which enforces an exact post-callback balance target (`test_flash_loan_callback_failure_rolls_back_pool_state`, flows.rs:1254-1278) — `recapitalize` is the one settlement verb with no measured receipt.

### Impact Explanation
Two compounding losses reachable by any address that can call `recapitalize`:

1. Theft of user funds: the `refund` leg pays out `amount - applied` in real tokens to `payer`. With `amount` chosen far above the shortfall, the attacker extracts up to the pool's full token balance.
2. Permanent insolvency accounting: `credit_cash(applied)` books cash that was never received. The cash book overstates custody, so `backing_shortfall` reports zero and `recapitalize` refuses further fills ("A fully backed market accepts no fill"), while withdrawals revert inside the token transfer — suppliers' funds are frozen/stranded behind a solvent-looking book.

### Likelihood Explanation
The path requires no price moves, no multi-account setup, and no privileges if the pool entrypoint is reachable directly — the test invokes it on the bare pool client with an arbitrary `payer`. Even if production wiring routes calls through the controller's `recapitalize` entrypoint (listed as a user-reachable verb), the missing receipt measurement means the safety of the refund depends entirely on the upstream caller's transfer ordering rather than on pool-enforced settlement, and any path that reaches the pool without the pre-transfer (router strategy, callback, or auth-tree gap) becomes a drain. Severity is bounded by the market's tracked cash on a single hub asset per call.

Caveat I could not fully resolve within the index: whether `Pool::recapitalize` performs its own `require_auth`/invoker check restricting it to the controller. The in-repo test calls it directly without funding, which indicates no custody check and no blocking auth in the test environment; if the production auth model gates it to the controller only, exploitation narrows to flows where the controller invocation is reached without its transfer leg.

### Recommendation
Make settlement measured rather than declared:

- Snapshot `token.balance(pool)` before crediting, or require the payer to pre-fund and compute `received = balance_after_transfer_in - balance_before`; cap `applied` and derive `refund = received - applied` (mirroring the flash-loan exact-balance settlement).
- Alternatively, pull the funds inside `recapitalize` (`token.transfer(payer → pool, amount)` or `transfer_from` with `require_auth`) so the credit cannot commit without custody.
- At minimum, add a post-commit assertion `token.balance(pool) >= cache.cash()` before paying the refund, reverting the whole call otherwise.

### Proof of Concept
Straight from the in-repo test (contracts/pool/tests/flows.rs:3405-3483), which the maintainers wrote to document this shape:

```rust
let token = token::Client::new(&t.env, &t.asset);
let payer = Address::generate(&t.env);   // holds nothing, transfers nothing

// Legitimate supplier deposited `deposit`; book == custody.
let custody = token.balance(&t.pool);

// Unfunded recapitalize: refund = custody - applied pays the "payer".
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);              // custody drained
assert!(t.state_snapshot().cash >= deposit);        // book still solvent

// Supplier's withdraw passes the pool's liquidity guards, then reverts
// inside the SAC transfer (BalanceError = 10) — funds frozen.
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err());
```

Repeatable once per market; no oracle, keeper, or admin cooperation needed.
