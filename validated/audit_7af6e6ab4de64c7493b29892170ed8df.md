### Title
ERC20 `transfer` boolean return value ignored in `IntentGatewayV2.withdraw()`/`SweepDust` handling on Tron - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` moves escrowed ERC20 payouts using raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the low-level `call` itself did not revert, never decoding or validating the boolean success value returned by the token's `transfer` function. Every other ERC20 movement in this codebase (`safeTransfer`/`safeTransferFrom` in `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`, `sdk/.../WrappedHyperFungibleToken.sol`, `EvmHost.sol`) correctly uses OpenZeppelin's `SafeERC20`, confirming this is a deviation specific to the Tron contract's `withdraw()` and `onAccept`'s `SweepDust` branch.

### Finding Description
`withdraw()` releases escrowed order tokens to a beneficiary after a `RedeemEscrow`/`RefundEscrow` message is delivered via ISMP from the source chain gateway: [1](#0-0) 

and the `SweepDust` handler pushes protocol dust to a beneficiary the same way: [2](#0-1) 

Both paths do `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...)); if (!success) revert TransferFailed();`. For any token that returns `false` on failure instead of reverting (e.g. legacy/non-compliant ERC20s, or a token deliberately designed to short-circuit and return `false`), the low-level `call` still reports `success = true` because the external call did not revert — only the ABI-encoded return data (the boolean) is `false`. Since that return data is discarded (`(bool success,)`), the contract treats the transfer as successful.

Despite the actual token transfer failing, the escrow accounting is unconditionally decremented right after: [3](#0-2) 

and fee accounting/deletion likewise proceeds unconditionally: [4](#0-3) 

This path is reached from an unprivileged, relayer-driven entry point: any relayer can deliver a proven ISMP POST request carrying `RequestKind.RedeemEscrow`/`RefundEscrow`, which the host forwards to `onAccept` → `withdraw()`: [5](#0-4) 

### Impact Explanation
If the escrowed token silently returns `false` on transfer failure, the beneficiary receives nothing, yet `_orders[commitment][token]` is decremented (and, on finalize, transaction fees are deleted) as if payment succeeded. The order is marked filled/refunded and the tokens remain permanently stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them (the escrow entry is already zeroed), causing a permanent loss of user/solver funds for that order. This satisfies the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Exploitation only requires the escrowed token to be a non-standard ERC20 that returns `false` instead of reverting on transfer failure (a known class of real-world tokens), combined with a transfer failure condition (e.g., blacklist, paused state, insufficient allowance/edge case in a specific token implementation). No privileged role is needed — any relayer delivering the standard `RedeemEscrow`/`RefundEscrow`/`SweepDust` message triggers the vulnerable code path once such a token is configured as an order's input/fee token.

### Recommendation
Replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (e.g. `evm/src/apps/intentsv2/IntentsBase.sol` lines 465-469, 472-477), so that both a reverting call and a token returning `false` are treated as failures.

### Proof of Concept
1. Deploy an ERC-20 mock whose `transfer()` returns `false` (without reverting) once a configurable failure flag is set, and use it as an order's input token in `IntentGatewayV2` (Tron variant).
2. Create and open an order with this token; escrow accounting records `_orders[commitment][token] = amount`.
3. Set the mock token's failure flag so `transfer()` returns `false`.
4. Have a relayer deliver a `RedeemEscrow` POST request for the commitment; `onAccept` → `withdraw()` executes `token.call(...)`, which returns `success = true` (call didn't revert) even though the encoded boolean is `false`.
5. Observe: beneficiary's token balance is unchanged, but `_orders[commitment][token]` is decremented to zero and `EscrowReleased` is emitted — the tokens are now stuck in the contract with no way to withdraw them again for that commitment.
