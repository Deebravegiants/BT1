## Title
Webhook HMAC only signs the raw body, letting the unauthenticated `shop-domain`/`topic` headers be forged to impersonate another tenant - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` entirely from HTTP headers, but `to_signable_string` — the value actually protected by the HMAC check in `Registry.process` — is only the raw request body. [1](#0-0)  The identity field (`shop`) that downstream app code relies on to attribute the webhook to a tenant is never bound into the signed bytes.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it to the `hmac` accessor: [2](#0-1)  For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, and `webhook_id` are read straight from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are never included in the signable string. [3](#0-2) 

`Registry.process` validates the HMAC and then, without any additional binding, forwards `request.shop` and `request.topic` verbatim into `WebhookMetadata`, which is handed to the app's handler as the authoritative tenant identity for the event: [4](#0-3) 

The break is the same class as the reported bug: the bytes that are *verified* (`raw_body`) are not the same as the bytes that are *parsed and trusted for identity* (`shop`/`topic` headers). Concretely:

`verified(HMAC) = HMAC_secret(raw_body)` while `trusted_identity = header["shop-domain"]`, and there is no equality constraint tying the two together.

Exploit path: the app's `client_secret` (used as the shared HMAC key) is identical for every shop that installs the app — it is not per-tenant. An attacker who controls any shop where the app is installed (an ordinary, unprivileged merchant) can trigger a real webhook delivery to capture a body + valid HMAC pair, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), so `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: ..., body: attacker_controlled_json, ...)`.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to select which tenant's records to update/delete (a standard and documented usage pattern shown in `docs/usage/webhooks.md`) can be made to perform actions attributed to a shop the attacker does not control — e.g. forging `app/uninstalled` to wipe a victim shop's stored session, or injecting attacker-controlled JSON body content as if it came from the victim shop. This is a cross-tenant identity-binding break rooted entirely in this gem's webhook verification API, not in host-application misuse of an undocumented feature — the gem's own `Request`/`Registry` never ties body-integrity to header-derived identity.

### Likelihood Explanation
Requires only: (1) the app be installed on at least one shop controlled by the attacker (a normal unprivileged install, not a leaked credential), and (2) the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which is by design internet-reachable). No access token, `client_secret`, or privileged account is needed beyond what any regular merchant already has by installing the app.

### Recommendation
Bind the header-derived identity fields into the signed material, or independently verify that the `shop-domain` header matches a shop known to have received this specific delivery (e.g., cross-check against the `webhook_id`/API delivery records via the Admin API), instead of trusting the raw header value returned by `Request#shop`/`Request#topic` after only a body-HMAC check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header (HMAC computed with the app's shared `client_secret`).
2. Attacker POSTs the same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`, e.g. `app/uninstalled`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — validation passes: [5](#0-4) 
4. The handler is invoked with `shop: "victim-shop.myshopify.com"`, causing the app to act as though the event originated from the victim's store.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
