### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`/`api_version`) values that the gem hands to the app's handler are read directly from unauthenticated HTTP headers that are never included in the signed material. This breaks the equality the app relies on: `shop_identity_used_by_handler == shop_identity_actually_authenticated_by_hmac`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the raw body) using the app's shared `api_secret_key`, and never touches the headers: [3](#0-2) 

`Registry.process` checks that HMAC and then immediately forwards `request.shop`, an unauthenticated header value, to the app's handler as the tenant identity, without any additional binding check: [4](#0-3) 

Because `api_secret_key` is a single shared secret for the whole app (not per-shop), a valid `(raw_body, hmac)` pair computed for one shop's webhook is cryptographically valid for *any* shop label placed in the `shopify-shop-domain` header — the signature carries no shop-specific binding at all. The library's own documentation instructs apps to trust `data.shop` directly for tenant routing (e.g. `shop_domain: data.shop`) without ever telling the app to cross-check the header against anything else: [5](#0-4) 

### Impact Explanation
An attacker who is a normal, unprivileged merchant of the app (or who otherwise can trigger any webhook whose body content they control, e.g. by editing their own store's orders/products which fires `orders/create`/`products/update` webhooks with attacker-influenced JSON) can capture a legitimately-issued `(raw_body, x-shopify-hmac-sha256)` pair for their own shop, then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will report success (the body/HMAC pair is genuinely valid for the shared app secret), and `Registry.process` will dispatch the handler with `shop` set to the victim's domain and attacker-controlled `body`. Any app that uses `data.shop` to key writes (order sync, inventory updates, per-tenant database rows, job dispatch as shown in the gem's own docs example) will have attacker-controlled data injected under another tenant's identity — a cross-tenant data-integrity/isolation break, satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) the ability to send an HTTP POST to the app's public webhook endpoint (any internet user, since that endpoint is public by design), and (2) access to one valid `(body, hmac)` pair produced under the app's shared secret — obtainable by any merchant who has the app installed on their own store and can trigger a webhook whose body they can shape. No access token, `client_secret`, or TLS interception is required, matching the "unprivileged internet user" threat model. The header-vs-signed-body mismatch is a structural property of `Request`/`HmacValidator` as implemented in this gem, not merely a documentation-ignoring mistake by the host app — the gem's own docs actively encourage trusting the unauthenticated `shop` field.

### Recommendation
Bind the shop identity (and ideally topic/webhook id) into the material that is verified, or provide/require an explicit secondary check: e.g., include the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers in the HMAC-covered signable string used by `HmacValidator`/`Request#to_signable_string`, or add a mandatory app-side callback to `Registry.process` that verifies `request.shop` against the set of shops for which that webhook was registered (since `register`/`register_all` are called per `session`) before invoking the handler.

### Proof of Concept
1. App registers webhook handler for `orders/create` and, per the gem's documented pattern, calls `perform_later(shop_domain: data.shop, ...)`.
2. Attacker installs the app on `attacker.myshopify.com` and creates an order with a crafted body (or observes a natural webhook delivery), capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent by Shopify (valid because `H = HMAC-SHA256(api_secret_key, B)` and `api_secret_key` is the same for every shop of this app).
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) returns `true` because it only checks `B`/`H` against the shared secret.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's body, and invokes the handler — the app now processes attacker-controlled data as if it came from `victim-shop`.

Note: I could not locate a `WebhookMetadata` class definition file in the indexed content (only its usage in `registry.rb`); this doesn't affect the finding, which is rooted in `Request`/`HmacValidator`, but if you need to inspect `WebhookMetadata` exactly, a full Devin session with complete repo access would be needed to confirm there is no additional validation there.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
