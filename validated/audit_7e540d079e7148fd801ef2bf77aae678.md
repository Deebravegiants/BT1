### Title
Unbounded solver payout from a flash-loan-manipulated Uniswap V4 spot price with the overfill clamp disabled - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
`FXFiller` (the Simplex intent-solver reference implementation) prices "venue" trading pairs directly off a Uniswap V4 pool's live spot tick, with no swap-impact or depth adjustment, and its only defense — a static `referencePrice`/`maxDeviationBps` guard — is optional and, even when configured, is checked against a fixed band rather than execution cost. Separately, the per-leg overfill clamp that used to cap payout at `(1 + maxOverfillBps) × userRequested` has been explicitly disabled: it now only logs a warning and lets the fill proceed at the raw, unclamped `policyMaxOutput`. An attacker who flash-loan-manipulates the referenced pool's tick — the same technique used in the reported LML/USDT incident — can place or trigger an intent order that gets priced off the distorted tick and drains the solver's inventory for tokens worth far more than what the order actually delivers.

### Finding Description
Venue pricing resolves a leg's rate straight from the pool's raw mid, derived from `sqrtPriceX96`, with no fee-tier or size/impact adjustment: [1](#0-0) 

`resolveLegRates` pulls this pool price for any curveless pair and only rejects it if a `checkPriceGuard` is configured for that chain — which is optional configuration, and even when present is a static-reference band check, not a manipulation-resistance check: [2](#0-1) [3](#0-2) 

Critically, the per-leg overfill protection that historically bounded loss from exactly this scenario — "a bug / stale cache / manipulated venue price" — has been deliberately disabled. The computed `rawPolicyMaxOutput` (derived from the manipulated pool rate) is used verbatim as `policyMaxOutput`, with the ceiling check downgraded to a warning log only: [4](#0-3) 

This mirrors the reported incident's root cause precisely: a price input reachable/movable by an unprivileged actor (flash-loan-inflated AMM spot price) feeds a payout-calculation path whose only safety bound has been removed/weakened (LML's 3600s stale-price cooldown vs. Hyperbridge's disabled overfill clamp), letting the attacker extract value far beyond what a correct price would allow.

### Impact Explanation
Any order routed to a solver running the shipped `FXFiller` strategy against a Uniswap V4-priced pair can be filled at an attacker-manipulated rate with no upper bound on the solver's loss (the clamp is disabled, not merely widened). This is a direct, concrete theft of solver-held funds (or, if the guard is left unconfigured for a chain — the guard is opt-in and validation only requires setting both fields together, not that they be set at all — no manipulation detection exists whatsoever). Given the shipped default config and documented Uniswap V4 venue pricing is a first-class, reachable path for solvers/fillers participating in the Intent Gateway, this is a Medium/High-severity theft-of-funds analog reachable by a single order placer combined with a flash-loan pool manipulation.

### Likelihood Explanation
Likelihood is high for solvers using pool-based (curveless) pricing without a configured `referencePrice`/`maxDeviationBps` guard (an entirely valid, documented configuration), and non-trivial even with a guard configured, since the guard only bounds deviation from a stale static reference rather than bounding execution cost/slippage, and does not account for swap-fee/size impact at all. The overfill clamp removal was a deliberate code change (explicitly commented as disabling a previous defense), so the vulnerable state is the current, intended behavior of the codebase — not a latent edge case.

### Recommendation
- Re-enable and enforce the overfill ceiling (`maxOverfillBps`) as a hard clamp rather than a warning-only path, at minimum for venue-priced (`priceSource === "venue"`) legs.
- Make the Uniswap V4 price guard (`referencePrice`/`maxDeviationBps`) mandatory whenever pool-based pricing is used for a pair, rather than optional.
- Incorporate swap-size/impact and fee-tier into `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` instead of extending the raw mid linearly across the whole quantity, and/or require a TWAP or multi-block price rather than the instantaneous tick to resist flash-loan manipulation.

### Proof of Concept
1. Solver configures a curveless (venue-priced) pair backed by a Uniswap V4 position with no `referencePrice`/`maxDeviationBps` guard (a documented, supported configuration) — see [5](#0-4) .
2. Attacker flash-loans into the referenced V4 pool to move `sqrtPriceX96` far from fair value.
3. Attacker (or anyone) places an intent order on that pair; `resolveLegRates`/`referenceRate` read the manipulated tick straight into `rate` with no guard rejecting it — [6](#0-5) .
4. `computeLegPolicyOutput`'s resulting `rawPolicyMaxOutput` at the distorted rate is passed through unclamped, since the overfill ceiling check is warning-only — [7](#0-6) .
5. The solver pays out its real inventory at the fictitious rate; attacker unwinds the flash loan and repays it, keeping the difference — the solver absorbs the loss.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.
