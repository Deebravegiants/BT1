### Title
Webhook `shop` and `topic` identity fields are trusted from unauthenticated HTTP headers while the HMAC signs only the raw body, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string as the raw body only [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never part of the HMAC computation [2](#0-1) . `Registry.process` validates only the HMAC of the body, then forwards the unauthenticated `request.shop` and `request.topic` header values as trusted identity into the handler [3](#0-2) . This breaks the identity binding: **shop/topic asserted in headers ≠ shop/topic actually authenticated by the HMAC**.

### Finding Description
The HMAC validator (`Utils::HmacValidator.validate`) computes the signature over whatever `to_signable_string` returns for the given `VerifiableQuery` [4](#0-3) . For webhook requests, `to_signable_string` returns `@raw_body` exclusively [1](#0-0) , so the HMAC proves only "this body was signed with the app's `client_secret`" — it says nothing about which shop or topic the sender intended.

`WebhookMetadata`, which handlers receive as the authoritative record of the webhook, is populated directly from the unauthenticated `shop-domain` and `topic` headers [5](#0-4) [6](#0-5) . Because these headers are not covered by the signature, any party who possesses one valid `(raw_body, hmac)` pair signed with the app's secret — for example, a merchant who installed the app and received a genuine webhook for their own store — can resend that exact body+HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` and/or `shopify-topic` headers to claim a different shop or a different (possibly more sensitive) topic. `Utils::HmacValidator.validate` still returns `true` because it only recomputes the signature over the unchanged raw body [7](#0-6) , and `Registry.process` dispatches the forged shop/topic straight to the app's handler as if it were authentic.

This is precisely the identity-binding bypass pattern from the analog report: a field that is *acted upon* (here, `shop`/`topic`, used by the app to select tenant data and business logic) is not *covered* by the authenticity check (the HMAC), so an attacker can present a value on one side of the check that diverges from what was actually verified on the other side.

### Impact Explanation
Any host application that follows this gem's documented API and trusts `WebhookMetadata#shop`/`#topic` to select or scope tenant data (the intended and only reasonable use of these fields, per `lib/shopify_api/webhooks/webhook_handler.rb`) can be made to apply attacker-controlled webhook data to the wrong shop's tenant, or process it under an unintended topic/handler. This is a cross-tenant data-integrity break: data destined for shop A can be attributed to and processed as if it originated from shop B, without any credentials for shop B, purely because the gem never binds the header-derived `shop`/`topic` to the HMAC-authenticated payload.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair produced by the app's own `client_secret` — trivially available to anyone who installs the target app on their own (even free) Shopify development store and captures a real webhook delivery. No access token, `api_secret_key`, or privileged account is required; only ordinary use of the app as an unprivileged merchant/tenant, followed by a direct POST to the app's public webhook endpoint with modified headers. This is a realistic, low-effort attack path entirely within an unprivileged internet user's reach.

### Recommendation
Bind the signature to the identity fields, not just the body: include `shop`, `topic`, and `webhook_id` (or a canonicalized representation of the full header set Shopify actually signs) inside `to_signable_string`, or re-derive `shop`/`topic` only from data verified to be internally consistent with the signed payload rather than trusting the raw headers unconditionally. At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` must not be treated as authenticated unless the header source is corroborated against out-of-band registered webhook subscription state.

### Proof of Concept
```ruby
# Attacker is a merchant with the target app installed on their own shop "attacker.myshopify.com".
# They receive one genuine webhook delivery:
raw_body = '{"id": 123, "note": "attacker-controlled content"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)
# (This hmac was legitimately generated by Shopify for shop "attacker.myshopify.com".)

# Attacker replays the SAME body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain (and/or topic) header to a victim shop:
forged_headers = {
  "shopify-topic" => "orders/create",              # possibly a different, more sensitive topic
  "shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com",  # <-- forged identity
  "shopify-webhook-id" => SecureRandom.uuid,
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (it only checks raw_body against the shared secret).
# => handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker content>)
# The app now processes attacker-controlled data as if it belonged to "victim-shop.myshopify.com".
```
