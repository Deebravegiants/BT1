### Title
Front-runnable deterministic lockup account address in `LockupFactory::create` allows griefing/DoS of legitimate vesting-lockup deployment - (`File: lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` is a public, unprivileged, payable method that deploys a new lockup contract at an account ID that is **deterministically derived only from the `owner_account_id` parameter**, independent of the caller, the deposit amount, or any other argument. Because NEAR account creation permanently fails if the target account already exists, any unprivileged attacker can pre-emptively call `create()` for a victim's `owner_account_id` with attacker-chosen (e.g. empty/short) vesting parameters, permanently occupying that address and preventing the legitimate/admin-driven creation of the real vesting/lockup contract for that employee.

### Finding Description
In `lockup-factory/src/lib.rs`, the `create` function computes the target account deterministically: [1](#0-0) 

```rust
#[payable]
pub fn create(
    &mut self,
    owner_account_id: ValidAccountId,
    lockup_duration: WrappedDuration,
    lockup_timestamp: Option<WrappedTimestamp>,
    vesting_schedule: Option<VestingScheduleOrHash>,
    release_duration: Option<WrappedDuration>,
    whitelist_account_id: Option<ValidAccountId>,
) -> Promise {
    assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

    let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
    let lockup_account_id =
        format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
    ...
``` [2](#0-1) 

There is no restriction on who can call `create()` — any unprivileged account can call it as long as it attaches `MIN_ATTACHED_BALANCE` (3.5 NEAR) [3](#0-2) . Since `lockup_account_id` depends solely on `owner_account_id` (via `sha256`), the resulting account name is fully predictable and identical no matter who the caller is or what vesting/lockup terms they specify.

This mirrors the root cause class of the reported Alchemix `Bribe.swapOutRewardToken` bug: an unprivileged actor can pre-empt a state slot (there: a `rewards[]` array entry keyed by token address; here: a NEAR account keyed by `sha256(owner_account_id)`) that an authorized party (there: the admin calling `Voter.swapReward`; here: the foundation/HR/admin calling `create()` to set up a real employee vesting lockup) needs to write to, causing the authorized party's transaction to permanently fail once the slot is occupied.

Because NEAR account creation is a one-time, irreversible operation (`Promise::new(lockup_account_id).create_account()...`), once an attacker front-runs the address with a minimal deposit and no/degenerate vesting schedule, the legitimate lockup deployment for that specific `owner_account_id` can never be redone at that address — the on-chain callback `on_lockup_create` [4](#0-3)  only refunds the deposit if the promise fails; it does not recover the address.

### Impact Explanation
This falls under the in-scope impact: "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release, vesting termination... flows." An unprivileged attacker, without needing any profit motive, can permanently deny a specific employee/owner their intended vesting lockup contract by squatting the deterministic address with a minimal deposit, blocking the legitimate lockup-factory-driven deployment forever (the account name is permanently consumed on-chain). This is a direct, protocol-level griefing/DoS analogous to the reported Bribe.sol issue, not a self-harm or misconfiguration scenario.

### Likelihood Explanation
Likelihood is high: the attack requires no special privileges, only knowledge of the target `owner_account_id` (which is typically known ahead of time, e.g. an employee's NEAR account) and the minimum attached deposit of 3.5 NEAR. The deterministic derivation via `sha256(owner_account_id)` makes the target address fully computable off-chain in advance by anyone.

### Recommendation
Bind the derived `lockup_account_id` to additional caller/admin-controlled entropy (e.g., include `predecessor_account_id`, a nonce, or restrict `create()` to be callable only by the foundation/admin account), or require the target `owner_account_id`'s consent (e.g., via a pre-registered allow-list) before allowing account creation at the deterministic address, so an unprivileged third party cannot pre-empt the slot with degenerate parameters.

### Proof of Concept
1. Foundation intends to create a real vesting lockup for `owner_account_id = alice.near` with a proper `vesting_schedule`.
2. Before the foundation's transaction lands, an attacker (any unprivileged account) computes `lockup_account_id = sha256("alice.near")[..20] || "." || factory_account_id` off-chain, and calls:
   `lockup-factory.create({owner_account_id: "alice.near", lockup_duration: 0, vesting_schedule: None, release_duration: None})` with `MIN_ATTACHED_BALANCE` attached, from an unrelated attacker account.
3. `Promise::new(lockup_account_id).create_account()...` succeeds and the deterministic account is created and initialized with attacker-chosen (degenerate) terms.
4. When the foundation's legitimate transaction for the same `owner_account_id` executes afterward, `create_account()` on the same (now-existing) `lockup_account_id` fails at the runtime level, and `on_lockup_create` [5](#0-4)  only refunds the deposit — the intended vesting lockup for `alice.near` can never be created at that address again.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
