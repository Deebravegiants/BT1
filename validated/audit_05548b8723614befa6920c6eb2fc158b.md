### Title
Predictable, Unvalidated PDA Derivation for AMM Pool Enables Front-Running/Squatting of `Initialize2` - (File: `program/src/processor.rs`)

### Summary
The `DaosLive::finalize()` bug stems from a contract address being fully predictable via `CREATE` before deployment, letting an attacker pre-seed a Uniswap pool at that address and later drain the protocol's real liquidity. Raydium's `process_initialize2` has the same structural weakness: every account that constitutes a new AMM pool (`AmmInfo`, LP mint, coin/pc vaults, target orders) is deterministically derived **solely from the `market` account's pubkey** via `find_program_address`, and the instruction explicitly treats `market_info` as an arbitrary, unvalidated account ("Just a seed for AMM account. Can be any account.").

### Finding Description
`get_associated_address_and_bump_seed()` computes every pool-related address as:
```
find_program_address(&[program_id, market_address, associated_seed], program_id)
``` [1](#0-0) 

This function is used to derive the `AmmInfo` account, the LP mint, the coin/pc vaults and the target-orders account, all keyed only by `market_account.key` and a constant seed suffix — never by the actual coin/pc mints or by any cryptographic proof that `market_info` is a genuine OpenBook market: [2](#0-1) 

Critically, `process_initialize2` never validates that `market_info` is owned by the OpenBook/market program or that it corresponds to the coin/pc mints supplied — the instruction docs and inline comments confirm this is deliberate ("Just a seed for AMM account. Can be any account."): [3](#0-2) [4](#0-3) 

The only guard against re-initialization is `generate_amm_associated_account`/`generate_amm_associated_spl_mint`, which check whether the target PDA is still owned by the system program; if not, they return `AmmError::RepeatCreateAmm` and abort: [5](#0-4) 

Because the market pubkey for a given token pair is typically known publicly ahead of the official `Initialize2` call (it must be created and announced/used before the pool-creation transaction is submitted), an attacker can precompute the exact `AmmInfo`/vault/LP-mint addresses in advance — exactly as the original report's attacker precomputes the `CREATE`-based token address — and race the legitimate pool creator's `Initialize2` transaction with their own, supplying arbitrary mints and a skewed `init_coin_amount`/`init_pc_amount` ratio.

### Impact Explanation
- **Permanent squatting / DoS of the legitimate pool**: once the attacker's `Initialize2` succeeds for that `market`, all of the PDA-derived accounts are irreversibly claimed (owner ≠ system program), so any subsequent legitimate `Initialize2` call for the same market fails with `AmmError::RepeatCreateAmm`. The intended pool for that market can never be created — a permanent freeze of the protocol's ability to list that market.
- **Fund loss / manipulated pricing for unaware integrators**: since the AMM address for a market is deterministically derivable off-chain, tools, bots and users that compute it directly (rather than through a registry) will interact with the attacker-controlled pool, depositing/swapping real tokens against an attacker-set skewed price ratio, mirroring the WETH-drain mechanic in the original report where real liquidity is captured against a spoofed asset.
- This qualifies as concrete theft/permanent freezing of user/LP funds reachable purely from `Initialize2`, callable by any unprivileged party with attacker-chosen accounts and data.

### Likelihood Explanation
`Initialize2` is a fully public, permissionless instruction; no signer other than the caller's own wallet is required, and the accounts checked (`amm_config`, `amm_authority`, `create_fee_destination`, spl/system program IDs) are all program-invariant, not market-specific. The `market` pubkey for an upcoming pool is routinely known before the pool-creation transaction lands (e.g., published by the market/AMM creator, or observable on-chain as soon as the OpenBook market itself is created), giving an attacker ample lead time to front-run with a single transaction containing attacker-chosen mints and amounts.

### Recommendation
Bind the derived PDA seeds (or add an explicit on-chain check) to something the legitimate creator controls and that cannot be replayed by a third party — e.g., require `market_info.owner` to equal the expected market/OpenBook program and validate the market's base/quote mints match `amm_coin_mint_info`/`amm_pc_mint_info` before allowing account creation, and/or incorporate the creator's own signer pubkey into the seed derivation so an unrelated third party cannot pre-compute and claim the same PDA set for a market they do not control.

### Proof of Concept
1. Attacker observes/derives the `market` pubkey that a legitimate team is about to use for `Initialize2` (e.g., from the newly-created OpenBook market, before the team's pool-creation tx lands).
2. Attacker computes `AmmInfo`, `lp_mint`, `coin_vault`, `pc_vault`, `target_orders` PDAs via `get_associated_address_and_bump_seed(program_id, market, seed, program_id)` — identical derivation used in `process_initialize2` — since these depend only on public `market` and constant seeds.
3. Attacker submits their own `Initialize2` transaction first, supplying their own `amm_coin_mint`/`amm_pc_mint` (or the real mints with a heavily skewed `init_coin_amount`/`init_pc_amount`) and a tiny `create_pool_fee`, claiming all PDAs (`generate_amm_associated_account` succeeds because accounts are still system-owned).
4. The legitimate team's subsequent `Initialize2` for the same `market` now fails with `AmmError::RepeatCreateAmm` — permanent DoS — while unaware integrators/users who resolve the pool address from `market` interact with the attacker's pool at a manipulated price, allowing the attacker to extract real value from later swaps/deposits.

pub fn get_associated_address_and_bump_seed(
    info_id: &Pubkey,
    market_address: &Pubkey,
    associated_seed: &[u8],
    program_id: &Pubkey,
) -> (Pubkey, u8) {
    Pubkey::find_program_address(
        &[
            &info_id.to_bytes(),
            &market_address.to_bytes(),
            &associated_seed,
        ],
        program_id,
    )
