### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant shop spoofing in `Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC-signed payload. `Utils::HmacValidator.validate` therefore only proves that the body bytes are unmodified; it says nothing about which shop the webhook is claimed to belong to. `Webhooks::Registry.process` nevertheless trusts `request.shop` (parsed directly from the unauthenticated `shop-domain` header) and hands it to the host app's handler as an identity used to route/attribute the webhook payload.

### Finding Description
The HMAC binding this gem verifies is:
`HMAC(secret, raw_body) == received_hmac` [1](#0-0) 

But the identity binding the host application actually relies on is:
`shop header == shop that owns this webhook body`

That second equality is never verified by the gem. `Request#shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately constructs `WebhookMetadata` using `request.shop` from that unauthenticated header and passes it to the registered handler: [3](#0-2) 

`WebhookMetadata#shop` is a plain, unauthenticated `String` field consumed by the handler interface: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it is per-app, not per-shop), any merchant who installs the app receives genuine, correctly-HMAC-signed webhook deliveries for their own store. Since the signature covers only `raw_body`, that attacker-controlled merchant can capture one of their own legitimately-signed webhook requests (valid `hmac-sha256` + body) and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because the signature only ever covered the body, and `Registry.process` will dispatch the handler with `shop: "victim-shop.myshopify.com"` even though the body was never signed for that shop.

If the host app's handler uses `data.shop` to look up a session/access token, attribute orders, or write data keyed by shop (the officially documented and expected usage pattern, see `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))`), this allows a low-privilege attacker (anyone able to install the app on their own store) to inject events that are misattributed to an arbitrary victim shop, i.e., a cross-tenant confusion at the trust boundary this gem is responsible for asserting.

### Impact Explanation
This breaks the shop/tenant identity binding that a webhook processing pipeline is supposed to guarantee, letting one tenant (an app-installing merchant) forge webhook events that appear to originate from a different tenant. Depending on how the host app keys data/actions off `WebhookMetadata#shop` (session lookup, data writes, downgrade/cleanup flows for GDPR topics, billing events, etc.), this can result in cross-tenant data corruption or unauthorized actions attributed to a victim shop — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged action any Shopify merchant can perform) and be able to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint (the endpoint is, by design, internet-reachable so Shopify's servers can deliver webhooks; nothing in this gem restricts or authenticates the caller's network origin). No knowledge of `api_secret_key` or any privileged credential is required — the attacker only needs a body+HMAC pair that Shopify legitimately signed for their own shop.

### Recommendation
Bind the shop identity into the value that is actually verified. Concretely: include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string alongside the body, or independently verify the shop by re-fetching/confirming it out of band (e.g., cross-check against a known/expected shop for the topic) before constructing `WebhookMetadata`, and document that host apps must not treat `WebhookMetadata#shop` as authenticated unless this is fixed. At minimum, update `Request#to_signable_string` so headers relied upon for identity are covered by the same HMAC check performed in `Utils::HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of body computed with app's api_secret_key>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   ```
3. Attacker intercepts/replays this exact request to the app's webhook endpoint, but changes only:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
   Body and `X-Shopify-Hmac-Sha256` are left untouched.
4. `Utils::HmacValidator.validate(request)` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb`), because it re-hashes only `raw_body`, per `Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though the payload was never signed on behalf of `victim-shop.myshopify.com`.
