### Title
Reentrant escrow drain via checks-effects-interactions violation in `withdraw` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
On the Tron fork of the Intent Gateway, `withdraw()` performs the external token/native transfer to the beneficiary *before* decrementing the corresponding `_orders[commitment][token]` escrow balance, exactly the "async transfer before cached-balance update" pattern the external report flags for `Governance::disburse_neuron`. The escrow decrement analog of `neuron.cached_neuron_stake_doms -= disburse_amount_doms` happens only after the value-bearing external call returns.

### Finding Description
`withdraw()` in the Tron `IntentGatewayV2.sol` releases escrowed tokens to a beneficiary: [1](#0-0) 

For each token, it checks `_orders[body.commitment][token] == 0` (not the actual amount owed) and then performs an external native `.call{value: amount}("")` or a raw `token.call(transfer(...))` **before** subtracting `amount` from `_orders[body.commitment][token]`. The `TRANSACTION_FEES` payout at the end follows the same pattern — external `feeToken.call(transfer(...))` happens, and only afterward is the fee entry deleted.

This is the same root-cause class as the report: the escrow (analog of `neuron.cached_neuron_stake_doms`)  is not updated *immediately* around the async/external transfer call — the state mutation trails the value transfer instead of preceding it. In the corresponding upstream EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`), the escrow is decremented **before** the transfer: [2](#0-1) 

showing the maintainers are aware of and follow correct CEI ordering elsewhere, but the Tron variant regresses to the vulnerable ordering, using raw low-level `.call` (not `SafeERC20`) and no `nonReentrant` guard anywhere in the contract.

If the beneficiary (or fee token) is (or delegates to) a contract that can execute code on receipt of native value or during a `transfer` call — plausible on Tron/TRC10/TRC20 tokens or any beneficiary contract with a payable fallback — that code runs while `_orders[body.commitment][token]` still holds the pre-decrement (stale) balance and `_filled[body.commitment]` has already been marked (so a straightforward re-entry into `withdraw` for the *same* commitment via a duplicate delivery is blocked at the host-receipt layer per `EvmHost.dispatchIncoming`'s replay protection). However, within the same `withdraw()` call, the loop iterates multiple tokens per commitment before any of them are individually finalized; more importantly, the fee payout block executes its external call while `_orders[body.commitment][TRANSACTION_FEES]` has not yet been deleted, and the escrow-token loop's per-token external call precedes that specific token's own state write, so a reentrant call that reaches `withdraw()` again for the *same* body/commitment (e.g., replay before receipt write finalizes, or via a nested call path that is not gated by the request-receipt mapure at the point of the callback) can re-read a not-yet-decremented `_orders[commitment][token]` and redeem the same escrowed amount more than once, or drain the `TRANSACTION_FEES` bucket twice.

### Impact Explanation
A successful drain permanently and unrecoverably removes escrowed user/solver funds (ERC20/TRC20 tokens or native value held by the gateway for pending orders) beyond what was legitimately owed to the beneficiary — concrete theft of escrowed funds, matching the report's "unlimited reward claim" outcome. This affects any order settling on the Tron deployment of the Intent Gateway, reachable purely through the normal cross-chain settlement/refund path (`onAccept`/`onGetResponse`), i.e., by a relayer delivering a legitimately proven message whose `beneficiary` is an attacker-controlled contract — no privileged role is required.

### Likelihood Explanation
Medium-to-High: it requires the attacker to be named `beneficiary` of a `WithdrawalRequest` (which any solver/user naturally is via the normal fill/cancel flow) and to deploy a contract that reenters on native-value receipt or on a token `transfer` callback. No governance, admin, or peer compromise is needed — a solver simply chooses their own beneficiary contract. The main constraint is that reentrancy into `withdraw()` itself must be reachable, which depends on the exact call graph of `onAccept`/`onGetResponse`/`dispatchIncoming` on Tron (the replay-receipt write happens before the module call per the shared EVM host pattern, which somewhat narrows the direct re-entry window); this could not be fully confirmed against the Tron-specific host/handler contracts within available context, and no reentrancy guard (`nonReentrant`) protects any function in this file.

### Recommendation
In `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing the corresponding external `.call`, mirroring the ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, add a `nonReentrant` guard (or equivalent reentrancy lock) around `withdraw`/`onAccept`/`onGetResponse` in this contract, and prefer `SafeERC20.safeTransfer` over raw low-level `.call` for token transfers to get consistent revert-on-failure semantics instead of silently trusting the boolean return of `.call`.

### Proof of Concept
Conceptual (could not be executed against actual Tron test harness within available tools):
1. Attacker places/solves an order whose `WithdrawalRequest.beneficiary` is set to `AttackerContract`, a contract with a payable `receive()`/fallback (native-token case) or that is itself the `token` contract used in `body.tokens[i].token` with a malicious `transfer()` (token case).
2. A relayer delivers a valid `RedeemEscrow`/`RefundEscrow` post request; `onAccept` → `withdraw(body, isRefund)` runs.
3. Inside the loop, `beneficiary.call{value: amount}("")` (or `token.call(transfer(...))`) transfers value to `AttackerContract`, which — before the subsequent line `_orders[body.commitment][token] -= amount;` executes — attempts to trigger a second `withdraw`-reachable path for the same commitment/token (e.g., via a nested `onGetResponse`/`onAccept` delivery already in flight, or a second entry point that reads `_orders[commitment][token]`), observing the stale (not yet decremented) escrow balance and redeeming it again.
4. Net effect: `AttackerContract` receives more than the escrowed amount for the commitment, draining gateway-held funds earmarked for other tokens/orders. [1](#0-0)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
