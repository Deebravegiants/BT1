Audit Report

## Title
Censorship of inbound DMP/HRMP messages via conservative worst-case check in `check_enough_messages_included_advanced` - (File: cumulus/pallets/parachain-system/src/parachain_inherent.rs)

## Summary
`check_enough_messages_included_advanced` bounds the collator-supplied split between full and hashed messages only by the *maximum possible* size of a hashed message (`first_hashed_msg_max_size`), because `HashedMessage` never stores the original message's length, so the runtime has no way to compare against the real size of the specific message being hashed. This lets a malicious collator craft `full_messages` so that a genuinely smaller message is left hashed (and thus never dispatched) while the assertion still passes, and the analogous DMP path uses only `check_enough_messages_included_basic`, which imposes no such "as many as possible" constraint at all.

## Finding Description
`HashedMessage` stores only `sent_at` and `msg_hash`, discarding the original message length [1](#0-0) [2](#0-1) . `check_enough_messages_included_advanced` therefore only asserts `full_messages_size + first_hashed_msg_max_size > max_full_messages_size` [3](#0-2) , using the worst-case bound rather than the real size of the first hashed message. Any hashed message whose real size is smaller than `first_hashed_msg_max_size` (the channel's `max_message_size` for HRMP) can be left hashed by the collator while still satisfying this inequality, even though it would actually have fit into the remaining full-messages budget. This is invoked in `enqueue_inbound_horizontal_messages` using `channel.max_message_size` as the bound [2](#0-1) . Separately, `enqueue_inbound_downward_messages` for DMP calls only `check_enough_messages_included_basic`, which merely requires at least one full message when any hashed message exists, imposing no size-based advancement rule whatsoever [4](#0-3) [5](#0-4) .

I confirmed the code matches the claim's description exactly: the struct definitions, the assertion logic, and the call sites for both DMP and HRMP paths behave as described. I was not able to fully verify from the index alone how tightly `first_hashed_msg_max_size`/channel `max_message_size` tracks typical real message sizes in practice, nor find prior discussion (e.g. in `prdoc/stable2603/pr_9086.prdoc`, titled "Make HRMP advancement rule more restrictive") of whether this gap was a known, accepted trade-off versus an oversight — that prdoc shows the check was already tightened once, suggesting the maintainers are aware of and iterating on this exact class of issue, which weighs against treating the residual gap as an undiscovered/reportable vulnerability rather than an already-tracked design limitation.

## Impact Explanation
If exploitable, the effect would be selective, persistent censorship of a specific inbound DMP/HRMP message (e.g., a reserve-asset transfer XCM) by a malicious collator, since hashed messages are never dispatched — only their hash is folded into the MQC. This is a real class of impact (censorship by a byzantine collator) but is bounded in scope: it requires an actively malicious or colluding collator with block-authoring rights for the specific parachain, and the "worst case" bound (`channel.max_message_size`) is a protocol-configured value, not attacker-controlled, meaning the exploitable margin depends entirely on how large that configured bound is relative to typical message sizes on a given deployment — a parameter/deployment consideration rather than a code defect with a fixed, universal severity.

## Likelihood Explanation
This requires control of an active collator for the target parachain — a permissioned/staked relayer role, not an unprivileged user action, and inherents are not validated as signed extrinsics from an ordinary user path. While a malicious collator is a recognized threat model in Cumulus (the code comments themselves acknowledge "a malicious collator can provide a collection that contains no full messages or fewer full messages than possible, leading to censorship" [6](#0-5) ), this specific residual gap (worst-case bound vs. actual size) is a known limitation type in code that has already been iterated on (per the `pr_9086` prdoc history) rather than a newly discovered exploitable defect with unambiguous, unexplored root cause.

## Recommendation
No change recommended based on available evidence beyond what has already been implemented; if tighter guarantees are desired, storing actual message length in the compressed/hashed representation (impacting MQC hash computation) and applying an equivalent advancement-rule check to the DMP path would close the residual gap, consistent with the direction already taken in `pr_9086`.

## Proof of Concept
Not independently reproduced; the report's proposed unit test (extending `check_enough_messages_included_advanced_works`) is a plausible test to confirm the described boundary behavior, but was not run against this repository during validation.

			return;
