### Title
Shared Emporium identity lets any user hijack another user's external-protocol positions via CASE 2 stateless calls - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, so any external protocol invoked in this way sees `msg.sender == Emporium` regardless of which Hinkal user actually authorized the call. Because Emporium is a single contract registered globally in `Hinkal.externalActionMap` and shared by all users, any unrelated caller can submit their own valid proof through `runAction`/CASE 2 and drive calls to the same external protocol, presenting the identical `msg.sender` identity as the victim's earlier interaction.

### Finding Description
The broken equality is: **the account an external protocol records as owner/maker of a position (`msg.sender` at call time, which is always `address(Emporium)`) != the account that actually authorized/funded that position (the depositing user's stealth key/proof)**.

Trace:
- `EmporiumUpgradeable.runAction` decodes `circomData.externalActionData.externalActionMetadata` into an `EmporiumStack` [1](#0-0) .
- For CASE 2 ("Stateless Interaction", used whenever `op.invokeWallet` is false or `stack.signerAddress == address(0)`), the call goes out directly as `op.endpoint.call{value: op.value}(op.callData)` from the Emporium contract itself [2](#0-1) .
- `verifyWallet` only checks an EIP-712 signature when `stack.signerAddress != address(0)`; when it is zero (the CASE 2 path used in the attack), it returns immediately after marking `emporiumMessage` used, with no binding between the depositor's identity and the outgoing call's target/calldata [3](#0-2) .
- `Hinkal.registerExternalAction` registers one Emporium address per `externalActionId` for the whole protocol [4](#0-3) , and `dimensionsCheck`/`checkOnchainCreation`/`performHinkalChecks` only validate array-length/token-dimension consistency and calldata-hash integrity of the caller's own proof — none of them constrain `op.endpoint`/`op.callData` contents or prevent two unrelated users from targeting the same external protocol [5](#0-4) .

Exploit flow: Victim calls `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction` CASE 2 with `op.endpoint = orderProtocol`, `op.callData = createOrder(...)`; from the order protocol's perspective, `maker == msg.sender == address(Emporium)`. Later, an unrelated attacker — using only their own funds, their own proof, and their own `CircomData`/`EmporiumStack` — calls `Hinkal.transact` → `runAction` CASE 2 with `op.endpoint = orderProtocol`, `op.callData = cancelOrder(orderId)` (or `fillOrder`). Since `msg.sender` as observed by `orderProtocol` is identical (`Emporium`) for both calls, any `require(msg.sender == order.maker)`-style authorization in the external protocol is satisfied for the attacker, letting them cancel or fill the victim's order.

None of Hinkal's existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, `nonReentrant`, `onlyAllowedRecipient`, `verifyWallet`) constrain or bind `op.callData`/`op.endpoint` to the specific depositor's identity — they validate only the caller's own proof/dimensions, not that the shared Emporium identity used for the external call is unique per user.

### Impact Explanation
Any victim who uses Emporium's stateless (CASE 2) path to interact with an external protocol that authorizes actions via `msg.sender` (order books, escrow, staking positions, governance delegations, etc.) is exposed to hijacking by any other unrelated Hinkal user, because all such calls share the identical on-chain identity (`address(Emporium)`). This can result in permanent freezing or outright theft of the victim's locked/escrowed collateral by an unprivileged third party — matching the Critical category ("permanent freezing of user funds" / theft of in-flight funds). The attack is repeatable against every victim position created through CASE 2 on any protocol using `msg.sender`-based ownership.

### Likelihood Explanation
Preconditions: the victim must interact with an external protocol via Emporium's stateless CASE 2 path (no `invokeWallet`/`signerAddress`) where the protocol records ownership/authorization by `msg.sender`, and that protocol must accept follow-on calls (cancel/fill) from the same `msg.sender` after order creation. The attacker only needs their own funds and a valid Hinkal proof for their own UTXOs — no privileged role. This is fully within the described unprivileged attacker capability set, and is repeatable for every affected external protocol integration; cost is a single normal `transact` call.

### Recommendation
Do not let external protocols observe a shared, protocol-wide identity for user-specific state. Either (a) route CASE 2 calls (like CASE 1) through a per-user `HinkalWallet` instance so `msg.sender` at the external protocol is unique per depositor, or (b) require external protocols integrated via CASE 2 to bind ownership to a per-call, per-user parameter (not `msg.sender`) and validate that parameter against the calling user's proven identity within Emporium before forwarding the call.

### Proof of Concept
Hardhat fork test: (1) deploy a mock limit-order book with `createOrder(maker, ...)` and `cancelOrder(orderId)` that requires `msg.sender == order.maker`; (2) victim calls `Hinkal.transact` with `externalActionId` = Emporium id, CASE 2 op targeting `createOrder(maker=address(this))` — assert `order.maker == EmporiumAddress`; (3) a second, unrelated attacker account generates its own valid proof/CircomData for its own UTXOs and calls `Hinkal.transact` with CASE 2 op targeting `cancelOrder(orderId)`; assert the call succeeds (`msg.sender == EmporiumAddress == order.maker`) and the victim's escrowed order is cancelled/drained despite the attacker never having signed or funded that order.
