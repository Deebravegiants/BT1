## Title
Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates only covers the raw request body. This breaks the binding "shop authenticated == shop the webhook is attributed to," letting anyone who can obtain one validly-signed webhook body (e.g., by installing the app on their own store) replay it with an arbitrary `shop-domain` header to make the app process the event as if it came from a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256` header value: `to_signable_string` is what `HmacValidator.validate` verifies. [1](#0-0) [2](#0-1) 

However `Request#shop` is read straight out of the (unsigned) `shopify-shop-domain` / `x-shopify-shop-domain` header, not from anything covered by the signable string: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [4](#0-3) 

`Registry.process` trusts this unauthenticated `request.shop` value once the (body-only) HMAC check passes, and forwards it as the tenant identifier to the app's webhook handler: [5](#0-4) 

The equality that should hold is: `shop that the HMAC secret proves the request originated from == shop the handler is told to act on`. Because the shop-domain header is outside the signed payload, an attacker can decouple these two values: capture a legitimately-signed webhook body (the HMAC secret, `Context.api_secret_key`, is the app's single shared secret used for *every* shop that installs the app, not a per-shop secret), then resend that same body with a different `X-Shopify-Shop-Domain` header value. The signature still validates because the body — the only thing signed — is unchanged.

### Impact Explanation
This is a cross-tenant confusion / webhook spoofing primitive: an attacker who has installed the target app on their own store (a normal, unprivileged action) can capture one of their own legitimately-signed webhook payloads and replay it against the app's public webhook endpoint with the `shop-domain` header set to any other merchant's shop domain. The app-level handler (via `WebhookMetadata#shop`, populated from `request.shop`) will believe the event came from the victim shop and act on it accordingly — this is especially severe for the mandatory privacy webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) and any app logic keyed by shop (e.g., deprovisioning, data deletion, notification dispatch, billing state changes). This crosses a tenant boundary using only the attacker's own credentials, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app built on this gem that uses `WebhookMetadata.shop` (or `request.shop`) as the tenant key without independently re-verifying it: any user can self-install the app to obtain a validly-signed webhook body, and the replay itself (POST to the app's public webhook endpoint with a modified header) requires no special access or secrets.

### Recommendation
Include the shop domain (and other Shopify-supplied webhook headers that are used as authorization/identity signals, e.g. `webhook-id`, `api-version`) in the signable payload that `HmacValidator` verifies, or otherwise cryptographically bind the header-derived `shop` value to the signed body before exposing it via `Request#shop` / `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated header data and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against a known, previously-established session/shop record).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers/receives any webhook (e.g. `orders/create`), capturing the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC_SHA256(app_secret, B)` and `app_secret` is the same for all shops using the app).
2. Attacker resends the request to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC_SHA256(app_secret, B)` — which still matches `H` — and returns `true`, per `lib/shopify_api/utils/hmac_validator.rb`.
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, per `lib/shopify_api/webhooks/registry.rb#L198-L199`, causing the app to act as if the (attacker-controlled) event content originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
