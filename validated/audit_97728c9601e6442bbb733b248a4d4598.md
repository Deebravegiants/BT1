### Title
Chainlink price feeds in `SimplexPaymaster` lack an L2 sequencer-uptime check, allowing mispriced gas charges during sequencer downtime - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice` only validates a Chainlink answer's positivity and staleness against `maxOracleAge`; it never checks whether the L2 sequencer is up. On the L2 rollups this paymaster is deployed to (the Chainlink feed address list includes Base, Optimism, Arbitrum, Unichain, Soneium — all Ethereum-rollup sequencer chains), a sequencer outage can leave a Chainlink answer "fresh enough" (within `maxOracleAge`, configurable up to `MAX_ORACLE_AGE` = 7 days, and per the code's own comment "Base/Ethereum stablecoins up to 24h") while actually reflecting a stale, off-market price, since no new rounds can be submitted while the sequencer is down.

### Finding Description
`_getOraclePrice` is the sole gate on both native/USD and token/USD Chainlink feeds used to price ERC-4337 gas payments: [1](#0-0) 

It checks only `answer <= 0` and `block.timestamp - updatedAt > maxOracleAge`, with no equivalent of Chainlink's recommended `sequencerUptimeFeed` check (verify `answer == 0` for "up" and enforce a `GRACE_PERIOD_TIME` after the sequencer's `startedAt`). `maxOracleAge` is governance-configurable up to a full week: [2](#0-1) [3](#0-2) 

`_tokenPrice`, which is reachable from every ERC-4337 `UserOperation` via `_fetchDetails` (called during paymaster validation for any unprivileged sender), depends entirely on this unchecked price: [4](#0-3) [5](#0-4) 

The Chainlink feed addresses used by the indexer/tooling side confirm deployment across sequencer-based L2s (Base, Optimism, Arbitrum, Unichain, Soneium): [6](#0-5) 

During a sequencer outage, the last on-chain Chainlink round can remain within `maxOracleAge` while the market price has since moved materially (this is precisely the class of issue Chainlink's own L2 documentation and the referenced Sherlock report warn about). Any unprivileged UserOp sender ("bandwidth purchaser" paying gas through the paymaster) can submit ops priced off that stale round.

### Impact Explanation
If the native asset (e.g. ETH) price falls after the sequencer halts while the stored Chainlink round still reports the higher pre-outage price, `_tokenPrice` overcharges users in `token` for gas — harming legitimate users. Conversely, if the native asset price rises while the stale low price remains "fresh" per `maxOracleAge`, any UserOp sender can pay the paymaster with `token` amounts computed off the stale (low) price, systematically underpaying for the native gas actually consumed. Because `PaymasterERC20`/`SimplexPaymaster` funds `postOp` refunds and prefund out of the EntryPoint deposit funded by `swapAndDeposit`/governance, an attacker can drain the paymaster's native deposit by repeatedly submitting UserOps during/just after a sequencer outage, extracting value at the mispriced rate before the oracle updates — a direct theft-of-funds vector against the paymaster's treasury-owned deposit.

### Likelihood Explanation
Sequencer outages on rollups like Arbitrum, Optimism, and Base, while infrequent, have occurred historically and are a known operational risk explicitly acknowledged by Chainlink's own guidance (the basis of this bug class). `maxOracleAge` can be configured (by governance) up to 7 days, and the code's own comments describe intended settings up to 24h for some feeds, widening the window in which a stale-but-"fresh" price can be exploited following an outage. The attack requires no privileged access — only submitting a normal ERC-4337 `UserOperation` through the paymaster, which any sender can do.

### Recommendation
Integrate a Chainlink `SequencerUptimeFeed` check (per-chain L2) in `_getOraclePrice` (or once per validation), mirroring the standard pattern:
- Read `latestRoundData()` from the sequencer uptime feed.
- Revert if `answer != 0` (sequencer down).
- Revert if `block.timestamp - startedAt < GRACE_PERIOD_TIME` (sequencer recently back up), a configurable grace window (commonly 1 hour) before trusting price feeds again.

### Proof of Concept
1. Sequencer for the L2 that `SimplexPaymaster` is deployed on halts; the last Chainlink round for `nativeOracle`/`tokenOracle` is, say, 1 hour old and still within `maxOracleAge` (which can be configured up to 24h per the code's own comment, or up to `MAX_ORACLE_AGE` = 7 days).
2. During the outage the true native-asset price moves down significantly (a plausible market event, or the outage itself can coincide with volatility).
3. Once the sequencer resumes processing transactions (before the Chainlink oracle's next round is submitted), an attacker submits a `UserOperation` via `SimplexPaymaster`, paying `token` computed via `_tokenPrice` off the stale (higher) native price relative to true market value.
4. `_fetchDetails`/`_prefund` accept the payment at the stale rate because `_getOraclePrice` only checks `updatedAt` staleness, not sequencer liveness: [7](#0-6) 
5. Repeating this across multiple UserOps drains the paymaster's EntryPoint deposit relative to the token fees actually collected, extracting value from the treasury-funded deposit before the price corrects.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
