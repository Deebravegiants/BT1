### Title
Webhook `shop` identity is trusted from an unauthenticated HTTP header while the HMAC signature only covers the request body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute read directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. The `shop` value used to attribute the event to a tenant is therefore never bound to the cryptographic signature, breaking the equality `HMAC-authenticated bytes == bytes used to identify the tenant`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` instead reads an HTTP header that is never part of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body), and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

Because the shop-identifying header is outside the signed payload, any two requests with an identical body and identical valid HMAC digest will pass validation regardless of which `X-Shopify-Shop-Domain` header accompanies them. An unprivileged internet user who installs the app on their own store (a free, self-service action requiring no special privilege) will legitimately receive real webhook deliveries — a genuine `(body, hmac)` pair signed with the app's shared `client_secret`. Since the shop identity is carried in an unsigned header, this exact `(body, hmac)` pair can be replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to any victim shop domain, and the HMAC check still passes (it only validates the body). The handler then executes business logic under the belief that the event genuinely originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the app relies on for its webhook data processing (order/update-type events, GDPR data, inventory changes, etc. attributed to `WebhookMetadata#shop`), a cross-tenant confusion issue: an attacker can make the app act on/store data as if it came from a shop they do not control.

### Likelihood Explanation
Low likelihood: the attacker needs to (a) install the app on a store they control to obtain one authentic `(body, hmac)` pair, and (b) know or guess the app's public webhook endpoint URL (typically discoverable, since it's a fixed public route configured at app registration). No access to `api_secret_key`, tokens or TLS interception is required — only the ability to send an arbitrary HTTP POST to the app's public webhook route, which matches the "unprivileged internet user" threat model.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` (or `X-Shopify-Webhook-Id`/topic) headers as tenant-identifying data independent of the signed payload. At minimum, document/require that `WebhookMetadata#shop` must be cross-checked by the consuming application against the shop embedded in the parsed body (most Shopify webhook payloads carry shop-scoped resource ids) or against a per-shop webhook secret/URL, and consider incorporating the header set into the signable string used for HMAC verification (or issuing per-shop webhook secrets) so that shop attribution is cryptographically bound rather than derived from an unauthenticated header.

### Proof of Concept
1. Register the app as an independent (attacker-owned) merchant; Shopify sends a legitimate webhook `POST` to the app's public endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H(B)`.
2. Attacker captures (or otherwise reconstructs) this raw `(B, H(B))` pair from their own legitimately-triggered event (e.g., by proxying their own server logs, which they control since it is their own webhook delivery).
3. Attacker resends an HTTP POST to the same public webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H(B)` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `Registry#process` succeeds because it only checks `B` against `H(B)`: [3](#0-2) 
5. The registered handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the event never originated there.
