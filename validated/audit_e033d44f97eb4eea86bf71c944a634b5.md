### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then extracts the `shop` (and `topic`, `webhook_id`, `api_version`) from HTTP headers that are never included in that signature, and hands them to the app's handler as trusted identity data.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed payload at all: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC using exactly this `to_signable_string` (i.e., body-only) via `Utils::HmacValidator.validate`, and then immediately trusts `request.shop` to construct the `WebhookMetadata` that is passed to the app's handler as the authenticated tenant identity: [4](#0-3) 

`Utils::HmacValidator.validate` recomputes the HMAC strictly over `verifiable_query.to_signable_string` and compares it to the `hmac` field, so it never covers the `shop` header: [5](#0-4) 

This breaks the intended identity binding: `hmac_valid_for(body) == true` should imply `shop_header == shop_that_actually_sent_the_webhook`, but the equality does not hold, because `shop` is never an input to the HMAC computation. Any request whose HMAC over the body validates (e.g., a webhook payload legitimately received by one merchant/shop that installed the same app) can be replayed to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value, and `Registry.process` will pass that attacker-chosen `shop` straight to the handler as if it were authenticated — with no cross-check inside the gem between the header and any other verified claim.

### Impact Explanation
Because the gem itself performs no binding between the cryptographically-verified bytes (the body) and the `shop` field it attaches to `WebhookMetadata`, any app whose handler uses `WebhookMetadata#shop` to select which tenant's data/session to act on (a very common and expected usage pattern, since `Registry.process` is the gem's own dispatch entry point) can be tricked into attributing a validly-HMAC'd payload to a different shop than the one that actually produced it. This enables cross-tenant data confusion: an attacker who controls (or has previously received a genuine webhook from) one shop can relabel the `shop-domain` header and have the app process/store that payload under a different, victim tenant's identity — a cross-tenant integrity violation.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly-signed webhook body (obtainable by installing/operating any shop that has the app installed and receiving its own legitimate webhooks, or by capturing one in transit), then resending it to the app's public webhook endpoint with a modified `shop-domain` header. No access to the app's `client_secret`, access tokens, or any privileged account on the target shop is needed — only network access to the endpoint and a legitimately-signed payload from any shop. This is directly analogous to the reported bug class: a field the code relies on (`assetToken` allowance state / here, `shop`) is acted upon without the corresponding authorization/verification step (`approve` / here, HMAC coverage) actually being performed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed material verified by `HmacValidator`, or independently authenticate the `shop` header against a store of shops known to have valid, installed sessions before dispatching to handlers. At minimum, `WebhookMetadata#shop` should never be treated as authenticated unless it has been cryptographically bound to the verified payload.

### Proof of Concept
1. App using this gem registers a webhook handler via `ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", delivery_method: :http, handler: handler)`.
2. Attacker installs the app on `attacker-shop.myshopify.com` (or otherwise obtains one legitimate webhook delivery) and captures a real webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(client_secret, B)`.
3. Attacker resends the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(client_secret, B) == H` — the forged `shop` header is never checked.
5. `handler.handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
