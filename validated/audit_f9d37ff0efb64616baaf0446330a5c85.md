Based on my review of the webhook verification path, I found a concrete analog that fits the "field acted on but not covered by the HMAC" pattern.

### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and handed to the host application as trusted, verified fields.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` against `to_signable_string`. For webhook requests, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC and then forwards the header-derived `shop` (along with `topic`) straight to the app's registered handler as trusted metadata: [3](#0-2) 

The equality this breaks: `shop that authenticated/produced the signed body` != `shop attributed to the request via the shop-domain header`. Because the HMAC secret is shared across all shops that install the same app, any user who has installed the app on their own shop can generate a genuinely-signed webhook body (e.g., by triggering an `orders/create` event on their own store). That valid `(raw_body, hmac)` pair can then be replayed to the app's webhook endpoint with an attacker-controlled `x-shopify-shop-domain` header set to a victim shop, and `Utils::HmacValidator.validate` will still return `true` because it never inspects the shop header.

### Impact Explanation
If the host application uses `data.shop` (as delivered by this gem) to select which shop's offline session/access token to use, or to attribute/process incoming webhook data per-tenant — which is the intended and documented use of `WebhookMetadata#shop` — an attacker can make the app believe body content genuinely produced by their own shop originated from a different, victim shop. This is a cross-tenant identity-binding break: attacker-controlled data gets processed under another tenant's identity, potentially triggering per-shop side effects (order/customer record mutation, resource lookups, GDPR webhook handling, billing events, etc.) that are keyed off the spoofed `shop` value. This satisfies the "cross-tenant access" impact class described in the rules.

### Likelihood Explanation
Any developer who can install the app on their own shop (or otherwise obtain one legitimately-signed webhook delivery) can freely replay it with a forged `shop-domain` header, since no part of the gem validates that the header-derived shop matches the HMAC-bound content. No leaked secrets, tokens, or privileged access are required — only a normal, unprivileged merchant/developer account capable of installing the app.

### Recommendation
Bind the `shop`, `topic`, `webhook_id`, and `api_version` values into the signable content used for HMAC verification (or otherwise cryptographically bind them, e.g., by requiring the host app to independently verify the shop against a known/allow-listed set of installed shops before trusting `WebhookMetadata#shop`). At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` are **not** covered by the HMAC and must not be used as the sole tenant-identity signal without an independent shop allow-list check.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the resulting valid `x-shopify-hmac-sha256` header `H` (both computed with the app's shared `client_secret`).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs `B`), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3) , which passes because it only checks `B` against `H`.
4. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the body content and signature were generated by the attacker's own shop, letting the attacker inject or trigger shop-scoped processing under the victim's identity.
