### Title
Missing uniqueness check on BEEFY authority indices allows signature duplication to spoof the 2/3+1 supermajority threshold - (File: `modules/consensus/beefy/verifier/src/lib.rs`, `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
Both the Rust and Solidity BEEFY consensus verifiers compute the number of participating authorities directly from the length of the submitted signature/vote array, and later index into the authority set using an attacker-supplied `authorityIndex`/`index` field per signature — exactly the kind of unchecked-index-driven accounting that caused the `L1Staking.sol` bug (miscounting derived from raw/attacker-influenced indices rather than validated distinct participants). Neither implementation verifies that the submitted `authorityIndex` values are unique, so a relayer can replay one valid signature multiple times with duplicate indices to inflate the apparent participant count past the supermajority threshold without ever gathering real supermajority participation.

### Finding Description
In the Rust verifier, `verify_mmr_update_proof` computes: [1](#0-0) 
and gates acceptance purely on this raw count against the authority set's declared length: [2](#0-1) 

It then loops over every submitted signature, recovers the signer address, and pushes `sig.index as usize` into `authority_indices` with no uniqueness constraint: [3](#0-2) 

The resulting `authority_indices`/`authority_leaves` pair is passed straight into the merkle multi-proof verifier: [4](#0-3) 

A merkle multi-proof only checks that the supplied `(index, leaf)` pairs are consistent with the committed root — it does not, and cannot, reject a proof where the same `(index, leaf)` pair is supplied multiple times, since that is simply a redundant (but internally consistent) claim about the same tree position. Consequently an attacker holding just one authority's ECDSA key can submit the same signature/index pair `N` times inside `signatures_length`, satisfy `check_participation_threshold`, and have `merkle_proof.verify` succeed (the recovered address for the single real signer legitimately sits at that index in the tree).

The Solidity `EcdsaBeefy.sol` has the identical structure: `sigLen` is simply `votes.length`, [5](#0-4) 
and each vote's `authorityIndex` (attacker-supplied, no uniqueness enforcement) is used to build the leaves passed to `MerkleMultiProof.VerifyProof`: [6](#0-5) 

This mirrors the root cause of the `L1Staking.sol` M-3 finding: an accounting value (there, the slashed-staker count derived from bitmap index iteration; here, the "participants" count derived from array length/index) is trusted without validating that it corresponds to distinct, legitimate entries, letting a minority attacker manufacture the appearance of majority participation.

### Impact Explanation
If a single (or minority) malicious/compromised relay-chain authority key is available to an attacker, they can forge a BEEFY finality proof that the on-chain/off-chain verifier accepts as having supermajority (2/3+1) sign-off, while in reality far fewer distinct authorities signed. This directly breaks the security assumption of the BEEFY consensus client used to finalize MMR roots and, downstream, parachain header/state commitments consumed by `pallet-ismp`/`EvmHost` for cross-chain message and state proof verification. This is a critical break of consensus soundness — it can be used to deliver forged messages or unsound state commitments into Hyperbridge, enabling theft or freezing of bridged funds.

### Likelihood Explanation
Exploitability requires only that the attacker control (or have leaked access to) at least one legitimate relay-chain authority's signing key at the time of the targeted validator set — a materially lower bar than the intended 2/3+1 supermajority collusion assumption BEEFY is designed to enforce. Given that BEEFY proofs are relayed and processed by the permissionless proof-submission path (`verify_mmr_update_proof` / `verifyMmrUpdateProof`), any single relayer able to construct such a duplicated-signature payload can trigger the bug; no privileged access to the chain is required.

### Recommendation
Enforce uniqueness of `authorityIndex`/`index` across the submitted signatures/votes before counting participants and before/while building the merkle multi-proof leaves — e.g., deduplicate by index (or require indices to be strictly increasing) in both `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof` and `EcdsaBeefy.sol::verifyMmrUpdateProof`, and only count unique indices toward the supermajority threshold check.

### Proof of Concept
1. Attacker obtains (or compromises) exactly one authority's ECDSA/secp256k1 key for the current/next BEEFY authority set.
2. Attacker signs a single valid commitment with that key, producing one legitimate `(signature, authorityIndex)` pair.
3. Attacker constructs a `SignedCommitment`/`RelayChainProof` whose `signatures`/`votes` array contains this single `(signature, authorityIndex)` pair repeated `ceil(2/3 * authority_set.len) + 1` times.
4. `signatures_length`/`sigLen` (array length) now meets `check_participation_threshold`/`checkParticipationThreshold`.
5. `merkle_proof.verify`/`MerkleMultiProof.VerifyProof` succeeds because every `(index, leaf)` entry, though duplicated, is individually consistent with the committed authority-set root.
6. The forged proof is accepted, updating trusted consensus state / admitting an MMR root that was never actually finalized by a real supermajority.
