### Title
Single-step `transferCreator` in Bonding permanently misroutes a token's creator fee stream and role, with no ability to recover from a mistake - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator` reassigns the `creator` role (and all future fee attribution) for a launched token in a single, unconfirmed call, exactly the pattern the external Trail of Bits report flags for Beanstalk's `transferOwnership()`. Unlike `Bonding`'s own owner-transfer path, which the codebase explicitly hardens with `Ownable2StepUpgradeable` specifically to avoid this class of bug, `transferCreator` has no analogous two-step confirmation.

### Finding Description
`transferCreator` is a one-step, self-serve identity change: [1](#0-0) 

It checks only `msg.sender == info.creator` and `newCreator != address(0)`/`newCreator != info.creator`, then immediately overwrites `info.creator` — there is no proposal/acceptance handshake, and no way for the caller to verify that `newCreator` is a controllable address before the assignment takes effect.

This is the same root cause the external report describes: an owner-style privileged mutation is made irrevocable in one transaction. The codebase's own authors clearly recognize this exact bug class and defend against it for the *protocol owner* role by using `Ownable2StepUpgradeable`, with an explicit natspec comment calling out the rationale: [2](#0-1) 

The same defense was never applied to `transferCreator`, the token-level "ownership" analog, even though the docs describe it as transferring "role and future fee attribution": [3](#0-2) 

Once `info.creator` is overwritten to a wrong/unintended address, the original creator immediately fails the `msg.sender != info.creator` check and can never call `transferCreator` again to undo the mistake — the change is permanent and irreversible from that point forward.

### Impact Explanation
`info.creator` is the sole attribution key used by `FeeVault.accrue` to route the 0.25% per-trade creator fee share into `creatorBalance[creator]`: [4](#0-3) 

If `transferCreator` is called with a mistyped, unchecksummed-but-valid, or otherwise uncontrolled address, every subsequent buy/sell fee for that token — for the lifetime of the token, both pre- and post-graduation — is permanently and unrecoverably redirected to an address the original creator cannot access, and can never be reclaimed via `claim()`. This is a permanent freezing/loss of creator funds (the ongoing 0.25% fee stream), not a one-off loss, since the mis-set `creator` also governs all future `transferCreator` calls.

### Likelihood Explanation
The action requires nothing more than the legitimate token creator making a single unprivileged call — no attacker or special conditions are needed, only an ordinary address-input mistake (the same failure mode Trail of Bits documented for owner transfers). Given creators routinely rotate payout addresses (e.g., moving to a multisig or a new wallet), and given there is no confirmation step, this is a realistic, low-effort mistake with a permanent, and increasingly large as fees accrue, consequence.

### Recommendation
Convert `transferCreator` into a two-step process mirroring `Ownable2StepUpgradeable`: have the current creator call a `proposeCreator(tokenAddress, newCreator)` that stores a pending creator, and require the proposed address to call `acceptCreator(tokenAddress)` to complete the transfer. This lets the new address prove control before `info.creator` is mutated, consistent with the two-step pattern already used for the protocol owner in `Bonding` and `FeeVault`.

### Proof of Concept
1. A token creator calls `bonding.transferCreator(tokenAddress, newCreator)` where `newCreator` is a mistyped/uncontrolled address (as in `packages/contracts/src/Bonding.sol#L738-748`).
2. `info.creator` is immediately overwritten; the original creator's subsequent calls to `transferCreator` now revert with `NotCreator` (`packages/contracts/src/Bonding.sol#L744`), since `msg.sender` no longer matches `info.creator`.
3. Every future `FeeVault.accrue(token, creator, ...)` call from `Zap` (see `packages/contracts/src/FeeVault.sol#L101-123`) credits `creatorBalance[newCreator]` instead, permanently diverting the 0.25% creator fee share on every subsequent buy/sell to the unreachable address, with no path to recovery.

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```
