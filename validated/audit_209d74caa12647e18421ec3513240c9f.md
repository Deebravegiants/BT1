### Title
Wrong rounding of VWAP spread when `weightedSpreadSum` is negative - ([File: evm/src/utils/VWAPOracle.sol])

### Summary
`VWAPOracle.spread()` divides a signed cumulative weighted-spread sum by an unsigned total volume using Solidity's default division, which truncates toward zero. Because negative numerators truncate upward (toward zero) while positive numerators truncate downward, the oracle systematically reports a less-negative (more favorable) spread than the true volume-weighted average whenever the aggregate spread is negative — the exact rounding-direction asymmetry described in the referenced TWAP report, applied to `weightedSpreadSum / totalVolume` instead of `tickCumulativeDelta / secondsAgos[0]`.

### Finding Description
`recordSpread` accumulates `weightedSpread = spreadBps * inputAmountNormalized` into `CumulativeSpreadData.weightedSpreadSum` (an `int256`), and separately tracks `totalVolume` (`uint256`). [1](#0-0) 

`spread()` then computes the running VWAP as a plain signed/unsigned integer division: [2](#0-1) 

Solidity integer division truncates toward zero. When `weightedSpreadSum` is negative (i.e., fillers have on average captured value from users), `weightedSpreadSum / int256(totalVolume)` rounds up (less negative) instead of flooring, exactly mirroring the reported TWAP bug where `tickCumulativeDelta / secondsAgos[0]` truncates asymmetrically depending on sign. The test suite documents this rounding without correcting it — e.g. `testVWAPWithAllNegativeSpreads` expects `-62` for a true value of `-62.5`, and `testVWAPWithExtremeVolumeDifferences` expects `-9` for a true value of `≈-9.99`: [3](#0-2) [4](#0-3) 

`spread()` is the sole external read path defined by `IIntentPriceOracle`, exposed for any consumer (governance, solver policy, or off-chain monitoring) that wants to gauge how much value fillers are capturing from users on a given `(sourceChain, token)` pair: [5](#0-4) 

### Impact Explanation
The bias is one-directional and adversary-exploitable in the source data: `recordSpread` is called permissionlessly-by-effect for every filled order through `restrict(_intentGateway)` — i.e. anyone who is a solver/filler on the `IntentGatewayV2` (an unprivileged, reachable actor) determines the `outputs` amounts that feed `weightedSpread`. Every negative-spread fill nudges the on-chain aggregate toward under-reporting the true magnitude of value fillers are extracting from users, and the error compounds (each additional negative-spread fill re-truncates the already-truncated running average toward zero). Any downstream logic or monitoring that trusts `spread()` to detect or bound abusive filler behavior will systematically underestimate value capture, degrading a price/spread safeguard rather than corrupting funds movement directly. Given the module's stated purpose ("Positive spread = filler provided more tokens... Negative spread = filler provided fewer tokens (filler captured spread)"), this rounding defeats the intended detection of value being siphoned from users via fills — a low-severity accounting/safeguard bug rather than a direct fund-loss primitive.

### Likelihood Explanation
High likelihood: any real-world traffic mix that includes negative-spread fills (fillers taking a cut, which is the normal/expected commercial case) triggers the bias on every single accumulation, with no special conditions needed — the test suite itself demonstrates the deviation on ordinary inputs (`-62` vs `-62.5`, `-9` vs `-9.99`).

### Recommendation
Round toward negative infinity (floor) instead of toward zero when `weightedSpreadSum` is negative, mirroring the reported fix pattern:
```solidity
function spread(bytes memory sourceChain, address token) external view returns (int256) {
    bytes32 chainHash = keccak256(sourceChain);
    CumulativeSpreadData memory data = _tokenSpreads[chainHash][token];
    if (data.totalVolume == 0) return 0;

    int256 volume = int256(data.totalVolume);
    int256 quotient = data.weightedSpreadSum / volume;
    if (data.weightedSpreadSum < 0 && (data.weightedSpreadSum % volume != 0)) {
        quotient -= 1;
    }
    return quotient;
}
```

### Proof of Concept
Using the existing test fixture `testVWAPWithAllNegativeSpreads`:
1. Fill 1: 1000 tokens at -100 bps, Fill 2: 3000 tokens at -50 bps.
2. True VWAP = `(-100*1000 + -50*3000) / 4000 = -250000/4000 = -62.5` bps.
3. `spread()` returns `int256(-250000) / int256(4000)` = `-62` (Solidity truncates toward zero), overstating the true spread by 0.5 bps in the filler's favor. [6](#0-5) 

A more extreme case, `testVWAPWithExtremeVolumeDifferences`, shows the same one-sided bias at `-9` reported vs. `≈-9.99` true. [7](#0-6)
