Confirmed root cause. The `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are never part of the signed material [2](#0-1) . `Registry.process` validates only that HMAC and then dispatches to the handler using `request.shop` taken directly from the unauthenticated header [3](#0-2) .

### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers — which `Registry.process` uses to identify the tenant and dispatch the payload — are never included in the signed data, so they can be freely altered without invalidating the HMAC.

### Finding Description
The gem's webhook verification flow is:
1. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)` [4](#0-3) .
2. `HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field [5](#0-4) .
3. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it never includes `shop`, `topic`, `api_version`, or `webhook_id` [1](#0-0) .
4. After the HMAC check passes, `Registry.process` builds `WebhookMetadata` and dispatches to the app's handler using `request.shop`, `request.topic`, etc., which are read straight from HTTP headers [6](#0-5) [7](#0-6) .

The identity binding that should hold is: `hmac == HMAC(secret, body ∥ shop ∥ topic)`, so that the shop a webhook is attributed to is cryptographically bound to the same signature that authenticates the payload. Instead the actual binding enforced is `hmac == HMAC(secret, body)`, with `shop` (and `topic`) supplied out-of-band and trusted implicitly.

Because any correctly-signed webhook body (which an attacker can legitimately obtain by installing the app on their own store and having Shopify deliver a real webhook to their endpoint) keeps a valid HMAC regardless of the `x-shopify-shop-domain` header value sent with it, an attacker who can reach the app's public webhook endpoint can replay a genuine `raw_body`/`hmac` pair while substituting an arbitrary `shop-domain` header. `Registry.process` will accept the HMAC (since it never checked the header) and hand the attacker-chosen `shop` value to the app's webhook handler as if it were authentic.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an app owner or any user who has legitimately received one signed webhook can forge the shop attribution for that payload to another merchant's shop domain. Depending on how the host application trusts `WebhookMetadata#shop` (e.g., mandatory GDPR topics like `shop/redact`, `customers/redact`, `customers/data_request`, or `app/uninstalled`), this can trigger data deletion, deprovisioning, or state changes attributed to a shop that never actually sent that webhook — a cross-tenant integrity violation.

### Likelihood Explanation
Medium-High: the attacker needs no access token, `client_secret`, or TLS interception — only the ability to (a) obtain one genuinely Shopify-signed webhook (trivially done by installing the app on an attacker-controlled dev store) and (b) POST it to the app's public webhook endpoint with a modified `shop-domain` header, which the endpoint accepts unauthenticated by design.

### Recommendation
Include the tenant-identifying headers (`shop`, and ideally `topic`) in the HMAC-signable material, or independently verify that the `shop-domain` header corresponds to a shop the app actually has an active relationship with (e.g., matching against a known installed-shop store) before dispatching to the handler. At minimum, `to_signable_string` should not omit fields that downstream code treats as authenticated.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`. Shopify delivers a legitimate webhook to the app's endpoint with body `B`, headers including `x-shopify-hmac-sha256: H` (valid for secret and `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H`, then sends a new POST to the same endpoint with identical body `B` and header `H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac: H...})` is constructed; `to_signable_string` returns `B` only.
4. `Utils::HmacValidator.validate(request)` succeeds because it only re-derives the HMAC from `B`, matching `H`.
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the app's handler, which now processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
