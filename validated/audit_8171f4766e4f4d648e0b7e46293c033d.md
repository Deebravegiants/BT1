## Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for a given `shop` and `topic` as soon as `Utils::HmacValidator.validate` succeeds. However, the HMAC only signs the raw request body — the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers that the library actually acts on are never included in the signed data. Any party that can obtain one valid `(raw_body, hmac)` pair for the app's shared `client_secret` (e.g. by legitimately installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC combination while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header. The library will accept it as an authentic webhook for the victim shop.

### Finding Description
`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`, and for webhooks that method returns only the raw body: [1](#0-0) [2](#0-1) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

and

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```

`HmacValidator.validate` only checks the HMAC against `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` then trusts the unsigned `shop` (and `topic`) header directly to dispatch the handler, binding the webhook to a tenant that was never cryptographically verified: [4](#0-3) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The equality the code implicitly assumes is:

```
shop header the app acts on == shop the raw-body HMAC was actually computed for
```

but the HMAC never binds the `shop` (or `topic`) header — it only proves "this body was signed with the app's `client_secret`" without saying *for which shop*. Because a Shopify app's `client_secret` is shared across every shop that installs the app, any tenant of the app — even a low-privilege attacker who simply installs the app on their own free/dev store — can capture a legitimate `(raw_body, x-shopify-hmac-sha256)` pair from their own webhook deliveries and replay it against the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` will still return `true` (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the attacker-controlled body to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce: an unprivileged attacker who only controls their own shop's install can inject data and trigger app business logic (order sync, fulfillment, inventory, uninstall handling, etc.) *as if* it came from a different merchant's shop. Because host applications key their session/data lookups off `WebhookMetadata#shop`, this is a cross-tenant access/data-injection vector using only the attacker's own legitimately-issued webhook traffic — no access token, leaked secret, or social engineering required.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on any shop (trivial for public/dev-store distributed apps), (2) capturing a single legitimate webhook delivery (freely available to the installer), and (3) sending a crafted HTTP request to the app's public webhook endpoint with a different `shop-domain` header. No cryptographic material needs to be recovered because the shared `client_secret` never needs to be known — the attacker reuses a signature Shopify itself produced.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the signed material verified for webhooks, or independently verify that the `shop` header corresponds to a shop the app actually issued this webhook body for (e.g., by including it in `to_signable_string`, or by cross-checking against a registered webhook/shop mapping) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`).
2. Send a forged request to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim.myshopify.com
   x-shopify-webhook-id: any-value
   x-shopify-api-version: 2024-01

   B
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because `H` matches `HMAC(B, client_secret)` — the `shop` header is never part of the signed data. `process` dispatches the handler with `shop: "victim.myshopify.com"` and attacker-controlled body `B`, corresponding to `lib/shopify_api/webhooks/registry.rb:188-200` and `lib/shopify_api/webhooks/request.rb:20-38`.
