Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. Any request whose body+HMAC pair is valid for the app's secret will be accepted regardless of what shop-domain header accompanies it, so the `shop` value handed to application webhook handlers is not cryptographically bound to the signed bytes.

### Finding Description
`Registry.process` is the sole authentication gate for inbound webhooks: [1](#0-0) 

It calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` and compares it to `request.hmac`: [2](#0-1) 

But `Request#to_signable_string` returns **only** the raw body bytes: [3](#0-2) 

while `Request#shop` is read directly from the (attacker-suppliable, in a directly-reachable HTTP endpoint) `shopify-shop-domain` header, with no cross-check against the HMAC or against any known/allowed shop list: [4](#0-3) 

`Registry.process` then forwards this unauthenticated `shop` value straight to the host application's handler as trusted tenant metadata: [5](#0-4) [6](#0-5) 

The equality that should hold is: **the shop asserted in `WebhookMetadata.shop` == the shop whose data actually produced the signed bytes**. Because `to_signable_string` excludes the shop header, this equality is never checked by the gem — `HmacValidator.validate` only proves "these bytes were signed with our app secret," not "these bytes came from shop X." A single app secret (`Context.api_secret_key`) is shared across every shop that installs the app, so any (body, hmac) pair that is valid for one shop is valid, byte-for-byte, when replayed with a different `shop-domain` header value. All downstream code paths in this gem (`Registry.process` → `WebhookHandler#handle` → `WebhookMetadata#shop`) inherit this unauthenticated value as if it were verified.

### Impact Explanation
This is a cross-tenant identity confusion at the trust boundary the gem is responsible for enforcing (HMAC verification of webhooks is this library's entire raison d'être for `Webhooks::Registry`/`Request`). Host applications are expected — and Shopify's own documentation instructs developers — to rely on `HmacValidator`/`Registry.process` as proof that a webhook is authentic and attributable to the shop named in it. Because the `shop` field is carried outside the signed envelope, an application that keys sessions, access tokens, or per-tenant data by `WebhookMetadata#shop` can be made to apply a legitimately-signed payload to the wrong tenant (e.g. process a mandatory `customers/redact`/`shop/redact` job, or update per-shop state) against an arbitrary victim shop of the attacker's choosing, without ever needing that shop's credentials. This matches the "shop authenticated versus shop stored/used as identity key" and "bytes verified versus bytes parsed" analog classes: the code proves body-authenticity but silently reuses a different, unverified field as the tenant identity.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid `(body, hmac)` pair produced with the app's real secret (e.g., from their own store's genuine webhook traffic, from a Partner Dashboard "send test notification," or any other legitimate delivery to the app for a shop the attacker controls), then resend that exact body to the app's webhook endpoint with the `shop-domain` header changed to a different, victim shop domain. No possession of the victim's or the app's `client_secret`/access token is required, and no network interception is needed beyond observing a webhook the attacker's own shop legitimately receives. The gem provides no header-authenticity or shop-consistency mechanism to prevent this, so likelihood is bounded only by the host app's own choices about how it uses `WebhookMetadata#shop`, which the gem does nothing to mitigate.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the signable string used for HMAC verification, or otherwise cryptographically tie the trusted headers to the signature, so that `HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually signed. At minimum, document prominently that `Request#shop` is not authenticated by `HmacValidator` and must not be trusted for tenant-keyed operations without an independent check (e.g., comparing against the shop of the session/webhook subscription that was registered).

### Proof of Concept
1. Install the app (as a normal, unprivileged Shopify merchant) on `attacker.myshopify.com`.
2. Trigger (or capture via the Partner Dashboard's "send test notification") one genuine webhook delivery to the app's HTTP endpoint; record the raw body `B` and the `x-shopify-hmac-sha256` header value `H` — both valid under the app's real `api_secret_key`.
3. Replay the exact same HTTP POST to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `HmacValidator.validate` succeeds because it only checks `B`/`H` against the shared app secret (see `to_signable_string` returning `@raw_body` only).
5. `Registry.process` invokes the host application's `WebhookHandler#handle` with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the application to act on data/actions attributed to `victim-shop.myshopify.com` even though it never sent this webhook.
