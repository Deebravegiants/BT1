### Title
Fixed-width `u16` FIFO indices in XCMP outbound queue can wrap and corrupt channel accounting - (File: cumulus/pallets/xcmp-queue/src/lib.rs)

### Summary
The Solidity report describes a fixed-width index field (`uint8`) used to track positions in a growing collection, which silently truncates once the collection's lifetime element count exceeds the type's range, corrupting the accounting structure. The `cumulus-pallet-xcmp-queue` pallet contains a structurally analogous pattern: `OutboundChannelDetails.first_index` / `last_index` are `u16` counters that are incremented on every new outbound page sent/consumed for a channel, and the code explicitly documents the same class of assumption the Solidity code violated.

### Finding Description
`OutboundChannelDetails` stores `first_index: u16` and `last_index: u16` to track the FIFO range of pages queued for a sibling parachain channel. [1](#0-0) 

The storage doc comment explicitly states the same unproven assumption that caused the Solidity bug: *"We assume queues grow no greater than 65535 items."* [2](#0-1) 

`last_index` is incremented with plain arithmetic (`channel_details.last_index += 1;`) every time a new page is created in `send_fragment`, and this value is also used directly as the key into the `OutboundXcmpMessages` double map: [3](#0-2) 

`first_index` is incremented similarly when a page is consumed in `take_outbound_messages`, and the pair is only reset to `(0, 0)` when the queue becomes fully empty (`first_index == last_index`): [4](#0-3) 

If a channel's queue never becomes fully empty for a sustained period (e.g. sending outpaces or matches consumption so the queue stays non-empty), `last_index`/`first_index` keep incrementing without ever resetting to 0, and will eventually wrap around `u16::MAX` (65535). Unlike the NFTFloorOracle case, the wrap here is on a monotonically incrementing counter feeding directly into a storage map key (`OutboundXcmpMessages<T>` keyed by `u16`), so a wraparound would cause `last_index` to become numerically smaller than `first_index`, corrupting the `page_count`/`queued_pages` accounting (`last_index.saturating_sub(first_index)`), and potentially causing stale/incorrect pages to be read, overwritten, or left un-removed in the double map, similarly to how the Solidity bug corrupted index-based removal.

### Impact Explanation
If wraparound is reached on a live/high-traffic channel, the affected parachain's outbound XCMP channel accounting (`queued_bytes`, page counts, and the `first_index`/`last_index` used to index `OutboundXcmpMessages`) can become inconsistent. This could result in messages left permanently stuck in storage (immortal orphaned map entries never cleaned up), incorrect delivery-fee-factor calculations (which key off `queued_bytes`/threshold), or the channel state becoming unusable, requiring manual intervention/migration to repair — a DoS-class impact on XCMP message delivery for that channel, comparable to the "Oracle malfunction" impact described in the source report.

### Likelihood Explanation
This requires a channel to sustain more than 65535 outstanding "created pages" over its lifetime without the queue ever hitting empty simultaneously with the wrap boundary — i.e., very high, sustained cross-chain messaging volume on a single HRMP channel over a long period. This is a lower likelihood than the original NFT oracle case because HRMP channels are typically drained every relay-chain block when not suspended, so hitting `first_index == last_index` (which resets counters to 0) is common under normal conditions; wraparound is only reachable under prolonged very-high sustained throughput that never lets the channel fully drain. I could not fully verify from the index whether the crate/workspace enables `overflow-checks` for release builds (attempts to inspect `Cargo.toml` profile settings did not return conclusive results in the final iteration), which affects whether a wraparound would panic (halting block production — potentially worse, a consensus/DoS issue) versus silently wrap (silent corruption, matching the original bug class) in production runtime execution.

### Recommendation
- Widen `first_index`/`last_index` to `u32` (matching the report's suggested widening of the Solidity `uint8` index to `uint32`), or add explicit `checked_add`/`saturating_add` with defensive handling (e.g., emitting an error/defensive log and refusing new sends) instead of plain `+= 1`, to avoid silent wraparound of a value used as both a counter and a storage map key.
- Add a runtime invariant/defensive assertion when `last_index` approaches `u16::MAX` to detect degenerate long-lived non-draining channels before wraparound occurs.

### Proof of Concept
Conceptual trace (cannot be executed as this is a design/arithmetic analysis, not a directly reproducible single-transaction exploit):
1. A sibling parachain channel remains continuously non-empty for a sustained period (sending new pages via `send_fragment` at least as fast as `take_outbound_messages` consumes them), so `first_index`/`last_index` never simultaneously return to `(0, 0)`. [5](#0-4) 
2. Over enough blocks, `last_index` (incremented via `channel_details.last_index += 1;`) crosses `u16::MAX` and wraps to a small value while `first_index` is still large, or vice versa. [6](#0-5) 
3. `page_count`/`queued_pages` computed via `last_index.saturating_sub(first_index)` (or `checked` equivalents elsewhere) becomes wrong, and `OutboundXcmpMessages<T>` double-map lookups/removals keyed by the wrapped index no longer correspond correctly to the intended FIFO order, mirroring the accounting corruption described in the source report. [7](#0-6)
