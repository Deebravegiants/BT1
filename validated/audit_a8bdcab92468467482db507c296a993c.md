### Title
`create()` in the Lockup Factory never validates the vesting schedule, enabling unprivileged account-squatting and permanent lockup-freezing griefing - (File: `lockup-factory/src/lib.rs`)

### Summary
The external report's root cause is a config value (`reactionDeadline`) that is accepted from an unprivileged, protocol-facing creation call without any bounds/consistency checks, which can later make the flow permanently unusable and freeze user value. The `core-contracts` repository has the same root-cause class in the lockup subsystem: `VestingSchedule::assert_valid()` [1](#0-0)  and its `lockup-factory` counterpart [2](#0-1)  exist specifically to validate that `start_timestamp <= cliff_timestamp <= end_timestamp`, but neither is ever invoked anywhere in the codebase (confirmed via repo-wide search — the only matches for `assert_valid` are the definitions themselves plus unrelated `assert_valid_request` calls in `multisig`/`multisig2`). The permissionless, public `LockupFactory::create()` entrypoint [3](#0-2)  accepts an explicit `vesting_schedule: Option<VestingScheduleOrHash>` directly from the caller and forwards it unchecked into the deployed lockup contract's `new()` [4](#0-3) , which likewise performs no validation on the vesting schedule before storing it.

### Finding Description
`LockupFactory::create()` has no access control — any unprivileged NEAR account can call it for any `owner_account_id`, as long as it attaches the minimum deposit [5](#0-4) . The deployed lockup account name is fully deterministic from the `owner_account_id`: `sha256(owner_account_id)[..20].<factory_account>` [6](#0-5) . Because NEAR account names are unique and cannot be recreated once they exist, the first successful `create()` call for a given `owner_account_id` permanently claims that address.

Combined with the missing `assert_valid()` check, an unprivileged caller can:
1. Front-run the intended (legitimate/foundation-driven) lockup deployment for a target `owner_account_id` by calling `create()` first with a permissible, but semantically broken, `VestingScheduleOrHash::VestingSchedule` (e.g., `cliff_timestamp` after `end_timestamp`, or `start_timestamp == end_timestamp`), since `assert_valid()` is dead code and never enforced.
2. This squats the deterministic lockup account name for that `owner_account_id` forever, meaning the legitimate lockup (with the correct amount and correct vesting terms intended for that employee/beneficiary) can never be deployed to that address again.
3. Even absent the squatting angle, any lockup deployed with a malformed vesting schedule (which the validation was designed to prevent) can produce inconsistent/underflowing arithmetic in vesting calculations, since the invariant `start <= cliff <= end` is never guaranteed to hold at runtime.

This mirrors the report's finding precisely: a struct field (`VestingSchedule` here, `reactionDeadline`/`Prompt` there) that has a dedicated validation routine, is accepted through a public/unprivileged creation entrypoint, but the validation is never actually wired into the call path — leaving downstream logic to operate on an unchecked, potentially degenerate value.

### Impact Explanation
This falls under "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release... flows." An unprivileged attacker can permanently deny a specific beneficiary (`owner_account_id`) from ever having a legitimate lockup/vesting contract created for them at the expected deterministic address, since the account name is squatted irrevocably. This is a direct, protocol-level DoS on a third party's expected token release process, not self-harm, since the victim (the intended lockup owner) never chose to interact and never authorized the malicious `create()` call.

### Likelihood Explanation
The entrypoint `create()` is fully public and requires only the minimum attached balance (3.5 NEAR) [7](#0-6) , and no on-chain reservation exists for `owner_account_id`. Any attacker who knows (or can guess/observe, e.g., via a pending token grant announcement) a target beneficiary's account ID can immediately front-run the legitimate deployment. Likelihood is high for any publicly known upcoming lockup recipient.

### Recommendation
- Call `vesting_schedule.assert_valid()` (or the equivalent check on `VestingScheduleOrHash::VestingSchedule`) inside both `LockupFactory::create()` and `LockupContract::new()` before persisting state.
- Add a reservation/access-control mechanism to `LockupFactory::create()` so that only an authorized deployer (e.g., the foundation account) can create a lockup for a given `owner_account_id`, closing the account-squatting vector entirely.

### Proof of Concept
1. Attacker (unprivileged) calls `lockup-factory::create` with `owner_account_id = "victim.near"`, attaching `MIN_ATTACHED_BALANCE`, and `vesting_schedule = Some(VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T, cliff_timestamp: T+100, end_timestamp: T+50 }))` (cliff after end — semantically invalid, but `assert_valid()` is never called so this passes unchecked).
2. The deterministic account `sha256("victim.near")[..20].lockup-factory.near` is created and deployed with this broken schedule.
3. The NEAR Foundation later attempts to deploy the real, correct lockup contract for `victim.near` by calling `create()` with the same `owner_account_id` — the `create_account()` promise fails because the account already exists, permanently preventing the legitimate lockup from ever being created for `victim.near`.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
