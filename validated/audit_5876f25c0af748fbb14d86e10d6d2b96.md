### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing via HMAC/body replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating the HMAC over the raw body only, but hands the handler a `shop` value taken from the unauthenticated `X-Shopify-Shop-Domain` header. The equality the gem is supposed to enforce - "the shop the HMAC proves the payload came from" == "the shop the handler is told to act on" - is not enforced, because the HMAC computation never binds the `shop-domain` (or `topic`/`webhook_id`) header to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only that the HMAC matches the body, then immediately trusts `request.shop` and `request.topic` to dispatch to the handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body for webhooks), so it never verifies `shop`/`topic`/`webhook_id`: [4](#0-3) 

The library's own documentation instructs app developers to key their downstream processing (e.g. job enqueue, session lookup) directly off `data.shop`, treating it as an authenticated tenant identifier: [5](#0-4) 

Because the HMAC only proves "this body+secret combination is valid" and not "this body belongs to shop X", any attacker who can obtain one valid `(raw_body, hmac)` pair (e.g. from a webhook sent to their own installed test shop, which they fully control network access to) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim tenant. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will pass `request.shop` (the attacker-supplied victim domain) straight to the handler as if the event genuinely originated from that shop - breaking the binding "shop authenticated by HMAC" == "shop attributed to the event."

### Impact Explanation
This crosses the cross-tenant boundary explicitly named in the rules: an unprivileged internet user (any merchant who can install the app and capture their own outbound webhook traffic) can cause the app to process attacker-controlled webhook content under a victim shop's identity, since the shop attribution used by the handler (and by any app logic keyed on `data.shop`, e.g. session/store lookups) is not covered by the same cryptographic proof that authenticates the payload.

### Likelihood Explanation
Moderate. It requires the attacker to obtain at least one legitimate `(body, hmac)` pair, which is realistic for anyone who installs the app on a shop they control and can intercept their own webhook deliveries (e.g., via a local proxy/log before the request reaches the real handler, or by using webhook topics whose body content is attacker-influenced, like `products/update` on their own store). No access to `client_secret` or any Shopify credential is needed - only the ability to send a crafted HTTP POST to the app's public webhook route with a spoofed header.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook_id`) header into the signable string used for HMAC verification, or otherwise cryptographically/contextually verify that the `shop-domain` header matches a shop for which this exact webhook (topic + id) was actually registered before dispatching to the handler. At minimum, document prominently that `data.shop` in `WebhookMetadata` is unauthenticated with respect to the HMAC and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against the app's own webhook subscription records for that shop).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers a webhook for a topic such as `products/update`.
2. Attacker triggers the webhook and captures the resulting `raw_body` and `X-Shopify-Hmac-Sha256` value sent to their app endpoint (they control the network path to their own installed app instance/proxy).
3. Attacker sends a new POST to the app's public webhook route with the exact same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC [1](#0-0) .
5. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the app to process attacker-controlled data attributed to the victim tenant.

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
