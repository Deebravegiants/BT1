### Title
Stale `_defaultRelayerFee` denominated in old `feeToken` decimals after host `feeToken` changes - ([File: sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol])

### Summary
`HyperbridgeLzEndpoint.setHost()` computes `_defaultRelayerFee` once from the host's `feeToken().decimals()` at configuration time and stores it as a plain state variable that is never refreshed. Because `EvmHost` allows the `feeToken` to be changed later via governance (`updateHostParams`), a subsequent fee-token swap to a token with different decimals leaves `_defaultRelayerFee` denominated in the old decimals, causing `relayerFee()`, `send()`, and `quote()` to compute wildly wrong fee amounts.

### Finding Description
`setHost` derives the $0.30-equivalent default relayer fee directly from the fee token's decimals at the time it is called: [1](#0-0) 

This cached `_defaultRelayerFee` is consumed later, unconditionally, by `relayerFee()`: [2](#0-1) 

and directly plugged into the `DispatchPost.fee` field in both `send()` and `quote()`: [3](#0-2) [4](#0-3) 

The `feeToken` referenced here is not immutable at the host level — `EvmHost.updateHostParamsInternal` explicitly permits changing `feeToken` once the old token's balance on the host is zero: [5](#0-4) 

So the same bug class as the reported `RedeemerWithFees::BASE_UNIT` finding applies here: a per-token decimal/unit value is snapshotted once from a currently-mutable external dependency (`IDispatcher(hostAddr).feeToken()` → `IERC20Metadata.decimals()`) and stored in a variable that is never re-derived when that dependency changes. Unlike `BASE_UNIT`, `_defaultRelayerFee` is technically mutable storage (owner can call `setDefaultRelayerFee`), but nothing in the contract ties a host-level `feeToken` rotation to updating it — the endpoint owner has no visibility into, or hook on, governance-driven fee-token changes on the ISMP host, so the value silently goes stale exactly as in the reported pattern.

### Impact Explanation
If the host's `feeToken` is rotated to a token with fewer decimals (e.g., 18 → 6), the stale `_defaultRelayerFee` becomes inflated by orders of magnitude (up to 10^12x), causing `send()`/`quote()` to demand an absurd fee amount in the new token — `IERC20(feeToken).forceApprove` / balance requirements become unsatisfiable, and dispatch of every LZ-routed message through this adapter reverts or drains disproportionate value, freezing message delivery for the OApp relying on the endpoint. If decimals increase (e.g., 6 → 18), the fee becomes negligible, starving relayers of any real incentive and causing outbound messages to go undelivered indefinitely — a route unable to deliver messages, matching the in-scope impact criteria.

### Likelihood Explanation
This requires only a normal, expected chain-governance action (rotating the host's `feeToken`, which the protocol explicitly supports and gates only on the old token's balance being zero) — not any admin misbehavior on the `HyperbridgeLzEndpoint` itself. Any unprivileged user or OApp calling `send()`/`quote()` after such a rotation is affected, so the likelihood is directly tied to routine `feeToken` migrations on `EvmHost`, which are a documented governance capability.

### Recommendation
Do not cache `_defaultRelayerFee` from `feeToken.decimals()` at `setHost` time. Either (a) recompute the default fee lazily/on read against the current `feeToken().decimals()`, or (b) require the endpoint to re-derive/re-normalize `_defaultRelayerFee` (and per-destination `_relayerFees`) whenever it detects/is notified of a `feeToken` change on the host, e.g. by exposing a `refreshDefaultRelayerFee()` entrypoint invoked as part of any host-parameter update workflow, and by denominating fees in USD-equivalent terms recomputed against the live decimals rather than a point-in-time snapshot.

### Proof of Concept
1. Deploy `HyperbridgeLzEndpoint` and call `setHost(hostAddr, eid)` while `feeToken` on `hostAddr` is an 18-decimal token → `_defaultRelayerFee = 0.3e18`.
2. Governance later rotates `hostAddr.feeToken` to a 6-decimal token (e.g., USDC) via `updateHostParams` (balance of the old token is zero, so the swap succeeds per `CannotChangeFeeToken` guard).
3. Any user calls `endpoint.send(...)` with `payInLzToken = true`; `relayerFee(dstEid)` still returns `0.3e18`, now interpreted in 6-decimal token units — an absurd 300 billion token fee — causing the transfer/approval to fail and the message to never dispatch, or (if the token were pre-funded to that size) an catastrophic fee overcharge relative to actual $0.30 intent.

```text
    function setHost(address hostAddr, uint32 localEid) external onlyOwner {
        _host = hostAddr;
        _eid = localEid;

        // Set default relayer fee to $0.30 based on feeToken decimals
        address feeToken = IDispatcher(hostAddr).feeToken();
        uint8 decimals = IERC20Metadata(feeToken).decimals();
        _defaultRelayerFee = (3 * 10 ** decimals) / 10; // 0.30
    }
```
