## Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts a webhook as valid whenever the body/HMAC pair checks out, then passes the caller-controlled `shop` header straight to the app's handler. Because the app's client secret used for HMAC computation is shared across all shops (it's the app-level `client_secret`, not a per-shop secret), any actor who can trigger a legitimate webhook for their own store can capture a valid `(raw_body, hmac)` pair and replay it to the same endpoint with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header pointing at a different shop. The HMAC check still passes because the shop identity was never part of the signed content, so the app processes attacker-supplied data as if it came from a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all parsed directly from headers and are never included in the signed bytes: [2](#0-1) 

`HmacValidator.validate` verifies the signature purely against `to_signable_string`, i.e., the raw body: [3](#0-2) 

`Registry.process` relies solely on this body-only HMAC check, then forwards the unauthenticated `request.shop` (and other header-derived fields) to the registered handler as trusted metadata: [4](#0-3) 

This breaks the intended identity binding: `hmac-verified bytes == the tenant the app believes sent the webhook`. In reality, the equality only holds for `hmac-verified bytes == raw_body`; `shop` is asserted, not authenticated. Since the signing secret (`Context.api_secret_key`, the app's `client_secret`) is identical for every merchant installation of the app, a person who operates (or has API access to) *any* one shop that has the app installed can:
1. Trigger a real webhook event on their own store (e.g., create an order, update a product) that the app subscribes to.
2. Capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair from the delivered webhook request.
3. Replay that exact body and HMAC to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to a victim shop that also uses the app.
4. `HmacValidator.validate` succeeds (body+hmac are unmodified and correctly signed with the shared secret), and `WebhookMetadata.shop` is set to the victim shop, so the handler acts on the victim shop's tenant context using attacker-controlled body content.

Depending on what the app's webhook handlers do with `shop` (e.g., look up/update the merchant's record, revoke access on `app/uninstalled`, process `customers/redact` or `shop/redact` GDPR webhooks, adjust billing state), this allows cross-tenant data corruption or a forced compliance/uninstall action against a shop the attacker doesn't control.

### Impact Explanation
This meets the "Critical - cross-tenant access" bar: an unprivileged holder of one tenant's webhook feed can inject events attributed to a different tenant because the shop identity is not bound to the signature that authenticates the payload. The severity depends on handler logic downstream (which is outside this gem, but the gem is what hands the unauthenticated `shop` value to handlers as if verified), but the primitive itself — spoofing the tenant identity of an HMAC-valid webhook — is a direct cross-tenant boundary break introduced by this gem's `Request`/`Registry` design.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to be a legitimate merchant of the target app (to generate a validly-signed body/HMAC pair) and knowledge that another shop shares the same app installation and public webhook endpoint (typically a single shared URL per app, easily inferable from a public app's OAuth callback URLs or webhook registration docs). No access to `api_secret_key`, tokens, or the victim's credentials is required.

### Recommendation
Bind the shop identity to the authenticated payload rather than trusting a header value uninvolved in the signature. Options:
- Include the `shop-domain` header (and ideally `topic`) in the signable string used by `HmacValidator`, e.g., have `Request#to_signable_string` incorporate `shop` and `topic` alongside `raw_body`, and update the signature computation accordingly if Shopify's delivery includes a matching signed value, or
- At minimum, cross-check the delivered `shop` header against an expected/allow-listed set of installed shops before dispatching to handlers, and document to consumers that `WebhookMetadata#shop` must be treated as untrusted unless corroborated by stored installation state.

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com" with the app installed.
# They trigger a real webhook (e.g. orders/create) and capture the delivered request:
raw_body = '{"id": 1, "note": "hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)

# Attacker replays the same body+hmac, but swaps the shop-domain header to a victim shop
# that also has the app installed:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by the HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body+hmac match),
#    and the handler receives WebhookMetadata with shop: "victim-shop.myshopify.com",
#    even though the payload actually originated from attacker-shop.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end
