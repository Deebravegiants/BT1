### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` (tenant identifier) from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value that `Registry.process` hands to the app's `WebhookHandler` (as `WebhookMetadata#shop`) is therefore an attacker-controllable, unauthenticated field, while only the body bytes are cryptographically bound to `Context.api_secret_key`.

### Finding Description
`ShopifyAPI::Webhooks::Request` reads the tenant-identifying `shop` value straight from a header: [1](#0-0) 

The HMAC signable string used by `Utils::HmacValidator.validate` is defined as just the raw body, not including the shop header: [2](#0-1) 

`Registry.process` verifies only this body-bound HMAC, then passes `request.shop` unmodified into `WebhookMetadata`, which is delivered to the app's handler: [3](#0-2) 

The library's own documentation instructs integrators to trust `data.shop` as the tenant key for routing work (e.g., `shop_domain: data.shop`): [4](#0-3) 

This is the exact bug class from the report: a field that is *acted on* (the tenant/shop binding used to route and attribute webhook data) is not covered by the authentication code (the HMAC) that is supposed to prove authenticity of the request. The equality that should hold — `hmac_verified_bytes == bytes_that_determine_the_tenant` — is broken because `hmac_verified_bytes = raw_body` while `tenant = header["shop-domain"]`, two disjoint sets of bytes.

### Impact Explanation
An unprivileged internet user who has installed the app on their own store (a normal, non-privileged action) receives genuine webhooks with a valid `raw_body` + HMAC pair signed with the app's real `api_secret_key`. Because the HMAC never covers the `shop-domain` header, that same `(raw_body, hmac)` pair remains valid if the attacker replays the request to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` still succeeds (it only recomputes over the body), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, while `body` still contains the attacker's own resource data. Any app that uses `data.shop` to select which tenant's records to create/update/delete (exactly as recommended in the gem's own docs) will attribute or inject the attacker's payload into another merchant's tenant context — a cross-tenant data-integrity/isolation break achieved without ever possessing the victim's or the app's credentials.

### Likelihood Explanation
Likelihood is high for any app that follows the documented pattern of trusting `data.shop`/`request.shop` as the routing key without independently confirming that shop against another authenticated source (e.g., the OAuth/session token for that request). No secret, session, or elevated privilege is required beyond the ability to install the app on an attacker-controlled shop and send arbitrary HTTP requests to the app's public webhook URL — capabilities available to any unprivileged internet user/merchant.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signable representation used by `Utils::HmacValidator`, or otherwise cryptographically bind them to the verified payload (e.g., re-deriving/confirming the shop from a value embedded and covered inside the JSON body, or requiring the caller to separately correlate `request.shop` against a previously verified, stored session before trusting it). At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop`/`request.shop` is unauthenticated and must be cross-checked against known installed shops before being used for tenant routing.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, completing OAuth normally (no special privilege).
2. Shopify sends the attacker a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this exact `(B, HMAC)` pair and replays it directly to the app's public webhook endpoint, substituting the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds `shop == "victim-shop.myshopify.com"`.
5. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (matching `to_signable_string == B`) and returns `true`, since the header is never part of the signed bytes.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to process attacker-supplied body content under the victim's tenant identity, per the library's own recommended usage pattern.
