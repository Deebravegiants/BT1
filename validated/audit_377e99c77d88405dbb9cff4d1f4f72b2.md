### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers and are never included in the signed payload, so the gem never binds "the shop the HMAC was computed for" to "the shop attributed to the resulting webhook event."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then hands the header-derived `shop` straight to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC using `Context.api_secret_key`/`Context.old_api_secret_key`, which is a single app-level secret shared across **every** shop that has installed the app — it is not per-shop: [4](#0-3) 

Because (a) the signing secret is identical for all tenants of the app and (b) the signature covers only the body, not the shop header, the equality the gem should enforce — `shop_the_signature_was_issued_for == shop_attributed_to_the_event` — is never checked. Any body+HMAC pair that is valid for one shop is *also* a valid HMAC for every other shop of the same app, since the secret and signable content are shop-independent. This is exactly the report's bug class: a field that is acted upon (the hook address / here, the shop identity) is not incorporated into the value that is cryptographically authenticated (the leaf / here, the HMAC digest), so two different "identities" collapse onto the same valid proof.

### Impact Explanation
A merchant who has legitimately installed the app (an "unprivileged" tenant with no special access to other tenants' data) receives genuine webhook deliveries for their own store, each consisting of a body and a matching HMAC computed with the app's shared secret. Because the signature never covers `shop-domain`, that same (body, hmac) pair remains valid if replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to name a *different* installed shop. `Registry.process` will accept the HMAC (it only checks the body) and dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain, alongside data controlled by the attacker's own store. This is a cross-tenant identity-confusion vector: if the host application trusts `data.shop` from the callback (as the gem's own documentation instructs: `puts "... shop: #{data.shop} ..."`), an attacker can inject events, trigger side effects, or pollute shop-scoped state under another merchant's identity without ever needing that merchant's credentials.

### Likelihood Explanation
Likelihood is constrained by the need for the attacker to already be a legitimate (if unprivileged) installer of the same app in order to obtain a genuinely-signed (body, hmac) pair — which is trivial to satisfy for any public app, since installation itself requires no privilege beyond running a store. Triggering a webhook event (e.g., `orders/create`) on their own store is entirely within their control. No leaked secrets, TLS interception, or social engineering are required, only the gem's design of excluding the shop identity from the signed content.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) inside the value that is HMAC-verified, or independently re-derive/validate the `shop` against the shop that the raw body's payload actually references (Shopify's webhook JSON payloads typically identify the resource's owning shop through other verifiable channels). Concretely, `Webhooks::Request#to_signable_string` should not rely on body-only signing when `shop` is used downstream as an identity; at minimum, `Registry.process` should cross-check `request.shop` against a shop known to have an active, matching webhook subscription/session before dispatching to the handler, rather than trusting the raw header value once the (shop-independent) HMAC passes.

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own shop "attacker.myshopify.com"
# and triggers a legitimate webhook (e.g. orders/create). Shopify sends:
#   headers: { "x-shopify-topic" => "orders/create",
#              "x-shopify-hmac-sha256" => "<VALID_HMAC_OF_BODY>",
#              "x-shopify-shop-domain" => "attacker.myshopify.com" }
#   body: '{"id": 1, "note": "hello"}'
#
# Because HmacValidator only signs the raw body with the app-wide secret
# (lib/shopify_api/utils/hmac_validator.rb#L26-L31), the same hmac value
# stays valid for ANY shop of this app.

# Step 2: Attacker replays the exact same body + hmac to the app's webhook
# endpoint but swaps the shop header to a victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<VALID_HMAC_OF_BODY>",   # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com" # forged
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id": 1, "note": "hello"}', headers: headers)

# Step 3: Registry.process accepts it because HmacValidator.validate only checks body:
ShopifyAPI::Webhooks::Registry.process(request)
# => Handler is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though this event never came from Shopify on behalf of that shop.
``` [5](#0-4) [6](#0-5)
