### Title
Webhook Shop/Topic Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only verifies the body against the HMAC, so the "identity" of the tenant a webhook claims to be from is never cryptographically bound to the signature that authenticates the request.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` purely from HTTP headers: [1](#0-0) 

Note that `to_signable_string` (the value that gets HMAC-verified) returns only `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC solely against `to_signable_string`, i.e. only the body bytes, using the shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` gates on this HMAC check and then dispatches the handler using `request.shop` (the unauthenticated header) as the tenant identity, alongside `request.parsed_body` (the HMAC-covered content): [4](#0-3) 

The binding that should hold is: `shop_claimed_by_header == shop_that_produced_this_signed_body`. Because `shop` (and `topic`/`webhook_id`) is excluded from the signable string, this equality is never checked — only body integrity/authenticity under the app's shared secret is checked. Any request whose body+HMAC pair is valid for *some* shop under this app (e.g., the attacker's own installed instance) will pass validation regardless of which shop's domain is asserted in the header.

### Impact Explanation
This breaks the tenant-identity binding for the app-wide webhook secret (`api_secret_key` is shared across every shop that installs the app; it is not a per-shop secret). An attacker who is a legitimate installer of the app on their own (e.g., free/dev) store can obtain a validly-signed `(body, hmac)` pair for a webhook topic they control (e.g., `orders/create`, with body content they influence as the shop owner). They can then submit that exact `body`/HMAC to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` (and optionally `topic`/`webhook-id`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes against the shared secret, and `Registry.process` calls the app's handler with `shop: <victim-shop>` and attacker-controlled `body`. Any host application that uses `data.shop` from `WebhookMetadata` as the tenant key (the intended and documented use, e.g., to look up/act on the victim's stored data) will act on attacker-controlled data attributed to the victim shop — a cross-tenant data-injection/spoofing primitive rooted entirely in this gem's webhook verification, which qualifies as Critical (cross-tenant access) per the identity-binding class described.

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop (their own, including a free development store) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no leaked credentials, access tokens, `client_secret`, or privileged account needed. This is squarely an "unprivileged internet user" path.

### Recommendation
Include the tenant/topic identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string verified by HMAC, or otherwise cryptographically bind them to the signed payload, so `Utils::HmacValidator.validate` cannot pass unless the asserted shop actually produced the signed body.

### Proof of Concept
1. App installs on attacker's own shop `attacker.myshopify.com`; attacker triggers/receives a real webhook (e.g. `orders/create`) with valid headers and a body they influence (order note, custom line item properties, etc.), yielding a genuine `(raw_body, hmac)` pair signed with the app's `api_secret_key`.
2. Attacker POSTs the same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `Utils::HmacValidator.validate` returns `true` because it only recomputes/compares HMAC over `raw_body`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's `body`, causing the host app to process attacker-controlled data under the victim's tenant identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
