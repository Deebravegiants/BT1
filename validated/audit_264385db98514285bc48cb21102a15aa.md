### Title
Interest accrual overflow permanently freezes an oversized high-utilization market - (File: contracts/pool/src/interest.rs)

### Summary
An unprivileged attacker can create or control accounts that provide liquidity and borrow most of it; once the scaled debt value multiplied by the growing borrow index exceeds the `i128` domain, every subsequent accrual panics, permanently blocking repayment, withdrawal, and liquidation for that market. [1](#0-0) 

### Finding Description
`Controller::supply(caller, account_id, spoke_id, assets)` and `Controller::borrow(caller, account_id, borrows, to)` expose the position-building side of the attack to an authorized account owner or delegate. [2](#0-1) 
`Controller::update_indexes(caller, hub_assets)` reaches `ops::market::accrue`, which loads each requested market and calls `interest::global_sync`. [3](#0-2) 
`global_sync` repeatedly calls `accrue_chunk`, which invokes the shared `accrue_step` calculation and stores the resulting borrow and supply indexes. [4](#0-3) [5](#0-4) 
The utilization calculation converts scaled borrow and supply balances back through `scaled_to_original`, so a sufficiently large scaled balance multiplied by a sufficiently large index can exceed the fixed-point `i128` value ceiling. [6](#0-5) 
The checked-in regression test demonstrates that this overflow occurs before `MAX_BORROW_INDEX_RAY` can cap the index. [7](#0-6) 

The strongest single-address path is to create two owned accounts with `account_id = 0`: supply the borrowed asset from one account, supply collateral and call `borrow` from the other, then let interest accumulate and call `update_indexes(caller, [borrowed_hub_asset])`. [2](#0-1) [3](#0-2) 
All ordinary market legs go through `ops::synced_market`, which accrues before the mutation, and `load_leg` uses that synchronized cache for position operations. [8](#0-7) 
Consequently, `withdraw` panics before burning or paying collateral, and `repay` panics before burning debt or crediting cash. [9](#0-8) [10](#0-9) 
The repository’s test confirms that `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow` after the cliff is reached. [11](#0-10) 
Even replacing the rate model cannot recover the market because `replace_rate_model` synchronizes and accrues the frozen market before writing the new model. [12](#0-11) 

### Impact Explanation
This causes permanent freezing of supplier collateral and pool liquidity in the affected market: suppliers cannot withdraw, borrowers cannot repay, and liquidation-dependent recovery cannot proceed through the normal accrued-market path. [8](#0-7) [13](#0-12) 
Because the panic happens before state is committed, `last_timestamp` remains behind while ledger time continues to increase, so every later operation repeats the overflowing accrual rather than skipping it. [4](#0-3) [14](#0-13) 

### Likelihood Explanation
The attacker does not need privileged contract access, leaked keys, oracle manipulation, or a third-party integration; the required calls are the normal `supply`, `borrow`, and permissionless `update_indexes` flows. [2](#0-1) [3](#0-2) 
The exploit is capital-intensive because the scaled position must be large enough for index growth to cross the `i128` value ceiling, and it requires sustained borrowing so utilization remains on the steep part of the configured rate curve. [15](#0-14) 
The included test constructs exactly that condition with a billion-unit, 18-decimal market and a 98% borrow, then observes the market freeze rather than a bounded-index state. [16](#0-15) 

### Recommendation
Enforce a maximum safe scaled-value-to-index product before accrual, or cap the index at the largest value for which `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` remain representable. [6](#0-5) 
Reject new `supply` or `borrow` amounts that can exceed that bound under the configured maximum rate and maximum accrual interval, and add a recovery path that can write down debt or replace market parameters without first executing the overflowing accrual. [12](#0-11)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
