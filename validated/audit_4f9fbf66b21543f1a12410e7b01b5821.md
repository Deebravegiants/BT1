### Title
Unauthenticated fan-out amplification via `HandleLegacyUserMessage` in the WebAPI gateway handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The GitLab advisory describes a DoS where an unprivileged/authenticated actor can spike server resource utilization by invoking a `gitlab-shell` command whose cost is disproportionate to the caller's privilege, with no throttling in place. The chainlink internet-facing Gateway has an analogous unthrottled amplification path: `handler.HandleLegacyUserMessage` accepts a `web_api_trigger` message from a user-facing entry point and, with an explicit unimplemented allowlist/rate-limit check, fans the request out to every member of the DON.

### Finding Description
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` validates message shape, decodes the `TriggerRequestPayload`, checks a staleness timestamp, and then explicitly skips authorization/rate limiting:

```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
``` [1](#0-0) 

After this point, it stores a callback keyed by `msg.Body.MessageID` in the shared `savedCallbacks` map and immediately fans the request out to **every DON member**:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()

// Send original request to all nodes
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [2](#0-1) 

Unlike the node→gateway direction, which is protected by `h.nodeRateLimiter.Allow(nodeAddr)` in `handleWebAPIOutgoingMessage` [3](#0-2) , there is no equivalent per-sender or global rate limiter guarding the client-facing `HandleLegacyUserMessage` entry point. The only mitigation is capping the total in-memory callback table via `pruneCallbacks`/`defaultMaxSavedCallbacks` [4](#0-3) , which bounds memory but does nothing to prevent repeated cheap requests from generating disproportionate DON-wide fan-out traffic (one HTTP request → N `SendToNode` RPCs, one per DON member).

I was unable to fully trace, within the available tool budget, the exact caller that invokes `HandleLegacyUserMessage` from the raw HTTP-facing gateway listener (e.g., whether an upstream layer in `gateway.go`/`multihandler.go` applies IP-based or session-based throttling before dispatch). This is a genuine gap in verification — if such upstream throttling exists, the practical severity is reduced, though the code-level allowlist/rate-limit control called out by the `TODO` comment is confirmed absent at this handler.

### Impact Explanation
A caller able to reach the `web_api_trigger` legacy path can repeatedly submit trigger messages that are each multiplied into `len(donConfig.Members)` outbound RPCs to every node in the DON, and each accepted request also consumes gateway memory (a `savedCallback` entry) until pruned. This is directly analogous to the GitLab issue: a single low-cost client action triggers disproportionate downstream resource consumption, enabling a DoS against the gateway and, transitively, against DON nodes that must process the forwarded requests.

### Likelihood Explanation
Likelihood is Medium: exploitation requires reaching this handler and method with unthrottled repetition; the code path itself (this handler function) has no built-in throttle and explicitly documents the gap via the `TODO` comment, but I could not confirm from the code fully whether an outer layer of the gateway server (HTTP/connection-level rate limiting) mitigates this before requests reach `HandleLegacyUserMessage`.

### Recommendation
Implement the allowlist and rate-limiting noted in the `TODO` at `core/services/gateway/handlers/capabilities/handler.go:384` before processing `MethodWebAPITrigger` requests in `HandleLegacyUserMessage` — e.g., reuse or extend the existing `ratelimit.RateLimiter` pattern already used for node-originated messages (`h.nodeRateLimiter`) to also bound per-sender and global request rates on the client-facing ingress path, prior to the DON-wide fan-out loop.

### Proof of Concept
Not independently verified end-to-end due to inability to trace the full HTTP-to-handler call chain within the tool budget; the PoC concept would be: repeatedly POST valid `web_api_trigger` payloads to the gateway's legacy user-message endpoint faster than `pruneCallbacks` can reclaim capacity, observing DON-member RPC volume scale linearly with request count with no rejection until `defaultMaxSavedCallbacks` (20000) is exceeded.
