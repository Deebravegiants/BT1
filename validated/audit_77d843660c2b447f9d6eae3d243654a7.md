### Title
Cardano address case-sensitivity mismatch between `validateCardanoAddress` and `compareAddresses` bypasses `DestinationAddressMatchesTokenAddressError` - (File: `packages/intents-sdk/src/lib/validateAddress.ts`, `packages/intents-sdk/src/lib/compareAddresses.ts`)

### Summary
`validateCardanoAddress` decodes the destination address with the BIP-173 compliant `bech32.decode`, which per spec accepts an address that is entirely upper-cased as an equally valid encoding of the same bytes as its lower-case form. `compareAddresses` for Cardano, however, does a raw `a === b` string comparison instead of canonicalising the bech32 payload, so an upper-cased copy of the token's own address passes `validateAddress` but fails to be recognised as equal to the (lower-case) `origin_chain_address` returned by the PoA bridge API.

### Finding Description
In `PoaBridge.validateWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:170-219`), the guard against sending funds to the token's own address is: [1](#0-0) 

This relies on `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)` returning `true` whenever the two strings denote the same account. For Cardano, `compareAddresses` falls into the generic branch: [2](#0-1) 

i.e. plain `a === b`, no bech32 decoding/canonicalisation at all.

Meanwhile `validateAddress` for Cardano uses `bech32.decode`: [3](#0-2) 

Per BIP-173, a bech32 string is valid if it is either all lower-case or all upper-case (mixed case is rejected), and both cases decode to the identical byte payload — an upper-cased Cardano address is a different string but the same account as its lower-case counterpart. `@scure/base`'s `bech32.decode`, as a spec-compliant implementation, accepts the all-uppercase form and normalises internally to reach the same `words`/bytes, so `validateCardanoAddress` returns `true` for `ADDR1...` just as it does for `addr1...`.

The `origin_chain_address` value coming back from the PoA bridge's `getSupportedTokens` API is a fixed lower-case bech32 string. An attacker who supplies `destinationAddress` as the upper-cased version of that same token address:
1. Passes `validateAddress(args.destinationAddress, Chains.Cardano)` — `true`, because `bech32.decode` accepts the all-caps encoding.
2. Fails `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, Chains.Cardano)` — `false`, because it does a case-sensitive `a === b` on two differently-cased strings representing the same bech32 payload.
3. `DestinationAddressMatchesTokenAddressError` is never thrown, and `createWithdrawalIntents` proceeds to build a withdrawal intent sending the token to its own contract address.

This exactly matches the invariant violation the question describes: for Cardano, an accepted destination (per `validateAddress`) that denotes the same account as the token address is not recognised as equal by `compareAddresses`.

### Impact Explanation
An unprivileged NEAR Intents user calling `IntentsSDK.processWithdrawal`/`createWithdrawalIntents` with a Cardano PoA-bridge asset and an upper-cased `destinationAddress` equal to the token's own address bypasses the self-send guard. The resulting signed withdrawal intent sends the user's own tokens to the Cardano token/minting address, which is not a spendable wallet — the funds are permanently unrecoverable. This is funds delivered to a wrong/contract address with no recovery path, matching the Critical impact category. The bug is repeatable for every Cardano PoA asset and every call using this technique.

### Likelihood Explanation
Preconditions are minimal: attacker only needs to know the plaintext Cardano token address (public information from `getSupportedTokens`) and upper-case it — no privileged access, no race condition, and no reliance on a malicious relayer/RPC. Any ordinary user (or an integrator forwarding an unsanitized address string on a user's behalf) can trigger this in a single call. Given bech32 is case-normalizing by design, this is a low-cost, deterministic bypass.

### Recommendation
Canonicalise Cardano addresses in `compareAddresses` the same way `validateCardanoAddress` parses them: bech32-decode both `a` and `b`, verify they share the same `prefix` ("addr") and identical decoded byte payload, rather than comparing raw strings. This mirrors the approach already used for TON, Tron, and hex-based chains in the same file.

import { describe, it, expect } from "vitest";
import { compareAddresses } from "./compareAddresses";
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";

const lower =
  "addr1qxg5fnc2dfssnhzygvkqzzy2fcqcph533ek58jngqksaqjwwk2uhs32lj8zh62fq5zdeawrshdfp23t5vcm538glyn6sqngmem";
const upper = lower.toUpperCase();

describe("Cardano address case bypass", () => {
  it("validateAddress accepts the upper-cased form", () => {
    expect(validateAddress(upper, Chains.Cardano)).toBe(true);
  });

  it("compareAddresses fails to recognise the same account across case", () => {
    // both denote the SAME Cardano account per BIP-173 bech32 semantics
    expect(compareAddresses(lower, upper, Chains.Cardano)).toBe(true); // EXPECTED true, currently false -> bug
  });
});

export function validateCardanoAddress(address: string) {
	try {
		// max length big enough for any Cardano Bech32 addr
		const { prefix, words } = bech32.decode(
			address as `${string}1${string}`,
			120,
		);

		// only mainnet
		if (prefix !== "addr") return false;

		// convert 5-bit words back to bytes
		const data = bech32.fromWords(words);
		//@ts-expect-error
		const addrType = data[0] >> 4;

		return addrType >= 0 && addrType <= 7;
	} catch {
		return false;
	}
}
