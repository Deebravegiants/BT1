### Title
Unrestricted, unauthenticated `CallDispatcher.dispatch()` allows any address to steal native/ERC20 dust left in the shared call-execution contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public, unauthenticated `external` function with no caller restriction and no validation on the encoded `Call[]` it executes beyond `extcodesize(to) != 0`. It is the shared execution engine used by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution and by `IntentGatewayV2` pre/post-dispatch calldata, both of which route real user value (native ETH and ERC20 tokens) *through* this contract's own balance before or after arbitrary attacker/solver-controlled calls execute. Because `dispatch()` itself carries no `onlyHost`/`onlyGateway`/ownership check, any unprivileged party can call it directly at any time to sweep out whatever native/ERC20 balance the dispatcher happens to be holding — exactly the same bug class as the reported issue: a powerful, unvalidated action (arbitrary external call, forwarding arbitrary value) reachable with attacker-controlled parameters and no gatekeeping.

### Finding Description
`CallDispatcher.dispatch()`: [1](#0-0) 

has no access-control modifier at all — anyone can call it with an arbitrary ABI-encoded `Call[]`, and the only check performed is that the target has code (`extcodesize(to) != 0`); `to`, `value`, and `data` are otherwise fully attacker-controlled, and `value` is paid out of the dispatcher's *own* balance.

This contract is deliberately designed to transiently (and, per the docs, sometimes not fully) hold real value:
- `HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept` mint/unlock tokens (or unwrap WETH to native ETH) directly *to the `_dispatcher`'s address* when the cross-chain sender sets `to = CALL_DISPATCHER`, then immediately execute attacker-supplied `message.data` via `ICallDispatcher(_dispatcher).dispatch(message.data)`, with **no sweep-back step afterward**: [2](#0-1) 
- The documented use case explicitly acknowledges the dispatcher "can hold and forward native tokens" (e.g., a Uniswap swap leaving slippage-refunded ETH sitting in the dispatcher, since `swapETHForExactTokens` refunds excess ETH to `msg.sender`, which is the `CallDispatcher`): [3](#0-2) 
- `IntentGatewayV2`/`IntentsBase` route escrowed inputs/outputs through the same shared dispatcher and rely on an explicit, self-implemented sweep loop after `dispatch()` to reclaim any residual balance, implicitly confirming that non-zero dust can and does remain in the dispatcher between the `dispatch()` call and the sweep: [4](#0-3) 

Because `CallDispatcher` has no owner, no per-app allowlist, and no restriction on who may call `dispatch()`, any dust left behind by any of these flows — from slippage refunds, fee-on-transfer overshoot, tokens received via a predispatch/postdispatch call that aren't enumerated in `order.inputs`/`order.output.assets`, or ETH forwarded to the `CALL_DISPATCHER` address during an HFT/WHFT calldata-execution transfer without full consumption — is permanently up for grabs by any unprivileged third party who calls `dispatcher.dispatch(...)` with `Call({to: token, data: transfer(attacker, balance)})` or `Call({to: attacker, value: dispatcher.balance, data: ""})`.

### Impact Explanation
This is a concrete theft-of-funds primitive reachable by any unprivileged actor (a token bridger sending an HFT calldata-execution transfer, or an intent solver filling an order) with zero special privileges required to reach the exploitable state: they only need to cause (even accidentally, via slippage/fee-on-transfer/overshoot) some residual balance to sit in a shared `CallDispatcher` instance, after which anyone — not just the depositor — can drain it via a direct, unauthenticated `dispatch()` call. Given `CallDispatcher` is explicitly documented to "hold and forward native tokens" as part of normal HFT/WHFT swap flows, and IntentGatewayV2's own code implements defensive sweep logic (implicitly acknowledging dust accumulates), this is a realistic and recurring condition, not a purely theoretical edge case.

### Likelihood Explanation
High likelihood: any transaction that uses the `data`/`predispatch`/postdispatch calldata-execution features and does not perfectly account for every token/ETH balance touched by the executed calls (e.g., DEX slippage refunds, fee-on-transfer tokens, airdrops, unexpected refunds) will leave dust in the dispatcher. Because `dispatch()` is public with no allowlist, exploitation requires nothing more than monitoring the dispatcher's balance and submitting a single transaction calling `dispatch()` with a crafted `Call[]`.

### Recommendation
Add an access-control modifier (e.g., `onlyOwner`/`onlyCaller` restricted to the deploying app contract) to `CallDispatcher.dispatch()` so it can only be invoked by the specific `HyperFungibleToken`/`WrappedHyperFungibleToken`/`IntentGatewayV2` instance that deployed/owns it, and/or add a permissioned rescue function so any accumulated dust can only be swept by the legitimate app contract rather than by an arbitrary caller.

### Proof of Concept
1. A user calls `WrappedHyperFungibleToken.send()` with `to = CALL_DISPATCHER` and `data` encoding a Uniswap `swapETHForExactTokens` call that leaves refunded excess ETH in the `CallDispatcher` (per the documented pattern) — see `evm/src/utils/CallDispatcher.sol` `dispatch()` and the WHFT `onAccept` flow at `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:301-328`.
2. The refunded ETH remains in `CallDispatcher`'s balance since `onAccept` never sweeps residual balance back.
3. Any third party observes the non-zero balance and calls `CallDispatcher.dispatch(abi.encode([Call({to: attacker, value: dispatcher.balance, data: ""})]))` directly — no access control prevents this — draining the dust to themselves.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Calldata Execution

Pass a non-empty `data` field to execute arbitrary calls on the destination chain after tokens are unlocked. The `data` must be an ABI-encoded `Call[]` array (see [overview](/developers/evm/hyper-fungible-token/overview#calldata-execution) for the full `Call` struct and security details).

When `isWeth = true`, the WrappedHFT unwraps WETH to native ETH on receive. This example bridges WETH back to the home chain, where it's unwrapped to native ETH and swapped for an exact amount of USDC via UniswapV2. The `Call.value` field forwards the native ETH to the router — demonstrating that the `CallDispatcher` can hold and forward native tokens:

path[1] = USDC;

Call[] memory calls = new Call[](1);

    /**
     * @dev Executes arbitrary calldata attached to an order's output via the CallDispatcher.
     * After dispatching the calls, any residual token balances left on the dispatcher
     * are swept back to this contract and accounted for as protocol dust.
     *
     * This enables composable order fulfillment — solvers can route through DEXes,
     * lending protocols, or other DeFi primitives as part of filling an order.
     *
     * @param order The order containing the output calldata to execute.
     * @param outputsLen The number of output assets to sweep after execution.
     */
    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }
