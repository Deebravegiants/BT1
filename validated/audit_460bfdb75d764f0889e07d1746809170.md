### Title
Webhook `shop-domain` (and `topic`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, and `webhook_id` values that the handler subsequently trusts are taken from unauthenticated HTTP headers. Because Shopify signs webhooks with the app's single, shop-independent `api_secret_key`, any merchant who has installed the app can capture a legitimately-signed `(body, hmac)` pair from their own webhook deliveries and replay it against the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a different (victim) shop. The HMAC check still passes because it only verifies the body bytes, not the header bytes, so the handler processes the payload as if it belonged to the victim tenant.

### Finding Description
The equality the gem is supposed to guarantee is:

`bytes_covered_by_hmac == bytes_the_handler_trusts_as_the_tenant_identity`

but the actual behavior is:

`bytes_covered_by_hmac (body only) != bytes_the_handler_trusts_as_the_tenant_identity (shop/topic headers)`

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all read straight from HTTP headers, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `to_signable_string` (the raw body) and compares it to the `hmac` header, never touching `shop`/`topic`: [3](#0-2) 

`Registry.process` gates on that body-only HMAC check and then unconditionally trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Since Shopify signs webhooks for *every* shop that has the app installed using the same `api_secret_key` (the HMAC secret is per-app, not per-shop), any installed merchant can legitimately obtain a `(raw_body, hmac)` pair for their own shop and then POST that exact body/hmac to the same webhook endpoint while substituting the `shopify-shop-domain` (and optionally `shopify-topic`) header for a different, victim shop. `HmacValidator.validate` still returns `true` because the body bytes are unchanged, so `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an app that keys any state, side effects, or data writes off `WebhookMetadata#shop` (e.g., updating orders/inventory/customer records "for that shop", or triggering per-shop billing/business logic) can be made to apply another shop's webhook payload to a shop chosen by the attacker. This is a cross-tenant access/data-integrity issue reachable by any unprivileged merchant who has installed the app — no `api_secret_key`, access token, or other credential leak is required beyond what the attacker already legitimately receives from Shopify for their own shop.

### Likelihood Explanation
High. Any merchant that installs the app receives real webhook deliveries (body + `hmac-sha256` header) that they fully control the delivery endpoint for (their own server or a proxy), so capturing a valid `(body, hmac)` pair is trivial. Replaying it with a spoofed `shop-domain` header to the target app's public webhook endpoint requires no special access.

### Recommendation
Bind the tenant identity to the signed content instead of trusting unauthenticated headers:
- Include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator` (Shopify's actual webhook HMAC is computed over the raw body per Shopify's spec, so instead the gem should independently confirm the claimed `shop` against a source of truth, e.g., verify the shop is a session/store the app has actually installed the app for and that the specific webhook subscription's expected shop matches), or
- At minimum, cross-check `request.shop` against the shop associated with the currently active/loaded session/subscription before invoking the handler, rejecting mismatches.

### Proof of Concept
1. App installs webhooks; Attacker (shop A, a real merchant with the app installed) receives a legitimate webhook at their configured endpoint:
   - Headers: `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid HMAC of body>`, `shopify-shop-domain: shop-a.myshopify.com`
   - Body: `{"id": 123, ...}`
2. Attacker resends the exact same body and `hmac-sha256` value to the app's public webhook endpoint, but changes the header to:
   - `shopify-shop-domain: shop-b.myshopify.com` (victim shop)
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over the unchanged raw body and it matches the replayed `hmac` header, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, even though the payload never originated from shop B.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
