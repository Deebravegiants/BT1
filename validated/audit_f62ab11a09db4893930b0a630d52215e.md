### Title
Webhook `shop` identity is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC signature that `ShopifyAPI::Utils::HmacValidator.validate` checks in `ShopifyAPI::Webhooks::Registry.process` never covers the `x-shopify-shop-domain` header. That header is nevertheless trusted as the tenant identity and handed straight to the host application's webhook handler.

### Finding Description
`Registry.process` gates webhook handling solely on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body — the `shop`, `topic`, `webhook_id`, and `api_version` headers are excluded from the signed material: [3](#0-2) 

Yet `Registry.process` passes `request.shop` — parsed straight from the unauthenticated header — into `WebhookMetadata`, which is the tenant identity the host application uses to route/attribute the payload: [4](#0-3) 

The equality this breaks is: `shop asserted by HMAC-signed bytes == shop acted on by the handler`. The gem authenticates only `(secret, raw_body) -> hmac`; it does not bind `shop` into that computation. `api_secret_key` is shared across every merchant that installs a given app (it's the app's client secret, not per-tenant), so any two webhook deliveries for the same app produce HMACs that are valid regardless of which shop header accompanies them.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (any unprivileged user can install a public/embeddable app) will receive genuinely signed webhooks — e.g., `(raw_body=B, hmac=HMAC(secret, B), shop-domain=attacker-shop.myshopify.com)`. Because `shop` is not part of the signed bytes, the attacker can resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still returns `true`, and `Registry.process` invokes the host handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker-controlled-JSON, ...)`. This lets an unprivileged, unauthenticated-to-the-victim attacker inject data that is attributed to a different merchant's tenant — a cross-tenant identity/data confusion, matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on an attacker-controlled store to obtain one genuinely signed webhook body/HMAC pair (or otherwise obtain any signed pair for that app), and (2) sending an HTTP POST to the app's webhook endpoint with a forged `shop-domain` header. No `api_secret_key`, access token, or privileged account is required — this is exploitable by any internet user who can self-register a shop with the app.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise require the host application to verify `request.shop` against the shop associated with the specific `webhook_id`/subscription before trusting it. At minimum, document prominently that `request.shop` is unauthenticated and must be independently verified by the host app against its own tenant/installation records before use, since currently the gem's own `process` method passes it straight through as if it were verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures/receives a real webhook, e.g. `orders/create`, capturing:
   - `raw_body = B`
   - `x-shopify-hmac-sha256 = Base64(HMAC-SHA256(api_secret_key, B))`
2. Attacker sends a POST to the app's webhook endpoint with:
   - `raw_body = B` (unchanged)
   - `x-shopify-hmac-sha256` (unchanged, still valid because only `B` is signed — see `Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:36-38`)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: orders/create`
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls `HmacValidator.validate(request)`, which passes since it only checks `B` against the HMAC.
4. The host handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and processes/stores data as if it originated from the victim's shop, even though `B` and the signature came from the attacker's own installation.
