## Analog Finding

### Title
Missing freeze-authority validation on coin/pc mints in `Initialize2` permits permanent freezing of LP and swap funds - ([File: program/src/processor.rs])

### Summary
The BASED incident described a hacker attempting to permanently freeze "Pool1" via a manipulation of the pool's underlying assets. In this codebase, `process_initialize2` validates that the LP mint has no freeze authority, but performs no equivalent check on the `coin_mint` / `pc_mint` supplied by the (unprivileged) pool creator. A pool creator can pick any SPL mint — including one where the mint's freeze authority is retained by the creator or a colluding party — as the pool's `coin_mint`/`pc_mint`. Once liquidity providers deposit into that pool, the mint's freeze authority can call `FreezeAccount` on the AMM's `coin_vault`/`pc_vault` token accounts, permanently disabling all subsequent `Swap`, `Deposit`, and `Withdraw` calls for that pool and permanently locking all LP and swapper funds inside the frozen vaults.

### Finding Description
In `Processor::process_initialize2`, the program unpacks the `coin_mint` and `pc_mint` and checks only that they differ from each other: [1](#0-0) 

It later unpacks the LP mint and explicitly rejects it if it carries a freeze authority: [2](#0-1) 

The same rejection is never applied to `coin_mint` / `pc_mint`. The AMM vaults (`amm_coin_vault_info`, `amm_pc_vault_info`) are SPL token accounts of those mints, owned by the `$authority` PDA: [3](#0-2) 

Because the mint's freeze authority is a separate keypair unrelated to the AMM `$authority` PDA, it can call the SPL Token Program's `FreezeAccount` instruction directly on `amm_coin_vault`/`amm_pc_vault` at any time after pool creation — completely outside of any Raydium instruction. Once frozen, every downstream Raydium instruction that CPIs into `spl_token::instruction::transfer` on the frozen vault (Deposit, Withdraw, Swap paths in `Invokers`) will fail, because the SPL Token Program itself blocks transfers on frozen accounts. There is no unfreeze path reachable from this program (the AMM `$authority` PDA is not the freeze authority), so the freeze is permanent for that pool.

### Impact Explanation
This results in permanent freezing of LP and swap funds for any pool created with a freezable mint, matching the "Validate" criterion of concrete permanent freezing of user/LP funds. All coin and pc vault balances, and any LP token holders' underlying claim, become permanently inaccessible through the AMM once the mint's freeze authority freezes the vault. This is directly analogous to the BASED report where an actor attempted to permanently freeze a staking/liquidity pool.

### Likelihood Explanation
Likelihood is Medium-to-High: pool creation via `Initialize2` is fully permissionless — any unprivileged user can pick arbitrary `coin_mint`/`pc_mint` accounts and become the pool creator. A malicious pool creator can mint a token with a freeze authority they control, seed the pool, attract deposits/liquidity, and later freeze the vault to trap victim funds — a single attacker-controlled transaction sequence with attacker-chosen mint accounts, requiring no privileged access to the Raydium program itself.

### Recommendation
Add a check in `process_initialize2` mirroring the existing LP mint check, rejecting `coin_mint`/`pc_mint` that have a non-`None` `freeze_authority`, e.g.:
```rust
if coin_mint.freeze_authority.is_some() || pc_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
```
placed immediately after unpacking `coin_mint`/`pc_mint`: [4](#0-3) 

### Proof of Concept
1. Attacker creates SPL mint `M` and retains the freeze authority (does not set it to `None`).
2. Attacker calls `Initialize2` (via `initialize2` instruction builder) with `amm_coin_mint = M`, seeding initial liquidity: [5](#0-4) 
3. `process_initialize2` proceeds without rejecting `M` for having a freeze authority (only `lp_mint.freeze_authority` is checked): [2](#0-1) 
4. Other users call `Deposit`/`Swap` against the new pool, growing `amm_coin_vault` balance of mint `M`.
5. Attacker, holding `M`'s freeze authority, submits a direct SPL Token Program `FreezeAccount` instruction targeting `amm_coin_vault`.
6. All subsequent `Deposit`, `Withdraw`, and `Swap` calls on that pool now fail at the `Invokers::token_transfer` CPI step because the vault is frozen, permanently locking all deposited funds in that pool.
