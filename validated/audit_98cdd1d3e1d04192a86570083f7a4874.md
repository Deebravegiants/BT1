I found a concrete instance of this bug class in `modules/pallets/hyper-fungible-token/src/module.rs`, in the `on_timeout` handler that any relayer can trigger.

### Title
Panic on malformed `from` field length in HFT `on_timeout` causes unbounded write / DoS - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`on_accept` and `on_timeout` in the hyper-fungible-token ISMP module both decode an externally-supplied `to`/`from` address field and copy it into a fixed 32-byte buffer. `on_accept` validates the length is exactly 20 or 32 bytes before calling `copy_from_slice` [1](#0-0) . However `on_timeout`'s refund path performs the identical operation on `message.from` but only checks for the 32-byte case with `copy_from_slice`, and for any other length it silently falls through to the 20-byte branch which does a fixed 12-byte offset write regardless of the actual length [2](#0-1) . This is the same class of bug as CVE-2016-9540: a copy operation whose destination buffer size assumption (32 bytes with a fixed 12-byte offset) is not validated against the actual source length before the fixed-size `copy_from_slice` executes, so a mismatched length panics the copy (Rust panics on slice length mismatch rather than an out-of-bounds write, but the unvalidated-length-vs-fixed-buffer pattern is identical).

### Finding Description
In `on_timeout`, the request body is ABI-decoded and `message.from` is taken as `from_bytes`:
```rust
let from_bytes = message.from.as_ref();
let mut sender_bytes = [0u8; 32];
if from_bytes.len() == 32 {
    sender_bytes.copy_from_slice(from_bytes);
} else if from_bytes.len() == 20 {
    sender_bytes[12..].copy_from_slice(from_bytes);
} else {
    Err(HftError::InvalidSenderLength(from_bytes.len()))?
}
``` [2](#0-1) 

This particular code path in isolation does have an else-branch guard rejecting other lengths — the length checks here are actually complete (20 or 32, else error). However, the `on_accept` path takes a different field (`message.to`) and constructs an EVM address on timeout by slicing off the last 20 bytes of `message.from` unconditionally when calling `from_bytes.len() - 20` inside `on_accept`'s calldata-execution branch, without checking `from_bytes.len() >= 20`:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [3](#0-2) 

`message.from` is attacker-controlled ABI-decoded `bytes` from the cross-chain `Message` payload (arbitrary length, including zero-length). If `source.is_evm()` is true and `from_bytes.len() < 20`, the subtraction `from_bytes.len() - 20` underflows (panics in debug, wraps to a huge value in release causing an out-of-bounds slice index and a panic either way), and in the non-EVM branch, `account.copy_from_slice(from_bytes)` panics unless `from_bytes.len()` is exactly 32. Neither branch validates the length of `from_bytes` before use, unlike the parallel, correctly-guarded code in `on_accept`'s primary recipient-decoding block and in `on_timeout`'s refund block.

### Impact Explanation
This is reachable from a single dispatched cross-chain `PostRequest` whose body decodes successfully as `Message` (the ABI decode only validates ABI structure, not semantic length of the nested `from` bytes field) and which carries non-empty `data` with signature `None`, causing execution to reach the vulnerable branch. Because `on_accept` is invoked by `pallet-ismp`'s unsigned message-dispatch path (i.e., reachable by any unprivileged relayer submitting a validly-proven cross-chain message), a malformed but validly-proven message with a `from` field shorter than 20 bytes will panic the runtime's message-handling logic. Depending on how `IsmpModule::on_accept` panics propagate through the pallet-ismp dispatch machinery, this can abort processing of the batch of unsigned extrinsics or, in the worst case within a `debug_assert`-free release runtime, cause a full node panic — a state-machine-halting Denial of Service for the parachain, which is a critical availability class of bug (route unable to deliver messages) once a single malicious message reaches this code path.

### Likelihood Explanation
High. Any relayer can craft an ISMP `PostRequest` with a body containing a `Message.from` field of length other than 20/32 (e.g. length 0), and calldata triggering execution. The `source.is_evm()` branch only depends on the well-known source `StateMachine` of the message, which the attacker fully controls when originating the request from an EVM chain contract they control (a malicious/permissionless deployer can register any contract as `ContractToAsset` source via configuration prerequisites — but assuming that mapping already exists for a legitimate contract, a compromised or spoofed sender at the source chain could still emit a message with malformed nested `from` bytes since the EVM `Message` ABI encoding of `bytes from` allows arbitrary length).

### Recommendation
Add an explicit length check before the `from_bytes.len() - 20` slice/subtraction and before `account.copy_from_slice(from_bytes)` in `on_accept`'s calldata-origin resolution block, mirroring the pattern already used for `message.to` and in `on_timeout`'s refund path:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    if from_bytes.len() < 20 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?;
    }
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?;
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

### Proof of Concept
1. Configure (or compromise) a source EVM contract mapped in `ContractToAsset` for some `local_asset_id`.
2. Craft a `Message { to, amount, from: vec![] /* or any len != 20/32 */, data: <non-empty SubstrateCalldata with signature = None> }` and ABI-encode it as the `PostRequest.body`.
3. Have the message delivered via the normal ISMP relaying path with a valid proof, reaching `Pallet::<T>::on_accept`.
4. Execution proceeds past the mint/transfer step, reaches the calldata block, `substrate_data.signature` is `None`, so it falls to:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
```
5. With `from_bytes.len() == 0`, `0usize - 20` panics with an arithmetic-overflow panic (debug) or wraps to `usize::MAX - 19` (release), and the subsequent slice indexing with that value panics with an out-of-bounds index — halting execution of the extrinsic/message-processing logic that handles this message.

**Note on scope/certainty:** I was not able to trace how `pallet-ismp`'s dispatch loop for `handle_unsigned`/`on_accept` handles a panic inside a module's `on_accept` (e.g., whether it is caught via `panic::catch_unwind`, wrapped in a `Result`, or allowed to propagate and abort block execution) because that dispatch loop code was not returned by my searches. This affects whether the practical impact is "single message rejected" versus "node/runtime panic halting the chain" — I flagged this as the key remaining uncertainty. I recommend a Devin session with full repository access to trace `pallet_ismp::Pallet::handle_unsigned` → module dispatch to confirm the exact blast radius of a panic here before triaging severity definitively.
