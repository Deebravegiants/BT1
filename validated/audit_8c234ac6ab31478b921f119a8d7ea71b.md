### Title
Webhook Tenant Spoofing via Shop-Domain Header Not Covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) identifier from the `X-Shopify-Shop-Domain` header, but the HMAC signature that `HmacValidator` verifies is computed only over the raw request body, not the shop header. `Registry.process` accepts the request as authentic once the body-only HMAC checks out, and hands the caller-supplied (unauthenticated) `shop` value straight to the webhook handler. This breaks the identity binding `HMAC-authenticated bytes == shop attribution used by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string`, i.e., only the body: [2](#0-1) 

`Registry.process` trusts the request once this body-only HMAC passes, and forwards `request.shop` — read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header — to the handler as the tenant identity for the event: [3](#0-2) [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that installs the app, an HMAC computed over a given body is identical no matter which shop the event is nominally "from." An attacker who controls a shop with the app installed (a normal, unprivileged action) will receive genuine Shopify-signed webhook deliveries for events they themselves generate. The HMAC on that delivery only proves "this body was signed by the app's secret" — it proves nothing about which shop it pertains to, since that binding lives solely in an easily-rewritten HTTP header. The attacker can therefore replay the exact same body + HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop domain of their choosing. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched), and `Registry.process` invokes the handler with `WebhookMetadata.shop` set to the victim's domain and attacker-controlled `body`/`topic`.

This is the same class of bug as the referenced report: the code verifies one thing (HMAC over the body) but a downstream consumer trusts a different, unverified field (the shop header) as if it were part of the authenticated payload — exactly the "bytes verified versus bytes parsed" / tenant-key confusion pattern.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which merchant's session/access token to act on, or to key persisted state (a documented and expected usage pattern for this gem, as shown in the gem's own tests and docs), can be made to perform actions against/on behalf of a shop the attacker does not control, using attacker-chosen topic/body content taken from their own shop's legitimate deliveries. This crosses the tenant boundary that the HMAC check is meant to enforce, qualifying as cross-tenant access.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on their own store (an ordinary, unprivileged action available to any merchant/developer) and be able to intercept/replay the HTTP request to the app's public webhook endpoint with a modified header — no access to `api_secret_key` or any privileged credential is needed. The header rewrite is trivial; the HMAC remains valid because it never covered the header in the first place.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the header set to the signed payload, so that `Utils::HmacValidator.validate` fails if any header used for tenant attribution has been altered. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop` so `HmacValidator` enforces the same binding the handler relies on.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook delivery (e.g., `orders/create`) with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(app_secret, B)`.
2. Attacker replays the identical request to the app's public webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(app_secret, B)` and compares it to `H` — this still matches because the HMAC never included the shop header: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, despite the request never having been authenticated as originating from that shop.
