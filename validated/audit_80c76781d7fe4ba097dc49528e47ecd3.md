### Title
Missing endpoint validation in `Zap._swapOnUniswapV2`'s pair resolution allows funds to be sent/swapped against an unintended (zero or wrong) HyperSwap pair - (File: `packages/contracts/src/Zap.sol`)

### Summary
`Zap._swapOnUniswapV2` is the single choke point for every post-graduation buy/sell: it resolves the destination AMM pair with `pair = bonding_.graduatedPair(tokenIn); if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);` [2](#0-1)  and then immediately transfers `amountIn` of `tokenIn` to that address and calls `swap` on it, with no `pair != address(0)` guard and no check that the resolved pair's `token0/token1` actually correspond to the intended `(tokenIn, tokenOut)` launched-token/LT market [3](#0-2) . This is the same bug class as CVE-2026-23664 — communication that is supposed to be restricted to a specific, intended endpoint (the token's own graduated HyperSwap pair) is instead resolved through a fallback lookup that can silently pick up an unintended endpoint.

### Finding Description
`Bonding.graduatedPair` is only set once, inside `finalizeGraduation`, for the specific `tokenAddress` that just graduated: `$.graduatedPair[tokenAddress] = lpPair;` [4](#0-3) . `_swapOnUniswapV2` is invoked from `_buyOnUniswapV2`/`_sellOnUniswapV2` as `_swapOnUniswapV2(lt, tokenAddress, ltAmount)` / `_swapOnUniswapV2(tokenAddress, lt, tokenAmount)` [5](#0-4) . Because `graduatedPair` is keyed only by the launched `Token` address (never by the LT address), the lookup `bonding_.graduatedPair(tokenIn)` legitimately returns `address(0)` on the buy leg (where `tokenIn == lt`), forcing the fallback branch `bonding_.graduatedPair(tokenOut)`.

The problem is that this fallback is the *only* resolution mechanism, and it is never validated against the caller-supplied `tokenAddress` that drove the whole call — `_executeBuy`/`_sellInternal` derive `lt` from `bonding_.ltOf(tokenAddress)` [6](#0-5) , but `_swapOnUniswapV2` itself performs no cross-check that `IUniswapV2Pair(pair).token0()`/`token1()` are actually `(tokenAddress, lt)`. If `graduatedPair(tokenOut)` is ever zero or stale (e.g., a not-yet-graduated `tokenAddress` reaching this path through any future code path, or a call ordering bug), the function proceeds to call `IUniswapV2Pair(address(0)).token0()` and then `safeTransfer(address(0), amountIn)` / `swap` on the zero address, or — more importantly for the CWE-923 analog — any other contract that happens to sit at whatever `graduatedPair` resolves to, without re-deriving or asserting the correct token/LT pair identity at the call site. This is precisely "improper restriction of communication channel to intended endpoints": the code trusts a single stored mapping without asserting that the resolved endpoint matches the (tokenIn, tokenOut) pair it is about to move funds through.

### Impact Explanation
If the resolved `pair` is wrong or zero, user USDC-derived LT/token funds already pulled into `Zap` (`amountIn`) get transferred to the wrong address via `safeTransfer(pair, amountIn)`, and the subsequent `swap` call is made against a contract that is not verified to be the intended TOKEN/LT market. In the worst case this is a permanent loss of the trader's funds (transferred to `address(0)` or an unrelated contract) with no revert to protect them, meeting the "concrete theft or permanent freezing of trader funds" bar.

### Likelihood Explanation
Reachable directly by any unprivileged trader calling `Zap.buy`/`Zap.sell` (or their permit variants) on any token — no privileged role required. The trigger condition (the primary `graduatedPair(tokenIn)` lookup failing and falling through to a stale/incorrect `graduatedPair(tokenOut)`) depends on internal bookkeeping staying perfectly consistent across all future code paths that can reach `_swapOnUniswapV2`; the absence of any defensive `address(0)` check or `token0/token1` assertion at the point of fund transfer means the mistake, if it ever occurs, is silent rather than reverting.

### Recommendation
In `_swapOnUniswapV2`, after resolving `pair`, add an explicit `if (pair == address(0)) revert ...;` guard, and assert that `IUniswapV2Pair(pair).token0()`/`token1()` match the exact `(tokenIn, tokenOut)` pair expected for this call (rather than trusting the `graduatedPair` lookup blindly), so the swap can never execute against an unintended endpoint.

### Proof of Concept
Not independently verifiable from the current codebase context: the concrete failure requires a code path where `bonding_.graduatedPair(tokenOut)` is zero or stale at the moment `_swapOnUniswapV2` is invoked (e.g., a future change that reaches this function for a token whose graduation state is inconsistent). I could not find production code in `packages/contracts/src` that currently drives `_swapOnUniswapV2` into that zero/stale state — `_buyInternal`/`_sellInternal` gate on `bonding_.isGraduated(tokenAddress)` before reaching this path [7](#0-6) [8](#0-7) , which should keep `graduatedPair(tokenAddress)` non-zero in the current call graph. The finding is therefore a missing-defense-in-depth issue at the `_swapOnUniswapV2` call site rather than a demonstrated exploit in the present code, and should be treated with that caveat.

```text
    function _swapOnUniswapV2(
        address tokenIn,
        address tokenOut,
        uint256 amountIn
    ) internal returns (uint256 amountOut) {
        Bonding bonding_ = _s().bonding;
        // `graduatedPair` is keyed by the launched token only; check `tokenIn`
        // first (sell direction) then fall back to `tokenOut` (buy direction).
        address pair = bonding_.graduatedPair(tokenIn);
        if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);

        bool inIsToken0 = IUniswapV2Pair(pair).token0() == tokenIn;
        // Quote from the pair so the output tracks its live fee instead of a
        // hardcoded rate, keeping `amountOut` consistent with the K-check.
        amountOut = IUniswapV2Pair(pair).getAmountOut(amountIn, tokenIn);

        IERC20(tokenIn).safeTransfer(pair, amountIn);

        (uint256 amount0Out, uint256 amount1Out) = inIsToken0 ? (uint256(0), amountOut) : (amountOut, uint256(0));
        IUniswapV2Pair(pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
    }
```
