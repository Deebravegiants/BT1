The pattern matches the CVE class exactly: a message field originating from an untrusted, permissionlessly relayed cross-chain payload is sliced with a length arithmetic operation (`len() - 20`) without first validating that the length is at least 20, unlike the `to`/`sender` conversion logic in the same file which does validate lengths.

### Title
Unchecked length subtraction on attacker-controlled `message.from` causes panic in `on_accept` cross-chain calldata path - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
In `HftError`-guarded `on_accept`, when a delivered ISMP `PostRequest` carries optional calldata (`message.data`) without an embedded signature, the module derives the dispatch origin from `message.from` for EVM sources via:
```rust
T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
``` [1](#0-0) 
`from_bytes` comes directly from the ABI-decoded `Message` field `from`, which is arbitrary attacker-controlled bytes carried in the cross-chain message body — it is never length-validated before this subtraction/slice.

### Finding Description
`message` is decoded from `body` via `Message::abi_decode(&body)` [2](#0-1)  and `from` is an ABI `bytes` field fully controlled by whoever dispatches/relays the corresponding cross-chain message (an unprivileged relayer/token bridger delivering a `PostRequest` via ISMP `HandlerV2`/`onAccept`). Elsewhere in the same function the code carefully validates recipient length before use (`to_bytes.len() == 32`/`== 20`, else error) [3](#0-2) , and the `on_timeout`/refund path also validates `from_bytes.len()` before use [4](#0-3) . However, the `on_accept` calldata-execution branch skips this validation entirely: if `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), producing either a panic (debug/checked arithmetic) or an enormous index that panics on the subsequent out-of-bounds slice (release). This mirrors the underlying bug class in the reported ath12k CVE: a length field from untrusted input is used to compute a byte-range access without a prior sanity/bounds check, leading to invalid memory access.

### Impact Explanation
This code path executes only after the token mint/transfer to the beneficiary has already succeeded (lines 93–117 execute unconditionally before reaching the vulnerable slice) [5](#0-4) . A relayer/token-sender who controls the source contract mapping (`ContractToAsset`) can craft a message with non-empty `data`, no `signature`, a `from` field shorter than 20 bytes, and `source.is_evm() == true`, triggering a runtime panic during extrinsic execution. In a Substrate/FRAME pallet-ismp module callback, an unhandled panic inside `on_accept` typically aborts the whole transaction/block execution path for message processing, which can be used to permanently block delivery of that specific request (and, depending on how the runtime handles panics in this dispatch context, potentially disrupt the ISMP message-processing pipeline) — a denial-of-service on the token bridge's inbound message route.

### Likelihood Explanation
Reaching this code requires only: (1) a registered `ContractToAsset` mapping for the attacker's chosen `(source, from)` pair — which is governance/config-dependent and may limit who can trigger it — and (2) crafting an ABI-encoded `Message` with `data` non-empty, no `signature` field, and a `from` field of fewer than 20 bytes. Since `from` is an arbitrary `bytes` ABI field with no length constraint enforced by the Solidity contract or the pallet before this point, this is straightforward for anyone able to originate/relay a `PostRequest` to a configured source contract.

### Recommendation
Before the slice, validate `from_bytes.len()` explicitly (mirroring the `to_bytes` validation and the `on_timeout` handler), returning an `HftError` (e.g., a new `InvalidSenderLength` variant) when the length is neither 20 nor 32 bytes, instead of performing unchecked pointer/length arithmetic.

### Proof of Concept
1. Configure `ContractToAsset::<T>::insert(source, from_contract, local_asset_id)` (as would occur in normal bridge setup).
2. From `source` (an EVM state machine), submit an ISMP `PostRequest` whose ABI-encoded body decodes to a `Message` with: `to` = valid 20/32-byte recipient, `amount` = any valid amount, `data` = a non-empty `SubstrateCalldata`-encoded payload with `signature = None`, and `from` = a byte string of length < 20 (e.g., 1 byte).
3. Deliver the request through the configured relayer/`HandlerV2` path so `on_accept` is invoked.
4. Execution reaches `from_bytes.len() - 20` with `from_bytes.len() == 1`, causing an underflow/panic at `modules/pallets/hyper-fungible-token/src/module.rs:180`, after the mint/transfer at lines 93–117 has already been applied.
