### Title
Webhook `shop` identity is taken from an unsigned header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the tenant-identifying `shop` (and `topic`/`webhook_id`) values are read straight from unauthenticated HTTP headers and are never included in the signed bytes. This breaks the identity binding `hmac == HMAC(secret, body ‖ shop)` down to `hmac == HMAC(secret, body)`, letting anyone who possesses one valid `(body, hmac)` pair for the shared app secret replay it while freely substituting the `shop` header to impersonate a different merchant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never part of the signed payload: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e., the body alone), then immediately trusts `request.shop` from the unauthenticated header to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms the signature is computed strictly over `verifiable_query.to_signable_string`, with no header material mixed in: [4](#0-3) 

Because every shop installed on a given app shares the same `api_secret_key`, any merchant (including an attacker who legitimately installs the app on their own store) can trigger a real webhook for a topic they control, capture the resulting `(body, hmac)` pair, and then replay it to the app's public webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain. The signature still validates (it only covers the body), so `Registry.process` dispatches the payload to the app's handler tagged as belonging to the victim shop — an equality (`authenticated body-owner == attributed shop`) that the code never actually checks.

### Impact Explanation
This is a cross-tenant identity-confusion vector: application code that trusts `data.shop` from `WebhookMetadata` (as documented and shown in this gem's own usage docs) to look up per-shop state, dispatch per-shop side effects, or attribute the webhook body to a tenant can be made to process attacker-supplied JSON under another merchant's identity. Depending on how the host app uses `data.shop` (e.g., keying database writes, background jobs, or session lookups), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" High/Critical impact class.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on any shop (a normal, unauthenticated action for public/embedded Shopify apps) can generate a validly-signed webhook body/HMAC pair for themselves and then freely replay it against the app's public webhook callback URL with an arbitrary `shop-domain` header, since nothing in this gem ties the header to the signature or to the originating shop's registered webhook subscription.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or independently verify that the `shop` header corresponds to a shop that has an active registration/session for the given `webhook_id`/topic before dispatching to the handler, rather than trusting the header value outright once only the body HMAC has been checked.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and receives
# a genuine webhook signed with the shared api_secret_key:
body = '{"id":1,"note":"legit payload from attacker-owned shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Attacker now replays the same (body, hmac) but spoofs the shop-domain header:
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (it only checks `body`),
# and the handler receives data.shop == "victim-shop.myshopify.com"
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
