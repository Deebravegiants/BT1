### Title
Unsanitized cache-key concatenation in `DirectBridge.getCachedStorageDepositValue` lets an attacker-controlled `contractId`/`accountId` pair collide with an unrelated cached entry, causing the storage-deposit fee to be miscalculated - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge` caches the NEAR storage-deposit lookup (`[minStorageBalance, userStorageBalance]`) used to compute the `storageDepositFee` portion of a withdrawal's fee. The cache key is built by naively concatenating two attacker-influenced strings, `tokenAccountId` and `destinationAddress`, with no separator: `` `${contractId}${accountId}` ``. Because NEAR account IDs are dot/hyphen-delimited strings of variable length, two different `(contractId, accountId)` pairs can produce the identical concatenated key, letting a party read (and act on) a storage-balance result that was computed for a completely different token contract/account pair.

### Finding Description
`estimateWithdrawalFee` calls `getCachedStorageDepositValue(tokenAccountId, destinationAddress)`: [1](#0-0) 

```

    contractId: string,
    accountId: string,

    const key = `${contractId}${accountId}`;
    const cached = this.storageDepositCache.get(key);
    ...
}
```

`tokenAccountId` comes from `parseDefuseAssetId(withdrawalParams.assetId)`, and `accountId` is the caller-supplied `destinationAddress`, both of which are NEAR account identifiers (dot-separated segments, arbitrary length). Because the key is a plain string concatenation with no delimiter, two distinct pairs can yield the same key, e.g.:
- `contractId = "usdc.near"`, `accountId = "alice.bob.near"` → key `"usdc.nearalice.bob.near"`
- `contractId = "usdc.nearalice"`, `accountId = "bob.near"` → key `"usdc.nearalice bob.near"` (same concatenation, different split)

An attacker who controls the pair used for one estimation call can deliberately choose an `assetId`/`destinationAddress` combination whose concatenation collides with the key of a legitimately cached, "storage already covered" entry (which is only cached when `userStorageBalance >= minStorageBalance`, i.e., `storageDepositFee = 0`). On a collision, the fee-estimation logic: [2](#0-1) 

```
const [minStorageBalance, userStorageBalance] =
    await this.getCachedStorageDepositValue(
        tokenAccountId,
        args.withdrawalParams.destinationAddress,
    );

if (minStorageBalance <= userStorageBalance) {
    return { amount: 0n, quote: null, underlyingFees: { [RouteEnum.NearWithdrawal]: { storageDepositFee: 0n } } };
}
```

would incorrectly report `storageDepositFee: 0n` for a destination account that, in reality, has no storage registered on the actual token contract. This is the same root-cause pattern flagged in the BathBuddy report: state used to compute a monetary outcome (fee) is read from a cache whose key/identity does not uniquely correspond to the entities it is supposed to represent, so the on-chain reality (the real storage balance of the real `(token, account)` pair) diverges from what the accounting logic assumes.

### Impact Explanation
When the fee estimate under-reports the required storage deposit, `IntentsSDK.createWithdrawalIntents` builds the withdrawal intent with an `actualAmount` that does not include the missing storage-deposit fee (see `sdk.ts` `_estimateWithdrawalFee`/`createWithdrawalIntents`, which trust the bridge's `estimateWithdrawalFee` result to size `feeEstimation.amount`). The resulting `ft_withdraw` will be submitted without the funds needed to cover `storage_deposit` on the destination token contract, causing the on-chain transfer to fail or the funds to become stuck until manual intervention — a "withdrawal stuck until manual intervention" scenario. The inverse case (colliding with an entry that assumed storage was *not* paid) can force an unnecessary storage-deposit fee to be added to a withdrawal, overcharging the user. Both outcomes match the listed High-impact categories (stuck withdrawal / fee overcharge).

### Likelihood Explanation
Exploitability depends on being able to choose an `assetId` (hence `tokenAccountId`) and `destinationAddress` whose concatenation collides with another already-cached key. Since both `contractId` and `accountId` are valid NEAR account-id strings of variable, attacker-influenced length and only `parseDefuseAssetId` format validation (not existence) gates `tokenAccountId`, an attacker with knowledge of a popular, frequently-queried `(token, destination)` pair (which is easy to predict — e.g. well-known token contracts and a wallet the attacker also controls) can craft their own `assetId`/`destinationAddress` split to reproduce the exact same character sequence. The cache has up to 100 entries with a 1-hour TTL, giving a real window for a crafted collision to hit a live cached entry. This is a purely unprivileged, integrator-side condition — no relayer, RPC, or admin misbehavior is required — so it meets the "unprivileged analog" bar, though weaponizing it requires the attacker to predict or seed a colliding, already-cached counterpart entry, which lowers likelihood somewhat compared to a trivially-reachable bug.

### Recommendation
Use a collision-free cache key, e.g. join the two identifiers with a delimiter that cannot appear ambiguously, or use a structured key such as an array/tuple-based cache (or `JSON.stringify([contractId, accountId])`), e.g.:
```
const key = `${contractId}\u0000${accountId}`;
```
or key the `LRUCache` on a composite object/tuple instead of a concatenated string. Apply the same review to any other place in `direct-bridge.ts`/`omni-bridge.ts` that builds cache keys from multiple dynamic identifiers.

### Proof of Concept
Conceptual reproduction (illustrates the key-collision mechanism, since the cache is a private field of `DirectBridge`):
```ts
// biome-ignore lint/complexity/useLiteralKeys: accessing private property for testing
bridge["storageDepositCache"].set("usdc.nearalice.bob.near", [1250000000000000000000n, 1250000000000000000000n]); // pretend this was legitimately cached for tokenAccountId="usdc.near", accountId="alice.bob.near" (storage already paid)

// Attacker crafts assetId/destinationAddress that concatenate to the SAME string
// tokenAccountId = "usdc.nearalice", destinationAddress = "bob.near"
const result = await bridge.estimateWithdrawalFee({
  withdrawalParams: {
    assetId: "nep141:usdc.nearalice",
    destinationAddress: "bob.near",
  },
});

// result.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee === 0n
// even though "bob.near" has never registered storage with "usdc.nearalice"
```
This demonstrates that `getCachedStorageDepositValue`'s naive string-concatenation key can return storage-balance data belonging to an entirely different `(contractId, accountId)` pair, breaking the equality between the fee actually required on-chain and the fee reported to the caller.

	/**
	 * Gets storage deposit for a token to avoid frequent RPC calls.
	 */
	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
