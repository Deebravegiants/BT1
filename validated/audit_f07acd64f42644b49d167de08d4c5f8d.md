### Title
Front-run of Emporium's stateless external calls permanently freezes claimed reward/asset value that the balance-delta accounting silently drops - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` accounts for value received from arbitrary external calls using a `balanceBefore`/`balanceAfter` delta over the shared Emporium contract's own balance, exactly the pattern flagged in H-16. Because Emporium is a single, well-known, shared contract address used by all Hinkal users (not per-user), and CASE 2 "stateless" ops let the prover-supplied `callData` invoke *any* external endpoint on behalf of Emporium, an unprivileged front-runner can pre-trigger the same external call (e.g., a public `claim`/`getReward(address account)` style function that accepts an arbitrary recipient, as in the original Convex bug) targeting Emporium's address before the user's `transact()` executes. The externally-arriving tokens land on Emporium before `balancesBefore` is snapshotted, so the user's own op yields `balanceChange == 0`, and `handleOut` explicitly ignores non-positive deltas, silently discarding the value instead of minting a UTXO for it.

### Finding Description
In `EmporiumUpgradeable.runAction`: [1](#0-0) 
balances of `circomData.erc20TokenAddresses` are snapshotted for the Emporium contract itself before any ops run, then again after: [2](#0-1) 

The "CASE 2: Stateless Interaction" branch lets the prover-supplied metadata make Emporium itself call an arbitrary `op.endpoint` with arbitrary `op.callData` (only `callHinkalWallet`/`doSendToRelay` selectors are blocked): [3](#0-2) 

`runAction` is only gated by `onlyAllowedRecipient`, which merely restricts the caller to a registered Hinkal-family contract, not to any specific user — so Emporium is a single, shared, well-known address for all users: [4](#0-3) 

Value counted into a spendable UTXO requires `balanceChange > 0`; any non-positive delta is dropped with no accounting: [5](#0-4) 

Attack: a user submits a `transact()` whose Emporium op calls an external protocol's public claim/reward function that accepts an arbitrary target account (the exact bug class from H-16). An unprivileged attacker observes this in the mempool and calls that same external claim function directly, specifying Emporium's address as the recipient, in an earlier transaction/block. The reward tokens land on Emporium's balance before the victim's `transact()` runs `balancesBefore` (line 85). When the victim's op then calls the (now already-claimed) external function, no new tokens arrive, so `balancesAfter[i] - balancesBefore[i] == 0`. `handleOut` treats this as "nothing happened" and skips UTXO creation entirely (lines 162-170). The tokens that did arrive on Emporium remain there permanently: they are baked into every subsequent transaction's `balancesBefore` too, so no future Emporium call can ever produce a positive delta for them. Because Hinkal's entire value model requires funds to be represented by a UTXO commitment to be spendable, this balance is now stuck in the shared Emporium contract forever, unspendable by anyone including the entitled user.

This is the exact "value moved by an external action but not counted in the balance equation" analog: the CircomData/balance-delta equation Emporium relies on can be broken by any unprivileged party racing a pending transaction, with no admin, relay, or signer key required.

### Impact Explanation
This causes permanent freezing of user funds — the reward/asset value the user's `transact()` was meant to pull into Hinkal (and later mint as a spendable UTXO) is instead left as unattributed dust locked in the shared `EmporiumUpgradeable` contract with no mechanism to ever recover or attribute it to any UTXO. Per the stated impact categories this qualifies as Critical (permanent freezing of user funds).

### Likelihood Explanation
Likelihood is high wherever an Emporium op is used to interact with any external protocol exposing a public "claim for arbitrary account" style function (mirroring numerous real reward-distributor designs, as cited in the original H-16 report). Any unprivileged EOA monitoring the mempool for such Emporium transactions can execute the front-run with a single call, no special access required.

### Recommendation
Do not rely on a simple `balanceOf(Emporium)` before/after delta for a shared, non-reentrant-but-multi-tenant contract. Instead:
- Require ops that pull external value to specify an explicit expected recipient other than the shared Emporium address (e.g., route claims directly to a per-transaction escrow or directly to `msg.sender`), or
- Track and reconcile any pre-existing/unexpected balance so it can still be attributed and recovered (e.g., allow a "sweep leftover balance" flow scoped by op sequencing/nonce), or
- Have the circuit/off-chain relayer simulate and revert if the pre-call state doesn't match an expected zero/known baseline, so the transaction fails safely and the user can retry rather than silently losing the value.

### Proof of Concept
1. Attacker observes a pending `Hinkal.transact()` whose `circomData.externalActionData.externalAddress == EmporiumUpgradeable` and whose `EmporiumStack.ops` include a CASE 2 stateless call to `RewardProtocol.getReward(Emporium)` (a function that lets anyone claim rewards for an arbitrary `_account`, mirroring the Convex example in H-16).
2. Before the victim's transaction is mined, the attacker calls `RewardProtocol.getReward(Emporium)` directly, causing the reward tokens to be transferred to the `EmporiumUpgradeable` contract.
3. The victim's `transact()` executes: `balancesBefore` (`EmporiumUpgradeable.sol:85`) already includes the reward tokens deposited by the attacker.
4. The op's own call to `RewardProtocol.getReward(Emporium)` (`EmporiumUpgradeable.sol:112`) succeeds but transfers 0 additional tokens (already claimed).
5. `balancesAfter == balancesBefore`, so `balanceChange == 0` (`EmporiumUpgradeable.sol:133`), and `handleOut` returns an empty UTXO (`EmporiumUpgradeable.sol:168-170`) — no commitment is created for the reward value.
6. The reward tokens permanently remain in `EmporiumUpgradeable`'s balance, uncounted by any future transaction's balance delta (since they are already present at every subsequent `balancesBefore` snapshot), and are unspendable by the entitled user or anyone else.
