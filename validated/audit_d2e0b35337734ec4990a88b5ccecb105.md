### Title
`EvmHost.dispatch()` sends excess native token to Uniswap without refunding the caller, permanently trapping the fee overpayment - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap the caller's `msg.value` for an exact amount of fee tokens via `swapETHForExactTokens`, but neither function refunds unused native token back to the caller. This is the same root-cause class as the reported `swapperImpl.flash()` issue — no reconciliation between an off-chain price quote and the actual on-chain swap outcome — except here the mismatch causes native-token funds sent by an unprivileged dispatcher to become permanently stuck in the contract instead of merely making an operation uneconomical.

### Finding Description
`dispatch(DispatchPost)` and `dispatch(DispatchGet)` both execute: [1](#0-0) [2](#0-1) 

Both call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. UniswapV2Router02's `swapETHForExactTokens` refunds any unused ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])` — and `msg.sender` from the router's perspective is `EvmHost` itself (the contract that called the router), not the end-user who supplied `msg.value` to `EvmHost.dispatch()`. `EvmHost` has no logic afterward to capture that refund and forward it to `_msgSender()`, nor is there any documented sweep/withdraw path for accidentally-trapped native token in the excerpts reviewed.

The documentation itself confirms the pricing gap this exploits: `quote()` on `HyperApp` (used to size `msg.value` off-chain) calls `getAmountsIn`, a spot AMM price read *before* the transaction is submitted, and the docs explicitly warn this is "vulnerable to sandwich attacks" and must only be used off-chain, never on-chain, because the true price a transaction settles at will differ from the quoted one: [3](#0-2) [4](#0-3) 

Any caller who follows the SDK's own guidance and pads `msg.value` with headroom to survive this exact price movement — as `IntentGateway.quoteOrderFees` does with an explicit buffer — pays into a swap whose leftover ETH is refunded to `EvmHost`, not the caller: [5](#0-4) 

`IntentGatewayV2.placeOrder` has the identical pattern when converting native input to the fee token, but there it does track the leftover and refunds it explicitly (`msgValue -= amounts[0]`, then `_sendValue(msg.sender, msgValue)`), showing the codebase is aware refunding is necessary — yet `EvmHost.dispatch()` (the lower-level primitive every `HyperApp`-derived contract, including `IntentGatewayV2`, ultimately calls with native value) does not perform this refund itself: [6](#0-5) 

### Impact Explanation
Because `EvmHost.dispatch()` is the base-layer function any unprivileged app/dispatcher relies on for native-fee-token payment (the "Native Token Payment" pattern the docs advertise for direct message dispatch outside of `IntentGatewayV2`'s wrapper), any caller who:
- sends `msg.value` computed from `HyperApp.quote()` off-chain (unavoidable per the docs' own warning against on-chain quoting), or
- pads `msg.value` for slippage/price-movement safety as SDK helpers do,

will have the unused ETH swept into `EvmHost` by Uniswap's own refund mechanism, with no path in `EvmHost` to return it. This is a permanent, protocol-level freezing of user (dispatcher) funds — every over-quoted native dispatch leaks value into the contract irrecoverably, and there's no legitimate way for a caller to know the exact `amounts[0]` Uniswap will consume at execution time to send `msg.value` exactly, given block-to-block price drift and MEV.

### Likelihood Explanation
High likelihood: this is triggered by ordinary, permissionless use of the documented Native Token Payment path for `dispatch(DispatchPost)`/`dispatch(DispatchGet)`, not by an adversarial actor. Since the docs themselves instruct users to only size `msg.value` off-chain (never live), any latency between quoting and submission, or any general price movement/front-running on the local AMM, produces a mismatch that results in a nonzero, non-refunded remainder on essentially every native-fee dispatch.

### Recommendation
After calling `swapETHForExactTokens`, compute the actual ETH consumed (`amounts[0]` returned by the router) and refund `msg.value - amounts[0]` to `_msgSender()` (or to `post.payer`/`get.payer` as applicable), mirroring the pattern already used in `IntentGatewayV2.placeOrder` (`msgValue -= amounts[0]; _sendValue(msg.sender, msgValue);`). Apply this fix to both `dispatch(DispatchPost)` and `dispatch(DispatchGet)` in `EvmHost.sol`.

### Proof of Concept
1. A dispatcher app computes `nativeFee = HyperApp.quote(post)` off-chain via `getAmountsIn`, per the documented flow.
2. Between the quote and the transaction landing on-chain, the local Uniswap V2 pool's ETH/feeToken price shifts (natural drift, or MEV sandwiching the pending tx) such that fewer wei than `nativeFee` are now required to buy `post.fee` fee tokens — or the caller intentionally/defensively pads `msg.value` for safety margin as the SDK does.
3. The dispatcher calls `EvmHost.dispatch{value: nativeFee}(post)`.
4. Inside, `swapETHForExactTokens{value: nativeFee}(post.fee, path, address(this), block.timestamp)` executes, consuming `amounts[0] < nativeFee` wei and refunding `nativeFee - amounts[0]` wei to `msg.sender` — which is `EvmHost`, since `EvmHost` itself called the router.
5. `EvmHost.dispatch()` returns without forwarding this refund anywhere; the excess ETH remains locked in `EvmHost`'s balance with no caller-facing sweep function identified in the reviewed contract, permanently freezing the dispatcher's overpayment.
