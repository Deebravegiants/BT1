### Title
`handle_unsigned` batch atomicity lets one invalidated/conflicting ISMP message roll back an entire batch of otherwise-valid messages - (File: modules/pallets/ismp/src/impls.rs, modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Pallet::execute` processes a `Vec<Message>` with `.collect::<Result<Vec<_>, _>>()`, which short-circuits on the first `Err` returned by `handle_incoming_message`. The dispatchable that calls it, `handle_unsigned`, is marked `#[frame_support::transactional]`. Consequently, if any single message in a batch becomes invalid (e.g., because an earlier message in the same block already consumed/mutated the state it depends on, such as a request commitment being deleted by a competing timeout or response), the entire extrinsic reverts — including state changes from other, completely valid and unrelated messages processed earlier in the same batch. This is the same bug class as the CKB advisory: a batch/candidate-set generation process fails outright instead of gracefully dropping only the conflicting item, penalizing unrelated valid work.

### Finding Description
`Pallet::<T>::execute` ( [1](#0-0) ) iterates messages and calls `handle_incoming_message` for each, collecting results with `collect::<Result<Vec<_>, _>>()`. Any single `Err` short-circuits the whole `execute` call and returns `Error::<T>::InvalidMessage`.

The public entry point, `handle_unsigned`, is annotated `#[frame_support::transactional]` and calls `Self::execute(messages.clone())?`: [2](#0-1) 

Because the call is transactional, an `Err` return causes Substrate to roll back *all* storage writes performed during the call — not just the effects of the offending message, but also the commitment insertions/deletions, receipts, fee charges, and events for every other message in the same batch that had already been processed successfully before the failing one was reached.

`handle_unsigned` is permissionless (`ensure_none(origin)`) and is explicitly documented as accepting arbitrary batches of messages: [3](#0-2) 

The state that can be "destroyed" mid-batch and invalidate a sibling message is exactly analogous to CKB's cell-dep/destroy race: e.g. `handlers/timeout.rs` explicitly deletes a request commitment via `host.delete_request_commitment(&request)` when processing a timeout for a `Request` that another message in a concurrent/competing batch might also be trying to respond to (`GetResponseAlreadyReceived` / `UnknownRequest` checks exist precisely because this race is a recognized hazard): [4](#0-3) 

The existing intra-batch dedup/re-check logic (`dedup_requests`, "re-check the commitment right before dispatch" comments) shows the team is aware that a prior message in the *same* batch can invalidate a later one, but the fix implemented is to reject the whole batch with an `Err`, not to drop the offending message and continue with the rest — which is precisely the anti-pattern the CKB advisory calls out.

Contrast this with `EvmHost.dispatchIncoming`, which deliberately does the opposite for the EVM side — it "instead of reverting the entire batch, early return[s] here" on a failed per-message callback so the rest of the batch still lands: [5](#0-4) 
This shows the protocol has already recognized and fixed this exact bug class on the EVM host/handler path, but the same fix was not applied to `pallet_ismp::execute`'s substrate-side batch handling.

### Impact Explanation
Since `handle_unsigned` is unsigned/permissionless and gasless (free execution), any actor can submit a message (e.g., a `Timeout` for a request `R`) that races against a relayer's already-in-flight batch that also contains a `Response`/`Request` for `R` bundled together with unrelated, otherwise-valid messages (consensus updates, other requests/responses). Because message ordering within a block/batch is attacker/relayer influenced, an unprivileged actor can deliberately invalidate one entry inside a legitimate relayer's batch, causing the pallet's `#[transactional]` rollback to discard delivery of every other valid message in that batch as well. This can be used to repeatedly grief message delivery ("a route unable to deliver messages"), forcing costly retries and delaying cross-chain settlement, consensus updates, or fee accrual that were otherwise valid and ready to land.

### Likelihood Explanation
Likelihood is Medium: it requires precise timing to get a conflicting/invalidating message into the same execution window as the batch being invalidated, but `handle_unsigned` is free (unsigned, no fee) to call, so the cost of spamming conflicting messages to a validator is negligible. The proof requirements for a valid competing message (e.g. a valid timeout proof) may raise the bar somewhat, but batching by design (recommended for gas/DB efficiency, as documented in the batching/off-chain sections) increases the number of messages exposed to this all-or-nothing failure per attempt.

### Recommendation
Change `Pallet::execute` to process messages independently rather than via a single short-circuiting `collect`, dropping/skipping only the message(s) that fail and applying/keeping the state changes and events of all other valid messages in the batch — mirroring the design already used in `EvmHost.dispatchIncoming`, which returns early on a per-message failure instead of reverting the whole call. This likely also requires removing or scoping the `#[frame_support::transactional]` attribute so that a per-message failure does not implicitly discard prior successfully-applied messages in the same extrinsic.

### Proof of Concept
1. Relayer submits `handle_unsigned` with messages `[Consensus update C, Response Resp(R), Request req2]`, all independently valid at submission time.
2. Attacker submits (or races via mempool ordering) a separate `handle_unsigned` containing a valid `Timeout` for request `R`, landing in the block before the relayer's batch executes `Resp(R)`.
3. When the relayer's batch executes, `handle_incoming_message` for `Resp(R)` now fails (`UnknownRequest`/similar) because `R`'s commitment was deleted by the attacker's timeout, per the "re-check the commitment right before dispatch" logic in `handlers/timeout.rs`/response handling.
4. `execute`'s `collect::<Result<Vec<_>, _>>()` short-circuits with `Err`; `handle_unsigned`'s `#[frame_support::transactional]` rolls back the entire extrinsic, discarding the consensus update `C` and `req2` as well, even though they had nothing to do with `R` and were fully valid.
5. The relayer must detect the failure and resubmit `C` and `req2` separately, while the attacker can repeat this griefing at negligible cost since `handle_unsigned` is free.

	impl<T: Config> Pallet<T> {
		/// Execute the provided batch of ISMP messages, this will short-circuit and revert if any
		/// of the provided messages are invalid. This is an unsigned extrinsic that permits anyone
		/// execute ISMP messages for free, provided they have valid proofs and the messages have
		/// not been previously processed.
		///
		/// The dispatch origin for this call must be an unsigned one.
		///
		/// - `messages`: the messages to handle or process.
		///
		/// Emits different message events based on the Message received if successful.
		#[pallet::weight(weight())]
		#[pallet::call_index(0)]
		#[frame_support::transactional]
		pub fn handle_unsigned(
			origin: OriginFor<T>,
			messages: Vec<Message>,
		) -> DispatchResultWithPostInfo {
			ensure_none(origin)?;

			Self::execute(messages.clone())?;

			Ok(().into())
		}
