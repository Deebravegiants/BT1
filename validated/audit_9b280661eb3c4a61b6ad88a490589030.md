## Finding

### Title
Webhook Shop-Tenant Spoofing via Unauthenticated `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then dispatches the webhook to the registered handler using a `shop` value pulled directly from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header. That header is never included in the HMAC signature computation, so the tenant identity ("which shop this webhook is for") is not cryptographically bound to the authenticated bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) and compares it with `Context.secure_compare`: [3](#0-2) 

`Registry.process` checks only that this body-only HMAC is valid, then immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and hands it to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop-used-for-tenant-dispatch == shop-that-produced-the-authenticated-bytes`. Here that equality is never enforced — the HMAC only proves "this body was produced (or replayed) with knowledge of a body whose HMAC matches under `api_secret_key`," not "this body belongs to shop X." Because Shopify computes each shop's webhook HMAC over the body with the *same* `api_secret_key` for every shop the app is installed on, and many webhook payloads are highly predictable or even identical byte-for-byte across shops (e.g., empty-body events, or payloads an attacker can trigger from their own store to learn the exact bytes/signature for that topic), an attacker who controls a shop where the app is installed can capture a legitimate `(body, hmac)` pair from their own store and resubmit it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will accept it as valid and route it to the handler as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding for the webhook dispatch path without requiring the app's `client_secret`, an access token, or any credential belonging to the victim shop — only knowledge obtainable from the attacker's own (unprivileged) install of the app. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., updating shop-scoped billing/subscription state, marking a shop as uninstalled, writing shop-scoped records), this can enable cross-tenant data corruption or spoofed shop-lifecycle events, matching the report's underlying class: a field (`shop`) that is *acted upon* but not *covered by the authentication mechanism* (HMAC).

### Likelihood Explanation
Requires only network reachability to the app's public webhook endpoint plus knowledge of a valid `(body, hmac)` pair — obtainable by any developer/merchant with their own installation of the target app, which is an unprivileged-internet-user position relative to other tenants of the same app.

### Recommendation
Bind the shop identity to the authenticated material: include the shop domain (and ideally topic/webhook id) in the signable string used for HMAC validation, or otherwise cryptographically verify that the `shop-domain` header matches the shop the webhook was actually issued for (e.g., by requiring/verifying it against a per-shop registered callback URL rather than trusting the header value at dispatch time).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook topic with a predictable/empty body (e.g., a topic that sends `{}` or another byte-for-byte reproducible payload) and capture the resulting `X-Shopify-Hmac-Sha256` value computed over that body.
3. Replay the same raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks the body against the shared secret), and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"`, even though the request has nothing to do with that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
