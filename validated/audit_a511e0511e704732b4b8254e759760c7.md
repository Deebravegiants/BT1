### Title
Webhook `shop` domain is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop` value taken from an unauthenticated HTTP header. Because the HMAC key (`Context.api_secret_key`) is shared across every shop that has installed the app, a valid `(body, hmac)` pair obtained from one tenant's legitimate webhook delivery can be replayed with a forged `shop` header to make the host application process attacker-controlled data under a different, arbitrary shop's identity.

### Finding Description
`Registry.process` performs authentication like this: [1](#0-0) 

The only integrity check is `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header: [2](#0-1) 

For webhooks, `to_signable_string` is defined as the raw body only: [3](#0-2) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers that are never included in the signable string: [4](#0-3) 

After the HMAC check passes, `shop` is forwarded to the application's handler as authoritative tenant identity, with no additional binding to the body or the HMAC: [5](#0-4) 

**Broken identity binding (equality that should hold but doesn't):**
`shop header value` == `shop that produced/authorized the HMAC-signed body`

Because `api_secret_key` is a single, app-wide secret (not per-shop), *any* tenant that has installed the app can capture one of their own legitimate webhook deliveries (a valid `raw_body` + `hmac` pair signed with the app's shared secret) and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` / `shopify-shop-domain` header. `HmacValidator.validate` will still pass, because it only proves "this body was signed with the app's secret," not "this body belongs to this shop." The gem then reports the forged shop to the handler as `request.shop`, and downstream code (e.g. shopify_app-style session/tenant lookups keyed by shop) will process the replayed body under the wrong tenant.

### Impact Explanation
This crosses a tenant boundary using only capabilities available to an ordinary, unprivileged app-installing merchant (no `api_secret_key`, no access token, and no TLS interception of someone else's traffic is required — the attacker only needs one webhook legitimately delivered to their own store). The result is data belonging to one merchant being attributed to and processed under another merchant's `shop` identity by the host application, i.e. cross-tenant confusion/contamination — matching the "cross-tenant access" impact class in scope.

### Likelihood Explanation
Moderate-to-high: the HMAC scheme used by Shopify webhooks (a single shared app secret, body-only signature) is a known characteristic, and any app developer or malicious merchant with basic HTTP tooling can capture one of their own valid webhook payload+signature pairs and replay it with a different `shop` header. No cryptographic secret needs to be recovered — only reuse of a validly-signed payload under a different claimed identity.

### Recommendation
Do not treat `request.shop` as trusted tenant identity purely because the body-level HMAC validated. At minimum:
- Cross-check the `shop` header against an expected/known set of shops for which the app currently holds an active session/installation before dispatching to handlers, and reject unknown or mismatched shops.
- Where feasible, bind `shop` (and `topic`/`webhook_id`) into the value that is verified, or otherwise document prominently that `request.shop` is unauthenticated and callers must independently verify it maps to a legitimate installed shop before using it as a tenant key.
- Consider rejecting replays via a nonce/webhook-id de-duplication check at the same layer that would only be effective when the `shop` binding itself is fixed.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com` and receives a legitimate webhook (e.g. `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H` (`H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker POSTs the captured `B` and `H` to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and any topic already registered).
3. `HmacValidator.validate` succeeds because `H` is a correct HMAC over `B` under the (shared) `api_secret_key`: [6](#0-5) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host app to process attacker-supplied data as if it originated from `victim-shop`.

**Note on scope limitations:** I could not locate a `WebhookMetadata` class file in the indexed codebase (only references in `registry.rb`, `webhook_handler.rb`, docs, and changelog were found), so I cannot confirm any additional validation that might exist inside a host application's own `WebhookHandler#handle` implementation — that is application-specific and outside this gem. Some file contents may be excluded from the index; if a full inspection of `webhook_handler.rb` or any related struct definitions is needed, a Devin session with full repository access would be required.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
