Confirmed: `to_signable_string` for webhook `Request` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, entirely outside the HMAC-covered bytes [2](#0-1) . `Registry.process` validates the HMAC over the request (body only) and then trusts `request.shop` to build `WebhookMetadata` dispatched to the app's handler [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC solely against that body [4](#0-3) . The `shop` identity used by the app (`request.shop`, sourced from the `x-shopify-shop-domain` header) is never included in the signed bytes, breaking the equality `verified_bytes == bytes_that_determine_tenant_identity`.

### Finding Description
`Request#hmac` is decoded from the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only [5](#0-4) . `Request#shop` is read straight from the `shop-domain` header, a value that plays no part in the HMAC computation [2](#0-1) . `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only proves the body bytes were HMAC'd with `Context.api_secret_key`; it says nothing about which shop the request claims to be from [3](#0-2) . The handler is then invoked with `shop: request.shop` taken directly from that unauthenticated header [6](#0-5) .

Because a single `api_secret_key` is shared by the app across all its installed shops, and the signature covers body bytes but not the shop header, any legitimately-received webhook payload (e.g., replayed by a merchant/attacker who controls their own shop and can observe/capture their own inbound webhook HTTP requests, or who has any means of relaying requests to the app's public webhook endpoint) can have its `x-shopify-shop-domain` header swapped for a different tenant's shop domain without invalidating the HMAC signature, since the header is not part of `to_signable_string`. The app will accept the forged shop binding as valid and dispatch webhook data under the wrong tenant identity.

### Impact Explanation
This is a cross-tenant identity binding failure: the HMAC proves body authenticity but not shop authenticity, so the equality "authenticated bytes == bytes used to select which merchant's data/session this event applies to" does not hold. An attacker able to relay/replay a validly-signed webhook body while altering only the `shop-domain` header can make the app process events under an arbitrary shop identity, which the rules classify as cross-tenant access (Critical).

### Likelihood Explanation
Exploitation only requires network-level access to the app's public webhook endpoint and possession of any one validly HMAC-signed body (an unprivileged internet user can capture this from their own inbox/shop's webhook deliveries or via generic body/HMAC pairs that don't reference shop identity at all, since the signed payload for many topics carries no shop reference itself). No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Bind the shop identity into the verified bytes: include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `to_signable_string`, or independently verify that the shop domain in the payload/registered subscription matches the tenant that the app expects to receive from, before trusting `request.shop` for dispatch.

### Proof of Concept
1. App receives (or a malicious actor obtains, e.g. via their own shop's webhook logs) a genuine webhook: body `B`, `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the identical body `B` and identical HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, since `to_signable_string` is `@raw_body` only, unaffected by the changed header [1](#0-0) .
4. `Registry.process` proceeds and calls the handler with `shop: "shop-b.myshopify.com"` even though the signed content never asserted anything about shop-b [6](#0-5) .
