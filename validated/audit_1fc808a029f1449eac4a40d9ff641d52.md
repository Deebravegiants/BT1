### Title
`Webhooks::Registry.process` dispatches on the unsigned `topic` header while HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` authenticates a webhook by calling `Utils::HmacValidator.validate(request)`, then selects and invokes a handler using `request.topic`. `Webhooks::Request#to_signable_string` returns only `@raw_body`, so `topic`, `shop`, `webhook_id`, and `api_version` are all read from headers that are never part of the signed material. An attacker who has any single validly-signed webhook body/HMAC pair can resend it with a different `X-Shopify-Topic` header and have it dispatched to an arbitrary registered handler while still passing signature validation.

### Finding Description
The binding the code implicitly assumes is: `verified(request) == acted_on(request)`, i.e. "the bytes that were HMAC-verified are the same bytes that determine what happens next." Tracing the code shows this is false.

- `Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `topic`, `shop`, `webhook_id`, and `api_version` are all read from HTTP headers, independent of the body: [2](#0-1) 
- `HmacValidator.validate` / `validate_signature` compute the HMAC only over `verifiable_query.to_signable_string` (the raw body) and compare it to the `hmac-sha256` header: [3](#0-2) 
- `Registry.process` checks that HMAC once, then immediately re-reads `request.topic` (an unsigned header) to select the handler and to build the `WebhookMetadata` passed to it: [4](#0-3) 

Root cause: the signature covers only the body; the dispatch key (`topic`) and other metadata (`shop`, `webhook_id`, `api_version`) live entirely outside the signed string. `HmacValidator.validate` returning `true` therefore only proves "this body was produced by someone holding `api_secret_key` for *some* topic," not "this body belongs to `request.topic`."

Attacker flow: the attacker creates their own development shop, installs the target app, and registers/receives one legitimately signed webhook delivery for topic `A` (any topic the attacker's own shop can trigger, e.g. `orders/create`). They capture the raw body, `hmac-sha256` header, and `webhook-id`. They then POST that exact body and HMAC to the app's webhook endpoint again, but with `X-Shopify-Topic` changed to a different registered topic `B` (potentially a more sensitive one, e.g. `shop/redact`, `customers/data_request`, or any handler the app owner registered). `Registry.process` still calls `HmacValidator.validate` successfully (body/HMAC unchanged), then looks up `@registry["B"]`, finds handler `B`, and invokes `handler_B.handle(data: WebhookMetadata.new(topic: "B", shop: ..., body: parsed_body_of_A, ...))`. Handler `B` receives attacker-influenced body content (from topic A's payload) under the authenticated guise of topic `B`.

None of the existing guards stop this: `HmacValidator.validate` only checks the body/secret pairing, not topic binding; there is no `ShopValidator.sanitize!`-style check tying `topic` to the signed content; Sorbet's runtime typing only enforces that `topic` is a `String`, not that it matches what was signed.

### Impact Explanation
This lets any attacker who can obtain one legitimately-signed webhook body (trivially achievable via their own dev shop) cause the app to invoke an arbitrary registered handler — including mandatory-compliance handlers (`shop/redact`, `customers/redact`, `customers/data_request`) or any business-logic handler — with attacker-chosen (mis-typed) body content, while the app's route layer treats the request as fully authenticated because `HmacValidator.validate` returned `true`. This is a topic-confusion/authentication-bypass class issue: the app trusts `request.topic` as authenticated when it is not covered by the signature. Repeatable against any app built on this gem, for any topic the attacker can get signed at all, and requires no `api_secret_key` or other credential.

### Likelihood Explanation
Low attacker cost: creating a development store, installing the target app, and receiving one signed webhook is a normal, unprivileged workflow explicitly permitted for this audit's attacker model. Once one signed body/HMAC/`webhook-id` triple is captured, the replay with a swapped `topic` header is a single HTTP request, fully repeatable, and works against any app that has registered more than one HTTP webhook handler via `Webhooks::Registry`.

### Recommendation
Include `topic` (and ideally `shop`, `webhook_id`, `api-version`) in the signed material checked before dispatch, or independently verify that the `topic` header used for dispatch matches the topic the signature was generated for. At minimum, `Webhooks::Request#to_signable_string` should not be the sole signal used to authorize routing decisions in `Registry.process`; the topic used to select `@registry[request.topic]` should be cryptographically bound to the verified body, not read from a bare header, matching Shopify's actual webhook contract only if that header is provably tied to the HMAC on Shopify's side — this gem must not assume that binding without checking it.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_confusion_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryTopicConfusionTest < Test::Unit::TestCase
      class HandlerA < ShopifyAPI::Webhooks::WebhookHandler
        def self.handle(topic:, shop:, body:)
          $handled_by = :A
        end
      end

      class HandlerB < ShopifyAPI::Webhooks::WebhookHandler
        def self.handle(topic:, shop:, body:)
          $handled_by = :B
        end
      end

      def setup
        super
        ShopifyAPI::Webhooks::Registry.clear
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "topic/a", delivery_method: :http, path: "/a", handler: HandlerA,
        )
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "topic/b", delivery_method: :http, path: "/b", handler: HandlerB,
        )
      end

      def test_signature_does_not_bind_to_topic
        raw_body = '{"id":1,"note":"legit for topic/a"}'
        hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body,
        )
        signature = Base64.strict_encode64(hmac)

        headers_a = {
          "shopify-topic" => "topic/a",
          "shopify-hmac-sha256" => signature,
          "shopify-shop-domain" => "test-shop.myshopify.com",
          "shopify-api-version" => "2024-01",
          "shopify-webhook-id" => "wh-1",
        }
        request_a = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_a)

        # Same body + same HMAC, only the topic header changes: the "replayed delivery".
        headers_b = headers_a.merge("shopify-topic" => "topic/b")
        request_b = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_b)

        # Binding under test: verified(request) should equal acted_on(request).
        # Left side: HMAC verification result is identical for both requests (body unchanged).
        assert(ShopifyAPI::Utils::HmacValidator.validate(request_a))
        assert(ShopifyAPI::Utils::HmacValidator.validate(request_b))

        # Right side: dispatch follows the unsigned topic header, not the signed body.
        ShopifyAPI::Webhooks::Registry.process(request_a)
        assert_equal(:A, $handled_by)

        ShopifyAPI::Webhooks::Registry.process(request_b)
        assert_equal(:B, $handled_by) # handler_B runs on body originally signed for topic/a
      end
    end
  end
end
```
This demonstrates that `HmacValidator.validate` accepts both `request_a` and `request_b` (identical body/HMAC), yet `Registry.process` dispatches to `HandlerA` or `HandlerB` purely based on the unsigned `topic` header — proving the signature-coverage invariant is violated and dispatch does not follow the signature.
