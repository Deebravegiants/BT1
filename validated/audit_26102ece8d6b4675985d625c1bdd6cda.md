### Title
Cross-tenant webhook spoofing via `shop-domain` header not covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity of an incoming webhook (`shop`, `topic`, `api_version`, `webhook_id`) entirely from HTTP headers that are **not** included in the HMAC-signed payload, while `ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw body. This breaks the intended binding `hmac(raw_body) == shop-domain header used by handler`, letting anyone who can obtain one valid `(raw_body, hmac)` pair (e.g. a merchant who has legitimately installed the app on their own store) replay that pair with a forged `shop-domain` (and `topic`) header, causing the app's webhook handler to process the payload under a different tenant's identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body — none of the Shopify headers are part of the signed material: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` — which determine *which tenant and which event* the webhook represents — are read directly, unauthenticated, from headers: [3](#0-2) 

`Registry.process` only checks the HMAC validity (over the body) before dispatching to the app's handler with `request.shop` used as the tenant identity in `WebhookMetadata`: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but does not:
`bytes_covered_by_hmac (raw_body) == bytes_used_to_determine_tenant (shop-domain header, topic header)`

Because the app's `api_secret_key` is shared across *all* shops using the app (it is not per-shop), any legitimate but unprivileged user who has installed the app on their own store can receive a genuine webhook — a valid `(raw_body, hmac)` pair signed with the app's secret. That user can then replay the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint while substituting the `shop-domain` header (and potentially `topic` header, since it's also unauthenticated) to name a different shop/tenant. `HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will hand the forged shop identity to the registered handler as if it originated from that other tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker with access to only their own installation's credentials/webhooks (unprivileged relative to any other tenant) can make the app process an event as though it came from an arbitrary other shop that also has the app installed. Depending on what the host application's webhook handlers do with `WebhookMetadata#shop` (e.g., invalidate/rotate sessions, trigger `app/uninstalled` cleanup, process GDPR `customers/redact` / `shop/redact` compliance actions, or update per-shop billing/subscription state), this can be leveraged to corrupt or manipulate another tenant's stored state — a cross-tenant access impact.

### Likelihood Explanation
Requires only: (1) attacker installs the app once on any shop they control (a normal, unprivileged install), (2) capture one legitimate webhook delivery (readily available — apps typically log/receive many), (3) replay it with a modified `shop-domain` (and/or `topic`) header to the app's webhook endpoint. No access to `api_secret_key`, tokens, or other tenants' credentials is required. The gem provides no built-in defense (no binding of headers to the signature, no shop allow-list check tying the header to a known/expected value at the `Registry`/`Request` layer).

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., by concatenating headers + body before computing/verifying the digest), so that any header used to determine tenant/event identity is covered by the same HMAC as the body.

### Proof of Concept
1. App has two installs: `attacker-shop.myshopify.com` (attacker-controlled) and `victim-shop.myshopify.com`.
2. Attacker triggers any webhook event on their own shop (e.g., updates a product to fire `products/update`), and captures the resulting HTTP request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the same body `B` and `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`, e.g. `app/uninstalled`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `B` against `H`.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act on `victim-shop.myshopify.com`'s behalf/state, even though the attacker never had any credential relationship with that shop.
