Audit Report

## Title
Refundable-deposit HRMP open/cancel loop lets any onboarded para inject unbounded, fee-free system notifications into a victim para's `DownwardMessageQueuePages`, saturating its DMQ - ([File: polkadot/runtime/parachains/src/hrmp.rs], [File: polkadot/runtime/parachains/src/dmp.rs])

## Finding Description
`Pallet::init_open_channel` validates only the *caller's* outstanding-channel quota (`egress_cnt + open_req_cnt < channel_num_limit`) and reserves a refundable `hrmp_sender_deposit` before unconditionally calling `Self::send_to_para`, which injects an `HrmpNewChannelOpenRequest` notification into the *recipient's* downward message queue via `dmp::Pallet::<T>::queue_downward_message` — with no consent or rate-limit check on the recipient side. [1](#0-0) [2](#0-1) 

`dmp::Pallet::can_queue_downward_message` only rejects a message once `dmq_length(para) > dmq_max_length(...)`, where `dmq_max_length = MAX_POSSIBLE_ALLOCATION / max_downward_message_size` is a large but finite hard cap with no per-sender accounting at all. [3](#0-2) [4](#0-3) 

Since `hrmp_cancel_open_request` deletes the request and refunds the sender's deposit while decrementing `HrmpOpenChannelRequestCount`, the caller's per-attacker quota is fully reset after every cycle, meaning `egress_cnt + open_req_cnt < channel_num_limit` never becomes a binding constraint across repeated open→cancel iterations — it only bounds concurrently *outstanding* requests, not cumulative notifications sent over time. There is also a congestion-pricing mechanism (`increase_fee_factor`, triggered once queue length crosses `dmq_max_length / THRESHOLD_FACTOR`) that raises delivery fees for callers using the fee-paying XCM `Sender` path, but `send_to_para` calls `queue_downward_message` directly and is not gated by any fee charge on the injecting party — so the deterrent that exists for ordinary XCM senders does not apply to the HRMP-notification injection path itself. [5](#0-4) [6](#0-5) 

## Impact Explanation
An unrelated, onboarded parachain can repeatedly enqueue `HrmpNewChannelOpenRequest`/`HrmpChannelAccepted`/`HrmpChannelClosing` notifications into a target para's DMQ at the cost of only transaction/weight fees (the deposit itself is fully refunded on cancellation), progressively filling `DownwardMessageQueuePages[victim]` toward the hard cap. Once the cap is approached, `can_queue_downward_message` begins rejecting all further downward messages to that para — including legitimate governance and third-party XCM traffic — until the victim's collators drain enough backlog via `prune_dmq`. This is a temporary, recoverable denial-of-service against a specific victim para's DMP channel rather than a fund-loss or consensus-safety issue.

## Likelihood Explanation
The attack requires the attacker to control an onboarded parachain capable of dispatching `hrmp_init_open_channel`/`hrmp_cancel_open_request` (a real but non-trivial precondition, since it requires an active parachain slot/registration, not merely an arbitrary end-user account). Given that precondition, the loop is cheap relative to its effect because the deposit is refunded each cycle and no fee-factor or per-sender rate limit applies to the injection path, so the attack is repeatable indefinitely subject only to the attacker's own transaction throughput and weight budget, and the victim's queue remains saturated as long as the attacker sustains the flood at or above the victim's drain rate.

## Recommendation
Track cumulative open+cancel churn per `(origin, recipient)` pair (not just currently-outstanding requests) and rate-limit or charge a non-refundable fee for repeated cycles; alternatively, apply the existing `DeliveryFeeFactor`/congestion-pricing logic to HRMP system-notification injection so that repeatedly targeting an already-congested victim queue becomes progressively more expensive for the originating para, independent of the refundable channel deposit.

## Proof of Concept
1. Register attacker para `A` and victim para `V`.
2. Loop: call `Hrmp::hrmp_init_open_channel(A_origin, V, cap, size)` then immediately `Hrmp::hrmp_cancel_open_request(A_origin, HrmpChannelId{sender:A, recipient:V})`.
3. Observe `Dmp::dmq_length(V)` increases by one per iteration while `A`'s reserved balance returns to baseline after each cancel.
4. Continue until `Dmp::dmq_length(V) > Dmp::dmq_max_length(max_downward_message_size)`, then show a subsequent legitimate `dmp::Pallet::<Test>::queue_downward_message(&config, V, legit_msg)` call fails with `QueueDownwardMessageError::ExceedsMaxMessageSize`.
5. Call `Dmp::prune_dmq(V, N)` to simulate backlog processing and show the legitimate message can then be enqueued, confirming the congestion is attacker-driven and recoverable only once the victim drains the queue.

	pub fn can_queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: &ParaId,
		msg: &DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len() as u32;
		if serialized_len > config.max_downward_message_size {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// Hard limit on Queue size
		if Self::dmq_length(*para) > Self::dmq_max_length(config.max_downward_message_size) {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// If the head exists, we assume the parachain is legit and exists.
		if !paras::Heads::<T>::contains_key(para) {
			return Err(QueueDownwardMessageError::Unroutable);
		}

		Ok(())
	}

	pub fn queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: ParaId,
		msg: DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len();
		Self::can_queue_downward_message(config, &para, &msg)?;

		let inbound = InboundDownwardQueue::<T>::push_back(para, msg)
			.map_err(|_| QueueDownwardMessageError::ExceedsMaxQueueSize)?;
		let q_len = InboundDownwardQueue::<T>::len(para).unwrap_or(0);

		// obtain the new link in the MQC and update the head.
		DownwardMessageQueueHeads::<T>::mutate(para, |head| {
			let new_head =
				BlakeTwo256::hash_of(&(*head, inbound.sent_at, T::Hashing::hash_of(&inbound.msg)));
			*head = new_head;
		});

		let threshold =
			Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
		if q_len > threshold as u64 {
			Self::increase_fee_factor(para, serialized_len as u128);
		}

		Ok(())
	}
