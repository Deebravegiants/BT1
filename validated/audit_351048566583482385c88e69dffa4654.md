Good — the `message.from` field is set to `abi.encodePacked(msg.sender)` on the EVM side, and it's `msg.sender` at burn time [1](#0-0) , so it does correctly identify the caller who burned tokens on the source chain — the field itself isn't forgeable. However, that legitimate "from" identity is then used, unauthenticated, to select a dispatch origin for an arbitrary `RuntimeCall` on the destination chain.

### Title
Unauthenticated cross-chain RuntimeCall dispatch via unsigned `SubstrateCalldata` in HyperFungibleToken - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` decodes an attacker-supplied `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` from the cross-chain message body and, when `signature` is `None`, dispatches the embedded `RuntimeCall` as `RawOrigin::Signed(origin)` where `origin` is derived purely from the message's `from` field — with no signature, nonce, or any other proof that the destination-chain account authorized this specific call [2](#0-1) .

### Finding Description
On the EVM side, any address can call `send()` on `HyperFungibleToken`, and the resulting cross-chain `Message.from` is simply `abi.encodePacked(msg.sender)` [1](#0-0) . `data` (which becomes SCALE-encoded `SubstrateCalldata`) is fully attacker-controlled `SendParams.data` — there is no restriction on what `runtime_call` bytes can be placed there.

On the substrate destination, `on_accept` decodes `SubstrateCalldata` from `message.data` [3](#0-2) . If `signature` is `None`, the code takes the unauthenticated branch:
```
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else { ... }
``` [4](#0-3) 

This derives the dispatch origin deterministically from the caller's own EVM address (which is legitimately theirs) — so far so good for *that* account. But then it decodes and dispatches an **arbitrary** `RuntimeCall`:
```
let runtime_call = T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)...
if !<T as frame_system::Config>::BaseCallFilter::contains(&runtime_call) { ... }
runtime_call.dispatch(RawOrigin::Signed(origin.clone()).into())...
``` [5](#0-4) 

Because the "unsigned" path is meant only for the case where an EVM account has *no* corresponding substrate private key to sign with, the protocol substitutes possession of an EVM private key (proven by `msg.sender` on the source chain) for authorization of *arbitrary* substrate-side dispatchable calls, executed as the deterministically-derived substrate proxy account for that EVM address. The `BaseCallFilter` only blocks runtime-level filtered calls (e.g. maintenance mode); it does not restrict which pallets/extrinsics a bridged, unsigned-origin call may invoke. Any dispatchable permitted by the base filter and reachable by a `Signed` origin (transfers, staking, asset operations, governance-adjacent calls exposed to signed origins, arbitrary approvals, etc.) can be triggered on behalf of that derived account — using funds/assets that account may hold from *any* source (not only the bridged transfer itself), since the call dispatches with a generic `Signed(origin)`, not scoped to only the escrowed/minted asset.

This is the closest analog in-repo to the report's "arbitrary deserialization for authenticated channel user regardless of assigned permissions" pattern: the report's ActiveMQ Minion channel allowed any authenticated relay participant to have arbitrary deserialized payloads executed with elevated trust; here, any address able to call `send()` on the EVM chain (i.e., anyone) causes arbitrary decoded `RuntimeCall` bytes to be dispatched with a signed origin's authority on a different chain, without any cryptographic signature proving the destination-chain account authorized *that specific call*.

### Impact Explanation
An attacker who controls or has previously used a given EVM address needs no substrate private key at all: sending any bridged transfer with attacker-chosen `data` causes the deterministically-mapped substrate account to dispatch an attacker-chosen `RuntimeCall`. If that mapped substrate account holds any balance or asset (e.g., because other users independently derive/fund the same deterministic account, or because prior bridged transfers accumulated balance there, or the mapping collides with an account holding funds for unrelated reasons), the attacker can move or spend those funds via any `Signed`-origin dispatchable not blocked by `BaseCallFilter` — meeting the "unauthorized app action" / "concrete theft of funds" bar. Even without pre-existing balance, this uses the recipient's own minted tokens without their consent for the call: a bridged transfer that also silently drains other assets held by the deterministically-derived account is an authorization bypass regardless of amount.

### Likelihood Explanation
High. The path is reachable by a single unprivileged EVM transaction to a public `send()` function; no relayer collusion, governance, or privileged role is required. The only gating is `BaseCallFilter`, a runtime-wide filter not designed to scope per-bridge-app authorization.

### Recommendation
Do not permit dispatch of an arbitrary `RuntimeCall` under an unsigned/no-signature `SubstrateCalldata`. Either (a) require a valid destination-chain signature for every dispatched call (remove the unsigned branch entirely), or (b) restrict the unsigned branch to a fixed, safe, narrowly-scoped set of calls (e.g., none, or only self-referential operations that cannot move funds beyond what was already minted to that same beneficiary in the same message), and additionally scope any executed call so it can only interact with the specific asset/amount just credited rather than dispatching with a general `Signed` origin capable of acting on all of that account's holdings.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send(params)` on the EVM source chain from address `A`, with `params.data` set to an ABI-encoded `Message.data` containing a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <encoded Balances::transfer_allow_death { dest: attacker_substrate_account, value: ALL } > }`.
2. On delivery, `on_accept` mints the bridged amount to `beneficiary` derived from `message.to`, then decodes `SubstrateCalldata`, sees `signature == None`, and computes `origin = T::EvmToSubstrate::convert(H160::from(A))` [4](#0-3) .
3. `on_accept` dispatches the attacker-chosen `RuntimeCall` as `RawOrigin::Signed(origin)` [5](#0-4) , transferring away any balance currently held by that derived account — including balances that are unrelated to, or exceed, the bridged transfer itself — with no signature ever checked.
4. The existing test `should_receive_asset_with_calldata` demonstrates the mechanics of this exact unsigned/signed dual-path dispatch (using the signed branch for its assertion), confirming the code path is live and exercised [6](#0-5) ; the unsigned branch (lines 176–187 of `module.rs`) has no equivalent authorization check.

fn should_receive_asset_with_calldata() {

		let final_recipient = AccountId32::new([5u8; 32]);
		let runtime_call =
			crate::runtime::RuntimeCall::Balances(pallet_balances::Call::transfer_allow_death {
				dest: final_recipient.clone(),
				value: SEND_AMOUNT,

		// Sign with sr25519
		let (pair, ..) = sp_core::sr25519::Pair::generate();

		let payload = (0u64, runtime_call.clone()).encode();

		let raw_signature = pair.sign(&message_hash);
		let multisignature = MultiSignature::Sr25519(raw_signature).encode();

		let substrate_data = SubstrateCalldata { signature: Some(multisignature), runtime_call };

		let module = HyperFungibleToken::default();
		let post = PostRequest {
			source: StateMachine::Evm(1),
			dest: StateMachine::Kusama(100),
			nonce: 0,
			from: hft_contract(),
			to: pallet_hyper_fungible_token::PALLET_ID.to_bytes(),
			timeout_timestamp: 1000,
			body: {
				let msg = Message {
					from: alloy_primitives::Bytes::from(vec![0x11u8; 20]),
					to: alloy_primitives::Bytes::from(beneficiary_bytes.to_vec()),
					amount: {
						let bytes = convert_to_erc20(SEND_AMOUNT, 18, 10).to_big_endian();
						alloy_primitives::U256::from_be_bytes(bytes)
