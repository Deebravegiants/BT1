### Title
`EvmHost.updateHostParamsInternal` fee-token migration is bricked if the old fee token reverts on `balanceOf` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal` blocks any change of `feeToken` while the old fee token still holds a non-zero balance on the host, by calling `IERC20(oldFeeToken).balanceOf(address(this))` [1](#0-0)  directly on the *old* token. This mirrors the reported `CrosschainDistributor._setToken` pattern: the ability to migrate away from a broken/compromised token is made contingent on a successful external call into that very token.

### Finding Description
`updateHostParamsInternal` is the sole gate for changing `HostParams.feeToken` (and all other host params). Whenever the caller supplies a `feeToken` different from the currently configured one, the function performs a live external call to the *old* token before allowing the swap:

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
``` [1](#0-0) 

`updateHostParams` is reachable only via the `hostManager` [2](#0-1) , which itself is driven by cross-chain governance requests delivered through `handler`/`onAccept` — i.e., a relayed ISMP request from the Hyperbridge governance chain, not a locally-signed admin transaction. If the currently configured `oldFeeToken` becomes non-functional — e.g. it is upgraded to a paused/blacklisting implementation, is selfdestructed, or its `balanceOf` starts reverting due to a bug/exploit — then every future `updateHostParams` call that tries to move away from it will unconditionally revert, since the high-level `IERC20` call either reverts directly or (in the selfdestruct case) reverts on ABI-decoding empty return data.

This is exactly the bug class in the report: a critical "replace the broken token" recovery path is coupled to a successful call into the very token being replaced.

### Impact Explanation
The `feeToken` is central to protocol revenue: relayer/dispatch fees are collected and escrowed in it, and `withdraw()` also depends on `IERC20(token).safeTransfer` succeeding for that same token [3](#0-2) . If the configured fee token misbehaves (reverts, selfdestructs, or is otherwise compromised), governance loses the only mechanism to switch to a working fee token, because the very check meant to protect against losing escrowed funds (`CannotChangeFeeToken`) can never be satisfied or bypassed. This permanently freezes the host's fee configuration and any funds denominated in the broken token, and can degrade or halt the host's normal cross-chain messaging economics indefinitely.

### Likelihood Explanation
This requires the deployed fee token to become non-functional (bug, governance-controlled pause/blacklist, proxy upgrade to malicious logic, or selfdestruct) — a real but not everyday occurrence for ERC20 tokens used as protocol fee tokens over the long operational lifetime of Hyperbridge. Given that `feeToken` is an admin/governance-configurable, non-immutable external contract, and the described failure modes (pausable/blacklistable tokens, proxy tokens) are common in production ERC20s, the likelihood is non-negligible for a Medium-severity, low-frequency but high-impact scenario — consistent with the original report's rating.

### Recommendation
Do not gate the `feeToken` migration on a live external call to the potentially-broken old token. Options:
- Wrap the `balanceOf` call in a try/catch and treat a revert as "not zero" only if governance explicitly wants to be conservative, or treat a revert as "proceed" (assume no recoverable balance) since the token is already known broken.
- Alternatively, allow governance to force a fee-token change via a separate emergency path that skips the balance check when the old token proves non-functional, or require a pre-step `sweepFeeToken` that itself tolerates old-token failure.

### Proof of Concept
1. Host is configured with `feeToken = T` and has accumulated `balance > 0` of `T` (from relayer fees).
2. Token `T`'s owner/implementation subsequently reverts on `balanceOf` (e.g., pausable behavior, a compromised upgrade, or the token contract is selfdestructed).
3. Governance detects the compromise and submits an `updateHostParams` request via `hostManager` with a new `feeToken = T2` to replace the broken token.
4. `updateHostParamsInternal` executes `IERC20(T).balanceOf(address(this))`, which reverts (or, for a selfdestructed contract, the call succeeds with empty returndata and Solidity's ABI decoding of the expected `uint256` return reverts).
5. The entire `updateHostParams` transaction reverts, and there is no other function to change `feeToken`, permanently trapping the host on the broken fee token and the escrowed balance of `T`.
