### Unreachable pool refund mismatch is not an unprivileged exploit - ([contracts/pool/src/ops/repay.rs:25](contracts/pool/src/ops/repay.rs))

### Summary
The closest analog to the reported double-free class is the pool’s refund behavior: `repay` and `recapitalize` refund a declared “excess” without independently reconciling that amount against an actual inbound token transfer.

However, the pool entrypoints are owner-only, and every reachable controller path prefunds the pool with a measured transfer before invoking the refunding pool call. I did not find a single unprivileged-address path that can make the pool refund unfunded custody.

### Finding Description
`contracts/pool/src/ops/repay.rs` computes `overpayment` from the declared `PoolAction.amount`, credits only `net_repay` to cash, then transfers `overpayment` to `payer` without debiting cash or checking the pool’s actual balance delta. [1](#0-0)  `contracts/pool/src/ops/recapitalize.rs` similarly calculates `refund = amount - applied` and transfers it to `payer` after crediting only `applied` to cash. [2](#0-1) 

A direct unfunded call would therefore release existing pool custody as a refund, which is the resource-release analogue of the CVE’s double free. The test suite even documents that a repay against a market with no debt makes the whole declared amount refundable. [3](#0-2) 

That sink is not independently reachable: `LiquidityPool::repay` and `LiquidityPool::recapitalize` are `#[only_owner]`, with the controller deployed as owner. [4](#0-3)  The controller’s public `repay` path transfers each payment to the pool with `transfer_amount_measured` and passes the measured `amount_in` into `pool.repay`. [5](#0-4)  The strategy repayment helper does the same for controller-held funds. [6](#0-5)  Public `recapitalize` likewise transfers the measured amount before calling `pool.recapitalize`. [7](#0-6) 

The liquidation repayment path also measures each liquidator-to-pool transfer and passes only the measured receipt into the pool action. [8](#0-7) 

### Impact Explanation
No in-scope impact can be established. The vulnerable-looking release is guarded by owner-only pool authorization, and the owner/controller only submits amounts it has just measured as actual pool receipts.

### Likelihood Explanation
An unprivileged user cannot call `pool.repay` or `pool.recapitalize` directly. Controller `repay`, `liquidate`, `repay_debt_with_collateral`, `swap_debt`, and `recapitalize` all prefund the pool using measured balance deltas before requesting the refunding operation.

### Recommendation
Even though no unprivileged route was found, the pool should defensively reconcile refunds with actual receipts or require an explicit funded amount separate from the requested amount. At minimum, an invariant should ensure `refund + credited` does not exceed the pool’s measured balance increase for the operation.

### Proof of Concept
No valid unprivileged proof of concept was found. The only demonstrated drain relies on invoking the owner-only `pool.repay` directly, which is outside the permitted attacker surface.
