Confirmed: the standard EVM `IntentsBase.sol` uses OpenZeppelin's `SafeERC20.safeTransfer` for withdrawals and dust sweeps [1](#0-0) , but the Tron deployment's `IntentGatewayV2.sol` reimplements withdrawal and dust-sweep logic with raw low-level `.call` and only checks that the call didn't revert — it never inspects the returned ABI-encoded boolean — which is exactly the return-value-not-checked bug class from the report.

### Title
Unchecked ERC20 boolean return value in Tron IntentGatewayV2 permanently drains escrow accounting without delivering funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.sol` releases escrowed order funds, transaction fees, and swept dust by making a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and treating the transfer as successful whenever the call does not revert, without decoding and checking the returned `bool`.

### Finding Description
In `withdraw()`, escrow release/refund and fee payout use: [2](#0-1) 
and `onAccept`'s `SweepDust` handler does the same: [3](#0-2) 

Each site checks only `success` (whether the low-level call reverted), never decoding `data` to confirm the token itself returned `true`. Per EIP-20, a compliant token is permitted to return `false` on failure instead of reverting, and this pattern is especially common for TRC-20 tokens on Tron (many differ from strict EIP-20 semantics, e.g. USDT-TRC20 return-value quirks are a known ecosystem issue — matching the analogous ERC20 return-value defect from the report). If `transfer` returns `false` without reverting, `success` is still `true`, so `withdraw()` proceeds to `_orders[body.commitment][token] -= amount;` (or clears `_orders[...][TRANSACTION_FEES]`), permanently marking the escrow as released even though the beneficiary or solver never received the tokens.

Contrast with the canonical EVM implementation in `IntentsBase.sol`, which correctly uses `SafeERC20.safeTransfer`, reverting on a falsy return: [1](#0-0) [4](#0-3) 

### Impact Explanation
This is reachable from the core intent-fill/refund path: any `RedeemEscrow`/`RefundEscrow` message delivered via `onAccept` (or a same-chain fill/cancel that routes through `withdraw`) triggers this unchecked transfer. If the escrowed token silently returns `false` on transfer failure (e.g., insufficient balance from a fee-on-transfer edge case, blacklist, paused state, or any TRC-20 with non-strict return semantics), the escrow accounting (`_orders[commitment][token]`) is decremented and the order is marked `_filled` as if funds were delivered, while the solver/user/beneficiary receives nothing. This is a permanent, unrecoverable loss of the escrowed funds for that order — the tokens remain stuck in the contract with no accounting path left to reclaim them, since `_filled` and `_orders` have already been updated as though settlement succeeded.

### Likelihood Explanation
This requires either (a) a non-standard/misbehaving ERC20/TRC20 token being used as an order's input/output token, or (b) an edge condition (blacklist, pause, insufficient contract balance from a prior accounting bug, fee-on-transfer mismatch) causing the token to return `false` rather than revert. Given the intent gateway is designed to be generic over arbitrary tokens supplied by users placing orders, and Tron's TRC-20 ecosystem has multiple tokens with historically inconsistent return-value behavior, this is a realistic and reachable condition, not a purely theoretical one.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (already used elsewhere in the same file, e.g. `IERC20(token).safeTransferFrom(...)`) consistently for every outbound transfer in `withdraw()` and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol`, replacing the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check pattern, so that a falsy return value reverts the transaction instead of allowing escrow state to be finalized without an actual transfer.

### Proof of Concept
1. A user places an order with input token `T` (a token whose `transfer` returns `false` on failure instead of reverting, e.g., due to a blacklist or paused flag applied to the beneficiary/solver after escrow but before fill).
2. The order is filled/refunded cross-chain, and Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` message to `onAccept`, invoking `withdraw(body, isRefund)`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; token contract logic returns `false` (e.g., beneficiary blacklisted) but does not revert.
4. `success` is `true` (the external call itself didn't revert), so the check `if (!success) revert TransferFailed();` passes.
5. `_orders[body.commitment][token] -= amount;` executes, and `_filled[body.commitment] = beneficiary;` is set, permanently finalizing the order as settled.
6. The beneficiary/solver never received the tokens; the tokens remain locked in the `IntentGatewayV2` contract with no further code path to reclaim them for that commitment — permanent loss of the escrowed funds. [5](#0-4)

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
