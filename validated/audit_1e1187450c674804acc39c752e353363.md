### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is refunded to the Host contract itself, not to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.fundRequest()` accept `msg.value` and swap it via UniswapV2 for the exact `feeToken` amount needed, but never account for or refund the leftover native token to the original transaction sender — the same bug class as the Swivel `lend()` report, where a swap-derived residual balance is left stranded in the contract instead of being returned to the payer.

### Finding Description
In both outgoing-dispatch paths, when `msg.value > 0` the host performs `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`: [1](#0-0) [2](#0-1) 

Because the router call is made with `recipient=address(this)` (the `EvmHost`), UniswapV2Router02's standard `swapETHForExactTokens` implementation refunds any unspent ETH (`msg.value - amounts[0]`) back to `msg.sender` of the router call — which is `EvmHost` itself, not the original caller that sent the overpaid `msg.value`. Unlike `IntentGatewayV2.placeOrder`, which explicitly tracks `msgValue -= amounts[0]` and refunds the remainder to the user: [3](#0-2) 

`EvmHost.dispatch()` and `fundRequest()` contain no equivalent tracking or refund logic after the swap call — the leftover native ETH simply accumulates on the `EvmHost` contract with no code path returning it to the caller.

### Impact Explanation
Any user or application dispatching a Hyperbridge POST/GET request (or calling `fundRequest`) with `msg.value` exceeding the exact amount the router consumes for the fee swap will have that excess permanently stuck in the `EvmHost` contract, unrecoverable by them. This is a direct, unconditional loss of funds for every overpaying caller — a very common occurrence since callers must estimate/quote the native fee in advance and typically pad it for slippage protection (as illustrated by the `IntentGatewayV2` fee-swap test sending 5x the required ETH). This affects the core outgoing dispatch primitive used by every app built on top of Hyperbridge (bridge tokens, intent gateway cross-chain fills, HyperFungibleToken, LayerZero endpoint adapter, etc.), and is the same underlying dispatch entrypoint (`IDispatcher.dispatch`) relied upon across the whole SDK.

### Likelihood Explanation
High likelihood: this triggers on the ordinary, expected usage pattern of overestimating the native fee (a documented practice, e.g. the 2x buffer noted in the LayerZero endpoint's `quote()` comment), and requires no malicious actor — simply calling `dispatch{value: X}()` with `X` greater than the exact swap cost.

### Recommendation
Track the amount consumed by `swapETHForExactTokens` and refund any unspent `msg.value` to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`:

```solidity
if (msg.value > 0) {
    ...
    uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
    uint256 refund = msg.value - amounts[0];
    if (refund > 0) {
        (bool sent, ) = _msgSender().call{value: refund}("");
        require(sent, "refund failed");
    }
}
```
Apply the same fix to `fundRequest()`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(post){value: 1 ether}` where the actual fee-token cost only requires the ETH-equivalent of e.g. 0.1 ether.
2. `swapETHForExactTokens` is invoked with `value: 1 ether`; internally it swaps only enough ETH to obtain `post.fee` feeTokens and refunds the remaining ~0.9 ether — but to `address(this)` (the `EvmHost`), since `EvmHost` is `msg.sender` from the router's perspective.
3. `EvmHost`'s ETH balance increases by ~0.9 ether; no logic in `dispatch()` forwards this back to the original caller.
4. The caller has permanently lost ~0.9 ether with no function in `EvmHost` to reclaim it (the only path is `IHostManager.withdraw`, restricted to `hostManager`, gated by governance, not by the original payer). [4](#0-3)
