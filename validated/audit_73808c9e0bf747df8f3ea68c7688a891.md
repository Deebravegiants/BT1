**Analysis:**

`THotStateSlot::set_prev`/`set_next` in [1](#0-0)  are trait methods with no implementation logic in this file — they're plumbing for a doubly-linked LRU used purely as an in-memory caching/eviction mechanism for the "hot state" performance optimization, not an ownership/authority store.

Key points that rule out the described attack:

1. **Lookups never traverse the LRU chain.** Both `HotStateLRU::get_slot` and `LayeredHotStateView::get_state_slot` resolve a key strictly by direct hash-map lookup (`pending`/`overlay`/`committed` DashMaps keyed by `HashValue`), never by walking `prev`/`next` pointers: [2](#0-1)  and [3](#0-2) . So even a corrupted LRU chain could not cause a "lookup collision" that serves one key's owner value for another key — the linked list is only used to pick eviction order, not to answer reads.

2. **prev/next are always updated in consistent pairs by the code itself**, not by attacker-supplied data. `insert_as_head` and `delete` update both the new/old neighbor's pointer and the current slot's pointer together, deterministically, based on internal state (`self.head`/`self.tail`), not on any value an unprivileged transaction can directly inject: [4](#0-3)  and [5](#0-4) . Transaction ordering can influence *which* keys become hot/evicted and in what order, but not the internal pointer-pairing logic, which is unconditional.

3. **Invariant is explicitly tested/asserted**, not merely "validated elsewhere" hopefully — `validate_lru` in the committer and `validate`/`validate_impl` in `HotStateLRU` tests, plus proptest fuzzing (`test_empty_overlay`, `test_nonempty_overlay`) already exercise exactly the insert/evict/overlay scenarios the question proposes, and they check bidirectional consistency (walking from head via `next` and from tail via `prev`) against a naive LRU oracle: [6](#0-5)  and [7](#0-6) .

4. **Even hypothetically, the hot state is a cache over authoritative state**, not the source of truth for ownership. The `HotStateValue`/`StateSlot` stored per key still holds the authoritative `StateValue` (e.g., the actual resource bytes including a code object's owner) fetched by exact key hash; the LRU metadata (`lru_info`) is bookkeeping for cache eviction, described in `StateSlotKind::HotOccupied`/`HotVacant` as containing `lru_info: LRUEntry`, separate from the `value` field that custody logic reads. So there is no code path in this file, or the files implementing the trait, where a code-object owner value could be swapped for another key's value due to LRU pointer corruption.

This is a caching/performance data structure issue at most (which would degrade to reduced cache-hit-rate or an internal debug-assert failure caught by `try_merge`'s `debug_assert!(self.validate_lru(...).is_ok())`), not a custody boundary that determines or leaks ownership, freeze, upgrade, or transfer authority. No unprivileged transaction input can make this code return the wrong owner value for a distinct key.

    fn delete(&mut self, key_hash: &HashValue) -> Option<StateSlot> {
        // Fetch the slot corresponding to the given key. Note that `self.pending` and
        // `self.overlay` may contain cold slots, like the ones recently evicted, and we need to
        // ignore them.
        let old_slot = match self.get_slot(key_hash) {
            Some(slot) if slot.is_hot() => slot,
            _ => return None,
        };

        match old_slot.prev() {
            Some(prev_key_hash) => {
                let mut prev_slot = self.expect_hot_slot(prev_key_hash);
                prev_slot.set_next(old_slot.next().copied());
                self.pending.insert(*prev_key_hash, prev_slot);
            },
            None => {
                // There is no newer entry. The current key was the head.
                self.head = old_slot.next().copied();
            },
        }

        match old_slot.next() {
            Some(next_key_hash) => {
                let mut next_slot = self.expect_hot_slot(next_key_hash);
                next_slot.set_prev(old_slot.prev().copied());
                self.pending.insert(*next_key_hash, next_slot);
            },
            None => {
                // There is no older entry. The current key was the tail.
                self.tail = old_slot.prev().copied();
            },
        }

        Some(old_slot)

impl HotStateView for LayeredHotStateView {
    fn get_state_slot(&self, key_hash: &HashValue) -> Option<StateSlot> {
        let shard_id = usize::from(key_hash.nibble(0));
        if let Some(delta) = &self.delta {
            if let Some(slot) = delta.shards[shard_id].get(key_hash) {
                // Delta says this key changed. If hot, return it. If cold/evicted, return None —
                // do NOT fall through to base, the key was explicitly evicted in committed state.
                return if slot.is_hot() { Some(slot) } else { None };
            }
        }
        // Key not in delta (unchanged) — read from base DashMap.
        self.base
            .get_from_shard(shard_id, key_hash)
            .map(|v| v.clone())
    }
}

    fn validate_lru(&self, shard_id: usize) -> Result<()> {
        let head = &self.heads[shard_id];
        let tail = &self.tails[shard_id];
        ensure!(head.is_some() == tail.is_some());
        let shard = &self.base.shards[shard_id];

                let entry = shard.get(&key_hash).expect("Must exist.");
                num_visited += 1;
                ensure!(num_visited <= shard.len());
                ensure!(entry.is_hot());
                current = entry.next().copied();
                total_value_bytes += entry.size();
