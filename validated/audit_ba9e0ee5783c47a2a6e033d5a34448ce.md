This confirms the contrast: `AuthQuery#to_signable_string` explicitly serializes `code`, `host`, `shop`, `state`, `timestamp` into the signed string, while `Webhooks::Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:36-38` returns only `@raw_body`, excluding `shop`, `topic`, `webhook_id`, and `api_version` entirely. `HmacValidator.validate` at `lib/shopify_api/utils/hmac_validator.rb:13-31` calls `verifiable_query.to_signable_string` generically and never inspects headers, so it cannot detect this asymmetry. `Registry.process` at `lib/shopify_api/webhooks/registry.rb:188-200` then trusts `request.topic` for handler dispatch and `request.shop`/`request.webhook_id`/`request.api_version` for the metadata passed to the handler — all sourced purely from unsigned headers.

### Title
Webhook HMAC only covers the raw body, not `shop`, `topic`, `webhook_id`, or `api_version` headers, enabling cross-tenant/cross-topic webhook forgery via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` [2](#0-1)  only authenticates the JSON body bytes and never binds them to the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` headers, which are read directly from unauthenticated request headers [3](#0-2) . `Registry.process` then dispatches to a handler keyed by `request.topic` and forwards attacker-controlled `request.shop`/`request.webhook_id`/`request.api_version` as trusted metadata to the app's handler [4](#0-3) .

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, raw_body || shop || topic || webhook_id)`, i.e. every value the app trusts downstream (shop, topic, webhook_id) should be inside the string that was HMAC'd. In this codebase that binding is false: `to_signable_string` for webhooks is exactly `@raw_body` with nothing else appended [5](#0-4) . Contrast this with `AuthQuery#to_signable_string`, which explicitly folds `code`, `host`, `shop`, `state`, and `timestamp` into the signed string [6](#0-5)  — the webhook path deliberately (or by omission) does not do the analogous thing for its own header-derived fields.

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from `@headers` via `shopify_header`, with no cross-check against the HMAC'd payload [3](#0-2) [7](#0-6) . `HmacValidator.validate` calls `validate_signature`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` via `OpenSSL.secure_compare` [8](#0-7)  — it has no visibility into headers at all, so it cannot catch a header swap.

`Registry.process` raises unless `Utils::HmacValidator.validate(request)` passes, then looks up `@registry[request.topic]&.handler` and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [4](#0-3) . Both the handler selection (`topic`) and the tenant/metadata context handed to the handler (`shop`, `webhook_id`, `api_version`) come entirely from headers outside the signed scope.

Attacker flow: the attacker installs the app on their own development store, receives one or more real, validly-HMAC'd webhook deliveries (e.g., a payload with body `{}` for some topic), then replays that exact raw body to the target app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop, `X-Shopify-Topic` with any topic registered in the app's `Registry`, and `X-Shopify-Webhook-Id`/`X-Shopify-Api-Version` with arbitrary values. Because `HmacValidator.validate` only recomputes HMAC over the untouched raw body, the signature still checks out, and `Registry.process` dispatches the swapped `topic` to whatever handler is registered for it, passing the spoofed `shop` and `webhook_id` through as trusted `WebhookMetadata`.

No existing guard in this code path stops this: `HmacValidator.validate` has no header awareness [2](#0-1) ; `Request#initialize` only checks that certain headers are *present*, not that they're bound to the body [9](#0-8) ; and `Registry.process` performs no independent shop/topic verification beyond the HMAC check [10](#0-9) .

### Impact Explanation
An attacker who can obtain even one validly-signed webhook body (trivially available by installing the app on their own store) can replay it against any handler registered in the target app's `Registry`, tagged with an arbitrary `shop` value and `webhook_id`. Combined with the fact that `shop` is never checked against a real installed-shop list at this layer, this allows a forged, cross-tenant, cross-topic webhook event to be accepted as authentic by the app's handler logic — matching the Critical category "authentication bypass (forged webhook ... accepted), cross-tenant access." This is repeatable per attacker-obtained body/topic pair and against arbitrary victim shop identifiers, since nothing in the gem restricts which `shop` string can be asserted.

### Likelihood Explanation
Preconditions are minimal: the app must use `Webhooks::Registry.process` as documented (the default flow), and the attacker needs only their own development store plus the ability to POST to the app's public webhook endpoint — capabilities explicitly granted to the unprivileged attacker persona. No secrets are required; only header manipulation on a replayed, previously-legitimate body. This is low-cost and fully repeatable.

### Recommendation
Include the relevant header values (`shop`, `topic`, `webhook_id`, and/or `api_version`) in the HMAC-signed string, or independently verify them against out-of-band trusted state (e.g., cross-check `shop` against the app's session store, and reject topics not matching a webhook subscription record keyed by `webhook_id`) before dispatching to a handler in `Registry.process`.
