### Title
Blacklistable feeToken causes permanent freezing of relayer rewards and timed-out request refunds - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost` pays relayer fees and refunds using unconditional `IERC20(feeToken()).safeTransfer(...)` calls with no fallback or try/catch. Hyperbridge's `feeToken` is documented to typically be a stablecoin such as DAI/USDC [4](#0-3) , and centralized stablecoins like USDC/USDT implement an admin-controlled blocklist that makes `transfer`/`transferFrom` revert for blacklisted addresses. Because the recipient of these transfers (`relayer` or `meta.sender`, the original request payer) is attacker-influenced and unprivileged, a malicious/blacklisted address can permanently and unconditionally block delivery of GET responses and timeout processing for entire batches of unrelated messages.

### Finding Description
In `dispatchIncoming(GetResponse ...)`, after the app callback succeeds, the host unconditionally rewards the relayer with the fee token: `IERC20(feeToken()).safeTransfer(relayer, fee)` [5](#0-4) . The `relayer` parameter is passed straight through from `HandlerV2.handleGetResponses`, which forwards `_msgSender()` (the caller of the handler) for every response in the batch [6](#0-5) .

Similarly, `dispatchTimeOut` for both GET and POST request timeouts unconditionally refunds the original payer: `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` [7](#0-6) [8](#0-7) . `meta.sender` is the arbitrary `payer` address supplied when the original request was dispatched via `DispatchPost`/`DispatchGet` (`_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})`) [9](#0-8)  — any unprivileged caller of `dispatch()` can set `payer` to any address, including an address they know is (or will become) blacklisted by the fee token issuer.

Crucially, `HandlerV2.handlePostRequestTimeouts` and `handleGetRequestTimeouts` process an entire batch of timeouts in a single loop within one transaction, invoking `host.dispatchTimeOut(...)` per item with no per-item isolation (no try/catch) [3](#0-2) . If any single `meta.sender` in that batch is blacklisted by the fee token, the `safeTransfer` reverts, unwinding the entire transaction — timeouts for every other unrelated request in the batch also fail to process, even though their proofs were otherwise valid.

### Impact Explanation
This breaks reachable Hyperbridge invariants in two ways:
1. **Permanent freezing of funds**: once a `payer`/`relayer` address is blacklisted by the fee-token issuer, the escrowed fee for that specific commitment can never be refunded or paid — `_requestCommitments`/fee accounting is only cleared after the transfer succeeds, so the commitment is stuck forever, with the fee tokens permanently locked in the `EvmHost` contract.
2. **Denial of message delivery / route unable to deliver messages**: since timeouts are processed as a batch and a single blacklisted-recipient transfer reverts the whole call, any relayer batching a poisoned timeout together with legitimate ones cannot get any of them processed. A malicious actor can grief relayers or the entire timeout pipeline by dispatching low-cost requests with `payer` set to a known-blacklisted (e.g., sanctioned) address, then letting them time out — poisoning any batch a relayer tries to include them in, effectively enabling a route/message-delivery DoS on legitimate users' timeouts as well.

### Likelihood Explanation
`dispatch(DispatchPost)`/`dispatch(DispatchGet)` are unprivileged, callable by any contract/EOA, and `post.payer`/fee payer is fully attacker-controlled [10](#0-9) . No governance or admin action is required — an attacker only needs to reference an address already on a stablecoin issuer's blocklist (200+ such addresses exist per the referenced report) as the `payer`, or use their own address after being sanctioned. Given USDC/USDT's real-world blocklist activity and the trivial cost of dispatching a request, likelihood is realistic, matching a Medium-severity classification.

### Recommendation
Wrap fee-token transfers to attacker-influenced recipients (`relayer` in `dispatchIncoming`, `meta.sender`/`payer` in `dispatchTimeOut`) in a try/catch (or low-level `call`) pattern: on failure, credit the amount to an internal "claimable" balance mapping that the intended recipient (or a designated alternate address) can withdraw later via `pull` semantics, rather than reverting the whole batch. This isolates a single blacklisted recipient's failure from unrelated messages in the same batch and prevents indefinite freezing of the escrowed fee.

### Proof of Concept
1. Attacker calls `EvmHost.dispatch(DispatchGet{..., payer: SANCTIONED_ADDR, fee: X})` (or `DispatchPost`), which stores `_requestCommitments[commitment] = FeeMetadata({sender: SANCTIONED_ADDR, fee: X})` [9](#0-8) .
2. The request times out without delivery.
3. A relayer batches this timeout together with several other legitimate, unrelated timeouts into a single `HandlerV2.handleGetRequestTimeouts` (or `handlePostRequestTimeouts`) call [11](#0-10) .
4. Inside the loop, `host.dispatchTimeOut(...)` for the poisoned entry executes `IERC20(feeToken()).safeTransfer(SANCTIONED_ADDR, X)`, which reverts because USDC/USDT blocks transfers to/from blacklisted addresses [7](#0-6) .
5. The revert propagates up through the loop, reverting the entire `handleGetRequestTimeouts` transaction — none of the batched timeouts (including legitimate users') are processed, and the fee for the poisoned commitment remains permanently locked in `EvmHost` since `_requestCommitments[commitment]` is only deleted at the top of `dispatchTimeOut` before the revert unwinds it back.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
