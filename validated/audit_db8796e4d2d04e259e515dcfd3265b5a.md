### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook shop-spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is verified against `to_signable_string`, which returns only the raw JSON body. The `shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header) is never included in the signed material, yet `Registry.process` hands that unauthenticated `shop` value straight to the app's webhook handler. This reproduces the report's root cause: a value ("wonAmountSecond"/here "shop") that is *acted on* is not *covered* by the integrity check ("2*depositAmount split"/here "HMAC signature"), breaking the intended binding `hmac_verifies(bytes) == identity_trusted(bytes)`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`shop` is read from an HTTP header that is never fed into the signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, so it validates the body's integrity, not the shop header: [3](#0-2) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, on success, forwards `request.shop` (the unauthenticated header value) directly into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality the gem is supposed to guarantee is:
`shop_attributed_to_webhook == shop_that_the_HMAC-signed_payload_originated_from`

But the actual guarantee is only:
`hmac_valid_for(body) == true`, independent of which shop the header claims.

For many webhook topics the body is invariant across shops (e.g. `{}` for topics like `app/uninstalled`, `shop/redact`, `customers/redact`), as the test suite itself demonstrates using a static `"{}"` payload for HMAC computation: [5](#0-4) 

Because the HMAC over `"{}"` (or any other shop-invariant body) is identical for every shop using the same `client_secret`, any merchant who legitimately installs the app on their own store (shop A) can capture a valid `(raw_body, hmac)` pair from a real webhook delivery to their own endpoint. That same `(raw_body, hmac)` pair remains cryptographically valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to any other shop domain (shop B), since the header is not part of the signed content.

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret`, an access token, or any credential belonging to the victim shop — only a legitimate installation of the app on the attacker's own store (an "unprivileged internet user" from the victim's perspective). The forged request is accepted by `HmacValidator.validate` and the handler receives `WebhookMetadata` claiming to be for the victim's shop (`shop: request.shop`), potentially causing the host application to process, store, or act on attacker-controlled/replayed events attributed to a shop the attacker doesn't control (e.g., triggering redaction/uninstall/data-processing side effects, or shop-keyed cache/storage writes under `shop`). This matches the Critical category: cross-tenant access via a broken identity binding.

### Likelihood Explanation
Likelihood is high for any topic whose payload does not embed shop-specific data (empty-body or generic-body topics are common in Shopify's mandatory/GDPR and lifecycle webhooks). The attacker only needs one legitimate app installation of their own to harvest a valid `(body, hmac)` pair — no secret-key knowledge, no interception of another tenant's traffic, and no social engineering required.

### Recommendation
Bind the `shop` identity into the signed material actually verified, or otherwise assert that the header-supplied `shop` is consistent with data derivable from an authenticated source (e.g., look up/verify the shop against a stored session/access-token record rather than trusting the header verbatim), before constructing `WebhookMetadata`. At minimum, the gem should document/enforce that `request.shop` is not authenticated by the HMAC and must not be trusted as a tenant identifier on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining valid webhook deliveries for a shop-invariant topic (e.g. body `"{}"`).
2. Attacker records the delivered headers `x-shopify-hmac-sha256: <H>` and body `"{}"`.
3. Attacker POSTs to the app's webhook endpoint with:
   - body: `"{}"`
   - `x-shopify-hmac-sha256: <H>` (unchanged, still valid because signed content is only the body)
   - `x-shopify-shop-domain: victim.myshopify.com` (spoofed)
   - `x-shopify-topic`, `x-shopify-webhook-id` set arbitrarily.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body signature: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata` claiming `shop: "victim.myshopify.com"`, even though the payload never originated from Shopify for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
