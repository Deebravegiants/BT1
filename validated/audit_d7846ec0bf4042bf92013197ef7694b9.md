### Title
Overpaid native token fees on `EvmHost.dispatch()`/`fundRequest()` are permanently stuck in the Host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all forward the caller's entire `msg.value` into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), ...)` but discard the returned `amounts` array and never refund unspent ETH to the caller, unlike the intents contracts in the same repo that explicitly track and refund the swap remainder.

### Finding Description
In `EvmHost.sol`, the POST/GET dispatch and fee-top-up entrypoints accept native token payment and swap it for the fee token via Uniswap V2: [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` only spends as much ETH as is required to obtain the exact `fee`/`amount` output; any leftover ETH from `msg.value` is refunded by the Uniswap V2 router to its immediate caller. Since `EvmHost` itself calls the router, the router's refund goes to `address(this)` (the `EvmHost` contract), not to the original transaction sender. `EvmHost` discards the `amounts` return value in all three call sites and has no logic to forward the residual ETH back to `msg.sender`, nor any admin/sweep function to reclaim stray native balance — `grep` across `EvmHost.sol` found no `receive`/`fallback` handling that redistributes funds and no withdraw/sweep function for native ETH.

This is directly analogous to the report's bug class ("native tokens mistakenly sent... will be stuck because withdraw functions don't account for the extra token/amount"): here, any user who overestimates the fee-swap cost and sends excess `msg.value` has that excess permanently locked in `EvmHost`.

Contrast with the correct pattern used elsewhere in the same codebase, `IntentGatewayV2.sol`, which captures `amounts[0]` from the swap, decrements `msgValue` by it, and explicitly refunds the remainder to `msg.sender`: [4](#0-3) 

`EvmHost.dispatch()`/`fundRequest()` never perform this refund step, confirming the omission is an actual bug rather than intended behavior.

### Impact Explanation
Any unprivileged user dispatching a POST/GET request or funding a pending request with native token payment (`dispatch{value: msg.value}(...)`, `fundRequest{value: msg.value}(...)`) will have any ETH sent beyond the exact amount needed for the Uniswap swap permanently locked in `EvmHost`, since there is no mechanism to recover it. This is a direct, unprivileged loss-of-funds/freezing issue reachable from a single transaction — fee estimation is inherently approximate (documentation itself instructs callers to "estimate fees on the client side" and send `msg.value`), so overpayment is a normal, expected occurrence, not an edge case requiring malicious input.

### Likelihood Explanation
High. Because Uniswap swap output pricing fluctuates with the pool state, any client that adds slippage buffer/safety margin to its fee estimate (a very common and encouraged practice, as shown in the SDK docs) will routinely overpay `msg.value`. Every dispatch call using native-token payment is exposed, making this a systemic rather than theoretical issue.

### Recommendation
Capture the `amounts` return value from `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()` (mirroring the pattern already implemented in `IntentGatewayV2._sendValue`/`msgValue -= amounts[0]`).

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires ~0.01 ETH worth of the underlying Uniswap pool at execution time.
2. `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` spends only the ~0.01 ETH equivalent and refunds the remaining ~4.99 ETH to the caller of the router, which is `EvmHost` (`address(this)` in `EvmHost`'s context), per `evm/src/core/EvmHost.sol:921-932`.
3. `EvmHost.dispatch()` never reads the `amounts` return value or forwards any ETH back to the user.
4. There is no admin/sweep/withdraw function found in `EvmHost.sol` for native ETH balance, so the ~4.99 ETH remains permanently stuck in the contract.
