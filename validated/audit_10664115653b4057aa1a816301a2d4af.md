The gem's own documentation explicitly states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and instructs handlers to trust `data.shop` as "The shop domain of the webhook" (`docs/usage/webhooks.md:14`) — yet the HMAC only covers the raw body, not the shop-domain header.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which checks the HMAC-SHA256 over the raw request body against the app's `api_secret_key`. The `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in the signed bytes, yet it is passed straight through to the app's webhook handler as the trusted tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `Request#shop` is read verbatim from an HTTP header that is completely outside the HMAC computation: [2](#0-1) 
`Registry.process` verifies only the HMAC over that signable string and then forwards `request.shop` unchanged into `WebhookMetadata`, which is what host applications use to select the tenant/shop record: [3](#0-2) 

The `api_secret_key` used to compute/verify the HMAC is per-app, not per-shop — every shop that installs the same app shares the identical secret for signing its own webhook deliveries. This breaks the intended binding `verified_bytes == shop_identity_bytes`: HMAC verification proves "this raw body was signed by our app's secret," but it does not prove "this raw body came from the shop named in the header." An attacker who controls (or has installed the app on) their own shop, `attacker.myshopify.com`, receives a legitimately-signed webhook (body + valid HMAC) from Shopify for their own store. Since the HMAC only signs the body, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain: victim.myshopify.com`. `HmacValidator.validate` still succeeds (the body bytes and HMAC are unchanged and valid), and `Registry.process` calls the handler with `WebhookMetadata.shop == "victim.myshopify.com"` — an identity the host app documented-ly trusts as the record owner per the gem's own docs.

### Impact Explanation
This is a cross-tenant access primitive: host applications built per this gem's documented contract (`docs/usage/webhooks.md`) use `data.shop` to select which merchant's data to create/update/delete in response to the webhook body content. An attacker can forge webhook events attributed to any other shop using this app, causing cross-tenant data corruption or disclosure without ever needing that victim's credentials or access token.

### Likelihood Explanation
Medium-to-High: any user who can install the app on their own store (common for public apps) can trivially trigger genuine, validly-signed webhooks for arbitrary topics/bodies they control (e.g., by editing their own products/orders), then replay the body+HMAC to the shared webhook endpoint with a forged shop header. No secrets, tokens, or privileged access are required beyond a normal install.

### Recommendation
Bind the shop identity into the verified bytes, or cross-check it against an authenticated source: e.g., include the `shop` (and `topic`/`webhook_id`) in the HMAC-signed payload verification, or require the host app to look up/validate the claimed shop against a known list of shops that have active registrations/sessions before trusting `WebhookMetadata.shop`, and document this requirement prominently. At minimum, `HmacValidator` should be extended so `Webhooks::Request#to_signable_string` incorporates the shop-domain header value in a way that ties it cryptographically to the signature Shopify sends, or the library should reject/flag mismatches between the header shop and any shop reference inside the parsed body where available.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`) for their own store; Shopify delivers:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 1, ...}`
2. Attacker resends this exact body and HMAC header to the app's webhook endpoint, only changing `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — matches, since body/HMAC are untouched. [4](#0-3) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: ..., topic: ...)`. [5](#0-4) 
5. The host application, following the gem's documented contract that `data.shop` is "The shop domain of the webhook," processes attacker-controlled data under the victim shop's tenant context.
