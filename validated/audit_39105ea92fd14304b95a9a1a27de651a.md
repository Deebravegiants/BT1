Based on my investigation, I found a genuine analog to the reported issue in `EvmHost.sol`.

### Title
Native ETH refunded by Uniswap during fee-swap dispatch becomes permanently stuck in `EvmHost` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` are all `payable` functions that, when called with `msg.value > 0`, swap the supplied native token for an exact amount of `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`. Any unprivileged user calling these functions with excess native token value will have the difference refunded by the Uniswap router — but that refund lands back in the `EvmHost` contract itself, not the original caller, and there is no function to recover it.

### Finding Description
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`: [1](#0-0) [2](#0-1) 

Each of these calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The UniswapV2 Router's `swapETHForExactTokens` implementation refunds any unused ETH (`msg.value - amounts[0]`) to `msg.sender` of that call — but because `EvmHost` itself is the caller of the router (not the original end user), the refund is sent back to `EvmHost`, not to the transaction originator. If a caller overestimates the required native fee (which is common since the exact price depends on live Uniswap reserves at execution time), the difference is trapped inside `EvmHost` permanently.

Unlike the original `XChainController` report, this isn't a hypothetical "deployer forgot payable" scenario — it's an active, guaranteed byproduct of the fee-swap mechanism triggered by ordinary, unprivileged users dispatching messages or funding requests with native token payment, which the docs explicitly recommend as a supported payment path. [3](#0-2) 

### Impact Explanation
Any dust/overpayment ETH sent via `dispatch()` or `fundRequest()` accumulates in `EvmHost` with no recovery mechanism identified in the contract. Over time and across many callers (this is a public, permissionless, frequently-used entry point), meaningful value can become permanently locked, constituting a freezing-of-funds impact under the given validation criteria. This is not a "no-impact" issue since real user funds (via unavoidable slippage/refund from the swap) are irrecoverably lost.

### Likelihood Explanation
High likelihood: `swapETHForExactTokens` requires the caller to send `msg.value` that's at least as much as needed but the exact optimal amount depends on Uniswap pool state at execution time, which can shift between fee estimation (off-chain, per the docs' "Estimating Fees" guidance) and on-chain execution due to normal price movement or MEV — the router mechanically refunds any excess, and that excess is guaranteed to be nonzero whenever the caller doesn't send the exact optimal amount to the wei. This is a routine occurrence for every user paying fees in native token, not an edge case.

### Recommendation
Add an owner/admin function to sweep any native ETH balance accidentally accumulated in `EvmHost` (e.g., a `withdrawNative()` restricted to the host manager/admin), or better, refactor the fee-swap calls to explicitly capture and forward any refunded native token back to `_msgSender()` within the same transaction rather than letting it settle in the contract.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` with `post.fee = X` and sends `msg.value = Y` where `Y > ` the ETH amount actually required to acquire `X` fee tokens at execution-time Uniswap price.
2. `swapETHForExactTokens{value: Y}(X, path, address(this), deadline)` executes, consuming only `amounts[0] < Y` ETH and refunding `Y - amounts[0]` to `msg.sender`, which is `EvmHost` (since `EvmHost` is the direct caller of the router). [1](#0-0) 
3. The refunded ETH sits in `EvmHost`'s balance. No function exists in `EvmHost.sol` to withdraw this native balance back out, permanently locking it.

Note: I was unable to fully enumerate every occurrence of "withdraw" in `EvmHost.sol` due to tool output limitations in this session (the search only returned match counts, not the surrounding code for all hits), so I cannot rule out with 100% certainty that some unrelated native-ETH sweep function exists elsewhere in the file under a different name. However, based on the portions of the file I was able to read directly (including the full `dispatch`/`fundRequest` functions and the end of the contract), no such function was present.
