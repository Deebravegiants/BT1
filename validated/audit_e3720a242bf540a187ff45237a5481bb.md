### Title
Webhook `shop` (tenant) identity is not HMAC-authenticated, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` (tenant identity) that the webhook handler receives is taken from an HTTP header that is never covered by that HMAC, so any request bearing a validly-signed body can be delivered with an arbitrary `shop` value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely independent from the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the `Request` object and, once it passes, forwards `request.shop` straight into the app's handler as the tenant identifier, with no additional check that the shop matches anything cryptographically bound to the signed body: [3](#0-2) 

Because Shopify signs webhooks with the single shared `client_secret` for the whole app (not a per-shop secret), any merchant who installs the app can obtain a validly-HMAC'd webhook body for their own shop by triggering a real event. The attacker (an unprivileged internet user who merely installed the app on their own store, i.e., no elevated privilege inside the target app) can then replay that exact body to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass (`compute_signature(verifiable_query.to_signable_string, secret)` only covers `raw_body`), yet `WebhookMetadata.shop` will report the victim's shop: [4](#0-3) 

This is the binding break: `shop_authenticated_by_hmac == ∅` while `shop_used_by_handler == attacker_supplied_header`. The gem provides no mechanism (and no documented guidance) for host applications to cryptographically bind the header-derived shop to the signed payload, so any consumer relying on the library's "validated webhook" abstraction inherits this gap.

### Impact Explanation
If the host app's webhook handler uses `WebhookMetadata#shop` to key data updates, uninstall/reinstall logic, credential rotation, or GDPR/compliance actions (all common webhook use-cases), an attacker can cause the app to apply another shop's webhook data/actions against an arbitrary victim shop record, i.e., cross-tenant access/corruption using only a self-service install of the app on the attacker's own store. No access token, `client_secret`, or privileged account is required — only the ability to install the target app on an attacker-controlled shop and replay one HTTP request with a modified header.

### Likelihood Explanation
Any developer/merchant can install a public Shopify app to obtain a legitimately-signed webhook body. Swapping one HTTP header before replaying to the app's public webhook endpoint requires no special access. The only friction is knowing/guessing the target app's expected webhook endpoint (typically public) and a target shop domain (public information, e.g., `victim.myshopify.com`).

### Recommendation
Bind the asserted `shop` to the signed material, e.g., include `shop` (and ideally `topic`/`webhook_id`) in `to_signable_string`, or independently validate that the `shop` domain returned by Shopify's webhook matches a shop the app has an active installation/session for before dispatching to the handler. At minimum, document prominently that `Request#shop` is unauthenticated and must not be trusted for tenant-scoping decisions without additional verification by the host app.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a real webhook delivery with header `shopify-shop-domain: attacker.myshopify.com`, some `raw_body`, and a valid `shopify-hmac-sha256` computed over `raw_body` with the app's shared secret.
2. Attacker replays the identical body/HMAC to the app's webhook endpoint, changing only the header to `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` [1](#0-0)  and succeeds.
4. `handler.handle` receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"` [5](#0-4) , causing the host app to process attacker-controlled data under the victim's tenant identity.
