### Title
Withdrawal completion status for POA Bridge matches by `assetId` only, causing a wrong transaction hash to be reported for the wrong withdrawal when multiple withdrawals of the same token exist in one batch - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status/hash for a specific withdrawal identifier (index + tx) by looking up the POA bridge indexer response and matching purely on `assetId`, not on index, destination address, or amount. When a single NEAR transaction contains two or more withdrawals of the same token (e.g. to two different destination addresses), `findMatchingWithdrawal` will always return the *first* entry in the unsorted API response that has that `assetId`, so every withdrawal index sharing that asset resolves to the same underlying transfer.

### Finding Description
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [1](#0-0)  which only filters by `assetId`, ignoring `args.index`, `args.withdrawalParams.destinationAddress`, and `args.withdrawalParams.amount`: [2](#0-1) 

The docstring explicitly acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but the caller-facing API (`WithdrawalIdentifier`, `watchWithdrawal`, `sdk.waitForWithdrawalCompletion`) does not reject or warn about this case — it silently returns a `completed` status with a `txHash` that may belong to an entirely different withdrawal (different destination address / amount) than the one the caller is polling for. This breaks the equality that "the status/hash reported for withdrawal index N corresponds to withdrawal N's actual on-chain outcome": with two same-asset withdrawals to different addresses in one intent, index 1's `describeWithdrawal` call can report `completed` with the `txHash` that actually belongs to index 0's transfer (whichever entry appears first in the unsorted response), even if index 1's own transfer is still pending, failed, or sent to a different address entirely.

### Impact Explanation
Per the rules, "a status or hash misreport making an integrator credit or refund twice" is a valid High-impact finding. Here, a caller (integrator or the SDK's own `sdk.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`, see [3](#0-2) ) that submits a batch of withdrawals with duplicate `assetId`s to different destinations would receive a false "completed" signal and a hash for the wrong withdrawal. This can cause an integrator to mark/credit the wrong recipient as paid, or resolve a promise for a withdrawal that has not actually settled, before its true destination transfer has finalized.

### Likelihood Explanation
This requires the caller to batch two or more withdrawals of the same `nep141` asset (regardless of differing destination addresses) into a single NEAR transaction/intent, which is an ordinary, permitted usage pattern of `withdrawalParams: WithdrawalParams[]` (no privileged actor required) as seen in `sdk.waitForWithdrawalCompletion` supporting arrays of `WithdrawalParams` [4](#0-3) .

### Recommendation
Match withdrawals by a discriminator that uniquely identifies each entry (e.g., destination address + amount, or order-preserving matching against the intent's withdraw actions) instead of `assetId` alone, or explicitly disallow/detect duplicate-asset batches and surface an error rather than silently returning a possibly-mismatched hash.

### Proof of Concept
The existing test `"matches withdrawal by assetId, not by index"` demonstrates the mechanism: two `COMPLETED` withdrawals for different assets (`eth`/`btc`) are correctly disambiguated by `assetId` [5](#0-4) . Replacing the second withdrawal's `defuse_asset_identifier`/`near_token_id` with the *same* asset as the first (e.g., two `nep141:btc.omft.near` entries with different `address`/`transfer_tx_hash`) while calling `describeWithdrawal` for `index: 1` shows `findMatchingWithdrawal` returns the first (`index 0`)'s entry — reporting `index 1`'s status/hash as that of `index 0`'s transfer.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

			? args.withdrawalParams

		const promises = this.createWithdrawalCompletionPromises({
			withdrawalParams: withdrawalParamsArray,
			intentTx: args.intentTx,
			signal: args.signal,
			logger: args.logger,
		});

		const result = await Promise.all(promises);

		if (Array.isArray(args.withdrawalParams)) {
			return result;
		}
