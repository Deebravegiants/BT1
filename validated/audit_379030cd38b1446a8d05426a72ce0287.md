### Title
Shared single `onChainEncryptedOutput` blob collides across multiple on-chain UTXOs of the same/different tokens, causing wrong-amount decryption and stranded funds - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` passes the single `bytes calldata circomData.onChainEncryptedOutput` field to `createOnchainCommitment` for *every* `utxoSet[j]` that matches a given `erc20TokenAddresses[i]` inside the nested loop, and it is the same value reused across all `i` iterations too. Each resulting `OnChainCommitment` therefore has a distinct `commitment` hash (derived from `utxo.amount`, `erc20Address`, `stealthAddress`, `timeStamp`) but an identical `onChainEncryptedOutput`, breaking the required one-to-one mapping between a leaf's commitment and the ciphertext that lets its owner recover the correct amount/timestamp.

### Finding Description
The broken equality: for every `NewCommitment` leaf `L_k` with `commitment_k = hash4(amount_k, erc20_k, stealthAddress_k, timeStamp_k)`, the emitted `onChainEncryptedOutput_k` must decrypt uniquely to `(amount_k, timeStamp_k, ...)` specific to that leaf. In the code: [1](#0-0) 

`circomData.onChainEncryptedOutput` (declared as a single `bytes`, not `bytes[]`, in `CircomData`) is passed unchanged for every matching `utxoSet[j]`: [2](#0-1) 

`createOnchainCommitment` stores whatever it is given verbatim into `OnChainCommitment.onChainEncryptedOutput`, with no linkage check between the ciphertext and the specific `utxo`: [3](#0-2) 

`insertCommitments` then emits one `NewCommitment` event per `OnChainCommitment`, each carrying `commitment_k` (which differs per UTXO) together with the identical `onChainEncryptedOutput`: [4](#0-3) 

Root cause: `CircomData` was designed assuming at most one on-chain-created UTXO exists per transaction (single `bytes onChainEncryptedOutput` field, singular, not indexed per token/utxo), while `Hinkal.transact`'s loop structure supports `utxoSet` containing multiple UTXOs (possibly for the same token, via an external action such as `DepositOnChainUtxosExternalAction` returning several UTXOs) or across multiple tokens. Nothing in `verifyProof`, `performHinkalChecks`, or the circuit constraints referenced in the prompt (`OverflowPreventer`/`ForceEqualIfEnabled` in `ConditionalOverflowPreventer.circom`) constrains or checks the encrypted output content — the circuit only proves numeric balance/overflow relationships on amounts, not that the off-chain ciphertext is bound to a specific leaf's commitment. There is no on-chain hash-commitment linking `onChainEncryptedOutput` to `commitment`.

Attacker flow: an attacker (as the transacting user, spending only their own funds) crafts `externalActionMetadata` for an external action returning `utxoSet` with 2+ UTXOs for the same `erc20Address` (or across two token addresses both processed with the shared field), completes a valid proof for the balance/overflow relations (which do not depend on the encrypted payload), and calls `transact`. All resulting `NewCommitment` events for those leaves carry byte-identical `onChainEncryptedOutput` despite different `commitment` values.

Existing guards do not catch this: `performHinkalChecks`, `dimensionsCheck`, `verifyProof`, `rootHashExists`, the slippage/balance `require`s, and `insertNullifiers` all operate on numeric fields (`amountChanges`, `balanceDif`, nullifiers, root) — none of them constrain or validate `onChainEncryptedOutput` against `commitment` or `utxo.amount/timeStamp`, since this ciphertext is off-chain/off-circuit data purely for the recipient's convenience.

### Impact Explanation
Whoever is the intended recipient of the second (or later) affected on-chain UTXO cannot decrypt the correct amount/timeStamp for their leaf — they would decrypt the same payload intended for a different leaf. If the ciphertexts encode a different UTXO's amount, the recipient recovers a wrong balance and cannot correctly construct a spending proof for their real leaf (the real `commitment` for their leaf depends on the true amount/timeStamp, which they never learn). This can result in funds becoming effectively unspendable/frozen for the affected leaf's owner. Note: this scenario is most damaging when the two UTXOs go to *different* stealth addresses/recipients (e.g., a swap/deposit action producing outputs for two different users or two different tokens for the same user in the same tx) — in the self-deposit-to-self case described in the proof idea, the depositor typically holds all the keys and could potentially reconstruct amounts by brute-force trial against known deposit amounts, which would reduce impact to at most a temporary/self-inflicted issue rather than true fund loss for a third party. Given the question's framing (single depositor creating 2 UTXOs of one token to themselves), the severity is bounded: the depositor knows both amounts already and typically also controls the stealth key, so the "loss" is a UX/decryption ambiguity rather than an unrecoverable freeze, unless the two leaves are destined for different recipients' stealth addresses.

### Likelihood Explanation
Preconditions are attacker-controllable: any external action registered via `registerExternalAction` (permissioned, done by the `DEFAULT_ADMIN_ROLE`, not the attacker) that returns multiple UTXOs matching a shared `erc20Address` must exist, or the attacker must deploy/route through such an action if one exists. `DepositOnChainUtxosExternalAction.sol` is referenced in the question as supporting `utxoAmounts[i]` with multiple positive entries per token; confirming whether it can actually return 2+ UTXOs of the *same* token within one `runAction` call (and whether the resulting `utxoSet` ordering causes the collision in the `Hinkal.transact` loop) required inspecting that contract's logic in depth, which the available context only partially covered. The mechanism (single shared `bytes` field applied per-matching-UTXO in a loop) is confirmed directly in `Hinkal.sol`, `HinkalBase.sol`, and `CircomData.sol`.

### Recommendation
Change `CircomData.onChainEncryptedOutput` from a single `bytes` to a `bytes[]` (or `bytes[][]` keyed by token index and UTXO-within-token index), and update `Hinkal.transact`'s `createOnchainCommitment` call to pass `circomData.onChainEncryptedOutput[onChainCommitmentCounter]` (or an equivalent per-UTXO index) instead of the single shared field, mirroring how `offChainEncryptedOutputs` is already indexed as `bytes[][]`. Update `performHinkalChecks`/`dimensionsCheck` and any circuit-side dimension checks accordingly to validate the new array length against the number of on-chain-created UTXOs.

### Proof of Concept
Because confirming the exact multi-UTXO return behavior of `DepositOnChainUtxosExternalAction` and constructing a valid Groth16 proof requires running the full proving pipeline and reading that contract's full logic (not fully available in this pass), a concrete Foundry test could not be finalized here. The suggested test plan:
1. Deploy `Hinkal`, register a mock/real `DepositOnChainUtxosExternalAction` that returns a `UTXO[]` with 2 entries for the same `erc20Address` (or one entry per of 2 different tokens), with distinct `amount`/`timeStamp`/`stealthAddress`.
2. Generate a valid proof (or use a mock verifier) with a single `circomData.onChainEncryptedOutput` blob and `circomData.erc20TokenAddresses` covering the affected token(s).
3. Call `transact` and capture both `NewCommitment` events.
4. Assert: `commitment_1 != commitment_2` (different leaves) while `onChainEncryptedOutput_1 == onChainEncryptedOutput_2` (byte-identical), demonstrating the broken one-to-one leaf↔ciphertext equality.

Given the partial confirmation of the multi-UTXO-return capability of `DepositOnChainUtxosExternalAction` and the mitigating factor that the depositor in the described scenario typically controls both resulting UTXOs, this finding is reported with the caveat that a full impact/severity determination (Critical permanent freezing of a *third party's* funds vs. self-inflicted UX ambiguity) depends on external-action-specific recipient/stealth-address assignment that was not fully verified in this pass.
