### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `x-shopify-shop-domain` header, but the HMAC signature verified by `HmacValidator` only covers the raw request body. Any unprivileged merchant who has installed the app (and can therefore obtain a genuine `body + hmac` pair for their own shop) can replay that pair against the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop, and the library will accept it as an authentic webhook for the victim tenant.

### Finding Description
The HMAC binding is defined by `to_signable_string`, which returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from a header and is never mixed into the signed material: [2](#0-1) 

`HmacValidator.validate` verifies exactly (and only) that string against the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` trusts this validation and then forwards `request.shop` straight into the metadata handed to the app-registered handler, with no additional binding between the verified bytes and the shop claim: [4](#0-3) 

The identity binding that should hold is:
`shop asserted in WebhookMetadata.shop == shop whose data actually produced the verified bytes`

Because `api_secret_key` is a single value shared across every shop that has installed the app (it's the app's `client_secret`, not a per-shop secret), any shop's genuine webhook delivery yields a valid `(body, hmac)` pair computed with that same key. An attacker who runs (or compromises) their own shop installation can trigger a real webhook to capture a valid `(body, hmac)` pair, then resend it to the app's webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body bytes, and `Registry.process` will invoke the handler believing the payload belongs to the victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to establish for webhook processing: the app's handler is invoked with attacker-controlled data explicitly labeled as belonging to a different, victim shop. Any host application that uses `WebhookMetadata.shop` to key data writes, cache invalidation, session lookups, or state transitions (the documented and expected usage pattern) can be made to attribute or apply attacker-supplied data to a victim tenant, i.e., cross-tenant data injection/confusion, without needing the victim's or the app's credentials.

### Likelihood Explanation
The attacker needs no privileged credentials, no `api_secret_key`, and no access to the victim shop. They only need (a) their own legitimate app installation, which is trivial to obtain for any public app, and (b) the ability to POST directly to the app's public webhook endpoint with custom headers, which is inherent to how webhook endpoints work (they must accept unauthenticated HTTP POSTs and rely solely on the HMAC + gem's parsing for trust). This is a low-effort, repeatable attack path.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed/verified material, or independently bind the `shop` header to the tenant context validated elsewhere (e.g., cross-check against a known/registered shop list, or require the shop domain to be echoed inside the signed body payload where Shopify includes it, per-resource). At minimum, `VerifiableQuery`/`HmacValidator` should be extended so `to_signable_string` incorporates the shop-domain header, and `Registry.process` should reject requests where the header-derived shop is not consistent with the verified payload.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (normal, unprivileged flow).
2. Attacker triggers a real Shopify webhook (e.g., updates an order) and captures the raw HTTP request Shopify sends to the app's webhook endpoint, including headers `x-shopify-hmac-sha256: <hmac>` and body `<raw_body>`.
3. Attacker resends this exact `raw_body` and `hmac` header to the same webhook endpoint, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged request; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-43`).
5. `Registry.process` invokes the registered handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and the attacker's chosen body (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host app to process attacker data under the victim's tenant identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
