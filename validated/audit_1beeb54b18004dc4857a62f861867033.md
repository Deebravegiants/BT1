### Title
Webhook `shop` identity trusted from unauthenticated header while HMAC only signs the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` value handed to the application's webhook handler is read from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header, which is never included in the signed material. This breaks the identity binding `shop authenticated == shop delivered to handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC using that signable string against `verifiable_query.hmac` [2](#0-1) . The `shop` accessor, however, is derived independently from the `shop-domain` header, which plays no part in the signable string: [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [4](#0-3) .

Because the header is not part of the signed payload, an attacker who can reach the webhook endpoint with a body/HMAC pair captured from (or legitimately computed for, e.g. via a `shop/redact`/`customers/redact` payload their own store received) shop A can resend it while forging the `X-Shopify-Shop-Domain` header to shop B's domain. `Utils::HmacValidator.validate` will still return `true` because it only checks `Digest.hexencode(Base64.decode64(hmac_header))` against `HMAC(raw_body, secret)` — the shop header is never verified. The gem then constructs `WebhookMetadata` with `shop: request.shop` set to the attacker-controlled value and invokes the registered handler as if the webhook genuinely originated from that shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the equality `shop value cryptographically bound by HMAC == shop value delivered to the handler` does not hold. Host applications that key data by `data.shop` (e.g., to update per-tenant state, deduct entitlements, revoke access, or process GDPR redaction requests) can be made to act on the wrong tenant's data because the gem provides no authenticated shop value — only an authenticated body. This matches the "shop authenticated versus shop used as identity/session key" analog class explicitly called out in the rules.

### Likelihood Explanation
Exploitability depends on an attacker being able to obtain one valid `(raw_body, hmac)` pair (trivial for topics whose body is public/predictable, such as `shop/redact` or `app/uninstalled` with generic content, or for any webhook the attacker's own shop legitimately receives) and then replaying it with a spoofed shop header to the same public webhook endpoint. Since `Registry.process` performs no additional binding of the header to the signature, likelihood is moderate to high wherever the host app trusts `WebhookMetadata#shop` without independent verification (e.g., cross-checking against the shop that owns the webhook subscription).

### Recommendation
Include the shop domain (and topic) in the signed material, or independently verify `request.shop` against a value derived from an authenticated source (e.g., look up the webhook by `webhook_id` via the Admin API, or bind the shop into the HMAC signable string per Shopify's REST webhook delivery contract) before passing it to `WebhookMetadata`/handlers. At minimum, document that `data.shop` in `WebhookMetadata` is unauthenticated and must not be trusted for tenant-sensitive operations without further verification.

### Proof of Concept
1. Attacker's own store receives a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (where `H = HMAC-SHA256(client_secret, B)`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends `POST /webhooks` to the victim host app with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` (the raw body) and `hmac` still match — the shop header was never part of the check [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com`, even though the payload was never actually generated for that shop [7](#0-6) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
