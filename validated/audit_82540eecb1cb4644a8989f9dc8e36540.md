## Analysis Result

<title>Wallet Contract's Hardcoded NEP-141 Storage Deposit Amount Causes Legitimate ERC-20 Transfer Emulations to Fail - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)</title>

### Summary
The `WalletContract`'s ERC-20 emulation logic uses a single hardcoded `NEP_141_STORAGE_DEPOSIT_AMOUNT` constant for the `storage_deposit` call required by every NEP-141 token contract, regardless of that specific token contract's actual `storage_balance_bounds`. This is directly analogous to the `UniswapV3Swapper` bug where a single fixed `poolFee` was used for all token pairs even though the correct value depends on the specific pair — here, a single fixed deposit amount is used for all token contracts (and implicitly for all receiver account IDs) even though the correct required amount can vary per token implementation and per receiver account ID length.

### Finding Description
The wallet contract emulates ERC-20 `transfer` calls by mapping them to NEP-141 `ft_transfer`, first checking if the receiver is registered via `storage_balance_of`, and if not, chaining a `storage_deposit` call before the transfer: [1](#0-0) 

The deposit amount attached to that `storage_deposit` call is the constant `NEP_141_STORAGE_DEPOSIT_AMOUNT`, hardcoded at `1_250 * MICRO_NEAR`: [2](#0-1) 

The code comment explicitly acknowledges this is a fixed-value shortcut instead of dynamically querying `storage_balance_bounds`: [3](#0-2) 

However, NEP-145 `storage_balance_bounds` is not a protocol-fixed constant — implementations commonly scale the minimum required deposit with the length of the `account_id` being registered (as seen in this very codebase's own `address-registrar` contract, which computes `bytes_to_store = 20 + account_id.len()` and requires a deposit proportional to it): [4](#0-3) 

Since NEAR account IDs can be up to 64 bytes, and different (fully legitimate, non-malicious) NEP-141 implementations can have different per-byte storage costs or minimum bounds larger than 1,250 μNEAR, a `storage_deposit` call funded with the fixed `NEP_141_STORAGE_DEPOSIT_AMOUNT` can be insufficient for a specific token/receiver combination. When that happens, the `storage_deposit` action panics for insufficient deposit, causing the whole batched receipt (`storage_deposit` + `ft_transfer`) to fail: [5](#0-4) 

The callback then reports the entire emulated ERC-20 transfer as `PromiseResult::Failed`: [6](#0-5) 

This mirrors the reported bug class precisely: a single fixed configuration value (`poolFee` / `NEP_141_STORAGE_DEPOSIT_AMOUNT`) is applied uniformly to targets (token pairs / token contracts+receivers) whose correct required value is actually target-specific, so the operation silently fails whenever the actual required value diverges from the hardcoded default.

### Impact Explanation
Medium — any legitimate NEP-141 token contract (or receiver account ID) whose actual minimum storage deposit exceeds 1,250 μNEAR will cause every unregistered-receiver ERC-20 transfer emulation through the Wallet Contract to fail with `"Failed Near promise"`, even though the user's underlying intent (a valid token transfer) was entirely legitimate. This breaks a documented user-facing capability of the Wallet Contract (automatic on-boarding of the receiver via `storage_deposit`) for a class of standard-compliant tokens/receivers.

### Likelihood Explanation
Medium — this only manifests for token contracts or account IDs whose storage requirement differs from the assumed default (e.g., non-default/longer account IDs, or NEP-141 implementations with different per-byte storage accounting), which is a plausible but not universal subset of real-world receivers/tokens.

### Recommendation
Instead of hardcoding a single deposit amount for all tokens, either (a) query the target token contract's `storage_balance_bounds` before constructing the `storage_deposit` call and use the actual `min` value (capped at a safe maximum to still guard against malicious contracts), or (b) attach a deposit sized to the specific receiver account ID length, consistent with how `storage_balance_bounds` is typically computed.

### Proof of Concept
1. Deploy a NEP-141 token contract whose `storage_balance_bounds.min` is set (or computed based on `account_id.len()`) to a value greater than `1_250 * MICRO_NEAR` (e.g. a token contract that charges storage proportional to a long receiver account ID, similar to the `address-registrar` contract's own `bytes_to_store = 20 + account_id.len()` pattern in this repo).
2. Have a Wallet Contract user send a valid ERC-20-emulated `transfer` (per `EthEmulationKind::ERC20Transfer`) to an unregistered receiver with a long account ID on that token.
3. `nep_141_storage_balance_callback` observes the receiver is unregistered (`None` storage balance) and issues `storage_deposit` funded only with the fixed `NEP_141_STORAGE_DEPOSIT_AMOUNT` constant.
4. Because the attached deposit is less than the token's actual required minimum, the `storage_deposit` action fails, the batched receipt fails, and `rlp_execute_callback` returns `ExecuteResponse { success: false, error: Some("Failed Near promise") }` even though the transfer itself was valid and well-formed.
