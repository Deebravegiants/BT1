### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop spoofing on an otherwise validly-signed webhook - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which HMACs only `request.to_signable_string` (the raw body) [1](#0-0)  against `Context.api_secret_key` [2](#0-1) . The `shop-domain` header, exposed to handlers as `WebhookMetadata#shop`, is never part of the signed content [3](#0-2) , so an attacker who possesses any valid `(raw_body, hmac)` pair signed with the app's shared secret can replay it with an arbitrary forged `shop-domain` header and still pass `Registry.process`'s HMAC check [4](#0-3) .

### Finding Description
Binding claimed: `shop authenticated by the HMAC` should equal `shop passed to the handler as WebhookMetadata#shop`. Tracing the code shows this binding is false by construction:

- `Registry.process` computes validity with `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature = HMAC-SHA256(secret, verifiable_query.to_signable_string)` [2](#0-1) .
- `Request#to_signable_string` returns only `@raw_body`; it never incorporates `shop`, `topic`, `webhook_id`, or `api_version` [1](#0-0) .
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed content [3](#0-2) .
- After successful HMAC validation, `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and hands it to the registered handler [4](#0-3) .

Attacker flow: attacker creates their own development shop, installs the target app, and legitimately receives a real Shopify webhook for their own shop — a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's `api_secret_key`. The attacker then sends their own HTTP POST directly to the app's public webhook endpoint, reusing that same `raw_body` and `hmac` header verbatim, but replacing `x-shopify-shop-domain` with `victim.myshopify.com`. Because `to_signable_string` never includes the shop header, `HmacValidator.validate` still succeeds, and `WebhookMetadata#shop` will be `"victim.myshopify.com"` even though the signature never covered that value.

None of the documented guards catch this: `Registry.process` only calls `HmacValidator.validate`; there is no `ShopValidator.sanitize!`, no comparison against a registered/expected shop, and no re-derivation of shop from signed data anywhere in `lib/shopify_api/webhooks/`. The gem's own documentation describes `Registry.process` as verifying "the request did indeed come from Shopify" and describes `data.shop` as "The shop domain of the webhook," which is a reasonable and foreseeable basis for a host handler to trust `data.shop` for session lookup, exactly as this question's threat model assumes.

The impact chain beyond this point (a host handler looking up a stored session keyed by `metadata.shop` and calling `Clients::Graphql::Admin` with it) is host-application code, not code inside this gem — `Registry.register`/`unregister` do use `Clients::Graphql::Admin.new(session:)` at lines 67 and 126, but that is for the app's own registration calls using a session the app already holds; `Registry.process` itself never looks up a session or calls the Admin API. The gem-internal, demonstrable defect is strictly that the unauthenticated `shop` value is handed to the handler as if it came from a verified source.

### Impact Explanation
What's exposed: a value (`WebhookMetadata#shop`) that the gem's own docs and API surface present as trustworthy/verified, but which is not covered by the cryptographic check that gives `Registry.process` its "verified" guarantee. Any host app that uses this field to key session/data lookups — a natural pattern encouraged by the field's name and documentation — is vulnerable to shop confusion. If a host app then uses that field to select a merchant's stored access token and issue Admin API calls (as speculated by the question, but outside this gem's code), the result would be cross-tenant mutation. This is repeatable against arbitrary victim shop domains at will, since spoofing is just a header substitution once a valid `(body, hmac)` pair is obtained on the attacker's own shop. Within the gem's own boundary, the concrete, demonstrable defect is an authentication-binding failure (unauthenticated `shop` trusted as authenticated) rather than a full, in-gem token exfiltration or Admin mutation — the final admin-API step requires host-app code not present in this repository.

### Likelihood Explanation
Preconditions are modest and attacker-cost is low: create/own a development shop, install the target app (any app using this gem to process webhooks), passively receive one legitimately-signed webhook, and replay it with a different header to the app's public webhook endpoint. No secrets, no privileged access, and no interaction with the victim shop are required. This is fully reachable by an unprivileged internet actor as described in the rules.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the authenticated material, or otherwise cross-verify it, before trusting `Request#shop`/`WebhookMetadata#shop`:
- Include `shop`, `topic`, and `webhook_id` header values in `to_signable_string` (or compute/verify a secondary MAC over them), so `HmacValidator.validate` fails if any of these are altered independently of the body.
- Alternatively, document/enforce that host apps must never use `WebhookMetadata#shop` alone to select credentials for outbound Admin API calls without an out-of-band cross-check (e.g., confirming the shop against the topic/body content or a registered webhook ID for that shop), and update `docs/usage/webhooks.md` to explicitly warn that `shop` is not covered by the HMAC signature.

### Proof of Concept
Minitest plan (extends `test/webhooks/registry_test.rb`), no live shop, no WebMock needed since `Registry.process` performs no outbound HTTP call itself:
```ruby
def test_forged_shop_domain_passes_hmac_validation
  # Attacker's own legitimately-signed webhook for their own shop
  attacker_body = "{}"
  valid_hmac = OpenSSL::HMAC.digest(
    OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, attacker_body
  )

  forged_headers = {
    "x-shopify-topic" => @topic,
    "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # unchanged, still valid for this body
    "x-shopify-shop-domain" => "victim.myshopify.com",      # forged, attacker never owned/received this
    "x-shopify-webhook-id" => "forged-id",
    "x-shopify-api-version" => "2024-01",
  }

  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: attacker_body, headers: forged_headers)

  # Binding check BEFORE: HMAC only covers raw_body, not shop
  assert_equal(attacker_body, forged_request.to_signable_string)

  received_shop = nil
  handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| received_shop = data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(topic: @topic, path: "path", delivery_method: :http, handler: handler)

  # No exception: HMAC validation succeeds despite the forged shop
  ShopifyAPI::Webhooks::Registry.process(forged_request)

  # Binding check AFTER: shop delivered to handler is the unauthenticated, forged value
  assert_equal("victim.myshopify.com", received_shop)
end
```
This demonstrates that `Registry.process` accepts a request whose `hmac` was never computed over `"victim.myshopify.com"`, yet delivers that shop value to the handler as if verified.
