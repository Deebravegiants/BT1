### Title
Unbounded per-batch `GetRequest.keys` iteration in `handle_get_requests` / GET-response handlers enables gas-exhaustion griefing of bundled requests - ([File: modules/pallets/state-coprocessor/src/impls.rs], [File: modules/ismp/core/src/handlers/response.rs])

### Summary
`GetRequest.keys` is an attacker-controlled, unbounded `Vec<Vec<u8>>` set at dispatch time on the source chain, with no on-chain limit on the number of keys. When Hyperbridge (or a destination chain) processes a batch of GET requests/responses, it iterates once per key per request inside a single call that also processes *other, unrelated* requests submitted by other users in the same batch.

### Finding Description
`GetRequest` is created by `EvmHost.dispatch(DispatchGet)` with `keys: get.keys` copied verbatim from caller input [1](#0-0) , and no size limit exists in the interface/struct or the dispatch path. Similarly on the Substrate side, `DispatchGet{ keys: params.keys, .. }` is forwarded unchecked into the dispatcher [2](#0-1) .

`pallet_state_coprocessor::handle_get_requests` accepts a **batch** (`GetRequestsWithProof { requests: Vec<GetRequest>, .. }`) and, after the batch-level duplicate/timeout/height checks, loops over every request in the batch and calls `verify_state_proof(&host, req.keys.clone(), ...)` for each one [3](#0-2) . `verify_state_proof`/`get_values_from_proof` internally iterates once per key, doing a full trie lookup per key [4](#0-3) . There is no cap on `req.keys.len()` anywhere in this path — I searched for `MAX_KEYS`/`max_keys`/similar bounds and found none.

The same batching pattern exists in the core response handler, `handlers/response.rs::handle`, which iterates `msg.requests` (a `Vec<GetRequest>` supplied by the relayer) and, for each, calls `state_machine.verify_state_proof(host, keys, ...)` [5](#0-4) .

Because a single dispatcher-controlled `GetRequest` can carry an arbitrarily large `keys` array, and because the batch-processing entry points (`handle_get_requests`, `handlers/response.rs::handle`) process *all* requests in one atomic call/extrinsic, one attacker-crafted request with a pathologically large `keys` array can dominate the gas/weight cost of the entire batch. If a relayer (or the coprocessor auto-batching logic) bundles this request together with legitimate, unrelated GET requests from other users to amortize proof/consensus overhead, the whole call can run out of gas/weight and revert, denying delivery for every other request in that same batch — a classic "unbounded loop consumes shared budget" pattern, directly analogous to the reported Carapace `DefaultStateManager` issue where one array iterated in service of many unrelated callers is unboundedly grown by an attacker.

### Impact Explanation
This is a griefing/DoS vector against message delivery, not a fund-theft primitive, but it satisfies the "route unable to deliver messages" acceptance criterion: an attacker can force reversion of `handle_get_requests`/GET-response batches that legitimately include other users' pending GET requests, delaying or indefinitely blocking their delivery (until relayers learn to isolate/exclude the malicious request, which requires off-chain heuristics not present in the reachable on-chain code). Because there is no bound on `keys.len()`, the attack scales with an attacker's own dispatch cost (cheap on the source side) versus disproportionate verification cost paid by whoever must process the batch.

### Likelihood Explanation
Medium likelihood: dispatching a `GetRequest` with thousands of keys costs the attacker only calldata/storage for the dispatch itself (bounded by the source chain's own block gas limit for that one dispatch), which is far cheaper than the downstream verification cost multiplied across a batch. No permission is required to dispatch a GET request — this is fully reachable from an unprivileged submitted transaction. The severity is bounded by relayer batching behavior (a relayer could choose to submit this request alone), which is why this is Medium rather than High/Critical.

### Recommendation
- Enforce a maximum number of keys per `GetRequest` (and/or a maximum total key-bytes) at dispatch time on both the EVM (`EvmHost.dispatch(DispatchGet)`) and Substrate (`dispatch_request`) paths.
- In `handle_get_requests` and `handlers/response.rs::handle`, reject or isolate any single request whose `keys.len()` (or aggregate proof-verification cost) exceeds a configured bound, rather than allowing it to consume the shared batch budget.
- Consider charging/weighing GET requests proportionally to `keys.len()` in the bandwidth gate/fee model so oversized requests are economically deterred before they reach batch processing.

### Proof of Concept
1. Attacker calls `EvmHost.dispatch(DispatchGet)` (or the Substrate `get_request` extrinsic) with `keys` containing e.g. 5,000–50,000 storage-key entries; no on-chain check rejects this at `evm/src/core/EvmHost.sol:974-1013` or `modules/pallets/demo/src/lib.rs:185-215`.
2. This GET request enters the pending set alongside independently-dispatched, legitimate GET requests from other users.
3. A relayer or the coprocessor batches multiple pending GET requests into one `GetRequestsWithProof`/`ResponseMessage` call for efficiency.
4. `handle_get_requests` (or `handlers/response.rs::handle`) processes the batch; the attacker's request forces `verify_state_proof`/`get_values_from_proof` to loop over all 5,000+ keys, inflating the call's gas/weight far beyond what the other bundled requests would need.
5. If the resulting weight/gas exceeds the block/extrinsic limit, the entire batch reverts, and the legitimate requests bundled with the attacker's fail to be delivered in that attempt.

```rust
pub fn get_values_from_proof<H: Keccak256 + Send + Sync>(
	keys: Vec<Vec<u8>>,
	root: H256,
	proof: Vec<Vec<u8>>,
) -> Result<Vec<Option<DBValue>>, Error> {
	let mut values = vec![];
	let proof_db = StorageProof::new(proof).into_memory_db::<KeccakHasher<H>>();
	let trie = TrieDBBuilder::<EIP1186Layout<KeccakHasher<H>>>::new(&proof_db, &root).build();
	for key in keys {
		let val = trie
			.get(&key)
			.map_err(|e| EvmStateMachineError::TrieReadError(format!("{e:?}")))?;
		values.push(val);
	}

	Ok(values)
}
```
