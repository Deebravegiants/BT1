### Title
Optional/omittable slippage checks in `Withdraw` allow LP withdrawals to be sandwiched for value extraction - (File: `program/src/processor.rs`)

### Summary
Unlike `SwapBaseIn`/`SwapBaseOut`, whose slippage bounds (`minimum_amount_out`, `max_amount_in`) are mandatory `u64` fields that are always checked, the `Withdraw` instruction's slippage protection (`min_coin_amount`, `min_pc_amount`) is defined as `Option<u64>` and is only enforced when **both** values are supplied. If a withdrawing user (or an integrating wallet/client) omits them — which the instruction encoding explicitly allows — the program computes and pays out `coin_amount`/`pc_amount` from whatever the pool's vault ratio happens to be at execution time, with no floor at all, exactly mirroring the "100% slippage tolerance" pattern described in the referenced report.

### Finding Description
`WithdrawInstruction` carries optional minimums: [1](#0-0) 

The unpacker only populates `min_coin_amount`/`min_pc_amount` when 16 extra bytes are present in the instruction data, otherwise both remain `None`: [2](#0-1) 

In `Processor::process_withdraw`, `coin_amount` and `pc_amount` are derived purely from the pool's current vault balances (`total_coin_without_take_pnl`, `total_pc_without_take_pnl`) and the LP share being redeemed, and the slippage guard is a no-op unless both optional fields are `Some`: [3](#0-2) 

Because the check is conditioned on `withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()`, a caller can trivially bypass all slippage protection simply by not appending the optional bytes to the instruction data (a single, ordinary, unprivileged transaction) — there is no forced minimum-output floor as there is for the swap instructions. This directly matches the report's root cause: a Uniswap-style interaction where a caller-facing "slippage" field exists but is effectively unset/zero, allowing the accompanying pool interaction to execute at any resulting price.

### Impact Explanation
An attacker can sandwich a `Withdraw` call that lacks slippage bounds: front-run with a swap that skews the coin/pc vault ratio, let the victim's withdrawal execute and receive tokens proportioned to the skewed ratio, then back-run to restore/complete the price move and capture the value shifted away from the withdrawing LP. Because `coin_amount`/`pc_amount` come straight from the manipulated vault ratio with no floor enforced, the LP can receive a materially unfavorable split of their redeemed value — a direct, unauthorized value transfer from an LP to an MEV searcher, consistent with the Medium severity assigned to the analogous Uniswap finding.

### Likelihood Explanation
Likelihood is real but conditional on client behavior: any user or integrator building a `Withdraw` transaction without appending both `min_coin_amount` and `min_pc_amount` (which the instruction format explicitly supports as optional) exposes themselves to this at every withdrawal, on any pool with sufficient onchain liquidity/MEV searcher attention — no special privileges, validator collusion, or non-default build is required, only ordinary composability of a swap + withdraw + swap in adjacent transactions/same block.

### Recommendation
Make `min_coin_amount`/`min_pc_amount` mandatory (non-`Option`) fields for `Withdraw`, matching the unconditional enforcement pattern already used for `SwapBaseIn`/`SwapBaseOut`, so slippage protection cannot be silently disabled by omitting instruction bytes.

### Proof of Concept
1. Attacker observes a pending `Withdraw` instruction whose data omits the optional `min_coin_amount`/`min_pc_amount` fields (16 bytes shorter payload, per `AmmInstruction::unpack` tag `4` handling).
2. Attacker front-runs with a `SwapBaseIn`/`SwapBaseOut` that shifts `amm_coin_vault`/`amm_pc_vault` balances, skewing `total_coin_without_take_pnl` vs `total_pc_without_take_pnl`.
3. The victim's `Withdraw` executes; `process_withdraw` computes `coin_amount`/`pc_amount` from the now-skewed ratio and, since `min_coin_amount.is_some() && min_pc_amount.is_some()` is `false`, performs the transfer/burn without any floor check.
4. Attacker back-runs to close out their swap position, capturing the value differential extracted from the victim's withdrawal.
