Audit Report

## Title
Unprivileged auction win against a para with a pending `AssignedSlots` temporary slot causes `allocate_temporary_slot_leases` to abort its entire batch via early-return `?`, denying other paras their scheduled temp-slot turn - (File: `polkadot/runtime/common/src/assigned_slots/mod.rs`)

## Summary
`assign_temp_parachain_slot` only checks `T::Leaser::already_leased` for a bounded near-term window (current period plus `2 * TemporarySlotLeasePeriodLength`), and never re-verifies this later. `allocate_temporary_slot_leases` iterates `slots_to_be_upgraded` and calls `TemporarySlots::<T>::try_mutate(...)?` inside the loop, where the `?` propagates any `Error::<T>::CannotUpgrade` (from a `LeaseError::AlreadyLeased` returned by `T::Leaser::lease_out`) out of the entire function, aborting processing of all subsequent paras in that batch and skipping the `ActiveTemporarySlotCount::<T>::set(...)` update.

## Finding Description
The code matches the claim precisely. `assign_temp_parachain_slot`'s `already_leased` guard only covers current + next 2 temp-slot periods: [1](#0-0) . This leaves recurring future turns (`last_lease + 2*period_count`) or delayed `SlotLeasePeriodStart::Next` assignments unchecked at assignment time.

`Auctions::bid` only requires `ensure_signed` [2](#0-1) , and `handle_bid` only rejects bids overlapping an *existing* `slots::Leases` entry [3](#0-2) . Since `AssignedSlots` doesn't pre-create `slots::Leases` entries for future recurring turns, nothing stops a third party from winning an auction for that future period range on the same para.

When the conflicting period arrives, `allocate_temporary_slot_leases` iterates the sorted, capped `slots_to_be_upgraded` list and, for each entry, calls `TemporarySlots::<T>::try_mutate(...)?`, where the closure calls `configure_slot_lease` → `T::Leaser::lease_out`, mapping any lease error to `Error::<T>::CannotUpgrade`: [4](#0-3) . The trailing `?` after `try_mutate(...)` at line 560 does indeed propagate the error out of the `for` loop and out of the function immediately — confirmed by direct reading of the code — bypassing all subsequent entries in `slots_to_be_upgraded` and never reaching `ActiveTemporarySlotCount::<T>::set(active_temp_slots + newly_created_lease)` at line 564: [5](#0-4) . `try_mutate` leaves the storage entry unchanged on `Err`, so the para in conflict is not advanced and remains "pending" for future retries, consistent with the claim.

I was unable to fully trace the caller of `allocate_temporary_slot_leases` (i.e. `manage_lease_period_start` in `polkadot/runtime/common/src/assigned_slots/mod.rs`, referenced by the report as invoked from `on_initialize`) to independently confirm that its caller "only logs the error... and does not retry the remaining entries" — the surrounding `on_initialize`/`manage_lease_period_start` code was not retrieved in full due to tool budget exhaustion. However, this does not change the core finding: regardless of what the top-level caller does with the propagated error, the batch-abort itself (skipping unrelated pending paras and the `ActiveTemporarySlotCount` update within the same call) is real and independent of caller behavior.

## Impact Explanation
This is a legitimate logic bug: a single `Err` from one para's lease configuration aborts processing of all other pending paras queued in the same `allocate_temporary_slot_leases` invocation, and `ActiveTemporarySlotCount` is not updated to reflect leases that were successfully created before the failing iteration. This causes denial-of-service of the temporary-slot allocation mechanism for uninvolved paras in the same batch, and can leave `ActiveTemporarySlotCount` inconsistent with actual active leases. This is an in-scope, concrete logic/accounting flaw in `AssignedSlots`, matching a genuine batch-isolation bug rather than a purely theoretical issue.

## Likelihood Explanation
Triggering requires only a signed `Auctions::bid` (or crowdloan contribution) for a specific `ParaId` and lease-period range — no special privilege, matching an in-scope unprivileged attacker path. The attacker needs to know the target para's `period_begin`/`TemporarySlotLeasePeriodLength`, which are public storage, and to win/overbid the auction for the exact conflicting range, which requires committing/reserving funds but no protocol-level permission. It is repeatable since a failed `try_mutate` leaves the conflicting para's slot unchanged, so it stays eligible for future pending rounds and can be re-blocked.

## Recommendation
- In `allocate_temporary_slot_leases`, isolate per-iteration failures (e.g., `let _ = TemporarySlots::<T>::try_mutate(...)` with a `log::warn!` on error) instead of propagating with `?`, so one para's failure does not prevent processing the rest of `slots_to_be_upgraded`.
- Ensure `ActiveTemporarySlotCount` is updated based on leases actually created regardless of individual failures.
- Consider widening the `already_leased` check window in `assign_temp_parachain_slot`, or otherwise reserving/blocking future recurring temp-slot periods against conflicting auction bids for paras holding an `AssignedSlots` entry.

## Proof of Concept
1. Register two parathreads `para_a` and `para_b`; call `AssignedSlots::assign_temp_parachain_slot(Root, para_a, SlotLeasePeriodStart::Next)` and the same for `para_b`, giving both `TemporarySlots` entries with `last_lease: None`.
2. Before the next lease-period boundary, start `Auctions::new_auction` and have a signed non-privileged account call `Auctions::bid` (or fund via `Crowdloan`) for `para_a`'s scheduled `period_begin..period_begin+period_count-1` range; let the auction conclude so `slots::Leases` for `para_a` is populated for that range.
3. Advance to the lease-period boundary that triggers `allocate_temporary_slot_leases(lease_period_index)`.
4. Assert `TemporarySlots::<Test>::get(para_a).last_lease` is still `None` (conflict, unchanged by failed `try_mutate`), and critically that `TemporarySlots::<Test>::get(para_b).last_lease` is also still `None` despite no conflict for `para_b`, demonstrating the batch-abort. Also assert `ActiveTemporarySlotCount::<Test>::get()` was not updated for this period.
