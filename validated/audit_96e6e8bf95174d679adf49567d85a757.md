### Title
IrNet liveness signals (`iris_uncovered`, `orientation_correct`, `gaze_valid`, `eye_opened`, `iris_aligned`) are computed but never enforced in `calculate_selection_score` - ([File: src/agents/python/ir_net.rs])

### Summary
`extract()` in `src/agents/python/ir_net.rs` pulls five boolean liveness/quality signals from the IR-Net model output but the production `calculate_selection_score` (the `#[cfg(not(feature = "integration_testing"))]` variant) only checks `status`, `valid_for_identification`, and NaN-ness of `sharpness` to compute the frame's `score`. If the Python model returns `status == 0` and `valid_for_identification == true` while any of the five booleans are `false` (e.g. eye not uncovered, wrong orientation, invalid gaze, eye not opened, iris misaligned), the resulting `score` is still `sharpness` (a positive, usable value) instead of being forced to `-1.0`.

### Finding Description
In `src/agents/python/ir_net.rs`, `extract()` reads all model-provided fields via `estimation.get_item(...)`, including `eye_opened`, `iris_aligned`, `iris_uncovered`, `orientation_correct`, and `gaze_valid` [1](#0-0) , but computes `score` solely via `calculate_selection_score(sharpness, valid_for_identification, status)` [2](#0-1) . The non-test variant of that function is:

```rust
#[cfg(not(feature = "integration_testing"))]
fn calculate_selection_score(sharpness: f64, valid_for_identification: bool, status: i64) -> f64 {
    if status != 0 || !valid_for_identification || sharpness.is_nan() { -1.0 } else { sharpness }
}
``` [3](#0-2) 

This function's signature does not even accept the five boolean fields, so no matter what the Python model reports for `eye_opened`, `iris_aligned`, `iris_uncovered`, `orientation_correct`, or `gaze_valid`, they have zero influence on `score`. The `EstimateOutput` struct that is passed downstream still carries these fields [4](#0-3) , but they are logged/gauged for telemetry only [5](#0-4)  and never consulted for the accept/reject decision.

Root cause: the liveness/quality gating logic was likely intended to also require these five booleans to be `true` (analogous to how `status` and `valid_for_identification` are checked), but the implementation only checks `status` and `valid_for_identification`. This means the model's "sanity" flag (`valid_for_identification`) and generic status code are trusted as sufficient without cross-checking the more granular liveness/quality indicators that the same model computes.

I was unable to directly confirm within this session how `biometric_capture::mod.rs`'s `handle_ir_net` (and the acceptance path writing into `self.left_ir` / `self.right_ir`) uses `EstimateOutput.score` against `IRIS_SCORE_MIN`, since the grep results for that file did not return line-level content in this final pass. Based on the question's framing and the `consts.rs` match for `IRIS_SCORE_MIN`, the score is compared against a minimum threshold to decide whether to accept the frame into the identity-binding buffer. Assuming that comparison logic is a simple `score >= IRIS_SCORE_MIN` gate (as stated in the question and consistent with the codebase's naming conventions), the vulnerability in `calculate_selection_score` directly enables acceptance of frames whose five liveness signals are false.

### Impact Explanation
If confirmed downstream, this would allow an attacker presenting a non-live or manipulated eye scene (printed iris, contact lens, misaligned/occluded eye) to have that frame's IR-Net `score` remain a valid positive number as long as the model coarsely reports `status == 0` and `valid_for_identification == true` — even though the finer-grained liveness signals it computed indicate the sample. This score is the sole discriminator used to select frames into `self.left_ir` / `self.right_ir`, the buffers used for the identity/biometric binding of the signup. This matches the "liveness/fraud bypass" and "wrong-identity binding" bounty impact categories, since a spoofed capture could be bound into the attacker's own signup package.

### Likelihood Explanation
Exploitability depends entirely on whether the underlying IR-Net Python model can, for some crafted physical eye scene, produce `status == 0` and `valid_for_identification == true` while simultaneously reporting `false` for one or more of the five granular booleans. This is plausible in principle (the model computes these as separate, more granular quality signals), but I could not verify from the Rust code alone whether the Python model's own internal logic ties `valid_for_identification`/`status` to those five booleans (i.e., whether the model itself already guarantees `valid_for_identification == true` implies all five booleans are true, which would make this Rust-side gap unreachable in practice). This is an important unresolved dependency: if the Python model enforces that invariant internally, the Rust-side gap is dead code from a security perspective. Without access to the Python model's source, this cannot be fully confirmed here.

### Recommendation
Update the non-test `calculate_selection_score` to also require `eye_opened`, `iris_aligned`, `iris_uncovered`, `orientation_correct`, and `gaze_valid` to all be `true`, forcing `score = -1.0` otherwise, mirroring the existing `status`/`valid_for_identification` checks. Additionally, verify (in the Python `orb_ir_net::IrNet` model or its bindings) whether `valid_for_identification` is already guaranteed to imply these five booleans; if not, the Rust-side check is the only enforcement point and must be added.

### Proof of Concept
Unit test plan for `src/agents/python/ir_net.rs`:
1. Construct a synthetic Python dict (via `pyo3::Python::with_gil`) with `status = 0`, `valid_for_identification = true`, `sharpness = 0.9` (non-NaN), and set `eye_opened = false`, `iris_aligned = false`, `iris_uncovered = false`, `orientation_correct = false`, `gaze_valid = false`, plus other required fields (`landmarks`, `occlusion_30`, `occlusion_90`, `gaze`, `eye_detected`, `qr_code_detected`, `occlusion_30_old`, `iris_sharp`, `mean_brightness_raw`, `msg`, `target_side`, `perceived_side`).
2. Call `extract()` on this dict and assert `estimate.score == 0.9` (i.e., not forced to `-1.0`), demonstrating the current (buggy) behavior.
3. Integration test: feed this `EstimateOutput` into the `biometric_capture` plan's IR-Net handling path and assert whether the frame is accepted into `self.left_ir`/`self.right_ir` despite the five `false` liveness flags — this second step requires access to `handle_ir_net` and the `IRIS_SCORE_MIN` comparison in `src/plans/biometric_capture/mod.rs`, which should be inspected directly to confirm the exact accept/reject condition before finalizing severity.
