## Analysis

I traced the reported bug class ("field acted on but not covered by the HMAC" / "bytes verified versus bytes parsed") to the webhook processing path in this gem.

### Title
Webhook shop/topic identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching to a handler with a trusted `shop` field. In reality, the HMAC only authenticates the raw request body bytes; the `shop`, `topic`, `webhook_id`, and `api_version` values — all read from unauthenticated HTTP headers — are never bound to that signature, so an attacker can replay a legitimately-signed body under a forged shop domain.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from the HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body) using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` performs this check and then immediately trusts `request.shop`/`request.topic` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. Because the signature covers only body bytes, this equality does not hold — `shop` (and `topic`) are parsed but never verified.

The gem's own documentation reinforces the false sense of security: it states `process` "will verify the request did indeed come from Shopify," and describes `data.shop` simply as "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

Since the `api_secret_key` is a single shared secret for the whole app (not per-shop), any shop that can receive a legitimately-signed webhook from Shopify (e.g., a merchant who has installed the attacker's own copy of the app, or any external actor able to capture one delivery) can replay that exact `raw_body` + `hmac-sha256` header pair while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header value. `HmacValidator.validate` will still pass because it only re-derives the HMAC from the body bytes and the shared secret — it never checks the header values it did not sign.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: a request that is validly signed for one shop can be dispatched to a handler as if it belongs to a different, victim shop. Any app that follows the documented pattern (using `data.shop` to key shop-scoped side effects such as cache updates, billing triggers, GDPR/compliance actions, or database writes) can be made to attribute attacker-controlled webhook bodies to a victim shop it never authorized — a cross-tenant confusion crossing the gem's own trust boundary of "HMAC-verified == belongs to this shop."

### Likelihood Explanation
Exploitation requires only the ability to trigger or observe one legitimately HMAC-signed webhook delivery for any shop using the same app (trivially achievable by installing the target app on an attacker-controlled store, or intercepting one's own webhook traffic) plus the ability to POST to the app's webhook endpoint with custom headers — both of which are available to an unprivileged internet user with no access token, `api_secret_key`, or privileged account required.

### Recommendation
Bind the shop/topic identity to the signed payload before trusting it: either include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (`to_signable_string`), or require callers to independently confirm that the delivered `shop` corresponds to a session/shop domain the app knows to have this webhook actively registered, and document this requirement prominently rather than describing `process` as a full authenticity check for `data.shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `products/update`) by editing a product, capturing the raw POST body and the legitimate `X-Shopify-Hmac-Sha256` header Shopify computed with the app's `api_secret_key`.
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged shop domain: `lib/shopify_api/webhooks/request.rb` lines 21-23.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the shared secret: `lib/shopify_api/webhooks/registry.rb` line 190.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs shop-scoped actions attributing attacker content to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
