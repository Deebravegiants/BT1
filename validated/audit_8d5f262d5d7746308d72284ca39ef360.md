### Title
Supply-index floor clamp resurrects wiped supplier shares after total bad-debt socialization, letting stranded claims drain fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary
`apply_bad_debt_to_supply_index` socializes bad debt by scaling the supply index down pro-rata, but clamps the result *up* to `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`). When bad debt meets or exceeds total supplied value, every supplier's scaled shares — which should be worthless — regain a claim valued at the floored index. An unprivileged user can trigger this via `clean_bad_debt`/`seize_positions` on the borrow side, then withdraw the resurrected claim against any future deposit, stealing real tokens. The repo's own unit tests (`test_raw_cache_floor_clamp_strands_claim_without_supply_guard`, `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard`, `test_apply_bad_debt_exactly_at_total_supplied_hits_cap_and_floor`) demonstrate the drain at cache level.

### Finding Description
The analog of CVE-2017-2466 (crafted input corrupts internal state to gain unintended control) maps onto XOXNO Lending's share-accounting layer: a crafted/unprivileged bad-debt cleanup corrupts the supply-index state so that burned-value shares still pay out.

In `contracts/pool/src/interest.rs:73-89`:

```rust
let capped = bad_debt.min(total_supplied_value);
let remaining = total_supplied_value.checked_sub(cache.env(), capped);
let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
let new_supply_index = cache.supply_index().mul_floor(cache.env(), reduction_factor);
cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

When `bad_debt >= total_supplied_value`, `remaining = 0`, `reduction_factor = 0`, `new_supply_index = 0`, and the `.max(SUPPLY_INDEX_FLOOR_RAW)` resets the index to `RAY/1000` instead of leaving it at zero. All existing scaled supply shares retain `scaled * RAY/1000` asset-units of claim — a phantom residual that is *not* backed by anything.

The borrow-side seize path in `contracts/pool/src/ops/seize.rs:24-28` reaches this directly: `unscale_borrow_ceil_ray(position)` → `apply_bad_debt_to_supply_index` → `burn_debt`. The controller's permissionless `clean_bad_debt` and liquidation paths submit `PoolSeizeEntry` records, so any unprivileged address can invoke it.

Withdrawal then unscales via `unscale_supply`/`resolve_withdrawal` (`contracts/pool/src/cache/scale.rs:50-57, 97-105`), and the only solvency check is `require_reserves(gross)` — that the *cash* covers this payout — not that remaining claims stay backed. The phantom claim therefore withdraws real cash belonging to later depositors, exactly as the tests assert: `userA drains exactly userB's fresh deposit out of the pool` and `cash {} cannot cover Bob's honest claim`.

### Impact Explanation
Theft of user funds / protocol insolvency. After a wipeout cleanup, every holder of pre-wipeout scaled shares (including the attacker, who can be both the defaulting borrower and a supplier) keeps a residual claim. The first fresh deposit into the market can be fully extracted by the stranded claimant via `withdraw`. The market is left insolvent: `unscale_supply_floor(supplied) > cash` immediately after the drain, so honest suppliers' claims become unpayable — permanent loss for them.

### Likelihood Explanation
Fully reachable by a single unprivileged address:

- `clean_bad_debt` and liquidation-driven `seize_positions` are permissionless entrypoints.
- Bad debt ≥ total supplied value is attainable: an attacker supplies the market, borrows up to the utilization cap, and lets borrow interest accrue (borrow index grows faster than supply index) until unscale debt value meets/exceeds the supplied claim; or collateral devalues normally leaving unpaid debt that clean-up socializes. Attacker-controlled supply means the wipeout is self-inflicted and cheap relative to the payoff.
- After the clamp, the attacker's wiped shares hold `~0.1% × pre-wipeout value` of claim. They wait for (or sandwich) any subsequent `supply` into that market — or self-fund a minimal deposit to activate the market — then call `withdraw` to take the cash.
- No oracle manipulation, privileged call, or off-chain component is required; the corruption is purely internal arithmetic policy.

One caveat: the floor is documented (`contracts/pool/README.md` notes the index is "floored at `SUPPLY_INDEX_FLOOR_RAW`"), but the documented intent is only "avoid a zero index" — the resulting stranded-claim drain of unrelated depositors' funds is an unintended consequence, confirmed by the dedicated drain tests in `contracts/pool/tests/interest.rs:317-494`.

### Recommendation
When `bad_debt >= total_supplied_value`, treat the market as wiped rather than flooring the index: either set the supply index such that residual claims are zero (e.g., also zero/burn tracked supplied shares, or mark the market drained and block withdrawals until `recapitalize`), or keep an explicit `wiped` flag that `resolve_withdrawal`/`withdraw` checks and rejects stranded claims against. Alternatively, gate withdrawals on the post-withdrawal backing invariant (`supplied_claim_floor <= cash + outstanding_debt_ceil`) so phantom residuals can never be paid out ahead of solvency. Size `SUPPLY_INDEX_FLOOR_RAW` only for *partial* reductions; never clamp up past a full wipeout.

### Proof of Concept
The repository already contains the exploit trace. Adapted from `contracts/pool/tests/interest.rs:316-428`:

```rust
// Market state: attacker holds 1_000_000 * RAY scaled supply, index = RAY.
// Borrow-side seize with bad_debt >= total supplied value.
apply_bad_debt_to_supply_index(&mut cache, Ray::from(2_000_000 * RAY));
// supply_index clamps UP to SUPPLY_INDEX_FLOOR_RAW, not to 0.
assert_eq!(cache.supply_index().raw(), SUPPLY_INDEX_FLOOR_RAW);

// Attacker's "wiped" shares retain a real claim:
let stranded = cache.unscale_supply_floor(attacker_scaled); // > 0

// Victim deposits `stranded` tokens; honest claim equals deposit.
let victim_scaled = cache.calculate_scaled_supply(stranded);
cache.mint_supply(victim_scaled);
cache.credit_cash(stranded);

// Attacker withdraws the stranded claim:
let (burn, gross) = cache.resolve_withdrawal(i128::MAX, attacker_scaled);
cache.require_reserves(gross);   // passes — cash covers this leg
cache.burn_supply(burn);
cache.debit_cash(gross);
// gross == victim's deposit; cache.cash() == 0 < victim's claim.
```

End-to-end path: attacker supplies+borrows in one market, lets unpaid debt reach the supplied-value cap, calls `clean_bad_debt` (permissionless) → pool `seize` writes the index down to the floor → a later (or attacker's own follow-on) `supply` credits cash → attacker's `withdraw` of the residual scaled shares removes that cash.
