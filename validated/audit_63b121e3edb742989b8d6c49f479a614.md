## Analysis

The reported bug class — a time-based accrual/decay mechanism that keeps running on wall-clock time even when the protocol path needed to *use* that accrual is unavailable — has a concrete analog in Hyperbridge's prepaid bandwidth subscription system.

### Title
Bandwidth subscriptions expire on a fixed wall-clock timer that keeps running while message delivery is blocked (host/consensus-client frozen), causing users to pay for unusable bandwidth - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` credits `(app_chain, app)` byte allowances with an `expires_at` fixed at purchase time and computed purely from `TimestampProvider::now() + duration_secs`, with no dependency on whether the app was actually able to consume any of that allowance. [1](#0-0)  Delivery of ISMP messages, however, can be halted for extended periods by mechanisms entirely outside the app's control: a consensus client freeze (`freeze_client`) blocks all subsequent request/response processing for that state machine indefinitely (frozen clients "cannot be unfrozen"), and an EVM host can be administratively frozen via `setFrozenState`, blocking `handlePostRequests`/`handleGetResponses`/timeouts. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
A subscription's `expires_at` is fixed once at purchase and "never extends" — the pallet's own docs state: "what you paid for is yours only until it expires," and the test suite explicitly documents this as intended even for byte allowances that are simply never reached: `unused_subscription_expires_independently` proves that a fully unused subscription is silently swept once its independent clock elapses. [5](#0-4) 

This "use it or lose it on a fixed clock" design assumes the app always has the *opportunity* to consume its allowance during the purchased window. That assumption breaks when the delivery path itself is unavailable for a duration comparable to (or longer than) the subscription window:
- If the consensus client servicing the app's source chain is frozen via a fraud proof (`freeze_client`), `validate_state_machine` will reject every subsequent request/response for that state machine with `FrozenConsensusClient` until governance creates a brand-new client — there is no unfreeze path. [6](#0-5) [7](#0-6) 
- Likewise, `EvmHost.setFrozenState(FrozenStatus.Incoming/All)` blocks `handlePostRequests`/`handleGetResponses` at the handler level. [3](#0-2) 

During any such freeze window, an app that already paid for bandwidth cannot get any of its POST requests delivered (the gate is never even reached because the message itself is rejected upstream), yet `Subscription.expires_at` keeps ticking against real time. [8](#0-7)  When the freeze is lifted, the gate sweeps the now-expired subscription on the next `try_consume` call, and the paid-for bytes are gone. [9](#0-8) 

This is structurally identical to the referenced Ajna/`ERC20Pool` bug: a time-driven charge/decay function (`_updateInterestState` there, `expires_at`-based sweep here) keeps advancing during a period when the protocol path is paused/frozen, so the user is charged (or loses paid-for value) for time they could not use — "users pay unnecessary money to protocol."

### Impact Explanation
Users/apps that pre-pay for a bandwidth tier lose the unused portion of their purchase (`remaining_bytes`) whenever a freeze (consensus-client freeze or host-level pause) spans into or past their subscription's `expires_at`. Since `duration_secs` for the smallest tier can be as short as 30 days and freezes are open-ended (frozen consensus clients require a full re-initialization, not a simple unfreeze), a moderate-length incident can cause outright loss of prepaid funds with no compensation or extension mechanism. This is a Medium-severity fund-loss/unfair-charge issue on the bandwidth-purchase surface reachable by any unprivileged app/relayer that purchased a subscription.

### Likelihood Explanation
This requires no attacker action beyond normal protocol operation — it triggers whenever a legitimate freeze/pause event (fraud-proof freeze or admin host freeze, both documented, expected recovery/incident mechanisms) overlaps a purchased subscription's window. Given that freezes are an intended safety mechanism of Hyperbridge (used specifically for incident response), and subscription windows are as short as 30 days, the overlap is a realistic, foreseeable operational scenario rather than an edge case.

### Recommendation
Track cumulative "frozen time" per relevant `(source chain, app)` pair (or per consensus-state-id / host) and extend `expires_at` for affected subscriptions by that duration when computing expiry in `allowances`/`remaining`/gate sweep logic, similar to the audit's own recommendation to "pause interest update when the protocol is paused." Alternatively, expose a governance-callable extension/refund path (analogous to `force_credit`) that compensates subscriptions whose window overlapped a documented freeze incident.

### Proof of Concept
1. App purchases `TierOne` bandwidth; pallet computes `expires_at = now + duration_secs` and stores the `Subscription`. [1](#0-0) 
2. A fisherman submits a valid fraud proof against the consensus client tracking the app's source chain; `freeze_client` sets `FrozenConsensusClients` for that client. [2](#0-1) 
3. For the remainder of the subscription window, every `RequestMessage`/`GetResponseMessage` for that state machine is rejected at `validate_state_machine` with `FrozenConsensusClient`, so the app cannot dispatch through the bandwidth gate at all. [10](#0-9) 
4. `now` passes `expires_at` while `remaining_bytes` is still fully unused.
5. Governance eventually re-initializes a new consensus client (frozen clients cannot be unfrozen), delivery resumes, but the next `try_consume` call sweeps the now-expired subscription — confirmed by the existing test pattern `unused_subscription_expires_independently`, which already demonstrates that an unreached subscription is swept purely on elapsed time with zero usage. [5](#0-4) 
6. The app has paid for bandwidth it never had the opportunity to use, with no refund or extension mechanism.

/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}

		// sub#0 is fat + long: drain stays inside it the whole test.

	});

The `freeze_client` method is used to prove the existence of a consensus fault to an onchain consensus client. This message will be sent by offchain parties, colloquially known as _fishermen_ when they detect the existence of two conflicting views of the network backed by consensus proofs. This may arise from double signing or eclipse attacks. The consensus client after successfully verifying the validity of the conflicting views of the network will go into a frozen state. In this state it can no longer process new consensus messages as well as new requests & responses. Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead.

/// One purchase, immutable across its lifetime: `remaining_bytes`
/// drains via the gate, `expires_at` is fixed at purchase time and
/// never extends. Repurchases append a new row instead of stacking.
#[derive(
	Encode, Decode, DecodeWithMemTracking, TypeInfo, MaxEncodedLen, Clone, PartialEq, Eq, Debug,
)]
pub struct Subscription {
	/// SKU this subscription was bought against; for analytics/events
	/// only — the gate doesn't look at it during drain.
	pub tier: TierIndex,
	/// Bytes left to spend. Decrements as the gate drains; the entry
	/// is popped once this hits zero.
	pub remaining_bytes: BandwidthBytes,
	/// Unix seconds. Gate sweeps entries where `expires_at <= now`.
	pub expires_at: u64,
	/// Unix seconds at insertion — fixes FIFO order under same-block buys.
	pub purchased_at: u64,
}
