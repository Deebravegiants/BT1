### Title
Malicious pool creator can freeze a specific LP's withdrawal by using a coin/pc mint with an uncontrolled freeze authority - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` validates the LP mint's `freeze_authority` but never validates the `freeze_authority` of the `coin_mint`/`pc_mint` that will actually be transferred on `Deposit`/`Withdraw`. A pool creator who controls the mint (or the mint's freeze authority) can therefore create a pool with a freezable coin or pc mint, wait for a specific victim to deposit, freeze only that victim's destination token account, and permanently block that individual's `Withdraw` call while leaving every other depositor unaffected — analogous to the reported FactoryDAO issue where a pool owner used a custom reward token to selectively block one receipt holder's withdrawal.

### Finding Description
In `process_initialize2`, the mint accounts are unpacked and several safety checks are performed, but only the LP mint's freeze authority is rejected: [1](#0-0) 

The coin and pc mints (`amm_coin_mint_info`, `amm_pc_mint_info`), which are attacker-supplied accounts at pool-creation time (`market_info` is explicitly documented as "Just a seed for AMM account. Can be any account", so the mints are not required to belong to a real OpenBook market), are unpacked with no equivalent `freeze_authority` check: [2](#0-1) 

Only the vault token accounts' `delegate`/`close_authority` fields are checked, never the mint's `freeze_authority`: [3](#0-2) 

`process_withdraw` unconditionally performs an SPL token transfer from the pool's coin/pc vault directly to the caller-supplied `user_dest_coin_info`/`user_dest_pc_info` account, and the whole instruction fails atomically if either transfer fails: [4](#0-3) [5](#0-4) 

Because the SPL Token program rejects transfers into (or out of) a frozen token account, an attacker who created the pool with a mint under their freeze-authority control can:
1. Create a permissionless pool via `Initialize2` using a mint they control (with `freeze_authority = Some(attacker)`).
2. Wait for a victim to deposit and receive LP tokens.
3. Freeze the victim's specific coin or pc ATA (not the pool vault, so all other LPs are unaffected).
4. The victim's `Withdraw` transaction now always fails at the `token_transfer_with_authority` call, and since there is no partial-withdraw/retry mechanism, the victim's underlying coin/pc/LP position is permanently locked in the pool.

This mirrors the reported bug class exactly: a pool-level actor selectively grief one user's withdrawal path via a token property they control, with no fallback available to the victim, while every other participant is unaffected.

### Impact Explanation
This results in a permanent freezing of a specific liquidity provider's funds (their deposited coin/pc value represented by LP tokens) with no way to recover them through the program's normal `Withdraw` path, since the instruction is all-or-nothing and offers no alternative or partial withdrawal route.

### Likelihood Explanation
The pool-creation path (`Initialize2`) is fully permissionless and accepts attacker-chosen mint accounts, so the attacker fully controls whether the coin/pc mint has an active freeze authority. The only requirement is that a victim be induced to interact with (deposit into) the malicious pool, which is a realistic scenario for permissionless AMM pools advertised to users.

### Recommendation
Reject mints with a non-null `freeze_authority` for `coin_mint`/`pc_mint` in `process_initialize2` (as is already done for the LP mint), or, alternatively, add a defensive fallback (e.g., an emergency/permissionless-recipient withdrawal path) so a griefed depositor is not permanently unable to redeem their share if a token transfer to their own account fails.

### Proof of Concept
1. Attacker mints a new SPL token `M` with `freeze_authority = attacker`.
2. Attacker calls `Initialize2` (`program/src/processor.rs` `process_initialize2`) using `M` as `amm_coin_mint`, paired with a normal pc mint, seeding the pool with initial liquidity.
3. Victim deposits into the pool via `Deposit`, receiving LP tokens, and their coin-side balance is held in their own ATA of mint `M` when withdrawing (destination account for `Withdraw`).
4. Attacker calls `spl_token::instruction::freeze_account` on the victim's ATA of mint `M` using their freeze authority.
5. Victim calls `Withdraw`; `Invokers::token_transfer_with_authority` (program/src/processor.rs:1787-1795) fails because the destination account is frozen, causing `process_withdraw` to return an error and abort the whole instruction (`program/src/invokers.rs:171-195`).
6. The victim can never withdraw through this instruction while their account remains frozen; other LPs using unfrozen accounts continue to withdraw normally, confirming the attack is selectively targeted.

    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
