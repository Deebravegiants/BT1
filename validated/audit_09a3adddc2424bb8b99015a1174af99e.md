Based on my research, I found a genuine custody analog in `pool_u64.move`'s share/coin conversion logic — the same class of bug as the Float Capital issue (an edge-case branch that computes value using the wrong basis, causing large value misallocation between parties).

### Title
Share-price basis corruption in `pool_u64::amount_to_shares_with_total_coins()` when only one of `total_coins`/`total_shares` is zero - (File: `aptos-move/framework/aptos-stdlib/sources/pool_u64.move`)

### Summary
`pool_u64::amount_to_shares_with_total_coins()` treats the pool as "empty" (and mints shares 1:1 by `scaling_factor`, ignoring the existing share supply) whenever **either** `total_coins == 0` **or** `total_shares == 0`, instead of only when both are zero. [1](#0-0) 

### Finding Description
The intended semantics (per the module doc) are that a fresh pool with no shares issued yet should price new shares 1:1 (scaled). But the guard condition `self.total_coins == 0 || self.total_shares == 0` also fires in the mixed state where **existing shareholders already hold shares (`total_shares > 0`) while the pool's tracked coin balance is `0`** (e.g., after a stake pool is slashed to zero, or dust settles such that `total_coins` reads 0 while share records for stakeholders are still present, since `total_coins` is maintained separately via `update_total_coins()` and is not atomically tied to share bookkeeping). [2](#0-1) 

In that state, a new depositor calling `buy_in()` gets `new_shares = coins_amount * scaling_factor`, and `total_shares` becomes `old_worthless_shares + new_shares` while `total_coins` becomes `0 + coins_amount`. [3](#0-2) 

The existing (previously worthless) shareholders now instantly own a nonzero fraction of the *new* depositor's coins, even though they contributed nothing to the new balance — this is proven directly by the module's own test, which shows shares issued via the "empty" branch ignore any pre-existing `total_shares`: [4](#0-3) 

This mirrors the Float Capital bug pattern exactly: an edge-case branch that should represent "no value exists yet" instead fires on a partial-zero state and computes a return value using the wrong basis (ignoring the real existing shares/coins ratio), corrupting the accounting that determines how much value each holder is entitled to.

### Impact Explanation
`pool_u64` is the share-accounting primitive used by `staking_contract.move` and `vesting.move` grant pools to track how much of a stake pool's real APT balance belongs to each staker/shareholder. [5](#0-4) 
If a pool's `total_coins` is driven to `0` while shareholders still hold nonzero `total_shares` (e.g., via `update_total_coins(0)` after a payout/slashing event that empties the tracked balance without also zeroing every shareholder's records), a subsequent depositor's coins are diluted to already-existing (and previously worthless) shareholders. This moves real APT value to the wrong holder — a custody/accounting corruption directly affecting `Custody Pivots`: "Custody invariants should hold across deposit, withdraw ... store-creation paths."

### Likelihood Explanation
The vulnerable branch is trivially demonstrable in isolation (the module's own unit test exercises exactly this mixed-zero state and documents the resulting share dilution behavior). However, I was **not able to fully confirm**, within the available tool budget, a concrete unprivileged call sequence in `staking_contract.move` or `delegation_pool.move` that drives `total_coins` to exactly `0` while `total_shares` remains nonzero under attacker control (rather than only via privileged/administrative `update_total_coins` calls tied to legitimate stake-pool state transitions). This gap means the **exploitability from an unprivileged actor** is unconfirmed — the bug is real in `pool_u64` itself, but its blast radius through `staking_contract`/`vesting` callers requires further verification of the exact conditions under which real pools reach `total_coins == 0` with `total_shares > 0`.

### Recommendation
Change the branch condition in `amount_to_shares_with_total_coins()` (and the analogous logic in `pool_u64_unbound.move`) to only treat the pool as "empty" when **both** `total_coins == 0` **and** `total_shares == 0`. When only `total_coins == 0` but `total_shares > 0`, either abort (the pool has shares but no backing value, an invalid state to buy into) or handle it explicitly so new deposits are not diluted to stale shareholders.

### Proof of Concept
Demonstrated directly by the existing test in the repo, which shows the exact "wrong basis" computation:
```
let pool = new(1);
pool.update_total_coins(0);
pool.add_shares(@1, 100);          // total_shares = 100, total_coins = 0
assert!(pool.amount_to_shares(1000) == 1000, 2); // ignores the 100 pre-existing shares
``` [6](#0-5) 
After this, `total_shares = 1100`, `total_coins = 1000`; shareholder `@1` (who contributed 0 of the 1000 new coins) is now entitled to `100/1100 * 1000 ≈ 90` coins that were solely contributed by the new depositor — an unearned transfer of custody-relevant value between holders, confirming the corrupted-value chain (edge-case branch → wrong basis for share pricing → value moved to wrong holder).

**Caveat:** This finding is scoped to the `pool_u64` primitive itself, which is self-contained and provably broken in the demonstrated state. Whether an unprivileged attacker can force a live `staking_contract`/`vesting` pool into `total_coins == 0` with `total_shares > 0` was not independently confirmed and would need further investigation of `update_total_coins()` call sites in `staking_contract.move` and `delegation_pool.move`.

    public fun buy_in(self: &mut Pool, shareholder: address, coins_amount: u64): u64 {
        if (coins_amount == 0) return 0;

        self.total_shares += new_shares;
        self.add_shares(shareholder, new_shares);
        new_shares
    }

```text
    /// Return the number of new shares `coins_amount` can buy in `self` with a custom total coins number.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u64 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            coins_amount * self.scaling_factor
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount, self.total_shares, total_coins)
        }
    }
```
