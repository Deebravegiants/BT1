## Finding: Webhook HMAC signature does not bind the `shop-domain` (or `topic`/`webhook-id`) header, allowing cross-tenant webhook spoofing via replay

### Title
Webhook HMAC only covers the raw body, not the `shop-domain` header, enabling cross-tenant webhook replay - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone. The `shop`, `topic`, `webhook_id`, and `api_version` values — all of which are trusted downstream by `ShopifyAPI::Webhooks::Registry.process` and handed to app webhook handlers as the identity of the tenant the payload belongs to — are taken from unauthenticated HTTP headers that are never part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` accepts the request once `Utils::HmacValidator.validate(request)` succeeds, and then builds `WebhookMetadata` using `request.shop` (read from the `shopify-shop-domain`/`x-shopify-shop-domain` header) and `request.topic`/`request.webhook_id` — none of which were part of the HMAC-verified bytes: [3](#0-2) 

The header values are read directly from the parsed HTTP headers with no cross-check against the signed body: [4](#0-3) 

This is the exact bug-class described in the analog report: a security control (HMAC) protects one artifact (the body bytes) while a different, unauthenticated artifact (the `shop-domain` header) is what the application actually trusts to identify which tenant the data belongs to — an identity-binding gap between "bytes verified" and "bytes/headers acted on."

### Impact Explanation
Because the signature only binds the body, any body+HMAC pair that was legitimately produced by Shopify for **one** shop (e.g., a shop the attacker themselves owns and has installed the app on) remains a valid signature under any other `shop-domain`/`topic`/`webhook-id` header value. An attacker can capture one genuine webhook delivery for their own tenant and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) changed to a victim shop. `HmacValidator.validate` still passes (only the body bytes are checked), and `Registry.process` dispatches the handler with `shop: <victim>` and the attacker's controlled body content. Any host application that keys per-tenant state off `WebhookMetadata#shop` (the officially recommended usage of this API) will apply attacker-controlled data to the wrong tenant — this is a cross-tenant data-integrity/confusion vulnerability reachable by an unprivileged internet user who controls only their own installation of the app.

### Likelihood Explanation
The webhook receiving endpoint is a public, unauthenticated HTTP endpoint by design (Shopify webhook delivery model), so any internet user can POST to it. The only prerequisite is obtaining one valid `(raw_body, hmac)` pair, which is trivially available to anyone who installs the target app on their own store and triggers any webhook-emitting action (e.g., updating a product). No secrets, tokens, or victim-tenant access are required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the signable content used for HMAC validation, or otherwise cryptographically bind these header values to the signed payload before they are trusted as the tenant identity in `WebhookMetadata`. At minimum, document that consuming applications must independently verify the `shop` header against a known/installed shop record before acting on webhook data, since this gem does not bind it.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `products/update`) to receive a legitimate delivery with body `B` and header `x-shopify-hmac-sha256: H` (valid signature of `B` under the app's `api_secret_key`).
2. Replay the captured request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `Digest.hexencode(Base64.decode64(hmac)) == HMAC(secret, B)`, per: [5](#0-4) 
4. `Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"` and body `B`, even though `B` was never associated with `victim.myshopify.com` by Shopify: [6](#0-5)
