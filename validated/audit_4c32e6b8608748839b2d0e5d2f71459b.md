### Title
Insertion-order (not height-order) eviction in `insert_bounded_state_commitment` can prematurely purge in-flight state commitments, blocking message delivery - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`Pallet::insert_bounded_state_commitment` in `modules/pallets/ismp/src/lib.rs` maintains a per-`StateMachineId` FIFO queue (`StateCommitmentQueue`/`CommitmentQueueStates`) that bounds `BoundedStateCommitments` to `state_machine_commitment_cap(id)` entries, evicting the oldest queue entries (by insertion order) whenever the count exceeds the cap. This mirrors the reported "convoluted update+clean" pattern from the `BeamBalanceStore.updateTo` report: a single function performs both the "keep state updated" and "clean older entries" responsibilities in one pass, with a bounded/likely-too-aggressive eviction condition and no event emitted on eviction.

### Finding Description
`insert_bounded_state_commitment` [1](#0-0)  is invoked from `IsmpHost::store_state_machine_commitment`, which is reached whenever any relayer submits a `ConsensusMessage` that is verified by `handlers::update_client` [2](#0-1) . This path is reachable by any unprivileged relayer relaying a valid consensus proof — no admin/governance action is required.

The eviction logic evicts strictly by insertion order from the queue head, not by whether the evicted height still has pending, unrelayed requests/responses that depend on that state commitment for proof verification:
```
let excess = (state.tail - state.head).saturating_sub(cap).min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
for _ in 0..excess {
    if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
        BoundedStateCommitments::<T>::remove(height.id, old);
        BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
    }
    state.head += 1;
}
```
Once a height is evicted, `state_machine_commitment` returns `Error::StateCommitmentNotFound` [3](#0-2) , which is used by the message handler to verify state (non-)membership proofs for pending requests/responses/timeouts committed at that height. Any request/response whose state proof was anchored to an evicted height can no longer be verified or delivered — the route is unable to deliver those specific in-flight messages, and the relayer fee/escrow tied to that message may become permanently stuck (never resolved, requiring a timeout path that itself may also depend on the same, now-missing, height for its own proof verification depending on chain design).

This is the same class of issue as the original report's "weak condition in cleaning mechanism" and "unclear/undocumented looping algorithm for balance updates": the eviction ("cleaning") loop is decoupled from any notion of whether the data being cleaned is still needed, and there is no event emitted when an entry is evicted (matching "lack of event emission in updateTo"), making the condition for safety (that `cap` is always large enough relative to real-world relaying latency and chain finality cadence) implicit, undocumented, and unverifiable on-chain.

### Impact Explanation
If the cap (`MAX_STATE_MACHINE_COMMITMENTS` = 10,240, or a lower `StateMachineCommitmentCap` override) is exceeded by the number of new heights arriving before a given height's associated requests are proven and relayed, the height's commitment is silently deleted with no corresponding safeguard, freezing the ability to deliver those specific messages permanently (their proof-of-existence can never again be verified against `BoundedStateCommitments`). This falls under the accepted impact class of "permanent freezing of funds" / "route unable to deliver messages."

### Likelihood Explanation
Likelihood is low-to-medium and depends entirely on the connected chain's finality cadence versus the configured cap and relaying speed. For chains with very fast block times or during long relayer outages, a large enough backlog of un-relayed messages could see their anchor heights evicted before delivery. There is no attacker-controlled amplification found (an attacker cannot fabricate new heights beyond what the source chain legitimately finalizes — the "skip duplicate/already-processed heights" checks in `update_client` prevent artificial inflation of the queue), so this is best characterized as a design/configuration risk rather than a directly exploitable attack, and it is explicitly a latent risk rather than a confirmed live incident.

### Recommendation
Decouple the "insert new commitment" and "evict old commitment" responsibilities into separate, well-documented helper functions (as the analog report suggests for `updateTo`), and make the eviction condition explicit and safe: track whether a height still has pending (unrelayed / unexpired) requests or responses anchored to it before evicting, or ensure the cap is provably large enough relative to the configured challenge/timeout periods and expected relaying cadence. Emit an event (e.g., `StateCommitmentEvicted`) whenever an entry is evicted from `BoundedStateCommitments`, so off-chain relayers/monitors can detect and react to imminent eviction of heights they still need to relay against.

### Proof of Concept
Not executable within this analysis; the risk is structural rather than a single-transaction exploit. Conceptually: configure/observe a `StateMachineId` where more than `cap` distinct finalized heights are legitimately submitted via consensus updates before a specific pending request (anchored at an older height) is relayed; on the `cap+1`-th (batched by `MAX_COMMITMENT_EVICTIONS_PER_INSERT`) insertion, the oldest height's `BoundedStateCommitments` entry is removed, and any subsequent attempt to submit a request/response/timeout message whose proof is verified against that height will fail with `Error::StateCommitmentNotFound`, permanently blocking delivery of that message.

		pub fn insert_bounded_state_commitment(
			height: StateMachineHeight,
			commitment: StateCommitment,
		) {
			let cap = Self::state_machine_commitment_cap(height.id).max(1) as u64;
			let mut state = CommitmentQueueStates::<T>::get(height.id);

			StateCommitmentQueue::<T>::insert(height.id, state.tail, height.height);
			state.tail += 1;

			let excess = (state.tail - state.head)
				.saturating_sub(cap)
				.min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
			for _ in 0..excess {
				if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
					BoundedStateCommitments::<T>::remove(height.id, old);
					BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
				}
				state.head += 1;
			}

			CommitmentQueueStates::<T>::insert(height.id, state);
			BoundedStateCommitments::<T>::insert(height.id, height.height, commitment);
		}

pub fn update_client<H>(host: &H, msg: ConsensusMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host.consensus_client_id(msg.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized { consensus_state_id: msg.consensus_state_id },
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;
	host.is_consensus_client_frozen(msg.consensus_state_id)?;
	host.is_expired(msg.consensus_state_id)?;

	let (new_state, intermediate_states) = consensus_client.verify_consensus(
		host,
		msg.consensus_state_id,
		trusted_state,
		msg.consensus_proof,
	)?;
	host.store_consensus_state(msg.consensus_state_id, new_state)?;
	let timestamp = host.timestamp();
	host.store_consensus_update_time(msg.consensus_state_id, timestamp)?;
	let mut state_updates = vec![];
	for (id, mut commitment_heights) in intermediate_states {
		commitment_heights.sort_unstable_by(|a, b| a.height.cmp(&b.height));
		let previous_latest_height = host.latest_commitment_height(id)?;
		let mut last_commitment_height = None;
		for commitment_height in commitment_heights.iter() {
			let state_height = StateMachineHeight { id, height: commitment_height.height };

			// Only allow heights greater than latest height
			if previous_latest_height > commitment_height.height {
				continue;
			}

			// Skip duplicate states
			if host.state_machine_commitment(state_height).is_ok() {
				continue;
			}

			last_commitment_height = Some(state_height);
			host.store_state_machine_commitment(state_height, commitment_height.commitment)?;
			host.store_state_machine_update_time(state_height, host.timestamp())?;
		}

		if let Some(latest_height) = last_commitment_height {
			let latest_height = StateMachineHeight { id, height: latest_height.height };
			state_updates.push(Event::StateMachineUpdated(StateMachineUpdated {
				state_machine_id: id,
				latest_height: latest_height.height,
			}));
			host.store_latest_commitment_height(latest_height)?;
		}
	}

	Ok(MessageResult::ConsensusMessage(state_updates))
}
