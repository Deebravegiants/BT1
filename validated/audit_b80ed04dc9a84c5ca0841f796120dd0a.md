### Title
POA bridge withdrawal status lookup matches by `assetId` only, causing status/txHash misreport for batched same-token withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a specific withdrawal using only the token `assetId`, ignoring the `index` and `destinationAddress` that make a `WithdrawalIdentifier` unique. When a single NEAR transaction contains more than one withdrawal of the same asset (e.g. two `ft_withdraw` intents for the same token to different destinations, both included in the same signed multi-intent transaction), the lookup can return the wrong underlying withdrawal's status and `txHash` for the wrong `WithdrawalIdentifier`.

### Finding Description
`describeWithdrawal` calls `getWithdrawalStatusWithRetry` (keyed only by `args.tx.hash`) and then `findMatchingWithdrawal`, which searches the (explicitly documented as "unsorted") API response array for the first entry whose `near_token_id` matches `args.withdrawalParams.assetId`: [1](#0-0) [2](#0-1) 

The code's own comment acknowledges the gap: *"multiple withdrawals of the same token in a single transaction are not supported"* [3](#0-2) . The `WithdrawalIdentifier` produced by `createWithdrawalIdentifier` does carry an `index` and the full `withdrawalParams` (including `destinationAddress`), but `describeWithdrawal`/`findMatchingWithdrawal` never uses `index` or `destinationAddress` to disambiguate: [4](#0-3) .

The equality that should hold is: *"status/hash reported for withdrawal index N" == "the on-chain outcome of withdrawal index N"*. Because the match key is reduced to `assetId` alone, two different withdrawals (different indices, different destination addresses, same token) collapse to the same lookup result. Whichever entry the (unsorted) API happens to return first is reported for both identifiers.

### Impact Explanation
If a caller batches two withdrawals of the same POA-bridged token to two different destination addresses within one NEAR transaction, and polls `describeWithdrawal` (or `waitForWithdrawalCompletion` from `sdk.ts`) per `WithdrawalIdentifier`, one of the two calls can receive the `status: "completed"` and `txHash` that actually belongs to the *other* withdrawal. An integrator that credits/marks-complete based on this status could mark the wrong withdrawal as completed while the real matching withdrawal is still pending — or report the same `txHash` for both, causing a double-credit/incorrect completion record on the integrator side. This matches the "status or hash misreport making an integrator credit or refund twice" impact category (High).

### Likelihood Explanation
This requires the caller/integrator to deliberately build a batch of ≥2 withdrawal intents for the *same* POA-bridge asset within a single signed transaction — a legitimate, unprivileged usage pattern already supported by `createWithdrawalIntents`/`processWithdrawal` batch APIs (`WithdrawalParams[]`). No malicious relayer, RPC, or bridge-operator behavior is needed; only an ordinary user/integrator submitting two same-token withdrawals together, which is explicitly a scenario the code comment concedes is unhandled.

### Recommendation
Disambiguate by more than `assetId`: match POA API withdrawal entries using `destinationAddress` (and `destinationMemo`/tag where applicable) in addition to `assetId`, or use `index`-based ordering once the POA API can guarantee stable ordering (as the existing comment suggests, e.g., sort both sides by amount when tokens are equal). Until the API supports a stable per-withdrawal identifier, `describeWithdrawal` should refuse to disambiguate ambiguous same-asset batches (e.g., throw/require callers not to batch same-asset POA withdrawals) rather than silently returning a matching but potentially wrong record.

### Proof of Concept
1. Build one NEAR transaction with two `ft_withdraw` intents for the same `assetId` (e.g. `nep141:usdc.omft.near`) to two different `destinationAddress` values, submitted together via the batch `WithdrawalParams[]` path.
2. Call `bridge.createWithdrawalIdentifier` for `index: 0` and `index: 1` with the same `tx.hash`.
3. After the POA indexer processes the tx and returns both withdrawal records (order not guaranteed), call `describeWithdrawal` for both identifiers.
4. `findMatchingWithdrawal` returns the same (first-matching) array entry for both calls regardless of `index`/`destinationAddress`, so if withdrawal #1 (to address B) completed but withdrawal #0 (to address A) is still pending, `describeWithdrawal({index:0, destinationAddress:A})` can report `status:"completed"` with the `txHash` that actually paid address B — mismatching the on-chain state for identifier 0.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
