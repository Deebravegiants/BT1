### Title
Webhook `shop-domain` header trusted for tenant attribution while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `Utils::HmacValidator.validate` never covers the `shop-domain` (or `topic`/`webhook-id`) header. `Registry#process` nonetheless uses `request.shop` — sourced straight from that unauthenticated header — to attribute the payload to a tenant when building `WebhookMetadata`.

### Finding Description
`Webhooks::Request` extracts `shop` directly from the HTTP header with no cryptographic binding: [1](#0-0) 

Its `to_signable_string` (used by the shared `HmacValidator`) returns only the raw JSON body: [2](#0-1) 

`HmacValidator.validate` computes/compares the HMAC solely over that signable string: [3](#0-2) 

`Registry.process` accepts the request as authentic once the body HMAC checks out, then hands `request.shop` (the unauthenticated header) to the handler as the tenant identifier: [4](#0-3) 

The equality the gem implicitly relies on is: `shop used for tenant attribution == shop bound by the verified HMAC`. In reality: `shop header (unauthenticated) != shop covered by HMAC (raw body only)`. Any party capable of obtaining one genuine, validly-signed webhook body (e.g., a merchant who installed the app and legitimately receives their own webhooks) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still passes because it only checks `@raw_body`, and the handler will process/store the data as belonging to whatever shop the attacker put in the header.

### Impact Explanation
This breaks the tenant identity binding between the cryptographically verified content and the shop the host application believes originated it. If the host application uses `WebhookMetadata#shop` (built from `request.shop`) to key data writes, cache invalidation, or entitlement checks, an attacker can attribute forged/duplicated events to a victim shop, i.e. cross-tenant access — one of the accepted Critical impact categories.

### Likelihood Explanation
Requires the attacker to possess at least one legitimately-signed webhook body (trivial for any merchant who installs the app themselves, since Shopify sends them real webhooks with valid HMACs), then simply resend it with a different `shop-domain` header value. No access token, `client_secret`, or TLS interception is needed — only standard HTTP access to the app's public webhook endpoint. This is a realistic, low-effort attack path for any unprivileged/self-installing user of the app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the HMAC verification, or otherwise cross-check the header-derived shop against an independently trusted identifier (e.g., re-fetching/validating via the registered webhook id from Shopify) before dispatching to `WebhookMetadata`. At minimum, document that host applications must not treat `request.shop`/`WebhookMetadata#shop` as authenticated on its own.

### Proof of Concept
1. Install the app on shop `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Replay the exact same request to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (all other headers/body unchanged).
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)`, which still equals `H` — validation succeeds (see `lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), even though the payload actually originated from the attacker's own shop.
