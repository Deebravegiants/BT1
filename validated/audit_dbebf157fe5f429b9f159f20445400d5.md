### Title
Case-insensitive bech32 BTC addresses bypass `compareAddresses` in `OmniBridge.validateWithdrawal`, letting `ft_withdraw` recipient collapse to the bridge's token/connector address - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.validateWithdrawal` uses `compareAddresses(destTokenAddress, args.destinationAddress, assetInfo.blockchain)` to block withdrawals to the bridge's own token address, but for `Chains.Bitcoin` (and other UTXO chains reachable via `ChainKind.Btc`) `compareAddresses` does a raw `a === b` string comparison [1](#0-0) , while `validateAddress`'s bech32 decoder accepts case-variant (e.g. all-uppercase) forms of the same address as valid [2](#0-1) . Downstream, `deriveOmniWithdrawIntentParams` silently lowercases the address for `ChainKind.Btc` before building the intent - meaning the address that ultimately gets paid can equal the token/connector address even though `validateWithdrawal` never threw.

### Finding Description
The broken equality is: `(chain, destinationAddress paid)` == `(chain, destinationAddress validated as “not the token address”)`.

- `validateWithdrawal` fetches the canonical token address via `getCachedDestinationTokenAddress`/`getAddress(destTokenOmniAddress)` and compares it to the caller-supplied `destinationAddress` with `compareAddresses(destTokenAddress, args.destinationAddress, assetInfo.blockchain)` [3](#0-2) .
- For `Chains.Bitcoin` (and the other exact-match branch chains), `compareAddresses` does not normalize case/encoding — it just checks `a === b` [1](#0-0) .
- However `validateAddress`'s bech32 path (`validateBtcBech32Address`) accepts an all-uppercase or otherwise differently-cased bech32 string as a *valid* Bitcoin address, since bech32 decoding per BIP-173 is case-insensitive as long as the whole string is consistently cased [4](#0-3) .
- So an attacker can submit `destinationAddress = destTokenAddress` with its case flipped (e.g. `bc1q...` → `BC1Q...`). `validateAddress` accepts it, `compareAddresses` sees two unequal strings and does **not** throw `DestinationAddressMatchesTokenAddressError`, and `validateWithdrawal` returns successfully.
- The bug is compounded by `deriveOmniWithdrawIntentParams`, which explicitly documents and implements a lowercase-normalization step for `ChainKind.Btc` bech32 addresses right before constructing the `recipient` used in the withdraw intent: *"Omni contract only accepts lowercase bech32 addresses; uppercase/mixed-case bech32 is spec-valid but rejected on-chain."* [5](#0-4) . This normalization runs downstream of `validateWithdrawal`'s check, not before it, so the case-flipped address that slipped past `compareAddresses` gets lowercased into the exact form of `destTokenAddress` when the actual `ft_withdraw` intent's `recipient`/`msg` is built.
- Net effect: `validateWithdrawal` approves a `destinationAddress` that is a mere case-variant of the token/connector address; `IntentsSDK.createWithdrawalIntents` proceeds; the final signed intent pays to the address the guard was supposed to block.

Existing guards fail because: `validateAddress` and `compareAddresses` use inconsistent normalization for the same chain (one canonicalizes bech32 case implicitly by accepting it, the other does not canonicalize at all), and the later silent lowercasing in `deriveOmniWithdrawIntentParams` (added specifically because "the Omni contract only accepts lowercase") is not applied before the `compareAddresses` safety check.

### Impact Explanation
Funds withdrawn via OmniBridge to a Bitcoin/UTXO destination can be routed to the bridge/token's own address instead of the user's real destination — this is a "funds delivered to a wrong address/chain/contract with no recovery" case, matching **Critical** severity. The attacker (a counterparty who supplies `destinationAddress` that an integrator forwards, per the threat model) gets no direct financial gain but can grief a victim into burning funds; more importantly, this proves `validateWithdrawal`'s check is not authoritative for chains with non-canonical `compareAddresses` semantics, so any integrator relying on it to prevent self-burns can have withdrawals silently pass validation while being paid to the token/connector address. This is repeatable per call/withdrawal for BTC/UTXO destinations.

### Likelihood Explanation
Preconditions: the withdrawal must target a UTXO chain routed through OmniBridge with a bech32 destination-token address (`ChainKind.Btc`, e.g. `nbtc.bridge.near`-style assets), and the caller must supply a destination address that is a same-address case-variant of the canonical (lowercase) token address. This costs nothing (any unprivileged SDK caller can pass any string), requires no special privilege, and is deterministic/repeatable. The main uncertainty is whether the token/connector "destination address" returned by `getCachedDestinationTokenAddress` for BTC is itself commonly a bech32-form address in practice; the code path and the explicit "Omni contract only accepts lowercase bech32" comment in `omni-withdraw-params.ts` strongly indicate this is a real, previously-known-about edge case for this exact chain.

### Recommendation
Normalize addresses identically in both places for chains with case-insensitive encodings (Bitcoin/Litecoin/Dash bech32, etc.): either make `compareAddresses` lowercase bech32-form addresses for `Chains.Bitcoin`/UTXO chains before comparing, or run the same normalization used in `deriveOmniWithdrawIntentParams` before calling `compareAddresses` inside `validateWithdrawal`, so the safety check operates on the exact string that will end up in the signed intent.

// packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.test.ts
it("bypasses DestinationAddressMatchesTokenAddressError via bech32 case variant", async () => {
  const destTokenAddressLower = "bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq";
  const destTokenAddressUpper = destTokenAddressLower.toUpperCase(); // same address, different case

  const nearProvider = nearFailoverRpcProvider({ urls: PUBLIC_NEAR_RPC_URLS });
  const bridge = new OmniBridge({ envConfig: configsByEnvironment.production, nearProvider });

  vi.spyOn(bridge as any, "getCachedDestinationTokenAddress")
    .mockResolvedValue(omniAddress(ChainKind.Btc, destTokenAddressLower));

  // 1) validateWithdrawal does NOT throw despite destinationAddress representing
  //    the exact same on-chain address as the token/connector address.
  await expect(
    bridge.validateWithdrawal({
      assetId: "nep141:nbtc.bridge.near",
      amount: 1000n,
      destinationAddress: destTokenAddressUpper,
      routeConfig: createOmniBridgeRoute(Chains.Bitcoin),
      feeEstimation: {
        amount: 1n,
        quote: null,
        underlyingFees: {
          [RouteEnum.OmniBridge]: {
            utxoMaxGasFee: 1n,
            utxoProtocolFee: 1n,
          },
        },
      },
    }),
  ).resolves.toBeUndefined(); // BUG: should reject with DestinationAddressMatchesTokenAddressError

  // 2) The produced intent recipient collapses to the lowercase form == destTokenAddress
  const params = deriveOmniWithdrawIntentParams({
    assetId: "nep141:nbtc.bridge.near",
    destinationAddress: destTokenAddressUpper,
    actualAmount: 1000n,
    omniChainKind: ChainKind.Btc,
    intentsContract: "intents.near",
    feeEstimation: {
      amount: 1n,
      quote: null,
      underlyingFees: {
        [RouteEnum.OmniBridge]: { utxoMaxGasFee: 1n, utxoProtocolFee: 1n },
      },
    },
  });

  expect(params.recipient).toBe(omniAddress(ChainKind.Btc, destTokenAddressLower));
  // Assert both sides of the DESTINATION TRUTH equality now DO match,
  // proving the address that gets paid equals the token/connector address
  // that validateWithdrawal was supposed to have blocked.
});

function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
}
