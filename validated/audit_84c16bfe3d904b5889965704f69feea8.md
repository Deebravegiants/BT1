### Title
Webhook `shop`, `topic`, `api-version`, and `webhook-id` fields are trusted from unauthenticated headers while only the raw body is covered by the HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` value that is handed to the app's handler as the tenant identifier is read from an HTTP header that is never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` gates processing on `Utils::HmacValidator.validate(request)` [1](#0-0) . `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` [2](#0-1) , and for `Webhooks::Request` that signable string is defined as `@raw_body` only [3](#0-2) . Meanwhile `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the HMAC at all [4](#0-3) . `process` then forwards `request.shop` unchanged into `WebhookMetadata` and passes it to the app-supplied handler as the tenant identifier [5](#0-4) [6](#0-5) .

This breaks the equality the HMAC is supposed to guarantee: `shop-header-used-by-handler == shop-that-Shopify-actually-signed-for`. Because Shopify signs webhooks with the app's single `client_secret` for *all* shops that installed the app, the same secret produces the same HMAC for the same body regardless of which shop the webhook is "from." Consequently, an unprivileged user who controls any shop that has installed the app (a normal, unprivileged tenant relationship) can:
1. Trigger a real webhook delivery to their own shop (e.g., a resource create) and capture the `raw_body` + valid `x-shopify-hmac-sha256` header that Shopify computed with the shared secret.
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and even `x-shopify-topic`) with a victim shop's domain / a different topic.
3. `HmacValidator.validate` still returns `true` (only the body is checked), so `Registry.process` proceeds and calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

Any app handler that uses `data.shop` to look up a stored session/access token, write victim-shop data, or otherwise act with that shop's identity performs a cross-tenant operation using data manufactured by another tenant.

### Impact Explanation
This meets the cross-tenant access impact bar: an unprivileged installer of the app can make the gem hand a handler a forged tenant identity (`shop`) that passed HMAC "verification," even though the header carrying that identity is entirely uncovered by the signature. Depending on what the host app's handler does with `data.shop` (nearly all Shopify webhook handlers key session/token lookups and side effects off this field), this can result in cross-tenant state corruption or actions being taken against another merchant's store using the attacker's own webhook payload.

### Likelihood Explanation
Requires only having a shop that has installed the app (no special privilege) and the ability to send a raw HTTP POST to the app's public webhook endpoint with attacker-controlled headers — both are available to a normal, unprivileged internet user/tenant. No access to `api_secret_key`, access tokens, or any other credential is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`api-version`/`webhook-id`) header values in the HMAC-signed content, or otherwise derive/verify these fields from data that is cryptographically bound to the signature, before constructing `WebhookMetadata` and dispatching to the handler in `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event so Shopify sends a webhook (e.g. `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the identical `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares it to `H` — matches, since `B` and `H` are unchanged from the legitimate delivery [8](#0-7) .
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` even though Shopify never sent this payload for that shop [5](#0-4) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
