### Title
Multi-token escrow release loop reverts entirely on a single failing transfer, permanently freezing all other escrowed assets in the order - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` releases every escrowed token for an order in a single loop. If any one of the tokens in a multi-token order permanently fails to transfer (e.g. a blacklisting stablecoin such as USDT/USDC refusing the beneficiary, or a malicious/paused ERC-20 chosen as an order input), the entire `_withdraw()` call reverts, blocking release of *all* other tokens (and the escrowed transaction fee) in that same order — exactly the "child fails → parent reverts → funds frozen" pattern described in TRST-H-2 for `ComplexRewarder.onReward()`.

### Finding Description
`_withdraw()` iterates `body.tokens` and unconditionally `safeTransfer`s (or sends native value) to the beneficiary for each entry, with no isolation between transfers: [1](#0-0) 

A `safeTransfer` failure on entry `i` reverts the whole function — including the fee release and finalize step that follow — and any tokens at indices `< i` that already updated state are also rolled back since Solidity reverts the entire call. This function is the single settlement primitive reached from three unprivileged, cross-chain-triggered paths:

- `ExtrinsicIntents.onAccept()` for `RedeemEscrow`/`RefundEscrow` messages delivered via ISMP after a solver fills a cross-chain order: [2](#0-1) 
- `ExtrinsicIntents.onGetResponse()` for the cancel-from-source flow: [3](#0-2) 
- `IntrinsicIntents._cancelSameChain()` / same-chain fill path, which batches *all* of an order's remaining input tokens into one `_withdraw()` call: [4](#0-3) 

Because `order.inputs[i].token` is an arbitrary address supplied by the user at `placeOrder` time, a single order can escrow a mix of "normal" tokens and one adversarial or blacklist-capable token. Once that one token's transfer becomes permanently unfulfillable (blacklisted beneficiary, paused contract, or a token deliberately crafted to always revert for a chosen address), every future retry of `onAccept`/`onGetResponse` for that commitment deterministically reverts in the same place, since none of the escrow state or `_filled` marking is ever durably updated. This differs from the TRST-H-2 report only in that the "children" are token transfers in a loop rather than child rewarder contracts, but the root cause and blast pattern are identical: a downstream, non-essential failure aborts an otherwise-successful top-level operation and there is no per-item exception handling.

Unlike `EvmHost.dispatchIncoming()`, which deliberately isolates `onAccept` failures with a raw `.call` and deletes the receipt so the message can be retried: [5](#0-4) 
...retrying does not help here because the failure inside `_withdraw()` is deterministic — the same token transfer will fail on every retry, so the message (and all its bundled tokens/fees) can never be delivered.

### Impact Explanation
All escrowed tokens tied to an order commitment — not just the one problematic token — become permanently unrecoverable, since `_withdraw()` must fully succeed to update `_orders`, mark `_filled`, and release fees. This is a permanent freezing-of-funds condition affecting both the user's original escrow (on cancel/refund) and the solver's redemption (on fill), for orders that happen to include any token capable of a deterministic transfer failure to the beneficiary.

### Likelihood Explanation
Reachable via ordinary, unprivileged use of the protocol: any user can construct an `Order` with `TokenInfo.token` set to any ERC-20 address at `placeOrder()`, and blacklist-capable tokens (USDT, USDC, and many others) are common in production liquidity. A malicious order creator could also deliberately include a custom token contract that reverts transfers to a specific address to grief a solver's future redemption, or a legitimate beneficiary could simply become blacklisted by a stablecoin issuer between order placement and settlement.

### Recommendation
Isolate each token transfer in `_withdraw()`'s loop (e.g. via `try/catch` around an external call or a low-level `.call` with per-token failure bookkeeping) so a single failing transfer does not block release of the other escrowed tokens or fees. Failed transfers should be tracked and made separately claimable/retriable rather than reverting the whole settlement.

### Proof of Concept
1. User calls `placeOrder` with two input tokens: a normal token (e.g. USDC) and a malicious/blacklist-style ERC-20 whose `transfer` reverts for a chosen beneficiary address.
2. Order is filled/cancelled normally; a `RedeemEscrow`/`RefundEscrow` ISMP message is dispatched back to the source chain.
3. On delivery, `ExtrinsicIntents.onAccept()` → `_withdraw()` iterates both tokens; the second token's `safeTransfer` reverts.
4. `_withdraw()` reverts entirely — the normal USDC amount that would have succeeded is never released, `_filled` is never set, and every subsequent delivery attempt fails identically, permanently freezing both tokens' escrow in `_orders`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
