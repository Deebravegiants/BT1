## #Vulnerability found

### Title
Webhook Shop-Domain Spoofing via HMAC That Only Covers the Request Body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, while the shop identity that gets propagated to the application's handler (`request.shop`) is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed material. An attacker who owns/installs the app on their own store can obtain a legitimately-signed `(body, hmac)` pair from Shopify and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, causing the handler to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body), against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC check, then forwards `request.shop` — an unauthenticated header value — straight into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the identity binding: `shop authenticated (covered by HMAC) != shop delivered to handler (header value)`. Shopify itself never sends mismatched pairs, but nothing in this gem enforces that the `shop-domain` header is bound to the signature — only the JSON body is. An attacker who is a legitimate (if malicious) merchant/installer of the app on their own store receives real webhook deliveries from Shopify, each with a valid `X-Shopify-Hmac-Sha256` computed over the body using the app's real `api_secret_key`. The attacker fully controls the *content* of that body (e.g., by creating an order, product, or customer object with attacker-chosen field values in their own store) and can capture the resulting `(raw_body, hmac)` pair. They then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. Because `to_signable_string` never includes the shop, topic, webhook-id, or api-version headers, this replay passes HMAC validation unchanged, and the app's `WebhookHandler#handle` is invoked with `shop: <victim>` and attacker-chosen `body`.

### Impact Explanation
This is a cross-tenant integrity/spoofing vulnerability: an attacker without any credentials for the victim shop can make the app process attacker-controlled webhook payloads under the victim shop's identity. Depending on how the host application's webhook handlers use `shop`/`body` (e.g., updating tenant-scoped records, triggering data syncs, invalidating caches, or writing to a victim's database rows), this can lead to cross-tenant data corruption or injection, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs to be a normal, unprivileged app installer on their own store — no leaked secrets, no access to the target shop, and no privileged account are required. Capturing their own webhook deliveries (via network capture, a simple relay/logging proxy in front of their own webhook endpoint, or a Shopify webhook explorer/test tool) is straightforward and entirely within their control, since it's their own shop generating the signed payloads.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the HMAC verification, not just the raw body — e.g., include the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` header values in `to_signable_string`/the value verified by `Utils::HmacValidator`, or otherwise cryptographically bind shop identity to the delivery so a body signed for one shop cannot be replayed with a different shop header value.

### Proof of Concept
1. Attacker creates/installs the vulnerable app on their own store `attacker-shop.myshopify.com` and registers an HTTP webhook (e.g., `orders/create`).
2. Attacker triggers an event in their own store with a body of their choosing, and captures the real delivery from Shopify, including the genuine `X-Shopify-Hmac-Sha256` header (computed over the JSON body with the app's real `api_secret_key`) and the raw body bytes.
3. Attacker sends a new HTTP request directly to the app's webhook endpoint, reusing the exact `raw_body` and `X-Shopify-Hmac-Sha256` from step 2, but setting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body/HMAC pair, unrelated to the `shop` header.
5. The registered handler's `handle` method executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, as shown in `lib/shopify_api/webhooks/registry.rb` lines 188-199.
