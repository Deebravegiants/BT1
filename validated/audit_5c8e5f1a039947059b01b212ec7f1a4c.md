## Analysis

I found a strong analog to the reported bug class in `IntentGatewayV2.placeOrder`, which credits escrow amounts based on `balanceOf()` deltas rather than the exact value requested for transfer — the same "trust balanceOf" pattern that the original report calls out.

### Title
Escrow crediting based on `balanceOf()` delta lets a malicious input token inflate `_orders` accounting beyond tokens actually held, enabling insolvent payouts to solvers/refunds - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` measures the tokens it actually escrowed for a given input by taking a `balanceOf(address(this))` snapshot before the transfer and subtracting it from the post-transfer `balanceOf(address(this))`, then stores that delta as the escrowed amount in `_orders[commitment][token]`. If `token` is a malicious/rebasing/manipulable ERC-20 whose `balanceOf` is not tied 1:1 to actual transferred value (the exact bug class described in the external report about `UPStable`), an attacker can make this delta larger than what was truly deposited, over-crediting `_orders` for a commitment they control.

This is structurally identical to the pattern flagged in the report: relying on a token's `balanceOf()` output (rather than the transfer amount actually authorized/expected) to determine how many tokens the pool/escrow "owns" and is obligated to pay out. A token like `UPStable`, whose `balanceOf()` is a function of an internal, attacker-influenceable "factor" rather than tracked ledger balances, can be crafted so that a `safeTransferFrom` of a small amount causes the gateway's `balanceOf(address(this))` to jump by far more than what was actually transferred (e.g., by having the attacker pre-seed a factor change, or by the token computing balances from a global multiplier that the attacker manipulates in the same transaction via a flash-loan-driven state change, if the token exposes any such mechanism). Because the gateway does not compare the delta against a token-specific whitelist or a sane upper bound, and because the same escrow token pool (`address(this)`'s balance) is shared across all orders that use that token, an over-credited `_orders[commitment][token]` entry allows the attacker's order to redeem/refund more tokens than were actually deposited for it, backed by balances that belong to other orders' escrowed input tokens for the same token address.

Note the predispatch path (lines 274-306) has an even looser check: it measures `received = balanceOf(after) - balanceOf(before)` against `dispatcher`'s balance and lets `received > order.inputs[i].amount` just get emitted as `DustCollected` rather than being sanity-checked against an actual transfer amount, compounding the exposure for the same token class.

### Impact Explanation
Any order placed with a malicious ERC-20 input token can cause `_orders[commitment][token]` to be credited with more value than the gateway actually received for that token address. Since `_orders` is keyed by `(commitment, token)` but the underlying custody is a single pooled `token.balanceOf(address(this))` shared by every order using that token, over-crediting one order's escrow directly threatens the solvency of other legitimate orders' escrowed inputs of the same token — the gateway can be drained of tokens legitimately deposited by other users, either through the solver-fill (`RedeemEscrow`) or refund (`RefundEscrow`) paths. This is a direct theft/insolvency vector reachable by any unprivileged caller of `placeOrder`, matching the High severity of the original finding.

### Likelihood Explanation
Likelihood depends on whether a token meeting this profile (manipulable `balanceOf` disconnected from real transfer semantics, as demonstrated by the real-world `UPStable`/Uniswap-skim exploit referenced in the report) is ever accepted as an input token by the gateway. The gateway currently places no restriction (whitelist/blacklist) on which ERC-20 addresses can be used as `order.inputs[i].token` — any caller supplies an arbitrary token address in `placeOrder`. Given permissionless token selection and the precedent of such tokens existing and being exploited in production, likelihood is Medium-to-High.

### Recommendation
- Do not let a single crafted input transaction determine escrow credit from an unconstrained `balanceOf` delta; bound the accepted "actual received" amount to be `<= order.inputs[i].amount` requested (only ever reduce for fee-on-transfer, never allow an increase) rather than trusting any observed increase.
- Maintain a governance-controlled allowlist of input tokens that are known to be standards-compliant (no rebasing, no balance manipulation independent of transfers), analogous to the recommendation in the original report, and reject `placeOrder` calls for unlisted tokens.
- Consider tracking gateway-held balances internally per token rather than relying on live `balanceOf()` reads for escrow accounting.

### Proof of Concept
1. Attacker deploys or acquires a token `EvilToken` whose `balanceOf(address(this_gateway))` can be inflated independent of the amount actually moved by `transferFrom` (e.g., a rebasing/factor-based token like `UPStable`).
2. Attacker calls `placeOrder` with `order.inputs[0].token = EvilToken`, `amount = X` (a small real value).
3. During the transfer step, `EvilToken.balanceOf(address(this))` is manipulated (via the token's own logic, triggered by the transfer or a preceding step in the same transaction) to report an increase of `Y >> X`. [4](#0-3) 
4. `order.inputs[0].amount` is now recorded as `Y`, and after fee reduction, `_orders[commitment][EvilToken] = Y' ≈ Y`.
5. Attacker cancels the order (or has a colluding "solver" fill it) and receives a refund/release of `Y'` `EvilToken` through `_withdraw`, even though only `X` tokens were actually deposited — the shortfall is paid out of the gateway's pooled `EvilToken` balance that belongs to other orders' escrow.
