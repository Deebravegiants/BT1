### Title
Missing revalidation ("deadline") for user QR-code authorization allows stale/expired signup validity to be used for biometric enrollment - (File: src/plans/mod.rs, src/backend/user_status.rs)

### Summary
The externally reported bug concerns Uniswap swaps lacking a `deadline` parameter, letting stale pending transactions be executed later under conditions the user never agreed to. The analog in `orb-core` is the lack of any freshness/deadline enforcement on the **user QR-code authorization result** once it has been fetched from the backend. The orb validates the user once via `backend::user_status::request` and then proceeds through a multi-step, non-trivial-duration pipeline (biometric capture, pipeline processing, fraud detection, PCP building, upload) using the cached `UserData`/`OperatorData` — with no re-check that the authorization is still valid at the time the signup is actually completed.

### Finding Description
`MasterPlan::do_signup` validates the operator QR code and user QR code once, via `verify_operator_qr_code`/`verify_user_qr_code` → `backend::user_status::request`, which returns a `UserData` struct containing cryptographic keys, `identity_commitment`, and authorization flags [1](#0-0) . The only "freshness" control that exists anywhere in this flow is `operator_qr_expiration_time`, which is checked purely against the **operator** QR-code's local scan timestamp before *starting* the remaining scan/validation flow [2](#0-1)  and in `scan_initial_qr_codes`/`idle_scan_user_qr_code` [3](#0-2) . This expiration guard does not cover the **user** authorization result once fetched, nor is it re-checked at any point after `do_signup` begins.

After the one-time validation, `do_signup` proceeds through `biometric_capture`, `biometric_pipeline`, `detect_fraud`, PCP package building, and data upload — all of which can take a non-trivial amount of wall-clock time — while continuing to rely on the `UserData` (encryption keys, `user_centric_signup` flag, `id_commitment`) captured at the single validation point [4](#0-3) . There is no second call to `backend::user_status::request` (or any other backend check) between the initial QR validation and the final `enroll_user`/upload step to confirm the user's status (e.g., not blocked, not already enrolled, fraud flags not raised server-side, session not revoked) is still current at completion time.

### Impact Explanation
This mirrors the report's root cause: an authorization decision made at one point in time is used to authorize an action that completes at a materially later point in time, with no deadline/expiry to bound that gap. If the backend invalidates a user's session between the initial QR check and signup completion (e.g., session revoked, fraud flag raised, user already completed signup on another orb, distributor/operator status revoked), `orb-core` has no mechanism to detect this and will still complete the biometric enrollment and upload using the stale authorization, potentially resulting in an unauthorized or otherwise-invalidated signup being finalized. This falls within the accepted "unauthorized or misattributed signup" impact category.

### Likelihood Explanation
The likelihood is moderate: it requires a real-world race between backend-side invalidation (revocation, fraud detection, duplicate signup detection) and the orb's local pipeline duration. Given that biometric capture + pipeline + fraud detection + PCP building + upload can span a meaningful duration, and there is no re-validation call anywhere in that path, this window is real and reachable through the normal, unprivileged signup flow — the same mempool/timing-gap mechanic as the original report, just mapped from a swap's `deadline` to a signup's authorization freshness.

### Recommendation
Introduce a bounded "authorization validity window" analogous to a `deadline`: re-invoke `backend::user_status::request` (or a lightweight status re-check) immediately before the point of no return (e.g., before `enroll_user`/before final PCP upload), and reject/abort the signup if the elapsed time since the initial validation exceeds a configurable threshold (similar to `operator_qr_expiration_time`), or if the re-check indicates the user is no longer valid.

### Proof of Concept
Not applicable — as with the original report, the issue is structural: `do_signup`'s single-point validation combined with the absence of any expiry/re-check between `verify_user_qr_code` and the final enrollment/upload steps is directly visible in `src/plans/mod.rs` lines 553-663 and `src/backend/user_status.rs` lines 145-178, with no code path performing a second freshness check.

                        qr_code: operator_qr_code,

                };
