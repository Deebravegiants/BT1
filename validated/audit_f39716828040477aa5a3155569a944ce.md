Audit Report

## Title
Silent, untrapped fund loss via `TransactAsset::transfer_asset` best-effort restore fallback - ([File: polkadot/xcm/xcm-executor/src/traits/transact_asset.rs])

## Summary
The default `transfer_asset` implementation withdraws from `from`, then deposits to `to`; if that deposit fails, it attempts a best-effort restore back to `from`, and if that restore also fails, the leftover `AssetsInHolding`/`Credit` is discarded via `let _ = ...` with no `AssetTrap` recording. This differs from the holding-based `DepositAsset` instruction path, which the codebase explicitly hardened to trap any leftover assets via `Config::AssetTrap::drop_assets`.

## Finding Description
`TransactAsset::transfer_asset`'s default implementation falls back to withdraw/deposit whenever `internal_transfer_asset` returns `AssetNotFound` or `Unimplemented`: [1](#0-0) 

On deposit failure, it discards the outcome of the second ("best effort") restore attempt with `let _ = Self::deposit_asset(unspent, from, Some(context));`, meaning any leftover credit is silently dropped and never routed to `self.holding` or `AssetTrap::drop_assets`.

`FungibleMutateAdapter` is documented to work "for everything but transfers" and has no `internal_transfer_asset` override, so it inherits the trait's default `Err(XcmError::Unimplemented)`, which forces `transfer_asset` calls through this fallback path: [2](#0-1) 

By contrast, `FungibleAdapter` composes `FungibleTransferAdapter::internal_transfer_asset`, which performs an atomic `Fungible::transfer` that does not debit `from` unless the credit to `to` succeeds, returning a concrete `FailedToTransactAsset` error rather than `AssetNotFound`/`Unimplemented`: [3](#0-2) [4](#0-3) 

This means the standard, recommended `FungibleAdapter` configuration never triggers the vulnerable fallback in `transfer_asset` — the exposure exists only for standalone `FungibleMutateAdapter` deployments or any third-party `TransactAsset` implementation without an atomic `internal_transfer_asset`. `deposit_asset` itself correctly returns unspent funds on failure via `Fungible::resolve`'s `Err(unspent)` path: [5](#0-4) 

so the loss occurs entirely in the caller (`transfer_asset`) discarding the second attempt's result rather than in `deposit_asset` destroying value directly.

I was not able to fully verify from the index whether `fungible::Credit`'s `Drop` implementation actually decrements `TotalIssuance` on discard (the `imbalance.rs` file's `Drop`/`drop` definitions were located but their content could not be retrieved within the available iterations), so I cannot independently confirm the claim's specific mechanism of "TotalIssuance decreases via Credit's Drop impl." This is a secondary detail, however; the core claim — that the leftover holding/credit is discarded without being trapped — is confirmed directly from the code.

## Impact Explanation
Where the vulnerable configuration is used (a standalone `FungibleMutateAdapter`, or any custom `TransactAsset` relying on the default `transfer_asset` without an atomic `internal_transfer_asset`), funds withdrawn from `from` during a `TransferAsset` XCM instruction can be lost with no `AssetsTrapped` record and no way to reclaim via `ClaimAsset`, since the leftover credit was never placed in `self.holding`. This is a genuine violation of the intended invariant that unprivileged flows should not silently destroy value without an accounting/trap trail.

## Likelihood Explanation
The exploit requires (1) a runtime configuring `AssetTransactor` such that `internal_transfer_asset` is unimplemented/returns `AssetNotFound` (not true for the standard, most commonly documented `FungibleAdapter`/`FungibleTransferAdapter` pairing), and (2) precise control of the sender's post-withdrawal balance and the beneficiary's deposit requirements to make both the primary deposit and the restore deposit fail (e.g., dropping below Existential Deposit). This is deterministic and attacker-triggerable via an unprivileged `TransferAsset` XCM instruction once the configuration precondition holds, but the configuration precondition is a real gating factor that limits applicability primarily to non-standard/custom transactor setups rather than the default recommended configuration.

## Recommendation
In the default `transfer_asset` implementation, do not discard the result of the best-effort restore deposit. If the restore-to-`from` deposit also fails, propagate the leftover `AssetsInHolding` back to the caller (e.g., as part of the `Err` variant) so the XCM executor can route it into `self.holding`/trap it via `Config::AssetTrap::drop_assets`, consistent with the guarantee already provided for the holding-based `DepositAsset` path.

## Proof of Concept
1. Configure `AssetTransactor = FungibleMutateAdapter<...>` (no atomic `internal_transfer_asset`) in the XCM executor test harness.
2. Fund `SENDER` with exactly the Existential Deposit; fund `RECIPIENT` with 0.
3. Execute an XCM message containing `TransferAsset { assets: (Here, amount), beneficiary: RECIPIENT }` from `SENDER`, choosing `amount` such that both the beneficiary's deposit and the restore-to-`SENDER` deposit fail (i.e., below ED after withdrawal).
4. Assert: `SENDER`'s balance decreased, `RECIPIENT` received nothing, and no `AssetsTrapped` event / `AssetTrap::drop_assets` record exists for the withdrawn amount — demonstrating the funds vanished without any trap or claim record, unlike equivalent failure paths tested for the holding-based `DepositAsset` instruction (e.g. `deposit_with_retry.rs`, `initiate_transfer.rs`).

	fn transfer_asset(
		asset: &Asset,
		from: &Location,
		to: &Location,
		context: &XcmContext,
	) -> Result<Asset, XcmError> {
		match Self::internal_transfer_asset(asset, from, to, context) {
			Err(XcmError::AssetNotFound | XcmError::Unimplemented) => {
				let credit = Self::withdraw_asset(asset, from, Some(context))?;
				Self::deposit_asset(credit, to, Some(context)).map_err(|(unspent, error)| {
					// best effort try to return the assets to original owner
					let _ = Self::deposit_asset(unspent, from, Some(context));
					error
				})?;
				Ok(asset.clone())
			},
			result => result,
		}
	}
