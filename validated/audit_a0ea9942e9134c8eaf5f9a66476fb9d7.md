## Title
Unchecked `copy_from_slice` on attacker-supplied BEEFY vote signature causes runtime panic (DoS) - ([File: evm/rust/src/conversions.rs])

## Summary
The `submit_proof` extrinsic of the `beefy-consensus-proofs` pallet accepts an ABI-encoded `BeefyConsensusProof` from any signed (unprivileged) account and converts it into the internal `ConsensusMessage` type via a chain of `From` impls in `evm/rust/src/conversions.rs`. One of those impls copies the ABI-decoded `Vote.signature` (an arbitrary-length Solidity `bytes` field) into a fixed `[u8; 65]` array with `copy_from_slice` without first checking the length, which panics whenever the length is not exactly 65. This is the same bug class as CVE-2017-12783 (assert/panic fault triggered by malformed, attacker-controlled input during parsing), except here the crash happens inside the Hyperbridge runtime's extrinsic-dispatch path instead of an EBML/MKV parser.

## Finding Description
`verify_and_apply` in `modules/pallets/beefy-consensus-proofs/src/lib.rs` reads the first byte of the submitted proof to pick a proof type and, for `PROOF_TYPE_NAIVE`, ABI-decodes the remaining bytes into `ismp_abi::ecdsa_beefy::BeefyConsensusProof`, then calls `.into()` to obtain a `beefy_verifier_primitives::ConsensusMessage`: [1](#0-0) 

That `.into()` call routes through `From<BeefyConsensusProof> for ConsensusMessage` → `From<RelayChainProof> for MmrProof` → `value.signedCommitment.votes.into_iter().map(Into::into).collect()`: [2](#0-1) 

which in turn calls `From<Vote> for SignatureWithAuthorityIndex`: [3](#0-2) 

`Vote.signature` is decoded from ABI as a dynamically-sized Solidity `bytes`, so it can be any length the caller chooses — there is no protocol-level constraint forcing it to be 65 bytes before this point. `signature.copy_from_slice(&sig_bytes)` panics immediately if `sig_bytes.len() != 65` (a length mismatch panic, analogous to `ReadDataFloat`'s assert fault on malformed input). Because this executes as part of dispatching a normal signed extrinsic (`submit_proof`), the panic aborts execution inside the runtime for that transaction/block, which the codebase elsewhere treats as an unacceptable outcome for consensus proofs — the sibling BEEFY/GRANDPA/sync-committee/Pharos verifiers in this same repo have all been hardened specifically to replace `.expect`/`copy_from_slice`-style panics with typed errors precisely because they are reachable from unsigned/permissionless consensus messages, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

This one conversion path in `evm/rust/src/conversions.rs` was missed.

## Impact Explanation
`submit_proof` is a normal signed extrinsic (confirmed by the pallet's own simtest submitting it with a regular `Keyring::Bob` signer, not a privileged account): [7](#0-6) 

Any unprivileged account can submit a `PROOF_TYPE_NAIVE`-prefixed payload whose `RelayChainProof.signedCommitment.votes[i].signature` is not exactly 65 bytes. The resulting panic occurs during dispatch of a signed extrinsic that has already passed the `BoundedVec` size check, so it is not filtered by the txpool. A wasm/native runtime panic during block execution is a critical liveness fault for the chain executing it — this matches the "route unable to deliver messages" impact class (BEEFY consensus updates, which gate delivery of every relayed message/proof from the relay chain, could no longer be processed if this path is exercised during block authoring/import).

## Likelihood Explanation
High: constructing the malformed `Vote.signature` requires no special knowledge beyond crafting an ABI-encoded `BeefyConsensusProof` with a `bytes signature` field of any length other than 65, wrapped with the `PROOF_TYPE_NAIVE` byte prefix, and calling the public `submit_proof` extrinsic.

## Recommendation
In `evm/rust/src/conversions.rs`, replace the panicking `From<Vote> for SignatureWithAuthorityIndex` conversion with a fallible `TryFrom` that validates `sig_bytes.len() == 65` and propagates a typed error (mirroring the `AbiDecodeFailed`/`VerificationFailed` error handling already used elsewhere in `verify_and_apply`), instead of calling `copy_from_slice` on unchecked, attacker-controlled length data.

## Proof of Concept
1. Craft a `BeefyConsensusProof` ABI payload where `relay.signedCommitment.votes[0].signature` is, e.g., 64 or 66 bytes instead of 65.
2. Prefix the ABI bytes with `PROOF_TYPE_NAIVE` (0) to form the full proof blob.
3. Submit it as any signed account via `BeefyConsensusProofs::submit_proof(proof)`.
4. `verify_and_apply` → `abi_decode_params` succeeds (Solidity `bytes` has no fixed-length constraint) → `.into()` → `From<Vote> for SignatureWithAuthorityIndex::signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, aborting execution of the extrinsic/block.
