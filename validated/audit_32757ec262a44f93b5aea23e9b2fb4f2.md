### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The HMAC signable string is defined as just `@raw_body` [2](#0-1) , while the `shop` identity that is handed to the app's webhook handler is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [3](#0-2) . The equality the gem implicitly assumes — `shop-domain header == shop that produced the signed body` — is never enforced.

### Finding Description
`Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` value, both supplied by the `VerifiableQuery` implementation [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only the raw JSON body, and `hmac` is derived from the `hmac-sha256` header [5](#0-4) ; the `shop`, `topic`, `webhook-id`, and `api-version` headers are entirely outside the signed content [6](#0-5) .

`Registry.process` treats a passing HMAC check as proof of authenticity for the whole request, then forwards `request.shop` — taken straight from the header — into `WebhookMetadata`, which is the only shop identity the app-provided handler receives [1](#0-0) [7](#0-6) .

All shops installing the same app share one `client_secret`/`api_secret_key`, and that same secret is used to sign every shop's webhooks [8](#0-7) . This means the HMAC on shop A's genuine webhook is also a valid HMAC for the identical body delivered under a forged `shopify-shop-domain` header claiming to be shop B — the signature says nothing about which shop it came from, only that *some* installed shop produced this body with the shared secret.

### Impact Explanation
A user who controls shop A (a legitimate, currently-installed tenant — an "unprivileged" actor relative to any other tenant) can capture one of their own genuine webhook deliveries (body + valid `hmac-sha256` value) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to shop B's domain. `Registry.process` will accept it as authentic (the body/HMAC pair is genuinely valid) and dispatch it to the handler tagged with shop B's identity [9](#0-8) . Any handler logic keyed off `WebhookMetadata#shop` (e.g., updating shop B's stored order/inventory/customer state, or triggering shop-scoped side effects) is then executed against the wrong tenant using attacker-supplied body content — a cross-tenant data integrity breach with no privileged credentials required beyond being any one of the app's installing merchants.

Note: `Utils::ShopValidator.sanitize!` exists in the gem, but it only normalizes/validates that a domain string looks like a trusted Shopify domain; it is never called by `Registry.process` or `Webhooks::Request`, and even if it were, it cannot detect that the header's shop doesn't match the shop that actually produced the signed body, because that binding does not exist anywhere in the signed content [10](#0-9) .

### Likelihood Explanation
Requires only that the attacker be a merchant who has installed the app (no access to `api_secret_key`, no stolen access token, and no privileged Shopify account) — well within the "unprivileged internet user" threat model for a multi-tenant app. Capturing your own webhook body/HMAC and replaying it with a modified header is trivial once the app's public webhook endpoint URL is known (it is typically public and documented in the app's configuration).

### Recommendation
Bind the shop identity into the signed content, or otherwise cryptographically verify it, before trusting `request.shop`:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) in the HMAC signable string, matching them against the actual signed payload, or
- Have `Registry.process` cross-check `request.shop` against an out-of-band trusted source (e.g., look up the webhook subscription/shop pairing via `webhook-id`) rather than trusting the header verbatim, or
- At minimum, document prominently that `request.shop` is unauthenticated header data and must not be trusted for tenant attribution without additional verification by the host application.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; Shopify sends a real webhook: body `{"id":123}`, header `x-shopify-shop-domain: shop-a.myshopify.com`, and a valid `x-shopify-hmac-sha256` computed over the body with the app's shared `api_secret_key`.
2. Attacker (owner/admin of shop-a) intercepts this legitimate delivery and captures the raw body and the `hmac-sha256` value.
3. Attacker POSTs the identical body and `hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC over the (unchanged) raw body and it matches — validation passes [11](#0-10) .
5. The handler is invoked with `WebhookMetadata(shop: "shop-b.myshopify.com", body: {"id":123}, ...)`, causing shop-a's data to be processed and attributed to shop-b.
