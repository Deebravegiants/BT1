### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant metadata spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates the body's HMAC and then dispatches the handler using these unauthenticated header values as the tenant identity (`shop`) and event type (`topic`). This breaks the identity binding "shop authenticated == shop acted upon", since the value verified (body bytes) is disjoint from the values trusted for tenant routing (headers).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are parsed straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body), then immediately trusts `request.topic` and `request.shop` to route to a handler and construct `WebhookMetadata`: [3](#0-2) 

`WebhookMetadata` carries `shop` as a plain, unverified field that handlers use to attribute the payload to a tenant: [4](#0-3) 

`HmacValidator.validate` computes/compares HMAC purely from `verifiable_query.to_signable_string`, i.e., only the body for webhooks: [5](#0-4) 

This is the same bug class as the referenced report: a value that downstream code treats as authoritative for a security decision (asset timestamp in the Ammplify bug; here, `shop`/`topic`) is derived from data that was not covered by the verification step actually performed (HMAC over `raw_body` only). The binding the gem should enforce is:

`verified(hmac_signed_bytes) == trusted(shop, topic)`

but the gem instead enforces only `verified(raw_body)` while `trusted(shop, topic)` comes from a disjoint, attacker-influenced source (HTTP headers), which any client sending the POST request controls.

Because the shared `client_secret` used to compute webhook HMACs is the same for every shop that installs a given app (not shop-specific), a HMAC that is valid for a body delivered to shop A's webhook subscription is equally valid ciphertext-wise for that same body regardless of which `shop-domain`/`topic` header accompanies it. An attacker who legitimately operates their own store (shop A) and has installed the target app can:
1. Trigger a real webhook so Shopify sends a validly-HMAC-signed body to the app's public webhook endpoint (the attacker can capture this, e.g., by installing the app on their own dev/test store and observing the delivered `raw_body` + `X-Shopify-Hmac-Sha256`).
2. Replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint, but with forged `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers naming a different (victim) shop and a different topic.
3. `HmacValidator.validate` succeeds (it only re-derives HMAC over `raw_body` with the app's `client_secret`, which the attacker never needed to know), and `Registry.process` dispatches the handler with `shop: <victim>, topic: <attacker-chosen>, body: <attacker's own real payload>`.

The handler now processes attacker-supplied body content under the identity of a different, victim tenant, e.g. a host application that uses `data.shop` to look up which merchant's database row to update, or uses `data.topic` to decide "customers/redact" vs. some benign topic. This crosses the tenant boundary that the gem is documented to protect through HMAC verification.

### Impact Explanation
This qualifies as **Critical - cross-tenant access**: the webhook verification primitive (`HmacValidator`/`Registry.process`) is the gem's documented mechanism for asserting "this payload genuinely originates for shop X, topic Y", yet the values actually used to key tenant-scoped side effects (`shop`, `topic`, `webhook_id`) are excluded from the signed bytes. Any application relying on the gem's built-in `Registry.process`/`WebhookMetadata.shop` for tenant attribution (as documented) inherits data that can be forged by any user who can obtain one valid signed body/HMAC pair for their own shop (trivially available to any app installer) and replay it with spoofed headers against a shared endpoint.

### Likelihood Explanation
Likelihood is high for apps that install on many shops (the common case) because:
- The `client_secret`/HMAC key is identical for every shop, so a signed body captured from any shop is valid ciphertext regardless of destination.
- Obtaining a legitimately-signed body/HMAC pair requires nothing more than installing the app on an attacker-controlled store and receiving one real webhook, and the webhook receiving endpoint is by design internet-reachable.
- No `api_secret_key`, access token, or privileged access is required — only the gem's own webhook verification path is used against itself.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC validation, or otherwise cryptographically bind them to the body (e.g., have `to_signable_string` concatenate a canonical representation of shop+topic+body, matching what Shopify actually signs if it does, or validate the header values against a stored subscription record keyed by webhook_id before trusting them). At minimum, document that `Request#shop`/`Request#topic` are unauthenticated header values and must not be used for tenant-scoped authorization decisions without independent verification (e.g., cross-checking `shop` against the caller's own recorded webhook subscription for that specific `webhook_id`).

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Step 1: Attacker triggers/receives a real webhook and captures body + valid HMAC
raw_body = capture_from_own_shop # e.g. '{"id":1,"note":"attacker payload"}'
valid_hmac_b64 = capture_from_own_shop_header # X-Shopify-Hmac-Sha256

# Step 2: Attacker replays the identical body+hmac to the app's public webhook
# endpoint but spoofs the shop-domain/topic headers to target another tenant.
forged_headers = {
  "x-shopify-topic"        => "customers/redact",       # attacker-chosen topic
  "x-shopify-hmac-sha256"  => valid_hmac_b64,             # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com" # forged tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds because it only checks raw_body,
#    and the handler is invoked with shop: "victim-shop.myshopify.com",
#    topic: "customers/redact", body: attacker-controlled JSON.
