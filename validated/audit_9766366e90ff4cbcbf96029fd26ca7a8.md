This confirms the vulnerability contrast: `AuthQuery#to_signable_string` explicitly includes `shop` in the signed payload (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`), but `Webhooks::Request#to_signable_string` only returns `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), excluding the `shop` header entirely from the HMAC-covered bytes, while `request.shop` (from `x-shopify-shop-domain` header) is still trusted downstream in `Registry.process` to build `WebhookMetadata` used by app-level tenant routing.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `x-shopify-shop-domain` header from the bytes that are HMAC-verified, yet `Registry.process` trusts `request.shop` unconditionally to attribute the webhook payload to a tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns `@raw_body` only. The `shop` accessor is derived independently, straight from an HTTP header, and is not part of the signed bytes: [2](#0-1) 
`HmacValidator.validate` verifies the HMAC strictly against `verifiable_query.to_signable_string`: [3](#0-2) 
Because `to_signable_string` omits `shop`, a valid HMAC only proves the *body* was produced by an entity holding `Context.api_secret_key` — it proves nothing about which shop the header claims to be from. `Registry.process` nonetheless treats the header-derived `request.shop` as authentic and forwards it straight into the handler: [4](#0-3) 

This is exactly the bug class from the report generalized to this gem: a field (`shop`) that is *acted on* (used to select/attribute tenant data in the handler) is *not covered by the binding check* (the HMAC). Contrast with `Auth::Oauth::AuthQuery`, where the equivalent `shop` field is explicitly included in the signed string: [5](#0-4) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop authenticated by HMAC` ≠ `shop the webhook handler acts on` — the latter is taken from an unauthenticated header, while only the raw body is authenticated.

### Impact Explanation
Since `Context.api_secret_key` is shared across all shops installed on a given app (it is the app's client secret, not a per-shop secret), any merchant that has installed the app can obtain a validly-HMAC-signed webhook body (e.g., by triggering an event on their own store). Because the signature covers only the body, that exact `(body, hmac)` pair remains valid regardless of which `x-shopify-shop-domain` header accompanies it. An attacker who controls the delivery endpoint's request (or can otherwise submit HTTP requests hitting the app's webhook receiver with attacker-controlled headers) can replay the captured body with a different `shop-domain` header to make `Registry.process` invoke the app's handler with `shop: "victim-shop.myshopify.com"` while the payload actually originated for the attacker's own shop. If the host application relies on `WebhookMetadata#shop` to select which tenant's database rows or per-shop side effects the payload applies to, this results in cross-tenant data confusion — writing or exposing data under another shop's tenant context.

### Likelihood Explanation
This requires the attacker to install the app on their own store (any unprivileged merchant can do this for public apps) to obtain a legitimate signed webhook body, and to have control over the raw headers reaching the app's webhook endpoint (e.g., by directly POSTing to the app's public webhook URL, which is typically an unauthenticated internet-facing endpoint). No access to `api_secret_key`, access tokens, or privileged accounts is required — only the ability to send crafted HTTP requests, which matches an "unprivileged internet user" threat model.

### Recommendation
Include `shop` (and ideally `topic`) in the HMAC-signed bytes verified for webhook requests, or otherwise cryptographically bind the shop-domain header to the signed body before it is trusted in `Registry.process`. At minimum, downstream consumers of `WebhookMetadata#shop` should be documented as receiving an unauthenticated value, and the gem should provide a signed alternative.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; attacker triggers any webhook event, capturing the real delivered request: body `B`, and header `x-shopify-hmac-sha256` computed as `HMAC(api_secret_key, B)`.
2. Attacker sends a new POST request directly to the app's webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `HmacValidator.validate` calls `to_signable_string`, which returns only `B`, so the computed HMAC matches and validation succeeds: [6](#0-5) 
4. `Registry.process` proceeds and calls the registered handler with `shop: "victim-shop.myshopify.com"` even though the payload content was generated by the attacker's own shop, demonstrating the header is trusted without being bound to the HMAC.
