### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string`. For `Webhooks::Request`, that signable string is only the raw HTTP body — never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Those header-derived values are nonetheless what gets handed, unauthenticated, to the host application's handler as the identity of the tenant (`shop`) the event belongs to.

### Finding Description
The binding that should hold is: **`shop` (and `topic`/`webhook_id`) delivered to the handler == `shop` (and `topic`/`webhook_id`) that Shopify actually signed for this event.**

- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field via `OpenSSL.secure_compare`. [1](#0-0) 
- For webhooks, `to_signable_string` returns only `@raw_body`; it does not fold in `shop`, `topic`, `webhook_id`, or `api_version`, all of which are read straight from attacker-controllable HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) with no cross-check against the signed body. [2](#0-1) 
- `Registry.process` gates only on the HMAC check, then immediately constructs `WebhookMetadata` from `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` — none of which were part of what was verified — and dispatches it to the app's handler. [3](#0-2) 
- `WebhookMetadata.shop` is a plain, unauthenticated `String` field that becomes the tenant identity the host application acts on. [4](#0-3) 

Because the `api_secret_key` (the app's client secret) is the same HMAC key for *every* shop that has installed the app, an attacker who controls one shop (their own free/dev store, installed as an unprivileged app user) can:
1. Trigger a real event on their own store to receive a legitimately Shopify-signed webhook (valid `hmac-sha256` header over the raw body, generated with the app's shared `api_secret_key`).
2. Replay that exact `raw_body` + valid `hmac-sha256` value to the app's webhook endpoint, but swap the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header to name a *different, victim* shop that also has the app installed.
3. `HmacValidator.validate` still succeeds because it only checks the raw body against the shared secret; `Registry.process` then dispatches a `WebhookMetadata` claiming the event came from the victim shop.

Any host application logic keyed off `WebhookMetadata#shop` (e.g., "look up victim shop's record and update it using this body", "disable subscription for shop X", GDPR/redact handling keyed by shop) is confused into acting on the wrong tenant using attacker-controlled body content.

### Impact Explanation
This crosses a tenant boundary using only a webhook payload the attacker can legitimately obtain from their own store — no `api_secret_key`, access token, or privileged account is required, satisfying the Critical "cross-tenant access" bar. The forged event is attributed to a shop the attacker does not control, and its (attacker-chosen, since it's from their own store) body content is delivered as if authoritative for that other shop.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the standard SaaS model) and trusts `WebhookMetadata#shop`/`topic`/`webhook_id` for tenant or event-type dispatch, which is exactly the intended usage pattern the gem promotes (`handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`). All the attacker needs is one of their own valid installations of the target app to harvest a signed body/HMAC pair, then a single HTTP request to the app's webhook endpoint with modified headers.

### Recommendation
Bind the identity fields into the signed material instead of trusting bare headers:
- Include `shop`, `topic`, and `webhook_id` (not just the raw body) in `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind them (e.g., derive/verify them from a signed envelope rather than independent headers).
- Alternatively/additionally, require and enforce that `request.shop` matches a shop for which the app holds an active session/webhook registration before dispatching to the handler, so a replayed body cannot be re-attributed to an arbitrary installed shop.
- Document clearly (and enforce in code) that `WebhookMetadata#shop` must be treated as unauthenticated unless the gem itself binds it into the HMAC computation.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com (a legitimate install of the target app)
# and captures a real, Shopify-signed webhook delivery:
raw_body       = '{"id":123,"note":"attacker controlled content"}'
valid_hmac     = "<hmac-sha256 header value Shopify actually sent for shop-a>"

# Attacker resends the exact same body/hmac but swaps the shop header
# to a different shop (shop-b.myshopify.com) that also installed the app:
forged_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,        # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id"  => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/HMAC pair is legitimate)
# => handler.handle(data: WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: "orders/create", body: ..., ...))
# The app's handler now processes attacker-controlled data as if it belongs to shop-b.
``` [5](#0-4) [6](#0-5)
