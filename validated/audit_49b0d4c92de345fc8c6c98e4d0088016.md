Based on my research, I found a strong analog to the CVE-2017-7598 divide-by-zero bug class within the allowed scope: swap math functions in `program/src/math.rs`.

### Title
Unchecked division in AMM swap/exchange math can panic and permanently halt pool operations - (File: program/src/math.rs)

### Summary
`Calculator::swap_token_amount_base_in`, `swap_token_amount_base_out`, `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin`, and `InvariantPool::exchange_pool_to_token`/`exchange_token_to_pool` all perform `.checked_div(...).unwrap()` or `.checked_ceil_div(...).unwrap()` on pool-state-derived denominators without validating the denominator is non-zero before the call.

### Finding Description
The core constant-product swap formulas compute a denominator from live pool reserves (`total_coin_without_take_pnl`, `total_pc_without_take_pnl`) and then immediately `.unwrap()` the result of `checked_div`/`checked_ceil_div`: [1](#0-0) [2](#0-1) 

Similarly, the LP token conversion helpers divide by `self.token_coin`, `self.token_pc`, or `self.token_total` without a zero check: [3](#0-2) [4](#0-3) 

These denominators originate from on-chain vault balances read directly from attacker-influenced state (`amm_pc_vault.amount`, `amm_coin_vault.amount`) via `calc_total_without_take_pnl_no_orderbook`, which itself is a `checked_sub` that can legitimately return `0` for one side if `need_take_pnl_pc`/`need_take_pnl_coin` equals the vault balance: [5](#0-4) 

This value flows unchanged into the swap instructions: [6](#0-5) [7](#0-6) 

For `swap_token_amount_base_out`'s `Coin2PC` branch, the denominator is `total_pc_without_take_pnl.checked_sub(amount_out)`; if a caller requests `amount_out` equal to `total_pc_without_take_pnl`, the subtraction yields zero and the subsequent `checked_ceil_div` on zero returns `None`, causing an `unwrap()` panic instead of a graceful error: [8](#0-7) 

While `process_swap_base_out` does check `swap.amount_out >= total_pc_without_take_pnl` and rejects the transaction with `InsufficientFunds` before the transfer, this check happens **after** the division already executed: [9](#0-8) 

That is, `Calculator::swap_token_amount_base_out` (line 2172) is invoked with attacker-chosen `swap.amount_out` *before* the `amount_out >= total_pc_without_take_pnl` guard at line 2214/2237 executes. If `amount_out == total_pc_without_take_pnl`, the denominator inside `swap_token_amount_base_out`'s `Coin2PC`/`PC2Coin` branch becomes zero and `checked_ceil_div(...).unwrap()` panics before the guard is ever reached.

### Impact Explanation
A panic in a Solana on-chain program causes the transaction to abort, but more importantly this is a reachable, attacker-controlled divide-by-zero triggered purely by choosing `amount_out` equal to the pool's available reserve of the destination token — no privileged signer or special account is required, matching the CVE's "crafted input causes divide-by-zero crash" bug class. Repeated exploitation forces every transaction attempting this boundary condition to fail deterministically, and in low-liquidity pools (especially post-`WithdrawPnl`, where `need_take_pnl_pc`/`coin` can approach vault balances) this is trivially reachable, effectively creating a denial-of-service vector against the swap path for that specific reserve state.

### Likelihood Explanation
High for the specific edge case: any unprivileged user submitting a single `SwapBaseOut`/`SwapBaseOutV2` transaction with `amount_out` set exactly to the current `total_pc_without_take_pnl` (or `total_coin_without_take_pnl` for the other direction) — values that are readable on-chain before submission — triggers the panic deterministically.

### Recommendation
Move the `amount_out >= total_*_without_take_pnl` bounds check in `process_swap_base_out`/`process_swap_base_out_v2` to execute **before** calling `Calculator::swap_token_amount_base_out`, and replace all `.checked_div(...).unwrap()` / `.checked_ceil_div(...).unwrap()` calls in `math.rs` with proper `Result`-propagating error handling (returning an `AmmError` such as `AmmError::ZeroDenominator` or similar) instead of panicking.

### Proof of Concept
1. Identify a pool with `total_pc_without_take_pnl = P` (readable via `amm_pc_vault` balance minus `state_data.need_take_pnl_pc`).
2. Submit `SwapBaseOut` with `swap_direction = Coin2PC` and `swap.amount_out = P`.
3. Execution reaches `Calculator::swap_token_amount_base_out` at `program/src/processor.rs:2172` before the `amount_out >= total_pc_without_take_pnl` check at line 2214.
4. Inside `swap_token_amount_base_out`, `denominator = total_pc_without_take_pnl.checked_sub(amount_out) = 0`, then `checked_ceil_div(0).unwrap()` returns `None.unwrap()`, panicking the program.

        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
