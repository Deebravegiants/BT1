### Title
Webhook Shop/Topic Spoofing via HMAC Signature Not Covering Identity Headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw request body only, while the shop, topic, webhook-id, and api-version identity fields — trusted and forwarded to app webhook handlers — are taken from unauthenticated HTTP headers that are never part of the signed content. This breaks the equality that should hold between "bytes verified by HMAC" and "bytes used to attribute the request to a tenant (shop)."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read directly from HTTP headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` to route and construct the metadata handed to the app's webhook handler: [4](#0-3) 

Because `shop-domain` (and `topic`, `webhook-id`, `api-version`) headers are excluded from the signable string, any request whose body+HMAC pair is valid for the configured `api_secret_key` will pass validation regardless of what `shop-domain` header accompanies it. The binding that should hold is:
`HMAC_valid(body, secret) == true` should imply `shop header is authentic for that body`, but the code only proves `HMAC_valid(body, secret) == true`, with the `shop` header entirely uncorrelated to that proof.

### Impact Explanation
A merchant who has legitimately installed the app receives real, validly-signed webhook deliveries for their own shop (a normal, unprivileged capability — any shop owner can trigger events like `products/create` and observe the resulting signed webhook body/HMAC that Shopify sends to the app's public webhook endpoint). Because the header carrying shop identity is not part of the signed payload, that same attacker can re-POST the identical `(raw_body, hmac-sha256)` pair directly to the app's endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim's shop). `HmacValidator.validate` will still succeed, since it only checks the body against the secret. `Registry.process` then dispatches to the app's handler with `WebhookMetadata` carrying the attacker-chosen `shop`, causing the app to process attacker-controlled webhook content under a different tenant's identity — a cross-tenant confusion of exactly the class called out as Critical impact (cross-tenant access) if the host application uses `data.shop` from `WebhookMetadata` to key session lookup, data writes, or trust decisions (which is the gem's documented usage pattern).

### Likelihood Explanation
Exploitation requires no privileged credentials, no access token, and no TLS interception — only that the attacker be a merchant who has installed the app (an "unprivileged internet user" relative to other tenants) and can freely POST to the app's public webhook endpoint with a header set of their choosing. The only prerequisite is a single legitimately observed `(body, hmac)` pair from their own shop, which is trivially obtainable by performing any action that triggers a subscribed webhook topic.

### Recommendation
Bind the shop (and ideally topic/webhook-id/api-version) into the value that is HMAC-verified, or independently verify the `shop-domain` header against a known/authorized shop for this installation before trusting it (e.g., cross-check against session storage keyed by an already-authenticated identifier, not solely by the unauthenticated header). At minimum, `to_signable_string` should not be usable to authenticate a body for an arbitrary shop; the header-derived `shop` must not be trusted as tenant identity unless it is itself covered by the HMAC or otherwise verified.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and subscribes to `products/create`.
2. Attacker creates a product in their own store, causing Shopify to POST a webhook to the app's endpoint with a body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` (they own this shop and can log/inspect their own inbound requests, or point the webhook subscription temporarily at a proxy they control) and re-sends a new POST directly to the app's public webhook endpoint with the same `B` and `H`, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `B` only and it matches `H`, so validation passes.
5. `Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim.myshopify.com"`, causing the app to act on attacker-supplied content under the victim tenant's identity.
