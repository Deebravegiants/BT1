## Title
Unauthenticated resource-exhaustion DoS: `pallet-state-coprocessor::handle_get_requests` runs full Merkle/state-proof verification for every `GetRequest` in a batch before the bandwidth gate ever checks allowance — (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
This is analogous to the Keycloak `CVE-2026-4634` bug class (CWE-1050): an unauthenticated caller supplies an attacker-controlled, unbounded-size field to a public endpoint, and the server performs expensive processing on that field *before* any authorization/quota check that would otherwise reject the request cheaply. Here, the "scope" analog is the `keys` field of each `GetRequest` in a `GetRequestsWithProof` batch submitted to the unsigned, permissionless `handle_get_requests` extrinsic. The bandwidth gate — the only per-app authorization/anti-abuse check — is invoked *after* full Merkle-trie / state-proof verification for every request's keys, not before, contradicting the pallet's own documented invariant.

### Finding Description
`pallet-state-coprocessor::handle_get_requests` is dispatched via `Call::handle_unsigned`, which is `ensure_none`-gated (unsigned/unauthenticated) and executed for free by any relayer: [1](#0-0) 

Its `ValidateUnsigned::validate_unsigned` implementation runs `Self::handle_get_requests(message.clone())` **in full** just to decide transaction-pool validity — meaning the entire cost below is paid even for a transaction that is ultimately discarded from the mempool: [2](#0-1) 

The `Config` trait's doc comment states the intended, safe ordering explicitly:
> "Bandwidth gate that meters per-app data consumption. The coprocessor charges `max(sum(keys.len()) + context.len(), 32)` bytes per `GetRequest` against `(req.source, req.from)` before any state proof work — fails fast for apps without allowance." [3](#0-2) 

But the actual implementation in `handle_get_requests` does the opposite: it calls `dest_state_machine.verify_state_proof(&host, req.keys.clone(), ...)` for **every** `GetRequest` in the batch — the expensive per-key trie/Merkle proof verification work — and only afterward calls `BandwidthGate::try_consume`: [4](#0-3) 

The comment at line 142-144 even acknowledges this ordering was chosen deliberately ("Charged after proof verification so the value sizes are final"), but this means an app with **zero** bandwidth allowance — or a `(source, from)` pair that was never registered/allowlisted at all — still forces the coprocessor to perform full `verify_state_proof` work for an arbitrary number of `GetRequest`s, each carrying an arbitrary number of `keys` (`Vec<Vec<u8>>`), before the batch is finally rejected with `GateError::NoAllowance`.

`verify_state_proof` implementations (EVM, Substrate-EVM, Tendermint, Pharos state machines) are non-trivial: they decode the proof, hash/group storage keys per-contract, walk Merkle/trie structures, and reconstruct storage roots — proportional in cost to `keys.len()` and requiring proof bytes to match: [5](#0-4) [6](#0-5) 

None of this per-request or per-key cost is gated by anything cheap up front — there is no `keys.len()` cap, no per-request byte cap, and no bandwidth pre-check — only the expensive proof machinery runs first, then the gate check happens per-request inside the same loop that already paid for verification. This lets an unauthenticated party name arbitrary `(source, from)` pairs and arbitrary numbers of keys per request, forcing worst-case verification work on every submission, with the low-cost rejection (`NoAllowance`) coming only at the very end.

### Impact Explanation
This satisfies the "route unable to deliver messages" / availability-impact bar: a single unsigned, feeless, unauthenticated submission can force Hyperbridge validator/collator nodes to repeatedly perform expensive Merkle-proof verification (proportional to attacker-chosen `keys` count and proof size) for apps that have no bandwidth allowance at all, and this cost is paid again by every node validating the transaction in the pool (`validate_unsigned` re-runs the full handler). Submitted repeatedly and in parallel, this can degrade block production / transaction-pool throughput for the whole Hyperbridge chain — a network-reachable, unauthenticated CPU-exhaustion vector, matching CWE-1050 exactly as in the Keycloak advisory (unbounded/attacker-controlled field processed before the authorization check that would otherwise short-circuit it).

### Likelihood Explanation
High likelihood: `handle_unsigned` on `pallet-state-coprocessor` is explicitly permissionless and free-to-call by design (no fee, no signature, no pre-registered relayer requirement beyond passing proof/timestamp/dedup checks that are themselves cheap relative to trie verification). Constructing a `GetRequestsWithProof` with many `GetRequest`s each carrying many keys against an unallowanced or attacker-chosen `(source, from)` app pair requires no special access — any node with mempool connectivity can submit it, and it will be executed to completion inside `validate_unsigned` before being dropped.

### Recommendation
Move the bandwidth-gate check (or an equivalent cheap upper-bound check on `sum(keys.len()) + context.len()`) to run **before** `verify_membership`/`verify_state_proof` for each `GetRequest`, exactly as the `Config` doc comment already claims is the design. Concretely, in `handle_get_requests` (`modules/pallets/state-coprocessor/src/impls.rs`), compute and charge/check `max(sum(keys.len()) + context.len(), 32)` per request against `(req.source, req.from)` immediately after the dedup/timeout checks and before calling `dest_state_machine.verify_state_proof`. If the gate check fails, abort the batch without running any state-proof verification. Additionally consider imposing a hard cap on the number of `keys` per `GetRequest` and the number of requests per batch, independent of the bandwidth gate, so that even allowlisted/legitimate but misbehaving batches cannot trigger unbounded per-call verification cost.

### Proof of Concept
1. Do not register or fund any bandwidth allowance for an arbitrary `(source, from)` pair (or pick one that was never configured).
2. Construct a `GetRequestsWithProof` whose `requests` vector contains many `GetRequest`s, each with a large `keys: Vec<Vec<u8>>` (e.g., hundreds of 52-byte EVM storage keys) and non-trivial `context`, targeting that unallowanced `(source, from)`.
3. Attach a `source` and `response` `Proof` sized/structured to make it past the cheap pre-checks (timeout, source/dest chain match, height match, dedup) — the proof itself does not need to be valid for the resource-exhaustion effect since it must at least be well-formed enough to enter the expensive `verify_membership`/`verify_state_proof` decode/walk path; even proof rejection deep inside `verify_state_proof` occurs only after per-key work has already been performed.
4. Submit as an unsigned extrinsic calling `StateCoprocessor::handle_unsigned`.
5. Observe: `validate_unsigned` fully executes `handle_get_requests`, running `verify_membership` and `verify_state_proof` (proportional to the attacker-chosen key count) for every request in the batch, before `BandwidthGate::try_consume` is ever reached to reject the batch with `NoAllowance`. Repeating this with many such transactions in parallel demonstrates the CPU-exhaustion effect on nodes validating the transaction pool.

*Note: I was not able to fully verify runtime-level extrinsic/block-size limits that might partially bound the maximum achievable batch size in a single call (these are standard Substrate `BlockLength`/`ByteLength` limits and were outside the pallet code reviewed here); a full assessment of the practical severity ceiling would benefit from checking the configured `MaxCallSize`/block length constants in the relevant runtime crate.*

```rust
pub fn verify_state_proof<H: Keccak256 + Send + Sync>(
	keys: Vec<Vec<u8>>,
	root: H256,
	proof: &Proof,
	ismp_address: H160,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
	// Reject repeats before doing any work at all. They are already an error — repeats collapse
	// in the map returned below, so the caller's key-count check fails — but reaching that
	// check means every repeat has been verified first, and for account queries that is a
	// clone of the whole contract proof each time.
	let mut seen_keys = BTreeSet::new();
	for key in &keys {
		if !seen_keys.insert(key.as_slice()) {
			return Err(EvmStateMachineError::DuplicateKey.into());
		}
	}

	let evm_state_proof = decode_evm_state_proof(proof)?;
	let mut map = BTreeMap::new();
	let mut contract_to_keys = BTreeMap::new();
	let mut contract_account_queries = Vec::new();

	// Group keys by the contract address they belong to
	for key in keys {
		// For keys that are 52 bytes we expect the first 20 bytes to be the contract address and
		// the last 32 bytes the slot hash.
		// For keys that are 20 bytes we expect that to the
		// contract or account address.
		// For keys that are 32 bytes we expect that to be a slothash in
		// the Ismp EVM host
		let contract_address = if key.len() == 52 {
			H160::from_slice(&key[..20])
		} else if key.len() == 32 {
			ismp_address
		} else if key.len() == 20 {
			contract_account_queries.push(H160::from_slice(&key));
			continue;
		} else {
			return Err(EvmStateMachineError::UnsupportedKeyLength.into());
		};
		let entry = contract_to_keys.entry(contract_address.0.to_vec()).or_insert(vec![]);

		let slot_hash = if key.len() == 52 {
			H::keccak256(&key[20..]).0.to_vec()
		} else {
			H::keccak256(&key).0.to_vec()
		};

		entry.push((key, slot_hash));
	}

	// The storage proof must correspond exactly to the contracts a key was requested from:
	// every one covered, and nothing else. Both directions are settled here, before a single
	// entry is resolved — resolving one clones the whole contract proof and rebuilds its trie,
	// so checking as we go would let a proof padded with unrequested accounts do that work
	// before being rejected, and would make which error surfaces depend on map ordering.
	// The honest prover already emits exactly this set, deriving its map from the requested
	// keys, so nothing legitimate is turned away.
	let result = contract_to_keys
		.clone()
		.into_keys()
		.all(|contract| evm_state_proof.storage_proof.contains_key(&contract));
	if !result {
		return Err(EvmStateMachineError::IncompleteStorageProof.into());
	}

	if evm_state_proof
		.storage_proof
		.keys()
		.any(|contract| !contract_to_keys.contains_key(contract))
	{
		return Err(EvmStateMachineError::UnrequestedContractProof.into());
	}
```
