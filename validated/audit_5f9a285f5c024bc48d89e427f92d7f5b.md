### Title
Webhook HMAC only signs the body, letting attacker-controlled headers spoof shop identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts `shop`, `topic`, `webhook_id`, and `api_version` taken from HTTP headers that are **not** covered by that signature. Any actor who can obtain one validly-signed webhook body (e.g., by installing the app on their own shop) can replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header and have it accepted as authentic, because the signature check never binds the signed bytes to the identity fields the handler acts on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

All other identity-bearing fields — `shop`, `topic`, `webhook_id`, `api_version` — are read directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` performs this HMAC check and then dispatches the handler using the header-derived `request.shop`, `request.topic`, and `request.webhook_id` without any further verification that these values match the shop/topic the signed body actually originated from: [4](#0-3) 

The equality this design assumes is:
`hmac == HMAC(secret, body)` implies `shop header == originating shop` AND `topic header == originating topic`.

That implication does not hold: the HMAC only proves the *body* bytes were signed by a holder of the shared `api_secret_key` (Shopify) — it says nothing about which shop or topic header accompanies that body. Since Shopify signs webhooks for every shop and every topic using the **same** per-app `client_secret`, a valid `(body, hmac)` pair obtained from one delivery (e.g., a webhook delivered to an attacker's own shop after a normal, unprivileged app install) remains valid when replayed with a different `shop-domain` / `topic` / `webhook-id` header, because the signature never covered those fields.

### Impact Explanation
An unprivileged internet user can install the target app on a shop they control (no special credential needed — this is the normal installation flow), capture one legitimately signed webhook `(raw_body, hmac)` pair, and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to point at a victim shop. `Registry.process` will accept it as valid (HMAC passes) and invoke the registered handler with `shop: <victim>`, causing the host application to process attacker-chosen data as if it came from the victim's tenant. Depending on the handler (e.g., `app/uninstalled`, `shop/redact`, order/customer topics), this enables cross-tenant data injection/corruption — a merchant's account state being manipulated using data signed for a different shop. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only: (1) ability to install the app on any shop (open to any developer/merchant), and (2) ability to POST an HTTP request with custom headers to the app's public webhook endpoint (trivial for any internet user, since the host app must expose this endpoint unauthenticated per Shopify's webhook design). No access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Bind the signature-verified identity to the fields the handler acts on:
- Include `shop`, `topic`, and `webhook_id`/`api_version` in the signable string (or otherwise cryptographically bind them), not just the raw body, or
- Cross-check the header-provided `shop`/`topic` against values embedded in the verified body payload (where Shopify includes them), rejecting mismatches, or
- At minimum, document and enforce that consuming applications must independently confirm the `shop` header corresponds to a shop with an active registration/session before trusting webhook data for tenant-scoped operations, and consider replay protection (webhook_id de-duplication) to reduce reuse of captured payloads.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, no special privilege).
2. Shopify delivers a legitimate webhook, e.g.:
   ```
   X-Shopify-Topic: customers/data_request
   X-Shopify-Hmac-Sha256: <valid HMAC over BODY>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: BODY
   ```
3. Attacker replays the exact same `BODY` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `HmacValidator.validate` recomputes `HMAC(secret, BODY)` and it matches the replayed header — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the host app to act on `victim-shop` using attacker-controlled webhook content.
