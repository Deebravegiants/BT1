## Finding: Webhook shop identity not covered by HMAC signature — cross-tenant webhook spoofing

The BBOX exploit's root cause was a data field (price) acted on without being cryptographically bound to the authenticated state used for validation. The closest concrete analog in this gem is `ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process`, where the webhook's `shop` field is trusted for tenant attribution but is **not included in the HMAC signature**.

### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `shop` is read directly from the unauthenticated `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then passes the header-derived `shop` value straight to the registered handler. This breaks the binding `shop authenticated == shop the handler acts on`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`shop` is a plain header read, entirely outside the signed bytes: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the computed signature — it never touches `shop`: [3](#0-2) 

`Registry.process` validates the HMAC, then forwards `request.shop` (the header value) directly to the handler as the tenant identifier, without re-deriving or cross-checking it against anything cryptographically bound to the payload: [4](#0-3) 

Because the app's `client_secret` (used to compute the HMAC) is shared across **every** shop that has the app installed, any merchant who installs the app receives genuine, validly-HMAC'd webhooks for their own shop. That merchant can replay the exact same `raw_body` + `hmac` header to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop that also has the app installed. The HMAC still validates (it only covers the body), so `Registry.process` calls the handler with `shop: <victim shop>` and `body: <attacker-chosen content>` — an equality the app relies on (`hmac_valid == shop_is_authentic`) that does not actually hold.

### Impact Explanation
This is a cross-tenant integrity break: the receiving application, trusting this gem's `WebhookMetadata#shop`, will process attacker-controlled webhook payloads (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`, `shop/redact`) as if they originated from a victim tenant. Depending on how the host app models webhook shop identity for session/token lookup and side effects, this enables forged tenant events, corrupting or exfiltrating data scoped to another merchant, or triggering destructive lifecycle events (e.g., simulated uninstall/redact) against a shop the attacker doesn't control — squarely a cross-tenant access impact.

### Likelihood Explanation
Requires only that the attacker be an ordinary merchant who has installed the target app on their own store (no `api_secret_key`, access token, or privileged access needed) and that another shop using the same app is a viable target. The webhook endpoint is public-facing by design, and header spoofing on a replayed HTTP request requires no special tooling.

### Recommendation
Bind the shop identity into the material verified by the HMAC (or otherwise cryptographically authenticate the shop-to-payload relationship), and/or document/enforce that consumers must cross-check `request.shop` against their own session/shop registry rather than trusting it as authenticated purely because `HmacValidator.validate` returned true.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a genuine webhook delivery (`raw_body`, `X-Shopify-Hmac-Sha256`, topic headers).
2. Resend the identical HTTP request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request where `hmac`/`to_signable_string` are unaffected by the header change; `Utils::HmacValidator.validate(request)` returns `true`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker body>, ...)`, causing the app to act on attacker data under the victim's tenant identity.
