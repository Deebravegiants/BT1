### Title
Webhook `shop-domain` header not covered by HMAC allows cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` value it hands to the app's handler is read from an unsigned header. The equality the code implicitly relies on — "HMAC-verified sender" == "`request.shop` value passed to the handler" — does not actually hold, because the shop-domain header is not part of the signed content.

### Finding Description
`Request#hmac`/`Request#to_signable_string` derive the HMAC comparison purely from `@raw_body`: [1](#0-0) 

`Request#shop` is read from a separate, unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`), which is never mixed into the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) and then constructs the metadata passed to the app's handler directly from `request.shop`, without re-deriving or cross-checking the shop from any signed material: [3](#0-2) 

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), an HMAC computed over a given body is valid for that body regardless of which shop it was originally sent for. This breaks the implicit binding: `shop that produced a valid HMAC` ≠ `shop asserted in the `shop-domain` header and forwarded to the handler`.

### Impact Explanation
This is a cross-tenant identity-confusion primitive purely inside the gem's own webhook-processing code path (`Registry.process`), which host applications are expected to call as-is per the documented webhook usage flow. A handler that trusts `WebhookMetadata#shop` (as the library's own tests and docs assume, e.g. using it to look up the tenant's session/access token) can be made to act on data as though it came from shop B while the payload actually originated from shop A. This matches the "cross-tenant access" High-impact category, since it can cause the app to apply another merchant's webhook payload to the wrong tenant's records/session.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on their own development/trial store (a normal, unprivileged action) will receive genuinely, validly HMAC-signed webhooks from Shopify for their own shop. They can then replay that exact body with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header pointed at a victim shop to the app's public webhook endpoint. `Registry.process` performs no additional binding check between the signed body and the shop header, so the forged request passes validation.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered signable content, or have `Registry.process`/the host app cross-validate `request.shop` against an out-of-band trusted source (e.g., only accept webhooks for shops with an existing active session, and treat any topic/shop mismatch as suspect) before invoking the handler. At minimum, document prominently that `request.shop` is not authenticated by the HMAC and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`; the app registers a webhook (e.g. `orders/create`).
2. Shopify sends a legitimately signed webhook to the app for `attacker-shop.myshopify.com`, e.g.:
   - `X-Shopify-Hmac-Sha256: <valid hmac over body B>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - body `B`
3. Attacker replays the exact same body `B` and the same valid `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but changes the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this as valid; `HmacValidator.validate` succeeds because it only checks the body-derived HMAC (`lib/shopify_api/webhooks/request.rb:35-43`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data under the victim shop's identity.
