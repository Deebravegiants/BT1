### Title
Tokens transferred directly to the Liquidity Pool or Controller are permanently stranded — no rescue path exists - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The `LiquidityPool` contract custodies all market tokens and can receive arbitrary `transfer` calls to its address, and the `Controller` can similarly hold token balances during and outside of strategy flows. Neither contract, nor any `AdminOperation` in governance, exposes a function to withdraw unbooked balances. The pool only ever pays out against its internal `cash` ledger; donated or misdirected tokens inflate the physical `token.balance(pool)` without any corresponding book entry, and no entrypoint — `supply`, `borrow`, `withdraw`, `repay`, `recapitalize`, `claim_revenue`, `seize_positions`, or `flash_loan` — can release them. This is the same bug class as the NounsDAO `Stream` report (contract accepts value but cannot return it), with the fix direction also analogous (`rescueETH` ≈ a sweep of unbooked balance).

### Finding Description
The pool's accounting is strictly bookkeeping-based. `contracts/pool/README.md` states that `supply`, `repay`, and `recapitalize` "credit `cash` on the controller's word" and that the only reconciliation against a real `token.balance()` is `flash_loan`'s strict-equality check. The money-flow audit test confirms a donation "belongs to no market's cash book": after `token.transfer(payer → pool, 7 * UNIT)`, the pool's balance is `cash + sibling_cash + 7 * UNIT` and the extra amount is never claimable (`tests/test-harness/tests/pool_money_flow_audit.rs:86-96`). `recapitalize` caps the credit at `backing_shortfall` computed from the book (`guards::backing_shortfall(&cache)`) and refunds the excess to the `payer` — it draws on the amount transferred in for that call, not on pre-existing surplus (`contracts/pool/src/ops/recapitalize.rs:44-67`). The complete `AdminOperation` enum (`contracts/governance/src/op.rs:124-431`) contains no sweep/rescue/donation-recovery variant; the pool is owner-gated to the controller, and the controller has no withdrawal entrypoint for stray balances either (`docs/explanation/threat-model.md:172-175`: "Neither category sweeps prior balances"). The swap-aggregator solves exactly this problem with `sweep_balance`, but the pool and controller have no equivalent.

### Impact Explanation
Any user, liquidation bot, or integration that transfers tokens directly to the pool or controller address — e.g., repaying debt by sending tokens to the pool instead of calling `controller.repay` (the liquidation skill explicitly warns "transferring repayment directly to the pool is a donation"), or refunding a failed strategy transfer — permanently loses those funds. For listed assets the tokens inflate `token.balance(pool)` above `Σ cash` forever; for unlisted tokens they are simply locked in the contract. Since Soroban tokens are push-transferred and the receiver cannot reject them, there is no user-side guard, and no on-chain path (permissionless or governance) exists to recover them absent a contract upgrade.

### Likelihood Explanation
Occasional accidental direct transfers are a realistic, documented failure mode — the project's own liquidation documentation warns integrators not to send repayment to the pool directly, implying this mistake is anticipated. The trigger requires only a mistaken `token.transfer` by an unprivileged address, matching the original report's "users occasionally send ETH" scenario. Severity is Medium: permanent loss limited to the sender's misdirected funds.

### Recommendation
Add an owner/governance-gated `sweep`/`rescue` entrypoint to the pool (and controller) that transfers out `token.balance(pool) - Σ cash` for a listed asset (or the full balance for an unlisted token), mirroring the swap-aggregator's `sweep_balance` which already correctly protects reserved balances via `ReservedTotal` (`contracts/swap-aggregator/src/lib.rs:189-203`). A corresponding `AdminOperation` variant should route the call through governance.

### Proof of Concept
Existing test evidence demonstrates the stranded state: `tests/test-harness/tests/pool_money_flow_audit.rs:86-96` transfers `7 * UNIT` to the pool address and asserts `token.balance(pool) == cash + sibling_cash + 7 * UNIT`, and no subsequent operation (`borrow`, `repay`, `recapitalize`, `withdraw`, `seize_positions`, `claim_revenue`) ever reduces the balance below `Σ cash`. `contracts/pool/src/ops/recapitalize.rs:52` shows the only "excess" handling refunds the same call's inbound amount, and `contracts/governance/src/op.rs:124-431` enumerates every governance operation with no rescue variant.     /// Transfers each token's balance above its reserved fee total to `recipient`. Owner only.
    #[only_owner]
    fn sweep_balance(env: Env, recipient: Address, tokens: Vec<Address>) {
        renew_instance(&env);
        let router = env.current_contract_address();
        let n = tokens.len();
        for i in 0..n {
            // `i < n == tokens.len()`, so the index is in range by construction.
            let token = tokens.get_unchecked(i);
            let client = token::Client::new(&env, &token);
            let balance = client.balance(&router);
            let reserved = storage::reserved_fee_balance(&env, &token);
            if balance > reserved {
                client.transfer(&router, &recipient, &(balance - reserved));
            }
        }
    }
