### Title
Webhook shop-domain, topic and webhook-id are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `HmacValidator.validate` binds *only* to the request body. The `shop-domain`, `topic`, and `webhook-id` headers — which `Webhooks::Registry.process` uses to route and attribute the payload — are read straight from unauthenticated headers and are never part of the signed data.

### Finding Description
`Webhooks::Request` includes `Utils::VerifiableQuery` and exposes `shop`, `topic`, and `webhook_id` purely as header lookups: [1](#0-0) 

`to_signable_string` (the data the HMAC actually covers) is just the raw body: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header value, then `Registry.process` trusts the (unsigned) `shop`, `topic`, and `webhook_id` to build the dispatched metadata: [3](#0-2) [4](#0-3) 

The `api_secret_key` used to compute the HMAC is a single, global per-app secret (not per-shop) — the same secret signs every shop's webhook traffic for a given app, as seen in `HmacValidator.validate_signature`/`compute_signature`: [5](#0-4) 

The equality the code should enforce is: `shop-domain (used for routing/attribution) == shop-domain (covered by the HMAC)`. Because `to_signable_string` never includes the header values, that equality is never checked — the signature is valid for any header combination as long as the body bytes match.

By contrast, the OAuth callback's `AuthQuery#to_signable_string` correctly folds `shop`, `host`, `state`, etc. into the signed string, so the same class of bug does not exist there: [6](#0-5) 

### Impact Explanation
An attacker who controls any shop that has installed the app (an ordinary, unprivileged merchant) receives legitimate webhook deliveries (body + valid HMAC) for their own shop. Because the HMAC only signs the body and the signing secret is shared across all shops for a given app, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers to name a victim shop/topic. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the handler with `shop: <forged victim shop>` and `topic: <forged topic>`. This lets an unprivileged tenant inject data into an app's per-shop state under another tenant's identity — e.g., forging `app/uninstalled` to trigger deletion of a victim's app data, `customers/redact` to trigger deletion in the victim's records, or `orders/paid`/`shop/update` payloads attributed to the victim shop. This is a cross-tenant integrity/data-attribution break driven directly by an unauthenticated field being trusted for routing.

### Likelihood Explanation
Any app built on this gem that relies on `Webhooks::Registry.process`/`Webhooks::Request` as documented is affected, and the only requirement is that the attacker controls one shop with the app installed (a routine, unprivileged condition) and can send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers — something trivially done outside of Shopify's own delivery infrastructure.

### Recommendation
Bind the shop, topic, and webhook id into the signed material (or otherwise cryptographically bind the header values to the payload) before trusting them for routing, e.g., have `to_signable_string` incorporate the normalized header values alongside the raw body, or independently verify that the `shop-domain` claimed in headers matches an app-side expectation (such as a shop known to have registered that specific webhook topic) rather than trusting the header verbatim.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify delivers a webhook with body `B` and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: customers/redact`, HMAC `H = HMAC(secret, B)` (secret shared across all shops of the app).
2. Attacker captures `B` and `H` from their own traffic (e.g., by logging their own webhook endpoint traffic, or simply reusing any topic they can trigger).
3. Attacker POSTs to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `HmacValidator.validate(request)` → passes, because validation only re-derives HMAC over `B`.
5. Handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to act on data attributed to `victim-shop.myshopify.com` even though it never sent that webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)

            secret,
            signable_string,
          )
        end
