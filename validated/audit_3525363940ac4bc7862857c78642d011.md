### Title
Unbounded `bytes signature` field lets a permissionless `submit_proof` caller panic the BEEFY consensus-proof conversion via `copy_from_slice` length mismatch - (File: `evm/rust/src/conversions.rs`)

### Summary
`pallet_beefy_consensus_proofs::verify_and_apply` ABI-decodes an attacker-supplied naive BEEFY proof and converts it with `abi_proof.into(): beefy_verifier_primitives::ConsensusMessage`, which recurses through `From<Vote> for SignatureWithAuthorityIndex` in `evm/rust/src/conversions.rs`. That conversion does an unchecked `copy_from_slice` of the Solidity `Vote.signature` `bytes` field into a fixed `[u8; 65]` array, with no length check beforehand. Because the Solidity `bytes` type is caller-controlled and has no length constraint, any signature of length ≠ 65 causes a Rust panic before any cryptographic or membership verification runs.

### Finding Description
`pallet-beefy-consensus-proofs::submit_proof` is documented and tested as a permissionless entry point that anyone can call with `PROOF_TYPE_NAIVE` to submit an ECDSA/naive BEEFY consensus proof (see `parachain/simtests/src/pallet_beefy_consensus_proofs.rs` tests submitting oversized/unknown/malformed proofs). The naive-proof path in `verify_and_apply` does: [1](#0-0) 

```rust
types::PROOF_TYPE_NAIVE => {
    let abi_proof =
        <ismp_abi::ecdsa_beefy::BeefyConsensusProof as SolType>::abi_decode_params(
            abi_payload,
        )
        .map_err(|_| Error::<T>::AbiDecodeFailed)?;
    let scale_proof: beefy_verifier_primitives::ConsensusMessage = abi_proof.into();
    ...
```

`BeefyConsensusProof` is ABI-decoded straight from the raw bytes submitted by the caller — an unsigned/permissionless extrinsic — with no signature-length validation at the ABI layer, because Solidity's `bytes signature` field (`Vote.signature`, see `Types.sol`) can be any length: [2](#0-1) 

The `.into()` call performs the `RelayChainProof -> MmrProof` conversion, which maps every `Vote` into a `SignatureWithAuthorityIndex` via: [3](#0-2) 

```rust
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);
        SignatureWithAuthorityIndex {
            signature,
            index: value.authorityIndex.try_into().expect("authority index out of bounds"),
        }
    }
}
```

`copy_from_slice` on a `[u8; 65]` target requires the source slice to be exactly 65 bytes; any other length causes `slice::copy_from_slice` to panic (`source slice length (N) does not match destination slice length (65)`). This conversion runs unconditionally before the `verify_mmr_update_proof` cryptographic checks that would otherwise reject a malformed signature gracefully via `Error::FailedToRecoverPublicKey` (compare with the well-guarded verifier at `modules/consensus/beefy/verifier/src/lib.rs:150` which calls `secp256k1_recover` and returns a typed error, never `copy_from_slice`-panics, on a `sig.signature: TSignature` that is already a fixed array by the time it gets there).

This is structurally the same bug class as CVE-2022-39244 (PJSIP): a length-prefixed/variable-length field from untrusted network input is copied into a fixed-size buffer without a bounds/length check, causing memory-safety-adjacent failure (in Rust, a guaranteed panic/abort rather than classic heap overflow, but still an uncontrolled crash triggered purely by malformed untrusted input reaching a parsing/conversion routine before validation).

The `try_into().expect(...)` on `authorityIndex` a few lines later is a second, narrower instance of the same pattern (a `U256` that doesn't fit `u32` also panics), though it is less trivially triggerable since `authorityIndex` values are typically small in practice — the primary, easily-triggerable issue is the `signature` field.

### Impact Explanation
A panic inside pallet logic invoked from an unsigned extrinsic's dispatch path (`handle_unsigned`-adjacent / `submit_proof`) causes the transaction to fail, but depending on how/where the panic unwinds (Substrate runtime `#[frame_support::transactional]` and WASM execution generally catch panics as extrinsic failures rather than crashing the whole node), the practical effect is at minimum a permanent denial-of-service against this specific `submit_proof` naive-proof code path — any single malformed submission with the wrong signature length reliably aborts before verification. Because BEEFY consensus proofs are what update the trusted relay-chain state and gate parachain state-commitment ingestion (i.e., unblocking cross-chain message delivery for the parachains rooted at this consensus client), a mechanism that can be repeatedly triggered to abort processing on this route degrades to "a route unable to deliver messages" if the panic escalates to a storage-poisoning/DoS of the wasm executor thread that services unsigned extrinsics (analogous to the RPC-thread crash regression noted elsewhere in this codebase, e.g. `modules/utils/serde/src/lib.rs:529-532` "the panic aborted the node's `rpc` worker thread and took the process down"). This qualifies as High under the Medium/High/Critical filter given it is a single-transaction, permissionless trigger against a core consensus-ingestion pipeline.

### Likelihood Explanation
High. `submit_proof` with `PROOF_TYPE_NAIVE` is explicitly permissionless (any signed account can call it per the simtests), requires no proof-crypto validity to trigger the bug — only a malformed ABI payload whose `Vote.signature` bytes field is not exactly 65 bytes long, which is trivial to construct and costs only the extrinsic's declared weight/fee.

### Recommendation
In `evm/rust/src/conversions.rs`, replace the unchecked `copy_from_slice` in `From<Vote> for SignatureWithAuthorityIndex` with a fallible conversion: validate `sig_bytes.len() == 65` and return/propagate an error (e.g. change the `From` impl to `TryFrom`, or validate immediately after ABI-decoding in `pallet_beefy_consensus_proofs::verify_and_apply` before calling `.into()`), mapping any mismatch to `Error::<T>::AbiDecodeFailed`. Apply the same defensive length/range check to the `authorityIndex.try_into().expect(...)` conversion in the same file (and its sibling `From<Commitment> for SpCommitment` / `From<crate::sp1_beefy::SP1Beefy::SP1BeefyProof> for Sp1BeefyProof` `expect(...)` calls a few lines above, which have the identical unchecked-`try_into().expect()` pattern) so that no attacker-controlled ABI field can panic the runtime before verification runs.

### Proof of Concept
1. Craft a `BeefyConsensusProof` ABI-encoded payload where `signedCommitment.votes[0].signature` is, e.g., 64 or 66 bytes instead of 65 (any value is accepted by Solidity's `bytes` ABI encoding — no on-chain constraint enforces the length).
2. Prefix the payload with `types::PROOF_TYPE_NAIVE` (`0x00`) as required by `verify_and_apply`.
3. Submit via `pallet_beefy_consensus_proofs::submit_proof` (permissionless call) as in the existing test harness `parachain/simtests/src/pallet_beefy_consensus_proofs.rs` (which already demonstrates submitting crafted/malformed naive proofs, e.g. lines 378-387), but with a validly-ABI-decodable `BeefyConsensusProof` whose one `Vote.signature` length ≠ 65.
4. `abi_decode_params` succeeds (ABI decoding does not care about the semantic 65-byte constraint), so execution reaches `abi_proof.into()` → `From<Vote> for SignatureWithAuthorityIndex` → `signature.copy_from_slice(&sig_bytes)` → Rust panic, aborting `verify_and_apply` before any BEEFY signature/membership verification takes place.
