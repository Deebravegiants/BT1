Audit Report

## Title
Disabled slippage control in `SwapFirstAssetTrader::refund_weight` swap-back - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` swaps unused fee credit from the `Target` asset back into the asset the user originally paid with by calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, disabling slippage protection on that leg of the round-trip swap. This is confirmed directly in the code at [1](#0-0)  and contrasts with `buy_weight`'s naturally-bounded `swap_tokens_for_exact_tokens` call at [2](#0-1) .

## Finding Description
`buy_weight` converts the client-supplied asset into exactly `fee` units of the `Target` asset via `swap_tokens_for_exact_tokens`, bounded by the `credit_in` supplied — it either produces the exact `fee` or fails, giving it implicit protection [3](#0-2) . `refund_weight` later extracts the unused portion of `total_fee` (denominated in `Target`) and swaps it back into `refund_swap_asset` via `swap_exact_tokens_for_tokens(..., None)`, with no lower bound enforced on the output amount [4](#0-3) . The underlying `SwapCredit::swap_exact_tokens_for_tokens` trait and `pallet_asset_conversion` implementation both explicitly support and enforce `amount_out_min` only when `Some(_)` is passed [5](#0-4) , so passing `None` accepts any nonzero output the pool happens to return at execution time. This trader is wired into production runtime configs for Asset Hub Westend and Penpal.

## Impact Explanation
If the specific `(Target, refund_swap_asset)` pool is manipulated immediately around the `refund_weight` execution, the refunded credit — which is folded back into the XCM holding register for the account whose message triggered the fee payment — can be worth materially less than fair value, with the difference captured by whoever manipulated the pool. The loss is bounded by the magnitude of the unused-weight refund (an "overpaid fee" amount), not by full account balances, and scales with how thin the specific pool's liquidity is.

## Likelihood Explanation
Exploitation requires an attacker to sandwich the exact block/transaction in which `refund_weight` executes for a given pool — feasible in principle for locally-submitted `pallet_xcm::execute` extrinsics (ordinary signed transactions, reorderable within a block), but much less clear for inbound HRMP/DMP messages typically processed as inherents ahead of ordinary extrinsics. This uncertainty is acknowledged in the report itself, and no working proof-of-concept (fork test, unit test, or reproduction) was provided to demonstrate the attack is practically executable against a real pool/block-authoring setup.

## Recommendation
Compute an acceptable lower bound for the refund swap (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` with a configurable tolerance) and pass `Some(min_amount)` to `SwapCredit::swap_exact_tokens_for_tokens` in `refund_weight`, falling back to returning the un-swapped `Target` credit if the bound cannot be met, mirroring how `pallet_asset_conversion`'s own extrinsics enforce `amount_out_min`.

## Proof of Concept
Not reproduced in this review. A concrete PoC would require: setting up a thin-liquidity `AssetConversion` pool for `(Target, refund_swap_asset)` in a runtime using `SwapFirstAssetTrader`; triggering an XCM execution path (e.g., via `pallet_xcm::execute` with over-estimated weight) that causes `refund_weight` to run; and interleaving a manipulating swap immediately before/after the refund within the same block to show the refunded amount is materially below the pre-manipulation quoted price.
