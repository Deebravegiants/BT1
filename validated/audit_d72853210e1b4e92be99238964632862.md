### Title
Webhook HMAC does not bind `shop` (or `topic`), enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `request.shop` and `request.topic` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Utils::HmacValidator.validate` only checks that the HMAC matches the raw body, so the `shop-domain` and `topic` headers can be freely altered by anyone without invalidating the signature check, breaking the equality that "the shop the HMAC is computed over" should equal "the shop that the payload is attributed to."

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

while `shop` and `topic` are pulled straight from headers with no cryptographic binding:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` validates the request purely through this signable string:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [3](#0-2) 

`HmacValidator.validate` computes and compares the signature strictly over `to_signable_string`, i.e. `@raw_body`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` is explicitly included in `to_signable_string` so it is bound by the HMAC:
```ruby
def to_signable_string
  params = { code: code, host: host, shop: shop, state: state, timestamp: timestamp }
  URI.encode_www_form(params)
end
``` [5](#0-4) 

The equality that should hold is: `shop bound by HMAC == shop attributed to the webhook payload`. In the webhook path this equality is broken — the HMAC only proves the body's integrity/origin (that it was signed with `api_secret_key` for that exact byte sequence), it says nothing about which shop or topic the body should be attributed to. Any party who can obtain one valid `(raw_body, hmac)` pair signed by the app's secret (e.g. by installing the app on their own store and receiving a genuine webhook for a topic they control) can replay that same body+hmac to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different shop/topic. `HmacValidator.validate` still succeeds because it never inspects those headers, so `Registry.process` will invoke the handler with `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant access vulnerability: a merchant/attacker who has a legitimate app installation (an unprivileged multi-tenant actor relative to other merchants) can forge webhook deliveries that the host application will attribute to any other shop domain of their choosing, using only a body/HMAC pair they legitimately obtained for their own store. Any host application logic keyed on `data.shop` (e.g., updating/creating shop-scoped records, triggering per-shop side effects) can be tricked into acting on behalf of, or against, a shop the attacker doesn't control — a direct cross-tenant boundary break with no access token or credentials for the victim shop required.

### Likelihood Explanation
The webhook HTTP endpoint is deliberately public (Shopify posts callbacks to it, and the docs show it wired directly to a public Rails route). An attacker needs only: (1) their own app installation/webhook subscription to receive one genuine `(raw_body, hmac)` pair, and (2) the ability to POST an HTTP request to the app's webhook route with attacker-controlled headers — both trivially available to an "unprivileged internet user" running their own Shopify store with the target app installed. No secrets, tokens, or TLS interception are required.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop/topic to the signed payload, so that spoofing the `x-shopify-shop-domain` / `x-shopify-topic` headers invalidates the HMAC check. At minimum, document and enforce that host applications must independently verify `data.shop` against a known/expected shop before acting on webhook data, since this gem currently provides no such guarantee.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`), yielding an actually-delivered request with valid headers `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and some `raw_body`.
2. Attacker replays this exact `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)` [6](#0-5) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
