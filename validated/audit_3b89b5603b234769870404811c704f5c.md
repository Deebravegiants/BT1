### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant spoofing in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Webhooks::Request#to_signable_string` method that feeds the HMAC computation returns only `@raw_body` [2](#0-1) . The `shop` value used to identify the tenant, however, is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) , and this header is never part of the signable string. That `shop` value is then passed straight into the `WebhookMetadata` object handed to the app's registered handler [4](#0-3) .

### Finding Description
The binding that should hold is:
`hmac-verified bytes == bytes the tenant identity ("shop") is derived from`

Here it does not: the HMAC only covers `@raw_body` (the JSON payload), while `shop` (and `topic`, `webhook_id`, `api_version`) are read from separate HTTP headers that carry no cryptographic protection of their own [5](#0-4) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [6](#0-5) , and for a `Webhooks::Request` that signable string is exclusively the body [7](#0-6) .

Concretely: if a body with a valid HMAC for the app's shared secret can be replayed or re-delivered (e.g., captured from a legitimate webhook for Shop A, or an attacker-controlled request that reaches the app's webhook endpoint with a body they can get correctly HMAC'd — for instance an idempotent or attacker-triggerable payload/topic where the body content doesn't vary per shop, such as `app/uninstalled` bodies which can be near-empty `{}` as shown in the gem's own tests), the `shop-domain` header can be swapped to name a *different* shop while the HMAC still validates, because the header was never part of the signed bytes. `Registry.process` will then invoke the app's handler believing the event originates from the attacker-chosen shop [8](#0-7) , i.e., `WebhookMetadata.shop` names a different tenant than the one whose secret actually produced the bytes that were verified.

This exactly matches the report's bug class — "a field acted on but not covered by the HMAC" — mirrored onto this gem's webhook authentication path, where the field is the tenant-identifying `shop` header rather than a swap-destination token.

### Impact Explanation
If a downstream application uses `WebhookMetadata#shop` from `Registry.process` as the authoritative tenant identifier (as the gem's documentation and design intend — this is the entire purpose of passing `shop` in the callback), an attacker who can produce (or replay) any correctly-HMAC'd body — most easily one whose content is shop-independent (e.g. the mandatory `shop/redact`, `customers/redact`, or minimal-body topics) — can cause the handler to process an event attributed to an arbitrary victim shop of the attacker's choosing. This is a cross-tenant confusion: data/state associated with Shop B gets acted upon/attributed under a webhook nominally "from" Shop A, purely because the tenant-identifying header sits outside the HMAC's protection scope.

### Likelihood Explanation
Exploitability depends on the attacker being able to get a validly-HMAC'd body to the app's webhook endpoint while controlling headers, which requires either: (a) a body that is shop-independent (so the same signature is valid regardless of which shop "sent" it) plus the ability to man-in-the-middle/replay/re-craft the delivery headers, or (b) capturing one legitimate webhook delivery and replaying it with a different `shop-domain` header value. Since headers are typically application-controlled input adjacent to the HTTP layer (and this gem does not mandate TLS-terminated header integrity beyond the HMAC), and the gem's own `Registry.process` never cross-checks `shop` against anything HMAC-protected, likelihood is non-trivial for any integrator who trusts the returned `shop` value as an authenticated tenant identifier.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signable string computed for webhook HMAC validation, mirroring how `AuthQuery#to_signable_string` binds `shop`, `host`, `state`, etc. into the OAuth callback HMAC [9](#0-8) . At minimum, document prominently that `WebhookMetadata#shop` is derived from an HMAC-unprotected header and must not be trusted as an authenticated tenant identifier without additional out-of-band verification (e.g., matching against a known/stored shop for the session that registered the webhook).

### Proof of Concept
Conceptual PoC (mirrors the gem's own test pattern):
```ruby
raw_body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Legitimate delivery claims to be from victim-shop
legit_headers = {
  "shopify-topic" => "app/uninstalled",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com",
  "shopify-webhook-id" => "id-1",
  "shopify-api-version" => "2024-01",
}

# Attacker resends the SAME body+hmac but swaps only the shop header
forged_headers = legit_headers.merge("shopify-shop-domain" => "attacker-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (it only checks raw_body), and the handler
#    receives WebhookMetadata with shop: "attacker-shop.myshopify.com"
#    even though the signed bytes say nothing about which shop this is.
```
This demonstrates that `Registry.process` at [8](#0-7)  and `Request#to_signable_string`/`#shop` at [10](#0-9)  allow the tenant identity to diverge from the HMAC-authenticated content.
