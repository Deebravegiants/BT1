### Title
Unchecked ERC20/TRC20 `transfer()` return value in escrow release and dust sweep - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` uses a raw low-level `.call()` with `IERC20.transfer.selector` to release escrowed intent funds and to sweep protocol dust, checking only that the external call did not revert (`success`) but never decoding/validating the ERC20 `bool` return value itself.

### Finding Description
In `withdraw()` and the `SweepDust` branch of the request handler, token payouts are performed as: [1](#0-0) 

and [2](#0-1) 

Here `success` reflects only whether the low-level call reverted, not whether the token contract's own transfer logic actually succeeded. Many TRC20/ERC20 tokens (a well-known class on both Tron and EVM, e.g. non-compliant or "USDT-style" tokens) return `false` on failure instead of reverting. In that case `success` is still `true` (the call executed and returned data without reverting), so `TransferFailed` is never raised, yet no tokens were actually moved.

This contrasts with the equivalent EVM-mainline implementation in `evm/src/apps/intentsv2/IntentsBase.sol`, where the same operations use OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and validates the return value (or requires a revert), closing this exact gap: [3](#0-2) [4](#0-3) 

The Tron variant of `IntentGatewayV2.sol` diverges from this safe pattern in exactly the two paths that pay out escrowed user/solver funds and protocol dust.

### Impact Explanation
Both affected code paths are reached via the ISMP relay/dispatch flow:
- `withdraw()` is invoked from `onAccept`/`onGetResponse` handling of `RedeemEscrow`/`RefundEscrow` cross-chain messages, releasing user-escrowed input tokens or the solver's fill payout, and refunding relayer fees.
- The `SweepDust` branch is invoked via a governance-relayed cross-chain message sweeping accumulated protocol dust.

If the payout token silently returns `false` on transfer failure (e.g. insufficient allowance/blacklist/paused-style tokens, or simply returns `false` instead of reverting per non-standard implementations), the contract's internal accounting (`_orders[commitment][token] -= amount`, `_filled[commitment] = beneficiary`) still records the funds as delivered/finalized even though the beneficiary received nothing. This permanently freezes/loses the escrowed funds for the affected token — the order is marked filled/refunded so it cannot be retried, and no further mechanism exists to redeliver the tokens. This is a direct fund-loss/freezing bug reachable purely from a relayed message settling an ordinary user-submitted intent order — no privileged role required.

### Likelihood Explanation
Likelihood depends on whether any token used with the intent gateway on Tron/EVM-Tron-compatible deployments exhibits non-reverting failure semantics (return `false` instead of reverting). This is a well-documented pattern among TRC20/ERC20 tokens, and the intent gateway is designed to be token-agnostic (arbitrary tokens specified per order), so the exposure is proportional to the diversity of tokens routed through this specific Tron deployment. Given the contract explicitly supports arbitrary ERC20-style tokens for escrow inputs/outputs, the likelihood of encountering at least one non-compliant token is non-trivial.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()` and the `SweepDust` handler of `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw`/`_sweepDust`. This ensures both call-revert failures and silent `false`-return failures cause a revert, keeping on-chain escrow accounting consistent with actual token movement.

### Proof of Concept
1. Deploy a mock TRC20/ERC20 token whose `transfer()` returns `false` on failure (e.g., insufficient balance edge case, blacklisted recipient, or intentionally non-standard) instead of reverting.
2. Place and escrow an order in `evm/tron/contracts/apps/IntentGatewayV2.sol` using this token as an input/output asset.
3. Trigger the cross-chain fill/refund flow so `onAccept`/`onGetResponse` calls `withdraw()` with a `beneficiary` address for which the mock token's `transfer` call returns `false` (without reverting).
4. Observe: `token.call(...)` returns `success = true` (call didn't revert) even though the token's internal `transfer` returned `false`; `TransferFailed` is not raised; `_orders[commitment][token] -= amount` executes and `_filled[commitment]` is set — the order is finalized as filled/refunded, but the beneficiary's token balance is unchanged, permanently losing the escrowed amount.
