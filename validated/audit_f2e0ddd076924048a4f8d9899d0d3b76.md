Audit Report

## Title
Missing `para_id` validation in `do_place_order` allows queue-filling / spot-price griefing via on-demand order placement - (File: polkadot/runtime/parachains/src/on_demand/mod.rs)

## Summary
`do_place_order` never validates that `para_id` corresponds to a registered parachain or parathread before charging the caller and pushing an `EnqueuedOrder` into `OrderQueue`. Any signed account with sufficient balance (via `place_order_allow_death`/`place_order_keep_alive`) or Credits (via `place_order_with_credits`) can enqueue orders for an arbitrary, unregistered `ParaId`, occupying queue capacity and inflating `spot_price` for legitimate purchasers.

## Finding Description
`do_place_order` computes the spot price from `order_status.traffic`, checks only that `spot_price <= max_amount` and that `order_status.queue.len()` is below `on_demand_queue_max_size`, then charges the sender and unconditionally pushes `(now, para_id)` into `order_status.queue` via `try_push`. [1](#0-0) [2](#0-1) 

There is no call anywhere in this function, or in the three public dispatchables `place_order_allow_death`, `place_order_keep_alive`, `place_order_with_credits`, to any lifecycle/registration check on `paras::Pallet::<T>` (e.g. `is_parathread`/`is_parachain`), despite `Config: paras::Config` being imported and available in this module. [3](#0-2) [4](#0-3) 

`OrderQueue::try_push` and `pop_assignment_for_cores` operate purely on the supplied `ParaId` with no validity filtering. [5](#0-4) 

`update_spot_traffic` derives the new traffic/spot price purely from `order_status.queue.len()` vs. `on_demand_queue_max_size`/`on_demand_target_queue_utilization`, with no distinction between orders for real vs. fake/unregistered paras, so junk orders directly inflate the price paid by legitimate purchasers. [6](#0-5) 

The `PaymentType::Balance` path (reachable via `place_order_allow_death`/`place_order_keep_alive`, requiring only native currency, no special privilege) and the `PaymentType::Credits` path both share this identical unvalidated `para_id` push, confirming the root cause is a structural omission in `do_place_order` rather than something specific to the credits mechanism. [7](#0-6) 

The queue is bounded by `ON_DEMAND_MAX_QUEUE_MAX_SIZE` and further capped by `on_demand_queue_max_size` from `HostConfiguration`, so repeated bogus orders can occupy queue slots up to that limit, causing subsequent legitimate `place_order_*` calls to fail with `Error::QueueFull` until stale entries are eventually popped by `pop_assignment_for_cores` (which removes "ready" entries regardless of whether the `ParaId` is actually schedulable). [8](#0-7) [9](#0-8) 

## Impact Explanation
Because there is no `para_id` registration check, an attacker can (a) fill on-demand queue capacity with orders for a `para_id` that will never legitimately consume a core, causing genuine `place_order_*` calls to fail with `QueueFull`, and (b) drive up `traffic`/`spot_price` via `update_spot_traffic`, forcing genuine payers to pay inflated prices or be rejected by `SpotPriceHigherThanMaxAmount`. This is a griefing/temporary-DoS vector against the on-demand marketplace's fairness and pricing mechanism, not an asset-theft or fund-loss bug — entries are eventually evicted by `pop_assignment_for_cores`, so the effect is repeatable but bounded/temporary rather than permanent.

## Likelihood Explanation
The `PaymentType::Balance` path is directly reachable by any signed account holding sufficient native currency, with no special privilege required, through the public extrinsics `place_order_allow_death`/`place_order_keep_alive`. The `PaymentType::Credits` path additionally requires a positive `Credits` balance, which in this codebase is granted via `Pallet::credit_account`, invoked from the `coretime` pallet's broker-chain-driven flow rather than freely by arbitrary users — this narrows (but does not eliminate) the credits-specific attack surface, since the underlying missing-validation bug is exploitable via the balance-payment path with no such precondition. Cost scales with `spot_price`, which itself rises as the queue fills, self-limiting but not preventing the attack.

## Recommendation
Add a validity check in `do_place_order` before charging and enqueueing, e.g. verifying the `para_id` is a currently onboarded parachain or parathread via `paras::Pallet::<T>` lifecycle state, returning a dedicated error (e.g. `Error::<T>::InvalidParaId`) otherwise, so that only orders for real, schedulable paras are charged for and counted toward queue occupancy and `spot_price`/`traffic` calculations.

## Proof of Concept
1. In `polkadot/runtime/parachains/src/on_demand/tests.rs`, build the mock runtime and do not register `para_id = ParaId::from(9999)` via `paras::Parachains`/`ParaLifecycles`.
2. Fund a test account with sufficient native balance, then repeatedly call `OnDemand::place_order_allow_death(RuntimeOrigin::signed(attacker), BalanceOf::max_value(), ParaId::from(9999))` (no credits precondition needed) and assert each succeeds and emits `OnDemandOrderPlaced`.
3. Continue until `OnDemand::get_order_status().queue.len() == on_demand_queue_max_size`; assert the next call from a second legitimate account for a real, registered `para_id` fails with `Error::<T>::QueueFull`.
4. Assert `OnDemand::get_order_status().traffic` increased above the default value purely due to the injected fake-para orders, demonstrating spot-price inflation.

impl<N> OrderQueue<N> {
	/// Pop `num_cores` from the queue, assuming `now` as the current block number.
	pub fn pop_assignment_for_cores<T: Config>(
		&mut self,
		now: N,
		mut num_cores: u32,
	) -> impl Iterator<Item = ParaId>
	where
		N: Saturating + Ord + One + Copy,
	{
		let mut popped = BTreeSet::new();
		let mut remaining_orders = Vec::with_capacity(self.queue.len());
		for order in mem::take(&mut self.queue) {
			// Order is ready 2 blocks later (asynchronous backing):
			let ready_at = order.ordered_at.saturating_plus_one().saturating_plus_one();
			let is_ready = ready_at <= now;

			if num_cores > 0 && is_ready && popped.insert(order.para_id) {
				num_cores -= 1;
			} else {
				remaining_orders.push(order);
			}
		}
		self.queue = BoundedVec::truncate_from(remaining_orders);
		popped.into_iter()
	}

	fn new() -> Self {
		OrderQueue { queue: BoundedVec::new() }
	}

	/// Try to push an additional order.
	///
	/// Fails if queue is already at capacity.
	fn try_push(&mut self, now: N, para_id: ParaId) -> Result<(), ParaId> {
		self.queue
			.try_push(EnqueuedOrder { para_id, ordered_at: now })
			.map_err(|o| o.para_id)
	}

	fn update_spot_traffic(
		config: &configuration::HostConfiguration<BlockNumberFor<T>>,
		order_status: &mut OrderStatus<BlockNumberFor<T>>,
	) {
		let old_traffic = order_status.traffic;
		match Self::calculate_spot_traffic(
			old_traffic,
			config.scheduler_params.on_demand_queue_max_size,
			order_status.queue.len() as u32,
			config.scheduler_params.on_demand_target_queue_utilization,
			config.scheduler_params.on_demand_fee_variability,
		) {
			Ok(new_traffic) => {
				// Only update storage on change
				if new_traffic != old_traffic {
					order_status.traffic = new_traffic;

					// calculate the new spot price
					let spot_price: BalanceOf<T> = new_traffic.saturating_mul_int(
						config.scheduler_params.on_demand_base_fee.saturated_into::<BalanceOf<T>>(),
					);

					// emit the event for updated new price
					Pallet::<T>::deposit_event(Event::<T>::SpotPriceSet { spot_price });
				}
			},
			Err(err) => {
				log::debug!(
					target: LOG_TARGET,
					"Error calculating spot traffic: {:?}", err
				);
			},
		};
	}
