### Title
`describeWithdrawal` in the POA bridge matches by `assetId` alone, misreporting completion status/txHash for batched withdrawals of the same asset - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` looks up the on-chain withdrawal state purely by `assetId`, not by the withdrawal's `index`/unique identity within the batch. When a single NEAR transaction contains more than one withdrawal of the *same* `assetId` (e.g. two POA withdrawals of `nep141:btc.omft.near` to different destinations submitted together), the lookup cannot disambiguate between them, so `describeWithdrawal` can report the wrong entry's status/txHash for a given withdrawal index — breaking the equality "status/txHash reported for withdrawal N == the on-chain outcome of withdrawal N".

### Finding Description
`describeWithdrawal` explicitly documents and implements assetId-based matching instead of index-based matching: [1](#0-0) 

```
async describeWithdrawal(...) {
    const response = await this.getWithdrawalStatusWithRetry(args);
    // Response list is unsorted, so we match by assetId instead of index
    const withdrawal = findMatchingWithdrawal(
        response.withdrawals,
        args.withdrawalParams.assetId,
    );
    ...
    if (withdrawal.status === "COMPLETED") {
        return { status: "completed", txHash: withdrawal.data.transfer_tx_hash };
    }
    ...
}
```

The bridge's own test suite documents this design and only verifies correctness for the case where the batch contains withdrawals of *different* asset ids: [2](#0-1) 

There is no test (and, per the code, no logic) covering a batch that withdraws the *same* `assetId` more than once (e.g. two BTC withdrawals to different addresses in one `createWithdrawalIntents`/NEAR transaction). In that scenario `findMatchingWithdrawal` has no way to select the correct entry for `index=0` vs `index=1`; it will return the first (or otherwise indeterminate) match for both indices. As a direct consequence:
- `describeWithdrawal({ index: 0, ... })` and `describeWithdrawal({ index: 1, ... })` can both resolve to the same `withdrawal.data`, reporting the same `transfer_tx_hash` and `status: "completed"` for two distinct withdrawals, even though only one of them has actually completed on-chain.
- This propagates directly into `watchWithdrawal`, which turns a `"completed"` status into a final `{ hash }` result trusted by callers to mark the withdrawal as done: [3](#0-2) 

An integrator relying on `watchWithdrawal`/`describeWithdrawal` per index would therefore credit or consider fulfilled a withdrawal that never happened, using the txHash of a sibling withdrawal — a status/hash misreport that can cause double crediting.

### Impact Explanation
This is a status/hash misreport for a batched same-asset withdrawal: an integrator can be told withdrawal #2 completed (with withdrawal #1's txHash) while #2 is still pending or failed. That matches the "status or hash misreport making an integrator credit or refund twice" impact class (High). No malicious relayer, RPC, or price-feed assumption is required — this occurs purely from the SDK's own lookup logic on a normal user-initiated batch withdrawal.

### Likelihood Explanation
Requires only that a caller submit more than one POA-bridge withdrawal of the same underlying asset in a single batch (e.g., two BTC withdrawals to different destinations), which is a supported and unprivileged usage pattern of `createWithdrawalIntents`/multi-withdrawal batching. The comment "Response list is unsorted, so we match by assetId instead of index" confirms this is a known, deliberate simplification rather than an edge case guarded against elsewhere.

### Recommendation
Disambiguate matching using a value unique per withdrawal within the batch (e.g., correlate by destination address + amount + `tx.hash`, or by an explicit sequence/nonce returned by the POA withdrawal-status API) instead of `assetId` alone, so `findMatchingWithdrawal` cannot select the wrong entry when a batch contains repeated `assetId`s.

### Proof of Concept
1. Build a NEAR transaction with two POA-bridge withdrawal intents both for `nep141:btc.omft.near` (e.g., withdrawal index 0 to address A and index 1 to address B).
2. Query `httpClient.getWithdrawalStatus` such that only withdrawal #1 (to B) has completed with `transfer_tx_hash = "btc-tx-hash-B"`; withdrawal #0 (to A) is still `PENDING` or absent.
3. Call `bridge.describeWithdrawal({ index: 0, withdrawalParams: { assetId: "nep141:btc.omft.near", ... }, tx })`.
4. Because `findMatchingWithdrawal` selects by `assetId` only, it can return the completed entry for B's withdrawal, causing `describeWithdrawal` for index 0 to report `{ status: "completed", txHash: "btc-tx-hash-B" }` even though withdrawal #0 (to A) has not completed — an incorrect status/hash for that specific withdrawal.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
