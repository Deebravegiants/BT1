Audit Report

## Title
`ExternalInitiatorsEnabled` config flag is enforced only at registration, not at authentication/run time - ([File: core/web/auth/auth.go])

## Summary
The `JobPipeline.ExternalInitiatorsEnabled` flag is checked only in `ExternalInitiatorsController.Create` when a new External Initiator credential is registered, but is never consulted in `AuthenticateExternalInitiator`, the middleware that authenticates inbound requests using existing External Initiator credentials and grants them the `Run` role. As a result, disabling the flag does not revoke the ability of already-provisioned External Initiator credentials to authenticate and trigger job runs.

## Finding Description
`ExternalInitiatorsController.Create` gates creation of a new external initiator behind the flag check `!eic.App.GetConfig().JobPipeline().ExternalInitiatorsEnabled()`, returning a 405 if disabled. [1](#0-0) 

However, `AuthenticateExternalInitiator`, the middleware used to authenticate External Initiator requests via the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, looks up the initiator, validates the credential via `bridges.AuthenticateExternalInitiator`, and on success unconditionally grants `clsessions.UserRoleRun` — with no check of `ExternalInitiatorsEnabled()` anywhere in this function. [2](#0-1) 

The generic `Authenticate` middleware just iterates configured `authMethod`s and grants access on the first successful match, without any additional feature-flag gate. [3](#0-2) 

A repo-wide search confirms `ExternalInitiatorsEnabled` is referenced only in the controller/config/docs/test files and never in `core/web/auth/auth.go` or anywhere along the authentication path, confirming the flag has no effect once a credential already exists.

## Impact Explanation
This is a real logic gap: an operator who disables `ExternalInitiatorsEnabled` intending to shut off the External Initiator run-triggering mechanism (e.g., during incident response) will find that previously-issued External Initiator credentials continue to authenticate successfully via `AuthenticateExternalInitiator` and retain the `Run` role, allowing continued triggering of job/pipeline runs. This maps to an in-scope "unauthorized job run" / authorization-bypass class of impact, since the intended kill-switch semantics of the config flag are not honored on the authentication path.

## Likelihood Explanation
The exploit path requires only possession of a previously-issued, valid External Initiator access key/secret — the same unprivileged actor class the External Initiator mechanism is designed for. No additional privilege or complexity is needed: the credential holder simply continues sending normal authenticated requests after the flag is disabled, and the bypass is deterministic (every existing credential works regardless of the flag state) rather than probabilistic.

## Recommendation
Add an explicit `App.GetConfig().JobPipeline().ExternalInitiatorsEnabled()` check inside `AuthenticateExternalInitiator` in `core/web/auth/auth.go`, returning `auth.ErrorAuthFailed` (or a dedicated "feature disabled" error) when the flag is off, so disabling the feature immediately revokes authentication for all existing External Initiator credentials, not just blocking new registrations.

## Proof of Concept
1. Start a node with `JobPipeline.ExternalInitiatorsEnabled = true`. Create an External Initiator via `POST /v2/external_initiators` (`ExternalInitiatorsController.Create`, `core/web/external_initiators_controller.go:62`), obtaining `AccessKey`/`Secret`.
2. Set `JobPipeline.ExternalInitiatorsEnabled = false` and restart/reload config.
3. Confirm `POST /v2/external_initiators` now fails with "The External Initiator feature is disabled by configuration" (405).
4. Using the previously obtained credentials, send a request with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers to an endpoint protected by `auth.Authenticate(..., AuthenticateExternalInitiator)` (e.g., a webhook job-run trigger route wired via `core/web/router.go`). Observe that `AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-149`) succeeds and grants `UserRoleRun`, allowing the job run to be triggered despite the feature being "disabled" — demonstrating the flag is not enforced on the authentication path.

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
```

```go
// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```
