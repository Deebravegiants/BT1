## Confirmed: erc20TokenAddresses (including address(0) for native ETH) is fully attacker/prover-controlled, with no requirement that ETH be included in the tracked-token list, and the outer `Hinkal.transact` balance check operates on `Hinkal`'s own balance, not `Emporium`'s balance.

### Title
Arbitrary-call ETH drain from Emporium via untracked token list - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes a caller-supplied list of low-level calls (`op.endpoint.call{value: op.value}(op.callData)`) and only re-validates the post-call balance for the tokens listed in `circomData.erc20TokenAddresses`—a list the prover freely chooses per-transaction. If the prover omits `address(0)` (native ETH) from that list, any ETH balance sitting on the `Emporium` contract (leftover ETH from a prior transaction, unclaimed relay fee, rounding remainder, etc.) can be sent to an arbitrary attacker-controlled address via the "Stateless Interaction" branch, with no balance-equation check ever verifying the ETH was accounted for.

### Finding Description
`runAction` computes `balancesBefore`/`balancesAfter` and requires `balanceChange >= 0` — but strictly only `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)`: [1](#0-0) [2](#0-1) 

`erc20TokenAddresses` is entirely prover-supplied and only constrained to match `dimensions.tokenNumber` in `dimensionsCheck`; nothing forces `address(0)` to be present: [3](#0-2) 

In the "Stateless Interaction" branch (`stack.signerAddress == address(0)` or `op.invokeWallet == false`), `verifyWallet` skips all signature verification and the op is executed directly with an attacker-chosen `endpoint`, `callData`, and `value`, drawn from Emporium's own ETH balance: [4](#0-3) [5](#0-4) 

The outer `Hinkal.transact` balance/equality check only tracks `Hinkal`'s own balance changes (`getBalancesForArray(circomData.erc20TokenAddresses)` on the `Hinkal` contract) and is likewise scoped to `circomData.erc20TokenAddresses`; it never inspects `Emporium`'s balance at all: [6](#0-5) [7](#0-6) 

So the equality that the `Emporium` balance-change loop is meant to enforce ("total change of emporium balance = what was moved to emporium + how emporium balance changed through the ops") is broken for any token type absent from the caller-chosen `erc20TokenAddresses` array — most importantly native ETH (`address(0)`), which is never forced into that array by any check in `dimensionsCheck`, `getHashedCalldata`, or the circuit's public-signal binding (the circuit only proves `calldataHash` integrity of whatever `erc20TokenAddresses` the prover chose to include, it does not force ETH's inclusion).

This directly mirrors the DEXRouter bug class: value (ETH) is moved by an external/arbitrary call but is never counted in the balance equation that is supposed to gate it.

### Impact Explanation
Any unprivileged EOA holding a valid (even zero-value) shielded UTXO can build a proof/`circomData` that:
1. Sets `externalActionData.externalActionId` to the Emporium action id.
2. Omits `address(0)` from `erc20TokenAddresses` (uses only some unrelated ERC-20 token, or none).
3. Sets `EmporiumStack.signerAddress = address(0)` (stateless path, no wallet signature required).
4. Supplies an op `{endpoint: attacker, invokeWallet: false, value: <Emporium's current ETH balance>, callData: ""}`.

`runAction` will send Emporium's ETH balance to the attacker while the post-call balance check only inspects the token(s) actually listed in `erc20TokenAddresses`, so the ETH loss is invisible to the `balanceChange >= 0` guard and never reverts. This is theft of protocol/relay-fee ETH sitting on the Emporium contract by an unprivileged actor — meets the High severity bar ("theft ... of protocol/relay fees ... executing calls or moving assets a wallet owner or prover never authorised", since ETH belonging to other users/relay is moved without their authorization).

### Likelihood Explanation
Likelihood is High whenever Emporium holds any residual ETH balance (e.g., from relay-fee ETH held pending `sendToRelay`, rounding dust from prior `handleOut` transfers, or a deposit whose corresponding op reverted mid-batch on an earlier tx and left ETH behind). The attack requires only a normal, unprivileged shielded transaction with attacker-chosen `erc20TokenAddresses`/`EmporiumStack` fields — no admin, relayer, or third-party key is needed.

### Recommendation
Force `address(0)` (native ETH) to always be included in the balance-tracked set for Emporium's `runAction`, independent of the caller-chosen `erc20TokenAddresses` array (e.g., always snapshot and re-check `address(this).balance` for ETH, or require `erc20TokenAddresses` to include `address(0)` whenever any op has `value > 0`). Alternatively, sum all `op.value` used in "Stateless Interaction" calls and require it not exceed the ETH portion of `deltaAmountChanges` moved in for that specific call, closing the untracked-token gap entirely.

### Proof of Concept
1. Emporium contract has, e.g., 0.1 ETH of leftover balance from unrelated prior activity (relay-fee remainder / rounding dust) — `address(emporium).balance == 0.1 ether`.
2. Attacker (unprivileged EOA) crafts a normal shielded transaction with:
   - `circomData.erc20TokenAddresses = [someERC20]` (ETH `address(0)` deliberately excluded)
   - `circomData.externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: emporium, externalActionMetadata: abi.encode(EmporiumStack{ signerAddress: address(0), ops: [ EmporiumOperation{ endpoint: attackerAddr, invokeWallet: false, value: 0.1 ether, callData: "" } ] , ... })}`
3. Circuit/proof is generated normally (the metadata is only bound into `calldataHash`, which the prover fully controls since they know their own note's secrets — no third-party signature required for `signerAddress == address(0)`).
4. `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction` executes the op, sending 0.1 ETH to `attackerAddr`.
5. `balancesBefore`/`balancesAfter` loop only iterates over `[someERC20]`, so the 0.1 ETH ETH decrease is never checked; `balanceChange` for `someERC20` stays `>= 0` and the transaction succeeds, netting the attacker 0.1 ETH they never funded.
