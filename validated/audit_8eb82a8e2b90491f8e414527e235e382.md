### Title
Webhook `shop` domain is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC signature computed over the raw request body, but then trusts the `shop` (and `topic`/`webhook_id`/`api_version`) values taken from HTTP headers that are never included in that HMAC computation. Because the signed bytes (`raw_body`) and the identity field the app actually acts on (`shop` header) are disjoint, any request carrying a previously-observed valid `(body, hmac)` pair can be replayed with an arbitrary `x-shopify-shop-domain` header and will still pass validation, causing the handler to process the webhook under an attacker-chosen tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` reads the signature from the `hmac-sha256` header, and `to_signable_string` — the data that gets HMAC-verified — returns only the raw body: [1](#0-0) 

Note in particular that `shop` is read straight from the `shop-domain` header and is completely outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e. the body) against the secret-derived signature — it has no knowledge of, or binding to, the `shop` header: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately forwards the unauthenticated `request.shop` value into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identifier: [4](#0-3) 

The gem's own documentation instructs app developers to key their business logic (job enqueuing, storage lookups, etc.) directly off `data.shop`: [5](#0-4) 

This breaks the intended identity binding: `hmac_valid(raw_body) == true` is treated as equivalent to `shop_header == shop_that_actually_sent_this_body`, but those are two independent equalities — the gem verifies the first and blindly accepts the second.

### Impact Explanation
Any actor who can install the app on their own shop (an ordinary, unprivileged action — no special credentials, no access token, no leaked secret required) legitimately receives valid `(raw_body, hmac)` pairs signed by the app's `api_secret_key` for their own shop's webhooks. Because the `shop-domain` header is not part of the signed material, that same attacker can resend the identical body + HMAC to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with an arbitrary victim shop's domain (shop domains are not secret — they are public `*.myshopify.com` names). `Registry.process` will accept the forged request as valid and dispatch it to the handler labeled with the victim's shop, per the documented flow. Depending on how the host app uses `data.shop` (session/store lookup, job dispatch, data writes keyed by shop), this enables cross-tenant data confusion/corruption — data intended for the attacker's own shop gets attributed to and processed against a different merchant's tenant context, which matches the "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs the capability any legitimate app installer already has (install the app to receive one legitimately-signed webhook), plus the ability to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — no secret key, token, or privileged access is required. The gem provides no mitigation (no binding of `shop` into the signed payload, no comparison against the shop from any authenticated source).

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the data that is HMAC-verified, or otherwise cross-check the header-derived `shop` against an authenticated source (e.g., validate that the shop belongs to a session/installation the app already trusts) before constructing `WebhookMetadata`. At minimum, `to_signable_string` should not allow tenant-identifying headers to bypass the signature boundary — consider verifying the full header+body construction Shopify actually signs, or require the app to independently confirm shop ownership before trusting `data.shop`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook: body `{}`, header `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (`@raw_body`) against the HMAC — this still passes since the body/HMAC pair is genuinely valid.
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop == "victim-shop.myshopify.com"`, and the app's handler processes the webhook believing it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
