### Title
Webhook shop-domain header is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop-domain` header used to attribute that payload to a specific merchant tenant is never included in the signed material. An attacker who legitimately controls one shop (and therefore receives genuine, correctly-signed webhooks for that shop from Shopify) can replay the same body/HMAC pair while swapping the `shop-domain` header to impersonate a different, victim shop to the host application.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, by contrast, is read directly from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — i.e., "were these body bytes signed with our `api_secret_key`" — and then immediately dispatches to the registered handler using `request.shop` as the tenant identity, without any check that the signature also covers that shop value: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body, in the webhook case) using the app's shared `api_secret_key`: [4](#0-3) 

Because a single app has one `api_secret_key` shared across every merchant that installs it, any merchant who installs the app receives genuinely-signed webhooks (valid `hmac` over some body `B`) for their own store. That merchant can then re-POST the exact same `(body=B, hmac=HMAC(B))` pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will accept it (the HMAC check passes — it never covered `shop`) and hand the handler a `WebhookMetadata` record where `shop` is the attacker-chosen victim domain but the `body`/`topic` are attacker-controlled content that was only ever authenticated for the attacker's own store.

This is precisely the class of bug described in the report's rules: "a shop authenticated versus the shop stored as a session key" — the gem authenticates *that Shopify (or holder of the secret) produced this byte stream*, but the host application's downstream logic almost always keys per-tenant state (offline session lookup, DB records, `app/uninstalled` handling, billing state, etc.) off `request.shop`, which is not part of what was authenticated.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata#shop` to look up or mutate per-tenant records (session/token lookup, uninstall processing, GDPR/customer-data handlers, billing webhooks), an attacker who is a legitimate merchant of the app can forge webhook events attributed to a **different tenant** by replaying a validly-signed body under a spoofed `shop-domain` header. This falls into the "cross-tenant access" Critical impact category — an unprivileged app installer can inject fabricated events for another merchant's tenant into the host application, without ever needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
This requires only that the attacker be an ordinary installer of the app (no elevated privileges) — a trivial bar for any public Shopify app. It requires no secret material beyond what Shopify legitimately hands them for their own store's webhooks, and no interaction with the victim. The only prerequisite is that the host application's webhook handler trusts `WebhookMetadata#shop` for tenant attribution, which is exactly the documented/intended usage pattern of this API (`ShopifyAPI::Webhooks::WebhookHandler#handle(data:)` where `data.shop` is the documented tenant identifier).

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signed material that `HmacValidator` checks for webhooks, or otherwise cryptographically tie the shop identity to the payload before it is exposed via `WebhookMetadata`. At minimum, document prominently that `shop` on a `Webhooks::Request`/`WebhookMetadata` is **not** authenticated by the HMAC and must not be trusted as a tenant identifier without independent verification (e.g., cross-checking against an already-known installed shop list) before being used for session/tenant lookups.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. an `orders/create` POST with body `B` and header `x-shopify-hmac-sha256: HMAC(B, api_secret_key)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical request to the host app's webhook endpoint, changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to `victim.myshopify.com`, leaving body and HMAC untouched.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(body, api_secret_key)` and finds it matches — validation passes: [5](#0-4) 
4. The registered `WebhookHandler` receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, even though Shopify never issued this event for the victim's store.
