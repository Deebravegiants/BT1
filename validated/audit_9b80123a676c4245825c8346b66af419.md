## Finding

### Title
Fee-on-transfer input tokens cause escrow over-crediting in Tron `IntentGatewayV2.placeOrder`, leading to insolvency/fund freezing on withdrawal - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron fork of `IntentGatewayV2` credits `_orders[commitment][token]` with the user-declared input amount (minus protocol fee only), without ever verifying how many tokens the contract actually received via `safeTransferFrom`. If an input token charges a transfer fee (the exact fee-on-transfer scenario described in the report, e.g. a future fee-enabled USDT/USDT-like token), the gateway records more escrowed tokens than it actually holds, corrupting the shared token-balance accounting across all orders.

### Finding Description
In `placeOrder`, the non-predispatch escrow path simply does: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

Neither `order.inputs[i].amount` nor `reducedInputs[i].amount` (used to credit `_orders`) is ever adjusted for the actual amount the contract received from `safeTransferFrom`. The commitment itself is also computed from the declared/protocol-fee-reduced amount, not the actually received amount: [2](#0-1) 

This is a direct contrast to the canonical EVM implementation of the same contract, which explicitly guards against this exact class of bug by measuring the balance delta before crediting escrow: [3](#0-2) 

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```

There is also an explicit code comment in the same file acknowledging this exact fee-on-transfer risk class and mitigation: [4](#0-3) 

The predispatch escrow path in the Tron file has the same gap — it checks `IERC20(token).balanceOf(dispatcher) >= requiredAmount` but still credits escrow with the pre-fee `reducedInputs[i].amount` rather than the delta actually transferred back to the gateway: [5](#0-4) 

Because `_orders[commitment][token]` is a bookkeeping entry against a single shared ERC20 balance held by the contract for all orders using that token, over-crediting one order's escrow effectively steals backing balance from other orders using the same token.

### Impact Explanation
On `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, or from `cancelOrder` same-chain path), the contract transfers out the escrowed (inflated) `amount` recorded in `_orders`: [6](#0-5) 

Since the real on-chain balance for that fee-on-transfer token is strictly less than the sum of all outstanding `_orders[...][token]` entries, the shortfall means:
- Some legitimate order's withdrawal will fail or leave the beneficiary short of the full escrowed value, since the actual balance runs out before all bookkeeping entries can be honored — a permanent freezing of funds for other users' orders denominated in the same token.
- Whoever redeems first can drain the actual balance, at the expense of later, legitimately-entitled order beneficiaries.

This satisfies the "permanent freezing of funds" bar from the validation criteria, and is reachable by any unprivileged user simply calling `placeOrder` with a fee-on-transfer input token — no privileged role required.

### Likelihood Explanation
Likelihood depends on a token used as an intent input actually implementing a transfer fee. This is squarely the report's threat model (fee-upgradeable stablecoins like USDT) and is already treated as a first-class risk in the sibling EVM contract (which was explicitly hardened against it), confirming the protocol's own risk model includes this token class as in-scope/expected on this integration surface.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure the actual balance delta received by the contract (and by the predispatch `dispatcher`) before crediting `_orders`, and compute/derive the commitment and protocol-fee reduction from the actually-received amount rather than the caller-declared `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and register it as an input token.
2. User A calls `placeOrder` with `inputs = [{token: FOT, amount: 1000}]`. Gateway actually receives 990 FOT via `safeTransferFrom`, but `_orders[commitmentA][FOT] = 1000` (minus protocol fee if any) is recorded — 10 FOT more than actually held.
3. User B places a second order also using FOT, similarly over-credited.
4. When both orders are filled/redeemed via `withdraw()`, the sum of `_orders[...][FOT]` amounts owed exceeds the contract's actual FOT balance, so the second (or later) redemption's `token.call(transfer...)` either reverts (funds frozen) or, if partial transfers are tolerated, silently under-delivers — confirming the escrow accounting has diverged from real custody. [7](#0-6)  shows the equivalent test that the EVM (non-Tron) contract passes precisely because it measures actual received balances — the Tron contract has no equivalent protection or test coverage for this path.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
