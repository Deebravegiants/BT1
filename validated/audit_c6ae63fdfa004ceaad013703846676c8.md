### Title
Webhook shop-domain header not bound to HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`, whose signable string is defined by `Request#to_signable_string` as `@raw_body` only. The `shop` value later handed to application handlers as the tenant identity comes from the `shop-domain` HTTP header, which is never included in the HMAC-signed material. As a result, the `shop` field used to route/attribute the webhook is not bound to the request that was cryptographically authenticated, breaking the identity binding: `verified(hmac) == body` while `trusted(tenant) == header["shop-domain"]`, and `body ⊉ header["shop-domain"]`.

### Finding Description
`Request#to_signable_string` [1](#0-0)  returns only the raw JSON body, and `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic tie to that body [2](#0-1) .

`Registry.process` validates only the HMAC of the signable string (the body) and, once validated, immediately trusts `request.shop` (along with `topic`, `api_version`, `webhook_id`) to build the `WebhookMetadata` passed to the app's registered handler: [3](#0-2) .

`HmacValidator.validate`/`validate_signature` compute and compare the signature strictly against `verifiable_query.to_signable_string`, i.e., the body bytes, never the shop header: [4](#0-3) .

The `WebhookMetadata` struct that the app's handler receives carries `shop` as an authenticated-looking field even though it was never verified: [5](#0-4) .

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," reinforcing that host apps are expected to trust the full `WebhookMetadata` (including `shop`) as authenticated: [6](#0-5) .

Because a single `api_secret_key` is shared across all shops/tenants of the app (Shopify signs webhooks per-app, not per-shop), any merchant who has installed the app can legitimately trigger Shopify to send them body+HMAC pairs that are valid under the app's shared secret. That merchant can then replay the exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. Since the HMAC only covers the body, the signature still validates, and `Registry.process` will dispatch the handler with `shop` set to the victim's domain and attacker-controlled body content — a direct violation of the identity binding `authenticated_shop == handled_shop`.

### Impact Explanation
This enables cross-tenant access/injection: a malicious low-privilege user of the app (any merchant who installed it) can cause the host application to process attacker-controlled webhook data under another tenant's (victim shop's) identity, since the shop identity used for handler dispatch, data attribution, or session/tenant lookup is not part of the authenticated payload. Depending on how the host app trusts `data.shop` (e.g., to select which shop's DB row to update, or to attribute customer/order data), this can lead to injecting fabricated data into a victim tenant's records — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app author following the documented pattern of trusting `WebhookMetadata#shop` for tenant routing (as demonstrated in the gem's own `docs/usage/webhooks.md` example, which uses `data.shop` directly as `shop_domain`). No secrets beyond becoming a legitimate installer of the app are required; the attacker only needs to be an unprivileged merchant/tenant of the app to obtain a validly-signed body and then directly POST it to the app's public webhook endpoint with a forged shop header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material, or otherwise independently authenticate the shop domain against the shop that the webhook subscription (`webhook_id`) was actually registered for, before dispatching to handlers. At minimum, `Request#to_signable_string` should incorporate the shop-domain header (and other trusted routing fields) in the value that is HMAC-verified, and `Registry.process` should reject requests whose header-derived `shop` cannot be tied to the verified payload.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and triggers an event (e.g., `orders/create`) causing Shopify to POST a webhook to the app's shared endpoint, signed with the app's `api_secret_key`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`
   - Body: attacker-controlled JSON (e.g., order note/customer fields containing crafted payload).
2. Attacker captures this exact `(raw_body, hmac)` pair.
3. Attacker sends a new POST directly to the app's public webhook endpoint (the same URL used for all shops), reusing the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker JSON>, ...)`, causing the host app to process attacker data under the victim's tenant identity.
