### Title
Path Traversal in `HttpClient.path()` via unsanitized `File.name` allows writes outside `TemporaryDirectoryPath` - ([File: modules/networking-mobile/src/http/client.ts])

### Summary
`HttpClient.path()` builds the temp file URI by concatenating `TemporaryDirectoryPath`, a UUID, and the raw `File.name` with no sanitization of path separators or `..` segments, then `HttpClient.asNativeFormData` calls `this.fs.writeFile(uri, ...)` with that unsanitized URI. Because this `HttpClient` is installed as the app's global `fetch` implementation, any code path in the wallet that performs a `fetch(...)` with a `FormData` body containing a `File` whose `name` is influenced by external data (e.g., an attachment name from an imported backup, a remote-config-driven upload flow, or a dapp/RPC-constructed request) can cause writes to attacker-chosen filesystem locations.

### Finding Description
`HttpClient.path()` constructs the write target as: [1](#0-0) 

`uniqueName` is `${uuid}-${fileName}` with no stripping of `/`, `..`, or null bytes, and `joinFragments` merely string-concatenates path fragments with `/` separators without normalizing `..`: [2](#0-1) 

Because the UUID prefix is glued to only the *first* path segment of `fileName`, any `/` characters inside `fileName` after the first one produce additional path segments that are *not* polluted by the UUID prefix. For example, `fileName = "x/../../../../data/data/com.exodus/databases/wallet.db"` yields `uniqueName = "<uuid>-x/../../../../data/data/com.exodus/databases/wallet.db"`. When this is passed as a filesystem path to `RNFS.writeFile` (real implementation, not the test mock), the OS/native layer resolves `<uuid>-x/..` back to the temp directory and then the remaining literal `..` segments walk further up, escaping `fs.TemporaryDirectoryPath` entirely.

`asNativeFormData` then unconditionally writes attacker-influenced base64 content to that resolved path: [3](#0-2) 

No validation exists anywhere in `File`, `FormData`, or `HttpClient` that restricts `name` to a safe basename (no `/`, no `..`, no null bytes): [4](#0-3) [5](#0-4) 

Critically, this `HttpClient` instance is wired up as the **global** `fetch` for the entire React Native app: [6](#0-5) 

This means every call site in the wallet app that does `fetch(url, { body: someFormData })` with a `FormData`/`File` from `@exodus/networking-mobile/form` funnels through this vulnerable code, not just an isolated upload feature.

### Impact Explanation
If reached with an attacker-influenced filename, this allows an arbitrary file write with attacker-controlled content (subject to base64 decoding) to a path outside the sandboxed temporary directory, potentially colliding with or overwriting files adjacent to wallet storage on the device. The impact is bounded by OS-level app-sandbox permissions (the write is confined to the app's own storage container, since RNFS calls typically cannot escape the app data root even via `..`), but it can still corrupt or overwrite app-owned files (databases, caches, preference files) within that sandbox if a caller's file name is derived from external data.

### Likelihood Explanation
Exploitability is fully dependent on finding a concrete call site in the wallet app (not present in the currently indexed portion of this repo) where a `File` is constructed with a `name` value that is influenced by untrusted external input (an origin, dapp RPC payload, imported backup metadata, or remote-config response) and then passed through `fetch`'s `FormData` body. I was unable to locate such a call site in this codebase — the only production usage found is the generic global `fetch` shim installation; no upload/backup/attachment feature code that builds a `FormData` with an attacker-controlled `File.name` was found within the indexed files. This limits confidence that the "unprivileged attacker" precondition is currently satisfiable anywhere in this repository, though the primitive itself (unsanitized filename in a global fetch path) is a real, exploitable defect if such a call site exists or is later added.

### Recommendation
Sanitize `File.name` in `HttpClient.path()` before building the write URI: reject or strip `/`, `\`, `..`, and control/null-byte characters, and only allow the sanitized basename to be joined with a single directory separator, e.g. `path.basename(fileName).replace(/[^\w.-]/g, '_')`, then re-derive the MIME type/display name separately from the original `File.name` for the multipart `name` field. Additionally, normalize `joinFragments`' output and assert (e.g., via a startsWith check) that the resolved path stays within `fs.TemporaryDirectoryPath` before calling `writeFile`.

### Proof of Concept
Add to `modules/networking-mobile/src/http/client.spec.ts`:
```ts
it('should not allow path traversal via File.name', async () => {
  const writeFile = jest.fn()
  const client = new HttpClient(
    { writeFile, TemporaryDirectoryPath: '/tmp/files', unlink: jest.fn() },
    OperatingSystem.iOS,
    () => 'uuid',
    fetchMock
  )
  const data = new FormData()
  data.append(
    'file',
    new File(Buffer.from('evil'), 'x/../../../../data/data/com.exodus/databases/wallet.db')
  )

  await client.fetch('/upload', { method: 'POST', body: data })

  const [writtenPath] = writeFile.mock.calls[0]
  expect(writtenPath.startsWith('/tmp/files/')).toBe(true) // currently fails: path escapes temp dir
})
```
Expected: with the current implementation, the resolved `writtenPath` contains `..` segments that resolve outside `/tmp/files/`, failing the `startsWith` assertion; the fix should make the assertion pass by rejecting/sanitizing traversal sequences in `File.name`.

function joinFragments(fragments: string[], separator = '/'): string {
  return fragments
    .slice(1)
    .reduce(
      (joined, fragment) =>
        joined.endsWith(separator) ? `${joined}${fragment}` : `${joined}${separator}${fragment}`,
      fragments[0] ?? ''
    )
}
