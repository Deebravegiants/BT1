## Title
Webhook Shop/Topic Identity Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The gem's webhook verification (`ShopifyAPI::Utils::HmacValidator.validate`) authenticates only the raw request body bytes, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Webhooks::Registry.process` trusts these unauthenticated headers to build the `WebhookMetadata` passed to the host app's handler. Because a single app installation shares one `api_secret_key` across all of Shopify's tenants that send it webhooks, any merchant who has the app installed can capture one of their own genuinely-signed webhook deliveries (valid body + HMAC) and replay it against the app's webhook endpoint with a forged `shop-domain` header, causing the app to process it as an event belonging to a different, victim shop. This breaks the identity binding: `HMAC(body) valid` should imply `shop == the shop that produced this HMAC`, but the gem only checks the former.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Only `@raw_body` participates in the HMAC computation. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers with no cryptographic binding to the signed payload:

```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` validates only the body's HMAC, then forwards the unauthenticated headers straight to the host app's handler as trusted tenant identity:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`HmacValidator.validate` confirms only that `HMAC(secret, body)` matches the supplied signature — it never checks that the signature is unique to a specific shop, topic, or webhook id:

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

This is the same bug class as the external report: signed metadata omits the field that should bind it to a specific identity (there, the depositing wallet/expiry; here, the originating shop/topic/webhook-id), so a validly-signed message can be replayed under a different claimed identity. The equality that should hold is `verified_shop == shop_that_produced_this_signature`, but the gem only proves `HMAC(secret, body)` is valid — it never proves the `shop-domain` header is the one Shopify actually attached to that specific signed body.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who controls (or has legitimate access to) a shop with the app installed can generate a genuinely-signed webhook body of their choosing (e.g., by performing an action on their own store that triggers a webhook they've registered, such as `orders/create`), capture the `(raw_body, hmac)` pair, and replay it to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header (and potentially `webhook-id`/`api-version`). Because the app only trusts `Registry.process` to hand it `WebhookMetadata` with `shop: request.shop`, the app will process attacker-supplied body content as if it originated from the victim shop — potentially triggering data writes, order/customer state changes, or business logic scoped to the victim tenant using attacker-controlled JSON. This matches the "cross-tenant access" Critical impact category, since it defeats the per-shop identity boundary that webhook consumers rely on to isolate tenants.

### Likelihood Explanation
Any merchant who installs the app (an unprivileged, ordinary action requiring no leaked credentials, no access token, and no privileged account) can obtain a valid `(body, hmac)` pair for content they control, since Shopify signs webhooks with the app's single shared `api_secret_key` regardless of which shop triggered them. Replaying that pair to the app's public webhook URL with a spoofed `shop-domain` header is a simple unauthenticated HTTP request. The only prerequisite is that the host application (as most integrations do) trusts `WebhookMetadata#shop` from this gem as the tenant identifier without independently re-verifying it — which is exactly the API contract this gem exposes.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind them to the payload before use, mirroring the report's recommendation to add an expiry/identity binding to signed metadata. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` into the signable string (or the library should document loudly that host applications must independently authorize `shop` against a known/registered tenant list before trusting `WebhookMetadata#shop`), so `Registry.process` cannot be tricked into attributing a validly-signed body to the wrong shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives a legitimate webhook (e.g., `orders/create`) with a Shopify-computed `X-Shopify-Hmac-Sha256` header over some `raw_body` JSON the attacker fully controls (they can shape order data they created).
2. Attacker captures `(raw_body, hmac)` from that legitimate, correctly-signed delivery.
3. Attacker sends a POST directly to the app's public webhook endpoint with:
   - Body: the captured `raw_body` (unchanged, so HMAC still validates)
   - Header `x-shopify-hmac-sha256`: the captured, valid signature
   - Header `x-shopify-shop-domain`: `victim.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged
4. `Webhooks::Request.new` accepts these headers; `Utils::HmacValidator.validate` succeeds because only `raw_body` is checked against the shared secret [5](#0-4) .
5. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and the attacker-controlled body [6](#0-5) , causing the host application to act on attacker-controlled data under the victim tenant's identity.
