## Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers — none of which are covered by that signature — to decide which tenant and which handler the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string` (i.e. the body): [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated headers: [3](#0-2) 

`Registry.process` validates only the body HMAC, then dispatches using `request.topic` (to look up the handler) and passes `request.shop` straight into the handler's `WebhookMetadata`: [4](#0-3) 

This is the same root-cause class as the referenced report: a value that is *acted upon* (here, the `shop`/`topic` used for tenant/handler routing, analogous to `totalCdsDepositedAmount` being adjusted by an unrelated quantity) is not bound to the value that was actually *verified* (the HMAC only attests to body integrity, not to which shop/topic it belongs to). The equality that should hold — `shop header used for dispatch == shop the HMAC-signed body was actually generated for` — is never enforced.

### Impact Explanation
An attacker who can obtain any one genuine `(raw_body, hmac)` pair (e.g., by installing the target app on their own store and capturing a real webhook delivery) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and/or substituting `X-Shopify-Topic` for a different registered topic. Because `HmacValidator.validate` only checks the body, the tampered request still passes verification, and the host application's handler receives attacker-chosen `shop`/`topic`/`webhook_id` values bound to a body it was never actually signed for. This produces cross-tenant data corruption/injection: a webhook payload legitimately generated for shop A gets attributed to shop B, or a body of one topic type gets processed under a different topic's handler logic.

### Likelihood Explanation
Exploitation requires only an HTTP client and one genuine sample delivery (trivially obtainable by installing the app, which is normal for any unprivileged internet user targeting a public app), so likelihood is high for any app relying on this gem's `Webhooks::Registry` for tenant/topic dispatch as documented.

### Recommendation
Bind the shop/topic/webhook identity into the authenticated material — e.g., include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, or independently verify that the `shop` header matches an actively known/authorized session before dispatching, rather than trusting header values that sit outside the HMAC's coverage.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`; trigger an `orders/create` webhook and capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` (a genuine `(B, H)` pair signed with the app's real secret).
2. Replay to the app's webhook endpoint:
```
POST /webhooks
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: <any>

B
```
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) .
4. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` even though the body was never generated for that shop [6](#0-5) , causing the host application to process attacker-controlled data under the victim tenant's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
