## Analysis

The bug class in the report — a value being *acted on* while a different value is *cryptographically verified* — maps cleanly onto how webhook requests are authenticated in this gem.

### The binding that should hold
`hmac == HMAC(secret, raw_body || shop || topic || ...)` for the `shop` value the handler ultimately trusts.

### What the code actually does

`ShopifyAPI::Webhooks::Request` reads `shop`, `topic`, `webhook_id`, and `api_version` straight from HTTP headers, none of which are covered by the signature: [1](#0-0) 

But the signable string used for HMAC verification is only the raw body: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string`, i.e. the body — it never touches `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` when building the data passed to the app's handler: [4](#0-3) 

Compare this with OAuth's `AuthQuery`, which does the correct thing — `shop` is explicitly part of the signed parameter set that composes `to_signable_string`: [5](#0-4) 

So there's an internal inconsistency in this gem: the OAuth callback binds `shop` into the HMAC-verified content, but the webhook request does not, even though `Registry.process` treats a successful HMAC check as license to trust `request.shop`.

### Exploit path
An attacker who controls their own shop and has installed the app can trigger a webhook for their own store (e.g., by creating a product/order/customer with attacker-chosen content). Shopify signs that webhook body with the app's `client_secret` and delivers it with `x-shopify-shop-domain: attacker-shop.myshopify.com`. The attacker captures `(raw_body, hmac)` and replays the exact same body/HMAC to the app's webhook endpoint, but swaps the `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body against the HMAC, and the attacker has a genuinely valid body+HMAC pair). `Registry.process` then calls the app's handler with `shop: "victim-shop.myshopify.com"` even though the payload was never actually associated with that shop by Shopify. If the host application uses `request.shop`/`WebhookMetadata#shop` to select which tenant's data store to write into (a very common pattern for webhook consumers), this becomes cross-tenant data injection under the guise of a validly-signed webhook.

### Title
Webhook `shop` field is trusted by `Registry.process` but not covered by HMAC verification — ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers. `Registry.process` treats a passing HMAC check as authorization to trust `request.shop`, breaking the equality `hmac == HMAC(secret, body || shop)` that a correct implementation (as seen in `AuthQuery`) enforces.

### Finding Description
`HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) only verifies `verifiable_query.to_signable_string` against the received HMAC. For webhooks, `to_signable_string` returns solely `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop` is pulled from the `x-shopify-shop-domain`/`shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) with no cryptographic tie to the signature. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) validates the HMAC and then passes `request.shop` straight to the app's handler as trusted identity for the event. Any request with a valid `(body, hmac)` pair — regardless of which shop it was originally generated for — will be accepted with an attacker-chosen `shop` value.

### Impact Explanation
This allows cross-tenant impersonation: a party who can obtain one genuinely-signed webhook body/HMAC pair (e.g., from their own installed shop) can relabel it as belonging to any other shop domain, and the app built on this gem will process it as authentic data for that victim shop. Applications that key persistence, authorization, or session lookups off `request.shop`/`WebhookMetadata#shop` (a standard usage pattern per this gem's own docs) can have attacker-controlled data attributed to and stored under a victim tenant.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (a normal, unprivileged action) and send raw HTTP requests to the app's public webhook endpoint with a forged `shop`-domain header — no access to `api_secret_key`, access tokens, or other credentials is needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, mirroring how `AuthQuery#to_signable_string` includes `shop` in its signed parameters, or independently authenticate the shop domain against session/installation state before trusting it in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook-eligible action (e.g., product create) with arbitrary content.
2. Shopify delivers `POST /webhooks` with header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, and the raw JSON body.
3. Attacker replays the identical body and HMAC header to the same endpoint, replacing only `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) returns `true` because it only checks body vs HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process attacker-controlled data as belonging to the victim tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
