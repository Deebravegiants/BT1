Based on my investigation, I found a genuine analog: the hostile pre-seed "M-02 regime" in `Bonding.sol`'s graduation LP seeding, which is functionally the same bug class as the ERC4626 first-depositor share manipulation — an attacker skews the "first mint" ratio into a pool before the protocol's real deposit lands, and a bounded correction mechanism cannot fully undo it, so the pool (the protocol's permanently-locked LP position) opens away from fair price.

### Title
Budget-capped rebalance swap lets a hostile HyperSwap V2 mint pre-seed permanently lock the protocol's graduation LP at a materially wrong price - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding._seedUniswapV2Direct`'s Regime-3 defense (`_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`) tries to correct a hostile `pair.mint` pre-seed by swapping the pool back to the curve-close ratio before depositing, but the rebalance swap is capped at 99% of the available inventory side via `_swapBudget` [1](#0-0) . When the pre-seed ratio is extreme enough that the theoretically required no-fee swap input exceeds this budget, `_noFeeSwapInput` silently returns the capped `maxSwap` instead of the corrective amount [2](#0-1) , and the subsequent `_routerDepositAndDispose` deposits at the still-skewed post-swap ratio into the permanently-locked LP held by `LPLock` [3](#0-2) , which has no withdraw path in v1 [4](#0-3) .

### Finding Description
This is directly analogous to the ERC4626 "first depositor" class: just as a malicious first depositor can donate assets to skew an empty vault's share price before a real depositor mints, an unprivileged attacker can front-run `Bonding.finalizeGraduation` by calling `factory.createPair` and `pair.mint(attacker)` with a self-funded, deliberately lopsided (TOKEN, LT) ratio before Phase 2 runs — exactly the scenario the protocol's own tests exercise via `_grieferMintPreSeed` [5](#0-4) .

The protocol's defense recognizes and tries to fix this ("Regime 3" in `_seedUniswapV2Direct`) by computing a no-fee corrective swap (`_noFeeSwapInput`) and executing it directly against the pair before depositing the remaining inventory via the router's `addLiquidity`. However, the corrective swap is deliberately capped at `_swapBudget(budget) = (budget * 99) / 100` of the available side [6](#0-5) . The protocol's own regression test `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` proves that a sufficiently lopsided pre-seed (e.g. TOKEN reserve at 1% of `tokensForLP`, LT reserve at 200× `ltFromPair`) drives the theoretically-required swap input past this cap, so the pool ends up depositing at a ratio roughly 2× off the curve-close price, and the test explicitly asserts `_poolPriceLtPerToken(...)` is more than 20% off curve-close (`* 12 / 10`) [7](#0-6) . The fuzz test `testFuzz_hostilePreSeed_neverProfitable_neverBricks` covers `seedMultiple` up to 1000×, confirming this "M-02 regime" is systematically reachable for any sufficiently large pre-seed [8](#0-7) .

Because `LPLock.recordLock` is the terminal, one-shot destination for this LP and the contract has no withdraw/rescue path in v1 [9](#0-8) , the mispriced LP position is permanently locked — the protocol can never rebalance or exit it, unlike the attacker's own LP which arbitrageurs will trade against.

### Impact Explanation
This satisfies the "LP seeded away from the curve close price" impact class explicitly. Any unprivileged wallet holding curve tokens (bought normally via `Zap.buy`) can trigger this by front-running `finalizeGraduation` with a self-funded `pair.mint`. The result is a HyperSwap V2 TOKEN/LT pool that opens materially (>2×) off the last curve price, and this mispricing is baked permanently into `LPLock`'s locked position since there is no rebalance or withdrawal mechanism. Post-graduation traders using `Zap` also inherit this wrong price until arbitrage closes the gap — but arbitrage profit is extracted from the pool's reserves, i.e., from the protocol's own locked LP share, a real and irreversible value transfer out of protocol/LP funds.

### Likelihood Explanation
The precondition is cheap and fully within reach of a single unprivileged actor: buy a small amount of curve tokens (any wallet can do this via `Zap.buy`/`createToken`), wait for graduation Phase 1 to fire (`_enterGraduating`, inline on a threshold-crossing buy or via permissionless `triggerGraduation`), then front-run Phase 2 (`finalizeGraduation`, itself permissionless) with `factory.createPair` + token/LT transfers + `pair.mint(self)` at a ratio designed to exceed the 99%-of-inventory swap budget. The two-phase split (Phase 1 caches amounts, Phase 2 is a separate, permissionless, keeper-driven transaction ~60s later) gives a guaranteed window for this front-run, and the attack's cost is bounded by whatever dust/LT the attacker seeds — while the confirmed effect (pool opening >20%–2x off price) is deterministic given a sufficiently large `seedMultiple`, as proven by the protocol's own fuzz test.

### Recommendation
Widen the corrective-swap budget beyond the current 99%-of-one-side cap for large pre-seeds, or add a second-pass rebalance step (further swap using the router's `addLiquidity`-supplied leftover) so the deposit ratio converges arbitrarily close to curve-close regardless of pre-seed magnitude, similar to how ERC4626 mitigates first-depositor manipulation by decoupling share price from a single attacker-controlled deposit. Alternatively, give `LPLock` (or `Bonding`) an owner-gated, delayed rebalance/exit path so a detected M-02-regime graduation can be corrected after the fact rather than permanently locking a mispriced position.

### Proof of Concept
Use the existing repro in `test/TwoPhaseGraduation.t.sol`:
1. Launch a token and drive it into `Graduating` via `_enterGraduating` [10](#0-9) .
2. Read cached `(tokensForLP, ltFromPair)` from `bonding.pendingGraduation(tokenAddr)`.
3. As `griefer`, set `reserveToken = tokensForLP / 100` and `reserveLt = ltFromPair * 200`, then call `_grieferMintPreSeed(tokenAddr, reserveToken, reserveLt)` to `factory.createPair` + `transfer` + `pair.mint(griefer)`.
4. Call `bonding.finalizeGraduation(tokenAddr)` — it succeeds (no brick) but `_poolPriceLtPerToken(hyperPair, tokenAddr)` is confirmed >20% off `ltFromPair/tokensForLP`, matching `test_hostilePreSeed_budgetCappedSwap_isNotProfitable` [11](#0-10) .
5. The resulting LP is locked in `LPLock` forever with no way to withdraw or correct it [4](#0-3) .

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

    /// @notice Record an LP lock. LP tokens must already sit at this address.
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }

    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
