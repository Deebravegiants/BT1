### Title
Session-key private keys for IntentGatewayV2 orders are persisted unencrypted in browser `localStorage` - ([File: sdk/packages/sdk/src/storage/index.ts])

### Summary
The Hyperbridge SDK's intent-solver-selection flow generates a per-order "session key" whose private key authorizes which solver may fill a user's escrowed order. This raw private key is persisted in plaintext via `unstorage`'s `localStorage`/`indexedDB` drivers with no encryption, mirroring the CWE-256 pattern in the reported Parse SDK advisory (plaintext credential stored in browser storage).

### Finding Description
`OrderPlacer.placeOrder` generates a fresh ephemeral session key for every order and immediately stores its raw `privateKey` via `this.ctx.sessionKeyStorage.setSessionKeyByAddress(...)`, later updating the same record with the order commitment: [1](#0-0) [2](#0-1) 

`createSessionKeyStorage` writes this `SessionKeyData` (which includes `privateKey: HexString`) as a plain `JSON.stringify` blob keyed by `session-key:` / `session-key-address:` prefixes, with no encryption at rest: [3](#0-2) 

The default storage driver is selected by `detectEnvironment()`, which picks `"localstorage"` whenever `globalThis.localStorage` exists (i.e., any browser context) unless the caller explicitly overrides it: [4](#0-3) 

The browser driver then wires this directly to `unstorage/drivers/localstorage` (or `indexeddb`), both of which store data unencrypted, origin-scoped but readable by any JavaScript running on that origin: [5](#0-4) 

This session key is later read back by `Bid.signSelection()` to sign the on-chain `SelectSolver` EIP-712 message, which the `IntentGatewayV2`/`SolverAccount` on-chain validation trusts to authorize a specific solver to fill the order: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any unprivileged script able to read the origin's `localStorage`/`indexedDB` (e.g., a supply-chain-compromised dependency, a malicious ad/widget on the integrating dApp, or an XSS payload) can exfiltrate the plaintext session private key for a pending, escrowed order. With that key the attacker can sign a valid `SelectSolver` message and authorize a colluding "solver" account of their choosing for that order's commitment, which `IntentGatewayV2.select()`/`SolverAccount.validateUserOp` will accept as legitimate on-chain, since the contracts only verify the EIP-712 signature recovers to the address stored in `order.session` — they have no way to know the key was stolen rather than used by its rightful owner. This is a real fund-safety-relevant credential (it gates who is allowed to claim the user's escrowed input tokens), not a cosmetic secret, so its plaintext exposure in a widely reachable browser storage sink is a legitimate reachable analog to the reported CWE-256 issue.

### Likelihood Explanation
Exploitation requires a separate vector to actually read the victim's `localStorage`/`indexedDB` (XSS, malicious browser extension, compromised third-party script on the dApp origin, or physical/device access) — the SDK itself does not leak the key over the network. This is a real but conditional/secondary-vector risk: the underlying design decision (storing raw signing keys in unencrypted, JS-readable browser storage by default, with no opt-in encryption path) is what elevates the bug class from a documentation-only note into a genuine analog of the reported plaintext-credential-storage issue.

### Recommendation
Do not persist the raw session private key unencrypted in `localStorage`/`indexedDB`. Options: (1) encrypt the `SessionKeyData.privateKey` at rest with a key derived from a user-supplied passphrase or a non-extractable WebCrypto key before calling `baseStorage.setItem`, decrypting only in memory when signing; (2) keep session keys purely in memory (or session-only storage) and require the caller to re-supply the key across page reloads rather than defaulting to persistent browser storage; (3) at minimum, warn/opt-out loudly when `detectEnvironment()` resolves to `"localstorage"`/`"indexeddb"` and document the exposure so integrators can choose a safer driver.

### Proof of Concept
1. A user places an IntentGatewayV2 order via the SDK; `OrderPlacer.placeOrder` generates a session key and calls `sessionKeyStorage.setSessionKeyByAddress(address, { privateKey, address, createdAt })`.
2. Because the dApp runs in a browser, `detectEnvironment()` resolves to `"localstorage"`, and the key is written unencrypted under `hyperbridge/sdk/proof/session-key-address:<address>` in `window.localStorage`.
3. Any script co-located on the origin (malicious npm dependency, injected XSS payload, malicious browser extension with storage access) reads `localStorage.getItem(...)`, parses the JSON, and recovers the raw `privateKey`.
4. The attacker calls `CryptoUtils.signSolverSelection(commitment, attackerSolverAddress, domainSeparator, stolenPrivateKey)` to produce a valid `SelectSolver` signature, then submits it (via `IntentGatewayV2.select` / `SolverAccount.validateUserOp`) to authorize their own colluding solver for the user's already-escrowed order, exactly as the legitimate flow in `Bid.execute()` does.

const detectEnvironment = (): StorageDriverKey => {
	if (typeof process !== "undefined" && !!process.versions?.node) return "node"
	if (typeof globalThis !== "undefined" && "localStorage" in globalThis) return "localstorage"
	if (typeof globalThis !== "undefined" && "indexedDB" in globalThis) return "indexeddb"
	return "memory"
}

/**
 * Session key data stored for each order
 */
export interface SessionKeyData {
	/**
	 * The private key as a hex string
	 */
	privateKey: HexString

	/**
	 * The derived public address
	 */
	address: HexString

	/**
	 * The order commitment this session key is associated with.
	 * This may be undefined for session keys that were created
	 * but whose corresponding order has not been finalized yet.
	 */
	commitment?: HexString

	/**
	 * Timestamp when the session key was created
	 */
	createdAt: number
}

/**
 * Creates a session key storage instance for IntentGatewayV2 orders.
 * The storage is used to persist session key private keys so they can be
 * used later to sign solver selection messages.
 *
 * @param options - Optional configuration for the storage driver
 * @returns A storage instance with methods to get, set, and remove session keys
 */
export function createSessionKeyStorage(options: SessionKeyStorageOptions = {}) {
	const key = options.env ?? detectEnvironment()
	const driver = loadDriver({ key, options }) ?? inMemoryDriver()
	const baseStorage = createStorage({ driver })

	const SESSION_KEY_PREFIX = "session-key:"
	const SESSION_KEY_ADDRESS_PREFIX = "session-key-address:"

	/**
	 * Gets a session key by order commitment
	 */
	const getSessionKey = async (commitment: HexString): Promise<SessionKeyData | null> => {
		const storageKey = `${SESSION_KEY_PREFIX}${commitment}`
		const value = await baseStorage.getItem<string>(storageKey)
		if (!value) return null

		try {
			return JSON.parse(value) as SessionKeyData
		} catch {
			return null
		}
	}

	/**
	 * Gets a session key by session key address
	 */
	const getSessionKeyByAddress = async (address: HexString): Promise<SessionKeyData | null> => {
		const storageKey = `${SESSION_KEY_ADDRESS_PREFIX}${address.toLowerCase()}`
		const value = await baseStorage.getItem<string>(storageKey)
		if (!value) return null

		try {
			return JSON.parse(value) as SessionKeyData
		} catch {
			return null
		}
	}

	/**
	 * Stores a session key for an order commitment
	 */
	const setSessionKey = async (commitment: HexString, data: SessionKeyData): Promise<void> => {
		const storageKey = `${SESSION_KEY_PREFIX}${commitment}`
		await baseStorage.setItem(storageKey, JSON.stringify(data))
	}

        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
