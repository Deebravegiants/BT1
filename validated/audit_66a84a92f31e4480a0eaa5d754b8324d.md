Confirmed: `handleConsensus` requires `notFrozen(host)`, checking `host.frozen()` against `FrozenStatus.Incoming`/`FrozenStatus.All` [1](#0-0) [2](#0-1) , and `setFrozenState` is restricted to admin or handler [3](#0-2) .

### Title
Sequential mandatory-consensus submission path never unfreezes/refreezes the host, silently reverting or leaving the route unable to deliver mandatory consensus updates - (File: tesseract/consensus/admin-relayer/src/batch.rs)

### Summary
This is the closest analog to the Linux CVE-2024-26757 pattern (a guard/mode transition that the recovery/handling routine silently disregards, causing the intended state machine to desynchronize and the operation to hang/never complete). In Hyperbridge, `EvmHost` uses a `FrozenStatus` guard analogous to md's read-only flag, and `HandlerV2.handleConsensus` is gated by the `notFrozen` modifier exactly as `md_check_recovery` is gated by the read-write check [1](#0-0) . The admin-relayer's `submit_mandatory_sequential` function is documented and designed to perform `setFrozenState(None) → handleConsensus → setFrozenState(All)` as three sequential transactions [4](#0-3) , but the actual unfreeze and refreeze calls are commented out/dead code, leaving only the `handleConsensus` call executed [5](#0-4) .

### Finding Description
`submit_mandatory_sequential` is intended for chains that don't support EIP-7702 batched transactions (e.g. Soneium) and is explicitly documented to run three steps in order: unfreeze, submit consensus proof, refreeze [6](#0-5) . In the implementation, both the unfreeze (`setFrozenState(FROZEN_NONE)`) and refreeze (`setFrozenState(FROZEN_ALL)`) transaction-sending calls are commented out, along with their associated logging [7](#0-6) . Only the `handleConsensus` call is actually sent [8](#0-7) .

This produces two possible outcomes depending on the pre-existing frozen state of the host, both bad:
1. If the host's persistent state is `FrozenStatus.All`/`Incoming` (which is what the refreeze step is supposed to enforce as the "resting" state per the module doc), every subsequent `handleConsensus` call on a chain configured for `Sequential` mode will unconditionally revert with `HostFrozen()` from the `notFrozen` modifier [1](#0-0) . Mandatory consensus updates can never land on that chain through this path — this is a route permanently unable to deliver consensus/messages, directly matching the "route unable to deliver messages" acceptance criterion.
2. If an operator or migration leaves the host unfrozen (state `None`) to work around this, the code never re-applies `FrozenStatus.All`, so the host stays permanently unfrozen — defeating the entire purpose of the freeze-gate protection mechanism (which exists to block message dispatch when consensus/state proofs are stale or under dispute), i.e. the guard is silently ignored, the same bug class as `md_check_recovery()` ignoring the read-only guard.

This is precisely the same bug shape as the CVE: a state-transition guard (`_frozen` / `mddev->ro`) that a caller flips temporarily around a privileged operation, but the code path responsible for flipping it back never executes, so downstream logic either wrongly proceeds as if the guard were absent, or wrongly treats the guard as permanently set, breaking the intended liveness of the associated state machine.

### Impact Explanation
For any chain configured with `submission_mode = "sequential"`, mandatory consensus proof delivery is broken end-to-end: either it always reverts (denial of service on the consensus-update route, freezing the light client state permanently at its last verified height on that chain) or the safety freeze around Batched submissions is bypassed and the host is left permanently unguarded. Given `notFrozen` gates `handleConsensus`, `handlePostRequests`, `handleGetResponses`, and timeout handlers alike [9](#0-8) , an inconsistent frozen state either halts all message delivery for that state machine (funds and cross-chain calls stuck, matching "permanent freezing of funds"/"route unable to deliver messages") or removes the protocol's emergency-freeze safety net entirely.

### Likelihood Explanation
This is not attacker-triggered in the sense of a crafted transaction; it is a deterministic logic bug in the admin-relayer's designated `Sequential` code path that fires on every mandatory consensus submission for any chain configured with `submission_mode = "sequential"` (documented as intended for chains like Soneium that lack EIP-7702 support). Any operator selecting this mode is unconditionally affected, since the dead-code unfreeze/refreeze calls never execute regardless of proof validity.

### Recommendation
Restore or reinstate the commented-out `setFrozenState(FROZEN_NONE)` and `setFrozenState(FROZEN_ALL)` transaction submissions in `submit_mandatory_sequential`, preserving the documented `submit → await receipt → next` ordering, and ensure the refreeze step is attempted even when the `handleConsensus` step fails (as the surrounding comment already states is the intent) [10](#0-9) . Add integration coverage exercising the `Sequential` mode end-to-end against a host in `FrozenStatus.All` to catch regressions of this kind.

### Proof of Concept
1. Configure a chain in `admin-relayer` config with `submission_mode = "sequential"` [11](#0-10) .
2. Ensure the target `EvmHost` is at rest in `FrozenStatus.All` (its expected steady state per the module's own documentation of the three-step protocol) [12](#0-11) .
3. Trigger `submit_mandatory(client, message, SubmissionMode::Sequential)` [13](#0-12) .
4. Observe that `submit_mandatory_sequential` sends only the `handleConsensus` transaction (unfreeze/refreeze calls are dead code) [5](#0-4) , which reverts on-chain with `HostFrozen()` because `notFrozen(host)` sees `FrozenStatus.All` [1](#0-0) , `evm/src/core/HandlerV2.sol:144`. Mandatory consensus can never be delivered on this chain via the admin-relayer's sequential path.
