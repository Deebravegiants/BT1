### Title
Withdrawal status misattributed across same-asset withdrawals in a batch - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal purely by matching `assetId`, ignoring the `index` that uniquely identifies which withdrawal within a batched NEAR transaction is being queried. When a single transaction contains two or more withdrawals of the same token, every caller querying any of those withdrawal indices receives the result of whichever entry `Array.prototype.find` happens to return first, so the reported status/txHash can belong to a different withdrawal than the one being polled.

### Finding Description
`createWithdrawalIdentifier` builds a `WithdrawalIdentifier` that carries an `index` field intended to disambiguate multiple withdrawals originating from the same NEAR transaction: [1](#0-0) 

However, `describeWithdrawal` never uses that `index` when resolving the status — it delegates to `findMatchingWithdrawal`, which matches purely on `assetId`: [2](#0-1) [3](#0-2) 

The code comment explicitly acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but the SDK's public batch API (`sdk.createWithdrawalCompletionPromises` / `sdk.waitForWithdrawalCompletion`) accepts an array of `WithdrawalParams` and creates one polling promise per entry via `watchWithdrawal`, with no guard preventing two entries from sharing the same `assetId`: [4](#0-3) 

Because `withdrawals.find(...)` returns the first array element whose `near_token_id`-derived assetId matches, both polling promises (for index 0 and index 1) converge on the same underlying `withdrawal` entry from the POA API response, regardless of which of the two withdrawals actually reached that state. This breaks the equality "status reported == on-chain outcome for *this* withdrawal index."

### Impact Explanation
If a batch contains two withdrawals of the same token to different destination addresses/amounts, and only one of them completes on the destination chain while the other fails or is still pending, both `describeWithdrawal` calls can report the completed one's `txHash` and "completed" status. An integrator relying on this SDK to confirm delivery before crediting a user, releasing an off-chain settlement, or marking an order fulfilled could be misled into treating a still-pending or failed withdrawal as completed — a status/hash misreport that can cause double-crediting or incorrect settlement decisions with no way to detect the mismatch from the SDK's return value alone.

### Likelihood Explanation
This requires no malicious actor — it is triggered by ordinary use of the SDK's documented batch-withdrawal capability (`createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` with an array of `WithdrawalParams`) whenever two or more entries in the batch share the same `assetId`. The internal design doc `docs/design/rfc-batch-withdrawal-granular-control.md` (found via search) confirms the SDK maintainers are aware of same-asset batching as a real use case, making this a plausible/likely configuration for integrators to hit.

### Recommendation
Disambiguate by more than `assetId` when matching a withdrawal to its identifier — e.g., match on `(assetId, destinationAddress, amount)` combined, or track already-consumed matches per polling session (remove/mark matched entries so subsequent `find()` calls for other indices cannot select the same entry again), and only return `completed`/`failed` when a withdrawal uniquely corresponding to the requested index/params is found; otherwise keep returning `pending`.

### Proof of Concept
1. Call `sdk.createWithdrawalCompletionPromises` with two `withdrawalParams` entries for the same `assetId` (e.g., `nep141:usdc.token.near`) but different `destinationAddress`/`amount`, both settled inside one NEAR transaction.
2. On the POA bridge indexer side, suppose withdrawal #0 completes with `transfer_tx_hash: "0xA"`, while withdrawal #1 is still `PENDING` (or fails).
3. `PoaBridge.describeWithdrawal` is invoked twice (once per index) with the same `args.tx.hash`, fetching the same `response.withdrawals` array.
4. `findMatchingWithdrawal(response.withdrawals, assetId)` returns the same first-matching entry (`status: "COMPLETED", tx_hash: "0xA"`) for **both** calls, because index/amount/address are never checked.
5. Both polling promises resolve as `{ status: "completed", txHash: "0xA" }`, even though withdrawal #1 never actually completed — the caller (e.g., `sdk.waitForWithdrawalCompletion`) reports success for a withdrawal that has not landed on-chain. [5](#0-4)

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
