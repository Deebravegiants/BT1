### Title
Single-solver price manipulation of phantom-order weighted median lets a dual liquidity-provider/bidder set the published pool rate that real IntentGateway orders are priced from - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
The Allbridge incident was caused by an attacker acting as both liquidity provider and trader against the same pool, manipulating the pool's internal price and then draining it. Hyperbridge's Intent Gateway "phantom order" pricing mechanism has an analogous single-actor dual-role design: a solver's bid price is weighted purely by *that same solver's own token inventory*, and `weightedMedian` is documented and tested to return one bidder's price verbatim once that bidder controls over half the leg's weight.

### Finding Description
`aggregatePhantomBids` prices each leg of a phantom order by collecting solver bids and weighting each bid's price by the **bidding solver's own balance** of that leg's output token on the destination chain: [1](#0-0) 

The per-leg price is then chosen by `weightedMedian`, which is a **selection, not a blend** — it returns one input entry's exact price when that entry's weight reaches half the total: [2](#0-1) 

This is confirmed by the SDK's own unit tests, which document that "the high-liquidity solver pulls the median to its price": [3](#0-2) 

The flow document confirms the same actor supplies both the weight (its own declared/held inventory) and the price (its own quote), i.e. the solver is simultaneously the "liquidity provider" whose balance sets the weight and the "trader" whose bid sets the price — exactly the dual role Allbridge's attacker exploited: [4](#0-3) 

The resulting `medianPrice` is written into `PhantomOrderPriceSnapshotV2` and then folded into the pair-centric `LiquidityPool.sellRate`/`buyRate` via `updateLiquidityPools`/`weightedRate` on the indexer: [5](#0-4) 

That aggregate rate is what `IntentGateway.quoteIntent()` uses **by default** (`indexed_rates` strategy) to compute `amountIn`/`amountOut` for real, on-chain IntentGatewayV2 orders that end users construct and solvers must fill: [6](#0-5) [7](#0-6) 

A single solver — or a solver colluding with itself across accounts — can hold a large balance of an output token (the "LP" role) and place a lone or dominant phantom bid at an arbitrary price for that leg (the "trader" role). Because weight comes only from self-reported/self-held inventory and the median degenerates to a verbatim pick once weight exceeds 50%, this solver alone determines the published rate for that pair/direction, with no reference to any independent market price. Any counter-pressure (a genuine competing bid) is only effective if it, too, is backed by inventory in the same token — an attacker with the largest position on a thin pair always wins.

### Impact Explanation
Once the manipulated rate is published as `LiquidityPool.buyRate`/`sellRate`, it silently feeds `quoteIntent()`'s default `indexed_rates` strategy, which end users and integrators rely on (per the docs, "no `strategy` option is needed for indexed-rate quotes"). A manipulated rate causes real orders to be sized incorrectly: an inflated rate lets an attacker's own subsequent order demand more output than fair value from whichever solver fills it (analogous to draining the "pool" — here, the honest solver network — of funds), while a depressed rate can make a legitimate user's order unfillable or force them to accept below-market output. Because the manipulated number becomes the basis for constructing signed, escrow-backed on-chain orders (real USDC/cNGN/etc. transfers), this is a genuine concrete-value manipulation path, not merely an off-chain display bug — it meets the "price manipulation leading to fund loss" bar of the Allbridge analog. Severity is Medium: it requires holding meaningful inventory in the specific thin pair being manipulated and depends on a victim (user or solver) subsequently using the tainted indexed rate, but no privileged role or governance access is needed — any solver reachable through the public bidding/dispatch path can attempt it.

### Likelihood Explanation
The mechanism is reachable by any unprivileged solver capable of submitting a bid to a phantom order (the same “relayer/bidder” surface addressed by the scope) and is most exploitable on thin/exotic pairs (e.g. cNGN, ZARP, etc., explicitly called out in the docs as low-liquidity pairs). The codebase's own documentation and tests explicitly acknowledge and describe this exact single-actor dominance ("a solver holding over half the leg's weight sets the published price verbatim"), indicating the behavior is a known, accepted design trade-off rather than a hardened defense — increasing the practical likelihood that it can be exploited on any pair where one solver can accumulate dominant inventory.

### Recommendation
- Do not let a single solver's self-reported/self-held inventory alone set weight and price simultaneously; require the weight to reflect independently verifiable, diversified liquidity (e.g., minimum bidder count, capped per-solver weight share, or a price-deviation guard against an external reference similar to the `maxDeviationBps` guard already used for Uniswap V4 venue pricing).
- Apply a maximum-deviation/reference-price sanity check (as already exists for pool-based Uniswap V4 pricing via `checkPriceGuard`/`maxDeviationBps`) to phantom-derived `medianPrice`/pool rates before they are published or consumed by `quoteIntent()`.
- Consider requiring a minimum number of distinct, inventory-backed bidders before a leg's price is considered authoritative, rather than allowing `weightedMedian` to degenerate to a single dominant entry.

### Proof of Concept
1. Attacker acquires a large balance of a thinly-traded output token (e.g. `cNGN`) on the destination chain — this becomes their "LP" position, exactly the weight source read in `phantom-aggregation.ts:1479-1503`.
2. Attacker (as the sole or dominant solver) submits a phantom bid quoting an arbitrary, favorable `solverAmount` for that leg.
3. Because the attacker's balance exceeds 50% of the total backed weight for that leg, `weightedMedian` (`phantom-aggregation.ts:709-724`) returns the attacker's exact quoted price as `medianPrice`.
4. The indexer's `handlePhantomOrderPrices` writes this into `PhantomOrderPriceSnapshotV2` and folds it into `LiquidityPool.sellRate`/`buyRate`.
5. Any user or integrator calling `IntentGateway.quoteIntent()` (default `indexed_rates` strategy) on that pair now receives amounts computed from the manipulated rate (`indexedRates.ts:156-172`), and places a real, escrow-backed `IntentGatewayV2` order using that skewed quote — extracting value from whichever solver fills it, or freezing the order as unfillable at fair value, mirroring the LP+trader dual-role manipulation from the Allbridge incident.

//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
