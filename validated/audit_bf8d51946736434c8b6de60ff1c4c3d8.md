### Title
`findMatchingWithdrawal` misattributes status/txHash between same-asset withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
When a single NEAR intent contains two or more POA-bridge withdrawals of the same token (e.g., two `nep141:eth.omft.near` payouts to different destinations/amounts), `PoaBridge.describeWithdrawal` cannot distinguish between them. `findMatchingWithdrawal` matches purely by `assetId` and returns the first entry found via `Array.prototype.find()`, so every `WithdrawalIdentifier` for that asset in the batch resolves to the same withdrawal record, regardless of which destination/amount it actually corresponds to.

### Finding Description
The broken equality is: `WithdrawalIdentifier_i.status/txHash === status/txHash of the withdrawal actually sent to WithdrawalIdentifier_i.withdrawalParams.destinationAddress/amount`.

The code path:
- `IntentsSDK.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` call `bridge.describeWithdrawal(withdrawalIdentifier)` once per withdrawal in the batch (see `WithdrawalIdentifier` in [1](#0-0) ).
- `describeWithdrawal` fetches the full status list keyed only by the shared NEAR intent tx hash (`args.tx.hash`), then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`: [2](#0-1) .
- `findMatchingWithdrawal` matches solely on `nep141:${w.data.near_token_id} === assetId` and returns the *first* array match, with the docstring explicitly stating: "multiple withdrawals of the same token in a single transaction are not supported": [3](#0-2) .

Root cause: no disambiguation by `destinationAddress`, `amount`, or `index` is performed, even though the underlying POA API response (`withdrawal.data.address`, `withdrawal.data.amount`) carries exactly this information. When two withdrawals share `assetId` in the same intent, both `WithdrawalIdentifier`s for that asset get the identical `find()` result — same `status`, same `txHash` — even though they may target different addresses/amounts and complete at different times.

None of the existing guards prevent this: `supports()`, `validateAddress`, `compareAddresses`, and `validateWithdrawal` operate per single withdrawal at construction time and have no knowledge of sibling withdrawals in the same batch; nothing rejects or reorders duplicate-assetId batches before they reach `describeWithdrawal`.

### Impact Explanation
An integrator building a batch withdrawal (any ordinary user constructs the batch via public SDK methods, e.g., `processWithdrawal`/`signAndSendWithdrawalIntent` with `withdrawalParams: WithdrawalParams[]`) that includes two withdrawals of `nep141:eth.omft.near` to different destinations will see `waitForWithdrawalCompletion` return misreported statuses: e.g., identifier #2's payout may still be pending on-chain, but the SDK reports `status: "completed", txHash: <hash of withdrawal #1>` because `find()` returns withdrawal #1 for both identifiers. This matches "a status or hash misreport making an integrator credit or refund twice" (High), since an integrator that credits users off-chain based on the SDK's `waitForWithdrawalCompletion` result could credit the wrong txHash/status as proof of completion for a withdrawal that has not actually settled to that destination, or treat a genuinely pending withdrawal as completed. It is repeatable on every batch that contains ≥2 same-asset POA withdrawals.

### Likelihood Explanation
Preconditions: the caller must construct a batch (`WithdrawalParams[]`) containing two or more withdrawals for the same POA-supported `assetId` (e.g., `nep141:eth.omft.near`) — this is entirely within a normal, unprivileged user's/integrator's control via public SDK entrypoints and is not a documented escape hatch that requires misuse; nothing in `supports()`/`validateWithdrawal()` rejects it. No special solver or relayer collusion is needed. Attacker cost is one intent with a duplicated line item.

### Recommendation
Disambiguate matches in `findMatchingWithdrawal` using `destinationAddress` and `amount` (and/or `destinationMemo`) in addition to `assetId`, consuming matched entries so repeats aren't reused (e.g., stateful matching that removes a matched withdrawal from the candidate pool per `describeWithdrawal` call, or sorts both sides by amount as the existing comment suggests). Until the POA API supports precise correlation (e.g., per-withdrawal id), the SDK should explicitly detect and reject/flag batches with duplicate `assetId` for POA-bridge withdrawals rather than silently returning a possibly-wrong status.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
