Based on my analysis, I've confirmed the vulnerability. The webhook `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) returns only `@raw_body`, while `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers (`lib/shopify_api/webhooks/request.rb:20-33`) that are never included in the HMAC-signed content. `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which checks the body-only HMAC) and then dispatches to the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values (`lib/shopify_api/webhooks/registry.rb:189-199`).

### Title
Webhook shop/topic/webhook-id identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-validated signable content from the raw request body only, while the `shop`, `topic`, and `webhook_id` values used by `Registry.process` to route and identify the tenant are read from unsigned HTTP headers.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are derived purely from HTTP headers, none of which participate in signature computation: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only checks `request.hmac` against `compute_signature(request.to_signable_string, secret)` — i.e., the body — and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to route the payload to the handler as tenant/topic identity: [3](#0-2) [4](#0-3) 

The identity binding broken is: `shop header value == shop value covered by HMAC`. In truth the HMAC covers `raw_body` only, so `shop header value != any value bound by the signature`. Because a legitimate merchant of shop A can receive genuinely-signed webhooks from Shopify (signed with the app's shared secret) for their own store, they can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with shop B's domain. Since the signature never covered these headers, `HmacValidator.validate` still returns `true`, and `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` attributing the payload to the attacker-chosen shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged internet user who is merely a legitimate merchant/webhook recipient for their own shop can cause the app to process a webhook body under an arbitrary victim shop's identity, without ever possessing the app's `client_secret`/`api_secret_key`. Any host application logic that uses `WebhookMetadata#shop` to look up sessions, update per-shop data, or trigger side effects (e.g., `shop/redact`, `customers/data_request`, `app/uninstalled` handling) can be tricked into acting on shop B's tenant context using attacker-supplied body content signed only for shop A. This satisfies the "cross-tenant access" High/Critical impact category since it defeats the very purpose of the per-request identity binding the gem exposes to host apps.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must first be a legitimate recipient of at least one genuine webhook (i.e., operate their own Shopify store using the same app) to obtain a validly-signed `(body, hmac)` pair, then replay it to the app's public webhook endpoint with modified headers. No secret material or privileged account is required — only normal use of the app as an ordinary merchant plus the ability to send arbitrary HTTP requests to the app's public webhook URL, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document that host applications must independently corroborate `request.shop` against a known session/tenant before using it, since the shared library does not bind it under the signature.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker operates this store and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (valid for `B` under the app's secret).
2. Attacker replays the same `(B, H)` to the app's public webhook endpoint but changes `shopify-shop-domain` to `shop-victim.myshopify.com` (and optionally `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers)` is constructed; `hmac` still decodes to `H`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) and compares to `H` — validation **succeeds** because the signature never covered the shop header. [5](#0-4) 
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "shop-victim.myshopify.com", body: request.parsed_body, ...))` is invoked, causing the host app to process attacker-controlled body `B` under `shop-victim`'s tenant identity.
