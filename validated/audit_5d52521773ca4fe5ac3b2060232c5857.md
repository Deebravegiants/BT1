### Title
IntentGatewayV2 (Tron) `placeOrder` escrows the nominal input amount instead of the actual tokens received, enabling insolvent/exploitable escrow accounting with fee‑on‑transfer or deflationary tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` pulls ERC20 input tokens with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits the escrow ledger `_orders[commitment][token]` with the *nominal, pre‑transfer* amount (`reducedInputs[i].amount`, itself derived from `order.inputs[i].amount`) rather than the amount actually received by the contract. This is the same class of bug as the GAIN exploit: an unprivileged actor can supply a token whose real balance delta does not match the amount the accounting logic assumes, producing an escrow ledger that is out of sync with the contract's real token balance.

### Finding Description
In the non‑predispatch branch of `placeOrder`: [1](#0-0) 


There is no balance-before/balance-after check. `reducedInputs[i].amount` is computed purely from `order.inputs[i].amount` (the caller-declared amount) minus the protocol fee — it is never adjusted for what the ERC20 `transferFrom` call actually delivered. For any ERC20 that charges a transfer fee, rebases, or otherwise delivers less (or more) than the nominal `amount` (fee-on-transfer tokens, deflationary/burn-on-transfer tokens, etc.), the gateway will record an escrow balance for `commitment`/`token` that exceeds the tokens it physically holds.

This is precisely analogous to the GAIN report: GAIN's swap/skim/sync path let an attacker desynchronize a pool's *recorded* reserves from its *actual* token balance, then exploit that gap for profit. Here the desynchronization is between the IntentGateway's `_orders` escrow ledger (a promise of tokens available to solvers/users on `withdraw`) and the contract's real ERC20 balance.

Crucially, the code path that actually protects against this exists elsewhere in the same repository — the EVM (non-Tron) version of `IntentGatewayV2.sol` explicitly measures the real balance delta before crediting escrow: [2](#0-1) 

```
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            uint256 balBefore = IERC20(token).balanceOf(address(this));
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
            order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
        }
        unchecked { ++i; }
    }
}
```

and this actual-received behavior is explicitly tested against fee-on-transfer tokens: [3](#0-2) 

The Tron deployment omits this balance-diffing fix (its `placeOrder` computes `reducedInputs` and the `commitment` purely from `order.inputs[i].amount` before any transfer, at lines 356-385, and never re-measures actual received tokens), so it reintroduces exactly the accounting flaw the EVM contract was hardened against.

### Impact Explanation
Any unprivileged user can call `placeOrder` on the Tron `IntentGatewayV2` with a fee‑on‑transfer, deflationary, or otherwise balance‑manipulating TRC20/ERC20 token as an input asset. The escrow ledger `_orders[commitment][token]` will record more tokens than the contract actually holds for that token. When a solver later calls `fillOrder`/`withdraw` (via `RedeemEscrow`/`RefundEscrow`/cancel paths) for this or subsequent orders sharing the same token, the contract will attempt to pay out escrow amounts that exceed its real balance:
- Legitimate solvers/users filling *other* orders denominated in the same token can find their withdrawal reverts or is starved (frozen funds) because the token's on-chain balance is insufficient to cover the sum of all recorded `_orders` entries.
- Alternatively, whichever order/withdrawal executes first drains the underfunded pool, causing the escrow to be insolvent for whoever attempts to withdraw afterward — a permanent loss/freezing of funds for other users of the gateway.

This satisfies "concrete theft or permanent freezing of funds" via an unauthorized-app-action-equivalent ledger desync reachable from a single `placeOrder` transaction by an unprivileged intent-placer.

### Likelihood Explanation
High reachability: this requires only a standard `placeOrder` call by any user, no special privileges, and works with any commonly deployed fee-on-transfer/deflationary token (a well-known and widely deployed token category on EVM/Tron-compatible chains). No governance, admin, or relayer collusion is needed — a single crafted order using such a token as input is sufficient to desynchronize escrow accounting.

### Recommendation
Apply the same balance-before/balance-after measurement used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract's `placeOrder` (and equivalently to its predispatch-sweep path), and derive `reducedInputs`/the commitment from the *actually received* amount rather than the caller-declared `order.inputs[i].amount`, mirroring the fix already present and tested in the primary EVM contract.

### Proof of Concept
1. Deploy (or use an existing) fee-on-transfer TRC20/ERC20 token `T` that deducts, e.g., 1% on every `transfer`/`transferFrom`.
2. Attacker (or any user) calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: T, amount: 1000e18}`.
3. `safeTransferFrom` delivers only `990e18` of `T` to the gateway (line 459), but `_orders[commitment][T] += reducedInputs[0].amount` (line 463) credits escrow based on the nominal `1000e18` (minus protocol fee), i.e., more than the `990e18` actually held.
4. Repeat placing multiple orders with `T` as input; the sum of `_orders[...][T]` across commitments now exceeds `T.balanceOf(gateway)`.
5. When solvers redeem/withdraw escrow for these orders (`onAccept`→`withdraw`, `RedeemEscrow`/`RefundEscrow`/cancel), at least one withdrawal will revert due to insufficient real `T` balance, freezing that user's/solver's escrowed funds — or an early withdrawer drains the shared balance, leaving later legitimate claimants unable to redeem.

```text
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
```
