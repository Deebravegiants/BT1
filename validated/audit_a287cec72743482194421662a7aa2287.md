### Title
Webhook shop identity spoofing due to `shop-domain` header not covered by HMAC — cross-tenant webhook injection ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then trusts the `shop-domain` header — which is never included in the signed material — as the tenant identity passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read directly from the (unsigned) HTTP header: [2](#0-1) 

`Registry.process` verifies the HMAC over the body only, then forwards `request.shop` straight into the handler without ever cross-checking it against anything covered by the signature: [3](#0-2) 

The identity binding that should hold is: `hmac_valid(raw_body) ⇒ shop_header == shop_that_Shopify_generated_this_body_for`. In this implementation that implication does not hold — `hmac_valid(raw_body)` only proves the body bytes were produced by *some* legitimate Shopify webhook delivery signed with the app's secret; it says nothing about which shop header accompanies it. Any tenant that has legitimately received a validly-signed webhook (e.g. by installing the app on their own store) can replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting a different value in the `shop-domain` (or `x-shopify-shop-domain`) header. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop while the JSON `body` is fully attacker-controlled content from their own store's legitimate webhook.

### Impact Explanation
This breaks the tenant boundary the host application relies on: the gem asserts "this event, with this body, came from `shop`" but the `shop` field is not covered by the same authenticity check as the body. A malicious merchant/tenant can inject forged, attributed-to-another-shop webhook events into the host app's processing pipeline (e.g., `orders/create`, `app/uninstalled`, GDPR webhooks), causing cross-tenant data corruption or state confusion in any application that keys per-shop side effects off `WebhookMetadata#shop` — this is a cross-tenant access impact.

### Likelihood Explanation
Any user who can install the app on their own store (a normal, unprivileged merchant) automatically receives validly HMAC-signed webhook deliveries for their own shop. Forging the replay only requires modifying an HTTP header on a replayed request — no possession of `api_secret_key` or an access token is needed, since the attacker never needs to compute the HMAC themselves.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/api-version) in the material that is verified, or independently verify that the `shop-domain` header matches a shop already known/authorized by the application (e.g., cross-reference against an existing session/install record) before dispatching to the handler. At minimum, document and warn that `WebhookMetadata#shop` is not authenticated by the HMAC and must be independently validated by the host app.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers `orders/create`, receiving a webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the real `api_secret_key`).
2. Attacker replays the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `HmacValidator.validate` recomputes HMAC over `B` only and succeeds (per [4](#0-3) ).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)` (per [5](#0-4) ), causing the host app to process attacker-controlled content as if it originated from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
