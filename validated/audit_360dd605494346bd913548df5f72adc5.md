### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC of the raw body, but the `shop` value that is handed to the app's handler is taken from an unauthenticated header that is never part of the signed payload. Any party that can obtain one validly-signed webhook (e.g. a merchant receiving webhooks for their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will accept it as authentic for the attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

But the value that is actually HMAC-verified, `to_signable_string`, returns only the raw request body — it never includes the shop header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` uses this HMAC check as its sole authenticity gate, and then forwards `request.shop` — the unauthenticated header value — straight into the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The documented contract explicitly tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is a safe, verified field to key data operations on: [5](#0-4) [6](#0-5) 

This breaks the intended binding `verified_shop == hmac_signed_shop`. In reality, `hmac_signed_bytes` cover only the body, so `verified_shop` (the header) is disjoint from what the signature actually authenticates. Any entity that legitimately receives a signed webhook for shop A (for example a merchant who installed the app on their own store and can capture Shopify's POST to their callback URL, or replay it via a proxy) can resend that same body+HMAC to the app's webhook endpoint with `x-shopify-shop-domain: shop-b.myshopify.com`. `HmacValidator.validate` still succeeds because it never looks at the shop header, and the handler is invoked believing the event legitimately originates from shop B.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who only controls their own shop's webhook traffic can forge events attributed to a different, victim shop. Depending on how the host application uses `data.shop` (e.g., to select which merchant's records to update, to look up which merchant's access token/session to act with, or to trigger side effects scoped by shop), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's store context — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is high for any app author following the documented `process` API exactly as shown in `docs/usage/webhooks.md`. The attacker only needs the ability to receive (or intercept via a webhook-forwarding proxy they control) one validly-signed webhook for any shop and to be able to POST to the target app's public webhook callback URL with a modified header — no `api_secret_key`, access token, or privileged credentials are required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop` header to the request the same way `VaultFactory.createNewMarket` binds the controller's `vaultFactory` field before trusting it. Concretely, `Request#to_signable_string` should not be the only authenticity anchor for `shop`; `Registry.process` should either verify `request.shop` against a known/registered shop for the topic/session, or the gem should document clearly that `data.shop` is unauthenticated and must be independently verified by the integrator against session/shop records before being trusted for tenant-scoped operations.

### Proof of Concept
1. App registers a webhook handler as shown in `docs/usage/webhooks.md` lines 20-30, trusting `data.shop`.
2. Shopify sends a legitimate webhook to a merchant's own callback endpoint for `shop-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(secret, B)`.
3. Attacker (the merchant, or anyone who can observe this traffic) resends `POST /callback` to the app with the same body `B` and same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Request.new(raw_body: B, headers: forged_headers)` builds a request whose `shop` is `shop-b.myshopify.com` while `to_signable_string` returns `B`.
5. `HmacValidator.validate` recomputes `HMAC_SHA256(secret, B)` and finds it equals `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
6. `Registry.process` invokes the handler with `WebhookMetadata(shop: "shop-b.myshopify.com", body: B, ...)`, causing the app to act on shop B's behalf using attacker-controlled `B`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
