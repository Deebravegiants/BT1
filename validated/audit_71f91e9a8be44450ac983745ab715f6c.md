### Title
Unvalidated `order.destination` in `placeOrder` permanently freezes escrowed funds when no gateway instance is registered - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
This mirrors the AssetManager report: `deposit()` accepted a token without checking `isMarketSupported`, but `withdraw()` enforced that same check and reverted, trapping user funds. In `IntentGatewayV2`, `placeOrder()` escrows the user's input tokens for a cross-chain order without ever validating that `order.destination` corresponds to a registered gateway instance in `_instances`, but the cancellation path (`_cancelFromSource`) unconditionally calls `_instance(order.destination)`, which reverts with `UnknownInstance` if no deployment is registered for that chain.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol:194-415` accepts an arbitrary `order.destination` value from the caller and escrows the caller's input tokens into `_orders[commitment][token]` [1](#0-0) . There is no check anywhere in `placeOrder` that `order.destination` maps to a registered `_instances[keccak256(order.destination)]` entry before tokens are pulled from the user and escrowed.

Once escrowed, there are exactly two ways for the user to recover funds for a cross-chain order:
1. A solver fills the order on the destination chain, which then dispatches `RedeemEscrow` back to the source via `_post`, which itself calls `_instance(order.source)` [2](#0-1) . If the destination chain has no `IntentGatewayV2` deployment for the order's destination, no solver can ever observe or fill the order there.
2. After the deadline passes, the user calls the cancel path, which reaches `_cancelFromSource`. This function unconditionally computes `_instance(order.destination)` to build the storage-proof key for the GET dispatch:
```solidity
keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
``` [3](#0-2) 

The `instance()`/`_instance()` accessor is documented to revert with `UnknownInstance` when no remote deployment is registered for the given state machine id [4](#0-3) . Because `_instances` is only populated via `NewDeployment` requests dispatched by Hyperbridge/governance [5](#0-4) , a user who places an order specifying a destination chain that has no (or not-yet) registered gateway instance can deposit/escrow funds successfully, but both the fill path and the cancel path revert — the tokens are escrowed with no reachable code path to release them.

This is the same asymmetry as the AssetManager bug: the "deposit" side (`placeOrder`) has no support-validity check, while the "withdraw" side (`_cancelFromSource`/fill path) enforces that check and reverts.

### Impact Explanation
Funds escrowed for an order targeting an unregistered/unsupported destination chain become permanently frozen: no solver can fill the order (no gateway there to authenticate/redeem against), and the user's own cancellation transaction reverts with `UnknownInstance` before it can even dispatch the GET request needed to trigger a refund. This is a permanent freezing of user funds reachable from a single unprivileged `placeOrder` call, satisfying the Medium-severity bar (concrete freezing of funds under specific, attacker/user-triggerable conditions — here, simply choosing a destination chain id without an active deployment).

### Likelihood Explanation
Likelihood is meaningful: `order.destination` is a fully user-supplied field with no gateway support enforced at input time, and new chain deployments are rolled out over time via governance (`NewDeployment`), so there is a realistic window (or permanent state for a chain intentionally never deployed) where users can mistakenly or maliciously target an unsupported destination. A front-end or integrator bug supplying a wrong/typo'd `StateMachine` id, or a user interacting with an SDK before a destination gateway is deployed, would trigger this with no attacker sophistication required.

### Recommendation
Validate `order.destination` against `_instances` in `placeOrder` before pulling/escrowing any tokens (i.e., call the equivalent of `_instance(order.destination)` and revert early with `UnknownInstance` if unregistered), mirroring the check already present implicitly in the cancel/fill paths. This ensures the same "supported destination" invariant is enforced symmetrically on both the escrow and release paths.

### Proof of Concept
1. Governance has not yet (or will never) call `NewDeployment` for `StateMachine::Evm(X)`, so `_instances[keccak256(bytes(X))] == address(0)`.
2. A user calls `placeOrder(order, graffiti)` with `order.destination = X` and valid `order.inputs`; `placeOrder` executes fully, transferring input tokens into escrow via `IERC20.safeTransferFrom` and recording `_orders[commitment][token] = amount` [1](#0-0) . No revert occurs because there is no destination-support check.
3. No solver can fill the order on chain `X` (no gateway deployed there to interact with).
4. After `order.deadline` passes, the user calls the cancel entrypoint, reaching `_cancelFromSource(order, options, commitment)`. Building the GET dispatch keys calls `_instance(order.destination)` [6](#0-5) , which reverts with `UnknownInstance` since `_instances[keccak256(X)] == address(0)`.
5. The user's escrowed tokens (`_orders[commitment][token]`) remain locked in the contract indefinitely, with no code path able to release them.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });
```
