`CallDispatcher.dispatch` has no access control, letting anyone hijack in-flight escrow/bridge funds routed through the shared dispatcher — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch(bytes memory encoded)` is `external` with **no caller restriction** — it is not gated to `IntentGatewayV2`, `HyperFungibleToken`/`WrappedHyperFungibleToken`, or any other authorized app. `IntentGatewayV2.placeOrder`, `IntrinsicIntents`/`IntentsBase._execute`, and the HFT `onAccept` calldata-execution path all temporarily route escrowed user funds and bridged tokens *through* this single shared `CallDispatcher` address before sweeping the resulting balance back into the calling contract. [1](#0-0) [2](#0-1) 

### Finding Description
This mirrors the Earning.Farm bug class: a function meant to be invoked only as an internal step of a privileged multi-step flow (there, the flash-loan callback; here, `dispatch()` as the "execute the attached calldata" step of `placeOrder`/`fillOrder`/`onAccept`) is directly callable by anyone, with no verification that the caller is the legitimate orchestrating contract or that the call is part of a sanctioned flow.

`placeOrder`'s predispatch path (`evm/src/apps/IntentGatewayV2.sol:235-311`) transfers `order.predispatch.assets` to the shared `dispatcher` address, then calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — itself **user-supplied calldata** (`order.predispatch.call` comes straight from the caller's `Order` struct) — followed by a second `dispatch()` call that sweeps the resulting balance back to the gateway based on a balance diff (`balancesBefore[i]` vs. post-dispatch balance). [3](#0-2) 

Because `order.predispatch.call` is attacker-controlled and forwarded verbatim to the unrestricted `CallDispatcher`, and because the dispatcher's `receive()` accepts value from anyone, a malicious order placer can craft `predispatch.call` to include a self-serving `Call` (e.g., `approve(attacker, type(uint256).max)` on any ERC20, executed with the dispatcher as `msg.sender`) instead of (or in addition to) whatever the predispatch is nominally meant to do. This approval persists in that ERC20's storage after the `placeOrder` transaction completes, since `CallDispatcher` is a **shared, address-fixed, stateful singleton** used across every `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` deployment on the chain (the docs and deploy scripts confirm one dispatcher address is reused across apps). [4](#0-3) 

Any subsequent, unrelated user's transaction that routes the same token through the dispatcher (e.g., another `placeOrder`/`fillOrder` predispatch/postdispatch, or an HFT `onAccept` with `data` targeting the dispatcher — explicitly recommended by the docs: "set `to` to the `CallDispatcher` address so tokens are delivered directly to it") will transiently place that victim's tokens in the dispatcher's balance. Since the attacker already holds a standing approval on that token from the dispatcher, the attacker can `transferFrom(dispatcher, attacker, amount)` at any point the dispatcher is holding a balance — including racing the legitimate sweep call within the same block, or catching any leftover dust — draining funds that belong to other users' in-flight bridge/intent operations. [5](#0-4) [6](#0-5) 

The project's own documentation implicitly acknowledges the danger of standing approvals from the dispatcher ("Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution") but this is only a caller-side best-practice note — `CallDispatcher.dispatch` itself enforces no restriction on who may call it or what it is allowed to approve, and nothing prevents an attacker from directly calling `dispatch()` (bypassing `placeOrder`/`fillOrder` entirely) to arm a malicious approval ahead of time. [7](#0-6) 

### Impact Explanation
This is a concrete theft-of-funds vector against a core, unprivileged, single-transaction-reachable primitive (any order placer / message dispatcher / relayer-delivered calldata executor can reach it). Because `CallDispatcher` is shared infrastructure across `IntentGatewayV2` orders and `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution transfers, a single attacker-armed approval threatens every future user whose bridged/escrowed tokens transiently pass through the same dispatcher instance for that token — a wide, ongoing blast radius rather than a one-off self-inflicted loss.

### Likelihood Explanation
The attack requires only a single, fully permissionless transaction: placing an `IntentGatewayV2` order (or delivering any HFT message) whose `predispatch.call`/`data` field contains an `approve()` call routed through the dispatcher, or calling `CallDispatcher.dispatch` directly (it has no gate at all). No privileged role, governance, or race against block producers is needed to set up the approval; the attacker then only needs to wait for/observe any subsequent transaction that leaves the target token balance sitting in the dispatcher.

### Recommendation
Restrict `CallDispatcher.dispatch` to a caller allow-list (e.g., only the registered `IntentGatewayV2`/HFT/WrappedHFT app addresses), or make the dispatcher stateless-per-call (e.g., deploy a fresh minimal-proxy dispatcher per invocation via `CREATE2`/`CREATE` so no standing approvals or balances can carry over between unrelated callers), and/or forbid `approve`-selector calldata from being routed to arbitrary ERC20 targets through the dispatcher.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.predispatch.assets = []`-adjacent but `order.predispatch.call` encoding a single `Call{ to: USDC, value: 0, data: approve(attacker, type(uint256).max) }` (any nonzero-length `predispatch.call`/`assets` combination that reaches `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` at `evm/src/apps/IntentGatewayV2.sol:258`).
2. This grants `attacker` unlimited `USDC` allowance from the shared `CallDispatcher` address, persisted in USDC's storage.
3. Later, any victim's `placeOrder`/`fillOrder` predispatch/postdispatch flow, or an `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` with `data` targeting the dispatcher for a USDC-denominated transfer, causes the dispatcher to transiently hold victim USDC (per `evm/src/apps/intentsv2/IntentsBase.sol:498-528` and `evm/src/apps/IntentGatewayV2.sol:268-289`).
4. Attacker calls `USDC.transferFrom(dispatcher, attacker, balance)` while that balance is present, stealing the victim's escrowed/bridged funds before the legitimate sweep call executes.

*Note: I could not fully confirm within the available index whether `CallDispatcher` deployments are genuinely shared across multiple `IntentGatewayV2`/HFT instances in production (vs. one dispatcher per app instance), since deployment configuration lives outside the indexed contract files. If each app instance deploys its own dedicated `CallDispatcher`, the cross-app blast radius is narrower (limited to that single app's own future orders/transfers) but the core vulnerability — an unrestricted `dispatch()` letting attacker-controlled calldata arm approvals from a balance-holding contract — still stands within that app's own user base.*

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```
