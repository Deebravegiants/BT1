### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates incoming webhook requests using `Utils::HmacValidator.validate(request)`, but the HMAC signature is computed only over the raw request body, never over the `shop` identity that the request carries. The `shop` value used to attribute the webhook to a tenant is read from an unauthenticated HTTP header, so an attacker who possesses one valid `(body, hmac)` pair can freely change which shop that payload is attributed to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` and `#topic` are read straight from HTTP headers, which are not part of the signed material: [2](#0-1) 

`Registry.process` validates only that the body's HMAC is correct, then forwards `request.shop` (the unauthenticated header) directly to the handler as the tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the raw body) matches the HMAC — it has no knowledge of, and does not bind, the `shop` header: [4](#0-3) 

The broken identity binding, as an equality that should hold but doesn't:
`hmac_verified_bytes (raw_body) == bytes_acted_on_for_tenant_attribution (raw_body + shop_header)`

Before the attacker's request: a legitimate webhook for shop A arrives with `body_A`, `hmac(body_A, secret)`, and header `x-shopify-shop-domain: A`. All three are consistent because Shopify itself sent the real, single request.

Attacker sequence: any merchant who has installed the app on their own shop (shop B, fully unprivileged relative to other tenants) legitimately receives real webhooks for shop B — e.g. `body_B` + valid `hmac(body_B, secret)`. Because the signature covers only `body_B`, this exact `(body_B, hmac)` pair remains valid regardless of which shop header accompanies it. The attacker replays that request to the app's public webhook endpoint, substituting `x-shopify-shop-domain: victim-shop.myshopify.com` for their own header.

After the attacker's request: `HmacValidator.validate` still returns `true` (body+hmac unchanged), so `Registry.process` proceeds and calls `handler.handle(... shop: "victim-shop.myshopify.com", body: parsed_body_B ...)`. The application now processes shop B's (attacker's) content as if it were victim-shop's webhook — a cross-tenant identity break that requires no credentials, no access token, and no knowledge of `api_secret_key`.

### Impact Explanation
This crosses a tenant boundary without any credential: it lets an app's own merchant (an "unprivileged internet user" relative to every other tenant of the app) inject attacker-controlled payloads that the app will process and attribute to a different, arbitrary shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to select the tenant record to update, look up a session, or trigger tenant-scoped side effects), this can result in cross-tenant data corruption or unauthorized actions performed against another merchant's data — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is Medium-to-High: the only requirement is that the attacker be a legitimate (even free/trial) installer of the app on their own store, enabling them to capture one real, validly-signed webhook body/HMAC pair, then replay it with a forged `x-shopify-shop-domain` header. No secrets, tokens, or privileged access are needed, and the replay can be repeated with any webhook the attacker can trigger on their own store (e.g., `orders/create`).

### Recommendation
Bind the tenant identity into the verified material instead of trusting the header independently of the signature:
- Include the `shop` (and ideally `topic`) header value as part of the signed content that `Utils::HmacValidator` checks, or
- Have `Webhooks::Request#to_signable_string` incorporate the shop domain header alongside the raw body so the HMAC computation itself fails if the shop is altered, or
- After HMAC validation, cross-check `request.shop` against an independently trusted source (e.g., the session/shop the webhook subscription was registered for) rather than trusting the header value verbatim.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to capture a real `raw_body` and its `x-shopify-hmac-sha256` value — both valid because Shopify signed them with the app's `api_secret_key`.
2. Send a POST request directly to the app's webhook endpoint reusing that exact `raw_body` and `x-shopify-hmac-sha256`, but replace the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC (see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `handler.handle` is invoked with `shop: "victim-shop.myshopify.com"` and the attacker's own `parsed_body`, demonstrating that shop attribution is fully attacker-controlled despite passing HMAC validation.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
