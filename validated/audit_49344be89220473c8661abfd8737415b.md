Audit Report

## Title
Single malicious para can cheaply flood a victim para's DMQ via `hrmp_init_open_channel` + `hrmp_cancel_open_request` loop - (File: `polkadot/runtime/parachains/src/hrmp.rs`)

## Summary
`init_open_channel` reserves a deposit and unconditionally enqueues an `HrmpNewChannelOpenRequest` downward message to the recipient via `send_to_para`, while `cancel_open_request` fully unreserves the deposit and clears the request state, allowing the same `(sender, recipient)` pair to repeat the cycle indefinitely at only transaction-fee cost. This lets a single onboarded malicious parachain drive a fixed victim's `InboundDownwardQueue` toward `Dmp::dmq_max_length`, blocking legitimate downward message delivery (HRMP notifications and XCM DMP traffic) to that para until it drains the queue by including blocks.

## Finding Description
`Pallet::<T>::init_open_channel` only guards against a *duplicate* request from the same sender by checking `HrmpOpenChannelRequests` for the existing `channel_id` [1](#0-0) , then reserves the sender's deposit and calls `Self::send_to_para(..., queue_downward_message(...))` to notify the recipient regardless of the queue's fill level [2](#0-1) . `cancel_open_request` removes `HrmpOpenChannelRequests`, decrements the sender's open-request count, and fully unreserves the deposit [3](#0-2) , which clears exactly the state that would otherwise block a repeat `init_open_channel` call from the same sender against the same recipient. There is no cooldown or rate limit between cycles, so this loop can be repeated as fast as the attacker's para can get extrinsics included.

`can_queue_downward_message` enforces a hard queue-length cap based on `dmq_max_length` [4](#0-3) , and `queue_downward_message` calls this check before pushing to `InboundDownwardQueue` [5](#0-4) . This confirms the core mechanism: repeated cheap `init`/`cancel` cycles against a fixed victim can, in principle, drive the victim's queue toward this cap, after which further downward messages to that para are rejected until the queue is drained via `prune_dmq` when the victim includes blocks.

However, one specific sub-claim in the original report is **not accurate** as written. The report asserts that once the queue is full, `can_queue_downward_message` returns `QueueDownwardMessageError::ExceedsMaxQueueSize`, and that `send_to_para` silently swallows this variant because it only pattern-matches `ExceedsMaxMessageSize`. Reading the actual code, the queue-length check inside `can_queue_downward_message` returns `QueueDownwardMessageError::ExceedsMaxMessageSize` (not `ExceedsMaxQueueSize`) when `dmq_length(*para) > dmq_max_length(...)` [6](#0-5)  — this is visible even in the report's own quoted citation, which contradicts its prose description. Since `queue_downward_message` calls `can_queue_downward_message` via `?` before reaching the `push_back` call [7](#0-6) , the practical "queue is full" case actually surfaces as `ExceedsMaxMessageSize`, which **is** handled by `send_to_para`'s `if let` branch — it logs `log::error!` and triggers `debug_assert!(false)` [8](#0-7) . This is not a fully silent, unobservable drop as claimed; it is logged (and would abort in debug/test builds). The genuinely-silent `ExceedsMaxQueueSize`/`Unroutable` paths only occur via the underlying `InboundDownwardQueue::push_back` bounded-storage failure or a non-existent recipient para, which are separate, much less reachable conditions than the queue-length cap that the described attack actually hits first.

## Impact Explanation
The core DoS mechanism — a malicious para cheaply filling a fixed victim's `InboundDownwardQueue` up to `dmq_max_length` via a free-standing `init_open_channel`/`cancel_open_request` loop — is grounded in real code and would block legitimate downward message delivery (HRMP channel-management notifications and ordinary XCM DMP traffic) to that para until it drains its queue. This is a genuine, in-scope availability concern for the targeted para. The secondary "silent, unobservable failure" characterization tied to `ExceedsMaxQueueSize`/`Unroutable` handling in `send_to_para` is overstated: the actual failure path taken during queue saturation is logged via `log::error!` and guarded by `debug_assert!(false)`, so it is observable in logs (and would fail loudly in debug/test environments), weakening that part of the claim's impact narrative about total silence.

## Likelihood Explanation
Requires the attacker to control an onboarded parachain, which is a real but non-trivial precondition. Given that, the loop itself is cheap (deposit is always returned) and has no explicit rate limit, so it is mechanically repeatable, bounded by the attacker's and relay chain's transaction throughput versus the victim's own block-inclusion/drain rate.

## Recommendation
- Add a rate limit or cooldown per `(sender, recipient)` pair between `hrmp_init_open_channel`/`hrmp_cancel_open_request` cycles to prevent cheap repeated DMQ-filling notifications.
- Fix the mismatched error variant in `can_queue_downward_message`'s queue-length check, which currently returns `ExceedsMaxMessageSize` instead of the semantically correct `ExceedsMaxQueueSize` for that branch, and update `send_to_para` to explicitly handle/log all `QueueDownwardMessageError` variants rather than relying on incidental matching.

## Proof of Concept
Unit test plan (in `polkadot/runtime/parachains/src/hrmp/tests.rs` style):
1. Register attacker para `A` and victim para `B`.
2. Compute `max_len = Dmp::dmq_max_length(config.max_downward_message_size)`.
3. Loop up to `max_len` times: call `Hrmp::hrmp_init_open_channel(A_origin, B, cap, size)` (assert `Ok`), then `Hrmp::hrmp_cancel_open_request(A_origin, HrmpChannelId{sender:A, recipient:B})` (assert `Ok`), and check `Dmp::dmq_length(B)` grows by one each iteration.
4. Once `Dmp::dmq_length(B)` reaches the cap, call `hrmp_init_open_channel` again and observe that the dispatch still returns `Ok(())` at the extrinsic level while `queue_downward_message` internally returns `Err(QueueDownwardMessageError::ExceedsMaxMessageSize)` (not `ExceedsMaxQueueSize` as originally claimed), and that `send_to_para`'s `log::error!`/`debug_assert!(false)` branch fires — verifying the notification is dropped but is logged, not fully silent.
5. Separately, call `Dmp::can_queue_downward_message(&config, &B, &some_msg)` directly at that saturated state and confirm it returns `Err(QueueDownwardMessageError::ExceedsMaxMessageSize)`, confirming legitimate downward delivery to `B` is blocked while the queue is full.

	fn cancel_open_request(origin: ParaId, channel_id: HrmpChannelId) -> DispatchResult {
		// check if the origin is allowed to close the channel.
		ensure!(channel_id.is_participant(origin), Error::<T>::CancelHrmpOpenChannelUnauthorized);

		let open_channel_req = HrmpOpenChannelRequests::<T>::get(&channel_id)
			.ok_or(Error::<T>::OpenHrmpChannelDoesntExist)?;
		ensure!(!open_channel_req.confirmed, Error::<T>::OpenHrmpChannelAlreadyConfirmed);

		// Remove the request by the channel id and sync the accompanying list with the set.
		HrmpOpenChannelRequests::<T>::remove(&channel_id);
		HrmpOpenChannelRequestsList::<T>::mutate(|open_req_channels| {
			if let Some(pos) = open_req_channels.iter().position(|x| x == &channel_id) {
				open_req_channels.swap_remove(pos);
			}
		});

		Self::decrease_open_channel_request_count(channel_id.sender);
		// Don't decrease `HrmpAcceptedChannelRequestCount` because we don't consider confirmed
		// requests here.

		// Unreserve the sender's deposit. The recipient could not have left their deposit because
		// we ensured that the request is not confirmed.
		T::Currency::unreserve(
			&channel_id.sender.into_account_truncating(),
			open_channel_req.sender_deposit.unique_saturated_into(),
		);

		Ok(())
	}

	/// Determine whether enqueuing a downward message to a specific recipient para would result
	/// in an error. If this returns `Ok(())` the caller can be certain that a call to
	/// `queue_downward_message` with the same parameters will be successful.
	pub fn can_queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: &ParaId,
		msg: &DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len() as u32;
		if serialized_len > config.max_downward_message_size {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// Hard limit on Queue size
		if Self::dmq_length(*para) > Self::dmq_max_length(config.max_downward_message_size) {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// If the head exists, we assume the parachain is legit and exists.
		if !paras::Heads::<T>::contains_key(para) {
			return Err(QueueDownwardMessageError::Unroutable);
		}

		Ok(())
	}
