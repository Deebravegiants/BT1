Let me verify the exact mechanics of webhook HMAC validation and how `shop` is derived versus covered by the signature.### Title
Webhook HMAC only signs the raw body, so the `shop-domain`/`topic`/`webhook-id` headers used to identify the tenant are unauthenticated and can be replayed cross-tenant - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and exposes `to_signable_string` as **only** the raw request body: [1](#0-0) 

but the fields the gem actually uses to route/attribute the webhook to a tenant - `shop`, `topic`, `webhook_id`, `api_version` - are read straight from HTTP headers that are never included in the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the HMAC over `verifiable_query.to_signable_string` (i.e. the body): [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of authenticity for the whole request, then forwards the unauthenticated `shop` header value straight to the app's handler: [4](#0-3) 

This is the same bug class as the external report: a field that is *acted upon* (the tenant/shop identity used to attribute and process the webhook) is not covered by the cryptographic check (`hmac`) that is supposed to authenticate the request, breaking the intended binding `hmac ⟺ (body, shop, topic)`.

### Finding Description
The equality the gem is supposed to guarantee is:

`HmacValidator.validate(request) == true` ⟺ `request.shop`, `request.topic`, `request.to_signable_string` (body) were all produced by Shopify for this specific delivery.

In reality, `to_signable_string` returns only `@raw_body`, and `hmac` is computed as `HMAC(secret, raw_body)`. The `shop`, `topic`, and `webhook_id` accessors read directly from headers that are not part of the signed material: [5](#0-4) 

Because of this, any two headers/body pairs where the body+hmac pair is valid for the shared `api_secret_key` will pass `HmacValidator.validate`, regardless of what `shop-domain`, `topic`, or `webhook-id` headers say. An attacker who legitimately receives even one valid `(raw_body, hmac)` pair from Shopify (e.g. by installing the target app on their own free development store and letting Shopify deliver a webhook such as `app/uninstalled` or a mandatory compliance webhook) can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata` built from the attacker-chosen `shop`: [4](#0-3) 

Any host application that trusts `data.shop` (a documented, exposed field of `WebhookMetadata`) to know which merchant the webhook is about - e.g. to look up that merchant's stored session/access token, to mark an app as uninstalled for that merchant, or to process GDPR data-request/redact webhooks for that merchant - can be made to act on behalf of a different, unrelated shop than the one that actually sent the request.

### Impact Explanation
This breaks the tenant-attribution guarantee the HMAC check is supposed to provide, allowing cross-tenant confusion in the host application: with only a single legitimately-received webhook body from any store (including one the attacker fully controls, e.g. a free dev/partner store), the attacker can forge requests that the gem will validate as authentic for **any other shop domain** they choose, since the shop identity is never part of the signed content. This matches the Critical - cross-tenant access impact category defined in scope.

### Likelihood Explanation
Likelihood is high for apps that rely on the gem's webhook flow as documented: no leaked secrets, access tokens, or privileged accounts are required - only the ability to install the target app on any store (including a free development store) to legitimately obtain one valid `(body, hmac)` pair, and then replay it with modified headers to the app's public webhook endpoint. The library does nothing to prevent this because `to_signable_string` and `hmac` are the only two properties involved in the check, and `shop`/`topic`/`webhook_id` are excluded from both by design of `Request`.

### Recommendation
Bind the identifying headers into the signed material checked by `HmacValidator`, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified body before they are trusted. For example, expose and require verification of a canonical string that concatenates the header values with the body (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into what gets HMAC-checked), or explicitly document that consuming apps must independently authenticate the `shop` claim (e.g. against records created during OAuth) rather than trusting `request.shop`/`WebhookMetadata#shop` as an authenticated value.

### Proof of Concept
1. Attacker installs the target app on Shop A (a store they control, e.g. a free Shopify Partner dev store) and lets Shopify deliver any webhook (e.g. `app/uninstalled`) to the app's public webhook endpoint, capturing the raw body `B` and the `x-shopify-hmac-sha256` header value `H` (valid for the app's shared secret).
2. Attacker sends a new HTTP POST to the same endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-topic` unchanged, but `x-shopify-shop-domain: shop-b.myshopify.com` (Shop B, a victim merchant of the same app).
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` and `to_signable_string` are unaffected by the header change.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — [6](#0-5)  — which returns `true` since only the body is checked.
5. The registered handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"shop-b.myshopify.com"` — [7](#0-6)  — even though Shop B never sent this webhook, demonstrating the identity-binding break.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
