### Title
Index-scaled value overflow permanently freezes a lending market - ([File: common/src/rates/index.rs])

### Summary
High. A market with enough scaled supply or debt can make `scaled_amount * index / RAY` exceed `i128::MAX`, causing accrual to panic with `MathOverflow` before its index cap can protect the market. [1](#0-0) [2](#0-1) 

### Finding Description
`scaled_to_original` delegates to `Ray::mul`, which computes `x * y / RAY` and panics when the resulting `i128` cannot represent the value. [1](#0-0) [3](#0-2) 

During accrual, `calculate_supplier_rewards` separately multiplies total scaled debt by both the old and new borrow indexes, then subtracts the two totals. [4](#0-3) 

The supply-index path similarly multiplies total scaled supply by the current index and then adds the newly accrued rewards. [5](#0-4) 

Once the stored scaled balance is large enough, these products can overflow even though the index itself remains below `MAX_BORROW_INDEX_RAY` or `MAX_SUPPLY_INDEX_RAY`; the cap is applied to the index, not to the resulting aggregate value. [2](#0-1) [6](#0-5) 

Every pool accrual runs through `global_sync` and `accrue_step` before mutating the market. [7](#0-6) [8](#0-7) 

The controller exposes this path through permissionless caller-authenticated `update_indexes`, while `supply` and `borrow` are ordinary user entrypoints. [9](#0-8) [10](#0-9) 

### Impact Explanation
After the scaled aggregate crosses the representable `i128` boundary, every operation that accrues first reverts with `MathOverflow`, so suppliers cannot withdraw, borrowers cannot repay, liquidations cannot proceed, and direct index updates remain unusable. [7](#0-6) [11](#0-10) 

Because the panic occurs before updated indexes or timestamp state are committed, subsequent calls only increase the elapsed accrual and hit the same overflow; the affected market's funds remain frozen absent a contract upgrade. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
The trigger requires a large configured cap and whale-scale liquidity, but cap validation only ensures that the asset amount's initial RAY representation fits in `i128`; it does not account for later index growth. [14](#0-13) [15](#0-14) 

For an 18-decimal market, approximately `1e9` whole tokens produce a raw scaled balance near `1e36`, after which an index around `170` is enough to exceed `i128::MAX`; the repository's horizon test demonstrates this boundary and the resulting withdraw/repay freeze. [16](#0-15) [11](#0-10) 

The likelihood is therefore market- and liquidity-dependent rather than dependent on privileged action, leaked keys, or malformed token behavior. [10](#0-9) 

### Recommendation
Enforce a value-domain bound in addition to the index caps: before applying an index, compute the largest index satisfying `scaled.raw() * index.raw() / RAY <= i128::MAX` and clamp the stored index to that bound. [17](#0-16) 

Avoid deriving interest as `scaled * new_index - scaled * old_index`; compute the delta as `scaled * (new_index - old_index)` where safe, or keep aggregate-value calculations in `I256` and explicitly saturate protocol accounting rather than panicking. [18](#0-17) 

Add an invariant for every market that both `supplied * supply_index` and `borrowed * borrow_index` remain representable, and exercise the boundary in `update_indexes`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `recapitalize` tests. [7](#0-6) 

### Proof of Concept
For a listed 18-decimal debt asset `D` and collateral asset `C`, an attacker can execute:

```rust
let debt = HubAssetKey { hub_id, asset: d_asset };
let collateral = HubAssetKey { hub_id, asset: c_asset };
let principal: i128 = 1_000_000_000 * 10i128.pow(18);
let debt_amount = principal * 98 / 100;

let account = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(debt.clone(), principal), (collateral.clone(), collateral_amount)],
);
controller.borrow(attacker, account, vec![(debt.clone(), debt_amount)], None);

// Advance ledger time until:
// scaled_debt.raw() * next_borrow_index.raw() / RAY > i128::MAX
controller.update_indexes(attacker, vec![debt.clone()]);
```

`update_indexes` calls the pool accrual entrypoint, `accrue_step` computes the scaled debt values, and the multiplication panics once the value no longer fits in `i128`. [19](#0-18) [8](#0-7) [20](#0-19) 

Subsequent `withdraw` and `repay` calls accrue first and therefore revert with the same `MathOverflow`, leaving the market permanently frozen under the current code. [21](#0-20) [22](#0-21)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}
```

```rust
/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(

        cap <= max_cap_for_decimals(asset_decimals),
```
