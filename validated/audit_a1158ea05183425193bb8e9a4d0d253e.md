### Title
Webhook shop identity spoofing via unsigned `shop-domain` header — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC-signed bytes, while `ShopifyAPI::Webhooks::Registry.process` accepts the webhook purely on HMAC validity and then hands that unauthenticated `shop` value straight to the app's handler. Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, not per-shop, any merchant who has installed the app on their own store can obtain validly-signed webhook bodies and replay them with a forged `shop-domain` header to impersonate another tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` (as well as `topic`, `api_version`, `webhook_id`) is read directly from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e. the body) against the app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` checks nothing beyond this HMAC validity, then constructs `WebhookMetadata` using the raw, unverified `request.shop` and dispatches it to the registered handler: [4](#0-3) 

This is the exact bug class from the external report generalized to identity binding: the bytes that are cryptographically verified (the body) are disjoint from the bytes that are parsed and acted upon (the `shop-domain` header). By contrast, the gem's own OAuth flow shows the correct pattern — `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed payload so the shop cannot be swapped without invalidating the HMAC: [5](#0-4) 

Because the webhook HMAC secret (`api_secret_key`/`client_secret`) is shared across every shop that has the app installed (it is not a per-shop secret), an attacker who installs the app on their own shop can legitimately trigger a webhook, capture the raw body and its valid HMAC signature, and replay that exact request to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Registry.process` will accept it as valid (HMAC checks out against the correct, shared secret) and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant-identity binding: `shop authenticated == shop acted upon` should hold, but here the shop field the handler trusts is not covered by the signature at all. Any downstream logic in the host application that keys off `WebhookMetadata#shop` (e.g., mandatory `customers/redact`, `shop/redact`, `customers/data_request` handlers, order/customer data ingestion, per-tenant session lookups) can be fed forged, cross-tenant data by an attacker who only needs their own (possibly free/dev) store installation of the app. This constitutes cross-tenant access/data injection.

### Likelihood Explanation
Likelihood is Low-to-Moderate: it requires the attacker to have (or create) their own install of the target app to legitimately obtain one validly-signed webhook payload, then replay it against the app's public webhook endpoint with a modified header — no privileged credentials, tokens, or secrets are needed, and the HMAC secret used for verification is the app-wide `client_secret`, which is never disclosed to the attacker but doesn't need to be, since they only replay an already-signed body.

### Recommendation
Include the tenant-identifying fields (at minimum `shop`, and ideally `topic`/`webhook_id`) in the bytes that are HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed payload before it is trusted by `Registry.process`/`WebhookMetadata`. Since Shopify's outbound webhook signature format is fixed (body-only), the gem should, at minimum, document/enforce that consuming applications must independently validate `request.shop` against an expected/registered tenant list rather than trusting it as authenticated identity — but within this gem, decoupling of the trusted `shop` field from `Utils::HmacValidator.validate`'s verified bytes is the root cause and should be flagged/hardened.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining a legitimate webhook delivery (e.g., `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B`, the same valid header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and it matches `H` (the secret is app-wide, not shop-specific), so `Registry.process` proceeds: [6](#0-5) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker-supplied body `B` as if it originated from the victim's store.
