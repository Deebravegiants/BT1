## Analysis

The Tracer bug class is: **an unprivileged actor temporarily inflates a balance-derived input, causing a rate to be computed and *persisted* at an artificial value, which the protocol then treats as authoritative for a subsequent economic settlement period, extracting value or evading a cost.**

The closest reachable analog in Hyperbridge is the phantom-order price aggregation path for `IntentGateway`, which determines the `LiquidityPool.sellRate`/`buyRate` that `IntentGateway.quoteIntent` uses to price real user orders. [1](#0-0) [2](#0-1) 

### Title
Phantom-order price median can be set by a single self-funded solver via inventory-weight manipulation, corrupting the indexed pool rate used to quote real intents - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` weights every solver's phantom quote by that solver's live on-chain balance of the leg's output token, read via RPC at aggregation time, and then selects the **exact quote of whichever solver holds the majority of the summed weight** (`weightedMedian`) as the leg's price — not a blended average.

### Finding Description
Per-leg pricing is explicitly a selection, not a blend: "a solver holding over half the leg's weight sets the published price verbatim" [1](#0-0) . The weight is simply the solver's spot balance of the output token on the destination chain at read time [3](#0-2) , with no minimum bond, no time-lock, and no history requirement — any account can temporarily hold a large balance of the output token (borrowed capital, a treasury top-up, or a same-block transfer) for the duration of one bid window, submit a signed phantom bid quoting an extreme price, and thereby dominate the weight sum and force `weightedMedian` to pick its own price verbatim.

That single-bid-selected price is written into `PhantomOrderPriceSnapshotV2` and folded by `updateLiquidityPools`/`mergeChainRowsIntoPool` into the pool's persistent `sellRate`/`buyRate` [4](#0-3) . Exactly like the Tracer insurance rate, this derived value is **locked into protocol-facing state** and stays authoritative until the next bid window closes or a fill/inventory event refreshes it (see `foldInventoryReadings`) [5](#0-4) . `IntentGateway.quoteIntent` reads this rate directly as the market price for constructing real orders [6](#0-5) , with no fallback and no sanity check against a second, independent source once the `indexed_rates` strategy is selected.

The zero-weight defense only filters solvers with *no* balance; it does nothing to stop one over-weighted solver from being the sole determinant of the price, which is the exact "sufficiently full pool → rate goes to the extreme" pattern in the referenced report.

### Impact Explanation
A solver that temporarily inflates its own output-token balance during one phantom bid window can force the published `sellRate`/`buyRate` to any value it likes. Any user or integrator who then calls `quoteIntent` (or any downstream consumer of `LiquidityPool.buyRate/sellRate`) to size a real cross-chain order will construct that order against the corrupted rate. Since solvers auction to fill real orders separately from phantom pricing, a manipulated quote lets the attacking solver structure orders it fills itself at an artificially favorable rate, extracting value from users' escrowed inputs — the same "attacker profits from a manipulated, temporarily-inflated snapshot that is written into durable state and used for real settlement" pattern as the original insurance-rate bug.

### Likelihood Explanation
Exploitation requires no special privilege — any address that can be delegated as a `SolverAccount` and post a signed `UserOperation` bid can participate; only being an EIP-7702-delegated solver account is required, which is a configuration any actor willing to run a solver can obtain. The balance manipulation only needs to be held for one bid window, not for one atomic transaction, which lowers — not raises — the bar relative to the original flash-loan-based report. As with the original finding, repeated abuse (e.g., always dominating the weight in a given window) would likely be visible in monitoring, which is the same mitigating factor cited by the Tracer team, but a single or occasional exploitation is not self-evidently detectable before damage is done, and the code's own doc comments acknowledge the deliberate "whoever holds over half the weight sets the price" design without additional bounding.

### Recommendation
- Cap the influence any single solver's weight can have on `weightedMedian` regardless of its balance share (e.g., clamp weight to a fraction of total leg weight, or require a minimum number of distinct backed bidders before a snapshot is accepted as authoritative).
- Require the balance backing a phantom bid's weight to have been held for a minimum duration (a block-height or time-based lookback) rather than reading a single spot RPC balance, closing the same "inflate right before the snapshot" window the report describes for `Insurance.sol`.
- Add a deviation guard between a new snapshot's rate and the pool's prior `sellRate`/`buyRate` (similar to `warnOnDivergentSample`, but rejecting rather than merely warning) so one dominant bidder cannot move the persisted market rate by more than a bounded percentage per window.

### Proof of Concept
1. Attacker becomes (or controls) an EIP-7702-delegated `SolverAccount` on the destination chain of a tracked pool leg.
2. During one `PhantomOrderV2` bid window, attacker temporarily moves a large balance of the leg's output token into the solver address (no flash loan needed — the read is a simple RPC balance check at aggregation time, not gated to one transaction).
3. Attacker signs and submits a `UserOperation` phantom bid quoting an extreme price for that leg.
4. Once `PhantomBidWindowExhausted` fires, `aggregatePhantomBids` weights quotes by output-token balance; the attacker's inflated balance makes it the majority weight, so `weightedMedian` returns the attacker's own extreme quote verbatim [7](#0-6) .
5. `updateLiquidityPools`/`mergeChainRowsIntoPool` persist that price into `LiquidityPool.sellRate`/`buyRate` [8](#0-7) .
6. Attacker withdraws the inflated balance; the corrupted rate remains authoritative until the next snapshot or fold event.
7. Any `quoteIntent` call made in the interim prices a real order off the corrupted rate, letting the attacking solver fill it at the manipulated rate and extract value from the user's escrow.

```typescript
function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}
```

```typescript
export async function foldInventoryReadings(params: { blockNumber: bigint }): Promise<void> {
	const { blockNumber } = params

	// The whole table, paged: the store offers no "newer than" filter, and the set is bounded by
	// bidders times tokens times chains, so the pass is a handful of pages at most.
	const readings = await readAllPages((limit, offset) =>
		SolverInventoryReading.getByFields([], { limit, offset, orderBy: "id", orderDirection: "ASC" }),
	)
	const fresh = readings.filter((reading) => (foldedReadings.get(reading.id) ?? -1) < reading.observedAt.getTime())
	if (fresh.length === 0) return

	const byChain = new Map<string, Map<string, SolverInventoryReading>>()
	for (const reading of fresh) {
		const targets = byChain.get(reading.chain) ?? new Map<string, SolverInventoryReading>()
		byChain.set(reading.chain, targets)
		targets.set(`${reading.provider.toLowerCase()}|${reading.tokenAddress.toLowerCase()}`, reading)
	}

	const touchedPools = new Set<string>()
	const applied = new Map<string, SolverInventoryReading>()
	for (const [chain, targets] of byChain) {
		// Every bidder on the chain, grouped by pool: a pool-chain is the unit that gets republished,
		// and reading it whole is what lets a direction whose bidders all vanished be zeroed.
		const rows = await readAllPages((limit, offset) =>
			PoolBidder.getByFields([["chain", "=", chain]], { limit, offset, orderBy: "id", orderDirection: "ASC" }),
		)
		const byPool = new Map<string, PoolBidder[]>()
		for (const row of rows) byPool.set(row.poolId, [...(byPool.get(row.poolId) ?? []), row])

		for (const [poolId, poolRows] of byPool) {
			const directions = new Set(poolRows.map((row) => row.direction))
			const survivors: PoolBidder[] = []
			let changed = false
			for (const row of poolRows) {
				const reading = targets.get(`${row.providerId.toLowerCase()}|${row.outputToken.toLowerCase()}`)
				if (!reading || !readingIsNewer(reading, row)) {
					survivors.push(row)
					continue
				}
				const liquidity = normalizedLiquidity(chain, row.outputToken, reading.balance)
				if (liquidity === null) {
					survivors.push(row)
					continue
				}
				changed = true
				applied.set(reading.id, reading)
				// Every row is a bidder with capacity, so a bidder holding nothing loses its row.
				if (liquidity === 0n) {
					await PoolBidder.remove(row.id)
					continue
				}
				row.liquidity = liquidity
				row.refreshedAt = reading.observedAt
				await row.save()
				survivors.push(row)
			}
			if (!changed) continue
			await republishChainRows(poolId, chain, survivors, directions)
			touchedPools.add(poolId)
		}
	}

	for (const reading of applied.values()) {
		await recordProviderBalance(reading, blockNumber)
	}

	for (const poolId of touchedPools) {
		const pool = await LiquidityPool.get(poolId)
		if (!pool) continue
		const chainRows = await PoolChainLiquidity.getByPoolId(poolId, { limit: CHAIN_ROWS_LIMIT })
		if (chainRows.length === 0) continue
		mergeChainRowsIntoPool(pool, chainRows, blockNumber)
		await pool.save()
	}

	// Recorded whether or not a reading applied to anything: one older than every row it could
	// back stays older, and one backing no row gains nothing from being looked at again.
	for (const reading of fresh) foldedReadings.set(reading.id, reading.observedAt.getTime())
}
```

```markdown
# 2026-08-25 — Intent quotes default to directional indexed rates without fallback

Chosen: `quoteIntent` defaults to an `indexed_rates` strategy that selects the depth-weighted aggregate `LiquidityPool.buyRate` for base-to-quote orders and `sellRate` for quote-to-base orders. Source and destination chains resolve the configured token deployments; raw amounts are calculated from the indexer's 18-decimal whole-token pool rate and both tokens' configured decimals. A missing directional rate is an error.

Alternatives considered:

- **Keep defaulting to the legacy directional Phantom snapshot.** Rejected: those snapshots resolve through a canonical Base market and do not use the pair-centric pool rate, so quotes can disagree with the indexer's current market.
- **Quote directly from one source/destination pair of `PoolChainLiquidity` rows.** Rejected: those rows are inputs to the indexer's pool price. `LiquidityPool.buyRate` and `sellRate` are the maintained depth-weighted merge of fresh chain samples and are the intended market-level quote.
```
