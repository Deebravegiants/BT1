### Title
Fee-on-transfer / short-transfer SIP-010 assets cause vault share/asset over-crediting versus actual tokens received - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Every vault's `deposit` function computes the shares to mint and the internal `assets` ledger increment directly from the caller-supplied `amount` parameter, without ever verifying that the vault actually received `amount` of the underlying SIP-010 token. If the configured underlying asset takes a transfer fee (or otherwise delivers less than the nominal `amount`), the vault mints shares and increases its assets accounting for tokens it never actually custodied, breaking the 1:1 identity between minted shares/assets-ledger and real token backing.

### Finding Description
In each vault contract (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, and their `local-testing` mirrors), `deposit` does: [1](#0-0) 

The shares to mint, `inkind`, are pre-computed from the nominal `amount` via `convert-to-shares-preview amount` *before* the transfer happens, and after `(try! (receive-underlying amount account))` the code unconditionally does `(try! (ft-mint? zft inkind recipient))` and `(var-set assets (+ current-assets amount))`. There is no balance-before/balance-after check to confirm the vault's actual underlying balance grew by `amount`; the code simply trusts the nominal value.

The same nominal-amount trust pattern appears one layer up in the market's collateral-top-up flow, which forwards user-supplied SIP-010 tokens via a generic `<ft-trait>`: [2](#0-1) 

`(contract-call? ft transfer amount account current-contract none)` is trusted to have delivered exactly `amount`, and that same `amount` is then passed straight into `vault-deposit`, compounding the accounting error identity `assets_ledger += amount` even when `balance_actual += amount - fee`.

This breaks the custody-vs-ledger identity that backs the protocol's core invariant:

`sum(shares) * price_per_share == actual_underlying_balance_held_by_vault`

After a fee-on-transfer deposit of nominal `amount` with fee `f`:
- Ledger side: `assets += amount`, `shares += convert_to_shares(amount)`
- Custody side: `actual_balance += amount - f`

The deficit `f` is never detected or reconciled, so shares now represent more value than the vault actually holds.

### Impact Explanation
Every subsequent depositor's shares are diluted relative to real backing, and on `redeem`, `available_assets`/`current-assets` checks pass using the inflated ledger `assets` value while actual on-chain token balance is lower. Once enough deposits/withdrawals accumulate this deficit, redeeming users can drain the vault's real token balance before all share-holders redeem, meaning the shortfall is socialized onto later withdrawers — a direct principal loss / protocol insolvency for the affected vault, matching the accepted "Critical: theft of principal ... or protocol insolvency" impact category, contingent on the underlying asset actually charging a transfer fee.

### Likelihood Explanation
Likelihood depends entirely on whether the underlying token configured for a given vault deployment is fee-on-transfer. The current mainnet asset set (USDC, USDH, sBTC, stSTX, stSTXbtc, STX) as typically deployed are not fee-on-transfer tokens, but the vault code enforces no restriction preventing an asset with such behavior (any SIP-010-conforming token satisfying `<ft-trait>`) from being onboarded, and the accounting logic itself provides zero defense if it were. This is a code-level defect independent of current token choice, but its exploitability is conditional on asset selection, which is a governance/DAO decision outside the code path itself — this lowers realistic likelihood under the current known asset list.

### Recommendation
In each vault's `deposit` (and the market's `supply-collateral-add`/`receive-underlying` helper), measure the vault's actual token balance immediately before and after the transfer/`receive-underlying` call, and use the observed delta — not the caller-supplied nominal `amount` — for both `convert-to-shares` share minting and the `assets` ledger increment.

### Proof of Concept
1. DAO/governance onboards a SIP-010 token with a transfer fee (e.g. 1%) as a new vault's underlying asset (permitted since `<ft-trait>` imposes no fee-on-transfer restriction).
2. Attacker (or any depositor) calls `deposit amount min-out recipient` on that vault: [3](#0-2) 
3. `receive-underlying` moves `amount` nominal tokens, but the vault's actual balance only grows by `amount * 0.99` due to the fee.
4. `inkind` shares are minted based on full `amount`, and `assets` is incremented by full `amount`, even though real custody is `1%` short.
5. Repeating deposits/withdrawals accumulates the shortfall; when total redemption pressure exceeds actual token balance held, the last redeemers cannot be paid in full even though the ledger reports sufficient `assets`, resulting in stuck/lost principal for those users.
