### Title
`RequestState` replay bypasses source-identity filtering, allowing cross-session state disclosure - (File: `orb-relay-client/src/client.rs`)

### Finding Description
In `PollerAgent::main_loop`, the branch that handles an incoming `RelayPayload` checks `self_serve::app::v1::RequestState::matches(&payload)` **before** the `src.id != self.config.dst_id` identity check is evaluated: [1](#0-0) 

If the payload matches `RequestState`, the code unconditionally calls `sender_tx.send(self.last_message.clone())`, without ever inspecting `src`. The `src.id != self.config.dst_id` filter — which is the only mechanism that restricts message processing to the intended peer — is only reached in the `else if` branch, i.e., it is skipped entirely for `RequestState` payloads.

`self.last_message` is the orb's most recently sent outgoing message (e.g. `AnnounceOrbId`, `CaptureStarted`, `SignupEnded`), stored unconditionally whenever a message is sent: [2](#0-1) 

This means any entity capable of delivering a `RelayPayload` into this client's `response_stream` — regardless of its `src.id` — can trigger a replay of the orb's last state message.

However, the actual exploitability hinges entirely on server-side/relay-transport session isolation, which is **not implemented in this crate**. This crate (`orb-relay-client`) is only the client-side gRPC stream consumer; whether an "unrelated" attacker session can even deliver payloads into a given orb's `response_stream` is determined by the relay server (out of scope of this repo) and by how `dst_id`/queue routing works there. I was unable to fully verify, within this repository, whether the relay server multiplexes multiple unrelated sessions onto the same client stream or strictly isolates queues per session/dst_id before delivery. If the server strictly isolates delivery per queue/session (which is the documented intent based on `dst_id`/`src_id` config fields), then an "unrelated" session could never reach this code path in the first place, making the missing client-side check redundant defense-in-depth rather than an exploitable vulnerability by itself.

### Impact Explanation
If reachable, the impact is limited to disclosure/replay of the orb's last outgoing self-serve state message (e.g., re-announcing `AnnounceOrbId`, replaying `CaptureStarted`/`SignupEnded`) to a party that did not originate it. This is a state/metadata replay, not an authorization bypass, identity-binding compromise, or biometric data leak — the replayed messages do not contain biometric data. This would map to a low-severity "cross-session state bleed" / informational disclosure at most, not the higher-severity signup-compromise categories (unauthorized signup, wrong-identity binding, liveness bypass, attestation forgery) the audit scope focuses on.

### Likelihood Explanation
Cannot be confirmed as reachable from the artifacts available in this repository. The precondition "attacker owns a valid but unrelated relay session" requires that the relay server delivers messages from unrelated sessions into this same client's stream — a server-side behavior not present in `orb-relay-client`. Without confirmation of that server behavior, the described attack path cannot be validated as a real, reproducible vulnerability solely from this code.

### Recommendation
Regardless of server-side guarantees, move the `src.id != self.config.dst_id` check above (or into) the `RequestState` handling so that state replay is only sent to the peer identified by `dst_id`, e.g. restructure the branch to check `src.id == self.config.dst_id` first, then match on `RequestState` vs. other payload types. This closes the gap defensively even if the relay server is expected to isolate sessions.

### Proof of Concept
Not confirmed exploitable: this would require an integration test harness that also emulates the relay *server's* multiplexing behavior (not present in this repo) to demonstrate that a second, unrelated session's `RequestState` payload actually reaches a given `PollerAgent`'s `response_stream`. Without that server component, a unit test can only show the client-side logic gap (i.e., that the `matches` branch does not check `src`), not a full end-to-end exploit.
