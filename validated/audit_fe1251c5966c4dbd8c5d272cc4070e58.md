### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant spoofing of webhook data - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request body. The `shop` value that is handed to the app's webhook handler is read from an HTTP header that is never included in the signed payload, and the HMAC secret (`Context.api_secret_key`) is the app's single, shop-independent `client_secret`. Any party who can get one valid HMAC (e.g. by operating their own install of the app) can therefore produce a request with a body they fully control and an arbitrary `x-shopify-shop-domain` header claiming to be a different merchant, and the gem will report it to the handler as `WebhookMetadata` for that other shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is simply the raw body — none of the Shopify headers are part of the signed material: [2](#0-1) 

The `shop` accessor used downstream is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to the HMAC at all: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then forwards the (unauthenticated) `request.shop` value directly into the `WebhookMetadata` object passed to the app's handler: [4](#0-3) 

Critically, the HMAC secret used for verification is the single, app-wide `api_secret_key` (`client_secret`), not a per-shop secret: [5](#0-4) 

This means: *any* shop that has installed the app knows a value that lets them (indirectly, since Shopify itself signs webhooks) construct a `raw_body`/`hmac` pair that will pass validation for *that specific body* — and the gem's documented `data.shop` claim is not bound to that HMAC in any way. Formally, the invariant the caller relies on is:
```
HMAC_valid(body, hmac) == true  =>  shop_header == originating_shop
```
but the actual code only guarantees:
```
HMAC_valid(body, hmac) == true  =>  body was signed with Context.api_secret_key
```
with `shop_header` completely uncontrolled by the signature. The equality the code should enforce (`shop` field acted upon == `shop` field covered by the HMAC) is broken.

### Impact Explanation
Because the app documentation instructs developers to trust `data.shop` to route/attribute webhook payloads to a specific merchant's tenant data (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`, per `docs/usage/webhooks.md`), any host application built per this gem's documented contract can be made to ingest attacker-controlled webhook bodies under an arbitrary victim shop's identity. This is a cross-tenant data-integrity/data-injection issue: an attacker with any own-shop webhook delivery capability (which is trivial to obtain — any developer/tester installing the app on their own store receives real, validly-HMAC'd webhooks from Shopify with fully attacker-controlled body content, e.g. via product/order titles or custom webhook topics) can relay/replay that body while swapping the `x-shopify-shop-domain` header to point at a different merchant, since nothing in the verification path detects the substitution. This falls under "cross-tenant access" per the accepted High/Critical impact categories, since it lets one tenant inject data attributed to another tenant purely through header manipulation, defeating the tenant isolation the gem's own webhook API is meant to provide.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker still needs a genuinely Shopify-issued, validly-signed webhook body to relay (they cannot forge the HMAC without knowing `api_secret_key`), and the body content they control is limited to fields Shopify will echo back for their own shop's data (product/order/customer text fields, custom webhook topic payloads, etc.), then replayed with a forged shop header directly to the app's webhook endpoint (bypassing Shopify's per-request delivery envelope, which the gem does nothing to prevent since it never checks webhook freshness/origin IP or binds `shop` to the signature). Any developer or attacker who legitimately installs the target app on their own test/attacker-controlled shop can trivially obtain such signed bodies, making exploitation realistic rather than purely theoretical.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values in the HMAC-signed material for webhook requests, or otherwise cryptographically bind the shop identity to the verified payload before it is surfaced to handlers via `WebhookMetadata`. At minimum, update `Webhooks::Request#to_signable_string` to incorporate the shop-domain header, and document that host apps must not treat `data.shop` as authenticated unless this binding exists.

### Proof of Concept
1. Attacker installs the target Shopify app on their own test shop `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g., `products/update`) whose body content they fully control (e.g., a product title field containing attacker-chosen data). Shopify signs this body with the app's single `client_secret` and delivers it with header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this exact `raw_body` + `hmac` pair to the app's registered webhook endpoint, but substitutes the header `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the (unchanged) HMAC — see `lib/shopify_api/utils/hmac_validator.rb` lines 12-22, `lib/shopify_api/webhooks/request.rb` lines 35-38.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, causing the host app to process attacker-controlled data as if it originated from `victim.myshopify.com`.
