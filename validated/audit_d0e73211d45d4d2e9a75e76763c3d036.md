### Title
Tron `IntentGatewayV2.placeOrder` escrows the requested amount instead of the actual received amount for fee-on-transfer tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2.sol` credits escrow (`_orders[commitment][token]`) with `reducedInputs[i].amount`, which is derived from the user-supplied `order.inputs[i].amount` minus protocol fee, rather than the amount the contract actually received via `safeTransferFrom`. If the input token charges a transfer fee (fee-on-transfer / deflationary token), the gateway will hold fewer tokens than it records in escrow, causing later withdrawals (solver fill payout, cancellation refund, or cross-chain `RedeemEscrow`/`RefundEscrow`) to revert or leave some legitimate claim under-collateralized/unpayable.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` (lines 331-506), for the non-predispatch path:

```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);

// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
``` [1](#0-0) 

`reducedInputs[i].amount` is computed purely from `order.inputs[i].amount` (the amount the user requested to transfer) minus the protocol fee bps — it never inspects the gateway's actual token balance before/after the transfer:

```solidity
uint256 originalAmount = order.inputs[i].amount;
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
...
reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
``` [2](#0-1) 

The same pattern exists in the predispatch branch, where dust is measured against `requiredAmount` for revert checks, but the credited escrow amount is still `reducedInputs[i].amount` (the nominal, pre-transfer-fee amount), not what the gateway actually holds:

```solidity
uint256 dust = balance - requiredAmount;
if (dust > 0) emit DustCollected(token, dust);

// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
``` [3](#0-2) 

This is exactly the bug class from the referenced report: an accounting mapping (`_orders`/`claims`) is credited with the pre-fee amount while the contract's real token balance is smaller due to a fee-on-transfer token, so later attempts to pay out the recorded amount (to a solver on `fillOrder`, to the user on `cancelOrder`/refund, or via cross-chain `RedeemEscrow`/`RefundEscrow` delivered through `onAccept` → `withdraw`) can revert or under-fund the intended recipient. Notably, the primary EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against this exact issue by snapshotting `balanceOf` before/after `safeTransferFrom` and mutating `order.inputs[i].amount` to the actually-received value before computing the commitment/escrow:

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [4](#0-3) 

The Tron variant, `evm/tron/contracts/apps/IntentGatewayV2.sol`, was not updated with this balance-before/after protection and still escrows the nominal requested amount.

### Impact Explanation
Because escrow is over-credited relative to actual token holdings, a solver filling the order (or the user cancelling/refunding, or a cross-chain `RedeemEscrow`/`RefundEscrow` settlement processed through `onAccept`) will be owed more tokens than the contract holds. Depending on how the withdraw path moves funds (transfer of the exact escrowed amount), this can cause reverts that permanently strand the order (denial of service / stuck funds for the recipient), or — if the withdraw function doesn't validate balance and pays from a shared pool — allow one order's shortfall to be paid from tokens escrowed for a different order, silently draining unrelated users' escrowed balances. Either outcome is a fund-freezing/fund-loss issue affecting the intents escrow subsystem reachable by any user placing an order with a fee-on-transfer ERC-20 as input on the Tron deployment.

### Likelihood Explanation
Likelihood is high whenever the Tron `IntentGatewayV2` is deployed to support arbitrary ERC-20 inputs (as intended by the `Order.inputs` API), since any unprivileged user can place an order using a fee-on-transfer token with zero special privileges required — this exactly mirrors the reachable path already fixed on the primary EVM contract and explicitly tested for (`testPlaceAndFill_FeeOnTransferToken_RoundTrip`, `testPlaceOrder_FeeOnTransferToken_Predispatch` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), confirming the protocol treats fee-on-transfer tokens as an expected, in-scope input type that the Tron contract fails to handle safely.

### Recommendation
Apply the same balance-before/after correction used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`: snapshot `IERC20(token).balanceOf(address(this))` immediately before `safeTransferFrom` and immediately after, use the delta as the actually-received amount, and compute `reducedInputs`/escrow credit and the commitment hash from that received amount rather than from the user-supplied `order.inputs[i].amount`. Apply the equivalent fix to the predispatch sweep path (measure actual balance delta on the gateway after sweeping from the dispatcher, as already done in the primary contract) before crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with a fee-on-transfer ERC-20 (e.g., 1% transfer fee, as modeled by `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) configured as a valid input token.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and approves the gateway for `1000e18`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but due to the 1% fee the gateway actually receives only `990e18`.
4. `_orders[commitment][FOT]` is nonetheless credited with `reducedInputs[0].amount` derived from the full `1000e18` (minus any protocol fee), i.e. an amount exceeding the `990e18` actually held.
5. When a solver later calls `fillOrder` (or the user calls `cancelOrder`, or a cross-chain `RedeemEscrow`/`RefundEscrow` is delivered via `onAccept`), the `withdraw` path attempts to pay out the escrowed (over-stated) amount, which the contract cannot fully cover from its actual FOT balance — causing a revert (funds stuck) or, if the withdraw logic lacks a balance guard, paying from other users' escrowed token balances.
