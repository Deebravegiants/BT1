## Title
Webhook HMAC signature does not bind `shop-domain` and `topic` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the registry dispatches to app handlers are read from unsigned HTTP headers. This breaks the intended identity binding: `hmac_valid(body) == true` is treated as proof that `(body, shop, topic)` as a tuple came from Shopify for that specific shop, but the signature only actually authenticates `body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled straight from HTTP headers, which are never part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only ever checks `to_signable_string` (the body) against the `hmac` header: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to the handler using the *unsigned* `request.shop` and `request.topic`: [4](#0-3) 

This is exactly the "bytes verified vs. bytes parsed" identity-binding break: the HMAC proves `body` is authentic Shopify content signed with the app's `client_secret`, but the tenant identity (`shop`) that the handler acts on is not covered by that proof. Since a webhook signing secret is the app's shared `client_secret` (not per-shop), any shop that has the app installed can legitimately receive a validly-signed `(body, hmac)` pair from Shopify for its own store, then replay that exact body/hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header to name a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke the topic handler with `WebhookMetadata.new(shop: <victim-shop>, ...)`, causing the app to process attacker-controlled webhook content attributed to a tenant the attacker does not own.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an entity that only controls its own (legitimately installed) shop can cause the app's webhook handlers to run business logic keyed to an arbitrary victim shop, using attacker-chosen body content, headers only. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (data storage, uninstall/redact handling, order/customer sync, billing state, etc.), this can lead to cross-tenant data corruption or disclosure — the "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any developer using only the documented API: the gem provides no protection, and nothing in the public interface hints that `shop`/`topic` are unauthenticated. Any actor who can install the app on their own store (a normal, unprivileged action) can capture a genuine `(body, hmac)` pair and replay it with forged shop/topic headers to the app's public webhook endpoint.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signed content that `to_signable_string` returns, or otherwise cryptographically bind them (e.g., verify the HMAC over `raw_body + canonicalized headers`). At minimum, `Registry.process` should not trust `request.shop`/`request.topic` unless they are covered by the same HMAC proof used to validate the payload.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; receive a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because it's signed with the app's shared `client_secret`).
2. Replay the exact same request to the app's webhook endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`).
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) returns `true` because it only re-derives the signature over `@raw_body`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: <forged topic>, body: parsed(B), ...)`, causing the app to act on attacker-supplied data as if it were sent by/for `victim.myshopify.com`.
