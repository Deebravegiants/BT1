### Title
Oversized receipts silently clamped to `max_receipt_size` in congestion accounting instead of being rejected, allowing unprivileged accounts to bypass bandwidth/congestion limits - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`CLFactory.getSwapFee` silently discards a governance-configured fee above its hardcoded 10% ceiling and substitutes the tick-spacing default instead of reverting, letting the value the module actually reports diverge from what the factory enforces. The same "silently substitute a smaller value for out-of-range input instead of rejecting it" pattern exists in nearcore's congestion-control forwarding logic, where receipts that exceed the protocol's hard receipt-size limit are not rejected but have their accounted size clamped down to `max_receipt_size` before the bandwidth/congestion admission check.

### Finding Description
`ReceiptSinkV2::try_forward` explicitly clamps the size used for the outgoing-bandwidth/congestion admission check whenever a receipt is actually larger than `max_receipt_size`, instead of rejecting it: [1](#0-0) 

This is a deliberate workaround for a known validation gap (nearcore issue #12606): `validate_receipt` computes `borsh::object_length(receipt)` and checks it against `limit_config.max_receipt_size` only in `ValidateReceiptMode::NewReceipt`, but for certain promise DAGs (e.g. a promise that returns another promise, or a value-return path) the receipt is validated *before* `output_data_receivers` is appended, so its final serialized size can exceed the limit after the fact: [2](#0-1) 

An unprivileged account can trigger this via ordinary cross-contract-call promise chaining, confirmed by the existing regression test that documents this exact bug: [3](#0-2) 

Once such an oversized receipt exists, `try_forward` does not reject it or treat it as an error; it pretends the receipt is exactly `max_receipt_size` for the purpose of the congestion/bandwidth admission comparison (`forward_limit.size >= size`), then forwards or buffers it while deducting only the *clamped* size from the receiver's remaining `OutgoingLimit`, not its true size: [4](#0-3) 

This mirrors the reported bug class exactly: a downstream enforcement point (factory ceiling / congestion admission) silently substitutes a bounded, incorrect value for an out-of-range input instead of reverting/rejecting, so the accounted state no longer reflects reality.

### Impact Explanation
Because the real byte size is never used for the outgoing-limit decrement, a shard can forward/accept receipts whose true total size exceeds the intended `outgoing_receipts_usual_size_limit` / `outgoing_receipts_big_size_limit` and `max_receipt_size` budget that the whole `ChunkStateWitness` sizing model (`docs/misc/state_witness_size_limits.md`) is built around. This causes the actual bytes moved/stored per chunk to be understated relative to the enforced cap — i.e., the congestion/bandwidth accounting is silently underpriced versus the actual resource consumption, which can push `ChunkStateWitness` size above its designed ~21 MiB bound and degrade distribution/validation performance, an unbounded-resource-use condition reachable purely through normal contract execution by any account.

### Likelihood Explanation
Triggering the underlying oversized receipt requires only a standard promise-chaining contract call pattern (already demonstrated to work in the existing test suite), so no privileged role or validator/node compromise is needed — any account that can deploy/call a contract can reach this path.

### Recommendation
Fix the root cause identified in issue #12606 so `validate_receipt`/`NewReceipt` validation accounts for `output_data_receivers` and any other post-hoc mutations before final serialization, ensuring receipts can never exceed `max_receipt_size` in the first place. Until then, `try_forward` should not silently clamp the accounted size for limit comparisons — it should either reject/hard-fail on receipts that already exceed `max_receipt_size`, or decrement the outgoing limit by the receipt's true size (potentially driving the limit negative/zero) rather than by the clamped value, so congestion/bandwidth accounting cannot be silently underrepresented.

### Proof of Concept [5](#0-4) 
The existing `test_max_receipt_size_promise_return` test deploys a contract, issues a promise chain `A -> C -> B` where `C`'s receipt is built to exactly `max_receipt_size`, then has `output_data_receivers` appended afterward, pushing it over the limit; `assert_oversized_receipt_occurred` confirms an incoming receipt with `receipt_size > max_receipt_size` is actually processed on-chain rather than rejected, and the code comment at `congestion_control.rs:413-417` confirms this oversized receipt's size is then clamped (not rejected) during congestion/bandwidth admission accounting.

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,

        account,

        Balance::ZERO,

        "".into(),
