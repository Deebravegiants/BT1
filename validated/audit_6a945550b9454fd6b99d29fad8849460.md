### Title
Webhook `shop` identity is taken from an unauthenticated header, not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. This breaks the intended binding `shop_used_by_handler == shop_bound_by_HMAC`, letting an attacker with any legitimately signed webhook payload (from a shop they control) relabel it as coming from an arbitrary victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string` (i.e. the raw body) using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then forwards the attacker-controlled, unauthenticated `shop` field straight into the handler's metadata without any additional cross-check: [4](#0-3) 

Because `client_secret`/`api_secret_key` is shared across every shop that installs the same app, an unprivileged user who installs the app on a shop they control receives their own legitimately-signed webhooks (valid `raw_body` + HMAC for their own shop). Since the HMAC never binds to the `shop-domain` header, that same `raw_body`/HMAC pair remains valid if replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different, victim shop. The gem will report `Utils::HmacValidator.validate(request)` as `true` and pass `request.shop` (now the victim's domain) to the registered `WebhookHandler`, exactly matching the "field acted on but not covered by the HMAC" identity-binding class from the referenced report (there, `totalPowerInTokens` was trusted without being re-derived/re-validated against the state actually backing the decision; here, `shop` is trusted without being covered by the same signature that is meant to authenticate the payload).

### Impact Explanation
Any app built on this gem that uses the `shop` value from `WebhookMetadata`/`Request#shop` to select which tenant's data to create, update, or delete (a standard and expected usage pattern for multi-tenant Shopify apps) can be made to attribute attacker-supplied webhook data to an arbitrary victim shop. This is a cross-tenant integrity/confusion issue: an attacker-controlled payload, properly signed for the attacker's own shop, gets processed as if it originated from a shop the attacker does not control. Depending on the handler's logic (e.g., `shop/redact`, `customers/redact`, `app/uninstalled`, or custom order/product sync handlers), this can lead to unauthorized cross-tenant data mutation or deletion — satisfying the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on any shop (trivial for public/unlisted embedded apps, requiring no special privilege beyond being a Shopify merchant), (2) capturing one legitimately delivered webhook (raw body + `X-Shopify-Hmac-Sha256` header) for that shop, and (3) POSTing that unmodified body/HMAC pair to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No access token, `api_secret_key`, or privileged account is needed. This is straightforward for any unprivileged internet user who can install the target app.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) claims into the HMAC-signed material rather than trusting a header, or independently re-validate that the reporting shop matches a shop known to be associated with the specific webhook subscription/access token used to register it. At minimum, `Request#to_signable_string` should incorporate the shop-domain header (and other identity-bearing headers) so that `Utils::HmacValidator.validate` cannot pass when those headers are altered independently of the body's signature.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`; Shopify delivers a legitimate webhook:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`, `X-Shopify-Topic: orders/create`
   - Body: `raw_body` (attacker fully controls the content of orders on their own store).
2. Attacker builds a new HTTP request to the app's webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request object; `shop` now returns `"victim.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only (per `to_signable_string`) — it still matches, since `raw_body` was untouched, per: [5](#0-4) 

5. The handler is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` and attacker-chosen `body`, even though the request never touched Shopify on behalf of `victim.myshopify.com`.
