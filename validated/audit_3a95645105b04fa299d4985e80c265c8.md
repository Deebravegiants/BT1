### Title
Missing Arbitrum Sequencer Uptime check allows `SimplexPaymaster` to price gas fees off stale Chainlink data during a sequencer outage - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` is deployed on Arbitrum (per `sdk/packages/sdk/src/configs/chain.ts` and `docs/content/developers/evm/simplex/configuration.mdx`) and prices ERC-4337 gas sponsorship using two Chainlink `AggregatorV3Interface` feeds (`nativeOracle`, `TokenConfig.tokenOracle`). Its only staleness protection is a fixed time-since-update window (`maxOracleAge`), with no check on the Arbitrum Sequencer Uptime Feed as recommended by Chainlink for L2 deployments.

### Finding Description
`_getOraclePrice` reads `latestRoundData()` and only validates the answer is positive and not older than `maxOracleAge`: [1](#0-0) 

`_tokenPrice` calls `_getOraclePrice` for both the native asset and the ERC-20 token feed and derives the conversion rate used to charge the user's gas fee: [2](#0-1) 

On Arbitrum, when the sequencer goes down, the L1 escape hatch (`ArbSys`) still allows transaction inclusion, and the sequencer coming back online can post a backlog of transactions with stale but not-yet-expired `updatedAt` timestamps from Chainlink. During this window, `_getOraclePrice`'s `block.timestamp - updatedAt <= maxOracleAge` check can pass even though the price feed hasn't been refreshed for the actual elapsed real-world time, because Arbitrum's `block.timestamp` tracks L1-time approximations that can also be manipulated/lag during sequencer downtime. There is no `sequencerUptimeFeed.latestRoundData()` check (the Chainlink-recommended pattern) anywhere in `SimplexPaymaster.sol` or elsewhere in the EVM contracts.

### Impact Explanation
If Arbitrum's sequencer is down or recovering, `SimplexPaymaster.getTokenPrice`/`estimateTokenCost`/`_tokenPrice` can compute gas-sponsorship pricing (native/USD vs token/USD conversion) from stale Chainlink rounds without any sequencer-liveness gate. An attacker/solver who monitors sequencer outages could submit UserOperations during the outage/recovery window to pay in an ERC-20 token at a stale, favorable exchange rate relative to the paymaster's actual native-gas cost, resulting in the paymaster underpricing gas fees and losing value on every affected sponsored operation. This is a protocol/fund-loss issue for the deployed paymaster (loss of accumulated markup/treasury value, and depletion of the EntryPoint deposit through consistently underpriced operations), a Medium severity impact consistent with the analog report.

### Likelihood Explanation
Arbitrum sequencer downtimes are infrequent but documented events. The `SimplexPaymaster` is a permissionless, publicly-callable contract (any UserOperation submitter/bundler can trigger `_tokenPrice`/`_prefund` paths), so exploitation requires no special privilege beyond normal usage during a sequencer outage — the analog is squarely within the unprivileged "relayer/bundler submits transaction" reachability class required by scope rules.

### Recommendation
Add an Arbitrum Sequencer Uptime Feed check to `_getOraclePrice` (or a dedicated `_checkSequencerUp()` guard called before pricing), following Chainlink's recommended pattern: read `sequencerUptimeFeed.latestRoundData()`, revert if `answer == 1` (sequencer down), and enforce a grace period after `startedAt` (typically 1 hour) before trusting feed data again. Make this check chain-conditional (only enabled where a sequencer uptime feed exists, e.g., Arbitrum/Optimism-style L2s configured via governance `Params`).

### Proof of Concept
1. Deploy/observe `SimplexPaymaster` on Arbitrum with `nativeOracle`/token oracles set to Chainlink feeds and `maxOracleAge` set to the feed's normal heartbeat (e.g., 24h for ETH/USD).
2. Simulate an Arbitrum Sequencer outage; Chainlink feeds on Arbitrum stop updating because they rely on the sequencer relaying updates, but `updatedAt` from the last successful round remains within `maxOracleAge`.
3. During the outage (or shortly after sequencer recovery, before feeds catch up), have a user submit a `PackedUserOperation` with paymasterData referencing a token whose real-world market price has moved (e.g., dropped) since the last on-chain round.
4. `_getOraclePrice` passes its staleness check (`block.timestamp - updatedAt <= maxOracleAge`) despite the price being stale, and `_tokenPrice`/`estimateTokenCost` computes the ERC-20 charge from the outdated rate.
5. `_prefund` collects the ERC-20 amount computed from the stale rate; the paymaster is systematically underpaid relative to actual native-gas cost, draining EntryPoint deposit/treasury value over the outage window. This confirms the root cause: [3](#0-2)  has no Arbitrum Sequencer Uptime Feed gate.

```text
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
