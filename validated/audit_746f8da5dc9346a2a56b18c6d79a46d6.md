This confirms the finding. In the OAuth flow, `AuthQuery#to_signable_string` explicitly includes `shop` as one of the signed fields [1](#0-0) , but in the webhook flow, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [3](#0-2) . `Registry.process` only validates the HMAC of the body and then trusts `request.shop`/`request.topic` when constructing `WebhookMetadata` passed to the handler [4](#0-3) . The `HmacValidator` uses a single, app-wide `Context.api_secret_key` (not a per-shop secret) to verify the body [5](#0-4) .

### Title
Webhook `shop`/`topic` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the `shop-domain` and `topic` headers used downstream for tenant/handler dispatch are never included in the signed content. Because the HMAC secret (`Context.api_secret_key`) is shared across all shops that install the app (it is not a per-shop secret), any party who can obtain one validly-signed webhook body/HMAC pair for their own shop can replay that same body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header, and `Registry.process` will accept it as an authentic webhook for a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the value from `Request#hmac` [6](#0-5) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are parsed straight from caller-supplied headers with no cryptographic binding to the signed body at all [3](#0-2) .

`Registry.process` relies on exactly this unbound `request.shop` and `request.topic` to select the handler and populate `WebhookMetadata` delivered to app code [4](#0-3) . Compare this to the OAuth callback path, `Auth::Oauth::AuthQuery`, where `shop` is explicitly included as part of the signed `to_signable_string` payload [7](#0-6)  — i.e., the gem's own OAuth code demonstrates that `shop` is intended to be part of the authenticated binding, but the webhook `Request` class omits it.

Since `Context.api_secret_key` is a single app-level secret shared across every shop that installs the app (not shop-specific), a merchant/attacker who has legitimately installed the app on their own store receives valid `(raw_body, hmac)` pairs signed with that same shared secret. They can then send an HTTP POST to the app's webhook endpoint with the original valid `raw_body` and `hmac` header, but a forged `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` will succeed (it only checks the body), and the handler will be invoked believing the (attacker-controlled) payload originated from the victim tenant.

The broken identity binding, stated as an equality that should hold but does not:
`hmac_verified(raw_body)` should imply `shop_header == shop_that_produced(raw_body)`, but the gem only proves `hmac_verified(raw_body)` — the `shop` field is never part of what is verified.

### Impact Explanation
This breaks tenant isolation for any app built on this gem's webhook processing: an attacker-controlled shop can inject fabricated webhook events (with attacker-chosen body content) that are dispatched to the victim shop's context (`WebhookMetadata#shop`), because nothing prevents the attacker from choosing which shop the verified payload is attributed to. Depending on how the host app uses `data.shop` (e.g., looking up the corresponding offline session/access token by shop, updating shop-scoped records, or triggering privileged shop-scoped actions), this can result in cross-tenant data corruption, unauthorized actions performed under a victim shop's identity, or information disclosure — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires an attacker to install the target app on any shop they control (a normal, unprivileged action for a public/embedded Shopify app) and to capture one delivered webhook body plus its HMAC header for a topic of interest, then replay it with a forged `shop-domain` header. No access to `api_secret_key`, session tokens, or victim credentials is required — the attacker never needs anything beyond what Shopify sends them for their own store.

### Recommendation
Bind the `shop` (and ideally `topic`) values into the material verified by the HMAC in `Webhooks::Request#to_signable_string`, or otherwise cryptographically tie the `shop-domain` header to the verified payload (e.g., look up the expected shop via a separately-authenticated channel rather than trusting the header) before constructing `WebhookMetadata` in `Registry.process`. At minimum, document and encourage host apps to independently verify that `data.shop` corresponds to a shop with which the raw body content is plausible, rather than treating HMAC-validated body + unrelated header as a single trusted unit.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook delivery (e.g., `orders/create`) and capture the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` that Shopify computed using the app's shared `api_secret_key`.
3. Replay a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only covers `B`), but `x-shopify-shop-domain: victim.myshopify.com` and any desired `x-shopify-topic`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [8](#0-7) , which succeeds since it only checks `raw_body` against `H`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)` [9](#0-8) , causing the host application to process attacker-supplied content as if it were an authentic event from the victim shop.
