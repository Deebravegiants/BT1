### Title
Permissionless index-update cadence can permanently divert supplier yield to protocol revenue - (File: common/src/rates/index.rs)

### Summary
An unprivileged caller can repeatedly invoke `Controller::update_indexes` after each ledger timestamp advance. When the supplier reward for the elapsed interval is too small to increment `supply_index` by one raw RAY unit, `update_supply_index` returns the old index and `supply_index_reward_shortfall` reclassifies the entire supplier reward as protocol revenue. Repeating this pattern prevents suppliers from receiving accrued yield while still increasing borrower debt.

### Finding Description
`Controller::update_indexes` only requires caller authorization and forwards the request to the pool, so it is permissionless. [1](#0-0) [2](#0-1)  The pool’s owner-only `update_indexes` entrypoint loads each market and runs `interest::global_sync`, which advances `last_timestamp` even for very small elapsed intervals. [3](#0-2) [4](#0-3) 

Each accrual step calculates borrower interest and splits it into `supplier_rewards` and `protocol_fee`. [5](#0-4)  `update_supply_index` computes the new index using floor division over total supplied shares. [6](#0-5)  If the reward is below the amount needed to move the index by one raw unit, the index remains unchanged.

When that happens, `supply_index_reward_shortfall` measures zero distributed supplier value and returns the full `supplier_rewards` amount. [7](#0-6)  `accrue_step` adds that shortfall to the reserve-factor fee and converts the result into protocol revenue shares. [8](#0-7)  `global_sync` then writes the unchanged supply index and mints those revenue shares into both `revenue` and `supplied`. [9](#0-8) 

### Impact Explanation
Supplier yield that should increase `supply_index` is instead permanently booked as protocol revenue. The attacker can continue calling `update_indexes` on every timestamp advance, maintaining each interval’s supplier reward below the index-increment threshold and preventing the supply index from reflecting the earned yield.

This affects all suppliers in the selected market, not only small positions, because the vulnerable division is performed globally over `supplied`. Suppliers retain their principal shares, but the yield accrued during the attack is unavailable to them and becomes claimable protocol revenue.

### Likelihood Explanation
The attack requires only an authorized signature from an arbitrary attacker address and repeated calls to `update_indexes`; no position, capital, privileged role, or oracle manipulation is required. [10](#0-9)  The condition is market- and rate-dependent: it is easiest when the supplier reward between ledger updates is small relative to total supplied shares. Revenue shares minted by each suppressed step increase total `supplied`, which can make subsequent rewards even less likely to move the index.

### Recommendation
Do not convert unreflected supplier rewards directly into protocol revenue on each accrual boundary. Track the sub-quantum supplier remainder in a dedicated pending-supplier-reward field and fold it into the next accrual until it is large enough to increase `supply_index`. Alternatively, increase index precision enough that an attacker cannot practically force per-interval rewards below one index unit. Any fix should preserve conservation accounting without allowing caller-selected accrual cadence to redirect supplier rewards.

### Proof of Concept
The following is a minimal Soroban-style scenario demonstrating the mechanism:

```rust
// Setup:
// 1. Deploy controller, pool, and one market.
// 2. Supplier deposits assets.
// 3. Borrower creates nonzero debt so interest accrues.
// 4. `attacker` is an unrelated address.

let market = hub_asset(usdc_address);
let before = pool_state(market.clone());

for _ in 0..N {
    // Advance the ledger timestamp by the smallest representable interval
    // accepted by the test environment.
    advance_ledger_timestamp_minimally();

    // Permissionless controller call; attacker only signs the transaction.
    controller.update_indexes(
        attacker.clone(),
        vec![&env, market.clone()],
    );
}

let after = pool_state(market.clone());

// Each interval's supplier reward was below one raw supply-index unit.
assert_eq!(after.supply_index, before.supply_index);

// Borrowers were still charged through `borrow_index`, while the supplier
// allocation was reclassified through `supply_index_reward_shortfall`.
assert!(after.borrow_index > before.borrow_index);
assert!(after.revenue > before.revenue);

// A withdrawal after the attack pays the supplier shares at the unchanged
// supply index, so the redirected yield is not recoverable by suppliers.
```

The key condition is that each call’s `supplier_rewards` is insufficient for `update_supply_index` to produce `old_index + 1`; in that case the full supplier allocation becomes part of `protocol_reward`. [11](#0-10) [12](#0-11)

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
pub fn supply_index_reward_shortfall(
    env: &Env,
    supplied: Ray,
    old_index: Ray,
    new_index: Ray,
    rewards_increase: Ray,
) -> Ray {
    let distributed = supplied
        .mul(env, new_index)
        .checked_sub(env, supplied.mul(env, old_index));
    rewards_increase.checked_sub(env, distributed)
}
```
