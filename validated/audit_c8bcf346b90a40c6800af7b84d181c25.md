### Title
Tokens transferred directly to the pool or controller are permanently locked — no rescue path exists - ([File: contracts/pool/src/lib.rs](contracts/pool/src/lib.rs))

### Summary
The XOXNO Lending pool and controller accept arbitrary SAC token balances (including native XLM) via direct `transfer`, but neither contract exposes any entrypoint that can move tokens out except against the internal `cash` accounting book, which never counts unsolicited transfers. Any tokens donated directly to the pool or controller address are permanently unrecoverable — the Soroban analog of "payable functions with no way to retrieve the native token."

### Finding Description
The pool holds all market custody in a single token balance per asset, shared across hubs, and tracks obligations in a separate accounting book (`PoolStateRaw.cash`). Every outbound token movement goes through `Cache::transfer_out`, which is only invoked by owner-gated ops (`withdraw`, `borrow`, `repay` refund, `recapitalize` excess refund, `flash_loan`, `create_strategy`, `claim_revenue`), and each of those ops first debits the book via `debit_cash` / `require_reserves` (`contracts/pool/src/lib.rs`, `contracts/pool/src/cache/cash.rs`). `claim_revenue` pays only `min(cash, revenue)` where `revenue` is protocol-owned scaled supply shares — it cannot touch a balance surplus (`contracts/pool/src/lib.rs:243-252`).

Incoming tokens are always *measured*: `transfer_amount_measured` in `common/src/token.rs` computes `post - pre` balance delta, and only that measured amount is credited to `cash`. A direct `token::Client::transfer(user, pool, amount)` — an unprivileged action anyone can perform on any SAC, including the native XLM SAC — raises the pool's physical balance without crediting any book. The architecture documentation confirms this is deliberate: "direct donations do not automatically increase booked cash" (`docs/reference/architecture.md:57-61`).

Crucially, there is no rescue or sweep entrypoint anywhere in the in-scope code: `grep` for rescue/sweep/skim finds a `sweep_balance` only in `contracts/swap-aggregator` (out of scope), and the pool's full entrypoint list (`contracts/pool/src/lib.rs:99-252`) contains no owner or public function that can disburse unbooked balance. The controller likewise has no recovery function, and the DeFindex adapter "has no administrative rescue interface" (`docs/reference/architecture.md:52-53`). Unlike the Solidity original, there is no `selfdestruct`-style fallback and no owner withdrawal path either — upgrades via `upgrade()` (`contracts/pool/src/lib.rs:122-126`) are the only theoretical escape.

The same applies to the controller address: tokens pushed to it (e.g., a `flash_position` callback over-push beyond declared collaterals, or a mistaken direct transfer) sit as stray balance. Only declared `refund_assets` in a strategy get returned; anything else is stranded, as the integration test explicitly documents with "protected" donated baselines (`tests/integration/flows/flash_position.sh:354-372`).

### Impact Explanation
Permanent freezing of funds. Any user who mistakenly transfers tokens — most plausibly native XLM, since the protocol is XLM-denominated and SAC `transfer` to a contract address requires no opt-in — loses them irreversibly. The tokens join a physical balance that the book overstates relative to nothing; no legitimate flow ever draws the surplus down. The donation cannot be claimed by the sender, cannot be claimed as revenue (revenue is share-denominated, not balance-derived), and cannot be skimmed by anyone.

A secondary effect partially mitigates custody shortfalls elsewhere: a stray balance silently backs the book, so donations incidentally cover shortfalls like the unfunded-`recapitalize` scenario in `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` — but they are never credited to or recoverable by their sender.

### Likelihood Explanation
Medium-low. Exploitation is not required — this is an accidental-loss class, matching the original Medium finding. The trigger is a single ordinary SAC `transfer` to the pool or controller address, which any user can execute by mistake (wrong recipient, mistaken "top-up" attempt believing it supplies collateral, or an over-push from a `flash_position` callback sending more than the declared collateral minimums). Contract senders and UI bugs make this more than purely hypothetical. The loss is total and permanent once it occurs.

### Recommendation
Add a rescue path for unbooked balances. Options:

1. An owner-gated `sweep` / `rescue` on the pool restricted to `balance > cash`-surplus: compute `token.balance(pool) - cash` and allow the owner (controller/governance) to withdraw only the excess, so booked user funds can never be touched. Note this is only exact for single-hub assets; for a token shared across hubs the surplus is `balance - Σ cash over all its books`.
2. A controller-gated `sweep` for stray controller balances, plus an explicit return of any post-callback controller balance in `flash_position` for declared collateral assets.
3. At minimum, document the behavior prominently so integrators never attempt direct-transfer "top-ups" — `supply` is the only crediting path.

### Proof of Concept
Conceptual, runnable in the existing pool test harness (`contracts/pool/tests/flows.rs` style):

```rust
// 1. Deploy pool + create XLM market, supplier deposits normally (as in TestSetup).
// 2. Any unprivileged address donates XLM directly:
let donor = Address::generate(&env);
token_admin.mint(&donor, &1_000_000_000);
token::Client::new(&env, &xlm_sac).transfer(&donor, &pool_addr, &1_000_000_000);

// 3. Physical balance now exceeds every book:
assert_eq!(token.balance(&pool_addr), state.cash + 1_000_000_000);

// 4. Exhaustive check: no entrypoint recovers it.
//    - withdraw/borrow/claim_revenue all call debit_cash -> require_reserves
//      caps them at `cash`; the surplus is unreachable.
//    - supply/recapitalize only credit measured deltas of *new* transfers-in.
//    - flash_loan restores balance to pre+fee; the donation is untouched.
//    - No sweep/rescue entrypoint exists on LiquidityPoolInterface.
// 5. The donor's 1 XLM is permanently locked absent a WASM upgrade.
```

This mirrors the original finding exactly: accidental value transfer to the contract with no retrieval mechanism, only now it applies to every SAC asset, not just the native token.
