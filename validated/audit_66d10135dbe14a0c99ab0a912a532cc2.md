### Title
Market accrual overflows `i128` on large scaled balances, permanently freezing all market actions - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

The pool represents supply and debt as RAY-scaled shares that can approach `i128::MAX`, while interest indexes also grow as RAY values. Every accrual first computes `scaled_shares * index / RAY`; once either product exceeds the `i128` result domain, `scaled_to_original` raises `MathOverflow`. Because every market mutation and the permissionless `update_indexes` path performs this accrual before changing state, the market becomes permanently unusable.

### Finding Description

`accrue_step` converts the stored scaled `borrowed` and `supplied` totals back to values by calling `scaled_to_original` twice before it computes utilization or applies the borrow-index cap. [1](#0-0) 

`scaled_to_original` delegates to `Ray::mul`. [2](#0-1)  `Ray::mul` uses `mul_div_half_up`, which returns `None` when the exact result does not fit `i128` and then panics with `GenericError::MathOverflow`. [3](#0-2) [4](#0-3) 

The index cap does not prevent this state. `update_borrow_index` multiplies the old index by the interest factor and only then clamps the result to `MAX_BORROW_INDEX_RAY`; more importantly, the earlier value conversions can already overflow while the stored index is still below that cap. [5](#0-4)  The admitted token-input ceiling only guarantees that `amount * 10^(27-d)` fits initially; it does not guarantee that the resulting scaled balance remains representable after multiplication by an index greater than 1.0. [6](#0-5) 

An unprivileged caller can trigger the failed accrual through `Controller::update_indexes(caller, assets)`, which is permissionless apart from caller authorization. [7](#0-6)  The controller forwards the supplied `HubAssetKey` list to `pool.update_indexes`. [8](#0-7)  The pool then loads each market and calls `global_sync`. [9](#0-8) 

Once the multiplication overflows, `global_sync` aborts before `mark_accrued`, so `last_timestamp` is never advanced and every later attempt repeats the same overflowing calculation. [10](#0-9)  All normal pool legs use `synced_market`, which loads the market and calls `global_sync` before performing the requested operation. [11](#0-10) 

### Impact Explanation

This permanently freezes the affected `(hub_id, asset)` market. `supply`, `borrow`, `withdraw`, `repay`, liquidation-driven pool calls, flash paths, `update_indexes`, and other operations that use `synced_market` fail before their state transition. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot unwind risk, and protocol revenue cannot move through that market.

The underlying user funds are not directly stolen, but they become permanently inaccessible through the contract's normal interface absent an upgrade or governance intervention. This meets the permanent-freezing impact class.

### Likelihood Explanation

Likelihood depends on the market reaching an extreme scaled balance and then accruing enough index growth for `scaled * index / RAY` to exceed `i128`. Caps prevent an initial asset-to-RAY conversion overflow, but they do not bound the later share-value product: the maximum admitted input is approximately `i128::MAX / 10^(27-d)`, and any index above 1.0 increases the represented value. High utilization causes the borrow index to grow repeatedly, while the supply index can also grow as rewards are distributed.

The condition is not reachable from a single tiny transaction: it requires a very large market and sustained interest accrual. However, it can arise through ordinary permissionless `supply` and `borrow` usage within configured caps, and once it exists, any unprivileged address can invoke `update_indexes` or any market action to trigger it. There is no privileged action, malformed protocol parameter, leaked key, or external oracle assumption required.

### Recommendation

Avoid converting the full scaled market value into an unbounded `i128` result during accrual, or make the overflow non-fatal and preserve a recovery path:

- Compute utilization through a ratio that does not materialize `borrowed * borrow_index` and `supplied * supply_index` as separate `i128` values.
- Calculate accrued interest from `borrowed * (new_index - old_index) / RAY`, or use a saturating/wider domain for intermediate total values.
- Before multiplication, detect unrepresentable value growth and clamp the relevant index or derive a capped utilization without panicking.
- Add an escape path that can reduce `borrowed`/`supplied`, recapitalize, or freeze index accrual without first requiring the overflowing `scaled_to_original` calculation.
- Add a deployment-level invariant that maximum admitted shares times the configured index ceiling remains inside the intended value domain, or explicitly lower cap ceilings accordingly.

### Proof of Concept

The vulnerable path is:

1. A market accumulates a scaled balance `S` that initially fits `i128`, for example near `max_cap_for_decimals(d) * 10^(27-d)`.
2. Time elapses while `borrow_index > RAY` or `supply_index > RAY`, so `S * index / RAY > i128::MAX`.
3. Any unprivileged address calls:

```text
Controller::update_indexes(
    caller = attacker,
    assets = [HubAssetKey { hub_id, asset }]
)
```

4. `update_indexes` reaches `pool.update_indexes`, then `ops::market::accrue`, then `interest::global_sync`.
5. `global_sync` calls `accrue_step`.
6. `accrue_step` calls `scaled_to_original(env, borrowed, borrow_index)` or `scaled_to_original(env, supplied, supply_index)`.
7. `mul_div_half_up` cannot represent the quotient in `i128`, so it panics with `MathOverflow`.
8. The transaction aborts before `mark_accrued`; the stored timestamp and balances remain unchanged. The same overflow occurs on every subsequent `repay`, `withdraw`, `liquidate` pool leg, `borrow`, `supply`, or `update_indexes`, leaving the market permanently frozen.

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {

    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
