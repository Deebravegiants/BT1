## Title
Webhook shop-domain (and topic/webhook-id) headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, but `to_signable_string` returns only the raw body. `Utils::HmacValidator.validate` checks the HMAC against the body alone, so none of these header-derived fields are cryptographically bound to the signature that authenticates the webhook.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook only if `Utils::HmacValidator.validate(request)` passes: [1](#0-0) 

The HMAC check computes the signature over `verifiable_query.to_signable_string`, which for a webhook `Request` is defined as just the raw JSON body: [2](#0-1) 

But the `shop`, `topic`, and `webhook_id` values that are handed to the handler come from HTTP headers that are never part of the signed content: [3](#0-2) 

The identity binding broken here is: `HMAC-signed bytes (body only)` ≠ `bytes acted on (headers: shop-domain, topic, webhook-id)`. This is the same bug class as the reported issue (`_php_imap_mail`), where a value flowing into security-relevant logic was never validated by the check that was supposed to protect it — here the `shop` header is trusted by `handler.handle` while carrying zero cryptographic linkage to the HMAC that "authenticates" the request.

For contrast, the OAuth-callback analog in this same gem correctly binds `shop` into the signable content: [4](#0-3) 
This shows the gem's own pattern for correct binding, which the webhook `Request` class does not follow.

### Impact Explanation
An unprivileged internet user who can obtain any one genuine, HMAC-valid webhook body for a shop they control (e.g., by installing the target app on their own free/dev Shopify store and receiving a real webhook callback with a valid `x-shopify-hmac-sha256`) can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still succeed because it only checks the body against the secret, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain. Any app logic that persists or acts on shop-scoped state keyed by this `shop` value (common pattern per the docs: `ShopifyAPI::Webhooks::Registry.process` → app database update per shop) can be corrupted or manipulated for a shop the attacker does not own — a cross-tenant data-integrity/access violation.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on any Shopify store (including a free development store) to receive a legitimately-signed webhook, and (2) sending a crafted HTTP request to the app's public webhook endpoint with a modified shop header. No access token, `client_secret`, or privileged account is needed — both are within reach of any unprivileged internet user, consistent with the report rules.

### Recommendation
Bind the security-relevant header fields into the signed content that `HmacValidator` verifies, or independently verify that the `shop` header matches a shop actually entitled to send the given payload before dispatching to handlers (e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, mirroring `Auth::Oauth::AuthQuery`, or cross-check the resolved shop against session/registration state before invoking `handler.handle`).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they control) and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and its valid `x-shopify-hmac-sha256: H` header (computed by Shopify with the app's real `api_secret_key`, unknown to the attacker but still valid since Shopify sent it).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `B` and compares to `H` (per `lib/shopify_api/webhooks/request.rb:35-43` and `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
