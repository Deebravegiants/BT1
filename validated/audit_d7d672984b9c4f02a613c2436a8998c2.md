### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but the shop identity that is handed to the application's webhook handler is read from the `x-shopify-shop-domain` HTTP header, which is never included in the signed material. This breaks the identity binding `HMAC-authenticated bytes == raw_body` vs. `tenant identity delivered to handler == unauthenticated header value`, allowing any party who has obtained one genuinely-signed `(body, hmac)` pair (e.g. by installing the app on their own shop and triggering a webhook) to replay those exact bytes against the app's public webhook endpoint while substituting an arbitrary victim shop domain in the header, causing the app to process/act on the forged event as belonging to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

None of the Shopify headers — `shop-domain`, `topic`, `api-version`, `webhook-id` — are folded into the signed string. Yet `shop` is derived straight from the unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate`, which internally calls `validate_signature` against `verifiable_query.to_signable_string` (i.e. the raw body only), and then immediately constructs and dispatches `WebhookMetadata` using `request.shop` — the unauthenticated header value: [3](#0-2) [4](#0-3) 

Because the signature is keyed with the app's shared `client_secret` but only ever certifies the byte content of the body — never which shop it is "for" — the same signed body/HMAC pair is valid for any `shop-domain` header value. This is functionally identical to the report's underlying bug class: a value that is *acted upon* (here, the tenant used to route/act on webhook data) is not the value that was *covered by the cryptographic check* (here, HMAC over body bytes only).

### Impact Explanation
Any user who can get one legitimately Shopify-signed webhook delivered (e.g., by installing the app on their own shop and performing an action that triggers a webhook whose body doesn't inherently disclose/bind the shop, such as `products/update`, `orders/create`, etc.) can capture the `(raw_body, hmac)` pair and POST it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to any victim shop. `HmacValidator.validate` will accept it, and the app's registered handler will execute business logic (data mutation, deletion, GDPR compliance actions like `customers/redact`/`shop/redact`, subscription/billing state changes, etc.) attributing it to the victim tenant — a cross-tenant access/data-integrity break using only the credentials of an ordinary app installer.

### Likelihood Explanation
Exploitation requires the attacker to (1) install/use the target app on a shop they control (routine, unprivileged), (2) trigger at least one webhook delivery whose body content they can capture, and (3) send a crafted HTTP request with a spoofed `x-shopify-shop-domain` header to the app's webhook endpoint, which is a public URL. No possession of `api_secret_key`, access tokens, or any Shopify-side credential is required — only the ability to author raw HTTP requests, which is squarely within an "unprivileged internet user" capability.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise verify the header-derived shop is consistent with a value the app independently trusts (e.g., cross-check against the shop associated with the specific `webhook_id`/subscription, or require the shop domain to be embedded in and covered by an HMAC computed over `headers + body`, not just `body`). At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop`, `topic`, and `webhook_id` header values so the HMAC in `lib/shopify_api/utils/hmac_validator.rb` actually certifies which tenant/topic the payload is for.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and performs an action that fires a webhook (e.g., updates a product), causing Shopify to POST a signed webhook to the app's endpoint with headers including `x-shopify-hmac-sha256: <valid HMAC over BODY>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `BODY` and the valid `HMAC` (e.g., by controlling a proxy in front of their own self-hosted instance of the app, or via any means of observing the delivery to infrastructure they control).
3. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the identical `BODY` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `OpenSSL::HMAC.hexdigest(..., @raw_body)` — unaffected by the header change (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to perform the webhook's associated action against the victim's tenant data/state.
