### Title
HOT Bridge withdrawal status is misattributed when the queried transaction contains additional withdrawals injected via `signedIntents.before` - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

### Summary
`HotBridge.describeWithdrawal` resolves a withdrawal's on-chain nonce as `nonces[args.index]`, where `args.index` is computed by `createWithdrawalIdentifiers` purely from the position of the entry inside the caller-supplied `withdrawalParams[]` array. When the underlying NEAR transaction also contains HOT-route withdrawal intents that were smuggled in via `signedIntents.before` (an attacker/counterparty-supplied, atomically co-published `MultiPayload[]`), the nonce order returned by `parseWithdrawalNonces(tx.hash, tx.accountId)` is shifted relative to that local index, so the SDK looks up and reports the status/`txHash` of a *different* withdrawal than the one the caller asked about.

### Finding Description
The broken equality: the SDK assumes
`nonces[wid.index] == nonce of the wid.index-th HOT withdrawal that the caller specified in its own withdrawalParams[]`.

This equality only holds if `wid.index` (a purely local, per-`withdrawalParams` counter) matches the actual position of that withdrawal's `mt_withdraw`/nonce-emitting intent inside the single NEAR transaction that executed the whole atomic bundle.

Code path:
- `IntentExecuter.signAndSendIntent` composes `[...before, newPayload, ...after]` and publishes them **atomically in one call** to `intentRelayer.publishIntents` [1](#0-0) . All of `before`/`new`/`after` execute together inside a single NEAR transaction (that is the entire purpose of "atomic multi-intent publishing", per the README's "Include pre-signed intents ... to be published atomically") [2](#0-1) .
- `IntentsSDK.processWithdrawal` only tracks `intentTx` (obtained via `waitForIntentSettlement` for the caller's own ticket) together with the caller's own `withdrawalParams` — it has no visibility into what withdrawal intents may exist inside `signedIntents.before`/`.after` [3](#0-2) .
- `createWithdrawalIdentifiers` assigns `index` by counting occurrences **only within the caller's own `withdrawalParams[]`**, per bridge route, starting at 0 [4](#0-3) .
- `HotBridge.describeWithdrawal` then fetches `nonces = parseWithdrawalNonces(tx.hash, tx.accountId)` — the full, transaction-wide, in-order list of withdrawal nonces present in that NEAR tx (which includes any HOT-route withdrawals from `before`/`after`) — and indexes into it with the caller-local `args.index` [5](#0-4) .

Exploit flow:
1. A counterparty (attacker) supplies the integrator with a pre-signed HOT-bridge withdrawal `MultiPayload` (e.g. via a quote/settlement flow that ends up as `args.intent.signedIntents.before`).
2. The integrator calls `processWithdrawal({ withdrawalParams: [victimWithdrawal], intent: { signedIntents: { before: [attackerWithdrawalPayload] } } })`.
3. The composed NEAR transaction executes `attackerWithdrawalPayload` first, then the victim's payload. `parseWithdrawalNonces` therefore returns `[attackerNonce, victimNonce, ...]`.
4. `createWithdrawalIdentifiers`, knowing only about `[victimWithdrawal]`, assigns `index = 0` to the victim's withdrawal.
5. `describeWithdrawal` reads `nonces[0]` = `attackerNonce`, queries `getGaslessWithdrawStatus(attackerNonce)` / the bridge indexer for that nonce, and returns the **attacker's** withdrawal `(status, txHash)` labeled as the result for the victim's withdrawal.
6. The integrator, trusting the SDK's per-index `(status, txHash)` pairing, may mark the victim's withdrawal "completed" using a `txHash` that has nothing to do with the victim's destination/amount, while the victim's real withdrawal nonce is never polled (the integrator only asked for index 0). This can cause the integrator to credit/settle based on a phantom completion, or refund the "stuck" real withdrawal separately — a double payout condition.

No existing guard prevents this: `validateWithdrawal`, `compareAddresses`, `FeeExceedsAmountError`, and the intents contract's own nonce/signature checks all validate that each *individual* signed intent is well-formed and correctly signed — none of them re-derive or cross-check the caller-local `index` against the true position of the withdrawal inside the composed transaction.

### Impact Explanation
The SDK reports a `(status, txHash)` pair for withdrawal index *i* that in fact belongs to a different withdrawal (the attacker's, injected via `signedIntents.before`). This is a status/hash misreport: an integrator that trusts the returned status to credit a user, release custody, or decide refund-vs-settle can act on wrong information — matching the "High: a status or hash misreport making an integrator credit or refund twice" category. It is fully repeatable per call to `processWithdrawal`/`waitForWithdrawalCompletion` whenever `signedIntents.before` (or `.after`, for later indices) contains HOT-route withdrawal intents.

### Likelihood Explanation
Preconditions: the integrator must use the documented `signedIntents` composition feature and forward externally-supplied `before`/`after` payloads (explicitly listed as attacker-controlled input in the prompt's threat model) together with a HOT-bridge-routed withdrawal. The attacker only needs to produce a validly signed HOT-bridge withdrawal MultiPayload for their own funds — trivial and free for anyone with funds in the intents contract. No privileged access, no relayer/indexer compromise required.

### Recommendation
Compute `WithdrawalIdentifier.index` from the withdrawal's **true position** within the fully composed transaction (i.e., account for the number of same-route withdrawal-emitting intents present in `signedIntents.before`) rather than purely from the caller's local `withdrawalParams[]` order; alternatively, have `HotBridge.describeWithdrawal` match nonces by a value derived from the specific signed intent (e.g. embed/derive the nonce from the withdrawal's own `mt_withdraw` intent instead of positional indexing into the whole tx's nonce list).

### Proof of Concept
```ts
// vitest, mocking only the HOT SDK / bridge-indexer HTTP layer
it("misattributes withdrawal status when before-signedIntents inject an extra HOT withdrawal", async () => {
  const tx = { hash: "0xNEARTX", accountId: "intents.near" };

  const hotSdk = {
    near: {
      parseWithdrawalNonces: vi.fn().mockResolvedValue([111n, 222n]), // [attackerNonce, victimNonce]
    },
    getGaslessWithdrawStatus: vi.fn(async (nonce: string) =>
      nonce === "111" ? "attacker-status" : "victim-status",
    ),
    api: { requestApi: vi.fn() },
  };

  const bridge = new HotBridge({ envConfig, hotSdk });

  // Victim's withdrawalParams array only contains the victim's own withdrawal
  const { wid } = (
    await createWithdrawalIdentifiers({
      bridges: [bridge],
      withdrawalParams: [victimWithdrawalParams],
      intentTx: tx,
    })
  )[0]!;

  expect(wid.index).toBe(0); // local index, unaware of attacker's prepended withdrawal

  await bridge.describeWithdrawal({ ...wid, tx });

  // BUG: fetches nonce belonging to the attacker's withdrawal (index 0 in the tx),
  // not the victim's real nonce (222n, at tx-position 1)
  expect(hotSdk.getGaslessWithdrawStatus).toHaveBeenCalledWith("111");
  // Expected (broken) equality: nonces[wid.index] should equal victimNonce (222n), but equals 111n instead.
});
```

### Atomic Multi-Intent Publishing

Include pre-signed intents (from other users or prior operations) to be published atomically with your new intent. 
Useful for multi-user coordination and batch operations.

```typescript
import type { MultiPayload } from '@defuse-protocol/intents-sdk';

// Include pre-signed intents before/after your new intent
await sdk.signAndSendIntent({
    intents: [{ intent: "transfer", receiver_id: "alice.near", tokens: {...} }],
    signedIntents: {
        before: [preSigned1],  // Execute before new intent
        after: [preSigned2]    // Execute after new intent
    }
});

// Also works with withdrawals
await sdk.processWithdrawal({
    withdrawalParams: {...},
    intent: {
        signedIntents: {
            before: [preSigned1],
            after: [preSigned2]
        }
    }
});
```

**Key Points:**
- All intents execute atomically in order: `before` → new intent → `after`
- Returned `intentHash` is for your newly created intent, not the included ones

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
