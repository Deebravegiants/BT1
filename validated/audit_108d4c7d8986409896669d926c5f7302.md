### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant shop spoofing via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while the `shop` value delivered to the app's webhook handler is read from an unsigned HTTP header. This breaks the binding: `shop reported to handler == shop cryptographically authenticated`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop`, however, is taken directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` only — it never inspects or binds the `shop` header: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once `HmacValidator.validate(request)` passes, and then forwards `request.shop` — the unauthenticated header value — straight into `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle`: [4](#0-3) [5](#0-4) 

Because the HMAC only covers `@raw_body`, the equality that should hold — `shop bound by HMAC == shop the handler acts on` — does not. Any party who can obtain one authentic webhook delivery (e.g., an unprivileged user who installs the app on their own store and receives their own legitimate webhooks, or anyone who can capture a webhook body since bodies are frequently non-secret/log-observable) can replay that exact `raw_body` + valid `hmac` pair while substituting a different value in the `shopify-shop-domain` header. `HmacValidator.validate` will still succeed because it only recomputes the signature over the untouched body, and `Registry.process` will deliver a `WebhookMetadata` claiming to be from an arbitrary victim shop the attacker never owned.

### Impact Explanation
This is a cross-tenant identity confusion: the gem asserts to the host application "this webhook, with this body, is from shop X" when in fact only the body — not the shop identity — was authenticated. Host applications commonly key persistence, session/token lookups, and business logic in `WebhookHandler#handle` off `WebhookMetadata#shop` (this is the intended and documented purpose of that field). An attacker can leverage this gap to make the app process (and potentially store, delete, or act on) data under a victim shop's identity, or to trigger the mandatory redact/data-request handlers with a forged `shop`, all without ever possessing `Context.api_secret_key` or any victim credentials. This matches the "Critical - cross-tenant access" impact bar since the trust boundary between tenants (shops) is what's broken.

### Likelihood Explanation
The attacker only needs to have received (or observed) one legitimate webhook body+HMAC pair for a topic they can trigger from their own store (webhook bodies are not inherently secret and payload replays are trivial once captured), then re-POST it to the app's webhook endpoint with a rewritten `shopify-shop-domain` header. No knowledge of `api_secret_key` or any access token is required, satisfying the "unprivileged internet user" constraint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the signable material, or otherwise cryptographically bind the `shop` value to the HMAC verification step — e.g., verify HMAC over a canonical string combining `raw_body` and the shop header, or have `HmacValidator`/`Webhooks::Registry.process` reject requests where these header-derived identity fields are not independently authenticated. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must not be trusted by host applications without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) to their own registered endpoint, capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify using the app's real `api_secret_key`, which the attacker never sees but doesn't need to).
2. Attacker re-sends an HTTP POST to the same webhook endpoint with:
   - body = `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256` = `H` (unchanged)
   - header `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com` (changed)
3. `Webhooks::Request.new` parses this into a request object; `Utils::HmacValidator.validate` recomputes the HMAC solely over `B`, which matches `H`, so validation succeeds: [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"`, and the app's `WebhookHandler#handle` executes business logic believing the event legitimately originated from the victim shop.
