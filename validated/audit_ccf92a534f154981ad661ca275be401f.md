## Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching webhook data to the app's handler [1](#0-0) . In reality, the HMAC computed by `Utils::HmacValidator` only covers the raw request body; the `shop`, `topic`, `webhook_id`, and `api_version` values — all taken directly from unauthenticated HTTP headers — are never part of the signed material and are handed to the handler as if they were verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop`, `topic`, `webhook_id` and `api_version` accessors instead read directly from client-supplied headers with no relation to the signed payload: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC solely over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [4](#0-3) 

`Registry.process` performs exactly this HMAC check and then immediately builds `WebhookMetadata` using the *unverified* `request.shop`, `request.topic`, etc., handing them to the application's handler as trusted identity fields: [5](#0-4) 

The binding that is broken: the app's documented contract is `hmac_valid(request) == request_came_from_shop(request.shop)`, i.e., "shop attributed to this webhook" should be authenticated together with the body. In truth, the HMAC only proves `hmac_valid(request) == body_untampered(request.raw_body)` — the `shop` header is never bound to that signature. Since a given app's `api_secret_key` is shared across every shop that installs it (it is not per-shop), any merchant who installs the app can obtain validly-HMAC'd webhook bodies for their own shop and then replay that exact body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header for an arbitrary victim shop domain. The signature still validates because it never covered the header, and `Registry.process` dispatches to the handler claiming the forged victim shop.

### Impact Explanation
This is a cross-tenant integrity violation: an unprivileged internet user who merely has (or creates) their own installation of the target app can forge webhook deliveries "from" any other shop that also uses the app, because the identity used by app-side handlers (`data.shop`) is not covered by the cryptographic proof the gem performs and advertises ("verify the request did indeed come from Shopify"). Depending on how the host app keys sessions/storage off `data.shop` (which is exactly what the gem's own documentation and example handler recommend — `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this can be used to inject, delete, or otherwise mutate data attributed to a shop the attacker does not own/operate, i.e., cross-tenant access, satisfying the "Critical - cross-tenant access" impact bar. It does not require the app's `client_secret` or any privileged credential — only an ordinary merchant/dev-store account able to install the app and receive its own legitimately-signed webhook bodies.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented pattern of trusting `WebhookMetadata#shop`/`#topic` for tenant identification, since that is exactly what the library's own usage docs and sample handler recommend [6](#0-5) . No secret material, TLS interception, or special privileges are needed — only the ability to install the app on an attacker-controlled shop (or capture one legitimate webhook body) and issue a crafted HTTP request with a different `shop` header.

### Recommendation
Include the identity-binding headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material used by `VerifiableQuery#to_signable_string`, or otherwise cryptographically bind them to the body before exposing them via `WebhookMetadata`. At minimum, the documentation should stop asserting that `process` "verifies the request did indeed come from Shopify" when only the body — not the shop/topic attribution — is actually authenticated, and should instruct implementers to independently validate that `data.shop` corresponds to a shop with an active, registered webhook subscription/session before trusting it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`, and body `B`.
3. Attacker captures this exact request, then re-sends it to the app's public webhook endpoint, keeping the body `B` and the (still-valid) `hmac-sha256` header unchanged, but replacing the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only re-computes the signature over `raw_body` (`B`), which is untouched. [2](#0-1) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)`, even though the payload actually originated from, and was signed for, the attacker's own shop. [5](#0-4)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
