## Title
Webhook HMAC verification does not bind the `shop-domain` header, allowing cross-tenant shop spoofing on webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` (and `topic`) header from the HMAC-signed content. `Registry.process` validates the HMAC solely against this body-only signable string, then dispatches the webhook to the registered handler using `request.shop`, a value taken straight from an HTTP header that was never part of the cryptographic proof. This breaks the intended binding: `shop authenticated by HMAC == shop used for tenant dispatch`.

### Finding Description
`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, Context.api_secret_key)`. [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only `@raw_body`: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors, however, are all read directly from HTTP headers with no cryptographic tie to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches using `request.shop` (and `request.topic`) taken from these unauthenticated headers: [4](#0-3) 

Because `Context.api_secret_key` is a single value shared by the app across every merchant shop that installs it (it is not per-shop), the HMAC computed from `(raw_body, api_secret_key)` is identical no matter which shop originated the webhook. An attacker who legitimately installs the same app on their own shop will receive genuine webhooks with a valid HMAC for that body. Nothing in the signed content prevents the attacker from replaying that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body and its HMAC are self-consistent), and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` field is the attacker-chosen victim domain.

This is the "field acted on but not covered by the HMAC" class of bug: the equality `hmac_signed_shop == dispatch_shop` never holds because `shop` is not part of `to_signable_string` at all.

### Impact Explanation
This directly enables cross-tenant confusion in host applications built on this gem's documented `Registry.process` API: any code path that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (e.g., updating a shop record, honoring `shop/redact` or `customers/redact` GDPR requests, syncing orders/products) can be made to act on/against a shop the attacker does not control, using data the attacker fully crafts (their own installed shop's webhook payload) but attributes to the victim. This falls into the Critical "cross-tenant access" category, since the identity boundary between shops is broken using only the ability to install the app on one's own store and replay HTTP requests.

### Likelihood Explanation
Likelihood is high for any consumer of this gem's webhook processing helper: no special privilege beyond installing the app (a normal unprivileged action available to any merchant) is required, and the header can be freely set on an HTTP POST to the app's own publicly reachable webhook endpoint. No secrets need to be known or brute-forced; the same shared `api_secret_key` signs webhooks for all shops by Shopify's own design, so a valid `(body, hmac)` pair from the attacker's own store is reusable verbatim.

### Recommendation
Include the shop-identifying header (and ideally `topic`) as part of the signed content that is checked, or independently bind the header value to a value already established for that shop (e.g., verify the `shop` header corresponds to a shop with a known/stored session before trusting it), rather than relying on `raw_body`-only HMAC validation. At minimum, document and/or enforce in `Registry.process` that callers must cross-check `request.shop` against an already-authenticated session/store, since the HMAC does not vouch for it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)` and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` — this still equals `H` because `to_signable_string` never included the shop header — so validation passes.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as though it originated from the victim shop. [4](#0-3)
