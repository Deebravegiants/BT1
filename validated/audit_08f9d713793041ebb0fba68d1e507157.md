### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC solely against that raw body before passing `request.shop` (read from the unsigned `x-shopify-shop-domain`/`shopify-shop-domain` header) to the application's webhook handler as the tenant identifier. The shop field that the handler relies on for tenant scoping breaks the equality: `bytes verified by HMAC` == `bytes acted on as the shop identity`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
This means the HMAC computed in `HmacValidator.validate_signature` only signs `@raw_body`: [2](#0-1) 
The `shop`, `topic`, and `webhook_id` values are all read directly from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 
`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant for the handler call: [4](#0-3) 

Because the app's `api_secret_key` (the HMAC secret) is shared across every shop that has installed the app — not scoped per-shop — any unprivileged merchant who installs the app on their own store legitimately receives Shopify-signed `(raw_body, hmac)` pairs for their own shop's webhooks. Since the shop identity is not part of the signed content, that same attacker can replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass (it only checks the body against the shared secret), and `Registry.process` will invoke the handler with `WebhookMetadata` bearing the victim's `shop` value, breaking the binding `authenticated shop == shop the handler acts on`.

### Impact Explanation
This is a cross-tenant data/action confusion vector: the host application's webhook handler (which typically looks up the shop's session/access token, updates shop-scoped state, or triggers install/uninstall side effects) is invoked with an attacker-chosen `shop` value while only the attacker's own legitimately-signed payload content is verified. Depending on the handler logic, this can lead to actions performed against a victim shop's tenant record (e.g., marking a victim shop as uninstalled via a replayed `app/uninstalled` webhook body, or writing attacker-controlled order/product data under the victim shop's key) — a cross-tenant access breach that meets the Critical impact bar in this assessment's rules.

### Likelihood Explanation
Exploitation only requires being any ordinary merchant who installs the target app (an unprivileged internet user action) to legitimately receive at least one valid `(raw_body, hmac)` webhook pair signed with the app's shared secret, then a simple HTTP replay with a different `shop-domain` header value against the app's public webhook endpoint. No access to the `client_secret`, access tokens, or any privileged account is required — likelihood is high for any app that uses `ShopifyAPI::Webhooks::Registry.process` and trusts `WebhookMetadata#shop` for tenant-scoped logic.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signable content, or otherwise cryptographically bind the shop identity to the payload before passing it to `HmacValidator.validate`/`to_signable_string`, so a valid signature for one shop's payload cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, causing the app to configure webhooks with the shared `api_secret_key`.
2. Shopify delivers a legitimate webhook to the attacker (e.g. `app/uninstalled`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker resends the identical request to the app's webhook endpoint, only replacing the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds a request whose `to_signable_string` is still `B`; `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and it still equals `H`, so validation passes.
5. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to act on the victim shop's tenant using attacker-controlled webhook content.
