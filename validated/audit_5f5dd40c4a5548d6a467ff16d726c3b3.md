### Title
SSRF exfiltrating the app's `client_secret` via unvalidated `shop` in `Oauth.begin_auth` / `Oauth.validate_auth_callback` - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` build the request host directly from the caller-supplied/query `shop` value without ever routing it through `Utils::ShopValidator.sanitize!`, unlike every sibling OAuth flow in this gem (`ClientCredentials`, `RefreshToken`, `TokenExchange`) which explicitly validate `shop` against `TRUSTED_SHOPIFY_DOMAINS` before using it to build the request host.

### Finding Description
The equality that should be enforced everywhere the gem sends the app's `client_secret` in an HTTP request is:

`host actually receiving the client_secret == a domain in Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`

`Utils::ShopValidator.sanitize!` exists precisely to enforce this and is used before every other credential-bearing request: [1](#0-0) [2](#0-1) [3](#0-2) 

However, `lib/shopify_api/auth/oauth.rb` never calls `ShopValidator` at all:
- `begin_auth` takes `shop:` directly from the caller (in real usage, an unauthenticated request parameter, e.g. a `login` route reading `request.headers["Shop"]` as shown in `docs/usage/oauth.md:181-185`) and feeds it straight into `auth_base_uri(shop)`: [4](#0-3) 
- `validate_auth_callback` takes `auth_query.shop` and builds `null_session = Auth::Session.new(shop: auth_query.shop)`, then constructs an `HttpClient` around it that POSTs the app's `client_id`/`client_secret` to `"https://#{session.shop}/admin/oauth/access_token"`: [5](#0-4) 

`HttpClient` derives the request host straight from `session.shop` with no domain allow‑list check: [6](#0-5) 

`auth_query.shop` is only integrity-protected by HMAC (i.e., it can't be *tampered with in transit* once Shopify signs the callback), but nothing in this gem verifies it is actually a `*.myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` host before it is used to choose where the `client_secret` is sent: [7](#0-6) [8](#0-7) 

The broken binding is: `host receiving client_secret == HMAC-covered shop field`, instead of the equality that all other flows enforce: `host receiving client_secret == Utils::ShopValidator.sanitize!(shop)`. HMAC coverage guarantees the `shop` value wasn't altered after signing, but says nothing about whether that value is a legitimate Shopify domain — the trust anchor (`ShopValidator::TRUSTED_SHOPIFY_DOMAINS`) is completely bypassed in this file.

### Impact Explanation
If any code path allows the `shop` value used in these two methods to end up being a non-Shopify host — e.g., a host application forwarding an unvalidated `shop` query/header straight into `begin_auth` (a documented usage pattern in `docs/usage/oauth.md`), or any deviation in how the callback's `shop`/`hmac` pair is produced/verified — the app's `client_id` and `client_secret` (`Context.api_secret_key`) are sent via HTTP POST to that attacker-influenced host. This matches the Critical impact category: "theft or exfiltration of ... the app's `client_secret`" via SSRF carrying the app's credentials. This is exactly the class of defense-in-depth check the gem's own author implemented for `ClientCredentials`, `RefreshToken`, and `TokenExchange`, but conspicuously omitted for the primary `Oauth` authorization-code flow.

### Likelihood Explanation
Medium. In the canonical Shopify OAuth flow, Shopify itself computes the HMAC over the exact `shop` value it place in the redirect, so a legitimate callback should always carry a genuine myshopify domain. The risk surfaces because: (1) `begin_auth`'s `shop` parameter is taken from application code before any HMAC exists (the docs literally show reading it from a request header), so there is no cryptographic protection at all for that call, and (2) `validate_auth_callback` never independently confirms `shop` resolves to a trusted domain, so it relies entirely on correct HMAC secret custody and leaves no defense-in-depth if that assumption is ever violated (e.g., stale/rotated secret confusion, or a host application that constructs its own `AuthQuery` from data not actually sourced from Shopify's redirect, which the API surface explicitly allows since `AuthQuery.new` takes arbitrary strings).

### Recommendation
Apply `Utils::ShopValidator.sanitize!` to `shop` in both `Oauth.begin_auth` and `Oauth.validate_auth_callback`, mirroring the pattern already used in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`, before constructing `auth_base_uri`/`Auth::Session`/`HttpClient`. This ensures the host that ultimately receives the `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, independent of the HMAC check.

### Proof of Concept
1. A host application implements the login route as documented, passing an unauthenticated, attacker-supplied `shop` value (e.g. `request.headers["Shop"]`, or a query param) directly to `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. Because `begin_auth` never calls `Utils::ShopValidator.sanitize!`, an attacker sets `shop = "attacker.example"`.
3. Later, if the host application (or a compromised/misconfigured integration) constructs `ShopifyAPI::Auth::Oauth::AuthQuery` from data whose `shop` field is not strictly re-derived from a value already verified to be a trusted domain, `validate_auth_callback` will build `null_session = Auth::Session.new(shop: "attacker.example")` and `Clients::HttpClient` will POST `{client_id, client_secret, code}` to `https://attacker.example/admin/oauth/access_token`, handing the attacker the app's `client_secret`.

Note: full exploitability of step 3 as a fully unauthenticated end-to-end attack in the standard flow depends on how the host application sources the callback's `shop`/`hmac` pair, which is outside this gem — I could not fully verify a concrete unauthenticated trigger path within `lib/shopify_api/**` alone beyond confirming the missing `ShopValidator` check that every analogous method in this codebase applies.
