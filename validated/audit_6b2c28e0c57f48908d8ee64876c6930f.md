### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`, `topic`, and `webhook-id` headers from the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` then trusts `request.shop` and `request.topic` — which are read straight from unauthenticated headers — to route the webhook to a handler and to populate `WebhookMetadata#shop`, the field host applications use to identify which tenant's data an incoming webhook applies to. This breaks the intended identity binding: `hmac_valid(raw_body) == true` is treated as proof of `shop_header == originating_shop`, but the signature never covers `shop_header`.

### Finding Description
`to_signable_string` in [1](#0-0)  returns `@raw_body` only. `HmacValidator.validate` computes the HMAC exclusively over this signable string using the app's single, shop-agnostic `api_secret_key` [2](#0-1) .

`Registry.process` then does:
```
raise ... unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [3](#0-2) 

`request.shop` and `request.topic` are read directly from the `shopify-shop-domain` and `shopify-topic` headers [4](#0-3) , none of which are included in `to_signable_string`. Because a single Shopify app uses **one** `api_secret_key` shared across every shop that installs it, any shop that installs the app (including a free/attacker-owned development store — no special privilege required) will receive webhooks whose bodies are validly HMAC-signed with that same shared secret. An attacker who owns such a shop can capture a `(raw_body, hmac)` pair from their own legitimate webhook deliveries, then replay that exact body+signature to the target app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain (and/or the `shopify-topic` header to select an arbitrary registered handler). `HmacValidator.validate` still succeeds because the signature only ever attested to the body, not to the shop or topic headers.

### Impact Explanation
This is a cross-tenant confusion vulnerability: the HMAC check the gem performs establishes only "this body was signed by our app's secret," not "this event originated from shop X." Any host application that relies on `WebhookMetadata#shop` (or `#topic`) as an authenticated tenant identifier — which is exactly what the gem's own API contract implies once `Registry.process` has not raised `InvalidWebhookError` — can be made to process attacker-controlled webhook bodies under a spoofed shop identity and/or through an arbitrary registered handler. Depending on what the handler does with the data (e.g., writing order/customer/product state keyed by `shop`), this can lead to cross-tenant data corruption or forged events attributed to a shop the attacker doesn't control. This matches the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop they control (a normal, unprivileged action available to any Shopify developer/merchant) and that the app's webhook endpoint be reachable over the internet — both of which are the default deployment model for Shopify apps, since Shopify's own guidance treats body HMAC validation as the sole authentication mechanism for webhook endpoints (no mutual TLS or IP allow-listing is enforced by this gem). No access token, `client_secret`, or privileged credential is needed; the attacker's own webhook traffic supplies a validly-signed body they can then relay with altered identity headers.

### Recommendation
Include the `shop-domain` and `topic` (and ideally `webhook-id`) headers in the value that is HMAC-verified, e.g. by binding them into `to_signable_string` or by validating them against a canonicalized form Shopify would produce, so that the signature attests to the identity fields the application relies on, not just the body bytes.

### Proof of Concept
1. Register the target app on an attacker-owned/free development store; trigger any subscribed event (e.g. `orders/create`) so Shopify delivers a webhook to the app's endpoint, giving the attacker a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's real `api_secret_key`.
2. Replay that exact body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and, optionally, `X-Shopify-Topic` to a different registered topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)` [5](#0-4) , which succeeds because it only checks the raw body against the shared secret.
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: <attacker-controlled>)` [6](#0-5) , and the host application processes attacker-controlled data as if it originated from the victim shop.
