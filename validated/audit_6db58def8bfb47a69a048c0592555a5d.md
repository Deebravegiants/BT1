### Title
Blacklisted beneficiary permanently freezes an entire multi-token order escrow in IntentGatewayV2 - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` atomically transfers *every* escrowed input token of an order to a single `beneficiary` in one loop. If any one of those tokens is a blacklist-capable stablecoin (e.g. USDC) and the beneficiary address is (or becomes) blacklisted, the `IERC20.safeTransfer` for that single asset reverts, which reverts the whole `_withdraw` call — and therefore all other, unrelated escrowed tokens in the same order that would otherwise have transferred successfully. Because the beneficiary in a `WithdrawalRequest` is fixed at fill/cancel time and cannot be changed on retry, this is not a transient failure — the order's escrow becomes permanently stuck.

### Finding Description
`_withdraw` loops over all `body.tokens` and unconditionally calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one, only finalizing (`_filled[commitment] = beneficiary`) and releasing fees at the end: [1](#0-0) 

This function is reached from two unprivileged, permissionless flows:

1. **Cross-chain fill settlement (`RedeemEscrow`)** — after a solver fills an order on the destination chain, `onAccept` on the source chain decodes the `WithdrawalRequest` and calls `_withdraw(body, false, true)`, sending escrow to the solver's address: [2](#0-1) 

2. **Cancellation / refund (`RefundEscrow` / GET-response path)** — when a user cancels an unfilled order, `_cancelFromDest`/`_cancelFromSource` dispatch a refund to `order.user`, and `onGetResponse` calls `_withdraw(body, true, true)` with `order.user` as beneficiary: [3](#0-2) [4](#0-3) 

An order's `inputs` array can contain multiple different ERC20 tokens escrowed together under one `commitment` (e.g. USDC + DAI). If the `user` (refund path) or `solver` (redeem path) address is blacklisted on just one of those tokens (USDC), `safeTransfer` for that token reverts inside the shared loop, reverting the entire `_withdraw` call, including the transfers of the *other*, non-blacklisted tokens in the same order, and the release of accrued Hyperbridge transaction fees.

Unlike the top-level `EvmHost.dispatchIncoming` mechanism, which catches a failing `onAccept` call and deletes the request receipt so the message stays retryable by another relayer, this "retryability" does not help here: the beneficiary encoded in the `WithdrawalRequest` is fixed by the order/fill parameters and cannot be substituted on retry. Every subsequent redelivery attempt will fail identically, so the escrow (all input tokens of that order, not just the blacklisted asset) is permanently frozen. There is no admin/dust-sweep path in `IntentsBase`/`ExtrinsicIntents` that can rescue tokens already `escrow`ed under a specific commitment once this deadlock occurs — `SweepDust` only operates on protocol dust, not `_orders[commitment][token]` balances.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by an ordinary unprivileged transaction flow (placing/filling/cancelling an intent order) without any special privilege. A single blacklisted beneficiary address — whether the user is later sanctioned/blacklisted by USDC's admin, or a solver knowingly/unknowingly uses an address that gets blacklisted — bricks the entire multi-asset escrow for that order permanently, not merely the blacklisted asset. Given IntentGatewayV2 explicitly supports composing arbitrary ERC20 tokens (including stablecoins like USDC per the SDK/test fixtures) as both inputs and outputs, this is a realistic, protocol-level design flaw rather than a token-specific edge case. This meets the "permanent freezing of funds" bar for Medium/High severity.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) a legitimate user/solver address later being added to a token's blacklist (has historically happened to 200+ USDC addresses, including addresses unrelated to the order at hand), or (b) an order being crafted such that the beneficiary happens to already be blacklisted. Because orders bundling stablecoins with other assets are an intended usage pattern of IntentGatewayV2 (confirmed by fee-on-transfer/USDC test fixtures in the test suite), the precondition is not exotic, and no on-chain actor needs elevated privileges to trigger it — the freeze occurs automatically as soon as the blacklist status exists at delivery time.

### Recommendation
Avoid all-or-nothing atomic transfers across heterogeneous tokens for a single beneficiary in `_withdraw`. Options:
- Wrap each token's transfer in a try/catch (or use low-level `call`) so a revert on one asset does not block release of the others; accumulate any failed transfers into a per-token, per-beneficiary "pending withdrawal" balance that can be claimed later (e.g., by redirecting to an alternate address) instead of reverting the whole batch.
- Alternatively, split `_withdraw` per-token so each transfer is dispatched/finalized independently, allowing partial settlement even if one asset's transfer is blocked.
- Provide a governance or user-initiated recovery path allowing the beneficiary (or order owner) to redirect a specific stuck token's escrow to an alternate, non-blacklisted address once a transfer has failed.

### Proof of Concept
1. User places a cross-chain order with `inputs = [USDC: 1000, DAI: 1000]`, `output` on chain B.
2. Solver fills the order on chain B; `_fillCrossChain` dispatches a `RedeemEscrow` `WithdrawalRequest{beneficiary: solver, tokens: [USDC, DAI]}` back to chain A.
3. Before delivery, `solver`'s address is added to USDC's blacklist (e.g. flagged by USDC's admin for unrelated reasons, or the solver deliberately fills using a soon-to-be-sanctioned address to grief the protocol/user).
4. On chain A, `onAccept` decodes the request and calls `_withdraw`. The loop reaches `IERC20(USDC).safeTransfer(solver, 1000)`, which reverts because `solver` is blacklisted.
5. The whole `_withdraw` call reverts — the DAI transfer (which would have succeeded) never executes, `_filled[commitment]` is never finalized, and the transaction fees held for this order are never released.
6. `EvmHost.dispatchIncoming` catches the revert and deletes the receipt so the message is technically "retryable" ( [5](#0-4) ), but every retry uses the same fixed `beneficiary = solver`, so the transfer always fails — the DAI and USDC escrow, and the accrued fee, are permanently locked in the IntentGatewayV2 contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
