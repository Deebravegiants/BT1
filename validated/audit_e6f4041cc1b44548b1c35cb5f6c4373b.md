### Title
Excess native ETH sent to `dispatch()`/`fundRequest()` is permanently lost, never refunded to caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all forward the entire `msg.value` to `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)` to buy an *exact* amount of fee token, but none of them capture or forward back any ETH refund the swap produces. Any ETH sent above what is strictly required for the fee-token swap is not returned to the caller.

### Finding Description
In all three payable dispatch/fund paths, the pattern is identical: [1](#0-0) [2](#0-1) [3](#0-2) 

Standard `UniswapV2Router02.swapETHForExactTokens` only spends as much ETH as needed to produce `post.fee`/`get.fee`/`amount` fee-tokens and refunds the unused ETH — but that refund goes to `msg.sender` of the router call, which is `EvmHost` itself, not the original caller (`_msgSender()`) who supplied the `msg.value`. `EvmHost` discards the router's `amounts` return value entirely and never sweeps or forwards this refunded ETH back to the user. The excess simply accumulates in the Host contract with no accounting or withdrawal path tied to the original payer.

This differs from the pattern already correctly implemented elsewhere in the same codebase — e.g. `IntentGatewayV2._placeOrder`/`ExtrinsicIntents._fillCrossChain` explicitly track `msgValue -= amounts[0]` and refund the remainder via `_sendValue(msg.sender, msgValue)`: [4](#0-3) 

and the custom AMM wrappers (`UniV4UniswapV2Wrapper.swapETHForExactTokens`) explicitly compute and refund `refundETH`: [5](#0-4) 

`EvmHost` itself has no such refund logic for its own `dispatch`/`fundRequest` calls, so any caller that overestimates the native ETH needed to cover `post.fee`/`get.fee`/`amount` permanently loses the difference into the Host's balance, with no accounting linking it back to the payer.

The issue is worse when `_hostParams.uniswapV2` is configured to `GnosisUniswapV2Wrapper`, which ignores the requested `amountOut` beyond a sanity check and converts the *entire* `msg.value` into fee token for the Host, discarding any notion of "exact amount": [6](#0-5) 

In that configuration, every dispatch call that estimates fees even slightly generously converts the full overpayment into fee tokens held by the Host, none of which is returned to the caller.

### Impact Explanation
Any user or app dispatching a POST/GET request or funding a pending request with native ETH permanently loses any ETH sent beyond the exact swap requirement. Given that documentation explicitly recommends estimating fees client-side and sending `msg.value` to cover them, and gas/AMM price fluctuations make exact estimation unreliable, this is a routine, systemic loss of user funds reachable from a single unprivileged transaction — not an edge case. This satisfies "concrete theft or permanent freezing of funds" for the calling user/app, since the excess ETH is irretrievably absorbed by the Host contract with no path to recovery for the original payer.

### Likelihood Explanation
High. This triggers on every normal usage path where a caller supplies native ETH to pay dispatch fees and slightly overestimates the required amount (which is expected/likely given AMM price movement between fee estimation and transaction execution), affecting `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` — the primary fee-payment entry points of the protocol.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` and refund the unspent `msg.value - amounts[0]` back to `_msgSender()` (or the intended payer) in `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`, mirroring the pattern already used in `ExtrinsicIntents._fillCrossChain` (`msgValue -= amounts[0]; if (msgValue > 0) _sendValue(msg.sender, msgValue);`).

### Proof of Concept
1. Caller estimates `post.fee` requires roughly `0.1 ETH` and calls `IDispatcher(host).dispatch{value: 0.15 ETH}(post)` to be safe against price movement.
2. `EvmHost.dispatch` forwards the full `0.15 ETH` to `swapETHForExactTokens{value: 0.15 ether}(post.fee, path, address(this), block.timestamp)`.
3. The router only needs, say, `0.08 ETH` to produce `post.fee` fee-tokens; it refunds `0.07 ETH` to `msg.sender` of the router call, i.e. `EvmHost`.
4. `EvmHost.dispatch` never reads or forwards this refund; the `0.07 ETH` remains stuck in the Host's balance, permanently lost to the caller, with no event or accounting tying it back to them.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
    }
