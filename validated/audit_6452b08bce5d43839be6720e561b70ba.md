### Title
`transactionSigner.signTransaction` has no lock/auth enforcement, allowing pre-authorization hardware device interaction while the wallet is locked - ([File: features/tx-signer/src/module/transaction-signer.ts])

### Summary
`TransactionSigner.signTransaction` in [1](#0-0)  only performs type/shape `assert` checks on `opts`, `baseAssetName`, `unsignedTx.txData`, and `unsignedTx.txMeta`. It never checks wallet/keychain lock state, and neither does the exposed `transactionSignerApi` layer [2](#0-1) , unlike the sibling `address-provider` API which explicitly gates every call on `lockedAtom.get()` before proceeding [3](#0-2) . As a result, a locked-wallet-aware caller boundary is missing for the transaction-signing surface, and for hardware wallet accounts this permits device interaction (`requireDeviceFor`) before any lock check ever fires.

### Finding Description
`#getTransactionSigner` dispatches purely on `walletAccount.isSoftware` / `walletAccount.isHardware` [4](#0-3) . For hardware accounts it immediately calls `this.#hardwareWallets.requireDeviceFor(walletAccount)`, which triggers device discovery/selection logic in `HardwareWallets` [5](#0-4)  — this path never touches `keychain` at all, so `keychain.lockPrivateKeys()` has zero effect on it.

For the software path, the eventual lock enforcement exists only deep inside `Keychain#getPrivateHDKey` → `#assertPrivateKeysUnlocked`, which throws `'private keys are locked'` [6](#0-5) [7](#0-6) . This is only reached once `signBuffer`/`getPublicKey` is actually invoked from `seed-signer.ts`'s `sign`/`getPublicKey` closures [8](#0-7) , i.e., after the asset's `signTx` implementation calls into the signer — well past `TransactionSigner.signTransaction`'s asserts and past `SeedBasedTransactionSigner.signTransaction`'s own `assert` calls on `txMeta.accountIndex`/`features.signWithSigner`/`keyId` [9](#0-8) .

Crucially, other feature APIs in this codebase (e.g. `address-provider`) implement an explicit `lockedAtom` check at the API boundary before doing any work [3](#0-2) , and this is verified by integration tests asserting rejection with `'address-provider: wallet should be unlocked'` prior to any downstream work [10](#0-9) . Neither `transactionSignerApi` nor `hardwareWalletsModuleDefinition`/`HardwareWallets` implement any equivalent `lockedAtom` gate — confirmed by the absence of any `lockedAtom` references in `features/tx-signer/**` or `features/hardware-wallets/**`. This means the application-level "locked" state (as exposed via `lockedAtom`, gating other modules) does not gate `transactionSigner.signTransaction` at all, and for hardware paths the keychain lock state is irrelevant by construction since hardware signing never touches the keychain.

### Impact Explanation
An unprivileged dapp/origin caller with RPC access to `exodus.transactionSigner.signTransaction` can invoke it for a hardware `WalletAccount` while the application/wallet is in a locked state (from the user's perspective), causing `HardwareWallets.requireDeviceFor` to run device discovery and get as far as issuing device commands (`ensureDeviceReady`, potential passphrase/PIN prompts on the physical device) before any locked-state check would ever occur — because no such check exists in this call path at all. This is an "unlocked-only side effect triggered while logically locked" issue: it does not by itself leak keys or produce an unauthorized signature (since the hardware device is still gated by its own physical confirmation), but it violates the invariant that a locked wallet should refuse to engage in any signing-adjacent activity, and can produce unexpected/unwanted device prompts, wasted device sessions, or UX-based confusion/social-engineering surface (e.g. a dapp causing a hardware prompt to appear while the user believes the wallet UI is locked).

### Likelihood Explanation
High feasibility: the `transactionSigner` module is `public: true` and reachable via the standard SDK/RPC surface documented in its README (`exodus.transactionSigner.signTransaction(...)`) [11](#0-10) . No privileged state or key material is required — only that the module remain wired up and a hardware `WalletAccount` object/name be passed, both of which are ordinary, attacker-controllable request parameters from a connected dapp/origin. The gap is structural (no `lockedAtom` dependency at all in `transactionSignerApi` or `hardwareWallets`), so it is fully repeatable.

### Recommendation
Add an explicit application/wallet lock check at the `transactionSignerApi` boundary (mirroring `address-provider`'s `withWalletAccountInstance` pattern using `lockedAtom.get()`) before dispatching to `transactionSigner.signTransaction`, for both software and hardware wallet accounts. Additionally, consider having `TransactionSigner.signTransaction` itself assert on a lock-state dependency before calling `#getTransactionSigner`, so the invariant holds even for callers that bypass the API layer.

### Proof of Concept
Integration test (in `sdks/headless/__tests__` style, matching the existing address-provider lock tests):
1. `await exodus.application.create({ passphrase })` then `await exodus.application.unlock({ passphrase })`, create/attach a mocked hardware `WalletAccount` (ledger/trezor source).
2. `await exodus.application.lock()` (sets `lockedAtom` true / calls `keychain.lockPrivateKeys()`).
3. Spy on the hardware wallet discovery entrypoint (e.g. `ledgerDiscovery.list` / `HardwareWallets.requireDeviceFor`).
4. Call `exodus.transactionSigner.signTransaction({ baseAssetName, unsignedTx, walletAccount: hardwareAccount })`.
5. Assert that `requireDeviceFor`/discovery was invoked (side effect occurred) despite the wallet being locked, and that no lock-related error was thrown prior to that side effect — demonstrating the missing lock gate. Expected (fixed) behavior: the call should reject immediately with a "wallet is locked" error before any hardware discovery call is made, and the spy should show zero invocations.

    const { baseAssetName, unsignedTx, walletAccount } = opts

    if (!('compatibilityMode' in unsignedTx.txMeta)) {
      unsignedTx.txMeta.compatibilityMode = walletAccount.compatibilityMode

    if (!('accountIndex' in unsignedTx.txMeta)) {
      unsignedTx.txMeta.accountIndex = walletAccount.index

    assert(

    const keyId = unsignedTx.txMeta?.keyId
    const signTx = baseAsset.api.signTx!

      const signer = await this.#getSignerForWalletAccount({ walletAccount, baseAsset })
