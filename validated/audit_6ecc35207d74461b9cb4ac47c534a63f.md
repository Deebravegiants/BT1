### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook shop spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app's secret [2](#0-1) . The `shop` value, read separately from the `shopify-shop-domain` / `x-shopify-shop-domain` header [3](#0-2) , is never part of the signed material, yet `Registry.process` trusts it unconditionally and hands it straight to the app's webhook handler as the tenant identifier [4](#0-3) .

### Finding Description
The identity binding that should hold is: **shop authenticated by the HMAC == shop the handler believes the webhook is from**. In this gem that equality does not hold, because the HMAC only covers `@raw_body` [1](#0-0) , while the `shop` field consumed by `Registry.process`/`WebhookMetadata` comes from an unauthenticated header [3](#0-2) [4](#0-3) .

Any unprivileged internet user who installs the app on their own (attacker-controlled) shop is a legitimate webhook recipient: they can trigger a real, correctly-signed webhook for their own store (e.g. by updating a product), capture the exact `raw_body` and the resulting `x-shopify-hmac-sha256` value that Shopify computed with the app's secret, and then replay that identical body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the body only) and will accept it, because it never looks at the shop header at all [5](#0-4) . `Registry.process` then dispatches the event to the app's handler with `shop: request.shop` set to the forged victim domain [6](#0-5) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an app relying on this library's HMAC validation to trust `shop` from a webhook will process/act on data (e.g. update local records, trigger side effects, invalidate caches, or write into the victim's stored session/data) under the wrong shop's identity — a cross-tenant access primitive reachable purely by an unprivileged merchant using their own store, with no access to `api_secret_key`, `client_secret`, or any privileged credential.

### Likelihood Explanation
High likelihood for any app that keys its webhook handling purely off the `shop`/`shop_domain` value provided by this library (as the docs imply is safe once `HmacValidator.validate` passes) [4](#0-3) . All that is required is: (1) install the app on an attacker-owned store to receive a legitimately signed webhook, and (2) resend the same body/signature with a different shop header — no secrets, tokens, or privileged access required.

### Recommendation
Bind the shop identity into the verified material, e.g. include the `shop-domain` header value in `to_signable_string` (or independently verify that `request.shop` matches an installation the app already knows the correct secret/session for) before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that `shop` from `Webhooks::Request` is not authenticated by the HMAC and must be cross-checked against known installed-shop records by the host application.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and legitimately triggers a webhook (e.g. `products/update`) — Shopify sends:
   - body: `{"id":123,...}`
   - `x-shopify-hmac-sha256: <valid HMAC of body with app secret>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
2. Attacker resends the identical body and HMAC to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC (`to_signable_string` returns `@raw_body`) [1](#0-0)  — validation succeeds.
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` [6](#0-5)  even though the event never originated from that shop.
