### Title
Cross-tenant webhook impersonation via unsigned `shop` domain header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` identity that the handler receives and acts on is read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is derived purely from the (unsigned) HTTP header: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` (i.e. the raw body only), and then immediately hands `request.shop` (from the header) to the app's handler without any additional binding check: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms the signature is computed only from `verifiable_query.to_signable_string` (the body), never the shop header: [4](#0-3) 

The identity binding the gem implicitly claims to enforce is: `shop authenticated by HMAC == shop the handler acts on`. In reality: `shop authenticated by HMAC (⊆ raw_body, no shop field) ≠ shop delivered to handler (== unsigned x-shopify-shop-domain header)`. Because the header is not part of the signed bytes, any bearer of one valid `(raw_body, hmac)` pair for topic `T` can resend that exact body/HMAC pair while substituting an arbitrary victim shop domain in the header, and `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the victim's shop.

### Impact Explanation
An unprivileged attacker who can obtain any single legitimate webhook delivery for a topic (e.g., by installing the app on their own shop, which is normal, permission-less merchant self-service, and receiving a real webhook such as `orders/create`, `customers/data_request`, or `shop/redact`) can capture the raw body and its valid HMAC signature. Because the HMAC never covers the shop domain, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while forging the `x-shopify-shop-domain` header to name any other merchant. `Registry.process` will pass HMAC validation and invoke the registered handler with `WebhookMetadata` carrying the victim's shop, even though the payload never originated from Shopify for that shop. If a host application uses `data.shop` to select the tenant's session/data (a documented, expected usage pattern for webhook handlers), this is a cross-tenant identity spoof: the attacker can inject fabricated business events (e.g., fake orders, fake GDPR `customers/redact`/`shop/redact` triggers) attributed to a shop they do not own and never authenticated as. This crosses a tenant boundary with no credential requirement beyond running the app once as any shop, satisfying the Critical "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs at least one legitimately signed `(raw_body, hmac)` pair, which they can freely acquire by installing the app on their own store (a permission-less, self-service action any internet user can take for a public app) and triggering an event that generates a webhook for a topic whose body content they don't need to control precisely (e.g., `shop/redact`, `customers/data_request`, or any recurring/predictable-body webhook). The replay itself only requires forging one HTTP header — no cryptographic material, access token, or `client_secret` is needed.

### Recommendation
Include the shop domain (and other identity-relevant metadata such as topic and API version) inside the HMAC-signed content, or otherwise cryptographically bind the header-derived `shop` value to the signed payload before it is trusted by `Registry.process`. At minimum, document and enforce that consuming applications must independently verify `request.shop` corresponds to a shop that actually has this app installed (i.e., cross-check against known-installed shop sessions) before acting on webhook data, and consider adding this check inside `Registry.process` itself rather than leaving it entirely to host applications.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (no special privilege required).
2. Attacker triggers a webhook whose body is attacker-controlled or predictable (e.g., updates a product to fire `products/update`, or waits for `customers/data_request`/`shop/redact` mandatory webhooks).
3. Attacker's own endpoint (or a sniffed proxy) captures the raw request body `B` and the header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — valid because it was really sent by Shopify for `attacker-shop.myshopify.com`.
4. Attacker sends a new request to the app's webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   Host: victim-app.example.com
   x-shopify-topic: <same topic>
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   Content-Type: application/json

   B
   ```
5. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and passes.
6. `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — the app now processes attacker-supplied data as if it came authentically from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
