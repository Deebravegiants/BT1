### Title
Webhook `shop` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `api_version`, and `webhook_id` from unauthenticated HTTP headers, while `to_signable_string` — the value that `Utils::HmacValidator.validate` actually verifies — only covers the raw request body. This breaks the intended binding `hmac == HMAC(secret, body ‖ shop ‖ topic)`; in reality the gem only enforces `hmac == HMAC(secret, body)`, with `shop`/`topic` left completely outside the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no cryptographic tie to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the body only) and then unconditionally forwards the header-derived, unauthenticated `request.shop` and `request.topic` to the app's handler: [3](#0-2) 

`HmacValidator.validate` and `validate_signature` compute the digest purely over `verifiable_query.to_signable_string`, never incorporating `shop`/`topic`: [4](#0-3) 

Because every shop installed on the same app shares the identical `api_secret_key` (the `client_secret`), a merchant/attacker who legitimately installs the app can capture a valid `(raw_body, hmac)` pair from one of their own genuine webhook deliveries, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. The signature check still passes — because it never examined those headers — and `Registry.process` dispatches the handler with `shop: <victim-shop>` derived entirely from the attacker-controlled, unsigned header. Any app logic that trusts `WebhookMetadata#shop` to select which merchant's tenant data to mutate (a common pattern, e.g. "delete customer data for `shop`", "update order status for `shop`") is now cross-tenant confusable.

This is the direct analog of the "bid amount vs. bid price" report: the security-relevant field acted upon by downstream logic (`shop`, used to select the tenant) is not the field actually covered by the cryptographic check (`raw_body` only).

### Impact Explanation
This breaks the equality `authenticated_shop == webhook_dispatch_shop`. Before the attack: the shop associated with a valid HMAC is only the shop that legitimately produced that body/HMAC pair. After the attack: an attacker who owns any single install of the app can forge webhook deliveries that `Registry.process` accepts as valid and dispatches under an arbitrary victim `shop` value, since `shop` is never included in the signed bytes. This crosses a tenant boundary using a spoofable, unauthenticated header — Critical, cross-tenant access, per the rules' impact categories.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the app on their own store (readily available to anyone using a public Shopify app) to obtain one valid `(body, hmac)` pair, and the ability to POST arbitrary HTTP headers to the app's public webhook endpoint (trivial for any unprivileged internet user, since webhook endpoints are unauthenticated HTTP receivers by design). No access token, `client_secret`, or privileged account is needed — matching the "unprivileged internet user" threat model.

### Recommendation
Include `shop` (and ideally `topic`) as part of the signable payload verified by `Utils::HmacValidator`, or independently validate that `request.shop` matches a shop domain the app has an active, previously-established session/installation for before dispatching to the handler. At minimum, document and enforce that `Registry.process` must be paired with an application-side check binding the header-derived `shop` to a known, authenticated installation prior to acting on it.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and capture a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Replay the same `B` and `H` to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`, both unchanged.
4. `Registry.process` dispatches the registered handler with `shop: "victim-shop.myshopify.com"`, `topic: "orders/create"`, and `body: B` — none of which Shopify's victim store actually sent — demonstrating that the shop identity used for tenant dispatch is unauthenticated and attacker-controlled: [3](#0-2)

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
