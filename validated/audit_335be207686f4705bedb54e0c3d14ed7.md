### Title
Webhook shop attribution is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant) attribute used by `ShopifyAPI::Webhooks::Registry.process` to dispatch the event is taken from an unauthenticated header. Any actor who can obtain one validly-signed webhook body (e.g., by triggering a webhook on their own, legitimately installed shop) can replay that body with a forged `shop-domain` header pointing at a different, victim shop, and the HMAC check will still pass.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then dispatches to the handler using the unauthenticated `request.shop` value as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that the `hmac` field matches a signature computed over `to_signable_string` (i.e., the body) using `Context.api_secret_key`, which is a single secret shared by the app across *all* installed shops: [4](#0-3) 

The broken identity binding is:

`hmac_verified(body)` == `true` while `shop_used_for_dispatch` (the `shopify-shop-domain` header) is never included in the signed material — the equality the gem should enforce, `hmac_covers(shop) == shop_used_for_tenant_attribution`, does not hold.

Because the API secret is the same for every shop that has installed the app (it's per-app, not per-shop), any shop owner who has installed the app (an "unprivileged" actor with respect to *other* tenants of the same app) can capture a legitimately-signed webhook body from their own store's event stream and re-POST it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to name a different, victim shop that also has the app installed. `HmacValidator.validate` will still succeed because it only checks the body signature, and `Registry.process` will hand the payload to the app's handler tagged as having come from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an attacker who is a legitimate (but unprivileged relative to other tenants) app installer can make the host application process arbitrary attacker-controlled JSON as if it originated from a different merchant's shop. Any app logic that keys state, access-token lookup, billing, inventory sync, or other side effects off `WebhookMetadata#shop` is exposed to cross-tenant data injection/confusion, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own valid installation of the target app (a normal unprivileged merchant install, not a privileged credential), and (2) network access to POST to the app's public webhook endpoint with a captured raw body and a modified shop header — both trivially available to any merchant who installs the app. No access token, `api_secret_key`, or TLS interception is needed.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signable content, or otherwise cryptographically bind them to the verified body, so that `HmacValidator.validate` fails if any of these attributes are altered independently of the signed body. At minimum, document that `Registry.process`/`WebhookMetadata#shop` must never be trusted as an authenticated tenant identifier and that consuming apps must cross-check `shop` against an existing, previously-established session/install record before acting on the payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any webhook subscription (e.g., `orders/create`), capturing the raw POST body `B` and the resulting `x-shopify-hmac-sha256` header `H` (valid because it's signed with the app's real, shared `api_secret_key`).
2. Attacker replays the request to the app's webhook endpoint, keeping `B` and `H` unchanged but setting `x-shopify-shop-domain: victim.myshopify.com` (a store that also has the app installed).
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and finds it matches `H`, since `shop` was never part of the signed content: [3](#0-2) [1](#0-0) 
4. The registered handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...)` and processes attacker-controlled data as if it belonged to `victim.myshopify.com`.
