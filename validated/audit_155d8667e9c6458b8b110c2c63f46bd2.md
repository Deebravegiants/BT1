### Title
Deprecated single-extension `StorageWeightReclaim<T>` mis-accounts `frame_system::BlockWeight` when transaction extensions execute after it in the pipeline - (File: cumulus/primitives/storage-weight-reclaim/src/lib.rs)

### Summary
`StorageWeightReclaim<T>::post_dispatch_details` snapshots the host-side proof size (`get_proof_size()`) at the moment *it* runs and immediately writes the reclaim/accrual delta into `frame_system::BlockWeight`. Because `TransactionExtension` tuples execute `post_dispatch_details` in forward (declared) order, any extension placed after `StorageWeightReclaim<T>` in `SignedExtra` that performs storage reads during its own `prepare`/`post_dispatch_details` contributes proof-size cost that is invisible to this snapshot.

### Finding Description
`post_dispatch_details` (lines 163-226) computes `consumed_weight` from `get_proof_size()` at the point it runs and mutates `frame_system::BlockWeight::<T>` accordingly (lines 195-224). The `Tuple` implementation of `TransactionExtension::post_dispatch_details` in `substrate/primitives/runtime/src/traits/transaction_extension/mod.rs` (lines 614-627) invokes each element's `post_dispatch_details` strictly in tuple order, not in reverse. Consequently, if a runtime configures `SignedExtra` as e.g. `(StorageWeightReclaim<T>, CustomFeeOrProxyCheck<T>)`, any storage reads performed by `CustomFeeOrProxyCheck<T>` during its `prepare`/`post_dispatch_details` occur *after* `StorageWeightReclaim<T>` has already read `get_proof_size()` and mutated `BlockWeight`. This exact limitation is explicitly called out in the crate's own deprecation note attached to `StorageWeightReclaim` (lines 114-118): "it ignores... the post dispatch logic for extensions subsequent to itself." An unprivileged signed user simply submitting a normal extrinsic through this misconfigured pipeline reaches the flawed code path — no special privilege is required, only the (documented, supported-but-deprecated) misconfiguration.

The `missing_from_node` catch-up logic (lines 211-223) is designed to correct cases where node-side proof size exceeds runtime bookkeeping, but it only compares against `node_side_pov_size` measured at the time *this* extension runs, so it cannot see growth caused by extensions after it in the same extrinsic. However, because `get_proof_size()` is a cumulative, block-wide host measurement, this drift is not permanent: the very next extrinsic's `StorageWeightReclaim` invocation in the same block will observe the increased cumulative proof size and reconcile it via `missing_from_node`. Only the final extrinsic of the block escapes this self-correction window within `BlockWeight`.

### Impact Explanation
Under the documented misconfiguration, `frame_system::BlockWeight` can transiently under- or over-represent true PoV/storage-proof consumption per extrinsic, with self-correction occurring on the next extrinsic in the same block via `missing_from_node`, except for the last extrinsic of a block. Note that hard PoV-size enforcement (`max_pov_size`) for block candidates is performed by the collator/relay-chain validation using the actual measured proof, independent of the runtime's `BlockWeight` storage value, so this bookkeeping drift affects fee-refund/weight-limit accounting fidelity rather than being the sole safeguard against oversized blocks.

### Likelihood Explanation
Requires a runtime to keep `StorageWeightReclaim<T>` (deprecated) wired as a non-terminal element of `SignedExtra`, which is an explicit misconfiguration the deprecation note warns against. Given that misconfiguration, any ordinary signed extrinsic exercises the flawed accounting, making it fully and repeatably reachable by an unprivileged attacker, but the drift is bounded and largely self-correcting within a block.

### Recommendation
Migrate to `StorageWeightReclaim` in `cumulus-pallet-weight-reclaim`, which wraps the entire extension pipeline as documented, instead of using the deprecated single-extension variant. If migration is not immediate, mandate at the `construct_runtime`/`SignedExtra` definition level that the deprecated `StorageWeightReclaim<T>` be the last element in the tuple, and add a runtime-metadata or CI check asserting this ordering.

### Proof of Concept
Extend `cumulus/primitives/storage-weight-reclaim/src/tests.rs` with an integration test using a `SignedExtra` tuple `(StorageWeightReclaim<Test>, StorageHeavyDummyExtension<Test>)` where `StorageHeavyDummyExtension::post_dispatch_details` performs a large storage read (simulated via `set_current_storage_weight`/host proof size mock) after `StorageWeightReclaim`'s `post_dispatch_details` has already run. Assert that `frame_system::BlockWeight::<Test>::get().total().proof_size()` immediately after dispatching this single extrinsic does not reflect the dummy extension's read, then dispatch a second extrinsic and assert the drift is reconciled via the `missing_from_node` branch, while for a single-extrinsic block the discrepancy remains uncorrected. 	fn post_dispatch_details(
		pre: Self::Pre,
		info: &DispatchInfoOf<T::RuntimeCall>,
		post_info: &PostDispatchInfoOf<T::RuntimeCall>,
		_len: usize,
		_result: &DispatchResult,
	) -> Result<Weight, TransactionValidityError> {
		let Some(pre_dispatch_proof_size) = pre else {
			return Ok(Weight::zero());
		};

		let Some(post_dispatch_proof_size) = get_proof_size() else {
			log::debug!(
				target: LOG_TARGET,
				"Proof recording enabled during pre-dispatch, now disabled. This should not happen."
			);
			return Ok(Weight::zero());
		};
		// Unspent weight according to the `actual_weight` from `PostDispatchInfo`
		// This unspent weight will be refunded by the `CheckWeight` extension, so we need to
		// account for that.
		let unspent = post_info.calc_unspent(info).proof_size();
		let benchmarked_weight = info.total_weight().proof_size().saturating_sub(unspent);
		let consumed_weight = post_dispatch_proof_size.saturating_sub(pre_dispatch_proof_size);

		let storage_size_diff = benchmarked_weight.abs_diff(consumed_weight as u64);

		let block_size = frame_system::BlockSize::<T>::get().unwrap_or(0);
		let node_side_pov_size = post_dispatch_proof_size.saturating_add(block_size.into());

		// This value will be reclaimed by [`frame_system::CheckWeight`], so we need to calculate
		// that in.
		frame_system::BlockWeight::<T>::mutate(|current| {
			if consumed_weight > benchmarked_weight {
				log::error!(
					target: LOG_TARGET,
					"Benchmarked storage weight smaller than consumed storage weight. extrinsic: {} benchmarked: {benchmarked_weight} consumed: {consumed_weight} unspent: {unspent}",
					frame_system::Pallet::<T>::extrinsic_index().unwrap_or(0)
				);
				current.accrue(Weight::from_parts(0, storage_size_diff), info.class)
			} else {
				log::trace!(
					target: LOG_TARGET,
					"Reclaiming storage weight. extrinsic: {} benchmarked: {benchmarked_weight} consumed: {consumed_weight} unspent: {unspent}",
					frame_system::Pallet::<T>::extrinsic_index().unwrap_or(0)
				);
				current.reduce(Weight::from_parts(0, storage_size_diff), info.class)
			}

			// If we encounter a situation where the node-side proof size is already higher than
			// what we have in the runtime bookkeeping, we add the difference to the `BlockWeight`.
			// This prevents that the proof size grows faster than the runtime proof size.
			let block_weight_proof_size = current.total().proof_size();
			let missing_from_node = node_side_pov_size.saturating_sub(block_weight_proof_size);
			if missing_from_node > 0 {
				log::debug!(
					target: LOG_TARGET,
					"Node-side PoV size higher than runtime proof size weight. node-side: {node_side_pov_size} block_size: {block_size} runtime: {block_weight_proof_size}, missing: {missing_from_node}. Setting to node-side proof size."
				);
				current.accrue(Weight::from_parts(0, missing_from_node), info.class);
			}
		});
		Ok(Weight::zero())
	}
