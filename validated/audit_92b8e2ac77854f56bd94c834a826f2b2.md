### Title
Escrow decrement after external token transfer in `IntentGatewayV2.withdraw` (Tron) violates checks-effects-interactions - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2.withdraw()` transfers escrowed native/ERC-20 tokens to the beneficiary via a raw `.call` *before* decrementing the corresponding `_orders[commitment][token]` escrow accounting, and does the same for accumulated transaction fees. This is the exact CEI-violation pattern flagged in the external report (transfer/burn ordering issue that enables reentrancy against depressed/stale accounting), and it is reachable from the unprivileged `cancelOrder` entrypoint and from relayer-delivered `RedeemEscrow`/`RefundEscrow` messages.

### Finding Description
`withdraw()` performs the external call and *then* updates storage: [1](#0-0) 

```
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = ...
    _filled[body.commitment] = beneficiary;
    for (...) {
        ...
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        }
        _orders[body.commitment][token] -= amount;   // <-- decremented AFTER the external call
    }
    ...
}
```

and the fee payout follows the same anti-pattern: [2](#0-1) 

This is reachable from `cancelOrder` (unprivileged, same-chain path) at: [3](#0-2) 
and from `onAccept`/`onGetResponse` for `RedeemEscrow`/`RefundEscrow` messages: [4](#0-3) [5](#0-4) 

Critically, the maintainers already recognized and fixed exactly this bug class in the primary EVM `intentsv2` implementation, where the escrow map is decremented *before* the external transfer (proper CEI): [6](#0-5) 

The Tron contract does not carry this fix.

### Impact Explanation
An attacker who places an order using a malicious ERC-20 as one of the escrowed input tokens (`order.inputs[i].token` is caller-supplied and unvalidated at `placeOrder`, see `evm/tron/contracts/apps/IntentGatewayV2.sol:451-469`) controls arbitrary code that runs mid-way through `withdraw()`'s token loop, before that token's own escrow entry is zeroed and before the transaction-fee escrow is cleared. Because `_filled[commitment]` is set as the very first statement of `withdraw()`, the most direct reentrant path (calling `cancelOrder` again for the same commitment) is blocked; however, the ordering still leaves the transaction-fee escrow (`_orders[commitment][TRANSACTION_FEES]`) and any not-yet-processed token entries in the same call readable/actionable by attacker-controlled code before they are cleared, and constitutes a deviation from the intended invariant that escrow state must be effects-before-interactions. Any future code path that reads `_orders[commitment][token]` (e.g. a partial-fill or balance-check helper) without an equivalent `_filled` style guard would be immediately exploitable for double-withdrawal of the same escrow. Given the sensitivity of this contract (it custodies user/solver funds crossing chains), this is at least a Medium severity defect even though the currently known reentrant paths are guarded by `_filled`.

### Likelihood Explanation
Likelihood is Medium: exploitation requires (1) an attacker to place an order using a malicious/callback-capable ERC-20 as an escrowed input, and (2) a call path into `withdraw()` (self-triggered `cancelOrder`, or a relayed `RedeemEscrow`/`RefundEscrow`) processing that token. This is fully reachable by any unprivileged user through `placeOrder` + `cancelOrder`, a single-transaction, no-privilege attack surface. The `_filled` guard reduces immediate exploitability of the most obvious double-withdrawal via `cancelOrder` re-entry, but the underlying storage-update-after-external-call pattern remains a latent, easily-triggered hazard that mirrors the reported bug class precisely, and any code change that reuses `_orders[...]` state (e.g. new partial-redemption/fill logic ported from the EVM side without the fixed CEI ordering) would immediately become exploitable.

### Recommendation
Decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing the native/ERC-20 transfer in `withdraw()`, mirroring the fix already applied in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` (`_orders[body.commitment][token] = escrowed - amount;` prior to `safeTransfer`/`_sendValue`). Apply the same reordering to the fee payout block and to `SweepDust` handling in `onAccept` for consistency.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs = [ { token: <MaliciousToken>, amount: X }, { token: USDC, amount: Y } ]`, escrowing both tokens under `commitment`.
2. Attacker (as `order.user`) calls `cancelOrder(order, options)` on the same chain; `_filled[commitment]` is unset so the check at `evm/tron/contracts/apps/IntentGatewayV2.sol:520` passes.
3. `withdraw()` runs: `_filled[commitment]` is set (line 693), then the loop reaches `MaliciousToken.transfer(beneficiary, X)` (line 706) — this executes attacker-controlled code *before* `_orders[commitment][MaliciousToken] -= X` and before `_orders[commitment][USDC] -= Y` are applied.
4. Inside the malicious `transfer()` hook, the attacker can attempt to read/act on the still-unset escrow state for USDC or the fee entry, or, in any future/alternate code path lacking the `_filled` gate (as demonstrated by the difference between this contract and the un-guarded `SweepDust` handler and the fee-clearing block that occurs even later), extract value tied to that stale accounting.

**Note on confidence:** the exact `_filled` guard placed at the top of `withdraw()` blocks the most straightforward "call `cancelOrder`/`withdraw` twice for the same commitment" reentrancy, so I could not construct a fully concrete double-spend transaction within the current codebase given available context. This finding is reported because the CEI-violation described in the external report exists verbatim in `withdraw()` and diverges from the already-fixed sibling implementation, and represents unresolved risk warranting remediation, but I was not able to fully verify the exact ordering of receipt-setting vs. `onAccept` invocation in `EvmHost.sol`/`HandlerV2.sol` (grep matches were found but not read in full) that would determine whether a nested cross-message replay is also possible — this would need further investigation via a live Devin session with full file access.
