### Title
Sweep deposits into ERC-4626 vaults have no minimum-shares-out check, allowing a donation front-run to worsen the solver's mint price - (File: `sdk/packages/simplex/src/funding/vault/VaultFundingPlanner.ts`)

### Summary
`VaultFundingPlanner.sweepChain` builds an `approve` + `deposit(depositAmount, solver)` pair against a configured ERC-4626 vault and submits it as a single batch, entirely on a periodic timer with no user-supplied slippage bound. [3](#0-2) 

The vault's exchange rate is `totalAssets() = asset.balanceOf(vault) - lockedYield()`, and `lockedYield` only masks yield contributed through `addYield`. A plain ERC-20 `transfer` of the underlying asset directly to the vault ("donation") is not tracked as locked yield and instantly changes `totalAssets`, hence the shares-per-asset conversion rate used by `deposit`. [4](#0-3) [2](#0-1) 

### Finding Description
This mirrors the Rio issue exactly: `deposit(assets, receiver)` mints `shares = convertToShares(assets)` computed at execution time from the *current* `totalAssets`/`totalSupply` ratio, with no `minSharesOut` argument anywhere in the sweep call construction. Because the sweep is triggered automatically once wallet balance crosses `vault.thresholdScaled`, an unprivileged attacker watching the mempool/predictable sweep cadence (`startSweeping` fires every `sweepIntervalMs`, default visible cadence) can front-run the solver's deposit transaction with a bare token donation to the vault, inflating `totalAssets` and thus worsening the shares-per-asset rate the solver's deposit receives. [5](#0-4) 

The code that computes the shares figure (`quoteShares`, via `previewDeposit`) is used purely for logging/ledger movements after the deposit call has already been constructed — it is never checked against the actual outcome or used to abort the deposit if the rate has moved unfavorably. [6](#0-5) 

The vault's own decimals-offset mitigation (`DECIMALS_OFFSET`) defends only against the classic first-depositor inflation attack on an empty/near-empty vault; it does not bound ordinary post-seed slippage from a donation that lands between a legitimate depositor's transaction submission and its inclusion. [7](#0-6) [8](#0-7) 

### Impact Explanation
The solver's automated treasury sweep can mint fewer vault shares than the deposited assets are actually worth, permanently transferring value to whichever address already holds shares in the vault at the time of the donation (which could be the attacker themselves, if they pre-position shares before donating). Because the sweep is unconditional (no min-shares check, no revert path on unfavorable rate), the loss is realized and not recoverable — it is not a transient/no-impact condition; it is a real value transfer out of solver-controlled funds on every sweep that gets sandwiched this way.

### Likelihood Explanation
The sweep cadence and trigger conditions (`threshold`, `minBalance`, periodic timer) are either predictable (fixed interval) or observable on-chain (wallet balance crossing the threshold, watchable via a public RPC), and the donation itself is a single unprivileged ERC-20 `transfer` to the vault address — no special permissions or races beyond ordinary front-running are required. This is comparable in reachability to the original Rio report, which the disclosure rated Medium.

### Recommendation
Add slippage protection to the sweep's deposit path: after building the intended `depositAmount`, read `previewDeposit(depositAmount)` immediately before submission and either (a) pass a minimum-shares check that reverts the batch if the vault's `deposit` mints fewer shares than a computed floor (e.g., via a custom deposit wrapper that checks `balanceOf(solver)` delta), or (b) tighten the sweep window so the deposit transaction is submitted and confirmed with minimal exposure, and treat `quoteShares`'s previewed value as an enforced floor rather than telemetry only.

### Proof of Concept
1. Attacker observes the solver's wallet balance for a configured vault asset approaching `vault.thresholdScaled` (public RPC read, same call the sweep itself performs).
2. Attacker front-runs the anticipated sweep transaction (or races the fixed-interval timer) with `asset.transfer(vault, donationAmount)`, a bare ERC-20 transfer with no special access.
3. This immediately raises `totalAssets()` (`balanceOf(vault) - lockedYield()`) without minting any shares to the attacker for that donation, worsening the assets→shares conversion rate.
4. The solver's `sweepChain` still executes `approve` + `deposit(depositAmount, solver)` unconditionally at the now-worse rate — `depositAmount` is unchanged and no `minSharesOut` is enforced, so the solver mints fewer shares than it would have without the donation, and the shortfall accrues to existing shareholders (including the attacker if they hold shares before donating). 	 * Starts the periodic sweep timer. Runs one sweep shortly after start, then
	 * every `sweepIntervalMs`. Idempotent — a second call is a no-op.

	startSweeping(): void {
		if (this.sweepInterval) return
		const intervalMs = this.config.sweepIntervalMs ?? DEFAULT_SWEEP_INTERVAL_MS

		// Initial sweep shortly after start (lets the filler settle first).
		this.initialSweepTimer = setTimeout(() => {
			this.sweepExcessToVault().catch((err) => this.logger.error({ err }, "Vault initial sweep failed"))
		}, 30_000)

		this.sweepInterval = setInterval(() => {
			this.sweepExcessToVault().catch((err) => this.logger.error({ err }, "Vault periodic sweep failed"))
		}, intervalMs)

		this.logger.info({ intervalMs }, "Vault periodic sweep started")
	}

        uint256 donation = 100 ether;

        uint256 attackerSpent;

        // 1 wei first deposit.

        uint256 victimShares = _deposit(alice, victimDeposit);
