### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler routing without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract only requires `hmac` and `to_signable_string` [1](#0-0) . For webhook requests, `to_signable_string` returns only the raw HTTP body (`@raw_body`); it does not include the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [2](#0-1) . `HmacValidator.validate` computes an HMAC over exactly that signable string and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header using `OpenSSL.secure_compare` [3](#0-2) .

`Registry.process` then calls `Utils::HmacValidator.validate(request)` and, if it passes, dispatches to the handler using `request.topic` and `request.shop` — both of which are read straight from unauthenticated HTTP headers and are never bound into the HMAC computation:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

This is the same class of bug as the `PreimageOracle` finding: a field that downstream code treats as authenticated/trusted (`request.shop`, which is handed to the app as the tenant identifier, analogous to `_precompile` used to key `preimagePartOk`) is not part of the data actually covered by the cryptographic check (`preimagePartOk[_key][_offset]` vs. `readPreimage`'s trust of that flag). Here the equality that should hold is:

`shop asserted by HMAC-signed content == shop attributed to the webhook by the gem`

but the gem instead verifies `HMAC(raw_body) == received_hmac` and then unconditionally trusts the header-derived `shop` for routing/attribution, breaking that equality.

### Impact Explanation
Because the `shop-domain` header sits outside the signed payload, a webhook payload/signature pair that Shopify legitimately generated for one shop can be re-sent by anyone who receives it (e.g., an attacker's own store, which does receive genuine webhooks with valid signatures for its own topics/body) with the `shop-domain` header swapped to a victim shop's domain. `Registry.process` still finds `Utils::HmacValidator.validate` returns `true` (since it only checks the raw body against the secret, and the app's secret is the same for all shops of that app), and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop [5](#0-4) . Any app logic that keys off `data.shop` (e.g., updating per-shop state, redact/GDPR mandatory topics such as `shop/redact`, `customers/redact`, `customers/data_request` in `MANDATORY_TOPICS` [6](#0-5) ) can be tricked into acting on the wrong tenant, i.e. cross-tenant data confusion/injection — matching the Critical "cross-tenant access" impact category, since the gem itself misattributes verified data to an arbitrary shop.

### Likelihood Explanation
Exploitation requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint plus possession of one genuinely-signed payload for the same app (trivially obtainable by installing the target app on the attacker's own development store, since HMAC uses the app's single `client_secret`, not a per-shop key) — no privileged credentials, access tokens, or `api_secret_key` leakage are required, which keeps this within scope as an unprivileged-internet-user issue. This is a real, structural design gap (the signable string excludes shop/topic) rather than a theoretical one, directly analogous to the confirmed “address not covered by hash” issue in the referenced report.

### Recommendation
Bind the identity fields used for tenant/topic routing into the verified data: either include `shop`, `topic`, `webhook-id`, and `api-version` in `to_signable_string` (if compatible with Shopify's documented HMAC scheme), or, since Shopify's HMAC only ever covers the raw body by design, treat `request.shop`/`request.topic` as merely advisory and require host applications/`Registry` to cross-check `request.shop` against the session/shop the webhook registration was created for before acting on `WebhookMetadata`. At minimum, document explicitly that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated header values not covered by the HMAC, so consuming apps do not treat `WebhookMetadata#shop` as a verified tenant identifier.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; capture a legitimately Shopify-signed webhook request (valid `raw_body` + `x-shopify-hmac-sha256`) for a topic the app also registers for the victim, e.g. `orders/create`.
2. Replay the exact same `raw_body` and `hmac-sha256` value to the app's webhook endpoint, but replace the `shopify-shop-domain` / `x-shopify-shop-domain` header with the victim shop's domain.
3. `ShopifyAPI::Webhooks::Request.new` builds the request from headers (no shop/topic binding) [7](#0-6) ; `Utils::HmacValidator.validate(request)` succeeds because it only re-hashes `@raw_body` [8](#0-7) .
4. `Registry.process` passes the validated request to the handler with `shop: request.shop` set to the victim's domain, even though Shopify never actually sent this webhook for the victim [5](#0-4) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
