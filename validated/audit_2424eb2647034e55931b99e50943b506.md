### Title
Webhook shop identity not bound to HMAC signature enables cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` identity that is handed to the application's business logic is read from an unauthenticated header. Any party capable of obtaining one valid `(body, hmac)` pair for the app (trivially available to anyone who installs the app on their own store, since Shopify signs webhooks with the app-wide `api_secret_key` rather than a per-shop key) can replay that pair while substituting an arbitrary `shop-domain` header, and the gem will report the request as fully validated and pass the attacker-chosen shop identity to the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed string at all: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (i.e., the body) against the HMAC: [3](#0-2) [4](#0-3) 

Once the HMAC check passes, `request.shop` (the unauthenticated header value) is forwarded unchanged into `WebhookMetadata`, which is what the host application's handler code trusts as the tenant identity of the event: [5](#0-4) 

This is the same bug class as the report's "field acted on but not covered by the signing/verification mechanism": the `shop` field is consumed by downstream logic but is excluded from the cryptographic binding (`hmac(body)`), so `shop` and `body` can be mixed-and-matched independently — an equality of `authenticated(body) == identity_used(shop)` that the code never actually enforces.

### Impact Explanation
Any internet-reachable party who has installed the app on any store (a normal, unprivileged action — no special access to the target shop, no leaked credentials, no `api_secret_key` needed) can generate genuine, correctly-signed webhook payloads for their own shop (Shopify signs all webhooks for an app with that app's single, app-wide `api_secret_key`, not a per-shop secret). They can then resend that valid `(body, hmac)` pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` will accept it as valid and hand the handler a `WebhookMetadata` claiming it originated from the victim shop. Any host application that keys its persistence, session lookup, or business logic off `data.shop` (the documented, expected usage) will process attacker-controlled data under the wrong tenant's identity — a cross-tenant data integrity/confusion issue, including for mandatory compliance topics such as `customers/redact` or `shop/redact`.

### Likelihood Explanation
High reachability: no privileged credentials, tokens, or `api_secret_key` are required — only the ability to install the app on an attacker-controlled shop (a normal capability of any Shopify merchant/developer) and the ability to POST to the app's public webhook endpoint, both of which are standard, expected interactions with this gem's own webhook-verification code path.

### Recommendation
Bind the shop identity to the authenticated content: include `shop` (and `topic`) in the HMAC-signed material, or independently verify `request.shop` against a known/authorized shop (e.g., cross-check with the app's session store) before constructing `WebhookMetadata`, mirroring the report's remedy of removing an independently-settable identity source and deriving it only from the already-authenticated channel.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`; Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)`.
3. Attacker sends a new POST to the same webhook endpoint with:
   - Body `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it only signs `B`)
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (attacker-controlled)
4. `Utils::HmacValidator.validate(request)` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`) because it only checks `B` against `H`.
5. `Registry.process` proceeds and calls `handler.handle` with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the event content actually belongs to the attacker's own shop.
