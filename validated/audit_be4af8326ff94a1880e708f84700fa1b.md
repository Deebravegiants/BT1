### Title
Unchecked-length `copy_from_slice` into a fixed 65-byte buffer during naive BEEFY consensus proof conversion causes a wasm trap on attacker-controlled proof bytes - (File: `evm/rust/src/conversions.rs`)

### Summary
The CVE-2019-25078 bug class is a fixed-size buffer write driven by unvalidated, attacker-controlled length data (`pacparser_find_proxy`). The closest reachable analog in Hyperbridge is the `From<Vote> for SignatureWithAuthorityIndex` conversion used while decoding a naive (ECDSA) BEEFY consensus proof submitted by any unprivileged caller: it copies a variable-length `signature` byte vector into a fixed `[u8; 65]` array with `copy_from_slice`, without first checking that the source is exactly 65 bytes.

### Finding Description [1](#0-0) 

```rust

	fn from(value: Vote) -> Self {
		let sig_bytes = value.signature.to_vec();
		let mut signature: TSignature = [0u8; 65];
		signature.copy_from_slice(&sig_bytes);
		...
```

`Vote` is the Solidity-ABI type produced by decoding the caller-supplied `BeefyConsensusProof` bytes (`ismp_abi::ecdsa_beefy::BeefyConsensusProof::abi_decode_params`) inside `BeefyConsensusProofsPallet::verify_and_apply`, which is invoked for `PROOF_TYPE_NAIVE`: [2](#0-1) 

`Vote.signature` corresponds to a Solidity `bytes` field, which ABI-decodes to an arbitrary-length byte string — the caller fully controls its length. `Rust`'s `copy_from_slice` on a fixed-size `[u8; N]` array **panics** ("source slice length … does not match destination slice length") whenever the source length differs from `N`. Since the destination here is a hard-coded `[u8; 65]`, any submitted `Vote.signature` that isn't exactly 65 bytes triggers a panic during message conversion, before any cryptographic verification takes place.

This is exactly the anti-pattern this codebase has already identified and fixed in multiple other places, each accompanied by an explicit comment stating the danger of `copy_from_slice` panicking on untrusted-length input reachable from external calls: [3](#0-2) [4](#0-3) 

The BEEFY naive-proof conversion path in `evm/rust/src/conversions.rs` was not covered by that hardening pass and still contains the unguarded fixed-size copy.

### Impact Explanation
A panic inside a pallet extrinsic's execution path is a Wasm trap. Depending on how `submit_proof`/`verify_and_apply` is invoked in the runtime (dispatched extrinsic execution), an unhandled panic during message dispatch can abort block execution for that transaction, and in aggressive cases destabilize the collator/validator executing it. At minimum this is a permanent denial-of-service vector against the BEEFY consensus-proof submission path: any signed account can submit a syntactically valid ABI payload with a `Vote.signature` of the wrong length and crash message processing, which maps to the "route unable to deliver messages" impact category (BEEFY-secured message delivery for the affected consensus client becomes unusable/unreliable while this input keeps being retried or while it corrupts relayer scheduling).

### Likelihood Explanation
High. `verify_and_apply` is reachable via `submit_proof`, which per the pallet's own test suite is open to "an unsigned origin ... only accepts `ensure_signed`" — i.e., **any signed, unprivileged account** can call it: [5](#0-4) . Constructing a malformed `Vote.signature` of length ≠ 65 requires no privileged access, no specific chain state, and no cryptographic material — only crafting the ABI payload, which any relayer/attacker can do trivially.

### Recommendation
Replace the unchecked `copy_from_slice` with a checked conversion (e.g. `TryFrom<&[u8]>` or an explicit length check returning an error) before constructing `SignatureWithAuthorityIndex`, mirroring the fixes already applied elsewhere in the codebase (`modules/ismp/core/src/host.rs`, `modules/utils/serde/src/lib.rs`, `parachain/node/fisherman/src/lib.rs`). Reject any `Vote.signature` that is not exactly 65 bytes with a typed error instead of panicking.

### Proof of Concept
1. Craft an ABI-encoded `BeefyConsensusProof` (per `ismp_abi::ecdsa_beefy::Beefy::BeefyConsensusProof`) containing a `SignedCommitment.signatures` entry whose `Vote.signature` field is populated with, e.g., 64 or 66 bytes instead of 65.
2. Prefix the payload with `types::PROOF_TYPE_NAIVE` and submit it via the pallet's `submit_proof` extrinsic (signed by any account) as accepted by `BeefyConsensusProofsPallet::verify_and_apply`.
3. Execution reaches `abi_decode_params::<BeefyConsensusProof>` (succeeds — ABI decoding places no length constraint on `bytes`), then the `From<...>` conversion chain calls `SignatureWithAuthorityIndex::from(Vote)`, which panics at `signature.copy_from_slice(&sig_bytes)` because `sig_bytes.len() != 65`.
