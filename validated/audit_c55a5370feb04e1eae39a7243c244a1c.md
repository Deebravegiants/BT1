### Title
LP-seeding fallback `_seedDirectMint` is reused outside its safe "dust-reserves" precondition inside `_seedRebalancing`, allowing a hostile pre-seed of the HyperSwap V2 TOKEN/LT pair to donate LP value and skew the graduation LP off the curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._seedUniswapV2Direct` / `_seedRebalancing` are documented as hardening against an attacker who pre-creates the HyperSwap V2 `TOKEN/LT` pair and calls `pair.mint()` with a self-chosen ratio before `finalizeGraduation` runs [1](#0-0) . The rebalance branch is supposed to swap the pool toward the curve-close ratio via direct `pair.swap` before depositing through the router's ratio-safe `addLiquidity` [2](#0-1) . However, whenever `_pairRebalance` returns `false` (the computed swap input or its fee-adjusted output rounds to zero), the code falls back to `_seedDirectMint` [3](#0-2) , which unconditionally transfers the full `(tokensForLP, ltFromPair)` to the pair and calls `pair.mint(lpLock)` [4](#0-3) . That function's own natspec says it is only safe "against dust reserves" where the V2 `min()` donation is negligible [5](#0-4) , but the actual guard on "dust" is a *separate*, narrower check (`DIRECT_MINT_PRESEED_BPS`, both sides ≤ 1 bp of the LP target) applied earlier at lines 1297-1301 [6](#0-5) . The `_pairRebalance`-returns-`false` fallback is a *different* condition (integer rounding of the no-fee swap input or the pair's fee-charging `getAmountOut`) that is not bounded by that dust threshold, so it can fire against a pre-seed that is far larger than 1 bp. This is the on-chain analog of `apply_patch`'s non-sandboxed path resolution reusing a "safe" primitive outside the boundary it was actually validated for — here, an "empty pool" mint primitive is invoked against a non-empty, attacker-controlled pool.

### Finding Description
`finalizeGraduation` calls `_ensureUniswapV2Pair`, which simply fetches or creates the HyperSwap V2 pair for `(token, lt)` [7](#0-6) . Anyone can permissionlessly call `IUniswapV2Factory.createPair` and then `IUniswapV2Pair.mint()` against that pair *before* the token graduates, seeding it with a self-funded, attacker-chosen `(reserveToken, reserveLT)` ratio and non-zero `totalSupply`. `_seedUniswapV2Direct` detects `totalSupply != 0` and routes to `_seedRebalancing` [8](#0-7) .

Inside `_seedRebalancing`:
1. If the pre-seed is "dust" on *both* sides (≤ `DIRECT_MINT_PRESEED_BPS` = 1 bp of the LP target on each side), the code deliberately accepts the small, bounded donation and calls `_seedDirectMint` [6](#0-5) .
2. Otherwise, it computes a rebalancing swap via `_pairRebalance`, which internally computes `_noFeeSwapInput` and the pair's fee-adjusted `getAmountOut` [2](#0-1) . If either value rounds to zero, `_pairRebalance` returns `false`, and the *same* `_seedDirectMint` fallback fires [3](#0-2) .

Crucially, `_seedDirectMint` performs a raw `IERC20.safeTransfer` of the entire `tokensForLP`/`ltFromPair` amounts to the pair and calls `IUniswapV2Pair(pair).mint(lpLock)` with no check on `totalSupply` [4](#0-3) . When `totalSupply != 0`, standard UniswapV2 `mint()` computes `liquidity = min(amount0 * totalSupply / reserve0, amount1 * totalSupply / reserve1)` — exactly the donation formula the whole "Regime 3" rebalancing mechanism was built to avoid, per its own natspec: "Without intervention `pair.mint(lpLock)`'s `min(amount0·S/r0, amount1·S/r1)` formula would (a) open the LP off curve-close-price and (b) donate the larger arm to the attacker's pre-existing LP" [9](#0-8) .

The rounding-to-zero condition that triggers this fallback is decoupled from the "dust" (≤1 bp) bound: it can occur when the pre-seeded ratio is already close to the curve-close target (so the required rebalancing swap `s` is tiny, or its fee-adjusted output floors to zero) even though the pre-seed's absolute size is well above the 1 bp dust threshold. An attacker can observe the bonding curve's live state (all pair reserves/`k`/`exchangeRate` are public) to closely predict the eventual `(tokensForLP, ltFromPair)` cached at `_enterGraduating`, and pre-seed the V2 pair at a ratio deliberately near — but not exactly — that target with a substantial absolute size, forcing `_pairRebalance` to return `false` and routing the deposit through the unguarded `_seedDirectMint`/`mint()` donation path.

### Impact Explanation
This produces the exact damage the surrounding hardening code documents as unacceptable: the graduation LP is minted through UniswapV2's `min()` formula against attacker-controlled reserves, which (a) opens the pool off the curve-close price and (b) donates the disproportionate arm of the protocol's `tokensForLP`/`ltFromPair` deposit to the attacker's pre-existing LP position, which is not subject to `LPLock` (only the newly-minted `liquidity` is locked via `LPLock.recordLock` — the attacker's original LP tokens remain freely withdrawable) [10](#0-9) . This is a direct value-extraction vector against the protocol's/creator's/traders' LT and tokens seeded at graduation, and results in an LP seeded away from the curve's true close price — both are explicitly listed as accepted, in-scope impacts.

### Likelihood Explanation
Reachable purely by an unprivileged wallet: creating and pre-seeding the HyperSwap V2 pair is explicitly a permissionless, in-scope entry point per the analysis rules, and `finalizeGraduation`/`_ensureUniswapV2Pair` never validate that the fetched pair is pristine beyond the totalSupply==0/dust checks already covered by other branches. The only requirement is timing the pre-seed ratio close enough to the eventual curve-close ratio to force the rounding-to-zero condition in `_pairRebalance`, which is a computable, observable quantity (the curve's reserves, `k`, and the LT's `exchangeRate()` are all public prior to the graduating trade), making this a realistically executable, not merely theoretical, attack.

### Recommendation
`_seedDirectMint` should never be invoked against a pair with non-zero `totalSupply` outside the explicitly-bounded `DIRECT_MINT_PRESEED_BPS` dust case. When `_pairRebalance` returns `false` for a non-dust pre-seed, the code should not silently fall back to a raw `mint()` — instead it should route through the same `min()`-donation-safe deposit used for the balanced case (`_routerDepositAndDispose`'s `addLiquidity`, which only pulls the optimal matched amounts) or explicitly re-verify that the rounding-to-zero condition also implies a bounded/negligible reserve size before falling back to direct mint.

### Proof of Concept
1. Attacker observes a curve token approaching graduation and computes the expected `(tokensForLP, ltFromPair)` ratio from the pair's live `getReserves()`/`k()` and the LT's `exchangeRate()` (all public views used identically inside `_prepareGraduationLiquidity` [11](#0-10) ).
2. Attacker calls the HyperSwap V2 factory's permissionless `createPair(token, lt)` (or lets `_ensureUniswapV2Pair` find it) and self-funds a `mint()` at a ratio close to, but slightly off from, the predicted target, sized well above `DIRECT_MINT_PRESEED_BPS` (1 bp) of the eventual `tokensForLP`/`ltFromPair`.
3. When the buy that crosses the graduation threshold lands, `_enterGraduating` caches `(tokensForLP, ltFromPair)` at the curve-close price [12](#0-11) .
4. Anyone calls `finalizeGraduation`; `_seedRebalancing` computes a rebalance swap whose fee-adjusted `getAmountOut` rounds to zero given the attacker's chosen near-target ratio, so `_pairRebalance` returns `false` [3](#0-2) .
5. `_seedDirectMint` transfers the full `tokensForLP`/`ltFromPair` to the pair and calls `pair.mint(lpLock)` against the attacker's non-empty pool, triggering UniswapV2's `min(amount0*S/r0, amount1*S/r1)` donation formula and minting the graduation LP off the curve-close ratio, with the excess value accruing to the attacker's un-locked pre-existing LP position [4](#0-3) .

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);

        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);

        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    function _seedDirectMint(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {
        IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
        IERC20(lt).safeTransfer(pair, ltFromPair);
        liquidity = IUniswapV2Pair(pair).mint(_s().lpLock);
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }
