### Title
Missing pair-existence check in `Router.buy` ignores the `factory.getPair` failure signal that `previewBuy`/`sell` both enforce - ([File: packages/contracts/src/Router.sol])

### Summary
`Router.buy` looks up the curve pair via `factory.getPair(token, asset)` and, unlike every sibling function in the same contract, never checks the zero-address failure signal before using it. This mirrors CVE-2017-1000460's root cause class: a call that signals failure (there, `init_get_bits`'s return value; here, `factory.getPair` returning `address(0)` for "no pair") is ignored, and the code proceeds to operate on the resulting invalid/uninitialized reference.

### Finding Description
In `Router.sol`, `sell`, `previewBuy`, and `getAmountOut` all guard the pair lookup: [1](#0-0) [2](#0-1) 

`Router.buy`, however, omits the identical check present in its siblings and immediately feeds the possibly-zero `pairAddr` into `_computeBuy`, then into `IPair(pairAddr).transferToken` / `.swap`: [3](#0-2) 

`_computeBuy` calls `IPair(pairAddr).getReserves()` and `.k()` unconditionally: [4](#0-3) 

If `pairAddr` is `address(0)` (or any address with no `Pair` code), these external calls hit an address with no contract code. A `staticcall`/`call` to an address with no code returns success with empty return data, and Solidity's ABI-decoding of the expected `(uint256, uint256)` / `uint256` tuple against empty bytes reverts. So today this specific gap degrades to a revert (DoS on that call), not a silent corruption — the crash is deterministic rather than a null-pointer style memory-safety issue as in the original CVE, because Solidity is memory-safe by construction (no analog of `get_ue_golomb` reading raw uninitialized memory).

### Impact Explanation
`Router.buy` is gated by `onlyRole(BONDING_ROLE)`, and the only holder of that role is `Bonding`. `Bonding.buy` already validates token existence via `info.creator == address(0)` before calling `router.buy`, and `Factory.createPair`/`ltFor` are written atomically at launch time, so `pairFor`/`ltFor` for any token that passed `Bonding`'s existence check will always resolve to a real pair. Under the current call graph, an unprivileged trader cannot reach `Router.buy` with a token whose pair is unregistered — the missing guard is dead code under existing invariants, not a live, unprivileged-reachable freeze or theft path.

### Likelihood Explanation
Low. The only way this gap becomes reachable is if a future code path calls `Router.buy` for a token whose `Factory` pair mapping was never populated (e.g., a new caller granted `BONDING_ROLE`, or a refactor that removes `Bonding`'s upstream `TokenNotTrading` gate). Under the current, audited call graph the check is unreachable, so there is no concrete unprivileged transaction sequence today that trips it.

### Recommendation
Add the same `if (pairAddr == address(0)) revert PairNotFound();` guard to `Router.buy` that already exists in `sell`, `previewBuy`, and `getAmountOut`, for defense-in-depth consistency and to close the gap against any future caller of `BONDING_ROLE` or refactor that removes the upstream `Bonding` existence check.

### Proof of Concept
Not exploitable today by an unprivileged address: `Router.buy` is `onlyRole(BONDING_ROLE)`, held only by `Bonding`, and `Bonding.buy`/`Zap.buy` both validate `tokenInfo[tokenAddress].creator != address(0)` before ever reaching `Router.buy`, which guarantees `factory.getPair` resolves to a real `Pair` for any token reachable through the public `Zap`/`Bonding` entry points. A PoC would require directly granting `BONDING_ROLE` to a test caller and invoking `Router.buy` with an unregistered `token` argument — a privileged-setup scenario, not a transaction an ordinary trader/creator can submit.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
