### Title
Webhook shop-domain identity spoofing via HMAC that covers only the raw body, not the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body via `Utils::HmacValidator.validate`, while the `shop` value used to identify the tenant is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in the signed bytes. This breaks the identity binding `hmac_signed_bytes == bytes_that_determine_the_tenant`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from an attacker-controllable header, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body and then forwards the unauthenticated `request.shop` value straight into the handler's `WebhookMetadata`: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further verification, and is the only tenant identifier delivered to the host application's handler: [4](#0-3) 

Because `HmacValidator.validate` (via `VerifiableQuery`) only checks `computed_signature == received_signature` over `to_signable_string` (the raw body), and the raw body never encodes the shop domain for the `Webhooks::Request` type (unlike `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly folds `shop` into the signed string): [5](#0-4) [6](#0-5) 

...an attacker who controls any shop that has this app installed (a normal, unprivileged install — no special permission needed beyond installing a free/dev app) legitimately receives real, correctly-signed webhook deliveries from Shopify for their own shop. Because the HMAC is computed with the merchant-agnostic `api_secret_key` over the body only, that exact `(body, hmac)` pair remains valid for **any** `shop` header value. The attacker can replay that captured `(body, hmac)` pair to the host application's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at the header), and the handler executes `data.shop == "victim-shop.myshopify.com"` with attacker-chosen body content believing it originates from the victim tenant.

The identity equality that should hold is:
`shop_bytes_verified_by_hmac == shop_value_delivered_to_handler`
but in this gem it is actually:
`hmac_covers(raw_body_only)` while `shop_value_delivered_to_handler = header("shop-domain")` (unauthenticated).

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker with access to their own (or any) shop's legitimate webhook stream can forge webhook events that a host application will attribute to an arbitrary other merchant/shop, because the gem hands the handler an unauthenticated `shop` value alongside a validated-but-shop-agnostic HMAC. Any host application that uses `WebhookMetadata#shop` (as documented/intended, and as exercised in this gem's own tests, e.g. asserting `data.shop`) to select which tenant's records to create/update/delete will act on forged data attributed to the wrong tenant — this is a cross-tenant access/data-integrity issue directly enabled by this gem's webhook verification API surface, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs the ability to install the app on a shop they control (a normal, unprivileged, self-service action for most Shopify apps) in order to capture a validly-signed `(body, hmac)` pair, and only needs to be able to POST an HTTP request with a custom `x-shopify-shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim shop is required.

### Recommendation
Bind the shop identity into the value that is cryptographically checked before it is trusted:
- Extend `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) to require that the resolved shop for a given webhook subscription/delivery matches an application-known, previously-registered shop (e.g., look up the webhook by `webhook_id` via the Admin API, or maintain a mapping of active installs and reject shops not in that set) before dispatching to the handler.
- At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as the sole tenant-selection key without cross-checking it against the app's own install/session records.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Shopify delivers a legitimate webhook to the attacker's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`
   - Body: `{"id": 1, ...}`
3. Attacker resends the identical body and HMAC to the host application's shared webhook endpoint but changes only the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `Webhooks::Request#hmac` and `#to_signable_string` compute the same signature check as before, because neither depends on the `shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-38`).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which returns `true`, and dispatches `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))`.
6. The host application's handler processes attacker-supplied data believing it is authentic data for `victim-shop.myshopify.com`.
