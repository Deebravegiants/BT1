Confirmed: `EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)` in `evm/src/core/EvmHost.sol` accept and lock a relayer fee, and record a commitment for any `post.dest` / `get.dest` value, with no validation that the destination `StateMachine` id is actually a chain Hyperbridge has a registered consensus client / route for.

### Title
Users can pay relayer fees to dispatch requests to an unsupported/unregistered destination `StateMachine`, permanently locking funds with no possible delivery - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` collect the caller's relayer fee (in native token via Uniswap swap, or directly in the fee token) and store a `FeeMetadata`/commitment keyed only on the request hash, without ever checking that `post.dest` (or `get.dest`) corresponds to a state machine for which a consensus client and relayer route actually exist.

### Finding Description
`dispatch(DispatchPost memory post)` [1](#0-0)  and `dispatch(DispatchGet memory get)` [2](#0-1)  both: (1) pull the fee from the caller (swapping native token or transferring `feeToken`), (2) build the request, (3) compute the commitment, and (4) store it in `_requestCommitments`. At no point do they validate `post.dest`/`get.dest` against the host's configured/whitelisted state machines or consensus clients (the whitelisting concept exists elsewhere, e.g. `testCanAddwhitelistedStateMachines` shows `HostParams.stateMachines` is used to add supported destinations [3](#0-2) , but this whitelist is not consulted inside `dispatch`).

This mirrors the reported Vault bug class exactly: the "deposit" (paying the relayer fee and escrowing the request) succeeds unconditionally, while the mechanism that is supposed to make the deposit useful (an actual relayer/consensus route capable of delivering the message to `dest`) may not exist at all — just as the Vault accepted LINK deposits with no plugin registered to generate yield.

### Impact Explanation
If a user (or an integrating application such as the Intent Gateway, Token Gateway, or HyperFungibleToken, all of which call `IDispatcher(host).dispatch(...)`) targets a `dest` state machine for which Hyperbridge has not yet configured a consensus client/relayer route (e.g., a typo'd chain id, a chain removed from the whitelist, or a chain not yet onboarded), the relayer fee is irrevocably collected and locked in the host contract with no relayer able to ever produce a valid consensus/state proof to deliver it. Because `dispatch` never reverts, this failure is silent — the caller only discovers the loss when the message never arrives and the timeout (if any was set) eventually refunds the fee; if `timeout == 0` ("no timeout... messages will never expire"), the fee is locked forever with no recovery path. This is a permanent freezing of relayer fee funds and a "route unable to deliver messages" per the explicit accepted-impact criteria.

### Likelihood Explanation
Likelihood is real but bounded: it doesn't require malicious intent — a benign integration bug, a chain being deprecated/removed from `HostParams.stateMachines` after requests were already designed for it, or governance not yet finishing onboarding a new chain are enough to trigger loss for any user who dispatches to that `dest`. Every unprivileged `dispatch` caller (end users of HyperFungibleToken/IntentGateway/any HyperApp, or a direct `IDispatcher` caller) can reach this path directly, with no special role required.

### Recommendation
Validate `post.dest`/`get.dest` inside `dispatch` (or in a common internal helper) against the host's known/whitelisted state machines (`HostParams.stateMachines` or an equivalent "has an active consensus client for this state machine" check) before collecting any fee, and revert with a clear error (e.g. `UnsupportedStateMachine()`) if the destination is not deliverable. This prevents fee collection for a message that can never be settled.

### Proof of Concept
1. Observe that `HostParams.stateMachines` is used by the host to track allowed/whitelisted destination state machines and that this list can be updated by governance (`updateHostParams`), i.e., a `dest` can become unsupported over time [3](#0-2) .
2. Call `dispatch(DispatchPost({dest: <arbitrary/unregistered StateMachine bytes>, fee: X, timeout: 0, ...}))`. As shown in `EvmHostForkTest.sol`, `dispatch` accepts arbitrary `dest` values and happily records the commitment and fee with no destination-support check [4](#0-3) .
3. Because `timeout` is `0` ("no timeout... Messages will never expire" per the docs), and no relayer/consensus client exists for `dest`, the fee `X` sits in the host forever with no way for the payer to reclaim it and no way for the message to be delivered.

Note: I could not fully verify, within the available context, whether any downstream component (e.g., a governance-controlled allow-list check elsewhere in the request lifecycle, or in `HandlerV2`) independently blocks dispatch to unsupported destinations before fee collection; the `dispatch` function itself, as read, performs no such check. A Devin session with full repository access could confirm whether any such guard exists elsewhere in the call path before this is escalated further.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
