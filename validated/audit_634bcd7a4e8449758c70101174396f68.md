### Title
Withdraw path in `IntentGatewayV2` (Tron) checks only call-success, not the ERC20 `transfer()` boolean return, causing escrow to be debited for tokens that were never actually delivered - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens with a raw low-level `.call()` to the token's `transfer` selector and only checks that the call itself did not revert (`success`). It never inspects the ABI-decoded boolean that `transfer()` returns. Some ERC20 tokens (including several whitelist/blacklist-gated stablecoin implementations) signal a failed transfer by returning `false` instead of reverting. In that case `success == true` even though no tokens moved, yet the code proceeds to permanently debit the escrow ledger as if the transfer succeeded — exactly the class of bug described in the referenced Gearbox report, where `totalValue`/accounting is updated on the assumption of a successful transfer that never actually completed.

### Finding Description
`withdraw()` releases escrowed order tokens to a beneficiary: [1](#0-0) 

For every ERC20 token, it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
```
`success` only reflects whether the external call reverted, not whether the token contract's internal `transfer()` logic returned `true`. Tokens that implement whitelist/blacklist restrictions by returning `false` (rather than reverting via `require`) will make this low-level call return `success = true` with an encoded `false` payload that is discarded. The function then unconditionally decrements `_orders[body.commitment][token]` and, if this is the last remaining amount, marks the order `_filled[body.commitment]` — even though the beneficiary received nothing.

The same pattern recurs in the `SweepDust` handler on the same contract: [2](#0-1) 

This is the identical bug class from the external Gearbox report: `_transferAssetsTo()` there advanced `totalValue`/`totalWeightedValue` regardless of whether the underlying token transfer to a blocked/whitelisted address actually succeeded, because the code trusted the call outcome rather than the true transfer result. Here, `_orders[...]` accounting (the escrow ledger backing user/solver funds) is likewise mutated as if the transfer succeeded.

Contrast this with the sibling (non-Tron) implementation in `IntentsBase.sol`, which correctly uses `SafeERC20.safeTransfer`, reverting the whole transaction (and therefore not touching escrow state) if the token's `transfer()` returns `false`: [3](#0-2) 

The Tron `withdraw()` function deliberately bypasses this safety net by using a raw low-level call and only gating on `success`.

### Impact Explanation
- `_orders[body.commitment][token]` is decremented and the order can be marked `_filled` even though the beneficiary never received the escrowed tokens. The tokens remain stuck in the `IntentGatewayV2` contract with no ledger entry pointing to them, and the beneficiary has no further path to reclaim them, since `withdraw()` is the only path that releases escrow and the commitment is now considered settled/filled.
- This is a permanent loss/freezing of user or solver funds for any token that returns `false` on a disallowed `transfer()` instead of reverting, whenever the recipient address happens to be blocked by that token's issuer.
- Reachable from the normal, unprivileged intent-fulfillment flow: `withdraw()` is invoked as part of settling `fillOrder`/cross-chain response handling and via `onGetResponse` after a relayer delivers a GET response proof, so a standard relayer-delivered message triggers the loss — no privileged role is required.

### Likelihood Explanation
Requires only that (a) one of the escrowed input/output tokens is a whitelist/blacklist-style token that signals failure by returning `false` rather than reverting, and (b) the beneficiary address is blocked by that token's off-chain compliance mechanism (a state fully outside Hyperbridge's control, but plausible for any long-lived cross-chain intents system handling regulated stablecoins). Given Hyperbridge explicitly targets USDC/USDT-class assets (see `HyperFungibleToken`/`TokenGateway` docs), encountering such a token is realistic, and the trigger condition (a blocked beneficiary at withdrawal time) is entirely outside the protocol's control and can occur at any point after an order is placed.

### Recommendation
Replace the raw `.call()` + `success`-only check in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer` (as already done in `IntentsBase.sol`), so a `false` return value reverts the entire transaction and the escrow ledger is never mutated for a transfer that did not actually happen. If a revert-free failure path is required for operational reasons, decode and check the boolean return value explicitly before mutating `_orders[...]`, and avoid updating `_filled`/deducting escrow unless the transfer is confirmed successful.

### Proof of Concept
1. Escrow a token `T` in `IntentGatewayV2` (Tron) for order commitment `C`, where `T.transfer()` returns `false` (does not revert) when the recipient is blacklisted.
2. Blacklist the intended beneficiary `B` on token `T` (an action fully controlled by `T`'s issuer, independent of Hyperbridge).
3. Trigger settlement so `withdraw(body, ...)` is called with `beneficiary = B`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, B, amount))` returns `(true, encodedFalse)`; `success` is `true`, so the `revert TransferFailed()` guard is skipped.
5. `_orders[C][T] -= amount` executes, and (if this was the last token) `_filled[C] = B` is set, permanently marking the order as settled.
6. `T.balanceOf(address(intentGateway))` still holds `amount`, but no ledger entry references it — the funds are stranded and unrecoverable through the contract's normal paths.
