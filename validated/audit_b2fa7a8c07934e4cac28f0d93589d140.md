## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` value that is handed to the app's webhook handler (and typically used as the tenant/session key to look up which shop's data/session to act on) comes from the `X-Shopify-Shop-Domain` header, which is never included in the signed content. Anyone who can obtain one validly-signed webhook body (e.g., a merchant who has the app installed and therefore legitimately receives webhooks for their own shop) can replay that same body/HMAC pair while substituting a different `shop-domain` header, and the gem will accept it as an authentic webhook for the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature only from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns just the raw JSON body: [2](#0-1) 

But `Request#shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never mixed into the signed bytes: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately trusts `request.shop` (from the unauthenticated header) when constructing the metadata passed to the app's handler: [4](#0-3) 

This is exactly the pattern called out by the analog rules: *bytes verified* (raw body via HMAC-SHA256, keyed with the app's `client_secret`) *versus bytes parsed* (the `shop-domain` header), where the header is the field host applications use as the tenant identity/session key but it carries no cryptographic binding to the signature.

Because a single app `client_secret` is shared across every shop that installs the app, any merchant who legitimately installs the app receives real webhooks—each with a valid HMAC computed only over that specific body. That merchant can capture one such `(body, hmac)` pair and resend it to the app's webhook endpoint with the `shop-domain` header changed to a different (victim) shop's domain. `HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This breaks the identity binding `shop authenticated (by HMAC) == shop used as tenant key`, allowing a shop that has installed the app (an ordinary, unprivileged tenant, not the target) to inject arbitrary attacker-controlled webhook payloads that the host application will process as if they originated from a different shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up sessions/access tokens or update tenant-scoped records), this is a cross-tenant data-integrity/cross-tenant access issue — one tenant can forge events attributed to another tenant without needing that tenant's credentials or the app's `client_secret`.

### Likelihood Explanation
Any user can install a public app on a shop they control and thereby obtain at least one legitimately-signed webhook body/HMAC pair for that body. No access to the app's `client_secret`, target shop credentials, or privileged access is required — only the ability to send an HTTP request to the app's public webhook endpoint with modified headers, which is a normal capability of an unprivileged internet-reachable actor.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or otherwise cryptographically bind the header-derived shop to the verified payload before it is trusted. Since Shopify itself signs webhooks only over the raw body per its API contract, the safer mitigation within this gem is to require host applications to cross-check `request.shop` against an independently known/expected shop (e.g., the shop tied to the session/webhook registration) rather than trusting the header value outright, and to document this gap prominently in `Registry.process`.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (attacker's own shop) so the app registers webhooks and the attacker's shop receives real webhook deliveries.
2. Capture one incoming webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H` is a valid HMAC of `B` under the app's shared `client_secret`.
3. Replay a POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks `B` against `H`), and `ShopifyAPI::Webhooks::Registry.process` calls the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's shop.
