### Title
Webhook `shop-domain` and `topic` headers are trusted by `Webhooks::Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never included in the HMAC computation [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` and then unconditionally trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Finding Description
This mirrors the DODO bug class: a security check (HMAC/`approve`) is unconditionally applied to only part of the relevant data, while another field that is acted upon (`fromToken` / here, `shop`-domain header) is not covered by that check. The binding that should hold is:

`bytes authenticated by HMAC == bytes used to identify the tenant (shop) and route the event (topic)`

but the actual code produces:

`bytes authenticated by HMAC (raw_body only)` ≠ `bytes trusted for tenant identity (shop-domain / topic headers)`

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined as `@raw_body` only [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are parsed straight from headers with no cryptographic binding to the signature [2](#0-1) . Yet `Registry.process` treats a passing HMAC check as sufficient authentication for the entire request, including these header-derived fields, and forwards `request.shop` directly into `WebhookMetadata` given to the app's handler [3](#0-2) .

Because the app's client secret used to sign webhooks is shared across all shops that install a public app, any unprivileged internet user who can install the same app on their own development/test store can legitimately trigger a webhook and obtain a genuine `(raw_body, hmac)` pair. Since headers are excluded from the signed content, that same valid `(raw_body, hmac)` can be replayed to the victim app's webhook endpoint with an altered `x-shopify-shop-domain` header (and/or `x-shopify-topic`), and `HmacValidator.validate` will still return `true`, because only the body bytes are checked, not the header claiming which shop/topic the event belongs to.

### Impact Explanation
This breaks the tenant-identity binding the HMAC check is presumed to establish. A host application whose webhook handlers key their state, session lookups, or actions off `WebhookMetadata#shop` (as is standard and encouraged usage of this API) can be made to process an attacker-controlled body under an arbitrary victim `shop` value, since the gem asserts "Invalid webhook HMAC" only fails on body tampering, not header spoofing. This is a cross-tenant identity-binding break consistent with the required Critical impact category (cross-tenant access) in the rules, since the `shop` value used to key handler state is unauthenticated even though the API surface (`Registry.process` raising `InvalidWebhookError` on HMAC failure) implies the whole request has been authenticated.

### Likelihood Explanation
Requires only: (1) ability to install the same public app on any shop (self-service, unprivileged), which grants a legitimately-signed webhook payload, and (2) ability to POST an HTTP request directly to the app's public webhook endpoint with modified headers — both are attacker capabilities available to any internet user with no special credentials. This does not require the `client_secret`, an access token, or any privileged account.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signable content verified by HMAC, or have `Registry.process` cross-validate `request.shop`/`request.topic` against an out-of-band trusted source (e.g., an installed-shop registry) before constructing `WebhookMetadata`. At minimum, document that `shop`/`topic` from `Webhooks::Request` are not cryptographically bound to the HMAC and must be independently corroborated by the host application before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target public app on their own development shop `attacker.myshopify.com` and triggers any webhook topic (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify computed with the app's shared `client_secret`.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) [1](#0-0)  — it matches, since the body was untouched.
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [5](#0-4) , where `shop` is now `victim-shop.myshopify.com` despite the payload actually originating from the attacker's own shop — the app processes attacker-controlled data under the victim's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
