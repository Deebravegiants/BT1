Found a valid analog: the Tron deployment of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) uses an unfixed, cruder version of `placeOrder`'s protocol-fee/predispatch accounting compared to the hardened EVM version (`evm/src/apps/IntentGatewayV2.sol`), and the same file also lacks the reentrancy and rounding-dust protections that were explicitly fixed in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`.

### Title
Predispatch dust accounting understates escrow debit vs. actual token pull, allowing escrow shortfall in `IntentGatewayV2.placeOrder` (Tron deployment) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of the Intent Gateway, `placeOrder`'s predispatch branch computes `dust = balance - requiredAmount` and credits escrow with only `reducedInputs[i].amount` (the fee-reduced amount) via `_orders[commitment][token] += reducedInputs[i].amount;` [1](#0-0) , while the mainline EVM contract instead measures actual received balance deltas and mutates `order.inputs[i].amount` to the true received amount before computing fees and commitment [2](#0-1) . The Tron path never re-measures what the gateway actually received after the predispatch call executes calldata that can move tokens off-path (e.g., unwrapping to a fee-on-transfer token, or a token whose `transfer` yields less than the nominal `balance` snapshot read at call time). This creates an accounting mismatch between the escrow bookkeeping (`_orders` mapping) and the real token balance the gateway can pay out on fill/cancel.

### Finding Description
The audited/fixed EVM `IntentGatewayV2.placeOrder` snapshot-and-diff pattern (`balancesBefore[i]` vs. post-sweep balance) exists specifically to make the escrowed amount match the tokens the gateway can actually redeem, accounting for fee-on-transfer tokens and calldata side effects [3](#0-2) . The Tron contract's predispatch branch instead trusts `IERC20(token).balanceOf(dispatcher)` read once after the arbitrary predispatch call, computes `dust` against the order's nominal `requiredAmount`, and credits escrow using `reducedInputs[i].amount` derived from the *pre-dispatch* `order.inputs[i].amount`, never validating that this reduced amount is actually backed by tokens delivered to `address(this)` [4](#0-3) . If the predispatch calldata (arbitrary, dispatcher-executed, attacker-supplied via `order.predispatch.call`) routes through a token whose final transfer to the gateway yields less than `balance` measured mid-flow — or if reentrant/multi-hop calls change balances between the `balance` read and the `transferCalls` execution — the gateway credits `_orders[commitment][token]` with an amount unbacked by its real balance, producing a solvency shortfall that manifests when any order later fills, is cancelled, or a subsequent unrelated order's escrow is drained from the same pooled token balance.

### Impact Explanation
This is a fund-accounting flaw reachable by any unprivileged user placing an order (`placeOrder` is a public, unprivileged entry point taking arbitrary `predispatch.call` calldata routed through the `CallDispatcher`). A confirmed shortfall between the sum of `_orders[...]` escrow entries and the gateway's real token balance means legitimate later withdrawals (`_withdraw`) can fail or drain funds belonging to other users' orders — the same class of "vault accounting drift causing insolvent redemptions" that caused the cited Solv Protocol BRO Vault loss. Given the Intent Gateway pools all users' escrowed tokens per-token-address rather than per-vault, a shortfall introduced by one malicious order corrupts shared solvency for all orders in that token.

### Likelihood Explanation
Medium-High: the attack only requires crafting an `order.predispatch.call` (arbitrary calldata dispatched via `ICallDispatcher`) that manipulates the dispatcher's or gateway's token balance between the vulnerable `balance` read and the final "credit reducedInputs[i].amount" step — achievable with any fee-on-transfer, rebasing, or reentrant ERC-20, all of which the fixed mainline contract explicitly defends against with balance-delta measurement.

### Recommendation
Port the balance-before/balance-after delta measurement from `evm/src/apps/IntentGatewayV2.sol` (lines 260-311) into the Tron contract's `placeOrder` predispatch branch: snapshot `address(this)` balances before the sweep, compute `received` after, mutate `order.inputs[i].amount` (or an equivalent reduced-input variable) to the true received amount, and only then compute and credit the protocol-fee-reduced escrow amount from that verified value.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer or reentrant token registered as an input.
2. Call `placeOrder` with `predispatch.call` set to a benign-looking calldata sequence that causes the dispatcher's token balance, when finally `transfer`'d to the gateway, to deliver less than the `balance` value read at line 424/428 (e.g., a token that burns/taxes on the *dispatcher→gateway* leg specifically, distinct from the *user→dispatcher* leg already taxed).
3. Observe `_orders[commitment][token]` credited with `reducedInputs[i].amount` computed from the nominal `order.inputs[i].amount`, exceeding the gateway's actual received balance for that token.
4. Fill or cancel enough orders sharing that token to demonstrate a later legitimate withdrawal reverting or another user's escrow being paid from misattributed balance.

**Caveat:** I was only able to verify this discrepancy by diffing the Tron contract against the hardened mainline `evm/src/apps/IntentGatewayV2.sol`; I could not confirm whether the Tron deployment is actually in-scope/production-deployed versus a legacy/unused variant, since the wiki and search results did not surface deployment status for `evm/tron/`. If Tron is out of scope, no other unpatched analog to the Solv-style vault accounting bug was found — the same-chain (`IntrinsicIntents.sol`) and cross-chain (`ExtrinsicIntents.sol`) intent-fill paths contain equivalent accounting logic, but all previously identified rounding-dust, reentrancy-theft, and native-ETH-surplus accounting bugs in those files have already been fixed and are covered by regression tests (`IntentGatewayV2SameChainTest.sol`, `IntrinsicIntentsReentrancyTest.sol`).

            // Build sweep calls and snapshot gateway balances before the sweep.
            Call[] memory transferCalls = new Call[](inputsLen);
            uint256[] memory balancesBefore = new uint256[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                if (order.inputs[i].amount == 0) revert InvalidInput();
                address token = address(uint160(uint256(order.inputs[i].token)));
                uint256 requiredAmount = order.inputs[i].amount;

                if (token == address(0)) {
                    uint256 balance = address(dispatcher).balance;
                    if (balance < requiredAmount) revert InsufficientNativeToken();
                    transferCalls[i] = Call({to: address(this), value: balance, data: ""});
                    balancesBefore[i] = address(this).balance;
                } else {
                    uint256 balance = IERC20(token).balanceOf(dispatcher);
                    if (balance < requiredAmount) revert InvalidInput();
                    transferCalls[i] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    balancesBefore[i] = IERC20(token).balanceOf(address(this));
                }

                unchecked {
                    ++i;
                }
            }

            ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls));

            // Measure actual received, emit dust for excess, update order.inputs.
            for (uint256 i; i < inputsLen;) {
                address token = address(uint160(uint256(order.inputs[i].token)));
                uint256 received;
                if (token == address(0)) {
                    received = address(this).balance - balancesBefore[i];
                } else {
                    received = IERC20(token).balanceOf(address(this)) - balancesBefore[i];
                }

                if (received > order.inputs[i].amount) {
                    uint256 dust = received - order.inputs[i].amount;
                    emit DustCollected(token, dust);
                } else {
                    order.inputs[i].amount = received;
                }

                unchecked {
                    ++i;
                }
            }
