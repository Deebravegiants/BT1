## Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that are handed to the application's webhook handler are taken directly from unauthenticated HTTP headers and are never included in the signed data, breaking the binding `hmac(secret, signable_string) == hmac(secret, raw_body)` where `signable_string` should equal `raw_body + shop + topic` but instead equals `raw_body` alone.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Registry.process` validates the request with `Utils::HmacValidator.validate(request)`, which computes the HMAC only over `to_signable_string` (i.e., the raw body) and compares it with the `hmac` header: [2](#0-1) 

After this single check passes, `process` immediately trusts `request.shop` and `request.topic`, both parsed straight from headers, and forwards them to the app's handler as the tenant identity for the event: [3](#0-2) 

`Request#shop` and `Request#topic` read the `shop-domain`/`topic` headers with no cryptographic tie to the body that was actually signed: [4](#0-3) 

Because the app's `client_secret` (used to compute the webhook HMAC) is a single value shared by the app across **all** installing shops, and the signed material excludes `shop`, any two webhook deliveries with the same JSON body produce the same valid HMAC. An attacker who can obtain one genuinely-signed webhook body/HMAC pair from Shopify — trivially available to them as the operator of their own shop installing the app — can replay that exact body while relabeling the `shop-domain` (and/or `topic`) header to point at a different, victim shop. `HmacValidator.validate` will report success because it only checks the body against the shared secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

This is the direct analog of the "Eleven Finance doesn't burn shares" bug class: an action (crediting/acting on an identity) is executed based on a field that was never checked by the guarding mechanism (the HMAC "burn" check only covers `raw_body`, not `shop`), so the state transition (attribution to shop X) can diverge from what was actually authorized.

### Impact Explanation
This allows cross-tenant confusion/spoofing: an attacker-controlled or replayed webhook payload can be attributed to an arbitrary victim `shop` value that the gem never authenticates. Any host application that trusts `WebhookMetadata#shop` (as the gem's own documentation and examples direct apps to do, e.g. to look up which shop's session/access token to act on) can be tricked into processing an event — such as `app/uninstalled`, `shop/update`, or a billing/subscription topic — under the wrong tenant's identity, without the attacker needing that victim's credentials. This matches the "cross-tenant access" Critical impact category, since the trust boundary crossed is exactly the shop identity binding the gem is responsible for asserting via HMAC.

### Likelihood Explanation
Likelihood is high for any application accepting webhooks through this gem's `Registry.process`/`Request` path: the attacker only needs one legitimately-signed webhook (obtainable by installing the target app on a shop they control, which is an unprivileged action available to any internet user who can install a public app) and the ability to POST to the app's public webhook endpoint with a modified `shop-domain` header — no access token, `client_secret`, or victim credentials are required.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signed material verified against the HMAC, or otherwise cryptographically bind them before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document/enforce that host applications must independently verify that the resolved shop actually has an active session/install matching the webhook's claimed shop before acting on it, and that `to_signable_string` cannot be considered a full authentication of the request's headers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and captures a legitimately delivered webhook: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because the app's shared `client_secret` was used to sign `B`).
2. Attacker sends a POST to the app's webhook endpoint with the exact same body `B` and HMAC header `H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com` and, if desired, a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` only returns `B`, the HMAC check passes.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", ...)` and calls the app's handler, which now acts as though the event originated from the victim shop, even though nothing about `shop` was ever verified. [3](#0-2) [5](#0-4)
