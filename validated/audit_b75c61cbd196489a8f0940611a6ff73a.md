### Title
Output-token duplicate check compares raw `bytes32` while fill/escrow logic truncates to `address`, allowing collision bypass of duplicate-output protection - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` rejects duplicate output tokens by hashing the *raw* `bytes32` value of `order.output.assets[i].token` into transient storage, but every downstream consumer of that same field (fill accounting, escrow, dust handling) decodes it via `address(uint160(uint256(token)))`, truncating to the low 160 bits. A user fully controls the `bytes32` encoding of `order.output.assets[i].token` (it is part of the order struct hashed into the commitment), so two entries that differ only in the unused upper 96 bits will be treated as distinct by the dedup check yet resolve to the identical ERC20 `address` everywhere else, defeating the guard that was specifically added to stop repeated output legs from sharing one accounting bucket.

### Finding Description
In `placeOrder`, the duplicate-output-token guard operates on the full 32-byte field: [1](#0-0) 

Meanwhile, every place that actually interprets a `TokenInfo.token` field — including the input side of the very same function — truncates it to an `address` by discarding the upper 96 bits: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Nowhere in `placeOrder` is `order.output.assets[i].token` validated to have zeroed upper 96 bits (i.e., to be a properly left-padded address). Because the commitment (`keccak256(abi.encode(order))`) is computed over the raw struct, a user (the order placer) can freely choose non-zero upper bits for one of two output legs targeting the same real token address, e.g.:

- `assets[0].token = bytes32(uint256(uint160(address(dai))))`
- `assets[1].token = bytes32(uint256(uint160(address(dai))) | (uint256(1) << 200))`

These are different 32-byte values, so the transient-storage loop at line 200-207 does **not** flag them as duplicates and `placeOrder` succeeds. The purpose-built regression test in the repo demonstrates exactly why this check exists — to prevent "same-chain partial fills [from] prematurely finaliz[ing] repeated output legs" because they "share one `_partialFills` bucket": [7](#0-6) 

Since the dedup check is bypassed via the truncation collision, an order with these two "distinct" (by the check) but colliding (by real semantics) output legs proceeds to fill/settlement, where the truncated `address` is used for all per-leg accounting (escrow buckets, dust/­surplus computation, and — per the test file's own commentary — `_partialFills`). This reintroduces the exact double-accounting/duplicate-bucket condition the guard was written to prevent, purely because the guard's key type (`bytes32`) doesn't match the semantic key type (`address`) used everywhere else.

### Impact Explanation
This breaks an integrity invariant the protocol explicitly relies on: that each output leg of an order references a distinct token for independent escrow/partial-fill accounting. An attacker who places an order with colliding output tokens can force two logically-identical-token legs to alias into the same underlying per-token state (partial-fill bucket / escrow release accounting) while bypassing the check meant to prevent it, which — per the accompanying regression test description — leads to premature/incorrect finalization of repeated output legs and incorrect release/accounting of escrowed funds. This is a fund-accounting integrity issue in the reachable, unprivileged order-placement/fill path of `IntentGatewayV2`.

### Likelihood Explanation
High likelihood of exploitability: `order.output.assets[i].token` is entirely attacker-controlled input to `placeOrder`, which is called directly by any unprivileged user placing an intent. No special permissions, timing, or governance are required — only crafting a `bytes32` value with non-zero upper 96 bits pointing at the same 20-byte address as another leg.

### Recommendation
Make the duplicate-token check operate on the same semantic key used everywhere else in the contract: normalize `order.output.assets[i].token` to its truncated `address` (as done at lines 240/265/293/347/365) before using it as the transient-storage dedup key, and additionally validate that the upper 96 bits of every `bytes32` token field are zero (reverting with `InvalidInput` otherwise) so that a single canonical encoding is enforced for every token reference in the order, matching the fix pattern (`abi.encodePacked`/canonical encoding) recommended for the analogous `HardVault` issue.

### Proof of Concept
1. Construct `order.output.assets` with two entries for the same real token (e.g. DAI):
   - `assets[0].token = bytes32(uint256(uint160(address(dai))))`
   - `assets[1].token = bytes32(uint256(uint160(address(dai))) | (uint256(1) << 200))`
2. Call `placeOrder(order, graffiti)`. The transient-storage loop in `placeOrder` (lines 197-221) compares the raw `bytes32` values, finds them distinct, and does **not** revert with `InvalidInput`, unlike the existing `testRevert_PlaceOrder_DuplicateOutputTokens` regression test which uses two identical `bytes32` values and correctly reverts.
3. During `fillOrder` → `_fillSameChain`/`_fillCrossChain`, both output legs are decoded via `address(uint160(uint256(token)))`, both resolving to `address(dai)`, causing both legs to reference the same underlying per-token accounting bucket — the exact "shares one `_partialFills` bucket" scenario the duplicate-output test suite is designed to prevent, but which is bypassed here due to the type mismatch between the dedup check and the downstream accounting key.
