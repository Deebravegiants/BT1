### Title
Webhook HMAC Only Covers Raw Body, Allowing Shop-Domain Header Spoofing for Cross-Tenant Confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, omitting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers from the HMAC-signed content. `Registry.process` validates only the body-derived HMAC, then trusts `request.shop` (read directly from the unsigned header) to identify which merchant/tenant the webhook belongs to when invoking the handler.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, raw_body + shop_domain)` and `shop_used_by_handler == authenticated_shop_domain`. In this implementation, the binding is broken: `hmac == HMAC(secret, raw_body)` only, while `shop_used_by_handler == unauthenticated header value`.

- `Request#to_signable_string` returns `@raw_body` exclusively: [4](#0-3) 
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the signed content: [5](#0-4) 
- `HmacValidator.validate` calls `verifiable_query.to_signable_string`, so it only re-computes and compares HMAC over the body — the shop-domain header is never included in what's authenticated: [3](#0-2) 
- `Registry.process` validates the HMAC, then immediately uses `request.shop` (the unauthenticated header) to build `WebhookMetadata` passed to the app's handler, which is where merchant-specific data routing/lookups typically occur: [6](#0-5) 

Because all shops using a given app share the same `client_secret` (there is one API secret key per app, not per shop), any merchant who has legitimately installed the app receives real webhooks with a valid HMAC computed over their own body. Since the HMAC never binds the body to a specific shop domain, that same (body, hmac) pair remains valid when replayed with an arbitrary `shop-domain` header value, because the validator only recomputes the HMAC over the raw body and never checks whether the header content matches what was signed.

### Impact Explanation
This breaks the tenant-isolation boundary the HMAC is meant to enforce: `authenticated_shop == shop_used_for_processing`. An app relying on `WebhookMetadata#shop` (from `request.shop`) to select which tenant's data to update, or to key merchant-specific de-duplication/state, can be made to process a webhook while believing it originates from a different (victim) shop, since the shop-domain field carries no authenticity guarantee under this HMAC scheme. This is a cross-tenant data confusion vector reachable by any user who can get a legitimate webhook delivered to their own store (i.e., any merchant able to install the app), without needing the `api_secret_key`, an access token, or any other privileged credential — they simply reuse an HMAC that Shopify already computed and sent to them.

### Likelihood Explanation
Likelihood is high for apps that trust `WebhookMetadata#shop` for any tenant-scoped action, since `Registry.process` unconditionally forwards this unauthenticated field to the handler right after a successful HMAC check that never covered it. Any install of the app by an unprivileged merchant grants them a stream of validly-signed (body, hmac) pairs that can be replayed with a forged `shop-domain` header to the webhook endpoint.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the HMAC-signed content, e.g. change `to_signable_string` to combine the raw body with the shop-domain header value (and other identifying headers) before hashing, and update `HmacValidator`/webhook senders' expectations accordingly. At minimum, document that `WebhookMetadata#shop` is not cryptographically authenticated by this gem, and require host applications to cross-check the delivered shop against session-derived state — but since the gem's own `Registry.process` presents this field as validated, this needs a code fix rather than a documentation note.

### Proof of Concept
1. Attacker registers/installs the target app on their own store `attacker.myshopify.com`, receiving legitimate webhooks (e.g., `orders/create`) signed by Shopify with the app's single shared `client_secret`.
2. Attacker captures one such delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H == HMAC(secret, B)`).
3. Attacker crafts a new HTTP POST to the app's webhook endpoint using the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this succeeds because the shop-domain header was never part of the signed content.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, believing the payload legitimately originated from `victim.myshopify.com`, even though it was forged by the attacker using data from their own store.
