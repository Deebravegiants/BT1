This confirms the finding. The gem's documentation itself instructs developers to trust `data.shop` as the tenant identifier (`docs/usage/webhooks.md:26` shows `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while the HMAC computation only covers the raw body.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then blindly trusts the `shop` value taken from the `X-Shopify-Shop-Domain` HTTP header — a field that is never included in the HMAC-signed payload. Any party who can obtain one validly-signed webhook body/HMAC pair (trivially available by installing the app on their own store and receiving a real webhook) can replay that exact body and signature to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, causing the app to process the (attacker-controlled) event as if it originated from the victim tenant.

### Finding Description
The equality the library is supposed to preserve is:
`shop value trusted by the handler == shop value cryptographically bound to the signed payload`

This equality is broken:

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop` is read straight from an HTTP header, entirely outside the signed material: [2](#0-1) 
- `HmacValidator.validate` computes/compares the HMAC only over `verifiable_query.to_signable_string`, i.e. the body, never the headers: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately forwards `request.shop` — the unauthenticated header value — into the handler as the tenant identity, with no independent check that this shop matches anything about the verified body: [4](#0-3) 

Because HMAC-SHA256 only authenticates the bytes it is computed over (the raw body), and the shop domain is carried in a header that is never part of that computation, the `shop` field is *acted on* (passed to the handler, and per the gem's own documented pattern, used as a tenant/shard key for job queues and storage) *without being covered by the HMAC*. This is exactly the "field acted on but not covered by the HMAC" binding break: an unprivileged internet user needs no secret to forge this — they only need one legitimately-signed webhook body from their own (attacker-owned) shop, which Shopify sends them automatically for events on their own store.

### Impact Explanation
This enables cross-tenant confusion at the application layer: an attacker-controlled webhook payload (fully attacker-influenced content, since it originates from their own store) can be delivered to the merchant application labeled with an arbitrary victim `shop` domain. Per the gem's own webhook documentation, `data.shop` is meant to be used to route/queue/store webhook data per-tenant (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so downstream host applications that follow the documented pattern will process attacker payloads under a victim shop's identity — e.g., writing attacker-controlled data into the victim's tenant records, dispatching background jobs scoped to the victim shop, or triggering data mutations keyed by `shop`. This matches the "cross-tenant access" high-impact category.

### Likelihood Explanation
Low-to-moderate: exploitation requires the attacker to install the target app on their own store (or otherwise be a legitimate merchant of the app) to receive one authentic, HMAC-signed webhook, and to know/guess the app's webhook endpoint. No secrets, tokens, or privileged access are required — this is achievable by any unprivileged user who can install the app, which for public apps is the entire internet.

### Recommendation
Bind the shop identity to the signed payload before trusting it:
- Include the `shop` (and ideally `topic`, `webhook_id`) values in the HMAC signable string alongside the raw body, matching Shopify's actual signing scheme where possible, or
- Cross-check the header-derived `shop` against a shop value embedded in the verified JSON body (when available for the topic), and reject the webhook if they disagree, or
- At minimum, document prominently (and enforce in `Registry.process`) that host applications must independently verify that the `shop` domain reported in `WebhookMetadata` corresponds to a shop with an active, expected registration for that specific webhook subscription (e.g. by tracking webhook IDs per shop) rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers an event (e.g. creates an order) to receive a real, Shopify-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs to the app's public webhook endpoint with the exact same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes the HMAC of `B` and it still matches `H` (see `lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`), because the shop header was never part of the signed material.
4. `Registry.process` passes validation and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...))` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host application to process attacker-controlled content as an authentic event from `victim.myshopify.com`.
