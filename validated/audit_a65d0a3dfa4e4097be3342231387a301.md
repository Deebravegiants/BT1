The `shop` value in `ShopifyAPI::Webhooks::Request` is read directly from an HTTP header, while the HMAC signature only covers the raw request body, creating exactly the "field acted on but not covered by the HMAC" pattern called out in the rules.### Title
Webhook `shop` identity is not covered by HMAC verification, allowing cross-tenant shop-domain spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, but its `to_signable_string` only returns the raw HTTP body, while the `shop` (tenant identity) is read from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, which is never part of the signed material. `Registry.process` trusts `request.shop` as the tenant identity when dispatching the webhook to the app's handler, without that value being bound to the HMAC signature that supposedly authenticates the request.

### Finding Description
`Registry.process` validates authenticity via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares an HMAC computed over that string against the `hmac` value: [1](#0-0) 

`to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop` (the identity used to route the webhook to a tenant) is pulled straight from an HTTP header that is completely outside the signed data: [3](#0-2) [4](#0-3) 

This value is then forwarded, unverified, to the host application's handler as the authoritative tenant identifier: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop_authenticated_by_HMAC == shop_used_for_tenant_routing`. In this implementation that equality does not hold — the HMAC only certifies the *body bytes*, not the *header-derived shop*. An attacker who is themselves a legitimate (unprivileged) merchant with the app installed on their own store receives genuine, correctly-signed webhook deliveries from Shopify for their own shop. Because the header is not part of the signed payload, they can replay that exact request (identical body, identical valid HMAC) while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still pass (it never inspects the header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop, while carrying data/body content the attacker fully controls (their own shop's webhook payload).

### Impact Explanation
This is a cross-tenant identity-spoofing vector: an unprivileged internet user (any merchant able to install the target app on their own free/dev store) can cause the app's own webhook processing pipeline to attribute a webhook body/topic to an arbitrary victim `shop` domain, without ever needing the app's `client_secret`, access token, or any elevated privilege. Downstream consequences depend on how the host app uses `WebhookMetadata#shop` (e.g., writing/updating merchant records, GDPR data-request/redact flows, billing/webhook-driven state transitions) — any app that trusts `shop` from this struct to select which tenant's data to mutate is exposed to cross-tenant data corruption or unauthorized actions performed against another merchant's account.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is that the attacker install the target Shopify app on a shop they control (trivial, unprivileged, requires no credential theft) and be able to receive at least one genuine webhook delivery, then replay it with a modified header — both are well within reach of any external actor and require no interaction with the app's secret key or TLS interception.

### Recommendation
Bind `shop` (and other routing-critical identifiers such as `topic`, `api_version`, `webhook_id`) to the HMAC-verified material, e.g., by validating that the header-derived `shop` matches an independently-known/authorized shop for the given webhook subscription, or by requiring the host application to cross-check `WebhookMetadata#shop` against a previously stored, trusted mapping (e.g., the shop associated with the webhook subscription ID) before acting on it. At minimum, document prominently that `shop` in `WebhookMetadata` is unauthenticated header data and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`) to the app's endpoint. Shopify signs the request with `X-Shopify-Hmac-Sha256` computed over the raw body using the app's real `client_secret` — the attacker does not need to know the secret; they just capture the resulting valid request.
2. Attacker replays the exact same HTTP request (identical body, identical `X-Shopify-Hmac-Sha256` header) but changes the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` then `Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `to_signable_string` (`@raw_body` only) and it matches, since the body was untouched — [2](#0-1)  and [7](#0-6) .
5. `Registry.process` calls the app's `handler.handle` with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` now returns `"victim-shop.myshopify.com"` — [5](#0-4)  and [3](#0-2) .
6. The app processes attacker-controlled webhook data believing it originates from the victim shop, despite the signature only ever certifying the attacker's own body.
