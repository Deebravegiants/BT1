Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header fields are trusted by the handler without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating that the HMAC of the raw request body matches the app's `client_secret`. However, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read straight from HTTP headers, which are never included in the signed material, and `shop` (the tenant identifier) is handed unchecked to the app's `WebhookHandler`. This breaks the identity binding `HMAC-authenticated bytes == bytes the handler treats as tenant-scoped`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining: [1](#0-0) 
i.e. `to_signable_string` returns only `@raw_body`. `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over exactly that signable string and compares it to the `hmac` header: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers that are completely outside the signed payload: [3](#0-2) 

`Registry.process` verifies only the HMAC of the request, then immediately forwards the unverified `request.shop` (and other header-derived fields) to the handler as the authoritative tenant identity: [4](#0-3) 

The `WebhookMetadata` struct that the handler receives has no independent verification of `shop`: [5](#0-4) 

Because the HMAC secret (`client_secret`) is per-app, not per-shop, it is identical across every merchant that has installed the app. Any actor who can obtain one validly-signed `(raw_body, hmac)` pair for the shared secret — for example by installing the app on their own development/test store and capturing a genuine webhook delivery — can replay that same body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because the signature check never inspects the shop header, so `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim shop of the attacker's choosing, alongside the attacker-controlled body.

This is exactly the class of bug called out in the rules: "a field acted on but not covered by the HMAC." Here the binding that should hold — `hmac_valid(raw_body) == true` implies `shop header is trustworthy for that raw_body` — does not hold, because `shop` is orthogonal to `raw_body` in the signature computation.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (as documented and intended — see `docs/usage/webhooks.md`) to route webhook data to the correct tenant record (e.g., "look up the shop's session/store by `data.shop` and update its state") can be made to attribute forged data to a shop the attacker does not control, since the gem provides no protection against header substitution once a valid signature has been obtained under the shared app secret. This is a cross-tenant data-integrity break entirely inside this gem's trust boundary (`HmacValidator`/`Registry`/`Request`), matching the Critical "cross-tenant access" impact category: the attacker crosses from their own tenant (their own shop) into another merchant's tenant context without ever possessing that merchant's credentials.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install the target app on an attacker-controlled shop (trivial for any public Shopify app) to legitimately obtain a valid `(raw_body, hmac)` pair signed with the shared `client_secret`, and (2) the ability to send an arbitrary HTTP POST to the app's publicly reachable webhook endpoint with a modified `shop` header — both of which are available to an unprivileged internet user and require no leaked credentials, TLS interception, or social engineering.

### Recommendation
Bind the tenant-identifying header (`shopify-shop-domain`) — and ideally `topic`/`webhook-id`/`api-version` — into the signed material that `HmacValidator` checks, or otherwise cryptographically tie the `shop` value to the specific webhook subscription it was registered for (e.g., cross-check against Shopify's registered webhook ID → shop mapping rather than trusting the header verbatim). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used by host applications to select per-tenant data without additional server-side verification (such as re-confirming the webhook via the Admin API for that shop).

### Proof of Concept
1. Attacker installs the target Shopify app on their own test store `attacker.myshopify.com`, causing Shopify to deliver a genuine webhook (e.g., `orders/create`) with a real `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `client_secret`.
2. Attacker captures the raw body and HMAC header from that delivery.
3. Attacker crafts a new POST to the app's webhook endpoint using the exact same raw body and HMAC, but replaces `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb` line 37) — the forged `shop` header is never part of that computation, so validation succeeds.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199) and, if it uses `data.shop` to select the tenant record to act on, processes attacker-controlled data under the victim's identity.
