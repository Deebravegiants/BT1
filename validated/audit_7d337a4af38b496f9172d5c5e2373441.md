### Title
Webhook shop-domain header not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop` value asserted by the incoming webhook headers, but the gem's HMAC verification only ever covers the raw request body — never the shop-domain header. Because Shopify signs webhooks with the app-level `client_secret` (shared across every shop that installs the app), any merchant who has installed the app can legitimately trigger webhooks against their own store, capturing a body + HMAC pair that is valid for *any* shop, then replay it with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop. The registry accepts this as an authenticated webhook "from" the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read directly from an attacker-controllable HTTP header with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body) and compares it with `secure_compare`; it never incorporates `shop`, `topic`, or any other header: [3](#0-2) 

`Webhooks::Registry.process` then passes `request.shop` straight through as the authenticated tenant identity in `WebhookMetadata`, which is handed to the host application's handler as though it were verified: [4](#0-3) [5](#0-4) 

The broken identity binding is:
`shop authenticated by HmacValidator.validate(request)` ≠ `shop actually covered by the HMAC (none)`.

Since Shopify webhook HMACs are keyed with the app's single `client_secret` for all installs, a valid `(raw_body, hmac)` pair obtained from any shop that has installed the app remains valid HMAC-wise no matter what `shop` header accompanies it. An attacker who is a legitimate merchant installer of the app can:
1. Trigger a webhook in their own store (e.g., `orders/create`) with a body they control, capturing the resulting `x-shopify-hmac-sha256` value.
2. Replay that exact raw body and HMAC to the app's webhook endpoint, substituting `x-shopify-shop-domain` with the victim shop's domain.
3. `Utils::HmacValidator.validate` still returns `true` because it only checks the body against the secret.
4. `Registry.process` builds `WebhookMetadata` with `shop: <victim shop>` and dispatches it to the host handler, which typically uses this field to look up the victim's session/access token and process the payload as if it genuinely originated from the victim's shop.

### Impact Explanation
This breaks the tenant-authentication boundary this gem is responsible for enforcing on behalf of the host application: the one signal (`request.shop`) apps are expected to trust for webhook routing/session lookup is unauthenticated. Depending on how the host app uses the (topic, shop, body) triple — updating orders, inventory, fulfillment, GDPR/customer data redaction, etc. — this enables cross-tenant data injection/corruption using another merchant's data disguised as the victim's, which matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop (a very low bar for public/embedded Shopify apps) and capture one legitimate webhook delivery for their own store — no access to `client_secret`, tokens, or the victim's credentials is needed. This is a realistic, low-effort attack path.

### Recommendation
Bind the HMAC to the shop identity, not just the body. Options:
- Have `to_signable_string` (or a new signable representation for webhooks) include the shop domain (and ideally topic/webhook-id) alongside the body before hashing, requiring host apps and the verifier to agree on a canonical signed string that binds `shop` cryptographically.
- Alternatively, cross-check `request.shop` against the shop associated with the session/access token the app already has on file for the topic being processed, rejecting mismatches, before invoking the handler in `Registry.process`.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be independently verified by host applications (e.g., against their own installed-shop registry) before being trusted for any tenant-scoped operation.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has the app installed there.
# Step 1: Attacker triggers e.g. an orders/create webhook on their own shop and
# captures Shopify's genuine delivery:
raw_body = '{"id":1,"note":"malicious payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
# (attacker does not need app_client_secret themselves -- Shopify computes and
#  sends this hmac to the app's registered webhook endpoint on delivery)

# Step 2: Attacker replays the same body+hmac to the endpoint, but swaps only
# the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because only raw_body is checked.
# The registered handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# and will act on victim-shop's behalf using attacker-controlled data.
```
