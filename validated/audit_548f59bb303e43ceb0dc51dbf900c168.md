### Title
Simplex venue pricing quotes an exotic token from a single direct Uniswap V4 pool with no hop-route or fee-tier check, letting a thin/mispriced pool set the fill price - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
For curveless pairs, Simplex's `FXFiller` prices the exotic token exclusively from a single Uniswap V4 position that pairs it directly against USDC/USDT, using the position with the largest liquidity. It never considers a multi-hop route (e.g. exotic → WETH → USDC) that could be materially more liquid or more accurately priced than the direct pair, and the direct pool's own fee tier is read but never applied to the quoted price. This is the same root cause as the referenced Sherlock finding: pricing off one pool/tier instead of checking whether a hop path gives the more accurate price.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` iterates the configured LP positions for a chain, keeps only those pairing the exotic token directly against USDC/USDT, and picks the single highest-liquidity one via `computeDirectPoolPriceUsd`, which returns the raw pool mid from `sqrtPriceX96`: [1](#0-0) [2](#0-1) 

This price feeds `FXFiller.resolveLegRates`, which for a curveless USD-stable pair fetches the single venue quote, checks only a static-reference deviation guard, and inverts it directly into the fill rate — with no comparison against a hop-priced alternative: [3](#0-2) 

The project's own internal flow documentation confirms the gap explicitly: the pool's fee tier is stored but never applied to the price, there is no size/impact term, and `checkPriceGuard` only bounds deviation from a static reference rather than validating against real execution cost or an alternate route: [4](#0-3) 

As in the Uniswap oracle report, if the exotic-USD direct pool is illiquid or has a wide fee tier while an indirect route (exotic → hop → USD) would offer a materially better/deeper price, Simplex still prices and fills exclusively off the thin direct pool. The `referencePrice`/`maxDeviationBps` guard is a static, manually configured band and does not detect this class of mispricing — a "good enough by deviation" price can still be far from the best executable price, and the guard is optional and per-chain, not per-route.

### Impact Explanation
Because Simplex sources both **pricing and inventory funding** for exotic-token legs from this single pool, an inaccurate price directly changes what the solver pays out per unit of the exotic token when filling cross-chain intents. A counterparty able to influence or exploit the direct pool's price (through low liquidity, timing, or simply a normal state where the direct pool is thinner/worse-priced than a hop route) can get the solver to fill orders at a rate that is worse than the fair market rate obtainable via a hop route, resulting in a loss of solver funds on repeated fills — a concrete value-extraction path against the intent solver's held inventory, consistent with Medium severity in the original report.

### Likelihood Explanation
This path is reachable by any ordinary user submitting an intent/order for a curveless, venue-priced pair configured under `[vault.uniswapV4]` — no privileged access is required. It only requires that the configured direct exotic/USD pool be thinner or otherwise worse-priced than an available hop route, which is a common real-world DEX liquidity condition (as illustrated in the original report with ARB/LINK vs. ARB/ETH/LINK). The `referencePrice` guard is optional and, when set, only bounds deviation from a fixed number set at config time — it does not adapt to or detect a better hop-priced alternative, so the condition can persist and be repeatedly exploited without tripping any guard.

### Recommendation
When evaluating venue-priced pairs, have `UniswapV4FundingPlanner`/`FXFiller` also compute an indirect quote via a common hop token (e.g. WETH) when available, and select (or cross-check against) the more liquid/accurate route rather than always using the highest-liquidity *direct* pool. Additionally, apply the pool's fee tier to the mid price before it is used for sizing/fills, and consider adding a route-level guard (e.g. reject or widen slippage when the direct and hop-derived prices diverge beyond a threshold) in addition to the existing static `referencePrice`/`maxDeviationBps` band.

### Proof of Concept
1. Configure `[vault.uniswapV4]` with a position pairing exotic token `X` directly against `USDC` on chain `C`, where this direct `X/USDC` pool has low liquidity (or a wide fee tier) — no `referencePrice` guard set (guard is optional).
2. A much deeper/better-priced route exists off-chain via `X → WETH → USDC`, which Simplex never queries (`getExoticTokenPrice` only looks at direct USDC/USDT-paired positions: [5](#0-4) ).
3. A user submits an intent order for the `USDC/X` pair sized so the direct pool's thin liquidity/wide spread quotes a materially worse rate for `X` than the hop-derived fair rate.
4. `resolveLegRates` reads the direct-pool venue quote, passes the (unset or wide) price guard, and fills at that inferior rate: [6](#0-5) .
5. The solver systematically loses value on this pair relative to what a hop-aware price would have yielded, repeatable on every order routed through the mispriced direct pool.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,

from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
