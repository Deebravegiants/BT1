Based on my research, I found a genuine custody-analog issue in this fork's custom `multisig_account.move` timelock feature — a resource-account-based multisig that gates fund-moving transactions behind a timelock unless a higher "override" quorum is met. This module does not exist in this form in upstream aptos-core; it's added extension code in this repo, and it contains a state-consistency bug in the same class as the bond-lock issue (a control/authority invariant that isn't re-enforced across state transitions), except here it manifests as an *authority-erosion* problem rather than a lock — enabling premature/unauthorized bypass of the security delay protecting multisig-custodied assets. [1](#0-0) 

### Title
Multisig timelock override_threshold invariant not re-validated on `num_signatures_required` update, allowing timelock bypass with only the normal quorum - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`MultisigAccountTimeLock.override_threshold` is defined as the elevated approval count required to bypass the timelock and execute a multisig transaction immediately, and must be strictly greater than `num_signatures_required` at the time it is set (`EINVALID_TIMELOCK_OVERRIDE_THRESHOLD`). [2](#0-1)  However, `update_owner_schema` — the single function used by `add_owners`, `remove_owners`, `swap_owners`, and `update_signatures_required`-style flows to mutate `num_signatures_required` — only clamps `override_threshold` down when the owner count shrinks below it, and never re-checks or re-clamps `override_threshold` relative to a newly increased `num_signatures_required`. [3](#0-2) 

### Finding Description
The invariant "override_threshold > num_signatures_required" is enforced only at set-time in `upsert_timelock`, not as a standing invariant maintained across all state mutations of `MultisigAccount`. `update_owner_schema` can raise `num_signatures_required` (e.g., via `swap_owners_and_update_signatures_required` or an owner-count/threshold update) up to and including the previously configured `override_threshold` value, with no assertion comparing the two. The only defensive clamp present adjusts `override_threshold` downward only when `num_owners` shrinks below it, which addresses a completely different failure mode (owner removal) and does nothing to protect the relationship between `override_threshold` and `num_signatures_required`. [3](#0-2) 

Once `num_signatures_required == override_threshold` (or higher), any transaction that reaches ordinary quorum (`num_signatures_required` approvals) simultaneously satisfies the "override" quorum condition, defeating the entire purpose of the timelock: it was meant to force a mandatory delay for transactions approved at the *normal* threshold, giving other owners a window to detect and reject a malicious payload (e.g., a transfer of multisig-custodied APT/FA, a resource-account signer-capability abuse, or an ownership/authority change). This is a custody-invariant break: multisig-held value's execution-authority gate is silently degraded by an ordinary owner-management transaction path that has no awareness of, or interaction with, the timelock security control.

### Impact Explanation
Multisig accounts in this framework are resource accounts that can hold APT, fungible assets, or serve as the authority behind other custody flows (owning objects, resource accounts, or code objects). The timelock/override_threshold mechanism exists specifically to protect against a subset of colluding or compromised owners meeting the base quorum and moving assets before the rest of the owner set can react. If `num_signatures_required` can be raised to meet or exceed `override_threshold` without re-validating or clamping the override value, transactions reaching normal quorum bypass the intended delay entirely — any owner subset large enough to satisfy `num_signatures_required` can execute custody-affecting transactions (fund transfers, ownership changes, additional owner/threshold changes) immediately, with no opportunity for the remaining owners to reject. This is a high-severity custody control failure because it silently disables a security delay that governs "high or critical" asset-moving transactions, without requiring any privileged/malicious admin action beyond the normal (permitted) `update_signatures_required` proposal flow.

### Likelihood Explanation
The trigger path uses only standard, already-exposed multisig entry functions (`update_owner_schema` via `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`, or similar signature-count-changing calls) that are reachable by the normal proposal/execution flow requiring only `num_signatures_required` approvals — the same threshold the invariant is supposed to gate. [4](#0-3)  No special privilege beyond being able to reach ordinary quorum is needed, and there's no compile-time or runtime assertion elsewhere in `update_owner_schema` preventing this state. This makes the likelihood realistic in any deployment using both the timelock feature and routine quorum/owner-count changes.

### Recommendation
In `update_owner_schema`, after applying `optional_new_num_signatures_required`, add an explicit check (mirroring the owner-count clamp logic already present) that asserts or adjusts `override_threshold` to remain strictly greater than the (possibly new) `num_signatures_required` whenever a `MultisigAccountTimeLock` exists — aborting the update (or auto-raising `override_threshold`, with an emitted event) if the invariant `override_threshold > num_signatures_required` cannot be preserved.

### Proof of Concept
1. Owners create a multisig with `num_signatures_required = 2`, `owners.length() = 5`, and call `upsert_timelock` with `override_threshold = Some(4)` (valid since `4 > 2`).
2. Owners later call `update_signatures_required`/`swap_owners_and_update_signatures_required` to raise `new_num_signatures_required` to `4`, reaching that quorum with only the (already-permitted) 2 original approvals under the old threshold. `update_owner_schema` accepts this because it only asserts `num_owners >= num_signatures_required`, never `override_threshold > num_signatures_required`. [5](#0-4) 
3. Now `num_signatures_required == override_threshold == 4`. A colluding set of exactly 4 owners creates and approves a fund-transfer or authority-change transaction and executes it immediately, since the "override" condition (`votes >= override_threshold`) is trivially satisfied by ordinary quorum — completely bypassing the intended timelock delay that the remaining owner was relying on to detect and reject it.

**Caveat:** I was unable to inspect `validate_multisig_transaction`/`successful_transaction_execution_cleanup` (the exact function where `override_threshold` is compared against votes/timelock to permit early execution) before running out of tool calls, so I cannot 100% confirm the precise comparison logic used at execution time. The invariant-maintenance gap in `update_owner_schema` is confirmed directly from source, but full end-to-end confirmation of the execution-time consequence would require reading that function as well.
