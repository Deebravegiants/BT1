### Title
Webhook `shop` identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature from the raw request body only, while the `shop` (tenant identifier) is read from an unauthenticated, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches, then hands the header-derived `shop` value straight to the host application's handler via `WebhookMetadata`. This breaks the equality `shop-bound-by-signature == shop-attributed-to-payload`, since the signature covers `body` but the trusted tenant identity comes from `shop-domain`/`x-shopify-shop-domain`, a header outside the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read purely from an HTTP header with no cryptographic binding to the body or its signature: [2](#0-1) 

`Registry.process` validates the HMAC against `Utils::HmacValidator.validate(request)` — which only checks the body-derived signature — and then immediately constructs `WebhookMetadata` using `request.shop` without any further cross-check that this shop is consistent with anything cryptographically verified: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and the app's `api_secret_key`: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field that host applications are expected to trust to identify which merchant/tenant a webhook event belongs to: [5](#0-4) 

Because the identical `(body, hmac)` pair is valid for any `shop-domain` header value, an attacker who has ever legitimately received one authentic webhook delivery for their own installed shop (body + hmac, both valid and observable to that attacker since it's delivered to their own endpoint) can replay that exact body and HMAC to the same endpoint while substituting a different `x-shopify-shop-domain` / `shopify-shop-domain` header value naming a victim shop. `Registry.process` will treat this as a validly-signed webhook and invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, because nothing in the code binds the header used for tenant attribution to the signed bytes.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` to look up per-tenant state — e.g., loading the corresponding merchant's stored access token, applying data mutations scoped "for this shop," or dispatching side effects keyed by shop — can be tricked into acting on/for a shop the attacker doesn't control, using data the attacker fully controls (their own webhook body). This is a cross-tenant identity-binding failure: the field the application uses to select a tenant (`shop`) is not covered by the same authentication mechanism (HMAC) that is presented as proving the request's authenticity. This matches the "Critical — cross-tenant access" impact category, since it lets an unprivileged user, who only needs their own installed app's legitimate webhook traffic, cause tenant-scoped webhook processing to be attributed to an arbitrary third-party shop domain.

### Likelihood Explanation
The attacker needs no `api_secret_key`, no access token, and no privileged account — only their own app installation, which is enough to be an unprivileged internet-facing actor from the perspective of the webhook receiving endpoint. They passively capture (or trivially replay via `curl`) a webhook they already legitimately received, and craft a new HTTP request re-using that body/HMAC with a forged shop header. The library performs no defense against this: `Utils::HmacValidator.validate` never inspects headers, and `Registry.process`/`WebhookMetadata` never cross-checks `shop` against anything HMAC-protected.

### Recommendation
Bind the `shop` claim to the same authenticated bytes used for verification — e.g., include the shop domain (and ideally webhook id / topic) in the HMAC-signable string, or independently verify that the `shop-domain` header corresponds to a shop already known/authorized by the host application (e.g., cross-reference against stored, previously-onboarded shop records) before dispatching to `WebhookHandler#handle`. At minimum, the gem's documentation and `WebhookMetadata` should make explicit that `shop` is unauthenticated and must not be trusted for tenant-sensitive decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid-hmac-for-body>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: abcd-...

{"id": 123, "note": "some payload"}
```
2. Attacker replays the identical body and `x-shopify-hmac-sha256` value, only changing the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same-valid-hmac-for-same-body>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: abcd-...

{"id": 123, "note": "some payload"}
```
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC, per `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds to call the host application's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
