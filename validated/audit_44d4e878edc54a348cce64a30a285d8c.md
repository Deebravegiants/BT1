### Title
Webhook `shop-domain` Header Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` value used by `Registry.process` to attribute the webhook to a tenant is read from an unrelated, unsigned header. Because the app's HMAC secret (`Context.api_secret_key`) is a single global secret shared across every shop that installs the app, this breaks the intended binding of `hmac == f(body, shop)`, allowing a legitimate-but-malicious user of one shop to relabel a validly-signed webhook payload as belonging to a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no part in that signable string: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., it only proves that the *body* bytes are authentic under the app-wide secret — it says nothing about which shop the header claims to be from: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` (the unauthenticated header) when constructing the metadata handed to the app's webhook handler: [4](#0-3) 

The identity-binding equality the library implicitly claims to enforce is:
`hmac_valid(body, secret) ⇒ (body, shop_header) is authentic`

but the actual binding enforced is only:
`hmac_valid(body, secret) ⇒ body is authentic`

`shop_header` is never covered by the signature. Since `secret` (`Context.api_secret_key`) is the same app-level secret for all merchants — confirmed by `HmacValidator.validate` always using the global `Context.api_secret_key`/`Context.old_api_secret_key` with no per-shop key material — any user who can trigger a genuine webhook for their own store (e.g., by installing a public app in their own test store and performing an action like updating a product) obtains a `(body, hmac)` pair that is valid under the app's secret regardless of which shop it is replayed against. That user can then POST the same body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain, and `Registry.process` will pass this spoofed shop identity straight to the handler as authentic.

### Impact Explanation
This is a cross-tenant identity confusion: the webhook consumer (the host application built on this gem) receives `WebhookMetadata#shop` values that are not actually bound to the cryptographically verified payload. Any app that uses `request.shop` to look up a merchant's session/access token or to perform per-tenant side effects (which is the documented, expected usage pattern of this field) can be made to act on behalf of, or write data attributed to, a shop the attacker does not control — a cross-tenant access impact, which is explicitly Critical severity per the impact criteria for this analysis.

### Likelihood Explanation
Exploitation only requires the attacker to have (or create) any single store where the target app is installed — a normal, low-privilege, unprivileged-internet-user capability for public apps — and the ability to send an arbitrary HTTP request to the app's public webhook endpoint with custom headers. No access to `api_secret_key`, tokens, or TLS interception is required, since the secret used for signing is never exposed to the attacker and is not needed — only a legitimately-issued signed body is replayed with a modified header.

### Recommendation
Include the shop domain (and ideally webhook id/topic) as part of the signed material verified by `HmacValidator`, or explicitly cross-check the header-derived `shop` against a shop-specific expectation before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that `request.shop` must not be trusted as tenant identity unless corroborated by other means (e.g., matching against the shop associated with the specific installed webhook subscription id).

### Proof of Concept
1. Attacker installs the target public app on their own test store `attacker-shop.myshopify.com` and triggers a webhook-eligible action (e.g., product update), causing Shopify to deliver a webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` to the app's webhook endpoint — the attacker captures this legitimate `(B, hmac)` pair from their own store's traffic.
2. Attacker crafts a new HTTP POST to the same webhook endpoint using the identical body `B` and identical `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it matches — validation passes because the signature only ever covered `B`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to process/attribute the event as coming from the victim shop even though the victim shop never sent it.
