### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives its authenticity solely from an HMAC computed over the raw request body, but the `shop` (shop-domain) field that host applications use to attribute the webhook to a tenant is taken from an unauthenticated HTTP header and is never included in the signed material. This breaks the intended binding "HMAC-verified bytes == the shop the webhook is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` recomputes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` field: [2](#0-1) 

`Registry.process` only checks this body-only HMAC before dispatching to the handler, and separately reads `request.shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed string) to build `WebhookMetadata`: [3](#0-2) [4](#0-3) 

The equality that should hold is: `shop_bound_by_hmac == shop_used_for_tenant_routing`. Before the request: the HMAC covers only body bytes; the header `shopify-shop-domain` is attacker/network-controlled metadata. After delivery: `Registry.process` verifies the body HMAC (passes, since it is a byte-for-byte replay of a genuine webhook the attacker actually received for their own store), then hands `request.shop` — an unauthenticated header — directly to the handler as the tenant identifier. Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app rather than being per-shop, any merchant who has installed the app can capture a genuine, validly-signed webhook delivered for their own store and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. The gem will report the HMAC as valid and dispatch `WebhookMetadata.shop = <victim shop>` to the handler, per the documented data contract: [5](#0-4) 

### Impact Explanation
The gem's own webhook-processing contract instructs host applications to use `data.shop` to key persistence/queueing operations for the affected tenant. Since this field is not bound by the HMAC that the gem itself validates, an attacker who legitimately controls one shop (or intercepts one genuine delivery) can forge webhook events attributed to any other shop, causing cross-tenant data confusion/injection inside the host app — a cross-tenant access impact within the scope of this bug bounty.

### Likelihood Explanation
Likelihood is high for any application that trusts `WebhookMetadata#shop` for tenant identification (which is exactly what the gem's documentation recommends). No secrets need to be leaked: the attacker only needs to be a legitimate installer of the app on at least one shop to obtain one genuinely signed payload/HMAC pair and can then freely vary the `shop-domain` header, since that header carries no cryptographic binding.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material used for webhook validation, or require host applications to cross-check `request.shop` against a known/authorized shop list independent of the HMAC. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant attribution without an additional, out-of-band verification step (e.g., matching against the shop stored with the corresponding installed-app session).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a genuine webhook to the app's endpoint with body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, and `shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker captures this raw request (`B` and the HMAC value).
3. Attacker resends the exact same body `B` and HMAC header to the same endpoint, but changes the header to `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (== `B`) — validation succeeds because `B` and the HMAC are unchanged: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and the host app (following the gem's documented usage pattern) processes/queues data as belonging to `victim-shop.myshopify.com`, even though the payload originated from `attacker-shop.myshopify.com`.
