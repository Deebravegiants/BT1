### Title
Webhook `shop`/`topic` header spoofing via HMAC verification that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` (used by `ShopifyAPI::Webhooks::Registry.process`) only authenticates the byte content of the webhook payload. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which `Registry.process` uses to route the request and which are handed to the app's handler as the tenant identity — are never included in the HMAC-signed material. This breaks the binding `hmac-authenticated bytes == data acted on`, allowing a body that was legitimately signed for one shop to be replayed with a different, attacker-chosen `shop` value.

### Finding Description
`Registry.process` gates all webhook processing on a single check: [1](#0-0) 

That check delegates to `HmacValidator.validate`, which recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header value: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed payload: [4](#0-3) 

And it is exactly these header-derived, unauthenticated values that get forwarded as the tenant identity to the app's handler: [5](#0-4) 

The identity binding that should hold is: `shop asserted to the handler == shop whose secret produced the HMAC`. Because the HMAC only covers the body, this equality is never actually checked — any (body, hmac) pair that is valid for the app's `api_secret_key` (i.e., a webhook legitimately delivered to *any* shop that installed the app, including a shop the attacker controls) remains valid no matter what `shop-domain`/`topic`/`webhook-id` headers accompany it.

### Impact Explanation
An unprivileged user who can install the app on their own (attacker-controlled) store receives genuine Shopify webhooks addressed to that store, each with a valid HMAC computed against the app's shared `api_secret_key`. Because the HMAC never covers the header set, the attacker can capture one such legitimate `(raw_body, hmac)` pair and replay it against the app's shared webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (and/or the `X-Shopify-Topic` header). `Registry.process` will accept it as authentic and invoke the app's handler with `shop: <victim-shop>` and attacker-controlled body content — i.e., cross-tenant data injection into the victim shop's processing pipeline without ever compromising the victim or obtaining their credentials.

### Likelihood Explanation
Any developer can sign up as a Shopify Partner, install their own app on a free development store, and receive real webhooks with valid HMACs for that store. Forging headers on a replayed HTTP request requires no special access — just knowledge of the app's public webhook endpoint, which is typically documented in the app's own OAuth/webhook setup. This makes the attack straightforward for anyone who is a legitimate (if low-privilege) merchant/tenant of the multi-tenant app.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise refuse to trust `shop`/`topic` unless they are corroborated against a known/registered shop-session record before dispatching to the handler. Concretely, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` alongside the body (mirroring how `Oauth::AuthQuery#to_signable_string` binds `shop`, `state`, etc. into its signature), and/or `Registry.process` should require the caller to supply the expected shop and reject mismatches, rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers for `orders/create`.
2. Shopify sends a legitimate webhook to the app's shared endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(B, api_secret_key)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (leaving `B` and the HMAC header untouched), and re-sends it to the app's webhook endpoint.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `hmac` still matches `HMAC(B, api_secret_key)`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which passes because it only checks `B` against the secret — it never checks that `victim-shop.myshopify.com` is the shop the HMAC was actually generated for.
6. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-supplied data as if it belonged to the victim tenant.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
