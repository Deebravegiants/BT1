## Vulnerability Analysis

The DODO "infinite approve + leftover" bug class maps directly onto `LifiExternalAction.callRouter` in this repo.

### Root Cause

In `contracts/external-actions/swaps/ExternalActionSwap.sol`, `swap()` computes `inputAmount` from the ZK-verified `deltaAmounts[0]` and passes it to `callRouter`: [1](#0-0) 

But in `contracts/external-actions/swaps/LifiExternalAction.sol`, the ERC-20 branch of `callRouter` never uses `inputAmount` to bound anything — it grants an **infinite, never-revoked approval** to `router` and then executes attacker-supplied `externalActionMetadata` bytes verbatim: [2](#0-1) 

`swappedAmount` is derived purely from the output-token balance delta, and the whole result is attributed to the caller's new UTXO: [3](#0-2) 

`approveUnlimited` sets `type(uint256).max` allowance and only re-approves if it later drops below `max/2` — it is never reset to zero: [4](#0-3) 

### Why `externalActionMetadata` isn't a safe constraint

The `externalActionData` (including `externalActionMetadata`) is only checked for *integrity* — it is hashed into `calldataHash`/`signedMessageHash` so the relay/prover cannot swap it for a different blob after the user signs, but its **content is never constrained to match `inputAmount`**: [5](#0-4) [6](#0-5) 

The circuit and `formBasicInput` never bind the byte content of `externalActionMetadata` to `amountChanges` — they only bind `calldataHash` as an opaque field. So the *user themselves* is free to craft `externalActionMetadata` (e.g. a LI.FI/1inch-style `swap()` call whose encoded `fromTokenAmount` field is larger than their committed `inputAmount`) while their own shielded ledger only gets debited by the (small) `inputAmount` encoded in `deltaAmounts[0]`.

### Break in the Balance Equation

`Hinkal._externalTransact` only ever transfers `uint256(-deltaAmountChanges[i])` (i.e. `inputAmount`) to `LifiExternalAction` before calling `runAction`: [7](#0-6) 

If `LifiExternalAction` holds any leftover `inputToken` balance (from prior partial-fill swaps returning excess input, or dust), that leftover — combined with the never-revoked infinite approval to `router` — is fully at the mercy of whatever `fromTokenAmount` the current caller encodes inside `externalActionMetadata`. The contract never verifies "input token balance decreased by exactly `inputAmount`"; it only checks the output side. This breaks the intended equality: *shielded-ledger debit (`deltaAmounts[0]`) == actual token amount consumed by the external swap*. The excess output produced by consuming stranded leftover funds is credited entirely to the attacker's own new UTXO — a straightforward theft-of-leftover-funds path with no privilege required.

### Title
Unbounded input-token consumption via infinite router approval lets any user steal leftover `LifiExternalAction` balances - (File: contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` grants an unlimited, permanent ERC-20 approval to the LI.FI `router` and then executes user-supplied `externalActionMetadata` calldata without validating that the router only pulls `inputAmount` of `inputToken`. Since `inputAmount` is otherwise unused in the ERC-20 branch, any user can encode a swap call whose internal "amount to pull" field exceeds their committed `inputAmount`, causing the router to sweep any leftover `inputToken` balance sitting in the contract (from prior partial fills/rounding) and crediting the resulting extra output entirely to the attacker's own UTXO.

### Finding Description
- `swap()` computes `inputAmount = uint256(-deltaAmounts[0])`, the amount actually debited from the caller's shielded balance per the ZK proof, and forwards it to `callRouter` [8](#0-7) .
- `LifiExternalAction.callRouter`'s ERC-20 branch ignores `inputAmount` entirely; it calls `approveUnlimited(inputToken, router)` and then `router.call(externalActionMetadata)` [9](#0-8) .
- `externalActionMetadata` is arbitrary attacker-controlled bytes; it is only integrity-checked via `calldataHash`/`signedMessageHash`, never constrained in *content* to `inputAmount` [10](#0-9) .
- Because the approval never resets to zero across calls (`approveUnlimited` only re-approves when allowance falls below `max/2`), the router can always pull up to the full balance of `inputToken` the contract holds, not just the freshly transferred `inputAmount`.
- The resulting `swappedAmount` (output-token balance delta) is fully paid out to the current caller as a new UTXO, without any check that input consumption matched `inputAmount` [3](#0-2) .

This exactly mirrors the DODO Sherlock finding: infinite approval + no validation of actual amount consumed by the external call = leftover-fund theft, except here the leftover funds could belong to the protocol/relay or be induced by any prior partial-fill swap dust.

### Impact Explanation
This is theft of protocol/leftover funds by an unprivileged EOA exploiting an authorization gap between the ZK-committed debit amount and the actual token amount consumed by the router call — classified High per the rules ("theft or permanent freezing of protocol/relay fees" / "moving assets ... never authorised" by the debited amount).

### Likelihood Explanation
Likelihood depends on `LifiExternalAction` accumulating a non-zero `inputToken` balance (from partial-fill refunds, rounding, or dust from prior swaps). LI.FI/1inch-style aggregators commonly refund unused input on partial fills, making leftover balances realistic over time; once any leftover exists, exploitation requires only a single crafted transaction from any user.

### Recommendation
- Enforce in `callRouter`/`swap()` that the contract's `inputToken` balance decreases by exactly `inputAmount` (not more) after the router call, reverting otherwise.
- Avoid unlimited/persistent approvals; approve exactly `inputAmount` before each call and reset allowance to zero afterward, or use a `permit`/pull-based amount that is cryptographically bound to `inputAmount`.
- Add a periodic/immediate sweep (e.g., `superWithdraw`-style) that only the protocol can trigger, and ensure no swap step can attribute more output than corresponds to the exact debited input.

### Proof of Concept
1. A prior transaction (partial fill, rounding, or dust transfer) leaves `X` amount of `TOKEN_A` sitting in `LifiExternalAction`.
2. Attacker (any EOA with a shielded balance, even trivially small) submits a valid Hinkal `transact()` proof committing to swap a tiny `inputAmount` of `TOKEN_A` for `TOKEN_B` via `LifiExternalAction`.
3. Attacker crafts `externalActionMetadata` so the embedded LI.FI/1inch `fromTokenAmount` field equals `inputAmount + X` instead of just `inputAmount`.
4. `LifiExternalAction.callRouter` has (or grants) unlimited approval to `router`; `router.call(externalActionMetadata)` pulls `inputAmount + X` of `TOKEN_A` via `transferFrom`, swaps it, and returns `TOKEN_B`.
5. `swappedAmount = balanceAfter - balanceBefore` reflects the full swap of `inputAmount + X`; this entire amount (minus fees) is credited to the attacker's new UTXO, even though their shielded ledger was only debited `inputAmount` of `TOKEN_A`.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
