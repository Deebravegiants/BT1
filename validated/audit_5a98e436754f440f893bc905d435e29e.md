### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `Request#to_signable_string` (used by `Utils::HmacValidator.validate`) only signs the raw request body. `Webhooks::Registry.process` validates the HMAC against the body only and then hands the unauthenticated `shop` header straight to the app's handler. This breaks the intended binding `HMAC(secret, signed_bytes) == HMAC(secret, all_bytes_acted_on)` — the `shop` value is "acted on" (dispatched to the handler as the tenant identifier) but is not part of the "bytes verified."

### Finding Description
- `Request#hmac` and `Request#to_signable_string` only cover `@raw_body`: [1](#0-0) 
- `shop` (and `topic`, `webhook_id`, `api_version`) are pulled from headers that are entirely outside the signed payload: [2](#0-1) 
- `Registry.process` validates only the body HMAC via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body in this case) and compares it to the `hmac` field — it never touches `shop`: [4](#0-3) 
- The gem's own documentation presents `data.shop` from `Registry.process` as a trusted, verified value ("This will verify the request did indeed come from Shopify") and shows sample handler code dispatching tenant-scoped work keyed on `data.shop`: [5](#0-4) [6](#0-5) 

**Equality that should hold but doesn't:**
`shop_used_by_handler == shop_bound_by_HMAC(secret, body)` — in reality `shop_used_by_handler` comes from an arbitrary, attacker-controllable header, while the HMAC only binds the JSON body bytes.

### Impact Explanation
Because Shopify's webhook HMAC (and this gem's validation of it) covers only the request body, any entity that possesses one *valid* signed webhook payload (e.g., a merchant who has legitimately installed the app on their own shop and thus receives real signed webhooks addressed to them) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Registry.process` will accept it (HMAC over the body still matches) and dispatch the handler with `shop` set to whatever domain the attacker chose. If the app (following the gem's documented usage pattern) uses `data.shop` to resolve tenant context, look up sessions, or attribute mutating/administrative actions (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`), the attacker can inject or misattribute events into a victim shop's tenant scope without ever compromising the victim, satisfying the "cross-tenant access" (Critical) impact category.

### Likelihood Explanation
Exploitation requires only (a) the app's public webhook endpoint URL, and (b) at least one previously-received, validly-signed webhook body (trivially obtainable by any merchant that installs the app themselves, or by intercepting/replaying any prior webhook delivery). No access to `client_secret`, access tokens, or privileged credentials is required — only standard HTTP access to the app's webhook route, which is unauthenticated by design. This is directly reachable through this gem's own `Registry.process`/`Request` code path, not dependent on the host app deviating from documented usage.

### Recommendation
- Do not treat `shop`, `topic`, `webhook_id`, or `api_version` headers as trusted/verified values. Either:
  - Extend the signable payload used for HMAC validation to include these header values (would require Shopify platform changes since HMAC is Shopify-generated and only covers the body), or, more practically within this gem's control,
  - Cross-check `request.shop` (and `topic`) against the body content (many webhook payloads embed the shop/store data or can be correlated with a known registration) before dispatching to handlers, and/or
  - Update `WebhookMetadata`/documentation to explicitly warn that `shop` is derived from an unauthenticated header and must be independently verified (e.g., against an existing stored session for that shop) before being used for any tenant-scoped or mutating action.

### Proof of Concept
1. App installs on `attacker.myshopify.com`; attacker's webhook endpoint legitimately receives a real webhook, e.g.:
   ```
   headers:
     x-shopify-topic: orders/create
     x-shopify-hmac-sha256: <valid HMAC over body, computed with app's client_secret>
     x-shopify-shop-domain: attacker.myshopify.com
   body: {"id": 123, ...}
   ```
2. Attacker resends the identical body and HMAC header to the app's webhook route, only changing:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
3. `Webhooks::Request.new` parses headers/body successfully [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC purely over the (unchanged) body and finds it matches — validation passes [8](#0-7) .
5. The handler is invoked with `shop: "victim.myshopify.com"`, even though the request never touched Shopify or the victim shop at all.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @raw_body = raw_body

          received_signature = verifiable_query.hmac

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
