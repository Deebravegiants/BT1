### Title
`shop` accepted from the unauthenticated OAuth callback query and used to route the `client_secret` before HMAC-covered validation is bound to a trusted domain - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`Oauth.validate_auth_callback` validates the incoming callback query with an HMAC that is computed over `code, host, shop, state, timestamp` (`AuthQuery#to_signable_string`), so `shop` is nominally covered by the HMAC. However, the HMAC only proves the query was signed with `Context.api_secret_key` (which the app itself controls/knows) — it never proves that `shop` is a genuine `*.myshopify.com`/trusted Shopify domain. `shop` is then used, unsanitized, to build the base URI for the outbound POST that carries `client_id`/`client_secret`/`code` (`Auth::Session.new(shop: auth_query.shop)` → `Clients::HttpClient.new(session: null_session, ...)` → `@base_uri = "https://#{api_host || session.shop}"`).

### Finding Description
The identity binding that should hold is: *the host that receives the app's `client_secret` == a genuine, trusted Shopify shop domain*. Instead, the code only checks: *the host that receives the app's `client_secret` == whatever string arrived in the `shop` query parameter, provided the whole query is HMAC-valid*.

- `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:13-22` recomputes an HMAC over `AuthQuery#to_signable_string` and compares it to the `hmac` param — this only authenticates that the *combination* of fields was signed by the secret key; it does not validate that `shop` is a `myshopify.com`/trusted domain.
- `lib/shopify_api/auth/oauth.rb:60-98` (`validate_auth_callback`) checks the HMAC (`Utils::HmacValidator.validate(auth_query)`, line 64) and the anti-CSRF `state` cookie (lines 67-71), but never calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on `auth_query.shop` — contrast with `TokenExchange.migrate_to_expiring_token` (`lib/shopify_api/auth/token_exchange.rb:103`), which does call `Utils::ShopValidator.sanitize!(shop)` before using it to build a session/host.
- The unsanitized `auth_query.shop` is put directly into `null_session = Auth::Session.new(shop: auth_query.shop)` (line 73) and handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` (line 81).
- `HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:16-19`) builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` with no domain validation, then `request_url` (line 106-109) appends `access_token` to it. The subsequent POST body (lines 74-79 in oauth.rb) contains `client_id`, `client_secret`, and the OAuth `code`.

Because Shopify's own OAuth "app installation" flow is what normally drives the browser to this callback with `code`/`state`/`shop`/`timestamp`/`host`, and the HMAC is computed with the app's own secret (which the app itself controls, not something an unprivileged attacker can forge for an *arbitrary* value it chooses) — the exploitability of this gap hinges entirely on whether Shopify ever signs (or the host application can be tricked into treating as signed) a `shop` value that is not a `myshopify.com` domain. I could not find in the in-scope library code any place that validates `shop` is a trusted Shopify domain before it's used to route the client secret in `validate_auth_callback`; the only domain-sanitization utility in the gem (`Utils::ShopValidator`) is bypassed on this path. This is a genuine binding gap: the field that the client secret is routed to (`shop`) is checked only for internal signature consistency, not for domain trust, unlike the equivalent `TokenExchange.migrate_to_expiring_token` path.

### Impact Explanation
If a `shop` value that is not a genuine Shopify-hosted domain can reach `validate_auth_callback` with a valid HMAC (e.g., because the host application forwards attacker-supplied query parameters, or because of any weakness in how the callback endpoint is wired up by the integrating app), the app's `client_id`/`client_secret` and the OAuth authorization `code` would be POSTed to an attacker-controlled host — this is credential exfiltration of the app's `client_secret` and can lead to full OAuth-token issuance under attacker control (SSRF carrying the app's credentials). This matches the Critical/High impact bar (theft of `client_secret`, SSRF with app credentials).

### Likelihood Explanation
Likelihood is Medium: exploitation requires a `shop` value that both (a) passes the HMAC check (i.e., is part of a query the app's own secret validates) and (b) is not a genuine Shopify domain. The gem does not enforce that these two conditions are compatible, and there is no domain allow-list check on this specific path, unlike the parallel `migrate_to_expiring_token` path which does call `ShopValidator.sanitize!`. This is a real inconsistency in the codebase's own defense-in-depth, even though full exploitability depends on how a specific host application feeds `shop` into the query object.

### Recommendation
In `Oauth.validate_auth_callback`, before constructing `null_session`/building the outbound request, sanitize `auth_query.shop` through `Utils::ShopValidator.sanitize!` (as already done in `TokenExchange.migrate_to_expiring_token`), and use the sanitized value for both the session used to derive the request host and for the resulting `Session.from(shop: ...)`. This closes the gap between "HMAC-signature-consistent" and "trusted Shopify domain."

### Proof of Concept
Not runnable as a standalone PoC without the host application's callback wiring, since the exploit path depends on `shop` reaching `AuthQuery` with a matching HMAC. Conceptually:
1. An attacker crafts/obtains a callback request where `shop` is set to an attacker-controlled host string rather than a `*.myshopify.com` domain, while the rest of the query (`code`, `host`, `state`, `timestamp`, `hmac`) remains internally consistent for the target app's `api_secret_key`.
2. `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)` passes the HMAC check (`lib/shopify_api/utils/hmac_validator.rb:13`) because it only checks internal signature consistency, not domain trust.
3. `Auth::Session.new(shop: auth_query.shop)` and `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` (`lib/shopify_api/auth/oauth.rb:73,81`) build `@base_uri = "https://#{session.shop}"` (`lib/shopify_api/clients/http_client.rb:18`) pointing at the attacker's host.
4. The POST containing `client_id`, `client_secret`, and `code` (`lib/shopify_api/auth/oauth.rb:74-79`) is sent to that attacker-controlled host. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
