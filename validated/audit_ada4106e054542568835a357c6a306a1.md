## Analysis: Excess native-token overpayment is stranded in `EvmHost` on `dispatch()`/`fundRequest()`

This is a valid analog of the "resource not freed/returned on a partial-completion path" bug class described in the CVE report, mapped to Hyperbridge's fee-payment flow.

### Root Cause

`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native ETH (`msg.value`) and swap it for the exact `feeToken()` amount needed via the configured Uniswap V2-style router: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three functions, `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called but its return value (`amounts`, which reports how much ETH was actually spent) is **discarded**. `swapETHForExactTokens` only consumes as much ETH as needed to produce the exact `fee` output amount and refunds the unspent remainder to its immediate caller — which, here, is `EvmHost` itself, not the original transaction sender. Since none of these three functions track "amount actually spent" or forward the leftover ETH back to `_msgSender()`/`post.payer`, any overpayment of native ETH is silently absorbed into `EvmHost`'s own balance and is unrecoverable by the depositor. `EvmHost.sol` contains no `receive()`/dust-sweep path for the depositor to reclaim it.

This is directly analogous to `IntentGatewayV2.placeOrder` and `ExtrinsicIntents._fillCrossChain`, which correctly capture the swap's actual spend and refund the difference: [4](#0-3) [5](#0-4) 

The custom AMM wrapper contracts (`UniV3UniswapV2Wrapper.sol`, `UniV4UniswapV2Wrapper.sol`) independently implement their own ETH-refund logic within `swapETHForExactTokens`, but that refund is sent to `msg.sender` of the wrapper call — which is `EvmHost`, not the original dispatcher — so the leftover ETH still ends up trapped in `EvmHost` regardless of which router backend is configured: [6](#0-5) [7](#0-6) 

### Impact

Any unprivileged caller invoking `IDispatcher.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `IHost.fundRequest()` with native ETH and any margin above the exact fee-swap requirement (routine given Uniswap price movement/slippage, or a caller intentionally rounding up `msg.value` for safety) permanently loses the unspent difference to the `EvmHost` contract with no refund path — a concrete, permanent freezing/loss of user funds reachable from a single transaction.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder` and `ExtrinsicIntents`.

### Proof of Concept
1. Configure `EvmHost` with a live `uniswapV2` router.
2. Call `dispatch(DispatchPost{fee: F, ...})` with `msg.value = 2F` in ETH-equivalent terms (deliberately overpaying to cover slippage).
3. `swapETHForExactTokens` spends only what's needed (`amountIn < msg.value`) to buy exactly `F` fee tokens and refunds the remainder to `EvmHost`.
4. Observe: `EvmHost`'s ETH balance increases by the unspent amount; the original caller receives nothing back and has no function available to reclaim it.

**Caveat**: I could not verify from the indexed files whether a governance/admin sweep function for stray native ETH exists elsewhere in `EvmHost.sol` (the grep found no `receive()`, `fallback()`, or `sweep`-named function in that file, but the file is large and the index may not cover 100% of it). If such an admin-only sweep exists, the classification shifts from "permanently frozen/lost user funds" to "funds recoverable only by governance, not by the depositor" — still a fund-freezing issue for the affected user, but less severe than total unrecoverable loss.
