### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` value used by the application to identify the tenant for that webhook event comes from an unauthenticated header that is never covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the webhook solely with `Utils::HmacValidator.validate(request)` against that signable string before dispatching to the handler [2](#0-1) . The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the signed payload [3](#0-2) . That unauthenticated `shop` value is then forwarded straight into the data the handler is invoked with (`WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`) [4](#0-3) , which is the value host applications are expected to use as the tenant/session key when acting on the webhook.

The identity binding that should hold is:
`shop header value == shop bound inside the HMAC-signed payload`

but the implementation only checks:
`HMAC(secret, raw_body) == received_hmac`

with no equality check tying `shop` to that signature. Since HMAC(secret, body) is independent of the `shop` header, any party capable of obtaining one valid `(body, hmac)` pair from the shared app secret (e.g., from a webhook fired for their own, attacker-controlled shop that has installed the same app) can replay that exact body+HMAC while substituting an arbitrary victim shop domain in the header, and the signature check in `Registry.process` will still pass.

### Impact Explanation
This breaks the shop-to-signature binding, enabling cross-tenant confusion: a webhook payload legitimately signed for the attacker's own shop can be delivered to the app's webhook endpoint claiming to originate from a victim shop. Any host application that trusts `WebhookMetadata#shop` (as the library's own API implies it should, since it's the only tenant identifier provided) to select which merchant's records to update/create/delete based on webhook data will apply the attacker-controlled body under the victim's shop identity — i.e., cross-tenant data injection/corruption through this gem's own webhook-processing API, without requiring `api_secret_key`, an access token, or any other privileged credential belonging to the victim.

### Likelihood Explanation
Exploitability requires only that the attacker control (or previously subscribe to) some shop that has the target app installed, so they can generate a genuinely-signed `(body, hmac)` pair using the shared app secret, and then send that pair with a spoofed `shopify-shop-domain` header to the app's public webhook receiver endpoint. No leaked secrets or elevated privileges are needed beyond being a normal merchant with the app installed — satisfying the "unprivileged internet user" bar.

### Recommendation
Include the shop domain (and ideally webhook id/topic) inside the signed material that `HmacValidator` verifies, or explicitly cross-check that the `shop` header matches an expected/allow-listed shop for the given signature/session before constructing `WebhookMetadata`, rather than treating the header as trusted merely because the HMAC over the body passed.

### Proof of Concept
1. Attacker registers/owns Shop A (same app installed) and triggers any webhook topic, capturing the exact `raw_body`, and the resulting `shopify-hmac-sha256` value computed by Shopify with the shared app secret.
2. Attacker replays this request to the app's webhook endpoint, but replaces the `shopify-shop-domain` header with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and compares to the (still valid, since body unchanged) received HMAC [6](#0-5) , so validation succeeds.
4. The handler is invoked with `shop: "victim-shop.myshopify.com"` and the attacker's body [4](#0-3) , causing the host application to process attacker-controlled data under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
