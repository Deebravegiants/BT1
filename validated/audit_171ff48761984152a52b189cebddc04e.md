### Title
Missing Bound on GRANDPA Justification Ancestry Headers Enables Unsigned-Extrinsic CPU/Memory DoS - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
The Apache CXF advisory (CVE-2013-2160) describes a DoS caused by an XML parser that accepts arbitrarily large numbers of elements/attributes/nested constructs without any size validation before doing expensive processing. The Hyperbridge GRANDPA consensus client has an analogous defect: `GrandpaJustification<H>` and `FinalityProof<H>` carry unbounded `Vec<H>` fields (`votes_ancestries`, `unknown_headers`) that are SCALE-decoded straight from attacker-controlled bytes and then fed into `O(n)`-per-precommit ancestry-walk logic, with **no upper bound on the number of headers** before this expensive work begins. Because GRANDPA consensus messages are submitted via the permissionless, fee-free `handle_unsigned` extrinsic (`pallet_ismp`), this is reachable by any unprivileged relayer/submitter with a single unsigned extrinsic.

### Finding Description
`GrandpaJustification<H>` is defined with an unbounded ancestry vector: [1](#0-0) 

`FinalityProof<H>` likewise carries an unbounded `unknown_headers: Vec<H>`: [2](#0-1) 

Both structures are decoded directly from bytes supplied in the `ConsensusMessage` proof, with no cap on `Vec` length checked before or during decode: [3](#0-2) 

and again in `verify_with_voter_set`, which decodes `votes_ancestries` implicitly (already decoded by the caller) and then, for every precommit in the commit, builds an `AncestryChain` over the *entire* `votes_ancestries` vector and walks a chain of parent-hash lookups per precommit: [4](#0-3) 

`AncestryChain::new` clones every header into a `BTreeMap` (O(n log n) allocation/hash work over the whole vector), and `ancestry()` walks parent-hash chains for **each precommit** in `commit.precommits`: [5](#0-4) 

There is no limit anywhere in this path on:
- the number of headers in `votes_ancestries` / `unknown_headers`,
- the number of precommits in `commit.precommits`,
- the size of each `Header` (digest logs, extrinsics root, etc., which are themselves unbounded `Vec<u8>`/`Vec<DigestItem>` in Substrate headers).

Compare this to the Pharos SPV verifier in the same codebase, which explicitly caps proof depth to defend against exactly this class of bug: [6](#0-5) 

No equivalent `MAX_ANCESTRY_LEN` / `MAX_PRECOMMITS` bound exists for the GRANDPA justification path. This is the same root cause pattern as CVE-2013-2160: a parser/verifier accepts an unbounded collection from untrusted input and performs work proportional to its size before any sanity/size check rejects it.

This proof is reachable from the free, permissionless entry point `pallet_ismp::handle_unsigned`, which executes messages — including `ConsensusMessage`s routed to the GRANDPA consensus client — for any unsigned submitter: [7](#0-6) 

The `ValidateUnsigned::validate_unsigned` implementation itself calls `Self::execute(messages.clone())`, meaning **the expensive decode-and-verify path runs during transaction-pool validation** — i.e., merely gossiping/validating the extrinsic (not even including it in a block) already pays the full ancestry-walk cost: [8](#0-7) 

An attacker can submit a `ConsensusMessage::StandaloneChain` or `ConsensusMessage::Relaychain` GRANDPA message whose `finality_proof.unknown_headers` and `justification.votes_ancestries` contain a very large number of headers (each with padded digest data) and whose `commit.precommits` contains many precommits referencing scattered targets in that header set, forcing:
1. SCALE decode of a large `Vec<Header>` (memory allocation proportional to attacker-chosen size),
2. `AncestryChain::new` building a `BTreeMap` over all headers (hashing + allocation),
3. an O(precommits × chain-depth) walk in `verify_with_voter_set`,
before the (necessarily failing, since it's not a real chain) signature/ancestry check ultimately rejects the message — but only after the CPU/memory cost has already been spent, repeatedly, for free, by every node validating the unsigned extrinsic in the transaction pool.

### Impact Explanation
Because `handle_unsigned` is fee-free and unsigned, and the cost is paid at `validate_unsigned` time (transaction-pool validation, run by every node that receives the gossiped extrinsic), an attacker can repeatedly submit crafted GRANDPA `ConsensusMessage`s with maximally-sized header/precommit vectors to force full-node CPU and memory consumption network-wide, with no economic cost (no fee, no stake). This matches the CWE-112 “missing validation causing CPU/memory DoS” class from the report and directly threatens the Hyperbridge relayer/collator network’s ability to process legitimate consensus updates and deliver messages (a “route unable to deliver messages” condition), which is explicitly in-scope impact for this analog search. Severity is Medium, consistent with the source advisory’s DoS classification, since this is a resource-exhaustion vector rather than fund theft or forged state.

### Likelihood Explanation
High reachability: `handle_unsigned` is explicitly documented as callable by anyone for free, and consensus messages are one of the message types processed there. No stake, signature, or fee gates this path — only the (post-hoc, expensive-to-reach) proof validity check does. The only mitigating factor is that constructing headers that are individually large still requires valid SCALE encoding (cheap to produce) and that eventually `finality_grandpa::validate_commit` / `AncestryChain::ancestry` will return an error for a bogus chain — but this rejection happens only *after* the decode and O(n) map-build/walk work, not before it.

### Recommendation
- Add explicit upper bounds (e.g., `MAX_ANCESTRY_HEADERS`, `MAX_UNKNOWN_HEADERS`, `MAX_PRECOMMITS`) checked immediately after SCALE-decoding `GrandpaJustification`/`FinalityProof`, before any `AncestryChain::new` or ancestry walk is performed — mirroring the `MAX_PROOF_DEPTH` guard already used in `modules/consensus/pharos/primitives/src/spv.rs`.
- Consider bounding these collections at the type level using `codec`'s bounded-vec decoding (`BoundedVec`) so oversized payloads fail to decode rather than allocate first.
- If `validate_unsigned` must re-run full `execute()` logic, ensure a cheap size/bound pre-check runs before any decode of nested `Vec<Header>` structures, so pool validation cannot be forced to do unbounded work.

### Proof of Concept
1. Construct a `ConsensusMessage::StandaloneChain` (or `::Relaychain`) whose `FinalityProof.unknown_headers` contains e.g. tens of thousands of synthetic `Header`s (chained by `parent_hash`, each header padded with large digest logs) and whose `GrandpaJustification.commit.precommits` list references many different target hashes scattered throughout that header set, and whose `votes_ancestries` similarly contains a large number of headers.
2. SCALE-encode this into the `proof` field of a `ConsensusMessage` inside a `Message::Consensus`, and submit it via `Ismp::handle_unsigned` as an unsigned extrinsic.
3. Observe that every node performing `validate_unsigned` (transaction pool validation) must fully SCALE-decode the large header vectors and run `AncestryChain::new` (BTreeMap build over all headers) plus one `ancestry()` walk per precommit in `verify_with_voter_set`, before the message is ultimately rejected (invalid signatures/ancestry) — repeatable indefinitely at zero cost to the attacker, since no fee or stake is charged for a rejected unsigned extrinsic that never reaches block inclusion.

*(Note: exact confirmation of on-chain resource limits — e.g., whether extrinsic byte-size limits or `max_rpc_payload_size` might partially cap the header vector before it reaches this code — was not fully explorable within available tooling; the codebase does not show any explicit `Vec<Header>` length cap in the GRANDPA justification/verifier modules examined.)*

	pub fn verify_with_voter_set(
		&self,
		set_id: u64,
		voters: &VoterSet<AuthorityId>,
	) -> Result<(), anyhow::Error> {
		use finality_grandpa::Chain;

		let ancestry_chain = AncestryChain::<H>::new(&self.votes_ancestries);

		match finality_grandpa::validate_commit(&self.commit, voters, &ancestry_chain) {
			Ok(ref result) if result.is_valid() => {
				if result.num_duplicated_precommits() > 0 ||
					result.num_invalid_voters() > 0 ||
					result.num_equivocations() > 0
				{
					Err(anyhow!("Invalid commit, found one of `duplicate precommits`, `invalid voters`, or `equivocations` {result:?}"))?
				}
			},
			err => {
				let result = err.map_err(|_| {
					anyhow!("[verify_with_voter_set] Invalid ancestry while validating commit!")
				})?;
				Err(anyhow!("invalid commit in grandpa justification: {result:?}"))?
			},
		}

		// we pick the precommit for the lowest block as the base that
		// should serve as the root block for populating ancestry (i.e.
		// collect all headers from all precommit blocks to the base)
		let base_hash = self
			.commit
			.precommits
			.iter()
			.map(|signed| &signed.precommit)
			.min_by_key(|precommit| precommit.target_number)
			.map(|precommit| precommit.target_hash.clone())
			.expect(
				"can only fail if precommits is empty; \
				 commit has been validated above; \
				 valid commits must include precommits; \
				 qed.",
			);

		let mut visited_hashes = BTreeSet::new();
		for signed in self.commit.precommits.iter() {
			let message = finality_grandpa::Message::Precommit(signed.precommit.clone());

			check_message_signature::<_, _>(
				&message,
				&signed.id,
				&signed.signature,
				self.round,
				set_id,
			)?;

			if base_hash == signed.precommit.target_hash {
				continue;
			}

			let route = ancestry_chain
				.ancestry(base_hash, signed.precommit.target_hash)
				.map_err(|_| anyhow!("[verify_with_voter_set] Invalid ancestry!"))?;
			// ancestry starts from parent hash but the precommit target hash has been
			// visited
			visited_hashes.insert(signed.precommit.target_hash);
			for hash in route {
				visited_hashes.insert(hash);
			}
		}

		let ancestry_hashes: BTreeSet<_> =
			self.votes_ancestries.iter().map(|h: &H| h.hash()).collect();

		if visited_hashes != ancestry_hashes {
			Err(anyhow!(
				"invalid precommit ancestries in grandpa justification with unused headers",
			))?
		}

		Ok(())
	}

/// A utility trait implementing `finality_grandpa::Chain` using a given set of headers.
/// This is useful when validating commits, using the given set of headers to
/// verify a valid ancestry route to the target commit block.
pub struct AncestryChain<H: HeaderT> {
	ancestry: BTreeMap<H::Hash, H>,
}

impl<H: HeaderT> AncestryChain<H> {
	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
