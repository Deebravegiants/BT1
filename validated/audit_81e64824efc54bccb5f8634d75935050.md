### Title
Quadratic-gas denial of service in `Codec.Encode(Commitment)` via unbounded BEEFY payload array - ([File: evm/src/consensus/Codec.sol])

### Summary
`Codec.Encode(Commitment)` rebuilds its `payload` byte buffer with `bytes.concat` inside a loop over `commitment.payload`. Each iteration reallocates and copies the entire accumulated buffer, so encoding cost is quadratic in the number of payload items. This function is invoked on every submitted BEEFY consensus proof in `EcdsaBeefy.verifyMmrUpdateProof`, and `commitment.payload` is fully attacker-controlled data decoded straight out of the calldata proof that any unprivileged relayer submits via `handleConsensus`.

### Finding Description
`Codec.Encode(Commitment)` [1](#0-0)  builds the SCALE encoding of a BEEFY commitment:

```solidity
function Encode(Commitment memory commitment) internal pure returns (bytes memory) {
    uint256 payloadLen = commitment.payload.length;
    bytes memory payload = bytes("");
    for (uint256 i = 0; i < payloadLen; i++) {
        payload = bytes.concat(
            payload,
            abi.encodePacked(commitment.payload[i].id),
            ScaleCodec.encodeBytes(commitment.payload[i].data)
        );
    }
    ...
}
```

`bytes.concat` in Solidity always allocates a brand-new byte array and copies every input into it. Because `payload` is both an input and the output of the concat call on every loop iteration, each iteration copies the entire, ever-growing accumulated buffer rather than only the newly appended bytes — the same defect class as the `SmartPunctExtension`/`AttributesExtension` quadratic re-copy in the reference advisory (`AdjacentTextMerger` reading-and-rewriting the whole literal on every merge). For `k` payload entries this costs `O(k^2)` in the total payload byte size, not `O(k)`.

This function is reachable from a fully untrusted input path. `EcdsaBeefy.verify()` is the pure entry point invoked by the consensus router when anyone submits a BEEFY consensus proof (via `HandlerV2.handleConsensus`, permissionless). It decodes `proof` directly from calldata into `(RelayChainProof, ParachainProof)` [2](#0-1) , and then calls `verifyMmrUpdateProof`, which computes:

```solidity
bytes32 commitmentHash = keccak256(Codec.Encode(commitment));
``` [3](#0-2) 

`commitment.payload` is an array of `(bytes2 id, bytes data)` items taken verbatim from the relayer-supplied `RelayChainProof.signedCommitment.commitment.payload`. Nothing bounds the number of payload entries or the size of `data` before `Codec.Encode` is invoked — the only checks before this line are a stale-height comparison, an authority-set-id match, and a signature-count threshold check, none of which limit payload array length or byte size.

### Impact Explanation
Because `handleConsensus` is a permissionless entry point that any relayer/dispatcher can call with an arbitrary proof, an attacker can craft a `Commitment` whose `payload` array has many entries (each carrying attacker-chosen `data` bytes) to blow up the gas cost of `Codec.Encode` quadratically. This can be used to:
- Force `verify()` calls (and hence any `handleConsensus`/consensus-update transaction) to consume disproportionately large gas relative to input size, up to the point of exceeding the block gas limit and reverting — effectively a DoS against consensus updates on the chain, blocking honest relayers from landing new BEEFY state and stalling message delivery (`EvmHost`/`HandlerV2` dispatch pipeline depends on fresh consensus state).
- Grief relayers/gas payers by forcing them to either pay excessive gas or have their transaction revert out-of-gas, since `estimate_gas`-driven relaying (as used by the tesseract relayer, e.g. `tesseract/messaging/evm/src/tx.rs`) would need to budget for the worst case or fail.

This matches the "route unable to deliver messages" / availability-impact criterion: a malicious relayer can submit a consensus proof engineered to be maximally expensive to encode, denying timely consensus updates and hence blocking downstream request/response delivery that depends on them.

### Likelihood Explanation
High. Submitting a consensus proof through `handleConsensus` requires no special privilege — this is exactly the "unprivileged... relayer" pattern for reachability the analysis targets. Crafting a `Commitment` with an inflated `payload` array is trivial: the caller fully controls the ABI-encoded `proof` bytes decoded in `EcdsaBeefy.verify`, and no length/size cap exists on `commitment.payload` prior to encoding.

### Recommendation
Rewrite `Codec.Encode(Commitment)` to avoid re-copying the accumulated buffer on every iteration:
- Precompute the total encoded length of all payload entries in a first pass, allocate a single fixed-size `bytes` buffer once, and write each entry's bytes directly into its computed offset (e.g. via low-level `mcopy`/assembly or a single `abi.encodePacked` over precomputed slices) instead of calling `bytes.concat` inside the loop.
- Alternatively, accumulate encoded parts into a `bytes[]` and perform exactly one final `bytes.concat` (or manual single-pass copy) over all parts, so total work is linear in total payload size.
- Additionally, consider bounding `commitment.payload.length` (and/or total encoded payload size) to a sane maximum before entering the loop, since even a corrected linear-time encoder should not process unbounded relayer-supplied payload arrays without an upper limit.

### Proof of Concept
1. Construct a `BeefyConsensusProof` (`RelayChainProof`, `ParachainProof`) whose `signedCommitment.commitment.payload` array contains, e.g., 5,000–20,000 entries, each with a small non-empty `data` field (to maximize the per-iteration copy volume while staying within calldata/gas limits for submission).
2. Ensure `commitment.validatorSetId` matches a known authority set and the signature count meets the supermajority threshold check (`checkParticipationThreshold`) so execution reaches `Codec.Encode(commitment)` at line 152 of `EcdsaBeefy.sol` before any authority-signature verification fails — the quadratic cost is paid regardless of whether the proof is ultimately valid, since it occurs before `ECDSA.recover`/merkle-multi-proof checks in the same function.
3. Call `EcdsaBeefy.verify(previousState, proof)` (directly, or via `HandlerV2.handleConsensus`) and measure gas: gas cost should scale quadratically with payload array length, causing the transaction to approach or exceed the block gas limit for a payload size that would be cheap under correct linear-time encoding — mirroring the 34.9s vs 0.069s blow-up cited in the analog `SmartPunctExtension` report.
