### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request by computing an HMAC over the raw request body only, then hands the caller-supplied `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers to the app's handler as trusted tenant-identifying metadata. None of these headers are part of the signed bytes, so the cryptographic proof and the value used to attribute the event to a merchant are decoupled.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it against the `hmac-sha256`/`x-shopify-hmac-sha256` header value: [2](#0-1) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all parsed straight from unsigned headers: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately constructs `WebhookMetadata` using `request.shop`, handing it to the app's handler as the tenant identity for the event: [4](#0-3) 

The identity binding the gem should enforce is:
`bytes(raw_body) signed by api_secret_key == bytes the handler attributes to shop X`

What is actually enforced is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

with `shop` (and `topic`/`webhook_id`/`api_version`) parsed from headers that are outside that signed payload. Any unprivileged internet user who can obtain one legitimately-signed `(raw_body, hmac)` pair for a topic the app processes — trivial for a public app, since anyone can install it in their own development shop and receive real webhooks for their own store — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to host applications: an app author reasonably assumes that if `Utils::HmacValidator.validate` passes, the entire `Webhooks::Request` (including which shop it is for) originated from Shopify for that specific shop. Because the shop identity is not bound to the signature, an attacker can cause the host application to process an authentic, HMAC-valid webhook payload under a different merchant's identity, leading to cross-tenant data corruption or disclosure in any app that uses `WebhookMetadata#shop` to select which merchant's session/records to update (a very common pattern, and the one demonstrated in the gem's own webhook docs).

### Likelihood Explanation
Any user can install a public Shopify app for free (or interact with any endpoint that emits Shopify webhooks they are entitled to receive) to legitimately capture one valid `(raw_body, x-shopify-hmac-sha256)` pair for a topic of interest, then replay it against the same public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or any credential is required — only network access to the target app's public webhook endpoint. This is a low-effort, low-privilege attack path.

### Recommendation
Bind the shop (and ideally topic/webhook id) to the verified bytes rather than trusting the header in isolation:
- Require host applications to cross-check `request.shop` against the shop associated with the currently-active session/store *before* trusting it, and document this requirement prominently, or
- Extend `VerifiableQuery`/`Request#to_signable_string` (or `Registry.process`) to incorporate the `shop`, `topic`, and `webhook_id` header values into what is verified against a per-shop secret/session record, so that a replayed body cannot be re-attributed to a different shop, or
- At minimum, have `Registry.process` reject requests where `request.shop` does not match an expected/known installed shop before invoking the handler.

### Proof of Concept
1. Attacker installs the target public app on their own development shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's real `api_secret_key`, which the attacker never sees).
2. Attacker POSTs to the app's public webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. Server builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac: H...})` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(B, api_secret_key)`, which still equals `H` (the body wasn't changed), so validation passes. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from, and was signed for, `attacker.myshopify.com`'s installation — a cross-tenant identity spoof with a cryptographically "valid" webhook.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
