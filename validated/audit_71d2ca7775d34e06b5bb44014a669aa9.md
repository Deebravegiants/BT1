Based on my investigation, I found the relevant analog in `pallet-ismp-relayer`'s fee accumulation/withdrawal flow, which mirrors the exact bug class from the external report: no minimum enforced on the "deposit" (fee accumulation) side, but a minimum enforced on the "withdrawal" side.

### Title
Relayer fee accumulation has no minimum cap while withdrawal enforces a governance-settable minimum, permanently freezing sub-threshold balances - ([File: modules/pallets/relayer/src/accumulate.rs], [File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::accumulate` (the "deposit" side of relayer fee accounting) credits `Fees::<T>` for any nonzero `total_fee` proven by a delivery proof, with no lower bound. [1](#0-0)  `Pallet::withdraw` (the "withdrawal" side) rejects the withdrawal unless the accumulated balance is at least `MinimumWithdrawalAmount::<T>::get(dest_chain)`, defaulting to `MinWithdrawal` ($10 equivalent) when governance hasn't set a per-chain override. [2](#0-1) [3](#0-2) 

### Finding Description
Just as in the reported VUSD issue — where deposits have no minimum but withdrawals require ≥5 VUSD — the relayer fee pallet allows crediting arbitrarily small (even single-wei-equivalent) amounts into `Fees::<T>` via `accumulate`/`accumulate_fee_and_deposit_event`, but `withdraw` categorically refuses to dispatch a withdrawal request unless the balance clears `min_withdrawal_amount(dest_chain).unwrap_or(MinWithdrawal::get())`. [2](#0-1)  Governance can also independently raise this floor per-chain via `set_minimum_withdrawal`, further widening the gap between what can be credited and what can be withdrawn. [4](#0-3) 

There is no partial-withdraw, no cross-chain aggregation of a relayer's balance, and no sweep/dust-recovery mechanism in this pallet — the only way out of `Fees::<T>` is `withdraw`, which is all-or-nothing and gated by the minimum. [5](#0-4)  Consequently, a relayer whose accumulated balance on a given destination chain never again crosses the minimum threshold (e.g. it delivers a single low-fee message to a chain with sparse cross-chain traffic, or governance later raises `MinimumWithdrawalAmount` above an already-accumulated balance) has that balance permanently and unconditionally stuck: it can never be reduced to zero nor withdrawn.

### Impact Explanation
Funds credited to `Fees::<T>` for a legitimate relayer are provably unrecoverable once trapped below the (possibly governance-raised) minimum, since neither `accumulate` nor `withdraw` — the only two entry points touching this storage — offer a path to reclaim a sub-threshold balance. This is a permanent, protocol-level freeze of funds belonging to relayers who performed real delivery work and are entitled to the fee. Because `set_minimum_withdrawal` is callable by governance at any time for any `StateMachine`, previously-withdrawable balances can retroactively become frozen without the relayer having any way to react before the raise applies.

### Likelihood Explanation
This requires no attacker action beyond normal relayer operation: relaying a small number of low-value messages to a chain with limited fee traffic, or a chain that goes quiet after a relayer's single delivery, is a realistic and unprivileged occurrence for any of Hyperbridge's many connected chains. Governance raising `MinimumWithdrawalAmount` is a routine parameter-tuning action, not an attack, yet it can strand existing balances as a side effect.

### Recommendation
- Add a partial/sweep withdrawal path so relayers (or governance, via a dust-sweep call) can reclaim balances below the per-chain minimum, e.g., allowing an explicit `min_amount = 0` withdrawal, or a slower/aggregate path.
- Alternatively, enforce the same minimum at `accumulate` time (reject or hold fee credits below the same floor until they cumulatively clear it, similar to VUSD's recommendation to mirror the deposit-side check against the withdrawal-side check) so a single delivery's proceeds are never smaller than what can eventually be withdrawn.
- When governance raises `MinimumWithdrawalAmount` for a chain, grandfather existing sub-threshold balances or provide a one-time migration path so no relayer's already-earned fees become retroactively frozen.

### Proof of Concept
1. Relayer A delivers a single cross-chain message to `StateMachine::Evm(X)` whose associated fee, once proven via `accumulate_fees`, credits `Fees::<T>::get(Evm(X), A) = 3 * 10^18` (i.e., $3 equivalent) — below the default `MinWithdrawal` of $10. [1](#0-0) 
2. Chain `Evm(X)` receives no further cross-chain traffic relayed by A (or by anyone, if it's a low-volume chain), so `Fees::<T>` for A on `Evm(X)` never grows past $10.
3. Relayer A calls `withdraw_fees` with `dest_chain = Evm(X)`; the extrinsic reverts with `Error::<T>::NotEnoughBalance` because `available_amount < MinWithdrawal::get()`. [2](#0-1) 
4. No other pallet call can reduce, sweep, or otherwise clear this balance — it remains permanently locked in `Fees::<T>`.

	pub fn withdraw(withdrawal_data: WithdrawalInputData) -> DispatchResult {
		let address = match &withdrawal_data.signature {
			Signature::Evm { address, .. } => address.clone(),
			Signature::Sr25519 { public_key, .. } => public_key.clone(),
			Signature::Ed25519 { public_key, .. } => public_key.clone(),
		};

		let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);
		let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());

		match &withdrawal_data.signature {
			Signature::Evm { address, .. } => {
				let eth_address = withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
				if &eth_address != address {
					Err(Error::<T>::InvalidPublicKey)?
				}
			},
			Signature::Sr25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
			Signature::Ed25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
		};
		let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());

		if available_amount <
			Self::min_withdrawal_amount(withdrawal_data.dest_chain)
				.unwrap_or(MinWithdrawal::get())
		{
			Err(Error::<T>::NotEnoughBalance)?
		}

		let dispatcher = <T as Config>::IsmpHost::default();

		Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| {
			*value += 1;
			Ok::<(), ()>(())
		})
		.map_err(|_| Error::<T>::ErrorCompletingCall)?;

		let beneficiary_address = withdrawal_data.beneficiary.clone().unwrap_or(address.clone());
		let (to, body) = match withdrawal_data.dest_chain {
			s if s.is_substrate() => (
				HYPERBRIDGE_MODULE_ID.to_vec(),
				Message::WithdrawRelayerFees(WithdrawalRequest {
					amount: available_amount.low_u128(),
					account: AccountId32::try_from(&beneficiary_address[..])
						.map_err(|_| Error::<T>::InvalidPublicKey)?,
				})
				.encode(),
			),
			_ => {
				let HostParam::EvmHostParam(params) =
					HostParams::<T>::get(withdrawal_data.dest_chain)
						.ok_or_else(|| Error::<T>::MissingMangerAddress)?;

				let body = WithdrawalParams {
					beneficiary_address: beneficiary_address.clone(),
					amount: available_amount.into(),
					token: params.fee_token,
				}
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidPublicKey)?;

				(params.host_manager.0.to_vec(), body)
			},
		};

		let post = DispatchPost {
			dest: withdrawal_data.dest_chain,
			from: MODULE_ID.to_vec(),
			to,
			body,
			timeout: 0,
		};

		// Account is not useful in this case
		dispatcher
			.dispatch_request(
				DispatchRequest::Post(post),
				FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
			)
			.map_err(|_| Error::<T>::DispatchFailed)?;

		Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());

		Self::deposit_event(Event::<T>::Withdraw {
			address: sp_runtime::BoundedVec::truncate_from(address.clone()),
			beneficiary_address: sp_runtime::BoundedVec::truncate_from(beneficiary_address),
			state_machine: withdrawal_data.dest_chain,
			amount: available_amount,
		});

		Ok(())
	}
