### Title
Fee destination (`circomData.relay`) and fee token are unsigned, letting anyone front-run a victim's Emporium message to redirect the wallet's `maxFee` payment to an attacker-controlled relay - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The EIP-712 `EmporiumSignature` typed data that a `HinkalWallet` owner signs only commits to `emporiumMessage`, the `ops` array, `maxFee`, and `deadline` — it never commits to `circomData.relay` or `feeStructure.feeToken`. Anyone who observes a valid, not-yet-consumed `(circomData, deltaAmountChanges, proof)` bundle carrying that signature (e.g. in the mempool, or via a relay network before submission) can resubmit it with `circomData.relay` set to their own address and `feeStructure.flatFee` maxed out to `stack.maxFee`, causing `HinkalWallet.doSendToRelay` to pay the fee token to the attacker instead of the intended relay.

### Finding Description
The equality that should hold is: **(destination, amount) of funds leaving the wallet == (destination, amount) the wallet owner signed**. Tracing `verifyWallet`: [1](#0-0) 

the signed hash only binds `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline`. The only fee-related check is a bound, not an identity commitment: [2](#0-1) 

`circomData.relay` and `feeStructure.feeToken` are read straight from calldata and never appear in the signed payload: [3](#0-2) 

The path `payRelayFees` → `payRelay` → `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)`: [4](#0-3) 

then unconditionally moves the wallet's own ERC-20 balance to `relay` inside `HinkalWallet`: [5](#0-4) 

`doSendToRelay` is `onlyEmporium`-gated but performs no check that `relay` matches anything the wallet owner authorized — it trusts whatever `EmporiumUpgradeable` passes in. Because `relay` and `feeToken` sit outside the signed struct, the guard `verifyWallet` provides authenticity only over *who* signed and an upper bound on the fee amount, not over *where* it goes.

One correction to the scenario as literally stated: `stack.signerAddress` cannot be freely "set" by the attacker to an arbitrary victim wallet, because `ECDSA.tryRecover(hashedMessage, stack.v, stack.r, stack.s) == stack.signerAddress` is enforced — the attacker cannot forge a signature for a wallet whose key they don't hold. However, the exploit does not require forgery: the attacker only needs to reuse an already-existing, still-unconsumed signed message (captured from the mempool/relay network before it lands on-chain) and change the *unsigned* fields (`circomData.relay`, `feeStructure.feeToken`, and set `flatFee` to the maximum permitted by `stack.maxFee`). `usedMessages[circomData.emporiumMessage]` only prevents a second successful use, so this is a front-running race, not a replay-after-consumption.

### Impact Explanation
An attacker who wins this race redirects up to `stack.maxFee` of fee-token funds held in the victim's `HinkalWallet` to an address the wallet owner never authorized, and simultaneously griefs the legitimate relay (whose valid signed message now reverts with `UsedMessage`). This is theft of relay/protocol-fee-equivalent funds moved from a wallet by an action the owner did not authorize the destination for — matching the "High: theft ... of protocol/relay fees ... moving assets a wallet owner ... never authorised" category.

### Likelihood Explanation
Preconditions: a victim must have produced a valid, still-pending `EmporiumStack` signature plus a valid ZK proof for the surrounding `runAction` call, and this pending transaction must be observable before inclusion (mempool visibility, or a relay-network broadcast channel). The attacker must also supply their own valid proof/CircomData for the rest of the call (deposits/other UTXO fields), which the rules confirm attackers can craft for their own funds/UTXOs. This is a feasible, repeatable MEV-style front-run for any observable Emporium transaction with a nonzero flat fee, requiring only gas cost and faster inclusion, no privileged role or victim key.

### Recommendation
Include `circomData.relay` and `feeStructure.feeToken` (and ideally the full `feeStructure`) inside the `EMPORIUM_SIGNATURE_TYPEHASH` payload so the wallet owner explicitly authorizes both the fee amount and its destination/token, closing the gap that lets an unsigned field determine where funds are sent.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a `HinkalWallet` for a victim EOA, fund the wallet with fee token.
2. Victim signs an `EmporiumStack` (`ops`, `maxFee = X`, `deadline`, `emporiumMessage = M`) intended for legitimate relay `R1` with `flatFee = small`.
3. Before this transaction is mined, attacker constructs their own `runAction` call using the identical `(v,r,s)`, `emporiumMessage = M`, `ops`, `maxFee`, `deadline` (all signed fields unchanged) but sets `circomData.relay = attackerAddr` and `feeStructure.flatFee = X` (i.e., maxed to `stack.maxFee`), supplying a locally generated valid snarkjs proof for the surrounding call.
4. Assert: (a) attacker's transaction succeeds, wallet fee-token balance decreases by `X` and `attackerAddr` balance increases by `X`; (b) `usedMessages[M] == true`; (c) the victim's originally intended transaction to `R1` now reverts with `UsedMessage`, proving `R1` never received the fee while `attackerAddr` did — demonstrating the destination/amount actually moved diverges from what the owner's signature constrained.

```text
    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }
```
