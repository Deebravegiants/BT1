### Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature verified by `HmacValidator` covers the payload bytes but not the `shop-domain`, `topic`, or `webhook-id` headers. Yet `Registry.process` trusts `request.shop` (and `request.topic`/`request.webhook_id`) as the authoritative tenant identity when dispatching to the app's handler. An attacker who can obtain one valid `(body, hmac)` pair — trivially, by triggering a webhook on their own store, which they legitimately own — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header. The signature check still passes because it only ever validated the body, letting the attacker impersonate any other shop to the app's webhook handler.

### Finding Description
The binding that should hold is:
`shop value trusted by the webhook handler == shop value cryptographically bound by the HMAC signature`

In this gem that equality is broken:

- `HmacValidator.validate` computes/verifies the signature over `verifiable_query.to_signable_string` [2](#0-1) .
- For webhook requests, `to_signable_string` is defined to be only `@raw_body`, deliberately excluding all headers: [3](#0-2) .
- `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers with no cryptographic tie to the body: [4](#0-3) .
- `Registry.process` validates only the HMAC of the body, then immediately hands `request.shop` to the app's handler as the trusted tenant identity for that webhook event: [5](#0-4) .

Because the header carrying the tenant identity (`shop`) is disjoint from the bytes actually covered by the HMAC, any request whose body/HMAC pair is valid for *some* shop is accepted as valid for *any* shop the attacker chooses to put in the header. The webhook endpoint is a public HTTP endpoint exposed by the host app (per `docs/usage/webhooks.md`), reachable by an unauthenticated internet user, so this is not a host-application misuse issue — the gem's own `process`/`HmacValidator`/`Request` implementation performs the identity check incorrectly.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who owns/controls one Shopify store can capture one legitimate webhook body+HMAC (e.g. an `orders/create` payload) from their own shop, then replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header set to a victim shop's domain. The app's webhook handler (built on this gem's documented API, using `WebhookMetadata#shop`) will process the event as if it genuinely originated from the victim shop — e.g. creating/updating tenant-scoped data keyed by the spoofed shop, or triggering shop-specific side effects (fulfilment, billing, notifications) attributed to the wrong tenant. This matches the "cross-tenant access" impact category, since the app is misled into acting under a different tenant's identity than the one the request was actually authenticated for.

### Likelihood Explanation
Likelihood is high for an attacker willing to invest minimal effort: they only need a legitimate Shopify development/trial store (freely obtainable) to generate one authentic webhook delivery, capture the raw body and `X-Shopify-Hmac-Sha256` header, and replay it with a forged shop-domain header to the target app's public webhook URL. No secrets, tokens, or privileged access are required — `api_secret_key` is never needed by the attacker since the HMAC from their own legitimate delivery is reused unmodified.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, and ideally `topic`/`webhook-id`) in the material that is HMAC-verified, or otherwise cryptographically bind them to the payload before trusting them. Since Shopify's webhook HMAC is computed by Shopify only over the raw body, the app-side mitigation is to additionally validate that the `shop-domain` header corresponds to a shop with an active, known installation/session before treating `request.shop` as authoritative, and to document this requirement clearly, rather than presenting `WebhookMetadata#shop` as a value safe to trust outright.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a real webhook event (e.g. `orders/create`), capturing:
   - raw body `B`
   - header `X-Shopify-Hmac-Sha256: H` (valid because `HMAC_SHA256(secret, B) == H`)
2. Attacker sends a POST to the app's webhook endpoint with:
   - body `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - header `X-Shopify-Shop-Domain: victim.myshopify.com` (forged)
   - header `X-Shopify-Topic: orders/create` (unchanged/forged)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers into `shop`/`topic` [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H` [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` [8](#0-7) , causing the app to process an order event as belonging to `victim.myshopify.com` despite it never originating from that shop.
