### Title
Fee-on-transfer tokens cause escrow-accounting insolvency in `IntentGatewayV2.placeOrder` (Tron variant) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` credits an order's escrow with a value derived from the user-supplied `order.inputs[i].amount` instead of the tokens actually received by the contract, so fee-on-transfer (FoT) ERC-20 inputs cause the recorded escrow to exceed the gateway's real token balance for that order.

### Finding Description
In the non-predispatch branch of `placeOrder`, the contract pulls tokens with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then increments escrow using `reducedInputs[i].amount`, a value computed purely from `order.inputs[i].amount` (minus protocol fee) before the transfer even executes: [1](#0-0) 

`reducedInputs` and the `commitment` hash are both derived from the caller-specified `order.inputs`, computed earlier in the function, with no measurement of actual balance change: [2](#0-1) 

For a fee-on-transfer token, `IERC20(token).balanceOf(address(this))` increases by less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is still incremented by the full (fee-inclusive) `reducedInputs[i].amount`. This is the same root cause identified in the referenced Sherlock report for `DonationVotingMerkleDistributionVaultStrategy` — using the transfer parameter rather than the observed balance delta.

Notably, the sibling, non-Tron implementation of the same contract already fixes this exact issue by snapshotting balances and mutating `order.inputs[i].amount` to the actually-received amount before computing fees/commitment/escrow: [3](#0-2) 
This is proven correct by the project's own fee-on-transfer regression tests for the main contract: [4](#0-3) 

The Tron variant lacks this balance-based accounting entirely in its non-predispatch path, so the discrepancy is not merely theoretical — it is a regression relative to the fixed sibling implementation.

Even in the predispatch branch, dust is computed only from the first leg of the transfer (`dispatcher`'s balance vs. `requiredAmount`), but the escrow credited is still `reducedInputs[i].amount`, not the balance actually landing in `address(this)` after the second `transfer` call — so a FoT token applied on that second leg is also unaccounted for: [5](#0-4) 

### Impact Explanation
`_orders[commitment][token]` is a shared escrow ledger used by other order lifecycle functions (fill/redeem/refund/cancel) that pay out based on this recorded value rather than actual on-chain balance. Because multiple orders can escrow the same token, over-crediting one order's escrow relative to its real token balance creates an accounting deficit in the pooled ledger: the sum of all `_orders[...][token]` entries can exceed `IERC20(token).balanceOf(address(this))`. This leads to either failed payouts (reverts due to insufficient balance, freezing legitimate funds/orders) or first-come-first-served withdrawal of one user's escrow using funds effectively belonging to another user's order for the same token — an insolvency condition that can result in permanent freezing of some users' funds or unauthorized draining of the escrow pool intended for a different order.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `placeOrder` with a fee-on-transfer/deflationary ERC-20 as an input asset — a single, direct, permissionless transaction. No special privileges, governance, or collusion are required; the only precondition is that the affected token contract charges a transfer fee, which is common among real-world tokens (e.g., certain reflection/tax tokens).

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`/sweep call, use the actual balance delta to mutate `order.inputs[i].amount`, and compute `reducedInputs`, the commitment hash, and the escrow credit from that measured amount rather than the caller-supplied parameter. Apply the same balance-delta measurement to the final leg of the predispatch sweep so double-taxed transfers are also correctly accounted for.

### Proof of Concept
1. Deploy a fee-on-transfer ERC-20 (e.g., 1% fee) and mint balance to `user`.
2. `user` approves `IntentGatewayV2` (Tron variant) for `inputAmount = 1000e18` and calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. Inside `placeOrder`, `commitment` and `reducedInputs[0].amount` are computed from `1000e18` (minus protocol fee, if any) before any transfer occurs.
4. `safeTransferFrom(user, address(this), 1000e18)` executes; due to the 1% fee, the gateway's actual token balance only increases by `990e18`.
5. `_orders[commitment][FOT] += reducedInputs[0].amount` credits (up to) `1000e18` (or the fee-reduced version of `1000e18`) to escrow, even though only `990e18` tokens are physically held.
6. When this order (or another order sharing the same token pool) is later filled/redeemed for the recorded escrow amount, the payout can fail due to insufficient balance, or can succeed by consuming tokens that were escrowed for a different order — demonstrating the insolvency in the shared `_orders` ledger.

The equivalent scenario is already validated as fixed-behavior via foundry tests on the main (non-Tron) contract, confirming the vulnerability’s mechanics: [6](#0-5)

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }

            session: address(0),
