### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` domain that identifies which tenant the webhook belongs to is read from an HTTP header that is **not included** in the signed content, so a party who legitimately receives one validly-signed webhook (for their own store) can replay it with an arbitrary `shop` header and have it accepted as originating from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is populated straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` performs exactly one authentication check — that HMAC — and then immediately forwards the untrusted `request.shop` value straight to the application-level handler: [4](#0-3) 

The identity-binding equality that should hold is:
`shop authenticated by the HMAC-covered bytes == shop delivered to the handler as the tenant identifier (request.shop / WebhookMetadata#shop)`

Because `api_secret_key` is a single shared secret for the whole app (not per-shop), and the `shop` header is outside the signed content, this equality is never enforced. Any body+HMAC pair that is valid for shop A remains valid for a request claiming to be shop B — the signature says nothing about which shop the payload belongs to.

### Impact Explanation
An attacker who installs the app on their own (unprivileged) shop receives genuine, correctly-HMAC-signed webhooks for that shop. By replaying the same body/HMAC pair against the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain, the attacker gets the gem to hand the host application a `WebhookMetadata` object that is falsely attributed to the victim tenant, while HMAC validation still succeeds. Any host application logic that trusts `WebhookMetadata#shop` to select which merchant's data/session to act on (a very common and gem-endorsed pattern, since `Registry.process` is the primary API for consuming webhooks) can be tricked into applying attacker-supplied webhook data to another merchant's account/session — i.e., cross-tenant data injection/corruption. This satisfies the Critical "cross-tenant access" impact category, since it is achieved purely by request manipulation, with no access token, `api_secret_key`, or privileged account for the *victim* required — only a self-service install of the app for the attacker's own shop.

### Likelihood Explanation
High. Getting a self-serve app install (and thus a stream of legitimately-signed webhooks for a shop the attacker controls) requires no special privilege — any merchant can install a public/development app. Capturing the raw body and HMAC header of one's own webhook and replaying it with a modified `shop` header is trivial and requires no cryptographic material beyond what the attacker is entitled to see for their own store.

### Recommendation
Bind the `shop` identity into the authenticated material before trusting it:
- Include the shop domain (and ideally webhook id / topic) in the string that is HMAC-verified, or
- After computing/validating the HMAC, cross-check `request.shop` against a shop that the host app expects to receive this particular payload for (e.g., verify it against a shop registered/known to the app, rather than passing it through unchecked in `WebhookMetadata`), and
- Document clearly (and possibly enforce in `Registry.process`) that consumers must not treat `WebhookMetadata#shop` as authenticated by itself.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook event, capturing the raw body `B` and the `x-shopify-hmac-sha256: H` header Shopify sent (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker POSTs `B` to the app's webhook endpoint again, keeping `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body without complaint (`lib/shopify_api/webhooks/request.rb:45-63`).
4. `Utils::HmacValidator.validate` succeeds because it only ever hashed `B` (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload actually originated from the attacker's own shop.
