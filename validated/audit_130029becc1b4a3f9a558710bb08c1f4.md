Audit Report

## Title
Unauthenticated request-ID collision allows any authorized client to block another user's workflow trigger execution - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

## Summary
The `httpTriggerHandler` keys its shared, in-memory `callbacks` map exclusively by the client-supplied JSON-RPC `id` field, with no binding to the requesting workflow ID or authorized key. Because `setupCallback` rejects any request whose `id` already exists in the map — regardless of which workflow or caller created that entry — any client authorized to trigger at least one workflow can pick an `id` colliding with another (unrelated) in-flight request and cause that other request to fail with `jsonrpc.ErrConflict`.

## Finding Description
`validateRequestID` only checks that `req.ID` is non-empty and does not contain `/`; it performs no uniqueness or ownership scoping: [1](#0-0) 

`setupCallback` is invoked after `authorizeRequest` (which validates the caller's signature against the *specific* `workflowID` in their own request) and `checkRateLimit`, but the uniqueness check itself is not scoped to `workflowID` or the caller's authorized key — it is a flat, global lookup: [2](#0-1) 

The `callbacks` map itself is declared as a single global `map[string]savedCallback` shared across every workflow and every user served by the gateway process: [3](#0-2) 

This is confirmed behaviorally by the existing unit test, which shows that submitting a second (different) request with the same `id` fails with `jsonrpc.ErrConflict` even though `HandleUserTriggerRequest`'s own authorization step (`authorizeRequest`) is scoped per-workflow: [4](#0-3) 

The broken assumption is that a client-chosen `id` is treated as a globally unique key sufficient to gate resource creation, when in fact nothing ties it to the requester's identity, workflow, or authorized key. Existing checks (`validateRequestID`, `authorizeRequest`, `checkRateLimit`) validate format, per-workflow signature authorization, and per-workflow/org rate limits respectively, but none of them scope or namespace the map key by caller/workflow, so they do not prevent this cross-caller collision.

## Impact Explanation
An attacker who is authorized to trigger any workflow (their own, or one they have legitimate access to) can cause a targeted victim's `workflows.execute` trigger request — for a completely different, unrelated workflow — to be rejected with `jsonrpc.ErrConflict` if the victim happens to use the same `id` value. This is a denial-of-service against a specific triggering attempt of another user's workflow, which maps to disruption of legitimate workflow execution triggering via the gateway (an in-scope impact class: unauthorized denial of a legitimate job-run trigger due to a cross-user resource-key collision).

## Likelihood Explanation
Exploitability requires only ordinary, minimally-privileged access: the attacker must be authorized to trigger some workflow (the same bar any legitimate integration meets), and must be able to predict or brute-force the exact `id` string the victim will use for a concurrent request. Random/UUID-based request IDs make blind collision unlikely, but many real integrations use predictable, sequential, or business-derived identifiers (e.g., idempotency keys, order numbers) as their JSON-RPC `id`, which significantly raises practical likelihood in such deployments. The underlying design flaw — a shared, unscoped uniqueness map — is deterministic and trivially reproducible whenever an `id` collision occurs, as shown by the existing test.

## Recommendation
Scope the in-flight request uniqueness check to the authenticated caller/workflow context rather than the raw `id` alone — e.g., key the `callbacks` map (or perform the "already in use" check) using a composite key such as `workflowID + separator + requestID`, mirroring the pattern already used in `core/capabilities/vault/vaulttypes/types.go` (`owner + vaulttypes.RequestIDSeparator + requestID`). This ensures request-ID collisions across different workflows/callers cannot produce cross-user conflicts, while still allowing per-workflow enforcement of ID uniqueness/idempotency if desired.

## Proof of Concept
1. Attacker (authorized to trigger `workflowA`) sends a `workflows.execute` JSON-RPC request with `id = "X"` to the gateway's HTTP trigger endpoint. `setupCallback` inserts `h.callbacks["X"] = ...`.
2. Victim (authorized to trigger unrelated `workflowB`) sends a legitimate `workflows.execute` request with `id = "X"`.
3. `setupCallback` finds `h.callbacks["X"]` already present (from step 1, an entirely different workflow/caller) and rejects the victim's request via `jsonrpc.ErrConflict`.
4. This exact behavior is demonstrated by the existing test `TestHttpTriggerHandler_HandleUserTriggerRequest/duplicate_request_ID` in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go` (lines 320-358); extending that test to use two different `workflowID`s / authorized keys with the same `id` would directly confirm the cross-workflow collision.

```go
func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}
```

```go
func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
```
