### Title
Permanent Loss of Bridged Funds via Zero-Timeout POST Requests Combined with Immutable/Unretryable `CallDispatcher` Calldata - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol, evm/src/utils/CallDispatcher.sol)

### Summary
`HyperFungibleToken.send()` / `WrappedHyperFungibleToken.send()` allow a user to attach optional `data` (an ABI-encoded `Call[]`) that is forwarded to `ICallDispatcher.dispatch()` on `onAccept()` at the destination. If this calldata is malformed, targets a non-contract, or otherwise always reverts, `onAccept` reverts in its entirety (including the token mint/unlock), exactly mirroring the "incorrect data parameter" bug class from the Scroll report. The only recovery path in the protocol is a POST-request timeout, which mints/unlocks the tokens back to the sender via `onPostRequestTimeout`. However, `DispatchPost.timeout`/`SendParams.timeout` accepts `0`, which is explicitly documented and coded (`Message.timeout()` in `sdk/packages/core/contracts/libraries/Message.sol:185-191`, and `EvmHost.dispatch` at `evm/src/core/EvmHost.sol:935`) to mean "never times out." A user (or a griefer who convinces a user, e.g. via a malicious frontend/dApp) who dispatches a transfer with `timeout = 0` and unexecutable calldata permanently burns/locks their tokens on the source chain with **no possible refund**, since redelivery cannot alter the fixed request body and the timeout path — the only refund mechanism the protocol implements — is unreachable.

### Finding Description
The relevant delivery path is:
1. `HyperFungibleToken.send()` burns the caller's tokens and dispatches a `PostRequest` with `body` containing `Message{from, to, amount, data}` (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:271-282` calling into `EvmHost.dispatch`).
2. On delivery, `EvmHost.dispatchIncoming` (`evm/src/core/EvmHost.sol:794-818`) low-level calls `IApp.onAccept`. On `onAccept`:
```solidity
function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
    ...
    _mint(beneficiary, message.amount);
    if (message.data.length > 0) {
        ICallDispatcher(_dispatcher).dispatch(message.data);
    }
    ...
}
``` [1](#0-0) 
3. `CallDispatcher.dispatch` reverts the whole call if any target has no code or any sub-call fails:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    if (size == 0) revert NotContract(to);
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [2](#0-1) 
4. When `onAccept` reverts, `EvmHost.dispatchIncoming` swallows the failure, deletes the receipt, and returns without reverting the batch — this makes the message "retryable" but the request body (and thus its calldata) is immutable, so redelivery will fail identically forever, exactly as described in the Scroll report ("the message field cannot be changed for a replay"). [3](#0-2) 

The protocol's documented mitigation for this exact scenario is the timeout/refund flow: "If any call in the array reverts, the entire `onAccept` handler reverts... The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain." [4](#0-3) 

But the timeout itself is user-controlled and can be set to zero, which is explicitly treated as "no timeout — messages will never expire":
```solidity
function timeout(PostRequest memory req) internal pure returns (uint64) {
    if (req.timeoutTimestamp == 0) {
        return type(uint64).max;
    } else {
        return req.timeoutTimestamp;
    }
}
``` [5](#0-4) 
and
```solidity
uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
``` [6](#0-5) 

The same "zero timeout = never expires" convention is stated for the Substrate dispatcher as well. [7](#0-6) 

Because the timeout path (`onPostRequestTimeout`, which is the *only* refund mechanism — see `sdk/packages/core/contracts/apps/HyperFungibleToken.sol:321-326`) is the sole way to recover funds when destination execution permanently fails, setting `timeout = 0` combined with calldata that always reverts on the destination (bad `Call.to` with no code, bad ABI-encoding, dependent-on-state calldata like a DEX swap with slippage bounds that can never be met, or a `to` address that is deliberately a self-destructed/non-existent contract) creates a state where tokens are burned/locked on the source chain permanently, with no code path to ever recover them. This is functionally identical to the Scroll `_executeMessage`/EOA-or-malformed-`_message`-data root cause: an irrecoverable cross-chain send whose only remedy (timeout-triggered refund) never fires.

### Impact Explanation
This is a **High** severity permanent freezing-of-funds bug. Any amount of bridged value (native ETH via WETH-mode `WrappedHyperFungibleToken`, or ERC20/HFT-minted tokens) sent with attached calldata and `timeout = 0` can become permanently unrecoverable if the calldata execution fails deterministically. This can happen accidentally (a frontend bug, a stale swap quote that always reverts due to slippage, an off-by-one in ABI encoding) or be induced by a malicious dApp/integrator that convinces users to sign transactions with `timeout=0` and broken calldata, effectively rug-pulling bridged assets with no recourse. Given `HyperFungibleToken`/`WrappedHyperFungibleToken` are documented, reusable SDK-level building blocks intended for third-party integrations, this defect is inherited by every app built on them unless the integrator independently enforces a sane non-zero timeout — which the base contracts do not enforce.

### Likelihood Explanation
Likelihood is Medium-to-High: `timeout` is a caller-supplied field with no minimum/maximum validation in `send()`, and `0` is a natural default a developer might pick to mean "just deliver it" without realizing it disables the entire refund safety net. Calldata targeting DeFi composability (swaps, deposits) is explicitly a supported/advertised feature ("Calldata Execution" docs), and those calls are exactly the kind prone to always-revert conditions (stale quotes, price movement, wrong `to` after a redeploy, chain-specific router address mistakes). No malicious relayer or admin action is required — it can be triggered by a single ordinary user transaction.

### Recommendation
- Enforce a sane minimum non-zero timeout (or disallow `timeout == 0`) whenever `data.length > 0` is supplied in `SendParams`, since zero-timeout removes the only refund mechanism for calldata-execution failures.
- Alternatively/additionally, decouple the mint/unlock from calldata execution: mint/unlock unconditionally first (in a way that cannot be rolled back by a later external call failure), and execute attached calldata in a separately-reverting inner call/try-catch so a broken `Call[]` cannot also revert away the underlying transfer.
- Emit a prominent warning/require in `send()` when `timeout == 0 && data.length > 0`, and consider capping the maximum permitted `timeout` for calldata-carrying transfers to bound the exposure window even when non-zero.

### Proof of Concept
1. User calls `HyperFungibleToken.send()` with `SendParams{ dest: chainB, to: recipientHFT, amount: X, timeout: 0, relayerFee: r, data: abi.encode([Call{to: badTarget, value: 0, data: garbage}]) }`. Tokens are burned on chain A (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:271-282`).
2. A relayer delivers the request on chain B via `EvmHost.dispatchIncoming` → `HyperFungibleToken.onAccept` (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:292-313`).
3. `ICallDispatcher(_dispatcher).dispatch(message.data)` reverts because `badTarget` has no code (`evm/src/utils/CallDispatcher.sol:55-56`, `NotContract`), causing the whole `onAccept` call to revert, including the `_mint` — no tokens are ever minted on chain B.
4. `EvmHost.dispatchIncoming` catches the failed low-level call, deletes the request receipt, and returns without reverting (`evm/src/core/EvmHost.sol:809-816`) — the message is nominally "retryable" but the calldata inside the (immutable) request body is still `garbage`/`badTarget`, so every future redelivery attempt fails identically.
5. Because `timeoutTimestamp` was computed as `0` (never expires) at dispatch time (`evm/src/core/EvmHost.sol:935`, `Message.timeout()` treats it as `type(uint64).max`), no `PostRequestTimeoutMessage` can ever be proven for this request, so `onPostRequestTimeout`'s refund mint (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:321-326`) can never be invoked.
6. Result: the burned tokens from step 1 are permanently unrecoverable on chain A, and no tokens ever exist on chain B — a total, permanent loss of the bridged amount `X`.

        PostRequest calldata request = incoming.request;

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
```

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
