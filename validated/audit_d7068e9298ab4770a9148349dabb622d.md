### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` bind the HMAC signature only to the raw webhook body, never to the `shopify-shop-domain` (or `x-shopify-shop-domain`) header. `ShopifyAPI::Webhooks::Registry.process` validates only that signature and then trusts `request.shop`, sourced purely from that header, to build the `WebhookMetadata` passed to the app's handler as the tenant identity.

### Finding Description
The identity binding that should hold is: `hmac_signature == HMAC(secret, raw_body + shop)`, i.e., the shop attributed to a webhook event must be cryptographically tied to the payload. Instead, the gem computes:
- `to_signable_string` → `@raw_body` only [1](#0-0) 
- `hmac` → decoded from the `hmac-sha256` header [4](#0-3) 
- `shop` → read verbatim from the `shop-domain` header, with zero cryptographic linkage to the body or the HMAC [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes HMAC over `to_signable_string` (the body) and compares it to the header-provided HMAC [5](#0-4) . Because the shop header is excluded from the signed content, any `(raw_body, hmac)` pair that is valid for one shop remains valid — HMAC-wise — no matter what value is placed in the `shop-domain` header. `Registry.process` then forwards this unauthenticated `shop` field directly into the handler's `WebhookMetadata` as the trusted tenant identifier [3](#0-2) , and the docs explicitly instruct host apps to key persistence/business logic off `data.shop` [6](#0-5) .

An attacker who is a legitimate merchant on their own store (a normal unprivileged internet user, no special credentials needed) can install the app and receive a genuine, validly-signed webhook for their own shop. The `(raw_body, hmac-sha256)` pair captured from that real Shopify delivery remains valid for *any* `shop-domain` value, since that header is never part of the signed content. The attacker can then replay that exact body+HMAC to the app's public webhook endpoint while substituting a victim shop's domain in the header. `HmacValidator.validate` still passes (it never inspects the header), and `Registry.process` calls the handler with `WebhookMetadata#shop` equal to the victim's domain, `WebhookMetadata#body` equal to attacker-controlled content signed under the attacker's own installation.

### Impact Explanation
This breaks the cross-tenant boundary the HMAC is supposed to enforce: an attacker can make the host application believe attacker-chosen webhook data (attacker's real body, valid signature) originated from an arbitrary victim shop. Depending on how the host app uses `data.shop`, this enables cross-tenant data corruption/injection — e.g., forging `app/uninstalled` to trigger deletion of a victim's stored session/access token, or forging `shop/redact`/`customers/data_request` compliance events attributed to a victim shop, or injecting fabricated order/product data keyed to the victim's tenant record. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any unprivileged attacker who can install the target app on any shop (including a free/dev store they control) — a normal, unprivileged path. No access token, `client_secret`, or the app's credentials are required; only capturing one legitimately-delivered webhook (raw body + its `hmac-sha256` header) from their own store and replaying it against the same public webhook endpoint with a different `shop-domain` header.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values into the signed content that is verified, or otherwise cross-check that the shop asserted in the header corresponds to a shop that is actually expected to receive that specific webhook subscription/topic (e.g., validate against the shop's known active session/subscription registration) before trusting `request.shop`. At minimum, document prominently that `WebhookMetadata#shop` is not covered by HMAC verification and must not be trusted as an authenticated tenant identifier without additional binding.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a genuine webhook to the app's endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>`, and some raw JSON body.
3. Attacker captures the exact raw body and `hmac-sha256` header value (e.g., via a debugging proxy they control since it's their own traffic).
4. Attacker sends a new HTTP request directly to the app's public webhook endpoint with the identical raw body and `hmac-sha256` header, but replaces `shopify-shop-domain` with `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)` — this still matches, since body and HMAC are unchanged.
6. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and the attacker-controlled body, even though this data never actually originated from Shopify for that shop.
