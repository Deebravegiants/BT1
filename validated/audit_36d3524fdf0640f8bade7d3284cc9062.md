### Title
Webhook shop-identity spoofing via header fields excluded from HMAC coverage - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the **raw body**, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP **headers** — none of which are covered by that HMAC — when building `WebhookMetadata` passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` verifies this HMAC and, once it passes, immediately forwards `request.shop` (parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` header) to the handler as the shop identity for the event, with no cross-check against the body contents or against a known/installed shop list: [2](#0-1) 

The `shop` accessor is defined purely as a header read: [3](#0-2) 

Because Shopify's HMAC-SHA256 signature (computed with the app's `api_secret_key`) covers **only the JSON body**, the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are unauthenticated. This breaks the identity binding `authenticated_shop == shop_used_for_downstream_processing`: an attacker who can obtain one validly-signed webhook delivery for a shop they control (e.g. by installing the app on their own store and triggering a webhook whose body they can influence, such as `products/update`) can replay that exact signed body to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Registry.process` will pass HMAC validation (since only the body is checked) and will call the handler with `shop: <attacker-chosen victim domain>`, spoofing the tenant identity for that event.

The documentation for `Process a Webhook` and `Create a Webhook Handler` instructs app developers to build the `Request` directly from `request.raw_post` / `request.headers.to_h` and to trust `data.shop` from the resulting `WebhookMetadata` without any indication that `shop` is unauthenticated header data: [4](#0-3) [5](#0-4) 

### Impact Explanation
This enables cross-tenant confusion: a merchant/attacker who can install the app on their own shop and produce arbitrarily-signed webhook bodies (their own shop's genuine webhook traffic) can relabel those events as belonging to a different, victim shop by forging only the header. Depending on how the host app keys its per-shop side effects off `data.shop` (job enqueuing, cache/database writes, triggering shop-scoped business logic), this can result in cross-tenant data corruption or unauthorized actions attributed to another merchant — matching the "Critical: cross-tenant access" impact category, since the gem itself provides no way for the host app to distinguish an authenticated shop from a spoofed one within its own API surface.

### Likelihood Explanation
Likelihood is moderate-to-high for any developer following the gem's documented usage exactly as shown (`Registry.process` + `WebhookHandler#handle`), since the gem's own public API returns an unauthenticated `shop` value labeled and documented as trustworthy ("The shop domain of the webhook"), with no caveat that only the body is HMAC-protected. No access token, `api_secret_key`, or other privileged credential is required by the attacker — they only need the ability to trigger a legitimately-signed webhook for a shop under their control and to replay the raw body with modified headers to the app's public webhook endpoint.

### Recommendation
Include the header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string in `ShopifyAPI::Webhooks::Request#to_signable_string`, or otherwise cryptographically bind them to the body before they are exposed as trusted attributes on `WebhookMetadata`. At minimum, document clearly that `shop`, `topic`, and other header-sourced fields on `WebhookMetadata` are not covered by the HMAC and must be independently validated by the host application against its own list of installed/authenticated shops before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers a webhook (e.g. `products/update`).
2. Attacker triggers the webhook, capturing the legitimately Shopify-signed request: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally spoofs `topic`/`webhook-id`).
4. `Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC over `B` only, matches `H`, and passes.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: <parsed B>, ...)` and invokes the app's handler, which now believes this event originates from `victim.myshopify.com`, even though `B` was never generated by or for that shop. [2](#0-1) [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
