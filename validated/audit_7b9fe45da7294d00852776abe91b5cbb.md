### Title
Double-counted `balanceDif` via an aliased-balance token lets `Hinkal.transact` mint two onchain UTXOs backed by a single real deposit - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` validates each token leg independently by iterating `circomData.erc20TokenAddresses` and comparing a per-index `balanceOf` snapshot delta against `amountChanges[i] + utxoAmount[i]`. Nothing in `dimensionsCheck`, `checkOnchainCreation`, or the balance loop enforces that the addresses in `erc20TokenAddresses` are distinct underlying balances. If the attacker deploys a token whose `balanceOf` is reachable from two different addresses that both reflect one shared storage slot, both index entries observe the *same* balance movement, letting the attacker satisfy the equality twice from a single real transfer.

### Finding Description
The invariant that should hold is: **real tokens received by the vault == sum of `amountChanges` credited off-chain + sum of on-chain UTXO amounts minted**, evaluated globally across the whole call. Instead, `Hinkal.transact` enforces this per-index: [1](#0-0) [2](#0-1) 

`oldBalances`/`newBalances` are computed via `getBalancesForArray(circomData.erc20TokenAddresses)`, which calls `balanceOf`/ETH balance once per array entry, keyed by the address the attacker supplied at that index — not by the token's real economic identity. `dimensionsCheck` in `HinkalHelper.sol` only checks array *lengths* against `dimensions.tokenNumber`; it never checks that `erc20TokenAddresses` entries are unique or that they resolve to distinct storage: [3](#0-2) 

`checkOnchainCreation` only forces `amountChanges[i] == 0` and zero nullifiers when `onChainCreation[i]` is true — it does nothing to prevent the same physical balance from being claimed under two different addresses: [4](#0-3) 

**Attack construction**: the attacker deploys a token pair `tokenA`/`tokenB` (two distinct contract addresses) that both proxy to one shared balance ledger (e.g., a delegatecall-based facade where both addresses' `balanceOf(Hinkal)` reads the same storage slot, and only one of them is used to perform the real `transferFrom`). They call `Hinkal.transact` with `erc20TokenAddresses = [tokenA, tokenB]`, deposit real value `X` once via the `tokenA` leg (`amountChanges[0] = X`, `onChainCreation[0] = false`), and additionally request `onChainCreation[1] = true` with an on-chain UTXO of amount `X` tagged to `erc20Address = tokenB`, `amountChanges[1] = 0` (required by `checkOnchainCreation`).

Because `tokenA` and `tokenB` alias the same balance, the single real deposit of `X` moves the shared underlying balance once, so:
- Index 0 (`tokenA`): `balanceDif = X`, check requires `X == amountChanges[0] (X) + utxoAmount(tokenA leg, 0)` → holds.
- Index 1 (`tokenB`): `newBalances[1] - oldBalances[1]` is again `X` (same shared storage, read through the `tokenB` facade), check requires `X == 0 + utxoAmount(tokenB leg, X)` → also holds.

The loop at lines 117-132 sums `utxoSet[j].amount` matched by `erc20Address` per index, so the `tokenB`-tagged UTXO of amount `X` is credited and inserted as a valid on-chain commitment, in addition to the already-credited `amountChanges[0] = X`. Net result: the vault received `X` in real tokens but minted `2X` of redeemable shielded value (`amountChanges[0] + onchain UTXO for tokenB`), because the same physical balance movement was independently "spent" twice by the per-index check. The proof/circuit constrains `inTotal + amountChanges === outTotal` per the circuit's own bookkeeping of `amountChanges`/UTXOs, but it has no visibility into real on-chain token balances — that check exists solely in Solidity's per-index balance loop, which is exactly what this aliasing defeats.

### Impact Explanation
The attacker mints shielded/on-chain UTXO value with no backing, directly reducing vault solvency by the unbacked delta (`X` per exploit iteration, scalable by repeating with larger `X` or additional aliased legs in the same call). This matches the Critical category: "minting shielded value without backing (protocol insolvency)." The attack is repeatable indefinitely as long as the attacker can call `transact` with a freshly crafted proof matching the fabricated `amountChanges`/`onChainCreation`/UTXO layout, and does not require any privileged role — only the ability to deploy an arbitrary token contract and generate their own valid proof for their own UTXO outputs.

### Likelihood Explanation
Feasibility hinges entirely on the attacker being able to make `balanceOf` return an identical, correlated value for two distinct addresses supplied in `erc20TokenAddresses`. This requires a custom token contract (not a standard, audited ERC20) since the attack model explicitly allows "attacker deploys a token." No admin/relay privilege is needed; the attacker only needs to control `erc20TokenAddresses`, `amountChanges`, `onChainCreation`, and craft a matching valid proof (which they can do for their own outputs since the circuit only enforces internal amount-change bookkeeping, not real balances). Cost is limited to gas plus deploying the aliasing token contract.

### Recommendation
Enforce token-identity integrity independent of attacker-supplied addresses:
- Require `erc20TokenAddresses` entries to be unique within a single `transact` call (reject duplicates and, ideally, disallow multiple entries whose `balanceOf` deltas cannot be independently attributed).
- Alternatively/additionally, compute a single global balance-conservation check across the whole array (sum of all `balanceDif` == sum of all credited `amountChanges` + `utxoAmount`, not per-index), so aliasing one balance across two indices cannot double-count a single deposit.
- Consider maintaining a per-token allowlist/registry rather than trusting arbitrary attacker-supplied token addresses for balance snapshotting.

### Proof of Concept
Foundry test outline:
1. Deploy `AliasedToken` — two thin proxy contracts `tokenA`, `tokenB` that both `delegatecall` into one shared implementation/storage so `balanceOf(any)` is identical from both addresses, but only `tokenA.transferFrom` is exercised by the attacker's deposit.
2. Fund attacker with `X` real `AliasedToken` balance and approve Hinkal.
3. Build `CircomData` with `erc20TokenAddresses = [tokenA, tokenB]`, `amountChanges = [X, 0]`, `onChainCreation = [false, true]`, one on-chain UTXO tagged `erc20Address = tokenB, amount = X`, and a locally generated valid proof for these signals (internal-transaction path, `externalActionData.externalActionId == 0`, `externalAddress == attacker`).
4. Call `Hinkal.transact(...)`.
5. Assert: (a) both per-index `require` statements at lines 111-114 and 137-146 pass; (b) actual vault token balance increase == `X`; (c) sum of newly inserted on-chain UTXO amounts + `amountChanges[0]` credited == `2X`. The mismatch `2X != X` demonstrates unbacked minting.
