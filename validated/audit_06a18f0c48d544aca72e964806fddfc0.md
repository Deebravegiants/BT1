### Title
Webhook `shop` (and `topic`) fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, but the `shop` (tenant identifier) and `topic` fields used downstream are taken directly from unauthenticated HTTP headers. This breaks the identity binding: `hmac-verified bytes == raw_body` while `shop used by handler == header-derived, unverified value`. An attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the app's secret (e.g., a webhook legitimately delivered to their own store) can replay that body/hmac while forging the `x-shopify-shop-domain` header to impersonate a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers without any cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` and `request.topic` to dispatch the payload to the app's handler as the tenant identity: [3](#0-2) 

Because `HmacValidator.validate` (via `to_signable_string`) checks only the raw body bytes, the `shop-domain` header can be swapped to any value after the HMAC was computed by Shopify for a *different* legitimate delivery, and the signature still validates: [4](#0-3) 

This is the same class of bug as the LOGLAB-19 report: a value acted upon (`isExecuted`/here, tenant `shop`) is derived from state that is not bound to the check that is supposed to guarantee its integrity (`utilizedAssets()`/here, the HMAC signature). The equality the gem should — but does not — enforce is:

`shop-domain header used by handler == shop bound inside the HMAC-signed payload`

Before the attack: victim's app only ever processes webhooks whose `shop-domain` header matches the shop that Shopify actually signed the request for. After the attack: an attacker replays a body+HMAC pair they legitimately received for their own shop, but with the `x-shopify-shop-domain` header rewritten to the victim's shop domain; `Registry.process` accepts it as valid and hands `WebhookMetadata` with the victim's shop to the host app's handler.

### Impact Explanation
This allows an unprivileged user who has installed the app on their own store (or who can otherwise obtain one legitimately signed webhook body/HMAC pair) to make the vulnerable app process attacker-controlled webhook data under a victim shop's identity. Since most `shopify_app`/host-app implementations key session lookup, data storage, and business logic off `WebhookMetadata#shop`, this enables cross-tenant data corruption/injection — writing or triggering actions attributed to a shop the attacker does not own. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-High. The gem is the public app-store SDK; nothing in the gem prevents replay across tenants because `topic`/`shop` are excluded from the signed payload. Any user who can install the target app on a shop they control (a normal, unprivileged action for public Shopify apps) can capture one legitimately signed webhook and immediately reuse it against any other installation of the app, only needing to alter the `x-shopify-shop-domain` header — no access token, `client_secret`, or privileged access is required.

### Recommendation
Bind the tenant identity into the value that is actually HMAC-verified. Either:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` so the header values are cryptographically covered by the same HMAC as the body, or
- Require host applications to independently confirm that `request.shop` corresponds to a shop with an active, known session/installation for this app before dispatching to the handler, and document this requirement explicitly in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a real webhook (e.g. `orders/create`) and captures the raw POST body plus the `x-shopify-hmac-sha256` header — this HMAC is valid because `HmacValidator` only signs `raw_body`: [5](#0-4) 
3. Attacker resends the same body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker's data, ...)`, causing the host app to process attacker-controlled data as if it originated from the victim's store.
