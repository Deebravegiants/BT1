Audit Report

## Title
Sensitive debug/profiling endpoints (`/v2/debug/pprof/*`, `/debug/vars`) lack role-based access control, allowing any authenticated low-privilege user to access them - (File: core/web/router.go)

## Summary
`debugRoutes` (mounts `/debug/vars`) and `metricRoutes` (mounts the full `net/http/pprof` handler set at `/v2/debug/pprof/*`) are wired behind only generic `auth.Authenticate` middleware, with no `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper, unlike every other sensitive route registered in the same file. This lets any authenticated user, including the lowest-privilege `view` role, pull goroutine stack dumps, heap profiles, CPU profiles, and `cmdline`/`expvar` runtime data from the running node.

## Finding Description
`debugRoutes` groups `/debug` under `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` only, then exposes `GET /vars` (`expvar.Handler()`) with no role gate: [1](#0-0) 

`metricRoutes` registers the entire stdlib `net/http/pprof` handler set (`/`, `/cmdline`, `/profile`, `/symbol`, `/trace`, `/allocs`, `/block`, `/goroutine`, `/heap`, `/mutex`, `/threadcreate`) with no per-route auth/role wrapper at all — the routes rely entirely on whatever middleware is applied to the group passed in: [2](#0-1) 

It is called as `metricRoutes(authv2)`, and `authv2` is defined only with the generic `Authenticate` middleware (token or session), with no role requirement: [3](#0-2) [4](#0-3) 

By contrast, every other sensitive/admin-adjacent route registered on the same `authv2` group in the same file is explicitly wrapped in a role-check middleware, e.g. `auth.RequiresAdminRole` for `/users`, `/log` PATCH, and `auth.RequiresEditRole` for `/vault/dkg_results/*`, `/pipeline/job_spec_errors/:ID`, `/nodes/evm/forwarders/*`: [5](#0-4) [6](#0-5) [7](#0-6) 

The role-check helpers `RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` exist and are the standard mechanism used throughout the router, confirming they were simply omitted for the debug/pprof group and this isn't an intentional design choice reflected elsewhere in the codebase.

The project's own RBAC regression suite, `routesRolesMap` in `core/web/auth/auth_test.go`, enumerates the minimum role required per route across the entire router but contains no entries for `/v2/debug/pprof/*` or `/debug/vars`, meaning there is no automated test coverage that would catch this gap or confirm intended behavior.

## Impact Explanation
Any authenticated node UI/API user — regardless of role, including a `view`-only account meant to have strictly read-only, non-privileged access — can pull full goroutine stack dumps (`/goroutine?debug=2`), heap profiles, CPU profiles (`/profile`), and process `cmdline`/`expvar` runtime data from the running Chainlink node. This is a genuine horizontal/vertical privilege-boundary violation (CWE-732-class), since the codebase's established security model explicitly reserves this class of operational/debugging capability for `edit`/`run`/`admin` roles on every comparable sensitive route, but omits that check here. The data exposed (stack traces, heap contents, potential in-flight request/internal state data) is materially more sensitive than the "non-confidential information disclosure" the program's SECURITY.md excludes (e.g., IPs, server names, generic stack traces), and represents a role-bypass class of finding, which is listed as an in-scope impact category.

## Likelihood Explanation
High for any account holding a valid `view`-role credential (the lowest tier Chainlink explicitly supports) — no exploit beyond a normal authenticated GET request is required, and the endpoints are unmodified, well-known stdlib pprof/expvar paths.

## Recommendation
Wrap the debug/pprof route groups (and `/debug/vars`) in `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`), matching the pattern already used for every other sensitive route in `core/web/router.go`, and add corresponding entries to `routesRolesMap` in `core/web/auth/auth_test.go` so RBAC regression tests cover these routes going forward.

## Proof of Concept
1. Obtain/create a Chainlink API user with `view` role (lowest privilege).
2. Authenticate as that `view` user via session cookie or API token against `/v2` (uses `auth.Authenticate` only, per `authv2` definition).
3. Issue `GET /v2/debug/pprof/goroutine?debug=2` or `GET /debug/vars`.
4. Observe HTTP 200 with full goroutine dump / runtime expvar data returned, confirmed by the route wiring shown above, which applies only `auth.Authenticate` and never any `Requires*Role` gate — unlike sibling routes (`/users`, `/vault/*`, `/nodes/evm/forwarders/*`) in the same file.
