Audit Report

## Title
User Enumeration via Distinct Login Error Messages in Session Creation - (File: core/sessions/localauth/orm.go)

## Summary
The unauthenticated `/sessions` login endpoint returns raw, distinct error strings ("Invalid email" vs "Invalid password") from `SessionsController.Create`, which are forwarded verbatim to the HTTP client through `jsonAPIError`. This lets an unauthenticated attacker distinguish between non-existent accounts and existing accounts with wrong passwords, enabling enumeration of valid Chainlink node user emails.

## Finding Description
`SessionsController.Create` accepts an unauthenticated JSON login request and calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`, forwarding any resulting error directly to the client via `jsonAPIError(c, http.StatusUnauthorized, err)`. [1](#0-0) 

`jsonAPIError` serializes `err.Error()` into the JSON response body when the error is not already a `*models.JSONAPIErrors`. [2](#0-1) 

In `orm.CreateSession`, the flow is: `FindUser` looks up the account by lowercased email via `SELECT * FROM users WHERE lower(email) = lower($1)`. If no row is found, `sqlx`'s `GetContext` returns `sql.ErrNoRows`, which propagates back up through `CreateSession` (`return "", err`) and ultimately to `jsonAPIError` as the raw driver/sqlx error string (e.g., "sql: no rows in result set"), not the literal string "Invalid email" claimed in the report. The `"Invalid email"` error path via `constantTimeEmailCompare` is only reachable once a `user` row has already been successfully found by `FindUser` — it exists to defend against timing side-channels comparing the found user's email against the requested email (case normalization edge case), not as the "no such user" branch. [3](#0-2) [4](#0-3) 

However, even with this correction, the underlying claim still holds: the response body for a non-existent email (`sql: no rows in result set` propagated as `err.Error()`) is textually distinct from the response body for an existing email with the wrong password (`"Invalid password"`). Both are returned unauthenticated, both reach the client via the same `jsonAPIError` code path with `http.StatusUnauthorized` in each case, and no normalization occurs anywhere in `SessionsController.Create` or `jsonAPIError` before the error reaches the response body. This is a genuine, reachable information-disclosure primitive that lets an unauthenticated client determine whether a given email is a registered account by diffing the two distinguishable error responses in each of the local, LDAP (`core/sessions/ldapauth/ldap.go`), and OIDC (`core/sessions/oidcauth/oidc.go`) local-fallback authenticators.

## Impact Explanation
This is a low-severity information disclosure (user enumeration), consistent with CWE-203/CWE-204 class issues. It does not grant authentication bypass, credential theft, fund movement, or any privileged action by itself — it only aids reconnaissance for a subsequent credential-stuffing or phishing attack against a known set of accounts. Per the stated scope, valid impacts must map to concrete categories such as authentication/role bypass, key/secret exfiltration, unauthorized job run/fund movement, gateway impersonation, allowlist bypass, or cross-user response corruption. Pure enumeration of email existence, without a demonstrated escalation to one of these categories, does not meet that bar on its own.

## Likelihood Explanation
The `/sessions` endpoint is unauthenticated and reachable by any client with network access to the node's admin API, and the differing error text is returned deterministically on every failed attempt (bounded only by the existing rate limiter, which triggers after repeated attempts but does not prevent the first enumeration attempt). This makes the underlying behavior easily reproducible, but the practical value to an attacker is limited to reconnaissance rather than direct compromise.

## Recommendation
Normalize all failure paths in `SessionsController.Create` (or within `AuthenticationProvider().CreateSession` implementations) to return a single generic message (e.g., "invalid credentials") regardless of whether the email exists, whether the password is wrong, or whether an internal MFA/database error occurred. Keep the detailed distinction only in the audit log (`audit.AuthLoginFailedEmail` / `audit.AuthLoginFailedPassword`) via `o.auditLogger.Audit(...)`, not in the value passed to `jsonAPIError`. Apply the same fix consistently across the local, LDAP, and OIDC authenticators.

## Proof of Concept
1. `POST /sessions` with `{"email":"realuser@node.com","password":"wrongpwd"}` where `realuser@node.com` exists → response body contains `"Invalid password"` (from `core/sessions/localauth/orm.go` line 161).
2. `POST /sessions` with `{"email":"doesnotexist@node.com","password":"wrongpwd"}` → response body contains the raw `sql.ErrNoRows`-derived error string (distinct from step 1's response) propagated from `FindUser` through `CreateSession` to `jsonAPIError`.
3. Diffing these two response bodies across a candidate list of emails reveals which accounts exist on the node, without any valid credentials, before rate limiting engages (as shown in `TestSessions_RateLimited`, which only triggers after 5 consecutive failed attempts against the same email).

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```
