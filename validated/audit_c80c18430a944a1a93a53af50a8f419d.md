Audit Report

## Title
Purchase pallet `payout` transfers locked funds as fully liquid balance when `VestingSchedule::add_vesting_schedule` fails, while still marking the account `Completed` - (File: polkadot/runtime/common/src/purchase/mod.rs)

## Summary
`Pallet::payout` transfers `free_balance + locked_balance` to `who` unconditionally and then attempts to apply a vesting lock to the locked portion via `T::VestingSchedule::add_vesting_schedule`, discarding any error with `let _ = ...`. If that call fails (e.g., because `who` already has `MaxVestingSchedules` schedule slots occupied), the locked funds remain fully liquid in `who`'s account while `status.validity` is still set to `AccountValidity::Completed`, breaking the pallet's core "locked purchase amount must be vesting-locked" invariant.

## Finding Description
In `payout` [1](#0-0) , the flow is:
1. `payment_account`/`PaymentAccount` origin check.
2. A pre-check `ensure!(T::VestingSchedule::vesting_balance(&who).is_none(), Error::<T>::VestingScheduleExists)` [2](#0-1)  — this guard only checks that the account currently has zero *outstanding locked* vesting balance; it does not check how many vesting schedule slots (`MaxVestingSchedules`) are already occupied in storage. A vesting schedule that has fully unlocked (locked amount = 0) but whose entry has not yet been cleaned up (cleanup only happens on `vest`/`vest_other` or on schedule merge inside `add_vesting_schedule`) still counts toward the slot limit while `vesting_balance` returns `None`.
3. Inside `Accounts::try_mutate`, the full `total_balance` (`free_balance + locked_balance`) is transferred to `who` via `T::Currency::transfer` [3](#0-2) .
4. Only afterward, `T::VestingSchedule::add_vesting_schedule(&who, locked, locked, unlock_block)` is called and its result is discarded with `let _ = ...` [4](#0-3) .
5. Regardless of whether the lock was actually applied, `status.validity = AccountValidity::Completed` is set and `Ok(())` is returned [5](#0-4) .

The existing guard at line 313-316 is **insufficient**: it prevents the trivial case of an attacker simply pre-loading `who` with an active (still-locked) vesting schedule, since that would make `vesting_balance` return `Some(...)` and abort the whole `payout` call before any transfer occurs. However, it does not defend against an attacker filling all `MaxVestingSchedules` slots with schedules that are already fully vested (locked amount `0`) — `vesting_balance` would correctly report `None` (or zero), passing the guard, while the vesting pallet's `Vesting` storage for `who` still holds `MaxVestingSchedules` schedule entries. In that state, the subsequent `add_vesting_schedule` call inside `payout` fails with `AtMaxVestingSchedules`, and because the return value is ignored, the transfer of `total_balance` (already executed) is never rolled back, no lock is applied to the locked portion, and the account is still marked `Completed`.

## Impact Explanation
An account can end up receiving the full "locked" purchase amount as immediately spendable balance instead of vesting-locked balance, breaking the pallet's documented guarantee that purchase-locked DOT remains locked until vesting unlocks. This is a lock-bypass/accounting-invariant violation rather than a new-money-creation bug, since `T::Currency::transfer` moves already-existing balance from the `PaymentAccount`.

## Likelihood Explanation
Exploitation requires: (1) the unprivileged `vested_transfer` extrinsic (available to any account) to be used to pre-fill `who`'s vesting schedule slots with schedules engineered to be fully vested by the time `payout` executes (so `vesting_balance` reports `None`/zero and the earlier guard in `payout` is bypassed), and (2) the privileged `PaymentAccount` calling `payout(who)` afterward, whose timing the attacker cannot fully control but can attempt to front-run within the same block or via mempool ordering. This is a narrower precondition than the raw claim suggests, since the pallet's own `vesting_balance(&who).is_none()` check (lines 313-316) already blocks the naive front-running scenario where `who` simply holds an active vesting schedule. The Purchase pallet is a retired, one-time DOT-sale module with no active `PaymentAccount`/`ValidityOrigin` workflow today, so real-world exploitability is essentially nil, though the underlying code defect (silently discarding `add_vesting_schedule`'s result via `let _ = ...`) is a genuine logic flaw that would be exploitable in any redeployment.

## Recommendation
- Do not discard the result of `add_vesting_schedule`. Either abort the entire `payout` (propagate the error, so the transfer is also rolled back within the same transactional `try_mutate`), or transfer only `free_balance` first and only transfer/lock `locked_balance` after `add_vesting_schedule` succeeds.
- Strengthen the pre-check to also account for the number of occupied vesting schedule slots for `who`, not just the currently-locked vesting balance, so that stale fully-vested schedule entries cannot be used to bypass the guard.
- If `add_vesting_schedule` fails, do not set `status.validity = AccountValidity::Completed`; instead surface the error and allow a retry path.

## Proof of Concept
1. `Purchase::create_account`, `update_validity_status(ValidHigh)`, and `update_balance(free, locked)` for account `who`, as in the existing `payout_works` test.
2. Have an unprivileged colluding account call `Vesting::vested_transfer` repeatedly to `who`, using schedules crafted so they are already fully vested (locked amount already released) by the time `payout` runs, until `who`'s vesting schedule count reaches `MaxVestingSchedules`. This ensures `T::VestingSchedule::vesting_balance(&who)` still returns `None`, so the pre-check inside `payout` at lines 313-316 does not abort the call.
3. Call `Purchase::payout(payment_account_origin, who)`.
4. Assert:
   - `Balances::free_balance(who)` increased by the full `free_balance + locked_balance`.
   - `Vesting::vesting_balance(&who)` does not reflect the purchase's `locked_balance` (the `add_vesting_schedule` call inside `payout` fails with `AtMaxVestingSchedules` and is silently discarded).
   - `Purchase::accounts(who).validity == AccountValidity::Completed`, confirming the account is marked complete despite the lock never being applied.

		pub fn payout(origin: OriginFor<T>, who: T::AccountId) -> DispatchResult {
			// Payments must be made directly by the `PaymentAccount`.
			let payment_account = ensure_signed(origin)?;
			let test_against = PaymentAccount::<T>::get().ok_or(DispatchError::BadOrigin)?;
			ensure!(payment_account == test_against, DispatchError::BadOrigin);

			// Account should not have a vesting schedule.
			ensure!(
				T::VestingSchedule::vesting_balance(&who).is_none(),
				Error::<T>::VestingScheduleExists
			);

			Accounts::<T>::try_mutate(
				&who,
				|status: &mut AccountStatus<BalanceOf<T>>| -> DispatchResult {
					// Account has a valid status (not Invalid, Pending, or Completed)...
					ensure!(status.validity.is_valid(), Error::<T>::InvalidAccount);

					// Transfer funds from the payment account into the purchasing user.
					let total_balance = status
						.free_balance
						.checked_add(&status.locked_balance)
						.ok_or(Error::<T>::Overflow)?;
					T::Currency::transfer(
						&payment_account,
						&who,
						total_balance,
						ExistenceRequirement::AllowDeath,
					)?;

					if !status.locked_balance.is_zero() {
						let unlock_block = UnlockBlock::<T>::get();
						// We allow some configurable portion of the purchased locked DOTs to be
						// unlocked for basic usage.
						let unlocked = (T::UnlockedProportion::get() * status.locked_balance)
							.min(T::MaxUnlocked::get());
						let locked = status.locked_balance.saturating_sub(unlocked);
						// We checked that this account has no existing vesting schedule. So this
						// function should never fail, however if it does, not much we can do about
						// it at this point.
						let _ = T::VestingSchedule::add_vesting_schedule(
							// Apply vesting schedule to this user
							&who,
							// For this much amount
							locked,
							// Unlocking the full amount after one block
							locked,
							// When everything unlocks
							unlock_block,
						);
					}

					// Setting the user account to `Completed` ends the purchase process for this
					// user.
					status.validity = AccountValidity::Completed;
					Self::deposit_event(Event::<T>::PaymentComplete {
						who: who.clone(),
						free: status.free_balance,
						locked: status.locked_balance,
					});
					Ok(())
				},
			)?;
			Ok(())
		}
