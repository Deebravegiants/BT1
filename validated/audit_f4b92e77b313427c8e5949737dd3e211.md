## Title
Webhook shop identity spoofing due to `shop`/`topic`/`webhook_id` fields not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — read from HTTP headers — are never included in the signed material and are handed to the app's handler unchecked. This breaks the identity binding `shop authenticated == shop attributed to the webhook payload`, letting any holder of one validly-signed webhook body (for example, a webhook delivered to an attacker's own store) relabel it as belonging to any other shop simply by changing the `x-shopify-shop-domain` header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers and are not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (the raw body) against the received HMAC using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly this body-only check, then constructs `WebhookMetadata` — including `shop: request.shop` — straight from the unauthenticated headers and forwards it to the app-registered handler: [4](#0-3) 

Because Shopify signs webhooks with the app's single shared `api_secret_key` (not a per-shop key), any shop that has the app installed receives webhooks whose HMAC is valid for that same secret regardless of which shop the header claims. The documented API explicitly instructs host applications to trust `data.shop` for shop-scoped processing (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is not a misuse of an undocumented API — it's the gem's advertised verification contract failing to bind the claimed shop to the signed bytes: [5](#0-4) 

The equality that should hold — `hmac_signed_content ⊇ {shop, topic}` — does not hold; only the body is signed, so `shop_claimed_in_header ≠ shop_bound_by_hmac`.

### Impact Explanation
An unprivileged internet user who installs the target app on their own store (a normal, unprivileged action requiring no credentials belonging to Shopify or the app) receives genuine webhook deliveries whose HMAC is valid under the app's shared secret. By resending that exact body/HMAC pair to the app's public webhook endpoint with a different `x-shopify-shop-domain` header, the attacker can make the app process/store attacker-controlled webhook content while attributing it to an arbitrary victim shop. Any app that follows the gem's documented pattern of keying data by `data.shop` (e.g., updating shop-scoped records, triggering shop-scoped side effects, or associating attacker-supplied order/customer data with the victim's tenant) suffers cross-tenant data confusion — this satisfies the Critical "cross-tenant access" bucket.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on a store the attacker controls (a routine, unprivileged action for any Shopify merchant/developer), (2) capturing one legitimate webhook request sent to the attacker's own endpoint (no TLS interception needed — it terminates at infrastructure the attacker controls), and (3) replaying it with a modified shop header to the target's webhook endpoint. No `api_secret_key`, access token, or social engineering is required, making this readily reachable by an unprivileged internet user.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified material, or otherwise cryptographically/contextually tie the claimed `shop` header to a specific, already-authenticated tenant (e.g., look up the expected shop by webhook subscription id server-side rather than trusting the header) before handing `WebhookMetadata` to the handler. At minimum, document that `data.shop` must never be trusted as an unverified tenant key and require host apps to cross-check it against a shop-specific value (e.g., an independently retrieved offline session/access token for a shop that must already be known, rather than derived from the same request).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw body, computed with the app's shared api_secret_key>`
   - raw body containing attacker-controlled order data.
3. Attacker captures this exact raw body + `x-shopify-hmac-sha256` value (trivial, since the request is delivered to infrastructure they control).
4. Attacker resends an HTTP POST to the same webhook endpoint with the identical raw body and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks the (unchanged) raw body against the HMAC — validation succeeds.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, as shown in `Registry#process`: [6](#0-5) 

Any app following the documented pattern of scoping work by `data.shop` now processes attacker-controlled data under the victim shop's identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```
