Audit Report

## Title
Response cache key in gateway v2 HTTP capability handler omits `WorkflowID`, breaking documented workflow-level isolation and enabling cross-workflow response disclosure - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's v2 HTTP-action response cache keys cached responses solely by `gateway_common.OutboundHTTPRequest.Hash()`, which — per the handler's own test suite — does not include `WorkflowID`, contradicting the `README.md`'s explicit claim that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage." As a result, two different workflows owned by the same `WorkflowOwner` that issue identical outbound HTTP requests (same method/URL/headers/body) with caching enabled can receive each other's cached HTTP responses within the TTL window.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` in `core/services/gateway/handlers/capabilities/v2/response_cache.go` use `req.Hash()` as the sole cache map key: [1](#0-0) , [2](#0-1) . The package doc comment claims the hash includes "workflowOwner" but not `WorkflowID`: [3](#0-2) .

The handler's own test suite proves this behaviorally: identical requests differing only in `WorkflowID` produce equal hashes (cache collision), while differing `WorkflowOwner` produces distinct hashes: [4](#0-3) , [5](#0-4) .

This directly contradicts the design goal stated in the README: [6](#0-5) .

The cache is exercised on the node-message path for outbound HTTP capability calls in `makeOutgoingRequest`, which reads `req.CacheSettings` and dispatches to `Fetch`/`Set` keyed purely on `req.Hash()`: [7](#0-6) . There is no additional per-`WorkflowID` namespacing anywhere else in `response_cache.go` (confirmed by full read of the file), so the collision demonstrated by the unit tests carries directly into the cache serving path.

## Impact Explanation
Because `WorkflowID` is excluded from the cache key, different workflows belonging to the same `WorkflowOwner` that issue byte-identical outbound HTTP action requests (same method, URL, headers, body) with `CacheSettings.Store=true` and `MaxAgeMs>0` will read each other's cached responses. This breaks the workflow-level isolation explicitly promised by the README and can leak response bodies/headers (potentially containing secrets or per-workflow-specific data) across workflow boundaries within the same account. This falls into the "cross-user response corruption" impact class, scoped to same-owner, cross-workflow leakage (not cross-tenant/cross-owner, since `WorkflowOwner` is still part of the hash).

## Likelihood Explanation
Exploitation is fully within an unprivileged workflow author's control and requires no external attacker: an owner running two workflows that make identical outbound HTTP requests with caching enabled will trigger the collision deterministically within the TTL window (default 10 minutes). This is realistic for shared/templated workflow patterns using common integrations. The bug is proven directly by the existing test assertions rather than requiring speculative reasoning.

## Recommendation
Include `WorkflowID` (alongside `WorkflowOwner`, method, URL, headers, and body) in `OutboundHTTPRequest.Hash()` in the `chainlink-common` module so the cache key matches the documented isolation guarantee, or explicitly update `README.md` to describe owner-level (not workflow-level) cache scoping if that is the intended design.

2.
