### Title
Lost-update race between `untrust` and `add`/`setAutoApprove`/other mutators lets a stale trusted-write clobber a legitimate untrust - ([File: features/connected-origins/module/connections.js])

### Summary
`ConnectedOrigins` implements read-modify-write operations (`untrust`, `add` via `#setAttributes`, `connect`, `disconnect`, `clearConnections`, etc.) as three separate steps: read via `#getData`, compute a new plain array in JS, then write via `#setData`. Because the computed value handed to the underlying atom is a plain value (not a functional updater), the atom's own write-serialization does not protect against application-level staleness, so two concurrent calls that both read the same pre-change snapshot can race, and whichever finishes last silently overwrites the other's change.

### Finding Description
`untrust` and `add`/`#setAttributes` both follow this pattern: [1](#0-0) [2](#0-1) 

Each of these methods independently calls `#getData()` (`this.#connectedOriginsAtom.get()`), computes a new array in JavaScript, and then calls `#setData(newData)`, which calls `this.#connectedOriginsAtom.set(data)` with a fully-formed plain value: [3](#0-2) 

The atom stack is `dedupe(createStorageAtomFactory(...))`. `dedupe.set` forwards a setter function into the underlying atom's `set`, and the storage atom's `set` is wrapped with `makeConcurrent` in `enforce-rules.ts`, which does serialize the *storage atom's own* `set()` invocations one at a time: [4](#0-3) 

However, that serialization only protects the value computed *inside* the queued setter call — it re-derives `current` via `get()` at the moment the queued call actually executes. The problem is that `ConnectedOrigins` never uses this setter form: `#setData` passes an already fully-computed plain array (built from a `#getData()` snapshot taken *before* entering the queue). So if `untrust({ origin })` and `add({ origin, trusted: true })` are both invoked concurrently:

1. Both call `#getOrigin`/`#getData` and observe the same initial state `D0` (origin present, trusted).
2. `untrust` computes `D1 = D0.filter(o => o.origin !== origin)` (origin removed).
3. `add` (via `#setAttributes`) computes `D2 = D0.map(...)` with `trusted: true` merged in (unaware `untrust` ran).
4. Both call `#setData`, which enqueue two `atom.set(plainValue)` calls. The storage atom's `makeConcurrent` serializes *execution order* but not *correctness of the input* — each call still writes its own pre-computed, stale-based value.
5. Whichever `#setData` call is scheduled second wins and overwrites storage with its own value, regardless of which represents the user's actual (last) intent. If `add`'s write lands after `untrust`'s, the origin ends up trusted again, i.e. an untrust performed by the user is silently discarded and `isTrusted({ origin })` returns `true` for a hostile origin the user explicitly revoked.

This is a genuine read-modify-write/TOCTOU gap: the "atomicity" enforced by `enforce-rules.ts` operates purely at the low-level atom's own setter-of-current-value pattern, and `connections.js` bypasses that protection by always working with externally-computed plain values instead of composable setter functions.

### Impact Explanation
If exploited, an attacker-controlled or malicious dapp origin that can trigger a `connect`/`add({ trusted: true })` call (e.g., via reconnect/auto-reconnect flows) at the same time a user clicks "revoke/untrust" in the wallet UI can cause its origin trust to persist despite the user's explicit revocation. A persistently "trusted" origin typically bypasses future approval prompts (see `isTrusted`/`isAutoApprove` usage gating auto-approval flows), so this is a persistence-of-unauthorized-origin-trust bug — a real, if narrow, wallet security defect matching a "privilege persistence" / "origin trust bypass" class of impact, since the wallet keeps trusting an origin the user believed was revoked.

### Likelihood Explanation
Exploitability requires precise timing: the attacker's connect/`add` call and the user's `untrust` action must race such that both read the atom before either writes, and the attacker's write must land after the user's. This is plausible in real usage because dapps can trigger reconnection/`add` calls autonomously (e.g., on window focus, periodic pings, or in response to detecting a disconnect) right as a user revokes access, and JS promise scheduling/storage I/O latency gives a real window for this interleaving. It is not trivially deterministic from a single attacker action, so likelihood is moderate rather than high, but it is realistically triggerable without any privileged access — only ordinary dapp-origin RPC calls plus normal user interaction.

### Recommendation
Convert `untrust`, `#setAttributes`, `connect`, `disconnect`, `clearConnections`, and any other read-modify-write mutator in `connections.js` to use the atom's setter-function form (`this.#connectedOriginsAtom.set(previous => computeNewValue(previous))`) instead of computing the new array from a separately-fetched snapshot and passing a plain value. This ensures the read and the write happen atomically within the atom's own serialized queue, eliminating the TOCTOU window. Alternatively, wrap the entire read-compute-write sequence in `connections.js` with its own mutex per key (e.g. `origin`) so only one mutating operation for a given origin can be in flight at a time.

### Proof of Concept
Integration test (extending `features/connected-origins/module/__tests__/connections.test.js`):
```js
test('concurrent untrust and add should not resurrect trust (lost-update race)', async () => {
  await connectedOriginsAtom.set([{ origin: 'exodus.com', trusted: true }])

  await Promise.all([
    connectedOrigins.untrust({ origin: 'exodus.com' }),
    connectedOrigins.add({ origin: 'exodus.com', trusted: true }),
  ])

  const isTrusted = await connectedOrigins.isTrusted({ origin: 'exodus.com' })
  // Expected: since untrust represents the last explicit user-intended revoke,
  // the origin must not silently end up trusted due to interleaved writes.
  expect(isTrusted).toBe(false)
})
```
Running this against the current implementation is expected to be flaky/fail intermittently (or deterministically fail if `add`'s internal awaits — e.g. `#getAccounts`/asset name resolution — make its `#setData` call land after `untrust`'s), demonstrating that the atom's final state can end up trusted even though the user's last intended action was `untrust`.
