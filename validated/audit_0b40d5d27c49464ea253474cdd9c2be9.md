### Title
Webhook shop/topic identity fields are unauthenticated (not covered by HMAC) - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, but exposes `shop` and `topic` from HTTP headers that are never included in that signature. Any code path (e.g. `ShopifyAPI::Webhooks::Registry`) that trusts `request.shop`/`request.topic` after `HmacValidator.validate` succeeds is trusting an unauthenticated value.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` and `topic` are read straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is `HMAC(secret, verifiable_query.to_signable_string)` — i.e. `HMAC(secret, raw_body)`: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`HMAC(secret, raw_body) == received_hmac` should imply `(shop, topic, raw_body)` is the exact tuple Shopify sent.

In reality the equality only proves `raw_body` is authentic; `shop-domain` and `topic` are attacker-controllable HTTP headers not covered by the digest. An unprivileged internet user who obtains one genuine, HMAC-signed webhook body for their own shop (trivial — install the app on any dev/trial shop and trigger a webhook) can replay that exact `raw_body` with the `X-Shopify-Shop-Domain` header changed to a victim shop and the request still passes `HmacValidator.validate`, because the header is never part of the signed string.

### Impact Explanation
Any host application that relies on `ShopifyAPI::Webhooks::Registry`/`Request#shop` (after HMAC validation succeeds) to determine which tenant a webhook belongs to — the gem's documented pattern — can be made to process a forged webhook as if it originated from a different, victim shop. This is a cross-tenant confusion: the app's own signature check gives a false sense of per-shop authenticity for a field it never actually signs.

### Likelihood Explanation
Requires only: (1) attacker has app installed on any shop they control (a normal, unprivileged self-serve app install) to obtain a validly-signed webhook body, and (2) ability to send an arbitrary HTTP request to the app's webhook endpoint with a modified `shop-domain` header — both are within reach of an unprivileged internet user with no access token or `client_secret`.

### Recommendation
Include `shop-domain` (and `topic`/`webhook-id`) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind the shop identity to the payload before it is exposed via `Request#shop`, so `HmacValidator.validate` failing/succeeding is meaningful for the identity fields the host application actually keys tenant lookups on.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture a real webhook delivery (raw body `B`, headers including `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`).
2. `H = Base64(HMAC-SHA256(client_secret, B))` — `H` is valid for body `B` regardless of headers, per `Request#to_signable_string`/`hmac`.
3. Replay to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` returns `true` (it only checks `HMAC(secret, B)`), so the host app processes the webhook believing it is authentic data for `victim.myshopify.com`.

          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
