### Title
Missing maximum-price protection in `BandwidthManager.purchase()` allows buyers to unexpectedly overpay when tier prices change between quote and execution - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` computes the fee-token amount to pull from the caller using the *current* on-chain `tierPrice[tier]` value at execution time, with no parameter letting the buyer cap the amount they are willing to pay. Since tier prices are mutable state (`tierPrice`, updated by the `SetTiers` governance message processed asynchronously via `onAccept`), the price seen at transaction execution can differ from the price the buyer quoted off-chain when building/approving the call, causing the buyer to be charged more than expected with no way to abort.

### Finding Description
`purchase()` reads `tierPrice[tier]` and derives the amount to transfer from the buyer purely from current storage, then immediately calls `safeTransferFrom`: [1](#0-0) 

There is no `maxAmount`/`maxPrice` argument, and no check comparing the computed `amount` against any buyer-specified ceiling — the function will pull whatever `tierPrice[tier] * months` scales to at the moment the transaction executes.

`tierPrice` is governance-mutable and is expected to change over the life of the protocol ("Governance keeps the two in sync by dispatching a `SetTiers` message... whenever prices change"). The update path is asynchronous cross-chain messaging (pallet → `onAccept` → `OnAcceptActions.SetTiers`), so there is an unavoidable window between a buyer computing/quoting a price off-chain (e.g. via the documented `quote()` helper) and the buyer's `purchase()` transaction landing on-chain, during which the tier price can be raised.

This is structurally the same defect as the reported issue: a function commits to transferring/spending a value calculated from mutable on-chain state at execution time, with no user-supplied bound to guard against that state having moved between off-chain calculation and on-chain settlement. In the original report the mutable state was `totalSlashableCollateral` (time/epoch-dependent); here it is `tierPrice` (governance-update-dependent). In both cases the caller has no mechanism to make the transaction revert instead of accepting the unfavorable outcome.

Buyers typically approve the manager for exactly the quoted amount (per the docs' recommended pattern), so in the common case the transaction would simply revert on insufficient allowance rather than silently overcharging — but any buyer who pre-approves a larger allowance (a common integration pattern, e.g. contracts computing `quote()` and approving with headroom, or using `approve(max)`), or any race where a price *decrease* lands right after the buyer's approval for the old higher price, is exposed. In the overpayment direction specifically, a price increase landing between quote and execution silently debits the buyer more than they intended, without any revert to signal the mismatch.

### Impact Explanation
A buyer can be charged an amount different from (specifically, higher than) what they computed and consented to off-chain, with the transaction succeeding and irreversibly moving fee-token funds to the manager contract. There is no way to bound the maximum spend or force the transaction to fail safely when the price has moved, so buyers suffer unexpected fund loss proportional to the price delta and the size of their pre-existing allowance.

### Likelihood Explanation
Tier price updates are an expected, routine governance operation (not a malicious or adversarial action), and the purchase flow explicitly separates off-chain quoting from on-chain execution across an asynchronous cross-chain messaging window (`SetTiers` delivered via ISMP), making the race condition realistically triggerable. Any buyer using a non-exact allowance (a normal integration pattern, as shown in the docs' own `BuyBandwidth` contract, which approves per-transaction but is a template many integrators would generalize with pre-approved allowances) is exposed without any additional attacker action required.

### Recommendation
Add a `maxAmount` (or `maxPricePer18d`) parameter to `purchase()` and revert (e.g. `PriceExceedsMax()`) if the computed `amount` exceeds the caller-specified ceiling, mirroring standard slippage-protection patterns (analogous to `amountOutMinimum` in AMM swaps).

### Proof of Concept
1. Buyer calls `quote(tier, months)` off-chain (per the documented pattern) and observes `tierPrice[tier] = P0`, approves the manager for `cost(P0, months)`, or approves an allowance with headroom for future purchases.
2. Governance dispatches `SetTiers` raising `tierPrice[tier]` to `P1 > P0`; the pallet delivers this to `BandwidthManager` via `onAccept`, updating `tierPrice[tier]` before the buyer's transaction is mined.
3. Buyer's `purchase(app, tier, months, chain)` transaction executes: `total18d = tierPrice[tier] * months` now uses `P1`, and `IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount)` pulls the higher amount — succeeding silently (assuming sufficient allowance) instead of reverting, and the buyer pays more than the amount they calculated and intended to authorize.     function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
