### Title
Webhook Shop-Domain Header Trusted Without HMAC Coverage Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature computed by `Utils::HmacValidator.validate` only covers the raw request body, not this header. `Registry.process` trusts the header-derived `shop` value and hands it to the app's `WebhookHandler` as an authenticated tenant identifier, even though it was never bound to the signature that was actually verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the signature purely from `to_signable_string` (the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` checks only that this body-only HMAC is valid, then immediately trusts `request.shop` (a header value never covered by that HMAC) as the tenant identity passed to the app-supplied handler: [4](#0-3) 

This is precisely the bug class in the report: an identity-establishing field (`shop`) is *acted on* (used to construct `WebhookMetadata.shop`, which the host application uses to route/attribute the webhook to a tenant) but is *not covered by the same integrity check* (`HMAC`) that authorizes the request. The equality that should hold — "shop claimed in the header == shop bound by the signature" — is never enforced; the code only enforces "body bytes verified == body bytes parsed."

### Impact Explanation
Because the app's client secret (`api_secret_key`) is shared across every shop that installs the app, any merchant who installs the app receives genuinely-signed webhooks whose HMAC is valid for that merchant's own payload. A malicious merchant can capture one of their own legitimate webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. If the host application uses this `shop` value to select which merchant's session/data record to update (which is the documented purpose of `WebhookMetadata.shop`), this results in cross-tenant data confusion/injection — writing or triggering actions against a shop the attacker doesn't control, using a signature that was never bound to that shop. This falls under the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only an internet-reachable webhook endpoint and the ability to install the app on an attacker-controlled shop (or otherwise obtain one valid signed webhook body/HMAC pair) — no access token, `api_secret_key`, or privileged account is needed. This mirrors the original report's frontrunning scenario: the attacker doesn't need to break the cryptography, only to reuse a validly-signed artifact against an unbound identity field.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, or otherwise cryptographically bind the header-derived identity to the verified payload, e.g. by having `to_signable_string` concatenate `shop + topic + raw_body` (matching whatever canonicalization Shopify actually signs), or by requiring the host application to cross-check `request.shop` against the session/shop record it expected before trusting the webhook. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-selection key without additional verification (e.g., confirming a webhook was actually expected/registered for that shop/topic/id combination).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, causing Shopify to deliver a real webhook with a valid body `B` and valid header `hmac-sha256: H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends `POST /webhooks` to the app with the exact same body `B` and header `hmac-sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of their own domain.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and matches `H` — validation succeeds because the shop header was never part of the signed input.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler with a shop identity the attacker fully controls despite the signature being unrelated to that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
