### Title
Webhook shop-tenant identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values directly from HTTP headers, but the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. `Registry.process` trusts `request.shop` to build the `WebhookMetadata` handed to the app's `WebhookHandler`, meaning the tenant-identifying field is never bound to the cryptographic signature that is supposed to authenticate the whole webhook delivery.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed payload: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., body-only) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` raises only if the HMAC (body) check fails, then immediately trusts `request.shop` (header-derived, unsigned) to construct `WebhookMetadata` passed to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop-header == shop-cryptographically-bound-to-signature`. Because the signature only covers `@raw_body`, an attacker who can obtain any single valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — e.g., by installing the app on a shop they control and capturing the genuine webhook Shopify sends them — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a different (victim) shop that also has the app installed. `Utils::HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will invoke the handler with `shop: <victim-shop>` and the attacker-supplied body — resulting in cross-tenant data being processed/stored under the wrong shop's identity.

### Impact Explanation
This breaks the tenant/shop identity binding that webhook consumers rely on to route and store per-merchant data (e.g., attributing an `orders/create` payload to the wrong shop, corrupting or injecting data into another merchant's tenant record, or triggering shop-scoped side effects for a shop that never sent the event). This matches the "Critical - cross-tenant access" impact class: the gem's own webhook-processing API (`Webhooks::Request` / `Webhooks::Registry`) delivers attacker-influenced, cross-tenant-attributable data to the host application's handler without any cryptographic binding of the shop field to the signature.

### Likelihood Explanation
Exploitation requires the attacker to possess one legitimately-signed `(body, hmac)` pair for the target app — achievable by any unprivileged user who installs the app on their own store (a normal, unprivileged action for public apps) and captures the webhook Shopify sends them. No `api_secret_key`, access token, or privileged access is required; only a normal app install by an unrelated shop. The victim shop must also have the app installed and a matching webhook topic. This is a realistic, low-privilege attack path.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed content that `HmacValidator` verifies, or otherwise cryptographically bind the shop identity to the webhook signature, matching Shopify's guidance that the shop domain must be treated as untrusted unless verified. At minimum, document and/or enforce that consumers cross-check `request.shop` against a shop they already know is installed with a matching, previously-issued webhook id/session — not solely rely on `HmacValidator.validate` to authenticate the shop attribution.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g., `orders/create`) and capture the exact raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sends (both are signed with the app's shared `api_secret_key`, valid for the app regardless of shop).
2. Send a forged HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unmodified)
   - Header `X-Shopify-Hmac-Sha256: H` (unmodified)
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com` (forged — victim shop also has the app installed)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as desired
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. The registered handler's `handle(data:)` is invoked with `WebhookMetadata#shop == "victim.myshopify.com"` and `body` fully attacker-controlled (from step 1), even though the event never originated from `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
