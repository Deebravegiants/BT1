## Analysis Result [1](#0-0) imports and enables `SafeERC20`, and uses it correctly for inbound transfers (`safeTransferFrom`), but the two functions that release escrowed funds to a beneficiary do not use it.

### Title
Intent Gateway (Tron) escrow release uses raw `IERC20.transfer` via low-level `call` instead of `SafeERC20.safeTransfer`, silently accepting failed transfers - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron variant of the Intent Gateway release escrowed/dust tokens to beneficiaries using a raw low-level call to the ERC20 `transfer` selector, checking only that the call did not revert — not that the token actually returned `true`. This is the exact bug class flagged in the referenced report (no use of `safeTransfer`), and here it is reachable on every cross-chain settlement delivered by an unprivileged relayer.

### Finding Description
In `withdraw()`, escrowed tokens are paid out with: [2](#0-1) 

and accumulated transaction fees with: [3](#0-2) 

The same pattern is used for dust sweeping in `onAccept`: [4](#0-3) 

In all three cases, the code does `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...)); if (!success) revert TransferFailed();`. A low-level `call` only reports `success = false` when the callee **reverts**. Many ERC20/TRC20 tokens (a class especially prevalent on Tron, where non-standard TRC20 implementations are common) signal failure by **returning `false`** instead of reverting — e.g. paused, blacklisted, or insufficient-allowance-style checks that degrade gracefully. In that case `success` is still `true` because the call itself completed normally, so `TransferFailed()` is never triggered, even though no tokens were actually moved.

Critically, the escrow accounting is unconditionally decremented right after the unchecked call: [5](#0-4) 

and the order is marked filled/refunded before any of this: [6](#0-5) 

By contrast, the canonical (non-Tron) equivalent, `IntentsBase._withdraw`, correctly uses `SafeERC20.safeTransfer`, which reverts on a `false` return value: [7](#0-6) 

This `withdraw()` path is triggered directly by `onAccept`, which is called by the `IsmpHost` whenever a relayer delivers a `RedeemEscrow`/`RefundEscrow` message from any registered gateway instance — i.e., driven by permissionless relaying of a cross-chain settlement, not by any privileged actor: [8](#0-7) 

### Impact Explanation
If the escrowed token silently returns `false` on transfer (e.g. paused/blacklisted TRC20, or a token temporarily failing an internal check), the contract:
1. Marks the order as filled/refunded (`_filled[commitment] = beneficiary`), permanently closing the order.
2. Decrements `_orders[commitment][token]`, permanently erasing the escrow accounting for those funds.
3. Never actually delivers the tokens to the beneficiary.

The tokens remain stranded in the `IntentGatewayV2` contract with no accounting entry pointing to them and no code path to reclaim them (the order is already finalized), resulting in a permanent freeze/loss of user or solver funds. This satisfies the "concrete... permanent freezing of funds" criterion.

### Likelihood Explanation
This triggers automatically whenever the escrowed/dust token behaves non-standardly (returns `false` instead of reverting), which is a well-documented and common pattern for TRC20 tokens on Tron (the exact chain this contract targets). No malicious actor is required — a normal relayer delivering a normal `RedeemEscrow`/`RefundEscrow`/`SweepDust` message against a token that returns `false` under certain conditions triggers the loss. Given the contract explicitly targets Tron, where non-conforming TRC20 semantics are prevalent, likelihood is realistic rather than purely theoretical.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (both the token loop and the fee payout) and in the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with `IntentsBase._withdraw` in the non-Tron implementation. `SafeERC20` is already imported and used elsewhere in this same contract (`safeTransferFrom`), so this is a drop-in fix.

### Proof of Concept
1. A user places an order escrowing token `T` (a TRC20 whose `transfer` returns `false` instead of reverting when, e.g., the recipient is blacklisted or the contract is paused) via `placeOrder`.
2. The order is filled on the destination chain and Hyperbridge delivers a `RedeemEscrow` `PostRequest` to the source-chain `IntentGatewayV2` via `onAccept` → `withdraw(body, false)`.
3. Suppose `T.transfer(beneficiary, amount)` returns `false` (e.g., beneficiary momentarily blacklisted, or token paused) instead of reverting.
4. `token.call(...)` returns `success = true` (the call itself did not revert), so `TransferFailed()` is not raised.
5. `_orders[commitment][token] -= amount` executes, and `_filled[commitment] = beneficiary` is already set — the order is permanently considered settled.
6. The `amount` of token `T` remains in the `IntentGatewayV2` contract balance forever, with no escrow entry pointing to it and no ability to sweep or redeem it, resulting in permanent loss of the beneficiary's (solver's) funds.
