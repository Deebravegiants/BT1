### Title
Arbitrary unconstrained `EmporiumOperation` calls let any caller drain residual/stranded ERC20 balances from `EmporiumUpgradeable` outside the `erc20TokenAddresses`/`deltaAmountChanges` accounting - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes a user-supplied list of `EmporiumOperation`s via raw `op.endpoint.call{value: op.value}(op.callData)` with no restriction that the touched tokens/endpoints be among `circomData.erc20TokenAddresses`. Because the post-tx balance reconciliation (`balancesBefore`/`balancesAfter`/`handleOut`) and Hinkal's slippage/balance-diff invariant in `Hinkal.transact` only iterate over `circomData.erc20TokenAddresses`, an attacker can craft an op that calls any ERC20 held by the Emporium contract (e.g. a token left over from a prior partial swap/router refund) and `transfer()` it straight to an address they control, completely bypassing every balance check tied to `deltaAmountChanges`.

### Finding Description
The invariant that should hold is: tokens leaving the Emporium action in a transaction == `-deltaAmountChanges` that Hinkal sent it for that transaction, reconciled through `handleOut`: [1](#0-0) 

That reconciliation, however, is only computed over `circomData.erc20TokenAddresses`, an array the attacker fully controls (they choose which tokens to declare and in what order): [2](#0-1) 

Before that reconciliation happens, `runAction` executes `stack.ops`, decoded from attacker-controlled `circomData.externalActionData.externalActionMetadata`, and for the "stateless" branch performs a fully arbitrary low-level call from the Emporium contract itself: [3](#0-2) 

Nothing constrains `op.endpoint`/`op.callData` to only affect tokens listed in `erc20TokenAddresses`, nor does anything require the ops to be swap/router calls at all. An attacker can therefore set `op.endpoint = strandedTokenAddress` and `op.callData = abi.encodeWithSelector(IERC20.transfer.selector, attackerAddress, strandedAmount)`. This call executes with `msg.sender == EmporiumUpgradeable` (i.e., using the Emporium's own token balance), moving `strandedAmount` directly to the attacker's address — completely outside the `balancesBefore`/`balancesAfter` diffing (which never even samples `strandedTokenAddress` because the attacker simply omits it from `circomData.erc20TokenAddresses`).

Consequently:
- `Hinkal.transact`'s balance-diff/slippage check, `require(balanceDif == amountChanges[i] + utxoAmount)`, never observes the stolen token because that loop also only iterates `circomData.erc20TokenAddresses`: [4](#0-3) 
- The circuit's `inTotal + amountChanges === outTotal` constraint only binds the tokens/UTXOs the attacker's own proof declares; it has no visibility into or control over what the Emporium contract's raw balance holds for unrelated tokens.
- `verifyWallet`/`performHinkalChecks`/`dimensionsCheck`/`calldataHash` all validate internal consistency of the attacker's own crafted `circomData`, but none of them restrict the content of `op.endpoint`/`op.callData` to the declared token set.

Any ERC20 balance the Emporium contract accumulates and does not immediately sweep out in the same transaction it arrived in (e.g., router partial-fill refunds, rounding dust, or any token a previous user's transaction left behind because that prior transaction's `erc20TokenAddresses` did not include it or `handleOut`'s `balanceChange <= 0` branch silently dropped it) becomes a standing target any subsequent unprivileged caller can drain in one call.

### Impact Explanation
Direct theft of funds parked in the `EmporiumUpgradeable` contract (residual/stranded protocol or in-flight user tokens) by any unprivileged attacker who can call `Hinkal.transact` with `externalActionId` pointing at Emporium and a self-crafted `externalActionMetadata`. This is repeatable for every stranded token/amount discovered in the contract, and the stolen value is not counted against, or reconciled with, `deltaAmountChanges`, `balanceDif`, or the circuit's public inputs at all — it is a raw external call, not a UTXO-accounted output. This matches Critical: direct theft of shielded or in-flight user funds/protocol funds sitting in the action contract.

### Likelihood Explanation
Preconditions: some ERC20 balance must be resting in the `EmporiumUpgradeable` contract that is not the attacker's own funds (e.g., dust/refund left by a prior transaction's router call, or any token not declared in a given tx's `erc20TokenAddresses`). The attacker needs no special role — only the ability to submit a valid Hinkal proof for their own (even zero-value) UTXOs and to freely encode `EmporiumStack.ops`, both of which are explicitly listed attacker capabilities. Cost is a single transaction; the check is trivially satisfiable since `op.endpoint`/`op.callData` are unconstrained bytes decoded straight from attacker-supplied `externalActionMetadata`.

### Recommendation
Restrict `EmporiumOperation.endpoint` calls so that any token balance change they cause is confined to (and fully accounted against) `circomData.erc20TokenAddresses`/`deltaAmountChanges` — e.g., snapshot and diff the balance of every token touched by an op's target (not just the declared array), or maintain an explicit allow-list/registry of permitted router/endpoint contracts and require `handleOut` to reconcile against the full set of tokens the Emporium contract could plausibly hold, not just the caller-declared subset. At minimum, sweep and zero out any per-token residual balance within the same transaction it is created so nothing is ever "parked" for a later, unrelated caller to claim.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`; register Emporium as an external action and as an allowed recipient of itself.
2. Seed a residual balance in `EmporiumUpgradeable`: deploy a mock ERC20, mint tokens directly to the Emporium contract address (simulating a stranded router refund/dust from a prior transaction), without any corresponding `deltaAmountChanges` entry.
3. As attacker EOA (with their own valid, unrelated shielded UTXO/proof, zero-value transaction), call `Hinkal.transact` with `externalActionId` = Emporium, and `externalActionMetadata` encoding an `EmporiumStack` whose single `op` is `{endpoint: strandedToken, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount)}`. `circomData.erc20TokenAddresses` omits `strandedToken` entirely.
4. Assert before/after: `strandedToken.balanceOf(attacker)` increases by `strandedAmount`, and `strandedToken.balanceOf(Emporium)` decreases by `strandedAmount`, while `deltaAmountChanges` for the tx (computed from `circomData.amountChanges`) contains no entry for `strandedToken` — i.e., tokens left the action with no corresponding `-deltaAmountChanges`, breaking the stated invariant.
5. Confirm `Hinkal.transact` does not revert (no `balanceDif`/slippage check ever inspects `strandedToken` since it's absent from `erc20TokenAddresses`).
