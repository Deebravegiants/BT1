### Title
Panic on empty BEEFY commitment `payload` array crashes proof verification before signature checks - (File: evm/rust/src/conversions.rs)

### Summary
`pallet-beefy-consensus-proofs::verify_and_apply` (called from the public `submit_proof` extrinsic) ABI-decodes an attacker-supplied `BeefyConsensusProof` and immediately converts it into the SCALE `ConsensusMessage` type via a chain of `From` impls, before any BEEFY signature or authority-set verification takes place. One of those impls, `From<Commitment> for SpCommitment`, unconditionally calls `.expect()` on the first element of the attacker-controlled `payload` vector. A submitter can craft a `PROOF_TYPE_NAIVE` proof whose `signedCommitment.commitment.payload` array is empty, causing an unrecoverable Rust panic inside on-chain execution instead of a typed error — the same bug class as CVE-2018-18192's NULL pointer dereference on unchecked first-element access.

### Finding Description
`Pallet::verify_and_apply` in `modules/pallets/beefy-consensus-proofs/src/lib.rs:805-838` is reached from `do_submit_proof`, dispatched by any signed account via the `submit_proof` extrinsic. For `types::PROOF_TYPE_NAIVE`, it does:

```rust

    .map_err(|_| Error::<T>::AbiDecodeFailed)?;
let scale_proof: beefy_verifier_primitives::ConsensusMessage = abi_proof.into();
``` [1](#0-0)

``` [3](#0-2) 

`Commitment.payload` is a Solidity dynamic array (`PayloadItem[]`) decoded straight from attacker-supplied ABI bytes — it can legally be zero-length. This `.expect()` runs unconditionally, entirely before `handlers::handle_incoming_message` is invoked to actually verify the BEEFY signature/authority set at line 840. There is no length check anywhere upstream (ABI decoding does not enforce non-empty dynamic arrays), so a submitter can trivially trigger the panic with a well-formed but empty-payload commitment.

This mirrors the exact bug class the codebase has already hardened against in multiple other conversion/verification paths (e.g. `beefy_verifier::verify_mmr_leaf`'s `leaf_indices[0]` guard, `grandpa` verifier's `RelayHeaderNotInUnknownHeaders`, `pharos`'s `MAX_PROOF_DEPTH`/`nibble_at_depth` guard, and the ethereum trie's empty-HP-prefix fix) — all of which replaced an unchecked first-element/index access with a typed `Err`. This one conversion path was missed.

### Impact Explanation
A panic during on-chain extrinsic execution in a Substrate runtime is not a graceful revert like a Solidity `require`; it aborts Wasm execution via the runtime's panic handler, which for defensive-panic paths in block-building/import can render the block invalid or halt further processing of that transaction batch, and in the worst case can be leveraged to repeatedly disrupt block production for any node executing this extrinsic (a permissionless, unprivileged transaction) — this is a denial-of-service against the consensus-message dispatch path, "a route unable to deliver messages," which is explicitly in-scope. The transaction sender pays no verification cost since the panic happens before the expensive BEEFY signature check, making this cheap to trigger repeatedly.

### Likelihood Explanation
High: the attack requires only a single signed extrinsic (`submit_proof`) with `PROOF_TYPE_NAIVE` and a syntactically valid ABI-encoded `BeefyConsensusProof` whose `payload` array is empty — no privileged role, no race condition, no dependency on other on-chain state. The `AbiDecodeFailed` map only catches ABI decoding errors, not semantic emptiness, so the empty array decodes successfully and the panic triggers deterministically at the `.expect()` call.

### Recommendation
In `evm/rust/src/conversions.rs`, change `From<Commitment> for SpCommitment` to a fallible conversion (`TryFrom`) that returns an error (e.g. `Error::<T>::AbiDecodeFailed` or a new `EmptyCommitmentPayload` variant) when `value.payload` is empty, and propagate that error through `From<RelayChainProof> for MmrProof` and `From<BeefyConsensusProof> for ConsensusMessage` (or perform the emptiness check directly in `verify_and_apply` before calling `.into()`), consistent with the guard pattern already used for `leaf_indices`, `RelayHeaderNotInUnknownHeaders`, and `MAX_PROOF_DEPTH` elsewhere in the codebase.

### Proof of Concept
1. Craft `BeefyConsensusProof` (Solidity struct) with `relay.signedCommitment.commitment.payload = []` (empty dynamic array), any values for the remaining fields (they need not be valid signatures — the panic occurs before verification).
2. ABI-encode it as the `abi_decode_params` input for `ismp_abi::ecdsa_beefy::BeefyConsensusProof`.
3. Submit `submit_proof(proof = [PROOF_TYPE_NAIVE_byte] ++ abi_encoded_bytes)` from any signed account, within the `MaxProofSize` bound.
4. Execution reaches `abi_proof.into()` → `From<Commitment> for SpCommitment` → `iter.next().expect("commitment has at least one payload entry")` on the empty vector → panic, aborting the extrinsic's Wasm execution instead of returning `Error::<T>::AbiDecodeFailed`/`VerificationFailed`.

Note: I was unable to execute this against a running node within this session; the finding is based on static analysis of the decode → conversion → dispatch call chain described above, and confidence would benefit from confirming in a test harness (e.g. `parachain/simtests/src/pallet_beefy_consensus_proofs.rs`) that this exact panic is not already caught by a `catch_unwind`/defensive wrapper elsewhere in `handlers::handle_incoming_message` or the extrinsic dispatch machinery.
