## Title
Webhook HMAC only signs the request body, allowing shop-domain spoofing across tenants - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` proves nothing about the `shop`, `topic`, or `webhook-id` values — those are taken straight from unauthenticated HTTP headers. `Registry.process` passes this unauthenticated `shop` value straight to the app's webhook handler as the tenant key, breaking the binding between "bytes verified by HMAC" and "shop identity trusted by the handler."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `to_signable_string` (i.e. the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header value) to the handler as the trusted tenant identifier: [4](#0-3) 

The binding that should hold is:
`bytes_verified_by_HMAC == identity_used_for_tenant_binding (shop)`

but instead:
`bytes_verified_by_HMAC = raw_body` while `identity_used_for_tenant_binding = header["shopify-shop-domain"]` (unsigned).

Because the app's own shared secret (`api_secret_key`) is identical across every shop that installs the app, any merchant who installs the app receives real Shopify-signed webhooks with a valid `(raw_body, hmac)` pair for their own shop. That merchant (an otherwise unprivileged internet user, since app installation is self-service) can capture this legitimate `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` hands the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain, even though the actual signed body/topic never came from that shop.

### Impact Explanation
This breaks the tenant/shop identity binding that the HMAC is supposed to guarantee. Any app that uses the `shop` value from `WebhookMetadata` to select which merchant's data to mutate, delete, or overwrite (a documented and expected usage pattern of this gem, since `WebhookMetadata#shop` is explicitly provided by the library for that purpose) can be tricked into applying data belonging to the attacker's own shop payload under a victim shop's identity — i.e., cross-tenant data confusion/injection, including triggering shop-scoped operations (e.g. `customers/redact`, `shop/update`, `app/uninstalled`) against a shop the attacker does not control. This matches the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Likelihood is high for an app that has any public/self-serve installation flow: obtaining a valid `(raw_body, hmac)` pair only requires installing the app on a shop the attacker controls (no special privilege, no credential theft, no access to `api_secret_key`) and receiving one real webhook delivery. The attacker then only needs to alter one header field when POSTing to the exposed webhook endpoint.

### Recommendation
Include the shop domain (and other trust-relevant fields such as `topic`) as part of the value verified by the HMAC, or explicitly require callers to cross-check `request.shop` against the shop associated with the currently stored/active session before trusting it as a tenant key. At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are NOT covered by the HMAC and must be independently validated by the host app (e.g., against a known list of installed shops) before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (self-serve, requires no special privilege).
2. Shopify sends a legitimate webhook to the app's endpoint: body `B`, headers including `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's `api_secret_key`).
3. Attacker replays this exact request to the app's webhook endpoint, but with the header changed to `x-shopify-shop-domain: victim.myshopify.com` (body `B` and `hmac` header `H` unchanged).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only recomputes HMAC over `B`: [5](#0-4) 
5. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B`, and performs shop-scoped mutation/deletion as if it were an authentic webhook for `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
