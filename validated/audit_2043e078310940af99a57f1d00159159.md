### Title
User-centric signup path bypasses backend authoritative verification, allowing a client-influenced local `signup_reason` to fully determine signup success - (File: `src/plans/mod.rs`)

### Summary
The Golom finding shows that a check which only validates an *identity/consistency* condition (`o.reservedAddress == address(this)`), while leaving the actual *value being validated* (payment amount) unchecked against a trusted, independently-computed reference, lets an attacker define both sides of a "self-consistency" check and thereby bypass the protocol's real enforcement (fees). The orb-core analog is in `MasterPlan::do_signup`: when the backend-asserted `user_centric_signup` flag is set, the orb never calls the authoritative backend enrollment/verification round-trip (`enroll_user`, which POSTs to `signup_post::request` and polls `signup_poll` for the backend's actual verdict). Instead, `success` is derived purely from the orb-local `signup_reason`, which is computed from a pipeline that is enabled/disabled and interpretable by build-time/CLI flags reachable in engineering/staging configurations (`skip_pipeline`, `skip_fraud_checks`, `biometric_input`).

### Finding Description
In `src/plans/mod.rs`, `do_signup` computes `signup_reason` locally based on whether the biometric pipeline succeeded and whether `detect_fraud` flagged fraud: [1](#0-0) 

It then branches on `user_centric_signup` (a value read out of `backend::user_status::UserData`, itself derived from `orb_qr_link::UserData` returned by the backend and gated behind a hash-verification step): [2](#0-1) 

When `user_centric_signup` is true and `ignore_user_centric_signups` is false, the orb **skips** the call to `enroll_user` (the function that actually contacts the backend via `signup_post::request` and polls `signup_poll::request` for the authoritative outcome): [3](#0-2) [4](#0-3) 

Instead, success is set to `signup_reason == SignupReason::Normal`, i.e., an entirely orb-local determination that is never round-tripped through the backend's server-side signup verification/poll status. `detect_fraud` in this FOSS build is a stub that always returns `Ok(false)` regardless of pipeline content: [5](#0-4) 

This mirrors the Golom root cause exactly: the code performs a "self-consistency" check (local pipeline outcome) instead of validating the actual protected invariant against an independent, trusted authority (the backend's own accept/reject decision via `signup_poll`). Just as Golom's contract-level check validated that `reservedAddress == address(this)` without validating `o.totalAmt` against the real payment, orb-core validates that `signup_reason == Normal` (an orb-computed, locally-influenced value) without validating that outcome against the backend's actual enrollment decision when `user_centric_signup` is asserted.

### Impact Explanation
If an attacker can influence what feeds `signup_reason` (e.g., through `allow-plan-mods`/`skip_pipeline`/`skip_fraud_checks`/`biometric_input` build configurations reachable in engineering images, or through weaknesses in the biometric pipeline/fraud-detection stubs shown in `fraud_check.rs`, which explicitly has zero enabled checks: `const N_FRAUD_CHECKS: usize = 0;`), a signup can be marked `Success` on the orb and the Personal Custody Package (PCP) can be built/uploaded, all without the backend's authoritative `signup_poll` ever confirming that the signup passed its checks. This risks unauthorized/misattributed signup completion locally divergent from backend state — a state bleed between the orb's local decision and backend's real decision, matching the "unauthorized or misattributed signup" impact category.

### Likelihood Explanation
Exploitability is conditioned on the `user_centric_signup` flag being asserted for the session (which the backend controls and cryptographically ties into the QR data via `user_data.verify(user_data_hash)` in `src/backend/user_status.rs:175`), so a bare unprivileged attacker cannot set this flag arbitrarily by external tampering with the QR alone. However, the code path itself demonstrates the identical pattern flagged in the report: a security-relevant boolean determination (signup success) is computed and trusted locally instead of being verified against an authoritative backend/server round trip, exactly like Golom trusting `o.totalAmt` without independent verification.

### Recommendation
For `user_centric_signup` sessions, still perform (or introduce an equivalent) authoritative backend confirmation of the signup outcome rather than relying solely on the orb-local `signup_reason`, mirroring the mitigation applied in the referenced finding (cross-validate the locally-derived value against an independently trusted source) at `src/plans/mod.rs:639-656`.

### Proof of Concept
Not independently reproducible against production backend state without backend cooperation to set `user_centric_signup=true`; the finding is a code-path/logic analog rather than a demonstrated exploit, since the impact depends on backend-controlled flags and build-time feature gating (`allow-plan-mods`) not available to a bare unprivileged attacker in production builds. This should be treated as a design/logic concern rather than a confirmed unprivileged exploit.
