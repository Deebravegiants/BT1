### Title
Freezing `FrozenStatus.Incoming` blocks timeout dispatch and permanently strands in-flight request fees - ([File: evm/src/core/HandlerV2.sol])

### Summary
The `HandlerV2.notFrozen(host)` modifier is applied uniformly to `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`, reverting whenever the host's `FrozenStatus` is `Incoming` or `All`. This mirrors the exact mitigation-error pattern in the referenced report: a single "disable" flag is used to block both the delivery of new incoming messages *and* the recovery/refund path (timeouts), so pausing incoming traffic during an incident also freezes funds that are already in flight and waiting to time out.

### Finding Description
`notFrozen` is defined once and reused for every incoming-message handler: [1](#0-0) 

It gates `handlePostRequestTimeouts` and `handleGetRequestTimeouts` exactly the same way it gates the normal delivery paths (`handlePostRequests`, `handleGetResponses`): [2](#0-1) [3](#0-2) 

The EVM-side counterpart, `EvmHost`, defines the same coarse-grained `FrozenStatus` enum (`None`, `Incoming`, `Outgoing`, `All`) and a `FrozenHost` error, admin-controlled and reversible via `setFrozenState`: [4](#0-3) [5](#0-4) 

Once a request is dispatched, its fee is escrowed on the source host as `FeeMetadata` and released only through delivery-confirmation or timeout dispatch: [6](#0-5) 

`dispatchTimeOut` (called from `handlePostRequestTimeouts`/`handleGetRequestTimeouts`) is the only path that releases the escrowed fee back to the payer once a request has expired without delivery. Because that call is gated by the same `notFrozen(host)` modifier as ordinary incoming delivery, an admin freezing `Incoming` (e.g., in response to a security incident, exactly the scenario described in the referenced report for pausing Lido/frxETH staking) simultaneously disables the only refund mechanism for requests that expire during the freeze window. This is the same class of error identified in the external report: a disable/pause mechanism that is "too restrictive" because it does not distinguish between blocking new operations and blocking the wind-down/withdrawal path, so it "will not only disable deposits but also withdrawals, causing locked funds."

### Impact Explanation
Any POST or GET request dispatched before or during an `Incoming`/`All` freeze that reaches its `timeoutTimestamp` while the freeze is active cannot have its timeout proof processed. The escrowed relayer fee (and, for apps built on top such as the token bridge/intents relayer, the underlying transferred value awaiting a refund via `onPostRequestTimeout`) remains locked in the host/app contracts for the entire duration of the freeze, with no way to force settlement. If the freeze persists (e.g., pending governance action or an extended incident response), funds are frozen for an indefinite/attacker-uncontrollable period — a temporary but potentially open-ended freezing of funds belonging to unrelated, honest users who have no way to unlock their own pending transfers.

### Likelihood Explanation
The freeze is admin-gated (`restrict`/admin-only in `EvmHost`), so this is not attacker-triggerable on demand, but it is a legitimate operational action (freezing `Incoming` in response to a consensus fault or exploit is the intended purpose of `FrozenStatus`) that will occur under exactly the adversarial conditions where freezing is most needed and most likely to be held for longer periods. Any request whose timeout falls inside that window is affected — this is a systemic design property, not a rare edge case, so likelihood of occurrence during any real freeze event is high.

### Recommendation
Decouple the "refund/timeout" path from the general incoming-delivery block. `handlePostRequestTimeouts` and `handleGetRequestTimeouts` should not be gated by `FrozenStatus.Incoming`/`All` (or should use a distinct status, e.g. one that keeps timeout processing open even while message delivery is halted), so that pausing new message intake never blocks users from reclaiming fees/funds on already-expired requests — mirroring the referenced recommendation that pause mechanisms must still allow withdrawal/refund of already-committed funds.

### Proof of Concept
1. Admin (or host manager, per governance) calls `EvmHost.setFrozenState(FrozenStatus.Incoming)` in response to an incident.
2. Prior to the freeze, a user dispatched a `PostRequest` via `EvmHost.dispatch`, escrowing a fee (`FeeMetadata`) as shown in `testFundRequest` in `evm/tests/foundry/EvmHostTest.sol`.
3. The request's `timeoutTimestamp` elapses while the host remains frozen.
4. A relayer attempts `HandlerV2.handlePostRequestTimeouts(host, message)` to trigger `dispatchTimeOut` and refund the payer — the call reverts with `HostFrozen()` due to the `notFrozen(host)` modifier.
5. The escrowed fee (and any app-level funds pending refund through `onPostRequestTimeout`, e.g. in `WrappedHyperFungibleToken`) stays locked until the admin manually unfreezes the host, with no way for the affected user to reclaim funds in the interim.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
