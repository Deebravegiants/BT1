### Title
Session-token audience confusion in `TokenExchange.exchange_token` allows non-admin JWTs to mint admin access tokens - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` accepts any JWT that decodes successfully under `ShopifyAPI::Auth::JwtPayload` and unconditionally uses its `dest` claim as the shop to exchange for an admin access token. `JwtPayload` only validates the signature and the `aud` claim (must equal `Context.api_key`); it does not require the `iss` claim to indicate an admin session context. A separate helper, `admin_session_token?` (`iss.end_with?("/admin")`), exists in the same class but is only used to gate `shopify_user_id` — it is never enforced in `exchange_token`.

### Finding Description
`JwtPayload#initialize` (`lib/shopify_api/auth/jwt_payload.rb:23-45`) decodes the token with the app's `api_secret_key` and checks only:
```ruby
raise ShopifyAPI::Errors::InvalidJwtTokenError,
  "Session token had invalid API key" unless @aud == Context.api_key
``` [1](#0-0) 

Any Shopify-issued token signed for the same app (`aud == api_key`) but scoped to a different, non-admin context (e.g. a Checkout UI Extension session token — explicitly supported per CHANGELOG entry "Make `sub` and `sid` jwt claims optional (Checkout ui extension support)") will pass this check even though its `iss` does not end in `/admin`. [2](#0-1) 

The library already has a way to distinguish admin vs. non-admin tokens — `admin_session_token?` — but it is private and only consulted by `shopify_user_id`:
```ruby
def shopify_user_id
  @sub.to_i if user_id_sub? && admin_session_token?
end
...
def admin_session_token?
  @iss.end_with?("/admin")
end
``` [3](#0-2) 

`TokenExchange.exchange_token` does not call `admin_session_token?` (or check `iss` in any way) before treating the token's `dest` as an authoritative admin shop identifier and exchanging it for a full admin access token:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = {
  client_id: ShopifyAPI::Context.api_key,
  client_secret: ShopifyAPI::Context.api_secret_key,
  grant_type: TOKEN_EXCHANGE_GRANT_TYPE,
  subject_token: session_token,
  subject_token_type: ID_TOKEN_TYPE,
  requested_token_type: requested_token_type.serialize,
}
``` [4](#0-3) 

This breaks the identity binding: `iss` (the JWT's declared audience/context, e.g. Admin embedded app vs. Checkout extension) is never verified to equal the expected value ("admin session") before the token is trusted and forwarded to Shopify's token-exchange endpoint as `subject_token` with `subject_token_type: id_token`. In other words, `JWT claim consumed (dest) != JWT claim verified (only aud)`.

### Impact Explanation
If Shopify's own token-exchange endpoint does not itself reject non-admin-context id_tokens as `subject_token` (which the gem's own comment/test around `invalid_subject_token` suggests is at least a possible outcome, not a guaranteed one), a caller who only possesses a valid non-admin (e.g., checkout extension) session token for a shop could use this library's `exchange_token` to request a legitimate offline/online **admin** access token for that shop — a scope/context escalation and potential cross-context credential theft, without ever holding an actual admin session token. This is categorized as a scope/expiry check bypass at the library layer: the gem fails to enforce the audience/context binding it already has code to check (`admin_session_token?`) before trusting the token for a highly privileged operation.

### Likelihood Explanation
Exploitability from an "unprivileged internet user" is conditional on obtaining a valid checkout/extension-context id_token for the target shop and on Shopify's remote endpoint not independently rejecting the token type — this part cannot be verified from the gem's code alone since the request goes to Shopify's `/admin/oauth/access_token` endpoint (out of scope for this repo). Within the scope of this gem, however, the missing local validation is a concrete root-cause defect: the library trusts `dest`/`iss` context without validation, unlike its sibling flows (`client_credentials.rb` and `refresh_token.rb`), which both call `Utils::ShopValidator.sanitize!(shop)` on caller-supplied input, while `token_exchange.rb` performs no equivalent binding check on the JWT's own context claim.

### Recommendation
In `TokenExchange.exchange_token`, before using `jwt_payload.shop`/`dest_shop`, require that the token asserts an admin session context, e.g.:
```ruby
raise ShopifyAPI::Errors::InvalidJwtTokenError, "Session token is not an admin session token" unless jwt_payload.send(:admin_session_token?)
```
or expose and enforce a public `admin_session_token?` predicate, so that only tokens whose `iss` matches the admin context can be exchanged for admin access tokens.

### Proof of Concept
1. Attacker/customer obtains a valid Shopify-issued id_token for the target shop's Checkout UI Extension (signed with the same app secret, `aud == api_key`, but `iss` not ending in `/admin`).
2. Attacker calls `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: checkout_token, requested_token_type: RequestedTokenType::OFFLINE_ACCESS_TOKEN)`.
3. `JwtPayload.new(checkout_token)` succeeds because only `aud` is checked [1](#0-0) .
4. `dest_shop` is taken from the token and used to build the token-exchange request without any admin-context check [5](#0-4) .
5. If Shopify's backend accepts the subject_token, the gem returns a full admin `ShopifyAPI::Auth::Session` to the caller — an escalation from a non-admin, customer-facing token to an admin access token.

Note: step 5's success depends on Shopify's server-side behavior, which is outside this gem's code and could not be verified here; the finding is scoped to the missing local `iss`/audience-context validation in this library.
