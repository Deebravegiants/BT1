### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id` headers) is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" (per `docs/usage/webhooks.md`), but the HMAC check only authenticates the raw request body. The `shop-domain`, `topic`, and `webhook-id` headers — which are the fields the handler actually acts on to identify the tenant and dispatch logic — are never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are parsed directly from headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC over that signable string (i.e., the body) and then constructs `WebhookMetadata` directly from the unauthenticated header values, passing it to the app's handler as trusted tenant/topic identity: [1](#0-0) 

The equality this breaks is: *bytes verified by HMAC (`raw_body`) ≠ bytes the handler treats as the authenticated tenant/topic (`shop-domain` / `topic` / `webhook-id` headers)*. A merchant who has legitimately installed the app receives genuine Shopify-signed webhook deliveries for their own shop (topic, headers, `hmac-sha256`, raw body) without ever needing the app's `client_secret`. Because the signature covers only the body bytes, that same unprivileged tenant can resend the identical body and HMAC to the app's webhook endpoint while substituting a different `shop-domain` (and/or `topic`/`webhook-id`) header. `HmacValidator.validate` will still pass, since it recomputes the HMAC over `raw_body` alone and never checks the headers: [4](#0-3) 

The gem then hands the forged `shop` value to the app's handler as if Shopify had certified it for that shop, achieving cross-tenant impersonation entirely from data the attacker already legitimately possesses as any one installed merchant — no secret, token, or privileged access required.

### Impact Explanation
This lets one tenant (any merchant with the app installed) impersonate webhook traffic as belonging to a different shop, since the `shop` identity delivered to the handler is unauthenticated relative to the signature. Any host application that uses `WebhookMetadata#shop` to key session/data lookups (the intended and documented usage pattern of this field) can be made to process data under the wrong tenant's identity — a cross-tenant access condition, matching the High-impact bucket ("cross-tenant access").

### Likelihood Explanation
Likelihood is realistic: the only prerequisite is having received one legitimate webhook as an installed merchant (a completely unprivileged position relative to other tenants), and replaying it with a modified header value using any HTTP client. No credential, token, or `api_secret_key` is needed.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the signable string that the HMAC covers (or otherwise cryptographically bind them to the signed payload), so that `HmacValidator.validate` fails if any of these identity-bearing headers are altered relative to what Shopify actually signed.

### Proof of Concept
1. App has two shops installed: `shop-a.myshopify.com` and `shop-b.myshopify.com`.
2. As the merchant/operator of `shop-a`, capture a genuine webhook delivery Shopify sends to the app's endpoint: headers `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid-hmac>`, `shopify-shop-domain: shop-a.myshopify.com`, plus the raw JSON body.
3. Resend the exact same raw body and `shopify-hmac-sha256` value to the app's webhook endpoint, but replace `shopify-shop-domain` with `shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches the untouched signature — validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "shop-b.myshopify.com"`, even though Shopify never signed anything asserting this body belongs to `shop-b`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
