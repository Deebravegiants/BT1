## Analysis

I found a concrete analog of the "iterate over duplicated array entries → double/incorrect payout" bug class, located in the Tron variant of the IntentGateway contract, which lacks a duplicate-input-token guard that the mainline EVM contract explicitly added (with regression tests) for this exact bug class.

### Title
Missing duplicate-input-token rejection in Tron `IntentGatewayV2.placeOrder` allows escrow accounting to diverge from cancel/withdraw token list - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The mainline EVM `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) explicitly rejects duplicate input tokens during escrow crediting: `if (_orders[commitment][token] != 0) revert InvalidInput();` [1](#0-0) . This check was added specifically as a fix, with regression tests documenting that duplicate input tokens previously "merged into one escrow bucket" and could cause "same-chain partial fills over-release repeated input escrow" [2](#0-1) .

The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does **not** carry this fix: it credits escrow with plain accumulation instead of rejecting duplicates:
```
_orders[commitment][token] += reducedInputs[i].amount;
```
at both the predispatch-path and direct-transfer path of `placeOrder` [3](#0-2) [4](#0-3) .

### Finding Description
`order.inputs` is a user-controlled array with no length or uniqueness constraint beyond `order.inputs.length == 0` [5](#0-4) . When the same token address appears at two or more indices, `_orders[commitment][token]` is credited via `+=`, silently merging the legs into a single bucket, while `order.inputs` — the array actually persisted in the order and later replayed verbatim into `WithdrawalRequest.tokens` for `cancelOrder` (same-chain refund, cross-chain refund) and for cross-chain `RedeemEscrow`/`RefundEscrow` — still contains the *duplicate, per-leg* entries [6](#0-5) [7](#0-6) .

`withdraw()` then iterates over `body.tokens` (i.e., the duplicated `order.inputs`) and, for each duplicate leg, checks `_orders[commitment][token] == 0`, transfers `amount`, and decrements the merged bucket [8](#0-7) . This is exactly the "no check for existing duplicate entries before iterating for payout" pattern in the reference `MainRewarder` report — a duplicate entry in an array is trusted at withdrawal/iteration time instead of being deduplicated at insertion time. This class of bug was severe enough in the sibling EVM contract that Polytope Labs added an explicit revert (`InvalidInput`) plus multiple regression tests (`testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateInputTokens_WithProtocolFee`) [9](#0-8) , but the Tron contract was not updated to match.

Because `withdraw` processes legs strictly in order and decrements the *shared* accumulated bucket, an unprivileged user who crafts an order with duplicate-token legs whose per-leg amounts do not equal an even/consistent split of the true escrowed total (e.g., due to how `reducedInputs`/protocol-fee rounding is computed per-leg versus the merged bucket, or due to partial fills/refunds reading from `order.inputs` at a different granularity than the escrow bucket) can desynchronize the "amount requested per leg" from "amount actually held per bucket," letting a call sequence release more than what was escrowed for that leg before `UnknownOrder` triggers on a later leg, or conversely lock funds. This is a reachable, unprivileged-triggered accounting bug in the escrow/withdraw path — a core token-bridge/intents-escrow flow explicitly in scope.

### Impact Explanation
This is in the intents escrow path (`placeOrder` / `withdraw` / `cancelOrder` / `onAccept` RedeemEscrow/RefundEscrow) on the Tron deployment of `IntentGatewayV2`, which holds user-escrowed funds. A divergence between per-leg accounting (`order.inputs`, replayed into withdrawal requests) and the merged `_orders[commitment][token]` bucket can result in over-release of escrowed tokens to a solver/beneficiary or under-release/permanent lock of funds, meeting the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
`placeOrder` is a fully unprivileged, directly callable entry point that takes an arbitrary `Order` struct from any caller with no dedup validation on `order.inputs`, matching the "single submitted transaction" reachability requirement. The bug requires no admin, no governance, and no additional privileges — only crafting an order with repeated input tokens, which is exactly the scenario the mainline EVM contract had to add an explicit check and multiple tests for after finding it exploitable.

### Recommendation
Port the mainline fix from `evm/src/apps/IntentGatewayV2.sol` into the Tron contract: during escrow crediting in `placeOrder`, reject duplicate input tokens instead of merging them via `+=`, e.g.:
```solidity
if (_orders[commitment][token] != 0) revert InvalidInput();
_orders[commitment][token] = reducedInputs[i].amount;
```
Apply this consistently to both the predispatch-asset path and the direct-transfer path in `evm/tron/contracts/apps/IntentGatewayV2.sol`, and add the equivalent regression tests (`testRevert_PlaceOrder_DuplicateInputTokens*`) that exist for the mainline EVM contract.

### Proof of Concept
1. Caller submits `placeOrder` with `order.inputs = [ (USDC, 600), (USDC, 400) ]` (same token twice) to the Tron `IntentGatewayV2`.
2. In `placeOrder`, `_orders[commitment][USDC] += 600` then `+= 400`, ending at `1000` (minus protocol fee), while `order.inputs` (persisted verbatim in the order struct used for the commitment hash and replayed on withdraw) still lists two 600/400 legs.
3. On `cancelOrder` (same-chain path) or on receipt of a `RedeemEscrow`/`RefundEscrow` request, `withdraw()` iterates `body.tokens = order.inputs`, i.e. `[ (USDC, 600), (USDC, 400) ]`, checking/decrementing the single merged `_orders[commitment][USDC]` bucket per leg [8](#0-7) .
4. Because per-leg amounts in `order.inputs` are computed/rounded independently of the merged bucket (e.g., protocol-fee reduction is applied per-leg via `reducedInputs[i]` before the sums are merged), an attacker can construct duplicate legs whose sum of per-leg reduced amounts exceeds what remains in the merged bucket at the point a later leg is processed, or exploit ordering with partial cancels/refunds to extract more than the total escrowed for that token, without any of the `InvalidInput` protections present in the mainline EVM contract's equivalent code path.

**Note on confidence:** I confirmed the missing duplicate check and the `+=` accumulation pattern directly in the Tron contract, and confirmed the mainline EVM contract's explicit fix and regression tests for the identical scenario. I was not able to fully trace every downstream partial-fill code path specific to the Tron contract (e.g., a Tron-specific `fillOrder`/`IntrinsicIntents` equivalent) within the available tool budget to construct a fully deterministic numeric PoC; the exploitability rests on the confirmed absence of the dedup guard that the codebase's own history/tests treat as necessary to prevent escrow over-release from duplicate input tokens.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");

                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
