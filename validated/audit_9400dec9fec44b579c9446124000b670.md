### Title
Stale `account.owner` lets the previous NFT owner (or their delegate) keep acting on a transferred position via `multiply`/`migrate_from_blend` — (contracts/controller/src/account.rs)

### Summary
`Account.owner` is written once at NFT mint (`create_account_with`) and is what `require_owner_or_delegate` authenticates against. A separate helper, `require_account_owner`, checks `storage::account_owner` — the live NFT owner. Because `multiply` and `migrate_from_blend` gate their existing-account path through `load_or_create_account` with `AccountGuard::Multiply`/`Migrate` (i.e., `require_owner_or_delegate` on the stored `account.owner`), a seller who transfers the position NFT to a victim retains operative authority over the victim's account: `caller == account.owner` still matches the attacker's recorded address, and any delegate the attacker granted while owning the account remains valid under the stale owner key. This mirrors CVE-2022-1497's class — attacker-crafted input presented with the identity/authority of a trusted source — by letting a stale ownership record masquerade as current authorization.

### Finding Description
- `create_account_with` stores `Account { owner: owner.clone(), .. }` at mint time (`contracts/controller/src/account.rs:62-70`). There is no NFT-transfer hook in the controller that rewrites `Account.owner` — Soroban NFT transfers cannot notify the controller.
- `require_owner_or_delegate` (and `is_owner_or_delegate`) compare `caller` to the passed `account.owner` and consult `get_delegates(env, account_id, owner)` keyed on that same stale owner (`account.rs:114-140`).
- `require_account_owner` instead reads `storage::account_owner(env, account_id)` — the live NFT owner — and is used by `renew_account`, `add_delegate`, `remove_delegate` (`account.rs:142-148, 217-225`). The coexistence of two different ownership sources shows the stored field is not authoritative.
- `load_or_create_account` applies `AccountGuard::Migrate` and `AccountGuard::Multiply` via `require_owner_or_delegate(env, account_id, caller, &account.owner)` (`account.rs:99-109`). These guards back `migrate_from_blend` (`contracts/controller/src/strategies/migrate_blend.rs:63-71`) and `multiply`.
- Result: after `position-nft` `transfer`/`approve` moves the NFT to a new owner, the previous owner (or a delegate they granted, if it is a registered active manager) can still invoke `multiply`/`migrate_from_blend` on that `account_id`.

### Impact Explanation
An attacker sells/transfers a position NFT to a victim, then uses retained stale-owner authority (or a pre-granted delegate manager) to call `multiply` or `migrate_from_blend` on the victim's `account_id`. `multiply` mints debt onto the victim's account and routes the borrowed funds through attacker-chosen, unallowlisted swap venues with balance-delta output measurement, so the attacker can sandwich/self-deal the swap and return minimal collateral — worsening the victim's health factor toward liquidation and extracting value, or deliberately pushing the account under water. `migrate_from_blend` likewise borrows `debt_caps` amounts onto the victim's account before `strategy_finalize` risk checks, letting the attacker impose leverage the victim never authorized. This is theft of user funds (value extracted via the swap leg and subsequent liquidation) and unauthorized debt creation — a spoofed-ownership authority path reachable by an unprivileged address.

### Likelihood Explanation
Reachable by any account holder: grant an active manager as delegate (or simply remain the recorded owner), transfer the NFT via the position-nft `transfer` entrypoint (explicitly in scope), then call `controller.multiply`/`migrate_from_blend` with the same `account_id`. No privileged role, upgrade, or off-chain dependency is needed; the only precondition is that the target account's spoke/mode match, which the attacker set at creation. Uncertainty: this analysis assumes `storage::account_owner` reflects the live NFT owner and that `Account.owner` is not resynced on transfer; the position-nft transfer implementation was not fully inspected in this pass, but the two distinct owner lookups in `account.rs` strongly indicate the stored field is stale after a transfer.

### Recommendation
Derive authority only from the live NFT owner. In `require_owner_or_delegate`/`is_owner_or_delegate`, replace the stored `account.owner` with `storage::account_owner(env, account_id)` (or drop `Account.owner` entirely and thread the verified owner through). Key delegate grants under the live owner, and clear delegate entries on NFT transfer — e.g., have the position-nft contract call a controller `on_transfer(account_id, old_owner)` hook that updates `Account.owner` and wipes `delegates(account_id, old_owner)`, or treat delegates as invalid unless `delegates(account_id, live_owner)` contains the caller.

### Proof of Concept
1. Attacker calls `controller.supply` (or `multiply` with `account_id = 0`) to create `account_id = A` in spoke `S`, mode `Multiply`, and supplies collateral `C`.
2. Attacker calls `add_delegate(caller=attacker, account_id=A, delegate=M)` where `M` is a registered active position manager the attacker controls (`account.rs:229-232`).
3. Attacker calls `position_nft.transfer(attacker → victim, A)`. The NFT now shows `victim` as owner; `Account.owner` in controller storage remains `attacker`.
4. Attacker (as `M`, or directly as the stale `account.owner`) calls `controller.multiply(caller, account_id=A, spoke_id=S, mode=Multiply, ...)` with `debt_caps`/route pointing at attacker-controlled venue liquidity. `load_or_create_account` passes `AccountGuard::Multiply`: `require_owner_or_delegate` succeeds on the stale `account.owner`/`delegates(A, attacker)` record (`account.rs:105-109, 124-127`).
5. The strategy mints debt on `A`, swaps through the attacker's route at manipulated prices, deposits the diminished collateral back on `A`, and passes `strategy_finalize` checks with a degraded health factor.
6. The attacker liquidates `A` via `controller.liquidate` once HF < 1, claiming the HF-based bonus; residual value of the victim's purchased position is extracted through the swap spread and liquidation bonus.
