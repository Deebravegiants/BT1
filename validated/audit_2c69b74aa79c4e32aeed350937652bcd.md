### Title
Unbounded Ancestry Traversal Before Signature Verification Enables Infinite-Loop DoS in GRANDPA Consensus Message Handling - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry()` walks backwards from an attacker-supplied target header to a base header by repeatedly following `parent_hash` pointers taken from headers submitted in the same untrusted proof (`finality_proof.unknown_headers` / `votes_ancestries`). There is no cycle detection and no bound on the number of hops, analogous to the reported ImageMagick bug class where `DestroyXMLTree()` recursed over an attacker-controlled tree with no depth limit, exhausting the stack. Here the attacker-controlled graph can be crafted with a cycle so the `while current_hash != base` loop never terminates, exhausting CPU instead of stack, and — critically — this traversal runs **before** the justification signatures are cryptographically verified.

### Finding Description
`GrandpaJustification::verify_with_voter_set` and `verify_grandpa_finality_proof` both call `AncestryChain::ancestry(base, block)`: [1](#0-0) 

```
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is a `BTreeMap<Hash, Header>` built directly from the caller-supplied `unknown_headers`/`votes_ancestries` list: [2](#0-1) 

Each `Header`'s `parent_hash` field is an arbitrary attacker-chosen value (headers here are *unverified* — that is the whole reason `unknown_headers` exists: to let the light client reconstruct ancestry it hasn't seen). Nothing checks that `header.hash()` is consistent with `header.parent_hash` of its "child," nor that the parent-hash chain is acyclic. An attacker can submit two or more headers `A`, `B` in `unknown_headers` where `A.parent_hash == hash(B)` and `B.parent_hash == hash(A)`, forming a cycle that never resolves to `base`. Because both `current_hash` values remain keys in `self.ancestry`, the lookup always succeeds and the loop runs forever.

The exploitable order-of-operations is in `verify_grandpa_finality_proof`: [3](#0-2) 

`headers.ancestry(from, target.hash())` (line 88) executes **before** `justification.verify(...)` (line 91-93). This means the unbounded/cyclic traversal is reached without any valid GRANDPA signature — an attacker only needs a syntactically well-formed, SCALE-decodable `FinalityProof`/`GrandpaJustification` with a crafted cyclic `unknown_headers`/`votes_ancestries` set.

The same unguarded `ancestry()` call is also used in the fraud-proof path: [4](#0-3) 

### Impact Explanation
This is reachable from a single relayed consensus message (an unsigned/permissionless dispatch that decodes and verifies a GRANDPA consensus proof for a Hyperbridge `EvmHost`/pallet-ismp GRANDPA consensus client). A crafted cyclic ancestry graph causes the verifier to enter an unbounded loop, hanging the thread/block executor processing that message. Because Substrate `on_initialize`/dispatchable execution is not preemptible per-instruction in the way EVM gas metering is, an infinite loop inside consensus-client verification stalls block production/import for the node executing it — a genuine denial-of-service of the message-delivery/consensus-update route, matching the "route unable to deliver messages" acceptance criterion. This is High severity: it can be triggered by any unprivileged relayer submitting a single malformed proof, requires no valid signatures, and can hang collator/validator execution.

### Likelihood Explanation
Likelihood is high: the attacker fully controls the contents of `unknown_headers`/`votes_ancestries` (they are SCALE-decoded structs whose `parent_hash` field is not tied to any external validity check at this stage), and the vulnerable traversal executes before signature verification, so no honest authority cooperation or valid signature is required to reach it.

### Recommendation
Bound `AncestryChain::ancestry` by the number of headers available (`self.ancestry.len() + 1`) and fail with `NotDescendent`/a dedicated error once that many hops have been taken without reaching `base`, exactly as `spv.rs`'s `MAX_PROOF_DEPTH` guards the Pharos trie-walk. Track visited hashes and fail immediately on cycle detection. Additionally, consider moving cryptographic/signature verification ahead of any ancestry traversal so untrusted structural data cannot be walked before it is authenticated.

### Proof of Concept
1. Build two dummy headers `A` and `B` (e.g., `Header::new(...)`) such that `A.parent_hash = B.hash()` and `B.parent_hash = A.hash()` (attacker can always achieve this since header contents besides `parent_hash` are free-form, and `hash()` is computed independently of `parent_hash`, so a fixed-point pair can be constructed by solving for either value or by brute-forcing/hash-grinding one field, similar in spirit to how `test_ancestry_route` in the existing test suite constructs linked headers): [5](#0-4) 
2. Set `unknown_headers = [A, B]`, with `target = max_by_key(number) = A` (or `B`) and craft a `GrandpaJustification` whose `commit.target_hash == A.hash()` (decoding succeeds; content need not be a *valid* signed commit because `ancestry()` runs before `justification.verify()`).
3. Submit this as a `FinalityProof` via the GRANDPA consensus-client message handling entry point (`verify_grandpa_finality_proof` in `modules/consensus/grandpa/verifier/src/lib.rs`, reached from `modules/ismp/clients/grandpa/src/consensus.rs`).
4. `headers.ancestry(from, target.hash())` at line 88 of `verifier/src/lib.rs` enters the `A → B → A → B → …` cycle indefinitely, hanging execution of the message-processing call.

Note: I was not able to fully trace the exact top-level pallet extrinsic (e.g., `pallet_ismp::Call::handle_unsigned` vs. a signed relayer call) that ultimately invokes `verify_grandpa_finality_proof` due to running out of investigation budget before completing that trace — the grep for `execute`/`handle_unsigned` in `modules/ismp/**` did not resolve before the session ended. This should be confirmed by a follow-up session to establish precisely which dispatch path (signed vs. unsigned, fee-bearing vs. free) delivers the crafted `ConsensusMessage` to this verifier, which affects the precise cost/likelihood calculus for an attacker.
