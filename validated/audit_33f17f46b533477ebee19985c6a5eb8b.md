Confirmed: `sendToRelay` in `Transferer.sol` performs an unconditional token transfer to `relay` with no check that `erc20TokenAddress` belongs to `circomData.erc20TokenAddresses`, and `feeStructure.feeToken` is never validated to be a member of that array anywhere in `HinkalHelper.performHinkalChecks`, `dimensionsCheck`, or `checkOnchainCreation`.### Title
Attacker-controlled `feeStructure.feeToken` in `ExternalActionSwap.swap` drains any stranded token balance not part of `circomData.erc20TokenAddresses` to attacker-controlled relay - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`ExternalActionSwap.swap` calls `sendToRelay(circomData.relay, relayFee, circomData.feeStructure.feeToken)` for the non-output-token branch, where `feeStructure.feeToken` is a fully attacker-controlled field with no on-chain or circuit constraint tying it to `circomData.erc20TokenAddresses`. Because `Hinkal.transact`'s balance-conservation loop only iterates `circomData.erc20TokenAddresses` [1](#0-0) , any token moved outside that array (i.e. `feeToken` when it differs from both `inputToken` and `outputToken`) is never checked against `balanceDif`, letting the attacker exfiltrate stranded balances of arbitrary tokens the `ExternalActionSwap` contract happens to hold.

### Finding Description
The claimed equality: for every token `t` transferred out of `ExternalActionSwap` during a `swap` call, `t` must be an element of `circomData.erc20TokenAddresses` so that `Hinkal.transact`'s balance-difference loop [1](#0-0)  can verify `balanceDif == amountChanges[i] + utxoAmount` for it. This equality is broken because:

1. `swap` sets `inputToken = circomData.erc20TokenAddresses[0]` and `outputToken = circomData.erc20TokenAddresses[1]` [2](#0-1) , but `circomData.feeStructure.feeToken` is never required to equal either of these.
2. When `feeToken != outputToken`, the code executes `sendToRelay(circomData.relay, relayFee, circomData.feeStructure.feeToken)` [3](#0-2) , which unconditionally transfers `relayFee` of `feeToken` to `relay` via `Transferer.sendToRelay` — a raw balance transfer with no membership check against `erc20TokenAddresses` [4](#0-3) .
3. Nothing in `HinkalHelper.performHinkalChecks`, `dimensionsCheck`, or `checkOnchainCreation` requires `feeStructure.feeToken` to be a member of `erc20TokenAddresses` [5](#0-4) [6](#0-5) . `feeStructure` is only bound by a keccak hash integrity check (`getHashedCalldata2`) [7](#0-6)  that merely proves the attacker's own submitted value is unmodified in transit — since the attacker generates their own proof, they can set `feeToken` to any address they want.
4. `Hinkal.transact`'s post-call balance check only scans `circomData.erc20TokenAddresses` (length 2 for a swap) [1](#0-0) , so a balance decrease in a third token `feeToken` (not in that array) is invisible to `balanceDif`/`amountChanges` reconciliation entirely.

Exploit flow: attacker crafts `circomData` for a swap with `erc20TokenAddresses = [inputToken, outputToken]`, `feeStructure.feeToken = <thirdToken>` (a token `ExternalActionSwap` holds a stray balance of), `feeStructure.flatFee = <amount they want to steal>`, and sets `circomData.relay` to an address they control (self-relay, satisfying `relayerIsValid` if they are a whitelisted relay, or via a colluding/self-deployed relay if the whitelist allows it). Since they generate the proof for their own UTXOs, all circuit constraints (`inTotal + amountChanges === outTotal`, hash checks) are satisfiable — `feeToken` is not meaningfully constrained by the circuit beyond being included in the calldata hash the attacker itself controls. On execution, `swap` calls `sendToRelay(relay, flatFee, thirdToken)`, draining `thirdToken` balance to the attacker's `relay`, while `Hinkal.transact`'s loop over `[inputToken, outputToken]` sees no discrepancy for either token and passes.

### Impact Explanation
This allows theft of protocol- or other-users'-stranded token balances held by `ExternalActionSwap`, undetected by Hinkal's balance-conservation loop, matching **High** severity ("theft ... of protocol/relay fees" / assets a wallet owner never authorized) rather than direct theft of actively-held shielded user funds in the current transaction's accounted tokens — the stolen value is limited to whatever balance of an out-of-scope token happens to be stranded in the contract (from a prior bug or external deposit). It is repeatable for as long as any stray balance remains, and each call can drain up to the full stray balance (bounded by `flatFee`/`variableRate` chosen by the attacker, but attacker can set `flatFee` arbitrarily high up to the balance since there is no check that `flatFee` is reasonable relative to swap size for the `feeToken` branch).

### Likelihood Explanation
Requires (a) a stray/stranded balance of some token in `ExternalActionSwap` unrelated to the current call's `erc20TokenAddresses` — this is an external precondition (e.g., a separate freezing bug, airdrop, or accidental send) not something this finding alone creates; (b) the attacker being able to set `circomData.relay` to an address they control, which requires passing `relayerIsValid` (`tx.origin == relay` and `isRelayInList(relay)`) [8](#0-7)  — i.e., the attacker must be (or control) a whitelisted relay, which is a nontrivial precondition not guaranteed for an arbitrary unprivileged EOA. Given the stated preconditions in the question (stranded balance exists, attacker controls `relay`), the exploit itself is straightforward and cheap (one `transact` call, own proof, no special access beyond relay whitelisting).

### Recommendation
Require `circomData.feeStructure.feeToken` to equal one of `circomData.erc20TokenAddresses` (specifically `inputToken` or `outputToken` for swaps), enforced either in `HinkalHelper.dimensionsCheck`/`performHinkalChecks` or directly in `ExternalActionSwap.swap`, e.g. `require(feeToken == inputToken || feeToken == outputToken, "invalid fee token")`. Additionally, extend `Hinkal.transact`'s balance-conservation check to also verify that no token outside `erc20TokenAddresses` had its balance decreased during the external action call (e.g., by snapshotting balances of any token touched by `sendToRelay`/`transferERC20TokenOrETH`, or by restricting `sendToRelay` calls in external actions to only tokens within the declared array).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `ExternalActionSwap` (with a mock router), and three ERC20 tokens: `tokenA` (input), `tokenB` (output), `tokenC` (unrelated/stray).
2. Airdrop/seed `tokenC` balance directly into `ExternalActionSwap` (simulating stranded funds), e.g. `tokenC.mint(address(externalActionSwap), 1000e18)`.
3. Whitelist an attacker-controlled address as `relay` via the relay-store setup (or use existing test relay infra), and have the attacker submit the transaction with `tx.origin == relay`.
4. Construct `circomData` with `erc20TokenAddresses = [tokenA, tokenB]`, `feeStructure = {feeToken: tokenC, flatFee: 1000e18, variableRate: 0}`, valid nullifiers/roots/proof for a real swap of `tokenA -> tokenB`, and `relay = attackerRelay`.
5. Call `Hinkal.transact(...)`.
6. Assert: `tokenC.balanceOf(attackerRelay) == 1000e18` (full stray balance drained) while `balanceDif` checks for `tokenA` and `tokenB` in `Hinkal.transact` pass (`balanceDif[0] == amountChanges[0] + utxoAmount[0]` and `balanceDif[1] == amountChanges[1] + utxoAmount[1]` both hold), proving the loss of `tokenC` was never checked because `tokenC ∉ circomData.erc20TokenAddresses`.
