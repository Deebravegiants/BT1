### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is trusted from an HTTP header that is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over `Request#to_signable_string`, which returns only the raw request body [1](#0-0) . However, the `shop` identity that the handler uses to attribute the webhook to a tenant is read straight from the `shopify-shop-domain` HTTP header, never included in the signed material [2](#0-1) . `Registry.process` validates the HMAC and then dispatches to the handler passing `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`, all header-derived) as trusted metadata [3](#0-2) .

### Finding Description
The binding that should hold is: `bytes verified by HMAC == bytes the app acts on for tenant attribution`. In this gem that equality is broken:
- Signed bytes: `@raw_body` only [1](#0-0) .
- Bytes acted on for tenant identity: the `shopify-shop-domain`/`x-shopify-shop-domain` header, read via `shopify_header("shop-domain")` [2](#0-1) [4](#0-3) .

`Utils::HmacValidator.validate` only checks that `hmac` matches `HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)` [5](#0-4) . Nothing in that computation binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers to the signature. As documented, the resulting `WebhookMetadata.shop` is exactly what downstream apps use to route/attribute the webhook to a specific merchant record (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) .

However, exploiting this requires an attacker to already possess a `(raw_body, hmac)` pair that is valid for the app's shared `client_secret` — i.e., a genuine webhook delivery that Shopify actually sent for some shop signed with the app's secret. Since the HMAC secret is the app's `client_secret`, shared across all shops installed on that app (not shop-specific), an attacker who can intercept or replay one legitimate webhook delivery (e.g., one delivered to a shop they control) could resend the same `raw_body`/`hmac` to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. Because `to_signable_string` never includes the shop header, the HMAC check still passes, and the handler will process the webhook attributing it to the attacker-chosen `shop`.

### Impact Explanation
This can cause cross-tenant data confusion: an app relying on `WebhookMetadata.shop` (as the shipped documentation instructs) to select the tenant's stored session/access token or write to tenant-scoped records could have webhook data attributed to, or trigger actions for, a shop the attacker does not own. This matches the "Critical - cross-tenant access" impact category since the attacker can force webhook processing to be misattributed to an arbitrary target shop domain.

### Likelihood Explanation
Likelihood is constrained: the attacker must first obtain at least one legitimately-signed `(raw_body, hmac)` pair for the target app (e.g., by installing the app on their own store and capturing a real webhook delivery, since HMAC secret is shared per-app not per-shop). Given that, replay against the same endpoint with a forged `shop-domain` header is straightforward and requires no cryptographic secret knowledge. This is a real gap in the gem's `Request`/`HmacValidator` design regardless of how likely a specific host app is to trust `data.shop` without independent verification.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the signed material verified by `HmacValidator`, or otherwise cross-check the header-derived shop against a known/expected registration before dispatching to the handler. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should not silently allow header fields used for tenant attribution to be excluded from the HMAC-covered bytes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, triggers a webhook (e.g. `orders/create`), and captures the raw POST: body `raw_body`, header `shopify-hmac-sha256: <hmac>`, header `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical `raw_body` and `shopify-hmac-sha256` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body without objection [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` and succeeds because it is unchanged [8](#0-7) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload actually originated from and describes `attacker.myshopify.com`'s data [9](#0-8) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
