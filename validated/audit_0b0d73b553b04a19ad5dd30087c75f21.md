## Finding

Shopify's webhook HMAC in this gem is computed only over the raw request **body**; none of the routing/identity headers (`shop`, `topic`, `webhook-id`, `api-version`) are included in the signed material. `Webhooks::Registry.process` nonetheless trusts those headers to decide *which shop* and *which topic* the payload belongs to.

### Binding broken
`shop authenticated by the HMAC` ⧧ `shop used to route/attribute the webhook payload`

`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` only compares the HMAC of `to_signable_string` (i.e. the body) against the `hmac` header value: [3](#0-2) 

`Webhooks::Registry.process` validates that body-only HMAC, then immediately trusts the unauthenticated `shop`/`topic` headers to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

### Exploit path (no privileged credentials needed)
1. An attacker registers as a normal (even free-trial) merchant and installs the target app, which is a fully unprivileged action.
2. Shopify sends the attacker a legitimate webhook for their own shop: `body`, `hmac-sha256`, `shop-domain: attacker-shop.myshopify.com`, `topic`.
3. Because the HMAC only signs `body`, the `(body, hmac)` pair remains valid for that same app's `client_secret` regardless of headers.
4. The attacker resends the exact same `body`/`hmac` to the app's webhook endpoint, but swaps `x-shopify-shop-domain` to a victim shop and/or changes `x-shopify-topic`.
5. `HmacValidator.validate` still returns `true` (body+secret unchanged), so `Registry.process` dispatches the attacker-controlled body to the handler tagged as coming from the victim shop/topic: [5](#0-4) 

Any host application that uses `WebhookMetadata#shop` to key data storage, cache invalidation, or tenant-scoped processing (the documented and expected usage pattern of this API) will store/process attacker-supplied data under the victim tenant's identity — a cross-tenant data-integrity break achieved purely through this gem's own webhook verification logic, without needing the app's `client_secret`, an access token, or any privileged account.

### Title
Webhook shop/topic identity spoofing via header fields excluded from the HMAC signature — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` come from unauthenticated HTTP headers. `Webhooks::Registry.process` trusts these headers for routing after validating only the body's HMAC, letting any shop that received one legitimate webhook replay it with a forged `shop`/`topic` header pair.

### Finding Description
The identity binding `shop covered by HMAC == shop trusted by the handler` does not hold: `Request#shop` and `Request#topic` are pulled straight from headers [6](#0-5)  that are never part of the signed payload [1](#0-0) . `Registry.process` validates only that body-derived signature and then forwards the header-derived `shop`/`topic` to the app handler [4](#0-3) .

### Impact Explanation
This meets the "cross-tenant access" Critical bar: an unprivileged merchant who legitimately receives one webhook for their own shop can replay it under an arbitrary victim shop's identity, causing the host app (following this gem's documented `WebhookMetadata` contract) to attribute attacker-controlled data to the victim tenant.

### Likelihood Explanation
Any merchant can install a public app for free/trial and immediately receive real webhooks with valid signatures for benign topics (e.g. `app/uninstalled`), then replay them with a modified `shop`/`topic` header — no secrets, tokens, or elevated access required.

### Recommendation
Bind the routing headers into the signed material check, or require the app to independently verify `shop` (and `topic`) against a lookup keyed by the `webhook_id`/subscription rather than trusting the header outright.

### Proof of Concept
```ruby
# Attacker legitimately receives this valid pair as their own shop:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)

# Replay with victim's shop domain / different topic - HMAC still validates:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}
req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => handler.handle receives shop: "victim-shop.myshopify.com", body: attacker's data
```
