### Title
Planted unpriceable dust collateral leg permanently bricks liquidation and bad-debt cleanup of a borrowing account - ([File: contracts/controller/src/risk/totals.rs])

### Summary
`supply` accepts a new collateral position without requiring a resolvable oracle price for that asset, while every risk-computing path (`liquidate`, `clean_bad_debt`, `withdraw`, `update_account_threshold`) iterates all supply legs through `calculate_account_risk_totals` / `Context::cached_price`, which panics on a stale or missing feed. A borrower can plant a dust leg in an asset whose feed has gone (or later goes) permanently stale, making their own account permanently unliquidatable and unclosable, so the borrowed funds can never be recovered — protocol insolvency.

### Finding Description
`calculate_account_risk_totals_body` iterates `iter_typed_positions(supply_positions)` and calls `cache.cached_price(&hub_asset.asset)` for every collateral leg ( [1](#0-0) ). `build_liquidation_plan` calls `risk::calculate_account_risk_totals` before planning, so one unpriceable leg reverts the whole liquidation regardless of `debt_payments` or `seize_mode` ( [2](#0-1) ). Permissionless `clean_bad_debt` goes through `socialize_bad_debt`, which runs the same totals computation before the dust gate is even checked ( [3](#0-2) ). Meanwhile `supply` does not require a fresh price for the deposited asset — the test `test_stale_price_allows_supply_without_price_read` explicitly pins that deposits succeed with a stale oracle ( [4](#0-3) ). The planted leg also cannot be removed: `withdraw` with outstanding borrows reverts on the same stale price ( [5](#0-4) ), and the owner cannot excise it because a withdraw of the poisoned leg itself panics at `cached_price` ( [6](#0-5) ). The in-repo PoC `audit_liquidate_and_clean_bricked_by_unpriceable_dust_leg` demonstrates the full chain: plant a 0.001 WBTC leg while the WBTC feed is stale, crash the real collateral, then both `liquidate` and `clean_bad_debt` revert with `PRICE_FEED_STALE` until the feed recovers ( [7](#0-6) ).

### Impact Explanation
An attacker opens a maximally-borrowed account, then supplies a dust amount of a listed asset whose feed is already stale (a feed that later dies permanently — e.g., a retired Reflector ticker or delisted source — works too). From that moment the account can never be liquidated, never cleaned via `clean_bad_debt`, and the owner's `force_socialize_bad_debt` also reverts since it runs the same totals. The attacker's debt is permanently shielded; the protocol keeps a permanently uncollectible borrow position whose interest keeps accruing — direct protocol insolvency up to the borrow size, for the cost of one dust deposit.

### Likelihood Explanation
Fully unprivileged path: `supply` (own account, `account_id` existing), `borrow`. No governance, no privileged flag, no token-semantics assumption required — only oracle staleness, which occurs naturally and which the deposit path deliberately tolerates. The cost is one dust deposit; the shield persists exactly as long as the feed stays dead, and is permanent if the feed never recovers. Severity: High.

### Recommendation
Do not let `supply`/`process_deposit` create a new supply-position leg (i.e., a `(hub_id, asset)` key not already in `account.supply_positions`) without successfully resolving that asset's price; alternatively, make `calculate_account_risk_totals` skip zero-value or unpriceable supply legs (treat them as zero collateral) so one dead feed cannot veto liquidation and bad-debt cleanup of the whole account.

### Proof of Concept
1. Attacker supplies $10,000 USDC to a new account and borrows 3 ETH.
2. While the listed WBTC market's Reflector feed is stale (last update > `max_stale`), call `supply(caller, account_id, spoke_id, [(hub(WBTC), 0.001)])` — accepted, per `test_stale_price_allows_supply_without_price_read` and `audit_supply_stale_shield`.
3. USDC price crashes; account HF < 1.
4. Every `liquidate(liquidator, account_id, [(hub(ETH), amt)], Transfer|Credit)` reverts with `PRICE_FEED_STALE` inside `calculate_account_risk_totals`; `clean_bad_debt` reverts the same way; `withdraw` of the WBTC leg also reverts, so the poison cannot be removed even by the owner.
5. If the WBTC feed never recovers, the debt is permanently unrecoverable — suppliers absorb the loss.
