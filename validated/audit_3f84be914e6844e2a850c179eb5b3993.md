### Title
Governance-set static consensus relayer reward (`StateMachinesCostPerBlock` / `OutboundConsensusDeliveryReward`) becomes economically unreliable during gas-price or token-price volatility, risking bridge liveness - (File: `modules/pallets/consensus-incentives/src/lib.rs`, `modules/pallets/relayer/src/lib.rs`)

### Summary
Both `pallet-consensus-incentives` and `pallet-ismp-relayer` pay consensus relayers a **fixed, admin/governance-set reward** for delivering consensus proofs, rather than deriving the reward from live market conditions (gas price, native/`$BRIDGE` token price). Exactly like `Lender::setEtherPrice`, this value can only be updated by a privileged extrinsic and has no automatic responsiveness to price/gas swings, so during periods of high volatility the configured reward can fall below the actual cost relayers incur, causing the permissionless relayer market to stop servicing the affected route.

### Finding Description
`pallet-consensus-incentives` rewards the first relayer to submit a `ConsensusMessage` update for a state machine using a strictly linear formula keyed off a governance value: [1](#0-0) 

`StateMachinesCostPerBlock` is only mutated by the privileged `update_cost_per_block` extrinsic: [2](#0-1) 

Likewise, `pallet-ismp-relayer` pays a fixed per-destination `OutboundConsensusDeliveryReward` to whichever relayer delivers a mandatory authority-set rotation proof to an EVM destination — this reward exists specifically to offset the relayer's on-chain gas cost on that destination chain: [3](#0-2) 

The documentation confirms the intent — mandatory rotations "must always be propagated" and the reward exists "to offset the gas cost of keeping that chain's on-chain Hyperbridge consensus client current": [4](#0-3) 

Neither `CostPerBlock` nor `OutboundConsensusDeliveryReward` is tied to any oracle, gas-price feed, or dynamic formula — both are static values an admin sets by hand, exactly the pattern flagged in the source report (`setEtherPrice`). Destination-chain gas prices and the pricing of `$BRIDGE`/native tokens can swing sharply (the same "market volatility" scenario cited in the report). If a spike in destination gas price or a crash in `$BRIDGE`/native token price makes the configured reward unprofitable relative to the relayer's real cost, permissionless relayers — who race competitively and only relay when profitable (`docs/content/protocol/ismp/relayers.mdx` lines 20-24, `docs/content/developers/explore/relayers.mdx` lines 153-161) — will stop submitting consensus proofs for that route until governance manually re-prices it.

### Impact Explanation
Consensus updates gated by `pallet-consensus-incentives` are the mechanism that "keeps Hyperbridge's view of every connected chain fresh — without it no cross-chain message can be securely verified" (README, lines 3, 9). If the reward becomes uneconomical during a volatility spike, relayers stop submitting consensus proofs, halting state-proof verification for that entire state machine — a "route unable to deliver messages" condition covering every message (requests, responses, timeouts) that depends on that chain's state commitments. Similarly, an underpriced `OutboundConsensusDeliveryReward` stops authority-set rotation delivery to an EVM destination, which the documentation explicitly calls **mandatory** for keeping that chain's on-chain consensus client from falling behind and rejecting all future Hyperbridge proofs — a permanent liveness freeze on that destination until governance re-prices and relayers resume, or the client falls too far behind to recover. This is a bridge-liveness / message-delivery freezing issue, not merely lost yield.

### Likelihood Explanation
No malicious actor is required — this is triggered purely by ordinary market conditions (a gas-price spike on an EVM destination, or a drop in `$BRIDGE`/native token price) combined with governance's inherent latency in reacting (the same "unreliable during volatility" root cause as the analog report). Any relayer or observer can trivially detect that submitting a proof is unprofitable and simply decline, which is rational behavior in the permissionless, profit-driven relayer market the protocol is explicitly designed around.

### Recommendation
Tie `CostPerBlock` and `OutboundConsensusDeliveryReward` to a responsive pricing mechanism rather than a purely static, manually-set value — e.g., periodic automated adjustment based on observed destination gas prices/native-token price feeds, or a self-adjusting auction/market-rate mechanism, with alerting when the effective margin for relayers approaches zero so governance can react before liveness is lost.

### Proof of Concept
1. Governance calls `pallet_consensus_incentives::update_cost_per_block(state_machine_id, X)` (or `pallet_ismp_relayer::set_outbound_consensus_delivery_reward(state_machine, Y)`), fixing the reward at a value profitable under current gas/token prices.
2. Destination chain gas price spikes (or `$BRIDGE`/native token price crashes) such that `X`/`Y` no longer covers the relayer's actual submission cost.
3. Competitive, profit-driven relayers (per `docs/content/developers/explore/relayers.mdx` lines 153-161) stop submitting consensus proofs / mandatory authority-set rotations for that state machine/destination, since doing so is a loss-making transaction.
4. Because no automatic re-pricing exists, the state machine's consensus stalls (blocking all cross-chain message verification for it), or the EVM destination's authority-set falls behind until its on-chain client can no longer accept further Hyperbridge proofs, freezing that route until governance manually intervenes with an updated `update_cost_per_block`/`set_outbound_consensus_delivery_reward` call.

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)

		/// Update cost per block for a state machine
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::update_cost_per_block())]
		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}

## Mandatory consensus proof rewards (EVM chains)

When the outbound task delivers an authority-set rotation (a
*mandatory* consensus proof) to an EVM destination, the destination
chain pays the relayer a reward on top of whatever messaging incentives
travel in the same transaction. This offsets the gas cost of keeping
that chain's on-chain Hyperbridge consensus client current even when
no user message would otherwise justify the delivery.

Tesseract claims this reward automatically in the background after a
successful mandatory consensus proof delivery — operators do not need
to take any extra action. Without this incentive, destinations that
see infrequent user traffic would be unprofitable to keep up to date;
with it, every EVM destination stays current.
