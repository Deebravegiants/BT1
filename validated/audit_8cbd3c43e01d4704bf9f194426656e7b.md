### Title
Unvalidated JWT `dest` claim used as request host lets a merchant redirect `client_secret` token-exchange requests to an attacker-controlled domain (SSRF with app credentials) - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` derives the destination host for the token-exchange HTTP request directly from the session token's `dest` claim, via `JwtPayload#shop`, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`. Every other credential-bearing flow in the gem (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`) explicitly sanitizes the `shop` value with `ShopValidator` before using it to build the request host. `exchange_token` is the one path that skips this check, breaking the invariant "host that receives `client_id`/`client_secret` == a validated `*.myshopify.com`/trusted Shopify domain."

### Finding Description
`JwtPayload#shop` simply strips the `https://` prefix from the `dest` claim with no domain allow-listing: [1](#0-0) 

`JwtPayload#initialize` only checks the `aud` claim against `Context.api_key`, and validates the signature against `Context.api_secret_key` (or the old secret) - it performs no validation of `iss`/`dest` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [2](#0-1) 

`TokenExchange.exchange_token` then takes this unsanitized `dest_shop` value and uses it directly to build a `Session`/`HttpClient` that is sent `client_id` and `client_secret` in the POST body to `https://#{dest_shop}/admin/oauth/access_token`: [3](#0-2) 

Contrast this with the two other credential-bearing flows in the same file/module, which both call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host: [4](#0-3) [5](#0-4) 

`ShopValidator` exists precisely to enforce that a shop/host string resolves to a domain under `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is trusted as a request target: [6](#0-5) 

The broken binding is: **host that receives `client_secret` == a `ShopValidator`-sanitized Shopify domain**, for every other flow, but for `exchange_token` the binding degrades to **host that receives `client_secret` == raw `dest` claim string from the JWT**, with no allow-list check.

### Impact Explanation
If a session token can ever be presented to the app backend with a `dest` claim that is not a genuine, trusted Shopify shop domain, `exchange_token` will happily send the app's `client_id` and `client_secret` (the gem's most sensitive secret) to that host as part of the OAuth token-exchange request. That is SSRF carrying the app's credentials to an attacker-chosen host — classified as High/Critical impact per the scan rubric (credential exfiltration of `client_secret`). The test suite's own accepted-domain set (`myshopify.io`, `spin.dev`) shows `dest` is expected to vary across environments, underscoring that this claim is not itself constrained to a single well-known suffix inside this code path — the only guard that exists for that purpose (`ShopValidator`) is bypassed here.

### Likelihood Explanation
Exploitability is gated by whether an unprivileged actor can get a validly-signed session token with an attacker-chosen `dest` accepted by `JWT.decode` in `JwtPayload#decode_token`. This gem verifies only the signature (against `Context.api_secret_key`/old secret) and the `aud` claim — it does not verify `iss` at all and does not bind `dest`/`iss` to a shop allow-list. Since normal issuance of these tokens is controlled by Shopify/App Bridge, I could not confirm from this codebase alone a concrete unauthenticated path to forge or otherwise obtain a validly-signed token with a malicious `dest`; that would require either a leaked secret or a flaw in how the token is issued/relayed, both outside this gem. I flag this as a **defense-in-depth gap** rather than a fully proven end-to-end exploit: the missing `ShopValidator` call is a real, confirmed inconsistency in this file relative to its sibling functions, but full exploitability depends on token-issuance behavior not visible in this repository.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, sanitize `dest_shop` with `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token` and `ClientCredentials.client_credentials`) immediately after extracting it from `jwt_payload.shop`, before it is used to construct `shop_session`/`Session.from`, e.g.:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
Additionally, consider validating the `iss` claim inside `JwtPayload#initialize` against the same trusted-domain allow-list used by `ShopValidator`, so the check is enforced at decode time rather than relying on every caller to remember to sanitize.

### Proof of Concept
Not fully constructible from this repository alone: reproducing the attack requires demonstrating that a validly-signed session token with an attacker-controlled `dest` claim can reach `TokenExchange.exchange_token`, which depends on token-issuance/relay behavior outside this gem's code. The concrete, provable artifact from static review is the asymmetry itself:
```ruby
# token_exchange.rb exchange_token (VULNERABLE - no sanitize)
dest_shop = jwt_payload.shop
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)   # unsanitized host used with client_secret

# token_exchange.rb migrate_to_expiring_token (SAFE)
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
```

module ShopifyAPI
  module Utils
    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
