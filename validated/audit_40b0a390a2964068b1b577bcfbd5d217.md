## Finding: Frozen consensus clients permanently strand relayer fees for in-flight requests, since both delivery and timeout/refund are gated by the same non-recoverable freeze check

### Title
Permanent consensus-client freeze strands escrowed relayer fees because the timeout/refund path shares the same unrecoverable frozen-client check as delivery - (File: `modules/ismp/core/src/handlers/timeout.rs`)

### Summary
`pallet-ismp`'s consensus-fault mechanism intentionally puts a consensus client into an unrecoverable frozen state once a valid fraud proof is submitted, exactly like Jackpot's `emergencyMode`. Unlike the Jackpot report's flow, the freeze here also disables the escape hatch (timeouts) that is supposed to let users recover funds when delivery becomes impossible, because both the request-delivery handler and the timeout handler share the same `validate_state_machine` gate that rejects any state machine tied to a frozen consensus client.

### Finding Description
`freeze_client` verifies a fraud proof and calls `host.freeze_consensus_client(msg.consensus_state_id)`, after which the client can never resume — the docs are explicit: "Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead." [1](#0-0) [2](#0-1) 

Every incoming message (requests, responses, **and timeouts**) that references a `StateMachineHeight` tied to that consensus client is routed through `validate_state_machine`, which asserts `host.is_consensus_client_frozen(...)` before proceeding: [3](#0-2) 

Critically, `timeout::handle` — the only path capable of refunding the relayer fee escrowed for an outgoing `PostRequest` when delivery is impossible — calls this exact same `validate_state_machine` gate on the destination state machine's consensus client before any timeout can be processed: [4](#0-3) 

The dedicated test confirms this: freezing the consensus client causes `handle_incoming_message` for a `Request` message to fail with `FrozenConsensusClient`, and the same check applies unconditionally to the `Timeout` variant since it calls the identical `validate_state_machine` helper. [5](#0-4) 

Relayer fees are escrowed at dispatch time and only released either on successful delivery (paid to the relayer) or on timeout (refunded to the payer): [6](#0-5)  On the EVM side the analogous escrow is `_requestCommitments[commitment]`, released only via `dispatchIncoming` or `dispatchTimeOut`. [7](#0-6) 

For any `PostRequest` in flight to a destination whose consensus client subsequently gets frozen (before delivery and before/without a completed timeout), there is no remaining code path to either deliver it or reclaim the escrowed fee: delivery reverts with `FrozenConsensusClient`, and timeout processing reverts with the same error since it uses `validate_state_machine` on the very same consensus state id. The funds sit in the fee-escrow account (`RELAYER_FEE_ACCOUNT` on Substrate, or `_requestCommitments` fee on EVM) permanently.

### Impact Explanation
Any relayer fee attached to a POST request that has not been delivered (or whose timeout has not yet been fully processed) by the time the destination's consensus client is frozen becomes permanently unrecoverable — neither the payer's refund path nor the relayer's payment path can execute. This is a permanent freezing-of-funds bug directly analogous to the Jackpot `lpEarnings` issue: a legitimate, intentionally-unrecoverable protocol state (frozen consensus client / emergency mode) blocks the *only* remaining accounting path (timeout/refund) that should have served as the safety valve once normal delivery is impossible.

### Likelihood Explanation
Freezing a consensus client is a normal, permissionless part of protocol operation — "fishermen" are explicitly designed to be unstaked, permissionless actors who submit `FraudProofMessage`s whenever they detect equivocation: [8](#0-7)  Any relayer/application that has dispatched fee-bearing requests to a chain whose consensus client is later legitimately frozen (a byzantine/equivocation event, which the protocol is explicitly designed to detect and respond to) will have its outstanding fee escrow permanently stuck, with no privileged or governance path shown in the codebase to recover it (no `unfreeze_consensus_client` function exists anywhere in `modules/ismp/core` or `modules/pallets/ismp`).

### Recommendation
Add an explicit fee-recovery/timeout path that does not depend on `is_consensus_client_frozen` for the affected consensus state id — e.g., allow a non-membership/timeout claim to proceed using the last known (pre-freeze) state commitment, or add a dedicated sweep function gated only on "consensus client X is frozen" that lets the original payer reclaim any fee whose request was never delivered, mirroring the External Report's recommendation of "a dedicated function that allows withdrawing the stuck funds."

### Proof of Concept
1. Dispatch a `PostRequest` with a non-zero relayer fee to a destination chain `D`, escrowing the fee via `dispatch_request`/`EvmHost.dispatch`. [6](#0-5) 
2. Before the request is delivered or timed out, a fisherman submits a valid `FraudProofMessage` for `D`'s consensus client, which succeeds and calls `host.freeze_consensus_client(...)` — this is a normal, permissionless call. [1](#0-0) 
3. Attempt to deliver the request via `handle_incoming_message(Message::Request(...))` — reverts `FrozenConsensusClient` (matches existing test `frozen_consensus_client_check`). [5](#0-4) 
4. After the request's `timeout_timestamp` elapses, attempt to submit `Message::Timeout(TimeoutMessage::Post{...})` for the same request/height — this also calls `validate_state_machine(host, timeout_proof.height)` on the same frozen consensus state id and reverts `FrozenConsensusClient`, exactly as in step 3. [4](#0-3) 
5. Since the consensus client can never be unfrozen, the escrowed relayer fee for this request remains locked in `RELAYER_FEE_ACCOUNT` (Substrate) / `_requestCommitments` (EVM) forever, with no callable recovery path in the codebase.

/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}

     * @dev Dispatch a POST request to Hyperbridge
     *
     * @notice Payment for the request can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in
     * the feeToken.
     *
     * @param post - post request
     * @return commitment - the request commitment
     */
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();

                post.fee, path, address(this), block.timestamp
            );

            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

            dest: post.dest,

            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body

### Fishermen

The fishermen have a simple task: they monitor the headers sent to on-chain consensus clients and compare them with the information shared in the p2p swarm. In the event of a byzantine attack, a fisherman can earn significant rewards by submitting fraud proofs for these headers and collecting the malicious validators's stake. Running fishermen should be permissionless and require no staking whatsoever.
