## Title
Streaming yield continues to vest with no recipients, letting a depositor capture abandoned yield after a full exit/re-entry — (`sdk/packages/core/contracts/vaults/StreamingYieldVault.sol`)

### Summary
`StreamingYieldVault` linearly unlocks each yield tranche purely as a function of elapsed time (`_vestingStart`, `VEST`), exactly like `VirtualStakingRewards`'s reward-per-token clock. Just as the reported bug shows time passing "distributes" rewards even with zero stakers, this vault keeps streaming a tranche even when `totalSupply() == 0` (i.e., every shareholder has exited). Because `redeem`/`withdraw` are never blocked during vesting (only `maxDeposit`/`maxMint` are gated), a user can deposit, watch a tranche start, immediately redeem their principal (leaving the still-vesting yield untouched in the vault with no shareholders), wait out `VEST`, and then re-deposit into the now-empty vault to capture the fully-vested yield that streamed to nobody.

### Finding Description
The vault's core assumption is that the time-locked yield in `_lockedYield()` unlocks pro-rata to the shareholders who are exposed to it throughout the vesting window: [1](#0-0) 

This unlock schedule is keyed solely on `block.timestamp - _vestingStart`, with **no dependency on `totalSupply()`**. Meanwhile, only deposits/mints are disabled while a tranche vests: [2](#0-1) 

`redeem`/`withdraw` are standard ERC4626 functions and are never gated by `_isVesting()`, so a shareholder can fully exit mid-tranche. If a user is the last (or only) shareholder and redeems everything while a tranche is still vesting, `totalSupply()` drops to `0`, but `_vestingStart`/`_vestingAmount` are untouched — the tranche keeps counting down "to nobody," exactly the scenario the `VirtualStakingRewards` report describes (funds are dispersed on a fixed schedule even though there are no recipients tracking that schedule).

Once `VEST` fully elapses, `_lockedYield()` returns `0` and the entire tranche is reflected in `totalAssets()` — but `totalSupply()` is `0`. The `addYield`/`_startVesting` guard only checks `block.timestamp` against the prior tranche's end, never whether anyone is currently holding shares: [3](#0-2) 

Since `deposit`/`mint` reopen the moment `_isVesting()` is false (regardless of `totalSupply()`), whoever deposits into this now-empty-but-asset-holding vault mints shares against the full (already-vested) balance under ERC4626's zero-total-supply / virtual-share conversion rules — capturing value nobody was exposed to during the vesting period.

### Impact Explanation
The `VEST`/`MIN_WINDOW` design's entire stated purpose is to prevent "yield sniping" — capturing yield without having been exposed to it for the streaming duration: [4](#0-3) 

The zero-total-supply gap defeats that guarantee entirely: instead of needing a same-block sandwich (which the design correctly blocks via unchanged share price), an attacker can exit before a tranche finishes vesting and later re-deposit once it has, claiming yield they were never at risk for. With a large enough deposit relative to the abandoned balance, the attacker can capture close to the entire unclaimed tranche (the `DECIMALS_OFFSET` virtual-share mechanism only dampens this for small deposits; it does not prevent it for deposits comparable to or larger than the outstanding balance). This is a fund-diversion/theft-of-yield issue affecting any funds the owner streams via `addYield`, satisfying the Medium-severity bar for unbacked value capture.

### Likelihood Explanation
Reaching `totalSupply() == 0` mid-vest requires no privileged role — any set of shareholders (including a single self-interested depositor) can simply redeem in full at any time, since `redeem`/`withdraw` are unrestricted during vesting. Because `addYield` is called periodically by the owner as part of normal vault operation, and each cycle has a deposit window immediately after full vesting, an attacker only needs to time one `redeem` before `vestedAt()` and one `deposit`/`mint` after it — both single, unprivileged transactions reachable by any external account.

### Recommendation
Tie the vesting/streaming mechanism to the presence of shareholders, analogous to the `VirtualStakingRewards` fix options:
- Pause/freeze the vesting clock (or snapshot `_lockedYield()` and stop advancing it) whenever `totalSupply()` drops to `0`, resuming only once a depositor is present again, or
- Disallow `redeem`/`withdraw` that would bring `totalSupply()` to `0` while a tranche is still vesting (forcing at least one holder to remain exposed through the full window), or
- On the next `addYield`/first deposit after a supply gap, explicitly sweep the leftover already-vested balance to the treasury/owner instead of letting an arbitrary new depositor claim it via ordinary ERC4626 minting.

### Proof of Concept
1. Attacker deposits `X` assets, becoming the vault's only shareholder (`totalSupply() = S`).
2. Owner calls `addYield(Y)`; `_vestingStart = now`, `_vestingAmount = Y`.
3. Attacker immediately calls `redeem`/`withdraw` for all `S` shares. `totalAssets()` at this moment ≈ `X` (since `Y` is still fully locked per `_lockedYield()`), so attacker recovers essentially their principal. `totalSupply()` is now `0`, while the vault still holds `~X + Y` in `asset` balance and the `Y` tranche keeps counting down unattached to any shareholder.
4. Attacker waits until `block.timestamp >= vestedAt()` (`_vestingStart + VEST`). `_lockedYield()` now returns `0`, so `totalAssets()` reports the full `~X + Y`, with `totalSupply() == 0`.
5. Attacker calls `deposit`/`mint` with an amount `Z` comparable to or larger than the outstanding balance. Because `totalSupply() == 0`, ERC4626's virtual-share conversion mints shares proportional to `Z` against the existing `~X+Y` balance; attacker can immediately `redeem` and withdraw a share of `Y` (the yield tranche) they were never exposed to during vesting — value that should have accrued only to shareholders present throughout the streaming window.

```text
    /// @dev Linear unlock of the current tranche, keyed on `block.timestamp` so that a deposit
    ///      and withdrawal within the same block observe an identical, unchanged share price.
    function _lockedYield() internal view returns (uint256) {
        uint256 start = _vestingStart;
        uint256 elapsed = block.timestamp - start;
        if (elapsed >= VEST) return 0;
        return (_vestingAmount * (VEST - elapsed)) / VEST;
    }
```

```text
    /// @dev Arms a new tranche after validating the no-overlap / deposit-window guards. The caller
    ///      must have already moved `amount` of `asset` into the vault (so `balanceOf` reflects it
    ///      before `_vestingAmount` is set, avoiding a transient `totalAssets` underflow).
    function _startVesting(uint256 amount) private {
        if (amount == 0) revert ZeroAmount();

        uint256 start = _vestingStart;
        if (start != 0) {
            if (block.timestamp < start + VEST) revert YieldStillVesting(start + VEST);
            // Hold off until the guaranteed deposit window has elapsed, so new capital always has
            // a chance to enter between tranches regardless of how promptly the keeper runs.
            if (block.timestamp < start + VEST + MIN_WINDOW) revert DepositWindowOpen(start + VEST + MIN_WINDOW);
        }

        _vestingAmount = amount;
        _vestingStart = block.timestamp;

        emit YieldAdded(amount, block.timestamp);
    }
```
