### Title
Webhook `shop-domain` and `topic` headers are trusted for routing and handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches to a handler using these unauthenticated header values, breaking the intended binding: `HMAC(secret, signed_bytes) == received_hmac` should equal `shop header == shop bound in signed_bytes`, but the gem only enforces the former.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) .

`Registry.process` validates the HMAC over the (header-independent) signable string, then immediately trusts `request.topic` (to select the handler) and `request.shop` (passed into the handler as the tenant identifier) without any additional verification that these header values were the ones the sender actually authenticated: [3](#0-2) .

`HmacValidator.validate` itself only ever compares the computed signature over `to_signable_string` against the provided `hmac`; it has no knowledge of headers at all: [4](#0-3) .

The identity binding that should hold is:
`shop_header == shop_bound_in_hmac_signed_bytes`

but the actual binding enforced is only:
`HMAC(secret, raw_body) == received_hmac`

with `shop_header` completely outside that computation.

### Impact Explanation
Because the HMAC only covers the raw body, any request whose body+HMAC pair is valid for shop A can have its `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) headers changed to point to shop B (or an arbitrary attacker-chosen value) without invalidating the HMAC check. `Registry.process` will still consider the request valid and will hand `WebhookMetadata` with the substituted `shop` value to the merchant's webhook handler. Any host application (built per this gem's documented API) that uses `WebhookMetadata#shop` to look up per-tenant records, sessions, or to key merchant data storage will process/attribute the event to the wrong tenant — a cross-tenant confusion enabled purely by the gem's failure to bind the header used for tenant identification to the authenticated bytes. This satisfies the "cross-tenant access" impact category, since the webhook processing pipeline is meant to give tenant-scoped guarantees per shop, and this gem is the security boundary responsible for authenticating which shop a webhook came from.

### Likelihood Explanation
Exploitation does not require the app's `client_secret`/HMAC key: the raw body and its correct HMAC can be observed from any single legitimate webhook delivery (webhook payloads are not always treated as fully confidential, and many apps log/relay them), after which only the headers need to be modified for replay to a public webhook endpoint. Since the header names/values are the only inputs `Registry.process` uses to select the handler and determine `shop`, the manipulation is trivial once a single valid (body, hmac) pair is captured. This is a design-level omission in the gem's own verification method rather than a host-application misuse, since `HmacValidator`/`Request` are documented as sufficient means to authenticate webhook shop identity.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload used by `Request#to_signable_string`, or otherwise cryptographically bind them (e.g., verify against a value independently confirmed via an authenticated API call, or accept these fields only from a channel that is itself authenticated, such as Shopify's push channel metadata rather than caller-supplied headers). At minimum, document that `request.shop`/`request.topic` are not covered by HMAC verification and must not be trusted for tenant routing without additional verification (e.g., confirming the shop exists in the app's own installed-shop store).

### Proof of Concept
1. Attacker (or anyone with network visibility into a legitimate webhook delivery) captures one valid webhook delivery for shop A: `raw_body`, and header `X-Shopify-Hmac-Sha256: <hmac_of_raw_body>`.
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a different shop) and/or a different `X-Shopify-Topic`.
3. `Request.new(raw_body:, headers:)` builds successfully (headers only checked for presence): [5](#0-4) .
4. `Registry.process(request)` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and finds it matches — validation passes despite the spoofed shop/topic headers: [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop` value, causing the event/body from shop A to be processed as if it belongs to shop B: [7](#0-6) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
