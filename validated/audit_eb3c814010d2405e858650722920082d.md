### Title
Unmeasured actual-received amounts in Tron `IntentGatewayV2.placeOrder` cause escrow ledger to exceed real token balance for fee-on-transfer/deflationary tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the `_orders` escrow mapping using amounts computed purely from the user-requested `order.inputs[i].amount` (minus protocol fee), instead of the amount actually received by the contract via `IERC20.safeTransferFrom`/`transfer`. This is the same class of bug as the reported Allo v2 issue: static bookkeeping (`poolAmount` there, `_orders[commitment][token]` here) diverges from the real token balance when deflationary/fee-on-transfer/rebasing ERC-20s are used, since no actual-balance measurement is performed before crediting escrow.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived only from the requested `order.inputs[i].amount` minus the protocol fee: [2](#0-1) 

No balance-before/balance-after check is performed, unlike the canonical EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`), which explicitly measures `IERC20(token).balanceOf(address(this))` before and after the transfer and mutates `order.inputs[i].amount` to the actually received amount before computing the commitment and crediting escrow: [3](#0-2) 

The same flaw exists in the predispatch branch of the Tron contract: the sweep-back transfer moves the dispatcher's full `balance` to the gateway, but the amount actually credited to escrow is still `reducedInputs[i].amount` (computed from the pre-transfer `order.inputs[i].amount`), not the balance the gateway actually receives after this second hop's transfer fee: [4](#0-3) 

For any ERC-20 with a transfer fee/burn-on-transfer (deflationary) mechanic, the actual tokens held by the gateway will be less than the sum credited into `_orders`. Fee-on-transfer behavior is explicitly anticipated and handled correctly elsewhere in the codebase (the non-Tron `IntentGatewayV2.sol` and its dedicated `FeeOnTransferToken` tests), confirming this is a known bug class the Tron fork failed to replicate.

### Impact Explanation
`withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow`, and from `cancelOrder`) transfers `amount = _orders[commitment][token]` directly to the beneficiary without checking the gateway's real token balance: [5](#0-4) 

Because the escrow ledger is inflated relative to the actual token balance, once enough deflationary-token orders are placed and settled, later legitimate redemptions/refunds/cancellations will revert (insufficient token balance) or leave some depositors permanently unable to reclaim/redeem their share — a permanent freezing of funds for users of any deflationary/fee-on-transfer token onboarded to this deployment. This matches the "Medium" severity and "permanent freezing of funds" criterion.

### Likelihood Explanation
Reachable directly by any ordinary user submitting `placeOrder` with a deflationary/fee-on-transfer ERC-20 as an input token — no privileged role is required. Likelihood scales with adoption of such tokens on the Tron deployment of the IntentGateway; solvers/fillers and the second (fee-on-transfer) input owner are both exposed once the ledger and real balance diverge.

### Recommendation
Mirror the balance-measurement pattern already used in `evm/src/apps/IntentGatewayV2.sol`: record `balanceOf(address(this))` before and after each `safeTransferFrom`/sweep-back transfer, mutate `order.inputs[i].amount` (and thus `reducedInputs[i].amount`) to the actually received amount, and use that measured amount — not the user-requested amount — both for the commitment hash and for crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer token (e.g., 1% burn-on-transfer) as a supported input token.
2. User A calls `placeOrder` with `inputs[0].amount = 1000`. `safeTransferFrom` moves tokens; gateway actually receives `990` (1% fee burned), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` computed from `1000` (minus any protocol fee), e.g. `1000` if protocol fee is 0.
3. Repeat for several orders — actual gateway token balance is always ~1% less than the cumulative `_orders` bookkeeping.
4. When enough orders attempt `withdraw()` (via `RedeemEscrow`, `RefundEscrow`, or `cancelOrder`), the last redemptions revert because `token.call(transfer(...))` fails due to insufficient actual balance, even though `_orders[commitment][token]` still shows a nonzero, "owed" balance — funds for the last redeemer(s) are permanently stuck.
