### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, while the shop identity (`x-shopify-shop-domain` header) is read unauthenticated and handed to the app's webhook handler as the tenant identifier. Because the same `api_secret_key` is shared across every shop that has the app installed, any merchant that has installed the app can capture a validly-signed `(body, hmac)` pair from their own webhook deliveries and replay it against the app's webhook endpoint with the `shop-domain` header changed to a victim shop, producing a request that passes `HmacValidator.validate` yet is attributed to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` straight from the header and exposes `to_signable_string` as only the raw body: [1](#0-0) 

`HmacValidator.validate` computes/verifies the signature purely from `to_signable_string`, i.e., only the body bytes: [2](#0-1) 

`Registry.process` checks only this body-HMAC, then immediately trusts `request.shop` (the unauthenticated header) to build the metadata handed to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop_header == shop_that_actually_produced(body)`.

In this implementation, the binding is broken: `hmac_valid(body)` only proves the body bytes were produced by *some* holder of the app's single, app-wide `api_secret_key` (i.e., any shop that installed this app), not that the accompanying `shop-domain` header is the shop that produced it. Since `api_secret_key` is one shared secret for the whole app (not per-shop), and the shop identity travels outside the signed material, an installer of the app (an unprivileged, non-privileged-relative-to-other-tenants internet user) can legitimately obtain `(body, valid_hmac)` pairs for their own shop and then present them with an arbitrary `shop-domain` value.

### Impact Explanation
This crosses a tenant boundary: a merchant/attacker who installs the app on their own store can cause the app's webhook handler to execute with `WebhookMetadata#shop` set to a different, victim shop, while the `body` is fully attacker-controlled content that they legitimately triggered (e.g., by editing their own store to fire `products/update`, `orders/create`, etc.). Any downstream logic in the host app that trusts `data.shop` to select which tenant's database rows / access token / configuration to mutate (a common and expected pattern per this gem's own webhook docs) will operate on the victim tenant using attacker-supplied data. This satisfies the "cross-tenant access" criterion (Critical) since it lets one tenant inject/forge events into another tenant's webhook processing pipeline without holding that tenant's credentials.

### Likelihood Explanation
Likelihood is high for any app that: (1) uses this gem's `Webhooks::Registry`/`Request`/`HmacValidator` as documented, and (2) uses `WebhookMetadata#shop` to key persistence or business logic (the intended and documented usage). The only prerequisite is that the attacker has (or can get) the app installed on a shop they control, which is the normal, unprivileged onboarding flow for any public or custom Shopify app — no leaked credentials, TLS interception, or privileged account is required.

### Recommendation
Bind the shop identity into the signed material, or otherwise validate it out-of-band:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signable string in `Webhooks::Request#to_signable_string`, matching it against a copy embedded in (or derivable from) the payload, or
- Require host apps to cross-check `request.shop` against an independently-verified value (e.g., a shop that is actually a known/subscribed tenant with a stored session) before trusting it, and document this prominently, or
- Consider verifying the source IP/allowed origin in addition to HMAC, and treat `shop-domain` as merely a routing hint that must be corroborated by that shop's existing session record rather than authoritative identity.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (standard, unprivileged install flow).
2. Attacker triggers a webhook for a topic the app subscribes to (e.g., updates a product), causing Shopify to POST a body `B` to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` header `H`, computed as `HMAC-SHA256(api_secret_key, B)`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts this request at their own server (they control the receiving endpoint) and re-sends it to the same webhook path with headers rewritten:
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body unchanged: `B`
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which recomputes the HMAC over `B` only and finds it matches `H` — validation succeeds.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the app processes attacker-controlled data under the victim shop's identity. [3](#0-2) [1](#0-0) [2](#0-1)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
