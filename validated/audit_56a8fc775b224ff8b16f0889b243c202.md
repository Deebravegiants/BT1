### Title
Webhook `shop` identity is unauthenticated by the HMAC, allowing cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute purely from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` validates only covers the raw request body. This breaks the binding: `shop_bound_by_hmac` (nothing — the signature only proves the body bytes were produced with the app's shared `client_secret`) ≠ `shop_attributed_to_handler` (the header value, fully attacker-controlled). The mismatch mirrors the report's bug class of "a value returned/acted upon without checking the actual authorization state that should gate it" — here, the `shop` field is trusted and forwarded to the host app's handler without being covered by the same check that "authenticates" the webhook.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it (via `OpenSSL.secure_compare`) to the received signature: [2](#0-1) 

`Request#shop` is read directly from the `shop-domain` header and is never part of `to_signable_string`: [3](#0-2) 

`Registry.process` validates only the HMAC of the request, then forwards `request.shop` (unauthenticated) into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identity for that webhook event: [4](#0-3) [5](#0-4) 

Because a single app's `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, any attacker who installs the app on their own shop can obtain a legitimately HMAC-signed webhook body for a real event (e.g. `orders/create`, `app/uninstalled`, `shop/redact`). Since the `shop-domain` header is not part of the signed payload, the attacker can resend that same body with an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` still succeeds (it only checks the body/secret), so `Registry.process` accepts the forged request and calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
Per the gem's own documented contract, the `shop` field of `WebhookMetadata` is the tenant identity host applications use to select which shop's session/access token to act on for that webhook event. Because this field is not bound by the cryptographic check that "authenticates" the webhook, an attacker with a paid/dev install of the target app can forge webhook deliveries attributed to any other merchant shop that has installed the same app, causing cross-tenant processing (e.g., the host app performing shop-specific side effects, such as data deletion for GDPR webhooks or business logic tied to `shop`, under a victim's identity). This falls under cross-tenant access, a Critical-impact category per the rules.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on their own store (a normal, unprivileged action available to any Shopify merchant/developer), (2) triggering or capturing one legitimately-signed webhook delivery for their own shop, and (3) replaying it with a modified `shop-domain` header to the app's webhook endpoint. No access token, `client_secret`, or privileged credential of the victim is needed — this is entirely within the unprivileged-internet-user threat model, since `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb) never checks the `shop` field.

### Recommendation
Extend `to_signable_string` (or add a secondary check in `Registry.process`) so the `shop-domain` header is part of the HMAC-verified data, or otherwise cryptographically bind `shop` to the signed payload before it is passed into `WebhookMetadata`. Alternatively, document/require that host applications never treat `WebhookMetadata#shop` as trusted without independently corroborating it (e.g., cross-checking against the shop stored for that installation), and consider validating that `shop` matches an existing/expected session before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g.:
```
POST /webhooks
shopify-topic: app/uninstalled
shopify-hmac-sha256: <valid signature over raw_body, computed with the app's shared client_secret>
shopify-shop-domain: attacker-shop.myshopify.com
<raw_body>
```
2. Attacker resends the exact same `raw_body` and `shopify-hmac-sha256` value, but changes the header:
```
shopify-shop-domain: victim-shop.myshopify.com
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (`@raw_body`) against the shared secret — `shop-domain` is never included: [6](#0-5) 
4. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)` and, per the gem's documented usage pattern, the host app performs shop-scoped actions (e.g., session/data cleanup) as if the event genuinely originated from `victim-shop.myshopify.com`.
