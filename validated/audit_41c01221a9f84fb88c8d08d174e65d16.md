### Title
`ShopifyAPI::Webhooks::Request#shop` is not covered by the HMAC signature, allowing cross-tenant shop-header substitution on a validly-signed webhook body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's tenant identity from the `shop-domain` HTTP header, but the HMAC signature (`hmac-sha256` header) is only computed over the raw request body via `to_signable_string`. The `shop` field is never included in the bytes that are HMAC-verified, breaking the binding `hmac_verified_bytes == identity_bytes`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Request#shop` reads the tenant identity from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload [2](#0-1) . `HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it against the `hmac` value, but never touches `shop` [3](#0-2) .

Because an app's `api_secret_key` (used to sign webhooks) is shared across every shop that installs the app, any merchant/tenant of a multi-tenant app can capture one of their own genuinely-signed webhook deliveries (valid `hmac-sha256` over a given raw body) and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a different shop's domain. Because the header is never covered by the signature, `HmacValidator.validate` still returns `true` for the tampered request, and any code that trusts `Request#shop` to select the tenant/session (as intended, since it's exposed as the canonical `shop` accessor) will process the payload under the wrong shop identity.

This matches the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `hmac_signed_bytes ⊇ {shop}`, but in fact `hmac_signed_bytes == {raw_body}` while `shop` is read from unauthenticated header bytes.

### Impact Explanation
This allows a legitimate but malicious tenant of a multi-tenant app to inject arbitrary (but validly-signed-for-their-own-shop) webhook payloads under another shop's identity into the host application, once the host relies on the gem's `Request#shop`/`HmacValidator.validate` combination as the trust boundary (which is exactly what this class is designed to provide). This is a cross-tenant data-integrity/identity-binding compromise: it lets one tenant supply attacker-controlled data that is processed as belonging to another tenant.

### Likelihood Explanation
Requires the attacker to control (or have access to) at least one shop installed on the target multi-tenant app in order to obtain a validly-signed webhook, plus the ability to POST directly to the app's webhook endpoint with a modified header. The webhook endpoint URL is normally public. This is a realistic scenario for any app that installs webhooks on more than one shop.

### Recommendation
Include the shop domain (and ideally topic / webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header to the signed body before exposing `Request#shop` as trusted tenant identity. At minimum, document/enforce that `shop-domain` must be independently verified by the host app (e.g., cross-checked against a known/installed shop for that specific webhook subscription) rather than treated as authenticated solely because `HmacValidator.validate` returned true.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both sharing the same `api_secret_key`.
2. Shopify sends a legitimate webhook to the app for `shop-a`: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. Attacker (who controls `shop-a` and can observe its own webhook deliveries) resends the same request but replaces `X-Shopify-Shop-Domain` with `shop-b.myshopify.com`, leaving body `B` and the HMAC header unchanged.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` — matching the received `hmac`, per `lib/shopify_api/utils/hmac_validator.rb` L12-L31 — and returns `true`.
5. `request.shop` returns `"shop-b.myshopify.com"` (attacker-controlled header), and the host application, trusting the HMAC-validated request, processes `B` as belonging to `shop-b`, even though `shop-b` never sent or authorized that payload.
