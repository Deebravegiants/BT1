### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to application webhook handlers come from unauthenticated HTTP headers. Any party that possesses one valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` — obtainable, for example, by installing the app on their own shop and observing a genuine Shopify webhook delivery — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still pass because it only checks the body, so the host application will process the replayed payload believing it originated from the attacker-chosen victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
```
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```
while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from request headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards the *unauthenticated* `request.shop` value to the handler as the tenant identifier: [3](#0-2) 
```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```
`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (the raw body) and compares it to the received signature: [4](#0-3) 

This is exactly the identity-binding break called out by the analog: the field the application *acts on* (the `shop` used to key sessions, credentials, and per-tenant data in the handler) is not the field the HMAC *covers* (only the body bytes). The equality the code implicitly assumes — `authenticated_shop == request.shop` — does not actually hold; `request.shop` is fully attacker-controlled while only the body is authenticated by the shared `api_secret_key`.

### Impact Explanation
Since `api_secret_key` is shared across every shop that installs the app, any attacker who legitimately installs the app on their own store can capture a real, validly-signed webhook `(body, hmac)` pair from Shopify. They can then resend that body/hmac unchanged to the app's webhook endpoint while forging the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret, and `Registry.process` passes the forged `shop` straight into `WebhookMetadata`. Any host application that uses `WebhookMetadata#shop` to select per-tenant secrets, write per-tenant records, or otherwise route trust decisions will attribute attacker-controlled data to a different tenant — a cross-tenant data/trust confusion.

### Likelihood Explanation
Exploitation requires the attacker to be an installer of the target app (to obtain one valid signed webhook body/hmac pair using the shared secret) and the ability to send an arbitrary HTTP request to the app's public webhook endpoint with custom headers — both are unprivileged, internet-reachable actions with no access token, `client_secret`, or credential leak needed. This satisfies the required threat model of an "unprivileged internet user."

### Recommendation
Bind the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed material that `HmacValidator` verifies, or otherwise document/enforce that `WebhookMetadata#shop` must never be trusted for tenant selection without independently confirming the shop is one for which the app holds a valid session before acting on the payload. At minimum, the gem should surface a clear warning in `Webhooks::Request`/`Registry` that only the body is HMAC-authenticated and the `shop` header is not, so host applications do not mistakenly treat it as an authenticated tenant identifier.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures a webhook (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker intercepts/replays this exact request to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally the topic), keeping `B` and `H` untouched.
4. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation passes: [5](#0-4) 
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` even though the body content actually belongs to `attacker-shop.myshopify.com`, causing the host application to act on the data under the wrong tenant's identity.
