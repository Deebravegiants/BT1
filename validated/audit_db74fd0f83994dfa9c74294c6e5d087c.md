### Title
Selling a small enough token amount permanently transfers tokens into the curve pair with zero LT returned - ([File: packages/contracts/src/Router.sol])

### Summary
`Router.sell` and its helper `_computeSell` never verify that the computed `assetOut` is non-zero before transferring the trader's tokens into the pair and finalizing the swap. Because `_computeSell` uses floor-division (`k / newReserveToken`), any sell whose `amountIn` is too small to move the floored quotient computes `assetOut == 0`, yet the trader's real tokens have already been irrevocably moved into the pair via `safeTransferFrom` and the swap is finalized regardless.

### Finding Description
`Router.sell` executes in this order: [1](#0-0) 

`tokensIn` (the trader's real tokens) are transferred to the pair with `IERC20(token).safeTransferFrom(to, pairAddr, amountIn)` *before* `assetOut` is computed. `assetOut` is derived by: [2](#0-1) 

`assetOut = reserveAsset - (k / newReserveToken)`. Because integer division floors, for any `amountIn` small enough that `k / (reserveToken + amountIn)` still floors to the same integer as `k / reserveToken` (i.e. `reserveAsset` itself), `assetOut` computes to exactly `0`. Given the curve's virtual token reserve is seeded at the full 1B `totalSupply` (documented in `docs/contracts-scope.md` lines 32-38) while `k` is fixed at launch, the derivative `dAssetReserve/dTokenReserve ≈ -k/reserveToken²` is extremely small relative to one LT wei near typical reserve magnitudes, so a wide range of small-but-nonzero `amountIn` values will floor to `assetOut = 0`.

Neither `Router.sell` nor `IPair.transferAsset`/`swap` guard against a zero `assetOut`: [3](#0-2) [4](#0-3) 

`pair.swap(amountIn, 0, 0, 0)` succeeds (the K-check `(newTokenReserve+1)*(newAssetReserve+1) < k` trivially holds when `assetOut=0`), and `transferAsset(to, 0)` is a harmless no-op transfer of zero LT. The net effect: the trader's ERC20 tokens are now permanently held by the pair (added to `reserveToken`), and the trader receives `0` LT back — this is the direct structural analog of the ArrakisV2 report, where `burn()` reduced `totalSupply` and consumed the caller's shares while `amount0`/`amount1` rounded to `0` and no compensating `require(amount0 > 0 && amount1 > 0)` guard existed.

This path is reachable by any unprivileged trader through `Zap.sell(tokenAddress, tokenAmount, minUsdcOut)` → `Bonding.sell()` → `Router.sell()`, with no privileged role required beyond normal trading.

### Impact Explanation
A trader who sells a token amount that floors to zero LT output loses their real, transferred-in tokens with no compensation and no revert to warn them — the tokens become permanently locked in the curve pair's `reserveToken`, unrecoverable through any user-facing function (the pair only exposes `transferToken`/`transferAsset` gated to `Router`, which never returns them to the seller in this path). This is a permanent, protocol-enforced loss of trader funds triggered by ordinary interaction with `Zap.sell`/`Bonding.sell`, matching the "permanent freezing/loss of trader funds" impact class.

### Likelihood Explanation
The condition depends purely on `amountIn` being small relative to `reserveToken` such that `k / (reserveToken + amountIn)` floors identically to `k / reserveToken`. Given the curve's virtual reserve is deliberately seeded at the full 1B-token `totalSupply` (documented design in `docs/contracts-scope.md`), this "dead zone" of `amountIn` values that yield zero output can be sizable in absolute token-wei terms, especially early in a curve's life or for tokens with a high `k`/`reserveToken` ratio. Any trader submitting a sell with a small `tokenAmount` (e.g. from a UI rounding error, a script bug, or dust cleanup) can trigger this without any special positioning or front-running.

### Recommendation
Add an explicit zero-output guard in `Router.sell` (and symmetrically in `Router.buy` for defense-in-depth) before transferring tokens into the pair or finalizing the swap:

```solidity
function sell(
    uint256 amountIn,
    address token,
    address to
) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
    if (amountIn == 0) revert ZeroAmount();

    address asset = assetTokenFor(token);
    address pairAddr = factory.getPair(token, asset);
    if (pairAddr == address(0)) revert PairNotFound();
    tokensIn = amountIn;

    assetOut = _computeSell(pairAddr, amountIn);
    if (assetOut == 0) revert ZeroAmount(); // reject dust sells that round to nothing

    IERC20(token).safeTransferFrom(to, pairAddr, amountIn);
    IPair(pairAddr).transferAsset(to, assetOut);
    IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
}
```
Compute `assetOut` before pulling funds so the transaction reverts cleanly instead of silently consuming the trader's tokens for nothing.

### Proof of Concept
1. A token is launched via `Bonding.launch`, seeding `Pair` with `reserveToken = totalSupply` (1B tokens, virtual reserve) and a small `reserveAsset` per the launch's `$3K` market-cap sizing, per `docs/contracts-scope.md` lines 32-38.
2. An unprivileged trader who already holds a small amount of the token (e.g. from a prior buy) calls `Zap.sell(tokenAddress, tinyAmount, 0)` with `tinyAmount` chosen (or accidentally small) such that `k / (reserveToken + tinyAmount)` floors to the same value as `k / reserveToken`.
3. This routes through `Bonding.sell()` into `Router.sell()`:
   - `_computeSell` returns `assetOut = 0` (see `packages/contracts/src/Router.sol` lines 172-182).
   - `IERC20(token).safeTransferFrom(to, pairAddr, amountIn)` still executes, permanently moving the trader's tokens into the pair (line 163).
   - `IPair(pairAddr).transferAsset(to, 0)` and `IPair(pairAddr).swap(amountIn, 0, 0, 0)` both succeed with no revert (lines 167-169, and `Pair.sol` lines 65-86).
4. The trader's tokens are gone; they received `0` LT and `0` USDC back from `Zap.sell`, with the transaction reporting success rather than reverting.

```text
    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }
```

```text
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
```
