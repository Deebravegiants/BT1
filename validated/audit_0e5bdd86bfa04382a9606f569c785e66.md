### Title
Unbounded, unauthenticated growth of the on-chain Vault allowlist causes O(n) linear-scan and per-request retry amplification in `AllowListBasedAuth`, degrading/denial-of-service the Gateway/Vault authorization path - ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
The Vault gateway authorizes every non-JWT request against an in-memory list of on-chain "allowlisted requests" (`allowListedRequests`) that is synced from the `WorkflowRegistry` contract by `workflowRegistry.syncAllowlistedRequests` [1](#0-0) . This list is unioned/appended across sync ticks with no protocol-enforced maximum size in the syncer code, and `AllowListBasedAuth.AuthorizeRequest` performs a full O(n) linear scan of that list — plus builds an O(n) formatted debug string of every entry — on **every single incoming vault request**, retried up to 10 times with 3-second sleeps between attempts when a digest is not (yet) found [2](#0-1) . Because workflow owners can permissionlessly add allowlist entries for their own workflows over time (an unprivileged, external, restricted-but-not-fully-trusted actor, analogous to the Convex "admin" in the referenced report who can grow an unbounded array that a critical function is forced to iterate), the list can be inflated without bound, causing every legitimate vault request's authorization step to become increasingly expensive and slow — with retry-driven amplification making the cost multiply for any request whose digest is not present in the allowlist.

### Finding Description
- `workflowRegistry.syncAllowlistedRequests` fetches new allowlisted requests from the `WorkflowRegistry` contract every 5 seconds and appends them to `w.allowListedRequests`, only pruning entries that have expired by wall-clock time; there is no cap on total live entries [3](#0-2) . `MaxResultsPerQuery = 1_000` only bounds the size of a single contract-read page, not the total number of entries the syncer will accumulate over time [4](#0-3) [5](#0-4) .
- `GetAllowlistedRequests` simply returns a full copy of this slice to callers [6](#0-5) .
- `AllowListBasedAuth.AuthorizeRequest` is invoked for every incoming vault request that does not carry a JWT (`req.Auth == ""`, the default/legacy path) [7](#0-6) . It calls `findAllowlistedItemWithRetry`, which on **every attempt** iterates the entire allowlist to build a debug string (`allowedRequestsStrs`) and calls `fetchAllowlistedItem`, itself an O(n) linear scan, up to `allowListBasedAuthRetryCount = 10` times with `allowListBasedAuthRetryInterval = 3s` sleeps between attempts [8](#0-7) [9](#0-8) .
- Any client (unprivileged, no allowlisting required) can trigger the full worst-case 10-retry/30-second path simply by sending a vault request whose digest is not allowlisted — this is the normal "not authorized" flow, not an edge case, since `AuthorizeRequest` is called before authorization succeeds.
- This mirrors the referenced bug class: a semi-trusted external party (here, any workflow owner who can permissionlessly register allowlist entries on-chain, analogous to a "RESTRICTED" admin in the report) can grow an array without bound that a critical, request-path function is forced to fully iterate, degrading or denying service to legitimate protocol users.

### Impact Explanation
As the allowlist grows (through normal onboarding of workflow owners, or an actor deliberately registering many transient allowlist entries), the CPU cost and latency of `AuthorizeRequest` for every vault RPC grows linearly, and the worst case (unauthorized/unknown digest) grows to `10 × O(n)` scans plus up to 30 seconds of enforced sleep per request. Since this authorization path sits in front of secret create/list/delete operations, this can meaningfully degrade Vault Gateway/DON throughput and latency for all users, and in the extreme can starve legitimate authorized requests of CPU time or hold connections open long enough to exhaust concurrency limits — a denial-of-service on a security-critical, internet-facing gateway path.

### Likelihood Explanation
The `AuthorizeRequest`/allowlist-scan path is the default authentication path for any client that does not present a JWT, making it directly reachable by unprivileged, unauthenticated callers. Growing the list requires only ordinary permissionless interaction with the `WorkflowRegistry` contract (adding allowlist entries for one's own workflow), which is a normal, expected on-chain action rather than a privileged one — unlike the panprog counter-argument in the source report (where triggering the bug required unusual, protocol-abusive admin behavior), here the abuse condition is closer to "normal use at scale," increasing realistic likelihood.

### Recommendation
- Replace the linear scan with a keyed lookup (e.g., `map[digest]allowlistedRequest`) so authorization is O(1) regardless of allowlist size.
- Cap the total number of allowlist entries retained in memory (and/or enforce per-owner limits), pruning aggressively and rejecting/erroring when the on-chain total exceeds a sane bound, similar to `MaxChannelsPerAdder` limiting seen elsewhere in this codebase.
- Avoid building the full `allowedRequestsStrs` debug listing on every attempt in the hot path; only construct it lazily when debug logging is actually enabled.
- Reconsider making the retry loop's 3-second sleep × 10 attempts unconditional for every unauthorized request; short-circuit or apply backoff/rate limiting per requester to avoid amplification.

### Proof of Concept
1. An unprivileged actor repeatedly registers "own-workflow" allowlist entries on the `WorkflowRegistry` contract over time (a normal, permissionless action), driving `totalAllowlistedRequests` and thus `workflowRegistry.allowListedRequests` to a very large size (e.g., hundreds of thousands of entries) — nothing in `syncAllowlistedRequests`/`getAllowlistedRequests` prevents this [3](#0-2) .
2. Any client sends a vault JSON-RPC request (e.g., `secrets/list`) without a JWT and with a digest that is not in the allowlist.
3. `AuthorizeRequest` → `findAllowlistedItemWithRetry` performs 11 full O(n) scans of the allowlist (once per retry attempt, `retryCount+1`), each also building an O(n) debug string, interleaved with 10 × 3-second sleeps, before finally returning "request not allowlisted" [10](#0-9) .
4. Repeating step 2 concurrently from multiple clients multiplies the CPU cost of these O(n) scans and ties up gateway/node handling resources for ~30 seconds per request, degrading service for legitimate, properly-allowlisted requests.

func (w *workflowRegistry) syncAllowlistedRequests(ctx context.Context) {
	ticker := w.getTicker(defaultTickIntervalForAllowlistedRequests)
	w.lggr.Debug("starting syncAllowlistedRequests")
	for {
		select {
		case <-ctx.Done():
			w.lggr.Debug("shutting down syncAllowlistedRequests, %s", ctx.Err())
			return
		case <-ticker:
			newAllowListedRequests, totalAllowlistedRequests, head, err := w.getAllowlistedRequests(ctx, w.contractReader)
			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			// Add new requests
			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)
			w.allowListedRequests = activeAllowlistedRequests
			w.lastSeenAllowlistedRequestsCount = totalAllowlistedRequests
			w.lggr.Debugw("synced allowlisted requests",
				"newRequestsNum", len(newAllowListedRequests),
				"expiredRequestsNum", expiredRequestsCount,
				"activeRequestsNum", len(w.allowListedRequests),
				"lastSeenOnchainRequestsNum", w.lastSeenAllowlistedRequestsCount,
				"blockHeight", head.Height,
			)
			w.allowListedMu.Unlock()

func (w *workflowRegistry) GetAllowlistedRequests(_ context.Context) []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (r *allowListBasedAuth) fetchAllowlistedItem(allowListedRequests []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, digest [32]byte) *workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	for _, item := range allowListedRequests {
		if item.RequestDigest == digest {
			return &item
		}
	}
	return nil
}

func (a *authorizer) authorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	// Requests without req.Auth continue using the allowlist-based path for backwards compatibility.
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
	if req.Auth == "" {
		return a.authorizeAllowListBasedAuth(ctx, req)
	}
	return a.authorizeJWTBasedAuth(ctx, req)
}
