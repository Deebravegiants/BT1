### Title
Missing length validation on `Message.from` causes a slice/arithmetic-underflow panic in `hyper-fungible-token::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The free5gc CVE is a class of bug where a length-prefixed identity field taken from an untrusted, attacker-supplied message is used to index/slice memory without validating its length first, producing an out-of-bounds/overflow read. In Hyperbridge's `hyper-fungible-token` pallet, the ISMP module handler `on_accept` decodes an attacker-controlled `Message` from the incoming cross-chain request body and validates the length of `message.to` (`to_bytes.len() == 32`/`== 20`, else `Err(HftError::InvalidRecipientLength)`), but never validates the length of `message.from` before it is sliced.

### Finding Description
`Message` is an ABI-decoded struct whose `from` field is an arbitrary-length `bytes` value fully controlled by whoever encodes the token-transfer payload on the source EVM chain, [1](#0-0) . When the message carries non-empty `data` (a calldata field executed on the destination) and the calldata's signature is absent, the destination pallet derives the effective calling origin from `message.from`: [2](#0-1) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else { ... }
```

`from_bytes.len() - 20` is computed with no prior check that `from_bytes.len() >= 20`. If `source` is an EVM state machine and the attacker crafts a `Message` where `from` is shorter than 20 bytes (including empty), the subtraction underflows: in debug builds this panics directly on subtraction overflow, and in release (wrapping) builds it produces a huge `usize` that is then used as a slice start index, which panics with an index-out-of-bounds error in `&from_bytes[...]`. This is functionally the same defect pattern as the CVE: a length field from an externally supplied identity/message is trusted implicitly and used to compute a slice bound, causing an overflow instead of a validation error.

By contrast, `message.to` is validated with an explicit length check just above (`to_bytes.len() == 32`/`20`, else return `HftError::InvalidRecipientLength`) [3](#0-2) , confirming that `from` was simply missed, not intentionally exempted.

### Impact Explanation
This code path executes inside `IsmpModule::on_accept`, which is invoked automatically by the pallet-ismp message-delivery machinery whenever `dest` module id resolves to this pallet and the request payload is decoded — i.e. it is reachable by any single relayed cross-chain PostRequest carrying a token/message from a registered source contract, provided the request also carries non-empty, unsigned `data`. A crafted `from` field shorter than 20 bytes causes the dispatchable to panic. In Substrate, an unhandled panic inside pallet logic invoked from `on_accept` during extrinsic execution will abort/trap that transaction (or, depending on how ISMP handling wraps panics, could be caught by the runtime's panic handler as a failed extrinsic, or in the worst case affect the executing worker). At minimum, it lets an attacker permanently block the delivery of a message/transfer that would otherwise legitimately mint or transfer funds for the intended beneficiary, since the message can never be processed successfully once it triggers a panic — a "route unable to deliver messages" condition explicitly covered by the report's acceptance criteria. It also risks destabilizing block execution for the batch of ISMP messages being processed together.

### Likelihood Explanation
High likelihood: `from` originates directly from ABI-decoded request body bytes that are fully attacker-chosen (any sender able to get a PostRequest routed to this pallet's module id from a registered source contract can set `from` to any byte string, including zero-length), and the vulnerable branch (`data` non-empty, no signature) is reachable without any privileged capability — it only requires crafting the calldata payload of an otherwise normal token transfer. No consensus proof forgery or governance/admin action is required, only a single relayed message.

### Recommendation
Validate `message.from.len()` before using it to index, mirroring the existing check on `message.to`:
```rust
let from_bytes = message.from.as_ref();
let origin = if let Some(signature) = substrate_data.signature {
    ...
} else if source.is_evm() {
    if from_bytes.len() < 20 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?;
    }
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?;
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
```
Return a proper `HftError` variant instead of allowing the slice/subtraction to panic.

### Proof of Concept
1. Register a token/contract mapping so `ContractToAsset::<T>::get(source, &from)` resolves for a chosen EVM `source` and attacker-controlled `from` (the "from" of the PostRequest header, not the message field) — standard for any legitimate cross-chain token route.
2. Craft an ABI-encoded `Message` body where the `Message.data` (`SubstrateCalldata`) field is non-empty, `substrate_data.signature` is `None`, and `Message.from` is set to `0` bytes (or any length `< 20`).
3. Relay this PostRequest to the destination chain's pallet-ismp `handle`/`handle_unsigned` path so it reaches `hyper-fungible-token::on_accept`.
4. Execution reaches `&from_bytes[from_bytes.len() - 20..]` at [4](#0-3)  with `from_bytes.len() == 0`, triggering an arithmetic-underflow/slice-index panic instead of a graceful `Result::Err`.
