This confirms the vulnerability: the `shop` field returned by `ShopifyAPI::Webhooks::Request#shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never included in the HMAC-signed payload. `to_signable_string` in `lib/shopify_api/webhooks/request.rb` only returns `@raw_body`, while `shop` is read straight from an unauthenticated header via `shopify_header("shop-domain")`. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` verifies only `Utils::HmacValidator.validate(request)` (body HMAC) and then forwards `request.shop` unchecked into `WebhookMetadata`, which host apps use as the tenant identifier per `docs/usage/webhooks.md`.

### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant/tenant identity (`shop`) from the `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Webhooks::Registry.process` only covers the raw request body (`to_signable_string` returns `@raw_body`). Since the `shop` field is not bound to the signature, an attacker who can obtain one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — which they trivially can, by owning/installing the app on their own store and receiving legitimate webhook deliveries to an endpoint they control — can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header value. The gem will treat the forged request as fully authentic and pass the attacker-chosen shop through to the handler as `WebhookMetadata#shop`.

### Finding Description
The identity binding that should hold is:
`shop domain acted upon by the handler` == `shop domain covered by the verified HMAC`

In practice:
- `Request#shop` reads `shopify_header("shop-domain")` [1](#0-0) , a raw, attacker-controlled HTTP header.
- `Request#to_signable_string` (used by `HmacValidator`) returns only `@raw_body`, never the headers [2](#0-1) .
- `HmacValidator.validate` computes/compares the HMAC purely against `to_signable_string`, i.e. body-only [3](#0-2) .
- `Registry.process` gates entirely on this body-only HMAC check, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler [4](#0-3) .

Because `shop-domain` is excluded from the signed bytes, "HMAC verified" does not imply "shop header authentic." An attacker who legitimately installs the app on their own store (or otherwise obtains one valid signed webhook body, e.g. by triggering an `orders/create` event on a store they control) captures a genuine `(raw_body, x-shopify-hmac-sha256)` pair signed with the real `client_secret`. They can then POST that identical body/HMAC to the app's webhook endpoint with `x-shopify-shop-domain` rewritten to a victim shop. `HmacValidator.validate` still succeeds (it never looks at the shop header), so `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting the victim's domain [5](#0-4) . Per the gem's own documentation, host apps are expected to key their persistence/business logic directly off `data.shop` [6](#0-5) , so this forged value is trusted end-to-end as the tenant identifier.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: any party capable of obtaining a single validly-signed webhook (trivial for anyone who can install the app, which for public apps is any merchant) can inject data attributed to an arbitrary other shop into the host application, since the gem provides no primitive to verify `shop` is bound to the signature. This is a cross-tenant integrity/confusion issue in the authentication boundary the gem exposes (`Registry.process`/`HmacValidator`), which apps rely on as their sole webhook authenticity check.

### Likelihood Explanation
High likelihood for any app that is installable by multiple merchants (the common case for public Shopify apps): obtaining one legitimately-signed webhook body is as easy as installing the app on a store you control and triggering the relevant event, no secrets or privileged access required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise assert that `request.shop` matches an app-known/expected shop (e.g., a shop with an active session/install) before trusting it. At minimum, update `VerifiableQuery`/`to_signable_string` for webhooks to incorporate the shop domain, or have `Registry.process`/`HmacValidator` reject requests whose `shop-domain` header cannot be independently corroborated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers `orders/create`, capturing the legitimate webhook POST: body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the real `client_secret`).
2. Attacker replays: `POST /webhooks` with body `B`, headers `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `HmacValidator.validate` succeeds because it only checks `B` against `H` [7](#0-6) .
4. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` [8](#0-7) , and the host app processes attacker-supplied `orders/create` data as belonging to `victim-shop.myshopify.com`.
