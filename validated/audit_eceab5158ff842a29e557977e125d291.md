### Title
Solver selection authorizes a solver address, not a bid's output amounts, letting the selected solver downgrade to the order floor after winning the auction - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The Teller `lenderAcceptBid` bug is a mismatch between what a counterparty reviews/accepts and what is cryptographically bound at acceptance time: the lender sees committed collateral but `lenderAcceptBid` never checks it, letting the borrower silently swap in worse terms right before acceptance. Hyperbridge's Intent Gateway auction has the same shape: the user selects a winning solver based on an off-chain bid's *output amount*, but the on-chain authorization (`SelectSolver`) only binds `(commitment, solver)` — not the amount the solver actually promised.

### Finding Description
`SELECT_SOLVER_TYPEHASH = keccak256("SelectSolver(bytes32 commitment,address solver)")` [1](#0-0)  is the only thing the user's session key signs to authorize a winning bid. It does not include the `FillOptions.outputs` (the amount the solver offered).

`select()`/`_select()` recovers the session key from this signature and stashes only the `(commitment, solver)` binding in transient storage; `fillOrder()` later checks the caller matches that stored authorization: [2](#0-1) . There is no comparison anywhere against the specific output amount the solver bid.

The only floor enforced at fill time is the order's own fixed `output.assets[i].amount` (set once by the user at `placeOrder`, not the bid amount):
- Same-chain: `_fillSameChain` only requires `solverAmount` to cover `totalRequired` (the order minimum) to avoid `InvalidInput`, treating anything above as optional "surplus" split with `surplusShareBps` [3](#0-2) .
- Cross-chain: `_fillCrossChain` has the identical `solverAmount < totalRequired` check and surplus split [4](#0-3) .

Off-chain, the auction and bid-selection flow presents users/executors with `FillerBid`/`Bid` objects carrying specific `outputs`, and the user's `SelectSolver` signature is meant to pick the best one [5](#0-4) . But because the signed message only names the solver address and the order commitment, that same signature authorizes *any* `fillOrder` call from that solver for that commitment — including one using a different `FillOptions.outputs` than the bid the user reviewed. `SolverAccount.validateUserOp` confirms the binding is only over `(commitment, solver)` (via the nonce-key check) and the solver's own signature over `userOpHash`, with no cross-check against a previously-bid amount [6](#0-5) .

Because bids can also be updated/replaced on the coprocessor pallet up until selection (`filler_can_update_own_bid`) [7](#0-6) , and the winning solver's own delegated `SolverAccount` constructs its own `fillOrder` calldata at execution time, a solver that was selected because it advertised a generous output can execute with only the bare order minimum, keeping the difference itself instead of it flowing to the user (or being split as protocol/beneficiary surplus). This is functionally identical to the Teller pattern: the accept/select action is decoupled from the specific terms it was supposed to lock in.

### Impact Explanation
A selected solver can unilaterally reduce its delivered output from the advertised competitive bid down to the order's bare floor (`order.output.assets[i].amount`) without breaking any on-chain check, pocketing the promised premium that legitimately belonged to the order placer/beneficiary. Since users choose which solver to authorize specifically because of the superior amount in a bid, this breaks the economic guarantee of the auction and is a direct value-extraction vector against order placers, reachable by any solver that can win selection — a single relayed/authorized transaction (the solver's own `fillOrder` UserOp).

### Likelihood Explanation
Any solver can exploit this on every order it wins by simply constructing its execution `FillOptions.outputs` at the order-floor amount rather than its bid amount — no race condition, mempool front-running, or special privilege required, since the vulnerability is a structural gap in what the selection signature covers rather than a timing window. It requires no cooperation from the user and no cross-chain proof forgery, only that the solver be the one selected, which is the normal, expected outcome of the auction it is participating in.

### Recommendation
Bind the `SelectSolver` EIP-712 message (and/or the transient-storage record checked in `fillOrder`) to the exact output amounts the solver bid, e.g. `SelectSolver(bytes32 commitment, address solver, bytes32 outputsHash)`, and have `fillOrder` reject `FillOptions.outputs` that hash differently (or that are below the amount included in the authorized selection) from what the user actually selected. Alternatively, remove the option for the selected solver to independently choose `FillOptions.outputs` post-selection and instead pass the bid's committed outputs through as part of the authorized selection payload.

### Proof of Concept
1. User places an order requiring `order.output.assets[0].amount = 900 DAI`.
2. Two solvers bid via `place_bid` on the intents-coprocessor: Solver A bids `outputs = 950 DAI`, Solver B bids `outputs = 900 DAI`.
3. The user reviews bids off-chain and picks Solver A (best price), signing `SelectSolver{commitment, solver: A}` — a signature that only names the order and Solver A's address [1](#0-0) .
4. Instead of submitting the UserOp it bid with, Solver A constructs a fresh `fillOrder` call with `FillOptions.outputs = [900 DAI]` (the order minimum) and its own signature over that `userOpHash`.
5. `SolverAccount.validateUserOp` accepts it: the nonce key and session signature only bind `(commitment, solver)`, and the solver's own signature is over its own new `userOpHash` [6](#0-5) .
6. `fillOrder`/`_fillSameChain` accepts `solverAmount = 900 == totalRequired`, no surplus, no revert [3](#0-2) .
7. Solver A wins the order at the losing bidder's (900 DAI) price while having been selected on the strength of its higher (950 DAI) bid, capturing the 50 DAI difference it never actually had to pay.

### Bid

A first-class, executable solver bid surfaced via the `NEW_BID` and `BIDS_RECEIVED` status updates. Each `Bid` wraps a single decoded `FillerBid` and exposes the metadata needed to rank it alongside the two primitives required to act on it: `simulate()` to pre-check it off-chain, and `execute()` to sign the solver selection and submit the UserOperation to the bundler.

interface Bid {
  /** The solver account that submitted this bid (`userOp.sender`). */
  readonly solverAddress: HexString
  /** Decoded fill outputs — the tokens and amounts the solver offers. */
  readonly outputs: TokenInfo[]
  /** Relayer fee from the decoded fill options. */
  readonly relayerFee: bigint
  /** Hyperbridge native dispatch fee from the decoded fill options. */
  readonly nativeDispatchFee: bigint
  /** Raw UserOperation for advanced consumers (custom batching, paymaster flows). */
  readonly userOp: PackedUserOperation

  /** Runs the batched `select` + `fillOrder` `eth_call` simulation. Throws if it reverts. */

  /** Signs the `SelectSolver` message, packs the signature, and submits the UserOp to the bundler. */
  execute(): Promise<SelectBidResult>
  /** Prices the bid's outputs in USD. Returns `null` when any output token cannot be priced. */
