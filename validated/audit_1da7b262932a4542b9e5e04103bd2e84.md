### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant impersonation of the sending shop - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking `Utils::HmacValidator.validate(request)` [1](#0-0) , but the HMAC is computed only over the raw request body, not over the `shop`, `topic`, `api_version`, or `webhook_id` header values [2](#0-1) . The `shop` value that is subsequently trusted and handed to the app's webhook handler is read straight from an unauthenticated header [3](#0-2)  and is not cryptographically bound to the signed body.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field with a constant-time compare [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers with no cryptographic link to the signature [5](#0-4) .

`Registry.process` validates only the HMAC of the body and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler [6](#0-5) .

The identity binding that should hold is: `shop asserted in the authenticated webhook == shop that produced the signed body`. Because `shop` is excluded from the signed content, this equality does not hold — the shop header can be swapped for a different value while the HMAC over the (unchanged) body remains valid. Anyone who can obtain one genuine `(body, hmac)` pair signed with the app's shared secret (e.g., by installing the app on their own store and capturing a real webhook Shopify sends them, or via a legitimately-received test webhook) can resend that exact `body`/`hmac` pair to the app's webhook endpoint while substituting the `shop` (and `topic`/`webhook-id`) header with an arbitrary victim shop domain. `HmacValidator.validate` will report the request as valid, because it only checks the body's HMAC, not the origin/topic binding, and the app's handler will process the payload attributing it to the attacker-chosen `shop`.

### Impact Explanation
This crosses the tenant boundary the HMAC check is meant to enforce: a request that only proves "this body was HMAC-signed with our shared secret" is treated as proof of "this event happened for shop X." A host application that keys session/token lookups, data writes, or business logic off `WebhookMetadata#shop` (the documented, expected usage of this gem's webhook API) can be made to act as if an event occurred for a shop that never sent it, and with a payload that never mentioned that shop. Depending on the topic replayed (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or order/customer topics), this enables cross-tenant data corruption, forced session/token deletion for a victim's shop, or processing of another tenant's data under an attacker-chosen shop identity — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one real `(raw_body, hmac)` pair produced by the app's own secret — trivially available to anyone who installs the target app on their own development/trial store and receives a genuine webhook, or to any user who can capture a webhook their own tenant already legitimately received — and (2) POSTing that same body/hmac pair directly to the app's public webhook endpoint with a different `shopify-shop-domain` header. No access to `api_secret_key`, access tokens, or `client_secret` is needed. This does not depend on the host application ignoring documented behavior; it is inherent to how `Webhooks::Request`/`Registry` construct and validate the signable content in this gem.

### Recommendation
Include the `shop` domain (and ideally `topic`) in the value that is HMAC-verified, or otherwise cryptographically bind the asserted shop to the signed payload before it is exposed via `WebhookMetadata`. At minimum, document and/or enforce that consumers of `WebhookMetadata#shop` must cross-check it against a shop known independently (e.g., an existing installed-app session) rather than treating it as authenticated purely because `Registry.process` did not raise.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and captures one legitimate webhook delivery, e.g. `orders/create`, giving them a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's real `api_secret_key`.
2. Attacker sends a POST directly to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256`: the captured, still-valid HMAC
   - body: the exact same captured `raw_body`
   - `x-shopify-shop-domain`: `victim.myshopify.com` (swapped from `attacker.myshopify.com`)
   - `x-shopify-topic`: unchanged or swapped to another registered topic
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body` [2](#0-1) [7](#0-6) .
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the attacker-controlled `victim.myshopify.com` value [8](#0-7)  and invokes the app's handler as if the event genuinely originated from the victim shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
