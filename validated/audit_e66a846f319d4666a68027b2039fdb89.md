## Title
Webhook shop-domain/topic identity spoofing via HMAC that only covers the raw body, not the headers used for tenant routing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC signature it checks is computed only over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are handed to the app's webhook handler as trusted identity fields without ever being covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates that signable string against the HMAC header and, if it passes, immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all parsed straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`request.shop`, `request.topic`, and `request.webhook_id` are simple header lookups: [3](#0-2) 

The equality the app relies on is: `HMAC-valid(raw_body) == HMAC-valid(shop-domain header, topic header, webhook-id header, raw_body)`. That equality is false — the verified bytes (`raw_body`) and the bytes acted on for tenant routing (`shop-domain` header) are disjoint. The gem's `api_secret_key` (`client_secret`) is shared across every shop that installs the app, so any merchant who has legitimately installed the app can capture a genuinely-signed `(raw_body, hmac)` pair from their own store's webhook deliveries. Because the signature check never touches the `shop-domain`, `topic`, or `webhook-id` headers, that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with those headers rewritten to point at a different, victim shop, and it will still pass `Utils::HmacValidator.validate`.

The gem's own documentation reinforces that host apps are expected to rely on this check as full authentication of the request's origin and content ("This will verify the request did indeed come from Shopify"), not just body integrity: [4](#0-3) 

The resulting `WebhookMetadata` (topic/shop/body/webhook_id/api_version) is then handed directly to the host app's handler as trusted per-tenant data: [5](#0-4) 

### Impact Explanation
An unprivileged attacker who has installed the app on their own shop possesses a valid `client_secret`-signed body/HMAC pair for content they control (e.g., an order they created, with attacker-chosen note/customer/line-item fields). By replaying that exact body+HMAC to the app's public webhook callback URL while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim merchant's shop domain, the attacker causes the host app's handler to ingest attacker-controlled data as though it originated from the victim tenant. Depending on what the handler does with `data.shop`/`data.body` (e.g., looking up the victim's stored session/access token and writing/dispatching data against the victim's store, or triggering business logic keyed off `data.shop`), this is a cross-tenant data-integrity/authorization break: the "shop" identity the app treats as authenticated is not actually bound to the signed payload.

### Likelihood Explanation
Any user who can install the app (which for most public/multi-tenant Shopify apps just requires visiting the install URL) automatically receives real, validly-signed webhook payloads for their own store, giving them the exact HMAC/body pairs needed. No secret leakage, TLS interception, or privileged access is required — only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers, and to know/guess a victim's `*.myshopify.com` domain (routinely public knowledge). The webhook endpoint is deliberately publicly reachable by design.

### Recommendation
Bind the trust-sensitive routing fields (`shop`, `topic`, `webhook_id`) into the signed material, or otherwise verify them independently — e.g., include the `shop-domain` and `topic` header values in `to_signable_string`, or require the host app to compare `request.shop` against an already-established, session-derived shop before dispatching to a handler. At minimum, update the documentation so it does not claim the process step authenticates "the request" as opposed to just the raw body, and warn implementers that `data.shop`/`data.topic` are not covered by the HMAC and must not be trusted for tenant selection without an independent check (e.g., cross-referencing against a known set of shops that have completed OAuth for this app).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, completing OAuth normally.
2. Shopify sends a legitimately signed webhook (e.g., `orders/create`) to the app's callback URL for `attacker-shop.myshopify.com`; the attacker intercepts/records the raw POST body and the `x-shopify-hmac-sha256` header (both are visible to the attacker since it's their own inbound traffic / they can also trigger events like editing their own order to control body content).
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com` and (if desired) altering `x-shopify-topic`/`x-shopify-webhook-id`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only re-computes the HMAC over `raw_body`, which is unchanged; `Registry.process` proceeds to call the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`.
5. The host app's handler processes attacker-controlled data believing it is authoritative data from `victim-shop.myshopify.com`.
