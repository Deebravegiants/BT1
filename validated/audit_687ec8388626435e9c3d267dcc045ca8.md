### Title
Webhook `shop` attribution is not covered by HMAC, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::HmacValidator` authenticates a webhook solely by validating the HMAC over the raw request body, while the `shop` value that the gem hands to the app's handler (and that the docs tell developers to trust as "the shop domain of the webhook") is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [4](#0-3) 

`Request#shop` is a separate accessor pulled straight from request headers, entirely independent of the signed payload: [5](#0-4) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) using the app's shared `api_secret_key`/`old_api_secret_key`, and returns true/false purely based on that body signature — it never touches `shop`: [6](#0-5) 

`Registry.process` uses that boolean gate, then immediately trusts `request.shop` (header-derived, unauthenticated) as the tenant identity forwarded to the handler: [2](#0-1) 

The equality the code implicitly assumes is:
`shop_bound_by_hmac == shop_delivered_to_handler`

but in reality:
`shop_bound_by_hmac = ∅` (the signable string has no shop field)
`shop_delivered_to_handler = header["shopify-shop-domain"]` (fully attacker-controllable)

Because `api_secret_key` is a single per-app secret shared across every merchant install of the app (not a per-shop secret), any merchant who installs the app can trigger events in their *own* store, capture the resulting validly-signed webhook (valid body + valid HMAC), and replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid for that app secret), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` — attributing the (attacker's own, but now relabeled) data/event to the victim shop.

### Impact Explanation
This lets an attacker who controls one tenant (a normal, unprivileged install of the app) cause the host application to process webhook data under a different, victim tenant's identity — a cross-tenant confusion/access vulnerability. Depending on what the host app's handler does with `data.shop` (e.g., look up/update the victim's stored session, trigger GDPR redaction logic like `shop/redact`, `customers/redact`, `customers/data_request`, or update per-shop business records), this can lead to cross-tenant data corruption or disclosure keyed off the spoofed shop identity, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any developer following the gem's own documented pattern (`docs/usage/webhooks.md`) is exposed, since the doc explicitly instructs handlers to key logic off `data.shop` without warning that it is unauthenticated. The only requirement to exploit is an app install (any merchant can install a public app), no special privilege, TLS interception, or leaked secret is required — only crafting an HTTP request with a forged `shopify-shop-domain` header alongside a previously-observed valid `(body, hmac)` pair for that same app.

### Recommendation
Bind the `shop` value into the signed material (e.g., include it, along with `topic`/`webhook_id`, in `to_signable_string`), or otherwise verify server-side that the `shop` claimed by the header is one for which an active, previously-established session/installation exists before trusting it for any tenant-scoped action. At minimum, the gem's docs and `WebhookMetadata#shop` should be updated to make clear that `shop` is unauthenticated header data and must not be trusted for authorization decisions without independent verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally (no special privilege).
2. Attacker triggers an event (e.g., updates a product) causing Shopify to deliver a webhook to the app's callback URL with body `B` and header `shopify-hmac-sha256: H` (valid signature over `B` using the app's shared secret) and `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker records `(B, H)` and replays a new HTTP POST to the same webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but setting `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B) == H`, which still holds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, causing the host application to process attacker-supplied data as if it originated from the victim shop.
