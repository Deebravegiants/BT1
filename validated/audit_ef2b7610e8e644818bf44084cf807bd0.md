### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read from separate, unsigned HTTP headers. `Registry.process` accepts any request whose body HMAC validates against the app's shared secret, then forwards the unauthenticated `shop` header value straight into the handler's `WebhookMetadata`. This breaks the expected binding `HMAC-verified payload == (shop, topic, webhook_id) trusted by the handler`, letting anyone who possesses one validly-signed webhook body/HMAC pair (e.g., from their own shop) relabel it as belonging to a different, victim shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only `@raw_body` is included in the signable string. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

The constructor only checks that the required headers are *present*, not that they are consistent with anything signed: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` verify the HMAC purely against `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key` — the same secret is shared across every shop installed on the app, it is not shop-specific: [4](#0-3) 

`Registry.process` only checks this body HMAC, then dispatches the handler using the unauthenticated `request.shop` value: [5](#0-4) 

Because the secret is shared across shops and the signature covers only the body, an attacker who controls (or operates) their own shop on the app can obtain a legitimately-signed webhook (valid body + `x-shopify-hmac-sha256`) from Shopify for their own store, then replay that exact body/HMAC pair to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a different, victim shop. `HmacValidator.validate` still succeeds (it never looks at the shop header), so `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim shop while the `body` is entirely attacker-controlled content from the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the field the handler trusts to select *which tenant's* data to create/update/delete (`shop`) is not part of the authenticated payload. Any app whose webhook handlers key persistence, authorization, or side effects off `WebhookMetadata#shop` (as the library's own docs and tests demonstrate, e.g. `data.shop`) can be made to apply attacker-supplied webhook bodies against another merchant's tenant, since the webhook endpoint is a public, unauthenticated internet-facing endpoint by design. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be a legitimate merchant with the vulnerable app installed on their own shop (no `api_secret_key`, access token, or TLS interception required) to obtain one validly signed webhook body/HMAC pair for their own store, then POST it to the app's public webhook endpoint with a forged `shopify-shop-domain` header. Nothing in `Request` or `Registry.process` cross-checks the header against the signed content.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable/verified material (or otherwise cryptographically bind them to the HMAC, e.g. by having `to_signable_string` canonicalize headers+body), and reject requests where the header values don't match what was actually signed by Shopify. At minimum, `Registry.process` should not trust `request.shop` for tenant selection unless it has been verified as bound to the HMAC-covered payload.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with attacker-controlled order content; Shopify delivers it to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `api_secret_key`.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` value from that delivery.
3. Attacker sends a new POST to the same webhook endpoint reusing the identical raw body and `x-shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and matching `topic`/`webhook_id` headers as desired).
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-31`) recomputes the HMAC over the unchanged body and it matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds and calls the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's data> ...)`, causing the app to process attacker-controlled content under the victim shop's tenant identity.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
