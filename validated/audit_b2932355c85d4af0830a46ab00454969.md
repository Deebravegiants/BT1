### Title
Unprivileged supply/borrow can push a large market past the i128 RAY-value ceiling, permanently freezing all pool operations before the borrow-index cap engages - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` unscales the market's scaled borrow and supply totals with `scaled_to_original`, which performs `scaled * index / RAY` via panicking fixed-point multiplication. On a sufficiently large book (reachable in one `supply`/`borrow` by a single unprivileged address on a high-decimal, high-supply token), index growth makes `borrowed * borrow_index` overflow `i128` before `update_borrow_index` can clamp the index to `MAX_BORROW_INDEX_RAY` (`10^36`). Since every state-mutating pool path synchronizes indexes first, the entire market — withdraw, repay, supply, borrow, liquidation, bad-debt cleanup, flash loans — reverts permanently with `MathOverflow`.

### Finding Description
Per accrual step, `accrue_step` computes utilization from unscaled totals:

- `contracts/pool/src/cache/scale.rs:23-24` and `common/src/rates/simulate.rs:60-61` call `scaled_to_original(env, borrowed, borrow_index)` / `scaled_to_original(env, supplied, supply_index)`.
- `common/src/rates/scaling.rs:14-16` implements `scaled_to_original` as `scaled.mul(env, index)`, which traps on i128 overflow (RAY values are `raw * RAY`, so a `10^18`-decimals token with ~1e9 whole units is already `1e36` ray-scaled; `i128::MAX ≈ 1.7e38` leaves only ~170x of index headroom).
- `update_borrow_index` (invoked at `common/src/rates/simulate.rs:66`) caps the index at `MAX_BORROW_INDEX_RAY`, but the unscale at lines 60-61 runs *before* the cap and on every subsequent step — so once `scaled * index` exceeds `i128::MAX` the panic happens first and the cap never engages.

The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-361`) demonstrates exactly this: after supplying `1e9` of an 18-decimal token and borrowing ~98%, repeated `update_indexes` eventually reverts with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and `try_withdraw_raw` and `try_repay` both revert with the same error — "no repay, no withdraw, no liquidation."

The setup uses only permissionless entrypoints: `controller.supply` (huge amount of the market token) and `controller.borrow` near `max_utilization`, then time plus permissionless `update_indexes`. No privilege, oracle manipulation, or external failure is required — only a token with enough supply/decimals that `amount * 10^(27-decimals)` scaled book times a reachable index exceeds `i128::MAX`. `calculate_scaled_cap` (`common/src/rates/scaling.rs:26-33`) explicitly documents that position accounting "panic[s] on overflow" and only listing-time `require_cap_within_asset_domain` guards caps, so a governance-approved cap can still admit a book large enough to hit the cliff at plausible index growth on the steep curve segment.

### Impact Explanation
Once crossed, the panic is permanent and total for that market: `global_sync` runs `accrue_step` at the head of every mutation, so suppliers can never withdraw, borrowers can never repay, liquidations and `clean_bad_debt` can never execute, and flash loans/revenue claims revert. This is permanent freezing of all funds in the market plus protocol insolvency risk on the un-liquidatable debt — within the accepted impact classes.

### Likelihood Explanation
Requires a market with large raw token scale (high decimals and/or large caps) and sustained high utilization so the borrow index compounds ~170x. This is a slow-burn condition rather than an instant attack, but it is fully reachable by a single unprivileged address via `supply`/`borrow` and permissionless `update_indexes`, needs no victim interaction or external failure, and cannot be undone once the overflow point is passed — any single accrual call that crosses the line bricks the market. Likelihood is constrained by needing a legitimately listed high-decimal, high-cap market, hence Medium.

### Recommendation
Order the index cap before the unscale: compute `new_borrow_index = min(borrow_index * factor / RAY, MAX_BORROW_INDEX_RAY)` first, then unscale with the capped index, or perform utilization on saturating arithmetic (`mul_div_floor_saturating` as `calculate_scaled_cap` already does). Additionally, enforce listing-time bounds so that `max_scaled_book * MAX_BORROW_INDEX_RAY / RAY` fits `i128` with margin, matching the documented numeric-limits guidance in `docs/reference/formulas.md`.

### Proof of Concept
1. Attacker calls `controller.supply` with ~`1e9` whole units of a listed 18-decimal token (scaled ≈ `1e36` ray).
2. Attacker calls `controller.borrow` to push utilization to ~98% on the steep rate segment.
3. Anyone calls `controller.update_indexes` periodically; each call runs `accrue_step`, multiplying `borrowed * borrow_index`.
4. When `borrow_index` growth would make the product exceed `i128::MAX` — before reaching `MAX_BORROW_INDEX_RAY` — `scaled_to_original` traps `MathOverflow`. All subsequent `supply`/`withdraw`/`repay`/`borrow`/`liquidate`/`clean_bad_debt`/`flash_loan` calls on that market revert identically, permanently. Confirmed by `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-361`.
