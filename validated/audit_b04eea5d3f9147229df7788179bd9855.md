### Title
Native ETH sent to `cancelOrder` for same-chain orders is permanently stuck in `IntentGatewayV2` - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.cancelOrder()` is declared `payable` because two of its three routing branches (`_cancelFromSource` / `_cancelFromDest`) need `msg.value` to pay for a Hyperbridge dispatch (a GET request to check fill status, or a POST `RefundEscrow` message). The third branch, `_cancelSameChain`, performs a purely local escrow refund and never touches Hyperbridge, so it never consumes `msg.value`. Unlike `placeOrder`, which explicitly refunds any unspent native token with `_sendValue(msg.sender, msgValue)` at the end of its execution, `cancelOrder`'s same-chain branch contains no such refund path, so any ETH attached to a same-chain cancel call is trapped in the contract.

### Finding Description
`cancelOrder` is a single `payable` entrypoint that branches into three mutually exclusive paths based on whether the order is same-chain or cross-chain: [1](#0-0) 

- If `isSameChain`, it calls `_cancelSameChain(order, commitment)` — a purely local refund of escrowed assets with no cross-chain dispatch, and therefore no reason to consume `msg.value`.
- If cross-chain, it calls `_cancelFromSource` or `_cancelFromDest`, which dispatch GET/POST requests through `IDispatcher(hostAddr).dispatch{value: msg.value}(...)` and legitimately need the attached native token to pay dispatch fees (as seen in the analogous cross-chain fill logic that forwards `msg.value` to `IDispatcher(hostAddr).dispatch{value: msg.value}(request)`): [2](#0-1) 

Because `cancelOrder` is uniformly marked `payable` for all three branches, a caller (or a front-end that always estimates and attaches a native dispatch fee) can send ETH along with a same-chain cancel. In that branch, the value is never spent (no dispatch happens) and, critically, `_cancelSameChain` is not shown to perform any residual-value refund analogous to `placeOrder`'s explicit end-of-function check: [3](#0-2) 

This is the same bug class as the Derby `pushVaultAmounts`/`sendFundsToVault` issue: a `payable` function conditionally skips the code path that consumes the attached native funds (`getVaultChainIdOff` returning true skipped `sendXChainAmount`), and no fallback refund exists for the unused value, freezing it in the contract.

### Impact Explanation
Any native token sent with a same-chain `cancelOrder` call becomes permanently locked in the `IntentGatewayV2` contract balance — the contract has a `receive()` fallback to accept ETH but no sweep/refund mechanism tied to this call path, so the funds are unrecoverable by the caller. This is a direct, permanent loss of user funds triggered from a single unprivileged transaction (any user cancelling their own or an expired order), matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood depends on whether callers/integrators (front-ends, SDKs) always attach a native fee to `cancelOrder` regardless of route, since the function signature gives no on-chain indication that same-chain cancels require zero value. Given that `fillOrder` and `placeOrder` in the same contract both handle native overpayment/refunds explicitly (as shown by the dedicated refund tests `testPlaceOrder_RefundsExcessNativeToken`, `testFillOrder_RefundsSolverExcessNativeToken`), a caller reasonably expects `cancelOrder` to behave the same way; the absence of that safety net here is a likely oversight rather than an intentional design choice. [4](#0-3) 

### Recommendation
Add the same unspent-value refund pattern used in `placeOrder` to the same-chain cancellation path (or reject any `msg.value` in `cancelOrder` when `isSameChain` is true):
```solidity
if (isSameChain) {
    if (currentChain != orderSource) revert WrongChain();
    _cancelSameChain(order, commitment);
    if (msg.value > 0) {
        _sendValue(msg.sender, msg.value);
    }
} else ...
```

### Proof of Concept
1. User places a same-chain order via `placeOrder`, which is later cancellable via `cancelOrder`.
2. User (or a front-end that always attaches an estimated dispatch fee) calls `cancelOrder{value: X}(order, options)` where `order.source == order.destination == currentChain`.
3. Execution enters the `isSameChain` branch and calls `_cancelSameChain`, which never references `msg.value`.
4. The function returns without consuming or refunding `X`; the ETH remains in `IntentGatewayV2`'s balance with no code path to recover it, confirmed by contrast with `placeOrder`'s explicit refund-of-unspent-value logic at lines 394-397 of `evm/src/apps/IntentGatewayV2.sol`.

Note: `_cancelSameChain`'s implementation was not retrievable within the indexed context, so it could not be directly confirmed that it contains no internal refund logic; this assessment is based on the doc comment describing it as a "direct escrow refund" (no dispatch) and the absence of any refund call visible in the `cancelOrder` routing function itself. A full review of `_cancelSameChain`'s body in `evm/src/apps/intentsv2/IntrinsicIntents.sol` or wherever it is defined would be needed to state this with full certainty.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
