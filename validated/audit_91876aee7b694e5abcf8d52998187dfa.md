### Title
`RequestState` handler in the Orb-Relay client replays the last cached signup-state message to any sender regardless of session identity - ([File: orb-relay-client/src/client.rs])

### Summary
`PollerAgent::main_loop` in `orb-relay-client/src/client.rs` validates that incoming relay payloads originate from the expected counterpart (`src.id == self.config.dst_id`) before processing them — except for one message type, `self_serve::app::v1::RequestState`. When a `RequestState` payload is received, the client immediately replays `self.last_message` (the last outgoing signup-state message, e.g. `AnnounceOrbId` / `SignupEnded`) to the sender **without ever checking `src.id` against `self.config.dst_id`**. This mirrors the PoolTogether `permitAndMulticall()` root cause: an authorization/identity check (`_from == msg.sender`, here `src.id == dst_id`) that gates a sensitive action is skipped for one code path, allowing the action to be performed on behalf of/for an unverified party.

### Finding Description
In `orb-relay-client/src/client.rs`, the main receive loop is: [1](#0-0) 

```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
```

For every other payload type, the client enforces that the message's `src.id` equals the configured `dst_id` — i.e., the identity bound to this session/channel at connect time (see `Client::new_as_orb`/`new_as_app`, which set `src_id`/`dst_id` from `orb_id`/`session_id` or `orb_relay_app_id`) [2](#0-1) . This check exists specifically to prevent a party who is not the expected session counterpart from being treated as trusted input.

The `RequestState` branch bypasses that check entirely: any entity that can deliver a `RequestState` payload over this relay connection (regardless of the `src.id` field/session identity carried in the payload) causes the Orb/App client to resend its cached `last_message` — the last piece of signup state it sent out, which for the Orb side is the `AnnounceOrbId`/`SignupEnded` sequence carrying orb-id, mode, hardware type, and signup outcome (see usage in `do_signup`/`orb_relay_announce_orb_id`, `src/plans/mod.rs`) [3](#0-2) . Because `dst_id` for the orb-side client is populated from the backend-asserted `orb_relay_app_id` bound to the *current signup's* user QR code [4](#0-3) , the entire point of the `src.id` check is to keep state scoped to that one authenticated app/session. Skipping it for `RequestState` means state belonging to one signup session can be replayed to an unverified requester on the same relay stream, an analogous "trust the caller, not the verified identity" flaw to the Code4rena `_from`/`msg.sender` bug.

### Impact Explanation
This allows cross-signup/cross-session state bleed: a party that is not the verified session counterpart (`dst_id`) can trigger disclosure of the last signup-state payload (which signup succeeded/failed, orb identifiers, mode/hardware type) by simply sending a `RequestState` message on the shared relay channel, without the `src.id` gate that protects every other message type. In a system whose entire purpose is to bind one physical signup session to one authenticated app, this breaks that binding for this one message class and can misattribute or leak signup completion state to the wrong party.

### Likelihood Explanation
Likelihood depends on whether the relay backend enforces strict per-session routing of `src`/`dst` at the transport layer independent of the client library's own check. Because the client code explicitly re-validates `src.id != self.config.dst_id` for all other message types, this indicates the authors did not fully trust the relay server/transport to guarantee sender identity, and added this check as defense-in-depth — the `RequestState` branch is the sole path where that defense-in-depth is missing. This is a genuine logic bug in code that runs on every orb/app relay session, but exploitation requires an attacker able to inject a `RequestState` payload into the target's stream, which depends on relay-server-side authorization not visible in this repo.

### Recommendation
Apply the same `src.id == self.config.dst_id` check to the `RequestState` branch before replaying `last_message`, so that only the verified session counterpart can trigger a state resend:

```rust
if src.id == self.config.dst_id && self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. Establish a relay connection as an Orb (or App) client for session A, with `last_message` populated (e.g., after sending `SignupEnded`).
2. As a second relay participant not bound to session A's `dst_id` (e.g., attached to the same relay stream with a different/spoofed `src.id`), send a `self_serve::app::v1::RequestState {}` payload.
3. Observe in `PollerAgent::main_loop` (lines 436-440 in `orb-relay-client/src/client.rs`) that the check on `src.id != self.config.dst_id` is never evaluated for this payload type — `self.last_message` is sent back to the requester unconditionally, disclosing the last signup-state message regardless of the requester's identity. Contrast with any other payload type, which is correctly dropped when `src.id != self.config.dst_id` (line 441-445).

Note: I could not fully verify server-side (relay backend) enforcement of `src`/`dst` routing since that service is out of scope of this repository; if the relay server strictly enforces that only the paired counterpart's messages are ever delivered to a given stream, this becomes defense-in-depth only. This uncertainty should be resolved before treating this as independently exploitable in production.
