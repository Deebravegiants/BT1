### Title
Webhook HMAC does not cover the shop domain, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable value from the raw body alone, while `shop`, `topic`, `api_version`, and `webhook-id` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler. This breaks the identity binding: "shop that produced a Shopify-signed webhook" ≠ "shop attributed to the processed webhook data."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor simply reads the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with no cryptographic tie to the payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts the header-derived `request.shop` (and `topic`/`api_version`/`webhook_id`) to build the metadata passed into the app's handler: [3](#0-2) 

The HMAC in `HmacValidator.validate_signature` is computed with `verifiable_query.to_signable_string`, which for webhook requests is exactly the raw body, so it never binds the shop header: [4](#0-3) 

Because Shopify's HMAC for webhooks is computed over the body with the shared `client_secret` (server-side, not attacker-controlled), an attacker cannot forge an arbitrary body+HMAC pair for a shop they don't own. But an attacker who legitimately installs the app on their **own** store (an unprivileged, self-service action) will receive real Shopify-signed webhooks for that store — with a valid signature over the body. The attacker can then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it never inspects the shop header), and `Registry.process` will invoke the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own shop's payload>, ...)`.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive baked into the library: the gem asserts a webhook is authenticated for a given shop, but the “shop” value it hands to the app was never covered by the signature. Depending on the topics an app registers (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, `orders/*`), a host application that trusts the library's `shop` field to key session lookup, data deletion, or de-provisioning logic can be made to act on the wrong tenant — e.g. wiping/rotating session data or redacting data for a victim shop instead of the attacker's own shop. This matches the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only that the attacker install the target app on a shop they control (self-service, no privileged credentials) to obtain one legitimately-signed webhook body/HMAC pair, then send a forged HTTP request to the app's webhook endpoint with a spoofed `shop` header and the captured body/HMAC. No access to `api_secret_key`, tokens, or the victim's environment is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable material for webhook requests, or otherwise cryptographically bind the `shop` header to the signed body (e.g., validate it against Shopify's documented webhook headers used consistently with the signature, or require host apps to independently verify shop-webhook binding via topic-specific fields in the JSON body where Shopify includes them). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant-sensitive logic without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event (e.g., uninstalls the app) causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint:
   - Headers: `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{}` (or whatever Shopify sends for that topic).
3. Attacker captures this exact raw body and its `x-shopify-hmac-sha256` value.
4. Attacker replays the same request to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only ever hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the host app to run its `app/uninstalled` (or other topic) logic against the victim tenant.
