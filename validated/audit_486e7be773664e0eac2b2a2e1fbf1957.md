## Title
Underflow in `IntentsBase._withdraw` when accumulated `WithdrawalRequest` amounts exceed remaining per-token escrow, permanently freezing an order's escrow - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` decrements per-(commitment, token) escrow with `_orders[body.commitment][token] = escrowed - amount` after only checking `escrowed == 0`, never that `escrowed >= amount`. This mirrors the reported symio-core bug class: a balance-accounting subtraction that is only guarded against the zero case, not against the requested amount exceeding what remains, so any accounting mismatch between the amount encoded in a settlement/refund message and the actual remaining escrow reverts the transaction with an arithmetic underflow instead of failing gracefully.

### Finding Description
`_withdraw` is the single internal function used by both `RedeemEscrow` (fill settlement) and `RefundEscrow` (cancellation) paths, invoked from `onAccept` after a Hyperbridge cross-chain message is verified, and also from the same-chain `fillOrder`/`cancelOrder` flows in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`. [1](#0-0) 

For each token in the withdrawal request it does:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
``` [2](#0-1) 

Solidity 0.8's checked arithmetic means `escrowed - amount` reverts on underflow when `amount > escrowed`. The guard only checks `escrowed == 0`; it does not check `amount <= escrowed`. Any code path (or attacker-influenced value, e.g. a corrupted/adversarial fee-on-transfer accounting edge case, an off-by-rounding partial-fill split, or a bug in `IntrinsicIntents`/`ExtrinsicIntents` computing the withdrawal body) that produces a `WithdrawalRequest.tokens[i].amount` larger than the currently escrowed balance for that commitment/token will cause `_withdraw` to revert unconditionally, rather than clamp or fail with a descriptive error. This is exactly the same bug shape as the referenced Sherlock report: balance underflow due to missing a "requested amount cannot exceed remaining balance" check, only using a zero-check as the guard.

The consequence differs from the original report's "solver can't be liquidated" scenario but has the same structural root cause and severity class: a revert that makes escrow permanently unrecoverable for that path. Specifically, for cross-chain orders, `_withdraw` is called from `onAccept` after the settlement/refund message has already been verified and delivered by Hyperbridge — if it reverts, the entire message processing reverts, and since ISMP does not automatically retry a message whose execution reverted deterministically (the same commitment/amounts will always underflow the same way), the escrowed input tokens for that commitment become permanently stuck: they can never be released to the solver (RedeemEscrow) nor refunded to the user (RefundEscrow) once this condition is hit.

### Impact Explanation
If reachable, this results in **permanent freezing of escrowed user funds** on the source chain for the affected order: neither the solver settlement path (`RedeemEscrow`) nor the cancellation/refund path (`RefundEscrow`) can succeed, because both funnel through the same `_withdraw` function using the same `_orders[commitment][token]` state and the same non-retriable revert condition. This satisfies the "permanent freezing of funds" bar for Medium/High severity.

### Likelihood Explanation
Likelihood depends entirely on whether any caller of `_withdraw` (the `RedeemEscrow`/`RefundEscrow` handlers in `IntrinsicIntents.sol` and `ExtrinsicIntents.sol`, which construct `WithdrawalRequest.tokens[i].amount`) can ever produce an amount exceeding the live `_orders[commitment][token]` value — e.g., through partial-fill proportional-release rounding, fee-on-transfer token edge cases, or a double-release attempt after a prior partial refund. I was not able to fully trace every amount-computation path in `IntrinsicIntents.sol` and `ExtrinsicIntents.sol` within the available tool budget to confirm a concrete amount-mismatch trigger (only saw that `_withdraw` and `WithdrawalRequest` are referenced there without inspecting the exact math). Because of this, I cannot certify a fully concrete, unprivileged trigger from a single transaction — this should be treated as **a root-cause hazard requiring validation of a defense-in-depth fix**, not a confirmed exploitable path with a demonstrated PoC.

### Recommendation
Add an explicit sufficiency check in `IntentsBase._withdraw` before subtracting:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed < amount) revert UnknownOrder(); // or a dedicated InsufficientEscrow error
_orders[body.commitment][token] = escrowed - amount;
```
This converts an unrecoverable underflow revert into an explicit, informative revert, and — more importantly — forces an audit of every call site in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol` that builds `WithdrawalRequest.tokens[i].amount` to guarantee it can never exceed the live escrow, eliminating the freeze condition at its source rather than only at the guard.

### Proof of Concept
Not independently reproduced within the scope of this review — the exact call sites in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol` that compute `WithdrawalRequest.tokens[i].amount` were not fully traced to construct a concrete amount-mismatch scenario. The finding is reported as a root-cause code hazard (missing `amount <= escrowed` check) analogous to the referenced report's missing deficit check, and should be validated against the full fill/refund amount-computation logic in those two contracts.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
