### Title
Webhook HMAC only covers the request body, not the `shop-domain` header, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the shop identity (`X-Shopify-Shop-Domain`), topic, API version, and webhook id are all taken from unauthenticated HTTP headers that are never included in the signed bytes. Because the HMAC secret (`api_secret_key`/`client_secret`) is the same for every shop that installs a given app, any unprivileged user who installs the app on their own store can obtain a validly-signed webhook body from Shopify and then replay that exact body+signature to the app's webhook endpoint while substituting a victim shop's domain in the header. The signature verification succeeds even though the "shop" the app believes the data came from is not the shop the body actually originated from — breaking the binding `shop asserted in header == shop that produced the signed bytes`.

### Finding Description
`Utils::HmacValidator.validate` verifies the received HMAC by recomputing it over `verifiable_query.to_signable_string` and comparing against `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from HTTP headers that are never part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` unconditionally when constructing the `WebhookMetadata` handed to the host application's handler: [4](#0-3) [5](#0-4) 

Because the same `api_secret_key` is used by Shopify to sign webhooks for every shop that has installed the app, an attacker who installs the app on their own store (an ordinary, unprivileged action) can capture one legitimately-signed webhook body/HMAC pair for their own shop, then submit that same body+HMAC to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header changed to point at a different, victim shop. `Registry.process` will accept it as valid — the HMAC check passes because the body is byte-identical to what was actually signed — and will invoke the handler with `WebhookMetadata#shop` set to the victim's domain while `body` contains attacker-controlled content from the attacker's own store. This is precisely a case of "a field acted on but not covered by the HMAC": the equality the code should be enforcing, `hmac == HMAC(secret, shop || topic || body)`, is in reality only `hmac == HMAC(secret, body)`, so `shop` and `topic` are free variables an attacker can set independently of the signature.

### Impact Explanation
Applications built on this gem's documented webhook contract (`docs/usage/webhooks.md`) receive `data.shop` as an implicitly trusted identifier and commonly use it to look up the corresponding merchant `Session`/access token or to key persisted data (e.g., "process this order-create payload for shop X"). Forging the shop while keeping a validly-signed body lets an attacker inject or spoof webhook events into another tenant's processing pipeline — a cross-tenant boundary violation, since the gem provides no binding between the asserted `shop` and the bytes that were actually signed by Shopify for that shop.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a store they control (a normal, unprivileged flow for any public/listed app) in order to legitimately receive one HMAC-signed webhook, and then be able to send an HTTP request to the app's public webhook endpoint with a modified header — both of which require no credentials belonging to the victim shop or the app's `client_secret`.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived shop identity to the signed payload, so that `Utils::HmacValidator.validate` cannot pass for a body whose declared shop differs from the shop it was actually signed for. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted without an independent binding (e.g., verifying the webhook id/shop pair against Shopify via API, or maintaining a per-shop webhook secret).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw request body `B` and the `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)` sent by Shopify.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally changed as well
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. The handler is invoked via `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the body `B` was never produced for that shop, per `lib/shopify_api/webhooks/registry.rb:198-199`.
