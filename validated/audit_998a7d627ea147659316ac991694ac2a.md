## Title
Unchecked length on `message.from` causes a runtime panic in `HyperFungibleToken::on_accept` when dispatching calldata without a signature - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` (the `IsmpModule` implementation for `pallet-hyper-fungible-token`) validates the length of `message.to` before copying it into a fixed-size buffer, but performs no equivalent validation on `message.from` before using it to derive the dispatch origin for signature-less calldata execution. A crafted cross-chain message can drive either an arithmetic-overflow panic (EVM source) or a `copy_from_slice` panic (non-EVM source), aborting block execution — the same missing-length-guard bug class as CVE-2021-3119's unchecked pointer/String comparison in SQLCipher.

### Finding Description
In `on_accept`, `to_bytes` is explicitly length-checked and rejected with a typed error before use: [1](#0-0) 

But later, when the message carries optional calldata with no signature, `message.from` is sliced/copied with **no length check at all**: [2](#0-1) 

Two distinct panics are reachable from this code:
1. `source.is_evm()` branch: `from_bytes.len() - 20` underflows (`usize` subtraction) whenever `from_bytes.len() < 20`, which panics on overflow-checked runtimes (and otherwise wraps into an out-of-bounds slice index, which also panics).
2. Non-EVM branch: `account.copy_from_slice(from_bytes)` panics whenever `from_bytes.len() != 32`.

Notably, `HftError` already defines an `InvalidSenderLength(usize)` variant analogous to `InvalidRecipientLength`: [3](#0-2) 

This shows the length-guard pattern was applied to `to` but the equivalent guard for `from` was never wired into `on_accept`, exactly the class of "one field checked, the sibling field forgotten" bug this codebase has repeatedly hardened against elsewhere (e.g. the `StateMachine::from_str` fixed-length copy fix and the `as_utf8_string` deserializer fix, both of which carry explicit regression comments about untrusted-input panics).

`message` is decoded straight from the untrusted `PostRequest.body` via `Message::abi_decode(&body)`: [4](#0-3) 

The gating check before this point (`ContractToAsset::<T>::get(source, &from)`) only authenticates the *dispatching contract address* — i.e., `PostRequest.from` — not the *application-level* `message.from` field embedded inside the ABI-encoded body: [5](#0-4) 

Because `message.from` is a free-form, dynamically-sized `bytes` field inside the body that the sending-side contract encodes, and is only consulted for deriving a dispatch origin in the no-signature branch, any relayer/attacker who can get an ISMP `PostRequest` accepted with this destination module (a routine unprivileged action — submitting a relayed message with a valid state/consensus proof for a request legitimately dispatched from the whitelisted source gateway) but with a manipulated `data`/`from` encoding inside `SubstrateCalldata` can supply a `from` of any length other than 20 (EVM) or 32 (non-EVM) bytes and panic the runtime during message execution.

### Impact Explanation
A panic inside `on_accept` during ISMP message dispatch aborts execution of that block/extrinsic on the destination parachain, denying service to all message delivery, minting/transfer, and dispatch operations for `pallet-hyper-fungible-token` — a `HandlerV2`/`pallet-ismp` `handle_unsigned`-reachable module callback. This matches the "route unable to deliver messages" / DoS criteria: an unprivileged relayer or token bridger can permanently or repeatedly halt processing of legitimate cross-chain token transfers routed through this pallet, analogous to the remote DoS achievable via CVE-2021-3119's NULL pointer dereference.

### Likelihood Explanation
Reaching this code requires only: (1) a message destined for `pallet-hyper-fungible-token` from a source/contract pair already present in `ContractToAsset` (a normal, expected condition for any live HFT bridge deployment — this is exactly the path legitimate token transfers use), and (2) a `data` payload whose `SubstrateCalldata.signature` is `None` and whose `from` field byte length is not 20/32. Since `message` is entirely attacker/relayer-controlled ABI-encoded bytes inside the request body, and no consensus or cryptographic check constrains the length of this specific sub-field, likelihood is high once a route to this module is live.

### Recommendation
Add explicit length validation for `from_bytes`, mirroring the existing `to_bytes` guard and the already-defined-but-unused `HftError::InvalidSenderLength`, e.g.:
```rust
let from_bytes = message.from.as_ref();
let origin = if source.is_evm() {
    if from_bytes.len() != 20 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    T::EvmToSubstrate::convert(H160::from_slice(from_bytes))
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
```

### Proof of Concept
1. Ensure `ContractToAsset::<T>::get(source, &from)` resolves for the attacker's chosen `(source, PostRequest.from)` pair (the normal, already-configured production path for a live HFT bridge route).
2. Craft `PostRequest.body` that ABI-decodes into `Message` with a valid `to` (20 or 32 bytes) and non-empty `data`.
3. Encode `data` as SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any allowed call> }`.
4. Set the top-level `Message.from` field (independent of `PostRequest.from`) to a byte string of length ≠ 20 for an EVM source (e.g. length 0), or ≠ 32 for a non-EVM source.
5. Relay this request through the normal `handle_unsigned`/`HandlerV2` path with a valid proof; when `pallet_ismp` dispatches it to `Pallet::on_accept`, execution reaches `&from_bytes[from_bytes.len() - 20..]` (or `copy_from_slice`) and panics, aborting the extrinsic/block.
