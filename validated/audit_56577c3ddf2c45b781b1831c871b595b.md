Based on my investigation, I found a genuine analog to the CSWSH bug class.

### Title
Unauthenticated relayer address in `GetRequestsWithProof.address` allows arbitrary reputation minting - ([File: modules/pallets/state-coprocessor/src/impls.rs])

### Summary
The CSWSH advisory's root cause is a server accepting a client-controlled identity/instruction without authenticating who is actually connecting. `pallet-state-coprocessor::handle_get_requests` (invoked via the permissionless `handle_unsigned` extrinsic) has the same class of flaw: the `address` field inside `GetRequestsWithProof` — the account credited with reputation-token minting — is taken verbatim from the caller-supplied message with no signature or provenance check, unlike the sibling flow in `pallet-messaging-incentives::relayer_for`, which cryptographically recovers the relayer from a signature over the message (`modules/pallets/messaging-incentives/src/lib.rs:140-153`).

### Finding Description
`handle_unsigned` in `modules/pallets/state-coprocessor/src/lib.rs:92-104` only calls `ensure_none(origin)` — it is a fee-free unsigned extrinsic anyone can submit, gated purely by `ValidateUnsigned::validate_unsigned` (`lib.rs:107-149`), which re-executes `handle_get_requests` to check the state/response proofs are valid. [1](#0-0) 

Inside `handle_get_requests` (`modules/pallets/state-coprocessor/src/impls.rs:62-64`), the `address: Vec<u8>` field of `GetRequestsWithProof` is destructured straight from caller input and used, unauthenticated, both as the response-receipt signer and as the reputation-mint beneficiary: [2](#0-1) 

Everything else in the batch (`requests`, `source` proof, `response` proof) is cryptographically verified against on-chain state commitments — but `address` is never checked against any signature, submitter identity, or proof. Any observer of the public mempool/chain state can construct the exact same `GetRequestsWithProof` (state and response proofs are derived from public chain data, not secret), swap in their own `address`, and resubmit it before or instead of the legitimate relayer, claiming the reputation mint for work they didn't relay.

This mirrors the CSWSH pattern precisely: a request payload that should be bound to "whoever actually delivered/connected" is instead trusted as self-reported data, because the endpoint (the unsigned extrinsic / the WebSocket handshake) performs no identity/origin check on that specific field.

### Impact Explanation
`ReputationMinted` credits `pallet_messaging_incentives::ReputationAsset::mint_into(&relayer, amount)` — an on-chain fungible asset mint (`modules/pallets/state-coprocessor/src/impls.rs:171-173`). An attacker who front-runs or simply resubmits a legitimately-provable `GetRequestsWithProof` batch with their own address can mint reputation tokens they did not earn, at the expense of the honest relayer who did the actual proof-fetching work and possibly at the expense of any economic value the reputation asset carries (staking weight, fee discounts, governance weight, etc., depending on how `ReputationAsset` is configured downstream). This is an unbacked/unauthorized mint of protocol-controlled value, reachable from a single unsigned extrinsic submission.

### Likelihood Explanation
High. The `source` and `response` proofs required by the extrinsic are, by ISMP design, membership proofs over public state — they are not secrets held only by the honest relayer. Any party monitoring the transaction pool or observing on-chain events can reconstruct an identical, validly-proven `GetRequestsWithProof` and simply substitute the `address` field, since `validate_unsigned`'s `provides` tag is only based on the request hashes (`msg_hash` from `messages`, `lib.rs:131-139`), not on `address` — so a resubmission with a different address for the same underlying requests is not blocked as a duplicate by transaction-pool logic (it would only fail on-chain if the underlying GetResponse receipt was already stored by an earlier successful call, i.e. a race/front-run condition, not a hard block).

### Recommendation
Bind `address` to a verifiable identity: either require a signature over the batch (recovering the beneficiary the way `pallet-messaging-incentives::relayer_for` does over `Message::Request`/`Message::Response`), or derive the reputation beneficiary strictly from the transaction submitter (though this is an unsigned extrinsic, so an `ensure_none` origin has no address) via a cryptographic signer field embedded in and verified as part of `GetRequestsWithProof`, analogous to how `RequestMessage`/`ResponseMessage::signer` is treated elsewhere in `pallet-ismp`.

### Proof of Concept
1. Observe a pending/executed `state_coprocessor::handle_unsigned(GetRequestsWithProof { requests, source, response, address: <honest_relayer> })` on-chain or in the mempool.
2. Construct an identical `GetRequestsWithProof` but with `address: <attacker_account_bytes>` — the `source`/`response` proofs remain valid since they attest to public chain state, not to the submitter's identity.
3. Submit the crafted unsigned extrinsic before the honest relayer's transaction is included (or resubmit for a request the honest relayer hasn't yet claimed).
4. `validate_unsigned` succeeds (proofs check out), `handle_get_requests` mints `ReputationMinted { relayer: <attacker_account>, ... }` via `ReputationAsset::mint_into`, crediting the attacker instead of the actual delivering relayer. [3](#0-2) [4](#0-3)
