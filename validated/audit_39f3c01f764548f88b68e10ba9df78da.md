### Title
Permanent lock of residual APT and FA reserves after `LiquidityPair` graduation with no recovery path — ([File: aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move])

### Summary
The AaveV3 bundler bug shows a custody invariant break where an amount is derived from an internal accounting value instead of the entity's real, controllable balance, leaving assets stranded/inaccessible under the wrong holder. The Aptos-native analog is in `bonding_curve_launchpad`'s `graduate` function: only 90% of the tracked `apt_reserves`/`fa_reserves` are migrated to the external DEX pool at graduation, and the remaining 10% of both APT and the FA stay custodied inside the bonding-curve `LiquidityPair` object's `fa_store` and its APT balance. After graduation, `is_enabled` is permanently set to `false`, and the module exposes no function to withdraw or sweep this residual balance from the (now dead) `LiquidityPair` object.

### Finding Description
`graduate()` disables the internal pair (`liquidity_pair.is_enabled = false`) and unfreezes the FA (`liquidity_pair.is_frozen = false`), then computes the amounts to migrate as 90% of both reserves: [1](#0-0) 

`add_liquidity_coin_entry_transfer_ref` withdraws exactly `optimal_amount_1`/`optimal_amount_2` (derived from the 90% figures, further capped by AMM `optimal_liquidity_amounts`) from the `lp` signer and the FA's `fa_store` via `transfer_ref`, and forwards them to the external DEX pool: [2](#0-1) 

The `LiquidityPair` struct holds the FA balance in `fa_store` (a `FungibleStore` object) and holds APT directly in the `liquidity_pair` object's account (funded via `aptos_account::transfer` during swaps): [3](#0-2) [4](#0-3) 

After `graduate()` runs, `is_enabled` is `false`, so `swap_fa_to_apt`/`swap_apt_to_fa` (the only entry points that reference the `LiquidityPair` object and its `transfer_ref`) will always abort on the `ELIQUIDITY_PAIR_DISABLED` check: [5](#0-4) [6](#0-5) 

Neither `liquidity_pairs.move` nor `bonding_curve_launchpad.move` defines any other function that can access `liquidity_pair.fa_store`, withdraw remaining APT from the `LiquidityPair` object, or otherwise reclaim the leftover balance — the only holder of the `TransferRef`/`ExtendRef` needed to move these funds is the internal `LiquidityPair`/`FAController` state, which is only ever used inside the disabled swap/graduate paths. The `fa_store`'s underlying object has no `owner`-level transfer path either, because it was created via `object::create_object(@bonding_curve_launchpad)` and stores are typically non-transferable once wired into `LiquidityPair`. This corrupts custody accounting: 10% of both sides of the pool's value is permanently owned by an object whose only code paths to move funds are now unreachable, destroying recovery rights for the FA creator, swappers, and the protocol alike.

### Impact Explanation
This is a permanent, non-recoverable loss of object-held value (10% of both the FA supply committed to the bonding curve and 10% of the real APT collected from swappers) for every FA that successfully graduates. Given `APT_LIQUIDITY_THRESHOLD` is fixed at 600,000,000,000 octas (~6,000 APT) and this triggers on every graduation, the locked amount is deterministic and substantial per launch, and recurs for every FA that graduates through the launchpad — a mainnet-relevant, custody-grade impact matching "permanent lock or non-recoverable loss of object-held ... value."

### Likelihood Explanation
This is not an edge case requiring an attacker — it fires automatically and deterministically on every successful graduation (`apt_updated_reserves > APT_LIQUIDITY_THRESHOLD`), which is the designed success path of the protocol. No special privileges or race conditions are needed; the 10% remainder always lands in a `LiquidityPair` object that becomes unreachable the moment `is_enabled` flips to `false`.

### Recommendation
Add a post-graduation sweep function (callable once `is_enabled == false`) that uses the stored `extend_ref`/`transfer_ref` to transfer the full remaining balance of `fa_store` and the `LiquidityPair` object's APT balance to a designated recipient (e.g., protocol treasury, FA creator, or pro-rata to swappers), or alternatively change `graduate()` to migrate 100% of tracked reserves (subject to `optimal_liquidity_amounts` capping) instead of a fixed 90%, and add an explicit sweep of any AMM-side leftover dust after `add_liquidity_coin`.

### Proof of Concept
1. Launch an FA via `create_fa_pair`, causing `register_liquidity_pair` to create a `LiquidityPair` with `apt_reserves = INITIAL_VIRTUAL_APT_LIQUIDITY`.
2. Repeatedly call `bonding_curve_launchpad::swap(..., swap_to_apt=false, amount_in=...)` to buy the FA with APT until `apt_updated_reserves > APT_LIQUIDITY_THRESHOLD`, triggering `graduate()` inside `swap_apt_to_fa`. [7](#0-6) 
3. `graduate()` migrates only 90% of `apt_updated_reserves`/`fa_updated_reserves` to the external DEX via `add_liquidity_coin_entry_transfer_ref`, leaving ~10% of both APT and FA in the `LiquidityPair` object's `fa_store` and account balance.
4. Attempt any further call into `liquidity_pairs` referencing this pair (`swap_fa_to_apt`, `swap_apt_to_fa`, or a hypothetical sweep) — all revert on `assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED)`, and no other function in the module can access `liquidity_pair.fa_store` or the object's APT balance, confirming the residual funds are permanently stranded.

Note: Given index size limits, I was not able to independently verify whether an external module (e.g., in `swap::router` or `swap::liquidity_pool`, which are referenced but not part of this repo's indexed contents) provides any indirect sweep mechanism for `fa_store`; this analysis is based solely on the code present in `bonding_curve_launchpad` and `liquidity_pairs.move`.

    fun add_liquidity_coin_entry_transfer_ref<CoinType>(
        transfer_ref: &TransferRef,
        lp: &signer,
        fa_store: Object<FungibleStore>,
        token_2: Object<Metadata>,
        is_stable: bool,
        amount_1_desired: u64,
        amount_2_desired: u64,
        amount_1_min: u64,
        amount_2_min: u64,
    ) {
        // Wrap APT into a FA. Then, determine the optimal amounts for providing liquidity to the given FA - APT pair.
        let token_1 = coin_wrapper::get_wrapper<CoinType>();
        let (optimal_amount_1, optimal_amount_2, _) = router::optimal_liquidity_amounts(
            token_1,
            token_2,
            is_stable,
            amount_1_desired,
            amount_2_desired,
            amount_1_min,
            amount_2_min,
        );
        // Retrieve the APT and FA from the liquidity provider.
        // `transfer_ref` is used to avoid circular dependency during graduation. A normal transfer would require
        // visiting `bonding_curve_launchpad` to execute the custom withdraw logic. `transfer_ref` bypasses the need to
        // return to `bonding_curve_launchpad` by not executing the custom withdraw logic.
        let optimal_1 = coin::withdraw<CoinType>(lp, optimal_amount_1);
        let optimal_2 = fungible_asset::withdraw_with_ref(
            transfer_ref,
            fa_store,
            optimal_amount_2
        );
        // Place the APT and FA into the liquidity pair.
        router::add_liquidity_coin<CoinType>(lp, optimal_1, optimal_2, is_stable);
    }
