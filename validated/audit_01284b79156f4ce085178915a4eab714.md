### Title
Bridge `outgoingToken` credential is exposed in plaintext to low-privilege "view" role users via `/v2/bridge_types` API and GraphQL - ([File: core/web/router.go])

### Summary
The Chainlink node's Bridge API and GraphQL resolvers return the `OutgoingToken` field — a plaintext authentication credential used by the node to authenticate itself to external bridge adapters — to any authenticated user, including the lowest-privilege "view" role, without any masking or redaction. This mirrors the Jenkins Apica Loadtest Plugin issue (CVE-2025-53664): a secret credential stored and served unencrypted/unmasked, viewable by users who should only have limited/read access.

### Finding Description
The `BridgeTypesController.Index` and `.Show` handlers are registered without any role gate beyond basic authentication: [1](#0-0) 

Compare this to sibling mutating routes (`POST`, `PATCH`, `DELETE`) which are wrapped in `auth.RequiresEditRole`, while `GET /bridge_types` and `GET /bridge_types/:BridgeName` have no role check at all — meaning even a "view"-role user (the lowest role in the RBAC hierarchy) can call them.

The handler builds its response via `presenters.NewBridgeResource`, which unconditionally copies `OutgoingToken` from the DB model into the JSON:API response, with no `omitempty` or masking (contrast with `IncomingToken`, which is only populated at creation time): [2](#0-1) [3](#0-2) 

The `Show` and `Index` controller methods pass the ORM-fetched `BridgeType` (which carries `OutgoingToken` from the `outgoing_token` DB column) straight into the presenter: [4](#0-3) 

The same field is exposed with no role restriction through the GraphQL `Bridge`/`Bridges` queries, which only require `authenticateUser` (i.e., any logged-in session, view role included) rather than `authenticateUserCanEdit`: [5](#0-4) [6](#0-5) [7](#0-6) 

RBAC test fixtures confirm `GET /v2/bridge_types` and `GET /v2/bridge_types/MOCK` are `viewOnlyAllowed: true`: [8](#0-7) 

`OutgoingToken` is the secret the Chainlink node sends to external adapters/bridges as an authentication credential (it is the same credential used e.g. in `X-Chainlink-Pending` style outgoing auth headers to external adapters). It is stored server-side and returned verbatim to any authenticated caller regardless of role.

### Impact Explanation
Any user granted only the lowest "view" role (e.g., an auditor, monitoring account, or read-only integration) can retrieve every bridge's `outgoingToken` via a simple authenticated `GET /v2/bridge_types` or GraphQL `bridges` query. Since this token is used by the node to authenticate to the external adapter, disclosure allows an attacker with only view-level Chainlink credentials to impersonate the node when calling the external adapter, or to replay/misuse the token elsewhere the adapter trusts it, without needing edit/admin privileges. This is a direct secret-disclosure / privilege-boundary issue (CWE-256/522 analog), though impact is moderated because it grants access only to the external-adapter side, not node funds or job execution directly.

### Likelihood Explanation
Likelihood is high for any node operator who provisions "view" role users (a common practice for monitoring/read-only dashboards or third-party access). No special conditions are required — a single authenticated GraphQL or REST call with view-role credentials is sufficient; there is no additional secret needed and no rate limiting or redaction in place.

### Recommendation
- Restrict `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` (and the GraphQL `bridge`/`bridges` resolvers) to require at least `edit`/`run` role, or strip `OutgoingToken` from the response for lower-privileged roles, similar to how `IncomingToken` is only surfaced at creation time.
- Alternatively, mask `OutgoingToken` in list/show responses by default and only reveal it via an explicit, higher-privilege "reveal secret" action, consistent with the recommended fix pattern for the Jenkins advisory (mask sensitive tokens, restrict to privileged read).

### Proof of Concept
1. Create a session/API token for a Chainlink node user with role `view`.
2. Call `GET /v2/bridge_types` (or the GraphQL query `{ bridges { results { name outgoingToken } } }`) using that view-role session.
3. Observe the response includes `outgoingToken` in plaintext for every configured bridge, as shown by the test fixtures at [9](#0-8)  and [10](#0-9) , which demonstrate `outgoingToken` returned in normal API/GraphQL responses without any role-based filtering.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// Bridge retrieves a bridges by name.
func (r *Resolver) Bridge(ctx context.Context, args struct{ ID graphql.ID }) (*BridgePayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	name, err := bridges.ParseBridgeName(string(args.ID))
	if err != nil {
		return nil, err
	}

	bridge, err := r.App.BridgeORM().FindBridge(ctx, name)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return NewBridgePayload(bridge, err), nil
		}

		return nil, err
	}

	return NewBridgePayload(bridge, nil), nil
}

func TestBridgeController_Show(t *testing.T) {
	t.Parallel()

	app := cltest.NewApplication(t)
	require.NoError(t, app.Start(t.Context()))

	client := app.NewHTTPClient(nil)

	bt := &bridges.BridgeType{
		Name:          bridges.MustParseBridgeName(testutils.RandomizeName("showbridge")),
		URL:           cltest.WebURL(t, "https://testing.com/bridges"),
		Confirmations: 0,
	}
	ctx := t.Context()
	require.NoError(t, app.BridgeORM().CreateBridgeType(ctx, bt))

	resp, cleanup := client.Get("/v2/bridge_types/" + bt.Name.String())
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusOK, resp.StatusCode, "Response should be successful")

	var resource presenters.BridgeResource
	cltest.ParseJSONAPIResponse(t, resp, &resource)
	assert.Equal(t, bt.Name.String(), resource.Name, "should have the same name")
	assert.Equal(t, bt.URL.String(), resource.URL, "should have the same URL")
	assert.Equal(t, bt.Confirmations, resource.Confirmations, "should have the same Confirmations")

	resp, cleanup = client.Get("/v2/bridge_types/nosuchbridge")
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusNotFound, resp.StatusCode, "Response should be 404")
}
