Audit Report

## Title
Silent `Workplan` update failure in `do_assign` desynchronizes `Regions`/`Workplan` and can strand paid coretime - (File: substrate/frame/broker/src/dispatchable_impls.rs)

## Summary
`do_assign` in [1](#0-0)  calls `Self::utilize`, which unconditionally removes the region from `Regions::<T>` for `Finality::Final` [2](#0-1) , and then only conditionally writes the new `ScheduleItem` into `Workplan` depending on whether `try_push` succeeds, without ever surfacing an error if it fails. This confirms the described root cause: the function can return `Ok(())` and emit `Event::Assigned` even though the `Workplan` entry was never written, while the source `Region` has already been irreversibly removed for `Finality::Final`.

## Finding Description
The code exactly matches the claim: `utilize` removes the region from `Regions::<T>` before `do_assign`'s workplan-push logic runs, and only re-inserts it when `finality == Finality::Provisional` [3](#0-2) . Back in `do_assign`, the `try_push(...).is_ok()` check gates only the `Workplan::<T>::insert` call — there is no `ensure!`/early return on failure, so the function proceeds to the `PotentialRenewals` update and unconditionally emits `Event::Assigned` regardless of whether the push succeeded [4](#0-3) . This means for `Finality::Final`, a failed `try_push` results in the `Region` being gone from `Regions`, absent from `Workplan`, and a misleading success event — the exact desynchronization the report describes.

However, I was unable to confirm the actual bound of the `Workplan`/`Schedule` bounded vector (`MaxScheduleItems` or equivalent constant) within the available tool results — repeated searches for `Workplan`, `Schedule`, and `MaxItems` type definitions in `substrate/frame/broker/src/types.rs` and `lib.rs` did not return readable content in this session, so the practical bound size and thus the real-world feasibility of filling it via `interlace`+`assign` spam could not be independently verified. The report's likelihood analysis also acknowledges this uncertainty ("was not confirmed by the index in this session").

## Impact Explanation
If the bound is small enough to be reachable through ordinary `interlace`/`assign` calls, this is a genuine state-desynchronization bug: a paid-for `Region` can be silently destroyed without a corresponding `Workplan` entry, misrepresented as a successful assignment via `Event::Assigned`, and (for `Finality::Final`) the loss is unrecoverable since the region is never restored. This matches an in-scope "loss of user-paid coretime / broken accounting invariant" impact class, assuming the bound is practically reachable.

## Likelihood Explanation
The exploit path (permissionless `interlace` + `assign` extrinsics available to any region owner) is realistic and requires no privileged access, matching the report's description. The main open question is the numeric bound of `Workplan`'s `BoundedVec<ScheduleItem, _>`, which determines how many `interlace`/`assign` calls are needed to fill a given `(begin, core)` slot to capacity — this could not be confirmed in this session due to index limitations, but the code logic itself is verified to behave exactly as claimed regardless of the specific bound value.

## Recommendation
- Make `do_assign` (and `do_pool`, which shares the same `try_push(...).is_ok()` pattern) return a hard error such as `Error::<T>::WorkplanFull` when `try_push` fails, instead of silently continuing.
- Avoid removing/finalizing the `Region` via `utilize` before the `Workplan` push is confirmed to succeed, or roll back the `Regions` removal on failure.
- Gate the `PotentialRenewals` update so it only runs when the `Workplan` insertion actually succeeded.

## Proof of Concept
1. Call `do_start_sales` and purchase a region covering a full core.
2. Repeatedly call `do_interlace` on the region to split it into as many mask slices as needed to fill the `Workplan` entry for `(begin, core)` to its bound, calling `do_assign` with `Finality::Final` for each slice.
3. Attempt one more `do_assign` call at the same `(begin, core)` key and observe:
   - The call returns `Ok(())`.
   - `Regions::<Test>::get(region_id)` is `None`.
   - `Workplan::<Test>::get((begin, core))` does not contain the new `ScheduleItem`.
   - `Event::Assigned` was still emitted.

Note: this PoC's feasibility (specifically how many `interlace`/`assign` calls are needed) depends on the exact `Workplan` bound size, which could not be verified from the available code index in this session; a Devin agent with full repository access should confirm the bound in `substrate/frame/broker/src/types.rs` / `Config` before finalizing severity, but the underlying code defect is confirmed as described.

	pub(crate) fn utilize(
		mut region_id: RegionId,
		maybe_check_owner: Option<T::AccountId>,
		finality: Finality,
	) -> Result<Option<(RegionId, RegionRecordOf<T>)>, Error<T>> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let region = Regions::<T>::get(&region_id).ok_or(Error::<T>::UnknownRegion)?;

		if let Some(check_owner) = maybe_check_owner {
			ensure!(Some(check_owner) == region.owner, Error::<T>::NotOwner);
		}

		Regions::<T>::remove(&region_id);

		let last_committed_timeslice = status.last_committed_timeslice;
		if region_id.begin <= last_committed_timeslice {
			let duration = region.end.saturating_sub(region_id.begin);
			region_id.begin = last_committed_timeslice + 1;
			if region_id.begin >= region.end {
				Self::deposit_event(Event::RegionDropped { region_id, duration });
				return Ok(None);
			}

				p.retain(|i| (i.mask & region_id.mask).is_void())
			});
