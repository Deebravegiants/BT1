### Title
`isCorrectPin` uses non-constant-time `pin === input` comparison on secret PIN - ([File: features/auth-mobile/module/auth.js])

### Summary
`Auth.isCorrectPin` compares the stored PIN and the caller-supplied guess with plain JavaScript strict equality (`pin === input`) instead of a constant-time comparison. This method is part of the `auth` module (`public: true`) and is exposed through the app's RPC surface as `exodus.auth.isCorrectPin`, making it reachable by any unprivileged caller with RPC/webview-bridge access, per the documented usage `await exodus.auth.isCorrectPin('645123')`.

### Finding Description
`isCorrectPin` reads the stored PIN via `keystore.getSecret` and returns the result of `!!pin && pin === input`: [1](#0-0) 

V8's `===` on strings for short values is not guaranteed constant-time — it short-circuits on length mismatch and can early-exit on the first differing character, and JS engines apply various optimizations (interning, SMI/rope checks) that can introduce measurable timing variance correlated with the number of matching leading characters. Because the PIN is fixed at 6 digits (`setPin` enforces `value.length !== 6`), an attacker who can invoke `isCorrectPin` repeatedly with different prefixes and measure response latency could, in principle, use timing differences to narrow down correct digits one at a time rather than brute-forcing the full keyspace.

The `auth` module is registered with `public: true` and is deep-traversed by the RPC layer (`rpc.exposeMethods(sdk)` in `sdks/headless`/`sdk-rpc`), exposing `isCorrectPin` as a callable method over the RPC bridge (e.g., `webviewTransport` on mobile) as documented in `features/auth-mobile/README.md`: [2](#0-1) [3](#0-2) 

No rate limiting, attempt counter, lockout, or artificial delay was found guarding `isCorrectPin` calls anywhere in the codebase (`grep` for `failedAttempts`, `lockout`, `throttle` near auth returns no hits in `features/auth-mobile`), so an attacker can issue an effectively unlimited number of timed guesses.

### Impact Explanation
If exploitable, this would let an unprivileged RPC caller recover the 6-digit PIN used to gate `shouldAuthenticate`-protected UI/signing flows without needing the correct PIN, bypassing the local authentication gate that restricts access to protect-worthy resources such as the mnemonic phrase (per the `authAtom` semantics documented in the README). This matches an auth-bypass / secret-disclosure impact class.

### Likelihood Explanation
Exploitability is conditioned on the attacker being able to measure end-to-end latency of `isCorrectPin` RPC calls with sufficient precision to detect a sub-microsecond/microsecond-level string-comparison timing difference through an async RPC transport (webview bridge / postMessage / multi-process JSON-RPC), which introduces significant scheduling and serialization jitter (`libraries/sdk-rpc/src/rpc.ts`, `requestTimeout` default 5m, async transport). This jitter substantially reduces — though does not theoretically eliminate — the practicality of the timing side channel compared to an in-process, unbuffered timing attack. No mitigating rate limit or lockout exists, so repeated sampling to average out noise is unconstrained.

### Recommendation
Replace the `pin === input` strict-equality check with a constant-time string comparison (e.g., timing-safe compare over fixed-length encodings, such as `crypto.timingSafeEqual` on padded/hashed buffers) in `isCorrectPin`, and consider adding attempt throttling/lockout for repeated failed PIN checks at the RPC boundary.

### Proof of Concept
Statistical timing test plan:
1. Instantiate the `Auth` module with a mocked `keystore.getSecret` returning a fixed 6-digit PIN, wired through the real `sdk-rpc`/`RPC` transport (as in `sdks/headless/__tests__/utils/rpc.js`) to include realistic RPC overhead.
2. For N ≥ 10,000 trials, call `exodus.auth.isCorrectPin(guess)` with (a) guesses sharing a long correct prefix and one wrong trailing digit, and (b) guesses wrong in the first digit; record high-resolution latency (`process.hrtime.bigint()`) for each call.
3. Compute mean/median latency and run a statistical test (e.g., Welch's t-test or Mann-Whitney U) comparing group (a) vs (b).
4. Assert: if `pin === input` is used, dataset should show measurable, reproducible correlation between latency and matching-prefix length after averaging out RPC/IPC noise (or, per the flagged proof idea, simply assert the implementation uses `===` instead of a documented constant-time compare, which is sufficient to flag the anti-pattern independent of a fully proven timing exploit).
