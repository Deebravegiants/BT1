### Title
Malicious swap route grafts a wallet-draining `token.transfer` into the victim's `swap_collateral` auth tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
CVE-2021-30587 is a UI-spoofing class: a crafted page makes the browser display trusted content while the attacker controls what is actually authorized. The on-chain analog exists in XOXNO Lending's router strategies: `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept an opaque `swap: Bytes` payload that the configured swap aggregator executes against arbitrary, unallowlisted venue contracts. A venue contract chosen inside the attacker's crafted route can itself call `token.transfer(victim, attacker, amount)` requiring the victim's auth. Soroban simulation records that theft as a sub-invocation under the victim's innocent-looking `swap_collateral` root entry, so a wallet or dApp that displays only the root function spoofs the user into signing an authorization tree that drains their wallet. The repo's own test harness demonstrates exactly this attack in both recording and enforcing mode.

### Finding Description
The controller's strategy entrypoints authorize the caller once at the root (`caller.require_auth()` / owner-or-delegate check) and then let the swap aggregator execute attacker-controlled route bytes whose hops can be arbitrary contracts. `contracts/controller/src/strategies/swap.rs` hands the opaque `swap` payload to `swap_aggregator` via `execute_strategy` without constraining which sub-contracts the route invokes. The test double `UnlistedPoolRouter` in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` decodes the route and calls `env.invoke_contract(&route.hop_pool, "swap", ...)` on whatever contract the payload names (lines 39–47). The attacker-registered `RogueHopPool` then calls `token::Client::transfer(&victim, &to, &amount)` (lines 62–71).

The test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` proves the spoofing step: simulating the transaction produces an `AuthorizedInvocation` whose root is `controller.swap_collateral` and whose single recorded sub-invocation is the stolen `token.transfer(alice → attacker, WALLET_BALANCE)` (lines 206–225). Then `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` proves execution: an honest root-only signed tree fails (`Unauthorized function call for address`, lines 243–254), but the exact simulation-produced "poisoned" tree — the one a UI presents as "sign swap_collateral" — succeeds and empties the wallet (lines 259–268). The source-account credential variant shows the graft works even without an entry signature scheme, when the victim's G-address is the transaction source account (lines 322–367).

This is not a general host-auth weakness: the host enforces the signed tree correctly. The vulnerability is that the protocol's design makes a wallet-draining invocation indistinguishable from a legitimate collateral swap at the presentation layer, because the route venue is unvalidated and its `require_auth` calls are folded into the caller's tree. The protocol only protects its own invariants (measured balance-delta input/output in `execute_strategy`, fair-output assertions in the test), not the victim's unrelated wallet funds consumed as an auth side effect.

### Impact Explanation
Any unprivileged attacker who can get a victim to sign a strategy transaction with a poisoned `swap` payload (phishing dApp, malicious route generated by a compromised or attacker-run quoting frontend — the direct analog of the "crafted HTML page" in the CVE) steals arbitrary balances of any token the victim holds, in any amount the crafted `RogueHopPool`-style contract requests. The theft requires no privileged role, no leaked key, and no bad parameters: it is exercised entirely through the user-facing `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` entrypoints. Test `Scene` confirms Alice loses her entire `WALLET_BALANCE` unrelated token while receiving a "fair" swap output, so the transaction looks successful and even economically correct from the protocol's perspective (lines 224–226, 267–268). This is theft of user funds.

### Likelihood Explanation
The exploit path is fully within the allowed reachable set: a single unprivileged address submits `swap_collateral(caller, account_id, collateral_asset, amount, debt_asset, swap_bytes)` where `swap_bytes` encodes a route through an attacker-deployed contract. The controller performs no venue allowlist — `UpdateSwapAggregatorEvent`/router tests show only the aggregator address is configured, and hop targets inside the payload are unrestricted. Realization requires user interaction (the victim signs the poisoned tree), matching the CVE's `UI:R` characteristic; wallets that render full sub-invocation trees would expose the theft, but wallets that display only the root contract/function — a common simplification — reproduce the spoof. The attack has no execution-uncertainty: once signed, the transfer is atomic within the transaction. Medium severity is consistent with the CVE's CVSS 4.3 (integrity impact bounded to users who sign attacker-crafted routes, with user interaction required).

### Recommendation
- Constrain execution so that untrusted route code cannot consume the caller's auth. Options: (a) have the controller/aggregator invoke hop venues through a call path where the victim's `require_auth` is not ambient — e.g., aggregator-authenticated transfers where the aggregator, not `sender`, is the `require_auth` principal for downstream calls; (b) allowlist permitted hop venues/function selectors and reject routes invoking anything else; (c) document and enforce that integrators must render complete sub-invocation trees and diff simulated auth trees against a declared capability manifest before signing.
- At minimum, add a prominent warning in the router-strategy documentation that `swap` bytes can cause arbitrary victim-authorized token transfers, and consider emitting the executed hop contract list in the position batch event so indexers can flag routes that invoked non-venue contracts.

### Proof of Concept
Demonstrated by the in-repo test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies 10,000 USDC and holds `WALLET_BALANCE` of an unrelated Stellar asset in her wallet (`Scene::new`, lines 84–108).
2. The route payload names an attacker-deployed `RogueHopPool` whose `swap()` executes `token.transfer(alice, attacker, WALLET_BALANCE)` under Alice's ambient auth (lines 56–71, 111–125).
3. `simulateTransaction` (recording mode) returns Alice's auth tree as root `swap_collateral` + child `transfer(alice → attacker)` (lines 195–225) — a UI showing the root spoofs the real effect.
4. Signing that exact tree makes the call succeed: `s.wallet(&s.alice) == 0`, `s.wallet(&s.attacker) == WALLET_BALANCE`, while Alice still receives `FAIR_OUT_ETH` so the swap appears legitimate (lines 265–268, 224–226). The same graft works via source-account credentials with no per-entry signature (lines 322–367).
