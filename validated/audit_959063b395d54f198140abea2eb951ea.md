### Title
Unchecked ERC-20 return value in Tron `IntentGatewayV2.withdraw()` finalizes escrow settlement even when the token transfer silently fails - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` finalizes order settlement (`_filled[commitment]`, escrow balance decrement, `EscrowReleased`/`EscrowRefunded` emission) based only on whether the low-level `.call()` to `token.transfer()` *executed without reverting*, never checking the ERC-20 return value. Tokens that return `false` on failure instead of reverting (a well-known non-conforming ERC-20 behavior) will cause the contract to mark the order filled/refunded and decrement the escrow accounting while the beneficiary receives no tokens - a direct analog to the GPToke bug class where state is finalized as "delivered" before/without confirming the transfer actually succeeded, permanently losing user funds.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 691-730) is the settlement path reached whenever an unprivileged relayer delivers a `RedeemEscrow` or `RefundEscrow` ISMP POST message via `onAccept()` (lines 631-635), or via the GET-response path in `onGetResponse()` (lines 738-743) after a source-side cancellation: [1](#0-0) 

Concretely:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        unchecked { ++i; }
    }
    ...
}
```
The ERC-20 branch only checks `success` — i.e., that the external call itself did not revert. It never decodes/validates the boolean returned by `transfer()`. Numerous real ERC-20 tokens (older/non-standard implementations, e.g. tokens following the pre-EIP20 pattern that return `false` on insufficient balance/blacklist instead of reverting) will make the `.call()` succeed with `success == true` while the transfer itself fails. Since `success` is `true`, execution continues: `_orders[commitment][token] -= amount` is decremented and (for the fee branch, same pattern at lines 716-723) `_orders[commitment][TRANSACTION_FEES]` is deleted, and the order is already marked `_filled[commitment] = beneficiary`, with `EscrowReleased`/`EscrowRefunded` emitted. The beneficiary receives nothing, but the protocol's accounting believes settlement is complete and permanently prevents any retry (the order is now "filled"/finalized and escrow is zeroed).

This is the same root-cause class as the GPToke report: **finalizing user-facing accounting/state as "paid" without a reliable check that the transfer actually delivered value**, leading to unrecoverable loss for the intended recipient. The comparable functions in the canonical EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) use OpenZeppelin's `SafeERC20.safeTransfer`, which does check the returned boolean and reverts on failure — confirming that the raw `.call()` pattern in the Tron variant is a deviation/regression that reintroduces the unchecked-return-value bug class in the fund-release path.

### Impact Explanation
Any solver/filler or user expecting a `RedeemEscrow` or `RefundEscrow` settlement can lose their entire escrowed input tokens if the escrowed token is a non-conforming ERC-20 (returns `false` instead of reverting on failure, e.g. due to a paused/blacklist state, insufficient contract balance edge case, or non-standard implementation). The order is marked filled/refunded, escrow balances are zeroed, and events are emitted as if payment succeeded, but the beneficiary never receives the tokens. Because `_filled[commitment]` is now set and `_orders[commitment][token]` has already been decremented, there is no path to retry or recover the funds — this is a permanent loss of user/solver funds reachable from a single relayed cross-chain message, matching the High severity of the original report.

### Likelihood Explanation
Likelihood depends on the escrowed token's ERC-20 implementation. Many production tokens are fully EIP-20 conforming and will revert on failure, which limits triggering to specific non-conforming tokens (or specific failure conditions of otherwise-conforming tokens that choose to return `false`). However, IntentGateway is a generic escrow accepting arbitrary caller-specified ERC-20 tokens as `inputs`/`outputs` (`TokenInfo.token` is attacker/user-supplied), so a malicious or unlucky combination of a non-conforming token and a transient failure condition (e.g., token pausing, denylist, insufficient balance due to another concurrent path) is fully reachable by an ordinary relayer delivering a normal settlement message — no privileged role is required.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (both the token-loop transfer and the transaction-fee transfer) with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and aliased (`using SafeERC20 for IERC20;`) in this same file but unused in `withdraw()`. This ensures the boolean return value is checked and reverts atomically on failure, so `_filled`/`_orders` state updates cannot be finalized without a real, successful transfer:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```

### Proof of Concept
1. Deploy a non-conforming ERC-20 token `T` whose `transfer()` returns `false` (instead of reverting) when, e.g., the recipient is blacklisted or the contract balance is insufficient at call time.
2. A user places an order on the Tron `IntentGatewayV2` escrowing `T` as an input (`_orders[commitment][T] = amount`).
3. A solver fills the order on the destination chain; `RedeemEscrow` is dispatched back to source and delivered by any relayer via `onAccept()` → `withdraw(body, false)`.
4. At the point of settlement, token `T`'s `transfer()` internally fails and returns `false` (e.g., contract's balance was drained by a reentrant/parallel call, or beneficiary got blacklisted between escrow and settlement) — the low-level `.call()` still reports `success = true` because the call did not revert.
5. `withdraw()` proceeds: `_orders[commitment][T] -= amount` and `_filled[commitment] = beneficiary` are committed, `EscrowReleased` is emitted.
6. The beneficiary's `T` balance is unchanged (transfer never delivered value), yet the order is permanently marked filled and the escrow is zeroed — the escrowed tokens are unrecoverable. [2](#0-1) [3](#0-2) [4](#0-3)

                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
