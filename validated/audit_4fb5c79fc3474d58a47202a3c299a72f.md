### Title
Unverified "signer" wrapper in `extract_signer`/`decode_receipt_relayer` lets any relayer forge delivery attribution, permanently freezing outbound-request delivery rewards - ([File: modules/pallets/ismp/src/host.rs])

### Summary
`handle_unsigned` for `RequestMessage`/`ResponseMessage` accepts a caller-supplied `signer: Vec<u8>` field that is stored verbatim as the "delivering relayer" for a request/response, without ever cryptographically verifying it. Both `extract_signer` (pallet-ismp) and `decode_receipt_relayer` (pallet-relayer) treat any byte string longer than 32 bytes as a SCALE-encoded `Signature` enum and call `Signature::signer()`, which just returns the embedded `address`/`public_key` field — it never calls `Signature::verify()`. This is structurally the same bug class as CVE-2018-15586: a value that *looks like* a verified/signed artifact (a `Signature` struct) is trusted as authentic by downstream consumers without the signature itself ever being checked against any message.

### Finding Description
- `modules/ismp/core/src/handlers/request.rs:112` and `modules/ismp/core/src/handlers/response.rs:102` store the receipt via `host.store_request_receipt(&wrapped_req, &msg.signer)` / `store_response_receipt`, passing through the raw, attacker-controlled `msg.signer` bytes from the `RequestMessage`/`ResponseMessage` a relayer submits via `handle_unsigned`. [1](#0-0) 
- `store_request_receipt`/`store_response_receipt` call `extract_signer(signer)`, which for any input longer than 32 bytes SCALE-decodes it as a `Signature` and calls `.signer()` — no `verify()` is invoked anywhere in this path: [2](#0-1) 
- `Signature::signer()` simply returns the embedded `address`/`public_key` field of whichever enum variant was decoded, with zero cryptographic check that the accompanying `signature` bytes are valid for anything: [3](#0-2) 
- The same unverified-wrapper pattern is repeated in the relayer pallet's `decode_receipt_relayer`, used by both local fee accumulation (`accumulate_fees`) and the outbound-request-delivery reward claim to interpret a proven `RequestReceipts[commitment]` value: [4](#0-3) 
- The outbound-request-delivery reward flow *does* later perform a real signature check, but only on the claimant's `OutboundRequestDeliveryClaim.signature`, and compares the recovered signer against whatever address was stored (unverified) in `RequestReceipts[commitment]` at delivery time: [5](#0-4) 

Because `Signature::decode` is a plain SCALE decode (any well-formed byte layout parses, regardless of whether the embedded "signature" bytes are cryptographically meaningful), any account submitting `handle_unsigned` with a `RequestMessage`/`ResponseMessage` can set `signer` to `Signature::Evm { address: <arbitrary_bytes>, signature: <garbage> }` (or the Sr25519/Ed25519 equivalents). This is accepted, stored as the authoritative "who delivered this message" record in `RequestReceipts`/`ResponseReceipts`, and later relied upon by reward-distribution logic as if it had been proven.

### Impact Explanation
The delivering party controls who is credited for delivery of any request/response without needing to actually control the credited address's private key. Concretely, for the outbound-request-delivery incentivization flow: whoever submits the delivery message on the destination chain can set `signer` to an arbitrary address for which no private key exists. That address is then durably recorded in the destination chain's `RequestReceipts[commitment]`. When a legitimate relayer later attempts `claim_outbound_request_delivery_reward`, step 10 (signature attribution) requires recovering a signer from a real signature that must equal the address baked into the receipt — but since that address was never actually validated as controlled by anyone, no one can ever produce a matching signature. The claim permanently fails with `OutboundRequestSignerMismatch`, and the reward for that commitment can never be paid out — a permanent freezing of relayer delivery rewards. The same unverified-attribution primitive also corrupts the destination-chain relayer identity used by the local fee-accumulation path (`accumulate_fees`), since `decode_receipt_relayer` performs the identical unverified length-based Signature decoding.

### Likelihood Explanation
`handle_unsigned` is an unsigned, permissionless extrinsic (any account can submit it, gated only by mempool `validate_unsigned` tag/replay checks, not by identity). Any relayer delivering a batch that includes a hyperbridge-originated, allowlisted request can trivially construct a `signer` field of >32 bytes that decodes as a `Signature` enum with an attacker-chosen (unowned) address and garbage signature bytes — no special privileges, timing, or race conditions are required, and the state/commitment verification of the request contents themselves is unaffected.

### Recommendation
Require `extract_signer` (and `decode_receipt_relayer`) to actually invoke `Signature::verify()` against a well-defined message (e.g., the request/response commitment) before accepting the embedded address/public key as the delivering relayer, rather than trusting the presence of a well-formed `Signature` wrapper. Reject any `signer` payload whose signature does not verify, falling back to treating it as a raw address only when it is exactly the expected raw length (≤32 bytes) with no purported signature attached.

### Proof of Concept
1. Attacker (or any relayer) observes a hyperbridge-originated `PostRequest` that is allowlisted for `OutboundRequestDeliveryReward`.
2. Attacker submits `handle_unsigned` on the destination chain with a `RequestMessage` containing this request and a valid membership proof, but sets `signer = Signature::Evm { address: <random 20 bytes with no known private key>, signature: <65 zero/garbage bytes> }.encode()`.
3. `extract_signer` (`modules/pallets/ismp/src/host.rs:351-359`) decodes this successfully (SCALE decode never checks cryptographic validity) and returns the random address via `Signature::signer()` (`modules/utils/crypto/src/verification.rs:109-115`), which is stored in `RequestReceipts[commitment]`.
4. Any legitimate relayer subsequently calls `claim_outbound_request_delivery_reward` with a correctly-signed `OutboundRequestDeliveryClaim`; the on-chain check recovers their real signer address and compares it to the random address proven from `RequestReceipts[commitment]` — they never match, so the claim is rejected with `OutboundRequestSignerMismatch` for as long as the commitment exists, permanently freezing the delivery reward for that request.

fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}
