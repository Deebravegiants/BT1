### Title
Unallowlisted swap-route venues can execute arbitrary token transfers under caller authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
A user-controlled `StrategySwap` payload can select arbitrary route venue code that runs beneath the caller’s `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` authorization. A malicious venue can request an unrelated token transfer from the caller; if the caller signs the authorization tree returned by simulation, that transfer succeeds independently of the protocol’s measured swap-input/output checks. This is a Medium-severity theft-of-user-funds analog to loading attacker-selected components through an unchecked request parameter. [1](#0-0) [2](#0-1) 

### Finding Description
`StrategySwap` is an opaque `Bytes` value supplied directly by the strategy caller rather than a controller-validated venue list. [1](#0-0) 

`swap_collateral` authorizes an account owner or delegate and forwards its `swap` parameter into the shared withdraw-and-swap strategy path. [3](#0-2) [4](#0-3) 

The same route parameter is exposed through `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [5](#0-4) [6](#0-5) [7](#0-6) 

`swap_tokens` forwards the opaque payload to the configured aggregator and authorizes only one exact input-token transfer for the router. [8](#0-7) 

The controller’s post-call checks bound only the controller’s measured input spend and require positive output; they do not inspect child calls made by route-selected venue code or constrain authorization side effects on the caller’s other wallet assets. [9](#0-8) [10](#0-9) 

The project’s threat model confirms that route payloads can name unallowlisted pool and token addresses and that a route-selected contract can place a caller-funded token transfer beneath the caller’s authorization entry. [11](#0-10) 

### Impact Explanation
An attacker can steal arbitrary tokens held by a victim if the victim signs a poisoned authorization tree produced during transaction simulation. [12](#0-11) 

The malicious transfer is not limited to the swap input because it can target a completely unrelated wallet token and a different recipient. [13](#0-12) [14](#0-13) 

The protocol can simultaneously settle a fair-looking swap and pass its measured output and final account checks, so the theft is not prevented by the controller’s accounting boundary. [9](#0-8) [15](#0-14) 

### Likelihood Explanation
An unprivileged attacker can deploy a malicious venue and distribute a route that names it; exploitation requires a victim to submit and sign the poisoned strategy transaction rather than any privileged protocol action. [16](#0-15) [17](#0-16) 

Simulation records the unrelated wallet transfer as a child of the caller’s `swap_collateral` authorization, making the attack dependent on route construction and wallet/client authorization presentation rather than protocol compromise. [18](#0-17) 

The threat model explicitly places responsibility on clients to decode routes and reject authorization trees containing unexpected children, which indicates that unsigned or honestly rejected trees do not execute the theft. [12](#0-11) [19](#0-18) 

### Recommendation
Restrict route venues to governance-approved contracts or decode and validate the route at the controller boundary before invoking the router. [8](#0-7) [1](#0-0) 

Until venue allowlisting exists, wallets and route-generating clients must treat any child authorization outside the expected input transfer as fatal and refuse to sign the authorization tree. [12](#0-11) 

### Proof of Concept
1. The attacker deploys a venue contract whose swap entry point calls `token.transfer(victim, attacker, amount)` on an unrelated token held by the victim. [17](#0-16) 

2. The attacker encodes that venue address into the `swap: Bytes` argument supplied to `Controller::swap_collateral`. [20](#0-19) [13](#0-12) 

3. The victim invokes `swap_collateral(caller, account_id, current, amount, new, swap)` while holding collateral and an unrelated wallet-token balance. [20](#0-19) [21](#0-20) 

4. The controller authorizes the expected input transfer and invokes the configured router with the attacker-controlled route payload. [22](#0-21) 

5. The route causes the malicious venue to run, and its unrelated token transfer is recorded as a child invocation beneath the victim’s `swap_collateral` authorization. [18](#0-17) 

6. If the victim signs that returned tree, the unrelated wallet-token balance moves to the attacker while the nominal swap output is still credited. [23](#0-22) 

7. If the victim signs only the expected root authorization without the rogue child transfer, the host rejects the transfer and rolls the entire call back. [19](#0-18)

    }

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    s.t.env.mock_all_auths();

    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((

            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

        sub_invocations: std::vec![],
