### Title
Unbounded in-memory growth of the intents-coprocessor RPC `BidCache` from unvalidated mempool `place_bid` extrinsics enables node memory-exhaustion DoS - (File: `modules/pallets/intents-coprocessor/rpc/src/lib.rs`)

### Summary
The intents-coprocessor mempool bid watcher caches every `place_bid` extrinsic it observes in the transaction pool into an in-process `HashMap<H256, OrderBids>`, keyed by attacker-supplied `commitment` and carrying up to 1 MB of `user_op` payload per entry, with pruning only on a periodic TTL sweep. Because caching happens on tx-pool admission rather than after successful on-chain execution, and `commitment` is never checked against a real existing order, an unprivileged, funded account can flood the cache with unique commitments faster than the TTL sweep reclaims them, growing memory without bound — the same "unbounded resource consumption from repeated user-input calls in a long-running process" bug class as CVE-2023-34109.

### Finding Description
`BidCache::insert` [1](#0-0)  inserts a new `OrderBids` entry per distinct `commitment` into `bids: RwLock<HashMap<H256, OrderBids>>` [2](#0-1) , with no cap on the number of distinct commitments and no cap on total memory consumed. Removal only happens via a TTL sweep triggered on a fixed timer tick in `run_bid_watcher` [3](#0-2) , so growth between ticks (or growth that outpaces the tick interval) is unbounded.

Entries are populated purely from the tx pool's "ready" notification stream, before block inclusion or extrinsic execution: `extract_bid` decodes any `place_bid` call from a pool transaction and pushes it into the cache as soon as the transaction is validated and ready [4](#0-3) . The runtime's `validate_transaction`/pool-admission logic only checks signature, nonce, and fee payability — it does not run the pallet's dispatch body, so a transaction can become "ready" (and thus cached) even if it would later fail on-chain (e.g. `InsufficientBalance` for the storage deposit in `place_bid`) [5](#0-4) .

Critically, `place_bid` never validates that `commitment` corresponds to any real, existing order — any `H256` is accepted [6](#0-5) . Combined with a `user_op` payload of up to 1 MB (`BoundedVec<u8, ConstU32<1_048_576>>`) [7](#0-6) , this lets an attacker sign a stream of low-fee `place_bid` transactions with unique random commitments and large `user_op` bodies, each of which populates a new, unbounded `HashMap` entry in every node's local RPC process — with no protocol-level cap analogous to the `MAX_SUBSCRIPTIONS`/`BoundedVec` FIFO-with-eviction pattern used elsewhere in the codebase (e.g. `pallet-bandwidth`'s `Allowance` list, capped and evicting at 1024 entries) [8](#0-7) .

This is structurally the same defect pattern as CVE-2023-34109: a user-input-driven collection in a long-running process is extended on every call with no upper bound, and only a slow/soft time-based cleanup exists to shrink it, which an attacker can simply outrun.

### Impact Explanation
An unprivileged attacker who controls a funded account (only enough balance to pay transaction fees, not the storage deposit) can drive the `BidCache` on any node running the intents-coprocessor RPC watcher (`run_bid_watcher`/`IntentsRpcHandler`) to unbounded memory growth, exhausting node memory and crashing the process. This is a Denial-of-Service against collators/full nodes serving bid discovery for the Intent Gateway, degrading or halting solver/filler bid discovery (`intents_getBidsForOrder`, `intents_subscribeBids`) and the intents order-matching route — a concrete "route unable to deliver messages/bids" outcome reachable from a single class of unprivileged, dispatched transaction, matching the Medium-severity CVSS profile of the reported analog (network-reachable, no privilege, requires interaction but no complex preconditions).

### Likelihood Explanation
High likelihood given preconditions: the attacker needs only a funded account able to pay transaction fees (no privileged role, no successful on-chain state change required), and can submit many `place_bid` transactions with distinct random commitments and near-maximum `user_op` payloads faster than the fixed cleanup interval reclaims them. The bug requires no cryptographic break, no admin/governance access, and works purely through the public transaction-submission path that any relayer/filler/bidder uses.

### Recommendation
- Cap `BidCache`'s total size and/or distinct-commitment count (e.g., an LRU/bounded structure similar to the `BoundedVec` + oldest-eviction pattern already used in `pallet-bandwidth`), rejecting or evicting before insertion rather than only sweeping by TTL on a timer.
- Reduce or bound total memory pressure by capping per-entry `user_op` size cached in-memory (independent of the on-chain 1 MB bound) and/or limiting entries per source account/IP.
- Consider deferring cache population until the extrinsic actually executes successfully on-chain (or at least performing a cheap pre-check, e.g., verifying the account can cover the storage deposit) rather than caching on mere pool admission.
- Shrink `cleanup_interval`/`ttl` or make eviction proportional to arrival rate so cache growth cannot outpace cleanup during a burst.

### Proof of Concept
1. Attacker funds an account with only enough balance to pay transaction fees (not the `place_bid` storage deposit).
2. Attacker generates a large number of `place_bid(commitment_i, user_op_i)` extrinsics, each with a fresh random `commitment_i` (no real order required) and `user_op_i` sized close to the 1 MB bound, signed with increasing nonces.
3. Attacker broadcasts these transactions to a target node faster than `run_bid_watcher`'s `cleanup_interval`. Each transaction passes pool `validate_transaction` (valid signature/nonce/fee) and becomes "ready," triggering `extract_bid` + `bid_cache.insert(...)` regardless of whether it will later fail with `InsufficientBalance` on execution.
4. `BidCache`'s `HashMap<H256, OrderBids>` grows unbounded in the node's RPC process memory, eventually exhausting available memory and crashing the node/collator process, disrupting `intents_getBidsForOrder`/bid-discovery service for legitimate solvers.

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

pub async fn run_bid_watcher<P, Block, T, Extra>(
	pool: Arc<P>,
	bid_cache: Arc<BidCache>,
	bid_sender: broadcast::Sender<RpcBidInfo>,
	cleanup_interval: Duration,
) where
	Block: BlockT,
	P: TransactionPool<Block = Block> + 'static,
	T: pallet_intents_coprocessor::Config,
	T::RuntimeCall: frame_support::traits::IsSubType<pallet_intents_coprocessor::Call<T>>
		+ DecodeWithMemTracking,
	T::AccountId: Encode + From<[u8; 32]> + DecodeWithMemTracking,
	Extra: DecodeWithMemTracking + Send + 'static,
{
	use futures::StreamExt;

	let mut stream = pool.import_notification_stream();
	let mut timer = tokio::time::interval(cleanup_interval);

	loop {
		tokio::select! {
			Some(tx_hash) = stream.next() => {
				let tx = match pool.ready_transaction(&tx_hash) {
					Some(tx) => tx,
					None => continue,
				};

				let extrinsic_bytes = tx.data().encode();

				if let Some((commitment, filler, user_op)) = extract_bid::<T, Extra>(&extrinsic_bytes) {
					log::info!(
						target: LOG_TARGET,
						"bid in mempool for {commitment:?}",
					);
					if let Err(e) = bid_cache.insert(commitment, filler.clone(), user_op.clone()) {
						log::warn!(target: LOG_TARGET, "failed to cache bid: {e}");
						continue;
					}

					let _ = bid_sender.send(RpcBidInfo { commitment, filler, user_op });
				}
			}
			_ = timer.tick() => {
				if let Err(e) = bid_cache.remove_expired() {
					log::warn!(target: LOG_TARGET, "failed to clean bid cache: {e}");
				}
			}
		}
	}

		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::place_bid())]
		pub fn place_bid(
			origin: OriginFor<T>,
			commitment: H256,
			user_op: BoundedVec<u8, ConstU32<1_048_576>>,
		) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Validate user_op is not empty
			ensure!(!user_op.is_empty(), Error::<T>::InvalidUserOp);

			// Phantom orders have stricter rules: one bid per filler, no updates, and only
			// within the configured acceptance window after the order was registered. Every
			// chain's active order is checked, not just the most recently generated one.
			if let Some(active) = CurrentPhantomOrder::<T>::get() {
				if let Some((_, info)) = active.iter().find(|(c, _)| *c == commitment) {
					let window: BlockNumberFor<T> = Self::phantom_bid_window().into();
					ensure!(
						frame_system::Pallet::<T>::block_number() <= info.created_at_block + window,
						Error::<T>::PhantomOrderBidWindowClosed
					);
					ensure!(
						!Bids::<T>::contains_key(&commitment, &filler),
						Error::<T>::DuplicatePhantomBid
					);
				}
			}

			// If a bid already exists, unreserve the old deposit first
			if let Some(old_deposit) = Bids::<T>::get(&commitment, &filler) {
				<T as Config>::Currency::unreserve(&filler, old_deposit);
			}

			let deposit = Self::storage_deposit_fee();

			// Reserve the new deposit
			<T as Config>::Currency::reserve(&filler, deposit)
				.map_err(|_| Error::<T>::InsufficientBalance)?;
