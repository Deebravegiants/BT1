### Title
Unchecked `.as_u64()` truncation of the swap-input amount in `SwapBaseOut`/`SwapBaseOutV2` allows near-free pool draining - (File: `program/src/processor.rs`)

### Summary
The base-out swap handlers compute the required input amount as a `U128` value and then convert it to `u64` using the uint crate's raw `.as_u64()`, which silently truncates to the low 64 bits instead of returning an error when the value does not fit — unlike `Calculator::to_u64()` elsewhere in the codebase, which uses a checked `try_into` and returns `AmmError::ConversionFailure` on overflow. This is functionally the same bug class as CVE‑2016‑2842: an unverified/unchecked operation (there, a memory allocation; here, a narrowing numeric conversion) is trusted to succeed, and when it doesn't, the program silently proceeds with a corrupted value instead of failing safely.

### Finding Description
`Calculator::swap_token_amount_base_out` computes `swap_in_before_add_fee` as `coin_or_pc_reserve * amount_out / (opposite_reserve - amount_out)` in `U128` arithmetic [1](#0-0) . Because `amount_out` is chosen by the caller and can be set arbitrarily close to the opposing reserve, the denominator `(reserve - amount_out)` can be driven to a very small value (as low as 1), making the numerator/denominator ratio grow to a magnitude far beyond `u64::MAX` while still fitting comfortably inside the 128-bit `U128` type used for the intermediate math (`checked_mul`/`checked_ceil_div` do not panic here because the operation is valid at the U128 level).

In `process_swap_base_out` (and the analogous `V2` path), this large `U128` result is then narrowed with a bare `.as_u64()` call rather than the checked `Calculator::to_u64()` helper: [2](#0-1) 

`.as_u64()` on the `uint` crate's `U128`/`U256` types truncates to the low 64 bits with no error path — it never fails, so an attacker can pick `swap.amount_out` such that the true required input is astronomically large but the truncated `swap_in_after_add_fee` value that the program actually uses is small (or even zero-ish), because the attacker effectively controls which low 64 bits survive the truncation by choosing `amount_out`.

That truncated (wrong) value is then used for every downstream safety check and for the actual token transfer amount: [3](#0-2) 

The same unchecked pattern exists in the `SwapBaseOutV2` handler: [4](#0-3) 

For contrast, other conversions in the math module go through the checked helper that fails cleanly on overflow instead of wrapping: [5](#0-4) [6](#0-5) 

### Impact Explanation
Because `user_source.amount < swap_in_after_add_fee`, `swap.max_amount_in < swap_in_after_add_fee`, and the actual `token_transfer` all use the truncated value, an attacker submitting `SwapBaseOut`/`SwapBaseOutV2` with `amount_out` chosen to make the true required input overflow `u64` can pay a token amount far smaller than what the constant-product invariant actually requires while still receiving `swap.amount_out` of the opposite token transferred out of the AMM vault via `Invokers::token_transfer_with_authority`. This directly breaks pool solvency and lets an unprivileged swapper drain LP/pool funds, which is a concrete theft-of-funds / insolvency impact reachable from a single attacker-crafted transaction with no special privileges — squarely in scope (swap instructions, swap math, SPL token CPIs in `invokers.rs`).

### Likelihood Explanation
The path is reachable by any unprivileged user through the standard `SwapBaseOut`/`SwapBaseOutV2` instructions with attacker-chosen `amount_out` and `max_amount_in`, requiring only that a pool with sufficiently large reserves exist (reserves are `u64` and can be up to ~1.8×10^19, well within normal token supplies for high-decimal SPL tokens), and no signer/permission beyond a normal swap is needed, making this highly likely to be practically exploitable once a pool with large enough reserves is targeted.

### Recommendation
Replace the raw `.as_u64()` calls in `swap_in_after_add_fee` computations (and any other place a `U128`/`U256` result is narrowed for use in transfer amounts or comparisons) with `Calculator::to_u64()` (or an equivalent checked `try_into`) so that overflow during the narrowing conversion causes the instruction to fail with `AmmError::ConversionFailure` instead of silently using a wrapped/truncated value.

### Proof of Concept
1. Identify or set up a pool where `total_coin_without_take_pnl` and `total_pc_without_take_pnl` are large (near `u64::MAX` scale, achievable with high-decimal tokens).
2. Submit `SwapBaseOut` (or `SwapBaseOutV2`) with `swap.amount_out` set to a value extremely close to the opposing reserve (e.g., `reserve - 1`), so that `swap_in_before_add_fee = other_reserve * amount_out / (reserve - amount_out)` computed in `Calculator::swap_token_amount_base_out` [1](#0-0)  produces a `U128` value exceeding `u64::MAX`.
3. In `process_swap_base_out`, this value is multiplied by `swap_fee_denominator` and divided, still exceeding `u64::MAX`, then truncated via `.as_u64()` [7](#0-6)  into a small/attacker-influenced `swap_in_after_add_fee`.
4. Because all downstream checks (`user_source.amount < swap_in_after_add_fee`, `swap.max_amount_in < swap_in_after_add_fee`) use this truncated value, the transaction passes with a small `user_source.amount`, and `Invokers::token_transfer` moves only the truncated (small) amount into the vault while `Invokers::token_transfer_with_authority` sends the full attacker-chosen `swap.amount_out` out of the vault [8](#0-7) , draining the pool far beyond what the constant-product formula should have allowed for the tokens actually paid in.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
