### Title
Fee-on-transfer/deflationary tokens cause escrow over-crediting and insolvency in the Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.sol` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) escrows the *requested* input amount from `order.inputs[i].amount` instead of the amount the contract actually received via `safeTransferFrom`. This is the same class of bug described in the external report (TickLogic.sol): the contract does not validate that the expected amount was transferred, so any deflationary/fee-on-transfer ERC20 used as an order input will cause the internal `_orders` accounting to record more tokens than the contract physically holds.

### Finding Description
In `placeOrder`, the commitment and `reducedInputs` (used to populate `_orders[commitment][token]`) are computed directly from `order.inputs[i].amount` — the amount the user *specified*, before any transfer occurs: [1](#0-0) 

The actual token movement for the non-predispatch path then calls `safeTransferFrom` with that same requested amount and never checks the resulting balance delta: [2](#0-1) 

Note that `_orders[commitment][token] += reducedInputs[i].amount;` at line 463 credits escrow based on the pre-fee requested amount, not on what was actually received. This is functionally identical to the `PoolCustodian._deposit` pattern in the external report: `safeTransferFrom` succeeding does not guarantee the full amount arrived if the token charges a transfer fee (e.g. a future USDT fee, or any deflationary/rebasing token).

This is a direct regression compared to the sibling contract at `evm/src/apps/IntentGatewayV2.sol`, which was explicitly hardened against this exact issue: it snapshots `balBefore`, transfers, then computes `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before using that value for fee calculation and escrow crediting: [3](#0-2) 

The Tron fork at `evm/tron/contracts/apps/IntentGatewayV2.sol` omits this actual-received measurement entirely for both the predispatch and direct-transfer branches, reintroducing the vulnerability that the main EVM contract already fixed and covered with dedicated fee-on-transfer tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, etc.).

### Impact Explanation
Because `_orders[commitment][token]` is credited with more tokens than the gateway contract actually holds, later redemption via `withdraw()` (triggered by `RedeemEscrow`/`RefundEscrow` incoming ISMP requests in `onAccept`) will attempt to pay out the inflated amount: [4](#0-3) 

`withdraw` performs a raw low-level `token.call(...transfer...)` and only checks `success`, not that the beneficiary actually received the full `amount`. If the escrowed accounting exceeds the real token balance, either:
- The first attempt to redeem/refund an over-credited order can drain balances belonging to *other* users' orders in the same contract (cross-order insolvency, since all inputs share one custody pool), leading to some legitimate orders being unable to be redeemed/refunded (permanent freezing of funds for those users), or
- Payouts silently short subsequent claimants once the pool is drained.

This satisfies "concrete theft or permanent freezing of funds" — solvers/users with legitimately placed and filled orders can lose access to their escrowed proceeds because the shared escrow pool becomes insolvent due to a single fee-on-transfer/deflationary token order.

### Likelihood Explanation
Likelihood is Medium: it requires an input token used in `placeOrder` to be a deflationary, fee-on-transfer, or rebasing ERC20. Any unprivileged user can submit such an order (the intent gateway accepts arbitrary ERC20 tokens as `order.inputs`), and no admin/governance/privileged role is needed. Given USDT is explicitly cited as at risk of enabling such a fee in the future and rebasing tokens exist and are commonly bridged, this is a realistic condition rather than a purely theoretical one. The bug is only reachable via the Tron deployment of `IntentGatewayV2`.

### Recommendation
Apply the same actual-received measurement pattern used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: snapshot the gateway's token balance before `safeTransferFrom`, compute the actual delta afterward, and use that measured amount (not the caller-supplied `order.inputs[i].amount`) for protocol fee calculation, commitment hashing, and `_orders` escrow crediting in both the direct-transfer and predispatch branches. Short term, consider disallowing known-risky tokens (rebasing, fee-on-transfer) from `IntentGatewayV2` inputs until parity with the hardened `evm/src/apps/IntentGatewayV2.sol` implementation is restored.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g. 1% fee) as one of `order.inputs`.
2. User calls `placeOrder` with `inputs[0].amount = 1000e18`; the contract computes `reducedInputs[0].amount` (and the commitment) from the full `1000e18` at `evm/tron/contracts/apps/IntentGatewayV2.sol:362-370`, then calls `safeTransferFrom(msg.sender, address(this), 1000e18)` at line 459, but due to the 1% fee the gateway only actually receives `990e18`.
3. `_orders[commitment][token] += reducedInputs[0].amount` (line 463) credits the escrow with a value derived from `1000e18`, while the contract's real balance of that token increased by only `990e18`.
4. When the order is later filled/redeemed and `withdraw()` is invoked from `onAccept` (RedeemEscrow/RefundEscrow), the escrow mapping claims more tokens exist than the contract holds; paying out this and other pending orders' escrow from the shared token balance will eventually fail or short-pay legitimate claimants, demonstrating insolvency of the shared custody pool.

(The equivalent scenario and expected-vs-actual behavior is already proven via unit tests against the corrected `evm/src/apps/IntentGatewayV2.sol` implementation, e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` in [5](#0-4) , which the Tron contract fails to replicate.)

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
