### Title
Sell-side underflow (Panic 0x11) can permanently freeze `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity` via the `+1` K-slack in `Pair.swap` - ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Bonding.sol])

### Summary
The external report's bug class is an unchecked index/value derived from user-controlled input going out of range of an implicit invariant, causing an array-out-of-bounds panic. The closest reachable analog in this codebase is an **arithmetic-underflow Panic (0x11)** in `Bonding._launchTimeVirtualLtReserve`'s consumers (`canGraduate`, `previewLtUntilGraduation`, `_prepareGraduationLiquidity`) caused by `Pair.swap`'s `(newTokenReserve+1)*(newAssetReserve+1) < _pool.k` slack, which lets `assetReserve` dip by up to 1 wei below the value the K-invariant would otherwise guarantee, in edge cases where `tokenReserve` is pushed toward `totalSupply` by repeated sells. [1](#0-0) 

### Finding Description
`Bonding.canGraduate` and `Bonding.previewLtUntilGraduation` compute the real LT raised by the curve as:
```
realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)
```
where `_launchTimeVirtualLtReserve` recovers the launch-time virtual LT seed as `Pair.k() / Token.TOTAL_SUPPLY()`. [2](#0-1) [3](#0-2) 

`Bonding._prepareGraduationLiquidity` performs the identical unchecked subtraction at graduation time:
```
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
``` [4](#0-3) 

This subtraction is safe **only** as long as `assetReserve >= virtualLtReserve` holds for every reachable pair state. By the K invariant, `assetReserve * tokenReserve >= k = totalSupply * virtualLtReserve`, so as long as `tokenReserve <= totalSupply`, `assetReserve >= virtualLtReserve` should hold mathematically. However, `Pair.swap` does not enforce the strict product `newTokenReserve * newAssetReserve >= k`; it enforces the looser, off-by-one-padded check:
```
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
``` [5](#0-4) 

This slack is explicitly documented as a known analog-relevant design element in the project's own threat model ("Pair.swap's `+1` K slack") alongside the bonding-curve AMM math and overflow cap. Because the check is on `(t+1)(a+1)` rather than `t*a`, a caller executing a sequence of sells that drives `tokenReserve` close to its ceiling (`totalSupply`, reachable when previously-bought tokens are sold back through `Router.sell`) can land on a state where the *true* product `tokenReserve * assetReserve` is strictly less than `k`, i.e. `assetReserve` is up to 1 wei below the value the strict invariant would require — potentially below `virtualLtReserve` at the boundary `tokenReserve == totalSupply`. Any unprivileged trader can reach this state purely through `Zap.sell` → `Bonding.sell` → `Router.sell` → `Pair.swap`, using only public entry points, no privileged role required.

Once `assetReserve < virtualLtReserve` (even by 1 wei), every subsequent call to `canGraduate`, `previewLtUntilGraduation`, and the graduation-triggering internal path (`_enterGraduating` → `_prepareGraduationLiquidity`) reverts with the generic arithmetic-underflow Panic(0x11), because Solidity 0.8.24's checked arithmetic traps the subtraction rather than wrapping — directly analogous to the kernel's array-index-out-of-bounds panic caused by an unvalidated computed value going negative/out-of-range.

### Impact Explanation
If the underflow is reachable at `tokenReserve == totalSupply` (i.e., every token ever bought on the curve has been sold back), the token's curve state becomes permanently un-graduatable and un-tradeable in that direction: `Bonding.buy`'s inline `canGraduate()` check at the end of `_executeBuy` would revert on every subsequent buy, and `triggerGraduation` would revert as well, since both depend on the same subtraction. This would strand the curve's real LT and the creator's/traders' tokens on the bonding curve (never reaching graduation, never redeemable through the normal LP-seeding flow) — a permanent freezing of trader/creator funds, which meets the "Validate" bar for concrete freezing impact.

### Likelihood Explanation
This requires landing on the exact boundary condition (`tokenReserve` at or extremely near `totalSupply`, i.e., every previously-bought token sold back) where the `+1` slack's 1-wei margin can flip the sign of the subtraction. This is a narrow, deterministic-but-hard-to-hit edge case: it depends on precise buy/sell sequencing and rounding, and I was not able to fully construct or verify a concrete calldata sequence proving the underflow is reachable within the tool budget available. The invariant-preserving math elsewhere in the repo (`GraduationInvariants.t.sol`'s `test_inv_virtualReserveAlwaysExceedsRealBalance`) suggests the team has already reasoned carefully about `tokenBalance() < tokenReserve`, but that test does not directly cover the `assetReserve >= virtualLtReserve` invariant under adversarial sell sequences at the `tokenReserve → totalSupply` boundary.

### Recommendation
Have a background engineer:
1. Write a targeted Foundry fuzz/invariant test that drives `tokenReserve` as close to `totalSupply` as possible via repeated `Router.sell` calls (selling back the maximum real token balance obtainable), then asserts `assetReserve >= Pair.k() / Token.TOTAL_SUPPLY()` never breaks.
2. If a break is found, either (a) tighten `Pair.swap`'s invariant check back to the strict, non-padded product `newTokenReserve * newAssetReserve >= k` (removing the `+1` slack) for the specific paths that feed `_launchTimeVirtualLtReserve`'s subtraction, or (b) make `canGraduate`/`previewLtUntilGraduation`/`_prepareGraduationLiquidity` use a saturating subtraction (clamp to 0) the same way `previewLtUntilGraduation`'s `_stageDonationAttack`-style guard already does for the `realBalance >= reserveToken` case, rather than reverting on underflow.
3. Re-run `test/GraduationInvariants.t.sol` and `test/Bonding.t.sol` to confirm no regression to the zero-price-gap and overflow-cap invariants.

        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;

        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
