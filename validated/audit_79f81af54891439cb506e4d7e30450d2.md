The Magic-QR reset action for wifi/mirror calibration is functionally identical to the reported bug class: a privileged state-mutating operation (`MagicResetWifi` / `MagicResetMirror`) is reachable through an unauthenticated, unprivileged input path — a plain regex match on scanned QR-code text — with no operator authorization or backend verification, unlike normal operator/user QR codes which go through `verify_operator_qr_code` (backend HTTP validation).

### Title
Unauthenticated Magic-QR reset actions allow any unprivileged QR scanner to trigger Wi-Fi and mirror-calibration resets - (File: `src/plans/qr_scan/operator.rs`)

### Summary
`qr_scan::operator::Data::try_parse` recognizes special "magic action" QR codes (`magic_action:reset_wifi_credentials`, `magic_action:reset_mirror_calibration`) purely via regex matching, with no cryptographic signature, backend authorization, or operator-identity check. Once matched, `MasterPlan::handle_magic_operator_qr_code` immediately executes `reset_wifi_and_ensure_network` or `reset_mirror_calibration` — unlike ordinary operator QR codes, which must pass `verify_operator_qr_code` against the signup backend before being trusted.

### Finding Description
Operator QR-code scanning parses two categories of codes: normal operator codes (`user::Data`) and "magic" administrative codes matched by `MAGIC_QR_CODE` [1](#0-0) . The `try_parse` function returns `Data::MagicResetWifi` or `Data::MagicResetMirror` for any string matching `magic_action:reset_wifi_credentials` / `magic_action:reset_mirror_calibration`, with no additional validation [2](#0-1) .

These variants are consumed in `handle_magic_operator_qr_code`, which is invoked right after the QR scan, before any backend verification step (`verify_operator_qr_code`) runs: [3](#0-2) 

Contrast this with the normal operator QR-code path, where `Data::Normal` codes are subsequently checked against the signup backend via `verify_operator_qr_code`, which performs an authenticated HTTP request (`basic_auth` with the orb token) before the code is trusted [4](#0-3)  and [5](#0-4) . Magic-action codes never go through this authorization gate — `handle_magic_operator_qr_code` returns `Ok(None)` and short-circuits the flow immediately after executing the reset, bypassing `verify_operator_qr_code` entirely.

The reset actions themselves mutate persistent, security-relevant device state:
- `reset_wifi_and_ensure_network` calls `network::reset()`, which shells out to `wpa-supplicant-interface restore-default-config` and `reconfigure`, wiping the orb's configured Wi-Fi credentials [6](#0-5)  and [7](#0-6) .
- `reset_mirror_calibration` overwrites the mirror calibration state and persists it to disk (`CALIBRATION_FILE_PATH`) [8](#0-7) .

This is the same bug class as the external report: a state-changing function reachable by an unprivileged actor (anyone who can present a QR code to the orb's camera) with no access-control/authorization check analogous to `onlyOwner`, whereas the "normal" code path in the same module (operator QR verification) does have that check.

### Impact Explanation
An unprivileged person — not necessarily an authorized operator — can print or display a `magic_action:reset_wifi_credentials` or `magic_action:reset_mirror_calibration` QR code and present it to the orb's camera during the idle/operator-scan phase. This:
- Wipes the orb's Wi-Fi configuration, forcing it into a disconnected/reconfiguration state and disrupting signup availability (denial of service), and
- Silently overwrites/persists mirror calibration data, degrading iris-capture accuracy for all subsequent signups without operator awareness or consent.

Both are reachable "before" any identity/authorization check runs, matching the report's core issue (critical unprivileged state mutation with no access control) and can cause operational disruption/DoS and integrity degradation of the signup process, analogous in severity class to the original finding.

### Likelihood Explanation
Likelihood is high in terms of reachability: the only precondition is presenting a piece of paper/screen with the magic QR text during the operator QR-scan phase — no privileged credentials, backend token, or physical device access are required, matching the "unprivileged-user analog" constraint of this task.

### Recommendation
Require the magic-action QR payload to be cryptographically signed/authorized by a trusted operator/backend (e.g., verify against the signup backend, similar to `verify_operator_qr_code`, or require a signature checked with a known public key) before executing `reset_wifi_and_ensure_network` or `reset_mirror_calibration`. At minimum, gate these actions behind the same backend authorization check used for normal operator QR codes rather than trusting a bare regex match.

### Proof of Concept
1. Generate a QR code encoding the literal string `magic_action:reset_wifi_credentials` (or `magic_action:reset_mirror_calibration`), as validated by the existing unit test fixtures [9](#0-8) .
2. Present it to the orb during the operator-QR-scan idle phase (`scan_initial_qr_codes` / `scan_remaining_qr_codes`) [10](#0-9) .
3. `try_parse` matches `MAGIC_QR_CODE` and returns `Data::MagicResetWifi`/`Data::MagicResetMirror`.
4. `handle_magic_operator_qr_code` executes the reset immediately — no operator credential, backend token, or signup-backend authorization call occurs beforehand.

                orb.ui.qr_scan_fail(QrScanSchema::Operator);

        }
