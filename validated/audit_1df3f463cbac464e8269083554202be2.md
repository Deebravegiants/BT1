### Title
`CallDispatcher.dispatch` has no caller restriction, letting any unprivileged address sweep tokens/ETH the contract holds mid-execution across app spheres - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is a single shared, unrestricted-access contract used by multiple independent trust domains — `HyperFungibleToken`/`WrappedHyperFungibleToken` (mint/unlock-then-call) and `IntentGatewayV2` (predispatch/postdispatch swap-then-escrow). Its `dispatch(bytes)` function is `external` with **no access control whatsoever** — not `onlyHost`, not an allowlist of calling apps, nothing. Any account (an unprivileged relayer, bot, or ordinary EOA) can call it directly with an arbitrary ABI-encoded `Call[]` and force it to execute calls with arbitrary `to`/`value`/`data`, moving out any native ETH or ERC-20 balance the dispatcher happens to hold at that moment.

### Finding Description
`CallDispatcher.dispatch` decodes an attacker-supplied `Call[]` and executes each entry with `to.call{value: call.value}(call.data)`, with the only check being that `to` has code: [1](#0-0) 

There is no `msg.sender` restriction, and the interface documents it as dispatching "untrusted call(s)": [2](#0-1) 

The dispatcher is meant to be invoked only by `HyperFungibleToken.onAccept` (after minting to the dispatcher) or `IntentGatewayV2` (predispatch/postdispatch, after moving order assets to it) as an atomic step: [3](#0-2) [4](#0-3) 

But because the contract accepts native ETH via `receive()` and can end up holding ERC-20 balances mid-flow (e.g. slippage/dust from a swap encoded in one app's `Call[]`, or unlimited-allowance approvals that the docs explicitly warn about), any residual value sitting in this single shared "sphere" is not bound to the app/session that put it there. Anyone — with no privilege, no relayer role, no ISMP proof — can call `CallDispatcher.dispatch()` directly, before the intended follow-up call executes or whenever dust remains, and redirect that balance to an address of their choosing: [5](#0-4) 

This is a textbook CWE-669 (Incorrect Resource Transfer Between Spheres): a resource (ETH/ERC-20 balance) that should only ever move under the control of the specific calling application's authorization context (an authenticated ISMP `onAccept`, or an in-flight `fillOrder`/`placeOrder` transaction) is instead reachable and transferable by any caller in the unprivileged "external" sphere, because the shared executor contract enforces no caller/session binding.

### Impact Explanation
If `CallDispatcher` ever holds a nonzero balance outside the single atomic transaction that deposited it — due to (a) an ERC-20 `approve` with unlimited allowance left by a `Call[]` (explicitly called out as a risk in the docs), (b) slippage dust from a swap not fully swept in the same `Call[]`, or (c) a race where value is sent to the dispatcher in one transaction and the intended follow-up call is submitted in a later transaction — any unprivileged address can steal that balance outright by calling `dispatch()` directly with a `Call[]` that transfers the tokens/ETH to itself. Because the dispatcher is shared across every `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` deployment that points at it, this is a cross-application theft primitive, not scoped to a single order or transfer. This satisfies "concrete theft ... of funds" under a High severity rating.

### Likelihood Explanation
Exploitation requires the dispatcher to be holding value it hasn't yet spent, which the docs themselves flag as a live risk ("Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution"). Any application integrator who follows the documented pattern with an unlimited approval, or any swap with slippage that leaves dust, creates an exploitable window. An attacker does not need any special role — just to watch the dispatcher's balance and front-run/back-run with their own `dispatch()` call, which is always public and reachable in a single transaction.

### Recommendation
Restrict `CallDispatcher.dispatch` to only the authorized calling application(s), e.g. via an `onlyAuthorizedCaller` allowlist (HFT/WrappedHFT/IntentGatewayV2 instances) set at deployment/configuration, or make the dispatcher single-use/ephemeral per call (e.g. deploy a minimal-proxy dispatcher per invocation via `CREATE2`/`CREATE` so no shared, cross-caller balance can ever accumulate). At minimum, require exact-amount approvals and a mandatory final "sweep remainder back to caller" step enforced by the dispatcher itself rather than relying on well-behaved `Call[]` encoders, and never let the shared contract retain value across transaction boundaries.

### Proof of Concept
1. An integrator (or Hyperbridge's own `IntentGatewayV2` postdispatch/predispatch swap path) encodes a `Call[]` that approves a router for `type(uint256).max` on an ERC-20 held by `CallDispatcher`, then calls `swapExactTokensForTokens`, as shown in the documented pattern: [6](#0-5) 
2. If the swap leaves any dust (common with `swapTokensForExactTokens`/slippage) or the approval remains outstanding after the batch, the ERC-20/ETH balance sits in `CallDispatcher` after the triggering transaction completes.
3. Any external, unprivileged address calls `CallDispatcher.dispatch(abi.encode(callsToSelf))` directly — nothing prevents this, since `dispatch()` has no caller check: [1](#0-0) 
4. The attacker's `Call[]` transfers the residual ERC-20/ETH balance to an address they control, stealing funds that belonged to the legitimate order/transfer flow.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
