### Title
Missing duplicate-input-token check in `placeOrder` allows escrow-key collision and over-release of duplicated funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` in the Tron `IntentGatewayV2` credits escrow using `_orders[commitment][token] += reducedInputs[i].amount;` [1](#0-0) [2](#0-1) , with no check that a token address is not repeated across multiple `order.inputs[]` entries. The mainline EVM `IntentGatewayV2` was patched to reject this exact condition with `if (_orders[commitment][token] != 0) revert InvalidInput();` [3](#0-2) , and a regression test documents the prior bug as "same-chain partial fills over-release repeated input escrow" [4](#0-3) . The Tron fork does not carry this fix.

### Finding Description
The root cause mirrors CVE-2024-42698's bug class: a per-index accounting structure (here, escrow keyed only by `token` address rather than by input index) fails to validate that an index/key is unique before crediting/decrementing against it, letting an attacker "duplicate" value tied to that key.

In the Tron gateway, `order.inputs` is an array of `TokenInfo{token, amount}` legs. `placeOrder` never rejects two legs sharing the same `token` address; instead, both legs' escrow amounts are summed into the single `_orders[commitment][token]` slot [5](#0-4) . The fill/withdraw path (shared logic pattern shown in `IntrinsicIntents.sol`, which the same audit history in this repo shows governs escrow release) computes, on a fully-filled output leg, `escrowedAmount = _orders[commitment][token]` — i.e., it reads back the *entire accumulated* escrow for that token rather than the proportional share owed to that specific input leg [6](#0-5) . Because the map is keyed only by token address, when two input legs use the same token, filling multiple output legs that each resolve to `amountFilled == totalRequired` can each pull the full combined escrow balance for that token, releasing it more than once — an over-release/duplication of escrowed funds, directly analogous to REI's failure to validate slot index before decrementing stack count.

### Impact Explanation
This allows a solver filling a same-chain (or equivalent) order with duplicate input tokens to receive escrow disbursed multiple times for what should be a single aggregated balance, resulting in direct theft of escrowed user funds from the gateway — a concrete theft-of-funds impact, matching the required Medium+ bar (funds theft via duplication).

### Likelihood Explanation
Reachable by any unprivileged user submitting a single `placeOrder` transaction with two or more input legs referencing the same token address, followed by a solver-submitted `fillOrder`, both of which are permissionless entry points. No governance, admin, or privileged role is required, and the attacker only needs to control the order construction (as order creator) and cooperate with (or act as) the filling solver.

### Recommendation
Add the same duplicate-input-token rejection used in the patched EVM contract to the Tron `IntentGatewayV2.placeOrder`: before/while crediting `_orders[commitment][token]`, revert if the slot is already non-zero (`if (_orders[commitment][token] != 0) revert InvalidInput();`), mirroring `evm/src/apps/IntentGatewayV2.sol` lines 364-368. Alternatively, key escrow storage by `(commitment, inputIndex)` instead of `(commitment, token)` so that duplicate token legs cannot collide.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: 1200}, {token: USDC, amount: 1000} ]`.
2. `_orders[commitment][USDC]` accumulates to `2200` via the two `+=` credits at lines 441/463, with no revert (contrast with the patched mainline behavior tested in `testRevert_PlaceOrder_DuplicateInputTokens`, which expects `InvalidInput` for exactly this input [7](#0-6) ).
3. A solver fills the order's corresponding output legs; each time a leg fully fills (`amountFilled == totalRequired`), the withdrawal path reads `_orders[commitment][USDC]` (the full `2200`) rather than the leg's proportional share, and credits it to the solver.
4. Repeating this across the two output legs releases the aggregated `2200` escrow more than once, duplicating funds beyond what was actually escrowed per leg.
