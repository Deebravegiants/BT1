### Title
Webhook Shop/Topic Identity Spoofing via Fields Not Covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `hmac` signature exclusively from the raw request body (`to_signable_string` returns only `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` fields are all read from HTTP headers that are never covered by that signature. `ShopifyAPI::Webhooks::Registry.process` validates only the body-derived HMAC and then unconditionally trusts these header-derived fields to build the `WebhookMetadata` object handed to the app's handler as the authoritative tenant/topic identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature to the body only: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers with no cryptographic binding to that same value: [2](#0-1) 

`Registry.process` validates only the HMAC computed over the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.topic` for handler dispatch and `request.shop` for tenant attribution when constructing `WebhookMetadata`: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field, and the gem's own documentation instructs app developers to use `data.shop` as the reliable tenant identifier for dispatching downstream work: [4](#0-3) [5](#0-4) 

The identity binding broken here is:
`HMAC-verified(bytes) == bytes acted on for tenant attribution`

but the actual behavior is:
`HMAC-verified(raw_body only) != (shop header, topic header) used for tenant attribution and dispatch`

Because the api_secret_key (client_secret) used to compute the HMAC is a single per-app secret shared by every merchant who installs the app — not per-shop — any unprivileged user can install the app on their own store, receive genuine webhooks with valid `(body, hmac)` pairs signed with that shared secret, and then replay the identical body+hmac to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers with values naming a different, victim shop. `HmacValidator.validate` still succeeds because it only re-derives the signature from the (unchanged) body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the attacker-supplied body originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary between shops of a multi-tenant Shopify app: an attacker with an ordinary/free store installation of the target app can forge webhook events that the app attributes to any other shop by spoofing the `shop-domain` (and `topic`) headers on a replayed, HMAC-valid body. Depending on how the host app (following this gem's documented pattern of trusting `data.shop`) persists or acts on webhook data, this enables cross-tenant data injection/corruption, spoofed mandatory-compliance webhooks (e.g. `shop/redact`, `customers/redact`), or triggering per-shop background jobs against a victim's tenant record — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate-to-high: the only prerequisite is installing the target app on any store (an action available to any unprivileged internet user for public apps), after which the attacker legitimately receives HMAC-valid webhook bodies signed with the app's single shared secret and can freely resend them with forged `shop`/`topic` headers, since no part of this gem binds those headers to the signature.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed material verified against the HMAC (or otherwise cryptographically bind the shop identity to the request, e.g. by requiring per-shop webhook secrets or validating `shop` against an independently trusted source such as a known/installed-shops list before dispatch), rather than trusting header values that sit outside the HMAC's coverage.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`.
2. Capture a real webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid against the app's shared `api_secret_key`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
3. Resend the same body `B` and same `hmac` `H` to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally another `x-shopify-topic`, e.g. `shop/redact`).
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) still returns `true` because it only checks the unchanged body/hmac pair.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)` and invokes the app's handler, which — per the gem's documented usage — treats `data.shop` as the trusted tenant identifier for `victim-shop.myshopify.com`, even though the payload actually belongs to the attacker's own shop.
