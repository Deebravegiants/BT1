Confirmed: the vulnerability is fully reproducible from the in-scope code path. The documentation explicitly states `Registry.process` "will verify the request did indeed come from Shopify" and the handler is expected to trust `data.shop` (docs example: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), yet the shop identity is never part of what's cryptographically verified.

### Title
Webhook shop-domain identity not bound by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which signs only `request.to_signable_string` (the raw body). The `shop` value — read from the `X-Shopify-Shop-Domain` header — is never included in the signed content, yet it is passed straight through as the trusted tenant identifier to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
while `shop` is parsed from an unauthenticated header: [2](#0-1) 
`Registry.process` validates only this body-bound HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop`: [3](#0-2) 
`HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` and the app's single, shared `api_secret_key` — the same secret is used to sign webhooks for every shop that installs the app: [4](#0-3) 

Because the HMAC secret is per-app (not per-shop) and the signed content excludes the shop identity, this breaks the intended binding `hmac == HMAC(secret, body ‖ shop)`; in reality `hmac == HMAC(secret, body)`. An attacker who legitimately installs the target app on their own (attacker-controlled) shop will receive genuinely-signed webhooks from Shopify for that shop. They can replay the exact `raw_body` and `hmac` header to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value with a victim shop's domain. `HmacValidator.validate` still returns `true` since it only checks the body, and `Registry.process` forwards `shop: request.shop` (now the victim's domain) to the handler as if it were an authentic event for the victim shop.

### Impact Explanation
The library's own documentation instructs apps to trust `data.shop` as the authoritative tenant identifier once `Registry.process` succeeds ("This will verify the request did indeed come from Shopify") and shows `data.shop` being used directly to route/persist per-tenant work. Any app following this documented pattern is exposed to cross-tenant data confusion: an attacker-controlled webhook payload (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) can be injected under a victim shop's identity, potentially triggering the app's per-tenant fulfillment logic, mandatory GDPR redaction flows, or state changes against a shop the attacker doesn't control. This is a cross-tenant authentication/authorization boundary violation caused directly by this gem's `Webhooks::Request`/`Registry` implementation, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop they control (a normal, unprivileged action available to any Shopify merchant/developer) and be able to send an arbitrary HTTP request to the app's public webhook endpoint with custom headers — no access to `api_secret_key`, tokens, or the victim's credentials is needed. The body and HMAC are captured from a legitimate webhook Shopify sent to the attacker's own shop, then replayed with a forged shop-domain header.

### Recommendation
Bind the shop identity to the signed content, or otherwise cryptographically verify it before trusting it:
- Include the shop domain (and ideally topic/webhook-id) as part of `to_signable_string` for webhook verification, matching it against a value looked up independently (e.g., cross-checking against the session/shop the webhook was registered for), or
- Require host applications to independently verify that `request.shop` corresponds to a shop with an active, known installation/session before acting on the payload, and document this requirement prominently, or
- At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not cryptographically bound to the HMAC and must be revalidated by the app before being trusted as a tenant identifier.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on their own shop "attacker.myshopify.com"
# and receives a real webhook from Shopify:
raw_body = '{"id":1,"note":"hi"}'
real_hmac_header = "<base64 hmac Shopify computed with the app's shared api_secret_key over raw_body>"

# Attacker replays the same body/hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to point at a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_header,   # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app now processes attacker-controlled data as if it originated from "victim-shop.myshopify.com".
```
