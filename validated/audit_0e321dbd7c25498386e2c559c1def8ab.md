### Title
Cross-chain replay of `SubstrateCalldata` signature in `pallet-hyper-fungible-token` due to missing chain/audience binding in the signed payload - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` verifies the `Ed25519`/`Sr25519`/`Ecdsa` signature attached to optional cross-chain calldata, but the signed message only covers `(account_nonce, runtime_call)` — it contains no domain separator identifying the destination chain, the pallet instance, the asset, or the amount/source. This mirrors the reported bug class exactly: a signature/JWT is cryptographically verified, but the "claims" that should scope it (audience/issuer equivalents) are never checked, so a payload captured from one context can be replayed in another.

### Finding Description
In `on_accept`, when `message.data` carries a `SubstrateCalldata{ signature, runtime_call }`, the signature is checked against `keccak256((nonce, runtime_call).encode())` (with an Ethereum-prefix variant for ECDSA): [1](#0-0) 

`nonce` here is `frame_system::Pallet::<T>::account_nonce(beneficiary)` — a per-chain, per-account counter that is `0` for any account that hasn't yet transacted on that particular chain: [2](#0-1) 

Critically, the payload the beneficiary signs contains **no chain identifier** (no genesis hash, no `StateMachine`/`dest`, no pallet instance id) and **no binding to the specific transfer** (asset id, amount, or a request commitment). The pallet's own module id is a fixed, well-known constant shared by every deployment of this pallet: [3](#0-2) 

The `send` extrinsic is fully permissionless and lets any caller choose `params.destination`, `params.recipient`, and arbitrary `params.call_data` (the attacker-controlled envelope carrying the victim's captured signature bytes): [4](#0-3) 

Because the destination is not part of what is signed, the same `SubstrateCalldata{signature, runtime_call}` bytes — once observed (they travel in cleartext inside the ISMP `PostRequest` body/event, or could simply be leaked by the sender-side dApp/relayer) — remain valid on *any* other chain instance of `pallet-hyper-fungible-token` where the beneficiary account also happens to be at the same `account_nonce` (trivially true for any account's first-ever transaction, nonce `0`, which is the common case for fresh accounts being onboarded via a cross-chain transfer). An attacker constructs a new EVM-side `send`/message targeting a different destination chain running the same pallet, embeds the intercepted signature+call, and the pallet dispatches `runtime_call` as `RawOrigin::Signed(beneficiary)` on that unintended chain: [5](#0-4) 

This is the direct analog of the reported CVE: the cryptographic check (Apple JWT signature / here, the account's own signature) passes, but the missing "claims" — chain id / pallet identity, i.e., the equivalent of `aud`/`iss` — mean the artifact is portable across contexts it was never intended for.

Note that the codebase elsewhere recognizes this exact class of bug and defends against it correctly: `beneficiary_message` in the relayer pallet explicitly folds `state_machine` into the signed digest specifically to prevent cross-chain signature replay, and a regression test enforces it: [6](#0-5) [7](#0-6) 
The `hyper-fungible-token` pallet lacks the equivalent protection.

### Impact Explanation
A successful replay lets an attacker cause an arbitrary `RuntimeCall` (subject only to `BaseCallFilter`) to be dispatched with the victim's account as signed origin on a chain the victim never authorized for that call. Given `BaseCallFilter` typically allows ordinary transfers/governance-adjacent calls, this can be used to move funds out of, or take unauthorized actions on behalf of, the beneficiary account on any parachain that (a) runs `pallet-hyper-fungible-token`, and (b) shares the beneficiary's account id (all `sp_core` accounts are cross-chain-portable by design) at a matching nonce. This is "unauthorized app action" / potential theft of funds via forged authorization, reachable from a single unprivileged, permissionless `send` call.

### Likelihood Explanation
Exploitation requires: (1) observing a legitimately signed `SubstrateCalldata` (visible in the source-chain dispatch event/PostRequest body, or leakable from any off-chain component that constructs it), and (2) a second chain running the same pallet where the victim account's nonce matches what was signed — trivially satisfied for a victim's very first cross-chain interaction (nonce 0), which is a common state for newly onboarded users. The attacking transaction itself is a normal, unprivileged `send` call with attacker-supplied destination and calldata, requiring no privileged role.

### Recommendation
Bind the signed payload to a unique execution context: include a chain identifier (e.g., `frame_system::Pallet::<T>::block_hash(0)` / genesis hash or a configured `ChainId`), the pallet's own module id, and ideally the specific request commitment/asset/amount, in the signed digest, e.g. sign `(chain_domain, PALLET_ID, nonce, runtime_call)` instead of `(nonce, runtime_call)`. This mirrors the pattern already used correctly in `beneficiary_message` in `modules/pallets/relayer/src/accumulate.rs`.

### Proof of Concept
1. Victim signs `SubstrateCalldata{ signature: sig_over_keccak256((0u64, runtime_call).encode()), runtime_call }` intending it to run once, on Chain A, via a legitimate `send()` call from an EVM contract to Chain A's `pallet-hyper-fungible-token`.
2. Attacker observes this payload (e.g., from the `PostRequest` body/emitted event on Chain A, or a leaked calldata blob).
3. Attacker calls `send()` on an EVM/HFT-integrated contract, choosing `destination = Chain B` (a different chain also running `pallet-hyper-fungible-token`), setting `recipient = victim`, and `call_data = SubstrateCalldata{ signature: <same sig>, runtime_call: <same call> }` unmodified.
4. On Chain B, the victim account (assumed at nonce 0, e.g. a first-time recipient) has `on_accept` recompute the same `keccak256((0u64, runtime_call).encode())` digest and successfully verify the same signature, then dispatch `runtime_call` as `RawOrigin::Signed(victim)` on Chain B — a chain/context the victim never authorized.
