### Title
Shielded UTXOs for rebasing ERC-20 tokens can desynchronize from the pool's actual token balance, allowing early exiters to extract full face value while leaving later holders permanently under-collateralized - (File: contracts/Hinkal.sol, contracts/HinkalBase.sol)

### Summary
Hinkal accepts any ERC-20 address as `erc20TokenAddresses[i]` with no allowlist or type restriction [1](#0-0)  and represents a user's deposited balance as a fixed numeric `amount` baked into a Poseidon commitment that is stored, unconditionally, in the Merkle tree until it is later nullified/spent [2](#0-1) . For a rebasing token (e.g. stETH), the number of tokens a share is redeemable for changes over time even though the committed face-value amount inside the shielded note never changes. Because `transact()` only checks the balance-conservation equality within a single atomic call (comparing `newBalances`/`oldBalances` measured in the same transaction) and never re-checks that the sum of all outstanding committed note amounts for a token still matches the contract's real token balance, a rebase that happens between deposit and withdrawal desynchronizes "shielded ledger total" from "actual custodied balance" for that token.

### Finding Description
When a user deposits a rebasing token through `transact()`/`prooflessDeposit()`, the contract measures the ERC20 balance change and creates an output commitment whose `amount` field is fixed at deposit time [3](#0-2) [4](#0-3) . This commitment sits in the Merkle tree indefinitely; nothing in `HinkalBase`/`Merkle`/`HinkalHelper` re-derives or rebases this value as the underlying token's balance changes.

When the note is later spent, the circuit only enforces `inTotal + amountChanges[i] === outTotal` for that transaction's inputs/outputs [5](#0-4) , and `Hinkal.sol` transfers out exactly the withdrawer's requested `amountChange`, drawn straight from `transferERC20TokenOrETH`/`transferERC20TokenFromOrCheckETH` [6](#0-5) . None of this logic ties the aggregate face value of all live commitments for a given token to the actual current ERC20 balance held by the Hinkal contract. If the token's balance shrinks via a negative rebase (e.g., stETH slashing) while notes are outstanding, the sum of committed note values for that token now exceeds the real token balance the contract holds. Users who nullify/withdraw first will successfully receive their full recorded `amountChange`; the shrinkage is pushed onto whoever tries to redeem later, whose `transferERC20TokenOrETH` call will fail once the contract's real balance is insufficient (or, if partial withdrawal is chosen, the residual leftover note will forever represent inflated, unbacked value that can never be fully redeemed).

This is the same root cause as the Renzo `WithdrawQueue` finding: an accounting unit (there, `amountToRedeem`; here, the shielded UTXO `amount`) is fixed at the time of a claim/commitment, while the actual custodied token balance for a rebasing asset drifts independently, so "amount recorded" and "amount actually available" silently diverge over time with no mechanism to reconcile them.

### Impact Explanation
This breaks the implicit backing invariant that every unspent commitment in the shielded pool for token `T` is fully redeemable for `T` from the contract's balance. A negative rebase event permanently strands value: some UTXO holders can never fully redeem their committed shielded balance for that token, which is a temporary/permanent freezing of user funds under the accepted impact categories, and other holders extract disproportionately more of the shrunken pool than their fair share (unfair value distribution at other users' expense), analogous to the "protocol/users lose value" outcome sustained as High severity in the source report.

### Likelihood Explanation
This requires the Hinkal deployment to whitelist/accept a rebasing token (e.g., stETH or similar) as a valid `erc20TokenAddresses[i]` entry — nothing in `HinkalHelper.performHinkalChecks`/`dimensionsCheck` prevents this [7](#0-6) . Given that Hinkal's design goal is to support arbitrary DeFi assets (including LSDs, which are commonly shielded for privacy), and there is no explicit guard against rebasing token semantics anywhere in `contracts/`, this is a realistic configuration rather than a purely theoretical one.

### Recommendation
Either (a) explicitly disallow rebasing/elastic-supply tokens as supported `erc20TokenAddresses`, or (b) require that only wrapped, non-rebasing representations (e.g., wstETH rather than stETH) be used as the shielded asset, so that the committed note `amount` remains an accurate, time-invariant claim on the contract's ERC20 balance for that token.

### Proof of Concept
1. Admin/relayer accepts `stETH` (or another rebasing token) as a valid token for `transact()`/`prooflessDeposit()` (no restriction exists to prevent this) [8](#0-7) .
2. Alice and Bob each deposit 100 stETH into Hinkal via `transact()`, producing two shielded UTXO commitments each recording `amount = 100e18`, while the Hinkal contract's actual stETH balance is 200e18.
3. A negative rebase occurs (e.g., simulated slashing) reducing the Hinkal contract's real stETH balance to 180e18, while both commitments still nominally represent 100e18 each (sum 200e18 > 180e18 actual).
4. Alice spends her note first via `transact()`, requesting `amountChange = -100e18`; `transferERC20TokenOrETH` succeeds because 180e18 ≥ 100e18 [9](#0-8) , leaving only 80e18 real stETH in the contract.
5. Bob attempts to spend his note for the full `amountChange = -100e18`; the transfer reverts for insufficient balance, and Bob can only ever redeem at most 80e18 despite his note claiming 100e18 — the shortfall is either permanently unredeemable or forces him to accept a partial withdrawal, leaving a residual note whose face value can never be matched to real balance again.
