### Title
Stale `storageDepositCache` entry causes `estimateWithdrawalFee` to under-report `storageDepositFee`, producing withdrawals with insufficient storage deposit - (`packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.getCachedStorageDepositValue` only writes to `storageDepositCache` when the queried NEAR storage balance is already `>= minStorageBalance` (no deposit needed), and then serves that exact `[minStorageBalance, currentStorageBalance]` tuple for up to one hour (`ttl: 3600000`). Because `OMNI_BRIDGE_CONTRACT`'s storage balance for a token is a shared, mutable, protocol-wide resource that any withdrawal of that token can deplete, the cached "no deposit needed" snapshot can become false well within the TTL window, causing `estimateWithdrawalFee` to keep returning `storageDepositFee = 0n` when a real, positive deposit is actually required on-chain.

### Finding Description
The broken equality is: `feeEstimation.underlyingFees[OmniBridge].storageDepositFee` (computed at estimation time and later consumed by `deriveOmniWithdrawIntentParams` to set `storageDepositAmount` in the `ft_withdraw` intent) must equal the *true* on-chain deficit `minStorageBalance - currentStorageBalance` **at execution time**.

Code path:
- `estimateWithdrawalFee` (`omni-bridge.ts:592-599`) calls `getCachedStorageDepositValue(assetInfo.contractId)` and computes `storageDepositFee = minStorageBalance - currentStorageBalance`, adding it to `totalAmountToQuote` and `underlyingFees.storageDepositFee` only if `> 0n`. [1](#0-0) 
- `getCachedStorageDepositValue` (`omni-bridge.ts:736-761`) fetches `minStorageBalance` and `currentStorageBalance` via RPC, but **only caches the pair when `result[1] >= result[0]`** (i.e., when no deposit is currently needed), with a 1-hour TTL. [2](#0-1) 
- The resulting `feeEstimation.underlyingFees[OmniBridge].storageDepositFee` flows unchanged into `deriveOmniWithdrawIntentParams`, which sets `storageDepositAmount = getUnderlyingFee(feeEstimation, RouteEnum.OmniBridge, "storageDepositFee")` and embeds it directly into the `ft_withdraw` intent as the amount to actually deposit on-chain. [3](#0-2) 

Root cause: `OMNI_BRIDGE_CONTRACT`'s NEP-141 storage balance for a given token is a shared account whose balance can be consumed by *any* withdrawal of that token (from any user, at any time), yet the cache treats a single "sufficient" observation as valid truth for up to an hour. There is no re-validation immediately before intent construction/execution, and no invalidation trigger tied to actual storage consumption events.

Exploit flow: (1) At time T0, attacker (or any user) calls `estimateWithdrawalFee` for `tokenX` while `currentStorageBalance >= minStorageBalance`; the cache is populated with `[minStorageBalance, currentStorageBalance]`. (2) Between T0 and T0+1h, other withdrawals of `tokenX` (by any party) consume enough of `OMNI_BRIDGE_CONTRACT`'s storage balance that it now falls below `minStorageBalance` on-chain. (3) Attacker calls `estimateWithdrawalFee` again for `tokenX` within the TTL window; the stale cache hit returns the same tuple, so `storageDepositFee` is computed as `<=0` and is not added to `underlyingFees.storageDepositFee` or `totalAmountToQuote`. (4) The resulting `feeEstimation` is used to build and sign the withdrawal intent via `deriveOmniWithdrawIntentParams`, embedding `storageDepositAmount = 0`. (5) On execution, the Omni Bridge's `ft_withdraw` needs to perform a real storage deposit that was never provided, causing the withdrawal to fail/get stuck on-chain, requiring manual intervention (or the relayer covering the shortfall).

None of the existing guards catch this: `validateWithdrawal` only asserts `feeEstimation.amount > 0n` and relayer-fee positivity for non-UTXO chains, and never independently re-checks the storage balance; `getUnderlyingFee` simply reads the (already wrong) value stored in `underlyingFees`; there is no `supports()`/`matchesRequest` check that re-validates storage sufficiency at execution time.

### Impact Explanation
The user signs an intent whose embedded `storageDepositAmount` (part of the `ft_withdraw` args on the Omni Bridge contract) does not reflect the real on-chain deficit, so the fee actually debited from the user's balance (`feeEstimation.amount`) is short by the true storage-deposit cost. This causes the withdrawal to become stuck until manual intervention (matching the "High" impact category: withdrawal stuck / fee shortfall absorbed by relayer). This is repeatable for any token whose storage balance oscillates around `minStorageBalance` within the 1-hour cache window, and is not limited to a single attacker action — it's a systemic staleness bug affecting any caller using the same long-lived `OmniBridge` instance during the affected window.

### Likelihood Explanation
Preconditions: the SDK instance must have previously cached a "sufficient" storage-balance observation for the specific token (a common, unprivileged, no-cost action — just calling `estimateWithdrawalFee` once), and the shared `OMNI_BRIDGE_CONTRACT` storage balance for that token must later drop below `minStorageBalance` before the 1-hour TTL expires. This latter condition depends on external withdrawal volume for that token depleting shared storage funds, which is plausible for popular tokens with many concurrent withdrawals, but isn't fully attacker-controlled (the attacker cannot force other parties' withdrawals to run in a tight window). Attacker cost is minimal (a couple of API calls); no special privileges required.

### Recommendation
- Do not cache the "sufficient" case for as long as the deficit case is left uncached; either shorten the TTL drastically for this data, or re-validate the on-chain storage balance immediately before intent construction (`createWithdrawalIntents` / `deriveOmniWithdrawIntentParams`) rather than relying on a stale `estimateWithdrawalFee` result.
- Consider caching only `minStorageBalance` (which is effectively static) and always freshly fetching `currentStorageBalance` (or applying a much shorter TTL, e.g., a few seconds) since it is a fast-changing shared resource.
- Add a final on-chain sanity check right before signing/submitting the withdrawal intent that recomputes the storage deficit and refuses to proceed (or triggers a re-quote) if the cached fee no longer matches reality.

// vitest test plan (mock only the NEAR RPC calls: getNearNep141MinStorageBalance / getNearNep141StorageBalance)
it("stale storageDepositCache entry causes storageDepositFee to be under-reported", async () => {
  const bridge = new OmniBridge({ envConfig, nearProvider, /* ... */ });

  // First call: min=100, current=150 (sufficient) -> cache stores [100n, 150n]
  mockGetNearNep141MinStorageBalance.mockResolvedValueOnce(100n);
  mockGetNearNep141StorageBalance.mockResolvedValueOnce(150n);

  const fee1 = await bridge.estimateWithdrawalFee({ withdrawalParams: params });
  expect(fee1.underlyingFees[RouteEnum.OmniBridge].storageDepositFee).toBe(0n);

  // Second call within TTL: real balance has dropped to 50 (deficit of 50),
  // but RPC mocks below should NOT even be hit because of the cache hit.
  mockGetNearNep141MinStorageBalance.mockResolvedValueOnce(100n);
  mockGetNearNep141StorageBalance.mockResolvedValueOnce(50n); // simulates real drained balance

  const fee2 = await bridge.estimateWithdrawalFee({ withdrawalParams: params });

  // Assert the broken equality: cached value (0n) diverges from the true deficit (100n - 50n = 50n)
  expect(fee2.underlyingFees[RouteEnum.OmniBridge].storageDepositFee).toBe(0n); // stale, WRONG
  expect(100n - 50n).toBe(50n); // true on-chain deficit that was silently dropped

  // Confirm mocks for the second RPC call were never invoked (cache hit, not RPC re-check)
  expect(mockGetNearNep141StorageBalance).toHaveBeenCalledTimes(1);
});

	private async getCachedStorageDepositValue(
		contractId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const cached = this.storageDepositCache.get(contractId);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: OMNI_BRIDGE_CONTRACT,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(contractId, result);
		}

		return result;
	}
