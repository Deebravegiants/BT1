## Custody Analog Found: Permanent lock of 10% APT/FA reserves after `graduate()` in the Bonding Curve Launchpad

### Title
Permanently stranded APT and FA reserves after liquidity-pair graduation — ([File: aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move])

### Summary
The external report's root custody invariant is: *when value is moved out during a settlement/exit flow, the full accounted amount must actually leave the origin custody point — otherwise value is stranded or misdirected.* In `liquidity_pairs::graduate()`, only 90% of the liquidity pair's tracked APT and FA reserves are migrated to the external DEX pool; the remaining 10% is left inside the `LiquidityPair` object's native-APT balance and its `fa_store`, with `is_enabled` permanently set to `false` and no function anywhere in the module (or in `bonding_curve_launchpad`) able to withdraw from a disabled pair again. That 10% becomes permanently irrecoverable.

### Finding Description
`graduate()` is invoked automatically from `swap_apt_to_fa` once `apt_updated_reserves` crosses `APT_LIQUIDITY_THRESHOLD`: [1](#0-0) 

Inside `graduate`, the pair is irreversibly disabled first: [2](#0-1) 

Then only 90% of both `apt_updated_reserves` and `fa_updated_reserves` is passed as the *desired* amount for the new external-DEX pool: [3](#0-2) 

`add_liquidity_coin_entry_transfer_ref` withdraws exactly `optimal_amount_1`/`optimal_amount_2` (derived from the 90% figures) — never the full reserve — from the liquidity-pair signer's APT balance and from `fa_store` via `transfer_ref`: [4](#0-3) 

After this, `graduate()` only forwards the newly-minted LP tokens to `@0xdead`; it never touches the remaining 10% APT sitting as a native coin balance on the `LiquidityPair`'s object address, nor the remaining 10% FA still sitting in `liquidity_pair.fa_store`: [5](#0-4) 

Once `is_enabled = false`, every entry point that could move funds out of the pair (`swap_fa_to_apt`, `swap_apt_to_fa`) is gated by `assert!(liquidity_pair.is_enabled, ELIQUIDITY_PAIR_DISABLED)`: [6](#0-5) [7](#0-6) 

There is no admin/sweep/rescue function in `liquidity_pairs.move` or in `bonding_curve_launchpad.move` that can extend or reclaim funds from a `LiquidityPair` object once graduated — `graduate` is the last write to `is_enabled`/`is_frozen`, and no other function reads or writes the `LiquidityPair.fa_store` or its native-APT balance after that point. The 10% is therefore held by an object whose custody state (`is_enabled = false`) makes it permanently unreachable through any code path in scope.

### Impact Explanation
Every FA launched through the bonding curve that reaches the graduation threshold permanently strands 10% of both its APT and FA reserves inside an on-chain object with no recovery path — a direct, protocol-wide, non-recoverable loss of object-held value (APT and the launched FA), matching the "Permanent lock or non-recoverable loss of object-held value" custody-impact category. Because graduation is a normal, expected, high-value event (it happens for every FA that succeeds), the aggregate loss scales with launchpad usage and is not an edge case.

### Likelihood Explanation
This triggers automatically and deterministically on every successful graduation (`apt_updated_reserves > APT_LIQUIDITY_THRESHOLD`), which is the intended success path of the whole bonding-curve mechanism — no attacker action or privileged capability is required, only normal trading activity that any user can trigger.

### Recommendation
In `graduate()`, migrate the full computed reserves (100%, not 90%) to the external pool, or explicitly transfer the remainder (real `fungible_asset::balance(fa_store)` and `coin::balance<AptosCoin>(liquidity_pair_address)` after `add_liquidity_coin_entry_transfer_ref` returns) to a designated recoverable destination (e.g., the DEX pool, the creator, or a documented treasury) before disabling the pair. Also update `liquidity_pair.fa_reserves`/`apt_reserves` to reflect actual post-graduation balances instead of leaving them at the pre-migration `fa_updated_reserves`/`apt_updated_reserves` values, so on-chain state cannot mislead future integrations about custody of the pair's residual assets.

### Proof of Concept
1. Launch an FA via `bonding_curve_launchpad::create_fa_pair`.
2. Perform `swap` calls with `swap_to_apt = false` until `apt_updated_reserves` exceeds `APT_LIQUIDITY_THRESHOLD` (600_000_000_000), triggering `swap_apt_to_fa` → `graduate`.
3. Observe that `graduate` calls `add_liquidity_coin_entry_transfer_ref` with `amount_1_desired = apt_updated_reserves - apt_updated_reserves/10` and `amount_2_desired = fa_updated_reserves - fa_updated_reserves/10` — i.e., only 90% of each reserve is ever requested for migration (lines 351–352).
4. After `graduate` returns, `liquidity_pair.is_enabled = false` permanently (line 340); confirm via `get_is_frozen`/direct resource inspection that `fa_store` still holds ~10% of the FA balance and the `LiquidityPair` object address still holds ~10% of APT as a native coin balance.
5. Attempt to call `swap_fa_to_apt`/`swap_apt_to_fa` or any other exposed function to retrieve these residual balances — every path aborts with `ELIQUIDITY_PAIR_DISABLED` or does not reference `fa_store`/the object's APT balance at all, confirming the funds are permanently unreachable.

    fun add_liquidity_coin_entry_transfer_ref<CoinType>(
        transfer_ref: &TransferRef,
        lp: &signer,
        fa_store: Object<FungibleStore>,
        token_2: Object<Metadata>,
        is_stable: bool,
        amount_1_desired: u64,
        amount_2_desired: u64,
        amount_1_min: u64,
        amount_2_min: u64,
    ) {
        // Wrap APT into a FA. Then, determine the optimal amounts for providing liquidity to the given FA - APT pair.
        let token_1 = coin_wrapper::get_wrapper<CoinType>();
        let (optimal_amount_1, optimal_amount_2, _) = router::optimal_liquidity_amounts(
            token_1,
            token_2,
            is_stable,
            amount_1_desired,
            amount_2_desired,
            amount_1_min,
            amount_2_min,
        );
        // Retrieve the APT and FA from the liquidity provider.
        // `transfer_ref` is used to avoid circular dependency during graduation. A normal transfer would require
        // visiting `bonding_curve_launchpad` to execute the custom withdraw logic. `transfer_ref` bypasses the need to
        // return to `bonding_curve_launchpad` by not executing the custom withdraw logic.
        let optimal_1 = coin::withdraw<CoinType>(lp, optimal_amount_1);
        let optimal_2 = fungible_asset::withdraw_with_ref(
            transfer_ref,
            fa_store,
            optimal_amount_2
        );
        // Place the APT and FA into the liquidity pair.
        router::add_liquidity_coin<CoinType>(lp, optimal_1, optimal_2, is_stable);
    }
