### Title
Webhook Tenant Identity (`shop`) Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop` (tenant) and `topic` values used by `Registry.process` to route and act on the webhook are read directly from unauthenticated HTTP headers. This breaks the intended binding `hmac == HMAC(secret, raw_body + shop + topic)`, allowing the header-derived `shop` to diverge from the `shop` that actually produced the signed body.

### Finding Description
`to_signable_string` for `Webhooks::Request` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop` and `topic` — the fields used to dispatch/identify the tenant for webhook processing — are parsed straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only checks that the HMAC over `to_signable_string` (the raw body) matches, using the app's single shared `api_secret_key`: [4](#0-3) 

This is the same class of bug described in the external report: an identity/claim value (`signId`/here, `shop`) that is *used* by the business logic is never *consumed by or cryptographically bound to* the verification step (`uuid`/here, the HMAC signature). The equality that should hold — `hmac == HMAC(secret, raw_body ‖ shop ‖ topic)` — actually only enforces `hmac == HMAC(secret, raw_body)`, so the `shop` header is free for an attacker to change after obtaining a validly-signed payload.

Because a single Shopify app installed across multiple merchant shops uses the **same `api_secret_key`** for all its shops, any merchant who has genuinely installed the app can capture one legitimately-HMAC-signed webhook delivery (raw body + valid HMAC) sent to their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a *different* shop that also uses the app. `HmacValidator.validate` will still pass, because it only checks the raw body bytes against the shared secret — it never verifies that the claimed `shop` matches the shop that actually signed the payload.

### Impact Explanation
This crosses a tenant boundary: `Registry.process` hands the (spoofed) `shop` and body to the registered handler as if it were an authentic event for that shop, as shown in the registry tests, where handler code trusts `data.shop`: [5](#0-4) 

Any application logic that keys off `Webhooks::Request#shop` (e.g., looking up/loading a session or performing shop-scoped actions such as billing, data sync, or deletion in response to a webhook) can be tricked into acting on behalf of an arbitrary victim shop that shares the same app installation base, using another tenant's identity while carrying only the attacker's own credentials. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker (i) install the target app on a shop they control (an ordinary, unprivileged action for any merchant), (ii) capture one webhook delivery Shopify sends them (which is delivered over HTTP to their own configured endpoint, fully attacker-observable), and (iii) replay the raw body with the same HMAC to the app's public webhook endpoint with a modified `shop`/`topic` header. No access token, `client_secret`, or privileged access is needed — the `api_secret_key` never needs to be known by the attacker, only its output for one message they legitimately received.

### Recommendation
Bind the tenant-identifying fields into the signed material, or otherwise cryptographically verify them, rather than trusting header-derived `shop`/`topic` independently of the HMAC. Concretely, include `shop` (and ideally `topic`, `webhook_id`) in `to_signable_string`, or validate that the `shop` header corresponds to a shop session/state that is independently known to the app (e.g. cross-checked against an existing installed-shop record) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, a shop they control, and registers a webhook subscription (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, a raw JSON body, and `x-shopify-hmac-sha256` computed as `HMAC-SHA256(api_secret_key, raw_body)` — this is the shared app secret, identical for all shops using the app.
3. Attacker intercepts/replays this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (a real shop that also has the app installed).
4. `Webhooks::Request#hmac` and `HmacValidator.validate` compute/check the signature only over `raw_body`, per [1](#0-0)  and [4](#0-3) , so validation succeeds despite the shop header being forged.
5. `Registry.process` looks up the handler by `topic` and invokes it with `data.shop == "victim-shop.myshopify.com"`, causing the host application to perform shop-scoped actions attributed to the victim tenant using data the attacker fully controls.
