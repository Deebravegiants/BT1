### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers to build the `WebhookMetadata` dispatched to the app's handler. The identity binding "the shop this webhook is attributed to" is never covered by the cryptographic signature, so any bytes that pass HMAC validation for one shop's webhook can be replayed with a different `shop-domain` header and will be accepted and processed as if it originated from a different, arbitrary tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC exclusively over that signable string (the body) and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` gates entirely on this body-only HMAC check, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all pulled straight from headers with zero cryptographic binding to the signed body — and forwards them to the app's `handler.handle`: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all simple header reads with no HMAC coverage: [4](#0-3) 

This is the exact identity-binding gap described in the analog bug class: a field ("shop") is *acted on* (used to attribute and dispatch the webhook to a specific merchant's data) but is *not covered by the HMAC* that is used to authenticate the request. The equality that should hold — "the shop bound by the signature == the shop the app acts on" — does not hold, because the signature binds nothing but the raw JSON body bytes.

Because a public Shopify app can be freely installed on any store (including a free/trial store an ordinary internet user can create without needing the app's `api_secret_key`, an access token, or any privileged account), such a user can:
1. Install the target app on their own store.
2. Trigger a legitimate webhook event (e.g. `orders/create`) on their own store, causing Shopify to send a genuinely-signed webhook (valid `hmac-sha256` computed with the app's real secret, which the attacker never needs to know) to the app's callback endpoint — the attacker simply captures this real, valid `(body, hmac)` pair from their own store's traffic (e.g., via a debugging proxy, or by controlling the receiving endpoint if they self-host a copy of the integration, or by using ngrok on their own dev/trial store).
3. Replay the exact same `raw_body` and `hmac-sha256` header value to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header (and, if desired, `x-shopify-topic`/`x-shopify-webhook-id`) with a **victim** shop's domain.
4. `HmacValidator.validate` passes (it never inspected the shop header), and `Registry.process` dispatches the payload to the handler with `shop: <victim-shop>`.

If the host application's webhook handler uses `data.shop` to select which tenant's local record to create/update/delete (the documented, expected usage pattern — see `docs/usage/webhooks.md` example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), the attacker's own webhook data is written into, or triggers webhook-driven side effects against, the victim shop's tenant, or the attacker can attribute their own store's webhook events to any shop domain string of their choosing.

### Impact Explanation
This breaks the shop/tenant identity binding that the HMAC signature is meant to establish, enabling **cross-tenant access**: an attacker can cause an app to process webhook data under an arbitrary shop's identity without ever needing that shop's credentials, the app's `client_secret`, or any access token. This matches the Critical "cross-tenant access" impact category — it requires no privileged account, no leaked secret, and no interception, only ordinary use of the app on an attacker-owned store plus an unauthenticated header substitution against the app's public webhook endpoint.

### Likelihood Explanation
High. Installing a public app on a throwaway/trial store and observing its own valid webhook traffic requires no special access. Replaying a POST with a modified header is trivial for any developer with basic HTTP tooling. The gem's documented usage pattern actively encourages host apps to key business logic off `data.shop`, making the unauthenticated header the de facto tenant identifier throughout the intended integration pattern.

### Recommendation
Bind the tenant/topic identity to the authenticated bytes instead of trusting unauthenticated headers:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (this would require Shopify-side changes and isn't something the gem can retrofit unilaterally, since Shopify signs only the body), or
- At minimum, require host applications to cross-check `request.shop` against a shop domain independently known/registered for the webhook subscription (e.g., verify `shop` corresponds to a shop that actually has an active session/subscription for that specific `webhook_id`/topic) before trusting `WebhookMetadata#shop`, and document this requirement prominently in `docs/usage/webhooks.md` and in `WebhookHandler`'s documentation, since currently the docs present `data.shop` as if it were an authenticated field.
- Consider validating that the `shop` header matches a shop domain format via `Utils::ShopValidator` as defense-in-depth, and reject/flag processing when webhook volume/timing suggests replay across differing shop headers for identical bodies.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Shopify sends a real, validly-signed webhook to the app for attacker's own store:
real_body = '{"id":1,"note":"legit order on attacker store"}'
real_hmac = "shopify-computed-hmac-sha256-base64"  # captured from genuine Shopify traffic

# Attacker replays the exact same signed body/hmac pair, but swaps the shop header:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => real_hmac,          # unchanged, still valid for the body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"   => "attacker-controlled-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: headers)

# Passes HMAC validation because only `real_body` is checked, not the shop header:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...))
```
`ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` for this forged request because `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) only ever includes `@raw_body`, never the `shop-domain` header, so the substitution is undetectable by the HMAC check performed in `lib/shopify_api/utils/hmac_validator.rb:26-31`.
