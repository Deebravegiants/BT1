### Title
Webhook shop-domain (and topic/webhook-id/api-version) headers are not covered by the HMAC signature, allowing cross-tenant spoofing via replayed webhook bodies - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are then forwarded, unauthenticated, into the app's `WebhookHandler` come exclusively from HTTP headers and are never included in the signed payload [2](#0-1) .

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for a webhook `Request` that method returns only `@raw_body` [3](#0-2) . The identity binding that should hold is:
`shop_that_the_signature_authenticates == shop_the_handler_acts_on`

But in this gem:
- The HMAC only binds `raw_body` to the app's `client_secret` — it never covers `shop`, `topic`, `webhook_id`, or `api_version` [4](#0-3) .
- After the HMAC check passes, `Registry.process` reads `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` directly from the (unsigned) `x-shopify-*`/`shopify-*` headers and passes them straight into the handler's `WebhookMetadata` [1](#0-0) [5](#0-4) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are pulled from `shopify_header(...)`, which just indexes into the caller-supplied headers hash with no cryptographic tie to the signed body [6](#0-5) [7](#0-6) .

Because the same `client_secret` signs webhook bodies for *every* shop that has the app installed, any actor who can install the app on their own store (an "unprivileged internet user" with respect to any other tenant of the app) can obtain a genuinely-signed `(raw_body, hmac)` pair from Shopify for their own shop, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) with an arbitrary victim shop domain or topic value. `Registry.process` will accept it: the HMAC check only verifies the body was produced by someone possessing the secret, and it says nothing about which shop, topic, or webhook the body belongs to.

### Impact Explanation
This breaks the tenant identity binding the app is relying on to route webhook data safely: `shop` (the value verified as being authentic) versus `shop` (the value the handler acts on) are not the same field. An app that keys any persistence, authorization, or side-effecting logic in its `WebhookHandler#handle` off `data.shop` (as the library's own documentation instructs apps to do — e.g. `docs/usage/webhooks.md` and the `BREAKING_CHANGES_FOR_V15.md` example handler) can be made to write, update, or act on data under a shop domain the attacker chooses, using a body the attacker fully controls the content/topic association for. This is a cross-tenant confusion primitive: data or events intended to be scoped to the attacker's own shop can be attributed to an arbitrary victim shop string as far as the app's own database/business logic is concerned.

### Likelihood Explanation
Moderate-to-high. The prerequisite (installing the target app on one's own trial/development store to obtain legitimately signed webhook traffic) is achievable by any unprivileged internet user for public apps, and Shopify's `client_secret`-based HMAC scheme is app-wide, not per-shop. No access token, refresh token, or `client_secret` leakage is required — this exploits the gem's own verification logic, which trusts unsigned headers after a body-only HMAC check.

### Recommendation
- Bind the shop domain (and ideally topic/webhook id) into the value that is HMAC-verified, or at minimum require the app to independently verify that `request.shop` corresponds to a shop with an active, stored session/installation before trusting it, and document this requirement prominently.
- Update `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` so that `Registry.process` cannot report a `shop` value that wasn't part of what was cryptographically verified, or explicitly reject the header-derived `shop`/`topic` unless corroborated by app-side installation state.

### Proof of Concept
1. Attacker installs the target app on their own development store (`attacker-shop.myshopify.com`), a legitimate unprivileged action available to any internet user for a public app.
2. Shopify sends a genuine webhook, e.g. `orders/create`, to the app's registered endpoint with:
   - Body: `{"id": 1, ...}` (raw JSON)
   - Headers: `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`
3. Attacker captures this exact `(raw_body, hmac_header)` pair.
4. Attacker crafts a new HTTP POST to the same app webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` [3](#0-2)  — validation succeeds because the body is unchanged.
6. The app's `WebhookHandler#handle` is invoked with `data.shop == "victim-shop.myshopify.com"` [8](#0-7) , even though that data never actually originated from, nor was authenticated for, `victim-shop.myshopify.com`.

Note: I could not find any code path within `lib/shopify_api/webhooks/**` that cross-checks the header-derived `shop` against a session store or an allow-list before invoking the handler; this appears to be entirely delegated to the host application, which the docs do not clearly warn about.
