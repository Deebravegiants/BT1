### Title
Webhook shop-domain header is not bound by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by the host application to route and attribute the webhook come from unauthenticated HTTP headers. Because a single app-wide `api_secret_key` is used to sign webhooks for *every* shop that installs the app, any merchant who legitimately receives one authentic, correctly-signed webhook for their own shop can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will accept it as authentic, and `Webhooks::Registry.process` will hand the attacker-controlled body to the app's handler tagged with the victim shop's identity.

### Finding Description
The binding that should hold is:
`shop cryptographically bound to the HMAC-authenticated payload == shop the app attributes the payload to`

In this gem that equality is broken:

- `Request#to_signable_string` returns only the raw body: [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers, which are entirely attacker-controlled on any inbound POST to the app's public webhook endpoint: [2](#0-1) 
- `Utils::HmacValidator.validate_signature` verifies only `to_signable_string` (i.e., the body) against the secret — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 
- `Registry.process` trusts the header-derived `request.shop` once the body-only HMAC check passes, and forwards it to the app's handler as the tenant identifier: [4](#0-3) 

Because `api_secret_key` (the app's client secret) is shared across every shop that installs the app — not per-shop — any merchant who installs the app can obtain a genuinely-signed `(body, hmac)` pair for their own store's webhook traffic. Nothing in the signable content ties that pair to their shop domain. Re-POSTing the identical body and `x-shopify-hmac-sha256` value with a different `x-shopify-shop-domain` header still passes `HmacValidator.validate`, yet the app processes it as data belonging to whatever shop the attacker put in the header.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged merchant/attacker with no access to a victim's credentials can make the host application process attacker-supplied webhook data as if it originated from the victim's shop. Any host application logic that keys off `WebhookMetadata#shop` (e.g., looking up the victim's session/access token, updating the victim's records, or triggering shop-specific side effects) can be tricked into acting on the wrong tenant using attacker-controlled body content and topic. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to be a legitimate (even free-tier) installer of the same app in order to first receive one authentic signed webhook. From that point, replay is trivial: it's a single unauthenticated HTTP POST with attacker-controlled headers to the app's public webhook endpoint, which is by design internet-reachable and not behind another authentication layer in this gem.

### Recommendation
Bind the shop (and topic/webhook id) into the material that is authenticated, or otherwise verify that the header-supplied shop is one the app has an active, matching installation/session for before dispatching, and reject/replace any workflow that treats the unauthenticated `shop-domain` header as trusted tenant context once only the body is HMAC-verified.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and has the app installed.
# They receive a real webhook from Shopify:
#   headers: {"x-shopify-hmac-sha256" => real_hmac, "x-shopify-shop-domain" => "shop-a.myshopify.com", "x-shopify-topic" => "orders/create"}
#   body: '{"id":1,"note":"attacker-controlled content"}'
#
# HmacValidator.validate only checks real_hmac against the raw body using the
# app-wide api_secret_key -- it never checks shop-domain.

forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,          # unchanged, still valid for this body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/hmac untouched)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app now processes attacker-chosen data under the victim shop's identity.
``` [4](#0-3)
