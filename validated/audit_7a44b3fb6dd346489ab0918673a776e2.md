### Title
`AuroraEngineBridge.describeWithdrawal` unconditionally reports `completed` with no chain read, breaking status-truth for VirtualChain withdrawals - (File: `packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts`)

### Summary
`AuroraEngineBridge.describeWithdrawal` ignores all of its arguments and always resolves `{ status: "completed", txHash: null }`, without ever querying NEAR RPC for the transaction/receipt outcome of the `ft_withdraw` intent that was submitted to the Aurora Engine proxy. This is inconsistent with every other bridge in the same file tree (`OmniBridge`, `PoaBridge`, `HotBridge`), all of which actually inspect indexer/contract state before declaring `completed`.

### Finding Description
The claimed equality is: `describeWithdrawal(wid).status == on-chain settlement outcome of the ft_withdraw/ft_transfer_call receipt chain triggered on Aurora Engine`.

The implementation is: [1](#0-0) 

It takes no parameters at all (the method signature doesn't even declare `args`, despite the `Bridge` interface requiring `WithdrawalIdentifier & { logger?: ILogger }`), performs zero NEAR RPC calls, and always returns `completed`/`txHash: null`.

The withdrawal is executed by submitting an `ft_withdraw` intent whose `receiver_id` is the `auroraEngineContractId` (or `proxyTokenContractId`) and whose `msg` encodes the destination EVM address, built in `createWithdrawIntentPrimitive`: [2](#0-1) 

Under the NEP-141 `ft_transfer_call` standard, the outer NEAR transaction can finalize as `SUCCESS` while the inner cross-contract call to the Aurora Engine proxy (`ft_on_transfer`) executes and potentially fails asynchronously in a subsequent receipt (e.g. insufficient `min_gas`, missing NEP-141 storage deposit on the proxy contract, or a revert on the destination EVM call), triggering a `ft_resolve_transfer` refund. `describeWithdrawal` never looks at any of these receipts, contract logs, or Aurora Engine chain state — it cannot distinguish a refunded/failed deposit from a genuinely completed one.

Contrast with the analogous methods that do perform real verification: [3](#0-2) [4](#0-3) 

`watchWithdrawal` treats any `completed` status as final and immediately returns the (possibly null) hash to the caller without further checks: [5](#0-4) 

None of the documented guards (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()` ordering, `FeeExceedsAmountError`, `getUnderlyingFee`, `matchesRequest`) apply here — they operate on intent construction, not on post-submission settlement verification, so they cannot compensate for the missing status check.

Note: `DirectBridge.describeWithdrawal` has an identical unconditional-completion pattern: [6](#0-5) 
This suggests the same class of gap exists for the `NearWithdrawal` route as well, though that method is outside the scope of this specific question.

### Impact Explanation
An integrator that calls `watchWithdrawal` for a `VirtualChain` route treats a `completed` status as proof that funds landed on the destination Aurora-Engine-powered chain, and typically credits or reconciles an off-chain balance on that basis. Because `describeWithdrawal` reports `completed` unconditionally — even when the underlying deposit failed and tokens were refunded on NEAR — the integrator can credit the user while the deposited value never left NEAR (or was returned). This matches the "status or hash misreport making an integrator credit or refund twice" category, which the rules classify as **High**, not Critical as the question's premise assumes.

### Likelihood Explanation
No special privilege is required: any ordinary user who withdraws through the `VirtualChain` route and encounters a proxy-side failure (insufficient `min_gas`, missing NEP-141 storage deposit on `auroraEngineContractId`/`proxyTokenContractId`, or a destination-side revert) triggers the divergence automatically. Every single `describeWithdrawal` call for this route returns `completed` regardless of outcome, so the bug is deterministic and repeatable on every VirtualChain withdrawal, not just failure cases — it simply never distinguishes success from failure since it never checks.

### Recommendation
Implement real settlement verification in `AuroraEngineBridge.describeWithdrawal`: query the NEAR transaction's receipt outcomes (via `this.nearProvider`) for the `ft_transfer_call`/`ft_on_transfer`/`ft_resolve_transfer` receipt chain (or an Aurora Engine-specific indexer/RPC call) to confirm the deposit succeeded on the destination side before returning `completed`; return `pending` while receipts are outstanding and `failed` if a refund receipt is observed, mirroring the patterns already used in `OmniBridge.describeWithdrawal` and `PoaBridge.describeWithdrawal`.

```ts
import { describe, it, expect } from "vitest";
import { AuroraEngineBridge } from "./aurora-engine-bridge";

describe("AuroraEngineBridge.describeWithdrawal status truth", () => {
  it("reports completed even though no chain state was ever read (violates STATUS_TRUTH)", async () => {
    const bridge = new AuroraEngineBridge({
      envConfig: {} as any,
      nearProvider: {} as any, // never called - proves zero RPC usage
    });

    const result = await bridge.describeWithdrawal({
      landingChain: "near" as any,
      index: 0,
      withdrawalParams: {} as any,
      tx: { hash: "any-tx-hash-including-one-that-reverted", accountId: "user.near" },
    } as any);

    // LHS: reported status/txHash
    // RHS: real on-chain settlement outcome (unknown/failed in this scenario)
    expect(result).toEqual({ status: "completed", txHash: null });
    // No mock of nearProvider was ever invoked -> equality is asserted by construction,
    // independent of the actual destination-chain outcome.
  });
});
```

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
```

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```
