Confirmed: the webhook `shop` (and `topic`, `webhook_id`, `api_version`) header fields are passed straight to the handler without being covered by the HMAC signature, which only signs the raw body.

### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` Are Not HMAC-Bound, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding to the HMAC signature that `ShopifyAPI::Utils::HmacValidator` checks.

### Finding Description
`HmacValidator.validate` verifies a `VerifiableQuery` by comparing `verifiable_query.hmac` against an HMAC computed over `verifiable_query.to_signable_string`, using the app's `Context.api_secret_key`. [1](#0-0)  For webhooks, `Request#to_signable_string` returns only `@raw_body`; the tenant-identifying field `shop`, along with `topic`, `webhook_id`, and `api_version`, are parsed from the `shopify-shop-domain`/`x-shopify-shop-domain` (and equivalent) headers and are never included in the signed string. [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — i.e. it verifies the *body* bytes are authentic — and then dispatches to the handler using `request.shop`, `request.topic`, etc. taken from the unauthenticated headers. [3](#0-2)  This is exactly the class of bug described in the reference report: a field that is acted upon (`shop`, used to attribute the webhook to a tenant) is not covered by the integrity check (HMAC over body only) that gates whether the request is trusted.

The binding that should hold is: `HMAC(body, secret) valid ⇒ shop header == shop the body was actually generated for`. In reality the gem only proves `HMAC(body, secret) valid ⇒ body was generated by Shopify (for *some* shop)`; the `shop` label is taken on faith from an attacker-influenceable header.

### Impact Explanation
Any party capable of relaying or replaying an HTTP request to the app's webhook endpoint (e.g. a proxy, load balancer quirk, header-rewriting intermediary, or a party who can obtain one authentic `(body, hmac)` pair for their own shop and re-POST it with a modified `x-shopify-shop-domain` header) can cause the host application's handler to process the webhook as if it came from a different, victim shop. Since `WebhookMetadata` built in `Registry.process` (line 198) carries this unauthenticated `shop` value directly into the handler, any tenant-scoping logic in the handler that trusts `data.shop` can be confused — enabling cross-tenant data attribution/access, which matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitability depends on an attacker being able to submit an HTTP request to the app's webhook receiver with attacker-controlled headers but a body+HMAC pair that validates (e.g., replaying their own shop's legitimately-received webhook while swapping the shop header). This requires network reachability to the endpoint and possession of at least one valid `(body, hmac)` pair, which is achievable by any merchant who has the app installed on their own store (an otherwise unprivileged actor relative to other tenants).

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the request), rather than trusting them as unauthenticated headers once the body's HMAC is valid. At minimum, document that consumers of `WebhookMetadata#shop` must independently verify the shop is one their app has installed/authorized before trusting it for tenant-scoped operations.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and valid header `x-shopify-hmac-sha256: HMAC(B, secret)`.
2. Attacker (or a MITM/relay) re-sends the exact same body `B` and HMAC header to the app's webhook endpoint, but with `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `"shop-b.myshopify.com"` from the header. [4](#0-3) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` and succeeds, since the body was unmodified. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata` carrying `shop: "shop-b.myshopify.com"`, even though the signed body was never produced for `shop-b`. [6](#0-5)
