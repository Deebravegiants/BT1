### Title
Opaque caller-supplied route bytes reach arbitrary `invoke_contract` hops, letting a malicious route execute attacker code beneath the caller's signed auth and drain wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The command-injection class maps to the swap-strategy path: user-supplied, unvalidated bytes (`swap_xdr` / `StrategySwap`) are forwarded verbatim by the controller to the router and then dispatched into `invoke_contract` calls against pool addresses the payload itself names. Nothing in the controller or router validates, decodes, or allowlists the callee or the code executed, so arbitrary attacker-deployed contracts run inside the victim's authorization tree. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves a rogue hop pool can call `token.transfer(victim, attacker, amount)` on any token the victim holds, and the host records/accepts it as a child of the caller's `swap_collateral` authorization. The same hazard is documented in `docs/explanation/threat-model.md:154-165`.

### Finding Description
`swap_tokens` takes `swap: &StrategySwap` — an opaque byte blob — and only asserts it is non-empty before passing it unchanged to `router.execute_strategy(&controller, &amount_in, swap)` inside `with_flash_guard` (contracts/controller/src/strategies/swap.rs:22, 36-38). The controller's only checks are balance deltas on the controller's own input/output (`RouterOverspend`, `NoSwapOutput`); the route's callee addresses, pool contracts, and sub-calls are never inspected. The router (per threat-model.md:154-156) "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization."

Reachable entrypoints for an unprivileged address: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and the direct `execute_strategy` path. The injected "command" is the decoded route: an attacker-registered contract address standing in for a hop pool. In the test, `RogueHopPool::swap` executes `token::Client::transfer(&victim, &attacker, &amount)` on an unrelated token the protocol never listed; in recording mode (simulation) this transfer is attached as a child of the victim's `swap_collateral` auth entry, and in enforcing mode it executes if the victim signs that tree (test lines 62-71, 195-269).

### Impact Explanation
Theft of user funds beyond the routed amount. Neither the payload `min_out` nor the controller's final risk gate bounds the loss: the rogue contract can transfer the victim's entire balance of any Stellar-asset token to the attacker (test asserts `s.wallet(&s.alice) == 0`, `s.wallet(&s.attacker) == WALLET_BALANCE` at lines 224-225 and 267-268). The victim's account can still end healthy — the swap pays fair output — so no on-chain gate intervenes. This is the injection property: attacker-controlled data (route bytes) becomes executable control flow carrying the victim's privileges.

### Likelihood Explanation
Requires the victim to sign an authorization tree containing the malicious child transfer. The route is opaque `Bytes`, so a compromised or malicious quote service/front-end (or phishing dApp) can construct a poisoned route; simulation in recording mode silently produces the expanded tree, and wallets/clients that do not decode and diff child entries will present a benign-looking signature. Threat-model.md:160-165 acknowledges the loss lands on "the caller's wallet" and places the entire mitigation burden on client-side auth-tree decoding — nothing in-contract prevents it. Rated Medium: exploitation needs victim signing, but the enabling condition (no callee validation) is fully in protocol code.

### Recommendation
Enforce a venue allowlist or decode-and-validate the route in the controller/router: reject hop pools/tokens that are not registered/known venues, or constrain hop callees to an operator-curated set. At minimum, reject any route whose resolved auth footprint requires sub-invocations beyond the single sanctioned input `transfer`, and document that clients must refuse signed trees with unexpected children.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` is a working PoC: `scene.route_through_pool_stealing(WALLET_BALANCE)` registers `RogueHopPool` (constructor-planted plan: victim, wallet token, attacker, amount), builds `RoutedSwap` XDR naming it as `hop_pool`, and calls `ctrl.swap_collateral(alice, account, USDC_key, 50e9, ETH_key, route)`. `RogueHopPool::swap` then executes `token.transfer(alice → attacker, 77_770e6)`; the test shows the transfer is recorded under Alice's `swap_collateral` entry and succeeds when she signs that tree, emptying her wallet token while her position still shows fair ETH output.
