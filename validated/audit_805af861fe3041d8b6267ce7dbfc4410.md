### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `to_signable_string` (the data actually authenticated by the HMAC) is only the raw request body. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body and then unconditionally trusts the header-derived `shop` value to build `WebhookMetadata`, which the docs explicitly instruct host apps to use as the tenant key (`shop_domain: data.shop`) for enqueuing/processing work.

### Finding Description
The HMAC binding equality that should hold is: `hmac == HMAC(secret, bytes_the_app_acts_on)`. Instead, the gem verifies `hmac == HMAC(secret, raw_body)` [1](#0-0)  while the tenant-identifying `shop` field used downstream comes from an unauthenticated header [2](#0-1) .

`Registry.process` validates only this body-bound HMAC and then immediately hands the header-derived `shop`, `topic`, and `webhook_id` to the handler without any cross-check that they correspond to the shop that actually owns the signed body: [3](#0-2) 

Because the api_secret_key used to sign webhooks is shared across all shops that install the app (it is the app's `client_secret`, not a per-shop secret), any entity that can install the app on their own store — an "unprivileged internet user" with respect to other tenants — receives genuine webhooks with valid `(raw_body, hmac)` pairs. That pair remains valid regardless of which `X-Shopify-Shop-Domain` / `X-Shopify-Topic` / `X-Shopify-Webhook-Id` header values accompany it, because those headers are never included in `to_signable_string`.

### Impact Explanation
This breaks the identity binding "shop authenticated == shop attributed to the processed data." An attacker who owns a shop that has installed the app can capture a legitimately signed webhook body+HMAC from their own tenant, then replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` will report success (it only checks the body) [4](#0-3) , and the handler will receive `WebhookMetadata` claiming the victim shop, per the documented handler contract that trusts `data.shop` as the tenant key [5](#0-4) [6](#0-5) . Any host app that follows this documented pattern (writing/enqueueing data keyed by `data.shop`) can be made to attribute attacker-controlled body content to another merchant's tenant record — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Moderate-to-high: exploitation requires only that the attacker be able to install the app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer building against a public app) and be able to POST to the app's known webhook callback URL — no access to `api_secret_key`, access tokens, or any privileged credential is required. The webhook endpoint path is typically predictable/public (`path` configured at `add_registration`), and the gem provides no mechanism to bind headers to the signed payload.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string / HMAC computation, or independently verify that `shop` corresponds to a shop with an active, registered subscription for that webhook `topic`/`webhook_id` combination before dispatching to the handler. At minimum, document prominently that `data.shop` is not cryptographically bound to the HMAC and must not be trusted as a tenant key without additional verification (e.g., cross-referencing against known installed shops).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a routine, unprivileged action).
2. Shopify sends a legitimate webhook to the app's callback URL with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid_hmac_of_body>`, and some `raw_body`.
3. Attacker records `(raw_body, valid_hmac)`.
4. Attacker replays a POST to the same endpoint with the identical `raw_body`/`hmac` but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC(secret, raw_body)` — unaffected by the header change — and returns `true` [7](#0-6) .
6. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` = `"victim-shop.myshopify.com"` and dispatches to the handler, which per documented usage enqueues/writes work keyed to that shop [8](#0-7) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
