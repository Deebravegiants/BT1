Found a valid analog. The webhook signature verification in this gem binds only the raw HTTP body to the HMAC, while the tenant-identifying `shop` (and `topic`/`webhook_id`) fields are taken from unauthenticated HTTP headers and passed straight to the merchant's webhook handler as trusted values.

### Title
Webhook `shop`/`topic`/`webhook_id` are not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates *nothing but the body bytes*. The `shop`, `topic`, and `webhook_id` values that `Registry.process` hands to the app's webhook handler as the trusted tenant identifier are read straight from unauthenticated HTTP headers that are outside the signed data.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns `@raw_body` only, while `shop`, `topic`, and `webhook_id` are read from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` only ever checks the signature over `to_signable_string`, i.e. the body: [3](#0-2) 

`Webhooks::Registry.process` verifies only this body-bound HMAC, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` / `request.topic` / `request.webhook_id` header values and dispatches it to the app's handler as trustworthy tenant/topic identity: [4](#0-3) 

The identity binding that should hold is: `shop header == shop cryptographically bound to this body`. Instead the gem only guarantees `HMAC == valid_for(body)`, with **no** binding between the signature and the `shop`/`topic`/`webhook_id` headers. Any party who has legitimately received one real webhook delivery (i.e., any merchant who has installed the app, which is an unprivileged, no-credential position relative to the app backend) possesses a valid `(body, hmac)` pair. Because the HMAC does not commit to the `shop-domain` header, that exact `(body, hmac)` pair can be replayed to the same webhook endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header, and `Registry.process` will accept it as valid and dispatch it to the handler tagged with the attacker-chosen `shop`.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: `request.shop` is the value host applications use as the session/tenant key to decide which merchant's data a webhook payload applies to (as documented — `WebhookMetadata` carries `shop` as the identity for the event). An attacker who is merely an installed/unprivileged user of the app can forge webhook events that the app will process as if they originated from a different, victim shop, since the HMAC that's supposed to authenticate the whole request only ever authenticates the body bytes. This is a cross-tenant access primitive: data (order/product/customer content controlled by the attacker's own shop) gets injected and attributed to another tenant purely by header substitution, with no need for any credential, access token, or `client_secret`.

### Likelihood Explanation
Likelihood is high for any app that has at least one non-trivial webhook subscriber: obtaining a valid `(body, hmac)` pair only requires being an ordinary installed merchant (no special access, no leaked secret) and receiving one real webhook delivery from Shopify to observe the raw body + `X-Shopify-Hmac-Sha256` header. Replaying that pair with a substituted `shop-domain`/`topic`/`webhook-id` header against the same public HTTP endpoint requires nothing beyond normal internet access — exactly the "unprivileged internet user" threat model in scope here.

### Recommendation
Bind the tenant/topic identity into what is verified before it is trusted:
- Include `shop`, `topic`, and `webhook_id` header values in `Webhooks::Request#to_signable_string` (or otherwise cryptographically bind them), so `HmacValidator.validate` fails if any of these are altered independently of the body.
- Alternatively/additionally, require host applications to cross-check `request.shop` against the shop stored for the session/access token used to register that specific webhook (i.e., verify the shop is a known, currently-installed shop) before trusting it as a tenant key, and document this requirement clearly since the current API surface implies `WebhookMetadata#shop` is already trustworthy.

### Proof of Concept
1. App `A` is installed on `shop-victim.myshopify.com` and `shop-attacker.myshopify.com`.
2. The attacker (merchant of `shop-attacker`) receives a real webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(secret, B)` — this pair is valid to `HmacValidator.validate` since it only checks the body against `H`.
3. Attacker sends a POST directly to the app's public webhook endpoint with the same body `B`, the same `X-Shopify-Hmac-Sha256: H`, but header `X-Shopify-Shop-Domain: shop-victim.myshopify.com` (and any `X-Shopify-Topic`/`X-Shopify-Webhook-Id` of choice).
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` (body+HMAC still match), and dispatches `WebhookMetadata.new(topic: ..., shop: "shop-victim.myshopify.com", body: parsed_body, ...)` to the app's handler — which now processes attacker-controlled data as if it came from the victim shop.
