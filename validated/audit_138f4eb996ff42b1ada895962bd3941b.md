### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC of the raw JSON body, while the `shop` identity that is handed to the application's webhook handler is read from an HTTP header that is never included in the signed material. Because the HMAC secret (`Context.api_secret_key`) is a single per-app secret shared across every merchant/shop that installs the app, any party who has ever observed one genuine `(raw_body, hmac)` pair (e.g. by installing the app on their own store and capturing a real webhook delivery) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. The signature check still passes because it only covers `@raw_body`, but the handler receives an attacker-chosen `shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all derived from headers that are excluded from the signed string: [2](#0-1) 

`Registry.process` validates the HMAC of the request and then, on success, forwards `request.shop` (the unauthenticated header value) straight to the registered handler as the tenant identity for that webhook: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it to the supplied `hmac`; it never folds in `shop`, `topic`, or `webhook_id`: [4](#0-3) 

This breaks the intended identity binding: `shop authenticated by HMAC == shop delivered to the handler`. In reality the equality that holds is only `body authenticated by HMAC == body delivered to the handler`; `shop` is a completely independent, attacker-controlled field once a valid body/HMAC pair is known.

### Impact Explanation
Since `Context.api_secret_key` is shared across all shops that install a given app, an unprivileged internet user only needs to capture one legitimate `(raw_body, hmac)` pair sent to the app's public webhook endpoint (e.g., by installing the app themselves on a shop they control, or via a publicly-viewable delivery log/proxy). They can then replay that exact payload with a forged `shopify-shop-domain` header pointing at a victim shop. `Registry.process` will validate the (unchanged) body's HMAC successfully and dispatch to the handler with `data.shop` set to the victim's domain, `data.body` set to the replayed (attacker-controlled) content, and `data.topic`/`data.webhook_id` also unauthenticated. Any app logic keyed on `webhook.shop` (e.g., "update this shop's order/customer/inventory record", GDPR redact triggers, billing state, plan changes) can be made to write into or delete another tenant's data — a cross-tenant access/data-integrity violation using only a body that is legitimately signed for a different shop.

### Likelihood Explanation
Exploitation requires the attacker to obtain any one genuine `(raw_body, hmac)` pair, which is trivial for an unprivileged party: any shop that installs the app receives real signed webhooks and can freely resend them with a modified header, since headers are attacker-controlled on the wire once the payload leaves Shopify's infrastructure and lands at the app's HTTP endpoint (no additional secret or privileged access is required, just the ability to make an HTTP POST). No knowledge of `api_secret_key` is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) as part of the signed material used to compute/verify the HMAC, or independently verify the `shop` header against Shopify's actual webhook delivery semantics (e.g., cross-checking with a per-shop secret/session rather than trusting the header value). Short term, `Webhooks::Request#to_signable_string` should incorporate the shop-domain header (matching Shopify's actual webhook HMAC calculation, which is computed over the body only by design — so the fix should be to stop trusting the header for identity purposes and instead resolve the shop via a lookup that is itself bound to the verified body/topic, or reject/re-verify using stored per-shop expectations) so that replay with a substituted shop header is cryptographically detectable.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop and captures a genuine webhook delivery:
#    raw_body = '{"id":1,...}'
#    valid_hmac = <HMAC-SHA256(raw_body, api_secret_key), base64>
#
# 2. Attacker replays the exact same body/hmac to the app's public webhook endpoint,
#    but swaps the shop-domain header to a victim shop:
headers = {
  "x-shopify-topic"        => "orders/create", # same topic and body as captured, or any signed body
  "x-shopify-hmac-sha256"  => valid_hmac,       # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds because it only checks raw_body
# => handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...))
# The app's handler now processes attacker-controlled data under the victim's shop identity.
```
