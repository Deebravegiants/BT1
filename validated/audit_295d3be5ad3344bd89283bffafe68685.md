### Title
Silent failure of escrow withdrawal for non-reverting ERC20 tokens permanently freezes user funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds and sweeps protocol dust using a raw low-level `.call` with the `IERC20.transfer` selector, checking only that the call itself did not revert (`success`) but never decoding/validating the boolean return value. Tokens that follow the non-reverting failure pattern (e.g. ZRX-style tokens, which return `false` instead of reverting on failure) will cause the accounting to be finalized as if the transfer succeeded, while the beneficiary receives nothing.

### Finding Description
In `withdraw()`, called from `onAccept()` when the ISMP host delivers a `RedeemEscrow`/`RefundEscrow` request from the counterparty chain, escrowed tokens are released via: [1](#0-0) 

The same unchecked pattern is used in the `SweepDust` handler inside `onAccept`: [2](#0-1) 

And again for transaction fee payout: [3](#0-2) 

In each case, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` only reverts if the call itself fails (e.g., no code at target, out-of-gas). If the target ERC20 token contract executes normally but returns `false` (rather than reverting) to signal a failed transfer, `success` is still `true`, so the code proceeds as though the transfer succeeded. Immediately after, `_orders[body.commitment][token] -= amount` is executed and, for `RedeemEscrow`/`RefundEscrow`, `_filled[body.commitment] = beneficiary` is permanently recorded — finalizing the order despite the beneficiary never receiving the underlying tokens.

This is notably worse than the reported pattern (which uses `IERC20.transfer` directly, at least emitting an event on the same tx): here, the escrow bookkeeping is deducted and the order is irreversibly marked filled, with no mechanism to retry or reclaim, because the sibling file `evm/src/apps/IntentGatewayV2.sol` (used on standard EVM chains) and `evm/src/apps/intentsv2/IntentsBase.sol` correctly use `IERC20(token).safeTransfer(...)` via OpenZeppelin's `SafeERC20`, which decodes and asserts the return value: [4](#0-3) 

Notably, the Tron contract already imports and aliases `SafeERC20` (`using SafeERC20 for IERC20;`) at the top of the file, but this safe path is bypassed specifically in the withdrawal/sweep/fee-payout code paths that use raw `.call`: [5](#0-4) 

### Impact Explanation
Any order settled using an input/output/fee token that returns `false` on failed transfer instead of reverting will result in:
- The escrow accounting (`_orders[commitment][token]`) being decremented as if funds were paid out.
- The order being irrevocably marked `_filled`, blocking any further redemption/refund attempt for that commitment.
- The beneficiary (solver or user) receiving zero tokens for a legitimately delivered cross-chain redeem/refund message.

This constitutes permanent freezing/loss of escrowed user funds reachable via a single relayed ISMP message (`onAccept`), which any relayer can deliver once the source-chain state is proven — no privileged role is required to trigger the vulnerable code path.

### Likelihood Explanation
Likelihood depends on the specific ERC20 token configured for orders on Tron deployments. While mainstream tokens (USDT, USDC) generally revert on failure, the "assumed" and "real" token behavior is exactly the class of tokens the reported issue calls out (e.g., legacy tokens/ZRX-style implementations that return `false`). Since the IntentGatewayV2 is generic and accepts arbitrary configured tokens as order inputs/outputs/fees, any listed token exhibiting this non-reverting failure behavior (due to insufficient balance/allowance edge cases inside the token's own implementation, or non-standard/proxy tokens) triggers the bug deterministically on every failed-but-silent transfer.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (fee and token payout) and in the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the already-imported `SafeERC20` library and consistent with the standard EVM version of this contract (`evm/src/apps/intentsv2/IntentsBase.sol`), which decodes and reverts on a `false` return value.

### Proof of Concept
1. Deploy/select an ERC20 token for an intent order's input/output that returns `false` on a failed `transfer` call instead of reverting (e.g. simulate insufficient balance at the token level while still succeeding as a call).
2. A user creates and escrows an order with this token via the Tron `IntentGatewayV2`.
3. A solver fills the order on the destination chain; the source chain's `IntentGateway` dispatches a `RedeemEscrow` request which is relayed and delivered via `onAccept` → `withdraw()`.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call didn't revert) even though the token internally returned `false` and did not move funds.
5. `_orders[commitment][token] -= amount` and `_filled[commitment] = beneficiary` execute, permanently finalizing the order and destroying the ability to retry, while `beneficiary` never received the tokens — the escrowed funds are now permanently stuck/unaccounted for in the contract with no accounting entry remaining to claim them.
