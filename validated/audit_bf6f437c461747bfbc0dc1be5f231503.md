### Title
Stale cross-seed cached address returned for reused wallet account index in `connectedAccountsAtom` - ([File: features/connected-origins/module/connections.js])

### Summary
`ConnectedOrigins#getWalletAccountAddresses` prefers a cached `existingAddress` from `connectedAccountsAtom` keyed by `walletAccount.toString()` without validating it against the wallet account's current seed. Because `WalletAccount.toString()` for the `exodus` source deliberately omits `seedId`, two different seeds' account at the same index (e.g. index 0) collide on the identical key `exodus_0`, so removing a seed's account and later reusing the same index with a different seed causes the old seed's address to persist and be served for the new seed under the same cache key.

### Finding Description
`WalletAccount.toString()` explicitly strips `seedId` for `exodus`-sourced accounts: [1](#0-0) , confirmed by the dedicated test `toString() for "exodus" account does not include seedId` [2](#0-1) . This means the primary/default account slot at a given index produces the same cache key (`exodus_0`, `exodus_1`, ...) regardless of which seed currently occupies that slot.

`connectedAccountsAtom` caches addresses keyed by exactly this string: [3](#0-2) . `#getWalletAccountAddresses` reads `connectedAccounts[walletAccount]?.addresses[assetName]` and returns it immediately if present, only falling back to `addressProvider.getDefaultAddress` when there's no cached entry — it never revalidates the cached address against the walletAccount's current seed/xpub: [4](#0-3) .

`updateConnectedAccounts` further compounds this: it computes `xor(Object.keys(walletAccounts), Object.keys(connectedAccounts))` and returns early as "up-to-date" if the key sets are unchanged: [5](#0-4) . Since the key is seed-independent for exodus accounts, removing the exodus_0 account for seed A and adding a new exodus_0 for seed B (reusing index 0) produces an identical key set, so this function skips recomputation entirely, leaving seed A's address cached under `exodus_0`.

Even where recomputation is triggered by other paths (e.g., `add`/`#setAttributes` → `#setData` → `#getAccounts` → `#getWalletAccountAddresses`), the cache-first logic at lines 127-130 still returns the stale seed-A address rather than recomputing from `addressProvider.getDefaultAddress`, because presence of any cached value under the reused key short-circuits the lookup.

The stale address is then exposed to connected origins via `getConnectedAccounts`, which reads directly from `connectedAccountsAtom`: [6](#0-5) .

### Impact Explanation
A connected dapp/origin calling `getConnectedAccounts` for a wallet-account slot can receive an address that belongs to a different, no-longer-active seed rather than the address actually derived from the current seed at that slot. This is a wrong-account/cross-seed address disclosure that violates the invariant that address identity must be bound to the current seed — a dapp could display or use an address that the user's current wallet does not control, leading to confused fund destinations or account-identity mismatches surfaced to third-party origins.

### Likelihood Explanation
Requires a specific sequence: user removes the wallet account at an index (e.g. index 0), then adds/activates a different seed reusing the same index, without `connectedAccountsAtom` being explicitly cleared, and `updateConnectedAccounts`'s xor-based "already up to date" short-circuit prevents recomputation because the seed-independent key set is unchanged. This is a plausible, deterministic outcome of normal account-management operations available in the ordinary wallet UI (delete account / add seed), not requiring privileged access, so it is realistically reachable, though it depends on the specific account-management flow being exercised.

### Recommendation
Do not key or trust cache entries purely by the seed-independent `toString()` representation for reused indices; include a seed/account-identity fingerprint (e.g. `seedId` or public key hash) in the cache key or store it alongside the address so `#getWalletAccountAddresses` can validate `existingAddress` still corresponds to the current seed before reusing it. Additionally, fix `updateConnectedAccounts`'s `xor` check so it also detects when a wallet account key is associated with a *different* underlying seed/account (not just added/removed key names), forcing recomputation via `addressProvider.getDefaultAddress` in that case.

### Proof of Concept
Unit test extending `features/connected-origins/module/__tests__/connections.test.js`:
1. Seed A: set `enabledWalletAccountsAtom` to `{ exodus_0: WalletAccount.defaultWith({ seedId: seedIdA }) }`; call `connectedOrigins.add(...)` with `trusted: true` and an `assetNames` list, letting `#getAccounts` populate `connectedAccountsAtom.exodus_0.addresses` from seed A.
2. Remove seed A's account by resetting `enabledWalletAccountsAtom` to `{}`.
3. Add seed B's account at the same index: `enabledWalletAccountsAtom.set({ exodus_0: WalletAccount.defaultWith({ seedId: seedIdB }) })`.
4. Call `connectedOrigins.updateConnectedAccounts()`.
5. Assert `connectedAccountsAtom.get().exodus_0.addresses[assetName]` equals `addressProvider.getDefaultAddress({ assetName, walletAccount: seedBAccount })` (seed B's real default address) — expected to FAIL because the stale seed-A address is retained, since `xor` sees no key-set difference and skips recomputation, and even direct recomputation via `#getWalletAccountAddresses` would prefer the stale cached `existingAddress`.

  #getWalletAccountAddresses = async (walletAccount, assetNames) => {
    const connectedAccounts = await this.#connectedAccountsAtom.get()
    const entries = await Promise.all(
      assetNames.map(async (assetName) => {
        const existingAddress = connectedAccounts[walletAccount]?.addresses[assetName]
        if (existingAddress) {
          return [assetName, existingAddress]
        }

        const address = await this.#addressProvider.getDefaultAddress({ assetName, walletAccount })
        return [assetName, address.toString()]
      })
    )

    return Object.fromEntries(entries)
  }

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

  updateConnectedAccounts = async () => {
    const walletAccounts = await this.#enabledWalletAccountsAtom.get()
    const connectedAccounts = await this.#connectedAccountsAtom.get()

    const difference = xor(Object.keys(walletAccounts), Object.keys(connectedAccounts))
    if (difference.length === 0) {
      // up-to-date
      return
    }

    const connectedOrigins = await this.#connectedOriginsAtom.get()
    const assetNames = this.#getConnectedAssets(connectedOrigins)
    const updatedAccounts = await this.#getAccounts(assetNames)

    await this.#connectedAccountsAtom.set(updatedAccounts)
  }
