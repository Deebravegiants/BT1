### Title
Webhook HMAC signature does not cover the `shop` tenant identifier, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies the integrity of the body bytes but never binds that signature to the `shop` value taken from the `x-shopify-shop-domain` header. Since the same app-level `api_secret_key` signs webhooks for every shop that installs the app, any holder of one valid `(body, hmac)` pair from a legitimately signed webhook can replay it against the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, and `Registry.process` will accept it and dispatch the payload to the handler tagged with the attacker-chosen shop.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` and then builds `WebhookMetadata` using `request.shop`, which is read straight from a header, independent of the signature:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

`HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [5](#0-4) 

For `Request`, `to_signable_string` is exactly `@raw_body` — the shop-domain header is not part of the signed material:
```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

and `shop` comes only from the header:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [1](#0-0) 

The equality being broken: `shop that the HMAC-verified bytes actually originated for` should equal `shop attributed to the processed payload (request.shop)`. The gem enforces `hmac(body) == valid`, but never enforces `body → shop` binding. Because a single app-level `api_secret_key` (the same secret used across every shop that installs the app) signs all webhooks, an attacker who controls any shop that has the app installed (an unprivileged action — installing a public/dev app on one's own store) can capture a legitimately-signed `(raw_body, hmac)` pair delivered to their own store, then POST the identical bytes to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. The signature still validates (it only covers `raw_body`), so `Registry.process` dispatches the handler with `data.shop` set to the victim's domain, causing the host application to process/store attacker-supplied webhook data as though it originated from and belongs to a different tenant.

### Impact Explanation
This breaks the tenant identity boundary the gem is trusted to enforce for webhook delivery: any data keyed by `request.shop` (e.g., order/customer/product upserts, redact requests, install/uninstall events) can be attributed to an arbitrary victim shop by any attacker who controls a single, otherwise legitimate, app installation. This is cross-tenant data injection/corruption inside a multi-tenant app — matching the in-scope "cross-tenant access" impact category, since the host application relies on this gem's `HmacValidator`/`Registry.process` to establish which tenant a webhook body belongs to before acting on it.

### Likelihood Explanation
Likelihood is realistic but requires attacker to control a valid app installation on some shop (achievable by any unprivileged developer/user who installs the app on their own store — no privileged Shopify or partner access needed) and to know or guess a victim's `.myshopify.com` domain (public information). No access token, `client_secret`, or leaked credential is required; only observing one's own legitimately delivered webhook body+HMAC and replaying it with a different header value against the app's public webhook receiver endpoint.

### Recommendation
Bind the shop identity into the signature verification path, or otherwise cryptographically tie `request.shop` to the verified payload before dispatch:
- Extend `to_signable_string` (or add a distinct verification step) so the shop-domain header is included in the HMAC-covered material, matching how Shopify's own webhook signing actually works only over the body — since Shopify does not sign the header, the gem/host app must instead verify that `request.shop` corresponds to a shop for which this app instance has an active, expected registration (e.g., cross-check against the webhook subscription/shop that was registered), rather than trusting the header verbatim.
- At minimum, document prominently in `Registry.process` and the webhook usage docs that `request.shop` is unauthenticated header data and host apps must independently verify shop ownership/installation state before trusting `data.shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 1, ...}` (attacker-shop's own order — attacker can craft/control this content on their own store)
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, raw_body)` — unchanged from step 2 — and it matches, so validation passes.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the host app to process attacker-controlled webhook data under the victim shop's tenant context.
