Audit Report

## Title
Weight/fuel desynchronization between host-call charges and PolkaVM engine fuel allows execution beyond `effective_weight_limit` before `OutOfGas` is raised - (File: substrate/frame/revive/src/metering/weight.rs)

## Summary
`WeightMeter::sync_to_executor` (called once in `ContractBlob::prepare_call`) and `WeightMeter::sync_from_executor` (called once in `PreparedCall::call`, after the entire `instance.run()` loop terminates) bracket an entire PolkaVM call, but host-function (`Ecalli`) charges made via `charge_weight_token`/`WeightMeter::charge` during that call check `weight_consumed` against `effective_weight_limit` without ever folding in the engine's independently-tracked, in-flight fuel consumption. This means a contract that interleaves host calls with instruction bursts can cause the sum of (engine fuel spent, capped at the initial budget derived from `effective_weight_limit`) and (host-call charges, independently capped at `effective_weight_limit`) to exceed `effective_weight_limit` before the final reconciliation in `sync_from_executor` detects and reports `OutOfGas`.

## Finding Description
In `substrate/frame/revive/src/vm/pvm/env.rs` (`prepare_call`, L85), `sync_to_executor()` computes the PolkaVM fuel budget from `weight_left()` once, before `instance.set_gas(gas_limit_polkavm)` and before the run loop starts: [1](#0-0) 

This uses `EngineMeter::sync_remaining_ref_time`, which converts the current `weight_left()` into a fuel value once: [2](#0-1) 

The PolkaVM module is configured with `GasMeteringKind::Sync`, meaning the engine autonomously decrements and enforces its *own* internal gas/fuel counter per basic block, independent of the `WeightMeter`: [3](#0-2) 

The interpreter loop in `PreparedCall::call` only calls `sync_from_executor` once, after `handle_interrupt` finally returns a terminal result (`Finished`, `Trap`, `NotEnoughGas`, etc.). Every `Ecalli` is dispatched to `handle_ecall` and the loop continues without syncing fuel back to the `WeightMeter`: [4](#0-3) [5](#0-4) 

Host functions charge weight directly via `charge_gas`/`charge_weight_token`, which calls `WeightMeter::charge`: [6](#0-5) 

That check compares `weight_consumed` (which, mid-execution, reflects only previously-charged host-call costs, since engine fuel usage is not synced until the very end) against `effective_weight_limit`. The two accounting paths — the engine's own fuel counter (bounded to the initial budget, `L`) and the `WeightMeter`'s `weight_consumed` (bounded to `L` by `charge()`, but populated only from host-call tokens until the final sync) — are independent and not summed until `sync_from_executor` runs: [7](#0-6) 

The doc comments on `sync_from_executor`/`sync_to_executor` explicitly describe the intended design as syncing "when entering a host function" and "when leaving a host function" respectively, confirming this is a per-host-call synchronization protocol that is not actually implemented at those boundaries — it is only invoked at the call's start and end: [8](#0-7) 

As a result, a contract can execute up to `L` worth of fuel-metered instructions (bounded and eventually caught by the engine's own `NotEnoughGas` interrupt) while independently accumulating up to `L` worth of host-call charges (bounded and eventually caught by `WeightMeter::charge`'s comparison against `effective_weight_limit`), because neither accounting path is aware of the other's consumption during the call. Only when the run loop terminates does `sync_from_executor` add the actual fuel-derived weight on top of already-charged host costs, at which point the combined overflow is detected — after the corresponding computation has already executed.

## Impact Explanation
Within a single call/frame, the code as verified allows the *combined* real resource consumption (engine-fuel-metered instructions plus separately-tracked host-call charges) to exceed `effective_weight_limit` before `OutOfGas` is finally raised at `sync_from_executor`. This is a genuine weight-metering enforcement gap: the intended per-host-call reconciliation (documented in the code) is not wired up at the `Ecalli` boundary in `handle_interrupt`/`PreparedCall::call`, so the invariant "`weight_consumed` reflects true cumulative consumption at every check" does not hold mid-call. The result is still eventually rejected as `OutOfGas`, but excess computation may have already been performed by the time it is detected, which is an over-consumption of block-execution resources relative to the configured weight limit — a resource-accounting/DoS-adjacent issue rather than a funds-loss or state-corruption issue.

## Likelihood Explanation
This is reachable by any unprivileged account able to deploy and invoke a PVM contract, since crafting bytecode that interleaves cheap host calls (e.g., simple storage/env syscalls) with heavy instruction loops requires no special privilege, signature, or origin checks — only ordinary contract deployment and calling. The degree of overrun is bounded by `effective_weight_limit` itself (worst case roughly double the intended limit for a single frame/call, per the mechanics shown above), not unbounded, but it is concretely reachable through the normal `call`/`instantiate` extrinsic path.

## Recommendation
Perform the fuel/weight reconciliation at every host-call (`Ecalli`) boundary rather than only once at the start and end of `PreparedCall::call`: call `sync_from_executor(instance.gas())` immediately upon entering `handle_ecall` (before charging the host-call cost) so `weight_consumed` reflects true cumulative usage, and call `sync_to_executor()` again immediately before returning control to the engine (updating `instance.set_gas(...)` with the correctly-reduced budget). This preserves the `weight_consumed <= effective_weight_limit` invariant at every `charge()` decision point, matching the behavior already documented in the `sync_from_executor`/`sync_to_executor` doc comments in `substrate/frame/revive/src/metering/mod.rs`.

## Proof of Concept
1. In `substrate/frame/revive/src/metering/weight.rs` test module, construct a `WeightMeter` with `effective_weight_limit = L`.
2. Call `sync_to_executor()` to obtain the initial fuel budget `F0` (simulating engine start), analogous to the real call in `prepare_call` (`substrate/frame/revive/src/vm/pvm/env.rs` L85).
3. Simulate the engine consuming fuel down to near-zero (without calling `sync_from_executor`), analogous to an instruction burst executed between `Ecalli` interrupts in `PreparedCall::call`.
4. While `sync_from_executor` has not yet been called, invoke `charge(token)` repeatedly for tokens whose cumulative weight cost approaches `L`, analogous to host calls dispatched via `handle_ecall` in `substrate/frame/revive/src/vm/pvm/env.rs` (L153-181); assert each succeeds.
5. Finally call `sync_from_executor(engine_fuel ≈ 0)`, analogous to the single call at the end of `PreparedCall::call` (`substrate/frame/revive/src/vm/pvm.rs` L853-856), and observe `weight_consumed` jumps to `(sum of host charges) + (fuel-derived weight)`, exceeding `L`, with `OutOfGas` only returned at this final step — confirming that the combined real work performed prior to detection exceeded the configured limit.

	pub fn sync_from_executor(&mut self, engine_fuel: polkavm::Gas) -> Result<(), DispatchError> {
		let weight_consumed = self
			.engine_meter
			.set_fuel(engine_fuel.try_into().map_err(|_| Error::<T>::OutOfGas)?);

		self.weight_consumed.saturating_accrue(weight_consumed);
		if self.weight_consumed.any_gt(self.effective_weight_limit) {
			self.weight_consumed = self.effective_weight_limit;
			return Err(<Error<T>>::OutOfGas.into());
		}

		Ok(())
	}

impl<'a, E: Ext> PreparedCall<'a, E> {
	pub fn call(mut self) -> ExecResult {
		let exec_result = loop {
			let interrupt = self.instance.run();
			if let Some(exec_result) =
				self.runtime.handle_interrupt(interrupt, &self.module, &mut self.instance)
			{
				break exec_result;
			}
		};
		crate::tracing::if_tracing(|tracer| {
			tracer.enter_ecall(crate::tracing::PVM_FUEL_NAME, &[], &self.runtime)
		});
		let sync_result =
			self.runtime.ext().frame_meter_mut().sync_from_executor(self.instance.gas());
		crate::tracing::if_tracing(|tracer| tracer.exit_step(&self.runtime, None));
		sync_result?;
		exec_result
	}
