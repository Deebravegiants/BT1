### Title
POA Bridge withdrawal status is matched by `assetId` only, causing duplicate withdrawals of the same token in a batch to report identical status/txHash - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` resolves the status of a specific withdrawal in a batch by calling `findMatchingWithdrawal(withdrawals, args.withdrawalParams.assetId)`, which uses `Array.prototype.find()` keyed solely on `assetId`. This mirrors the MEME404 bug class: an equality check that should bind to the *specific instance* (here, the specific withdrawal within a batch, analogous to the specific tier/nftId) instead only validates one field (assetId, analogous to the previously-added tier) and stops there, silently accepting/matching duplicates.

### Finding Description
The `WithdrawalIdentifier` returned by `createWithdrawalIdentifier` carries an `index` field meant to disambiguate multiple withdrawals of the same route/bridge in one NEAR transaction [1](#0-0) . However, `PoaBridge.describeWithdrawal` never uses that `index`; it locates the withdrawal purely by `assetId`: [2](#0-1) 

and the matching helper is explicit about this limitation: [3](#0-2) 

`createWithdrawalIdentifiers` in the batch-withdrawal watcher assigns a per-bridge sequence `index` to every withdrawal, including multiple withdrawals of the same `assetId` through the same bridge route: [4](#0-3) 

`watchWithdrawal` (used by `waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`) polls `describeWithdrawal` per identifier and resolves each one to whatever status/txHash comes back: [5](#0-4) 

Because `findMatchingWithdrawal` ignores `index` and just returns the first API entry whose `defuse_asset_identifier`/`near_token_id` equals the requested `assetId`, if a single batch (`sdk.processWithdrawal({ withdrawalParams: [...] })`) contains two or more withdrawals of the *same* token (e.g., two USDT withdrawals to different destination addresses in one intent), both `WithdrawalIdentifier`s (`index: 0` and `index: 1`) resolve to the **same** POA API entry. Whichever entry the API happens to return matching that `assetId` gets echoed back to both callers.

### Impact Explanation
This breaks the equality "status/txHash reported == the on-chain outcome of *this specific* withdrawal." Concretely:
- If withdrawal #0 (assetId X) completes with `transfer_tx_hash: "tx-A"`, and withdrawal #1 (same assetId X, different destination/amount) is still pending or failed, `describeWithdrawal` for index 1 will return `{ status: "completed", txHash: "tx-A" }` — the same completed status/hash belonging to a different withdrawal.
- An integrator using `createWithdrawalCompletionPromises` or `waitForWithdrawalCompletion` (both built directly on `watchWithdrawal`/`describeWithdrawal`) would treat withdrawal #1 as completed and would associate/credit/reconcile it against `tx-A`, even though the funds for withdrawal #1 either haven't moved, failed, or moved to a different destination. This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category from the rules — the wrong transaction hash can be attributed to a withdrawal that didn't actually settle that way, leading an integrator to double-credit a user, mis-reconcile ledgers, or falsely mark a stuck/failed withdrawal as done.
- This requires no malicious relayer/RPC behavior; it's triggered purely by ordinary user input (an unprivileged caller batching two withdrawals of the same PoA-bridged token in one `processWithdrawal`/`signAndSendWithdrawalIntent` call), which the SDK's own README explicitly advertises as a supported use case ("Batch Processing: Process multiple withdrawals at a time").

### Likelihood Explanation
Likelihood is meaningful but not certain to be exploited by chance: it only manifests when a batch contains ≥2 withdrawals with identical `assetId` through the POA bridge route. The SDK explicitly documents and supports batch withdrawals with arbitrary `withdrawalParams` arrays, and nothing in `supports()`/`createWithdrawalIntents()`/`createWithdrawalIdentifiers()` rejects or deduplicates same-asset entries — so any integrator or end-user constructing such a batch (a normal, unprivileged action) will trigger this. The code comment in `findMatchingWithdrawal` acknowledges the limitation but the library does not guard callers against it (no validation error is thrown when duplicate assetIds are detected in a batch for the PoA route).

### Recommendation
- In `createWithdrawalIdentifiers`/`processWithdrawal`, detect and reject (or otherwise disambiguate) batches containing multiple `withdrawalParams` entries with the same `assetId` routed to `PoaBridge`, until the POA bridge API supports matching by more than `assetId`.
- Alternatively, as hinted in the existing comment, match by sorting both the API's `withdrawals` list and the local `withdrawalParams` list by `amount` for a given `assetId` (since fees are equal for the same token, relative amount ordering should be preserved) rather than blindly taking `Array.find()`'s first match, and validate that the count of on-chain entries for that `assetId` is not exceeded.
- At minimum, surface a runtime error/warning from `PoaBridge.supports()` or `createWithdrawalIdentifiers()` when duplicate `assetId`s are detected in a single POA-routed batch, so integrators cannot silently rely on misattributed statuses.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: "addrA", feeInclusive:false}, {assetId: "nep141:btc.omft.near", amount: 200000n, destinationAddress: "addrB", feeInclusive:false} ] })` — two BTC withdrawals in one intent, both through PoaBridge.
2. `createWithdrawalIdentifiers` assigns `index: 0` to the first and `index: 1` to the second (same bridge route "poa_bridge") [6](#0-5) .
3. The relayer executes both `ft_withdraw` calls with the same `near_token_id` ("btc.omft.near"); the POA API's `getWithdrawalStatus` response contains two `withdrawals` entries both with `defuse_asset_identifier: "nep141:btc.omft.near"`.
4. `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` both call `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the *same* first matching entry (e.g., the one that completed to addrA) for both calls [2](#0-1) [7](#0-6) .
5. `sdk.createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` resolves both entries to `{ hash: <addrA's tx hash> }`, even though the withdrawal to `addrB` may still be pending or may have gone to a different transaction — an integrator polling per-index results will incorrectly believe withdrawal #1 (to addrB) landed with the tx hash intended for withdrawal #0 (to addrA).

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
