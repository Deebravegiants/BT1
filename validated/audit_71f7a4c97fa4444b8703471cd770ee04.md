### Title
Missing zero-amount check in `IntentGatewayV2.withdraw` permanently freezes escrowed funds on Tron - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases/refunds escrowed order tokens in `withdraw()` by iterating every `TokenInfo` in the order and calling `token.call(transfer, beneficiary, amount)` unconditionally, even when `amount == 0`. The mainline EVM implementation of the same logic (`IntentsBase._withdraw`) explicitly skips zero-amount transfers with `if (amount == 0) continue;`, but this guard is absent from the Tron contract. If any escrowed input token reverts on a zero-value `transfer` call (a well-known non-standard ERC20 behavior, e.g. the historical LEND token cited in the original report), or if an order simply contains a zero-amount `TokenInfo` entry, the entire `withdraw()` call reverts every time it is invoked, permanently freezing all tokens escrowed under that order commitment.

### Finding Description
`placeOrder` only requires `order.inputs.length != 0` — it never rejects a per-token `amount` of `0`: [1](#0-0) 

When the settlement/refund message is delivered via `onAccept` (for `RedeemEscrow`/`RefundEscrow`) or via `onGetResponse` (for source-chain cancellation), the contract calls `withdraw(body, ...)`, which loops over `body.tokens` and performs a raw low-level `call` to `transfer` for **every** entry, without ever checking `amount == 0`: [2](#0-1) 

Compare this to the mainline EVM `IntentsBase._withdraw`, which explicitly guards against this exact case: [3](#0-2) 

Because `withdraw` on Tron does not skip zero-amount transfers, any token in the escrowed set that reverts on a zero-value `transfer()` call — or simply a legitimately-placed zero-amount `TokenInfo` — causes the low-level `call` to return `success = false`, which is then converted into `revert TransferFailed()`. Since the `amount` and the underlying token behavior never change between retries, **every subsequent delivery attempt of the same commitment's settlement/refund message reverts identically**, permanently freezing the escrowed funds with no recovery path.

### Impact Explanation
This directly mirrors the "repay" bug class from the report: a single non-zero-value-tolerant ERC20 asset (or a zero-amount input) embedded in an order's `inputs` causes the `EscrowReleased`/`EscrowRefunded` withdrawal to become permanently un-callable for that commitment. Because `withdraw()` processes the *entire* token list for the order atomically, even legitimately non-zero escrowed tokens bundled in the same order become unreachable — a concrete, permanent freezing of user/solver funds. This satisfies the "permanent freezing of funds" acceptance criterion for the Hyperbridge-analog validation.

### Likelihood Explanation
Reachable by any ordinary user submitting a cross-chain intent order (`placeOrder`) with a token amount of `0` for one of the assets, or by using any input token that reverts on transferring zero value — both are conditions fully controlled by an unprivileged end user constructing the order, requiring no special privileges, and matching the exact reproduction pattern (deposit/transfer of a zero-value-reverting token) demonstrated in the original report.

### Recommendation
Add the same zero-amount guard used in the mainline EVM `IntentsBase._withdraw` to the Tron `IntentGatewayV2.withdraw` function — skip the transfer (and corresponding escrow bookkeeping) whenever `amount == 0`, e.g.:
```solidity
if (amount == 0) { unchecked { ++i; } continue; }
```
before performing the `token.call(...)` transfer, mirroring the fix already present in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs` containing two `TokenInfo` entries: one for USDC (100 units) and one for a token that reverts on `transfer(to, 0)` (or simply set that entry's `amount` to `0`).
2. Order is filled on the destination chain; a `RedeemEscrow` message is dispatched back and delivered via `onAccept` → `withdraw(body, false)`.
3. Inside `withdraw`, the loop reaches the zero-value token entry and calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, 0))`.
4. The token reverts (or the low-level call fails), causing `success == false`, and `withdraw` reverts with `TransferFailed()`.
5. Because the request/commitment state and the token's revert-on-zero behavior never change, retrying the message delivery reproduces the same revert indefinitely — the USDC and any other escrowed tokens for this commitment remain locked in the contract forever.
