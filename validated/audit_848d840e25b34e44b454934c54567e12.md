### Title
Signup signature domain omits `signup_id`, enabling cross-signup replay of a genuine secure-element signature - ([File: src/plans/enroll_user.rs])

### Summary
The GMX Oracle report's root cause is that a signature's domain (`SALT`) is fixed to a subset of context (only `chainid` at construction) and omits a value that changes per-use, so a signature legitimately produced in one context can be replayed in a different context that the signer never intended to authorize. The orb-core analog is `make_signature()` in `src/plans/enroll_user.rs`, which builds the secure-element-signed payload from `ORB_ID`, `user_qr_code.user_id`, and the deterministic iris/mask codes/versions, but never includes the per-attempt `signup_id` (the unique identifier POSTed as the URL path segment in `signup_post::request`). ### Finding Description
`make_signature` hashes together `ORB_ID`, `user_qr_code.user_id`, `pipeline.v2.ir_net_version`, `pipeline.v2.iris_version`, and the left/right `iris_code`/`mask_code`/`iris_code_version` fields, then signs the digest with the secure element key: [1](#0-0) 

None of these inputs is bound to the specific signup session (`signup_id`) that the signature is meant to authorize. `signup_id` is generated separately by the caller in `Plan::run` and sent as a distinct multipart field/URL path in `signup_post::request`, entirely outside of what is cryptographically signed: [3](#0-2) [4](#0-3) 

Because the iris pipeline outputs (`iris_code`, `mask_code`, version strings) are deterministic for a given capture, the exact same secure-element signature bytes will be produced any time the same biometric data and user QR code are re-submitted — regardless of which `signup_id` (session) is attached to the HTTP request. This is structurally identical to the GMX bug: the signed artifact's domain separator (`SALT` in GMX, the signature payload here) does not include the value that is supposed to scope the signature to one specific execution context (`block.chainid` there, `signup_id` here), so a valid signature obtained for one context can be attached to a request in a different context and still validate.

### Impact Explanation
If an entity with visibility into a previously-submitted signup's HTTP request (e.g. a compromised/local component able to observe outbound requests, or a captured request that is later resubmitted) reuses the `signature` field with a different `signup_id`, the backend has no cryptographic means to detect that the signature was not generated for that particular signup attempt, since the signature never encoded which `signup_id` it was for. This can let a stale, previously-issued proof-of-orb-signing be attached to an unrelated signup record, undermining the guarantee that each `signup_id`'s biometric submission was freshly attested by the physical orb hardware for that specific session — a cross-signup state-bleed / misattributed-signup condition.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires the attacker to obtain a previously valid `(userId, codes, signature)` tuple (e.g., via network capture, a compromised local process able to see outbound signup requests, or a retried/duplicated request) and resubmit it against a different `signup_id`. Because there is no timestamp, nonce, or `signup_id` binding in the signed digest, the backend's only defense would have to come from out-of-band request-level checks rather than the signature itself, meaning any gap in those separate checks makes this fully exploitable.

### Recommendation
Include `signup_id` (and ideally a freshness value such as a timestamp/nonce) directly in the data hashed by `make_signature` before calling `secure_element::sign`, so the signature cryptographically binds to the exact signup session it authorizes rather than only to the user and biometric outputs:
```rust
ctx.update(signup_id.as_bytes()); // bind signature to this specific signup attempt
```
This mirrors the GMX fix recommendation of separately including the per-context value (`block.chainid`) rather than relying on a value baked in once and reused across contexts.

### Proof of Concept
1. A signup completes normally: `make_signature` produces `sig_A` from `(ORB_ID, user_id, iris codes)` for `signup_id = A`, and `signup_post::request` posts `sig_A` to `/api/v2/signups/A`.
2. An attacker (or a buggy/malicious local component with request visibility) captures the multipart body containing `sig_A` and the unsigned `codes` JSON.
3. The attacker submits a new request to `/api/v2/signups/B` (a different `signup_id`) using the same `userId`, `codes`, and `sig_A` value.
4. Because `sig_A` never encoded `signup_id = A`, it is bit-for-bit identical to what would have been produced for `signup_id = B` given the same biometric inputs, so signature verification (if solely based on the signed payload contents) cannot distinguish the replay — the second, unauthorized signup record is accepted as if freshly attested by the secure element for session `B`. fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
