### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop` attribute that downstream handlers use to attribute the webhook to a specific merchant is read from an unauthenticated HTTP header. Any unprivileged internet user who can obtain one genuine, HMAC-signed webhook body from the app (e.g., by installing the app on their own development/test store) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the library will report the request as valid and attribute it to the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks the body against the secret; it never incorporates `shop`, `topic`, `api-version`, or `webhook-id`: [3](#0-2) 

`Registry.process` passes this unauthenticated `shop` value straight to the app's webhook handler as the tenant identifier for the event, after only checking the (body-only) HMAC: [4](#0-3) 

The identity binding that should hold is: `shop_header == shop_that_the_signature_authenticates`. In reality the HMAC only authenticates `hmac_computed(secret, raw_body) == received_hmac`; the `shop` header is never part of that computation. Because the app's `client_secret` is shared across every shop that installs the app, any user can legitimately install the app on their own store, capture a real webhook (valid body + valid HMAC), and then re-send that same body/HMAC pair to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` will dispatch the event to the handler with `data.shop` set to the attacker-chosen (victim) shop.

### Impact Explanation
This breaks the tenant-identity binding at the exact point host applications rely on this gem to establish trust: `WebhookMetadata#shop`. Any application built on top of this gem that scopes data lookups/writes by `data.shop` (the documented, intended usage) can be tricked into applying a webhook payload — order data, GDPR/compliance topics, uninstall events, etc. — to a different merchant's tenant than the one that actually produced it. This is a cross-tenant impact carried entirely by data forged by an unprivileged party who only needed to install the app once on their own store; it does not require the victim's or the app's `api_secret_key`.

### Likelihood Explanation
Likelihood is high: installing an app on a self-owned development store is normal, unauthenticated-relative-to-the-victim behavior, and capturing/replaying an HTTP request with modified headers requires no special access. The vulnerable code path (`Request#to_signable_string`, `Request#shop`, `HmacValidator.validate`) is on the default webhook-processing path documented and used by every consumer of `ShopifyAPI::Webhooks::Registry.process`.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material, or otherwise cryptographically bind them to the body before trusting them, e.g., have `to_signable_string` incorporate a canonicalized representation of body + shop + topic, or independently verify `shop` against a known/allow-listed value before dispatching to handlers, mirroring the approach `AuthQuery#to_signable_string` already uses to include every field it later trusts (`code`, `host`, `shop`, `state`, `timestamp`): [5](#0-4) 

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw POST body `B` and the genuine `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(client_secret, B)`.
2. Attacker sends a new request to the app's webhook endpoint with:
   - Body: the same `B`
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since `B` is unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as desired
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (required headers present).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and compares to `H` — this matches, so validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, causing the host application to process attacker-supplied data as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
