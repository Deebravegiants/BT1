Found the analog vulnerability. `ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw body, while the `shop` field used for tenant identification is taken from an unauthenticated header and never enters the signed material — this exactly matches the reported bug class ("a field acted on but not covered by the HMAC").

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop` — the field the registry uses to identify which tenant the webhook belongs to — is read directly from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) . `Utils::HmacValidator.validate` only checks that the HMAC matches `to_signable_string`, i.e., only the body bytes, never binding the shop header to the signature [3](#0-2) . `Webhooks::Registry.process` then trusts `request.shop` and hands it straight to the app's handler as the tenant identity for the delivered payload [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop header value == shop whose secret produced the HMAC over this body`. Because `to_signable_string` is `@raw_body` only, the HMAC proves nothing about which shop domain header accompanies the request — it only proves the body was signed with the app's `client_secret` (shared across every shop that installs the app) [5](#0-4) . Any merchant who installs the app on their own store legitimately receives correctly-HMAC'd webhooks from Shopify for their own shop's events. Since the app's `client_secret` is identical for all shops, that attacker-controlled merchant can replay the exact same signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate(request)` still succeeds because the signature check never inspects the header [6](#0-5) , and `WebhookMetadata` is built with `shop: request.shop` set to the victim's domain [7](#0-6) .

### Impact Explanation
Host applications built on this gem are expected to use `WebhookMetadata#shop` to identify which merchant/session/access-token record a webhook payload applies to. Because the shop identity is not cryptographically bound to the signed content, a malicious but legitimately-installed merchant can forge webhook deliveries that the app will process as if they originated from a different, victim tenant — a cross-tenant access/data-injection vector using only the attacker's own valid installation, no leaked secrets required.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as a normal merchant (something any attacker can do for an app they target), (2) triggering or observing a webhook Shopify sends for their own shop, and (3) resending that exact body to the app's public webhook endpoint with a different `x-shopify-shop-domain` header. No access to the app's `client_secret`, access tokens, or other shops' credentials is needed, making this a low-effort, unprivileged-attacker path.

### Recommendation
Bind the shop (and ideally the webhook id/topic) into the signed material, or otherwise cryptographically tie the header values to the verified request — e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or require the host application to independently confirm the shop-domain header matches a previously known/authorized tenant before trusting `WebhookMetadata#shop`. Document clearly that only the body is HMAC-protected and headers must not be trusted as-is for tenant identification.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., empty-body test webhook) and captures the resulting `x-shopify-hmac-sha256` value Shopify computed over the raw body using the app's `client_secret`.
3. Attacker sends a POST to the app's webhook endpoint with the same raw body and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` passes because it only checks `@raw_body` against the HMAC [1](#0-0) .
5. `ShopifyAPI::Webhooks::Registry.process` invokes the app handler with `shop: "victim.myshopify.com"` [7](#0-6) , causing the host app to act on data as if it came from the victim tenant.
