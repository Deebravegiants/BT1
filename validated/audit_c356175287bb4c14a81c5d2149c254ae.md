### Title
Webhook shop-domain attribution is not cryptographically bound to the HMAC-verified body, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from an HTTP header that is never covered by the HMAC signature check performed by `ShopifyAPI::Utils::HmacValidator`. `Registry.process` treats a passing HMAC check as proof that the *entire* webhook, including its shop attribution, is authentic, and hands the header-derived shop straight to the host application's handler.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

Only `@raw_body` is included in `to_signable_string`, i.e. only the body is HMAC-protected. But `shop` is read directly from an unauthenticated header: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the digest solely over `verifiable_query.to_signable_string` (the body) and never incorporates `shop`, `topic`, or `webhook-id`: [4](#0-3) 

The broken identity binding is: `HMAC-authenticated body == shop-domain header used for tenant attribution`. These are two independent fields, only one of which is signed, yet the gem's `Registry.process` treats a valid HMAC as authorizing both. Because a public Shopify app's HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the same across *all* merchant installations, any unprivileged internet user who installs the app on their own free/dev store can trigger a webhook and obtain a body + HMAC pair that is genuinely valid for the app. They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because the header is not part of the signed content, and `Registry.process` dispatches the (attacker-chosen) body content to the handler labelled as coming from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break carried entirely within the gem's own trust logic (`HmacValidator` + `Webhooks::Registry`/`Request`), not merely "the host ignoring documented behavior" — the gem itself asserts the request is valid ("Invalid webhook HMAC" is the only check performed) and hands over an attacker-controlled `shop` value as trusted metadata. Any host application that uses `WebhookMetadata#shop` from the handler (the documented, intended usage) to select which merchant's session/access token/data to act on will process attacker-supplied body content under another tenant's identity — i.e., cross-tenant data poisoning/access. This matches the Critical "cross-tenant access" bucket.

### Likelihood Explanation
Likelihood is significant: obtaining a valid (body, HMAC) pair requires nothing more than installing a public app on one's own store — an entirely unprivileged, self-service action — and triggering any webhook event. Forging the shop header on the replayed HTTP request requires no cryptographic material at all, since it is excluded from the signed content. The webhook endpoint is, by design, a publicly reachable, unauthenticated HTTP endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content for webhook requests, or otherwise independently bind the `shop` header to the signing key/tenant before it is passed downstream (e.g., verify the header against a registered/expected list of installed shops server-side, or require that the `shop` header be within the canonicalized/signed payload similar to how `Oauth::AuthQuery#to_signable_string` binds `shop`, `state`, `code`, `host`, and `timestamp` together — see `lib/shopify_api/auth/oauth/auth_query.rb` lines 33-43). At minimum, document prominently that `WebhookMetadata#shop` is *not* authenticated by the HMAC check and must not be used by host applications as an identity boundary without additional verification.

### Proof of Concept
1. Attacker installs the target public app on their own store `attacker-shop.myshopify.com` (self-service, unprivileged) and triggers any registered webhook topic (e.g. `products/update`), capturing the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC-SHA256(api_secret_key, B)`, per `lib/shopify_api/utils/hmac_validator.rb` lines 33-40).
2. Attacker resends this exact `B`/`H` pair to the app's public webhook endpoint but replaces the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shop-domain" => "victim-shop.myshopify.com", "hmac-sha256" => H, ...})` is constructed; `to_signable_string` returns `B` only (`lib/shopify_api/webhooks/request.rb` lines 35-38), so `Utils::HmacValidator.validate(request)` returns `true` (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. `ShopifyAPI::Webhooks::Registry.process(request)` passes the check at line 190 (`lib/shopify_api/webhooks/registry.rb`), and calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...))`, causing the app's handler to act on attacker-chosen body content under the victim shop's identity — even though the victim never sent this webhook.
