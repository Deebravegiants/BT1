## Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` treats the HTTP `X-Shopify-Shop-Domain` header as an authenticated tenant identifier, but the HMAC signature that `Registry.process` validates is computed **only over the raw request body** — the shop-domain header (along with topic, webhook-id, api-version) is never part of the signed material. Any caller who can produce one valid `(body, hmac)` pair for the app's shared webhook endpoint (trivially obtainable by installing the app on their own store and capturing the genuine webhook Shopify sends them) can replay that exact body/hmac pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the app to process the payload as if it originated from a different tenant.

### Finding Description
`Request#hmac` is computed from `shopify-hmac-sha256`, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature strictly against `verifiable_query.to_signable_string` (i.e. the raw body for webhooks), never incorporating the shop header: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the host application's handler, without ever re-deriving or cross-checking the shop against anything covered by the signature: [4](#0-3) 

`WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is the value host apps use to scope handler logic to a tenant: [5](#0-4) 

**Broken identity binding (as an equality):**
`shop authenticated by HMAC` should equal `shop attributed to the processed event`, but the code only guarantees `hmac(raw_body, api_secret_key) == received_hmac`; it never guarantees `shop-domain header == the shop that Shopify actually generated this body/hmac pair for`. Because SaaS apps built on this gem typically expose a single shared webhook URL for all installed shops, any merchant who is a legitimate (unprivileged) installer of their own instance of the app can:

1. Install the app on their own store (`attacker-shop.myshopify.com`), triggering a genuine, correctly-signed webhook delivered to the shared endpoint — `body`, `X-Shopify-Hmac-Sha256`, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` are all attacker-observable since they hit the attacker's own request logs.
2. Replay that exact `body` + `X-Shopify-Hmac-Sha256` value directly to the app's public webhook endpoint, but with `X-Shopify-Shop-Domain` rewritten to `victim-shop.myshopify.com`.
3. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the forged event to the handler tagged as belonging to `victim-shop`.

### Impact Explanation
This crosses a tenant boundary without any credential, TLS interception, or privileged access: the attacker only needs to be a normal, unprivileged installer of the app on their own shop and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. Depending on which webhook topics the host app subscribes to (e.g. `app/uninstalled`, `orders/paid`, `customers/data_request`, `shop/update`), this enables spoofed cross-tenant events that can trigger unauthorized state changes, data disclosure, or business-logic actions attributed to a victim shop the attacker never actually controls — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any host application built with this gem that (a) exposes one shared HTTP callback URL for all shops (the common SaaS pattern shown in the gem's own docs/usage/webhooks.md example) and (b) trusts `WebhookMetadata#shop` as the tenant key without additional server-side verification (e.g. checking the shop is one that legitimately has this webhook_id registered). No special privileges, secrets, or network position are required — only the ability to install the app once and issue a normal HTTP POST.

### Recommendation
Do not treat the `shop-domain` header as authenticated. Either:
- Include the shop domain in the material verified by the HMAC (not possible unilaterally since Shopify controls the signing scheme), or
- Cross-check the incoming `shop` value against a shop that is known to have an active registration/subscription for the given `webhook_id`/topic before dispatching to the handler, and reject mismatches, or
- Document explicitly and enforce (e.g. via a guard in `Registry.process`) that the `webhook_id` in the payload must correspond to a subscription owned by the claimed `shop`, closing the gap between "body integrity proven" and "shop attribution proven."

### Proof of Concept
1. Install the target app (built on this gem) on an attacker-controlled shop `attacker.myshopify.com`; the app's shared webhook endpoint `POST /webhooks` receives a real request:
   - Headers: `X-Shopify-Topic: orders/paid`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Webhook-Id: w1`
   - Body: `{"id": 1, ...}`
2. Attacker captures this exact request from their own server logs (no interception of Shopify's traffic needed).
3. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (the body) — see `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"`, and the host handler processes the attacker's payload as an event belonging to the victim tenant — `lib/shopify_api/webhooks/registry.rb:198`.
