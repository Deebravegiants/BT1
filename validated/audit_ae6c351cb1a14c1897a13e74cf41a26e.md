## Finding

### Title
Webhook shop attribution is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so the HMAC signature that `Registry.process` validates covers nothing but the payload bytes. The `shop-domain` header—which `Registry.process` trusts as the tenant identity passed to the host app's webhook handler—is never included in the signed material. Any actor who can obtain one valid `(raw_body, hmac)` pair for the app (e.g. by triggering a real webhook delivery on their own installed shop) can resend that same payload/signature to the app's endpoint with an arbitrary `shop-domain` header, and the gem will accept it as coming from that other shop.

### Finding Description
`Request#hmac` reads the signature from the `hmac-sha256` header, but `to_signable_string` is hard-coded to `@raw_body` only: [1](#0-0) 

`Request#shop` is read straight from the unauthenticated `shop-domain` header with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., the body only) and compares it with `secure_compare`—correct in isolation, but it never incorporates the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the host application's handler: [4](#0-3) 

Because Shopify's webhook HMAC for a given app is keyed by the single app-wide `client_secret` (shared across every shop that has the app installed, not per-shop), the same secret is used to sign webhooks for every tenant. This means the equality that should hold—**"shop the HMAC-signed bytes were generated for" == "shop attributed to the handler call"**—is broken: the HMAC signs only the body, while the shop identity used for dispatch comes from an independent, unauthenticated header.

An attacker who is simply an ordinary Shopify merchant/developer who has installed the target public app on their own shop can capture a legitimate webhook delivery Shopify sends them (valid body + valid HMAC, signed with the app's shared `client_secret`). They can then replay that exact `(raw_body, hmac)` pair directly to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: request.shop, ...)`—attributing attacker-controlled data to the victim tenant.

### Impact Explanation
This is a cross-tenant identity spoofing vector inside the gem's own webhook-processing pipeline (not a misuse of a documented API by the host app): the host application receives a `WebhookMetadata` object it is told to trust as coming from a specific shop, verified by this gem, when in fact only the payload bytes—not the shop attribution—were verified. Depending on how the host app's handler uses `data.shop` (e.g., to select which tenant's session/access token/order/customer record to mutate), this enables cross-tenant data corruption or disclosure, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any user who can install the target Shopify app on a shop they control (a normal, unprivileged action available to any Shopify merchant/developer) can trigger a real webhook and capture a valid `(raw_body, hmac)` pair, since the HMAC key is the app-level `client_secret` shared across all installs, not a secret unique to the requester. No access token, no leaked credential, and no privileged account is required—only participation as an ordinary installer of the app, which is squarely within the unprivileged-internet-user threat model.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed payload before it is trusted for dispatch. At minimum, `Registry.process` should refuse to trust `request.shop` unless the shop is derivable from data that is itself covered by the HMAC (e.g., validate that `parsed_body`'s own shop-identifying fields, if present, are consistent with the header, or require the host app to cross-check `data.shop` against a shop it already expects for the given webhook subscription/session before acting).

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (ordinary, unprivileged action).
2. Trigger any subscribed webhook event on that shop; capture Shopify's POST request, including the raw body and the `X-Shopify-Hmac-Sha256` header.
3. Resend the identical raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks the body against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188–200) invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: attacker-controlled body, ...)`, causing the host app to act on the attacker's payload under the victim's tenant identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
