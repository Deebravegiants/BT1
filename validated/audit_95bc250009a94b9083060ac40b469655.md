### Title
Tokens transferred directly to the liquidity pool are permanently locked — no recovery path exists - (File: contracts/pool/src/lib.rs)

### Summary
The UXD report describes funds accepted by a contract (payable `receive()`) with no function to recover them. The analog in XOXNO Lending is stronger and structural: the `LiquidityPool` contract accepts ordinary SAC `transfer`s to its address from anyone, but its accounting is a cash book (`state.cash`) that only contract-driven flows mutate. A direct token transfer to the pool raises the token balance without crediting any market's cash book, and no entrypoint — privileged or permissionless — can move the excess. The donated/stranded tokens are locked in the contract forever.

### Finding Description
The pool deliberately separates custody from the cash book: "Cash is an accounting book, separate from the token balance" and "direct donations do not automatically increase booked cash" ( [1](#0-0) , [2](#0-1) ). The money-flow test confirms a raw `token.transfer(payer, pool, 7 * UNIT)` sits outside every market's `cash` ( [3](#0-2) ).

Every outbound path is bounded by the book, not the balance:

- `withdraw` / `borrow` / `claim_revenue` / `seize` debit `cash` or burn booked shares/revenue; `claim_revenue` pays `min(cash, revenue)` ( [4](#0-3) ).
- `recapitalize` credits only the measured delta of its own inbound `transfer_amount_measured`, so a pre-existing surplus is never applied ( [5](#0-4) , [6](#0-5) ).
- `flash_loan` enforces exact balance transitions, so the surplus can never ride out on a flash payout ( [7](#0-6) ).

The complete public surface — `create_market`, `update_params`, `upgrade`, `supply`, `borrow`, `withdraw`, `repay`, `update_indexes`, `recapitalize`, `flash_loan`, `create_strategy`, `seize_positions`, `net_settle`, `claim_revenue`, plus views — contains no sweep/rescue function ( [8](#0-7) ). Unlike the swap-aggregator, which exports `sweep_balance` to recover stray tokens, the pool (and controller, which also holds no sweep for the dust receivers can leave behind) has no equivalent ( [9](#0-8) , [10](#0-9) ). Because all pool mutators are `#[only_owner]` gated to the controller and the controller's entrypoint list exposes no token-forwarding escape, there is no reachable path — even for governance — to release the stranded balance.

### Impact Explanation
Permanent freezing of funds. Any user who mistakenly transfers a listed (or any) token directly to the pool contract address — e.g., intending to supply but bypassing `controller.supply`, exactly the UXD "sent ETH instead of calling `mintWithEth`" scenario — loses the full amount irrevocably. The tokens raise pool custody but belong to no cash book, no supply shares, and no revenue claim; they can never be withdrawn, borrowed against, or swept. For listed tokens the lock also permanently inflates the shared physical balance across all hubs using that token.

### Likelihood Explanation
Reachable by any unprivileged address via a single `token.transfer` to the pool address — an explicitly allowed analog path (direct token transfers to the pool or controller). It requires only user error, not attacker positioning, so occurrence is plausible; conversely the loss is confined to the sender's own mistake, which bounds expected frequency.

### Recommendation
Add an owner-authorized rescue entrypoint on the pool that transfers out only `token.balance(pool) - Σ cash(book)` across all markets on that token, keeping the surplus-vs-booking invariant intact. Alternatively/additionally, document the pool address prominently and warn integrators that direct transfers are unrecoverable. A parallel sweep for stray controller balances would cover callback-dropped dust.

### Proof of Concept
1. Alice holds USDC and calls `usdc.transfer(alice → pool, X)` directly (a plain SAC transfer; no contract approval needed since `to` is the pool).
2. `token.balance(pool)` increases by `X`, but `pool.get_reserves(hub_asset)` (`views::reserves`, the cash book) is unchanged — verified by `test_reserves_returns_accounted_cash_not_token_balance`, where minting 1,000,000 to the pool leaves `reserves` at the booked 50,000,000 ( [11](#0-10) ).
3. Attempt every exit: `supply`/`repay`/`recapitalize` only book measured inbound deltas; `withdraw`/`borrow`/`claim_revenue` can only pay up to booked `cash`; `flash_loan` requires exact balance round-trip. No entrypoint transfers the `X` surplus out.
4. Result: `X` remains at the pool address with no caller able to move it — permanent loss, matching the UXD finding's shape (accepted funds, no recovery function), but for arbitrary tokens rather than native ETH.

Caveat: I confirmed the pool and controller export no sweep via the entrypoint listing and grep of `contracts/{controller,pool,governance}`; governance `timelock/recovery.rs` concerns proposal-lifecycle recovery, not token sweeps, so I did not count it as a rescue path.

impl LiquidityPoolInterface for LiquidityPool {
    /// Creates a new asset market under `hub_id` with the given rate
    /// parameters. Initializes indexes at RAY (1.0) with zero cash, supply,

    }

    /// Replaces the interest-rate model (curve, utilization cap, reserve
    /// factor) and flash-loan settings for a market. Accrues interest first so
    /// the old model applies through the current ledger, then writes the new
    /// model into market params. Restricted to the owner.
    #[only_owner]
    fn update_params(env: Env, hub_asset: HubAssetKey, model: InterestRateModel) {
        ops::market::replace_rate_model(&env, hub_asset, model);
    }

    /// Upgrades the contract WASM to `new_wasm_hash`, extending instance TTL
    /// first. Restricted to the owner.
    #[only_owner]
    fn upgrade(env: Env, new_wasm_hash: BytesN<32>) {
        renew_instance(&env);
        env.deployer()
            .update_current_contract(ContractExecutable::Wasm(new_wasm_hash));

    /// Accrues, mints scaled supply shares and credits cash per entry. The
    /// controller transfers the tokens in before this call. Owner-only.
    #[only_owner]
    fn supply(env: Env, entries: Vec<PoolSupplyEntry>) -> Vec<PoolPositionMutation> {
        ops::run_batch(&env, entries, ops::supply::apply)
    }

    /// Batch-borrows assets and transfers them to `receiver`: accrues
    /// interest, mints scaled debt, debits cash, and enforces max
    /// utilization after each mint. Restricted to the owner; returns one
    /// [`PoolPositionMutation`] per entry.
    #[only_owner]
    fn borrow(
        env: Env,
        receiver: Address,
        entries: Vec<PoolBorrowEntry>,
    ) -> Vec<PoolPositionMutation> {
        ops::run_batch(&env, entries, |env, entry| {
            ops::borrow::apply(env, &receiver, entry)
        })
    }

    /// `is_liquidation` skips the max-utilization check and may withhold a

        receiver: Address,

        }
        indexes
    }

    /// Transfers each token's balance above its reserved fee total to `recipient`. Owner only.
    #[only_owner]
    fn sweep_balance(env: Env, recipient: Address, tokens: Vec<Address>) {
        renew_instance(&env);
        let router = env.current_contract_address();
        let n = tokens.len();
        for i in 0..n {
            // `i < n == tokens.len()`, so the index is in range by construction.
            let token = tokens.get_unchecked(i);
            let client = token::Client::new(&env, &token);
            let balance = client.balance(&router);
            let reserved = storage::reserved_fee_balance(&env, &token);
            if balance > reserved {
                client.transfer(&router, &recipient, &(balance - reserved));
            }
        }
    }
