### Title
Webhook Shop Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (and the library verifies) only the raw request body against the app's shared `client_secret`, while the `shop` identity used by the host application to route/act on the webhook is read from an unauthenticated HTTP header. Because Shopify webhooks for a given app are all signed with the same `api_secret_key` regardless of which shop sent them, an attacker who controls their own installation of the app can replay a genuinely-signed webhook body while substituting an arbitrary victim shop domain in the header, and the gem will report the request as valid.

### Finding Description
`Request#to_signable_string` returns only the raw body, never any header value: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the signed payload: [2](#0-1) 

`Registry.process` verifies the HMAC over the body only, then constructs the trusted `WebhookMetadata` handed to the app's handler using `request.shop`, the unauthenticated header field: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop`: [4](#0-3) 

The identity-binding equality that should hold is:
`HMAC-verified(body, secret) == shop-that-body-belongs-to`

but the actual binding enforced by the code is only:
`HMAC-verified(body, secret) == valid`, with `shop` supplied separately and unauthenticated.

Since Shopify signs webhooks per-app (using the single `client_secret`/`api_secret_key`) and not per-shop, any shop that has installed the app receives genuinely-signed webhook bodies. An attacker who installs the app on their own store (an ordinary, unprivileged action) can capture a real `(raw_body, hmac)` pair, then POST it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body/secret), and `Registry.process` forwards `shop: <victim-domain>` to the host application's handler as if Shopify itself vouched for that shop, achieving cross-tenant confusion at the gem level.

### Impact Explanation
This breaks the tenant/shop identity binding the whole webhook-processing API is meant to guarantee: callers rely on `Utils::HmacValidator.validate` + `Registry.process` to assert "this event authentically originates from `shop`." Because `shop` is not covered by the signature, an attacker can make the library assert a false shop identity for an otherwise-valid signed payload, leading host applications to execute actions, write data, or otherwise treat attacker-supplied content as originating from and pertaining to a victim's tenant — i.e., cross-tenant access facilitated entirely within this gem's verification logic.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the target app on a shop they control (a normal, unprivileged capability for any public/embedded Shopify app) in order to obtain one genuinely HMAC-signed webhook body/signature pair, then replay it with a different `shop` header value against the same endpoint. No access token, `client_secret`, or privileged account is required — the attacker never needs Shopify's own secret because they are reusing a legitimately issued signature.

### Recommendation
Bind the shop identity into the verified signable content, or otherwise force the HMAC validation to be a function of (body, shop) rather than body alone — e.g., include `request.shop` in `to_signable_string`, or require callers to separately confirm that the header `shop` matches an out-of-band trusted value (such as the shop associated with the currently loaded session) before acting on `WebhookMetadata#shop`. At minimum, document prominently that `Request#shop` is not covered by the HMAC and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(B, secret)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body `B` and identical HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes/verifies against `B` — this passes.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and the host application processes attacker-controlled data believed to be authenticated for the victim shop.

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
