Audit Report

## Title
Outbound HTTP response cache key omits WorkflowID, allowing cross-workflow response cache poisoning/leakage - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The gateway's `responseCache` for outbound HTTP actions keys cached responses solely by `req.Hash()`, and `req.Hash()` is documented and tested to exclude `WorkflowID` while including `WorkflowOwner`. This contradicts the handler's own README claim that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage," meaning two distinct workflows owned by the same account can receive each other's cached HTTP responses.

## Finding Description
`Fetch` and `Set` on `responseCache` use `req.Hash()` as the sole cache map key [1](#0-0) [2](#0-1) . The struct's doc comment states the hash covers "method, URL, headers, body, workflowOwner" [3](#0-2) , and `TestRequestHash` confirms `WorkflowID` differences do not change the hash while `WorkflowOwner` differences do [4](#0-3) . The `req` driving the cache key comes from unmarshalling an `OutboundHTTPRequest` from a node's JSON-RPC message in `makeOutgoingRequest` [5](#0-4) . The README explicitly documents the opposite intended guarantee: workflow-ID-scoped isolation [6](#0-5) . No other code path re-namespaces the cache key by `WorkflowID` before calling `Fetch`/`Set`.

## Impact Explanation
Two workflows belonging to the same `WorkflowOwner` that issue outbound HTTP requests with identical method/URL/headers/body and caching enabled will collide on the same cache entry, so one workflow's cached response can be served to, or overwritten by, another workflow's request. This is a concrete cross-workflow response confusion/data-leakage bug within a single owner's workflow set, directly contradicting the documented isolation guarantee, though it is scoped to same-owner workflows rather than cross-tenant/cross-owner leakage since `WorkflowOwner` is still part of the hash.

## Likelihood Explanation
This triggers under ordinary, non-malicious usage: any account operating multiple workflows that call the same external endpoint with the same parameters and caching enabled will experience the collision — no attacker privilege escalation or malicious node behavior is required beyond normal capability usage.

## Recommendation
Add `WorkflowID` to the `OutboundHTTPRequest.Hash()` computation, or explicitly prefix/namespace the `responseCache` key with `WorkflowID` in `Fetch`/`Set` before using `req.Hash()`, matching the documented workflow-scoped isolation.

## Proof of Concept
The existing unit test `TestRequestHash` subtest "having different workflowID results in same Hash" in `response_cache_test.go` (lines 139-149) is itself a reproducible proof: it constructs two requests identical except for `WorkflowID` and asserts their hashes are equal, demonstrating the cache-key collision directly. Extending this to a `responseCache.Fetch`/`Set` integration test (populate cache for `req1` with `WorkflowID="workflow-123"`, then call `Fetch` with `req2` having `WorkflowID="workflow-456"` but otherwise identical fields) would show `req2` receives `req1`'s cached response.
