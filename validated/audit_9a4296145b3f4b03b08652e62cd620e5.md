## Analysis

The bank-tile bug is a memory-safety trust issue: a value taken from an unauthenticated/unvalidated portion of a message (the `bank` pointer and undersized `sz` field) is trusted for a downstream privileged action. The closest structural analog in this Ruby gem's in-scope code (`lib/shopify_api/webhooks/**`) is an identity-binding gap in webhook processing: the `shop` field that the gem hands to application handlers as the tenant identity is never covered by the HMAC signature it itself validates.

### Title
Webhook `shop-domain` header is trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, but delivers the unauthenticated `shop-domain` header as the trusted tenant identifier to the application's webhook handler, allowing an attacker who controls one legitimately-signed webhook payload to relabel it as belonging to a different shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) .

`HmacValidator.validate` computes and compares the HMAC strictly against `verifiable_query.to_signable_string`, i.e., the body bytes only: [3](#0-2) .

`Webhooks::Registry.process` validates the HMAC and then immediately dispatches the handler using the *unverified* `request.shop` as the tenant identity, with no independent check that this shop matches the tenant the signed body actually originated from: [4](#0-3) .

Equality that should hold but doesn't: `shop_bound_by_HMAC == shop_delivered_to_handler`. In reality, `shop_covered_by_HMAC = ∅` (only body bytes are covered) while `shop_delivered_to_handler = request.shop` (attacker-supplied header). Because the app-level `api_secret_key` used to sign webhooks is shared across every shop that installs the app (not a per-shop secret), any shop that has installed the app can obtain a validly-signed `(body, hmac)` pair from Shopify for its own store, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still passes (body unchanged), and `Registry.process` hands the handler `WebhookMetadata` claiming the victim shop as the source: [5](#0-4) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce when it validates webhook authenticity: an unprivileged attacker (any merchant who can install the app on their own store) can make the application believe attacker-controlled webhook content came from an arbitrary other shop. Depending on what the host application does with `WebhookMetadata#shop` (e.g., looking up and mutating shop-scoped state, uninstall handling, order/customer data ingestion keyed by shop), this enables cross-tenant data confusion/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to run their own store with the target app installed (no `api_secret_key`, no stolen token, no TLS interception) — well within "unprivileged internet user" capability, since Shopify signs webhooks with the app's single shared secret across all installs, and the gem never checks that the `shop-domain` header actually matches the tenant the signed bytes came from.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the signed material verified by `HmacValidator`, or require callers of `Webhooks::Registry.process` to independently confirm `request.shop` against a known, previously-established session/shop record before dispatching to handlers.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify.
2. Replay the identical raw body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (body/HMAC pair is valid), and `Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to treat attacker-supplied content as originating from the victim shop.
