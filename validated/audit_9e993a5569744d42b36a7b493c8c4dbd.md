## Finding

### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) headers are trusted for tenant identification but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` by reading them directly from unauthenticated HTTP headers, while `to_signable_string` — the value the HMAC is actually computed and verified over — is defined as only `@raw_body`. `HmacValidator.validate` only proves that the request `body` was produced with the app's `client_secret`; it proves nothing about which shop, topic, or webhook the headers claim to belong to.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

```
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
def shop
  T.cast(shopify_header("shop-domain"), String)
end
def to_signable_string
  @raw_body
end
```

`shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers, but `to_signable_string` — the only thing `HmacValidator` actually authenticates — is the raw body alone: [2](#0-1) 

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, on success, hands the *unauthenticated* `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` straight to the app's handler as `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [4](#0-3) 

**The broken binding:** `hmac_valid(body, secret) == true` is treated as proof of `shop_header == originating_shop`, but the equality that is actually verified is only `hmac_header == HMAC(secret, body)`. The `shop-domain` header is a field that is acted on (passed to the app's webhook handler as the tenant identifier) but is not covered by the HMAC.

Because `client_secret` (the HMAC key) is the same for every shop that installs a given app — it is not a per-shop secret — any merchant who has installed the app can legitimately trigger webhook deliveries to their own store and thereby obtain valid `(raw_body, hmac)` pairs signed with the app's shared secret. That attacker-controlled shop can then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `topic`/`api-version`/`webhook-id`) header with a victim shop's domain. `HmacValidator.validate` will still pass, because it never inspects those headers, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: "<victim-shop>.myshopify.com", ...)`.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as returned by this gem) to select which tenant's records to write, sync, or invalidate — the officially documented purpose of this field per `docs/usage/webhooks.md` — an attacker who is nothing more than a legitimate but malicious app installer on their own store can inject arbitrary attacker-chosen webhook bodies that are processed by the host app under a victim shop's tenant identity. This is a cross-tenant access primitive: data belonging to shop A can be attributed to and acted upon on behalf of shop B purely by header manipulation, without ever compromising shop B's credentials.

### Likelihood Explanation
Any user can sign up for a Shopify Partner account and install the target app on their own development/free store, giving them a legitimate channel to obtain valid `(body, hmac)` pairs signed with the app's shared `client_secret`. From there, forging the `shop-domain` header on a replayed HTTP POST to the app's public webhook endpoint requires no special access — it is a routine HTTP request. This is a completely unprivileged-internet-user path once the attacker has installed the app on any store.

### Recommendation
Do not treat header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) as authenticated. Either:
- Include the shop domain (and other identifying headers) in the value passed to `to_signable_string` so the HMAC covers them (this deviates from Shopify's current webhook signing scheme, which only signs the body), or
- Require host applications to cross-check `WebhookMetadata#shop` against the shop domain the webhook subscription was registered for/known via `webhook_id` lookup rather than trusting the header verbatim, and document this requirement prominently since `HmacValidator` provides no such guarantee.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and an attacker-influenced `raw_body` (e.g. an order they place themselves, so they control the body content).
3. Attacker captures this exact `(raw_body, hmac)` pair and re-sends it to the same app webhook endpoint, replacing only `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(client_secret, raw_body) == hmac_header`: [3](#0-2) 
5. The app's registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` and processes the attacker's payload as if it originated from and belongs to the victim's tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
