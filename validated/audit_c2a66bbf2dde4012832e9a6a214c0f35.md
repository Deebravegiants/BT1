This confirms the design: `Registry.process` explicitly documents that it "will verify the request did indeed come from Shopify" [1](#0-0) , and `data.shop` is documented as "The shop domain of the webhook" — a trusted tenant identifier handed straight to the app's handler [2](#0-1) . However, the HMAC signature computed in `Utils::HmacValidator.validate` is verified only against `Request#to_signable_string`, which returns solely the raw request body, never the shop domain header [3](#0-2) . The `shop` accessor is read directly and unauthenticated from the `x-shopify-shop-domain`/`shopify-shop-domain` header [4](#0-3) , then passed straight into `WebhookMetadata` and the app's handler after only the body-HMAC check passes [5](#0-4) .

### Title
Webhook tenant (shop) attribution is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate` succeeds, and then trusts `request.shop` — taken from the `x-shopify-shop-domain` header — as the tenant identity delivered to the app's handler. But the HMAC only covers the raw body; the shop-domain header is never part of the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC over exactly that signable string and secure-compares it to the `hmac` header [6](#0-5) . The `shop` value is read straight off request headers with no cryptographic binding to the signed payload [4](#0-3) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — before dispatching to the handler with `shop: request.shop` [5](#0-4) . The equality the gem implicitly claims to enforce is:

`verified(hmac) == authenticated(shop, body)`

but what it actually enforces is only:

`verified(hmac) == authenticated(body)`, while `shop` is passed through unauthenticated.

Any party who can obtain one genuine, validly-signed webhook body+HMAC pair for the app (e.g., a merchant who installed the app and receives real webhook deliveries for their own store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. Because the shop header is not covered by the signature, `HmacValidator.validate` still succeeds, and the handler is invoked believing the payload originated from the spoofed shop (a different tenant than the one that actually holds the app's data). Any app logic that uses `data.shop` to scope database writes/reads (as the documentation instructs: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [7](#0-6) ) will attribute that webhook's data to the wrong tenant.

### Impact Explanation
This breaks the tenant isolation boundary the gem is expected to guarantee for webhook processing: the gem markets `process` as verifying "the request did indeed come from Shopify" [1](#0-0) , but a body-only HMAC cannot attest to *which* shop the request is claimed to be for. This enables cross-tenant data confusion/injection without needing the app's `client_secret` — only a single legitimate webhook capture is needed, which any onboarded merchant of the app already receives. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to be an existing, unprivileged merchant/tenant of the app (someone who can install the app and receive at least one real webhook delivery for their own shop) but not a privileged operator and not in possession of the app's `client_secret`. No credential of the target shop is needed at all — only replaying an intercepted, previously-valid body+HMAC pair for a different claimed shop domain.

### Recommendation
Bind the shop identity to the verified request. E.g., derive/verify the shop from the parsed body when the body contains shop-scoped identifiers, or require host applications to cross-check `data.shop` against a shop known to have an active registration/webhook subscription for that specific `webhook_id`/topic before trusting it, and clearly document that `data.shop` is unauthenticated. Ideally, incorporate the shop domain into the signable bytes used for HMAC comparison if any additional binding data is available, or reject/flag mismatches between claimed shop and any shop-identifying data embedded in the body.

### Proof of Concept
1. Attacker installs the app as a legitimate merchant for `attacker-shop.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, then re-sends it to the app's webhook endpoint changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping body `B` and the HMAC header identical.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body without validating shop against anything [8](#0-7) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` never included the shop header [9](#0-8) .
6. The handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` and body `B`, and the app persists/acts on `B` as if it belonged to `victim-shop`.
