### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw HTTP body, while `shop` (from the `X-Shopify-Shop-Domain` header) is trusted and forwarded to the app's handler unauthenticated. Because the `shop` binding is not included in the value the HMAC actually protects, an attacker who possesses one valid `(body, hmac)` pair for their own shop can replay it with a forged `shop` header pointing at a victim tenant, and `ShopifyAPI::Webhooks::Registry.process` will accept it and hand the handler `WebhookMetadata` attributed to the victim shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 
`to_signable_string` returns only `@raw_body`; the `shop` value (line 21-23, sourced purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header at line 46-63) is never mixed into the signed string.

`Registry.process` verifies only this body-only HMAC and then builds the metadata handed to the app's handler directly from the unauthenticated `request.shop`: [2](#0-1) 

`HmacValidator.validate` simply recomputes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac`: [3](#0-2) 

`WebhookMetadata.shop` is a plain `T::Struct` field populated straight from the header: [4](#0-3) 

**The broken binding, stated as an equality that the gem fails to enforce:**
`shop authenticated by the HMAC` (∅, since `to_signable_string` never includes `shop`) ≠ `shop acted upon by the handler` (`request.shop`, taken from an attacker-controllable header).

Because the same app is typically installable on any merchant's store, an attacker can install the app on a shop they control, trigger any webhook topic they've registered, and capture a genuine `(raw_body, hmac)` pair signed with the app's real `api_secret_key`. Since the signature is computed over `raw_body` alone, that exact `(raw_body, hmac)` pair remains valid for *any* value of the `shop-domain` header — the shop identity is completely decoupled from what is cryptographically verified. The attacker then replays the same request to the app's public webhook endpoint with the `shop-domain` header changed to `victim-shop.myshopify.com`. `HmacValidator.validate` passes (it never inspected `shop`), and `Registry.process` invokes the app's `WebhookHandler#handle` with `WebhookMetadata.shop == "victim-shop.myshopify.com"` while `body` is fully attacker-controlled content that was never actually sent by, or associated with, the victim's shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem authenticates the message payload but not its tenant/shop association, then treats the unauthenticated `shop` value as authoritative when constructing the object passed to the host application's webhook handler. Any host app that relies on this gem's HMAC verification as proof the `WebhookMetadata.shop`/`body` pair genuinely originated from that shop (a very natural assumption, since `Registry.process` performs the "security check" internally before invoking the handler) will process attacker-controlled data under a victim's tenant identity — e.g., updating the wrong merchant's order/inventory/customer records, or triggering account/data mutations keyed off `data.shop`. This falls in the cross-tenant access category.

### Likelihood Explanation
Requires only that the attacker be able to install (or otherwise get valid webhooks delivered for) the target app on a shop they control — a normal, unprivileged action for any public Shopify app — and the ability to POST directly to the app's public webhook endpoint with modified headers, which is standard HTTP capability. No access to `api_secret_key`, tokens, or the victim's credentials is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the string that is HMAC-verified, or otherwise cryptographically bind `shop` to the signed payload before trusting it in `WebhookMetadata`. Short of that, `Registry.process` (or the host application, but the gem should not make this trivially bypassable) should cross-check that the `shop` supplied in the request corresponds to a shop actually authorized/known for this specific webhook delivery rather than accepting whatever value arrives in the header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers/receives any webhook topic (e.g., `orders/create`) — Shopify delivers a POST with a legitimate body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical request to the app's public webhook endpoint, unmodified except:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   (body `B` and `H` untouched).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because `shop` was never part of the signed material [5](#0-4) .
4. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` is invoked [2](#0-1) , and the host app processes attacker-controlled data believing it came from the victim's shop.
