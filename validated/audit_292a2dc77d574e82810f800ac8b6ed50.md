This confirms the finding: the OAuth `AuthQuery#to_signable_string` includes `shop`, `host`, `code`, `state`, and `timestamp` in the HMAC-covered payload [1](#0-0) , but `Webhooks::Request#to_signable_string` returns only the raw body, excluding the `shop`, `topic`, `webhook_id`, and `api_version` values that are read straight from HTTP headers [2](#0-1) . `Registry.process` verifies only this body-only HMAC and then dispatches `request.shop` unchecked to the handler [3](#0-2) .

### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values once the body-only HMAC passes, breaking the identity binding `shop authenticated == shop used by the handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively [4](#0-3) . `Utils::HmacValidator.validate` computes the HMAC over that signable string with the app's `client_secret` and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header via `OpenSSL.secure_compare` [5](#0-4) . Crucially, the `shop`, `topic`, `webhook_id`, and `api_version` accessors all read from separate, unsigned headers (`shopify-shop-domain`, `shopify-topic`, etc.) [6](#0-5) , and none of these values feed into `to_signable_string`.

`Registry.process` validates only the body-bound HMAC, then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, passing them unchecked to the registered handler [3](#0-2) .

This is the same bug class as the report: the equality that should hold is `shop authenticated by HMAC == shop delivered to handler`, but the gem instead checks `body authenticated by HMAC` while `shop delivered to handler` is taken from an out-of-band, unauthenticated header — precisely the "shop authenticated versus the shop stored/used" binding break called out in scope.

Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly includes `shop` (and `host`, `code`, `state`, `timestamp`) inside the HMAC-covered string [1](#0-0) , so the OAuth callback path does correctly bind shop identity to the signature. The webhook path does not follow the same pattern, despite implementing the same `Utils::VerifiableQuery` interface [7](#0-6) .

An attacker who controls their own Shopify store (an unprivileged tenant relative to any other merchant using the app) receives legitimate webhook deliveries for their own shop, each with a valid `(raw_body, hmac)` pair signed by the app's `client_secret`. Because the HMAC never covers the `shopify-shop-domain` header, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shopify-shop-domain` header (and, independently, an arbitrary `shopify-topic`/`shopify-webhook-id`, since those are also unsigned). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` forwards the attacker-chosen `shop`/`topic` straight to the handler as if Shopify itself vouched for that shop/topic combination.

### Impact Explanation
This crosses a tenant boundary the gem is supposed to enforce cryptographically: the handler is invoked with `WebhookMetadata.shop`/`topic` values that were never actually authenticated by Shopify for that shop or that topic, only the body bytes were. Depending on how the host app's handler uses `data.shop` (e.g., to look up a stored session, to key writes into a per-tenant data store, or to act on mandatory-compliance topics like `customers/redact` or `shop/redact`), an attacker can inject or misattribute events into a shop namespace they do not control — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on their own store (readily achievable for any public app) to obtain one valid `(body, hmac)` pair, then replay it with a modified `shop-domain`/`topic` header to the app's public webhook endpoint. No access to the app's `client_secret`, access tokens, or any victim credential is required.

### Recommendation
Bind the `shop`, `topic`, `webhook_id`, and `api_version` header values into the HMAC-signed material (e.g., include them in `to_signable_string` alongside the body, matching the pattern used by `AuthQuery`), or otherwise cryptographically tie the header claims to the verified body before constructing `WebhookMetadata`.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app,
# so Shopify delivers them a legitimate webhook with a valid HMAC over the body.
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
)

# Attacker replays the same (body, hmac) pair but swaps the shop header
# to point at a victim shop they do not control.
spoofed_headers = {
  "shopify-topic" => "customers/redact", # also unsigned, can be changed freely
  "shopify-hmac-sha256" => valid_hmac,
  "shopify-shop-domain" => "victim-shop.myshopify.com",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body+hmac match),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "customers/redact", ...))
#    executes as if Shopify authenticated this event for victim-shop.
```
