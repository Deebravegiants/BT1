### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-spoofing on replayed webhooks - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for a webhook from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` field is never included in the signed material, so the binding "HMAC-verified bytes == data trusted as authoritative for this shop" does not hold for the `shop` attribute.

### Finding Description
`Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` succeeds, then immediately hands the handler a `WebhookMetadata` built from `request.shop`, `request.topic`, and `request.parsed_body`: [1](#0-0) 

`Request#hmac` and `Request#to_signable_string` show that only the raw body bytes are part of the signable string used to compute/verify the HMAC: [2](#0-1) 

`Request#shop` reads directly from the `shopify-shop-domain` header, which is not part of `to_signable_string`: [3](#0-2) [4](#0-3) 

`HmacValidator.validate`/`validate_signature` computes and compares the HMAC purely against `verifiable_query.to_signable_string` (the body), never incorporating the shop header: [5](#0-4) 

The identity binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` implies `shop == the shop the payload actually originated from`. Because `signed_bytes` excludes the `shop-domain` header, this equality is false — the header is a field acted on (used to construct `WebhookMetadata.shop`, which host apps use to select tenant context, credentials, or database records) but not covered by the HMAC.

An unprivileged internet user who captures/observes one legitimately-signed webhook delivery for a body value `B` (webhook endpoints are internet-facing and their bodies are not always confidential, e.g. `orders/create` payloads containing only order data, or a topic with a fixed/predictable body) can replay the exact same body+HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` (it only checks the body against the secret), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, body: <original body>, ...)`. If the host application uses `data.shop` to decide which merchant's session/store the `data.body` belongs to (which is the documented, expected use of this field per `WebhookHandler#handle`), this allows cross-tenant data injection/confusion: data intended for shop A is attributed to shop B.

### Impact Explanation
This breaks the tenant/shop identity binding for webhook processing, enabling cross-tenant data injection: an app trusts `WebhookMetadata.shop` as the authenticated identity of the payload origin, but that field is attacker-controllable independent of the HMAC. This matches the "Critical - cross-tenant access" category, since it lets one tenant's data be attributed to and processed under another tenant's identity within the app.

### Likelihood Explanation
Medium. The attacker does not need `api_secret_key` — they only need to have observed/captured one valid `(body, hmac)` pair for any topic (webhook payloads are delivered over plain HTTPS to the app's public endpoint, and topics like product/collection updates can carry no shop-specific secret data), then replay it with a modified `shop-domain` header. No credentials are required to perform the replay itself, only knowledge of a prior valid signed body, which is a realistic bar to clear for many webhook topics with non-sensitive or predictable payload content.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC signable string, or otherwise cryptographically bind the shop domain to the payload before validation, so that `to_signable_string` reflects all fields the application will subsequently trust as authenticated. At minimum, document that `WebhookMetadata.shop` is not integrity-protected by the HMAC and must not be trusted for tenant selection without additional verification (e.g., cross-checking against a known/registered shop for that webhook subscription).

### Proof of Concept
1. Attacker registers/observes (or otherwise obtains) a valid webhook delivery for topic `T` with raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a POST request to the app's webhook endpoint with the same body `B` and the same `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a shop different from the one that actually triggered the original webhook).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — validation succeeds because the shop header is not part of `to_signable_string`. [6](#0-5) 
4. The handler executes `handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...))`, so the host application processes body `B` (originally belonging to a different shop) as if it belonged to `victim-shop.myshopify.com`. [7](#0-6)
