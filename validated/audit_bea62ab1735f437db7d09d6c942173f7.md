### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body-derived HMAC and then unconditionally trusts the header-derived `shop` value when dispatching to the handler, breaking the binding between "HMAC-verified sender" and "shop the payload is attributed to."

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only, and `#hmac` decodes the `hmac-sha256`/`x-shopify-hmac-sha256` header value: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers via `shopify_header`, none of which are part of `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` only checks that `compute_signature(verifiable_query.to_signable_string, secret)` matches the `hmac` header — i.e., it only proves the *body* bytes were signed by the app's shared secret, not that the `shop-domain` header is authentic: [3](#0-2) 

`Registry.process` validates this HMAC and then passes `request.shop` straight into `WebhookMetadata` for the handler, with no additional binding check between the verified body and the claimed shop: [4](#0-3) 

Because the shared HMAC secret (`Context.api_secret_key`) is identical for every shop that installs the app, any merchant who has legitimately installed the app can capture a validly-signed webhook for their own store (attacker-controlled tenant) and replay the exact same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds (the body bytes and HMAC are unchanged and genuinely signed), but `Registry.process` now attributes the payload to the victim's tenant. This is the analog of the reported "field acted on but not covered by the signature" bug class: the binding `shop_authenticated_by_hmac == shop_used_for_tenant_dispatch` is broken because `shop` is never part of the signed material.

### Impact Explanation
This crosses a tenant boundary: an attacker who controls one legitimate shop installation can cause the host application to process/store webhook data under a different shop's identity, since `Registry.process` uses the unauthenticated `shop` header for dispatch. Depending on how the host app's handler keys sessions/data by `data.shop` (the intended and documented use, per `WebhookMetadata`), this can lead to cross-tenant data injection or corruption — data or state changes attributed to a shop that never sent them.

### Likelihood Explanation
Exploitation requires no privileged credentials beyond installing the app on the attacker's own store (an ordinary, unprivileged action available to any merchant), then replaying a captured webhook body with a forged `shop-domain` header to the app's public webhook endpoint. The HMAC check as implemented in this gem cannot detect this because it never covers the header.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`/`api_version`) in the material verified by the HMAC, or otherwise cryptographically bind the shop domain to the payload before dispatch (e.g., cross-check `request.shop` against an already-authenticated session/shop record rather than trusting the header in isolation). At minimum, document that `request.shop` from `Webhooks::Request` is not covered by HMAC verification and must not be trusted for tenant attribution without an independent check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256: H` header, both computed by Shopify using the app's shared secret.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`/`x-shopify-webhook-id` as desired
3. `Webhooks::Request.new` parses these headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `compute_signature(B, secret) == H`. [5](#0-4) [6](#0-5) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes `B`'s contents as if they originated from the victim shop, despite the payload actually being the attacker's own data.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
