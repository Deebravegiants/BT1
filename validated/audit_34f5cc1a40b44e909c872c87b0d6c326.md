### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by HMAC-checking only the raw request body, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers when dispatching to the host app's handler. Any actor who can obtain one genuine, validly-signed webhook body (e.g., by installing the app on their own store — a self-service action requiring no special privilege) can replay that same body with forged `shop-domain`/`topic`/`webhook-id` headers, since none of these fields are part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers, entirely outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (the body) against the HMAC: [3](#0-2) 

`Registry.process` performs this single HMAC check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the app's handler, with no cross-check that these header values are consistent with what the HMAC actually authenticates: [4](#0-3) 

This is the direct structural analog of the reported bug class: the report describes a component that verifies one piece of state (the "locked" harvested amount) while silently letting an adjacent, causally-linked value (the pending yield) go unchecked, breaking the invariant that the checked quantity represents the whole picture. Here, the binding that should hold is:

`shop header used by the handler == shop that produced the HMAC-signed body`

Because Shopify signs webhooks per-app (all shops share the same `client_secret`/HMAC key for webhook signing), a body+HMAC pair valid for the attacker's own shop is *also* a valid HMAC for the exact same body when paired with a different `shop-domain` header — the check never binds the two together. An attacker who has installed the app on their own store (self-service, no special access token or leaked credential needed) can:
1. Trigger a real event on their own shop, capturing a legitimately-signed webhook body + HMAC.
2. Replay that request to the app's webhook endpoint, substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim merchant's shop domain.
3. `Registry.process` accepts it (HMAC on the body matches) and calls the handler with `WebhookMetadata.shop` set to the victim's domain, causing the host app to act on/against the wrong tenant's data using attacker-controlled body content.

### Impact Explanation
This breaks the tenant isolation the gem is documented to provide: `docs/usage/webhooks.md` instructs developers to construct `Request` from raw headers/body and trust `Registry.process` to "verify the request did indeed come from Shopify" before dispatching to per-shop logic, implying the `shop` field is part of that verified identity. Since it is not, cross-tenant access is possible — an app that keys any subsequent action (order sync, data deletion, inventory update, GDPR webhook side effects, etc.) off `WebhookMetadata#shop` can be tricked into applying attacker-supplied body data to a different merchant's tenant, which qualifies as cross-tenant access under the stated Critical impact criteria.

### Likelihood Explanation
Requires only the ability to install the target app on any shop (a normal, unprivileged, self-service action for any Shopify app listed publicly or in dev mode) and the ability to POST arbitrary headers to the app's public webhook endpoint — no access token, `client_secret`, or leaked credential is needed. This makes the likelihood realistic for any app relying solely on `ShopifyAPI::Webhooks::Registry.process`/`Request` for both authenticity and shop identification, which is exactly the pattern the gem's own documentation recommends.

### Recommendation
Bind the shop identity to the signed content: either (a) include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (not possible unilaterally since Shopify controls the signature format), or (b) cross-validate `request.shop` against an independently-trusted source (e.g., require the caller to look up/verify the shop has an active webhook registration/session for the `webhook_id`, or validate the shop domain against the session store before invoking the handler) rather than passing header-derived `shop` straight into `WebhookMetadata`. At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are **not** cryptographically authenticated and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app registers for (e.g. `orders/create`).
2. Capture the raw POST: body `B`, and header `x-shopify-hmac-sha256` = HMAC-SHA256(`client_secret`, `B`) — valid because the app's `client_secret` is shared across all installs.
3. Replay the identical body `B` and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com` (and `x-shopify-webhook-id`/`x-shopify-topic` if desired).
4. `HmacValidator.validate` succeeds (only `B` is checked): [5](#0-4)  
5. `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "victim.myshopify.com"` and attacker-controlled `body`, even though the HMAC never attested to that shop: [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
