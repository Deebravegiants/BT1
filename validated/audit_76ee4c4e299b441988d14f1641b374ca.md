### Title
`_sweepDust` in `IntentsBase.sol` can sweep tokens still escrowed for un-finalized orders, causing legitimate `withdraw()` calls (fill/refund/cancel) to fail from insufficient contract balance - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
This is analogous to the reported bug class: a legitimate protocol-level accounting mismatch between a "recorded entitlement" (the Ubiquity `redeemCollateralBalances` / here the `_orders[commitment][token]` escrow ledger) and the contract's actual spendable token balance (which the Ubiquity AMO could borrow against; here it can be reduced by the governance-triggered `SweepDust` action) can leave a legitimate claimant (`_withdraw`) unable to collect funds they are entitled to.

### Finding Description
`IntentsBase._withdraw` decrements the `_orders[commitment][token]` mapping and transfers `amount` of `token` out of the contract on fill, cancel, or refund [1](#0-0) . The dust-sweep event documentation states dust is "accumulated protocol dust" swept via a Hyperbridge-governance `SweepDust` message, transferring `SweepDust.outputs[i].amount` of a given token directly to a beneficiary [2](#0-1) . Crucially, the `SweepDust` handler (and its Tron equivalent) sweeps by an admin/governance-supplied `amount` field rather than by a separately tracked "known dust" balance that excludes tokens still reserved in `_orders`: [3](#0-2) 

There is no on-chain invariant tying the `SweepDust` amount to `IERC20(token).balanceOf(address(this)) - sum(_orders[*][token])`; the check is only done off-chain/at governance-message-construction time. If the token's total contract balance temporarily includes both real dust and escrowed order funds (which is unavoidable since `_orders` is a per-order accounting ledger over a shared pooled token balance, not a segregated vault per order), a `SweepDust` request that computes "dust" incorrectly (or that races with orders being placed after the amount was computed) can drain balance below what `_orders` requires for outstanding fills/cancellations/refunds. The subsequent user- or solver-initiated `_withdraw()` call (`fillOrder`, `cancelOrder` same-chain, or the cross-chain `RedeemEscrow`/`RefundEscrow` `onAccept` path) then reverts on `IERC20.safeTransfer` due to insufficient balance, even though `_orders[commitment][token]` still shows the user/solver as entitled to the funds — mirroring the Ubiquity `collectRedemption` failure where `redeemCollateralBalances` still records the user's entitlement but the AMO has already moved the backing collateral out.

### Impact Explanation
A user or solver with a legitimately recorded escrow claim (order fill claim, refund, or cancellation) can have their `_withdraw()` transaction revert because the pooled token balance was reduced by an unrelated `SweepDust` governance action that did not fully account for concurrently-escrowed order balances. This is a fund-availability/DoS-style freezing issue on withdrawal rather than an unbacked mint, but it directly parallels the reported bug class ("normal privileged/authorized action drains a shared pool that user withdrawals depend on, causing withdrawal calls to fail").

### Likelihood Explanation
Likelihood is Medium: it requires the `SweepDust` accounting (computed by governance/relayer tooling off-chain) to overestimate the truly-idle dust balance relative to concurrently placed/active orders in the same token, which is plausible given `_orders` is a shared, non-segregated ledger over the gateway's pooled ERC20 balances and new orders can be placed between the time dust is measured and the sweep request is delivered (cross-chain governance messages have delivery latency).

### Recommendation
Track "protocol dust" as an explicit incrementing/decrementing on-chain accumulator (as is partially done via `DustCollected` events) rather than allowing `SweepDust.outputs[i].amount` to be an arbitrary governance-supplied value, and enforce `amount <= trackedDust[token]` (analogous to bounding AMO borrows by `unclaimedPoolCollateral`) so a sweep can never dip into balances currently reserved by `_orders`.

### Proof of Concept
1. User places an order escrowing 1000 USDC; `_orders[commitment][USDC] = 1000e6`. Contract's USDC balance is 1000e6 (assume no other dust yet).
2. Some genuine dust (e.g., 50 USDC) accumulates from a separate order's overpayment; contract balance is now 1050e6, with 1000e6 owed to order 1.
3. Governance computes and dispatches a `SweepDust` message for 1050e6 USDC (miscalculating dust as the entire contract balance, or the message being stale by the time it's delivered because a new order was placed in the interim, e.g., order 2 escrows another 500 USDC, making the true balance 1550e6 but the in-flight `SweepDust` message still requests 1050e6, i.e. more than actual free dust).
4. `SweepDust` executes via `onAccept`, transferring 1050e6 to the beneficiary, leaving only 500e6 in the contract while `_orders` still records 1000e6 (order1) + 500e6 (order2) = 1500e6 owed.
5. Order 1's user calls `cancelOrder`/fill settlement triggers `_withdraw`, which attempts `IERC20(token).safeTransfer(beneficiary, 1000e6)` against a contract balance of only 500e6 — the transfer reverts and the legitimate withdrawal fails, exactly mirroring the `collectRedemption` failure in the original report.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
