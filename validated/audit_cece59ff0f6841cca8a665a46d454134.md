### Title
Arbitrary route contracts can execute unauthorized token transfers under the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
High severity: an unprivileged caller-controlled `swap` payload can place attacker-deployed contract code on the call stack beneath a victim’s `swap_collateral` authorization, allowing that code to request additional `transfer` authorization from the victim’s wallet. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` accepts `swap` as opaque `Bytes` and forwards it to the configured router through `execute_strategy`. [3](#0-2) [4](#0-3)  The controller protects only its own input transfer by authorizing one exact controller-to-router transfer and checking measured balances afterward. [5](#0-4)  Those checks do not constrain contracts selected inside the route: the router invokes payload-named pool and token addresses without an allowlist. [6](#0-5)  A malicious route contract can therefore call `token.transfer(victim, attacker, amount)`, causing Soroban simulation to record that transfer as a child invocation under the victim’s signed `swap_collateral` root. [7](#0-6) [8](#0-7)  If the victim signs the simulated authorization tree, the unrelated wallet-token transfer executes while the swap still returns a valid output. [9](#0-8) 

### Impact Explanation
The route can steal token balances unrelated to the supplied collateral and unbounded by `amount`, router output, or final account risk checks. [10](#0-9)  The regression test demonstrates loss of the victim’s full unrelated wallet balance while the attacker receives it and the victim still receives fair swap output. [11](#0-10)  Other user-controlled swap paths such as `swap_debt`, `repay_debt_with_collateral`, and `multiply` expose the same opaque route execution pattern. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
An attacker can deploy the malicious venue and supply a route through it; no privileged role, leaked key, compromised router implementation, or protocol parameter is required. [14](#0-13)  Execution requires the account owner or delegate to submit and sign the malicious strategy transaction, including the child authorization disclosed by simulation. [15](#0-14) [16](#0-15)  That makes the attack dependent on route construction or client-signing behavior rather than an always-available unilateral theft, but successful exploitation directly steals user funds.

### Recommendation
Do not allow opaque route bytes to select arbitrary executable venues beneath the caller’s authorization. [4](#0-3)  Restrict router execution to governance-allowlisted venue implementations or validated program templates, and make the router enforce the allowlist rather than trusting payload-supplied pool addresses. [17](#0-16)  Add a regression check that a signed honest `swap_collateral` authorization tree contains no child invocations, and reject route encodings or router configurations that can introduce additional `require_auth` children. [18](#0-17) 

### Proof of Concept
1. Deploy a route-selected contract whose `swap` function executes `token.transfer(victim, attacker, WALLET_BALANCE)`. [19](#0-18) 
2. Build a `swap` payload naming that contract as a hop while paying fair output. [14](#0-13) 
3. Have the victim invoke `swap_collateral(victim, victim_account_id, USDC, amount, ETH, swap)`. [20](#0-19) 
4. Simulation records the malicious wallet transfer as a child of the victim’s `swap_collateral` authorization. [8](#0-7) 
5. Signing that tree makes the transaction succeed, empties the victim’s wallet-token balance, credits the attacker, and still deposits the expected swap output. [9](#0-8)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    s.t.env.mock_all_auths();
    s.try_swap(&route)

    let recorded = s.t.env.auths();

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),

            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

        function: AuthorizedFunction::Contract((

    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
