## Title
Webhook HMAC only signs the raw body, not the `shop`/`topic` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The shop identity (`x-shopify-shop-domain`), topic (`x-shopify-topic`), and webhook id (`x-shopify-webhook-id`) headers that the handler uses to attribute the payload to a tenant are never included in the HMAC-signed material. This breaks the equality that should hold: `hmac_signed_bytes == bytes_the_handler_trusts_for_shop/topic_identity`.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against that signable string: [2](#0-1) 

Yet `Registry.process` dispatches the webhook using the unauthenticated `shop`, `topic`, and `webhook_id` header accessors after only checking the body-only HMAC: [3](#0-2) 

Those accessors read straight from attacker-controllable HTTP headers with no cryptographic binding to the shop/topic: [4](#0-3) 

Because every shop installed under the same app shares the same `client_secret`, an attacker who legitimately installs the app on their own shop will receive genuinely-signed webhooks (HMAC over body only) for events they can trigger themselves (e.g., creating an order with attacker-chosen field values as the JSON body). The attacker can capture a `(body, hmac)` pair from their own tenant, then replay that exact body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain and `x-shopify-topic`/`x-shopify-webhook-id` with any value they choose. `Registry.process` will accept it as valid (HMAC matches) and hand the handler a `WebhookMetadata` claiming the victim shop and an arbitrary topic: [5](#0-4) 

This is the same bug class as the analog report: an identity-critical field (here, `shop`/`topic`, analogous to `proposalId`) is acted upon downstream without being covered by the integrity check (analogous to the un-hashed `proposalId` not binding the confirmation to the correct proposal).

### Impact Explanation
Any app built on this gem that uses `data.shop` from `Registry.process`'s `WebhookMetadata` to select which tenant's data to create/update/delete (a standard and documented usage pattern) can be made to process forged, cross-tenant webhook events. This crosses a tenant boundary using only the attacker's own legitimate but unprivileged access to the app (their own shop installation), qualifying as Critical - cross-tenant access.

### Likelihood Explanation
Likelihood is moderate to high: exploitation only requires the attacker to install the app on a shop they control (an ordinary unprivileged action), trigger an event that produces a webhook with attacker-influenced body content, capture the resulting `(body, hmac)` pair from their own endpoint, and replay it against the target app's webhook endpoint with spoofed headers. No access to `client_secret`, access tokens, or victim credentials is required.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material in `Request#to_signable_string`, or otherwise cryptographically bind them (e.g., derive/verify shop and topic from a value covered by the signature) before `Registry.process` dispatches to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event (e.g. creates an order) causing Shopify to send a legitimately HMAC-signed webhook to the app's endpoint, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)` per `Request#to_signable_string`/`HmacValidator`).
3. Attacker captures `(B, H)` from their own endpoint logs.
4. Attacker sends a new HTTP request to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
5. `HmacValidator.validate` passes (only `B` and `H` matter); `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: B, ...)`, causing the app to act on forged data attributed to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
