### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain residual token allowances and dust left by prior orders' predispatch/postdispatch calldata - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` has no access control and is shared by every `IntentGatewayV2`/`IntentsBase` order (predispatch/postdispatch calldata) and every `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-bridge. Any order's `Call[]` can (and, per the audit-class hint, typically does) `approve()` a swap target/router for an amount rather than resetting it to zero afterward. Because `dispatch()` is `external` with no caller restriction, any unrelated third party can call it directly at any time to either (a) exploit a lingering ERC20 allowance still held by an old, approved spender against the shared `CallDispatcher`, or (b) sweep any token/ETH dust that was left in the dispatcher outside the tracked escrow-asset list.

### Finding Description
`CallDispatcher` is a single, protocol-wide shared contract: [1](#0-0) 

It executes an arbitrary `Call[]` supplied in `data`/`predispatch.call`/`output.call` with no `onlyGateway`/`onlyHost` guard, meaning literally anyone can call `dispatch()` directly: [2](#0-1) 

`IntentGatewayV2.placeOrder` and `IntentsBase._execute` route user/solver-supplied swap calldata (which routinely includes an `approve()` to a router before the swap, exactly matching the reported bug class) through this shared dispatcher, then sweep back only the tokens that are part of `order.inputs`/`order.output.assets`: [3](#0-2) [4](#0-3) 

The project's own documentation acknowledges the approval-leftover risk described in the report ("Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution"), but this is only advisory guidance for order/message authors — it is not enforced anywhere on-chain: [5](#0-4) 

Because `CallDispatcher` is reused across every order/message from every user, and its `dispatch` entrypoint is unrestricted, the residual-allowance problem from the external report is amplified: an approval granted by *any* order's swap calldata (e.g. `approve(router, type(uint256).max)`, as used in the repo's own test) remains live on the token contract against the `CallDispatcher` address indefinitely if not fully consumed: [6](#0-5) 

Any token/ETH dust that is not part of the tracked escrow asset list for that specific order (e.g., a reward token claimed mid-swap, a router refund, or leftover balance of a token not enumerated in `order.output.assets`) is never swept, and stays sitting in `CallDispatcher`. Since `dispatch()` has no access control, any external party can subsequently call `CallDispatcher.dispatch()` directly with a `Call{to: token, data: transferFrom(dispatcher, attacker, amount)}` (exploiting a stale allowance) or `Call{to: attacker, value: ethDust}` (sweeping stray ETH) to steal it.

### Impact Explanation
This allows outright theft of funds sitting in the shared `CallDispatcher`: any lingering ERC20 allowance from a swap-approval left over-approved by a prior order, or any un-swept token/ETH dust from prior predispatch/postdispatch/HFT calldata execution, can be drained by an arbitrary unprivileged caller. This is a concrete theft-of-funds vector reachable by any address with no special privileges, satisfying "Medium" severity at minimum since it directly enables loss of protocol/user funds sitting transiently in a core dispatch component reused by `IntentGatewayV2`, `IntentsBase`, `HyperFungibleToken` and `WrappedHyperFungibleToken`.

### Likelihood Explanation
Likelihood is realistic: `Call[]` payloads that approve a router before swapping are the documented, expected usage pattern (shown in the project's own docs and tests using `type(uint256).max` approvals), and the sweep logic only recovers tokens that are explicitly enumerated as order inputs/outputs — any unexpected token or unconsumed allowance is left behind. Since `dispatch()` is a public, unauthenticated entrypoint, exploitation requires no special positioning — just monitoring the shared `CallDispatcher`'s token allowances/balances and calling `dispatch()` (or directly calling the token's `transferFrom`) to claim them.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to authorized callers only (e.g., the registered `IntentGatewayV2`/`IntentsBase` and HFT/WrappedHFT contracts), or deploy a dedicated, single-use dispatcher/proxy per order instead of a shared singleton.
- After executing the `Call[]`, explicitly zero out any allowances the calls granted to third-party spenders (`approve(spender, 0)`), not just sweep tracked balances.
- Sweep *all* token balances the dispatcher could plausibly hold as a result of executing the calls (not only the tokens enumerated in `order.inputs`/`order.output.assets`), or restrict allowed `Call[]` targets/selectors to prevent unaccounted token drift.

### Proof of Concept
1. A user/solver submits an order whose `predispatch.call` or `output.call` includes `approve(ROUTER, type(uint256).max)` followed by a swap that only consumes part of the approved amount (as in `testPostdispatchTokenSweep`, which explicitly approves `type(uint256).max`). [7](#0-6) 
2. `IntentGatewayV2`/`IntentsBase` sweeps only the balance of the tracked input/output tokens back to the gateway, leaving the now-stale `approve(ROUTER, remaining)` allowance intact on the token contract against `CallDispatcher`.
3. If `ROUTER` (or any other address that was ever granted an allowance by any prior order's calldata) later becomes attacker-controlled, or if any token/ETH dust outside the tracked asset list is left in `CallDispatcher`, an attacker calls `CallDispatcher.dispatch()` directly (no access control) with a `Call` that either exploits the outstanding allowance via `transferFrom` or transfers out the ETH/token dust, stealing the funds.     function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
