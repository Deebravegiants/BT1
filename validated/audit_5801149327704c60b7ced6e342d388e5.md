### Title
Webhook `shop-domain` and `topic` headers are trusted for merchant/tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and label the payload are pulled unauthenticated from HTTP headers.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers, which are outside the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC, then dispatches based on the unauthenticated `topic` header and hands the unauthenticated `shop` header straight to the app's handler as the tenant identifier: [3](#0-2) 

The binding this breaks is: `hmac == HMAC(api_secret_key, signable_content)` should imply `signable_content` (including the shop and topic it is attributed to) is authentic, but `signable_content` here is only `raw_body`. So the equality that's actually enforced is `hmac == HMAC(api_secret_key, raw_body)`, while the code *acts on* `shop`/`topic` as if `hmac == HMAC(api_secret_key, raw_body + shop + topic)` held.

Because `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (it is not per-shop), any body an attacker can get legitimately signed for one shop (e.g. by triggering a webhook event on their own store, or from a body whose exact bytes are guessable/constant, such as `{}` for `app/uninstalled` or similar minimal payloads) can be replayed directly to the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop and/or a forged `x-shopify-topic` header. The `HmacValidator.validate` check still passes because it only checks the body bytes, and the app then treats the request as authentic data for the victim's shop.

### Impact Explanation
This crosses a tenant boundary: `WebhookMetadata#shop` handed to the app-defined handler is not proven to correspond to the shop that actually generated the signed payload. An app that uses `data.shop` to select which merchant's DB row to modify (a documented, intended usage pattern per `docs/usage/webhooks.md`) can be induced to apply another merchant's webhook body to a victim shop's record, or to process a body under the wrong `topic` (e.g., attacker submits a body captured from a benign topic but tags it as `shop/redact` or `customers/data_request` to trigger sensitive handler logic for an arbitrary shop). This matches the Critical "cross-tenant access" impact category, since the identity binding between the cryptographic proof and the acted-upon `shop`/`topic` fields is absent.

### Likelihood Explanation
Exploitation requires: (1) obtaining at least one validly-signed webhook body (achievable by installing the app on an attacker-owned test shop and triggering any webhook, since HMAC only signs bytes of body content, not shop identity), and (2) POSTing that raw body directly to the app's public webhook endpoint with forged shop/topic headers, since nothing in this gem ties the header values to the HMAC. No access token, `api_secret_key`, or privileged access is needed beyond running a normal shop that has installed the target app — a capability any unprivileged internet user/merchant can obtain by installing a public app.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind them (e.g., include them in `to_signable_string`, or independently verify `shop` against an actively installed/known session for the app before dispatching). At minimum, document and/or enforce that consumers must not treat `data.shop`/`data.topic` as authenticated without additional binding, and consider validating the `shop` domain via `Utils::ShopValidator` combined with a lookup against a known/installed session before invoking handlers.

### Proof of Concept
```ruby
# Attacker installs the target app on their own store "attacker.myshopify.com"
# and triggers a webhook whose body happens to be empty/predictable, e.g. "{}"
# Because HmacValidator only signs raw_body, this signature is valid for ANY
# shop/topic combination sharing the same api_secret_key:

hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  app_api_secret_key,   # single secret shared by all shops on the app
  "{}"
)

forged_headers = {
  "x-shopify-topic"       => "customers/redact",       # forged: arbitrary topic
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),     # still valid: only body is signed
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged: arbitrary tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body-only check passes)
# => handler.handle(data: WebhookMetadata.new(topic: "customers/redact",
#      shop: "victim-shop.myshopify.com", body: {}, ...))
# The app's handler now acts on data attributed to "victim-shop.myshopify.com"
# even though that shop never sent this webhook.
``` [3](#0-2) [4](#0-3)

          unless handler
