### Title
Pod-bound SA token accepts unverified Node claim, allowing SA-to-node identity confusion enabling `system:node:*` impersonation - ([File: pkg/serviceaccount/claims.go])

### Summary
When a token is bound to a Pod and `features.ServiceAccountTokenPodNodeInfo` is enabled, `(v *validator) Validate` blindly trusts the `Node` ref embedded in the token's private claims for pod-bound tokens without re-verifying that the referenced pod is actually (still) scheduled on that node. This `NodeName`/`NodeUID` value flows into `ServiceAccountInfo.NodeName`/`NodeUID` and is exposed as `user.Extra[serviceaccount.NodeNameKey]`, which is subsequently used by `associatedNodeImpersonationMode` to authorize a service account to impersonate `system:node:<name>`.

### Finding Description
In `pkg/serviceaccount/claims.go`, for the pod-bound-token branch: [1](#0-0) 
the code takes `noderef` straight from the private claims with no call to `v.getter.GetPod`/`GetNode` re-validation of the *current* pod-to-node relationship (unlike the pure Node-bound branch a few lines below, which does call `v.getter.GetNode` and check UID/deletion). The `Pod` ref itself is checked against the live pod object (name/UID/deletion) at lines 232-250, but the `Node` ref accompanying it is never cross-checked against `pod.Spec.NodeName`.

The Node value is originally populated at token-mint time in `pkg/registry/core/serviceaccount/storage/token.go`, by reading `pod.Spec.NodeName` and looking up that Node object: [2](#0-1) 
An ordinary namespaced user with only `create pods`/`create serviceaccounts/token` permission can set `pod.Spec.NodeName` directly at pod-create time (this is standard, unprivileged "manual scheduling" — no special RBAC verb beyond `create pods` is required). This lets the attacker embed an **arbitrary existing Node's identity** into their own pod-bound SA token, regardless of whether that node's kubelet ever actually admits/runs the pod.

Because `Validate` never re-derives or cross-checks `noderef` against the pod's real `Spec.NodeName` (it only checks Pod UID/deletion, not the Node linkage), the resulting `ServiceAccountInfo.NodeName`/`NodeUID` is returned as trustworthy, and downstream consumers treat it as an authoritative binding between the SA and that node. The most notable consumer is `requesterAssociatedWithRequestedNodeUsername`/`associatedNodeImpersonationMode`: [3](#0-2) [4](#0-3) 
which grants a service account permission to impersonate `system:node:<NodeName>` purely based on the `NodeNameKey` extra value matching, sourced from this unverified claim.

### Impact Explanation
An unprivileged user (namespace-scoped `create pods` + `create serviceaccounts/token`) can obtain a token whose extra info claims association with any Node object in the cluster (by name+real UID) without that node ever running the attacker's pod. If that token is authorized (via RBAC `impersonate` on `serviceaccounts`) to use the `associated-node` impersonation mode, this becomes a path to impersonate `system:node:<victim-node>`, which is a node-identity/RBAC-authorization bypass — a serious privilege-escalation and identity-confusion class bug (matches Kubernetes bounty class "authentication/token identity confusion leading to privilege escalation").

### Likelihood Explanation
Preconditions: `ServiceAccountTokenPodNodeInfo` feature gate enabled (GA/beta enabled by default in modern releases); attacker RBAC limited to namespace `create pods` and ability to call `serviceaccounts/token` `create` subresource for a SA they control; ability to set `spec.nodeName` on a pod they create (standard, unrestricted by default RBAC). The steps are fully reproducible without any cluster-admin, node, or webhook access, and repeat deterministically since Node objects and their UIDs are cluster-visible (listable) or guessable/enumerable via any read access to `nodes`.

### Recommendation
In `(v *validator) Validate`, for the `podref != nil && noderef != nil` branch, re-fetch the pod's current `Spec.NodeName` (already available from `v.getter.GetPod` at line 235) and require it to equal `noderef.Name`; additionally fetch the live Node object and confirm `noderef.UID == node.UID` and it is not past its deletion grace period, mirroring the checks already performed in the `podref == nil` branch. Reject validation if the pod is not (or no longer) actually bound to that node.

### Proof of Concept
Unit test addition to `pkg/serviceaccount/claims_test.go`, variant of `TestValidatePrivateClaims`:
1. Construct a fake `ServiceAccountTokenGetter` whose `GetPod` returns a Pod with `Spec.NodeName = "node-A"`.
2. Construct `privateClaims` with `Kubernetes.Pod` matching that pod, but `Kubernetes.Node` set to `{Name: "node-B", UID: <real UID of node-B>}` (simulating a token minted for a pod that was later rescheduled, or a forged/mismatched claim from a manually-set `nodeName`).
3. Enable `features.ServiceAccountTokenPodNodeInfo`.
4. Call `validator.Validate` and assert:
   - Current behavior (bug): `Validate` succeeds and returns `ServiceAccountInfo.NodeName == "node-B"` even though the pod's `Spec.NodeName` is `"node-A"`.
   - Expected behavior (fix): `Validate` should return an error indicating node/pod mismatch, or should derive `NodeName`/`NodeUID` from the live pod object instead of trusting the claim verbatim.

// associatedNodeImpersonationMode allows a requestor service account to impersonate the node that it is
// associated with.  this is by far the most complex impersonation mode because it caches successful
// impersonation attempts in a way that results in a high cache hit ratio even when the same service account
// is used across different pods running on different nodes (i.e. a node agent running as a daemonset).
// only the username can be specified by the requester.  all other fields in user.Info are controlled by the API server.
func associatedNodeImpersonationMode(a authorizer.UnconditionalAuthorizer) impersonationMode {
	// we wrap the authorizer so that we can override the requestor service account's extra values
	// and the node name used in the authorization check.  this makes our authorization checks match
	// the exact semantics of our cache key which prevents unexpected privilege escalation on a cache
	// hit.  see the comment below for the cache key details.
	wrappedAuthorizer := authorizer.AuthorizerFunc(func(ctx context.Context, attributes authorizer.Attributes) (authorizer.Decision, string, error) {
		// we use checkAuthorization instead of directly calling the authorizer so we can
		// make the error message line up with the actual attributes authorized against
		if err := checkAuthorization(ctx, a, &associatedNodeImpersonationAttributes{Attributes: attributes}); err != nil {
			return authorizer.DecisionDeny, "", err
		}
		return authorizer.DecisionAllow, "", nil
	})
	mode := newConstrainedImpersonationMode(wrappedAuthorizer, "associated-node",
		func(wantedUser *user.DefaultInfo, requestor user.Info) bool {
			wantedNodeName := wantedUser.Name
			return onlyUsernameSet(wantedUser) && requesterAssociatedWithRequestedNodeUsername(requestor, wantedNodeName)
		},
	)
	return &associatedNodeImpersonationCheck{mode: mode}
}

func requesterAssociatedWithRequestedNodeUsername(requestor user.Info, username string) bool {
	nodeName, ok := isNodeUsername(username)
	if !ok {
		return false
	}
	if _, _, ok := isServiceAccountUsername(requestor.GetName()); !ok {
		return false
	}
	return getExtraValue(requestor, serviceaccount.NodeNameKey) == nodeName
}
