### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) values that are handed to the host application's handler are read from unauthenticated HTTP headers that are never included in the signed payload. This breaks the intended binding `hmac-signed bytes == bytes the app trusts as originating from a specific shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` (the raw body only) and compares it against `request.hmac`: [3](#0-2) [4](#0-3) 

After a successful HMAC check, `request.shop` (taken straight from the unauthenticated header) is forwarded verbatim into `WebhookMetadata`, which is the exact object host apps are documented to trust for tenant identification: [5](#0-4) [6](#0-5) 

The gem's own documentation instructs developers to key their business logic (e.g., background job routing) directly off `data.shop`: [7](#0-6) 

Because the app's `client_secret` (the HMAC key) is a single shared secret for the whole app across all shops that have installed it, a valid HMAC only proves "this body byte-string was signed with our app secret" — it proves nothing about *which* shop the payload is for. Any party who can obtain one valid `(raw_body, hmac)` pair for their own shop (e.g., a malicious merchant who installed the app and receives real webhooks for their own store, or anyone who can replay a captured webhook delivery) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` will still return `true` because it never looks at the header, and the handler will receive `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker who has legitimate access to one shop's webhook traffic (their own, or via replaying a leaked payload) can inject webhook data attributed to a different shop. Applications that use `data.shop` per the documented pattern to look up shop-specific sessions, enqueue shop-scoped jobs, or write shop-scoped state will process attacker-controlled body content under the wrong tenant's identity — a cross-tenant confusion/injection primitive rooted entirely in this gem's verification logic (`to_signable_string` excluding `shop`).

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(raw_body, hmac)` pair, which is trivially obtainable by any merchant who installs the app (they receive real signed webhooks for their own store) or by intercepting/replaying a delivery. No access to the app's `client_secret`, access tokens, or TLS interception of the victim's traffic is required — only reuse of a signature the attacker legitimately received for themselves, replayed against the shared endpoint with a forged `shop-domain` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) headers into the signable string so the HMAC covers exactly the data the handler is going to trust, e.g. compute `to_signable_string` as a canonical concatenation of `shop-domain` + `raw_body` (or otherwise incorporate the shop header into the HMAC verification) rather than the raw body alone. At minimum, document and/or enforce that host apps must independently verify `data.shop` against a known/registered shop list rather than trusting it as authenticated.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; Shopify delivers a real webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker (who controls `shop-a` or intercepted this delivery) captures `(B, HMAC)`.
3. Attacker sends a new HTTP request to the same webhook endpoint with the identical body `B` and identical `hmac` header, but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B`; `HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches → validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(shop: "shop-victim.myshopify.com", body: parsed(B), ...)` and invokes the host's handler, which now processes `B` as if it were `shop-victim`'s data.
