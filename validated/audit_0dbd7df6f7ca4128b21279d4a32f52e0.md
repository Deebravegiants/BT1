### Title
Excess ETH refunded by Uniswap during fee-swaps becomes permanently stuck in `EvmHost` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept `msg.value` and forward it to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` to buy an *exact* amount of `feeToken()`. `swapETHForExactTokens` refunds any unused ETH to its caller — which is `EvmHost` itself, since `EvmHost` is the one calling the router, not the original end user. ### Finding Description
Every dispatch-with-native-token path in `EvmHost` swaps the entire `msg.value` for an exact `post.fee`/`get.fee`/`amount` of `feeToken`. Because `swapETHForExactTokens` guarantees only that the *exact output* amount of tokens is bought, any ETH sent beyond what the swap actually consumes is refunded by the Uniswap router back to `msg.sender` of the swap call — which is `address(this)` (the `EvmHost` contract), not the caller who originally dispatched the request. `EvmHost` declares a payable `receive()` fallback (also present analogously in `HostManager`, `CallDispatcher`, `IntentGatewayV2`, and the `WrappedHyperFungibleToken` contracts) so this refunded ETH is silently accepted and retained in the contract's balance.

Unlike the fee-token revenue, which `HostManager`'s `OnAcceptActions.Withdraw` governance action can sweep out, there is no equivalent mechanism to withdraw the native-token balance that accumulates in `EvmHost` from these swap refunds. Any discrepancy between the price used to compute the quoted `msg.value` off-chain and the price at execution time (normal AMM price movement between quoting and transaction inclusion) will leave a residual ETH balance permanently locked in the host with no recovery path — mirroring the reported bug class of ETH being accepted via `receive()` with no admin/withdraw function to recover it.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged caller of `dispatch`/`fundRequest` with native token payment — the single most common integration path documented for users (see native-token payment examples in the SDK/docs). Each such call risks trapping a small amount of ETH (dust from slippage/price-drift between the quoted fee and swap execution) that becomes permanently unrecoverable, accumulating in the host contract over time with no governance or admin recovery hook.

### Likelihood Explanation
High likelihood: it triggers on essentially every native-token-funded `dispatch`/`fundRequest` call whenever the quoted fee amount and the actual on-chain price at execution differ even slightly, which is the normal case rather than an edge case, since price quotes are fetched off-chain before the transaction is mined.

### Recommendation
1. Refund any leftover ETH from `swapETHForExactTokens` back to `_msgSender()` / `post.payer` instead of letting it be retained by `EvmHost`, e.g. by checking `address(this).balance` delta before/after the swap and forwarding the difference to the original caller.
2. Alternatively/additionally, add a governance-gated (e.g., via `HostManager`) sweep function that can withdraw the native token balance accumulated in `EvmHost` to prevent value from being permanently locked.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `msg.value = X` where `X` was quoted slightly higher than what is actually required to buy `post.fee` amount of `feeToken` at the time of execution (normal due to block-time price drift).
2. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes; the router consumes only the ETH needed to buy exactly `post.fee` tokens and refunds the remainder to `msg.sender` of that call, i.e. `EvmHost`. [1](#0-0) 
3. The refunded ETH lands in `EvmHost`'s balance via its `receive()` fallback and is never credited back to the user nor recoverable by any admin/governance function, remaining permanently stuck.

        if (msg.value > 0) {
            address[] memory path = new address[](2);

        }
