### Title
Webhook `shop` (and topic/webhook_id) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from the raw HTTP body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and never enter the HMAC computation. `Utils::HmacValidator.validate` only re-derives the signature over `to_signable_string`, so it can never detect tampering with those header-derived fields.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` gates on `Utils::HmacValidator.validate(request)` and then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Request#hmac`/`#to_signable_string` show the signed material is only the raw body bytes, while `#shop`, `#topic`, and `#webhook_id` are pulled from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC only over `verifiable_query.to_signable_string` and compares it to the received signature: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is a single shared secret across every shop that installs the app (not a per-shop secret), a valid `(body, hmac)` pair captured or produced for one tenant's webhook remains cryptographically valid no matter what `x-shopify-shop-domain` header accompanies it. An attacker who is simply a merchant using the app (an unprivileged actor with no access to the app's secret) can capture one legitimate webhook delivery to their own shop, then replay the identical body/HMAC to the app's public webhook endpoint with the `x-shopify-shop-domain` header (and/or `x-shopify-topic`/`x-shopify-webhook-id`) rewritten to a victim shop. `HmacValidator.validate` still returns `true` because it never inspects those headers, so `Registry.process` passes the spoofed `shop` through to the handler as though Shopify itself asserted it for that tenant.

This breaks the identity binding: **shop value cryptographically authenticated == shop value acted upon by the handler**. The HMAC only proves "this body was sent by someone who knows `api_secret_key`" (true of any installing merchant, since the app-wide secret is effectively usable to forge signed bodies for any body content whatsoever using that same secret) — it proves nothing about which shop the event is *for*.

### Impact Explanation
Any host application relying on this gem's webhook verification (as documented/intended usage — `Registry.process` is the supported entry point) to attribute an inbound webhook to the correct tenant is vulnerable to cross-tenant data/state confusion: an attacker-controlled shop identifier can be injected into another merchant's data pipeline (e.g., triggering `orders/create`, `app/uninstalled`, GDPR, or billing-related webhook handling attributed to a victim shop), since the gem provides no other tenant-binding guarantee. This matches "cross-tenant access" impact for a security-sensitive library primitive that apps are expected to trust as-is.

### Likelihood Explanation
Any merchant who installs the app receives real webhooks for their own shop and can trivially capture a valid `(raw_body, hmac)` pair; rewriting the `x-shopify-shop-domain` (or `x-shopify-topic`/`x-shopify-webhook-id`) header on a replayed POST to the app's public endpoint requires no special access, no leaked credentials, and no interaction with Shopify's servers — only the ability to send an HTTP request. This makes exploitation straightforward and repeatable, bounded only by the requirement of controlling at least one shop (a normal, unprivileged capability).

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header-derived fields consumed by handlers) in `Request#to_signable_string`/the value verified by `HmacValidator`, or otherwise cryptographically bind them to the signed body (e.g., via a canonical string that concatenates headers + body prior to HMAC verification), so a signature computed for shop A's payload cannot be replayed as shop B's payload.

### Proof of Concept
1. App merchant M installs the app; Shopify delivers a legitimate webhook to the app's endpoint with body `B`, `x-shopify-hmac-sha256: H = HMAC(api_secret_key, B)`, and `x-shopify-shop-domain: m.myshopify.com`.
2. M captures `(B, H)` (trivial — they control the receiving server, or a proxy in front of it).
3. M crafts a new POST to the same webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(api_secret_key, B) == H`, which is unaffected by the header change.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the app processes an event attributed to a shop the attacker does not control.
