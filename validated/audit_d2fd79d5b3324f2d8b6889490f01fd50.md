### Title
Cross-tenant webhook impersonation via `shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, using the app's single, shop-independent `client_secret`. The `shop` value that the handler uses to attribute the webhook to a tenant is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed bytes. Any merchant who has legitimately installed the app (an ordinary, unprivileged tenant) can therefore capture a validly-signed webhook body that Shopify sent for their own shop, and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, producing a request that passes HMAC validation but is falsely attributed to the victim tenant.

### Finding Description
The identity binding that should hold is:
`{bytes verified by HmacValidator} == {tenant identity the handler acts on}`

In `lib/shopify_api/webhooks/request.rb`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is pulled straight from the (attacker-controllable, unsigned) HTTP header: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, and then forwards `request.shop` (an unauthenticated field) directly into the data handed to the app's handler: [3](#0-2) 

`HmacValidator` computes/verifies the signature using `Context.api_secret_key`, i.e. the single client secret for the whole app (shared across every merchant/shop that installs it), not a per-shop key: [4](#0-3) [5](#0-4) 

Because the HMAC key is shared across all tenants and the signed content is only the body (never shop, topic, or webhook-id), any tenant who has a working, legitimately-installed webhook subscription can:
1. Receive one real, correctly-signed webhook for their own store (attacker's own shop — no special privilege beyond being an ordinary merchant).
2. Replay that exact `raw_body` + `hmac-sha256` header combination to the app's public webhook endpoint, but substitute `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Webhook-Id`/`X-Shopify-Topic`, which are also unsigned) with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the body's signature against the shared secret — which was legitimately produced by Shopify — the check has no knowledge of, or binding to, which shop the signature was meant for.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata` claiming `shop: <victim-shop>`, even though the payload never actually originated from Shopify for that shop.

This breaks the tenant-authentication boundary: the gem verifies "this body was signed by our secret" but the host application (per this gem's documented contract, e.g. `docs/usage/oauth.md`/webhook handler pattern) is expected to trust `WebhookMetadata#shop` as the authenticated tenant identifier for storage, billing, GDPR redaction, order/customer updates, etc. No leaked credentials, TLS interception, or privileged access is required — only the capability every ordinary installed merchant already has (receiving one legitimate webhook of their own).

### Impact Explanation
This matches the "Critical - cross-tenant access" impact category: an unprivileged tenant can force the host application to process arbitrary attacker-supplied webhook bodies (e.g. `customers/data_request`, `app/uninstalled`, `orders/create`, etc., subject to which topics they can legitimately trigger for themselves) under the identity of a different shop. Depending on how the host app's `WebhookHandler#handle` implementation uses `WebhookMetadata#shop` (a pattern this gem explicitly documents and expects), this can lead to cross-tenant data corruption, forged app-uninstall/GDPR-redaction actions against a victim store, or state confusion between tenants sharing the same app installation.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's `Webhooks::Registry.process`/`WebhookMetadata` API as documented: the attacker only needs their own legitimate app installation (any developer/merchant sandbox or paid install) to obtain one genuine signed webhook body, then a trivial HTTP replay with a modified header value — no cryptographic secret is ever needed or leaked, since the same secret validates bodies for every tenant.

### Recommendation
Bind the tenant identity into the verified bytes. E.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`/the HMAC computation (or, if that is not possible because Shopify's own signature only covers the body), require the host application to independently correlate `shop` against a shop that has an active, known webhook subscription/session before trusting it, and document this gap prominently. At minimum, the library should not present `request.shop` as a "verified" field via `HmacValidator.validate(request)` succeeding — the API should make explicit that only the body, not the shop attribution, was authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it register a webhook (e.g. `orders/create`).
2. Attacker triggers the webhook by, e.g., placing an order in their own store, and observes the resulting HTTP request Shopify sends to the app's webhook endpoint, including headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - raw JSON body `B`
3. Attacker resends the exact same body `B` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object; `Utils::HmacValidator.validate(request)` succeeds because it only checks `Digest.hexencode(...)` against `OpenSSL::HMAC.hexdigest(sha256, Context.api_secret_key, raw_body)`, per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38 — none of which reference `shop`.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb lines 188-199) invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to act on forged data attributed to the victim shop.

Note: I could not locate `webhook_metadata.rb` directly in the index (only its definition inside `lib/shopify_api/webhooks/webhook_handler.rb` was found via grep, and its contents were not retrieved) — the exact fields/consumers of `WebhookMetadata` beyond `shop`, `topic`, and `body` are based on the constructor call in `Registry.process` above. If deeper verification of downstream consumers of `WebhookMetadata#shop` is needed, a Devin session with full repo access should inspect `lib/shopify_api/webhooks/webhook_handler.rb` in full.
