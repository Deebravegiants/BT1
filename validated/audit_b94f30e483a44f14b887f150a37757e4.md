## Title
Webhook HMAC only covers the raw body, letting an attacker who owns a legitimate shop replay a genuine webhook payload against another shop's tenant identity - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Webhooks::Registry.process` and handed to application handlers via `WebhookMetadata` come from unauthenticated HTTP headers that are never part of the signed payload.

## Finding Description
`Request#hmac` is read from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, while `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes and compares the signature purely over `to_signable_string` (the body): [3](#0-2) 

`Webhooks::Registry.process` only calls this HMAC check, and then trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by the signature — to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The binding that should hold is:

```
HMAC_valid(body, secret) == true  ⇒  (shop, topic, webhook_id) in the request == (shop, topic, webhook_id) that produced the body
```

but the implementation only proves `HMAC_valid(body, secret) == true`; it says nothing about which shop, topic, or webhook id the signed body belongs to. Any two fields that travel together in the same POST (headers + body) are treated as bound, but only the body is cryptographically bound to the app's secret.

## Impact Explanation
Because the app's `api_secret_key` is shared across every installed shop (it is not per-tenant), any actor who installs the app on their own store — an ordinary, unprivileged action available to any internet user — receives genuine webhook deliveries with valid `(body, hmac)` pairs for their own shop. Since the `shop-domain` header is not part of the signed material, that same `(body, hmac)` pair remains valid when replayed with the `shop-domain` header changed to a different (victim) shop. A multi-tenant application that funnels all shops' webhooks through a shared endpoint and calls `Registry.process` will accept the replayed request as valid and hand the handler a `WebhookMetadata` whose `shop` claims to be the victim's, while the body content is actually the attacker's. This is a cross-tenant identity binding break: the gem authenticates the payload's origin (the app), not its claimed tenant.

## Likelihood Explanation
No secret, access token, or privileged account is required — only ordinary app installation, which is the normal, expected way to become an "authenticated" webhook sender for this app. The attacker fully controls the `shop-domain` (and `topic`/`webhook_id`) header of the request they send to the app's own public webhook endpoint, since it is the attacker's own HTTP client making that request (not a MITM against Shopify's delivery, which remains TLS-protected and out of the attacker's control).

## Recommendation
Bind the tenant-identifying fields into the HMAC-verified material, e.g., include `shop-domain`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, matching how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signable string), so `HmacValidator.validate` cannot succeed for a request whose header-derived shop/topic differs from what was actually signed.

## Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`; the app registers a webhook (e.g. `orders/create`) pointed at the app's shared endpoint.
2. Shopify delivers a legitimate webhook to the app: body `B`, headers include `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(secret, B)`.
3. Attacker captures `(B, H)` from their own inbound traffic (no interception of Shopify's channel required — it is their own destination).
4. Attacker sends a new POST directly to the app's public webhook endpoint with the exact same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only checks `H` against `B` — this succeeds — and then builds `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)`, which the host application processes as authentic data belonging to `victim.myshopify.com`.       def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
