## Analysis Result [1](#0-0) 

### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw()` (Tron variant) — state decrement occurs after external token transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-specific `IntentGatewayV2.withdraw()` function transfers escrowed tokens to the beneficiary via a raw low-level `.call()` **before** decrementing the corresponding `_orders[commitment][token]` escrow accounting, mirroring the exact root-cause pattern described in the referenced `depositBribeERC20` finding: an external, potentially attacker-controlled call is made while the contract's bookkeeping is still stale.

### Finding Description
In `withdraw()`, for each escrowed token the function performs the external transfer first and only afterward updates storage:
```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;   // <-- effect happens AFTER interaction
``` [2](#0-1) 

This is a direct interaction-before-effect ordering, unlike the canonical `_withdraw()` implementation used by the main EVM `IntentGatewayV2`/`IntentsBase.sol`, which decrements the escrow balance **before** performing the transfer:
```solidity
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [3](#0-2) 

Since `order.inputs` (the tokens escrowed and later paid out through `withdraw`) are fully attacker-controlled at order-placement time — the order creator picks arbitrary token addresses — an attacker can supply a malicious ERC20 contract as one of the order's escrowed inputs. That contract's `transfer()` code executes with the gateway as `msg.sender` regardless of who the beneficiary is, giving the attacker a reentrant callback exactly at the point where `_orders[commitment][token]` for that token (and any tokens/fees processed later in the same loop) has not yet been decremented.

This is compounded by the fact that Tron's `placeOrder()` credits escrow using the caller-supplied nominal amount without verifying the gateway's actual balance increase:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [4](#0-3) 

The mainline EVM `placeOrder()` explicitly guards against this by measuring the actual balance delta to handle fee-on-transfer / non-standard tokens:
```solidity
// For fee-on-transfer tokens, the gateway receives less than the requested amount.
// We mutate order.inputs to reflect actual received so the commitment and escrow
// are consistent with what the gateway holds.
``` [5](#0-4) 

The Tron variant lacks this correction, so escrow bookkeeping can be inflated relative to the tokens the contract actually custodies for a given (fee-on-transfer or malicious) token — worsening the impact of any reentrant drainage enabled by the transfer-before-decrement ordering in `withdraw()`.

### Impact Explanation
`withdraw()` is reachable from an unprivileged, user-initiated same-chain cancellation path (`cancelOrder` → `withdraw`) as well as from `onAccept`/`onGetResponse` settlement callbacks. Because the state update for a given token's escrow trails its external transfer, and because the token contract itself (not merely the recipient) is fully attacker-supplied, a malicious token can execute arbitrary logic mid-loop while `_orders[commitment][token]` is still un-decremented. Combined with the missing actual-balance verification at `placeOrder`, this weakens the invariant that on-chain escrow accounting matches real custodied balances for a token pooled across all commitments, creating a path toward accounting inconsistency / fund loss for that token pool.

### Likelihood Explanation
Reaching `withdraw()` with an attacker-chosen token requires only placing an order with a self-deployed ERC20 as one of the inputs and having it filled/cancelled — both permissionless actions available to any user. The primary mitigating factor is that `_filled[body.commitment]` is set at the very top of `withdraw()`, before any external calls, which blocks straightforward re-entry into `cancelOrder`/`withdraw` for the *same* commitment. This reduces but does not eliminate the risk, since the interaction-before-effects ordering remains a structural deviation from the safe pattern used elsewhere in the codebase (`IntentsBase._withdraw`), and the missing fee-on-transfer balance check independently degrades the escrow/backing invariant for the affected token.

### Recommendation
Apply the same checks-effects-interactions ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` (and the fee balance) *before* performing the external transfer/call in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`. Additionally, align Tron's `placeOrder()` escrow crediting with the mainline EVM implementation by measuring the actual token balance delta received rather than trusting the nominal `order.inputs[i].amount`, to prevent under-collateralized escrow accounting for fee-on-transfer or malicious tokens.

### Proof of Concept
1. Attacker deploys a malicious ERC20 `X` whose `transfer()`/`transferFrom()` functions execute arbitrary attacker logic and can fake success without moving real value.
2. Attacker calls `placeOrder` with `order.inputs = [X: hugeAmount]` (and optionally other real tokens). Since Tron's `placeOrder` doesn't verify actual balance received [6](#0-5) , `_orders[commitment][X]` is credited with the nominal amount regardless of real backing.
3. Attacker triggers `cancelOrder` (same-chain path) as the order owner, invoking `withdraw(body, true)`.
4. Inside the token loop, `token.call(transfer(...))` for `X` executes attacker-controlled code before `_orders[body.commitment][X] -= amount` runs [7](#0-6) , giving the attacker a reentrant execution window with stale escrow state for that commitment/token.
5. This callback window, combined with the absence of an actual-balance check at deposit time, allows escrow accounting for token `X` to diverge from real custodied funds, undermining the pooled-balance invariant that other commitments/tokens implicitly rely on.
