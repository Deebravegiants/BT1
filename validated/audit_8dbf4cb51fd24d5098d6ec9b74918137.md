### Title
Webhook `shop` field used for tenant identification is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied, unauthenticated `shop-domain` header straight to the app's handler as the trusted tenant identifier. This mirrors the report's root cause: a value that a downstream security-relevant decision depends on ("shop"/tenant identity) is not part of the data covered by the cryptographic check ("HMAC" here plays the role of "GlobalImpliedCollateralService" state — a value trusted by a later step but never re-validated at the point of use), so the two can diverge and be exploited.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Utils::HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string` [3](#0-2)  — i.e. the shop header is never part of the signed material. `Webhooks::Registry.process` validates that HMAC and, on success, immediately builds `WebhookMetadata` using `request.shop` (the raw header value) as the shop identity passed to the app's handler [4](#0-3) . The library's own documentation instructs apps to trust `data.shop` for shop-scoped work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [5](#0-4) .

Because the app's `api_secret_key` used to sign webhooks is shared across every shop/tenant that installs the app (it is the app's client secret, not a per-shop secret), an attacker who installs the app on their own shop receives legitimately-signed webhook deliveries: `raw_body` + valid HMAC computed with the shared `api_secret_key`. Since the HMAC covers only `raw_body`, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` forwards the attacker-chosen shop string to the handler as if Shopify itself asserted that identity for that payload.

This is the direct analog of the H-06 pattern: the "identity/state" value acted upon in the security-sensitive step (`shop` used to attribute business logic / tenant-scoped side effects) is not bound by the mechanism (`HMAC`) that is supposed to prove authenticity of the whole message, exactly as `getActualPriceTarget`/`getSwingTraderEntryPrice` acted on `globalIC.collateralRatio()` data that was not re-synced at time of use.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to key shop-scoped side effects (queue jobs by shop, update per-shop records, trigger per-shop billing/inventory actions, etc., exactly as the library's own example shows) can have those actions misattributed to an arbitrary victim shop domain by a low-privileged attacker who merely installs the app once on their own store. This is a cross-tenant integrity issue: an attacker-controlled body (from their own install) can be injected into another merchant's processing pipeline under a spoofed shop identity. This satisfies the "cross-tenant access" Critical impact category, since it breaks the binding `hmac-authenticated body == shop the body is attributed to`.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user: no leaked secrets, no privileged account, and no TLS interception are required. The only "privilege" needed is being able to install the app on any shop (the normal, unprivileged self-service Shopify app-install flow), after which the attacker legitimately receives real, validly-signed webhook payloads for their own shop and can replay them with a forged `shop-domain` header to the app's public webhook endpoint.

### Recommendation
Include the shop/tenant identifier inside the HMAC-covered signable string (or otherwise cryptographically bind header-derived identity claims to the signed payload), or require `Registry.process`/`WebhookMetadata` to cross-check the header-derived `shop` against an independently authenticated source (e.g., a shop that the app has an active, previously-established session/installation record for, obtained via `client_id`/webhook subscription metadata from Shopify's API rather than trusting the raw header) before handing it to the handler. At minimum, update the documentation and `WebhookMetadata` contract to explicitly warn that `shop` is unauthenticated header data and must not be used for authorization or tenant-scoping decisions without independent verification.

### Proof of Concept
1. Attacker creates a free/dev Shopify store `attacker-shop.myshopify.com` and installs the target app (normal, unprivileged OAuth flow).
2. Shopify sends the attacker a legitimate webhook, e.g. `orders/create`, with body `raw_body` and header `x-shopify-hmac-sha256 = HMAC-SHA256(api_secret_key, raw_body)`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `raw_body` and the valid `hmac` value.
4. Attacker POSTs to the app's public webhook endpoint (e.g. `/webhooks`) reusing the exact same `raw_body` and `hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only [6](#0-5)  and succeeds because the body/hmac pair is genuinely valid for this app's `api_secret_key` [7](#0-6) .
6. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop = "victim-shop.myshopify.com"` [4](#0-3) , causing the app to process attacker-controlled data as if it originated from the victim shop.
