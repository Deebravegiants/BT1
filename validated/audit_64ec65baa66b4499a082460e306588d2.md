### Title
Unvalidated `shop` parameter in `begin_auth` enables forced OAuth redirect to attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from the caller-supplied `shop:` string without validating that it is a trusted Shopify domain, unlike the other credential-issuing flows in this gem (`ClientCredentials`, `TokenExchange`, `RefreshToken`), which all call `Utils::ShopValidator.sanitize!` before using the shop value.

### Finding Description
`begin_auth` takes `shop:` as a plain `String` and passes it straight into `auth_base_uri(shop)`, which returns `"https://#{shop}/admin"` with no domain check: [1](#0-0) [2](#0-1) 

The resulting `auth_route` (containing the app's `client_id`, `redirect_uri`, requested `scope`, and a nonce `state`) is returned to the caller to redirect the merchant's browser to. There is no equivalent of `Utils::ShopValidator.sanitize!` here, contrary to every other entry point in the auth namespace that accepts a `shop` argument: [3](#0-2) [4](#0-3) 

The intended binding is: *the host that receives the OAuth authorize redirect (and later the `client_id`/`redirect_uri`) == a domain suffixed by a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`)*. `begin_auth` never enforces this equality — it trusts whatever `shop` string the host application passes in, and typical integrations (per this gem's own docs example) source that value from an unauthenticated request parameter/header supplied by the browser initiating installation: [5](#0-4) 

By contrast, `validate_auth_callback` (the second half of the flow) is protected because the `shop` value returned in the callback is bound by Shopify's HMAC over the query string, which an attacker cannot forge without the app's secret: [6](#0-5) [7](#0-6) 

But that protection only applies to the callback step; `begin_auth` itself has no such binding, so the redirect target is attacker-controllable at the very first, unauthenticated step of the flow.

### Impact Explanation
An unprivileged internet user can craft an install/login link for a vulnerable host app with `shop=attacker-controlled-host`. If the host app (following this gem's documented `begin_auth` usage) passes that value straight through, the victim merchant's browser is redirected to `https://attacker-controlled-host/admin/oauth/authorize?client_id=...&redirect_uri=<app_callback>&state=<nonce>`. The attacker's server can then present a fake authorization page (or silently forward/replay to real Shopify with attacker-influenced parameters), enabling forced OAuth completion / session fixation against the victim — the `state` nonce and cookie set by `begin_auth` originate from the app but the flow the merchant is directed through is entirely attacker-controlled. This falls under the in-scope High-severity category "session fixation or forced OAuth completion."

### Likelihood Explanation
Likelihood is high given that: (1) this is the very first, unauthenticated step of the OAuth flow, requiring no prior credentials; (2) the gem's own documentation instructs developers to read `shop` directly from a request header/param without validation; (3) the parallel functions in the same file (`ClientCredentials`, `TokenExchange`, `RefreshToken`) already recognize the need for `ShopValidator.sanitize!` on shop-domain input, showing the library authors were aware of this class of risk but did not apply it consistently to `begin_auth`.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) inside `begin_auth` before constructing `auth_base_uri`, raising `Errors::InvalidShopError` for any `shop` value that does not resolve to a trusted Shopify domain, mirroring the existing checks in `ClientCredentials.client_credentials`, `TokenExchange.exchange_token`, and `RefreshToken`.

### Proof of Concept
1. A vulnerable host application implements the login route exactly as shown in this gem's docs, taking `shop` from an incoming request header/param:
```ruby
def login
  shop = request.headers["Shop"]  # attacker controlled, e.g. "evil.example.com"
  auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
  redirect_to auth_response[:auth_route]
end
```
2. Attacker sends a victim merchant a link that triggers this route with `Shop: evil.example.com`.
3. `begin_auth` computes `auth_route = "https://evil.example.com/admin/oauth/authorize?client_id=<app_key>&scope=...&redirect_uri=<callback>&state=<nonce>"` with no domain validation (`lib/shopify_api/auth/oauth.rb:117-120`).
4. The victim's browser is redirected to the attacker-controlled host, which can spoof the Shopify consent screen or proxy/manipulate the flow to force an unintended OAuth completion, while the app's `client_id` and callback URL are exposed to the attacker's server.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state
