### Title
Unauthenticated `create` in lockup-factory allows front-running to permanently block a victim's deterministic lockup account - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the new lockup contract's account ID deterministically from only the `owner_account_id` parameter and the factory's own account ID, and it can be called by **any** unprivileged account with no check that the caller is authorized to create a lockup for that `owner_account_id`. This mirrors the `vestFor` bug: any attacker can pre-empt a legitimate lockup/vesting setup for a victim by "claiming" the victim's deterministic account name first, permanently blocking the real lockup from ever being deployed for that owner.

### Finding Description
`create()` computes the lockup account name purely from `owner_account_id`: [1](#0-0) 

There is no check that `env::predecessor_account_id()` is the `owner_account_id`, the foundation, or any other trusted party — the function is `#[payable]` and callable by anyone who attaches at least `MIN_ATTACHED_BALANCE` (3.5 NEAR): [2](#0-1) [3](#0-2) 

Because NEAR account creation via `Promise::create_account()` fails if the account already exists, and the lockup account ID is a deterministic function of only `owner_account_id` (`sha256(owner_account_id)[..20]` + factory account), the account name-space for every possible owner is fully predictable and can be squatted ahead of time. If the account already exists, the subsequent legitimate `create()` call for the same `owner_account_id` will fail at `create_account()`, and the callback simply refunds the deposit to the second (legitimate) caller — it does not, and cannot, dislodge the attacker's already-deployed contract: [4](#0-3) 

An attacker can front-run a foundation/employer's legitimate lockup creation for a known `owner_account_id` (e.g., observed in mempool, or simply predicted ahead of an announced token grant) by calling `create` themselves first with the minimum required deposit and arbitrary/degenerate parameters (e.g., a bogus `vesting_schedule`, or `lockup_duration` set to an enormous value). This permanently occupies the deterministic account name tied to that `owner_account_id`, since account names on NEAR cannot be reused by a different deployment while still allocated.

### Impact Explanation
This is a permanent, irrecoverable griefing/freezing vector: the legitimate lockup/vesting contract for the targeted `owner_account_id` can never be created at its expected deterministic address, and the real deposit (potentially the user's entire vesting allocation) is instead only refunded to the caller — the lockup never gets set up as intended. This matches the "Critical: Permanent freezing / unrecoverable lock ... in lockup release, vesting termination" impact category, since a targeted account is denied its intended lockup allocation indefinitely with only a minimal (3.5 NEAR) griefing cost to the attacker.

### Likelihood Explanation
Likelihood is high for any scenario where `owner_account_id`s for planned lockups are predictable or observable in advance (e.g., publicly known team/investor account names, or a `create` transaction visible in the mempool before it's mined). The attack requires no privilege and only a small deposit, and the deterministic account naming scheme makes the target address computable off-chain in advance by anyone.

### Recommendation
Require that `create` either be restricted to a whitelist of trusted callers (e.g., only the foundation/master account, similar to the report's suggested mitigation of whitelisting `Converter`-like callers), or that `env::predecessor_account_id()` equal the `owner_account_id` being created for, or incorporate an unpredictable/attacker-uncontrollable salt (e.g., combined with `predecessor_account_id` and a nonce) into the derived lockup account name so it cannot be pre-squatted by unrelated third parties.

### Proof of Concept
1. Foundation intends to create a lockup for `victim.near` via `create(owner_account_id="victim.near", ...)`, which would deploy to `sha256("victim.near")[..20].factory.near`.
2. Attacker observes this intent (public announcement or pending tx) and submits their own `create(owner_account_id="victim.near", lockup_duration=..., ...)` with only `MIN_ATTACHED_BALANCE` attached, before the foundation's transaction lands.
3. Attacker's transaction succeeds first, deploying a lockup contract to the deterministic address `sha256("victim.near")[..20].factory.near` under attacker's chosen (degenerate) terms.
4. Foundation's legitimate `create()` call for `victim.near` now fails at `create_account()` (account already exists); `on_lockup_create` refunds the deposit but the intended legitimate lockup is never deployed at that address — `victim.near` is permanently denied its intended lockup/vesting contract at the expected location.     #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
