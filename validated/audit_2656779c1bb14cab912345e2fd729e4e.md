### Title
Direct-donation of a launched Token into its own `Pair` breaks the `virtualReserve > realBalance` invariant and turns `Router._computeBuy`'s overflow-cap branch into an unhandled arithmetic-underflow `Panic`, permanently DoS-ing `buy()` on that curve - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` relies on the invariant "`Pair`'s virtual `tokenReserve` always exceeds the real `tokenBalance()`" to safely compute `cappedReserveToken = reserveToken - tokensOut` when a buy's uncapped output would exceed the pair's real token balance. This invariant is asserted only under normal trading (`test_inv_virtualReserveAlwaysExceedsRealBalance` in `test/GraduationInvariants.t.sol`) and is never enforced on-chain. Any unprivileged holder of the launched `Token` can `transfer()` it directly to the `Pair` contract, inflating `tokenBalance()` (real ERC20 balance) without moving `_pool.tokenReserve` (the virtual reserve tracked by `Pair.swap`/`Pair.mint`). Once `tokenBalance() >= tokenReserve`, the very next buy whose uncapped output exceeds `realBalance` hits the capping branch and computes `reserveToken - tokensOut` with `tokensOut == realBalance >= reserveToken`, causing a raw Solidity arithmetic-underflow `Panic(0x11)` instead of the intended `OverflowCapDegenerate` revert. This is a reachable-assertion/panic class bug (CWE-617 analog): attacker-controlled external input (a plain ERC20 donation) drives the contract into a state where a subsequent, otherwise-legitimate transaction unconditionally reverts via an unhandled low-level panic, permanently freezing trading (and graduation) on that curve — the same "specific attacker-crafted input past a threshold triggers an abort()" shape as CVE-2023-1428, just realized in Solidity arithmetic instead of gRPC's C++ assertions.

### Finding Description
`Router._computeBuy` (`packages/contracts/src/Router.sol:127-148`):
```solidity
function _computeBuy(address pairAddr, uint256 amountIn) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
    IPair pair = IPair(pairAddr);
    (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
    uint256 k = pair.k();
    amountInUsed = amountIn;
    uint256 newReserveAsset = reserveAsset + amountInUsed;
    tokensOut = reserveToken - (k / newReserveAsset);
    uint256 realBalance = pair.tokenBalance();
    if (tokensOut > realBalance) {
        tokensOut = realBalance;
        uint256 cappedReserveToken = reserveToken - cappedReserveToken; // reserveToken - tokensOut
        if (cappedReserveToken == 0) revert OverflowCapDegenerate();
        uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
        amountInUsed = cappedReserveAsset - reserveAsset;
    }
}
``` [1](#0-0) 

`reserveToken` here is `Pair._pool.tokenReserve`, the virtual reserve updated only by `Pair.mint`/`Pair.swap` (`packages/contracts/src/Pair.sol:55-79`) [2](#0-1) . `realBalance` is `Pair.tokenBalance()`, a **live** `IERC20(launchedToken).balanceOf(address(this))` read (`packages/contracts/src/Pair.sol:103-105`) [3](#0-2) . Nothing gates or reconciles a plain ERC20 `transfer()` of the launched `Token` into the `Pair` address — it silently inflates `tokenBalance()` while `_pool.tokenReserve` stays untouched.

The safety of the capping branch (`cappedReserveToken = reserveToken - tokensOut`, `tokensOut = realBalance`) depends entirely on `reserveToken > realBalance` holding at all times — precisely the property the codebase's own docs call out as an invariant made purely of "production seeding" arithmetic (`virtualReserveToken = totalSupply`, `realTokenAmount = curveSupply = 75%`), and tests only under that seeding, never under donation:
```
/// makes `pair.tokenBalance() < pair.tokenReserve()` a hard property at
/// every state of the curve. This invariant is what makes the
/// `cappedReserveToken == 0` branch in `Router._computeBuy`
/// unreachable; if it ever ceased to hold, that branch would
/// revert with `OverflowCapDegenerate` rather than over-pay.
``` [4](#0-3) 

This natspec explicitly assumes the invariant only fails in the direction `reserveToken == realBalance` (giving the clean, named revert `OverflowCapDegenerate`). It does not consider the direction where `realBalance` is pushed **above** `reserveToken` by direct donation — a path that is not merely "hint," it is one of the explicitly allowed reachable surfaces per the scope rules ("direct ERC20 transfers of a launched Token ... into ... Pair"). In that direction, `tokensOut` is capped to `realBalance > reserveToken`, and `reserveToken - tokensOut` underflows a `uint256`, producing an unguarded `Panic(0x11)` — not the intended custom error, and not caught or handled anywhere in `Router.buy`/`Bonding.buy`/`Zap.buy`. Because the trigger condition (`realBalance >= reserveToken`) persists in storage/balance until burned, every subsequent buy that would size a capped output reverts identically, i.e. the DoS is sticky, not a one-shot revert.

### Impact Explanation
Once an attacker donates enough of the launched `Token` to push `Pair.tokenBalance()` to or above `Pair.tokenReserve()` (the virtual reserve), any buy sized to exceed the (inflated) real balance — which, near curve exhaustion or after a moderate donation, includes ordinary trader buys and specifically the threshold/graduation-crossing buy — reverts with an unhandled arithmetic panic instead of completing or cleanly erroring. This:
- Permanently freezes `Bonding.buy`/`Zap.buy` for that token's curve (denial of service on trader funds already in flight via `Zap._executeBuy`'s USDC pull, which precedes the revert and must then be rolled back, but the intended trade never lands).
- Blocks the token from ever reaching the supply-exhaustion or USD-threshold graduation trigger through the affected buy sizes, since `_enterGraduating`/`triggerGraduation` depend on `canGraduate`/the same curve math to fire.
- Is cheap: the attacker only needs to hold or buy some of the launched `Token` (which anyone can obtain via a normal curve buy) and `transfer()` it to the `Pair` address — no privileged role, no protocol interaction beyond a standard ERC20 transfer.

This satisfies the "permanent freezing of trader/creator funds" bar in the validation rubric: curve trading becomes unusable for buys that hit the capping branch, and there is no recovery path in `Router`/`Bonding`/`Pair` that reconciles a donated `tokenBalance()` back down or otherwise repairs the invariant before `finalizeGraduation`/burn logic in `_prepareGraduationLiquidity` (which only runs post-trigger, i.e. too late to prevent the panic on the triggering buy itself).

### Likelihood Explanation
High. The launched `Token` is a standard ERC20 (`packages/contracts/src/Token.sol`) transferable by any holder — obtaining tokens requires only a single ordinary curve buy. Donating tokens straight to the `Pair` address requires no special permissions, no timing window relative to graduation phases, and no interaction with `BONDING_ROLE`/`onlyRouter` gates (those only gate `Pair.swap`/`mint`/`transferToken`, not plain ERC20 receipt). The condition needed to trigger the panic — a buy whose *uncapped* curve output exceeds the (now-inflated) real balance — is exactly the kind of large/closing buy the overflow cap exists to handle, so it is naturally reachable once the curve nears exhaustion, and can also be forced deliberately by a large buy from the attacker themselves immediately after the donation.

### Recommendation
- In `Router._computeBuy`, explicitly bound the capping branch against the case `tokensOut > reserveToken` (i.e. `realBalance >= reserveToken`) and revert with the existing named `OverflowCapDegenerate` error (or a new, equally explicit error) instead of allowing the subtraction to underflow.
- More fundamentally, do not trust `Pair.tokenBalance()` as an authoritative capacity bound without reconciling it against `_pool.tokenReserve`; either (a) track "real transferred supply" as explicit `Pair` state updated only by `Router`, independent of live `balanceOf`, or (b) sweep/burn any donated `launchedToken` balance in `Pair` before it can be read by `_computeBuy` (mirroring the existing donation-burn behavior already implemented for the graduation path in `_prepareGraduationLiquidity`).
- Add a regression test that donates `Token` directly to `Pair` to push `tokenBalance() >= tokenReserve`, then executes a buy sized to hit the overflow-cap branch, asserting a clean revert (not a `Panic`) and, ideally, that trading remains usable afterward.

### Proof of Concept
1. Launch a token via `Bonding.launch`/`Zap.createToken` (standard flow); `Pair.tokenReserve = totalSupply` (virtual), `Pair.tokenBalance() = curveSupply` (e.g. 75% of `totalSupply`) per the documented virtual-reserve seeding [5](#0-4) .
2. Attacker buys some amount of the launched `Token` on the curve via `Zap.buy`/`Bonding.buy` (any unprivileged trader can do this).
3. Attacker calls `IERC20(token).transfer(pairAddr, X)` directly, sending most/all of their tokens straight to the `Pair` contract — this is a plain ERC20 transfer, not `Pair.mint`/`swap`, so `_pool.tokenReserve` is untouched while `Pair.tokenBalance()` (a live `balanceOf` read, `packages/contracts/src/Pair.sol:103-105`) jumps by `X`. Repeat/size `X` so that `tokenBalance() >= tokenReserve`.
4. Any subsequent buy through `Bonding.buy`/`Zap.buy` that computes an uncapped `tokensOut` (via the constant-product formula in `Router._computeBuy`, `packages/contracts/src/Router.sol:130-138`) greater than the now-inflated `realBalance` enters the capping branch at line 141-146, computing `cappedReserveToken = reserveToken - tokensOut` with `tokensOut == realBalance >= reserveToken`, which underflows and reverts with `Panic(0x11)` instead of the intended `OverflowCapDegenerate` custom error — bricking that buy path for as long as the donated-inflated balance persists.

(Note: exact numeric thresholds to force the capping branch to fire post-donation depend on live curve state and were not independently re-derived against the concrete test harness in this pass; a Devin session with the Foundry test suite would be needed to confirm the precise `X` and buy-size values that trigger the panic end-to-end and to add the regression test described above.)
