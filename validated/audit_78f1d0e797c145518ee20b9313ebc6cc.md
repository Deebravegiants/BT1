## Title
Single authorized-relayer gate on `IntentGatewayV2`/`ExtrinsicIntents` can permanently freeze all escrowed intent funds if that relayer's key is lost — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents.onAccept` and `onGetResponse` — the callbacks that settle every cross-chain intent order (`RedeemEscrow`, `RefundEscrow`) as well as every governance action reaching the gateway (`NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`) — gate on a single stored `_relayer` address before decoding anything else. If that one address's private key becomes inaccessible, no message of any kind, including the one that would rotate the relayer itself, can ever be delivered again, permanently freezing all escrowed order funds.

### Finding Description
`_checkRelayer` rejects any delivery whose `msg.sender`-derived `relayer` field does not match the stored `_relayer`, once one has been set: [1](#0-0) 

`onAccept` runs this check **unconditionally, before even reading the request-kind byte**, so it applies identically to escrow settlement and to governance: [2](#0-1) 

`onGetResponse`, used to refund escrow after a source-side cancellation, has the same unconditional gate: [3](#0-2) 

Crucially, the *only* way to change `_relayer` is `setRelayer`, which is `onlyHost` and reachable exclusively through a `RequestKind.Execute` delivery — itself an incoming message that must first pass through `_checkRelayer`: [4](#0-3) 

This is confirmed by the project's own documentation of the delivery path: rotation happens via the `Execute` discriminator, delegatecalled with the host as `msg.sender`, but that delegatecall is only reached after the same relayer check at the top of `onAccept`: [5](#0-4) 

Because `incoming.relayer` is the `msg.sender` of the on-chain transaction that calls the handler (`HandlerV2.handlePostRequests`), and Ethereum transactions must be signed by the private key of that exact address, losing access to the `_relayer` key means **no account can ever again produce a valid delivery to this gateway** — not settlement messages, and not the governance `Execute`/`setRelayer` message that would otherwise reopen or rotate the gate. Every escrowed order's `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund), all dispatched with `timeout: 0` (never expiring) via `_post`, becomes permanently undeliverable: [6](#0-5) 

The identical pattern (relayer allowlist covering both escrow and governance actions) was intentionally introduced as documented in the changelog: [7](#0-6) 

### Impact Explanation
This is a hard, unrecoverable centralization risk analogous to WP-H9: a single off-chain key (the authorized relayer address) is required to complete every settlement of escrowed cross-chain intent orders, and that same key is also required to deliver the only message capable of rotating or clearing it. If the key holder loses access (compromise of hardware, loss of seed, operator disappearance), all funds currently escrowed in `ExtrinsicIntents`/`IntentGatewayV2` for cross-chain orders (solver settlement payouts and user refunds) are permanently frozen, with no on-chain recovery path — governance itself cannot reach the contract to fix it, because governance's own `Execute`/`setRelayer` message must be delivered by that same lost key.

### Likelihood Explanation
Once `setRelayer` is used to arm the gate (the documented, intended deployment configuration per the changelog above), the risk is structural and always present for the lifetime of that relayer assignment — no attacker action is required, only ordinary key loss/unavailability of the single designated relayer operator. Given real-world custody risk (device loss, personnel turnover, compromised infrastructure with no backup signer), this is a realistic Medium-likelihood event with permanent-freeze consequences.

### Recommendation
Do not gate governance-originated actions (`NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`) behind the same single relayer address used for economic settlement messages. At minimum, allow a distinct, more resilient (e.g., multisig or Hyperbridge-governance-controlled) path to call `setRelayer`/reset the gate that does not itself require delivery by the very key being rotated, and/or maintain a fallback relayer set instead of a single address so operational key loss cannot brick settlement.

### Proof of Concept
1. Governance arms the gateway via `Execute` → `setRelayer(relayerA)`, so `_relayer = relayerA` (per `evm/src/apps/intentsv2/ExtrinsicIntents.sol:86-88,101-104`).
2. Users place cross-chain orders and escrow tokens in `IntentGatewayV2`/`ExtrinsicIntents`; solvers fill orders on the destination chain, dispatching `RedeemEscrow` (and/or users cancel, dispatching `RefundEscrow`), both with `timeout: 0` (`_post`, lines 128-142).
3. `relayerA`'s private key is lost (device failure, compromised custody, operator departure).
4. Any other address attempting to deliver the pending `RedeemEscrow`/`RefundEscrow` message via `HandlerV2.handlePostRequests` has its call reach `onAccept`, which reverts at `_checkRelayer(incoming.relayer)` (`ExtrinsicIntents.sol:331`) since `relayer != relayerA`.
5. An attempt by governance to dispatch a new `Execute` message containing `setRelayer(relayerB)` suffers the identical revert at the same line before the body is even decoded, since it too must be delivered by `relayerA`.
6. Result: every escrowed input token for every pending cross-chain order remains locked in the gateway indefinitely, with no further deliverable message capable of releasing it.

     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The

        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }

3. `ExtrinsicIntents.onAccept` runs `onlyHost`, then `_checkRelayer(incoming.relayer)`, which reverts
   with `Unauthorized` when a relayer is set and the delivery is from anyone else. Only then is the
   first body byte read as a `RequestKind`. `onGetResponse` has the same two steps before touching
   the response.

So a delivery from anyone but the authorised relayer never decodes the body, never runs
`_authenticate`, and leaves no receipt. The authorised relayer submitting the same message later
takes the normal path. A gateway whose `_relayer` is zero accepts every relayer: that is the state
a fresh proxy is in until governance arms it, below.

# 2026-09-03 — Relayer allowlist on the intent gateway

The gateway now accepts `onAccept` and `onGetResponse` deliveries only from a single authorised
relayer stored at `_relayer` (slot 13, packed behind `_paused`). The check runs before the message
body is decoded, so escrow redemptions, refunds and every governance action, upgrades included, are
covered. A refused delivery reverts, which the host records as undelivered, so the authorised
relayer can submit the same message later. `setRelayer(address)` is callable by the immutable
`_owner` and by the host; the host branch exists so a governance `UpgradeContract` can carry the
call as its migration calldata and arm the relayer in the upgrade transaction (`upgradeToAndCall`
delegatecalls that calldata with the host still as `msg.sender`).
