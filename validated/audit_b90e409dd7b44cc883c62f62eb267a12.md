### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) identity fields are trusted from unauthenticated headers while only the raw body is covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw HTTP body, while the tenant-identifying `shop` field (and `topic`) are read directly from HTTP headers that are never included in the signed content. `Registry.process` accepts the request once the body's HMAC validates, then dispatches the handler using the unauthenticated `shop` header value, breaking the equality "bytes verified == bytes acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight out of the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body only via `HmacValidator.validate(request)`, and then, on success, forwards the caller-supplied `request.shop` (and `request.topic`) straight to the app's handler without any check that binds `shop` to the signature: [3](#0-2) 

`HmacValidator.validate_signature` confirms the digest matches `verifiable_query.to_signable_string` (the raw body) against the shared `api_secret_key`/`old_api_secret_key` — never the shop header: [4](#0-3) 

Because the `client_secret` (`api_secret_key`) used to sign webhooks is a single per-app secret shared across every merchant that has installed the app — not a per-shop secret — any valid `(raw_body, hmac)` pair captured from a genuine Shopify webhook (e.g. from the attacker's own store, or any other store on which the app is installed) remains a *valid* signature no matter which `shop-domain` header accompanies it, as long as the raw body bytes are unchanged. An unprivileged attacker who controls a store with the target app installed can therefore:
1. Trigger any webhook topic with a predictable/attacker-controllable body (many Shopify webhook payloads — e.g. `app/uninstalled`, `shop/redact`, or custom webhooks with attacker-influenced content — are stable or attacker-shaped), capturing the resulting `(raw_body, hmac)` from their own shop's genuine delivery.
2. Replay that exact `raw_body` and `hmac` to the app's webhook endpoint, substituting the `shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still returns `true` because it only checks the body against the secret; `Registry.process` then calls the handler with `WebhookMetadata.new(..., shop: <victim-domain>, ...)`, so the host application processes an event that it believes originated from, and is bound to, the victim tenant.

This is precisely the class of bug reported in the external analog: a downstream security decision (routing/acting on a per-tenant identity) is made using a value that was never covered by the cryptographic check meant to authenticate it — here, `state.data.variablePool` balance (wrong source for liquidity) is directly analogous to `request.shop` (wrong/unauthenticated source for tenant identity) being trusted despite the HMAC guaranteeing only the body's integrity.

### Impact Explanation
This enables cross-tenant webhook spoofing: an attacker who can trigger or observe one legitimate webhook delivery (from any shop, including their own) can impersonate a different, victim shop to the host application's webhook handler while the gem still reports the HMAC as valid. Depending on what the host app's `WebhookHandler#handle` does with `shop` (e.g., cache invalidation, uninstall/redact processing, feature toggles, or persistence keyed by shop), this can lead to cross-tenant data manipulation or state corruption attributed to a shop the attacker does not control. This matches the "cross-tenant access" / "credential leakage" class of High-severity impact defined in scope, since the tenant boundary (`shop`) is not authenticated even though the request as a whole is treated as verified.

### Likelihood Explanation
Requires only an unprivileged attacker who can install the target app on any shop (including a free/dev store) to legitimately obtain a valid `(body, hmac)` pair signed with the app's shared `client_secret`, then replay it to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or victim credentials is needed — satisfying the "unprivileged internet user" constraint. The main variable affecting exploitability is how much of the JSON body a given topic lets the attacker control/predict, but several topics (including the mandatory `shop/redact`, `customers/redact`, `customers/data_request`, and generic lifecycle webhooks) have stable, low-entropy bodies, making replay straightforward.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`, `webhook-id`) values into the HMAC-verified content, or otherwise cryptographically tie the header-derived identity to the signed payload before it is used for dispatch — e.g., include the shop domain in `to_signable_string`, or independently verify the `shop` value against session/installation state known to the host app before trusting `WebhookMetadata#shop`. At minimum, document clearly that `request.shop` is unauthenticated and must not be used as the sole tenant identifier by consuming applications.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers (or waits for) a webhook whose body is stable/predictable, e.g. `shop/redact` with body `{}`.
2. Attacker captures the resulting HTTP request, including headers `x-shopify-hmac-sha256: <hmac>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `{}`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `{}`, the same `x-shopify-hmac-sha256` header, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `hmac` against `@raw_body` (`{}`), independent of the `shop` header: [3](#0-2) 
6. The registered handler executes with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"`, even though the request never actually originated from or was authorized by that shop.
