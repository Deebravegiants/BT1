### Title
Ambiguous withdrawal matching in `PoaBridge.describeWithdrawal` misreports status/txHash for batched same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the status/txHash of a specific withdrawal (identified by `index` within a multi-withdrawal intent transaction) by matching POA Bridge API results only by `assetId`, not by `index`, `destinationAddress`, or `amount`. When a single NEAR transaction contains more than one withdrawal of the same asset (e.g., two withdrawals of the same token to different destination addresses in one batch intent), the lookup can return the wrong underlying withdrawal record for the requested index, causing the SDK to report a completion status/txHash that does not correspond to the on-chain outcome of the withdrawal actually being queried.

### Finding Description
`describeWithdrawal` is invoked per withdrawal index by `watchWithdrawal`/`waitForWithdrawalCompletion` (`packages/intents-sdk/src/core/withdrawal-watcher.ts` and `packages/intents-sdk/src/sdk.ts`) to determine whether a particular withdrawal (identified by its `WithdrawalIdentifier`, which carries `index` and `withdrawalParams`) has completed on the destination chain.

The code comment explicitly acknowledges the limitation: "matches by assetId... multiple withdrawals of the same token in a single transaction are not supported" (lines 412-416). Since `Array.prototype.find` returns the *first* match in an unsorted API response list, any call to `describeWithdrawal` for *any* index of a batch that withdraws the same asset multiple times (to different destination addresses and/or amounts) will resolve to the *same* single withdrawal record — regardless of which index was actually requested.

This breaks the equality that should hold between "the withdrawal identified by (tx, index, destinationAddress, amount)" and "the withdrawal record whose status/txHash is reported back to the caller." The caller queries per-index expecting the status of *that specific* withdrawal (a specific destination/amount pair); instead it may receive the status and destination transaction hash belonging to a *different* withdrawal in the same batch.

### Impact Explanation
This is a status/hash misreport: `waitForWithdrawalCompletion`/`watchWithdrawal` (`packages/intents-sdk/src/core/withdrawal-watcher.ts`, `packages/intents-sdk/src/sdk.ts`) will resolve the promise for withdrawal index 1 with the `txHash` and completion status that actually belong to withdrawal index 0 (or vice versa) if both withdraw the same asset. An integrator relying on `waitForWithdrawalCompletion`'s per-withdrawal result to mark a specific destination-address transfer as settled could:
- Mark a withdrawal to destination B as "completed" using a transaction hash that actually paid out destination A, or
- Report an entry as `completed` while the correct withdrawal (to a different address/amount) is still pending or failed.

This matches the listed High-impact category: "a status or hash misreport making an integrator credit or refund twice" — an integrator could credit the wrong recipient's off-chain ledger entry as fulfilled based on a txHash that actually satisfies a different withdrawal, or fail to detect that the intended withdrawal has not actually completed (leading to duplicate processing/refund logic firing incorrectly).

### Likelihood Explanation
The precondition (a single NEAR intent transaction with two or more withdrawal legs of the *same* `assetId`) is a realistic usage pattern for the SDK, since `withdrawalParams` accepted by `waitForWithdrawalCompletion`/`processWithdrawal` is explicitly typed/documented to support arrays of withdrawals within one intent transaction (batched withdrawals), and nothing in `createWithdrawalIntents`/`createWithdrawalIdentifier` prevents two withdrawal legs from using the same asset with different destinations or amounts. The bug is deterministic once that precondition is met (not a race condition), and it's explicitly called out as a known gap in the code's own comments, confirming the root cause and its reachability.

### Recommendation
Match POA API withdrawal records using more than just `assetId` — e.g., combine `assetId` with `amount` and `destinationAddress` (and if the bridge API exposes any ordering/sequence field, use `index` positionally after sorting both lists deterministically by amount/creation order as suggested in the existing code comment). At minimum, add a `strict` fallback that throws/returns `pending` (rather than silently matching the wrong record) if multiple withdrawal records match the same `assetId` and their `amount`/`address` cannot be disambiguated against the requested `withdrawalParams`, to avoid ever reporting a wrong txHash as the outcome for a specific withdrawal index.

### Proof of Concept
1. Submit a NEAR intent transaction containing two withdrawal legs for the same POA-bridged asset (e.g., `nep141:usdc.token.near`) with different `destinationAddress` values (`indexA` -> address X, `indexB` -> address Y).
2. The POA Bridge API eventually returns both withdrawal records in its (unsorted) `withdrawals` list for that `tx.hash`, one `COMPLETED` with `transfer_tx_hash` for X, one still `PENDING` for Y.
3. Call `bridge.describeWithdrawal({ ...withdrawalIdentifierForIndexB (destination Y) })`.
4. `findMatchingWithdrawal` matches by `assetId` only and returns the first array element — the `COMPLETED` record for destination X — even though the caller asked about the withdrawal to Y.
5. `describeWithdrawal` returns `{ status: "completed", txHash: <X's tx hash> }` for the request about Y's withdrawal, and `watchWithdrawal`/`waitForWithdrawalCompletion` resolves as if Y's withdrawal succeeded with X's transaction hash — a status/hash misreport not reflecting Y's actual on-chain outcome.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
