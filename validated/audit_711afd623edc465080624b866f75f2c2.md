## Title
Webhook HMAC signature does not cover the `shop` (tenant) identity, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw HTTP body only, while the `shop` (tenant) identity used by `ShopifyAPI::Webhooks::Registry.process` to dispatch business logic is taken from an HTTP header that is never included in the HMAC-covered content. This breaks the identity binding `hmac-covered content == data acted upon`, letting anyone who can obtain one valid `(raw_body, hmac)` pair replay it against the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to execute merchant-specific business logic under a victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the raw body, and then forwards `request.shop` (an unauthenticated header value) directly into the handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate` in turn only checks the `hmac` field against `to_signable_string`, i.e. the body — it has no knowledge of `shop`: [4](#0-3) 

Because Shopify signs webhooks with the app's single shared `client_secret`/`api_secret_key` across *all* installed shops (not per-shop), the HMAC over a given `raw_body` is identical regardless of which shop originated it. Any entity that can install the app on their own store (a normal unprivileged action requiring no special credentials) will receive real, validly-signed webhooks whose body content is often shop-independent (e.g., `app/uninstalled`, or topics with static/templated bodies). That attacker-controlled tenant can capture one legitimate `(raw_body, hmac)` pair and replay it to the app's public webhook HTTP endpoint while forging the `x-shopify-shop-domain` header to name a victim shop. `Registry.process` will pass HMAC validation (the body/HMAC pair is genuinely valid) and then execute the registered handler with `WebhookMetadata#shop` set to the victim's domain — a value that was never covered by the signature the code just verified.

This is the direct analog of the Solmate `safeTransfer`/`safeTransferFrom` bug class: the code checks one thing (the HMAC over the body) but acts on another, unchecked thing (the `shop` header used as the tenant/identity key), letting an attacker who satisfies the checked condition control the unchecked one.

### Impact Explanation
This crosses a tenant boundary using only actions available to any unprivileged user who can install the app once (no `api_secret_key`, no access token, and no privileged account needed): the attacker forges the tenant identity attached to webhook processing, causing the app to perform shop-specific side effects (e.g., data deletion/erasure on uninstall, order/customer state changes, cache/database updates keyed by `shop`) against a shop chosen by the attacker rather than their own. This matches the Critical bucket "cross-tenant access."

### Likelihood Explanation
Likelihood is realistic for apps whose webhook handlers rely on `WebhookMetadata#shop` as the sole tenant key and where at least one subscribed topic has a body that is static, empty, or otherwise not shop-specific (common for topics like `app/uninstalled`, `shop/redact`, or simple event pings). The only prerequisite is installing the app on an attacker-controlled store once and being able to send HTTP requests to the app's public webhook endpoint — both are standard unprivileged capabilities.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed content, or otherwise cryptographically tie the tenant identity to the verified payload, e.g. by having `Request#to_signable_string` incorporate the shop header, or by requiring the host application to independently verify that `shop` corresponds to a shop known to have triggered that specific `webhook_id`/event rather than trusting the header outright.

### Proof of Concept
1. Install the app on `attacker.myshopify.com` (a normal, unprivileged action).
2. Trigger/receive a genuine webhook from Shopify for a topic with a static/empty body, e.g. raw body `"{}"`, headers include a valid `shopify-hmac-sha256` computed over `"{}"` with the app's shared secret, and `shopify-shop-domain: attacker.myshopify.com`.
3. Replay this exact request to the app's webhook controller endpoint, but change only the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to `victim-shop.myshopify.com`, leaving `raw_body` and `hmac` untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the HMAC: [3](#0-2) 
5. The registered handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, performing the app's business logic as if it originated from the victim shop.
