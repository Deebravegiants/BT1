### Title
Webhook shop-domain header not covered by HMAC signature, allowing cross-tenant shop spoofing on replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, then trusts the `shop-domain` header — which is never part of the signed bytes — to identify which tenant the payload belongs to. This is the same bug class as the reported Solidity finding: a value that is *acted on* (the deadline / here, the shop identity) is not covered by the check that is supposed to gate the action (the deadline check / here, the HMAC).

### Finding Description
`HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`, and for webhook requests that method returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read straight from unauthenticated HTTP headers, with `shop` in particular becoming the tenant identity handed to the developer's webhook handler: [2](#0-1) 

`Registry.process` only checks the HMAC (over the body) and then immediately builds `WebhookMetadata` using `request.shop` from the unauthenticated header, with no cross-check that the header matches any property actually bound to the signature: [3](#0-2) 

Because the API secret (`Context.api_secret_key`) is shared across every shop that has installed a given app, an unprivileged user can install the app on their own store (no elevated credential needed — this is exactly the merchant-install flow the gem exists to support), receive a legitimate webhook (valid `raw_body` + HMAC signed with the app's own secret), and then resend that identical body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) will still return `true`, since it only checks `raw_body` against the shared secret, and `Registry.process` will dispatch the handler believing the payload originates from the victim shop.

The equality that should hold and doesn't:
`shop header trusted by the handler == shop identity actually bound by the HMAC`
In reality the HMAC binds nothing about `shop`, so any header value passes as long as the body+secret combination was ever valid for *some* shop under the same app.

### Impact Explanation
If the host application (as documented/intended by this gem's `WebhookMetadata#shop` value) uses the `shop` field returned by `Registry.process`'s handler callback to select which tenant's data to update, credit, or act on (a well within documented usage — see `docs/usage/webhooks.md` and `WebhookMetadata`), an attacker who is a legitimate (if malicious) merchant of the app can inject fabricated events attributed to any other shop, i.e., cross-tenant data corruption/action-forgery. This lines up with the "Critical – cross-tenant access" impact category, since the identity binding that should segregate shops is bypassed while the cryptographic check reports success.

### Likelihood Explanation
Likelihood is high for apps that trust `data.shop` from `WebhookMetadata` for tenant routing without independently re-validating it (e.g., against a known/installed-shop list) — which is the pattern the docs show. The only requirement is the attacker being an ordinary installer of the app (no `api_secret_key`, no stolen tokens, no privileged access), consistent with the "unprivileged internet user" threat model of this scan.

### Recommendation
Bind the tenant identity into the value that is cryptographically checked, not just the body:
- Compute/verify the HMAC over a canonical string that includes the `shop-domain` (and ideally `topic`, `webhook_id`) header value in addition to the raw body, rejecting the request if any of those headers do not match what Shopify actually signed for that delivery, or
- At minimum, document/require that consuming applications verify `data.shop` in `WebhookMetadata` against their own list of installed shops (with an active, matching session) before trusting it for any tenant-scoped action, and make this an explicit step in `Registry.process` rather than leaving it implicit.

### Proof of Concept
1. Attacker signs up for the app on their own store `attacker.myshopify.com`. The app's webhook endpoint receives a legitimate webhook: body `{"id":1}"`, headers include `x-shopify-hmac-sha256: <valid hmac over body with shared api_secret_key>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body and HMAC value to the same endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` is still valid because `to_signable_string` only returns `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which passes, and then invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), despite the payload never having been produced or signed for that shop.
