### Title
i128 overflow in `scaled_to_original` during accrual permanently freezes a whale-sized market before the borrow-index cap engages - (File: common/src/rates/scaling.rs)

### Summary
The integer-overflow bug class from CVE-2021-29338 maps onto XOXNO Lending's accrual engine. Every pool mutation first runs `global_sync` → `accrue_step`, which unscales `borrowed * borrow_index` and `supplied * supply_index` via `scaled_to_original` to compute utilization. That multiply panics with `MathOverflow` once `scaled × index` exceeds `i128::MAX`. The `MAX_BORROW_INDEX_RAY = 1e36` cap is checked only *after* this product is computed, so a sufficiently large book hits the `i128` value ceiling before the index cap can clamp growth. Once that line panics, every subsequent accrual panics too, permanently freezing the market.

### Finding Description
`accrue_step` computes utilization from unscaled values at `common/src/rates/simulate.rs:60-62`: [1](#0-0) 

`scaled_to_original` is a plain `Ray::mul`, which panics on `i128` overflow: [2](#0-1) 

The borrow-index cap exists but is applied to `new_index` only after `update_borrow_index` returns — and `accrue_step` reaches the overflowing `scaled_to_original` call *before* `update_borrow_index` runs, so the cap at `common/src/rates/index.rs:15-17` never gets a chance to engage: [3](#0-2) 

`global_sync` runs this on every entry into the pool (`contracts/pool/src/interest.rs:20-33`), so every verb — withdraw, repay, borrow, liquidate, `update_indexes` — hits the same panic first: [4](#0-3) 

The repo's own harness demonstrates the cliff: a billion whole 18-decimal tokens (`1e36` raw ray) at ~98% utilization on the XLM curve grows the index past ~170× within a few years; `borrowed_scaled × borrow_index` then exceeds `i128::MAX`, `update_indexes` reverts with `MathOverflow`, and withdraw/repay fail identically while `borrow_index < MAX_BORROW_INDEX_RAY`: [5](#0-4) 

### Impact Explanation
Permanent freezing of funds. Once `borrowed_scaled × borrow_index` (or `supplied_scaled × supply_index`) crosses `i128::MAX`, `accrue_step` panics inside `global_sync`, which every market verb executes first. No supplier can withdraw, no borrower can repay, and no liquidator can seize on that (hub, token) book — the market is bricked irreversibly because `last_timestamp` can never advance past the panic. All user funds in that market are locked indefinitely.

### Likelihood Explanation
The trigger is permissionless in mechanism but whale-gated in capital: an unprivileged address must supply (and, to accelerate, collateralize and borrow) on the order of `1e9` whole tokens of a high-decimal asset, then let the borrow index grow past ~170× at sustained high utilization. For realistic listed assets this requires extraordinary principal and years of steep-curve utilization, so likelihood is low — but no privileged action, parameter change, or oracle manipulation is needed; caps (`lift_caps` in the test mirrors supply-cap headroom) and utilization are reachable through ordinary `supply`/`borrow` calls, and `update_indexes` itself is permissionless. Medium severity.

### Recommendation
Make the unscale step saturation- or cap-aware instead of panicking inside accrual:
- In `accrue_step` / `Cache::calculate_utilization`, compute utilization via a saturating or widened path (`mul_div_floor_saturating` or `I256`-based division without materializing the `i128` product) so utilization simply clamps at `RAY` when the book value exceeds the representable range.
- Alternatively, clamp `borrowed`/`supplied` products by checking `scaled > i128::MAX / index` before multiplying and treating the market as fully utilized — the index cap and interest bookkeeping can then proceed normally and withdrawals/repayments remain possible.

```rust
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
