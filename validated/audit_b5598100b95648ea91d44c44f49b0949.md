**Analysis:**

The scenario described is not a race condition or cache-staleness bug — it's the documented, intentional behavior of the endpoint. In `get_by_height` (`api/src/blocks.rs:108-122`), `get_latest_ledger_info()` is fetched once and passed through consistently to bound the query, and `Context::get_block_by_height` reads `first_version`/`last_version` from the block info at that same point [1](#0-0) .

The `transactions` field is deliberately capped by `max_block_transactions_page_size`, independent of whether an upgrade transaction was just committed:

```rust
let max_txns = std::cmp::min(
    self.node_config.api.max_block_transactions_page_size,
    (last_version - first_version + 1) as u16,
);
``` [2](#0-1) 

This means `transactions.len() < last_version - first_version + 1` is an expected, normal outcome for any block whose transaction count exceeds the configured page size — not something specific to upgrade transactions or cache staleness. The API documentation for `get_block_by_height` explicitly states this: "Transactions are limited by max default transactions size. If not all transactions are present, the user will need to query for the rest of the transactions via the get transactions API" [3](#0-2) . Clients relying on `transactions.len() == last_version - first_version + 1` as an invariant are using the API incorrectly; the correct invariant is documented pagination, not automatic completeness.

There is also no separate "ledger-info cache that lags" in this path — `latest_ledger_info` and the block's `first_version`/`last_version` are read from the same underlying DB state within a single call, so there's no torn read between "last_version already reflecting the upgrade" and "transactions omitting it" beyond the documented page-size truncation.

Since this is a read-only reporting behavior governed by a documented pagination limit, it does not cross any custody boundary — it does not change ownership, transfer authority, upgrade authority, or freeze state of any asset, object, or resource account. A multisig approver relying on this endpoint without following the documented pagination contract is a client-side integration issue, not a custody-authority defect in the node/API code.
