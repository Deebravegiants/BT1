## Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string from the raw body only, while `shop`, `topic`, `api-version`, and `webhook-id` are taken verbatim from HTTP headers that are never part of the signed data. `Registry.process` trusts `request.shop` (and `request.topic`) to route the payload to a handler and to construct `WebhookMetadata`, breaking the binding `shop authenticated == shop used for tenant routing`.

## Finding Description
`HmacValidator.validate` verifies the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated headers: [3](#0-2) 

`Registry.process` then uses `request.topic` to select the handler and passes `request.shop` straight into `WebhookMetadata`, which app code uses as the tenant identifier for storing/updating data: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`, the app's client secret) is identical for every shop that installs the app, a valid HMAC for one shop's webhook body is also a valid HMAC for the same body claimed to originate from a different shop — the signature proves only "signed by this app's secret," never "this body belongs to this shop." This is exactly the "field acted on but not covered by the HMAC" identity-binding failure: the `shop` value verified by nothing is the same `shop` value used to select the tenant context in which the payload is processed.

## Impact Explanation
This is a cross-tenant access vulnerability. A malicious merchant who has installed the app on their own shop (Shop A) can trigger a legitimate, correctly-HMAC-signed webhook for content they fully control (e.g., `customers/create`, `orders/create` with attacker-chosen fields). Because the `x-shopify-shop-domain` header is not part of the signed bytes, the attacker can replay/craft the exact same body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header value with a victim shop's domain. The library will accept it as valid (`Utils::HmacValidator.validate` only checks the body) and hand it to the app's handler labelled as coming from the victim shop, resulting in attacker-controlled data being written/processed under another tenant's identity — a cross-tenant access/data-injection primitive that satisfies the Critical severity bar in this scope.

## Likelihood Explanation
High. Any merchant that installs the app can generate arbitrarily-signed bodies of their choosing (since Shopify signs webhooks for every installed shop with the same app secret), and the header substitution requires no cryptographic secret at all — only the ability to send an HTTP request with a modified header, which is trivial for any actor able to reach the app's public webhook endpoint (directly, or by racing/replaying their own legitimately delivered webhook).

## Recommendation
Bind the `shop` (and ideally `topic`) value into the signed data used for verification, or independently authenticate the shop domain (e.g., cross-check against a known/previously-registered shop for that specific webhook subscription/session) before using `request.shop` for tenant routing. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should not allow header-only fields that determine tenant context to bypass the integrity check that the HMAC is meant to provide.

## Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `customers/create`) with attacker-controlled body content.
2. Shopify delivers the webhook to the app's endpoint with a valid `x-shopify-hmac-sha256` computed over that body using the app's `client_secret`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request and resends it to the same endpoint, keeping body and HMAC identical but changing the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the HMAC: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the app to process attacker-controlled data as if it belongs to the victim's tenant.
