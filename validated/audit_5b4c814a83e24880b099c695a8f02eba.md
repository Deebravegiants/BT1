### Title
Unchecked ERC20 `transfer()` return value lets `placeOrder` credit escrow with tokens never received - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the predispatch path of `placeOrder`, the Tron variant of `IntentGatewayV2` sweeps input tokens from the `CallDispatcher` back to the gateway using a raw, ABI-encoded `IERC20.transfer` call routed through `ICallDispatcher.dispatch`, rather than OpenZeppelin's `SafeERC20.safeTransfer`. The boolean success value returned by `transfer()` is never inspected — only the outer low-level call's revert status is checked inside `CallDispatcher.dispatch` — so a token that returns `false` instead of reverting on a failed transfer will cause the escrow ledger (`_orders[commitment][token]`) to be incremented by the full `reducedInputs[i].amount` even though no tokens actually arrived at the gateway.

### Finding Description
`placeOrder`'s predispatch branch builds a `Call` whose `data` is `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` and pushes it into `transferCalls`, later dispatched via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`: [1](#0-0) 

`CallDispatcher.dispatch` only checks that the low-level `.call` itself did not revert; it never decodes/checks the boolean return value of the target function: [2](#0-1) 

Immediately after building this unchecked transfer call, the function unconditionally credits escrow with the *requested* amount, not a measured, post-transfer balance delta: [3](#0-2) 

This differs from the corresponding mainline EVM implementation, which re-reads `IERC20(token).balanceOf(address(this))` before and after the sweep and sets `order.inputs[i].amount` to the *measured* delta rather than trusting the transfer call blindly: [4](#0-3) 

The Tron variant has no equivalent balance-verification step after `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` — it commits `_orders[commitment][token] += reducedInputs[i].amount` before the sweep dispatch call even executes, based purely on the pre-sweep `balanceOf(dispatcher)` snapshot and the assumption that the encoded `transfer()` call succeeds semantically, not just syntactically.

### Impact Explanation
If the input token is a non-standard ERC20 that signals failure by returning `false` rather than reverting (this pattern is explicitly anticipated elsewhere in the codebase, e.g. the fee-on-transfer/return-value test mock at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2709-2724`), a failed sweep from the `CallDispatcher` back to the gateway would still be treated as a successful transfer by `CallDispatcher.dispatch`. The gateway would then hold an escrow accounting entry (`_orders[commitment][token]`) backed by no actual token balance. Subsequent fill, refund, or withdrawal flows that pay out based on `_orders[commitment][token]` would drain real funds from unrelated orders/users to satisfy this phantom balance — a fund-freezing/insolvency condition for the protocol's escrow accounting reachable directly from a single `placeOrder` transaction using a predispatch order structure.

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with a `predispatch.call` and `predispatch.assets` set (a supported, documented flow — "swap-then-escrow"), using any ERC20 token that returns `false` on transfer failure instead of reverting. No special privileges are required; the attacker only needs to supply or interact with such a token as an order input.

### Recommendation
Replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` call routed through `CallDispatcher` with a measured-balance verification (as already done in the mainline `evm/src/apps/IntentGatewayV2.sol`), or ensure the `Call`'s encoded data uses `SafeERC20`-equivalent semantics and that `_orders[commitment][token]` is only credited with the actually measured post-sweep balance delta, not the pre-sweep requested amount.

### Proof of Concept
1. Deploy a malicious/non-standard ERC20 whose `transfer()` returns `false` (without reverting) when called by the `CallDispatcher` for a specific recipient/amount condition (e.g., a blacklist or paused state toggled mid-transaction via the predispatch call's arbitrary calldata).
2. Call `placeOrder` with `predispatch.call` executing arbitrary logic that flips the malicious token into its "silently fail" mode, and `order.inputs` referencing that token.
3. `CallDispatcher.dispatch` executes the encoded `transfer()` call; the low-level call succeeds (returns `true` for `success`) even though the token's internal logic returned `false` and moved no funds.
4. `_orders[commitment][token] += reducedInputs[i].amount` is credited despite the gateway holding zero of that token.
5. The attacker (or any solver) can later trigger withdrawal/refund/fill logic that pays out against this phantom `_orders` balance, draining real tokens from the gateway's other escrowed funds.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
