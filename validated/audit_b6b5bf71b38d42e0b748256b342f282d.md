### Title
Missing per-sender validation on user-supplied `MessageID` in `savedCallbacks` allows cross-user response hijacking - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Pyth confidence-interval bug is a "trust external input without bounding/validating it" class of issue. The closest reachable analog in an unprivileged-actor path (the internet-facing WebAPI gateway) is in `handler.go`'s `HandleLegacyUserMessage`/`handleWebAPITriggerMessage`: the gateway trusts the caller-supplied `MessageID` as a unique correlation key for routing DON responses back to callbacks, without validating that it is unique to the sender or scoping it by sender identity.

### Finding Description
`HandleLegacyUserMessage` accepts a message from any external, unauthenticated (or only signature-authenticated but otherwise arbitrary) caller and stores the pending callback keyed solely by the attacker-controlled `msg.Body.MessageID`: [1](#0-0) 

Critically, `MessageID` is not validated for uniqueness or bound to the sender — it is only checked for length/null-byte constraints in `Message.Validate`: [2](#0-1) 

When a DON node later replies, the response is matched purely on `MessageID` and delivered to whichever callback is currently stored under that key, with no verification that the response corresponds to the same requester or request payload: [3](#0-2) 

Because the map is a global `map[string]*savedCallback` shared across all users hitting the gateway, and insertion at line 412 unconditionally overwrites any existing entry for the same ID, a second caller who submits a request reusing an in-flight `MessageID` silently replaces the first caller's callback registration. This is directly analogous to using unchecked/unbounded external data (the Pyth price) for a security-relevant decision without validating it falls inside an expected, trusted range — here the "range" that should be enforced is per-sender uniqueness/ownership of the correlation ID, but the system accepts it at face value.

The staleness check in the same function similarly only validates a lower bound (`too old`) and never enforces an upper bound (future timestamps), mirroring the report's core complaint about not fully validating a value against its expected valid interval: [4](#0-3) 

### Impact Explanation
If an unprivileged client can predict or brute-force another in-flight `MessageID` (e.g., by observing timing, or if application-layer IDs are low-entropy/sequential from the calling web app), it can overwrite the victim's `savedCallbacks` entry. When the DON node responds to the victim's original request, the response gets routed to the attacker's registered callback instead of the victim's — a concrete cross-user response confusion, potentially exposing response data (which may include private computed results) to an unauthorized party, or causing legitimate users to never receive their result (denial of service for that request).

### Likelihood Explanation
Exploitability depends on the attacker being able to guess or observe a victim's in-flight `MessageID` before the DON responds (a race window bounded by `CallbackMaxAgeSec`, default 120s). Since `MessageID` is caller-supplied and only length/format validated — never checked for collision against the currently pending set — likelihood is non-trivial for any deployment where message IDs are not high-entropy random values generated by the trusted client SDK.

### Recommendation
- Scope `savedCallbacks` keys by `(sender, MessageID)` rather than `MessageID` alone, and reject/`409`-style-error insertion attempts when the key is already in-flight for a different sender.
- Enforce upper-bound (future) timestamp validation in `HandleLegacyUserMessage`, not just staleness, matching the "reject if outside the interval" remediation pattern used for the Pyth fix.
- Consider requiring the gateway (not the caller) to mint the correlation ID, or cryptographically bind it to the sender's signature so it cannot be replayed/collided by another sender.

### Proof of Concept
Not independently verified end-to-end (would require running the gateway with two concurrent legacy requests sharing a `MessageID` from different signers and confirming the second overwrites the first's callback registration before the first DON response arrives). The described overwrite-on-insert behavior at `handler.go:412` and the lack of sender binding in `Message.Validate` were confirmed by direct code reading, but I did not execute a live race condition test against a running gateway instance, so real-world exploitability (timing window, ID predictability) is not empirically confirmed here.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	return nil
}
