I found a concrete analog: `withdraw()` in `IntentGatewayV2.sol` performs a low-level external token call *before* decrementing the corresponding escrow accounting, inside a per-token loop — a check-effects-interactions violation reachable from a permissionless, relayer-delivered message (`onAccept`/`onGetResponse`), which is exactly the bug-class the report highlights: shared state (`_orders[commitment][token]`) is read and used to authorize a transfer while the "cleanup" of that same state (the decrement) has not yet happened, and a malicious token can re-enter mid-flight to observe/exploit that stale state before it is retired — analogous to the UAF pattern where a buffer/state is used by one in-flight operation while its owning operation's cleanup callback hasn't run yet.

### Title
Escrow token transfer executed before balance decrement in `withdraw()` allows reentrant double-spend of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()`, reachable via `onAccept` (RedeemEscrow/RefundEscrow messages delivered by any relayer) and via `onGetResponse` (GET response delivered by any relayer), performs `token.call(...transfer...)` for each escrowed token and only decrements `_orders[body.commitment][token]` *after* that external call returns. [1](#0-0) 

### Finding Description
The loop in `withdraw()` checks `_orders[body.commitment][token] == 0` to authorize a payout, performs an unguarded low-level `.call` to the token contract, and only then subtracts `amount` from `_orders[body.commitment][token]`. [2](#0-1) 
`withdraw()` is `internal` and is invoked from two externally-triggered, permissionless message-delivery paths: `onAccept` (only guarded by `onlyHost`, called whenever the host delivers a `RedeemEscrow`/`RefundEscrow` POST request that any relayer submitted proof for) and `onGetResponse` (called whenever the host delivers a GET response, again submitted by any relayer). [3](#0-2) [4](#0-3) 
`_filled[body.commitment]` is set at the top of `withdraw()`, but this mapping is never checked inside `withdraw()` itself — it only guards the separate `fillOrder` path (per the CEI fix documented and tested elsewhere in the repo for `_fillSameChain`/`_fillCrossChain`), not `withdraw()`. [5](#0-4) 
Because escrowed tokens in `_orders` are arbitrary tokens supplied by the order (not restricted to a vetted allowlist visible in this excerpt), a token with a transfer hook (ERC-777-style callback, or a malicious/proxy token) can re-enter the host's message-delivery path during the `.call`. If the same commitment/GET-response can be delivered again (e.g. the non-membership/duplicate-response guard in the host is at a different layer than `withdraw`'s own bookkeeping, or if `_orders[body.commitment][token]` still holds its pre-decrement value for a *different* token index in the same call, or the response can be resubmitted before host-level replay protection catches it), the stale, not-yet-decremented `_orders[body.commitment][token]` value permits an additional transfer of the same escrowed balance before it is retired — a use of shared escrow-accounting "state" while it is still logically in-flight, mirroring the analog bug class of consuming a resource before its owning operation has finished tearing it down.

### Impact Explanation
A successful reentrant call during the token transfer loop can drain escrowed input tokens or transaction fees for a commitment beyond what was legitimately owed, resulting in direct theft of escrowed user funds from `IntentGatewayV2` — a concrete theft-of-funds impact.

### Likelihood Explanation
Exploitability depends on whether: (1) an ERC-777/callback-bearing or malicious token can be placed as an order's input token, and (2) the host-level replay/duplicate-delivery protections (`_requestReceipts`/`_responseReceipts` in `EvmHost`) do not fully close the reentry window before `withdraw`'s own per-token loop and fee redemption complete. I could not confirm from the available context whether `_orders` tokens are restricted to a safe allowlist, nor could I fully trace whether `EvmHost.dispatchIncoming`'s receipt-set-before-call ordering (which does follow CEI) fully forecloses a second `onGetResponse`/`onAccept` delivery for the same commitment during the token `.call`. This uncertainty affects confidence in likelihood; without confirming an allowlist or full re-entrancy trace this should be treated as medium-to-high rather than certain.

### Recommendation
Apply checks-effects-interactions in `withdraw()`: decrement `_orders[body.commitment][token]` (and delete fee entry) *before* making the external `.call`, matching the pattern already used correctly in `EvmHost.dispatchIncoming` (receipt set before external call) and in the CEI fix applied to `_fillSameChain`/`_fillCrossChain`. Additionally consider a reentrancy guard on `withdraw()` itself, and verify/enforce that escrowed input tokens are restricted to contracts without arbitrary callback hooks, or use `SafeERC20.safeTransfer` consistently instead of raw `.call`.

### Proof of Concept
Conceptual (not confirmed executable without further tracing of `EvmHost` replay-protection interplay):
1. Attacker crafts an order whose input token is a malicious ERC-20/777-style token with a transfer hook.
2. Order is placed and escrowed normally into `_orders[commitment][maliciousToken]`.
3. A `RedeemEscrow`/`RefundEscrow` message (or GET response) is delivered, entering `withdraw()`.
4. During `token.call(...transfer...)` to the malicious token, the token's hook re-enters the ISMP delivery path (e.g., triggers another `onAccept`/`onGetResponse` for the same or a related commitment) before `_orders[body.commitment][token] -= amount` executes.
5. Because the decrement has not yet occurred, the reentrant path's `_orders[...] == 0` check still passes, causing a second payout for tokens that should have already been retired, draining escrow beyond the legitimate amount.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
