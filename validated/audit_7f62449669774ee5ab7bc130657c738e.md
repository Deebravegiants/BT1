### Title
Malicious multi-input order can permanently freeze all escrowed tokens via a reverting/blacklistable ERC-20 in `IntentsBase._withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`placeOrder` lets any user pick arbitrary ERC-20 contracts as `order.inputs` [1](#0-0) . When the order is later settled (fill, cross-chain refund, or cancel), `_withdraw` iterates over *all* escrowed tokens for the commitment and releases them in a single, atomic loop of `safeTransfer` calls [2](#0-1) . If the order creator includes a malicious/blacklistable token as one of several inputs and later blocks the gateway (or the beneficiary) from receiving it, that single failing transfer reverts the whole settlement, permanently freezing every other legitimate token escrowed under the same commitment — this mirrors the Mantra DEX bug class where one poisoned asset in an aggregated payout locks unrelated, legitimate rewards.

### Finding Description
`placeOrder` accepts an arbitrary list of ERC-20 addresses as `order.inputs`, with no allow-list or validation beyond non-zero amount and no-duplicate checks [1](#0-0) . These tokens are escrowed per-commitment in `_orders[commitment][token]` [3](#0-2) .

Settlement of that escrow — whether via a successful cross-chain fill (`onAccept` → `RedeemEscrow`), a cross-chain cancel refund (`onAccept` → `RefundEscrow`, or `onGetResponse`), or a same-chain cancel — always funnels through the same `_withdraw` function, which loops over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one in a single transaction [2](#0-1) . `_withdraw` is invoked from `_cancelSameChain`, from `onAccept` (RedeemEscrow/RefundEscrow), and indirectly from `onGetResponse`'s cancel-from-source path [4](#0-3) [5](#0-4) .

Because `safeTransfer` reverts on failure and there is no per-token try/catch, if any single token in `body.tokens` is designed to revert or is blacklist-capable (e.g., a Compound/USDC-style blacklist token, a pausable token, or a token that self-destructs its transfer logic once a target condition is met), the attacker (as the order creator, who fully controls both the token contract and which tokens are listed as inputs) can:

1. Place an order with two inputs: one legitimate, valuable token, and one malicious ERC-20 they control.
2. Wait for a solver to fill the order on the destination chain (releasing real value to the user) — at which point `RedeemEscrow` is dispatched back to the source chain to pay the solver from escrow.
3. Before/at delivery, blacklist the IntentGateway contract address (or the solver beneficiary) in the malicious token's `transfer` function.
4. The `onAccept` call to `_withdraw` reverts on the malicious token's transfer, which reverts the *entire* transaction — including the legitimate token's transfer to the solver.
5. Since the ISMP message delivery attempt failed, the solver/relayer cannot re-deliver a corrected payout (the message is architecturally atomic and re-delivery hits the same revert), permanently freezing the legitimate token in escrow.

The identical mechanism blocks refunds: an attacker can use the same trick to prevent `_cancelFromDest`/`onGetResponse`/`_cancelSameChain` refund paths from ever completing, exactly paralleling the Mantra DEX report's second impact ("the owner/user cannot close/refund a malicious position because the aggregated payout reverts").

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged order creator. A single self-deployed malicious ERC-20 combined with a legitimate high-value token in the same order's `inputs` array can be used to lock the legitimate token in escrow indefinitely, since:
- The solver's payout (`RedeemEscrow`) and the user's refund path (`RefundEscrow`/same-chain cancel) both go through the same all-or-nothing `_withdraw` loop.
- There is no owner/governance path in `IntentsBase`/`IntentGatewayV2` to force-release or skip a poisoned token per-commitment; `SweepDust`/`_sweepDust` only handles protocol-owned dust, not order escrow [6](#0-5) .
- This qualifies as Medium/High severity permanent freezing of funds for any counterparty (solver or user) whose legitimate assets are bundled in the same commitment as the poisoned token.

### Likelihood Explanation
Likelihood is high in the sense that any user can trivially deploy a blacklist-capable/reverting ERC-20 and construct a multi-input order pairing it with real value; no special privilege, front-running, or governance compromise is required — only that a solver or counterparty engages with an order whose input token list includes an untrusted, attacker-controlled asset. This is analogous to why the original Mantra DEX report was rated High: an attacker-supplied asset unilaterally weaponized to revert an aggregated fund-release call.

### Recommendation
- In `_withdraw`, isolate each token transfer so a single failing/malicious token cannot block release of the others — e.g., wrap each `safeTransfer` in a low-level call and, on failure, credit the amount to a per-beneficiary/per-token "claimable" balance that can be pulled separately, rather than reverting the whole batch.
- Alternatively, require an allow-list of vetted input tokens for `placeOrder`, or cap/validate that flagged/incompatible tokens cannot be combined with legitimate ones in a single commitment.
- Ensure the `_filled` state transition (marking the order settled) is not rolled back by a downstream token-transfer failure, so retried settlement doesn't get stuck reprocessing the same poisoned path.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer`/`transferFrom` can be made to revert for any address the attacker chooses (e.g., via an owner-controlled blacklist mapping checked in `_beforeTokenTransfer`).
2. Attacker (as `msg.sender`) calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 10_000e6}, {token: EvilToken, amount: 1} ]`, targeting a cross-chain destination [7](#0-6) .
3. A solver fills the order on the destination chain, dispatching `RedeemEscrow` back to source with `body.tokens = [USDC, EvilToken]` and `beneficiary = solver`.
4. Before the message is delivered on source, attacker calls `EvilToken.setBlacklist(gatewayAddress, true)` (or configures it to always revert).
5. Relayer delivers the message; `onAccept` → `_withdraw` transfers USDC successfully, then reverts on `EvilToken.safeTransfer(solver, 1)` [8](#0-7) ; the whole `onAccept` call reverts, so USDC is never actually released (state changes rolled back) and the ISMP delivery is recorded as failed.
6. Every re-delivery attempt hits the same revert since `EvilToken` continues blocking the gateway, permanently freezing the solver's USDC payout in escrow, with no owner override to force-settle only the USDC leg. [2](#0-1)

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
