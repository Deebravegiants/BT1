### Title
`IntentGatewayV2.setParams` (Tron variant) lacks bounds validation on `protocolFeeBps`/`surplusShareBps`, allowing fee > 100% to underflow and permanently freeze escrowed order funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` exposes a `setParams` function that overwrites the entire `Params` struct — including `protocolFeeBps` — with **no validation whatsoever**, unlike the canonical EVM `IntentsBase._validateParams`/`_updateParams` path which explicitly bounds `protocolFeeBps < 10_000` and `surplusShareBps <= 10_000`. [1](#0-0) [2](#0-1) 

### Finding Description
`setParams` on the Tron `IntentGatewayV2` is guarded only by an `_admin` check, not by any input validation, and it directly assigns the caller-supplied `Params` to `_params`:
```solidity
function setParams(Params memory p) public {
    if (msg.sender != _admin) revert Unauthorized();
    _admin = address(0);
    _params = p;
}
``` [3](#0-2) 

Compare this to the audited/hardened EVM path, `IntentsBase._validateParams`, which is invoked from `_updateParams` before any assignment and explicitly caps `protocolFeeBps` and `surplusShareBps`:
```solidity
function _validateParams(Params memory p) internal view {
    if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
    if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
    if (p.surplusShareBps > 10_000) revert InvalidInput();
    if (p.protocolFeeBps >= 10_000) revert InvalidInput();
    if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
}
``` [2](#0-1) 

Once `protocolFeeBps` (a value with denominator 10_000, same convention as the audit report's `_withdrawalFee`) is set above 10_000 via the unguarded Tron `setParams`, the fee-deduction arithmetic in `placeOrder` underflows:
```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;   // reverts if protocolFee > originalAmount
``` [4](#0-3) 

This is the exact same bug class as the referenced Y2K report: a percentage/basis-point fee parameter that is set once with no maximum check, and whose overflow value causes an unconditional underflow revert in the core value-transfer arithmetic — halting the affected contract path.

### Impact Explanation
Because `_params` is set once at deployment/initialization by `_admin` via `setParams` with `_admin` being permanently zeroed afterward, an incorrectly configured `protocolFeeBps` (≥ 10_000) can **never be corrected** — there is no other setter for `_params` on this Tron variant besides governance's `UpdateParams` request path (`onAccept`), and if that path also flows through the same unguarded field, or if `_admin` has already been zeroed before the mistake is caught, the contract is permanently bricked for `placeOrder`. Every user attempting to place a new order on this gateway hits the underflow revert, is unable to escrow funds or use the intent flow, and any escrow logic dependent on `protocolFeeBps` being sane fails — this is a denial-of-service on the "unprivileged message dispatcher... intent solver" path described in the analog scope, i.e., ordinary users calling `placeOrder` cannot use the gateway at all, freezing the intent function of the affected chain.

### Likelihood Explanation
This requires an admin-set value; however unlike the EVM path, there is **no code-level defense** against a fat-fingered or malicious value on Tron, whereas the audited EVM path was hardened after review (evidenced by the presence of `_validateParams` bounds and dedicated revert tests `testRevert_SetParams_ProtocolFeeBpsTooHigh`, `testRevert_UpdateParams_DestinationFeeBpsTooHigh`). The Tron contract, being a distinct, apparently unaudited fork/duplicate of the EVM `IntentGatewayV2`, was not patched with the same protection, so a single incorrect deployment-time parameter permanently halts the contract with no possible correction once `_admin` self-zeroes. [5](#0-4) 

### Recommendation
Add the same bounds checks used in `IntentsBase._validateParams` to the Tron `setParams` function before assignment — reject `p.protocolFeeBps >= 10_000` and `p.surplusShareBps > 10_000` (and ideally the same host/dispatcher/oracle code-length checks) — so a malformed `protocolFeeBps` cannot be committed and subsequently brick `placeOrder`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and, while `_admin` is still set, call `setParams` with `Params.protocolFeeBps = 15000` (150%). [3](#0-2) 
2. `_admin` is zeroed, so `setParams` can never be called again to fix the value.
3. Any user calls `placeOrder` with a nonzero-fee destination; `protocolFee = (amount * 15000) / 10_000` exceeds `originalAmount`, so `reducedAmount = originalAmount - protocolFee` underflows and reverts. [4](#0-3) 
4. Every `placeOrder` call to this gateway now permanently reverts — the intent-gateway is fully bricked with no recovery path, since the only parameter setter is the one-time, unguarded `setParams`.
