## Analysis

The strongest analog to the reported bug class (a "reserve then commit" value checked via a non-atomic read-then-write, allowing two concurrent requests to both pass the same gate) is the JWT replay guard in `WorkflowMetadataHandler.Authorize`, used by the gateway's HTTP trigger flow to authenticate unprivileged, internet-facing workflow-execution requests.

### Title
Non-atomic check-then-record JWT replay guard allows duplicate/replayed workflow-trigger authorization under concurrent requests - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
`Authorize` is meant to guarantee that a given JWT (identified by its `jti` claim) can authorize exactly one gateway-routed workflow execution request. It does so with two separate, independently-locked calls into `jwtReplayCache`: `isReplay()` (read lock) followed later by `recordUsage()` (write lock), with unrelated authorization-key lookups happening in between and no lock held across the whole sequence.

### Finding Description
`Authorize` performs:
1. `h.jwtCache.isReplay(claims.ID)` — acquires `RLock`, checks map, releases lock.
2. Authorized-key lookups against `h.authorizedKeys`.
3. `h.jwtCache.recordUsage(claims.ID)` — acquires `Lock`, writes the map, releases lock. [1](#0-0) 

`isReplay` and `recordUsage` are each atomic on their own, but the *combination* — check, then act — is not atomic across the whole `Authorize` call: [2](#0-1) 

This is structurally identical to the `currentWithheldETH` bug: the guard variable (`currentWithheldETH` / the replay cache) is checked for availability, but the "commit" that would prevent a second caller from also passing the check happens strictly after other work, in a separate critical section. If two `HandleUserTriggerRequest` calls carrying the same JWT (same `jti`) reach `Authorize` concurrently, both can execute `isReplay` before either executes `recordUsage`, and both will see `exists == false`, both will pass the replay check, and both will be granted an `AuthorizedKey`, resulting in two accepted triggers for a signature meant to be single-use.

The test suite only demonstrates the sequential (non-concurrent) case: a second call with the same JWT after the first completes is rejected. [3](#0-2) [4](#0-3) 
It does not cover truly concurrent submission of the same JWT, which is the scenario where the TOCTOU gap is exploitable.

### Impact Explanation
A successful race lets an unprivileged external caller who possesses one signed JWT (e.g., captured/replayed via retried HTTP calls, proxies, or client-side retries with the same signed request) get it accepted more than once by the gateway before the replay cache is updated, defeating the single-use guarantee. Depending on downstream processing, this could result in duplicate/unauthorized triggering of a workflow execution using credentials/signatures intended to authorize only one run — i.e., request impersonation / unauthorized job run, matching the accepted impact classes for this exercise.

### Likelihood Explanation
Exploitability requires the attacker (or an unintentional duplicate submission, e.g., client retry/proxy fan-out) to send the same signed JWT concurrently to the gateway. This is plausible for internet-facing HTTP trigger endpoints where request replays/retries are common, and the race window (RUnlock → intervening map lookup → Lock) is small but real and directly analogous to the reported bug class. I could not fully verify from the index whether `HandleUserTriggerRequest` in `http_trigger_handler.go` wraps the `Authorize` call in any additional per-JWT/per-request serialization lock that would close this window — the tool budget was exhausted before I could inspect that call site in full. This is a material uncertainty: if such serialization exists there, the race is not reachable through that call path.

### Recommendation
Merge the check-and-record into a single atomic operation under one lock, e.g. add a `TryRecord(jti) bool` method on `jwtReplayCache` that acquires the write lock once, checks for existence, and, if absent, inserts and returns success — eliminating the gap between "isReplay" and "recordUsage". Call this single atomic method immediately upon receiving the JWT, before any authorization-key lookups, in `Authorize`.

### Proof of Concept
Not verifiable purely via static review; would require confirming whether `http_trigger_handler.go`'s `HandleUserTriggerRequest` serializes concurrent calls with identical `jti`/request IDs before invoking `Authorize`. Given the reasoning-effort/tool budget was exhausted before this could be checked, this should be validated by writing a concurrency test that calls `WorkflowMetadataHandler.Authorize` (or `HandleUserTriggerRequest` with the same signed JWT) from two goroutines simultaneously and asserting that at most one succeeds — analogous to `TestRequestReplayGuard_ConcurrentAccess` in the unrelated (and correctly atomic) vault `RequestReplayGuard`: [5](#0-4) 
Note that the vault package's `RequestReplayGuard.CheckAndRecord` (a single atomic check-and-insert under one lock) is the correct pattern that `jwtReplayCache` should follow but currently does not. [6](#0-5)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func TestRequestReplayGuard_ConcurrentAccess(t *testing.T) {
	guard := NewRequestReplayGuard()
	futureExpiry := time.Now().UTC().Unix() + 100

	const goroutines = 100
	results := make([]error, goroutines)
	var wg sync.WaitGroup
	wg.Add(goroutines)

	for i := range goroutines {
		go func(idx int) {
			defer wg.Done()
			results[idx] = guard.CheckAndRecord("same-digest", futureExpiry)
		}(i)
	}
	wg.Wait()

	successCount := 0
	duplicateCount := 0
	for _, err := range results {
		if err == nil {
			successCount++
		} else {
			require.ErrorIs(t, err, ErrRequestAlreadySeen)
			duplicateCount++
		}
	}

	assert.Equal(t, 1, successCount, "exactly one goroutine should succeed")
	assert.Equal(t, goroutines-1, duplicateCount, "all others should be rejected as duplicates")
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
