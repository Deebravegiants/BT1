### Title
Signed `verifying_contract` sourced from mutable global singleton instead of caller-validated environment - ([File: packages/internal-utils/src/utils/messageFactory.ts])

### Summary
`makeSwapMessage()` / `makeEmptyMessage()` embed `verifying_contract` (and NEP413 `recipient`) into the exact payload that gets signed by the user's wallet, but instead of taking this value as a caller-supplied, validated argument, they read it at call time from the mutable module-level singleton `config` exported by `packages/internal-utils/src/config.ts`. Any code in the same JS process/runtime that calls the exported `configureSDK()` mutates this shared global (`export let config`), which silently changes what contract every subsequent `makeSwapMessage()` caller signs against — mirroring the reported Storm bug class where a setting intended for one narrow feature (`skip_tls_validation` for Prometheus) leaked via a process-wide mutable side effect (`SSLContext.setDefault`) and silently altered unrelated call sites.

### Finding Description
- `config` is declared as a mutable, exported, module-scoped singleton: `export let config: SDKConfig = { env: configsByEnvironment.production, ... }` [1](#0-0) .
- `configureSDK()` reassigns this shared global for the entire process: `config = { ...config, env: resolveEnvConfig(env) }` [2](#0-1) . It is exported from the package's public entry point for consumer use [3](#0-2) .
- `makeSwapMessage()` reads `config.env.contractID` directly, at call time, with no parameter to override it: `verifying_contract: config.env.contractID` (used for the ERC191/SOLANA/STELLAR/TON_CONNECT/TRON payload) and `recipient: config.env.contractID` (used for NEP413) [4](#0-3) .
- This is inconsistent with the rest of the codebase's own signing path: `IntentPayloadBuilder`, which is the SDK's dedicated payload builder, captures `verifyingContract` from an explicitly passed, per-instance `EnvConfig` at construction time (`this.verifyingContract = this.envConfig.contractID`) and uses it deterministically per-instance [5](#0-4) , and `IntentsSDK` resolves and stores its own immutable `envConfig` per instance [6](#0-5) .
- Because `messageFactory.makeSwapMessage` is exported from the package's public surface (`export * as messageFactory from "./utils/messageFactory"` [7](#0-6) ), any dApp/integrator process that (a) hosts more than one environment/tenant in the same runtime, or (b) calls `configureSDK()` from one code path (e.g., to point another SDK instance at "stage") mutates the same singleton read by `makeSwapMessage` on an unrelated code path. The result: the value embedded into, and signed as part of, the wallet message no longer matches the environment the caller validated/displayed/intended — the wallet ends up cryptographically signing a message bound to a different `verifying_contract`/`recipient` than the one the calling code actually validated against.

This breaks the equality "a signature is bound to the environment/contract that was validated" — exactly the class called out as reachable High-impact: *"a signature bound to the wrong contract, signer, or nonce."*

### Impact Explanation
If `configureSDK()` is invoked anywhere in a shared process (a common integration pattern for backend services or multi-tenant frontends that need to support both `production` and `stage`, or that create multiple `IntentsSDK` instances with different `env`), every subsequent `makeSwapMessage()`/`makeEmptyMessage()` call — regardless of which logical session/tenant it belongs to — signs against whichever environment was last set globally. A user could be shown/validated one environment's contract while their wallet signature is actually computed and bound against a different contract ID embedded in the very payload being signed. Since `verifying_contract`/`recipient` is a security-critical field checked on-chain by the intents contract, this can result in a signature that is rejected by the intended contract (funds/intent stuck) or, in constructed multi-environment deployments, processed against the wrong deployment's contract, contrary to what the caller's own environment validation (`envConfig`) actually confirmed.

### Likelihood Explanation
This requires no privileged or malicious actor — it is triggered purely by ordinary, documented use of the public API: any process that constructs more than one environment context (multiple `IntentsSDK` instances, or a server handling both `stage` and `production` traffic) and calls the exported `configureSDK()` will encounter the mismatch deterministically, not via attacker action against the contract logic itself, but via a foreseeable, reachable API-shape defect (shared global mutable state read by a function that signs data). No external RPC/relayer/bridge trust assumption is required — it is entirely internal to `internal-utils`.

### Recommendation
Change `makeSwapMessage`/`makeEmptyMessage` to accept an explicit `envConfig`/`contractID` parameter (mirroring `IntentPayloadBuilder`'s pattern of capturing per-instance `envConfig`), rather than reading from the mutable global `config` singleton, so that the value embedded in the signed payload is always the same value that the calling code resolved and validated.

### Proof of Concept
1. Application starts two logical contexts in one Node process: `sdkA = new IntentsSDK({ env: "production", ... })` for tenant A, and elsewhere calls `configureSDK({ env: "stage" })` (a documented, exported API) to configure a second area of the app for tenant B.
2. Tenant A's flow calls `messageFactory.makeSwapMessage({ innerMessage })` expecting `verifying_contract` to be `"intents.near"` (production), matching what was validated/shown to Tenant A's user.
3. Because `config` is a shared, mutated global (`config.env.contractID`) [4](#0-3) , the produced payload instead contains `verifying_contract: "staging-intents.near"`.
4. The user's wallet signs this payload, producing a valid signature bound to the staging contract while the application believed/validated it was operating in production — the signature is now bound to a contract different from the one the caller's own validated `EnvConfig` specified.
