### Title
Interest accrual overflow permanently freezes a whale market before the borrow-index cap engages — (File: common/src/rates/index.rs)

### Summary
The MariaDB segfault class (crash on reachable input) maps onto XOXNO Lending as a permanent market freeze: once a large market accrues long enough that `borrowed * new_borrow_index` exceeds `i128::MAX`, every accrual panics with `MathOverflow` inside `calculate_supplier_rewards`, so `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, and `liquidate` all revert forever for that market. The `MAX_BORROW_INDEX_RAY` ceiling in `update_borrow_index` never engages because the value overflow trips first.

### Finding Description
Accrual runs `global_sync` → `accrue_chunk` → `accrue_step`, which calls `calculate_supplier_rewards`. There, `let new_total_debt = borrowed.mul(env, new_borrow_index)` ( [1](#0-0) ) computes `scaled_debt * index` in RAY. `borrowed` is already scaled to RAY (27 decimals beyond asset units), so for a large book the product overflows `i128` and `Ray::mul` panics with `GenericError::MathOverflow`. The index itself is capped at `MAX_BORROW_INDEX_RAY` only *after* this multiplication succeeds ( [2](#0-1) ), so the cap cannot rescue the market. `scaled_to_original` is a bare `scaled.mul(index)` ( [3](#0-2) ) with no saturation on this path.

Every position verb accrues first: `global_sync` is invoked at the head of pool operations ( [4](#0-3) ), and the controller's `update_indexes`, `repay`, `withdraw`, `liquidate`, and `clean_bad_debt` all route through pool calls that accrue. Once the product overflows, no subsequent call can skip accrual — the panic repeats identically at any later timestamp, so the freeze is permanent rather than a transient DoS. `recapitalize` also accrues via the pool call, so the documented shortfall-recovery path is equally dead.

The existing harness test pins exactly this: at 98% utilization on the XLM rate curve with a billion-unit 18-decimal market, `update_indexes` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and both `withdraw` and `repay` fail identically afterward — "the market is frozen: exits and repayments accrue first and hit the same panic. The index cap never engages" ( [5](#0-4) ). The test also notes the claimed bound in `docs/reference/formulas.md` is wrong, i.e., the cliff is reachable sooner than documented.

### Impact Explanation
Permanent freezing of user funds and protocol insolvency for the affected market: suppliers can never withdraw, borrowers can never repay, liquidators cannot liquidate underwater accounts, and `clean_bad_debt`/`recapitalize` cannot recover or refill the market. All tokens held by the pool for that `(hub, token)` book are stranded, including unclaimed revenue.

### Likelihood Explanation
Reachable by an unprivileged address via `supply`, `borrow`, and `update_indexes` alone, but the precondition is heavy: a whale-scale position (on the order of 10^27 raw units ≈ a billion 18-decimal tokens, or proportionally less for larger effective indexes) sustained near maximum utilization for years, since the overflow needs `borrowed_shares * borrow_index > i128::MAX` (~1.7e38, i.e., debt value above ~170 RAY-units). Caps and real-world token supplies make this unlikely but not impossible for high-supply assets, and no governance action can reverse it once crossed. Medium-to-low likelihood, critical severity.

### Recommendation
Make the value computation in `calculate_supplier_rewards` saturate or widen instead of panicking: clamp `borrowed` or the index to `MAX_BORROW_INDEX_RAY` *before* multiplying, or compute `new_total_debt` via `mul_div_floor_saturating`-style saturating arithmetic and cap the index when the product would overflow. Additionally, make `accrue_chunk` detect the would-be-overflow case and clamp `borrow_index` to `MAX_BORROW_INDEX_RAY` so accrual degrades to capped-index behavior rather than trapping. The scale boundary should be enforced consistently — currently `update_borrow_index` caps the index but the RAY-value ceiling in `scaled_to_original` fires first.

### Proof of Concept
See the pinned reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

1. `supply(BOB, "BIG18", 10^9 * 10^18)`; `borrow(ALICE, "BIG18", 98% of that)` — both ordinary unprivileged calls.
2. Advance ledger time year by year, calling `update_indexes` (permissionless).
3. Within the XLM-curve steep segment the index grows past ~170×; `borrowed.mul(new_borrow_index)` overflows inside `calculate_supplier_rewards` and `update_indexes` returns `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
4. `withdraw(BOB, "BIG18", 1)` and `repay(ALICE, "BIG18", ...)` return the same `MATH_OVERFLOW` — the market is permanently frozen.

One caveat: this cliff is already pinned by an in-repo test, so it may be a known limitation; however the test itself asserts the documented bound in `formulas.md` is incorrect, and the freeze affects exits/recovery paths that invariants claim stay open, so it is reported as a live analog rather than a documented safe-by-design bound.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
