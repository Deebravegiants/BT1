Found a strong analog. The `pallet-bandwidth` gate exhibits exactly the CWE-639 bug class described in the Keycloak advisory: a check/credit is keyed on a coarse identifier pair that isn't bound to the actual verified sender/entity, letting one entity consume or attribute state intended for another.

### Title
Bandwidth allowance is keyed by an attacker-controlled `(app_chain, app)` pair independent of the actual paying/verified source, enabling cross-tenant bandwidth theft and griefing - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth`'s `Allowance` storage credits and drains a `(app_chain, app)` bucket where `app_chain` and `app` are taken verbatim from the purchase message body (`msg.chain`, `msg.app`), not from any property that is cryptographically bound to who is entitled to that bandwidth. Anyone who can dispatch an ISMP POST from a registered `BandwidthManager` on any registered source chain controls both fields, so the "identity" the credit is scoped to is fully attacker-chosen — analogous to Keycloak's verification proof being scoped only by `(userId, idpAlias)` without binding to the specific verified upstream account, letting a second identity consume/redirect a link meant for someone else.

### Finding Description
`BandwidthManager.purchase()` on the EVM side lets any caller specify an arbitrary `app` and `chain` (the credit chain) in the dispatched `BandwidthPurchaseMsg`: [1](#0-0) 

On Hyperbridge, `pallet-bandwidth::on_accept` only checks that `request.from` matches the registered manager for `request.source` — it performs no validation that `msg.app` is actually deployed on `msg.chain`, nor that the entity paying is authorized to credit that specific `(chain, app)` pair: [2](#0-1) 

The allowance storage key is explicitly documented as keyed by the message-supplied `app_chain`, not `request.source`: [3](#0-2) 

And the gate itself, `BandwidthGate::try_consume`, drains whatever is in that `(source, app)` bucket without any binding back to who funded it or verifying that the consumer is the legitimate owner of that `app` identifier — `app` is just raw bytes supplied by the dispatching application on the destination chain's router call: [4](#0-3) 

This mirrors the Keycloak flaw precisely: the "proof of legitimate ownership" (having paid for bandwidth) is recorded under a coarse, attacker-influenceable key `(app_chain, app)` rather than a key cryptographically bound to the specific paying entity/module that is supposed to benefit. Since `app` is arbitrary bytes (an address is only "usually" packed there per the docs, with no on-chain enforcement of format or ownership), any purchaser can direct — or squat on — the identifier belonging to a different, legitimate application's module id on a different chain, either:
1. Crediting/consuming bandwidth intended for a victim app it doesn't own (griefing via unrelated eviction, since the `SubscriptionList` is capped at 1024 and old entries get evicted — see `push_subscription`), or
2. More importantly, an unrelated party can pre-emptively squat a `(chain, app)` key that a legitimate app is about to be assigned/deployed at, then let the bandwidth entries sit there — since nothing ties the credited key to actual deployment/ownership of that module id, a malicious actor with a small purchase can occupy and manipulate the FIFO for any target app's future purchases (e.g., forcing evictions of the app's own legitimately purchased subscriptions once the malicious entries are interleaved and the 1024 cap is exceeded).

### Impact Explanation
This is reachable by any unprivileged caller of `BandwidthManager.purchase()` (a single submitted transaction on any registered EVM source chain), i.e. exactly the class of actor called out in scope ("relayer, token bridger, ... bandwidth purchaser"). The impact is a route unable to reliably deliver messages for the victim app (denial of bandwidth via forced eviction of legitimate subscriptions) and cross-tenant griefing/theft of a shared metering resource, since the identifier the funds are credited against is never validated to belong to the entity that is supposed to consume it. This is a CWE-639 authorization-bypass-through-user-controlled-key class bug analogous in structure to the reported Keycloak CVE, though the severity ceiling here is bandwidth griefing rather than account takeover — still a concrete availability/economic-abuse impact on the message-dispatch path.

### Likelihood Explanation
Likelihood is high: the only requirement is calling the public, unpermissioned `purchase()` function with a chosen `app`/`chain` and paying the tier price; no special privilege, timing, or race condition is required.

### Recommendation
Bind the credited `(app_chain, app)` key to a cryptographically verified identity rather than raw attacker-supplied bytes: e.g., require `msg.chain == request.source` unless the manager/purchaser is on an explicit sponsorship allowlist per target app, or require the target app to pre-register/opt-in (e.g., via a signed acknowledgment or governance-set mapping) before it can be credited by a foreign chain. At minimum, add an explicit allowlist of which `(source_manager, target_chain, app)` sponsorship relationships are permitted, so a purchaser cannot arbitrarily aim credits (and therefore FIFO-list pressure) at an app it does not control.

### Proof of Concept
1. Attacker deploys/uses the registered `BandwidthManager` on any registered source chain.
2. Attacker calls `purchase(app = <victim_app_bytes>, tier, months, chain = <victim's actual chain>)` repeatedly with the cheapest configured tier, paying only the (possibly negligible) tier price each time. [5](#0-4) 
3. Each purchase is relayed and lands in `Allowance::<T>::mutate(&victim_chain, &victim_app_key, ...)` via `on_accept`/`push_subscription`, with no check that the attacker controls `victim_app`. [6](#0-5) 
4. After 1024 such purchases, any further purchase — including the victim's own legitimate top-up — evicts the oldest entry in the FIFO, per `push_subscription`'s eviction logic, potentially evicting bandwidth the victim legitimately paid for. [7](#0-6)

        returns (bytes32 commitment)
    {
        if (app.length == 0 || app.length > MAX_APP_LENGTH || chain.length == 0 || months == 0) {
            revert InvalidPurchase();
        }

        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();

            tier: tier,
            months: months,
            chain: chain

            feeToken: feeToken,
            tier: tier,
            months: months,
            amountPaid: amount,
            app: app,
            chain: chain,

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

			if request.from != manager.0.to_vec() {

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

				app_chain: msg.chain,
				app: key,

				tier,
				bytes,
				expires_at,
			});

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}
}
