### Title
Unchecked ERC20/TRC20 `transfer()` return value in `IntentGatewayV2.withdraw()` and `onAccept` dust sweep on Tron - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` handler in the Tron variant of the intent gateway move escrowed tokens using a low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the *call itself* did not revert (`success`). They never decode/validate the boolean return value that ERC20/TRC20 `transfer()` is supposed to return.

### Finding Description
In `withdraw()`, escrowed tokens and transaction fees are released to a beneficiary with: [1](#0-0) [2](#0-1) 

The same unchecked pattern is used for dust sweeping in `onAccept`: [3](#0-2) 

Immediately after the unchecked transfer, the contract unconditionally decrements the internal escrow accounting: [4](#0-3) 

For any token whose `transfer()` implementation returns `false` on failure instead of reverting (a well-documented non-standard-but-common ERC20/TRC20 behavior, notably relevant since this file is the Tron-specific deployment where TRC20 token semantics are less uniform than mainnet ERC20), `success` from the low-level `.call()` is `true` even though no tokens were actually moved. The contract only checks `success`, never inspects `returndata` to confirm the token itself reported success. This is exactly the "unchecked transfer" bug class described in the external report (Sense `AutoRoller.sol`), applied here to a fund-release path instead of a simple accounting path.

Because `_orders[body.commitment][token] -= amount` executes regardless of whether the transfer truly succeeded, and `_filled[body.commitment]` is set unconditionally at the top of `withdraw()`, the escrow is marked spent/filled even though the beneficiary received nothing. There is no way to retry or recover — the funds remain locked in the contract while the accounting says they were already redeemed.

`withdraw()` is reachable via `onAccept()` when Hyperbridge relays a `RedeemEscrow`/`RefundEscrow` post request from the source/destination gateway, i.e., through the standard permissionless message-relay path (`onlyHost`, but ultimately triggered by any relayer submitting a valid cross-chain message/proof, not a privileged admin): [5](#0-4) 

This makes the vulnerability reachable end-to-end from an ordinary user placing an intent order and a relayer delivering the corresponding cross-chain message — no admin/governance action required.

### Impact Explanation
- Permanent freezing of user/solver funds: escrow state is marked redeemed/refunded (`_filled`, `_orders[...] -= amount`) while the token balance stays in the `IntentGatewayV2` contract and the beneficiary never receives it.
- No retry mechanism exists once `_orders[commitment][token]` is decremented and `_filled[commitment]` is set, so the loss is unrecoverable through normal contract flow.
- This affects the core escrow-redemption and fee-redemption path of the cross-chain intents system on Tron, directly matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood depends on whether input/output tokens configured for the Tron `IntentGatewayV2` include any TRC20/ERC20-like token that returns `false` on failed transfer rather than reverting. This is a known real-world pattern (e.g., some TRC20/BEP20 tokens, deflationary/fee-on-transfer tokens with insufficient-balance guards that return false, or tokens paused/blacklisted mid-flight returning false instead of reverting). Given IntentGatewayV2 is designed to support arbitrary user-specified ERC20/TRC20 tokens as escrow assets (`order.inputs`/`order.output.assets`), and the contract elsewhere already uses `safeTransferFrom`/`safeTransfer` in the main EVM `IntentGatewayV2.sol`/`IntentsBase.sol` (i.e., the project is aware of this class of issue) but the Tron variant reverts to raw `.call` + `IERC20.transfer.selector` without checking the decoded boolean, this is a straightforward regression specific to the Tron deployment.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` (lines 706, 720) and in the `SweepDust` branch of `onAccept()` (line 674) with a proper safe-transfer helper that:
1. Checks `success` from the low-level call, and
2. Decodes `returndata` when non-empty and reverts if it decodes to `false`.

This mirrors the `safeTransfer`/`safeTransferFrom` usage already present in `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntentsBase.sol`, and should be applied consistently to the Tron contract variant.

### Proof of Concept
1. Configure (or have a user select) an escrow input/output token on Tron whose TRC20 `transfer()` implementation returns `false` on failure instead of reverting (e.g., due to a balance/allowance/pause check implemented without `require`).
2. A user places an order with this token as input via `placeOrder`; a solver fills it and Hyperbridge relays a `RedeemEscrow` message back to the source chain gateway.
3. `onAccept()` routes to `withdraw()`, which calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`. If, for any reason at execution time (e.g., a race condition draining the gateway's balance of that token, or a token-specific business rule), the token's `transfer()` returns `false` without reverting, `success == true` is observed.
4. `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment]` is set, marking the order as redeemed, even though the beneficiary's TRC20 balance never changed.
5. The beneficiary permanently loses the escrowed funds with no path to re-claim them, since the escrow record no longer reflects an outstanding balance.
