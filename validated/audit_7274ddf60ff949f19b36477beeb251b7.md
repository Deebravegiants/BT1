### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC over the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as authoritative once `Utils::HmacValidator.validate` passes, and forwards it unchanged into `WebhookMetadata` for the host application's handler. This breaks the identity binding: `HMAC-authenticated sender == shop attributed to the webhook`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are pulled straight from headers, entirely outside the HMAC-covered bytes: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the raw body): [4](#0-3) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` (and topic/webhook_id/api_version) to build the `WebhookMetadata` passed to the host application's handler, without any additional binding to the value that was actually signed: [5](#0-4) [6](#0-5) 

Because `HMAC(client_secret, raw_body)` is identical regardless of which shop domain header accompanies it, and every shop that installed the app shares the same app `client_secret`, a genuine webhook payload/HMAC pair captured from one tenant (Shop A) remains a *valid* signature no matter what `x-shopify-shop-domain` / `shopify-shop-domain` header value is attached to the replayed request. The gem's own validation logic never re-derives or cross-checks the shop identity against the signed bytes, so `Registry.process` will happily hand the host app a `WebhookMetadata` claiming the data came from Shop B while it was actually authenticated (HMAC-wise) only as "some payload signed with this app's secret."

This directly matches the "field acted on but not covered by the HMAC" analog: the equality that should hold is `hmac_covers(shop) == true`, but in this implementation `hmac_covers(shop) == false` — only the body bytes are bound to the signature.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (Shop A) receives real, validly-signed webhooks addressed to Shop A. By replaying that exact body+HMAC pair to the app's webhook endpoint while swapping the `shop-domain` header to an arbitrary victim shop (Shop B), the attacker causes the gem to report a valid HMAC and deliver `WebhookMetadata.shop == "shop-b.myshopify.com"` to the host application's handler. Any host logic that keys off `data.shop` to look up sessions, write per-tenant records, or authorize actions (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be tricked into acting on Shop B's tenant context using attacker-controlled body content, or into polluting/spoofing Shop B's webhook-driven state. This is a cross-tenant identity confusion rooted entirely in this gem's own signature-verification code, not a host-app misuse.

### Likelihood Explanation
Exploitation requires no privileged credentials: any unprivileged internet user can install the target app for free/trial on their own shop to obtain a validly-signed webhook body+HMAC, then send arbitrary HTTP requests with forged headers directly to the app's public webhook endpoint. No access token, `client_secret`, or session is needed — only the ability to receive one genuine webhook and replay it with a modified header, which `ShopifyAPI::Webhooks::Request`/`Registry` will still accept as valid.

### Recommendation
Bind the shop identity into the signature verification path instead of trusting an unauthenticated header:
- Include the shop domain (and ideally topic/webhook id) in the signable string used for HMAC computation, or
- Cross-validate `request.shop` against a shop-specific secret/session lookup before constructing `WebhookMetadata`, so a body signed for Shop A cannot be reattributed to Shop B by simply changing a header.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled Shop A; capture a real webhook delivery, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Replay the identical body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `shop-b.myshopify.com` (a victim shop that also uses the app).
3. `Utils::HmacValidator.validate` succeeds because it only checks the body bytes: [7](#0-6) 
4. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` and invokes the host app's handler as if Shop B genuinely sent this webhook, even though the signature never bound to Shop B at all.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
