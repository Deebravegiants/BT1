## Title
Webhook shop/topic identity spoofing — HMAC signs only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers used for tenant identification (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, and `webhook_id` for an incoming webhook entirely from unauthenticated HTTP headers, while its HMAC signature covers only the raw request body. `ShopifyAPI::Webhooks::Registry.process` validates that HMAC and then hands `request.shop` straight to the app's handler as the authoritative tenant identifier. Because the signed bytes and the trusted identity field are disjoint, anyone who can reach the app's public webhook endpoint can keep a validly-signed body (e.g. captured from a webhook legitimately delivered to their own shop) and swap the `shop-domain` header to any other merchant's domain, making the host app process attacker-controlled data as if it were an authentic event from the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates that body-only HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` as the tenant/event identity handed to the app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that fails to hold:
`shop authenticated by HMAC` ⊉ `shop used by handler` — the gem treats `request.shop` (an unauthenticated header value) as equivalent to "the shop whose secret produced this HMAC," but the HMAC computation never includes `shop`, `topic`, or `webhook-id`, so these fields can be freely substituted without invalidating the signature.

**Before attacker's request:** A merchant installs the app on `attacker.myshopify.com`. Shopify legitimately delivers a webhook to the app's endpoint with body `B` and `hmac-sha256: HMAC(secret, B)`, plus header `x-shopify-shop-domain: attacker.myshopify.com`.

**Attacker's request sequence:** The attacker captures that request (their own webhook, no special privilege needed — any merchant can install any app and observe traffic to their own endpoint, or simply control the raw HTTP request sent to the app's public endpoint since nothing authenticates the *source* of the request, only the body/secret pairing). They replay the identical body `B` and identical `hmac-sha256` header (since HMAC(secret, B) is still valid — the signature never changes because it never depended on the shop header) but substitute `x-shopify-shop-domain: victim.myshopify.com`.

**After attacker's request:** `HmacValidator.validate` passes (body and HMAC still match), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, so the host app processes attacker-supplied payload `B` under the victim's tenant identity.

### Impact Explanation
This is a cross-tenant identity confusion: the gem allows an unprivileged caller with no credentials for `victim.myshopify.com` to make the host application believe a webhook event — and its body content — originated from that victim's shop. Depending on how the host app's webhook handler consumes `WebhookMetadata#shop` (e.g., to look up/update per-shop records, react to `app/uninstalled`, `shop/redact`, or reflect order/customer data into the wrong tenant's records), this can produce cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker does not control. This matches the Critical "cross-tenant access" category, since the gem's own webhook-processing primitive is what mis-attributes the request instead of it being the host app ignoring documented behavior — the gem provides no signed binding between the HMAC and the identity fields it exposes.

### Likelihood Explanation
The webhook endpoint is, by design, a public internet-facing HTTP endpoint (Shopify posts to it over the open internet), so no authentication, TLS interception, or leaked credentials are required — only the ability to send an HTTP POST to the app's webhook route with attacker-chosen headers and a body/HMAC pair that is valid for *any* shop (which any merchant obtains by installing the app on a shop they control, entirely a normal, unprivileged action). The only additional step is swapping the `shop-domain` header value, which the library does not protect.

### Recommendation
Bind the identity fields into the signed content, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC before trusting them: for example, include the relevant headers in the value passed to `to_signable_string`, or require the host app to independently re-validate that `request.shop` matches a shop with a known/installed session before acting on the webhook. At minimum, document that `request.shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

ShopifyAPI::Context.setup(
  api_key: "key", api_secret_key: "secret", host: "https://example.com",
  scope: "read_products", is_embedded: false, api_version: "2024-01"
)

body = '{"id":1,"note":"legit webhook for attacker.myshopify.com"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", body)
)

# Attacker captured this valid (body, hmac) pair from a webhook legitimately
# delivered to their OWN shop, then replays it with a spoofed shop header.
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim.myshopify.com", # not attacker's shop!
  "x-shopify-webhook-id" => "attacker-controlled-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: spoofed_headers)

# Passes because HmacValidator only checks the (unmodified) body against the HMAC.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

ShopifyAPI::Webhooks::Registry.process(request)
# Handler is invoked with WebhookMetadata(shop: "victim.myshopify.com", body: attacker's body)
# even though the HMAC secret only proves the body itself was signed by Shopify —
# not that it belongs to victim.myshopify.com.
``` [4](#0-3)

          received_signature = verifiable_query.hmac
