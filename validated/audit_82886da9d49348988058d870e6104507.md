## Finding

Webhook processing in this gem authenticates only the **raw body** bytes with HMAC, but the `shop` (and `topic`/`webhook_id`/`api_version`) used to attribute a webhook to a specific merchant is taken from unauthenticated HTTP headers.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then dispatches to the handler using the unauthenticated `shop` header as the tenant identifier: [3](#0-2) 

The gem's own docs describe `Registry.process` as verifying "the request did indeed come from Shopify," and describe `data.shop` simply as "The shop domain of the webhook" without any caveat that this value is unauthenticated: [4](#0-3) [5](#0-4) 

### Identity binding broken

`hmac-verified(raw_body)` ≠ `shop attributed to raw_body`. The HMAC proves the body bytes came from Shopify (signed with the app's shared secret), but does **not** bind those bytes to the `shop-domain` header value that the handler uses to route/attribute the event to a merchant.

### Why this crosses a tenant boundary without special credentials

Any developer can install the target app on their own (free) development store — this requires no `api_secret_key`, access token, or privileged access, matching the "unprivileged internet user" threat model. Once installed, they legitimately receive a validly-HMAC-signed webhook for their own shop. Because the signature covers only `raw_body`, they can replay that exact body with a modified `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`) pointing at a victim shop. `Registry.process` will still validate the HMAC successfully (body unchanged) and will call the handler with `data.shop` set to the attacker-chosen victim shop domain — despite the docs implying this handler only receives host-verified data from the shop that generated it.

### Impact

If a host application uses `data.shop` from `WebhookMetadata` as the tenant key to decide which merchant's records to update/delete/read (the documented and expected usage pattern per the docs example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this allows an attacker to inject falsely-attributed webhook events into another merchant's data pipeline — a cross-tenant confusion vulnerability rooted entirely in this gem's HMAC design, not a downstream misuse of an undocumented API. ### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw JSON body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which `Registry.process` passes straight through to the app's handler as the trusted tenant/event identity — are excluded from the HMAC computation.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string`, which for `Webhooks::Request` is just `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`). The `shop`, `topic`, and `webhook_id` accessors read directly from headers (`lib/shopify_api/webhooks/request.rb:15-23`) and are forwarded unchanged into `WebhookMetadata` by `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`). Consequently, an HMAC that is valid for a given body says nothing about which shop, topic, or webhook id that body is meant to represent.

### Impact Explanation
Because the docs instruct developers to treat `Registry.process` as proof the request "did indeed come from Shopify" and to treat `data.shop` as "the shop domain of the webhook" (`docs/usage/webhooks.md:12-17,125`), applications following the documented pattern will use `data.shop` as an authenticated tenant identifier. An attacker who has any legitimate, unprivileged relationship with the app (e.g., installs it on their own store) can capture a validly-signed webhook body and resubmit it with a forged `shop-domain` header, causing the host application to process/store data under a different merchant's identity — a cross-tenant integrity break.

### Likelihood Explanation
Requires no leaked secrets, tokens, or privileged access — only the ability to install the app on any shop (including the attacker's own) and to send an HTTP POST to the app's public webhook endpoint with modified headers. This is directly reachable by any unprivileged internet user/app installer.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the payload), or clearly document that these header-derived fields are untrusted and must be independently corroborated (e.g., against the session/shop that registered the webhook) before use as a tenant key.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; receive a legitimate `orders/create` webhook with body `B` and valid header `x-shopify-hmac-sha256: H` (H is valid for `B` under the app's shared secret).
2. Replay the same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` → `Utils::HmacValidator.validate` succeeds (only `B` is checked) and the handler is invoked with `data.shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
