Confirmed: the HMAC in `Webhooks::Request` only ever covers `@raw_body` via `to_signable_string`, and none of the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) are part of the signed payload.### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature strictly over `@raw_body` (`to_signable_string` returns only `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` and handed to the app's `WebhookHandler` are read straight from HTTP headers that are never included in the signed payload. This breaks the identity binding: "the shop attributed to a processed webhook" should equal "the shop whose credentials produced the verified HMAC," but nothing in this gem enforces that equality.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers, which are entirely outside the HMAC's scope: [2](#0-1) 

`HmacValidator.validate` only recomputes the signature over `to_signable_string` (the body) and compares it to the `hmac` header value — it never binds `shop`/`topic`/`webhook_id` into the signed material: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then dispatches to the app's handler using the unauthenticated header-derived `shop`/`topic`/`webhook_id`: [4](#0-3) 

That value flows straight into `WebhookMetadata`, which app code uses to scope work to a specific merchant/shop: [5](#0-4) 

Because Shopify apps share a single `api_secret_key` across every shop that installs them, a valid `hmac-sha256`/body pair generated for one shop's webhook is cryptographically indistinguishable from a valid pair for any other shop's webhook — the signature says nothing about which shop it belongs to. A user who controls a shop that has this app installed (an "unprivileged" party relative to any other tenant) can capture a legitimate webhook delivery (raw body + valid `hmac-sha256`), then replay it to the app's webhook endpoint with the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers swapped to name a different, victim shop. `HmacValidator.validate` still returns `true` because the body bytes and HMAC bytes are unchanged, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain.

This is the same bug class as the report: a field acted upon (`shop`, used to route/attribute the webhook to a tenant) is not covered by the verification mechanism (`HMAC` over `raw_body`) that is supposed to authenticate the request.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive: any app built on this gem that trusts `WebhookMetadata#shop` (or `topic`/`webhook_id`) to scope database writes, trigger business logic, or make decisions "on behalf of" a shop, can be made to act on data attributed to a shop the attacker does not own or control, purely by replaying a webhook they legitimately received for their own shop with forged headers. Depending on what the host app does with that data (e.g., updating merchant-scoped records, disabling features, processing GDPR/redact webhooks for the wrong shop), this can constitute cross-tenant data corruption or an authentication/authorization bypass for shop-scoped operations — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker operate (or has installed the app on) any shop capable of receiving a real webhook from the app — no special privilege, no leaked secret, no TLS interception. Header manipulation on a self-controlled HTTP request is trivial once a valid body+HMAC pair has been observed from any of the attacker's own webhook deliveries.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, rather than trusting bare headers post-hoc:
- Have `Webhooks::Request#to_signable_string` incorporate the `shop-domain` (and `topic`) header alongside the raw body when computing/verifying the signature, or
- Require callers of `Registry.process` to supply the expected shop (e.g., resolved from the URL path/session) and assert it matches the header value before dispatch, rejecting any mismatch.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (any topic), capturing:
   - raw body `B`
   - header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`)
2. Attacker POSTs to the app's webhook endpoint with:
   - body `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - header `X-Shopify-Topic`/`X-Shopify-Webhook-Id` optionally forged too
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and executes app logic believing the event genuinely originated from `victim-shop.myshopify.com`.
