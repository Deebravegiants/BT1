## Title
Fee-on-transfer/deflationary `feeToken` breaks `IntentGatewayV2` escrow accounting for `order.fees`, freezing withdrawals - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` already defends input-token escrow against fee-on-transfer/deflationary tokens by measuring actual balance deltas before crediting `_orders[commitment][token]`, but the fill-fee (`order.fees`) branch pulls the fee token with a plain `safeTransferFrom` and records the *requested* amount, not the amount actually received, into the escrow ledger.

### Finding Description
In `placeOrder`, for input tokens the contract explicitly snapshots balances and derives the credited amount from the actual balance delta to defend against fee-on-transfer tokens: [1](#0-0) 

However the fill-fee transfer immediately below does not apply the same defensive pattern — it uses the raw `order.fees` value both for the `safeTransferFrom` call and for what gets credited to escrow: [2](#0-1) 

If `feeToken` (returned by `IDispatcher(hostAddr).feeToken()`) is a fee-on-transfer or rebasing/deflationary ERC-20, the gateway contract actually receives less than `order.fees`, yet `_orders[commitment][TRANSACTION_FEES]` is set to the full, un-adjusted `order.fees`. This creates a divergence between the contract's real `feeToken` balance and the sum of all outstanding `TRANSACTION_FEES` liabilities recorded across orders — the same class of bug described in the referenced report, where `validateCollateralizationPostTransferInPreHook` under- or over-estimates collateral because it trusts the nominal transferred amount instead of the delta actually received.

At settlement, `_withdraw` unconditionally transfers the full recorded `fees` amount out of the shared contract balance: [3](#0-2) 

Because `feeToken` balance is a shared pool across all orders (not segregated per-commitment), any single fee-on-transfer/deflationary `order.fees` deposit creates a permanent shortfall between recorded liabilities and actual holdings. As this shortfall accumulates, `_withdraw` calls for *other, unrelated* orders can revert on `IERC20.safeTransfer` due to insufficient actual balance — and since `_withdraw` also releases the escrowed input tokens for that order in the same function/transaction, this reverts and freezes those users' input-token withdrawals as well, since `withdraw()` is called atomically from `onAccept()`/`onGetResponse()` cross-chain settlement paths with no partial-success/retry mechanism.

### Impact Explanation
This is reachable from an ordinary user calling `placeOrder` (an unprivileged, single-transaction entry point) with an order whose `fees` are non-zero and paid in ERC20 mode (`msg.value == 0` branch). If the configured `feeToken` is, or becomes, a deflationary/fee-on-transfer/rebasing token, the escrow accounting becomes insolvent relative to actual contract balance. Subsequent legitimate settlements (`withdraw`) can then permanently revert due to insufficient `feeToken` balance, freezing both the transaction fee payout and the previously-escrowed input tokens/outputs for those orders — a concrete freezing-of-funds condition satisfying Medium severity.

### Likelihood Explanation
Likelihood depends on `feeToken` being fee-on-transfer/deflationary. Since `feeToken` is a governance-configurable address (`IDispatcher(hostAddr).feeToken()`), and the protocol explicitly considers such compatibility important enough to already defend the input-token path, a governance change to a token with transfer fees, or a token that later adds one, would trigger this. This mirrors the exact bug class from the referenced report (protocol incompatibility with fee-on-transfer tokens), but here it manifests as an asymmetric fix — one code path (inputs) is hardened while the sibling path (fees) is not.

### Recommendation
Apply the same balance-delta pattern used for `order.inputs` to the `order.fees` ERC20 branch: snapshot `IERC20(feeToken).balanceOf(address(this))` before `safeTransferFrom`, and credit `_orders[commitment][TRANSACTION_FEES]` with the actual received delta rather than the nominal `order.fees` value.

### Proof of Concept
1. Governance configures a deflationary/fee-on-transfer ERC20 as `feeToken` on `IDispatcher`.
2. User calls `placeOrder` with `order.fees = 100` and `msg.value == 0`, so the ERC20 branch executes: [4](#0-3) 
3. Due to the token's transfer fee, the gateway actually receives e.g. 98 tokens, but `_orders[commitment][TRANSACTION_FEES]` is set to 100.
4. Repeat across multiple orders; the aggregate on-chain `feeToken` balance of the gateway falls increasingly short of the sum of all recorded `TRANSACTION_FEES` entries.
5. When `withdraw`/`_withdraw` is eventually invoked for an order (via `onAccept` cross-chain settlement) and the shortfall has grown large enough, `IERC20(feeToken).safeTransfer(beneficiary, fees)` reverts for insufficient balance: [3](#0-2) , causing the entire `_withdraw` call — including release of that order's escrowed input/output tokens — to revert and permanently freeze those funds.
