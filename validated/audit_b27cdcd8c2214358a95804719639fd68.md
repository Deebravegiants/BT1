### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC, allowing tenant-attribution spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then forwards these unauthenticated header values straight to the app's webhook handler as trusted tenant-identifying metadata, breaking the binding `authenticated(shop) == shop_acted_on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are parsed straight from HTTP headers, none of which are part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `to_signable_string` (the body) against the secret — it has no knowledge of `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the metadata object handed to the app's handler, with no separate verification that this `shop` matches the tenant the body content actually belongs to: [4](#0-3) 

Because `shop` is acted on (used to attribute the event to a tenant) but not covered by the HMAC, the binding `hmac_verified(body) == shop_the_app_trusts` does not hold. A party who can obtain one genuinely-signed webhook body/HMAC pair for their own shop (i.e., a legitimate but unprivileged merchant installing the app — no `api_secret_key`, access token, or privileged Shopify account required) can replay that same body+HMAC to the app's public webhook endpoint while substituting a different `shop-domain` header. The HMAC will still validate (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the attacker-chosen shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to decide which tenant's session/access token/data the event applies to (a common and expected usage pattern for this exact field, since it's the field this gem exposes for that purpose), an attacker can cause the app to misattribute an event to an arbitrary shop — a cross-tenant confusion/attribution issue. This matches the Critical impact criterion of cross-tenant access, since the gem provides no protection against the `shop` header being decoupled from the HMAC-covered body.

### Likelihood Explanation
Low-to-moderate: the attacker needs at least one legitimately-signed webhook body+HMAC pair, which is trivial to obtain by installing the app on their own store (an ordinary, unprivileged action) and capturing any webhook Shopify sends them. No secrets, tokens, or elevated access are required. The main constraint is that the replayed body's content must be plausible/useful once misattributed to another shop, which depends on the handler's logic, but the binding failure in this gem's code itself is unconditional.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified signable string (or otherwise cryptographically bind the header values to the body), so `Registry.process` cannot be tricked into trusting a `shop` value that wasn't part of what the HMAC actually authenticated. At minimum, document/require host apps to independently verify that `request.shop` matches an actively installed, known shop before trusting it, and consider deriving the shop from the registered endpoint/session context rather than solely from the unauthenticated header.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` (fully unprivileged, self-service action) and lets the app register a webhook.
2. Shopify delivers a webhook to the app's endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid HMAC of raw body>`.
3. Attacker captures the raw body and the valid HMAC (computed only over that body, per `Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. Attacker replays the identical raw body and HMAC to the same public endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
5. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks the body against the secret; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches it to the handler as if Shopify itself vouched for that shop attribution.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
