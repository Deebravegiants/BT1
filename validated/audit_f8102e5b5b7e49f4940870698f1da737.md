### Title
Webhook Cross-Tenant Shop Spoofing via HMAC Scope Gap — Shop Identity Header Not Covered by Signature ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers and passed straight into the handler. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identifier without that value ever being covered by the signature. Because the webhook signing secret (`Context.api_secret_key`) is a single app-wide secret shared across every shop that installs the app, any merchant that receives one authentic, signed webhook can replay that exact body with a forged `shop-domain` header claiming to be a different shop, and the signature will still validate.

### Finding Description
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, and `api_version` are all read from headers that are never part of the signed material: [2](#0-1) 
- `Registry.process` validates the HMAC over the body, then unconditionally trusts `request.shop` (and the other header-derived fields) to build `WebhookMetadata` handed to the app's handler: [3](#0-2) 
- `HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. it verifies bytes of the body, not the tenant/topic metadata the app actually acts on: [4](#0-3) 

The identity binding the gem implicitly promises is: `shop header == shop cryptographically bound by HMAC`. In reality the equality is:
`verified(bytes) = HMAC(raw_body, api_secret_key)` while `acted_on(shop) = header["shopify-shop-domain"]`, and these two sides are never tied together. Since `api_secret_key` is one value for the whole app (not per-shop), any shop that has legitimately installed the app can capture a genuine webhook delivery for itself (same body + same valid HMAC), then re-POST that identical body to the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header rewritten to name a different, victim shop. `Utils::HmacValidator.validate` will report success because the body and HMAC are unchanged and valid, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an app author's webhook handler typically uses `data.shop` to select which merchant's local records to update, invalidate caches for, or trigger side effects on behalf of. Because `shop` is unauthenticated header data that is decoupled from the cryptographic verification, an attacker who is nothing more than a legitimate installer of the target app on their own store can impersonate arbitrary other shops in webhook processing, causing cross-tenant state corruption/actions in the host application. This matches the Critical "cross-tenant access" impact category, since the app cannot distinguish a webhook authentically destined for shop A from an attacker-forged one claiming to be shop B, as long as the payload bytes and signature are replayed correctly.

### Likelihood Explanation
Likelihood is meaningful but bounded by the mechanics: the attacker needs (a) their own valid, uncompromised installation of the target app (an unprivileged action any internet user/merchant can perform), and (b) a webhook event topic/body whose semantics are generic enough to be misused across shops, or ability to capture a webhook whose body content is attacker-influenced (e.g. `orders/create`, `carts/update`, etc., where fields like IDs are attacker-controlled by the attacker's own store actions). The header rewrite itself is trivial once a payload is captured, since nothing about `shop-domain`, `topic`, or `webhook-id` is cryptographically bound.

### Recommendation
Include the `shop`, `topic`, and `webhook_id`/`api_version` values in the HMAC-signable string (or otherwise cryptographically bind them, e.g. via a per-shop secret or a signed envelope) so `Utils::HmacValidator.validate` fails whenever any header the handler relies on for tenant identity has been altered relative to what was actually signed for that delivery.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) that gets delivered with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's single `api_secret_key`.
2. Attacker captures the raw request: body `B`, and headers including `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker replays the exact same body `B` and HMAC header `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) — identical to what was originally signed — and passes.
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled order data under `victim-shop`'s identity.
