### Title
Webhook shop domain (and other Shopify headers) not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers that are entirely excluded from the HMAC signature computation. Only the raw request body is HMAC-verified. An attacker who can obtain any single valid `(raw_body, hmac)` pair (e.g., from a webhook legitimately delivered to their own shop) can replay it against the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop. `Utils::HmacValidator.validate` will still report success because it only checks the body bytes, and `Webhooks::Registry.process` will hand the forged shop identity straight to the app's handler.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are read directly from attacker-suppliable HTTP headers, independent of that signed payload: [2](#0-1) 

`Webhooks::Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The HMAC validator itself only ever checks `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) against the secret — it has no knowledge of, and does not bind, the header fields: [4](#0-3) 

This breaks the identity binding: `shop == authenticated tenant that generated this signed byte stream`. In reality, `hmac` only proves `raw_body` was signed by *some* legitimate delivery; it proves nothing about which shop, topic, or webhook id the request headers claim. Any holder of one valid `(raw_body, hmac)` pair — trivially obtainable by any merchant who installs the app and receives one real webhook, since Shopify's HMAC secret is shared across all shops using the app's `client_secret` — can resend that exact body with a spoofed `X-Shopify-Shop-Domain` (and spoofed topic/webhook-id/api-version) header to the app's public webhook endpoint. `HmacValidator.validate` returns `true` because the body/HMAC pair is genuinely valid, and the handler receives attacker-chosen `shop`/`topic` values.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the gem hands the host application webhook metadata (`shop`, `topic`, `webhook_id`) that is unauthenticated and attacker-controllable, while presenting it as HMAC-verified. Any host application that uses `WebhookMetadata#shop` to scope database writes, trigger per-shop business logic, or route event data (the documented and expected usage pattern) can be made to apply another shop's legitimate webhook payload to an attacker-chosen victim shop, or attribute forged topics to a shop. This matches the Critical "cross-tenant access" category, since it lets one tenant present data that gets processed under a different tenant's identity, entirely through the gem's own webhook verification API.

### Likelihood Explanation
Exploitation only requires an attacker to install the target app on their own shop (or otherwise capture one legitimately signed webhook body/HMAC pair) and replay it with a rewritten `X-Shopify-Shop-Domain` header to the app's public webhook receiver endpoint. No access to `api_secret_key`, access tokens, or privileged accounts is needed. Because `HmacValidator.validate` is the only defense used by `Registry.process`, and it never inspects headers, the replay succeeds deterministically.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed/verifiable payload (or otherwise cryptographically bind them to the verified body, e.g., verify a canonicalized string containing headers to a signature), rather than trusting them as bare headers separate from HMAC verification. At minimum, document and/or enforce that `Registry.process` reject bodies whose header-derived `shop` was previously seen bound to a different signed body from Shopify, or require the host application to cross-check `shop` against an authorized/installed-shop list before trusting `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's shared secret, and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures the exact raw body bytes and the HMAC header value from that delivery.
4. Attacker sends a new HTTP request to the app's public webhook endpoint with the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
5. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `"victim.myshopify.com"` from the header; `Utils::HmacValidator.validate(request)` returns `true` because it only checks the (unchanged) raw body against the HMAC.
6. `Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process attacker-controlled/replayed data under the victim shop's identity.
