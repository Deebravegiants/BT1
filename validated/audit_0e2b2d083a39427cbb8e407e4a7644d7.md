Confirmed: the HMAC signature over a webhook only covers the raw request body, while the `shop`, `topic`, and `webhook_id` fields—used to route and attribute the webhook to a tenant—come from unauthenticated headers that are never included in the signed bytes.

### Title
Webhook HMAC only covers the raw body, allowing shop/topic header spoofing and cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . The `shop`, `topic`, and `webhook_id` values consumed by `Registry.process` are read straight from HTTP headers (`shop-domain`, `topic`, `webhook-id`) and are never part of the signed payload [3](#0-2) .

### Finding Description
The gem's webhook verification breaks the binding: `shop claimed via header == shop covered by HMAC`. `Registry.process` only asserts `Utils::HmacValidator.validate(request)` before dispatching to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)` [4](#0-3) . Since `hmac`, `topic`, `shop`, `webhook_id`, and `api_version` are all pulled from `shopify_header(...)` [3](#0-2)  but only the raw body bytes are what gets HMAC-validated, the signature proves "Shopify's shared secret produced this HMAC for this body" but says nothing about which shop or topic the request is for.

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any attacker who installs the app on their own (attacker-controlled) shop will receive real, validly-signed webhooks for that shop. The attacker can capture one `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while spoofing the `shopify-shop-domain` header (and optionally `topic`/`webhook-id`) to name a victim shop instead. `HmacValidator.validate` still succeeds because the body and HMAC are unmodified and correctly bound to each other — the mismatch is entirely in the unauthenticated headers that determine tenant identity.

### Impact Explanation
This is a cross-tenant identity confusion: the host application's webhook handler receives `WebhookMetadata` claiming to be about victim shop X, backed only by an HMAC that was really issued for shop Y (the attacker's own shop). Any host app logic that trusts `data.shop` to look up/act on a specific merchant's local records (e.g., updating billing state, marking `app/uninstalled`, processing `shop/redact`, or writing order data keyed by `data.shop`) can be tricked into acting on the wrong tenant's data using attacker-supplied content, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Getting a valid `(raw_body, hmac)` pair requires no special privilege beyond installing the target app on an attacker-owned development/trial store — a normal, unprivileged action any internet user can take, then simply resending an HTTP POST with edited headers. No `api_secret_key`, access token, or leaked credential is needed since the secret never has to be known — it's reused verbatim from a legitimately received webhook.

### Recommendation
Bind the shop/topic/webhook identity into what's HMAC-verified, or otherwise cryptographically tie the header claims to the request: e.g., include `topic`, `shop-domain`, and `webhook-id` header values into `to_signable_string` before hashing (matching how Shopify itself scopes delivery per shop), or require the caller to separately verify that `request.shop` matches an expected/registered shop for the delivery in question before trusting it. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must be cross-checked against known installed shops before use.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - Body: `{"id": 1, ...}`
2. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` [1](#0-0)  — validation passes because the body/HMAC pair is untouched.
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker's body>, ...)` [5](#0-4) , and the host app processes attacker-controlled data as if it originated from the victim shop.
