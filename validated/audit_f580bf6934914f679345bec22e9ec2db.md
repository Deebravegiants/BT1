## Analysis Result

A valid analog exists in the codebase.

### Title
Unchecked-length `copy_from_slice` panic on attacker-controlled `message.from` in `HftPallet::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The CVE-2023-54286 bug class is: a fixed-size destination buffer is filled via a raw `memcpy`/`copy_from_slice` from a variable-length, attacker-influenced source without first validating that the source length matches the destination size. In `hyper-fungible-token`'s ISMP module handler, the recipient field (`message.to`) is defensively length-checked before being copied into a `[u8; 32]`, but the sibling field `message.from` is not, even though it is copied/sliced in exactly the same fixed-size-buffer pattern a few lines later.

### Finding Description
`Pallet::on_accept` decodes an ABI-encoded cross-chain `Message` from the incoming `PostRequest` body [1](#0-0) . For the recipient (`message.to`), the code carefully validates the byte length is either 32 or 20 before copying into the fixed `[u8; 32]` buffer, and returns an error (`HftError::InvalidRecipientLength`) for any other length [2](#0-1) .

However, when optional calldata is present and unsigned (`substrate_data.signature` is `None`), the code derives an `origin` from `message.from` without any length validation:

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [3](#0-2) 

`message.from` is a field of the ABI-decoded `Message` struct and is fully attacker-controlled at the encoding level (the source contract, though whitelisted via `ContractToAsset`, can still encode an arbitrary-length `bytes` value for `from` inside the message payload) [4](#0-3) . Two panics are reachable:
- `account.copy_from_slice(from_bytes)` traps if `from_bytes.len() != 32` (non-EVM `source`).
- `from_bytes[from_bytes.len() - 20..]` underflows/panics if `from_bytes.len() < 20` (EVM `source`).

This mirrors the exact root cause of the CVE: an unchecked fixed-size copy from a variable-length, network/message-supplied buffer.

### Impact Explanation
A relayer delivering an attacker-crafted `PostRequest` with a malformed `message.from` length and non-empty, unsigned `message.data` triggers a Rust panic inside `on_accept`, which executes in the runtime's message-dispatch path (`HandlerV2`/ISMP module dispatch). Because Substrate/FRAME runtime execution aborts the extrinsic (and in some execution contexts can trap the WASM instance) on an unhandled panic, this is a Denial-of-Service on the token-bridge message-handling path: the pallet becomes unable to process legitimate `on_accept` deliveries for this route, i.e., "a route unable to deliver messages" per the impact categories in scope. It does not appear to be exploitable for token theft or unbacked minting, since the panic occurs after the mint/transfer step but a repeated attack still degrades or halts delivery of TokenReceived callData execution for this bridge.

### Likelihood Explanation
Reaching this path requires: (1) a source contract that is registered in `ContractToAsset` (i.e., a legitimate/whitelisted bridged asset contract on the counterparty chain), and (2) a message with non-empty `data` and no `signature` in `SubstrateCalldata`. Both are attacker-controllable once a bridge/asset mapping exists, since the `from` field itself is just payload data set by whoever encodes the `Message` on the source chain side (a malicious or compromised token contract, or a user calling a permissive bridge-out function that lets them set `from` freely). The likelihood is moderate — it depends on whether any deployed source-chain contract lets a user set the encoded `from` value to an arbitrary length, which is plausible for many ERC20-style bridge-out implementations that don't validate `msg.sender`-derived byte length before encoding.

### Recommendation
Add the same explicit length validation used for `message.to` (lines 63–71) to the `message.from` handling in the unsigned-calldata branch: verify `from_bytes.len() == 32` before `copy_from_slice` in the non-EVM branch, and verify `from_bytes.len() >= 20` before slicing in the EVM branch, returning a proper `HftError` (e.g., a new `InvalidSenderLength` variant) instead of panicking.

### Proof of Concept
1. Register/assume a source contract `C` mapped in `ContractToAsset` for some `local_asset_id`.
2. From `C` (or any component that can shape the ABI-encoded `Message` sent as the ISMP `PostRequest` body), encode a `Message` where:
   - `to` is a valid 20 or 32-byte recipient (passes the existing check),
   - `data` is non-empty and decodes to a `SubstrateCalldata` with `signature = None`,
   - `from` is set to a byte string of length other than 32 (if `source` is a non-EVM state machine) or shorter than 20 bytes (if `source.is_evm()`).
3. Relay this `PostRequest` to the Hyperbridge host; `Pallet::on_accept` decodes the message, performs the mint/transfer, then reaches the unsigned-calldata branch and panics on `account.copy_from_slice(from_bytes)` or the `from_bytes.len() - 20` slice, aborting extrinsic execution and preventing delivery of that (and potentially subsequent) messages on this route until the runtime/pallet is patched.
