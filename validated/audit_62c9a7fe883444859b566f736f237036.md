### Title
Webhook shop identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are read from unauthenticated HTTP headers. `HmacValidator.validate` verifies only that the body matches a known HMAC, never that the `shop` field is cryptographically bound to that signature. This breaks the identity binding: `hmac(raw_body) == valid` is treated as proof that `shop-domain == <the authenticated tenant>`, when in fact the equality that actually holds is only `hmac(raw_body) == valid`, independent of `shop-domain`.

### Finding Description
In `lib/shopify_api/webhooks/request.rb`:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`to_signable_string` only returns `@raw_body`; `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from attacker-controllable HTTP headers and are never included in the signed payload.

`HmacValidator.validate` (used identically for OAuth callbacks and webhooks) computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

`Webhooks::Registry.process` then trusts `request.shop` unconditionally once the HMAC on the body passes, and forwards it straight into the handler as the tenant identity:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

Because `shop` (as well as `topic`/`webhook_id`/`api_version`) is never part of the signed bytes, any request whose body+HMAC pair is valid for *some* secret-holder-signed payload can be replayed with an arbitrary `shop-domain` (and `topic`/`webhook-id`) header and will still pass `HmacValidator.validate`. This is exactly the pattern called out in the rules: "bytes verified versus bytes parsed" — the gem verifies the body bytes but parses (and trusts) the shop identity from separate, unauthenticated bytes.

### Impact Explanation
An attacker who legitimately installs the app on their own Shopify store (an unprivileged action available to anyone) will receive genuinely Shopify-signed webhooks — i.e., valid `(raw_body, hmac)` pairs — for their own shop. Because the signature covers only the body, the attacker can freely re-POST that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to name a **different, victim shop**. `HmacValidator.validate` will still return `true` (the body/HMAC pair is valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

If the host application uses `data.shop` as the tenant key to act on stored sessions/data (the documented, expected usage pattern shown in `docs/usage/webhooks.md`, e.g. reacting to `app/uninstalled` by deleting the shop's stored session/access token), this allows an attacker to forge cross-tenant events for any known shop domain — for example forging an `app/uninstalled` webhook for a victim store to cause the app to erase/invalidate that victim's stored access token, a cross-tenant denial-of-service/data-integrity break with no credentials belonging to the victim required. This matches the Critical "cross-tenant access" impact bucket, since actions intended to be scoped to the authenticated shop of the signed payload are executed against an attacker-chosen shop identity instead.

### Likelihood Explanation
The prerequisite (installing the app on an attacker-owned shop to obtain one legitimately-signed webhook body/HMAC pair) is trivial for any user who can install a public Shopify app, and the webhook HTTP endpoint is by design internet-reachable and unauthenticated apart from this HMAC check. No access token, `client_secret`, or privileged account is required — only an ordinary merchant/developer account able to install the app once. The only defensive property the gem provides (HMAC on the body) does not bind the `shop` header, so the attack is a straightforward header substitution/replay, well within reach of an unprivileged internet user.

### Recommendation
Bind the shop identity (and other trust-sensitive metadata such as topic/webhook-id/api-version) into the verified signature, or otherwise cross-check them against an independently trusted source before dispatching to the handler:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) as part of the signable content used by `HmacValidator`, matching how `Auth::Oauth::AuthQuery` binds `shop`/`state`/`host` into its `to_signable_string`.
- Alternatively, since Shopify's real HMAC only signs the body, mitigate by validating the incoming `shop-domain` against the set of shops for which the app currently holds an active session/installation, rejecting webhooks for domains that were never associated with a signed nonce/registration, before allowing header-derived fields to influence any state change.
- At minimum, document/enforce that `WebhookMetadata#shop` must be corroborated against the app's own session store before being used for destructive/tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and configures a webhook endpoint they control (e.g., using `ngrok`) to also receive the legitimate delivery, OR simply captures one legitimately delivered webhook (e.g. `app/uninstalled` or `orders/create`) sent by Shopify to the app's public callback URL, recording:
   - raw body `B`
   - header `X-Shopify-Hmac-Sha256: H` (a valid HMAC of `B` under the real `client_secret`)
2. Attacker crafts a new HTTP POST to the same public webhook endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <anything>
   X-Shopify-Api-Version: 2024-01

   B
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` parses `shop` as `victim-shop.myshopify.com` while `to_signable_string` returns `B` only. [4](#0-3) 
4. `Utils::HmacValidator.validate(request)` recomputes HMAC of `B` with the app's `client_secret` and compares to `H` — validation succeeds, since `H` was a genuinely valid HMAC of `B`. [5](#0-4) 
5. `Registry.process` invokes the app's `app/uninstalled` handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to treat this as a genuine uninstall event for `victim-shop`, e.g., deleting `victim-shop`'s stored session/access token — a cross-tenant denial-of-service impact triggered entirely by an unprivileged attacker who only installed the app on their own store. [3](#0-2)
