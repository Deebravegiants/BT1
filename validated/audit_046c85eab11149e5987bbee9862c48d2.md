Confirmed the trust boundary issue in the webhook processing path. Here's the finding.

### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the authenticated tenant identifier. The `shop` field is never part of the signed data, so it can be altered without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read verbatim from the `X-Shopify-Hmac-Sha256` header: [1](#0-0) [2](#0-1) [3](#0-2) 

`shop` is read from the unauthenticated `shop-domain` header: [4](#0-3) 

`Registry.process` validates the HMAC (which only covers `raw_body`) and then dispatches to the app's handler using `request.shop` as the tenant identity, with no additional binding between the signed body and the shop header: [5](#0-4) 

`HmacValidator.validate` / `validate_signature` compute and compare the signature strictly against `verifiable_query.to_signable_string` (i.e., the body), never the shop or topic: [6](#0-5) 

The gem's own documentation instructs host apps to key persistence/business logic directly off `data.shop` from `WebhookMetadata`: [7](#0-6) [8](#0-7) 

This breaks the equality that should hold: `shop bound by the HMAC` == `shop delivered to the handler`. In reality: `shop covered by HMAC = ∅` (only `raw_body` is signed) while `shop used as tenant key = request.shop` (an arbitrary attacker-controlled header value).

### Impact Explanation
Any entity that operates its own Shopify shop and has the app installed (an unprivileged, ordinary Shopify merchant — no special privilege, no leaked secret, no access to `client_secret`) legitimately receives real webhook deliveries from Shopify for their own shop, each carrying a valid HMAC computed by Shopify over the body using the app's `client_secret`. Because the signature never covers the `shop-domain` header, that attacker can replay the identical `raw_body` + `hmac` pair to the app's webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` value. `HmacValidator.validate` still returns `true` (the body and hmac match), and `Registry.process` forwards `shop: <attacker-chosen victim domain>` to the host application's handler as if Shopify itself vouched for that shop. Depending on how the host app uses `WebhookMetadata#shop` (exactly as the docs recommend — to look up sessions, key persisted records, or trigger actions "for shop X"), this enables cross-tenant data confusion/injection: an attacker can make the app record, act on, or emit data attributed to a shop they do not control, with the app trusting it as authentic.

### Likelihood Explanation
No special privilege is required beyond installing the public app on the attacker's own shop, which is the normal, offered install flow for any Shopify app; capturing/replaying one's own legitimate webhook to the app's public HTTP callback endpoint with a modified header requires nothing more than basic HTTP tooling. The gem provides no additional mechanism binding `shop`/`topic` into the HMAC, so any host app following the documented pattern (`data.shop`) inherits this gap.

### Recommendation
Cryptographically bind the shop (and ideally topic/webhook_id) into the value that is verified, e.g., include `shop-domain` in the signable string used for `to_signable_string`, or independently verify the `shop-domain` header value against the known set of shops that installed the app / against a value derived from a signed source (such as the API's own webhook subscription metadata) before handing it to the handler. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be trusted as a tenant key without independent verification.

### Proof of Concept
1. Attacker installs the target public app on their own Shopify dev/test shop `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`).
2. Shopify delivers `POST /callback/orders/create` to the app with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over raw body>`, and the JSON body.
3. Attacker captures this exact request, then resends it to the same endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (raw body and hmac header untouched).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and it matches — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled data>, ...)`, and the host app processes it believing it genuinely originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
