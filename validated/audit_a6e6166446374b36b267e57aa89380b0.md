Based on the investigation, I've confirmed the vulnerability pattern that matches the report's bug class.

### Title
Webhook shop-domain and topic identity not bound by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `HmacValidator` uses that string as the sole input to the HMAC check. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — all taken from unauthenticated HTTP headers — are never included in the signed material, yet `Registry.process` trusts these header-derived fields to route/attribute the webhook to a specific shop and handler.

### Finding Description
`HmacValidator.validate` computes `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field via `OpenSSL.secure_compare` [1](#0-0) . For webhook requests, `to_signable_string` is defined as simply `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` validates only the HMAC over the body, then unconditionally trusts `request.shop` and `request.topic` to select the handler and construct `WebhookMetadata` passed to the app's business logic: `raise ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: ..., ...))` [4](#0-3) .

This breaks the intended identity binding: `shop-that-HMAC-authenticates == shop-that-data-is-attributed-to`. Before the request sequence, the invariant an app relies on is that a valid HMAC implies the accompanying `shop` header is the shop Shopify actually sent the webhook for. After the request sequence, because the header is unsigned, any two requests whose *bodies* are byte-identical (common for webhooks with generic/empty payloads, e.g. `{}` or minimal JSON such as `shop/redact`, `app/uninstalled`, or bulk-operation completion pings) will produce the same computed HMAC even if the `shop-domain` header is swapped — the signature check cannot detect the substitution.

### Impact Explanation
This is a cross-tenant identity-confusion vector: an entity capable of observing/replaying a legitimately-signed webhook body (e.g., a webhook with a fixed or attacker-predictable body shared by many topics/shops) can present that same signed body under a different `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (the signature only certifies the body), but `Registry.process` will hand the host application data attributed to the wrong shop via `WebhookMetadata`. If the host app uses `data.shop` to key data writes, deletions, or side effects (as the gem's own documentation instructs apps to do — see `docs/usage/webhooks.md`), this results in cross-tenant data corruption or disclosure keyed off attacker-controlled tenant identifiers, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires the attacker to reuse a body+HMAC pair that was legitimately generated by Shopify for some shop/topic (this gem cannot forge a new HMAC without `api_secret_key`). This is realistic for topics with constant or highly predictable bodies (mandatory compliance topics `shop/redact`, `customers/redact`, `customers/data_request`, or app lifecycle topics that carry minimal JSON), and only requires the ability to POST to the app's public webhook callback endpoint with attacker-chosen headers — no credentials or privileged access needed. Likelihood is moderate: it depends on body predictability/collision but the gem provides zero structural defense since the header fields are never part of the signed material.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` header values in the signable string used for the HMAC computation in `ShopifyAPI::Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the shop/topic identity to the signature verification path before `Registry.process` passes `WebhookMetadata` to handlers, so a valid signature can only be produced for the exact header/body combination Shopify sent.

### Proof of Concept
1. App registers a handler for topic `shop/redact` (body is always `{}`) and separately for `customers/redact` (also frequently near-empty/fixed JSON).
2. Attacker captures a legitimate Shopify webhook POST for Shop A with body `{}`, headers `x-shopify-topic: shop/redact`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-"{}">`.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `"{}"` only [2](#0-1)  — it matches, since the shop header was never part of the signed data.
5. `Registry.process` invokes the `shop/redact` handler with `WebhookMetadata` reporting `shop: "shop-b.myshopify.com"` [5](#0-4) , causing the app to perform a redaction/data action against Shop B triggered by data intended for Shop A.
