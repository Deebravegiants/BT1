Confirmed: the docs explicitly state the gem's job is to "verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and the tenant identity (`shop`) is handed to the app as trusted data via `WebhookMetadata`, while the HMAC only covers the raw body.

### Title
Webhook `shop` tenant identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` passes, and then forwards `request.shop` to the app's handler as the trusted tenant identifier. However, the HMAC signature only ever covers the raw request body — never the `shop-domain` header that carries the tenant identity. An unprivileged attacker who can obtain one validly-signed webhook body (e.g. from their own trial/dev store) can replay that exact body+HMAC pair to the victim app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, causing the app to attribute the (attacker-controlled) payload to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop` accessor, by contrast, is read straight from an HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is completely outside the signed material: [2](#0-1) 

`HmacValidator.validate` only ever verifies `to_signable_string` (the body) against the secret: [3](#0-2) 

`Registry.process` gates entirely on this HMAC check, then hands `request.shop` — the unauthenticated header value — straight into `WebhookMetadata` for the app's handler to use as the tenant identity: [4](#0-3) 

The documented contract tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "the shop domain of the webhook": [5](#0-4) 

The binding that should hold is: `shop-that-was-cryptographically-authenticated == shop-that-the-app-acts-on`. Because the HMAC only binds the body bytes, not the shop header, this equality does not hold — the gem authenticates "this body came from *a* store owned by this app," not "this body came from *this* store." Any actor who legitimately controls one installation of the app (a free/trial store is enough — no `api_secret_key`, access token, or credential theft required) can capture one valid `(raw_body, hmac)` pair from their own store's webhook traffic and resend it to the app's public webhook endpoint with a forged `shopify-shop-domain` header naming any other shop that has installed the app. The signature still validates (it was computed correctly by Shopify, over that exact body, using the app's shared secret), so `Registry.process` accepts it and dispatches the handler with the victim shop's identity attached to attacker-controlled/replayed body content.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook ingestion: a party with no more than their own legitimate (e.g. trial) store install can cause an app to process and persist webhook data under another merchant's tenant context (cross-tenant data confusion/injection), since the app has no way to distinguish this from a genuine webhook for that victim shop. This matches "cross-tenant access," a Critical-impact outcome, and is fully analogous to the reported bug class: an identity field (`shop`, playing the role of "whose deposit/lock this is") is acted upon by the receiving system without being covered by the same authentication mechanism (HMAC) that gates the action, just as `unstakeDelay` records were mutated by an actor whose identity/authorization wasn't properly bound to the balance being locked.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any store — including the attacker's own free development store, which is available to any internet user — to receive at least one genuinely-signed webhook, and (2) the ability to send an arbitrary HTTP POST to the target app's public webhook callback URL with custom headers, which is inherent to any exposed HTTP endpoint. No `api_secret_key`, access token, TLS interception, or social engineering is needed, matching the "unprivileged internet user" threat model.

### Recommendation
Include the tenant-identifying fields (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed material `to_signable_string` computes over, or otherwise cryptographically bind the header-derived `shop` value to the signed body (e.g., by having `HmacValidator` verify a canonical string built from headers + body rather than body alone). Until that binding exists, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must not be trusted for tenant scoping without independent corroboration (e.g., cross-checking against the webhook body's own `myshopify_domain`/`admin_graphql_api_id` field, when present, or a server-side registration lookup).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store, `attacker-shop.myshopify.com`, and registers for a webhook topic (e.g. `orders/create`).
2. Shopify sends a legitimately HMAC-signed webhook to the app's public callback URL:
   - Headers: `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>`, `shopify-topic: orders/create`
   - Body: attacker-controlled JSON (e.g. crafted order content), since the attacker owns the store and can trigger arbitrary events (e.g. create an order with attacker-chosen fields).
3. Attacker captures this exact `(raw_body, shopify-hmac-sha256)` pair.
4. Attacker sends a new POST directly to the app's public webhook endpoint with the same body and same `shopify-hmac-sha256` header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate(request)` computes the HMAC over `@raw_body` only and it matches (since the body and secret are unchanged), so `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body — i.e., the app now believes attacker-controlled webhook data originated from `victim-shop.myshopify.com`.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
```
