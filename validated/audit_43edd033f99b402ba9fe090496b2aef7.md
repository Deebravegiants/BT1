### Title
Escrow accounting (`_orders[commitment][token]`) is never reconciled against the gateway's actual token balance, so a balance loss during an order's pending lifetime permanently freezes escrowed funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The IntentGateway escrows an order's input tokens by writing a fixed accounting value to `_orders[commitment][token]` at `placeOrder` time, and later spends that same tracked value out of the contract's real token balance when the order is settled (`_withdraw` / `withdraw`). Nothing ever reconciles the tracked value against `IERC20(token).balanceOf(address(this))` between escrow and withdrawal. This is structurally the same bug class as the reported `unclaimedPoolCollateral` issue: a persistent "amount owed to a pending claimant" counter that is trusted as ground truth for later balance-moving operations, with no mechanism to shrink it if the underlying token balance held by the contract falls below what is recorded.

### Finding Description
`placeOrder` credits escrow purely from bookkeeping (adjusted for protocol fee and, for fee-on-transfer tokens, for the amount actually measured as received at that moment): [1](#0-0) 

Settlement (`_withdraw` in the base contract, `withdraw` in the Tron/legacy port) decrements `_orders[commitment][token]` by the fixed `amount` passed in and unconditionally transfers that amount out - it never re-derives the amount from, or checks it against, the gateway's current token balance: [2](#0-1) [3](#0-2) 

The `TRANSACTION_FEES` sentinel entry in the same mapping behaves identically - it is set once from the amount actually transferred in and paid out later as a raw stored value with no balance check: [4](#0-3) 

Between `placeOrder` and settlement (which for cross-chain orders can take an arbitrary amount of time, gated only by the order's `deadline` and cross-chain message delivery), the gateway's real balance of the escrowed token can decrease relative to what `_orders` records - e.g., a negative-rebase/deflationary/upgradeable token whose holder balances shrink while custodied, or any other external reduction of the contract's token balance that is not routed through `_withdraw`. `_orders[commitment][token]` is never adjusted to reflect this loss, exactly mirroring the reported pattern where `unclaimedPoolCollateral` is not decremented when the pool's real collateral takes a loss.

### Impact Explanation
Because settlement transfers the value literally recorded in `_orders` rather than a value bounded by the real balance, a token-balance loss that occurs while an order is pending makes that order's `_withdraw`/`withdraw` call revert with an ERC-20 insufficient-balance failure (`safeTransfer` reverts, or the low-level `token.call` variant returns `success == false` and reverts with `TransferFailed`). Since there is no function anywhere in `IntentsBase`/`IntentGatewayV2` to adjust `_orders[commitment][token]` downward outside of `_withdraw` itself, the escrow entry is permanently stuck above what the contract can pay: the order's `RedeemEscrow`/`RefundEscrow` message can never be processed and the escrowed collateral is permanently frozen (both the user's principal, and, for a shared token, the solvent portion of that balance which other legitimate order withdrawals may also need if the mismatch cascades). This satisfies the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Reachability requires no privileged role: any user calling `placeOrder`/`fillOrder`/`cancelOrder` on the escrow path can trigger the condition once the escrowed token experiences a balance-reducing event outside the gateway's control (rebasing tokens, upgradeable/pausable tokens with clawback semantics, or any token whose `balanceOf` can diverge from a naive transfer-in/transfer-out accounting model over time). The gateway does not restrict `order.inputs[i].token` to a vetted allowlist of "safe" ERC-20s at the base-contract level, so an order using such a token is sufficient to hit this path through the ordinary intents flow (a single dispatched order + one relayed settlement message).

### Recommendation
Reconcile the escrow entry against the actual token balance before transferring: in `_withdraw`/`withdraw`, cap the outgoing transfer amount at `min(_orders[commitment][token], IERC20(token).balanceOf(address(this)))`, or equivalently, on top of the current transfer-in/out accounting, add an admin/governance-gated resync function that lets `_orders[commitment][token]` be lowered to match a measured balance shortfall so affected orders can still be partially settled instead of being frozen forever - mirroring the audited recommendation for `unclaimedPoolCollateral` (an explicit, permission-gated reconciliation entry point) rather than trusting the stored ledger value unconditionally at payout time.

### Proof of Concept
1. A user places an order whose input token is a deflationary/rebasing ERC-20 (or any token whose balance the gateway holds can be reduced by a mechanism outside `_withdraw`, e.g. an owner-controlled `burn`/clawback on that token). `placeOrder` records `_orders[commitment][token] = reducedInputs[i].amount` based on the balance measured at that moment (`evm/src/apps/IntentGatewayV2.sol:363-373`).
2. Before the order is filled/settled, the token's mechanism reduces the gateway's actual `balanceOf(gateway)` for that token (e.g., a negative rebase) without any call into the gateway's `_orders` accounting.
3. The order proceeds through the normal fill/settlement flow; the cross-chain `RedeemEscrow`/`RefundEscrow` message reaches `onAccept`, which calls `_withdraw`/`withdraw` with `body.tokens[i].amount` equal to the originally recorded (now larger-than-actual) escrow amount (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`).
4. `IERC20(token).safeTransfer(beneficiary, amount)` reverts because the gateway's balance is now less than `amount`; there is no fallback path that reduces `_orders[commitment][token]` to the real balance, so the settlement message can never be reprocessed successfully and the remaining escrow for that commitment is permanently stuck.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
