Based on my investigation, I found a directly analogous bug-class pattern in `process_withdraw()`.

### Title
Silent Bypass of LP Withdrawal Slippage Protection When Only One of `min_coin_amount`/`min_pc_amount` Is Provided - ([File: program/src/processor.rs])

### Summary
The `WithdrawInstruction` struct defines `min_coin_amount` and `min_pc_amount` as `Option<u64>` slippage-protection fields [1](#0-0) . In `process_withdraw()`, the slippage check is only performed when **both** options are `Some` simultaneously; if either one is `None` (including if the caller supplies only one of the two, which the wire-format `unpack()` allows to degrade to `(None, None)`), the withdrawal proceeds with no minimum-output check at all, mirroring the reported bug class of "optional field silently skipped where it should be mandatory."

### Finding Description
The instruction decoder unpacks `min_coin_amount`/`min_pc_amount` for the `Withdraw` tag (4) only as a pair — if the instruction data does not contain both trailing u64s, both fields decode to `None`: [2](#0-1) .

In `process_withdraw()`, the resulting slippage protection is gated by an `is_some() && is_some()` check:
```rust
if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some() {
    if withdraw.min_coin_amount.unwrap() > coin_amount
        || withdraw.min_pc_amount.unwrap() > pc_amount
    {
        return Err(AmmError::ExceededSlippage.into());
    }
}
``` [3](#0-2) 

Because a caller fully controls the instruction data of a `Withdraw` (tag `4`) instruction, they can simply omit the trailing 16 bytes so that `min_coin_amount`/`min_pc_amount` unpack to `(None, None)`, entirely bypassing the slippage/minimum-output validation, just as the Hyperliquid report describes an optional price field being silently omitted for order types that should require it.

### Impact Explanation
While the caller withdrawing their own LP is the one who would be harmed by no slippage protection (self-inflicted risk in isolation), this same optional/conditional pattern removes a safety guarantee that programs and off-chain callers (aggregators, bots, other on-chain programs composing with Raydium) rely upon to bound `coin_amount`/`pc_amount` received per burned LP token. Any composed transaction or program that assumes the withdraw instruction enforces minimum-output guarantees (e.g., relying on it as a backstop against a manipulated pool state achieved via other instructions in the same transaction, such as a sandwich/manipulation of `total_pc_without_take_pnl`/`total_coin_without_take_pnl` via preceding swaps) gets no such protection when the field is omitted, allowing withdrawals at a manipulated/unfavorable ratio with no on-chain enforcement. This is a Medium severity issue: it silently disables a documented safety check rather than corrupting global pool accounting directly.

### Likelihood Explanation
Likelihood is high that this state is reachable: the `min_coin_amount`/`min_pc_amount` fields are optional by design in the instruction encoding [2](#0-1) , and any transaction builder or malicious integrator can trivially construct a `Withdraw` instruction with only the base `amount` field (8 accounts + tag, no trailing 16 bytes), which is a single, ordinary, unprivileged transaction reachable by any LP holder — no special accounts or privileges are required.

### Recommendation
Enforce `min_coin_amount` and `min_pc_amount` as required (non-`Option`) fields for the `Withdraw` instruction, or reject the instruction with `InvalidInstructionData`/`InvalidInput` if either is `None`, rather than silently skipping the slippage check only when one of the two is absent. The `&&`-gated check should be replaced by two independent mandatory checks (analogous to the deposit-side `other_amount_min` handling, which at least checks it when present, but likewise should be made mandatory) — mirroring the reported fix of "enforcing price as required."

### Proof of Concept
1. Attacker (any LP token holder) builds a `Withdraw` instruction (tag `4`) with only `amount` (8 bytes) and omits the following 16 bytes for `min_coin_amount`/`min_pc_amount`.
2. `AmmInstruction::unpack()` decodes this as `WithdrawInstruction { amount, min_coin_amount: None, min_pc_amount: None }` per the `rest.len() >= 16` branch [2](#0-1) .
3. `process_withdraw()` computes `coin_amount`/`pc_amount` from current pool ratios, and because both options are `None`, the `if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` guard is `false`, so no `ExceededSlippage` check runs regardless of how unfavorable the ratio is [3](#0-2) .
4. The withdrawal completes and burns LP for whatever `coin_amount`/`pc_amount` the current (possibly manipulated within the same transaction via preceding swap instructions) pool state dictates, with no on-chain enforcement of the caller's intended minimums.
