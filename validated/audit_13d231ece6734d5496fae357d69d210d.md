### Title
Escrow ledger credited with the caller-declared amount instead of the actual tokens received, allowing over-crediting for non-standard ERC20 transfers - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` in the Tron variant of the IntentGateway credits the escrow accounting map `_orders[commitment][token]` with the amount the caller *declared* in `order.inputs[i].amount` (via `reducedInputs[i].amount`), rather than the amount of tokens the contract actually received through `safeTransferFrom`. This is the same bug class as the Pinecone Finance incident, where the pledge pool recorded the number of tokens the caller claimed to deposit instead of validating what was actually transferred in, letting an attacker withdraw more than they deposited.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally does `_orders[commitment][token] += reducedInputs[i].amount;` — it never measures the gateway's actual token balance before/after the transfer. Compare this to the canonical EVM contract `evm/src/apps/IntentGatewayV2.sol`, which explicitly snapshots `balBefore`/`balAfter` and sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before computing fees/escrow: [2](#0-1) 
This diff-based accounting is exactly what the test suite verifies is required for fee-on-transfer tokens (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`): [3](#0-2) 

The Tron contract's predispatch branch does perform a `balance = IERC20(token).balanceOf(dispatcher)` check against `requiredAmount`, but even there it credits escrow with `reducedInputs[i].amount` (the declared amount) rather than the swept `balance`: [4](#0-3) 
and the non-predispatch else-branch has no balance check at all — it trusts `order.inputs[i].amount` completely.

For any ERC20 token where `transferFrom` moves less than the requested `amount` into the gateway (fee-on-transfer tokens, deflationary/burn-on-transfer tokens, or any token with non-1:1 transfer semantics — all of which are permitted since `placeOrder` accepts an arbitrary `token` address chosen by the caller), the escrow ledger `_orders[commitment][token]` records more tokens than the gateway actually custodies.

### Impact Explanation
`_orders[commitment][token]` is the authoritative escrow accounting record used for cross-chain withdrawal/cancellation (`withdraw`, `cancelOrder` → `RefundEscrow`) and for solver fill payouts on other order flows that reference this mapping across the codebase (`evm/tests/foundry/IntentGatewayV2Test.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol` all treat `_orders[commitment][token]` as the ground truth for how much is actually held). Since the value stored can exceed the gateway's real token balance for the affected token, later withdrawals/fills/refunds against that inflated balance can drain tokens belonging to other users' orders held by the same contract — a direct analog of the Pinecone incident where the pledge pool recorded more PCT than was truly deposited, letting the attacker withdraw more than deposited and drain the pool. This is reachable by any unprivileged user simply by calling `placeOrder` with a non-standard ERC20 as the input token, with no admin/governance/relayer privilege required.

### Likelihood Explanation
Likelihood is high on chains/tokens where fee-on-transfer, rebasing, or otherwise non-1:1-transfer ERC20 tokens can be listed as escrow input tokens — `placeOrder` places no restriction on the token address, and the function is a single, unprivileged, permissionless entry point (`function placeOrder(Order memory order, bytes32 graffiti) public payable`). The project's own EVM (non-Tron) implementation and test suite demonstrate the team is aware of and defends against this exact scenario, confirming the Tron variant is a regression/inconsistency rather than an intentional design choice.

### Recommendation
In the Tron `IntentGatewayV2.placeOrder`, mirror the balance-diff pattern used in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before each `safeTransferFrom`, compute the actually-received amount from the post-transfer balance, mutate `order.inputs[i].amount` to that received amount before computing `reducedInputs`/fees, and only then credit `_orders[commitment][token]` with the fee-adjusted actually-received amount (also apply the same fix to the predispatch branch, crediting from the swept `balance` rather than the declared `requiredAmount`/`reducedInputs[i].amount`).

### Proof of Concept
1. Deployer/community lists a fee-on-transfer ERC20 (e.g., 1% fee) as a valid escrow token (no special permission needed since `placeOrder` accepts any token address).
2. Attacker calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and only approves/holds enough to transfer 1000e18 (of which the gateway actually receives 990e18 due to the transfer fee).
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; the gateway's real FOT balance increases by only 990e18.
4. `_orders[commitment][FOT] += reducedInputs[0].amount` records (up to) 1000e18 (minus any protocol fee, still overstated relative to the 990e18 actually held).
5. On `cancelOrder`/withdrawal, or when a solver fills/refunds against this commitment, the accounting math operates on the inflated 1000e18 figure instead of the actual 990e18 custodied, allowing withdrawal of tokens that belong to the gateway's other escrowed balances — draining value analogous to the Pinecone PCT pool being drained via inflated deposit records.     function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
