I found a valid vulnerability class match: the webhook HMAC in this gem only covers the raw body, not the `shop-domain` or `topic` headers that downstream handler code trusts as tenant/event identity.

### Title
Webhook HMAC does not cover the `shop-domain` or `topic` headers, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` passes these header-derived values straight to the app's handler as the tenant identity (`shop`) and event type (`topic`), without ever binding them to the HMAC signature that was actually verified.

### Finding Description
`Utils::HmacValidator.validate` computes/verifies the HMAC over `verifiable_query.to_signable_string`, and for webhook requests that method is defined as: [1](#0-0) 

Only `@raw_body` is signed. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic linkage to that signature: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards the *unverified* `shop`/`topic` values to the app-defined handler as trusted webhook metadata: [3](#0-2) 

The equality the code should guarantee is: `hmac == HMAC(secret, body ++ shop ++ topic)`, i.e., the identity fields a handler acts on must be part of what was authenticated. Instead the code only guarantees `hmac == HMAC(secret, body)`, leaving `shop` and `topic` completely attacker-controlled on the wire while still passing `HmacValidator.validate`.

Because a single app's webhook HMAC secret (`Context.api_secret_key`) is shared across every shop that has installed the app, any merchant who installs the app can legitimately receive a real webhook delivery (valid `body` + valid `hmac-sha256` header) for their *own* store. That merchant can then replay the exact same body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain and/or substituting the `shopify-topic` header with a different registered topic (e.g. `app/uninstalled`, `customers/redact`, `orders/create`). `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` hands the forged `shop`/`topic` to the app's handler as if they were authentic.

### Impact Explanation
This breaks the tenant isolation boundary the whole webhook mechanism is supposed to provide: the app's own business logic (which is almost universally keyed off `data.shop`, e.g. to look up/rotate/revoke access tokens, mark a shop uninstalled, process GDPR redaction, or create/update per-shop records) can be triggered for a shop the attacker does not own and never authorized. This is a cross-tenant access vulnerability — one merchant can forge events/state changes attributed to another tenant using only their own legitimately-issued webhook credentials, without ever needing the app's `api_secret_key`.

### Likelihood Explanation
Any developer/merchant who installs the target app can trivially capture one legitimate webhook delivery (body + `hmac-sha256`) for their own shop (e.g. via a test order, or via `app/uninstalled` on install/uninstall), then replay it with a modified `shop-domain`/`topic` header to the app's public webhook endpoint. No secrets, privileged access, or advanced tooling are required — just basic HTTP replay capability, which is squarely within reach of any unprivileged internet user who can install the app.

### Recommendation
Bind the trusted identity fields into the signed payload verification, or otherwise ensure the value of `shop`/`topic` used by handlers can only originate from a source the HMAC actually covers (e.g., derive `shop`/`topic` exclusively from the JSON body content that is itself signed, or require `to_signable_string` to canonically include the header values that `Registry.process` relies on before comparing HMACs).

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook subscription (e.g. `orders/create`) to receive a legitimate delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay the exact same `B`/`H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally change `x-shopify-topic` to another registered topic string).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(api_secret_key, B) == H`, both unchanged.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is passed to the app's handler with `shop == "victim-shop.myshopify.com"`, even though the delivery never originated from Shopify for that shop, letting the attacker's app-registered handler execute tenant-scoped logic against the victim shop's identity.
