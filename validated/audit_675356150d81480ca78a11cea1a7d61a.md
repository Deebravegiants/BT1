### Title
Unbounded `while` loop in GRANDPA ancestry-route reconstruction can be driven into pathological work by a relayer-supplied justification - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
CVE-2023-1390 describes a `while` loop in `tipc_link_xmit()` that spins on attacker-supplied packets that don't match an expected queue state, burning CPU. The analogous pattern here is `AncestryChain::ancestry()`, invoked from `GrandpaJustification::verify_with_voter_set`, which walks parent-hash pointers built entirely from attacker-supplied `votes_ancestries` headers with no bound on route length or iteration count, and no protection against being re-invoked once per precommit in a justification with many precommits.

### Finding Description
`GrandpaJustification::verify_with_voter_set` [1](#0-0)  builds an `AncestryChain` directly from the untrusted `votes_ancestries: Vec<H>` field of the justification, and then, for every precommit in `self.commit.precommits`, calls `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)` [2](#0-1) .

The `ancestry` function itself is the loop of concern: [3](#0-2) 

It walks `current_hash -> parent_hash` links taken from an attacker-controlled `BTreeMap<H::Hash, H>` (`self.ancestry`), pushing onto `route` on every iteration, until `current_hash == base` or a hash is missing from the map (in which case it errors out). Because the map is built from `votes_ancestries` supplied wholesale by the message submitter, and headers in that map can be constructed with arbitrary (non-consensus-checked) `parent_hash` fields chained together, an attacker can construct a long chain of headers whose hashes/parent-hashes form a cycle-free but very long walk from many different `target_hash` values back toward `base_hash`, or, if hashes collide/point back into the map repeatedly, a long walk. This is called once per precommit (so `O(precommits × chain_length)` amortized), and this whole path is reachable for free through `pallet_ismp::Call::handle_unsigned` (unsigned extrinsic) if a GRANDPA client is registered as a consensus client, since `ConsensusMessage`/`RequestMessage` handling ultimately calls into the registered consensus client's `verify_consensus`/`verify` routine which for GRANDPA runs this justification-validation code. `handle_unsigned` is explicitly documented as executing "for free" as an unsigned transaction [4](#0-3) , and the `ValidateUnsigned::validate_unsigned` implementation itself calls `Self::execute(messages.clone())` at the mempool-validation stage [5](#0-4) , meaning the ancestry walk is paid for by every node's tx-pool validation of every submitted (and possibly rejected) justification, not just by blocks that get included.

This mirrors CVE-2023-1390's root cause: a loop over attacker-influenced state that lacks an explicit upper bound on iteration count/size, executed on cheap/free unsigned input, causing disproportionate CPU consumption relative to the resources the attacker expended.

### Impact Explanation
If exploitable, this would let an unprivileged submitter of GRANDPA consensus messages/justifications force validating nodes (both in block-authoring and, more critically, in `validate_unsigned` mempool gossip validation, which every full node performs on every propagated transaction) to spend unbounded CPU walking long ancestry chains, for a fee-free unsigned extrinsic. That is a network-wide CPU-exhaustion / DoS vector against relayers and collators processing consensus updates — consistent with "a route unable to deliver messages" under the Validate criteria, since sustained CPU exhaustion during justification validation stalls processing of legitimate consensus updates and blocks messages that depend on that consensus client being current.

### Likelihood Explanation
Requires the codebase to actually register GRANDPA as a consensus client for some counterparty chain (the repo does support this via `ismp::clients::grandpa`), and the attacker must be able to submit an unsigned `ConsensusMessage` carrying a `GrandpaJustification` with a crafted `votes_ancestries`/`commit.precommits` combination. Note that `finality_grandpa::validate_commit` runs first and would reject a justification with obviously invalid precommit signatures/duplicate votes, so a genuinely exploitable version of this would need enough valid-looking (or at least signature-passing per the `check_message_signature` check inside the loop) precommits/ancestries to blow up route-walking cost — I could not fully verify from the available files whether `validate_commit`'s own checks (upstream `finality_grandpa` crate, not in this repo) already bound the precommit count or ancestry size before this function is reached, since that logic lives outside the indexed codebase.

### Recommendation
Bound the maximum length of `votes_ancestries` and the maximum number of precommits accepted in a single `GrandpaJustification` before any ancestry walking is attempted (reject early with a cheap length check), and bound the number of steps `AncestryChain::ancestry` is allowed to take (e.g., cap iterations at `votes_ancestries.len() + 1` and error out rather than looping further). Apply the same due-diligence check to any other consensus-client ancestry/traversal code reachable via unsigned messages.

### Proof of Concept
Not fully constructible from the available code alone: a concrete PoC requires knowing exactly what `finality_grandpa::validate_commit` (external crate) accepts as "valid" before `verify_with_voter_set`'s post-validation ancestry loop runs, which is outside this repository's indexed files. Conceptually: submit a `pallet_ismp::Call::handle_unsigned` extrinsic carrying a `Message::Consensus(ConsensusMessage)` for a registered GRANDPA `consensus_state_id`, with a `GrandpaJustification` whose `commit.precommits` contains the maximum practical number of distinct precommit targets and whose `votes_ancestries` contains a long chain of headers linking each target back toward the lowest-numbered `base_hash`, forcing `ancestry()` to be called `precommits.len()` times, each walking a long parent-hash chain, before any of the walks fail validation.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
