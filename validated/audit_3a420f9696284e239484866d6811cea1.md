Confirmed: this gem's documentation explicitly tells developers to trust `data.shop` (derived from `ShopifyAPI::Webhooks::Request#shop`, i.e. the `shopify-shop-domain` / `x-shopify-shop-domain` header) as the tenant identifier, feeding it directly into `perform_later(shop_domain: data.shop, ...)`, and the library's `Registry.process` doc explicitly states that `process` "will verify the request did indeed come from Shopify" — but the HMAC verification only covers the raw body, not the `shop`, `topic`, or `webhook_id` headers.

### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted for tenant routing but excluded from HMAC verification, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates solely the JSON body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values used for tenant identification and handler dispatch are read straight from HTTP headers that are never part of the signed data.

### Finding Description
`lib/shopify_api/webhooks/request.rb` defines: [1](#0-0) 
```
def hmac
  Digest.hexencode(Base64.decode64(...))
end
def shop
  T.cast(shopify_header("shop-domain"), String)
end
def to_signable_string
  @raw_body
end
```
`to_signable_string` binds the HMAC exclusively to `@raw_body`, while `shop`, `topic`, and `webhook_id` are parsed from headers that participate in no cryptographic binding whatsoever. `Registry.process` then does: [2](#0-1) 
```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```
`Utils::HmacValidator.validate` only proves "these body bytes were HMAC-signed with `api_secret_key`" — it says nothing about which shop or topic that signature was originally minted for. The identity binding that should hold is: `shop asserted to the handler == shop the signature was actually generated for`. Because only the body is signed, this equality does not hold: any request whose body+HMAC pair is valid for *some* webhook delivery can be replayed with **arbitrary `shop-domain`, `topic`, and `webhook-id` headers** substituted, and `process` will accept it and dispatch it as if it belonged to the attacker-chosen shop/topic.

The gem's own documentation instructs app authors to treat `data.shop` as the authoritative tenant identifier for downstream dispatch (e.g. `perform_later(shop_domain: data.shop, ...)`), reinforcing that this field is meant to be trusted as an identity boundary, yet the library never binds it to the signature that "verifies the request did indeed come from Shopify," as its own docs claim. [3](#0-2) 

### Impact Explanation
An attacker who is a legitimate, unprivileged merchant of the multi-tenant app (i.e., has installed the app on their own store, a normal unprivileged action) will receive genuine Shopify-generated webhook deliveries containing valid `(raw_body, hmac)` pairs for their own shop. Because the signature covers only the body, the attacker can capture such a pair and replay it to the shared webhook endpoint while forging the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers to name a **different, victim shop**. `Registry.process` will accept the forged headers as valid since HMAC validation succeeds on the (unmodified) body, and will hand `WebhookMetadata` carrying the attacker-chosen `shop` to the app's handler. Any app that uses `data.shop` to look up/act on a tenant's stored session or trigger tenant-scoped background jobs is thereby subject to cross-tenant confusion/injection of attacker-controlled webhook payloads attributed to a victim tenant — a cross-tenant boundary violation.

### Likelihood Explanation
Moderate-to-high: exploitation requires no privileged credentials, no `api_secret_key`, and no interception of TLS — only that the attacker (a normal merchant) can observe/capture one legitimate webhook delivery to their own endpoint, which is trivial to do by simply pointing a webhook registration at an endpoint they control, then replaying the exact `(raw_body, hmac header)` bytes to the shared multi-tenant endpoint with substituted routing headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload construction (or otherwise cryptographically bind the header values used for routing/tenant identification to the signature), and reject any request where these header values cannot be verified against the signed content. At minimum, documentation should not describe `process` as proving the request "did indeed come from Shopify" for the shop/topic asserted in headers, since that guarantee does not currently hold.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`) pointing at the shared processing endpoint.
2. Shopify delivers a legitimate webhook to the attacker with a valid `x-shopify-hmac-sha256` for the raw body, plus headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the HMAC. [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the app processes attacker-controlled body content as if it originated from `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
