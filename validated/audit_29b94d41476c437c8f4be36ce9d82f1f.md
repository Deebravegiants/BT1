Audit Report

## Title
CORS Origin Allowlist Bypass via Unanchored Suffix Matching in Gateway HTTP Server - (File: `core/services/gateway/network/httpserver.go`)

## Summary
`isAllowedOrigin` implements wildcard CORS origin matching (e.g. `*.ethereum.org`) using a raw `strings.HasSuffix` comparison without enforcing a dot label boundary before the suffix. Consequently, an attacker-registered domain such as `myethereum.org` textually satisfies `strings.HasSuffix("myethereum.org", "ethereum.org")` and is wrongly treated as a trusted subdomain of `ethereum.org`.

## Finding Description
In `isAllowedOrigin`, once the scheme and port checks pass, the wildcard branch strips the `*.` prefix from the configured allowed origin and performs a plain suffix check against the incoming `Origin` host: [1](#0-0) 
There is no verification that the character preceding the matched suffix is a `.`, so any second-level domain that happens to end with the exact configured suffix string (not just true subdomains) passes the check. This directly feeds into the CORS header logic that reflects the caller-controlled `Origin` back to the client when `isAllowedOrigin` returns true: [2](#0-1) 
The existing test suite exercises the case where the extra label is dot-separated (`ethereum.remix.org` vs `*.ethereum.org`, correctly rejected) but never exercises the no-dot-boundary concatenation case (`myethereum.org` vs `*.ethereum.org`), so this gap was not caught by tests: [3](#0-2) 

## Impact Explanation
This is a genuine CORS allowlist bypass: an attacker who registers or controls a domain ending in a configured wildcard suffix (e.g. `evilethereum.org` when `*.ethereum.org` is allowed) can have their origin reflected in `Access-Control-Allow-Origin`, enabling their web page to make authenticated cross-origin browser requests to the gateway's HTTP API as if it were a trusted first-party subdomain. This falls under the gateway request impersonation / allowlist bypass impact category recognized by the bounty scope.

## Likelihood Explanation
Exploitation requires only that the gateway operator configure a wildcard `CORSAllowedOrigins` entry (a supported, documented pattern per `core/scripts/gateway/sample_config.toml`) and that the attacker register a domain textually ending in that suffix — a low bar since arbitrary second-level domains ending in common strings are freely registrable. No privileged access, credentials, or victim interaction beyond visiting the attacker's page is required, making it a realistic, unprivileged, browser-based exploit.

## Recommendation
Require a dot-anchored boundary for wildcard suffix matches, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```
This ensures `originHost` must be exactly the base domain or a proper subdomain (separated by a `.`), rejecting unrelated domains like `myethereum.org`.

## Proof of Concept
1. Configure the gateway with `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP request to the gateway endpoint with header `Origin: https://myethereum.org`.
3. `isAllowedOrigin` computes `allowedHost = "ethereum.org"` and evaluates `strings.HasSuffix("myethereum.org", "ethereum.org")`, returning `true`.
4. Observe the response includes `Access-Control-Allow-Origin: https://myethereum.org`, confirming the unrelated domain is treated as trusted.
5. This can be codified as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but asserting the origin `https://myethereum.org` against allowed `https://*.ethereum.org` incorrectly returns a non-empty `Access-Control-Allow-Origin` header.
