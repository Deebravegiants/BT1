### Title
Webhook `X-Shopify-Shop-Domain` (and topic/webhook-id) is not covered by the HMAC, enabling cross-tenant webhook shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from the unauthenticated `X-Shopify-Shop-Domain` header when dispatching to the app's handler. The identity binding that should hold — "shop the HMAC authenticates" == "shop the handler acts on" — is broken because the shop field is never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string`, i.e. the raw body, using the app's real `api_secret_key`: [2](#0-1) 

`Registry.process` gates everything on that body-only HMAC check, and then reads `request.shop`, `request.topic`, and `request.webhook_id` directly from headers to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Request#shop` is a plain header read with no cryptographic binding to the body or to the HMAC: [4](#0-3) 

Equality that should hold: `shop_bound_by_hmac == shop_used_by_handler`. In this implementation, `shop_bound_by_hmac` doesn't exist (only body bytes are signed), while `shop_used_by_handler = request.shop` is taken verbatim from an attacker-controllable header. Any entity that can obtain one legitimate `(raw_body, hmac)` pair signed with the real `api_secret_key` for topic `T` — e.g., by installing the app on their own store and receiving a real webhook for `T` — can replay that exact body+HMAC to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and even `X-Shopify-Webhook-Id`) with any victim shop domain. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the spoofed victim shop and `webhook_id` set to an arbitrary attacker-chosen value.

### Impact Explanation
Because the shop attribution is unauthenticated, a host application built on this gem's documented API (per `docs/usage/webhooks.md`, handlers are told to trust `data.shop` to route work "for that shop", e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-supplied payload content and webhook-id under a victim tenant's identity. This is a cross-tenant confusion at the credential-binding layer this gem is responsible for: the gem's own contract for `WebhookMetadata` claims `shop` reflects the verified webhook shop, but it is not verified. Depending on how the host app uses `data.shop` (e.g., looking up the victim's session/access token and using attacker-controlled `data.body` to update or fan out data for the victim's records, or defeating dedupe purely keyed on attacker-controlled `webhook_id`), this crosses into cross-tenant access, which is the type of impact this scan is scoped to look for.

### Likelihood Explanation
Requires only the ability to (a) install the app on any shop (including the attacker's own free/dev store) to obtain one genuine `(raw_body, hmac)` webhook delivery for a topic of interest, and (b) send an unauthenticated HTTP POST to the app's public webhook endpoint with forged headers — both are within reach of an "unprivileged internet user" and require no `api_secret_key`, access token, or privileged account.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values as signed input, or otherwise verify them are consistent with what the HMAC-authenticated body implies. If the gem cannot change wire-format compatibility with Shopify's actual webhook delivery, it should at minimum document prominently that `request.shop`/`WebhookMetadata.shop` and `webhook_id` are unauthenticated header values not covered by `HmacValidator.validate`, so host apps do not treat `data.shop` as a verified tenant identity for authorization or fan-out decisions, and should instead independently confirm the shop is one the app is actually installed on before acting.

### Proof of Concept
1. Attacker installs the target app on shop `attacker.myshopify.com` and receives a real webhook `POST` to the app's registered endpoint:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, body `{"id":1,...attacker-controlled fields...}`.
2. Attacker captures the exact raw body and its valid `X-Shopify-Hmac-Sha256` value.
3. Attacker sends a new POST to the same app webhook endpoint with the identical raw body and HMAC header, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally a fresh `X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes the raw body against `Context.api_secret_key` — it validates successfully because the body is unchanged, per: [5](#0-4) 
5. `Registry.process` then dispatches to the app's handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker body>, webhook_id: <attacker-chosen>, ...)`, per: [3](#0-2) 
6. The host app's handler processes attacker-controlled data as if it originated from `victim.myshopify.com`.
