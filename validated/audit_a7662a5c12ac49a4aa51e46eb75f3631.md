### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant spoofing of `WebhookMetadata.shop` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then hands the caller's handler a `shop` value that is read from an HTTP header never covered by that signature. Documentation explicitly tells the host app that `Registry.process` "will verify the request did indeed come from Shopify," and that `data.shop` is "the shop domain of the webhook," implying `shop` is authenticated. In fact `shop` is fully attacker-controllable independent of the signed body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e. the raw body for webhooks) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop` header value, passing it straight to the host app's handler: [4](#0-3) 

The identity binding that should hold is: `shop header value == shop bound inside the HMAC-signed payload`. In this library that equality is never enforced — the HMAC only proves the *body bytes* are unmodified for *some* valid signer, but does not bind those bytes to the `shop` header that accompanies them.

Because the app's `client_secret` (the webhook signing key) is a single, app-wide secret shared across *all* merchants who install the app — not a per-shop secret — any merchant who installs the app receives their own genuinely-signed webhook deliveries (valid `raw_body` + valid `hmac`, both computed with the shared secret). Nothing stops that merchant (an ordinary, unprivileged installer of the app — no special access needed) from replaying that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a different (victim) shop's domain. `HmacValidator.validate` still passes because it never looks at the header, and `Registry.process` will invoke the handler with `shop:` set to the attacker-chosen value.

### Impact Explanation
This breaks the shop-to-payload identity binding that host applications reasonably rely on (and that the gem's own documentation implies is verified). An app that uses `data.shop` from `WebhookMetadata` to determine which tenant's records to update (a very common pattern, and the one shown in the gem's own documentation example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into applying data intended for the attacker's own shop against a different tenant's records — a cross-tenant data confusion/injection primitive. This matches the High-impact "cross-tenant access" category: an attacker who legitimately installed the app on their own shop can cause the receiving application to process webhook data under an arbitrary victim shop's identity, without needing the app's `client_secret`, an access token, TLS interception, or any privileged account.

### Likelihood Explanation
Likelihood is moderate-to-high in real deployments: any developer account can install a public/development app to become a legitimate webhook recipient, requiring no privileged access or secret material — only the ability to receive one real webhook and replay it with a modified header to the same public endpoint. The main mitigating factor is that a well-written host app might independently correlate `body` contents (e.g., resource IDs) against known shop-owned data before trusting `shop`, but the gem provides no built-in protection or even a warning that `shop` is unauthenticated, and its own example code trusts it directly.

### Recommendation
Bind the `shop` field to the signed payload before trusting it:
- Update `HmacValidator`/`Webhooks::Request` to include the shop domain (and ideally topic/webhook-id) in the signable content, or
- Have `Registry.process` cross-check `request.shop` against the shop associated with the currently active/looked-up session or webhook registration before invoking the handler, and
- Document clearly that `data.shop` is derived from an unauthenticated header and that host apps must independently validate it against their own tenant records if used for authorization decisions.

### Proof of Concept
1. Attacker installs the target (public/dev) Shopify app on their own store `attacker-shop.myshopify.com`, receiving a legitimate webhook delivery to the app's public endpoint with headers including `x-shopify-hmac-sha256: <valid-hmac>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some `raw_body`.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — validation succeeds because the body/hmac pair is unchanged. [4](#0-3) 
4. The host app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's `body`, and — following the gem's own documented usage pattern — processes/stores that body under the victim shop's tenant context.
