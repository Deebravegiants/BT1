After analyzing the OAuth, JWT, and webhook code, the AuthQuery's `to_signable_string` binds `shop` into the HMAC, and `JwtPayload` binds `aud` to `Context.api_key`. However, the `Webhooks::Request` class shows a genuine, concrete instance matching the requested bug class.

### Title
Webhook `shop` field is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed by `Utils::HmacValidator.validate` only authenticates the body bytes. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers and are never included in the signed content, yet `Webhooks::Registry.process` uses `request.shop` to populate `WebhookMetadata` that is handed to the app's handler as the tenant identity.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
while `shop` is derived independently from the `shopify-shop-domain` header: [2](#0-1) 
`Registry.process` verifies only the HMAC of the body and then trusts `request.shop` as the tenant for the handler invocation without any additional binding check: [3](#0-2) 

The identity equality that should hold is: `HMAC-covered bytes == bytes used to derive the tenant (shop)`. Here, `HMAC-covered bytes = raw_body` while `tenant-identifying bytes = header["shopify-shop-domain"]`. These are disjoint sets, so the `shop` value is never bound by the signature that the library treats as its sole authenticity check for the whole webhook object.

### Impact Explanation
Because the client_secret used to compute the HMAC is shared across every merchant install of a given app, a raw body + matching HMAC pair, once known, remains valid for that body regardless of which `shop` header is attached. Any request reaching `Registry.process` with a body/HMAC pair that validates, plus an attacker-controlled `shopify-shop-domain` header, will be processed by the merchant-supplied handler with `WebhookMetadata#shop` set to that attacker-controlled value — enabling cross-tenant confusion in the handler's data (e.g. writing/reading records under the wrong shop) despite `HmacValidator.validate` reporting success. This matches the "Cross-tenant access" impact tier since the gem's own verification step gives the host application false confidence that `shop` is authentic.

### Likelihood Explanation
Exploitation requires the attacker to possess or replay a valid `(raw_body, hmac)` pair for the shared app secret and to control or influence the headers on the request delivered to the app's webhook endpoint (e.g., a proxy, or an app architecture that forwards webhook headers from an untrusted source, or multi-tenant demultiplexing before `Registry.process`). This is a real gap in the library's own verification contract — `HmacValidator`/`VerifiableQuery` is documented as authenticating the object, but for `Request`, the signature does not cover the very field (`shop`) that determines tenant routing.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or `HmacValidator`) so verification binds `shop`, `topic`, and `webhook_id` together with the body, or have `Registry.process` independently authenticate/validate the shop header against a known set of installed shops before trusting it, rather than relying solely on a body-only HMAC.

### Proof of Concept [4](#0-3) 
Using the same raw body (`"{}"`) and a validly-computed HMAC for that body (as constructed in the test setup), an attacker who can influence only the `x-shopify-shop-domain` header (leaving `x-shopify-hmac-sha256` and body untouched) produces a `Request` object that still passes `Utils::HmacValidator.validate` in `Registry.process`, line 190, because `to_signable_string` never reflects the header change: [5](#0-4) 
`WebhookMetadata.new(... shop: request.shop ...)` is then invoked with the attacker's chosen `shop`, demonstrating the shop field is unauthenticated relative to the signature that gates processing.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
