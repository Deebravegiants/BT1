### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing in `Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC solely against that raw body. The `shop` (and `topic`, `api_version`, `webhook_id`) values, however, are read directly from HTTP headers that are never part of the signed material. `Registry.process` trusts `request.shop` after only confirming the body's HMAC, so the header can be freely substituted without invalidating the signature.

### Finding Description
The identity binding that should hold is: `shop header == shop that the HMAC-signed body actually originated from`. In practice:

- `to_signable_string` only serializes `@raw_body`: [1](#0-0) 
- `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body: [2](#0-1) 
- `HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac-sha256` header — i.e., it only proves the body wasn't tampered with, never that the accompanying `shop-domain` header is authentic: [3](#0-2) 
- `Registry.process` checks only `Utils::HmacValidator.validate(request)` and then immediately forwards `request.shop` (the unauthenticated header) to the app's webhook handler as the merchant identity: [4](#0-3) 

Because the merchant-identifying field (`shop`) is "acted on but not covered by the HMAC," any party capable of capturing one legitimately HMAC-signed webhook body+signature pair (e.g., a webhook that Shopify sent to their own installed app instance, which they fully control and can freely inspect) can resend that exact body/hmac pair to the app's webhook endpoint while substituting a different `shop-domain` header value. `HmacValidator.validate` will still return `true` because it only re-hashes the untouched raw body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the attacker-chosen shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: a request purportedly "for shop A" can actually carry data that was HMAC-signed for shop B (the attacker's own shop) while claiming to be shop A, or vice versa. Any host application that keys off `WebhookMetadata#shop` to route/act on data — the model recommended by this gem's own webhook API (`WebhookHandler#handle`) — can be made to write/process data under the wrong shop's identity, i.e. cross-tenant data confusion. This matches the report's bug-class hint (identity value acted upon vs. bytes actually authenticated by HMAC) and rises to "Cross-tenant access" impact.

### Likelihood Explanation
Requires only:
1. The attacker controls a shop that has this same app installed (a normal unprivileged merchant), so they receive real, validly signed webhooks for their own shop.
2. They resend the identical raw body + `hmac-sha256` header, but with the `shop-domain` header changed, to the same webhook endpoint.

No access to `api_secret_key`, tokens, or the target shop's credentials is needed — only replay of a webhook the attacker legitimately received for their own tenant. This is a realistic unprivileged-internet-user path.

### Recommendation
Bind the shop (and topic/webhook id) into the signed material verified for webhooks, or otherwise independently verify that the `shop-domain` header matches the shop associated with the webhook subscription/HMAC context (e.g., include the header set in `to_signable_string`, or require callers to separately validate `shop` against a known, previously-registered shop before trusting `WebhookMetadata#shop`). At minimum, document prominently that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be used as an identity/authorization boundary by consuming apps.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`) and receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `B`/`H` pair to the app's webhook endpoint, replacing the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate(request)` recomputes `HMAC(secret, B)`, which still equals `H`, so validation passes.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under `victim-shop`'s identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
