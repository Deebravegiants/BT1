### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields — all taken from unauthenticated HTTP headers — are never included in the signed material, yet they are handed to the app's handler as trusted identity data (`WebhookMetadata#shop`). An attacker who can obtain any one genuinely-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own shop, which is unprivileged/self-service) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and the signature check still passes.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s HMAC against `to_signable_string`. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` performs exactly one check — HMAC over the body — then immediately trusts `request.topic` and `request.shop` to dispatch to a handler and construct `WebhookMetadata`: [3](#0-2) [4](#0-3) 

The HMAC secret (`Context.api_secret_key`) is the app's single client secret, shared across every shop that installs the app — it is not shop-specific. Since the signature never binds `shop`, any party who can obtain one valid `(raw_body, hmac)` pair for the app — trivially achievable by installing the app on their own store and capturing a real webhook delivery — can replay that identical body and signature to the app's public webhook URL with a forged `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header pointing at a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and the forged shop domain flows straight into `WebhookMetadata#shop`.

This breaks the identity binding: `shop authenticated by HMAC == shop consumed by the handler` — the left side is actually the empty set (no shop is authenticated at all), while the right side is fully attacker-controlled. The library's own documentation instructs developers to treat `data.shop` as the trustworthy tenant key: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity confusion: an app that keys any per-shop state, GDPR/mandatory topics (`shop/redact`, `customers/redact`, `customers/data_request`), uninstall handling, or business logic off `WebhookMetadata#shop` can be made to apply another merchant's webhook body under a victim shop's identity, or attribute the attacker's own webhook payload to a victim tenant. Depending on handler logic (e.g. `app/uninstalled` deleting local shop records, or order/customer redaction routines), this can lead to unauthorized cross-tenant data modification/deletion for a shop the attacker never installed on — satisfying the "cross-tenant access" critical-impact category, since the attacker only needs to be an unprivileged self-service merchant of their own store using the same app.

### Likelihood Explanation
Moderate-to-high: obtaining a valid `(body, hmac)` pair only requires installing the target app on a shop the attacker controls (self-service, no special privilege) and capturing one webhook delivery — something any developer/tester can do. Replaying it to the app's public webhook endpoint with a modified `shop-domain` header requires no cryptographic material, since the header is outside the signed payload. The main constraint is that the replayed body's *content* must be something the handler will act on meaningfully for the victim shop (e.g. a topic like `app/uninstalled` that carries little/no shop-specific payload is trivially reusable as-is).

### Recommendation
Bind the header fields that matter for authorization (`shop-domain`, `topic`, `webhook_id`) into the HMAC-signed material, or otherwise cryptographically tie them to the body, in `Webhooks::Request#to_signable_string`. Short of changing wire format compatibility with Shopify's webhook signature scheme, at minimum the library should not present `WebhookMetadata#shop`/`topic` as verified data without a prominent warning, and should encourage/require host apps to cross-check the delivered shop domain against an independently known active shop/session before acting on the payload.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers e.g. the `app/uninstalled` webhook.
2. Attacker uninstalls the app, capturing the real webhook `POST` — raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker sends a new POST directly to the app's public webhook endpoint with the same body `B` and same `H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` only look at `B`; `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H` — validation succeeds.
5. `Registry.process` dispatches to the registered `app/uninstalled` handler with `WebhookMetadata#shop == "victim.myshopify.com"`, causing the app to treat the victim shop as uninstalled/redacted even though the victim never sent this request. [6](#0-5) [3](#0-2)
