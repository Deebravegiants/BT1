Based on my investigation, `IntentGatewayV2.placeOrder` contains the closest analog to the FraxPoolV3 issue: a dynamically-computed, protocol-controlled fee is deducted from user-escrowed funds at execution time, and the user has no parameter to cap it.

### Title
Users cannot bound the protocol fee deducted from escrowed order inputs in `placeOrder` - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` reads `protocolFeeBps` from mutable governance-controlled state at execution time and deducts it from the user's already-transferred escrow, with no user-supplied maximum-fee parameter to cause a revert if the fee rate has changed since the transaction was signed/broadcast.

### Finding Description
When a user calls `placeOrder`, tokens are pulled from the user (or from predispatch swap output) into escrow first, and only afterward is the protocol fee computed: [1](#0-0) 

`protocolFeeBps` is resolved from `_destinationProtocolFees[destinationHash]` or the global `_params.protocolFeeBps`, both of which are governance-mutable values (see `ParamsUpdate.protocol_fee_bps` / `destination_fees`) that can change between the moment a user signs/broadcasts the `placeOrder` transaction and the moment it is mined: [2](#0-1) 

Unlike `fillOrder`, which enforces that solver output amounts satisfy the user's required minimum (`InvalidInput()` if below), or the client-side Bid API which caps quote staleness via `validUntil` before submission, `placeOrder` has no equivalent user-supplied bound (e.g., a `maxProtocolFeeBps` or `minReceivedAmount`) that would cause the call to revert if the effective fee at execution time exceeds what the user expected when they built/signed the transaction. The reduced amount (`originalAmount - protocolFee`) is silently used as the new escrowed/commitment amount, so the user's actual input is committed to a value they never confirmed at the fee rate that will really be applied.

### Impact Explanation
If governance increases `protocolFeeBps` (or a destination-specific override) after a user has broadcast `placeOrder` but before it lands on-chain, the user's escrowed order amount is silently reduced by more than expected, and the order is placed with a smaller-than-intended input (and correspondingly smaller filler output requirement, since the whole order — including `output` in the commitment — is now anchored to `reducedInputs`). The user has committed capital to an order priced against an unexpected fee rate, with no on-chain guard to make the transaction revert instead. This is a direct value-loss/manipulation vector for user funds, analogous to the FraxPoolV3 `mintFrax` slippage issue: dynamically-computed deductions from user funds without a user-enforced cap.

### Likelihood Explanation
Requires governance (or a permissioned fee-setter) to change `protocolFeeBps`/`destinationFees` between a user's transaction being signed and mined — a normal governance action, not an attack requiring any special privilege beyond what governance already has. It could also occur incidentally (fee schedule updates coinciding with pending user transactions), making the likelihood non-trivial for a widely-used gateway, though it does depend on a fee-rate change occurring in that narrow window rather than a single attacker fully controlling the outcome.

### Recommendation
Add an optional user-supplied `maxProtocolFeeBps` (or equivalent minimum-received-amount) field checked in `placeOrder` before applying the fee deduction, reverting if the effective `protocolFeeBps` resolved at execution time exceeds the user's accepted maximum — mirroring the short-term Trail of Bits recommendation for FraxPoolV3's `mintFrax` (`maxCollateralIn`/`maxFXSIn`). As a long-term practice, any dynamically-computed amount deducted from or paid to a user during order placement/fill should carry an explicit user-set bound rather than relying solely on governance discipline around fee-change timing.

### Proof of Concept
1. User A builds and signs a `placeOrder` transaction with `protocolFeeBps` currently at 30 bps (0.3%), expecting to escrow 1000 USDC and receive a `reducedInputs` amount of 997 USDC net of fee.
2. Before the transaction is mined, governance calls the params-update path that sets `protocolFeeBps` to 500 bps (5%) — a normal, permitted governance action.
3. User A's transaction executes: `IntentGatewayV2.placeOrder` transfers the full 1000 USDC from the user, then computes `protocolFee = 1000 * 500 / 10_000 = 50 USDC`, reducing the escrowed/commitment amount to 950 USDC — 47 USDC more fee than the user expected, with no revert or user recourse, per [1](#0-0) .
4. The order proceeds with the reduced amount baked into the commitment hash, meaning User A cannot recover the difference; funds are effectively lost to the unexpected fee change.
