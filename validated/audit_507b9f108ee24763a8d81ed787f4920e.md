This confirms the vulnerability chain: `WebhookMetadata.shop` is documented as "the shop domain of the webhook" [1](#0-0)  and the gem's own example handler uses `data.shop` to key downstream work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [2](#0-1) , so host apps are expected to trust this field as the tenant identity for the webhook payload.

### Title
Cross-tenant webhook shop spoofing — `shop-domain` header is not covered by HMAC verification - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook is authentic by checking `Utils::HmacValidator.validate(request)` [3](#0-2) , but the HMAC signable string is defined as only the raw body, never the shop domain header [4](#0-3) . The `shop` value handed to the app's handler is parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [5](#0-4) . This breaks the identity binding `verified_bytes (HMAC over raw_body) == acted_upon_identity (shop used by handler)`.

### Finding Description
`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, which for `Webhooks::Request` returns only `@raw_body` [6](#0-5) . The `shop` accessor is derived independently from a request header that is completely outside the HMAC-covered content [5](#0-4) . Once `process` confirms the HMAC is valid for the body, it forwards `request.shop` (unauthenticated) into `WebhookMetadata` without any additional binding to the signed content [7](#0-6) .

Any internet user who installs the app on their own store (a fully unprivileged interaction — no leaked credentials or `api_secret_key` needed) receives real webhooks from Shopify for their own store, complete with a valid `x-shopify-hmac-sha256` signature computed by Shopify using the app's real secret over the raw body. Because that signature never covers the shop domain, the attacker can capture one such legitimately-signed request and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to name a victim shop. `HmacValidator.validate` will still return `true` since it only re-derives the signature from the (unchanged) raw body [8](#0-7) , and the forged `shop` value is delivered to the host application's handler as if it were authentic [9](#0-8) .

### Impact Explanation
This is a cross-tenant confusion at the SDK boundary: the gem hands the host application a `shop` value that looks HMAC-verified (the webhook as a whole passed signature validation) but is in fact attacker-controlled. Host applications following the gem's own documented pattern — keying background jobs, session lookups, or data writes off `data.shop` [2](#0-1)  — can be tricked into attributing attacker-supplied webhook bodies (from the attacker's own store) to a victim shop, or into processing/queuing work under the victim's tenant identity. This matches the "Critical - cross-tenant access" impact category because the shop/tenant boundary that the gem is expected to enforce via HMAC verification is not actually covering the field used for tenant identification.

### Likelihood Explanation
High likelihood for any unprivileged attacker: installing the target app on an attacker-owned development or trial store is a normal, self-service action requiring no special privileges, stolen credentials, or `api_secret_key` access. Capturing one's own inbound webhook traffic and replaying it with a modified header is trivial and repeatable for any topic the app subscribes to.

### Recommendation
Bind the shop domain into the HMAC-covered signable content (or independently validate `shop` against the session/shop the webhook subscription was registered for) before trusting `WebhookMetadata#shop`. At minimum, `Webhooks::Request#to_signable_string` should not be the sole basis for trusting `shop`; `Registry.process` should cross-check `request.shop` against a known, previously-authenticated tenant record before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a subscribed topic (e.g., `orders/create`) so Shopify sends a webhook with a body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Capture the raw request (`B`, `H`, and other headers).
3. Replay the exact same body `B` and signature header `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged header set [10](#0-9) ; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` which still equals `H` [11](#0-10) , so validation succeeds.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's body>, ...)` [9](#0-8) , causing the host application to process attacker-controlled data under the victim's tenant identity.

          received_signature = verifiable_query.hmac
