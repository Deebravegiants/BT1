### Title
Webhook `shop` identity is trusted from an unauthenticated header while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC check only authenticates the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that the handler receives and treats as the authenticated tenant identity are read straight from HTTP headers that are never part of the signed content, so any party who can produce one valid `(raw_body, hmac)` pair can replay it with a forged shop header to make the app process it as belonging to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) 
`to_signable_string` returns only `@raw_body` — none of the Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signable content.

`Utils::HmacValidator.validate` verifies the HMAC strictly against `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` uses this validation result as the sole authenticity gate, then forwards `request.shop` (an unauthenticated header value) into `WebhookMetadata` and to the app's handler: [3](#0-2) 

`request.shop` itself is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body: [4](#0-3) 

The identity binding the gem's documentation implies is: `hmac_valid? == request_is_authentically_from_Shopify_for_this_shop`. The actual binding enforced in code is only: `hmac_valid? == raw_body_bytes_are_unmodified`. The `shop` field used downstream as the tenant key is outside that binding — i.e., `verified_bytes (body) != identity_bytes (shop header)`.

The gem's own documentation states the mismatch explicitly as a guarantee it does not provide: [5](#0-4) 

An unprivileged internet user who is themselves a Shopify merchant (no special credentials, no access to the target app's `api_secret_key` or tokens) can:
1. Register the target app's webhook handler for their own shop through the app's normal install flow.
2. Trigger a legitimate webhook for their own shop, capturing the resulting `raw_body` and its valid `X-Shopify-Hmac-Sha256` value (both computed with the target app's real secret over the attacker's own data).
3. Replay that exact `(raw_body, hmac)` pair directly to the target app's webhook endpoint, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (and any other non-signed headers, like `webhook-id`, to defeat naive de-dup checks).
4. `HmacValidator.validate` still returns `true` (body/HMAC pair is valid), so `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`.

Any host application that follows the gem's documented contract — trusting `data.shop` as the authenticated tenant identifier because "this will verify the request did indeed come from Shopify" — will process attacker-controlled data attributed to a victim shop's tenant context.

### Impact Explanation
This breaks a tenant/identity boundary: an unauthenticated (from the target app's perspective) actor can make forged, attacker-chosen webhook payloads be attributed to and processed as belonging to an arbitrary victim shop, as long as they can obtain one authentic `(body, hmac)` pair from their own shop (which requires no privileged access to the target app). Depending on how the host app keys its data by `data.shop` (as the docs' own example does: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data injection/corruption — the impact category of cross-tenant access called out as in-scope.

### Likelihood Explanation
Moderate-to-high: the attacker only needs to be a legitimate merchant of the target app (a normal, unprivileged installation) to obtain one valid signed body/HMAC pair for any topic they subscribe to, and then can freely forge every other webhook header, since none of them are covered by the signature. No secret material, tokens, or elevated access is required.

### Recommendation
Bind the identity fields used for authorization/routing decisions into the signed content (or independently verify them), e.g.:
- Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed material, or
- Cross-validate `request.shop` against the shop associated with the previously stored session/subscription for that specific webhook, rather than trusting the header verbatim, and
- Update `docs/usage/webhooks.md` to clarify precisely what `Registry.process` verifies (body integrity only) versus what it does not (header-derived shop identity), so host apps do not conflate the two.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app normally.
# Step 1: Attacker triggers any webhook for their own shop (e.g. orders/create) and
# captures the raw POST body + the "X-Shopify-Hmac-Sha256" header sent by Shopify —
# both are valid and signed with the target app's real api_secret_key.

captured_body = '{"id":1,"note":"attacker-controlled payload"}'
captured_hmac = "..." # value Shopify actually sent for the attacker's own shop

# Step 2: Attacker replays this exact pair to the target app's public webhook endpoint,
# but swaps only the shop header (never covered by the signature):
POST /callback/orders/create HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <captured_hmac>          # unchanged, still valid for captured_body
X-Shopify-Shop-Domain: victim-shop.myshopify.com # forged
X-Shopify-Webhook-Id: <any-value>
X-Shopify-Api-Version: 2024-01

<captured_body>
```
```ruby
# In the target app:
ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
)
# => Utils::HmacValidator.validate(...) returns true (body/HMAC match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_json, ...))
```
The handler receives attacker-controlled data attributed to `victim-shop.myshopify.com`, even though nothing about that shop identity was ever authenticated.

          received_signature = verifiable_query.hmac
