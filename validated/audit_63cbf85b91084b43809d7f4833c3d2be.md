### Title
Crafted swap routes can execute malicious venue code that drains unrelated caller tokens - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
The controller forwards caller-supplied swap instructions to the configured router after authorizing only the controller’s own exact input-token transfer, but it does not constrain the venue addresses embedded in the route or the additional authorization children that route execution can request. [1](#0-0) 

### Finding Description
`swap_collateral` accepts arbitrary `swap` bytes and reaches the strategy path after authenticating `caller` and verifying that the caller owns or delegates the target account. [2](#0-1) [3](#0-2)  During settlement, the controller invokes `execute_strategy` with those bytes while relying on pre/post balances and positive output rather than decoding or constraining route-selected external contracts. [4](#0-3)  A malicious route can therefore place attacker-controlled pool code inside the transaction, where it can request a token transfer from the caller to the attacker unrelated to the routed input. [5](#0-4)  Transaction simulation records that transfer as a child of the caller’s authorization, and it executes if the wallet signs the poisoned authorization tree. [5](#0-4) 

### Impact Explanation
This permits theft of caller funds outside the collateral amount deliberately routed through the strategy. [5](#0-4)  The controller’s exact invoker authorization protects only `token_in.transfer(controller, router, amount_in)` and does not bound additional authorization children requested by route-selected code. [6](#0-5) 

### Likelihood Explanation
An unprivileged caller can invoke `swap_collateral` with a crafted route, and the same pattern is reachable through the other route-bearing strategy entrypoints. [7](#0-6)  Exploitation requires the signer to accept the simulated authorization tree containing the malicious child transfer, which is feasible when the route is supplied by an untrusted quote source or the client does not independently validate the authorization tree. [5](#0-4) 

### Recommendation
Restrict routes to governance-approved venue/pool contracts or introduce a route registry that prevents arbitrary contract addresses from being invoked during strategy execution. [8](#0-7)  Independently require wallet and integration clients to reject any authorization tree containing children beyond the expected input-token transfer. [5](#0-4) 

### Proof of Concept
1. The victim holds collateral in an account and an unrelated token balance in the same wallet.
2. An attacker supplies a `swap_collateral` route whose selected pool address is an attacker-controlled contract.
3. The victim submits `swap_collateral(caller = victim, account_id = victim_account, current = collateral_asset, amount = victim_amount, new = output_asset, swap = malicious_route)`.
4. The controller authorizes only its own input transfer and calls the configured router with the malicious route. [9](#0-8) 
5. The route invokes the attacker’s pool contract, which calls `unrelated_token.transfer(victim, attacker, victim_balance)`.
6. Simulation adds that transfer as a child authorization under the victim’s `swap_collateral` entry; if the victim signs that tree, the unrelated wallet balance is transferred to the attacker while the measured swap output can still satisfy the controller’s positive-output and risk checks. [5](#0-4)
