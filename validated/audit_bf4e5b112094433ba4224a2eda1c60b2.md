### Title
Unfunded `recapitalize` refund pays pool custody to the "payer" while leaving the cash book overstated — ([File: contracts/pool/src/ops/recapitalize.rs](contracts/pool/src/ops/recapitalize.rs))

### Summary
`recapitalize::apply` computes `refund = amount - applied` where `applied = min(amount, backing_shortfall)`, then unconditionally transfers `refund` out of the pool's token custody to the `payer` argument. It never verifies that the payer actually transferred `amount` in. This is the same bug class as the ext4 fix: a "repair" path that adjusts bookkeeping for a partially-completed operation without confirming the precondition it assumes (funds injected / extent split completed), leaving the data structure inconsistent — here, a `cash` book that still claims custody it no longer holds.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs`:

```rust
// contracts/pool/src/ops/recapitalize.rs:32-38
let outcome = accounting(env, hub_asset, amount);
outcome.cache.transfer_out(&payer, outcome.refund);
```

```rust
// contracts/pool/src/ops/recapitalize.rs:52-58
let applied = amount.min(guards::backing_shortfall(&cache));
let refund = amount.checked_sub(applied)...
cache.credit_cash(applied);
cache.commit();
```

The doc comment states "The controller transfers `amount` into the pool before this call," but nothing in the pool enforces it: the contract never measures its token balance delta. Any caller can pass a `payer` they control and an `amount` exceeding the backing shortfall, and the pool pays the excess out of its own custody — suppliers' tokens — while `cash` is credited only `applied`.

The repo's own regression test documents the aftermath: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408-3483`) shows that after `recapitalize(&hub, &payer, &custody)` with an unfunded payment, the pool balance is 0 while `cash` still claims the funds exist. `Cache::require_reserves` reads the book, not the balance, so withdrawal exits pass the liquidity guard and then fail inside the SAC transfer with `BalanceError = 10` — the exact "overlapping extent" outcome: the fix-up (credit cash, refund excess) produced a book/custody mismatch that persists.

### Impact Explanation
Theft of user funds plus permanent freezing of funds. An unprivileged caller drains `pool_balance - backing_shortfall` of token custody to an address they control, and additionally the overstated `cash` book means subsequent legitimate withdrawals pass `require_reserves` and revert inside the token transfer — suppliers cannot exit because the accounting claims solvency that the custody cannot satisfy. Every withdrawal of the affected hub asset fails until external recapitalization actually occurs.

### Likelihood Explanation
A single call to `Pool::recapitalize(hub_asset, payer, amount)` with `payer` = attacker and `amount` = the pool's current token balance executes the drain whenever `amount > backing_shortfall(cache)` — including the common case of zero shortfall, where the entire `amount` is refunded. No flash loan, oracle manipulation, or multi-block setup is required.

### Recommendation
Make the cash injection measured, not declared: record the pool's token balance before crediting, require the caller's incoming transfer of `amount` (or pull it via `transfer_from`/`require_auth`), and compute `refund` from the actual received balance rather than the argument. Failing that, gate `recapitalize` so only the controller can invoke it and have the controller transfer in the same atomic call. Never transfer `refund` from custody that was not demonstrably injected in the same transaction.

### Proof of Concept
Mirrored by the existing test at `contracts/pool/tests/flows.rs:3408-3483`:

```rust
token_admin.mint(&t.pool, &deposit);           // supplier custody exists
t.client().supply(&t.sup(0, deposit));         // book: cash = deposit
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
// payer receives `custody - applied` from pool; pool balance == 0
// cash book still >= deposit; withdraw passes require_reserves,
// then fails inside the SAC transfer with BalanceError = 10
```

Conceptual on-chain attack: attacker calls `recapitalize(hub_asset, attacker, pool_balance)`. With `backing_shortfall == 0`, `applied == 0` and `refund == pool_balance` is transferred to the attacker. Suppliers' withdrawals now pass the pool's liquidity checks but revert on the token transfer — funds stolen and exits frozen.
