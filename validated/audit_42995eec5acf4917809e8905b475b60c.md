Confirmed. The `WebhookMetadata.shop` field, which the docs explicitly tell app developers to trust for tenant identification (`shop_domain: data.shop`), is populated straight from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header and is never part of the HMAC-signed payload.

### Title
Webhook shop-domain identity spoofing via unsigned header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the tenant identity straight from the `shopify-shop-domain` HTTP header, while `Request#to_signable_string` (the value that is actually HMAC-verified) only ever returns the raw request body. Because the app's webhook HMAC secret (`client_secret`) is shared across every shop that installs the app, any merchant who legitimately installs the app can capture a validly-signed webhook delivered to their own store and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `ShopifyAPI::Webhooks::Registry.process` accepts the request because the HMAC still validates (the body is unchanged), and hands the attacker-controlled `shop` value straight to the app's handler as trusted tenant identity.

### Finding Description
`Utils::HmacValidator.validate` verifies the request using `verifiable_query.to_signable_string` as the signed payload: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, which becomes the tenant identifier delivered to the app, is taken from the `shopify-shop-domain` header and is not covered by that signable string at all: [3](#0-2) 

`Registry.process` validates the HMAC over the body only and then forwards `request.shop` verbatim into `WebhookMetadata`, which is the object handed to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that is broken is: `HMAC-verified bytes (raw_body) == bytes used to determine the acting shop`. In reality: `HMAC-verified bytes (raw_body) != request.shop (header)`. Since a single `client_secret` is shared for every shop that has the app installed, an attacker who is a legitimate merchant on their own store can:
1. Install the target app on their own shop, and receive genuine, Shopify-signed webhooks (whose HMAC is valid for the app's `client_secret`).
2. Replay the exact same raw body/HMAC pair to the app's webhook endpoint, but with the `Shopify-Shop-Domain` header (or `X-Shopify-Shop-Domain`) changed to a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the (unmodified) body, while `Registry.process` trusts the forged `shop` header for `WebhookMetadata#shop`.

The official usage docs confirm the header value is meant to be trusted as authoritative shop identity, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [6](#0-5) 

### Impact Explanation
An unprivileged internet user who is merely a merchant capable of installing the app on their own store can forge the shop-domain binding of a genuinely-signed webhook and cause the app to process attacker-supplied webhook content under a victim tenant's identity. Depending on how the host app persists/acts on webhook data keyed by `data.shop` (e.g., updating order/customer/fulfillment records, triggering redact/GDPR flows, invalidating sessions, or writing to a shop-scoped data store), this enables cross-tenant data corruption or state changes attributed to a shop the attacker doesn't own — a cross-tenant access violation stemming from this gem's own identity-binding logic, not from any documented misuse by the host app.

### Likelihood Explanation
Likelihood is high: exploitation requires no secrets, tokens, or privileged access — only the ability to install the app as a normal merchant (a capability every app is designed to grant to any Shopify merchant) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers.

### Recommendation
Include the shop domain (and ideally topic, api_version, webhook_id) in the HMAC-signable representation, or independently verify that the `shop-domain` header corresponds to a shop that this specific webhook payload was actually addressed to (e.g., cross-checking against Shopify's per-shop webhook secrets if available, or requiring the app layer to reconcile `data.shop` against the shop context under which the webhook subscription was registered) before trusting it as tenant identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggers an event (e.g. `orders/create`), and captures the resulting webhook POST, including its valid `Shopify-Hmac-Sha256` header and raw body.
2. Attacker resends the exact same raw body and `Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the shared `client_secret`: [7](#0-6) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, and the attacker-crafted body is now processed under the victim shop's identity.
