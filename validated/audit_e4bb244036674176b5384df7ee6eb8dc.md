### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC signature that `Utils::HmacValidator` verifies is computed over the raw body only. This breaks the intended binding `verified_bytes == acted_upon_identity`, letting any party who can obtain one valid `(raw_body, hmac)` pair for their own shop attribute that payload to an arbitrary victim shop when replayed against the app's webhook endpoint.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop` is read straight from an HTTP header with no cryptographic tie to that signature: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`, i.e. against the body alone: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` value to the app's handler as the tenant identifier, with no further check that this shop matches whatever secret was used to sign the body: [4](#0-3) 

The `WebhookMetadata#shop` field is explicitly documented as the trusted per-tenant key that host apps use to route/store data: [5](#0-4) [6](#0-5) 

The binding the code should enforce is:
`hmac_verified(shop, body) == true` before `shop` is trusted as the tenant key.

What actually happens is:
`hmac_verified(body) == true`, and `shop` is taken from an unsigned header, so `shop` is never actually bound to the signature that "authenticates" the request.

Since the app's `api_secret_key` (the HMAC key Shopify uses to sign webhooks) is identical for every shop that installs the app — it is the app's single client secret, not a per-shop secret — any merchant who installs the app on their own store legitimately receives real `(raw_body, X-Shopify-Hmac-SHA256)` pairs signed with that shared secret. That merchant, an "unprivileged internet user" with respect to every other tenant of the app, can capture one such valid webhook delivery and replay it to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` for a different (victim) shop's domain. `HmacValidator.validate` still succeeds because it never looks at that header, so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain but attacker-controlled `body`/`topic`. Any host application that uses `data.shop` to key per-tenant records (as the gem's own docs instruct) will attribute attacker-controlled data to another tenant — a cross-tenant write/confusion primitive.

### Impact Explanation
This is a cross-tenant boundary break: the value the gem tells host applications to trust as the tenant key (`WebhookMetadata#shop`) is not covered by the same authentication check (`HmacValidator`) that is supposed to prove the request is legitimate. An attacker who is merely one legitimate installer of the app can inject webhook events that will be processed as if they belong to any other shop, defeating the multi-tenant isolation the HMAC check is meant to provide.

### Likelihood Explanation
Exploitation only requires installing the target app on the attacker's own store (a normal, unprivileged action available to any merchant) to obtain a valid `(raw_body, hmac)` pair signed with the app's shared secret, then replaying that request with a modified `shop-domain` header to the app's public webhook callback endpoint. No access to `api_secret_key`, tokens, or the app's infrastructure is required.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed material that `HmacValidator` checks, or otherwise cryptographically bind the shop domain to the signature before it is passed to `WebhookMetadata`/handlers. At minimum, document that host apps must independently verify `data.shop` against a shop they know installed the app (e.g., cross-reference against stored sessions) rather than trusting the header as gem-authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-SHA256: <valid-for-body>`.
2. Attacker crafts a new HTTP request to the same app webhook endpoint reusing the exact same raw body and `X-Shopify-Hmac-SHA256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`@raw_body`) — validation succeeds. [7](#0-6) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: {"id"=>1}, ...)` and processes/stores it as data belonging to `victim.myshopify.com`, even though it was never verified as coming from that shop.
