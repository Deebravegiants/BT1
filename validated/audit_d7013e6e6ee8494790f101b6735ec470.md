### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant shop spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` validates the HMAC only against the raw request body, but the `shop` attribute — the field the host application uses to determine which tenant a webhook belongs to — is read directly from an unauthenticated HTTP header. This breaks the identity binding `hmac_verified_bytes == bytes_the_handler_trusts_for_tenant_identity`, letting a merchant who has captured one of their own valid (body, HMAC) webhook deliveries replay it against the app's shared webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header changed to a victim shop, causing the app to process attacker-controlled data under the victim's tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`, i.e. the body: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally forwards `request.shop` to the handler as the trusted tenant identifier, with no cross-check that the shop the HMAC was computed for matches the shop asserted in the header: [4](#0-3) 

That value is placed into `WebhookMetadata#shop`, a `T::Struct` field the host application's `WebhookHandler#handle` implementation is expected to trust as the authoritative shop for the delivered payload: [5](#0-4) 

This is structurally analogous to the reported issue: an accounting-critical field (`stakedForDomain.stakedAmount`, trusted based on transferred token amount) can diverge from the real, "signed" quantity (actual token reserve) because the contract doesn't re-verify the discrepancy. Here, the field the host app treats as authoritative tenant identity (`shop`) is never bound to what the HMAC actually authenticates (only the body bytes), so `hmac_authenticated_shop != header_asserted_shop` can silently diverge.

### Impact Explanation
A shop owner who has installed the app on their own store is, by definition, capable of receiving valid webhook deliveries (body + `hmac-sha256` header) signed by the app's `api_secret_key` for their own store — this is normal, unprivileged usage requiring no leaked secret. By capturing such a delivery and replaying the identical body/HMAC pair to the app's shared webhook endpoint while only modifying the `shop-domain` header to a different (victim) shop, the HMAC validation in `HmacValidator.validate` still succeeds (it never inspects the shop header), and `Registry.process` will deliver `WebhookMetadata` claiming the victim shop as the origin of attacker-supplied body content. If the host application performs shop-scoped writes/lookups keyed on `data.shop` (a documented, expected usage pattern of `WebhookHandler#handle`), this results in cross-tenant data injection/corruption, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any merchant with the app installed can trigger their own real webhook events (e.g. by placing a test order or resource update) to obtain a legitimately signed `(body, hmac)` pair for the topics they have access to, then send that unmodified body/HMAC to the app's public webhook URL with only the shop header changed. No secrets, credentials, or privileged access are required beyond ordinary app usage, making this readily reachable by any unprivileged tenant of a multi-tenant app built on this gem.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cross-check it against a trusted source (e.g., look up the shop from a previously established session/webhook registration rather than trusting the header verbatim), and reject webhooks where the header-derived shop cannot be corroborated. At minimum, document prominently in `docs/usage/webhooks.md` that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., matching against the shop the webhook was registered for).

### Proof of Concept
```ruby
# 1. Attacker (owner of shop "attacker.myshopify.com") triggers a real webhook,
#    capturing raw_body and the legitimate x-shopify-hmac-sha256 header
#    computed by Shopify using the app's real api_secret_key.
raw_body = '{"id":1,"note":"malicious payload"}'
hmac_b64 = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_api_secret_key, raw_body)
hmac_b64 = Base64.encode64(hmac_b64) # this value is legitimately produced by Shopify itself

# 2. Attacker replays the exact same body+hmac to the app's shared webhook
#    endpoint, but swaps only the shop-domain header to the victim's shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,      # valid, unchanged
  "x-shopify-shop-domain" => "victim.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. Passes HMAC validation because only raw_body is signed:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches this to the handler as if it came from victim.myshopify.com
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata(shop: "victim.myshopify.com", body: {...attacker content...}))
```
