### Title
Webhook signature does not bind the `shop`/`topic` headers used for tenant dispatch, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the **unauthenticated** `shop`, `topic`, and `webhook_id` header values straight to the app's handler. The HMAC never covers those header fields, so any bytes that are legitimately signed for one shop's webhook can be replayed with a different `shop-domain`/`topic` header and still pass validation.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates only that HMAC (i.e., only the body) and then dispatches the handler using the unauthenticated header values: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the raw body in the webhook case — the `shop`, `topic`, and `webhook_id` headers are never part of the signed material: [4](#0-3) 

The identity binding this breaks is:
`hmac_secret_key.sign(raw_body) == received_hmac` while the app trusts `request.shop` (a header) as if it were `hmac_secret_key.sign(raw_body ‖ shop)`. Because `shop` is outside the signed scope, `signed_bytes != data_the_handler_acts_on`.

### Impact Explanation
An app that keys any tenant-scoped action (e.g., "which merchant does this webhook belong to", using `WebhookMetadata#shop` passed to `handler.handle`) purely off `request.shop`/`request.topic` can be made to process attacker-controlled tenant/topic values while still passing signature validation, since the signature only proves the body is unmodified — not which shop or topic it was issued for. An attacker who can obtain one validly-signed body/HMAC pair (e.g., by installing the app on their own store and capturing a legitimate webhook delivery, which requires no privileged credentials) can resend that exact body+HMAC to the app's shared webhook endpoint with a forged `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header. If the host application uses `data.shop` from `WebhookMetadata` to determine which merchant record to update, this crosses a tenant boundary — the classic "field acted on but not covered by the HMAC" pattern called out in the reference report (there, `mint_stable_coin`'s caller identity wasn't checked; here, the webhook's shop/topic identity isn't checked because it's outside the signed scope while the HMAC-checking code silently proceeds).

### Likelihood Explanation
Any Shopify app receiving webhooks and using this gem is affected identically, since `Registry.process` is the only entry point provided and it always performs this split validation. The header values are attacker-controllable at the HTTP layer (any process that can reach the endpoint can set arbitrary headers on the raw request); no access token, `api_secret_key`, or TLS interception is needed, only a body+HMAC pair the attacker can legitimately obtain by triggering a webhook to their own shop.

### Recommendation
Extend the signable material used for webhook HMAC validation to include the `shop`, `topic`, and `webhook_id` headers (or otherwise cryptographically bind them, e.g. by validating that the shop domain in the header matches an expected value derived from a trusted source before dispatch), so that `HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually signed for. At minimum, document that host applications must not trust `WebhookMetadata#shop`/`#topic` without an independent tenant check.

### Proof of Concept
1. Attacker installs the target app on their own development shop (`attacker.myshopify.com`) and receives a legitimate webhook delivery for topic `orders/create` — capturing the raw body and the corresponding `X-Shopify-Hmac-Sha256` value.
2. Attacker sends a request to the app's webhook endpoint with the **same raw body and HMAC**, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (the raw body) — this succeeds because the body is unchanged. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` containing the forged `victim.myshopify.com` value, even though that value was never covered by the signature. [6](#0-5)
