### Title
Accrual-time RAY value overflow permanently freezes a market — repay, withdraw and liquidation all revert (File: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`)

### Summary
Every mutating entrypoint on the controller and pool accrues interest before it acts. Accrual converts scaled debt/supply into RAY values via `scaled_to_original`, which panics with `MathOverflow` once `scaled_amount * index` leaves `i128`. An unprivileged user can drive a market into this state — by seeding a whale-scale supply book and holding utilization high — at which point the panic is in the shared prelude of every operation: `repay`, `withdraw`, `liquidate`, `borrow` and even `update_indexes` itself all revert permanently. All supplier funds and all borrower collateral in that market are frozen forever. This mirrors the CVE-2021-40608 class: an attacker-reachable input/state causes an unhandled abort that kills the code path, not just the offending call.

### Finding Description
The crash is not in a caller-controlled argument (those are validated) but in a market state an unprivileged address can construct:

1. `supply`/`borrow` are permissionless up to the admitted caps; the token-to-RAY input maximum is ~170 billion whole tokens per listing (`docs/reference/formulas.md` "Caps, fees, and numeric limits"). A whale supplies and a borrower (can be the same entity via a second account) borrows near the utilization steep segment of the rate curve.
2. Interest accrues in `interest::global_sync` / `accrue_step`. Both indexes are capped (`MAX_BORROW_INDEX_RAY` = 10^36), but the *value* product `scaled_to_original(shares, index)` panics with `GenericError::MathOverflow` well before the index cap engages — the certora spec notes `update_supply_index` panics via `supplied.mul(old_index)` once the product leaves `i128` (`certora/common/spec/rates_rules.rs:316-320`), and `mul_div_*` panic on overflow in `common/src/math/fp_core.rs:104-118`.
3. Once the debt value crosses the representable bound, the next accrual traps. Because accrual runs first inside every verb — and inside the permissionless `update_indexes` keeper itself — there is no reachable call that skips it. `docs/reference/formulas.md:433-437` states this explicitly: "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."

The project test proves the end state, not just the theory: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` seeds a ~1 billion-token 18-decimal market at 98% utilization on the XLM curve, advances time until `update_indexes` fails with `MATH_OVERFLOW` below the index cap, and then asserts `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW` — "the market is frozen: no repay, no withdraw, no liquidation" [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Impact Explanation
Permanent freezing of funds. Every supplier's deposit and every borrower's collateral in the affected market becomes unrecoverable: withdrawals, repayments and liquidations all revert in the accrual prelude, and no privileged escape hatch can bypass the panic (governance can delist or pause, but cannot return the trapped tokens). This is market-wide, not per-account.

### Likelihood Explanation
Medium-low but non-zero. It requires a market near the admitted size ceiling (~170B whole tokens for an 18-decimal asset) and sustained very high utilization for the index to compound far enough — the harness observes the cliff within 40 simulated years on the steepest configured curve, and sooner for curves/parameters with higher rates or lower-decimal assets where the RAY headroom per token is smaller. An attacker with sufficient capital (or a market that grows organically into this regime) can hold utilization pinned by supplying and borrowing through separate accounts; `update_indexes` being permissionless means the attacker — not a keeper — controls when the final accrual is submitted, so the freeze can be timed to trap the maximum balance. Once reached it is irreversible: the panic is in shared code, so no subsequent call can unwind it.

### Recommendation
Make accrual saturate rather than panic: at the point `scaled_to_original` would overflow, clamp the borrow index progression (or the value computation) the same way `mul_div_floor_saturating` is used elsewhere (`common/src/math/fp_core.rs:177-201`), or enforce a hard invariant that accrued market value stays representable by capping `borrow_index` dynamically as a function of `supplied`/`borrowed` so the product can never exceed `i128::MAX`. A cheaper mitigation is a supply-side admission check that refuses deposits/borrows which would let `shares × MAX_BORROW_INDEX_RAY` overflow, so the cliff is unreachable in admitted states.

### Proof of Concept
The repository already contains the executable PoC — `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);            // unprivileged supply
let debt = principal / 100 * 98;
t.borrow_raw(ALICE, "BIG18", debt);               // unprivileged borrow, ~98% util.
// advance time until accrual overflows i128 inside scaled_to_original:
//   t.try_update_indexes_for(&["BIG18"]) -> Err(MATH_OVERFLOW), below MAX_BORROW_INDEX_RAY
// then every verb accrues first and hits the same panic:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Caller path: `controller::withdraw`/`repay`/`liquidate` → `pool` mutation → `interest::global_sync` → `accrue_step` → `scaled_to_original` → `mul_div_*` panic in `common/src/math/fp_core.rs`. No auth, privilege, or governance action is needed to reach the frozen state; it is induced purely by market size and elapsed accrual.

Caveat: this overflow cliff is disclosed in `docs/reference/formulas.md` as an arithmetic limit rather than a hidden defect, so a triager may judge it a documented boundary; however the accepted impact class (permanent freezing of funds reachable by unprivileged supply/borrow) is demonstrated, and the documentation explicitly says these are "arithmetic limits, not ... deployment proofs."

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {

        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```

```rust
/// Residual hidden bound: `update_supply_index` computes
/// `supplied.mul(old_index)`, which panics with `MathOverflow` once
/// `supplied * old_index / RAY` leaves `i128`. Sunbeam treats that panic as
/// `assume(false)`, so the trap, not an assume, prunes the upper corner of the
/// `supplied x old_index` box. The assertion is proved on the rest.
#[rule]
fn update_supply_index_capped(e: Env, supplied: i128, old_index: i128, rewards: i128) {
    cvlr_assume!((0..=1_000_000 * RAY).contains(&supplied));
    cvlr_assume!((SUPPLY_INDEX_FLOOR_RAW..=MAX_SUPPLY_INDEX_RAY).contains(&old_index));
    cvlr_assume!((0..=MAX_RAY_VALUE).contains(&rewards));

    let out = update_supply_index(
        &e,
        Ray::from(supplied),
        Ray::from(old_index),
        Ray::from(rewards),
    );
    cvlr_assert!(out.raw() <= MAX_SUPPLY_INDEX_RAY);
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```
