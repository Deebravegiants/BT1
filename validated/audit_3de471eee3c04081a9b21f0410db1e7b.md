### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing shop-domain spoofing via signature replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating the HMAC over the raw body only, then hands the caller-supplied `shop-domain` header — which is *not* part of the signed material — to the app's handler as the trusted tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the HMAC purely over `to_signable_string` (the body): [3](#0-2) 

`Registry.process` calls this validator, then immediately forwards the **unauthenticated** `request.shop` value into `WebhookMetadata`, which is passed to the app's handler as the tenant identity for the event: [4](#0-3) 

The identity binding that should hold is: `shop_value_verified_by_hmac == shop_value_used_by_handler`. Because the HMAC only covers the body bytes, this equality does not hold — the `shop` header can be swapped for an arbitrary value while the HMAC signature (computed over the unchanged body) remains valid.

### Impact Explanation
An unprivileged internet user can obtain a genuinely-signed webhook body + HMAC pair for a shop they control (e.g., by installing the target app on their own store and observing/capturing the resulting webhook delivery, or via any endpoint that echoes/logs raw body+HMAC). They can then replay that exact `raw_body`/`x-shopify-hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a different, victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it only checks the body against the secret), and `Registry.process` will invoke the registered handler with `WebhookMetadata#shop` set to the spoofed victim domain. Any host application logic that keys off `data.shop` (e.g., looking up the victim's session/access token, writing data associated with the victim shop, or triggering shop-scoped side effects) is executed under the wrong tenant — a cross-tenant confusion condition.

### Likelihood Explanation
Requires only a self-service app install (or ability to capture one's own genuine webhook delivery) plus a single HTTP replay with one modified header — no access to the app's `client_secret` or any merchant's access token is needed. This is directly reachable by any unprivileged internet user who can install the app on a shop they control.

### Recommendation
Bind the tenant/shop identity into the signed material, or independently verify `request.shop` against a value derived from an authenticated source (e.g., cross-check the `webhook_id`/topic against records created for the session associated with the shop, or require the host application to only trust `shop` after confirming HMAC coverage includes the header, e.g., by hashing `shop + topic + body` server-side or validating the shop against the known set of shops for which registration occurred with a matching webhook id looked up server-side rather than trusting the header value at face value).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a legitimate webhook delivery with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac>`, and some `raw_body`.
2. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook route, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the secret (`lib/shopify_api/utils/hmac_validator.rb` line 26-31; `lib/shopify_api/webhooks/request.rb` line 35-38).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` line 188-200) invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from, and was signed for, the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
