Audit Report

## Title
Path traversal in workflow artifact HTTP fetcher via unvalidated `filepath.Join` on attacker-controlled URL - (File: `core/services/workflows/syncer/v2/fetcher.go`)

## Summary
`newHTTPFetcher` in `core/services/workflows/syncer/v2/fetcher.go` builds the fetch URL by joining a configured base path with `req.URL`, which originates from the on-chain workflow registry's `binaryURL`/`configURL`. Unlike its sibling `newFileFetcher`, which explicitly re-verifies the joined path stays within `basePath` via a prefix check, `newHTTPFetcher` never performs an equivalent containment check after the `filepath.Join`, allowing `..` sequences in `req.URL` to make the resulting request target paths outside the intended base path on the configured artifact-storage host.

## Finding Description
`newHTTPFetcher` cleans `req.URL` in isolation (`filepath.Clean(req.URL)`) and trims a leading `/`, then does `u.Path = filepath.Join(u.Path, cleanPath)`. [1](#0-0) 
`filepath.Join` normalizes `..` across the combined string, so a `req.URL` such as `../../secret.bin` collapses segments of the base path itself, escaping the intended directory — there is no subsequent check that the result is still prefixed by the original base path, unlike `newFileFetcher`, which performs exactly this check: [2](#0-1) 

`req.URL` is populated directly from `binaryURL`/`configURL` passed into `FetchWorkflowArtifacts`, which come from workflow registry entries (attacker/registrant-controlled) and are handed unmodified to `h.fetchFn` (the configured `FetcherFunc`): [3](#0-2) 

The HTTP fetcher path is only reachable when `NewFetcherFunc` is configured for an `http`/`https` base URL: [4](#0-3) 
which happens only when the node operator has explicitly set `CRE.WorkflowFetcher.URL`, wired through `opts.FetcherFunc` in `newFetcherServiceV2`: [5](#0-4) [6](#0-5) 

This is a real code-level bug: the containment check present in `newFileFetcher` is genuinely absent in `newHTTPFetcher`, confirmed by direct code reading.

## Impact Explanation
If exploited, the impact is limited to fetching arbitrary paths from the *same host* the operator configured as the artifact-storage server (SSRF-style traversal to sibling paths on that host), not from the node's local filesystem or a different host, since `url.Parse(baseURL)` retains the original scheme/host and only `u.Path` is mutated. The disclosed content would be whatever static/dynamic resource lives at that path on the storage host — this could match a CWE-22/information-disclosure class, but the practical blast radius depends entirely on what other resources happen to be co-located on the operator's storage host.

Importantly, this data path is used only when the operator opts out of the default gateway/DON-consensus fetch mechanism and instead points the node directly at an HTTP artifact store — a configuration described in the code itself as "bypasses the gateway." This is a non-default, operator-opt-in bypass mode intended primarily for local/test CRE environments.

## Likelihood Explanation
Exploitation requires: (1) the node operator to have configured `CRE.WorkflowFetcher.URL` with an `http`/`https` scheme (an explicit administrative choice to disable the default trust model), and (2) the operator's artifact-storage host to have other sensitive resources reachable via relative path traversal from the configured base path. Both are operator-configuration-dependent conditions, not properties of default node behavior. The underlying workflow-registration step is attacker-controlled and cheap, but the overall exploit is gated by an operator opt-in/misconfiguration precondition (using a non-default fetch bypass mode against a storage host with traversable, unintended sibling content), which the validation rules classify as an operator-configuration-dependent scenario rather than a vulnerability exploitable against a node in its default, unprivileged-actor-facing configuration.

## Recommendation
In `newHTTPFetcher`, after computing `u.Path = filepath.Join(u.Path, cleanPath)`, verify the resulting path is still prefixed by the original base path (`strings.HasPrefix` check equivalent to the one in `newFileFetcher`) and reject the request otherwise, to defense-in-depth harden this opt-in fetch mode regardless of operator configuration.

## Proof of Concept
1. Configure `CRE.WorkflowFetcher.URL = https://storage.example.com/workflows`.
2. Register (or simulate) a workflow with `binaryURL = ../../other-tenant/secret.bin`.
3. Call `FetchWorkflowArtifacts`, which invokes `newHTTPFetcher`'s closure with `req.URL = "../../other-tenant/secret.bin"`.
4. `u.Path` becomes `filepath.Join("/workflows", "../../other-tenant/secret.bin")` = `/other-tenant/secret.bin`, and the node issues an HTTP GET to `https://storage.example.com/other-tenant/secret.bin`, outside `/workflows`.
5. A unit test asserting `newHTTPFetcher(...)("../secret")` produces a request URL outside the base path (contrasted with `newFileFetcher` returning an error for the analogous case) would confirm the missing containment check.
