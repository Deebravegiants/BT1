### Title
Unchecked `checked_sub().unwrap()` panic in `swap_token_amount_base_out` allows any user to abort/DoS `SwapBaseOut` transactions with attacker-chosen `amount_out` - ([File: program/src/math.rs])

### Summary
`Calculator::swap_token_amount_base_out` (`program/src/math.rs:327-367`) computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or the coin-side equivalent) using the pool's live vault-derived reserves and the **unvalidated** `swap.amount_out` field taken directly from instruction data. This function is called from `process_swap_base_out` and `process_swap_base_out_v2` in `program/src/processor.rs` at lines 2172 and 2551, respectively — both calls happen *before* the only reserve-sufficiency check (`if swap.amount_out >= total_pc_without_take_pnl { return Err(...) }` / the coin equivalent) which is located later inside the `match swap_direction` arms (lines 2212-2238 and 2591-2617). [4](#0-3) 

### Finding Description
Any unprivileged caller can submit a `SwapBaseOut`/`SwapBaseOutV2` instruction with `amount_out` set to a value greater than or equal to the current `total_pc_without_take_pnl` (for `Coin2PC`) or `total_coin_without_take_pnl` (for `PC2Coin`). Because `swap_token_amount_base_out` is invoked with the raw, unchecked `amount_out` before the corresponding sufficiency check runs, `total_pc_without_take_pnl.checked_sub(amount_out)` (or the coin equivalent) returns `None`, and the immediately chained `.unwrap()` at `program/src/math.rs:341` (or `:358`) panics. [5](#0-4) 

Since the reserve values (`total_pc_without_take_pnl`/`total_coin_without_take_pnl`) come directly from the pool's live token-vault balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`) fed into `Calculator::calc_total_without_take_pnl_no_orderbook`, and `amount_out` is a raw `u64` fully attacker-controlled in the instruction payload, no signer privilege or special account is required — any account can be passed as `user_source_owner`/`user_destination_info` as long as the mint/PDA checks pass, and `amount_out` merely needs to exceed the pool's reserve on one side. This is directly analogous to the CVE-2024-44775 bug class: attacker-supplied protocol input reaches an unguarded null/undefined-value dereference (here, `Option::None` from `checked_sub`) before validation, causing an unhandled panic and process abort of instruction execution. [6](#0-5) 

### Impact Explanation
A Solana program panic causes the transaction to fail/abort (returns a runtime error), which does not crash the validator process itself, but it does deterministically deny the `SwapBaseOut`/`SwapBaseOutV2` instruction path for any caller who submits such a malformed `amount_out`, and more importantly it demonstrates a hard availability/reliability defect: the intended slippage/liquidity-sufficiency guard (`AmmError::InsufficientFunds`) is unreachable for these edge inputs because the panic occurs first. This is a control-flow ordering bug that converts what should be a clean, catchable `ProgramError` into an unrecoverable panic, undermining the deterministic error-handling contract these swap instructions are documented to provide, and blocking legitimate swap composability that depends on receiving a proper error instead of a panic (e.g., downstream aggregators/CPI callers cannot gracefully catch a panic the same way as a returned `ProgramError`).

### Likelihood Explanation
High likelihood of trigger — an attacker only needs to submit a single `SwapBaseOut` or `SwapBaseOutV2` instruction (both reachable by any unprivileged swapper) with `amount_out` set to a value at or above the current pool reserve on the relevant side, which is public/observable on-chain state. No special accounts, signatures, or privileges beyond a valid signer for `user_source_owner` are required.

### Recommendation
Move the sufficiency check (`swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl`) to occur immediately after computing `swap_direction` and before calling `Calculator::swap_token_amount_base_out`, in both `process_swap_base_out` and `process_swap_base_out_v2`. Additionally, harden `swap_token_amount_base_out` itself to return a `Result`/`Option` instead of relying on `.unwrap()` after `checked_sub`, propagating a proper `AmmError` (e.g., `AmmError::InsufficientFunds` or `AmmError::CalculationExRateFailure`) instead of panicking.

### Proof of Concept
1. Identify an active Raydium AMM pool with known `total_pc_without_take_pnl` (derivable from `amm_pc_vault.amount` and `AmmInfo` pnl fields via `calc_total_without_take_pnl_no_orderbook`).
2. Construct a `SwapBaseOut` instruction (`program/src/instruction.rs`) targeting that pool, setting `swap.amount_out` to a value `>= total_pc_without_take_pnl` (for the `Coin2PC` direction, i.e., `user_source` = coin mint, `user_destination` = pc mint) and any `max_amount_in`.
3. Submit the transaction with a valid signer for `user_source_owner` and correctly derived PDA/vault accounts (all publicly known/derivable) — no elevated privilege needed.
4. Execution reaches `process_swap_base_out` → `Calculator::swap_token_amount_base_out(swap.amount_out, total_pc_without_take_pnl, total_coin_without_take_pnl, Coin2PC)` at `program/src/processor.rs:2172`, which computes `total_pc_without_take_pnl.checked_sub(amount_out)` returning `None`, and `.unwrap()` panics at `program/src/math.rs:341`, aborting the instruction before the `AmmError::InsufficientFunds` check at `program/src/processor.rs:2214` is ever reached.

        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc

                    .unwrap()
