### Title
Authorization-code OAuth flow builds the authorize redirect and the client_secret/code exchange host from an unvalidated `shop` string, unlike sibling flows - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` both derive the *host* they talk to (the Shopify authorize URL, and later the `/admin/oauth/access_token` endpoint that receives the app's `client_secret` and the authorization `code`) directly from a caller-supplied `shop` string, with no call to `ShopifyAPI::Utils::ShopValidator.sanitize!`. Every other credential-exchange flow in this gem (`RefreshToken.refresh_access_token`, `TokenExchange.exchange_token`, `ClientCredentials`) explicitly sanitizes `shop` through `ShopValidator` before using it to build a request host. `oauth.rb` is the one exception.

### Finding Description
`begin_auth` builds the redirect target purely from the raw `shop` argument: [1](#0-0) 
and returns `auth_route = auth_base_uri(shop) + "/oauth/authorize?..."` with no `ShopValidator` call anywhere in the method: [2](#0-1) 

`validate_auth_callback` then takes `auth_query.shop` — a field that is present in the `AuthQuery` object built from raw callback query-string parameters — and uses it, again unsanitized, to construct the session/host that receives the app's `client_secret` and the authorization `code`: [3](#0-2) 
`null_session = Auth::Session.new(shop: auth_query.shop)` feeds `Clients::HttpClient`, which builds the outbound POST target purely from `session.shop`: [4](#0-3) 

The only integrity check present is `Utils::HmacValidator.validate(auth_query)`, which confirms the callback's query fields (`code`, `host`, `shop`, `state`, `timestamp`) were signed with the app's own `api_secret_key`: [5](#0-4) 
That check only proves the query string wasn't tampered with after Shopify (or whoever knows the api_secret_key) signed it — it does **not** independently prove `shop` is a trusted `*.myshopify.com`/`*.myshopify.io`/etc. host the way `ShopValidator` does: [6](#0-5) 

Contrast with `RefreshToken.refresh_access_token`, which explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using `shop` to build the request host that receives `client_secret`: [7](#0-6) 
`TokenExchange.exchange_token` similarly derives the shop from a JWT `dest` claim rather than a raw request field: [8](#0-7) 

The identity binding that is broken: *the host that is validated as "the shop"* (nothing, in `begin_auth`/`validate_auth_callback`) versus *the host that actually receives the app's `client_id`, `redirect_uri`, and later `client_secret`+authorization `code`* (whatever string the request supplied as `shop`). Because `begin_auth`'s `shop` parameter comes straight from application/router input (the docs' own example takes it from `request.headers["Shop"]` with no sanitization shown), an unprivileged internet user who can influence that parameter (e.g., via `shop=` in the login URL of a host app that follows this gem's documented usage) can force the OAuth-authorize redirect to point at an attacker-controlled host instead of Shopify. That host then receives the app's `client_id`, the `redirect_uri`, and the CSRF `state` nonce that this gem places in the victim's session cookie — information that is otherwise only supposed to reach Shopify.

### Impact Explanation
An attacker who captures the `state` value from a diverted authorize request can pair it with a separately obtained, genuinely Shopify-signed callback (from a shop the attacker themselves controls/owns) and force it onto the victim's browser. Because `validate_auth_callback`'s only anti-CSRF check is `state == auth_query.state` against the victim's cookie, this can bind the victim's session to a shop of the attacker's choosing — a forced OAuth completion / session-fixation outcome, one of the explicitly listed High-severity impacts for this analysis. This is squarely a defect in this gem's own code path (`lib/shopify_api/auth/oauth.rb`), not a case of a host application ignoring documented usage, since the sibling flows in the same gem (`refresh_token.rb`, `token_exchange.rb`, `client_credentials.rb`) demonstrate that `ShopValidator` sanitization is the gem's own established, expected control for exactly this kind of host derivation.

### Likelihood Explanation
Exploitation requires the attacker to run their own server, own (or have access to) a real Shopify store to obtain one genuinely-signed HMAC callback, and to get a victim (an authenticated admin/merchant user of the app) to visit two crafted links in sequence — a multi-step but fully unprivileged, internet-reachable attack chain with no need for the app's `api_secret_key` or an existing access token.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize the `shop` parameter through `ShopifyAPI::Utils::ShopValidator.sanitize!` in `begin_auth` before it is used to construct `auth_base_uri(shop)`, and sanitize `auth_query.shop` the same way in `validate_auth_callback` before constructing `null_session`/`Clients::HttpClient`, mirroring the pattern already used in `refresh_token.rb` and `token_exchange.rb`.

### Proof of Concept
1. Attacker sends victim (a logged-in user of the host app) a link to the app's login route with `shop=attacker-controlled.example`.
2. `Oauth.begin_auth(shop: "attacker-controlled.example", ...)` sets a `state` nonce cookie on the victim and redirects the victim's browser to `https://attacker-controlled.example/admin/oauth/authorize?client_id=<app client id>&redirect_uri=<legit callback>&state=<NONCE>&...` (per `auth_base_uri`/`begin_auth` — [2](#0-1) ), leaking `client_id`, `redirect_uri`, and `state` to the attacker's server instead of Shopify.
3. Separately, the attacker performs a real install flow on their own Shopify store to obtain a genuinely Shopify-signed `code`/`hmac` pair for `shop=attacker-store.myshopify.com`.
4. The attacker builds `https://<legit-app>/callback?code=<real code>&shop=attacker-store.myshopify.com&timestamp=...&host=...&hmac=<real hmac>&state=<captured NONCE>` and forces the victim's browser to load it.
5. `validate_auth_callback` passes HMAC validation (genuinely signed) and state validation (matches victim's cookie) — [9](#0-8)  — completing OAuth and binding the victim's session/cookie to the attacker's shop.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
