### Title
Webhook `shop-domain` header is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw JSON body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are taken straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then dispatches the handler using the header-derived `shop`, `topic`, etc. Because the app's `api_secret_key` (Shopify client secret) is a single secret shared across every shop that installs the app, any signed webhook body an attacker legitimately receives on their own test/attacker-controlled shop remains validly signed no matter which `shop-domain` header value is attached to the replayed request. This breaks the intended binding: `shop asserted in header == shop authenticated by HMAC`.

### Finding Description
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, and `api_version` are read straight from request headers, none of which participate in the signed string: [2](#0-1) 
- `HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string` (i.e., the body), with no binding to header fields: [3](#0-2) 
- `Registry.process` validates that body HMAC and then immediately trusts `request.shop` (a header) to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because a Shopify app's `client_secret` (`api_secret_key`) is the same for all shops that install the app, the HMAC computed over a given raw body is identical regardless of which shop actually generated the event. An unprivileged attacker can:
1. Install the target (public) app on their own attacker-controlled development/test shop.
2. Receive a legitimately-signed webhook (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`) from Shopify for their own shop — capturing the raw body and its valid `X-Shopify-Hmac-Sha256` value.
3. Replay that exact raw body + HMAC to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain (and/or a different `topic`/`webhook-id`).
4. `HmacValidator.validate` succeeds (the body's HMAC is still valid), and `Registry.process` calls the app's webhook handler with `shop: <victim-shop>` even though the payload never originated from that shop.

This is directly analogous to the reported oracle issue's root cause: a value that is acted upon (`shop`) is not covered by the integrity check (`HMAC`) that is meant to authenticate the whole message.

### Impact Explanation
This is a cross-tenant confusion/injection vector: the receiving app will process attacker-supplied, attacker-controlled event data (order contents, customer data, install/uninstall events, etc.) as if it were authentic data from a victim merchant's shop, since the `shop` binding used by downstream app logic (`WebhookMetadata#shop`) is not authenticated. Depending on how a downstream app uses this shop value (e.g., writing/merging records keyed by shop, triggering data deletion on `app/uninstalled`, GDPR data requests), this enables cross-tenant data corruption or spoofed lifecycle events attributed to a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only: (a) the ability to install the target app on any shop (trivial for public apps, which self-installable by any Shopify merchant/developer account), and (b) network access to the app's public webhook endpoint. No leaked credentials, TLS interception, or privileged account access is needed — the attacker only needs their own legitimately-issued webhook signature, which by design is not scoped to their shop.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed content, or otherwise independently verify that the header-provided `shop-domain` corresponds to a shop this app installation actually expects/owns before dispatching to handlers. At minimum, cross-check the `shop-domain` header against a shop-specific secret/session record (e.g., per-shop offline token existing) rather than trusting it solely because the shared app-level HMAC validated the body.

### Proof of Concept
1. Install the target Shopify app on attacker-owned dev shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., update an order) so Shopify sends a webhook POST to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
3. Capture `B` and `H` (attacker fully controls their own endpoint's traffic/logs, or proxies the callback).
4. Resend an HTTP POST to the same app webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (body/HMAC pair unchanged), and `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"`, `body: <attacker's order/customer data>` — demonstrating that the shop attribution is unauthenticated.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
