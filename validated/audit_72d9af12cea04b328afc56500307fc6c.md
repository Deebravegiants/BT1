Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the app's `WebhookHandler` are taken from unauthenticated HTTP headers that the HMAC never covers. This breaks the identity binding `shop authenticated == shop attributed to the webhook payload`, letting anyone who possesses one valid `(body, hmac)` pair for the app's shared secret relabel that payload as belonging to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are never part of the signed material: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then immediately builds the trusted `WebhookMetadata` object using `request.shop` — the unauthenticated header value — and dispatches it to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further validation, and the app-level `WebhookHandler#handle` interface receives it as authenticated fact: [4](#0-3) 

Crucially, `api_secret_key` is a single **app-wide** secret shared across every shop that installs the app — it is not per-shop. `HmacValidator.validate` only proves the body was signed with *some* valid secret for the app; it proves nothing about which shop the request is "from": [5](#0-4) 

**Attack sequence:**
1. An attacker installs the target app on their own store, `attacker.myshopify.com` (an ordinary, unprivileged merchant action — no special access needed).
2. Shopify sends the attacker's own store a genuine webhook, HMAC-signed with the app's shared `api_secret_key`. The attacker captures this `(raw_body, x-shopify-hmac-sha256)` pair.
3. The attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) body against the (unmodified) HMAC header — the `shop` header is invisible to this check.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/persists data as if it genuinely originated from the victim shop.

**Equality broken:** `shop authenticated by HMAC` (nothing — HMAC binds only to the body) `!=` `shop attributed to the webhook payload` (`request.shop`, an arbitrary attacker-controlled header).

### Impact Explanation
This is a cross-tenant identity-spoofing vector: an app built on this gem's documented `Registry.process` API cannot distinguish "this event body is genuinely from shop X" from "this event body is genuinely from *some* shop using this app, but headers claim it's shop X." Any app logic that trusts `WebhookMetadata#shop` to select which merchant's records to update, credit, or delete is exposed to cross-tenant data injection/corruption using another real tenant's identity, satisfying the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is Medium-High: exploitation requires no privileged credentials, no `api_secret_key`, and no TLS interception — only ordinary self-service app installation on an attacker-controlled store to harvest one valid signed payload, then a single forged HTTP POST to the app's own public webhook endpoint with a different `shop` header. This fits the "unprivileged internet user" threat model since the webhook secret is shared across all shops for a given app.

### Recommendation
Bind the shop identity into the signed material, or otherwise verify it independently of the header:
- Have `Registry.process` (or `HmacValidator`) require that the shop claimed in the request corresponds to a shop with a legitimate, currently-installed session/access token before dispatching, rather than trusting the raw header.
- Alternatively, document explicitly (and enforce in code) that `WebhookMetadata#shop` is unauthenticated header data and that consuming applications MUST cross-check it against their own session/shop store before acting on it — currently `docs`/API surface implies it is trustworthy webhook metadata.
- Consider incorporating the `shop` domain into the HMAC computation performed by this gem (if compatible with Shopify's webhook signing scheme) or reject requests where the header shop does not match a shop this app has an active installation/session for.
