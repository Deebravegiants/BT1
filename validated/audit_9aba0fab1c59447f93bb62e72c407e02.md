### Title
Webhook `shop-domain` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies its HMAC only over the raw request body, while the `shop` (tenant) identity that the gem hands to the host application's handler is read from an HTTP header that is completely outside the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in that signable string [2](#0-1) . `Utils::HmacValidator.validate` verifies the received HMAC strictly against `to_signable_string` (the body) using `OpenSSL.secure_compare` [3](#0-2) . `Registry.process` trusts this validation and then forwards `request.shop` straight into `WebhookMetadata`, which is the tenant-identifying field the host app's `WebhookHandler#handle` uses to attribute the payload to a shop [4](#0-3) , [5](#0-4) .

The broken identity binding, stated as an equality that should hold but does not:
`hmac == HMAC(secret, raw_body)` is verified, but the gem also treats `shop == header["shopify-shop-domain"]` as authenticated tenant identity — even though `shop` is not part of the signed bytes. Before the request: attacker has a legitimately-delivered, correctly-signed webhook body+HMAC for any shop that can trigger a webhook to their own endpoint (e.g. their own dev/test store, or one they can generate events for). After the request: attacker resends the identical `raw_body`/`hmac` pair to the app's webhook endpoint, substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` because it only checks the (unchanged) body against the (unchanged) HMAC — the header substitution is invisible to the check [6](#0-5) , [7](#0-6) . `Registry.process` then passes the attacker-chosen `shop` value on to the handler as if it were authenticated [8](#0-7) .

### Impact Explanation
Any host application that keys per-tenant behaviour off `WebhookMetadata#shop` (e.g. looking up the offline session/access token for that shop, updating that shop's data, deciding which merchant's webhook subscription this is) can be made to process a validly-HMAC'd payload under a different shop's identity, because the gem itself provides no cross-check between the signed body and the header-derived shop. This is a cross-tenant identity-confusion vector satisfying the Critical "cross-tenant access" impact category, since the *gem's own verification primitive* (`Utils::HmacValidator`) offers no guarantee about the `shop` field despite it being the field callers rely on for tenant attribution.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one validly signed `(raw_body, hmac)` pair — obtainable by owning a shop/dev store that installs the target app (a normal, unprivileged action) and capturing a webhook it triggers, or by intercepting any webhook payload sent to a shared/public endpoint. No `api_secret_key`, access token, or privileged credential of the app is needed to perform the replay itself; only header manipulation on an otherwise-unauthenticated HTTP request to the merchant's webhook endpoint. Reaching real damage additionally depends on how the host app uses `WebhookMetadata#shop`, which is outside this gem's control, but the gem's `Request`/`Registry`/`HmacValidator` code path itself provides no mitigation.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the bytes that are HMAC-verified, or otherwise cryptographically bind the header-derived shop to the signed body before it is exposed via `Request#shop`/`WebhookMetadata`. At minimum, document in `Utils::HmacValidator`/`Webhooks::Request` that `shop`, `topic`, and other headers are unauthenticated and must not be used by consuming applications as a sole tenant-identity source without an independent check (e.g. cross-referencing against the shop embedded in `parsed_body`, when present, or against the shop tied to the currently loaded offline session).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value sent by Shopify.
2. Attacker POSTs the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers, exposing `shop => "victim-shop.myshopify.com"` [2](#0-1) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`raw_body`, unchanged) and succeeds [9](#0-8) , [3](#0-2) .
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and, if it uses this value to select the target shop's session/data (a common pattern), processes/updates the wrong tenant's data using the attacker's payload [10](#0-9) .
