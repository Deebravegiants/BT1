### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by checking only that the HMAC over the raw request body matches, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers to dispatch the payload to the app's business logic. Because the HMAC signature never covers these headers, and the signing secret (`api_secret_key`) is shared across every shop that installs the app, any party who can obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store and receiving genuine webhook deliveries) can replay that exact body/HMAC pair with arbitrary `shop-domain`, `topic`, and `webhook-id` headers. The gem will accept it as an authentic webhook "from" any shop the attacker names, crossing the tenant boundary the `shop` field is supposed to enforce.

### Finding Description
The bug-class described in the report is: a value that downstream logic depends on for correctness/identity is not bound by the same check that grants trust — here it is the analog of "unrealized loss not covered by the PnL update," and in this gem the analogous broken equality is:

`bytes verified by HMAC (raw_body only)` ≠ `bytes used to establish shop identity (shop-domain / topic / webhook-id headers)`

Concretely:
- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, and `webhook_id` are all read straight from HTTP headers, entirely outside the signed material: [2](#0-1) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and the app's `api_secret_key`, with no dependency on shop/topic/webhook_id: [3](#0-2) 
- `Registry.process` gates entirely on this body-only HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because `api_secret_key` is a single app-level secret (not per-shop), the HMAC over a given body is identical no matter which shop the webhook is "for." An attacker who installs the target app on a shop they control will receive genuine webhook deliveries with valid `(body, hmac)` pairs signed by that shared secret. Nothing prevents them from re-POSTing that exact body and hmac to the app's webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally any `topic`/`webhook-id`). `HmacValidator.validate` will report success because it only ever re-derives the signature from the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` even though the request never actually originated from Shopify on behalf of that shop.

### Impact Explanation
This breaks the tenant-identity binding the gem is supposed to provide to the host application: a webhook handler that keys any business logic off `WebhookMetadata#shop` (billing, deauthorization/GDPR, order sync, per-shop feature toggles, etc.) can be made to act on behalf of, or inject state for, a shop the attacker has no relationship with — cross-tenant access/spoofing achieved purely from the gem's own trust logic, without needing the victim's access token or `client_secret`. This matches the Critical category ("cross-tenant access").

### Likelihood Explanation
Medium-to-High: exploitation requires only that the attacker be able to install the target app on a shop they control (any unprivileged internet user can typically do this for a public app) to legitimately harvest one or more valid `(body, hmac)` pairs, then replay them with a forged `shop-domain` header at the app's own webhook endpoint. No secrets, tokens, or elevated privileges are required beyond normal app installation.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signed material the HMAC covers, or otherwise cryptographically bind the header-derived tenant identity to the verified body (e.g., verify the shop domain against the session/shop the delivery was registered for, rather than trusting the header value directly) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g. `orders/create`), receiving a legitimate POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(app_secret, B)`.
2. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `B` with the shared `api_secret_key` and it matches `H`, so `Registry.process` proceeds. [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and any host-app logic keyed on `shop` executes as though Shopify itself delivered this event for `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
