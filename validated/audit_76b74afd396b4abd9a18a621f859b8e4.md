Audit Report

## Title
`paras_registrar::deregister` bypasses `assigned_slots::unassign_parachain_slot`, orphaning `TemporarySlots`/`TemporarySlotCount` accounting - (File: polkadot/runtime/common/src/assigned_slots/mod.rs)

## Summary
`assign_temp_parachain_slot` can insert a `TemporarySlots` entry and increment `TemporarySlotCount` without creating a `slots::Leases` entry or transitioning the para's `ParaLifecycle` away from `Parathread`, which happens whenever the slot is scheduled for `SlotLeasePeriodStart::Next` or the current period's `MaxTemporarySlotPerLeasePeriod` cap is reached. Because `paras_registrar::do_deregister` only inspects `paras::Pallet::lifecycle(id)` and never consults `assigned_slots` storage, a para manager can call `deregister` via `ensure_root_para_or_owner` (an unprivileged signed path), completely bypassing the `AssignSlotOrigin`-gated `unassign_parachain_slot` cleanup and leaving `TemporarySlots`/`TemporarySlotCount` permanently desynchronized.

## Finding Description
In `assign_temp_parachain_slot`, the lease is only synchronously created via `Self::configure_slot_lease` (which invokes `T::Leaser::lease_out`) when `lease_period_start == SlotLeasePeriodStart::Current` and `ActiveTemporarySlotCount::<T>::get() < T::MaxTemporarySlotPerLeasePeriod::get()`. [1](#0-0)  In every other case, the function still unconditionally executes `TemporarySlots::<T>::insert(id, temp_slot)` and `TemporarySlotCount::<T>::mutate(|count| count.saturating_inc())` without creating a lease. [2](#0-1)  Since no lease was ever created, the para's `ParaLifecycle` remains `Parathread`.

`paras_registrar::do_deregister` only checks the lifecycle and has no awareness of `assigned_slots` storage: it allows deregistration whenever `lifecycle(id)` is `Parathread` or `None`. [3](#0-2)  This function is reachable through `deregister`'s call to `ensure_root_para_or_owner`, which permits a plain signed manager (not root, not `AssignSlotOrigin`) to invoke it as long as the para is unlocked. [4](#0-3) 

The only code path that removes `TemporarySlots`/`PermanentSlots` entries and decrements the associated counters is `unassign_parachain_slot`, which is gated behind `T::AssignSlotOrigin::ensure_origin`. [5](#0-4)  `do_deregister` never calls this function or any equivalent cleanup hook, so a deregistration that goes through while a `TemporarySlots` entry exists leaves that entry and the associated `TemporarySlotCount` permanently orphaned/stale.

I additionally reviewed `allocate_temporary_slot_leases`, the periodic function that later processes pending `TemporarySlots` entries: it iterates `TemporarySlots::<T>::iter()` and, for entries whose `period_begin` has passed, calls `Self::configure_slot_lease(*id, temp_slot.manager.clone(), ...)` directly using the stored (now stale) manager, without re-validating that `id` is still registered in `paras_registrar::Paras` or still owned by that manager. [6](#0-5)  `configure_slot_lease` merely forwards to `T::Leaser::lease_out` with no registrar-existence check. [7](#0-6)  This confirms the secondary risk flagged in the report (a deregistered/re-registered `ParaId` could receive an unsanctioned lease turn), though I could not fully trace `T::Leaser::lease_out`'s (slots pallet) internal validation in this pass to confirm whether it independently guards against leasing a para that is no longer a registered parathread.

## Impact Explanation
This is a genuine accounting desynchronization between `assigned_slots::TemporarySlotCount`/`TemporarySlots` and the real registrar/lifecycle state, triggerable without any governance/root/`AssignSlotOrigin` involvement. `TemporarySlotCount` never decrements for the orphaned entry, permanently consuming capacity against `MaxTemporarySlots` and degrading the temporary-slot allocation mechanism over repeated exploitation (a DoS/griefing effect on `assigned_slots` capacity, confirmed by code review). The secondary consequence — that `allocate_temporary_slot_leases` may later grant a lease turn to a `ParaId` based on stale `TemporarySlots` data without re-validating registrar existence/manager — is a real code-level gap I confirmed via `allocate_temporary_slot_leases`, but whether this actually results in a fraudulent lease being granted to an unrelated, subsequently re-registered para depends on `T::Leaser::lease_out` / `slots` pallet internals that were not fully verified in this session.

## Likelihood Explanation
The exploit is reachable by an unprivileged signed account: an attacker only needs to be the manager of a para assigned a temporary slot with `SlotLeasePeriodStart::Next` (or during a period when the `MaxTemporarySlotPerLeasePeriod` cap is saturated), and to keep the para unlocked (the default state before `on_new_head` sets `locked = Some(true)`), then call `deregister` themselves. This is deterministic and reproducible, not a race condition, and does not require any privileged origin. Note that the initial `assign_temp_parachain_slot` call itself requires `T::AssignSlotOrigin` (root/governance), so the "attacker" here is a para manager exploiting an existing governance-approved temporary-slot assignment rather than an entirely permissionless attack chain from scratch — this is consistent with the report's framing but worth noting as a precondition dependent on governance action, not solely attacker-controlled setup.

## Recommendation
Add a check in `paras_registrar::do_deregister` (and `swap`) that rejects deregistration, or triggers equivalent `assigned_slots` cleanup, whenever `assigned_slots::PermanentSlots::<T>::contains_key(id)` or `assigned_slots::TemporarySlots::<T>::contains_key(id)` is true — e.g., via a trait hook implemented by the `assigned_slots` pallet (similar to the existing `OnSwap` pattern), returning a distinct error (e.g. `CannotDeregister`) otherwise. Additionally, harden `allocate_temporary_slot_leases`/`configure_slot_lease` to re-validate that the target `ParaId` is still registered and still a `Parathread` before calling `lease_out`.

## Proof of Concept
The report's PoC is a valid reproduction of the bug against the code in this repository:
1. Register a para and, via `AssignedSlots::assign_temp_parachain_slot` under root/`AssignSlotOrigin`, request a temporary slot with `SlotLeasePeriodStart::Next` (or ensure the per-period cap is already reached).
2. Confirm the para's lifecycle stays `Parathread`/absent from `slots::Leases`, while `assigned_slots::TemporarySlots` contains the entry and `TemporarySlotCount` is incremented.
3. As the para manager (plain signed origin, unlocked para), call `paras_registrar::deregister`; this succeeds because `do_deregister` only checks `paras::Pallet::lifecycle`.
4. Observe that `assigned_slots::TemporarySlots::<T>::contains_key(id)` remains `true` and `TemporarySlotCount` remains non-decremented even though the para no longer exists in `paras_registrar::Paras`/`paras::ParaLifecycles`, confirming the orphaned accounting state exactly as described in the report's `deregister_orphans_temporary_slot_accounting` test.

	fn allocate_temporary_slot_leases(lease_period_index: LeasePeriodOf<T>) -> DispatchResult {
		let mut active_temp_slots = 0u32;
		let mut pending_temp_slots = Vec::new();
		TemporarySlots::<T>::iter().for_each(|(para, slot)| {
				match slot.last_lease {
					Some(last_lease)
						if last_lease <= lease_period_index &&
							lease_period_index <
								(last_lease.saturating_add(slot.period_count)) =>
					{
						// Active slot lease
						active_temp_slots += 1;
					}
					Some(last_lease)
						// Slot w/ past lease, only consider it every other slot lease period (times period_count)
						if last_lease.saturating_add(slot.period_count.saturating_mul(2u32.into())) <= lease_period_index => {
							pending_temp_slots.push((para, slot));
					},
					None if slot.period_begin <= lease_period_index => {
						// Slot hasn't had a lease yet
						pending_temp_slots.insert(0, (para, slot));
					},
					_ => {
						// Slot not being considered for this lease period (will be for a subsequent one)
					},
				}
		});

		let mut newly_created_lease = 0u32;
		if active_temp_slots < T::MaxTemporarySlotPerLeasePeriod::get() &&
			!pending_temp_slots.is_empty()
		{
			// Sort by lease_count, favoring slots that had no or less turns first
			// (then by last_lease index, and then Para ID)
			pending_temp_slots.sort_by(|a, b| {
				a.1.lease_count
					.cmp(&b.1.lease_count)
					.then_with(|| a.1.last_lease.cmp(&b.1.last_lease))
					.then_with(|| a.0.cmp(&b.0))
			});

			let slots_to_be_upgraded = pending_temp_slots.iter().take(
				(T::MaxTemporarySlotPerLeasePeriod::get().saturating_sub(active_temp_slots))
					as usize,
			);

			for (id, temp_slot) in slots_to_be_upgraded {
				TemporarySlots::<T>::try_mutate::<_, _, Error<T>, _>(id, |s| {
					// Configure temp slot lease
					Self::configure_slot_lease(
						*id,
						temp_slot.manager.clone(),
						lease_period_index,
						temp_slot.period_count,
					)
					.map_err(|_| Error::<T>::CannotUpgrade)?;

					// Update temp slot lease info in storage
					*s = Some(ParachainTemporarySlot {
						manager: temp_slot.manager.clone(),
						period_begin: temp_slot.period_begin,
						period_count: temp_slot.period_count,
						last_lease: Some(lease_period_index),
						lease_count: temp_slot.lease_count + 1,
					});

					newly_created_lease += 1;

					Ok(())
				})?;
			}

	fn do_deregister(id: ParaId) -> DispatchResult {
		match paras::Pallet::<T>::lifecycle(id) {
			// Para must be a parathread (on-demand parachain), or not exist at all.
			Some(ParaLifecycle::Parathread) | None => {},
			_ => return Err(Error::<T>::NotParathread.into()),
		}
		polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)
			.map_err(|_| Error::<T>::CannotDeregister)?;

		if let Some(info) = Paras::<T>::take(&id) {
			<T as Config>::Currency::unreserve(&info.manager, info.deposit);
		}

		PendingSwap::<T>::remove(id);
		Self::deposit_event(Event::<T>::Deregistered { para_id: id });
		Ok(())
	}
