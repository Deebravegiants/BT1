Found it — the webhook `Request` binds `hmac` to `to_signable_string`, which is the raw request body only. The `shop` (and `topic`) fields are read directly from the `shopify-shop-domain` HTTP header and are **not part of the HMAC-signed material**, so an attacker who has a validly-signed webhook payload for their own shop can replay/relay it while forging the `shopify-shop-domain` header to point at a victim shop, causing the host application to process the webhook under the wrong tenant's identity.

### Title
Webhook `shop` (and `topic`) identity claimed from unauthenticated headers, not bound by HMAC — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw request body only, while the `shop` domain and `topic` used by the host application to route/process the webhook are taken from unauthenticated HTTP headers that are excluded from the signed material.

### Finding Description
The equality the gem is supposed to enforce is: `shop used to route/process webhook == shop that Shopify actually signed the payload for`. Instead, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header("shop-domain")` [2](#0-1)  and similarly `topic` from `shopify-topic` [3](#0-2) . The `hmac` accessor decodes `shopify-hmac-sha256` and is verified via `Utils::HmacValidator.validate`, which computes the signature only over `to_signable_string` (the raw body) using `Context.api_secret_key` [4](#0-3) . Because `shop` and `topic` never enter the signed string, they are "bytes verified versus bytes parsed" mismatches: Shopify's HMAC only proves the body integrity, not which shop/topic the body is claimed to belong to. A party who receives one legitimately-signed webhook body (e.g. for their own store, or any publicly-observable webhook payload with a fixed HMAC for a known secret-independent path) can replay the identical raw body with a modified `shopify-shop-domain` header pointing at a different shop, and `HmacValidator.validate` will still return `true` because the signature check never inspected the header at all.

### Impact Explanation
If a host application built on this gem uses `Webhooks::Request#shop` (post signature-validation) to determine which tenant's data to update — the documented and expected usage pattern — an attacker who can obtain any one validly HMAC-signed webhook body (their own shop's webhook, which they are entitled to receive) can relabel it to another shop's domain and have the host process it as if it came from that victim shop. This crosses a tenant boundary: it is a cross-tenant data-integrity/spoofing issue where webhook effects intended for shop A get attributed to shop B, without needing the app's `client_secret`, an access token, or any privileged credential beyond the attacker's own legitimate webhook traffic.

### Likelihood Explanation
Likelihood is high for any app that trusts `Request#shop` for tenant routing after `HmacValidator.validate` succeeds — this is exactly the pattern the gem's `Request`/`HmacValidator` classes are designed to support, and the exploit requires only network-observable legitimate webhook traffic (no leaked secrets, no TLS interception, no privileged account).

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signed material used for verification, or independently bind the header-derived `shop` value to a value obtained from a source that is itself authenticated (e.g., cross-check against the session/shop that requested the corresponding earlier action), so that the HMAC check actually covers the identity claim (`shop`) that consuming applications rely on, not just the payload bytes.

### Proof of Concept
1. Attacker's own shop (`attacker-shop.myshopify.com`) receives a legitimately Shopify-signed webhook: body `B`, header `shopify-hmac-sha256: H`, header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and hmac `H` to the app's webhook endpoint, but changes the header to `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully — `hmac` still decodes to `H`, `to_signable_string` returns `B` unchanged [5](#0-4) .
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` with `Context.api_secret_key` and finds it matches `H`, returning `true` [6](#0-5) .
5. The host application, trusting validation success, reads `request.shop` and processes/attributes the webhook payload to `victim-shop.myshopify.com` instead of the actual originating shop.
