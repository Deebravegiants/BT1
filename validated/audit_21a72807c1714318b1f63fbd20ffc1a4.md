**Analysis:**

The `verify_ungated_and_descendant` function at [1](#0-0)  performs a bounded ascent up the ownership chain starting from the destination object, checking that `allow_ungated_transfer` is set at every hop and that the count never reaches `MAXIMUM_OBJECT_NESTING` (8).

Two properties defeat the proposed attack:

1. **Cycles that don't include the caller's address are safely rejected, not bypassed.** If the chain forms a cycle that never reaches `owner`, the `count` monotonically increases on each loop iteration (there is no way to "skip" the increment), so after at most 8 iterations the `assert!(count < MAXIMUM_OBJECT_NESTING, ...)` fires and the transaction aborts with `EMAXIMUM_NESTING`. This is explicitly covered by the existing unit tests `test_exceeding_maximum_object_nesting_owns_should_fail` and `test_exceeding_maximum_object_nesting_transfer_should_fail` at [2](#0-1) , which confirm a 9-level-deep chain aborts as expected rather than silently succeeding.

2. **An unprivileged attacker cannot construct a chain where their own address appears as an ancestor owner.** The only way `current_address` can ever equal `owner` partway up the chain is if some `ObjectCore.owner` field genuinely stores that address — and that field can only be set via `transfer_raw_inner` at [3](#0-2) , which is only reachable through `transfer_raw` after `verify_ungated_and_descendant` has already succeeded for the current legitimate owner. So inserting oneself into an ownership chain to satisfy the loop's exit condition already requires the same ownership authority the check is meant to enforce — there's no way to "misjudge" a forged cycle since the owner graph is authoritative on-chain state, not attacker-supplied input.

The Move prover spec file itself flags this loop as only partially verified (`pragma aborts_if_is_partial`, "TODO: Verify the link list loop") at [4](#0-3) , but the unresolved formal-verification gap is not the same as a demonstrable exploit — the Move unit tests show the bounded-nesting logic correctly rejects excess depth and cycles without a legitimate owner in the chain, and the ownership graph cannot be forged by an unprivileged caller since every edge is written only under the same ownership check being questioned.

    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
