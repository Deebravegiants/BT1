### Title
`orb.ir_eye_save_fps_override` bleeds into the next signup when biometric capture times out during Pupil Contraction extension - ([File: src/plans/biometric_capture/pupil_contraction.rs])

### Finding Description
`pupil_contraction::Plan::handle_ir_net` sets `orb.ir_eye_save_fps_override = Some(FPS)` when entering `State::RampingUp` and only clears it back to `None` inside the `State::Waiting` branch, and only when `start_time.elapsed() >= WAIT_TIME` [1](#0-0) . This clearing path is the *only* place in the entire pupil-contraction module (or the orchestrator) that resets the override.

The overall biometric-capture timeout (`BIOMETRIC_CAPTURE_TIMEOUT` / `self_serve_biometric_capture_timeout`) is enforced independently by `biometric_capture::Plan::poll_extra`, which sets `self.timed_out = true` and returns `BrokerFlow::Break` as soon as the deadline elapses, regardless of which pupil-contraction sub-state (`RampingUp`/`Waiting`) is currently active [2](#0-1) . When this timeout fires while state is `RampingUp` or `Waiting` (i.e. before `elapsed >= WAIT_TIME`), execution unwinds to `pupil_contraction::Plan::run`, whose loop exits via `self.biometric_capture.run_check(orb)` returning `true` because `timed_out` is set, and then calls `run_post` [3](#0-2) . `biometric_capture::Plan::run_post` disables/stops agents (ir_net, rgb_net, auto-exposure, eye tracker, cameras, mirror, distance) but never touches `orb.ir_eye_save_fps_override`, `ir_face_save_fps_override`, or `thermal_save_fps_override` [4](#0-3) .

Contrast this with the other extensions (`focus_sweep`, `mirror_sweep`, `overcapture`), which set the override immediately before and explicitly reset it to `None` immediately after each sweep/capture round trip inside their own `perform_*` helper, independent of overall timeout state [5](#0-4) [6](#0-5) . `pupil_contraction` uniquely relies on reaching the natural end of `WAIT_TIME` to clear the flag, with no fallback cleanup on early abort.

After `do_signup` returns, `MasterPlan::run` calls `self.reset_hardware_except_led(orb)` between signups, which only resets `FrameRate`, IR LED, and `LiquidLens` on the MCU — it does not reset `orb.ir_eye_save_fps_override` [7](#0-6) . The `Orb` struct field `ir_eye_save_fps_override` is a plain broker field that persists across `do_signup` invocations for the lifetime of the process [8](#0-7) . The next signup's `biometric_capture::Plan::run_pre` does not initialize or clear it either [9](#0-8) .

Consequently, when the next signup's IR frames are captured, `handle_ir_net`/`handle_ir_eye_camera` in `brokers/orb.rs` still pass the stale `fps_override: self.ir_eye_save_fps_override` (`Some(FPS)`, i.e. 6.0) into `image_notary::SaveIrNetEstimateInput`, causing the unrelated next user's IR frames to be sampled/saved at the pupil-contraction rate instead of the default `IR_EYE_SAVE_FPS` [10](#0-9) , [11](#0-10) .

An attacker reaches this purely through their own signup session: `signup_extension_config` (mode `PupilContractionExtension`) is derived from the presented QR code data via `qr_scan::user::Data` and threaded into `biometric_capture` without additional server-side gating visible in this path [12](#0-11) . The attacker can then simply not react to the LED ramp (or otherwise stall completion) so that `BIOMETRIC_CAPTURE_TIMEOUT`/self-serve timeout expires while state is `RampingUp`/`Waiting`, guaranteeing the stale override.

### Impact Explanation
This is a cross-signup state-bleed of capture configuration: the *following* unrelated user's IR eye frames get saved/sampled under a different (non-default) FPS policy tied to the previous attacker's extension configuration, without the orchestrator resetting this per-signup capture setting. This is a metadata/config integrity issue — captured biometric data for the next signup is produced under mislabeled/misconfigured capture settings, which is scoped as a session-isolation violation of capture configuration rather than a full authentication/liveness bypass. Actual data-visibility impact is limited to builds where `internal-data-acquisition` is compiled in, since that is what gates whether `ir_eye_save_fps_override` affects saved files [13](#0-12) ; the underlying state-bleed condition in `Orb`/`pupil_contraction`/`run_post` itself is unconditional.

### Likelihood Explanation
Reproducible deterministically: an attacker just needs a QR code selecting `SignupMode::PupilContractionExtension` and to stall (or rely on ambient conditions delaying) completion until the overall biometric-capture timeout fires while in `RampingUp`/`Waiting` state. No privileged access, hardware tampering, or backend compromise is required — only the attacker's own signup session and QR content.

### Recommendation
Reset `orb.ir_eye_save_fps_override` (and, for consistency, `ir_face_save_fps_override`/`thermal_save_fps_override`) unconditionally in `biometric_capture::Plan::run_post` (or in `pupil_contraction::Plan::run`'s cleanup path, guaranteed via a `Drop`/guard or explicit `orb.ir_eye_save_fps_override = None;` after the loop regardless of exit reason), so cleanup does not depend on reaching `elapsed >= WAIT_TIME`. Additionally, `reset_hardware_except_led`/`reset_hardware` in `plans/mod.rs` should defensively clear all *_save_fps_override fields between signups as a second line of defense, independent of individual plan cleanup.

### Proof of Concept
Integration test plan:
1. Configure a signup with `signup_extension_config.mode = PupilContractionExtension` and a short `BIOMETRIC_CAPTURE_TIMEOUT`/`self_serve_biometric_capture_timeout` such that the timeout fires while the mocked `ir_net` estimate stream keeps `pupil_contraction::Plan` in `State::RampingUp` or `State::Waiting` (i.e., never let `elapsed >= WAIT_TIME` occur, and never satisfy `run_check`'s "both eyes captured" condition).
2. Assert that `orb.ir_eye_save_fps_override == Some(pupil_contraction::FPS)` at the moment of timeout.
3. Let `do_signup` complete (as a failed/aborted signup) and let `MasterPlan::run`'s loop invoke `reset_hardware_except_led` and proceed to the next iteration.
4. Start a second, unrelated signup (default `SignupMode::Basic`, no extension config) and assert, before any frame is processed, that `orb.ir_eye_save_fps_override == None`. The test should currently fail, showing the stale `Some(FPS)` value persists, and that IR frames for the second signup's `image_notary::SaveIrNetEstimateInput.fps_override` are sampled at `FPS = 6.0` rather than the default `IR_EYE_SAVE_FPS`.
