## Title
`SimplexPaymaster._getOraclePrice()` uses Chainlink `latestRoundData()` on Arbitrum without checking the L2 sequencer uptime feed - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` is deployed on Arbitrum (confirmed by chain-42161 entries in the rebalancing config) and prices every gas-payment token, as well as the treasury-only fee-recycling swap, from Chainlink `AggregatorV3Interface.latestRoundData()` feeds via `_getOraclePrice()`. This validation only checks `answer > 0` and a staleness bound (`block.timestamp - updatedAt <= maxOracleAge`); it never consults the Arbitrum `SequencerUptimeFeed`, mirroring exactly the Sherlock M-3 finding in Bond Protocol's `BondChainlinkOracle._validateAndGetPrice()`. [1](#0-0) 

### Finding Description
`_getOraclePrice()` is the sole gate on Chainlink data used throughout the paymaster: [1](#0-0) 

It is called from `_tokenPrice()` — which prices every incoming ERC-4337 `UserOp`'s gas payment (`_fetchDetails` → `_tokenPrice`) — and from the treasury-gated `swapAndDeposit()`: [2](#0-1) [3](#0-2) 

Like `BondChainlinkOracle._validateAndGetPrice()` in the referenced report, the check `block.timestamp - updatedAt > maxOracleAge` is *only* a staleness bound relative to `block.timestamp`; it has no knowledge of whether the Arbitrum sequencer was down when the last round was posted. When the sequencer is offline, feeds stop updating but retain their last `updatedAt`; once the sequencer resumes (or a transaction is force-included through the L1 delayed inbox during the outage), a UserOp can be validated and prefunded against a price that is technically "within `maxOracleAge`" of `block.timestamp` yet reflects market conditions from before/during the outage — precisely the accepted root cause in the referenced Sherlock issue (fixed upstream in Bond-Protocol/bonds#53 by adding the L2 sequencer-uptime check).

The `DeploySimplexPaymaster.s.sol` script and `filler-config-example.toml` confirm chain 42161 (Arbitrum) is a live target for this contract, with no sequencer-feed parameter anywhere in `Params`/`TokenConfig`/`initialize`: [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged UserOp sender (the "bandwidth purchaser" paying gas through this paymaster) can submit a UserOp during/immediately after an Arbitrum sequencer outage and have `_tokenPrice()` compute gas cost from a stale-but-"fresh" native/USD or token/USD price. Since the paymaster prefunds `maxCost` from its own EntryPoint deposit and only later collects the ERC-20 equivalent via `_prefund`/`PaymasterERC20._postOp`, a favorable stale price directly lets an attacker underpay for gas relative to the paymaster's real native-asset outlay, draining the paymaster/treasury's subsidized value — concrete theft of funds. The same stale price also drives `swapAndDeposit()`'s `amountOutMin`, so a stale-favorable price could similarly let the treasury (or an interaction that manipulates timing around the outage) mis-price fee-recycling swaps, though that path is treasury-gated and lower likelihood.

### Likelihood Explanation
Arbitrum sequencer outages have occurred historically and force-inclusion via the L1 delayed inbox is a documented, permissionless mechanism, so the precondition is realistic. The exploit only requires a normal `UserOp` submission timed around an outage — no special privileges — matching the "unprivileged... bandwidth purchaser" reachability bar.

### Recommendation
Add Chainlink's recommended L2 sequencer-uptime check to `_getOraclePrice()` (or a wrapper called before both `_tokenPrice()` and `swapAndDeposit()`): read the `SequencerUptimeFeed`'s `latestRoundData()`, revert if `answer == 1` (sequencer down), and additionally enforce a grace period after `startedAt` before trusting any price feed again, exactly as done in the fix referenced by the report (Bond-Protocol/bonds#53) and Chainlink's example code.

### Proof of Concept
1. Register `SimplexPaymaster` on Arbitrum (chain 42161) with a token/native Chainlink feed as done in `DeploySimplexPaymaster.s.sol`.
2. Arbitrum sequencer goes offline; the underlying native/USD or token/USD feed's last `updatedAt` stops advancing while the real off-chain price moves against the cached value.
3. Once the sequencer resumes (or via forced L1 inclusion during the outage), submit a `UserOp` with `paymasterData` selecting the affected token; `_validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` passes because `block.timestamp - updatedAt <= maxOracleAge` still holds.
4. The paymaster prefunds gas at the stale, attacker-favorable rate, transferring value from the paymaster/treasury to the sender — no sequencer-uptime check exists anywhere in `SimplexPaymaster.sol` to block this.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
