### Title
Ambiguous withdrawal status matching by `assetId` instead of `index`/destination causes cross-withdrawal status and tx-hash misattribution in PoA Bridge - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain completion status/tx-hash of a withdrawal by matching the bridge indexer's response list solely on `assetId` (`findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`), ignoring the `index` field that is supposed to uniquely identify which withdrawal within a batched NEAR transaction is being queried. When a single NEAR transaction contains two or more withdrawal intents for the **same token** (same `assetId`) but different destination addresses, the matching function cannot disambiguate between them and may report the status/tx-hash of a *different* withdrawal in the batch than the one actually requested.

### Finding Description
`WithdrawalIdentifier` is explicitly documented as needing `index` to distinguish "per-bridge withdrawal sequence number" within a transaction: [1](#0-0) 

`createWithdrawalIdentifier()` in the PoA bridge assigns this `index` from the position of the intent in the withdrawal batch: [2](#0-1) 

However, `describeWithdrawal()` never uses `index` (or the destination address) to select the corresponding entry from the bridge's response; it matches purely on `assetId`: [3](#0-2) 

The code comment even acknowledges the response list is unsorted and matching is done "by assetId instead of index" — a deliberate but unsafe simplification when multiple withdrawals share the same `assetId`. The existing test suite only validates disambiguation across *different* assetIds (BTC vs ETH) and confirms index is intentionally not used: [4](#0-3) 

No test covers the case of two withdrawals with the **identical** `assetId` (same token) but different `destinationAddress` values batched in the same NEAR transaction — a scenario explicitly supported by the SDK, since `createWithdrawalIntents`/`processWithdrawal` accept arrays of `WithdrawalParams` and allow multiple `ft_withdraw` intents of the same token to different recipients within one call: [5](#0-4) 

In that scenario, `findMatchingWithdrawal` would find multiple candidate entries in `response.withdrawals` that all match the queried `assetId`, and (based on its unsorted-list handling) may return the entry belonging to a sibling withdrawal instead of the one identified by `index`. This breaks the equality "status/tx-hash reported == the on-chain outcome for *this* withdrawal index," which is exactly the CWE-863/288-style equality break called out in the scan rules (a status/hash misreport).

### Impact Explanation
This is a status/hash misreport bug that can make an integrator or the SDK's `watchWithdrawal`/`waitForIntentSettlement` flow believe a specific withdrawal (to destination A) is `completed` with a specific `txHash`, when that `txHash` actually corresponds to a different withdrawal in the same batch (to destination B). Downstream consumers (integrators crediting users, or automated systems releasing funds/marking orders fulfilled) could:
- Credit/mark-complete the wrong withdrawal based on another withdrawal's proof-of-completion, or
- Report a `pending`/`failed` withdrawal as `completed` because a sibling entry with the same assetId satisfied the match first.

This falls into the High-severity bucket ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
Requires:
1. A caller to submit a NEAR transaction with 2+ `ft_withdraw` intents for the same token (`assetId`) but different destination addresses via the PoA bridge route (a supported, unprivileged usage pattern — no attacker cooperation from admin/relayer needed).
2. The PoA bridge indexer to return an unsorted list containing both entries.

This does not require any malicious relayer/bridge behavior — it is a self-inflicted correctness bug reachable by any normal caller of `sdk.processWithdrawal`/`createWithdrawalIntents` with a batched same-asset, multi-destination withdrawal, making it moderately likely in real usage (e.g., a service batching payouts of the same token to multiple users in one NEAR transaction).

### Recommendation
Update `findMatchingWithdrawal` / `describeWithdrawal` to disambiguate using additional fields available in the PoA bridge response (e.g., `data.address` / destination address, and ideally position/order or a bridge-provided withdrawal index) in addition to `assetId`, rather than only `assetId`. At minimum, when multiple response entries match the queried `assetId` for the same `tx_hash`, cross-check `data.address` against `args.withdrawalParams.destinationAddress` before returning a status, and treat an unresolved ambiguity as `pending` rather than silently returning a possibly-wrong match.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents`/build a NEAR transaction with two `ft_withdraw` intents for `nep141:btc.omft.near`: one with `destinationAddress: addrA` (index 0) and one with `destinationAddress: addrB` (index 1).
2. After the tx lands, the PoA bridge indexer returns `withdrawals: [{assetId: btc, address: addrB, status: COMPLETED, transfer_tx_hash: hashB}, {assetId: btc, address: addrA, status: PENDING}]` (unsorted).
3. Call `describeWithdrawal({ index: 0, withdrawalParams: { assetId: btc, destinationAddress: addrA, ... }, tx })`.
4. `findMatchingWithdrawal` matches on `assetId` alone and returns the first matching entry (`addrB`'s completed entry with `hashB`), causing the caller to believe withdrawal to `addrA` (index 0) is `completed` with `hashB`, even though it is actually still pending — misattributing a sibling withdrawal's completion to the wrong destination/index.

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
	public async createWithdrawalIntents(args: {
		withdrawalParams: WithdrawalParams;
		feeEstimation: FeeEstimation;
		referral?: string;
		logger?: ILogger;
	}): Promise<IntentPrimitive[]> {
		for (const bridge of this.bridges) {
			if (await bridge.supports(args.withdrawalParams)) {
				const actualAmount = args.withdrawalParams.feeInclusive
					? args.withdrawalParams.amount - args.feeEstimation.amount
					: args.withdrawalParams.amount;

				await bridge.validateWithdrawal({
					assetId: args.withdrawalParams.assetId,
					amount: actualAmount,
					destinationAddress: args.withdrawalParams.destinationAddress,
					destinationMemo: args.withdrawalParams.destinationMemo,
					feeEstimation: args.feeEstimation,
					routeConfig: args.withdrawalParams.routeConfig,
					logger: args.logger,
				});

				return bridge.createWithdrawalIntents({
					withdrawalParams: {
						...args.withdrawalParams,
						amount: actualAmount,
					},
					feeEstimation: args.feeEstimation,
					referral: args.referral ?? this.referral,
				});
			}
		}

		throw new Error(
			`Cannot determine bridge for withdrawal = ${stringify(
				args.withdrawalParams,
			)}`,
		);
	}
```
