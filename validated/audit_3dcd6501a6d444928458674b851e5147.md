### Title
Excess native `msg.value` sent to `EvmHost.dispatch()`/`fundRequest()` gets permanently locked in the contract - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment via `msg.value` and swap it for `feeToken` through `swapETHForExactTokens`, but none of them refund any leftover native token that the router returns after the exact-output swap. Any surplus ETH sent by callers becomes permanently stuck in the `EvmHost` contract, mirroring the reported analog where mismatched native-token handling locks ETH in a contract with no recovery path.

### Finding Description
In `dispatch(DispatchPost)` [1](#0-0) , when `msg.value > 0` the contract calls:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

`swapETHForExactTokens` is an *exact-output* swap: it only consumes as much ETH as needed to buy `post.fee` units of `feeToken`, and refunds any unused ETH back to `msg.sender` of the router call — which is `EvmHost` itself (since `EvmHost` is the direct caller of the router, not the original dispatching contract/user). `EvmHost.dispatch()` never forwards, tracks, or exposes this refunded ETH; it simply accumulates in the host's balance.

The exact same pattern (swap without excess-refund) exists in:
- `dispatch(DispatchGet)` [2](#0-1) 
- `fundRequest(bytes32,uint256)` [3](#0-2) 

Callers reach these functions from many entry points across the protocol — e.g. `IntentGatewayV2._fillCrossChain`/`placeOrder`, `WrappedHyperFungibleToken.send()`, `HyperFungibleToken.send()`, or any `HyperApp` sending a native-paid POST/GET request or funding a pending request. If any of these upstream callers pass a `msg.value` that is even slightly greater than what the Uniswap swap needs (e.g. due to slippage margin added by the caller for safety, or a quote computed off-chain becoming stale by the time the transaction executes), the difference is silently absorbed by `EvmHost` and is unrecoverable — there is no `receive()`/sweep/withdraw function in `EvmHost.sol` that lets anyone reclaim native balance held by the contract.

This differs from safer patterns already used elsewhere in the same codebase, such as `IntentGatewayV2.placeOrder()`, which explicitly tracks `msgValue` through every step and refunds any unspent amount to the caller at the end [4](#0-3) , and `ExtrinsicIntents._fillCrossChain()`, which similarly refunds unspent native tokens to the solver [5](#0-4) . `EvmHost` lacks this equivalent refund/accounting logic for the swap remainder.

### Impact Explanation
Any native token sent to `EvmHost.dispatch()`/`fundRequest()` beyond the exact amount consumed by the Uniswap exact-output swap is permanently locked in the `EvmHost` contract with no code path to withdraw it — this is a direct, unbacked loss of user/caller funds (medium-to-high severity fund freezing), consistent with the reported bug class ("Will lock ETH in the contract"). Because `dispatch`/`fundRequest` are core, single-transaction-reachable entry points used by essentially all native-fee-paying dispatchers (message senders, token bridge apps, intent fillers), the surface for triggering this is broad and requires no special privileges — any ordinary user overestimating slippage or reusing a slightly stale `quote()` result will lose the difference.

### Likelihood Explanation
Likelihood is high in practice: the protocol's own documentation explicitly warns that native-token fee estimation via `quote()` is "Approximate (subject to slippage)" and recommends using it only off-chain, implying callers will commonly send `msg.value` with a safety margin above the exact computed fee [6](#0-5) . Any such margin, or any beneficial price movement in the Uniswap pool between quoting and execution, results in leftover ETH being trapped every single time `dispatch()`/`fundRequest()` is called with native payment.

### Recommendation
Capture the amounts actually spent by the router (`amounts[0]` returned by `swapETHForExactTokens`) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()` (or the designated payer) at the end of each function, mirroring the refund pattern already implemented in `IntentGatewayV2.placeOrder()` and `ExtrinsicIntents._fillCrossChain()`.

### Proof of Concept
1. Caller (a `HyperApp` or end user) invokes `EvmHost.dispatch(DispatchPost)` with `msg.value = X`, where `X` is intentionally or unavoidably greater than the ETH amount required to purchase `post.fee` units of `feeToken` on the local Uniswap pool.
2. Inside `dispatch()`, `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes; the router spends `amounts[0] < X` ETH and refunds `X - amounts[0]` ETH to its caller, which is `EvmHost`.
3. `dispatch()` returns normally, having credited the `feeToken` balance and emitted the `PostRequestEvent`, but the `X - amounts[0]` ETH refund is now sitting in `EvmHost`'s balance.
4. No function in `EvmHost.sol` allows withdrawing or sweeping this native balance; it remains permanently locked, repeating and accumulating with every over-funded `dispatch`/`fundRequest` call.

```text
### Payment Method Comparison

| Feature | Native Token | FeeToken (Recommended) |
|---------|-------------|------------------------|
| **Gas Cost** | Higher (includes swap) | Lower (no swap) |
| **Slippage** | Yes (Uniswap swap) | No |
| **Fee Calculation** | Approximate (subject to slippage) | Exact |
| **Token Approval** | Not required | Required  |
| **User Convenience** | High (users have native tokens) | Low (users need feeToken) |
| **Best For** | One-off transactions, user-facing apps | Frequent dispatches, cost optimization |
```
