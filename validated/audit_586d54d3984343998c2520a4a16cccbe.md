### Title
Untrusted flash-loan receiver can attach arbitrary victim-token transfers to the caller’s signed authorization tree - ([File: contracts/pool/src/ops/flash.rs](contracts/pool/src/ops/flash.rs))

### Summary
`flash_loan` accepts a caller-selected Wasm receiver and invokes it while the caller’s authorization is active. The receiver learns the authorizing address through its `initiator` callback argument and can request that address’s authorization for unrelated token transfers. If a crafted interface causes the victim to simulate and sign the poisoned authorization tree, the receiver can transfer assets unrelated to the flash loan to an attacker while still repaying the loan correctly.

### Finding Description
The controller authenticates only `caller`, then delegates the arbitrary `receiver` address to the pool inside the flash guard. It validates that the receiver is Wasm, but does not restrict what external contracts the receiver calls during the callback. [1](#0-0) 

The pool pays `receiver`, invokes its callback, and passes the original caller as `initiator`. [2](#0-1) 

Soroban authorization is invocation-tree based: a nested contract may request authorization from an address already represented in the tree, but that additional invocation becomes a child that simulation records and the signer can authorize. The repository explicitly demonstrates this behavior with a route-selected contract that calls `token.transfer(victim, attacker, amount)` beneath the user’s authorized lending call. [3](#0-2)  The same test shows that enforcement rejects the extra transfer with an honest authorization tree but executes it when the victim signs the poisoned tree. [4](#0-3) 

This maps the reported browser security-UI origin-spoofing class onto Soroban’s authorization UI: the lending call and receiver may look plausible, while the generated signature payload contains an additional victim-authorized transfer.

### Impact Explanation
Theft of user funds.

A malicious receiver can transfer any token held by the victim that implements standard `from.require_auth()` semantics, including tokens unrelated to the lending market. The amount is limited only by the victim’s balance and token-specific authorization rules. The enclosing flash loan can still satisfy all protocol settlement checks because the malicious receiver may approve `amount + fee` for the pool before returning.

The same mechanism does not bypass Soroban authorization itself: execution requires the victim to sign an authorization tree containing the malicious child invocation. The vulnerability is therefore the ability of protocol-invoked attacker code to expand the requested signature scope beyond the operation’s expected semantics.

### Likelihood Explanation
Medium.

Exploitation requires user interaction: the victim must be induced to call `flash_loan` with an attacker-controlled `receiver` and sign a simulated authorization tree containing the extra transfer. This is analogous to the CVE’s requirement that a user install or trust malicious content. No privileged role, leaked key, oracle manipulation, or contract upgrade is required.

The repository’s threat model acknowledges the equivalent route-hop exposure and states that clients must decode routes and reject unexpected authorization children. [5](#0-4)  However, no equivalent contract-level authorization-scope restriction exists for the arbitrary flash-loan callback.

### Recommendation
Do not treat `caller.require_auth()` as limiting the callback to actions needed for flash-loan repayment. Reduce signing ambiguity and enforce callback isolation:

1. Prefer a fixed, governance-approved flash-receiver interface or receiver allowlist for user-facing flows.
2. If arbitrary receivers remain supported, emit and standardize a strict authorization-policy manifest so wallets can flag child invocations unrelated to repayment.
3. Make the expected authorization tree explicit for `flash_loan`: the controller root plus only the receiver’s repayment-related authorization expected by the integration.
4. Client-side, simulate immediately before signing and reject any child authorization other than the exact expected token approval/transfer needed for `amount + fee`.
5. Document that `receiver` and `data` are adversarial and that the callback receives `initiator`, making the victim address directly available to malicious code.

### Proof of Concept
Conceptual receiver:

```rust
#[contractimpl]
impl Receiver {
    fn execute_flash_loan(
        env: Env,
        initiator: Address, // victim/caller supplied by the pool
        asset: Address,
        amount: i128,
        fee: i128,
        pool: Address,
        _data: Bytes,
    ) {
        let attacker: Address = stored_attacker(&env);
        let victim_token: Address = stored_unrelated_token(&env);

        // Adds a child authorization request under the victim's flash_loan auth.
        token::Client::new(&env, &victim_token).transfer(
            &initiator,
            &attacker,
            &victim_balance,
        );

        // Keep the outer loan valid.
        token::Client::new(&env, &asset).approve(
            &env.current_contract_address(),
            &pool,
            &(amount + fee),
            &(env.ledger().sequence() + 1),
        );
    }
}
```

Execution flow:

1. Victim calls `Controller::flash_loan(caller=victim, asset, amount, receiver=attacker_receiver, data)`.
2. The controller calls `caller.require_auth()` and forwards the call to the pool. [1](#0-0) 
3. The pool transfers `amount` to the receiver and invokes `execute_flash_loan`, passing `initiator=victim`. [2](#0-1) 
4. The receiver invokes `unrelated_token.transfer(victim, attacker, victim_balance)`.
5. Simulation records the transfer as a child of the victim’s `flash_loan` authorization.
6. If the victim signs the poisoned tree, the unrelated token moves to the attacker; the receiver then approves `amount + fee`, allowing the pool’s repayment pull and outer transaction to succeed.
7. With an honest tree lacking that child, host authorization rejects the extra transfer and rolls back the transaction, as demonstrated by the repository’s authorization-tree test. [4](#0-3)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
