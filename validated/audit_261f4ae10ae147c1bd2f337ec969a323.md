### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` value and forwards it to the app's webhook handler. Because Shopify signs webhooks with the app's single `client_secret` (shared across every shop that installs the app), any merchant who has installed the app can capture a legitimate `(raw_body, hmac)` pair from their own store's webhook deliveries and replay it to the app's endpoint with the `shop-domain` header swapped to a victim shop, producing a valid signature for attacker-chosen tenant identity.

### Finding Description
The identity binding that should hold is:
`shop asserted to the handler == shop whose data actually produced the signed bytes`

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string`, and for webhooks that string is exactly the raw body: [1](#0-0) [2](#0-1) 

The `shop` accessor pulls straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of `to_signable_string` and therefore not covered by the HMAC at all: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then unconditionally forwards `request.shop` (the unauthenticated header) to the registered handler: [4](#0-3) 

The HMAC secret used to sign webhooks is the app-wide `api_secret_key`, not something scoped per shop — confirmed by the library's own test fixtures, which sign with `ShopifyAPI::Context.api_secret_key` regardless of which shop the webhook is "from": [5](#0-4) 

Because the same secret authenticates webhooks for every shop that installs the app, and the `shop` field is excluded from the signed payload, a merchant who legitimately installs the app can capture the `(body, hmac)` pair produced by their own store's genuine webhook and resend it to the app's webhook receiver with the `x-shopify-shop-domain` header replaced by a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and the handler receives `WebhookMetadata` claiming the victim shop, with body content actually belonging to the attacker's shop.

### Impact Explanation
This breaks the tenant/identity boundary the gem is supposed to guarantee to host applications: a webhook accepted as "signed and therefore trustworthy for shop X" can in fact carry attacker-controlled data attributed to any shop of the attacker's choosing. Depending on how the host app persists/acts on webhook data (e.g., updating order/inventory/customer records keyed by `data.shop`), this enables cross-tenant data injection/corruption — a Critical-severity cross-tenant access impact per the given impact categories.

### Likelihood Explanation
Any user who can install the app on a store (the normal, unprivileged path for any Shopify app) receives genuine webhook deliveries signed with the app's `client_secret` for their own shop. No access to `api_secret_key`, access tokens, or any privileged account is required — only the ability to intercept/replay their own legitimate webhook HTTP request with a modified header, which is trivial for anyone controlling the receiving network path or simply replaying a captured request. This is a repeatable network-level manipulation, not a theoretical scenario.

### Recommendation
Bind the `shop` identity into the value that is cryptographically verified. Options:
- Have the gem cross-check `request.shop` against the shop associated with the currently registered/expected session before invoking the handler, or
- Extend `to_signable_string` (or add a separate verification step) so the `shop-domain` header is included in what is validated against the HMAC, rejecting mismatches, or
- Explicitly document and enforce that host applications must additionally verify `data.shop` against their own session/tenant record before trusting webhook payload contents, and have `Registry.process` refuse to call handlers when no such binding is established.

### Proof of Concept
1. App developer's `client_secret` is `S`. Merchant M installs the app on `m.myshopify.com` and it registers a webhook.
2. Shopify delivers a legitimate webhook to the app: `raw_body = B`, header `x-shopify-shop-domain: m.myshopify.com`, header `x-shopify-hmac-sha256 = HMAC(S, B)`.
3. Merchant M (an unprivileged party w.r.t. the app, with no access to `S`) intercepts this legitimate delivery (e.g., via a local proxy on their own infrastructure) and resends the exact same `raw_body` and `hmac` value to the app's public webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb:190` succeeds because it only checks `HMAC(S, B) == HMAC(S, B)` — the shop header plays no role.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...))`, and the host application processes attacker-controlled body `B` as though it belongs to `victim.myshopify.com`.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
