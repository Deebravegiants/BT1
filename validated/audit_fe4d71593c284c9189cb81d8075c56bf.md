Confirmed root cause: `Registry.process` at [1](#0-0)  validates the HMAC via `Utils::HmacValidator.validate(request)` and, if it passes, immediately trusts `request.shop` (and `request.topic`) to construct `WebhookMetadata` handed to the app's handler — with no check that the `shop` header was itself covered by the signature.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , so the HMAC verified by `Utils::HmacValidator.validate` only binds the request body to the app's secret — it never binds the `shop`, `topic`, `webhook-id`, or `api-version` headers [3](#0-2) . `Registry.process` trusts `request.shop` unconditionally once the body HMAC passes [1](#0-0) .

### Finding Description
The identity binding that should hold is: `shop-header-value == shop-that-produced-this-signed-body`. Because only `@raw_body` is fed into `to_signable_string`, that equality is never checked — the HMAC only proves "this body byte-string was signed by the app's secret at some point," not "this body was delivered for this shop." Any party that has ever legitimately received one valid `(raw_body, hmac)` pair from Shopify for their own shop (which is trivial — any merchant installing the app on a `*.myshopify.com` test store receives real, validly-signed webhooks) can resend that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` because it only recomputes and compares against `verifiable_query.to_signable_string`, which is just the raw body [4](#0-3) [5](#0-4) . `Registry.process` then builds `WebhookMetadata` using the unverified `request.shop` and dispatches it to the registered handler [6](#0-5) , so the host application's handler is invoked believing the event originated from a shop that never actually sent it.

This is the same class of bug as the Sherlock H-12 report: a value that is *acted on* downstream (there, the slippage-adjusted amount; here, the `shop` identity) is not the value that was actually *covered* by the integrity check (there, the `sellPrincipalToken` slippage bound; here, the HMAC signature) — the check answers permissively for a field that was never bound.

### Impact Explanation
This crosses a tenant boundary: a handler intended to process shop-A's event can be made to run with shop-B's identity while using a payload that a real shop legitimately produced with the app-approved HMAC secret. Any host application that uses `WebhookMetadata#shop` to key data writes, trigger side effects, or select which merchant record to update (the intended and documented use of the `shop` field passed to handlers, per `docs/usage/webhooks.md` process-webhook instructions) can have its per-tenant data or actions corrupted by an attacker who legitimately controls one shop's own webhook stream. This satisfies the "cross-tenant access" bar for High severity, since the gem's own webhook-processing entry point fails to bind an identity field to the cryptographic proof it relies on.

### Likelihood Explanation
Likelihood is significant: no access token, `api_secret_key`, or any privileged credential is required, only the ability to (a) install the app on any shop and receive one real webhook delivery, or observe body/hmac pairs via the app's own inbound webhook endpoint, and (b) replay that raw body + HMAC header to the same endpoint with a different `shopify-shop-domain` (or `x-shopify-shop-domain`) header. The endpoint is by design internet-reachable and unauthenticated apart from the HMAC check.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) header value in the signable string that `HmacValidator` verifies, or independently cross-check `request.shop` against the shop resolved from the session/access-token context before dispatching to the handler, so the identity used downstream is provably the one the signature actually covers.

### Proof of Concept
1. Register a handler with `ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", delivery_method: :http, path: "path", handler: handler)`.
2. Capture a legitimate webhook delivery for `shop-a.myshopify.com`: raw body `body` and header `x-shopify-hmac-sha256: hmac_of(body)` (computed by Shopify with the real `api_secret_key`, valid and unmodified).
3. Replay to the app's webhook controller with the same `body` and same `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: shop-victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` at [7](#0-6)  calls `Utils::HmacValidator.validate(request)`, which passes because only the body is checked; the handler then executes with `data.shop == "shop-victim.myshopify.com"` even though the payload never came from that shop.
