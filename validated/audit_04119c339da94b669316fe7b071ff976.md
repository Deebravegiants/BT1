### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the application's webhook handler are taken from unauthenticated HTTP headers. The identity binding "the shop whose secret validated this payload" == "the shop the handler believes it received the webhook from" is never enforced by the library.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` decodes the `hmac-sha256`/`x-shopify-hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop`, `#topic`, and `#webhook_id` are read straight from request headers with no cryptographic binding to the signed body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only that `raw_body` matches the HMAC computed with `Context.api_secret_key`, then immediately trusts `request.shop` to build the metadata passed to the developer's handler: [3](#0-2) 

Because `Context.api_secret_key` is a single shared secret used by the app across **every** shop that installs it (not a per-shop secret), any unprivileged attacker who installs the app on a store they control can capture a genuinely-signed webhook (valid `raw_body` + valid `hmac`) delivered to their own endpoint. That `(raw_body, hmac)` pair remains valid for the same body content forever, because it depends only on the body — not on the shop header. The attacker can then replay that exact `raw_body`/`hmac` pair to the target app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header to name a **different, victim** shop. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` calls the handler with `WebhookMetadata` claiming the payload originated from the victim shop: [3](#0-2) 

This breaks the identity equality that application code implicitly relies on: `shop_header_used_by_handler == shop_that_the_signature_actually_authenticates_for`. In practice, the signature only authenticates "this body was produced with knowledge of this app's shared secret" — it says nothing about which shop the header claims.

### Impact Explanation
Any host application that dispatches persistence/business logic keyed off `WebhookMetadata#shop` (e.g., "delete customer data for this shop", "update subscription status for this shop", "disable this shop's session") can be tricked into applying attacker-chosen webhook bodies to an arbitrary victim shop of the attacker's choosing, without ever needing that shop's data or the app's `client_secret`. This is a cross-tenant confusion/injection primitive that satisfies the "cross-tenant access" Critical-impact category, since one merchant/tenant can forge events attributed to another tenant using only their own legitimate installation.

### Likelihood Explanation
Exploitation requires only:
1. Installing the app on any shop the attacker controls (or otherwise obtaining one valid signed webhook body/hmac pair for a topic of interest — many public sample payloads/topics are predictable, e.g. `app/uninstalled`, `shop/redact`).
2. Sending an unauthenticated HTTP POST to the target app's public webhook endpoint with the captured body/hmac and a forged `x-shopify-shop-domain` header.

No access token, `client_secret`, or privileged account is required — only participation as a normal merchant/developer, which is realistically available to any internet user who can install a public app.

### Recommendation
Bind the shop identity into the value that is authenticated, or otherwise verify it out-of-band:
- Extend `VerifiableQuery#to_signable_string` for webhook requests to include the shop domain (if Shopify's webhook signing scheme is changed to support this), or
- Require host applications (and provide a documented helper) to cross-check `request.shop` against the shop associated with the currently active/stored session for that webhook subscription before acting on it, rejecting mismatches.
- At minimum, document prominently in `docs/usage/webhooks.md` that `WebhookMetadata#shop` is **not** authenticated by the HMAC and must be independently corroborated (e.g., against known installed shop records) before being trusted for any state-changing operation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the exact `raw_body` and `x-shopify-hmac-sha256` header sent by Shopify to the app's public webhook URL.
2. Attacker sends a new HTTP request to the same public webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <captured-valid-hmac>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <any>

   <captured-raw-body>
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `raw_body`, which is unchanged, using the app's single shared `api_secret_key`. [4](#0-3) 
4. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, and the handler acts on victim-shop data/state believing the event is authentic for that shop. [3](#0-2) 

Note: I could not find any in-scope code path (outside `test/**` and `docs/**`) that cross-checks `WebhookMetadata#shop` against a known/installed session before invoking the handler, confirming the gap is unmitigated within this library's scope.
