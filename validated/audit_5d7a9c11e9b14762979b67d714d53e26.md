### Title
Webhook HMAC signs only the raw body, not `X-Shopify-Topic`/`X-Shopify-Shop-Domain`, allowing cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` verifies the HMAC solely against that body. Since topic and shop headers are never part of the signed material, a validly-signed webhook received by an attacker's own installed shop can be replayed to the shared webhook endpoint with forged `X-Shopify-Topic`/`X-Shopify-Shop-Domain` headers and will still pass validation, causing `Registry.process` to dispatch the attacker-chosen topic/shop combination to the handler.

### Finding Description
The claimed binding — `request.topic`/`request.shop` authenticated by HMAC == `request.topic`/`request.shop` acted on by the handler — does not hold. `to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`topic` and `shop` are read from separate, unsigned HTTP headers: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and the app's shared `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC, then trusts `request.topic` to select the handler and passes `request.shop` straight into `WebhookMetadata` without any cross-check against the body or against session/shop records: [4](#0-3) 

Root cause: since `Context.api_secret_key` is the app's single client secret shared across every shop that installs the app, and the signature covers only the body, any party who can obtain one validly-signed webhook (e.g., by installing the app on their own dev shop and receiving their own legitimate webhook) possesses a body+HMAC pair that remains valid under the same secret regardless of which topic/shop headers are later attached. The documented controller pattern in `docs/usage/webhooks.md` explicitly funnels every topic/shop through the same `Registry.process` call with headers read directly from the inbound request, with no additional shop/topic binding: [5](#0-4) 

No other guard in the gem re-derives or checks topic/shop against the signed payload — there is no session lookup, no webhook_id/topic binding check, nothing analogous to `ShopValidator.sanitize!` for this path.

Attacker exploit flow:
1. Attacker creates their own dev shop `attacker.myshopify.com`, installs the target app, and registers/receives a legitimately signed webhook for any topic (e.g., `orders/create`) at their own controlled listener — this yields a real `raw_body` + `hmac` pair signed with the app's real secret.
2. Attacker POSTs that identical `raw_body`/`hmac` to the victim app's shared webhook route, but sets `X-Shopify-Topic: shop/redact` and `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes HMAC over `@raw_body` only — it matches, since the body and secret are unchanged.
4. `Registry.process` resolves the `shop/redact` handler and invokes it with `WebhookMetadata(topic: "shop/redact", shop: "victim.myshopify.com", body: <attacker's own body>)`.
5. The app performs a mutation/data action attributed to `victim.myshopify.com` using attacker-controlled body content and an attacker-chosen topic, despite never having received an actual signed webhook for that shop/topic combination.

### Impact Explanation
This is a cross-tenant authentication-binding failure: the app treats an unauthenticated field (`shop`/`topic` headers) as if it were authenticated by the HMAC, when the HMAC covers only the body. Any handler logic that branches on `topic`/`shop` (mandatory redact handlers, per-shop data mutations, job dispatch keyed by `shop_domain`, etc.) can be triggered for an arbitrary victim shop, using content the attacker fully controls, as long as the attacker can obtain one legitimately-signed body/HMAC pair from their own install. This matches the Critical category: cross-tenant access via forged webhook processing attributed to a victim tenant.

### Likelihood Explanation
Preconditions match the stated attacker capabilities: the attacker only needs to install the app on their own dev shop (an ordinary, permitted action) and observe a legitimate webhook delivery. The app must use the shared webhook controller as documented (the pattern shown in `docs/usage/webhooks.md`), which is the gem's standard, recommended usage. No secret material is required — only header manipulation and body replay, both fully attacker-controlled per the threat model. The attack is trivially repeatable against any topic/shop pair the attacker chooses, for as many "victim" shop-domain strings as desired, since `shop` and `topic` are plain unauthenticated headers.

### Recommendation
Bind `topic` and `shop` into the signed material actually verified before dispatch, or independently authenticate `shop` against known installed shops. Concretely: after HMAC validation succeeds, verify that `request.shop` corresponds to a session/shop actually known to the app (e.g., look up an active session/store record for that domain) before invoking the handler, and/or reject requests where the `shop-domain` header doesn't match records associated with the webhook subscription (Shopify webhook subscriptions are shop-scoped server-side, so cross-checking against local install records closes the gap). At minimum, document prominently that `request.shop`/`request.topic` are NOT authenticated by the HMAC and must not be trusted without an additional shop-existence check by the host app.

### Proof of Concept
minitest + WebMock plan (no live shop):
1. Set `Context.api_secret_key` to a known test secret.
2. Compute `hmac = OpenSSL::HMAC.hexdigest("sha256", secret, "{}")` (simulating a legitimately-received webhook body for the attacker's own shop, topic `orders/create`).
3. Build a first `Request` with headers `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: Base64.encode64([hmac].pack("H*"))`, `raw_body: "{}"`. Assert `HmacValidator.validate(request)` is `true` (this is the attacker's legitimate delivery).
4. Build a second `Request` reusing the identical `raw_body` and `hmac` header, but with headers overwritten to `X-Shopify-Topic: shop/redact` and `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. Assert `HmacValidator.validate(second_request)` is still `true`.
6. Register a mock handler for `shop/redact` in `ShopifyAPI::Webhooks::Registry`, call `Registry.process(second_request)`, and assert the handler's `handle` was invoked with `data.shop == "victim.myshopify.com"` and `data.topic == "shop/redact"` — demonstrating the equality `request.topic/shop authenticated by HMAC == request.topic/shop acted on by handler` fails.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
