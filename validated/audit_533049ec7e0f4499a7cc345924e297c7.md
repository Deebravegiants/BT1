### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing tenant impersonation via webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` value taken from the `X-Shopify-Shop-Domain` header to identify the tenant the payload belongs to. Because the `shop` header is never included in the signed content, a party who can obtain one validly-signed webhook body (e.g. from their own installed/test shop) can freely swap the `shop` header to any other shop domain and the request still passes `HmacValidator.validate`. The host application, which receives `WebhookMetadata.shop` from this gem as an authenticated tenant identifier, will process the replayed payload under the wrong shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature using `verifiable_query.to_signable_string` only, i.e. the raw body — never any header, including `shop`: [3](#0-2) 

`Registry.process` gates all further logic on that HMAC check, then immediately hands the attacker-controllable `request.shop` value to the app's handler as an authenticated field via `WebhookMetadata`: [4](#0-3) 

The binding that should hold is: `hmac == HMAC(secret, shop || body)` (or some equivalent binding of `shop` into the signed content). Instead, the actual invariant enforced is only `hmac == HMAC(secret, body)`, with `shop` sourced from an unauthenticated header. This is precisely the "field acted on but not covered by the HMAC" identity-binding gap: the secret key is shared across all shops registered under the same `api_secret_key`/app, so any shop that can legitimately receive one signed webhook (by installing the app, or by triggering any webhook-eligible action in their own store) possesses a `(body, hmac)` pair that remains valid under the shared secret regardless of which `shop` header is attached to the replay.

### Impact Explanation
This breaks the tenant/shop identity boundary that host applications rely on this gem to enforce. A host application built on `ShopifyAPI::Webhooks::Registry.process` reasonably treats `WebhookMetadata#shop` as authenticated, since it comes from a "verified" `Request` that has already passed HMAC validation. An attacker (any merchant who has the app installed, or who can otherwise obtain one legitimately signed webhook body/HMAC pair) can replay that pair against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain, causing the host app to apply the payload's data (e.g., order/customer/app-uninstalled state changes) to the wrong tenant. This is a cross-tenant identity confusion vulnerability rooted in this gem's webhook verification contract.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that trusts `WebhookMetadata.shop` (which is the documented and expected usage pattern per `docs/usage/webhooks.md`). No access token, `api_secret_key`, or privileged account is required — only the ability to install the target app on an attacker-controlled store and capture a single outbound webhook, or otherwise obtain a validly-signed webhook body for the shared app secret.

### Recommendation
Do not treat `request.shop` as authenticated data based solely on the body HMAC. Either bind `shop` (and `topic`/`webhook_id`) into the signed content that `HmacValidator` verifies, or require callers to cross-check `request.shop` against an expected/known shop for the session/context before acting on the payload, and document this requirement clearly since the gem currently implies the whole `Request` is "verified" once `process` succeeds.

### Proof of Concept
1. Install the app (or otherwise legitimately trigger a webhook) on attacker-controlled shop `attacker.myshopify.com`; capture the delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (line 198) builds `WebhookMetadata.new(... shop: request.shop ...)` using the attacker-supplied `victim.myshopify.com`, and invokes the app's handler as if the event genuinely originated from the victim shop.
