### Title
Direct token donation can invert `reserveToken`/`tokenBalance()` and permanently DOS the overflow-cap buy path in `Router._computeBuy` - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap branch subtracts the pair's live `tokenBalance()` from its stored `reserveToken` without checking that `tokenBalance() <= reserveToken`. A trader can buy tokens off the curve and then donate them straight back to the `Pair` via a plain ERC20 `transfer`, inflating `tokenBalance()` above the stored `reserveToken`. Any subsequent buy that is large enough to hit the overflow cap will then underflow and revert, permanently bricking every cap-binding buy on that token (including the sellout closing buy that many curves rely on to graduate).

### Finding Description
`Router._computeBuy` computes the normal (uncapped) `tokensOut`, then caps it at the pair's real ERC20 balance if it would exceed it: [1](#0-0) 

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // <-- unchecked subtraction
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
    amountInUsed = cappedReserveAsset - reserveAsset;
}
```

`reserveToken` is the stored virtual reserve (`Pair._pool.tokenReserve`, initialized to `totalSupply` and mutated only by `Pair.swap`), while `realBalance = pair.tokenBalance()` is a live `IERC20.balanceOf(pair)` read. The whole design (and the codebase's own invariant tests) assumes `tokenBalance() < tokenReserve()` at every point of curve life: [2](#0-1) 

That invariant only holds as long as nothing but curve buys/sells moves real tokens into the pair. A `Token` is a normal ERC20 (`Token.sol`), so anything (including an attacker who has already bought tokens off the curve) can call `token.transfer(pair, amount)` directly — this is one of the explicitly in-scope reachable primitives (direct ERC20 transfers of a launched `Token` into `Pair`). Such a donation increases `tokenBalance()` but does **not** touch the stored `_pool.tokenReserve` (only `Pair.swap` mutates it), so it is possible to donate enough tokens to make `tokenBalance() > tokenReserve()`.

The codebase has already identified and patched exactly this root cause once, in `Bonding.previewLtUntilGraduation`, which explicitly guards against a donation inflating `realBalance` above `reserveToken`: [3](#0-2) 

The regression test for that fix even documents the underlying bug class: [4](#0-3) 

```
// A TOKEN donation that drives `realBalance > reserveToken` previously
// underflowed `Bonding.previewLtUntilGraduation`'s supply leg,
// cascading into a `Zap.buy` DoS. Guard added; tests pin the fix.
```

However, `Router._computeBuy` (the function that actually executes state-changing buys, called from `Router.buy`, which `Bonding._executeBuy` invokes on every trade) has the exact same unguarded subtraction `reserveToken - tokensOut` (where `tokensOut` was just set to the inflated `realBalance`) and was **not** patched. If `realBalance > reserveToken`, `reserveToken - tokensOut` underflows and reverts under Solidity 0.8 checked arithmetic.

### Impact Explanation
Once an attacker inverts `tokenBalance() > tokenReserve()` for a given `Pair`, any buy sized to exceed the (inflated) real balance takes the overflow-cap branch and reverts unconditionally — it is not a one-time revert but a permanent state: nothing removes the donated tokens from the pair (they are not burned until graduation succeeds, and graduation's closing buy is itself one of the transactions likely to hit this exact cap branch). This:
- Permanently freezes the ability to complete the supply-exhaustion ("sellout") graduation path for that token, since the very buy meant to drain the remaining real balance is the one that trips the cap and reverts.
- Denies any trader from executing a large buy that would otherwise legitimately hit the overflow cap (e.g., "buy all remaining supply"), freezing their USDC/LT and blocking the trade.
- Constitutes a concrete, permanent freezing-of-funds / complete-DOS condition on the affected bonding curve, analogous to the CVE's "hang or frequently repeatable crash (complete DOS)" impact.

### Likelihood Explanation
The attack requires only ordinary, unprivileged actions: buy tokens off the curve (any trader can do this any time) and call `token.transfer(pair, amount)` (a completely permissionless ERC20 transfer). The economically cheapest window is late in the curve's life, when `reserveToken - tokenBalance()` (the "virtual gap") has shrunk close to zero as more of the real 750M supply has been sold — at that point only a small number of already-owned tokens need to be donated back to flip the inequality and set up the DOS for the next cap-binding buy. No special privileges, timing races against keepers, or admin cooperation are required.

### Recommendation
Add the same donation guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy`: before computing `cappedReserveToken = reserveToken - tokensOut`, check `if (tokensOut >= reserveToken)` and handle it safely (e.g., treat the cap input as `min(realBalance, reserveToken - 1)`, or otherwise fail gracefully without reverting on every future call), so a token donation directly to the pair can never permanently disable the overflow-cap buy path.

### Proof of Concept
1. Attacker buys a modest amount of `Token` off the curve via `Zap.buy` / `Bonding.buy`, receiving real tokens.
2. Attacker waits (or times the attack) until the curve's real `tokenBalance()` is close to `reserveToken` (this gap monotonically shrinks as the curve is bought down — see `test_inv_virtualReserveAlwaysExceedsRealBalance`).
3. Attacker calls `Token(tokenAddress).transfer(pairAddr, gapAmount + 1)`, sending the token directly to the `Pair` contract. This increases `pair.tokenBalance()` above the stored `_pool.tokenReserve` without touching the `Pool` struct.
4. Any subsequent buy sized to attempt to purchase more than the (now-inflated) `pair.tokenBalance()` enters the overflow-cap branch in `Router._computeBuy`, computes `tokensOut = realBalance` (> `reserveToken`), and then reverts on `cappedReserveToken = reserveToken - tokensOut` due to Solidity 0.8 underflow protection — permanently, since nothing un-inflates `tokenBalance()` for that pair outside of graduation succeeding (which itself may need to pass through this same cap branch).

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);
