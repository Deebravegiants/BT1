### Title
Zero-token Emporium ("Min") transactions bypass both Hinkal's balance equation and Emporium's own signer check, letting any EOA drain residual/pooled funds held by the Emporium contract - (File: `contracts/CircomDataBuilder.sol`, `contracts/Hinkal.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The reported bug class is a forced action executed on a victim contract via a check that can be trivially satisfied/bypassed by an unprivileged attacker (hardcoded/weak auth). The closest reachable analog in this repo is the "Emporium Min" code path: when `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` diverts to `formInputEmporiumMin`, which produces a circuit public-input vector containing only `[emporiumMessage, timeStamp, calldataHash]` — no `signedMessageHash`, no `rootHashHinkal`, no nullifiers/commitments. In this same scenario, `Hinkal.transact`'s post-execution balance equation (which is the only place that enforces "value moved == amountChanges + UTXO delta") is a loop bounded by `circomData.erc20TokenAddresses.length`, i.e. it never executes. Independently, `EmporiumUpgradeable.verifyWallet` skips its ECDSA authorization entirely whenever `stack.signerAddress == address(0)`. Combined, an attacker can submit a zero-token-dimension proof (trivially satisfiable, since no nullifiers/commitments/signature are constrained for this path) and drive the Emporium contract to execute arbitrary `op.endpoint.call{value: op.value}(op.callData)` calls, with zero on-chain balance accounting and zero Emporium-side signature check.

### Finding Description
1. `CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`) routes to `formInputEmporiumMin` when the external action is Emporium and no ERC20 tokens are declared: [1](#0-0) 

`formInputEmporiumMin` builds only 3 public signals (`emporiumMessage`, `timeStamp`, `calldataHash`) — critically, it never calls `getSignedMessageHash`, unlike `formBasicInput` used by the normal path. This means the EdDSA signature check inside the circuit (`SignatureVerifier`, wired into `signedMessageHash` in `MainEVMCircuit.circom:33,92-95`) is not bound to anything meaningful for this path; the circuit used for this dimension set is not present in the indexed circuit sources, so the only enforced invariant visible on-chain is `calldataHash` matching `CircomDataBuilder.getHashedCalldata` in `HinkalHelper.performHinkalChecks`: [2](#0-1) 

2. Since `dimensions.tokenNumber == 0` is attacker-chosen, `HinkalHelper.dimensionsCheck` is satisfied trivially (empty arrays match empty arrays): [3](#0-2) 

3. Back in `Hinkal.transact`, the balance/slippage equation that is supposed to guarantee "on-chain balance change == declared amountChanges + created UTXOs" is bounded by `circomData.erc20TokenAddresses.length`, which is 0 for this scenario, so the loop body never runs and no invariant is checked at all: [4](#0-3) 

4. `_externalTransact` calls `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` with `deltaAmountChanges` also empty (its length equals `circomData.erc20TokenAddresses.length`): [5](#0-4) 

5. Inside `EmporiumUpgradeable.runAction`, execution of the operation stack is independent of `deltaAmountChanges`/`erc20TokenAddresses` — the stack is decoded straight from `circomData.externalActionData.externalActionMetadata` and executed: [6](#0-5) 

6. `verifyWallet` skips the EIP-712/ECDSA signature check entirely when `stack.signerAddress == address(0)`, leaving only a nonce (`usedMessages`) check: [7](#0-6) 

The equality broken is the core Hinkal balance/authorization invariant: "every unit of value that leaves a Hinkal-controlled contract must be tied to a `calldataHash`-committed `amountChanges`/UTXO entry AND to a valid EdDSA proof of ownership (`signedMessageHash`) or a valid Emporium signer signature." For the zero-token Emporium path, none of these three checks fire: the circuit's public input set for this branch omits `signedMessageHash`, the Solidity balance-equation loop is vacuous, and the Emporium-level ECDSA check is explicitly bypassed when `signerAddress == address(0)`. Any residual ETH/ERC20 balance sitting in the Emporium contract (e.g., accrued relay fees, transient funds from a prior multi-op stack, or dust) can be moved to an attacker-controlled `op.endpoint` via a stateless `.call{value: op.value}(op.callData)`.

### Impact Explanation
This matches the High-impact bucket: theft or permanent freezing of protocol/relay fees and value not authorized by any wallet owner or prover, since the attacker never proves ownership of any shielded UTXO nor obtains a valid Emporium signer signature, yet still triggers arbitrary external calls with contract-held value.

### Likelihood Explanation
The attacker needs only: (a) a proof for the zero-dimension circuit variant used by `formInputEmporiumMin` (uncertain from the indexed sources whether this variant enforces anything more than `calldataHash` matching — this could not be fully confirmed because the corresponding circuit template file was not found in the indexed `circuits/**` tree), and (b) a registered verifier for `dimensions.tokenNumber == 0` under the Emporium `externalActionId`. If such a verifier is registered (a protocol/owner decision, not attacker-controlled), the rest of the path (dimensionsCheck, balance-equation loop, verifyWallet bypass) is fully reachable by an unprivileged EOA with no special conditions.

### Recommendation
- Ensure `formInputEmporiumMin`/its corresponding circuit always binds `calldataHash` to a valid `signedMessageHash`/ownership proof, matching the normal path.
- Make the `Hinkal.transact` balance/slippage equation independent of `erc20TokenAddresses.length` for external actions that can move value through opaque call stacks (e.g., verify Emporium/Wallet's own pre/post ETH and token balances against a declared bound regardless of declared token count).
- Remove or gate the `stack.signerAddress == address(0)` bypass in `EmporiumUpgradeable.verifyWallet` so stateless ops still require the calldataHash to be cryptographically bound to a signature/proof that a specific unprivileged caller cannot forge.

### Proof of Concept
Conceptual PoC (concrete circuit witness generation for the zero-dimension "Min" variant could not be produced from the indexed code, as the circuit template itself is not visible in the indexed `circuits/**` tree — this is a limitation of the analysis, not a claim the path is unreachable):
1. Craft `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: attacker, invokeWallet: false, value: X, callData: "" }] })`.
2. Compute `calldataHash = CircomDataBuilder.getHashedCalldata(circomData)` and set it in `circomData.calldataHash`.
3. Generate a proof for the zero-dimension Emporium verifier (registered by protocol) satisfying only the 3-signal public input `[emporiumMessage, timeStamp, calldataHash]`.
4. Call `Hinkal.transact(a, b, c, dimensions{0,0,0}, circomData)` from any EOA.
5. `performHinkalChecks` and `dimensionsCheck` pass trivially; the proof verifies; `Hinkal.transact`'s balance-equation loop is skipped (`erc20TokenAddresses.length == 0`); `_externalTransact` calls `EmporiumUpgradeable.runAction`, whose `verifyWallet` skips signature verification (`signerAddress == 0`), and the stateless op executes `attacker.call{value: X}("")`, moving `X` ETH out of the Emporium contract with no balance check anywhere in the call graph.
