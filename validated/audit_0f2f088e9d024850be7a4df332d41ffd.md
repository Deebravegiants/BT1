Webhook tenant identity (`shop`) is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `shop` identity that the gem hands to the app's handler as the authoritative tenant for that webhook is read from the `shopify-shop-domain` HTTP header [2](#0-1) , but `to_signable_string` — the value the HMAC is actually computed over — is defined as only `@raw_body`, excluding all headers including `shop-domain` [3](#0-2) . This is the same bug class as the reference report: a field that is *acted upon* (here, tenant attribution `request.shop`) is not covered by the integrity check (the HMAC), breaking the intended binding `HMAC-verified-bytes == identity-used-for-tenant-action`.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only [3](#0-2) , and `hmac` is derived from the `hmac-sha256` header [5](#0-4) . The `shop` attribute, however, comes from a separate, unsigned header `shopify-shop-domain`/`x-shopify-shop-domain` [2](#0-1) .

`Registry.process` trusts `request.shop` as the tenant identity forwarded to the app's webhook handler after the HMAC check passes: [1](#0-0) 

The binding the gem is implicitly supposed to guarantee is:
`HMAC-verified(raw_body) == identity-bound(shop-domain-header)`

but the actual behavior is:
`HMAC-verified(raw_body) != shop-domain-header` (the header is not part of the signed material at all)

Because Shopify computes the webhook HMAC using `HMAC-SHA256(api_secret_key, raw_body)` with no header material included, any party who can obtain one genuine, validly-signed webhook body+HMAC pair for the app (e.g., by installing the same public app on their own store and receiving a legitimate webhook) can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` because it only checks the body against the signature, and `Registry.process` will hand the handler a `WebhookMetadata` object attributing the (attacker-controlled) shop to that body [6](#0-5) .

This lets an unprivileged internet user (any merchant who can install the target app on their own store, an action requiring no special privilege) forge webhook deliveries that are attributed to a shop of their choosing — including victim shops they do not own — since the gem never checks that the signed bytes are cryptographically tied to the shop identity used for the tenant-scoped action.

### Impact Explanation
This matches the "Critical - cross-tenant access" impact bucket: an attacker can cause the app to process/store webhook data (e.g. `customers/data_request`, `shop/redact`, order/product mutation webhooks, etc.) under an arbitrary victim shop's tenant context, without possessing that shop's credentials, purely by controlling the unsigned `shop-domain` header while replaying an HMAC that was legitimately computed for their own store's payload. Depending on what the app does in its webhook handler (e.g., updating per-shop state, triggering redaction, writing to the shop's data store), this is a direct cross-tenant data integrity/confidentiality breach rooted entirely in this gem's `HmacValidator`/`Webhooks::Request` design, not a host-app misuse of a documented contract — the header is exposed on the `Request` object as the vetted "shop" but the gem's own signature check never covers it.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple/public shops: obtaining one authentic `raw_body` + `hmac-sha256` pair only requires installing the target app on an attacker-controlled store (a normal, unprivileged action for any Shopify merchant), then replaying the exact bytes with a forged `shop-domain` header. No access to `api_secret_key`, access tokens, or any privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material that `HmacValidator` checks, or otherwise cryptographically tie the header used for tenant attribution to the HMAC-verified payload — e.g., include the shop domain in `to_signable_string`, or require the caller to separately verify `request.shop` against an app-known allowlist of installed shops that is derived from an already-authenticated source (not from this unauthenticated header) before dispatching to the handler.

### Proof of Concept
1. Install the app (assumed public) on attacker-owned store `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic; capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sends — these satisfy `HMAC-SHA256(api_secret_key, B) == H`.
3. Replay to the app's webhook endpoint:
```
POST /webhooks
X-Shopify-Topic: <same topic>
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com   <-- forged, arbitrary value
X-Shopify-Webhook-Id: <anything>
X-Shopify-Api-Version: <anything>

B
```
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process(request)` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` → returns `true` [7](#0-6) .
5. `handler.handle` is invoked with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"` even though the payload `B` and signature `H` were generated for the attacker's own store [6](#0-5) .
