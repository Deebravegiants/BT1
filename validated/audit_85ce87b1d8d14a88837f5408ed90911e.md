## Analysis

The Tron deployment of `IntentGatewayV2` duplicates the EVM contract's logic but drops the parameter sanity check that the canonical EVM version enforces. The canonical EVM `IntentsBase._validateParams()` explicitly rejects `protocolFeeBps >= 10_000` and `surplusShareBps > 10_000` before they can be stored, and `_updateParams` further rejects `destinationFeeBps >= 10_000`, exactly the class of check the external report says was missing for `PermittedPartners.setPartnerRevenueShare()`: [1](#0-0) [2](#0-1) 

The Tron variant's `setParams`, however, writes `_params = p` directly with no call to any validation routine — it only checks that the caller is the one-time `_admin`: [3](#0-2) 

### Title
Missing bps sanity check in Tron `IntentGatewayV2.setParams` permanently bricks `placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`setParams` on the Tron `IntentGatewayV2` accepts an arbitrary `Params` struct and stores it verbatim, with no upper-bound check on `protocolFeeBps` (or `surplusShareBps`), unlike the canonical EVM `IntentsBase._validateParams()` which enforces `protocolFeeBps < 10_000` and `surplusShareBps <= 10_000`.

### Finding Description
`placeOrder` computes the escrowed amount as:
```
protocolFee = (originalAmount * protocolFeeBps) / 10_000;
reducedAmount = originalAmount - protocolFee;
``` [4](#0-3) 

If `protocolFeeBps` is set to `10_000` or greater, `protocolFee >= originalAmount` for every input, and the subtraction underflows, which Solidity 0.8's checked arithmetic reverts on. Because `setParams` never validates this value before permanently committing it (`_admin` is zeroed immediately after the call, closing off any future fix path from that same admin), a single unchecked initialization call permanently bricks the contract's core `placeOrder` entry point for every subsequent user, on every input token, with no recovery short of a governance-driven `UpdateParams` message arriving through Hyperbridge to reset it.

### Impact Explanation
This matches the "route unable to deliver messages" category: any user attempting to place an order against this gateway deployment has their transaction unconditionally revert, making the entire chain's IntentGateway instance non-functional for intent placement. Unlike the referenced report (where funds get stuck in an unliquidatable loan), here the revert happens before escrow, so no funds are locked — but the route itself is permanently disabled until an external governance correction lands, which is exactly the underlying "no sanity check on a bps parameter baked into an immutable/hard-to-change state" bug class.

### Likelihood Explanation
This is triggered by a single, ordinary call to the one-time initializer `setParams` with a mis-set `protocolFeeBps` (e.g., an off-by-one in bps vs percent, or a copy-paste of a value meant for a different field) — no malicious intent is required, matching the "audit-issue: no sanity check leads to broken invariant" pattern from the source report. Given the value is written once and the admin slot is cleared right after, an operational mistake here cannot be self-corrected.

### Recommendation
Mirror the canonical `IntentsBase._validateParams()` logic in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `setParams`: revert if `protocolFeeBps >= 10_000` or `surplusShareBps > 10_000` (and validate `host`/`dispatcher` non-zero/contract-code checks as done in the EVM version) before committing `_params = p`.

### Proof of Concept
1. Deploy `evm/tron/contracts/apps/IntentGatewayV2.sol` with a constructor `admin`.
2. Admin calls `setParams(Params{ ..., protocolFeeBps: 10000, ... })` — succeeds with no revert since there is no bounds check.
3. Any user calls `placeOrder(order, graffiti)` with any nonzero input amount — the fee computation `originalAmount - protocolFee` underflows and reverts, permanently disabling `placeOrder` on that deployment.
