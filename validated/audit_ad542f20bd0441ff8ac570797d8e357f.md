### Title
`_withdraw()` reverts atomically across all escrowed tokens in a multi-token order, permanently freezing unrelated tokens if any single token transfer fails - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` iterates over every token in a `WithdrawalRequest` and calls `IERC20.safeTransfer` (or a native `_sendValue`) for each one in a single unguarded loop. If any one token in that list fails to transfer — e.g. because the beneficiary is blacklisted on that specific token (USDC/USDT-style blacklists), the token is paused, or the token reverts for any other reason — the entire function reverts, which rolls back the escrow decrements and transfers already performed for the *other, unrelated* tokens in the same order. This mirrors the M-13 pattern: an unprivileged/uncontrollable failure on one item in a loop makes the whole batch (all items) permanently unable to be redeemed. [1](#0-0) 

### Finding Description
`_withdraw` is the single funds-release primitive used for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) across the IntentGateway. It loops over `body.tokens`, and for each token:
1. Reads `_orders[commitment][token]`.
2. Decrements the escrow.
3. Transfers the token to `beneficiary` via `safeTransfer` (ERC-20) or a raw call (native). [2](#0-1) 

There is no per-token isolation (no try/catch, no skip-on-failure, no partial redemption path). A cross-chain order can escrow multiple distinct input tokens (`order.inputs` is a `TokenInfo[]`), and the same `WithdrawalRequest.tokens` array is what gets redeemed on `RedeemEscrow`/`RefundEscrow` delivery via `onAccept`/`withdraw`. If the beneficiary (solver on redeem, user on refund) is later blacklisted on **any one** of the multiple escrowed tokens (a realistic and externally-triggerable condition for centralized-issuer stablecoins such as USDC/USDT, or any token with owner-controlled pause/blacklist), that single token's `safeTransfer` reverts, and the `for` loop's revert propagates out of `_withdraw`, reverting the whole transaction — including the release of the *other*, non-blacklisted tokens that would have succeeded independently. Because `_filled[body.commitment]` and the escrow decrements are also rolled back, the order can never be finalized through this same path again unless the blacklisted condition is somehow lifted — the legitimate tokens are stuck for as long as the blacklisted token stays blocked, which for many stablecoin blacklists is effectively indefinite absent issuer intervention.

This is the same root cause pattern as M-13: a loop executing an unconditional action per array element, where one element's failure (outside the caller's/relayer's control) blocks value transfer for all other elements in the same call, instead of segregating each token's success/failure independently.

### Impact Explanation
This can cause **permanent freezing of funds**: multiple legitimate token escrows (e.g. a DAI leg of a multi-token order) become unredeemable solely because a co-escrowed token (e.g. a blacklist-capable stablecoin) cannot be transferred to that specific beneficiary. Since `_withdraw` is invoked both from `onAccept` (cross-chain redeem/refund delivery, triggered by the fixed protocol `_relayer`) and reused by same-chain flows, and there is no fallback/retry mechanism that skips the failing token, the stuck tokens have no recovery path within the contract's existing logic. This satisfies "concrete... permanent freezing of funds" per the validation criteria.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an order escrowing more than one token, and (b) one of those tokens later becoming non-transferable to the specific beneficiary address (blacklist, pause, or a malicious/non-standard ERC-20 that reverts under certain conditions). Given widely-used stablecoins (USDC, USDT) implement blacklisting and are common in intents/bridging flows, and beneficiaries are attacker-influenceable in some flows (e.g. a malicious counterparty could deliberately get blacklisted, or a user could intentionally include a token they know will later be frozen for their own address to grief a solver, or vice versa), this is a realistically reachable griefing/freezing vector, not purely theoretical.

### Recommendation
Isolate per-token transfer failures inside `_withdraw` so that a revert on one token does not block release of the others:
```solidity
for (uint256 i; i < len; i++) {
    ...
    if (token == address(0)) {
        _sendValue(beneficiary, amount);
    } else {
        // wrap in try/catch or a low-level call and record failed transfers
        // for later retry / alternate beneficiary rather than reverting the whole loop
        (bool ok, ) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!ok) {
            // re-credit escrow and emit an event so failed leg can be swept/retried separately
            _orders[body.commitment][token] += amount;
            emit TokenTransferFailed(body.commitment, token, amount);
            continue;
        }
    }
}
```
Alternatively, provide a governance/permissionless sweep function that lets a stuck leg's tokens be redirected to an alternate address (e.g. re-attempt with a different beneficiary) once escrow accounting has already been finalized for the other legs, so one non-transferable token cannot hold hostage the rest of the order's funds.

### Proof of Concept
1. User places a two-input order: `inputs = [USDC: 1000, DAI: 1000]`, source chain A, destination chain B.
2. Solver fills on chain B; `RedeemEscrow` is dispatched back to chain A naming the solver as beneficiary.
3. Before the redeem message is delivered on chain A, the solver's address is blacklisted on USDC (by the USDC issuer, independent of the protocol).
4. `onAccept` on chain A calls `_withdraw(body, false, true)` with `body.tokens = [USDC:1000, DAI:1000]`.
5. Loop reaches the USDC leg; `IERC20(USDC).safeTransfer(beneficiary, 1000)` reverts because the solver is blacklisted.
6. The revert propagates out of `_withdraw`, rolling back the DAI leg's transfer and escrow decrement as well.
7. The solver can never successfully redeem the DAI portion through this call because every retry hits the same USDC blacklist revert first in the loop — DAI (1000) is now permanently stuck in escrow even though it was fully claimable on its own. [3](#0-2)

```text
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
```
