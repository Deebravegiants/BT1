### Title
Operator/User QR-code Format Collision Allows a Signup-Only User QR Code to Be Accepted as an Operator QR Code - (File: src/plans/qr_scan/operator.rs)

### Finding Description
The reported Putty Finance bug is a classic "two distinct roles share one wire format" collision: `ERC20.transferFrom` and `ERC721.transferFrom` have the identical 4-byte selector, so a value meant to be treated as one asset type is silently accepted as the other, breaking the intended type/role separation.

orb-core has a structurally identical pattern in its QR-code schema parsing. The `Schema` trait defines `try_parse(code: &str) -> Option<Self>` per-type [1](#0-0) , and each caller only knows "this string parsed successfully as schema `S`" — there is no independent tag distinguishing "this is an operator identity" from "this is a user identity" in the underlying format.

Concretely, `qr_scan::operator::Data::try_parse` implements the "Normal" (non-magic) operator variant by directly delegating to `user::Data::try_parse(code)`: [2](#0-1) 

This means **any string that is a valid user-signup QR code (`userid:<uuid>:<data_policy>` or the `decode_qr` self-serve format) is also, by construction, a valid operator QR code** — the two "types" share exactly the same parse grammar with zero distinguishing marker, exactly mirroring the `transferFrom(address,address,uint256)` selector collision where an ERC721 token is accepted wherever an ERC20 token is expected.

Downstream, the resolved "operator" `Data::Normal(user::Data)` is stored as `OperatorData` and its `user_id` is sent to the backend as `distributorId` in the signup request, and used to differentiate operator vs. user roles in `handle_user_qr_code` (which only rejects the case where the *same* code is scanned twice, not the case where a user identity is used in the operator role): [3](#0-2) [4](#0-3) 

The only server-side validation found in this codebase for the operator code is `verify_operator_qr_code` (called from `scan_remaining_qr_codes`) [5](#0-4) ; I was not able to fully inspect the backend implementation of `verify_operator_qr_code` (it lives outside the indexed portion of `src/plans/mod.rs`/`src/backend/`), so I cannot confirm with certainty whether the backend performs additional role-based validation (e.g., checking that the scanned code corresponds to a registered "operator"/distributor account rather than any arbitrary end-user code) that would fully mitigate the client-side format collision. This is an area that would need direct code confirmation in a full Devin session, since the ask-only index does not expose the complete `backend::operator_status` module contents.

### Impact Explanation
If the backend does not independently enforce that the `distributorId` field corresponds to a role explicitly registered as an "operator" (as opposed to any valid signed-up user code), then the client-side type collision allows:
- A regular user's own signup QR code to be scanned in the "operator" QR-code step, self-authorizing entry into the signup flow without a legitimate operator present.
- Misattribution of signups to the wrong "operator"/distributor identity in backend records (`distributorId` in the signup POST), corrupting attribution/analytics and potentially bypassing operator-gated flows (self-serve vs. distributor flows, magic QR actions).

This matches the "misattributed signup" / "cross-signup state bleed" impact category, since operator identity — which gates and tags the signup — can be filled with data intended purely for the user role, exactly as ERC721 tokens ended up filling an ERC20 slot in the original report.

### Likelihood Explanation
Likelihood is moderate: any attacker (or curious operator) simply needs to present their own valid *user* signup QR code during the operator-scan phase of the flow, since the parser accepts it unconditionally as long as it matches the shared regex/decode grammar. No cryptographic bypass is required client-side. The residual risk is fully bounded by whatever server-side role check exists in the (unverified) `verify_operator_qr_code`/backend operator-status endpoint — if that endpoint validates against a real operator/distributor registry, the practical impact is reduced to logging/attribution corruption rather than full self-authorization.

### Recommendation
- Introduce an explicit, disjoint format discriminator between operator and user QR codes (e.g., a required prefix/tag or distinct encoding) so that `operator::Data::try_parse` cannot silently accept a valid `user::Data` payload as "Normal" operator data.
- Do not implement `operator::Data::Normal`'s parsing via direct reuse of `user::Data::try_parse`; instead validate operator identity against a role-scoped backend check independent of the shared string grammar.
- Confirm (in a follow-up session with backend code access) that `verify_operator_qr_code` enforces that the resolved `user_id` belongs to an authorized operator/distributor account, not merely "any successfully-parsed identity string."

### Proof of Concept
1. Generate/obtain a valid user signup QR-code string, e.g. `userid:3bcf883d-ce22-4a03-8608-4a8a01b88d4d:1` (matches `QR_CODE_V2` in `src/plans/qr_scan/user.rs`).
2. Present this same string during the **operator** QR-code scanning phase (`qr_scan::Plan::<qr_scan::operator::Data>::new(...)` in `scan_operator_qr_code`, `src/plans/mod.rs`).
3. `qr_scan::operator::Data::try_parse` calls `user::Data::try_parse(code)` first [6](#0-5)  and successfully returns `Data::Normal(user::Data{ user_id: "3bcf883d-...", .. })`, exactly as it would for a legitimate operator code, because the two schemas share an identical grammar (test `test_cli_operator` in `src/plans/qr_scan/user.rs` lines 209-214 demonstrates the operator dummy code being parsed via the *user* `QR_CODE_V2` regex, confirming the shared format).
4. This value is subsequently used as the "operator" identity (`distributorId`) for the remainder of the signup, without any code-level indication that it originated from a user-role QR code.
