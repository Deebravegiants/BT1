### Title
Last solver to complete a partial-fill order steals the entire `order.fees` reward from earlier contributing solvers - (File: evm/src/apps/intentsv2/IntentsBase.sol / IntrinsicIntents.sol)

### Summary
`IntentGatewayV2` same-chain orders support permissionless partial fills: multiple independent solvers can each fill a slice of the order over separate transactions, with proportional escrow released to each as they go. But the single `order.fees` reward (meant to compensate for the gas/work of completing the order) is not split proportionally — it is paid out in full, only once, to whichever solver's fill happens to make `isFullyFilled == true`. This is the same bug class as the reported `LimitOrderHook` issue: value that should be distributed based on actual contribution is instead swept entirely by whoever is present at the moment the "filled" state transition fires, rewarding a small, late, opportunistic contribution over the earlier solvers who did the bulk of the work.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:53-143`), any solver may call `fillOrder` with any positive amount toward a still-open order. Escrowed input tokens are released proportionally per fill (`fillAmount / totalRequired`), tracked via `_partialFills`, as documented in `docs/content/developers/evm/intent-gateway/overview.mdx:31-33`.

The withdrawal call, however, is:
```
_withdraw(body, false, isFullyFilled);
``` [1](#0-0) 

and `_withdraw` in `IntentsBase.sol` only releases the accumulated `TRANSACTION_FEES` bucket (`order.fees`, paid once at order placement) when `finalize == true`:
```
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
    ...
}
``` [2](#0-1) 

Since `finalize` is exactly `isFullyFilled`, the entire `order.fees` amount is paid to a single beneficiary: the solver whose fill happens to push `amountFilled == totalRequired` for every output leg. Every solver who filled an earlier slice of the same order receives none of this fee, regardless of how much of the order (and hence gas/capital) they contributed. The docs even document this outright: "A partial collects NO `order.fees`: the gateway releases those to whoever completes the order" — a design decision, but one that creates a clear incentive to game.

This is functionally identical to the `LimitOrderHook` bug: multiple independent participants (solvers) contribute to a shared position (the order) over time; a single lump-sum value (`order.fees`) accrues to that position; and the *entire* amount is captured by whichever participant happens to be present at the moment the position transitions to "complete," irrespective of their share of the underlying work.

### Impact Explanation
An attacker can watch a partially-filled order (e.g., filled 95%+ by other, unrelated solvers over multiple blocks/transactions) and submit a trivial final fill for the last remaining dust amount, becoming the `finalize`-triggering solver and sweeping 100% of `order.fees` — a reward sized to compensate for completing the *whole* order's execution/relayer cost — while having done negligible work. This is a direct, repeatable theft of value intended for the actual bulk-contributing solvers, and it discourages legitimate solvers from partially filling orders at all (since doing so exposes them to being front-run for the fee on the final sliver), degrading the partial-fill mechanism's usefulness. This is a concrete theft-of-funds scenario reachable by any unprivileged solver.

### Likelihood Explanation
High. `fillOrder` for same-chain orders is fully permissionless and requires no special privileges — any address holding the output token can submit a fill of arbitrary size, including a minimal dust amount to complete an order others have already mostly filled. No collusion, timing tricks, or special access are needed; simply monitoring `PartialFill` events for near-complete orders and racing to submit the final dust fill is sufficient to capture the entire fee.

### Recommendation
Distribute `order.fees` proportionally across all solvers who contributed a partial fill to the order, in proportion to each solver's `fillAmount / totalRequired` for the leg(s) they filled, rather than paying the full amount to the single finalizing fill. This can be implemented by accruing each solver's proportional fee share at the time of their partial fill (similar to how escrow is already released proportionally), or by tracking a list of (solver, fillAmount) pairs per commitment and splitting `TRANSACTION_FEES` pro-rata on finalization.

### Proof of Concept
1. User places a same-chain order with `order.fees = F` (fee token) and `output.assets[0].amount = 1000`.
2. Solver A fills 999/1000 of the output in one transaction — receives 999/1000 of the escrowed input proportionally, but (per current logic) `isFullyFilled = false`, so no `order.fees` are released to A.
3. Attacker (Solver B) observes the near-complete order and fills the remaining `1` unit of output — `isFullyFilled` becomes `true`, triggering `_withdraw(..., finalize=true)`.
4. `_withdraw` releases the entire `order.fees = F` to Solver B, even though B contributed only 0.1% of the fill effort/capital; Solver A, who did 99.9% of the work, receives nothing from the fee bucket.
5. This can be repeated against any partially-filled order the attacker observes nearing completion, systematically capturing fees meant for other solvers' larger contributions.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
