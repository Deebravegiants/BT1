### Title
Webhook HMAC does not bind the `shop-domain` header, allowing shop-identity forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` accepts a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds against that body-only signature. The `shop` value that the registry hands to application webhook handlers is read straight from the `X-Shopify-Shop-Domain` header, which is never part of the signed material. An attacker who can obtain any one validly-signed webhook delivery (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary victim shop domain in the header, and the gem will still report the webhook as HMAC-valid and hand the forged shop identity to the handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which is only `@raw_body`, while `shop` is derived independently from a header: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` to build the metadata passed into the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e. the body) and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

The identity binding that should hold is:
`shop_the_HMAC_was_computed_for == shop_the_handler_acts_on`

Because the header carrying `shop` is excluded from `to_signable_string`, this equality is never enforced. The `api_secret_key` used to sign webhooks is shared across every shop that has the app installed (it is the app's single secret, not a per-shop secret), so any signed body from any shop is valid for every shop. An attacker who legitimately installs the app on a shop they control receives real, validly-signed webhook deliveries. They can capture one such request and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (same body, same shared secret), so `Registry.process` proceeds and invokes the handler with `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding that webhook processing is expected to guarantee, enabling cross-tenant confusion: the application's webhook handler will act as if the victim shop sent the event (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, or any handler-specific business logic keyed off `data.shop`), while the actual signer was the attacker's own shop. Depending on what the host application does with `WebhookMetadata#shop` (deleting/resetting victim shop data, marking the app uninstalled for the victim, processing GDPR redact/data-request flows against the wrong tenant, etc.), this can result in unauthorized cross-tenant state changes performed using the attacker's own credentials while masquerading as another merchant. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on a shop they control (which is trivial for any Shopify merchant/developer), since that is the only prerequisite to obtain one validly signed webhook body/HMAC pair. No access token, `api_secret_key`, or privileged account is required — only a normal, unprivileged installation of the target app, followed by a simple HTTP replay with a modified header.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) in the material that is authenticated, or otherwise cryptographically bind the header-derived `shop` to the verified body before it is handed to consumers. At minimum, `ShopifyAPI::Webhooks::Registry` should require host applications to independently verify that `request.shop` corresponds to a shop that actually has an active, legitimate session/installation before acting on webhook data, and the gem's documentation/API should make this binding explicit rather than implying that a passing `HmacValidator.validate` result vouches for the `shop` header value.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. `POST /webhooks` with body `{}` and headers:
   - `X-Shopify-Topic: app/uninstalled`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over "{}">`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
2. Replay the identical request to the app's webhook endpoint, changing only:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: headers)` is constructed with the forged shop header; `Utils::HmacValidator.validate(request)` still returns `true` because it only checks `to_signable_string` (the untouched body) against the (unchanged) HMAC.
4. `ShopifyAPI::Webhooks::Registry.process(request)` proceeds and calls the registered `app/uninstalled` handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though `victim-shop` never sent this webhook.
