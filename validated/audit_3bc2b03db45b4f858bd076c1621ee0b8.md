### Title
Rounding down in `convert_to_balance` lets a HyperFungibleToken cross-chain transfer permanently burn/lock the sender's tokens while crediting zero to the beneficiary - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler converts an incoming EVM ERC20 amount into the local substrate balance by dividing by `10^(erc_decimals - local_decimals)`. When the ERC20-side amount is smaller than that scaling factor, the division truncates to zero, so a real (non-zero) amount minted/escrowed on the source chain is credited to the beneficiary as zero on the destination chain — an unconditional, un-guarded rounding-to-zero, structurally identical to the `MIN_GNS_WEI_IN` report where a caller's transferred tokens were silently not recorded.

### Finding Description
`convert_to_balance` performs an integer division to scale ERC20 (typically 18-decimal) amounts down to the local chain's decimals (e.g. 12 for BRIDGE on nexus, or fewer for other assets): [1](#0-0) 

This function is called unconditionally in `on_accept` (crediting a beneficiary for an inbound transfer) and in `on_timeout` (refunding the original sender): [2](#0-1) 

There is no minimum-amount check anywhere in the pipeline — neither on the EVM `HyperFungibleToken.send()` path (which burns/locks the ERC20 amount and dispatches the message) nor in `convert_to_erc20`/`convert_to_balance` on the substrate side, nor in `register_token`/`update_token` (which only enforces `config.decimals >= local_decimals`, not that dust amounts be rejected): [3](#0-2) 

Concretely, for the BRIDGE token (18 decimals on EVM, 12 on nexus, scale factor `10^6`), any ERC20 `amount < 1_000_000` wei (i.e. < 0.000001 BRIDGE) truncates to `0` local units. The source-chain `HyperFungibleToken.send()`/burn still executes for the full nonzero `amount`: [4](#0-3) 

and the message is dispatched and delivered with that nonzero ERC20 `amount` field, but `on_accept` mints/releases `amount = 0` to the beneficiary since `convert_to_balance` truncated it — the tokens are effectively burned with nothing minted on the other side. The same non-zero-truncated-to-zero issue applies symmetrically to the EVM→EVM leg when a wrapped/hyper-fungible token's decimals differ enough to require division, and to `on_timeout` refunds where dust amounts below the scale factor would refund `0` instead of restoring the sender's balance.

### Impact Explanation
This is a direct loss-of-funds bug reachable by any unprivileged user who calls `send()` (EVM `HyperFungibleToken.send`/`BridgeToken.send`, or the substrate `pallet-hyper-fungible-token::send` extrinsic) with a dust amount below the chain's decimal-scaling threshold. The source side burns/escrows the user's real value; the destination side credits nothing, permanently destroying the sender's value (functionally equivalent to freezing/loss of funds). This maps to the "concrete theft or permanent freezing of funds" acceptance criterion and is analogous to the GNS report's "transferred tokens not recorded" class of bug, but here it is a token-bridge mint/burn path explicitly in scope.

### Likelihood Explanation
Likelihood is medium: it requires a user (or relayer/token bridger acting on a user's behalf) to send an amount smaller than the decimal-scale factor (e.g., under 10^6 wei of an 18-decimals ERC20 for a 12-decimals destination, or a larger truncation factor for other configured token pairs with bigger decimal gaps). This can happen accidentally (dust transfers, wrapped small balances, script/automation bugs) or be triggered deliberately by a griefer to strand another account's inbound dust, though the primary victim is the sender/beneficiary themselves. No privileged role is needed — a single `send` transaction is sufficient to trigger it.

### Recommendation
Add an explicit minimum-transfer-amount check (analogous to fixing `MIN_GNS_WEI_IN`) before dispatching on the source side and/or after scaling on the destination side:
- On the EVM `HyperFungibleToken.send()` / substrate `send()` extrinsic, reject amounts whose scaled-down local representation would be zero (i.e., require `amount >= 10^(erc_decimals - local_decimals)`), or reject any transfer below a governance-configured minimum.
- In `convert_to_balance`, return an explicit error (rather than silently returning `0`) when the computed local balance is zero for a non-zero input, and have `on_accept`/`on_timeout` propagate/handle this as a failure rather than crediting zero.

### Proof of Concept
1. Register BRIDGE on nexus with EVM decimals = 18 and local `Decimals` = 12 (as done for `BridgeToken`, scale factor `10^6`).
2. On the EVM `BridgeToken`, call `send({ ..., amount: 999_999 })` (less than `10^6` wei) — this burns 999,999 wei of BRIDGE from the sender and dispatches a `Send` message with `amount = 999999`.
3. On delivery, `on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs` calls `convert_to_balance(U256::from(999_999), 18, 12)`, which computes `999_999 / 10^6 = 0` (integer division), so `Assets::mint_into`/`NativeCurrency::transfer` credits the beneficiary with `0`.
4. Net effect: 999,999 wei of BRIDGE permanently disappears (burned on EVM, never credited on nexus), with `TokenReceived { amount: 0, ... }` emitted as if nothing was wrong. [5](#0-4) [6](#0-5)

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
