### Title
Native-fee dispatch path prices required fee-token output from unguarded Uniswap V2 spot reserves, letting a single dispatcher over/under-pay via sandwich manipulation - (File: `sdk/packages/core/contracts/apps/HyperApp.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`HyperApp.quote()` and the native-payment branch of `EvmHost`'s dispatch flow derive the amount of native currency required to cover a message's fee by calling `IUniswapV2Router02.getAmountsIn`/executing a native→feeToken swap against the configured Uniswap V2 pool at call time, with no deviation check, TWAP, or minimum-liquidity/staleness guard. This is the same bug class as H‑04: an external price source is consumed directly by a fund-moving operation (a swap that determines how much of the caller's native token is taken to fund a relayer-fee-token payment) without filtering for a manipulated/outlier price.

### Finding Description
`HyperApp.quote(DispatchPost)` / `quote(DispatchGet)` read the WETH→feeToken price straight from `IUniswapV2Router02.getAmountsIn` on the host's configured router: [1](#0-0) 

The protocol's own documentation for `post-requests`/`get-requests` explicitly states that a caller paying in native token has `IDispatcher(host()).dispatch{value: msg.value}(...)`, and that "the Host will swap native -> feeToken via Uniswap" as part of that single dispatch transaction: [2](#0-1) 

The docs go on to warn, in the same page, that `quote()` "uses Uniswap's getAmountsIn, making it vulnerable to sandwich attacks" and should only ever be used off-chain for estimation — never inside a smart-contract transaction: [3](#0-2) 

Despite that warning, the actual on-chain dispatch-with-native flow performs the swap in the same transaction the caller controls (`dispatch{value: msg.value}(...)`), which is exactly the "vulnerable" usage the docs describe, not the off-chain estimation usage they recommend. The off-chain relayer tooling (`tesseract/messaging/evm/src/gas_oracle.rs::get_price_from_uniswap_router`) independently confirms this router/pool is the sole price source used to convert fee-token costs to native, with no secondary oracle or bounds check: [4](#0-3) 

The `EvmHostForkTest.sol` test harness's own `quote()` helper reproduces the same unguarded `getAmountsIn` call pattern used by the real dispatch path: [5](#0-4) 

Unlike Chainlink-fed contracts elsewhere in this codebase (`SimplexPaymaster._getOraclePrice`, which enforces staleness and positivity checks), the Uniswap V2 spot price consumed here has none of the mitigations recommended by the H‑04 report or even the codebase's own basic protections (staleness bound, deviation-from-median check). Any account that can manipulate the reserves of the WETH/feeToken pool immediately before calling `dispatch{value: msg.value}(...)` — e.g. via a large swap in the same block, a flash loan, or a favorable-timing bundle — can distort the native amount pulled from `msg.value` relative to the actual fee-token cost intended to be charged.

### Impact Explanation
Because the swap and the price read happen atomically inside the dispatcher's own transaction, an attacker dispatching a message can manipulate the pool immediately beforehand (self-sandwich) to make the swap under-price the fee token, extracting more native value back as "refund" than intended, or force other unrelated in-flight dispatches that reuse the same pool state to overpay. Over repeated dispatches this directly siphons value from the protocol's fee/relayer economics — a fund-loss vector reachable by a single unprivileged dispatcher, matching the "concrete theft of funds" bar.

### Likelihood Explanation
Uniswap V2 pools are trivially manipulable within a single block/transaction bundle via flash loans, and the dispatch call is fully permissionless — any address can call `dispatch{value: msg.value}` and control the preceding swap that sets the pool state. No governance, relayer, or consensus proof is required to reach this path, so likelihood is high wherever the configured Uniswap V2 pool for a given fee token has moderate-to-low liquidity (common on newer or smaller EVM deployments).

### Recommendation
Do not perform the native→feeToken conversion using a live `getAmountsIn`/spot-reserve read inside the same transaction as `dispatch`. Either: (1) require callers to pre-quote off-chain and pass an explicit `amountInMax`/slippage-bounded parameter enforced on-chain, (2) source the native/feeToken price from a TWAP oracle or a Chainlink feed with staleness and deviation checks (mirroring `SimplexPaymaster._getOraclePrice`), or (3) adopt the H‑04-style mitigation of tracking recent price samples and rejecting a swap whose implied price deviates beyond a threshold from the recent median before executing the fee-token conversion.

### Proof of Concept
1. Attacker identifies a chain where `EvmHost`'s configured `uniswapV2Router` pool for WETH/feeToken has shallow liquidity.
2. In one bundled/atomic sequence, attacker swaps a large amount into/out of the pool to shift the WETH/feeToken price.
3. Attacker immediately calls a HyperApp's dispatch entrypoint with `dispatch{value: msg.value}(post)`, where `msg.value` was sized off the pre-manipulation `quote()` (or is undercharged relative to the post-manipulation pool state that the underlying swap executes against).
4. The host's native-fee swap executes against the manipulated pool, producing a fee-token amount inconsistent with the real market price, either under-funding the relayer fee (message likely undelivered/DoS) or draining excess value from the swap output back to the attacker, depending on manipulation direction.
5. Attacker reverts the initial pool manipulation in the same block/bundle, retaining the profit or paying an artificially cheap fee, at the expense of the protocol/relayer economics.

Note: I could not fully trace the exact `EvmHost.sol` function that executes the on-chain native→feeToken swap (grep found 14 references to `uniswapV2Router`/`getAmountsIn` in that file, but the full function body wasn't read due to the iteration limit) — the finding is corroborated by the docs' explicit dispatch flow description and warning, plus the identical unguarded pattern reused in test harnesses and the off-chain gas oracle, but a Devin session with full file access should confirm the precise swap call site and its slippage-protection (if any) before filing this as final.

        path[0] = IUniswapV2Router02(_uniswap).WETH();

async fn get_price_from_uniswap_router(
	ismp_host: H160,
	client: Arc<AlloyProvider>,
) -> Result<U256, Error> {
	let host = EvmHostInstance::new(Address::from_slice(&ismp_host.0), client.clone());
	let params = host.hostParams().block(BlockId::latest()).call().await?;

	// There are no uniswap pool on testnet, return 1 usd as native token value
	if params.hyperbridge.0.starts_with(b"KUSAMA") {
		return Ok(U256::from(10).pow(U256::from(27)));
	}

	let uniswap_v2 = H160::from_slice(params.uniswapV2.as_slice());
	let fee_token = Address::from_slice(params.feeToken.as_slice());

	if uniswap_v2 == H160::zero() {
		return Err(anyhow!("Uniswap V2 Router not configured in Host Params"));
	}

	let router = IUniswapV2Router::IUniswapV2RouterInstance::new(params.uniswapV2, client.clone());
	let native_token = router.WETH().block(BlockId::latest()).call().await?;

	let fee_token_contract = IERC20::IERC20Instance::new(fee_token, client.clone());
	let fee_token_decimals = fee_token_contract.decimals().block(BlockId::latest()).call().await?;

	let native_token_contract = IERC20::IERC20Instance::new(native_token, client.clone());
	let native_decimals = native_token_contract.decimals().block(BlockId::latest()).call().await?;

	let path = vec![fee_token, native_token];
	let amount_out = primitive_to_alloy_u256(U256::from(10).pow(U256::from(native_decimals)));

	let amounts = router.getAmountsIn(amount_out, path).block(BlockId::latest()).call().await?;

	if amounts.is_empty() {
		return Err(anyhow!("Invalid amounts returned from Uniswap V2 Router"));
	}

	let amount_stable = alloy_u256_to_primitive(amounts[0]);

	let target_decimals = 27;
	Ok(amount_stable * U256::from(10).pow(U256::from(target_decimals - fee_token_decimals as u32)))
}
