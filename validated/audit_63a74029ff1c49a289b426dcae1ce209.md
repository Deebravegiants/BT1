Based on the investigation, I found a directly reachable analog of the "single signer inflating a submission count" bug class in the EVM BEEFY consensus client.

### Title
Missing duplicate-signer check in BEEFY commitment verification allows an attacker to inflate the supermajority count with a single authority's repeated signature - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
`EcdsaBeefy.sol:verifyMmrUpdateProof` (L122-172) derives the number of participating signers purely from `relayProof.signedCommitment.votes.length` (`sigLen`, L127) and feeds this count directly into `checkParticipationThreshold(sigLen, authoritySet.len)` (L140) to decide whether a 2/3+1 supermajority was reached. Nowhere in the loop that recovers signer addresses (L144-159) is there a check that the `vote.authorityIndex` values (and thus the underlying authority) are unique across the submitted `votes` array.

### Finding Description
The `votes` array inside `relayProof.signedCommitment` is fully attacker/relayer supplied calldata. For each vote, the contract recovers the signer via `ECDSA.recover` and builds a `MerkleMultiProof.Leaf` keyed on `vote.authorityIndex`: [1](#0-0) 

Nothing prevents the same `(authorityIndex, signature)` pair from appearing multiple times in `votes`. Since `sigLen` is simply `votes.length` (L127) and is used directly as the numerator for the supermajority check at L140, a single valid authority signature duplicated N times inflates the apparent participant count by N without any additional real signer. This is structurally identical to the `Reject.sol` bug described in the report, where `submissionCount`/`custodians` were counted per loop iteration without deduplication, allowing one malicious signer to fake multiple independent submissions. [2](#0-1) 

By contrast, the codebase's other consensus verifiers explicitly guard against this exact bug class: the Pharos verifier deduplicates `participant_keys` via a `BTreeSet` and returns `Error::DuplicateParticipant` on collision [3](#0-2) , and the Tendermint verifier calls `ensure_unique_addresses` to reject validator sets/next-validator sets with duplicate addresses [4](#0-3) . `EcdsaBeefy.sol`, which is one of the production consensus clients wired into `IConsensusV2` for relay-chain state commitment updates, has no equivalent uniqueness check on the votes/authority indices used for its supermajority threshold.

### Impact Explanation
If exploitable, this would let a relayer submit a consensus proof to `EcdsaBeefy.verify` (the `IConsensusV2` entry point, L96-114) that appears to meet the 2/3+1 supermajority using far fewer than the required number of distinct authorities — potentially just one signer plus duplicated vote entries. That would allow finalization of an attacker-influenced MMR root / parachain header state commitment, i.e. an unsound state commitment being accepted as finalized, which downstream `HandlerV2`/`EvmHost` message delivery relies on for state and non-membership proofs.

### Likelihood Explanation
This part is only partially verifiable from the repo: `MerkleMultiProof.VerifyProof` is provided by the external `@polytope-labs/solidity-merkle-trees` dependency, whose implementation is not present in this repository, so I could not confirm from in-scope code whether it independently rejects duplicate `(index, hash)` leaf entries in a multi-proof, which would determine whether the merkle membership check alone prevents the exploit even though the `sigLen` counting itself is unguarded. The root-cause gap — no explicit duplicate-authorityIndex check in `EcdsaBeefy.sol` before using `votes.length` for the threshold — is confirmed and present in-repo, but full exploitability depends on external library behavior I cannot verify here.

### Recommendation
In `verifyMmrUpdateProof`, track seen `authorityIndex` values (e.g. via a bitmap or a scratch mapping) while building the `authorities` leaves array, and revert with a new error (e.g. `DuplicateAuthorityIndex`) if any index repeats, before computing `sigLen`/calling `checkParticipationThreshold`.

### Proof of Concept
1. Obtain (or wait for) one valid BEEFY authority signature over a commitment.
2. Construct `relayProof.signedCommitment.votes` with that same `(authorityIndex, signature)` entry repeated `k` times so that `votes.length` alone satisfies `checkParticipationThreshold(sigLen, authoritySet.len)`.
3. Submit via `EcdsaBeefy.verify(previousState, proof)`; since no dedup check exists on `authorityIndex` before the threshold check, `verifyMmrUpdateProof` proceeds to accept the MMR update as if a genuine supermajority had signed, assuming the merkle multi-proof library does not independently reject duplicate leaf indices (unverified external dependency).

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}

/// Rejects a validator set that reuses the same address twice. Each address is a
/// hash of its public key, so a duplicate signals a set that was not built honestly.
fn ensure_unique_addresses(
	validators: &[cometbft::validator::Info],
) -> Result<(), VerificationError> {
	let unique = validators.iter().map(|v| v.address).collect::<BTreeSet<_>>();
	if unique.len() != validators.len() {
		return Err(VerificationError::ValidatorSetError(
			"duplicate validator address in set".to_string(),
		));
	}
	Ok(())
}
