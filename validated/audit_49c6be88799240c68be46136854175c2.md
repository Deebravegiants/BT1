### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` (via the `shopify-shop-domain` / `x-shopify-shop-domain` header) and the HMAC signature independently, but the HMAC is computed and verified only over the raw request body. The `shop` field is never part of the signed material, so a caller in possession of any single valid `(body, hmac)` pair — for example one obtained from a legitimate webhook delivered to their own installed shop — can resend that exact body/HMAC pair while substituting an arbitrary `shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` accepts this as valid and dispatches it to the app's handler labeled with the attacker-chosen shop, breaking the binding `authenticated_shop == webhook_recipient_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC solely from `verifiable_query.to_signable_string` (i.e. the raw body) and the secret, and compares it to the `hmac` header value: [3](#0-2) 

`Webhooks::Registry.process` validates only this body HMAC before dispatching the handler with `request.shop` taken straight from the unsigned header, with no additional check that the shop is the one Shopify actually delivered the webhook for: [4](#0-3) 

Because the `hmac-sha256` value only proves "this body was signed by our `api_secret_key` at some point for some webhook," and not "this body belongs to shop X," any entity that can obtain one genuine `(raw_body, hmac)` pair signed under the app's `api_secret_key` — trivially available to any merchant who has installed the app and can trigger/capture a webhook delivery for their own store — can replay that exact pair to the app's public webhook endpoint with a forged `shopify-shop-domain` header naming a different (victim) shop. `HmacValidator.validate` returns `true` because the body/HMAC pair is genuinely valid, and `Registry.process` proceeds to invoke the app's handler with `WebhookMetadata` carrying the attacker-chosen `shop`.

This is exactly the "field acted on but not covered by the HMAC" identity-binding defect category: the equality that should hold is `hmac_verifies(body) => shop_in_payload == the_shop_that_produced_that_body`, but the library only proves the left side and lets the host trust the unauthenticated `shop` value.

### Impact Explanation
Any application built on this gem that keys per-tenant business logic (order creation, inventory updates, uninstall/GDPR flows, product sync, etc.) off `WebhookMetadata#shop` as returned by `Registry.process`/`Request#shop` can be made to attribute attacker-supplied webhook payloads to an arbitrary victim shop, without ever possessing that victim's access token or the app's `client_secret`. This is a cross-tenant data/state injection primitive purely through this gem's own webhook verification contract, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) being any merchant/attacker who has installed the target app on their own store (a normal, unprivileged flow — no special access needed), (2) capturing one legitimate webhook delivery (body + `hmac-sha256` header) sent to their own shop, and (3) POSTing that exact body with the same HMAC header to the app's webhook endpoint while changing the `shop-domain` header to the victim shop's domain. No credential of the victim or the app's secret is needed. The library performs no header/shop binding, so likelihood is high wherever an app trusts `request.shop`/`WebhookMetadata#shop` for tenant-scoped effects, which is the documented usage pattern.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`) in the HMAC-verified signable material, or otherwise cryptographically bind the shop domain to the signature (e.g., verify the shop against a value derived from data covered by the HMAC, not a bare header). At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against a shop it already has an active, verified session/installation for before using it as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic subscribed by the app (e.g. `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` sent by Shopify — both are valid under the app's real `api_secret_key`.
2. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` → returns `true`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.
