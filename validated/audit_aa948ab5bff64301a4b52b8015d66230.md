### Title
Webhook `shop-domain` Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the webhook HMAC against that body alone. The `shop-domain` header, which is passed unauthenticated into the handler as the tenant identifier, is never included in the signed material. An attacker who can obtain one validly-signed webhook (e.g., by installing the app on their own store) can replay the identical body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the request still passes validation while claiming to originate from a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field via `OpenSSL.secure_compare`. [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers that are outside the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop` (from the unauthenticated header) as the tenant identity in `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(secret, signed_bytes) == true` must imply `shop == the shop that produced signed_bytes`.

In this implementation, `signed_bytes = raw_body` only, so the equality actually enforced is `hmac_valid(secret, raw_body) == true`, which says nothing about `shop`. Any two requests with the same body but different `shop-domain` headers are equally "valid" per this check — this is exactly the "field acted on but not covered by the HMAC" analog: the gem cryptographically proves body integrity but silently trusts the header-derived `shop` used for tenant routing.

### Impact Explanation
This breaks the tenant boundary that the webhook signature is supposed to enforce. A merchant/attacker who runs their own store can install the target app and receive a legitimately Shopify-signed webhook (body + HMAC) for their own shop, then replay that exact byte-identical body with a forged `shop-domain` (and optionally forged `topic`/`webhook-id`) header pointing at any victim shop, since `to_signable_string` never binds `shop` into the signature. Because `WebhookMetadata.shop` is the value host applications use to select the tenant record to act on (create/update/delete data, trigger redaction, etc.), an attacker can cause the app to process data under a victim shop's tenant context — e.g., trigger `shop/redact`/`customers/redact` handling, or inject fabricated order/customer payloads attributed to a shop the attacker does not control. This is a cross-tenant data-integrity/impersonation issue.

### Likelihood Explanation
Exploitation only requires the attacker to run their own Shopify development/trial store and install the target app (both are free, unprivileged actions any internet user can perform), then capture one legitimate webhook delivery and replay it with a modified header value. No access to the app's `client_secret`, access tokens, or any victim credentials is required, and the HMAC check as implemented will still pass.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material actually verified, e.g., verify the header-derived `shop` against session/installation records known to be associated with that webhook subscription, or require the host application to independently confirm that `data.shop` corresponds to a shop with an active installation before trusting it for tenant-scoped operations. At minimum, document prominently that `WebhookMetadata.shop` is unauthenticated and must not be used as the sole tenant key without additional verification (e.g., cross-checking against a known list of installed shops) since the HMAC in this gem only covers the raw body, not headers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only checks `OpenSSL::HMAC.hexdigest(sha256, secret, raw_body)` against the received HMAC — the header is irrelevant to this computation, per `lib/shopify_api/webhooks/request.rb` line 36-38 and `lib/shopify_api/utils/hmac_validator.rb` line 26-31.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)`, causing the host application to act as though the payload genuinely originated from `victim.myshopify.com`. [4](#0-3) [5](#0-4)
