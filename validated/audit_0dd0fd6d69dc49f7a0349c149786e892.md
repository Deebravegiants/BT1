### Title
`Wallet#updateSeed` injects phantom seed metadata for arbitrary/non-existent `seedId` without validation - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet#updateSeed` merges an arbitrary attacker-supplied `seedId` string directly into `seedMetadataAtom` without verifying that the `seedId` corresponds to a real seed in the keychain or `extraSeeds` storage. This allows creation of phantom metadata entries not backed by any actual seed, breaking the invariant that every key in `seedMetadata` corresponds to a real seed (primary or extra).

### Finding Description
`updateSeed` only asserts that `seedId` and `label` are non-empty and then unconditionally writes to `#seedMetadataAtom`: [1](#0-0) 

There is no existence check against `#primarySeedIdAtom` or against `#getExtraSeeds()`/`getExtraSeedIds()`, unlike `removeManySeeds`, which explicitly resolves real extra seed IDs before mutating state [2](#0-1) , and unlike `addSeed`, which derives `seedId` from an actual mnemonic via `getSeedId(seed)` rather than accepting a caller-supplied ID [3](#0-2) .

Notably, `updateSeed` also does not call `#assertWalletIsUnlocked()`, unlike `addSeed`/`removeManySeeds`, but per the question's precondition the wallet is already unlocked so this is not the focus.

`walletApi` exposes `updateSeed` directly to callers with no additional guard: [4](#0-3) . So the reachable call `wallet.updateSeed({ seedId: 'attacker-controlled-id', label: 'x' })` will succeed and write `seedMetadata['attacker-controlled-id'] = { label: 'x', dateUpdated: ... }` even though no seed with that ID exists in the keychain or `extraSeeds` storage.

`getSeedMetadata()` simply returns the raw atom content [5](#0-4) , so the phantom entry is directly observable by any consumer of `getSeedMetadata()`, and the atom is declared `public: true` [6](#0-5) , meaning other modules/UI can subscribe to it directly.

### Impact Explanation
The consistency invariant "every key in `seedMetadata` maps to a real seed in keychain/extraSeeds" is violated. This is a data-integrity/state-corruption issue confined to metadata: no keys, mnemonics, signing, or funds are affected, since keychain operations (`exportKey`, `addSeed`, `removeSeeds`) key off actual seed IDs derived from real seed material, not off `seedMetadataAtom`. The scoped impact is limited to UI/consumer modules potentially rendering a bogus seed entry (e.g., in a seed list) that does not correspond to any real, importable/exportable seed. This does not constitute unauthorized signing, secret disclosure, auth bypass, or account/origin confusion for actual key material — it is a metadata/state hygiene bug with UI-facing (cosmetic/confusing) consequences rather than direct wallet compromise.

### Likelihood Explanation
Trivially reachable: after `wallet.create()` and `wallet.unlock()` (both routine, unprivileged operations for the wallet's own owner), a single call `wallet.updateSeed({ seedId: 'attacker-controlled-id', label: 'x' })` succeeds every time with no error and no side effects preventing it. No secrets, timing, or race conditions required.

### Recommendation
In `updateSeed`, validate `seedId` against real seed identities before merging: check it equals `await this.#primarySeedIdAtom.get()` or appears in `await this.getExtraSeedIds()`, and throw (e.g., "No seed matches seedId.", consistent with `getMnemonic`'s existing error) otherwise. Optionally also add `await this.#assertWalletIsUnlocked()` for consistency with `addSeed`/`removeManySeeds`.

### Proof of Concept
```js
it('rejects updateSeed for a non-existent seedId (metadata consistency invariant)', async () => {
  await wallet.create()
  await wallet.unlock()

  const bogusSeedId = 'attacker-controlled-id'
  await expect(wallet.updateSeed({ seedId: bogusSeedId, label: 'x' })).rejects.toThrow(
    /No seed matches seedId/
  )

  const metadata = await wallet.getSeedMetadata()
  const primarySeedId = await wallet.getPrimarySeedId()
  const extraSeedIds = await wallet.getExtraSeedIds()
  const validIds = new Set([primarySeedId, ...extraSeedIds])

  for (const seedId of Object.keys(metadata)) {
    expect(validIds.has(seedId)).toBe(true) // invariant: every metadata key maps to a real seed
  }
})
```
Current behavior (before fix): the first assertion fails because `updateSeed` resolves without throwing, and the loop assertion fails because `bogusSeedId` appears as a key in `metadata` despite not being a real seed.

  addSeed = async ({ mnemonic, label, compatibilityMode }) => {
    await this.#assertWalletIsUnlocked()

    const seed = await mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })
    const seedId = await getSeedId(seed)
    if (seedId === (await this.#primarySeedIdAtom.get())) {
      throw new Error('Seed already present')
    }

    const dateCreated = this.#clock.now()
    const data = { mnemonic, seed, dateCreated, compatibilityMode }
    const seeds = await this.#getExtraSeeds()
    if (seeds.length >= this.#maxExtraSeeds) {
      throw new Error('Maximum number of seeds reached')
    }

    if (seeds.some((seed) => seed.mnemonic === mnemonic)) {
      throw new Error('Seed already present')
    }

    seeds.push(data)
    await this.#setExtraSeeds(seeds)
    await this.#seedMetadataAtom.set((previous) => ({
      ...previous,
      [seedId]: { dateCreated, label, compatibilityMode },
    }))

    return this.#keychain.addSeed(data.seed)
  }
