### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the HMAC signature over the raw webhook body only, while the `shop` (tenant identity) is taken from an HTTP header that is never included in the signed bytes. An attacker who can obtain one legitimately-signed webhook (trivial: install the app on their own store) can replay that exact body/HMAC pair against the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `HmacValidator`/`Request` will report the payload as valid because verification only checks the body, not the shop binding, breaking the intended identity equality `verified_bytes == (body, shop)`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, but `to_signable_string` — the value that actually gets HMAC-verified — returns only `@raw_body`: [2](#0-1) 

Verification itself is generic and only checks whatever `to_signable_string` returns against `hmac`: [3](#0-2) 

Because Shopify computes the same HMAC-SHA256 over the raw body using the single shared `api_secret_key` for the whole app (not per-shop), a body+HMAC pair that is valid for shop A's webhook remains a byte-for-byte valid signature no matter which `shop-domain` header accompanies it. The gem's `Request#shop` accessor — the only tenant-identifying field it exposes to host applications — is therefore never actually authenticated.

This directly matches the requested bug class: "a field acted on but not covered by the HMAC" — here the acted-on field is the webhook's shop identity.

### Impact Explanation
`Webhooks::Request#shop` is the gem's documented mechanism for host applications to determine which merchant a webhook event belongs to. If an app trusts this value (as the gem's own API implies is safe once `hmac` validates), an attacker can:
1. Install the app on an attacker-controlled/free development store to receive one genuine, correctly-signed webhook (e.g., `orders/create`).
2. Replay the identical raw body and `hmac-sha256` header to the app's public webhook endpoint, but with the `shopify-shop-domain` header changed to a victim merchant's domain.
3. The HMAC check passes (it only checks the body), and the host application, relying on this gem's `Request#shop`, processes/stores the event under the victim's tenant.

This is a cross-tenant data-integrity issue: an unprivileged internet user (any developer with access to a free dev store) can inject events attributable to a shop they do not own, without possessing that shop's access token, `client_secret`, or any privileged credential.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining one valid signed webhook only requires installing the app on any store (including a free development store), which is available to any unprivileged internet user. No secret material or victim credentials are needed — only the ability to replay an HTTP POST with a modified header, which is trivial once armed with a captured valid (body, hmac) pair. The library itself provides no cross-check to prevent this, so exploitability depends entirely on how consistently host apps trust `Request#shop`, but the gem does nothing to prevent or warn against the mismatch.

### Recommendation
Bind the `shop` value into the signed material, or provide a documented, mandatory secondary check: e.g., require the host application to pass the expected/session shop domain to `Request.new`/`HmacValidator.validate` and reject mismatches, or fold the shop-domain header into `to_signable_string` if Shopify's signing scheme is updated to support it. At minimum, update `Webhooks::Request` to clearly flag `shop` as unauthenticated, and add a helper that cross-references `shop` against a caller-supplied trusted shop before exposing it, so host apps do not implicitly rely on an unverified header for tenant routing.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw body B computed with the app's shared client_secret>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Raw body `B`
2. Attacker replays the exact same raw body `B` and the same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers)` and calls the HMAC validator: [4](#0-3) 
   Validation succeeds because `to_signable_string` only re-hashes `B`, which is unchanged.
4. The host application reads `request.shop` (now `victim-shop.myshopify.com`) and `request.parsed_body` (attacker-controlled order data from their own store) and processes it under the victim's tenant record — a cross-tenant data-integrity violation rooted entirely in this gem's `Webhooks::Request` design.
