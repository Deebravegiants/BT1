## Analysis

This maps directly onto the "process breaks when the counterpart chain/bridge is left in a paused/frozen state" bug class from the Sherlock report, but manifests in `tesseract`'s mandatory-consensus admin relayer rather than in a single on-chain contract.

`EvmHost` normally gates almost every state-mutating entrypoint behind a `frozen` status: `dispatch()` reverts via the `notFrozen` modifier when `_frozen` is `Outgoing` or `All`, and `HandlerV2.handleConsensus()`/`handlePostRequests()` revert via their own `notFrozen(host)` modifier when `_frozen` is `Incoming` or `All`. [1](#0-0) [2](#0-1) 

The admin-relayer's design intentionally keeps the host in `FROZEN_ALL` at rest and only briefly unfreezes it to submit a mandatory authority-set-handover consensus proof, via an atomic `[unfreeze, handleConsensus, freeze]` sequence. [3](#0-2) 

For chains that use `SubmissionMode::Sequential` (chains without EIP-7702 support, e.g. Soneium, per the code comment), `submit_mandatory_sequential` builds the `unfreeze` calldata but never sends it — the transaction is commented out — and jumps straight to calling `handleConsensus`: [4](#0-3) 

Because the host is never unfrozen, `handleConsensus` will unconditionally revert with `HostFrozen()` (since `_frozen == FrozenStatus.All` triggers the `notFrozen(host)` modifier). This means mandatory consensus/authority-set-handover updates for that chain can never be submitted through this path — the consensus client for that state machine stalls permanently, and since all downstream `handlePostRequests`/`handleGetResponses` calls depend on fresh state commitments derived from consensus updates, the entire route to/from that chain becomes unable to deliver messages. This is the same failure mode as the source report: a paused/frozen bridge silently blocks not just the intended operation but every other process dependent on it.

The `submission_mode` config defaults to `Batched`, but any chain explicitly configured with `submission_mode = "sequential"` in the admin-relayer TOML is exposed to this permanent stall. [5](#0-4) 

### Title
Sequential mandatory-consensus submission path never unfreezes the host, permanently blocking consensus updates and message delivery - (File: tesseract/consensus/admin-relayer/src/batch.rs)

### Summary
`submit_mandatory_sequential` is supposed to perform `setFrozenState(None)` → `handleConsensus` → `setFrozenState(All)` as three sequential EOA transactions for chains that don't support EIP-7702 batching. The unfreeze and refreeze transactions are commented out, so only `handleConsensus` is sent while the host remains frozen.

### Finding Description
`EvmHost`/`HandlerV2` gate `handleConsensus` behind a `notFrozen(host)` modifier that reverts with `HostFrozen()` whenever `frozen()` is `Incoming` or `All`. [2](#0-1) 
The admin-relayer design keeps hosts frozen at rest (`FROZEN_ALL`) between mandatory updates and relies on the atomic `[unfreeze, consensus, freeze]` sequence to briefly lift the freeze so `handleConsensus` can succeed. [6](#0-5) 
In `submit_mandatory_sequential`, the `_unfreeze_cd` calldata is built but the corresponding `send_and_await_receipt` call is commented out, so the host is never actually unfrozen before `handleConsensus` is submitted, and the "refreeze" is also disabled. [7](#0-6) 
Every `handleConsensus` submission via this mode will revert because the host is still frozen, and the task's retry loop will keep re-submitting the same failing transaction forever. [8](#0-7) 

### Impact Explanation
Any chain configured with `submission_mode = "sequential"` can never receive its mandatory authority-set-handover consensus updates through this relayer. Since consensus updates gate all subsequent state-machine commitment updates, and `validate_state_machine`/`is_consensus_client_frozen` checks are prerequisites for processing any incoming request/response, this permanently stalls message delivery to/from that state machine — a "route unable to deliver messages" condition affecting all applications relying on that route, not merely a single operation.

### Likelihood Explanation
This is deterministic, not probabilistic: every invocation of `submit_mandatory_sequential` will hit the `notFrozen` revert as long as the host is frozen at rest, which is the intended steady state per the module's own documentation. Any chain operator selecting `Sequential` mode (documented as required for EIP-7702-incompatible chains) triggers this immediately on the first mandatory handover.

### Recommendation
Re-enable the `unfreeze` transaction before `handleConsensus` and the `freeze` transaction after it in `submit_mandatory_sequential`, ensuring the refreeze is attempted (with fallback alerting) even if the consensus step fails, matching the doc comment's stated intent.

### Proof of Concept
1. Deploy/configure a chain in the admin-relayer TOML with `submission_mode = "sequential"`.
2. Set the corresponding `EvmHost._frozen` to `FrozenStatus.All` (the intended steady state).
3. Trigger an `EpochChanged` notification so `run_mandatory_task` pulls a mandatory proof and calls `submit_mandatory(&client, proof, SubmissionMode::Sequential)`.
4. Observe that `submit_mandatory_sequential` only sends `handleConsensus`, which reverts with `HostFrozen()` inside `EvmHost`/`HandlerV2`'s `notFrozen` modifier, since `_frozen` was never reset to `None`.
5. The task logs the failure and retries indefinitely; the host's consensus/state commitments never advance for this chain.
