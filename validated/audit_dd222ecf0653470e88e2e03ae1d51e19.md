Confirmed: `request.from` is set to `abi.encodePacked(_msgSender())` [1](#0-0)  meaning any EOA can dispatch a `PostRequest` (or, analogously, a `GetRequest`) with `from` set to their own EOA address, which has no code.

### Title
Missing contract-existence check in `EvmHost.dispatchIncoming(GetResponse)` and `dispatchTimeOut` allows silent "success" and permanent loss of relayer fee refunds / app notifications - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(PostRequest, ...)` explicitly checks `extcodesize(destination) == 0` and early-returns before making the low-level `.call` to the destination module [2](#0-1) . However, the sibling entry points `dispatchIncoming(GetResponse, ...)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)` perform the identical pattern of a low-level `.call` to `_bytesToAddress(...)` but omit this check entirely [3](#0-2) . This is exactly the bug class described in the external report: a low-level `call` to a destination is treated as evidence of successful execution, but `call` to an address with no code trivially returns `success = true` in the EVM, regardless of whether any real logic executed.

### Finding Description
In `dispatchIncoming(GetResponse memory response, address relayer)`, the receipt bookkeeping (`_responseReceipts[commitment] = ...`) is written, then a raw `.call` is made to `_bytesToAddress(response.request.from)` invoking `onGetResponse` [4](#0-3) . If that address has no deployed code (an EOA, or a contract that never existed / was mis-encoded), the call still returns `success = true`. Since the code branches on `success`, it proceeds down the "handled" path: it pays out the relayer fee via `IERC20(feeToken()).safeTransfer(relayer, fee)` and emits `GetRequestHandled` [5](#0-4)  — even though the target app's `onGetResponse` logic never ran.

The same pattern recurs in `dispatchTimeOut(GetRequestTimeout, ...)` and `dispatchTimeOut(PostRequestTimeout, ...)`: `_requestCommitments[commitment]` is deleted for replay protection *before* the call, the call is made to `_bytesToAddress(timeout.request.from)`, and only on `!success` is the commitment metadata restored to allow a retry [6](#0-5) [7](#0-6) . If `timeout.request.from` has no code, the call spuriously succeeds, the commitment stays deleted (no retry path exists), and the relayer/sender fee is refunded — but the module's `onGetTimeout`/`onPostRequestTimeout` handler, which apps rely on to reverse escrow or release locked funds on timeout, is never actually invoked.

`request.from`/`response.request.from` originates from `_msgSender()` at the time the original request was dispatched via `EvmHost.dispatch(DispatchPost ...)`, with no restriction that the sender be a contract [1](#0-0) . Thus an EOA (or any address that is code-less at delivery time) can be a legitimate `from`/module address for a dispatched request, making this reachable without any admin/relayer privilege — the relayer simply submits the proof for an already-dispatched cross-chain message whose originating "module" is a non-contract address.

### Impact Explanation
This diverges from the intentionally-hardened `dispatchIncoming(PostRequest, ...)` path (which was clearly patched with the `extcodesize` guard to prevent exactly this class of bug), indicating an inconsistent/incomplete fix applied to only one of four structurally identical dispatch functions. The consequence for the `GetResponse`/timeout paths is: (1) receipts/commitments are deleted, permanently precluding retries, (2) relayer/sender fees are paid out as if the message was successfully delivered, while (3) the actual application-side handler (`onGetResponse`, `onGetTimeout`, `onPostRequestTimeout`) is never executed. For apps like `IntentGatewayV2`/`HyperFungibleToken` that depend on these timeout callbacks to refund escrowed user funds or roll back cross-chain transfer state, this can result in a message being marked "handled" while the corresponding escrow release/refund logic is permanently skipped — a real freezing-of-funds outcome, not merely an accounting inconsistency.

### Likelihood Explanation
Reachability requires only that the `from` address recorded in the original outgoing request lacks deployed code at delivery time — achievable trivially since `dispatch()` records `_msgSender()` as `from` without any contract-code requirement [8](#0-7) . Any user dispatching a `GetRequest` or `PostRequest` directly from an EOA (rather than through an app contract) creates this exact condition for the return leg. No proof forgery, consensus compromise, or privileged role is needed — a relayer simply submits the (valid) proof for such a message, and the vulnerable branch executes automatically.

### Recommendation
Add the same `extcodesize`-based contract-existence check used in `dispatchIncoming(PostRequest, ...)` to `dispatchIncoming(GetResponse, ...)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)` before making the low-level `.call`, treating a code-less destination consistently (e.g., early return without deleting the commitment/receipt, so relayers cannot claim fees for undelivered callbacks and the record remains available for correct handling).

### Proof of Concept
1. An EOA (or any address that will later be code-less) calls `EvmHost.dispatch(DispatchPost{...})` directly, causing `request.from = abi.encodePacked(EOA)` to be recorded [1](#0-0) , and the request/get-request eventually times out or (for a `GetRequest`) receives a response.
2. A relayer submits a valid proof for the timeout/response; the handler invokes `EvmHost.dispatchTimeOut(PostRequestTimeout, ...)` (or `dispatchIncoming(GetResponse, ...)`).
3. Inside, `_requestCommitments[commitment]` is deleted, then `_bytesToAddress(timeout.request.from).call(...)` is executed against the EOA address, which has no code and thus returns `success = true` [9](#0-8) .
4. Because `success == true`, the fee refund to `meta.sender` executes and `PostRequestTimeoutHandled` is emitted [10](#0-9)  — even though no `onPostRequestTimeout` logic ran anywhere (there is nothing to run, since the target has no code), demonstrating that the "handled" state and fee payout are decoupled from any actual message delivery, exactly mirroring the `_externalCall` flaw in the report.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    /**

     * @param timeout - timed-out get request bundled with the relayer that submitted the timeout proof

     * @param commitment - request commitment

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
