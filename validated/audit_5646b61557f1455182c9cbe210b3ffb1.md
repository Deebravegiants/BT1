This confirms the vulnerability: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC only over that signable string [2](#0-1) . Meanwhile `shop`, `topic`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the HMAC-covered body [3](#0-2) , yet `Registry.process` trusts `request.shop` and `request.topic` for dispatch after validating only the body's HMAC [4](#0-3) .

### Title
Webhook tenant identity (`shop-domain` header) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes a webhook solely by validating an HMAC computed over the raw body [5](#0-4) , then dispatches to the app's handler using `request.shop`, `request.topic`, and `request.webhook_id`, all of which are read directly from HTTP headers that are excluded from the signed content [6](#0-5) [7](#0-6) . The equality the gem should enforce — "the shop the HMAC authenticates" == "the shop the handler acts on" — is broken because `to_signable_string` returns only `@raw_body`, never the `shop-domain`/`topic`/`webhook-id` headers [1](#0-0) .

### Finding Description
`HmacValidator.validate` proves only that *some* holder of the app's `client_secret` (i.e., Shopify) produced the given raw body [8](#0-7) . It says nothing about which shop, topic, or webhook the request headers claim to represent, because `VerifiableQuery#to_signable_string` for webhooks is exactly `@raw_body` [1](#0-0) . `Registry.process` nonetheless builds `WebhookMetadata` — the object handed to the app's business logic — directly from these unauthenticated headers: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [7](#0-6) . Any party capable of triggering (or replaying) one valid, HMAC-signed webhook delivery for a shop they legitimately control can swap the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header of that captured request to name a different, victim shop while keeping the same body and HMAC value, since the signature never covered those headers. `HmacValidator.validate` will still return `true` [9](#0-8) , and the app's handler will execute as though the event came from the victim shop.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is expected to provide via `HmacValidator`/`Registry.process`: an unprivileged actor who controls (or has captured traffic for) their own shop's webhook delivery can impersonate another merchant's shop identity to any handler registered through `ShopifyAPI::Webhooks::Registry`, for any topic (including sensitive lifecycle topics like `app/uninstalled`, `shop/redact`, or `customers/data_request`) — a cross-tenant access condition, since the "authenticated" shop and the shop the handler operates against are not proven to be the same value.

### Likelihood Explanation
Exploitation requires only the ability to replay/modify HTTP headers of one genuinely delivered webhook (trivial for anyone who runs their own store with the app installed, or who can intercept a webhook callback endpoint that doesn't enforce TLS/header integrity beyond this gem's check) — no access to `api_secret_key`, tokens, or privileged accounts is needed, and the gem itself performs no cross-check between the signed body and the header-derived shop/topic values.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (e.g., include them in `to_signable_string`, or independently verify `request.shop` against the shop associated with the specific `webhook_id`/subscription before dispatch), so `Registry.process` cannot be made to act on header values that were never covered by the signature.

### Proof of Concept
1. App has legitimate webhook subscription for `shop-a.myshopify.com`; attacker owns `shop-a` and installs the app, capturing a real webhook POST (raw body `B`, header `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: app/uninstalled`).
2. Attacker resends the same body `B`/`H` to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and matches `H` — validation succeeds [5](#0-4) .
4. The handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, causing the app to process an `app/uninstalled` (or other) event for a shop that never sent it [7](#0-6) .
