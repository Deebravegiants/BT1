### Title
`ShopifyAPI::Auth::TokenExchange.exchange_token` sends the app's `client_secret` to a shop host derived from the JWT `dest` claim without passing it through `ShopValidator.sanitize!` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` takes the `shop` used to build the outbound token-exchange request exclusively from the caller-supplied session token's `dest` claim (`jwt_payload.shop`), and unlike every other credential-issuing flow in this gem, never routes that value through `Utils::ShopValidator.sanitize!` before using it to build the HTTP host that receives `client_id`/`client_secret`.

### Finding Description
`exchange_token` decodes the session token via `JwtPayload.new(session_token)` and uses `dest_shop = jwt_payload.shop` directly to build `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, which is then used as the `Clients::HttpClient` session that determines the host receiving the POST containing `client_id`/`client_secret`: [1](#0-0) 

`JwtPayload#shop` merely strips the `"https://"` prefix off the raw `dest` claim with no domain allow-listing: [2](#0-1) 

Contrast this with every sibling credential-issuing method in the same module and neighboring files, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to send `client_secret`:
- `TokenExchange.migrate_to_expiring_token`: [3](#0-2) 
- `ClientCredentials.client_credentials`: [4](#0-3) 
- `RefreshToken.refresh_access_token`: [5](#0-4) 

`ShopValidator.sanitize!` is the gem's dedicated defense against domain-confusion / lookalike-domain values (e.g. `myshopify.com.evil.com`, userinfo-`@` tricks, unified-admin path tricks) as shown by its allow-list of `TRUSTED_SHOPIFY_DOMAINS` and rejection tests: [6](#0-5) 

`exchange_token` breaks the intended binding equality: `host receiving client_secret == a ShopValidator-attested Shopify domain`. Instead it substitutes `host receiving client_secret == raw JWT dest claim, trusted solely because the JWT signature check passed`. Signature verification (HS256 against `api_secret_key`) does confirm the token was minted by an entity holding the shared secret, but it performs no additional check that `dest` is actually a `*.myshopify.com`/trusted-domain host, and the code path bypasses the very sanitizer the codebase itself uses everywhere else specifically for that purpose. Since `session_token` is a value the calling application receives from the browser/App Bridge context and passes straight into this API, this method is one supply-chain step removed from the same class of domain-confusion protections the rest of the gem enforces uniformly.

### Impact Explanation
If `dest` can be made to resolve to an attacker-controlled or attacker-influenced host (e.g. through a lookalike domain that a weaker verification path in the surrounding app/infra might accept, or simply because this call site is the only one in the gem's OAuth-token-issuing surface that omits the allow-list check the maintainers clearly intend to apply universally), the app's `client_id`/`client_secret` would be POSTed to that host — an SSRF-with-credentials / `client_secret` exfiltration primitive (High impact per the given classification, "SSRF with the app's credentials" / "credential leakage").

### Likelihood Explanation
Exploitability strictly requires a validly-HS256-signed session token with an attacker-influenced `dest` value; the gem's own JWT decode step restricts the algorithm to HS256 and requires signature verification, which is why this is not immediately a full authentication bypass. It is nonetheless a genuine defense-in-depth regression: the same file, and every neighboring OAuth credential-issuing method, all pass the same class of shop value through `ShopValidator.sanitize!` before use, while `exchange_token` alone omits it, meaning any future weakening or edge case in JWT `dest`-claim handling (e.g. proxies, spin/shop.dev environments, or a JWT-library edge case) has no second line of defense here.

### Recommendation
Route `dest_shop` (or `jwt_payload.shop`) through `Utils::ShopValidator.sanitize!` in `TokenExchange.exchange_token` before constructing `shop_session`, matching the pattern already used in `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`.

### Proof of Concept
Conceptual PoC (illustrates the code-path asymmetry, not a demonstrated live bypass since it depends on obtaining a validly-signed token with an untrusted `dest`):
1. Obtain/produce a session token whose `dest` claim is `https://sub.myshopify.com.attacker.example` (or any value ShopValidator would reject, e.g. via `test/utils/shop_validator_test.rb`'s `test_rejects_shopify_suffix_as_subdomain_of_attacker` case), signed with the app's `api_secret_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that unlike `migrate_to_expiring_token`/`client_credentials`/`refresh_access_token`, no `ShopifyAPI::Errors::InvalidShopError` is raised, and the POST containing `client_id`/`client_secret` is sent to `https://sub.myshopify.com.attacker.example/admin/oauth/access_token`. [7](#0-6)

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
