## Analysis

The claim is substantiated by the code. `Message.Validate()` in `core/services/gateway/api/message.go` checks only length/format of `MessageID`, never uniqueness or binding to sender [1](#0-0) . Crucially, comparing this to the codebase's own `RequestCache` abstraction (used by other handlers like vault/confidentialrelay) shows the correct pattern is to key pending requests by `globalID{sender, id}`, combining `request.Body.Sender` (the ECDSA-signature-derived, unforgeable identity) with `MessageID` [2](#0-1) . The legacy capabilities `handler` deviates from this safer pattern: it stores and later resolves callbacks using `msg.Body.MessageID` alone, with no sender component, in both the write path [3](#0-2)  and the resolve path [4](#0-3) .

`HandleNodeMessage` only validates that the responding node's signature matches the `nodeAddr` it's connected as — it never cross-checks that the response actually corresponds to the original requesting client [5](#0-4) . The handler code even contains an explicit `// TODO: apply allowlist and rate-limiting here` acknowledging the missing checks at this exact insertion point [6](#0-5) . Requests reach this handler via the unauthenticated/unprivileged `gateway.ProcessRequest` → `HandleLegacyUserMessage` path with no session or per-caller isolation applied beforehand [7](#0-6) .

This confirms: an attacker who submits a legacy request with a `MessageID` colliding with a victim's in-flight `MessageID` will silently overwrite `savedCallbacks[id]`, and a subsequent DON response for that ID will be delivered to whichever callback currently occupies the slot — this is a genuine cross-user response confusion primitive, not a hypothetical/misconfiguration issue, and is reachable by an unprivileged client.

Audit Report

## Title
Unscoped, user-controlled MessageID in gateway legacy handler allows cross-user callback hijack / response confusion - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The gateway's legacy capabilities handler (`handler.HandleLegacyUserMessage`) stores each pending request's response callback in a shared map keyed solely by the client-supplied `msg.Body.MessageID`, with no binding to the requester's identity (`msg.Body.Sender`). Since `Message.Validate()` only checks `MessageID` length/format and never uniqueness or sender binding, an unprivileged client can submit a colliding `MessageID` to overwrite another in-flight client's callback entry, causing a later DON node response for the original request to be delivered to the attacker instead.

## Finding Description
`Message.Validate()` in `core/services/gateway/api/message.go` (lines 54-66) validates only that `MessageID` is non-empty, ≤128 bytes, and does not end in a null character — it performs no uniqueness or per-sender check. In `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go`, lines 411-414), the handler unconditionally writes `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}`, overwriting any existing entry under that key. When a DON node later replies with `MethodWebAPITrigger`, `handleWebAPITriggerMessage` (lines 148-161) looks up and deletes `h.savedCallbacks[msg.Body.MessageID]` and delivers the response to whatever callback is currently registered — without verifying that the callback belongs to the original requester. `HandleNodeMessage` (lines 248-255) only validates that the message's sender matches the connected `nodeAddr` (i.e., it is really from that DON node) — it performs no validation tying the response back to the correct originating user session.

This is a deviation from the codebase's own safer pattern: `RequestCache` (`core/services/gateway/handlers/common/requestcache.go`, lines 34-37, 50-63) — used elsewhere in the gateway — keys pending requests by `globalID{sender, id}`, combining the message's cryptographically-derived `Sender` with the ID, and explicitly rejects insertion if a request already exists for that key. The capabilities handler's `savedCallbacks` map has neither of these protections.

## Impact Explanation
An unprivileged client can cause its own callback to intercept another client's pending trigger response by colliding `MessageID`, since the callback storage/lookup provides no per-caller isolation and silently overwrites on collision. This is a concrete cross-user response confusion primitive reachable via the internet-facing gateway endpoint through ordinary unauthenticated/unprivileged user requests (`gateway.ProcessRequest` → `HandleLegacyUserMessage`).

## Likelihood Explanation
Moderate: the attacker must predict or observe another client's `MessageID` and win a timing race before the legitimate DON response arrives, since `MessageID` is client-supplied rather than a server-issued secret. This requires only ID collision plus timing — no elevated privileges, credentials, or host access are needed.

## Recommendation
Scope `savedCallbacks` by a composite key of `MessageID` and the request's cryptographically verified `Sender` (mirroring the `globalID{sender, id}` pattern already used in `requestcache.go`), and reject insertion when an active callback already exists for that key rather than silently overwriting it.

## Proof of Concept
1. Client A sends a legacy user message with `MessageID = "X"`; the handler stores `savedCallbacks["X"] = A's callback` (`handler.go:411-414`).
2. Before A's request completes, Client B sends its own legacy user message reusing `MessageID = "X"` (no uniqueness check exists in `Validate()`, `message.go:54-66`), overwriting `savedCallbacks["X"] = B's callback`.
3. A DON node responds for the original request under ID `"X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers A's response data to B (`handler.go:148-161`).
