### Title
Predictable, unsigned session-cookie value trusted as session identity for non-embedded apps — (`lib/shopify_api/utils/session_utils.rb`)

### Summary
For apps configured with `is_embedded: false`, `SessionUtils.current_session_id` returns the raw `shopify_app_session` cookie value verbatim as the session id used to look up a merchant's stored session/access token, with no HMAC, signature, or shop binding on that value. Because offline session ids are deterministically generated as `"offline_#{shop}"` [1](#0-0) , and the shop's `.myshopify.com` domain is public information, an attacker can construct a `Cookie: shopify_app_session=offline_<victim>.myshopify.com` header and be treated as that victim's authenticated session.

### Finding Description
The claimed binding is: `session_id == bytes authenticated under Context.api_secret_key`. In practice, for the non-embedded branch:

```
lib/shopify_api/utils/session_utils.rb:31-36
else
  raise Errors::CookieNotFoundError, ... unless cookies && cookies[SESSION_COOKIE_NAME]
  cookie_session_id(cookies)
end
```
`cookie_session_id` simply returns `cookies[SESSION_COOKIE_NAME]` unchanged [2](#0-1) . There is no MAC, no signature check, and no comparison against a server-held secret — the raw client-supplied bytes become the session id used by the calling app to fetch a `Session` (and its access token) from session storage.

The cookie value is originally set by `Auth::Oauth.validate_auth_callback` to `session.id` after a legitimate OAuth exchange [3](#0-2) . For offline sessions, `session.id` is computed by `SessionUtils.offline_session_id(shop)` as the deterministic string `"offline_#{shop}"` [1](#0-0)  — a value derived entirely from the public shop domain, with no random or secret component, and no cryptographic tie to `Context.api_secret_key`.

Because the identifier space is guessable (any known `*.myshopify.com` domain), and the lookup mechanism trusts the cookie byte-for-byte, an attacker who has installed the app on their own shop (satisfying "unprivileged, self-service" access) can send raw HTTP requests with a forged `Cookie` header naming any other target shop, e.g.:

```
Cookie: shopify_app_session=offline_victim-shop.myshopify.com
```

`current_session_id` returns `"offline_victim-shop.myshopify.com"` unchanged, which the host app then uses to load the victim's stored session (including their offline access token) from its session storage, and proceeds to serve the request using the victim's credentials.

None of the existing guards intervene here: `HmacValidator.validate` only applies to the OAuth callback query string, not to authenticated-request cookies; `ShopValidator.sanitize!` validates shop domain format, not session ownership; the JWT `aud`/`sub` checks in `JwtPayload` are only exercised in the embedded branch (`Context.embedded?` true), which is explicitly bypassed here since `is_embedded: false`; and `Context.embedded?` / `Context.private?` do not gate the cookie branch's trust model at all.

### Impact Explanation
Any attacker who knows (or can enumerate/guess) a target shop's `.myshopify.com` domain — which is not secret — can forge the session cookie and have the app load and act on the victim merchant's stored session and access token. This is a cross-tenant access vulnerability: one shop's unprivileged client can read or trigger API operations bound to another merchant's offline access token, matching the Critical cross-tenant access category. It is fully repeatable against any shop whose domain the attacker knows and whose app installation flow this gem backs, requiring no interaction with the victim.

### Likelihood Explanation
Preconditions: the host app must be configured `is_embedded: false` (a supported, documented configuration) and use cookie-based session identification as designed by this gem's `SessionCookie`/`SessionUtils` flow. The attacker cost is trivial — crafting an HTTP request with a chosen `Cookie` header, no secrets or prior victim interaction needed, and the target shop domain is ordinarily public/discoverable. This makes the attack highly feasible and repeatable at will.

### Recommendation
Do not use the raw, predictable session id as the trusted cookie payload. Instead, store a cryptographically random, unguessable session identifier (or an HMAC-signed/encrypted value keyed by `Context.api_secret_key`) in the cookie, and validate that MAC/signature in `current_session_id` before trusting the cookie's contents as an identity.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (conceptual addition)
def test_cookie_session_id_is_guessable_offline_id
  ShopifyAPI::Context.setup(..., is_embedded: false)
  victim_shop = "victim-shop.myshopify.com"
  forged_cookie_value = "offline_#{victim_shop}"  # attacker constructs this without any secret

  session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(
    nil,
    { "shopify_app_session" => forged_cookie_value },
    false,
  )

  # The attacker-chosen value is returned verbatim and is identical to the
  # real offline session id computed by offline_session_id(victim_shop),
  # with no HMAC/signature check ever applied.
  assert_equal(
    ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop),
    session_id,
  )
end
```
This demonstrates the equality `current_session_id(cookie) == offline_session_id(shop)` holds for attacker-supplied bytes with no authentication step in between, confirming the session id is trusted without being derived from any value authenticated under `Context.api_secret_key`.
