### Title
Rounding-down in ERC20→local decimal conversion silently truncates dust to zero on `on_accept`/`on_timeout`, permanently burning user funds - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` truncates via integer division when converting an incoming ERC20 `amount` (expressed in `erc_decimals`) down to the pallet's local asset `decimals`. Whenever `amount` is not an exact multiple of `10^(erc_decimals - local_decimals)`, the fractional remainder is silently discarded rather than rejected, and whenever `amount < 10^(erc_decimals - local_decimals)` the minted/transferred `amount` rounds all the way to zero. [1](#0-0) 

### Finding Description
Cross-chain sends are only round-trip-safe when the ERC20 amount is produced by the pallet itself via `convert_to_erc20` (which always yields an exact multiple of the scaling factor). However, `on_accept` unconditionally trusts any `message.amount` delivered by a relayed POST request from a registered `HyperFungibleToken`/`WrappedHyperFungibleToken` contract on the source EVM chain — that amount is fully attacker/user controlled from an ordinary, unprivileged `send()` call on the EVM side. [2](#0-1) 

`register_token`/`update_token` only guarantee `erc_decimals >= local_decimals` (never equality), so a nonzero decimal gap is a normal, expected configuration (e.g. an 18-decimal EVM token bridging to a 6- or 12-decimal Substrate asset). [3](#0-2) 

With that gap in place, `convert_to_balance` performs plain integer division with no remainder check and no minimum-amount guard:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
``` [4](#0-3) 

Any user who calls `send()` on the EVM-side `HyperFungibleToken`/`WrappedHyperFungibleToken` contract (burning/locking real value there) with an `amount` smaller than `10^(erc_decimals - local_decimals)`, or not an exact multiple of it, causes `on_accept` to mint/transfer a truncated (possibly zero) amount to the beneficiary on the destination chain. The same unchecked division is reused in `on_timeout` for refunds, so a timed-out message with a sub-threshold amount also refunds less than was originally escrowed — permanently destroying the difference, since the EVM-side tokens were already burned/locked and there is no path to reclaim the truncated remainder. [5](#0-4) 

### Impact Explanation
This is a fund-loss bug reachable by any ordinary token holder, not just malicious governance/admin: real value burned or escrowed on one chain does not correspond to what is credited on the other. For amounts under the scaling threshold, users lose 100% of their transfer with the message still succeeding (no revert), i.e. a permanent, silent freezing/destruction of user funds. It also affects the timeout/refund path, so even the safety-net refund can under-deliver relative to what was actually escrowed.

### Likelihood Explanation
The decimal gap (`erc_decimals > local_decimals`) is an explicitly supported and expected configuration (confirmed by the `ErcDecimalsBelowLocal` check only enforcing `>=`, and by `BridgeToken.sol`'s own documented 18-vs-12-decimal scaling). Any unprivileged EVM user choosing (deliberately or accidentally) a small `amount` when calling `send()` triggers the truncation; no special privileges, races, or governance actions are required.

### Recommendation
In `convert_to_balance`, reject (return an error) whenever the division has a nonzero remainder or the result is zero for a nonzero input, instead of silently truncating:
```rust
let divisor = U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32));
if !value.is_zero() && value % divisor != U256::zero() {
    return Err(...); // reject dust / non-exact amounts
}
```
Apply the same guard on both the `on_accept` and `on_timeout` call sites so processing fails safely (and the request can be retried/resolved) rather than delivering a truncated, unbacked amount.

### Proof of Concept
1. Register a token with `local_decimals = 6` on Substrate and `erc_decimals = 18` on an EVM chain via `register_token` (passes the `erc_decimals >= local_decimals` check).
2. On the EVM chain, an ordinary user calls `HyperFungibleToken.send()` with `amount = 500_000_000_000` (i.e. `5 * 10^11`, which is less than `10^(18-6) = 10^12`). Tokens are burned/locked in the EVM contract and an ISMP POST request is dispatched.
3. When the relayer delivers the request, `on_accept` calls `convert_to_balance(500_000_000_000, 18, 6)` → `500_000_000_000 / 10^12 = 0` (integer division), minting/transferring `0` to the beneficiary while the message is accepted successfully.
4. The user's EVM-side tokens are gone; the Substrate-side beneficiary receives nothing — a permanent loss of the full transferred amount, with no revert or error surfaced anywhere in the pipeline.
