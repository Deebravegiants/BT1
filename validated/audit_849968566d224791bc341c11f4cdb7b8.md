Found a genuine analog of the reported bug class: the webhook `shop` identity used for tenant dispatch is not the field covered by the HMAC signature.

### Title
Webhook `shop` domain used for tenant identification is not covered by HMAC verification - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed bytes. This breaks the intended binding: `bytes verified == bytes used to identify the tenant`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC validation performed by `HmacValidator.validate` (used generically for any `VerifiableQuery`, including `Request`) only checks that the HMAC matches the signable string, i.e. `@raw_body`: [2](#0-1) 

However, `Request#shop` — the value used by `Registry.process` to identify which merchant/tenant the webhook belongs to and to invoke the registered handler with — is pulled straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is completely outside the HMAC-signed bytes: [3](#0-2) 

This is exactly the bug class described in the report: a field that is *acted on* (here, the tenant-identifying `shop`) is not covered by the same integrity check (`HMAC`) that is verified before trusting the request. Verifying `hmac-sha256` over the body proves the request body genuinely came from Shopify's webhook signer using `Context.api_secret_key`, but it proves nothing about the `shop-domain` header value, which an attacker who can reach the webhook endpoint (e.g., by replaying a legitimately-signed body captured from their own shop, or from any endpoint that just forwards attacker-controlled headers alongside a validly-signed body) can freely set to any other merchant's domain.

`Registry.process` uses `request.shop` to call the handler: [4](#0-3) 

If the host application uses this `shop` value to select tenant-scoped data, sessions, or database records (which is the documented purpose of this field per the resource-based topic handler pattern), an attacker in control of the delivery request (for instance, someone who can trigger identical, validly-signed webhook payloads for their own shop, then relay/replay them with a substituted `shop-domain` header to the app's webhook endpoint) can cause the app to process the payload under a different tenant's identity — a cross-tenant confusion at the identity-binding layer.

### Impact Explanation
This maps to the Critical category "cross-tenant access": the `shop` value returned by an HMAC-"verified" `Request` is not actually authenticated, so any code path that trusts `request.shop` as an authenticated tenant identifier is relying on unverified data. Since many Shopify apps use the webhook's shop domain to look up/act on the correct merchant's session or data, forging this header (while reusing or crafting a validly-HMAC'd body) breaks the tenant boundary the gem is expected to enforce.

### Likelihood Explanation
Exploitation requires the attacker to produce a request whose body/HMAC pair is valid (trivial if the attacker owns any Shopify shop with the app installed and can trigger a webhook for their own data, since bodies for many topics are attacker-influenced or predictable) and then deliver it to the app's endpoint with an arbitrary `shop-domain` header — something fully within reach of any unprivileged internet user/merchant, not requiring `api_secret_key` or any credential. The main uncertainty is whether the host application's webhook endpoint enforces any additional binding (e.g., matching URL path to shop) before calling into this gem, which is outside this gem's control; this gem's own `HmacValidator`/`Request` API provides no such binding.

### Recommendation
Include the shop-domain (and ideally topic and webhook-id) in `to_signable_string`, or otherwise document/enforce that `Request#shop` must not be treated as authenticated unless independently corroborated (e.g., cross-checked against a known session's shop looked up via a value that *is* covered by the HMAC, or via the `X-Shopify-Webhook-Id` combined with idempotent, previously-registered expectations). At minimum, the gem's documentation and `HmacValidator` should make explicit that only `@raw_body` is verified and that header-derived fields like `shop` require separate validation by the integrating application.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook topic, capturing the raw body and its valid `x-shopify-hmac-sha256` value (computed by Shopify using the app's real `client_secret`, so it passes `HmacValidator.validate`).
2. Attacker crafts a new HTTP request to the app's webhook endpoint using the exact same `raw_body` (so the HMAC still validates), but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)` — which passes because only the body is checked — then dispatches to the topic handler with `request.shop == "victim-shop.myshopify.com"`, per [3](#0-2) , even though nothing about that shop value was ever cryptographically verified.
