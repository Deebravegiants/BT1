Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then forwards the unauthenticated `shop-domain` (or `x-shopify-shop-domain`) header value to the app's handler as the trusted tenant identifier. Because the shop identity is not bound to the HMAC-signed content, any request that carries a body+HMAC pair valid for the shared `api_secret_key` can be attributed to an arbitrary shop, breaking the identity binding `shop_header == shop_that_signed_body`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` value is read from a separate, unsigned header: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively against `to_signable_string` (the body), never touching headers such as `shop-domain`, `topic`, or `webhook-id`: [3](#0-2) 

`Registry.process` performs this HMAC check and, once it passes, immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) as authenticated tenant/context data passed straight into the app's handler: [4](#0-3) 

The gem's own documentation instructs apps to use `data.shop` directly as the tenant key for follow-up work (e.g., background job dispatch), reinforcing that this field is treated as authoritative: [5](#0-4) 

The identity binding that should hold is: **the `shop-domain` header value == the shop whose secret produced the HMAC over this exact body**. Because the HMAC is computed with the app-level `api_secret_key` (shared across every shop that has installed the app) and covers only the body, that binding is never enforced. Any body+HMAC pair that is valid for the app's secret (e.g., one legitimately produced by Shopify for *some* shop that installed the app) remains valid when replayed with a different `shop-domain` header value, since the header is not part of the signed material.

### Impact Explanation
This is a cross-tenant identity confusion: a webhook payload legitimately generated (and signed) for Shop A can be delivered to the app's webhook endpoint with the `shop-domain` header rewritten to Shop B, and it will pass HMAC validation and be processed as if it originated from Shop B. Handlers that key their database writes, cache invalidation, uninstall/deprovisioning logic, or entitlement changes off `data.shop` will act on the wrong tenant's records using another tenant's payload content — a cross-tenant access/integrity violation, matching the "Critical - cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. This is realistically achievable by any merchant who has installed the app themselves (they legitimately receive real webhooks with valid HMACs for their own shop, since the same app-level secret signs webhooks for every shop that installs it) and can then replay that captured body/HMAC to the app's public webhook endpoint with an arbitrary `shop-domain` header. No access to another tenant's credentials, TLS interception, or the app's `client_secret` disclosure is required — only the ability to send an HTTP request to the app's own webhook route, which is by design internet-reachable.

### Recommendation
Bind the identity fields to the authenticated content instead of trusting bare headers:
- Include `shop-domain`/`shop`, `topic`, and `webhook-id` in the signable string validated by `Utils::HmacValidator`, or otherwise cryptographically bind them to the payload signature.
- Alternatively/additionally, require per-shop secrets (or validate that the resolved shop is one for which the app currently holds an active, matching offline session) before dispatching `WebhookMetadata` to handlers, rather than trusting the header value unconditionally.
- Document to consuming apps that `data.shop` must not be treated as fully authenticated unless the header is bound to the signature.

### Proof of Concept
1. App installs on Shop A and Shop B, sharing one `api_secret_key`.
2. A legitimate webhook for Shop A arrives: `raw_body = '{"id":123,...}'`, header `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw_body>`.
3. Attacker (a user who legitimately receives Shop A's webhooks, e.g. the Shop A merchant) replays the exact same `raw_body` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) recomputes the HMAC over `raw_body` only, matches the supplied `hmac`, and returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and Shop A's body, then invokes the app's handler, which believes this event pertains to Shop B.
