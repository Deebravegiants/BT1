### Title
Unchecked ERC20 transfer return value in Tron `IntentGatewayV2` permits silent fund loss on escrow withdrawal and dust sweep - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports and attaches `SafeERC20` to `IERC20` [1](#0-0)  but its outbound payout paths — `withdraw()` and the `SweepDust` branch of `onAccept()` — bypass `safeTransfer` entirely and instead perform a raw low-level `.call()` with a manually encoded `IERC20.transfer.selector`, checking only that the call itself did not revert (`success`), never decoding/validating the returned boolean.

### Finding Description
In `withdraw()`, escrowed token payouts to a beneficiary use: [2](#0-1) 
and fee redemption uses the same unchecked pattern: [3](#0-2) 

The `SweepDust` handler inside `onAccept` has the identical pattern: [4](#0-3) 

`token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only reverts if the target has no code or the call itself throws; for a non-standard ERC20 that returns `false` on failure (instead of reverting) — a well-known real-world token pattern — `success` is still `true` because the low-level call completed normally, so the code proceeds as if the transfer succeeded. This is precisely the class of bug the referenced report flags (using the wrong/legacy interface path instead of the vetted one — here, hand-rolled `.call` instead of `SafeERC20.safeTransfer`, which explicitly checks the returned success boolean via `Address.verifyCallResult`/`SafeERC20._callOptionalReturn`).

By contrast, the canonical EVM `IntentGatewayV2` in this same repo correctly uses `safeTransferFrom`/`safeTransfer` for these operations, confirming this is a Tron-specific regression rather than an intentional design choice: [5](#0-4) 

`withdraw()` is reached from `onAccept` for `RedeemEscrow`/`RefundEscrow` kinds after `authenticate(incoming.request)`, i.e. via a relayed, source-authenticated ISMP POST request — exactly the "relayed proof / dispatched request" unprivileged path in scope: [6](#0-5) 

### Impact Explanation
Once the low-level call "succeeds" (even though the token transfer silently failed), the contract:
- Decrements internal escrow accounting `_orders[body.commitment][token] -= amount` and sets `_filled[body.commitment] = beneficiary`, permanently marking the order as resolved.
- Emits `EscrowReleased`/`EscrowRefunded` and deletes the fee entry, even though the beneficiary received nothing.

Because the commitment is marked filled/refunded, the withdrawal path cannot be retried, so the escrowed tokens become permanently stranded in the contract while the intended recipient receives zero funds — a permanent freezing/loss of user or solver funds for any ERC20 that returns `false` instead of reverting on transfer failure (e.g. paused/blacklisted transfer attempts on tokens implementing that convention, or any token whose `transfer` can return `false`).

### Likelihood Explanation
This triggers whenever any listed input/output/fee token used with the Tron `IntentGatewayV2` follows the "return false" failure convention and a transfer condition causing failure occurs (e.g., recipient blacklisted, paused token, insufficient balance edge cases). Given Tron's TRC20 ecosystem includes tokens with non-reverting failure semantics, and this path executes on every relayer-delivered `RedeemEscrow`/`RefundEscrow`/`SweepDust` message, likelihood is realistic rather than purely theoretical, warranting Medium severity consistent with the analog report.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout sites in `withdraw()` and the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(beneficiary, amount)`, using the `SafeERC20` library already imported and used elsewhere in this same contract, so failed transfers revert instead of being silently accepted.

### Proof of Concept
1. Configure (or have governance register via `NewDeployment`) an output/fee token whose `transfer()` implementation returns `false` on failure without reverting (a real, non-hypothetical ERC20 pattern).
2. An order is created and escrowed normally in `IntentGatewayV2`.
3. A relayer delivers a `RedeemEscrow`/`RefundEscrow` POST request that passes `authenticate()`; inside `withdraw()`, the token's `transfer` call to `beneficiary` returns `false` (e.g., beneficiary is blacklisted or contract-side condition fails) but the low-level `.call` itself does not revert, so `success == true`.
4. `_orders[body.commitment][token] -= amount` executes, `_filled[body.commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — the contract believes payout is complete.
5. The beneficiary never received the tokens, and because the order commitment is now marked filled, there is no path to retry or reclaim the escrowed amount, resulting in a permanent loss of the escrowed funds. [7](#0-6)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

                ++i;
            }
        }
