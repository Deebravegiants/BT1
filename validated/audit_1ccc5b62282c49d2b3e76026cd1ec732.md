## Title
Webhook shop identity is not bound by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook using an HMAC computed **only over the raw request body**, but then hands the handler a `shop` value taken from an **unauthenticated HTTP header**. Because the `shop` field is never included in the signed payload, any party who can obtain one validly-signed webhook (e.g., by installing the app on a shop they control) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, causing the app to process the webhook as if it belonged to a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so `hmac` is verified strictly against the body bytes. The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` value to the handler as the tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `HMAC(secret, raw_body)` matches; it has no knowledge of, and does not cover, the shop header: [4](#0-3) 

This breaks the identity binding `shop authenticated by HMAC == shop delivered to handler`. The gem's shared secret (`Context.api_secret_key`) is identical for every shop that installs the app — it is not per-tenant. Consequently, an attacker who legitimately installs the target app on their own shop can capture one valid `(raw_body, hmac)` pair from a real webhook delivery, then send a forged HTTP request to the app's webhook endpoint reusing that exact `raw_body`/`hmac`, but with the `shop-domain` header changed to any other shop domain (e.g. a victim's). `HmacValidator.validate` still returns `true` because it only checks the body, and `WebhookMetadata.new(... shop: request.shop ...)` is constructed with the attacker-chosen shop: [5](#0-4) 

Any host application that trusts `data.shop` from `WebhookMetadata` to select which tenant's record to read, update, or delete (a very common pattern, since many webhook topics/bodies do not embed the shop domain themselves) will act on the wrong tenant's data based on attacker-controlled input.

### Impact Explanation
This crosses a tenant boundary: a party with only their own low-privilege app installation can cause the library to authenticate a webhook payload as originating from an arbitrary other merchant. Depending on how the host app uses `WebhookMetadata#shop` (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or any topic used to gate per-shop state), this can lead to cross-tenant state corruption, unauthorized data deletion, or disclosure — matching the "cross-tenant access" Critical impact category, since the gem itself provides no protection and silently vouches for an unauthenticated field as if it were verified.

### Likelihood Explanation
Likelihood is high for any app that has at least one merchant installation reachable by the attacker (including the attacker's own store) and that relies on `WebhookMetadata#shop` for tenant scoping without independently cross-checking it (e.g. against the shop stored for the specific `webhook_id`, or requiring an equality with an authenticated session-derived shop). No secret material or privileged access is required beyond a normal, self-service app installation.

### Recommendation
Bind the shop domain into the material that is actually verified, or otherwise cryptographically tie it to the signed body, e.g.:
- Include the `shop` header (and other identifying headers such as `webhook-id`/`api-version`) in `to_signable_string`, matching what is verified, or
- Require callers to supply the shop associated with an active installation/session and compare it against `request.shop`, rejecting mismatches, before invoking the handler in `Registry.process`.
Document clearly that `WebhookMetadata#shop` must not be trusted as an authenticated tenant identifier unless one of the above is done.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and captures a real webhook delivery, e.g. for `app/uninstalled`, recording the raw body `B` and the header `X-Shopify-Hmac-Sha256: H` (a valid HMAC over `B` computed with the app's shared secret).
2. Attacker sends a POST request directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim.myshopify.com` (changed)
   - Header `x-shopify-topic: app/uninstalled` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and performs whatever tenant-scoped action the app implements (e.g., marking `victim.myshopify.com` as uninstalled/deactivated), even though the actual Shopify-originated request was for `attacker.myshopify.com`.
