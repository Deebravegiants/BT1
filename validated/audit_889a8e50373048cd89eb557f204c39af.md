### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only (`to_signable_string` returns `@raw_body`), while the `shop` (and `topic`/`webhook_id`) values used to route and attribute the webhook are taken from HTTP headers that are never included in the HMAC computation. `Registry.process` accepts any request whose body/HMAC pair is valid for the app's shared `api_secret_key`, then trusts whatever `shop` header accompanies that body to identify the tenant.

### Finding Description
The equality this code implicitly assumes is: `hmac_valid(raw_body) == authenticated(shop_header)`. In fact `HmacValidator.validate(request)` at [4](#0-3)  only proves that `raw_body` was signed with `Context.api_secret_key` — the single secret shared by the app across *all* installed shops, per `HmacValidator.validate_signature` in `lib/shopify_api/utils/hmac_validator.rb`. It proves nothing about which shop's header accompanies that body.

Because `shop`, `topic`, and `webhook_id` are read straight from HTTP headers (`shopify_header("shop-domain")`, etc.) that are excluded from `to_signable_string`, any party capable of triggering delivery of one legitimate, validly-signed webhook (e.g., installing the app on their own shop and receiving a real webhook for it) can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with a different `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (it never looks at the header), so `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen value while `body` remains the attacker's own (valid) payload.

### Impact Explanation
Any host application that uses `request.shop`/`WebhookMetadata#shop` from this gem to decide which merchant's records a webhook payload applies to (the documented, expected usage pattern) can be made to apply attacker-controlled body content under a victim shop's identity — a cross-tenant confusion in the app's data model, achieved purely by header manipulation with no possession of the victim's credentials.

### Likelihood Explanation
Requires only the ability to send an arbitrary raw HTTP request to the app's public webhook endpoint together with one valid `(body, hmac)` pair, which is trivially obtainable by installing the app on any shop the attacker controls and capturing one real inbound webhook.

### Recommendation
Bind the shop identity into the signed payload verification path rather than trusting it as an unauthenticated header: e.g., verify the received webhook against the specific shop's stored offline session (fetch the shop's own access-token/secret context) before trusting `request.shop`, or otherwise cryptographically bind topic/shop into the material that is HMAC-verified, and reject webhooks whose header-derived `shop` does not match an active installation the app already recognizes for that payload.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, receives a real webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` with the app's `api_secret_key`), header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical `B`/`H` pair to the same webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and matches — it never inspects the `shop` header [4](#0-3) .
5. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's payload>, ...)`, so the app processes attacker-controlled data as if it originated from the victim tenant [6](#0-5) .
