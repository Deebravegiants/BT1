### Title
Unrestricted `EmporiumOperation.endpoint.call` lets an attacker drain any stray token balance held by EmporiumUpgradeable, bypassing the balance-change invariant entirely - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes an attacker-crafted list of `EmporiumOperation`s (`stack.ops`, decoded from `circomData.externalActionData.externalActionMetadata`) via raw `op.endpoint.call(op.callData)`, with the Emporium contract itself as `msg.sender`, and the only restriction is blocking two specific function selectors. The post-execution balance/UTXO reconciliation loop only checks tokens present in `circomData.erc20TokenAddresses`, so an attacker can target a token that is *not* included in that array and directly `transfer()` (or `approve()`) any balance the Emporium contract happens to hold of that token straight to themselves, with zero accounting, zero UTXO creation, and zero revert.

### Finding Description
The invariant that should hold is: for every token that leaves the Emporium contract during a `runAction` call, `balanceChange[token] == -deltaAmountChanges[token] (if negative) + utxoAmount[token]`, checked only for `token ∈ circomData.erc20TokenAddresses` [6](#0-5) . This equation is silently vacuous for any token outside that array — no balance is even sampled for it, before or after.

The `stack.ops` array, however, is fully attacker-controlled through `circomData.externalActionData.externalActionMetadata` (decoded via `abi.decode(..., (EmporiumStack))` [7](#0-6) ) and each operation's `endpoint`/`callData`/`value` is completely decoupled from `circomData.erc20TokenAddresses`. In "Stateless Interaction" mode, the only calldata check blocks the `callHinkalWallet`/`doSendToRelay` selectors [8](#0-7) ; any other call, including `IERC20(token).transfer(attacker, amount)` or `IERC20(token).approve(attacker, type(uint256).max)` on any ERC20 contract, executes with the Emporium proxy as caller.

Exploit call: attacker submits `Hinkal.transact` with `circomData.externalActionData.externalActionId` set to Emporium, `circomData.erc20TokenAddresses` containing only tokens with `amountChanges == 0` (so both the inner and outer balance equations trivially hold `0 == 0 + 0`), and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` (skipping the EIP-712 signature check entirely, per `verifyWallet` [5](#0-4) ) and a single op `{ endpoint: strandedToken, invokeWallet: false, value: 0, callData: transfer(attacker, strandedTokenBalance) }`. Since `strandedToken` is absent from `circomData.erc20TokenAddresses`, `handleOut` is never invoked for it, `utxoSet` is returned empty (`utxoAmount == 0` for every tracked token), and the outer `Hinkal.transact` balance check also passes trivially for the tokens it does track [9](#0-8) . The stray/stranded balance (leftover dust from prior swaps, rounding, mis-sent tokens, or ETH refund remnants sitting in the Emporium proxy) leaves the contract straight to the attacker's address with no counted output, breaking the invariant `tokens leaving an action in a tx == -deltaAmountChanges Hinkal sent it that tx`.

### Impact Explanation
Direct theft of any ERC20 (or ETH, via `op.value`/native calls) balance the Emporium contract holds that is not explicitly listed by the attacker in `circomData.erc20TokenAddresses` for that call. This is repeatable — any time the Emporium contract accumulates a balance of a token (dust, rounding remainder, a stuck/failed prior operation, or a mistaken transfer), any unprivileged attacker can drain it in one transaction with no signature, no privileged role, and no proof constraint blocking it (the circuit only constrains `amountChanges`/UTXOs for the entries the attacker chooses to declare). This matches "Critical: direct theft of shielded or in-flight user funds" since any user/protocol funds resting in the shared Emporium contract are exposed.

### Likelihood Explanation
Preconditions: the Emporium contract must hold a non-zero balance of some token at the time of the attack. This is plausible given normal operational dust (rounding in swaps, partially executed multi-op sequences, refunds, or simply another user's transaction leaving value momentarily before its own `handleOut` runs — though same-tx reentrancy is blocked by `nonReentrant` on `Hinkal.transact`, cross-transaction dust and third-party mis-sent tokens remain realistic). Attacker cost is a single transaction with a self-crafted proof only over the entries they choose to include (Hinkal's circuit does not constrain what `stack.ops` may contain, since `externalActionMetadata` is treated as opaque calldata). This is fully repeatable each time stray balance accumulates.

### Recommendation
Restrict `stack.ops[i].endpoint` and the effective selector set so that arbitrary ERC20 `transfer`/`approve`/`transferFrom` calls cannot be issued against tokens outside `circomData.erc20TokenAddresses`, or require that `handleOut`'s post/pre balance snapshot cover the *union* of `erc20TokenAddresses` and every `op.endpoint` touched, reverting if any untracked token's Emporium balance decreases. Alternatively, sweep/zero out the Emporium contract's balance for any token after each `runAction` call (routing leftover dust back through the same UTXO-accounting path) so no exploitable residue can persist between transactions.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20 `Stranded`, and seed `Stranded.transfer(emporiumAddress, 1000e18)` directly (simulating dust/mistaken transfer) — no Hinkal transaction involved.
2. Craft `CircomData` with `erc20TokenAddresses = [someOtherToken]`, `amountChanges = [0]`, `externalActionData.externalActionId = <emporiumId>`, and `externalActionMetadata = abi.encode(EmporiumStack({v:0, r:0, s:0, signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(Stranded), invokeWallet:false, value:0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 1000e18)})], maxFee:0, deadline: block.timestamp+1000}))`.
3. Generate a locally-produced valid proof for the trivial `someOtherToken` leg (`amountChanges[0]==0`, no UTXO in/out) and call `Hinkal.transact` from `attacker`.
4. Assert before/after: `Stranded.balanceOf(attacker)` increases by `1000e18` while `Hinkal.transact` succeeds, no `UTXO` was emitted for `Stranded`, and `utxoSet.length == 0`/`utxoAmount == 0` — i.e. `tokens leaving action (1000e18 of Stranded) != -deltaAmountChanges (0)`, proving the invariant is broken.
