### Title
Withdraw permanently reverts and locks a user's LP position if either coin or pc destination account is frozen by its mint's freeze authority - (File: program/src/processor.rs, function `process_withdraw`)

### Summary
`process_withdraw` unconditionally issues **two** SPL token transfers — one for `coin_amount` and one for `pc_amount` — in the same atomic instruction, both required to succeed for the LP burn and pool-state update to occur. If either the coin-side or pc-side mint has an active freeze authority (e.g., a stablecoin such as USDC) and the user's destination token account is frozen, the entire `Withdraw` instruction fails, and there is no alternate code path in the program allowing the user to redeem their LP tokens for only the non-frozen side.

### Finding Description
`process_withdraw` computes `coin_amount` and `pc_amount` pro-rata to the LP amount being redeemed, and then performs both transfers back-to-back: [1](#0-0) 

Both `Invokers::token_transfer_with_authority` calls invoke the SPL Token program's `Transfer` instruction directly via CPI: [2](#0-1) 

The SPL Token program will reject a `Transfer` if the destination token account has been frozen by its mint's freeze authority. Because both transfers, the LP burn, and the `amm.lp_amount` update happen in a single all-or-nothing instruction, a `Transfer` failure on either side (e.g. the pc-side USDC destination account being frozen) causes the whole instruction — including the otherwise-unblocked coin-side transfer and the LP burn — to revert. There is no partial-withdraw or single-sided-withdraw instruction elsewhere in the program (`process_deposit`, the four swap handlers, and `process_withdrawpnl` all follow the same "both sides in one shot" pattern), so the user has no alternative mechanism to redeem their LP position once one destination account is frozen.

### Impact Explanation
A user whose coin or pc destination token account becomes frozen (by the mint's freeze authority, which is external to and unprivileged with respect to this program) permanently loses the ability to call `Withdraw` on their LP position. Since `Deposit`/`Withdraw`/swap paths never let a user redeem LP for a single asset, their pool share (and the underlying coin+pc value it represents) is frozen indefinitely — a permanent freezing of user funds, consistent with the reported bug class of an all-or-nothing multi-asset withdrawal reverting entirely due to one blocked transfer.

### Likelihood Explanation
Any pool that includes a token with freeze-authority semantics (common for centralized stablecoins) is exposed. The condition (the user's own destination ATA becoming frozen) is outside the attacker's control but is a realistic real-world event (e.g., regulatory blacklisting, exchange compliance action) reachable purely by an ordinary LP calling the public `Withdraw` instruction with their own accounts — no privileged signer or non-default build is required.

### Recommendation
Provide a way for a user to withdraw only the non-frozen side of their proportional entitlement (e.g., allow skipping one transfer with an explicit flag and adjusting `lp_amount`/vault accounting accordingly), or allow a permissioned/emergency path to burn LP and credit only the transferable asset while recording the remainder as a claimable balance instead of atomically requiring both transfers to succeed.

### Proof of Concept
1. A pool is created with `coin_mint` = USDC (or any SPL token with an active freeze authority) and `pc_mint` = SOL-wrapped token.
2. Alice deposits and receives LP tokens via `Deposit`.
3. USDC's freeze authority freezes Alice's USDC associated token account.
4. Alice calls `Withdraw` with her LP amount; `process_withdraw` computes non-zero `coin_amount` (USDC) and `pc_amount`, then calls `Invokers::token_transfer_with_authority` for the coin side, which fails because her destination account is frozen.
5. The whole instruction reverts: LP tokens are not burned, `amm.lp_amount` is unchanged, and the pc-side amount (which she could have received) is also not transferred.
6. Alice has no way to redeem her LP tokens for the pool's assets as long as her USDC account remains frozen, since no partial-withdraw instruction exists in `program/src/processor.rs`.

    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
