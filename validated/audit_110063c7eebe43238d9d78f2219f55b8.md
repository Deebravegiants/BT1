## Custody analog found: `override_threshold` can go stale relative to `num_signatures_required`, silently disabling the multisig timelock

### Title
Multisig timelock override quorum is not re-validated against `num_signatures_required`, allowing owners to bypass the configured delay after a routine signature-threshold increase - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`multisig_account::upsert_timelock_internal` enforces `override_threshold > num_signatures_required` only at the moment the timelock is configured. `update_signatures_required` (and the combined `add_owners_and_update_signatures_required` / `swap_owners_and_update_signatures_required`) can subsequently raise `num_signatures_required` without touching or re-validating the existing `MultisigAccountTimeLock.override_threshold`. Once `override_threshold <= num_signatures_required`, the timelock's "early execution" path becomes trivially satisfiable every time normal quorum is met, defeating the delay that owners configured to protect custody-relevant multisig transactions (e.g., withdrawing assets, rotating a resource account's ownership, or reassigning ownership over code objects controlled by the multisig).

### Finding Description
`upsert_timelock_internal` [1](#0-0)  validates:
```
override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required
```
at configuration time only.

`can_execute_with_timelock` [2](#0-1)  allows immediate execution, bypassing the elapsed-time wait, whenever `num_approvals >= override_threshold`.

`validate_multisig_transaction` (the VM prologue for multisig execution) checks quorum and timelock as two independent asserts [3](#0-2) :
```
assert!(num_approvals >= num_signatures_required(...), ENOT_ENOUGH_APPROVALS);
assert!(can_execute_with_timelock(...), ETIMELOCK_NOT_EXPIRED);
```
`update_signatures_required` (and the owner-add/swap variants that also bump signatures required) route through `update_owner_schema` and mutate `MultisigAccount.num_signatures_required` [4](#0-3)  with no reference to, or re-check of, `MultisigAccountTimeLock.override_threshold`.

Because these are independent resources (`MultisigAccount` vs. `MultisigAccountTimeLock`) with no cross-invariant enforcement outside the one-time `upsert_timelock_internal` check, an owner-approved (but not necessarily malicious/privileged-governance) call to `update_signatures_required` that raises `num_signatures_required` to or above the existing `override_threshold` silently breaks the invariant `override_threshold > num_signatures_required`. From that point on, `can_execute_with_timelock` returns true as soon as ordinary quorum (`num_approvals >= num_signatures_required`) is met, because `num_approvals >= num_signatures_required >= override_threshold`. The timelock delay - the custody control the owners configured specifically to gate high-value/high-risk multisig-controlled transactions (fund transfers, resource-account signer capability use, code-object or fungible-asset owner reassignment) - is rendered a no-op without any explicit disable action or warning.

### Impact Explanation
This breaks a custody invariant that the multisig's own owners rely on: "any transaction requires both quorum AND a cooling-off `timelock_period` unless `override_threshold` approvals are reached." Once `override_threshold` becomes stale (`<= num_signatures_required`), the cooling-off period silently disappears for all transactions, including ones that move APT/fungible assets held by the multisig's resource account, rotate ownership of objects/code-objects owned by the multisig, or change owners further. This is a supply/custody accounting corruption path: the timelock -- the mechanism that lets other owners detect and react to (e.g., reject) a malicious pending transaction before execution -- can be defeated by a routine, non-privileged administrative action (raising the signature threshold) that has no apparent connection to the timelock at all. Any owner subset able to submit and approve `update_signatures_required` (itself normal multisig quorum, not privileged governance) can inadvertently or deliberately collapse the safety margin the timelock was meant to guarantee, enabling faster-than-intended draining of multisig-held value once quorum is reached.

### Likelihood Explanation
Likelihood is moderate to high in any multisig that (a) enables the timelock feature and (b) later performs a normal, expected lifecycle operation of increasing `num_signatures_required` (e.g., adding owners and requiring more signers) without also raising `override_threshold` in lockstep. There is no code path enforcing this coupling, no warning event, and the `TimelockUpdated`/`UpdateSignaturesRequiredEvent` events are emitted from separate independent functions, so operators have no automatic alert that the invariant has been broken.

### Recommendation
Re-validate (or automatically adjust) `MultisigAccountTimeLock.override_threshold` whenever `num_signatures_required` changes: `update_owner_schema` should check `exists<MultisigAccountTimeLock>` and assert `override_threshold.is_none() || override_threshold > new_num_signatures_required`, aborting (or requiring the caller to also update the timelock in the same proposal) if the invariant would be violated. Alternatively, store the override_threshold as a delta/percentage above `num_signatures_required` rather than an absolute value so it tracks automatically.

### Proof of Concept
1. Owner creates a multisig account with `num_signatures_required = 2`, 4 owners, and configures `upsert_timelock(timelock_period = 7 days, override_threshold = Some(4))` (valid because `4 > 2`).
2. Owners later submit and approve `add_owners_and_update_signatures_required` raising `num_signatures_required` to `4` (still `<= 4` owners, valid state per `MultisigAccount` invariants) — `override_threshold` (4) is untouched.
3. Now `override_threshold (4) <= num_signatures_required (4)`.
4. Any subsequent transaction (e.g., a fund transfer from the multisig's resource account) that reaches ordinary quorum (4 approvals) automatically satisfies `can_execute_with_timelock` immediately: `num_approvals(4) >= override_threshold(4)` is true, so `validate_multisig_transaction` allows execution with zero elapsed wait — the configured 7-day cooling-off period never applies, even though no one explicitly disabled or reconfigured the timelock.

**Note on verification limits:** I was unable to fully trace whether `update_owner_schema`'s full body (not shown in the excerpts retrieved) contains any hidden interaction with `MultisigAccountTimeLock` that might already guard this case — the middle portion of `update_owner_schema` was not returned by search/read calls before the tool budget was exhausted. If `update_owner_schema` does independently re-validate the timelock override invariant, this finding would not hold; a full read of that function is recommended to confirm before treating this as conclusively exploitable.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    fun upsert_timelock_internal(
        multisig_account: &signer,
        timelock_period: u64,
        override_threshold: Option<u64>,
    ) {
        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);

        assert!(
            timelock_period >= MIN_TIMELOCK_PERIOD && timelock_period <= MAX_TIMELOCK_PERIOD,
            error::invalid_argument(EINVALID_TIMELOCK_DURATION)
        );

        let multisig_account_resource = &MultisigAccount[multisig_address];
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required,
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length(),
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(

            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );
