### Title
Webhook HMAC validation covers only the raw body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw HTTP body alone, while the `shop` (`shop-domain`) header that identifies which merchant/tenant the webhook belongs to is read separately and never included in the HMAC-covered bytes. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` field to route/attribute the event, so a request whose body+HMAC pair is valid for tenant A can be replayed with the `shop-domain` header rewritten to tenant B and will still pass HMAC verification, resulting in cross-tenant data being attributed to the wrong shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic link to the HMAC: [2](#0-1) 

`HmacValidator.validate` verifies the signature purely against `to_signable_string` (the body), via `VerifiableQuery`: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, and forwards the *unauthenticated* `request.shop` value straight into the handler's metadata, which apps use to know which merchant the payload belongs to: [4](#0-3) 

The identity binding that should hold is: `shop_header == shop_bound_by_hmac`. Because the HMAC signable string is `raw_body` only, this equality never actually holds — `shop` is parsed but never verified. Any attacker who can obtain one legitimately-signed `(raw_body, hmac)` pair for their own shop (trivial: they own a store with the app installed and can observe their own webhook deliveries) can resubmit that exact body+HMAC to the app's webhook endpoint while substituting a victim's `shop-domain` header value. `HmacValidator.validate` will still return `true` since it only checks `raw_body` against the HMAC, so `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: the `shop` value handed to host application handlers is supposed to be an authenticated fact confirmed by Shopify's signature, but it is not covered by the signature at all. A host app that (reasonably, per the gem's documented `WebhookMetadata`) trusts `data.shop` to select/update per-tenant records can have attacker-supplied body content persisted or acted upon under a victim shop's identity — a cross-tenant access/data-confusion vulnerability, which meets the Critical bar (cross-tenant access) defined for this analysis.

### Likelihood Explanation
Likelihood is high for any attacker who has (or creates) their own store with the target app installed: they receive valid `(body, hmac)` pairs for topics they control (e.g. `app/uninstalled`, `orders/create` on their own test orders) and only need to forge the `shop-domain` header on replay — no access to `client_secret`, access tokens, or any privileged credential is required, only network access to the app's public webhook endpoint.

### Recommendation
Include the shop identity in the value that is HMAC-verified, or otherwise cryptographically bind `request.shop` to the signed payload before it is trusted. Concretely:
- Do not treat `Request#shop` as authenticated data on its own; require host apps to cross-check it against a shop already known/authorized for the delivered `topic`/registration, or
- Extend `to_signable_string` (or add a secondary check in `Registry.process`) so the shop domain used for routing is verified to match the shop that was used to compute/expect the given HMAC signature (e.g., validate against the shop associated with the registered webhook subscription rather than blindly trusting the header).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook delivery (e.g. `orders/create`), capturing the raw JSON body `B` and the corresponding `X-Shopify-Hmac-Sha256` header `H` computed by Shopify with the app's `client_secret`.
2. Attacker sends a POST to the app's webhook endpoint with:
   - body = `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256` = `H` (unchanged)
   - header `X-Shopify-Shop-Domain` = `victim.myshopify.com` (changed)
   - header `X-Shopify-Topic` = same topic
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `"victim.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds even though `shop` was swapped.
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the attacker-controlled body to be processed as if it belonged to the victim's shop.
