### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop-domain spoofing/cross-tenant confusion in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while the `shop` value consumed by the handler is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `HmacValidator.validate` only checks that the HMAC matches over `to_signable_string` (the body) [3](#0-2) , so the `shop` field is never part of the value that is cryptographically bound to the signature. `Registry.process` nonetheless trusts `request.shop` as the tenant identity and forwards it, unverified, to the app's `WebhookHandler#handle` via `WebhookMetadata` [4](#0-3) , and `WebhookMetadata.shop` is a plain `String` const with no further validation [5](#0-4) .

### Finding Description
This is the identity-binding-break analog from the report: "a field acted on but not covered by the HMAC." In the audited contract, `poolInfo()`'s destructured return values were assumed correct/authoritative without accounting for a mismatched contract shape; here, the gem assumes the `shop` header is authoritative/tenant-bound merely because *a* valid HMAC was found on the request, but the HMAC computation never actually covers the `shop` value.

Concretely:
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [3](#0-2) .
- For webhook requests, `to_signable_string` is `@raw_body` only [1](#0-0) ; `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are excluded from the signed content [6](#0-5) .
- `Registry.process` raises only if the HMAC over the body is invalid, then immediately treats `request.shop` as ground truth for the tenant and dispatches to the handler [4](#0-3) .

The equality that should hold but doesn't: `shop_bound_by_hmac == shop_used_for_tenant_dispatch`. Before the attack: for a genuine Shopify-delivered webhook, both are `shop-A.myshopify.com` (they coincide because Shopify itself set both consistently). After the attacker's request sequence: an entity that receives a legitimate webhook for their own shop (`shop-A`, which they are entitled to control since it's their store) can replay the exact same body and HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain: shop-B.myshopify.com`. Because HMAC validation only checks body bytes, `Utils::HmacValidator.validate` still returns `true` [7](#0-6) , yet the `shop` value handed to the app-defined handler is now `shop-B`, a tenant the attacker does not control.

### Impact Explanation
This directly matches the "cross-tenant access" Critical impact bucket. Any app whose `WebhookHandler#handle` implementation uses `data.shop` to select/lookup a session, database record, credential, or perform an action scoped to that shop (a documented, intended usage of `WebhookMetadata.shop`) can be made to process an attacker's forged/replayed webhook body as if it belonged to a different merchant. Since the shop identity is not bound by the signature, this breaks the authentication boundary the HMAC is supposed to enforce between tenants.

### Likelihood Explanation
Exploitation requires the attacker to possess a validly-signed webhook for at least one shop (trivial — they can register a webhook on their own store and observe the delivered payload/HMAC, or use webhooks for public/global topics whose bodies are shop-independent, e.g. `app/uninstalled` boilerplate bodies), then replay it to the app's webhook endpoint with a different `shop`-domain header value. No access to `api_secret_key` or any privileged credential is needed beyond what a normal merchant/app-installer already has for their own shop. This is a realistic, unprivileged-internet-user analog.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-signed material for webhook validation, or otherwise require the handler-facing `shop` value to be independently cross-checked against a value that is authenticated by the request (e.g., verify it against the topic/shop combination Shopify actually signs, matching Shopify's official webhook verification which signs the raw body under the assumption that the delivery endpoint is unique per app and the header is trusted only in combination with body — but explicitly document/require that consumers must not derive tenant identity solely from `shop` without additional binding, or extend `to_signable_string` to incorporate the `shop` header so a mismatched replay fails HMAC validation).

### Proof of Concept
1. Attacker owns `shop-A.myshopify.com`, installs the target app, and registers a webhook (e.g., `orders/create` with a fixed/predictable body content, or any topic whose payload doesn't reveal the shop, e.g. `app/uninstalled`).
2. Shopify delivers a request to the app's endpoint with headers `x-shopify-shop-domain: shop-A.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and the JSON body.
3. Attacker captures this raw body and HMAC value, then re-sends an HTTP POST to the same webhook endpoint with:
   - Same raw body
   - Same `x-shopify-hmac-sha256`
   - `x-shopify-shop-domain: shop-B.myshopify.com` (victim shop)
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only the body bytes were checked [9](#0-8) .
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "shop-B.myshopify.com"` [10](#0-9) , even though the HMAC never bound this value to the request — resulting in the app performing shop-B-scoped actions triggered by an attacker who controls only shop-A.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
