### Title
Cross-Tenant Webhook Confusion via Unauthenticated `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw body only, while the `shop` (and `topic`/`webhook_id`) values that the registry hands to application handlers are read from unauthenticated HTTP headers. This breaks the identity binding `shop authenticated == shop acted upon`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to the handler using `request.shop`, which is the unauthenticated header value: [4](#0-3) 

Because the app's `api_secret_key` is shared across all shops installed on the app (it is not per-shop), any merchant who has installed the app can trigger a legitimate webhook for their own shop, capture the `(raw_body, hmac)` pair that Shopify sends, and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a *different* merchant's shop. The HMAC check still passes because it only validates the body bytes against the shared secret — it says nothing about which shop the body belongs to. The registry then invokes the application's webhook handler believing the request originated from the victim shop (`request.shop`), while the actual signed content originated from the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity confusion: the identity used for authorization/HMAC verification (`raw_body` signed with the shared `api_secret_key`) is not the same as the identity acted upon (`shop` header trusted by the handler). Any application built on this gem's webhook `Registry`/`Request` API that uses `WebhookMetadata#shop` to select which tenant's session/records to update is exposed to cross-tenant data corruption or disclosure purely from a header value that carries no cryptographic guarantee.

### Likelihood Explanation
Any account that can install the app (a normal, unprivileged merchant relative to other tenants) can generate at least one validly-signed webhook body/HMAC pair for their own shop, then replay it against the shared webhook endpoint with an arbitrary `shop-domain` header. No access token, secret key, or privileged account for the *victim* shop is required — only the ability to trigger any webhook on the attacker's own installation, which is available to every merchant.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material, or otherwise cross-check the `shop-domain` header against an independently verified value (e.g., a registered webhook ID to shop mapping) before handing it to application handlers, so the identity used for signature verification matches the identity acted upon in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers any subscribed webhook topic (e.g., updates a product), and Shopify POSTs a validly HMAC-signed body to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac over body>`.
3. Attacker captures `raw_body` and the `hmac` header, then re-sends the same request but swaps `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still succeeds because it only checks `raw_body` against the shared `api_secret_key`; `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the application to process attacker-controlled data as if it belonged to the victim tenant.
