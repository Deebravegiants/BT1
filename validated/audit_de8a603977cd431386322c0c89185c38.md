### Title
Unchecked `abi_decode`→SCALE conversions in the BEEFY/SP1 proof pipeline panic on attacker-controlled proof bytes, crashing block execution - ([File: evm/rust/src/conversions.rs])

### Summary
CVE-2017-3317 is a MySQL logging-path bug where a high-privileged, authenticated user can supply data that makes the server panic/hang (complete DoS), without any memory-safety violation — pure "malformed input reaches an unchecked code path and the process crashes." The closest reachable analog in this codebase is the family of `From` conversions in `evm/rust/src/conversions.rs` that turn Solidity-ABI-decoded BEEFY proof structs into the internal SCALE types consumed by the BEEFY/SP1 consensus verifier. These conversions use `.expect(...)` and raw `copy_from_slice` instead of returning `Result`, and the input they operate on is attacker-supplied proof bytes submitted through a permissionless extrinsic.

### Finding Description
`pallet_beefy_consensus_proofs::verify_and_apply` ABI-decodes an untrusted `proof: &[u8]` blob into either `SP1BeefyProof` or `BeefyConsensusProof`, then converts it `.into()` a SCALE type before dispatching it into `handlers::handle_incoming_message`: [1](#0-0) 

That `.into()` call resolves to the `From` impls in `evm/rust/src/conversions.rs`, several of which panic instead of erroring on adversarial input:

- `From<Commitment> for SpCommitment` unwraps the first payload entry unconditionally: [2](#0-1) 
An attacker who submits a `Commitment` with an empty `payload` array (a valid ABI encoding of a dynamic array) hits `.expect("commitment has at least one payload entry")` and panics. `block_number`/`validator_set_id` are also `try_into().expect(...)`, which panics for any `uint256` value in the proof that doesn't fit the target integer width.

- `From<Vote> for SignatureWithAuthorityIndex` copies an attacker-controlled `bytes signature` field into a fixed `[u8; 65]` without checking its length first: [3](#0-2) 
`Bytes` is a dynamic ABI type the caller fully controls; any length other than 65 makes `copy_from_slice` panic (`source slice length does not match destination slice length`).

- `From<RelayChainProof> for MmrProof` similarly panics via `try_into().expect("mmr leaf index out of bounds")` on the attacker-supplied `leafIndex`: [4](#0-3) 

None of these code paths validate lengths/ranges before the panic-prone conversion, unlike the numerous other proof-handling paths in this codebase that were explicitly hardened against this exact bug class (see the BEEFY MMR-leaf-index fix, sync-committee multi-proof length check, GRANDPA header-lookup fix, Pharos SPV proof-depth guard, and RLP node-codec HP-prefix guard, all of which carry comments describing the same "attacker-controlled input reaches an `.unwrap()`/index/`copy_from_slice` and panics the runtime" pattern): [5](#0-4) [6](#0-5) [7](#0-6) 

The `submit_proof` extrinsic that reaches `verify_and_apply` is exercised in the pallet's own benchmark with a plain `Signed` origin (not root/admin), consistent with the pallet's design as a permissionless, competitively-rewarded "uncle proof" submission mechanism (`ProverCount`, `AcceptedProvers`): [8](#0-7) 
I was not able to directly inspect the `submit_proof` dispatchable's body/origin check in this pass to fully confirm there is no additional permission gate beyond `ensure_signed`; this should be verified before treating the finding as fully confirmed.

### Impact Explanation
A panic inside runtime (WASM) code executed during `apply_extrinsic`/block-building traps the executor. Depending on how the host handles the trap, this either aborts the transaction pool validation for that call, or — if triggered during actual block execution/import — can abort block production/import entirely, which is the direct analog of MySQL's "hang or frequently repeatable crash (complete DoS)." Because `submit_proof` is meant to be callable by arbitrary competing provers with only a valid-looking ABI encoding (not a cryptographically valid proof, since these are conversions that run *before* verification), a malformed-but-well-typed proof can repeatedly crash the pallet's proof-processing path.

### Likelihood Explanation
High for a "difficult to exploit but low-privilege" class: the attacker only needs to know the ABI schema for `SP1BeefyProof`/`BeefyConsensusProof` (both public, since they're used by the SDK/relayer) and submit a signed extrinsic with an empty `payload` array, an oversized `signature` field, or an out-of-range `blockNumber`/`leafIndex`. No cryptographic material or privileged role is required — matching the "single submitted transaction" reachability bar in scope.

### Recommendation
Replace every `.expect(...)`/unchecked `copy_from_slice`/`unwrap` in `evm/rust/src/conversions.rs`'s `BeefyConsensusState`/`Commitment`/`Vote`/`RelayChainProof`/`Sp1BeefyProof`-related `From` impls with fallible `TryFrom` implementations that return typed errors (mirroring the fix pattern already applied to `beefy_verifier::verify_mmr_leaf`, `sync-committee`'s multi-proof length check, and the RLP node codec). Thread these errors up through `pallet_beefy_consensus_proofs::verify_and_apply` as a rejected/invalid-proof `Error<T>` variant instead of allowing the underlying panic to propagate.

### Proof of Concept
1. Craft a valid ABI encoding of `SP1Beefy::SP1BeefyProof` (or `BeefyConsensusProof`) where the nested `Commitment.payload` array is empty, or where any `Vote.signature` field is not exactly 65 bytes, or where `commitment.blockNumber`/`latestMmrLeaf.leafIndex` exceeds the target integer's range.
2. Submit it as the `proof` argument of `pallet_beefy_consensus_proofs::submit_proof` via a normal signed extrinsic (per the pallet's benchmark, no elevated origin is required).
3. `verify_and_apply` ABI-decodes the payload and calls `.into()` on the decoded struct, which reaches the offending `From` impl in `evm/rust/src/conversions.rs` and panics inside runtime execution, before any cryptographic verification of the proof occurs.
