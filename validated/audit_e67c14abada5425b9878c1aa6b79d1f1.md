### Title
Unbounded router pull via `approveUnlimited` lets attacker drain residual/stranded token balance from `ExternalActionSwap` and mint it into their own output UTXO - (File: contracts/external-actions/swaps/ExternalActionSwap.sol / contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` grants the LI.FI router an unlimited, standing ERC20 allowance via `approveUnlimited` and then blindly forwards attacker-supplied `externalActionMetadata` bytes to `router.call(...)`, with no post-swap check that the router only consumed `inputAmount` (i.e. `-deltaAmounts[0]`, the amount Hinkal actually transferred to the action this transaction). `ExternalActionSwap.swap` computes `swappedAmount` purely from the *output*-token balance delta and forwards that whole amount to the caller as a new UTXO, without ever reconciling the *input*-token balance consumed against `-deltaAmountChanges`. Any input-token balance already resident in the action (dust/residual from a prior swap that didn't fully consume its approved allowance, or any other token stranded there) can therefore be swept into the router by a crafted `externalActionMetadata` payload and minted into the attacker's own output UTXO.

### Finding Description
The invariant that should hold is: *tokens leaving `ExternalActionSwap` in a transaction == `-deltaAmountChanges` that Hinkal sent it that transaction*. `ExternalActionSwap.swap` never checks this on the input side: [1](#0-0) 

`inputAmount` is derived from `-deltaAmounts[0]` but is only actually enforced for native ETH (`router.call{value: inputAmount}`). For ERC20 input tokens it is passed into `callRouter` and then simply discarded: [2](#0-1) 

Because `approveUnlimited` sets the router's allowance to `type(uint256).max` whenever it drops below half of that, and the router is then called with fully attacker-controlled `externalActionMetadata` (there is no on-chain or circuit binding of this payload to `inputAmount`), the attacker can encode a LI.FI call whose embedded `amount` parameter pulls more of `inputToken` from `ExternalActionSwap` than the `inputAmount` Hinkal just deposited into it — up to the contract's entire balance of that token. Any pre-existing balance of `inputToken` sitting in `ExternalActionSwap` (e.g. dust left over from a prior swap where the router didn't fully consume the approved amount, since `swap()` never verifies input-side balance drawdown) becomes available to be swept in.

`swappedAmount` is computed as a pure before/after delta of the *output* token around the router call:

`swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;`

so it faithfully captures whatever the router actually produced — including the extra output generated by swapping the stranded residual on top of the attacker's declared `inputAmount`. That inflated `swappedAmount` (minus fees) is then transferred to `msg.sender` (Hinkal) and wrapped into a new `UTXO` credited to the attacker's `stealthAddressStructure`: [3](#0-2) 

Critically, `Hinkal.sol`'s own balance-consistency check (`balanceDif == amountChanges[i] + utxoAmount`) only reconciles **Hinkal's own** balances against the UTXO amounts reported by the action — it has no visibility into what happened *inside* `ExternalActionSwap` between the deposit and the swap: [4](#0-3) 

Since `ExternalActionSwap` correctly forwards to Hinkal exactly what it measured as `swappedAmount`, Hinkal's own bookkeeping is self-consistent and passes — the discrepancy is entirely hidden inside `ExternalActionSwap`, where the actual input-token drawdown was never checked against `-deltaAmountChanges`. Unlike `EmporiumUpgradeable.runAction`, which explicitly reconciles `balanceChange` against `deltaAmountChanges[i]` and reverts via `BalanceChangeShouldBePositive` if more than what was deposited is consumed, `ExternalActionSwap` has no equivalent guard for the input token.

The mention of `HinkalWrapper`'s fee settlement in the question is not part of the exploitable path here: `HinkalWrapper.prooflessDeposit` only forwards deposits to `Hinkal.prooflessDeposit` (unrelated to `transact`/external actions), and its allowances are granted to `hinkal`, not to `ExternalActionSwap`. It does not seed or interact with any balance inside `ExternalActionSwap`, so it is not a required or contributing precondition for this bug.

### Impact Explanation
An attacker who observes (or can seed, e.g. via a prior legitimate-looking small swap that leaves the router unable to fully consume the approved amount due to slippage/partial-fill behavior) a stranded ERC20 balance inside `ExternalActionSwap` can craft `externalActionMetadata` to sweep that balance through the router and mint the resulting output entirely into their own UTXO, stealing value that was never accounted to them by `-deltaAmountChanges`. This is direct theft of value that passed through (or was stranded in) the action, matching the Critical category: "direct theft of shielded or in-flight user funds." It is repeatable any time residual balance accumulates in the action.

### Likelihood Explanation
The precondition is a nonzero standing balance of `inputToken` inside `ExternalActionSwap` at the time the attacker's transaction executes. This can arise from normal aggregator behavior (a prior swap not fully consuming the unlimited-approved amount, e.g. positive slippage, partial fills, or rounding) or accidental transfers to the contract. The attack itself costs only a normal `transact` call with a self-crafted small deposit and a router-calldata payload the attacker fully controls (LI.FI router accepts arbitrary calldata forwarded verbatim), requiring no privileged role.

### Recommendation
In `ExternalActionSwap.swap` (or `LifiExternalAction.callRouter`), record the `inputToken` balance immediately before and after the router call and require that the balance decreased by exactly `inputAmount` (mirroring the reconciliation `EmporiumUpgradeable` performs for `deltaAmountChanges`), reverting otherwise. Additionally, avoid `approveUnlimited`; approve only the exact `inputAmount` needed for the swap (reset to 0 after) so the router can never pull more than what Hinkal placed into the action for that transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock LI.FI router), and register the action.
2. Simulate a stranded balance: directly `deal`/`mint` some `inputToken` into `LifiExternalAction` (representing dust from a prior partial-fill swap), without any corresponding UTXO or `deltaAmountChanges` record.
3. As the attacker, build a valid proof/`CircomData` for a `transact` call with `deltaAmounts[0] = -X` (small, honestly declared deposit) and `erc20TokenAddresses = [inputToken, outputToken]`.
4. Craft `externalActionMetadata` for the mock router such that it calls `transferFrom(action, router, X + R)` (pulling the residual `R` on top of the declared `X`) and returns `outputToken` proportional to `X + R`.
5. Assert: attacker's resulting UTXO `amount` (from `utxoSet[0]`) corresponds to output derived from `X + R`, not `X` — i.e. `swappedAmount(X+R) > swappedAmount(X)` while `-deltaAmountChanges` committed in the proof only equals `X`.
6. Assert this passes all of `Hinkal.sol`'s existing checks (`balanceDif == amountChanges[i] + utxoAmount`, slippage checks) with no revert, confirming the residual `R` was silently captured by the attacker beyond what `-deltaAmountChanges` authorized.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
