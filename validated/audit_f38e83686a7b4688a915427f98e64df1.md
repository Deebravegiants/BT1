This is the key finding: in `ShopifyAPI::Webhooks::Request`, the `shop` (tenant identity) is read directly from the `X-Shopify-Shop-Domain` header, but that header is **not part of the HMAC-signed material** — only `@raw_body` is signed [1](#0-0) [2](#0-1) . This breaks the binding `shop_used_for_tenant_lookup == shop_covered_by_hmac`, since the HMAC only proves the body's integrity/authenticity with the app's shared secret, not which shop the header claims to represent.

### Title
Webhook `shop` identity not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the value of the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header verbatim, while `#hmac`/`#to_signable_string` only cover the raw body [3](#0-2) . `Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it against the `hmac` header [4](#0-3) . Because the shop-domain header is excluded from the signed content, a valid HMAC proves only "this body came from a webhook-registrant with the app secret" — it says nothing about which shop the request claims to be for.

### Finding Description
The `VerifiableQuery` interface requires implementers to define `hmac` and `to_signable_string`, and `HmacValidator.validate` only checks that the HMAC matches `to_signable_string` computed with `Context.api_secret_key` (or `old_api_secret_key`) [5](#0-4) [6](#0-5) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [7](#0-6) , and the `shop` accessor is derived purely from an HTTP header that is not part of that signed string [1](#0-0) . This means: for any given valid `(raw_body, hmac)` pair genuinely produced by Shopify for shop A, an attacker (an unprivileged internet user, not needing `api_secret_key`) who can observe or replay that pair can resubmit it to the host application with an arbitrary `X-Shopify-Shop-Domain: shop-B.myshopify.com` header. Since this gem exposes no method that cross-checks `shop` against the signed payload, a host application that trusts `Request#shop` (as the gem's own accessor implies is safe once `hmac` validates) to route/attribute the webhook to a tenant can be tricked into processing shop A's webhook data under shop B's identity — a tenant-binding break: `shop_used_by_host_app != shop_that_actually_produced_the_signed_body`.

Note: this requires the host application to call `Webhooks::Request#shop` after `HmacValidator.validate` succeeds and use it for tenant attribution, which is the intended/documented usage pattern of this class (it exists specifically to expose `shop` alongside signature verification).

### Impact Explanation
This is a cross-tenant data confusion vector: an attacker who can capture one legitimately-HMAC'd webhook delivery (e.g., from their own shop's dev store, or an intercepted/replayed request against a publicly reachable webhook endpoint) can relabel it as belonging to a different shop before the host app processes it, since the gem's `Request` class provides no way to detect the mismatch — the shop identity is not cryptographically bound to the payload it accompanies. This matches the "field acted on but not covered by the HMAC" identity-binding class named in scope.

### Likelihood Explanation
Medium-to-Low: exploitation requires the attacker to have captured or otherwise obtained one valid `(raw_body, hmac)` pair for some shop (e.g., their own store, where they can install the app and freely generate legitimate webhook traffic), then resend the same body/HMAC with a different shop-domain header to the host's public webhook endpoint. This is directly reachable by any unprivileged internet user with app access (installing on their own dev store is a normal/uncontrolled action), and does not require `api_secret_key`, an access token, or any privileged account belonging to the victim shop.

### Recommendation
Include the shop domain (and ideally webhook id/topic) in the signed material, or explicitly document/enforce that `shop` must never be trusted without an out-of-band, per-shop registered-webhook-endpoint check. At minimum, the gem should provide/require a way to bind the verified HMAC to the specific expected shop (e.g., accept an `expected_shop` parameter to `validate`/`Request` and compare it against a value obtained independently of the header), rather than exposing `shop` as if it were verified once `hmac` matches.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers/captures a legitimate webhook delivery, obtaining a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's shared secret.
2. Attacker resends this exact body and HMAC header to the host application's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. Host app calls `ShopifyAPI::Utils::HmacValidator.validate(request)` — this only checks the body/HMAC pair, which is unchanged and thus still valid [8](#0-7) .
4. Host app then calls `request.shop`, gets `"victim-shop.myshopify.com"` [1](#0-0) , and attributes/stores the attacker's payload (or re-triggers processing) under the victim tenant's record — a cross-tenant integrity/confusion issue achieved without any credential belonging to the victim.
