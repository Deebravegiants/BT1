### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` attribute used by the application to attribute the webhook to a tenant is read from an HTTP header that is never included in that signed payload. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts the header-derived `shop` value, breaking the intended binding between "the request whose authenticity was cryptographically verified" and "the tenant the verified request is attributed to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop`, however, is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed string: [3](#0-2) 

`Registry.process` validates the HMAC of the request (i.e., proof that the caller knows `Context.api_secret_key` and produced a body with the correct digest) and then, without any further check, hands `request.shop` to the registered handler as the tenant identity: [4](#0-3) 

The verification performed by `Utils::HmacValidator.validate` only proves:

`HMAC_secret(raw_body) == received_hmac`

It does **not** prove:

`header["shop-domain"] == shop_that_actually_produced_raw_body` [5](#0-4) 

Because the secret (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant/attacker who has legitimately installed the app on their own store receives at least one genuine, validly-signed webhook (valid HMAC over a body they can influence, e.g. `products/create`, `app/uninstalled`, etc., fired from their own store). That attacker can then replay the exact same `raw_body` + `hmac` header to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. The HMAC check still passes (it only checks the body), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain: [6](#0-5) 

Any host application logic that uses `WebhookMetadata#shop` to look up per-tenant sessions, credentials, or state will now act on the victim tenant using attacker-controlled webhook content, i.e., cross-tenant confusion caused entirely by this gem's failure to bind the header-derived `shop` field to the HMAC-authenticated payload.

### Impact Explanation
This breaks the tenant-authentication boundary the HMAC check is supposed to enforce: the gem's own webhook-processing API (`Registry.process` / `Webhooks::Request`) authenticates the *body* but reports an unauthenticated *shop identity* to the handler, enabling cross-tenant webhook injection/spoofing without any credential belonging to the victim. This matches the Critical "cross-tenant access" impact category — an unprivileged installer of the app can cause handlers to process forged data under another merchant's identity.

### Likelihood Explanation
Any developer/attacker can freely install the app on their own store (a completely unprivileged action), obtain a genuine signed webhook, and replay it with a modified shop header against the app's public webhook endpoint. No secrets, tokens, or privileged access to the victim's shop are required — only network access to the app's own webhook endpoint, which is inherently public. This is straightforward to execute.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed payload construction, or otherwise cryptographically bind the header-derived `shop` value to the verified body before trusting it — e.g., have `to_signable_string` incorporate the shop-domain header, or require host applications to independently corroborate `request.shop` against a value derived from data that is actually inside the signed body/session context. At minimum, document prominently that `Request#shop` is unauthenticated header data and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com`, so the app's registered webhook endpoint receives a legitimate webhook, e.g. topic `products/create`, with body `B` and a valid `X-Shopify-Hmac-Sha256` header `H = HMAC_secret(B)`.
2. Attacker captures `B` and `H` from this legitimate delivery.
3. Attacker sends their own POST request directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (attacker-modified)
   - Header `X-Shopify-Topic: products/create`
4. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`, which calls `Utils::HmacValidator.validate(request)`; since validation only checks `HMAC_secret(B) == H`, it passes: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`, causing the host application to process attacker-controlled data as though it originated from `victim-shop.myshopify.com`.
