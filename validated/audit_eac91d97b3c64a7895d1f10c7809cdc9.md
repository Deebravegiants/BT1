## Finding: Unbounded, unmetered growth of `RequestCommitments` via free-form `dispatch_request` — analogous to Nova's missing per-tenant IP quota

The Nova CVE is a classic CWE-770 (missing quota) bug: an authenticated caller could invoke `addFixedIp` an unbounded number of times because no quota check gated the resource-allocating call, exhausting a shared, finite resource. Hyperbridge has a directly analogous quota gap in `pallet-ismp`'s outbound dispatch path.

### Root cause

`Pallet::<T>::dispatch_request` inserts a permanent `RequestCommitments` entry (child-trie + offchain MMR leaf) for every dispatched request, and only removes it on response, timeout, or claim — it enforces no cap on the number of outstanding/total commitments and no minimum relayer fee: [1](#0-0) 

The only "payment" gate is the optional relayer `fee`, which callers are explicitly permitted to set to zero for self-relay — this is documented as a first-class, supported mode, not an edge case: [2](#0-1) [3](#0-2) 

`IsmpDispatcher::dispatch_request` on `pallet-ismp` only moves funds if `fee.fee != Zero::zero()`; a zero fee skips the transfer entirely and dispatch still succeeds: [4](#0-3) 

`timeout` is also attacker-controlled and can be `0`, meaning "never expire" — the commitment then persists in the child-trie/offchain MMR forever, since it is never eligible for the timeout cleanup path: [5](#0-4) 

Compare this with `pallet-bandwidth`, which was clearly built to close exactly this class of gap for *inbound* EVM→Hyperbridge messages — every non-purchase POST is metered against a capped, evictable per-`(source, app)` byte allowance: [6](#0-5) [7](#0-6) 

However, that gate is applied by the *router when it accepts a request destined for a Hyperbridge module* (i.e., inbound traffic from EVM chains), not on the low-level `IsmpDispatcher::dispatch_request` entry point itself, which any pallet/module on Hyperbridge (or any parachain running `pallet-ismp`) can call directly with `fee: 0` and `timeout: 0`. There is no equivalent cap on the *number* of outstanding commitments a single dispatching account/module can create in `RequestCommitments`/the offchain MMR — only the ordinary per-extrinsic weight fee applies, which is a generic anti-spam mechanism, not a resource-specific quota.

### Impact

An unprivileged account (or any pallet exposing an unauthenticated dispatch call, such as the example `dispatch_to_evm` pattern) can repeatedly call `dispatch_request` with `fee: 0`, `timeout: 0`, at only the marginal cost of transaction weight fees. Because entries are never purged (no timeout, no response ever arrives for junk destinations/bodies), this:
- Permanently bloats the on-chain child-trie (`RequestCommitments`) and the offchain MMR that back all state/membership proofs, degrading proof generation, sync, and storage costs for the whole chain.
- Grows the request queue that relayers must scan indefinitely, degrading relayer economics and message-delivery liveness for legitimate routes — i.e., a chain-wide "route unable to deliver messages" effect as junk crowds out legitimate outstanding requests and increases the cost/latency of proof construction and verification.

This is the direct structural analog of CVE-2013-1838: a resource-creating call path reachable by an ordinary caller with no bound on repetition, backed only by a payment field that can be legitimately set to zero.

### Recommendation
- Enforce a non-zero minimum relayer fee (or an explicit protocol-level dispatch fee) on `dispatch_request`, scaled to storage cost, rather than allowing `fee: 0` unconditionally.
- Add a hard cap / rent-like expiry on `RequestCommitments` analogous to `BoundedStateCommitments`'s `StateMachineCommitmentCap` + FIFO eviction, so zero-fee or never-timeout requests cannot accumulate unboundedly.
- Extend `pallet-bandwidth`-style metering to the outbound `dispatch_request` path itself, not only inbound router acceptance.

### Proof of Concept (conceptual)
1. Any account calls a pallet exposing `IsmpDispatcher::dispatch_request` (or the example `send_message`/`dispatch_to_evm` pattern) with `DispatchPost { timeout: 0, body: <minimal>, .. }` and `FeeMetadata { fee: Zero::zero(), .. }`.
2. Repeat in a loop across many blocks/accounts — each call succeeds, inserting a new `RequestCommitments` entry that is deleted only if a matching response/timeout is delivered, both of which the attacker controls (never trigger by picking an unreachable/garbage `dest`/`to`).
3. Over time, `RequestCommitments` (child-trie) and the backing offchain MMR grow without bound, degrading proof verification performance and relayer throughput chain-wide. [1](#0-0)

```rust
	/// Dispatch an outgoing request, returns the request commitment
	pub fn dispatch_request(request: Request, meta: FeeMetadata<T>) -> Result<H256, ismp::Error> {
		let commitment = hash_request::<Pallet<T>>(&request);

		if RequestCommitments::<T>::contains_key(commitment) {
			Err(ismp::Error::Custom("Duplicate request".to_string()))?
		}

		let (dest_chain, source_chain, nonce) =
			(request.dest_chain(), request.source_chain(), request.nonce());
		let leaf_index_and_pos = T::OffchainDB::push(Leaf::Request(request));
		// Deposit Event
		Pallet::<T>::deposit_event(Event::Request {
			request_nonce: nonce,
			source_chain,
			dest_chain,
			commitment,
		});

		RequestCommitments::<T>::insert(
			commitment,
			RequestMetadata {
				offchain: LeafIndexAndPos {
					leaf_index: leaf_index_and_pos.index,
					pos: leaf_index_and_pos.position,
				},
				fee: meta,
				claimed: false,
			},
		);

		Ok(commitment)
	}
```

```rust
//! # pallet-bandwidth
//!
//! Prepaid `(chain, app)` byte balances credited by tier purchases
//! from `BandwidthManager.sol`. Each purchase carries its own
//! `app_chain`, so any deployment can sponsor any app on any chain.
//!
//! Each `(chain, app)` row holds a FIFO list of [`Subscription`]s
//! (`BoundedVec`, capped at 1024). Every purchase appends a new
//! subscription with a fixed `expires_at`; expiry never extends and
//! same-tier repurchases don't stack — they queue. The gate drains
//! the oldest live subscription first; once empty it moves to the
//! next. Subscriptions that aren't reached before their expiry are
//! swept silently — what you paid for is yours only until it expires.
//! Pushes onto a full list evict the oldest entry and emit
//! [`Event::SubscriptionEvicted`].
//!
//! [`BandwidthGate`] is the hook the runtime's ISMP router consults
//! for every message; insufficient balance → rejected.
```
