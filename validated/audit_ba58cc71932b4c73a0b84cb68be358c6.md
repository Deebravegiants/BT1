### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant shop spoofing on replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `ShopifyAPI::Webhooks::Registry.process` verifies covers exclusively the JSON body bytes. The `shop` value that identifies which tenant the webhook belongs to is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the signed content, and `Registry.process` forwards that unauthenticated header value straight into `WebhookMetadata#shop` passed to the app's handler.

### Finding Description
`Request#to_signable_string` at [1](#0-0)  only signs the raw body. `Request#shop` is derived purely from an HTTP header: [2](#0-1) . `Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac` field [3](#0-2) , so the shop-domain header is never authenticated. `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) . `WebhookMetadata#shop` is documented and typed as the authoritative shop domain for the event [5](#0-4) , and the gem's own documentation instructs integrators to key their business logic (e.g., `shop_domain: data.shop`) off this field, trusting it as verified [6](#0-5) .

The identity binding that should hold is:
`hmac-verified bytes == bytes that determine tenant identity (shop)`

In this gem it instead is:
`hmac-verified bytes == raw_body only`, while `shop` (tenant identity) is sourced from an out-of-band, unsigned header.

Attack sequence (unprivileged actor who only needs to be a normal merchant that has installed the app on their own shop — no `api_secret_key`, no access token, no privileged account required):
1. Attacker installs the target app on their own shop (Shop A) and triggers any subscribed webhook topic (e.g. `orders/create`) by performing a normal, permitted action in their own store.
2. Shopify sends the legitimate webhook request to the app's endpoint with a correctly computed `hmac-sha256` header (computed server-side by Shopify using the real `api_secret_key`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker intercepts/replays this exact request to the app's webhook endpoint, but rewrites only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, leaving the raw body untouched.
4. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) raw body and it matches the (unchanged) `hmac` header, so validation succeeds.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-originated body, and calls the app's handler as if this were a genuine event for the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an app's handler receives attacker-controlled body content falsely attributed to another merchant's shop, with a signature that still validates. Any downstream logic that trusts `data.shop` to select which tenant's records/session/access token to act on (exactly the pattern the gem's own docs recommend) can be made to write, mutate, or dispatch actions against the wrong tenant — i.e., cross-tenant access/data injection triggered entirely through this gem's webhook-processing code path, without any credentials belonging to the victim or knowledge of the app's `api_secret_key`.

### Likelihood Explanation
High for any app that follows the gem's documented pattern of trusting `WebhookMetadata#shop`. The only prerequisite is that the attacker can install the app on their own shop (or otherwise cause one legitimate webhook to be generated) and can replay an HTTP request to the app's public webhook endpoint with a modified header — no secret material, no elevated privileges, and no reliance on the host app misusing an undocumented API.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/api-version/webhook-id) in the HMAC-signed payload, or independently verify `request.shop` against a value derived from data that is itself authenticated (e.g., re-deriving/confirming the shop from a signed component, or requiring the caller to supply the expected shop and comparing it to the header only as a secondary check, never as the source of truth). At minimum, update `to_signable_string` to bind the shop-domain header into the signature so a replayed body cannot be re-attributed to a different shop.

### Proof of Concept
```ruby
# Legitimate webhook received for shop-a.myshopify.com
raw_body = '{"id":123}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker swaps this from shop-a to victim-shop
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>123}, ...))
# HMAC validation passes because to_signable_string only covers raw_body, not the shop-domain header.
