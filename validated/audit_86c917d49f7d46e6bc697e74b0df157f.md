Webhook `shop` (and `topic`) identity is trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook signature only over the raw HTTP body, while the `shop` (and `topic`) fields that are handed to the application's `WebhookHandler` are read from HTTP headers that are never included in that signature. `Registry.process` validates the HMAC and then unconditionally forwards `request.shop`/`request.topic` (taken straight from headers) into `WebhookMetadata`, which the host app uses to select the tenant the webhook belongs to. This breaks the intended identity binding: `HMAC(secret, signed_bytes) == received_signature` should imply `signed_bytes == (shop, topic, body)`, but here `signed_bytes == body` only.

### Finding Description
- `lib/shopify_api/webhooks/request.rb:35-38` — `to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `lib/shopify_api/webhooks/request.rb:20-23` — `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, not from the signed payload: [2](#0-1) 
- `lib/shopify_api/utils/hmac_validator.rb:26-31` — validation only compares the HMAC of `verifiable_query.to_signable_string` (i.e., the body) against the received `hmac`; it never touches `shop`/`topic`: [3](#0-2) 
- `lib/shopify_api/webhooks/registry.rb:188-199` — `process` gates only on `Utils::HmacValidator.validate(request)`, then builds `WebhookMetadata` using `request.shop` and `request.topic` unconditionally: [4](#0-3) 
- `lib/shopify_api/webhooks/webhook_handler.rb:6-12` — `WebhookMetadata.shop` is the field host applications use to route/attribute webhook data to a specific merchant/tenant: [5](#0-4) 

Compare this with the OAuth callback path, where the equivalent `AuthQuery#to_signable_string` explicitly folds `shop` into the signed string, so the HMAC does bind `shop` to the rest of the payload: [6](#0-5) 
No such binding exists for webhooks — `shop` and `topic` are asserted by the sender via headers and never covered by the signature check.

Root cause as an equality that should hold but doesn't:
- Expected: `valid_hmac(body, secret) == true` implies `(shop_header, topic_header)` are authentic for that body.
- Actual: `valid_hmac(body, secret)` only proves the *body bytes* were signed by someone holding `api_secret_key` (i.e., Shopify) for *some* webhook delivery; it says nothing about which shop or topic that delivery was for, since those live in headers outside the signed bytes.

### Impact Explanation
Because the api_secret_key is shared across all shops that install an app (it is not a per-shop secret), any actor who can get a legitimately signed webhook body from their own tenant (e.g., by installing the target app on their own free/dev store and triggering an event) possesses a `(body, hmac)` pair that will pass `HmacValidator.validate`. If that request (or a fabricated request carrying the same signed body) is replayed to the app's webhook endpoint with a `shop-domain` header pointing to a *different* shop, `Registry.process` will still accept it and pass the attacker's body content through as if it belonged to the victim shop, because the validation never checks that the header-derived `shop`/`topic` match anything cryptographically. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (e.g., loading tenant DB context, creating orders/customers records, updating tenant-scoped state), this enables cross-tenant data injection or corruption attributed to a victim merchant — a cross-tenant boundary violation.

### Likelihood Explanation
The attacker needs no privileged Shopify credentials beyond being able to install the target app on any shop they control (including a free development store) and being able to send arbitrary HTTP requests to the app's public webhook endpoint. Both requirements are attainable by an ordinary internet user, and this is the exact scenario listed in the rules ("shop authenticated versus the shop stored as a session key" / "a field acted on but not covered by the HMAC"). The library provides no built-in defense (e.g., verifying `shop`/`topic` are part of the signed content, or independently checking the shop against session state) — this is a gap in the gem's own request/validation code, not merely a host application misuse.

### Recommendation
Bind `shop` and `topic` into the value that is HMAC-verified for webhooks, or require `Registry.process`/`WebhookHandler` implementations to cross-check `request.shop` against an independently trusted source (e.g., the recipient URL/path that was registered per-shop, or a per-shop signing secret) before dispatching. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically authenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook-eligible event (e.g., `orders/create`), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` to the app's webhook endpoint.
2. Attacker captures `(B, H)` from this legitimate delivery (they own the store, so this requires no elevated privilege).
3. Attacker crafts a new POST request to the same app webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) and `Utils::HmacValidator.validate` succeeds, because it only recomputes the HMAC over `B`, per [1](#0-0)  and [3](#0-2) .
5. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...))`, per [4](#0-3) , so the host app processes the attacker's data as though it belongs to `victim-shop`.
