### Title
Webhook HMAC Validates Only the Raw Body, Not the Shop/Topic/Webhook-Id Headers, Enabling Cross-Tenant Webhook Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by signing only the raw HTTP body [1](#0-0) , while the tenant-identifying metadata — `shop`, `topic`, `webhook_id`, `api_version` — is read straight from unauthenticated HTTP headers [2](#0-1) . `ShopifyAPI::Utils::HmacValidator.validate` only ever checks `to_signable_string` against the HMAC secret [3](#0-2) , so the signature never covers which shop the webhook claims to be for. `Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic`/`request.webhook_id` unconditionally when dispatching to the app's handler [4](#0-3) .

### Finding Description
The report's bug class is "an attacker can change data that influences trust decisions but is not covered by the cryptographic binding meant to protect it" — here the binding that breaks is:

`bytes verified (raw_body signed by HMAC)` ≠ `bytes/headers actually parsed and trusted (shop-domain, topic, webhook_id headers)`

Any holder of a validly-signed webhook body/HMAC pair for *any* shop (e.g., an attacker who installs the same app on their own free/dev store and receives a legitimately-signed webhook from Shopify) can replay that exact `raw_body` + `hmac` header combination to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `topic`/`webhook-id`) header to name a different, victim shop. Because `HmacValidator.validate` recomputes the signature purely from `@raw_body` [5](#0-4)  and never incorporates the shop/topic headers into the signable string, the forged request passes signature validation unchanged. `Registry.process` then hands the header-derived `shop` value straight to the handler as authoritative metadata [6](#0-5) , so the app believes attacker-controlled body content originated from, and applies it to, the victim shop.

This differs from the standard OAuth `AuthQuery`, where `shop` (and `host`) are explicitly included in `to_signable_string` and thus covered by the HMAC [7](#0-6)  — the webhook path is the one place in this gem where the identity field is excluded from the signed payload despite being trusted downstream.

### Impact Explanation
This is a cross-tenant confusion vector: an unprivileged user who is a legitimate customer/installer of the app on their own store can forge webhook deliveries that the host application will process as if they came from an arbitrary other shop that also uses the app, without possessing the app's `client_secret`/`api_secret_key`. Depending on how the host application's webhook handler code trusts `shop`/`topic` (e.g., to look up records, update per-tenant data, or trigger uninstall/GDPR flows), this can lead to cross-tenant data corruption, spoofed shop lifecycle events (e.g. fake `app/uninstalled`), or data written into another merchant's records — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that expose the standard webhook endpoint publicly (which is required by Shopify's webhook delivery model) and where any user can self-install the app on a store they control to harvest a validly-signed body/HMAC pair, then replay it with a forged shop header. No secret material or elevated privilege is required — only a normal app installation.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable representation, or otherwise cryptographically bind them to the body (e.g., concatenate them into the signed string similarly to how `AuthQuery#to_signable_string` binds `shop`/`host`/`state`), so that `HmacValidator.validate` fails if any of these fields are altered independently of the signed payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g. `orders/create`), receiving a POST to the app's webhook endpoint with a real `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's `api_secret_key` (unknown to attacker), and headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Webhook-Id: <id>`
2. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint but changes:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) [1](#0-0)  — validation succeeds because the body/HMAC pair is untouched.
4. `Registry.process` invokes the app's handler with `shop: request.shop` == `"victim-shop.myshopify.com"` [8](#0-7) , causing the app to process attacker-controlled order data as if it belonged to the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
