Based on my investigation, I found a genuine identity-binding gap: `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` never call `ShopValidator.sanitize!`/`sanitize_shop_domain` on the `shop` value, unlike every other OAuth-adjacent flow in this gem.

### Title
Oauth module never validates `shop` against `ShopValidator`, letting an attacker-supplied `shop` value receive the app's `client_secret` - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` take a caller-supplied `shop` string and use it, unvalidated, both to build the authorization redirect host and — critically — as the `Session#shop` used to target the `POST /admin/oauth/access_token` request that carries the app's `client_secret`. Every other credential-issuing flow in this gem (`token_exchange.rb`, `refresh_token.rb`, `client_credentials.rb`, `clients/graphql/storefront.rb`) calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` to constrain `shop` to `TRUSTED_SHOPIFY_DOMAINS`, but `Oauth` does not.

### Finding Description
`Oauth.begin_auth(shop:, ...)` builds the redirect target with `auth_base_uri(shop)` directly from the caller-supplied `shop` with no domain check: [1](#0-0) [2](#0-1) 

`Oauth.validate_auth_callback(cookies:, auth_query:)` then uses `auth_query.shop` to construct a `null_session` and to issue the token-exchange POST that includes `client_secret`: [3](#0-2) 

The only integrity check applied to `auth_query` is `Utils::HmacValidator.validate(auth_query)`, which recomputes the HMAC over `code, host, shop, state, timestamp` and compares against the caller-supplied `hmac` field: [4](#0-3) [5](#0-4) 

This proves the HMAC binds `shop` to the *signature*, but nowhere does the library bind `shop` to a *trusted Shopify domain*. Compare this to the sibling flows that do enforce that binding, e.g. `Auth::TokenExchange`, `Auth::RefreshToken`, `Auth::ClientCredentials`, and `Clients::Graphql::Storefront`, all of which call `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` (constrained to `TRUSTED_SHOPIFY_DOMAINS = ["shopify.com", "myshopify.io", "myshopify.com", "spin.dev", "shop.dev"]`) before using `shop` to target a request or build a session: [6](#0-5) [7](#0-6) 

The equality the gem is supposed to enforce is: `shop authorized by a valid HMAC == shop constrained to a genuine *.myshopify.com/trusted Shopify domain`. In `Oauth`, only the left side is checked; the right side is entirely absent, so `client_secret` can be POSTed to any host string that happens to pass through as `shop` (e.g. `evil.example.com`) as long as the caller can produce a matching HMAC or as long as `begin_auth` is invoked with an app-supplied, un-sanitized `shop`.

### Impact Explanation
If `shop` reaches `begin_auth`/`validate_auth_callback` without prior sanitization by the host application (which the docs do not instruct developers to perform manually — `ShopValidator` is only wired into the newer `TokenExchange`/`RefreshToken`/`ClientCredentials` grant helpers), an attacker-influenced `shop` value causes the app's `client_id`/`client_secret` and the OAuth `code` to be POSTed to an attacker-chosen host during `validate_auth_callback`'s `client.request(...)` call. This is exactly the "High: SSRF with the app's credentials / credential leakage" class in scope: the app's `client_secret` leaves the trust boundary to a host the merchant/attacker controls, rather than only ever going to `*.myshopify.com`.

### Likelihood Explanation
Likelihood is limited by the fact that `validate_auth_callback` also requires a passing HMAC over `code, host, shop, state, timestamp` using the app's real `api_secret_key`; a fully unprivileged internet attacker without the secret cannot forge that HMAC for an arbitrary `shop`. The concrete risk is that this gem provides no defense-in-depth for `shop` inside `Oauth`, unlike its own newer modules — so the gem itself does not enforce the "trusted domain" invariant it clearly considers important elsewhere, and any host application that passes a raw, attacker-supplied `shop` (e.g., from a query string on `begin_auth`) into this API without its own validation inherits the flaw silently.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth` and again on `auth_query.shop` at the top of `Oauth.validate_auth_callback`, mirroring `Auth::TokenExchange`, `Auth::RefreshToken`, and `Auth::ClientCredentials`, so that no `client_secret`-bearing request or session shop key can ever be constructed from an un-vetted domain.

### Proof of Concept
1. Host application invokes `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")` directly with a query parameter that has not been run through `ShopValidator` (the gem's docs/usage examples do not mandate this step for `Oauth`, unlike the newer grant flows).
2. `auth_base_uri(shop)` builds `"https://#{shop}/admin/oauth/authorize?..."` with no check that `shop` matches `TRUSTED_SHOPIFY_DOMAINS`. [2](#0-1) 
3. On callback, `validate_auth_callback` trusts `auth_query.shop` (bound only by HMAC integrity, not domain trust) to build `null_session = Auth::Session.new(shop: auth_query.shop)` and issues the `client_secret`-bearing POST against that shop's host. [8](#0-7) 
4. No code path in `lib/shopify_api/auth/oauth.rb` calls `Utils::ShopValidator` to close this gap, unlike `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/auth/client_credentials.rb`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
