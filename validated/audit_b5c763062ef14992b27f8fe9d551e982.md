### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing after HMAC validation passes - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop`, `topic`, and `webhook_id` are read directly from HTTP headers that are never included in the HMAC computation [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` — i.e. it authenticates the raw body bytes, then trusts `request.shop` and `request.topic` (taken straight from unauthenticated headers) to route and identify the tenant for the handler [3](#0-2) .

### Finding Description
The equality this code implicitly assumes is:

`shop_used_by_handler == shop_that_the_HMAC-authenticated_body_belongs_to`

But what is actually true is:

`HMAC verified over raw_body only` and `shop/topic/webhook_id come from separate, unsigned headers`

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined to be the raw body string only [1](#0-0) , so the signature check proves nothing about the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers — those are read verbatim from the (attacker-writable, if the raw body + valid HMAC pair can be obtained for one topic/shop) headers by `shop`, `topic`, and `webhook_id` methods [2](#0-1) .

`Registry.process` then does:
```
raise ... unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [3](#0-2) 

This means once an attacker (any unprivileged internet user who can trigger even a single legitimate webhook delivery to their own shop, or capture one over an insecure channel/log) has one valid `(raw_body, hmac)` pair, they can freely resend that exact body with a **different `shopify-shop-domain` header value** to the app's webhook endpoint. `HmacValidator.validate` will still pass — because it only checks the body bytes against the secret — while `Registry.process` will report the event as belonging to whatever `shop` the attacker put in the header, and the app-level handler is documented to be trusted for that shop identity [5](#0-4) . The topic header is likewise unauthenticated, letting an attacker route a captured signed body to a different handler by changing `shopify-topic`.

### Impact Explanation
This breaks the tenant/shop identity binding at the point where the gem hands data to the app: the `WebhookMetadata.shop` value that host apps are documented to rely on (`data.shop`, "The shop domain of the webhook" [5](#0-4) ) is not authenticated by the HMAC that the gem itself performs. Any app that follows the gem's documented pattern of trusting `data.shop`/`data.topic` for tenant-scoped processing (e.g., looking up the correct shop's session/store, or dispatching to a job queue keyed by `shop_domain`, exactly as shown in the doc's example `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [6](#0-5) ) can be made to process attacker-supplied body content under a victim shop's identity, or process a payload under the wrong topic handler. This constitutes cross-tenant data injection through the gem's own webhook verification API, matching the required Critical impact category (cross-tenant access) since it stems entirely from this gem's `HmacValidator`/`Webhooks::Request`/`Registry.process` design rather than misuse of an undocumented API.

### Likelihood Explanation
Likelihood is bounded by the need for the attacker to first obtain one valid `(raw_body, hmac)` pair — e.g., by installing the target app on their own store (any merchant can do this for public apps) and capturing a webhook Shopify sends them, or by any channel where a signed webhook body leaks. No access to `api_secret_key` or any credential is required; the attacker never needs the secret to replay the body under a spoofed `shop-domain`/`topic` header, since those headers are outside the signed material. This is fully reachable from the internet against the app's public webhook endpoint using only the gem's documented `Registry.process` verification path.

### Recommendation
Include the `shop-domain` and `topic` (and ideally `webhook-id`/`api-version`) header values in the signable material used for HMAC verification, or otherwise cryptographically bind them to the raw body before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document prominently that `HmacValidator.validate` only authenticates the body and that host apps must independently corroborate the shop identity (e.g., against the `webhook_id`'s or body's own shop reference and a known registered shop) before using `data.shop` for tenant-scoped operations.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker-shop.myshopify.com` and trigger a webhook subscription event (e.g., `orders/create`) to receive one legitimate `(raw_body, x-shopify-hmac-sha256)` pair signed by the app's real secret.
2. Replay the exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set the header `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [7](#0-6) , `Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body` [1](#0-0) , and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [3](#0-2)  — the app now processes attacker data under the victim's tenant identity.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
