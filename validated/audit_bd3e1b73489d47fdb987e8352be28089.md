This confirms the analysis: valid AccountId charset is `a-z 0-9 - _ .` only — the comma (`,`) used as `ACCOUNT_DATA_SEPARATOR` is never a valid AccountId character, and separators (`-`, `_`, `.`) cannot lead/trail/repeat but are unrelated to the comma byte.

Since `TrieKey::ContractData::account_id` is always a validated `AccountId` (enforced at the type level via `AccountId::validate`/`parse` before it can be used to construct a `TrieKey`), the encoded bytes `account_id.as_bytes()` can never contain a `,` byte. In `TrieKey::append_into` for `ContractData`, exactly one `ACCOUNT_DATA_SEPARATOR` (`,`) is written immediately after the account_id bytes and before the arbitrary attacker-controlled `key` bytes: [1](#0-0) 

`parse_account_id_from_contract_data_key` calls `next_token(account_id_prefix, ACCOUNT_DATA_SEPARATOR)`, which returns the slice up to the **first** occurrence of `,`: [2](#0-1) 

Because the account_id portion is guaranteed comma-free, the first `,` byte encountered in the raw key is always exactly the separator written by `append_into`, regardless of what arbitrary bytes (including additional commas) the attacker places in the `key` portion afterward. There's no way for an attacker-controlled `key` payload to "shift" the token boundary earlier, since the search starts at the beginning of the buffer and account_id bytes are the very first bytes. Consequently, round-tripping `TrieKey::ContractData{account_id, key}.to_vec()` through `parse_account_id_from_contract_data_key` / `parse_data_key_from_contract_data_key` will always recover the original `(account_id, key)` pair correctly — there is no cross-account attribution.

The premise in the question (that `.` and `-` being valid near the boundary could cause ambiguity) doesn't create any exploit path, since the parser only splits on the `,` byte, not on `.` or `-`; those characters are irrelevant to `next_token`'s separator search. The attacker also cannot embed a raw `,` inside their own `account_id`, since account IDs are validated at multiple points (`AccountId::validate`, `action_validation.rs::validate_action_account_id`) before ever reaching a `TrieKey`.
