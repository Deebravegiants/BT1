### Title
Missing pair-existence check in `Router.buy` lets a call proceed on an unminted/nonexistent pair - (File: `packages/contracts/src/Router.sol`)

### Summary
The CVE-2025-21982 analog is a missing NULL/zero check before use — `npcm8xx_gpio_fw` used `devm_kasprintf()`'s return value without checking it was non-null. The same defect class exists in `Router.buy()`: every sibling entry point in `Router.sol` (`getAmountOut`, `addInitialLiquidity`, `previewBuy`, `sell`, `graduate`) explicitly does `if (pairAddr == address(0)) revert PairNotFound();` right after resolving `pairAddr = factory.getPair(token, asset)`, but `buy()` omits this check entirely and proceeds straight into `_computeBuy(pairAddr, amountIn)` and `IPair(pairAddr).transferToken/swap`. [1](#0-0) 

### Finding Description
`Router.buy()` resolves the pair the same way every other function in the contract does:
```
address asset = assetTokenFor(token);
address pairAddr = factory.getPair(token, asset);
(amountInUsed, tokensOut) = _computeBuy(pairAddr, amountIn);
```
but unlike `previewBuy`, `sell`, `addInitialLiquidity`, and `graduate`, it never validates `pairAddr != address(0)` before using it. [2](#0-1) 

Compare with `sell`, which performs the exact same lookup but guards it: [3](#0-2) 

and `previewBuy`, which guards the identical `_computeBuy` call: [4](#0-3) 

If `pairAddr` is `address(0)` (e.g. a pair not yet minted, or a `token`/`asset` combination for which `Factory.createPair` was never called), `_computeBuy` calls `IPair(pairAddr).getReserves()` / `.k()` / `.tokenBalance()` on the zero address, and subsequently `IPair(pairAddr).transferToken(...)`/`.swap(...)` on the zero address. Solidity's low-level `call` to `address(0)` for a function returning `bool`/values will still "succeed" (EOA-style no-code call), so the result may silently decode as zero-valued returns rather than reverting outright — the exact "used without checking, dereferenced a null/degenerate value" shape of the kernel CVE, just realized on-chain as an unguarded external call to `address(0)` instead of a `NULL` pointer dereference.

`Bonding.buy()` currently front-loads a similar guard via `TokenInfo.creator == address(0)` / lifecycle checks before calling `Router.buy()`, and normal launches create the `Factory` pair before flipping a token's tradable lifecycle. Because of that, under the documented, single-transaction happy path this specific null-pair branch is not trivially reachable today. However, this is exactly the property the missing check should not depend on: `Router.buy()` is a `BONDING_ROLE`-gated function reachable from any code path that (a) holds `BONDING_ROLE` and (b) resolves `pairAddr` from `factory.getPair`, independent of `Bonding`'s own `tokenInfo` bookkeeping. Any future/alternate caller with `BONDING_ROLE`, or any state where `Bonding.tokenInfo[token]` and `Factory`'s `_pairs`/`ltFor` mappings diverge (the two registries are separate storage and are not kept atomically consistent by a single invariant enforced inside `Router`), removes the safety net that currently comes only from `Bonding`'s own checks rather than from `Router` itself. The asymmetry between `buy()` and its four sibling functions is itself evidence that this is an accidental omission, not an intentional trust boundary — precisely the pattern of the referenced kernel commit, which added the check to one function after it was already present in the analogous code path.

### Impact Explanation
If reached, a call into `_computeBuy`/`transferToken`/`swap` against `address(0)` can either revert with an unhelpful low-level failure (denial of service on that call path) or, depending on how the zero-return values decode, allow `_computeBuy` to compute a nonsensical `tokensOut`/`amountInUsed` from all-zero "reserves" and "k" (e.g. division by zero panics, or degenerate zero-value flows) before attempting to move real LT (`IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)`) to the zero address — a fund-loss/freezing vector consistent with the "unbacked token/LT payouts" and "permanent freezing of trader funds" impact classes in scope. Because `Router.buy` is `BONDING_ROLE`-gated and its safety currently depends entirely on the caller (`Bonding`) doing the null-check for it, this is a latent structural defect rather than a hardened invariant.

### Likelihood Explanation
Directly reachable today would require: a `BONDING_ROLE` holder other than `Bonding` calling `Router.buy` for a `token` whose `Factory.getPair` entry is unset, or a state divergence between `Bonding.tokenInfo` and `Factory`'s registries. Given `BONDING_ROLE` is intended to be Bonding-only and `Bonding` currently gates on `tokenInfo.creator`/`lifecycle` first, exploitation likelihood under the current single-contract deployment is low-to-moderate, but the missing check is a concrete code defect (not speculative) and is a straightforward regression risk for any future integration, upgrade, or additional `BONDING_ROLE` grant that reintroduces the exact scenario the sibling functions were written to guard against.

### Recommendation
Add the same guard used elsewhere in `Router.sol` to `buy()`:
```solidity
address pairAddr = factory.getPair(token, asset);
if (pairAddr == address(0)) revert PairNotFound();
```
placed immediately after resolving `pairAddr`, mirroring `sell()`, `previewBuy()`, `addInitialLiquidity()`, and `graduate()`, so `Router.buy` does not rely solely on its caller for this invariant. [5](#0-4) 

### Proof of Concept
1. Deploy `Factory`, `Router`, and grant a test address `BONDING_ROLE` on `Router` directly (simulating any future/alternate authorized caller, or a state where `Bonding`'s bookkeeping has diverged from `Factory`'s).
2. Do not call `Factory.createPair(token, asset)` for a chosen `token`/`asset` pair (so `factory.getPair(token, asset) == address(0)`).
3. From the `BONDING_ROLE` holder, call `Router.buy(amountIn, token, to)`.
4. Observe that unlike `Router.previewBuy`/`Router.sell` (which revert with `PairNotFound()` under the identical setup), `Router.buy` proceeds past the pair lookup directly into `_computeBuy(address(0), amountIn)` and then attempts `IPair(address(0)).transferToken(...)` / `.swap(...)`, demonstrating the missing guard that all four sibling functions enforce. [6](#0-5)

```text
    function buy(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 amountInUsed, uint256 tokensOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);

        (amountInUsed, tokensOut) = _computeBuy(pairAddr, amountIn);

        IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed);

        IPair(pairAddr).transferToken(to, tokensOut);
        IPair(pairAddr).swap(0, tokensOut, amountInUsed, 0);
    }

    /// @notice External view of `_computeBuy`. Returns `(amountInUsed,
    ///         tokensOut)` for a hypothetical LT-in buy of `amountIn`,
    ///         honouring the same overflow cap as `buy()`. Used by `Zap` to
    ///         pre-size the LT mint and by the frontend for buy-quote previews.
    function previewBuy(
        address token,
        uint256 amountIn
    ) external view returns (uint256 amountInUsed, uint256 tokensOut) {
        if (amountIn == 0) revert ZeroAmount();
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        return _computeBuy(pairAddr, amountIn);
    }
```
