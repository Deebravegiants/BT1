### Title
Emporium Aave position (aToken) is unaccounted for by Hinkal's balance/UTXO equality and can be drained by any unrelated caller - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only tracks balance deltas for the tokens explicitly listed in `circomData.erc20TokenAddresses`, and `Hinkal.transact`'s closing equality (`balanceDif == amountChanges + utxoAmount`) only ever inspects that same array. When a "stateless" op (CASE 2, `stack.signerAddress == address(0)`) calls `aaveV3Pool.supply(token, amount, address(this), 0)`, the deposited underlying token leaves Emporium's tracked balance and the equality nets to zero (correctly, from the contract's point of view), but the aToken minted to Emporium is never represented by any UTXO or committed anywhere. That aToken position is then a bearer asset sitting in the shared, unowned `EmporiumUpgradeable` contract that any other unprivileged caller can later drain via a second, completely unrelated `runAction` call.

### Finding Description
The broken equality is: **economic value actually held by Emporium (aToken balance) vs. value represented by outstanding UTXOs**. In `Hinkal.sol` the accounting invariant enforced per transaction is:

```
balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount
``` [1](#0-0) 

and inside `EmporiumUpgradeable.runAction`, the local equivalent is:
```
balanceChange = balancesAfter[i] - balancesBefore[i];
if (deltaAmountChanges[i] < 0) balanceChange -= deltaAmountChanges[i];
``` [2](#0-1) 

Both equalities are computed strictly over `circomData.erc20TokenAddresses` — the underlying deposit token. Aave's `supply()` transfers the underlying token out of Emporium (captured correctly, netting `balanceChange` to `0`) but mints the corresponding aToken to `address(this)` (Emporium), which is a *different* ERC20 address never listed in `erc20TokenAddresses` and never checked by `handleOut`/`getBalancesForArray`. Because `balanceChange <= 0`, `handleOut` mints no UTXO for it either [3](#0-2) . Net effect: the victim's principal is now represented purely as an aToken balance owned by the shared `EmporiumUpgradeable` contract address, with zero UTXOs anywhere referencing it.

Root cause: `EmporiumUpgradeable` is a single shared contract for all users (not a per-user wallet) for CASE 2 stateless ops, and `verifyWallet` performs **no signature/ownership check at all** when `stack.signerAddress == address(0)` — it only marks `usedMessages[circomData.emporiumMessage]` and returns [4](#0-3) . The only binding for CASE 2 ops is `circomData.calldataHash`, which is a public signal the *caller* chooses and can be satisfied by any valid ZK proof over *the caller's own* nullifiers/UTXOs — it does not bind the ops to the depositor's identity, only proves the caller owns some unrelated commitment. `onlyAllowedRecipient` only checks `msg.sender == Hinkal` (the registered recipient), not who benefits economically [5](#0-4) .

Attack flow:
1. Victim calls `Hinkal.transact` with `externalActionId` pointing at `EmporiumUpgradeable`, ops = `[{endpoint: aaveV3Pool, invokeWallet:false, value:0, callData: supply(token, amount, address(this), 0)}]`, `stack.signerAddress == address(0)`. Funds move Hinkal → Emporium (via `_externalTransact`'s `deltaAmountChanges[i] < 0` transfer) → Aave, minting aTokens to Emporium [6](#0-5) . All on-chain equalities balance to zero; no UTXO is created for the position, by design of CASE 2/aToken not being tracked.
2. Any unprivileged attacker, using their own legitimately-generated proof over their own unrelated UTXO/nullifiers (or even a zero-amount deposit), calls `Hinkal.transact` again targeting `EmporiumUpgradeable` with a crafted `EmporiumStack` whose op is `aavePool.withdraw(token, type(uint256).max, attackerRecipient)`. Since Aave's `withdraw` sends the underlying token directly to the `to` address specified (not necessarily to `msg.sender`), the attacker can set `to = attackerRecipient` and omit `token` from `circomData.erc20TokenAddresses` entirely (or include it with `deltaAmountChanges[i] == 0`), so the withdrawal never touches Emporium's tracked balance and is invisible to both `balanceChange` and `balanceDif` checks.
3. Attacker receives the victim's principal (plus yield) directly, with the proof/equality machinery seeing nothing amiss because the exfiltrated funds never appear in `erc20TokenAddresses`/`balancesBefore`/`balancesAfter` for that call.

None of the existing guards prevent this: `verifyProof`/`buildVerifierId` only prove the attacker owns *some* valid commitment, not that they're entitled to the Aave position; `rootHashExists` and `insertNullifiers` operate on the attacker's own tree state; `onlyAllowedRecipient` only gatekeeps that the call routes through Hinkal; the circuit's `inTotal + amountChanges === outTotal` constrains only the tokens declared in the (attacker-controlled) `erc20TokenAddresses`/`amountChanges` arrays for that specific call, and has no knowledge of Aave's aToken accounting at all.

### Impact Explanation
Direct theft of shielded user funds: any principal a user deposits into Aave (or any other protocol) via Emporium's stateless (`signerAddress == address(0)`) path becomes an unowned bearer asset held by the shared `EmporiumUpgradeable` contract, immediately withdrawable to an arbitrary address by any unrelated, unprivileged actor. This matches the "Critical - direct theft of shielded or in-flight user funds" category. The attack is trivially repeatable against every future deposit routed through this pattern and costs the attacker only gas plus the cost of producing one throwaway valid proof.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's capability per the rules: they need only their own valid UTXO/nullifier and the ability to craft `CircomData`/`EmporiumStack` (both attacker-controlled per the threat model). No relay, admin, or victim key is required. The victim's deposit and the attacker's theft are two independent, ordinary `Hinkal.transact` calls; the attacker merely needs to front-run/monitor the mempool or simply wait for any such deposit to land, then race to withdraw. This is highly likely to be exploitable in practice whenever Emporium is used for multi-step (deposit-then-later-withdraw) integrations rather than atomic in/out actions like swaps.

### Recommendation
- Do not allow stateless (`signerAddress == address(0)`) Emporium ops to leave value parked in the shared contract across transactions (e.g., disallow `supply`/deposit-style calls that mint a persistent balance to `address(this)` without an atomic, same-call unwind), or
- Require CASE 2 ops to be scoped to a per-user ephemeral wallet/proxy (like `IHinkalWallet` used in CASE 1) rather than the shared `EmporiumUpgradeable` contract, so aToken balances are attributable to a specific depositor, or
- Extend the balance-tracking loop in `runAction`/`Hinkal.transact` to include *all* tokens touched by arbitrary `op.endpoint` calls (e.g., via a return-value/token-registry mechanism) so that any residual balance change (including receipt tokens like aTokens) is forced into the UTXO accounting, and reject completion of the action if any tracked or untracked token balance of Emporium changed without being reflected in `outCommitments`/`amountChanges`.

### Proof of Concept
Foundry fork test (mainnet/Aave V3 fork):
1. Deploy/point to real `Hinkal`, `EmporiumUpgradeable`, `aaveV3Pool`, and `USDC`.
2. Victim: generate a valid proof (using project's proof-gen tooling) for a `Hinkal.transact` call with `externalActionId` = Emporium's id, `deltaAmountChanges[0] < 0` for `USDC`, `stack = {signerAddress: address(0), ops:[{endpoint: aaveV3Pool, invokeWallet:false, value:0, callData: abi.encodeCall(IPool.supply,(USDC, 1000e6, address(emporium), 0))}]}`. Execute; assert `aUSDC.balanceOf(address(emporium)) == 1000e6` and that no UTXO/commitment referencing this amount was inserted (i.e., `utxoSet.length == 0` for this token in the emitted event/return).
3. Attacker: independently generate a valid proof for their own trivial/unrelated UTXO (e.g., depositing 1 wei of a different or same token, or a zero-value action), craft `circomData.erc20TokenAddresses = []` (or `[USDC]` with `deltaAmountChanges[0] == 0`), `stack = {signerAddress: address(0), ops:[{endpoint: aaveV3Pool, invokeWallet:false, value:0, callData: abi.encodeCall(IPool.withdraw,(USDC, type(uint256).max, attackerRecipient))}]}`. Execute via `Hinkal.transact`.
4. Assert: `USDC.balanceOf(attackerRecipient)` increased by ~1000e6 (the victim's principal + yield), `aUSDC.balanceOf(address(emporium))` dropped to 0, and that the second `Hinkal.transact` call succeeded without reverting on `"Balance Diff Should be equal to sum of onchain and offchain created commitments"` or `BalanceChangeShouldBePositive` — proving both equalities never detected the theft.
