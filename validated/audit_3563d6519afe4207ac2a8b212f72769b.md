### Title
Unbounded-depth SCALE decode of relayed cross-chain calldata enables stack-exhaustion panic in HFT `on_accept` - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`Pallet::on_accept` (the `IsmpModule` callback invoked automatically when a relayed `PostRequest` is delivered to the hyper-fungible-token module) decodes the attacker-controlled `SubstrateCalldata::runtime_call` bytes with the plain, unbounded `codec::Decode::decode` instead of a depth-limited decoder.

### Finding Description
`on_accept` decodes the cross-chain `Message` via ABI decode, then, when `message.data` is non-empty, decodes it into `SubstrateCalldata` and finally decodes `substrate_data.runtime_call` with: [1](#0-0) 
`T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` uses the standard SCALE `Decode` trait, which recurses once per nested call variant (e.g. `Sudo::sudo { call: Box<RuntimeCall> }`, `Utility::batch`, or any other pallet call wrapping a boxed/nested `RuntimeCall`) with no depth bound.

This is exactly the bug class the codebase's own `call-decompressor` pallet was hardened against: it explicitly switched to `decode_all_with_depth_limit` with a `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT` and added a regression test (`decompress_stack_exhaustion_poc`) after discovering that naive `Decode` on nested calls could exhaust the stack: [2](#0-1) [3](#0-2) 

The hyper-fungible-token pallet's `on_accept` path never received this same fix — it calls `T::RuntimeCall::decode` directly, without any depth limit, at line 189-190. Unlike the call-decompressor pallet, this path is reachable purely by anyone dispatching a relayed cross-chain ISMP `PostRequest` targeting this module — the request body is ABI-decoded into `Message{from, to, amount, data}` and `data` is fully attacker-controlled by whoever sourced the original cross-chain send on the source chain (a token bridger/relayer-submitted message), with no depth or size restriction visible in `SubstrateCalldata`: [4](#0-3) 

### Impact Explanation
A crafted `runtime_call` payload with deeply nested boxed calls (mirroring the `decompress_stack_exhaustion_poc` PoC pattern used against the sibling pallet) can exhaust the executor's stack during decoding inside `on_accept`, which executes as part of normal ISMP message-handling/block execution. A stack overflow during runtime execution is undefined behavior for the WASM/host boundary and can crash/panic the node processing the block — a denial-of-service against the state machine that delivers this class of message, rather than a memory-safety issue with fund theft directly, but it can halt message delivery for this route (an inability to deliver messages), which is one of the explicitly in-scope impacts.

### Likelihood Explanation
High: reachable from a single relayed ISMP message with attacker-controlled `data`, requires no privilege beyond being able to send a cross-chain transfer with a calldata payload (any user of the source-chain HyperFungibleToken contract, or a relayer who forwards it), and the codebase's own prior incident (the `call-decompressor` regression) shows this exact primitive (nested `Sudo`/boxed `RuntimeCall` decoding) has previously caused a real stack-exhaustion bug in this repo.

### Recommendation
Replace the unbounded `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` call in `on_accept` with `T::RuntimeCall::decode_all_with_depth_limit(MAX_DEPTH, &mut &*substrate_data.runtime_call)` using the same bounded-depth pattern already adopted in `pallet_call_decompressor`, and add a regression test mirroring `decompress_stack_exhaustion_poc` that submits a deeply nested `Sudo`-wrapped call through `on_accept` and asserts a clean decode error instead of a stack overflow.

### Proof of Concept
Analogous to the existing `decompress_stack_exhaustion_poc` test: build `RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(...) })` nested ~1000 times, SCALE-encode it as `substrate_data.runtime_call`, wrap it in `SubstrateCalldata`, ABI-encode as `Message.data`, and deliver it via a `PostRequest` to the hyper-fungible-token module's `on_accept`. Where the call-decompressor pallet rejects this cleanly (`ErrorDecodingCall`) because of its depth-limited decode, the hyper-fungible-token module has no equivalent guard at line 189, so the same nested payload drives unbounded recursion in the plain `Decode::decode` call. #[test]
fn decompress_stack_exhaustion_poc() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		use crate::runtime::RuntimeCall;
		use codec::Encode;

		let inner_call = RuntimeCall::System(frame_system::Call::remark { remark: Vec::new() });

		let mut nested_calls =
			RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(inner_call) });

		for _ in 1..1000 {
			nested_calls =
				RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(nested_calls) });
		}

		let encoded = nested_calls.encode();
		let mut buffer = vec![0u8; 1000000];
		let compressed = zstd_safe::compress(&mut buffer[..], encoded.as_slice(), 3).unwrap();
		let final_compressed_call = buffer[..compressed].to_vec();

		let res = pallet_call_decompressor::Pallet::<Test>::decompress_call(
			RuntimeOrigin::none(),
			final_compressed_call.to_vec(),
			encoded.len() as u32,
		)
		.err()
		.unwrap();

		assert_eq!(
			res,
			DispatchError::Module(ModuleError {
				index: 10,
				error: [3, 0, 0, 0],
				message: Some("ErrorDecodingCall")
			})
		);
	});
