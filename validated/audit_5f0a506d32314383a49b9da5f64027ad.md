This vulnerability class — a live "allowed/reward" flag check performed at *claim time* instead of at *event-occurrence time*, which retroactively voids access to already-completed, legitimate work — has a direct structural analog in Hyperbridge's outbound request delivery incentive system.

### Title
Governance removing `OutboundRequestDeliveryReward` for a module after dispatch permanently voids the relayer's reward for an already-delivered request - (File: `modules/pallets/relayer/src/outbound_request.rs`)

### Summary
`process_outbound_request_delivery_claim` looks up the reward for `request.from` at claim time via a live storage read, not against any value snapshotted when the request was dispatched. If governance sets the module's reward to `0` (removing it from the allowlist) between the time a hyperbridge-originated request is dispatched/delivered and the time the relayer submits its claim, the relayer permanently loses the reward for work it already, legitimately, performed — exactly the "past loot with a now-removed distributor" pattern from the source report.

### Finding Description
The allowlist/reward check is: [1](#0-0) 

```rust
let module_id: BoundedVec<u8, ModuleIdBound> = request.from.clone().try_into()...
let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);
ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured);
```

`OutboundRequestDeliveryReward` is mutated freely at any time by governance: [2](#0-1) 

Documentation confirms zero is overloaded to mean both "reward off" and "module not on the allowlist," and that the allowlist is enforced solely at claim time with no dispatch-time snapshot: [3](#0-2) , and step 6 of the pipeline explicitly re-reads the live value: [4](#0-3) .

The delivery/claim flow has an inherent delay: a relayer must (1) see the `PostRequest` event, (2) deliver it to the destination chain, (3) wait for the destination's state commitment to land back on Hyperbridge before it can build a state proof for the claim. This is the same window described in the off-chain trigger docs: [5](#0-4) . Nothing records what the reward *was* at dispatch time — `RequestCommitments` only proves the request was dispatched, not the fee terms it was dispatched under: [6](#0-5) .

Consequently, if governance runs `set_outbound_request_delivery_reward(module_id, 0)` (e.g., pausing a deprecated/misbehaving module, or simply reallocating incentive budget) any time after a request was dispatched under a non-zero reward but before the relayer's claim lands, the claim is rejected with `OutboundRequestNoRewardConfigured` — permanently, since there is no other path to redeem that specific already-delivered commitment.

### Impact Explanation
This is a permanent loss of legitimately-earned relayer compensation for already-performed, provable delivery work — the on-chain equivalent of the "past loot" being unclaimable in the source report. Relayers deliver hyperbridge-originated system messages (host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's own withdrawal requests) expecting payment under the reward rate active at dispatch time; that expectation can be silently and permanently invalidated by an unrelated, later governance action, with no recovery mechanism (the commitment is not marked claimed, so relayers may repeatedly and fruitlessly attempt to submit the now-worthless claim). This falls squarely within "relayer fee and reward accounting" in scope.

### Likelihood Explanation
Medium. This does not require a malicious actor — it is triggered by ordinary, permitted governance use of `set_outbound_request_delivery_reward` (e.g., disabling a module's incentive, rebalancing treasury allocation), the same class of routine administrative action as the original Paladin `removeDistributor` call. Given BEEFY-driven cross-chain finality delays between delivery and claim eligibility, there is a realistic window during which such a governance update can land and strand an already-delivered claim.

### Recommendation
Snapshot the reward amount at dispatch time (e.g., store `(commitment -> reward_at_dispatch)` when the request is recorded in `RequestCommitments`, or have dispatching pallets pass the current reward through as part of the dispatch), and have `process_outbound_request_delivery_claim` pay out based on that snapshot rather than re-reading the live `OutboundRequestDeliveryReward` map. Alternatively, gate only *new* dispatches on the live allowlist value (as is arguably intended) while allowing claims for already-dispatched, already-delivered commitments to proceed against the value captured at dispatch time, mirroring the suggested fix of checking accrued state (`totalQuestPeriodRewards[...] != 0`) rather than only the current allowlist flag.

### Proof of Concept
1. Governance calls `set_outbound_request_delivery_reward(module_id, R)` with `R > 0`, enabling rewards for `module_id`.
2. A pallet dispatches a `PostRequest` with `from = module_id`; it lands in `RequestCommitments` and is delivered by a relayer to the destination chain.
3. Before the destination's state commitment propagates back to Hyperbridge (or before the relayer submits its claim), governance calls `set_outbound_request_delivery_reward(module_id, 0)`.
4. The relayer submits `claim_outbound_request_delivery_reward` with a valid state proof of delivery; the check at `modules/pallets/relayer/src/outbound_request.rs:148-149` reads the now-zero reward and rejects with `OutboundRequestNoRewardConfigured`, even though `RequestCommitments` and the destination's `RequestReceipts[commitment]` both prove genuine delivery occurred while the reward was non-zero. The relayer's earned reward is permanently unclaimable.

```markdown

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.

No changes to pallet-hyperbridge or to any of the system-message dispatch sites. The reward is decoupled from the dispatch path and paid out at claim time against a destination state proof.
```

Three practical pieces:

- **Distinguishing hyperbridge-originated requests.** Receipts whose `query.source_chain == coprocessor` are forwarded; everything else is ignored.
- **Carrying the request.** Each `PendingRequestDeliveryClaim` carries the full `PostRequest` because the pallet hashes it on chain to derive the commitment and reads `request.from` to key the allowlist. The tesseract trigger extracts post requests from the outgoing batch before submit, indexes them by commitment, and pairs them back to receipts after the submit returns.
- **Waiting for the state commitment.** Same wait the existing accumulate_fees flow uses.

Backpressure: the claim channel uses `try_send` with a 512-slot buffer. If the channel is saturated the trigger drops the channel push, but the DB row persisted right above the send survives and is replayed on the next trigger. The DB is the source of truth.
