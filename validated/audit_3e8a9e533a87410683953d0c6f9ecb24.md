## Title
Order-level solver-selection intent bypassed by a global, mutable `_params.solverSelection` flag read at fill-time - (File: evm/src/apps/IntentGatewayV2.sol / evm/src/apps/intentsv2/IntentsBase.sol)

## Summary
`fillOrder()` gates the session-key/solver-authorization check behind the *current* value of the gateway-wide `_params.solverSelection` boolean rather than any state captured at order-placement time. A user who places an order with `order.session` set (intending to enforce exclusivity for the winning bidder) has no on-chain guarantee that this protection is still active by the time the order is filled — the check is skipped entirely whenever the live flag reads `false`, exactly the "changes between signing and execution" class of defect the source report flags (a single boolean/module check that ignores everything that could have shifted since the signed intent was produced).

## Finding Description
`fillOrder()`'s only defense against an unauthorized solver claiming a selection-protected order is: [1](#0-0) 

This is conditioned entirely on the *live* `_params.solverSelection` flag, not on anything bound at `placeOrder()` time. `Order.session` is stored in the order (and used to build the commitment), but nothing in `placeOrder()` freezes "solver selection was required for this order": [2](#0-1) 

`_params` (including `solverSelection`) is a single mutable struct that cross-chain governance can update on the destination gateway between the moment a user places an order (and off-chain solvers begin auctioning/signing bids against the session key) and the moment a solver actually calls `fillOrder()`: [3](#0-2)  The `Params` struct carries `solverSelection` as one global on/off switch for the whole gateway: [4](#0-3) 

This is structurally the same defect described in the source report for `validatePostExecutorTransaction()`: a critical authorization check inspects only *one* piece of *current* on-chain state (there, `isModuleEnabled`; here, `_params.solverSelection`) instead of validating that the state a party actually signed against still holds at execution time. If the flag flips to `false` between order placement and fill (a legitimate `UpdateParams` cross-chain governance message can arrive at any point, independent of any specific order's lifecycle), `fillOrder()`'s `if (_params.solverSelection) { ... }` branch is skipped in its entirety — the `Unauthorized()` revert path is simply never reached — and *any* solver, not the one the user's session key selected, can fill the order and collect its (often favorable, auction-set) terms.

## Impact Explanation
This breaks the core guarantee `solverSelection` exists to provide: exclusivity of a specific, user-authorized solver for a specific order. When the flag transitions off mid-flight:
- Orders that were placed expecting solver-selection protection (with off-chain auctions run under that assumption, and a winning bid selected and signed by the session key) become fillable by *any* solver, including one who never won the auction and never obtained a valid `SelectSolver` signature.
- A solver who observes a pending selection-protected order can front-run the legitimately selected solver and capture the fill (and its output-token terms) for themselves, since the on-chain enforcement momentarily vanishes.
- This is an unauthorized app action / broken access-control guarantee on real user funds already escrowed in the gateway, reachable purely by an unprivileged solver submitting a normal `fillOrder()` transaction once the window opens.

## Likelihood Explanation
The window requires a governance-issued `UpdateParams` to land while orders that rely on `solverSelection` are still pending — this is not attacker-triggered, but it is entirely plausible in normal operation (e.g., governance disabling solver-selection network-wide for maintenance, fee changes, or a phased rollout while in-flight orders still expect the old behavior; the `ParamsUpdate` body doesn't carry any awareness of currently-pending orders). Once that window exists, *any* unprivileged solver can exploit it with a single ordinary `fillOrder()` call — no special access, no forged proofs, no consensus manipulation required.

## Recommendation
Bind the solver-selection requirement to the order itself rather than to the live gateway-wide flag. Options:
- Capture `solverSelection` in the order/commitment at `placeOrder()` time (e.g., stamp `order.solverSelectionRequired = _params.solverSelection` before hashing, mirroring how `order.nonce`/`order.source` are already finalized on placement) and check that captured value at `fillOrder()` instead of the live `_params.solverSelection`.
- Alternatively, key the check off `order.session != address(0)` rather than the global flag: if a user set a session key, always require authorization regardless of the gateway's current `solverSelection` setting, since the presence of a non-zero session key is itself the user's expressed intent for exclusivity.
- More generally, any parameter that participates in an off-chain-signed commitment (auction bids, session-key selections) must be validated against the value in force when that commitment was made, not against whatever value happens to be live when the message finally executes.

## Proof of Concept
1. Deploy `IntentGatewayV2` with `Params.solverSelection = true`.
2. User calls `placeOrder(order, graffiti)` with `order.session = sessionKeyAddress`. Solvers begin auctioning; a winning solver `S1` obtains a valid `SelectSolver` EIP-712 signature from the session key and calls `select()` (staging `tstore(commitment, keccak256(S1, sessionKey))`).
3. Before `S1` submits `fillOrder()`, Hyperbridge governance dispatches a legitimate `UpdateParams` request (via `IntentsBase._updateParams`) setting `solverSelection = false` for unrelated reasons (fee/config change). This is processed by `onAccept` and updates `_params` in place, exactly as exercised in `testOnAcceptUpdateParams`: [5](#0-4) 
4. An unrelated solver `S2` (who never won the auction, has no valid `SelectSolver` signature, and never called `select()`) calls `fillOrder(order, options)` directly. Because `_params.solverSelection` is now `false`, the `if (_params.solverSelection) { ... }` block in `fillOrder()` is skipped entirely, `_filled[commitment]` is still `address(0)`, and the fill proceeds — `S2` claims the order that the user had exclusively authorized `S1` to fill.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
