### Title
`EvmHost.dispatch()` values the native-token relayer fee off a single-block Uniswap V2 spot price with a fixed `amountOut`, letting an unprivileged dispatcher get the fee-token swap executed against a manipulated pool - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept native token and swap it for the protocol's `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, sourcing the exchange rate straight from the router's live reserves in the same transaction, with no TWAP or oracle bound, mirroring the LP/AMM spot-price mispricing bug class described in the reference report.

### Finding Description
Every native-token-funded dispatch path in `EvmHost.sol` performs an on-chain swap priced directly by the configured `UniswapV2Router02`'s instantaneous reserves: [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` computes `amountIn` for the fixed `fee`/`amount` output using the pair's reserves at execution time (`amt = reserveIn * amountOut / (reserveOut - amountOut)` per Uniswap V2 math) — exactly the "TVL/reserve-derived price" pattern flagged in the referenced report (`amt0*price0 + amt1*price1` from live reserves). Any address (the message dispatcher itself, or an unrelated actor front-running/backrunning the same block) can move the `WETH/feeToken` pair's reserves immediately before this call executes, since the router call and the swap happen atomically inside the dispatcher's own transaction with `block.timestamp` as the deadline (no slippage/price bound is enforced by `EvmHost` beyond the caller's own `msg.value`).

The SDK's own commentary makes the same point about the resulting fragility: the off-chain `quote()`/`quoteNative()` helper explicitly warns that this on-chain path is "vulnerable to sandwich attacks": [4](#0-3) 

and elsewhere the SDK pads swap inputs specifically because "pool reserves drift between quote and execution": [5](#0-4) 

`quoteNative()` itself reads the exact same unprotected `getAmountsIn` spot quote off the host's configured router before the dispatcher submits `msg.value`: [6](#0-5) 

This is structurally identical to the reported bug class: a protocol-critical monetary amount (here, how much native ETH must be spent to cover a fixed feeToken output, i.e., the relayer-fee escrow that gets refunded on timeout) is derived from a single AMM pool's live reserves, manipulable within one block/transaction, with no time-weighting, external oracle check, or slippage guard enforced by the contract itself.

### Impact Explanation
- Because `swapETHForExactTokens` fixes the *output* amount (`post.fee`/`get.fee`/`amount`) and only bounds the maximum ETH spent by `msg.value`, an attacker who manipulates the WETH/feeToken pool's reserves downward (cheapens WETH in feeToken terms) forces the dispatch to consume more of the dispatcher's `msg.value` than a fair price would require, with any leftover ETH refunded to the caller by the router — so a dispatcher who under-funds `msg.value` after such manipulation will have their transaction revert, and one who over-funds effectively donates the manipulated slippage to the pool/attacker via the swap.
- Because `_requestCommitments[commitment].fee` records the resulting feeToken amount (not the ETH spent), a manipulated swap does not corrupt the escrowed relayer fee's later refund/payout logic in feeToken terms, but it does mean the ETH cost quoted off-chain via `quoteNative()` can silently diverge from what is charged on-chain in the same block, causing either reverted dispatches (denial of service on message submission) or ETH loss to sandwich/backrun attackers when reserves are thin.
- This affects the "unprivileged message dispatcher" path directly reachable from any `EvmHost.dispatch()`/`fundRequest()` call — exactly the class of actor in scope — and is a real, non-mocked, non-admin path shipped in the production `EvmHost.sol`.
- Severity is bounded by the fact the escrowed `feeToken` amount itself is fixed (not derived from the manipulated price) and any full loss is capped to one dispatcher's ETH slippage per manipulated block, not a systemic drain of protocol-held funds — this differentiates it from the referenced High-severity LP-price report, which directly mispriced a collateral/loan valuation. Given the bound, reachable, single-transaction nature of the manipulation and its potential for real ETH loss/DoS on message dispatch, this is best characterized as **Medium** severity.

### Likelihood Explanation
High for chains with thin native/feeToken liquidity on the configured `uniswapV2` router: manipulating reserves within a single block (via flashloan or simply front-running/back-running the dispatcher's transaction) is a well-known, cheap, zero-risk technique, and `EvmHost` performs no minimum-output/maximum-input check beyond the caller-controlled `msg.value`. Likelihood is lower on deep, highly-liquid pools, but the contract provides no protection regardless of pool depth.

### Recommendation
- Do not let `EvmHost` derive the effective swap rate purely from the spot reserves of a single router call executed atomically with the dispatch. Either:
  - Require dispatch callers to also pass an explicit `amountInMax` (or minimum acceptable output) so `swapETHForExactTokens` can revert on excessive slippage instead of silently consuming the manipulated rate, and/or
  - Source a TWAP or externally-verified reference price to sanity-check the router's live quote before or after the swap, rejecting dispatches whose realized native-token cost deviates beyond a configurable threshold from that reference (the same remediation direction cited in the underlying report, adapted from spot-reserve pricing to a manipulation-resistant reference).
  - Document/enforce that native-token dispatch should only be used against deep, non-manipulable pools, or restrict it to feeToken-denominated dispatch (`dispatchWithFeeToken`) by default for security-sensitive integrations.

### Proof of Concept
1. Identify an `EvmHost` deployment whose configured `uniswapV2` router's WETH/feeToken pair has shallow liquidity (`evm/src/core/EvmHost.sol` lines 921-932, 974-985, 1031-1042 all read `_hostParams.uniswapV2` and swap through it).
2. In the same block as a victim's `dispatch(DispatchPost)`/`dispatch(DispatchGet)`/`fundRequest()` call (which the victim built its `msg.value` for based on an off-chain `quoteNative()` call using the router's pre-manipulation reserves, `sdk/packages/sdk/src/chains/evm.ts` lines 746-777), the attacker submits a large swap against the same WETH/feeToken pair to shift reserves.
3. The victim's `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` call now requires materially more ETH than `msg.value` was sized for at quote-time (frontrun) — causing the dispatch to revert (denial of service on message submission) — or, if the attacker instead backruns, the victim's transaction executes at the manipulated (cheaper WETH) price, letting the attacker's subsequent trade extract the resulting slippage from the pool that the victim's outsized purchase created (sandwich profit at the victim's ETH's expense).
4. Repeat per block as desired; no risk to the attacker beyond gas and any capital used to move reserves (recoverable via flashloan), matching the "inflate/deflate within 1 block, no risk" characterization of the referenced report's bug class.

	async quoteNative(request: IPostRequest | IGetRequest, fee: bigint): Promise<bigint> {
		const totalFee = (await this.quote(request)) + fee
		const feeToken = await this.getFeeTokenWithDecimals()
		// Quote against the router the host actually swaps through on dispatch,
		// which may price differently than the canonical Uniswap V2 router.
		const hostRouter = await this.publicClient.readContract({
			address: this.params.host,
			abi: EvmHost.ABI,
			functionName: "uniswapV2Router",
		})
		return this.getAmountsIn(totalFee, feeToken.address, request.source, hostRouter)
	}

	/**
	 * Given a desired output amount of a token, returns how much native is needed as input.
	 * Uses the chain's Uniswap V2 router (or `router` when provided): WETH → tokenOut path.
	 */
	async getAmountsIn(amountOut: bigint, tokenOutForQuote: HexString, chain?: string, router?: HexString): Promise<bigint> {
		const chainId = chain ?? `EVM-${this.params.chainId}`
		const v2Router = router ?? this.configService.getUniswapRouterV2Address(chainId)
		const WETH = this.configService.getWrappedNativeAssetWithDecimals(chainId).asset
		const v2AmountIn = await this.publicClient.simulateContract({
			address: v2Router,
			abi: UniswapRouterV2.ABI,
			// @ts-ignore
			functionName: "getAmountsIn",
			// @ts-ignore
			args: [amountOut, [WETH, tokenOutForQuote]],
		})

		return v2AmountIn.result[0]
	}
