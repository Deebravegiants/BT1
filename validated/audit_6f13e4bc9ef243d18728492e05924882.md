### Title
Webhook shop-domain identity is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` value used for tenant identification from the raw `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body. The shop identity is therefore never cryptographically bound to the payload that was authenticated.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `#shop` is read straight from an unauthenticated header: [2](#0-1) .

`Registry.process` validates the HMAC using exactly this `to_signable_string` value, and then immediately forwards the *header-derived, unauthenticated* `request.shop` to the app's handler as the trusted tenant identifier: [3](#0-2) .

This breaks the intended identity binding:
`shop authenticated by HMAC == shop stored/used as tenant key`

In reality: `shop covered by HMAC (∅, body only) ≠ shop used as tenant key (header value)`.

Because the HMAC only proves "this body was produced using our client_secret for *some* legitimate webhook event," and not "this body belongs to shop X," any party who can obtain one validly-signed webhook (trivially achievable by an unprivileged attacker who installs the app on their **own** store and receives real webhook deliveries) can replay that exact body to the app's webhook endpoint while substituting an arbitrary victim's shop domain in the `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` (which only checks the body signature) will still pass: [4](#0-3) , and the forged `shop` value is handed to the app's `WebhookHandler` as if verified.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is a legitimate (but unprivileged) merchant for their own store can make the host application process webhook data — order changes, uninstall notifications, GDPR events, shop updates, etc. — as if it belonged to a different, victim shop, without ever needing the victim's credentials, session, or access token. Any app logic that keys state exclusively off `WebhookMetadata#shop` (which is precisely the value the gem tells developers is "verified" once `Registry.process` returns without raising) can be corrupted or manipulated cross-tenant. This matches the Critical "cross-tenant access" impact category, since the tenant boundary is what's being crossed using only a legitimately-obtained-but-misattributed signed payload.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker must (a) sign up for the target app on a shop they control to receive a genuinely-HMAC-signed webhook, and (b) know/predict a topic+body shape that is meaningful when replayed under another shop's identity (e.g., an `app/uninstalled` or generic update webhook whose body doesn't itself embed a shop reference verified elsewhere by the host app). No secrets, tokens, or privileged access are required — only normal merchant-level interaction with the app is needed to harvest a signed sample.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-covered signable string, or otherwise cryptographically bind the shop identity to the payload before trusting it, e.g. by having `to_signable_string` incorporate `shop-domain` alongside the raw body, or by cross-checking the header shop against a shop already known/registered for that specific webhook subscription rather than trusting the header unconditionally.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g. `orders/create`) to the app's endpoint. They capture the raw HTTP request, including body `B` and the valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(secret, B)`.
2. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body: `request.shop` returns `"victim.myshopify.com"`; `request.hmac` returns the decoded `H`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` and compares to `H` — this matches since `B` is unchanged, so validation passes: [3](#0-2) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes `B`'s contents as if genuinely originating from the victim shop, even though it never came from Shopify for that tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
