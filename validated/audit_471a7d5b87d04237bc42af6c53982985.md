Confirmed: `EcdsaBeefy.verifyParachainHeaderProof` (`evm/src/consensus/EcdsaBeefy.sol:198-229`) calls `Codec.DecodeHeader(para.header)` **before** the merkle-multiproof authentication of `para.header` against `headsRoot` (the `MerkleMultiProof.VerifyProof` call happens afterward, at line 224). This means the digest-count field inside `para.header` is fully attacker-controlled at the time it's decoded, unauthenticated by any hash/signature check yet.

### Title
Unbounded Memory Allocation in BEEFY Header Digest Decoding Before Proof Authentication - ([File: evm/src/consensus/Codec.sol])

### Summary
`Codec.DecodeHeader` (`evm/src/consensus/Codec.sol:71-102`) reads an attacker-supplied SCALE compact-encoded digest count and immediately allocates `Digest[] memory digests = new Digest[](length)` with no upper bound, before any authentication of the header bytes has occurred.

### Finding Description
`DecodeHeader` decodes:
```solidity
uint256 length = ScaleCodec.decodeUintCompact(slice);
Digest[] memory digests = new Digest[](length);
for (uint256 i = 0; i < length; i++) { ... }
``` [1](#0-0) 

`decodeUintCompact` can decode values up to `2^53` (mode 3), so `length` is attacker-controllable up to that range [2](#0-1) .

Crucially, `EcdsaBeefy.verifyParachainHeaderProof` calls `Codec.DecodeHeader(para.header)` and iterates the resulting header **before** `MerkleMultiProof.VerifyProof(headsRoot, proof.proof, leaves, proof.leafCount)` authenticates `para.header` against the trusted `headsRoot`: [3](#0-2) 

This is the naive/ECDSA BEEFY consensus path reachable from `HandlerV2.handleConsensus` → `EvmHost` → `EcdsaBeefy.verify`, which any relayer can invoke with an unsigned/permissionless consensus proof (`RelayChainProof`, `ParachainProof`) as shown in the mainnet-rotation relayer flow calling `HandlerV2::handleConsensus` [4](#0-3) . Because decoding happens before the merkle-proof check, an attacker can supply a `para.header` whose digest-count compact integer is enormous, forcing the EVM to attempt allocating and looping over an oversized `Digest[]` array purely to fail the authentication check later — but the gas/memory cost of the allocation and loop is incurred first.

In contrast, the SP1/zk BEEFY path (`SP1Beefy.sol`) authenticates header content via the zk proof's public inputs (`keccak256(proof.headers[i].header)` is committed into `publicInputs` verified by `verifier.verifyProof`) before/alongside decoding, so that path is not equally exposed to this pattern — the ECDSA path is the one lacking pre-decode authentication.

### Impact Explanation
Each malicious `para.header` in `ParachainProof.parachains[]` can carry an oversized/malformed digest-count, forcing EVM memory expansion and a bounded-but-costly loop for every entry, multiplied by `proof.parachains.length`. In the worst case this burns gas up to the block gas limit for the submitting relayer's own transaction (reverting after doing wasted work), and because Solidity memory-expansion gas cost is quadratic, a moderately large declared `length` can push a transaction to hit the gas limit before the legitimate merkle-proof check that would have rejected the forged header is ever reached. This degrades the consensus-update path's usability/predictability (resource exhaustion of the calling relayer's gas budget, and repeated failed txs can be used to grief/block honest relayers' transactions in the mempool or make legitimate consensus updates unreliable), matching CWE-770 (uncontrolled resource allocation) from the reference advisory. Impact is bounded to gas/DoS of that call — no funds are stolen and consensus state itself is not corrupted since the merkle check still fails afterward.

### Likelihood Explanation
Likelihood is limited: while `Codec.DecodeHeader` is reachable by anyone submitting a naive BEEFY consensus proof through `HandlerV2.handleConsensus`, the caller pays the gas for their own oversized decode attempt, and the transaction ultimately reverts at the merkle-proof check. This makes it self-inflicted (griefing at most the caller's own tx, or requiring the caller to intentionally target a large gas cost to trigger a revert late) rather than a high-likelihood attack that damages the protocol or third parties directly. There is no way for an unprivileged attacker to force a victim to pay this cost; they can only waste their own gas or, at best, submit crafted transactions that fail late enough to consume most of a self-chosen gas limit.

### Recommendation
In `evm/src/consensus/Codec.sol`, bound `length` in `DecodeHeader` (and `decodeDigestItem`'s inner `length`) to the remaining bytes in `slice` before allocating, e.g. `require(length <= slice.data.length - slice.offset)`, so a malformed compact integer cannot request an allocation larger than the actual input can support. Additionally, consider reordering `EcdsaBeefy.verifyParachainHeaderProof` so `para.header` is authenticated (merkle-multiproof against `headsRoot`) before being passed to `Codec.DecodeHeader`, eliminating decode-before-auth exposure entirely.

### Proof of Concept
1. Craft a `ParachainProof.parachains[0].header` byte string that is valid up through `extrinsicsRoot` (96 bytes) but whose digest-count compact-integer field encodes a very large value (e.g., mode-3 encoding of a value near `2^53`), with no actual digest bytes following.
2. Submit this as part of a `BeefyConsensusProof` payload to `HandlerV2.handleConsensus` targeting the naive/ECDSA `EcdsaBeefy` route.
3. `EcdsaBeefy.verifyParachainHeaderProof` calls `Codec.DecodeHeader(para.header)`, which allocates `Digest[](length)` for the huge `length` and attempts to loop, consuming gas disproportionate to the input size, before the `MerkleMultiProof.VerifyProof` authentication check (which would have rejected the forged header) is ever reached.
