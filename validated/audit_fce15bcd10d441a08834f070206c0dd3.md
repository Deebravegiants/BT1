### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` passes, and then hands the caller-supplied `shop` header straight through to the app's handler as the tenant identifier. The HMAC, however, is computed only over the raw request body — the `shop`, `topic`, `webhook-id` and `api-version` headers are never part of the signed data. This is the exact bug class flagged in the report (a field acted on but not covered by the authentication check), applied here to the shop/tenant-binding field instead of a missing modifier.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC — it never touches `shop`: [3](#0-2) 

`Registry.process` performs the HMAC check and, immediately after it passes, constructs `WebhookMetadata` using `request.shop` as the tenant identifier passed to the app's handler, with no separate verification that this shop is the one that actually signed/owns the payload: [4](#0-3) 

The equality the code implicitly assumes is:
`shop_bound_by_HMAC(request) == shop_used_as_tenant_key(WebhookMetadata)`

In reality:
`shop_bound_by_HMAC(request) = ∅` (nothing — HMAC covers only `@raw_body`)
`shop_used_as_tenant_key(WebhookMetadata) = request.shop` (an unauthenticated header)

So the equality is false: the `shop` value consumed by the handler is never part of what the HMAC actually authenticates.

### Impact Explanation
Any party capable of obtaining one valid `(raw_body, hmac)` pair — for example by installing the app on their own trial/development store and capturing a legitimate webhook delivery — can replay that exact body and HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` / `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field names an arbitrary tenant of the attacker's choosing. Any host application that uses this `shop` value as the tenant/session key (a very common and expected usage pattern for Shopify webhook handlers) will process a webhook payload it "authenticated" via HMAC while attributing/binding it to the wrong merchant — a cross-tenant identity-binding bypass mediated entirely by this gem's `Registry`/`Request`/`HmacValidator` code.

### Likelihood Explanation
This requires no possession of the app's `client_secret`/`api_secret_key`: an attacker only needs to be able to obtain one legitimately-signed webhook (trivial for anyone who can install or trial the app on a shop they control) and can then freely relabel the tenant for that captured payload. The gem gives no indication to the integrator that the `shop` field is unauthenticated, since the check that "protects" webhook processing (`Errors::InvalidWebhookError` on HMAC failure) creates the impression that the whole request, including sender-identifying headers, was verified.

### Recommendation
- Include `shop` (and ideally `topic`/`webhook_id`) in the signed material used by `HmacValidator`, or otherwise cryptographically bind the shop header to the payload before it is exposed via `WebhookMetadata`.
- At minimum, document prominently (and enforce in `Registry.process`) that the `shop` field is not covered by the HMAC and that consumers must cross-check it against a known/subscribed shop (e.g., an existing session) before trusting it as a tenant key, and consider raising an explicit error path in `Registry.process` if no matching, previously-authenticated session exists for `request.shop`.

### Proof of Concept
1. Install/trial the target app on shop `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the raw request: body `B`, header `X-Shopify-Hmac-Sha256: H`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the request unmodified except for the shop header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, keeping body `B` and HMAC `H` identical.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, so validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload was never signed for that shop — any app logic keyed on this `shop` value now operates on the wrong tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
