## Analog Vulnerability Found

### Title
Unchecked ERC20 return value in Tron `IntentGatewayV2` allows silent transfer failure while escrow accounting proceeds as successful - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports and even declares `using SafeERC20 for IERC20`, but its `withdraw()` function and the `SweepDust` handler inside `onAccept()` bypass `safeTransfer` and instead perform raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, checking only that the call did not revert (`success`) and never decoding/validating the returned boolean.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the escrow-release path used for both `RedeemEscrow` and `RefundEscrow` incoming ISMP messages is: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    _orders[body.commitment][token] -= amount;
    ...
}
```

For any TRC20/ERC20-style token that follows the non-reverting failure pattern (returns `false` instead of reverting, e.g. tokens like `ZRX` on EVM, or Tron TRC20 tokens with similar semantics), the low-level `.call` itself succeeds (`success == true`) even though the token transfer did not move any value — because `success` here only reflects that the callee did not revert, not that the ABI-encoded return data decoded to `true`. The function then unconditionally decrements the escrowed balance (`_orders[body.commitment][token] -= amount`) and, on `finalize`, marks the order filled (`_filled[body.commitment] = beneficiary`) and emits `EscrowReleased`/`EscrowRefunded`, as if the beneficiary was paid.

The same unchecked pattern also appears in the `SweepDust` handler inside `onAccept`: [2](#0-1) 

This is reachable by any relayer delivering a normal `RedeemEscrow`/`RefundEscrow`/`SweepDust` ISMP message once a solver has filled (or a user has cancelled) an intent order — no privileged role is required to trigger the code path; it fires on every settlement.

By contrast, the sibling non-Tron contract `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntentsBase.sol` consistently use `IERC20(token).safeTransfer(...)` / `safeTransferFrom(...)` for the equivalent escrow release logic: [3](#0-2) 

confirming that the Tron variant's raw `.call` pattern is a regression/inconsistency rather than an intentional design choice, since `SafeERC20` is imported and aliased in the very same Tron file but simply not used at these call sites.

### Impact Explanation
This results in permanent value loss for order beneficiaries: escrow that should back a user's or solver's redemption is deducted from `_orders[...]` and the order is marked filled/refunded, but the underlying tokens never leave the gateway contract. The beneficiary receives nothing and cannot re-claim the escrow (since `_orders[commitment][token]` is already zeroed and `_filled[commitment]` is already set, so any retry reverts with `UnknownOrder`/already-filled checks). This is a concrete, permanent freezing/loss of escrowed intent funds triggered by ordinary message delivery, meeting the Medium/High severity bar for fund loss.

### Likelihood Explanation
Likelihood depends on whether any of the tokens configured as input/output assets or the protocol `feeToken` on the Tron deployment follow the non-reverting-on-failure ERC20/TRC20 semantics. Given Tron's TRC20 ecosystem includes tokens with such quirks (and the reported bug class explicitly targets this class of token), and that the escrow/settlement flow is executed unconditionally for every filled or refunded order, likelihood is non-trivial for any deployment that does not exclusively allowlist tokens with 100%-reverting transfer semantics.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (lines 706, 720) and in the `SweepDust` branch of `onAccept()` (line 674) with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with the rest of the codebase (`IntentsBase.sol`, `EvmHost.sol`, `WrappedHyperFungibleTokenUpgradeable.sol`), so that both call-revert and false-return failure modes cause the settlement transaction to revert instead of silently succeeding.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with an input/output token that returns `false` on a failed `transfer` instead of reverting (e.g., insufficient balance or a blocklisted recipient on a non-standard TRC20/ERC20).
2. A solver fills an order or a user cancels/refunds an order, causing an ISMP `RedeemEscrow`/`RefundEscrow` message to be dispatched and eventually delivered to `onAccept` → `withdraw`.
3. Arrange for the token's `transfer` to return `false` (e.g., beneficiary momentarily fails a custom transfer restriction, or the gateway's tracked balance and true balance diverge due to any external interaction) so the low-level `.call` succeeds without moving tokens.
4. Observe `_orders[commitment][token]` is decremented, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — despite the beneficiary's token balance being unchanged, permanently losing the escrowed funds.
