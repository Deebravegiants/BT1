### Title
Webhook `shop` attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but then hands the handler a `shop` value taken from an HTTP header that is not part of the signed data at all. This breaks the binding `shop authenticated == shop acted upon`, letting anyone who can produce one valid `(body, hmac)` pair (e.g. a merchant receiving genuine webhooks for their own shop) replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Webhooks::Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`, i.e. the body, and never touches the shop header: [3](#0-2) 

`Registry.process` performs exactly one authentication check — the HMAC over the body — and then immediately forwards the unauthenticated `request.shop` to the app's handler as the tenant identifier: [4](#0-3) 

Because `client_secret` (and thus the HMAC key) is shared by every shop that has installed the app, and because the `shop-domain` header is completely outside the signed content, a party who legitimately receives one authentic webhook `(body, hmac)` pair for their own shop can replay the identical body and HMAC to the app's public webhook endpoint with a forged `shop-domain` header pointing at any other shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the body signature, and `WebhookMetadata.shop` — the field application code is documented to use for tenant identification — is populated from the forged header.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to key shop-scoped lookups (session retrieval, database writes, GDPR redaction targets, etc.) can be made to apply another shop's genuinely-signed webhook payload to an attacker-chosen shop context. This is a cross-tenant data-confusion vector reachable by an unprivileged internet user who only needs to be a legitimate (even free-trial) merchant of the app to obtain one authentic body/HMAC sample, then replay it against arbitrary shop identifiers.

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint exposed directly by the merchant's app; nothing in the gem enforces that requests originate from Shopify's own infrastructure. Obtaining a valid `(body, hmac)` pair requires only installing the app on any single shop and capturing one delivered webhook — a low-effort, no-privilege action. Replaying that captured request with a different `shop-domain` header is trivial.

### Recommendation
Bind the shop identity into the authenticated material, e.g. by requiring the `Registry.process` (or `HmacValidator`) call to receive the expected shop out-of-band (e.g. matched against the app's own webhook registration/session store) rather than trusting the unauthenticated `shop-domain` header, or by rejecting/flagging when the header-derived shop cannot be independently corroborated by the caller before invoking the handler.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` and trigger any webhook topic the app subscribes to (e.g. `orders/create`).
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header of that delivery — this is a valid `(body, hmac)` pair signed with the app's `client_secret`.
3. Replay an HTTP POST to the app's webhook endpoint using the identical body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (called from `Registry.process`) succeeds because it only checks the body signature; the app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's order data>, ...)`, causing the host app to process attacker-controlled data under the victim shop's tenant context.
