### Title
Unrelated `T::Currency::transfer` inside `pallet-nfts::do_claim_swap` can drain a `pallet-asset-conversion` pool's sovereign account when the pool's native currency backs the NFT price - ([File: substrate/frame/nfts/src/features/atomic_swap.rs])

### Summary
`do_claim_swap` fetches `send_item.owner` / `receive_item.owner` fresh from `Item` storage at claim time and unconditionally calls `T::Currency::transfer` between them for the swap price, with no restriction on which accounts can be named. Because NFT ownership can be transferred to *any* `AccountId` — including a deterministically-derivable, keyless pool sovereign account — without that account's consent, an attacker can plant an NFT on a pool account and then claim a self-created swap whose price direction pulls `T::Currency` funds out of that account.

### Finding Description
In `do_claim_swap` [1](#0-0) , `receive_item.owner` is read live from `Item::<T,I>::get(&receive_collection_id, &receive_item_id)` at claim time, not the owner recorded when the swap was created. The subsequent price transfer moves funds between `send_item.owner` (the caller) and `receive_item.owner` using `T::Currency::transfer(..., KeepAlive)` with no check that either account is a "normal" user account rather than a pallet-derived sovereign account.

NFT ownership transfer in `pallet-nfts`/`pallet-uniques` never requires consent from the destination account — `do_transfer` simply overwrites the `owner` field. This means an attacker who owns an NFT can freely transfer it to any `AccountId`, including a `pallet-asset-conversion` pool's sovereign account (`PoolLocator::address`), which is a plain, keyless `AccountId` derived deterministically from a `PalletId` and the asset pair (`AccountIdConverter` in `substrate/frame/asset-conversion/src/types.rs` lines 146-158) — publicly computable, no signature required to "own" tokens or receive an NFT there.

Exploit flow (single attacker, two of their own accounts A1/A2, or even one account acting in both roles):
1. Attacker (A1) owns NFT #1 in collection C. A1 calls `do_create_swap` offering NFT#1, `desired_collection = D`, `price = Some({amount: X, direction: Send})`, long `duration` [2](#0-1) .
2. A1 transfers NFT#1 to the pool's sovereign account (a normal NFT transfer the owner is fully entitled to perform; the destination need not consent).
3. Attacker (A2) calls `do_claim_swap`, naming `receive_collection_id=C`, `receive_item_id=1`. At this point `receive_item.owner` resolves to the **pool account**, not A1.
4. Because `price.direction == Send`, the code executes `T::Currency::transfer(&receive_item.owner /* pool account */, &send_item.owner /* A2 */, X, KeepAlive)` [3](#0-2) . This drains `X` of the pool's native currency directly to A2, with no interaction with `pallet-asset-conversion`'s `swap_exact_tokens_for_tokens`, `add_liquidity`/`remove_liquidity`, or any `k = x*y` accounting.
5. NFT ownership is then swapped as usual: NFT #1 moves to A2, and the item A2 offered moves to the pool account — irrelevant to the currency theft, which has already completed.

None of the existing checks stop this: `do_claim_swap` only validates that `send_item.owner == caller`, that `swap.desired_collection`/`witness_price` match, and the deadline — it never restricts which account may end up holding `receive_item`/`send_item`, and it never checks whether `receive_item.owner` or `send_item.owner` is a pallet-derived, no-private-key sovereign account that backs unrelated pooled funds. `pallet-asset-conversion` has no hook, freeze, or lock on its pool account's `T::Currency` balance to prevent arbitrary pallets/extrinsics from moving funds out of it; the pool's reserves are just the live `T::Currency`/`T::Assets` balance of that account (as confirmed by `quote_price_ignores_unrelated_non_sufficient_assets_in_pool_account` and swap tests that assert `balance(pallet_account, token)` directly), so nothing internally blocks an outside transfer.

### Impact Explanation
If a runtime configures `pallet_nfts::Config::Currency` (or `pallet_uniques::Config::Currency`) to the same fungible implementation used as the native asset in `pallet-asset-conversion` (a realistic and common setup — Asset Hub runtimes use `type Currency = Balances` for `pallet_nfts` while `Balances` is also the native asset for the DOT/native pools), an attacker can drain a pool's native currency reserves down to the existential deposit (respecting only `KeepAlive`), without going through `swap_exact_tokens_for_tokens` and without updating any pool reserve/LP accounting. This desyncs the pool's actual backing from its LP-token-implied entitlements: LP providers become unable to redeem their full pro-rata share, and any live-balance-based quoting/swapping (`quote_price_*`, `swap_exact_tokens_for_tokens`) will silently operate on the reduced, attacker-drained balance going forward — a direct pool drain / unbacked-liquidity condition.

### Likelihood Explanation
This is fully attacker-executable with unprivileged, signed accounts and no special preconditions beyond: (a) the runtime enabling `PalletFeature::Swaps` in NFTs (`Self::is_pallet_feature_enabled(PalletFeature::Swaps)`), (b) the NFTs pallet's `Currency` type coinciding with an asset-conversion pool's native asset, and (c) the attacker being able to own/mint an NFT (self-service in most configurations via `CreateOrigin = EnsureSigned`). No governance, leaked keys, or node/relayer control is needed — only two ordinary extrinsics (`create_swap`, an NFT `transfer`, `claim_swap`) from accounts the attacker controls. The pool sovereign account address is fully computable off-chain from public `PalletId`/pool-id data, so the attacker does not need any privileged discovery step. This makes the exploit repeatable against every pool sharing the currency instance.

### Recommendation
- In `do_claim_swap` (and `do_create_swap`), reject swaps where `send_item.owner` or `receive_item.owner` (at claim time) is a "system"/pallet-derived sovereign account (e.g., check against a registry/trait of reserved accounts, or require the account to be a "normal" signed account/have no `frame_system::Provider`-style pallet marker).
- Alternatively/additionally, `pallet-asset-conversion` should not treat a pool account's live `T::Currency`/`T::Assets` balance as ground truth for reserves; introduce pool-account balance freezes (similar to `pallet-nomination-pools`'s `FreezeReason::PoolMinBalance` pattern) or explicit reserve storage synchronized via `MutateLiquidity`/`Swap` calls only, with active mismatch detection.
- More generally, `T::Currency::transfer` calls triggered by unrelated pallets should validate that the counterparties are not addresses reserved/derived by other pallets (`PalletId::into_account_truncating` outputs), e.g. via a shared "protected accounts" check exposed by `frame_support`.

### Proof of Concept
Rust integration test (cross-pallet, in a test runtime that includes both `pallet-nfts` and `pallet-asset-conversion` sharing `Balances` as native currency):
```rust
#[test]
fn nft_swap_can_drain_asset_conversion_pool_account() {
    new_test_ext().execute_with(|| {
        // 1. Set up a native/asset pool and add liquidity as `lp_provider`.
        assert_ok!(AssetConversion::create_pool(RuntimeOrigin::signed(lp_provider), native.clone(), asset.clone()));
        assert_ok!(AssetConversion::add_liquidity(RuntimeOrigin::signed(lp_provider), native.clone(), asset.clone(), 10_000, 100, 1, 1, lp_provider));
        let pool_id = <Test as pallet_asset_conversion::Config>::PoolLocator::pool_id(&native, &asset).unwrap();
        let pool_account = <Test as pallet_asset_conversion::Config>::PoolLocator::address(&pool_id).unwrap();
        let pool_balance_before = Balances::free_balance(&pool_account);

        // 2. Attacker mints an NFT and creates a swap wanting `X` native tokens (direction: Send).
        assert_ok!(Nfts::create(RuntimeOrigin::signed(attacker1), collection_c, ..));
        assert_ok!(Nfts::mint(RuntimeOrigin::signed(attacker1), collection_c, item1, attacker1, None));
        assert_ok!(Nfts::create_swap(RuntimeOrigin::signed(attacker1), collection_c, item1, collection_d, None,
            Some(PriceWithDirection { amount: X, direction: PriceDirection::Send }), duration));

        // 3. Attacker transfers the offered NFT to the pool's sovereign account (no consent needed).
        assert_ok!(Nfts::transfer(RuntimeOrigin::signed(attacker1), collection_c, item1, pool_account.clone()));

        // 4. Attacker2 owns an item in collection D and claims the swap.
        assert_ok!(Nfts::mint(RuntimeOrigin::signed(attacker2), collection_d, item2, attacker2, None));
        assert_ok!(Nfts::claim_swap(RuntimeOrigin::signed(attacker2), collection_d, item2, collection_c, item1,
            Some(PriceWithDirection { amount: X, direction: PriceDirection::Send })));

        // Assertions: pool account lost X of native currency with NO asset-conversion extrinsic invoked.
        assert_eq!(Balances::free_balance(&pool_account), pool_balance_before - X);
        assert_eq!(Balances::free_balance(&attacker2), attacker2_balance_before + X);

        // Show the pool's reserve accounting is now inconsistent with LP token claims:
        let (reserve_native, reserve_asset) = AssetConversion::get_reserves(&native, &asset).unwrap();
        assert!(reserve_native < expected_reserve_from_lp_supply, "pool under-backed relative to LP tokens after unrelated NFT swap drain");
    });
}
```
Expected result: the test passes today (transfer succeeds, pool drained, `get_reserves`/live balance shows a value inconsistent with outstanding LP token supply), confirming the vulnerability. A fix should make this test fail either at the `Nfts::claim_swap` step (transfer rejected because the counterparty is a protected pool account) or ensure `get_reserves` cannot silently reflect an externally-drained balance without triggering a defensive error/lock.

	pub(crate) fn do_create_swap(
		caller: T::AccountId,
		offered_collection_id: T::CollectionId,
		offered_item_id: T::ItemId,
		desired_collection_id: T::CollectionId,
		maybe_desired_item_id: Option<T::ItemId>,
		maybe_price: Option<PriceWithDirection<ItemPrice<T, I>>>,
		duration: BlockNumberFor<T, I>,
	) -> DispatchResult {
		ensure!(
			Self::is_pallet_feature_enabled(PalletFeature::Swaps),
			Error::<T, I>::MethodDisabled
		);
		ensure!(duration <= T::MaxDeadlineDuration::get(), Error::<T, I>::WrongDuration);

		let item = Item::<T, I>::get(&offered_collection_id, &offered_item_id)
			.ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(item.owner == caller, Error::<T, I>::NoPermission);

		match maybe_desired_item_id {
			Some(desired_item_id) => ensure!(
				Item::<T, I>::contains_key(&desired_collection_id, &desired_item_id),
				Error::<T, I>::UnknownItem
			),
			None => ensure!(
				Collection::<T, I>::contains_key(&desired_collection_id),
				Error::<T, I>::UnknownCollection
			),
		};

		let now = T::BlockNumberProvider::current_block_number();
		let deadline = duration.saturating_add(now);

		PendingSwapOf::<T, I>::insert(
			&offered_collection_id,
			&offered_item_id,
			PendingSwap {
				desired_collection: desired_collection_id,
				desired_item: maybe_desired_item_id,
				price: maybe_price.clone(),
				deadline,
			},
		);

		Self::deposit_event(Event::SwapCreated {
			offered_collection: offered_collection_id,
			offered_item: offered_item_id,
			desired_collection: desired_collection_id,
			desired_item: maybe_desired_item_id,
			price: maybe_price,
			deadline,
		});

		Ok(())
	}
