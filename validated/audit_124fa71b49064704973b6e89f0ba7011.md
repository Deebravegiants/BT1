Based on my research, I found a valid analog matching the identity-binding class described in the rules.### Title
Webhook `shop`/`topic`/`webhook_id` fields are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to the registered handler using `request.shop`, `request.topic`, and `request.webhook_id`, none of which are covered by that signature.

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers, which are completely outside the HMAC computation: [2](#0-1) 

`Registry.process` then uses the unauthenticated header values to select the handler and to build the `WebhookMetadata` object that is handed to application code as the trusted identity of the event: [3](#0-2) 

The binding the gem is supposed to enforce is:
`shop/topic/webhook_id delivered to handler == shop/topic/webhook_id that Shopify actually signed for`

In reality the gem only enforces:
`raw_body verified by HMAC == raw_body received`

`shop`, `topic`, and `webhook_id` are never part of the signed material, so the equality above does not hold — any request whose *body* carries a valid HMAC for the configured `api_secret_key` will be accepted regardless of what `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` say. This mirrors the reentrancy report's root cause pattern of "a value is used/trusted before/without the invariant that's supposed to protect it actually covering it" — here it's a field acted upon (`shop`, used by host apps to look up per-tenant session/access tokens) that is not covered by the authentication mechanism (HMAC) that is meant to prove the request's authenticity.

### Impact Explanation
An app built on this gem typically uses `WebhookMetadata#shop` to look up the correct per-merchant session/access token and to decide how to act on the payload (e.g., updating that merchant's data). Since `shop` is not bound to the HMAC-signed body, a request whose body carries a validly-signed payload (for the shared `api_secret_key` of the app) can be delivered with an attacker-chosen `shop` header, causing the host application to process the body under a different tenant's identity than the one the payload was actually generated for. This is a cross-tenant identity-confusion vector at the point the gem hands data to application code, since the library documents `WebhookMetadata#shop` as verified/trusted output of `Registry.process` (the whole point of the surrounding `Utils::HmacValidator.validate` check).

### Likelihood Explanation
Exploitation requires the attacker to possess at least one raw body/HMAC pair valid for the app's shared secret (e.g., from a webhook delivered for their own shop's install of the app) and the ability to re-POST it to the app's public webhook endpoint with modified `x-shopify-shop-domain`/`x-shopify-topic`/`x-shopify-webhook-id` headers, since the webhook endpoint is a normal public HTTP route. No access token, `api_secret_key`, or privileged account is required — only a legitimate (even free) install of the target app on an attacker-controlled shop, which is an unprivileged-internet-user starting position.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (at minimum `shop`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. If Shopify's webhook HMAC scheme does not support signing headers, cross-check `request.shop` in `Registry.process` against the shop associated with the webhook subscription (e.g., via the `webhook_id` looked up through the Admin API) before invoking the handler, rather than trusting the raw header value outright.

### Proof of Concept
1. Install the target app (built with this gem) on an attacker-controlled shop `attacker.myshopify.com`; the app registers a webhook via `ShopifyAPI::Webhooks::Registry.register`.
2. Trigger a real webhook delivery for `attacker.myshopify.com` (e.g., create an order) and capture the exact `raw_body` and the `x-shopify-hmac-sha256` value Shopify sends — this pair is valid because `to_signable_string` only signs `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
3. Replay this exact `raw_body` + `x-shopify-hmac-sha256` to the same public webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (or any other installed shop) and/or a different `x-shopify-topic`.
4. `Utils::HmacValidator.validate` returns `true` because the body/HMAC pair is legitimate (`lib/shopify_api/webhooks/registry.rb:190`), and `Registry.process` dispatches the attacker's body to the handler tagged with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to act on attacker-controlled data under another tenant's identity.
