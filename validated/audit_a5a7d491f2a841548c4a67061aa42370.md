### Title
Webhook `shop` (and `topic`/`webhook-id`) header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , yet the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` are all read directly from unauthenticated HTTP headers [2](#0-1) . The HMAC only binds the body bytes, never the shop identity that the app trusts and dispatches on.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it against the received `hmac` value [3](#0-2) . For webhook requests, `to_signable_string` is defined to be just `@raw_body` [1](#0-0) , so the signature proves nothing about which shop, topic, or webhook id the request claims to represent — those are parsed straight out of the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers with no cryptographic binding to the body/HMAC pair [2](#0-1) .

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` and `request.topic` for dispatch to the app's handler: [4](#0-3) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

This breaks the identity binding: `shop authenticated == shop the HMAC actually vouches for` should hold, but instead `shop authenticated != shop covered by the HMAC` — the HMAC covers `raw_body` only, while the trusted tenant identity comes from an arbitrary, replayable header.

Because the app's `api_secret_key` (client secret) is shared across every shop that installs the app, an unprivileged attacker who installs the app on their own (attacker-controlled) development shop can legitimately receive a real webhook delivery with a valid `(raw_body, hmac)` pair signed by Shopify with that same shared secret. The attacker then replays that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` dispatches the forged request to the handler as if it genuinely originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity-binding failure: an attacker with no access to the victim shop can make the app process attacker-chosen webhook payloads under the victim's `shop` identity. Depending on how the hosting app's `WebhookHandler` uses `WebhookMetadata#shop` (e.g., to look up/update the victim's session, mark data as redacted for `customers/redact`/`shop/redact`, or trigger shop-scoped business logic), this enables cross-tenant data manipulation using only the attacker's own legitimate app installation — no access token or secret is required for the attack itself, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
The precondition (attacker can install the app on their own shop and receive a real webhook to harvest a valid raw_body/HMAC pair, then replay it with modified headers) is easily achievable by any unprivileged internet user for public/embedded apps that support open installation, since headers are fully attacker-controlled in raw HTTP proxying/replay and the gem itself performs no additional binding.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum the shop domain) in the HMAC-signed content check, or independently verify that the `shop` header corresponds to a shop with an active app installation/session before dispatching, rather than trusting it purely because the body HMAC validated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receiving a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally changes `X-Shopify-Topic`/`X-Shopify-Webhook-Id` to another registered topic, since those aren't part of the signable string either).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `@raw_body` [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to process attacker-controlled data as if it came from the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
