## Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies an inbound webhook by computing an HMAC over the raw request body only, then hands the caller a `WebhookMetadata` object whose `shop` field is taken from an **unsigned** HTTP header. Because the shop identity is never bound to the signature, an attacker who legitimately receives real, validly-signed webhooks for their *own* shop (by installing the app) can replay that exact body/HMAC pair to the app's webhook endpoint while swapping only the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to a victim shop. The signature still validates, and the app's handler is invoked believing the (attacker-controlled) payload belongs to the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read straight from request headers, entirely outside that signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC using only `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and then dispatches the handler using `request.shop` unconditionally, without any additional binding between the verified bytes (body) and the field acted on (shop): [4](#0-3) 

The documented usage pattern confirms host apps are expected to trust `data.shop` as the tenant key for business logic (e.g., routing background jobs per shop): [5](#0-4) 

This is the same class of bug as the reported UFARM finding: a value that drives sensitive, tenant/state-changing action (`shop`) is not covered by the integrity check that gates the action (HMAC over body only). The equality that should hold — `shop authenticated == shop the payload is attributed to` — is broken because `shop` is parsed from the request but never verified as part of the signed content.

### Impact Explanation
Since the app's `api_secret_key` (the webhook signing secret) is shared across all shops that install the app — it is not shop-specific — any attacker who installs the app on their own (or any) store receives genuine, correctly-signed webhooks. They can capture one such `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim's `myshopify.com` domain. `HmacValidator.validate` will still pass because it never inspects the header, so `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain and `body` equal to attacker-controlled JSON. Any host application that uses `data.shop` for tenant-scoped writes, cache keys, job routing, or state transitions (as the gem's own documentation recommends) can be made to apply attacker-supplied data under a victim tenant's identity — a cross-tenant data-integrity/confusion primitive reachable by an unprivileged internet user with no credentials belonging to the victim.

### Likelihood Explanation
Any user can self-install the app to obtain a stream of validly-signed webhooks, since installing an app on one's own store requires no special privilege and no access to the victim's secrets. Replaying the request to the (public, unauthenticated-by-design) webhook endpoint with a modified header is trivial and requires no cryptographic material beyond what Shopify already hands the attacker for their own shop.

### Recommendation
Bind the identity fields (`shop`, and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or otherwise cross-check the header-derived `shop` against an independently trusted source (e.g., the webhook subscription/registration record fetched from Shopify for that specific shop) before invoking handlers. At minimum, document/enforce that `WebhookMetadata#shop` must not be trusted as a tenant key unless corroborated by a stored, HMAC-independent mapping (such as validating the webhook_id belongs to a subscription registered for that shop).

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) to receive a real request from Shopify with body `B` and header `Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay the captured request to the app's webhook controller endpoint, keeping body `B` and header `Shopify-Hmac-Sha256: H` unchanged, but replace `Shopify-Shop-Domain: attacker.myshopify.com` with `Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` — matching `H` regardless of the shop header — so validation succeeds.
4. The registered handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker JSON>, ...)`, letting the attacker inject data or trigger business logic attributed to the victim shop.

          received_signature = verifiable_query.hmac
