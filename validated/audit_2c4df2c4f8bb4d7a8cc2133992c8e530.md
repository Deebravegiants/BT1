### Title
Tokens sent to the controller or pool outside measured-payment flows are permanently locked with no recovery path - (File: contracts/controller/src/payments.rs)

### Summary
The external report's bug class — assets over-sent to a contract that has no withdrawal functionality — maps onto XOXNO Lending's custody model. Every controller entrypoint that moves user tokens either pulls exactly the declared amount (`supply`, `repay`, `liquidate`, `recapitalize`, `multiply` initial payment) or measures balance deltas and refunds only declared assets (`flash_position`, strategy repay legs). Any token balance that lands on the controller or the pool outside those measured windows is invisible to the accounting layer, and neither contract exposes a sweep, rescue, or admin recovery entrypoint, so those funds are frozen permanently.

### Finding Description
The controller's custody model is delta-based. `snapshot_balances` records pre-operation balances and `refund_controller_balance_delta` refunds only the *increase* since the snapshot, explicitly "preserving the pre-existing balance" [1](#0-0) . In `flash_position`, after the receiver callback the controller only (a) deposits positive deltas of *declared* collateral assets and (b) refunds positive deltas of *declared* `refund_assets` [2](#0-1) . Any other token pushed to the controller during the callback is neither credited nor refunded — confirmed by the documented behavior "An undeclared token left on the controller is neither deposited nor refunded" [3](#0-2) . The same applies to plain token `transfer`s to the controller address, and tests explicitly pin that pre-existing controller balances are never swept (`pre-existing controller ETH must remain (not used as refund or swept)`) [4](#0-3) .

The pool is symmetric: `cash` is pure bookkeeping credited only from controller-reported amounts, and the only outbound paths are `borrow`, `withdraw`, refund legs, `claim_revenue`, `create_strategy`, and `flash_loan` [5](#0-4) . A direct token transfer to the pool raises custody above `cash` with no entrypoint to release the difference. Neither `ControllerInterface` nor `ControllerAdmin` contains any token-recovery function — the complete admin surface (registry setters, spoke/asset config, deploys, upgrades, pause, ownership) has nothing that moves tokens out [6](#0-5) .

### Impact Explanation
Permanent freezing of funds. A user whose `execute_flash_position` receiver pushes an undeclared token to the controller (for example a leftover output token from its internal swap that was not listed in `refund_assets`), or anyone who directly transfers tokens to the pool or controller, loses those assets forever. Unlike the Aave report — where the recommendation was to *add* a withdraw function — this codebase deliberately snapshots and protects pre-existing balances on every flow, which guarantees stranded balances can never be claimed by anyone, including the owner. There is no governance operation or upgrade-independent path that can move them.

### Likelihood Explanation
Medium-low, requiring a user-side mistake rather than an exploitable condition against third parties. The realistic trigger is the `flash_position` callback: receivers compute collateral internally and push it with a plain `token::transfer`, and any asset not enumerated in `collaterals` or `refund_assets` (which are capped at `max_supply_positions` entries each) is abandoned [7](#0-6) . Accidental direct transfers to the controller/pool addresses are also possible since both are publicly known. Because the loss requires the sender's own error, Medium is the ceiling.

### Recommendation
Add a recovery mechanism for stranded balances, e.g. an owner- or governance-gated `recover_assets(token, to, amount)` on the controller, and for the pool either the same or a permissionless skim of `balance - cash` to the accumulator/revenue. Alternatively, in `flash_position`, fail the call when the controller holds a positive post-callback delta of any asset that is neither a declared collateral nor a declared refund asset, so senders cannot silently strand funds.

/// Refunds only the controller balance increase since `balance_before`,
/// preserving the pre-existing balance; no-op for a nonpositive delta.
pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
}

fn validate_refund_assets(
    env: &Env,
    cache: &mut Context,
    spoke_id: u32,
    hub_id: u32,
    collaterals: &Vec<(HubAssetKey, i128)>,
    refund_assets: &Vec<Address>,
) {
    let limits = storage::get_position_limits(env);
    assert_with_error!(
        env,
        refund_assets.len() <= limits.max_supply_positions,
        GenericError::InvalidPayments
    );

    let mut seen: Map<Address, bool> = Map::new(env);
    for asset in refund_assets.iter() {
        assert_with_error!(
            env,
            !seen.contains_key(asset.clone()),
            GenericError::InvalidPayments
        );
        seen.set(asset.clone(), true);
        // Refund transfers run after the guard; restrict tokens to listed assets.
        cache.require_listed_active_config(
            spoke_id,
            &HubAssetKey {
                hub_id,
                asset: asset.clone(),
            },
        );
        for (collateral, _) in collaterals.iter() {
            assert_with_error!(
                env,
                asset != collateral.asset,
                GenericError::InvalidPayments
            );
        }
    }
}
