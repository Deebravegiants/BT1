## Title
`EvmHost.dispatch`/`fundRequest`/`IntentGatewayV2` unconditional native→feeToken swap reverts when no direct Uniswap V2 path exists, permanently blocking native-fee dispatch - (File: evm/src/core/EvmHost.sol)

## Summary
The original finding is a bug class: a function that must handle a set of assets executes a swap step assuming a valid swap path always exists, but for at least one asset (here, the base asset itself) no path was configured, and the code has no fallback/guard, so the whole operation reverts and a critical recovery/settlement path is permanently blocked whenever that condition is hit.

The closest reachable analog in this codebase is `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in [1](#0-0) , [2](#0-1) , and [3](#0-2) , and the equivalent fee-escrow logic in `IntentGatewayV2`/its Tron port at [4](#0-3) . All of these paths unconditionally build a fixed two-hop path `[WETH, feeToken()]` and call `swapETHForExactTokens` whenever `msg.value > 0`, with no fallback for the case where no direct Uniswap V2 pool exists for that pair (or where `feeToken() == WETH`).

## Finding Description
Any unprivileged caller who dispatches a POST/GET request or funds a pending request by sending native token (instead of pre-approved fee token) triggers this code:

```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

This is structurally identical to the reported bug: the code assumes a swap "path" is always resolvable for the configured token (analogous to `pathsell` for a collateral asset), but never checks whether:
1. `feeToken() == WETH` (identical addresses — Uniswap V2 reverts with `IDENTICAL_ADDRESSES` on `getReserves`/`sortTokens` for such a path, exactly like the DAI case where no swap should be necessary and no path was defined), or
2. no direct WETH↔feeToken pool exists on the configured router (`INSUFFICIENT_LIQUIDITY`/`revert` on `swapETHForExactTokens`).

Both conditions are outside the caller's control — they're a function of governance/host configuration (`_hostParams.uniswapV2`, `feeToken()`), yet the dispatch is fully permissionless and reachable by any account, including relayers and app contracts, paying native token for message dispatch. The same unconditional path-building pattern (no path-existence check, no branch for the identity case) is repeated three times in `EvmHost.sol` (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and once more in `IntentGatewayV2`'s order-fee escrow logic when a solver/user pays the solver/relayer fee (`order.fees`) in native token [4](#0-3) .

Root cause: the swap step is treated as always-available infrastructure (identical to `pathsell` being assumed always-defined for every collateral asset in the USSD rebalancer), with no guard for the base-asset/no-path case, and no fallback to plain `feeToken()` transfer when the native-token payment path cannot execute.

## Impact Explanation
When triggered, this reverts the entire dispatch/fundRequest/fillOrder transaction:
- `dispatch(DispatchPost)`/`dispatch(DispatchGet)`: any app or user attempting to pay Hyperbridge's relayer fee in native token cannot submit cross-chain requests at all — this is a "route unable to deliver messages" condition for any chain where the configured fee token has no direct native pool, or where `feeToken()` is misconfigured to equal `WETH`.
- `fundRequest`: users who need to top up the relayer fee on an already-dispatched pending request (e.g., to avoid a timeout and recover funds) cannot do so via native token, risking the message timing out and funds/fees being stuck in limbo.
- `IntentGatewayV2` order placement with native-token solver fee payment fails identically, blocking users from placing intent orders paid in native token on that route.

Because dispatch is the fundamental entry point for ISMP message delivery, this is a High-severity availability/freezing issue for the affected route: it can permanently block requests from being dispatched with native-token fee payment on any chain/host configuration where the WETH↔feeToken pool is thin, nonexistent, or where the fee token equals WETH.

## Likelihood Explanation
Likelihood is high on any newly-deployed or low-liquidity chain, or one where the feeToken is deliberately set to the wrapped native asset for simplicity — both realistic host configurations. The trigger requires no attacker action; it is a naturally occurring configuration state, exactly mirroring how the DAI-as-base-collateral case in the original report was a normal, intended configuration (not an edge case introduced by an attacker).

## Recommendation
- Before building the swap path, check whether `feeToken() == IUniswapV2Router02(uniswapV2).WETH()`. If so, skip the swap and instead wrap the sent ETH directly (`IWETH(WETH).deposit{value: msg.value}()`) rather than routing through the AMM.
- Guard the `swapETHForExactTokens` call with a liquidity/quote check (e.g., `getAmountsIn` first) and revert with a clear, distinguishable error (e.g., `NoSwapRouteForFeeToken()`) rather than letting the low-level Uniswap revert propagate, so integrators can detect and handle the failure mode explicitly.
- Apply the same fix consistently across `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`, and the fee-escrow swap logic in `IntentGatewayV2`/its Tron port.

## Proof of Concept
1. Deploy/govern an `EvmHost` where `feeToken()` is configured to equal the chain's WETH address (or where the Uniswap V2 factory has no pool for `[WETH, feeToken()]`).
2. Any user calls `dispatch(DispatchPost)` (or `dispatch(DispatchGet)`, or `fundRequest`) with `msg.value > 0` intending to pay the relayer fee in native token, per [1](#0-0) .
3. `IUniswapV2Router02(uniswapV2).swapETHForExactTokens` reverts (`UniswapV2Library: IDENTICAL_ADDRESSES` when `feeToken()==WETH`, or a pair-not-found/insufficient-liquidity revert otherwise).
4. The entire `dispatch`/`fundRequest` transaction reverts — no request commitment is created, no fee is escrowed, and the message is never delivered to Hyperbridge, blocking that route for every native-fee payer until governance reconfigures `feeToken()` or seeds a WETH pool.
