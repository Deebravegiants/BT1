### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook exclusively from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that the gem verifies is computed over the raw request body only — the shop header is never part of the signed material. An attacker who can obtain one valid `(body, hmac)` pair (trivially available by installing the app on a shop they control themselves) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header value. `Utils::HmacValidator.validate` will still report success because it only checks the body against the secret, and the forged shop value is handed straight to the app's webhook handler as the authoritative tenant identity.

### Finding Description
This mirrors the report's root cause: a value that is *acted upon* (used to identify which tenant/session a payload belongs to) is not covered by the cryptographic binding that is supposed to authenticate the message — analogous to `_totalSupply`/`_totalShares` drifting apart because a mutation path bypassed the invariant that should tie them together.

Concretely:
- `Webhooks::Request#shop` reads the header value directly with no verification: [1](#0-0) 
- `Webhooks::Request#to_signable_string`, the value that is actually HMAC-verified, returns only the raw body — `shop` (and `topic`, `webhook_id`, `api_version`) are excluded from the signable string entirely: [2](#0-1) 
- `Utils::HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string` (i.e., the body), with no binding to `shop`: [3](#0-2) 
- `Registry.process` only calls `HmacValidator.validate(request)` (body-only check) and then immediately trusts `request.shop` to construct the tenant-scoped payload delivered to the host app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC_valid(body) == true` is treated as proof that `shop == <the shop that actually sent this body>`, but in reality `HMAC` only proves `body` was signed by *some* shop the secret is shared with (i.e., any shop that has this app installed) — it says nothing about which shop's header value accompanies that body. Before the attack: `shop_header == originating_shop`. After: `shop_header` is attacker-controlled while `body`/`hmac` remain valid for the attacker's own shop, so `shop_header != originating_shop` yet the gem still returns `hmac_valid? == true` and forwards `shop_header` as trusted tenant context.

### Impact Explanation
This is a cross-tenant data-injection vector: a host application built on this gem uses `WebhookMetadata#shop` (populated straight from the unauthenticated header) to route/attribute webhook data to a specific merchant/tenant record. Since the gem does not bind `shop` to the HMAC, any actor with a legitimate webhook subscription on their own (attacker-owned, freely installable) shop can forge webhooks that claim to originate from a different, victim shop, injecting attacker-chosen data (order/product/customer payloads, app-uninstall notifications, etc.) into the victim tenant's context in the host application. This satisfies the "Critical - cross-tenant access" impact bucket, since the identity boundary between tenants is broken using only the gem's own verification logic.

### Likelihood Explanation
High. No access token, `client_secret`, or privileged account is required — any user can create a development/trial Shopify store, install a public app to receive one legitimately-signed webhook body/HMAC pair, and then replay that body with a spoofed `shop-domain` header against the app's public webhook endpoint. The gem provides no additional check (e.g., verifying `shop` against an active session, or including `shop` in the HMAC signable string) to prevent this.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-verified signable string, or independently validate that the `shop-domain` header corresponds to a shop with an active, known session/access token before trusting it as the payload's tenant. At minimum, document and enforce that host applications must cross-check `request.shop` against a shop the app has record of installing, rather than treating it as authenticated purely because the HMAC check passed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (no special privilege needed — any Shopify Partner/dev account).
2. Shopify sends a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for secret `S`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `B`/`H` pair to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which only checks `H` against `B` — this still passes because `B` and `H` are unchanged: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the host application processes attacker-supplied data as if it came from the victim shop: [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
