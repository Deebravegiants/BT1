### Title
Webhook shop-domain tenant identifier is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," and the resulting `WebhookMetadata#shop` field is documented as "the shop domain of the webhook." In reality, the HMAC signature validated by `Utils::HmacValidator` is computed only over the raw request body, never over the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` headers. This breaks the identity binding: `hmac(secret, body) == received_hmac` says nothing about `shop == actual_originating_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC and then, on success, immediately trusts `request.shop` (and `request.topic`) taken straight from headers with no cross-check against the signed body: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` compute the HMAC solely from `verifiable_query.to_signable_string` (i.e. the body), never incorporating the shop header: [3](#0-2) 

The shop header is read independently of the signed content: [4](#0-3) 

Because the shop identity travels in an unsigned header while only the body is authenticated, any party who can obtain one genuine `(body, hmac)` pair signed with the app's secret — for example a merchant who installs the app on their own shop and receives their own legitimate webhook deliveries — can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because the signature check only ever examines the body, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` claims to be the victim tenant while `body` is actually the attacker's own data.

### Impact Explanation
This breaks the identity binding `shop_header == shop_that_the_HMAC_actually_authenticates`. Host applications are told by the gem's own documentation that `Registry.process` "verifies the request did indeed come from Shopify" and that `shop` is "the shop domain of the webhook," so it is reasonable — and typical — for host apps (e.g. the pattern shown in the docs: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) to key all downstream tenant-scoped side effects (order sync, inventory writes, GDPR shop/customer redaction, uninstall handling, credential/session lookups keyed by shop, etc.) off `data.shop` without additional verification, since the gem presents this value as already authenticated. An attacker who is any installed merchant of the app can therefore inject data attributed to a different shop, i.e. cross-tenant access/write, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be an unprivileged, legitimate installer of the app on their own shop (no `api_secret_key`, no stolen access token, no privileged account) — they merely capture one webhook delivery Shopify sends them (trivial, since Shopify sends real webhooks to every installed shop) and replay it with a modified header. This is a low-effort, credential-free attack path, matching the required threat model of an unprivileged internet user.

### Recommendation
Bind the tenant/topic identity into the authenticated material: either include `shop`, `topic`, and `webhook_id` in the HMAC-signed string (would require Shopify-side changes since Shopify controls signing), or, more practically within this gem, require host apps to cross-validate `request.shop` against an independently known/authorized shop list (e.g. only accept webhooks for shops with an active stored session) before trusting `WebhookMetadata#shop`, and update the documentation to explicitly state that only the body is authenticated by the HMAC check — the shop/topic headers are not cryptographically bound to the signature and must not be treated as verified identity.

### Proof of Concept
1. App merchant "Attacker Shop" installs the target app and registers for `orders/create` webhooks; Shopify sends a legitimate webhook to the app's endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 1, "note": "malicious payload"}
   ```
2. Attacker captures this exact body and `X-Shopify-Hmac-Sha256` value.
3. Attacker replays the identical body/HMAC to the same endpoint, only changing the shop header:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same-valid-hmac-of-body>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {"id": 1, "note": "malicious payload"}
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the secret: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/stores the attacker's data as if it belonged to `victim-shop`, achieving cross-tenant data injection without any credentials belonging to the victim.
