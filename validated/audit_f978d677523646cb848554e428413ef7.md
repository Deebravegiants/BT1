This confirms the root cause. The gem's `Registry.process` at `lib/shopify_api/webhooks/registry.rb:188-200` validates only the HMAC over `request.to_signable_string` (which is just `@raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38`), then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all pulled directly from unauthenticated HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33,67-70`) — and hands them to the app's `WebhookHandler#handle` inside `WebhookMetadata` (`lib/shopify_api/webhooks/webhook_handler.rb:6-12`) without any of those fields being part of the signed content.

### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id`) is trusted from unsigned headers while only the raw body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as solely the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are never included in the signed bytes. `Registry.process` verifies the HMAC and then unconditionally trusts these header-derived fields to build the `WebhookMetadata` handed to the app's handler, breaking the intended binding `verified_bytes == acted_upon_bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all derived from the `shopify-*`/`x-shopify-*` HTTP headers via `shopify_header`, which are never part of the signed string: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body): [4](#0-3) 

`Registry.process` performs this HMAC check and, once it passes, unconditionally forwards the header-derived, unauthenticated `shop`, `topic`, and `webhook_id` values into `WebhookMetadata`, which the app's `WebhookHandler#handle` implementation uses to determine which tenant/shop the event applies to and act accordingly (e.g., updating that shop's state, using that shop's stored session/access token): [5](#0-4) [6](#0-5) 

The identity binding the gem is supposed to enforce is `hmac_verifies(bytes) == bytes_used_to_identify_the_tenant`. Instead, `hmac_verifies(raw_body) != {shop, topic, webhook_id}_used_for_tenant_dispatch`. Since a single app's `client_secret` is shared across every shop that installs it (it is not shop-specific), any shop that has the app installed can legitimately receive a `(raw_body, hmac)` pair valid under that shared secret for an event in its own store, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body against the shared secret; `Registry.process` then dispatches the handler with `shop: <victim shop>`, causing the app to process attacker-controlled webhook content as if it originated from the victim tenant.

### Impact Explanation
This breaks the cross-tenant isolation the HMAC check is meant to provide: an unprivileged app-installing shop (attacker-controlled tenant, no special privilege) can forge the identity of the delivering shop for events processed by the host app, since the gem asserts authenticity of only the body and blindly trusts headers for tenant attribution. Any app-side logic keyed off `WebhookMetadata#shop` (fetching/acting on the victim's stored session or access token, updating victim records, etc.) can be triggered with attacker-chosen body content misattributed to the victim shop — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only that the attacker be an installer of the same multi-tenant app (an ordinary, unprivileged merchant with no special access) capable of triggering any webhook-eligible event in their own store, capturing the legitimately delivered `(raw_body, X-Shopify-Hmac-Sha256)` pair, and re-POSTing it to the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No `client_secret`, access token, or credential theft is needed beyond what the attacker already legitimately possesses as an app user; the check in `HmacValidator.validate` will still pass.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them to the body) inside `Request#to_signable_string`, so `HmacValidator.validate` fails if any header used for tenant/topic dispatch is altered relative to what was actually signed by Shopify for that specific delivery.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both sharing the same app `client_secret`.
2. Attacker triggers a webhook-eligible event (e.g., `orders/create`) on their own shop, and their endpoint receives a genuine request with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`.
3. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `to_signable_string` (`@raw_body` only) and it matches, returning `true` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data attributed to the victim shop.
