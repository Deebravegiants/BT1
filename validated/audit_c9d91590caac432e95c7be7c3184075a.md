Audit Report

## Title
Nil pointer dereference (DoS) in Vault gateway node handler when `PublicKeyGet` request has `nil`/omitted `params` - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` in `core/capabilities/vault/gw_handler.go` dispatches `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` without validating `req.Params`, unlike the other vault methods which are gated behind `GatewayVaultRequestProcessor.ProcessRequest`. `handlePublicKeyGet` unconditionally dereferences `*req.Params`, causing a nil pointer dereference panic if `Params` is nil. Critically, the gateway-side handler (`core/services/gateway/handlers/vault/handler.go`) also forwards user `PublicKeyGet` requests to nodes without any params validation, confirming the request is reachable from an unprivileged external client.

## Finding Description
In `GatewayHandler.HandleGatewayMessage`, the `MethodSecretsCreate/Update/Delete/List` cases are routed through `h.requestProcessor.ProcessRequest`, which explicitly rejects `req.Params == nil`. [1](#0-0)  The `MethodPublicKeyGet` case skips this entirely and calls `h.handlePublicKeyGet(ctx, gatewayID, req)` directly, which then does `json.Unmarshal(*req.Params, r)` without a nil check. [2](#0-1)  Dereferencing a nil `*json.RawMessage` here panics.

I traced the full request path from the internet-facing gateway. In `handler.HandleJSONRPCUserMessage` (gateway-side, user-facing), the `MethodPublicKeyGet` branch is handled specially and bypasses `h.requestProcessor.ProcessRequest` (the same validation pipeline that guards nil params for other methods) entirely — it goes straight to `h.newActiveRequest(req, callback)` and `h.handlePublicKeyGet(ctx, ar)`, with no params validation: [3](#0-2)  When the cache is empty, this calls `fanOutToVaultNodes`, which forwards `ar.req` — the original, unvalidated user request — verbatim to every DON node via `h.don.SendToNode(ctx, node.Address, &ar.req)`: [4](#0-3)  This confirms that a malformed `vault.publicKey.get` JSON-RPC request from an unprivileged HTTP client, with `params` omitted or `null`, is forwarded unmodified from the gateway to the node's `GatewayHandler.HandleGatewayMessage`, where it panics in `handlePublicKeyGet`.

## Impact Explanation
This is a Denial of Service against the node process (or at minimum the goroutine handling gateway messages) triggerable by any unprivileged client that can reach the gateway's public-key-get endpoint — no authentication or authorization is required for this method by design ("Public key requests don't require authorization" per the code comment). [5](#0-4)  If unrecovered, a panic in this handler crashes the node process, denying vault/secrets functionality to all workflows on that node.

## Likelihood Explanation
High. The gateway-side code path explicitly treats `MethodPublicKeyGet` as requiring no authorization and bypasses the same `ProcessRequest` validation pipeline used for other methods, and forwards the raw, unvalidated request to nodes. An unprivileged external caller can trigger this simply by sending `{"jsonrpc":"2.0","id":"1","method":"vault.publicKey.get"}` with `params` omitted, so long as the gateway's public-key cache is empty (e.g., on startup or after cache expiry/miss), causing the request to be forwarded to nodes.

## Recommendation
Add a nil-params guard to `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go`, consistent with the checks in `gateway_vault_request_processor.go`:
```go
func (h *GatewayHandler) handlePublicKeyGet(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
    if req.Params == nil {
        return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, errors.New("request params must not be nil"))
    }
    ...
```
Additionally, validate `req.Params` on the gateway-side handler (`core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage`'s `MethodPublicKeyGet` branch) before caching/forwarding, and audit all other `json.Unmarshal(*req.Params, ...)` call sites for the same issue.

## Proof of Concept
1. Ensure the gateway's cached public key is empty (e.g., fresh gateway start, before `fetchVaultPublicKey`'s periodic refresh populates the cache, or after cache eviction).
2. As an unauthenticated HTTP client, send a JSON-RPC request to the gateway's vault endpoint:
```json
{"jsonrpc":"2.0","id":"1","method":"vault.publicKey.get"}
```
   with `"params"` omitted (or explicitly `null`).
3. `handler.HandleJSONRPCUserMessage` routes this to `handlePublicKeyGet` → `fanOutToVaultNodes`, forwarding the request as-is to all DON nodes.
4. Each node's `GatewayHandler.HandleGatewayMessage` dispatches to `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)`, dereferencing a nil `*json.RawMessage` and panicking.
5. A Go unit test confirming this: construct a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and call `GatewayHandler.HandleGatewayMessage`, observing the panic.

func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}
