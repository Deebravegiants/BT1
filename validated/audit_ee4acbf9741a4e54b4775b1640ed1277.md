### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies an HMAC only over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — all of which are used by `ShopifyAPI::Webhooks::Registry.process` to route the payload and identify the tenant — come straight from HTTP headers that are never included in the signed content. This is the same class of defect as the report: a security-critical field ("shop") is acted upon but not covered by the integrity check ("hmac").

### Finding Description
`VerifiableQuery#to_signable_string` is the data that `Utils::HmacValidator` verifies against the HMAC header [4](#0-3) . For `Webhooks::Request`, this signable string is just `@raw_body` [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read from separate, unsigned headers [2](#0-1) .

`Registry.process` validates the HMAC (of the body only) and then unconditionally trusts `request.shop` and `request.topic` to dispatch to a handler and construct `WebhookMetadata` for the app: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) .

The equality that should hold is: **shop value covered by the HMAC == shop value acted on by the handler**. Here, the shop value used for HMAC verification is empty (only the body is signed), while the shop value acted on is taken entirely from an attacker-controllable header. Any entity capable of delivering an HTTP POST to the app's webhook endpoint with a body+HMAC pair it has legitimately observed (e.g., a merchant who has installed the app and received their own genuine webhook for their own shop) can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a different shop. `HmacValidator.validate` will still succeed because it only checks the untouched raw body, and `Registry.process` will hand the payload to the app's handler tagged as originating from the victim shop.

### Impact Explanation
This breaks the shop-identity binding relied upon by every consumer of `WebhookMetadata#shop`. An app that uses the webhook's `shop` field to look up which merchant's records to update, credit, or delete would process attacker-supplied (but genuinely-HMAC'd) webhook content under a different tenant's identity — a cross-tenant data-integrity/confusion issue reachable by any unprivileged party that can capture one legitimate webhook delivery for their own shop and replay it toward the shared webhook endpoint with a modified shop header. This matches the Critical "cross-tenant access" impact category, since data intended for/about one tenant ends up attributed to and processed against another tenant.

### Likelihood Explanation
Any merchant who installs an app using this gem receives real webhook deliveries (body + valid HMAC) addressed to their own shop. Capturing one such delivery (e.g., `orders/create`, `app/uninstalled`) is trivial for that merchant. Constructing a forged HTTP request with the same body/HMAC but a different `x-shopify-shop-domain` header requires no secret material and no interaction with Shopify's authentication flow — only network access to the app's public webhook endpoint.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in `to_signable_string` (or otherwise cryptographically bind them to the payload) so `HmacValidator.validate` fails if any of these identity fields are altered relative to what Shopify actually signed. At minimum, document that the `shop` field of `WebhookMetadata` is not covered by the current HMAC check and must not be trusted for tenant routing without an additional binding (e.g., cross-checking against a shop the app has an active session/installation for), per the "check the identity fields you act on" recommendation from the referenced report.

### Proof of Concept
```ruby
# Step 1: A malicious but legitimately-installed merchant (shop "attacker.myshopify.com")
# receives a real webhook delivery from Shopify for their own shop:
raw_body = '{"id": 1, "note": "hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body) # captured, not computed by attacker

# Step 2: Attacker replays the same body/hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop they do not own:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),   # still valid! only raw_body is signed
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, unsigned field
  "x-shopify-webhook-id" => "attacker-controlled-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked),
#    handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the payload never originated from that shop.
```
