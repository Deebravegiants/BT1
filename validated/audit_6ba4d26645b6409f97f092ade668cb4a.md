### Title
Operator/User QR freshness is validated only at scan time, not re-checked before signup enrollment/upload, allowing stale QR-bound data to be used after a significant execution delay - (File: src/plans/mod.rs)

### Summary
The reported bug describes contracts that validate oracle prices only against the current execution time and never against the time the deposit/withdrawal/order was originally requested, so a stale request can be executed with prices/context from long after creation. The orb-core signup flow has an analogous pattern: the freshness of the operator QR code (and the user QR code bound to it) is checked only when the `ResolvedQrCodes` are assembled in `scan_remaining_qr_codes`, but that freshness is never re-validated at the point where the signup is actually executed (enrollment/PCP upload), even though a large amount of time-consuming work happens in between.

### Finding Description
`scan_remaining_qr_codes` accepts previously-scanned operator data only if `operator_data.timestamp.elapsed() < operator_qr_expiration_time` [1](#0-0) , and freshness is likewise used to bound waiting time for the user QR scan in `idle_scan_user_qr_code` [2](#0-1) . Once `ResolvedQrCodes` is produced, `do_signup` proceeds through a long sequence of operations — a fixed UX delay, `biometric_capture`, `biometric_pipeline`, `detect_fraud`, `build_pcp`, PCP upload (`upload_pcp_tier_0`, tier1/tier2 sends), and finally `enroll_user` — all using the `qr_codes`/`operator_data` and `user_data` captured at scan time [3](#0-2) . None of this later code re-checks `operator_data.timestamp.elapsed()` against `operator_qr_expiration_time`, nor is there any equivalent freshness check for the user QR-derived data before the credentials/PCP are built and enrollment is executed.

This mirrors the report's root cause exactly: a value (oracle price / QR-scan timestamp binding) is validated to be within an acceptable window only at request/collection time, but is never re-validated at the actual execution/commit point (`executeDeposit` vs. `enroll_user`/PCP upload), despite the two points potentially being separated by an arbitrary and possibly large amount of time (slow biometric capture retries, pipeline processing, network stalls during PCP upload, etc.).

### Impact Explanation
If the elapsed time between QR-code scanning and enrollment execution is large (e.g., due to slow biometric capture, retries, or pipeline delays), a signup can complete and be attributed to an operator/location and user binding that is stale relative to the orb's freshness policy encoded in `operator_qr_expiration_time`. Because the operator location and QR binding are the pieces of context the backend uses to attribute/authorize the signup, this can result in a signup being committed under operator/location context that should have been considered expired by the time enrollment/upload actually executed — a misattributed-signup class impact analogous to the price-staleness impact in the report (execution with information stale relative to what should be current at commit time).

### Likelihood Explanation
The stages between the freshness check and final enrollment (`biometric_capture`, `biometric_pipeline`, `build_pcp`, upload, `enroll_user`) are all normal, non-adversarial parts of the signup flow and can legitimately take a non-trivial amount of time, especially under retries, slow hardware/pipeline conditions, or slow network for PCP uploads. No attacker action is required to trigger the gap; it can occur under ordinary operational delay, making it moderately likely to occur without any additional configuration change (only requiring elapsed real time to approach or exceed `operator_qr_expiration_time` during those stages).

### Recommendation
Re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` (and any equivalent freshness bound for the user QR data) immediately before committing state that depends on it — i.e., right before `build_pcp`/`upload_pcp_tier_0` and before calling `enroll_user` in `do_signup` — and abort/re-scan if the freshness window has elapsed by execution time, mirroring the check already performed in `scan_remaining_qr_codes` [1](#0-0) .

### Proof of Concept
1. Operator QR is scanned; `OperatorData.timestamp` is set to `Instant::now()` and validated fresh in `scan_remaining_qr_codes` [4](#0-3) .
2. Signup proceeds into `do_signup`, which reads the config-provided `operator_qr_expiration_time` but only uses it earlier, in `scan_remaining_qr_codes`, not again later in the same function [5](#0-4) .
3. `biometric_capture`, `biometric_pipeline`, fraud detection, PCP building/upload, and `enroll_user` all execute using the same `qr_codes`/`operator_data`, with no additional timestamp check [6](#0-5) .
4. If the cumulative time of steps 3 exceeds `operator_qr_expiration_time` (default 23 hours, but potentially any configured shorter window per `Config::default` [7](#0-6) ), the enrollment still completes using operator/location context that should have been treated as expired at commit time — exactly analogous to executing a deposit with stale prices that were only checked to be fresh relative to the current block time, not relative to the original request.
