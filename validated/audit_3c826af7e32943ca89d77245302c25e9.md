### Title
Decimal-scaling helpers in `pallet-hyper-fungible-token` silently skip the divide when local decimals exceed EVM decimals, allowing an unbacked mint or a bridge-amount truncation to (near) zero - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_erc20` and `convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs` scale a token amount between the local substrate asset's decimals and the EVM contract's decimals for every `send` and `on_accept`/`on_timeout` in `pallet-hyper-fungible-token`. Both functions compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)` (or vice-versa), which silently becomes `0` — i.e. "no scaling" — whenever the subtraction would otherwise be negative, instead of dividing in the other direction. This is analogous to the D3Trading `buyToken()` bug (M-13): a decimal mismatch between two assets is not rounded/handled safely, and a raw magnitude from one token's decimal space is reinterpreted as if it were in the other token's decimal space, producing an amount that is off by the missing power of ten.

### Finding Description [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both helpers assume `erc_decimals >= local_decimals` (the documented/tested case is EVM=18, local=12, e.g. `BridgeTokenTest.t.sol` comment: "18 here while BRIDGE is 12 decimals on nexus, so the pallet scales by 10^6 in both directions"). `Precisions` storage (`modules/pallets/hyper-fungible-token/src/lib.rs:145-155`) records `erc_decimals` per `(AssetId, StateMachine)` with no constraint forcing it to be `>= local_decimals`; a token can legitimately be registered where the local asset has *more* decimals than the paired EVM contract (e.g. an 18-decimal local asset bridged to an 8-decimal EVM token, mirroring the exact 18-decimal/8-decimal mismatch in the referenced report).

In that configuration:
- **`send` (outbound, `modules/pallets/hyper-fungible-token/src/lib.rs:241-325`)**: `decimals` (local) = 18, `erc_decimals` = 8. `erc_decimals.saturating_sub(local_decimals) = 0`, so `convert_to_erc20` multiplies by `10^0 = 1` instead of dividing by `10^10`. The dispatched `Message.amount` sent to the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract is therefore `10^10`x larger than the correctly-scaled amount, and the EVM contract mints that inflated amount to the recipient — an unbacked mint of the wrapped token on the destination chain, funded only by burning/escrowing the much smaller correctly-scaled amount on the source chain.
- **`on_accept` (inbound, `modules/pallets/hyper-fungible-token/src/module.rs:74-91`)**: the reverse configuration truncates the minted/transferred local balance toward zero instead of scaling up, so a legitimate incoming transfer can be reduced to a token amount many orders of magnitude smaller than intended — permanent loss of the bridged value for the recipient once escrow/burn already happened on the source side.

Both `send` and the ISMP `on_accept`/`on_timeout` handlers are reachable by any unprivileged user dispatching a transfer through the pallet's `send` extrinsic or by any relayer delivering the resulting cross-chain message, matching the "token bridge mint/burn" analog class explicitly in scope.

### Impact Explanation
This is a concrete unbacked-mint / permanent-fund-loss bug class:
- If `erc_decimals < local_decimals` for a registered pair, every outbound `send` mints `10^(local_decimals - erc_decimals)` times too many tokens on the destination EVM chain relative to what was actually escrowed/burned on the source chain, letting any user drain the bridge's backing 1:1 collateral guarantee (unbacked mint).
- In the opposite direction (inbound receipt with the same misconfigured pair), the recipient can receive an amount truncated by the same factor, causing an irrecoverable loss of value for legitimate transfers.

Either direction constitutes the kind of concrete theft/unbacked-mint or fund-loss impact this analysis is meant to surface.

### Likelihood Explanation
Likelihood depends entirely on whether any registered token pair has `local_decimals > erc_decimals`. The pallet's own test fixture (`BridgeTokenTest.t.sol`) explicitly exercises the opposite, "expected" case (`erc_decimals=18 > local_decimals=12`), and I did not find (with the tools/time available) an explicit guard in `register_token`/`update_token` (`modules/pallets/hyper-fungible-token/src/lib.rs`) preventing `Precisions` from storing a `decimals` value smaller than the local asset's own decimals. I was unable to fully verify, within the remaining budget, whether such a guard exists elsewhere (e.g. in `TokenRegistration`/`TokenUpdate` validation logic in `modules/pallets/hyper-fungible-token/src/module.rs` or `lib.rs`) — this should be confirmed by a deeper review of the registration call path before treating this as fully proven. Given that the two `saturating_sub` calls in `impls.rs` have no runtime assertion enforcing the ordering they implicitly assume, this is at minimum a latent correctness bug that becomes exploitable the moment any token is registered (intentionally or by operator mistake) with the "wrong" decimal ordering.

### Recommendation
Replace the one-directional `saturating_sub`-based scaling in `convert_to_balance`/`convert_to_erc20` (`modules/pallets/hyper-fungible-token/src/impls.rs`) with logic that explicitly handles both directions (multiply when scaling up, divide when scaling down), mirroring how `VWAPOracle._normalizeAmount` (`evm/src/utils/VWAPOracle.sol:240-248`) already handles both `decimals < 18` and `decimals > 18` cases. Additionally, add a registration-time validation (in `register_token`/`update_token`) that either enforces the assumed decimal ordering or rejects/warns on pairs where it does not hold, so a misconfigured `Precisions` entry cannot silently produce an inflated mint or truncated transfer.

### Proof of Concept
Register a token via `register_token` with `local_id` pointing to a local asset with 18 decimals, and a `ChainConfig.decimals = 8` for the EVM destination (a valid registration under the pallet's current constraints, see `modules/pallets/hyper-fungible-token/src/lib.rs:237-325` and `types.rs:66-90`). Any account then calls:
```rust
Pallet::<T>::send(origin, SendParams { asset_id: <the 18-dec asset>, amount: 1_000_000_000_000u128 /* 1e12, i.e. 0.000001 token at 18dp */, destination, recipient, .. })
```
`convert_to_erc20(1_000_000_000_000, erc_decimals=8, local_decimals=18)` computes `10u128.pow(8u8.saturating_sub(18) as u32) = 10u128.pow(0) = 1`, so `erc20_amount = 1_000_000_000_000` is dispatched as the `Message.amount` and minted 1:1 by the EVM `HyperFungibleToken` contract's `onAccept` — instead of the correctly scaled `1_000_000_000_000 / 10^10 = 100` (the value that would preserve economic parity), an amount `10^10`x larger is minted on the destination chain against a tiny amount escrowed/burned on the source chain.
