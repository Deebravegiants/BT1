### Title
Phantom-order price aggregation weights bids by an unprotected live token balance, letting a solver buy majority weight and dictate the published pool exchange rate used to price real intent orders - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
Hyperbridge's intent/phantom-order pricing pipeline (SDK `aggregatePhantomBids`, consumed by the Nexus indexer's `handlePhantomOrderPrices` handler and by the `IntentGateway.quoteIntent` path) selects a leg's canonical price with `weightedMedian`, weighting each solver's quote by that solver's *live, unprotected* on-chain balance of the leg's output token, read via a plain `eth_call` at the `"latest"` block tag. Because `weightedMedian` performs a *selection* (returns one bidder's exact quote) rather than a blend, a party that can temporarily dominate that balance can make the published price for a leg equal exactly the price it quoted. This is the same bug class as the Array Finance incident: a pricing mechanism that trusts an easily-inflatable, instantaneous balance/supply figure with no time-weighting or manipulation resistance.

### Finding Description
`getTotalSolverBalance` / `memoizedSolverBalance` compute a bidding solver's weight as raw ERC-20 `balanceOf` plus ERC-4626 `maxWithdraw`, read at the chain head (`blockTag = "latest"` by default): [1](#0-0) 

That weight directly drives which bid's price is published as the leg's price: [2](#0-1) 

The project's own flow documentation states the consequence explicitly: *"a solver holding over half the leg's weight sets the published price verbatim"* and that `weightedMedian` is a selection, not a blend, so the result is always one bidder's raw integer: [3](#0-2) 

That per-leg median then feeds `updateLiquidityPools`, which renormalizes it into the pool's `sellRate`/`buyRate`: [4](#0-3) [5](#0-4) 

Those published `sellRate`/`buyRate` values are the exact numbers the SDK uses by default to price **real** cross-chain intent orders that end users submit and solvers fill for real funds: [6](#0-5) [7](#0-6) 

Root cause: the weight (the analog of Array Finance's `totalSupply`) is a point-in-time on-chain balance with no TWAP, no cap, no minimum bidder diversity requirement, and no cross-checking against historical balances. Any account that is a permitted "intent solver" for a chain (i.e., one on the delegated `solverAccounts` allow-list, which the code treats as an "unprivileged message dispatcher/intent solver" class actor reachable from a single relayed bid) can inflate its balance of the leg's output token immediately before/during a bid window — e.g., via a flash loan, a large temporary transfer, or borrowing from a lending market for the duration of the window — bid a favorable-to-itself price, and become the majority-weight quote, which the aggregation then publishes verbatim as the market price.

### Impact Explanation
The manipulated price is not confined to the phantom-order bookkeeping; it becomes the canonical `LiquidityPool.sellRate`/`buyRate` that `IntentGateway.quoteIntent` uses by default to size real orders' `amountIn`/`amountOut` (documented as the new default strategy): [8](#0-7) 

A manipulated rate lets an attacker construct real intent orders that receive far more output than the true market rate would allow (theft from the counterparty solver/liquidity), or forces legitimate users into mispriced fills. This satisfies "concrete theft" via forged/false pricing feeding an actual value-transfer path (real order fills), analogous to the Array Finance loss driven by a manipulable pricing input.

### Likelihood Explanation
Medium. Exploitation requires: (1) the attacker control or be a "solver" account whose bid the aggregation accepts (`isVerifiedSolverBid`/delegation check) — a permissionless-enough bar since solver accounts are the intended actors this pipeline exists to serve; (2) enough temporary capital in the leg's output token on the destination chain to dominate weight over the bid window, which for cheaply-borrowable tokens (stablecoins, WETH, etc. — exactly what phantom-order legs quote) is realistic via lending markets rather than a strict same-transaction flash loan; (3) the leg/pool must not otherwise have deep, well-distributed competing solver liquidity, which is plausible for newer chains/pairs with few solvers online. This is lower likelihood than a pure single-transaction flash-loan attack (the balance read happens asynchronously, keyed to the block the indexer processes the `PhantomBidWindowExhausted` event, not necessarily the same block as the bid), but the underlying design — an unweighted, TWAP-free, live-balance-as-price-authority mechanism — is the exact fragility class the report describes.

### Recommendation
- Do not let `weightedMedian` return a single dominant bidder's raw quote unmodified; cap any single solver's weight share (e.g., at some percentile of total leg weight) so no bidder can single-handedly set the price.
- Require the balance backing a bid's weight to be sampled over a window (e.g., averaged across multiple blocks) or require a minimum bidder count/diversity before a leg's median is trusted and published to `LiquidityPool`.
- Add sanity/deviation bounds when writing `sellRate`/`buyRate`: reject or flag updates that move the rate beyond a configured bound versus the previous published rate within one window.
- Consider decoupling real-order pricing (`quoteIntent`'s `indexed_rates` strategy) from the same live snapshot solvers can influence, e.g., by requiring rate staleness/consistency checks across multiple independent chains' samples before use.

### Proof of Concept
Conceptual PoC (not executable from the index alone, given async timing and live-chain dependencies):
1. Attacker registers/controls a delegated solver account for chain `EVM-X` participating in a phantom order on pair (tokenA, tokenB), where tokenB is borrowable in size on `EVM-X` (e.g., via a lending protocol).
2. During (or just before) the active bid window for the phantom order, attacker borrows a very large amount of tokenB into the solver account, so `getTotalSolverBalance(EVM-X, tokenB, solver)` vastly exceeds all other bidders' balances.
3. Attacker submits a bid quoting an artificially favorable output amount for the tokenA→tokenB leg.
4. When `PhantomBidWindowExhausted` fires and the indexer runs `aggregatePhantomBids`, the attacker's bid's weight (`weights` in `phantom-aggregation.ts:1479-1497`) dominates; `weightedMedian` (`phantom-aggregation.ts:1551`) returns the attacker's exact quoted price as `medianPrice`.
5. `updateLiquidityPools` writes this into `LiquidityPool.sellRate`/`buyRate`.
6. Attacker (or a colluding account) immediately calls `IntentGateway.quoteIntent`/places a real order priced off the now-manipulated `sellRate`/`buyRate`, receiving output disproportionate to the true market rate, extracting value from the solver/liquidity that fills it.
7. Attacker repays the borrowed tokenB once no longer needed for weight domination.

export async function getTotalSolverBalance(
	evmRpcUrl: string,
	chain: string,
	token: string,
	solver: string,
	yieldVaults: YieldVaultMap,
	blockTag = "latest",
): Promise<bigint> {
	const padded = solver.replace("0x", "").padStart(64, "0")
	const raw = await ethCallUint(evmRpcUrl, token, `0x70a08231${padded}`, blockTag) // balanceOf(address)
	const vaults = yieldVaults[chain]?.[token.toLowerCase()] ?? []
	const vaultBalances = await Promise.all(
		vaults.map((v) => ethCallUint(evmRpcUrl, v, `0xce96cb77${padded}`, blockTag)), // maxWithdraw(address)
	)
	return vaultBalances.reduce((acc, b) => acc + b, raw)
}

export function poolRateFromQuote(
	medianPrice: bigint,
	resolved: Pick<ResolvedPoolLeg, "inDecimals" | "outDecimals">,
	standardAmount: bigint,
): bigint {
	const scale = 10n ** BigInt(POOL_RATE_DECIMALS - resolved.outDecimals)
	const inputUnit = 10n ** BigInt(resolved.inDecimals)
	return (medianPrice * scale * inputUnit) / standardAmount
}

function quoteWithIndexedRate(
	params: QuoteIntentParams,
	tokenIn: ResolvedQuoteAsset,
	tokenOut: ResolvedQuoteAsset,
	selectedRate: SelectedIndexedRate,
	rates: BuyAndSellRates,
	protocolFeeBps: bigint,
): IndexedRateQuoteIntentResult {
	const inputUnit = 10n ** BigInt(tokenIn.decimals)
	const outputUnit = 10n ** BigInt(tokenOut.decimals)
	if (params.amountIn !== undefined) {
		const netAmountIn = deductProtocolFee(params.amountIn, protocolFeeBps)
		const amountOut =
			selectedRate.side === "buy"
				? (netAmountIn * selectedRate.scaledRate * outputUnit) / (inputUnit * INDEXED_RATE_SCALE)
				: (netAmountIn * outputUnit * INDEXED_RATE_SCALE) / (inputUnit * selectedRate.scaledRate)
		if (amountOut <= 0n) throw new InvalidIndexedRateError("quote rounds down to zero output")
		return buildResult("EXACT_INPUT", params.amountIn, amountOut, selectedRate, rates, protocolFeeBps)
	}

	if (params.amountOut === undefined) throw new Error("Quote amount is missing after validation")
	const netAmountIn =
		selectedRate.side === "buy"
			? divCeil(params.amountOut * inputUnit * INDEXED_RATE_SCALE, selectedRate.scaledRate * outputUnit)
			: divCeil(params.amountOut * inputUnit * selectedRate.scaledRate, outputUnit * INDEXED_RATE_SCALE)
	const amountIn = grossUpForProtocolFee(netAmountIn, protocolFeeBps)
	return buildResult("EXACT_OUTPUT", amountIn, params.amountOut, selectedRate, rates, protocolFeeBps)
}
