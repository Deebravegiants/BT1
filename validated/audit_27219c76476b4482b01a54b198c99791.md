## Title
Uniswap V4 spot-price venue pricing can be flash-loan manipulated to drain solver-held funds during intent fills, and the safety clamp that once bounded the loss has been explicitly disabled - (File: sdk/packages/simplex/src/strategies/fx.ts, sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
Simplex's `FXFiller` prices curveless (venue-priced) trading pairs directly from a Uniswap V4 pool's current tick (`sqrtPriceX96`), which is an instantaneous spot price with no TWAP or reserve-based manipulation resistance. This is exactly the bug class in the referenced Abracadabra `MagicLpAggregator` report: an on-chain price read that reflects current pool state can be pushed within the same block via a swap (flash-loan funded or otherwise), and any consumer that trusts it as ground truth pays out based on the manipulated number. Here the consumer is a live solver bot that fills user intents and transfers real tokens, so a manipulated quote directly drains solver inventory.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` refreshes on-chain state and computes the USD price straight from the pool's spot price (`sdkPool.token0Price`/`token1Price`, derived from `sqrtPriceX96`), picking the most-liquid qualifying pool: [1](#0-0) [2](#0-1) 

This price feeds `FXFiller.resolveLegRates`, which converts it directly into the leg's fill rate (`rate = 1/venueUsd`) for any curveless pair whose `token0` is a USD stable: [3](#0-2) 

The only defense is `checkPriceGuard`, which is optional per chain and, when configured, only rejects a quote that deviates from a *static* reference by more than `maxDeviationBps` — it is not a manipulation-resistance mechanism, just a stale/thin-pool sanity bound: [4](#0-3) 

The project's own docs confirm the guard is optional and that pool-based pricing "trusts the live pool": [5](#0-4) 

Critically, the codebase itself documents that the per-leg loss bound which used to cap exposure to "a manipulated venue price" has been deliberately disabled — the overfill clamp is now warn-only: [6](#0-5) 

The same flow doc for venue pricing independently confirms `checkPriceGuard` is the only defense and it does not account for execution/impact cost: [7](#0-6) 

### Impact Explanation
An unprivileged actor (an intent submitter, matching the "intent solver" surface explicitly in scope) can:
1. Execute a swap (optionally flash-loan funded) against the configured Uniswap V4 pool to push its spot tick, crashing the reported USD price of the "exotic" token.
2. Submit an intent order swapping the USD-stable `token0` for the exotic `token1` in the same or a near-simultaneous block.
3. `FXFiller` prices the leg using the manipulated `1/venueUsd` rate, which — with the price guard unconfigured (an explicitly supported and documented configuration) or with the manipulation kept inside the configured `maxDeviationBps` band — computes an inflated `policyMaxOutput`.
4. Because the overfill clamp is now warn-only, the filler executes the fill and transfers the excess exotic tokens out of its own wallet/Uniswap V4 LP position, realizing a real loss of solver-held funds with no on-chain protection stopping the payout.

This is a concrete, unbacked-value transfer out of the solver's funding venue (LP position withdrawals plus wallet balance), i.e., theft of funds reachable from a single submitted intent/order plus an ordinary DEX swap.

### Likelihood Explanation
- The attack requires only standard DEX interaction (a swap against the exotic/stable pool) plus a normal intent submission — both are permissionless, single-transaction-reachable actions.
- The price guard is optional by design ("omit both to leave the chain unguarded"), so any operator who has not configured it is fully exposed.
- Even with the guard configured, it bounds deviation from a static reference, not manipulation — an attacker can move the pool price up to the configured band and still capture profit on repeated fills, or exploit thinly-liquid exotic/stable pools where realistic flash-swap sizes exceed the guard's band without needing capital beyond swap fees.
- The removal of the overfill clamp (explicitly called out in code comments as previously protecting against "a manipulated venue price") materially increases likelihood/impact versus the pre-existing state.

### Recommendation
- Replace or supplement the instantaneous `sqrtPriceX96`-derived spot price with a manipulation-resistant price (e.g., a TWAP over multiple blocks, or a Chainlink/other independent oracle cross-check similar to the original report's recommended mitigation).
- Make the price guard mandatory (not optional) for any venue-priced pair, and tighten `maxDeviationBps` defaults.
- Reinstate a hard overfill ceiling (not just a warning) for venue-priced legs, since these lack the router-level slippage protection that direct swaps have.
- Consider requiring the guard's reference price to be refreshed from an independent source rather than a static TOML value that can drift stale.

### Proof of Concept
Conceptually mirroring the original report's flash-loan PoC against `MagicLpAggregator`:
1. Attacker flash-loans the stable side of the configured Uniswap V4 exotic/USDC (or USDT) pool and swaps it into the exotic token, crashing `sqrtPriceX96` and thus `sdkPool.token1Price`/`token0Price`.
2. In the same window, attacker (or a colluding party) submits an `IntentGateway` order whose leg matches this curveless, venue-priced pair (`token0` USD-stable, `token1` exotic), sized so `resolveLegRates` → `venueUsdPrice` returns the crashed price.
3. `FXFiller.calculateProfitability` computes `policyMaxOutput` from the manipulated rate; since the overfill clamp at `fx.ts` lines 678-701 is warn-only, the filler proceeds to fill at the inflated exotic amount, pulling excess tokens from its Uniswap V4 LP position (`UniswapV4FundingPlanner.planWithdrawalForToken`) and/or wallet.
4. Attacker reverses the initial swap to restore the pool and repays the flash loan, keeping the excess exotic tokens received from the solver's fill as profit. [8](#0-7)

```typescript
	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}
```

```typescript
		const c0 = pos.currency0.toLowerCase()

			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),

		}

	}
```

```typescript
	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```

```markdown
`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
```
