### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` field that identifies which tenant/store the webhook belongs to is taken from an HTTP header that is never included in the signed material. This breaks the identity binding `hmac_signed_bytes == bytes_the_app_trusts_for(shop)`, exactly the bug class described in the reference report (a value used for a security decision that is not covered by the integrity check).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are instead read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no HMAC coverage: [2](#0-1) 

`Registry.process` verifies only this body-only HMAC and then hands the unverified `shop` header straight to the app's handler: [3](#0-2) 

The gem's own documentation instructs host apps to treat `data.shop` as a trusted, verified tenant identifier once `Registry.process` has run ("This will verify the request did indeed come from Shopify"), and shows it being used directly (e.g., `shop_domain: data.shop`) to route/attribute the webhook payload: [4](#0-3) [5](#0-4) 

Because the webhook HMAC secret (`api_secret_key`) is a single, app-wide secret shared across every shop that has installed the app — not a per-tenant secret — any merchant who has installed the app (an "unprivileged internet user" relative to other tenants) legitimately receives, for their own store, genuine `(raw_body, hmac)` pairs signed with that shared secret. Since the `shop` header is outside the signed bytes, that merchant can replay the exact same `raw_body`/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value (naming a victim shop). `Utils::HmacValidator.validate` will pass (the HMAC over the body is still valid), and `Registry.process` will construct `WebhookMetadata` with the attacker-chosen `shop`, causing the host application to process/attribute Shopify-authenticated-looking data under another tenant's identity.

This is not a case of the host app "ignoring the documented API" — the documentation explicitly presents `data.shop` as the verified output of `Registry.process` for tenant attribution, so relying on it is the intended, documented usage pattern.

### Impact Explanation
This crosses a tenant boundary: a request that is only proven to originate from *some* installation of the app can be relabeled to appear as if it belongs to *any other* shop using the same app, without requiring the victim's or the app's `client_secret`/access token. This matches the Critical "cross-tenant access" impact category — a malicious/compromised merchant can inject or spoof webhook events attributed to another merchant's store, corrupting that store's app-side data or triggering privileged actions keyed on `shop`.

### Likelihood Explanation
Likelihood is realistic for any multi-tenant app built on this gem: the attacker only needs to be a legitimate installer of the app (no elevated privilege, no access to `api_secret_key`, no TLS interception) and simply needs to capture one of their own genuine webhook deliveries (trivial, since it's delivered to their own endpoint) and re-POST it with a modified shop header — an action fully reachable from the public internet against the app's public webhook callback URL.

### Recommendation
Bind the tenant identity to the signed material instead of trusting the unauthenticated `shop` header:
- Include `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or
- Cross-check the header-derived `shop` against an independently trusted source (e.g., look up the webhook registration/subscription by `webhook_id` and confirm it belongs to the claimed shop) before invoking the handler, and reject webhooks where the two disagree.

### Proof of Concept
1. App is installed on `shopA.myshopify.com`. Shopify sends a genuine webhook to the app's callback endpoint with headers `shopify-shop-domain: shopA.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over raw_body>`, and body `B`.
2. The merchant of `shopA` (an unprivileged actor with respect to `shopB`) captures `(B, hmac)` from their own delivered webhook.
3. The attacker re-sends a request to the same endpoint with body `B`, the same `shopify-hmac-sha256` value, but header `shopify-shop-domain: shopB.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190` succeeds because it only checks `raw_body`.
5. `WebhookMetadata.new(... shop: request.shop ...)` at `lib/shopify_api/webhooks/registry.rb:198` now reports `shop: "shopB.myshopify.com"`, and the host app's handler processes/attributes `B`'s content to `shopB`, per the documented usage pattern in `docs/usage/webhooks.md`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
