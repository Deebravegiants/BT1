### Title
Webhook `shop-domain` header trusted as tenant identity while the HMAC only signs the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's tenant identity (`shop`) from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, but `Utils::HmacValidator` validates the HMAC only against the raw request body via `to_signable_string`. The header carrying the shop identity is never part of the signed material, so a valid HMAC only proves the *body* was produced with the app's `client_secret` — it proves nothing about which shop the event belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it to the `hmac` header: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relation to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unauthenticated header) as the tenant identity into `WebhookMetadata`, which is delivered to the app's handler as the trusted shop for that event: [4](#0-3) [5](#0-4) 

This is the same bug class described in the report: an operation (here, tenant attribution of a verified event) is driven by a field (`shop-domain`) that the identity/integrity check (the HMAC) does not cover. The equality the gem implicitly promises but fails to enforce is:
`shop bound by HMAC == shop delivered to handler`
In reality the left side doesn't exist at all — no shop value is signed — while the right side is attacker-controlled header data.

Because a public Shopify app's `client_secret` is a single secret shared across every installed shop (not shop-specific), any tenant that legitimately receives a webhook for its own shop possesses a body+HMAC pair that is valid under the same secret used for every other shop of that app. Replaying that exact body with the `shop-domain` header rewritten to a different shop yields a request that still passes `HmacValidator.validate` (since the body is unchanged) but is attributed by the gem to an arbitrary victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: `Registry.process` and the delivered `WebhookMetadata` allow one merchant's genuine, validly-signed webhook payload to be attributed to a different, victim merchant simply by changing an unauthenticated header. Depending on how a host app keys per-shop state off `WebhookMetadata#shop` (e.g., processing `app/uninstalled`, `shop/redact`, or order/customer data events), this enables cross-tenant data corruption or disclosure attributed to the wrong shop — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires the attacker to control (or observe) a legitimately delivered webhook body+HMAC for a shop where they hold merchant/admin access to the target app (any single-shop install is enough, since `client_secret` is shared across installs of the same app), then replay that request to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No access to the app's `client_secret`, access tokens, or the victim's credentials is required — only observation of one legitimate webhook delivery for any shop.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the material that is cryptographically verified, or otherwise reject/ignore the header-derived shop for trust decisions unless it is corroborated by data inside the verified body. At minimum, `Registry.process`/`WebhookMetadata` should not present `request.shop` as an authenticated fact to handlers without documenting that it is unverified, and host-app guidance should require cross-checking the header shop against the shop embedded in the JSON body where available.

### Proof of Concept
1. App has webhooks configured for shops A (attacker) and B (victim), sharing the same `client_secret`.
2. Attacker's own shop A triggers a webhook (e.g., `orders/create`) to the app; attacker captures the raw body and the valid `X-Shopify-Hmac-Sha256` header for that request.
3. Attacker resends this exact body/HMAC pair to the app's webhook endpoint, replacing the `X-Shopify-Shop-Domain` header with `shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC — unaffected by the header change: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged header value and dispatches it to the handler as if it were a verified event for shop B: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)

            secret,
            signable_string,
          )
        end
