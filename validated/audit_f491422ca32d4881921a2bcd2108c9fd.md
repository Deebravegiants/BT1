## Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify," but the HMAC verification only covers the raw request body — it never binds the `shop-domain` header (or any other header) into the signed payload. Because the same `Context.api_secret_key` HMAC secret is shared across every shop that installs the app, any merchant (an ordinary, unprivileged install of the app on their own store) who has ever obtained one valid `(raw_body, hmac)` pair for their own shop can present that identical body/HMAC pair to the app's public webhook endpoint together with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a different, victim shop. The signature will still validate, and the handler will be invoked believing the event legitimately originated from the victim shop.

## Finding Description
`Registry.process` only checks the body-derived HMAC before dispatching to the handler: [1](#0-0) 

The signable content used for that HMAC is exclusively the raw body, per `VerifiableQuery`: [2](#0-1) 

and `HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` and compares it against the `hmac` header, with no reference to `shop`, `topic`, or any other header: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers and passed to the handler unmodified: [4](#0-3) [5](#0-4) 

The identity binding that the gem's own documentation implies — "This will verify the request did indeed come from Shopify" and thus `data.shop` is "The shop domain of the webhook" — does not actually hold: [6](#0-5) [7](#0-6) 

The broken equality is:
`HMAC-verified(raw_body, api_secret_key) == true` is treated as `shop header == authenticated tenant of raw_body`, but in reality the `shop` header is never part of the signed material, so `verified body` and `claimed shop` are independent values that an attacker can mix and match.

Because `api_secret_key` is one single value shared by the app across **all** merchant installs (it's the app's client secret, not per-shop), any shop that installs the app can legitimately trigger a real Shopify-signed webhook to the app's endpoint (e.g. by creating an order/product with attacker-chosen field content), record the `(raw_body, hmac)` pair, and then send a new HTTP request directly to the app's public webhook route reusing that exact body/HMAC while substituting the victim shop's domain into the `shop-domain` header. `Registry.process` accepts it because HMAC verification never inspected the header.

## Impact Explanation
This breaks the tenant boundary the whole webhook subsystem is supposed to enforce: attacker-controlled data (a real webhook body they legitimately generated on their own shop) can be delivered to the app labeled as belonging to any other victim shop. Depending on what the host app's webhook handler does with `data.shop`/`data.body` (e.g., updating locally cached shop records, triggering shop-scoped side effects, feeding a background job keyed by shop), this enables cross-tenant data corruption/injection under a victim's identity — a cross-tenant access impact.

## Likelihood Explanation
The prerequisite — being able to install the app on one's own store and trigger any webhook topic the app subscribes to — is available to any unprivileged internet user who installs a public Shopify app (development stores are free and require no privileged Shopify credentials). No knowledge of `api_secret_key` or any merchant's access token is needed; only capture of one's own legitimately-received webhook request and replay with a modified header is required.

## Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the signed material verified by `HmacValidator`, or independently authenticate the shop identity against a known/registered set of shops before dispatching to the handler, rather than trusting the `x-shopify-shop-domain` header solely because the body-only HMAC validated.

## Proof of Concept
1. Attacker installs the target app on their own (attacker-owned) development store, a normal unprivileged action.
2. Attacker triggers a webhook subscribed by the app (e.g. `products/update`) with a payload of their choosing content, causing Shopify to POST a correctly HMAC-signed request (`raw_body`, `x-shopify-hmac-sha256`) to the app's public callback endpoint, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures that exact `raw_body` and `hmac` value (their own request, no MITM required — it's a request they caused and can also directly replicate by resending a copy from their own client).
4. Attacker sends a new POST directly to the app's public webhook route with the **same** `raw_body` and `hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` against the shared `api_secret_key`.
6. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com` while `body` is fully attacker-controlled content, and the host app processes it as a legitimate event for the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
