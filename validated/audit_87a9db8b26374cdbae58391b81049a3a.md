### Title
Attacker-grown debt share value overflows i128 inside accrual, permanently freezing all market entrypoints - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
CVE-2021-44491 is a crafted-input size calculation that produces an extreme intermediate value and crashes the application. The direct analog in XOXNO Lending is the RAY-value ceiling in `accrue_step`: `scaled_to_original(borrowed, borrow_index)` computes `borrowed_shares × borrow_index / RAY` with no clamp, so once the scaled-debt value exceeds `i128::MAX`, the accrual panics with `GenericError::MathOverflow`. Because `interest::global_sync` runs `accrue_step` first inside every state-changing verb, the panic permanently bricks the market — no withdraw, repay, borrow, liquidate, or `update_indexes` can ever succeed again. The borrow-index cap (`MAX_BORROW_INDEX_RAY = 1e36`) is meant to bound growth, but the value overflow fires long before the index reaches the cap, so the guard never engages.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60-66` unscales the scaled debt before doing anything else:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
```

`scaled_to_original` (`common/src/rates/scaling.rs:14-16`) is `scaled.mul(env, index)` — `half_up(scaled × index / RAY)` — which panics when the product does not fit `i128`. `i128::MAX` ≈ 1.7e38 while RAY = 1e27, so a scaled debt of ~1e38 shares (e.g., ~1 billion whole tokens of an 18-decimal asset scaled to RAY) overflows at index ≈ 170×, well below `MAX_BORROW_INDEX_RAY` (1e36 = 1e9×). `update_borrow_index` clamps the index only after multiplying (`common/tests/rates/index.rs:497-517`), and nothing bounds `borrowed` against the index; `calculate_scaled_cap` saturates for cap checks but position accounting deliberately panics on overflow (`common/src/rates/scaling.rs:20-25`).

The repo's own harness proves the freeze end-to-end in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`: after enough accrual at high utilization on a steep curve, `update_indexes` returns `MATH_OVERFLOW` with `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw` and `repay` fail with the same error because every verb accrues first.

The single-attacker path is:
1. `controller::supply` a very large amount of a high-decimals asset on a hub market (caps can be lifted to `max_cap_for_decimals`, and validation only checks the cap, not `shares × index` headroom).
2. `controller::borrow` to push utilization into the steep segment of the curve, maximizing `compound_interest` growth per chunk.
3. Wait (or leave the market untouched — utilization drifts upward as debt compounds faster than supply, per the test file's own comment at lines 8-13), then anyone — including the attacker — calls `update_indexes`, which panics at `simulate.rs:60`.
4. Every subsequent call to `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `update_indexes`, and pool-side `update_indexes` for that market reverts forever.

### Impact Explanation
Permanent freezing of funds and permanent market liveness loss. All supplier principal and accrued interest in the affected (hub, token) book becomes unrecoverable: withdrawals revert, repayments revert, liquidations revert, and bad-debt cleanup/recapitalization revert because they all go through `global_sync` → `accrue_step` → `scaled_to_original`. No admin verb rescues it because the panic occurs before any privileged check. This is the "crash the application" consequence of the CVE mapped to a contract: the oversized computed value is `borrowed × borrow_index`, and the crash is a catchable-but-unavoidable `MathOverflow` panic on every call.

### Likelihood Explanation
The trigger conditions are demanding but entirely reachable by one unprivileged address. The attacker needs whale-scale capital in one market (the harness uses 1e9 whole tokens at 18 decimals) and sustained high utilization — which they can manufacture themselves by supplying and borrowing with two positions or two accounts, keeping utilization in the steep part of a configured curve. Accrual chunking caps each step at one year but does not bound cumulative index growth; `update_indexes` is permissionless, so the partitioning/cadence of accruals is attacker-influenced. Time-to-overflow is years at realistic curve parameters (the harness hits it inside ~40 years at 175% max rate at 98% utilization), which lowers likelihood but does not eliminate it — a stuck market cannot self-recover, so the window only ever widens. Severity: Medium (high impact, low likelihood).

### Recommendation
Bound the value calculation, not just the index. Concretely:
- In `accrue_step` (`common/src/rates/simulate.rs:60-61`), detect the `scaled_to_original` overflow before it panics (use a `try_`/saturating `mul_div` variant like `mul_div_floor_saturating` already used in `calculate_scaled_cap`) and clamp utilization to `RAY`/cap the index at `MAX_BORROW_INDEX_RAY`, letting the market continue to operate under the documented cap semantics instead of bricking.
- Alternatively, enforce an invariant on `borrow`: reject borrows where `scaled_borrow × MAX_BORROW_INDEX_RAY` would overflow `i128`, mirroring how listings validate caps via `require_cap_within_asset_domain`.
- Whichever is chosen, add a regression test asserting that a market at the RAY-value ceiling converges on the index cap rather than panicking, since `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` currently codifies the panic.

### Proof of Concept
The repository already contains an executable PoC: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`.

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))   // 175% max rate, optimal 75%
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // attacker supplies
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // attacker borrows to 98% util

// advance time; eventually:
//   try_update_indexes_for(&["BIG18"]) -> Err(MATH_OVERFLOW)
//   book.borrow_index < MAX_BORROW_INDEX_RAY  (cap never engaged)
//   try_withdraw_raw(BOB, "BIG18", 1) -> MATH_OVERFLOW   // supplier funds frozen
//   try_repay(ALICE, "BIG18", 1.0)   -> MATH_OVERFLOW    // debt unpayable
```

Root cause chain: `update_indexes` → pool `interest::global_sync` → `accrue_step` (`common/src/rates/simulate.rs:60`) → `scaled_to_original` (`common/src/rates/scaling.rs:14-16`) → `Ray::mul` → `MathOverflow` panic, before `update_borrow_index`'s clamp to `MAX_BORROW_INDEX_RAY` can ever take effect.
