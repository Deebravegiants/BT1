### Title
Webhook `shop` domain is trusted from an HMAC-unsigned header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` is read directly from the `x-shopify-shop-domain` HTTP header, but the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body, not this header. This breaks the identity binding: `shop` delivered to the app's webhook handler ≠ `shop` actually covered by the cryptographic signature, allowing an attacker to make the library report a forged/attacker-chosen shop for an otherwise-validly-signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) using `Context.api_secret_key`: [2](#0-1) 

Meanwhile, `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC of the body only, and then forwards `request.shop` (the unauthenticated header value) straight to the host app's handler via `WebhookMetadata`: [4](#0-3) [5](#0-4) 

Because `Context.api_secret_key` is a single shared app secret used for every shop that installs the app (not per-shop), any party who can obtain one validly-HMAC'd body+signature pair (e.g., by installing/operating their own test store using the same app and capturing a real webhook delivery) can replay that exact `body`/`hmac` pair while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the attacker-chosen `shop`.

This is the direct analog of the report's root cause pattern: an identity/ownership field (`receiver` in the L2 royalties case) that is checked against the wrong entity. Here the equality that should hold is:
`shop delivered to handler == shop authenticated by the signature`
but in practice:
`shop delivered to handler == shop header (attacker-controlled, unsigned)` while `HMAC-verified content == body only`.

### Impact Explanation
This crosses the tenant boundary this gem is responsible for enforcing: the webhook processing pipeline is the mechanism by which a Shopify app determines which merchant/shop an event pertains to. If a host application trusts `WebhookMetadata#shop` (as the library's own contract implies it should, since it is the only shop identifier exposed after HMAC validation succeeds), an attacker can inject events attributed to a shop of their choosing while using a body/signature pair they legitimately obtained for a different shop under the same app. Depending on how a host app keys data updates by `shop`, this can produce cross-tenant data corruption/confusion — matching the High-severity "cross-tenant access" category defined for this scan, since the trust boundary broken is precisely "the shop authenticated versus the shop attributed to the request."

### Likelihood Explanation
The attacker only needs the ability to send arbitrary HTTP requests to the app's webhook endpoint (unprivileged internet user) and to have obtained one legitimate `raw_body` + `hmac` pair produced by the shared `api_secret_key` — trivially available to anyone who installs the app on their own store, since standard webhook payloads (e.g., `app/uninstalled`, `shop/update`) are shop-agnostic content or have predictable structure. No access token, `client_secret`, or privileged access is required, satisfying the scan's unprivileged-attacker constraint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material, or otherwise cryptographically bind the header values used downstream to the payload that was HMAC-verified — e.g., verify that the `shop` header matches a shop value embedded in/derived from the verified body, or require host applications only trust `shop` values that have been independently confirmed via the installation record for that specific webhook subscription. At minimum, document prominently that `WebhookMetadata#shop` is NOT covered by the HMAC and must not be used as an authoritative tenant identifier without additional verification.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both use the same `Context.api_secret_key`.
2. Attacker controls `shop-a.myshopify.com` (e.g., a free dev store) and receives a real webhook delivery: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = shop-a.myshopify.com`.
3. Attacker resends this exact `raw_body = B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `HmacValidator.validate` at [6](#0-5)  succeeds because it only checks `B` against the signature — the shop header is irrelevant to this check.
5. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` at [7](#0-6) , even though the payload was never actually generated for `shop-b`.
