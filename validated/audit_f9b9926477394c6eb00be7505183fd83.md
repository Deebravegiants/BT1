Confirmed: the webhook HMAC only signs the raw body, while the `shop` (tenant identity), `topic`, `api_version`, and `webhook_id` come from unsigned headers and are trusted directly by `Registry.process` and passed straight into `WebhookMetadata` for the app's handler to act on.### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely by HMAC-validating the raw request body, then trusts the unsigned `shop-domain` header as the tenant identity handed to the app's handler. This breaks the identity binding `HMAC-authenticated bytes == identity acted upon`, since the HMAC covers only `@raw_body` while `shop` (and `topic`, `api_version`, `webhook_id`) are parsed straight from HTTP headers that are excluded from the signable string.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `HmacValidator.validate` computes/compares the signature over that signable string only: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from HTTP headers, none of which participate in the HMAC computation: [3](#0-2) 

`Registry.process` performs exactly one check — HMAC over the body — and then unconditionally trusts `request.topic` and `request.shop` to look up the handler and build the metadata object passed to the app's business logic: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further validation or cross-check against the body contents or any known-shops list: [5](#0-4) 

This is the "field acted on but not covered by the HMAC" analog explicitly called out in the rules: the gem verifies `HMAC(body) == received_hmac`, but the security-relevant tenant identifier (`shop`) is a disjoint, attacker-controllable header field that is never bound into that signature. Since the HMAC secret (`api_secret_key`) is shared across all shops installed on a given app, any legitimate installer of the app (an unprivileged internet user who installs the app on their own store and thus receives genuinely-signed webhooks) can capture a valid `(raw_body, hmac)` pair for their own shop and replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. The HMAC still validates (it only signs the body), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen victim domain, with `body` content controlled by the attacker (since it's their own previously-received payload, or any body they can get legitimately signed).

### Impact Explanation
Any app built on top of this gem that uses `WebhookMetadata#shop` to key per-tenant state (e.g., to decide which merchant's data to update/delete, e.g. `shop/redact`, `customers/redact`, `customers/data_request` mandatory webhooks, or order/product sync per shop) can be tricked into attributing an attacker-supplied webhook body to an arbitrary victim shop. This is a cross-tenant identity-binding bypass: the gem's own signature check gives applications false confidence that `request.shop` is authentic when it is not bound by the cryptographic check at all. Depending on the host handler's logic this can cause cross-tenant data corruption/deletion or unauthorized actions performed against a victim merchant's data — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own store (a normal, unprivileged flow) — no leaked secrets, TLS interception, or privileged access is required. They obtain fully valid `(body, hmac)` pairs for topics of their choosing (they can trigger many webhook topics on their own store) and only need to modify the `shop-domain` header before replaying to the app's public endpoint, which this gem does not protect against since the header is entirely outside the HMAC's scope.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header claims to the signed body (e.g., include them in the signable string, or require applications to independently verify `shop` against a known/installed-shops list before trusting `WebhookMetadata#shop`). At minimum, `Webhooks::Request#to_signable_string` should not silently exclude header fields that downstream consumers treat as authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving a legitimately Shopify-signed webhook, e.g.:
```
POST /webhooks
X-Shopify-Topic: customers/data_request
X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>
X-Shopify-Shop-Domain: attacker-shop.myshopify.com
X-Shopify-Webhook-Id: ...

{"customer": {...}}
```
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but rewrites the header:
```
X-Shopify-Shop-Domain: victim-shop.myshopify.com
```
3. `HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks the body bytes, which are unchanged.
4. `Registry.process` (see `lib/shopify_api/webhooks/registry.rb:188-199`) proceeds to build `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {...}, ...)` and invokes the app's handler, which now believes this attacker-controlled body/action legitimately originated from `victim-shop.myshopify.com`.
