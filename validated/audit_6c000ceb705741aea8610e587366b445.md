### Title
Excess native token sent to `EvmHost.dispatch()`/`fundRequest()` is never refunded and becomes trapped - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and forward the entire amount into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, ...)`, but never check for or refund any unspent native token back to the caller after the swap completes.

### Finding Description
All three payable entry points follow the same pattern: forward the full `msg.value` to the router requesting an *exact* output amount (`post.fee` / `get.fee` / `amount`), but do nothing with any leftover value: [1](#0-0) [2](#0-1) [3](#0-2) 

For a standard UniswapV2 router, `swapETHForExactTokens` refunds unspent ETH to `msg.sender` of that call — which is `EvmHost` itself (since `EvmHost` is the direct caller), not the original transaction sender. `EvmHost` has no logic afterward to detect this returned dust and forward it back to `_msgSender()`/`post.payer`, so it accumulates in the host contract with no accounting or user-facing withdrawal path.

On chains using the custom Uniswap-V2-compatible wrappers included in this repo, the situation is worse: `GnosisUniswapV2Wrapper.swapETHForExactTokens` wraps the **entire** `msg.value` (not just `amountOut`) into WETH and transfers it all to `EvmHost`: [4](#0-3) 
meaning any overpayment is fully consumed with zero refund at all — not even routed back to `EvmHost`'s balance as recoverable ETH, it is directly converted into fee-token and kept.

This is the same root cause reported in the external analog: a payable dispatch entry point accepts `msg.value` for a swap/deposit but never returns the unspent remainder to the caller. Notably, other payable entry points in this same codebase (`IntentGatewayV2.placeOrder`, `IntrinsicIntents`/`ExtrinsicIntents` fill/cancel flows) explicitly call `_sendValue(msg.sender, msgValue)` after performing the identical `swapETHForExactTokens` pattern to refund unspent native tokens: [5](#0-4) [6](#0-5) 
confirming this refund step was intentionally implemented elsewhere but omitted in `EvmHost.sol`'s own dispatch/fundRequest functions.

### Impact Explanation
Any unprivileged caller who dispatches a POST/GET request or funds a request through `EvmHost` with native token payment (a documented, first-class payment method per `docs/content/developers/evm/messaging/post-requests.mdx`) and supplies more ETH than the exact fee requires — which is expected in practice since fee estimation is off-chain and subject to slippage/sandwiching as the docs themselves warn — permanently loses the excess. The funds are not recoverable by the user and there is no visible admin sweep function tied to user compensation, so this is a direct, unbounded loss of funds for any caller of these core dispatch paths, reachable from ordinary message dispatch by IsmpModules/HyperApps.

### Likelihood Explanation
High likelihood: `dispatch{value: msg.value}(...)` is the officially documented pattern for native-token fee payment (see `docs/content/developers/evm/messaging/post-requests.mdx` and `get-requests.mdx`, which explicitly instruct developers to forward `msg.value` and let "the Host handle the Uniswap swap"). Since `quote()` is explicitly warned to be sandwich-attack-prone and meant only for off-chain estimation, real-world callers will routinely send a buffer above the exact fee to avoid reverts, guaranteeing frequent overpayment.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, snapshot the native balance (or track amounts spent via the swap's returned `amounts[0]`) and refund any leftover `msg.value` to `_msgSender()` after the swap, mirroring the `_sendValue(msg.sender, msgValue)` pattern already used in `IntentGatewayV2.sol` and `IntrinsicIntents.sol`/`ExtrinsicIntents.sol`.

### Proof of Concept
1. Caller invokes `IDispatcher(host).dispatch{value: 5 ether}(DispatchPost{ ..., fee: 0.01 ether })` following the documented pattern in `post-requests.mdx`.
2. `EvmHost.dispatch` forwards all 5 ETH to `swapETHForExactTokens(0.01 ether, path, address(this), block.timestamp)`.
3. On a standard router, ~4.99 ETH worth of unspent ETH is refunded to `msg.sender` of the swap call, i.e. `EvmHost`, and stays in `EvmHost`'s balance — no code path returns it to the original caller.
4. On the Gnosis wrapper variant, all 5 ETH is unconditionally wrapped and transferred to `EvmHost` as fee token regardless of the requested `amountOut`, with zero refund.
5. The caller has irrecoverably lost the ~4.99 ETH difference with no function in `EvmHost.sol` to reclaim it.

```text
    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
    }
```
