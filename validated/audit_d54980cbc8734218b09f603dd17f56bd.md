### Title
Unvalidated `dest` claim from session token used as OAuth token-exchange host, allowing SSRF with the app's `client_secret` - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the `/admin/oauth/access_token` call directly from the JWT `dest` claim without ever checking it against `ShopifyAPI::Utils::ShopValidator`, unlike every sibling credential-issuing method in the same module and its neighbour `ClientCredentials`, which do call `ShopValidator.sanitize!` before using `shop` as the request host.

### Finding Description
`exchange_token` takes the `dest` claim from the session token as the trusted shop and uses it, unsanitized, to build the `Auth::Session` that in turn becomes the HTTP request host that receives the app's `client_id`/`client_secret`: [1](#0-0) 

Compare this to `migrate_to_expiring_token` in the same file, and to `ClientCredentials.client_credentials`, both of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host that will receive `client_secret`: [2](#0-1) [3](#0-2) 

`JwtPayload#shop` performs no domain validation at all — it just strips the `https://` prefix from the raw `dest` claim: [4](#0-3) 

`Clients::HttpClient` then builds the request URI straight from `session.shop` (unless `Context.api_host` is configured, which is optional and unset in typical deployments): [5](#0-4) 

The binding this breaks (equality that should hold but doesn't) is:
`host that receives client_id/client_secret == a domain validated as a real, trusted Shopify shop (via ShopValidator.sanitize!)`

In `exchange_token`, the right-hand side of that equality is never computed — the check present in `migrate_to_expiring_token`/`client_credentials` is missing here, exactly mirroring the reported bug class ("an operation may need a specific verification, but the check is absent even though an equivalent check exists elsewhere in the codebase").

Whether this is practically exploitable depends on whether an attacker can influence the `dest` claim of a JWT that still verifies against `Context.api_secret_key`/`Context.old_api_secret_key`. The JWT signature check itself is sound (HS256 verified against the app secret, `aud` pinned to `Context.api_key`), so a completely unsigned/forged token would be rejected. The residual risk is narrower than a full pre-auth SSRF: it is a defense-in-depth gap versus the rest of the module, and it means the library provides no protection if a session token's `dest` ever ends up not equal to a genuine `*.myshopify.com`/trusted domain (e.g., value manipulated in transit by a compromised iframe/postMessage channel that forwards the token from the host page to the app, or any code path where the token's `dest` is not itself independently checked before this call). Because the gem is the last line of defense before `client_secret` is sent over the network, and it explicitly implements this exact check in the two sibling methods, the omission here is a real gap in the library's own contract.

### Impact Explanation
If the host derived from `dest` is not constrained to a trusted Shopify domain, the app's `client_id` and `client_secret` (i.e. its OAuth credentials) are sent to whatever host winds up in `dest`, which matches the report's "High – SSRF with the app's credentials" impact bucket. This is strictly worse than the sibling methods because they already do the sanitization; `exchange_token` skips it despite being the higher-traffic, embedded-app auth path (called on every session-token refresh).

### Likelihood Explanation
The signature check on the JWT prevents casual forgery from an anonymous internet user, so likelihood is moderate rather than trivial: this is an inconsistency/gap in the library's belt-and-suspenders validation rather than a demonstrated pre-auth bypass. It is still concerning because it is the only credential-issuing path in `token_exchange.rb`/`client_credentials.rb` that omits the `ShopValidator` check, and the library cannot guarantee upstream callers or transport layers never let a malformed `dest` through.

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) on the `dest` claim in `exchange_token` before constructing `shop_session`/issuing the HTTP request, mirroring `migrate_to_expiring_token` and `ClientCredentials.client_credentials`. This closes the asymmetry and ensures the app's `client_secret` is never sent to a host that hasn't been confirmed to be a trusted Shopify domain.

### Proof of Concept
1. Obtain (or otherwise cause the app to receive) a session token whose `dest` claim does not correspond to a value previously sanitized by `ShopValidator` (e.g. `https://attacker-controlled-host.example`), while still being validly signed for this app's `aud`/secret in whatever channel actually issues/relays the token to the app.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` sends a POST to `https://attacker-controlled-host.example/admin/oauth/access_token` containing `client_id` and `client_secret` in the body — no `ShopValidator` check ever runs, unlike the equivalent call in `client_credentials` or `migrate_to_expiring_token`, which would have raised `Errors::InvalidShopError` for the same value.
