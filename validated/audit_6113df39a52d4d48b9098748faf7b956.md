The Arrakis bug stems from a "whitelist routers" access-control list being populated before the guarded `token0`/`token1` state variables are set, letting an attacker register those tokens as trusted "routers" that later receive delegated calls draining user allowances. Raydium AMM v0.18 has no analogous whitelist/router mechanism reachable by an unprivileged swapper, LP, or pool creator — `process_initialize2` in [1](#0-0)  only accepts token mint/vault accounts, validates them via `unpack_mint`/`unpack_token_account`, and directly sets `amm.coin_vault_mint`/`amm.pc_vault_mint` from the passed-in accounts [2](#0-1) , with no separate authorization list being populated prior to those fields being finalized. The `coin_mint != pc_mint` guard at initialize time is checked directly against the caller-supplied mint account keys before any dependent state is used [3](#0-2) , so there's no window where an uninitialized/default token address could be mistakenly whitelisted as in the Arrakis report. The swap instructions (`process_swap_base_in`, `process_swap_base_out`, and their V2 variants) also independently re-validate `amm.coin_vault`/`amm.pc_vault` and reject user source/destination accounts matching the vaults [4](#0-3) , so there is no comparable "authorization list populated before state is finalized" bug class present in this codebase.
