### Title
Backend-configurable operator-QR expiration timeout has no enforced bound, breaking the intended timing guarantee for operator/user QR pairing - ([File: src/config.rs], [File: src/plans/mod.rs])

### Summary
`operator_qr_expiration_time` is a `Duration` field in `Config` that is meant to bound how long an operator QR-code scan remains valid before a matching user QR-code must be scanned, defaulting to 23 hours [1](#0-0) . It is fully overridable by the backend response with no range validation, exactly the "spec vs. code" mismatch pattern described in the report: an implicit timing guarantee that the implementation does not actually enforce as a bounded/sane value.

### Finding Description
`Config::from_backend` maps the backend-supplied `operator_qr_expiration_time` (a raw `u64` of milliseconds) directly into a `Duration` with no minimum/maximum clamp, unlike other numeric fields such as `sound_volume` and `fan_max_speed` which are explicitly `clamp`-ed [2](#0-1) [3](#0-2) . The subsequent `Config::validate` function only checks `sound_volume <= MAX_SOUND_VOLUME` and performs no check on `operator_qr_expiration_time` (or most other duration/threshold fields) [4](#0-3) .

This value is used as the window during which the previously-scanned operator QR-code/session remains valid while waiting for the user to scan their own QR-code, both during the idle loop (`idle_wait_for_signup_request` → `idle_scan_user_qr_code`) and later in `scan_remaining_qr_codes` inside `do_signup` [5](#0-4) [6](#0-5) [7](#0-6) . The remaining timeout is computed as `operator_qr_expiration_time.saturating_sub(operator_data.timestamp.elapsed())` [8](#0-7) .

Because the backend can set this value to anything — including `0` or an unreasonably large number — with no orb-side range enforcement, the effective binding window between an operator's QR scan and a user's QR scan diverges silently from whatever the intended/documented behavior is. This mirrors the reported bug class: a security-relevant timing parameter (there: a 2-week timelock; here: the operator-QR validity window) is fully attacker/operator-controllable through configuration with no defensive bounds checking in code, so the enforced behavior can silently diverge from the expected invariant.

### Impact Explanation
If the backend (or a compromised/misconfigured management-backend response) sets `operator_qr_expiration_time` to `0`, an operator's QR scan would be treated as immediately expired, forcing repeated re-scans or degraded UX. Conversely, an excessively large value would leave a scanned operator QR-code (and its associated operator-permission context) valid far longer than intended, extending the window during which a user QR-code could be paired with a stale operator session — a scenario relevant to correct attribution of a signup to the intended operator/location. Since this is purely a config-driven timing window with no attacker-supplied override path from an unprivileged user (the value comes from the trusted management backend, not from QR/MECARD parsing or an untrusted signup flow), the practical exploitability from an unprivileged-user standpoint is limited; the primary issue is the lack of defense-in-depth range validation matching intended semantics, not a directly attacker-triggerable bypass.

### Likelihood Explanation
Low-to-moderate. Triggering this requires the value returned by the backend config endpoint to be unusually small/large, which is not attacker-controlled by an unprivileged orb user; it depends on backend misconfiguration or compromise. The absence of any clamp/validate step (as compared to the pattern already used for `sound_volume`/`fan_max_speed`) makes this a data-validation gap consistent with the reported bug class, though it does not by itself provide an unprivileged-user exploitation path.

### Recommendation
Add an explicit range check for `operator_qr_expiration_time` (and other unbounded backend-supplied timing/threshold fields) inside `Config::validate`, clamping or rejecting values outside a sane min/max window (e.g., consistent with the documented/intended operator-QR pairing window), mirroring the existing `sound_volume`/`fan_max_speed` clamping pattern [2](#0-1) [4](#0-3) . Document the intended bound so implementation and specification stay in sync, and add tests asserting out-of-range backend values are rejected or clamped rather than silently accepted.

### Proof of Concept
Not independently verifiable from the indexed code alone: the actual exploitation path depends on backend-side response construction (outside this repo) and there is no attacker-controlled client input that can set this value directly. The concrete, verifiable root cause is the absence of a bound check, shown by contrasting `Config::validate` (checks only `sound_volume`) [4](#0-3)  with the unclamped mapping of `operator_qr_expiration_time` in `Config::from_backend` [3](#0-2) , and its use to gate operator/user QR pairing timing in `idle_scan_user_qr_code`/`do_signup` [9](#0-8) [7](#0-6) .

    async fn idle_scan_user_qr_code(
        &mut self,
        orb: &mut Orb,
        operator_data: &OperatorData,
        operator_qr_expiration_time: Duration,
        mut ui_idle_delay: Option<time::Sleep>,
    ) -> Result<Option<(qr_scan::user::Data, backend::user_status::UserData, String)>> {
        loop {
            orb.reset_rgb_camera().await?;
            match idle::Plan::with_user_qr_scan(
                ui_idle_delay.take(),
                Some(operator_qr_expiration_time.saturating_sub(operator_data.timestamp.elapsed())),
                #[cfg(feature = "internal-data-acquisition")]
                self.data_acquisition,
            )
            .run(orb)
            .await?
            {
                idle::Value::UserQrCode(qr_scan_result) => {
                    if !check_signup_conditions(orb).await? {
                        continue;
                    }
                    if let Some(Some((user_qr_code, user_data, user_qr_code_string))) =
                        self.handle_user_qr_code(qr_scan_result, orb, operator_data, None).await?
                    {
                        break Ok(Some((user_qr_code, user_data, user_qr_code_string)));
                    }
                }
                idle::Value::TimedOut => break Ok(None),
                idle::Value::ButtonPress => unreachable!(),
            }
        }
    }
