## Finding

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated for a given shop as soon as `Utils::HmacValidator.validate(request)` succeeds, and then hands `request.shop` straight to the app's handler as the tenant identifier. The HMAC, however, is computed only over the raw request body — none of the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers are part of the signed bytes. This breaks the equality `HMAC-verified bytes == bytes the app trusts for tenant identification`, since the trusted `shop` value is taken from an unsigned header while only the body is signed.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Webhooks::Request#shop` (the tenant identifier used downstream) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the body-derived signature against `hmac`, it never touches `shop`, `topic`, `webhook_id`, etc.: [3](#0-2) 

`Registry.process` relies on that same validation and then forwards the unauthenticated `request.shop` directly into `WebhookMetadata`, which is the tenant-scoping value the app's handler will act on: [4](#0-3) 

Because `shop` is not part of the signed bytes, any body+HMAC pair that is valid for shop A (trivially obtainable by an attacker who installs the app on their own store and receives one real webhook) remains a **valid** signature when replayed with the `shop-domain` header changed to point at shop B. `HmacValidator.validate` will still return `true`, and `Registry.process` will call the app's handler with `WebhookMetadata#shop == "B"`, even though the signed content actually originated for shop A. This is exactly the "field acted on but not covered by the HMAC" pattern: the identity binding `signed-body ⇒ shop` that the library implicitly promises to callers via `request.shop` does not hold.

### Impact Explanation
This is a cross-tenant confusion vulnerability. An attacker who controls their own shop (any unprivileged internet user can create a Shopify dev/trial store and install a target app) can legitimately trigger webhooks for their own store, capture the body+HMAC, and then send that exact pair to the app's public webhook endpoint while spoofing the `shopify-shop-domain` header to a victim shop. Because the gem hands `request.shop` to the handler as the trusted tenant key without any binding, the app will process attacker-controlled webhook body content as though it belongs to the victim shop. For handlers backing mandatory topics such as `customers/data_request` or `customers/redact`/`shop/redact`, this can trigger GDPR data export/deletion flows against the wrong tenant, or otherwise let attacker-controlled data be written into another merchant's tenant state — a cross-tenant access/data-integrity break.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install the target app on any shop the attacker controls (a normal, unprivileged action for any Shopify developer/merchant), (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers (webhook endpoints are internet-reachable by design). No access token, `client_secret`, or privileged account is needed — the attacker never needs to know the app's secret, they only need one legitimately-signed payload from their own tenant. This makes the likelihood high for any app whose webhook handlers key business logic off `WebhookMetadata#shop` (the pattern the docs recommend, see `test/webhooks/registry_test.rb`).

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise cryptographically tie the header values to the verified body — e.g. include `shop-domain` in `to_signable_string`, or require callers to cross-check `request.shop` against an already-authenticated session/installation record before trusting it as a tenant key. At minimum, document that `request.shop` is unauthenticated and must be independently verified by the host application against its own store of installed shops before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. for `orders/create`, with `body = raw_body` and header `shopify-hmac-sha256 = HMAC-SHA256(secret, raw_body)`.
2. Attacker replays the exact same `raw_body` and `shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` instead of their own domain.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))`.
4. `Utils::HmacValidator.validate(request)` (registry.rb:190) recomputes the HMAC over `raw_body` only — it matches, since the body wasn't altered.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` (registry.rb:198), even though the payload actually originated from the attacker's shop.
6. Any handler logic keyed on `data.shop` (e.g., writing order data, triggering redaction) now operates on `victim.myshopify.com`'s tenant context using attacker-supplied body content.
