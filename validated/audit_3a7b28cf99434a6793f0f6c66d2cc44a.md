### Title
Webhook `shop` identity header not covered by HMAC verification enables cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from raw, unauthenticated HTTP headers, but `to_signable_string` (used by `Utils::HmacValidator.validate`) signs only the request body. `Registry.process` trusts `request.shop` as the tenant identity and hands it, unverified, to the host application's `WebhookHandler#handle` via `WebhookMetadata`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which compares an HMAC over `request.to_signable_string` against `request.hmac`. For `Request`, `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `hmac` is decoded from the `hmac-sha256` header. Critically, `shop` is read directly from the `shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`) and is never part of the signed bytes.

Because a single app has one `api_secret_key` shared across every merchant that installs it (`lib/shopify_api/context.rb`, `lib/shopify_api/utils/hmac_validator.rb:16`), any tenant of a multi-tenant app can capture one of their own genuine webhook deliveries (valid body + valid HMAC, since the secret is app-wide, not per-shop) and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Utils::HmacValidator.validate` still returns `true`, because it only re-derives the HMAC from `@raw_body`, and `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) straight from these unverified headers, delivering the attacker-chosen `shop` value to the host application's handler as if it were authenticated tenant identity.

This breaks the identity binding: `shop_asserted_by_signed_bytes == shop_delivered_to_handler`. The gem verifies the body but delivers a shop value that was never bound to that signature, letting one tenant forge webhook events "from" another tenant's shop.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (the value the gem itself hands to `WebhookHandler#handle`) to select which merchant's session/data to act on — the documented and expected usage per `docs/usage/webhooks.md` — is exposed to cross-tenant confusion: a malicious merchant can trigger webhook side effects (data updates, redactions, order/customer processing) attributed to a victim shop, using only their own legitimately-issued webhook payload. This matches the Critical "cross-tenant access" impact category, since the boundary broken is the per-tenant identity binding that the gem is supposed to enforce as part of HMAC verification.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate installer of the same app (an unprivileged, ordinary merchant/user of the app), since the `api_secret_key` is shared per-app rather than per-shop. No access to the app's `client_secret`, no token theft, and no privileged account are needed — only capturing one webhook delivery to their own shop and replaying it with a modified header, which is trivial for anyone who controls an HTTP endpoint receiving their own webhooks.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed material checked by `Utils::HmacValidator`, or independently verify that `request.shop` matches an expected/allow-listed shop for the installation before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant selection without additional verification (e.g., cross-checking against the shop associated with the stored session/access token for that installation).

### Proof of Concept
1. App `A` is installed on `shop-victim.myshopify.com` and `shop-attacker.myshopify.com` (same app, same `api_secret_key`).
2. Shopify sends a genuine webhook to the attacker's own registered endpoint for `shop-attacker.myshopify.com`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body computed with the app's api_secret_key>
   x-shopify-shop-domain: shop-attacker.myshopify.com
   <raw_body>
   ```
3. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, only changing the header:
   ```
   x-shopify-shop-domain: shop-victim.myshopify.com
   ```
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-31`) recomputes the HMAC over `raw_body` only and finds it matches — the forged `shop-domain` header is never checked.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) builds `WebhookMetadata` with `shop: "shop-victim.myshopify.com"` and invokes the host app's handler, which processes the event as if it legitimately originated from the victim shop. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
