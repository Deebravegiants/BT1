### Title
Webhook shop identity is not covered by the HMAC signature, allowing tenant spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only proves the *body bytes* were signed by the app's secret [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and are never included in the signed payload [3](#0-2) . Yet `Registry.process` treats HMAC success as proof that the whole `Request` — including `request.shop` — is authentic, and forwards `request.shop` unauthenticated straight into the handler as the shop identity for the event [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop header used to attribute the event == shop that produced the HMAC-signed bytes`. In this gem it does not: `HmacValidator.validate(request)` only checks `OpenSSL.secure_compare(computed_signature, hmac)` where `computed_signature` is derived solely from `verifiable_query.to_signable_string`, which for `Webhooks::Request` is `@raw_body` [5](#0-4) [6](#0-5) .

The `shop`, `topic`, `webhook_id`, and `api_version` accessors simply read the corresponding `x-shopify-*`/`shopify-*` header without any cryptographic binding to the signed body [7](#0-6) . `Registry.process` validates only the HMAC, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic` and passes it to the app's handler [4](#0-3) . The library's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," encouraging apps to trust `data.shop` as an authenticated tenant identifier (e.g., to look up per-shop sessions/tokens or attribute stored data) — see `docs/usage/webhooks.md` lines 10-30 and 123-136.

Consequently, anyone who can obtain one genuine `(raw_body, hmac)` pair — trivially available to any unprivileged user who installs the app on their own store and lets it deliver one real webhook, or simply captures their own store's webhook traffic — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` (and `topic`/`webhook-id`) headers to name an arbitrary victim shop. The signature still validates because it never covered those headers, and the handler receives `WebhookMetadata#shop` pointing at the victim tenant.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an attacker-controlled body can be attributed to an arbitrary victim shop that has never sent that data. Any app logic that uses `data.shop` from `WebhookHandler#handle` to select which merchant's session/access token to act with, or to write/update per-tenant records, can be tricked into acting on/against a different tenant's data using attacker-supplied content — i.e., cross-tenant access facilitated entirely by this gem's webhook processing API, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Medium: the attacker doesn't need any secret or privileged credential — only their own store's app installation and the ability to POST directly to the app's public webhook endpoint (which by design accepts webhook requests over the internet). Obtaining one valid `(body, hmac)` pair from their own store's webhook delivery is trivial (own the receiving endpoint or use a request logger), after which the header substitution requires no cryptographic secret at all.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the signed material (or otherwise cryptographically verify them, e.g., against the actual delivering endpoint's registered shop) before trusting `request.shop`/`WebhookMetadata#shop`, instead of relying on an HMAC that only covers the raw body. At minimum, `Request#to_signable_string` should not be the sole authenticity check used to justify trusting `shop`/`topic` header values.

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a genuine webhook to the app: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, plus a JSON body the attacker can influence (e.g., via placing arbitrary text in an order note field before the create event fires).
3. Attacker captures this exact `raw_body` and its `hmac` (either by controlling the same endpoint, or via a proxy).
4. Attacker crafts a new HTTP request to the app's webhook route with the same `raw_body`/`hmac` but changes `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
5. `HmacValidator.validate` passes because it only checks `raw_body` against `hmac`, unrelated to the `shop-domain` header [8](#0-7) .
6. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` [9](#0-8) , and any app logic keyed off `data.shop` now acts on the victim tenant using attacker-supplied content.
