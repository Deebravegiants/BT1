### Title
Webhook `shop` identity used for tenant routing is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value that a host application uses to determine *which merchant* the webhook belongs to is read from an HTTP header that is never included in the signed bytes. This breaks the intended binding: `hmac == HMAC(body)` while `shop == header("shopify-shop-domain")`, i.e. the byte range verified by HMAC and the byte range used to establish the tenant identity are disjoint.

### Finding Description
`Request#hmac` derives the signature purely from header data, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop` simply returns the `shopify-shop-domain` (or `x-shopify-shop-domain`) header value verbatim: [3](#0-2) 

The HMAC validator (`Utils::HmacValidator.validate`) only checks that `HMAC(secret, to_signable_string) == hmac`, i.e. it authenticates the raw body bytes: [4](#0-3) 

Because `to_signable_string` for a webhook request is the raw body, the `shop-domain` header carrying tenant identity is entirely outside the signed material. This is the exact class of bug identified in the referenced report ([M-08], "two address tokens can be withdrawn... admin address check ≠ actual balance moved"): the code checks/signs one thing (`body`) but acts on a different, unauthenticated thing (`shop` header) as if it had been verified together with the signature.

Equality that should hold but doesn't:
`bytes_covered_by_hmac(raw_body) == bytes_used_to_identify_tenant(shop-domain header)` — false, because the header is disjoint from the signed body.

### Impact Explanation
Any host application that follows the documented pattern of calling `request.shop` to select/route to a merchant's session or store record — while relying on `HmacValidator.validate(request)` (or equivalent) purely to confirm "this webhook is legitimately from Shopify" — is exposed to cross-tenant confusion: an attacker who possesses one legitimately-signed webhook payload+HMAC pair (e.g., their own shop's webhook, which Shopify will deliver to any endpoint they control) can resend that exact body/HMAC pair while altering the `shopify-shop-domain` header to a victim shop's domain. The signature still validates (it only covers the body), but the application will process/act on it as if it originated from the victim shop, satisfying the "cross-tenant access" impact criterion.

### Likelihood Explanation
Likelihood is **Medium**: it requires the attacker to control (or be) a legitimate Shopify merchant/app installer who can capture a validly-signed webhook for their own shop, and it requires the integrating application to trust `request.shop` for tenant identification without any additional binding (e.g., without independently verifying the shop against a registered store/session per app installation). This is a realistic integration pattern since `shop` is the only tenant-identifying accessor exposed by `Request`, and the gem provides no alternative bound-shop mechanism for webhooks (unlike OAuth's `AuthQuery`, where `shop` is part of `to_signable_string` and thus HMAC-covered — see `lib/shopify_api/auth/oauth/auth_query.rb` lines 34-43).

### Recommendation
Include the shop-domain (and topic/webhook-id) header values in the signable material for webhook requests, or otherwise cryptographically bind them to the raw body before trusting `Request#shop` for tenant routing. At minimum, document clearly that `shop` is unauthenticated and that consuming applications must cross-check it against an independently known, per-installation shop value (e.g., the shop tied to the specific webhook subscription/session) rather than trusting the header in isolation.

### Proof of Concept
1. Merchant A installs the app; Shopify sends a webhook to the app's endpoint with body `B`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`, and `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker (who is Merchant A, or intercepts/replays this request) resends the exact same body `B` and HMAC header, but changes `X-Shopify-Shop-Domain` to `shop-victim.myshopify.com`.
3. The host application calls `ShopifyAPI::Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` — this still passes since `B` and the HMAC are unchanged. [5](#0-4) 
4. The application then calls `request.shop`, which returns the attacker-controlled `shop-victim.myshopify.com`, and proceeds to act on/store data as if the (valid, signed) webhook body belonged to `shop-victim`. [3](#0-2)
