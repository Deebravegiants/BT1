### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch and identify the tenant are taken from unauthenticated HTTP headers that are never included in the signature check.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to build the HMAC input. [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, independent of the signed body: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` only compares the HMAC computed over `to_signable_string` (i.e., the body) against the received signature — it never binds `shop`, `topic`, or `webhook_id` into that computation: [5](#0-4) 

Once HMAC validation passes, `Registry.process` unconditionally trusts `request.shop` and `request.topic` and forwards them to the app's handler as the authenticated tenant identity, with no independent check that this shop is the one that actually produced the signed body: [1](#0-0) 

The identity binding the gem is supposed to guarantee is:
`shop_header (trusted by handler) == shop_that_produced(raw_body, hmac)`

Because the HMAC only covers `raw_body`, this equality is never enforced — the gem enforces only:
`hmac == HMAC(secret, raw_body)`

which is a strictly weaker binding.

### Impact Explanation
Any actor who can obtain one valid `(raw_body, hmac)` pair signed by the app's shared `client_secret` — trivially achievable by installing the app on their own (attacker-controlled) shop and capturing a legitimate webhook delivery for that shop — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body against the secret; `Registry.process` then invokes the app's handler with `WebhookMetadata` carrying the attacker-chosen `shop` and topic values, causing the host application to process attacker-controlled data under the identity of a different, victim tenant. This crosses a tenant boundary using only the attacker's own legitimate credential and directly matches the "Critical - cross-tenant access" impact category, since the vulnerability lives entirely in this gem's `process`/`HmacValidator` logic rather than requiring the host app to violate documented usage.

### Likelihood Explanation
Likelihood is realistic: obtaining a valid signed webhook body requires nothing more than installing the target app on any shop the attacker controls (a normal, unprivileged flow for any Shopify app that is publicly installable), and the header substitution requires only a standard HTTP client capable of setting custom headers when hitting the app's public webhook URL. No access token, `api_secret_key`, or privileged account is needed beyond the attacker's own shop's legitimate installation.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`) in the HMAC-signed payload verification, or independently and cryptographically bind the `shop` header to the specific webhook subscription/secret so that a valid signature for shop A's payload cannot be replayed while claiming to originate from shop B. At minimum, `Request#to_signable_string` should incorporate the shop domain, and `HmacValidator`/`Registry.process` should reject any request where the shop asserted in headers does not match the shop bound to the HMAC.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and captures one legitimate webhook delivery with:
raw_body = '{"id": 1, "note": "attacker-controlled payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the SAME raw_body/hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # still valid! body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, NOT covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Passes validation because HmacValidator only checks raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process dispatches to the handler believing this is legitimately from victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", ...))
```
