### Title
Front-running of `Initialize2` permanently squats the deterministic AMM pool address for a given `market` key, causing denial of service and pool-address hijack - ([File: program/src/processor.rs])

### Summary
`process_initialize2` derives every PDA of a new AMM (the `AmmInfo` account itself, the LP mint, the coin/pc vaults, and the target-orders account) purely from the caller-supplied `market_info.key` combined with fixed seed constants, with no binding to the transaction sender, a nonce chosen by the creator, or any cryptographic commitment that ties the pool to the legitimate creator's intent. Because these addresses are 100% predictable once `market_info` is known, an attacker who observes a pending `Initialize2` transaction in the mempool (or simply guesses the `market` pubkey a project intends to use) can submit their own `Initialize2` for the same `market_info` key first, permanently claiming every derived PDA for that market. This mirrors the reported `NarwhalReferrals.signUp` front-running class: a value tied to a public, front-runnable input (block number there, `market_info.key` here) lets an attacker preempt legitimate use and cause a permanent DoS of the intended functionality.

### Finding Description
`generate_amm_associated_account` and `generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` compute PDAs using only `program_id`, `market_account.key`, and a fixed seed: [1](#0-0) 

These helper functions are invoked from `process_initialize2` to create the target-orders account, LP mint, coin vault, pc vault, and the `AmmInfo` account itself, all keyed off the same `market_info`: [2](#0-1) 

Critically, the instruction documentation and code comments confirm `market_info` is not validated to be a real market — it can be "any account", and is used purely as a seed: [3](#0-2) 

If the derived account is already assigned/owned (i.e., someone else already initialized a pool for that `market_info` key), the helper returns `AmmError::RepeatCreateAmm`, permanently blocking any future `Initialize2` call using that same `market_info` key: [4](#0-3) 

None of `coin_mint`, `pc_mint`, `nonce`, `init_coin_amount`, or `init_pc_amount` are cryptographically bound to `market_info` — they are freely chosen by whichever transaction lands first: [5](#0-4) 

Because Solana leaders/validators can reorder or simply race transactions within the same slot (and the instruction set has no nonce, commitment, or minimum-stake requirement gating pool creation), an attacker can observe a legitimate `Initialize2` transaction targeting a specific `market_info` in-flight and submit a copy with the same `market_info`/mint pair but trivial `init_coin_amount`/`init_pc_amount` (e.g., `1`/`1`), landing first.

### Impact Explanation
Once the attacker's `Initialize2` lands:
- The legitimate creator's transaction reverts with `RepeatCreateAmm`, and the intended AMM pool for that token pair/market can never be created again through that `market_info` key — a permanent denial of service of the pool-creation functionality, exactly analogous to the referral-registration DoS in the source report.
- The attacker now controls the canonical, deterministically-derived AMM (and its LP-mint authority-derived address, vaults, etc.) for that `market_info` key with an artificially skewed initial price ratio (from the minimal, attacker-chosen `init_coin_amount`/`init_pc_amount`), since `liquidity` and the initial LP mint amount are computed directly from these attacker-supplied vault balances: [6](#0-5) 
  Any user or integrator that subsequently derives the pool address from the well-known `market_info`/token-pair and deposits or swaps against it interacts with a squatted, mispriced pool instead of the intended one, exposing later depositors to loss from the distorted initial ratio.

### Likelihood Explanation
Exploitation only requires observing (or predicting) a pending `Initialize2` transaction's `market_info`, `amm_coin_mint`, and `amm_pc_mint` — all public instruction data — and submitting a copy with trivial amounts before it lands. On networks with public mempools/fast blocks this is cheap and requires no special privilege, matching the "cheap to perform" characterization in the original report.

### Recommendation
Do not derive the AMM's canonical PDAs solely from a caller-controlled, unauthenticated `market_info` key. Bind pool creation to a value the legitimate creator controls exclusively and that cannot be front-run with mismatched intent — e.g., require the `market_info` account to be a real, already-existing market/config account owned by a known program and validated against the supplied mints, and/or require the creator's own signature/nonce to be part of the seed derivation so an attacker cannot preemptively claim the address with arbitrary parameters.

### Proof of Concept
1. Alice prepares an `Initialize2` transaction for `market_info = M`, `amm_coin_mint = X`, `amm_pc_mint = Y`, with a real `init_coin_amount`/`init_pc_amount` and broadcasts it.
2. Attacker observes the transaction (mempool/simulation) and extracts `M`, `X`, `Y`.
3. Attacker submits their own `Initialize2` with the same `M`, `X`, `Y`, `init_coin_amount = 1`, `init_pc_amount = 1`, ensuring it lands first (same slot, higher fee, or faster relay).
4. `generate_amm_associated_account`/`generate_amm_associated_spl_*` succeed for the attacker (accounts are still system-owned), creating the AMM, vaults, LP mint, and target orders deterministically keyed to `M`.
5. Alice's transaction now fails at the same helper functions with `AmmError::RepeatCreateAmm` because the derived accounts are no longer system-owned: [7](#0-6) 
6. The `X`/`Y` pool tied to market `M` can never be legitimately (re)initialized, and any depositor targeting that market/token pair now interacts with the attacker's mispriced squatted pool.
