### Title
Predispatch sweep in `placeOrder` transfers the shared dispatcher's *entire* token balance instead of only the caller's own contribution, allowing theft of residual funds - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch path sweeps tokens from the shared `_params.dispatcher` contract back to the gateway by reading `IERC20(token).balanceOf(dispatcher)` and transferring that *whole* balance, rather than only the amount produced by the current caller's own predispatch call. Any residual token balance left sitting on the shared dispatcher — from a prior order's unswept dust, an unrelated side-effect of another user's predispatch calldata, or a partially-completed sweep — can be claimed in full by any subsequent unrelated caller simply by declaring that token as one of their order inputs, without any check that the swept funds actually originated from, or belong to, the current transaction.

### Finding Description
In `placeOrder`, when an order has `predispatch` calldata, the flow is:
1. Transfer the caller's declared `predispatch.assets` to the shared `dispatcher` contract [1](#0-0) .
2. Execute the attacker/caller-supplied `order.predispatch.call` via `ICallDispatcher(dispatcher).dispatch(...)` [2](#0-1) .
3. Build a sweep call that reads the dispatcher's **current total balance** of each `order.inputs[i].token` and instructs the dispatcher to transfer that *entire balance* (not the amount specifically produced by this call) to the gateway: [3](#0-2) 
4. The gateway then measures its own balance delta to compute `received` for accounting/commitment purposes [4](#0-3) .

The critical gap is step 3: `balance = IERC20(token).balanceOf(dispatcher)` and the constructed `Call` transfers that **full balance**, gated only by `balance < requiredAmount` (i.e., "is there enough," never "is this mine"). `_params.dispatcher` is a single shared, protocol-wide contract (`address dispatcher = _params.dispatcher;`, line 236) used by every `placeOrder` call across every user. There is no provenance/ownership check equivalent to verifying that the swept tokens were actually deposited or produced by the *current* caller's predispatch execution — exactly the class of bug flagged in the reference report, where an asset sitting at a contract is moved out without verifying it legitimately belongs to the party triggering the transfer.

Because each `placeOrder` transaction is atomic, the practical attack requires the dispatcher to be left holding a residual balance of some token after a prior, unrelated `placeOrder` transaction completes (e.g., a fee-on-transfer/partial-swap predispatch call that produces or leaves behind an unaccounted token, or any deposit into the dispatcher not fully consumed by that transaction's own `order.inputs` list). Any later caller can then place an order whose `predispatch.assets`/`predispatch.call` is a no-op and whose `order.inputs` simply names that residual token with `requiredAmount` at or below the leftover balance — the sweep call unconditionally pulls the *whole* dispatcher balance for that token to the new caller's escrow, not just up to `requiredAmount`.

### Impact Explanation
This allows theft of funds that do not belong to the calling order: any ERC20 (or native ETH via the analogous `address(dispatcher).balance` branch) balance stranded on the shared `dispatcher` contract can be fully drained by an unrelated, unprivileged caller through a single `placeOrder` transaction. This is a direct theft-of-funds vector against whichever party (protocol or a prior user) the residual balance actually belonged to, reachable purely by submitting a crafted order — satisfying the "concrete theft of funds" bar.

### Likelihood Explanation
Likelihood depends on the shared `dispatcher` contract ever holding a non-zero, unswept token balance between transactions (e.g., due to fee-on-transfer tokens, `predispatch.call` side effects that create additional token balances beyond what the current order's `inputs` array anticipates, or a previous sweep only partially matching balances). Given the code already anticipates fee-on-transfer and dust scenarios (`DustCollected` events, balance-delta accounting), it is plausible for the dispatcher to accumulate token remnants across separate transactions in normal operation, making exploitation realistic without requiring any special privilege — any address can call `placeOrder`.

### Recommendation
Track and sweep only the balance actually attributable to the current caller's predispatch execution (e.g., snapshot the dispatcher's balance for each `order.inputs[i].token` **before** step 1's asset transfer and the `dispatch` call, then only pull `min(currentBalance - preCallBalance, ...)` or otherwise require the swept amount to equal the delta produced by this specific call), rather than sweeping the dispatcher's entire current balance. Alternatively, ensure the dispatcher never carries balance across transactions (revert if pre-existing balance is nonzero, or route unrelated residues to a protocol-controlled sweep function instead of allowing arbitrary callers to claim them via `order.inputs`).

### Proof of Concept
1. User A calls `placeOrder` with a `predispatch.call` that (intentionally or due to a token quirk) leaves `100 TOKEN_X` sitting on `dispatcher` beyond what User A's own `order.inputs` accounts for (e.g., `order.inputs` only lists `TOKEN_Y`, so the sweep loop at lines 263–287 never touches `TOKEN_X`, leaving it on the dispatcher after User A's transaction completes).
2. User B (attacker, unrelated to User A) calls `placeOrder` with a no-op `predispatch.call` (empty `Call[]`) and `order.inputs = [{token: TOKEN_X, amount: 100}]`.
3. In User B's transaction, the sweep-building loop at [5](#0-4)  reads `balance = IERC20(TOKEN_X).balanceOf(dispatcher) == 100`, satisfies `balance >= requiredAmount`, and constructs a transfer of the full `100 TOKEN_X` from `dispatcher` to the gateway, crediting it entirely to User B's escrow — funds that were never contributed by User B.
