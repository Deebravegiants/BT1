Based on the investigation, the strongest reachable analog is in `CallDispatcher.sol`, the shared utility contract used by `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents` predispatch/postdispatch flows and by `HyperFungibleToken`'s calldata-execution feature.

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain tokens transiently held/approved by the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever — it is a plain `external` function callable by any address, not gated to only be invoked by `IntentGatewayV2` or `HyperFungibleToken`. Because these apps route escrowed/bridged tokens *through* the dispatcher's own address (so that user-supplied `Call[]` calldata can act on them) and rely on the calling app to sweep balances back out within the same transaction, any token balance or ERC20 approval that ends up parked on the dispatcher outside that atomic sweep — due to dust, fee-on-transfer edge cases, or incompletely-specified calldata — is directly stealable by anyone, at any time, by calling `dispatch()` themselves.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes each `to.call{value}(data)` as the `CallDispatcher` contract itself: [2](#0-1) . There is no `onlyGateway`/`onlyOwner`/`onlyHost` modifier — any EOA or contract can call it directly.

Multiple apps route funds through this exact same, singleton, permanently-deployed contract, trusting that the tokens it temporarily holds are only ever manipulated by the orchestrating app in the same transaction:

- `IntentGatewayV2.placeOrder()`'s predispatch flow transfers assets to `dispatcher`, executes the user's `order.predispatch.call` via `dispatch()`, then sweeps the resulting balance back to the gateway: [3](#0-2) [4](#0-3) .
- `IntentsBase._execute()` (postdispatch, used by both `ExtrinsicIntents` and `IntrinsicIntents`) similarly dispatches `order.output.call` through the same dispatcher and then sweeps whatever balance remains: [5](#0-4) .
- `HyperFungibleToken.onAccept()`/`onPostRequestTimeout()` mint tokens directly to the recipient (`to`), which the docs explicitly instruct integrators to set to the `CallDispatcher` address when the attached `data` needs to spend the minted tokens, then forward `message.data` to `dispatch()`: [6](#0-5) . Unlike the intent gateways, this path has **no automatic sweep-back** — whatever the attached `Call[]` doesn't fully consume/forward stays on the `CallDispatcher`'s balance indefinitely.
- The project's own documentation acknowledges the dispatcher accumulates state across calls and cautions against unlimited approvals, confirming the shared/stateful trust model: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution." — yet nothing prevents an outsider from invoking `dispatch()` to immediately weaponize any residual balance or lingering approval, e.g. the `type(uint256).max` router approval demonstrated in `IntentGatewayV2Test.testPostdispatchTokenSweep`: [7](#0-6) .

This mirrors the `BribeVault` bug class but is strictly worse: the original report required a *privileged* `DEFAULT_ADMIN_ROLE` to bootstrap the attack via `grantDepositorRole`. Here, `dispatch()` requires **no privilege at all** — any unprivileged relayer, solver, or arbitrary third party watching the mempool/chain state can, at the moment any token balance or stale approval sits on the shared `CallDispatcher`, submit `dispatch()` with a `Call{to: token, data: transfer(attacker, balance)}` (draining the dispatcher's own balance directly, no allowance needed) or a `Call` that exercises a previously-granted router approval to redirect swap output to themselves.

### Impact Explanation
Any token balance that transiently or accidentally remains on the singleton `CallDispatcher` — from an `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents` predispatch/postdispatch calldata execution that doesn't perfectly zero out the balance (fee-on-transfer tokens, reverts mid-sweep-array construction, rounding), or from a `HyperFungibleToken` cross-chain calldata delivery whose attached calls don't fully forward the minted tokens — can be stolen outright by any external caller. Because the dispatcher is a single, chain-wide, permanently-deployed shared resource referenced by `_params.dispatcher` across multiple gateway/app instances, this is a direct theft-of-funds vector, not merely a griefing bug.

### Likelihood Explanation
Likelihood is elevated by the fact that `dispatch()` requires zero setup or privilege — it is a bare public function, so exploitation is simply "watch for any nonzero balance/approval on the well-known `CallDispatcher` address and call `dispatch()`." Fee-on-transfer tokens, DEX slippage/rounding on postdispatch swaps, and any HFT calldata payload that isn't perfectly balance-neutral all create realistic windows.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a whitelist of authorized callers (the specific `IntentGatewayV2`/`Intents*` and `HyperFungibleToken` instances that are expected to use it), or deploy a fresh, single-use `CallDispatcher` per invocation (e.g., via CREATE2/minimal proxy scoped to the calling transaction) so no shared, permanently-addressable balance or approval state can ever exist between transactions. Additionally, ensure `HyperFungibleToken.onAccept` sweeps any residual dispatcher balance back to a safe destination after `dispatch()` returns, matching the sweep pattern already used by `IntentGatewayV2`.

### Proof of Concept
1. A user bridges tokens via `HyperFungibleToken.send()` with `to = CallDispatcher` and `data` encoding a swap that (due to slippage or a bug in the attached calldata) leaves 10 tokens un-forwarded on the `CallDispatcher` after `onAccept()` mints and dispatches: [8](#0-7) .
2. Since `onAccept` performs no sweep-back, those 10 tokens sit on the `CallDispatcher`'s balance after the transaction concludes.
3. Any unprivileged attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 10e18)})]))` directly: [2](#0-1) .
4. The call succeeds because `dispatch()` has no access control, transferring the dispatcher's own balance (as `msg.sender = CallDispatcher`) to the attacker — no approval or relationship to the original bridging user required.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
