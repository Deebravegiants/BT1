### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed payload. This breaks the identity binding `HMAC-covered bytes == bytes acted upon`: the signature covers only `raw_body`, while `request.shop` (used to attribute the webhook to a tenant) is read from an out-of-band header that anyone who can produce a validly-signed body can freely set.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` only — i.e., only the body is checked: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, without any further binding check between the validated body and the claimed shop: [4](#0-3) 

Because the `client_secret`/`api_secret_key` used to sign webhooks is shared across all shops that install a given app (it is one secret per app, not per shop), any merchant who has legitimately installed the app on their own store receives real, validly-HMAC-signed webhook deliveries. That merchant can capture such a delivery (body + valid HMAC) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to point at a different (victim) shop. `HmacValidator.validate` still passes (the body and HMAC are untouched and were validly signed by Shopify with the shared secret), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` claims to be the victim's store while carrying attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity confusion: the gem provides no mechanism, and the documented API pattern in `Registry.process`/`WebhookMetadata` gives host applications no way to detect, that the `shop` attribute wasn't actually the origin of the signed payload. Any downstream logic keyed on `WebhookMetadata#shop` (e.g., looking up which merchant's session/data to update, deciding which store's records to modify per `shop/redact`, `customers/redact`, `customers/data_request`, or business webhooks) can be tricked into acting on attacker-chosen data under a different tenant's identity — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires only becoming an app user (installing the app on one's own store, which is an ordinary unprivileged action any merchant can perform — no theft of `api_secret_key`, no privileged account, no access token) and capturing/replaying a webhook delivery which is trivial (webhooks are plain HTTP POSTs reaching a public endpoint). No cryptographic secret needs to be recovered because the attacker reuses a genuinely-issued signature; they only need to change an unsigned header.

### Recommendation
Bind the tenant identity into the verified signature space, or otherwise cryptographically/authoritatively confirm that the `shop` header corresponds to the shop that actually owns the signed body — e.g., cross-check `request.shop` against a shop value embedded in (or independently verifiable from) the payload/session store before constructing `WebhookMetadata`, and document that host apps must not trust `shop` from headers alone for authorization decisions.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Attacker triggers/receives a legitimate webhook from Shopify for their own shop; captures `raw_body` and the `X-Shopify-Hmac-Sha256` value (both are exactly what `HmacValidator.validate` will check).
3. Attacker POSTs the same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — passes.
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged header value `victim-shop.myshopify.com`, and invokes the app's handler as if the (attacker-controlled) body legitimately originated from the victim shop.
