### Title
Webhook `shop-domain` (tenant identity) header is not covered by the HMAC signature, allowing shop-spoofing via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while the HMAC signature computed by `Utils::HmacValidator` is only ever calculated over `to_signable_string`, which for `Request` returns just `@raw_body` [1](#0-0) [2](#0-1) . This breaks the equality that should hold between "the shop the HMAC authenticates" and "the shop the gem hands to the app's webhook handler."

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)` [3](#0-2) . `HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field using a constant-time comparison [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body (`@raw_body`) [2](#0-1) ; none of the HTTP headers — including `shop-domain`, `topic`, `webhook-id`, and `api-version` — are part of the signed material.

After HMAC validation succeeds, `Registry.process` builds a `WebhookMetadata` object using `request.shop`, which is read verbatim from the unauthenticated header [5](#0-4) [1](#0-0) . The equality the gem should be enforcing is: `shop authenticated by the HMAC == shop delivered to the handler`. Because the header is outside the signed scope, that equality does not hold — an attacker who can capture (or replay) any single valid `(raw_body, hmac)` pair signed with the merchant's API secret can resubmit it with an arbitrary `x-shopify-shop-domain` header value, and the request will pass HMAC validation while `WebhookMetadata#shop` reports the attacker-chosen shop to the host application's handler.

### Impact Explanation
Host applications commonly use `WebhookMetadata#shop` (i.e., `request.shop`) as the tenant key to look up/update per-merchant data, since this is the only shop identifier the gem's webhook API exposes. An attacker who can influence or replay the unauthenticated `shop-domain` header while reusing a validly-signed body can cause a legitimate webhook event to be attributed to a different (attacker-controlled or victim) shop, i.e., a cross-tenant data confusion inside the app built on this gem's documented webhook API. This matches the "Critical - cross-tenant access" category, since the root cause is entirely inside this gem's HMAC-verification logic (`to_signable_string` scope), not something the host app can be expected to compensate for since it is only given `request.shop` and told the request is HMAC-verified.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one valid `(raw_body, hmac)` pair for the target API secret — this is available to anyone able to observe webhook traffic that already flows over the network to the app's webhook endpoint (e.g. via a compromised intermediary, logging pipeline, or a malicious/legitimate co-tenant capturing their own delivered webhook and simply changing the shop header when replaying it to the same shared endpoint). No possession of `api_secret_key` or an access token is needed, satisfying the "unprivileged internet user" bar. Likelihood is moderate, since it depends on the app either exposing one shared webhook endpoint for multiple shops or an attacker's ability to capture at least one valid signed payload.

### Recommendation
Include the tenant-identifying headers (`shop-domain`/`shop_domain`, and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body, so that `HmacValidator.validate` fails whenever any of those header values are altered relative to what was actually signed by Shopify. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop` value so the identity used downstream (`WebhookMetadata#shop`) is provably the same one Shopify authenticated.

### Proof of Concept
1. Attacker observes/obtains one legitimately delivered webhook `(raw_body, x-shopify-hmac-sha256)` pair for any shop (e.g., because they run their own store connected to the same app, or intercept traffic to a shared multi-tenant webhook endpoint).
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (any arbitrary tenant value).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the (unchanged) hmac [3](#0-2) [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim-shop.myshopify.com"` — the attacker-supplied, unauthenticated value [5](#0-4) .
5. The host app processes the webhook payload under the wrong tenant's identity, even though HMAC verification reported success.
