## Analysis

The report's bug class — a truncating cast that silently discards high-order bits instead of using a checked/validated conversion — has a direct analog in the Solana AMM's swap-base-out math.

`Calculator` defines a *safe* conversion helper, `to_u64`, that uses `try_into` and returns `AmmError::ConversionFailure` on overflow: [1](#0-0) 

But in `swap_base_out` and `swap_base_out_v2`, the final `swap_in_after_add_fee` value — computed entirely in `U128` — is converted to `u64` with the *unchecked, truncating* `.as_u64()` instead of `Calculator::to_u64`: [2](#0-1) [3](#0-2) 

`swap_token_amount_base_out` computes `amount_in = coin * amount_out / (pc - amount_out)`, where the denominator is `total_pc_without_take_pnl - amount_out`: [4](#0-3) 

`amount_out` is the attacker-supplied `swap.amount_out` field from the swap instruction data, and the only bound on it (`swap.amount_out >= total_pc_without_take_pnl` → error) is checked *after* `swap_in_before_add_fee`/`swap_in_after_add_fee` have already been computed and truncated: [5](#0-4) 

By choosing `amount_out` just below `total_pc_without_take_pnl`, the denominator can be driven to a very small value (e.g., 1), making `coin * amount_out / denominator` (and the subsequent fee-adjustment multiply) grow far beyond `u64::MAX` while still fitting inside `U128`. The unchecked `.as_u64()` then silently wraps this huge value down to an arbitrary small 64-bit residue, rather than erroring like `Calculator::to_u64` would. That truncated (attacker-tunable) value is then used both for the slippage/balance checks and as the actual amount transferred from the user, while the full attacker-chosen `swap.amount_out` is paid out from the pool: [6](#0-5) 

This is reachable from a single transaction submitted by any unprivileged swapper via the `SwapBaseOut`/`SwapBaseOut2` instructions, with fully attacker-controlled `amount_out`/`max_amount_in` data, matching the pattern of the report (unsafe truncating cast bypassing a downstream sanity check, enabling value creation/drain).

### Title
Unsafe truncating `.as_u64()` cast in `swap_base_out`/`swap_base_out_v2` allows integer overflow-based pool drain - (File: `program/src/processor.rs`)

### Summary
`swap_base_out` and `swap_base_out_v2` compute the required `amount_in` in `U128` arithmetic and convert the final result to `u64` using the truncating `U128::as_u64()` instead of the checked `Calculator::to_u64()` used elsewhere in the codebase. Because the denominator of this division (`total_pc_without_take_pnl - swap.amount_out`, or the coin equivalent) is fully attacker-controlled via `swap.amount_out` and is only bounds-checked *after* the division, an attacker can force the true (unrounded) required input amount to exceed `u64::MAX`. The unchecked cast then wraps this to an arbitrary small `u64` value.

### Finding Description
`Calculator::swap_token_amount_base_out` (`program/src/math.rs:327-367`) computes `amount_in = total_X * amount_out / (total_Y - amount_out)` entirely in `U128`. The caller in `processor.rs` (`Process::swap_base_out` and `swap_base_out_v2`) further multiplies/divides this in `U128` to add the swap fee, then converts to `u64` with `.as_u64()` — a truncating conversion that keeps only the low 64 bits, with no overflow check — as opposed to `Calculator::to_u64()`, which safely errors on overflow (`program/src/math.rs:46-48`).

The check that would normally prevent a degenerate (near-zero) denominator — `swap.amount_out >= total_pc_without_take_pnl` (or coin equivalent) — is performed only after `swap_in_after_add_fee` has already been computed and truncated (`program/src/processor.rs:2212-2216`, `2211-2216` region). This lets an attacker pick `amount_out` arbitrarily close to the pool reserve, driving the denominator to a very small integer and the true `amount_in` value to a huge multiple of the pool's coin reserve — far beyond `u64::MAX` — which then wraps around during the unchecked cast into a small, attacker-influenceable residue.

### Impact Explanation
The wrapped, arbitrarily small `swap_in_after_add_fee` is used both for the `user_source.amount`/`max_amount_in` sufficiency checks (`program/src/processor.rs:2202-2210`) and as the amount actually transferred in from the user (`program/src/processor.rs:2218-2234`), while the pool pays out the full attacker-chosen `swap.amount_out` from its vault. This allows an attacker to withdraw pool funds (coin or pc side) while paying a negligible or attacker-chosen small counter-amount, directly draining LP/pool funds — a concrete theft of pool funds and insolvency of pool accounting.

### Likelihood Explanation
The path is reachable by any unprivileged user in a single transaction via the public `SwapBaseOut`/`SwapBaseOut2` instructions with fully attacker-chosen instruction data (`amount_out`, `max_amount_in`), and requires no special account permissions — only ordinary swap accounts. The main obstacle is arithmetic precision: the attacker must select `amount_out` so that the huge `U128` result wraps to a `u64` value that is simultaneously ≤ their `user_source.amount`, ≤ their `max_amount_in`, and nonzero-but-small enough to be profitable, which is a solvable Diophantine/brute-force search offline before submitting the transaction.

### Recommendation
Replace `.as_u64()` with `Calculator::to_u64(...)?` (or equivalent checked `try_into`) at every point where a `U128`/`U256` intermediate swap value is narrowed to `u64` in `swap_base_out`/`swap_base_out_v2` (and audit `swap_base_in` for the same pattern), so that an overflow causes the instruction to fail with `AmmError::ConversionFailure` instead of silently wrapping.

### Proof of Concept
1. Attacker identifies a pool with reserves `total_coin_without_take_pnl = C`, `total_pc_without_take_pnl = P`.
2. Attacker submits `SwapBaseOut` with `swap.amount_out = P - k` for a small integer `k` (e.g., `k = 1`), and `swap.max_amount_in = u64::MAX` (or a small value chosen to match the expected wrapped residue), with `user_source.amount` sufficient to cover only the wrapped (truncated) value.
3. `swap_token_amount_base_out` computes `amount_in = C * (P-k) / k`, a value that for realistic `C`/`P` reserves vastly exceeds `u64::MAX` when `k` is small.
4. After multiplying by `swap_fee_denominator` and ceil-dividing, the `U128` result is truncated via `.as_u64()` to a wrapped low-64-bit value `w`.
5. If `w` happens to satisfy `w <= user_source.amount` and `w <= swap.max_amount_in`, the checks at `program/src/processor.rs:2202-2210` pass, and the swap proceeds: the attacker transfers only `w` tokens in but receives `swap.amount_out = P - k` (nearly the entire pc reserve) out, at `program/src/processor.rs:2217-2234`.

Note: exact exploitability requires computing/searching for reserve/`k` combinations that produce a favorable wrapped `w`; this cannot be fully validated without executing the on-chain math against live reserve values, but the unchecked truncating cast combined with the attacker-controlled denominator is a concrete, exploitable root cause matching the reported bug class.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
