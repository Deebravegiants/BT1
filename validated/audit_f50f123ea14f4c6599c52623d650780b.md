### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` (and `topic`, `webhook_id`, `api_version`) directly from HTTP headers, but the HMAC signature that `Registry.process` verifies only covers the raw request body. This breaks the identity binding: `shop reported to handler == shop bound by HMAC` is false; the HMAC binds only `body == signed(body)`, leaving `shop` completely unauthenticated relative to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and does not include the `shop`, `topic`, or `webhook_id` headers: [1](#0-0) 

`shop` is read straight from the (attacker-controllable at the transport level, i.e. anyone who can send an HTTP request to the app's webhook endpoint) header, with no cryptographic binding to that value: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body was signed with the app's shared secret — the same secret is used for *every* shop that installs the app, not a per-shop secret) and then unconditionally forwards `request.shop` to the developer's handler as the trusted tenant identifier: [3](#0-2) 

The `WebhookMetadata` struct and the gem's own documented usage pattern treat `data.shop` as the authoritative tenant/shop identifier for routing work (e.g. `shop_domain: data.shop`): [4](#0-3) [5](#0-4) 

Because the api_secret_key is shared across all shops that install the app (not shop-specific), a valid `hmac-sha256` value for a given raw body is identical no matter which shop header accompanies it. An attacker who is themselves a legitimate merchant installing the vulnerable app can capture one authentic webhook delivery (body + valid HMAC) sent to their own endpoint, and then replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` because it only checks `computed_signature(body, secret) == received_signature`, never touching `shop`: [6](#0-5) 

The forged request is accepted, and the handler is invoked with attacker-chosen `shop` value alongside genuine, HMAC-valid body content, letting an unprivileged internet user impersonate webhook traffic "from" any other tenant/shop of the host application.

### Impact Explanation
This crosses the tenant boundary the report's rules explicitly call out: "a shop authenticated versus the shop stored as a session key" — here the shop value acted upon by the handler is never authenticated at all. Any host application following the gem's documented pattern (using `data.shop` to select which tenant's records to update, e.g. `shop_domain: data.shop`) can be tricked into writing/processing data under an incorrect shop, i.e. cross-tenant access/data confusion, satisfying the "High"/"Critical" cross-tenant criteria.

### Likelihood Explanation
Likelihood is High: the attacker only needs to be an existing, unprivileged merchant that has installed the app (no special access, no leaked secrets) to obtain one legitimate body+HMAC pair from their own webhook deliveries, then can replay it against the app's public webhook endpoint with an arbitrary `shop` header value. This requires no `api_secret_key`, no access token, and no privileged account — only observation of one's own outbound-to-them webhook traffic, which is normal usage.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed payload verification, e.g. by re-deriving/cross-checking the shop domain against a value obtained independently (such as a stored per-shop session, or Shopify's separate signed webhook headers introduced for exactly this purpose), or by documenting/enforcing that `data.shop` from `WebhookMetadata` must never be trusted as an authorization boundary without additional verification (e.g., checking it against an existing installed-shop record) before using it to select tenant-scoped resources.

### Proof of Concept
1. Install the vulnerable app on shop `attacker-shop.myshopify.com`; capture a legitimate webhook POST to the app's callback endpoint, e.g. body `{"id":123}` with header `x-shopify-hmac-sha256: <validHmac>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the same endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) body using the app's single shared `api_secret_key` and finds it matches — validation succeeds.
4. The registered `WebhookHandler#handle` is invoked with `data.shop == "victim-shop.myshopify.com"` even though the payload never actually originated from Shopify on behalf of that shop, causing the host app to process/act on data under the wrong tenant.
