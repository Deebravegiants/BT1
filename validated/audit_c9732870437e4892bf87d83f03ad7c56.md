### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with the delivered `shop` value [1](#0-0) . In reality, `HmacValidator.validate` only checks the HMAC against `to_signable_string`, and `Webhooks::Request#to_signable_string` returns only the raw body, never the headers [2](#0-1) . The `shop`, `topic`, and `webhook_id` values that are ultimately handed to the app's handler are all read directly from unsigned headers [3](#0-2) .

### Finding Description
`Registry.process` raises `InvalidWebhookError` only when `Utils::HmacValidator.validate(request)` fails, then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id` and dispatches it to the registered handler [4](#0-3) . `HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the received signature [5](#0-4) , and for a webhook `Request`, `to_signable_string` is defined as `@raw_body` alone [2](#0-1) .

Because the signature only binds the body bytes, the identity binding the gem's own documentation promises — "verified HMAC" ⟺ "the `shop`/`topic`/`webhook_id` delivered to the handler" — does not hold. The `shop-domain`, `topic`, and `webhook-id` headers are read straight from the (unsigned) HTTP headers [3](#0-2)  and are trusted as authentic tenant/topic identifiers by the handler, per the documented `data.shop` contract "The shop domain of the webhook" [6](#0-5) .

Any unprivileged party can install the app on a shop they control (a normal, unprivileged action for any public/dev Shopify app) and thereby legitimately receive real webhook deliveries signed with the app's shared `client_secret`, since the `client_secret`/`api_secret_key` used for HMAC computation is the same for every shop installing the app — it is not shop-specific. Having obtained a `(raw_body, hmac-sha256)` pair that validates successfully, the attacker can resend that exact body/signature pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to a different, victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` calls the handler with `shop:` set to the attacker-forged domain.

### Impact Explanation
This crosses a tenant boundary: an app that persists or acts on webhook data keyed by `data.shop` (exactly as recommended in the docs' own handler example, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [7](#0-6)  can be made to attribute attacker-controlled webhook content to an arbitrary victim shop, or to falsely mark a topic/webhook-id as processed/deduplicated for a shop that never sent it. This is cross-tenant data injection/impersonation through a channel the gem explicitly claims to authenticate.

### Likelihood Explanation
The prerequisite (installing a public app on a self-controlled shop to obtain a validly-signed webhook body) is achievable by any unprivileged actor without needing the target's or the app's actual secret — they only need to trigger their own genuine webhook delivery, since the HMAC secret is shared across all installs of the same app.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) header values in the signable content verified against the HMAC, or independently verify that `request.shop` corresponds to a shop with an active, known session/install before dispatching to the handler, rather than trusting the header verbatim.

### Proof of Concept
1. Install the target app on an attacker-controlled shop (`attacker.myshopify.com`); trigger any subscribed event so Shopify delivers a genuine webhook with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared secret.
2. Capture `raw_body` and `x-shopify-hmac-sha256` from that request.
3. Replay a POST to the app's webhook endpoint using the same `raw_body`/`x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` passes (only `raw_body` is checked) [2](#0-1) ; `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` and the attacker's body content [4](#0-3) .

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
