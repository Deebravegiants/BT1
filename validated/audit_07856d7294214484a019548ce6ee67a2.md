## Title
Unregistered source chain spoofs the gateway itself, bypassing `RedeemEscrow`/`RefundEscrow` authentication - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron `IntentGatewayV2.authenticate` function validates an incoming `RedeemEscrow`/`RefundEscrow` message by comparing the encoded `from` module address against `instance(request.source)`. But `instance()` does not revert on an unregistered state machine — it falls back to `address(this)`: [1](#0-0) 

```
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
``` [2](#0-1) 

This mirrors the Exactly Protocol root cause: an "is this address valid/registered" check that silently substitutes a default/fallback identity instead of rejecting the unknown input, letting an attacker impersonate a trusted address.

### Finding Description
`onAccept` reaches `authenticate` for `RedeemEscrow`/`RefundEscrow` before checking that `request.source` is a legitimately paired chain [2](#0-1) . `authenticate` calls `instance(request.source)`, and for any `stateMachineId` that was never registered via `NewDeployment`, `_instances[keccak256(stateMachineId)]` is zero, so `instance()` returns `address(this)` rather than reverting.

Consequently, a relayed ISMP `PostRequest` whose `source` is any state machine that Hyperbridge governance never paired with this gateway (i.e., not in `_instances`) will pass `authenticate` as long as its `from` field is set to `address(this)` (the gateway's own address on this chain). The attacker only needs a state machine identifier that is not in `_instances` — this includes chains that were simply never configured, not just malicious ones — and a relayed proof asserting a `PostRequest` with `from = address(this)`.

Compare this to the corrected mainline implementation of the same authentication logic in `IntentsBase._instance`, which explicitly reverts with `UnknownInstance` when the gateway is unregistered: [3](#0-2) 

The Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) retains the older, unsafe fallback-to-`address(this)` pattern that the EVM `IntentsBase`/`ExtrinsicIntents` codebase has since moved away from — an exact structural analog of the Exactly `DebtManager` bug, where an unchecked/mis-defaulted "market" (here, "instance") address let the attacker impersonate a trusted caller.

### Impact Explanation
If exploitable end-to-end (see Likelihood), this allows an attacker to forge a `WithdrawalRequest` claiming any commitment/token/beneficiary and have `withdraw()` transfer out escrowed tokens and accumulated transaction fees to an attacker-controlled beneficiary [4](#0-3) , i.e., theft of all currently escrowed user funds on that gateway deployment — a direct analog of the Exactly $7.2M drain via a spoofed "valid" address.

### Likelihood Explanation
Reachability requires the attacker to get a `PostRequest` with `source` = an unregistered state machine and `from` = `address(this)` delivered through the real ISMP pipeline (`HandlerV2` → `EvmHost.dispatchIncoming` → `onAccept`), which in turn requires either: (a) a legitimate consensus/state proof from a state machine ID that was never paired via `NewDeployment` but is still verifiable by the host's configured consensus client, or (b) the message being routed via Hyperbridge itself using a spoofed/omitted `_instances` entry. This is architecturally the same "unvalidated address defaults to a trusted identity" class as the rekt report, but exploitability is contingent on whether an attacker can actually source/verify a message from an "unregistered" state machine through the host's consensus verification — that reachability detail could not be fully confirmed from the available Tron client/consensus wiring in this pass. Given the explicit fix already applied on the primary EVM codebase (`IntentsBase._instance` reverts on unregistered instance) but seemingly not backported to `evm/tron/contracts/apps/IntentGatewayV2.sol`, this is very likely a real, unpatched regression on the Tron deployment rather than a false positive.

### Recommendation
Change `instance()` (or `authenticate`) in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g., with an `UnknownInstance` error) when `_instances[keccak256(stateMachineId)] == address(0)`, matching the `IntentsBase._instance` implementation in `evm/src/apps/intentsv2/IntentsBase.sol`, instead of silently falling back to `address(this)`.

### Proof of Concept
1. Do not call `NewDeployment` for state machine `X` (leaving `_instances[keccak256(X)] == address(0)`).
2. Craft/relay a `PostRequest` with `source = X`, `from = abi.encodePacked(address(gatewayOnThisChain))`, `body[0] = RequestKind.RedeemEscrow`, and `body[1:]` decoding to a `WithdrawalRequest` referencing an existing escrowed `commitment`/token/amount with `beneficiary` set to the attacker.
3. Deliver it through the host so `onAccept` is invoked; `authenticate` computes `instance(X) == address(this)`, matching the forged `from`, so the check passes and `withdraw()` pays the attacker the escrowed tokens and fees. [2](#0-1) [1](#0-0)
