### Title
Same-block DeleteKey+AddKey resets an access key's nonce below an already-used nonce, enabling replay of a stale signed transaction - ([File: runtime/runtime/src/access_keys.rs])

### Summary
The nonce range seed `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` is derived from the *current* block height at the time of `AddKey`, not from the highest nonce previously consumed on that public key. Because the nonce upper bound enforced in `verify_nonce` also floats with the current block height, an attacker who consumes a nonce close to the current block's ceiling and then deletes/re-adds the same public key **within the same block** causes the new key's stored nonce to reset to a value *below* the already-used nonce, making a previously-executed signed transaction valid again for replay.

### Finding Description
`initial_nonce_value` seeds a freshly (re)created regular access key's nonce as `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0) , and this is what `add_regular_key` writes into the trie on `AddKey` [2](#0-1) .

`verify_nonce` enforces two things: (1) `tx_nonce > current_nonce` (Monotonic) and (2) `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (the upper bound), where `block_height` is the *current* block being processed [3](#0-2) . This upper bound is intended to make room for legitimate nonces up to just under the current block's ceiling.

The exploit sequence, all executed within a single block/chunk (so `apply_state.block_height == H` for every transaction processed in it):
1. At block `H`, attacker (owning full-access key `pk`) sends `TX_A` signed with `pk`, nonce `N1` chosen close to the ceiling, e.g. `N1 = H*1_000_000 - 1`. This passes `verify_nonce` (upper bound is `H*1_000_000`) and executes, updating the on-chain access key's nonce to `N1`.
2. In the same block `H`, attacker sends `TX_B`, also signed by `pk` with nonce `N1+1` (valid, still `< H*1_000_000`), containing actions `[DeleteKey(pk), AddKey(pk)]`. `action_delete_key` removes the key [4](#0-3) , then `action_add_key` → `add_regular_key` re-creates it with `nonce = initial_nonce_value(H) = (H-1)*1_000_000` [5](#0-4) . Because `(H-1)*1_000_000 < N1`, the freshly recreated key's stored nonce is now *lower* than the nonce already consumed by `TX_A`.
3. At any later block `H' > H`, attacker resubmits (replays) the original signed `TX_A` bytes. `verify_nonce` checks `tx_nonce (N1) > current_nonce ((H-1)*1_000_000)` — true — and `tx_nonce (N1) < H'*1_000_000` — also true since `H' > H`. The stale transaction is accepted and re-executed, duplicating its effects (e.g., a `Transfer` action executes twice).

The design comment in `initial_nonce_value` references only the goal of avoiding hash collisions across key re-creation over increasing block heights (near/nearcore#3779), and the protocol-model spec confirms the nonce-monotonicity invariant is meant to prevent exactly this kind of replay [6](#0-5) . The invariant holds only when the delete+recreate happens at a *later* block than the nonce's use (`new_seed = (H-1)*1e6 ≥ Hp*1e6 > N1` when `H > Hp`), but breaks when delete and recreate occur in the *same* block as the high-nonce usage, because the seed uses `H-1`, not `H`, and does not track the maximum nonce actually consumed on that key in the current block.

### Impact Explanation
This allows an unprivileged account holder to force double-execution of one of their own previously-signed transactions (e.g., a `Transfer`, `FunctionCall`, or other action) by replaying it after intentionally corrupting their own key's nonce state. Because the signer is the account owner and this only affects the signer's own account/keys, the direct fund-loss/authorization-bypass impact is limited to the attacker's own account state — it does not by itself let an attacker forge authorization over *another* account. However, it does violate the stated protocol invariant "nonce monotonicity prevents replay" and can be leveraged wherever off-chain systems (exchanges, bridges, relayers) rely on nonce-based idempotency/uniqueness of a transaction hash to guarantee at-most-once execution (e.g., a receiver contract or indexer assuming a given signed transaction can only ever execute once). This falls into the "authorization exactness / replay of a stale signed transaction" impact class described in the question, though the blast radius is confined to the attacker's own account and any counterparties who signed off assuming replay-safety.

### Likelihood Explanation
Fully attacker-controlled and repeatable: it requires only (a) owning a full-access or appropriately-permissioned key, (b) crafting two transactions with adjacent nonces near the current block's ceiling, and (c) getting both included in the same block/chunk (feasible since a single account can submit both transactions back-to-back and NEAR's transaction pool/chunk producers commonly batch same-signer transactions into the same chunk, especially for accounts with few competing transactions). No validator or node-operator collusion is needed, and block height is public via RPC, so the ceiling nonce `H*1_000_000 - 1` is easily computed in advance.

### Recommendation
Do not reset the nonce to a purely block-height-derived seed on `AddKey` if the account already has other means of tracking previously-used nonces for that public key; alternatively, track the account-level or key-level maximum nonce ever used (not just the value on the currently-active key record) and reject re-creation seeds below that historical maximum, or seed with `max(existing tombstone nonce ceiling, (block_height) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER)` using `block_height` rather than `block_height - 1`, ensuring `initial_nonce_value(H) >= H*1_000_000 - 1 ≥` any nonce that could have been validated in block `H`. A tombstone/floor record persisted across delete/re-add cycles for the same `(account_id, public_key)` would close this gap regardless of same-block or cross-block timing.

### Proof of Concept
Unit/integration test plan (in `runtime/runtime/src/verifier.rs` or `runtime/runtime/src/tests/apply.rs`, mirroring the existing `test_validate_transaction_invalid_bad_nonce` style tests):
1. Set up an account with a full-access key `pk` at height `H`.
2. Apply `TX_A`: `Transfer` action, nonce `N1 = H*1_000_000 - 1`, signed by `pk`. Assert success and that the account balance changed.
3. In the *same* apply/block (`apply_state.block_height == H`), apply `TX_B`: `[DeleteKey(pk), AddKey(pk, FullAccess)]`, nonce `N1+1`, signed by `pk`. Assert success and read back the access key's stored nonce; assert it equals `(H-1)*1_000_000`, which is `< N1`.
4. Advance to block `H' = H+1` (or later) and re-apply the exact same serialized `TX_A` (same nonce `N1`, same signature). Assert this is accepted by `verify_nonce`/`validate_verify_and_charge_transaction` and executes again, duplicating the `Transfer` effect — demonstrating replay of an already-executed transaction, violating the "nonces strictly increasing / no replay" invariant.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
```

```rust
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
```
