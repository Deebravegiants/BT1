Confirmed: the webhook `to_signable_string` at [1](#0-0)  signs only `@raw_body`, while `shop` (line 20-23) and `topic` come from unauthenticated headers. `Registry.process` at [2](#0-1)  validates the HMAC over the request but then trusts `request.shop`/`request.topic` from headers to dispatch tenant-scoped webhook data to the handler, without binding those header values into the signed bytes.

### Title
Webhook `shop-domain`/`topic` headers are not covered by the HMAC, allowing cross-tenant webhook data injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only proves the body's integrity/authenticity, never the `shop-domain`, `topic`, or `webhook-id` headers that `Registry.process` reads and hands to the app's handler as the tenant/topic identity [2](#0-1) .

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook == shop that generated/authenticated the signed bytes`. In this gem that binding is broken because:

- `Request#shop` and `Request#topic` are read straight from HTTP headers [3](#0-2) .
- `Request#hmac` decodes the `hmac-sha256` header [4](#0-3) , and `to_signable_string` signs only `@raw_body` [1](#0-0) .
- `HmacValidator.validate_signature` compares the HMAC only against `to_signable_string` [5](#0-4) , so it never authenticates which shop or topic the body belongs to.
- `Registry.process` raises only if the HMAC over the body is invalid, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to construct `WebhookMetadata` passed to the app's handler [2](#0-1) .

Any legitimate holder of one valid `(raw_body, hmac)` pair — e.g., a merchant who installs the app on their own store and receives a genuinely-signed webhook for their own shop — can resend that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and/or `shopify-topic`) header naming a victim shop. Validation still succeeds because the header values were never part of the signed bytes, and the app's handler will process/attribute that body's data as belonging to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged user who legitimately controls only their own shop's webhook stream can cause data to be processed under another merchant's identity by any app built on this gem's `Webhooks::Registry`/`Request` (e.g., triggering `shop/redact`, `customers/redact`, or order/product update handlers against a shop the attacker doesn't control). This matches the Critical "cross-tenant access" category since the shop identity used for authorization/data-partitioning inside the handler is unauthenticated.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that (a) allows self-install (development stores, public app listings) so an attacker can obtain a validly-signed body/HMAC for at least one shop, and (b) relies on `request.shop`/`WebhookMetadata#shop` as the sole tenant key inside its handler, which is the pattern this gem's own docs recommend (`WebhookMetadata.new(topic:, shop:, body:, ...)`, `lib/shopify_api/webhooks/registry.rb:198`). No credentials, tokens, or secrets are needed — only a normal webhook endpoint reachable on the internet and one previously-observed valid webhook body/signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material, or otherwise cryptographically bind them to the verified body, so `HmacValidator.validate` fails whenever the attacker changes the `shopify-shop-domain`/`shopify-topic` headers independent of the signed body. At minimum, document/enforce that consuming apps must cross-check `request.shop` against a shop they have an active, previously-stored session/installation for before trusting webhook data, rather than treating the header alone as authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`; Shopify delivers a webhook with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — this is valid per `Request#hmac`/`to_signable_string` [6](#0-5) .
2. Attacker replays the identical `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [7](#0-6) .
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)` [8](#0-7)  and processes/persists attacker-controlled data under the victim shop's identity.
