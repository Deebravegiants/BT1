Confirmed: `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in `EvmHost.sol` all call Uniswap V2's `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`, and `EvmHost` has no `receive()`/`fallback()` or ETH-sweep function [1](#0-0) . `swapETHForExactTokens` refunds any unspent ETH to the immediate caller of the router — which is `EvmHost`, not the original user — so any ETH sent above the exact amount needed for the swap becomes stranded in the `EvmHost` contract with no recovery path. This is a stronger, more concrete analog of the reported bug class (user overpaying/losing ETH due to an inexact payment-vs-refund mismatch) than a mere off-by-one comparison.

### Title
Excess native-token payment on `dispatch`/`fundRequest` is refunded to `EvmHost` instead of the caller and becomes permanently stuck - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and swap it for the exact fee-token amount required via `IUniswapV2Router02.swapETHForExactTokens`. Any ETH sent in excess of what the swap actually needs is refunded by the Uniswap router — but to `EvmHost` (the caller of the router), not to the end user who dispatched the message. `EvmHost` has no mechanism to forward, track, or withdraw this stranded ETH, so users effectively lose any overpayment.

### Finding Description
In all three payable entry points:

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
``` [1](#0-0) 

the same pattern repeats for `dispatch(DispatchGet)` [2](#0-1)  and `fundRequest` [3](#0-2) .

`swapETHForExactTokens(amountOut, path, to, deadline)` computes the exact ETH input needed to receive `amountOut` of the output token and, per Uniswap V2 router semantics, **refunds any leftover ETH to `msg.sender` of the router call**. Here, the router's `msg.sender` is `EvmHost` itself (since `EvmHost` calls the router directly), not `tx.origin`/the actual dispatching account. Consequently:

- If a user sends more ETH than the exact amount required for the swap (a very plausible situation, since the docs explicitly instruct front-ends to "estimate" the required native amount client-side rather than compute it exactly — see `quote()` guidance in the docs), the excess is returned to `EvmHost`'s own balance.
- `EvmHost.sol` defines no `receive()`/`fallback()` function and no admin/owner sweep or refund function for stray ETH, based on the grep across the file.
- The ETH is not tracked in any per-request or per-user accounting structure (`_requestCommitments` only tracks `feeToken` amounts via `FeeMetadata`), so it cannot be attributed back to the original payer even if a future upgrade added a sweep.

This is directly analogous to the reported Allo.sol issue: the sender pays more ETH than is actually owed, and the excess is not returned to them — except here the loss is not bounded by a single wei off-by-one, it's the full difference between `msg.value` and the exact swap cost, and the funds are entirely unrecoverable rather than merely reverting the transaction.

### Impact Explanation
Any user who dispatches a POST/GET request or funds a request with native token and sends `msg.value` even slightly above the exact amount needed for the Uniswap swap permanently loses the excess ETH — it becomes stuck in the `EvmHost` contract's balance with no way for the user (or anyone) to reclaim it. Given that the documented usage pattern relies on off-chain `quote()`/`getAmountsIn` estimation (with the docs' own warning that `quote()` is unsafe to call on-chain due to sandwich-attack risk), a mismatch between the estimated and actual required ETH is common and expected, meaning this is not just an edge case — it's a normal-usage funds-loss vector. This qualifies as concrete freezing/loss of user funds.

### Likelihood Explanation
High. Every native-token dispatch or `fundRequest` call is exposed to this: exact `msg.value` is nearly impossible to guarantee due to price movement between quote-time (off-chain) and execution-time (on-chain), block-time slippage in the AMM pool, and the explicit documentation guidance that `quote()` should only be used off-chain as an estimate. Any unprivileged user calling `dispatch{value: msg.value}(...)` with a even a minor overestimate triggers the loss — no special conditions or malicious actors are required.

### Recommendation
After calling `swapETHForExactTokens`, check `address(this).balance` (or capture the return value / pre/post balance delta) and forward any leftover ETH back to `_msgSender()` (or the `payer`) instead of letting it sit in the contract. Alternatively, use `swapETHForExactTokens` with an explicit refund step:
```solidity
uint256 balanceBefore = address(this).balance - msg.value;
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp);
uint256 refund = address(this).balance - balanceBefore;
if (refund > 0) {
    (bool sent, ) = _msgSender().call{value: refund}("");
    require(sent);
}
```
Apply the same fix to `dispatch(DispatchGet)` and `fundRequest`.

### Proof of Concept
1. Attacker/user computes the fee-token cost via off-chain `quote()`/`getAmountsIn`, then adds a safety buffer (as recommended in the docs to avoid slippage-induced revert) and calls:
   `EvmHost.dispatch{value: bufferedAmount}(postRequest)` where `bufferedAmount > exactAmountNeeded`.
2. Inside `dispatch`, `swapETHForExactTokens{value: bufferedAmount}(post.fee, path, address(this), deadline)` executes; the router computes the exact ETH input for `post.fee` output tokens and refunds `bufferedAmount - exactAmountNeeded` ETH to `msg.sender` of the swap call, i.e., `EvmHost`.
3. `EvmHost`'s ETH balance increases by the refunded amount; the original caller never receives it back, and `EvmHost` has no function to send it anywhere (confirmed by the absence of `receive()`, `fallback()`, or sweep functions in `EvmHost.sol`).
4. The user has permanently lost `bufferedAmount - exactAmountNeeded` in native token.
