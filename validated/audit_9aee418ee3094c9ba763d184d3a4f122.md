### Title
Pharos state machine `verify_state_proof`/`verify_membership` lack duplicate-key rejection, allowing CPU amplification DoS via padded `GetRequest.keys` - ([File: modules/ismp/state-machines/pharos/src/lib.rs])

### Summary
The EVM state-machine client explicitly guards `verify_state_proof` against duplicate keys before doing any proof work, because a repeated key still resolves to the same value and is rejected anyway by the caller's key-count check — but only *after* every repeat has paid for a full proof walk. The Pharos state-machine client, which implements the identical `StateMachineClient` interface and is reachable from the exact same unsigned dispatch paths, has no equivalent check: it iterates over an attacker/relayer-supplied `keys: Vec<Vec<u8>>` and performs a full `spv::verify_proof`/`verify_non_existence_proof` SHA-256 Merkle walk for every entry, including exact duplicates, before any downstream length/dedup check runs.

### Finding Description
`modules/ismp/state-machines/evm/src/lib.rs::verify_state_proof` rejects duplicate keys up front: [1](#0-0) 

This was a deliberate fix (see the accompanying test suite explicitly named for "reported shape: many repeats of one account key"): [2](#0-1) 

The Pharos client, `modules/ismp/state-machines/pharos/src/lib.rs`, implements the same `StateMachineClient::verify_state_proof`/`verify_membership` trait but has no duplicate-key `BTreeSet` guard anywhere in the crate. It simply loops over every supplied key and, for each one, performs a full SPV proof verification (`spv::verify_proof` / `spv::verify_non_existence_proof`, SHA-256 hashing over the proof path) with no de-duplication: [3](#0-2) [4](#0-3) 

This function is reached unprivileged: `pallet-ismp::handle_unsigned` accepts any `Vec<Message>` from `ensure_none` origin, and `ResponseMessage`/`RequestMessage`/`TimeoutMessage` handlers call `state_machine.verify_state_proof(...)`/`verify_membership(...)`/`verify_non_membership(...)` where `state_machine` is resolved dynamically per consensus client (Pharos included): [5](#0-4) 

Critically, `dedup_requests` (used in `handlers/response.rs`, `handlers/request.rs`, `handlers/timeout.rs`) only rejects duplicate *top-level requests* by hashing the whole `Request` — it does not look inside a single `GetRequest`'s `keys: Vec<Vec<u8>>` field: [6](#0-5) 

So a relayer can submit one `GetRequest` (or a small batch) whose `keys` vector contains a large number of copies of the same key. `handlers/response.rs` forwards that field verbatim into `state_machine.verify_state_proof`: [7](#0-6) 

For a Pharos-backed `state_id`, this drives the unbounded per-key SPV verification loop with no early rejection — the exact bug class from CVE-2015-0222 (duplicate submitted values causing an unbounded multiplication of expensive per-item work), which the EVM client was already patched against but the Pharos client was not.

### Impact Explanation
This is reachable by any unprivileged party who can submit an unsigned `handle_unsigned` extrinsic with a crafted `ResponseMessage`/`GetRequest` targeting a Pharos-consensus state machine. Padding `keys` with thousands of duplicate entries multiplies SPV verification cost (SHA-256 proof-node walks) per submission, consuming block execution weight/CPU disproportionate to the batch's declared size, and can be repeated cheaply (an unsigned, fee-free extrinsic) to degrade block production/relayer throughput — a resource-exhaustion / denial-of-service on the message-delivery route for Pharos state machines. This directly matches the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Likely to be practically exploitable wherever a Pharos consensus client is configured: the entry point (`handle_unsigned`) is designed to be permissionless/unsigned, requires no funds beyond gas/weight, and the vulnerable loop is a straightforward, already-known bug class (proven exploitable and explicitly fixed in the sibling EVM implementation), making rediscovery trivial via code diffing between the two state-machine clients.

### Recommendation
Add the same up-front duplicate-key rejection used in the EVM client to `modules/ismp/state-machines/pharos/src/lib.rs::verify_state_proof` (and, if commitments can also repeat, to `verify_membership`): collect seen keys into a `BTreeSet` and return an error (e.g. `PharosStateMachineError::DuplicateKey`) on the first repeat, before any `spv::verify_proof`/`verify_non_existence_proof` call is made.

### Proof of Concept
1. Configure a Pharos consensus client/state machine for a destination.
2. As an unprivileged relayer, submit `Ismp::handle_unsigned([Message::Response(ResponseMessage { requests: [GetRequest { keys: vec![same_key; N], .. }], proof, signer })])` with `N` large (e.g. tens of thousands, bounded only by extrinsic/weight limits).
3. `handlers/response.rs` calls `state_machine.verify_state_proof(host, keys, ...)`, which for the Pharos client runs `verify_state_proof` in `modules/ismp/state-machines/pharos/src/lib.rs`, executing a full SPV Merkle proof walk once per duplicate key with no short-circuit — consuming CPU/weight proportional to `N` before the eventual key-count mismatch (or success) is even evaluated.

/// Verify membership of ISMP commitments in the Pharos state.
pub fn verify_membership<H: Keccak256 + Send + Sync>(
	commitments: Vec<H256>,
	root: StateCommitment,
	proof: &Proof,
	contract_address: H160,
) -> Result<(), Error> {
	let pharos_proof = decode_pharos_state_proof(proof)?;

	let state_root = H256::from_slice(&root.state_root[..]);
	let address: [u8; 20] = contract_address.0;

	let commitment_keys = req_commitment_key::<H, _>(commitments, |k| k.to_vec());

	// Pharos uses a flat trie — storage proofs verify directly against state_root.
	for slot_hash in commitment_keys {
		let storage_proof_nodes = pharos_proof
			.storage_proof
			.get(&slot_hash)
			.ok_or(PharosStateMachineError::MissingCommitmentStorageProof)?;

		let slot_key: [u8; 32] = slot_hash
			.try_into()
			.map_err(|e: Vec<u8>| PharosStateMachineError::InvalidSlotHashLength(e.len()))?;

		spv::verify_membership_proof(
			storage_proof_nodes,
			&spv::build_storage_key(&address, &slot_key),
			&state_root.0,
		)
		.map_err(|e| PharosStateMachineError::SpvVerificationFailed(alloc::format!("{e:?}")))?;
	}

	Ok(())
}

/// Verify state proof and return key-value map.
pub fn verify_state_proof<H: Keccak256 + Send + Sync>(
	keys: Vec<Vec<u8>>,
	root: H256,
	proof: &Proof,
	ismp_address: H160,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
	let pharos_proof = decode_pharos_state_proof(proof)?;

	let state_root = root;

	// Pharos uses a flat trie — storage proofs verify directly against state_root.
	let mut map = BTreeMap::new();

	for key in keys {
		let (contract_addr, slot_hash) = if key.len() == 52 {
			// First 20 bytes = contract address, last 32 = slot hash
			let addr = H160::from_slice(&key[..20]);
			(addr, key[20..].to_vec())
		} else if key.len() == 32 {
			// Direct slot hash for the ISMP host contract
			(ismp_address, key.clone())
		} else if key.len() == 20 {
			// Account query which verifies account proof and return raw account value
			let address: [u8; 20] = key
				.clone()
				.try_into()
				.map_err(|e: Vec<u8>| PharosStateMachineError::InvalidAddressLength(e.len()))?;
			let account_data = pharos_proof
				.account_proofs
				.get(&key)
				.ok_or(PharosStateMachineError::MissingAccountProof)?;

			spv::verify_proof(
				&account_data.proof_nodes,
				&address,
				&account_data.raw_value,
				&state_root.0,
			)
			.map_err(|e| PharosStateMachineError::SpvVerificationFailed(alloc::format!("{e:?}")))?;

			map.insert(key, Some(account_data.raw_value.clone()));
			continue;
		} else {
			return Err(PharosStateMachineError::UnsupportedKeyLength.into());
		};

		let contract_address: [u8; 20] = contract_addr.0;

		let slot_key: [u8; 32] = slot_hash
			.clone()
			.try_into()
			.map_err(|e: Vec<u8>| PharosStateMachineError::InvalidSlotHashLength(e.len()))?;

		// Check if this is a non-existence proof
		if let Some(non_existence) = pharos_proof.non_existence_proofs.get(slot_key.as_slice()) {
			spv::verify_non_existence_proof(
				&non_existence.proof_nodes,
				&spv::build_storage_key(&contract_address, &slot_key),
				&state_root.0,
				&non_existence.sibling_proofs,
			)
			.map_err(|e| PharosStateMachineError::SpvVerificationFailed(alloc::format!("{e:?}")))?;
			map.insert(key, None);
			continue;
		}

		// Otherwise verify existence proof
		let storage_proof_nodes = pharos_proof
			.storage_proof
			.get(slot_key.as_slice())
			.ok_or(PharosStateMachineError::MissingStorageProof)?;

		let storage_value = pharos_proof
			.storage_values
			.get(&slot_hash)
			.ok_or(PharosStateMachineError::MissingStorageValue)?;

		// Pad value to 32 bytes for proof verification
		let mut padded_value = [0u8; 32];
		if storage_value.len() <= 32 {
			padded_value[32 - storage_value.len()..].copy_from_slice(storage_value);
		} else {
			return Err(PharosStateMachineError::StorageValueTooLarge.into());
		}

		spv::verify_proof(
			storage_proof_nodes,
			&spv::build_storage_key(&contract_address, &slot_key),
			&padded_value,
			&state_root.0,
		)
		.map_err(|e| PharosStateMachineError::SpvVerificationFailed(alloc::format!("{e:?}")))?;

		map.insert(key, Some(storage_value.clone()));
	}

	Ok(map)
}

/// Reject duplicate requests within a batch. Each request's ISMP
/// canonical commitment (via `hash_request`) is tracked in a `BTreeSet`;
/// the first repeat short-circuits with `DuplicateRequest` and names the
/// offending request in the error meta. Wire format for batches is a
/// `Vec`, so this is the line of defence against an attacker padding a
/// batch with identical requests to inflate its apparent size.
pub fn dedup_requests<H: Keccak256>(requests: &[Request]) -> Result<(), Error> {
	let mut seen = alloc::collections::BTreeSet::new();
	for req in requests {
		if !seen.insert(hash_request::<H>(req)) {
			return Err(Error::DuplicateRequest { meta: req.clone().into() });
		}
	}
	Ok(())
}
