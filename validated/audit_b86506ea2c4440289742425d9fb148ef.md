### Title
Webhook `shop` domain is trusted for tenant identification without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies the authenticity of an incoming webhook solely by HMAC-validating the raw request body, then unconditionally trusts the `shop` value extracted from the `X-Shopify-Shop-Domain` HTTP header — a value that is never included in the signed bytes — to build the `WebhookMetadata` handed to the host application's handler. This breaks the identity binding `hmac_verified_bytes == identity_used_for_tenant_lookup`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from an HTTP header, entirely outside the signed content: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC: [3](#0-2) 

`Registry.process` performs exactly this body-only check, then immediately trusts `request.shop` (the unauthenticated header) to construct the `WebhookMetadata` dispatched to the app's handler: [4](#0-3) 

Because the app's `api_secret_key` used to compute the HMAC is shared across *all* merchants who install the app (it is not per-shop), any unprivileged user can install the app on their own store (a normal, unprivileged signup action) and receive genuinely-signed webhook deliveries for events on their own shop. That request — with a valid `X-Shopify-Hmac-Sha256` header and body — can then be resent directly to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop that also uses the app. `Registry.process` will accept it: the HMAC over the (attacker-controlled but legitimately-signed) body still validates, and `request.shop` is taken at face value as the victim's domain.

This matches the identity-binding break called out in the prompt: a field ("shop") acted upon by the handler but not covered by the HMAC.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select the tenant record to update (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, or any custom-fields webhook that writes to per-shop storage), an attacker can inject fabricated events attributed to a victim shop, using attacker-controlled body content, achieving cross-tenant data corruption/impersonation. This satisfies the Critical bar of "cross-tenant access" since the attacker (an unprivileged installer of the same app) causes shop-B-tagged data/actions to be processed using data of their own choosing.

### Likelihood Explanation
Requires only: (1) that the attacker be a legitimate, unprivileged installer of the target app on their own store (freely available via app stores / dev stores), and (2) the ability to replay an HTTP POST with modified headers to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. This is a straightforward replay/header-tampering attack.

### Recommendation
Include the shop domain (and topic/webhook-id) in the HMAC-signed content, or otherwise cryptographically bind the header-derived `shop` to the verified payload before it is handed to `WebhookHandler#handle`. At minimum, the gem should document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant key without additional verification (e.g., cross-checking against the app's own record of registered shops/access tokens).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a legitimately HMAC-signed webhook (e.g., `customers/data_request`) to the app's public webhook URL, with body `B` and header `X-Shopify-Hmac-Sha256: H` computed as `HMAC(api_secret_key, B)`, and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this exact request to the same endpoint, but rewrites the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (a real merchant using the app). Body `B` and `X-Shopify-Hmac-Sha256: H` are left unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and finds it equals `H` — validation passes because it only checks the body bytes: [5](#0-4) 
5. `request.shop` returns `"victim.myshopify.com"` from the tampered header, and `WebhookMetadata.new(shop: request.shop, body: request.parsed_body, ...)` is passed to the app's handler as if this event legitimately originated from the victim shop, with attacker-chosen body content.
