### Title
Cross-Tenant Webhook Shop Spoofing via HMAC Scope Mismatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read from unauthenticated HTTP headers and passed straight through to the app's webhook handler. Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that has the app installed, a valid `(body, hmac)` pair captured from one shop's legitimate webhook can be replayed to the same endpoint with the `shop-domain` header rewritten to a victim shop, and `Registry.process` will accept it as authentic.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the signature over `verifiable_query.to_signable_string`. For webhooks, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` fields are pulled from headers that are never part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then constructs `WebhookMetadata` using the *unauthenticated* `request.shop`, `request.topic`, etc., and forwards it directly to the app-supplied handler: [3](#0-2) 

`WebhookMetadata#shop` is a plain `String` field, with no cryptographic binding to the signed body: [4](#0-3) 

The identity binding that should hold is: `shop header used by the handler == shop that the HMAC signature actually attests to`. Because the signature covers only the body, this equality does not hold — the same `(body, hmac)` pair is valid under the app's single shared `api_secret_key` regardless of which shop's header is attached to it. The library's documented usage pattern explicitly treats `data.shop` as the trusted per-tenant identifier for downstream processing (queuing jobs by shop domain), confirming that host apps rely on this field for tenant scoping: [5](#0-4) 

### Impact Explanation
Any user can install the app for free on their own development/trial store (an "unprivileged internet user" from the app's perspective — no special credentials, tokens, or access to `api_secret_key` are required). Once installed, Shopify will send that user genuinely-HMAC-signed webhooks addressed to their own shop. Since the signature only ever covers the JSON body (never the shop header) and the same `api_secret_key` is shared by the app across *all* installations, the attacker can take a captured, validly-signed `(body, hmac)` pair and resend it to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header changed to a victim shop's domain. `Registry.process` will validate the HMAC successfully (it only checks the body) and will invoke the handler with `WebhookMetadata(shop: <victim-shop>, ...)`. Any host application logic keyed off `data.shop` (looking up the victim's stored session/access token, updating victim shop records, enqueuing jobs against the victim's tenant) is now operating on attacker-chosen tenant data — a cross-tenant identity confusion.

### Likelihood Explanation
High reachability, no privileged credentials needed: an attacker only needs (1) the ability to install the target app on any shop (trivial — any Shopify Partner/dev store), and (2) to intercept/replay an HTTP request to a publicly reachable webhook endpoint they already legitimately receive events on. No access to `api_secret_key`, tokens, or the victim's environment is required. The vulnerability is entirely within this gem's `Webhooks::Request`/`Registry` implementation, not a misuse of a documented safety contract by the host app — the documented usage pattern (`docs/usage/webhooks.md`) actively encourages trusting `data.shop`.

### Recommendation
Bind the tenant/topic identity into the signed payload verification, e.g. include the `shop-domain`, `topic`, and `webhook-id` headers as part of the signable string (mirroring Shopify's actual HMAC scheme if it differs), or independently verify that `request.shop` corresponds to a shop with an active, matching webhook registration/subscription id before dispatching to the handler. At minimum, document/require that host apps cross-check `data.shop` against a shop-specific state (e.g., known `webhook_id` to shop mapping) rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app registers webhook, e.g., `orders/create`.
2. Attacker triggers an event and captures the legitimate webhook POST, including body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), along with `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same request to the app's webhook endpoint, only replacing the header value with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (body `B` and `H` unchanged).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `Utils::HmacValidator.validate(request)` recomputes `HMAC(api_secret_key, B)`, which still equals `H`, so validation succeeds: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act on `victim-shop` using attacker-controlled body content.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
