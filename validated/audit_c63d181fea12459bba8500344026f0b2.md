Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read from unauthenticated HTTP headers. `Registry.process` validates only that HMAC-over-body, then hands the unverified `shop` header straight to the app's `WebhookHandler` as the tenant identity, breaking the binding `HMAC-verified-bytes == shop-claimed-in-request`.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` (shared by OAuth and webhooks) only recomputes the HMAC over `to_signable_string` and compares it to the `hmac` field: [3](#0-2) 

`Registry.process` uses exactly this validation, then forwards `request.shop` — the unauthenticated header value — into `WebhookMetadata`, which is delivered to the app's handler as the tenant identity for data processing: [4](#0-3) [5](#0-4) 

The `api_secret_key` (client secret) used to sign webhooks is shared across **all** shops that install a given app, not per-tenant. Consequently, any shop that installs the app — an event fully reachable by an unprivileged internet user for a public app — can trigger a real webhook delivery for its own store, capturing a genuinely valid `(raw_body, hmac)` pair. Because the signature covers only the body and never the `shop-domain` header, that same `(raw_body, hmac)` pair remains valid when replayed with the `x-shopify-shop-domain` header changed to any other shop that has installed the same app. `Registry.process` will accept it (HMAC check passes) and dispatch it to the handler tagged with the attacker-chosen victim shop.

The broken equality is:
`shop authenticated by HMAC == shop delivered to the handler`
In reality: HMAC authenticates only the body bytes; `shop` is parsed from an untrusted header and never fed into `to_signable_string`.

### Impact Explanation
This allows a malicious app-installer (any shop owner who installs the third-party app) to inject attacker-controlled webhook payloads that the host application will process *as if* they originated from a different, victim tenant of the same app. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up/update per-shop records, trigger redactions, or drive business logic keyed by shop), this is a cross-tenant data-integrity/confusion vector — matching the "cross-tenant access" Critical impact category, since the tenant boundary that the gem is supposed to enforce via HMAC validation is not actually bound to the `shop` value it hands to the app.

### Likelihood Explanation
Moderate-to-high: the attacker needs only to be a legitimate (even free/trial) installer of the target app to obtain their own valid `(body, hmac)` pairs from real Shopify-delivered webhooks — no secrets or elevated privileges are required. The `shop-domain` header is then trivially rewritten in a replayed HTTP request to the app's webhook endpoint, which validates HMAC using the shared `api_secret_key` and does not check the header/body binding.

### Recommendation
Bind the tenant/topic identity into the HMAC-covered signable string, or otherwise cryptographically tie the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers to the signed payload before trusting them. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop-domain header (and ideally topic/webhook-id) so that a replay with a modified shop header fails signature validation, matching the approach Shopify's platform uses (HMAC is computed over the raw body server-side, but the gem should not present `request.shop` as trusted tenant context without an out-of-band verification, e.g., confirming the shop against the app's own installed-shop store/session before processing).

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and also on `victim.myshopify.com` (same app, shared `api_secret_key`).
2. Attacker triggers/receives a genuine webhook delivery to their own endpoint for `attacker.myshopify.com`, capturing the raw body `B` and its valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the shared secret).
3. Attacker POSTs a forged request to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new` parses headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — it matches `H`, so validation passes: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)` and processes it as if `victim.myshopify.com` sent that body — a forged, cross-tenant webhook.
