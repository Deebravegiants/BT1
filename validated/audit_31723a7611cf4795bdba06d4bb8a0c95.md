## Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw request body only, while the `shop`, `topic`, and `webhook_id` values that are trusted and forwarded to the app's webhook handler are read from HTTP headers that are excluded from the signed payload.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
`Request#shop`, `#topic`, and `#webhook_id` are parsed straight from HTTP headers, independent of the signed body: [2](#0-1) 
`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `verifiable_query.to_signable_string` (i.e. the raw body) against the received `hmac`, then immediately dispatches the handler using the **unverified** `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 
`HmacValidator.validate` and `validate_signature` never reference `shop`, `topic`, or `webhook_id` — they operate exclusively on `to_signable_string`: [4](#0-3) 

The identity binding broken is:
`shop attributed to the webhook by Registry.process/WebhookMetadata` ≠ `shop covered by the HMAC signature`.

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app, a `(raw_body, hmac)` pair valid for one shop's webhook delivery is also a valid HMAC for **any** `x-shopify-shop-domain` header value, since that header is not part of the signed content. An unprivileged user who operates their own shop (a legitimate, low-privilege install of the target app) legitimately receives real webhook deliveries containing a valid `raw_body` + `hmac` pair for their own shop. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with an arbitrary victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only re-derives the HMAC from `@raw_body`, and `Registry.process` proceeds to invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
Any app built on this gem that uses `shop` from `WebhookMetadata` to look up per-tenant data, credentials, or to key persistence (a very common pattern, and the one implied by the gem's own session/shop-keyed session model) can be tricked into processing attacker-controlled webhook content under a victim shop's identity. This is a cross-tenant confusion/spoofing vector satisfying the Critical impact bar ("cross-tenant access") since the shop identity binding that consuming applications rely on is not cryptographically enforced by the gem.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be a legitimate (unprivileged) merchant with the target app installed on their own store to capture one valid `(raw_body, hmac)` pair from a real webhook delivery, then replay it with a forged shop header to the same public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-covered signable string (or otherwise cryptographically bind them, e.g. by having `Request#to_signable_string` concatenate the canonicalized headers with the raw body), so that `Utils::HmacValidator.validate` fails if any of these values are altered independently of the body. At minimum, document that consuming applications must not trust `WebhookMetadata.shop`/`topic`/`webhook_id` without additional verification, and add that binding at the library layer since `Registry.process` already advertises "validated" webhook data to handlers.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `products/update`) and capture the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` that Shopify sends to the app's webhook endpoint.
2. Replay a POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only [5](#0-4) , matches `H`, and passes.
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [6](#0-5) , causing the app to process attacker-supplied content attributed to the victim tenant.
