### Title
Webhook HMAC only signs the request body, not the `shop-domain` header — allows cross-tenant shop spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` — sourced from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` header — as the tenant identifier passed to the app's webhook handler. Because the shared app `client_secret` is identical for every merchant installation, an attacker who controls one legitimate installation can capture a validly-signed webhook body and replay it with a forged shop-domain header, causing the app to process the payload under a different tenant's identity while the HMAC check still passes.

### Finding Description
`Request#hmac` and `Request#to_signable_string` establish what is cryptographically bound by the signature: [1](#0-0) 

Only `@raw_body` is included in the signable string. The `shop` accessor, however, is read directly from an HTTP header with no relation to the signed bytes: [2](#0-1) 

`HmacValidator.validate` verifies exactly the bytes returned by `to_signable_string` against the app's `api_secret_key`: [3](#0-2) 

`Registry.process` then validates the HMAC and, using the *same* `request` object, forwards the unauthenticated `request.shop` value straight into the handler as the tenant identity, alongside the HMAC-authenticated body: [4](#0-3) 

The identity binding that should hold is:
`shop asserted to the handler (request.shop, header-derived)` == `shop that produced the HMAC-signed bytes (request.raw_body, secret-derived)`.

This binding is not enforced: the signature only proves "this body was produced by someone holding the app's `client_secret`" — it says nothing about which shop that body belongs to. Since Shopify apps use one `client_secret` shared across *all* installations of the app, any merchant that installs the app can trigger legitimate webhooks for their own store and thereby obtain a body+HMAC pair that is valid under the app's shared secret. That merchant (or anyone able to relay the request, e.g. via a malicious proxy/CDN they control in front of the app, or replaying an intercepted delivery) can then resend the identical raw body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `WebhookMetadata.shop` is populated with the attacker-chosen victim domain, causing the app to act on attacker-controlled body content attributed to another tenant.

### Impact Explanation
This is a cross-tenant identity confusion: the webhook processing pipeline binds attacker-influenced tenant identity (`shop` header) to data that is only proven to originate from *some* installation of the app, not from the shop it claims to be. Downstream app code (as documented in `docs/usage/webhooks.md` and reflected in `WebhookMetadata`) is expected to use `shop` to select which merchant's session/data to update in response to the webhook — an attacker can use this gap to make the app record/act on data as if it came from a shop it does not control, crossing tenant boundaries. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitability requires only that the attacker control (or previously observe) one valid webhook delivery from any shop that has the target app installed — a bar any merchant/developer can trivially clear by installing the app on their own free development store and capturing one webhook call — plus the ability to deliver an HTTP request to the app's public webhook endpoint with a modified header, which is inherent to any HTTP endpoint fronted by a proxy/load balancer or accessible to a man-in-the-middle on non-TLS-pinned paths. No access to the app's `client_secret` or another merchant's access token is needed.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the header to the signed payload, e.g.:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in `to_signable_string` so the signature covers the header used for tenant routing, or
- After HMAC validation, independently verify that `request.shop` corresponds to a shop with an active session/install known to the app (rather than trusting the header value verbatim) before dispatching to the handler.

### Proof of Concept
1. App `A` is installed on attacker-controlled shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`, both using the same app `client_secret`.
2. Attacker triggers a webhook event (e.g. `products/update`) on their own shop and captures the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker sends a new HTTP POST to the app's webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` matches `H` and `shop` is `victim.myshopify.com`.
5. `HmacValidator.validate(request)` calls `to_signable_string` (returns `B`) and recomputes `HMAC-SHA256(client_secret, B)`, which equals `H` — validation passes. [3](#0-2) 
6. `Registry.process` dispatches `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body(B), ...)` to the registered handler, which now processes attacker-supplied content under the victim's tenant identity. [4](#0-3)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
