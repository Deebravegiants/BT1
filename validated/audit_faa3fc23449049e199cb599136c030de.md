### Title
Unbounded ancestry walk over attacker-supplied GRANDPA headers causes pre-authentication infinite loop / permanent hang - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
The GRANDPA `AncestryChain::ancestry` walk-back loop has no cycle detection or depth bound. It is invoked on a `BTreeMap` built directly from attacker-supplied `unknown_headers` (via `pallet_ismp::handle_unsigned`, an unsigned/free extrinsic), and — critically — it is invoked *before* any cryptographic signature verification of the GRANDPA justification. An attacker can submit two or more crafted headers whose `parent_hash` fields point at each other, forming a cycle that never terminates at the trusted base hash, causing the loop to run forever. This mirrors the pdfio CVE-2023-24808 pattern: a crafted, fully attacker-controlled input drives a parser/verifier into a non-terminating loop, causing indefinite CPU consumption. Because `handle_unsigned` messages are also executed inside `validate_unsigned` (transaction-pool validation, which runs unmetered by block weight), this hang can occur on every node that receives the malicious extrinsic, before it is even included in a block.

### Finding Description
`AncestryChain::ancestry` walks parent hashes from `block` back to `base`: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is a `BTreeMap<H::Hash, H>` built by `AncestryChain::new` purely from `finality_proof.unknown_headers` — an attacker-controlled `Vec<H>` submitted inside a consensus message: [2](#0-1) 

Since headers are decoded from raw bytes and keyed by their own computed hash, the attacker fully controls every field, including `parent_hash`. Two crafted headers `A` and `B` can be constructed such that `A.parent_hash == hash(B)` and `B.parent_hash == hash(A)`, forming a 2-cycle that contains neither the trusted `base`/`from` hash nor terminates.

The critical detail is *where* `ancestry()` is first called in `verify_grandpa_finality_proof` — **before** the GRANDPA justification signature is checked: [3](#0-2) 

```rust

justification.verify(...)?;
```

`from` (`consensus_state.latest_hash`) is public/known, and `target.hash() == finality_proof.block` is a self-consistency check the attacker trivially satisfies by choosing both values themselves. No signature, authority-set membership, or any other authenticated check gates this call. The attacker needs zero valid signatures to reach the infinite loop.

The same unbounded `ancestry()` primitive is also called per-precommit inside `GrandpaJustification::verify_with_voter_set`: [4](#0-3) 

Entry point: this whole path is reachable from the permissionless, fee-less `pallet_ismp::handle_unsigned` extrinsic, whose `ValidateUnsigned::validate_unsigned` implementation calls `Self::execute(messages)` — the same function used for actual dispatch — during **mempool/transaction-pool validation**, which is not gated by block weight metering: [5](#0-4)

A `Message::Consensus` entry that names the GRANDPA consensus client (any chain using `ismp-grandpa`, e.g. relay/standalone-chain GRANDPA clients not filtered out the way BEEFY is on Nexus) routes into `verify_grandpa_finality_proof` and hits the infinite loop described above.

### Impact Explanation
This is a Denial-of-Service vulnerability with no signature or economic cost required to trigger: any account can submit a single unsigned extrinsic containing a crafted `ConsensusMessage` with a 2-node header cycle in `unknown_headers`. On every node that attempts to validate this transaction (both in the transaction pool and, if it slips through, at block-execution time), the GRANDPA ancestry walk loops forever, hanging that thread/task indefinitely (equivalent to the pdfio "100% utilization, never terminates" DoS). Because `validate_unsigned` executes outside block weight metering, this can stall transaction-pool validation across the network for the GRANDPA-consensus route, effectively bricking message delivery for that route until the node is restarted or the code is patched — i.e., "a route unable to deliver messages," which matches the accepted impact categories.

### Likelihood Explanation
Likelihood is high: the attack requires no signatures, no valid authority set membership, no funds, and no privileged origin — only an unsigned extrinsic that any peer can submit. The vulnerable check (`headers.ancestry(from, target.hash())`) executes before `justification.verify()`, so the loop triggers pre-authentication on the very first submission, with the attacker fully in control of every relevant field (`unknown_headers`, `parent_hash` values, `finality_proof.block`).

### Recommendation
Bound `AncestryChain::ancestry` against non-termination:
- Track visited hashes in a `BTreeSet`/`HashSet` during the walk and return an error (e.g. `Error::NotDescendent` or a new `CyclicAncestry` variant) if a hash is revisited.
- Additionally/alternatively bound the loop by `self.ancestry.len() + 1` iterations, since a valid ancestry route can never exceed the number of supplied headers.
- Apply the same fix to any other GRANDPA/BEEFY ancestry-walking code paths that consume attacker-supplied header sets before signature verification.

### Proof of Concept
1. Construct two headers `A`, `B` (implementing `HeaderT`) such that `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)`, with `A.number` and `B.number` chosen so `B` is `max_by_key(number)` (the "target") and `A` is `min_by_key(number)` (the "base"), and neither equals the node's trusted `consensus_state.latest_hash`.
2. Build a `FinalityProof { block: hash(B), unknown_headers: vec![A, B], justification: <any bytes that decode, or omit call before this point> }` and wrap it in `ConsensusMessage`/`Message::Consensus` with `consensus_state_id` pointing at a registered GRANDPA client.
3. Submit via `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(msg)] }` as an unsigned extrinsic.
4. `validate_unsigned` → `Self::execute` → GRANDPA `verify_consensus` → `verify_grandpa_finality_proof` reaches `headers.ancestry(from, target.hash())` at modules/consensus/grandpa/verifier/src/lib.rs:88 before `justification.verify()` runs, and loops forever inside `AncestryChain::ancestry` (`while current_hash != base` alternating between `hash(A)` and `hash(B)`), hanging the calling thread.

Note: I could not fully trace every intermediate dispatch hop from `pallet_ismp::Message::Consensus` through `modules/ismp/core/src/handlers/consensus.rs` to `ismp-grandpa`'s `verify_consensus` within the available iterations (only file listings were retrieved, not their contents), so the exact routing glue code was not directly inspected — this should be verified in a live session, though the vulnerable primitive (`AncestryChain::ancestry`) and its two call sites shown above are directly confirmed in the codebase.
