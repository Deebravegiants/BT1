### Title
Attacker-controlled swap routes can inject unauthorized wallet-token transfers into a victim’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Route-bearing controller operations authenticate the account owner once, then execute attacker-supplied route bytes through the configured router. Because a route can name an arbitrary pool/venue contract, code below the signed controller invocation can request authorization for an unrelated wallet-token transfer. Transaction simulation records that transfer as a child of the victim’s authorization entry; if the victim signs the poisoned tree, the malicious venue can steal wallet funds unrelated to the lending operation.

### Finding Description
`swap_collateral` accepts opaque `swap: Bytes` supplied by the caller and passes it into `process_swap_collateral` together with the selected collateral and amount. [1](#0-0)  The strategy first calls `require_authorized_caller`, which performs `caller.require_auth()`, and then verifies owner/delegate authority. [2](#0-1)  The withdrawn collateral is routed through `swap_tokens`, which invokes `router.execute_strategy(controller, amount_in, swap)` with the caller-provided bytes still opaque to the controller. [3](#0-2) 

The controller’s router authorization is narrow: it authorizes only `token_in.transfer(controller, router, amount_in)` and creates no sub-invocation authorization. [4](#0-3)  The problem is the opposite direction of trust: an attacker-selected venue called below the router can itself call `token.transfer(victim, attacker, amount)`. That child call is matched against the victim’s already-signed invocation tree rather than against the controller’s narrow router grant.

The repository’s harness demonstrates the exact behavior. Simulation records `token.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice’s `swap_collateral` authorization, and the injected transfer succeeds when that recorded tree is signed. [5](#0-4) 

### Impact Explanation
This enables theft of user funds. A malicious route provider can present an economically valid swap that also causes a selected venue to request a transfer of any token held by the victim. Simulation includes the malicious token call in the authorization tree, and a wallet or UI that does not independently decode and compare every child authorization can have the victim sign it. The resulting loss is not limited to the collateral being swapped: the malicious venue can request unrelated wallet-token balances. Final account-risk checks and measured swap settlement do not bound this side transfer.

### Likelihood Explanation
Exploitation requires victim interaction—specifically, getting the victim to submit a poisoned route and sign the expanded authorization tree. This is comparable to the external report’s reflected-injection precondition. No protocol privilege, leaked key, upgrade, governance action, or compromised router configuration is required. The same route execution primitive is reachable through `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, all of which accept caller-controlled route bytes. [6](#0-5) 

### Recommendation
Do not allow arbitrary venue addresses in production routes. Restrict executable pool addresses to a governed venue/pool registry and bind each route hop to the expected venue adapter before invocation. In addition, expose or canonicalize the expected authorization tree so wallets can reject any child invocation other than the required swap-input pull. At minimum, clients should simulate the transaction and reject any authorization subtree that contains token transfers or contract calls unrelated to the requested strategy.

### Proof of Concept
1. Victim holds `VICTIM_TOKEN` unrelated to the lending markets and owns a funded lending account.
2. Attacker deploys a pool-shaped contract whose `swap` or `get_reserves` call invokes `VICTIM_TOKEN.transfer(victim, attacker, balance)`.
3. Attacker constructs a route that names that contract as a venue and offers a sufficiently valid token output for the swap to pass settlement.
4. Victim calls `swap_collateral(victim, account_id, current, amount, new, poisoned_route)`.
5. `require_authorized_caller` creates the victim authorization root, and the router executes the poisoned route below it.
6. Simulation records the unrelated `VICTIM_TOKEN.transfer(victim, attacker, balance)` as a child of the victim’s authorization.
7. If the victim signs that tree, the malicious pool transfers the wallet token to the attacker while the swap itself can still return positive output and pass final risk checks.

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {

    s.t.env.mock_all_auths();

        function: AuthorizedFunction::Contract((

        sub_invocations: std::vec![],

    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
```
