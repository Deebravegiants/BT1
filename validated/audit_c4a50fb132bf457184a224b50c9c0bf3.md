This confirms the finding: the gem's documented API (`docs/usage/webhooks.md#L125`) explicitly tells developers that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" and hands the `shop` field to the handler as a trusted webhook attribute, based purely on `ShopifyAPI::Webhooks::Request#shop`, which reads the unsigned `x-shopify-shop-domain`/`shopify-shop-domain` header.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, while `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (and `request.topic`) taken straight from HTTP headers to build the `WebhookMetadata` passed to the app's handler. The HMAC that `Utils::HmacValidator` verifies never binds the `shop-domain` header to the signed bytes, so the equality the library implicitly assumes — "shop that produced a valid HMAC" == "shop attributed to the webhook" — does not actually hold.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) [2](#0-1) 

`to_signable_string` is only `@raw_body`; the `shop` accessor pulls straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header without any cryptographic tie to the signature. `HmacValidator.validate` then only proves that the *body bytes* were produced with the app's secret — it says nothing about which header values (topic, shop-domain, webhook-id, api-version) accompanied that body: [3](#0-2) 

`Registry.process` then validates the HMAC and immediately forwards the header-derived `shop` (and `topic`) to the app's handler as authoritative metadata: [4](#0-3) 

The documented usage pattern instructs app authors that `Registry.process` "will verify the request did indeed come from Shopify" and that handlers can rely on `data.shop`/`data.topic`: [5](#0-4) [6](#0-5) 

Because only the body is signed, an attacker who controls (or has previously captured) any single legitimate `(raw_body, hmac)` pair signed by the app's shared `client_secret` — for example a webhook delivered by Shopify for their **own** store, which the app is publicly installed on — can replay that exact body and valid HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a **different, victim** shop that also has the app installed. `HmacValidator.validate` still passes (the body is unchanged and correctly signed), yet `Registry.process` hands the handler `shop: <victim-shop>` together with the attacker's own body content. This breaks the binding the library promises: "shop verified by HMAC" ≠ "shop reported to the handler," letting an unprivileged, unauthenticated attacker inject data attributed to a tenant they do not control.

### Impact Explanation
This is a genuine cross-tenant boundary break carried entirely by this gem's own logic (no reliance on any host-app-specific behavior beyond following the documented `data.shop`/`data.topic` contract). An attacker can make the multi-tenant app process attacker-chosen webhook bodies (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) as if they belonged to an arbitrary victim shop that also installed the app, since `shop` is never bound to the signed content. Depending on how the host handler keys off `data.shop` (which is exactly what the gem's own documentation instructs it to do), this can lead to cross-tenant data injection/corruption or spoofed lifecycle events (e.g. faking `app/uninstalled` for a victim shop) — a cross-tenant access violation.

### Likelihood Explanation
Exploitation requires the attacker to obtain one valid `(raw_body, hmac)` pair signed with the app's `client_secret`. This is trivial for any attacker who installs the app themselves (a normal, unprivileged onboarding flow for any public/multi-tenant Shopify app) — Shopify will sign and deliver real webhooks to their shop, giving them a body+HMAC pair they fully control the content of, which they can then replay with a forged `shop-domain` header at the app's public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`) header values in the HMAC-covered signable string (or independently verify `shop`/`topic` against a value derived from the signed body/session), so the HMAC binds the identity attributes reported to the handler, not just the JSON payload bytes. At minimum, document that host apps must not trust `data.shop`/`data.topic` for tenant scoping without independent verification.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store `attacker.myshopify.com`
#    and receives a genuine webhook from Shopify, e.g. for "orders/create":
raw_body = '{"id":1,"note":"hello"}'
valid_hmac_b64 = "<HMAC Shopify computed over raw_body with the app's real client_secret>"

# 2. Attacker replays the exact same body+hmac to the app's public webhook
#    endpoint, but swaps the shop-domain header to a victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # still valid: raw_body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body/HMAC match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked with attacker-controlled body content attributed to the victim shop.
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
