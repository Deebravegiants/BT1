### Title
Unbounded loop in GRANDPA `AncestryChain::ancestry` allows a crafted finality proof to hang transaction-pool validation and block execution - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`AncestryChain::ancestry` walks from a `block` hash back to a `base` hash by repeatedly looking up `parent_hash` in a map built entirely from attacker-supplied header structs (`FinalityProof::unknown_headers` and `GrandpaJustification::votes_ancestries`). Nothing in the decode or verification path checks that this parent chain is acyclic or terminates. An attacker can submit two (or more) headers whose `parent_hash` fields point at each other, forming a cycle that is fully contained within the attacker-controlled header set. When `ancestry()` is invoked on such a set, the `while current_hash != base` loop toggles between the cyclic hashes forever, since every lookup in `self.ancestry` succeeds and `base` is never reached.

### Finding Description
`AncestryChain<H>::new` builds a `BTreeMap<H::Hash, H>` from `ancestry: &[H]`, indexing every header by `header.hash()` [1](#0-0) . The header's `parent_hash` field is arbitrary, attacker-controlled data — it is not required to correspond to any header's *actual* recomputed hash relationship beyond what the attacker chooses to encode. `ancestry()` then walks: [2](#0-1) 

Since `self.ancestry.get(&current_hash)` will keep succeeding for every hash in the attacker-crafted cycle, and `current_hash` never becomes `base`, the `while` loop never terminates (and `route` grows without bound each iteration).

This function is reached from two places inside `verify_grandpa_finality_proof` and `GrandpaJustification::verify_with_voter_set`:
- `headers.ancestry(from, target.hash())` in `verify_grandpa_finality_proof`, where `headers` is built from `finality_proof.unknown_headers` [3](#0-2) .
- `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)` in `GrandpaJustification::verify_with_voter_set`, where `ancestry_chain` is built from `votes_ancestries`, also fully attacker-supplied [4](#0-3) .

Both `unknown_headers` and `votes_ancestries` come straight from `FinalityProof`/`GrandpaJustification`, which are SCALE-decoded from the `consensus_proof` bytes of a `ConsensusMessage` submitted in a `handle_unsigned` extrinsic [5](#0-4) . `handle_unsigned` is a permissionless, unsigned, fee-less extrinsic anyone can submit, and is also invoked directly by `ValidateUnsigned::validate_unsigned` in the mempool validation path before block inclusion [6](#0-5)  and dispatched via `Self::execute(messages)` [7](#0-6) . This means the infinite loop can be triggered both during transaction-pool validation (hanging the collator/full node's mempool worker) and during block execution (halting the runtime, since Substrate blocks are wasm-executed single-threaded with no built-in loop-iteration timeout other than the block's weight/gas metering — and this loop performs no weight-charged, gas-metered operation per iteration, only cheap `BTreeMap` lookups).

This mirrors the reported bug class: a piece of attacker-supplied input drives a loop whose exit condition can never be satisfied, causing the process to hang indefinitely (CWE-835), analogous to the jpeg-js infinite-loop DoS.

### Impact Explanation
A single crafted GRANDPA consensus proof can hang block execution/validation indefinitely on any parachain/relayer node running the GRANDPA consensus client, denying service to the network (collators stall producing/importing blocks, full nodes stall on mempool validation). This is a High-severity liveness/DoS impact reachable by any unprivileged party who can submit an unsigned extrinsic — no signature, fee, or special permission is required.

### Likelihood Explanation
High. Constructing two synthetic `SubstrateHeader`-shaped structs with reciprocal `parent_hash` values requires no cryptographic break — headers only need to decode successfully and hash to the values referenced by each other's `parent_hash` field, which is entirely achievable since header hashing is over attacker-chosen header content. No signature check gates entry into `AncestryChain::ancestry`; the cycle is exercised purely by the map-lookup walk before any GRANDPA signature verification of precommits is meaningfully bounded by it.

### Recommendation
Bound the `ancestry()` walk with a maximum iteration count (e.g. the number of distinct headers supplied, since a valid, acyclic ancestry can visit each header at most once) and/or track visited hashes in a `BTreeSet`, returning `Error::NotDescendent` (or a new cycle-specific error) once a hash is revisited or the iteration count exceeds `ancestry.len()`.

### Proof of Concept
1. Construct two `SubstrateHeader` values `A` and `B` (arbitrary bodies) such that `A.parent_hash = B.hash()` and `B.parent_hash = A.hash()` (trivial: pick any header content for `B`, compute `B.hash()`, set it as `A.parent_hash`; then compute `A.hash()` and set it as `B.parent_hash` — since header hash does not include `parent_hash`... verify this against the specific header hashing scheme, but standard Substrate header hash is over the whole SCALE-encoded header, so the two hashes must be solved for jointly, e.g., via brute-force grinding one field while leaving `parent_hash` fixed until the hash matches, or by using two headers whose mutual dependency is broken with an intermediate common value — a chain of headers `A → B → C → A` also works and is easier to construct incrementally).
2. Include `A` and `B` in `FinalityProof::unknown_headers` (or in `GrandpaJustification::votes_ancestries` alongside a matching precommit `target_hash`) so that `target.hash()` (or a precommit's `target_hash`) resolves into the cycle without ever reaching `base`/`consensus_state.latest_hash`.
3. Wrap this in a `ConsensusMessage::StandaloneChain`/`Polkadot`/`Relaychain` variant, encode as the `consensus_proof` of a `Message::Consensus`, and submit via `handle_unsigned`.
4. `AncestryChain::ancestry` in `verify_grandpa_finality_proof` (or inside `GrandpaJustification::verify_with_voter_set`) loops forever walking `A → B → A → B → …`, hanging the validating/executing node.
