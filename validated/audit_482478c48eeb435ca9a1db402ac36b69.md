### Title
Webhook `shop` and `topic` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers that are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then dispatches to the app's handler using the unverified `shop` and `topic` header values, breaking the binding "shop authenticated == shop acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no cryptographic linkage to the HMAC: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which — per `Request#to_signable_string` — only checks that the *body* matches the HMAC signed with the app's `api_secret_key`. It then immediately trusts `request.shop` and `request.topic` to route and construct `WebhookMetadata` for the handler: [3](#0-2) 

Because the same `api_secret_key` is shared across every shop that installs the app, any merchant/attacker who installs the app on their own (even free/dev) store can capture a legitimately-signed webhook body+HMAC pair delivered to the app for their own store. Since `shop`/`topic`/`webhook_id` are not part of the signed content, the attacker can replay that same body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` will still succeed (the body/HMAC pair is valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

This breaks the required identity binding: **shop verified by HMAC ≠ shop delivered to the handler**. Any app logic in the handler that trusts `data.shop` (updating shop-scoped state, revoking access, marking uninstall via `shop/redact`, etc.) can now be triggered for a different tenant than the one that actually authenticated the request.

### Impact Explanation
This is a cross-tenant boundary violation: an authenticated event for shop A can be delivered to the app's webhook handler labeled as shop B, letting a low-privilege attacker (any merchant who installs the app) inject spoofed events attributed to a victim tenant. Depending on handler logic, this could lead to unauthorized state changes for a merchant that never sent the event — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to install the app on a shop they control (a standard, unprivileged action) and to capture one real webhook delivery, which is straightforward since webhooks are delivered over plain HTTP POST to the app's public endpoint and the attacker fully controls the receiving side for their own shop.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed payload used for HMAC verification (or independently verify that `X-Shopify-Shop-Domain` corresponds to a shop with a valid, existing session/installation before trusting it), rather than relying on Shopify's raw-body-only HMAC scheme as an implicit tenant-binding mechanism. At minimum, `Registry.process` should cross-check `request.shop` against a known/installed shop record before invoking handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control).
2. Shopify sends a legitimate webhook (e.g., `orders/create`) to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid hmac over raw body>`.
3. Attacker captures this raw body and its valid HMAC (computed with the app's shared `api_secret_key`).
4. Attacker replays the exact same body + HMAC to the app's webhook endpoint, but changes the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks the body against the HMAC.
6. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though that shop never sent or authorized this event.
