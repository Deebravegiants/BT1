### Title
`PoaBridge.describeWithdrawal` misattributes withdrawal status/txHash when a batch contains two withdrawals of the same PoA token - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.findMatchingWithdrawal` matches a withdrawal record from the PoA bridge's `withdrawal_status` response purely by `nep141:<near_token_id> === assetId`, with no use of `index`, destination address, or amount to disambiguate. When an intent contains two withdrawals of the same token (e.g. `nep141:dash.omft.near`) to different destinations, `Array.prototype.find` deterministically returns the first matching entry for *both* `WithdrawalIdentifier`s, so the second withdrawal's `describeWithdrawal` call reports the first withdrawal's status and `transfer_tx_hash`.

### Finding Description
The broken equality: the SDK's caller-visible invariant is "`WithdrawalIdentifier[i].status/txHash` corresponds to the withdrawal whose destination/amount matches `withdrawalParams[i]`." The code instead computes `withdrawal = withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` [1](#0-0) , which only checks the token id, not `index`, destination address, or amount.

Path: `IntentsSDK.waitForWithdrawalCompletion` → `createWithdrawalCompletionPromises` → `createWithdrawalIdentifiers` builds one `WithdrawalIdentifier` per withdrawal param, all sharing the *same* `intentTx` (`tx.hash`) but with a per-bridge-route `index` [2](#0-1) . For both same-token withdrawals in one intent, `bridge.route` is identical (`RouteEnum.PoaBridge`), so `index` becomes `0` and `1` respectively, but `tx.hash` is identical for both, since it's the single NEAR intent transaction [3](#0-2) .

`watchWithdrawal` calls `bridge.describeWithdrawal({...wid, logger})` independently per identifier [4](#0-3) . `PoaBridge.describeWithdrawal` calls `getWithdrawalStatusWithRetry` with `{ withdrawal_hash: args.tx.hash }` [5](#0-4)  — since `tx.hash` is the same for both identifiers, both calls hit the same API endpoint and receive the *same* `response.withdrawals` array (unsorted, containing both withdrawal records for that tx) [6](#0-5) . `findMatchingWithdrawal` then returns the *first* array entry whose token matches — identical for index 0 and index 1 — so `describeWithdrawal` reports the same `status`/`txHash` for both `WithdrawalIdentifier`s regardless of `index`, destination, or amount [7](#0-6) .

The code comment explicitly documents this as a known, unresolved limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported. POA API doesn't currently support this case either" [8](#0-7) . Despite this, nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers()` rejects or warns about batches with repeated `assetId` for the PoA route — `supports()` only checks route/asset compatibility [9](#0-8) , and `createWithdrawalIdentifiers` happily assigns increasing indexes with no duplicate-assetId guard [10](#0-9) .

### Impact Explanation
An integrator polling `waitForWithdrawalCompletion` for a batch of two `nep141:dash.omft.near` withdrawals to different destinations will, for the second identifier, receive the *first* withdrawal's `status`/`transfer_tx_hash` once the first completes — even if the second withdrawal is still pending, failed, or completed to a different destination with a different `transfer_tx_hash`. This is a status/hash misreport that can lead an integrator to believe a payout to destination B succeeded (and credit/release funds accordingly) while the actual transfer to B may still be pending or has a different hash, or vice versa — matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. The misreport is deterministic and repeatable any time a same-token batch with ≥2 PoA withdrawals is polled.

### Likelihood Explanation
Preconditions: an ordinary unprivileged user (or integrator forwarding user-controlled withdrawal params) submits a batch withdrawal intent with two or more withdrawals of the same PoA-bridged NEP-141 asset (e.g. `nep141:dash.omft.near`) to different destination addresses, then calls `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`. No special privileges, contract admin, or malicious infrastructure are required — this is achievable purely via legitimate SDK usage with attacker-controlled `withdrawalParams` composition. Nothing in the current code path rejects such batches, so the flaw is trivially and repeatably reachable.

### Recommendation
In `findMatchingWithdrawal`, disambiguate same-token withdrawals within a batch — e.g., match by `(near_token_id, destination address, amount)` tuple where the PoA API exposes that data, or reject/throw when multiple `withdrawals` entries match the same `assetId` for a given `tx.hash` and the SDK cannot uniquely resolve them (rather than silently returning the first match). Alternatively, proactively reject batches containing duplicate PoA `assetId`s in `createWithdrawalIdentifiers`/`supports()` until the POA bridge API supports disambiguation, per the code's own comment about the intended future fix (sorting API results and withdrawal params by amount).

### Proof of Concept
Vitest plan (mock only the HTTP client `poaBridge.httpClient.getWithdrawalStatus`):
1. Build two `WithdrawalIdentifier`s for `nep141:dash.omft.near`, same `tx.hash`, `index: 0` and `index: 1`, with different `destinationAddress` (A and B) and `amount` in `withdrawalParams`.
2. Mock `getWithdrawalStatus` to return `withdrawals: [{status: "COMPLETED", data: {near_token_id: "dash.omft.near", transfer_tx_hash: "0xA"}}, {status: "PENDING", data: {near_token_id: "dash.omft.near"}}]` (order simulating destination-A record first).
3. Call `poaBridge.describeWithdrawal(widIndex0)` and `poaBridge.describeWithdrawal(widIndex1)`.
4. Assert the broken equality: both calls return `{status: "completed", txHash: "0xA"}` — i.e. `describeWithdrawal(widIndex1)` incorrectly equals `describeWithdrawal(widIndex0)`, even though `widIndex1.withdrawalParams.destinationAddress !== widIndex0.withdrawalParams.destinationAddress`. A correct implementation should return distinct results (`"pending"` for index 1) or throw an explicit "unsupported duplicate assetId in batch" error instead.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
