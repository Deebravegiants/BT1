## Title
Webhook shop-domain identity spoofing via HMAC that only signs the raw body, not the `shop` header - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant) identity used downstream by `ShopifyAPI::Webhooks::Registry.process` is read from an unsigned HTTP header. An attacker who can obtain one genuinely HMAC-signed webhook delivery (e.g., from a shop they legitimately install the app on) can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header for an arbitrary victim shop, and the gem will accept it as authentic and hand it to the host app's handler as if it originated from the victim shop.

### Finding Description
`Request#to_signable_string` — the value that is HMAC-verified — is defined as just the raw body: [1](#0-0) 

`Request#shop` is read straight from a header and is not part of that signed string at all: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over the body only) and then, independently, uses `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` performs a `secure_compare` of the computed signature against the received one, using `verifiable_query.to_signable_string` — for webhooks this is exactly `@raw_body`, so the `shop` header never enters the computation: [4](#0-3) 

The broken identity binding, expressed as an equality that the gem fails to enforce:
`hmac_valid(raw_body)` == `true` does **not** imply `shop_header == shop_that_actually_produced(raw_body)`.

Concretely: an attacker who operates their own shop (call it `attacker.myshopify.com`) with the app installed will receive genuine webhook deliveries signed with the app's `client_secret` over the raw body. Because the signature never covers the `shop` header, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to `victim.myshopify.com`. `Utils::HmacValidator.validate` still succeeds (it only checks the body against the HMAC), so `Registry.process` calls the handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...)` — attacker-controlled data attributed to a shop the attacker does not control.

Downstream host applications commonly key session/tenant lookups and data mutations directly off the `shop` value provided in `WebhookMetadata` (this is the documented purpose of the field), so this allows cross-tenant webhook forgery/injection without ever needing the victim's access token or `client_secret`.

### Impact Explanation
This crosses a tenant boundary using only knowledge the attacker already legitimately possesses (their own shop's valid webhook deliveries), and lets them make the app believe the payload originated from an arbitrary other shop. Depending on the handler's use of `shop` (e.g., GDPR/compliance webhooks, order/customer data ingestion, uninstall/app-lifecycle webhooks), this can result in cross-tenant data corruption or unauthorized actions being taken against a different merchant's account — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged user of the app on their own shop to harvest a valid `(raw_body, hmac)` pair, then forge the shop header on a replayed request. No access token, `client_secret`, or privileged access is required, making this practically exploitable by any app user.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed material, or otherwise cryptographically bind `shop` to the HMAC before it is used for tenant-routing — e.g., validate the header-derived `shop` against a shop value embedded in the signed payload, or require verification against a per-shop secret/session rather than the app-wide `client_secret` alone.

### Proof of Concept
1. Attacker's shop `attacker.myshopify.com` has the app installed; a legitimate webhook fires with body `B` and header `x-shopify-hmac-sha256: H` computed as `HMAC-SHA256(client_secret, B)`.
2. Attacker resends a request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` at `lib/shopify_api/utils/hmac_validator.rb:13-21` recomputes the HMAC over `to_signable_string` (= `B`) and it matches `H`, so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds to call the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, even though `victim.myshopify.com` never sent this data.
