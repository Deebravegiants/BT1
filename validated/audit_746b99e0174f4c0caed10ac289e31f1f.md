### Title
Direct LT donations to a bonding-curve `Pair` are permanently unrecoverable after graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
The external report's core bug class is "user spends real funds on a destination the protocol never intends to make whole/usable, and those funds are simply lost." The direct analog in alt.fun is a leveraged-token (LT) holder transferring LT directly to a bonding-curve `Pair` contract instead of routing through `Zap`/`Bonding`. That LT increases the pair's real balance but never updates the pair's accounted `assetReserve`, so it is excluded from every downstream calculation and, once the token graduates, becomes permanently stranded with no code path left to retrieve it.

### Finding Description
`Pair` tracks a separate accounted `_pool.assetReserve` that is mutated only by `Pair.swap` and `Pair.mint`, never by raw ERC-20 transfers into the contract [1](#0-0) . A direct `IERC20(lt).transfer(pairAddr, amount)` from any wallet therefore raises `assetBalance()` but leaves `getReserves()`'s `assetReserve` untouched.

At graduation, `_prepareGraduationLiquidity` computes the LT to drain strictly from the stored reserve minus the recovered launch-time virtual reserve: [2](#0-1) 

`ltFromPair = assetReserve - virtualLtReserve` is exactly the amount passed to `Router.graduate`, which is the only code path that can trigger `Pair.transferAsset` (gated `onlyRouter` on `Pair`, and `BONDING_ROLE` on `Router`) [3](#0-2) . Any LT balance above `assetReserve` (i.e., donated LT) is left behind by construction. Token-side donations are explicitly caught and burned via `unsoldBurned = IPair(pairAddr).tokenBalance()` [4](#0-3) , but there is no equivalent sweep on the asset (LT) side.

Once `finalizeGraduation` flips the token's lifecycle to `Graduated` and deletes `pendingGraduation`, no code path ever calls `Router.graduate` again for that token — this is documented as an explicit trust assumption ("Donated LT remains in the curve pair... under the trust assumption that BONDING_ROLE is only ever held by Bonding") [5](#0-4) . The graduated trading venue is a *different* HyperSwap pair, entirely disjoint from the abandoned bonding-curve `Pair`, so the donated LT sits in a contract that is no longer part of any live trading flow, with no owner-sweep or recovery function exposed on `Pair` or `Bonding` for this LT.

### Impact Explanation
Any unprivileged wallet that sends LT directly to a bonding-curve `Pair` (e.g., mistaking it for adding liquidity, or trying to "boost" a token pre-graduation the way one might naively assume donations help liquidity) permanently loses those funds once the token graduates — the LT can never be moved out again by any transaction the protocol exposes. This is a permanent freeze of user funds, matching the Sherlock report's "wasted funds for nothing" impact class, except here the loss is total and irreversible rather than merely inefficient.

### Likelihood Explanation
The action requires only a standard ERC20 `transfer` call from any wallet to a publicly known `Pair` address (returned by `Bonding.launch`/`Factory.getPair`) — no special permissions, timing, or protocol interaction beyond holding the LT. Given LT donation to a bonding curve is a plausible user mistake (mirroring liquidity-donation patterns common on other bonding-curve/AMM platforms), and the protocol's own documentation acknowledges donations are excluded from `ltFromPair` by design without offering any recovery mechanism, the likelihood of accidental (or even deliberate griefing/burn) loss is non-trivial over the system's lifetime.

### Recommendation
Add an owner- or Bonding-gated sweep for LT held by a `Pair` in excess of its accounted `assetReserve`, callable pre- or post-graduation (mirroring `_sweepLTToOwner`'s pattern already used in `finalizeGraduation` for `protectedLT`), so donated LT can be returned to depositors or swept to a recoverable destination instead of being permanently stranded.

### Proof of Concept
1. Launch a token via `Bonding.launch` and let it trade normally on the curve.
2. From any unprivileged wallet holding LT, call `IERC20(lt).transfer(pairAddr, X)` directly to the bonding-curve `Pair` address (no interaction with `Zap`/`Bonding` needed).
3. Continue trading until the token graduates (`_enterGraduating` → `finalizeGraduation`). Observe that `_prepareGraduationLiquidity`'s `ltFromPair` computation is based only on `getReserves().assetReserve` [6](#0-5) , which never included the donated `X`.
4. After `finalizeGraduation` completes, `Pair`'s `assetBalance()` still holds `X` LT, `Pair.transferAsset` is `onlyRouter`-gated [3](#0-2) , and no code path calls `Router.graduate` (or any other function reaching `transferAsset`) for this token again — `X` LT is permanently stuck in the now-inert `Pair` contract.

```text
    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
```

```markdown
- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
```
