### Title
Governance token-contract re-pointing on `pallet-hyper-fungible-token` permanently strands escrowed/burned user funds when in-flight transfers later time out - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `update_token` extrinsic lets `CreateOrigin` add or remove per-chain EVM contract mappings for a registered asset. Both the add-path (re-pointing a chain to a new contract) and the remove-path delete the reverse-lookup entry `ContractToAsset` for the *old* contract address. `on_timeout`, which refunds users whose `send()` transfer never got delivered, looks the asset up solely via that same `ContractToAsset` map keyed by the destination chain and the original `to` contract address. If the mapping is updated/removed while a `send()` is still in flight, the timeout handler can no longer resolve the asset, the refund reverts, and the user's escrowed (native) or already-burned (non-native) funds can never be recovered — the exact "removed accepted-asset breaks the recovery code path used elsewhere" bug class described in the external report, just applied to Hyperbridge's `HyperFungibleToken` bridge instead of `TokenManager`.

### Finding Description
`send()` resolves the destination contract address purely from current storage at dispatch time: [1](#0-0) 
and burns/escrows the user's funds before dispatching the cross-chain post request: [2](#0-1) 

`update_token`, callable at any time by `CreateOrigin` for entirely benign reasons (e.g. migrating to a new/upgraded token contract on a chain, or deprecating a chain), deletes the *old* `ContractToAsset` reverse mapping both when re-pointing a chain (`add_chains`) and when dropping it (`remove_chains`): [3](#0-2) [4](#0-3) 

The only recovery path for an undelivered `send()` — `on_timeout` — re-derives the local asset exclusively from that reverse mapping, keyed by the exact `(dest, to)` pair that was current when the message was dispatched: [5](#0-4) 
If `update_token` has since re-pointed or removed that `(dest, to)` pair, `ContractToAsset::<T>::get(dest, &to)` returns `None` and `on_timeout` errors out with `UnknownContractOnTimeout` before any refund/re-mint logic runs: [6](#0-5) 

There is no other function in the pallet that can refund a stuck transfer once its `on_timeout` fails — the escrowed native balance sits permanently in the pallet account (or, for non-native assets, the tokens were already burned entirely and have no on-chain record to recover from). This mirrors the `TokenManager`/`SmartVaultV3.liquidate` bug precisely: a routine registry-mutation action leaves stale references that a completely unprivileged, otherwise-correct user flow (here: any account calling `send`, followed by anyone submitting the ISMP timeout for it) can no longer reconcile, resulting in unrecoverable/frozen user funds.

### Impact Explanation
Any user's `send()` transfer that is in flight at the moment governance calls `update_token` (whether to rotate a compromised/upgraded contract address or to sunset support for a chain) permanently loses the escrowed or burned funds if that transfer later times out, since `on_timeout` can no longer resolve the asset and reverts. This is not a hypothetical edge case: contract migrations and chain deprecations are expected, routine governance operations for a long-lived bridge, and the pallet provides no way to reconcile a stuck request against a stale `(dest, to)` pair after the fact. This is a direct, permanent freezing of user funds with no remediation path, satisfying the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
No malicious behavior by governance is required — a single ordinary `update_token` call (re-pointing a chain to a new contract, which the pallet explicitly supports and which its own benchmarks/tests exercise) executed while any user's transfer to that chain is still awaiting delivery is sufficient. Given realistic finalization/relayer timeout windows across chains, and that governance has no visibility into which individual `send()` calls are currently in flight, this can occur during normal operational maintenance without any adversarial intent.

### Recommendation
Do not derive `on_timeout`'s asset resolution from the mutable `ContractToAsset` map. Instead, either (a) embed the local `AssetId` directly in the dispatched `Message`/request body so timeout processing is self-contained and independent of current registry state, or (b) snapshot the `(dest, to) → asset_id` mapping per outstanding request at `send()` time and consult that snapshot (rather than the live, governance-mutable map) in `on_timeout`. Additionally, `update_token` should require that a chain has no outstanding in-flight requests (or provide a dedicated, permissionless recovery function keyed by the original commitment) before allowing its contract mapping to be repointed or removed.

### Proof of Concept
1. Governance registers asset `X` with `chains = { Evm(1) → contractA }` via `register_token`.
2. User calls `send({asset_id: X, destination: Evm(1), amount, timeout: T, ...})`; funds are escrowed/burned per: [2](#0-1) 
   and the request is dispatched to `contractA` on `Evm(1)`.
3. Before the message is delivered or the timeout elapses, governance calls `update_token` to re-point `Evm(1)` to `contractB` (a routine contract upgrade): [7](#0-6) 
   This deletes `ContractToAsset::<T>::get(Evm(1), contractA)`.
4. The original message to `contractA` is never delivered (e.g. relayer failure, or `contractA` no longer functioning) and times out; someone submits the ISMP timeout, invoking `on_timeout` with `to = contractA`, `dest = Evm(1)`: [5](#0-4) 
5. `ContractToAsset::<T>::get(Evm(1), contractA)` now returns `None`, `on_timeout` errors with `UnknownContractOnTimeout`, and the user's escrowed/burned funds are permanently unrecoverable — this pallet has no other function to reconcile the stuck request.

	fn on_timeout(&self, request: Request) -> Result<Weight, anyhow::Error> {
		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?
				}
				let beneficiary: T::AccountId = sender_bytes.into();

				// Look up the asset from the destination contract address
				let local_asset_id = ContractToAsset::<T>::get(dest, &to)
