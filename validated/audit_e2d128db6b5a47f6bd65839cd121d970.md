### Title
Predictable, unauthenticated `shopify_app_session` cookie value is trusted verbatim as the session lookup key - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`SessionUtils.cookie_session_id` returns `cookies['shopify_app_session']` with no cryptographic verification, and the value that this gem places in that cookie (`session.id`) is not a random, secret-derived token but a deterministic string built only from the public shop domain (`"offline_#{shop}"`) or shop+user id (`"#{shop}_#{associated_user.id}"`). Because the "session id" carries zero entropy tied to `Context.api_secret_key`, an attacker who simply knows a victim's public `myshopify.com` domain can construct the exact cookie value the victim's session would have, and any app that uses `current_session_id`'s return value as a raw storage key for session retrieval will hand back that shop's session data to the attacker's own request.

### Finding Description
The claimed binding is: `session_id == MAC(Context.api_secret_key, authenticated_bytes)`. In reality:

- `session.id` is computed in `Session.from` as `id = "offline_#{shop}"` for offline tokens or `id = "#{shop}_#{associated_user.id}"` for online tokens [1](#0-0) . Neither branch uses `Context.api_secret_key`, any HMAC, or any signature — it's a plain string concatenation of publicly known values (the shop domain, and for online sessions, the associated user id, itself readable from a JWT).
- This id is placed directly into the non-embedded OAuth callback cookie: `SessionCookie.new(value: session.id, expires: ...)` [2](#0-1) .
- On every subsequent request, `SessionUtils.cookie_session_id` returns that cookie value **verbatim**, with no MAC check, no signature check, and no shop binding: `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` [3](#0-2) .
- `current_session_id` reaches this cookie fallback in two places: for non-embedded apps unconditionally, and for embedded apps whenever `shopify_id_token` is `nil` or, after `.gsub("Bearer ", "")` normalization elsewhere, effectively empty — the `MissingJwtTokenError` path only fires when a token string was *passed but empty*; when no token argument is supplied at all (`nil`), the code silently falls through to `cookie_session_id` instead [4](#0-3) .

Exploit flow: the attacker installs the app on their own shop to legitimately learn (or simply infers, since it's deterministic) the ID format `offline_#{shop}`. They then send an HTTP request to the target app with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. `cookie_session_id` returns that string unchanged, and any app that follows the documented pattern of using this id as the primary key into its own session store (e.g., `MyApp::SessionRepository.retrieve(session_id)`, mirrored in `shopify_app`'s `ShopSessionStorage#retrieve(id)` reference implementation) will hand back the victim shop's session, including its `access_token`.

None of the existing guards apply here: `HmacValidator.validate` and the `state == auth_query.state` check in `Oauth.validate_auth_callback` only protect the one-time OAuth callback exchange, not the cookie's later reuse; `JwtPayload`'s `aud` check and `HttpRequest#verify` are irrelevant to the cookie code path since no JWT is involved; `Context.setup?`/`private?`/`embedded?` only gate which branch of `current_session_id` runs, they add no authentication to the cookie value itself.

### Impact Explanation
Because the "session id" is fully derivable from a shop's public domain name (no secret material, no signature under `Context.api_secret_key`), any app relying on `SessionUtils.cookie_session_id`/`current_session_id` to key its session storage is exposed to cross-tenant session hijacking: attacker's crafted request is treated as the victim merchant's session, exposing/mutating that merchant's data and access token — matching **Critical: cross-tenant access**. This is repeatable against any shop whose domain is known (shop domains are generally public/discoverable), with no per-victim secret to brute-force.

### Likelihood Explanation
Preconditions: the host app must use the documented pattern of persisting/retrieving sessions keyed by the id returned from this gem's `SessionUtils` (exactly what `getting_started.md` and `oauth.md` instruct, and what the referenced `shopify_app` `ShopSessionStorage#retrieve(id)` does) for a non-embedded flow, or an embedded flow that falls back to the cookie. No secrets, no MITM, and no XSS are required — the attacker only needs to know the victim's shop domain and send one crafted HTTP request with a self-chosen `Cookie` header, which is squarely within the attacker's stated capabilities (full control over headers/cookies of their own requests). This makes the attack low-cost and repeatable against arbitrary shops.

### Recommendation
Do not derive the cookie/session id from public, attacker-predictable values. Generate an unguessable random token (e.g., `SecureRandom.uuid`, which `Session#initialize` already supports via its `id:` default) as the cookie value, and/or bind the cookie to an HMAC computed under `Context.api_secret_key` that `cookie_session_id` verifies before returning the value, rejecting any cookie whose MAC doesn't validate.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (additional case)
class SessionUtilsCookiePredictabilityTest < Test::Unit::TestCase
  def test_offline_session_cookie_value_is_deterministic_from_public_shop_domain
    victim_shop = "victim-shop.myshopify.com"

    # Simulate what Oauth.validate_auth_callback would have produced for the victim,
    # entirely from public information (no api_secret_key involved).
    predicted_id = ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop)

    # Attacker crafts a cookie header with the guessed id and it's accepted verbatim.
    forged_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => predicted_id }

    returned_id = ShopifyAPI::Utils::SessionUtils.cookie_session_id(forged_cookies)

    # VIOLATION: no MAC/signature check occurred; the attacker-forged value
    # is returned as-is and equals the id that would key the victim's real session.
    assert_equal(predicted_id, returned_id)
    assert_equal("offline_#{victim_shop}", returned_id)
  end
end
```
This demonstrates that `cookie_session_id` performs no authentication of the cookie's bytes, and that the value it trusts (`session.id`) is fully computable from public shop-domain data rather than from anything authenticated under `Context.api_secret_key`.
