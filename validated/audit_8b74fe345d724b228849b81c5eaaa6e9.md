### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from only the raw request body, but the `shop` value used downstream to identify which tenant a webhook belongs to comes from the unauthenticated `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. The HMAC never binds the `shop` field to the signed payload, so `shop_in_header == shop_covered_by_hmac` is not enforced.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is read straight from an HTTP header that is never mixed into the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (the body) against the `hmac` field — it has no knowledge of, and does not check, the `shop` header at all: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then hands the handler a `WebhookMetadata` built from `request.shop` — the unauthenticated field — as the tenant identity for the event: [4](#0-3) 

Because a shop can install the app on their own store, they legitimately receive real Shopify webhook deliveries — bodies with a valid HMAC computed by Shopify using the app's real `api_secret_key`. Since the HMAC covers only the body and not the shop header, that attacker can replay the exact same body + HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with an arbitrary victim shop's domain (shop domains are public/discoverable). `HmacValidator.validate` will pass (body+HMAC pair is valid), and the handler will process the payload as if it belonged to the victim shop.

### Impact Explanation
This breaks the tenant identity binding an app relies on when routing webhook data (e.g., `orders/create`, `app/uninstalled`, GDPR webhooks) to per-shop logic/storage. An attacker who is a legitimate (but unprivileged, non-victim) merchant can inject events falsely attributed to another shop into the host application's webhook processing pipeline, causing cross-tenant data corruption/confusion (e.g., writing attacker-controlled order/customer data under the victim shop's records, or triggering victim-shop side effects such as app-uninstalled cleanup). This matches the Critical "cross-tenant access" impact category since it defeats the tenant separation this gem's webhook verification is meant to provide.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own (or any) shop — a normal, unprivileged action — since they can capture a real Shopify-signed webhook body/HMAC pair from their own store's traffic and simply replay it with a forged `shop-domain` header value pointing at a victim's `myshopify.com` domain, which is typically discoverable.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-signed content, or otherwise cryptographically tie the `shop-domain` header to the verified body (e.g., include it in `to_signable_string`, or require host applications to independently corroborate the shop via a value that is itself HMAC-covered, such as the `api-version`/topic checks that Shopify's real webhook payloads already include). At minimum, document that `request.shop` is not authenticated by `HmacValidator.validate` and that callers must not trust it without additional verification (e.g., cross-checking against a known, previously verified session/shop).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header sent by Shopify (a valid `hmac(B, api_secret_key)`).
2. Attacker sends `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...different shop...})` is constructed; `Utils::HmacValidator.validate` calls `to_signable_string` (only `B`) and finds the signature valid.
4. `Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed B, ...)`, causing the app to process attacker-controlled data under the victim's tenant identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
