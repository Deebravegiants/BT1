Audit Report

## Title
`RawMeter::nested` drops the parent's storage-deposit limit when a sub-call omits its own explicit limit, allowing unbounded storage deposit accumulation in nested contract calls - (File: substrate/frame/revive/src/metering/storage.rs)

## Summary
`RawMeter::nested` combines the caller-supplied sub-call limit with the parent's limit only via `if let (Some(new_limit), Some(old_limit))`, which fails to match when the sub-call passes `None` while the parent has `Some(old_limit)`. In that case the child meter is constructed with `limit: None` (unbounded) instead of inheriting the parent's cap, silently discarding an intended storage-deposit ceiling for that nested call frame.

## Finding Description [1](#0-0)  The tuple pattern only reassigns `limit` when both the argument and `self.limit` are `Some`; when the argument is `None` and `self.limit` is `Some(old_limit)`, `limit` remains `None` and the resulting `RawMeter { limit, ..Default::default() }` is unbounded. No other logic in `storage.rs` re-derives or re-applies the parent's cap onto an already-constructed child meter; `limit` is otherwise consumed only by the test-only `available()` and by `RawMeter::new()` for the root meter. This contrasts with the analogous, intentionally-designed logic in the older `frame/contracts` pallet's `RawMeter::nested`, which always takes `self.available().min(limit)` regardless of whether the child requests "no special limit" (represented there as `0`), confirming that a parent cap should always bound descendants. [2](#0-1) 

## Impact Explanation
If a nested frame is created with `limit: None` due to this bug, storage-deposit accounting for that sub-tree loses its intended ceiling, potentially allowing a call chain to accumulate storage deposits beyond what an outer caller or the root extrinsic's `storage_deposit_limit` intended to enforce for that sub-call, up to whatever the origin's balance allows at final settlement.

## Likelihood Explanation
The code defect itself is unconditionally present and trivially reproducible in isolation via a unit test. However, whether this is reachable by an ordinary unprivileged contract call through `seal_call`/`exec.rs` — i.e., whether the ABI can produce a `None` limit for an ordinary sub-call while the outer meter is capped, and whether any other downstream check compensates — could not be confirmed in this session due to tooling errors preventing inspection of `substrate/frame/revive/src/exec.rs`. This end-to-end reachability remains unverified, matching the original report's own stated uncertainty.

## Recommendation
Change the combination logic so a missing sub-call limit inherits the parent's existing limit rather than becoming unbounded:
```rust
pub fn nested(&self, limit: Option<BalanceOf<T>>) -> RawMeter<T, E, Nested> {
    let limit = match (limit, self.limit) {
        (Some(new_limit), Some(old_limit)) => Some(new_limit.min(old_limit)),
        (Some(new_limit), None) => Some(new_limit),
        (None, old_limit) => old_limit,
    };
    RawMeter { limit, ..Default::default() }
}
```
