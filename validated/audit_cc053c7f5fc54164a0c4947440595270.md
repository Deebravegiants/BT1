### Title
Webhook shop identity spoofing via HMAC scope gap — attacker-controlled `shop-domain` header is not bound by the webhook HMAC signature (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to application webhook handlers from an HTTP header, while the HMAC signature that authenticates the webhook is computed only over the raw request body. This breaks the binding `HMAC-authenticated bytes == bytes used to identify the tenant`, letting an attacker who possesses one valid `(raw_body, hmac)` pair replay it with an arbitrary `shop-domain` header and have it accepted as coming from a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read straight from request headers, entirely outside the signed content: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC over `to_signable_string` (i.e., the body only) and then forwards `request.shop` — an unauthenticated field — directly to the application's handler as the tenant identity: [3](#0-2) 

The `HmacValidator` confirms this: it validates `verifiable_query.hmac` against `verifiable_query.to_signable_string` using the app's single shared `api_secret_key`, with no dependency on any header value: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that installs the app, any `(raw_body, hmac)` pair that is valid for one shop's webhook delivery is *also* a cryptographically valid pair for a POST carrying a spoofed `x-shopify-shop-domain` header naming a different (victim) shop. The equality that should hold — `shop bound by HMAC == shop delivered to handler` — does not: the HMAC binds only the body bytes, not the shop header that the handler trusts as the tenant identity in `WebhookMetadata.new(... shop: request.shop ...)`.

### Impact Explanation
This is a cross-tenant identity-binding failure: an attacker who has installed the app on their own shop (an unprivileged action available to anyone) will receive genuine webhook deliveries from Shopify with valid, secret-derived HMACs for their own shop's payload. Since the HMAC covers only the body, the attacker can resend that exact `(body, hmac)` pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` still returns true (the body/hmac match), and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop. Any host application that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (the documented and intended use of this field) can be made to act on the wrong tenant's data — a cross-tenant integrity/confidentiality break attributable to this gem's own validation logic, not to host misuse.

### Likelihood Explanation
Reachable by any unprivileged internet user who can install the app on a shop they control (a normal, unprivileged flow for any public/embedded app) and can send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only a single legitimately-received webhook body/HMAC pair for a topic the app subscribes to.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-covered content, or otherwise cryptographically tie the accepted headers to the verified body — e.g., include the shop domain in `to_signable_string`, or independently verify that `request.shop` matches an expected/allow-listed shop for the session context before dispatching to handlers. At minimum, document that `request.shop` is unauthenticated and must not be used by host applications as a sole tenant selector.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g., `orders/create`) that Shopify signs with the app's shared `api_secret_key`. Attacker captures `raw_body` and the `x-shopify-hmac-sha256` header value.
2. Attacker sends a POST directly to the app's webhook endpoint with the same `raw_body`, the same captured `x-shopify-hmac-sha256`, but `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` unchanged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged `raw_body`) and finds it matches — validation succeeds: [5](#0-4) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload and HMAC were generated for `attacker-shop.myshopify.com`, demonstrating the cross-tenant spoof.
