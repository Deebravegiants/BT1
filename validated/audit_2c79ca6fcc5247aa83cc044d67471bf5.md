### Title
Escrow duplicate-input-token check collapses on a legitimately-zero received amount, letting a duplicate token bypass anti-duplicate protection - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` de-duplicates input tokens by checking `_orders[commitment][token] != 0` before writing the escrow amount for each input leg. This is structurally the same "zero-as-sentinel" flaw as the Saddle `Swap.sol` bug: the mapping's default unset value (`0`) is indistinguishable from a leg that was validly recorded with a received amount of `0`, so a duplicate token entry that lands on `0` first is never flagged as a duplicate.

### Finding Description
In `placeOrder`, duplicate detection for input tokens is: [1](#0-0) 
```
// Phase 3: Credit escrow.
for (uint256 i; i < inputsLen;) {
    address token = address(uint160(uint256(order.inputs[i].token)));
    // Reject duplicate input tokens
    if (_orders[commitment][token] != 0) revert InvalidInput();
    _orders[commitment][token] = reducedInputs[i].amount;
    ...
```
This mirrors the audited Saddle `Swap.sol` pattern where `tokenIndexes[token] != 0` is used both as the "already seen" sentinel and as a valid stored value, so a token that legitimately maps to `0` is never caught as a repeat.

The requested (pre-transfer) amount is validated to be non-zero up front, but the value actually written into `order.inputs[i].amount` (and thus into `_orders`) is the *received* amount computed after the ERC20 transfer completes, not the requested amount: [2](#0-1) 
```
for (uint256 i; i < inputsLen;) {
    if (order.inputs[i].amount == 0) revert InvalidInput();
    address token = address(uint160(uint256(order.inputs[i].token)));
    if (token == address(0)) {
        ...
    } else {
        uint256 balBefore = IERC20(token).balanceOf(address(this));
        IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
    }
    ...
```
This post-transfer `balanceOf` delta is never re-checked for zero in the no-predispatch / zero-protocol-fee path. When `protocolFeeBps == 0`, `reducedInputs = order.inputs` is used verbatim with no zero-amount re-validation: [3](#0-2) 

Because `order.inputs[i].token` is an arbitrary address chosen by the order placer (the intent creator — an unprivileged actor), the placer can specify the same token address twice, using a custom ERC20 whose `transferFrom`/`balanceOf` behavior yields a received delta of exactly `0` on the first leg (e.g., a token contract that mints/burns oddly, a rebasing token, or a "fee-on-transfer" style token with a 100% first-leg fee) and a non-zero delta on the second leg. The first leg then writes `_orders[commitment][token] = 0`, which is indistinguishable from "not yet set." The second leg's duplicate check `_orders[commitment][token] != 0` reads `0` and passes, silently overwriting the escrow record instead of reverting, defeating the intended duplicate-token guard entirely.

### Impact Explanation
The duplicate-input guard exists specifically to stop the same token address from occupying two escrow "legs" of a single order commitment (as demonstrated by the project's own regression tests for this exact scenario, `testRevert_PlaceOrder_DuplicateInputTokens*`). Bypassing it reintroduces the underlying class of bug the guard was written to prevent: `_orders[commitment][token]` collapsing multiple legs into one bucket breaks the invariant that escrow accounting, commitment hashing, and downstream fill/refund logic (in `IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents`) rely on one-token-per-commitment-per-address bookkeeping. This can corrupt escrow accounting for the affected commitment (a leg's transferred value is not reflected/tracked correctly), which is a fund-accounting integrity issue in the intents escrow path explicitly in scope. Severity is Medium, matching the source finding, since the practical exploitation requires the placer to use a token with non-standard transfer/balance semantics under their own control, but reachable from a fully unprivileged transaction (`placeOrder`).

### Likelihood Explanation
Likelihood is limited by the precondition that the input token must be a non-standard ERC20 whose transfer/`balanceOf` delta can legitimately be `0` on one leg and non-zero on the same token in another leg within a single call — this typically requires a custom or exotic token, not a mainstream ERC20. Since the intent placer fully controls which token contracts appear in `order.inputs`, this is trivially reachable by any unprivileged caller who supplies such a token; no privileged role, governance, or protocol collusion is required. This mirrors the original Saddle finding's likelihood profile (a permissionless configuration path where a zero-colliding value silently defeats a duplicate check).

### Recommendation
Do not use `0` as both the "unset" sentinel and a valid stored escrow value. Options:
- Track presence with a separate `mapping(bytes32 => mapping(address => bool)) seen` (or a "amount+1" offset) purely for the duplicate check, independent of the actual escrowed amount.
- Alternatively, perform the duplicate-token pass on `order.inputs` token addresses *before* any transfers occur (as already done for `order.output.assets` via transient storage in the same function), rather than relying on the escrow-amount mapping's zero-ness after transfers.
- Re-validate that the *received* amount (post-transfer) is non-zero for every leg regardless of `protocolFeeBps`, closing the gap where `reducedInputs = order.inputs` skips the zero check entirely.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transferFrom` succeeds but whose `balanceOf(gateway)` delta is `0` for the first call from a given order and the real requested amount for the second call (e.g., by tracking a per-tx call counter or leveraging a rebase/fee toggle it controls).
2. Attacker calls `IntentGatewayV2.placeOrder` with `order.inputs = [{token: EvilToken, amount: X}, {token: EvilToken, amount: Y}]` and `protocolFeeBps == 0` (default when no destination-specific fee is configured).
3. In Phase 1 (no predispatch branch), leg 0's `order.inputs[0].amount` becomes `0` after `balanceOf` delta measurement; leg 1's remains `Y`.
4. In Phase 3, leg 0 writes `_orders[commitment][EvilToken] = 0`; leg 1's duplicate check `_orders[commitment][EvilToken] != 0` reads `0` and passes (instead of reverting with `InvalidInput`), overwriting the mapping with `Y`.
5. The order is placed successfully with a duplicated token leg that should have reverted per the contract's own duplicate-input-token invariant (contradicting the behavior asserted by `testRevert_PlaceOrder_DuplicateInputTokens`), corrupting the commitment's escrow bookkeeping for that token.
