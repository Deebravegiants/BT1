### Title
Unmeasured repay overpayment "refund" drains pool custody on a debt-free market - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool's `repay` leg treats the caller-declared `amount` as money already received and refunds the "overpayment" — `amount` minus the ceiling-rounded outstanding debt — directly out of the pool's token balance. On a market with zero outstanding debt, `resolve_repay` computes `current_debt_ceil == 0`, so the entire declared `amount` becomes the overpayment and is transferred to the caller, while the cash book is untouched and no reserves check runs on the refund. An unprivileged address can therefore call `repay` with `amount` equal to the pool's custody balance and walk away with suppliers' funds without depositing anything.

### Finding Description
The bug class from ALPINE-CVE-2019-9755 — an attacker-controlled size argument feeding a subtraction whose result is trusted as a payout length — maps onto `ops::repay::accounting` in `contracts/pool/src/ops/repay.rs:40-67`:

- `cache.resolve_repay(amount, position)` (`common/src/rates/scaling.rs:171-191`) computes `overpayment = amount - current_debt_ceil` when `amount >= current_debt_ceil`.
- `net_repay = amount - overpayment` is credited to `cash`, and `RepayRoundsToZeroShares` passes trivially on its `net_repay == 0` disjunct.
- `ops::repay::apply` then calls `cache.transfer_out(payer, overpayment)` (`repay.rs:32`) — a real token transfer funded by pool custody, not by any measured inbound delta. The doc comment admits the assumption: "The controller transfers the repay amount into the pool before this call," but the pool entrypoint is directly callable and never verifies receipt.
- When `borrowed == 0` (or `pos_scaled == 0` for the submitted action), `current_debt_ceil` is 0, `overpayment == amount`, `net_repay == 0`, and the book is untouched while custody pays out.

The same shape exists in `ops::recapitalize::apply` (`contracts/pool/src/ops/recapitalize.rs:52-55`), where `refund = amount - applied` is transferred out without debiting cash or passing `require_reserves`.

This is pinned by the repo's own regression test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590-3610`), which calls `client().repay(&payer, &t.ract(0, custody_before))` on a market with no debt and asserts the payer receives the full custody balance.

### Impact Explanation
Theft of user funds. The refund transfer is real SAC custody backing supplier shares; draining it breaks the `cash == balance` invariant and leaves suppliers unable to withdraw (fail-closed loss of principal, not merely a DoS). The attacker's payout is bounded only by the pool's live token balance, since claiming more than custody reverts inside the SAC transfer — so the optimal call declares exactly the pool's balance.

### Likelihood Explanation
Fully reachable by any unprivileged address in one call: `pool.repay(payer, actions)` with a `PoolAction` whose `hub_asset` names a debt-free (or zero-position) market and `amount` equal to the pool's token balance. No position, collateral, oracle state, or privileged role is required; `payer` receives the refund directly. Any market that has been fully repaid, never borrowed, or freshly created qualifies.

### Recommendation
Measure receipts instead of trusting declared amounts: snapshot the pool's token balance at entry and cap `overpayment`/`refund` at the observed inbound delta (balance-after-transfer minus balance-before, or the amount actually pulled via `transfer`/`transfer_from` inside the same call). Alternatively, gate `repay` and `recapitalize` behind the controller so the prefund invariant is enforced structurally, and reject `repay` actions on markets where the resolved burn is zero while `amount > 0` rather than passing on the `net_repay == 0` disjunct.

### Proof of Concept
```rust
// Attacker calls pool.repay directly; no tokens are transferred in.
// Market state: supplied > 0, borrowed == 0, cash == token balance.
let custody: i128 = token::Client::new(&env, &asset).balance(&pool);

let actions = vec![&env, PoolAction {
    hub_asset: key.clone(),
    position: ScaledPositionRaw { scaled_amount: 0 },
    amount: custody, // entire pool balance declared as "repayment"
}];

// resolve_repay: current_debt_ceil == 0 -> overpayment == custody, net_repay == 0
// transfer_out(payer, custody) pays the attacker from supplier custody.
pool_client.repay(&attacker, &actions);
// attacker balance += custody; state.cash unchanged; book/custody diverge.
```
