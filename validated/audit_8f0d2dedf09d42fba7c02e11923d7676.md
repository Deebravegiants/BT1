### Title
Emporium Min-circuit path allows unauthenticated arbitrary calls that drain Emporium's held funds - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` — a statement anyone can satisfy without owning any Hinkal UTXO. `EmporiumUpgradeable.runAction` then decodes an attacker-supplied `EmporiumStack` from `externalActionData.externalActionMetadata` and, if `signerAddress == address(0)`, skips the EIP-712 signature check in `verifyWallet` entirely, letting the attacker execute arbitrary `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own address while the balance-accounting loop (bounded by the empty `erc20TokenAddresses` array) does nothing.

### Finding Description
The invariant that should hold is: *every asset Emporium can move in a transaction is accounted for in `balancesBefore`/`balancesAfter`*. This breaks because the accounting loop in `EmporiumUpgradeable.runAction` is indexed over `circomData.erc20TokenAddresses` [1](#0-0) , [2](#0-1)  while the operations actually executed are indexed over `stack.ops`, an attacker-controlled array decoded straight from calldata with no relation to `erc20TokenAddresses` [3](#0-2) .

The attacker's path:
1. Choose `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses = []`. This makes `formInputForCircom` select `formInputEmporiumMin`, whose only public inputs are `emporiumMessage`, `timeStamp`, `calldataHash` [4](#0-3) , matching `MainEVMCircuitMin`, which only constrains `message === Poseidon(messageSeed)` [5](#0-4) . The attacker picks any unused `messageSeed`/`emporiumMessage` and generates a valid proof unrelated to any UTXO ownership.
2. Because `erc20TokenAddresses.length == 0`, `dimensionsCheck` forces `amountChanges`, `inputNullifiers`, `outCommitments`, `onChainCreation`, `slippageValues` to all be empty too [6](#0-5)  — no nullifiers are spent, no shielded funds are committed.
3. In `externalActionData.externalActionMetadata`, the attacker encodes an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: <token Emporium holds>, invokeWallet: false, value: 0, callData: transfer(attacker, allBalance)}]`.
4. `verifyWallet` sees `stack.signerAddress == address(0)` and returns immediately without checking any signature [7](#0-6) .
5. The op loop takes the "Stateless Interaction" branch (since `invokeWallet && signerAddress != 0` is false) and calls `op.endpoint.call{value: op.value}(op.callData)` directly from Emporium's address [8](#0-7) , moving any ERC20/ETH Emporium holds to the attacker.
6. The post-call accounting loop is skipped entirely because `circomData.erc20TokenAddresses.length == 0`, so `balancesBefore`/`balancesAfter`/`BalanceChangeShouldBePositive` never observe the stolen token, and no `UTXO` output is required to account for it.
7. `calldataHash` integrity (`getHashedCalldata`) is only a self-consistency check computed from the attacker's own calldata [9](#0-8)  — it does not bind the proof to any prior authorization, so it provides no protection here. `onlyAllowedRecipient` on `runAction` only checks `msg.sender == Hinkal` [10](#0-9) , and does not constrain `op.endpoint`/`op.callData`.

None of the existing guards (`performHinkalChecks`, `rootHashExists`, `insertNullifiers`, `onlyAllowedRecipient`, the trivial circuit's `ForceEqualIfEnabled`/overflow checks) prevent this, because the Min circuit and the empty-array accounting path were designed to skip exactly the checks that would otherwise bind the operation to real funds.

### Impact Explanation
Any unprivileged attacker can drain any ERC20 tokens or ETH balance held by the Emporium contract by crafting an `EmporiumStack` with `signerAddress == 0` and an arbitrary op, combined with a trivially self-generated Min-circuit proof. This is direct theft of funds held by/in-flight through Emporium, repeatable for every distinct `emporiumMessage` the attacker chooses, matching **Critical: direct theft of shielded or in-flight user funds**.

### Likelihood Explanation
Preconditions are minimal: the Emporium contract must hold some balance (which happens whenever users deposit into Emporium or funds are in-flight during multi-step Emporium operations), and a Min verifier must be registered for `verifierId = buildVerifierId({tokenNumber:0, nullifierAmount:0, outputAmount:0}, HINKAL_EMPORIUM_ACTION_ID)` (which is the stated purpose of the Min-circuit feature). No special role, whitelisting, or victim cooperation is required; the attacker only needs to generate one cheap Groth16 proof for a 1-constraint circuit. This is fully repeatable and low-cost.

### Recommendation
Do not allow `signerAddress == address(0)` to bypass authorization when `stack.ops` is non-empty and performs arbitrary calls; require every op to be authorized either via wallet signature or via strict binding to `circomData.erc20TokenAddresses`/`amountChanges`. Additionally, ensure the Min-circuit/empty-token-array path can only be used for message-only interactions that provably cannot move funds Emporium already holds — e.g., disallow non-empty `stack.ops` (or restrict callable selectors/endpoints) whenever `erc20TokenAddresses.length == 0`, or require the post-call balance check to cover Emporium's full token surface rather than only `circomData.erc20TokenAddresses`.

### Proof of Concept
Foundry test plan:
1. Deploy Hinkal + `EmporiumUpgradeable`, register a Min verifier for `verifierId = buildVerifierId(Dimensions(0,0,0), HINKAL_EMPORIUM_ACTION_ID)` that always returns true (or use a locally-generated valid Groth16 proof for `MainEVMCircuitMin` with attacker-chosen `messageSeed`).
2. Fund Emporium with `TOKEN.transfer(emporiumAddress, 1000e18)` to simulate held/in-flight balance.
3. Build `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `emporiumMessage = Poseidon(messageSeed)`, and `externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(TOKEN), invokeWallet: false, value: 0, callData: abi.encodeCall(TOKEN.transfer, (attacker, 1000e18))})], maxFee: 0, deadline: type(uint256).max}))`.
4. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from `attacker`.
5. Assert: `TOKEN.balanceOf(emporiumAddress) == 0` and `TOKEN.balanceOf(attacker) == 1000e18` after the call, i.e., `balancesBefore == balancesAfter` for the empty `erc20TokenAddresses` array (both empty arrays, trivially "equal") while actual on-chain token balances diverged by the full stolen amount — demonstrating the broken equality "assets Emporium can move == assets accounted in balancesBefore/balancesAfter."

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
