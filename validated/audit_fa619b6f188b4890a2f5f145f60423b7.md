Investigation confirms a genuine origin-validation bypass in the Gateway's internet-facing HTTP server, analogous in bug class to the Vite CORS issue (permissive/incorrect origin matching allowing untrusted websites to read cross-origin responses).

### Title
CORS wildcard-origin suffix-match bypass allows any attacker-registered domain to pass as an allowed subdomain - (File: core/services/gateway/network/httpserver.go)

### Summary
The Gateway's `UserServerConfig` HTTP endpoint implements a custom CORS origin allowlist (`isAllowedOrigin`) supporting wildcard subdomain entries such as `https://*.ethereum.org`. The wildcard match strips the `*.` prefix and then only checks `strings.HasSuffix(originHost, allowedHost)`, without requiring a `.` boundary before the suffix. This lets an attacker register any domain that merely *ends with* the configured suffix (e.g. `evilethereum.org`) and have it treated as a trusted subdomain of `ethereum.org`, defeating the intended allowlist and enabling the same "malicious website reads dev/API server response" bug class described in the Vite CVE.

### Finding Description
`isAllowedOrigin` in [1](#0-0)  parses both the request `Origin` header and each configured allowed origin into scheme/host/port, then for wildcard entries does: [2](#0-1) 

After stripping `*.` from `allowedHost` (e.g. `*.ethereum.org` → `ethereum.org`), it accepts any `originHost` for which `strings.HasSuffix(originHost, allowedHost)` is true. Because there is no boundary check (no requirement that the character preceding the matched suffix is a `.`), a completely unrelated, attacker-registered domain such as `evilethereum.org` or `notarealethereum.org` will also satisfy `HasSuffix(originHost, "ethereum.org")`, even though it is not a subdomain of `ethereum.org` at all.

This is consumed directly in `handleRequest`, which reflects the attacker-controlled `Origin` header back as `Access-Control-Allow-Origin` once `isAllowedOrigin` returns true: [3](#0-2) 

The existing test suite only validates the negative case where the origin doesn't end with the configured suffix at all (e.g. `https://ethereum.remix.org` vs `*.ethereum.org`), but does not test the sibling-domain suffix-collision case, so the bypass is untested and unnoticed: [4](#0-3) .

### Impact Explanation
This affects the Gateway's `UserServerConfig` endpoint, which is explicitly documented/used as an internet-facing API meant to be reachable from browsers with a restricted origin allowlist (e.g. `https://remix.ethereum.org`) as shown in the integration test config: [5](#0-4) . If an operator configures a wildcard allowlist entry (a supported, documented feature), any attacker who registers a sibling domain sharing the suffix can have their malicious webpage's `fetch()` requests receive `Access-Control-Allow-Origin` reflecting their origin, letting them read authenticated JSON-RPC responses (which may include job-run/request data processed via `ProcessRequest`) that were only meant to be exposed to the legitimate subdomains of the trusted parent domain — a cross-user/cross-origin response confusion analogous to the Vite CORS disclosure.

### Likelihood Explanation
Exploitability only requires an attacker to register any domain ending in the configured allowed suffix (e.g. buy `evilethereum.org` when the allowlist has `*.ethereum.org`) and lure a victim to visit it while their browser can reach the Gateway's user-facing port. No authentication or privileged position is required — this is a standard unprivileged-web-attacker scenario, matching the same class described in the CVE.

### Recommendation
Fix the wildcard suffix check in `isAllowedOrigin` ( [2](#0-1) ) to require a `.` boundary immediately preceding the suffix match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
Add regression tests covering sibling-domain suffix collisions (e.g. `evilethereum.org` against `*.ethereum.org`) to prevent recurrence.

### Proof of Concept
1. Configure the Gateway `UserServerConfig` with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. From a browser, host a page on `https://evilethereum.org` and run:
```js
fetch('https://gateway.example.com/user', { method: 'POST', body: '...' })
  .then(r => r.text()).then(console.log);
```
3. The server's `isAllowedOrigin` matches `evilethereum.org` via `strings.HasSuffix("evilethereum.org", "ethereum.org")`, returns `true`, and reflects `Access-Control-Allow-Origin: https://evilethereum.org`, letting the attacker's page read the JSON-RPC response despite not being any subdomain of `ethereum.org`.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
