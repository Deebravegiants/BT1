## Title
Donation-based first-depositor share-price manipulation in `swap::liquidity_pool` permits near-total draining of later LPs' liquidity - (File: `aptos-move/move-examples/swap/sources/liquidity_pool.move`)

## Summary
The seed report's core custody invariant is: *a permissionless pool/price-setting operation must not let the first actor set an arbitrary, easily-manipulated exchange rate that a later depositor is forced to accept, allowing the first actor to extract value from subsequent depositors.* In `swap::liquidity_pool.move`, pool creation (`create`) is fully permissionless [1](#0-0) , and the LP-share pricing formula in `mint` derives the exchange rate from the *live on-chain balance* of the pool's fungible-asset stores (`fungible_asset::balance(store_1)/(store_2)`) rather than from an internally tracked reserve variable [2](#0-1) .

## Finding Description
`create()` lets anyone create an LP-token/pool object for an arbitrary pair of fungible assets with no minimum-liquidity delay, allow-list, or cooldown [1](#0-0) .

`mint()` computes the number of LP tokens to award using:
- On first mint (`lp_token_supply == 0`): `total_liquidity = sqrt(amount_1 * amount_2)`, minus a fixed `MINIMUM_LIQUIDITY = 1000` that is permanently locked [3](#0-2) .
- On subsequent mints: `token_i_liquidity = amount_i * lp_token_supply / reserve_i`, where `reserve_i` is `fungible_asset::balance(store_i)` — the *actual* token balance sitting in the pool's stores, not an internally accounted reserve field [4](#0-3) .

Because the reserve figure used for share pricing is the raw balance of the fungible store rather than a value only mutated by `mint`/`swap`/`burn`, any party that can push a `FungibleAsset` into `store_1`/`store_2` outside of `mint()` inflates the reserve without minting corresponding LP shares. Combined with attacker control over the very first deposit (`total_liquidity - MINIMUM_LIQUIDITY`, which can be reduced to as little as 1 LP share by choosing `amount_1`/`amount_2` just above `MINIMUM_LIQUIDITY`), this reproduces the classic "donation/inflation attack" that is the direct custody analog of the seed report's cheap-synth/first-LP price manipulation: the attacker sets an artificial price for the pool's shares, and a later depositor's `mint()` call rounds `token_i_liquidity` down toward zero while their real assets are absorbed into the now-inflated store balance that the attacker's single LP share is redeemable against via `burn()`.

Concretely:
1. Attacker calls `router::create_pool` for a fresh, permissionless pair (their own coin + a wanted target FA/coin) [5](#0-4) .
2. Attacker calls `mint()` with `amount_1 = amount_2 = MINIMUM_LIQUIDITY + 1`, receiving `1` LP token while `MINIMUM_LIQUIDITY` LP tokens are burned to the pool object address [3](#0-2) .
3. Attacker (or anyone) pushes a large amount of tokens directly into `store_1`/`store_2` without calling `mint`, inflating `fungible_asset::balance(store_1)`/`(store_2)` used as `reserve_1`/`reserve_2` in the very next `mint()` call.
4. A victim then calls `mint()` with a "normal" deposit amount; `math64::mul_div(amount_i, lp_token_supply, reserve_i)` rounds down to `0` (aborting via `EINSUFFICIENT_LIQUIDITY_MINTED`) or to a tiny nonzero LP amount, while their tokens are deposited into the now-shared, attacker-dominated store balances.
5. Attacker calls `burn()` with their `1` LP share and redeems a share of `pool.coin1`/`coin2` proportional to `1 / lp_token_supply` of the *inflated* store balance — i.e., most/all of the victim's real deposit [6](#0-5) .

I was not able to fully confirm within the indexed content whether `fungible_asset::deposit`/`fungible_asset::transfer` allows an arbitrary account to push assets into an arbitrary `Object<FungibleStore>` address without being the store's owner or holding a `TransferRef` (the module's `deposit` semantics are analogous to ERC-20 `transfer`-to-any-address in the standard Aptos FA implementation, but the exact permission check in `fungible_asset.move`'s `deposit` internals was not retrievable via the indexed snippets in this session). This is the key unverified precondition for step 3 of the exploit chain.

## Impact Explanation
If step 3 is achievable (donation to an arbitrary store), this is a high-severity custody-accounting corruption: legitimate LPs' deposited assets are redirected to an unprivileged attacker's LP share via rounding-down of `liquidity_token_amount`, directly matching the "Custody Impact Gate" criteria for supply/custody accounting corruption that moves value to the wrong holder. The result is not a permanent lock but an outright transfer of value from honest depositors to the attacker upon `burn()`.

## Likelihood Explanation
`swap::liquidity_pool.move` is an `aptos-move/move-examples` reference implementation (not core framework), and pool creation requires no allow-listing. The attack requires (a) permissionless pool creation — confirmed, (b) the classic sqrt/`MINIMUM_LIQUIDITY` first-mint formula — confirmed, and (c) permissionless donation into the pool's store — unconfirmed in this session. Because criterion (c) could not be independently proven from the retrieved code, likelihood should be treated as **unconfirmed/moderate** pending verification of `fungible_asset::deposit`'s access control, rather than definitively proven.

## Recommendation
- Verify whether `fungible_asset::deposit` enforces store ownership; if not, `liquidity_pool::mint`/`get_amount_out`/`swap` should track reserves in an internally-maintained field (updated only by `mint`/`burn`/`swap`) rather than reading live `fungible_asset::balance()`, exactly as Uniswap V2's `sync`-guarded reserves do.
- If reserves must be balance-derived, require a much larger `MINIMUM_LIQUIDITY` lock and/or a minimum-liquidity threshold plus a cooldown period before large withdrawals/burns are permitted, mirroring the seed report's own recommended mitigation (minimum liquidity + cooldown).
- Round `liquidity_token_amount` up methodically or enforce a minimum share-per-deposit floor to prevent zero/near-zero LP minting for victims while the attacker's share balance captures the inflated balance.

## Proof of Concept
Conceptual PoC (pending confirmation of unrestricted FA deposit):
1. Attacker calls `router::create_pool(APT_wrapped, TARGET_FA, false)`.
2. Attacker calls `router::add_liquidity`/`liquidity_pool::mint` with `amount_1 = amount_2 = 1001`, receiving `1` LP token (`sqrt(1001*1001) - 1000 = 1`).
3. Attacker calls `fungible_asset::deposit(store_1_addr, large_donation_of_token_1)` directly (bypassing `mint`), inflating `store_1` balance to, e.g., `1,000,000`.
4. Victim calls `mint()` depositing `1000` of token_1 and proportional token_2; `token_1_liquidity = mul_div(1000, 1 /*lp_token_supply*/, 1,000,000) = 0`, causing `EINSUFFICIENT_LIQUIDITY_MINTED` to fire, OR with a larger amount the victim gets far fewer LP tokens than their contribution warrants.
5. Attacker calls `burn()` on their single LP token, redeeming `≈100%` of the pool's real balance including the victim's deposited tokens. [7](#0-6) 

**Note:** This finding is contingent on confirming that `fungible_asset::deposit` (or equivalent primitive) permits depositing to a `FungibleStore` object that the caller does not own, without going through `liquidity_pool::mint`. I was unable to retrieve the exact body of `fungible_asset::deposit`/`deposit_internal` within this session's indexed context to confirm this precondition — a Devin session with full file access should verify `aptos-move/framework/aptos-framework/sources/fungible_asset.move`'s `deposit` function before treating this as conclusively exploitable.

    public fun mint(
        lp: &signer,
        fungible_asset_1: FungibleAsset,
        fungible_asset_2: FungibleAsset,
        is_stable: bool,
    ) acquires FeesAccounting, LiquidityPool {
        let token_1 = fungible_asset::asset_metadata(&fungible_asset_1);
        let token_2 = fungible_asset::asset_metadata(&fungible_asset_2);
        if (!is_sorted(token_1, token_2)) {
            return mint(lp, fungible_asset_2, fungible_asset_1, is_stable)
        };
        // The LP store needs to exist before we can mint LP tokens.
        let pool = liquidity_pool(token_1, token_2, is_stable);
        let lp_store = ensure_lp_token_store(signer::address_of(lp), pool);
        let amount_1 = fungible_asset::amount(&fungible_asset_1);
        let amount_2 = fungible_asset::amount(&fungible_asset_2);
        assert!(amount_1 > 0 && amount_2 > 0, EZERO_AMOUNT);
        let pool_data = liquidity_pool_data(&pool);
        let store_1 = pool_data.token_store_1;
        let store_2 = pool_data.token_store_2;

        // Before depositing the added liquidity, compute the amount of LP tokens the LP will receive.
        let reserve_1 = fungible_asset::balance(store_1);
        let reserve_2 = fungible_asset::balance(store_2);
        let lp_token_supply = option::destroy_some(fungible_asset::supply(pool));
        let mint_ref = &pool_data.lp_token_refs.mint_ref;
        let liquidity_token_amount = if (lp_token_supply == 0) {
            let total_liquidity = (math128::sqrt((amount_1 as u128) * (amount_2 as u128)) as u64);
            // Permanently lock the first MINIMUM_LIQUIDITY tokens.
            fungible_asset::mint_to(mint_ref, pool, MINIMUM_LIQUIDITY);
            total_liquidity - MINIMUM_LIQUIDITY
        } else {
            // Only the smaller amount between the token 1 or token 2 is considered. Users should make sure to either
            // use the router module or calculate the optimal amounts to provide before calling this function.
            let token_1_liquidity = math64::mul_div(amount_1, (lp_token_supply as u64), reserve_1);
            let token_2_liquidity = math64::mul_div(amount_2, (lp_token_supply as u64), reserve_2);
            math64::min(token_1_liquidity, token_2_liquidity)
        };
        assert!(liquidity_token_amount > 0, EINSUFFICIENT_LIQUIDITY_MINTED);

        // Deposit the received liquidity into the pool.
        fungible_asset::deposit(store_1, fungible_asset_1);
        fungible_asset::deposit(store_2, fungible_asset_2);

        // We need to update the amount of rewards claimable by this LP token store if they already have a previous
        // balance. This ensures that their update balance would not lead to earning a larger portion of the fees
        // retroactively.
        update_claimable_fees(signer::address_of(lp), pool);

        // Mint the corresponding amount of LP tokens to the LP.
        let lp_tokens = fungible_asset::mint(mint_ref, liquidity_token_amount);
        fungible_asset::deposit_with_ref(&pool_data.lp_token_refs.transfer_ref, lp_store, lp_tokens);
    }
