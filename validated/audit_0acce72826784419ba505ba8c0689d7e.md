## Title
Webhook shop identity spoofing via unsigned `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) used to route and process a webhook entirely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. This breaks the identity binding `shop authenticated == shop acted upon`: the gem cryptographically verifies the *body* came from Shopify's secret, but blindly trusts the caller-supplied `shop-domain` header for tenant attribution.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from headers with no cryptographic tie to the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` field — it never incorporates the `shop` header: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then dispatches the handler using `request.shop` taken from the unauthenticated header, attributing the event to whatever shop the header claims: [4](#0-3) 

Because Shopify webhooks for a given app are all signed with the same app `client_secret` (regardless of which installed shop originated them), a request with a *valid* body/HMAC pair captured from one tenant remains valid when replayed directly to the app's webhook endpoint (bypassing Shopify) with the `shop-domain`/`X-Shopify-Shop-Domain` header changed to a different tenant. `HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop: [5](#0-4) 

The binding that should hold is: `shop verified by HMAC == shop used for tenant-scoped processing`. Instead, only the body is verified while the shop identity is parsed from an out-of-band, unsigned header — precisely the "field acted on but not covered by the HMAC" analog.

### Impact Explanation
Any party who can obtain one legitimately-signed webhook body/HMAC pair for the app (e.g., by installing the app on their own shop, or observing a webhook they legitimately receive) can forge a request directly to the app's webhook endpoint with an arbitrary `shop-domain` header. The gem will report the HMAC as valid and hand the host application data attributed to a shop the attacker does not control — a cross-tenant confusion primitive. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., GDPR `customers/redact`/`shop/redact` mandatory topics, order/customer sync, uninstall handling), this can lead to cross-tenant data corruption, unauthorized redaction/erasure actions being triggered against a victim shop's records, or false uninstall/state changes recorded for a shop the attacker doesn't own.

### Likelihood Explanation
Exploitation requires only an internet-reachable webhook endpoint (which is a documented public app requirement) and possession of any one valid signed webhook body for the app — trivially obtainable by installing the app on an attacker-controlled development shop, since Shopify signs all webhooks for an app with the same shared `client_secret` irrespective of shop. No privileged credentials, access tokens, or tenant-specific secrets are required.

### Recommendation
Bind the shop identity to the signed content: either include the `shop-domain` (and `topic`/`webhook_id`) in `to_signable_string` so they are covered by the HMAC, or require the host application to independently verify that `request.shop` corresponds to a shop actually known/installed by the app before trusting it, and document this requirement explicitly since the gem currently does neither.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g. `orders/create`) signed by Shopify with the app's shared `client_secret`. Attacker captures the raw body `B` and header `X-Shopify-Hmac-Sha256: H`.
2. Attacker sends `POST /webhooks` directly to the app's public endpoint with body `B`, `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` while `to_signable_string` remains `B`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` and matches `H` → returns `true` (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled data under the victim tenant's identity.
