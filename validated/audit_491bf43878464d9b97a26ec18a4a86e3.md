Confirmed: at the gateway-side handler `HandleJSONRPCUserMessage` in `core/services/gateway/handlers/vault/handler.go`, for `vaulttypes.MethodPublicKeyGet` the request is forwarded to node handling (`h.handlePublicKeyGet` / `fanOutToVaultNodes`) with no validation that `req.Params` is non-nil [1](#0-0) . This means an unprivileged client can send `vault.publicKey.get` with `params` omitted through the public gateway endpoint, and it will be forwarded unchanged to the DON node's `GatewayHandler.HandleGatewayMessage`, which routes it directly to `handlePublicKeyGet` without going through `GatewayVaultRequestProcessor` (unlike secrets methods) [2](#0-1) . There `json.Unmarshal(*req.Params, r)` dereferences `req.Params` without a nil check [3](#0-2) , unlike every method routed through `processRequest`, which explicitly checks `req.Params == nil` before unmarshalling [4](#0-3) .

I could not find any `recover()` wrapping around the connector's `readLoop` or `HandleGatewayMessage` invocation — [5](#0-4)  shows the goroutine calling `handler.HandleGatewayMessage` directly with no `defer recover()`. The only panic-handling utilities found in the repo (`core/recovery/recover.go`) are not referenced by this code path in the index. This corroborates the report's core claim: the nil check that exists in every other vault-method code path is genuinely missing on the `MethodPublicKeyGet` fast path, and nothing upstream (gateway-side handler) rejects a `params`-less request before it reaches the vulnerable `json.Unmarshal(*req.Params, r)` line.

Audit Report

## Title
Nil-pointer panic on unprivileged vault `publicKey.get` gateway request - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` without going through `GatewayVaultRequestProcessor`, and `handlePublicKeyGet` dereferences `*req.Params` without checking for `nil`, unlike every other vault method's processor function. An unauthenticated caller can send a JSON-RPC `vault.publicKey.get` request with `params` omitted (valid per JSON-RPC 2.0) through the gateway to crash the node-side handler goroutine with a nil-pointer dereference.

## Finding Description
`GatewayHandler.HandleGatewayMessage`'s switch statement sends `MethodPublicKeyGet` straight to `h.handlePublicKeyGet(ctx, gatewayID, req)` with no authorization step and no participation in `GatewayVaultRequestProcessor.processRequest`, which is the only place nil-params checks exist for the other vault methods (`processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`) [6](#0-5) [7](#0-6) . `handlePublicKeyGet` unconditionally executes `json.Unmarshal(*req.Params, r)` [3](#0-2) , so if `req.Params` (`*json.RawMessage`) is `nil`, this panics.

On the gateway side, `handler.HandleJSONRPCUserMessage` special-cases `MethodPublicKeyGet` and forwards it to nodes via `fanOutToVaultNodes`/`h.don.SendToNode` without validating `req.Params != nil` [1](#0-0) , ` [8](#0-7) `. This confirms an unauthenticated, unprivileged actor can get a `params`-less request through to the DON node.

The connector's read loop that invokes `HandleGatewayMessage` on the node side has no `recover()` around the handler call [5](#0-4) , so a panic here is not contained.

## Impact Explanation
This is a denial-of-service against the node's connector read-loop goroutine handling gateway traffic for the vault capability, triggerable by any unauthenticated client able to reach the gateway HTTP endpoint. Depending on Go runtime behavior for an unrecovered panic in a spawned goroutine, this can crash the entire node process, not just the read loop, since Go panics that are not recovered anywhere in the goroutine's call stack terminate the program.

## Likelihood Explanation
High. `vault.publicKey.get` requires no authentication/authorization to reach the vulnerable code, and omitting `params` in a JSON-RPC 2.0 request is standards-compliant and trivial to construct. This is a single crafted request, fully repeatable.

## Recommendation
Add `if req.Params == nil { return h.errorResponse(...) }` in `handlePublicKeyGet` before dereferencing, mirroring the pattern already used in `GatewayVaultRequestProcessor`'s process* functions. Additionally add the same nil check in the gateway-side `handler.HandleJSONRPCUserMessage`'s `MethodPublicKeyGet` branch before forwarding to nodes.

## Proof of Concept
1. Craft `jsonrpc.Request[json.RawMessage]{Method: "vault.publicKey.get", Params: nil}` (omit the `params` field in the JSON payload).
2. Send it to the gateway's public JSON-RPC endpoint for the vault DON (no auth header required for this method).
3. Gateway-side `handler.HandleJSONRPCUserMessage` forwards it to node(s) via `fanOutToVaultNodes`.
4. Node's connector read loop calls `GatewayHandler.HandleGatewayMessage`, which calls `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` and panics on nil dereference, crashing the goroutine (and potentially the process, since no `recover()` guards the call).

func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}
