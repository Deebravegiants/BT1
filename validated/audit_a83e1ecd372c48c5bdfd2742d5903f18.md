## Title
Direct LT transfers into a bonding-curve `Pair` are permanently unrecoverable, with no rescue path for payer or admin - ([File: packages/contracts/src/Pair.sol])

### Summary
An unprivileged wallet can send the LT reserve asset directly to a token's bonding-curve `Pair` address (e.g. mistakenly, instead of going through `Zap.buy`). This LT never returns to circulation: `Pair.sol` exposes only `transferAsset`/`transferToken`, both gated `onlyRouter` [1](#0-0) , and `Router.graduate` — the only caller of `transferAsset` for the asset side — is restricted to `BONDING_ROLE` and is invoked by `Bonding` exactly once per token, during `_prepareGraduationLiquidity`, while the token's lifecycle is still `Curve` [2](#0-1) . Once the lifecycle flips past `Curve`, no code path ever calls `Router.graduate`/`Pair.transferAsset` for that pair again, so any LT sitting in (or later sent to) the curve `Pair` is frozen forever — for the mistaken sender, for the protocol owner, and for everyone else.

### Finding Description
`Pair.sol` is a minimal AMM pair (forked from Virtuals `FPair.sol`) with no `skim`, no admin rescue, and no owner — its only asset-moving functions are `transferAsset`/`transferToken`, both `onlyRouter` [3](#0-2) . `Router.sol`'s only path to `transferAsset` on the asset (LT) side is `graduate()`, gated by `BONDING_ROLE` [4](#0-3) . `Bonding` calls `Router.graduate` a single time, from `_prepareGraduationLiquidity`, and passes an *explicit* `amount = ltFromPair` (stored-reserve raised, excluding the virtual seed and excluding any donated LT) rather than draining the full balance — this is documented as intentionally donation-resistant [5](#0-4) . The natspec on `Router.graduate` itself states plainly that any LT donated to the pair is "unreachable as long as (a) `BONDING_ROLE` is not granted to any other address, and (b) future `Bonding` upgrades preserve the lifecycle gate" [6](#0-5) .

The test suite confirms this is not a transient state but a permanent one: after legitimate graduation, `assetBalance()` on the curve pair equals exactly the donated amount and is asserted to "remain locked in the curve pair" [7](#0-6) , and this holds under fuzzing across arbitrary donation sizes and stages [8](#0-7) , and equally at the `Router` unit-test level (`test_graduate_leavesDonationBehind`) [9](#0-8) .

This is the same root cause as the nounsDAO report: a state transition (there, `cancel()`; here, the `Curve → Graduating → Graduated` lifecycle flip) zeroes/locks the "recoverable" window for a token that was sent to the contract, and afterward there is no path — for the payer or anyone else — to reclaim it. Unlike `FeeVault`, which explicitly ships `sweepDonations()` to handle exactly this class of mistaken/donated transfer for USDC [10](#0-9) , and unlike the HyperSwap LP-seeding path, which sweeps hostile-preseed LT residue to the owner via `_sweepLTToOwner` [11](#0-10) , the internal curve `Pair` has **no equivalent sweep/rescue mechanism at all** for LT sent directly to it.

### Impact Explanation
Any unprivileged wallet that sends LT directly to a bonding-curve `Pair` address — whether by accident, by misreading the intended integration point (`Zap.buy`), or intentionally to "top up" a curve — permanently loses those funds. There is no admin escape hatch, no future `Bonding` call, and no owner-only sweep on `Pair.sol` itself; the only way LT ever leaves the pair is `Router.graduate`'s single, amount-capped, one-time call gated to the `Curve` lifecycle. This is a genuine, irreversible loss of funds for the mistaken sender, satisfying the "permanent freezing of trader ... funds" bar.

### Likelihood Explanation
Likelihood is realistic: `Pair` addresses are publicly known/discoverable (emitted in `TokenLaunched`/`PairCreated` events and readable via `Factory.getPair`), and a user or bot integrating against the wrong address, or attempting a "manual" LT transfer instead of routing through `Zap`, is a plausible mistake — the same class of mistake the original nounsDAO report and alt.fun's own `FeeVault.sweepDonations()` were built to mitigate for USDC.

### Recommendation
Add a permissionless (or owner-gated) sweep function to `Pair.sol`, analogous to `FeeVault.sweepDonations()`, that lets excess/mistakenly-sent LT (and TOKEN) balance beyond the pool's tracked reserves be recovered — e.g. to the protocol owner, mirroring the pattern already used for hostile-preseed LT residue via `_sweepLTToOwner` in `Bonding.sol`. Alternatively, expose a `Router`-mediated sweep callable after a token has reached `Lifecycle.Graduated`, since at that point the curve `Pair` no longer needs further isolation from graduation math.

### Proof of Concept
1. Attacker/user calls `IERC20(lt).transfer(pairAddr, X)` directly on a live or graduated bonding-curve `Pair` — no permission required, `Pair` has no deposit guard.
2. Token eventually graduates (or already has). `Bonding._prepareGraduationLiquidity` computes `ltFromPair` from **stored** reserves only, explicitly excluding `X`; `Router.graduate` drains only `ltFromPair`, leaving `X` in the pair (`test_graduate_leavesDonationBehind`, `test_inv_donation_zeroGapPreserved`).
3. Post-graduation, `Bonding`'s lifecycle for that token is `Graduated`; no future call to `Router.graduate`/`Pair.transferAsset` exists for it.
4. `X` sits in the `Pair` contract forever — `IERC20(lt).balanceOf(pairAddr) == X` for all time, unreachable by the original sender, the protocol owner, or any other address, since `Pair.sol` exposes no sweep/skim/admin-withdraw function.

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }

    ///         direct USDC transfers would otherwise inflate `balanceOf` above

    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));

    /// @dev Send LT held by this contract above `keep` to the owner,
    ///      emitting `LTRescued`. Called at the end of
    ///      `finalizeGraduation` with `keep = protectedLT` (any escrow
    ///      that doesn't belong to this graduation), so only THIS
    ///      graduation's rebalance residue lands on the owner. No-op on
    ///      the empty-pair fast path (nothing to sweep).
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
