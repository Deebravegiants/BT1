### Title
`findMatchingWithdrawal` matches only by `assetId`, causing duplicate status/txHash reports for multiple same-asset withdrawals in one intent - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the withdrawal record purely via `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, ignoring `WithdrawalIdentifier.index`. When a single intent contains two POA withdrawals of the same `assetId` (e.g. two `nep141:btc.omft.near` transfers to different destinations), both `WithdrawalIdentifier{index:0}` and `{index:1}` produce the same `tx.hash` (the shared NEAR intent tx), so both calls hit the same `getWithdrawalStatus({withdrawal_hash})` response, and `findMatchingWithdrawal` returns the *first* array entry whose `near_token_id` matches the assetId for both indices.

### Finding Description
The broken equality is: `describeWithdrawal({index:0}).{status,txHash}` should equal the outcome of withdrawal 0 only, and `describeWithdrawal({index:1}).{status,txHash}` should equal the outcome of withdrawal 1 only. Because `findMatchingWithdrawal` at [1](#0-0)  matches purely by `nep141:${w.data.near_token_id} === assetId` with no use of `index`, `destinationAddress`, or any per-withdrawal disambiguator, calling `describeWithdrawal` (defined at [2](#0-1)  ) for both `index:0` and `index:1` widget identifiers (both sharing the same `tx.hash`, since `createWithdrawalIdentifiers` in [3](#0-2)  only increments a per-bridge counter while reusing `args.intentTx` for `tx`) will each call `getWithdrawalStatusWithRetry` with the identical `withdrawal_hash`, and both resolve via `findMatchingWithdrawal` to the *same* first-matching array element. The code even documents this as a known limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) . None of the existing guards (`validateAddress`, `compareAddresses`, `supports()`, `assert` checks) touch this matching logic — they only validate a single withdrawal's destination/amount at creation time, not the identity of the returned status record.

The attacker's exact input: submit a single Near Intents transaction containing two POA-bridge withdrawal intents for the same `assetId` (e.g. `nep141:btc.omft.near`) with two different `destinationAddress` values. Both withdrawals get processed by the POA bridge indexer as separate on-chain transfers to different destinations, but the SDK's `watchWithdrawal` (via `withdrawal-watcher.ts`) will report the same `(status, txHash)` for both `WithdrawalIdentifier`s once the first-matching one completes.

### Impact Explanation
An integrator relying on `watchWithdrawal`/`describeWithdrawal` per `WithdrawalIdentifier` to determine when to credit/settle a withdrawal will see index 1 reported "completed" with index 0's `transfer_tx_hash` as soon as index 0's real transfer completes, even though the real on-chain transfer for index 1 (to a different destination) may still be pending, failed, or never independently verified. This matches the High/Critical criteria of "a status or hash misreport making an integrator credit or refund twice" since the reported outcome for one withdrawal is silently duplicated onto another, distinct, un-verified withdrawal. This is repeatable on every intent that contains 2+ same-`assetId` POA withdrawals.

### Likelihood Explanation
Preconditions: attacker only needs to construct one Near Intents transaction with two (or more) POA-bridge withdrawal intents sharing the same `assetId` but different destinations — no privileged action, no relayer/contract compromise. This is fully within a normal user's control (`createWithdrawalIntents` accepts arbitrary `withdrawalParams`), so the attacker cost is a single, normal intent submission. Likelihood is high and fully attacker-controlled/repeatable.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` beyond `assetId` — e.g., match by `assetId` + `destinationAddress` (+ `amount` if destinations can also collide), or coordinate with the POA bridge API to expose a stable per-withdrawal correlation id (e.g. sorted by amount, or an explicit index/sub-id in the API response) as hinted in the existing code comment, and only return a match when uniqueness across the response set can be guaranteed; otherwise conservatively return `pending`/error rather than an incorrect match.

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

```typescript
export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
```
