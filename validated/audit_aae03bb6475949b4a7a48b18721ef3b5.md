This is a real analog. `extract_signer` at [1](#0-0)  calls `Signature::decode(...).map(|sig| sig.signer())`, and `Signature::signer()` for the `Evm` variant simply returns the **unverified, attacker-supplied `address` field** rather than the address recovered from the ECDSA signature: [2](#0-1) . It is never checked that this `address` matches the key that actually produced `signature`. Compare this to `Signature::verify()`, which for the `Evm` variant correctly ignores the embedded `address` and returns the recovered signer from `secp256k1_ecdsa_recover` — the *only* correct place to derive an EVM signer identity: [3](#0-2) .

`extract_signer` is invoked directly from `IsmpHost::store_request_receipt` / `store_response_receipt`, which is the code path that persists the "who delivered this message" attribution used later for relayer fee/reward claims: [4](#0-3) . The `signer` bytes passed in originate from `msg.signer` in `handle_incoming_message` / `execute`, ultimately from the relayer-supplied `Message` in the unsigned `handle_unsigned` extrinsic (`pallet_ismp::Call::handle_unsigned`) — a call reachable by anyone, unsigned, per [5](#0-4) . Because `handle_unsigned`'s `validate_unsigned` only checks that `Self::execute` succeeds and does not independently verify signer attribution beyond what `execute`/`extract_signer` already (mis)computes, an unprivileged relayer can submit a `Signature::Evm { address: <victim>, signature: <their own valid ECDSA sig over msg> }`. `extract_signer` never calls `.verify()`, so it accepts whatever `address` the attacker wrote, and `RequestReceipts`/`ResponseReceipts` records the victim's address as the delivering relayer — even though the victim never delivered anything and never produced that signature.

### Title
Unverified EVM address in `Signature::signer()` allows forging relayer delivery attribution - (File: modules/pallets/ismp/src/host.rs)

### Summary
`extract_signer` in `pallet-ismp`'s `IsmpHost` implementation derives the relayer identity recorded in `RequestReceipts`/`ResponseReceipts` by calling `Signature::signer()` instead of `Signature::verify()`. For the `Signature::Evm` variant, `signer()` returns the raw, attacker-controlled `address` field embedded in the signature struct without ever checking that it corresponds to the key that produced the accompanying ECDSA `signature`. This mirrors the MinIO advisory's bug class: a signature-bearing payload is accepted and its identity/authorization field trusted, without validating that the cryptographic signature actually attests to that exact identity/content.

### Finding Description
`Signature::verify()` correctly recovers the EVM signer from the ECDSA signature via `secp256k1_ecdsa_recover` and returns that recovered address: [3](#0-2) . However, `Signature::signer()` is a separate accessor that, for the `Evm` variant, simply clones the `address` field carried in the enum — a field the caller (relayer) fully controls when constructing the `Signature` — with no relation enforced to `signature`: [2](#0-1) .

`extract_signer` in `modules/pallets/ismp/src/host.rs` decodes the raw signer bytes as a `Signature` and calls `.signer()` (not `.verify()`) to obtain the address to persist: [1](#0-0) . This function backs `store_request_receipt` and `store_response_receipt`, which pallet-ismp calls from the message-handling path (`handlers::request`/`handlers::response`) every time an incoming POST/GET request or response is processed, recording the resulting bytes as the "relayer" for that commitment: [4](#0-3) ; [6](#0-5) .

This whole path is reachable through `pallet_ismp::Call::handle_unsigned`, an unsigned extrinsic open to anyone: [5](#0-4) . Its `validate_unsigned` hook only re-runs `Self::execute(messages)` and checks it succeeds; it does not separately validate that the persisted signer/relayer identity is cryptographically sound: [7](#0-6) .

Downstream, relayer-reward flows are built on the trustworthiness of `RequestReceipts`/`ResponseReceipts` as attribution of who actually delivered a message (e.g., `pallet_ismp_relayer`'s outbound-request/consensus delivery claims prove the address stored at that slot and pay it a reward): the docs explicitly describe recovering a signer and matching it "against the address proven in `RequestReceipts[commitment]`" — [8](#0-7) . If the `RequestReceipts` value itself was populated from an unverified `address` field rather than a cryptographically recovered one, this whole attribution chain can be seeded with a forged identity by anyone submitting `handle_unsigned` messages.

### Impact Explanation
An unprivileged party (any relayer, or anyone able to submit an unsigned extrinsic) can craft a `Signature::Evm { address: <arbitrary/victim address>, signature: <their own valid signature over the message> }` and have it accepted as the delivering relayer's identity for a request/response receipt, because `extract_signer` never confirms `address` was the key that actually signed. This can be used to misattribute delivery credit to an address the attacker does not control (griefing a legitimate relayer, or funnelling relayer fee/reward claims toward an address the attacker does control if reward mechanisms elsewhere key off this attribution) — i.e., forged message delivery attribution / unauthorized crediting inside the relayer incentive system reachable from a single relayed transaction. This satisfies "forged message delivery" from the validation criteria.

### Likelihood Explanation
High. `handle_unsigned` is unsigned and permissionless by design (documented as "cannot be exploited as a spam vector" only with respect to proof validity, not signer-attribution correctness): [9](#0-8) . Constructing a `Signature::Evm` with a mismatched `address` requires no special privilege — the attacker only needs any valid keypair to produce `signature`, and can set `address` to any 20 bytes.

### Recommendation
In `extract_signer` (`modules/pallets/ismp/src/host.rs`), never trust `Signature::signer()` for attribution when the identity must be cryptographically bound to the signed message. Instead call `Signature::verify(&msg, None)` (as already correctly done in `outbound_consensus.rs` and `accumulate.rs`) and use the recovered address/public key as the stored relayer identity. Alternatively, harden `Signature::signer()` itself (or rename/deprecate it) so it cannot be mistaken for a verified accessor, and audit all remaining call sites of `.signer()` to ensure none of them use it as a trust boundary without a preceding `.verify()` call.

### Proof of Concept
1. Attacker prepares a POST request/response message to submit via `pallet_ismp::Call::handle_unsigned`.
2. Attacker generates any secp256k1 keypair `k` and produces `signature = sign(k, msg)`.
3. Attacker sets `msg.signer = Signature::Evm { address: <victim_or_arbitrary_address>, signature }.encode()`.
4. Submits the unsigned extrinsic; `validate_unsigned`/`execute` runs `handlers::request`/`response`, which calls `host.store_request_receipt(&wrapped_req, &msg.signer)` → `extract_signer(signer)` → `Signature::decode(...).signer()`, returning `address` (the attacker-chosen bytes) without ever calling `verify()`.
5. `RequestReceipts[commitment]` is now populated with the attacker-chosen `address`, regardless of whether that address's key ever produced the signature — confirmed by comparing against the correct pattern in `outbound_consensus.rs::process_outbound_consensus_delivery_claim`, which explicitly calls `signature.verify(&msg, None)` and asserts `recovered_address == evm_address` before trusting it: [10](#0-9) .

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
