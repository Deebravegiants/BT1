### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, but the `shop` value that the gem hands to the app's `WebhookHandler` (and that apps use to decide which tenant/store the payload belongs to) is read from an HTTP header that is never included in the signed material. An attacker who possesses one valid `(raw_body, hmac)` pair — trivially obtainable by triggering a real webhook to their own, attacker-owned/dev shop, since the HMAC secret (`client_secret`) is shared across every shop that installed the app — can replay that exact body/HMAC while substituting the `shop-domain` header for a victim shop's domain, breaking the binding between the authenticated bytes and the shop identity the app relies on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is parsed independently from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of the signable string at all: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then forwards `request.shop` straight to the app-supplied handler as part of `WebhookMetadata`, with no additional check that `shop` corresponds to the entity that actually produced the signed bytes: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this: it only recomputes and compares the HMAC of `verifiable_query.to_signable_string`, i.e. the raw body — the `shop` header is never fed into `compute_signature`: [4](#0-3) 

This breaks the identity binding `HMAC-covered-bytes == bytes-that-determine-tenant`. The equality that should hold is:
`shop-used-for-tenant-routing == shop-that-produced-the-HMAC-signed-body`
but instead the gem only proves `hmac == HMAC(secret, raw_body)`; `shop` is an unauthenticated, attacker-controllable header value that the app is documented to use directly for per-tenant business logic (see `docs/usage/webhooks.md`: "`data.shop` - The shop domain of the webhook"), e.g. enqueuing/writing data keyed by `shop_domain`.

Since the `client_secret` (HMAC key) is the same for the app regardless of which of its installed shops sends the webhook, any shop that has installed the app — including one an attacker legitimately installed the app on themselves — can produce a validly-signed `(body, hmac)` pair. The attacker then re-sends that request to the app's webhook endpoint with the `shop-domain` header rewritten to the victim shop, causing the handler to process attacker-controlled/attacker-triggered webhook data as though it originated from the victim's store.

### Impact Explanation
This allows cross-tenant data confusion: a webhook payload the attacker fully controls (by triggering it in their own store) can be attributed to a victim shop in the host application, because the gem never binds the `shop` value to the HMAC-signed content. Depending on how the host app uses `data.shop` (e.g., updating per-shop state, enqueuing per-shop jobs, writing to a per-shop database row keyed only by `shop_domain`), this can lead to cross-tenant data corruption or unauthorized actions being attributed/applied to a shop the attacker does not own. This matches the "Critical - cross-tenant access" impact category since it breaks the shop-identity boundary the gem is meant to enforce via HMAC validation.

### Likelihood Explanation
Exploitation only requires installing the target app on any shop the attacker controls (including a free/dev store) to obtain one valid signed webhook body/HMAC pair, then replaying it with a modified `shop-domain` header to the app's public webhook endpoint. No access to the victim's credentials, access token, or `client_secret` is required, and no privileged access is needed — only that the app process webhooks whose body content can be attacker-influenced (e.g. `orders/create`, `customers/update`, etc., where the attacker controls object contents in their own shop).

### Recommendation
Include the `shop-domain` header (and ideally `webhook-id`/`topic`) in the HMAC-signed material verified for webhooks, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted. At minimum, document/require that host applications independently verify `data.shop` is an install they recognize (e.g., matches a stored session) rather than trusting webhook-derived `shop` values for identity purposes, since the gem currently provides no such guarantee.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and obtains the app's shared `client_secret` in effect (they don't need to see it — Shopify computes the HMAC for them on webhook delivery).
2. Attacker triggers an event (e.g., creates an order) causing Shopify to deliver a webhook to the app with headers:
   `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some `raw_body`.
3. Attacker intercepts/replays this exact HTTP request to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body) == received_signature` — a check unaffected by the header change.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, so the host application processes attacker-supplied data as belonging to the victim shop.
