### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC signature over the request body [3](#0-2) . The `shop` value that is subsequently handed to the app's webhook handler is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a field that is never part of the signed payload [4](#0-3) . This breaks the equality that the report's bug class targets: `shop authenticated via HMAC` ≠ `shop trusted/used by the handler`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` show that the HMAC is computed and verified exclusively against `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` recomputes the signature from `to_signable_string` (the body) and compares it to the `hmac` header, with no reference to `shop`, `topic`, or `webhook_id`: [5](#0-4) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (parsed straight from the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [2](#0-1) 

Because the `shop-domain` header is disjoint from the signed bytes, any request body/HMAC pair that is valid for one shop remains a perfectly valid signature when the `shop-domain` header is swapped to a different shop. An attacker who is a legitimate merchant/tenant of a multi-tenant app (i.e., an "unprivileged" party relative to other tenants) receives authentic signed webhooks for their own shop and can replay the identical body+HMAC to the app's shared webhook endpoint while substituting a victim shop's domain in the header. `Registry.process` will accept the HMAC (since it never inspects headers) and dispatch the handler with `shop: <victim shop>`, causing the host application to attribute attacker-controlled webhook data to another tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem's own signature verification does not bind the `shop` field it hands to the app, so an app that keys any tenant-scoped action (data storage, redaction handling, GDPR mandatory topics, session/state lookups) off `WebhookMetadata#shop` can be made to act on/for the wrong tenant using only forged/replayed header values, with no access token or `client_secret` required. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app builder that trusts `WebhookMetadata#shop`/`request.shop` as an authenticated identity value (which the gem's public API implies, since it's returned right after `HmacValidator.validate` succeeds) — no special access is required beyond being able to send HTTP requests to the app's public webhook endpoint and possessing one legitimately signed body/HMAC pair (trivially obtainable by installing the app on any shop, including the attacker's own).

### Recommendation
- Short term: Include `shop`, `topic`, and `webhook_id` (or the full header set) in the signable string used by `Request#to_signable_string`, or otherwise document loudly that `request.shop`/`WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host app against the shop that owns the currently active session before use.
- Long term: Add regression tests asserting that flipping the `shop-domain` header on an otherwise-valid webhook request causes `HmacValidator.validate` to fail.

### Proof of Concept
```ruby
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, "{}")
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped from attacker's own legitimate shop
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, even though shop-domain was forged
ShopifyAPI::Webhooks::Registry.process(request)    # handler invoked with shop: "victim-shop.myshopify.com"
```
