No deduplication or validation exists to prevent multiple withdrawals of the same PoA token in a single batch. The `createWithdrawalIdentifiers` function in `withdrawal-watcher.ts` builds a distinct `WithdrawalIdentifier` per withdrawal param with a unique `index`, but that `index` is never used by `PoaBridge.describeWithdrawal`/`findMatchingWithdrawal` to disambiguate results — matching is only by `assetId`.

### Title
PoA bridge status/hash misattribution for multiple same-token withdrawals in one batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.findMatchingWithdrawal` selects a withdrawal from the PoA indexer response using only `` `nep141:${w.data.near_token_id}` === assetId ``, ignoring destination address, amount, and the caller-assigned `WithdrawalIdentifier.index`. When a single NEAR intents transaction contains two or more withdrawals of the same PoA token (e.g. `nep141:bera.omft.near`) to different destinations, `Array.prototype.find` deterministically returns the same first-matching entry for every identifier querying that assetId, so `describeWithdrawal` can report one destination's status/`transfer_tx_hash` for a different destination's `WithdrawalIdentifier`.

### Finding Description
The broken equality is: `WithdrawalIdentifier[i].destinationAddress/amount` should equal the destination/amount encoded in the withdrawal record returned as `status`/`txHash` for that identifier. In `describeWithdrawal` ( [1](#0-0) ), the withdrawal is looked up purely by `args.withdrawalParams.assetId` via `findMatchingWithdrawal` ( [2](#0-1) ), which uses `.find()` and returns the first entry whose `near_token_id` matches, regardless of amount, destination address, or account. The code comment explicitly documents this limitation: "multiple withdrawals of the same token in a single transaction are not supported" ( [3](#0-2) ), yet nothing upstream rejects or deduplicates such a batch.

Tracing the reachable path: `IntentsSDK.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` call `createWithdrawalIdentifiers` ( [4](#0-3) ), which assigns a per-bridge-route `index` to each `WithdrawalIdentifier` but does not check for or reject duplicate `assetId`s within the batch. Each identifier is passed independently to `watchWithdrawal` → `bridge.describeWithdrawal` ( [5](#0-4) ). Neither `supports()`, `validateAddress`, `validateWithdrawal`, nor any assert in `poa-bridge.ts` checks for duplicate assetIds across a batch — these guards validate the address format and token support per-item, not batch composition.

An ordinary user of the SDK (or an integrator forwarding user-supplied `withdrawalParams`) can submit a batch of two withdrawals both for `nep141:bera.omft.near`, to two different destination addresses (e.g., Destination A and Destination B). Once the PoA indexer processes both and returns a `withdrawals` array (in unspecified order per the code's own comment "Response list is unsorted"), both `WithdrawalIdentifier`s (index 0 for A, index 1 for B) query `findMatchingWithdrawal` with the same assetId and receive the *same* first match — e.g., both resolve to B's `COMPLETED` status and B's `transfer_tx_hash`, even though A's real withdrawal may still be pending or went to a different address.

### Impact Explanation
An integrator using `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` receives a `TxInfo` with a `txHash` for withdrawal A that actually corresponds to the payout made to B's address, and vice versa. Since this is the sole completion signal, an integrator that reconciles credits/refunds based on `describeWithdrawal`'s reported `txHash`/status could think A's withdrawal completed with B's transaction — a status/hash misreport that "could make an integrator credit or refund twice" or misattribute a destination transaction to the wrong internal request, matching the High severity category ("a status or hash misreport making an integrator credit or refund twice"). This is repeatable on every batch containing ≥2 withdrawals of the same PoA token, and is not limited to `bera.omft.near` — it applies to any PoA-bridged token.

### Likelihood Explanation
Preconditions: the batch of withdrawal intents must include two or more withdrawals for the same NEP-141 PoA token (same `assetId`) to different destinations, executed within a single NEAR intents transaction, and the caller must invoke `waitForWithdrawalCompletion` or `createWithdrawalCompletionPromises` to track completion via `describeWithdrawal`. This requires no special privilege — any SDK caller can construct a `WithdrawalParams[]` array with a repeated `assetId`; nothing in `supports()`, `validateWithdrawal()`, or the batch-building code (`createWithdrawalIdentifiers`) rejects or dedupes this composition. The attacker cost is zero beyond normal withdrawal fees, and the bug is deterministically repeatable each time such a batch is submitted and the PoA indexer returns multiple entries for the same token in an unsorted list.

### Recommendation
`findMatchingWithdrawal` should disambiguate among withdrawals sharing the same `near_token_id` by also matching on destination address (`data.address`) and amount (`data.amount`), or, as the code comment suggests, by consistently sorting both the API response and local withdrawal params by amount and matching by relative order. At minimum, `describeWithdrawal` should throw an explicit unsupported-batch error (rather than silently returning a possibly wrong status) when multiple api withdrawal records share the same `near_token_id` and cannot be disambiguated, and/or `createWithdrawalIdentifiers` should reject batches with duplicate PoA-bridge `assetId`s until amount/address-based matching is implemented.

### Proof of Concept
Vitest test in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts`, mocking only `poaBridge.httpClient.getWithdrawalStatus`:
1. Mock `getWithdrawalStatus` to return two `withdrawals` entries, both `near_token_id: "bera.omft.near"`, one with `data.address = "0xAAA..."`, `amount: 100`, `status: "COMPLETED"`, `transfer_tx_hash: "hashA"`, and the other `data.address = "0xBBB..."`, `amount: 200`, `status: "PENDING"`.
2. Create two `WithdrawalIdentifier`s via `createWithdrawalIdentifier` with `index: 0`/`destinationAddress: "0xAAA..."`/`amount: 100n` and `index: 1`/`destinationAddress: "0xBBB..."`/`amount: 200n`, both `assetId: "nep141:bera.omft.near"`.
3. Call `bridge.describeWithdrawal` for both identifiers.
4. Assert the equality that should hold: identifier for `0xBBB...` should report `{status: "pending"}` and identifier for `0xAAA...` should report `{status: "completed", txHash: "hashA"}`.
5. Observe the actual (broken) behavior: both calls return `{status: "completed", txHash: "hashA"}` because `findMatchingWithdrawal`'s `.find()` returns the first `bera.omft.near` entry regardless of which `WithdrawalIdentifier.index`/destination was queried — proving the misattribution.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
