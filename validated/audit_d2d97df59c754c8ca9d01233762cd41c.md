### Title
Missing zero-address validation on order beneficiary allows permanent loss of escrowed native token / fill payouts - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` never validates that `order.output.beneficiary` (or `order.user`, used as the refund beneficiary) is non-zero before using it as the destination of a native-token transfer or ERC20 transfer. `_sendValue`, used to release escrowed native ETH on fill/refund/cancel, performs a raw `.call{value: amount}("")` to the beneficiary address with no zero-address check, and this low-level call succeeds silently even when `to == address(0)`, unlike a standard ERC20 `_transfer`/`_mint` which reverts on the zero address.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` (and the tron/sdk mirrors) accepts an arbitrary `PaymentInfo.beneficiary` supplied by the user with no validation: [1](#0-0) 

That `beneficiary` (or, in cancellation, `order.user`) later flows unchecked into `_withdraw`, which decodes it to an `address` and, for native-token (`token == address(0)`) entries, calls `_sendValue(beneficiary, amount)`: [2](#0-1) 

`_sendValue` itself performs a bare low-level call with no destination check: [3](#0-2) 

The same unchecked beneficiary is used directly in `_fillSameChain` (`IntrinsicIntents.sol`) and `_fillCrossChain` (`ExtrinsicIntents.sol`) to pay out native ETH to `beneficiary` on a fill: [4](#0-3) [5](#0-4) 

Unlike ERC20 transfers (OpenZeppelin's `_transfer`/`safeTransfer` to `address(0)` reverts), a raw `address(0).call{value: amount}("")` succeeds — there is no contract code check and no revert — so any native-token escrow release, refund, or fill payout addressed to `address(0)` is executed successfully and the ETH is irrecoverably lost.

This is reachable by any unprivileged party: a user who (by error, or a malicious/buggy front-end/SDK integration) submits `placeOrder` with `output.beneficiary = bytes32(0)` for a native-token output order will have their escrow, once filled/cancelled, sent to `address(0)` and burned. Likewise, a solver providing native ETH output during `fillOrder` against such an order pays the beneficiary (address(0)) directly and that ETH is lost as well.

### Impact Explanation
Successful triggering results in permanent, irrecoverable loss of native token funds — escrowed user deposits or solver-provided fill payouts sent to `address(0)` cannot be retrieved by any actor, including governance. This satisfies the "permanent freezing/loss of funds" bar for Medium severity. It does not enable theft of others' funds or protocol insolvency, and for ERC20 outputs the standard token-level zero-address revert already prevents the loss, limiting the blast radius to native-ETH-denominated legs of orders (same-chain fill, cross-chain fill, refund, and cancel-refund paths that use `_sendValue`).

### Likelihood Explanation
Likelihood is driven entirely by user/integration error since there is no economic incentive for an attacker to grief themselves. However, `placeOrder` is a completely permissionless, single-transaction call with attacker/user-controlled struct fields, and no client-side or on-chain guard exists at any layer (contract, SDK type, or tests) that rejects a zero beneficiary for native-ETH orders — the docs and tests reviewed only cover non-zero beneficiaries by convention, not by enforcement. A single malformed transaction (fat-fingered address encoding, buggy integration, or bytes32 encoding bug when packing an address) is sufficient.

### Recommendation
Add explicit zero-address validation at the point beneficiaries are established/consumed:
1. In `placeOrder`, revert if `order.output.beneficiary == bytes32(0)` (and, if refunds use `order.user`, that is already forced to `msg.sender` so it is safe).
2. Defense-in-depth: in `_sendValue` (or at its call sites in `_withdraw`, `_fillSameChain`, `_fillCrossChain`), revert if `to == address(0)` before attempting the native transfer, so any future caller path is protected even if upstream validation is missed.

### Proof of Concept
1. User calls `placeOrder` with an input token (e.g., USDC) and an output leg where `output.assets[0].token = bytes32(0)` (native ETH) and `output.beneficiary = bytes32(0)`.
2. A solver calls `fillOrder` (same-chain) providing the required native ETH amount; `_fillSameChain` computes `beneficiary = address(uint160(uint256(0))) = address(0)` and executes `beneficiary.call{value: beneficiaryTotal}("")`, which succeeds, permanently burning the solver's ETH.
3. Alternatively, if the order is cancelled instead of filled, `_withdraw` releases the escrowed native ETH input to `beneficiary = address(0)` via `_sendValue`, permanently burning the user's own escrowed ETH with no revert and no recovery path.
