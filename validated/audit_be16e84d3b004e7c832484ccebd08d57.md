## Analysis: Webhook Identity Fields Not Bound to HMAC



### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and passed unmodified into the app's webhook handler. Because these identity fields are not part of the signed content, a `(body, hmac)` pair captured from one legitimate webhook delivery can be replayed with different `shop-domain`/`topic` headers and will still pass `Utils::HmacValidator.validate`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from headers that are never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` trusts this validation and then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as the tenant-identifying metadata: [4](#0-3) 

The binding that should hold is: `hmac_valid(body) == true` should imply `shop_header == shop_that_actually_produced_body`. In reality, `hmac_valid` only certifies the body bytes came from a holder of the secret at some point in time — it says nothing about which `shop-domain`/`topic`/`webhook-id` header accompanies that body. Any party who has legitimately received one webhook delivery (e.g., an attacker who installed the app on their own store) possesses a valid `(raw_body, hmac)` pair signed with the app's real secret. That party can resend the exact same body and HMAC to the app's public webhook endpoint while substituting a different `shop-domain` header (and/or `topic`/`webhook-id`), and the HMAC check still passes because the header values were never part of the signed content.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (built from `request.shop`) to decide which merchant record to update (a documented, expected usage pattern per `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`), an attacker can inject an HMAC-valid payload under an arbitrary victim shop domain, causing state changes, cache poisoning, or data confusion across tenants — a cross-tenant integrity issue within this gem's own trust boundary (HMAC validation is supposed to be the authenticity anchor for the whole webhook, not just the byte content).

### Likelihood Explanation
Exploitation requires no knowledge of `api_secret_key` — only capture of a single legitimate webhook delivery, which any developer/merchant with the app installed on their own store can obtain trivially (Shopify sends real webhooks to the registered endpoint for every installed shop). Replaying it with a modified `shop-domain` header against the same public endpoint is straightforward once one valid `(body, hmac)` sample is captured.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload, so that a valid signature certifies the full tuple of (shop, topic, body) rather than the body alone.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's real secret) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures `(B, H)` from this delivery.
3. Attacker POSTs to the app's public webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `Utils::HmacValidator.validate` re-derives the HMAC from `B` alone, finds it matches `H`, and `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` — even though `victim.myshopify.com` never produced or authorized this payload.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
