### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, but the `shop` value that is handed to the app's webhook handler is read from an unauthenticated HTTP header, so the two identities are never bound together.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate_signature` computes/verifies the HMAC solely over that signable string against `Context.api_secret_key` [4](#0-3) . The `shop` value used by the rest of the pipeline, however, comes from the `shop-domain` header, which is never included in the signed bytes: `def shop; T.cast(shopify_header("shop-domain"), String); end` [5](#0-4) .

`Registry.process` validates only the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler: `raise ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [6](#0-5) . There is no check that the signed body actually corresponds to the shop asserted in the header.

Because `api_secret_key` is a single value shared across every shop that installs the app (configured once via `Context.setup`, not per-tenant) [7](#0-6) , any HMAC that validates for one installed shop's webhook is cryptographically valid for **any** shop under the same app. This breaks the identity binding: `shop authenticated by HMAC(raw_body, api_secret_key)` ≠ `shop asserted via unauthenticated shop-domain header and passed downstream`.

### Impact Explanation
An attacker who legitimately installs the target app on their own shop can capture one genuine, correctly-signed webhook delivery (body + HMAC) that Shopify sends them. They can then resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will treat the HMAC as valid (it only checks the body, which is unchanged) and will invoke the handler with `data.shop` set to the victim's domain and attacker-controlled `data.body`. Any app that uses `data.shop` to look up/update per-tenant records (the documented usage pattern shown in `docs/usage/webhooks.md`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will act on forged, attacker-supplied content attributed to another merchant's tenant — a cross-tenant data-integrity/write bypass entirely from an unprivileged internet user with only their own low-privilege app installation.

### Likelihood Explanation
Moderate-to-high: any user can install a public app on their own development/free shop to obtain one valid signed webhook, then replay it against the shared endpoint with a forged shop header — no access token, `client_secret`, or privileged account is required, only a normal app installation available to any Shopify merchant.

### Recommendation
Bind `shop` to the signed payload before trusting it: e.g., require apps to look up an active, previously-registered session for the asserted shop and cross-check it against install state, or extend the signable string/verification to include the header-derived shop, or validate the `shop` domain against a value obtained from an authenticated source (such as verifying the shop is associated with a webhook ID previously registered for that specific shop via the GraphQL API) rather than trusting the raw header value used only to authenticate the byte-identical body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, subscribing to a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for `Context.api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same `B` and `H` to the app's webhook endpoint but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate`, which only recomputes HMAC over `B` and succeeds because `B`/`H` are unchanged [8](#0-7) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, and the host app processes it as authentic data for the victim's tenant [9](#0-8) .
