### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop-domain`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers — none of which are covered by that signature — to route and identify the tenant for the event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, completely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)` — which calls `request.to_signable_string` (body only) and `request.hmac` — and, once that body-only check passes, immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` performs a strict `OpenSSL.secure_compare` of the computed vs. received HMAC of the signable string only: [4](#0-3) 

The root cause mirrors the reported bug class exactly: the identity binding the app relies on (`request.shop == the shop the HMAC was computed for`) is never enforced. The HMAC only proves "this body was signed with this app's `client_secret`" — since `client_secret` (and therefore the HMAC key) is per-app, not per-shop, that proof holds equally for every shop that has installed the app. The `shop-domain` header is an unauthenticated side-channel value that the gem's own documentation instructs handler authors to trust as "The shop domain of the webhook": [5](#0-4) 

### Impact Explanation
Any unprivileged user who can install the app on their own store (a normal, low-privilege action) can capture a legitimately-signed webhook body+HMAC pair addressed to their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (a victim shop) and/or `X-Shopify-Topic` header. Because `Registry.process` only re-verifies the HMAC over the body, the forged request passes verification, and the handler receives `WebhookMetadata` claiming to originate from the victim shop: [6](#0-5) 

Depending on how the host app acts on `data.shop` (e.g. updating shop records on `shop/redact`, `customers/redact`, or business-logic topics keyed by shop), this enables cross-tenant data corruption/impersonation — an attacker-controlled shop can inject events attributed to a shop it does not own, which is a cross-tenant boundary violation stemming directly from this gem's `Request`/`Registry` design.

### Likelihood Explanation
The attacker only needs to install the app on any store they control (or already legitimately use), which is an unprivileged action requiring no leaked credentials, TLS interception, or privileged account. Capturing one real webhook delivery is sufficient to obtain a valid body/HMAC pair, and replaying it with modified headers is trivial once the endpoint is known (the endpoint path is typically documented/predictable per the app's own callback routes).

### Recommendation
Include the identity-critical fields (`shop-domain`, `topic`, and ideally `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload before `Registry.process` trusts them. At minimum, `Webhooks::Request#to_signable_string` should not be limited to `@raw_body`, and `Registry.process` should require the caller to supply/verify an expected shop (e.g. cross-check against a known/installed-shops store) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`) delivered by Shopify with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's `client_secret`.
2. Attacker captures the raw body and the HMAC header value.
3. Attacker sends a POST to the app's webhook endpoint with the same raw body and the same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds (it only checks the body against the secret), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", ...)`, even though the payload never actually originated from `victim-shop`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
