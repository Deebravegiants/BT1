Based on my investigation, I found a valid analog in the Intent Gateway's client-side bid selection logic.

### Title
Multi-output bid auction winner selection falls back to un-normalized raw-amount comparison when tokens lack direct/WETH DEX liquidity, letting a malicious solver's worthless-token bid outrank a legitimate solver's valuable bid - (File: `sdk/packages/sdk/src/protocols/intents/BidManager.ts`)

### Summary
`selectAndExecuteBest`/`sortBids` in `BidManager.ts` picks the "best" solver bid to fill a user's cross-chain intent by valuing each bid's outputs in USD via on-chain DEX quotes. Exactly like the reported `getUsdPrice()` bug, the DEX-quote helper (`quoteTokenToUsdc`) only supports a direct token→USDC pool or a token→WETH→USDC path [1](#0-0) . Whenever any bid or the order itself contains a token outside that path (no listed pool, thin liquidity, or an exotic ERC-20), pricing returns `null` and the code silently falls back to comparing **raw, unnormalized token amounts** across bids of different tokens/decimals [2](#0-1) [3](#0-2) .

### Finding Description
`sortBids` dispatches to `sortMixedOutputs` whenever an order's outputs are not all USDC/USDT [4](#0-3) . `sortMixedOutputs` calls `computeOutputsUsdValue`, which prices each non-stable token via `quoteTokenToUsdc` — direct-to-USDC, else token→WETH→USDC — and returns `null` for the whole basket if *any* token cannot be quoted [5](#0-4) . On `null`, `sortMixedOutputs` unconditionally calls `sortByRawAmountFallback`, which sums raw `bigint` amounts per bid — with no decimal normalization and no price weighting whatsoever — and ranks bids purely by that raw sum [3](#0-2) .

This is a direct analog of the `getUsdPrice()` flaw: pricing "works" only for a narrow set of paths (direct pool or WETH hop), and anything outside that set is treated as unpriceable. But unlike the audited contract (used only for off-chain matchmaking), this logic feeds `selectAndExecuteBest`, which autonomously **selects and submits the winning solver's `UserOperation` on behalf of the user** [6](#0-5) . A solver is an unprivileged actor who freely chooses which output token/amount to bid with; a solver bidding with a token the pricer cannot value (e.g., a brand-new, thinly-traded, or intentionally illiquid ERC-20, or one whose only pool sits a hop beyond WETH) can force the fallback path for the entire bid set. Once in the fallback, a malicious solver can simply state an enormous raw integer amount of a low/no-value or high-decimal token to make its bid's `totalOffered` exceed a legitimate competitor's properly-valued bid, causing `selectAndExecuteBest` to try and execute the malicious bid first.

### Impact Explanation
If the malicious solver's bid passes on-chain simulation (e.g., it does supply the escrow-required amount of *some* accepted output token per `fillOrder`'s checks, just of negligible real value, or abuses decimal mismatches to inflate the raw sum), the user's `SelectSolver` signature is produced and the fill executes against the worthless bid instead of a genuinely valuable competing bid. The user receives outputs worth far less than the escrowed input the solver claims, and a legitimate/fair-value solver is passed over — a direct value-extraction/theft vector against the intent's escrowed funds reachable by any unprivileged solver participating in the auction.

### Likelihood Explanation
Any account can act as a solver and submit a `UserOperation` bid with attacker-chosen output tokens/amounts. Triggering the fallback only requires bidding (or waiting for a competitor's order to include) at least one output token without a configured direct-to-USDC or WETH-hop pool, which is common for newly listed, illiquid, or unlisted tokens. No privileged access or protocol bug on-chain is required — the flaw lives entirely in the client-side ranking heuristic that end users/wallets rely on via `selectBid`/`selectAndExecuteBest`.

### Recommendation
Do not fall back to raw, unnormalized amount comparison across heterogeneous tokens. Either (a) reject/deprioritize bids containing any token that cannot be priced through the supported DEX paths rather than ranking the whole bid set by raw sums, (b) extend `quoteTokenToUsdc` to support additional routing paths (multi-hop, other stable/bridge tokens) as recommended in the original report, or (c) normalize the fallback comparison per-token to the order's own required amount per token (percentage-of-requirement) rather than summing raw quantities across different tokens/decimals, and never let an unpriceable-token bid outrank a bid composed entirely of priceable, in-order tokens.

### Proof of Concept
1. User places a cross-chain intent order requiring output `[100 USDC, 1 WETH]` (mixed, non-stable) on the destination chain.
2. Solver A bids honestly: `[100 USDC, 1 WETH]` — correctly priced by `computeOutputsUsdValue` at full order value.
3. Solver B bids with a newly deployed ERC-20 "SCAM" token that has no USDC pool and no WETH pool, e.g. `[100 USDC, 1e30 SCAM]` (SCAM priced at $0), and a tiny amount of a real output to pass on-chain minimum checks if required.
4. `computeOutputsUsdValue(orderOutputs)` or `computeOutputsUsdValue(bidB.outputs)` throws inside `quoteTokenToUsdc` for SCAM (no direct or WETH-path liquidity) [7](#0-6) , causing `computeOutputsUsdValue` to return `null`.
5. `sortMixedOutputs` falls back to `sortByRawAmountFallback`, which sums raw amounts: Solver B's `1e30` SCAM units dwarfs Solver A's real value, so Solver B's bid sorts first [8](#0-7) .
6. `selectAndExecuteBest` simulates and (if simulation passes) executes Solver B's bid first, causing the user to receive a bid worth far less than Solver A's, or to have the malicious bid attempted/selected ahead of the fair one [9](#0-8) .

	private sortByRawAmountFallback(bids: Bid[], orderOutputs: TokenInfo[]): Bid[] {
		console.log(
			`[BidManager] sortByRawAmountFallback: checking ${bids.length} bid(s) against ${orderOutputs.length} required output(s)`,
		)
		const validBids: { bid: Bid; totalOffered: Decimal }[] = []

		for (const bid of bids) {
			let valid = true
			let totalOffered = new Decimal(0)
			let rejectReason = ""

			for (const required of orderOutputs) {
				const matching = bid.outputs.find((o) => o.token.toLowerCase() === required.token.toLowerCase())
				if (!matching) {
					valid = false
					rejectReason = `missing output token=${required.token}`
					break
				}
				totalOffered = totalOffered.plus(new Decimal(matching.amount.toString()))
			}

			if (!valid) {
				console.warn(`[BidManager] Bid from solver=${bid.solverAddress} REJECTED (fallback): ${rejectReason}`)
				continue
			}

			const totalRequired = orderOutputs.reduce(
				(acc, o) => acc.plus(new Decimal(o.amount.toString())),
				new Decimal(0),
			)

			if (totalOffered.lt(totalRequired)) {
				console.log(
					`[BidManager] Bid from solver=${bid.solverAddress}: partial fill candidate (fallback) ` +
						`(offered=${totalOffered.toString()}, required=${totalRequired.toString()}, ` +
						`covers=${totalOffered.div(totalRequired).mul(100).toFixed(2)}%)`,
				)
			} else {
				console.log(
					`[BidManager] Bid from solver=${bid.solverAddress} ACCEPTED (fallback): totalOffered=${totalOffered.toString()}`,
				)
			}

			validBids.push({ bid, totalOffered })
		}

		validBids.sort((a, b) => b.totalOffered.comparedTo(a.totalOffered))
		return validBids.map(({ bid }) => bid)
	}

	private async computeOutputsUsdValue(
		outputs: { token: HexString; amount: bigint }[],
		chainId: string,
	): Promise<Decimal | null> {
		const configService = this.ctx.dest.configService
		const client = this.ctx.dest.client
		const usdcAddr = configService.getUsdcAsset(chainId)
		const usdcDecimals = configService.getUsdcDecimals(chainId)
		const { asset: wethAddr } = configService.getWrappedNativeAssetWithDecimals(chainId)

		let totalUsd = new Decimal(0)

		for (const output of outputs) {
			const tokenAddr = bytes32ToBytes20(output.token)

			if (this.isStableToken(tokenAddr, chainId)) {
				const decimals = this.getStableDecimals(tokenAddr, chainId)
				totalUsd = totalUsd.plus(new Decimal(output.amount.toString()).div(new Decimal(10).pow(decimals)))
				continue
			}

			try {
				const usdcAmount = await this.quoteTokenToUsdc(
					tokenAddr,
					output.amount,
					wethAddr,
					usdcAddr,
					chainId,
					client,
				)
				totalUsd = totalUsd.plus(new Decimal(usdcAmount.toString()).div(new Decimal(10).pow(usdcDecimals)))
			} catch {
				return null
			}
		}

		return totalUsd
	}

	private async quoteTokenToUsdc(
		tokenAddr: HexString,
		amount: bigint,
		wethAddr: HexString,
		usdcAddr: HexString,
		chainId: string,
		client: IntentGatewayContext["dest"]["client"],
	): Promise<bigint> {
		const isWethOrNative = tokenAddr.toLowerCase() === wethAddr.toLowerCase() || tokenAddr === ADDRESS_ZERO

		if (isWethOrNative) {
			const { amountOut, protocol } = await this.ctx.swap.findBestProtocolWithAmountIn(
				client,
				wethAddr,
				usdcAddr,
				amount,
				chainId,
			)
			if (protocol === null || amountOut === 0n) throw new Error("No WETH→USDC liquidity")
			return amountOut
		}

		// Try direct: token → USDC
		try {
			const { amountOut, protocol } = await this.ctx.swap.findBestProtocolWithAmountIn(
				client,
				tokenAddr,
				usdcAddr,
				amount,
				chainId,
			)
			if (protocol === null || amountOut === 0n) throw new Error("No direct liquidity")
			return amountOut
		} catch {
			// Fallback: token → WETH → USDC
			const { amountOut: wethOut, protocol: p1 } = await this.ctx.swap.findBestProtocolWithAmountIn(
				client,
				tokenAddr,
				wethAddr,
				amount,
				chainId,
			)
			if (p1 === null || wethOut === 0n) throw new Error("No token→WETH liquidity")

			const { amountOut: usdcOut, protocol: p2 } = await this.ctx.swap.findBestProtocolWithAmountIn(
				client,
				wethAddr,
				usdcAddr,
				wethOut,
				chainId,
			)
			if (p2 === null || usdcOut === 0n) throw new Error("No WETH→USDC liquidity")
			return usdcOut
		}
