### Title
Secure-element signature over iris/face biometrics excludes `signup_id`, allowing signature reuse across signup sessions - (File: `src/plans/enroll_user.rs`)

### Summary
The reported Divergence Protocol bug is a classic "unbound parameter" flaw: a value (`startSqrtPriceX96`) that materially affects the outcome of an operation is left out of the identifier (`battle key`) that is supposed to uniquely and immutably characterize that operation, letting an attacker vary the excluded value while keeping the identifier constant, thereby griefing or profiting from the mismatch. The analogous pattern in `orb-core` is the construction of the secure-element signature during user enrollment: the signed payload commits to the iris/face codes and the orb+user identity, but does **not** commit to the `signup_id` that is submitted alongside it and used by the backend to track/complete that specific signup. This decouples the cryptographic attestation from the identifier that binds it to a particular signup session.

### Finding Description
`make_signature` builds the SHA-256 digest that is passed to the secure element for signing: [1](#0-0) 

The digest is built from `ORB_ID`, `user_qr_code.user_id`, and the pipeline's iris/face code fields only — the `signup_id` is never mixed into the hashed payload.

In `Plan::run`, the signature is computed independently of `signup_id`: [2](#0-1) 

`signup_id` is generated separately (by the orb, via `SignupId::new`) and is sent to the backend alongside the signature as an independent, unauthenticated field: [3](#0-2) 

Because the secure element's signature never binds the `signup_id` (the "battle key" analog that identifies a particular signup transaction end-to-end, and is later used by `signup_poll::request(&signup_id)` to track/complete the enrollment), the same signed biometric attestation is valid for a request carrying *any* `signup_id` value. This mirrors the `startSqrtPriceX96` issue exactly: the value that ties a cryptographic commitment to a specific transaction/session identifier is excluded from what gets bound/signed, so the identifier can be freely substituted after the commitment is made.

### Impact Explanation
If the request-construction path (or an intermediary between the secure element and the backend request, e.g. `signup_post::request`) is compromised or racing/duplicated, the same iris-code signature can be replayed with a different `signup_id`. Since the backend correlates polling/completion state strictly by `signup_id` (`signup_poll::request(&signup_id)`), this creates a cross-signup state-bleed condition: one biometric signing operation could be attributed to, or replayed against, more than one signup session, undermining the guarantee that a signed biometric attestation corresponds 1:1 to a single tracked signup.

### Likelihood Explanation
Exploitation requires the ability to influence or duplicate the outbound `signup_post::request` call with an alternate `signup_id` while reusing an already-obtained signature — a scenario more plausible in retry/duplicate-request logic (the code already performs up to `RETRIES_COUNT` retries with the same signature and could, with a code defect or IPC-boundary issue, be re-triggered with a differing `signup_id`) than via network-layer QR spoofing. It is a design gap rather than a directly internet-exploitable bug, hence moderate likelihood, but it represents a real deviation from binding the attestation to the transaction identifier.

### Recommendation
Include `signup_id` (and ideally `s3_region`) in the data hashed and signed by the secure element in `make_signature`, so the resulting signature cryptographically commits to the specific signup transaction it is meant to authenticate — analogous to the report's recommendation to fold `startSqrtPriceX96` into the battle key.

### Proof of Concept
Conceptual reproduction path (no external tooling required, purely from code inspection):
1. `Plan::run` calls `make_signature(&user_qr_code, &pipeline)` which hashes only `ORB_ID`, `user_id`, and iris/face codes.
2. `signup_id` is generated independently via `SignupId::new(...)` and passed to `signup_post::request` as a separate, unsigned argument.
3. Because the signature never covers `signup_id`, any code path that resubmits the same `(signature, user_qr_code, pipeline)` tuple with a different `signup_id` (e.g., on retry logic, or a bug reusing cached signature data) produces a request that is indistinguishable, from the signature's perspective, from a legitimate one-time attestation — the backend has no cryptographic means to detect that the signature was not generated for that particular `signup_id`. fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
