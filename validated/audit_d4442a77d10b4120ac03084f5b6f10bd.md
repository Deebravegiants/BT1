### Title
Unprivileged users can permanently freeze a market by driving the borrow index accrual into an `i128` overflow panic - (File: tests/test-harness/tests/controller/large_positions_and_long_horizons.rs)

### Summary
The bug class of CVE-2016-6132 is "crafted input drives parsing into an out-of-bounds read → crash/DoS". The analog on XOXNO Lending is "attacker-controlled book state drives fixed-point index accrual past the `i128` value ceiling → panic on every verb → permanent market freeze". All arithmetic in the protocol is checked and panics (`MathOverflow`) rather than saturating, so a market whose scaled debt value can no longer fit in `i128` traps inside accrual. Since every entrypoint accrues first, a single unprivileged supplier/borrower pair can push a market past this cliff and freeze it forever.

### Finding Description
Interest accrual and index unscaling in the pool compute `scaled * index / RAY`-style products that are checked against `i128` bounds. `fp::checked_sub_nonneg` and `mul_div`/`mul_div_half_up` panic with `GenericError::MathOverflow` on overflow (`common/src/math/fp.rs:13-25`, `common/src/math/fp_core.rs:108-143`), and `scaled_to_original` in the pool's cache/scale path applies the same checked arithmetic to `scaled_debt * borrow_index`.

The market protects the borrow index with `MAX_BORROW_INDEX_RAY`, but that cap is checked on the *index* (a RAY-scaled ratio), while the overflow occurs on the *value* `scaled_debt * index`. For a large book at sustained high utilization on a steep interest-rate curve, the index grows past ~170x while `scaled_debt` is near the cap, so `scaled_debt * index` overflows `i128` before the index ever reaches `MAX_BORROW_INDEX_RAY`. The cap therefore never engages.

The repository's own test proves this end-to-end (`large_positions_and_long_horizons.rs:316-361`):

- `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` supplies `BILLION * 10^18` of an 18-decimal asset, borrows 98% of it, and advances time. Within the tested horizon `update_indexes` fails with `MATH_OVERFLOW`.
- After the failure, `last.borrow_index < MAX_BORROW_INDEX_RAY` — the index cap never engaged.
- `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both fail with `MATH_OVERFLOW`: "the market is frozen: exits and repayments accrue first and hit the same panic."

### Impact Explanation
Permanent freezing of funds and a contract unable to operate. Once the value ceiling is hit, accrual panics inside every state-changing path that touches the market — `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `recapitalize`, `update_indexes` — because each accrues the market before doing anything else. All supplier principal in that market is unrecoverable, and liquidations cannot run, so any unhealthy debt in the market becomes unclosable bad debt.

### Likelihood Explanation
Reachable by a single unprivileged address with no privileged role: the attacker supplies a large principal into one market and borrows it to ~98% utilization (the test uses two accounts, but one address with sufficient collateral can hold both sides). The freeze then requires only passive waiting — no further attacker action — and, once triggered, cannot be undone by governance since `recapitalize` and `force_socialize_bad_debt` also accrue first. The capital requirement is large (the test uses billion-scale deposits at the steep segment of the XLM curve), so exploitation is capital-bound rather than free, but it is deterministic and requires no oracle manipulation, leaked keys, or admin access. This is not a fail-closed revert of a single transaction: the panic permanently wedges all state for the market.

### Recommendation
Engage `MAX_BORROW_INDEX_RAY` against the *product* bound, not just the index bound: cap accrual when `scaled_debt * borrow_index` would approach `i128::MAX / WAD`-ish headroom, e.g. clamp the index to `i128::MAX / scaled_debt` (rounded down to RAY units) so `scaled_to_original` can never overflow. Alternatively, make accrual saturate the index and flag the market for admin resolution rather than panicking, so `repay`/`withdraw`/`liquidate`/`recapitalize` remain callable after the cliff.

### Proof of Concept
The in-repo test demonstrates the trigger with unprivileged entrypoints:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);            // unprivileged supply
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);               // ~98% utilization

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// e is MathOverflow; last.borrow_index < MAX_BORROW_INDEX_RAY (cap never engaged)
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Sequence: (1) attacker supplies principal and borrows ~98% via `supply`/`borrow`; (2) time accrues the index along the steep curve segment until `scaled_debt * index` overflows `i128` in `scaled_to_original`; (3) the next `update_indexes` (or any verb) panics with `MathOverflow`, and every subsequent `supply`/`withdraw`/`repay`/`liquidate` on the market panics identically, permanently freezing all supplier funds.

Uncertainty note: I could not fully trace `scaled_to_original` in `pool/src/cache/scale.rs` within the iteration budget; the mechanism is inferred from the test's assertions and the checked-arithmetic helpers in `common/src/math/`. The repo treats this cliff as a discovered property (the test comment flags the formulas doc bound as wrong), which may make it a known/accepted limitation rather than a novel finding.
