### Title
Webhook HMAC validation does not bind the `shop` (and `topic`/`webhook-id`) header used for tenant identification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC solely over that string [2](#0-1) . The `shop` value used downstream to attribute the webhook to a tenant, `request.shop`, is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never included in the signed bytes [3](#0-2) . `Registry.process` verifies only the body HMAC and then forwards `request.shop` unchanged to the host app's handler as the trusted tenant identity [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop header value == shop covered by the verified HMAC`. In this gem it does not — the HMAC only authenticates the request body bytes, not the `shop-domain` header that `WebhookMetadata.shop` exposes to the handler. Anyone who can obtain one genuine, validly-signed webhook delivery for a shop they control (any free/dev store; no privileged credentials needed) can present that exact body + HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. Because `HmacValidator.validate` only recomputes and compares the digest of `@raw_body` [1](#0-0) [5](#0-4) , the tampered header does not invalidate the signature, and `Registry.process` accepts the request and dispatches it with the attacker-chosen `shop` [4](#0-3) .

This is the direct analog of the report's bug class: an implicit typecast covers "the wrong bytes" and the check silently accepts a value it never actually validated. Here the HMAC covers the wrong field set — it verifies bytes it parsed (the body) but the gem acts on bytes it never verified (the `shop` header) as if they carried the same trust level.

### Impact Explanation
`WebhookMetadata.shop` is the only tenant-identifying field the gem hands to the host application's webhook handler [6](#0-5) . Any app that uses this value (as the API intends it to be used, since it is the only shop identifier the gem provides for webhook processing) to key persistence, session lookup, or business logic will attribute attacker-supplied, HMAC-"verified" webhook data to a victim tenant of the attacker's choosing — a cross-tenant integrity/confidentiality break requiring no credentials, tokens, or privileged access, only a free Shopify development store and the ability to send an HTTP request to the app's public webhook URL.

### Likelihood Explanation
High. Obtaining a genuine signed webhook is trivial and free (install the app on any dev store and trigger any subscribed event); resending it with a modified header requires no special access and no knowledge of `api_secret_key`. The check that is bypassed (`Utils::HmacValidator.validate`) is the sole authentication mechanism in `Registry.process` [7](#0-6) ; nothing else in the gem constrains `request.shop`.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified by `HmacValidator`, or have `Registry.process` independently cross-check `request.shop` against a value bound to the HMAC-covered payload (e.g., verify shop identity server-side against the known session/shop rather than trusting the header). At minimum, document prominently that `WebhookMetadata.shop` is unauthenticated so host applications do not use it as a trust boundary.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (free dev store) and triggers a subscribed webhook (e.g. `orders/create`), capturing the exact raw body `B` and the resulting valid header `x-shopify-hmac-sha256: H` that Shopify sent to the app's endpoint.
2. Attacker replays an HTTP POST to the same app webhook endpoint with body `B` unchanged, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` [2](#0-1)  — validation passes despite the spoofed shop header.
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ..., ...)` [6](#0-5)  and processes attacker-controlled data under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
