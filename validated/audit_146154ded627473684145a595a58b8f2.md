### Title
Withdrawal status forced to "completed" for destination chains not covered by `describeWithdrawal`'s chain checks - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal()` decides how to determine a withdrawal's on-chain hash/finality by branching on the destination `ChainKind`. Any destination chain that is not EVM, `Sol`, `Fogo`, `Strk`, `Aptos`, or a UTXO chain (`Btc`/`Zcash`) falls into a catch-all `else` branch that unconditionally reports `{ status: "completed", txHash: null }`, without ever checking whether the transfer actually finalized on the destination chain.

### Finding Description
`describeWithdrawal` fetches the transfer record from the Omni Bridge indexer and then computes `txHash` based on the destination chain type: [1](#0-0) 

```
const destinationChain = getChain(transfer.recipient as OmniAddress);
let txHash = null;
if (
    isEvmChain(destinationChain) ||
    destinationChain === ChainKind.Sol ||
    destinationChain === ChainKind.Fogo ||
    destinationChain === ChainKind.Strk ||
    destinationChain === ChainKind.Aptos
) {
    txHash = transfer.finalised?.transaction_hash;
} else if (isUtxoChain(destinationChain)) {
    txHash = ... // BTC/Zcash-specific handling
} else {
    return { status: "completed", txHash: null };
}
if (!txHash) {
    return { status: "pending" };
}
return { status: "completed", txHash };
```

For every enumerated chain kind, the code correctly waits for `transfer.finalised?.transaction_hash` (or the UTXO-specific equivalent) before reporting `"completed"`. But the `else` branch — reached for any `ChainKind` not in that explicit list (e.g. `ChainKind.Near` or any additional chain kind supported by `@omni-bridge/core`/the destination-chain resolver `getChain` and `caip2ToChainKind`/`chainKindToCaip2` mappings in `omni-withdraw-params.ts` and `omni-bridge-utils.ts` that isn't mirrored here) — skips the finality check entirely and reports `"completed"` immediately, with `txHash: null`, as soon as the indexer has merely recorded the transfer (i.e., as soon as `transfer != null && transfer.recipient != null`, checked earlier at line 700).

This breaks the equality that should hold between "status reported by the SDK" and "actual on-chain outcome of the withdrawal." The destination chain for a withdrawal is attacker/caller-selectable via `routeConfig.chain` on `withdrawalParams` (see `targetChainSpecified`/`caip2ToChainKind` in `omni-bridge.ts` lines 140-231), so an unprivileged caller can pick any destination chain value that is mapped by `caip2ToChainKind` but not one of the five hard-coded chain kinds (nor a UTXO chain) checked in `describeWithdrawal`, causing the SDK to falsely declare the withdrawal "completed" the moment the indexer merely acknowledges the transfer request — well before the destination-chain transaction is actually finalized (or possibly before it happens at all, e.g., if the relayer fails to submit it).

### Impact Explanation
An integrator that relies on `sdk.describeWithdrawal`-derived status to gate downstream actions (e.g., crediting a user's off-chain balance, releasing a corresponding asset, or allowing a follow-up withdrawal) would treat the withdrawal as settled prematurely. Because `txHash` is `null` in this branch, there is no way to independently verify on-chain settlement from the returned data, so a double-credit/double-release scenario is possible if the destination chain transfer later fails, is delayed, or never confirms. This matches the "status ... report[ed] that is not the on-chain outcome" / "a status or hash misreport making an integrator credit or refund twice" impact class (High).

### Likelihood Explanation
Reachable by any caller of the SDK who selects a `routeConfig.chain` mapped to a `ChainKind` outside the five explicitly special-cased kinds and the two UTXO kinds — no privileged access, relayer cooperation, or malicious third party is required; it's a straightforward gap in an exhaustive `if/else` over an externally-extensible enum (`ChainKind` from `@omni-bridge/core`). The exact set of currently-affected chain kinds could not be fully enumerated from the in-scope code (the `ChainKind` enum itself lives in the external `@omni-bridge/core` package), but `ChainKind.Near` is confirmed reachable via `chainKindToCaip2(ChainKind.Near)` returning `null` in tests, and any future chain kind added to `@omni-bridge/core`/`CHAIN_MAPPINGS` without a corresponding update to this `if/else` chain would silently fall into the same unsafe default.

### Recommendation
Replace the catch-all `else` branch with a fail-closed default: return `{ status: "pending" }` (or throw/log an "unsupported chain" error) for any destination chain that isn't explicitly recognized, and only report `"completed"` once a verified finalized transaction hash (or equivalent proof) is available for that chain kind. Add exhaustiveness checking (e.g., a `never` type assertion) over `ChainKind` so that adding a new chain kind to the dependency forces an explicit decision here instead of silently reporting completion.

### Proof of Concept
1. Initiate a withdrawal via `IntentsSDK`/`OmniBridge` with `withdrawalParams.routeConfig.chain` set to a CAIP-2 chain that `caip2ToChainKind` maps to a `ChainKind` other than `Eth`/other EVM kinds, `Sol`, `Fogo`, `Strk`, `Aptos`, `Btc`, or `Zcash` (e.g. a chain kind that maps through `getChain(transfer.recipient)` to `ChainKind.Near` or any newly-added chain kind not yet special-cased here).
2. Submit the withdrawal intent so the Omni Bridge indexer records the transfer request (`omniBridgeAPI.getTransfer` returns a non-null transfer with `recipient` set) — this happens as soon as the relayer/indexer sees the transfer, before actual destination-chain settlement.
3. Call `bridge.describeWithdrawal({...})` (or `sdk.waitForWithdrawalCompletion`/equivalent status API built on it).
4. Observe the function returns `{ status: "completed", txHash: null }` immediately, even though no destination-chain transaction has occurred, letting a caller/integrator treat the withdrawal as finished and act on it (e.g., credit funds) prematurely.
