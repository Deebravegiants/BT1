### Title
Webhook shop/topic/id headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The shop, topic, API version and webhook-id are all taken from HTTP headers that are never included in the signed content, so the gem trusts these header values even though they carry no cryptographic binding to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over exactly that signable string and compares it to the `hmac` value the request exposes: [2](#0-1) 

`Registry.process` only checks this HMAC before dispatching to the handler with `request.shop`, `request.topic`, and `request.webhook_id`, all of which are read straight from headers: [3](#0-2) [4](#0-3) 

The broken identity binding is:
`verified_bytes (HMAC-signed content) = raw_body` **≠** `attributed_tenant/topic = headers["shopify-shop-domain"/"shopify-topic"/"shopify-webhook-id"]`.

Because the shop, topic, and webhook id are never part of the signed payload, any request whose body+HMAC pair is valid for the app's shared `client_secret` will pass verification regardless of what shop/topic headers accompany it. In this codebase, that (body, hmac) pair is not a secret an attacker needs to already possess — Shopify's own "Send test notification" feature (available to any merchant who installs the app, i.e. an unprivileged tenant of the app) produces a documented, fixed JSON body signed with the real `client_secret`, deliverable to the app's public webhook endpoint. This gives an unprivileged app-installing user a valid `(raw_body, hmac)` pair which they can then POST directly to the webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header pointing at a victim tenant, since `HmacValidator.validate` never checks those headers.

### Impact Explanation
This is a cross-tenant boundary break: the handler in the host application receives `WebhookMetadata` (built from unverified `request.shop`/`request.topic`) and will act as if the event legitimately originated for the spoofed shop. [5](#0-4) 
Depending on the handler wired up by the host app (mandatory GDPR/uninstall handlers, order-processing handlers, etc.), this can cause data to be deleted, sessions revoked, or business logic executed for a victim tenant triggered by another tenant's forged request — a Critical cross-tenant access impact per the classification the gem's own HMAC check is supposed to prevent.

### Likelihood Explanation
Any merchant who installs an app built on this gem can obtain a validly-signed webhook body via Shopify's built-in test-notification mechanism without needing the app's `client_secret`, an access token, TLS interception, or local access — only knowledge of the public webhook URL, which is typically fixed and discoverable. The header spoof itself is a trivial unauthenticated HTTP request forgery.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the verified payload (e.g., require them to be re-derived only from data embedded in the verified JSON body, never from raw headers) before constructing `WebhookMetadata` in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com`.
2. From Shopify Admin → Notifications → Webhooks, attacker triggers "Send test notification" for a topic (e.g. `orders/create`), capturing the raw JSON body and the `X-Shopify-Hmac-Sha256` value Shopify computed with the app's real `client_secret`.
3. Attacker sends that exact `raw_body` and `hmac` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC — validation succeeds. [6](#0-5) 
5. The handler registered for that topic executes with `shop: "victim-shop.myshopify.com"`, `topic` and `webhook_id` fully attacker-controlled, even though none of these were part of the signed content. [7](#0-6)
