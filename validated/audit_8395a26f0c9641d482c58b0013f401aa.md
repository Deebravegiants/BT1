### Title
Webhook HMAC signs only `@raw_body`, so attacker-replayable topic/shop/api-version/webhook-id headers are trusted as authenticated by `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Webhooks::Request#shopify_header` reads `topic`, `shop-domain`, `api-version`, and `webhook-id` straight from attacker-suppliable HTTP headers with no cross-check against the HMAC. `Registry.process` validates only the HMAC over the body and then dispatches on `request.topic` and passes `request.shop` into `WebhookMetadata` unauthenticated, breaking the binding that "the HMAC-authenticated request" and "the topic/shop the app acts on" are the same identity.

### Finding Description
The invariant that should hold is: `authenticated(body) == authenticated(topic, shop, api_version, webhook_id)`, i.e., every field the app trusts as coming from Shopify for a given HMAC-valid request should itself be covered by that HMAC. In this code:

- `Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Webhooks::Request#shopify_header` prefers `shopify-<name>` over `x-shopify-<name>` and is the sole source for `topic`, `shop`, `api_version`, and `webhook_id`, none of which are re-checked against the HMAC [2](#0-1) .
- `Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header [3](#0-2) .
- `Registry.process` validates only that HMAC, then dispatches using `request.topic` for handler lookup and forwards `request.shop`, `request.api_version`, `request.webhook_id` into `WebhookMetadata` as if they were authenticated [4](#0-3) .

Exploit flow: an attacker installs the target app on their own development shop (permitted per the rules) and receives a genuine webhook delivery — a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's real `api_secret_key`. Because the app's webhook endpoint is a public HTTP endpoint, the attacker can POST directly to it (bypassing Shopify's delivery infrastructure entirely — no TLS interception needed) replaying the exact same body and HMAC header, but with `X-Shopify-Topic`, `X-Shopify-Shop-Domain`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` changed to arbitrary values. Since `to_signable_string` never includes these headers, `HmacValidator.validate` still returns `true`, and `Registry.process` will dispatch to whichever handler is keyed by the forged `topic`, and hand the forged `shop` value to that handler as if Shopify itself vouched for it.

No existing guard closes this gap: `ShopValidator.sanitize!` is not called anywhere in the webhook request path (confirmed by search — it's only used in OAuth/token-exchange flows), and `Registry.process` performs no independent verification that `request.shop`/`request.topic` match the shop/topic that actually produced the signed body.

### Impact Explanation
Downstream app code (outside this gem, but foreseeably built exactly as documented) typically uses `WebhookMetadata#shop` to look up that shop's persisted offline access token/session and `WebhookMetadata#topic` to select handler behavior (including the mandatory `customers/redact`/`shop/redact` handlers). Because both fields are unauthenticated relative to the HMAC, an attacker holding one valid `(body, hmac)` pair for their own shop can impersonate an arbitrary victim shop identity and arbitrary topic for that single signed payload, causing the app to perform privileged, token-bearing actions (e.g., data deletion, resource mutation via the victim's Admin API access token) attributed to a shop the attacker does not control. This is a cross-tenant identity confusion with the potential to reach Critical impact (misuse of a merchant's Admin API access token) if the host app derives session/token lookup from `WebhookMetadata#shop` — which is the documented pattern for this gem's webhook handlers.

### Likelihood Explanation
Preconditions: the attacker needs (a) their own dev shop with the app installed (freely obtainable, matches the allowed attacker capability), (b) at least one genuine webhook delivery from that shop (trivial — trigger any subscribed event), and (c) the app's webhook endpoint reachable directly over HTTP (true for any publicly deployed app, since Shopify delivers webhooks over the open internet to a configured URL). No secrets, no TLS interception, and no victim cooperation are required. This is fully repeatable against any topic/shop value for as long as the attacker retains one valid signed body.

### Recommendation
Include the security-relevant headers (`topic`, `shop-domain`, `api-version`, `webhook-id`) in the HMAC-signable material, or otherwise independently and cryptographically bind them to the body before trusting them in `Registry.process` and `WebhookMetadata`. At minimum, document/require host apps to independently authenticate `shop` (e.g., via `ShopValidator.sanitize!` plus a session lookup, not a raw header) before using it for token-scoped operations, and treat `Registry.process`'s dispatch topic as untrusted unless it round-trips through the signed payload.

### Proof of Concept
```ruby
# test/webhooks/registry_replay_test.rb
require "test_helper"

class RegistryHeaderReplayTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear

    @handler_a = mock_handler
    @handler_b = mock_handler
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", delivery_method: :http,
      path: "/wh", handler: @handler_a)
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "customers/redact", delivery_method: :http,
      path: "/wh", handler: @handler_b)
  end

  def test_hmac_does_not_bind_topic_header
    raw_body = '{"id":1}'
    hmac = OpenSSL::HMAC.base64digest(OpenSSL::Digest.new("sha256"),
      ShopifyAPI::Context.api_secret_key, raw_body)

    # Original, legitimately-signed request for orders/create.
    original_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "attacker-dev.myshopify.com",
      "x-shopify-webhook-id" => "1",
      "x-shopify-api-version" => "2024-01",
    }
    request_original = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: original_headers)
    ShopifyAPI::Webhooks::Registry.process(request_original)
    assert @handler_a.handled? # expected, legitimate dispatch

    # Replay identical body+hmac, forged topic/shop headers.
    forged_headers = original_headers.merge(
      "x-shopify-topic" => "customers/redact",
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
    )
    request_forged = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

    # Assert the binding is broken: HMAC still validates, dispatch honors forged topic/shop.
    assert ShopifyAPI::Utils::HmacValidator.validate(request_forged)
    ShopifyAPI::Webhooks::Registry.process(request_forged)
    assert @handler_b.handled_with_shop?("victim-shop.myshopify.com")
  end
end
```
Assertions on both sides of the binding: (1) `HmacValidator.validate(request_forged)` returns `true` despite `topic`/`shop` differing from the originally signed request — proving the HMAC covers body only; (2) `Registry.process` dispatches to `customers/redact`'s handler with `shop == "victim-shop.myshopify.com"`, a value never authenticated by the HMAC, demonstrating the divergence between "HMAC-authenticated request" and "topic/shop the app acts on."
