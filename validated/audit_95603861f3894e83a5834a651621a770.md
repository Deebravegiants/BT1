Audit Report

## Title
ERC20Transactor: Strict ABI-decoded bool assumption on `transfer()` breaks XCM deposit/withdraw for non-standard ERC20 tokens (USDT-class) - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call `transfer()` on an arbitrary ERC20 contract via `pallet_revive::Pallet::<T>::bare_call`, then require the returned bytes to strictly ABI-decode as `bool` using `IERC20::transferCall::abi_decode_returns_validate`. Non-standard ERC20 tokens that return no data on `transfer()` (the canonical example being mainnet USDT) will cause this decode to fail, and the code maps any decode failure to `XcmError::FailedToTransactAsset`, permanently breaking XCM deposits/withdrawals for that asset.

## Finding Description
Both functions perform a `bare_call` to the target contract's `transfer()` and, when the call does not revert, immediately attempt a strict ABI decode of the return bytes as `bool`: [1](#0-0) [2](#0-1) 

There is no fallback path treating empty return data as success (as OpenZeppelin's `SafeERC20` does); any decode error is mapped to a hard `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")`, unconditionally failing the transfer even though the underlying on-chain state change (if any) may have succeeded. The code accurately matches the claim's description, and the vulnerability class (interface mandating a `bool` return against a token that omits it) is real and matches the well-known USDT-compatibility issue.

## Impact Explanation
If a backing ERC20 contract behind an XCM asset id routed through `ERC20Transactor` does not return `abi.encode(bool)` from `transfer()` (e.g., a USDT-style contract), every `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` call for that asset fails, causing a complete and permanent denial of service for that asset's XCM in/out transfers. This is a legitimate, concrete in-scope impact (asset transfers permanently broken) if such a token is ever backing an asset through this transactor.

## Likelihood Explanation
The likelihood hinges entirely on how a backing ERC20 contract becomes associated with an XCM asset id via the `Matcher: MatchesFungibles` generic parameter — this mapping is runtime-configuration-defined, not shown to be attacker-controlled or permissionless within the code reviewed. I was unable to confirm, from the available `asset-hub-westend/xcm_config.rs` wiring, whether an unprivileged user can cause a non-compliant contract to be registered as an asset's ERC20 backing, or whether this is strictly a governance/runtime-config decision (i.e., analogous to a chain operator choosing to back an asset with a non-standard token). Without confirming an unprivileged, attacker-triggerable registration path, this does not meet the requirement that "a valid report must be triggerable by an unprivileged user, unless the claim proves privilege escalation from a user path." The report itself concedes this gap ("I was not able to fully verify... whether the Matcher/foreign-asset registration path... is permissionless or governance-gated"), and the burden of proving reachability by an unprivileged actor was not met.

## Recommendation
Adopt SafeERC20-style semantics: treat a non-reverted call with empty return data as success, and only require a strict `bool` decode when return data is non-empty (treating `false` as failure). Apply this uniformly to any other strict `bool`-decoded ERC20 calls made against externally supplied, potentially non-standard ERC20 contracts.

## Proof of Concept
As described in the submission: deploy a `pallet-revive` ERC20-like contract whose `transfer()` returns no data (USDT-style), have it configured as the backing contract for an asset matched by `Matcher`, then submit an XCM program triggering `deposit_asset_with_surplus`/`withdraw_asset_with_surplus` for that asset — the call succeeds on-chain but the transactor incorrectly returns `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")` due to the empty return data failing strict ABI decoding at [3](#0-2) . This PoC path was not independently verified end-to-end (e.g., no test demonstrating unprivileged registration of the malicious contract as an asset backing), leaving the reachability/likelihood question open as noted above.
