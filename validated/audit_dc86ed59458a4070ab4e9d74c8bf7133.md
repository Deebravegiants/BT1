### Title
Accrued interest value overflow permanently freezes a high-utilization market - (File: common/src/rates/index.rs)

### Summary

A large market’s scaled debt is multiplied by the current borrow index during every interest accrual without checking that the resulting total-debt value remains within the protocol’s `i128` arithmetic domain. [1](#0-0)  Once accumulated interest raises the index enough that `borrowed * borrow_index` exceeds `i128::MAX`, `update_indexes`, `withdraw`, `repay`, `liquidate`, and the other market mutations revert before reaching their own logic because they accrue interest first. [2](#0-1)  The existing borrow-index ceiling is applied to the newly computed index, but it does not prevent the debt-value multiplication from overflowing beforehand. [3](#0-2)  The repository’s own long-horizon test demonstrates the resulting permanent market freeze with `MathOverflow`. [4](#0-3) 

### Finding Description

Market supply and debt are stored as scaled RAY shares, while `global_sync` computes each accrual step before committing the updated indexes and revenue. [5](#0-4)  Each accrual calls `calculate_supplier_rewards`, which computes both `borrowed * old_borrow_index` and `borrowed * new_borrow_index` through checked `Ray::mul`. [1](#0-0)  Therefore, even if the newly calculated borrow index is below `MAX_BORROW_INDEX_RAY`, the unscaled debt value can still overflow `i128` when the scaled debt principal is sufficiently large. [3](#0-2) 

`global_sync` executes `accrue_chunk` for every elapsed interval before marking the market accrued. [6](#0-5)  `accrue_chunk` invokes `accrue_step`, which reaches the overflowing supplier-reward calculation before the cache can commit a bounded index. [7](#0-6)  Because every pool mutation first loads the market and synchronizes interest, the same overflow repeats on subsequent calls and prevents all recovery paths that need to mutate the market. [2](#0-1) 

An unprivileged attacker can establish the precondition using `Controller::supply` with a large token position and `Controller::borrow` against separately supplied collateral. [8](#0-7)  Anyone can later trigger the overflow through `Controller::update_indexes`, which forwards the selected `HubAssetKey` to the pool’s owner-gated `update_indexes` entrypoint. [9](#0-8)  The repository’s test uses a one-billion-token, 18-decimal market at 98% utilization and shows that `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow` after sustained accrual. [10](#0-9) 

### Impact Explanation

This permanently freezes all funds and obligations in the affected `(hub, asset)` market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot unwind the position, flash loans and strategy operations touching the market cannot complete, and revenue cannot be claimed because each path performs interest accrual before its operation-specific logic. [2](#0-1)  The pool remains operational for unrelated markets, but the affected market’s cash and position accounting become inaccessible without an out-of-band contract change. [5](#0-4)  This satisfies the permanent freezing-of-funds impact class. [4](#0-3) 

### Likelihood Explanation

The vulnerability requires an unusually large token position and sustained high borrow utilization, so it is not triggerable in an ordinary small market. [11](#0-10)  It nevertheless uses only reachable user operations: supplying tokens, borrowing them against collateral, allowing time to pass, and calling `update_indexes`. [12](#0-11)  Governance-provided market caps, utilization limits, token supply, and the rate curve determine whether a production market can reach the required principal and index. [13](#0-12)  The likelihood is therefore medium: the capital and time requirements are substantial, but no privileged call or third-party failure is needed once a sufficiently large market reaches the vulnerable index range. [14](#0-13) 

### Recommendation

Cap or saturate the unscaled debt and supply values before multiplying scaled shares by their indexes, rather than relying on `MAX_BORROW_INDEX_RAY` after index growth. [15](#0-14)  `calculate_supplier_rewards` should explicitly detect `borrowed * index` overflow and clamp the computed totals to the maximum representable accounting value, or accrue in smaller deterministic pieces that keep every multiplication within the checked domain. [16](#0-15)  At minimum, `update_borrow_index` should enforce a market-size-aware bound where `borrowed * new_index <= i128::MAX`, and the same bound should be applied to `supplied * supply_index`. [17](#0-16)  Add regression coverage for maximum configured principal, maximum decimals, high utilization, and index values just below `MAX_BORROW_INDEX_RAY` to verify that accrual saturates instead of freezing the market. [4](#0-3) 

### Proof of Concept

The repository contains a concrete scenario in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`. [10](#0-9) 

1. Create an 18-decimal market and a collateral market, with market caps and utilization configured to permit the position. [18](#0-17) 
2. Have one user supply `1_000_000_000 * 10^18` base units of the market token. [19](#0-18) 
3. Have another user supply collateral and borrow 98% of that liquidity through the public `borrow` path. [20](#0-19) 
4. Advance ledger time in yearly intervals and invoke the public `update_indexes` path after each interval. [21](#0-20) 
5. Observe that `update_indexes` fails with `MathOverflow` before `MAX_BORROW_INDEX_RAY` is reached. [22](#0-21) 
6. Subsequent `withdraw` and `repay` calls fail with the same error because both first attempt the overflowing accrual. [23](#0-22)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {

        }

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}
