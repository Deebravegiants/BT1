### Title
Stale FIFO queue index in `delete_state_commitment` permanently evicts a live, resubmitted state commitment before its retention cap is reached - ([File: modules/pallets/ismp/src/host.rs])

### Summary
`Pallet::<T>::delete_state_commitment` (invoked by governance to veto a state machine height) removes the entry from `BoundedStateCommitments`/`BoundedStateMachineUpdateTime` but deliberately leaves the corresponding index in the per-chain FIFO `StateCommitmentQueue` untouched, "to avoid scanning the queue" [1](#0-0) . This is analogous to the fbcon bug: an entry is torn down in one place while a stale reference/index to it survives in another data structure that is later dereferenced, producing incorrect/unsafe behavior on that later access.

### Finding Description
`delete_state_commitment` explicitly documents and accepts that the queue slot for the vetoed height stays behind as a "stale index" [1](#0-0) . When the vetoed height is the *latest* one, `LatestStateMachineHeight` is rolled back to the previous height, which reopens that same height number for honest resubmission through the normal consensus-update path [2](#0-1) .

When that height is legitimately resubmitted, the FIFO queue (`StateCommitmentQueue`, tracked by `CommitmentQueueStates`) ends up with two entries pointing at the same height — the stale one (which still occupies its original queue slot from before the veto) and the new live one [3](#0-2) . Because eviction on the next insertion walks the queue strictly by index (head pointer) rather than validating that the height at that index still corresponds to the live commitment, the stale entry is evicted first and, since it shares the same height key as the just-resubmitted live commitment, the eviction logic deletes the *live* `BoundedStateCommitments` entry for that height — one insertion earlier than the configured cap would have required [4](#0-3) .

This is the direct structural analog of CVE-2025-40323: a freed/removed logical entry (the vetoed mode / vetoed height) leaves a dangling index in a separate bookkeeping structure (`fb_display[]` / `StateCommitmentQueue`) that is not cleared, and a subsequent, unrelated operation (opening the console / resubmitting the height) walks that structure and acts on the stale index, destroying live state it shouldn't have touched.

### Impact Explanation
The consequence is that a state machine height's commitment — which relayers rely on to submit membership/non-membership proofs for cross-chain messages (requests/responses) committed at that height on the destination chain — can be silently and prematurely deleted from `BoundedStateCommitments` even though it was honestly resubmitted and is still within the chain's configured retention cap. Any request/response proof verification that depends on `state_machine_commitment` for that height (via `Pallet::<T>::state_machine_commitment`, consumed throughout `pallet-ismp`'s message handlers) will then fail with `StateCommitmentNotFound`, even though the height is legitimate and within the retention window operators configured. This is a permanent, unrecoverable loss of an intended-to-be-retained state commitment, which can strand in-flight messages that were relying on that height for delivery — i.e., a route becomes unable to deliver/verify messages for that height, one insertion earlier than the operator's own cap dictates, and the chain permanently retains fewer live commitments than its configured cap going forward [5](#0-4) .

### Likelihood Explanation
This requires the root-gated veto path (`delete_state_commitment` is only reachable through governance/root vetoing a state commitment) combined with a normal, expected resubmission flow, both of which are explicitly exercised and acknowledged as intentional (if "negligible") behavior in the pallet's own tests and comments [6](#0-5) . It is not attacker-controlled from an unprivileged transaction by itself (it depends on the veto being exercised), so likelihood is moderate rather than high, but the resulting deletion of a live, in-window commitment is a concrete correctness/availability defect in the consensus-verification path that any relayer or app depending on that height's commitment can be affected by.

### Recommendation
When evicting the head of `StateCommitmentQueue`, verify the height stored at that queue index still resolves to the specific commitment/entry that was live when it was queued (e.g., store a generation/commitment fingerprint alongside the height, or actively remove/patch the stale queue slot inside `delete_state_commitment` itself, mirroring the upstream fbcon fix of nulling `fb_display[i]->mode` at release time). At minimum, `delete_state_commitment` should scan for and null out (or mark tombstoned) any queue slot referencing the vetoed height so a later eviction cannot conflate it with a subsequently resubmitted, live entry at the same height.

### Proof of Concept
The existing test `vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early` in the repository is itself a working PoC: it vetoes the latest height, resubmits it, inserts one more height, and asserts that the live, resubmitted commitment for the vetoed height is deleted early due to the stale queue entry [7](#0-6) .

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

#[test]
fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		// Two queue entries now point at height 11: the stale one and the live one.
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 1), Some(11));
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
		// The queue still counts index 2 as live, so the burnt slot leaves this
		// chain retaining one fewer commitment than its cap of 2.
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 4 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));
	})
