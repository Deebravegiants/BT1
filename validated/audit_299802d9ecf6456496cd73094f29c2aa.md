### Title
Tron IntentGatewayV2 accepts unsafe raw ERC20 `transfer` calls, permanently losing escrowed funds when tokens signal failure by returning `false` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` redeems and refunds escrowed order tokens using a raw low-level `.call()` to the token's `transfer` selector, checking only that the call itself did not revert (`success`), never decoding/validating the returned `bool`. Non-reverting-on-failure ERC20 tokens (e.g. USDT-style tokens) can return `false` while the call still succeeds at the EVM level, causing the contract to treat the transfer as successful, mark the order filled/refunded, and decrement escrow accounting — even though the beneficiary received nothing.

### Finding Description
`withdraw()` is the internal function invoked by `onAccept()` when a `RedeemEscrow` or `RefundEscrow` cross-chain message is delivered by a relayer [1](#0-0) . For every escrowed input token (and for the protocol fee token), it performs:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` here only reflects whether the external call executed without reverting — it does not decode the ABI-encoded return data to check the token's own success flag. ERC20 implementations that return `false` on failure instead of reverting (a well-documented category including several USDT deployments, and the exact bug class cited in the referenced report) will make this `.call` return `success = true` with return data encoding `false`. The unchecked code path then proceeds to:
1. Set `_filled[body.commitment] = beneficiary` (marking the order permanently settled) at the top of `withdraw()` [3](#0-2) .
2. Decrement `_orders[body.commitment][token] -= amount` as if funds were paid out [4](#0-3) .
3. Emit `EscrowReleased`/`EscrowRefunded` [5](#0-4) .

Because `_filled[commitment]` is now set and the escrow accounting is already zeroed, there is no retry path — the beneficiary can never claim these tokens again, while the tokens remain stuck in the `IntentGatewayV2` contract balance. The exact same unchecked pattern also appears in the `SweepDust` handling branch of `onAccept` [6](#0-5) .

This contrasts with the same contract's own deposit path, which correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom` when pulling user funds into escrow [7](#0-6) , and with the sibling EVM (non-Tron) `IntentGatewayV2.sol` and the `HyperFungibleToken`/`WrappedHyperFungibleToken` apps, all of which use `SafeERC20.safeTransfer`/`safeTransferFrom` consistently for outbound payouts [8](#0-7) . The Tron deployment is the one path in the escrow-payout flow that deviates to raw, unchecked `.call()`.

### Impact Explanation
Any order whose input token or fee token is a "silent-failure" ERC20 (returns `false` instead of reverting) will result in the intent solver/user beneficiary permanently losing their escrowed tokens on the Tron deployment: the commitment is marked filled/refunded and escrow balances are decremented, but the tokens never leave the contract. This is a permanent freezing/loss of user funds reachable by a single relayed `RedeemEscrow`/`RefundEscrow` ISMP message — no privileged role is required, since any relayer can deliver the proof that triggers `onAccept` → `withdraw`.

### Likelihood Explanation
Likelihood depends on the intent gateway being configured to accept a token that returns `false` on failure rather than reverting. Given IntentGatewayV2 is a general-purpose, permissionless cross-chain intents settlement contract intended to support arbitrary ERC20 input/fee tokens (this is explicitly why the deposit-side code uses `SafeERC20`), such tokens are a realistic and foreseeable input, especially on Tron/TRC20 tokens which have known non-standard/legacy behavior. The bug triggers deterministically once such a token transfer would otherwise fail (e.g., blacklist, pause, insufficient allowance edge cases in the token's own logic) — the contract accounting and `_filled` marking happen unconditionally regardless of actual fund movement.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the deposit-side `safeTransferFrom` usage and with the non-Tron `IntentGatewayV2.sol` and `HyperFungibleToken` contracts. `SafeERC20` correctly decodes non-empty return data and reverts on a `false` result, ensuring `_filled`/`_orders` state is never updated unless the token transfer genuinely succeeded.

### Proof of Concept
1. An order is created with an input token `T` that implements ERC20 but, under some internal condition (e.g., recipient blacklisted, contract paused for that address), returns `false` from `transfer()` instead of reverting.
2. The order is filled/expires, and a relayer delivers a `RedeemEscrow` (or `RefundEscrow`) ISMP POST request to the Tron `IntentGatewayV2`, invoking `onAccept` → `withdraw(body, isRefund)` [1](#0-0) .
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; the low-level call succeeds (`success = true`) even though `T.transfer` internally returned `false` and moved no tokens [9](#0-8) .
4. `_orders[commitment][token] -= amount` executes, and `_filled[commitment]` is already set to the beneficiary, so the order is now permanently considered settled [10](#0-9) .
5. The beneficiary never received the tokens, they remain stuck in the `IntentGatewayV2` contract, and there is no code path to retry or reclaim them since the commitment is already marked filled — permanent loss of the beneficiary's funds.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
