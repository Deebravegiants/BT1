Audit Report

## Title
Client-supplied `MessageID` used as sole key for `savedCallbacks` map allows response misdelivery on collision - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` stores the callback for a pending web-API-trigger request in `h.savedCallbacks` keyed only by the client-supplied `msg.Body.MessageID`, with no uniqueness check or binding to the caller's identity/session. [1](#0-0)  When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `msg.Body.MessageID` and forwards the raw node response to whatever callback is currently registered under that key. [2](#0-1)  If two independent requests use the same `MessageID` while the first is still pending, the second call silently overwrites the first entry, and the DON's eventual reply to the first request is delivered to the second caller.

## Finding Description
`api.Message.Validate()` only checks that `MessageID` is non-empty, ≤128 bytes, and does not end in a null byte — it imposes no format, uniqueness, or entropy requirement, and it is entirely chosen by the requester. [3](#0-2)  The gateway's `ProcessRequest` validates the message (signature over sender's own message, not over any global uniqueness) and calls `h.HandleLegacyUserMessage(ctx, msg, callback)` synchronously, with a freshly created per-request `callback` used to `Wait()` for the reply. [4](#0-3)  The signature proves who sent that particular message, but nothing ties `MessageID` to the sender, so two *different* signers can pick the identical `MessageID` and the map entry for the first is silently overwritten by the second (`h.savedCallbacks[msg.Body.MessageID] = ...`), with no collision detection. [5](#0-4)  The same unguarded pattern exists in the dummy handler (`core/services/gateway/handlers/handler.dummy.go`), reinforcing that this is the general design pattern for legacy callback routing.

However, exploiting this requires the attacker to know or predict the victim's exact `MessageID` value while the victim's request is still in flight (during the trigger's round trip to the DON and back, bounded by `defaultCallbackMaxAgeSec` = 120s). In real usage, callers (e.g., the invoke_trigger script or SDK client) choose `MessageID` themselves and would typically use a unique/random per-request identifier. [6](#0-5)  Nothing in the reviewed code base demonstrates that `MessageID`s are predictable, sequential, or otherwise discoverable by an unrelated third party; the vulnerability is a real robustness/design gap (missing collision detection, no ID-to-sender binding), but a concrete exploit requires either the victim voluntarily reusing/leaking a `MessageID`, or an attacker who can already observe/guess the victim's chosen ID — a precondition not established as practically achievable in this codebase.

## Impact Explanation
If an attacker can supply a colliding `MessageID` for a pending victim request, they can receive the victim's DON response instead — a cross-user response corruption/misdelivery, which is an in-scope Chainlink gateway impact category. The severity is bounded by the fact that this only misdelivers the *response* payload for that specific trigger event, not credentials or funds directly, and requires precise timing/knowledge of a colliding ID.

## Likelihood Explanation
Likelihood is low-to-moderate and depends entirely on how `MessageID`s are generated by real clients (out of scope of this repo — this is an SDK/client behavior, not the gateway server's). The gateway itself performs no server-side derivation or uniqueness enforcement of `MessageID`, so if any real-world caller uses predictable or attacker-guessable IDs (e.g., short/sequential/reused IDs, as seen in the example script's default `"12345"`), the described misdelivery is directly reachable by an unprivileged HTTP client with no additional access needed. This is a genuine defense-in-depth gap even though the primary practical exploit likelihood depends on external ID-generation practices not controlled by this code.

## Recommendation
- Do not rely solely on client-supplied `MessageID` for `savedCallbacks` keys; derive the key from a server-generated correlation ID, or combine `MessageID` with the sender's authenticated address (`msg.Body.Sender`) extracted during `Validate()`.
- On registration in `HandleLegacyUserMessage`, check for an existing unexpired entry under the same key and reject/error instead of silently overwriting (`core/services/gateway/handlers/capabilities/handler.go` lines 411-414, and analogous code in `core/services/gateway/handlers/handler.dummy.go`).
- Apply the same fix to `handler.dummy.go`'s equivalent map.

## Proof of Concept
1. Client A sends a signed `web_api_trigger` legacy request with `MessageID = "X"` to the gateway; `HandleLegacyUserMessage` stores `h.savedCallbacks["X"] = callbackA` and forwards the request to DON nodes. [7](#0-6) 
2. Before any DON node responds, Client B (a different signer) sends their own signed request also using `MessageID = "X"`; `h.savedCallbacks["X"]` is overwritten with `callbackB`.
3. A DON node responds to Client A's original request; `HandleNodeMessage` → `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers Client A's response to Client B via `codec.EncodeLegacyResponse(msg)`. [2](#0-1) 
4. A Go unit test extending `TestHandlerReceiveHTTPMessageFromClient` in `handler_test.go` could register two `HandleLegacyUserMessage` calls with the same `MessageID` from different signers before calling `HandleNodeMessage`, then assert which callback receives the response — confirming misdelivery. This was not executed in this review session; live/test confirmation is recommended before treating exploitability as fully established, since it hinges on whether real callers ever produce colliding `MessageID`s within the callback TTL window.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
