## Title
Sandwich-attack-vulnerable native-token fee swap enables griefing/loss on message dispatch - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` allow any unprivileged caller to pay Hyperbridge protocol/relayer fees in the native token. When `msg.value > 0`, the host performs an on-chain Uniswap V2 swap (`swapETHForExactTokens`) with a fixed exact-output amount and no attacker-independent slippage protection, using `block.timestamp` as the deadline (i.e., no real deadline protection at all). This is directly analogous to the reported `MosaicNativeSwapperETH`/`MosaicNativeSwapperAVAX` finding: a swap parameter that should protect the caller from adverse pricing is effectively neutralized, letting a sandwiching bot manipulate the pool to extract value from — or grief — every native-fee-paying dispatch. [1](#0-0) 

### Finding Description
Any unprivileged user calling `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with `msg.value > 0` triggers:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [1](#0-0) 

The same pattern repeats for `dispatch(DispatchGet)` and `fundRequest()`. [2](#0-1) [3](#0-2) 

Two protections are missing/defective, mirroring the reported bug class:
1. **Deadline is not a real deadline.** `block.timestamp` is always valid at execution time, so it provides zero MEV/sandwich protection — functionally equivalent to the reported hardcoded `minAmountOut = 0` because the "protective" parameter is set to a value that can never actually block execution.
2. **No caller-supplied slippage bound.** The only bound on the swap's cost is `msg.value` itself (used as `amountInMax`), and the "output" (`post.fee`/`get.fee`/`amount`) is a fixed protocol-fee figure set independently of current pool price. A sandwich bot can push the WETH→feeToken price up right before the dispatch executes, forcing the exact-output swap to consume close to (or exceed) the caller's `msg.value`:
   - If the manipulated price makes the required input exceed `msg.value`, `swapETHForExactTokens` reverts with `INSUFFICIENT_INPUT_AMOUNT`, and the entire dispatch transaction reverts — denying the caller's ability to dispatch a cross-chain message paid for in native token (a route unable to deliver messages for that caller).
   - Otherwise, the swap consumes far more of the caller's ETH than the fair-market amount, with the attacker capturing the spread — the refund from the exact-output swap is returned to `address(this)` (the Host), not to the original caller, so any ETH the caller overpaid beyond the manipulated price is not recoverable by them via this call path.

This function is reachable from a single, unprivileged, submitted transaction by any dispatcher of a POST/GET request or any funder of a pending request — exactly the class of actor the scope permits ("EvmHost ... dispatch and delivery").

### Impact Explanation
This directly maps to the DoS/value-extraction class in the external report: a relayer/dispatcher pays fees with a hardcoded/ineffective slippage guard, and a malicious actor can sandwich the trade for profit or to grief the transaction. Concretely:
- **Denial of service on message dispatch**: An attacker can reliably front-run any `dispatch()`/`fundRequest()` call that pays with native token, causing the swap (and the whole dispatch) to revert. This blocks the affected caller's cross-chain message/fee-funding from being submitted in that transaction, and can be repeated to persistently grief a specific victim's dispatches paid via native token.
- **Value extraction**: Even when the transaction does not revert, an attacker can profit from the price impact at the caller's expense, since the "exact output, capped input" swap has no independently-set minimum protection beyond the attacker-visible `msg.value`.

### Likelihood Explanation
High for any chain where the configured `uniswapV2` pool (WETH/feeToken) has moderate-to-low liquidity — sandwiching a `swapETHForExactTokens` call with a `block.timestamp` deadline is trivial for MEV bots, since the deadline never expires and the call is fully visible in the mempool before inclusion. Any dispatcher/relayer paying fees in native token on `dispatch()`/`fundRequest()` is exposed on every call.

### Recommendation
- **Short term:** Add a caller-supplied slippage/deadline parameter to `DispatchPost`/`DispatchGet`/`fundRequest` (e.g., `amountInMax` distinct from `msg.value`, and a real `deadline` rather than `block.timestamp`), and refund any unspent native token to the actual caller (`_msgSender()`) rather than leaving it on the Host.
- **Long term:** Consider routing native-fee swaps through a TWAP-resistant or multi-block-averaged price source, or allow paying fees only in the fee token to remove on-chain AMM dependency from the critical dispatch path; audit all other Uniswap-integrated paths in the repo for the same `block.timestamp`-deadline anti-pattern.

### Proof of Concept
1. Attacker monitors mempool for a pending `EvmHost.dispatch(DispatchPost)` (or `DispatchGet`/`fundRequest`) call with `msg.value > 0`.
2. Attacker front-runs with a large buy of `feeToken` against WETH on the configured `uniswapV2` pool, pushing up the feeToken price.
3. Victim's transaction executes `swapETHForExactTokens{value: msg.value}(post.fee, [WETH, feeToken], address(this), block.timestamp)`:
   - Case A: required input now exceeds `msg.value` → reverts with `INSUFFICIENT_INPUT_AMOUNT`, victim's dispatch fails (DoS).
   - Case B: swap still succeeds but consumes materially more ETH than fair price, with the delta captured by the attacker's back-run sell.
4. Because `deadline == block.timestamp`, no deadline check can ever prevent step 3 regardless of how much the price moved.

**Uncertainty:** I could not fully confirm within the available context whether any later code path (outside the read excerpt) sweeps or refunds leftover native balance on `EvmHost` back to callers, which would slightly change the severity of the "excess ETH stuck at the Host" sub-claim; the core sandwich/DoS root cause via `block.timestamp` deadline and uncontrolled `swapETHForExactTokens` slippage is confirmed directly in the cited code.
