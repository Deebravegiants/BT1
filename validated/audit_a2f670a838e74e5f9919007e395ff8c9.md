## Analog Found

### Title
Removing a Chain from a Token's Configuration Permanently Blocks Timeout Refunds - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token` lets `CreateOrigin` "add or remove chains from an existing token's configuration" via `update_token` [1](#0-0) . If a chain is removed from an asset's configuration after a `send` was already dispatched to it, the escrowed/burned funds for that in-flight message can never be recovered: the `on_timeout` handler that performs the refund depends on the very configuration entry that was just deleted, and reverts unconditionally when it is missing.

### Finding Description
`send` locks (native) or burns (non-native) the user's tokens and dispatches a `Send` message to the destination via ISMP [2](#0-1) . If that message never gets delivered before its timeout, `pallet-ismp`'s permissionless timeout-processing path invokes `IsmpModule::on_timeout` on this pallet to refund the sender.

`on_timeout` resolves the local asset purely from `ContractToAsset::<T>::get(dest, &to)`, and reverts with `HftError::UnknownContractOnTimeout` if that entry is absent: [3](#0-2) 

That same map is also what `on_accept` uses to identify a token for inbound transfers, and it's exactly the structure `update_token`'s "remove chains" capability mutates [4](#0-3) . There's no check in `on_timeout` for "was this contract/chain valid when the message was sent" versus "is it valid now" — it only consults current state. Consequently:

1. User calls `send` for asset X to chain C. Tokens are locked/burned; a `Send` PostRequest is dispatched.
2. Before the request is delivered or times out, `CreateOrigin` calls `update_token` to remove chain C from asset X's configuration (e.g., deprecating support for that route, or during a token migration).
3. The request eventually times out. Any relayer permissionlessly submits the timeout proof through `pallet-ismp`, which calls this pallet's `on_timeout`.
4. `ContractToAsset::<T>::get(dest, &to)` now returns `None` because the mapping was removed in step 2, so `on_timeout` reverts with `UnknownContractOnTimeout` instead of refunding.
5. Because `on_timeout` is the pallet's only exit/refund path for an undelivered `Send`, and it unconditionally fails once the configuration entry is gone, the escrowed/burned funds are stuck permanently — governance re-adding the chain does not necessarily restore the exact same `(dest, to)` pairing the original message used (and even if it does, this is not a designed recovery path, just an accidental workaround).

This is the same bug class as NAZ-M3: a legitimate configuration change (delisting/removing an asset-chain mapping) blocks a user's finalization/exit path (there, `redeem`; here, `on_timeout` refund) for funds that were already locked in under the old configuration.

### Impact Explanation
Funds locked or burned by `send` become permanently unrecoverable if governance removes the destination chain from the asset's configuration while the corresponding cross-chain message is still in flight. This is a direct freezing-of-funds bug reachable from a single user-submitted extrinsic (`send`) combined with an ordinary, non-malicious governance action (`update_token`), with no way for the user to recover.

### Likelihood Explanation
`update_token` is a routine administrative action — removing a chain is a normal operation when deprecating a route, rotating contract addresses, or trimming supported destinations, not an attack. Any in-flight `send` at the moment of that removal is affected, and since ISMP timeouts routinely occur (delayed relaying, congestion, chain outages), the race window is realistic in production rather than purely theoretical.

### Recommendation
Do not let `on_timeout` depend on live, mutable configuration. Options:
- Snapshot the resolved `local_asset_id`, decimals, and precision into the dispatched request's context/body at `send` time, so `on_timeout` (and `on_accept`'s counterpart) can refund purely from data carried with the message rather than re-resolving current storage.
- Alternatively, make `update_token`'s removal path preserve stale `(chain, contract)` entries until all in-flight messages referencing them have resolved (timed out or been accepted), only pruning the mapping once no live request could still reference it.

### Proof of Concept
Conceptual sequence (Substrate runtime with `pallet-hyper-fungible-token`):
1. Alice calls `hyperFungibleToken.send(asset_id, dest=ChainC, amount, ...)`. Contract mapping `TokenContracts[ChainC][asset_id] = 0xEvmContract` and `ContractToAsset[ChainC][0xEvmContract] = asset_id` exist; Alice's tokens are locked/burned.
2. Governance calls `hyperFungibleToken.update_token(update)` removing `ChainC` from `asset_id`'s configuration, deleting `TokenContracts`/`ContractToAsset` entries for `(ChainC, asset_id)`.
3. The dispatched `Send` request to `ChainC` times out (never delivered, or destination unreachable).
4. Any relayer submits the timeout message through `pallet-ismp`; it invokes `HyperFungibleToken::on_timeout` for the request.
5. `ContractToAsset::<T>::get(ChainC, &to)` returns `None` → `Err(HftError::UnknownContractOnTimeout)` [3](#0-2)  → the timeout dispatch fails, and no refund event/mint/transfer happens. Alice's original tokens remain locked/burned indefinitely with no other recovery mechanism exposed by the pallet.

Note: I could not directly inspect the `update_token` extrinsic implementation in `modules/pallets/hyper-fungible-token/src/lib.rs` (index coverage did not return its body), so I cannot confirm from source whether it fully deletes both `TokenContracts` and `ContractToAsset` entries or only one side, nor whether any additional safety check exists there. This should be verified directly in a Devin session with full repository access before treating this as fully confirmed; the analysis above is based on the pallet's README description of `update_token`'s "add or remove chains" behavior and the confirmed `on_timeout` lookup logic.
