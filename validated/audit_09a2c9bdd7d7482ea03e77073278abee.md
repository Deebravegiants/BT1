### Title
Webhook Tenant Identity Spoofing via HMAC That Covers Only the Body, Not the `shop` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC that is computed **exclusively over the raw request body**, then dispatches the handler using the `shop` value taken from an **unauthenticated HTTP header**. The identity binding the app relies on — "the shop this webhook is for equals the shop verified by the HMAC" — does not hold, because the HMAC signable string never includes the shop (or topic) at all.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` for webhooks is implemented as: [1](#0-0) 

i.e. only `@raw_body` is signed. The `shop`, `topic`, and `webhook-id` values are read straight from request headers with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair and then trusts the header-derived `shop`/`topic` to build the dispatched metadata: [3](#0-2) 

That metadata (`WebhookMetadata`) is a plain struct with a `shop` field that carries no relation to what was actually verified: [4](#0-3) 

The equality the app implicitly assumes is:

`shop_used_by_handler == shop_bound_by_hmac`

but the actual state is:

`shop_used_by_handler = header["x-shopify-shop-domain"]` (attacker-controllable)
`shop_bound_by_hmac = ` — undefined; the HMAC only proves "this exact body byte-string was signed with the app secret," nothing about which shop it belongs to.

Because the api_secret_key used to compute the HMAC is shared by the app across **all** installing shops (it is not shop-specific), any shop that installs the app can legitimately receive a validly-signed `(raw_body, hmac)` pair from Shopify for an event on their own store. An unprivileged holder of one such shop install can replay that exact `raw_body`/`hmac` pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to claim the payload belongs to a different, victim shop. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` will accept it, since it only recomputes the signature over `to_signable_string` (the body), which is unchanged.

### Impact Explanation
This breaks the tenant (shop) identity boundary that host applications rely on this gem to enforce before dispatching to per-shop business logic (e.g. looking up a shop's session/store record by `data.shop` and applying that webhook's body to the wrong tenant's records). This is a cross-tenant data-confusion vector reachable by any entity that can install the app once (a low-privilege, unprivileged-relative-to-other-tenants actor), qualifying as cross-tenant access.

### Likelihood Explanation
Any of the app's own shops (or a party who can trigger one authentic webhook delivery for themselves, e.g., by performing an action that fires a webhook on their own installed store) can capture one legitimate `(body, hmac)` pair and immediately replay it with forged identity headers against the app's public endpoint — no secret material, access token, or privileged access is required, only knowledge of the endpoint URL and one legitimately-received webhook.

### Recommendation
Bind the tenant/topic identity into what is verified: include `shop`, `topic`, and `webhook_id` in the signable string (matching what Shopify actually signs per its documented webhook validation scheme) or, at minimum, require the app to independently verify the `shop` value from the HMAC-covered payload/session context rather than trusting the raw header once the body-only HMAC succeeds. Document clearly that `Request#shop`/`#topic` are not currently part of the authenticated data and must not be used for authorization decisions without additional verification (e.g. matching against a previously known/installed shop record).

### Proof of Concept
1. App exposes a webhook endpoint using `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker's own shop (`attacker-shop.myshopify.com`) has the app installed; Shopify delivers a genuine webhook to the app for a benign topic, e.g. `{}` body with headers:
   - `x-shopify-hmac-sha256: <valid-hmac-of-"{}" >`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
3. Attacker intercepts/replays this exact body and `x-shopify-hmac-sha256` value directly to the app's public webhook URL, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks `raw_body` against the hmac, per `to_signable_string` returning `@raw_body`), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled body content under the victim shop's identity.
