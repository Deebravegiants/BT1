Audit Report

## Title
Match-arm ordering in `run_call` grants full `AllowReentry` instead of stipend-restricted `AllowNext` for value-transferring calls at `gas_limit == CALL_STIPEND` - (File: substrate/frame/revive/src/vm/evm/instructions/contract.rs)

## Summary
In `run_call`, the tuple match `match (value.is_zero(), gas_limit == CALL_STIPEND)` places the `(false, _)` arm before `(_, true)`. Because Rust matches top-to-bottom and `(false, _)` is a wildcard on the gas-limit position, any non-zero-value call is captured by the first arm regardless of `gas_limit`, making the intended stipend heuristic `(_, true) => AllowNext` unreachable whenever `value != 0` — exactly the case (Solidity `.transfer()`/`.send()`, `value != 0 && gas_limit == 2300`) that the heuristic is documented to protect. [1](#0-0) 

## Finding Description
`run_call` computes reentrancy protection via:
```rust
match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND)) {
    (false, _) => (true, ReentrancyProtection::AllowReentry),
    (_, true) => (true, ReentrancyProtection::AllowNext),
    (_, _) => (false, ReentrancyProtection::AllowReentry),
}
``` [1](#0-0) 

`value.is_zero() == false` (i.e., value is non-zero) matches the first arm unconditionally on the gas-limit component, so it also captures `gas_limit == CALL_STIPEND`. The comment directly above the second arm states the intent is to detect "solc passes `gas_limit = 2300`" for the stipend pattern and to apply `AllowNext`, but that arm is unreachable for any non-zero-value call because the first arm always wins. This is used identically by both `CallScheme::Call`/`StaticCall` and passed into `interpreter.ext.call(...)` as the `reentrancy` parameter. [2](#0-1) 

`ReentrancyProtection::AllowReentry` is documented as "Don't activate reentrancy protection," while `AllowNext` is documented specifically for "calls that transfer value but restrict gas so that the callee only has a stipend gas amount" and states protection "must be enforced explicitly" due to gas-scale differences between Ethereum and revive/PolkaVM. [3](#0-2)  The match-arm ordering bug means this explicit enforcement never happens for the exact scenario it was designed for.

## Impact Explanation
This is an actual logic bug matching the documented intent in the code comments themselves, confirming the arm ordering is inverted from what was intended. The security consequence is that value-transferring calls with `gas_limit == CALL_STIPEND` (the canonical Solidity `.transfer()`/`.send()` reentrancy-guard pattern) receive no reentrancy protection (`AllowReentry`) instead of the intended `AllowNext` protection, potentially permitting reentrant calls back into the calling contract before its own state updates complete.

## Likelihood Explanation
The triggering condition (`value != 0`, `gas_limit == 2300`) is fully attacker-controlled and requires no privileged origin — any contract using the common `.transfer()`/`.send()` pattern, or any attacker crafting a `CALL` with these exact parameters, reaches the vulnerable code path deterministically.

## Recommendation
Reorder the match so the compound stipend condition is checked before the general non-zero-value condition:
```rust
let (add_stipend, reentrancy) = if !value.is_zero() && gas_limit == CALL_STIPEND {
    (true, ReentrancyProtection::AllowNext)
} else if !value.is_zero() {
    (true, ReentrancyProtection::AllowReentry)
} else {
    (false, ReentrancyProtection::AllowReentry)
};
```

1. Unit test in `substrate/frame/revive/src/vm/evm/instructions/contract.rs`: construct a call with `value = U256::from(1)` and `gas_limit = U256::from(2300)` (`CALL_STIPEND`), invoke `run_call`, and assert the `reentrancy` value passed to `Ext::call`. Currently this returns `ReentrancyProtection::AllowReentry` instead of the documented `ReentrancyProtection::AllowNext`.
2. Integration test: deploy a victim contract whose `withdraw()` calls `CALL` with `value=attacker_balance, gas=2300` before zeroing the attacker's internal balance record, and an attacker contract whose fallback re-enters `victim.withdraw()`. Under the current buggy ordering, the reentrant call is not blocked by reentrancy protection (since `AllowReentry` is granted instead of `AllowNext`), demonstrating the broken guarantee.

/// Level of reentrancy protection.
///
/// This needs to be specifed when a contract makes a message call. This way the calling contract
/// can specify the level of re-entrancy protection while the callee (and it's recursive callees) is
/// executing.
#[derive(Copy, Clone, PartialEq, Debug)]
pub enum ReentrancyProtection {
	/// Don't activate reentrancy protection
	AllowReentry,
	/// Activate strict reentrancy protection. The direct callee and none of its own recursive
	/// callees must be the calling contract.
	Strict,
	/// Activate reentrancy protection where the direct callee can be the same contract as the
	/// caller but none of the recursive callees of the callee must be the caller.
	///
	/// This is used for calls that transfer value but restrict gas so that the callee only has a
	/// stipend gas amount. In Ethereum that is not sufficient for the callee to make another call.
	/// However, due to gas scale differences that guarantee does not automatically hold in revive
	/// and we enforce it explicitly here.
	AllowNext,
}
