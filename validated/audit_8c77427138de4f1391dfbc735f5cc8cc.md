## Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the shop identity, topic, and webhook id used by the registry dispatch and passed to app handlers come from unauthenticated HTTP headers. This breaks the intended binding "the shop/topic a webhook is processed for == the shop/topic the HMAC actually vouches for," permitting cross-tenant webhook forgery by anyone able to obtain one valid `(raw_body, hmac)` pair from the shared `api_secret_key`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from request headers, which are not part of the signed content at all: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string`, i.e., the raw body, using `Context.api_secret_key` (a single secret shared across every shop that has the app installed): [3](#0-2) 

`Registry.process` uses this same validation and then dispatches the handler and builds the metadata object using the unauthenticated `request.topic` and `request.shop`: [4](#0-3) 

Because the HMAC only proves "this body was produced with our `api_secret_key`" and never binds that body to the particular shop or topic claimed in the headers, an attacker who can obtain any single legitimate `(raw_body, hmac)` pair — e.g., by installing the app on their own store (a normal, unprivileged action for any public app) and capturing one of their own webhook deliveries — can replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` and `x-shopify-topic` headers to claim the payload belongs to a different shop or a different topic. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the forged `shop`/`topic`/`webhook_id` straight to the registered handler as if Shopify had certified them.

This is exactly the "field acted on but not covered by the HMAC" identity-binding failure: the equality that should hold is `hmac_covers(shop, topic, body) == true`, but in fact `hmac_covers(body) == true` and `shop, topic` are trusted unconditionally.

### Impact Explanation
This enables cross-tenant confusion: a handler that persists, deletes, or otherwise acts on data keyed by `WebhookMetadata#shop` (as documented for consumers of this gem, e.g. GDPR/customer-data webhooks, order/product sync, uninstall handling) can be made to act on behalf of an arbitrary victim shop using attacker-supplied body content that was only ever certified for the attacker's own shop. Depending on the handler, this can range from data corruption/injection under a victim shop's identity to processing forged uninstall or redaction events for shops the attacker has no relationship with — a cross-tenant integrity/authorization violation.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on a shop they control (true for any publicly listed app) and can freely choose which topic/shop headers to send with a replayed, validly-signed body to the app's public webhook endpoint. No access to the `api_secret_key`, access tokens, or the victim's credentials is required — the attacker only needs one legitimately-signed payload of their own to reuse under a different claimed identity.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them) in the value that is HMAC-verified, or have the registry cross-check the header-derived `shop`/`topic` against values embedded in the verified body/metadata before dispatching to handlers. At minimum, document and enforce that consumers must not trust `WebhookMetadata#shop`/`#topic` as anything other than headers, and provide first-class support for verifying them against the signed payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one such delivery's raw body and its `X-Shopify-Hmac-Sha256` header (both valid).
3. Attacker POSTs that exact `raw_body` + `hmac` to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC.
5. The handler registered for that topic receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` even though the payload was never issued for that shop, and processes it as if Shopify had certified this attribution.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
