### Title
Malicious swap route injects token-transfer sub-invocations into the caller authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

`swap_collateral` accepts a caller-supplied opaque `swap: Bytes` payload and forwards it to the configured router without inspecting the contracts that the route invokes. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

A route-selected contract can therefore execute attacker-controlled contract code underneath the victim's authorized `swap_collateral` invocation and request token transfers from the victim that are unrelated to the swap. [5](#0-4) [6](#0-5) 

### Finding Description

`swap_collateral` requires authorization and account ownership, making `caller`'s signed invocation the authority context for the entire strategy. [7](#0-6) 

The strategy withdraws collateral and reaches `swap_tokens`, which snapshots only the controller's input and output balances, authorizes one exact controller-to-router input transfer, and invokes `execute_strategy` with the uninspected route bytes. [8](#0-7) [9](#0-8) [4](#0-3) 

The authorization granted by the controller is correctly limited to the configured router and has no sub-invocations, but it does not constrain what the router calls or what other authorization requests are added beneath the victim's signed top-level invocation. [10](#0-9) [11](#0-10) 

After the router returns, the controller verifies only that its own input balance did not grow, that spend did not exceed `amount_in`, and that its output balance increased; these checks do not detect a transfer from the caller's unrelated wallet balance. [12](#0-11) [13](#0-12) [14](#0-13) 

A deployed test demonstrates a route-selected contract calling `token.transfer(victim, attacker, amount)`, after which simulation records that transfer as a child of the victim's `swap_collateral` authorization entry. [15](#0-14) [16](#0-15) [17](#0-16) [18](#0-17) 

### Impact Explanation

If the victim signs the simulated authorization tree, the malicious route can transfer arbitrary assets from the victim's wallet to the attacker while still delivering a valid swap output to the controller. [19](#0-18) 

This is theft of user funds beyond the supplied collateral or routed input, because neither the payload minimum, the controller's measured output check, nor the final account-risk check bounds an unrelated wallet transfer. [20](#0-19) [21](#0-20) [22](#0-21) 

### Likelihood Explanation

An unprivileged attacker can construct a valid route that names attacker-controlled code and presents it to a victim through a malicious quote, interface, or transaction-building flow. [23](#0-22) [24](#0-23) 

Exploitation requires the victim to authorize the poisoned simulated authorization tree, matching the crafted-document user-interaction pattern in CVE-2023-51698 rather than a purely unauthenticated contract call. [18](#0-17) 

The same pattern is reachable wherever controller strategies forward route bytes, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [25](#0-24) [26](#0-25) [27](#0-26) 

### Recommendation

Constrain route execution to a governance-approved registry of token, venue, pool, and adapter addresses, and reject payloads that can invoke arbitrary route-supplied contract addresses. [5](#0-4) 

Additionally, transaction construction and signing interfaces should fail unless the simulated authorization tree contains only the expected child invocation; a normal controller swap should not introduce any caller-authorized token transfer below the top-level strategy call. [28](#0-27) [18](#0-17) 

### Proof of Concept

1. Deploy a malicious hop contract whose `swap` function calls `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`. [29](#0-28) 
2. Construct route bytes that direct the configured router through that contract while promising enough `ETH` output to satisfy the swap checks. [30](#0-29) 
3. Have the victim invoke `swap_collateral(caller=victim, account_id, current=USDC_market, amount=5_000_USDC, new=ETH_market, swap=poisoned_route)`. [23](#0-22) [31](#0-30) 
4. Simulation records the malicious wallet transfer as a sub-invocation of the victim's `swap_collateral` authorization. [32](#0-31) 
5. When the victim signs that tree, the attacker receives the unrelated wallet token while the victim's account still receives the expected `ETH` collateral output, so the strategy completes successfully. [19](#0-18)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization

final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
