### Title
Passphrase cache indefinitely extends past `maxTtl` via repeated `restartAutoLockTimer()` because `get()` never re-checks `maxTtl` once an activity period is set - (File: `features/application/src/modules/passphrase-cache.ts`)

### Finding Description
`PassphraseCache.get()` enforces the `maxTtl` bound (`addedAt + this.#maxTtl > Date.now()`) only in the `else` branch, i.e. only when `inactiveAt` is not yet set: [1](#0-0) 

As soon as `scheduleClear()` is called once, `INACTIVE_AT_KEY` is written with `Date.now()`: [2](#0-1) 

From that point on, `get()` takes the `if (inactiveAt)` branch and validates only `inactiveAt + ttl > Date.now()` — the `maxTtl`/`addedAt` check is never reached again for the lifetime of that cache entry. `scheduleClear()` is invoked from `Application.restartAutoLockTimer()`, which is directly RPC-reachable: [3](#0-2) 

An unprivileged caller (any dapp/origin/RPC consumer with access to this API) can therefore call `restartAutoLockTimer()` repeatedly, each call resetting `inactiveAt` to "now" and thus resetting the `inactiveAt + ttl` validity window, before `ttl` elapses. Because the `maxTtl` check is structurally unreachable once `inactiveAt` exists, this works regardless of whether the underlying `alarms.clear`/`alarms.create` calls in `#scheduleClear()` actually complete, race, or get dropped — the storage-side state (`inactiveAt`) is what `get()` reads, and it is refreshed synchronously in `scheduleClear()` before the (fire-and-forget, `void`-called) `#scheduleClear()` alarm scheduling even runs: [4](#0-3) 

This confirms the tested invariant is violated: expiry is not enforced purely by `get()`'s own `addedAt`/`maxTtl` math independent of the alarm — instead, `get()`'s logic itself has no maxTtl backstop once an "activity period" begins, so it depends entirely on the caller stopping the `restartAutoLockTimer()` cadence (or the alarm actually firing and calling `clear()`) to ever expire.

### Impact Explanation
The cached, in-memory-storage passphrase can be kept alive indefinitely beyond the configured `maxTtl` bound as long as an attacker (or malicious dapp) can invoke `restartAutoLockTimer()` (mapped to `application.ts` `restartAutoLockTimer`) more frequently than the current `ttl`. This extends the window during which `autoUnlock`/passphrase-cache consumers can retrieve the passphrase, increasing exposure for auto-unlock-based account takeover if any other primitive can read/exfiltrate the cached passphrase or trigger auto-unlock while the attacker keeps the timer alive.

### Likelihood Explanation
Feasibility depends entirely on `restartAutoLockTimer()` being reachable from a low-privilege caller (dapp/RPC) without additional auth, which the code shows is a plain RPC-exposed method on `Application` calling `passphraseCache.scheduleClear()` with no lock/session check other than the cache having a passphrase set. Repeating this call faster than `ttl` is trivial (a `setInterval` loop), making the bypass of `maxTtl` highly likely once reachability is confirmed. I was not able to locate the RPC permission/auth gating for `restartAutoLockTimer` in `features/application/src/api/index.ts` within the available index, so I cannot confirm with certainty whether an additional authorization layer restricts which callers can invoke it — this should be verified before treating the finding as fully unauthenticated.

### Recommendation
In `PassphraseCache.get()`, always evaluate the `addedAt + maxTtl` bound in addition to the `inactiveAt + ttl` check, e.g. require both conditions to hold (`Date.now() < min(inactiveAt + ttl, addedAt + maxTtl)`), so no combination of `scheduleClear()`/alarm timing can extend the passphrase's life past `maxTtl`.

### Proof of Concept
Unit/invariant test for `features/application/src/modules/passphrase-cache.ts`:
1. Construct `PassphraseCache` with a fake clock, `config.maxTtl = 60` (minutes), and a mocked `autoLockTimerAtom` returning a short `ttl` (e.g. 1 minute).
2. Call `set('secret')` at `t=0`.
3. In a loop, call `scheduleClear()` every simulated 30 seconds (less than `ttl`), while advancing the fake clock, continuing well past `t = maxTtl + 10min`.
4. At `t > addedAt + maxTtl`, call `get()`.
5. Assert `get()` returns `undefined` (expected per invariant) — the test will fail because `get()` still returns `'secret'`, proving `maxTtl` is never enforced once `inactiveAt` is set, independent of whether `alarms.clear`/`alarms.create` ever fire.
