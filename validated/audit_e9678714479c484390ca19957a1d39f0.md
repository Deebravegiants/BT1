### Title
Shop Domain Not Bound to Webhook HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as "verified to have come from Shopify" once the HMAC check passes, and then hands the caller-supplied `shop` domain header straight through to the app's handler as the tenant identifier. The HMAC, however, is computed only over the raw body — never over the shop domain — so the shop attribution can be swapped on any HMAC-valid payload the attacker can obtain for one of their own shops.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read from an independent, unsigned HTTP header: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` gates on that HMAC check alone, then constructs `WebhookMetadata` directly from `request.shop`, forwarding it to the app-supplied handler as the tenant key: [4](#0-3) 

The library's own documentation instructs integrators to trust `data.shop` from `Registry.process` as the shop identity and to use it to key their business logic (e.g. job queues, per-shop data operations), and explicitly states that `process` "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

**Identity binding broken (as equality):** the gem asserts `authenticated_source == "Shopify"` after HMAC(body) succeeds, and then implicitly asserts `authenticated_source.shop == request.shop`. But `request.shop` is never part of the signed bytes, so this second equality does not actually hold — the shop header is attacker-controlled data riding along with a genuinely Shopify-signed body.

### Impact Explanation
Any developer can install their own (or a target's public) app on a shop they control and legitimately receive a Shopify-signed webhook (raw body + valid `x-shopify-hmac-sha256`). Because the HMAC never covers the shop domain, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` with an arbitrary victim shop's domain. `Registry.process` will pass HMAC validation (the body/HMAC pair is genuinely valid) and dispatch the handler with `data.shop` set to the victim's domain, with the attacker's own body content. Since the gem's documentation directs hosts to treat `data.shop` as the authenticated tenant key, this results in a cross-tenant event: the app performs shop-scoped actions (e.g., data mutation, GDPR-style `shop/redact`/`customers/redact` handling, queue dispatch keyed by shop) attributed to a shop the attacker does not control.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on any shop they control (a normal, unprivileged action for a public Shopify app) to obtain one valid signed webhook body/HMAC pair, and then replay it with a modified `shop` header to the same webhook endpoint. No access token, `client_secret`, or privileged account for the victim shop is needed. The mechanics rely entirely on this gem's own `Request`/`HmacValidator`/`Registry` code path, not on the host ignoring documented behavior — the host is following the documented `data.shop` usage pattern from `docs/usage/webhooks.md`.

### Recommendation
Bind the shop domain (and topic/webhook id) into the signable material verified by `HmacValidator`, or otherwise cryptographically tie the `shop` header to the HMAC-verified body (e.g., require it as part of the signed payload rather than a bare header), so that the shop attribution cannot be altered independently of the HMAC-protected content. At minimum, document loudly that `data.shop` is not authenticated by the HMAC and must be independently verified (e.g., cross-checked against a shop for which a registration/session is known) before being used as a tenant key.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (attacker-owned) and register for a webhook topic (e.g. `shop/redact`).
2. Capture a real Shopify webhook delivery to the app: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Replay the request to the same app endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equal to `H` — validation passes.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and any shop-keyed logic in the host app (per the documented pattern) now executes as if this event genuinely came from `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
