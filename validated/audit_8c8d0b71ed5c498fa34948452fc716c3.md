## Analysis

The reported bug class—deriving a critical price from a manipulable constant-product AMM reserve ratio without slippage/oracle protection—maps onto `EvmHost`'s native-to-fee-token conversion path in this repository.

### Finding

`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all convert `msg.value` (native ETH) into the ISMP fee token by calling the local Uniswap V2 router's `swapETHForExactTokens`, using the pool's live (spot) reserve ratio as the exchange rate, with no TWAP, oracle bound, or slippage guard [1](#0-0) . The same unguarded pattern repeats for GET dispatch and fee top-ups [2](#0-1) [3](#0-2) .

This is reachable by any unprivileged caller who dispatches a POST/GET request with native value — exactly the "single submitted transaction/dispatched request" reachability the scan requires [4](#0-3) . Because `swapETHForExactTokens` computes `amountIn` from the pool's instantaneous `reserve0`/`reserve1` ratio (the same constant-product mechanic flagged in the report), a searcher can sandwich the dispatch transaction: push the pool price up immediately before the victim's call so the router requires more ETH than `msg.value` provides, causing the swap (and thus the whole dispatch) to revert with `UniswapV2Router: EXCESSIVE_INPUT_AMOUNT` — a route temporarily unable to deliver messages — or push the price down before their own dispatch call to extract a favorable rate at the AMM's expense. Notably, `EvmHostForkTest` even declares an intended `maxSlippagePercentage` guard that is never wired into the actual `dispatch`/`fundRequest` swap calls [5](#0-4) , confirming the protection is expected but absent on-chain.

By contrast, `SimplexPaymaster.swapAndDeposit` shows the correct pattern elsewhere in the same codebase — it derives `amountOutMin` from Chainlink oracle prices with an explicit `swapSlippageBps` bound before touching the router [6](#0-5) , which `EvmHost`'s dispatch path lacks entirely.

### Title
Unprotected Uniswap V2 spot-price swap in `EvmHost` dispatch/fundRequest lets an attacker sandwich native-fee conversions - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` convert native ETH sent with a message dispatch into the fee token via `IUniswapV2Router02.swapETHForExactTokens`, pricing the conversion purely off the local pool's live reserves with no slippage bound, oracle cross-check, or TWAP.

### Finding Description
Each of the three payable entry points builds a two-hop `WETH -> feeToken` path and calls `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` [1](#0-0) [2](#0-1) [3](#0-2) . `swapETHForExactTokens` derives the required input amount (`amountIn`) directly from the pool's current `reserve0`/`reserve1` (constant-product) state — the exact "CPM" pricing model flagged in the report — and reverts if `amountIn > msg.value`. There is no independent price reference (Chainlink or otherwise) bounding how far this spot price may have moved, unlike the slippage-bounded, oracle-anchored swap in `SimplexPaymaster.swapAndDeposit` [7](#0-6) .

### Impact Explanation
An attacker can front-run a pending `dispatch`/`fundRequest` transaction with a large trade that shifts the pool's ETH/feeToken reserves, forcing the victim's swap to require more ETH than the `msg.value` supplied and causing the transaction (and hence message dispatch) to revert — a griefing/DoS on the messaging route (`a route unable to deliver messages`). Alternatively, an attacker can manipulate the pool immediately before their own dispatch call to obtain the required fee-token amount for less ETH than fair value, extracting value at the AMM's expense while still crediting the correct nominal `fee` amount into `_requestCommitments`. Both outcomes stem from trusting an unprotected, single-block AMM spot price for a security-relevant conversion.

### Likelihood Explanation
Any address can call `dispatch`/`fundRequest` with `msg.value`, and any address can trade against the configured Uniswap V2 pool in the same block (flash loan or ordinary capital), making this attack trivially reachable and requiring no special privileges — the pool used is whichever `uniswapV2` router/pair is configured in `HostParams`, typically a lower-liquidity pairing on non-mainnet chains, increasing feasibility of large single-block price shifts.

### Recommendation
Bound the swap with an oracle- or TWAP-derived maximum acceptable input (mirroring `SimplexPaymaster._getOraclePrice` + `swapSlippageBps`), reject dispatches whose implied price deviates beyond a configurable tolerance, and/or replace `swapETHForExactTokens`'s deadline of `block.timestamp` with a real deadline plus a minimum-output/maximum-input check tied to an external reference price rather than the live pool alone.

### Proof of Concept
1. Attacker observes a pending `EvmHost.dispatch(DispatchPost)` call with `msg.value` sized for the current WETH/feeToken pool price.
2. Attacker submits a large swap in the same pool (front-run) that moves the reserve ratio so the required `amountIn` for `post.fee` feeToken units now exceeds the victim's `msg.value`.
3. Victim's `IUniswapV2Router02.swapETHForExactTokens` call reverts with `EXCESSIVE_INPUT_AMOUNT`, reverting the entire `dispatch` call and blocking that message from being sent until retried with a larger, unpredictable ETH amount — demonstrating denial of message delivery driven purely by unguarded reliance on the pool's constant-product spot price, as referenced by `EvmHost.dispatch` at [1](#0-0) .
