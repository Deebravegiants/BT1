## Title
Fee-on-transfer/deflationary underlying tokens cause unbacked minting and insolvency in `WrappedHyperFungibleToken` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks an underlying ERC20 by calling `safeTransferFrom(msg.sender, address(this), params.amount)` but never verifies the amount actually received by the contract. It then dispatches a cross-chain `Message` carrying the *nominal* `params.amount`, which the peer `HyperFungibleToken` on the destination chain mints in full via `_mint(beneficiary, message.amount)`. If the underlying token charges a transfer fee (deflationary/fee-on-transfer token), the wrapper receives less than `params.amount` while the destination mints the full requested amount, creating unbacked supply and draining the home-chain collateral pool that legitimate users rely on to redeem/unlock their bridged tokens.

### Finding Description
In `send()`:
```solidity

function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
    uint256 msgValue = msg.value;
    if (_isWeth && msgValue >= params.amount) {
        msgValue = msgValue - params.amount;
        IWETH(_underlying).deposit{value: params.amount}();
    } else {
        IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    }
``` [1](#0-0) 

there is no balance-before/after check. `_buildDispatchPost` then embeds `params.amount` unchanged into the cross-chain `Message.amount` field: [2](#0-1) 

On the destination chain, the peer `HyperFungibleToken.onAccept` mints exactly `message.amount` with no cross-check against what was actually locked:
```solidity

address beneficiary = _toAddr(message.to);

``` [3](#0-2) 

For a fee-on-transfer token, `IERC20(_underlying).balanceOf(address(this))` increases by less than `params.amount`, yet the destination mints the full `params.amount`. Every subsequent bridge-back burns tokens on the remote chain and calls `onAccept` on the home-chain wrapper, which unconditionally transfers `message.amount` of the underlying out via `safeTransfer`:
```solidity
} else {
    IERC20(_underlying).safeTransfer(beneficiary, message.amount);
}
``` [4](#0-3) 

The timeout refund path has the identical issue — it also transfers the full nominal `message.amount` back, not the actual amount ever received: [5](#0-4) 

Notably, the codebase already demonstrates awareness of this exact class of bug elsewhere: `IntentGatewayV2.placeOrder` explicitly measures `balanceBefore`/`balanceAfter` around `safeTransferFrom` to compute the actual received amount before crediting escrow:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [6](#0-5) 

`WrappedHyperFungibleToken.send()` (and its upgradeable twin `WrappedHyperFungibleTokenUpgradeable.sol`) lacks this protection entirely.

### Impact Explanation
Any unprivileged user can call `send()` with a fee-on-transfer/deflationary underlying token to mint more wrapped supply on the destination chain than what is actually locked as collateral on the home chain. Since the wrapper is a shared custody pool across all users of that token pair, this progressively under-collateralizes the pool: legitimate users who locked "clean" (non-fee) tokens, or earlier depositors, may find the wrapper unable to fulfill `onAccept` unlocks or timeout refunds because the underlying balance has been drained by the inflated redemptions from the fee-on-transfer deposits. This results in permanent freezing/loss of funds for other bridge users and effectively an unbacked mint on the destination chain — a direct violation of the 1:1 backing invariant the lock/unlock design depends on.

### Likelihood Explanation
Reachable by a single, unprivileged `send()` transaction with no special preconditions beyond the token owner choosing (or being tricked into supporting) a fee-on-transfer ERC20 as the wrapped underlying. Any deployer configuring `WrappedHyperFungibleToken` with a deflationary token (a common token category on EVM chains) triggers this on the very first bridge-out transaction; no attacker collusion with governance/relayers is required.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder`: measure `balanceOf(address(this))` before and after the `safeTransferFrom` in `send()`, and use the actual delta as the `amount` encoded in the dispatched `Message`, instead of trusting the caller-supplied `params.amount`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A configured with a fee-on-transfer ERC20 (e.g., 5% fee) as `_underlying`, paired with `HyperFungibleToken` on chain B.
2. User calls `send({amount: 1000, to: user, dest: chainB, ...})`. `safeTransferFrom` pulls 1000 nominal, but wrapper only receives 950 due to the fee (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:266-273`).
3. `Message.amount = 1000` is dispatched; on chain B, `HyperFungibleToken.onAccept` mints 1000 tokens to the user (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:299-301`), a 50-unit unbacked surplus.
4. Repeat with more users/volume; the wrapper's on-chain balance of the underlying grows slower than the cumulative minted supply on chain B.
5. When users bridge back (burn on chain B, `onAccept` unlock on chain A), the wrapper's `safeTransfer` calls eventually revert or drain balance meant for other legitimate depositors, freezing funds for the wrapper's remaining users.
