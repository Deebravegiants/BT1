Audit Report

## Title
Bridge and External Initiator `OutgoingToken` secrets disclosed to view-only API/GraphQL users via `GET /v2/bridge_types`, `GET /v2/bridge_types/:name`, `GET /v2/external_initiators`, and the `Bridge` GraphQL query - (File: core/web/presenters/bridges.go, core/web/presenters/external_initiators.go, core/web/resolver/bridge.go)

## Finding Description
`BridgeResource.OutgoingToken` is declared without `omitempty` and is unconditionally populated by `NewBridgeResource` from the persisted `bridges.BridgeType.OutgoingToken` field: [1](#0-0) 

This `OutgoingToken` is a 24-byte generated secret created alongside the bridge's hashed incoming credentials in `NewBridgeType`: [2](#0-1) 

Unlike `IncomingToken`, which is explicitly `json:"incomingToken,omitempty"` and documented as "only provided when creating a Bridge," `OutgoingToken` has no such redaction, so it is present in the JSON response of every subsequent `GET /v2/bridge_types` and `GET /v2/bridge_types/:name` call, not just at creation time.

The RBAC route table confirms these GET routes are reachable by `view`-role (read-only, lowest-privilege) tokens, not just `edit`/`admin`: [3](#0-2) 

The GraphQL resolver exhibits the identical pattern, exposing `OutgoingToken` on every `Bridge` query with no role-based filtering: [4](#0-3) 

The `ExternalInitiatorResource` presenter has the same flaw — `OutgoingToken` lacks `omitempty` and is always serialized: [5](#0-4) 

and `GET /v2/external_initiators` is likewise reachable by `view`-role users: [6](#0-5) 

No redaction, role check, or middleware filters this field out for lower-privileged callers before serialization — the existing `RequiresEditRole` / `RequiresAdminRole` middleware only gates entire routes (e.g., blocking `POST`/`PATCH`/`DELETE`), not field-level content within an already-permitted `GET`.

## Impact Explanation
This maps to the CWE-200/522 credential-exposure pattern: a caller holding only the `view` role (intended for non-administrative, read-only access) can retrieve `OutgoingToken` — a live secret used to authenticate the node's outgoing bridge/external-initiator callbacks — for every configured bridge and external initiator, without needing `edit` or `admin` privileges. This is an in-scope secret-exfiltration issue since possession of this token could allow the low-privileged caller to forge/replay authenticated outgoing-callback traffic toward external adapters/initiators that rely on this token for authentication, which is a broken privilege boundary within the node's own role model (`view` vs `edit`/`admin`), not a misconfiguration or externally-caused issue.

## Likelihood Explanation
Likelihood is high in any deployment that issues `view`-scoped API tokens to less-trusted operators, dashboards, or monitoring integrations — a documented and tested part of the role model (`routesRolesMap` in `auth_test.go`). Exploitation requires only a valid `view`-role API token and a single authenticated GET request; no operator/admin escalation, host access, or network positioning is needed, and it is fully repeatable against any bridge/external initiator on the node.

## Recommendation
Apply the same redaction convention already used for `IncomingToken`: mark `OutgoingToken` as `json:"outgoingToken,omitempty"` in `BridgeResource` and `ExternalInitiatorResource`, and populate it only in the one-time create-response path (mirroring `bridge_types_controller.go`'s handling of `IncomingToken`), not in list/get responses or the GraphQL resolver. Alternatively, gate `OutgoingToken` visibility in read paths (`NewBridgeResource`, `NewExternalInitiatorResource`, `BridgeResolver.OutgoingToken`) behind an `edit`/`admin` role check, or redact it for `view`-role requests.

## Proof of Concept
1. As an admin, create a bridge via `POST /v2/bridge_types` and record the returned `outgoingToken`.
2. Issue/obtain an API token restricted to the `view` role.
3. As the `view`-role user, call `GET /v2/bridge_types/<name>` — permitted per the RBAC table entry `{"GET", "/v2/bridge_types/MOCK", true, true, true}`.
4. Observe `attributes.outgoingToken` in the JSON response contains the same secret from step 1, disclosed to a role with no edit/admin privileges.
5. Repeat with `GET /v2/external_initiators` (RBAC entry `{"GET", "/v2/external_initiators", true, true, true}`) and with a GraphQL `bridge(name: ...) { outgoingToken }` query to confirm the same disclosure through the resolver path.

// NewBridgeType returns a bridge type authentication (with plaintext
// password) and a bridge type (with hashed password, for persisting)
func NewBridgeType(btr *BridgeTypeRequest) (*BridgeTypeAuthentication,
	*BridgeType, error,
) {
	incomingToken := utils.NewSecret(24)
	outgoingToken := utils.NewSecret(24)
	salt := utils.NewSecret(24)

	hash, err := incomingTokenHash(incomingToken, salt)
	if err != nil {
		return nil, nil, err
	}

	return &BridgeTypeAuthentication{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingToken:          incomingToken,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, &BridgeType{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingTokenHash:      hash,
		Salt:                   salt,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, nil
}
