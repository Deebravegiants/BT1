Confirmed: `WebhookMetadata.shop` is populated directly from the unauthenticated `shop-domain` header [1](#0-0) , and `WebhookMetadata` is a plain struct with no verification tie to the HMAC [2](#0-1) .

### Title
Webhook HMAC only covers the raw body, not the `shop-domain` header used as tenant identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that body string. The `shop`, `topic`, `api_version`, and `webhook_id` values, which are all read from HTTP headers, are never part of the signed material. `Registry.process` nonetheless trusts `request.shop` as the tenant identity and hands it straight to the app's `WebhookHandler` via `WebhookMetadata`, which is the value host applications use to look up/attribute the webhook to a specific merchant.

### Finding Description
The identity binding broken here is: `HMAC-verified bytes == request.shop used as tenant key`. In practice:

- `Request#to_signable_string` returns `@raw_body` only [3](#0-2) .
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body [4](#0-3) .
- `HmacValidator.validate` verifies `verifiable_query.to_signable_string` against the received HMAC, i.e. only the body bytes [5](#0-4) .
- `Registry.process` raises only if the body HMAC is invalid, then immediately constructs `WebhookMetadata` using `request.shop` (the unverified header) as the merchant identity passed to the app's handler [1](#0-0) .

Because the app-level `client_secret` is shared across every shop that installs the app (it is not per-shop), any merchant who has legitimately installed the app can trigger a real webhook for their own shop, capture the valid `(raw_body, hmac)` pair Shopify sent, and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop. Since the HMAC only binds the body — never the header — the signature still validates, and `Registry.process` will pass `shop: <victim-shop>` (attacker-controlled) together with the attacker's own body content into the handler. Any host application that uses `WebhookMetadata#shop` (as the docs instruct [6](#0-5) ) to key merchant-scoped writes/lookups will attribute attacker-supplied data to the victim shop — a cross-tenant data-integrity/confusion issue rooted entirely in this gem's verification logic, not in host-application misuse of an undocumented API.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee for webhook processing: cross-tenant data injection/attribution using only the attacker's own legitimately-issued webhook body and signature, no access token or secret leakage required. This matches the Critical "cross-tenant access" impact category since the `shop` value the gem hands the app as authenticated is not actually bound to what was cryptographically verified.

### Likelihood Explanation
The attacker needs only to be an ordinary merchant who has installed the target app (installing an app and triggering a webhook, e.g., creating an order, is an unprivileged, self-service action) and the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified header. No access to `api_secret_key`, tokens, or any privileged account is required — the replayed HMAC was legitimately produced by Shopify for the attacker's own shop event.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) header values into the signed material verified against the HMAC, or independently corroborate the header-derived shop against a value embedded in the verified body/metadata before it is exposed via `WebhookMetadata`. At minimum, document/require that host apps verify the shop against installed-shop state rather than trusting `WebhookMetadata#shop` directly.

### Proof of Concept
1. As a merchant `attacker.myshopify.com` who has installed the target app, perform an action that triggers a subscribed webhook (e.g., `orders/create`). Shopify sends: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw_body>`, plus `raw_body`.
2. Capture `raw_body` and `x-shopify-hmac-sha256` from this legitimate request.
3. Resend the same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in [7](#0-6)  succeeds because it only checks `raw_body` against the HMAC.
5. `Registry.process` in [1](#0-0)  builds `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` and invokes the app's handler with attacker-controlled body content attributed to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
