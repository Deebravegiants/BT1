## Vulnerability Found

### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `ShopifyAPI::Webhooks::Request#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC over the body and, once it passes, forwards `request.shop` unmodified to the app's handler. The `shop` value that the handler uses to identify the tenant is therefore never bound by the signature that authenticates the request.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature exclusively against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, that signable string is defined as just the raw body: [2](#0-1) 

Meanwhile `shop` is pulled straight from an HTTP header that is completely outside the signed material: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` to build the metadata passed to the app's business logic: [4](#0-3) 

The identity binding this breaks, expressed as an equality that should hold but doesn't:
`shop authenticated by the HMAC` ≠ `shop acted upon by the handler (request.shop / WebhookMetadata#shop)`.

Any bytes that produce a valid HMAC over the body (which an attacker can legitimately obtain by triggering a real webhook on their own store, since HMAC validation does not require the app's `client_secret` to be known by the attacker — only to be correctly configured on the receiving app) can be replayed with an arbitrary `x-shopify-shop-domain` header value. The gem will still report `Utils::HmacValidator.validate(request)` as `true`, because the header plays no role in that computation, and will hand the attacker-chosen `shop` to the host application's handler as if it were authentic.

### Impact Explanation
This is a cross-tenant access vector: a merchant/attacker who owns any store that installs the app can capture (or simply own) a validly-signed webhook payload for their own shop, then submit it directly to the app's public webhook endpoint with the `shop` header swapped to point at a victim shop domain. Host applications built on this gem's documented contract (`WebhookMetadata#shop`, as returned by `Registry.process` / `handler.handle`) will process that webhook believing it originates from the victim tenant, potentially triggering tenant-scoped side effects (data updates, session/store lookups, cache invalidation, order/inventory changes, etc.) under the wrong shop's identity — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or knowledge of the app's `client_secret`: an unprivileged internet user who can install the target app on any store (including a free development store) can obtain a validly HMAC-signed webhook body/signature pair for that store and then freely vary the `shop` header when re-submitting it to the app's public webhook endpoint. The check in `Registry.process` provides no defense against this because the header is outside the signed data.

### Recommendation
Bind the tenant identity into the material that is actually verified. Either:
- Include the shop domain (and ideally topic/webhook id) inside `to_signable_string` so the HMAC covers it, or
- Require host applications to cross-check `request.shop` against a shop value derived from an already-authenticated context (e.g., the shop associated with the offline session/access token used to register the webhook) before trusting it, and document this requirement prominently since `Registry.process` currently gives no such guarantee.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify — both are validly signed with the app's real `client_secret`.
2. Attacker crafts a new HTTP request to the app's public webhook endpoint using the identical raw body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (the raw body) — validation succeeds.
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and performs tenant-scoped processing under the victim's shop identity, even though the payload never actually originated from or concerned that shop.
