### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body alone, while the `shop` (tenant) identifier used by the host application to route webhook data is read from an unauthenticated header. This breaks the binding between "the party the HMAC proves the request came from" and "the shop the data is attributed to," letting a holder of any single valid `(raw_body, hmac)` pair relabel that payload as belonging to a different merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read separately, straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, and is never part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string and, if it passes, unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The documentation explicitly tells integrators that calling `Registry.process` "will verify the request did indeed come from Shopify," implying the whole payload — including the shop attribution — is authenticated: [4](#0-3) 

The identity binding that should hold is: `shop used to authenticate the HMAC == shop delivered to the handler`. Because `to_signable_string` only covers `@raw_body`, this equality is never checked — the HMAC only proves "some request with this exact body was signed with the app's shared `api_secret_key`" (a secret shared across all merchants of the app), not "this body belongs to shop X." Any party that has ever legitimately received one webhook for their own store (an "unprivileged" merchant relative to other tenants of the same app) possesses a valid `(raw_body, hmac)` pair. They can replay that same body/hmac to the app's webhook endpoint while swapping only the `shop-domain` header to a victim shop's domain. `HmacValidator.validate` still passes because it never looks at the header, and `Registry.process` passes the attacker-chosen `shop` value straight into `WebhookMetadata`, which apps use to select the tenant/session the payload is applied to.

### Impact Explanation
This crosses the tenant boundary that host applications rely on this gem to enforce: a request cryptographically proven only to have come from "the app's Shopify integration for some merchant" is delivered to the handler labeled as belonging to an arbitrary other merchant. Host applications following the documented contract (`data.shop` is trustworthy because `process` "will verify the request did indeed come from Shopify") will store, act on, or forward webhook bodies under the wrong tenant, i.e., cross-tenant data injection/misattribution — the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or TLS interception — only possession of one legitimately delivered webhook (body + valid HMAC) for the attacker's own store, which any merchant who installs the app can obtain trivially, plus the ability to POST an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header.

### Recommendation
Include the shop identifier (and other identity-bearing headers such as `topic`/`webhook-id`, consistent with Shopify's documented signing scheme extensions) in the signed material, or otherwise cryptographically bind `request.shop` to the verified payload before it is handed to `WebhookMetadata`/handlers, so that `to_signable_string` cannot be satisfied by a body that was authenticated for a different shop. At minimum, document clearly that `request.shop` is not covered by the HMAC and must not be trusted for tenant routing without independent verification (e.g., against known/installed shop domains).

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and receives a legitimate `orders/create` webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`).
2. Attacker replays the exact same request to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shop-domain" => "victim.myshopify.com", "hmac-sha256" => H})` is built, and `HmacValidator.validate` recomputes HMAC over `B` only — matches `H`, so `Utils::HmacValidator.validate(request)` in `Registry.process` returns `true` (see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/webhooks/registry.rb:190`).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-controlled data attributed to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
