### Title
Ambiguous operator identity binding in user QR-code validation ("session location" instead of explicit operator ID) - ([File: src/backend/user_status.rs])

### Summary
The reported BTC issue is that a relayer selects an on-chain input/output as the "receiver"/"onramp" without any unambiguous binding rule, so the wrong address may be picked when several are present. The orb-core analog is in the user QR-code signup validation flow: by default the Orb validates a scanned user session against the backend using **only GPS coordinates** of the operator instead of the operator's explicit identity, so when multiple operator sessions can share the same location, the backend has no unambiguous way to know which operator/session the validation request actually belongs to.

### Finding Description
`verify_user_qr_code` in [1](#0-0)  calls `backend::user_status::request` passing the config flags `user_qr_validation_use_full_operator_qr` and `user_qr_validation_use_only_operator_location`.

In `do_request` [2](#0-1) , when `use_only_operator_location` is `true`, the HTTP request to `/api/v2/session/{user_id}/status` includes **only** `lat`/`lon` query parameters derived from `operator_data.location_data.session_coordinates` — it does **not** include the operator's QR-code/id at all. Only when `use_full_operator_qr` is set does the request include `operator_id`.

The default configuration explicitly prefers the location-only path over the identity-bound path: [3](#0-2)  sets `user_qr_validation_use_full_operator_qr: false` and `user_qr_validation_use_only_operator_location: true`. This means in the default/production configuration, the backend is asked to validate/attribute a user's signup session using coordinates alone, with no cryptographic or identifier-based binding to the specific operator Orb performing the scan.

This mirrors the BTC report's root cause exactly: just as a BTC transaction can have multiple inputs/outputs and the relayer has no deterministic rule for choosing the correct one, here multiple operator sessions (e.g., several Orbs deployed at the same site/location, or an operator whose location happens to coincide with another's) are indistinguishable to the backend from location alone, so the session/operator that gets bound to a given user validation is ambiguous rather than deterministically tied to the specific operator scan that occurred.

### Impact Explanation
If two operator sessions resolve to overlapping/identical coordinates, the backend's session lookup can return status/authorization data intended for a different operator's session than the one that actually initiated the scan on this Orb. This can misattribute a user signup to the wrong operator context, or allow session state to bleed across concurrently active signups at the same site, since the orb never proves which specific operator QR-code corresponds to the validation request being made unless `use_full_operator_qr` is enabled.

### Likelihood Explanation
This requires no malicious actor — it can occur any time multiple Orbs/operator sessions are active at the same physical location (which is an expected operational deployment pattern, e.g., a signup event with several stations), combined with the default configuration flags that omit operator identity in the validation request.

### Recommendation
Set `user_qr_validation_use_full_operator_qr: true` (or otherwise always include an explicit operator/session identifier in the `user_status::request` call) so the backend can deterministically bind the validation request to the exact operator session, rather than relying on potentially non-unique GPS coordinates as the sole discriminator.

### Proof of Concept
1. Deploy two Orbs/operators at the same physical location (e.g., same booth/room), each starting independent operator QR sessions.
2. With default config (`user_qr_validation_use_only_operator_location = true`, `user_qr_validation_use_full_operator_qr = false`), a user scans their QR code at Orb A.
3. `do_request` in [4](#0-3)  sends only `lat`/`lon` (shared by both Orbs) with no `operator_id`, so the backend cannot distinguish which operator session should be bound to this validation, leading to non-deterministic operator/session attribution for the signup.

#[cfg(not(feature = "skip-user-qr-validation"))]
async fn do_request(
    qr_code: &qr_scan::user::Data,
    operator_data: &OperatorData,
    use_full_operator_qr: bool,
    use_only_operator_location: bool,
) -> Result<Response> {
    let request = if use_only_operator_location {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id,))
            .query(&[
                ("lat", operator_data.location_data.session_coordinates.latitude),
                ("lon", operator_data.location_data.session_coordinates.longitude),
            ])
    } else if use_full_operator_qr {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
            .query(&[("operator_id", &operator_data.qr_code.user_id)])
    } else {
        super::client()?
            .get(format!("{}/api/v1/user/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
    }
    .basic_auth(&*ORB_ID, Some(get_orb_token()?));
