The docs explicitly state: `Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md:125), and `data.shop` is documented as "The shop domain of the webhook" (docs/usage/webhooks.md:14) — implying it is a trusted, verified value. ### Title
Webhook `shop`/`topic` identity fields are not covered by HMAC, allowing tenant/topic spoofing via header substitution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that `raw_body` was signed with the app's secret [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and are never included in the signed content [3](#0-2) . `Registry.process` trusts `request.shop` and `request.topic` after only validating the body's HMAC [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop that HMAC authenticates == shop the handler attributes the payload to`. In this gem that equality is never enforced — the HMAC binds only the byte-for-byte `raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated header values pulled out separately by `shopify_header` [5](#0-4) .

Any unprivileged internet user who can obtain one genuine `(raw_body, hmac)` pair — trivially available by installing the app on their own free development store and capturing the real webhook Shopify sends to the registered endpoint — can replay that exact body/HMAC to the same endpoint while substituting an arbitrary `shopify-shop-domain` header (any other merchant's domain string) and/or a different `shopify-topic` header (any topic the app has a handler for). Because `validate_signature` only recomputes the HMAC over `raw_body` [2](#0-1) , this forged request passes validation identically to the genuine one, and `WebhookMetadata` is built directly from the forged headers [4](#0-3) .

### Impact Explanation
Apps are documented to trust `data.shop` as "the shop domain of the webhook" [6](#0-5)  and to key their per-tenant persistence/business logic off it (as shown in the gem's own example, `shop_domain: data.shop` [7](#0-6) ). Since the gem's own `HmacValidator`/`Request` pairing does not bind `shop` (or `topic`) to the signature, an attacker can make the "verified Shopify webhook" appear to originate from any target shop domain, or be misclassified under any registered topic, achieving cross-tenant attribution of attacker-controlled data.

### Likelihood Explanation
This is fully reachable by an unprivileged internet user with no access to the app's `client_secret`, access tokens, or any privileged account beyond a free Shopify development store to generate one legitimate webhook of their own. The only requirement is that the app's webhook endpoint is internet-reachable, which is the gem's documented deployment model.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-covered signable content (or otherwise cryptographically bind them to the verified body, e.g. requiring the caller to pass an already-authenticated shop from session/installation state rather than trusting the header), so `Utils::HmacValidator.validate` authenticates the full set of identity-bearing fields that `WebhookMetadata` exposes to handlers, not just the JSON body.

### Proof of Concept
1. Register the app on an attacker-owned development store `attacker-shop.myshopify.com`; trigger a real webhook (e.g. `products/update`) to the app's public webhook endpoint and capture the raw POST: `raw_body` and header `x-shopify-hmac-sha256`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (or any string) and/or `x-shopify-topic` to a different registered topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [8](#0-7) , which succeeds because it only checks `raw_body` against the HMAC.
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-chosen `topic`, even though the request never actually came from `victim-shop.myshopify.com` [9](#0-8) .
