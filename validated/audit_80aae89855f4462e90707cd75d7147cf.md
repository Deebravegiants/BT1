### Title
GET response batches revert entirely if EvmHost lacks feeToken balance to pay the relayer reward - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` transfers the relayer's fee reward unconditionally, with no check that the host actually holds enough `feeToken` balance to cover it. Because this function is called directly (not via a low-level, failure-tolerant `.call`) from `HandlerV2.handleGetResponses` inside a loop over the whole batch, a revert in the fee transfer reverts the delivery of **every** GET response bundled in that proof, not just the underfunded one. This mirrors the reported AuctionHouse bug class: an unchecked token transfer for a "refund/reward" that can revert due to insufficient balance, causing a denial of service for an otherwise-valid operation.

### Finding Description
In `dispatchIncoming(GetResponse memory response, address relayer)`: [1](#0-0) 

after the destination app's `onGetResponse` callback succeeds, the function unconditionally rewards the relayer:
```solidity
uint256 fee = _requestCommitments[commitment].fee;
if (fee != 0) {
    IERC20(feeToken()).safeTransfer(relayer, fee);
}
```
There is no `try/catch`, no balance check, and no isolation of this transfer's failure the way the app callback's failure is isolated (`if (!success) { delete _responseReceipts[commitment]; return; }`). If `feeToken().balanceOf(address(this))` is less than `fee`, `safeTransfer` reverts, and since `dispatchIncoming` is invoked as a normal (not low-level) external call inside a `for` loop in `HandlerV2.handleGetResponses`: [2](#0-1) 

the revert propagates all the way up, aborting the whole `handleGetResponses` transaction — including every other, unrelated GET response bundled in the same MMR proof batch.

This is structurally identical to the AuctionHouse issue: a "refund the previous party" transfer performed without verifying the contract's own balance first, so a legitimate delivery/settlement operation can be blocked by an unrelated balance shortfall.

Fee accounting for `feeToken` in `EvmHost` is not strictly escrowed per-commitment; the same pooled balance also backs POST-timeout refunds and other transfers (e.g. `dispatchTimeOut` refunding `meta.fee` to `payer`, `dispatchIncoming(PostRequest,...)`'s eventual relayer rewards, and swap-derived fee token from `dispatch()`): [3](#0-2) 

Any drift between the sum of all outstanding, promised `fee` values and the host's actual `feeToken` balance (e.g., concurrent draws against the shared pool, rounding in swap-based fee collection via `swapETHForExactTokens`, or any other consumer of the same balance) can leave the host short by the time a given GET response is finally relayed.

### Impact Explanation
A single GET response whose associated relayer fee cannot be paid from the host's current `feeToken` balance blocks delivery of **all** GET responses batched together with it in the same `handleGetResponses` call. Since relayers batch multiple requests/responses for gas efficiency, this can stall message delivery for many unrelated applications and users simultaneously — a route becomes unable to deliver messages until the host's `feeToken` balance is topped up, which is an operational/governance action outside the control of the affected app or relayer. This satisfies the "route unable to deliver messages" acceptance criterion for Medium severity.

### Likelihood Explanation
This requires the host's `feeToken` balance to fall (even temporarily) below the sum of fees owed for in-flight GET requests. Given the pooled (non-escrowed) nature of the balance backing multiple fee-paying flows (dispatch fee collection via swap, POST timeout refunds, GET/POST relayer rewards), such drift is plausible under normal operation load or timing skew between fee collection and reward payout, without requiring a malicious actor — a relayer simply submitting a normal batch at the wrong moment reveals the issue, exactly as in the original AuctionHouse report ("the contract may run out of WETH for some reasons").

### Recommendation
Before transferring the relayer fee in `dispatchIncoming(GetResponse,...)`, check `IERC20(feeToken()).balanceOf(address(this)) >= fee`. If insufficient, either (a) skip the individual response's reward and mark it for later collection/retry rather than reverting the whole call, or (b) have `HandlerV2.handleGetResponses` invoke `dispatchIncoming` via a failure-tolerant low-level call per response (as is already done for the `onAccept`/`onGetResponse` app callbacks), so an unrelated balance shortfall cannot block delivery of the rest of the batch.

### Proof of Concept
1. `EvmHost` accumulates `feeToken` from `dispatch()` calls for POST/GET requests; balance is pooled, not escrowed per-commitment.
2. Some other flow drains the host's `feeToken` balance (e.g. many `dispatchTimeOut` refunds process concurrently, or swap-derived fee collection under-delivers versus the recorded `fee`), so `balanceOf(host) < sum(outstanding request fees)`.
3. A relayer submits `HandlerV2.handleGetResponses` with a batch of N GET responses, one of which (`response_k`) has `_requestCommitments[commitment_k].fee > balanceOf(host)`.
4. Verification and dispatch proceed; for `response_k`, `onGetResponse` succeeds, then `IERC20(feeToken()).safeTransfer(relayer, fee)` reverts due to insufficient balance.
5. Because `dispatchIncoming` is a normal external call inside the loop in `handleGetResponses` (not a try/catch-guarded low-level call), the revert bubbles up and reverts the entire transaction, so none of the N responses in the batch are delivered, even though N-1 of them had no funding issue at all.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
