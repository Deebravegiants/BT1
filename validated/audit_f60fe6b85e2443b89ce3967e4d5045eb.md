### Title
Missing per-relayer authorization gate on `BandwidthManager.onAccept` allows unauthorized treasury drain and tier manipulation - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.onAccept` (evm/src/apps/BandwidthManager.sol:208-232) authorizes inbound governance (`SetTiers`, `Withdraw`) using only `onlyHost` plus a static check that `request.source` equals hyperbridge's state-machine id. Unlike every other governance-recipient contract in this codebase — `HostManager` [1](#0-0) , `BridgeToken` [2](#0-1) , `IntentGatewayV2`/`ExtrinsicIntents` [3](#0-2) , and `SimplexPaymaster` (per its dedicated flow doc) — `BandwidthManager` never checks `incoming.relayer` against an authorized allowlist. This is exactly the bug class in the OpenClaw report: a per-account/per-caller disablement/authorization check that other equivalent code paths enforce is silently skipped in this one, letting a lower-trust caller through a delivery path that should require a stronger check.

### Finding Description
The codebase has an explicit, documented threat model (see `sdk/packages/core/docs/ai/decisions/2026-09-03-hostmanager-deliveries-are-gated-too-and-that-does-not-touch.md`) for exactly this scenario: the ISMP `handler` contract is a mutable host parameter (`HostParams.handler`), replaceable via a `SetHostParam` governance request. If a `SetHostParam` swap is ever delivered on a forged/compromised consensus proof, the newly installed handler is fully untrusted — it can call `EvmHost.dispatchIncoming(request, arbitraryRelayer)` with an arbitrary `PostRequest` (forged `source`, forged `body`) and an arbitrary claimed relayer address, since `EvmHost.dispatchIncoming` is only restricted to "whoever the current handler is," not to any proof of authenticity of the request content itself [4](#0-3) .

Because of that threat, every governance-facing `onAccept` in this codebase was hardened to add a second, independent check: the delivered `incoming.relayer` must equal a specific authorized address configured by the contract's own admin/owner, separate from and unguessable to an attacker who merely controls a forged handler:
- `HostManager.onAccept` requires `restrict(incoming.relayer, _params.admin)` before decoding any action [5](#0-4) .
- `BridgeToken.onAccept`/`onPostRequestTimeout` call `_checkRelayer(incoming.relayer)` before minting [2](#0-1) .
- `ExtrinsicIntents._checkRelayer` gates every `onAccept`/`onGetResponse` action, including governance kinds like `UpgradeContract`/`NewDeployment`, before the body is even decoded [3](#0-2) .
- `SimplexPaymaster` applies the same `_checkRelayer` pattern to all governance kinds including `Withdraw`/`SetRelayer` per its dedicated design doc.

`BandwidthManager.onAccept` has no equivalent. It checks only:
```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    PostRequest calldata request = incoming.request;
    if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();
    OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
    ...
}
``` [6](#0-5) 

Both `request.source` and `request.body` are attacker-controlled inputs once a malicious handler is installed — the `source.equals(hyperbridge)` check is a trivial byte comparison the forged handler can satisfy at will, and there is no `_relayer`/allowlist state at all in `BandwidthManager` (confirmed by grep: zero occurrences of "relayer" in the contract) [7](#0-6) . The `Withdraw` action transfers arbitrary `token`/`amount` to an arbitrary `beneficiary`, and pays out native token via a raw call, straight out of the contract's balance [8](#0-7) .

### Impact Explanation
If the `EvmHost` handler is ever replaced by an unauthorized/malicious contract (the exact route the rest of the codebase already treats as a live, defended-against threat), `BandwidthManager` has no second line of defense: the attacker's handler can call `dispatchIncoming` with a forged `PostRequest` whose `body` starts with `OnAcceptActions.Withdraw` and drain the full fee-token and native-token treasury held by the contract, or push `SetTiers` updates that let it (or an accomplice) purchase bandwidth at attacker-chosen (e.g., zero) prices. This is concrete theft of funds and unauthorized app action — the two impact classes the codebase's own hardening for `HostManager`, `BridgeToken`, `IntentGatewayV2`, and `SimplexPaymaster` was specifically built to prevent, but `BandwidthManager` is left unprotected.

### Likelihood Explanation
Exploitation is gated on the same precondition documented for the other, already-hardened contracts: a forged consensus proof (or otherwise malicious handler installation) reaching the host. That precondition is nontrivial on its own, but it is the exact scenario the Hyperbridge team has already identified, documented, and mitigated for every sibling app in the codebase (`docs/ai/decisions/2026-09-03-hostmanager-deliveries-are-gated-too...`, and the per-app changelog entries for `BridgeToken`, `IntentGatewayV2`/`ExtrinsicIntents`, and `SimplexPaymaster`). `BandwidthManager` appears to have been added without the same treatment, making it the single remaining unauthorized-action route once that precondition is met — a direct parity gap, analogous to OpenClaw's per-account disablement being ignored on one code path while enforced elsewhere.

### Recommendation
Add a `_relayer`/allowlist mechanism to `BandwidthManager` mirroring the pattern used in `HostManager`, `BridgeToken`, and `ExtrinsicIntents`/`SimplexPaymaster`: store an authorized relayer address (set by `owner`), and in `onAccept`, check `incoming.relayer` against it (reverting, e.g., with `UnauthorizedRelayer`) before decoding `request.body`, for both `SetTiers` and `Withdraw` actions. Ensure the check fails closed (no relayer configured ⇒ no deliveries accepted) to match `BridgeToken`'s fail-closed model, and add Foundry tests analogous to `testOnAcceptRejectsUnlistedRelayer` / `testForgedHandlerSwapIsRefused` in `HostManagerTest.sol` and `BridgeTokenTest.t.sol`.

### Proof of Concept
Conceptual PoC (mirrors `testForgedHandlerSwapIsRefused` in `evm/tests/foundry/HostManagerTest.sol`, but unlike that test, there is no gate to trip here):
1. Attacker forges/obtains a consensus proof that gets a `SetHostParam` request accepted, swapping `EvmHost`'s `handler` to `MaliciousHandler` (a contract that satisfies `IHandlerV2`'s ERC-165 check and performs no verification), exactly as modeled by `MaliciousHandler` in `HostManagerTest.sol` [9](#0-8) .
2. Attacker calls `MaliciousHandler.deliver(host, forgedRequest, anyAddress)` where `forgedRequest.source = hyperbridge`, `forgedRequest.to = BandwidthManager`, and `forgedRequest.body = abi.encodePacked(OnAcceptActions.Withdraw, abi.encode(Withdrawal({token: feeToken, beneficiary: attacker, amount: fullBalance})))`.
3. `EvmHost.dispatchIncoming` calls `BandwidthManager.onAccept(IncomingPostRequest(forgedRequest, anyAddress))`.
4. `onlyHost` passes (caller is `EvmHost`); `request.source.equals(hyperbridge)` passes (attacker set it); no relayer check exists; `Withdraw` executes, transferring the full fee-token/native balance to `attacker`.

Note: I was not able to fully verify within this session whether any other, non-handler-swap-dependent path (e.g., a compromised admin key with authority to call `setHost`/`Ownable` functions) could independently reach `onAccept` without the handler-swap precondition; the analysis above assumes the same handler-compromise precondition documented and mitigated for the sibling contracts.

# How a cross-chain delivery reaches the gateway, and where the relayer gate sits

Verified against `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol` and
`evm/src/apps/intentsv2/ExtrinsicIntents.sol`, and exercised by
`testRejectedDeliveryStaysRetryableThroughHost` in `evm/tests/foundry/IntentGatewayV2Test.sol`.

1. A relayer calls `HandlerV2.handlePostRequests` (or `handleGetResponses`). After proof
   verification the handler calls `host.dispatchIncoming(request, _msgSender())`. `_msgSender()` is
   plain `msg.sender`; the handler has no trusted forwarder.
2. `EvmHost.dispatchIncoming` (restricted to the handler) writes a receipt for the request
   commitment, then low-level calls the module with `IApp.onAccept(IncomingPostRequest(request,
   relayer))`. If that call fails the host deletes the receipt and returns without reverting, so the
   rest of the batch proceeds and the message stays deliverable.
3. `ExtrinsicIntents.onAccept` runs `onlyHost`, then `_checkRelayer(incoming.relayer)`, which reverts
   with `Unauthorized` when a relayer is set and the delivery is from anyone else. Only then is the
   first body byte read as a `RequestKind`. `onGetResponse` has the same two steps before touching
   the response.

    /// UTF-8 chain id like `"EVM-8453"` or `"EVM-137"`.
    bytes chain;

    /// Tier discriminant (matches `pallet_bandwidth::TierIndex`).
    uint256 tier;
    /// Price in 18-decimal units; scaled at purchase time to fee-token decimals.

    address beneficiary;

    /// must match `pallet_bandwidth::lib.rs::ACTION_*`.

        SetTiers,
        Withdraw

    // The host address
    address public _host;

    /// tier → price in 18-decimal units. Zero = unconfigured (purchases

    mapping(uint256 => uint256) public tierPrice;

        address feeToken,
        uint256 tier,
        uint256 months,
        uint256 amountPaid,
        bytes app,
        bytes chain,
        bytes32 commitment
    );
    /// Emitted once per tier in a `SetTiers` governance batch.
    event TierSet(uint256 indexed tier, uint256 price18d);
    /// Emitted by a `Withdraw` governance message after the transfer succeeds.
    event Withdrawn(address indexed token, address indexed beneficiary, uint256 amount);

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
