### Title
Attacker forces Emporium to grant unlimited `IERC20.approve` allowance via unrestricted CASE 2 stateless dispatch, permanently exposing any token balance Emporium ever holds - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`runAction`'s CASE 2 branch only blacklists the `callHinkalWallet`/`doSendToRelay` selectors and otherwise executes `op.endpoint.call{value: op.value}(op.callData)` with no endpoint allowlist, letting an attacker force Emporium to call `IERC20.approve(attacker, type(uint256).max)` on any ERC20 contract. Because the post-call solvency check in `runAction` is purely a balance diff over `circomData.erc20TokenAddresses` [3](#0-2) , it can never detect or reject an `approve()` call (which changes allowance, not balance), so this hostile approval is granted for free regardless of which tokens are listed in the array.

### Finding Description
**Equality claimed broken:** `token.allowance(Emporium, attacker)` before the call should equal `token.allowance(Emporium, attacker)` after any `runAction` call that isn't explicitly authorizing that allowance; instead the attacker can set it to `type(uint256).max` with a call whose accounting equality (`balancesAfter[i] - balancesBefore[i] == expected UTXO/deltaAmountChanges`) is trivially satisfied on both sides since `approve` never touches `balanceOf`.

**Code path:** `Hinkal.sol` invokes `EmporiumUpgradeable.runAction` (gated only by `onlyAllowedRecipient`, i.e. caller == Hinkal) [4](#0-3) . `runAction` decodes attacker-controlled `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` — a field that is only hash-bound to the attacker's *own* proof, so an attacker generating a proof for their own valid UTXOs fully controls its contents, including `stack.signerAddress = address(0)` and an arbitrary `ops` array. With `signerAddress == address(0)`, `verifyWallet` returns immediately without any signature check [5](#0-4) . Each op then falls into CASE 2 (`!(op.invokeWallet && signerAddress != 0)`), where the only guard is a selector blacklist for `callHinkalWallet`/`doSendToRelay`; any other `op.endpoint`/`op.callData`, including `TOKEN.approve(attacker, type(uint256).max)`, executes directly from Emporium's context [6](#0-5) .

The subsequent solvency check computes `balancesAfter[i] - balancesBefore[i]` only for tokens explicitly included in `circomData.erc20TokenAddresses`, and even if the approved token were included, `approve` doesn't change `balanceOf`, so `balanceChange == 0` and the check trivially passes [7](#0-6) . The comment at line 141 ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call") confirms the codebase's own acknowledgment that Emporium can and does carry standing/residual token balances across transactions (e.g., dust from prior swaps/actions) [8](#0-7) . Any such residual balance — present now or accrued later by any other legitimate user's flow — becomes permanently drainable by the attacker via a plain `token.transferFrom(Emporium, attacker, amount)` call made entirely outside Hinkal, at any future time, with no proof, nullifier, or root check involved.

### Impact Explanation
Critical: this sets up unlimited, attacker-controlled, un-revocable-by-victims theft of any current or future ERC20 balance Emporium holds for that token, independent of proof/nullifier verification and independent of the specific transaction that granted the approval. It requires only one crafted, self-funded transaction to plant the approval, then arbitrarily many future `transferFrom` calls to harvest any balance that ever appears. This is a direct theft vector against protocol-held/shielded funds routed through Emporium, matching the Critical bar ("direct theft of shielded or in-flight user funds").

### Likelihood Explanation
Preconditions are minimal and entirely attacker-controlled: the attacker only needs valid UTXOs of their own (obtainable via a normal deposit) to generate a self-authored proof, and to set `stack.signerAddress = address(0)` to skip the EIP-712 signature check in `verifyWallet`. No relayer, admin, or victim cooperation is required, and the attack is cheap (gas only) and fully repeatable for every ERC20 that Emporium might ever hold or receive.

### Recommendation
Restrict CASE 2 endpoint calls with an explicit allowlist of permitted target contracts/selectors (not just a selector blacklist for wallet functions), and/or forbid `approve`/`increaseAllowance`/`permit`-style selectors and any state-mutating call to ERC20 token contracts Emporium tracks unless explicitly authorized by a signed `stack.signerAddress`. Additionally, require `stack.signerAddress != address(0)` (or another strong authorization binding) whenever `ops` contains calls to arbitrary endpoints, and consider re-checking `allowance` state for all tokens in `circomData.erc20TokenAddresses` (and ideally any token Emporium can ever hold) before/after execution, not just `balanceOf`.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable` (or a lightweight harness with `onlyAllowedRecipient` set to the test contract), a mock ERC20 `TOKEN`, and fund Emporium with a nonzero standing `TOKEN` balance (simulating residual dust as acknowledged in the code comment at line 141).
2. Craft `CircomData` with `erc20TokenAddresses = []` (or containing an unrelated token), and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)`, `ops = [{endpoint: address(TOKEN), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)}]`.
3. Call `runAction(circomData, deltaAmountChanges)` from the allowed-recipient address; assert it succeeds and `TOKEN.allowance(Emporium, attacker) == type(uint256).max`.
4. Assert `balancesBefore == balancesAfter` for all tracked tokens (equality holds, proving the check is blind to the allowance change).
5. In a separate subsequent call (no Hinkal/Emporium interaction), have `attacker` call `TOKEN.transferFrom(Emporium, attacker, TOKEN.balanceOf(Emporium))` directly; assert success and that Emporium's `TOKEN` balance is fully drained to the attacker, demonstrating fund loss uncorrelated with any proof/nullifier check.

        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges

            (EmporiumStack)

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }

            else {
                bytes4 selector = bytes4(op.callData);

                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector

                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

                revert CallFailed(err);
