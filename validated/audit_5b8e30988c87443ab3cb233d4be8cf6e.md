### Title
Webhook Shop-Domain Spoofing via HMAC Signature That Only Covers Request Body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are all taken from unauthenticated HTTP headers. Because `Utils::HmacValidator.validate` only verifies that the header-supplied HMAC matches a signature computed purely over the body, the binding `hmac_verified_bytes == body` holds, but the binding the application actually relies on, `hmac_verified_shop == request.shop`, does not. Anyone who can obtain one valid `(body, hmac)` pair from a legitimate webhook delivery (e.g., an app-installing merchant receiving webhooks for their own shop) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will accept it as an authentic webhook for the victim shop.

### Finding Description
- `Request#hmac`/`Request#to_signable_string` sign only `@raw_body`: [1](#0-0) , [2](#0-1) 
- `shop`, `topic`, `webhook_id`, `api_version` are pulled straight from request headers, none of which are part of the signable string: [3](#0-2) 
- `Registry.process` validates only the HMAC of the body, then dispatches the handler with `request.shop` treated as trusted tenant identity: [4](#0-3) 
- Contrast with the OAuth callback flow, where `shop` **is** part of the signed payload (`AuthQuery#to_signable_string` includes `shop`): [5](#0-4) 

This is the same class of bug as the external report: a value that the application treats as authenticated/trustworthy (the tenant identity used for the "transfer"/dispatch operation) is not actually covered by the cryptographic check that gates the operation. Here, the equality the code implicitly assumes is `hmac_valid(body) ⇒ shop_header_is_authentic`, but the HMAC secret is shared across all shops installing the same app, so any shop that has received one legitimate webhook can produce a `(body, valid_hmac)` pair and pair it with a forged `shop` header for a different shop.

### Impact Explanation
An attacker who is a legitimate (unprivileged) user of the app — i.e., they installed the app on their own shop and thus receive real webhook deliveries — can capture a `(body, hmac)` pair and replay it against the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header set to a victim shop's domain. `Utils::HmacValidator.validate` returns true because it only checks the body signature, and `Registry.process` forwards `shop: request.shop` (the forged header) to the app's handler. This causes the host application to process attacker-controlled webhook payloads as if they originated from a different tenant, resulting in cross-tenant data injection/confusion (e.g., an `orders/create` or `app/uninstalled` webhook attributed to a shop that never sent it). This crosses a tenant boundary and matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app for their own shop (a normal, unprivileged interaction) and observe webhook deliveries, since no access token, `api_secret_key`, or privileged access is required — only a shared HMAC secret across all installs and knowledge that shop/topic/webhook-id are excluded from the signed payload.

### Recommendation
Include the tenant-identifying and routing-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., by having `to_signable_string` concatenate these header values with the raw body before hashing), so that a valid HMAC can only be produced for the exact combination of headers and body that Shopify actually sent.

### Proof of Concept
1. Install the app on shop A (attacker-controlled) and receive a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC_SHA256(secret, B)`.
2. Replay a POST to the app's webhook endpoint with the same raw body `B` and the same `X-Shopify-Hmac-Sha256: H` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` computes `HMAC_SHA256(secret, B)` and finds it matches `H`, returning `true` — see [6](#0-5) .
4. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` even though the payload actually came from shop A — see [4](#0-3) .

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
