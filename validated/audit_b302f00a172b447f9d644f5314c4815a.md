### Title
`CallDispatcher.dispatch()` is fully permissionless, letting anyone drain any tokens/ETH transiently or residually held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes an attacker-supplied array of `Call{to, value, data}` with no caller restriction whatsoever [1](#0-0) . This mirrors the `MarginTrading.executeOperation()` bug class in the report: a state-changing "callback"/dispatch entry point that moves value out on behalf of whoever calls it, reachable by any unprivileged address with attacker-chosen parameters, letting them sweep out any balance the contract happens to be holding.

### Finding Description
`CallDispatcher` is a shared utility contract (one deployment reused across `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, etc., per the documented "Existing `CallDispatcher` deployments are listed on the contract addresses page") whose `dispatch(bytes memory encoded)` function is `external` with no modifier, no `onlyOwner`, and no check on `msg.sender`:

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [1](#0-0) 

`IntentGatewayV2` and the fungible-token apps intentionally route pre-/post-dispatch swap calldata through this dispatcher and rely on it *temporarily* holding token/ETH balances while calldata executes — the docs explicitly say: "the dispatcher contract holds tokens temporarily during execution" [2](#0-1) . Callers transfer assets to the dispatcher and then invoke `dispatch()` themselves, e.g. in `IntentsBase._execute` and `IntentGatewayV2`'s predispatch flow:

```solidity
address dispatcher = _params.dispatcher;
ICallDispatcher(dispatcher).dispatch(order.output.call);
...
ICallDispatcher(dispatcher).dispatch(abi.encode(sweepCalls));
``` [3](#0-2) 

```solidity
IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount);
...
ICallDispatcher(dispatcher).dispatch(order.predispatch.call);
``` [4](#0-3) 

Because `dispatch()` itself checks nothing about the caller, any address holding no privileged role can call `CallDispatcher.dispatch()` directly (not through the gateway) with a `Call[]` that transfers `address(this).balance` or any ERC20 balance currently sitting in the dispatcher to itself. `CallDispatcher` also accepts stray ETH via `receive() external payable {}` [5](#0-4) , and because it is shared across multiple apps and orders, any leftover dust, an ERC20 with fee-on-transfer/hook behavior leaving a temporary excess balance, or a swap step that leaves residual value on the dispatcher before the caller's own sweep call executes, is a target any third party can seize the instant it appears — an outside caller doesn't need to be involved in the order at all, unlike the report's flash-loan callback which at least required going through the lending pool's `flashLoan` entry point.

### Impact Explanation
Any funds momentarily or residually held by `CallDispatcher` — ERC20 tokens or native ETH belonging to users' in-flight orders/transfers routed through `IntentGatewayV2`, `HyperFungibleToken`, or `WrappedHyperFungibleToken` — can be stolen outright by an unrelated, unprivileged caller who simply calls `dispatch()` with a `Call` that redirects the balance to themselves. This is concrete theft of funds reachable by anyone submitting a plain transaction, matching the High-severity classification of the analog report.

### Likelihood Explanation
No privileged role, governance action, or malicious insider is required — any account can call `CallDispatcher.dispatch(bytes)` directly at any time. The only precondition is that the dispatcher hold a non-zero balance at that moment, which the design explicitly creates (temporary token custody during predispatch/postdispatch execution) and which `receive() external payable {}` makes even easier to happen incidentally. Given `CallDispatcher` is a shared, reused deployment across products, the exposure window recurs on every order fill/cancellation/token transfer that routes calldata through it.

### Recommendation
Restrict `CallDispatcher.dispatch()` to trusted callers only, e.g. gate it to a specific authorized app address (set at construction/configuration) or make each `HyperApp` deploy/own its own `CallDispatcher` instance rather than sharing one globally, and add a check such as `if (msg.sender != authorizedCaller) revert Unauthorized();` at the top of `dispatch()`. Additionally, ensure any residual balance is swept back to the initiating contract before the function returns so nothing is ever left standing on the dispatcher between calls.

### Proof of Concept
1. Wait for (or trigger, e.g., via a dust-leaving swap) a state where `CallDispatcher` holds any ERC20 or native ETH balance — e.g. mid `IntentGatewayV2._execute`/predispatch flow, or simply after any transaction that sends value to the dispatcher's `receive()`.
2. From any unprivileged EOA, call:
```solidity
CallDispatcher(dispatcher).dispatch(
    abi.encode(
        [Call({to: attacker, value: address(dispatcher).balance, data: ""})]
    )
);
```
for native ETH, or a `Call{to: token, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(dispatcher))}` for an ERC20 balance.
3. `dispatch()` performs the low-level call with no caller check, transferring the dispatcher's balance to the attacker [1](#0-0) .

        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;

                size := extcodesize(to)
            }

                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
