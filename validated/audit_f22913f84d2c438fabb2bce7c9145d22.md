### Title
Stale account delegates survive position-NFT transfer, letting a prior owner's delegates keep acting on the account - ([File: contracts/controller/src/storage/account.rs](contracts/controller/src/storage/account.rs))

### Summary
The controller stores per-account delegate authorizations under `ControllerKey::Delegates(account_id)`. Those entries are keyed by account id, not by owner, and are only deleted when the account itself is removed (`remove_account_entry`). Because the controller resolves ownership live through `owner_of(account_id)` on the position NFT and "nothing in the controller changes on transfer," a delegate granted by the previous owner remains authorized after the NFT — and the whole collateralized position — moves to a new owner. This mirrors the kernel bug: a cached authorization/pointer is cleared on one teardown list (account deletion) but not on the other ownership-changing path (NFT transfer), leaving a dangling capability that is later dereferenced.

### Finding Description
- `remove_account_entry` removes `AccountMeta`, `SupplyPositions`, `BorrowPositions`, and `Delegates` — cleanup happens only on account deletion [1](#0-0) .
- Account ownership is never cached in the controller; it is resolved via `PositionNft::owner_of(token_id)` on every call, and the docs state "Transferring the token transfers the whole position. Nothing in the controller changes on transfer: the next controller call resolves the new holder and accepts it" [2](#0-1) .
- `renew_user_account` renews `Delegates(account_id)` alongside the position maps on every user operation, keeping the stale delegate entries alive with a fresh TTL even after the owner changed [3](#0-2) .
- The position NFT itself clears token-level approvals on burn, but nothing on the controller side is invoked by an NFT `transfer`/`approve`, so `Delegates(account_id)` is untouched by a sale, gift, or marketplace transfer of the position.

Consequence: any address previously registered as a delegate on the account (e.g., by a seller preparing the position for sale) retains whatever delegated powers the controller grants — debt/supply/strategy actions referenced in `positions/supply.rs`, `positions/debt.rs`, and `strategies/*` — against the new owner's collateral.

### Impact Explanation
Theft of user funds. A seller can register a delegate they control, list/transfer the position NFT, and after settlement the delegate entry — which the buyer cannot reasonably audit via `account_exists` or position views — still authorizes actions on the account. Depending on delegate scope this enables borrowing against or withdrawing the buyer's collateral.

### Likelihood Explanation
Reachable by a single unprivileged address via the permissionless `transfer`/`approve` path on the position NFT. No admin, upgrade, or oracle assumption is needed; it requires only that delegate authorization persists across ownership change, which follows directly from `Delegates` being keyed by account id and removed only in `remove_account_entry`.

### Recommendation
Treat NFT transfer as an ownership-changing event for delegated state: either (a) have the position-NFT `transfer` notify the controller to clear `Delegates(account_id)`, or (b) stamp each delegate grant with the owner at grant time and reject delegates whose stamped owner differs from the current `owner_of` result, so stale grants are implicitly voided on transfer.

### Proof of Concept
1. Alice supplies USDC into account `A`, then registers `EVIL` as a delegate for `A` via the controller's delegate-management entrypoint.
2. Alice transfers position NFT `A` to Bob (or sells it on a marketplace).
3. `EVIL` invokes a delegated controller action on `A` (e.g., borrow or withdraw path that checks `Delegates(A)`).
4. The controller resolves the owner via `owner_of(A)` → Bob for ownership checks, but the `Delegates(A)` entry — untouched by the transfer — still authorizes `EVIL`, who drains/borrows against Bob's collateral.

Caveat: I could not fully confirm the exact delegate permission surface (which controller verbs consult `Delegates` and whether delegation itself requires owner auth). The storage-level facts — delegates keyed by account id, deleted only on account removal, renewed on every operation, and ownership resolved live — are verified; if delegate grants confer no fund-moving power, this finding degrades to no impact.

```rust
/// Deletes metadata, both position maps, and delegates. Does not burn the NFT.
pub(crate) fn remove_account_entry(env: &Env, account_id: u64) {
    let persistent = env.storage().persistent();
    persistent.remove(&ControllerKey::AccountMeta(account_id));
    persistent.remove(&ControllerKey::SupplyPositions(account_id));
    persistent.remove(&ControllerKey::BorrowPositions(account_id));
    persistent.remove(&ControllerKey::Delegates(account_id));
}
```

```rust
pub(crate) fn renew_user_account(env: &Env, account_id: u64) {
    let persistent = env.storage().persistent();
    let keys = [
        ControllerKey::AccountMeta(account_id),
        ControllerKey::SupplyPositions(account_id),
        ControllerKey::BorrowPositions(account_id),
        ControllerKey::Delegates(account_id),
    ];
    for key in &keys {
        if persistent.has(key) {
            renew_user_key(env, key);
        }
    }
}
```
