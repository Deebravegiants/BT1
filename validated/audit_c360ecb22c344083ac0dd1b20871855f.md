### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) values are trusted for tenant routing despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the **raw request body**, but then hands the handler a `shop` value taken from the **`X-Shopify-Shop-Domain` HTTP header**, which is never included in the signed payload. Because the same `api_secret_key` is used to sign webhooks for *every* shop that has the app installed, any unprivileged merchant/attacker who installs the app on their own store can obtain a genuinely-signed webhook (valid body + valid HMAC) and replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop. The HMAC check still passes (it only checks the body), and the handler is invoked believing the data belongs to the victim shop.

### Finding Description
The signable string for a webhook request is defined as just the raw body: [1](#0-0) 

`shop` is read from a header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, immediately forwards `request.shop` (the unauthenticated header) to the registered handler as the tenant identifier: [3](#0-2) 

The HMAC validator itself only checks `verifiable_query.to_signable_string` against the secret — it has no knowledge of, or binding to, the `shop` header: [4](#0-3) 

The identity-binding equality that should hold is:
`shop authenticated by HMAC == shop acted upon by the handler`

In reality, the HMAC only authenticates `(body, secret)`; it says nothing about which shop the body came from. The `shop` used for tenant routing is taken from an attacker-controllable header. Since `api_secret_key` is shared across all installs of the app (it is the app's own client secret, not a per-shop secret), any shop that has installed the app can generate a body+HMAC pair that is valid for *any* shop-domain header, simply by re-signing the header value they choose — no, more precisely: they cannot forge a new HMAC without the secret, but they can take a webhook that Shopify legitimately sent them (valid body + valid HMAC for their own shop) and resend the exact same body/HMAC pair to the endpoint with a different `shop-domain` header. The HMAC still validates because it never covered that header, so the endpoint processes it as belonging to the victim shop.

### Impact Explanation
This breaks the tenant boundary between shops sharing the same app installation. A malicious merchant can cause the app to process their own webhook payloads (e.g., `orders/create`, `app/uninstalled`, etc.) as if they belonged to a different, victim shop, because `WebhookMetadata#shop` — the only tenant discriminator passed to the handler — comes from an unauthenticated header. Any host application that uses `data.shop` from `Registry.process` to select which merchant record/session/store to update (the documented and expected usage pattern) can be tricked into writing or acting on data under the wrong tenant. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on their own store (a routine, unprivileged action for any Shopify merchant) and can capture/replay a raw HTTP request (trivial with tools like `curl`). No access to `api_secret_key`, access tokens, or victim credentials is required — only a legitimately-received webhook for the attacker's own shop and knowledge of the victim's shop domain (public information).

### Recommendation
Bind the `shop` (and other trust-relevant fields such as `topic`) into the HMAC-signed payload verification, or otherwise cryptographically tie the header values to the signed body (e.g., include them in `to_signable_string`, or cross-check the `shop` header against an independently-verified value, such as the shop associated with the specific HMAC key if per-shop secrets are ever supported). At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must be independently corroborated (e.g., against an existing session/webhook subscription record) before being used for tenant-scoped writes.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`. Shopify sends a legitimate webhook:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of body B, computed with the app's shared api_secret_key>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: B
   ```
2. Attacker captures this request, then resends it to the same endpoint, changing only the header:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   Body: B   (unchanged)
   X-Shopify-Hmac-Sha256: <same, unchanged>
   ```
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes the HMAC over `B` [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the host app to process attacker-controlled data under the victim shop's tenant context.
