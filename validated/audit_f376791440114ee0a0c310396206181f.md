### Title
Webhook Shop Identity Spoofing via HMAC Scope Mismatch - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching to the app's handler with a `WebhookMetadata` struct that includes `shop`. In reality, the HMAC signature it verifies covers only the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values handed to the handler are read from unauthenticated HTTP headers. Because the signing secret (`api_secret_key`) is a single, app-wide secret shared across every merchant install, any attacker who has legitimately installed the app on their own shop can capture a genuine `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop, causing the app to process the payload under the victim's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from request headers with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks the received HMAC against `to_signable_string` (i.e. the raw body) using the shared `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request and then forwards the *unauthenticated* `request.shop` header straight into the handler-visible `WebhookMetadata`: [4](#0-3) 

The gem's own documentation reinforces the false guarantee, stating that `process` "will verify the request did indeed come from Shopify": [5](#0-4) 
and that `data.shop` is simply "The shop domain of the webhook": [6](#0-5) 

The broken identity binding, stated as an equality: the gem asserts `verified_source_shop == data.shop`, but what is actually proven is only `HMAC(api_secret_key, raw_body) == received_hmac`, which holds for **any shop using the same app** (the secret is app-wide, not per-shop). `data.shop` is taken from an unauthenticated header that is disjoint from the signed bytes.

### Impact Explanation
Any merchant who installs the app (an unprivileged, ordinary internet user with respect to other tenants) can:
1. Register/observe a webhook topic on their own shop and capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered by real Shopify infrastructure.
2. Replay that exact body and HMAC to the app's public webhook endpoint, substituting `X-Shopify-Shop-Domain` (and optionally `topic`) with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the raw body against the shared secret, so `Registry.process` dispatches to the app's handler with `WebhookMetadata#shop` set to the victim's domain.

Depending on what the app's webhook handlers do (e.g., trigger sync/uninstall logic, invalidate caches, write to per-shop records, mark subscription/billing state, queue background jobs keyed by shop), this results in cross-tenant action being taken against a shop the attacker does not control — satisfying the "cross-tenant access" Critical/High impact bar, since the trust boundary between tenants is broken purely through the gem's own verification logic.

### Likelihood Explanation
Exploitation only requires: (a) an unprivileged attacker installing the target app on their own store (standard, no special access), and (b) sending one crafted HTTP POST with a copied raw body/HMAC and a modified shop-domain header. No access token, `client_secret`, or privileged account is needed — only a self-service app install, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity to the verified bytes: include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload check, or independently verify that `request.shop` corresponds to a shop with a currently active, previously-established session/installation record before constructing `WebhookMetadata`. At minimum, update `Utils::HmacValidator`/`Webhooks::Request` so `to_signable_string` incorporates the shop-domain header (or have `Registry.process` cross-check `request.shop` against known installed shops) rather than trusting the header purely because the body HMAC matched.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook, capturing:
   - `raw_body`
   - `X-Shopify-Hmac-Sha256: <valid-hmac-for-raw_body>`
2. Attacker POSTs to the app's webhook endpoint (e.g. `/callback/orders/create`) with:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same valid hmac captured above>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: <same raw_body captured above>
   ```
3. `ShopifyAPI::Webhooks::Request.new` builds a request object from these headers/body.
4. `HmacValidator.validate` recomputes HMAC over `raw_body` using the shared `api_secret_key` and it matches, since only the body (not the shop header) is signed — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) passes validation and invokes the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process attacker-supplied webhook data as if it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
