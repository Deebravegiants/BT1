This confirms the vulnerability. The `Session#id` for offline sessions is fully deterministic: `id = "offline_#{shop}"` [1](#0-0) , and for online sessions it's `"#{shop}_#{associated_user.id}"` [2](#0-1) . This exact deterministic ID is what gets written verbatim into the non-embedded session cookie [3](#0-2)  and is later read back with zero verification by `cookie_session_id` [4](#0-3) , feeding directly into `current_session_id` for both non-embedded flows and the embedded-app cookie fallback path [5](#0-4) .

### Title
Session identity binding relies on a guessable, unsigned cookie value, allowing cross-tenant session hijacking - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
The gem's documented session-lookup mechanism binds "the session id trusted by `current_session_id`" to "any bytes present in the `shopify_app_session` cookie," with no cryptographic signature or nonce tying the cookie to the browser that completed OAuth. Because `Session#id` is deterministically derived from public information (the shop domain, and for online sessions the numeric associated-user id), an attacker can construct a target's exact session id and simply set it as their own cookie value.

### Finding Description
During `validate_auth_callback`, the returned `SessionCookie.value` is set to `session.id` verbatim for non-embedded (and non-embedded-cookie-fallback) flows [3](#0-2) . That id is not a random secret — it is generated as `"offline_#{shop}"` for offline sessions or `"#{shop}_#{associated_user.id}"` for online sessions [6](#0-5) , both fully derivable from public/guessable data (a store's `myshopify.com` domain, and low-cardinality Shopify user ids).

Later, `SessionUtils.current_session_id` retrieves this identifier straight from the cookie via `cookie_session_id`, which does nothing but echo `cookies[SessionCookie::SESSION_COOKIE_NAME]` back [4](#0-3) . There is no HMAC, no signature, and no binding back to the OAuth state/nonce that was validated during the callback. The equality the app relies on for tenant isolation — "cookie value provided by the browser" == "the shop/session the app should authenticate as" — is never actually verified; it is merely assumed.

This is functionally analogous to the VaultFacet report's underlying bug class: a value used to make security-relevant/tenant-identifying decisions is trusted without being cryptographically bound to the party that is supposed to control it. Here, instead of an owner unilaterally rug-pulling collateral parameters, an unprivileged attacker unilaterally sets an unsigned identity token (the cookie) that the receiving code treats as authoritative for session retrieval.

### Impact Explanation
Any application built on this gem's documented, non-embedded cookie flow — or the embedded cookie-fallback path — inherits an identifier the gem itself computes deterministically and hands back unsigned. If a host app's session store (as shown in the gem's own official example in `BREAKING_CHANGES_FOR_V16.md`, `retrieve(id) { find_by(id: id) }`) looks a session up purely by this id, an attacker who sets `shopify_app_session=offline_target-shop.myshopify.com` in their own browser can cause the app to load and act on the target shop's `access_token`, resulting in cross-tenant access to another merchant's Shopify data through the app.

### Likelihood Explanation
Exploitation requires no credentials, no TLS interception, and no privileged access — only knowledge of the target's `.myshopify.com` domain (public) and, for online sessions, the target's numeric Shopify user id (low entropy, often enumerable). The attacker only needs to send a request to the app with a forged cookie value; this is squarely within reach of an unprivileged internet user interacting with the app's own documented cookie mechanism.

### Recommendation
Do not use a deterministic, predictable string as the value stored directly in the session cookie. Either sign/HMAC the cookie value with the app's `api_secret_key` (verified before being trusted by `cookie_session_id`), or store a high-entropy random token in the cookie that maps to the deterministic session id server-side, so that possession of the cookie — not just knowledge of the shop domain — is what proves the session's identity.

### Proof of Concept
1. Attacker observes/knows the victim's store domain, `victim-shop.myshopify.com`, which is public knowledge.
2. Attacker sets their own browser cookie: `shopify_app_session=offline_victim-shop.myshopify.com`.
3. Attacker visits the app; the app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged via `cookie_session_id` [5](#0-4) .
4. The host app's session storage (per the gem's own documented pattern) looks up and loads the victim's stored `Session`, including `access_token`, and the attacker's subsequent requests are authenticated as the victim shop.
