### Title
Webhook `shop-domain`, `topic`, `webhook_id` and `api_version` headers are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while the tenant-identifying `shop` (and `topic`/`webhook_id`/`api_version`) values are read from HTTP headers that are never included in that signable string. `Registry.process` accepts any request whose body-only HMAC validates, then hands the caller-supplied `shop` header straight to the webhook handler as the authoritative tenant identifier.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field [1](#0-0) .

For webhooks, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers that are not part of the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC (body-only) and then forwards the unauthenticated `request.shop` value to the application's webhook handler as the tenant identity for the payload: [4](#0-3) 

This is the same class of bug as the reference report: a value that is *acted upon* (here, the tenant/shop binding for the delivered payload) is disjoint from the value that is *cryptographically verified* (here, only the JSON body bytes). The equality that should hold — `HMAC-covered-bytes ⊇ {shop, topic}` — does not hold; instead `HMAC-covered-bytes = raw_body` while `shop = header("shopify-shop-domain")`, entirely attacker-suppliable in any raw HTTP request that reaches the shared webhook endpoint.

### Impact Explanation
Any request delivered to the app's single, shared webhook endpoint with a body/HMAC pair that is valid for the app's secret (obtained from any legitimate delivery, e.g. one addressed to the attacker's own shop) can be replayed with an arbitrary `shopify-shop-domain` header. Because the gem does not bind `shop` to the signature, the host application's handler will process the (attacker's own, but validly-signed) payload as if it belongs to a different tenant, since `WebhookMetadata#shop` is taken from the unauthenticated header. Depending on how the host app keys per-tenant behavior off of `data.shop` (loading sessions/access tokens, writing to per-shop records, invoking mandatory GDPR compliance flows, etc.), this can lead to cross-tenant data corruption/injection — one of the accepted "Critical" categories (cross-tenant access).

### Likelihood Explanation
Exploitation does not require the app's `client_secret`/`api_secret_key`: HMAC validation only ever checks the body bytes, so a merchant who legitimately receives one valid (body, HMAC) pair for their own shop (a routine, unprivileged event — install the app, trigger any subscribed action) already possesses everything needed to replay it against the shared webhook URL with a forged `shop-domain` header. However, actually delivering a *replayed* HTTP request requires the attacker to have captured that legitimate delivery in transit (webhooks are pushed server-to-server by Shopify directly to the app, not exposed to the merchant's browser), which most deployments don't hand to an unprivileged party. This materially limits real-world likelihood even though the missing binding itself is a clear root-cause defect in the gem.

### Recommendation
Include the tenant-identifying header values (`shop`, and ideally `topic`/`webhook_id`) inside the signed/verified material, or independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it in `WebhookMetadata`. At minimum, document and enforce that host applications must cross-check `data.shop` against their own installed-shop records rather than trusting it as authenticated solely because the HMAC passed.

### Proof of Concept
1. App exposes one webhook endpoint (e.g. `/webhooks`) shared by all installed shops, registered via `ShopifyAPI::Webhooks::Registry`.
2. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a subscribed event (e.g. `products/update`), causing Shopify to deliver a webhook with body `B` and header `x-shopify-hmac-sha256: H = HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com` to the shared endpoint.
3. Having obtained a genuine `(B, H)` pair (e.g. via a delivery-inspection feature, retry/replay tooling, or any channel that surfaces the raw delivery to the shop owner), the attacker sends a new HTTP request to the same endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds (verifies only `B` against `H`) [5](#0-4) , and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` [6](#0-5) , causing the host application to process attacker-controlled data under the victim tenant's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
