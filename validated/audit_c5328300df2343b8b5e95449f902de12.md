### Title
Webhook `shop` (tenant) identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used to identify the tenant are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then forwards the header-derived `shop` value to the application's webhook handler as the trusted tenant identifier. This breaks the equality that should hold: `HMAC-verified bytes == bytes used to determine tenant identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are read directly from HTTP headers, with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC: [3](#0-2) 

`Registry.process` raises only if the body HMAC fails, then immediately trusts `request.shop` (an unauthenticated header) as the tenant identity handed to the app's handler: [4](#0-3) 

Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is identical across every merchant/tenant that has the app installed, a valid `(raw_body, hmac)` pair generated for one shop remains cryptographically valid for any other shop. An unprivileged user who can install the app on their own store (or otherwise trigger a webhook delivery to themselves) can capture a legitimately-signed `(body, hmac)` pair, then replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. `HmacValidator.validate` will still succeed since it never inspects the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: the gem allows an attacker-controlled, validly-signed payload to be attributed to an arbitrary victim shop, because the identity field (`shop`) that host applications rely on to key their per-tenant logic (e.g., updating orders/inventory/customer records scoped by shop) is never bound to the HMAC. Any host application that follows this gem's documented pattern (validate via `Registry.process`, trust `WebhookMetadata#shop`) inherits this cross-tenant data-integrity gap without any indication from the library that the header is unauthenticated.

### Likelihood Explanation
Exploitation only requires: (1) the ability to install/operate the target app on an attacker-owned store to obtain one legitimately signed `(body, hmac)` pair (no special privileges, no leaked secrets, no TLS interception needed), and (2) the ability to send arbitrary HTTP requests to the app's public webhook endpoint with a modified `shop`/`topic` header. Both are available to a standard unprivileged internet user/merchant.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content used for HMAC validation, or have `Registry.process`/`HmacValidator` cryptographically bind the header-derived `shop` value to the verified payload (e.g., by requiring the caller to supply the expected shop and comparing it against a value covered by the signature, or by re-deriving the signing key per shop) before trusting `request.shop` for any tenant-scoped action.

### Proof of Concept
1. Install the target app (built on `shopify_api`) on attacker-owned store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimately Shopify-signed request: headers include `x-shopify-hmac-sha256: <hmac>`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
2. Capture `(B, hmac)`.
3. Send a forged HTTP POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: <hmac>` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body; `HmacValidator.validate` succeeds because it only checks `B` against the shared `api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the application to process attacker-controlled data under the victim tenant's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
