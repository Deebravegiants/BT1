### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0)  while the `shop` value that the registry hands to application handlers is read straight from the `X-Shopify-Shop-Domain` header, outside of the HMAC-protected data [2](#0-1) . `Registry.process` validates the HMAC over the body only and then dispatches to the handler using the unauthenticated `shop` header value [3](#0-2) .

### Finding Description
`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it with the `hmac` value using `OpenSSL.secure_compare` [4](#0-3) . For webhook requests, `to_signable_string` is defined as the raw request body only [1](#0-0) ; the `topic`, `shop-domain`, `api-version`, and `webhook-id` values are read directly from HTTP headers and are never included in the signable string [5](#0-4) .

`Registry.process` raises `InvalidWebhookError` only if the body-only HMAC fails, and otherwise builds `WebhookMetadata` using `request.shop` taken straight from the header, then invokes the application's `handler.handle` with that unauthenticated shop value [3](#0-2) .

This breaks the identity binding: `shop-domain header == tenant identifier trusted by the handler`, without that header ever being bound to the HMAC signature that supposedly authenticates the request as coming from Shopify for that shop. Concretely: HMAC(body) is valid ⇏ shop-domain header is authentic. An attacker who is a legitimate (unprivileged) merchant can register the app on their own store, capture a genuine webhook delivery (valid HMAC over a body they control/observe), and replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value naming a different, victim shop. `HmacValidator.validate` will still succeed because it never inspects the header, and the app-level handler will process the payload believing it originated from the victim shop, since `WebhookMetadata#shop` is populated from the spoofed header [6](#0-5) .

### Impact Explanation
Any application using this gem's `Registry.process` to dispatch webhook handlers keyed by `data.shop` (the documented and only way to know which tenant a webhook belongs to) is exposed to cross-tenant data confusion: a valid-HMAC webhook can be attributed to an arbitrary shop domain chosen by the attacker, since the shop identity is not bound to the cryptographic proof of Shopify origin. This matches the "cross-tenant access" critical-impact category, because the tenant boundary (which shop a webhook event belongs to) is defined entirely by an unauthenticated header.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled Shopify store (an ordinary, unprivileged merchant action, no leaked secrets needed), (2) capturing one legitimately-delivered, validly-signed webhook for that store, and (3) resending the identical raw body with the identical `hmac-sha256` header to the app's public webhook endpoint while changing only the `shop-domain` header. No knowledge of `api_secret_key` is required because the HMAC never covers the header that is being forged.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) headers in the HMAC-signable data for webhook requests, or otherwise cryptographically bind the header-derived `shop` value to the verified payload before it is passed to `WebhookMetadata`/handlers, e.g., by re-deriving/confirming the shop from an independently-trusted source (such as an active offline session lookup) rather than trusting the raw header once HMAC-over-body succeeds.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and subscribe to any webhook topic.
2. Capture a real webhook delivery: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` with the app's secret), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Resend an HTTP POST to the app's webhook endpoint with the exact same body `B` and the exact same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and adjust `X-Shopify-Webhook-Id`/`Topic` headers as desired, since those are also unsigned).
4. `ShopifyAPI::Utils::HmacValidator.validate` in `Registry.process` [7](#0-6)  succeeds because it only checks `B` against `H`.
5. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the application to process attacker-supplied data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
