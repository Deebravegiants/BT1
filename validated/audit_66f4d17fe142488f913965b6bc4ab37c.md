### Title
Non-Membership Proofs Are Normalized to the Same Encoding as On-Chain Empty Values, Collapsing a Provable-Absence/Presence Distinction Before Delivery to EVM Apps - ([File: modules/ismp/core/src/abi.rs])

### Summary
When Hyperbridge constructs a `GetResponse` for delivery to an EVM `HyperApp`, the verified `StorageValue.value: Option<Vec<u8>>` — where `None` cryptographically proves a key is **absent** from state (a non-membership proof) and `Some(vec![])` proves the key **exists** with an empty payload — is silently collapsed into the same wire form via `.unwrap_or_default()`. Both cases become an empty `bytes` value once encoded for Solidity, exactly mirroring the zcashd/Zebra bug class: a distinct, semantically meaningful on-the-wire state is normalized away by one code path (Rust ABI conversion for EVM delivery) while the authoritative Rust-side model (`Option<Vec<u8>>`) still treats them as different states.

### Finding Description
The protocol-level `StorageValue` type explicitly documents the distinction: [2](#0-1) 

This is preserved through state-machine proof verification, where `None` and `Some(vec![])`/`Some(bytes)` are kept apart in the `BTreeMap<Vec<u8>, Option<Vec<u8>>>` returned by `verify_state_proof`, and consuming code inside Rust (e.g. non-membership checks) explicitly matches on `is_some()`/`is_none()`: [3](#0-2) 

However, at the boundary where a `router::GetResponse` is converted into the Solidity-facing ABI type delivered to `HandlerV2`/`EvmHost` consumers, both conversions discard the `Option` via `unwrap_or_default()`: [4](#0-3) 

After this conversion, a Solidity `StorageValue.value` of length zero is produced identically whether the underlying state proof was:
- a non-membership proof (key never existed / cryptographically absent), or
- a membership proof for a key that legitimately stores an empty byte string (a state possible on Substrate/Polkadot destinations, whose storage items can hold `Vec<u8>::new()` or unit values, unlike raw EVM storage slots which are simply absent when zero).

Any `HyperApp` receiving a `GetResponse` via `onGetResponse` and branching on `value.length` cannot distinguish these two states, even though the ISMP host itself proved something semantically different for each. This is architecturally the same failure mode as the zcashd advisory: a field or variant that should be preserved through the wire representation is instead normalized to a fixed default, so two logically different verified facts become indistinguishable to downstream logic, while the authoritative Rust model that produced them still distinguishes them internally.

### Impact Explanation
Applications built on Hyperbridge's GET-request/response primitive (documented examples include balance reads, reserve reads, and the intents `onGetResponse` "is this order filled?" checks) rely on `value.length == 0` (or `!= 0`) as a proxy for "the queried state does not exist" vs. "the queried state exists." Because non-membership and membership-with-empty-value collapse to the same encoding:
- An app intending to treat "key never written" and "key present with empty content" as different application states (e.g., "order not yet filled" vs. "order filled by an explicitly-zero-length payload", or "account not yet initialized" vs. "account initialized with empty metadata") cannot do so safely — an attacker who can steer or wait for either proof shape gets an identical `GetResponse` delivered on the destination chain.
- This can lead to unauthorized app actions (an app branch intended only for provable non-existence instead firing for a legitimate present-but-empty value, or vice versa), which for escrow/refund-style flows built on this primitive constitutes a path to incorrect fund release or freezing decisions driven purely by which trie-proof shape a relayer happened to submit.

### Likelihood Explanation
The conversion is unconditional and reached by every GetResponse delivered from Hyperbridge/Substrate-side state machines to Solidity-based `HyperApp`s — no privileged action is required, only an ordinary GET-request/response cycle initiated by any dispatcher. The two proof shapes (true non-membership vs. an explicit empty value) are both reachable states on Substrate/Polkadot-style destination chains supported by Hyperbridge's state-machine clients, so a relayer or the natural state of a target chain can produce either shape without any special privilege.

### Recommendation
Preserve the `Option<Vec<u8>>` semantics through to the Solidity-facing representation instead of coercing `None` to a default empty vector — e.g., encode presence/absence explicitly (a boolean flag, sentinel encoding, or by reverting/omitting the entry) so that `HyperApp` consumers of `GetResponse` can distinguish "proven absent" from "proven present but empty" rather than relying on `.length == 0` as an overloaded signal for both.

### Proof of Concept
1. Dispatch a `GetRequest` targeting a Substrate/Polkadot storage key that the destination pallet defines as capable of holding an empty `Vec<u8>` (i.e., a key that can be membership-proven with `Some(vec![])`).
2. Separately, dispatch a `GetRequest` targeting a key that has genuinely never been written (yielding `None` via non-membership proof).
3. Observe that `From<router::GetResponse> for ismp_abi::...::GetResponse` (`modules/ismp/core/src/abi.rs:143-172`) encodes both responses' `StorageValue.value` as an identical zero-length `bytes` on the Solidity side.
4. Any `HyperApp::onGetResponse` implementation branching on `values[i].value.length` (as shown in `evm/src/apps/intentsv2/ExtrinsicIntents.sol:360-366` and `evm/tron/contracts/apps/IntentGatewayV2.sol:738-743`, and in documented patterns at `docs/content/developers/evm/messaging/get-requests.mdx:257-267`) cannot tell these two proofs apart, confirming the normalization collapses a semantically distinct, cryptographically-verified pair of states into one encoding.
