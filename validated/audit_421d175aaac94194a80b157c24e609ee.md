### Title
Webhook `shop` (and other Shopify headers) are not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-valid webhook deliveries - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [4](#0-3) . However, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , so the HMAC never authenticates the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers. Yet `Registry.process` passes `request.shop` — read straight from the unauthenticated header [1](#0-0)  — directly into `WebhookMetadata` handed to the host app's handler [5](#0-4) . This breaks the identity binding: `HMAC-verified bytes (body)` ≠ `shop identity used for tenant routing (header)`.

### Finding Description
The equality that should hold is: *bytes authenticated by the HMAC == bytes/fields the application acts on to determine tenant (shop) identity*. Here it does not hold — the signature only covers the body, while the shop attribution the host application relies on for multi-tenant data isolation comes from a header outside the signed payload.

An unprivileged internet user can independently install the target Shopify app on their own store (a normal, unprivileged action requiring no special credentials). Doing so causes Shopify to send that user's shop legitimate webhooks — complete with a valid HMAC computed over the body with the app's shared secret. Since the attacker legitimately possesses these valid `(body, hmac)` pairs for their own shop, they can replay the exact HTTP request to the app's public webhook endpoint while only changing the `x-shopify-shop-domain` header to a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it never inspects headers [6](#0-5) , and the forged `shop` value flows straight into the handler's `WebhookMetadata` unquestioned.

### Impact Explanation
This enables cross-tenant data confusion: an attacker can inject data attributed to a shop they do not own into a receiving app's per-shop records (e.g., causing the app to process/store attacker-controlled order/customer/product payloads as if they belong to the victim shop), because the shop-to-payload binding the gem asserts is authenticated is, in fact, unauthenticated. This matches the Critical "cross-tenant access" impact category, since it lets a normal, unprivileged app-installer cross into another merchant's tenant data boundary purely through data the gem exposes as "verified."

### Likelihood Explanation
Likelihood is high for any developer who trusts `ShopifyAPI::Webhooks::Registry.process`'s successful HMAC validation as a guarantee that the entire webhook — including the shop attribution — is authentic (which is the natural, and encouraged, reading of "HMAC validated" in `docs/usage/webhooks.md`). The only prerequisite is installing the target app on an attacker-owned shop, a zero-privilege action available to anyone.

### Recommendation
Extend `to_signable_string` (or add a separate verification step in `Registry.process`) to bind the `shop-domain`, `topic`, and `webhook-id` header values into what's authenticated, or otherwise document/enforce that the caller must independently reconcile `request.shop` against the shop tied to the session/subscription that is expected to receive that specific `webhook_id`/topic combination before trusting `WebhookMetadata#shop` for tenant routing.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a legitimate webhook, e.g. an `orders/create` webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker captures this full raw HTTP request (body `B`, valid HMAC, and headers).
3. Attacker replays it to the same app's public webhook endpoint but overwrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (leaving body `B` and the HMAC header untouched).
4. `Utils::HmacValidator.validate` succeeds because it only recomputes over `@raw_body` [7](#0-6) .
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `shop == "victim-shop.myshopify.com"` [5](#0-4) , and the host app's handler processes attacker-controlled data under the victim's tenant context.
