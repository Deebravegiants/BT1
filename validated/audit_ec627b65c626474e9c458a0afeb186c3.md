### Title
Webhook `shop` identity not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook verification (`Utils::HmacValidator.validate`) authenticates only the raw JSON body of an incoming webhook [5](#0-4) . The `shop` value that identifies which tenant the webhook belongs to is read straight from an unauthenticated HTTP header (`x-shopify-shop-domain`) and is never included in the HMAC-signed bytes [6](#0-5) . `Registry.process` treats this header value as trustworthy and hands it directly to the app's webhook handler as `WebhookMetadata#shop` after only checking the body HMAC [3](#0-2) .

### Finding Description
The binding that should hold is: `shop_authenticated_by_hmac == shop_acted_on_by_handler`. In `Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC computed by `HmacValidator.compute_signature` covers only the JSON body bytes, using the shared `Context.api_secret_key`/`old_api_secret_key` for the app (this secret is identical for every shop that installs the same app) [7](#0-6) . Meanwhile `shop` is parsed from `shopify-shop-domain`/`x-shopify-shop-domain`, a plain header not covered by that signature at all [2](#0-1) .

Because the same app secret is shared across every shop that installs the app, any merchant who has legitimately installed the app can capture one authentic webhook delivery (raw body + valid HMAC) that Shopify sent for their own shop, then resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Registry.process` only calls `Utils::HmacValidator.validate(request)`, which re-derives the signature purely from `to_signable_string` (the body) and never checks the header against anything [3](#0-2) . The forged request therefore passes validation, and the handler receives `WebhookMetadata.new(topic:, shop: request.shop, ...)` with an attacker-chosen `shop` value that the host application will treat as authenticated tenant identity [4](#0-3) .

This is a direct analog of the report's bug class: a field ("shop") that is acted upon by downstream logic is not covered by the integrity check ("bytes verified versus bytes parsed" / "shop authenticated versus the shop stored").

### Impact Explanation
Any application built on this gem that keys per-tenant state, deduplication, or side effects (order sync, inventory writes, GDPR/mandatory topic processing, credential-linked lookups) off `WebhookMetadata#shop` can be made to attribute an attacker-controlled payload to a different, victim shop. This is a cross-tenant data-integrity/authentication-boundary violation — Critical per the scope's cross-tenant access class — because it lets one tenant's holder of a legitimately-issued webhook forge webhook events "from" any other shop using the same app.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even trial) install of the target app — no access token, secret, or privileged account is needed, satisfying the "unprivileged internet user" bar. Capturing one's own webhook deliveries and replaying them with a modified header is trivial (e.g., via curl), so likelihood is high wherever the host app trusts `WebhookMetadata#shop` for tenant-scoped actions.

### Recommendation
- **Short term:** Document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must not be trusted as a tenant identifier by itself; require host apps to cross-check it against the shop associated with the resource/topic in the payload, or against a shop known from an already-authenticated session.
- **Long term:** Extend `Request#to_signable_string` (or add a companion check) so that the shop-domain header is bound into the integrity verification — e.g., validate that the header matches a shop the app has on record for that installation before dispatch, or require Shopify to include the shop in the signed payload and reject mismatches in `Registry.process`.

### Proof of Concept
1. Install the target app on shop `attacker-shop.myshopify.com`; capture one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's shared secret), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Replay the exact same body `B` and `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the signature from `to_signable_string` (body only) — matches `H`, so validation succeeds [8](#0-7) .
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [9](#0-8) , causing the app to act on attacker-controlled data as though it originated from `victim-shop.myshopify.com`.
