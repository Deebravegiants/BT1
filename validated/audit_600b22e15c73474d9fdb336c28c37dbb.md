### Title
Attacker drains any vault shares held collectively by `EmporiumUpgradeable` via unauthenticated `redeem()` CASE 2 op, stealing prior depositors' funds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes CASE 2 ("Stateless Interaction") ops with `op.endpoint.call(...)`, so `msg.sender` inside the target contract is always `address(emporium)` regardless of which user submitted the `transact`. Any ERC4626 vault that a victim previously deposited into with `receiver = address(emporium)` holds shares owned by `address(emporium)`, and because ERC4626's `redeem(shares, receiver, owner)` only checks `msg.sender == owner` (or an allowance) when `owner` is passed as `address(emporium)`, any unrelated attacker can call `redeem` through their own, independent `transact`/CASE 2 op and pass that check trivially, since Emporium itself is a shared singleton across all users.

### Finding Description
The broken equality is: **authority over vault shares should be scoped to the depositing stealth-address/UTXO owner, but on-chain it is scoped only to `address(emporium)`**, a contract shared by every Hinkal user.

Victim's deposit (CASE 2): `op.endpoint.call(deposit(amount, address(emporium)))` executed from `EmporiumUpgradeable.runAction` [1](#0-0)  mints vault shares to `address(emporium)`. The resulting balance increase (share token or eventually underlying) is turned into a fresh UTXO for the victim only via `handleOut`, encrypted for the victim's `stealthAddressStructure` [2](#0-1) . Nothing on-chain in the vault itself records that these shares "belong" to that stealth address — that binding exists only off-chain in the encrypted commitment.

Attacker's separate `transact` later submits a CASE 2 op `{endpoint: vault, callData: redeem(shares, attackerReceiver, address(emporium))}`. Inside `runAction`, since `invokeWallet` is false or `signerAddress == address(0)`, the call goes through the CASE 2 branch: `op.endpoint.call{value: op.value}(op.callData)` [1](#0-0) . Because Emporium calls the vault directly (not via delegatecall or `IHinkalWallet.callHinkalWallet`), `msg.sender` observed by the vault's `redeem` is `address(emporium)`. The attacker sets `owner = address(emporium)` in the call data, so the vault's standard `msg.sender == owner` authorization passes — with zero allowance and zero involvement of the victim.

The resulting balance increase on Emporium is turned into `utxoOut` via `handleOut`, based purely on the ERC20 balance diff, with no requirement that the caller actually owns any UTXO representing those shares [2](#0-1) .

To pass `Hinkal.sol`'s value-conservation check `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` [3](#0-2) , the attacker simply sets `circomData.onChainCreation[i] = true` for the underlying/withdrawn token. `HinkalHelper.checkOnchainCreation` only requires that the transaction is external (not `externalActionId == 0`), that `amountChanges[i] == 0`, and that `inputNullifiers[i][j] == 0` [4](#0-3)  — it never checks that the attacker actually owns any prior claim to the funds being redeemed. This means the attacker spends **no nullifier at all** and needs **no valid prior UTXO**; they simply harvest whatever balance increase the `redeem()` call produces and mint themselves a brand-new on-chain UTXO for it via `insertCommitments`/`onChainCommitments` [5](#0-4) .

None of the existing guards prevent this:
- `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate array shapes and internal consistency of `circomData`, not that the caller has a legitimate economic claim on funds created via `onChainCreation` [6](#0-5) .
- `verifyProof`/circuit constraints only bind the attacker's own inputs/outputs (their own nullifiers and commitments); since `inputNullifiers[i]` is forced to zero for the `onChainCreation` token, the circuit never constrains ownership of the redeemed shares.
- `onlyAllowedRecipient` on `EmporiumUpgradeable.runAction` only checks that the caller is the registered `Hinkal` contract, not that the underlying op is authorized by the rightful depositor [7](#0-6) .
- `verifyWallet`/EIP-712 signature checks in Emporium only apply to CASE 1 (`invokeWallet` + `signerAddress != 0`) ops; CASE 2 explicitly bypasses any signature requirement.

### Impact Explanation
Any funds routed through `EmporiumUpgradeable` into an ERC4626 (or any contract with an owner/`msg.sender`-based authorization model) where the shares/position end up owned by `address(emporium)` can be stolen outright by an unrelated attacker in a completely separate transaction, with no proof of prior deposit, no nullifier spend, and no signature. This is direct theft of a victim's shielded, vault-routed deposit — Critical severity (direct theft of shielded/in-flight user funds; value created via `onChainCreation` with no economic backing). The attack is fully repeatable against every past and future victim deposit routed the same way, and against every vault/endpoint interacted with through CASE 2 ops where authorization keys off `msg.sender`/`owner` rather than a Hinkal-specific caller identity.

### Likelihood Explanation
Preconditions: at least one prior (or even the attacker's own concurrent) CASE 2 deposit into a vault with `receiver = address(emporium)`, leaving shares/assets held by the Emporium contract. The attacker needs no special role — any EOA can submit a `transact` with a self-crafted `CircomData`/`Dimensions`/`EmporiumStack` (all attacker-controlled fields per the threat model), set `onChainCreation[i] = true`, `amountChanges[i] = 0`, `inputNullifiers[i] = [0,...]`, and encode the `redeem` call data with `owner = address(emporium)`. The exploit cost is just gas plus generating a valid Groth16 proof over their own (irrelevant/empty) inputs, which is trivial to produce off-chain. It is fully repeatable for every unit of value sitting in Emporium-owned vault positions.

### Recommendation
Do not allow `onChainCreation` (or any UTXO minted from a bare balance-diff) to be used together with external-action calls whose target authorization is keyed off `address(this)`/`msg.sender` at the endpoint level, unless Emporium enforces its own internal, per-position accounting (e.g., track per-stealth-address share balances explicitly on-chain, or force all vault interactions through the `IHinkalWallet.callHinkalWallet` CASE 1 path with a signature bound to the specific depositor, disallowing `owner == address(emporium)` redemptions from CASE 2 unless the caller is cryptographically proven to be the original depositor). At minimum, require that `onChainCreation` UTXOs originating from external-action balance increases can only be created by the same `circomData.originalSender`/proof context that performed the corresponding deposit, or require CASE 2 redemption-type calls (`redeem`, `withdraw`, and similarly privileged calls with an `owner`/`from` parameter equal to `address(emporium)`) to be disallowed entirely and only permitted via CASE 1 signed operations.

### Proof of Concept
Hardhat fork test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, `HinkalHelper`, and a mock ERC4626 vault wrapping a mock ERC20.
2. Victim: submit `transact` with a valid proof, CASE 2 `EmporiumOperation{endpoint: vault, invokeWallet:false, callData: deposit(1000e18, address(emporium))}`, `amountChanges[underlying] < 0` (funds pulled from victim), `onChainCreation[shareOrUnderlying] = false`. Assert vault shares now held by `address(emporium)` equal `1000e18`-equivalent, and victim's UTXO commitment is inserted with `balanceDif == amountChanges + utxoAmount` holding on both sides.
3. Attacker (unrelated address, no relation to victim's UTXO/nullifiers): submit a second, independent `transact` with a locally-generated proof over the attacker's own (empty/zero) UTXO set, CASE 2 `EmporiumOperation{endpoint: vault, invokeWallet:false, callData: redeem(sharesHeldByEmporium, attackerAddress, address(emporium))}`, `onChainCreation[underlying] = true`, `amountChanges[underlying] = 0`, `inputNullifiers[underlying] = [0,...]`.
4. Assert: (a) the vault call succeeds because `msg.sender == owner == address(emporium)`; (b) attacker's on-chain UTXO/balance increases by the full `1000e18` withdrawn amount; (c) no nullifier belonging to the victim (or to any real deposit of the attacker) was inserted for that amount — i.e., `nullifiers[...]` mapping shows no entry consuming value equal to the stolen amount; (d) `balanceDif == 0 (amountChanges) + utxoAmount (1000e18)` holds trivially on the attacker's side while the victim's originally deposited value is gone.
5. Confirm the victim cannot later redeem their own UTXO for the equivalent value because the underlying vault position has been fully drained by the attacker.

                if (onChainCreation[i]) break;
                length += offChainCommitments[i][j] != 0 ? 1 : 0;
            }
        }
        length += onChainCommitments.length;

        if (length > 0) {
            // 2) Flattening leaves array
            uint256[] memory leaves = new uint256[](length);
            uint256 index = 0;
            for (uint256 i = 0; i < offChainCommitments.length; i++) {
                for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        leaves[index++] = offChainCommitments[i][j];

                }
