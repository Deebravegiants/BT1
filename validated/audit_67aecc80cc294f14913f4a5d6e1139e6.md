### Title
Webhook shop/topic identity fields excluded from HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers from the HMAC-signed bytes, while `ShopifyAPI::Webhooks::Registry.process` trusts those same unsigned headers to route and identify the tenant for the webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` as `@raw_body` only [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers, entirely outside the HMAC-covered bytes [2](#0-1) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — which hashes `to_signable_string` (the body) against `Context.api_secret_key` [3](#0-2) [4](#0-3)  — and then dispatches to the app's handler using `request.shop`, `request.topic`, and `request.webhook_id` taken directly from the (unsigned) headers [5](#0-4) .

The identity binding that should hold is: `hmac-verified bytes == bytes the handler acts upon (including shop/topic)`. Here it does not: the verified bytes are `{raw_body}`, but the handler acts upon `{shop, topic, webhook_id} ∪ {raw_body}`, where the former set is attacker-controllable without invalidating the signature.

`Context.api_secret_key` is the app's single client secret shared across every shop that has installed the app — it is not a per-shop secret [6](#0-5) . Consequently, any user who has installed the app on their own shop can capture one legitimately-signed webhook delivery (e.g., an `app/uninstalled` event, whose body is commonly `{}` and shop-independent, as used in the test fixtures [7](#0-6) ), and replay that exact `raw_body` + valid `hmac-sha256` header to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) to name a victim shop. `HmacValidator.validate` will still pass because the signature only ever covered the body, and the handler will receive `WebhookMetadata` claiming the victim's shop [5](#0-4) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an attacker who is merely an installer of the app (unprivileged, no access token, no leaked secret, no `client_secret` needed) can make the host application execute webhook-handler logic attributed to an arbitrary victim shop. Any app logic keyed off `WebhookMetadata#shop` (e.g., invalidating a session/cache, marking a shop uninstalled, triggering data deletion, GDPR redaction flows) can be forged against a shop the attacker doesn't own — this is cross-tenant access achieved purely through this gem's own verification logic, satisfying the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to be a legitimate (if low-privilege) user of the target app — they must install the app on at least one shop of their own to receive a validly-signed webhook body, then replay it with a forged `shop-domain` header. No secrets, tokens, or credentials beyond normal app installation are needed, and no TLS interception or social engineering is required — only header manipulation on an HTTP POST to the app's own public webhook endpoint.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` into the HMAC-verified surface, or otherwise cryptographically tie them to the signed body, e.g.:
- Include the relevant headers in `to_signable_string` (mirroring Shopify's documented HMAC calculation only over the body is intentional for Shopify's own signing, so instead) cross-check `shop` against a shop that is independently known to the app (e.g., an existing installed/offline session) before trusting it, rather than trusting the raw header value uncritically.
- At minimum, document and enforce that webhook handlers must independently verify that the `shop` in `WebhookMetadata` corresponds to a shop with an existing app installation/session before performing any state-changing action, since the header itself carries no cryptographic guarantee.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook whose body is shop-independent, e.g. `app/uninstalled`, delivered with body `"{}"` and a valid `x-shopify-hmac-sha256` header computed as `HMAC-SHA256(api_secret_key, "{}")` [8](#0-7) .
2. Capture that raw HTTP POST (headers + body).
3. Replay the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [1](#0-0) [9](#0-8) .
5. The registered handler is invoked with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to act on the victim's tenant data based on attacker-forged input.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
