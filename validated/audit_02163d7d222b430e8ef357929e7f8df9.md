## Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate` succeeds, and then dispatches the handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` as trusted tenant/context identifiers. However, the HMAC is computed only over the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` decodes the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the identity fields used downstream — `shop`, `topic`, `webhook_id`, `api_version` — are pulled straight from `@headers` with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC and, if it passes, immediately trusts `request.shop` (and the other header-derived fields) to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The HMAC secret used (`Context.api_secret_key`) is the **app's** client secret, shared across every shop that has installed the app — it is not a per-shop secret. This means: given `hmac == HMAC(api_secret_key, body)`, that same `(body, hmac)` pair is valid for **any** shop using this app. A user (unprivileged, but with a legitimate/free install of the app on Shop A) can capture one of their own genuine webhook deliveries (which carries a body and a valid HMAC signed with the shared app secret), then resend the identical `(body, hmac)` pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because only the body is checked, and `Registry.process` will invoke the handler believing the payload legitimately originated `from` the victim shop.

This is exactly the identity-binding gap called out in the analog: a field that is acted upon (`shop`, used as the tenant key for all downstream processing/storage) is not covered by the HMAC that is supposed to prove authenticity of the request, i.e. `shop_verified == shop_acted_upon` is not enforced — only `body_verified == body_acted_upon` is. The gem's own documentation explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify," which is not true for the `shop` field.

### Impact Explanation
This breaks the shop/tenant boundary: an app built with this gem's webhook processing dispatches handler logic keyed by `data.shop` (see `docs/usage/webhooks.md`), so a spoofed webhook lets an attacker inject fabricated events attributed to a different, victim merchant's shop — e.g. triggering handlers that write to the victim's records, mark orders paid/fulfilled, or feed attacker-controlled data into per-shop business logic, all using a validly-signed HMAC. This is a cross-tenant data integrity/authentication issue reachable by any user who can install the app to any shop (even a free/trial shop) and control the webhook target, i.e. no privileged credentials are required beyond an ordinary app install.

### Likelihood Explanation
Any app that uses `ShopifyAPI::Webhooks::Registry.process`/`ShopifyAPI::Webhooks::Request` as documented is affected, since the vulnerability is in the gem's core verification logic, not a host-app misuse. The only requirement is that the attacker controls an installation of the same app on some shop (trivial for public apps) to obtain one valid `(body, hmac)` pair, then can freely swap the shop header when replaying the request to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material verified by `HmacValidator`, or otherwise cryptographically or out-of-band verify that the `shop` header corresponds to a shop actually entitled to send the given HMAC (e.g., look up a per-shop webhook secret if available, or reject/flag when the `shop` header does not match a shop with an active session/installation known to the app before trusting `request.shop`). At minimum, document loudly that `HmacValidator` only authenticates the raw body and that `shop`/`topic`/`webhook_id` are NOT authenticated, so consuming apps must independently verify the shop is a legitimate destination for that specific webhook (e.g. cross-check against a known/expected webhook ID per shop) before acting on it.

### Proof of Concept
1. Install the target app on attacker-controlled Shop A. Trigger any webhook (e.g. `orders/create`) and capture the raw POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
2. Replay a request to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (via `Registry.process`, see `lib/shopify_api/webhooks/registry.rb:190`) validates successfully because it only recomputes the HMAC over `B`.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload/body actually originated from Shop A, demonstrating the cross-tenant spoof. [4](#0-3)
