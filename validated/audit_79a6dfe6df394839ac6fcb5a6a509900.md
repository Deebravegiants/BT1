### Title
Balance-diff check in `Hinkal.transact` can be satisfied twice for one real transfer via a double-entry (address-aliased) ERC-20 token, allowing minting of unbacked on-chain UTXOs - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact` verifies solvency per-index over `circomData.erc20TokenAddresses` by comparing `balanceOf()` deltas at two arbitrary attacker-supplied addresses against the UTXO amounts matched to each address. Because the check never verifies that the addresses in `erc20TokenAddresses` correspond to independent underlying balances, an attacker who deploys a malicious "double-entry" token — two distinct contract addresses `A` and `B` that both read the *same* underlying balance via `balanceOf`, but where only one of them performs a real `transferFrom` — can get a single real token movement counted as backing for two separate on-chain UTXOs of the same amount.

### Finding Description
The invariant intended by the code is:

```
newBalances[i] - oldBalances[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]
```
checked independently for every index `i` of `erc20TokenAddresses` [1](#0-0) .

`oldBalances`/`newBalances` are produced by `getBalancesForArray`, which just calls `balanceOf(address(this))` (or reads ETH balance) once per array entry, with no deduplication or independence check across entries [2](#0-1) .

Exploit flow:
1. Attacker deploys a malicious ERC-20 "double-entry" token whose two public addresses `A` and `B` both expose `balanceOf` reading from the *same* internal ledger slot, but where `transferFrom` called through `B` is a no-op (returns `true` without moving real value), while `transferFrom` through `A` performs the real transfer.
2. Attacker calls `Hinkal.transact` with `externalActionData.externalActionId` pointing at `DepositOnChainUtxosExternalAction`, `erc20TokenAddresses = [A, B]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]` (required, since `runAction` asserts `deltaAmounts[i] == 0` [3](#0-2) ), and `externalActionMetadata` encoding `utxoAmounts = [[X], [X]]`.
3. `DepositOnChainUtxosExternalAction.runAction` iterates the token list and calls `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` once per index, using `A` and `B` respectively, while creating one UTXO of amount `X` for each [4](#0-3) . Only the `A`-indexed call moves real value (`X` total); the `B`-indexed call is a no-op in the attacker's token but still succeeds.
4. Back in `Hinkal.transact`, `newBalances` shows the *same* real increase of `X` reflected at both index 0 (`A`) and index 1 (`B`), because both addresses alias the same underlying balance. `balanceDif` is `X` at both indices, and `utxoAmount` matched by `erc20Address == erc20TokenAddresses[i]` is also `X` at both indices (one UTXO of amount `X` tagged `A`, one UTXO of amount `X` tagged `B`) [5](#0-4) .
5. Both per-index checks (`balanceDif == 0 + utxoAmount` and the slippage check) pass, yet the vault only actually received `X` real value while `2X` of shielded UTXO value was created and inserted into the tree via `insertCommitments` [6](#0-5) .

The root cause is that the balance-diff invariant is enforced per array index using `balanceOf` snapshots, with an implicit but unverified assumption that every `erc20TokenAddresses[i]` corresponds to an independent balance ledger. Nothing in `performHinkalChecks`, `verifyProof`, or the balance loop itself asserts that the addresses are distinct real tokens or de-duplicates aliased balances; the circuit likewise only constrains `inTotal + amountChanges === outTotal` over the shielded amounts it is given, not over on-chain token identity/uniqueness, so it cannot detect that two "addresses" alias one balance.

### Impact Explanation
The attacker mints shielded on-chain UTXOs worth `2X` while only depositing real value `X` into the vault — i.e., minting shielded value without backing, causing protocol insolvency. This directly matches the Critical category ("minting shielded value without backing... protocol insolvency"). The attack is repeatable for any amount `X` the attacker can afford to real-transfer once, and scales to arbitrarily many aliased addresses to multiply the discrepancy per call.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: they deploy their own malicious token contract exposing two addresses that alias one balance, then call `Hinkal.transact` once with `DepositOnChainUtxosExternalAction` as the external action, `erc20TokenAddresses` containing both aliases, and matching `externalActionMetadata`. No relay, admin, or victim interaction is required, and the attacker only needs enough of their own real token balance to cover the single genuine transfer leg. This is feasible with a single transaction and is fully repeatable.

### Recommendation
Enforce, inside `Hinkal.transact` (or `performHinkalChecks`), that `erc20TokenAddresses` contains no duplicate *underlying* balances that could be confused as independent — at minimum require distinct addresses and consider maintaining a governance-controlled whitelist of accepted token addresses rather than trusting arbitrary attacker-supplied ERC-20 contracts for on-chain UTXO creation. Additionally, aggregate/verify balance deltas using a single canonical identifier per real token rather than trusting `balanceOf` under attacker-chosen proxy addresses, or track deposited amounts using return values of `transferFrom` (post/pre balance deltas on the *source* side as well) rather than only vault-side aggregate balances keyed by caller-controlled addresses.

### Proof of Concept
Foundry test plan:
1. Deploy `DoubleEntryToken` with two entrypoint addresses `A` and `B` sharing one internal balance mapping; `transferFrom` via `A` moves real balance, `transferFrom` via `B` returns `true` without state change; `balanceOf(A/B, addr)` both read the shared mapping.
2. Fund attacker EOA with `X` tokens (real balance under the shared ledger).
3. Register `DepositOnChainUtxosExternalAction` in `Hinkal` (as done in existing deployment scripts/tests) and build valid `CircomData`/proof with `erc20TokenAddresses=[A,B]`, `onChainCreation=[true,true]`, `amountChanges=[0,0]`, `slippageValues=[0,0]`, `externalActionData.externalActionMetadata = abi.encode([[X],[X]])`.
4. Call `Hinkal.transact(...)`.
5. Assert: `IERC20(A).balanceOf(hinkal) - oldBalanceA == X` and `IERC20(B).balanceOf(hinkal) - oldBalanceB == X` (both pass individually) but the real vault token holding increased by only `X` (single real transfer), while `2 * X` worth of shielded UTXOs (tree leaves) were inserted — assert `sum(utxoSet[].amount) == 2X > realBalanceIncrease == X`, demonstrating `net tokens entering Hinkal (X) != sum(amountChanges) + sum(on-chain UTXO amounts minted) (2X)`.
