Confirmed: `placeOrder` accepts arbitrary ERC20 addresses in `order.inputs` with no whitelist check [1](#0-0) , and the redemption/refund path (`_withdraw`/`withdraw`) loops through *all* tokens of an order in a single transaction, transferring each to the beneficiary [2](#0-1) [3](#0-2) . This is the exact analog of the OpenQ bug: any single malicious/blocking token bundled into a multi-token container causes the entire payout loop to permanently revert, freezing the legitimate tokens escrowed alongside it.

### Title
Malicious ERC20 input token permanently freezes legitimate escrowed funds in IntentGateway multi-token orders - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`placeOrder` lets the order creator escrow an arbitrary list of ERC20 tokens with no whitelist [1](#0-0) . Settlement (`_withdraw` in same-chain fills, and `onAccept`/`withdraw` in cross-chain `RedeemEscrow`/`RefundEscrow` handling, and cancellation) iterates over *every* token in the order's input list in one loop and transfers each to the beneficiary [2](#0-1) . If any one of the bundled tokens is a malicious ERC20 that reverts on transfer to any address but the attacker's own, the entire loop — and hence the whole transaction (fill, redemption, refund, or cancellation) — reverts, permanently blocking withdrawal of the other, legitimate tokens escrowed in the same order.

### Finding Description
`IntentsBase._withdraw` decrements escrow and calls `IERC20(token).safeTransfer(beneficiary, amount)` inside a `for` loop over `body.tokens`, with no per-token isolation, no try/catch, and no way to skip a failing token [4](#0-3) . This function is the sole exit point for escrowed inputs, reached from:
- Same-chain fills (`_fillSameChain`, `_fillCrossChain`) that call `_withdraw(body, ..., isFullyFilled)` [5](#0-4) 
- Cross-chain settlement (`onAccept` → `_withdraw`) [6](#0-5) 
- Cancellation/refund (`_cancelSameChain` → `_withdraw`) [7](#0-6) 
- GET-response driven refund (`onGetResponse` → `_withdraw`) [8](#0-7) 

Because `placeOrder` permits any ERC20 address in `order.inputs` and duplicate-token protection only rejects exact duplicates (not malicious tokens) [9](#0-8) , the order creator (who is fully unprivileged, a single `placeOrder` transaction) can bundle a legitimate token (e.g. USDC) alongside a malicious token that reverts on any transfer except back to the attacker. Once a solver fills the order and the settlement/cancellation path tries to release *all* input tokens together, the malicious token's transfer reverts, and the *entire* transaction (including the transfer of the legitimate USDC) reverts. Since there is no per-token fallback or alternate redemption route, the legitimate escrow becomes permanently unclaimable — the same "unremovable poison token blocks the whole payout list" pattern as the OpenQ report.

The tron variant contains the identical pattern using low-level `.call()` with an explicit `if (!success) revert TransferFailed()` check, which is equally blocking [3](#0-2) .

### Impact Explanation
Any legitimate token escrowed in the same order as an attacker-supplied malicious token becomes permanently frozen: it can never be released to a solver on fill, refunded to the user on cancellation, or redeemed via the GET-response refund path, since all three routes go through the same all-or-nothing `_withdraw` loop. This is a concrete permanent freezing of funds for any counterparty (solver or user) who interacts with such an order, satisfying the High severity bar from the original report.

### Likelihood Explanation
`placeOrder` is fully permissionless and requires only a single transaction; no admin, allowlist, or special privilege is needed to include an arbitrary ERC20 token as one of several `order.inputs` entries [1](#0-0) . A malicious actor (either the order creator griefing solvers, or a griefer targeting a user's escrow by design of an adversarial pairing) can trivially deploy an ERC20 that allows transfers only from/to itself and include it as a secondary input leg. This requires no special market conditions and is reproducible on demand.

### Recommendation
Change `_withdraw` (and its tron equivalent `withdraw`) to isolate each token transfer so a single failing token cannot block the release of the others — e.g., wrap each `safeTransfer`/low-level call in a try/catch (or push-pull pattern where failed transfers accrue to a per-user claimable balance instead of reverting the whole loop). Alternatively, restrict `order.inputs` to a bounty/protocol-level ERC20 allowlist (as recommended in the original OpenQ report) so only vetted tokens can be escrowed, preventing malicious tokens from being paired with legitimate ones in the first place.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer`/`transferFrom` succeeds only when `msg.sender == deployer` or `to == deployer`, and reverts otherwise.
2. Attacker calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 1000e6}, {token: EvilToken, amount: 1} ]`, escrowing both tokens; `placeOrder` accepts this with no whitelist check [10](#0-9) .
3. A solver fills the order, providing the required outputs; `_fillSameChain`/`_fillCrossChain` builds a `WithdrawalRequest` containing both `USDC` and `EvilToken` and calls `_withdraw` [5](#0-4) .
4. Inside `_withdraw`'s loop, the `IERC20(EvilToken).safeTransfer(solver, amount)` call reverts because the recipient is not the deployer [11](#0-10) .
5. The entire `fillOrder`/`onAccept` transaction reverts, so the solver never receives the escrowed USDC either. The same order can never be cancelled successfully for the same reason, since `_cancelSameChain` also calls `_withdraw` over the same token list [7](#0-6) , permanently freezing the escrowed USDC.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
