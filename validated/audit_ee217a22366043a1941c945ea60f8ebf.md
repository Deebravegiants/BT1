### Title
`deposit` mints zero `zft` shares while fully crediting `assets`, permanently diluting depositor principal into existing/frozen shares - (`mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`deposit` computes `inkind` via `convert-to-shares-preview`, which floors `(amount * ts) / ta` and can legitimately return `u0` when `ts` (post-`initialize` this can be as low as `MINIMUM-LIQUIDITY = u1000`) is small relative to `ta`. Unlike `redeem`, which asserts `(> inkind u0)` (`ERR-OUTPUT-ZERO`), `deposit` has no equivalent check, so it will accept the underlying transfer, credit `assets`, and mint `0` shares to the depositor.

### Finding Description
The broken invariant is:
`shares_minted == convert-to-shares-preview(amount) > 0 whenever amount > 0`,
which the code fails to enforce.

Relevant code:
- `convert-to-shares-preview` at [1](#0-0)  computes `(mul-div-down amount ts ta)`, which floors to `u0` whenever `amount * ts < ta`.
- `deposit` at [2](#0-1)  only checks `(> amount u0)` and `(>= inkind min-out)` — if the caller supplies `min-out u0` (the common default), a deposit that rounds to `inkind = u0` still passes both checks, the full `amount` is added to `assets` (line 781), and `ft-mint? zft u0 recipient` mints nothing to the depositor.
- By contrast, `redeem` explicitly guards against this same rounding failure with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` at [3](#0-2) , confirming the omission in `deposit` is a real asymmetry/gap rather than an intentional design choice.
- `initialize` seeds exactly `MINIMUM-LIQUIDITY = u1000` shares to `NULL-ADDRESS` at [4](#0-3) , which is the theoretical supply floor once all other depositors exit.

Because `total-assets-preview` (`ta`) includes unrealized interest on outstanding debt (`assets + (debt - total-borrowed)`, see [5](#0-4) ), `ta` can grow disproportionately to `ts` through ordinary, permissionless lending activity: a user deposits, borrows against collateral through the lending module (which calls `system-borrow`, gated only by `check-caller-auth` for the *caller contract*, not by any special privilege for the underlying borrower), lets interest accrue (`accrue` is public and callable by anyone, see [6](#0-5) ), and then redeems shares down toward the `u1000` floor while the unpaid interest receivable keeps `ta` elevated. At that point any deposit (the attacker's own follow-up deposit, or an unsuspecting victim's deposit) below `ta / 1000` underlying units mints `u0` shares. The `amount` is still pulled from the depositor and added to `assets`, so the deposited value is absorbed pro-rata by whoever holds the remaining shares (including the attacker's own retained balance and/or the permanently frozen `NULL-ADDRESS` shares, in which case the value is destroyed outright).

Existing guards do not prevent this: `min-out` slippage protection is opt-in and defaults to `u0` in naive callers/UIs; `cap-supply` only bounds total deposits, not per-deposit share rounding; there is no pause or health check tied to the `ts`/`ta` ratio; and Clarity's integer division silently floors rather than reverting.

### Impact Explanation
Per triggering deposit, the entire deposited `amount` (up to just under `ta/1000` underlying units) is lost by the depositor and captured pro-rata by other shareholders (or burned into the unredeemable `NULL-ADDRESS` position). This is repeatable every time the vault's share supply is driven down near the `MINIMUM-LIQUIDITY` floor while `ta` remains large from accrued-but-unrepaid interest — a state reachable through normal permissionless deposit/borrow/redeem sequences. This is a direct, permanent loss of depositor principal, matching the Critical category (direct theft/permanent loss of funds at rest).

### Likelihood Explanation
No privileged access is required: depositing, borrowing against posted collateral, calling the public `accrue`, and redeeming are all ordinary user actions available to any Stacks principal. The attacker's capital cost is the amount needed to become a majority depositor/borrower long enough for interest to accrue meaningfully, plus the ability to time their own final small deposit (self-inflicted proof) or to front a victim's deposit into the vulnerable window. The scenario is more feasible the longer the vault has operated and the more concentrated supply becomes near the `u1000` floor.

### Recommendation
Add an explicit check in `deposit` mirroring `redeem`'s guard, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` immediately after computing `inkind`, so any deposit that would round to zero shares reverts instead of silently absorbing the depositor's funds.

### Proof of Concept
Clarinet simnet test outline:
1. Deploy vault, call `initialize` — assert `(get-total-supply)` returns `u1000` and `(get-assets)` returns `u1000`.
2. Have a funded principal `borrower` deposit a large amount `D` (e.g. `u10_000_000_000` microSTX), then borrow most of the available liquidity through the lending module (calls into `system-borrow`), and set a high interest-rate curve via `set-points-rate`/`set-points-util` (DAO-only setup, not part of attacker path, done at deployment).
3. Advance `stacks-block-time` and call `accrue` repeatedly (any principal can call) until `(get-total-assets)` (`ta`) grows to e.g. `u20_000_000_000` while outstanding debt remains unrepaid.
4. Have `borrower` `redeem` shares down to leave `(get-total-supply)` at exactly `u1000` (only `NULL-ADDRESS`'s minimum liquidity remains), while `ta` still reflects the unrepaid interest receivable.
5. Call `(convert-to-shares (some-amount below ta/1000))`, e.g. `u10_000_000` microSTX, and assert it returns `u0`.
6. Call `(deposit u10_000_000 u0 victim)` and assert: (a) the call succeeds (`ok inkind` with `inkind = u0`), (b) `(get-balance victim)` is `u0`, and (c) `(get-assets)` increased by `u10_000_000` with no corresponding share issuance — proving the victim's `u10_000_000` microSTX deposit was absorbed with zero shares minted.
