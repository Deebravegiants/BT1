### Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing after HMAC validation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw JSON body [1](#0-0) . The `shop` value used downstream to identify the tenant is read straight from an HTTP header and is never part of the signed material [2](#0-1) . `Registry.process` validates the HMAC (over the body only) and then forwards `request.shop` unchanged into `WebhookMetadata`, which the host app's `WebhookHandler` trusts as the authenticated tenant identity [3](#0-2) [4](#0-3) .

### Finding Description
The binding that should hold is: `shop` value cryptographically verified == `shop` value acted upon. Here, only the body bytes are bound to the HMAC via `compute_signature(verifiable_query.to_signable_string, secret)` [5](#0-4) ; the `shop-domain` header (and `topic`, `api-version`, `webhook-id` headers) are parsed from unauthenticated request metadata [6](#0-5) . Because the app's `client_secret`/`api_secret_key` is shared across all shops that install the app, any actor who legitimately installs the app on one shop (e.g., their own free/dev store) receives genuinely-signed webhooks (valid `(raw_body, hmac)` pairs) for that shop. Since the `shop` header is excluded from the signed bytes, that actor can replay the exact same body+HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` because it only re-derives the signature from `@raw_body` [7](#0-6) , and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` claims to be the victim tenant [8](#0-7) .

This is the same identity-binding class described in the report: a field that is acted on (`shop`, used by the host app to select which tenant's records to mutate/delete/redact) is not covered by the authentication primitive (`hmac` over body only).

### Impact Explanation
This crosses a tenant boundary: an app built on this gem cannot distinguish "webhook genuinely originated for shop B" from "attacker replayed a body they legitimately received for shop A, claiming it is from shop B." For the mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`), or any handler that keys its side effects off `data.shop` (e.g., `app/uninstalled` triggering data deletion, or order/product sync writing to the wrong tenant's store), this enables cross-tenant data corruption/deletion/disclosure without ever touching the victim's credentials — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Requires only that the attacker be able to install the target app once on a shop they control (trivial for any public app, and free for development stores) and that the app's webhook endpoint be internet-reachable (a functional requirement of webhooks). No access token, `client_secret`, or privileged account is needed — only observation of one legitimate webhook delivery for a shop they already control, which is the normal course of using the app.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically tie header claims to the request: e.g. include `shop`, `topic`, `api_version`, and `webhook_id` in `to_signable_string` (mirroring the design already used for `Auth::Oauth::AuthQuery#to_signable_string`, which does canonicalize all identity fields before signing [9](#0-8) ), or require host apps to independently correlate `WebhookMetadata#shop` against a shop they have an active, previously-established session/installation record for before acting on the payload, and document this requirement explicitly in `WebhookHandler`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and triggers a webhook they can subscribe to (e.g. `orders/create`), capturing the exact `raw_body` and the valid `shopify-hmac-sha256` value Shopify computed with the app's `client_secret`.
2. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with:
   - the same `raw_body`
   - the same `shopify-hmac-sha256` header
   - `shopify-shop-domain: victim.myshopify.com` (arbitrary victim tenant)
   - `shopify-topic` unchanged (or spoofed the same way if the app doesn't correlate topic to expected schema)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only from `request.to_signable_string` (`@raw_body`) — validation succeeds [1](#0-0) [7](#0-6) .
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", ...)` and dispatches it to the registered `WebhookHandler` [10](#0-9) , causing the host app to process attacker-supplied data as if it belonged to `victim.myshopify.com`.

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
