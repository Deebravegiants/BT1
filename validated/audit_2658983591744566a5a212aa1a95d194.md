### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the **raw request body**. The `shop` (and `topic`/`webhook_id`/`api_version`) values, which are taken from HTTP headers and passed straight through to the app's webhook handler as the tenant identifier, are never included in the signed material. This breaks the equality "bytes verified == bytes trusted for tenant identity," letting an attacker replay a validly-signed webhook body under an arbitrary `shop` header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely over that `to_signable_string` value and compares it to the `hmac` extracted from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header: [2](#0-1) 

`Registry.process` uses only this body-only HMAC check as its authentication gate, then forwards the **unauthenticated** `request.shop` header value (along with `topic`, `webhook_id`, `api_version`, also all unauthenticated headers) to the app's handler as the tenant/shop identity for the webhook: [3](#0-2) 

`request.shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed body or any other verified value: [4](#0-3) 

Because the signature only binds the JSON payload bytes and never binds `shop-domain`, `topic`, or `webhook-id`, any two values are interchangeable from the signature's point of view as long as the body bytes are unchanged. This is exactly the "field acted on but not covered by the HMAC" bug class: the equality that should hold — `signed_bytes == (body ‖ shop ‖ topic ‖ webhook_id)` — is instead only `signed_bytes == body`.

### Impact Explanation
An unprivileged internet user who operates their own legitimate shop installation of the app (or who otherwise obtains one authentic webhook body+HMAC pair, e.g. from their own store's webhook deliveries) can capture that valid `(body, hmac)` pair and replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim merchant's domain. `HmacValidator.validate` still succeeds because it never inspected the header, and `Registry.process` hands the handler `WebhookMetadata` claiming the payload originated from the victim's shop. Any app logic that trusts `data.shop` to select which tenant's records to create/update/delete (a documented, intended use of `WebhookMetadata#shop`) will act cross-tenant, i.e. write or mutate data attributed to a shop that never actually sent that webhook. This is a cross-tenant data-integrity/confusion vulnerability stemming directly from this gem's own webhook verification code.

### Likelihood Explanation
Medium-to-High: webhook endpoints are internet-reachable by design and require no additional secret to trigger (that's the point of webhooks). Obtaining one genuine `(body, hmac)` pair is trivial for anyone who installs the app on a shop they control (their own legitimate webhook deliveries), and replaying it with a different `shop-domain` header requires nothing more than a normal HTTP client — no access token, no `api_secret_key`, and no privileged account is needed to *mount* the attack (only to obtain the one legitimate sample body, which any installer already has).

### Recommendation
Bind the tenant-identifying headers into the signed material verified by `HmacValidator`, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or independently verify them against a value derived from a signed/trusted source), so a valid HMAC for one shop's payload cannot be replayed under a different shop's identity.

### Proof of Concept
1. Install the app on Attacker's own shop `attacker.myshopify.com`; capture one legitimate webhook delivery: body `B` and header `x-shopify-hmac-sha256: H` (valid signature over `B`).
2. Send `POST /webhooks` (the app's registered webhook path) with the same body `B` and header `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim.myshopify.com`, `x-shopify-topic: orders/create` (or whatever true topic `B` corresponds to), and a fresh `x-shopify-webhook-id`.
3. `HmacValidator.validate` returns `true` because `compute_signature(B, secret) == H` regardless of headers, per [5](#0-4) .
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)`, per [3](#0-2) , causing the app to process attacker-controlled data as if it were sent by `victim.myshopify.com`.
