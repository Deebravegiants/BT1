### Title
Cache-key collision in `DirectBridge` storage-deposit check causes wrong fee estimation for unrelated (token, destination) pairs - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU-cache key by naive string concatenation of `contractId` and `accountId` with no delimiter. Because NEAR account IDs and contract IDs are both variable-length strings composed of the same character set, two different `(contractId, accountId)` pairs can produce an identical concatenated key. A collision causes `estimateWithdrawalFee` to return the storage-deposit fee/quote that was computed for a completely different token/destination pair.

### Finding Description
In `getCachedStorageDepositValue`:
```
packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts:277
const key = `${contractId}${accountId}`;
```
`contractId` comes from the asset being withdrawn (`utils.parseDefuseAssetId(args.withdrawalParams.assetId)`), and `accountId` is `args.withdrawalParams.destinationAddress` — a value fully controlled by the SDK caller. Since the key is a plain concatenation, `contractId = "ab"`, `accountId = "cd"` and `contractId = "abc"`, `accountId = "d"` collide on the same cache key `"abcd"`.

`estimateWithdrawalFee` (`direct-bridge.ts:194-268`) uses this cache to decide whether a storage-deposit fee is owed:
```
packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts:225-241
const [minStorageBalance, userStorageBalance] =
    await this.getCachedStorageDepositValue(tokenAccountId, args.withdrawalParams.destinationAddress);
if (minStorageBalance <= userStorageBalance) {
    return { amount: 0n, ... };
}
```
If a cache hit occurs for the wrong pair (because of a collision), the returned `[minStorageBalance, userStorageBalance]` tuple describes storage state for a different token/account combination entirely. The equality that should hold — "the storage-deposit balance checked belongs to the exact `(token, destinationAddress)` pair currently being withdrawn to" — is broken.

Only successful ("has enough storage") results are cached (`if (result[1] >= result[0]) this.storageDepositCache.set(key, result)`), so a collision can cause `estimateWithdrawalFee` to wrongly report `feeAmount = 0n` for a destination/token pair that in fact has no storage registered on that token contract, since the LRU entry from an unrelated but colliding key is served instead of performing a fresh RPC check.

### Impact Explanation
This falls under "a fee overcharge or ... [fee] error" and "a withdrawal stuck until manual intervention": if `estimateWithdrawalFee` reports a zero storage-deposit fee for a destination account that is not actually registered for storage on the NEP-141 contract being withdrawn (because the cache served another pair's cached "sufficient storage" result), the resulting withdrawal transaction is submitted without funding the recipient's storage deposit. On NEAR, `ft_transfer` to an unregistered account fails/reverts, so the withdrawal can get stuck and require manual intervention/replay by the integrator, matching the "High" impact tier ("a withdrawal stuck until manual intervention").

### Likelihood Explanation
The collision requires an attacker (or even an unlucky legitimate caller) to choose an `assetId`/`destinationAddress` combination whose concatenation matches an already-cached key from a prior legitimate call served by the same long-lived `DirectBridge` instance (the cache is an instance-level `LRUCache` with `max: 100` and `ttl: 3600000`, i.e., up to 1 hour). Since `destinationAddress` is fully caller-controlled and NEAR account name character sets overlap with contract IDs, constructing a colliding pair is straightforward once an integrator knows (or guesses) a previously-served `(contractId, accountId)` combination. The cache is per-process/instance, so exploitability depends on the SDK being run as a shared long-lived service handling multiple callers/tokens — a realistic deployment pattern for backend integrators using `intents-sdk`.

### Recommendation
Use a delimiter that cannot appear ambiguously in either component (e.g. join with a NUL byte `\x00` or a compound key `` `${contractId}:${accountId}` `` combined with length-prefixing, or simply use a `Map<string, Map<string, [...]>>` / tuple key) when building the cache key in `getCachedStorageDepositValue`. Apply the same review to any other place using ad-hoc string concatenation for cache/map keys in this file.

### Proof of Concept
1. Caller A withdraws token `contractId = "usdc.nearalice"`... actually to construct a concrete collision:
   - Call 1: `estimateWithdrawalFee({ assetId: "nep141:usdc.near", destinationAddress: "alice.near" })` → `getCachedStorageDepositValue("usdc.near", "alice.near")` → key = `"usdc.nearalice.near"`. Suppose `alice.near` already has sufficient storage on `usdc.near`, so `[min, bal]` with `bal >= min` is cached under this key.
   - Call 2 (attacker/different caller): `estimateWithdrawalFee({ assetId: "nep141:usdc.nearalice", destinationAddress: ".near" })` → `getCachedStorageDepositValue("usdc.nearalice", ".near")` → key = `"usdc.nearalice.near"` — identical string.
   - Because the key matches, the second call returns the cached tuple from call 1 without any RPC check, reporting `feeAmount = 0n` even though `.near`'s storage state on `usdc.nearalice` was never checked.
2. The resulting `estimateWithdrawalFee` result feeds into the withdrawal-intent construction with `storageDepositFee: 0n`, so no storage deposit is attached to the withdrawal, and the on-chain `ft_transfer`/withdraw can fail if the destination is in fact not registered on that contract, leaving the withdrawal stuck. 	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
