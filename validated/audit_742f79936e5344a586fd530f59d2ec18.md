### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only. The `shop`, `topic`, and `webhook_id` values — which are taken verbatim from unauthenticated HTTP headers — are never included in the signed string, yet they are the values the registry hands to the application's webhook handler as the authoritative tenant identity for the event.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the body that was actually HMAC-signed: [2](#0-1) 

`Registry.process` validates only the body HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` as the tenant/event identity passed into the handler: [3](#0-2) 

This is exactly the "field acted on but not covered by the HMAC" pattern from the report: the identity binding that should hold is `hmac_signed_scope == data_acted_on`, i.e. `HMAC-verified(body, shop-domain, topic)` == `(shop, topic passed to handler.handle)`. Here only the body half of that equality is authenticated; `shop`/`topic`/`webhook_id` can differ from what Shopify actually intended for that specific body/secret pairing, exactly as `targetZRC20` in the report could diverge from the actual swap output without validation.

Because `api_secret_key` is shared across every shop that installs the same public/partner app, any user who has installed the app on their own store can trigger a webhook for their own store, capture the resulting `(raw_body, hmac)` pair (which will validate successfully since it was genuinely signed by Shopify with the app's shared secret), and then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook_id`) header for an arbitrary victim shop. `HmacValidator.validate`/`process` will accept it because the signable string never included those headers: [4](#0-3) 

The application then executes tenant-scoped logic (e.g. GDPR redact handlers, `app/uninstalled` cleanup, order/customer processing) believing the event legitimately originates from the victim shop.

### Impact Explanation
This breaks the tenant boundary the library is supposed to provide to consuming applications: an attacker who is merely a legitimate (unprivileged relative to other tenants) installer of the shared app can forge webhook events that appear to originate from an arbitrary other shop using the same app installation's secret, since `shop`/`topic` identity is never bound to the HMAC. This is a cross-tenant access primitive — the exact "Critical: cross-tenant access" category called out in scope.

### Likelihood Explanation
Any user capable of installing (or already installed on) the same publicly distributed app can generate a genuine `(body, hmac)` pair for their own store by triggering any webhook topic they control (e.g. product update), then simply changing the header value that the gem — not the merchant's code — treats as the trusted tenant identifier. No access to `api_secret_key`, tokens, or TLS interception is required beyond what a normal installer already legitimately possesses.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cross-check them against the caller's own expected/registered shop and against a per-shop record) inside `to_signable_string`, or explicitly validate `request.shop` against the shop associated with the session/install before dispatching to `handler.handle`, so the HMAC covers the full identity tuple that the handler will act upon.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic they control (e.g. updates a product to fire `products/update`).
2. Attacker's endpoint captures the resulting POST: raw body `B` and header `x-shopify-hmac-sha256: H`, both validly computed by Shopify using the shared `api_secret_key`.
3. Attacker resends the identical body `B` and header `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
4. `HmacValidator.validate` succeeds because `to_signable_string` only checked `B`/`H`; `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B))` and invokes the app's handler as if the event genuinely came from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
