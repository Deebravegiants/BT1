### Title
Starknet address validation regex accepts hex values above the felt252 field prime, permanently stranding withdrawals - (File: packages/intents-sdk/src/lib/validateAddress.ts)

### Summary
`validateStarknetAddress` only checks the address is `0x` followed by 1-64 hex characters, with no comparison against the Starknet felt252 field modulus (2^251+17·2^192+1). A destination address whose numeric value exceeds this modulus (e.g. `0x` + 64 `f`s) passes `validateAddress`/`validateWithdrawal` and is signed into the withdrawal intent unmodified.

### Finding Description
The broken equality is: *"the value accepted by `validateAddress(address, Chains.Starknet)` is a valid Starknet felt252 field element."* The regex `/^0x[a-fA-F0-9]{1,64}$/` in `validateStarknetAddress` [1](#0-0)  only bounds the string to at most 64 hex chars (256 bits), but felt252 values must be strictly less than `2^251 + 17*2^192 + 1`, which is well below the 256-bit maximum representable by 64 hex chars. `0x` followed by 64 `f` characters (`2^256 - 1`) satisfies the regex but is far above the modulus.

`OmniBridge.validateWithdrawal` calls this validator via `validateAddress(args.destinationAddress, assetInfo.blockchain)` [2](#0-1)  and only rejects on `false`; no subsequent range/modulus check exists anywhere else in `validateWithdrawal`. The address then flows into `deriveOmniWithdrawIntentParams`, where `omniAddress(params.omniChainKind, destinationAddress)` builds the `recipient` field directly from the unvalidated string [3](#0-2) , which is then used to compute the storage account id and packed into the withdrawal intent that gets signed. I could not locate the implementation of `omniAddress` from `@omni-bridge/core` in this repo's index (it's an external dependency), so I cannot confirm whether that library itself performs a modulus check before constructing the `OmniAddress` — this is a gap in verification.

Existing guards that were checked and do not catch this:
- `compareAddresses`'s `normalizeHexAddress`/`compareHexAddress` for Starknet [4](#0-3)  only strips the `0x` prefix and leading zeros for string-equality comparison against the token address; it performs no numeric range check either.
- `validateWithdrawal`'s other asserts (fee > 0, asset supported, token found, decimals present) are unrelated to address range validation [5](#0-4) .

### Impact Explanation
If the out-of-range value is accepted and actually gets encoded into the signed intent's recipient field without truncation/modulus reduction by `@omni-bridge/core`, the resulting on-chain call on Starknet would either revert (funds stuck, requiring the relayer/manual intervention to reprocess with a corrected address) or, in the worst case, misinterpret/wrap the felt in a way that sends the withdrawal to an unintended recipient. Since NEAR intents signatures are for a specific signed payload, the amount is already debited/committed once the intent is created and cannot be "un-signed" without a new withdrawal flow. This matches the **High** category ("a withdrawal stuck until manual intervention") if the on-chain contract simply reverts, or **Critical** ("funds delivered to a wrong address... with no recovery") if the value is silently reduced mod p or truncated to an unintended felt by the downstream library.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: any user or integrator-forwarded `destinationAddress` targeting a Starknet asset via `routeConfig`/`assetInfo.blockchain === Chains.Starknet` can supply a 64-hex-character string above the modulus at zero cost, and the flow is deterministic and repeatable on every call. However, whether this actually reaches an unrecoverable/misrouted state on-chain depends entirely on the behavior of `omniAddress` from `@omni-bridge/core`, which is external to this repo and not verifiable from the indexed code — it is plausible that library normalizes/rejects out-of-range felts before final encoding, which would make this merely a client-side lax-validation issue rather than an exploitable on-chain divergence.

### Recommendation
Strengthen `validateStarknetAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` to parse the hex value as a `bigint` and reject any value `>= STARKNET_FELT_PRIME` (`2n**251n + 17n*2n**192n + 1n`), in addition to the existing format regex.

### Proof of Concept

// packages/intents-sdk/src/lib/validateAddress.spec.ts
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";

describe("validateStarknetAddress felt252 bound", () => {
  const STARKNET_FELT_PRIME = 2n ** 251n + 17n * 2n ** 192n + 1n;

  it("rejects hex values >= felt252 prime", () => {
    const outOfRange = "0x" + "f".repeat(64); // 2^256 - 1, far above prime
    expect(BigInt(outOfRange) >= STARKNET_FELT_PRIME).toBe(true);

    // Current behavior (documents the bug): validator wrongly accepts it
    expect(validateAddress(outOfRange, Chains.Starknet)).toBe(true);

  });
});

// Aptos/Movement/Sui/Starknet addresses are hex field elements: case is not
// significant, and both zero-padded (0x000...01) and short (0x1) forms refer
// to the same address.
function compareHexAddress(a: string, b: string): boolean {
	const normalizedA = normalizeHexAddress(a);
	const normalizedB = normalizeHexAddress(b);
	if (normalizedA === null || normalizedB === null) return false;
	return normalizedA === normalizedB;
}

function normalizeHexAddress(address: string): string | null {
	const withoutPrefix = address.toLowerCase().startsWith("0x")
		? address.slice(2)
		: address;
	if (withoutPrefix.length === 0 || !/^[0-9a-fA-F]+$/.test(withoutPrefix)) {
		return null;
	}
	const withoutLeadingZeros = withoutPrefix.replace(/^0+/, "");
	return withoutLeadingZeros.toLowerCase() || "0";
}
