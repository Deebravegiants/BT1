Audit Report

## Title
JWT single-use replay protection has a check-then-act race allowing token reuse in `WorkflowMetadataHandler.Authorize` - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` verifies a JWT, checks whether its `jti` has already been used via `jwtCache.isReplay`, performs unrelated authorized-key validation, and only then marks the `jti` as used via `jwtCache.recordUsage`. Because the check and the record-usage write are two independently locked operations rather than one atomic check-and-set, concurrent requests carrying the same JWT can both pass the replay check before either records usage, defeating the single-use guarantee.

## Finding Description
In `Authorize` [1](#0-0) , the sequence is: verify JWT signature/claims, call `h.jwtCache.isReplay(claims.ID)` under a read lock, perform `h.authorizedKeys[workflowID]` lookup and signer validation, and only afterward call `h.jwtCache.recordUsage(claims.ID)` under a write lock. `isReplay` and `recordUsage` are implemented as two separately-locked methods on `jwtReplayCache` [2](#0-1) , with no combined "check-and-set" primitive. This leaves a window in which two goroutines processing the same JWT concurrently can both observe `isReplay == false` before either calls `recordUsage`, so both requests are authorized instead of just one. The existing replay test only exercises strictly sequential calls and does not catch this race [3](#0-2) . A correct atomic pattern already exists elsewhere in the codebase in `RequestReplayGuard.CheckAndRecord`, which performs the existence check and the write under a single `mu.Lock()` critical section [4](#0-3) , confirming that `jwtReplayCache` lacks the equivalent atomicity.

## Impact Explanation
This affects gateway-routed, node-facing "web-api trigger" workflow-metadata request authorization, reachable by an unprivileged internet-facing client that submits a signed JWT. The missing atomicity allows a single client-issued, intended-single-use JWT to authorize two (or more) independently-processed gateway requests instead of one, undermining the single-use/idempotency guarantee the design relies on for bounding per-token request volume. This falls into the "gateway request impersonation" / unauthorized action impact category.

## Likelihood Explanation
Exploitation only requires sending the same valid JWT to the gateway concurrently or in rapid succession — no privileged access, node compromise, or network trickery is required. The race window (between `isReplay` and `recordUsage`, with JWT verification and map lookups executed in between) is real, though narrow, and is repeatable by any client capable of issuing concurrent requests.

## Recommendation
Replace `isReplay` + `recordUsage` with a single atomic `checkAndRecord(jti) bool` method on `jwtReplayCache` that acquires `mu.Lock()` once, checks for existence, and if absent immediately writes `cache[jti] = time.Now()` within the same critical section — mirroring the existing `RequestReplayGuard.CheckAndRecord` pattern in `core/capabilities/vault/request_replay_guard.go`. Call this atomic method immediately upon JWT verification in `Authorize`, before performing the authorized-key lookup, so no request that fails the check can proceed further.

## Proof of Concept
Go unit test plan: create a `WorkflowMetadataHandler` with a registered authorized signer for `workflowID`, generate one signed JWT (`tokenA`), then launch two goroutines that both call `handler.Authorize(workflowID, tokenA, req)` concurrently (e.g., synchronized with a start barrier to maximize the chance both pass `isReplay` before either calls `recordUsage`). Assert that both goroutines returning `nil` error and a non-nil key (both succeeding) demonstrates the race; run with `-race` and repeated iterations/loop to increase reliability of hitting the window, since the race is inherently timing-dependent and may require multiple attempts to trigger deterministically.

func (cache *jwtReplayCache) isReplay(jti string) bool {

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
