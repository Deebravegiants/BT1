### Title
Attacker-controlled QR `parameters` octal value can panic-crash the Orb signup session via `assert_eq!` in `SweepConfiguration::parse_configuration_value` - ([File: src/plans/biometric_capture/focus_sweep.rs])

### Summary
The `parse_configuration_value` function assumes `configuration_value: u8` will always fit into exactly 3 binary digits, but an unprivileged attacker can present a self-crafted QR code whose `parameters` field parses (via `u8::from_str_radix(parameter, 8)`) to a value greater than 7, causing the internal `assert_eq!` to fail and panic. This is reachable from `From<biometric_capture::Plan> for Plan` and `SweepConfiguration::reset`, both invoked during a live biometric-capture/signup session.

### Finding Description
`SignupMode::parse` in `src/plans/qr_scan/user.rs` (lines 167-186) accepts a QR-encoded `mode` field and, when it equals `2`, resolves to `SignupMode::FocusSweepExtension`. The accompanying `parameters` capture group (regex `[a-z0-9:]+`, `src/plans/qr_scan/user.rs` lines 50-56) is stored unchecked as a `String` in `SignupExtensionConfig::parameters`.

In `focus_sweep.rs`, `impl From<biometric_capture::Plan> for Plan` (lines 156-179) converts this raw string into a `u8` via:
```
.and_then(|parameter| u8::from_str_radix(parameter, 8).ok())
.unwrap_or(1)
```
`from_str_radix(_, 8)` only validates that each digit is `0-7`; it does not restrict the resulting numeric value to ≤7. A `parameters` string such as `"10"` parses cleanly to `8u8`, `"77"` parses to `63u8`, etc.

This value is passed to `SweepConfiguration::new`, which calls `parse_configuration_value` (lines 307-321):
```rust
let binary_repr = format!("{configuration_value:0>3b}");
assert_eq!(
    binary_repr.chars().count(),
    3,
    "Focus Sweep configuration value needs to be octal (<=3 bit)!"
);
```
For any `configuration_value > 7`, the zero-padded binary representation is longer than 3 characters (e.g. `8` → `"1000"`), so the assertion fails and the function panics. The same panic path is re-triggered every time `SweepConfiguration::reset` is called (e.g., between eyes during the same signup), via `Plan::reset_extension` (line 281-283) invoked from `extension_finished` (line 270-278), which runs inside the biometric capture broker loop (`Plan::run`, lines 188-203).

No validation exists upstream: the regex only restricts characters to `[a-z0-9:]`, and `from_str_radix` only restricts digit values 0-7 per character, not the resulting integer magnitude. There is no clamp, `Result`-based error handling, or backend-side check before the value reaches the panicking assertion.

### Impact Explanation
A crafted QR code causes a Rust panic inside the async task running the Orb broker loop during an active biometric capture/signup session. Depending on the panic strategy configured for the binary, this either aborts the whole `orb-core` process (denial of service for all subsequent signups on that physical Orb until manual/automatic restart) or, at minimum, unwinds and terminates the in-progress signup task, wedging that signup's state. This falls under the "signup-state wedge" / availability-impacting category of accepted findings — it is a real, reachable panic caused entirely by attacker-controlled QR content, not a hypothetical or purely stylistic issue.

### Likelihood Explanation
- Precondition: the Orb binary must be compiled with the `internal-data-acquisition` Cargo feature, since `QR_CODE_SIGNUP_EXTENSION`/`from_signup_extension` in `src/plans/qr_scan/user.rs` are gated behind `#[cfg(feature = "internal-data-acquisition")]`. If this feature is disabled in production/field firmware, this specific QR-driven path is unreachable to a real-world attacker presenting a code to a public-facing device.
- If the feature is enabled (e.g., in engineering/internal fleets or if shipped in some builds), the attack is trivial and fully repeatable: any user can present their own crafted QR (`userid:<id>:<policy>::2:10::`) to reach `SignupMode::FocusSweepExtension` with `parameters = "10"`.
- No operator privileges, keys, or social engineering are required — only presenting a self-made QR code to the camera during signup.

### Recommendation
Replace the `assert_eq!` panic with proper input validation that rejects (via `Result`/`Option`, not panic) any `configuration_value` outside `0..=7` before use, e.g., return `None`/fallback to default wavelength configuration and log a warning instead of asserting. Additionally, validate/clamp the parsed octal value immediately in `SignupExtensionConfig`/`SignupMode::parse`, before it reaches `focus_sweep.rs`, so malformed QR-derived parameters can never propagate into panic-prone code.

### Proof of Concept
Unit test to add to `src/plans/biometric_capture/focus_sweep.rs` (or a new integration test gated the same way as existing tests) reproducing the panic:
```rust
#[test]
#[should_panic(expected = "Focus Sweep configuration value needs to be octal (<=3 bit)!")]
fn parse_configuration_value_panics_on_out_of_range_octal_string() {
    // Simulates parameters = "10" from a crafted QR code, octal-parsed to 8u8.
    let value = u8::from_str_radix("10", 8).unwrap(); // = 8
    let _ = SweepConfiguration::new(value); // triggers parse_configuration_value -> panics
}
```
Expected assertion: the test panics with the message `"Focus Sweep configuration value needs to be octal (<=3 bit)!"`, confirming that attacker-supplied QR `parameters` such as `"10"`, `"77"`, etc. crash the focus-sweep configuration path when reached through `From<biometric_capture::Plan> for Plan` or `SweepConfiguration::reset` during a live signup session.
