### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted downstream without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers and passed downstream (via `Registry.process`) as trusted, verified data. Any request whose body produces a valid HMAC will have its header-derived `shop` value trusted for tenant attribution, even though that value was never part of what the HMAC actually authenticates.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing the HMAC over `to_signable_string` and comparing it to the `hmac` value [1](#0-0) . For webhooks, `to_signable_string` is defined as just `@raw_body` [2](#0-1) , meaning the cryptographic check binds only to the body bytes. The `shop`, `topic`, `api_version`, and `webhook_id` accessors are derived purely from HTTP headers, independent of that signature [3](#0-2) .

`Registry.process` validates the HMAC once (`Utils::HmacValidator.validate(request)`), then immediately uses `request.shop` and `request.topic` as authenticated identity/routing fields, constructing a `WebhookMetadata` struct that is handed to the app's handler as trusted data: [4](#0-3) . `WebhookMetadata#shop` is a plain `String` field with no further validation [5](#0-4) .

The identity binding that should hold is: `hmac-verified bytes == bytes that determine tenant (shop)`. Here it is: `hmac-verified bytes (raw_body) != identity field used for tenant attribution (shop-domain header)`. Since the header is not part of the signed content, any request whose body's HMAC is valid — regardless of which shop it originated from — can carry an arbitrary `shop-domain` header and will pass `Registry.process`'s single HMAC check while attributing the payload to a different tenant.

### Impact Explanation
An unprivileged internet user who can install the app on their own store (a normal, permission-free action any merchant can take) receives real webhooks from Shopify that are validly HMAC-signed with the app's `client_secret` over the body. Because the signature never covers the `x-shopify-shop-domain` header, that user can capture one such request and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Utils::HmacValidator.validate` still succeeds (the body is unchanged), and `Registry.process` forwards `shop: <victim-shop>` to the app's `WebhookHandler#handle` as if Shopify had certified that pairing of body and shop. Depending on the topic used (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, `orders/create`), this can cause the app to perform tenant-scoped operations (deleting/redacting data, updating tenant state, writing records) against the wrong tenant — a cross-tenant integrity breach rooted entirely in this gem's webhook-verification API, not in host-application misuse.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that key any state change off `WebhookMetadata#shop`: exploitation requires only (1) installing the app on an attacker-controlled shop to obtain a body/HMAC pair, and (2) replaying it with a rewritten header — no access to `api_secret_key`, access tokens, or privileged accounts is needed, satisfying the unprivileged-attacker constraint.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) so the `shop` (and ideally `topic`/`webhook_id`) used for downstream routing/tenant attribution is cryptographically bound to the signed request — e.g., by validating the reported shop against the session/shop the webhook subscription was registered for, or by requiring transport-level assurance (mutual TLS/allow-listed source) in addition to body HMAC, rather than trusting the `shop-domain` header purely because the body's HMAC matched.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a request with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` to the app's webhook endpoint.
2. Capture this request.
3. Replay it to the same endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (body `B` and HMAC header untouched).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: replayed_headers)` yields `hmac` unchanged; `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only recomputes over `B`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ..., body: parsed_body_of_B)` — the app now believes attacker-controlled body `B` genuinely originated from `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
