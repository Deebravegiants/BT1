### Title
Webhook shop/topic identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` only authenticates the body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which are trusted verbatim and handed to the app's webhook handler as the identity of the acting tenant — are never bound to the HMAC. This is the same class of bug as the reported issue: a field that is *acted on* (here, the shop identity used to route/attribute a webhook) is excluded from the cryptographic authentication that is supposed to bind it, exactly as `MetaTxLib` used unauthenticated/incorrectly-encoded array fields while claiming EIP-712 integrity over the whole struct.

### Finding Description
`ShopifyAPI::Webhooks::Request` parses headers and body separately: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` computes/compares the HMAC over that string alone: [3](#0-2) 

`Webhooks::Registry.process` validates only that HMAC, then immediately forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — none of which are covered by the signature — to the app's handler as trusted identity metadata: [4](#0-3) 

So the binding the gem implicitly claims is: `hmac_valid(request) == (shop, topic, body) authentic`. In reality it only proves `hmac_valid(request) == body authentic`; `shop` and `topic` are unauthenticated header values. An unprivileged user who controls their own Shopify store receives real, validly-signed webhooks from Shopify for their own shop's events. Because the signature never covers the `shop-domain` header, that same `(body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain — the HMAC check in `HmacValidator.validate` still passes, and `Registry.process` will invoke the handler with `shop: <victim-shop>` while the body content is fully attacker-controlled data from the attacker's own store.

### Impact Explanation
This breaks the tenant boundary the webhook system is supposed to enforce: the app is told "this authentic Shopify-signed payload belongs to shop X" when in fact only the payload bytes were authenticated, not the shop attribution. Any app logic that uses `WebhookMetadata#shop` (as constructed in `Registry.process`) to look up per-shop sessions, update per-shop data, or make decisions keyed by shop domain can be tricked into applying attacker-supplied data under a different tenant's identity — a cross-tenant integrity violation reachable by any unprivileged internet user who can register their own store and observe webhook HMACs/replay requests to the target's public webhook endpoint. This matches the "cross-tenant access" Critical impact category, since the shop-to-payload binding, which is the entire point of using HMAC-authenticated webhooks, is not actually enforced by the gem.

### Likelihood Explanation
Likelihood is moderate to high: no privileged credentials, access tokens, or `client_secret` are required. An attacker only needs (a) their own Shopify development/free store to generate a real signed webhook body+HMAC pair, and (b) the ability to POST to the target app's public webhook endpoint with a modified `shop-domain` header — both are unprivileged-internet-user capabilities. It is the exact structural analog to the reported bug: a value is trusted as part of an authenticated struct while being outside what is actually hashed/signed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated material, e.g. by including the `X-Shopify-Shop-Domain` header value in the string that is HMAC-verified (mirroring how `Oauth::AuthQuery#to_signable_string` includes `shop` in its signable string, as seen at `lib/shopify_api/auth/oauth/auth_query.rb` lines 33-43), or by requiring callers to independently verify the shop domain came from a known/registered shop before trusting `WebhookMetadata#shop`. At minimum, document clearly that `shop`/`topic` are not authenticated by `HmacValidator.validate` so host applications don't assume otherwise.

### Proof of Concept
1. Attacker registers store `attacker.myshopify.com` and installs the target app, so the app registers a webhook subscription for it.
2. Shopify sends a legitimately HMAC-signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: attacker-controlled JSON (attacker can craft this content since it's their own store's order).
3. Attacker captures this raw request and replays it to the same public endpoint, changing only the `x-shopify-shop-domain` header to `victim.myshopify.com`, keeping body and HMAC identical.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `request.to_signable_string` (i.e., the unchanged raw body) against the unchanged HMAC — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31, `lib/shopify_api/webhooks/request.rb` lines 35-38).
5. `Registry.process` invokes the app handler with `shop: "victim.myshopify.com"` and the attacker-controlled body (`lib/shopify_api/webhooks/registry.rb` lines 188-199), causing the app to process attacker data as if it originated from the victim's shop.
