### Title
Same-batch write-write lock conflicts are not detected in `AccountLocks::try_lock_transaction_batch`, allowing two transactions to hold conflicting write locks on the same account simultaneously - ([File: accounts-db/src/account_locks.rs])

### Summary
`try_lock_transaction_batch` validates every transaction's account keys against the *current* lock state in a first pass, but never incrementally applies the locks during that pass; locks are only applied in a second pass to all transactions that passed. As a result, two transactions in the same batch that both declare the same account as writable will both pass `can_lock_accounts` (since neither has locked the account yet at check-time) and both then get write-locked in the second pass.

### Finding Description
`try_lock_transaction_batch` is implemented as two sequential passes over `validated_batch_keys`: [1](#0-0) 

In the first pass, `self.can_lock_accounts(keys.clone())` is called for each transaction in the batch, but the result is *not* applied to `self` — no call to `lock_write`/`lock_readonly` happens here: [2](#0-1) 

`can_lock_accounts` only consults `write_locks`/`readonly_locks` as they currently stand (i.e., locks held by *other, already-processed* batches), via `can_write_lock`/`can_read_lock`: [3](#0-2) [4](#0-3) 

Because none of the in-batch checks mutate `self`, if transaction A and transaction B in the *same* batch both list account `X` as writable, and `X` is not already locked by some prior batch, then:
1. Checking A's keys: `can_write_lock(X)` → true (no locks yet) → A stays `Ok`.
2. Checking B's keys: `can_write_lock(X)` → still true (A's lock was never applied) → B stays `Ok`.

The second pass then unconditionally calls `self.lock_accounts(keys)` for every `Ok` entry: [5](#0-4) [6](#0-5) 

which calls `lock_write`, incrementing the write-lock counter for `X` for both A and B: [7](#0-6) 

Both A and B end up successfully "locked" (`Ok(())` returned for both), violating the intended invariant that only one writer may hold a write lock on an account at a time. This breaks the exclusivity guarantee that downstream schedulers/executors rely on to safely run non-conflicting transactions concurrently — two transactions writing the same account can now be scheduled for concurrent execution, resulting in a data race / undefined mutation ordering on account state.

An unprivileged attacker can trigger this simply by constructing two transactions in one batch that both declare the same writable account (e.g., their own fee payer, or any account, as long as duplicate keys within a single transaction are separately rejected by `validate_account_locks`/`has_duplicates` — this is a check for duplicates *within one transaction*, not across transactions in a batch) — no privileged access, staking, or special config is required, only normal TPU batch submission with two overlapping write-writable transactions.

### Impact Explanation
This breaks the fundamental "only declared-writable, unlocked accounts may be mutated concurrently" invariant, permitting concurrent, unsynchronized mutation of the same account by two transactions in the same processing batch. This can produce cross-node divergence (different execution/interleaving order between nodes with different timing) or corrupted/lost account state, both categories covered under Agave's consensus/state-corruption bounty tier.

### Likelihood Explanation
Fully triggerable by an unprivileged attacker via normal TPU ingestion: submit a batch containing two transactions that both write the same account (e.g., both transferring from/into a shared account, or writing to a shared PDA). No special permissions, staking, leader control, or leaked keys are needed — only crafting an ordinary transaction batch, making this highly likely to be reachable and repeatable.

### Recommendation
Apply locks incrementally within the same pass instead of splitting validation and locking into two separate passes: for each transaction, first check `can_lock_accounts`, and if it succeeds, immediately call `lock_accounts` before moving to the next transaction in the batch, so that later transactions in the same batch see the locks taken by earlier ones. Alternatively, pre-aggregate all write/read keys declared across the batch and detect intra-batch conflicts before locking any of them, then fail all conflicting transactions consistently.

### Proof of Concept
```rust
#[test]
fn test_try_lock_transaction_batch_rejects_same_batch_write_conflict() {
    let mut account_locks = AccountLocks::default();
    let shared_key = Pubkey::new_unique();

    // Two transactions in the same batch, both declaring `shared_key` as writable.
    let tx1_keys = vec![(&shared_key, true)];
    let tx2_keys = vec![(&shared_key, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = account_locks.try_lock_transaction_batch(batch);

    // Invariant: only one of the two conflicting writers may succeed.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both transactions writing the same account were locked simultaneously: {:?}",
        results
    );
}
```
Running this test against the current implementation is expected to fail, showing `ok_count == 2` (both transactions succeed), confirming that `try_lock_transaction_batch` does not enforce write-lock exclusivity within a single batch.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }
