### Title
Webhook shop identity not bound to HMAC signature enables cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`/`webhook_id`) from HTTP headers, while `Utils::HmacValidator` only authenticates the raw request body. The HMAC signature therefore proves that the *body bytes* were produced with the app's `client_secret`, but it makes no claim about which shop the request is *for*. Any request whose body was legitimately signed by Shopify for the app (i.e. a webhook delivered to any shop that installed the app) can have its `shop-domain` header swapped to a different tenant without invalidating the signature, because the signature never covers that header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it to the `hmac` header value: [3](#0-2) 

`Webhooks::Registry.process` accepts the request purely on that body-only HMAC check, then builds `WebhookMetadata` using the unauthenticated `shop` header and dispatches it to the app's handler: [4](#0-3) 

The equality this breaks is: **shop authenticated by HMAC** should equal **shop the handler is told to act on**. In this implementation, the HMAC only authenticates `raw_body`; `request.shop` is trusted independently. Because Shopify signs webhooks with the app's single `client_secret` (shared across every shop that installs the app, not a per-shop secret), a request body that was legitimately signed for shop A remains validly signed regardless of which `shop-domain` header accompanies it. An attacker who controls (or has installed the app on) any shop can:

1. Trigger a webhook delivery to their own shop with an attacker-chosen body (e.g., by editing a customer/product/order field that's included in the payload).
2. Capture the legitimate `raw_body` + `hmac-sha256` header pair Shopify sent for that delivery.
3. Replay that exact body/HMAC pair to the app's webhook endpoint, substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header with a victim shop's domain.
4. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim shop.

If the host application's webhook handler uses `data.shop` to select which shop's session/store to write to (the intended and documented pattern), the attacker has achieved cross-tenant data injection/processing under a victim shop's identity, using only their own (possibly attacker-controlled) app installation - no access token, session, or credential belonging to the victim is required.

### Impact Explanation
This is a cross-tenant access vulnerability: an unprivileged party with a legitimate install of the app on their own shop can forge webhook events attributed to a different shop, causing the host application to process attacker-controlled data under another tenant's identity. This matches the Critical "cross-tenant access" impact category, since it breaks the tenant isolation the gem's `Webhooks::Registry`/`HmacValidator` are meant to guarantee.

### Likelihood Explanation
Likelihood is high for any app that installs on more than one shop (i.e., any public app) and relies on `WebhookMetadata#shop` (as documented) to scope handler behavior. The only prerequisite is the ability to install the app on an attacker-controlled shop and observe/capture one legitimate webhook delivery — no secret material, session, or victim-shop credential is needed.

### Recommendation
Bind the header-derived identity fields to the authenticated payload before trusting them:
- Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (this requires a corresponding change server-side would not be possible since Shopify controls webhook signing, so instead) enforce that `request.shop` matches an expected/registered shop for the delivery, and/or require the host application to independently verify that the shop in `WebhookMetadata` corresponds to a shop that is actually expecting the given `webhook_id`/`topic` combination.
- At minimum, document prominently that `WebhookMetadata#shop` is **not** covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., cross-checking against Shopify's webhook registration records via `get_webhook_id`).

### Proof of Concept
1. App is installed on attacker's shop `attacker.myshopify.com` and victim's shop `victim.myshopify.com`, both using the same app `client_secret`.
2. Attacker edits their own store data to trigger a webhook (e.g. `customers/update`) with a body containing attacker-chosen values.
3. Attacker captures the delivered request: `raw_body` and header `X-Shopify-Hmac-Sha256`.
4. Attacker POSTs this exact `raw_body` to the app's webhook endpoint, replacing header `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — validation passes.
6. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` with attacker-controlled body content, causing the app to process/act as though victim's shop sent this data.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
