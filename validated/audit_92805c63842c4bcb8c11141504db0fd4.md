Based on my investigation, I found a genuine analog in `EvmHost.dispatch()`, where native-token fee payments are converted into fee tokens via a live Uniswap V2/V3 spot swap with no oracle-based sanity check, no TWAP, and no slippage/deviation bound beyond the caller-supplied `msg.value`. This is directly analogous to the reported `MavEthOracle` issue: both price a value directly from a manipulable, single-block AMM state (spot reserves / spot price) rather than a resistant oracle.

### Title
Native-fee-to-token conversion in `EvmHost.dispatch`/`quoteNative` relies on manipulable Uniswap spot price, letting an attacker under- or over-pay dispatch fees ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch()` swaps the caller's native token for the exact fee-token amount needed to pay for a POST dispatch by calling the configured `uniswapV2` router's `swapETHForExactTokens`, which derives the required ETH input directly from the pool's current reserves/spot price with no oracle cross-check, TWAP, or deviation bound.

### Finding Description
In `EvmHost.dispatch()`, when `msg.value > 0`, the contract swaps native ETH for `post.fee` amount of fee tokens using the local Uniswap V2 router at the current block's spot reserves: [1](#0-0) 

The router used can be the native V2 router or one of the V3/V4 "UniswapV2-compatible" wrappers, such as `UniV3UniswapV2Wrapper.swapETHForExactTokens`, which computes `amountInMaximum` off `msg.value` and quotes via `exactOutputSingle` against the live pool state with `sqrtPriceLimitX96: 0` (no price-impact guard): [2](#0-1) 

Just as `MavEthOracle.getPriceInEth` computes LP value from a live, flash-loanable `getReserves()` snapshot with no TWAP/manipulation resistance, this dispatch path derives the ETH cost of a required fee-token amount purely from the pool's instantaneous state at execution time. Any unprivileged caller of `dispatch()` — the entry point reachable by every message dispatcher, token bridger, or intent solver posting a cross-chain message and paying with native token — chooses the block in which their transaction executes and can flash-loan/trade against the configured Uniswap pool immediately before calling `dispatch()`, moving the spot price before the swap executes.

### Impact Explanation
By manipulating the pool's reserves in the same transaction (via a flash loan/large swap on the underlying pool immediately before calling `dispatch`), an attacker can:
- Cause the swap to consume far less ETH than the true market price of `post.fee` fee tokens, extracting value from the host's ETH balance / the swap's slippage tolerance while still successfully paying the exact fee-token requirement, or
- Cause it to overpay in ETH (unlikely to be attacker-favorable but shows unsound pricing), or, more critically,
- If the manipulation makes the swap revert or drain unexpected value via sandwich, disrupt fee payment for legitimate dispatchers — this can degrade or block message dispatch (a route unable to deliver messages) for a given chain's fee-token pool.

This directly affects protocol funds custody (the fee token balance backing relayer payouts) since fees collected here fund relayer rewards; underpayment or drained value from the swap represents a concrete theft/loss vector for protocol funds tied to message dispatch — the core operation of `EvmHost`.

### Likelihood Explanation
The vulnerable code path is reachable by any unprivileged caller who calls `dispatch()` with `msg.value > 0`, which is the standard, permissionless way applications pay native-token fees for cross-chain dispatch. No governance/admin gating exists on this swap; the only protections are the router's own `amountInMaximum`/deadline mechanics, not an oracle or TWAP-based price sanity bound. Any chain where the configured `uniswapV2` pool has moderate-to-low liquidity relative to available flash-loan capital is exploitable pre-transaction.

### Recommendation
Do not derive the fee-token cost purely from the live AMM pool at time of the swap. Cross-check the computed input against a manipulation-resistant reference (TWAP oracle, Chainlink, or a bounded max-deviation check similar to `checkPriceGuard` used elsewhere in this codebase for Uniswap V4 venue pricing), and enforce a maximum acceptable ETH input (slippage bound) independent of `msg.value`, reverting if spot price deviates beyond a configured threshold from the reference price.

### Proof of Concept
1. Attacker identifies an `EvmHost` deployment whose `_hostParams.uniswapV2` points to a thinly-liquid WETH/feeToken pool (or a `UniV3UniswapV2Wrapper`-wrapped V3 pool).
2. In a single transaction (optionally via flash loan), attacker swaps a large amount into/out of the pool to shift the spot price favorably.
3. Still within the same transaction, attacker calls `EvmHost.dispatch()` with a `DispatchPost` whose `post.fee` is the desired fee-token amount, sending `msg.value` calculated against the manipulated price.
4. `dispatch()` calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` [1](#0-0) , which executes at the attacker-manipulated spot price, paying `post.fee` fee tokens for less ETH than fair market value.
5. Attacker reverses the initial swap/repays the flash loan, netting the value difference at the expense of the fee-token reserves/backing that fund relayer rewards.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactOutputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 spent = abi.decode(results[0], (uint256));

        if (spent < msg.value) {
            uint256 refund = msg.value - spent;
            IWETH(weth).withdraw(refund);

            (bool success,) = msg.sender.call{value: refund}("");
            if (!success) revert RefundFailed();
        }

        uint256[] memory amounts = new uint256[](2);
        amounts[0] = spent;
        amounts[1] = amountOut;

        return amounts;
    }
