### Title
Unsanitized `destinationMemo` allows colon-injection into POA bridge withdrawal memo, letting a user override the signed destination address — (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts)

### Summary
`createWithdrawIntentPrimitive()` builds the `memo` field of a signed `ft_withdraw` intent by naively colon-joining the caller-controlled `destinationAddress` and `destinationMemo` strings, without escaping or rejecting a colon character in either input.

### Finding Description
The memo is constructed as a positional, colon-delimited string: [1](#0-0) 

`memo.join(":")` produces something like `WITHDRAW_TO:<address>[:<xrpMemo>]`. This is the exact bug class from the report: a structured/serialized payload is built by inline string concatenation of user-controlled fields without escaping the field separator, so a value can inject additional "fields" that a downstream parser (here, the POA bridge, which is documented to consume this memo to route/settle the off-chain withdrawal) will interpret differently than the caller of the SDK intended.

`destinationAddress` for POA-bridge-routed withdrawals is validated by chain-specific format checks in `validateAddress.ts` (e.g. `validateXrpAddress`, `validateBtcAddress`, etc.), and these formats generally cannot contain a literal `:` for the chains that accept a companion `destinationMemo` (XRP classic/X-addresses do not contain `:`), so the primary injection vector is the **`destinationMemo`** parameter — which is documented as free text passed through to the transaction memo field and is not shown anywhere in the reachable code to be validated, length-limited, or rejected for a `:` character: [2](#0-1) 

Since `memo.push(xrpMemo)` appends the raw value as the third colon field, a caller-supplied `destinationMemo` containing `:` (e.g. `"0:rEvilAddressXXXX"` or similar) changes the number/content of colon-delimited fields signed into the intent. This is signed and submitted as part of the intent (`memo` field of `IntentFtWithdraw`) that the POA bridge later parses to decide the physical on-chain destination/tag.

### Impact Explanation
If the downstream POA bridge relayer/service parses this memo positionally by splitting on `:` (which is the documented purpose of the `"WITHDRAW_TO:<address>:<xrpMemo>"` format), a caller can craft a `destinationMemo` that injects extra colon-separated segments. Depending on how strictly the relayer validates the segment count/content, this can change what the relayer treats as the destination address or destination tag versus what the SDK/API caller/UI displayed and intended to authorize — i.e., "an address ... paid that was not the one validated" against the caller's original `destinationAddress`. Because this memo is embedded inside a signed `MultiPayload` intent, the injected content is cryptographically committed alongside the legitimate address, mirroring the samlify root cause (unescaped value placed into a delimited/structured signed field, changing how a downstream consumer parses it).

### Likelihood Explanation
Any caller of the SDK's withdrawal API can supply an arbitrary `destinationMemo` string (it is a plain, unvalidated `string | undefined` per `WithdrawalParams`), and `createWithdrawIntentPrimitive` performs no sanitization before concatenation — the vulnerable path is reached on every POA-bridge withdrawal that sets a memo, with no privileged or admin action required. The only limiting factor for exploitation is how leniently the external POA bridge relayer parses the memo, which is outside this repo's control and could not be verified given the read-only, index-limited investigation of this codebase.

### Recommendation
Validate `destinationMemo` (and `destinationAddress`) to reject `:`/other memo-delimiter characters before use in `createWithdrawMemo`, or switch to an unambiguous, length-prefixed or JSON-based memo encoding so a value cannot inject additional positional fields. Additionally, enforce this at the type/parameter level in `WithdrawalParams.destinationMemo` (packages/intents-sdk/src/shared-types.ts) so all bridges share the same guarantee.

### Proof of Concept
```ts
import { createWithdrawIntentPrimitive } from "packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils";

const intent = createWithdrawIntentPrimitive({
  assetId: "nep141:usdc.omft.near", // -> resolves to an XRP-routed token in practice
  destinationAddress: "rLegitimateReceiverAddressXXXXXXX",
  destinationMemo: "0:rAttackerControlledAddressYYYYYYYY", // colon injects an extra field
  amount: 1000000n,
});

console.log(intent.memo);
// -> "WITHDRAW_TO:rLegitimateReceiverAddressXXXXXXX:0:rAttackerControlledAddressYYYYYYYY"
// A relayer that positionally parses "WITHDRAW_TO:<address>:<tag>" may split this
// unexpectedly, since the third field itself contains a colon-delimited sub-structure.
```

Note: I could not access or verify the external POA-bridge relayer's memo-parsing logic (it is outside this repo and outside the review scope per the rules), so the exact downstream misparsing behavior is unconfirmed; the finding is scoped strictly to the unsanitized concatenation in `createWithdrawMemo` within `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts`, which is the root-cause equality break (memo content the caller did not intend to authorize becomes part of the signed intent).

```typescript
function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
```
