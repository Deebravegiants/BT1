### Title
Webhook HMAC only authenticates the raw body, not the `shop-domain` or `topic` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies the authenticity of an inbound webhook solely by HMAC-validating the raw request body against the app's shared `api_secret_key`. The `shop` and `topic` values, which are taken directly from unauthenticated HTTP headers, are never part of the signed material and are handed to the application's handler as if they were verified identity fields.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the request purely through `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., only the raw body) and compares it against a signature computed with the shared `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

Because the `api_secret_key` is the app's single client secret shared across every shop that installs the app (not a per-shop secret), any merchant who installs the app can legitimately trigger real webhook deliveries to their own store and thereby obtain a body + valid HMAC pair signed with that shared secret. Since the HMAC never covers the `shop-domain` or `topic` headers, that attacker can replay the exact same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a *different* victim shop. `HmacValidator.validate` will still succeed because it only checks the body bytes, and `Registry.process` will dispatch to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is the attacker-controlled, unauthenticated header value: [5](#0-4) 

This breaks the identity binding `authenticated_shop == shop_used_for_tenant_lookup`: the gem authenticates the byte content but silently trusts an unauthenticated `shop` field for tenant identification, exactly the pattern of "bytes verified versus bytes parsed" called out as in-scope.

### Impact Explanation
Applications built on this gem (matching the documented pattern in `docs/usage/webhooks.md` and the `WebhookMetadata` handler contract) use `shop` from the webhook payload to select which merchant's session/data to update in response to the event (e.g., processing an `orders/create`, `app/uninstalled`, or GDPR webhook "for" a given shop). Since `shop` is not bound to the signature, an attacker who is a legitimate (or trial) merchant installing the app can forge webhooks that appear to originate from any other shop the app serves, causing the app to process attacker-supplied webhook bodies under a victim tenant's identity — a cross-tenant integrity/confidentiality violation depending on what the handler does with the data (e.g., could trigger `app/uninstalled` cleanup, GDPR data deletion, or order-processing side effects against the wrong store).

### Likelihood Explanation
The attacker only needs their own working install of the target app (any developer can create one) to obtain a validly-signed body/HMAC pair — no access to the actual `api_secret_key` value is required, satisfying the "unprivileged internet user" constraint. Crafting and sending the replayed HTTP POST with a modified `x-shopify-shop-domain` header requires no special access beyond reaching the app's public webhook endpoint.

### Recommendation
Include the `shop-domain` and `topic` header values (or an equivalent shop-bound nonce) inside the signed material, or independently verify that the shop in the webhook maps to the app's own known/installed shop-secret pairing (if per-shop secrets are used) before trusting `request.shop` for tenant dispatch. At minimum, document that `Registry.process` does not guarantee the authenticity of the `shop` header and require downstream consumers to cross-check it against an independently verified value (e.g., an active session for that shop).

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed using the app's shared `api_secret_key`.
2. Attacker sends a new HTTP POST directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid because only the body is signed)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged or attacker-chosen
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [6](#0-5) 
4. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this webhook, demonstrating the cross-tenant spoof.
