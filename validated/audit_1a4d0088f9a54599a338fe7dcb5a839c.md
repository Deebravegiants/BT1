### Title
Changing token decimals via `update_token` mis-prices in-flight cross-chain transfers, causing unbacked mint or permanently frozen funds - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`Precisions<T>` stores the ERC20 decimals used to convert between local (Substrate) and EVM token amounts for a given `(AssetId, StateMachine)` pair. This value is read fresh at the moment a transfer is processed rather than being snapshotted per-message. `update_token()` lets the `CreateOrigin` change this decimals value for a chain that is already live and has messages in flight, with no mechanism to keep already-dispatched-but-unprocessed messages consistent with the precision that was in effect when they were created — mirroring the founders-vesting bug class where a config value (`reservedUntilTokenId`) used to derive per-message state is mutated without re-deriving or reconciling already-created dependent state.

### Finding Description
`Precisions::<T>` is a live, mutable per-`(AssetId, StateMachine)` mapping used purely for precision conversion between local decimals and the peer EVM chain's decimals [1](#0-0) .

On send, `Precisions::<T>::get(asset_id, destination)` is read and used to compute `erc20_amount = convert_to_erc20(amount, erc_decimals, decimals)`, which is embedded in the dispatched cross-chain `Message` body [2](#0-1) . This conversion factor is baked into the message payload at dispatch time and is never re-derived once the request commitment is created — the counterparty is expected to interpret the encoded amount using the precision that was configured when the message was produced.

`update_token()` allows the `CreateOrigin` to overwrite `Precisions::<T>` for a chain that already has a registered contract and (potentially) in-flight messages, unconditionally and without any check for outstanding, unprocessed requests: 

```rust
Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
``` [3](#0-2) 

Because the mapping doc explicitly states it exists "for precision conversion" between the two representations, and there is no per-message stored precision snapshot (only the live map), any code path that must reinterpret an already-encoded amount using the *current* `Precisions` value (e.g. converting an inbound EVM amount back to local balance, or refunding/timing-out a previously sent message) will use whichever decimals value happens to be configured at processing time, not the value in effect when the message/commitment was created. This is structurally identical to the Nouns Builder bug: `_addFounders()` computes derived per-founder token slots from `reservedUntilTokenId` at creation time, but `updateFounders()`/later logic recomputes slots from the *current* `reservedUntilTokenId`, which no longer matches the value the allocation was actually built from once the DAO calls `setReservedUntilTokenId()`.

### Impact Explanation
If `update_token()` is called to change a chain's decimals configuration while a `send()`-originated message is still in flight (unconfirmed/unprocessed), the amount encoded in the commitment (computed with the old decimals) can be reinterpreted with the new decimals during later reconciliation. Depending on direction, this either:
- mints/credits an incorrect (larger) amount relative to what was actually escrowed/burned — an unbacked mint, or
- mints/credits an incorrect (smaller) amount — permanently stranding the difference in escrow with no path to recover it, a freezing-of-funds bug.

Both outcomes are direct, unprivileged-user-reachable consequences (the `send()` call is available to any signed account) of an ordinary governance/administrative action that does not anticipate outstanding cross-chain state, exactly the "impact on ordinary derived state after an ordinary config change" pattern flagged in the source report.

### Likelihood Explanation
Likelihood is moderate: it requires a chain operator to call `update_token()` on a token/chain pair that already has messages in flight (a plausible operational event — e.g. correcting a misconfigured decimals value for a token that is already live and being actively bridged). Since there is no guard rejecting changes to `Precisions` while outstanding requests exist for that `(asset, chain)` pair, this can occur during normal, non-malicious governance operation, just as the original issue occurs during a normal, non-malicious `reservedUntilTokenId` update.

### Recommendation
Either (a) snapshot the precision/decimals value used for a given transfer at `send()` time inside the request/commitment metadata so any later reconciliation reuses that exact value rather than the live `Precisions` map, or (b) block `update_token()` from mutating `Precisions` for a `(asset_id, chain)` pair while any dispatched requests to that chain remain unconfirmed, analogous to recomputing (or freezing) dependent derived state whenever the underlying configuration value changes.

### Proof of Concept
1. Operator registers asset `X` for `StateMachine::Evm(chain)` with `decimals = 6` via `register_token` [4](#0-3) .
2. User calls `send()`, locking/burning `amount` of local balance and dispatching a message whose body encodes `erc20_amount = convert_to_erc20(amount, 6, local_decimals)` [5](#0-4) .
3. Before the message is finalized/processed, the operator calls `update_token()` to change decimals for that same `(asset_id, chain)` to `18` [6](#0-5) .
4. Any subsequent logic that reinterprets the message's encoded amount (timeout refund conversion, or destination-side accounting keyed on the live `Precisions` value) now derives a mismatched local amount relative to what was actually escrowed/burned in step 2, producing an unbacked mint or a permanently stranded balance for the user.

		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}

		pub fn update_token(
			origin: OriginFor<T>,
			update: TokenUpdate<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if update.asset_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					update.asset_id.clone(),
				)
			};

			for (chain, config) in update.add_chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				// Remove old reverse mapping if it exists
				if let Some(old_contract) = TokenContracts::<T>::get(chain, update.asset_id.clone())
				{
					ContractToAsset::<T>::remove(chain, old_contract);
				}

				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					update.asset_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(chain, token_contract, update.asset_id.clone());
				Precisions::<T>::insert(update.asset_id.clone(), chain, config.decimals);
			}
