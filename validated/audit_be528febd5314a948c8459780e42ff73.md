### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` as trusted identity fields read straight from HTTP headers, but the HMAC signature the gem verifies only ever covers the raw request body. Any attacker capable of obtaining one valid `(body, hmac)` pair from Shopify (trivially available by installing the app on their own shop and receiving a real webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for any other tenant, and the HMAC check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic`, which the host application uses to determine which tenant/shop the webhook payload belongs to, are pulled directly from headers that are never fed into `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the raw body) and compares it against the `hmac` field: [3](#0-2) 

This breaks the identity binding the gem is expected to guarantee: `verified(hmac, body) == true` should imply `shop == the shop that Shopify actually sent this body for`. Instead the equality only holds for `body`; `shop` and `topic` are unauthenticated inputs. This is exactly the "field acted on but not covered by the HMAC" bug class: the same pattern in the analog report where the loop-margin position handling doesn't account for external state changes (liquidation) that must be tracked but isn't bound into the operation performed.

Since `shop` is the field host applications rely on (per the gem's own documented API, `WebhookHandler#handle(topic:, shop:, body:)`) to select which tenant's data/access token context the webhook body should be attributed to, an attacker who legitimately owns a shop that installs the target app can:
1. Receive a real webhook (e.g. `orders/create`) for their own shop, with a Shopify-computed valid `X-Shopify-Hmac-Sha256` over the raw body.
2. Replay the identical raw body and HMAC value directly to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain (and/or a different `X-Shopify-Topic`).
3. `HmacValidator.validate` still returns `true` because it only checks the body bytes, not the shop/topic headers, so `ShopifyAPI::Webhooks::Registry`/`Request` will treat the forged headers as authenticated and hand the body to the app's handler tagged as the victim shop.

### Impact Explanation
This is a cross-tenant integrity/attribution bypass: an unprivileged attacker who is merely another (possibly free/trial) merchant of the same app can make the app process attacker-controlled webhook content under a victim shop's identity, despite passing HMAC verification. Depending on how the host app's webhook handler uses `shop` (e.g., persisting attacker data against the victim's account, triggering victim-shop-scoped actions, or associating unrelated business data cross-tenant), this crosses the tenant boundary that the HMAC check is supposed to enforce — matching the "cross-tenant access" Critical impact category, since the guarantee the gem's `HmacValidator` is meant to provide (authenticity of the whole webhook envelope, including which shop it is for) does not actually cover the shop identity field.

### Likelihood Explanation
Likelihood is realistic: no privileged credentials, access tokens, or `client_secret` are required. The only prerequisite is that the attacker can install the target app on a shop they control (a normal, unprivileged action for any Shopify app that supports public/dev installs), and can send arbitrary HTTP headers to the app's public webhook endpoint (which is exposed to the internet by design). No interception of Shopify's traffic is needed — only reuse of an authentic body+HMAC pair the attacker legitimately received for their own shop.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signable content, or otherwise cryptographically bind them to the raw body before computing/verifying the signature, so that `HmacValidator.validate` cannot pass unless the `shop` and `topic` values are exactly what Shopify computed the signature over. At minimum, document (and better, enforce in the gem) that `Request#shop`/`Request#topic` must not be trusted as authenticated unless the caller independently confirms them out-of-band (e.g., cross-checking against a shop the app has an active session for), since today's `to_signable_string` implementation only authenticates `@raw_body`.

### Proof of Concept

# Attacker installs the target app on their own shop "attacker.myshopify.com"
# and receives a legitimate webhook POST from Shopify, e.g.:
#   headers: {
#     "X-Shopify-Topic" => "orders/create",
#     "X-Shopify-Hmac-Sha256" => "<valid-base64-hmac-of-body>",
#     "X-Shopify-Shop-Domain" => "attacker.myshopify.com"
#   }
#   body: '{"id":1,...}'

# Attacker replays the SAME body + SAME hmac header to the app's public
# webhook endpoint, only swapping the shop-domain header:
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <same valid hmac from step above>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
Content-Type: application/json

{"id":1,...}

# In the gem:
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because
# HmacValidator only recomputes HMAC over request.to_signable_string == raw_body,
# never over request.shop ("victim-shop.myshopify.com") or request.topic.
#
# The host app's WebhookHandler is then invoked with shop: "victim-shop.myshopify.com"
# even though Shopify never sent this webhook for that shop.
