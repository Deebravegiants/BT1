### Title
Single invalid message in a `handle_unsigned` batch reverts and rejects all other valid messages bundled with it - ([File: modules/pallets/ismp/src/impls.rs])

### Summary
`pallet_ismp::Pallet::execute` processes a `Vec<Message>` submitted via the permissionless `handle_unsigned` extrinsic by mapping every message through `handle_incoming_message` and collecting into a single `Result<Vec<_>, _>`. Because `.collect::<Result<Vec<_>, _>>()` short-circuits on the first `Err`, one malformed/duplicate/timed-out message anywhere in the batch causes the whole extrinsic to return `Error::<T>::InvalidMessage`, discarding (on rollback) any state changes already made for the other, otherwise-valid messages in the same batch. This mirrors the reported bug class: a per-item failure that should be logged/skipped instead bubbles up and denies processing for the entire batch.

### Finding Description
`execute()` builds `message_results` from every message in the incoming `Vec<Message>` and immediately fails the whole call if any single one errors: [1](#0-0) 

The same short-circuiting exists at the individual `RequestMessage` level: `handle::<H>` in the request handler validates every `PostRequest` inside a single membership-proof batch in one loop, and returns immediately (`Err(...)?`) as soon as any one request is a duplicate, timed out, or misrouted — before any of the batch's requests are dispatched to their destination modules: [2](#0-1) 

This is reachable by any unprivileged relayer submitting `handle_unsigned` (an unsigned, permissionless extrinsic validated via `ValidateUnsigned`): [3](#0-2) 

Since relayers commonly batch multiple ISMP messages (and multiple `PostRequest`s under one proof) from potentially many different, unrelated senders into a single submission for efficiency, an attacker who controls one request in that batch (e.g., by dispatching a request that will time out, or that a competing relayer already delivered, creating a duplicate) can poison the entire bundle. Any legitimate messages bundled alongside it fail to be delivered even though they individually would have succeeded.

### Impact Explanation
This does not directly steal funds or forge messages, but it degrades message delivery: a batch containing several unrelated, otherwise-valid cross-chain messages can be denied delivery in bulk because of a single unrelated invalid entry, chosen or triggered by an unprivileged third party. Under the rules' impact categories this falls into "a route unable to deliver messages" — repeated poisoning of batches can stall throughput for a shared batching relayer, delaying request/response/timeout delivery for many users at once. It is not obviously a "Critical" or "High" fund-loss bug; it is a batch-atomicity/availability issue, similar in class (not in state) to the original Lombard report.

### Likelihood Explanation
Likelihood depends on relayer batching behavior. Hyperbridge relayers in `tesseract/messaging` (e.g. `outbound.rs`, `retries.rs`) group multiple `PostRequest`s from possibly unrelated sources under one `RequestMessage`/proof height to save proof-verification cost — this batching logic exists but I could not fully confirm, within the available tool budget, whether an unprivileged external actor can reliably force one of *their own* choosing into a bundle alongside targeted victims' requests, or whether relayers isolate batches per submission window in a way that limits blast radius. This detail is unverified due to the search budget being exhausted before I could trace `batch_requests`/`group_by_proof_height` definitions fully.

### Recommendation
Change `execute()` (and the per-request loop in `handlers/request.rs`/`handlers/response.rs`) to process each message/request independently, collecting individual successes and failures (e.g., emitting an `Errors` event per failed item, as the code already does for the aggregate case) rather than short-circuiting the whole batch via `.collect::<Result<Vec<_>,_>>()`. Valid messages in a batch should be applied and their events emitted even when a sibling entry in the same call is invalid.

### Proof of Concept
Not independently reproduced; reasoning is based on static code-path analysis:
1. Relayer submits `handle_unsigned` with `messages = [ValidRequestA, ValidConsensusB]` batched together.
2. Attacker independently ensures `ValidRequestA`'s underlying request is already delivered (or times out) before the batch lands, so `handle_incoming_message` for it returns `Err(DuplicateRequest)` / `Err(RequestTimeout)`. [4](#0-3) 
3. `execute()`'s `.collect::<Result<Vec<_>, _>>()` turns the whole batch into `Err`, and the dispatchable returns `Error::<T>::InvalidMessage`, rolling back any storage effects from `ValidConsensusB` as well. [5](#0-4)

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;
