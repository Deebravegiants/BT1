### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing via header substitution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` binds solely to `@raw_body`. The `shop` (and `topic`, `webhook_id`, `api_version`) values, which are read from unauthenticated HTTP headers, are never part of the signed bytes but are still trusted and forwarded to the app's webhook handler for shop attribution.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via: [1](#0-0) 

The HMAC check calls into `HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Request`, `to_signable_string` returns only `@raw_body` — headers are excluded entirely from the signed bytes: [3](#0-2) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` — all read from headers, not from the signed body — are trusted and handed to the app's handler as the tenant/routing identity: [4](#0-3) [5](#0-4) 

This breaks the intended binding: `shop header == shop the signed body actually belongs to`. Because the app's `client_secret` (`Context.api_secret_key`) is shared across every shop that has installed the app, any merchant who installs the app receives legitimately-signed webhooks for their own store — i.e., a valid `(raw_body, hmac)` pair signed with the app's single shared secret. That merchant (an unprivileged internet user relative to other tenants of the same app) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`/`webhook-id`) header for a different shop, since none of those header values are covered by the signature. `HmacValidator.validate` still returns `true` because it only checks the untouched body bytes, and `Registry.process` forwards the attacker-chosen `shop` to the handler as if Shopify itself had asserted it for that domain.

### Impact Explanation
This is a cross-tenant identity-binding break: data that the host application uses to route/attribute a webhook payload to a specific merchant (`shop`) is not authenticated, only the payload body is. Any downstream app logic that uses `WebhookMetadata#shop` to select which tenant's records to update (a documented, expected usage per `docs/usage/webhooks.md`) can be tricked into applying one shop's webhook body under another shop's identity, corrupting or leaking data across tenant boundaries — matching the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Any unprivileged actor able to install the app on their own store (which most public/embedded Shopify apps allow via normal app-install flow) automatically obtains a validly-HMAC-signed webhook body/signature pair for their own shop merely by triggering an event (e.g., updating a product). They can then replay that captured `(raw_body, hmac)` to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No secrets, tokens, or privileged access are required beyond ordinary app installation, which is the normal entry point for any merchant.

### Recommendation
Bind the identity headers into the signed material verified by the gem, e.g., include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (or otherwise require an out-of-band trust check, such as verifying `shop` against the shop associated with the session/registration under which delivery is expected) before handing them to the handler as trusted values. At minimum, document/enforce that host apps must independently verify `data.shop` is an installed, known tenant rather than treating it as authenticated by the HMAC check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining the app's shared `client_secret`-derived trust relationship like any other merchant.
2. Attacker triggers a webhook event (e.g., `products/update`) on their own shop and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header sent to the app's webhook endpoint — this is a legitimately signed `(raw_body, hmac)` pair.
3. Attacker replays the identical body and HMAC header to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over the unchanged `raw_body` and returns `true`, because `to_signable_string` never includes the shop header.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds to invoke the app's handler with `shop: "victim-shop.myshopify.com"`, causing the attacker's own webhook payload to be processed/attributed as belonging to the victim tenant.
