### Title
Fee-refund `IERC20.safeTransfer` inside `dispatchTimeOut` permanently blocks message-timeout delivery for a blacklisted fee payer - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchTimeOut` (both the `PostRequestTimeout` and `GetRequestTimeout` overloads) refunds the relayer fee to the original request payer (`meta.sender`) via a direct `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` call, executed in the same transaction as, and *after*, the successful app-level `onPostRequestTimeout`/`onGetTimeout` callback. If this transfer reverts — e.g. because `feeToken()` is a blacklist-capable token like USDC and `meta.sender` is blacklisted, or the token reverts on a zero-value transfer — the entire transaction, including the already-executed app-level timeout refund, is rolled back. Because the state (`_requestCommitments[commitment]`) is restored on revert, the request remains permanently un-timeoutable: any relayer re-submitting the same timeout proof hits the identical revert. This mirrors the reported `_executeForeclosure` bug class where a push-style token transfer to a party outside the caller's control blocks an entire critical settlement/refund flow.

### Finding Description
`dispatchTimeOut` for `PostRequestTimeout` (and the analogous `GetRequestTimeout` variant) is only reachable through the `HandlerV2`, called by any relayer submitting a valid timeout proof — this is an unprivileged, permissionless path (`restrict(_hostParams.handler)` only gates it to the handler contract, not to any specific caller).

```solidity
function dispatchTimeOut(
    PostRequestTimeout memory timeout,
    FeeMetadata memory meta,
    bytes32 commitment
) external restrict(_hostParams.handler) {
    // replay protection
    delete _requestCommitments[commitment];
    (bool success,) = _bytesToAddress(timeout.request.from)
        .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

    if (!success) {
        // so that it can be retried
        _requestCommitments[commitment] = meta;
        return;
    }

    if (meta.fee != 0) {
        // refund relayer fee
        IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
    }
    emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
}

`meta.sender` is `post.payer`, an arbitrary address supplied by the dispatching app/user when the original request was created — the host does not control or vet it:
```solidity
_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
``` [2](#0-1) 

The app-level `onPostRequestTimeout` call already succeeds and performs its state-changing refund logic (e.g. `HyperFungibleToken`/`BridgeToken` re-minting burned tokens to the refundee) before the fee-refund transfer executes:
```solidity
function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
    Message memory message = abi.decode(incoming.request.body, (Message));
    address refundee = _toAddr(message.from);
    _mint(refundee, message.amount);
    emit Refunded({to: refundee, amount: message.amount});
}
``` [3](#0-2) 

Because `dispatchTimeOut` performs the app callback and the fee refund in a single atomic transaction with no try/catch or pull-payment fallback around the `safeTransfer`, any revert in the fee transfer unwinds the whole call — including the app's successful refund `_mint`. The `_requestCommitments[commitment]` state is fully restored (it was only conditionally re-set inside the `if (!success)` branch, but a revert restores it regardless via EVM revert semantics), so the exact same failure recurs on every retry by every relayer. There is no way to separate "deliver the timeout to the app" from "pay the relayer-fee refund" — unlike the `dispatchIncoming`/`onAccept` path, which explicitly deletes/restores receipts on failure but does not couple an uncontrolled ERC-20 transfer to a third-party address into the same all-or-nothing call for the *timeout* refund path.

This is the same root-cause pattern as the reported Blueprint-Finance issue: a push-transfer to an address the contract cannot control (here, the original fee payer `meta.sender`, analogous to `_owner()` in the report) is embedded in a critical, unprivileged, relay-driven settlement path, and its failure (blacklist, zero-transfer revert, or any other revert-on-transfer token behavior of the configured `feeToken()`) blocks the whole flow rather than being isolated behind a pull-pattern.

### Impact Explanation
If the host's `feeToken()` is a blacklist-capable stablecoin (USDC, USDT-style tokens are common `feeToken()` configurations referenced throughout the docs) and the original fee payer becomes blacklisted (sanctions, compliance action, or any other reason outside the protocol's control) after dispatching a request that later times out, `dispatchTimeOut` becomes permanently unexecutable for that commitment. Consequences:
- The relayer that submits the valid timeout proof can never complete the delivery — this is a "route unable to deliver messages" condition for that specific request.
- Any app-level compensating action gated behind the timeout (e.g., re-minting burned bridge tokens back to the sender in `HyperFungibleToken`/`BridgeToken`, refunding escrowed intent inputs, etc.) is permanently blocked too, since it is rolled back together with the failing fee transfer every time.
- This results in permanent freezing of the underlying principal funds associated with that request (not just the relayer fee), because the app-side refund and the fee refund cannot be decoupled.

### Likelihood Explanation
Likelihood is moderate: it requires the configured `feeToken()` to implement transfer-blocking semantics (a real-world condition for USDC/USDT and many compliance-sensitive stablecoins) and the specific `meta.sender` to become non-transferable (blacklisted) or for the fee refund to be zero-value and revert on that condition, at a point in time when a request they paid for times out. This does not require any malicious action by an attacker against the protocol itself — it can be triggered passively by an unrelated compliance/blacklist event on the fee token, and once triggered it is a deterministic, permanent freeze with no privileged recovery path exposed in this function.

### Recommendation
Decouple the relayer-fee refund from the mandatory app callback success path using a pull-payment pattern, mirroring the remediation used in the referenced report:
- Wrap the `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` calls in `dispatchTimeOut` (both overloads) and in `dispatchIncoming`'s relayer-fee reward in a `try/catch`.
- On failure, credit an internal `pendingWithdrawals[meta.sender][feeToken()] += meta.fee` balance instead of reverting, and expose a `claim()` function for the payer/relayer to withdraw once eligible.
- This ensures the app-level timeout/response handling (and its associated fund recovery) can never be blocked by a downstream fee-token transfer failure.

### Proof of Concept
1. Configure `EvmHost.feeToken()` to point at a mock ERC-20 that reverts transfers to a specific "blacklisted" address (simulating USDC's blacklist behavior).
2. Have `payer` (an address that will later be blacklisted) dispatch a `PostRequest` via `dispatch(DispatchPost)` with `post.payer = payer` and `post.fee > 0`; this records `_requestCommitments[commitment] = FeeMetadata({sender: payer, fee: fee})`.
3. Let the request time out without delivery, and mark `payer` as blacklisted on the mock fee token.
4. Call `EvmHost.dispatchTimeOut(PostRequestTimeout, meta, commitment)` from the `handler` — observe that `onPostRequestTimeout` succeeds (app-level refund/mint would occur) but the subsequent `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` reverts, reverting the whole transaction.
5. Confirm `_requestCommitments[commitment]` is unchanged and re-submitting the identical timeout proof reverts identically every time — the app-level refund for `payer` can never be completed, demonstrating permanent freezing of funds/blocked message delivery for that commitment.     function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
        emit PostRequestEvent({
            source: string(request.source),
            dest: string(request.dest),
            from: _msgSender(),
            to: abi.encodePacked(request.to),
            nonce: request.nonce,
            timeoutTimestamp: request.timeoutTimestamp,
            body: request.body,
            fee: post.fee
        });
    }
