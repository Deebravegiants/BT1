### Title
Webhook shop-domain identity used for handler dispatch is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the handler as trusted tenant identity, without that header ever being part of the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . `Registry.process` does: `raise ... unless Utils::HmacValidator.validate(request)`, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and passes it to the app's registered handler [3](#0-2) . `request.shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [4](#0-3) , which is never included in `to_signable_string` and therefore never checked by the HMAC.

The binding that should hold is: `shop_used_for_dispatch == shop_that_the_HMAC_was_computed_for`. Because the app's `client_secret` (and thus HMAC key) is shared across every shop that has installed the app, any shop that legitimately installs the app receives genuine, correctly-signed webhooks for its own body content. That same shop-owner (an unprivileged internet user with respect to *other* merchants' tenants) can replay that valid `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` (it only ever looks at the body), and `Registry.process` forwards the attacker-chosen `shop` string to the handler as `WebhookMetadata#shop`. Any host application that uses this field to select which merchant's record to update (the intended and documented use of `WebhookMetadata`) can be tricked into applying the attacker's webhook body under a victim shop's identity — a cross-tenant data-integrity/dispatch bypass rooted entirely in this gem's webhook verification not covering the identity field it hands back to the caller.

### Impact Explanation
This breaks the shop-authentication boundary the gem is supposed to provide for webhook processing: the "trusted, verified" `shop` value returned to the handler is not actually bound to the cryptographic proof of authenticity. This maps to the Critical "cross-tenant access" category — an app relying on `ShopifyAPI::Webhooks::Registry.process` + `WebhookMetadata#shop` to route/persist per-merchant webhook data can have one tenant's attacker-controlled request processed under another tenant's identity, without needing the victim's or the app's `client_secret`, access token, or any privileged credential.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must be (or control) at least one shop that has legitimately installed the target app, so they can obtain a validly-signed webhook body/HMAC pair to replay. That is a low bar — installing a free/dev copy of a target Shopify app is something any unprivileged internet user can do. No knowledge of `api_secret_key` or any access token is required; only header manipulation on the replayed HTTP request. Whether this is actually exploitable end-to-end also depends on host-application code trusting `WebhookMetadata#shop` for tenant selection, which is the documented and expected usage pattern of this API.

### Recommendation
Include the shop-domain (and ideally the topic/webhook-id) in the HMAC-signed material, or require callers to cross-check `request.shop` against an independently trusted shop→session mapping (e.g., verify the shop is a known, installed shop before dispatching) rather than trusting the header value implicitly once the body HMAC passes. At minimum, document explicitly and loudly that `Webhooks::Request#shop` is unauthenticated and must not be used as a tenant-selection key without additional verification.

### Proof of Concept
1. App AppX has a single `client_secret` shared by all installers.
2. Attacker installs AppX for their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, and a valid `x-shopify-hmac-sha256` computed over `B` with AppX's `client_secret` (per `Webhooks::Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`).
3. Attacker resends the exact same body `B` and HMAC header to AppX's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over `B` only (`lib/shopify_api/utils/hmac_validator.rb:26-31`) — it matches, so `Registry.process` does not raise `InvalidWebhookError` (`lib/shopify_api/webhooks/registry.rb:190`).
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler, which processes attacker-controlled webhook content `B` under the victim's tenant identity.
