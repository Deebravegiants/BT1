Confirmed: `Request#to_signable_string` returns only `@raw_body` (the JSON body), while `topic`, `shop`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to that body or to each other.This confirms the vulnerability: the gem's documented usage pattern explicitly instructs handlers to key business logic (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) off of `data.shop`, `data.topic`, and `data.webhook_id` — all of which come from `WebhookMetadata` built directly from unauthenticated headers in `Registry.process`.### Title
Webhook shop/topic/webhook_id headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request **body**. The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler are read directly from HTTP headers and are never included in the signed data. Because the same `api_secret_key` is shared across every shop that installs the app, an attacker who controls their own (legitimately installed) shop can capture one valid `(body, hmac)` pair from their own webhook deliveries and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header pointing at a victim shop. The HMAC check still passes because it only verifies the body bytes, letting the attacker make the app process attacker-controlled data as if it belonged to the victim tenant.

### Finding Description
`Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are parsed straight from headers with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header value — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC check, then builds `WebhookMetadata` straight from the unauthenticated headers and passes it to the app's handler: [4](#0-3) 

This breaks the identity-binding equality that should hold: `hmac_valid(body)` should imply `shop_header == source_of(body)`. Instead, `hmac_valid(body)` only proves the body bytes were HMAC'd with `api_secret_key` at some point — it says nothing about which shop, topic, or webhook the header values claim. Since `api_secret_key` is a single, app-wide secret (not per-shop), any shop that has installed the app can generate a validly-signed `(body, hmac)` pair for itself and then present that exact pair to the app's webhook endpoint with arbitrary header claims about `shop`/`topic`/`webhook_id`.

The gem's own documentation instructs developers to key multi-tenant logic directly off these unauthenticated fields: [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity confusion vulnerability: an attacker who is a legitimate (even free/trial) merchant of the app can trick the app into attributing attacker-supplied webhook body data to a different tenant (the `shop` field), because the HMAC only authenticates "this body byte string came from someone who knows `api_secret_key`" and not "this body belongs to shop X" or "this is topic Y" or "this is webhook Z (not a replay)". Any downstream logic in a host application that uses `data.shop` to select which tenant's session/config/data to read or mutate — exactly the pattern the gem's own docs recommend (`shop_domain: data.shop`) — can be made to act on/for the wrong shop. This matches the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Likelihood is high for any consumer of this gem: no access token, `api_secret_key`, or privileged access is required — only the ability to install the app on one's own shop (a normal, unprivileged action) to obtain a valid `(body, hmac)` pair, and the ability to send an arbitrary HTTP request to the app's public webhook endpoint. The header/body decoupling is baked into `Request`/`HmacValidator`/`Registry.process`, so every consumer of the standard `Registry.process` flow inherits this gap unless they add out-of-band shop/topic verification themselves (which the gem does not do or document as required).

### Recommendation
Bind the identity-relevant headers into the HMAC-verified data, or otherwise force apps to independently verify that the `shop`/`topic`/`webhook_id` values are consistent with a shop the app actually installed and expects, e.g.:
- Include `shop`, `topic`, and `webhook_id` in the string that is HMAC-validated (this would require a change in Shopify's webhook signing scheme, so in the gem this may instead mean requiring/validating that `request.shop` corresponds to a known installed session before dispatching to the handler), and/or
- Track delivered `webhook_id`s and reject reused/replayed ids, and
- Explicitly document that host applications must cross-check `data.shop` against their own installed-shop record before trusting it, since the HMAC does not protect that field.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery for topic `orders/create` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker replays this exact HTTP request to the app's webhook endpoint, but modifies the header `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally `X-Shopify-Webhook-Id` to a fresh value to bypass dedupe).
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` from the (unverified) header, while `to_signable_string` still returns body `B`.
4. `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it matches `H`, since `api_secret_key` is the same secret for all shops of this app — validation passes. [4](#0-3) 
5. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: ..., body: B, ...)`, and any host-application logic that trusts `data.shop` (as the gem's docs recommend) now processes attacker-controlled body `B` as if it belonged to the victim shop.
