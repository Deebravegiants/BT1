Audit Report

## Title
Stale LDAP-cached role/session survives permission revocation - ([File: core/sessions/ldapauth/ldap.go])

## Summary
When `WebServer.AuthenticationMethod = 'ldap'`, `AuthenticateBySession` calls `AuthorizedUserWithSession` on every request, and for the LDAP provider this reads the user's role solely from the local `ldap_sessions` cache table without ever re-querying the upstream directory. Revalidation against upstream only happens via `LDAPServerStateSyncer`, which under the shipped default `UpstreamSyncInterval = '0s'` runs `Work(ctx)` exactly once at process startup and never again, so a revoked/demoted LDAP user's cached role and session remain valid indefinitely until node restart.

## Finding Description
`AuthenticateBySession` (`core/web/auth/auth.go:55-71`) invokes `authr.AuthorizedUserWithSession(ctx, sessionID)` on the request path. [1](#0-0) 

For the LDAP provider, `AuthorizedUserWithSession` performs `SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1` and returns the cached `user_role` with no upstream LDAP call. [2](#0-1) 

Cache refresh is delegated entirely to `LDAPServerStateSyncer.Work()`, which re-queries LDAP groups and updates/purges `ldap_sessions` / `ldap_user_api_tokens` rows accordingly. [3](#0-2) 

`Start()` only schedules a recurring ticker when `UpstreamSyncInterval` is non-zero (`IsInstant()` false); otherwise it calls `Work(ctx)` a single time at startup, with no further periodic re-check. [4](#0-3) 

The default config value for `UpstreamSyncInterval` is documented as `'0s'`, which the code comment explicitly states "disables the background sync being run on an interval." [5](#0-4) 

`RequiresAdminRole` and related role wrappers trust whatever role was attached to the session context by `AuthenticateBySession`/`AuthorizedUserWithSession`, so they provide no additional freshness check. [6](#0-5) 

## Impact Explanation
If an operator revokes or downgrades an LDAP user's group membership (or deactivates the account) while that user holds a live session cookie or `ldap_user_api_tokens` API token, the node continues honoring the stale cached role (potentially Admin) for that user for the remainder of the node's uptime, since there is no per-request re-validation against the directory and no recurring background sync under the default configuration. This is a real access-control/role-bypass persistence issue: the node's authorization state diverges from the intended source of truth (the LDAP directory), enabling continued privileged actions (bridge management, job runs, key management) by a de-provisioned identity purely by replaying an already-issued credential — no new privilege escalation is required, but a security boundary (revocation) is not enforced.

## Likelihood Explanation
Requires `WebServer.AuthenticationMethod = 'ldap'` to be configured. Once configured, the described condition is the out-of-the-box behavior because `UpstreamSyncInterval` defaults to `'0s'`, so an operator must proactively set a non-zero interval for timely revocation to take effect. This is a realistic offboarding scenario (an admin removes a user from a privileged group while that user has an active session), and the exposure window is unbounded absent a node restart or explicit interval configuration.

## Recommendation
Re-validate the cached role/active-status against the upstream directory (or enforce a bounded, non-zero default `UpstreamSyncInterval`) rather than allowing indefinite caching under `'0s'`. Consider immediate session/token invalidation on-demand (e.g., an admin "force resync" action) in addition to, or instead of, relying solely on a background ticker with a zero-disables-forever default.

## Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'ldap'` with `WebServer.LDAP.UpstreamSyncInterval` left at default `'0s'`.
2. `alice`, a member of the LDAP `NodeAdmins` group, logs in via `/sessions`, creating an `ldap_sessions` row with `user_role = 'admin'` (`core/sessions/ldapauth/ldap.go:396-457`).
3. Operator removes `alice` from `NodeAdmins` upstream without restarting the chainlink node.
4. `alice` continues issuing requests with her existing session cookie; `AuthenticateBySession` → `AuthorizedUserWithSession` returns the stale cached `admin` role, and `RequiresAdminRole` grants admin-level actions.
5. Access persists until the node process restarts (triggering the one-time startup `Work()` call) or an operator sets a non-zero `UpstreamSyncInterval`.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field. The state of the upstream LDAP server
// is polled and synced at the defined interval via a SleeperTask
func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

func (l *LDAPServerStateSyncer) Work(ctx context.Context) {
	// Purge expired ldap_sessions and ldap_user_api_tokens
	recordCreationStaleThreshold := l.config.SessionTimeout().Before(time.Now())
	err := l.deleteStaleSessions(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire local LDAP sessions: ", err)
	}
	recordCreationStaleThreshold = l.config.UserAPITokenDuration().Before(time.Now())
	err = l.deleteStaleAPITokens(ctx, recordCreationStaleThreshold)
	if err != nil {
		l.lggr.Error("unable to expire user API tokens: ", err)
	}

	// Optional rate limiting check to limit the amount of upstream LDAP server queries performed
	if !l.config.UpstreamSyncRateLimit().IsInstant() {
		if !time.Now().After(l.nextSyncTime) {
			return
		}

		// Enough time has elapsed to sync again, store the time for when next sync is allowed and begin sync
		l.nextSyncTime = time.Now().Add(l.config.UpstreamSyncRateLimit().Duration())
	}

	l.lggr.Info("Begin Upstream LDAP provider state sync after checking time against config UpstreamSyncInterval and UpstreamSyncRateLimit")
