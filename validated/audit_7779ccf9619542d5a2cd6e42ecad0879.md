Audit Report

## Title
Weight-exhausted XCMP page processing silently drops legitimate inbound HRMP messages without retry - (cumulus/pallets/xcmp-queue/src/lib.rs, cumulus/pallets/parachain-system/src/lib.rs)

## Summary
`Pallet::handle_xcmp_messages` uses a single shared `WeightMeter` across every sender's inbound HRMP page processed in one relay-parent inherent call, and once it is exhausted, subsequent senders' pages are dropped via `continue`/`break` with only a `defensive!` log [1](#0-0) [2](#0-1) [3](#0-2) . Separately, `HrmpWatermark` is advanced based purely on message metadata computed *before* `handle_xcmp_messages` is invoked, independent of whether the handler actually enqueued the messages [4](#0-3) [5](#0-4) . Since the relay chain's `prune_hrmp` unconditionally removes `HrmpChannelContents` up to the submitted watermark [6](#0-5) , dropped messages cannot be resent.

## Finding Description
The code matches the claim precisely: `handle_xcmp_messages` creates one `WeightMeter::with_limit(max_weight)` for the entire call and iterates over all `(sender, sent_at, data)` tuples [7](#0-6) . For each sender's first batch, `try_consume(T::WeightInfo::uncached_enqueue_xcmp_messages())` is checked against the *shared* meter; once that meter is exhausted (from processing an earlier sender's large page), this check fails for every subsequent sender and their entire page is dropped via `continue`, logging only `defensive!("Out of weight: cannot enqueue XCMP messages; dropping page...")` [2](#0-1) . Mid-page decode failures due to weight exhaustion inside `take_first_concatenated_xcms`/`enqueue_xcmp_messages` similarly cause `can_process_next_batch = false` and `break`, dropping the remainder of that page with only a `defensive!("HRMP inbound decode stream broke; page will be dropped.")` [8](#0-7) .

Independently, `enqueue_inbound_horizontal_messages` computes `last_processed_block` from the `sent_at` metadata of the messages included in the inherent (an ordering/inclusion check unrelated to weight-metered processing success), and then unconditionally writes `HrmpWatermark::<T>::put(last_processed_block)` after calling `handle_xcmp_messages`, discarding only the weight return value [9](#0-8) . The relay chain's `hrmp::Pallet::prune_hrmp` then removes `HrmpChannelContents` up to the reported watermark unconditionally, with no feedback loop checking whether the parachain actually processed those messages [10](#0-9) . Sender ordering (`(sent_at, sender ParaId)` ascending) is confirmed in `InboundHrmpMessages::from_map` [11](#0-10) , so a lower-ParaId sender is processed first in the shared meter.

No suspension (`InboundXcmpSuspended`) is triggered on this drop path — `on_queue_changed` is only called from a *successful* `enqueue_messages`/`T::XcmpQueue` enqueue path (see `OnQueueChanged` impl and `on_queue_changed` logic that only reacts to queue footprint changes) [12](#0-11) , so this backpressure mechanism does not fire for messages that are dropped before being enqueued.

## Impact Explanation
The described mechanism is real and directly supported by the code: a single, whole-call `WeightMeter` shared across all senders' pages, combined with a watermark that is advanced regardless of processing success, and a relay-chain pruning step that is unconditional on the submitted watermark. This is a legitimate design flaw that can cause silent, permanent loss of legitimate inbound XCM messages (including asset-transfer XCMs) from a victim parachain sharing the same relay-parent block, with the sender receiving no failure signal, no channel suspension, and no possibility of relay-chain-level retransmission.

## Likelihood Explanation
Exploitation requires: (1) an open HRMP channel between attacker and this parachain, (2) a numerically lower `ParaId` than the intended victim so the attacker's page is processed first by the shared meter, and (3) sufficient channel capacity to submit a page large enough to exhaust `ReservedXcmpWeight` in a single relay block. All three conditions are governance/protocol-legal and reachable by any registered parachain with an open channel — no privileged origin is required, and the drop path is explicitly (if only partially) acknowledged in the code via the `defensive!` messages. This makes the issue realistically triggerable, though the exact weight/capacity thresholds needed (dependent on `ReservedXcmpWeight` and per-channel `max_capacity`/`max_total_size` values, which vary per-runtime and are governance-configured) were not independently confirmed as always sufficient in this review — this is an unprivileged-user-reachable design gap in the shared codebase rather than a runtime-specific misconfiguration.

## Recommendation
- Do not advance `HrmpWatermark` past messages that `handle_xcmp_messages` failed to fully process due to weight exhaustion; either fail the block/inherent or persist residual undecoded bytes for retry on a subsequent block instead of allowing relay-chain pruning to proceed past them.
- Account weight per-sender (or fairly partition the shared budget, e.g., round-robin/pro-rata) rather than using a single cumulative meter across the whole `iter`, so an earlier sender's oversized page cannot cannibalize the weight budget available to later senders in the same call.
- When a page is dropped due to meter exhaustion or `can_process_next_batch = false`, trigger inbound channel suspension/backpressure signaling analogous to `InboundXcmpSuspended`, so the affected channel is not silently starved.

## Proof of Concept
Rust unit test in `cumulus/pallets/xcmp-queue/src/tests.rs`:
1. Configure a small `ReservedXcmpWeight`/mock `WeightMeter` limit.
2. Build an `iter` yielding two senders' pages in ascending `ParaId` order: sender A (`ParaId=1`, attacker) with a page containing enough small XCM messages to consume nearly all of `max_weight`; sender B (`ParaId=2`, victim) with a single legitimate XCM message.
3. Call `Pallet::<Test>::handle_xcmp_messages(iter, max_weight)`.
4. Assert sender B's message never appears in `T::XcmpQueue`'s enqueued messages (mock `EnqueuedMessages` storage), demonstrating the silent drop.
5. Assert `InboundXcmpSuspended` does not contain sender B, confirming no backpressure/retry signal was triggered for the dropped message.

	pub(crate) fn prune_hrmp(recipient: ParaId, new_hrmp_watermark: BlockNumberFor<T>) {
		// sift through the incoming messages digest to collect the paras that sent at least one
		// message to this parachain between the old and new watermarks.
		let senders = HrmpChannelDigests::<T>::mutate(&recipient, |digest| {
			let mut senders = BTreeSet::new();
			let mut leftover = Vec::with_capacity(digest.len());
			for (block_no, paras_sent_msg) in mem::replace(digest, Vec::new()) {
				if block_no <= new_hrmp_watermark {
					senders.extend(paras_sent_msg);
				} else {
					leftover.push((block_no, paras_sent_msg));
				}
			}
			*digest = leftover;
			senders
		});

		// having all senders we can trivially find out the channels which we need to prune.
		let channels_to_prune =
			senders.into_iter().map(|sender| HrmpChannelId { sender, recipient });
		for channel_id in channels_to_prune {
			// prune each channel up to the new watermark keeping track how many messages we removed
			// and what is the total byte size of them.
			let (mut pruned_cnt, mut pruned_size) = (0, 0);

			let contents = HrmpChannelContents::<T>::get(&channel_id);
			let mut leftover = Vec::with_capacity(contents.len());
			for msg in contents {
				if msg.sent_at <= new_hrmp_watermark {
					pruned_cnt += 1;
					pruned_size += msg.data.len();
				} else {
					leftover.push(msg);
				}
			}
			if !leftover.is_empty() {
				HrmpChannelContents::<T>::insert(&channel_id, leftover);
			} else {
				HrmpChannelContents::<T>::remove(&channel_id);
			}

			// update the channel metadata.
			HrmpChannels::<T>::mutate(&channel_id, |channel| {
				if let Some(ref mut channel) = channel {
					channel.msg_count -= pruned_cnt as u32;
					channel.total_size -= pruned_size as u32;
				}
			});
		}

		HrmpWatermarks::<T>::insert(&recipient, new_hrmp_watermark);

impl InboundHrmpMessages {
	// Prepare horizontal messages for a more convenient processing:
	//
	// Instead of a mapping from a para to a list of inbound HRMP messages, we will have a
	// list of tuples `(sender, message)` first ordered by `sent_at` (the relay chain block
	// number in which the message hit the relay-chain) and second ordered by para id
	// ascending.
	pub fn from_map(messages_map: BTreeMap<ParaId, Vec<InboundHrmpMessage>>) -> Self {
		let mut messages = messages_map
			.into_iter()
			.flat_map(|(sender, channel_contents)| {
				channel_contents.into_iter().map(move |message| (sender, message))
			})
			.collect::<Vec<_>>();
		messages.sort_by(|(sender_a, msg_a), (sender_b, msg_b)| {
			// first sort by sent-at and then by the para id
			(msg_a.sent_at, sender_a).cmp(&(msg_b.sent_at, sender_b))
		});

		Self { messages }
	}
