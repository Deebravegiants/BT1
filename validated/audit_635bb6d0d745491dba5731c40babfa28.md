### Title
Tron IntentGatewayV2 escrows nominal (pre-fee) input amounts instead of actually-received amounts, causing insolvent escrow accounting with fee-on-transfer tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` on the Tron contract escrows tokens by calling `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally increments `_orders[commitment][token] += reducedInputs[i].amount` using the nominal order amount (minus protocol fee) — never checking the contract's actual token balance before/after the transfer. For a fee-on-transfer (deflationary) ERC20, the amount received by the contract is strictly less than `order.inputs[i].amount`, so the internal escrow ledger `_orders[commitment][token]` is inflated above the tokens the contract actually holds.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract transfers `order.inputs[i].amount` via `safeTransferFrom` but never measures `balanceOf(address(this))` before and after the transfer. It then credits `_orders[commitment][token]` with `reducedInputs[i].amount`, which is derived from the nominal `order.inputs[i].amount` reduced only by the protocol fee basis points, computed earlier here: [2](#0-1) 
This is the exact bug class from the referenced Allo.sol report: crediting internal accounting with the pre-transfer amount rather than the actual amount received, which is inaccurate for fee-on-transfer/deflationary tokens.

Notably, the sibling EVM implementation of the same contract already fixes this exact issue by snapshotting balances before/after the transfer and mutating `order.inputs[i].amount` to the actually-received delta: [3](#0-2) 
and this fix is explicitly covered by dedicated fee-on-transfer tests: [4](#0-3) 
The Tron variant lacks this fix entirely — it never adjusts `order.inputs`/`reducedInputs` to reflect the real balance delta, so the escrow ledger silently accrues phantom balance whenever a fee-on-transfer token (or any token with non-1:1 transfer semantics, e.g. rebasing/deflationary tokens) is used as an input.

### Impact Explanation
Because `_orders[commitment][token]` is the sole ledger used by `_withdraw`/redeem-escrow/refund flows to pay out beneficiaries or solvers, an inflated ledger entry means the contract promises more tokens than it physically holds for that token. As multiple orders using the same fee-on-transfer token accumulate phantom escrow, eventually a `_withdraw` call for one order can drain real balances that were meant to back a different, unrelated order's escrow — resulting in some legitimate withdrawals reverting (frozen/undeliverable funds) or, in a race, allowing an earlier claimant to receive tokens that rightfully belonged to a later order. This is a direct accounting-insolvency / fund-freezing vulnerability reachable from a single unprivileged `placeOrder` transaction using an unprivileged, permissionlessly listable ERC20 as the input token.

### Likelihood Explanation
`placeOrder` is a fully permissionless, unprivileged entry point — any user can submit an order specifying any ERC20 token address as an input, including a fee-on-transfer/deflationary token. No governance or admin action is required to trigger the mismatch; it happens automatically and silently on every such order.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom` in the non-predispatch path, mutate `order.inputs[i].amount` (and thus `reducedInputs`) to the actual received delta, and compute `commitment`/escrow crediting from that real amount rather than the nominal user-supplied amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee, as modeled by `FeeOnTransferToken` in the test suite) and mint balance to a user.
2. User calls `placeOrder` on `evm/tron/contracts/apps/IntentGatewayV2.sol` with `inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. `safeTransferFrom(user, address(this), 1000e18)` executes; the contract actually receives only `990e18` (1% burned/fee), verifiable via `FOT.balanceOf(address(this))`.
4. Despite this, `_orders[commitment][token]` is credited with `reducedInputs[0].amount` derived from the full `1000e18` (minus only the protocol fee), i.e., roughly `1000e18 - protocolFee`, which exceeds the `990e18` actually held.
5. Repeating this with multiple orders accumulates a ledger balance permanently greater than `FOT.balanceOf(address(this))`; when withdrawals/redemptions are processed via `_withdraw`, later legitimate claims can fail (`ERC20: transfer amount exceeds balance`) or drain funds belonging to other orders, demonstrating both freezing and cross-order fund-loss potential.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
