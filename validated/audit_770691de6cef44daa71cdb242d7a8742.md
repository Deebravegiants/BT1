### Title
Webhook `shop` identity derived from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature only over the raw request body, but exposes `shop` (the tenant identifier the host application uses to route/attribute the webhook) from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed bytes. This breaks the binding "bytes verified == bytes used to identify the tenant."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#hmac` reads the signature from the `hmac-sha256` header and is checked against that same `@raw_body` via `HmacValidator.validate`/`validate_signature`, which computes `OpenSSL::HMAC.hexdigest` over `to_signable_string` and compares with `OpenSSL.secure_compare`: [2](#0-1) 

However, `Request#shop` — the value a host application uses to identify which merchant/tenant the webhook belongs to — is read directly from the `shopify-shop-domain` header, a field that is completely outside the HMAC-covered payload: [3](#0-2) 

The identity equality that should hold is: `bytes verified by HMAC == bytes used to determine tenant (shop)`. Here it does not: the signature only binds `@raw_body`, while `shop` is taken from a header. `Request#initialize` only checks for the *presence* of the required headers, not their integrity: [4](#0-3) 

Because HTTP headers are fully attacker-controlled at the transport layer (unlike the signed body, which Shopify computes on the real payload), any party able to submit or replay a validly-signed webhook body (e.g., a body that was legitimately signed for shop A, replayed with a forged `shopify-shop-domain: shop-b.myshopify.com` header) can cause the host application to attribute the webhook payload to a different tenant than the one Shopify actually generated it for — while `HmacValidator.validate` still reports success, since it only checks the body bytes.

### Impact Explanation
This crosses a tenant boundary: an app relying on `Webhooks::Request#shop` after a successful `HmacValidator.validate` check (the gem's documented pattern) to select the tenant's session/data would process (or misattribute) data under the wrong shop, i.e., cross-tenant access/confusion, without needing the app's `client_secret` or any privileged credential — only the ability to influence request headers. This matches the Critical "cross-tenant access" impact category since the identity binding (signed bytes ⇒ trusted shop) that the library is supposed to provide is violated.

### Likelihood Explanation
Exploitation requires the host application's request-handling stack to accept attacker-influenced headers for the `shopify-shop-domain` field reaching this gem's `Request#shop`, or a scenario allowing body replay (e.g., a proxy/CDN configuration that does not lock headers to the verified sender, or an endpoint that can be reached with attacker-supplied headers alongside a legitimately-signed body). This is dependent on deployment/proxy specifics of the host app rather than a pure library-only exploit, so likelihood is moderate rather than trivial, but the root cause — the HMAC in this library never protects the header-derived `shop` value — is a concrete gap in the gem's own code.

### Recommendation
Do not derive the tenant identifier from an unsigned header field. Either:
- Include the `shop-domain` (and `topic`, `webhook-id`) header values in the signed/verified payload used for `to_signable_string`, or
- Document/enforce that `Request#shop` must never be trusted unless the deployment guarantees header integrity (e.g., only trust `shop` when it can be independently cross-checked against a signed claim), and provide a built-in check in `Registry`/`WebhookHandler` dispatch that rejects mismatches between any signed tenant claim and the header-derived `shop`.

### Proof of Concept
1. Attacker captures or is otherwise able to submit a raw webhook body `B` together with its correct `hmac-sha256` signature `H` for shop A (any legitimately signed webhook payload works, since only the body is signed).
2. Attacker sends a POST to the host application's webhook endpoint with body `B`, header `hmac-sha256: H`, and header `shopify-shop-domain: shop-b.myshopify.com` (spoofed).
3. Host app calls `ShopifyAPI::Utils::HmacValidator.validate(request)` — this passes, because it only checks `B` against `H`: [5](#0-4) 
4. Host app then calls `request.shop` to select/authorize the tenant context, receiving the attacker-controlled `shop-b.myshopify.com` instead of the shop the payload was actually generated for: [3](#0-2) 
5. The webhook payload (from shop A) is now processed under shop B's tenant context — a cross-tenant data confusion enabled purely by the library's failure to bind `shop` to the HMAC-verified bytes.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
