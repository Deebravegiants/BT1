## Title
Excess native-token payment in `EvmHost.dispatch()`/`fundRequest()` is silently absorbed by the host instead of refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native-token payment and forward the *entire* `msg.value` into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`, but never capture or use the router's return value to refund the unspent portion to the original caller. This is the same root-cause pattern as the `receiveTokenOrETH` bug in the referenced report: `msg.value` can legitimately exceed the amount actually needed (`post.fee` / `get.fee` / `amount`), and the difference is not returned to the sender, only internal accounting (`FeeMetadata.fee`) tracks the intended fee, not the actual `msg.value` received.

### Finding Description
In `EvmHost.sol`: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
```

The same pattern is repeated for `dispatch(DispatchGet)` [2](#0-1)  and `fundRequest()` [3](#0-2) .

Standard `UniswapV2Router02.swapETHForExactTokens` computes the exact input required for the requested output (`post.fee`), swaps that amount, and refunds any unspent ETH (`msg.value - amounts[0]`) to `msg.sender` of the *router call*. Because `EvmHost` itself is the caller of the router (not the original dispatcher/relayer), any refund from the router lands back in `EvmHost`'s own balance, not the account that funded the transaction. `EvmHost` never records or reads this excess amount — the return value of `swapETHForExactTokens` (an `amounts` array with the actual ETH spent) is discarded entirely, unlike the fixed pattern used elsewhere in this same codebase.

By contrast, the sibling `IntentGatewayV2.placeOrder` explicitly captures the swap's spent amount and refunds the difference to the caller: [4](#0-3) 

```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```

`EvmHost.dispatch`/`fundRequest` have no equivalent refund step, and a `grep` of `EvmHost.sol` shows no `receive()`, `fallback()`, or native-token `withdraw` function exists on the host to later reclaim any ETH that accumulates there. Any wei sent by an app/user/relayer above the exact quoted fee for a POST/GET dispatch, or above the exact top-up amount in `fundRequest`, is either (a) permanently stranded in `EvmHost`'s balance with no accounting path back to the payer, since `_requestCommitments[commitment].fee` only tracks `post.fee`/`get.fee`/`amount`, not `msg.value`; or (b) causes the whole transaction to revert if `EvmHost` cannot receive bare ETH transfers at all (no explicit `receive`/`fallback` found in this file).

### Impact Explanation
Every app built on Hyperbridge that dispatches messages by paying with native token (documented as a first-class payment path — see `docs/content/developers/evm/messaging/post-requests.mdx`) is exposed: any relayer, app contract, or end user who cannot perfectly predict the exact fee-token amount a given `msg.value` will convert to (due to AMM price movement between quote and execution, or simply passing round `msg.value` amounts) will overpay, and the surplus native token is not returned to them. This matches the Medium-severity classification of the referenced finding: loss of user/app funds resulting from an external factor (overpayment) rather than an internal accounting flaw exploitable without user cooperation.

### Likelihood Explanation
`dispatch()` and `fundRequest()` are the primary, unprivileged entry points for any app or relayer paying Hyperbridge dispatch/relayer fees in native token — reachable directly from a single transaction with no special permissions. Because native-token fee quoting depends on live AMM pricing (documented explicitly as "Automatically swapped to fee token via Uniswap"), slight overestimation of `msg.value` by callers is a normal, expected occurrence rather than an edge case, making this readily triggerable in production usage.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2._placeOrder` (`msgValue -= amounts[0]; ... _sendValue(msg.sender, msgValue);`).

### Proof of Concept
1. Query the current AMM price and compute `nativeIn` for `swapETHForExactTokens(post.fee, ...)`.
2. Call `EvmHost.dispatch{value: nativeIn + X}(post)` with `X > 0` extra wei (e.g., to buffer against price movement, a common and reasonable pattern).
3. Internally, `swapETHForExactTokens` consumes only `amounts[0] <= nativeIn + X` and refunds `X' = (nativeIn + X) - amounts[0]` to `EvmHost` (the router's `msg.sender`), not to the original caller.
4. `EvmHost` never forwards `X'` onward; `_requestCommitments[commitment]` only stores `post.fee`, with no reference to the surplus.
5. Repeat with `fundRequest()` for the same effect on relayer fee top-ups.

Result: `X'` wei accumulates in `EvmHost`'s balance across every overpaid dispatch/fundRequest call, with no function in `EvmHost.sol` to withdraw or return this native-token balance to affected callers.
