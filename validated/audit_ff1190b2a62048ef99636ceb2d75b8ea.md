### Title
Source-authorization bypass in Orb-Relay client message loop lets any relay peer trigger orb state replay - (File: orb-relay-client/src/client.rs)

### Summary
The WETH.sol bug allowed an attacker to bypass an authorization check (verifying the caller is the actual token owner) via an alternate code path (`approve(address owner, address spender)`) that skipped the `msg.sender` check entirely. The analogous pattern in `orb-core` is in the Orb-Relay client's incoming-message dispatch loop `PollerAgent::main_loop`, where the source-identity check that normally gates all incoming relay messages is explicitly bypassed for one special message type (`self_serve::app::v1::RequestState`), before the sender's identity is validated.

### Finding Description
In `orb-relay-client/src/client.rs`, `PollerAgent::main_loop` processes incoming relay payloads as follows: [1](#0-0) 

The normal authorization invariant for this trust boundary is: only messages whose `src.id` equals the configured pairing partner (`self.config.dst_id`) — i.e., the orb or app that this client is actually paired with for the current signup session — are accepted and routed to `handle_message`. This mirrors an "owner-must-match-caller" check, analogous to WETH's `approve(msg.sender, ...)` invariant.

However, the check is short-circuited: if the incoming payload matches `self_serve::app::v1::RequestState`, the code responds by resending `self.last_message` immediately, in an `if` branch evaluated *before* the `src.id != self.config.dst_id` check that gates every other message type:
```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source...");
} else {
    self.handle_message(...).await?;
}
```
This is structurally identical to the WETH bug class: an alternate, less-restrictive entry point exists that performs a sensitive action (replaying the last known signup/session state message) while skipping the identity/ownership check that all other paths enforce. Any relay-connected entity that can deliver a `RequestState` payload to this client — regardless of whether its `src.id` matches the paired `dst_id` — can force the orb (or app) to retransmit its last relay message (e.g. `SignupEnded`, `CaptureStarted`, `CaptureEnded`, `AgeVerificationRequiredFromOperator`) on demand.

### Impact Explanation
`self.last_message` can carry self-serve signup lifecycle state (`self_serve::orb::v1::SignupEnded`, `CaptureStarted`, `CaptureEnded`, `AgeVerificationRequiredFromOperator`, etc., see `orb-relay-client/src/lib.rs`). Because the `RequestState` branch bypasses the source-identity check, this creates a cross-signup state bleed / unauthorized state-disclosure primitive at the agent-IPC trust boundary between the Orb-Relay client and its peer: an unauthorized entity that is not the legitimate paired app/orb for the current session can repeatedly force replay of session-lifecycle state without being validated as the actual counterpart, undermining the `src.id == dst_id` invariant that the rest of the loop relies on to isolate one signup session's messages from another. While this does not directly forge biometric data or a secure-element signature, it breaks the intended trust boundary designed to keep session state confined to the paired participant, which is the closest unprivileged-user-reachable analog to the WETH `approve(owner, spender)` root cause (an alternate code path that skips the caller/owner identity check).

### Likelihood Explanation
Exploitability depends on whether the underlying Orb-Relay transport/auth layer (`ConnectRequest`/`AuthMethod`, token or ZKP auth) prevents an unauthorized third party from delivering a payload that reaches this client's `response_stream` with an arbitrary `src.id`. The code within `orb-core`'s own client only enforces this identity match for non-`RequestState` messages, and the bypass is unconditional in `main_loop` for any decoded `RequestState` payload — the exploit only requires the ability to have the relay server forward a `RequestState`-shaped message to this stream, which is a reachable, unprivileged-user path in the self-serve signup flow (app-to-orb communication is inherently attacker-influenceable since the "app" side is an ordinary user device). The full server-side routing/authorization enforcement of the relay backend is outside `orb-core` and could not be verified from this repository alone, so likelihood is assessed as Medium pending that boundary.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` special case so that source validation is uniformly enforced for all message types, including `RequestState`:
```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}: {payload:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else {
    self.handle_message(...).await?;
}
```
This removes the alternate, unauthenticated path — mirroring the WETH fix of removing the extra `approve(owner, spender)` function and requiring all authorization to flow through the single, correctly-checked path.

### Proof of Concept
1. Attacker (or malicious relay peer) with any valid relay connection crafts an `Any` payload matching `self_serve::app::v1::W::RequestState` (per `PayloadMatcher` impl in `orb-relay-client/src/lib.rs`) and sets `src.id` to a value different from the target client's configured `dst_id`. [2](#0-1) 
2. This payload is delivered as a `RelayConnectResponse::Payload` to the target's `main_loop`.
3. Because `self_serve::app::v1::RequestState::matches(&payload).is_some()` is checked first, the `src.id != self.config.dst_id` branch is never evaluated for this message, and the client immediately calls `sender_tx.send(self.last_message.clone())`, disclosing/replaying the last signup-lifecycle message regardless of the sender's true identity. [3](#0-2)
