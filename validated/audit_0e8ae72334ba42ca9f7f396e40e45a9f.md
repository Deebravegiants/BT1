### Title
Source-chain order cancellation dispatches a permanently non-timeoutable GET request, permanently freezing escrowed funds - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents._cancelFromSource` (the source-chain leg of `IntentGatewayV2.cancelOrder`) dispatches a Hyperbridge `DispatchGet` with `timeout: 0` to verify on the destination chain that an expired order was never filled, before refunding the escrowed input tokens. A `timeout` of `0` means the message can **never** expire/time out, by design of the ISMP dispatcher. Since the contract provides no `onGetTimeout` override and the GET request itself is unkillable (no timeout, no cancellation API), if the `onGetResponse` callback never fires — because the destination state proof cannot be produced/verified, the destination consensus client is frozen, or any other liveness failure prevents relayers from ever delivering the response — the user has no way whatsoever to cancel the outstanding GET request. Both the escrowed order inputs and the relayer fee paid for this dispatch become permanently unrecoverable, mirroring the "no way to cancel l1->l2 message" bug class from the referenced report, but here the frozen asset is not just a fee — it is the entire order's escrowed principal.

### Finding Description
`_cancelFromSource` builds and dispatches the request like this: [1](#0-0) 

```solidity
bytes memory context =
    abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

bytes[] memory keys = new bytes[](1);
keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
DispatchGet memory request = DispatchGet({
    dest: order.destination,
    keys: keys,
    timeout: 0,
    height: options.height,
    fee: options.relayerFee,
    context: context,
    payer: msg.sender
});
```

The `timeout: 0` field is explicitly documented as "no timeout ... messages will never expire": [2](#0-1) 

and is enforced at the dispatcher level, where a zero timeout resolves to `timeout_timestamp = 0` regardless of elapsed time: [3](#0-2) 

The ISMP handler for GET timeouts requires the timeout to have actually elapsed before a timeout can be processed and the commitment deleted/refunded: [4](#0-3) 

Because `get_timeout(0)` resolves to `Duration::MAX`, this GET request can never satisfy `timed_out()`, so `handleGetRequestTimeouts`/`TimeoutMessage::Get` can never be invoked against it: [5](#0-4) 

The only resolution path implemented in the app is `onGetResponse`, which only fires on a successful response delivery: [6](#0-5) 

There is no `onGetTimeout` override in this contract and no alternate cancellation entrypoint for a GET request already in flight. If the response is never delivered — e.g. the destination `stateMachineCommitment` at `options.height` becomes unreachable, the destination state machine's consensus client is later frozen, the storage layout assumption in `_calculateCommitmentSlotHash` fails to verify, or relayers simply refuse/are unable to deliver the response — the request commitment (`_requestCommitments[commitment]` on the source `EvmHost`) sits forever, the escrowed `order.inputs` remain locked in the gateway (never released via `_withdraw`), and the `options.relayerFee` paid to dispatch the GET is permanently unrecoverable since a GET request has no relayer-fee refund path outside of timeout handling anyway.

### Impact Explanation
This goes beyond the "loss of fees" characterization in the referenced report: the escrowed order principal (`order.inputs`), not merely the relayer fee, becomes permanently frozen with no recovery mechanism once `_cancelFromSource` is invoked and the destination fails to answer. This is a direct instance of "permanent freezing of funds" from a single unprivileged transaction (`cancelOrder` routed through `_cancelFromSource`), which the validation rules explicitly treat as in-scope Medium-or-higher impact.

### Likelihood Explanation
`_cancelFromSource` is reachable by any order creator after their order's deadline passes, and is the recommended/only source-side recovery path when the destination-side cancel route is unavailable or undesired (per SDK docs describing "Choose the source route only after expiry"). Any liveness disruption on the destination state machine (consensus client update lag/freeze, challenge-period stalls, indexer/relayer downtime, or a future storage-layout mismatch making the proof unverifiable) after the GET is dispatched is sufficient to trigger permanent lock, with no admin or user-level override to force resolution.

### Recommendation
Do not hardcode `timeout: 0` for the source-cancellation GET request. Set a bounded `timeout` (mirroring `CancelOptions` or a configurable parameter) so that, if the destination response never lands, the request can be timed out via `handleGetRequestTimeouts`, and implement `onGetTimeout` in `ExtrinsicIntents` (and the corresponding Tron `IntentGatewayV2.sol`) to refund the escrowed `order.inputs` back to `order.user` (and/or the relayer fee to `msg.sender`), consistent with how POST-request timeouts are already handled elsewhere in the protocol (e.g. `HyperFungibleToken.on_timeout`, `WrappedHyperFungibleToken.onPostRequestTimeout`).

### Proof of Concept
1. User creates a cross-chain order via `IntentGatewayV2`/`ExtrinsicIntents`; order deadline passes without a fill.
2. User calls `cancelOrder` → `_cancelFromSource`, which dispatches a `DispatchGet` with `timeout: 0` and pays `options.relayerFee` plus locks `order.inputs` in escrow pending refund.
3. Simulate destination unavailability (e.g. the destination consensus client used by Hyperbridge stalls, or the height `options.height` state root can never be finalized/proved) so no relayer can ever submit a valid `handleGetResponses` call for this commitment.
4. Attempt to recover via `handleGetRequestTimeouts` — this reverts with `RequestTimeoutNotElapsed` forever because `timeout_timestamp == 0` resolves to `Duration::MAX` in `get_timeout`.
5. Observe: `order.inputs` remain permanently locked in the gateway's escrow, `options.relayerFee` is unrecoverable, and no function in `ExtrinsicIntents.sol` exists to cancel or otherwise resolve the outstanding GET commitment.

	/// Returns true if the host timestamp has exceeded the request timeout timestamp
	pub fn timed_out(&self, proof_timestamp: Duration) -> bool {
		proof_timestamp >= self.timeout()
	}
}

/// Get the timeout in seconds
fn get_timeout(timeout_timestamp: u64) -> Duration {
	// zero timeout means no timeout.
	if timeout_timestamp == 0 {
		Duration::from_secs(u64::MAX)
	} else {
		Duration::from_secs(timeout_timestamp)
	}
}
