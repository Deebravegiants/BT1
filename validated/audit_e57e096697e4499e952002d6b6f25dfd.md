Based on my investigation, I found a concrete identity-binding flaw in the webhook processing path.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`/`x-shopify-shop-domain` header verbatim when building the `WebhookMetadata` passed to the app's handler. Because the HMAC signable string is only the raw body, the `shop` field used by the handler is not bound to the signature that was actually verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id`, none of which participate in the signable string [2](#0-1) . The `shop` accessor is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) .

`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it against the received signature using `OpenSSL.secure_compare` [4](#0-3) . Since the `api_secret_key` is per-app (shared across every shop/merchant that has installed the app) and not per-shop, and the signature covers only the body, an attacker who legitimately controls one shop where the app is installed can:
1. Trigger a genuine webhook for their own shop (e.g. `orders/create`) and capture the raw body + valid `x-shopify-hmac-sha256` header Shopify sent.
2. Replay that exact body and HMAC to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (body+secret unchanged), and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: <victim-shop>` [5](#0-4) .

This breaks the intended identity binding: `shop authenticated by HMAC` should equal `shop the handler acts on`, but the gem only authenticates the body, not the shop header, and documents/hands the header value straight through to app code (see the recommended handler pattern in `docs/usage/webhooks.md`, which uses `data.shop` directly to look up/act on tenant records) [6](#0-5) . The test suite confirms the shop header is read but never validated against the signature - `test_process_hmac_validation_fails` only exercises HMAC-vs-body mismatch, never shop-header-vs-body binding [7](#0-6) .

### Impact Explanation
Any application built on this gem that uses `data.shop` from `WebhookMetadata` to key tenant-specific side effects (updating merchant records, uninstall flags, GDPR redaction routines for `shop/redact`/`customers/redact`, provisioning, etc.) is exposed to cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker does not control. This matches the "cross-tenant access" impact category, since a legitimate but low-privilege app-installer (any merchant who installs the app) can forge webhook events attributed to a different merchant/shop.

### Likelihood Explanation
Exploitation requires only that the attacker run their own Shopify store with the target app installed (a normal, unprivileged action any internet user can take by installing a public app) and be able to POST arbitrary headers to the app's public webhook endpoint - both trivially available capabilities, no `api_secret_key`, access token, or privileged access needed.

### Recommendation
Bind the `shop`, `topic`, `api_version`, and `webhook_id` fields into the HMAC signable string (or otherwise cryptographically bind them to the verified body), or require the host application to independently verify that the shop-domain header corresponds to a shop with an active webhook registration/session before trusting it. At minimum, document prominently that `data.shop` from `WebhookMetadata` is unauthenticated and must not be used to key privileged, tenant-scoped operations without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# Shopify sends a legitimate webhook:
raw_body = '{"id":1,"note":"hi"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker replays same body+hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) passes (body-only check)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# App code acting on `data.shop` now believes this event originated from "victim-shop.myshopify.com".
```
