## Finding

### Title
Webhook `shop-domain` and `topic` are trusted from unauthenticated HTTP headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's HMAC over the raw request body only, then trusts the `shop-domain` and `topic` fields taken straight from HTTP headers to route and attribute the payload — even though those fields are never covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` by returning only the raw JSON body from `to_signable_string`, and pulls `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers that are completely outside the HMAC: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC of the body and, once it passes, unconditionally forwards `request.shop` and `request.topic` (both header-derived, unsigned) to the app's webhook handler: [3](#0-2) 

The `api_secret_key` used to compute the HMAC is the **app's single secret**, shared across every shop that installs the app — it is not a per-shop or per-tenant secret. Consequently, the HMAC only proves "this body+signature pair was produced by someone holding the app's secret" (in practice, genuinely delivered by Shopify), but it says nothing about *which shop* the payload is for. The binding that should hold is:

`shop authenticated by the signed payload == shop the app attributes/acts on`

but the code actually checks:

`HMAC(raw_body, secret) valid == true` and then trusts `header["x-shopify-shop-domain"]` independently, with no cryptographic tie between the two.

### Impact Explanation
Any unprivileged internet user can install the target app for free on their own development/test store (a normal, unprivileged action). Shopify will deliver genuine, correctly-HMAC-signed webhooks to the app's endpoint for that attacker-owned shop. Because `shop-domain` (and `topic`) are not part of the signed content, the attacker can replay that captured, validly-signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) to name a victim shop. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will invoke the app's handler believing the event legitimately originates from the victim shop/topic. This is a cross-tenant data/state confusion: an app that keys internal actions (e.g., marking an order paid, revoking access on `app/uninstalled`, updating billing state, deleting merchant data on `shop/redact`) by `data.shop` can be manipulated into applying attacker-controlled data to another tenant's account.

### Likelihood Explanation
The only prerequisite is the ability to install the app once on an attacker-controlled shop (or to trigger any webhook Shopify already sends there) and replay the captured request with a modified header — no access to the `api_secret_key`, no credential theft, and no privileged account are required. This is directly reachable through the gem's own public `Webhooks::Registry.process` API exactly as documented.

### Recommendation
Do not trust `shop`/`topic`/`webhook_id` purely from headers for identity-sensitive decisions. At minimum:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) in the HMAC-signed payload verification (e.g., verify the HMAC in combination with these header values, not just the raw body), or
- Require applications to cross-check `request.shop` against a shop known to have received that specific webhook subscription/id via the Admin API prior to acting on it, and document this requirement prominently since `Registry.process` does not perform this check itself.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (free, unprivileged action).
2. Shopify delivers a legitimately signed webhook, e.g.:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: ...

{ "id": 1, "total_price": "0.00", ... }
```
3. Attacker replays the identical body and HMAC header, only changing:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
4. `ShopifyAPI::Utils::HmacValidator.validate` (which only hashes `@raw_body`) still returns `true`, and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"`: [4](#0-3) 
The app processes attacker-supplied data as if it came from `victim-shop.myshopify.com`.
