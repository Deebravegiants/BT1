Audit Report

## Title
Missing ParaId validity check in `do_place_order` allows queue/spot-price manipulation via orders for unschedulable parachains - (File: polkadot/runtime/parachains/src/on_demand/mod.rs)

## Summary
`Pallet::do_place_order` (invoked by `place_order_with_credits`, `place_order_allow_death`, `place_order_keep_alive`) accepts any `ParaId` value without checking that it corresponds to a registered parachain/parathread. Since the pallet uses a single shared `OrderStatus.queue` whose length directly drives `traffic`/`spot_price` for all users via `calculate_spot_traffic`, an attacker can inflate the effective price paid by all legitimate orderers by repeatedly queuing orders for a bogus `ParaId`.

## Finding Description
`do_place_order` (lines 471-558) only validates `spot_price <= max_amount`, that the queue is not full, and sufficient balance/credits for the caller; it never verifies `para_id` against `paras::Pallet::<T>` registration state before pushing the order into the bounded `queue` via `try_push` (line 547). [1](#0-0) [2](#0-1)  `ParaId` is a bare wrapper type with no innate validity constraint, so any `u32` value the caller supplies is accepted. `queue.len()` is fed straight into `calculate_spot_traffic` on every call to `update_spot_traffic`, which raises `traffic` (and hence `spot_price` charged to every subsequent orderer, regardless of which para they target) whenever queue utilization crosses `on_demand_target_queue_utilization`. [3](#0-2)  Downstream, `pop_assignment_for_cores` dequeues entries purely based on readiness/ordering with no para-validity check either, and the coretime scheduler's `advance_assignments_single_impl`/`pop_assignment_for_ondemand_cores` path treats whatever `ParaId` comes out of the on-demand queue as a `CoreAssignment::Task(para_id)` without filtering for registration. [4](#0-3)  No component in this call chain validates para registration, confirming the claim that the check is entirely missing.

## Impact Explanation
Because `traffic`/`spot_price` is a single global state shared across the entire on-demand queue, an attacker can consume their own credits or balance placing orders for a nonexistent/unschedulable `ParaId`, driving up `queue.len()` and thus `traffic`, which raises the price paid by every other on-demand orderer for real, registered parachains. This is a legitimate economic griefing/fee-manipulation vector against the shared pricing mechanism, though the attacker also pays the inflated price for their own subsequent orders, which bounds but does not eliminate the incentive (e.g., an attacker could grief competitors' pricing while accepting their own cost, or exploit it opportunistically for short windows). Impact is best categorized as a market-manipulation/griefing issue against on-demand pricing fairness rather than a fund-loss or consensus-safety bug.

## Likelihood Explanation
The precondition is minimal: any account holding on-demand credits (via `credit_account`) or a funded balance (for the deprecated balance-based calls) can call `place_order_with_credits`/`place_order_allow_death`/`place_order_keep_alive` directly with an arbitrary `para_id`, with no special origin required, repeatable every block up to `on_demand_queue_max_size`. [5](#0-4)  This is fully reachable via a standard signed extrinsic.

## Recommendation
Add a validity check in `do_place_order` ensuring `para_id` refers to a currently registered parachain or parathread (e.g. checking `paras::Pallet::<T>` lifecycle state) before charging the account and pushing to the queue, returning a dedicated error such as `Error::<T>::InvalidParaId` on failure.

## Proof of Concept
1. In a mock runtime for `polkadot/runtime/parachains/src/on_demand/tests.rs`, do not register `ParaId::from(9999)` with `paras::Pallet`.
2. Call `Pallet::<T>::credit_account(attacker, large_amount)`.
3. Repeatedly call `place_order_with_credits(RuntimeOrigin::signed(attacker), max_amount, ParaId::from(9999))` across blocks, advancing `on_initialize` between calls.
4. Observe each call succeeds and `Credits::<T>::get(attacker)` decreases, while `SpotPriceSet` events show `spot_price` rising as `queue.len()` grows past `on_demand_target_queue_utilization`, despite `ParaId::from(9999)` never being registered.
5. Have a second honest account place an order for a real registered `ParaId` in the same window and observe it pays the same inflated `spot_price` caused by the bogus-para orders.
