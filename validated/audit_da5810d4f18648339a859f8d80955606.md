### Title
Webhook `shop-domain` and `topic` headers are not covered by HMAC verification, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` and `topic` headers from the HMAC-verified data. `ShopifyAPI::Webhooks::Registry.process` uses this same unauthenticated `shop-domain` header value to build the `WebhookMetadata` passed to the app's handler. An attacker who legitimately receives one valid `(body, hmac)` pair for their own shop can replay it with a forged `shop-domain` header, and the library will accept it as valid and attribute the payload to an arbitrary victim shop.

### Finding Description
`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body: [2](#0-1) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read from separate, unauthenticated headers: [3](#0-2) 

`Registry.process` validates only the HMAC (which covers the body) and then constructs the metadata handed to the application handler directly from the unauthenticated `request.shop` and `request.topic`: [4](#0-3) 

This breaks the intended identity binding: `hmac_verified(body) == true` is treated as proof that `(body, shop, topic)` as a whole is authentic, when in fact only `body` is covered. The `shop` field is "acted on" (passed straight into `WebhookMetadata` and to the registered handler, which typically uses it to select/scope the tenant's data) but is not part of what the HMAC actually verifies.

### Impact Explanation
Because the signable string is `raw_body` alone, a `(raw_body, hmac)` pair valid for one shop remains cryptographically valid forever, for any `shop-domain`/`topic` header value the caller supplies, as long as the raw body bytes are unchanged. An attacker who is a legitimate merchant of their own shop installation (an unprivileged actor relative to other tenants of the same app) can capture a real webhook delivery for their own shop and replay the identical body/HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header (and/or a different registered topic, since topic is also unauthenticated). `Registry.process` will accept it as a valid, verified webhook and hand the attacker-controlled body to the handler tagged with the victim's shop identity, resulting in cross-tenant data injection/corruption in any app that persists or acts on webhook data keyed by `WebhookMetadata#shop`.

### Likelihood Explanation
Exploitation requires no possession of the app's `client_secret`/`api_secret_key` — only a single legitimate webhook delivery for a shop the attacker controls (trivial for any real merchant/installer of a multi-tenant app) and the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which is standard, low-effort tooling (e.g., curl). This is a realistic, unprivileged-internet-facing scenario reachable purely through this gem's own webhook verification and dispatch code (`Request`/`Registry`), not dependent on the host app ignoring documented behavior.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the string that is HMAC-verified, or otherwise cryptographically bind them to the body (e.g., by concatenating them into `to_signable_string` in a canonical, unambiguous format) so that tampering with any of these fields invalidates the signature. Short term, at minimum validate `request.shop` against the set of shops known/authorized for the app before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid, computed by Shopify over `B` with the app's real secret).
2. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) — identical to what was originally signed — so validation succeeds: [4](#0-3) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's own order body `B`, causing the host app to process/store attacker-controlled data under the victim shop's identity.
