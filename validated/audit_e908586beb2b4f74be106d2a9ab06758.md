## Title
Webhook `shop` (and `topic`) attribution is not covered by the HMAC, enabling cross-tenant webhook forgery — (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop as soon as `Utils::HmacValidator.validate(request)` succeeds, but the HMAC that is validated only covers the raw request body. The `shop-domain` (and `topic`) values that the handler is told to act on come from unsigned HTTP headers and are never bound into the signed bytes, and the HMAC secret (`Context.api_secret_key`) is the single app-wide `client_secret`, not a per-shop secret. This breaks the intended identity binding `hmac_valid_for(body) == authenticated_shop`.

## Finding Description
`ShopifyAPI::Webhooks::Request` derives all its identity fields from HTTP headers: [1](#0-0) 

but `to_signable_string`, which is what actually gets HMAC-verified, is only the raw body: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature strictly against `to_signable_string`, i.e. only the body, using the single app-wide secret: [3](#0-2) 

`Registry.process` gates on that same body-only HMAC check, and then hands the *unsigned* `request.shop`/`request.topic` header values straight to the app's handler as the tenant/topic to act on: [4](#0-3) 

Because the `client_secret` used for the HMAC is shared across every shop that has installed the app (it is not shop-specific), any merchant who has legitimately installed the app can obtain a genuinely-signed webhook for their own shop (e.g. one with a static/predictable body such as `{}` or any duplicate content), then replay that exact body while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. The HMAC validation still passes — it only proves "signed with this app's secret," not "signed for this shop" — and `Registry.process` will invoke the handler believing the event originated from the victim's shop.

## Impact Explanation
This is a cross-tenant identity-binding break: `shop_header == shop_that_produced_valid_hmac` does not hold. An app that uses `WebhookMetadata#shop` to key database writes, entitlement checks, or session lookups can be made to apply a webhook payload against a shop that never sent it, i.e. cross-tenant data corruption/access using only another legitimate (attacker-controlled) install's traffic. This matches the Critical "cross-tenant access" impact category.

## Likelihood Explanation
Any user who can install the app on their own store (an ordinary, unprivileged action — no leaked credentials, no `api_secret_key`, no TLS interception needed) can capture a validly-signed webhook for their own shop and replay it with a forged `shop-domain`/`topic` header against the app's public webhook endpoint. The only requirement is a body that is acceptable/predictable for the target topic (many webhook topics have minimal or empty bodies), which is realistic.

## Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically tie the header values to the verified request: e.g. include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (would require a Shopify-side spec change), or — within this gem — require callers to additionally verify `request.shop` against the shop of the `Session`/subscription that registered the webhook before dispatching to a handler, rather than trusting the header value as-is once the body HMAC passes.

## Proof of Concept
1. App installs on `attacker.myshopify.com`; Shopify sends a real webhook, e.g. `orders/create` with a minimal/empty body `{}`, headers:
   `x-shopify-hmac-sha256: <valid for "{}"`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request and replays it to the app's public webhook endpoint, only changing:
   `x-shopify-shop-domain: victim.myshopify.com` (keeping the same body `{}` and therefore the same valid HMAC).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, because it only checks the body against the shared `api_secret_key`.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and performs whatever tenant-scoped action the app implements for that topic, attributed to `victim.myshopify.com` despite never having sent this webhook.
