### Title
Webhook `shop` identity not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for whatever shop domain is asserted in the `x-shopify-shop-domain`/`shopify-shop-domain` header, but the HMAC signature that `Utils::HmacValidator.validate` checks only covers the raw request body — never the shop header. This is the same bug class as the report: a field that is *acted on* (here, the tenant identity `shop`) is not covered by the cryptographic binding that is supposed to authenticate the request, exactly analogous to the sign-loss in `tickToTreeIndex` producing an index that no longer reflects the value it was derived from.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` straight from a request header with no cryptographic tie to the signed payload: [1](#0-0) [2](#0-1) 

`to_signable_string` (used by `HmacValidator`) returns only `@raw_body`: [2](#0-1) 

`HmacValidator.validate` recomputes an HMAC purely over `to_signable_string` and compares it to the `hmac` header — it never includes `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` validates only that the body's HMAC is correct, then unconditionally forwards `request.shop` (the unauthenticated header) to the handler as the tenant identifier: [4](#0-3) 

The intended identity binding is: `shop header == shop that produced/owns this signed body`. Because the HMAC only binds the body bytes to the app's secret, and not the shop header, this equality is never actually checked by the gem. Any two values (a body that Shopify legitimately signed for shop A, and an arbitrary `shop` header value B) pass validation together. The gem's own documentation confirms host apps are expected to trust `data.shop` as the source-of-truth tenant identifier coming out of `Registry.process`, with no caveat that it must be independently re-verified: [5](#0-4) 

### Impact Explanation
An unprivileged attacker who is a merchant with the vulnerable app installed on their own store receives legitimately-Shopify-signed webhooks (valid `hmac-sha256` over the raw body) for their own shop, without ever needing `api_secret_key` — Shopify computes and delivers that HMAC to them. The attacker can capture one such request/body/HMAC pair from their own tenant and re-POST it to the app's webhook endpoint, substituting the `x-shopify-shop-domain` header with any other shop domain string (e.g. a victim shop that also uses the app). `HmacValidator.validate` still succeeds (the body bytes and signature are unchanged and valid), and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain and `body` containing the attacker's own (attacker-controlled) shop data. Any host application that uses `data.shop` to key persistence/side effects (exactly as the gem's own documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will apply attacker-controlled webhook content under a different tenant's identity. That is a cross-tenant data-integrity/confusion vulnerability satisfying the "cross-tenant access" impact category, without requiring the app secret, an access token, or TLS interception.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to (a) have the vulnerable app installed on a store they control (any merchant can install a public app), (b) trigger and capture at least one legitimate webhook event for a topic the app subscribes to, and (c) know/guess the target's shop domain (public information — `*.myshopify.com`). No secrets, tokens, or privileged access are needed, and no protocol-level MITM is required since the attacker owns the traffic they are replaying.

### Recommendation
Bind the shop identity into the value that is actually verified. Options:
- Include the shop domain (and ideally the webhook id / topic) inside the string that `to_signable_string` returns for `Webhooks::Request`, or otherwise require the caller to re-derive/verify the `shop` from a source outside the attacker's control (e.g., cross-check `shop` against the URL path/route bound to the registered webhook subscription, or against the topic + webhook_id via a server-side lookup).
- At minimum, document explicitly that `WebhookMetadata.shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identity by itself.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# Step 1: Attacker triggers a legitimate webhook (e.g. orders/create) on their own shop.
# Shopify sends:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<valid HMAC over the raw body, computed by Shopify with the real api_secret_key>",
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  "x-shopify-webhook-id" => "real-id",
  "x-shopify-api-version" => "2024-01",
}
raw_body = '{"id":1,"note":"attacker-controlled content"}'

# Step 2: Attacker replays the SAME body + SAME valid hmac header to the app's
# webhook endpoint, but swaps the shop-domain header to the victim:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator.validate(request) still returns true, because it only hashes raw_body,
# which is unchanged and still matches the untouched, Shopify-issued hmac header.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com",
#      body: {"id"=>1, "note"=>"attacker-controlled content"}, ...))
# The host app now processes attacker-controlled data under the victim's tenant identity.
```
