This shopify_api ruby gem doesn't contain an `_claimWithdrawal`/reentrancy-style vault, so the "hint" bug class doesn't map to funds-draining. But applying the report's underlying class — "an action is performed using a field that isn't covered by the authentication check" — does map to a real identity-binding gap in this gem's webhook processing path.

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` verifies is computed only over the raw request body, never the shop header. This breaks the equality that should hold: `shop authenticated by HMAC == shop the handler acts on`.

### Finding Description
`Webhooks::Registry.process` validates a webhook exclusively via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator recomputes the HMAC over `request.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body: [3](#0-2) 

Meanwhile, `shop` (the tenant identifier ultimately handed to the app's webhook handler via `WebhookMetadata`) is read straight from an HTTP header that is never part of the signed material: [4](#0-3) [1](#0-0) 

Because the app's `api_secret_key` is shared across all shops that install the app (it is not per-shop), any body+HMAC pair that is valid for one legitimately-installed shop is also a valid HMAC for the exact same body regardless of which `shopify-shop-domain` header accompanies it. The gem verifies "is this HMAC valid for this body" but the app-facing contract treats the response as "is this event authentically from shop X" — the header carrying `X` is not part of what was authenticated.

### Impact Explanation
This is a cross-tenant identity-binding gap: an attacker who controls (or has legitimately received, e.g. via their own shop's real webhook delivery) one valid `(body, hmac)` pair for the app can resend that exact body to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different, victim shop. `Registry.process` will accept the HMAC as valid (it only checks the body) and will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any host application that uses `WebhookMetadata#shop` as the tenant key (the documented, expected usage) will process attacker-controlled data under the wrong tenant, potentially triggering state changes, notifications, or side effects attributed to the wrong merchant — a cross-tenant confusion condition.

### Likelihood Explanation
Exploitability requires the attacker to already have a valid `(raw_body, hmac)` pair, which is trivially obtainable by installing the app on any shop the attacker controls (a normal, unprivileged action for any Shopify merchant) and capturing one real webhook delivery. From there, replaying it against the app's public webhook endpoint with a forged shop header requires no secret material at all.

### Recommendation
Bind the `shop` identity into the material that is cryptographically verified before it is trusted by the app, e.g. by having `Webhooks::Request#to_signable_string` incorporate the shop header (where supported by the delivery format) or, at minimum, documenting clearly that `WebhookMetadata#shop` is unauthenticated header data and must never be used as the sole tenant key by host applications. Where possible, cross-check the resolved `shop` against a shop already known/authorized for the delivered `webhook_id`/registration before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, normal merchant flow) and lets Shopify deliver one real webhook for topic `orders/create`, capturing `raw_body` and the `x-shopify-hmac-sha256` value.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the identical `raw_body`/HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` → `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`: [6](#0-5) 
5. Any host app logic keyed on `data.shop` now operates as if this attacker-controlled event genuinely originated from `victim-shop.myshopify.com`.
