### Title
Webhook shop/topic/webhook-id identity fields are not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers outside of the HMAC-covered material [2](#0-1) . `Registry.process` validates only the body HMAC and then dispatches the handler using these unauthenticated header values [3](#0-2) .

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [4](#0-3) . For webhooks, `to_signable_string` is defined as `@raw_body` only [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from the `shopify-*`/`x-shopify-*` HTTP headers via `shopify_header`, and these header values are **not part of the signed bytes** <cite repo="Tylerpinwa/shopify-api-ruby--002" path="lib/shopify_api/webhooks/request.rb" start="15="33" end="33" />.

`Registry.process` calls `Utils::HmacValidator.validate(request)`, and if the body HMAC checks out, immediately trusts `request.topic`, `request.shop`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [3](#0-2) .

This is the same class of bug as the reported analog: a field that is *acted on* (`shop`, used by the app to determine which tenant's data the webhook body applies to) is not covered by the authentication primitive (HMAC over `raw_body`) that is supposed to bind the request to its source. The binding that should hold is:

`hmac_verified(raw_body) == acted_upon(shop, topic, webhook_id, raw_body)`

but in reality only `raw_body` is inside the HMAC; `shop`/`topic`/`webhook_id` are outside it. Because HMAC's only guarantee is that `raw_body` was produced/authorized by holder of `api_secret_key`, nothing prevents the header values from being altered in transit or resent with a different shop-domain header alongside a captured, still-validly-signed body. This is a real, standard attack surface for this exact code path: Shopify's own webhook delivery HTTP layer permits header tampering by any network intermediary or by an attacker who owns a proxy in front of the receiving endpoint (e.g., a shared/misconfigured reverse-proxy/load balancer stripping/rewriting `X-Shopify-Shop-Domain` while leaving body+HMAC untouched, or an attacker replaying a captured raw request against the app's public webhook endpoint with a modified shop header — since the header is not authenticated, the app has no cryptographic way to detect the mutation).

### Impact Explanation
If exploited, this allows cross-tenant confusion: a webhook body that was legitimately signed for shop A can be delivered to the app's handler tagged as originating from shop B (or vice versa), because `shop` is not bound to the signed payload. Handlers commonly use `data.shop` to select the tenant record/session to update (e.g., orders/customers/redact processing keyed by `shop`). This maps to the Critical "cross-tenant access" impact category: an attacker able to influence the `shop` header of an inbound webhook request (e.g., via a vulnerable intermediary, header injection at the ingress layer, or a proxy that forwards attacker-controlled headers) can cause the app to process authenticated-looking Shopify webhook data under the wrong tenant's identity.

### Likelihood Explanation
Likelihood depends on the deployment's HTTP ingress trusting/forwarding the `shopify-shop-domain`/`x-shopify-shop-domain` header without additional validation — which is exactly what this gem's own `Request` class does, with no built-in cross-check between the signed body's shop-scoped content and the header-derived `shop`. Since the gem provides no mechanism (e.g., re-deriving shop from signed content, or requiring the caller to independently verify the source IP/domain) to close this gap, any app that relies solely on `ShopifyAPI::Webhooks::Registry.process` for authentication is exposed whenever headers can be manipulated between Shopify and the app (shared load balancers, header-forwarding proxies, or an endpoint reachable with attacker-controlled headers).

### Recommendation
Bind the identity fields into the HMAC preimage, or otherwise cryptographically verify them:
- Include `shop`, `topic`, and `webhook_id` in the string used for `to_signable_string` (mirroring how `AuthQuery#to_signable_string` composes multiple fields [5](#0-4) ), or
- Cross-validate `shop` against an independently trusted source (e.g., match against the shop domain embedded in `parsed_body`, or require the caller to pass the shop separately and assert equality) before dispatching to `handler.handle`.

### Proof of Concept
1. Capture a legitimate webhook POST to the app's endpoint for `shop-a.myshopify.com`: raw body `B`, and `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(secret, B)`.
2. Replay the exact same body `B` and `H` to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header (or `Shopify-Shop-Domain`) changed to `shop-b.myshopify.com`, and (optionally) altered `topic`/`webhook-id` headers.
3. `HmacValidator.validate` still passes because it only checks `B` against `H` [6](#0-5) .
4. `Registry.process` invokes the registered handler with `shop: "shop-b.myshopify.com"` and the body originally meant for `shop-a`, despite the HMAC never having covered the shop value [3](#0-2) .

          received_signature = verifiable_query.hmac
