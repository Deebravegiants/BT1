### Title
Emporium's `runAction` operation loop is unbounded by `erc20TokenAddresses`, letting an unprivileged caller drain all ETH held by Emporium via a zero-token (`MainEVMCircuitMin`) transact - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes `stack.ops[i].endpoint.call{value: op.value}(op.callData)` for every operation in the caller-supplied `EmporiumStack`, independent of `circomData.erc20TokenAddresses.length`. When a transaction is built with `dimensions.tokenNumber == 0` (`erc20TokenAddresses = []`), all of the balance-accounting loops in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` are bounded by that empty array and never execute, so any ETH moved by the `ops` array is completely unaccounted for. Combined with `verifyWallet` skipping signature verification when `stack.signerAddress == address(0)`, an attacker can freely craft an `EmporiumStack` that sends arbitrary ETH from Emporium to any address they choose.

### Finding Description
Broken equality: *set of assets Emporium's `msg.sender` identity can move in this call* (all ETH in `stack.ops`, unbounded) **!=** *set of assets accounted for in `balancesBefore`/`balancesAfter`* (the empty set, since `circomData.erc20TokenAddresses.length == 0`).

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks` → `dimensionsCheck`, which only requires `erc20TokenAddresses.length == dimensions.tokenNumber` [1](#0-0) . `tokenNumber = 0` is a valid, unconstrained choice; no minimum is enforced.
2. `verifyProof` is checked against `verifierMap[buildVerifierId(dimensions, externalActionId)]` [2](#0-1) . For `tokenNumber=0`, the circuit is `MainEVMCircuitMin`, whose only logic is `message <== Poseidon(1)([messageSeed])` [3](#0-2)  — it constrains nothing about `erc20TokenAddresses`, `emporiumMessage`, or the ops payload, so any attacker can trivially generate a valid proof for an arbitrary `messageSeed`.
3. In `Hinkal.transact`, the balance-diff/slippage/UTXO-accounting loop is `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` [4](#0-3) ; with an empty array this loop is a no-op, so no check ever runs against whatever `_externalTransact` did.
4. `_externalTransact` builds `deltaAmountChanges` of length `erc20TokenAddresses.length` (0) and calls `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` [5](#0-4) .
5. `EmporiumUpgradeable.runAction` decodes an attacker-controlled `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` and computes `balancesBefore`/`balancesAfter` over `circomData.erc20TokenAddresses` (empty) [6](#0-5) , but the operation-execution loop iterates `stack.ops.length`, completely independent of that array: `(success, err) = op.endpoint.call{value: op.value}(op.callData);` [7](#0-6) . With `erc20TokenAddresses = []`, the balance-check loop after the ops run (`for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) ...`) also never executes [8](#0-7) , so nothing catches the resulting negative ETH balance change.
6. `verifyWallet` requires an ECDSA signature only when `stack.signerAddress != address(0)`; if the attacker sets `signerAddress = address(0)`, the function just marks the message used and returns, with zero authorization of `stack.ops` content [9](#0-8) .
7. Emporium accumulates ETH via `receive() external payable {}` from any unrelated prior legitimate flow [10](#0-9) .

The attacker's exact call: `Hinkal.transact` with `dimensions.tokenNumber=0`, `circomData.erc20TokenAddresses=[]`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: attackerEOA, invokeWallet: false, value: address(emporium).balance, callData: ""})], ...}))`, and a `MainEVMCircuitMin` proof for a self-chosen `messageSeed`. No existing guard (`dimensionsCheck`, `verifyProof`, `rootHashExists`, the balance/slippage requires, `insertNullifiers`, `onlyAllowedRecipient`, `verifyWallet`, `nonReentrant`) constrains the relationship between `stack.ops` and `circomData.erc20TokenAddresses`.

### Impact Explanation
Direct, permanent theft of all ETH held by the Emporium contract — protocol/relay-fee-dust and leftover balances that legitimately belong to no accounted UTXO — to an attacker-chosen address, with zero token ownership or role required. This is repeatable every time ETH accumulates in Emporium (e.g., from fee remainders, rounding, or partial-swap leftovers). Category: Critical (direct theft of protocol/Emporium-held funds via an action never authorized or accounted for by the proof/checks).

### Likelihood Explanation
Preconditions: (a) a verifier must be registered for `verifierId = buildVerifierId({tokenNumber:0, nullifierAmount:0, outputAmount:0}, EMPORIUM_ACTION_ID)` pointing at `MainEVMCircuitMin` (this is the exact "Min circuit" configuration the question is scoped to), and (b) Emporium must hold nonzero ETH (trivially true after any normal usage due to `receive()`). Attacker cost is a single transaction plus a trivially generated zero-knowledge proof (the circuit has no real constraints). No signature, whitelisting, or privileged role is needed since `signerAddress = address(0)` bypasses `verifyWallet`'s ECDSA check entirely. Fully repeatable, limited only by however much ETH Emporium is holding at the time.

### Recommendation
- Require `circomData.erc20TokenAddresses` (and thus the accounted balance set) to include every distinct token/ETH actually moved by `stack.ops`, e.g. by deriving the touched-asset set from the ops themselves (or requiring `op.value == 0` unless `address(0)` is present in `erc20TokenAddresses`), and reject the transaction otherwise.
- Alternatively, disallow `tokenNumber == 0` for the Emporium action entirely, or bound the `stack.ops` loop's total `op.value` by a value explicitly reconciled against `deltaAmountChanges`/`erc20TokenAddresses`.
- Do not allow `stack.signerAddress == address(0)` to bypass authorization of `stack.ops` content; if this mode is meant only for protocol-internal use, gate it behind a privileged check rather than accepting it from arbitrary `msg.sender`-supplied `CircomData`.

### Proof of Concept
Foundry fork test plan:
1. Deploy/mock Hinkal + HinkalHelper + EmporiumUpgradeable with a `MainEVMCircuitMin`-based verifier registered for `verifierId = buildVerifierId(Dimensions(0,0,0), HINKAL_EMPORIUM_ACTION_ID)` (mock verifier returning `true` to stand in for a real snarkjs-generated proof, or generate a real proof for an arbitrary `messageSeed` using circomjs).
2. Seed Emporium with ETH via a legitimate multi-token `transact` (e.g., a swap leaving dust), asserting `address(emporium).balance > 0`.
3. Record `attacker.balance` before.
4. Call `Hinkal.transact(a,b,c, Dimensions(0,0,0), circomData)` where `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation(attackerEOA, false, address(emporium).balance, "")], maxFee:0, deadline: type(uint256).max, v:0,r:0,s:0}))`, `feeStructure.flatFee = 0`, and a valid `rootHashHinkal`.
5. Assert: `attacker.balance` increased by the pre-call `address(emporium).balance`, `address(emporium).balance == 0` after, and that `circomData.erc20TokenAddresses` never contained `address(0)` — proving the equality "assets moved by Emporium" ≠ "assets accounted for in balancesBefore/balancesAfter" (empty set) was violated with no revert.
