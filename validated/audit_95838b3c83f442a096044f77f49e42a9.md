### Title
Caller-supplied swap route lets attacker code drain the signer's wallet inside its own authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) forward fully attacker-controlled `swap` bytes to the configured router. The router keeps no allowlist of pools or tokens and invokes whatever `pool` address each hop names. A malicious hop pool runs inside the caller's authorization subtree, so a `token.transfer(victim, attacker, amount)` it makes is recorded as a child of the victim's own `require_auth` entry and executes under enforcing auth once signed — a direct analog of host-header poisoning: attacker-supplied input is used to build trusted security-relevant calls.

### Finding Description
`swap_tokens` authorizes exactly one `token_in.transfer(controller, router, amount_in)` and calls `router.execute_strategy` with the raw `StrategySwap` bytes [1](#0-0) . The hop context pulls funds and calls the `hop.pool` address the payload names [2](#0-1) . The threat model itself concedes that "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization," and that such a transfer "executes if the caller signs that tree," losing "the caller's wallet, not the routed amount" [3](#0-2) . The harness proves reachability: a `RogueHopPool.swap` invoked from the route calls `token::Client::transfer(victim, attacker, amount)` on an unlisted wallet token, and recording/enforcing auth attaches it to Alice's entry [4](#0-3) .

### Impact Explanation
Theft of user funds beyond the swapped amount: any token balance in the victim's wallet (including assets the protocol never listed) can be moved to the attacker inside the signed auth tree while the routed swap itself returns a fair output and all controller invariants (`RouterOverspend`, `NoSwapOutput`, final risk gates) still pass.

### Likelihood Explanation
Requires the victim to submit a route built by an attacker (malicious quote server, compromised frontend, or social-engineered `routeXdr`). This is user-supplied input rather than a pure permissionless attack on an unwilling victim, and the mitigation (decode the route and reject authorization trees with unexpected children) is documented and exists in the SDK (`verifyRoutePayload`). Medium likelihood, Medium overall.

### Recommendation
Enforce a governance-maintained venue/pool allowlist in the router (or pin pool addresses per market in controller storage) so route bytes cannot name arbitrary contracts, and/or have the controller authorize the router with `sub_invocations` depth zero and verify the auth tree shape. Keep enforcing the measured-output and overspend checks in `swap_tokens`.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` registers a router double that calls `env.invoke_contract(&route.hop_pool, "swap", …)`; the attacker-deployed `RogueHopPool` then calls `token.transfer(alice, attacker, WALLET_BALANCE)` on a token the protocol never listed, and the auth tree attaches it to Alice's authorization for `swap_collateral`.
