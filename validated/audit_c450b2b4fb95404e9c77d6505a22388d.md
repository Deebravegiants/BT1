## Analysis

I traced the bug-class hint ("a field acted on but not covered by the HMAC") to the webhook processing path in this gem. [1](#0-0) 

`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return **only** `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from unauthenticated HTTP headers, not covered by the signature: [3](#0-2) 

`Registry.process` validates only the body HMAC, then hands the raw header-derived `shop` directly to the app's handler as the tenant identifier: [4](#0-3) 

### Title
Webhook tenant identity (`shop-domain`) is not bound to the HMAC-verified payload, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers — it only proves the body bytes were signed with the app's secret at some point, by Shopify, for *some* shop. `Registry.process` then trusts the `shop` header verbatim and passes it to the host app's handler via `WebhookMetadata`, which apps use to look up the correct offline session/access token for that tenant.

### Finding Description
The identity binding that should hold is:
`shop_used_for_tenant_routing (header) == shop_that_actually_produced_the_signed_body`

This equality is not enforced anywhere in the gem. The HMAC only authenticates `@raw_body`; the `shop-domain` header travels outside the signed envelope: [5](#0-4) [2](#0-1) 

Any actor who can install the target app on their own store (an ordinary, unprivileged action available to any internet user for public apps) legitimately receives real webhook deliveries for their own shop with a valid `x-shopify-hmac-sha256` value for the exact body Shopify sent. Because the header is not part of the signed content, that attacker can resend the identical `raw_body` + `hmac` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` will still succeed (it only recomputes the HMAC over `raw_body`), and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop: [6](#0-5) 

If the host application (as documented/intended) uses `WebhookMetadata#shop` to select the stored session/access token to act on (a normal pattern since all webhooks for all shops land on one endpoint URL and must be dispatched by this header), the attacker's crafted body is now processed under the wrong tenant's identity and access token — a cross-tenant confusion primitive.

### Impact Explanation
This breaks tenant isolation: attacker-controlled webhook content (topic + body, since `topic` is likewise header-derived and unauthenticated) is attributed to and processed against a victim shop's session, potentially causing the host app to act on the wrong merchant's data/access token. This matches the "cross-tenant access" Critical category, since the binding between authenticated bytes (the body) and the tenant identity (the shop header) that routes credential usage is not enforced by the gem.

### Likelihood Explanation
Requires only that the attacker be able to install the app themselves (or otherwise obtain one legitimately-signed webhook body/HMAC pair for their own store) and replay it with a modified `shop-domain` header directly to the app's public webhook endpoint — no secrets, tokens, or privileged access needed.

### Recommendation
Bind the routing-critical headers into the signed material verified by `HmacValidator`, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the payload before dispatch — e.g., include them in `to_signable_string`, or require the host app be given an explicit warning/API to cross-check `shop` against the shop that the `client`/session used to register that specific webhook subscription, rather than trusting the raw header value passed through unauthenticated in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers/receives a real webhook (e.g. `orders/create`), capturing `raw_body` and its valid `x-shopify-hmac-sha256`.
2. Attacker POSTs the same `raw_body` + same `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)`; since only `raw_body` is signed and unchanged, validation passes.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's data>, ...)`, i.e., attacker-supplied data is processed as if it belongs to `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
