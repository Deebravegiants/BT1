### Title
Updating a token's per-chain contract mapping mid-flight permanently strands escrowed/burned funds - ([File: modules/pallets/hyper-fungible-token/src/lib.rs, module.rs])

### Summary
`pallet-hyper-fungible-token`'s `send` extrinsic burns/escrows a user's balance and dispatches an ISMP `PostRequest` addressed to whatever contract is currently recorded in `TokenContracts`/`ContractToAsset` for the destination chain. If the token's contract mapping for that chain is subsequently reconfigured via `update_token` (a routine maintenance call, e.g. migrating to an upgraded token contract) before the in-flight request resolves, the `on_timeout` refund path can no longer resolve the old contract address to an asset, and the already-burned/escrowed funds can never be refunded or delivered — a direct analog of the GMX "un-whitelisting" bug class.

### Finding Description
`send()` looks up the destination contract address and decimals at dispatch time and embeds that address as the `to` field of the outgoing `DispatchPost`, after burning or escrowing the user's tokens: [1](#0-0) 

The reverse lookup used later to process either an accepted delivery or a timeout is `ContractToAsset<T>`, keyed by `(StateMachine, contract_address_bytes)`: [2](#0-1) 

`update_token` allows `CreateOrigin` to change a token's contract address for a chain (`add_chains`) or remove chain support entirely (`remove_chains`). Both paths delete the *old* `ContractToAsset` entry (and, for removal, also delete `Precisions`) without any check for outstanding in-flight requests still addressed to that old contract: [3](#0-2) 

When the original request eventually times out, `on_timeout` re-derives the asset via `ContractToAsset::<T>::get(dest, &to)` using the *old* `to` address baked into the already-dispatched request, and via `Precisions::<T>::get(local_asset_id, dest)`: [4](#0-3) 

If the mapping was updated/removed in the interim, both lookups fail (`UnknownContractOnTimeout` / `DecimalsNotConfigured`), and `on_timeout` errors out permanently — there is no fallback path to recover the escrowed/burned funds. The funds were already deducted from the user in `send()`, so this is not merely a delayed delivery: it is unrecoverable, since the request's identity (destination + old `to` address) is immutable once dispatched, while the pallet's routing tables are mutable and can be changed by ordinary token maintenance.

### Impact Explanation
Any user who calls `send()` shortly before a legitimate `update_token` reconfiguration (e.g. the token's contract address is migrated to a new deployment on a given chain, or the chain support is removed) has their tokens burned/escrowed with no path to refund if the request times out, and no path to have it accepted either since the destination contract's own registration would also need updating in lockstep. This is a permanent loss of user funds triggered by routine, non-malicious protocol maintenance — matching the "High" severity impact described in the reference report (stuck funds/loss of funds due to whitelist/registry changes racing in-flight transfers).

### Likelihood Explanation
Token contract migrations and chain-list updates via `update_token` are an expected, periodically-exercised operational function (e.g., correcting a misconfigured address or rotating to an upgraded contract), not a rare or adversarial event. Any `send()` transaction whose ISMP timeout window overlaps such an update is affected; because ISMP timeouts can be tens of minutes to hours out, the race window is realistic for legitimate governance operations, not requiring any malicious behavior from `CreateOrigin`.

### Recommendation
Do not hard-delete old `ContractToAsset`/`Precisions` entries when updating a token's registration. Instead, retain historical entries (or version them) so that `on_timeout`/`on_accept` for requests dispatched under the old configuration can still resolve correctly, or track a per-request snapshot of the asset id/decimals used at dispatch time so that resolution doesn't depend on a mutable global mapping that can change after the request has already left the chain.

### Proof of Concept
1. Governance registers asset `X` for `StateMachine::Evm(1)` with contract address `A` via `register_token`.
2. User calls `send()` for asset `X` to `Evm(1)`; the pallet burns/escrows the amount and dispatches a `PostRequest` with `to = A`.
3. Before the request resolves, governance calls `update_token` to migrate asset `X` on `Evm(1)` to a new contract address `B` (a routine, legitimate migration): this removes `ContractToAsset[(Evm(1), A)]` and inserts `ContractToAsset[(Evm(1), B)]`, per [5](#0-4) .
4. The original request eventually times out. `on_timeout` calls `ContractToAsset::<T>::get(Evm(1), A)`, which now returns `None`, raising `UnknownContractOnTimeout` per [6](#0-5) .
5. The user's burned/escrowed funds are never refunded and were never delivered — permanently stuck.
