### Title
Webhook HMAC Validation Does Not Cover the `shop`, `topic`, `webhook_id`, or `api_version` Fields, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` never authenticates the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `ShopifyAPI::Webhooks::Registry.process` nonetheless treats `request.shop` as the trusted tenant identifier and hands it straight to the app's webhook handler, exactly as the gem's own documentation instructs apps to do. This breaks the identity binding `HMAC-verified bytes == bytes used to identify the tenant`, letting an attacker replay a legitimately-signed webhook body under a forged `shop-domain` header to make the receiving app believe the payload originated from a different (victim) shop.

### Finding Description
The HMAC signable string is defined as just the raw body: [1](#0-0) 

But the `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from unauthenticated HTTP headers: [2](#0-1) 

`HmacValidator.validate` only checks the HMAC against `verifiable_query.to_signable_string` (i.e., the raw body), never against the headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, passing them to the app's handler as if they were verified: [4](#0-3) 

The gem's own documentation instructs apps to treat `data.shop` as the authoritative tenant/shop identifier for routing and persistence, reinforcing that this field is expected to be trustworthy once `Registry.process` succeeds: [5](#0-4) 

The broken equality is: **bytes verified by HMAC (`raw_body` only) != bytes relied upon for tenant identification (`shop-domain` header)**. Any party who can obtain one valid `(raw_body, hmac)` pair — trivially, by owning their own Shopify store and receiving a legitimate webhook for it — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`webhook-id`) header for a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the headers, and `Registry.process` will label the (attacker-supplied) payload as coming from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion vulnerability: an unprivileged internet user (an app installer on their own store) can make the app process attacker-chosen webhook content while it is attributed to an arbitrary other shop known to have installed the app. Depending on how the host app uses `data.shop` (as documented by this gem — for storage, job dispatch, or session/access-token lookup keyed by shop), this can lead to cross-tenant data injection or corruption under another merchant's identity, which maps to the "Critical – cross-tenant access" category in scope.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own (or a trial) store: they only need to trigger one webhook topic they're registered for to capture a valid `(raw_body, hmac)` pair signed with the real `api_secret_key` by Shopify, then replay it to the app's public webhook endpoint with a forged `shop-domain` header. No access token, secret key, or privileged access is required — this uses only publicly observable webhook deliveries and the app's public HTTP webhook endpoint.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in the HMAC-signed material (or independently verify that the shop indicated by these headers matches an installation actually authorized for that webhook subscription) before trusting `request.shop`/`WebhookMetadata#shop` in `ShopifyAPI::Webhooks::Registry.process`. At minimum, update `Request#to_signable_string` to bind the shop domain into what is verified, and document that `data.shop` must be independently confirmed against known/installed shops before being used for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Attacker triggers the topic (e.g., creates an order) and captures the resulting legitimate webhook request: `raw_body` and the `x-shopify-hmac-sha256` header, both signed by Shopify with the app's real `api_secret_key`.
3. Attacker sends a new HTTP POST to the app's webhook endpoint containing the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally alters `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-computes the HMAC over `raw_body` (`Request#to_signable_string`) — the forged `shop-domain` header is never checked.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the app to process attacker-controlled content as if it came from `victim-shop.myshopify.com`.

```ruby
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
