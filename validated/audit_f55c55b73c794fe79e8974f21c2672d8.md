### Title
Webhook shop/topic/api_version headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but signs only the raw request body, while the shop domain, topic, api version, and webhook id are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC and then dispatches the handler using these header-derived, unsigned values, so an attacker who possesses one genuinely-signed webhook payload (which they can obtain by installing the app on a store they control, since Shopify signs every webhook for an app with the same `client_secret`) can replay that raw body against the app's webhook endpoint with a forged `shopify-shop-domain` header. The HMAC still validates because it never covered the header in the first place, and the host application processes the payload as if it belonged to a different, victim shop.

### Finding Description
`to_signable_string` in `Webhooks::Request` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all derived purely from the incoming HTTP headers, with no relation to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the request and, once it passes, immediately trusts `request.shop` and `request.topic` (taken from the unauthenticated headers) to route the payload to a handler and populate `WebhookMetadata`: [3](#0-2) 

The identity binding that should hold is: `shop` authenticated by the HMAC == `shop` attributed to the payload for downstream processing. Because `to_signable_string` only covers `@raw_body`, this equality is never enforced — the `shopify-shop-domain` header can differ arbitrarily from whatever shop the body was actually signed for by Shopify, and `HmacValidator.validate` (which only recomputes the HMAC over `to_signable_string`) has no way to detect the mismatch: [4](#0-3) 

Since a single app's `api_secret_key` is used to sign webhooks for *every* shop that installs the app, any user who installs the target app on a shop they control can legitimately receive a validly-HMAC'd webhook body (e.g. `orders/create`, `customers/data_request`, `customers/redact`) and then replay that exact body to the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. The signature check passes because it only verifies the body bytes, not the header, and the handler receives `WebhookMetadata` claiming the victim shop as the source.

### Impact Explanation
This breaks tenant isolation: the host application's webhook handler acts on data (e.g. mandatory compliance topics `customers/redact`, `customers/data_request`, `shop/redact`, or business-logic topics like `orders/create`) while believing it originates from a shop the attacker does not own. Depending on what the host app does with `WebhookMetadata#shop`, this can cause cross-tenant data corruption, spurious GDPR redaction/deletion actions against a victim shop's data, or incorrect app state updates attributed to another tenant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires that the attacker install the target app on a shop under their own control (a normal, unprivileged action any internet user can take with a public Shopify app) and capture the resulting webhook body/HMAC pair, then replay it with a modified `shopify-shop-domain` header to the app's public webhook endpoint. No access to the app's `client_secret`, access tokens, or any privileged account is required.

### Recommendation
Include the shop domain (and ideally topic/api_version/webhook_id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the payload before it is trusted by `Registry.process`/`WebhookHandler.handle`. At minimum, `to_signable_string` should not allow the tenant-identifying header to be excluded from what is verified against the HMAC.

### Proof of Concept
1. Attacker creates their own development store `attacker.myshopify.com` and installs the target Shopify app (any public app using this gem for webhook processing).
2. Shopify sends a legitimately signed webhook, e.g. `customers/data_request`, to the app's webhook endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>` and body `B`.
3. Attacker captures `B` and the valid `hmac`.
4. Attacker sends a new HTTP request to the same webhook endpoint with the same body `B` and the same valid `hmac`, but sets `shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only checks `raw_body`, so `Utils::HmacValidator.validate(request)` in `Registry.process` returns `true`.
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: ...)`, causing the host app to act on victim.myshopify.com using attacker-controlled payload content.
