This confirms the vulnerability: `AuthQuery#to_signable_string` includes `shop`, `code`, `host`, `state`, `timestamp` all in the signed content [1](#0-0) , but `Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop`, `topic`, `webhook_id`, and `api_version` header values from the HMAC computation [2](#0-1) . The `shop` value returned by `request.shop` is read directly and unvalidated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) , and `Registry.process` only validates the HMAC before passing `request.shop` straight into the handler as the tenant identity [4](#0-3) .

### Title
Webhook HMAC Validation Excludes the `shop` (and `topic`) Header, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers. Since `HmacValidator.validate` verifies the signature over `to_signable_string` only [5](#0-4) , an attacker who possesses a single valid `(raw_body, hmac)` pair for the app (e.g. obtained legitimately from their own shop, since Shopify webhook HMACs are computed with the app's single shared `client_secret`, not a per-shop secret) can replay that exact body/HMAC combination while substituting any value in the `shopify-shop-domain` header. `Registry.process` accepts the request as valid and forwards the attacker-chosen `shop` value to the host application's webhook handler as the trusted tenant identifier.

### Finding Description
The binding that should hold is: `shop authenticated by HMAC == shop passed to the handler as the tenant identity`. Here that equality is broken:

- Before the request: the HMAC the attacker holds was computed by Shopify over `raw_body` only, using the app's `client_secret`, for a webhook that was genuinely destined for the attacker's own shop.
- The signed content, per `to_signable_string`, is exactly `@raw_body` [2](#0-1) . `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers but never included in what gets hashed [6](#0-5) .
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header using `OpenSSL.secure_compare` [7](#0-6) . Since `to_signable_string` never contains the shop domain, mutating `x-shopify-shop-domain`/`shopify-shop-domain` does not change the value being hashed, so the same signature remains valid.
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, then constructs `WebhookMetadata` using `request.shop` unmodified [4](#0-3) .
- After the attacker's replay: the request still passes HMAC validation, but `request.shop` now equals the attacker-chosen victim shop domain instead of the shop the payload was actually generated for.

This exactly matches the flagged analog class: "a field acted on but not covered by the HMAC" — `shop` is acted upon (used as the tenant key by the handler) but is not part of the HMAC-protected content.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a host application that stores/updates per-shop state keyed by `WebhookMetadata#shop` (e.g. updating an order, customer record, or subscription status for "shop X") can be made to apply attacker-supplied payload data under an arbitrary victim shop's identity, because the gem hands back a `shop` value that was never cryptographically bound to the verified payload. This satisfies the Critical "cross-tenant access" impact bar defined in scope.

### Likelihood Explanation
The `api_secret_key`/`client_secret` for a Shopify app is shared across every shop that installs the app; it is not shop-specific. An unprivileged attacker only needs to install the target app on a shop they control (a normal, low-privilege action), capture one legitimate webhook delivery (raw body + HMAC pair) for their own shop, and replay that HTTP POST to the app's webhook endpoint with the `shopify-shop-domain` header changed to the victim shop. No possession of the app's `client_secret` or any victim credential is required — only reachable via the gem's own `Webhooks::Request`/`Registry.process` code path.

### Recommendation
Do not treat header-derived fields (`shop`, `topic`, `api_version`, `webhook_id`) as trusted merely because the body's HMAC validates. Either:
- Bind the shop domain (and topic) into the signed content check by cross-referencing it against known/expected values (e.g., session lookup keyed by shop, or requiring the host application to independently confirm the shop has an active session before trusting `data.shop`), or
- Document explicitly and enforce that `WebhookMetadata#shop` must not be used as a sole tenant-authorization key without an independent installed-shop check, since it is not covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`), receiving a legitimate POST with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical POST to the same webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers and stores `@raw_body = B` [8](#0-7) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) and compares to `H` — this matches, since `shop` was never part of the signed content [9](#0-8) .
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and dispatches to the app's handler, which now applies attacker-controlled payload data under the victim shop's tenant identity [10](#0-9) .
