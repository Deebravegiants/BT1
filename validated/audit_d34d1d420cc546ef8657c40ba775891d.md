### Title
Webhook `shop` domain field is trusted for tenant identity but not covered by HMAC signature - cross-tenant webhook confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `x-shopify-shop-domain`/`shopify-shop-domain` header [1](#0-0)  and this value is passed unmodified into `WebhookMetadata.shop`, which host apps use as the tenant identifier to route/store webhook data [2](#0-1) [3](#0-2) . However, the HMAC signature computed by `to_signable_string` only covers the raw request body, never the shop-domain header [4](#0-3) , and `HmacValidator.validate` verifies exactly that signable string against `Context.api_secret_key` (a single app-wide secret shared across all installed shops, not a per-shop secret) [5](#0-4) .

### Finding Description
The identity binding that should hold is: `shop domain authenticated by HMAC == shop domain used as tenant key`. In this gem that binding is broken — the bytes cryptographically verified (`@raw_body`) are disjoint from the bytes trusted for tenant identity (the `shop-domain` header). Because `Context.api_secret_key` is one shared secret for the whole app (not scoped per shop), any user who has genuinely installed the app on their own shop can capture a legitimately-signed webhook body/HMAC pair generated for their own shop, then replay that exact body+HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header value (e.g., a victim shop the attacker does not control). `Registry.process` only checks `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `@raw_body` and compares it to the header-provided HMAC — it never binds the verified body to the specific `shop` header value [6](#0-5) . The signature therefore passes, and the forged `shop` value is handed to the app's handler as trusted tenant context.

### Impact Explanation
This enables cross-tenant confusion: an app that uses `data.shop` from `WebhookMetadata` to look up or create per-shop records (a documented, expected pattern per `docs/usage/webhooks.md`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be made to process an attacker-supplied payload under another store's identity. Depending on the host app's webhook handler logic, this can be leveraged to write attacker-controlled data into another tenant's records, trigger tenant-scoped side effects (e.g., order/fulfillment logic) attributed to a shop the attacker doesn't own, or pollute another shop's synced data — a cross-tenant access impact.

### Likelihood Explanation
Moderate-to-high: exploitation requires only that the attacker have (or previously had) the app installed on some shop they control so they can capture one genuine, validly-signed webhook body from Shopify. No access token, `api_secret_key`, or privileged account is needed — the attacker only replays a header they fully control (`shop-domain`) alongside a body/HMAC pair that was legitimately issued to them. Any webhook topic whose body doesn't itself echo the shop (most topics only include resource data, not the shop domain) is exploitable this way.

### Recommendation
Bind the verified bytes to the shop identity: either (a) include the `shop-domain` header (and ideally `webhook-id`/`topic`) in the HMAC-signed content check by validating against Shopify's documented header-inclusive scheme, or (b) require the caller to independently verify that `data.shop` corresponds to a shop with an active, previously-established session/installation before trusting it, and reject/flag mismatches. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant key without cross-checking against known installed shops.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify.
2. Attacker replays this exact body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and compares to the supplied HMAC — validation succeeds because the body/HMAC pair is genuine [8](#0-7) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the app processes the attacker's body as if it belongs to the victim shop [6](#0-5) .

            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
