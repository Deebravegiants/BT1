### Title
Non-embedded session cookie value is a deterministic, unsigned identifier (`{shop}_{user_id}` / `offline_{shop}`), not a random secret, enabling session-id guessing across the cookie-fallback lookup path - ([File: lib/shopify_api/auth/session.rb], [File: lib/shopify_api/utils/session_utils.rb], [File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Session.from` sets `id = "#{shop}_#{associated_user.id}"` for online sessions and `"offline_#{shop}"` for offline sessions [1](#0-0) , and `Oauth.validate_auth_callback` writes exactly that value, unsigned and unencrypted, into the `shopify_app_session` cookie for non-embedded apps [2](#0-1) . `SessionUtils.cookie_session_id`/`current_session_id` later returns that raw cookie value verbatim as the "session id" with zero cryptographic verification [3](#0-2) [4](#0-3) . `AssociatedUser.id` is a plain `Integer` [5](#0-4) , so the online session id is fully deterministic given a known shop domain and a small integer staff-user id.

### Finding Description
Binding claimed: `session_id used for lookup == cryptographically-authenticated (shop, user)` should hold. Trace:

- `Session.new` by default assigns `@id = SecureRandom.uuid` [6](#0-5)  - unguessable.
- But `Session.from`, used specifically by `Oauth.validate_auth_callback` after a completed OAuth Authorization Code Grant, overrides this and sets `id = "#{shop}_#{associated_user.id}"` (online) or `"offline_#{shop}"` (offline) [1](#0-0) . This deterministic id is exactly what is placed into the plain `SessionCookie` value for non-embedded apps [2](#0-1) .
- `SessionCookie` is a plain `T::Struct` with no signing/HMAC of its own [7](#0-6) .
- On subsequent requests, `SessionUtils.current_session_id(nil, cookies, true)` (the documented non-embedded / cookie-fallback path) simply reads `cookies[SESSION_COOKIE_NAME]` and returns it unmodified — no HMAC check, no JWT decode, no signature verification whatsoever [3](#0-2) .
- Contrast with the embedded/JWT path: there, `session_id_from_shopify_id_token` first constructs `Auth::JwtPayload.new(id_token)`, which verifies an HS256 signature against `Context.api_secret_key` before trusting `shop`/`sub` [8](#0-7) . The cookie path has no equivalent check — the returned "session id" is trusted purely because it arrived in a cookie header, with no proof it was ever issued by this app to this specific browser via a verified OAuth flow.

Because the session id itself is deterministic and low-entropy (`shop` domain is often already known/public for an attacker's own installed copy of the target app, and Shopify staff numeric ids are small sequential integers), an attacker who never has an access token or `api_secret_key` can construct the exact victim session id and send it directly as an HTTP `Cookie` header to the host app's endpoint (raw HTTP clients are not bound by browser same-origin cookie jar rules). If the host application, following this gem's documented pattern, uses this id as the lookup key into its own session/token store (as the reference `shopify_app` gem's `ShopSessionStorage#retrieve(id)` does), the attacker's guessed id resolves to the real victim session, and the attacker inherits that victim's access token and scopes for API calls made through `ShopifyAPI` clients.

None of the gem's existing guards intervene here: `HmacValidator.validate` and the `state` comparison only protect the *original* OAuth callback (they ran once, when the *real* victim authorized the app) [9](#0-8) ; they are never re-checked on subsequent API requests that merely resolve a session id from a cookie. `JwtPayload`'s `aud` check only applies to the embedded/JWT branch, not the cookie branch. `Context.setup?`/`private?`/`embedded?` gate configuration, not per-request authentication of the cookie value.

### Impact Explanation
Per successful guess, the attacker obtains the ability to make Shopify Admin API calls under a specific victim staff user's online (or the shop's offline) access token/scopes — cross-user and cross-tenant impersonation, matching the "Critical: cross-tenant access / theft of a merchant access token" category. This is repeatable against any shop/user-id combination the attacker can enumerate, since the id format is fixed and public (`{shop}_{integer}` or `offline_{shop}`); the blast radius spans every non-embedded app built on this gem's documented Authorization Code Grant flow that stores sessions keyed by `session.id` as recommended.

### Likelihood Explanation
Preconditions: the host app must be a non-embedded app using the Authorization Code Grant (`Oauth.validate_auth_callback`) and must key its session storage by `session.id` (the pattern this repo's own `BREAKING_CHANGES_FOR_V16.md` shows as the reference implementation via the `shopify_app` gem). The attacker needs to know/guess the target shop's domain (frequently public) and a staff user's numeric id (small, often sequentially enumerable, e.g., by installing the app themselves as staff and observing their own low id, or from account-owner==false collaborator accounts). Cost is a single crafted HTTP request per guess — no secrets, no signature forgery, no live-shop MITM required. This is feasible and repeatable against arbitrary shops running default, documented configuration.

### Recommendation
Never derive a browser-facing session cookie value from cryptographically predictable components. `Session.from`/`Oauth.validate_auth_callback` should keep using a cryptographically random `SecureRandom.uuid` (already the `Session.new` default) as the *cookie* value, while the deterministic `"#{shop}_#{user_id}"` string can remain an internal storage lookup key that is only ever derived by first validating an authenticated artifact (JWT signature or HMAC-validated OAuth callback), analogous to the embedded path. Alternatively, sign/encrypt the session cookie (e.g., via the host framework's signed/encrypted cookie jar) so `SessionUtils.cookie_session_id` cannot be forged by constructing an arbitrary string.

### Proof of Concept
minitest + Mocha plan (no live shop):
1. Stub `ShopifyAPI::Context.embedded?` to `false`.
2. Build `session = ShopifyAPI::Auth::Session.from(shop: "victim-shop.myshopify.com", access_token_response: <online AccessTokenResponse with associated_user.id = 42>)` and assert `session.id == "victim-shop.myshopify.com_42"`.
3. Simulate the attacker independently constructing `forged_cookie_value = "victim-shop.myshopify.com_42"` with no access to any secret, api_secret_key, or the real cookie.
4. Call `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }, true)` and assert the returned value `== session.id` (i.e., `== "victim-shop.myshopify.com_42"`), proving the forged, unauthenticated string is indistinguishable from — and accepted identically to — the legitimately issued session id, with no signature or HMAC check performed anywhere in the call path.
5. Assert (via `Mocha` spy/`assert_not_requested`/absence of stub expectations) that no call to `Auth::JwtPayload.new`, `HmacValidator.validate`, or any HMAC/JWT verification method occurs during this lookup, confirming the binding `attacker-guessed id == authenticated victim id` is accepted with zero cryptographic check.
