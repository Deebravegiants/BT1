### Title
Webhook shop identity spoofing — `shop-domain` header is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable content for HMAC verification from the raw request **body only**, while the `shop` identity used downstream for tenant dispatch is read from an **unauthenticated header**. Any actor who can obtain one genuine, validly-signed webhook payload from Shopify for the app (which any merchant who installs the app can trivially do, since the HMAC secret is the app's shared `client_secret`, identical across every shop install) can replay that exact body/HMAC pair to the app's webhook endpoint while forging the `shop-domain` header to name a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` / `validate_signature` verify the HMAC strictly against `verifiable_query.to_signable_string` (the body), never incorporating `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once the HMAC check passes and forwards the **unauthenticated** `request.shop` straight into `WebhookMetadata`, which is the value host applications use to route/scope the incoming payload to a tenant: [4](#0-3) 

This breaks the intended identity binding: **`shop` authenticated via HMAC == `shop` used to attribute/act on the webhook data**. In reality: `shop (HMAC-covered) = body only`, while `shop (used for tenant action) = header value chosen freely by whoever sends the HTTP request`.

Because the HMAC secret is the app's `client_secret`, which is identical for every shop that installs the app (not a per-shop secret), any legitimate merchant who installs the app can capture one authentic `(raw_body, hmac)` pair from a real Shopify-delivered webhook for their own shop. They can then POST that exact `raw_body` and `hmac` directly to the app's public webhook endpoint while substituting `shopify-shop-domain` (and `shopify-topic`, `shopify-webhook-id`) with a victim shop's domain and IDs of their choosing. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` dispatches the handler with `data.shop` set to the forged victim shop.

### Impact Explanation
This allows cross-tenant data injection/attribution: an unprivileged internet user (any merchant able to install the app on a throwaway shop) can make the host application believe attacker-controlled webhook data originated from an arbitrary other shop. Depending on how host apps use `WebhookMetadata#shop` (which the gem's own documentation and webhook registry design expects apps to trust for tenant scoping), this can be used to poison another tenant's records, trigger tenant-specific business logic, or otherwise cross tenant boundaries without ever compromising the victim's credentials — this matches the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any application built on this gem's webhook flow: obtaining a valid `(body, hmac)` pair requires nothing more than installing the app once (a normal, unprivileged action any developer/merchant can perform), and replaying it with a forged shop header is a single crafted HTTP request to the app's own public webhook endpoint — no TLS interception, leaked secrets, or privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-signature verification, or otherwise cryptographically tie the header-derived shop identity to the payload before it is handed to handlers — e.g., require the registered/expected shop to be supplied out-of-band by the host application and reject requests where the header-provided shop cannot be independently corroborated (for instance, only trust shop identity resolved via the session store keyed by data already verified through OAuth, rather than by trusting `request.shop` directly for tenant dispatch).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged onboarding flow).
2. Attacker triggers a webhook-eligible event (e.g., `orders/create`) on their own shop, causing Shopify to POST a genuine webhook to the app: raw body `B`, header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` (they own this shop and can freely capture their own traffic).
4. Attacker crafts a new HTTP POST directly to the app's public webhook endpoint with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged, still valid because `to_signable_string` only covers `B`, see `lib/shopify_api/webhooks/request.rb#L35-L38`)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - header `x-shopify-topic`, `x-shopify-webhook-id`: attacker's choice
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb#L12-L31`).
6. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though nothing about the request was ever authorized by or for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
