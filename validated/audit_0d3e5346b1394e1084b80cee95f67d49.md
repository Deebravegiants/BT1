### Title
Webhook `shop` header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` (used by `Registry.process`) checks the HMAC solely against that body. The `shop` value that is handed to the application's webhook handler is read straight from the `X-Shopify-Shop-Domain` header, which is never part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives the `shop` accessor purely from an HTTP header: [1](#0-0) 

The HMAC that this gem validates, however, is only computed over `@raw_body`: [2](#0-1) 

`Registry.process` validates that HMAC and then immediately forwards `request.shop` (the unauthenticated header) into `WebhookMetadata`, which is passed to the app's handler as the authoritative shop for that webhook: [3](#0-2) 

`WebhookMetadata` treats `shop` as a normal trusted field with no further validation: [4](#0-3) 

Compare this to `HmacValidator`, which computes the signature purely from `to_signable_string` and the app's `api_secret_key`: [5](#0-4) 

**Broken identity binding (as an equality):**
`shop_used_by_handler (request.shop, from unauthenticated header)` ≠ `shop_the_HMAC_was_actually_computed_for (implicit in the signed body, but never checked)`.

The signature only proves "this body was signed by Shopify with our app secret" — it proves nothing about which shop that body belongs to. An attacker who can obtain **any** validly-signed webhook body for **their own shop** (which is trivial — they install/uninstall the app on their own free/dev store and receive real, HMAC-signed webhook deliveries for known topics such as `app/uninstalled`, `orders/create`, etc.) can replay that exact body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop domain. Because the header is not part of `to_signable_string`, `HmacValidator.validate` will still succeed, and the handler will process it believing it originated from the victim shop.

### Impact Explanation
This breaks a tenant boundary: an unprivileged attacker (who only needs their own, unrelated shop's webhook credentials — obtainable at zero cost/privilege) can inject events attributed to a shop they do not control. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the tenant's session/access token, mark subscriptions, process `app/uninstalled` cleanup, or record customer-redact requests), this enables cross-tenant data corruption or triggering of privileged per-shop actions (deleting a victim's stored session/access token, marking a victim's app as uninstalled, injecting fake order data attributed to the victim) without ever compromising the victim. This satisfies the "cross-tenant access" Critical/High impact class since the boundary that should isolate shop A's webhook traffic from shop B is not authenticated.

### Likelihood Explanation
High. Any developer can freely create a Shopify development store, install the target app (or any Shopify webhook-consuming app), and passively capture a legitimately signed webhook (body + HMAC) for a controlled topic. Replaying that request with a forged `Shop-Domain`/`shop-domain` header against the app's public webhook endpoint requires no special access, no leaked secrets, and no interaction with the victim.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered signable content, or otherwise cryptographically bind the header to the body before trusting it. Concretely:
- Modify `ShopifyAPI::Webhooks::Request#to_signable_string` (or the validation call site in `Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` into what is verified, matching what Shopify actually signs, OR
- Independently verify the `shop-domain` header against session/tenant records the app already trusts before acting on it, rather than trusting the header verbatim once the body HMAC passes.

### Proof of Concept
1. Attacker creates their own Shopify store `attacker.myshopify.com` and installs the target app, subscribing it to `app/uninstalled` (or any registered topic).
2. Shopify delivers a real webhook to the app's endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over body>`
   - body: `{}` (or actual payload)
3. Attacker captures this exact request (body + HMAC unchanged) and replays it to the same endpoint, changing only:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` computes the HMAC only over the (unchanged) body via `HmacValidator.validate`, so verification succeeds. [3](#0-2) 
5. The app's `WebhookHandler#handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though Shopify never issued this webhook for `victim-shop.myshopify.com`.
