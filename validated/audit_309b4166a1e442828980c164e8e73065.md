### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` identity used downstream by `ShopifyAPI::Webhooks::Registry.process` is read from an HTTP header that is never included in the signed material. The equality the code implicitly assumes — "HMAC-verified sender" == "shop the payload is attributed to" — does not hold, because the `shop-domain` header can be swapped freely without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is pulled straight from the `shop-domain` header with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then, once that check passes, treats `request.shop` as trusted and forwards it to the handler as the authenticated tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `to_signable_string` (the body) matches the supplied HMAC using the app's `api_secret_key`; it says nothing about which shop the body belongs to: [4](#0-3) 

Because the header carrying the shop identity sits entirely outside the HMAC-covered bytes, the identity binding the gem implicitly asserts — `verified_bytes == acted_on_identity` — is false: the verified bytes are the body only, while the acted-on identity is an unauthenticated header value. Any request bearing a body/HMAC pair that is valid for the app's secret (e.g., captured from one legitimate webhook delivery, or a delivery an attacker can otherwise obtain/replay) can be resubmitted to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header. `Registry.process` will accept it and dispatch it to the app's handler as `WebhookMetadata` carrying that attacker-chosen `shop`, causing the host application to attribute the payload's data (order IDs, customer data, GDPR redact instructions, etc.) to a different, unrelated merchant.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: a payload that was HMAC-legitimate for shop A can be relabeled as belonging to shop B purely by changing an unauthenticated header, since `shop` is never part of the signed content. Host applications that key persistence, deduplication, or authorization decisions off `WebhookMetadata#shop` (as the gem's own tests and `docs` demonstrate is the intended usage) can be made to write or act on cross-tenant data, satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(body, hmac)` pair for the target app's secret — for example a webhook delivery captured off a public or shared endpoint, replayed from logs, or obtained via any channel other than knowledge of `api_secret_key` itself. Given that, no privileged credential, secret, or session is needed to remount it against the same endpoint with a forged `shop-domain` header, matching the "field acted on but not covered by the HMAC" analog class called out in scope.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed material, or otherwise re-derive/cross-check the tenant identity from a value that is covered by the HMAC (e.g., include the shop domain in the canonical signable string, or validate it against a shop already known to be associated with the specific webhook subscription/session before dispatching to the handler).

### Proof of Concept
1. Register a webhook handler for topic `orders/create` that persists `data.shop` alongside `data.body`.
2. Capture (or otherwise obtain) one legitimate webhook delivery: raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (valid for shop `victim.myshopify.com`).
3. Send a new request to the app's webhook endpoint with the same body `B` and header `H`, but with `x-shopify-shop-domain: attacker-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only re-hashes `B` against `H`; `Registry.process` dispatches `WebhookMetadata.new(shop: "attacker-shop.myshopify.com", body: parsed(B), ...)` to the handler, which now stores/acts on victim data under the attacker-controlled shop identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
