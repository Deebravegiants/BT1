## Title
Unauthenticated pipeline task resume endpoint allows arbitrary job-run manipulation - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `PATCH /v2/resume/:runID` route is registered in the completely unauthenticated route group and directly forwards a caller-supplied result into `App.ResumeJobV2`, with no session, API-token, or external-initiator check. This is structurally analogous to the reported `mintRebalancer`/`burnRebalancer` issue: a state-mutating operation (resuming/completing a pipeline task with attacker-controlled data) is exposed without any access-control modifier equivalent.

### Finding Description
In `core/web/router.go`, the resume route is mounted on the unauthenticated `v2` group, separate from the `authv2` group that wraps all other endpoints with `auth.Authenticate(...)`: [1](#0-0) 

The handler itself performs no additional authorization check before mutating the pipeline run: it parses `runID` as a UUID, decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, and passes it straight to `App.ResumeJobV2`: [2](#0-1) 

The audit log call itself is even named `audit.UnauthedRunResumed`, confirming the endpoint is intentionally reachable without authentication — the only implicit "secret" protecting it is the unguessability of the `runID` UUID, which is not a documented or enforced credential mechanism like the API token / external-initiator secret used everywhere else in the router.

### Impact Explanation
Whoever can guess or otherwise obtain a pending task's `runID` (e.g., via logs, error messages, monitoring dashboards, or a suspended/paused bridge task that leaks its ID) can inject arbitrary task results into a running pipeline, resuming it with attacker-controlled data. Depending on the job's pipeline (e.g., feeding an `ethtx` task, VRF fulfillment path, or other downstream task consuming the resumed value), this could cause corrupted data to be committed on-chain or cause a denial-of-service by resuming/erroring runs that shouldn't be touched by an external party. This mirrors the impact class of the referenced report: an unprivileged actor mutating protocol/application state with no authorization gate.

### Likelihood Explanation
Exploitation requires the attacker to know or guess a valid pending `runID` (a UUIDv4), which is a non-trivial but not impossible constraint (IDs can leak via node logs, external monitoring integrations, or race conditions where the ID is exposed before the task naturally resumes). Given the endpoint is deliberately not authenticated (as evidenced by the `UnauthedRunResumed` audit event and its placement in the `unauthedv2` group), the design assumes the UUID is a sufficient bearer secret — but there is no rate limiting or additional hardening visible at this route, and no confirmation that `runID` values are always generated and transmitted only over authenticated/trusted channels.

### Recommendation
- Verify whether `runID` is intended to act as a bearer secret; if so, ensure it is generated with sufficient entropy, never logged/exposed in unauthenticated responses, and rate-limit/throttle guesses on this endpoint.
- If the intended callers of this endpoint are internal only (e.g., bridge adapters resuming a previously-suspended task), consider adding an explicit authentication mechanism (e.g., a per-task secret token issued when the task is suspended) instead of relying solely on UUID unguessability.
- At minimum, add logging/alerting on repeated failed or suspicious resume attempts and confirm this design decision is documented and intentional, since it is a deviation from the authentication pattern applied to every other `/v2` route.

### Proof of Concept
1. Trigger any job with a task capable of suspending the pipeline run (e.g., a bridge task) and observe/obtain the resulting `runID` (e.g., via logs, timing side channels, or if it is exposed in any semi-trusted interface).
2. As an unauthenticated client, send:
   ```
   PATCH /v2/resume/<runID>
   Content-Type: application/json

   {"error": null, "value": "<attacker-controlled-serialized-value>"}
   ```
3. Observe that the server accepts the request (HTTP 200) without any authentication header, and `App.ResumeJobV2` is invoked with the attacker-supplied result, resuming the pipeline run with data the attacker controls, as confirmed by the code path in [3](#0-2) .

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
