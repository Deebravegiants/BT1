## Title
Fee-on-transfer / non-standard token amounts are escrowed using nominal `order.inputs` values instead of actual received balance in Tron's `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits escrow (`_orders[commitment][token]`) using the nominal `reducedInputs[i].amount` (derived directly from the user-specified `order.inputs[i].amount`), while the actual token amount received from `safeTransferFrom` may be smaller for fee-on-transfer, rebasing, or other non-standard ERC20 tokens. This is the same class of bug as the reported Allo V2 issue where `poolAmount`/escrow accounting is derived from the nominal transfer amount rather than the contract's real token balance.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` pulls tokens with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally records `_orders[commitment][token] += reducedInputs[i].amount` — both derived from the *requested* `order.inputs[i].amount`, not from a before/after balance measurement: [1](#0-0) 

The predispatch branch has the same flaw: it computes `dust = balance - requiredAmount` for events, but still stores `reducedInputs[i].amount` (nominal, fee-blind) into escrow rather than the amount actually swept back into the contract: [2](#0-1) 

This directly parallels the reported Allo V2 defect where `_fundPool` passes `amountAfterFee` to `increasePoolAmount`, and `poolAmount` becomes disconnected from the strategy's real `balanceOf`. Here, `_orders[commitment][token]` plays the role of `poolAmount`: it is meant to be a source of truth for how much of a given token is escrowed for an order and is later used to pay solvers/beneficiaries on redemption or refund on cancel.

Notably, the primary EVM implementation of the same contract was hardened against exactly this class of bug: `evm/src/apps/IntentGatewayV2.sol` measures `balBefore`/`balanceOf` deltas after each `safeTransferFrom` and rewrites `order.inputs[i].amount` to the actual received amount before computing `reducedInputs` and the commitment: [3](#0-2) [4](#0-3) 

This fix (and its associated fee-on-transfer tests) is entirely absent from the Tron contract, confirming the Tron deployment regressed to the vulnerable pattern that the report describes.

### Impact Explanation
Because `_orders[commitment][token]` can be credited with more than the contract's actual `balanceOf(token)`, the escrow ledger for one order can claim tokens that were never actually received — tokens that, in reality, belong to (or are needed by) other orders' escrows sharing the same pooled contract balance. When a solver fills the order and the escrow is redeemed (transferring `_orders[commitment][token]` worth of tokens to the solver/beneficiary) or the order is cancelled and refunded, the contract may attempt to pay out more than it actually holds for that token, causing either: (a) reverts that permanently strand legitimate escrowed funds for the affected order (denial of settlement/refund), or (b) insolvency across pooled escrows where honoring one inflated claim consumes token balance that rightfully belongs to a different order's depositor, resulting in loss of funds for other users. This satisfies the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Any ERC20 with a transfer fee, rebasing behavior, or blacklist/deflationary mechanics used as an order input token on the Tron deployment triggers this immediately and deterministically on every `placeOrder` call — no privileged role or special conditions are required, only a single unprivileged `placeOrder` transaction with such a token. Given IntentGatewayV2 is explicitly designed to support arbitrary caller-supplied ERC20 tokens (as evidenced by the fee-on-transfer test suite added for the main EVM contract), this is a realistic, reachable condition for the Tron deployment.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol` (measure `balanceOf` before/after each `safeTransferFrom`/predispatch sweep, and use the actually-received amount to derive `reducedInputs` and populate `_orders[commitment][token]`) in the Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol`, and add the equivalent fee-on-transfer regression tests that exist for the main EVM version.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and a fee-on-transfer ERC20 (e.g. 1% fee) as an input token.
2. User calls `placeOrder` with `order.inputs[0].amount = 1000e18` for the fee-on-transfer token.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but due to the 1% fee the contract's actual balance only increases by `990e18`.
4. `_orders[commitment][token] += reducedInputs[0].amount` stores a value derived from `1000e18` (minus only the protocol fee, if any) — i.e. up to `1000e18`, exceeding the `990e18` actually held.
5. On `cancelOrder`/refund or on `RedeemEscrow` processing for this commitment, the contract attempts to transfer the escrowed (inflated) amount, either reverting (freezing funds for this order) or depleting shared pooled token balance belonging to other orders (fund loss for other users), exactly as demonstrated by the passing fee-on-transfer tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`) that exist only for the fixed main EVM contract and would fail against this Tron code path: [5](#0-4)

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
