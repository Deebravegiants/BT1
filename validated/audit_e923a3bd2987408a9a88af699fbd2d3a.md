### Title
Webhook shop-domain spoofing via HMAC that only covers the request body, not the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identity) from the `X-Shopify-Shop-Domain` header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body via `to_signable_string`. Any party that can obtain one genuinely-signed webhook payload for the app (e.g., by installing the app on their own store) can replay that body with a forged `shop-domain` header pointing to a different merchant, and it will pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the (attacker-controlled) HTTP header and is not part of that signable string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which only proves the body was signed with the app's `api_secret_key`, and then unconditionally trusts `request.shop` to build the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm this: it only ever signs/compares `verifiable_query.to_signable_string`, never any header value: [4](#0-3) 

Because a single app-level `api_secret_key` is shared across every merchant that installs the app, an attacker who installs the target app on their own store will receive Shopify webhooks with a valid HMAC computed from that same secret. The attacker can then capture the raw body + HMAC pair from their own legitimate webhook delivery and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` will still succeed because it never inspects the shop header, so `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain despite the payload never having originated from — or being authorized by — the victim.

This is the binding break: the equality the library implicitly claims is `hmac_valid(body) == shop_is_authentic`, but the actual equality enforced is only `hmac_valid(body) == body_was_signed_with_api_secret_key`, with `shop` left completely unauthenticated.

### Impact Explanation
This breaks tenant isolation for any host application that uses `request.shop`/`WebhookMetadata.shop` from this gem to key data (order processing, GDPR redaction, inventory sync, uninstall handling, etc.) without independently re-verifying the shop. An attacker with only an unprivileged install of the target app on their own shop can cause the app to process forged webhook events "as" an arbitrary other merchant, i.e., cross-tenant access/manipulation using only body+HMAC material they legitimately possess for their own tenant.

### Likelihood Explanation
Likelihood is high for any deployment: no access token, `client_secret`, or privileged credential is required beyond simply installing the target Shopify app (which is the normal, unprivileged path any internet user can take), and the request is trivial to craft (HTTP request with a modified header).

### Recommendation
Include `shop` (and ideally `topic`) in the HMAC-signed material, or otherwise cryptographically bind the header value to the signature Shopify computes, rather than relying on the header being trustworthy on its own. Documentation/consumers should also be told to independently correlate `shop` with a session/installation record rather than treating it as verified by `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook, e.g. `orders/create`, to the app: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays this exact request to the same endpoint, but rewrites the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, keeping body `B` and HMAC `H` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (`B`) — matches `H`, validation passes.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on data as if it came from `victim-shop.myshopify.com`, even though nothing about the request was authorized by or originated from that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
