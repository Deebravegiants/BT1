## Title
`object::transfer` allows an object to become owner of itself, permanently bricking any object-held assets - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
The Aptos `object` module's ownership-transfer path (`object::transfer` / `object::transfer_call` → `transfer_raw` → `transfer_raw_inner`, guarded by `verify_ungated_and_descendant`) does not reject a transfer whose destination address is the object's own address. When an object owner calls `transfer(owner, object, object.object_address())`, the transfer succeeds and sets `ObjectCore.owner` to the object's own address, creating a self-owned object. Because no signer can be produced for that address afterward (short of a previously-generated `ExtendRef`), the object — and any assets held at that address (a `FungibleStore`, nested sub-objects, or other resources) — become permanently uncontrollable. This is the direct Aptos analog of the Wormhole NTT bug: a normal, unprivileged, legitimate-looking operation (setting a "destination" equal to "self") is not rejected even though the protocol logic implicitly assumes the destination is distinct from the source, and the result is irrecoverable custody loss.

### Finding Description
`object::verify_ungated_and_descendant` is meant to prevent transferring an object into a destination that (directly or transitively) is or is owned by the object itself, so as to prevent creating unreachable ownership cycles: [1](#0-0) 

However, when `destination == object` (i.e., you transfer object `O` to `O`'s own address), the check is trivially satisfied on the *first* call:
- `current_address = destination = O`
- `object.owner` is read as the object's *current* owner (still the real owner, e.g. `creator`, since the transfer hasn't happened yet)
- the `while (owner != current_address)` loop compares `owner` (`creator`) against `current_address` (which was just reassigned to `object.owner`, i.e. `creator`) — so the loop body never executes and the function returns without aborting.

`transfer_raw_inner` then unconditionally applies the write: [2](#0-1) 

This sets `ObjectCore.owner = O` (the object address itself). The publicly callable entry points that reach this code are: [3](#0-2) 

The bug is unintentionally demonstrated by the framework's own test, which shows the *first* self-transfer succeeds silently and only the *second* call (now walking a genuine infinite non-terminating owner chain) aborts due to exceeding `MAXIMUM_OBJECT_NESTING`: [4](#0-3) 

After the first (successful) self-transfer, the object's owner field equals the object's own address. To move, burn, or otherwise administer the object (or extract fungible/token assets stored under that address) afterward, a `signer` for that address is required. The only way to obtain such a signer post-creation is via a previously generated `ExtendRef`; `object::transfer` itself provides no way to produce one. If the caller does not already hold an `ExtendRef` for that object (the common case for simple owned objects, primary fungible stores holding assets, NFTs, etc.), the object and everything it holds become permanently inaccessible — no owner signer can ever be reconstructed.

### Impact Explanation
This meets the custody impact gate: it is a **permanent, non-recoverable loss of object-held value**. Any assets that live at the object's own address — for example a `FungibleStore` resource co-located under the object (as used by `primary_fungible_store` derived stores or custom `Object<FungibleStore>` deployments), nested/child objects transitively owned through this object, or NFTs/tokens whose metadata object is transferred to itself — become permanently frozen because no signer for that address can ever be produced again. This is a direct violation of the custody invariant that "object creation, transfer, burn, extensibility, and ownership refs must preserve the intended controller" — here the controller becomes an address that can never sign again.

### Likelihood Explanation
The trigger is a single, unprivileged, standard call to the public entry function `object::transfer` (or `transfer_call`) by the object's rightful owner, with the destination address set equal to the object's own address — analogous to a peer/config value accidentally equal to "self" in the source report. This can happen via a scripting/tooling mistake (e.g., passing the object's own address as the recipient), a malicious front-end, or a buggy integration that computes "self" and "target" identically. No governance/admin privilege escalation or third-party dependency is needed; the owner of any object can trigger this on their own object using only standard framework APIs.

### Recommendation
Add an explicit check in `transfer_raw` / `verify_ungated_and_descendant` (or at the top of `transfer_raw`) that aborts if `to == object` (self-transfer), independent of the cyclic-ownership loop, mirroring the mitigation recommended in the source report ("prevent owners from setting the destination equal to the source/self"). This closes the loophole where the loop's boundary condition trivially passes because the pre-transfer owner value is read before mutation.

### Proof of Concept
The framework's existing test already demonstrates the vulnerable state transition (only annotated as testing the *second* call's failure, not flagging that the *first* call silently succeeds and corrupts ownership):

```move
#[test(creator = @0x123)]
#[expected_failure(abort_code = 131078, location = Self)]
fun test_cyclic_ownership_transfer_should_fail(creator: &signer) {
    let obj1 = create_simple_object(creator, b"1");
    // This call SUCCEEDS: obj1.owner becomes obj1.object_address() itself.
    transfer(creator, obj1, obj1.object_address());
    // Only the *second* call fails, once the object is already unrecoverable.
    transfer(creator, obj1, obj1.object_address());
}
``` [4](#0-3) 

To turn this into a concrete fund-loss PoC: create an object, move a `FungibleStore`/`Coin`-holding resource under it via `move_to(&constructor_ref.generate_signer(), ...)` without retaining an `ExtendRef`, then call `object::transfer(owner, obj, obj.object_address())` once. After this call, `object::owner(obj) == obj.object_address()`; any subsequent attempt to withdraw/transfer/burn using the original owner's signer will fail with `ENOT_OBJECT_OWNER`, and there is no way to reconstruct a signer for `obj.object_address()`, permanently locking the held assets.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
```
