### Title
Webhook shop-domain identity not bound to HMAC signature, enabling cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, but the `shop` value that is handed to the app's webhook handler (and that many apps use to select the tenant/session to act on) is read from an HTTP header that is never included in the signed material. Because the HMAC secret (`api_secret_key`) is a single app-level secret shared across every merchant that has installed the app, any merchant with the app installed can capture one legitimate, validly-signed webhook delivery from their own store and replay it with the `shop-domain` header rewritten to a different (victim) shop, producing a request that passes this gem's validation while claiming to originate from a tenant the attacker does not control.

### Finding Description
`Webhooks::Registry.process` validates authenticity with `Utils::HmacValidator.validate(request)` and, if it passes, immediately constructs `WebhookMetadata` using `request.shop` and hands it to the app's handler: [1](#0-0) 

The HMAC validator recomputes the signature only over `to_signable_string`, and for the webhook `Request` class this returns `@raw_body` — the header fields are excluded entirely: [2](#0-1) 

`request.shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, with no cross-check against the signed body or against any allow-list of shops known to the app: [3](#0-2) 

The validator itself only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, so it can never detect that the `shop` header was altered, since that header isn't part of `to_signable_string`: [4](#0-3) 

This breaks the identity binding: `shop_authenticated_by_HMAC == shop_delivered_to_handler` does not hold. The equality that should be enforced — the shop asserted by the header equals the shop the (single, app-wide) HMAC secret was actually used to sign for — is never checked, because the secret is not shop-specific and the header is not covered by the signature. `WebhookMetadata.shop` is the exact field the gem's own documentation tells developers to use as the tenant identifier when dispatching background work: [5](#0-4) 

### Impact Explanation
Since `api_secret_key` is one shared secret for the whole app (not per-shop), any of the app's own merchants is an "unprivileged" party with respect to every other merchant's data. Such a merchant can obtain one authentic, validly-HMAC'd webhook delivery from their own store (trivial — they just need to run the app), then resend the identical raw body/HMAC pair while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop domain. `Registry.process` will pass HMAC validation and dispatch the handler with `WebhookMetadata#shop` set to the victim's domain. Any app that uses `data.shop` to select which merchant's session/record to update (the exact pattern shown in this gem's own docs and breaking-changes notes) will perform actions attributed to, or scoped to, a shop the attacker does not control — i.e., cross-tenant access/write. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, unprivileged install of the target app on their own store — no access to `api_secret_key`, no TLS interception, no social engineering. Capturing one's own valid webhook delivery and replaying it with a modified header is straightforward with any HTTP tool. The likelihood is bounded only by whether a given host application trusts `WebhookMetadata#shop` for tenant selection, which this gem's own documentation actively encourages.

### Recommendation
Include the shop domain (and other identity-bearing headers such as `topic`) inside the HMAC-signed material, or otherwise verify that the shop claimed in the header matches a shop the app expects for this specific `access_token`/session context before dispatching to the handler. At minimum, document/require that the header value be cross-checked against a known registered shop-topic pairing rather than trusted verbatim once the body-only HMAC passes.

### Proof of Concept
1. App installs the target Shopify app on `attacker-shop.myshopify.com`; the app's webhook endpoint receives a real delivery:
   - headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body: `{"id":1}`
2. Attacker resends the identical body and HMAC header, but changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. Using the gem:
   ```ruby
   ShopifyAPI::Webhooks::Registry.process(
     ShopifyAPI::Webhooks::Request.new(raw_body: '{"id":1}', headers: {
       "x-shopify-topic" => "orders/create",
       "x-shopify-hmac-sha256" => "<same-valid-hmac>",
       "x-shopify-shop-domain" => "victim-shop.myshopify.com",
     })
   )
   ```
4. `Utils::HmacValidator.validate` succeeds (it only checks the body/secret, per `lib/shopify_api/utils/hmac_validator.rb:12-31`), and the handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the request never touched the victim's store.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
