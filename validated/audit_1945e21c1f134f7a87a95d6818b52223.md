The `Request#to_signable_string` (used by `HmacValidator.validate`) covers only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and passed unmodified into the `WebhookMetadata` object handed to the app's handler.### Title
Webhook shop/topic/id metadata is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies authenticity of an inbound webhook using only the HMAC over the raw JSON body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler are read directly from unauthenticated HTTP headers. This breaks the intended binding `HMAC-covered-data == data-acted-on`, mirroring the reported bug class where a security-relevant field (`EntryPoint`) is excluded from the value that is actually verified.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers, which are not part of the HMAC-signed data at all: [3](#0-2) 

`Registry.process` trusts these header-derived values unconditionally after validating only the body's HMAC, then forwards them to the app's registered handler: [4](#0-3) 

The equality that should hold is:
`bytes verified by HMAC == bytes/fields the handler acts on (shop, topic, webhook_id, api_version)`

In this implementation that equality is false: the HMAC only ever covers `@raw_body`, while `shop`/`topic`/`webhook_id`/`api_version` — the exact fields the documentation says handlers should use to route/attribute work per-tenant (`data.shop`, used to `perform_later(topic: ..., shop_domain: data.shop, ...)`) — are unauthenticated header values.

### Impact Explanation
Any unprivileged internet user who can obtain one legitimately-signed webhook body/HMAC pair (e.g., a request their own developer/test store received, or one intercepted from a shared/public endpoint) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. Because the HMAC never covers the shop header, the signature check in `HmacValidator.validate` still passes, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain while the body content is the original (different) shop's real data. Any app that uses `data.shop` from the webhook to select the tenant's database record, ignore-list, or job queue (as the gem's own documentation recommends: "`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`") will process/attribute another tenant's payload data under a different shop's identity — a cross-tenant data-confusion condition rooted entirely in this gem's unauthenticated header trust.

### Likelihood Explanation
The `topic`, `shop-domain`, `webhook_id`, and `api_version` headers are trivial to set on any HTTP POST to the webhook endpoint, and the webhook endpoint is a public, unauthenticated HTTP route by design (Shopify calls it directly). No secret, token, or privileged access is required — only knowledge of one previously-issued (raw_body, HMAC) pair, which is not treated as confidential by design (it's delivered over the public internet to the merchant's server). This is a systemic property of the gem's design (`Request#to_signable_string` hard-codes body-only signing) rather than a host-application misuse, since the gem is the one that manufactures `WebhookMetadata` from unauthenticated headers and presents it to handlers as trusted.

### Recommendation
Bind the header-derived identity fields into the value that is HMAC-verified, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the signed payload before constructing `WebhookMetadata`. At minimum:
- Cross-validate the `shop-domain` header against a shop identifier embedded in the signed body (e.g., compare to `body["shop_domain"]` / `body["myshopify_domain"]`/tenant id if available in the payload), rejecting mismatches.
- Consider incorporating the relevant headers into the signable string used for HMAC verification (following Shopify's guidance on binding headers when available) or require a per-request nonce validated against the shop's session/subscription registration.
- Document clearly that `WebhookMetadata#shop` is unauthenticated relative to the body signature so host applications do not use it as a sole tenant-selection key without additional verification.

### Proof of Concept
```ruby
# 1. Attacker captures/replays one legitimate webhook delivery for VICTIM store,
#    body: '{"id":1,"note":"secret order data"}', signed with the real api_secret_key.
raw_body = '{"id":1,"note":"secret order data"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# 2. Attacker POSTs the exact same body+hmac to the app's webhook endpoint,
#    but swaps the shop-domain header to a shop they control ("attacker-shop.myshopify.com").
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),      # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com", # forged, NOT covered by HMAC
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation passes because it only checks raw_body against the secret.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(topic: "orders/create",
#                                          shop: "attacker-shop.myshopify.com",  # attacker-controlled
#                                          body: {"id"=>1, "note"=>"secret order data"}, # victim's real data
#                                          ...))
```
The handler receives the victim's real order payload tagged with the attacker's shop domain, since nothing in `Request` or `Registry.process` binds `shop` to the HMAC-signed `raw_body`. [4](#0-3) [5](#0-4)
