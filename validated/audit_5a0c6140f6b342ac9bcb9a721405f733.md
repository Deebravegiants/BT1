### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant spoofing of the shop bound to webhook data - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop identity for a webhook exclusively from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC that `Registry.process` verifies is computed only over the raw request body. The `shop` field is acted upon (passed to the app's `WebhookHandler#handle` as trusted tenant identity) without being part of the signed payload, breaking the intended binding `hmac == HMAC(secret, body_bound_to_shop)`.

### Finding Description
`Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the shop identity is not included in the signed string at all: [3](#0-2) 

Yet immediately after this HMAC check succeeds, `request.shop` (read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with zero cryptographic binding) is forwarded to the app's handler as the authoritative tenant identifier: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
```
HMAC(secret, signed_bytes) valid  ⇒  signed_bytes fully determine (topic, shop, body)
```
Here, `signed_bytes` = raw body only, so the equality that actually holds is:
```
HMAC(secret, body) valid  ⇒  body is authentic (from *some* shop using *this app's* shared secret)
```
`shop` is outside `signed_bytes`, so an attacker can vary `shop` freely while keeping `hmac` valid, as long as they can supply any legitimately-signed `(body, hmac)` pair — which is possible because Shopify uses the **same `api_secret_key` for every shop that has installed the app**. Any merchant/attacker who has installed the target app on their own store legitimately receives real webhook deliveries with valid `(body, hmac)` pairs signed by the shared `api_secret_key`. That attacker can then send an HTTP request directly to the app's webhook endpoint, keeping the intercepted valid `body`/`hmac-sha256` header, but substituting an arbitrary victim's `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still return `true` (the body/hmac pair is unchanged and valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the gem hands the consuming app a `shop` value with the full trust implied by "HMAC verified," but that value was never actually authenticated. Any app that uses `WebhookMetadata#shop` (the documented, gem-provided value) to key per-tenant storage, invalidate/rotate a specific merchant's data, or make authorization decisions can be tricked into applying attacker-controlled body content to a different, victim shop's tenant record — i.e., cross-tenant data injection/corruption via this gem's own trusted API surface. This matches the Critical "cross-tenant access" impact category, since the vulnerability lives entirely in the gem's `Request`/`Registry`/`HmacValidator` handling and does not require the host app to do anything unusual — it is simply relying on the documented `WebhookMetadata.shop`.

### Likelihood Explanation
Exploitation only requires: (1) the attacker be a merchant who has installed the target app (a normal, unprivileged step available to any internet user for public apps), giving them a stream of validly-signed webhook `(body, hmac)` pairs from their own store, and (2) the ability to send a raw HTTP POST to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header — no access to `api_secret_key`, tokens, or TLS interception needed. This is straightforward and repeatable, making likelihood high.

### Recommendation
Bind the shop identity (and topic) cryptographically into the value that is HMAC-verified, or otherwise cross-check it against an out-of-band authenticated source (e.g., verify the `shop` header value against the destination the webhook was registered for, or include the header in the canonical signed string used by `to_signable_string`, mirroring how `AuthQuery` includes `shop` in its own `to_signable_string`). At minimum, document/enforce that `WebhookMetadata#shop` is unauthenticated and must be revalidated by the host app against its own stored per-shop webhook secret/session before being trusted, or change `Request#to_signable_string` to include the shop-domain header content so a mismatch invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving genuine webhook deliveries with valid `X-Shopify-Hmac-Sha256` values computed with the app's shared `api_secret_key` (any topic/body works, e.g. `orders/create`).
2. Attacker captures one such delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - Body: same `B` (unmodified, so the signature stays valid)
   - Headers: `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Topic: orders/create`, `X-Shopify-Api-Version: <valid>`, `X-Shopify-Webhook-Id: <any>`, and `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (any other shop using the app).
4. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`, which calls `Utils::HmacValidator.validate(request)` — this passes because it only checks `B` against `H`, per `Webhooks::Request#to_signable_string` returning `@raw_body`. [6](#0-5) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, even though the body content and shop have no cryptographic relationship — the handler processes attacker-controlled data as though it belonged to `victim-shop`. [7](#0-6)

          received_signature = verifiable_query.hmac

        end
