Audit Report

## Title
Discordant/stale OIDC role caching in `oidc_sessions` and `oidc_user_api_tokens` with no upstream resync (privilege persists after downgrade) - ([File: core/sessions/oidcauth/oidc.go])

## Summary
The OIDC authenticator caches the RBAC role derived from the identity provider's ID-token claims into `oidc_sessions` (and `oidc_user_api_tokens` for API tokens) at creation time, and never re-validates it against the identity provider afterward. Unlike LDAP's `core/sessions/ldapauth/sync.go`, which runs `LDAPServerStateSyncer.Work` to periodically re-query the upstream directory and rewrite/purge stale roles, OIDC's only background job, `reaper.go`, purely deletes rows past a time threshold and never touches `user_role`.

## Finding Description
`handleTokenExchange` derives a role once from ID-token claims and inserts it into `oidc_sessions.user_role` at login [3](#0-2) . `AuthorizedUserWithSession` and `FindUserByAPIToken` subsequently trust that cached role for the full session/token lifetime without any upstream re-check [4](#0-3) . The in-code comment in `FindUserByAPIToken` claims this is safe due to "the UpstreamSyncInterval config and reaper.go sync implementation," but this is demonstrably false: the `OIDC` config interface in `core/config/web_config.go` (lines 58-71) has no `UpstreamSyncInterval()` method at all — only the `LDAP` interface does (line 54) [5](#0-4) . `reaper.go`'s `Work`/`deleteStaleSessions` only performs `DELETE FROM oidc_sessions WHERE created_at < $1`, with zero role-resync logic [2](#0-1) . This contrasts with LDAP's `sync.go`, which explicitly re-queries upstream group membership and issues `UPDATE ldap_sessions SET user_role = CASE ... END` for existing sessions.

## Impact Explanation
If an OIDC user's group membership is revoked/downgraded at the identity provider, their existing session or API token retains the old higher-privileged role for the remainder of `SessionTimeout` or `UserAPITokenDuration` (default up to 240h), granting continued unauthorized access to privileged node APIs (job management, key operations, config changes) after the operator believed access was revoked. This maps to the "node API authentication/role bypass" impact category.

## Likelihood Explanation
This requires OIDC authentication to be enabled (an opt-in configuration, `WebServer.AuthenticationMethod = 'oidc'`) and does not require any bug-triggering action by the victim — it's a deterministic architectural gap: revocation at the IdP is a normal, expected admin operation, and the node will not honor it until natural session/token expiry. This is a realistic operational scenario (e.g., offboarding), and once OIDC is configured, the behavior is 100% reproducible.

## Recommendation
Add an OIDC analog to `LDAPServerStateSyncer` (`core/sessions/ldapauth/sync.go`) that periodically re-verifies each active `oidc_sessions`/`oidc_user_api_tokens` entry's role against the identity provider (e.g. via refresh token + userinfo/claims re-check), purging or downgrading entries whose upstream membership can no longer be confirmed. At minimum, correct the misleading comment in `oidc.go` and/or drastically shorten default cache lifetimes for OIDC-authenticated sessions/tokens.

## Proof of Concept
1. Configure the node with `WebServer.AuthenticationMethod = 'oidc'`, mapping `NodeAdmins` claim group to the Admin role.
2. `alice@example.com`, a member of `NodeAdmins`, logs in via `/oidc/login`/token exchange; `handleTokenExchange` inserts a row into `oidc_sessions` with `user_role = 'admin'` (`core/sessions/oidcauth/oidc.go:233-260`).
3. The IdP admin removes alice from `NodeAdmins` — no corresponding action occurs on the chainlink node.
4. Alice's existing session cookie continues to resolve via `AuthorizedUserWithSession` (`oidc.go:351-391`) to `Role: admin` until `SessionTimeout` naturally elapses (or up to `UserAPITokenDuration` for API tokens), since no code path re-verifies the role against the IdP or a syncer.
5. Alice performs admin-only operations on the node despite being revoked upstream, demonstrating the stale-role bypass. A Go integration test can assert this by manually inserting an `oidc_sessions` row with an outdated role and confirming `AuthorizedUserWithSession` returns it unchanged regardless of IdP state.

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
