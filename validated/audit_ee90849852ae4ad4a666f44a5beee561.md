### Title
`describeWithdrawal` cross-matches same-asset batch withdrawals by `assetId` only, misreporting `txHash`/status - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status of a specific batch index by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which matches purely on `assetId` (`nep141:${w.data.near_token_id}`) and ignores `destinationAddress`/`amount`. When a batch withdrawal contains two entries with the same `assetId` (e.g., two `nep141:btc.omft.near` withdrawals to different addresses), both `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` can resolve to the same matched record — the first one found by `Array.find` — causing one withdrawal's `txHash`/status to be reported for the wrong index.

### Finding Description
The broken equality: `describeWithdrawal({index: i}).txHash` should equal the `transfer_tx_hash` of the withdrawal whose `data.address`/`data.amount` correspond to `withdrawalParams[i].destinationAddress`/signed amount. After tracing the code, this equality does **not** hold when duplicate `assetId` entries exist in a batch.

Code path: `poa-bridge.ts:313-343` `describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` at line 319-322, and `findMatchingWithdrawal` (lines 418-427) does:
```
return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
``` [1](#0-0) 
This is the same pattern duplicated in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:144-153`.

The root cause is explicitly acknowledged in the code's own comment: "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported. POA API doesn't currently support this case either." [2](#0-1) 

Attacker input: a batch `WithdrawalParams[]` where two entries share the same `assetId` but different `destinationAddress`/`amount`, submitted via `sdk.processWithdrawal` (or `signAndSendWithdrawalIntent` + `waitForWithdrawalCompletion`). Batching is a fully supported, documented feature with no uniqueness constraint on `assetId` across entries — `createWithdrawalIdentifiers` in `withdrawal-watcher.ts:80-107` only tracks per-bridge-route indexes, not per-asset indexes, and does not reject or dedupe same-asset entries. [3](#0-2) 

Exploit flow:
1. Attacker (an ordinary user with their own funds) submits a batch withdrawal with two entries of the same `assetId`, different `destinationAddress` values (e.g., attacker's own two wallets, or one belonging to a counterparty relying on the integrator).
2. Intent settles on NEAR; PoA bridge processes both withdrawals, producing two `withdrawals[]` records in `getWithdrawalStatus`, potentially returned unsorted (per PoA's own indexing, not guaranteed to align with request order).
3. `waitForWithdrawalCompletion` calls `bridge.describeWithdrawal({index: 0, withdrawalParams: params[0], ...})` and `describeWithdrawal({index: 1, withdrawalParams: params[1], ...})`.
4. Both calls invoke `findMatchingWithdrawal` with the same `assetId`, which returns the **same** array element (`Array.find` returns the first match) or, depending on when each completes, the wrong one — decoupling reported `txHash` from the destination that was actually signed for that index.

Existing guards do not catch this: `validateAddress`/`compareAddresses` validate address format/collision with token contract, not batch-entry uniqueness; `supports()` and `assert` checks only validate individual asset/route compatibility; nothing in `sdk.ts`'s `processWithdrawal`/`waitForWithdrawalCompletion` orchestration enforces per-batch `assetId` uniqueness. The intents contract's own signature/nonce verification is unaffected since the on-chain funds transfer for each entry is still correct (correct address gets correct amount on-chain) — the bug is purely in the SDK-side off-chain **status reporting**, causing an integrator to misattribute the `txHash` to the wrong withdrawal index.

### Impact Explanation
The party harmed is the integrator (and any counterparties relying on it) that maps `destinationTx[index]` to a specific business record (e.g., crediting an order, releasing an escrow) — this is exactly the "status or hash misreport making an integrator credit or refund twice" category in the Rules (High). It is repeatable for every same-asset batch submitted while the POA bridge API doesn't provide unambiguous per-withdrawal identification. The underlying on-chain transfer is not misrouted (funds still go to the correct signed destination address), but the SDK's reported mapping of `index -> txHash` can be swapped, causing an integrator to believe withdrawal 0 completed with a hash that actually belongs to withdrawal 1 (or vice versa), risking wrongful crediting/double-crediting in downstream systems.

### Likelihood Explanation
Preconditions are trivial to satisfy: any unprivileged user can submit a batch withdrawal with two entries sharing the same PoA-bridged `assetId` — this is a documented, first-class SDK feature (see `README.md` "Batch Withdrawals" section) with no explicit restriction against duplicate assets. [4](#0-3)  No special timing or race is required beyond the PoA API returning an unsorted `withdrawals` array (acknowledged as a real possibility in the code comment itself). Attacker cost is minimal (one intent, two withdrawal legs). This is fully repeatable per batch.

### Recommendation
Either (a) reject/validate batches at the SDK level that contain duplicate `assetId` entries destined for the PoA bridge (throwing a clear `UnsupportedBatchWithdrawalError`) until the PoA API supports disambiguation, or (b) extend `findMatchingWithdrawal` to also match on `destinationAddress` (and ideally `amount`), and when multiple withdrawals share `assetId`, deterministically sort both the local `withdrawalParams` list and the API's `withdrawals` response by a stable key (e.g., amount, since fees are equal for same-token entries as the code comment suggests) before pairing by relative order, and fail closed with `status: "pending"` (or a dedicated ambiguous-match error) rather than silently returning a possibly-wrong record when more than one candidate matches.

### Proof of Concept
```typescript
// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.duplicate-asset.test.ts
import { describe, it, expect, vi } from "vitest";
import { poaBridge } from "@defuse-protocol/internal-utils";
import { PoaBridge } from "./poa-bridge";

describe("PoaBridge.describeWithdrawal - duplicate assetId in batch", () => {
  it("misreports txHash when two withdrawals share the same assetId", async () => {
    const bridge = new PoaBridge({ envConfig: /* poaTokenFactoryContractID set */, xrplRpcUrls: [] });

    const withdrawalParams0 = { assetId: "nep141:btc.omft.near", amount: 100n, destinationAddress: "addrA" };
    const withdrawalParams1 = { assetId: "nep141:btc.omft.near", amount: 200n, destinationAddress: "addrB" };

    vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
      withdrawals: [
        { status: "COMPLETED", data: { near_token_id: "btc.omft.near", address: "addrB", amount: "200", transfer_tx_hash: "hashForB" } },
        { status: "COMPLETED", data: { near_token_id: "btc.omft.near", address: "addrA", amount: "100", transfer_tx_hash: "hashForA" } },
      ],
    });

    const result0 = await bridge.describeWithdrawal({
      landingChain: "eip155:1" as any,
      index: 0,
      withdrawalParams: withdrawalParams0,
      tx: { accountId: "x.near", hash: "near-tx-hash" },
    });

    const result1 = await bridge.describeWithdrawal({
      landingChain: "eip155:1" as any,
      index: 1,
      withdrawalParams: withdrawalParams1,
      tx: { accountId: "x.near", hash: "near-tx-hash" },
    });

    // EXPECTED (broken today): result0.txHash should equal the tx hash whose
    // data.address === withdrawalParams0.destinationAddress ("addrA" -> "hashForA")
    // and result1.txHash should equal the one for "addrB" -> "hashForB".
    // Because findMatchingWithdrawal only matches by assetId, `.find()` returns
    // the FIRST array element for BOTH calls, so:
    expect(result0.status === "completed" && (result0 as any).txHash).toBe("hashForB"); // WRONG: should be "hashForA"
    expect(result1.status === "completed" && (result1 as any).txHash).toBe("hashForB"); // WRONG: should be "hashForB" but for wrong reason (index 1 gets same match as index 0)
  });
});
```
This demonstrates that `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` both resolve to the same (first) matched record regardless of which `destinationAddress`/`amount` was actually signed for that index, confirming the STATUS TRUTH equality is broken.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
