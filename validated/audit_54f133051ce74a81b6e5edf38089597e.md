### Title
Webhook shop-domain identity spoofing via HMAC that only covers the body, not the tenant header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`/`webhook_id`/`api_version`) values used to identify *which tenant* the webhook is about are read from unauthenticated HTTP headers that are never included in the signed material, breaking the equality `hmac-authenticated bytes == bytes used to identify the tenant`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from headers with no relationship to the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the metadata handed to the app's handler, with no cross-check that the header-derived shop is the one the HMAC/secret actually corresponds to: [3](#0-2) 

Because the `client_secret`/`api_secret_key` used to sign webhooks is a single, app-wide secret shared across all shops that installed the app (see `Utils::HmacValidator.validate`, which validates against `Context.api_secret_key`): [4](#0-3) 

any tenant that has installed the app can capture a legitimately-signed `(raw_body, hmac-sha256)` pair delivered to their own store, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a *different*, victim shop. `HmacValidator.validate` will still succeed because it only checks the body signature against the shared app secret — it never binds the signature to the shop header. `Registry.process` then dispatches to the app's handler with `WebhookMetadata` claiming the victim's shop, topic and webhook id, even though none of that was authenticated.

### Impact Explanation
This breaks the tenant-identity binding at the core of the webhook trust model: any equality of the form `shop claimed in webhook == shop whose secret actually signed it` fails silently. An app that trusts `WebhookMetadata#shop` to select which tenant's data to update, delete, or invalidate (e.g., processing `customers/redact`, `shop/redact`, `app/uninstalled`, order/fulfillment updates, etc.) can be tricked by any other installer of the same app into acting on a victim's tenant data using attacker-supplied body content, since the body's semantic content is fully attacker-controlled while only its integrity is verified — its ownership/shop-scoping is not. This is a cross-tenant access vector reachable by any unprivileged internet user who has installed the app on some shop of their own, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is elevated because the prerequisite (installing the app on any shop, or observing any legitimately delivered webhook) is trivial for any developer of a public/multi-tenant Shopify app, and the replay itself only requires forging HTTP headers — no cryptographic material is needed beyond a passively captured, legitimate `(body, hmac)` pair. The vulnerable code path (`HmacValidator.validate` + `Registry.process`) is on the default/documented webhook processing flow used by every consumer of this gem's webhook registry.

### Recommendation
Bind the tenant/topic identity into the signed material verification, or otherwise validate the `shop-domain` header against a source of truth (e.g., confirm it matches a shop with an active, previously-stored session/installation record) before trusting it in `WebhookMetadata`. At minimum, document and encourage host apps to cross-check `request.shop` against their own installed-shop registry rather than trusting it implicitly post-HMAC-validation, and consider incorporating the `shop-domain`/`topic`/`webhook-id` headers into the value that `to_signable_string` returns wherever Shopify's webhook signing scheme is extended to support it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one such delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `HMAC(secret, B) == H`).
3. Attacker POSTs the same body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a topic of their choosing among topics the app has registered handlers for).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this still matches since `B` and `H` are unmodified.
5. `Registry.process` proceeds to build `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` and invokes the app's handler, which now processes attacker-controlled data believing it originated from `victim-shop.myshopify.com`.
