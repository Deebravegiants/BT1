### Title
Webhook shop/topic identity is trusted from unauthenticated headers while the HMAC only signs the raw body - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as fully authenticated once `Utils::HmacValidator.validate(request)` succeeds, then dispatches to the app's handler with a `WebhookMetadata` built from `request.shop` and `request.topic`. However, the HMAC is computed and verified only over the raw request body (`Request#to_signable_string` returns `@raw_body`), never over the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. This breaks the implicit identity binding: `shop` acted upon (delivered to the handler as "the shop this webhook came from") ≠ `shop` actually covered by the signature.

### Finding Description
`Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [1](#0-0) 

Its `to_signable_string` — the only thing the HMAC actually authenticates — is just the raw body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) and compares it against the received `hmac` header, with no reference to `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` then gates everything on that single check and immediately forwards the header-derived `request.shop` and `request.topic` to the handler as if they were verified: [4](#0-3) 

Because `shop`/`topic`/`webhook_id` are not part of the signed material, any `(raw_body, hmac)` pair that is valid for one shop/topic is also valid when replayed with a different `shop-domain` or `topic` header — the signature check still passes, and the handler receives an attacker-chosen `shop` value in `WebhookMetadata`. Equality that should hold is: `shop authenticated by HMAC == shop delivered to handler`; here the left side is undefined (not covered) while the right side is fully attacker-controlled header data.

### Impact Explanation
Apps commonly use `WebhookMetadata#shop` to look up per-tenant sessions/access tokens or to route data into a specific merchant's records. If a webhook body+HMAC pair for Shop A (which can be observed by anyone who receives that webhook, e.g., a merchant collaborator, a compromised delivery endpoint, or via non-TLS-terminated proxies logging headers) is replayed with the `shop-domain` header changed to Shop B, `Registry.process` will still pass HMAC validation and hand the handler a `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"` with Shop A's body. Depending on how the host app trusts this field, this enables cross-tenant data confusion/injection into another merchant's record — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitation requires only network delivery of an HTTP POST with attacker-controlled headers plus a legitimate body+hmac pair obtained from any prior real delivery (webhooks are delivered over the open internet to a public endpoint, and the HMAC by design does not require the app secret to replay — only to forge a *new* body). No access token, `client_secret`, or privileged account is needed to mount the header-substitution replay itself.

### Recommendation
Bind `shop`, `topic`, and other dispatch-relevant identifiers into the signed material (or otherwise verify `shop-domain` against a list of shops the app has legitimately installed on, with a nonce/timestamp check) before constructing `WebhookMetadata`, so headers used for tenant routing cannot be swapped independently of the HMAC-covered body.

### Proof of Concept
1. App receives a legitimate webhook: `POST /webhooks` with body `B`, headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
2. Attacker (or a compromised intermediary) captures `(B, H)` and replays: `POST /webhooks` with the same body `B` and same `H`, but `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this only recomputes HMAC over `B`, which still matches `H`, so validation passes as shown in `lib/shopify_api/utils/hmac_validator.rb` lines 12-31.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "shop-b.myshopify.com"` (attacker-controlled) and dispatched to the handler, even though the signature never covered that value.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
