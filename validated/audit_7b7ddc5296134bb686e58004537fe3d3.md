### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC only over the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values used by the app's business logic are read from HTTP headers that are entirely outside the signed content. This breaks the identity binding `shop authenticated == shop dispatched to handler`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature strictly against `verifiable_query.to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once `HmacValidator.validate` passes and then dispatches `request.shop` (an unauthenticated header value) straight into `WebhookMetadata`, which app code uses to route processing per-tenant: [4](#0-3) 

Because the app's `client_secret` is shared across every shop that has the app installed, any unprivileged merchant who installs the app on their own store receives genuine webhooks with a valid HMAC computed over a body they control the shop context of. That same (body, HMAC) pair remains valid if replayed to the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to a different, victim shop's domain — the signature still validates because the header was never part of the signed bytes. The equality that should hold is `HMAC-authenticated request == shop the handler treats it as belonging to`; here `HMAC` binds only body bytes, so the shop identity is trusted without being covered.

### Impact Explanation
This is a cross-tenant identity confusion: the gem, and by extension the host application relying solely on `Registry.process`'s HMAC validation to trust `request.shop`, will attribute a webhook payload to an arbitrary shop chosen by the attacker. Depending on the app's webhook handlers (e.g., order/customer/app-uninstalled events keyed by `shop`), this can trigger state changes, data writes, or session/token lookups against a shop the attacker does not control, i.e., cross-tenant access — one of the accepted Critical impacts.

### Likelihood Explanation
Any merchant can install the target app on their own store (unprivileged, no special credentials, no `api_secret_key` or access token needed) to obtain one legitimately signed webhook body/HMAC pair, then simply replay the raw request with a modified shop header to the app's public webhook endpoint. No secret material or elevated privilege is required — only the ability to intercept/read one's own app-generated webhook traffic and resend it.

### Recommendation
Include `shop`/`shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) in the signable content, or independently verify that the `shop-domain` header matches a shop context established through another authenticated channel before dispatching to handlers. At minimum, document that `request.shop` is not covered by the HMAC and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (a normal, unprivileged action).
2. The app's webhook endpoint receives a legitimate webhook: body `B`, header `shopify-shop-domain: attacker.myshopify.com`, header `shopify-hmac-sha256: H` where `H = HMAC(client_secret, B)`.
3. Attacker replays the exact same request to the same endpoint, but rewrites the `shopify-shop-domain` header to `victim.myshopify.com`, keeping body `B` and HMAC header `H` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` — still equal to `H` because the shop header is not part of `to_signable_string` — so validation passes.
5. `request.shop` returns `"victim.myshopify.com"`, and `WebhookMetadata.new(shop: request.shop, ...)` is dispatched to the app's handler as if it were a legitimate webhook for `victim.myshopify.com`.
