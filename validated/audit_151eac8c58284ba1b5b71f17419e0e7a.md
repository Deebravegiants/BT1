### Title
Webhook shop-tenant identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is taken from an HTTP header which is not covered by that HMAC. This breaks the required binding `shop_authenticated == shop_used_for_tenant_dispatch`, letting an attacker splice a genuinely-signed body from one shop with a spoofed `shop-domain` header for a different (victim) shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers and are never included in the signed material: [2](#0-1) 

`Registry#process` validates only this body-only HMAC and then trusts `request.shop` (and `request.topic`) as the tenant identifier passed straight into the handler's `WebhookMetadata`: [3](#0-2) [4](#0-3) 

Because Shopify webhooks for a given app are all signed with the same app-wide `client_secret` (it is not a per-shop secret), any merchant who installs the app receives legitimately HMAC-signed webhook deliveries at their own endpoint. Since only the body bytes are bound to the signature — not the `shop-domain` header — that same merchant (an unprivileged, non-victim tenant with respect to any other install of the app) can take a validly-signed body they received and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different, victim shop. `HmacValidator.validate` will still return `true` because it only recomputes the signature over `to_signable_string` (the raw body), and the handler will process the payload as if it originated from the victim shop.

This is exactly the "field acted on but not covered by the HMAC" pattern: the equality that should hold is
`hmac_covered_bytes == bytes_that_determine_tenant`, but here `hmac_covered_bytes = raw_body` while `tenant_identity = header["shopify-shop-domain"]`, which are disjoint.

### Impact Explanation
This allows cross-tenant confusion in webhook processing: an app's own webhook handler logic (e.g., updating per-shop billing state, uninstall bookkeeping, GDPR mandatory topics like `shop/redact` or `customers/redact`, order/product sync, etc.) can be triggered for an arbitrary victim shop using data an attacker fully controls the delivery of (an authentic but reusable payload) combined with a forged shop identity, without ever possessing the app's `client_secret`. Depending on what the host application does with `WebhookMetadata#shop`, this can lead to cross-tenant data corruption or disclosure keyed by a shop domain the attacker does not own — meeting the "cross-tenant access" bar for a Critical/High finding since the tenant boundary (`shop`) is not authenticated.

### Likelihood Explanation
Any developer/merchant who can install the target app on their own shop can obtain real signed webhook payloads (Shopify sends them to the app's registered endpoint, which the merchant can point at infrastructure they control, or intercept if self-hosting a proxy). Constructing the replay only requires forging an HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) on a raw POST to the app's public webhook endpoint — no cryptographic material is needed since the header sits entirely outside the signed scope. This requires no privileged credentials, tokens, or social engineering, only having valid app installation (which is the normal, expected, low-barrier state for any merchant).

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable material, or otherwise verify that the `shop-domain` header in the request matches a value derivable from data that is itself covered by the signature (e.g. incorporate the shop domain into `to_signable_string`, mirroring how `AuthQuery#to_signable_string` binds `shop` into the OAuth callback signature). At minimum, cross-check the delivered `shop-domain` against an expected/registered shop before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker registers/receives a legitimate webhook (e.g. `orders/create`) at an endpoint they control; Shopify signs it with the app's shared `client_secret`, producing `raw_body` + valid `X-Shopify-Hmac-Sha256`.
3. Attacker replays this exact `raw_body` (and its unmodified HMAC header) to the real app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts it (all required headers present), `Registry#process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`raw_body` only) — validation succeeds because the body/HMAC pair is untouched.
5. `request.shop` returns `"victim-shop.myshopify.com"` from the forged header, and the handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, processing attacker-supplied data under the victim's tenant identity.
