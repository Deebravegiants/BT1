### Title
Unbounded accrued debt value overflows `i128` and permanently freezes a market — no repay, withdraw, or liquidation can ever execute again - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
XOXNO Lending's interest accrual computes total debt value as `borrowed_shares × borrow_index` in `i128`. Both operands grow without bound: `borrowed` is RAY-scaled debt (up to ~`i128::MAX` for an 18-decimal asset) and `borrow_index` compounds at up to `max_borrow_rate` per millisecond. Once the product `borrowed × borrow_index / RAY` exceeds `i128::MAX`, `accrue_step` panics with `MathOverflow`. Because every pool verb — `update_indexes`, `borrow`, `repay`, `withdraw`, `seize_positions` (liquidation), `claim_revenue`, `recapitalize` — accrues the market first via `interest::global_sync`, the panic permanently bricks the market. `borrow_index` is monotone and can never retreat, so there is no recovery path. This is the direct analog of the reference report's "uncontrolled resource consumption → irreversible DoS": an unbounded accumulator (debt × index) drives a hard panic in a path every operation must traverse.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs` calls `scaled_to_original(env, borrowed, borrow_index)` to value the debt for utilization, and `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)`. `Ray::mul` is `mul_div_half_up`, which widens intermediates to `I256` but panics with `GenericError::MathOverflow` when the *result* does not fit `i128` (`common/src/math/fp_core.rs:122-143`). The only guard is `MAX_BORROW_INDEX_RAY` (10³⁶), applied to the index alone in `update_borrow_index` — the value ceiling `borrowed × index < i128::MAX` is never enforced. The protocol itself acknowledges the gap: `docs/reference/invariants.md` INV-IDX-01 states "Debt-value overflow can still revert accrual before that ceiling is reached." A harness test demonstrates the full chain end-to-end: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`) shows a 10²⁷-unit 18-decimal market at 98% utilization hitting `MATH_OVERFLOW`, after which `try_withdraw_raw` and `try_repay` both fail with the same error — the market is frozen while `borrow_index < MAX_BORROW_INDEX_RAY`.

### Impact Explanation
Permanent freezing of user funds and protocol insolvency-by-freeze. Once the threshold is crossed, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize, and bad debt cannot be cleaned or recapitalized — all deposited tokens and unclaimed revenue in that (hub, token) market are locked forever. Because accrual is monotone, no governance action short of a code upgrade can restore the market, and even an upgrade must rescue already-trapped positions. This is worse than the fail-closed revert class: the revert is triggered by state, not by the request, and the state can never improve.

### Likelihood Explanation
Medium-low, matching a Medium severity. Reaching the cliff requires a very large market (RAY-scaled debt on the order of `i128::MAX / index`, e.g. a billion-token 18-decimal book at ~98% utilization) and multi-year sustained accrual at a steep curve segment — the test needed several simulated years at ~170× index growth. Borrow caps (`max_borrow_cap`, validated by `require_cap_within_asset_domain`) are the main mitigating bound, but they are governance parameters and `calculate_scaled_cap` deliberately saturates rather than traps, so a generously capped high-decimal market admits the state. No privileged action is needed to trigger the freeze once the state exists — the permissionless `update_indexes` keeper call itself panics — so any user can be the one to brick the market simply by calling it after enough time passes.

### Recommendation
Saturate rather than panic on the debt-value product inside accrual: use `mul_div_floor_saturating`/`I256` for `borrowed × new_borrow_index` and `borrowed × old_borrow_index` in `calculate_supplier_rewards` and `scaled_to_original`'s use in `accrue_step`, capping effective debt value at `i128::MAX` (accrual then yields zero marginal interest, consistent with the existing `MAX_BORROW_INDEX_RAY` cap semantics). Alternatively, enforce an explicit market-level ceiling — revert `borrow`/`mint_debt` when `borrowed` scaled shares exceed `i128::MAX / MAX_BORROW_INDEX_RAY` — so the state that triggers the overflow is unreachable. Add a regression test asserting `update_indexes` still succeeds at the index-cap boundary on a whale-scale market.

### Proof of Concept
Existing in-repo PoC: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`.

1. List/seed an 18-decimal market with lifted caps and the XLM-shaped curve; supply `10⁹ × 10¹⁸` units (`supply` with `account_id` 0, permissionless) and borrow 98% of it (`borrow`, owner-authorized — attacker uses their own account).
2. Advance ledger time in yearly steps, calling the permissionless `update_indexes` each step.
3. At the step where `borrowed × borrow_index / RAY > i128::MAX`, `accrue_step` → `scaled_to_original` → `Ray::mul` → `mul_div_half_up` returns `None` → `panic_with_error!(MathOverflow)` (`common/src/math/fp_core.rs:116-117`, `common/src/rates/index.rs:80-81`).
4. Thereafter `withdraw` and `repay` (which call `Cache::load` → `global_sync` → `accrue_chunk` → `accrue_step` in `contracts/pool/src/interest.rs:20-53`) fail identically — permanently, since `borrow_index` is monotone (`update_borrow_index` only grows, `common/src/rates/index.rs:13-19`).
