Based on my research, the closest architectural analog to the reported bug (a governance setter updating one contract's reference to a peer while other contracts continue holding a stale mirrored copy, since the “sync” is not atomic) is in `pallet-intents-coprocessor`'s `add_deployment`, which fans out a peer-address change to every other deployed `IntentGatewayV2` but tolerates per-target delivery failure, leaving Hyperbridge's own registry and the individual gateways permanently disagreeing about which contract is the trusted peer for a chain.

### Title
`add_deployment` silently ignores per-gateway dispatch failures, permanently desynchronizing peer `_instances` registries across `IntentGatewayV2` deployments - (File: modules/pallets/intents-coprocessor/src/lib.rs)

### Summary
`pallet_intents_coprocessor::add_deployment` records a gateway's address in Hyperbridge's own `Gateways` storage and then attempts to propagate that address to every other already-registered `IntentGatewayV2` deployment via a cross-chain `NewDeployment` ISMP dispatch, one message per peer chain. Dispatch failures for individual peers are explicitly discarded (`let _ = Self::dispatch(...)`), so Hyperbridge's canonical view and the state each `IntentGatewayV2._instances` mapping holds can permanently diverge after a single failed dispatch, exactly the "parallel copies maintained between manager and factory" desync described in the analog report, except here the two (or more) diverging parties are the coprocessor's own bookkeeping and every deployed gateway contract that ISMP is supposed to keep synchronized.

### Finding Description
`add_deployment` in [1](#0-0)  performs:
1. `Gateways::<T>::insert(state_machine, gateway_info)` — Hyperbridge's local record is updated unconditionally.
2. A loop over every other registered `(existing_state_machine, existing_gateway_info)`, dispatching a `NewDeployment` notification to each one so their local `_instances[state_machine]` gets updated to the new gateway address, but the dispatch result is discarded with `let _ = Self::dispatch(...)`.

On the EVM side, each `IntentGatewayV2`/`ExtrinsicIntents` instance stores its view of every peer gateway address in `_instances`, written only by `_addDeployment` when it receives a `NewDeployment` request from Hyperbridge: [2](#0-1) . This mapping is exactly what cross-chain redemption/refund authentication is checked against (`_authenticate`, described in the `onAccept` docstring): [3](#0-2) .

Because the coprocessor updates its own record first and then best-effort fans out to N-1 peers with no retry, no event distinguishing failed sends, and no reconciliation mechanism, any transient ISMP dispatch failure to a subset of peers (e.g. a chain temporarily paused, out of fee-token balance, or simply erroring inside `Self::dispatch`) leaves those peers permanently pinned to the stale gateway address for the affected chain while Hyperbridge and the successfully-notified peers move on to the new one. There is no compensating flow that later retries or reconciles the missed peers; the desync is silent and permanent unless another manual governance `add_deployment` call happens to be issued again for the same pair.

### Impact Explanation
Once desynchronized, cross-chain order settlement for orders whose source or destination is the mis-registered chain breaks in one of two ways:
- If the old gateway address on the un-notified peer no longer holds valid contract state consistent with `_authenticate`'s expectations (e.g., the chain redeployed its gateway, changing its address as part of normal, non-malicious upgrade/migration operations), legitimate `RedeemEscrow`/`RefundEscrow` messages from the new, correctly-registered gateway will be rejected by the stale peer as unauthenticated, since `keccak256(request.from) != keccak256(expectedSource)`-style checks depend on `_instances` matching. This permanently freezes escrowed user/solver funds on that route — the withdrawal path can never validate.
- Conversely, if the old (stale) gateway address is retained by a peer that should have moved on, and the old contract remains reachable and controllable by whoever holds keys/roles for it, that stale peer will continue accepting and authenticating messages "from" the old address on chains that Hyperbridge itself considers decommissioned for that route, an unauthorized-app-action / forged-message-delivery style risk on that specific lane.

Both outcomes are consistent with the Validate criteria: concrete permanent freezing of escrowed funds on the affected lane, or unsound state commitment among the registered peer set, reachable purely by the coprocessor's normal (non-malicious) `add_deployment` governance flow combined with an ordinary ISMP dispatch failure — not by any malicious admin/governance action.

### Likelihood Explanation
`add_deployment` is a normal, expected operational call issued whenever a new chain's `IntentGatewayV2` is deployed or an existing one is redeployed (as documented for gateway upgrades elsewhere in the repo, e.g. the SolverAccount/IntentGateway redeploy flow). ISMP dispatch failure to at least one of N-1 peers during a fan-out is not a contrived or rare condition — it can occur from ordinary conditions (insufficient relayer fee balance, a paused destination, a misconfigured route) — and the code deliberately swallows the error ("ignore errors to not fail the whole operation"), so the bug triggers under routine operational circumstances rather than requiring an attacker or a malicious governance actor.

### Recommendation
Do not silently discard per-peer dispatch failures. Track which peers were not successfully notified (e.g., persist a pending-notification set keyed by `(state_machine, existing_state_machine)`) and expose a permissionless or governance-triggered retry/resend extrinsic that fans the missed `NewDeployment` notifications out again until every peer confirms receipt (or until it can be independently verified via ISMP request-status queries). Alternatively, make `add_deployment` fail atomically if any peer dispatch fails, so Hyperbridge's own `Gateways` record cannot advance ahead of the peer set it is meant to represent.

### Proof of Concept
1. Two chains, A and B, each run an `IntentGatewayV2` registered in Hyperbridge's `Gateways` map.
2. Governance calls `add_deployment` for a redeployed gateway on chain A with a new address `G_A'`. Hyperbridge updates `Gateways[A] = G_A'` and attempts to dispatch a `NewDeployment` notification to chain B's gateway.
3. The dispatch to chain B fails (e.g., `Self::dispatch` returns an error due to an ISMP routing/fee issue) — the error is discarded via `let _ = ...`, and `add_deployment` returns `Ok(())` regardless.
4. Chain B's `IntentGatewayV2._instances[A]` still points at the old `G_A`. A user's order from chain B destined for chain A, once filled, dispatches a `RedeemEscrow` message that is authenticated against `_instances[A]` on chain B — but the message's `from` field is `G_A'` (the new address), so authentication fails and the escrow can never be redeemed on chain A's leg of the flow, freezing the escrowed funds permanently, per [2](#0-1)  and [4](#0-3) .

		pub fn add_deployment(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			gateway: H160,
			params: IntentGatewayParams,
		) -> DispatchResult {
			T::GovernanceOrigin::ensure_origin(origin)?;

			// Store gateway info
			let gateway_info = GatewayInfo { gateway, params };

			Gateways::<T>::insert(state_machine, gateway_info);

			// Notify all existing gateways about the new deployment
			// Only notify gateways with different addresses (same address automatically accepts)
			for (existing_state_machine, existing_gateway_info) in Gateways::<T>::iter() {
				// Skip if same state machine or same gateway address
				if existing_state_machine == state_machine ||
					existing_gateway_info.gateway == gateway
				{
					continue;
				}

				// Prepare cross-chain request to notify existing gateway
				let new_deployment =
					types::NewDeployment { chain: state_machine.to_string().into_bytes(), gateway };
				let request = RequestKind::AddDeployment(new_deployment);
				let body = request.encode_body();

				// Dispatch cross-chain message (ignore errors to not fail the whole operation)
				let _ = Self::dispatch(existing_state_machine, existing_gateway_info.gateway, body);
			}

			Self::deposit_event(Event::GatewayDeploymentAdded { state_machine, gateway });

			Ok(())
