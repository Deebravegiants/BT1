I have sufficient evidence to confirm the vulnerability. In `HandlerV2.handlePostRequests` (and identically in `handleGetResponses`), the multiproof over the *entire* batch of leaves is verified first, and only afterward does a second loop check each leaf's receipt for duplicates and revert the whole call on the first duplicate found — exactly the "verify-then-iterate-and-revert-on-one-bad-item" pattern from the OpenQ report.

### Title
Permissionless single-leaf front-run causes atomic revert of an entire `handlePostRequests`/`handleGetResponses` batch, DOSing message delivery - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` verify a Merkle Mountain Range multiproof covering *every* leaf in the submitted batch, then loop a second time and call `revert DuplicateMessage()` if **any single leaf** already has a receipt. Because delivery is permissionless and a single leaf can be proven independently with its own MMR sub-proof, an attacker can extract one leaf from a relayer's pending batch, deliver it alone first, and thereby force the relayer's larger batch transaction to revert entirely once it lands — even though every other request/response in that batch is legitimate, unrelated, and still perfectly deliverable.

### Finding Description
`handlePostRequests` performs two passes over `request.requests`:

1. First pass (lines 190–197) builds MMR leaves and validates destination/timeout for every request, then a single `MerkleMountainRange.VerifyProof` call (line 201) validates the whole set against the state-machine commitment.
2. Second pass (lines 204–209) re-walks the same array and, for each leaf, checks `host.requestReceipts(leaf.request.hash()) != address(0))`, reverting the **entire transaction** with `DuplicateMessage()` if any single one was already delivered: [1](#0-0) 

The identical structure exists for GET responses: [2](#0-1) 

Both `handlePostRequests` and `handleGetResponses` are explicitly permissionless — "anyone can call them to relay messages" — and MMR multiproofs support proving an arbitrary subset of leaves (a single leaf with its own `kIndex`/proof path), as documented in the MMR multiproof scheme: [3](#0-2) 

Since Hyperbridge relayers routinely batch many unrelated requests into one `handlePostRequests`/`batchCall` transaction to save gas (`tesseract/messaging/evm/src/tx.rs::submit_batch_messages`, `evm/src/core/HandlerV2.sol::batchCall`), and `batchCall` also reverts atomically on any inner failure: [4](#0-3) [5](#0-4) 

an attacker can:
1. Observe a relayer's pending `handlePostRequests`/`batchCall` transaction (or its constituent state) in the mempool, containing N legitimate `PostRequestLeaf`s bound for a destination.
2. Independently self-relay just one of those N leaves via their own minimal `handlePostRequests` call, with a smaller MMR sub-proof for that single leaf (permissionless, no fee gating needed for delivery itself — only the destination module decides whether to reward the relayer).
3. Because `EvmHost.dispatchIncoming` unconditionally writes `_requestReceipts[commitment] = relayer` before calling `onAccept` and only deletes it if `onAccept` itself reverts, a successful single-leaf delivery permanently sets the receipt for that commitment.
4. When the original relayer's larger batch transaction then executes, its second-pass duplicate check hits that one already-delivered leaf and reverts `DuplicateMessage()` for the **whole call**, discarding delivery of the other N−1 unrelated, legitimate, and still-undelivered requests/responses bundled in that same transaction.

This mirrors the OpenQ analog precisely: an unprivileged actor performs one cheap, legitimate-looking action (delivering a single item that they are permitted to deliver) that, when combined with a batch iteration that reverts wholesale on any single item's already-processed state, denies service to all other unrelated items processed together.

### Impact Explanation
This is a concrete "route unable to deliver messages" condition. A griefer can repeatedly and cheaply front-run relayer batches — extracting and self-relivering a single leaf from each new batch as it appears in the mempool — forcing every large batched `handlePostRequests`/`batchCall` submission to that chain to revert. Relayers observing repeated failures are forced to fall back to per-message delivery (higher gas cost, higher latency), or in the worst case the griefing can be sustained faster than relayers can adapt, materially delaying delivery of legitimate cross-chain messages (including token bridge mints, intent fills/settlements, and consensus-carrying deliveries bundled in the same tx) to a destination chain. Because delivery races are inherently permissionless and profit-driven, this also degrades the relayer fee economics that fund message delivery, and in aggregate this can amount to a sustained denial of message delivery for a targeted route.

### Likelihood Explanation
Likelihood is high: the attack requires no special privilege, no capital at risk beyond gas for a single-leaf delivery, and no cooperation from any other party. Pending relayer transactions containing multiple leaves are visible in the public mempool before inclusion, and MMR multiproofs are explicitly designed to support proving any subset of leaves, so constructing a valid single-leaf sub-proof from data already available (or independently queryable from Hyperbridge) is straightforward. The attack can be repeated indefinitely and cheaply against any destination chain that receives batched relayer submissions.

### Recommendation
Do not let a single already-delivered leaf abort the whole batch. In `handlePostRequests`/`handleGetResponses`, skip (rather than revert on) leaves whose receipt already exists, mirroring the graceful-skip pattern already used in `EvmHost.dispatchIncoming` for failed/no-code destinations:

```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    if (host.requestReceipts(leaf.request.hash()) != address(0)) continue; // skip, don't revert
    host.dispatchIncoming(leaf.request, _msgSender());
}
```

This preserves replay protection for the individual duplicate leaf while allowing every other legitimate, undelivered request/response in the same batch to still be processed and delivered in that transaction.

### Proof of Concept
1. Relayer A observes N pending POST requests destined for chain X and prepares `handlePostRequests(host, {requests: [leaf_1 .. leaf_N], proof})` (or wraps it in `batchCall`) and broadcasts it.
2. Attacker sees this transaction in the mempool, extracts `leaf_k` (any single leaf, 1 ≤ k ≤ N) together with the MMR data needed to build an independent single-leaf multiproof for `leaf_k` against the same `overlayRoot`.
3. Attacker submits `handlePostRequests(host, {requests: [leaf_k], proof: subProof})` with higher gas/priority, landing before Relayer A's transaction. `EvmHost.requestReceipts[leaf_k.hash()]` is now set to the attacker's address.
4. Relayer A's original transaction lands afterward. The multiproof for `[leaf_1..leaf_N]` still verifies (all leaves remain valid members of the MMR), but the duplicate-check loop hits `leaf_k`, whose receipt is now non-zero, and reverts `DuplicateMessage()` for the entire call — `leaf_1..leaf_N` except `leaf_k` are not delivered, even though they were never touched by the attacker and remain fully valid, undelivered requests.
5. Attacker repeats step 2–3 against every subsequent retry batch Relayer A constructs, sustaining the denial of delivery for the targeted destination at minimal cost.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
