### Title
Unvalidated `RequestKind` enum discriminant in `onAccept` permanently freezes cross-chain messages and their escrowed relayer fees - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`ExtrinsicIntents.onAccept` (and its Tron analogue `IntentGatewayV2.onAccept`) reads the first byte of an incoming Hyperbridge `PostRequest` body and casts it directly to the `RequestKind` enum without checking that the byte value falls within the enum's valid range: [1](#0-0) [2](#0-1) 

Solidity reverts with a `Panic(0x21)` when an integer is cast to an enum value outside its declared range. Since the request `body` is attacker-controlled data delivered from a remote chain, an out-of-range first byte causes `onAccept` to always revert for that specific message, and it can never be delivered successfully.

### Finding Description
Any account on any connected source chain can call the Hyperbridge dispatcher (`IDispatcher.dispatch`) with an arbitrary `to` (the `ExtrinsicIntents`/`IntentGatewayV2` contract address on the destination chain) and an arbitrary `body`, since dispatch is permissionless from the perspective of the caller choosing destination module and payload. This request is fee-paid, verified by consensus/state proofs, and eventually delivered by a relayer through `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `IApp.onAccept`. [3](#0-2) 

`dispatchIncoming` writes a request receipt, then makes a low-level `.call()` to `onAccept`. If the call fails, it deletes the receipt and returns without reverting the whole batch — allowing the delivery to be "retried" later: [4](#0-3) 

Inside `onAccept`, the relayer gate (`_checkRelayer`) only restricts *who may deliver* the message, not what the original sender put in the body: [5](#0-4) 

Immediately after that check, the first body byte is cast to the `RequestKind` enum without any bounds validation: [6](#0-5) 

Because the request body is fixed at dispatch time and is part of the content committed on the source chain (and verified by MMR/state proof on delivery), a malicious sender can craft a body whose first byte is outside the declared `RequestKind` range (e.g. any value the enum does not define). Every delivery attempt of that specific request will revert with the same `Panic(0x21)`, `dispatchIncoming` will delete the receipt each time ("so it can be retried"), and the message will never leave the "pending" state — it can be retried indefinitely but never succeeds, because the malformed byte is immutable once the request is committed.

This is the same bug class as the referenced CVE: a request/body parameter's type is not validated before being consumed, allowing an unprivileged sender to trigger a crash (here, an EVM panic revert) in the destination handler.

### Impact Explanation
- **Permanent freezing of funds**: Hyperbridge post requests can carry an escrowed relayer fee that is only released on successful delivery. A request whose `onAccept` can never succeed leaves that fee permanently locked/unredeemable, since the message commitment neither completes nor is designed to "time out" successfully into a refund path once dispatched with a non-zero timeout of 0 in this app's own outbound dispatch pattern; for the inbound side, the fee/escrow tied to the malformed request commitment cannot be settled through the normal accept path.
- **Route unable to deliver messages**: The destination module for this state machine pair becomes unable to process this specific message ever, since the malformed discriminant is baked into the already-committed request body and cannot be "fixed" by a relayer resubmission — this is a permanent, attacker-triggerable denial of a specific cross-chain message, at the cost of only whatever gas/fee is required to dispatch a 1-byte-body PostRequest to the target module.
- The impact is scoped per-message (does not directly corrupt other messages' state or halt the whole `IntentGatewayV2`/`ExtrinsicIntents` module for other requests), but it is a concrete unbounded, repeatable, low-cost griefing primitive reachable by any unprivileged sender on any connected chain, and it can specifically be aimed at requests whose delivery a victim depends on (e.g., blocking a specific `RedeemEscrow`/`RefundEscrow` withdrawal by making the relayer never able to successfully post the companion message, or wasting relayer fee funds attached to spam requests).

### Likelihood Explanation
High reachability: the only requirement is the ability to dispatch a PostRequest to Hyperbridge with `to` set to the target `ExtrinsicIntents`/`IntentGatewayV2` instance address and a body whose first byte is not one of the enum's declared discriminants (`RedeemEscrow`, `RefundEscrow`, `NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`, etc.). This requires no special privileges, no compromised keys, and no consensus/relayer collusion — any account capable of calling the source-chain dispatcher can trigger it, matching the "unprivileged message dispatcher" reachability required by the report criteria.

### Recommendation
Validate the discriminant byte range before casting to the enum, e.g.:
```solidity
uint8 raw = uint8(incoming.request.body[0]);
if (raw > uint8(RequestKind.Execute)) revert InvalidRequestKind();
RequestKind kind = RequestKind(raw);
```
Apply the same fix to `IntentGatewayV2.onAccept` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, and audit any other `IApp.onAccept`/`onGetResponse` implementations in the codebase (e.g. `SimplexPaymaster.sol`, `VWAPOracle.sol`, `BandwidthManager.sol`) that perform a similar `RequestKind(uint8(body[0]))`-style cast on attacker-supplied request bodies, since they share the same `RequestKind` decoding pattern shown in `modules/pallets/intents-coprocessor/src/types.rs`.

### Proof of Concept
1. On the source chain, call the Hyperbridge host's `dispatch(DispatchPost)` with:
   - `dest` = the destination state machine hosting the target `ExtrinsicIntents`/`IntentGatewayV2` instance.
   - `to` = `abi.encodePacked(<ExtrinsicIntents address>)`.
   - `body` = a single byte with a value outside the `RequestKind` enum's declared range (any value greater than the highest defined discriminant, e.g. `0xFF`).
   - Attach a relayer fee (optional, but demonstrates fund lock).
2. Wait for the request to be relayed via `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming`.
3. `dispatchIncoming` low-level-calls `ExtrinsicIntents.onAccept`, which executes `RequestKind(uint8(incoming.request.body[0]))` and reverts with `Panic(0x21)` (enum conversion out of range).
4. `EvmHost.dispatchIncoming` catches the failure (`success == false`), deletes the request receipt, and returns without reverting the outer batch — the message is left in a permanently undeliverable state; any relayer fee attached is not released back or forwarded and the message is retried indefinitely without ever succeeding.

**Note on verification limits**: I was not able to fully trace how relayer fee escrow accounting reacts specifically to a permanently-failing `dispatchIncoming` call (i.e., whether there's a separate timeout/refund mechanism on the destination side that would recover the fee) within the scope of this review — this would need to be confirmed against `EvmHost`'s fee accounting and the source-chain fee-refund/timeout logic before asserting outright fund loss versus indefinite lock.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
