### Title
Withdrawal status/tx-hash misreport when multiple withdrawals share the same `assetId` in one batch - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the outcome (status, `transfer_tx_hash`) of a specific withdrawal by matching the PoA Bridge API response **only by `assetId`**, ignoring the withdrawal's index/position, amount, and destination address. When `IntentsSDK.waitForWithdrawalCompletion` (or the lower-level `withdrawal-watcher`) is used with multiple withdrawals in the same batch that share the same `assetId` (e.g., withdrawing the same token to two different destination addresses in one multi-withdrawal intent), each call ends up matching the same withdrawal record, so the reported completion status and `txHash` for one withdrawal can be attributed to a different, unrelated withdrawal.

### Finding Description
`describeWithdrawal` explicitly documents and tests that it does **not** use index-based correspondence: [1](#0-0) 

The accompanying test `"matches withdrawal by assetId, not by index"` confirms the matching key is `assetId` alone, and a further test shows matching happens via `near_token_id` regardless of the `defuse_asset_identifier` format: [2](#0-1) 

The shared helper `findMatchingWithdrawal` in `internal-utils` performs the same weak match — solely on `near_token_id` derived `assetId` — with an explicit code comment acknowledging the limitation that same-asset, multi-withdrawal scenarios are unsupported and can misattribute results: [3](#0-2) 

At the SDK layer, `IntentsSDK.waitForWithdrawalCompletion` invokes `bridge.describeWithdrawal` once per withdrawal in the batch, tagged with an `index`, and the test suite documents that callers rely on positional correspondence (`promises[i]` / `withdrawalParams[i]`) to know which destination/amount each returned status belongs to: [4](#0-3) 

The equality that should hold is: *the status/txHash reported for withdrawal `i` (with its specific `amount`+`destinationAddress`) equals the on-chain outcome of that specific withdrawal.* Because the match key is only `assetId`, when two or more withdrawals in the same NEAR transaction share the same `assetId` but differ in `amount` and/or `destinationAddress`, `findMatchingWithdrawal` (a `.find()` over the unsorted API list) will return the same record for both/all of them. This breaks the equality: a caller polling per-index status can receive the *same* `transfer_tx_hash` and `COMPLETED` status for withdrawal #2 that actually belongs to withdrawal #1, even though withdrawal #2 sent funds to a different address/amount and either failed or completed with a different hash.

### Impact Explanation
This is a status/hash misreport, which the rules classify as High impact ("a status or hash misreport making an integrator credit or refund twice"). An integrator (exchange, wallet, custodial service) that calls `sdk.waitForWithdrawalCompletion` with a batch of same-asset withdrawals to different destination addresses can be told that withdrawal B settled with the transaction hash that actually belongs to withdrawal A. This can cause the integrator to mark withdrawal B as delivered (and release corresponding internal credit/lock) when it did not settle as reported, or to attribute a fee/refund event to the wrong withdrawal.

### Likelihood Explanation
Likelihood is limited to specific but realistic batch usage: any caller that submits multiple withdrawals of the **same underlying token** (same `assetId`) to different destinations/amounts in a single intent transaction and then relies on `waitForWithdrawalCompletion`/`describeWithdrawal` per-index results. The bug requires no malicious action by a counterparty — it is triggered purely by normal multi-withdrawal batching of identical-asset withdrawals, which is an explicitly acknowledged, unaddressed limitation in the code comments themselves.

### Recommendation
Extend `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate among same-`assetId` withdrawals using additional fields returned by the PoA API (e.g., `amount`, `address`/destination, and `created` timestamp order) rather than `assetId` alone, and reject/flag ambiguous matches instead of silently returning the first hit. At minimum, `describeWithdrawal` should refuse to report `COMPLETED` for an index-derived withdrawal unless the matched record's amount and destination address also equal the corresponding `withdrawalParams` for that index.

### Proof of Concept
1. Build and sign an intent (via `IntentsSDK`) containing two `Nep141Withdraw` (or the SDK's high-level equivalent) intents for the same `assetId`, e.g. `nep141:btc.omft.near`, with different `amount`/`destinationAddress` pairs — withdrawal #0 to address A for 100000 sats, withdrawal #1 to address B for 50000 sats.
2. Call `sdk.waitForWithdrawalCompletion({ intentTx, withdrawalParams: [paramsA, paramsB] })`.
3. Internally this calls `PoaBridge.describeWithdrawal` twice, once per index, each internally calling `findMatchingWithdrawal(response.withdrawals, assetId)` — as shown by the test `"matches withdrawal by assetId, not by index"` [2](#0-1) .
4. If the PoA API returns the withdrawal list in a different (unsorted) order than submitted, or if withdrawal #1 is still `PENDING`/`FAILED` while withdrawal #0 is `COMPLETED`, both index-0 and index-1 lookups can resolve to the same `COMPLETED` record (whichever the `.find()` first matches by `assetId`), causing the SDK to report `{status: "completed", txHash: <withdrawal #0's hash>}` for withdrawal #1 as well — misreporting its actual outcome to the caller.

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
```
