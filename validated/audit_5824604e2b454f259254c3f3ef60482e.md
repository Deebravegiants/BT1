Audit Report

## Title
CORS Allowlist Bypass via Unanchored Suffix Match in Gateway HTTP Server Wildcard Origin Check - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in core/services/gateway/network/httpserver.go strips the `*.` prefix from a configured wildcard allowed origin and then checks `strings.HasSuffix(originHost, allowedHost)` without verifying that the matched suffix is preceded by a `.` label boundary. This lets an attacker-controlled host such as `evilexample.com` satisfy an allowlist entry of `*.example.com`, and `handleRequest` echoes the raw attacker `Origin` value back in `Access-Control-Allow-Origin`, granting the attacker's page a CORS-allowed cross-origin read of gateway responses.

The root cause is that `strings.HasSuffix(originHost, allowedHost)` treats any string ending in the allowed substring as a match, with no check that the character immediately preceding the matched suffix is a `.`. For an allowlist entry `*.example.com`, `allowedHost` becomes `example.com`, and `HasSuffix("evilexample.com", "example.com")` evaluates to `true` even though `evilexample.com` is not a subdomain of `example.com`. There is no other validation step upstream (scheme/port checks in the same function are unrelated boundary conditions and do not mitigate the host-suffix issue) that catches this. Because `handleRequest` sets `Access-Control-Allow-Origin` to the literal attacker-supplied `origin` string once `isAllowedOrigin` returns true, this is a genuine allowlist-bypass bug reachable by any unauthenticated client capable of sending an HTTP request with a crafted `Origin` header — no credentials or special role required.

## Impact Explanation
This is a broken allowlist implementation in an internet-facing component (the gateway HTTP server), which maps to the "allowlist bypass" / CORS-misconfiguration impact class. An operator who configures a wildcard entry (a documented, supported pattern shown in the code comment `*.remix.com` and covered by the existing wildcard tests in `core/services/gateway/network/httpserver_test.go`) unintentionally also allows any domain that merely ends with the same character sequence, without an intervening label separator, to receive CORS approval and have its JavaScript read gateway responses cross-origin. The severity is bounded by the fact that gateway authentication uses a Bearer/JWT `Authorization` header (not cookies) per `handleRequest`'s `jwtToken` extraction, so the browser will not automatically attach credentials cross-origin unless the victim page/script explicitly supplies them; still, the allowlist itself is demonstrably broken as implemented.

## Likelihood Explanation
Exploitation requires only that (a) the operator configures a wildcard `CORSAllowedOrigins` entry (a normal, intended configuration path, not a misconfiguration in the excluded sense — it's the code's own advertised feature) and (b) an attacker controls a domain sharing the trailing character sequence without a preceding dot. This is fully reachable by an unprivileged remote client sending ordinary HTTP requests with a forged `Origin` header; no authentication, elevated role, or host access is needed.

## Recommendation
Anchor the suffix match to a label boundary:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
This ensures only genuine subdomains of the allowed host satisfy the wildcard rule.

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.example.com"}` (mirrors the existing test harness in `core/services/gateway/network/httpserver_test.go`, e.g. `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`).
2. Send an HTTP POST to the gateway path with header `Origin: https://evilexample.com`.
3. Observe the response contains `Access-Control-Allow-Origin: https://evilexample.com`, confirming `isAllowedOrigin` incorrectly returned `true` for a non-subdomain host.
4. Add a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` asserting that `origin := "https://evilexample.com"` against `[]string{"https://*.example.com"}` should yield an empty `Access-Control-Allow-Origin` header; the current code fails this assertion.
