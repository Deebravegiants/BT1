### Title
Attacker-crafted order with a poisoned/reverting input token permanently bricks `RedeemEscrow`/`RefundEscrow` for the whole order - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw` in `IntentsBase.sol` iterates over `body.tokens` and calls `safeTransfer`/`_sendValue` for every entry, reverting the entire call if any single token transfer fails. [1](#0-0)  The `tokens` array in the `WithdrawalRequest` is derived directly from `order.inputs`, which is fully attacker-controlled at `placeOrder` time (the order creator picks the token list) and is later replayed verbatim into the `RedeemEscrow`/`RefundEscrow` post body dispatched back to the source chain. [2](#0-1) 

### Finding Description
This mirrors the Teller `CollateralManager` bug class: a loop over an attacker-influenced list of token transfers where one poisoned/malicious entry (e.g. a token that always reverts on `transfer`, or a blacklist/pausable token) causes the entire settlement loop to revert, permanently freezing every other legitimate asset bundled with it. In Teller, the list was appendable post-approval by a third party; here, the equivalent attacker surface is the order creator (an unprivileged, ordinary caller of `placeOrder`) choosing `order.inputs` to include a token that will unconditionally revert on `transfer`/`transferFrom` when escrow is later released, alongside legitimate collateral value. Because `_withdraw` is a single all-or-nothing loop over `body.tokens` with no per-token isolation/try-catch, and no validation exists at `placeOrder` restricting or vetting the tokens list, a malicious or negligent order can be crafted such that:

- The destination-chain solver fulfills the order and pays out real value to the beneficiary via `_fillCrossChain`, transferring tokens/value before dispatching the `RedeemEscrow` request. [2](#0-1) 
- When `RedeemEscrow` lands on the source chain and `onAccept`/`_withdraw` executes, iterating `body.tokens` in order, hitting the poisoned token causes `IERC20(token).safeTransfer` to revert, reverting the whole transaction. [1](#0-0) 
- Because `_filled[commitment]` is set for finalize but the transaction as a whole reverts, the escrowed legitimate tokens (and accrued transaction fees) alongside the poisoned token entry become permanently unredeemable — no unilateral or partial-redemption path exists to skip the bad entry, so the solver who already paid on the destination chain gets nothing back.

The same loop-and-revert-together pattern also exists in the mirrored implementations (`evm/tron/contracts/apps/IntentGatewayV2.sol` `withdraw()`), confirming this is systemic to the withdrawal implementation, not a one-off. [3](#0-2) 

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by an unprivileged party who simply calls `placeOrder` with a crafted token list, with no privileged role required. It causes the solver who already delivered value on the destination chain to permanently lose the ability to redeem escrowed input tokens/fees on the source chain, and simultaneously locks the depositor's escrowed funds beyond recovery via the normal `RedeemEscrow`/`RefundEscrow` path, since both paths funnel through the same `_withdraw` loop.

### Likelihood Explanation
Likelihood assessment is **uncertain** without confirming whether `placeOrder` (or an earlier escrow step, e.g. in `evm/src/apps/IntentGatewayV2.sol`) enforces any allowlist, cap on `inputs.length`, or per-token safety checks (such as a pull-based/try-catch transfer, or restricting `inputs` to a fixed/short list of vetted tokens) before escrowing. I was not able to fully inspect `evm/src/apps/IntentGatewayV2.sol`'s `placeOrder` implementation within the available iterations to confirm the absence of such a safeguard, nor whether `SafeERC20.safeTransfer` failures from a malicious token are otherwise contained. If no allowlist or isolation exists, likelihood is high since crafting a reverting ERC-20 is trivial and costs the attacker nothing beyond gas; if an allowlist/validation exists at order placement, this analog would not be exploitable and should be treated as **not applicable**.

### Recommendation
Given the above uncertainty, recommend: (1) confirming whether `placeOrder` validates/allowlists `order.inputs` tokens; if not, add such validation, and (2) regardless, make `_withdraw`'s per-token loop resilient to a single failing transfer — e.g., using low-level calls with try/catch that credit failed transfers to a separately claimable balance instead of reverting the whole withdrawal, so one malicious token cannot hold the rest of the escrow hostage.

### Proof of Concept
Conceptual, pending confirmation of `placeOrder` validation (not fully verified in the available context):
1. Attacker deploys a token `EvilToken` whose `transfer`/`transferFrom` always reverts.
2. Attacker calls `placeOrder` with `order.inputs = [ {legit_token, amount}, {EvilToken, amount} ]`, escrowing both.
3. A solver fills the cross-chain order via `_fillCrossChain`, paying the beneficiary the required output on the destination chain, and the contract dispatches `RedeemEscrow` back to source with `tokens = order.inputs` (including `EvilToken`). [2](#0-1) 
4. On the source chain, `onAccept` → `_withdraw` loops through tokens; the `EvilToken` transfer reverts, reverting the entire redemption. [1](#0-0) 
5. The solver, having already paid out on the destination chain, can never redeem the legit-token escrow or fees on the source chain; funds are permanently stuck.

Note: this PoC assumes `placeOrder` does not reject unvetted/arbitrary ERC-20 tokens — a detail not fully confirmed against `evm/src/apps/IntentGatewayV2.sol` within this investigation.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

                _sendValue(beneficiary, amount);
