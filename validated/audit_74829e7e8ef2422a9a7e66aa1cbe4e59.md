This confirms the vulnerability. `verify_signed_message` only checks that the signature is valid against `message` (the `Approval` struct built with `nonce: account::get_sequence_number(from)`), and it performs no state mutation whatsoever — it does not increment `from`'s sequence number, nor does it store the `proof` bytes as "consumed" anywhere. Since `transfer_from` is never submitted as a transaction *by* `from` (it's submitted by `spender`), `from`'s actual on-chain sequence number never advances as a result of this call.

### Title
Signature replay in `usdk::transfer_from` allows unbounded draining of an approver's stablecoin balance - (File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move)

### Summary
`usdk::transfer_from` lets an owner pre-sign an off-chain `Approval{owner, to, nonce, chain_id, spender, amount}` message and lets `spender` execute the transfer on-chain via `primary_fungible_store::transfer_with_ref`. The intended one-time-use guarantee relies on `nonce: account::get_sequence_number(from)`, but this function never advances or consumes that sequence number, so the exact same `proof` can be replayed indefinitely, draining `from`'s stablecoin balance far beyond the amount they approved.

### Finding Description
`transfer_from` builds the expected message as: [1](#0-0) 
and validates it with `account::verify_signed_message`, which only checks the ed25519/multi-ed25519 signature against the constructed message and current auth key — it performs **no mutation of on-chain state**: [2](#0-1) 

The `nonce` field is populated from `account::get_sequence_number(from)`, which is the sequence number tracked by normal transaction execution for `from`'s own account: [3](#0-2) 

Because `transfer_from` is submitted by `spender` (not `from`), invoking it does not cause the Aptos VM to increment `from`'s sequence number the way a normal user-submitted transaction would. Nothing in `usdk.move` stores a per-approval "used" flag or an internal nonce counter tied to this specific approval flow. Consequently, once `from` signs a single `Approval` message for `spender`, `spender` can call `transfer_from` with the identical `proof` bytes repeatedly. Each call reconstructs the same `expected_message` (since `nonce` is still `from`'s unchanged sequence number), passes signature verification, and executes `primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount)`, moving `amount` out of `from`'s primary fungible store every time — until the store is empty.

### Impact Explanation
This is a custody-accounting break: an unprivileged `spender` (any holder of a validly signed approval, not an admin) can repeatedly withdraw funds from `from`'s fungible-asset store beyond the single authorized transfer, corrupting the intended custody accounting (one-time approved amount → unbounded balance drain). This is a direct theft of fungible-asset value tied to a live custody control path (`TransferRef`-gated primary-store transfer), matching the Custody Impact Gate's "Theft ... of ... fungible assets" and "Supply or custody accounting corruption that moves value to the wrong holder" criteria. Impact is High: total balance of any account that ever signs one `transfer_from` approval can be fully drained by the approved spender.

### Likelihood Explanation
Likelihood is High for any deployment of this pattern: it requires no admin compromise, no race condition — merely that `spender` retains the `proof` bytes from one legitimate approval (which they must have, in order to execute the first transfer) and calls the public `transfer_from` function again with the same arguments. There is no time delay, cooldown, or additional check preventing resubmission.

### Recommendation
Track approval usage explicitly on-chain rather than relying on the account's global transaction sequence number, e.g., store a `Table<address, u64>` of last-used per-`(owner, spender)` nonces (or a used-`proof`-hash set) inside `usdk`'s own state, increment/mark it inside `transfer_from` before or after the transfer, and include that internal nonce (not `account::get_sequence_number`) in the signed `Approval` message so each signature can only be redeemed once.

### Proof of Concept
1. `owner` (`from`) signs an `Approval { owner: from, to, nonce: N, chain_id, spender, amount }` off-chain and hands the signature (`proof`) plus `from_public_key` to `spender`.
2. `spender` calls `usdk::transfer_from(spender, proof, from, scheme, from_public_key, to, amount)`. `assert_not_paused`/`assert_not_denylisted` pass, `account::get_sequence_number(from)` still equals `N` (unchanged, since `from` has not sent any transaction), so `expected_message` matches, signature verifies, and `amount` is transferred from `from` to `to`.
3. `spender` calls the exact same `transfer_from(spender, proof, from, scheme, from_public_key, to, amount)` again. `account::get_sequence_number(from)` is still `N` (this call is submitted by `spender`, and nothing increments `from`'s sequence number), so `expected_message` is identical again, signature re-verifies successfully, and another `amount` is withdrawn from `from`.
4. Repeat step 3 until `from`'s store balance is exhausted — total drained can be an arbitrary multiple of the single `amount` the owner intended to approve once.
