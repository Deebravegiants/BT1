### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value used by the registry to identify which tenant a webhook belongs to comes from the unsigned `x-shopify-shop-domain` / `shopify-shop-domain` header. Because that header is never part of the signed material, the binding "HMAC-authenticated request == shop attributed to that request" does not hold, letting a party who already possesses one valid (body, HMAC) pair reuse it while claiming an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` — it does not fold in any header value: [2](#0-1) 

Yet `Request#shop` — the value used by the registry to attribute the webhook to a specific merchant — is read straight from the (unauthenticated) `shop-domain` header, with no cryptographic tie to the HMAC: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC over the body and then dispatches the handler using `request.shop` taken from that same unauthenticated header: [4](#0-3) 

The security invariant this gem is supposed to provide is: *"a webhook whose HMAC verifies came from Shopify for the shop it claims to be from."* In reality the gem only proves *"the body was signed with `api_secret_key`"* — the shop attribution is asserted, not authenticated. Since `api_secret_key` is shared across every shop that installs a given app, anyone who is themselves a legitimate merchant of the app (an unprivileged installer, not the app's `client_secret` holder) can observe one authentic `(body, hmac)` pair delivered to their own endpoint and resend it with the `shop-domain` header rewritten to a different, victim shop. `HmacValidator.validate` still returns `true` because the body/HMAC pair is unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: a webhook handler that uses `data.shop` (built from `request.shop`) to select which merchant's records to create/update/delete, or to look up which stored session/access token to act with, can be tricked into performing that action against the wrong tenant's data — cross-tenant access/injection using only a body+HMAC pair the attacker legitimately possesses for their own shop.

### Likelihood Explanation
Any app that receives webhooks for more than one shop (the standard multi-tenant SaaS pattern that this gem's `Webhooks::Registry`/`WebhookMetadata` design assumes) is affected. The prerequisite — being a merchant who has installed the app and can observe/replay one valid webhook delivery — is an ordinary, unprivileged capability, not a leaked secret or privileged account.

### Recommendation
Bind the shop identity into the material that is HMAC-verified (e.g., require the `shop-domain` header, together with the body, to be part of `to_signable_string`, or independently verify that the shop reported in the header matches a shop value embedded in the signed payload) so that `Registry.process`/`WebhookMetadata` can only attribute a verified webhook to the shop that was actually authenticated by the signature.

### Proof of Concept
1. Install the target app on shop A (`a-shop.myshopify.com`) and receive a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: a-shop.myshopify.com` (H = HMAC-SHA256(`api_secret_key`, `B`), matching `to_signable_string` in `lib/shopify_api/webhooks/request.rb`).
2. Replay the identical request to the app's webhook endpoint, but change only the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body `B` and HMAC `H` unchanged.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12`) recomputes the HMAC over `B` only, matches `H`, and returns `true`.
4. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188`) proceeds and calls the handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though the request never involved the victim shop or Shopify's servers at all.
