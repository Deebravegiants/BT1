Audit Report

## Title
Cross-user response hijacking via un-scoped `savedCallbacks` map keyed only by client-supplied `MessageID` - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` stores the caller's response callback in `h.savedCallbacks` keyed solely by `msg.Body.MessageID`, with no binding to the caller's `Sender` identity, even though `Sender` is already computed and available on the validated message. A second unprivileged caller who submits a request with a colliding `MessageID` before the first caller's DON response arrives silently overwrites the first caller's callback slot, so the first caller's forwarded-to-DON response is later delivered to the second caller.

## Finding Description
`HandleLegacyUserMessage` is reached from any unprivileged client through `gateway.ProcessRequest` for legacy (DON-ID-bearing) requests [1](#0-0) . After validating the message signature (which populates `msg.Body.Sender` via `ExtractSigner`) [2](#0-1) , the handler saves the callback keyed only by `MessageID`, discarding the already-known `Sender`: [3](#0-2) 

No check exists for whether an entry under that key is already occupied by a pending request from a different sender — the assignment unconditionally overwrites. When a DON node later responds, the handler looks up and deletes whatever sits at that key by `MessageID` alone and delivers to it, with no sender/session cross-check against the original requester: [4](#0-3) 

The `MessageID` used as the map key is fully attacker-controlled: for the outer JSON-RPC decode, `msg.Body.MessageID` is overwritten with the raw JSON-RPC `request.ID` supplied by the client [5](#0-4) , and the only server-side constraints are a length bound (`MessageIDMaxLen`/200-char cap) and a null-byte suffix check [6](#0-5) [7](#0-6)  — there is no uniqueness/randomness enforcement. Each caller signs their own message including their own chosen `MessageID`, so an attacker can legitimately, validly sign a request carrying any `MessageID` string of their choosing, including one equal to a victim's in-flight ID. The sibling `RequestCache` implementation in the same package family already demonstrates the correct pattern of scoping by `(sender, id)` via `globalID{sender, id}` [8](#0-7) , confirming this handler's map is missing an available, straightforward mitigation.

The existing sender check in `HandleNodeMessage`/`handleWebAPITriggerMessage` only verifies that the responding DON node matches `nodeAddr` [9](#0-8) ; it does not verify that the callback being delivered belongs to the same original requester, so this check is insufficient to prevent the described hijack.

## Impact Explanation
This is a genuine cross-user response confusion in the Gateway's legacy web API trigger path: an unprivileged caller can, by choosing a `MessageID` colliding with another in-flight caller's ID, receive the victim's DON response (containing that victim's workflow-trigger output) or cause the victim to receive the attacker's own response/no response at all. This falls under the in-scope "cross-user response corruption" impact category for a Gateway handling unprivileged client requests.

## Likelihood Explanation
The attacker needs no privileges beyond being able to send a normal signed legacy request to the Gateway — the same access any legitimate `web_api_trigger` caller has. Exploitability is bounded by the `defaultCallbackMaxAgeSec` (120s) window during which a victim's request must still be pending [10](#0-9) , and by whether the attacker can predict/observe the victim's chosen `MessageID`. Since `MessageID` is fully client-chosen with no server-enforced uniqueness or entropy requirement, clients using predictable ID schemes (e.g., sequential counters, a common JSON-RPC client pattern) make collisions trivial to force deliberately; clients using high-entropy random IDs make it harder but the underlying missing ownership/scoping check remains a real defect regardless of the calling client's ID generation strategy.

## Recommendation
Scope `savedCallbacks` by both `MessageID` and the validated `msg.Body.Sender` (mirroring `globalID{sender, id}` in `RequestCache`), and reject or otherwise fail to overwrite an existing pending entry that belongs to a different sender for the same `MessageID`, rather than silently overwriting it in `HandleLegacyUserMessage`.

## Proof of Concept
1. Client A (victim) sends a signed legacy `web_api_trigger` request to the Gateway with `MessageID = "X"`; `HandleLegacyUserMessage` stores victim's callback at `savedCallbacks["X"]` and forwards the request to all DON members.
2. Before any DON node responds, Client B (attacker) sends their own validly signed legacy request also using `MessageID = "X"`; `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with attacker's callback (no ownership check performed).
3. A DON node responds for `MessageID = "X"` (the response destined for victim's original request); `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds attacker's callback, deletes the entry, and delivers the DON's response to the attacker.
4. Victim's original HTTP call to the Gateway times out (or, if attacker's own forwarded request also completes and a DON response for it arrives afterward under key `"X"`, victim's callback — if instead it were the second write — would receive attacker's data), demonstrating the cross-user response hijack via the unscoped map key.

A Go unit/integration test can instantiate two `handlers.Callback` objects, call `handler.HandleLegacyUserMessage` twice with distinct signers but identical `Body.MessageID`, then invoke `handler.HandleNodeMessage`/`handleWebAPITriggerMessage` once and assert which callback's `SendResponse` is invoked, confirming the second caller's callback receives the response intended for the first.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
