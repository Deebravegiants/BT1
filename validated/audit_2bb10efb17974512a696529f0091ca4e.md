## Title
OAuth Callback Sends `client_secret` to an Unvalidated `shop` Host, Allowing SSRF/Credential Exfiltration via a Signed but Unsanitized `shop` Parameter - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` verifies the OAuth callback's HMAC over the raw `shop` string, but never runs that same `shop` value through `Utils::ShopValidator.sanitize!` before using it to build the session/host that receives the app's `client_secret` in the subsequent access-token exchange request. This breaks the intended equality: `shop value covered by HMAC` == `shop value that must be a trusted myshopify/Shopify host before it is trusted with client_secret`.

### Finding Description
In `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-113`), the HMAC check only proves that `auth_query.shop` (along with `code`, `host`, `state`, `timestamp`) was signed with the app's `api_secret_key` [1](#0-0) , [2](#0-1) . Immediately after that check passes, `auth_query.shop` is used verbatim to construct `null_session = Auth::Session.new(shop: auth_query.shop)`, and that session is passed into `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which then performs the `access_token` POST containing `client_id` and `client_secret` in the body [3](#0-2) .

`HttpClient#initialize` builds the destination host directly from `session.shop` with no format/domain validation: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) . Unlike `TokenExchange.exchange_token` and `TokenExchange.migrate_to_expiring_token`, which explicitly call `Utils::ShopValidator.sanitize!(shop)` before building the session that is used to send `client_secret` [5](#0-4) , the Authorization Code Grant path (`validate_auth_callback`) has no equivalent call to `ShopValidator` anywhere in `lib/shopify_api/auth/oauth.rb`. The `shop` used for HMAC verification and the `shop` used to pick the host that receives `client_secret` are treated as the same trusted value, but only the signature is checked — the value's format/domain is never checked to be a genuine `*.myshopify.com` (or other `TRUSTED_SHOPIFY_DOMAINS`) host as defined in `Utils::ShopValidator` [6](#0-5) .

This matters because the callback endpoint in a hosting application is typically built by echoing request parameters (`shop`, `code`, `hmac`, `host`, `state`, `timestamp`) into `AuthQuery.new`, exactly as shown in the gem's own docs example [7](#0-6) . If a legitimate merchant is redirected through a normal OAuth start (`begin_auth`) but the `shop` value that ultimately reaches `validate_auth_callback` is not re-derived/sanitized by the host app (which the gem's docs do not instruct it to do, since the gem itself performs no such sanitization here), and if Shopify's callback redirect or an intermediary allows a non-canonical `shop` string that nonetheless is valid input to `URI.encode_www_form` and gets HMAC-signed by Shopify for the given `code`/`state` pair, the gem will still send `client_id`/`client_secret` to whatever host `session.shop` evaluates to.

### Impact Explanation
If the `shop` value used to compute the HMAC and the `shop` value used to build the outbound `admin/oauth/access_token` request host are not both constrained to a genuine Shopify domain, the app's `client_secret` (and the OAuth authorization `code`) could be sent to an attacker-influenced host — an SSRF carrying the app's credentials, potentially leaking the `client_secret` and authorization code to a third party (High/Critical impact per the rules: SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
This requires an OAuth callback request whose `shop` parameter is not a properly formatted/trusted Shopify domain but which still passes HMAC verification with a genuine `api_secret_key`. This can only occur if Shopify itself would sign such a callback (unlikely, since Shopify generates the callback), or if the host application's controller passes through a manipulated `shop` param before constructing `AuthQuery` — a scenario partially outside pure gem control. The likelihood is therefore moderate/uncertain: the gem's `TokenExchange` module already treats this as a real risk (it explicitly sanitizes `shop` before use), but `Oauth.validate_auth_callback` — which handles the same trust boundary (a shop string → a network destination that receives `client_secret`) — has no equivalent guard. This inconsistency between the two OAuth flows in the same gem is the root cause worth flagging even though full exploitability depends on how a calling application wires up the callback route.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb`), call `Utils::ShopValidator.sanitize!(auth_query.shop)` (as already done in `TokenExchange.exchange_token`/`migrate_to_expiring_token`) and use the sanitized/validated host both for constructing `null_session` and for the resulting `Session` object, before performing the `access_token` exchange that transmits `client_secret`.

### Proof of Concept
1. A malicious or compromised intermediary crafts (or a host app forwards) an OAuth callback with a `shop` parameter that is a syntactically-valid string accepted by `URI.encode_www_form`/HMAC signing but is not constrained to `*.myshopify.com` (e.g., contains a `.` making it pass through `ShopValidator`'s absence unchecked in this path).
2. `AuthQuery.new(code:, shop:, timestamp:, state:, host:, hmac:)` is built directly from the raw request parameters, matching the documented integration pattern in `docs/usage/oauth.md:246-251`.
3. `ShopifyAPI::Auth::Oauth.validate_auth_callback` passes HMAC validation (since the request was signed over exactly this `shop` value) and proceeds to `Auth::Session.new(shop: auth_query.shop)` → `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`.
4. `HttpClient#initialize` sets `@base_uri = "https://#{session.shop}"` unchecked, and `client.request(...)` POSTs `{client_id, client_secret, code, expiring}` to `https://<attacker-influenced-shop>/admin/oauth/access_token`, exfiltrating the app's `client_secret` and the authorization `code` to the attacker-controlled host.

**Uncertainty / what I could not fully verify:** I was unable to confirm within the available index whether Shopify's real OAuth redirect mechanism (outside this gem) could ever produce a signed callback with a non-canonical `shop` string, nor could I trace how downstream framework integrations (e.g., `shopify_app`) populate the `shop` parameter before constructing `AuthQuery`. The root-cause code inconsistency (missing `ShopValidator.sanitize!` call in `validate_auth_callback` versus its presence in `TokenExchange`) is confirmed directly in the gem source, but full end-to-end exploitability depends on factors outside this gem's own code that I could not verify with the tools available.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
```
