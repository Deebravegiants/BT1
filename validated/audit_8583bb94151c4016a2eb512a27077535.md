### Title
`convert_to_erc20`/`convert_to_balance` scaling formula breaks (and silently applies no scaling) when the ERC20 side has fewer decimals than the local asset - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The `pallet-hyper-fungible-token` boundary-scaling helpers assume the EVM/ERC20-side decimals (`erc_decimals`) are always greater than or equal to the local asset's decimals (`local_decimals`). When a registered token pair has the opposite relationship (a completely legitimate, non-malicious configuration — e.g. a local 18-decimal wrapped asset paired with a 6-decimal ERC20 like USDC), the exponent used for scaling collapses to zero via `saturating_sub`, and amounts are transmitted/credited unscaled. This is the same class of bug as the referenced LoopFi `CDPVault.liquidatePosition()` finding: a scaling factor that is correctly applied in some code paths/configurations but silently skipped in others, leading to wrong amounts of value moving across a trust boundary.

### Finding Description
The conversion helpers are: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`. This is only correct when `erc_decimals >= local_decimals`:
- `convert_to_erc20` should multiply by `10^(erc_decimals - local_decimals)` when `erc_decimals > local_decimals`, but should **divide** by `10^(local_decimals - erc_decimals)` when `local_decimals > erc_decimals`. Instead, `saturating_sub` returns `0` in that case, so the exponent becomes `0` and the value is passed through completely unscaled.
- Symmetrically, `convert_to_balance` should multiply when `local_decimals > erc_decimals`, but instead divides by `10^0 = 1`, again passing the raw ERC20 amount through unscaled.

This mirrors the `tokenScale` inconsistency in the LoopFi report: the scaling logic implicitly assumes one fixed ordering of decimals (there, `tokenScale <= 1 ether`; here, `erc_decimals >= local_decimals`) and silently degrades to a no-op scaling factor outside that assumption, rather than erroring or handling the reverse case.

The helpers are used on both the outbound and inbound paths:

Outbound `send()` — burns/escrows `params.amount` in local units, then converts to the ERC20 amount that gets embedded in the cross-chain `Message` and dispatched via ISMP to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, which mints/unlocks exactly that amount: [2](#0-1) 

Inbound `on_accept()` — converts the incoming ERC20 `U256` amount back into local balance units before minting/releasing to the beneficiary: [3](#0-2) 

`on_timeout()` performs the same conversion when refunding an undelivered send: [4](#0-3) 

`Precisions`/`ChainConfig.decimals` is set via `register_token`/`update_token` and is documented simply as "ERC20 decimals on that chain" with no constraint that it must be `>=` the local asset's decimals: [5](#0-4) 

### Impact Explanation
If a token is registered where the local asset's decimals exceed the configured EVM-side decimals (e.g., a locally 18-decimal representation paired with a 6-decimal ERC20 like USDC — a realistic, non-malicious setup, not requiring any adversarial admin action beyond normal registration per the documented fields), then:

- On `send()`: `convert_to_erc20` fails to divide down, so the `Message.amount` delivered to the destination EVM contract is inflated by `10^(local_decimals - erc_decimals)` relative to what was actually burned/escrowed on the source chain. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will mint or unlock that inflated amount to the recipient — an unbacked mint that drains the destination custody pool or fabricates tokens far exceeding the value actually locked/burned on the source chain. This is a direct theft/unbacked-mint vector reachable by any signed account calling `send()`.
- On `on_accept()`/`on_timeout()`: the reverse direction under the same misconfiguration under-credits users receiving inbound transfers or refunds by the same factor, i.e., permanent loss of the difference for the depositor — analogous to Frank being unable to withdraw his collateral in the original LoopFi PoC.

Given the direct path to unbacked minting / theft of protocol-custodied funds through a normal `send()` call, this qualifies as at least Medium severity (matching the judged severity of the original LoopFi finding), potentially High depending on custody amounts at risk.

### Likelihood Explanation
The trigger condition is a token registration where `erc_decimals < local_decimals`. Nothing in `register_token`/`update_token` or the pallet's types enforces `erc_decimals >= local_decimals`, and the documentation gives no such guidance to the CreateOrigin operator — it is a foreseeable, ordinary configuration (many chains represent bridged stablecoins like USDC at 18 decimals locally while the true ERC20 is 6 decimals). Once such a pair exists, every unprivileged `send()` call against it triggers the bug; no attacker-controlled or malicious-admin action is required beyond a plausible registration that the pallet does nothing to prevent or flag.

### Recommendation
Fix `convert_to_erc20` and `convert_to_balance` to handle both orderings of `erc_decimals` vs `local_decimals` symmetrically, e.g.:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the mirrored fix for `convert_to_balance`. Additionally, consider validating at `register_token`/`update_token` time (or documenting explicitly) the expected decimal ordering, and add test coverage for `erc_decimals < local_decimals` pairs.

### Proof of Concept
1. Governance registers a local asset `X` with `local_decimals = 18` (e.g. an `Assets` pallet asset or the chain's native currency) and configures its EVM-chain `Precisions`/`ChainConfig.decimals = 6` (a plausible pairing with a 6-decimal ERC20 like USDC), via `register_token`.
2. A user calls `send(SendParams { asset_id: X, amount: 1 * 10^18, destination, recipient, ... })`, escrowing/burning 1 token (in 18-decimal local units).
3. Inside `send()`, `erc_decimals = 6`, `local_decimals = 18`. `convert_to_erc20(1e18, 6, 18)` computes exponent `6.saturating_sub(18) = 0`, so `erc20_amount = 1e18 * 10^0 = 1e18` — i.e. the same raw value, now misinterpreted as a 6-decimal ERC20 amount (`1,000,000,000,000 USDC` worth, instead of `1 USDC`).
4. This inflated `amount` is ABI-encoded into the `Message` and dispatched via ISMP `DispatchPost` to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract.
5. On delivery, the destination contract mints/unlocks `1e18` raw ERC20 units (`1,000,000,000,000` USDC-equivalent) to the recipient, vastly exceeding the single token that was actually escrowed/burned on the source chain — an unbacked mint / drain of the destination custody pool.
