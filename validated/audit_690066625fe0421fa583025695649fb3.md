### Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC is computed only over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values used afterwards to identify the tenant and dispatch the handler come from unauthenticated HTTP headers that are never part of the signed material. An attacker who can supply any valid `(raw_body, hmac)` pair for the configured `api_secret_key` (e.g. by replaying/legitimately receiving one webhook delivery for a shop they control) can resend the same body with a forged `shop-domain` header, and the gem will report the request as valid and hand the spoofed shop identity to the app's handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/compares the signature purely against `to_signable_string`: [2](#0-1) 

`Registry.process` uses this HMAC check as the sole authenticity gate, then trusts `request.shop`, `request.topic`, `request.webhook_id` — all sourced from headers — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no relation to the signed payload: [4](#0-3) 

The identity binding that should hold is: `shop asserted by the request == shop bound by the HMAC signature`. Because the signature only covers `raw_body`, this equality never actually holds — any header value can be substituted post-hoc without invalidating the HMAC. Concretely: before an attack, a genuine delivery has `(body=B, hmac=HMAC(B), shop-domain=S)`. An attacker can resend `(body=B, hmac=HMAC(B), shop-domain=S')` for any `S'`, and `HmacValidator.validate` still returns `true` because it never inspects `shop-domain`.

### Impact Explanation
This breaks tenant isolation: the app's webhook handler is invoked with `WebhookMetadata#shop` pointing to an arbitrary shop while `HmacValidator` reports the request as authentic. Any host application that follows this gem's documented pattern of trusting `WebhookMetadata.shop` after `Registry.process` succeeds (which is the intended and only documented usage) can be made to attribute one shop's webhook payload (orders, customer data, GDPR events, uninstall events, etc.) to a different shop, resulting in cross-tenant data confusion/injection. This matches the Critical "cross-tenant access" impact category, since the attacker needs no access to `api_secret_key` or any credential belonging to the victim shop — only a valid `(body, hmac)` pair from any shop that installed the same app.

### Likelihood Explanation
Exploitability requires the attacker to possess one legitimate `(raw_body, hmac)` pair generated by Shopify for the shared `api_secret_key` — trivially obtainable by installing the target app on an attacker-controlled development/test store and capturing one webhook delivery. From there, forging the `shop-domain` (and `topic`/`webhook_id`) headers on a replayed POST to the app's public webhook endpoint requires no further secrets, so likelihood is high wherever a host app relies on `WebhookMetadata.shop` as the tenant key, which is the gem's documented pattern.

### Recommendation
Bind the tenant-identifying and dispatch-relevant fields (`shop`, `topic`, possibly `webhook_id`) into the signed material, or otherwise cryptographically tie them to the verified body — e.g., by including them in `to_signable_string`, or by requiring the host app to cross-check `shop` against a known/expected value from session storage rather than trusting the header verbatim. At minimum, document prominently that `HmacValidator.validate`/`Registry.process` only authenticates the payload body and that `shop`/`topic` headers are unauthenticated, so callers do not use them as a trust boundary.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B`, header `shopify-hmac-sha256: H = HMAC-SHA256(api_secret_key, B)`, `shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same body `B` and hmac `H` to the app's webhook endpoint, but set `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, so validation succeeds: [5](#0-4) 
4. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload and signature originated from the attacker's own shop, demonstrating the cross-tenant identity confusion.
