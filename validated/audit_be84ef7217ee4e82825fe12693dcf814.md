### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC-SHA256 of the raw request body. The `shop` (and `topic`/`webhook_id`) that the gem hands to the app's handler are taken straight from unauthenticated HTTP headers that are never part of the signed payload, so an attacker who possesses any single genuine (body, hmac) pair can replay it while freely relabeling which shop the event is attributed to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers that are never mixed into that signable string: [2](#0-1) 

`Registry.process` validates only the HMAC of that signable string (i.e. the body) and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC only over `verifiable_query.to_signable_string`, using `Context.api_secret_key` (or the old key): [4](#0-3) 

The identity-binding equality the gem should enforce is:
`shop_covered_by_hmac == shop_delivered_to_handler`

In reality the left side is empty (the HMAC only covers the body), while the right side is fully attacker-controlled via the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. Because Shopify's webhook HMAC by design signs only the body, this gem never re-binds the `shop` header to that signed content, so `process()` cannot distinguish "this body was genuinely delivered for shop X" from "this body was genuinely delivered (for some shop), replayed with header claiming shop Y."

### Impact Explanation
Any entity capable of legitimately receiving one webhook delivery from Shopify (e.g., an attacker who installs the target app on their own store — a completely unprivileged action requiring no credentials belonging to the victim or the app) obtains a valid `(raw_body, hmac)` pair. They can then POST that exact body/HMAC to the app's shared webhook endpoint while substituting the `shop-domain` header with an arbitrary victim shop's domain. `Registry.process` will accept it as authentic (`Errors::InvalidWebhookError` is not raised) and invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any app logic keyed by `data.shop` (looking up the shop's stored access token/session, updating per-shop state, attributing orders/inventory changes, etc.) is now operating under a falsified tenant identity — a cross-tenant confusion/injection primitive, without the attacker ever needing the app's `client_secret` or any merchant's access token.

### Likelihood Explanation
The prerequisite — legitimately receiving at least one real webhook delivery — is trivial: any developer/merchant can install a public app on their own store and trigger events (orders, product updates, app/uninstalled, etc.) to harvest valid `(body, hmac)` pairs, then replay them against the same shared endpoint with a forged shop header. No secret material, TLS interception, or social engineering is required, and the gem provides no built-in defense (no nonce/timestamp/shop binding in the HMAC check) as shown above.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header into the value that is cryptographically verified — e.g. include them in `to_signable_string`, or independently confirm that `request.shop` matches an expected/registered shop domain for the given install before invoking the handler. Additionally, reject replays by tracking `webhook_id` (idempotency) per shop.

### Proof of Concept
1. App developer installs the target Shopify app on their own store `attacker-shop.myshopify.com`. Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's shared endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {"id":123, ...}
   ```
   Attacker records the exact raw body and `x-shopify-hmac-sha256` value.
2. Attacker replays the identical request to the same endpoint, only changing the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same-valid-hmac-of-same-body>
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {"id":123, ...}   (unchanged)
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `HMAC(body)`, which is unchanged. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., webhook_id: ...)`, causing the app to process attacker-supplied event data under the victim shop's identity.
