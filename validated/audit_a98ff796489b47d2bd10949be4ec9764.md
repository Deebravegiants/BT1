## Analysis

**Equality claimed to be broken:** the on-chain "owner" of a Uniswap V3 LP position (`ownerOf(tokenId) == Emporium`) should map back exclusively to the depositing user's shielded balance, so that any fees/liquidity `collect()`-ed from that position accrue only to that user's UTXO/stealth address. The claim is that `collect()`'s `recipient` parameter lets an attacker redirect those funds to `attackerStealth` with zero footprint in `deltaAmountChanges`/`utxoSet`.

This is confirmed by tracing the code:

- `EmporiumUpgradeable.runAction` executes attacker-controlled `EmporiumStack.ops` in a loop. CASE 2 (`op.invokeWallet == false` or `stack.signerAddress == address(0)`) performs a raw `op.endpoint.call{value: op.value}(op.callData)` with only a selector blacklist against `callHinkalWallet`/`doSendToRelay`. [1](#0-0) 
- `verifyWallet` skips all signature checks entirely when `stack.signerAddress == address(0)` — i.e., CASE 2 requires no wallet-owner authorization at all. [2](#0-1) 
- The only binding of `externalActionMetadata` (which contains the entire `EmporiumStack`, including `op.endpoint`/`op.callData`) to the ZK proof is a `keccak256` hash rolled into `circomData.calldataHash`, checked in `performHinkalChecks` via `CircomDataBuilder.getHashedCalldata`. [3](#0-2) [4](#0-3)  That hash only prevents *tampering after proof generation* — it does not constrain what an attacker, generating their own proof for their own (arbitrary, even trivial) UTXO, is allowed to put into `op.endpoint`/`op.callData`. The circuit (`MainEVMCircuit.circom`) never inspects the semantics of `externalActionMetadata`. [5](#0-4) 
- `runAction`'s post-call accounting only reconciles `circomData.erc20TokenAddresses` balances of `msg.sender` (Emporium itself) against `deltaAmountChanges`, and only mints a UTXO when `balanceChange > 0`. [6](#0-5) [7](#0-6)  Because Uniswap's `NonfungiblePositionManager.collect()` sends `amount0`/`amount1` directly to the attacker-supplied `recipient` (not to `msg.sender`), Emporium's own token balances never move, so `balanceChange == 0` for every tracked token — no revert, no UTXO minted, and the outer `Hinkal.transact` slippage/balance-equality checks (`balanceDif == amountChanges[i] + utxoAmount`) also pass trivially since `balanceDif == 0 == amountChanges[i] (attacker sets 0) + 0`. [8](#0-7) 
- `Hinkal.transact` → `performHinkalChecks`/`verifyProof`/`rootHashExists` only validate the attacker's *own* UTXO ownership and nullifiers; nothing here validates that `op.endpoint`/`op.callData` operate only on assets the attacker themselves deposited. [9](#0-8) 

The precondition that makes this exploitable — a victim's LP NFT ending up owned by the `Emporium` contract (e.g., via an earlier `mint()` stateless op where `recipient == Emporium`) — is architecturally consistent with how Emporium is designed to hold interim state across ops/transactions for composable stateless DeFi actions, since Emporium has no ERC721/NFT-position accounting layer at all; its accounting model (`getBalancesForArray`/`deltaAmountChanges`/`utxoSet`) is exclusively ERC20/ETH-balance-based. Any asset held by Emporium that falls outside that ERC20 accounting model (an owned NFT, an approval, a staking receipt, etc.) is unprotected: `onlyAllowedRecipient` only checks that the caller of `runAction` is `Hinkal` itself, not that the *content* of the op is scoped to the calling user's own assets. [10](#0-9) 

None of the listed guards (`performHinkalChecks`, `verifyProof`, `rootHashExists`, slippage/balance requires, `insertNullifiers`, `onlyAllowedRecipient`, `verifyWallet`, `nonReentrant`, circuit constraints) constrain the *target* or *recipient* of an arbitrary stateless external call — they only validate that the caller legitimately owns the UTXOs being spent/created in that same transaction, which is unrelated to third-party state (like another user's NFT position) that Emporium happens to hold custody of.

### Title
Any user can hijack another user's Uniswap V3 LP position custodied by Emporium via unrestricted CASE 2 `collect()` calls with attacker-controlled `recipient` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction`'s stateless CASE 2 branch performs an unrestricted low-level `call` to any `op.endpoint`/`op.callData` supplied by whoever submits a valid Hinkal proof for their *own* UTXOs, with no check that the call only touches assets belonging to the caller. Because Emporium can end up as the on-chain owner of a Uniswap V3 position NFT (from an earlier stateless `mint`), any unrelated attacker can call `positionManager.collect(tokenId, attackerStealth, ...)` through Emporium, redirecting the victim's accrued fees/liquidity straight to themselves, entirely outside Emporium's ERC20-only balance/UTXO accounting.

### Finding Description
Emporium's balance reconciliation in `runAction` only tracks `circomData.erc20TokenAddresses` balances of `msg.sender` (Emporium) before/after the op loop and mints a UTXO only when Emporium's own balance rises. `collect()` on Uniswap's `NonfungiblePositionManager` sends `amount0`/`amount1` to an arbitrary `recipient` parameter, bypassing `msg.sender`'s balance entirely, so Emporium's balance is unchanged (`balanceChange == 0`), no revert fires, and no UTXO is minted — the transfer is completely invisible to Hinkal's shielded accounting. The attacker only needs a valid Hinkal proof over their own (even trivial/zero-value) UTXO; the CASE 2 branch requires no wallet signature (`verifyWallet` returns early when `stack.signerAddress == address(0)`) and the only binding of the malicious `EmporiumStack`/`op.callData` to the proof is a hash check (`calldataHash`) that the attacker themselves computes and controls when generating their own proof. Since `NonfungiblePositionManager.collect` authorizes solely on `msg.sender == ownerOf(tokenId)` (i.e., Emporium, as recorded on the Uniswap contract, regardless of which Hinkal user originally deposited it), any attacker can drain any LP position custodied by Emporium.

### Impact Explanation
Critical — direct theft of a victim's already-accrued (and not-yet-collected) LP fees/liquidity, an action the victim never authorized, executed by an unprivileged third party. Repeatable for every LP position Emporium ever custodies and for every future round of accrued fees until the position is fully drained or withdrawn by the legitimate owner.

### Likelihood Explanation
Requires only that some victim previously left a Uniswap V3 position with Emporium as the NFT owner via a stateless `mint` op (a normal usage pattern for composable, multi-step stateless DeFi flows) and that the position has accrued fees/liquidity. Attacker cost is a single `transact()` call with a proof over their own funds (which can be minimal) plus knowledge of the victim's `tokenId` (discoverable on-chain via `Transfer`/`Mint` events or `ownerOf` scans). No relayer, admin, or victim cooperation needed.

### Recommendation
Do not allow Emporium (or any stateless external-action executor) to become the long-term on-chain owner/approver of non-fungible or non-ERC20-accounted assets across transactions. Either (a) forbid `mint`-type ops from setting `recipient == Emporium`/require immediate transfer-out in the same transaction, (b) track NFT/position custody per-depositor (e.g., via an on-chain registry keyed by the depositor's identity, checked before allowing further ops on that `tokenId`), or (c) restrict CASE 2 `op.endpoint`/selector to an allowlist that excludes calls capable of redirecting funds to a `recipient` param not equal to `msg.sender`/Emporium itself.

### Proof of Concept
Foundry fork test plan:
1. Deploy `EmporiumUpgradeable`, register it in `Hinkal` as the `HINKAL_EMPORIUM_ACTION_ID` external action.
2. Victim calls `transact()` with a valid proof spending their own UTXO, `externalActionMetadata` encoding an `EmporiumStack` with a CASE 2 op: `endpoint = positionManager`, `callData = mint(...)` with `recipient = address(Emporium)`. Assert `positionManager.ownerOf(tokenId) == address(Emporium)` after.
3. Let fees accrue (simulate swaps against the pool).
4. Attacker (unrelated address, no relationship to victim's funds) calls `transact()` with a valid proof over their own trivial UTXO, `externalActionMetadata` encoding an `EmporiumStack` with a CASE 2 op: `endpoint = positionManager`, `callData = collect({tokenId: victimTokenId, recipient: attackerStealth, amount0Max: type(uint128).max, amount1Max: type(uint128).max})`, `deltaAmountChanges` for token0/token1 set to 0.
5. Assert: `token0.balanceOf(attackerStealth)` and `token1.balanceOf(attackerStealth)` increased by the collected fee amounts; assert no UTXO was returned for token0/token1 (`utxoSet.length == 0` for those tokens); assert Emporium's own token0/token1 balances are unchanged (`balancesBefore == balancesAfter`), proving the theft is completely untracked by Hinkal's accounting.
