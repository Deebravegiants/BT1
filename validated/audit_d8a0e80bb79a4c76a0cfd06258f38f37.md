### Title
Fee-on-transfer tokens cause escrow over-crediting and permanent fund freezing in the Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` escrows tokens by crediting `_orders[commitment][token]` with the user-declared (fee-reduced) input amount rather than the amount actually received by the contract. If the input token charges a transfer fee, the contract's internal escrow accounting will exceed its real token balance, eventually causing withdrawal reverts (frozen funds) for legitimate order fillers/refund claimants. This is the exact bug class from the referenced report ("Vault can't receive deposits if underlying token charges fees on transfer"), except here it manifests as escrow insolvency/fund freezing rather than a deposit-time revert, because the mainline EVM gateway (`evm/src/apps/IntentGatewayV2.sol`) was hardened against fee-on-transfer tokens but the Tron gateway was not updated to match.

### Finding Description
In `placeOrder`, `reducedInputs[i].amount` is derived purely from the order's stated `order.inputs[i].amount` minus the protocol fee — it is never adjusted for actual tokens received: [1](#0-0) 

Tokens are then pulled via `safeTransferFrom` with no balance-delta check, and the escrow is unconditionally incremented by `reducedInputs[i].amount`: [2](#0-1) 

The same unchecked pattern exists in the predispatch branch, which sweeps the dispatcher's `balanceOf` but still credits escrow with `reducedInputs[i].amount` rather than the swept amount: [3](#0-2) 

Compare this to the mainline EVM gateway, which was explicitly fixed to measure `balanceOf` before/after each transfer and mutate `order.inputs[i].amount` to the actual received amount before computing the commitment and crediting escrow: [4](#0-3) 

This fix is also verified by dedicated fee-on-transfer tests for the mainline gateway: [5](#0-4) 

No equivalent tests or logic exist for the Tron `IntentGatewayV2.sol`. Consequently, if a fee-on-transfer token (or a token that later enables a fee, e.g. USDT-style tokens) is used as an order input on the Tron gateway, the contract will hold strictly less of that token than the sum of `_orders[...][token]` it has promised across all commitments involving that token.

### Impact Explanation
Escrow bookkeping (`_orders[commitment][token]`) becomes inflated relative to the actual on-chain token balance held by the gateway. When a solver fills the order and the `RedeemEscrow`/refund path attempts `IERC20(token).safeTransfer(beneficiary, amount)` for the full escrowed amount, the transfer can fail once the shortfall accumulates across multiple orders sharing that token, or the specific order's fill reverts if it was underfunded from the start. This results in permanent freezing of funds for solvers who filled the order in good faith (destination-side legitimate spend already occurred) and inability to release the corresponding escrow on the source chain — a direct, unprivileged-reachable fund-freezing condition triggered by a single `placeOrder` call from any ordinary user/token bridger.

### Likelihood Explanation
Any user can call `placeOrder` with an arbitrary ERC20 as input; no privileged role is required. Fee-on-transfer tokens are a known, common token class (and some widely used tokens like USDT can enable fees via governance later), so this is readily triggerable, not a purely theoretical edge case — and the mainline gateway's own test suite/fix acknowledges this as a real threat the team already mitigated for other deployments.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron gateway: measure `balanceOf(address(this))` (or the dispatcher, for predispatch flows) before and after each `safeTransferFrom`/sweep, mutate `order.inputs[i].amount` (and thus `reducedInputs`) to the actual amount received, and only then compute the commitment hash and credit `_orders[commitment][token]`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and mint balance to a user.
2. User approves and calls `placeOrder` on the Tron `IntentGatewayV2` with `inputs[0].amount = 1000` of this token.
3. `safeTransferFrom(msg.sender, address(this), 1000)` transfers only 990 tokens into the gateway (1% fee burned/redirected), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` computed from `1000` (minus protocol fee, if any) — i.e., escrow says the gateway holds ~1000, but it only holds 990.
4. When the corresponding `RedeemEscrow`/refund is processed via `_withdraw`, `IERC20(token).safeTransfer(beneficiary, amount)` for the escrowed (over-stated) amount can fail once other legitimate escrow claims on the same token exhaust the real balance, freezing funds for the affected beneficiary.     /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
