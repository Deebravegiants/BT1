### Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shopify-shop-domain` (and `shopify-topic`) header to build the `WebhookMetadata` passed to the app's handler. Because the shop-identifying header is never included in the signed material, a request whose body carries a valid signature for one shop can be replayed with a different `shop-domain` header, and the gem will report it to the handler as originating from the spoofed shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw HTTP body, while `Request#shop` (and `#topic`) are read directly from headers that are never fed into the signable string: [2](#0-1) [3](#0-2) 

`Registry.process` checks only the body HMAC, and then unconditionally uses `request.shop` (and `request.topic`) — values that were never part of the signed payload — to route to a handler and populate `WebhookMetadata`: [4](#0-3) 

The equality that should hold is:
`shop bound by HMAC == shop delivered to the app's handler`

Instead, the gem only proves `HMAC(body) == received_hmac`. The `shop-domain` header is unauthenticated data that is trusted as if it were signed. Any actor who can obtain one genuinely-signed webhook body/HMAC pair for shop A (trivial — install the app on a store you control and trigger any subscribed event) can resend that exact body to the app's webhook endpoint with `x-shopify-shop-domain` (or `shopify-shop-domain`) rewritten to shop B. `HmacValidator.validate` still returns `true` because the body — the only signed input — is unchanged, and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: "B"` while the body content actually belongs to shop A.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: the host application relies on `WebhookMetadata#shop` (derived from `Request#shop`) to determine which merchant's data/record the webhook event applies to. An attacker controlling any shop that has the app installed can forge webhook events attributed to a shop they do not control, causing the host app to write, delete, or act on data under the wrong tenant's identity — a cross-tenant access condition, one of the explicitly listed Critical impacts.

### Likelihood Explanation
Exploitation requires no access token, no `api_secret_key`, and no privileged account beyond the ordinary ability to install the app on any store (including a free development store) and capture one legitimate webhook delivery. The attacker then only needs to send an unauthenticated HTTP POST with a modified header value to the app's public webhook endpoint — well within reach of an unprivileged internet actor.

### Recommendation
Bind the shop identity into the authenticated material before trusting it: either include the `shop-domain` (and `topic`) header values in the HMAC-signed content compared during validation, or independently verify (e.g., against session/install records) that the `shop-domain` header matches the shop the webhook subscription belongs to before invoking the handler, rather than trusting the header value outright.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger any subscribed webhook topic (e.g., `orders/create`) to legitimately capture `raw_body` and its `x-shopify-hmac-sha256` header from Shopify.
2. Replay the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only the (unmodified) body is checked: [5](#0-4) 
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host application to process attacker-controlled data as if it belonged to the victim shop.
