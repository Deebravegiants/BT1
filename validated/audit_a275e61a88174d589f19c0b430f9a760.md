### Title
Webhook `shop`/`topic` identity fields are unauthenticated by the HMAC, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values that the registry uses to route and attribute the webhook are read from unauthenticated HTTP headers. This breaks the identity binding `hmac_signed_bytes == bytes_used_for_tenant/handler_dispatch`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, which are never part of the signed string: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then dispatches purely based on the unauthenticated `topic`/`shop` header values: [3](#0-2) 

`HmacValidator.validate` confirms `computed_signature(raw_body)` matches the supplied hmac — it says nothing about which shop or topic the bytes are supposed to belong to: [4](#0-3) 

This is directly analogous to the M-7 report's root cause: a privileged operation (`oracle.update()`) checked the wrong identity (`factory().owner()` instead of `factory()`), so the check answered permissively for a party that shouldn't be trusted for that action. Here, the app's webhook processor checks "does this body have a valid HMAC" but then trusts headers that were never bound to that HMAC to determine *which tenant/topic* the verified bytes belong to — the verified identity (the body) and the acted-upon identity (`shop`, `topic`) are different things.

### Impact Explanation
Any unprivileged internet user who can get a legitimate app installed on a shop they control (the normal, unprivileged path for any public Shopify app) will receive genuinely-signed webhooks: `(raw_body, hmac)` pairs valid under the app's `api_secret_key` for their own shop/topic. Because `shop-domain` and `topic` headers are not covered by the signature, that same attacker can replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and/or substituting the `X-Shopify-Topic` header for a different registered topic (e.g. a mandatory topic like `customers/redact`/`shop/redact`). `Registry.process` will accept the HMAC (it only checks body bytes) and hand `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the handler as if it genuinely originated from the victim shop/topic. Any host application that uses `shop`/`topic` to select which tenant's data to mutate (a documented, intended use of this field per `docs/usage/webhooks.md`) can be made to process attacker-controlled body content under a different shop's identity — a cross-tenant data-integrity break requiring no credentials, tokens, or privileged access.

### Likelihood Explanation
Requires only: (1) ability to install the target app on an attacker-controlled shop (the standard installation flow for any public app, no special privilege), (2) capturing one legitimate webhook delivery to observe a valid `(raw_body, hmac)` pair, and (3) POSTing that same body/hmac to the app's public webhook endpoint with forged `shop-domain`/`topic` headers. No secret key, access token, or elevated account is needed, and the flow is fully reachable via this gem's own `Webhooks::Request`/`Webhooks::Registry` API as documented.

### Recommendation
Include the trust-critical headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signed payload used by `to_signable_string`, or otherwise cryptographically bind them (e.g., verify the HMAC over `"#{shop}|#{topic}|#{raw_body}"` if compatible with Shopify's signing scheme, or require host apps to cross-check `shop`/`topic` against out-of-band expected values before trusting `WebhookMetadata`). At minimum, document loudly that `request.shop` and `request.topic` are unauthenticated and must not be used as sole tenant/routing identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid hmac of body>`. Attacker's own endpoint/proxy captures `raw_body` and `hmac`.
3. Attacker sends a new HTTP POST directly to the app's webhook endpoint with the exact same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`, e.g. `customers/redact`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the hmac — this passes.
5. The registry looks up the handler by the forged `topic` and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: forged_topic, body: attacker_body, ...)`, causing the host app to process attacker-controlled data attributed to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
