### Title
Webhook shop identity is taken from an unauthenticated header not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value that gets handed to app webhook handlers exclusively from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies covers only the raw request body. Because the shop identity is never bound into the signed material, an attacker who can obtain one validly-signed webhook delivery for a shop they control can replay that same body/HMAC pair while substituting the `shop-domain` header for a victim shop, and the gem will accept it as authentic and dispatch it to the handler under the victim's identity.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop` is read straight from a header that is never fed into the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC, then unconditionally trusts `request.shop` (and `request.topic`) to build the metadata passed to the app's handler: [4](#0-3) 

The broken identity equality is:
`HMAC-authenticated bytes (raw_body signed with client_secret)` ≠ `shop identity acted upon (request.shop, read from an unauthenticated header)`.

The HMAC only proves "this body was signed by someone holding `Context.api_secret_key`" (i.e., Shopify, for *some* shop that has the app installed) — it proves nothing about which shop the body belongs to. Since the shop is carried out-of-band in a header that is fully attacker-controlled at the transport layer, the two values that should be bound together (the signing subject and the shop claimed to own the payload) are never checked for equality.

### Impact Explanation
This is analogous to the reported bug class: a security-relevant field (`shop`) is acted upon by the application (used as the tenant key in `WebhookMetadata` passed to the handler) but is not covered by the cryptographic check that is supposed to authenticate the request, exactly like the report's `authPW`-without-2FA scenario where a field controlling account state bypasses a required binding check.

Concretely: an attacker who installs the app on their own low-value/development shop can capture a legitimately Shopify-signed webhook (valid `hmac-sha256` for a given body) for their own store, then resend that exact body and signature to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `shop: <victim-shop>`. If the host application's handler uses this `shop` value to look up sessions/access tokens, write into shop-scoped data stores, or make authorization decisions (which is the documented purpose of `WebhookMetadata#shop`), this yields cross-tenant data confusion/access — an unprivileged user of the app (in control of only their own shop) can inject data or trigger actions attributed to a different merchant's tenant.

### Likelihood Explanation
Any developer/merchant can install the app to obtain a legitimate signed webhook body+HMAC pair for a topic they can trigger (e.g., `products/update`, `orders/create` on their own store), then replay it with a forged `shop-domain` header — no possession of `api_secret_key`, access tokens, or victim credentials is required; only a network client capable of setting an arbitrary HTTP header. The only friction is that this gem's own code does not stop it: it is a straightforward root-cause gap in `Request#shop`/`Registry.process`.

### Recommendation
Bind the shop identity into the value being cryptographically verified, or verify the delivered shop identity independently of the header, e.g.:
- Include the `shop-domain` header (and `topic`/`webhook-id`) in the signable string alongside the raw body for webhook verification, so any header tampering invalidates the HMAC; or
- Cross-check `request.shop` against a record of shops for which the app is currently installed with a valid stored access token, rejecting webhooks for shops without an active session, before invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., updates a product), causing Shopify to POST a correctly HMAC-signed payload to the app's webhook endpoint with header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` value from this legitimate delivery.
3. Attacker replays the identical POST body and `hmac-sha256` header to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the HMAC — the header is irrelevant to the signature: [5](#0-4) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload was never actually generated by or for that shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
