### Title
Unsanitized JWT `dest` claim used as request host for `client_secret` exfiltration in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the OAuth token-exchange POST (which carries the app's `client_id` and `client_secret`) directly from the unvalidated `dest` claim of the caller-supplied session token, whereas every other credential-sending flow in the same file/module family (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) passes the shop through `Utils::ShopValidator.sanitize!` first.

### Finding Description
`exchange_token` decodes the JWT with `ShopifyAPI::Auth::JwtPayload.new(session_token)` [1](#0-0) , then uses `jwt_payload.shop` (`dest_shop`) directly to build the `Session` and the `Clients::HttpClient` base host that the request is sent to, and merges `client_secret: ShopifyAPI::Context.api_secret_key` into the POST body [2](#0-1) .

`JwtPayload#shop` simply strips the literal string `"https://"` from the `dest` claim (`@dest.gsub("https://", "")`) [3](#0-2) . The JWT is verified only for signature/`aud`/`exp`/`nbf` — there is no check that `dest` is an actual `*.myshopify.com` (or otherwise trusted) domain [4](#0-3) .

Contrast this with the sibling methods in the same auth namespace, which all sanitize the shop before it becomes the request host for a secret-carrying POST:
- `TokenExchange.migrate_to_expiring_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [5](#0-4) 
- `ClientCredentials.client_credentials`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [6](#0-5) 
- `RefreshToken.refresh_access_token`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [7](#0-6) 

`Utils::ShopValidator.sanitize!` exists precisely to enforce that a shop-derived host belongs to `TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`) before that value is trusted as a request destination [8](#0-7) [9](#0-8) . `exchange_token` is the one path in this family that skips this check entirely, breaking the equality that should hold across the module: `host validated == host that receives client_secret`.

Note: because the JWT is HMAC-signed with `Context.api_secret_key`, an attacker cannot forge an arbitrary `dest` value without the secret — this significantly limits practical exploitability (it requires the app itself to accept a token whose signature check somehow degrades, e.g., via `Context.old_api_secret_key` fallback after a rotation, or any future code path that constructs a `JwtPayload`-equivalent object from less trustworthy input). Still, the missing defense-in-depth check is a genuine deviation from this codebase's own established pattern for exactly this class of "verifying identity vs. identity used for credential transmission" bug, matching the report's root cause (using an unvalidated/wrong identity as the binding for a security-sensitive operation).

### Impact Explanation
If the `dest` claim can ever contain a non-Shopify host — whether through a future signature-verification regression, a secret-rotation edge case, or reuse of `JwtPayload`/`dest_shop` outside the currently-audited code path — the app's `client_id`/`client_secret` would be POSTed to that host, i.e., SSRF with credential exfiltration (client_secret disclosure to an attacker-controlled endpoint). This matches the High-severity class: "SSRF with the app's credentials" / "credential leakage."

### Likelihood Explanation
Low-to-moderate under current conditions, since JWT signature verification via `Context.api_secret_key` (or `old_api_secret_key`) is required first, so a remote unprivileged attacker cannot trivially forge the `dest` value today. However, likelihood rises during/after key rotation windows (the `old_api_secret_key` fallback), and the missing sanitize! call is a real, provable code-level inconsistency versus the three sibling functions that explicitly guard this exact operation.

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) on `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`Clients::HttpClient`, consistent with `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`.

### Proof of Concept
Not independently demonstrable as a live exploit within this gem alone, since forging a `dest` claim requires knowledge of `api_secret_key`/`old_api_secret_key`. The finding is a static code-consistency/defense-in-depth gap: [10](#0-9)  lacks the `Utils::ShopValidator.sanitize!` call present in the three analogous credential-sending methods cited above, meaning any future weakening of JWT verification (or reuse of `dest_shop`) would immediately allow POSTing `client_id`/`client_secret` to an attacker-chosen host.
