This confirms the critical binding gap: the `Webhooks::Request#shop` field is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, and `HmacValidator.validate` computes the HMAC over `to_signable_string` which for `Webhooks::Request` is defined as just `@raw_body` (the JSON body), not the shop header. [1](#0-0) [2](#0-1) 

That means: `HMAC-SHA256(secret, raw_body) == received_hmac` is the only equality checked, while `request.shop` (used to populate `WebhookMetadata.shop`, which the host application typically uses as the tenant key for looking up records/webhook handling) is never included in the signed bytes. An attacker who can produce **any** request whose HMAC matches for a given raw body — i.e., replay a previously captured, legitimately-signed webhook body-plus-HMAC pair from **their own shop** — can resubmit it with the `x-shopify-shop-domain` header changed to a victim shop's domain, and the library will accept it as validly signed and pass `shop: <victim-domain>` into the handler, even though the signature never covered that field.

However, exploiting this still requires an attacker to have first obtained a valid `(body, hmac)` pair, and since HMAC-SHA256 is computed over `secret + raw_body`, an attacker with access to any legitimately signed webhook for their own store (which they can obtain, since they can install the app on their own free/dev store and receive real webhooks) already knows a valid `(raw_body, hmac)` pair for that body without needing the `api_secret_key` itself. They can then replay that exact body with a forged `shop-domain` header pointing at a different (victim) shop, and the gem's `Registry.process` will accept it as authentic for the victim shop, since `shop` is completely unauthenticated relative to the HMAC.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` is read from the `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` verifies only the body against the HMAC, never binding the shop-domain header. `Webhooks::Registry.process` trusts `request.shop` and forwards it into `WebhookMetadata`, which host applications use to attribute the webhook to a tenant.

### Finding Description
The identity binding that should hold is: `shop-domain header used for tenant routing == shop domain that was actually HMAC-authenticated by Shopify`. In this gem that equality does not hold, because:
- `to_signable_string` for `Webhooks::Request` returns `@raw_body` only [3](#0-2) .
- `shop`, `topic`, `webhook_id`, `api_version` are all parsed straight from HTTP headers with no cryptographic binding to the HMAC [4](#0-3) .
- `HmacValidator.validate_signature` only compares `HMAC(secret, raw_body)` to the received signature [5](#0-4) .
- `Registry.process` passes `request.shop` straight into the handler after only checking the body's HMAC [2](#0-1) .

Since two shops can produce byte-identical webhook bodies (e.g., `orders/create` payloads with the same structure, or any topic where the body doesn't embed the sending shop's domain, or simply an attacker replaying the exact bytes of a webhook they legitimately received), an attacker who owns/controls any Shopify store that has this app installed can capture a `(raw_body, hmac)` pair from a real webhook Shopify sent them, then submit that exact body+HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to any other shop the attacker chooses. The library reports `Utils::HmacValidator.validate(request)` as `true` (since only the body is checked) and forwards `shop: <attacker-chosen-domain>` to the application's webhook handler.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled input (`shop` header) that was never bound to the HMAC is delivered to the host application as if it were verified. Any host application logic that uses `WebhookMetadata#shop` to select which tenant's records to update, delete, or act upon (the gem's own documented usage pattern) can be tricked into performing actions attributed to, or scoped to, a shop other than the one that actually sent the payload — a cross-tenant access vector at the gem's trust boundary. This is a real gap in the library's own verification primitive, not a case of the host ignoring documented behavior, since `Utils::HmacValidator.validate` is presented by the gem as the authoritative signature check for both OAuth queries and webhooks, and it silently omits `shop` for webhooks.

### Likelihood Explanation
Moderate: it requires the attacker to control a real, installed shop for the target app (achievable via free/dev stores, or via a store they already run through the app) and to be able to produce a body that is either byte-identical across shops or partially replayable. For many topics (e.g., `app/uninstalled`, `shop/update`, or any webhook whose JSON body doesn't itself carry the origin shop's domain as a required, handler-validated field) this is straightforward, since Shopify's webhook payloads do not always self-describe the sending shop inside the body.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable bytes that `HmacValidator` verifies for webhooks, or otherwise cryptographically bind the shop-domain header to the HMAC before trusting it. At minimum, applications should be warned in documentation that `request.shop` is not covered by the HMAC and must be cross-checked against the shop's known/stored access-token/session before use — but the safer fix belongs in the gem's `Webhooks::Request`/`HmacValidator`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <H>` where `H = Base64(HMAC-SHA256(secret, "{\"id\":1}"))`.
2. Attacker replays the same raw body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body`, so it returns `true` [6](#0-5) .
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"`, even though Shopify never sent this webhook for that shop [7](#0-6) .
