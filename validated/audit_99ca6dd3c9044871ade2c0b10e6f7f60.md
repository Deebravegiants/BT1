## Title
Webhook HMAC does not cover the `shop-domain` header, allowing shop-spoofed webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body against the app's `client_secret`. The `shop-domain` header, which the gem hands to the app's handler as the authoritative shop identity, is never included in the signed material. An attacker who legitimately installs the target app on a shop they control can capture one of their own genuine webhook deliveries (body + valid HMAC) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop, and the HMAC check still passes.

### Finding Description
The signable string used for HMAC verification is exactly the raw body, nothing else: [1](#0-0) 

The `shop` accessor used downstream is read straight from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate_signature` recomputes the HMAC only over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac-sha256` header, never touching `shop-domain`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request — including the shop — is authentic, then forwards the unauthenticated `request.shop` to the app's handler: [4](#0-3) 

The gem's own documentation reinforces that this is the guaranteed contract: `Registry.process` is documented as verifying "the request did indeed come from Shopify," and `data.shop` is documented as "The shop domain of the webhook," which the example handler uses directly to key persisted data (`shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler`

Because the HMAC only binds `(client_secret, body)` and not the shop header, this equality does not hold: any body/HMAC pair that is valid for shop A can be replayed with the `shop-domain` header set to shop B, and the gem will report it as verified and hand `shop: "B"` to the application, even though the payload actually originated from (and was signed for) shop A.

### Impact Explanation
Since the app's `client_secret` (and thus the HMAC) is the same for every shop that installs the app, any unprivileged user able to install the app on a shop they control can obtain genuine `(body, hmac)` pairs at will (e.g., by creating orders/products on their own store and capturing the resulting webhook). They can then submit these bodies with an arbitrary victim `shop-domain` header to the app's public webhook endpoint. `ShopifyAPI::Webhooks::Registry.process` will validate the HMAC successfully and invoke the app's handler with `shop` set to the victim shop and `body` set to the attacker's own data. Any host application that follows this gem's documented pattern (using `data.shop` to key stored records, as shown in the gem's own docs) will attribute attacker-controlled content to a victim tenant — a cross-tenant data injection / spoofing primitive entirely enabled by this gem's verification logic.

### Likelihood Explanation
High. No credentials beyond the ability to install the app on any shop (a normal, low-privilege action available to any Shopify merchant) are required. The webhook endpoint is unauthenticated by design (that's the point of HMAC verification), and capturing/replaying an HTTP request with one modified header is trivial.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material used for verification, or otherwise cryptographically bind the `shop` value to the verified payload before it is handed to the application's handler. At minimum, document (and ideally enforce in the gem) that `data.shop` from `Registry.process` is not proven to correspond to the same tenant that produced `data.body`, so callers do not rely on it as a trusted tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers the `orders/create` webhook.
2. Shopify delivers a genuine webhook to the app:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of BODY using app's client_secret>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   BODY: {"id": 1, ...attacker's own order...}
   ```
3. Attacker replays this exact request to the app's public webhook callback route, changing only the shop header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
   (`X-Shopify-Hmac-Sha256` and `BODY` unchanged.)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `BODY` only and matches the header — validation succeeds.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`.
6. A host application following this gem's documented pattern (`shop_domain: data.shop`) stores/acts on the attacker's data as if it belongs to `victim-shop.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
