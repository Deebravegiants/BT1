### Title
Liquidity withdrawal fee can be bypassed by fragmenting `remove_liquidity` calls into small `lp_token_burn` amounts - (File: substrate/frame/asset-conversion/src/lib.rs)

### Summary
`do_remove_liquidity` computes `withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn` using `Permill` multiplication, which performs integer (floor) division. For sufficiently small `lp_token_burn` values this product rounds down to zero, so `lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount)` equals `lp_token_burn` unchanged, letting an unprivileged LP holder repeatedly withdraw in small increments to avoid the fee that would otherwise be charged on an equivalent single large withdrawal.

### Finding Description
The withdrawal-fee logic in `do_remove_liquidity` (substrate/frame/asset-conversion/src/lib.rs) multiplies the configured `Permill` fee rate directly against the caller-supplied `lp_token_burn` amount:

```
let withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn;
let lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount);
```

`Permill * Balance` uses truncating (floor) integer arithmetic. For any `Permill` value `p` (parts-per-million) and burn amount `b`, the fee is zero whenever `b < 1_000_000 / p_ppm` (roughly). Since `lp_token_burn` is fully attacker-controlled through the public `remove_liquidity` extrinsic, a signed account holding LP tokens can call `remove_liquidity` repeatedly with `lp_token_burn` values chosen below this threshold, redeeming the same aggregate LP amount as a single large call but paying zero fee on every call instead of the fee that would apply to the combined amount. There is no per-account/global fee floor, no minimum accumulation-before-fee check, and no aggregation of fee state across calls, so nothing in the current implementation prevents this transaction-splitting pattern. The origin/signature/nonce checks on the extrinsic are irrelevant here — the bug is purely in the per-call floor-rounded fee arithmetic, not in access control.

### Impact Explanation
The protocol-level withdrawal fee, whose purpose is to disincentivize/monetize liquidity removal, can be systematically avoided by splitting withdrawals into fee-rounding-to-zero increments, causing the protocol to under-collect fees relative to the intended fee schedule. The magnitude of fee lost per split is bounded (roughly up to `threshold - 1` LP tokens' worth of fee per split, where `threshold ≈ 1_000_000 / fee_ppm`), but by repeating the split N times an attacker can withdraw an arbitrarily large aggregate amount while paying zero cumulative protocol fee, whereas a single call for the same aggregate amount would pay a fee scaling with the amount. This is an accounting/fee-bypass issue, not an ability to mint or steal already-backed assets beyond what the LP tokens represent.

### Likelihood Explanation
This is fully feasible for any unprivileged user holding LP tokens, requiring only repeated calls to the public `remove_liquidity` extrinsic with small `lp_token_burn` values — no special origin, proxy, or governance access needed. The main practical constraint is that each call incurs its own transaction weight/fee cost, which puts an economic floor under how profitable the exploit is relative to per-extrinsic transaction fees; for pools/fee configurations where the LP withdrawal fee is meaningful relative to transaction fees, splitting remains profitable.

### Recommendation
Round the fee calculation up rather than down (e.g., use a ceiling-based `Permill` multiplication or `checked_mul_ceil`), or enforce a minimum fee of at least 1 unit whenever `lp_token_burn > 0`, so that no amount of transaction splitting can reduce the aggregate fee below what a single equivalent withdrawal would incur.

### Proof of Concept
Rust unit test in `substrate/frame/asset-conversion/src/tests.rs`:
1. Set up a pool and mint LP tokens to an account, with `LiquidityWithdrawalFee` set to a nonzero `Permill` (e.g., 3_000 ppm).
2. Call `remove_liquidity` once with `lp_token_burn = N` (large enough that the fee floor is nonzero); record `assets_received_single`.
3. Reset state, call `remove_liquidity` N times with `lp_token_burn = 1` each; sum `assets_received_split`.
4. Assert `assets_received_split - assets_received_single` is not bounded by a single rounding unit but instead scales with the number of splits (demonstrating fee bypass), i.e. `assert!(assets_received_split > assets_received_single)` and that the gap grows proportionally with N in a fuzz/invariant loop over increasing N.
