## Title
Token-donation to a curve Pair permanently DoSes closing/large buys via unguarded underflow in `Router._computeBuy`'s overflow-cap branch - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeBuy` caps `tokensOut` at `pair.tokenBalance()` (a live ERC20 balance read) whenever the uncapped constant-product quote would exceed the pair's real token balance, then computes `cappedReserveToken = reserveToken - tokensOut` where `reserveToken` is the pair's *stored* reserve. `reserveToken` and `tokenBalance()` are two independent quantities in `Pair.sol` — `tokenBalance()` is a live `balanceOf` read, while `tokenReserve` is stored state updated only by `swap()`. An unprivileged attacker can inflate `tokenBalance()` above `tokenReserve` by simply transferring launched Token to the Pair address, which is a plain ERC20 transfer callable by anyone holding the token. Once that gap exists, any buy whose uncapped quote would push `tokensOut` past `realBalance` hits the cap branch and underflows `reserveToken - tokensOut`, reverting with a Solidity Panic instead of the intended `OverflowCapDegenerate` custom error — permanently DoSing the tail of the curve (and the supply-based graduation trigger) for that token.

### Finding Description
`Router._computeBuy` (`packages/contracts/src/Router.sol:127-148`) is:
```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
``` [1](#0-0) 

`reserveToken` comes from `pair.getReserves()` (stored `_pool.tokenReserve`), while `realBalance` comes from `pair.tokenBalance()`, a live `IERC20.balanceOf` read [2](#0-1) . These two are only kept in lockstep by the `swap()` accounting for regular buys/sells [3](#0-2) , but an attacker can break the invariant by directly transferring launched Token (a plain ERC20) to the Pair contract, increasing `tokenBalance()` without touching `tokenReserve`. This exact break is already reproduced by the codebase's own regression test `test_donation_realBalanceExceedsReserveToken`, which drains the curve for >250M tokens and then transfers them to the pair to assert `realBalance > reserveToken` [4](#0-3) .

Once `realBalance > reserveToken` holds, any subsequent buy whose uncapped `tokensOut` computation exceeds `realBalance` enters the cap branch and computes `reserveToken - tokensOut` with `tokensOut = realBalance > reserveToken`, causing an unconditional Solidity 0.8 arithmetic-underflow Panic (revert code `0x11`) rather than the guarded `OverflowCapDegenerate()` revert the code intends for the `cappedReserveToken == 0` case. The codebase's own fix for the *sibling* bug in `Bonding.previewLtUntilGraduation` explicitly guards this exact condition with `if (realBalance >= reserveToken) return ltUntilThreshold;` [5](#0-4)  and the accompanying comment states this donation shape "previously underflowed `Bonding.previewLtUntilGraduation`'s supply leg, cascading into a `Zap.buy` DoS" [6](#0-5) . That fix only guards the *preview* helper's supply leg — it does not add an equivalent guard to `Router._computeBuy`'s cap branch, which is the function that actually executes `Bonding.buy` / `Router.buy` / `Zap.buy` on-chain. The existing regression test `test_donation_zapBuyStillSucceeds` only exercises a *small* post-donation buy that never triggers the cap branch [7](#0-6) , so it does not cover the tail-of-curve / closing-buy scenario where the cap branch fires and underflows.

Because `tokenReserve` only decreases in lockstep with real transfers via `swap()`, the `realBalance > reserveToken` gap created by a donation persists indefinitely (both sides decrease by the same amount on every legitimate buy) — this is a permanent, not transient, DoS once seeded.

### Impact Explanation
Any unprivileged wallet holding a modest amount of a launched Token can permanently brick the tail end of that token's bonding curve by donating tokens directly to the Pair. Concretely:
- Large buys that would otherwise sell the remaining real supply (the exact buy that would trip the supply-based graduation trigger, `IPair.tokenBalance() == 0`) revert with an unhandled Panic instead of executing or cleanly reverting with a documented error.
- This can prevent a token from ever reaching graduation via the supply trigger, freezing the curve in `Lifecycle.Curve` indefinitely for tokens whose LT never appreciates enough to trip the USD trigger, and griefing traders/creators who can no longer complete large buys or trigger graduation.
- This falls squarely in the "permanent freezing of trader/creator funds" impact class the scope calls out, reached via a fully unprivileged `Bonding.buy` / `Zap.buy` call plus an ordinary ERC20 `transfer` to the Pair — no special roles, no upgrade, no off-chain component.

### Likelihood Explanation
Likelihood is Medium-High: the attack requires only (a) acquiring launched Token (buyable by anyone on the curve) and (b) a plain `IERC20.transfer` to the Pair address — both actions any unprivileged wallet can perform without permission. The codebase's own test suite already demonstrates the state can be trivially reached (`_stageDonationAttack`), confirming the preconditions are realistic and cheap relative to the size of the curve being griefed. The only gate is sizing the donation large enough to flip `tokenBalance() > tokenReserve`, which the existing test shows is achievable with normal curve buys.

### Recommendation
Add the same defensive check already applied in `Bonding.previewLtUntilGraduation` to `Router._computeBuy`'s cap branch: before computing `cappedReserveToken = reserveToken - tokensOut`, check `if (tokensOut >= reserveToken) revert OverflowCapDegenerate();` (or equivalent), so a donation-inflated `realBalance` degrades to a clean, documented revert rather than an unguarded arithmetic Panic. Extend `test_donation_*` regression coverage in `test/Zap.t.sol` / `test/Router.t.sol` to exercise a buy sized to trigger the overflow-cap branch (not just a small post-donation buy) after staging the donation attack, asserting the call reverts with `OverflowCapDegenerate` (or succeeds gracefully) rather than an unhandled Panic.

### Proof of Concept
1. Launch a token via `Bonding.launch` / `Zap.createToken`.
2. As an unprivileged wallet, buy a large chunk of the curve via `Bonding.buy` (>250M tokens, as in `_stageDonationAttack`) [8](#0-7) .
3. Transfer the purchased Token directly to the Pair address (`IERC20(token).transfer(pair, amount)`), inflating `tokenBalance()` above stored `tokenReserve` [9](#0-8) , confirmed by `test_donation_realBalanceExceedsReserveToken` [10](#0-9) .
4. Call `Bonding.buy` / `Zap.buy` with an amount sized so the uncapped constant-product `tokensOut` exceeds the now-inflated `realBalance` (i.e., a buy attempting to purchase near/at the remaining real supply) — this trips the cap branch in `Router._computeBuy` [11](#0-10) .
5. Because `realBalance > reserveToken`, `cappedReserveToken = reserveToken - tokensOut` underflows and the call reverts with a Solidity Panic, not `OverflowCapDegenerate` — the buy (and any future attempt to sell out the remaining real supply, including the closing buy that would trigger supply-based graduation) is permanently blocked.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }
