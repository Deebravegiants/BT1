### Title
Silent truncation of cross-chain amount in `convert_to_balance` permanently burns dust on every HFT inbound transfer - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` converts an incoming ERC20 `U256` amount (sent from a paired `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract) into the local balance type via `convert_to_balance`, which performs plain integer division with no error/remainder tracking. Whenever `erc_decimals > local_decimals` for the `(asset, chain)` pair — the normal case since ERC20 tokens are typically 18-decimal while the local `pallet-assets` asset can be registered with fewer decimals — any amount that isn't an exact multiple of `10^(erc_decimals - local_decimals)` has its remainder silently discarded and permanently lost, with no compensating credit anywhere. This mirrors the LQTYStaking `F_Collateral` rounding bug: a proportional/scaling division with truncation and no error-carry term, reachable by an ordinary unprivileged token bridger.

### Finding Description
`convert_to_balance` divides the raw ERC20 value by `10^(erc_decimals - local_decimals)` and parses the truncated integer string into the local balance type: [1](#0-0) 

This is invoked in `on_accept`, the `IsmpModule` handler that processes inbound `Send` messages relayed from a paired EVM contract and mints/releases tokens to the beneficiary: [2](#0-1) 

The `erc_decimals` value comes from governance-set `Precisions` storage (typically 18 for standard ERC20/ERC6160 tokens), while `local_decimals` is the destination asset's own decimals (frequently lower, e.g. 6 or 8 for stable/BTC-like assets bridged onto a Substrate chain). Any transfer amount whose ERC20-side value is not an exact multiple of `10^(erc_decimals - local_decimals)` loses the remainder outright: the value is floor-divided and the fractional part vanishes with no accounting, no dust pool, and no error term (contrast with the LQTY fix's `lastLQTYError` pattern). The same unmitigated division exists symmetrically in `on_timeout`'s refund path: [3](#0-2) 

Unlike `EvmHost`'s `HandlerV2`/dispatch paths that reject non-representable amounts outright (see `BandwidthManager.purchase`, which explicitly reverts with `PriceNotRepresentable()` rather than silently truncating: `evm/src/apps/BandwidthManager.sol` lines 163-168), this pallet has no analogous guard — it always succeeds and simply drops the remainder.

### Impact Explanation
Every inbound `Send` (and every `on_timeout` refund) whose scaled amount isn't an exact multiple of the decimal-gap factor loses value permanently: tokens were burned/locked on the EVM source side for the full requested amount, but the destination mints/releases strictly less, and the difference is unrecoverable (it isn't credited to any account, the pallet's escrow, or a treasury). Because this triggers on essentially any transfer amount that doesn't land on a round multiple at the destination's precision, it is not an edge case — it is the default outcome for most real-world amounts whenever `erc_decimals != local_decimals`, causing steady, unbounded, permanent loss of user funds across every bridged asset pair with mismatched decimals. This satisfies the "permanent freezing/loss of funds" bar.

### Likelihood Explanation
High. This requires no privileged action and is triggered by ordinary token-bridging usage — any user calling the paired `HyperFungibleToken`/`WrappedHyperFungibleToken` contract's send function on an EVM chain to bridge to this pallet. The only precondition is that the asset be registered with `erc_decimals > local_decimals` (a configuration choice made by governance via `register_token`/`update_token`, not by the attacker), which is the common real-world case for ERC20 (18-decimal) tokens bridged onto assets registered with fewer decimals. No race condition, no large-value threshold, and no special crafting is needed beyond picking an amount that doesn't divide evenly — which is nearly all amounts.

### Recommendation
Adopt the same error-carry approach recommended in the referenced report: persist a per-`(asset_id, source_chain)` `lastConversionError` (or equivalent) storage item. On each conversion, add the previous remainder into the numerator before dividing, and store the new remainder for next time, so rounding dust accumulates and eventually crosses a whole local unit instead of being discarded. Alternatively/additionally, reject (or require exact-multiple) transfers whose ERC20 amount does not scale cleanly into the local decimals, mirroring `BandwidthManager.purchase`'s `PriceNotRepresentable` guard, so silent value loss cannot occur.

### Proof of Concept
Given `erc_decimals = 18` and `local_decimals = 6` (a plausible registration for an ERC20 bridged onto a 6-decimal Substrate asset):
1. A user calls `send` (or the paired EVM contract's send) with an amount corresponding to `1_500_000_000_000` wei (`1.5 * 10^12`, i.e., 0.0000015 tokens in 18-decimal terms) — this fully burns/locks that ERC20 amount on the source side.
2. On the destination, `on_accept` calls `convert_to_balance(value = 1_500_000_000_000, erc_decimals = 18, local_decimals = 6)`, computing `1_500_000_000_000 / 10^(18-6) = 1_500_000_000_000 / 10^12 = 1` (should be `1.5`, i.e. `1` after floor, discarding the `0.5` unit's worth of value, `500_000_000_000` wei, forever).
3. Repeating with an amount just below one local unit, e.g. `999_999_999_999` wei, yields `convert_to_balance = 0`: the full amount is burned/locked at the source and the beneficiary receives **nothing** — 100% loss of that transfer.
4. No storage anywhere records the truncated remainder for later crediting; it is unrecoverable. The same applies to `on_timeout`'s refund conversion, so even failed/timed-out sends refund less than what was escrowed.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
