## Analysis

The reported bug class ("a field is trusted/acted upon without actually being covered by the cryptographic check that is supposed to protect it") maps directly onto how `ShopifyAPI::Webhooks::Request` computes and uses its HMAC.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers, never included in the signed string: [2](#0-1) 

`Registry.process` validates the HMAC (which only binds the body) and then trusts `request.shop`, `request.topic`, etc., handing them straight to the handler as the tenant identity for the event: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever hash `verifiable_query.to_signable_string`, i.e., for webhooks, just the body: [4](#0-3) 

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity headers are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` come from HTTP headers that are never part of the HMAC input. `Registry.process` verifies the HMAC and then unconditionally trusts `request.shop` as the source-of-truth tenant identifier passed to the app's webhook handler.

### Finding Description
The identity binding that should hold is:
`HMAC-verified bytes == bytes the handler uses to determine which shop/topic the event belongs to`

In this gem that equality is broken: `to_signable_string` == `@raw_body` only [1](#0-0) , whereas the `shop` value handed to the application-level handler is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header [5](#0-4) , which is completely outside the signed payload.

An unprivileged internet user who can install the app on their own store (a normal, free installation flow available to anyone with a Shopify store) will legitimately receive real webhooks from Shopify, each with a valid HMAC computed over the body using the app's shared `api_secret_key`. Because that same `api_secret_key` produces a valid signature for *any* body value paired with *any* shop header (the header is not part of the signed material), the attacker can:
1. Capture (or independently construct, since only the body is signed) a `(body, hmac)` pair that is valid for the app's secret.
2. Replay this payload to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain.
3. `Utils::HmacValidator.validate` passes (it never looks at the shop header) [6](#0-5) , and `Registry.process` forwards `shop: request.shop` (the attacker-controlled, victim-spoofed value) into `WebhookMetadata` for the handler [7](#0-6) .

Any host application built on this gem that keys its per-tenant state (order records, inventory sync, GDPR/compliance actions, billing, etc.) off `WebhookMetadata#shop` as returned by this library will process attacker-supplied data under the victim shop's identity, resulting in cross-tenant data injection/corruption — entirely through this gem's own trust decision, not through host-app misuse.

### Impact Explanation
This falls into the Critical/High bucket: cross-tenant access. An attacker with only a self-service Shopify store (no elevated privilege, no access to the app's `client_secret`, no access to the victim's credentials) can make the library believe attacker-supplied event data belongs to an arbitrary other merchant, because the header value the gem treats as the authenticated tenant identity is never actually verified by the HMAC that gates webhook processing.

### Likelihood Explanation
High. Getting a `(body, valid-hmac)` pair requires nothing more than installing the app on any store and triggering any webhook subscription — a capability available to any internet user who can create a Shopify dev/free store. Swapping the `shop-domain` header on the replayed request is trivial since HTTP headers are fully attacker-controlled at replay time.

### Recommendation
Bind the shop (and ideally topic/webhook id) identity into the value verified by the HMAC check, e.g., by rejecting the webhook unless `request.shop` matches a shop the app has an active session/installation record for (should be validated in the library or explicitly documented as a required host-app step), or by including the header values in a canonicalized signed string. At minimum, `Request#to_signable_string` documentation/interface should make explicit that only the body is covered, and `Registry.process` should not hand out `request.shop` as if it were HMAC-verified — it should require the caller to have already confirmed `request.shop` corresponds to a known, previously authorized session before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free/self-service).
2. Shopify sends a genuine webhook to the app with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker resends `POST /webhooks` with the same body `B` and same header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `H` against `B` [8](#0-7) .
5. `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen body content [7](#0-6) , even though this event never originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
