### Title
Webhook Shop Identity Spoofing via Header Fields Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the webhook HMAC over the raw body only, while the `shop-domain` (and `topic`/`webhook-id`) header used to identify the tenant is never included in the signed material. Any attacker who can obtain one valid `(body, hmac)` pair signed with the app's `client_secret_key` — trivially available by installing the app on their own shop and receiving one legitimate webhook — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The signature still validates, and `ShopifyAPI::Webhooks::Registry.process` hands the attacker-chosen `shop` straight to the app's handler as if it were authenticated.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` and nothing else: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are outside the signed payload: [5](#0-4) 

`HmacValidator.validate`/`validate_signature` recompute the HMAC solely from `to_signable_string` (the body) and compare it to the `hmac-sha256` header value using `OpenSSL.secure_compare` — headers such as `shop-domain` never enter the computation: [6](#0-5) 

`Registry.process` trusts this body-only HMAC check and then forwards `request.shop` (an unauthenticated header value) directly into `WebhookMetadata` for the app's handler to act on: [4](#0-3) 

Because Shopify signs app webhooks with the app's single `client_secret_key` (identical across every shop that installs the app), this is not a per-tenant secret. Consequently, an attacker who installs the app on their own store obtains genuinely valid `(body, hmac)` pairs. Since the header carrying the tenant identity (`shop-domain`) is not part of the signed bytes, the attacker can freely swap that header to any victim `myshopify.com` domain and resend the exact same body + HMAC to the app's public webhook endpoint. The equality the code implicitly assumes — `shop that produced the HMAC == shop delivered to the handler` — does not hold, breaking the tenant-identity binding.

### Impact Explanation
This crosses a tenant boundary: the app's webhook handler will process attacker-supplied body content believing it originates from a victim shop chosen by the attacker (e.g., forging `orders/create`, `app/uninstalled`, `shop/update`, etc. for a shop the attacker doesn't operate). Depending on what the handler does with `data.shop` (e.g., looking up/mutating the victim's stored session, access token record, or business data keyed by shop), this enables cross-tenant data corruption or triggering privileged flows (such as an app-uninstall cleanup or resource deletion) against a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is significant for any app relying on `ShopifyAPI::Webhooks::Registry.process`/`Request` as documented: obtaining a valid `(body, hmac)` pair requires only installing the app on a shop the attacker controls (or observing/replaying any of their own real webhook deliveries), which is available to any unprivileged internet user capable of installing a public app. No access token, `client_secret`, or privileged account is needed — only a normal merchant account for a throwaway shop.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, causing Shopify to deliver a legitimate webhook (e.g., `orders/create`) to the app's callback URL with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, and some JSON body.
2. Attacker captures the exact raw request body and its valid `x-shopify-hmac-sha256` value (both are visible to them as the receiving party is under their control, or via any request logging/proxy they run).
3. Attacker resends an HTTP POST to the same webhook endpoint with the identical raw body and identical `x-shopify-hmac-sha256` header, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the headers and body normally [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over the (unchanged) body and finds it matches, so validation passes [8](#0-7) .
5. The handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload was never actually produced by or for the victim shop [9](#0-8) .

### Recommendation
Include the tenant-identifying header(s) — at minimum `shop-domain`, and ideally `topic`/`webhook-id`/`api-version` — in the signed material that `to_signable_string` returns (or independently verify `shop` against a value bound into the signature, e.g., by re-deriving/whitelisting shops from stored session data rather than trusting the header verbatim). Until fixed, document that `request.shop` from `ShopifyAPI::Webhooks::Request` must not be trusted as authenticated tenant identity by itself, and that consuming apps should independently confirm the resolved shop matches an installed/known shop before acting on webhook data.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
