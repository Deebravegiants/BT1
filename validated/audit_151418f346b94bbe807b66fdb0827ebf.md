## Finding

### Title
Webhook processing trusts the unauthenticated `shopify-shop-domain` header rather than the HMAC-bound body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that covers only the raw request body, but the tenant identity (`shop`) used to route and label the webhook payload to a handler is read from an HTTP header that is never included in that HMAC computation. An unprivileged holder of any one valid, HMAC-signed webhook (e.g., from their own shop's installation of the app) can replay that signed body to the same endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value, and the library will accept it as authentic and hand it to the app's handler labeled with the victim shop.

### Finding Description
`Webhooks::Request` computes its authenticated signable payload strictly from the raw body: [1](#0-0) [2](#0-1) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header`, a value that is completely outside the HMAC's signable string: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC over `request` (i.e., over `to_signable_string == @raw_body`) and, on success, immediately trusts `request.shop` to construct the tenant-scoped metadata delivered to the app's handler: [5](#0-4) 

The HMAC validator itself only ever signs/verifies `verifiable_query.to_signable_string`: [6](#0-5) 

The binding that should hold is:
`shop_header == shop_that_the_HMAC_was_computed_for`

But since the HMAC only covers `@raw_body`, this equality is never checked. Any request whose body+HMAC pair is valid (signed once by Shopify, for any shop that has installed the app — including one the attacker controls) will pass `HmacValidator.validate`, regardless of what `shop` header accompanies it. This is the same bug class as the report's "field acted on but not covered by the signature/identity check" — here the `shop` field routed into `WebhookMetadata` is disjoint from the field(s) actually covered by the HMAC.

### Impact Explanation
An attacker who installs the target app on their own (attacker-controlled) shop will legitimately receive real, correctly HMAC-signed webhooks from Shopify for actions in their own store (e.g., `customers/data_request`, `orders/create`, etc.). By capturing one such raw body + HMAC pair and replaying it to the app's webhook endpoint with the `shop` header rewritten to a victim's `myshopify.com` domain, the attacker forces the app to process attacker-controlled webhook content as if it originated from the victim tenant. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (commonly used to look up/scope the tenant record the webhook data is written to), this enables cross-tenant data injection/corruption — e.g., writing attacker-chosen order/customer data into the victim shop's tenant record, or triggering compliance/redact handlers against the wrong tenant. This matches the Critical "cross-tenant access" impact category, since it lets an unprivileged actor cross a tenant boundary using only the gem's own webhook-processing logic and no leaked credentials.

### Likelihood Explanation
Likelihood is moderate-to-high: no access to the app's `client_secret`/access tokens is required. The only prerequisite is that the attacker be able to install the app on any shop they control (a standard, unprivileged action for a Shopify app that supports public installs) in order to obtain one valid signed webhook body/HMAC, and be able to reach the app's public webhook endpoint (which is exposed to the internet by design). No mempool/timing race is even required, unlike the original report's front-running scenario — a simple replay with a modified header suffices because the gem never binds the shop header to the HMAC.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered signable payload, or otherwise cryptographically bind the `shop` header to the verified body before it is used to construct `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop`, `topic`, and `webhook-id` header values so that `HmacValidator.validate` fails if any of them are altered relative to the signed body, closing the gap between what is verified and what is subsequently trusted.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook-firing action (e.g., updates an order), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` to the app's registered webhook endpoint. `H` is valid because `HmacValidator.validate` only checks `H` against `B` using the app's shared `api_secret_key` — see `lib/shopify_api/utils/hmac_validator.rb:12-31`.
3. Attacker captures `B` and `H` and replays them directly to the same endpoint, this time setting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` builds `@raw_body = B`; `HmacValidator.validate(request)` recomputes the HMAC over `B` only (`lib/shopify_api/webhooks/request.rb:35-38`) and it matches `H`, so validation succeeds.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `request.shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:188-200`), even though the payload `B` actually originated from and describes the attacker's own shop.
