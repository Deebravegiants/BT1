The GRANDPA ancestry-chain walk in this codebase has the same defect class as `CalcProfileID()`: an unbounded loop driven entirely by attacker-supplied data, with no cycle detection and no iteration cap.

### Title
Denial of Service via Infinite Loop in `AncestryChain::ancestry()` (GRANDPA consensus verification) - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry()` walks a linked list of parent-hash pointers taken from an attacker-controlled `Vec<Header>` (`unknown_headers` / `votes_ancestries`) without any cycle detection or bound on the number of steps. A submitter can construct two (or more) synthetic headers whose `parent_hash` fields point at each other, forming a cycle that never reaches the `base` hash the loop is searching for. Because every hash in the cycle is present in the lookup map, the `while current_hash != base` loop never terminates, exactly mirroring the CalcProfileID infinite-loop bug class (an untrusted, attacker-controlled traversal with no termination guarantee).

### Finding Description
`AncestryChain` is built directly from attacker-supplied header lists: [1](#0-0) 

The vulnerable walk has no cycle guard: [2](#0-1) 

This function is called before any cryptographic signature is checked, both directly on the raw `unknown_headers` list in `verify_grandpa_finality_proof`: [3](#0-2) 

and again inside `GrandpaJustification::verify_with_voter_set`, over `votes_ancestries`, another attacker-controlled `Vec<H>`: [4](#0-3) 

Both `unknown_headers` and `votes_ancestries` are plain SCALE-decoded header vectors with no requirement that they form a connected, acyclic, cryptographically-anchored chain — the only "proof" that a header belongs is that its `hash()` (computed purely from attacker-chosen header content) appears as a key in the `BTreeMap`. An attacker fully controls header fields (digest, extrinsics root, etc.), so producing two headers `H1`/`H2` with `H1.parent_hash = H2.hash()` and `H2.parent_hash = H1.hash()` is trivial — no proof-of-work or preimage search is required, since the hash is simply computed from the content the attacker writes.

This is reachable through the unsigned, permissionless `handle_unsigned` extrinsic of `pallet-ismp`, which decodes and executes a `ConsensusMessage::Polkadot(...)` payload: [5](#0-4) [6](#0-5) 

Crucially, `handle_unsigned` messages are also fully re-executed inside `validate_unsigned`, which runs on every node whenever the extrinsic is gossiped/validated for the transaction pool: [7](#0-6) 

So a single malicious unsigned extrinsic can hang not just the block-executing collator but every peer node validating it in its transaction pool.

### Impact Explanation
An unauthenticated attacker can submit one unsigned extrinsic containing a crafted `ConsensusMessage::Polkadot` GRANDPA finality proof whose `unknown_headers` (or `votes_ancestries`) list contains a 2-cycle of synthetic headers. When `verify_grandpa_finality_proof` (or `GrandpaJustification::verify`) calls `AncestryChain::ancestry`, the loop spins forever, consuming a full CPU core indefinitely and never returning. Since this code path executes both at block execution time (`handle_unsigned`) and at `validate_unsigned` transaction-pool validation time (executed by every node relaying/validating the extrinsic before inclusion), this can halt the chain's collators/validators and DoS the whole network processing GRANDPA consensus updates — a "route unable to deliver messages" condition, directly impacting availability of the bridge. This matches High severity, analogous to CVE-2026-21507's CVSS 7.5 (availability-only, network-reachable, no privileges required).

### Likelihood Explanation
High. The `handle_unsigned` call is explicitly designed to be callable by anyone without a signature (documented as "Execute the provided batch of ISMP messages for free with valid proofs"), and GRANDPA consensus updates are one of the normal message kinds processed there. No collusion, special privileges, or expensive precomputation (e.g., hash preimage search) is needed — the attacker directly authors the header content whose hash is inserted as another header's `parent_hash`.

### Recommendation
- Add cycle detection to `AncestryChain::ancestry` (e.g., track visited hashes in a `BTreeSet` and return an error if a hash is revisited).
- Bound the number of iterations/hops to at most `unknown_headers.len()` (or `votes_ancestries.len()`), since a genuine acyclic ancestry chain can never need more steps than there are headers supplied.
- Reject `unknown_headers`/`votes_ancestries` lists containing duplicate hashes before beginning the walk.

### Proof of Concept
1. Construct header `H2` with arbitrary but valid-looking fields; compute `h2 = H2.hash()`.
2. Construct header `H1` with `parent_hash = h2`; compute `h1 = H1.hash()`.
3. Set `H2.parent_hash = h1` (re-deriving `H2` so its hash stays consistent, or choosing filler fields such that this holds — trivial since the attacker controls all header content and simply fixes point 1/2 by construction order, e.g., build `H2` last after knowing `h1`).
4. Insert `[H1, H2]` into `unknown_headers` of a `ParachainHeadersWithFinalityProof` / `finality_proof.unknown_headers`, with `target = H1` (`finality_proof.block = h1`) and a `base` chosen so that `from`/`base_hash` never equals `h1` or `h2` (e.g., use the current `consensus_state.latest_hash`, which is public/queryable state).
5. Submit this as the `proof` payload of `pallet_ismp::Call::handle_unsigned { messages: [Message::Consensus(consensus_message)] }` as an unsigned extrinsic.
6. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())`, which enters the `H1 → H2 → H1 → H2 → …` cycle and never returns, hanging the executing node (and every node that validates the unsigned extrinsic via `validate_unsigned`).

	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}

	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
