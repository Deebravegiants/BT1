### Title
Webhook HMAC covers only the raw body, not topic/shop/api_version/webhook-id headers, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`Utils::HmacValidator.validate` verifies only `@raw_body` via `Webhooks::Request#to_signable_string`, never the `shopify-topic`, `shopify-shop-domain`, `shopify-api-version`, or `shopify-webhook-id` headers. `Registry.process` trusts those unsigned headers to build `WebhookMetadata` and route to a handler, so an attacker who has received one legitimate signed webhook to their own shop's endpoint can replay that exact body/hmac pair to a victim app while freely rewriting the routing/identity headers.

### Finding Description
The intended binding should be: `signed_data == {raw_body, topic, shop, api_version, webhook_id}`, but the actual binding is `signed_data == {raw_body}` only.

- `Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
- `topic`, `shop`, `api_version`, and `webhook_id` are all read straight from attacker-controllable HTTP headers with no signature coverage: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` and constant-time-compares it to the `hmac-sha256` header: [3](#0-2) 
- `Registry.process` calls this validator, and on success builds `WebhookMetadata` directly from the unsigned `request.topic`, `request.shop`, `request.api_version`, `request.webhook_id`: [4](#0-3) 

Exploit flow: the attacker registers a webhook endpoint on their own dev shop, receives one legitimate `(raw_body, hmac)` pair from Shopify, then sends a new POST to the victim app's webhook endpoint with that same body and `hmac-sha256` header, but with `shopify-topic`, `shopify-shop-domain`, `shopify-api-version`, and `shopify-webhook-id` set to any values of the attacker's choosing. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` dispatches the handler for the attacker-chosen topic with an attacker-chosen `shop` value baked into `WebhookMetadata`, even though that content never actually originated for that shop/topic/webhook. No other guard in this codebase (`ShopValidator`, `Context.setup?`, etc.) constrains `request.shop`/`request.topic` against the signed payload before dispatch.

### Impact Explanation
This lets one attacker-controlled shop forge webhook deliveries that impersonate any other shop domain and any topic to a host app built on this gem, as long as the app's webhook handler trusts `WebhookMetadata#shop`/`#topic` (which is the documented, expected usage pattern of this gem). This is a cross-tenant impersonation/authentication-bypass class issue: handlers that key off `shop` to fetch/update per-tenant data, or off `topic` to decide mandatory GDPR actions (e.g. `customers/redact`, `shop/redact`), can be triggered for a shop the attacker does not own, using a body that was never actually about that shop. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Preconditions are minimal per the prompt's threat model: the attacker only needs to have received one legitimate webhook to their own shop/endpoint (trivial — install their own app in a dev shop and let any webhook fire). No secrets are required. The attack is fully repeatable: the same captured body/hmac pair can be replayed indefinitely with different header combinations, and the only degree of freedom the attacker loses is that the JSON body content itself is fixed (whatever their own shop received), not any header value.

### Recommendation
Include the routing/identity headers (`topic`, `shop`, `api_version`, `webhook_id`) in the signable string, or otherwise validate their consistency against the signed body's own shop/topic fields (Shopify's webhook payloads typically embed shop info in the body too), before trusting them in `WebhookMetadata`. At minimum, `Registry.process` should cross-check `request.shop` against the body content or an authenticated shop context rather than relying solely on unsigned headers alongside a body-only HMAC.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
require "test_helper"

class HeaderMutationHmacBypassTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host_name: "example.com",
      api_version: "2024-01", is_private: false, is_embedded: true, session_storage: nil,
    )
    @raw_body = '{"id":1}'
    @hmac = Digest.hexencode(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @raw_body)
    )
    # base64-decode round trip expected by Request#hmac
    @hmac_b64 = Base64.strict_encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", @raw_body))
  end

  def test_hmac_validation_ignores_topic_shop_api_version_webhook_id
    headers_a = {
      "x-shopify-hmac-sha256" => @hmac_b64,
      "x-shopify-topic" => "orders/create",
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-api-version" => "2024-01",
      "x-shopify-webhook-id" => "aaa",
    }
    headers_b = headers_a.merge(
      "x-shopify-topic" => "customers/redact",
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
      "x-shopify-webhook-id" => "zzz",
    )

    req_a = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_a)
    req_b = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_b)

    assert ShopifyAPI::Utils::HmacValidator.validate(req_a)
    assert ShopifyAPI::Utils::HmacValidator.validate(req_b),
      "HMAC validation must remain valid even though topic/shop/webhook_id were rewritten, " \
      "proving the signature does not bind these fields"

    refute_equal req_a.shop, req_b.shop
    refute_equal req_a.topic, req_b.topic
  end
end
```
This directly demonstrates that `HmacValidator.validate` is invariant under mutation of `topic`, `shop-domain`, `api-version`, and `webhook-id`, confirming the signature coverage gap that `Registry.process` relies on for routing and dispatch.
