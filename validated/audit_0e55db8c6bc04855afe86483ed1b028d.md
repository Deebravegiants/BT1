Confirmed: the docs explicitly tell developers `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  and that `data.shop` is "The shop domain of the webhook" [2](#0-1)  — establishing that the gem promises the `shop` field is an authenticated identity, when in fact it is not covered by the HMAC.

### Title
Webhook HMAC only signs the raw body, not the `shop-domain`/`topic`/`webhook_id`/`api_version` headers, allowing tenant impersonation in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` only proves the body bytes were signed by Shopify with the app's shared client secret. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never part of the signed data, yet `Registry.process` trusts them to route and label the event, and the gem's own docs promise `data.shop` is a verified property of "the webhook."

### Finding Description
`AuthQuery` correctly binds `shop` into the HMAC-signed string used for OAuth callbacks: [3](#0-2) 

But `Webhooks::Request` does not do the same. `to_signable_string` is defined as only the raw body: [4](#0-3) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers that are excluded from that signable string: [5](#0-4) 

`Registry.process` validates only the HMAC over the body, then immediately trusts the unauthenticated header-derived `shop`/`topic`/`webhook_id`/`api_version` fields to dispatch to a handler and construct `WebhookMetadata`: [6](#0-5) [7](#0-6) 

Because Shopify signs webhook bodies with a single client-secret shared across *all* shops that have installed the app (not a per-shop secret), any `(raw_body, hmac)` pair that was legitimately generated for one shop's installation remains a valid signature no matter what `shop-domain`, `topic`, `webhook-id`, or `api-version` headers are sent alongside it. An unprivileged attacker who has installed the app on any shop they control (e.g., a free dev/test store) receives fully valid, signed webhook deliveries for that shop. They can capture one `(body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header to name a *different, victim* shop. `HmacValidator.validate` still returns `true` because it never inspects those headers, and the resulting `WebhookMetadata.shop` — which the gem's own documentation states is "the shop domain of the webhook" — is forged, breaking the binding: **shop authenticated by HMAC == shop delivered to the handler**.

### Impact Explanation
Host applications built on this gem are told (and reasonably rely on the fact) that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` identifies the originating shop. If a handler uses `data.shop` as the tenant key to look up/mutate per-shop state (a common, encouraged pattern, e.g. `perform_later(shop_domain: data.shop, webhook: data.body)` in the gem's own example), an attacker can inject arbitrary attacker-authored webhook bodies that are attributed to a victim shop of their choosing — a cross-tenant data-integrity/confidentiality issue reachable by any unprivileged internet user who can install the target app on a shop they control.

### Likelihood Explanation
The attacker only needs the ability to install the vulnerable app on any shop (including a free/trial store) and to send an HTTP request with a spoofed `shop-domain` header to the app's public webhook endpoint — no access to the app's `client_secret`, no privileged account, and no cryptographic break is required, since the header is simply never covered by the signature.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body, so that `Utils::HmacValidator.validate` cannot succeed for a request whose header-derived identity fields differ from what Shopify actually signed for that delivery.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker-shop.myshopify.com`. Shopify sends a legitimately signed webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (`H` = HMAC-SHA256(`B`, client_secret)), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Capture `(B, H)`.
3. Send a POST to the app's registered webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds `to_signable_string == B`; `Utils::HmacValidator.validate` recomputes HMAC over `B` and it matches `H`, so validation succeeds.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the app to process attacker-authored data as if it originated from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
