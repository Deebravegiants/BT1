### Title
Webhook `shop` (tenant identifier) is trusted from an unauthenticated HTTP header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the request body via HMAC, then hands the host application a `shop` value taken from the `X-Shopify-Shop-Domain` header, which is not part of the signed material. The binding `hmac-verified bytes == (shop, body)` does not hold; only `hmac-verified bytes == body` holds. Anyone who can obtain one genuinely-signed `(body, hmac)` pair (e.g., by installing the app on their own shop and receiving a legitimate webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will accept it and dispatch it to the host handler as if it belonged to the spoofed shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC solely over `to_signable_string` and compares it to the `hmac` field: [2](#0-1) 

`Request#shop`, however, is read directly from the (attacker-suppliable) `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the body: [3](#0-2) 

`Registry.process` verifies the HMAC over the body, then immediately forwards `request.shop` (the unauthenticated header) to the host application's handler as the tenant identifier, alongside the (authenticated) body: [4](#0-3) 

This is delivered to the handler via `WebhookMetadata`, whose `shop` field the host app is expected to use to select/attribute the correct tenant: [5](#0-4) 

The equality the gem should enforce is: `hmac == HMAC(secret, shop || body)` (or otherwise cryptographically bind `shop` to the signed payload). What is actually enforced is `hmac == HMAC(secret, body)`, with `shop` supplied out-of-band and unauthenticated. Consequently `verified(body) ⇏ verified(shop, body)` — the exact "field acted on but not covered by the HMAC" divergence pattern in the report (there, sigops after a disabled opcode; here, the shop/tenant header after the signed body).

### Impact Explanation
An attacker who obtains any single legitimately-signed `(body, hmac)` pair from Shopify (trivially achievable by installing the target app on a shop they control and receiving one real webhook, which requires no privileged access or leaked secrets) can replay that exact body and HMAC to the app's shared webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` value. `HmacValidator.validate` will accept it because it never inspects the shop header, and `Registry.process` will hand the host app a `WebhookMetadata` claiming the body originated from a different, victim shop. Any host application that uses `data.shop` to select the tenant record to update (a common, gem-endorsed pattern, since `WebhookMetadata#shop` is the only tenant hint the gem provides) will apply the attacker's payload to the wrong tenant's data — a cross-tenant write/data-confusion primitive driven entirely through this gem's webhook verification API.

### Likelihood Explanation
Moderate-to-high: no secrets, tokens, or privileged access are required. The only precondition is capturing one real webhook payload+signature, which any user who installs the target app on their own store can obtain by design (e.g., pointing/observing their own webhook endpoint traffic). Replaying an HTTP request with a modified header is trivial. The bug is exercised entirely through the gem's own `Webhooks::Request` / `Webhooks::Registry` / `HmacValidator` code paths, not through host misuse.

### Recommendation
Bind the shop identity to the signed material before trusting it: derive `shop` for `WebhookMetadata` from a source that is cryptographically covered by the HMAC (e.g., include the shop domain in the signable string, or cross-check `request.shop` against a shop already associated with the delivered `webhook_id`/topic via a prior registration lookup) rather than passing the raw, unauthenticated `X-Shopify-Shop-Domain` header straight through to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers webhook `orders/create`.
2. Shopify delivers a legitimate webhook to the app's endpoint: body `B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and resends a request to the same endpoint with headers `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:13-22` succeeds because it only checks `H` against `HMAC(secret, B)`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` invokes the host handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
