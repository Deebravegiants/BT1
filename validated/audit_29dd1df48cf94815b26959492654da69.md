### Title
Malicious swap route can append an unrelated wallet-token transfer to the victim's authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

Strategy entrypoints accept an opaque route payload and execute route-selected third-party code beneath the caller's broad strategy authorization. A malicious route component can request a token transfer from the victim to the attacker; Soroban simulation records that request as a child of the victim's `swap_collateral` authorization, and enforcement accepts it if the poisoned tree is signed. This allows theft of wallet assets unrelated to the supplied collateral. [1](#0-0) [2](#0-1) 

### Finding Description

`swap_collateral(caller, account_id, current, amount, new, swap)` accepts `swap` as arbitrary `Bytes`, while `StrategySwap` is only an opaque alias for bytes. [1](#0-0) [3](#0-2) 

`process_swap_collateral` requires the caller to be the account owner or an active delegate, withdraws `amount` of `current`, passes the opaque route to the configured aggregator, and deposits the measured output. [4](#0-3) 

The controller narrowly authorizes only `token_in.transfer(controller, router, amount_in)` on its own behalf, but this does not prevent route-selected code from making a separate `require_auth` request against the human caller. [5](#0-4) [6](#0-5) 

The route boundary allows payload-selected third-party code below the caller's authorization; such a transfer is recorded as a child of that authorization and executes if the caller signs the resulting tree. [7](#0-6) 

The dedicated regression test demonstrates the concrete shape: a route-selected malicious pool calls `transfer(victim, attacker, wallet_balance)` for an unlisted wallet token, simulation attaches that transfer beneath the victim's `swap_collateral` root, and signing the recorded tree drains the wallet token. [8](#0-7) [2](#0-1) 

### Impact Explanation

A victim signing a poisoned route can lose unrelated wallet tokens up to the amounts encoded in the hidden authorization child, in addition to performing the requested collateral swap. [9](#0-8) 

This is theft of user funds rather than route slippage: the stolen token need not be a listed collateral, debt asset, route input, or route output. [10](#0-9) [9](#0-8) 

### Likelihood Explanation

Exploitation requires the victim to submit a malicious route and sign the authorization tree containing the extra token transfer, so it depends on compromised route generation, malicious route construction, or inadequate wallet decoding. [7](#0-6) 

The host rejects the same malicious route when only the honest root authorization is signed, which limits the issue to signed poisoned trees rather than allowing an unauthenticated direct drain. [11](#0-10) 

Because the malicious child is produced by route-selected code and is not bounded by the controller's input authorization, opaque route bytes create a practical supply-chain-style signing attack surface. [3](#0-2) [12](#0-11) 

### Recommendation

Restrict strategy routes to governance-approved venue contracts and pool addresses rather than allowing route-selected arbitrary contracts beneath the user's authorization. [7](#0-6) 

Require clients and wallets to decode every `swap` payload and reject any authorization child other than the expected strategy operations; legitimate collateral swaps should not contain an unrelated wallet-token transfer. [7](#0-6) 

Display the full decoded child authorization tree before signing, including token contract, function, sender, recipient, and amount. [13](#0-12) 

### Proof of Concept

1. The victim owns `account_id` with USDC collateral and also holds an unrelated wallet token. [14](#0-13) 
2. The attacker supplies a route whose selected pool contract is configured with `(victim, wallet_token, attacker, wallet_balance)`. [8](#0-7) 
3. The victim invokes `swap_collateral(victim, account_id, usdc_key, amount, eth_key, malicious_swap_bytes)`. [1](#0-0) 
4. During route execution, the malicious pool calls `wallet_token.transfer(victim, attacker, wallet_balance)`. [15](#0-14) 
5. Simulation records that transfer as a child under the victim's `swap_collateral` authorization. [16](#0-15) 
6. If the victim signs that returned tree, enforcement executes both the legitimate swap and the unrelated wallet transfer, leaving the attacker with `wallet_balance`. [9](#0-8)

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
