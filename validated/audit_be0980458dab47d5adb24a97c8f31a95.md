### Title
Webhook shop/topic identity fields are read from unauthenticated headers while the HMAC only signs the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the webhook HMAC exclusively over the raw request body, but the `shop`, `topic`, and `webhook_id` fields that the `Registry` uses to route the payload to a tenant-specific handler are taken from HTTP headers that are **not** covered by that HMAC. This breaks the identity binding `authenticated_bytes == acted_upon_bytes`, mirroring the reported bug class where the value acted upon (`shop`/`topic`) is not the value the signature actually protects (only `@raw_body`).

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from request headers with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` only checks that `hmac` matches `compute_signature(to_signable_string, secret)` — i.e. it authenticates the body bytes, never the header bytes: [3](#0-2) 

`Registry.process` (exercised in `test/webhooks/registry_test.rb`) dispatches the handler using `data.topic` and `data.shop` taken directly from this unauthenticated header data: [4](#0-3) 

The equality the gem should enforce is:
`hmac_signed_bytes == bytes_that_determine_tenant/topic_routing`

but instead the gem enforces only:
`hmac_signed_bytes == raw_body`

while `shop`/`topic`/`webhook_id` (the values that determine *which tenant's* handler processes the payload) are taken from a completely separate, unauthenticated channel (HTTP headers).

### Impact Explanation
Any party who possesses one legitimate, validly-signed `(raw_body, hmac)` pair for a webhook delivered to their own app installation (e.g., from their own shop's test webhook subscription) can replay that exact request while substituting the `shopify-shop-domain` (and/or `shopify-topic`/`shopify-webhook-id`) header. Because the HMAC never covers those headers, `HmacValidator.validate` still returns `true`, and `Registry.process` will hand the (attacker-influenced) payload to the handler under a **different shop's identity**. Host applications that key their per-shop data mutations off `Webhooks::Request#shop` (as the gem's own tests and docs assume they will) can be made to write/act on data under a victim tenant's shop, which is a cross-tenant access/confusion issue.

### Likelihood Explanation
Exploitation requires only one genuine `(body, hmac)` webhook delivery, which any installer of the app can obtain for their own shop through normal use (no `client_secret`, access token, or privileged role needed, and no TLS interception is required since the attacker is the legitimate recipient of their own webhook). The header substitution itself is trivial once such a delivery is captured.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material, or otherwise verify them against a trusted source (e.g., the shop associated with the currently-processing session/subscription) before dispatching to a handler. At minimum, `Registry.process` should cross-check that the `shop-domain` header corresponds to a shop that this app instance actually expects for the given webhook_id/topic before trusting it as the tenant identity.

### Proof of Concept
1. App merchant A installs the app on `shop-a.myshopify.com` and legitimately receives a real webhook delivery: body `B`, headers `{shopify-topic: "orders/create", shopify-shop-domain: "shop-a.myshopify.com", shopify-hmac-sha256: H}` where `H = HMAC(secret, B)`.
2. Attacker (merchant A) replays the exact same request to the app's webhook endpoint but changes only `shopify-shop-domain` to `shop-b.myshopify.com` (a victim tenant). `H` is unchanged and still valid because it was only ever computed over `B`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` succeeds validation via `HmacValidator.validate` (see [5](#0-4) ), and `Registry.process` dispatches the handler with `shop == "shop-b.myshopify.com"`, causing the app to process attacker-controlled body content under the victim shop's identity.

          received_signature = verifiable_query.hmac
