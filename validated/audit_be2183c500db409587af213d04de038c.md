### Title
Silent zero-value delivery on cross-chain token receipt due to decimal down-conversion truncation - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler converts an incoming ERC20-denominated amount to the local substrate balance by integer division, with no check that the result is non-zero. A cross-chain transfer whose value is smaller than the decimal scaling factor between the EVM token and the local asset is silently accepted and processed as a zero-amount mint/unlock, while the corresponding value was already burned/locked on the EVM side — a permanent, un-refundable loss of the transferred value, with no revert and no timeout-triggered refund.

### Finding Description
The decimals-down conversion helper simply truncates: [1](#0-0) 

`register_token`/`update_token` only enforce `erc_decimals >= local_decimals`: [2](#0-1) 

so `on_accept` (handling a `PostRequest` dispatched from an EVM `HyperFungibleToken`/`BridgeToken` contract) always divides the incoming amount down when `erc_decimals > local_decimals`: [3](#0-2) 

`convert_to_balance` never rejects a result of `0`; `"0".parse::<B>()` succeeds, so the flow proceeds to `NativeCurrency::transfer`/`Assets::mint_into` with `amount = 0`, deposits a `TokenReceived` event with `amount: 0`, and returns `Ok(...)` — the message is treated as fully and successfully delivered. There is no on-chain validation anywhere in this path that the post-conversion amount must be greater than zero.

The same truncating conversion is reused, with the same lack of a non-zero check, in the timeout-refund path: [4](#0-3) 

A concrete instance: `BridgeToken` on EVM is 18-decimal while `BRIDGE` is 12-decimal on nexus, so the pallet scales by `10^6` in both directions per its own documentation: [5](#0-4) 

Any EVM `send()` call whose burned amount is less than `10^6` wei (i.e. less than `0.000001` of a token in 18-decimal terms — an amount well within reach of any unprivileged caller/relayer) produces `convert_to_balance(value, 18, 12) == 0` on nexus: the ISMP request is accepted, `on_accept` succeeds, the beneficiary is credited nothing, and no error/timeout is raised to trigger a refund path. The EVM-side burn (or lock, for `WrappedHyperFungibleToken`) is final and irreversible once the request has been "successfully" delivered, so the corresponding value is permanently lost with no recovery mechanism, exactly the "rounds to zero and the caller has no way to know / no revert occurs" bug class described in the source report (there, a Bancor virtual-supply initialization producing a zero input to `calculatePurchaseReturn`; here, ERC20→substrate decimal truncation producing a zero-value mint that the module still reports as a successful delivery).

### Impact Explanation
This is a token-bridge mint/burn correctness bug directly reachable by any unprivileged token bridger dispatching a cross-chain transfer through `HyperFungibleToken`/`BridgeToken` and `pallet-hyper-fungible-token`. Funds burned/locked on the EVM source chain can be permanently lost (frozen with no recipient) whenever the decimal-scaled amount truncates to zero, without any revert, error, or timeout-triggered refund — a permanent freezing/loss-of-funds condition on a live, ISMP-driven message-delivery path.

### Likelihood Explanation
Likelihood is moderate: the condition triggers deterministically whenever `amount < 10^(erc_decimals - local_decimals)`, which for pairs with a large decimal gap (e.g. BRIDGE's 18-vs-12 setup, `10^6`) covers a wide range of legitimate small transfer sizes, not just adversarially crafted dust. It requires no special privilege, only a normal `send()` call with a sufficiently small amount, and can also occur accidentally from a UI/SDK amount-formatting mistake, or be deliberately triggered by anyone wanting to grief a specific transfer/timeout-refund flow.

### Recommendation
In `convert_to_balance` (or immediately after calling it in both `on_accept` and the `on_timeout` refund path), explicitly reject a truncated-to-zero result — return an error (e.g. a new `HftError::AmountTooSmall`) instead of silently proceeding — so that any inbound transfer/refund whose local-denominated value would be zero fails loudly (leaving the request undelivered/refundable) rather than completing as a false "success" with no value transferred.

### Proof of Concept
1. Register a token via `register_token` with `local_decimals = 12` and `config.decimals (erc_decimals) = 18` for an EVM chain (satisfies `erc_decimals >= local_decimals`), as `BridgeToken` does.
2. From the EVM `HyperFungibleToken`/`BridgeToken` contract, call `send()` with `amount = 999_999` (less than `10^6`), which burns/locks `999_999` wei on the EVM side and dispatches an ISMP POST with `Message.amount = 999_999`.
3. On nexus, `on_accept` is invoked: `convert_to_balance(999_999, 18, 12)` computes `999_999 / 10^6 = 0`, parses to `0`, and the handler proceeds to `mint_into`/`transfer` with `amount = 0`, emits `TokenReceived { amount: 0, .. }`, and returns `Ok(..)` — the ISMP module reports successful delivery.
4. Result: the `999_999` wei burned/locked on EVM is never recovered; the beneficiary receives `0` tokens on nexus, and because the message was processed "successfully" (not timed out), the automatic timeout-refund path in `on_timeout` never triggers.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
