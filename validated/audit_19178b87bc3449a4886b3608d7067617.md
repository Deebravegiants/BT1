This confirms the analog: the workflow owner's request digest is deterministic — computed purely from the JSON-RPC request content (`method`, `id`, `params`) via `req.Digest()` — and is published on-chain via `WorkflowRegistry.AllowlistRequest()` **before** the owner ever sends the actual request to the gateway [1](#0-0) . Since the on-chain allowlist entry (`RequestDigest`, `Owner`, `ExpiryTimestamp`) is public, any unprivileged party can read it and learn the exact digest that will authorize a pending request [2](#0-1) . Chainlink's own `RequestReplayGuard` records the digest on **first-use** and rejects any subsequent request with the same digest, regardless of which caller submitted it first [3](#0-2) , and this guard is invoked immediately after `AuthorizeRequest` succeeds, before validating that the caller's request body matches the allowlisted owner's actual secret payload [4](#0-3) .

### Title
Front-runnable Vault request-digest allowlist enables unprivileged replay-guard DoS of legitimate `vault.secrets.*` requests - (File: `core/capabilities/vault/authorizer.go`)

### Summary
The Vault gateway authorizes JSON-RPC requests by matching a locally-computed `req.Digest()` against digests published on-chain via `WorkflowRegistry.AllowlistRequest()` [5](#0-4) . Because the digest is a pure hash of `method`+`id`+`params` and is broadcast on-chain (public and visible before the owner's actual gateway call lands), an unprivileged actor who observes the on-chain allowlist transaction can construct/replay the identical JSON-RPC body and race it to the gateway first.

### Finding Description
`allowListBasedAuth.AuthorizeRequest` treats *any* caller whose submitted request digest matches an on-chain allowlisted digest as authorized for that digest's owner [6](#0-5) : it returns an `AuthResult` with `workflowOwner = allowlistedRequest.Owner`, independent of who actually sent the HTTP/gateway request. The generic `authorizer.AuthorizeRequest` then immediately calls `a.replayGuard.CheckAndRecord(authResult.Digest(), ...)`, which succeeds only for the first submission of that digest and permanently (until expiry) rejects every subsequent submission with `ErrRequestAlreadySeen` [7](#0-6) [8](#0-7) .

Because the digest depends only on the exact serialized request body (not on any request-signing secret held solely by the true owner), and because that digest is published on-chain by the owner's own `AllowlistRequest` transaction (a public blockchain transaction, analogous to a mempool-visible tx) prior to the owner's HTTP submission to the gateway, an attacker monitoring the chain can:
1. Observe the newly allowlisted `RequestDigest` and reconstruct/guess the exact request JSON that hashes to it (for non-secret methods such as `vault.secrets.list`/`vault.secrets.delete`, whose params are plaintext and not randomized, the attacker can trivially know or brute-force the exact byte-for-byte body — e.g., `{"request_id":..., "owner":..., "namespace":...}` — since these fields are typically predictable/observable metadata, unlike the encrypted-secret `create`/`update` paths).
2. Submit that reconstructed JSON-RPC request to the gateway before the legitimate owner does.
3. Have it pass `AllowListBasedAuth` (digest matches) and consume the replay-guard slot for that digest.
4. The legitimate owner's subsequent, genuine submission of the same request is then rejected with "request was already authorized previously" for the full `ExpiryTimestamp` window (the code's own tests confirm the on-chain expiry can be set up to an hour or more ahead — see `ExecuteSecrets`, `expiry := ... time.Now().Add(time.Hour)` [9](#0-8) ).

This mirrors the Treasury report's root cause precisely: an unprivileged actor observes a soon-to-be-legitimate operation in a public/pending state (mempool tx / on-chain allowlist tx) and front-runs it to poison shared state (`_totalValue` overflow / replay-guard "seen" map) that blocks the legitimate operation from ever succeeding.

### Impact Explanation
An unprivileged party can deny a specific workflow owner's `vault.secrets.list`, `vault.secrets.delete` (and potentially `create`/`update` for non-random or replayed ciphertext) requests for as long as the allowlist entry remains valid, disrupting Vault-dependent workflow operations without needing any credentials, JWT, or knowledge of secret material. This is a genuine allowlist/request-impersonation-adjacent bypass: the replay guard authorizes based purely on digest match, not on request provenance, so "first digest wins" regardless of caller identity.

### Likelihood Explanation
Likelihood is bounded by the requirement that the attacker can reconstruct the *exact* serialized request bytes that will hash to the on-chain-published digest. For `vault.secrets.list`/`delete`, whose params contain no attacker-unknown randomness (namespace, owner, ids — all attacker-observable or guessable metadata), this is straightforward. For `create`/`update`, params contain TDH2-encrypted ciphertext which is normally randomized per-encryption, making exact reconstruction infeasible unless the attacker can observe the plaintext request bytes in transit (e.g., via network positioning) — reducing likelihood for those methods to a monitor-and-race scenario rather than pure guessing.

### Recommendation
- Do not authorize solely on digest match with an "any first submitter wins" replay guard; bind the digest check to a request-provenance signal that only the legitimate owner controls (e.g., require an additional owner signature over the full request, or scope the replay-guard entry to the specific connection/session that fetched the allowlisted expiry, not to a global first-come map).
- Consider making the on-chain `AllowlistRequest` call itself carry a commitment (e.g., allow the owner to also submit a nonce/secret alongside the digest that must be echoed in the gateway request) so an observer of the on-chain digest cannot forge a request that satisfies both digest match and provenance.
- Shorten the default allowlist expiry window and/or allow the legitimate owner to explicitly invalidate/replace a consumed digest before expiry so a front-run cannot block them for the full window.

### Proof of Concept
Conceptual reproduction based on existing test helpers (`allowlistRequest` / `ExecuteSecrets`) [10](#0-9) :
1. Owner O prepares a `vault.secrets.list` request body B with predictable `namespace`/`owner` fields and computes `digest = Digest(B)`.
2. O calls `WorkflowRegistry.AllowlistRequest(digest, expiry)` on-chain — this transaction and its `RequestDigest` are publicly visible via `GetAllowlistedRequests` [11](#0-10) .
3. Attacker A observes the on-chain digest, reconstructs the exact byte-for-byte body B (feasible for list/delete since params are non-secret and observable/guessable), and POSTs B to the gateway before O does.
4. `allowListBasedAuth.AuthorizeRequest` matches digest → returns `AuthResult{workflowOwner: O}` [6](#0-5) ; `authorizer.AuthorizeRequest` records the digest in the replay guard and processes A's request as if from O [7](#0-6) .
5. O's subsequent legitimate submission of the identical B is rejected: `CheckAndRecord` returns `ErrRequestAlreadySeen` [12](#0-11) , denying O's operation until `ExpiryTimestamp` passes.

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

	for _, item := range allowListedRequests {
		if item.RequestDigest == digest {
			return &item
		}
	}
	return nil

var ErrRequestAlreadySeen = errors.New("request was already authorized previously")

// RequestReplayGuard prevents replay of already-processed requests by tracking
// request digests with expiry timestamps. It is safe for concurrent use.
//
// Used by both the AllowListBasedAuth flow and the JWTBasedAuth flow to ensure
// that a given request digest is only accepted once.
type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
