### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted as tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC verification only covers the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values — which are handed to the app's handler as the trusted tenant/event identity — come straight from unauthenticated HTTP headers and are never bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read verbatim from HTTP headers with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` performs exactly that check and then immediately forwards the *unauthenticated* `request.shop` to the app-supplied handler as the trusted tenant identifier: [4](#0-3) 

The gem's own documentation describes `process` as verifying "the request did indeed come from Shopify" and describes `data.shop` simply as "The shop domain of the webhook" with no caveat that it is unauthenticated: [5](#0-4) [6](#0-5) 

This is the same identity-binding failure described in the report's bug class: a field that is *acted on* (the shop used to route/scope the webhook payload) is not *covered by the HMAC* that is supposed to authenticate the request. The equality that should hold — `shop bound by HMAC == shop used for tenant scoping` — is broken: the HMAC only proves `hmac == HMAC(body, shared_secret)`, it proves nothing about which shop the body belongs to.

### Impact Explanation
Because the app's shared `client_secret` (`api_secret_key`) is the same for every shop that installs the app, any merchant who installs the app on their *own* store is an "unprivileged internet user" relative to other tenants of the same app, yet can obtain real, validly-signed `(body, hmac)` pairs for events they trigger in their own store (e.g. creating an order with attacker-chosen field values, since only the shared secret — not a shop-specific secret — is used to sign). Because the header carrying `shop` is not included in the signed material, that attacker can POST the exact same `(body, hmac)` pair to the target app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` calls the handler with `shop: <victim-domain>` and attacker-controlled `body`. Any host application that uses `data.shop` from `WebhookMetadata` to scope/attribute the payload (exactly as the gem's own documented example does — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-controlled data under a victim tenant's identity — cross-tenant data injection/confusion.

### Likelihood Explanation
Requires only: (1) the attacker holds a legitimate (even free/trial) installation of the target app on their own store — no special privilege, secret, or token needed; (2) they can trigger a webhook-eligible event in their own store with attacker-controlled content; (3) they can send an arbitrary HTTP POST to the app's public webhook URL, which is unauthenticated by design (that's the point of HMAC verification). No TLS interception, credential theft, or social engineering is required. This is a realistic, low-effort path once the identity-binding gap is understood, though it is bounded by needing the app's webhook endpoint URL (typically discoverable/predictable) and reliant on the host app trusting `data.shop` as the gem's own documentation instructs.

### Recommendation
Do not treat `Registry.process`/`HmacValidator.validate` as proof of shop identity. At minimum:
- Update `docs/usage/webhooks.md` and `WebhookMetadata` documentation to explicitly state that `shop`, `topic`, `api_version`, and `webhook_id` are **not** covered by the HMAC and must not be trusted as authenticated tenant identity on their own.
- Provide (or require) a secondary check that the `shop` in the webhook matches a shop for which the app currently holds an active session/installation before dispatching to the handler, and reject otherwise.
- Where feasible, prefer verifying the `webhook_id` for idempotency/replay defense in addition to shop validation, since HMAC alone does not prevent replay to a different tenant context.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (a normal, unprivileged installation flow).
2. Attacker triggers a webhook-eligible event (e.g. `orders/create`) with attacker-chosen order fields in their own store; Shopify sends a real HTTP POST to the app's webhook endpoint with headers `x-shopify-hmac-sha256: <valid hmac of body>`, `x-shopify-shop-domain: attacker.myshopify.com`, and the JSON body.
3. Attacker captures this exact `(raw_body, hmac header)` pair (e.g. by running the webhook receiver behind a proxy they control, or via any request logging they have access to for their own endpoint).
4. Attacker sends a new POST directly to the same app's public webhook endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds — the forged shop header was never checked.
6. The app's handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, causing the host app (following the gem's documented usage pattern) to process/attribute attacker-controlled data as belonging to `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

- `body`, `T::Hash[String, T.untyped]`- The body of the webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
