### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the shop identity used to route the webhook to a merchant's data is taken from an unauthenticated HTTP header. Any user who can trigger and capture a legitimately-signed webhook for their own store (which anyone can do simply by installing the app on their own development shop) can replay that valid `(body, hmac)` pair while substituting a different `shop-domain` header, and the library will accept it as authentic for the substituted shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the supplied `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body — none of the identifying headers are part of the signed content: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all parsed straight from unauthenticated headers: [3](#0-2) 

`Registry.process` validates the HMAC against the body, then immediately trusts `request.shop` (and the other header-derived fields) to dispatch the webhook to the app's handler, without any additional binding between the signed body and the claimed shop: [4](#0-3) 

Because the HMAC is computed with the app's single, shop-independent `api_secret_key` (the same secret is used to validate webhooks for every shop that has installed the app — see `HmacValidator.validate` above, which only depends on `Context.api_secret_key`/`Context.old_api_secret_key`, not on any per-shop value), a `(body, hmac)` pair generated for one shop is valid input for *any* shop as far as this library's verification is concerned. The equality the library should enforce — "the shop the HMAC-signed bytes originated from" == "the shop passed to the webhook handler" — is never checked; instead the code checks "HMAC(body) is valid" and separately, unconditionally trusts "the shop header says X".

### Impact Explanation
This breaks the tenant isolation guarantee that host applications rely on: `WebhookMetadata.shop` is the value applications use to look up the correct merchant record/session and apply the webhook payload. An attacker who operates their own shop (a completely unprivileged, legitimate install) can capture a real, validly-signed webhook delivery for an event they control (e.g., `orders/create` with a body they crafted via their own store), then replay it against the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. `Registry.process` will validate the (unmodified) body's HMAC successfully and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Depending on how the host app uses `data.shop` and `data.body` together (e.g., writing/merging attacker-supplied body content into the victim shop's records, or triggering actions scoped to the victim shop), this can result in cross-tenant data corruption or unauthorized actions being taken against a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app that has a public/unauthenticated webhook installation on more than one shop: obtaining a legitimately-signed webhook body/HMAC pair requires nothing more than installing the app on an attacker-owned test store (or any store) and triggering an event — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. The only capability required is direct HTTP access to the webhook endpoint, which is by design internet-reachable.

### Recommendation
Include a shop-binding value inside the HMAC-signed payload rather than trusting an out-of-band header. Since Shopify does not include a per-shop HMAC key, mitigate by cross-checking the `shop-domain` header against an independently-authenticated source of truth before processing (e.g., verifying the shop is a known/installed shop for this app and, where possible, correlating the header with a value embedded in the body such as `admin_graphql_api_id`/`myshopify_domain` fields Shopify includes in many payloads), and reject/flag webhook processing when they disagree. At minimum, document that `request.shop` is unauthenticated and must not be trusted for authorization decisions without an additional installed-shop check performed by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and configures/triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header `H` that Shopify sends — both are valid for the app's shared `api_secret_key`.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with the same body `B` and same `hmac` header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` instead of their own domain.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (unchanged, still `B`) and successfully matches `H`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, i.e., attacker-controlled body content is delivered as if it originated from the victim shop.
