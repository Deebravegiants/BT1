Confirming the key facts: `Router._computeBuy` in `Router.sol` lacks the `realBalance >= reserveToken` donation guard that `Bonding.previewLtUntilGraduation` explicitly added (visible at `Bonding.sol:728-729`), and the TOKEN-donation attack that inflates `pair.tokenBalance()` above the stored `reserveToken` is proven reachable and demonstrated in `test_donation_realBalanceExceedsReserveToken` in `Zap.t.sol`.

### Title
Permanent DoS of the bonding-curve buy path via TOKEN-donation-induced underflow in `Router._computeBuy`'s overflow cap - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's real token balance whenever the uncapped constant-product output would exceed it, and back-calculates `amountInUsed` from `cappedReserveToken = reserveToken - tokensOut`. This subtraction assumes the hard invariant `pair.tokenBalance() < reserveToken` (`realBalance < reserveToken`), which the codebase itself acknowledges can be broken by an unprivileged TOKEN-donation attack (as proven by `Zap.t.sol`'s `test_donation_realBalanceExceedsReserveToken`). `Bonding.previewLtUntilGraduation` was patched with an explicit `if (realBalance >= reserveToken) return ...` guard for exactly this scenario, but `Router._computeBuy` — the function that actually executes buys — has no equivalent guard. Once an attacker donates enough TOKEN directly to the `Pair` to push `realBalance` above the stored `reserveToken`, any subsequent buy whose uncapped `tokensOut` exceeds `realBalance` triggers `cappedReserveToken = reserveToken - tokensOut`, which underflows and reverts with an unhandled `Panic(0x11)`.

### Finding Description
The overflow-cap branch in `Router._computeBuy`:

```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // assumes realBalance < reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
``` [1](#0-0) 

relies on the documented invariant "`pair.tokenBalance() < pair.tokenReserve()`... at every state of the curve," which the invariant test explicitly calls "what makes the `cappedReserveToken == 0` branch in `Router._computeBuy` unreachable; if it ever ceased to hold, that branch would revert with `OverflowCapDegenerate` rather than over-pay": [2](#0-1) 

The comment's own claim — that violating the invariant would only revert with the clean `OverflowCapDegenerate`, not underflow — is wrong: `OverflowCapDegenerate` only fires when `cappedReserveToken == 0` (i.e. `tokensOut == reserveToken` exactly); if `tokensOut = realBalance > reserveToken`, the subtraction underflows to a Panic *before* that check is ever reached.

The invariant is not actually enforced on-chain. Any wallet that has bought TOKEN from the curve can donate it straight back to the `Pair` via a plain ERC20 `transfer`, inflating `pair.tokenBalance()` without touching the stored `reserveToken`. This exact primitive is already proven reachable and is unrelated to `previewLtUntilGraduation` — it operates purely on `Pair.tokenBalance()`, which `Router._computeBuy` also reads directly: [3](#0-2) 

The protocol already recognized this donation class breaks the `realBalance < reserveToken` invariant and patched the symptom in `previewLtUntilGraduation` with an explicit guard:
```solidity
// Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
if (realBalance >= reserveToken) return ltUntilThreshold;
``` [4](#0-3) 

but the identical guard is missing from `Router._computeBuy`, the function that `Router.buy` (and therefore `Bonding.buy` / `Zap.buy`) actually executes trades through: [5](#0-4) 

After the donation, small buys still succeed because the uncapped `tokensOut` for a small `amountIn` doesn't exceed the (now-inflated) `realBalance`, so the cap branch never fires — this is exactly the scenario the existing `test_donation_zapBuyStillSucceeds` covers, and it masks the bug for casual review. But any buy large enough that the uncapped `tokensOut` (computed from `reserveToken`, unaffected by the donation) exceeds the inflated `realBalance` enters the cap branch and underflows. Since `realBalance` only grows with each additional donation and the curve's remaining sellable-supply headroom shrinks as more buys land, this scenario becomes trivially reachable: the attacker (or anyone) simply needs to submit one large enough `Zap.buy` / `Bonding.buy` after donating.

### Impact Explanation
Once triggered, every subsequent buy attempt that lands in the cap branch reverts with an undecodable `Panic(0x11)` instead of executing or cleanly reverting. Because the donation is cheap relative to the curve (an attacker recycles TOKEN they already bought back into the `Pair`, and `test_donation_realBalanceExceedsReserveToken` shows the necessary drain is achievable via ordinary large buys), any unrelated wallet can permanently grief the closing/large-size buy path on a live bonding curve: traders attempting to buy the tail of the curve's remaining sellable supply, and the closing buy that is supposed to arm the supply-trigger graduation via `IPair.tokenBalance() == 0`, become unreachable. This is a freezing-of-funds / availability bug on the core `Zap.buy` / `Bonding.buy` path reachable by any unprivileged wallet, directly analogous to the reported CVE's malformed-input-triggers-crash-on-a-specific-code-path class.

### Likelihood Explanation
High. The precondition — TOKEN donation inflating `realBalance` above `reserveToken` — is already demonstrated as reachable in the existing test suite (`_stageDonationAttack` / `test_donation_realBalanceExceedsReserveToken`), requiring only ordinary curve buys plus a plain ERC20 `transfer` of the purchased TOKEN back to the `Pair`. No privileged role, no upgrade, and no off-chain component is needed; the trigger buy is a normal `Zap.buy`/`Bonding.buy` call sized to intersect the overflow-cap branch.

### Recommendation
Add the same donation guard to `Router._computeBuy` that `Bonding.previewLtUntilGraduation` already has: before computing `cappedReserveToken = reserveToken - tokensOut`, check `if (realBalance >= reserveToken)` and handle it without underflowing (e.g. treat the curve as fully drained / cap at `reserveToken - 1`, or revert with a clean, documented error rather than a bare Panic). Re-run `test/GraduationInvariants.t.sol` and add a dedicated regression test that drives a large buy through the donation-inflated state to confirm `Router.buy` no longer underflow-reverts.

### Proof of Concept
1. Launch a token via `Bonding.launch` / `Zap.createToken`.
2. Attacker (or any wallet) buys a large chunk of the curve via `Zap.buy`/`Bonding.buy`, sized so `tokensOut > LP_RESERVE` (250M), exactly as `_stageDonationAttack` does in `Zap.t.sol`: [6](#0-5) 
3. Attacker `transfer`s the purchased TOKEN directly to the `Pair` address (no `Router`/`Bonding` involvement). This is proven in the test suite to push `pair.tokenBalance() > reserveToken`: [7](#0-6) 
4. Any wallet then submits a buy sized so that the *uncapped* constant-product `tokensOut` (computed from the unaffected `reserveToken`/`k`) exceeds the now-inflated `realBalance` — e.g. a buy attempting to acquire most of the remaining nominal curve supply. `Router._computeBuy` enters the `tokensOut > realBalance` branch, sets `tokensOut = realBalance`, and computes `cappedReserveToken = reserveToken - tokensOut`, which underflows (`realBalance > reserveToken`) and reverts with `Panic(0x11)`, bricking that buy and every future buy that would land in the same branch.

    function previewBuy(

        uint256 amountIn

        if (amountIn == 0) revert ZeroAmount();
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();

    /// @dev Capped: `amountInUsed` is back-calculated from the K invariant
    ///      (rounded up so the curve never under-charges).
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {

        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
