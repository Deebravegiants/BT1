### Title
Denial of Service via Infinite Loop in GRANDPA `AncestryChain::ancestry()` on Cyclic Attacker-Supplied Headers - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
The GRANDPA consensus client's ancestry-walking routine, `AncestryChain::ancestry()`, contains an unbounded `while` loop that walks `parent_hash` pointers from a `block` hash back to a `base` hash using a map built entirely from attacker-supplied header data (`finality_proof.unknown_headers`). Because the loop's only exit conditions are "reached `base`" or "hash missing from map," a relayer can submit two or more crafted headers whose `parent_hash` fields form a cycle (`H_A.parent_hash() == H_B.hash()` and `H_B.parent_hash() == H_A.hash()`), causing the loop to spin forever. This is executed inside `verify_grandpa_finality_proof`, *before* the justification's cryptographic signatures are ever checked, so no valid GRANDPA votes are required to trigger it. Because this path is reached via `pallet-ismp`'s permissionless `handle_unsigned` extrinsic (and its `validate_unsigned` hook, which runs during transaction-pool validation on every node), a single crafted message can hang block execution / transaction validation indefinitely — the same bug class (CWE-835, loop with unreachable exit condition on adversarial zero/cyclic input) as the reported `BigInteger.modInverse()` DoS.

### Finding Description
`AncestryChain::ancestry()`: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is a `BTreeMap<H::Hash, H>` built directly from `finality_proof.unknown_headers`, a `Vec<H>` fully controlled by whoever submits the consensus message — there is no validation that these headers form an acyclic chain, and no iteration bound.

`verify_grandpa_finality_proof` calls this function twice, and critically, *before* verifying the justification's signatures: [2](#0-1) 

The order is:
1. Build `headers = AncestryChain::new(&finality_proof.unknown_headers)` from fully attacker-controlled headers.
2. Cheap hash-equality checks (`target.hash() == finality_proof.block`, `justification.commit.target_hash == finality_proof.block`) — trivially satisfiable by an attacker who freely chooses header contents and just SCALE-decodes an arbitrary `Commit` with a matching `target_hash`.
3. `headers.ancestry(base.hash(), consensus_state.latest_hash)` and `headers.ancestry(from, target.hash())` — the vulnerable calls — executed **before** `justification.verify(...)` on line 92.

So an attacker can craft two headers `H_A`/`H_B` with `H_A.parent_hash() = H_B.hash()` and `H_B.parent_hash() = H_A.hash()`, set `base`/`target`/`block` values so the hash-equality gates pass, and never needs a validly-signed justification at all — the infinite loop is hit before any signature is checked.

This is reached through the standard, permissionless consensus-update path: `pallet-ismp::handle_unsigned` is an unsigned extrinsic executable by anyone, and dispatches into the GRANDPA `ConsensusClient::verify_consensus` implementation: [3](#0-2) [4](#0-3) 

Note that `validate_unsigned` itself calls `Self::execute(messages.clone())`, meaning the infinite loop triggers during **transaction-pool validation on every node**, not merely on block execution by one collator — an even lower-cost, more widely amplifying DoS than a normal execution-time bug.

### Impact Explanation
This is a High severity, network-reachable Denial of Service against a core consensus-verification component: any full node or collator running `pallet-ismp` with the GRANDPA client would hang indefinitely (100% CPU, unresponsive) upon receiving/validating a single crafted `ConsensusMessage`. Because the hang occurs in `validate_unsigned`, it can stall transaction-pool processing network-wide, and if it occurs during block execution it can stall/brick block production for the chains using this consensus client — a "route unable to deliver messages" condition satisfying the validation criteria, achieved via a single relayed/dispatched message from an unprivileged party.

### Likelihood Explanation
High. The attacker needs only to submit an unsigned `ConsensusMessage` (permissionless, no fee required per the pallet's design) containing a `FinalityProof` with two crafted headers whose `parent_hash` fields cycle, and pass a couple of cheap hash-equality checks that require no valid signatures. No privileged role, valid authority key, or governance action is needed.

### Recommendation
- Add cycle/visited-set detection to `AncestryChain::ancestry()` (e.g., track visited hashes and bail out with an error if a hash is revisited), and/or bound the loop by the size of `self.ancestry` (at most `ancestry.len() + 1` iterations before erroring).
- Alternatively, verify the justification's signatures (`justification.verify`) before performing any ancestry walk over attacker-supplied headers, so unauthenticated header graphs are never traversed.
- Apply the same defensive check to any other analogous ancestry-walk helpers in the codebase that build a lookup map from unauthenticated proof data and then loop until a target is found.

### Proof of Concept
1. Craft two headers `H_A` and `H_B` (arbitrary `state_root`/`extrinsics_root`, valid SCALE encoding) such that `H_A.parent_hash() == H_B.hash()` and `H_B.parent_hash() == H_A.hash()`.
2. Set `finality_proof.unknown_headers = [H_A, H_B]`, `finality_proof.block = H_A.hash()` (the higher-numbered of the two, so it's picked as `target`).
3. Construct a `Commit` with `target_hash = H_A.hash()` and an empty/garbage `precommits` list (decoding only needs to succeed; no valid signatures required to reach the vulnerable call), SCALE-encode into `finality_proof.justification`.
4. Ensure `consensus_state.latest_height` is greater than `H_B`'s block number (attacker sets these numbers), so the `base.number() < consensus_state.latest_height` branch is taken and `headers.ancestry(base.hash(), consensus_state.latest_hash)` is invoked with `consensus_state.latest_hash` not equal to either `H_A.hash()` or `H_B.hash()`.
5. Submit this as a `Message::Consensus` in `pallet_ismp::handle_unsigned`. `AncestryChain::ancestry` will loop forever bouncing between `H_A` and `H_B`, hanging both `validate_unsigned` (transaction-pool validation) and, if it reaches inclusion, block execution.
