### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header values are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC validated by `Registry.process` binds solely to the body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never included in the signed content, yet `shop` is handed to the app's webhook handler as the tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [1](#0-0) 

The `shop` accessor reads straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards `request.shop` (from the unauthenticated header) to the app's handler as the tenant identity: [3](#0-2) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not per-tenant), any party who can obtain one genuinely-signed webhook body+HMAC pair (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body to the same webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `OpenSSL.secure_compare` in `HmacValidator` will still succeed because the signature only ever covered the body: [4](#0-3) 

This breaks the intended binding `HMAC-verified-bytes == (shop, body)`; in reality it only enforces `HMAC-verified-bytes == body`, while the handler-facing tenant field `shop` is taken from `header value` unconditionally.

### Impact Explanation
An app that uses `WebhookMetadata#shop` to route or persist webhook data per-tenant (the documented and expected usage shown in `docs/usage/webhooks.md`) can be made to attribute one shop's webhook data to a different shop chosen by the attacker, since the `shop` field is fully attacker-controlled and unauthenticated relative to the HMAC. This is a cross-tenant data-confusion vector reachable by any unprivileged party who can install the target app on a shop they control and capture one legitimate webhook delivery.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have installed the app themselves (readily available for public apps) and to capture at least one legitimate webhook body/HMAC pair for a topic the app subscribes to, then replay it with a forged `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required.

### Recommendation
Include the `shop-domain` header value (and ideally `topic`) in the signable string used for HMAC verification, or otherwise cryptographically bind the claimed shop to the signed body, so a valid signature for one shop cannot be replayed with a different shop identity.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` (both signed with the app's single shared `client_secret`).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data as if it originated from the victim shop.
