## Analog Found

### Title
Webhook shop-domain header not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The Truffle-migration report describes a dependency (the whitelist contract) whose validity was assumed but never actually checked end-to-end, letting the system move into an inconsistent state. The same class of bug exists in this gem's webhook handling: the HMAC signature that authenticates an inbound webhook only covers the raw request body, while the `shop` identifier that the handler uses to attribute the payload to a tenant is taken from an **unauthenticated** header. The binding the code implicitly assumes — "HMAC-valid body" ⇒ "HMAC-valid `(shop, body)` pair" — does not actually hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed material: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` as the tenant identity when dispatching to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` field — again, `shop` never enters this computation: [4](#0-3) 

Because the same `api_secret_key` is shared across every merchant that installs the app, a real, validly-signed `(raw_body, hmac)` pair obtained from **any one tenant's own webhook delivery** (e.g., an app developer's own test store, or any shop that installed the app) remains cryptographically valid no matter which `shop` header is attached to it. The identity binding the app needs — "this HMAC-verified body legitimately originated from shop X" — is never actually established; only "this body was HMAC-signed by *some* shop using this app" is established.

### Impact Explanation
This breaks the equality `authenticated_shop == shop_used_by_handler`. An app's webhook handler (`WebhookMetadata.new(topic:, shop: request.shop, body:, ...)`) will process attacker-supplied body content while believing it is scoped to an arbitrary victim shop of the attacker's choosing, since `shop` is copied verbatim from the unauthenticated header into the metadata passed to the handler: [5](#0-4) 

Depending on how a host application uses `WebhookMetadata#shop` (e.g., to look up which merchant record to update, which access token to use for reactive API calls, or to route the event through per-tenant business logic), this enables cross-tenant data confusion/corruption — an attacker-controlled event body gets attributed to and processed against a shop the attacker does not own.

### Likelihood Explanation
Exploitation requires only unprivileged capabilities:
1. Attacker installs the target app on their own (attacker-controlled) Shopify development store — a normal, unprivileged action.
2. Attacker triggers a webhook delivery to their own registered endpoint (or, if they run their own instance of the app for testing, captures the `raw_body` + `hmac-sha256` header Shopify sends).
3. Attacker POSTs that exact `raw_body` and `hmac-sha256` value to the target app's public webhook endpoint, substituting an arbitrary `shopify-shop-domain` header value.
4. `HmacValidator.validate` succeeds (it never looked at the shop header), and the handler is invoked with the attacker's chosen `shop`.

No possession of the app's `api_secret_key`, access token, or any victim-shop credential is required — only a legitimately-issued signature for *some* body, which any app installer can obtain for themselves.

### Recommendation
- **Short term:** Include the shop domain (and ideally topic) as part of the material verified against the webhook signature, or independently verify that the `shop` header corresponds to a shop actually known/authorized for this app installation before trusting `request.shop` in `WebhookMetadata`.
- **Long term:** Treat webhook `shop` attribution as security-sensitive: bind it cryptographically (e.g., derive it only from data covered by the HMAC, or cross-check it against the app's own installation/session store for that shop) rather than accepting it from a raw, unauthenticated header value.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app there.
# Step 1: Attacker captures a real, validly-signed webhook Shopify sent them:
raw_body = '{"id": 1, "note": "attacker controlled payload"}'
valid_hmac = "<hmac-sha256 header value Shopify actually sent for raw_body>"

# Step 2: Attacker replays it directly to the app's public webhook endpoint,
# swapping only the shop-domain header (never covered by the signature):
headers = {
  "shopify-topic"        => "orders/create",
  "shopify-hmac-sha256"  => valid_hmac,       # still valid: HMAC only covers raw_body
  "shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) passes (body-only check),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked with attacker-controlled body attributed to a shop the attacker doesn't own.
```
