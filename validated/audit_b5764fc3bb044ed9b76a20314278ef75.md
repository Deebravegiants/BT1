This confirms the vulnerability: `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) signs only `@raw_body`, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers (`lib/shopify_api/webhooks/request.rb:20-23`) and passed downstream to the handler by `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`).

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`. For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` (`x-shopify-shop-domain`), `topic`, and `webhook_id` values used by the dispatcher and passed to the merchant's handler are read directly from HTTP headers and are never included in the signed material [2](#0-1) .

### Finding Description
The identity binding that should hold is: `shop-domain header == shop bound by the HMAC signature`. In this gem it does not — the HMAC only proves "this body byte sequence was signed by Shopify with `api_secret_key`"; it says nothing about which shop or topic the signature was intended for.

`Registry.process` performs:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [3](#0-2) 

Because `request.shop`, `request.topic`, and `request.webhook_id` are plain header reads, not signed fields [2](#0-1) , any party who possesses one valid `(raw_body, hmac)` pair — which Shopify legitimately sends to *any* shop that installs the app, including a store an unprivileged attacker creates and controls themselves — can replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain. `HmacValidator.validate` will still return `true`, because it only recomputes the HMAC over `@raw_body` and compares it to the (unmodified, still-valid) signature [4](#0-3) . The handler then executes business logic attributing the replayed payload to the victim's `shop`, crossing the tenant boundary the header was supposed to enforce.

### Impact Explanation
This is a cross-tenant access issue: an attacker with only an unprivileged, legitimately-installed copy of the app (something any internet user can obtain by installing a public app on their own free development store) can inject webhook events that the merchant's application will process as if they originated from a different, victim shop. Depending on how the app's registered handlers use `WebhookMetadata#shop` (e.g., to look up/update per-tenant records, mark subscriptions, or trigger side effects keyed by shop), this can corrupt or leak another tenant's application state — satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop`/`#topic` for authorization or record lookup: the attacker only needs (1) their own legitimate install of the target app to receive a genuinely-signed body/HMAC pair, and (2) the ability to POST an HTTP request with custom headers to the app's public webhook endpoint — no access token, secret, or privileged account is required.

### Recommendation
Bind the identity fields to the signature instead of trusting bare headers: include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signed material used by `to_signable_string` for webhook `Request` objects, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` folds `shop` into its signable string [5](#0-4) . Short of changing the wire format, the gem should at least document/require callers to independently verify `request.shop` against a known, previously-authorized shop (e.g., an existing offline session) before invoking the handler, rather than presenting it as already-trusted `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (no special privilege required — any user can create a dev store and install a public app).
2. Shopify sends a legitimately-signed webhook to the app's endpoint: headers include `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, with some `raw_body`.
3. Attacker captures this exact `(raw_body, x-shopify-hmac-sha256)` pair and replays it to the same endpoint, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com` (topic/webhook-id can also be altered).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds [6](#0-5) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker's own order data>, ...)` [7](#0-6) , causing the app to process attacker-supplied data under the victim's tenant identity.
