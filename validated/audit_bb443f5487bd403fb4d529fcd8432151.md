## Title
Webhook shop/topic identity confusion via unauthenticated headers not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds a webhook's tenant identity (`shop`), dispatch key (`topic`), API version, and webhook id to raw, attacker-controllable HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies covers only the raw request body. An unprivileged attacker who can obtain one validly-signed webhook body (e.g., by installing the app on their own free/dev store and capturing a webhook Shopify sends them) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` (and/or `topic`) header for a victim shop, and the library will accept it as authentic for that victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers that are never part of the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` verifies the HMAC over the body only, then dispatches using the unauthenticated `request.shop`/`request.topic` values with no further cross-check that they match the shop/topic that was actually signed: [4](#0-3) 

`HmacValidator.validate` confirms only that `to_signable_string` (the raw body) was signed with the app's shared `api_secret_key` — a secret that is identical across *all* shops that installed the app, not shop-specific: [5](#0-4) 

Because the secret is shared across tenants and the shop/topic headers are excluded from the signable content, the binding "shop the HMAC was computed for" == "shop the library reports to the handler" does not hold. Any unprivileged user who installs the app on their own shop can capture a legitimately-signed webhook body and replay it with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header pointing at a different, victim shop. The signature check in `HmacValidator.validate` still passes (it only re-hashes the untouched body), so `Registry.process` calls the registered handler with `WebhookMetadata` claiming the victim's shop while the body content is entirely attacker-controlled.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC check is supposed to provide: `shop_authenticated_by_hmac == shop_used_for_tenant_dispatch` is false. A malicious app-installer can inject attacker-chosen webhook payloads (e.g. fake `orders/create`, `customers/data_request`, `shop/redact`) attributed to any other shop that uses the same app, causing cross-tenant data corruption/processing in the host application's webhook handlers. This qualifies as Critical — cross-tenant access — since the "identity" of the incoming event is fully attacker-controlled while riding on a signature that was never meant to authenticate it.

### Likelihood Explanation
Likelihood is high for any app that is publicly installable (the normal SaaS/embedded-app model Shopify apps target): obtaining one valid signed webhook only requires installing the app on a shop the attacker controls (no privileged credentials, no secrets, no social engineering needed), then replaying the captured body to the same public webhook endpoint with a modified header.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the signature), and have `Registry.process` reject requests where these values are not verifiably tied to the same signed payload, instead of trusting raw headers independently of the signature check.

### Proof of Concept
1. Attacker creates a free/dev Shopify store and installs the vulnerable app; Shopify sends a legitimately-signed webhook to the app's public callback URL with headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and some JSON body.
2. Attacker captures the exact raw body and `X-Shopify-Hmac-Sha256` value.
3. Attacker crafts a new POST to the same webhook endpoint using the identical body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Request#hmac`/`#to_signable_string` only look at the body, so `Utils::HmacValidator.validate` returns `true`; `Registry.process` calls the topic handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker body>, ...)`, causing the host app to process attacker-controlled data as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
