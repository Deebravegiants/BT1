### Title
Webhook `shop` and `topic` fields are trusted without HMAC binding, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
This is the same bug class as the Astaria finding: a field that is *acted on* by the application is not covered by the cryptographic check that is supposed to authenticate the request. In `VaultImplementation._validateCommitment()` the strategy's `deadline` field was used without being part of the verified data path. Here, `ShopifyAPI::Webhooks::Request#shop` and `#topic` are used by `Registry.process` to select the handler and to attribute the event to a merchant, but neither field is included in the HMAC that authenticates the webhook.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers: [2](#0-1) 

`HmacValidator.validate` only ever hashes `to_signable_string` (the body), never the headers: [3](#0-2) 

`Registry.process` validates the HMAC, then dispatches on `request.topic` and forwards `request.shop` into the handler's `WebhookMetadata`, trusting both values as if they had been authenticated: [4](#0-3) 

The equality that should hold but doesn't:
`shop/topic verified by HMAC == shop/topic acted on by Registry.process`
In reality, only `raw_body` is bound to the HMAC; `shop` and `topic` are unauthenticated attacker-controllable headers.

The gem's own documentation states the opposite guarantee — that calling `Registry.process` "will verify the request did indeed come from Shopify" as a whole, not just the body bytes: [5](#0-4) 

Because `Context.api_secret_key` (the app's `client_secret`) is the same for every shop that installs the app, any unprivileged merchant/attacker who installs the app can trigger a real webhook delivery to obtain a legitimately-signed `(raw_body, hmac)` pair for their own store, then replay that exact byte-identical body+HMAC to the app's public webhook endpoint while freely rewriting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers, since those are never checked against the signature.

### Impact Explanation
This breaks the tenant isolation boundary between merchants sharing the same app: an attacker-controlled shop can forge webhook events that the app attributes to a *different* shop, or replay a payload under a different topic (e.g. relabeling an ordinary webhook as `shop/redact` or `customers/data_request`, which are mandatory GDPR topics per `Registry::MANDATORY_TOPICS`). Any handler logic keyed on `data.shop` or `data.topic` (exactly the pattern shown in the gem's own docs, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into performing actions against, or attributing data to, a shop that never sent that event — a cross-tenant access/impersonation issue.

### Likelihood Explanation
Exploitation requires no access token, no `api_secret_key`, and no privileged account — only the ability to install the target app on any Shopify store (a normal, unprivileged action any internet user can perform for a public app) and to send a raw HTTP POST with attacker-controlled headers to the app's public webhook route. No TLS interception or credential leakage is needed.

### Recommendation
Include the authenticated identity fields (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., verify `shop` against the session/shop that installed the app before trusting it), rather than relying solely on a body-only signature check for values that are read from unauthenticated headers. At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop domain and topic, and update `Registry.process` to fail closed on mismatch.

### Proof of Concept
1. Attacker installs the target app on their own dev/free store (`attacker-shop.myshopify.com`) and triggers any subscribed webhook (e.g. `orders/create`), capturing the exact `raw_body` and the `x-shopify-hmac-sha256` header Shopify sent — a validly-signed pair under the app's shared `client_secret`.
2. Attacker POSTs that identical `raw_body` (and the captured HMAC) to the app's public webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: shop/redact` (or any other topic string)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds because it only hashes `raw_body` (unchanged), and `Registry.process` invokes the registered handler for the spoofed topic with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "shop/redact", body: <attacker's own store's body>)`.
4. The app's handler acts on this forged, cross-tenant event as though Shopify itself sent it for `victim-shop.myshopify.com`.
