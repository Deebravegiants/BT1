### Title
Webhook `shop` (and `topic`/`api_version`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers and handed to the app's webhook handler unchanged. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches, then trusts these header-derived fields to identify which merchant/tenant the payload belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all sourced purely from HTTP headers, which are never fed into the HMAC computation: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — which in turn calls `verifiable_query.to_signable_string` (the raw body) against the secret — and then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` confirms the comparison is solely against `verifiable_query.to_signable_string`: [4](#0-3) 

This is the exact "field acted on but not covered by the HMAC" identity-binding break: the equality the code implicitly assumes is `hmac_verified(raw_body) == hmac_verified(raw_body, shop, topic, webhook_id)`, but only the left side is actually true. A merchant who legitimately receives real webhooks for their own shop (an unprivileged, non-credentialed party with respect to *other* merchants' data) can capture a raw body + valid HMAC pair from their own webhook deliveries, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with another shop's domain. `HmacValidator.validate` still returns `true` (it only checked the body), and `Registry.process` dispatches the handler with `shop: <attacker-chosen-domain>`, `topic`, and `webhook_id` all attacker-controlled and unauthenticated.

### Impact Explanation
Any app built on this gem that uses `data.shop` from the webhook handler to key its per-tenant lookups (session retrieval, database records, job dispatch) can be made to process/attribute a valid Shopify-originated payload to a different shop than the one that actually sent it. This crosses the tenant boundary: an attacker (holder of one legitimate, low-privilege merchant account) can inject or misattribute webhook-derived data belonging to their own store into another merchant's data pipeline, or cause the target shop's webhook processing pipeline to run using a topic/id of the attacker's choosing. This matches the High-severity "cross-tenant access" impact class, since the identity binding between the authenticated payload and the claimed shop is broken entirely within this gem's own webhook verification logic — not by the host application ignoring documented behavior.

### Likelihood Explanation
Exploitation requires only: (1) an attacker with any legitimate Shopify store (i.e., anyone), which can be used to generate real, validly-signed webhook deliveries; and (2) the ability to replay HTTP requests to the app's public webhook endpoint with modified headers, which is standard HTTP tooling. No access to `api_secret_key`, access tokens, or the app's `client_secret` is required, since the header fields are never part of the cryptographic check.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-verified signable content, or independently authenticate the shop domain against the session/shop store before dispatching to the handler — do not trust header-derived tenant-identifying fields that lie outside the HMAC's coverage.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared secret), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the same request to the app's webhook endpoint, keeping body `B` and `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B` only) — validation passes, as shown in [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)`, as shown in [6](#0-5) , causing the app to process attacker-controlled/attacker-originated data under the victim shop's identity.
