## Title
Webhook `shop-domain` header trusted for tenant routing despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while `ShopifyAPI::Webhooks::Registry.process` uses the unauthenticated `shop-domain` header to determine which shop the webhook payload belongs to before dispatching it to the host application's handler. This breaks the equality that should hold: `shop authenticated by HMAC == shop delivered to the handler as the tenant identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  The `shop` accessor is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is not part of the signed material: [2](#0-1) 

`HmacValidator.validate` only calls `verifiable_query.to_signable_string`, so it never verifies the `shop` (or `topic`, `api-version`, `webhook-id`) headers: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`) verbatim to build the `WebhookMetadata` passed to the host app's handler: [4](#0-3) 

Because the HMAC binds only the body bytes to the secret, and not the shop identity, any request bearing a `(body, hmac)` pair that is valid for the app's `api_secret_key` — for instance a genuine webhook the attacker legitimately receives for their own store — remains HMAC-valid after the attacker swaps the `shop-domain` header to a victim shop's domain. `Registry.process` will accept it and hand the host application a `WebhookMetadata` object claiming the (attacker-controlled) body originated from the victim shop, since the shop field is never covered by the signature it just validated.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: the identity binding "the shop bytes verified equal the shop bytes acted on" fails. A host application built on this gem's webhook API — following its documented `Registry.process` contract — would attribute forged/replayed webhook content to a shop chosen by the attacker rather than the shop it actually verified, even though the HMAC check reports success. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the shop's session/store data and acting on the payload), this can lead to cross-tenant data injection or state corruption attributed to a shop the attacker does not own.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimate `(raw_body, hmac)` pair signed with the app's `api_secret_key` — obtainable by installing the app on an attacker-controlled shop and capturing/replaying one of its own real webhook deliveries with a substituted `shop-domain` header. No knowledge of `api_secret_key` itself is required, only a shop-domain header, which is trivially forgeable by any caller since it is not part of the signed payload.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header values in the HMAC-signable string in `Request#to_signable_string`, or otherwise cryptographically bind the shop identity to the signature so `HmacValidator.validate` fails if the shop header is altered independently of the body.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com` and capture a real webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, letting the attacker deliver content of their choosing (constrained to whatever `B` the attacker could obtain) under the victim's shop identity.
