Found it: `LPLock.recordLock` reverts with `ZeroAmount` if `amount == 0`, and `finalizeGraduation` calls it unconditionally with no zero-guard — an attacker can permanently freeze a token's graduation by driving `liquidity == 0`.

### Title
Permissionless zero-liquidity griefing bricks `finalizeGraduation` via `LPLock.recordLock`'s `ZeroAmount` guard - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.finalizeGraduation` unconditionally calls `LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity)` after seeding the HyperSwap V2 pool [1](#0-0) . `LPLock.recordLock` reverts with `ZeroAmount` whenever `amount == 0` [2](#0-1) . The `liquidity` value comes straight from `_seedUniswapV2Direct` → `_routerDepositAndDispose`, whose deposit leg is explicitly documented as capable of skipping `addLiquidity` entirely (and therefore returning `liquidity = 0`) under an "extreme hostile pre-seed" that drains one side of the swap budget to zero, per the natspec on `_swapBudget` [3](#0-2) . Once `_prepareGraduationLiquidity` has already run (Phase 1: curve drained, `Lifecycle.Graduating`, trading frozen, `pendingGraduation[token]` cached), any transaction path in Phase 2 that yields `liquidity == 0` causes `finalizeGraduation` to revert deterministically forever — the token is permanently stuck in `Lifecycle.Graduating` with `LPLock.recordLock`'s one-shot `lockedAt` sentinel never set, and no owner override or retry path exists because the trigger condition (attacker-controlled pre-seed ratio) is reproducible on every retry.

### Finding Description
This is the same bug class as CVE-2025-8183: an externally-reachable, attacker-shaped input (there, a non-singleton destination EID; here, an attacker-chosen HyperSwap V2 pre-seed ratio/size) reaches a code path that assumes a non-degenerate value and reverts/dereferences instead of handling the edge case, causing a reliable, remote, unprivileged DoS.

The attack surface is exactly the one the codebase's own AGENTS.md calls out as load-bearing: "Phase 2 must never revert under any pre-seed shape" and "Brick resistance: the rebalance swap input is capped at our per-side budget... So a hostile pre-seed of any shape cannot DoS `finalizeGraduation`" [4](#0-3) . However, this guarantee is about `pair.swap` / `addLiquidity` not reverting — it says nothing about the *value* of `liquidity` that flows out of that leg. `_routerDepositAndDispose`'s underlying budgeting logic explicitly acknowledges a scenario where the rebalance swap consumes 100% of one side's inventory, leaving nothing for the deposit leg, and calls this out by name as the failure mode the `_swapBudget` 99% cap is defending against — but only for the *empty-mint* regime, not for the case where the deposit leg itself still lands on `liquidity = 0` through other rounding/degenerate paths (e.g., `remToken == 0` or `remLT == 0` after the router's `quote()`-based split, described directly in the same comment) [5](#0-4) .

Regardless of whether `_swapBudget`'s 99% reservation is sufficient to fully close every degenerate case, the structural problem is that `finalizeGraduation` has zero defense-in-depth against a zero-liquidity outcome: it passes whatever `_seedUniswapV2Direct` returns straight into `LPLock.recordLock`, which unconditionally reverts on `amount == 0` [6](#0-5) . There is no fallback mint, no minimum-liquidity floor, and no way to re-attempt with different parameters — Phase 1's cached `(tokensForLP, ltFromPair)` are pinned and immutable, and the pre-seed on the HyperSwap pair (permissionlessly creatable and fundable by anyone before `finalizeGraduation` runs, as documented in the "HyperSwap Pre-Seed Defense" section) is fully attacker-controlled [7](#0-6) . Any input shape that survives the brick-resistance swap/mint logic without reverting but produces `liquidity == 0` permanently bricks the token: `Lifecycle.Graduating` can never advance to `Graduated`, curve trading stays frozen (buy/sell both reject non-`Curve` lifecycle), and every subsequent `finalizeGraduation(tokenAddress)` call by the keeper or any rescuer reverts identically with `LPLock.ZeroAmount`.

### Impact Explanation
This is a permanent freezing-of-funds / permanent DoS on a specific token's graduation, matching the "Accept only concrete theft or permanent freezing" bar. All curve-raised LT already drained into `Bonding` via `Router.graduate` in Phase 1, the 250M `LP_RESERVE` tokens burned/allocated in Phase 1, and every holder's ability to trade or exit through the post-graduation HyperSwap pool are all frozen indefinitely — the token can never reach `Lifecycle.Graduated`, and curve trading is already frozen by Phase 1, so holders have no exit path at all. This is a High-severity, permissionless, single-transaction DoS reachable by any unrelated wallet pre-seeding the pair before the keeper's `finalizeGraduation` call, directly analogous to the reliable remote DoS in CVE-2025-8183.

### Likelihood Explanation
Likelihood is bounded by how tightly `_swapBudget`'s 99%-reservation and the router's `quote()`-based optimal split actually prevent every degenerate `liquidity == 0` outcome — the natspec itself frames the 99% cap as closing one specific over-consumption scenario, implying awareness that the deposit leg's output was not unconditionally guaranteed non-zero without it. Given HyperEVM's uint112 reserve space and attacker-chosen pre-seed ratios/amounts (a pair is permissionlessly creatable and fundable ahead of Phase 2, as the codebase's own threat model documents at length), an attacker with a modest budget controls both the timing (front-run before the keeper's ~60s finalize) and the shape of the pre-seed. Precisely pinning the boundary condition that defeats the 99% cap requires exercising `_routerDepositAndDispose`'s exact rounding behavior against the router's `quote()` math, which is not fully observable from the indexed contract snippets — this uncertainty should be resolved with targeted fuzzing/PoC work on `_routerDepositAndDispose` and the removed `HostilePreSeed.t.sol` scenarios (the repo's own AGENTS.md notes this dedicated integration suite was removed for runtime reasons and its properties are "no longer enforced by automated tests") [8](#0-7) .

### Recommendation
Add an explicit floor in `finalizeGraduation` (or inside `_seedUniswapV2Direct`) that treats `liquidity == 0` as a recoverable condition rather than letting it propagate into `LPLock.recordLock`'s hard revert — e.g., fall back to `_seedDirectMint` (which is already proven brick-resistant, see the "Regime 1" documentation) whenever the rebalancing path would otherwise yield zero LP tokens, or explicitly clamp/guarantee a non-zero deposit before calling `recordLock`. Extend `test/TwoPhaseGraduation.t.sol` / restore a `HostilePreSeed.t.sol`-style regression that specifically fuzzes pre-seed ratios/amounts to hunt for any `liquidity == 0` outcome from `_routerDepositAndDispose`.

### Proof of Concept
Conceptual PoC (exact numeric boundary requires fuzzing `_routerDepositAndDispose` / `_noFeeSwapInput` against the router's `quote()` split, which was not directly observable in the indexed snippets):
1. Launch a token via `Bonding.launch` / `Zap.createToken`; let it accrue enough curve activity to arm `canGraduate` (USD or supply trigger).
2. Before the keeper's `finalizeGraduation` lands, front-run: call `HyperSwapV2Factory.createPair(token, lt)`, then `transfer` a carefully sized (TOKEN, LT) pair to the pool and `pair.mint(attacker)` to establish a pre-existing reserve ratio engineered so that after `_pairRebalance`'s swap consumes up to `_swapBudget` (99%) of the rebalance-in side, the remaining on-ratio deposit amount that `_routerDepositAndDispose`'s `router.addLiquidity(..., min0=1, min1=1, ...)` would pull rounds to zero on one side (`remToken == 0` or `remLT == 0`).
3. Trigger/await Phase 1 (`_enterGraduating`) to fire, pinning `(tokensForLP, ltFromPair)`.
4. Call `Bonding.finalizeGraduation(tokenAddress)` (permissionless) — `_seedUniswapV2Direct` returns `liquidity = 0`, and the subsequent `LPLock.recordLock(tokenAddress, lpPair, 0)` reverts with `LPLock.ZeroAmount`.
5. Every future call to `finalizeGraduation(tokenAddress)` reverts identically (Phase 1 state is immutable/cached), permanently stranding the token in `Lifecycle.Graduating`.

```text
    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
```

```text
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
```
