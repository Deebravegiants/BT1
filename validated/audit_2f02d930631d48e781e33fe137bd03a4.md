### Title
Webhook shop-domain, topic, api-version, and webhook-id headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `api_version`, and `webhook_id` values pulled from HTTP headers to build the `WebhookMetadata` passed to the host app's handler. None of these header values are included in the HMAC-signed content, so they are not bound to the authentication check at all.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature over `verifiable_query.to_signable_string` using the app's shared `Context.api_secret_key`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw request body — never the shop domain, topic, webhook id, or API version: [2](#0-1) 

`Registry.process` then raises only if this body-only HMAC fails, and otherwise dispatches the handler using `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — all read directly and unauthenticated from HTTP headers: [3](#0-2) 

Critically, `Context.api_secret_key` is the **app's** client secret, shared across every merchant shop that has installed the app — it is not shop-specific. This means the HMAC only proves "this body was signed with this app's secret"; it proves nothing about *which* shop the body/headers claim to originate from.

The security-relevant identity binding that should hold is:
`hmac-signed content == (shop, topic, webhook_id, api_version, body)`

but the actual binding implemented is:
`hmac-signed content == (body only)`

This is exactly the "field acted on but not covered by the HMAC" class described in the report: the `shop` (tenant identity) field is acted on (passed to the host app's handler as the authoritative merchant identity for the event) but is never verified as part of the authenticated payload.

### Impact Explanation
Any actor who can obtain one legitimately-HMAC-valid webhook body for the app (e.g., a merchant who installs the app themselves and triggers an event on their own store, thus receiving a body+HMAC pair signed with the shared app secret) can replay that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `topic`/`webhook-id`/`api-version`) header. `HmacValidator.validate` will still pass because it only checks the body against the shared secret. The host application's handler — which trusts `WebhookMetadata#shop` as the tenant identifier to look up/update records — will then process the event as if it belongs to a different, victim shop, corrupting or leaking data across tenants. This satisfies the "cross-tenant access" critical-impact category, since the attacker (an unprivileged, self-service merchant/internet user with no special credentials for the victim shop) can cause the app to attribute forged webhook data to another tenant.

### Likelihood Explanation
Likelihood is realistic but requires the attacker to first obtain a validly-signed body/HMAC pair, which is straightforward for any actor who can install the app on their own shop (a normal unprivileged flow) and trigger a webhook of their choosing, then replay it with modified headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is required — only the ability to install the app as a normal merchant and observe/replay its own outbound webhook traffic.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material for webhooks, or otherwise cryptographically bind the header-derived shop to the verified body (e.g., require the host app framework to cross-check `request.shop` against a previously known/authorized shop record before trusting it as the tenant key). At minimum, document prominently that `Webhooks::Request#shop`/`#topic`/`#webhook_id`/`#api_version` are **not** covered by the HMAC and must not be trusted as tenant-authenticated values by downstream handlers without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":123}` with header `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over that body with the app's shared secret.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds, because `to_signable_string` only checks the (unchanged) body against the shared app secret: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/stores the attacker-controlled body as if it were genuine data belonging to `victim-shop.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
