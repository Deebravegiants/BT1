### Title
POA bridge status/txHash misreport on batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves a withdrawal's status/txHash by matching only on `assetId` via `findMatchingWithdrawal`, ignoring `WithdrawalIdentifier.index`. When a single MultiPayload contains two POA-routed withdrawals for the same `assetId` (e.g. two `nep141:btc.omft.near` withdrawals to different destinations), both `watchWithdrawal` calls can resolve to the same array element, causing one destination's `transfer_tx_hash` to be reported for both withdrawal indices.

### Finding Description
The equality that should hold is: `describeWithdrawal(wid_i).txHash == outcome.transfer_tx_hash of the withdrawal actually addressed to withdrawalParams[i].destinationAddress`. This breaks because `findMatchingWithdrawal` in [1](#0-0)  selects the first array element whose `near_token_id` matches the requested `assetId`, with no use of `args.index` or `args.withdrawalParams.destinationAddress` to disambiguate. `describeWithdrawal` at [2](#0-1)  calls this matcher and directly returns `withdrawal.data.transfer_tx_hash` as the completed status. `createWithdrawalIdentifiers` in [3](#0-2)  assigns sequential `index` values per bridge route but this index is never consulted by `PoaBridge.describeWithdrawal`. This is a documented, acknowledged limitation in the code itself (comment at lines 409-416: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported"), and the same limitation exists in the analogous helper `waitForWithdrawalCompletion.ts` ( [4](#0-3) ). I found no batch-level validation in `sdk.ts`, `withdrawal-watcher.ts`, or `PoaBridge.validateWithdrawal`/`supports()` that rejects or deduplicates multiple withdrawals sharing the same `assetId` within a POA-routed batch — nothing blocks the attacker's input from reaching this code path.

### Impact Explanation
An integrator relying on per-index `watchWithdrawal`/`describeWithdrawal` results to credit or refund users will attribute the same destination `transfer_tx_hash` to two distinct withdrawals, double-crediting one destination's outcome and never learning the true outcome of the other withdrawal. This matches the "status or hash misreport making an integrator credit or refund twice" High severity category. It is repeatable on any POA-routed batch with duplicate `assetId` entries.

### Likelihood Explanation
Preconditions: POA bridge route, `feeInclusive=false`, a batch of ≥2 `withdrawalParams` sharing the same `assetId`, and the POA relay's `getWithdrawalStatus` response containing the corresponding entries (in any order, since `find` returns unsorted results). No special privileges are needed — an ordinary user can construct and sign such a batch through documented batch-withdrawal APIs (`processWithdrawal`/`signAndSendWithdrawalIntent` with a `WithdrawalParams[]`), and nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers` prevents duplicate `assetId` entries in a POA batch.

### Recommendation
Disambiguate withdrawals within `findMatchingWithdrawal` beyond `assetId` alone — e.g., match by `assetId` + `destinationAddress` (+ `amount` where available), or, if the POA API does not expose enough fields to uniquely correlate entries, explicitly reject/throw when more than one candidate matches the same `assetId` in a batch rather than silently returning the first match, and reject creation of POA-routed batches with duplicate `assetId` entries until the underlying POA API supports per-index correlation.

```ts
// vitest, mocking only poaBridge.httpClient.getWithdrawalStatus
it("misreports txHash for duplicate-assetId POA batch withdrawals", async () => {
  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "TX_A", chain: "btc" } },
      { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "TX_B", chain: "btc" } },
    ],
  });

  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });
  const baseParams = { assetId: "nep141:btc.omft.near", amount: 1n, feeInclusive: false };
  const wid0 = bridge.createWithdrawalIdentifier({
    withdrawalParams: { ...baseParams, destinationAddress: "addrA" },
    index: 0, tx: { hash: "h", accountId: "a" },
  });
  const wid1 = bridge.createWithdrawalIdentifier({
    withdrawalParams: { ...baseParams, destinationAddress: "addrB" },
    index: 1, tx: { hash: "h", accountId: "a" },
  });

  const status0 = await bridge.describeWithdrawal(wid0);
  const status1 = await bridge.describeWithdrawal(wid1);

  // BROKEN EQUALITY: both indices report the same txHash despite distinct destinations
  expect(status0).toEqual({ status: "completed", txHash: "TX_A" });
  expect(status1).toEqual({ status: "completed", txHash: "TX_A" }); // should be TX_B, proving misreport
});
```

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

```typescript
export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
```

```typescript
/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
```
