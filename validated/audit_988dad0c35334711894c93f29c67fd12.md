### Title
Lost-update race between `untrust` and `connect`/`setAutoApprove` can resurrect a revoked origin's privileges - ([File: features/connected-origins/module/connections.js])

### Finding Description
`untrust` performs a classic non-atomic check-then-act sequence: it calls `isTrusted({ origin })` (which internally does `#getOrigin` → `#getData` → `connectedOriginsAtom.get()`), then separately re-reads `#getData()`, filters out the origin, and finally writes the result with `#setData(newData)` (`connectedOriginsAtom.set(...)`) [1](#0-0) .

Every other origin-mutating method (`connect`, `disconnect`, `setAutoApprove`, `setFavorite`, `updateConnection`, `add`) goes through the same read-then-write pattern via `#setAttributes`, which itself does an existence check with `#getOrigin`, a fresh `#getData()` read, and then a separate `#setData(newData)` write built from that earlier snapshot [2](#0-1) . `connect` in particular first reads the origin, computes an updated `activeConnections` array from that stale read, and only then calls `#setAttributes` [3](#0-2) .

The underlying `connectedOriginsAtom` (`createStorageAtomFactory`) serializes `.get()` calls among themselves and `.set()` calls among themselves via separate `makeConcurrent(..., { concurrency: 1 })` queues in `enforceObservableRules`, and a `.get()` will always await any `pendingWrite` in flight, so it never returns data from a half-completed write [4](#0-3) [5](#0-4) . However, this only guarantees atomicity of a *single* `get`/`set` call — it does not make the *compound* multi-step sequences in `untrust`/`connect`/`#setAttributes` atomic with respect to each other. There is no optimistic-concurrency check (e.g. re-validating the record hasn't changed, or a version/CAS token) between the moment `connect`/`setAutoApprove` reads the origin record and the moment it commits its own `#setData` write.

Exploit flow: if `connect` (or `setAutoApprove`) reads the still-trusted origin record and builds its updated record (with `activeConnections`/`autoApprove` set) *before* `untrust`'s deletion write is queued, but `connect`'s own `connectedOriginsAtom.set(...)` call happens to be queued *after* `untrust`'s `set(...)` call, then `untrust`'s deletion executes first and `connect`'s write executes second, re-inserting the (now supposedly revoked) origin record — including the granted `activeConnections`/`autoApprove` attributes — back into storage. Because the write in `#setAttributes` builds `newData` from a `data.map()` over a stale snapshot that still contains the origin object, it fully resurrects the record rather than merely reapplying a partial patch.

### Impact Explanation
A revoked (untrusted) origin can regain live wallet privileges (an active connection and/or `autoApprove`) despite the user believing it had been disconnected/untrusted, because consent revocation (`untrust`) is not enforced atomically against concurrent origin-state mutations. This is a privilege-persistence-after-revocation issue: the origin can continue to be treated as connected/auto-approved, letting it request account/address exposure or auto-approved actions it should no longer have.

### Likelihood Explanation
Exploitation requires precise interleaving of two async call chains sharing the same atom (`untrust` racing `connect`/`setAutoApprove` on the same origin), which is plausible in a single-threaded JS event loop only under specific microtask/storage-I/O timing (e.g., a dApp firing rapid reconnect/RPC requests around the time the user clicks "disconnect/untrust" in the UI). No cryptographic or authentication bypass is needed — it purely depends on scheduling order of already-permitted operations, and the caller (attacker) does not need special privileges. This is a real but timing-dependent race, not a deterministic one; likelihood is moderate.

### Recommendation
Make the check-then-act sequences atomic:
- Introduce an optimistic-concurrency guard: have `#setAttributes`/`untrust` re-derive `newData` from the freshest `#getData()` read taken immediately before the final `#setData` write (single read, not two separate reads at different times), and/or use a version stamp on the record to detect concurrent modification and retry/abort instead of blindly overwriting.
- Alternatively, serialize all `ConnectedOrigins` mutation entry points (`untrust`, `connect`, `disconnect`, `setAutoApprove`, `setFavorite`, `updateConnection`, `add`) behind a single `makeConcurrent({ concurrency: 1 })` queue at the module level so only one compound read-modify-write can execute at a time for the whole origins list.
- After any write in `#setAttributes`, re-validate that the origin is still expected to exist/be trusted before applying attribute changes that grant privileges (`activeConnections`, `autoApprove`).

### Proof of Concept
Unit/integration test plan (Jest) using the real module with the actual `connectedOriginsAtom`/storage-atom stack (not a bare mock) to preserve the queueing semantics described above:

1. Seed storage with a trusted origin: `await connectedOriginsAtom.set([{ origin: 'evil.com', trusted: true, activeConnections: [] }])`.
2. Instrument/delay the storage backend's `get`/`set` (similar to the existing `delay(1)` pattern used in `libraries/atoms/__tests__/index.test.ts`) so that `connect`'s internal reads resolve before `untrust`'s write is queued, but `connect`'s final `#setData` write is queued after `untrust`'s write.
3. Fire concurrently: `const untrustPromise = connectedOrigins.untrust({ origin: 'evil.com' }); const connectPromise = connectedOrigins.connect({ id: 'conn-1', origin: 'evil.com' }); await Promise.all([untrustPromise, connectPromise])`.
4. Assert the invariant: `const final = await connectedOriginsAtom.get(); expect(final.find(o => o.origin === 'evil.com')).toBeUndefined()` — i.e., once `untrust` has been invoked, no concurrent `connect`/`setAutoApprove` call should be able to leave the origin record (with granted `activeConnections`/`autoApprove`) present afterward.
5. Repeat with `setAutoApprove({ origin: 'evil.com', value: true })` racing `untrust` to confirm the same invariant holds for the `autoApprove` flag.
