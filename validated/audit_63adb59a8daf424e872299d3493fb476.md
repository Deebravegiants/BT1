### Title
Webhook `shop` field is not covered by HMAC signature verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC signature that is computed **only over the raw request body**, yet the `shop` identity attribute (and `topic`/`webhook_id`/`api_version`) used to route and attribute the webhook to a tenant is taken from an **HTTP header that is not part of the signed payload**. This breaks the intended binding `shop authenticated by HMAC == shop used as the tenant identifier passed to the handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `raw_body`) and, if valid, immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by that signature — and forwards them to the app's handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, confirming the `shop` header plays no role in the signature check: [4](#0-3) 

Because the HMAC secret is the app's own `client_secret` shared across all shops that install the app, **any unprivileged user can obtain a validly-signed webhook body** simply by installing the app on their own (e.g., free/trial) store and letting Shopify deliver a real webhook to their endpoint. The attacker then replays that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint, but substitutes the `shop-domain` header with a victim shop's domain. The HMAC check still passes (it only checks the body), but `WebhookMetadata.shop` now equals the attacker-chosen victim domain instead of the shop that actually generated the payload: [5](#0-4) 

This is the equality violation: `shop verified by HMAC (∅, not covered)` ≠ `shop trusted as tenant key (request.shop header, attacker-controlled)`.

### Impact Explanation
Applications built on this gem use `WebhookMetadata.shop` to determine which tenant's data a webhook affects (e.g., updating that shop's cached data, triggering shop-scoped side effects, or deciding storage/routing). Since the header is unauthenticated relative to the signature, an attacker with any legitimate app install can forge webhook events that appear to originate from a different, victim shop while smuggling attacker-controlled body content, or associate legitimate victim body content with attacker desired topic/shop metadata combinations. This is a cross-tenant data integrity/confusion issue meeting the "cross-tenant access" Critical bar, since the identity boundary between shops is not enforced by the security mechanism (HMAC) that is supposed to authenticate the webhook.

### Likelihood Explanation
Likelihood is high for any app that (a) allows public/self-serve installation (common for Shopify apps) and (b) uses the `shop` field from `WebhookMetadata` to scope data operations without independently re-validating it against another authenticated source (e.g., an existing session/access token for that shop). No secrets need to be obtained — the attacker only needs their own legitimate install to acquire one validly-signed body/HMAC pair, then can freely vary the `shop-domain` header on repeated requests to the public webhook endpoint.

### Recommendation
Include the identity-relevant fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or independently verify `request.shop` against a value that is cryptographically bound to the request (Shopify does not currently sign headers, so the safer mitigation is for `Registry.process` / documentation to require callers to cross-check `request.shop` against the shop associated with the specific webhook subscription id, or to only trust `shop` in combination with the app's own stored, authenticated session/shop registry — not from an unauthenticated header). At minimum, the docs/consumers of this gem must be warned that `WebhookMetadata.shop`/`topic`/`webhook_id` are not covered by the HMAC and must not be trusted as the sole tenant identifier for security-sensitive operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (self-serve, unprivileged).
2. Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures this full HTTP request.
4. Attacker resends the same request to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (body `B` and `H` unchanged).
5. `HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and compares it to `H` — it still matches because the signature never included the shop header: [6](#0-5) 
6. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the app to process attacker-controlled data as if it belongs to the victim shop.
