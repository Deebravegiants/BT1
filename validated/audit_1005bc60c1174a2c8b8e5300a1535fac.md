## Finding

### Title
Permissionless `coin::migrate_coin_store_to_fungible_store` can silently unfreeze a victim's primary fungible store - ([File: aptos-move/framework/aptos-framework/sources/coin.move])

### Summary
`coin::migrate_coin_store_to_fungible_store` is a fully permissionless `public entry fun` that takes an arbitrary list of addresses (no signer) and migrates each account's legacy `CoinStore<CoinType>` into its `PrimaryFungibleStore`. Internally it calls `maybe_convert_to_fungible_store`, which blindly overwrites the target `FungibleStore`'s frozen flag with the stale `CoinStore.frozen` value whenever the two differ. Because the Fungible Asset (FA) side can be frozen directly and independently through the paired `TransferRef` (obtainable from a `FreezeCapability<CoinType>` via `coin::get_paired_transfer_ref`), an unprivileged caller can trigger this migration to flip a store that was deliberately frozen at the FA layer back to unfrozen, restoring transfer ability without any authorization check.

### Finding Description
`maybe_convert_to_fungible_store` deposits the remaining coin balance into the primary fungible store and then reconciles freeze state purely by equality comparison: [1](#0-0) 

```
fun maybe_convert_to_fungible_store<CoinType>(
    account: address
) acquires CoinStore, CoinConversionMap, CoinInfo {
    if (exists<CoinStore<CoinType>>(account)) {
        let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
            move_from<CoinStore<CoinType>>(account);
        ...
        // Note:
        // It is possible the primary fungible store may already exist before this function call.
        // In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
        // function would convert and deposit the rest coin into the primary store and freeze it to make the
        // `frozen` semantic as consistent as possible.
        if (frozen != fungible_asset::is_frozen(store)) {
            fungible_asset::set_frozen_flag_internal(store, frozen)
        }
    ...
```

The design comment only reasons about the "frozen CoinStore → unfrozen FA store" case, but the same equality check equally triggers in the opposite direction: an **unfrozen** `CoinStore.frozen == false` combined with an **already-frozen** primary fungible store (`fungible_asset::is_frozen(store) == true`) results in `set_frozen_flag_internal(store, false)`, i.e., unfreezing the store.

This code path is reachable by anyone, without the account owner's or freeze-capability-holder's consent, via: [2](#0-1) 

```
public entry fun migrate_to_fungible_store<CoinType>(
    account: &signer
) acquires CoinStore, CoinConversionMap, CoinInfo { ... }

/// Migrate to fungible store for `CoinType` if not yet.
public entry fun migrate_coin_store_to_fungible_store<CoinType>(
    accounts: vector<address>
) acquires CoinStore, CoinConversionMap, CoinInfo {
    accounts.for_each(|account| {
            maybe_convert_to_fungible_store<CoinType>(account);
        });
}
```

`migrate_coin_store_to_fungible_store` has no `&signer` argument at all — it accepts an arbitrary `vector<address>` and operates on each unconditionally. It is intentionally permissionless (that's the point of a "migrate anyone" helper), but this means the freeze-flag sync side effect inherits that same lack of authorization.

The FA-side freeze is a first-class, independent control surface: `FreezeCapability<CoinType>` holders can obtain the paired `TransferRef` for the coin's FA metadata and use it to freeze *any* specific store (including a primary store) directly, entirely independent of the legacy `CoinStore.frozen` field: [3](#0-2) 

```
let (mint_ref, mint_ref_receipt) = get_paired_mint_ref(&mint_cap);
let (transfer_ref, transfer_ref_receipt) = get_paired_transfer_ref(&freeze_cap);
let (burn_ref, burn_ref_receipt) = get_paired_burn_ref(&burn_cap);
```

If a compliance/freeze action is applied at the FA layer (`fungible_asset::set_frozen_flag` via this `TransferRef`) while the victim's legacy `CoinStore<CoinType>.frozen` remains `false` (never touched by the freeze action), the store is now in the state: FA store frozen = `true`, `CoinStore.frozen` = `false`. Any third party can then call `migrate_coin_store_to_fungible_store<CoinType>([victim])`, which will execute `set_frozen_flag_internal(store, false)` and unfreeze the FA store — reversing the freeze-capability holder's authorized action without their involvement.

### Impact Explanation
This breaks the custody invariant that freeze control over a fungible asset store may only be changed by the holder of the relevant `TransferRef`/`FreezeCapability`. An unprivileged, arbitrary caller can restore transferability to a store that was deliberately frozen (e.g., for compliance, sanctions, or security-incident containment), enabling the account owner to move/drain funds that were meant to stay locked. This is a genuine "unauthorized takeover of freeze control tied to live assets" per the custody impact gate, and could facilitate theft/exfiltration of funds that regulators or protocol admins intended to be frozen.

### Likelihood Explanation
Likelihood is high given the mechanism requires no special privilege: `migrate_coin_store_to_fungible_store` is a public entry function callable by any account for any address list, with no gas-prohibitive complexity. The only precondition is that a target account has both a still-existing `CoinStore<CoinType>` (frozen = false) and a primary fungible store that has been frozen directly via the FA-native `TransferRef` path (a codepath the framework itself exposes and documents, e.g. `get_paired_transfer_ref`). This scenario is plausible in any workflow where freeze actions are applied at the FA layer post fungible-asset migration availability but before an account's `CoinStore` has been fully migrated/deleted.

### Recommendation
In `maybe_convert_to_fungible_store`, do not silently downgrade (unfreeze) an already-frozen `FungibleStore` based on a stale `CoinStore.frozen` value. At minimum, only propagate the frozen flag in the "freeze" direction (`false → true`), never `true → false`, or require that unfreezing during migration be gated behind the same authority (`FreezeCapability`/`TransferRef`) used to freeze in the first place. Alternatively, always keep both representations of freeze state synchronized at the moment any freeze/unfreeze action occurs (i.e., have `coin::freeze_coin_store`/`unfreeze_coin_store` — and any FA-side freeze path invoked with the paired `TransferRef` — update both `CoinStore.frozen` and the FA store's frozen flag atomically), so no permissionless migration call can ever observe or act on a stale, diverging value.

### Proof of Concept
1. Admin holding `FreezeCapability<CoinType>` calls `coin::get_paired_transfer_ref(&freeze_cap)` to obtain the paired FA `TransferRef`, then calls `fungible_asset::set_frozen_flag`/`primary_fungible_store::set_frozen_flag` on victim's primary store, setting `frozen = true`. Victim's legacy `CoinStore<CoinType>.frozen` remains `false` (untouched).
2. Attacker (any account) calls `coin::migrate_coin_store_to_fungible_store<CoinType>(vector[victim_addr])`.
3. Inside `maybe_convert_to_fungible_store`, `frozen (false) != fungible_asset::is_frozen(store) (true)` evaluates true, so `fungible_asset::set_frozen_flag_internal(store, false)` executes.
4. Victim's primary fungible store is now unfrozen, despite never having been unfrozen by the `FreezeCapability` holder — an unauthorized reversal of freeze control.

**Note on verification limits**: I was unable to retrieve the full source of `coin::freeze_coin_store`/`unfreeze_coin_store` in this session (grep results were truncated to match counts without content), so I could not directly confirm whether those specific entry points always keep `CoinStore.frozen` and the FA store's frozen flag in lockstep. My conclusion relies on the confirmed existence of an independent, capability-gated path to freeze the FA store directly (`get_paired_transfer_ref` + `fungible_asset`/`primary_fungible_store` freeze APIs) combined with the directly-read, unconditional equality-based sync logic in `maybe_convert_to_fungible_store`. I recommend a Devin session with full file access to confirm `freeze_coin_store`'s exact implementation before treating this as fully confirmed.
