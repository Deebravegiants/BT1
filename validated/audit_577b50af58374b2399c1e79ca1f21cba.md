## Title
Webhook `shop` field is not covered by the HMAC signature, allowing shop-domain spoofing on signature-valid webhook requests - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. Because the tenant-identifying field (`shop`) is not bound into the signed material, an attacker can take any body+HMAC pair that is valid for shop A and resubmit it with a `shop-domain` header claiming shop B. `Webhooks::Registry.process` will accept the request as authentic and hand the attacker-chosen shop value to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is derived purely from an unauthenticated header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively from `to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request — including `request.shop` — is authentic, and forwards `request.shop` unchanged into the handler-visible metadata: [4](#0-3) 

The intended equality the HMAC is supposed to guarantee is:
`hmac == HMAC(secret, body) AND shop == "the shop that actually generated this signed body"`

but the gem only proves the first half. The `shop` header is fully attacker-controlled independent of the signature, so the equality `verified_shop == actual_source_shop` does not hold. Any party that can obtain one genuine `(raw_body, hmac)` pair — trivially available by installing the app on their own store and receiving a real webhook, or from any shop the app is publicly installable on — can replay that same body/hmac to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` dispatches the handler with the attacker-supplied `shop` value.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on this gem to enforce for incoming webhooks. A host app that keys per-tenant state, credentials, or data-deletion routines (e.g. `customers/redact`, `shop/redact`, `orders/*`) off `WebhookMetadata#shop` can be made to act on behalf of, or against, a shop that never actually sent that event — i.e. cross-tenant access/action, satisfying the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Webhook endpoints are public, unauthenticated HTTP endpoints by design (Shopify calls them without any additional caller authentication beyond the HMAC). Obtaining one valid `(body, hmac)` sample requires only installing the target app on any store (including the attacker's own free/dev store) and triggering any webhook topic the app subscribes to — no `api_secret_key`, access token, or privileged access is needed. Replaying that captured pair with a forged `shop-domain` header is a simple unauthenticated HTTP request.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the material that is authenticated, or otherwise cryptographically bind `shop` to the signed body — e.g., require host applications to cross-check `request.shop` against a shop they already have an installed/active session for, and document this requirement prominently; alternatively, extend `to_signable_string` to incorporate the shop header (matching how `AuthQuery#to_signable_string` binds `shop` into its signable string) so `HmacValidator.validate` fails when the header does not match the shop that actually produced the signed payload.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook subscribed by the app (e.g. `orders/create`) and capture the raw POST: headers include `x-shopify-hmac-sha256: <HMAC>` and `x-shopify-shop-domain: attacker.myshopify.com`, with some `raw_body`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds successfully (all required headers present); `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `raw_body`, unaffected by the header change (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. `Registry.process` dispatches the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` even though the event body/data actually originated from `attacker.myshopify.com` (`lib/shopify_api/webhooks/registry.rb` lines 190-199), letting the attacker inject data or trigger tenant-scoped side effects labeled as belonging to `victim.myshopify.com`.
