### Title
Bundling relayer/protocol fee transfer with message batch execution can force valid ISMP message delivery to permanently revert - (`modules/pallets/ismp/src/impls.rs`, `modules/pallets/ismp/src/fee_handler.rs`)

### Summary
`pallet-ismp`'s `execute()` function processes an entire batch of incoming ISMP messages (consensus updates, requests, responses, timeouts) and, in the same atomic extrinsic, charges a fee to each message's signer via `T::FeeHandler::on_executed`. If that fee transfer fails for any single message in the batch, the whole extrinsic returns an error, causing Substrate to roll back **all** storage changes performed while processing every message in the batch — including unrelated, legitimate message deliveries that had already succeeded.

### Finding Description
`Pallet::execute` first processes every message in the batch (dispatching to modules, updating consensus/request/response state) and only afterwards calls the configured `FeeHandler`: [1](#0-0) 

The default `WeightFeeHandler::on_executed` implementation transfers a computed fee from each message's signer to the treasury account using `Currency::transfer(..., ExistenceRequirement::KeepAlive)` and propagates any transfer failure as a hard error: [2](#0-1) 

Because `execute()` maps this error to `Error::<T>::ErrorChargingFee` and returns it from the dispatchable, the entire extrinsic — and therefore every state mutation made while handling *every* message in the batch (not just the one whose fee payment failed) — is reverted by the runtime's atomic extrinsic semantics.

This mirrors the reported pattern in `Vault.vy`: a fee-distribution transfer that can legitimately fail (e.g. due to `KeepAlive`/existential-deposit constraints, frozen/vested balances, or an account intentionally left with insufficient free balance) is executed in the same transaction as critical protocol logic, so a failure in the fee leg forces the critical logic to revert as well.

### Impact Explanation
`handle_unsigned` (the entry point that invokes `execute`) is callable by any relayer submitting any set of ISMP messages, including messages signed by third parties whose accounts are not controlled by the submitting relayer. A single message whose declared signer has insufficient free balance to survive `KeepAlive` (or is otherwise unable to pay the computed fee) causes `on_executed` to fail, rolling back consensus updates, request/response handling, and timeout processing for every other message batched alongside it. This can be used to reliably block delivery of otherwise valid, unrelated messages, and — because consensus state updates can also be included in a batch — can stall the light-client/consensus pipeline, i.e. "a route unable to deliver messages."

### Likelihood Explanation
Any account can be signer of a message with a balance deliberately kept at or near the existential deposit; a relayer (or the account itself, self-relaying) then batches this message with genuinely important messages to force a full-batch revert. No privileged role is required — only a validly signed message and control over what gets included in the same `handle_unsigned` call. This makes the griefing condition realistic though it depends on batch composition, which is why it aligns with the source report's Medium categorization (dangerous but not always triggered).

### Recommendation
Decouple fee charging from message execution so that a fee-transfer failure cannot revert already-processed, unrelated messages:
- Process fee charging per-message rather than as a single all-or-nothing batch step, or
- Move to a pull-based/accrual model similar to the recommendation in the source report — accrue owed fees in storage and let payers/treasury settle balances in a separate transaction — or
- If a signer cannot pay, only reject/skip that specific message's inclusion effects rather than failing the whole extrinsic, and use `AllowDeath`/best-effort fee collection with graceful degradation instead of a hard error that aborts the transaction.

### Proof of Concept
1. A relayer submits `handle_unsigned` with a batch containing: (a) a high-value consensus/request message from Alice, and (b) an unrelated Request message signed by Mallory, whose account balance is deliberately kept at exactly the existential deposit.
2. `Pallet::execute` processes both messages successfully, updating consensus/request storage for both. [3](#0-2) 
3. `T::FeeHandler::on_executed` attempts `Currency::transfer(&mallory, &treasury, fee, KeepAlive)`, which fails because it would drop Mallory below the existential deposit. [4](#0-3) 
4. `execute()` returns `Error::<T>::ErrorChargingFee`, the extrinsic fails, and Substrate reverts all storage writes made during step 2 — including Alice's legitimate consensus/request update — even though it had nothing to do with Mallory's failed fee payment.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

		for event in events.clone() {
			// deposit any relevant events
			Pallet::<T>::deposit_event(event.into());
		}

		Ok(events)
	}
