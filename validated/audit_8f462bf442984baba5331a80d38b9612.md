## Analysis

The geddy CVE is a classic CWE‑22 directory-traversal: a client-supplied path is decoded/joined against a base directory without confirming the final path stays inside that directory. The closest, concretely reachable analog in this repository is the `newHTTPFetcher` implementation used by the CRE workflow artifact fetcher.

### Title
Directory Traversal in `newHTTPFetcher` allows workflow-owner-controlled artifact URLs to escape the configured base path - (File: `core/services/workflows/syncer/v2/fetcher.go`)

### Summary
`NewFetcherFunc` builds a `FetcherFunc` used to download workflow binary/config artifacts. When configured with an `http(s)://` base URL, the returned `newHTTPFetcher` treats the caller-supplied `req.URL` as a *relative path* and joins it onto the configured base path with `filepath.Join`, which itself calls `filepath.Clean`. Because `filepath.Clean`/`filepath.Join` resolves `..` segments across the join boundary, a `req.URL` containing enough `../` sequences collapses through the configured base path prefix and reaches sibling paths on the same host — the exact traversal pattern described in the geddy advisory.

### Finding Description
`newFileFetcher` (the `file://` variant) explicitly re-validates the joined path is still prefixed by `basePath` before reading: [1](#0-0) 

`newHTTPFetcher` (the `http(s)://` variant) has no equivalent post-join containment check — it only cleans the incoming path and strips a leading `/` before joining: [2](#0-1) 

`filepath.Join(base, "../../admin/secret")` collapses to a path outside `base` (e.g. `/secure/prefix` + `../../admin/secret` → `/admin/secret`) because `Clean` resolves `..` against the absolute joined string, not against `base` alone. There is no check analogous to `newFileFetcher`'s `strings.HasPrefix(fullPath, basePath+...)` guard.

`req.URL` here is `ghcapabilities.Request.URL`, which is populated directly from the on-chain `binaryURL`/`configURL` values supplied at workflow registration time: [3](#0-2) 
and passed straight through to the configured fetcher when the node uses the direct (gateway-bypassing) fetcher mode, in which case `retrieveFunc`/host-allowlist validation is skipped entirely (per the code comment): [4](#0-3) 

This fetcher mode is wired up from operator config `cfg.CRE().WorkflowFetcher().URL()`: [5](#0-4) [6](#0-5) 

Once this feature is enabled with an `http(s)://` base, any workflow owner who can register/upsert a workflow (an external, lower-trust actor relative to the node operator) fully controls the string used as `req.URL`, and can therefore force the node to fetch attacker-chosen paths on the configured trusted host instead of the intended artifact-storage prefix.

### Impact Explanation
An attacker who can register a workflow (a normal, comparatively unprivileged workflow-owner action gated only by workflow-registry authorization, not node-operator privilege) can redirect the node's outbound artifact-fetch requests to arbitrary paths on the configured host, bypassing the intended base-path restriction. Depending on what else is hosted at that host/path (e.g. internal APIs, other tenants' artifacts, admin endpoints reachable from the same origin), this can lead to unauthorized data disclosure or request impersonation against internal services that trust requests originating from the node. It does not grant local filesystem traversal (that path is already guarded in `newFileFetcher`), but it does break the intended path confinement for the HTTP fetch mode.

### Likelihood Explanation
Likelihood is moderate: it requires the node operator to have configured `CRE().WorkflowFetcher().URL()` with an `http(s)://` scheme (a documented, gateway-bypass configuration path), and it requires an attacker capable of registering a workflow with a crafted `binaryURL`/`configURL`. In that configuration, exploitation is straightforward and requires no additional privilege beyond normal workflow registration.

### Recommendation
Add the same containment check used in `newFileFetcher` to `newHTTPFetcher`: after joining, verify the resulting `u.Path` still has the original base path as a prefix (comparing path segments, not raw strings, to avoid partial-segment matches), and reject the request otherwise. Alternatively, reject any `req.URL` containing `..` path segments before joining.

### Proof of Concept
1. Configure `CRE.WorkflowFetcher.URL = "https://artifacts.internal.example/prefix"`.
2. Register a workflow (via `UpsertWorkflow`) with `binaryURL = "../../internal/admin-config"`.
3. When the syncer processes the `WorkflowRegistered` event, `FetchWorkflowArtifacts` calls `fetchFn` with `req.URL = "../../internal/admin-config"`.
4. `newHTTPFetcher` computes `filepath.Join("/prefix", "../../internal/admin-config")` → `/internal/admin-config`, and issues an HTTP GET to `https://artifacts.internal.example/internal/admin-config`, outside the intended `/prefix` scope. [7](#0-6)
