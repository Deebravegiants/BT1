Confirmed: `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` with no validation against `ShopifyAPI::Utils::ShopValidator` [1](#0-0) , and `Auth::Oauth.validate_auth_callback` builds that session directly from `auth_query.shop` [2](#0-1) , then POSTs the app's `client_secret` to `https://#{auth_query.shop}/admin/oauth/access_token` [3](#0-2) .

### Title
OAuth callback sends `client_secret` to attacker-influenced `shop` host with no domain allowlist check - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` only checks that the `shop` query parameter matches the HMAC computed over the callback query string; it never validates that `shop` is an actual `*.myshopify.com`/trusted Shopify domain via `ShopifyAPI::Utils::ShopValidator`, even though that validator exists in the same gem specifically for this purpose [4](#0-3) .

### Finding Description
The equality that should be enforced is: `host that receives the app's client_secret == a domain in ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. Instead, the code only enforces `hmac(query) == computed_hmac(query, api_secret_key)`, and since `shop` is one of the fields *inside* the signed string (`to_signable_string` includes `shop`) [5](#0-4) , this only proves the query was untampered en route — it does nothing to prove `shop` is a legitimate Shopify domain rather than an arbitrary value that Shopify itself was willing to sign when the OAuth flow was initiated for that "shop".

`validate_auth_callback` takes this unvalidated `auth_query.shop`, wraps it in a `null_session`, and passes it straight into `Clients::HttpClient` [6](#0-5) . `HttpClient#initialize` then builds the request base URI directly from `session.shop` with no domain check: `@base_uri = "https://#{api_host || session.shop}"` [1](#0-0) . The subsequent POST to `/admin/oauth/access_token` includes the request body `{ client_id, client_secret, code, expiring }` [3](#0-2) .

Contrast this with `Auth::TokenExchange`, which — for the newer OAuth flow — derives `shop` from the JWT `dest` claim and is documented to ignore any caller-supplied `shop` [7](#0-6) , and `ClientCredentials`/`RefreshToken`, which explicitly call `ShopValidator` [8](#0-7) . The Authorization Code Grant path (`Oauth.validate_auth_callback`) is the one code path in the gem's core auth flow that skips this domain allowlist entirely, breaking the same "identity binding" class described in the report (a value is validated for integrity/authenticity of its bytes, but the semantic constraint on those bytes — being an actual Shopify shop host — is never re-checked before it's used to route a credential-bearing request).

### Impact Explanation
If an app can be driven through the callback with a `shop` value that Shopify will still sign into a valid callback (e.g., via a shop domain the attacker legitimately controls in Shopify's system, or any host value accepted at `begin_auth` time and echoed back with a valid HMAC), the app will send its `client_id` and `client_secret` in a POST body to a host chosen from that `shop` value. This is High severity: SSRF carrying the app's `client_secret`/credentials to a location influenced by the requester, which can lead to `client_secret` theft (Critical-adjacent, since the report's impact list explicitly names theft of the app's `client_secret` as Critical impact).

### Likelihood Explanation
Likelihood is bounded by whether `begin_auth`/the calling app permits an attacker-influenceable `shop` value to reach `validate_auth_callback` without prior sanitization. `begin_auth` itself does not sanitize `shop` either — it just interpolates it into `auth_base_uri` [9](#0-8) . Any host application that passes a user/request-derived `shop` string straight into `begin_auth`/`validate_auth_callback` (a common integration pattern, since the docs show `shop = request.headers["Shop"]`) [10](#0-9)  inherits this gap, because the gem itself never calls `ShopValidator.sanitize!` in this path even though the validator exists for exactly this purpose.

### Recommendation
In `ShopifyAPI::Auth::Oauth.begin_auth` and `validate_auth_callback`, call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (as `TokenExchange`/`ClientCredentials`/`RefreshToken` effectively guarantee for their flows) before using `shop` to construct request hosts, and reject the callback if the shop does not resolve to a trusted domain.

### Proof of Concept
1. App calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: attacker_shop, redirect_path: "/callback")` where `attacker_shop` is not validated against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.
2. Shopify (or a replayed/crafted flow reachable through host-app misuse) redirects back with `shop=attacker_shop`, a valid `hmac` computed over the exact query string using the correct `api_secret_key`.
3. `validate_auth_callback` verifies the HMAC (passes, since `shop` is part of the signed content) and proceeds to build `Auth::Session.new(shop: attacker_shop)` and issue `HttpClient.new(session: null_session, base_path: "/admin/oauth").request(...)`.
4. `HttpClient` sends `POST https://#{attacker_shop}/admin/oauth/access_token` with body containing `client_id` and `client_secret` in plaintext [3](#0-2) , exfiltrating the app's `client_secret` to a host under `attacker_shop`'s control since no code path validates `shop` against `ShopValidator`.
