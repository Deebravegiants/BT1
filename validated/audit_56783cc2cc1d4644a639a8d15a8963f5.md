### Title
Missing reentrancy guard on Tron `IntentGatewayV2.placeOrder` allows external `transferFrom`/predispatch calls to re-enter escrow accounting before state is finalized - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron port of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reimplements `placeOrder` without the `nonReentrant`/`ReentrancyGuardTransient` protection present in the canonical EVM implementation. `placeOrder` performs external calls — `IERC20.safeTransferFrom` to arbitrary user-supplied `order.inputs[i].token` addresses, and `ICallDispatcher(dispatcher).dispatch(...)` for the predispatch path — before/while mutating shared state such as `_orders[commitment][token]` and `_nonce`.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol:60`, the production EVM contract composes `IntrinsicIntents`/`ExtrinsicIntents` with `ReentrancyGuardTransient`, and `placeOrder` is marked `nonReentrant` (`evm/src/apps/IntentGatewayV2.sol:194`). [1](#0-0) [2](#0-1) 

The Tron variant re-declares the same logic from scratch as `contract IntentGatewayV2 is HyperApp, EIP712` with no `ReentrancyGuard` inheritance, and its `placeOrder` function has no `nonReentrant` modifier: [3](#0-2) [4](#0-3) 

Within this unguarded function, tokens supplied by the caller (`order.inputs[i].token`, `order.predispatch.assets[i].token`) are attacker-controlled addresses whose `transferFrom` implementation runs arbitrary code, and the predispatch path invokes `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — again arbitrary caller-supplied calldata executed by the dispatcher: [5](#0-4) 

State such as `order.nonce = _nonce++` and, later, `_orders[commitment][token] += reducedInputs[i].amount` are set/mutated interleaved with these external calls rather than fully finalized beforehand (Checks-Effects-Interactions is violated): [6](#0-5) [7](#0-6) [8](#0-7) 

Because `placeOrder` is not `nonReentrant`, a malicious ERC-20-like token used as `order.inputs[i].token`, or a crafted predispatch call routed through the dispatcher, can re-enter `placeOrder` (or other public gateway functions such as `fillOrder`/`cancelOrder`, if present in the same contract) mid-execution — before the current call's nonce increment and escrow bookkeeping are consistent, or while gateway/dispatcher balances are in a transient, partially-swept state (the predispatch/sweep pattern at lines 416–446 snapshots balances and sweeps via a *second* dispatcher call, exactly the kind of multi-step balance-then-transfer sequence the reported bug class targets).

### Impact Explanation
This matches the reported bug class: an externally-reachable function that calls `transferFrom`/executes attacker-influenced external calls (dispatcher `dispatch`) before internal escrow/nonce state is fully settled, without reentrancy protection. On Tron this can let a malicious token or predispatch payload re-enter the gateway to manipulate escrow accounting (`_orders`), potentially double-crediting escrow entries, corrupting the nonce/commitment sequencing used for order uniqueness, or interacting with the dispatcher's held balances during the sweep window — leading to theft of escrowed funds or fund-freezing via corrupted commitments. This is the intents escrow entry point explicitly in scope.

### Likelihood Explanation
Reachable by any unprivileged user submitting a single `placeOrder` transaction with a malicious `order.inputs[i].token` address or malicious `predispatch.call`/`predispatch.assets` — no special privileges required, matching the "single submitted transaction... token transfer or order" reachability bar. The missing guard is a straightforward code-review finding (absence of `nonReentrant`/`ReentrancyGuard` compared to the parallel, guarded EVM implementation of the same function), which raises likelihood that this was an oversight in the Tron port rather than an intentional platform difference.

### Recommendation
Add reentrancy protection to the Tron `IntentGatewayV2` matching the EVM contract: inherit a reentrancy guard (e.g. `ReentrancyGuard`/`ReentrancyGuardTransient`, verifying transient storage/`TSTORE` support on Tron since it's used elsewhere in this file's tload/tstore patterns) and mark `placeOrder` (and any other externally reachable state-mutating functions performing external token/dispatcher calls) as `nonReentrant`, consistent with `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker deploys a malicious ERC-20 token whose `transferFrom` callback re-enters `IntentGatewayV2.placeOrder` (Tron contract) before returning.
2. Attacker calls `placeOrder` with `order.inputs[0].token` = malicious token.
3. Execution reaches `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` inside the unguarded loop (or the predispatch branch calling `dispatcher.call`/`ICallDispatcher.dispatch`).
4. The malicious token's `transferFrom` re-enters `placeOrder` (or another public gateway function), operating on partially-updated `_nonce`/`_orders` state, since no `nonReentrant` modifier blocks re-entry.
5. Depending on downstream logic, this permits crafting two orders that share manipulated escrow bookkeeping or exploiting the sweep-balance window in the predispatch branch, resulting in inconsistent/duplicated escrow credit.

Note: I could not fully verify downstream functions (`fillOrder`, `cancelOrder`, `withdraw`) in the Tron file within the available index snippets to confirm the complete exploit chain end-to-end; the index only surfaced `placeOrder` for this file. Given the file size and truncation, further review of the full Tron contract source via a Devin session would be needed to confirm exact fund-drain mechanics beyond the confirmed missing-guard root cause.
