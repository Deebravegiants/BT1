## Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), event `topic`, and `webhook_id` from HTTP headers that are never included in the HMAC computation, while `ShopifyAPI::Utils::HmacValidator` only verifies the raw request body. Any party that has ever received a legitimately Shopify-signed webhook for their own store (i.e., any merchant who installs the app — an unprivileged action available to anyone with a free dev store) can replay that exact body+signature pair while substituting the `shop-domain` header, causing the receiving app to process attacker-supplied data under a victim shop's identity.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns solely the raw HTTP body, deliberately excluding every other header: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` verifies only the HMAC (i.e., the body) and then unconditionally forwards the header-derived, unauthenticated `shop` value to the application's handler as the tenant identity: [4](#0-3) 

The identity binding broken here is: `shop value verified by HmacValidator (∅, not covered) ≠ shop value delivered to the handler as WebhookMetadata#shop`. Because the app's `client_secret` (used to compute the HMAC) is shared across *all* shops that install the app, a real signature obtained honestly for one tenant's body remains valid when replayed with a different `shop-domain` header — the signature says nothing about which shop the payload belongs to.

### Impact Explanation
This is a cross-tenant identity confusion: a legitimately signed body from Shop A can be relabeled as belonging to Shop B and will pass `HmacValidator.validate`. If the host application's webhook handler uses `WebhookMetadata#shop` to select which tenant's record to update (a documented, expected usage per `WebhookMetadata`), an attacker who is merely a merchant of their own store (no special privilege) can inject arbitrary attacker-controlled event data into another shop's application state, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the normal case for public apps): any installer can trivially capture their own genuinely-signed webhook (via network logging, a proxy, or simply reading their own app's request logs) and replay it with a modified `shop-domain` header — no secret material, privileged account, or credential theft is required beyond becoming an ordinary app installer.

### Recommendation
Include the tenant-identifying and topic-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material that `HmacValidator` verifies, or have the gem cross-check that the resolved `shop` matches a shop the caller has bound the session/state to, rather than trusting header-only, HMAC-uncovered fields as tenant identity.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook-eligible event (e.g., `orders/create`) on their own store; Shopify sends a legitimately signed POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(client_secret, B)`, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `B` and `H` (from their own logs/proxy — no secret needed).
4. Attacker resends the identical `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H`, per `to_signable_string`.
6. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the app to treat attacker-controlled data as originating from the victim shop.
