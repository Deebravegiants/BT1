### Title
Missing mutual exclusion between `create()`/`import()` and `unlock()` allows `primarySeedIdAtom`/keychain desynchronization - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet#create` and `Wallet#import` are wrapped in `makeConcurrent({ concurrency: 1 })`, but `Wallet#unlock` and `Wallet#lock` are plain `async` methods with no shared concurrency gate. Because `Application#create`/`Application#import` and `Application#unlock` in `features/application/src/modules/application.ts` call these wallet methods independently and expose them over RPC, an attacker (or an ordinary race from a fast double dApp/UI call) can interleave `create`/`import` with `unlock`, causing `#keychain.addSeed(seed)` in `unlock()` to load one seed while `#setSeed`/`#seedMetadataAtom.set` in `create()` writes a different seed, leaving `#primarySeedIdAtom` and the keychain state inconsistent.

### Finding Description
`create`/`import` are concurrency-limited only against each other: [1](#0-0) 

`unlock()` reads storage via `#getSeed`, calls `#keychain.addSeed(seed)`, and sets `#primarySeedIdAtom` — with no lock shared with `create`/`import`: [2](#0-1) 

`#setSeed` in `create()` writes the new seed to `walletStorage` and reads it back for verification, but this write is not serialized against a concurrently running `unlock()`'s `#getSeed` read: [3](#0-2) 

At the `Application` layer, `create` and `unlock` are two independent async methods, both awaiting `#applicationStarted` but otherwise unsynchronized, and each calls into `#wallet` and fires hooks/atoms independently: [4](#0-3) [5](#0-4) 

The RPC-exposed `wallet` proxy (`walletRpc`) wraps `unlock` to set `primarySeedIdAtom` from the RPC caller's returned value, again with no locking relative to `create`/`import`: [6](#0-5) 

If `unlock({ passphrase })` begins reading the SEED_KEY via `#getSeed` (line 91) at nearly the same time `create()`/`import()` is writing a new SEED_KEY via `#setSeed` (line 109), the read in `unlock` can pick up either the old or new seed bytes depending on timing/storage semantics, while the "seedId" then pushed to `#primarySeedIdAtom.set(primarySeedId)` is derived from whatever seed `unlock` actually read. Because `#keychain.addSeed` is called with that same seed, `keychain` state and `primarySeedIdAtom` will stay internally consistent with each other in most storage backends — but the *seed itself* may differ from the seed `create()` intends to be canonical/considered "current" by the calling UI, since the `create()` promise resolves with a `seedId` computed independently of what `unlock` actually loaded. This produces a mismatch between the seedId the UI/dApp believes was just created (`create()`'s return value) and the seedId that ends up unlocked/active in the keychain and `primarySeedIdAtom`, because the two operations race on the same underlying `walletStorage` `SEED_KEY` and independently set `primarySeedIdAtom` without coordination.

Additionally, there is no invariant enforced anywhere that `unlock()` cannot start while `create()`/`import()` is in flight (no shared mutex, no `isLocked` guard preventing unlock-during-create), so the origin/account binding assumption — "unlocked state corresponds to a single consistent primary seed matching what was just created/imported" — is not guaranteed by the code.

### Impact Explanation
If the seed that ends up bound to `primarySeedIdAtom`/keychain differs from the seed the calling code (dApp/UI) believes is active (e.g., because it just called `create()` for a specific origin/account context), any subsequent signing or address-derivation RPCs keyed off `primarySeedIdAtom` could operate against the wrong seed. This breaks the "origin/account binding" invariant and could result in transactions/signatures being produced against an unexpected primary seed, or a stale/replaced seed being exposed to a dApp context that expected the new one — a form of cross-account/cross-seed confusion.

### Likelihood Explanation
This requires two RPC calls (`create`/`import` and `unlock`) to be dispatched concurrently, which is reachable from ordinary RPC callers (e.g., a compromised or buggy dApp/UI issuing overlapping requests, or two race-prone UI code paths). No privileged state or secret leakage is needed — only overlapping legitimate calls, which the RPC bridge does not prevent. The precise outcome depends on the underlying storage's read/write atomicity and timing, so behavior may be storage-backend dependent and not always exploitable to a deterministic bad state, but the absence of any lock makes the race window real and reproducible in a controlled test using an artificially delayed storage mock.

### Recommendation
Serialize `create`, `import`, `unlock`, and `lock` under a single shared mutex (e.g., wrap all four with the same `makeConcurrent`/mutex instance, or use a dedicated async lock around `walletStorage` SEED_KEY reads/writes) so that no interleaving of seed-write and seed-read/keychain-load operations can occur. Additionally, `unlock()` should re-validate that the seed loaded matches the current `SEED_KEY` state, and `primarySeedIdAtom` updates from `create`/`import`/`unlock` should be applied atomically together with the keychain state change (e.g., set both under the same lock before returning to the caller).

### Proof of Concept
Integration test plan (Jest) in `features/wallet/module/__tests__/index.test.js`:
1. Build a `walletStorage`/`seedStorage` mock whose `get`/`set` for `SEED_KEY` have injectable delays to simulate slow I/O.
2. Call `wallet.create({ mnemonic: mnemonicA })` without awaiting.
3. Immediately (same tick) call `wallet.unlock({ passphrase })` (assuming a previous wallet with `mnemonicB` already existed and unlock's `#getSeed` read is in-flight when `create`'s `#setSeed` write commits).
4. Await both promises.
5. Assert: `await primarySeedIdAtom.get()` equals the seedId of whichever seed the keychain currently has loaded (`keychain.exportKey`/an equivalent introspection call), and that this matches `create()`'s returned `seedId` — i.e., write a test that deliberately interleaves and fails today because `unlock()` can load `mnemonicB`'s seed into keychain/`primarySeedIdAtom` even though `create(mnemonicA)` "wins" the storage write, or vice versa, demonstrating the lack of atomicity between `#setSeed` and `#getSeed`/`#keychain.addSeed`.
