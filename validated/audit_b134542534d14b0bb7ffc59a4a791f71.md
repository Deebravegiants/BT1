### Title
Webhook HMAC covers only the raw body, letting topic/shop-domain headers be forged while keeping a valid signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` authenticates nothing but the byte content of the body. The `topic` and `shop` values that `Registry.process` uses to select a handler and populate `WebhookMetadata` come from `shopify-topic`/`shopify-shop-domain` headers that are never covered by the signature, so they can be freely rewritten on any request that carries a body+HMAC pair that is valid for the app's secret.

### Finding Description
The broken binding: `HMAC_valid(raw_body, api_secret_key) == true` is treated as if it implied `(topic, shop) authenticated`, but the actual equality enforced by the code is only `computed_HMAC(raw_body) == received_HMAC` [2](#0-1) . `topic` and `shop` are derived from `@headers`, which are excluded from `to_signable_string` [5](#0-4) .

Because a single app has one shared `client_secret` used by Shopify to sign webhook bodies for every shop that installs the app, an attacker who installs the app on their own development shop will legitimately receive real, validly-signed webhook deliveries at an endpoint they control (e.g. for `orders/create` on their own shop). They can then take that exact `raw_body` + `x-shopify-hmac-sha256` pair — which is genuinely valid for the app's secret — and issue a brand-new, self-crafted HTTP request directly to the victim app's webhook-processing endpoint, but with `x-shopify-topic: customers/redact` and `x-shopify-shop-domain: victim.myshopify.com` substituted in. Since `Registry.process` only calls `Utils::HmacValidator.validate(request)` before trusting `request.topic`/`request.shop` [4](#0-3) , and that validation never touches the headers, the forged request passes. The registered `customers/redact` handler then receives a `WebhookMetadata` struct whose `shop` and `topic` fields are entirely attacker-controlled while `body` still reflects the attacker's own (unrelated) shop data [6](#0-5) . Any handler that trusts `data.shop`/`data.topic` (as the documentation examples do — `puts "... shop: #{data.shop} ..."`) to decide which merchant's records to erase will act against the victim shop id supplied only in an unauthenticated header.

No component in the reachable path re-derives `shop`/`topic` from signed content or cross-checks them against a known-installed shop list: `Request#initialize` only checks header *presence*, not consistency with the body [7](#0-6) ; `HmacValidator` never sees the headers at all.

### Impact Explanation
This lets one tenant's (the attacker's) genuinely-signed webhook traffic be relabeled to impersonate metadata for an arbitrary victim shop and an arbitrary (including mandatory/data-destructive) topic, satisfying the "cross-tenant access" Critical category when the host app's handler logic keys off `WebhookMetadata#shop`/`#topic` (as the gem's own documentation instructs developers to do) rather than re-validating shop/topic against the body. The attack is repeatable against any victim shop the attacker chooses to name in the forged header, for any topic the app has registered a handler for, at the cost of a single legitimate app install by the attacker.

### Likelihood Explanation
Preconditions: the app must expose a webhook-processing endpoint (documented usage pattern) and register a handler that trusts `data.shop`/`data.topic` without independently confirming them against verified state (e.g. without checking that `data.shop` matches a shop id embedded in the signed body, which most webhook payloads do include as a field, or without maintaining a stricter shop allow-list check). Shopify's real payloads typically embed the shop's own identifiers in the JSON body, so a careful handler could cross-check `body["something"]` vs. header `shop`, but the gem does nothing to enforce or facilitate this, and the documented example (`docs/usage/webhooks.md`) shows trusting `data.shop` directly. Attacker cost is low: sign up for a free/dev Shopify store, install the target app, capture one webhook delivery, and replay it with modified headers to the same processing endpoint — all attacker actions permitted under the stated threat model (own shop, own server, arbitrary headers/body).

### Recommendation
Do not treat `HmacValidator.validate` as authenticating anything beyond the exact bytes it signs. At minimum:
- Extend `to_signable_string` (or add a secondary check) to bind `topic` and `shop` into the authenticated material where the Shopify delivery format allows it, or
- Require/encourage handlers to cross-validate `WebhookMetadata#shop` against a shop identifier embedded in the verified body / against the session's known shop for that install, rather than trusting the header value outright, and
- Document explicitly that `shop`/`topic` are unauthenticated relative to the HMAC and must not be used for authorization decisions without additional verification.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_trusts_unauthenticated_topic_and_shop_headers
  attacker_body = '{"attacker":"own-shop-data"}'
  valid_hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, attacker_body)
  )

  received_shop = nil
  received_topic = nil
  handler = TestHelpers::FakeWebhookHandler.new(lambda do |data|
    received_shop = data.shop
    received_topic = data.topic
  end)

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "customers/redact", path: "path", delivery_method: :http, handler: handler,
  )

  # Attacker captures their own valid (body, hmac) pair from an install on
  # their own shop, then relabels headers to target a victim shop/topic.
  forged_headers = {
    "x-shopify-topic" => "customers/redact",
    "x-shopify-hmac-sha256" => valid_hmac,
    "x-shopify-shop-domain" => "victim.myshopify.com",
  }

  request = ShopifyAPI::Webhooks::Request.new(raw_body: attacker_body, headers: forged_headers)
  ShopifyAPI::Webhooks::Registry.process(request) # succeeds: HMAC only covers raw_body

  assert_equal("victim.myshopify.com", received_shop) # unauthenticated header trusted as tenant identity
  assert_equal("customers/redact", received_topic)
end
```
This demonstrates that `Registry.process` accepts the forged headers and dispatches `WebhookMetadata` with a `shop`/`topic` pair that was never covered by the HMAC, confirming the equality `authenticated(topic, shop) == trusted(topic, shop)` does not hold.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

          end

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @raw_body = raw_body
      end
