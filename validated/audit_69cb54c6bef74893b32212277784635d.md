## Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw request body only, while `shop-domain`, `topic`, `webhook-id`, and `api-version` are read directly from unsigned HTTP headers. `Webhooks::Registry.process` trusts these header-derived fields (`request.shop`, `request.topic`) to route and label webhook data to the host app's handler, without any cryptographic binding between the signature and those identity fields. This mirrors the reported bug class: a field that is acted upon (the shop/topic identity) is not covered by the authenticity check (the HMAC).

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it (via `OpenSSL.secure_compare`) against the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic linkage to the signed bytes: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately trusts `request.topic` and `request.shop` to select the handler and populate the metadata delivered to the host application: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that has installed a given app, any body+HMAC pair that is authentic for one merchant's webhook delivery is also a valid signature for that exact same body when replayed with a different `shopify-shop-domain` (or `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) header. `HmacValidator.validate` will still return `true` because it never inspects those headers — only the raw body bytes are verified. `Registry.process` will then hand the host app a `WebhookMetadata` object asserting an arbitrary/attacker-chosen `shop` value alongside body content that was actually authored for a different shop, breaking the equality that should hold: `shop bound by HMAC == shop the handler is told to trust`.

### Impact Explanation
This breaks the tenant-identity binding between the cryptographic signature and the shop the host application acts on behalf of. A host application that uses `WebhookMetadata#shop` to determine which merchant's records to update, delete, or key by (a normal and expected usage pattern per the gem's own docs) can be made to apply another shop's payload/body to an attacker-chosen shop identifier, or to mislabel the topic/version. This is a cross-tenant data-integrity issue: an attacker who can obtain one legitimate captured webhook delivery (e.g., from their own store where the app is installed, which requires no special privilege) can replay the same body+HMAC with a forged `x-shopify-shop-domain` header to have it processed as belonging to a different shop.

### Likelihood Explanation
Exploitation requires access to one valid `(raw_body, hmac)` pair for the app (obtainable by installing the app on any shop and observing/capturing its own outbound webhook delivery — no secret or privileged account needed) and the ability to POST directly to the app's public webhook endpoint with modified headers, which any unauthenticated internet user can do since webhook endpoints are public HTTP endpoints. No `api_secret_key`, access token, or victim credentials are required.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified payload, so that `HmacValidator.validate` fails if any of these fields are altered independently of the signed body.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook delivery, e.g. `POST /webhooks` with body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC-SHA256 of `B` under the app's shared secret) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same request to the app's webhook endpoint, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B) == H` — this still passes.
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., data intended for `attacker.myshopify.com` is now processed under `victim.myshopify.com`'s identity, as shown in [5](#0-4) .
