### Title
Emporium EIP-712 signature never binds output destination (`stealthAddressStructure`), fee token/recipient or `erc20TokenAddresses` — a validly signed op-stack can be executed to route funds/fees to an attacker-chosen address - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`verifyWallet` recovers the owner's signature only over `(circomData.emporiumMessage, hash(ops), stack.maxFee, stack.deadline)`. It never binds `circomData.stealthAddressStructure` (who receives the resulting shielded UTXO), `circomData.relay`/`feeStructure.feeToken` (who receives fee payments), or `circomData.erc20TokenAddresses`/`deltaAmountChanges` (which balances are measured/paid). Because `runAction` is invoked with attacker-supplied `CircomData` for any given valid signature+ops, an unprivileged caller can replay an owner's signed operation stack while redirecting both the resulting UTXO and the fee payment to themselves.

### Finding Description
The claimed invariant is: `(assets leaving the wallet, their destination) == (ops, maxFee) the owner signed`. In practice only the *calls* (`ops`) and the fee *ceiling* (`maxFee`) are cryptographically bound: [1](#0-0) 

- `hashedMessage` = `EMPORIUM_SIGNATURE_TYPEHASH(message, hashOps, maxFee, deadline)`. It excludes `circomData.relay`, `circomData.feeStructure.feeToken`, `circomData.erc20TokenAddresses`, and `circomData.stealthAddressStructure`.
- Only `feeStructure.flatFee > stack.maxFee` is checked; the destination token/relay for that fee is unchecked.

Downstream, these unbound fields directly control where value ends up:

1. **Fee redirection** — `payRelayFees` pulls `flatFee` (≤ `maxFee`, so it looks "authorized") from the signer's wallet and sends it to `circomData.relay`, an address chosen entirely by whoever calls `Hinkal.transact`: [2](#0-1) [3](#0-2) 

2. **UTXO destination redirection** — after the signed `ops` execute (moving/producing funds through the owner's `IHinkalWallet`), any resulting balance increase in the Emporium contract is wrapped into an output UTXO whose recipient is `circomData.stealthAddressStructure`, taken straight from attacker-supplied `CircomData`, not from anything the owner signed: [4](#0-3) 

The owner's signature says "you may perform exactly these calls, and I authorize up to `maxFee` in fees," but it says nothing about which relay collects that fee or which stealth address receives the shielded output. Any unprivileged party who can call `Hinkal.transact` (submitting their own proof/`CircomData`, per the threat model) and who obtains/observes a validly signed `EmporiumStack` (e.g., from a normal user-facing flow meant to be relayed faithfully) can instead submit it once with `circomData.relay = attacker` and/or `circomData.stealthAddressStructure = attacker's stealth key`, capturing the fee and/or the resulting UTXO for themselves — before the intended relay does. `verifyWallet`'s replay guard (`usedMessages[circomData.emporiumMessage]`) only prevents *re*-use after the first execution; it does nothing to stop the *first* execution from diverting funds, since the guard is set unconditionally regardless of which unsigned fields were substituted.

A far-future `deadline` widens the attacker's window to wait for/front-run the legitimate submission of a given signed stack and execute it first with the substituted destination.

### Impact Explanation
- Relay-fee theft: attacker redirects up to `maxFee` worth of fee tokens per signed message from the wallet owner to themselves instead of the legitimate relay — theft of protocol/relay fees (High).
- Unauthorized fund destination: any surplus token balance produced by the owner-authorized `ops` (e.g., claimed rewards, unwrapped tokens, refunds) is shielded into a UTXO under an attacker-chosen stealth address rather than the owner's — executing/settling a fund movement to a destination the owner never authorized (High, matches "executing calls or moving assets a wallet owner ... never authorised").
- Both are one-shot per signed `emporiumMessage`, but since the wallet owner has no visibility into which `relay`/`stealthAddressStructure` will be paired with their signature at submission time, this is fully exploitable against any legitimate off-chain automation/relay flow.

### Likelihood Explanation
- Precondition: existence of a validly EIP-712-signed `EmporiumStack` with `signerAddress != address(0)` and `flatFee` set, intended to be submitted by a relay on the owner's behalf (a documented, expected usage pattern given `sendToRelayFromWallet`/`doSendToRelay`).
- Attacker cost: none beyond calling `Hinkal.transact` with their own proof and the intercepted signature+ops; no special role or privilege is required — `runAction` itself is gated by `onlyAllowedRecipient` (the Hinkal core contract), but the attacker only needs to be the party that calls into `Hinkal.transact`, which is permissionless.
- Feasible for any observer of a pending/broadcast signed stack (e.g., via mempool, an API, or a compromised/malicious front-end integrating with the flow) to front-run the intended relay.

### Recommendation
Include `circomData.relay`, `feeStructure.feeToken`, and `circomData.stealthAddressStructure` (and ideally `erc20TokenAddresses`) inside the `EMPORIUM_SIGNATURE_TYPEHASH` payload so the owner explicitly authorizes the fee recipient and the destination of resulting shielded output, not just the raw calls and fee ceiling.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, an `IHinkalWallet` mock funded with ERC20 tokens, and a mock `Hinkal`/relay-call harness that can call `runAction` as the allowed recipient.
2. Owner signs an `EmporiumStack` (`ops` that cause the wallet to produce a token surplus + `maxFee`, `deadline`, `emporiumMessage`) intending `relay = relayA` and expecting output UTXO to go to `stealthAddressA`.
3. Attacker builds `CircomData` reusing the same signature/`ops`/`maxFee`/`deadline`/`emporiumMessage`, but sets `circomData.relay = attacker` and `circomData.stealthAddressStructure = attackerStealthAddress`.
4. Call `runAction` with attacker's `CircomData`; assert:
   - `verifyWallet` does not revert (signature still validates).
   - Fee tokens (`flatFee`) land at `attacker`, not `relayA`.
   - The returned `UTXO.stealthAddressStructure == attackerStealthAddress`, not `stealthAddressA`.
5. Assert the broken equality: `(destination paid fees, destination of output UTXO) != (relayA, stealthAddressA)` that the owner intended/authorized, while `(ops, maxFee)` match what was signed — proving destination fields are unauthenticated.
