## Title
Webhook Sender/Topic Spoofing via HMAC Not Binding `shop`, `topic`, `webhook-id`, or `api-version` Headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers to route and attribute the event. Because these header fields are never included in the HMAC-signed content, an attacker who has legitimately received one valid `(body, hmac)` pair (e.g., by triggering a webhook on their own store) can replay that exact body/HMAC to the app's public webhook endpoint while substituting arbitrary values for the `shop-domain`, `webhook-id`, and `topic` headers.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — none of the identifying headers are included: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all sourced from unauthenticated headers — to dispatch the event to the app's handler: [3](#0-2) 

This breaks the identity binding: `shop authenticated (bytes covered by HMAC) != shop acted upon (header value passed to the handler)`. Contrast this with the OAuth callback flow, where `AuthQuery#to_signable_string` correctly includes `shop` in the signed content, binding the shop to the signature: [4](#0-3) 

No equivalent binding exists for webhooks. Since HMAC-SHA256 with the app's secret only proves the body wasn't tampered with, and the same signed body can be paired with any header set, an attacker who has captured one legitimate `(body, hmac)` pair for a webhook delivered to their own shop can forge a POST to the app's webhook endpoint with:
- the same `body` and `hmac` (kept from the legitimate delivery, so `HmacValidator.validate` still returns `true`)
- an arbitrary `shopify-shop-domain` header naming a different (victim) shop
- an arbitrary `shopify-topic` / `shopify-webhook-id` header

`Registry.process` will accept this as valid and call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`, attributing attacker-controlled webhook content to a shop the attacker does not control.

### Impact Explanation
This is a cross-tenant identity-binding failure: the app's webhook handler processes attacker-supplied `shop`/`topic`/`webhook_id` values as if Shopify itself vouched for them, when only the body bytes were actually verified. Any app logic keyed on `WebhookMetadata#shop` (e.g., updating per-merchant records, triggering merchant-specific side effects, billing, or data sync) can be manipulated to act against the wrong tenant, or be fed spoofed topic/webhook-id metadata for replay/confusion attacks. This satisfies the Critical - cross-tenant access impact category.

### Likelihood Explanation
Exploitation requires only the ability to receive one legitimate webhook delivery (trivial for any user who installs the target app on their own development/test shop, since webhooks are addressed to the app's public endpoint) and the ability to issue an HTTP POST to that same public endpoint with modified headers — no access to `api_secret_key`, access tokens, or TLS interception is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) inside the HMAC-signed payload validation, or otherwise cryptographically bind these header values to the signed body (e.g., require the app-level handler to cross-check `shop` against a shop known to have a stored webhook subscription with the given `webhook_id`, or have `HmacValidator` incorporate the headers into `to_signable_string` for webhook requests, mirroring what `AuthQuery` already does for OAuth callbacks).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and legitimately receives a webhook delivery: raw body `{"id":123}` with header `x-shopify-hmac-sha256: <valid-hmac-for-that-body>`.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint reusing the exact same body and HMAC header, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (or any registered topic)
   - `x-shopify-webhook-id: <arbitrary>`
3. `HmacValidator.validate` passes because it only checks the body's HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` even though the request never came from or was authorized for that shop, as seen in `lib/shopify_api/webhooks/registry.rb:188-200`.
