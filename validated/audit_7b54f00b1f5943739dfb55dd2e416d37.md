### Title
Unguarded double subtraction in `process_withdraw` PnL accounting can underflow and revert - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` recomputes `target_orders.calc_pnl_x` / `calc_pnl_y` by chaining two `checked_sub(...).unwrap()` calls against the pre-withdrawal normalized totals `x1`/`y1`. Just as `DssProxyActionsCharter._getWipeAllWad()` underflowed when the recorded balance already covered the debt (an unguarded subtraction that assumed a fixed ordering relationship), this code assumes `x1 >= normalize(pc_amount) + delta_x` (and analogously for `y1`) without an explicit bound check, relying entirely on decimal-normalization/rounding invariants holding exactly.

### Finding Description
In `process_withdraw`, after computing the pnl split via `calc_take_pnl`, the code derives the withdrawal amounts and updates the target-order accounting with: [1](#0-0) 

`x1`/`y1` are computed once, before `calc_take_pnl` mutates `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, via floor-dividing normalization: [2](#0-1) 

`delta_x`/`delta_y` returned by `calc_take_pnl` are derived through a separate chain of `restore_decimal` → multiply by `pnl_numerator/pnl_denominator` → truncate to `u64`, each step performing independent integer division/rounding: [3](#0-2) 

`pc_amount`/`coin_amount` are then computed from the *already-decremented* `total_pc_without_take_pnl` using the withdrawal-ratio invariant: [4](#0-3) 

Because `x1` was normalized before the pnl deduction, while `pc_amount`'s normalization and `delta_x` pass through independent floor/ceiling rounding paths, the identity `x1 == normalize(pc_amount) + delta_x + normalize(remaining_total)` is not enforced by any checked arithmetic guard — it is only expected to hold "by construction." If accumulated rounding causes `normalize(pc_amount) + delta_x` to exceed `x1` (or the coin analog for `y1`), the `checked_sub(...).unwrap()` chain panics, aborting the transaction. This mirrors the reported bug class: a subtraction that is only safe under an implicit, unverified precondition, reverting when that precondition is violated.

### Impact Explanation
A revert here does not directly steal funds, but it denies withdrawal (and, since the exact same computation pattern updates `calc_pnl_x`/`calc_pnl_y` in `process_deposit` and `process_withdrawpnl`, potentially deposits and pnl withdrawal too) for any user/LP whose transaction happens to trigger the rounding edge case, freezing access to their liquidity through the standard `Withdraw` instruction for as long as the adverse pool state persists. This is a liveness/DoS-class impact on user funds rather than a Medium/High theft, consistent with the "possible revert due to underflow" classification in the source report.

### Likelihood Explanation
Triggering it requires no privileged access — any account can submit ordinary `Withdraw` instructions with attacker-influenced amounts, and repeated small deposit/withdraw/swap activity naturally drifts the pool's `need_take_pnl_pc/coin` and vault balances, increasing the chance that floor/ceiling rounding in `normalize_decimal_v2`/`restore_decimal` combined with the `pnl_numerator/pnl_denominator` scaling produces the off-by-rounding condition. The likelihood is not proven to be reliably reproducible from this analysis alone (no concrete failing input was derived), so it should be treated as a latent edge case rather than a guaranteed-to-trigger bug.

### Recommendation
Replace the unguarded `checked_sub(...).unwrap()` chains in `process_withdraw` (and the analogous ones in `process_deposit`/`process_withdrawpnl`) with `checked_sub` returning a proper `AmmError` (e.g., `AmmError::CalcPnlError`) instead of panicking, and/or use `saturating_sub` combined with an explicit invariant check that recomputes the post-state directly from the mutated `total_pc_without_take_pnl`/`total_coin_without_take_pnl` rather than re-deriving it via a separate, independently-rounded subtraction chain.

### Proof of Concept
Concrete failing numeric inputs were not derived in this analysis; the finding is based on structural code review showing the missing bound-check invariant between `x1`/`y1`, `delta_x`/`delta_y`, and `pc_amount`/`coin_amount`. Confirming exploitability requires fuzzing `calc_take_pnl` together with `process_withdraw`'s decimal-normalization chain (varying `pc_decimals`, `coin_decimals`, `sys_decimal_value`, `pnl_numerator/denominator`, and vault balances) to find an input where `normalize(pc_amount) + delta_x > x1`.

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
