### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw` (Tron) enables solver reentrancy drain of escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of the intents gateway, `evm/tron/contracts/apps/IntentGatewayV2.sol`, contains an internal `withdraw` function that transfers escrowed native/ERC-20 tokens to an attacker-influenced `beneficiary` **before** decrementing the corresponding `_orders[commitment][token]` accounting entry. This is the exact bug class ("Contract Vulnerability" — unchecked external call ordering leading to fund loss) referenced by the Shido incident report, and it is the same class of bug that was already found and fixed in the sibling EVM implementation (`IntentsBase.sol`), as evidenced by `IntrinsicIntentsReentrancyTest.sol`. The Tron contract does not carry that fix.

### Finding Description
In the audited/fixed EVM path, `IntentsBase._withdraw` decrements escrow state before performing any external call: [1](#0-0) 

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [2](#0-1) 

By contrast, the Tron contract's `withdraw` performs the low-level `.call` (which forwards all gas and can trigger arbitrary reentrant execution in the beneficiary) **before** updating `_orders`:

```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

This ordering is a textbook Checks-Effects-Interactions violation: the escrow balance for `(commitment, token)` is still non-zero at the moment execution control is handed to `beneficiary` via the raw `.call`. The main-line EVM implementation was demonstrably vulnerable to exactly this pattern and required a dedicated fix, confirmed by regression tests describing "escrow theft" via reentrant fills: [4](#0-3) 

The `beneficiary` for a `RedeemEscrow` withdrawal is the filler/solver address supplied in the `WithdrawalRequest`, which originates from the destination-chain fill performed by an unprivileged solver (`msg.sender` on `fillOrder`), i.e., an attacker fully controls this address and can make it a malicious contract with a reentrant fallback/`receive()`.

### Impact Explanation
An attacker acting as an intent solver can set the fill's beneficiary to a malicious contract. When the source-chain gateway processes the resulting `RedeemEscrow`/`RefundEscrow` withdrawal (or an analogous same-chain fill/cancel path that calls the same internal `withdraw`), the native-token `.call` hands control to the attacker's contract while `_orders[commitment][token]` still reflects the pre-withdrawal balance. If any other externally reachable function reads or acts on that stale balance during the reentrant window (e.g., a parallel cancel/refund path, or multiple tokens processed in the same loop before the specific token's line is decremented), funds can be extracted more than once against the same escrow entry, permanently draining locked user/solver funds — a direct, unbacked loss of escrowed assets analogous to the BNB drained from Shido.

### Likelihood Explanation
Likelihood is Medium: the vulnerable ordering is concrete and unconditional in the code (not a hypothetical), and the beneficiary address is fully attacker-controlled through the normal solver/filler flow. Exploitation requires the attacker to also control (or race) a second entry point that touches the same `(commitment, token)` slot during the reentrant window; I could not fully enumerate the Tron contract's `fillOrder`/`cancelOrder` code within this session to confirm the exact second entry point, so likelihood is assessed as Medium rather than High pending that confirmation.

### Recommendation
Apply the same Checks-Effects-Interactions fix used in `IntentsBase._withdraw` and `IntrinsicIntents.sol` to the Tron `IntentGatewayV2.withdraw`: decrement `_orders[body.commitment][token]` (and mark `_filled` where relevant) strictly before making any external call or token transfer. Consider also adding `ReentrancyGuard`/`nonReentrant` to all externally reachable entry points that can reach `withdraw` as defense in depth, matching the mitigation already validated by `IntrinsicIntentsReentrancyTest.sol`.

### Proof of Concept
1. Attacker deploys a malicious contract `Evil` with a `receive()`/fallback that, upon receiving native token from the gateway, attempts to re-trigger a second withdrawal/cancel against the same `commitment` while `_orders[commitment][token]` has not yet been decremented.
2. Attacker places/fills an order (as an unprivileged solver) such that the `WithdrawalRequest.beneficiary` for the `RedeemEscrow`/`RefundEscrow` message resolves to `Evil`.
3. When `IntentGatewayV2.onAccept` → `withdraw` executes the native-token branch, `Evil.call{value: amount}("")` is invoked before `_orders[body.commitment][token] -= amount` executes.
4. During this call, `Evil` re-enters a second reachable path referencing the same commitment/token, observing the stale (not-yet-decremented) escrow balance and extracting additional funds beyond what was legitimately owed. [3](#0-2)
