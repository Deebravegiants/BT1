## Title
Unsynchronized Map Access in `WorkflowMetadataHandler.Authorize` Causes Concurrent Read/Write Race With `syncMetadata` - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` at line 92 without holding `h.mu`, while the background `syncMetadata` goroutine reassigns `h.authorizedKeys` (and related maps) under `h.mu.Lock()` at line 178. This is an unsynchronized concurrent map access that can crash the gateway process with `fatal error: concurrent map read and map write`.

## Finding Description
`h.authorizedKeys` is declared as a plain Go map guarded by `h.mu sync.RWMutex`. [1](#0-0) . `Authorize` reads this map directly with no lock acquired anywhere in the function body. [2](#0-1) . Meanwhile, `syncMetadata`, invoked periodically via `h.runTicker(time.Duration(h.config.MetadataAggregationIntervalMs)*time.Millisecond, h.syncMetadata)` [3](#0-2) , correctly takes `h.mu.Lock()` before reassigning `h.authorizedKeys = authorizedKeys` and the other maps. [4](#0-3) .

Every other reader of these shared maps (`WorkflowShards`, `GetWorkflowID`, `GetWorkflowReference`) correctly acquires `h.mu.RLock()` before reading. [5](#0-4) [6](#0-5) . `Authorize` is the sole exception, confirming this is an oversight rather than an intentional design.

I confirmed via `grep_search` that `.Authorize(` / `Authorize(workflowID` is referenced in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`, indicating it is called from the client-facing HTTP trigger handler path. However, I was unable to view the exact call-site code or surrounding context in `http_trigger_handler.go` within the available tool results (the file's content for that specific line was not retrievable via the search patterns used), so I cannot independently confirm from source whether that call path is reachable by a fully unauthenticated/unprivileged external actor, whether there is any request-level serialization that prevents this race in practice, or whether other mitigating logic (e.g., request queuing, single-threaded processing of triggers) exists upstream of `Authorize`.

## Impact Explanation
If the race is genuinely reachable as described, unsynchronized concurrent Go map read/write causes the Go runtime to panic with `fatal error: concurrent map read and map write`, crashing the whole process (not recoverable via `defer/recover`). This would constitute a remotely triggerable denial-of-service against the gateway, which is an in-scope impact class. Severity should be scoped to DoS given a panic crashes the process outright — it does not appear to permit authentication bypass or key exfiltration since `Authorize`'s logic itself is unchanged, only its safety under concurrency is affected.

## Likelihood Explanation
The likelihood depends on: (1) how frequently `syncMetadata` runs (`MetadataAggregationIntervalMs`), and (2) request concurrency/throughput on the trigger path. The race window per tick is narrow (a single map pointer reassignment), so while theoretically triggerable by sending many concurrent trigger requests, in practice hitting the exact race window reliably requires sustained request volume aligned with tick timing. Go's map access detector is probabilistic, not always guaranteed to catch every unsynchronized access in a given run, but doing so repeatedly under load is a reasonably established DoS class in Go codebases.

## Recommendation
Wrap the read of `h.authorizedKeys[workflowID]` in `Authorize` with `h.mu.RLock()`/`RUnlock()`, consistent with `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`. Ensure that JWT-cache operations remain outside the `h.mu` critical section (they use a separate mutex already) to avoid lock ordering or performance issues.

2. In one goroutine, drive `syncMetadata` repeatedly (feed aggregator observations to force map reassignment on each tick).
3. In parallel, spawn many goroutines invoking `Authorize(workflowID, token, req)` concurrently, simulating simultaneous unprivileged client requests hitting the HTTP trigger endpoint.

Run with `go test -race` or under sustained load; expect either a race-detector report or (without `-race`, under real concurrent load) a `fatal error: concurrent map read and map write` process crash, since the write in `syncMetadata` (line 178) is lock-protected while the read in `Authorize` (line 92) is not.
