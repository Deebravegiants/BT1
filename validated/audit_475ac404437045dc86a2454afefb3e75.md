### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-spoofing / cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body. The `shop-domain` header, which is handed to the application's handler as the trusted tenant identifier, is never included in the signed material. Any actor able to obtain one valid `(body, hmac)` pair for the shared app secret — for example by installing the app on their own store and receiving a legitimate webhook — can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `Registry.process` will still consider the request authentic and will invoke the handler with the attacker-chosen `shop`, breaking the intended binding `hmac_valid(body) ⇒ shop == authenticated_shop`.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string`, and for webhooks that string is defined as just the raw body: [1](#0-0) 

The comparison itself is a straightforward `secure_compare` of `HMAC(secret, raw_body)`: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are all pulled straight from request headers and are never mixed into the signed bytes: [3](#0-2) 

`Registry.process` gates entirely on `Utils::HmacValidator.validate(request)` and then forwards the unauthenticated `request.shop` value straight to the handler as the tenant identity: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app, any party who can obtain one genuine `(raw_body, hmac)` pair — trivially achievable by installing the app on their own development/test store and capturing a real webhook delivery for a topic whose body doesn't leak shop identity (e.g. `app/uninstalled`, `shop/update` with attacker-controlled content, or any topic where the body is attacker-influenced) — can resend that exact body and HMAC to the app's webhook endpoint while setting `x-shopify-shop-domain` to a victim shop's domain. `HmacValidator.validate` will accept it because it only checks the body bytes, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the spoofed victim domain. This is the analog of the reported curl bug class: a value (`shop`) that is *acted upon* as an authenticated identity binding is not covered by the cryptographic check (`HMAC`) that is supposed to authenticate the message, exactly as the trailing-dot bypassed the HSTS host-matching check while still being accepted as "the same host."

### Impact Explanation
Applications built on this gem naturally trust `WebhookMetadata#shop` (or `request.shop`) as the authenticated tenant for the webhook, since it comes from a request that "passed HMAC validation." Because that field is outside the signed scope, an attacker can inject events attributed to a shop they do not own into the host application's webhook handler — e.g., causing an `app/uninstalled` handler to wipe/deactivate a victim shop's stored session and access token, or causing data attributed to one tenant to be written under another tenant's record — a cross-tenant integrity/confidentiality violation of the app's data model, driven entirely by this gem's authentication primitive silently omitting `shop` from its signature check.

### Likelihood Explanation
Any unprivileged internet user who can install the app on any store (including their own store, which the app's public installation flow always allows) can obtain a valid `(body, hmac)` pair for the shared secret, then trivially replay it with a modified `shop-domain` header via a normal HTTP POST to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or any privileged account is required — only observation of one legitimate webhook delivery, which the attacker themselves can trigger.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header in the signable material used by `HmacValidator`, or otherwise cryptographically bind the shop identity to the HMAC-verified payload before it is exposed to consumers via `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` is unauthenticated and that host applications must independently verify the shop against their own session store before trusting it, and consider rejecting/flagging webhooks whose header-derived shop cannot be corroborated by application state.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a real webhook delivery for a topic whose body is attacker-influenced (e.g. `products/create` with content the attacker controls), and captures `raw_body` plus the `x-shopify-hmac-sha256` header — both valid under the app's shared `api_secret_key`.
2. Attacker sends a POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` to the desired topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, raw_body)`: [5](#0-4) 
4. The handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the request never originated from Shopify on behalf of that shop.
