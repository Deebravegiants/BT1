### Title
Blacklisted/paused ERC20 recipient can permanently brick `IntentGatewayV2` cross-chain escrow settlement (DoS + fund freezing) - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` iterates over a `WithdrawalRequest.tokens[]` array and unconditionally calls `IERC20(token).safeTransfer(beneficiary, amount)` for every entry, with no try/catch or per-token isolation. This function is the terminal step of both cross-chain fill settlement (`RedeemEscrow`) and cross-chain cancellation (`RefundEscrow`), invoked from `ExtrinsicIntents.onAccept()` [1](#0-0)  and `onGetResponse()` [2](#0-1) , both of which are `onlyHost`-gated callbacks triggered by delivery of a relayed ISMP message — i.e. reachable from a single relayed proof submitted by any relayer, no privileged role required to trigger the revert once the order/beneficiary already exists.

### Finding Description
`_withdraw()` loops over `body.tokens` and, for any ERC20 (ex. USDC-like pausable/blacklist-capable token), calls `IERC20(token).safeTransfer(beneficiary, amount)` without isolating failures: [3](#0-2) 

If the escrowed order contains a token whose transfer to `beneficiary` reverts — because (a) the token contract is globally paused (e.g. USDC's `Pausable`), or (b) the specific `beneficiary` address has been blacklisted by the token issuer — the entire `safeTransfer` call reverts, which bubbles up and reverts the whole `_withdraw()` call, and therefore the whole `onAccept`/`onGetResponse` handler.

Because `onAccept` is the ISMP host's delivery callback (`EvmHost` calls into the app upon message delivery), a revert here is indistinguishable to the host/message-delivery pipeline from "module rejected the message" — the message cannot be delivered successfully. Since the request commitment/order state is not rolled back cleanly for a retry that would ever succeed (the beneficiary/token composition of the order is fixed at `placeOrder`/`fillOrder` time and cannot be altered), the message becomes **permanently undeliverable**: every relayer attempt to deliver the same `RedeemEscrow`/`RefundEscrow` post request will revert identically, forever, as long as any one of the escrowed tokens targets a blacklisted/paused ERC20 route.

This is a strict-superset failure compared to the referenced report: not only does the specific order's escrow get stuck, but if a same-commitment order contains multiple different `TokenInfo` entries in `body.tokens`, a single blacklisted-recipient/paused-token entry anywhere in the array blocks release of *all* other tokens in that same order as well, since `_withdraw` performs all transfers in one atomic loop before finalizing (`_filled[body.commitment] = beneficiary` is set at the top, but the whole call still reverts, so effectively nothing is finalized or transferred).

The same unguarded pattern also appears in the sibling functions `_fillCrossChain` (uses `safeTransferFrom` to `beneficiary` directly during fill) [4](#0-3)  and `_fillSameChain` [5](#0-4) , and in `_sweepDust` [6](#0-5) , all of which use unconditional ERC20 transfers to externally-supplied addresses.

### Impact Explanation
This is a High-severity permanent freezing-of-funds / message-non-delivery bug:
- Escrowed user/solver funds tied to the affected commitment become permanently locked in the `IntentGatewayV2`/`IntentsBase` contract — there is no path to retry with a different beneficiary or to skip the offending token, since `WithdrawalRequest.beneficiary` and `tokens` are fixed by the original cross-chain message body.
- The underlying ISMP `PostRequest` for that commitment can never be delivered successfully; every relayer's attempt to submit the proof and call `onAccept` reverts, wasting relayer gas and permanently stalling that route's queue position for the given commitment.
- Because a single order can escrow multiple tokens under one commitment, one blacklisted-recipient token can also freeze the release of unrelated, non-blacklisted tokens bundled in the same order.
- This matches the "route unable to deliver messages" / "permanent freezing of funds" acceptance criteria directly.

### Likelihood Explanation
Likelihood is realistic without needing any privileged actor:
- Any user can place a cross-chain order (`placeOrder`) specifying themselves or any third party as `output.beneficiary`/refund recipient.
- USDC (and similar centrally-blacklistable stablecoins) are explicitly supported input/output tokens in the Intent Gateway per the docs and tests (`usdc` fixtures used throughout `IntentGatewayV2*Test.sol`).
- An adversarial or unlucky beneficiary can become blacklisted (e.g., via unrelated interactions with sanctioned protocols) at any point between order placement and settlement — the attacker does not need to control the gateway, only to get their own or a target address blacklisted, or to target a period when the token issuer pauses transfers.
- No special timing or race condition is required — the failure is deterministic and reproducible on every delivery attempt.

### Recommendation
Do not let a single token transfer failure brick the entire withdrawal/settlement path:
- Wrap each per-token transfer in `_withdraw`, `_sweepDust`, `_fillCrossChain`, and `_fillSameChain` in a low-level call and catch failures (e.g., `try/catch` via an external self-call, or manual `call` + bool check) so that a revert on one token does not block the others.
- For tokens whose transfer fails, route the funds to a separate per-beneficiary/per-token "pending claims" ledger that can be claimed later (e.g., once unblacklisted) or redirected to an alternate address by the order's owner, rather than reverting the whole settlement.
- Ensure the escrow accounting (`_orders[commitment][token] -= amount`) is only decremented for transfers that actually succeed, keeping state consistent with a partial-success settlement model.

### Proof of Concept
1. User places a cross-chain order via `placeOrder` with `order.inputs` containing USDC, escrowed on the source chain.
2. Solver fills the order on the destination chain via `fillOrder`/`_fillCrossChain`, which dispatches a `RedeemEscrow` `WithdrawalRequest{commitment, tokens: [USDC amount], beneficiary: solver}` back to the source chain [7](#0-6) .
3. Before the relayer delivers this message, the solver's address becomes blacklisted on USDC (e.g., via Tornado Cash interaction), or USDC issuer pauses the contract.
4. A relayer submits the proof; `EvmHost` invokes `IntentGatewayV2.onAccept()` → `_authenticate` → `_withdraw(body, false, true)` [8](#0-7) .
5. Inside `_withdraw`, `IERC20(USDC).safeTransfer(beneficiary, amount)` reverts because the beneficiary is blacklisted [9](#0-8) .
6. The entire `onAccept` call reverts. Every subsequent relayer retry for the same commitment hits the identical revert — the escrowed USDC (and any other tokens bundled in the same order) is permanently stuck, and the message can never be delivered.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
