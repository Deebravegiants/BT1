### Title
`handleTokenExchange` writes an error status but continues execution, creating an authenticated session with an unvalidated empty email - ([File: core/sessions/oidcauth/oidc.go])

### Summary
In `oidcAuthenticator.handleTokenExchange`, the code checks whether the OIDC ID-token claims contain an `email` field, writes an HTTP 500 error to the response, but never returns from the handler. Execution falls through and proceeds to compute a role and insert a new authenticated session row keyed on the (empty) email value, exactly mirroring the reported bug class: a check is performed but its result is never actually applied to gate subsequent security-relevant logic.

### Finding Description
`handleTokenExchange` is the callback endpoint used to complete the OIDC login flow after the front end exchanges an authorization code (`core/sessions/oidcauth/oidc.go`, function `handleTokenExchange`, lines 163-260). After exchanging the token and verifying the ID token, it extracts the `email` claim:

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
oi.lggr.Tracef("Received and validated ID claims: %v\n", idClaims)
``` [1](#0-0) 

Unlike every other error branch in this same function (all of which call `return` after writing the error response, e.g. the `rawIDToken` extraction check just above it), this branch is missing the `return` statement:

```go
rawIDToken, ok := oauth2Token.Extra("id_token").(string)
if !ok {
    oi.lggr.Errorf("No id_token field in oauth2 token: %v", err)
    c.String(http.StatusInternalServerError, "Missing id_token field in response")
    return
}
``` [2](#0-1) 

Because the `email` check's failure path has no `return`, when `claims["email"]` is missing or not a string, the handler still proceeds to:
1. Map the ID claims to an RBAC role via `IDClaimsToUserRole` (still using the correctly-parsed `idClaims`, independent of the broken `email` variable).
2. Insert a new row into `oidc_sessions` using the empty `email` (zero value of `string`) together with the computed role:

```go
_, err = oi.ds.ExecContext(
    ctx,
    "INSERT INTO oidc_sessions (id, user_email, user_role, created_at) VALUES ($1, $2, $3, now())",
    clSession.ID,
    strings.ToLower(email),
    role,
)
``` [3](#0-2) 
3. Return a `200 OK` `{"success": true}` JSON response to the caller even though an error string was written earlier in the same request (Gin allows multiple writes; the last `c.JSON` call after this point wins), effectively hiding the earlier failure from the client while still handing back a valid, usable session cookie.

The session created is fully valid for `AuthorizedUserWithSession` lookups later (`core/sessions/oidcauth/oidc.go`, `AuthorizedUserWithSession`, lines 351-391), which only checks `session ID` validity/expiry and returns whatever `user_email`/`user_role` was stored — including an empty email and an elevated role (Admin/Edit/Run) if the IdP's group claims mapped the user to one.

### Impact Explanation
This is a real authentication-integrity defect reachable by any unprivileged client hitting the OIDC callback endpoint: it allows a completed login/session-creation flow to proceed with a corrupted identity field (empty `user_email`) whenever the IdP's ID token/userinfo claims omit an `email` field (e.g., IdP misconfiguration, an IdP that doesn't return `email` by default, or a crafted token from a semi-trusted/compromised IdP). The resulting session:
- Is a genuine, authenticated, non-expired session with a real role (computed independently from `idClaims`, e.g., "admin"), so the created session can grant privileged access under an identity of `""`.
- Silently discards the earlier logged error path, so the operator-visible behavior looks like a successful login (`success: true`) even though the code detected and reported a fault condition.
- Produces broken audit trails/session bookkeeping: multiple distinct real users hitting this bug would all be recorded under the same blank `user_email`, undermining per-user accountability and any downstream logic keyed on email uniqueness.

This matches the required bug class of "concrete authentication ... bypass / cross-user response confusion" reachable from an unprivileged client via the internet-facing OIDC login endpoint, not a privileged/operator-only or mock-only path.

### Likelihood Explanation
Likelihood is moderate: it requires the OIDC identity provider's response (or its userinfo/ID token claims) to omit an `email` field while still supplying the configured RBAC group claim(s), which is a normal boundary condition for certain IdP configurations, non-default scopes, or providers that don't include `email` unless explicitly configured — not a highly adversarial or malicious-server-only scenario. The vulnerable code path is exercised on every OIDC login attempt, so any environment using this auth provider is exposed whenever the IdP's claims are missing `email`.

### Recommendation
Add the missing `return` after writing the error response in the `email` claim check, so the login flow aborts rather than creating a session:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, consider using `c.JSON(...)` consistently (this branch uses `c.String`, inconsistent with the rest of the handler's `ExchangeTokenResponse` JSON contract) and verify no other branch in this function is missing a `return` after an error response.

### Proof of Concept
1. Configure the chainlink node with OIDC auth (`core/sessions/oidcauth`) pointed at an IdP/mock IdP that authenticates the user and returns valid ID-token claims including the required RBAC group claim, but does **not** include an `email` claim (e.g., a `userinfo`/ID-token response omitting `email` while granting the "admin" group).
2. Complete the standard front-end OIDC flow: `GET /oidc-login` (`handleSignIn`) → provider auth → front end calls the token-exchange endpoint with the authorization `code` and `state` (`handleTokenExchange`).
3. Observe that:
   - The server logs `"Failed to get email from claims"` and writes an interim `500` body via `c.String`.
   - Execution continues; `IDClaimsToUserRole` still succeeds (using `idClaims`, unrelated to `email`), and a row is inserted into `oidc_sessions` with `user_email = ''` and `user_role = 'admin'`.
   - The final response written by the handler is `200 {"success": true}` and a valid session cookie is set (`ginSession.Set(...); ginSession.Save()`), because these calls happen unconditionally after the broken check.
4. Using the returned session cookie, call any authenticated admin API route; `AuthorizedUserWithSession` will resolve this session to a valid, non-expired admin user with `email = ''`, confirming a session was successfully created and is usable despite the detected claims failure.
