### Title
Webhook `shop-domain` header is trusted for tenant identity but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` value that is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Registry.process` verifies only covers the raw request body. This breaks the identity binding `HMAC-authenticated bytes == bytes used to determine tenant`, allowing the `shop` field consumed by app-provided `WebhookHandler` implementations to be forged independently of the cryptographically verified payload.

### Finding Description
`Registry.process` validates a webhook exclusively through `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares it against the received HMAC: [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

but `Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from HTTP headers that are never part of the signed material: [3](#0-2) [4](#0-3) 

`Registry.process` then forwards this unauthenticated `shop` value into `WebhookMetadata`, which is delivered verbatim to the application's handler: [1](#0-0) [5](#0-4) 

The gem's own documentation instructs integrators to key their tenant-scoped work off this field directly (`shop_domain: data.shop`), reinforcing that `shop` is treated as an authenticated tenant identifier by consuming applications: [6](#0-5) 

The identity binding that should hold is:
`HMAC(raw_body, api_secret_key) valid` ⇒ `shop header == originating tenant for raw_body`

But because the HMAC only signs `raw_body`, this equality does not hold. Anyone who possesses one genuine `(raw_body, hmac)` pair for a webhook topic they legitimately receive (e.g., a merchant who has the app installed on their own store and receives its own webhooks over an inspectable channel, or any party who can observe such a request) can resend the same body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header changed to a different, victim tenant's domain. `HmacValidator.validate` will still return `true` because the body and signature are unchanged; only the unsigned header differs, and `process` will invoke the handler with `data.shop` set to the victim's domain.

### Impact Explanation
This crosses a tenant boundary: an attacker who is not authorized for a victim shop can cause the host application to process (and typically persist/act on) webhook data under the identity of that victim shop, since the gem hands the attacker-controlled `shop` value to the handler as if it were verified. Depending on how the host app uses `data.shop` (e.g., to select which merchant record to update, which access token to use for follow-up API calls, or to log data under an account), this can result in cross-tenant data corruption or cross-tenant action. This matches the "cross-tenant access" High/Critical impact category, since the tenant/shop identity binding that consumers rely on is not actually enforced by the gem.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair for some topic — trivially available to any merchant who has installed the app (they legitimately receive their own webhooks and can capture the exact bytes and signature), or to anyone who can observe an app's inbound webhook traffic. No knowledge of `api_secret_key` is needed to mount the replay; only the header is altered, and that header is unsigned by design in this implementation. This is a realistic, low-effort scenario for any party who already receives webhooks from the app (e.g., a merchant using the app on their own shop) to target other tenants of the same app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material that is HMAC-verified, or otherwise cross-check the header-derived `shop` against a value embedded in the verified body/session context before handing it to `WebhookHandler#handle`. At minimum, document prominently that `data.shop` is unauthenticated header data and must not be trusted for tenant selection without additional verification (e.g., confirming the shop has an active, stored session/access token) — since currently both the code and the docs treat it as trustworthy.

### Proof of Concept
1. App A operates a webhook handler that does `Tenant.find_by(shop: data.shop).update!(...)` based on `WebhookMetadata#shop`.
2. Merchant M (installed App A on `m.myshopify.com`) receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's secret), and `x-shopify-shop-domain: m.myshopify.com`.
3. M replays the exact same POST to the app's webhook endpoint, but changes only the `x-shopify-shop-domain` header to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the signature over `B` only, matches `H`, and returns `true`. [7](#0-6) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and App A's handler acts on `victim.myshopify.com` using data that actually originated for `m.myshopify.com`.
