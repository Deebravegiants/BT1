### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC-signed payload. `ShopifyAPI::Utils::HmacValidator` only validates the raw request body, so any attacker who can obtain one valid `(body, hmac)` pair for the shared app secret (e.g. by installing the app on their own store and capturing a legitimate webhook) can replay that same body/hmac pair while swapping the `shop-domain` header to an arbitrary victim shop. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated header and hands it to the app's webhook handler as the tenant identifier.

### Finding Description
The webhook `Request` object exposes `shop` straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

But the value that is actually HMAC-verified is only the raw body: [2](#0-1) 

`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) using the app's shared `api_secret_key`, and compares against the received signature: [3](#0-2) 

`Registry.process` only checks this body HMAC, then forwards `request.shop` — the *unauthenticated* header — directly to the handler as the tenant identity: [4](#0-3) 

This breaks the intended identity binding: `HMAC(body) == received_hmac` is verified, but the equality that matters for tenant isolation — `shop_header == shop_that_body_was_actually_signed_for` — is never checked. Because a single app typically shares one `api_secret_key`/`client_secret` across all merchants that install it, any merchant (an ordinary, unprivileged app installer) can capture a legitimate webhook sent to their own store (valid body + valid HMAC), then POST that identical body/HMAC pair to the app's public webhook endpoint while substituting a different shop's domain in the `shop-domain` header. The HMAC check still passes because it never covered the shop field, and `WebhookMetadata.shop` (used by the host app to route/attribute data) will report the attacker-chosen victim shop.

This is directly analogous to the report's underlying bug class: a value that downstream logic depends on for correctness/identity (there: a CDP's collateral/stake attribution; here: a webhook's shop/tenant attribution) is not covered by the mechanism that is supposed to guarantee its integrity (there: the corrected-stake accounting; here: the HMAC signature).

### Impact Explanation
This allows cross-tenant confusion/forgery of webhook events: a low-privilege attacker who is merely one of the app's own merchants can make the app process — and hand to the host application's business logic — a genuine, HMAC-valid webhook body while asserting it belongs to a different, victim merchant. Any host application that relies on `WebhookMetadata#shop` (as documented/intended by this gem) to select the session, tenant data store, or access token context can be tricked into cross-tenant data mixing, since the gem itself provides no binding between the verified bytes and the claimed shop.

### Likelihood Explanation
Any entity that can install the app on a shop they control (a normal, self-service action, not requiring any special privilege) can capture a real webhook for their own store and immediately has a valid `(body, hmac)` pair signed with the app's shared secret. Replaying it with a modified `shop-domain` header requires no additional secrets and no cryptographic break — only a standard HTTP POST to the app's public webhook callback URL.

### Recommendation
Bind the shop identity into the verified material: either include the `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signable string, or independently verify that the shop asserted in the header matches a shop expected/known for that specific webhook delivery (e.g., cross-check against Shopify's `X-Shopify-Webhook-Id` via the Admin API, or require per-shop signing where feasible). At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant routing without further verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its valid `x-shopify-hmac-sha256` header (both are computed using the app's single shared `api_secret_key`).
2. Attacker sends this exact body/HMAC to the app's public webhook endpoint again, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` reads the (still valid, since unmodified) signature; `HmacValidator.validate` recomputes HMAC over the unmodified raw body and it matches, per [5](#0-4) .
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is now `"victim-shop.myshopify.com"`, per [6](#0-5) , despite the payload actually originating from and describing the attacker's own store.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
