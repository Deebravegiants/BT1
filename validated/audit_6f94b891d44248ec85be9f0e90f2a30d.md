### Title
Unrestricted swap venues can execute arbitrary token transfers beneath a caller’s signed authorization tree - ([File: contracts/swap-aggregator/src/execute/mod.rs](https://github.com/AYontt/rs-lending-xlm--015/blob/main/contracts/swap-aggregator/src/execute/mod.rs))

### Summary
The swap aggregator treats pool addresses in user-supplied routes as trusted executable code. During `execute_strategy`, the attacker-selected venue runs while the original caller remains an authorizing ancestor. A malicious pool can therefore request a token transfer directly from the caller’s wallet. Soroban simulation records that transfer as a child authorization beneath the caller’s controller-strategy authorization; if the caller signs the simulated tree, the malicious contract receives the requested wallet funds even though the signed controller call appeared to authorize only a collateral swap. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Controller strategy entrypoints pass user-controlled route bytes to `swap_tokens`. `swap_collateral` authorizes the caller, verifies account ownership, withdraws collateral, and forwards the route into the router through `withdraw_and_swap_from_supply`. [4](#0-3) 

The controller correctly constrains its own authority: it authorizes one exact input-token transfer to the configured router and checks only the controller’s input and output balance deltas afterward. [5](#0-4) [6](#0-5) 

The vulnerability is that the route itself selects the `pool` address and `SwapVenue`. `execute_op` loads `pool`, `token_in`, and `token_out` from the unauthenticated `assets` registry and dispatches the venue without an allowlist or trusted-pool check. [2](#0-1)  Program validation checks structure, indices, opcode, token-chain compatibility, and amount modes, but not whether `idx_a` names a legitimate pool. [7](#0-6) [8](#0-7) 

Because `execute_strategy` begins with `sender.require_auth()`, any token call made by the malicious venue can attach itself to that signed authorization tree. A regression test shows a rogue hop calling `wallet_token.transfer(victim, attacker, amount)`, simulation adding it beneath the caller’s `swap_collateral` root, and enforcement succeeding when that simulated tree is signed. [9](#0-8) [3](#0-2) [10](#0-9) 

### Impact Explanation
An attacker can steal arbitrary tokens held by a user who signs a poisoned route’s simulated authorization. The theft is not limited to the swap input, routed collateral, or token contracts listed by XOXNO: the malicious venue can name any victim-held token and recipient. The repository’s proof uses an unlisted wallet-token balance and moves the entire `WALLET_BALANCE` to the attacker while the strategy still returns a fair swap output and succeeds. [11](#0-10) [10](#0-9) 

This maps directly to the external report’s DLL-redirection class: a trusted operation loads attacker-selected executable code, and that code inherits privileges associated with the enclosing operation. Here, the attacker-selected “module” is the hop-pool contract and the inherited privilege is authorization attached beneath the victim’s root call. [12](#0-11) 

### Likelihood Explanation
Likelihood is medium. The attacker can deploy a contract implementing the selected venue ABI and encode it as the `pool` registry entry in a route offered to a victim, because pool addresses are not allowlisted. [13](#0-12)  However, the malicious transfer does not silently inherit an unrestricted allowance: transaction enforcement requires the victim to sign an authorization tree that contains the rogue token transfer as a child. The attack therefore depends on a wallet or integration exposing only the top-level action, the victim failing to inspect nested authorizations, or the attacker convincing the victim to sign the simulated tree. [14](#0-13) [10](#0-9) 

### Recommendation
Do not invoke arbitrary route-selected contract addresses beneath an account-level `sender.require_auth()` operation. Restrict `idx_a` to governance-registered venue/pool identities, or separate untrusted route execution into a context that cannot create child authorizations for the original caller. At minimum, make every user-facing signer reject authorization trees containing children other than the expected `token_in.transfer(sender, router, total_in)` entry and surface any nested transfer to a different token or recipient. [1](#0-0) [15](#0-14) [2](#0-1) 

### Proof of Concept
The included test constructs an attacker-controlled `RogueHopPool`. Its `swap` method reads a stored plan and calls `token.transfer(victim, attacker, amount)` on a wallet token unrelated to the swap. [16](#0-15) 

The route names that contract as the hop pool. During recording-mode simulation, the rogue transfer is recorded as a sub-invocation beneath the victim’s `swap_collateral` authorization root. [17](#0-16) 

If the victim signs that returned tree, enforcement permits the transfer: the victim’s wallet balance falls to zero, the attacker receives `WALLET_BALANCE`, and the collateral swap still completes with the expected output. [10](#0-9)
