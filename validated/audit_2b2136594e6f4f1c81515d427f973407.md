I have sufficient evidence to finalize the analog finding on webhook shop-domain spoofing.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook solely by checking the HMAC over the raw request body, but the `shop` value it hands to the app's handler is read from an unauthenticated HTTP header. Any party that can obtain one legitimately-signed webhook body (e.g., by installing the app on their own store) can replay that exact body/HMAC pair while substituting a different `shop-domain` header, causing the app to process the payload as if it belonged to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled straight from HTTP headers and are never part of the signed content: [2](#0-1) 

`Registry.process` validates only this body-based HMAC and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values, passing them straight to the app-provided handler: [3](#0-2) 

The equality that is broken: the identity actually authenticated by `HmacValidator.validate` is *"HMAC(secret, raw_body) == received_hmac"*, i.e. only the **body bytes** are bound to the secret. The identity that the handler is told to trust is *"this webhook belongs to `shop`"* — but `shop` is never an input to that HMAC. Any attacker who can produce or capture a validly-signed body (trivial: install the target app on their own store, and Shopify will send them genuinely HMAC-signed webhooks for their own shop's events) can resend that identical body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header. `HmacValidator.validate_signature` recomputes the HMAC purely from `verifiable_query.to_signable_string` (the body) and compares it via `OpenSSL.secure_compare`, so the forged header has zero effect on the validation outcome: [4](#0-3) 

The gem's own documentation compounds this by asserting that `Registry.process` "will verify the request did indeed come from Shopify," and its example handler forwards `data.shop` directly into downstream job processing (`shop_domain: data.shop`) without any caveat that `shop` is unauthenticated: [5](#0-4) 

This is the direct analog of the reported bug class: a value (`shop`) that is *acted upon* by downstream logic is not covered by the integrity check (HMAC) that is supposed to bind the whole request together, just as the vault balance was updated from a value that diverged from the actually-verified lending-pool balance.

### Impact Explanation
This breaks tenant isolation: a party who has legitimately received one signed webhook (by installing the app on their own shop, or from any topic they subscribe to) can cause the app to attribute arbitrary attacker-supplied event bodies to any other shop domain of their choosing, since the `shop` field the handler receives is not authenticated. Depending on how the host application keys its downstream processing (job queues, database writes, cache invalidation, redaction handling for `shop/redact`/`customers/redact`/`customers/data_request` mandatory topics) by `data.shop`, this enables cross-tenant data confusion/injection — a Critical-tier impact per the rules (cross-tenant access), since the receiving application has no means, using only what this gem provides, to distinguish a genuine event about shop A from a replayed event maliciously labeled as shop A.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs at least one valid signed webhook body from the target app (most easily obtained by being a legitimate installer of the same public app on their own store — an unprivileged action requiring no leaked credentials). Once obtained, forging the `shop-domain` header on replay requires no secret at all, since the header is entirely outside the HMAC's scope. Any host app following the documented pattern of trusting `data.shop` (as literally shown in the gem's own docs example) is exposed.

### Recommendation
Do not trust `request.shop`/`WebhookMetadata#shop` as an authenticated tenant identifier. At minimum, the library should either (a) include the shop-domain (and topic/webhook_id) header values in the HMAC-signable string so they are cryptographically bound to the request, or (b) explicitly document that `shop` is unauthenticated and instruct integrators to cross-check it against an existing session/shop record for that install, plus dedupe on `webhook_id`, before acting on the payload. The current documentation's claim that `process` "will verify the request did indeed come from Shopify" should be corrected to clarify that only the body is verified.

### Proof of Concept
1. Install the target Shopify app (using this gem) on attacker-controlled store `attacker.myshopify.com`. Trigger a webhook event (e.g. `orders/create`) and capture the raw POST: headers `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, and the raw JSON body `B`.
2. Resend the exact same body `B` with the exact same `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` yields `shop == "victim.myshopify.com"`; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches the still-valid signature, so validation passes.
4. The handler's `WebhookMetadata` reports `shop: "victim.myshopify.com"` for attacker-controlled content `B`, and the app processes/enqueues work under the victim shop's identity as shown in the documented handler pattern (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
