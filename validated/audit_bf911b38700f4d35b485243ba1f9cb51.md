### Title
Webhook shop-domain spoofing due to identity field excluded from HMAC signature — ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts an unauthenticated HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) as the tenant identifier passed to the app's handler. Because the shop domain is never included in the signed content, an attacker who possesses one *valid* signed webhook payload/HMAC pair (e.g., from their own installed shop) can resend it with a different `shop-domain` header value and have the app process it as if it belonged to another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` attribute is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and, if it passes, forwards `request.shop` — the unauthenticated header value — directly into `WebhookMetadata` given to the app's handler: [3](#0-2) 

The identity binding that should hold is: `hmac_signed_content == content_the_app_trusts_for_tenant_attribution`. Here, the equality is broken: `hmac` is computed over `raw_body` only, while the app attributes the payload to `shop` taken from a header that is outside that signed content. Compare with the OAuth `AuthQuery`, where `shop` **is** included in `to_signable_string` and therefore is bound by the HMAC: [4](#0-3) 

This is the correct pattern that the webhook `Request` class fails to follow for the `shop` field.

### Impact Explanation
This crosses a tenant boundary: any party that can obtain one legitimately-signed webhook body (e.g., from a shop they themselves control, which installed the vulnerable app) can craft a new HTTP request reusing that exact `raw_body`/HMAC pair while substituting an arbitrary `shopify-shop-domain` header. `Registry.process` will accept it as valid (HMAC matches) and the app's `WebhookHandler` will receive `WebhookMetadata` claiming the payload is for the attacker-chosen shop. Depending on how the host application persists or acts on webhook data (common patterns: upserting records keyed by `shop`, triggering per-tenant side effects, redact/data-request compliance workflows), this enables cross-tenant data injection/confusion — writing or triggering actions attributed to a victim shop using attacker-controlled body content, or masking the true origin of sensitive payloads (e.g., `customers/data_request`, `shop/redact`).

### Likelihood Explanation
Requires only an unprivileged attacker who can install the app on their own shop (or otherwise obtain one valid webhook body+HMAC, e.g. via disclosure) and can send arbitrary HTTP requests to the app's webhook endpoint with a forged header — no access to `api_secret_key`, access tokens, or privileged accounts is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the HMAC-signed content, or otherwise cryptographically bind the `shop` value that is forwarded to handlers, e.g. by deriving `to_signable_string` from a canonical combination of body and the trusted webhook headers, or by requiring the host app to independently verify `shop` against a known/authorized store list before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker resends the same `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and succeeds, since the body/HMAC pair is untouched: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_from_B, ...)` — i.e., attacker-controlled body content is now attributed to the victim shop, with no cryptographic tie between `shop` and the signed content.
