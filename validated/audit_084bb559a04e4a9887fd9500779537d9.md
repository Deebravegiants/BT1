### Title
Unset `challengePeriod` in `EvmHost` fully disables the fraud-proof veto window, allowing forged message delivery - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2` gates the delivery of `PostRequest`s, `GetResponse`s, and both timeout message types behind a challenge-period check that reads `host.challengePeriod()`. If the admin never sets `challengePeriod` for a state machine (it defaults to `0` in `HostParams`), the guard is silently skipped entirely rather than falling back to a safe minimum or reverting, letting any relayer deliver messages the instant a state commitment is stored.

### Finding Description
`HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` all perform the same check before accepting a relayer-submitted MMR/state proof: [1](#0-0) 

```
uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
```

The same `challengePeriod != 0 && ...` pattern is repeated for `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`. [2](#0-1) [3](#0-2) [4](#0-3) 

`challengePeriod` is a plain `uint256` field of `HostParams`, with no enforced minimum and no revert-on-unset semantics: [5](#0-4) 

Because Solidity uninitialized `uint256` values are `0`, and `HostParamUpdate`/`EvmHostParamUpdate` treat `challenge_period` as an `Option` that is simply not applied when omitted, any deployment or governance update that forgets to explicitly configure a non-zero `challengePeriod` for a given state machine leaves the check permanently disabled (`challengePeriod != 0` evaluates false), rather than defaulting to a safe non-zero value or rejecting the configuration: [6](#0-5) 

The challenge period exists specifically to give fishermen/watchers a window to submit a fraud proof and veto a maliciously or incorrectly finalized state commitment before it is relied upon. This is exactly analogous to the reported Blueberry bug: an unset safety threshold (`liquidationThreshold` there, `challengePeriod` here) does not block the action that depends on it (`openPosition` there, message delivery here) — it silently degrades to a value that removes the protection, letting the system proceed in an unsafe state that looks locally valid but is not actually safe.

### Impact Explanation
If `challengePeriod` is left unset (0) for any connected state machine — whether by oversight during initial deployment/host-param configuration or via a subsequent `updateHostParams`/`HostExecutive::set_host_params` call that doesn't specify it — any relayer can immediately submit `handlePostRequests`/`handleGetResponses`/timeout messages the moment a (possibly fraudulent) state commitment is stored, with zero time for a fisherman to veto it. This permits forged/fraudulent message delivery to `IApp` modules based on state commitments that would otherwise have been challenged and reverted, directly enabling unbacked mint/theft-style exploitation of any application relying on Hyperbridge's finality guarantees on that route.

### Likelihood Explanation
This requires only an operational misconfiguration (a state machine's `challengePeriod` never being explicitly set to a non-zero value), which is a low bar compared to a malicious-admin scenario — it can happen from a simple omission in a `updateHostParams`/`set_host_params` call, since the field has no forced minimum and silently defaults to `0`. Once misconfigured, the exploit path is fully permissionless: any relayer can submit the affected handler functions immediately after any consensus update.

### Recommendation
- Enforce a minimum non-zero `challengePeriod` at the point host params are set (reject `0` explicitly, or clamp to a `MIN_CHALLENGE_PERIOD` constant), instead of allowing `challengePeriod == 0` to silently bypass the `HandlerV2` guard.
- Alternatively, change the `HandlerV2` check from `challengePeriod != 0 && challengePeriod > delay` to unconditionally `challengePeriod > delay`, and ensure `challengePeriod` can never be persisted as `0` for a live state machine.

### Proof of Concept
1. Admin deploys/updates `EvmHost` `HostParams` for a state machine but omits `challengePeriod` (or omits it in `updateHostParams`), leaving it at the default `0`.
2. Hyperbridge's consensus client submits a new state machine commitment for that state machine via `HandlerV2.handleConsensus`/proof verification, storing it with `host.storeStateMachineCommitment`.
3. An attacker-controlled relayer immediately (same block) calls `handlePostRequests` with a `PostRequestMessage` whose MMR proof verifies against the just-stored (potentially fraudulent) `overlayRoot`.
4. In `handlePostRequests`, `delay = 0`, `challengePeriod = 0` ⇒ `challengePeriod != 0` is `false` ⇒ the `ChallengePeriodNotElapsed` revert is skipped, and `host.dispatchIncoming(leaf.request, _msgSender())` executes immediately, before any fisherman had a chance to veto the commitment.

struct HostParams {
    // The fee token contract address. This will typically be DAI.
    // but we allow it to be configurable to prevent future regrets.
    address feeToken;
    // The admin account, this only has the rights to freeze, or unfreeze the bridge
    address admin;
    // Ismp message handler contract. This performs all verification logic
    // needed to validate cross-chain messages before they are dispatched to local modules
    address handler;
    // The authorized host manager contract, is itself an `IApp`
    // which receives governance requests from the Hyperbridge chain to either
    // withdraw revenue from the host or update its protocol parameters
    address hostManager;
    // The local UniswapV2Router02 contract, used for swapping the native token to the feeToken.
    address uniswapV2;
    // The unstaking period of Polkadot's validators. In order to prevent long-range attacks
    uint256 unStakingPeriod;
    // Minimum challenge period for state commitments in seconds;
    uint256 challengePeriod;
    // The consensus client contract which handles consensus proof verification
    address consensusClient;
    // State machines whose state commitments are accepted
    uint256[] stateMachines;
    // The state machine identifier for hyperbridge
    bytes hyperbridge;
}
