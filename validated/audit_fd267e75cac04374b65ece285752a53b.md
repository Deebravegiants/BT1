### Title
Webhook shop domain is not covered by HMAC, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC of the raw request body, but then trusts the `shop` (and `topic`/`webhook_id`) values taken from unauthenticated HTTP headers when dispatching to the app's handler. This breaks the binding "shop whose secret produced this signature" == "shop the handler is told the event came from."

### Finding Description
`Utils::HmacValidator.validate` verifies the request by calling `verifiable_query.to_signable_string` and comparing it against `verifiable_query.hmac`. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `hmac` is read straight from the `X-Shopify-Hmac-Sha256` header: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled from separate, unsigned HTTP headers: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and the other header-derived fields) to build the metadata passed to the app's registered handler — with no check that the `shop` header is bound to the HMAC-signed payload: [4](#0-3) 

Because the signature covers only the body bytes, not the headers, `HMAC(secret, body)` is identical regardless of which shop's `X-Shopify-Shop-Domain` header accompanies it. An unprivileged internet user who controls any Shopify store that has the target app installed (a "legitimate" but unprivileged tenant) can capture one of their own store's genuine webhook deliveries (valid body + valid HMAC for that body, computed with the app's own `client_secret`, which they never see or need), and replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different value in `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`). `Registry.process` will accept it as authentic and hand the attacker-controlled `shop` value straight to the app's handler.

This is the same bug class as the report's root cause — a value the code relies on for a security decision (attribution of the event to a specific shop) is not covered by the check that is supposed to authenticate it (the HMAC), so the two can diverge.

### Impact Explanation
Apps commonly key state changes off the webhook's `shop` value (e.g. marking an app as uninstalled, disabling billing, invalidating tokens, processing GDPR data-request/erasure webhooks, or writing per-shop data) as documented for consumers of `ShopifyAPI::Webhooks::WebhookMetadata#shop`. Since this library provides no binding between the authenticated body and the claimed shop, any app built on top of it that trusts `data.shop` from a validated webhook is exposed to cross-tenant confusion: one shop's legitimately-signed webhook can be replayed and misattributed to another shop, letting an attacker with only a free/dev store trigger shop-B-labeled side effects (e.g. forcing an uninstall/deauthorization workflow or corrupting another tenant's stored webhook data) without ever compromising shop B or the app's `client_secret`. This is a cross-tenant integrity issue rooted in the gem's own authentication primitive.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any Shopify store (something an unprivileged internet user can freely do via a development store), (2) capturing one legitimate webhook delivery (body + HMAC header) from that store, and (3) replaying it with a modified shop-domain header to the app's public webhook endpoint. No access to the app's `client_secret`, access tokens, or the victim shop is needed, and the vulnerable code path (`Registry.process` / `Webhooks::Request`) is exercised on every webhook delivery apps process through this gem.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id/api-version) in the value that is authenticated, or otherwise cryptographically bind the claimed `shop` to the signed body before it is exposed to handler code — e.g., require callers to pass the shop obtained via out-of-band verification (matching against a previously stored, authenticated session/shop) rather than trusting the header value populated only from `X-Shopify-Shop-Domain`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC check and must be cross-checked against the app's own installed-shop records before use in security-relevant decisions.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker-shop.myshopify.com"
# and receives a legitimate webhook delivery, e.g.:
body = '{"id":123,"some":"legit payload"}'
valid_hmac = <captured from X-Shopify-Hmac-Sha256 header of the real delivery>

# Attacker replays the exact same body + hmac to the app's public webhook
# endpoint, but swaps the shop-domain header:
headers = {
  "x-shopify-topic" => "app/uninstalled",       # can also be swapped freely
  "x-shopify-hmac-sha256" => valid_hmac,        # unchanged, still valid for `body`
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks `body`,
# and the registered handler receives WebhookMetadata with
# shop: "victim-shop.myshopify.com" even though the request never
# originated from that shop.
``` [4](#0-3) [5](#0-4)
