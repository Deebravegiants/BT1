### Title
Rounding-induced underflow panics in `target_orders.calc_pnl_x`/`calc_pnl_y` updates can revert `Deposit`/`Withdraw`/`WithdrawPnl` - (File: program/src/processor.rs)

### Summary
`Processor::calc_take_pnl` and the `Deposit`/`Withdraw`/`WithdrawPnl` handlers perform multiple independent, non-idempotent decimal-scaling roundings (`normalize_decimal_v2` / `restore_decimal`, both floor-only integer divisions) and then combine the results with `.checked_sub(...).unwrap()` on `target_orders.calc_pnl_x` / `target_orders.calc_pnl_y`. As in the referenced `ERC20RebaseDistributor` bug class, chained roundings computed via different paths can make the subtrahend momentarily larger than the minuend, causing the `unwrap()` to panic and abort the whole instruction.

### Finding Description
`calc_take_pnl` computes `delta_x`/`delta_y` directly in normalized (`sys_decimal_value`) units: [1](#0-0) 

but the amount actually deducted from the raw pool balances (`pc_pnl_amount`/`coin_pnl_amount`) is derived through a *different* rounding path: `diff_x` is first restored to native decimals (`restore_decimal`, floor) and only then scaled by the pnl ratio (floor again): [2](#0-1) 

`normalize_decimal_v2` and `restore_decimal` are both single-direction (floor) integer-division based, and are not exact inverses of each other because of double/triple rounding: [3](#0-2) 

In `process_withdraw`, after `calc_take_pnl` mutates `total_pc_without_take_pnl`/`total_coin_without_take_pnl` in place, the withdrawn `coin_amount`/`pc_amount` are computed from the pnl-adjusted totals via `InvariantPool::exchange_pool_to_token` (floor), and then `target_orders.calc_pnl_x`/`calc_pnl_y` are recomputed as:

```
target_orders.calc_pnl_x = x1
    .checked_sub(normalize_decimal_v2(pc_amount, pc_decimals, sys_decimal_value))
    .unwrap()
    .checked_sub(U128::from(delta_x))
    .unwrap();
``` [4](#0-3) 

`x1` is the *pre*-pnl-adjustment normalized value of `total_pc_without_take_pnl`, while `delta_x` was computed via the "ratio-first" path and `normalize_decimal_v2(pc_amount, ...)` was derived via the "restore-then-ratio-then-normalize" path off the *post*-pnl-adjustment total. Because floor-division subtraction is not associative/monotonic across independently-rounded quantities (`floor(a·k) − floor(b·k)` can exceed `floor((a−b)·k)`), it is possible for `normalize_decimal_v2(pc_amount,...) + delta_x` to exceed `x1` by a small amount, causing either `checked_sub` to return `None` and `.unwrap()` to panic. The identical pattern (`x1.checked_add(...).checked_sub(U128::from(delta_x)).unwrap()`, `.checked_sub(U128::from(delta_y)).unwrap()`) appears again in `process_deposit`: [5](#0-4) 

and in `process_withdrawpnl`: [6](#0-5) 

The developers' own precision test exercises exactly this multi-step rounding chain but does not assert against the underflow case, and does not sweep over adversarial `withdraw.amount` / timing combinations that would be needed to trigger the edge case: [7](#0-6) 

### Impact Explanation
A panic inside a Solana program instruction aborts the whole transaction (equivalent to a Solidity revert). If a rounding-driven mismatch occurs for a given pool state and requested withdraw/deposit amount, that specific `Withdraw`/`Deposit`/`WithdrawPnl` call reverts, denying the LP or the `pnl_owner` the ability to complete that operation until the pool's `need_take_pnl_*`/`calc_pnl_x`/`calc_pnl_y` state (which continuously drifts with every swap) shifts enough to clear the rounding collision — exactly the "temporary DoS" pattern described in the source report. Because `Withdraw` is the only path by which an LP can redeem their share of the pool, an LP whose specific withdrawal amount collides with this rounding edge case is temporarily unable to exit their position, which is a funds-availability (temporary freezing) issue rather than a loss of funds, since no partial state is committed on panic.

### Likelihood Explanation
Reachability only requires an unprivileged LP submitting an ordinary `Withdraw` (or any account submitting `Deposit`/permissioned `WithdrawPnl`) instruction on a pool that has previously accrued `need_take_pnl_*` via swaps — no privileged signer, no malicious validator, and no off-chain component is needed. However, unlike the original C4 report which included a concrete, reproducible Foundry PoC demonstrating the exact underflow, I was not able to construct or verify a concrete numeric example that triggers a negative `checked_sub` in this codebase's specific integer arithmetic (the analysis above shows the theoretical possibility via floor-subtraction non-monotonicity, but confirming an actual reachable input set requires exhaustively simulating `calc_take_pnl` + `exchange_pool_to_token` with real `pc_decimals`/`coin_decimals`/`sys_decimal_value`/`pnl_numerator`/`pnl_denominator` values, which I could not do with the available read-only tools). This uncertainty should be resolved with fuzzing/property-based testing (e.g., proptest over `total_pc/coin_without_take_pnl`, `calc_pnl_x/y`, `withdraw.amount`, and fee ratios) before treating this as confirmed-exploitable rather than a plausible rounding-safety gap.

### Recommendation
- Replace `.checked_sub(...).unwrap()` on `calc_pnl_x`/`calc_pnl_y` in `process_deposit`, `process_withdraw`, and `process_withdrawpnl` with saturating subtraction (clamped to zero) or otherwise tolerate rounding fluctuations, as recommended in the source report.
- Ensure `delta_x`/`delta_y` (normalized units) and `pc_pnl_amount`/`coin_pnl_amount` (raw units, later re-normalized) are derived through a single consistent rounding path so they can never diverge.
- Add property-based/fuzz tests asserting that `calc_pnl_x`/`calc_pnl_y` updates never underflow across the full space of decimals, pnl ratios, and withdraw/deposit amounts.

### Proof of Concept
No concrete triggering input set was constructed/verified with available tools; a Rust unit test analogous to `test_calc_pnl_precision` (program/src/processor.rs:3090) that fuzzes `pc_decimals`, `coin_decimals`, `sys_decimal_value`, `pnl_numerator`/`pnl_denominator`, and `withdraw.amount` around the boundary where `normalize_decimal_v2(pc_amount,...) + delta_x` approaches `x1` would be needed to confirm reachability, mirroring the C4 PoC methodology.

    pub fn normalize_decimal(val: u64, native_decimal: u64, sys_decimal_value: u64) -> u64 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = Self::to_u64(
            ret_mut
                .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
                .unwrap()
                .as_u128(),
        )
        .unwrap();
        ret
    }

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }
