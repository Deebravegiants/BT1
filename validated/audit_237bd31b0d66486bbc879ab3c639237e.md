Audit Report

## Title
Cross-Workflow HTTP Response Cache Poisoning/Disclosure via Workflow-ID-Agnostic Cache Key - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's HTTP action `responseCache` keys entries solely by `OutboundHTTPRequest.Hash()`, which per the struct's own documentation and the `TestRequestHash` test suite incorporates method/URL/headers/body/`WorkflowOwner` but explicitly excludes `WorkflowID`. Two distinct workflows deployed under the same owner that issue an HTTP action with identical method/URL/headers/body collide on the same cache entry, contradicting the component's documented "Workflow Isolation" guarantee and allowing one workflow to read, poison, or force eviction of another workflow's cached HTTP response.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` both key the cache map exclusively by `req.Hash()`: [2](#0-1) [3](#0-2) 

The struct's own comment states the hash is derived from "method, URL, headers, body, workflowOwner" — `WorkflowID` is not part of it: [4](#0-3) 

This is confirmed directly by `TestRequestHash`, which explicitly asserts that differing `WorkflowID` produces the *same* hash while differing `WorkflowOwner` produces different hashes: [5](#0-4) [6](#0-5) 

Yet the module's README explicitly documents per-workflow isolation as a security property: "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage": [7](#0-6) 

The `gatewayHandler` maintains a single shared `responseCache` instance used directly for every incoming `OutboundHTTPRequest` regardless of `WorkflowID`, dispatched from `makeOutgoingRequest`: [8](#0-7) 

No other layer in the request path (rate limiting, JSON-RPC parsing, or the cache itself) reintroduces `WorkflowID` into the key — the cache is a flat `map[string]*cachedResponse` keyed only by `req.Hash()`. Consequently, any two workflows under the same owner that issue byte-identical HTTP action requests share one cache slot, so a request from Workflow A can populate, be read by, or evict the entry consulted by Workflow B.

## Impact Explanation
This is a genuine cross-workflow response confusion bug within the gateway's HTTP action handling path. A workflow can:
- Read another (sibling, same-owner) workflow's previously cached HTTP response by issuing an identical request with `MaxAgeMs > 0` (disclosure).
- Overwrite the shared entry via `Set`/`Fetch` with `Store=true`, causing the other workflow to receive stale or attacker-influenced cached data (poisoning/integrity).
- Trigger premature/unexpected cache misses for the sibling workflow since `storedAt`/TTL bookkeeping is also per-hash, not per-workflow.

This matches the "cross-user response corruption" impact class in scope. Severity is bounded by the requirement that colliding workflows share the same `WorkflowOwner`, and by cache contents being limited to the HTTP action's external response payload rather than credentials or secrets.

## Likelihood Explanation
Deploying multiple workflows under one owner is a normal, low-privilege operation available to any workflow author. Constructing two workflows whose HTTP action method/URL/headers/body and `CacheSettings` are identical is trivial and fully attacker-controlled, requiring no elevated permission, network position, or victim interaction — only the ability to author and deploy workflow code, which is the baseline capability assumed for this component.

## Recommendation
Include `WorkflowID` in the cache key computed by `OutboundHTTPRequest.Hash()` (or otherwise incorporate `WorkflowID` into the `responseCache` map key, e.g., prefixing/concatenating it with the existing hash), and update the `response_cache_test.go` assertions and README to reflect true per-workflow isolation instead of documenting a guarantee the implementation does not provide.

## Proof of Concept
1. Deploy Workflow A and Workflow B under the same `WorkflowOwner`.
2. From Workflow A's HTTP action, send an `OutboundHTTPRequest` to `https://victim.example/api` with identical method/URL/headers/body, `CacheSettings.Store = true`, `MaxAgeMs = 600000`. The gateway calls `h.responseCache.Set(req, outboundResp)` (or `Fetch` with `storeOnFetch=true`), storing the response under `req.Hash()`.
3. From Workflow B (different `WorkflowID`, same owner), send the identical request with `CacheSettings.MaxAgeMs > 0`. Because `Hash()` ignores `WorkflowID`, `responseCache.Fetch` returns Workflow A's cached response to Workflow B without contacting the external endpoint.
4. This is directly reproducible as a unit test extension of the existing `TestRequestHash` "having different workflowID results in same Hash" case at `response_cache_test.go:139-149`, or as an integration test against `gatewayHandler.makeOutgoingRequest` asserting that two `OutboundHTTPRequest`s with different `WorkflowID` but identical other fields return the same cached `OutboundHTTPResponse`.
