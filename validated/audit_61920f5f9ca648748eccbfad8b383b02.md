### Title
Unbounded `Order.inputs` / `Order.output.assets` array length in `IntentGatewayV2.placeOrder` enables gas-griefing DoS that can permanently freeze escrowed intent funds - (File: evm/src/apps/IntentGatewayV2.sol, evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` only validates that `order.inputs.length != 0` and rejects duplicate output tokens; it enforces no upper bound on the number of `TokenInfo` entries in `order.inputs` or `order.output.assets`. Every downstream consumer of the order — `fillOrder`'s length-matching check, the per-token escrow bookkeeping, and `IntentsBase._withdraw`'s release/refund loop — iterates once per array element and performs an external token transfer per iteration. This is structurally identical to the reNFT `_processBaseOrderConsideration` bug: an attacker-controlled array with no size cap that a *different* party (the solver filling the order, or whoever triggers escrow release/refund) must pay to iterate over, at a cost far higher than what it took to create.

### Finding Description
`placeOrder` escrows one `TokenInfo` entry per element of `order.inputs`, keyed by `(commitment, token)`: [1](#0-0) [2](#0-1) 

There is no maximum-length check anywhere in this function — only a `== 0` guard on `order.inputs.length`, and a duplicate-token guard on `order.output.assets` via transient storage: [3](#0-2) 

`fillOrder` requires `order.inputs.length == order.output.assets.length == options.outputs.length`, so the same unbounded size propagates to the fill path with no cap enforced there either: [4](#0-3) 

Finally, whichever party finalizes the order — a solver's fill or a cancellation/refund — must go through `_withdraw`, which loops once per token in `body.tokens` and performs an external `.call`/`safeTransfer` per iteration: [5](#0-4) 

An order placer can therefore create an order with thousands of dust-value `TokenInfo` entries (e.g., 1 wei each of a cheap ERC-20) in `order.inputs`/`order.output.assets`. Any solver who wants to fill the order — or the RedeemEscrow/RefundEscrow flow dispatched cross-chain through Hyperbridge and processed via `onAccept` → `_withdraw` — must pay gas proportional to the number of entries to complete a single transaction. This exactly mirrors the reNFT root cause: `_processBaseOrderConsideration` had no cap on `considerations.length`, so `Stop::stopRent()`'s settlement loop could be made arbitrarily expensive by whoever created the order.

### Impact Explanation
If the array is large enough, the transfer loop inside `_withdraw` (invoked by `fillOrder`'s settlement path and by the cross-chain `RedeemEscrow`/`RefundEscrow` `onAccept` handler) can push the required gas above the destination chain's block gas limit. In that case:
- No solver can ever profitably (or at all) fill the order, since the fill transaction cannot fit in a block.
- The escrowed input tokens locked by `placeOrder` (`_orders[commitment][token]`) can become permanently unreleasable — neither fillable nor refundable — because both the fill-and-settle path and the cancel/refund path route through the same unbounded `_withdraw` loop.
- This satisfies "permanent freezing of funds" and a "route unable to deliver messages" (the cross-chain RedeemEscrow/RefundEscrow message becomes undeliverable once decoded and dispatched to `_withdraw`), which are explicitly in-scope high-impact outcomes for the intents escrow bug class.

Even short of hitting the hard gas-limit wall, this is at minimum a severe griefing vector: the order placer pays comparatively little to create the order (`placeOrder`'s loops are the same size but touch only storage writes and cheap transfers for a self-controlled token), while any solver attempting to fill must pay for the entire matching-length transfer loop in `_fillSameChain`/`_fillCrossChain` plus `_withdraw`, asymmetrically inflating solver cost — the same "attacker pays little, victim pays exponentially more to unwind" dynamic as the original finding.

### Likelihood Explanation
This is directly reachable by any unprivileged user calling `placeOrder` with a crafted `Order` struct — no special permissions, no privileged role, and no reliance on malicious admin/governance/relayer behavior. The only cost to the attacker is gas to place the order and (optionally) trivial amounts of a cheap ERC-20 token per array entry, exactly analogous to the "tip 5000 x 1 wei" pattern in the original finding. Given Solidity/EVM per-call gas limits are well within reach with a few thousand array entries (as demonstrated in the original PoC's 3000–5000 item benchmark), this is practically achievable on any EVM chain Hyperbridge's `IntentGatewayV2` is deployed to.

### Recommendation
Add an explicit, protocol-level maximum on `order.inputs.length` and `order.output.assets.length` in `placeOrder` (and correspondingly validate it wherever `Order` structs are decoded from cross-chain messages in `onAccept`), e.g.:
```solidity
if (order.inputs.length == 0 || order.inputs.length > MAX_ORDER_ITEMS) revert InvalidInput();
if (order.output.assets.length > MAX_ORDER_ITEMS) revert InvalidInput();
```
Choose `MAX_ORDER_ITEMS` conservatively based on the worst-case gas cost of `_withdraw`'s and the fill loops' external transfers, ensuring the resulting worst-case fill/withdraw transaction stays comfortably under the target chain's block gas limit.

### Proof of Concept
Conceptual PoC (mirrors the reNFT PoC structure):
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.inputs` containing N (e.g., 3000–5000) `TokenInfo` entries, each specifying a trivial amount (e.g., 1 wei) of a cheap/self-controlled ERC-20, and `order.output.assets` populated with a matching-length array of distinct dummy output tokens (required by `fillOrder`'s length check at `IntentGatewayV2.sol:475-476`).
2. `placeOrder` succeeds, looping N times to transfer/escrow each input and writing N entries into `_orders[commitment][token]` (`IntentGatewayV2.sol:364-373`), at a per-entry cost the attacker controls (can be minimized since the tokens are attacker-supplied/cheap).
3. A solver attempts `fillOrder`, which requires supplying N matching `options.outputs` and drives execution into `_fillSameChain`/`_fillCrossChain`, which — like `_withdraw` (`IntentsBase.sol:451-470`) — must iterate and transfer once per array element.
4. With N large enough, the solver's `fillOrder` transaction (or the cross-chain `RedeemEscrow`/`RefundEscrow` `onAccept` call that eventually invokes `_withdraw`) exceeds the destination chain's block gas limit and can never be mined, leaving the escrowed input tokens permanently stuck — unfillable and unrefundable.

I was unable to inspect the full bodies of `_fillSameChain` (ExtrinsicIntents.sol) and `_fillCrossChain`/`IntrinsicIntents.sol` in this session due to the tool budget running out, so the exact per-item gas cost of those loops is not independently confirmed here beyond the `grep_search` evidence showing repeated `inputs.length`/`outputs.length`/`assets.length` iteration sites in both files. A Devin session with full file access should confirm the precise loop bodies in `ExtrinsicIntents.sol`/`IntrinsicIntents.sol` to finalize the exact PoC gas numbers before remediation.
