### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the **raw request body**. The `shop` identity that the gem hands to the app's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed content. Any actor who can obtain one genuinely signed webhook (e.g., by installing the app to their own store) can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will report it as authentic and attribute it to the victim shop.

### Finding Description
The binding that should hold is:
`shop value trusted by HMAC verification == shop value delivered to the application handler`

In `lib/shopify_api/webhooks/request.rb`, `to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is parsed independently from a header that is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` performs exactly this body-only check, and then forwards the **unverified** `request.shop` header straight to the handler as the tenant identifier: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, a valid `(body, hmac)` pair obtained from a webhook delivered to the attacker's own shop remains valid no matter which `shop-domain` header value is attached to the replayed request. The gem provides no mechanism binding the verified bytes to the `shop` header, so the equality above is broken: the HMAC check passes on content that says nothing about which shop the event belongs to, while the app-facing `WebhookMetadata#shop` says whatever the attacker put in the header.

### Impact Explanation
This breaks the tenant boundary this gem is supposed to enforce for webhook delivery: the "Critical - cross-tenant access" impact category applies. An application built on this gem that keys off `WebhookMetadata#shop` (as documented/intended, see `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`) can be made to apply a spoofed shop's webhook data (order/customer/app-uninstalled events, etc.) to a different, victim shop's records, without the attacker ever needing the victim's access token, refresh token, or the app's `client_secret`.

### Likelihood Explanation
Any unprivileged internet user can install a public Shopify app to their own development/free store, capture one legitimately HMAC-signed webhook delivered to them (bodies for many topics are attacker-fully-controlled, e.g. `app/uninstalled`, or at least attacker-triggerable), and replay that exact body/HMAC pair to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. No TLS interception, credential theft, or privileged account is required — only normal use of the app installation flow that is available to any merchant.

### Recommendation
Bind the shop identity into what is actually verified: reject requests where the shop header cannot be cryptographically tied to the signed content, e.g. include `shop-domain` (and `topic`) in the signable string used for HMAC verification, or require the caller (the host application) to independently corroborate `request.shop` against a known, previously-authenticated shop record (e.g., an existing offline session) before trusting it, and document this requirement prominently since the current API silently returns an unauthenticated `shop` value from `Webhooks::Request#shop`.

### Proof of Concept
1. Install the target app to attacker-owned store `attacker.myshopify.com`.
2. Trigger any webhook topic the app is subscribed to (e.g. `app/uninstalled`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` — `H = HMAC-SHA256(client_secret, B)`.
3. Replay a new HTTP request to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`.
5. `Registry.process` calls the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data as if it originated from the victim shop.
