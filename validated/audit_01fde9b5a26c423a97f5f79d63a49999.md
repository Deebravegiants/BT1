This is a strong, concrete analog to the report's bug class ("a field acted on but not covered by the HMAC"): the webhook's `shop` (and `topic`, `webhook_id`, `api_version`) come from HTTP headers that are entirely outside the HMAC signature's scope, since the signature only covers the raw body.### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but `to_signable_string` — the data actually protected by the HMAC — returns only the raw request body. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to route the payload to the app's webhook handler. This breaks the intended binding: `shop authenticated by HMAC == shop the handler acts on`.

### Finding Description
`Request#to_signable_string` is defined as just the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which, per `HmacValidator#validate_signature`, only compares `verifiable_query.to_signable_string` (the body) against the signature — and then immediately hands `request.shop` (and topic/webhook_id/api_version) straight to the registered handler: [3](#0-2) [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is the same across every shop installing the app, an HMAC that is valid for one shop's webhook body is also a valid HMAC for the *same body* sent with a different `shop-domain` header. This is exactly the report's bug class: a field the code acts on (`shop`, used to identify which merchant's data this is) is not covered by the value that is cryptographically bound (`hmac` over `body` only).

### Impact Explanation
An unprivileged attacker who has access to at least one shop installing the target app (e.g., a free/dev store) can register a webhook to a URL they control, capture a legitimate `(raw_body, hmac-sha256)` pair from that webhook delivery, and then replay it to the app's real webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to point at a victim shop. `HmacValidator.validate` will still return `true` (it never inspects the shop header), and `Registry.process` will dispatch the handler with `WebhookMetadata` claiming the data belongs to the victim shop. Any app logic that trusts `data.shop` to select the shop's stored access token, mutate the shop's local record, or short-circuit multi-tenant authorization creates cross-tenant data confusion/injection — data or events attributed to a shop that never sent them.

### Likelihood Explanation
Requires only (a) ability to install/register a webhook on one's own shop (freely available to any developer/attacker), and (b) a webhook topic whose body content doesn't itself embed/verify the shop (many bodies are generic JSON payloads with no shop identifier inside, e.g., `products/create`, `orders/create` for a specific object id). No access to the target's `api_secret_key` or access tokens is needed — only the shared secret already known implicitly through the attacker's own legitimate webhook deliveries (which are signed for them, but with the same per-app secret).

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the material verified by the HMAC, or otherwise cryptographically tie the header-derived shop domain to the specific delivery. At minimum, the gem should document/require that consuming apps cross-check `request.shop` against the shop context under which the webhook was expected (e.g. only accept payloads for shops with an active, matching subscription record), rather than presenting `WebhookMetadata#shop` as a value verified by `Utils::HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target Shopify app on Shop A (a store the attacker controls) and lets the app register `orders/create` (or any topic with no shop-identifying data in the body) to `https://attacker-controlled-relay.example/webhooks`.
2. Attacker triggers an order create on Shop A; Shopify POSTs the raw JSON body plus header `X-Shopify-Hmac-Sha256: <hmac>` and `X-Shopify-Shop-Domain: shop-a.myshopify.com` to the relay.
3. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` header to the real app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the unchanged raw body) and matches — validation passes.
5. The registered handler executes with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, causing the app to process/store data as if it originated from `victim-shop`, despite never having received anything from that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
