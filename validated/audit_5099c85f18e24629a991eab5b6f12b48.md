### Title
Permissionless Pool-Creation Front-Running via `Initialize2` Enables Permanent DoS and Attacker-Controlled Initial Price - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives the AMM pool account, LP mint, target-orders account, and coin/pc vaults as PDAs seeded only by `market_info.key` (an arbitrary, attacker-supplied "seed" account, not tied to the caller's identity), and creates + initializes all of these accounts atomically inside a single, fully permissionless instruction. Because the instruction accepts caller-chosen `init_coin_amount`/`init_pc_amount` and any signer can invoke it for a given market seed, an attacker can observe a pending legitimate `Initialize2` transaction for a given market/token pair and front-run it, permanently claiming the deterministic pool address with a self-chosen (skewed) initial price and becoming the sole minted LP holder, while the legitimate creator's transaction fails with `AlreadyInUse`.

### Finding Description
`process_initialize2` computes the AMM info, target orders, LP mint, and vault addresses via `get_associated_address_and_bump_seed`, which uses `program_id`, `market_info.key`, and a fixed seed string — nothing that binds the address to a specific "legitimate" creator: [1](#0-0) 

The market account passed in is explicitly documented as not needing to be a real market — "Just a seed for AMM account. Can be any account" — and is not required to be signed or owned by any privileged party: [2](#0-1) 

Inside a single call, the instruction creates the AMM, target-orders, LP-mint, and vault accounts and immediately initializes them (mints LP tokens, sets `amm.status`, records vaults/mints) with the caller-controlled `init.init_pc_amount` / `init.init_coin_amount`: [3](#0-2) [4](#0-3) [5](#0-4) 

The only re-entrancy guard is a check that the AMM account is still `Uninitialized`; once any first caller succeeds, subsequent calls for the same `market_info` seed fail permanently: [6](#0-5) 

Because the instruction is entirely permissionless (only requires `user_wallet_info.is_signer`, with no check that the wallet corresponds to any "intended" creator) and the mints, vault authority etc. checks only validate internal consistency rather than the identity of whoever is initializing, an attacker who sees a pending `Initialize2` transaction referencing a specific `market_info` account in the mempool can submit their own `Initialize2` with the same `market_info`, their own tiny `init_coin_amount`/`init_pc_amount` (yielding an arbitrary initial price ratio), and get included first. This is the direct analog of the reported `NoteERC20.initialize()` front-running class: an unprivileged actor races to be the first "initializer" of a deterministically-addressed resource, permanently locking out the legitimate party and gaining effective control of the resource's initial state.

### Impact Explanation
- The legitimate pool creator's `Initialize2` transaction reverts with `AmmError::AlreadyInUse` once the attacker's transaction lands first, permanently preventing the intended pool from ever being created at that deterministic address for that market seed (Denial of Service on pool creation).
- The attacker becomes the sole minted LP holder of the newly created pool (`user_lp_amount = liquidity - 10^decimals`, minted to the attacker's own ATA) and can set the pool's *initial* coin/pc ratio to any value they choose via `init_coin_amount`/`init_pc_amount`, effectively controlling the genesis price. This can be leveraged to profit if any downstream integrator/UI resolves the pool for that market and unknowing users deposit/swap against the skewed reserves before anyone notices the pool was created by an unrelated party.
- Fixed protocol-level fields such as `amm.amm_owner` and `create_pool_fee_address` are program constants, not attacker controlled, so this is not a full "take ownership of admin rights" exploit, but the combination of permanent pool-creation DoS plus attacker-controlled initial liquidity/price for a specific market is a concrete fund/price-integrity impact matching the reported bug class (front-running an atomic create+initialize step).

### Likelihood Explanation
High. Front-running is trivially achievable on Solana by any party monitoring the mempool/leader schedule for `Initialize2` transactions referencing a not-yet-initialized `market_info` seed, since the instruction requires no special permissions, no existing account ownership by the "real" creator, and no prior on-chain reservation of the market/pool pairing. The cost to the attacker is minimal (a small token deposit plus the one-time `create_pool_fee`).

### Recommendation
Bind the pool-creation PDA derivation (or add an explicit authorization check) to the actual creator's identity or to a pre-registered/reserved market so that an arbitrary third party cannot preempt initialization of a pool tied to a specific market seed. Alternatively, require that `market_info` be a genuine market account owned by the expected market program (rather than "can be any account"), and/or allow the legitimate creator to reserve/verify the market before broadcasting the funded `Initialize2` transaction, removing the race window entirely.

### Proof of Concept
1. Alice prepares a legitimate `Initialize2` transaction for a new pool using `market_info = M`, `amm_coin_mint = X`, `amm_pc_mint = Y`, and a fair `init_coin_amount`/`init_pc_amount` ratio, and broadcasts it.
2. Attacker Bob observes the pending transaction (mempool/RPC), and derives the same deterministic AMM/target-orders/LP-mint/vault PDAs using `get_associated_address_and_bump_seed(program_id, M, seed, program_id)` [1](#0-0) .
3. Bob submits his own `Initialize2` instruction with the same `market_info = M`, his own `amm_coin_mint`/`amm_pc_mint` (or the same mints if he wants to actually intercept Alice's specific token pair) and a minimal, heavily skewed `init_coin_amount`/`init_pc_amount`, paying only the flat `create_pool_fee`, and gets it included first (e.g., with a higher priority fee).
4. Bob's transaction succeeds: the AMM account transitions out of `Uninitialized` [6](#0-5) , vaults/LP mint are created and populated, and Bob is minted the entire initial LP supply at his chosen price ratio [4](#0-3) .
5. Alice's original transaction is processed afterward, loads the same AMM account, finds `amm.status != Uninitialized`, and reverts with `AmmError::AlreadyInUse` [7](#0-6) , permanently preventing her from creating the pool at that deterministic address for market `M`.
