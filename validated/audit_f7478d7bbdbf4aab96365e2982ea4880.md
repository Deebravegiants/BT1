### Title
Webhook HMAC only authenticates the request body, not the `shop`, `topic`, or `webhook_id` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as fully authenticated once `Utils::HmacValidator.validate(request)` returns true. In reality, the signable string used for that check is only the raw HTTP body, so the shop domain, topic, and webhook id headers that are handed to the app's handler are never covered by the HMAC and can be freely set by whoever sends the HTTP request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e. the body) and compares it to the `hmac` field: [3](#0-2) 

`Registry.process` uses this single check as its entire authentication gate, then forwards the unauthenticated `shop`/`topic`/`webhook_id` header values to the app's handler as if they were verified: [4](#0-3) 

The gem's own documentation tells developers that calling `Registry.process` "will verify the request did indeed come from Shopify," and explicitly instructs handlers to trust `data.shop` as "The shop domain of the webhook": [5](#0-4) [6](#0-5)  This is precisely the kind of documented, gem-provided guarantee that a host application is entitled to rely on — the gem, not the host app, is responsible for validating which fields are actually authenticated.

The broken identity binding is: `shop asserted in the `X-Shopify-Shop-Domain` header` (used by `Registry.process`/handlers as the tenant key) `≠` `shop bytes actually covered by the HMAC signature` (which is empty — only the body is signed). Any party capable of triggering a real webhook delivery to their own shop (any merchant who installs the app — an unprivileged internet actor with respect to other tenants) obtains a body + valid HMAC pair, then can re-POST that exact body/HMAC to the app's webhook endpoint while substituting a victim shop's domain (and an arbitrary registered topic/webhook id) in the headers. The signature still validates because it is only checked against the body, and the handler executes attacker-chosen data attributed to the victim tenant.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker who legitimately installs the app on their own store can forge webhook deliveries that the gem reports as fully verified but that carry an arbitrary victim `shop` value. Any handler that uses `data.shop` to select which tenant's records to create/update/delete (exactly as the gem's documentation recommends) can be tricked into writing attacker-controlled data into another merchant's tenant, or triggering mandatory-topic handlers (e.g. `shop/redact`, `customers/redact`) against a victim shop using attacker-authored payloads. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented handler pattern and trusts `data.shop`/`data.topic` without independently cross-checking them against its own session/tenant store, because the only requirement for the attacker is control of one legitimate, HMAC-issuing installation (their own store) plus the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint — no secrets, tokens, or privileged access to the victim tenant are required.

### Recommendation
Include the shop domain, topic, and webhook id in the signable string that is HMAC-verified (or otherwise cryptographically bind them, e.g. by having `HmacValidator`/`Webhooks::Request` fail closed unless the header-derived `shop` matches a shop the app has an active session for), so that `Registry.process` cannot be fed a validated body with a substituted tenant identity.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets Shopify deliver any subscribed webhook (e.g. `customers/redact`) to the app's webhook endpoint; this produces a body `B` and a valid `X-Shopify-Hmac-SHA256` header `H` computed only over `B`.
2. Attacker re-sends an HTTP POST to the same webhook endpoint with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id` matching a registered handler).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (no cross-check against `H`) and `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, which matches `H`, so `Registry.process` proceeds. [4](#0-3) 
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to act on victim-shop's tenant data using attacker-controlled `B`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
