### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let a single `msg.value` satisfy two independent `balanceDif` equations, minting shielded ETH without backing - (File: `contracts/Hinkal.sol`)

### Summary
`transact()` computes `oldBalances`/`newBalances` per index by re-querying the *same* global `address(this).balance` for every `erc20TokenAddresses[i] == address(0)` entry, and adds the full `msg.value` back into the equality check for *each* such index independently. Because `dimensionsCheck` and `checkOnchainCreation` in `HinkalHelper.sol` never assert that `erc20TokenAddresses` entries are unique, an attacker can list `address(0)` twice, deposit a single `msg.value = V`, and have the identical `balanceDif == amountChanges[i] + utxoAmount` equality satisfied twice — once per duplicate slot — minting `2V` worth of shielded UTXOs/credits for only `V` of real ETH.

### Finding Description
The equality that must hold is: **real ETH received by the contract (`msg.value = V`) must equal the sum of shielded value created across all slots that represent that ETH leg.** Instead, the code checks each slot independently without decrementing a "used" pool of `msg.value`.

Trace:
- `oldBalances = getBalancesForArray(circomData.erc20TokenAddresses)` is taken before `_internalTransact`/`_externalTransact` runs [1](#0-0) . Since ETH arrives atomically with the payable call, `oldBalances[i]` for `address(0)` already includes `msg.value`.
- `newBalances` is captured after the transfer loop [2](#0-1) . For a pure deposit (`deltaAmountChange > 0`, `_to == address(this)`), `transferERC20TokenFromOrCheckETH` only asserts `msg.value == _value` and performs no actual transfer [3](#0-2) , so `newBalances[i] == oldBalances[i]` for every ETH slot.
- The per-index check then computes, for **every** index where `erc20TokenAddresses[i] == address(0)`: `balanceDif = newBalances[i] + msg.value - oldBalances[i]`, which reduces to `balanceDif = msg.value = V` for **each** duplicated index [4](#0-3) .
- This `balanceDif` is then required to equal `amountChanges[i] + utxoAmount` (or `0 + utxoAmount` if `onChainCreation[i]`) [5](#0-4) . Since `balanceDif == V` for both duplicated indices, setting `amountChanges = [V, V, ...]` (or one off-chain `amountChanges[i]=V` and one on-chain UTXO of value `V` via `onChainCreation[j]=true`) makes **both** independent equations pass with only one real `V` of ETH ever deposited.
- `dimensionsCheck` only validates array lengths against `dimensions.tokenNumber`; it never asserts `erc20TokenAddresses` uniqueness [6](#0-5) . `checkOnchainCreation` only validates zero-amount/zero-nullifier invariants for `onChainCreation[i]==true` slots, not cross-slot token uniqueness [7](#0-6) .
- The circuit itself constrains `inTotal + amountChanges === outTotal` **per slot**, using the public `erc20TokenAddresses[i]` input for that slot only; it has no cross-slot uniqueness constraint, so a legitimately generated proof for two independent slots — both labelled `address(0)`, each self-consistent (`in=0, amountChanges=V, out=V`) — verifies without issue.

Because both `oldBalances`/`newBalances` are indexed reads of the *same* underlying contract-wide ETH balance (there is no per-slot ETH accounting), and `msg.value` is added back unconditionally in the formula for every ETH slot rather than being consumed once globally, the value-conservation invariant is broken.

### Impact Explanation
The attacker mints two shielded value units (e.g., two spendable UTXOs of `V` ETH each, or one off-chain `amountChanges` credit of `V` plus one on-chain UTXO of `V`) while only ever transferring `V` real ETH into the contract. This is direct protocol insolvency: the shielded pool's total claimed balance exceeds actual contract holdings by `V` per exploit transaction, and the extra `V` can later be withdrawn by spending the fabricated UTXO/nullifier, draining real funds deposited by other users. This matches the **Critical** category: minting shielded value without backing, direct protocol insolvency. The attack is repeatable every transaction, scaling insolvency linearly with each call (and further with more duplicate `address(0)` slots).

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: they choose `erc20TokenAddresses`, `amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`, and `outCommitments` arrays and generate their own valid proof for these self-consistent per-slot circuit inputs. No special tree state, root, or privileged role is required — only a normal `transact()` call with `msg.value = V` and a circuit proof that satisfies the (per-slot, not cross-slot) circuit constraints. This is low-cost, deterministic, and fully repeatable, making likelihood high once a valid witness/proof for the duplicated-slot input vector can be generated.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` entries in `dimensionsCheck` (or a dedicated check called from `performHinkalChecks`), rejecting any transaction where the same token address (including `address(0)`) appears more than once. Alternatively, restructure the balance-diff logic to track ETH consumption against a single shared `msg.value` budget across all slots rather than re-adding `msg.value` independently for each `address(0)` index.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` + `HinkalHelper` with a verifier that accepts a locally-generated proof for the crafted witness (or mock verifier if allowed for PoC purposes matching real circuit constraints per slot).
2. Build `circomData` with:
   - `erc20TokenAddresses = [address(0), address(0)]`
   - `amountChanges = [V, V]`
   - `onChainCreation = [false, false]`
   - `slippageValues = [V, V]`
   - matching `inputNullifiers`, `outCommitments`, `encryptedOutputs` arrays of equal per-slot length, each slot internally consistent for the circuit (`in=0, amountChanges=V, out=V`).
3. Call `hinkal.transact{value: V}(a, b, c, dimensions, circomData)` with `externalActionData.externalActionId == 0` (internal transact) and `externalAddress == attacker`.
4. Assert:
   - Real ETH transferred into contract == `V` (`address(hinkal).balance` increased by exactly `V`).
   - Both `balanceDif` checks in the loop pass (transaction does not revert).
   - Two commitments totaling `2V` of claimed shielded ETH value are inserted via `insertCommitments`.
   - Equality broken: `V (msg.value) != 2V (total amountChanges credited)`.
