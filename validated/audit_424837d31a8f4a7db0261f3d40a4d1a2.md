### Title
Emporium min-proof path lets any address execute unauthenticated, unaccounted `EmporiumStack` calls that drain standing ERC20 approvals - ([File: contracts/CircomDataBuilder.sol], [File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose corresponding circuit (`MainEVMCircuitMin.circom`) only proves `message == Poseidon(messageSeed)` and never constrains `calldataHash`/`outTimeStamp`. Combined with `EmporiumUpgradeable.verifyWallet` skipping all signature checks on `stack.ops` when `stack.signerAddress == address(0)`, and the balance-accounting loop in `runAction` iterating the (attacker-chosen, empty) `erc20TokenAddresses` array, an unprivileged attacker can force Emporium to execute arbitrary external calls from its own identity with zero accounting, stealing any standing ERC20 approval previously granted to the Emporium contract.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. This holds for the "normal" Emporium path (`erc20TokenAddresses.length > 0`), but breaks entirely on the "min" path.

Path:
1. `formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
This function only feeds `emporiumMessage`, `timeStamp`, `calldataHash` into the proof's public input vector: [2](#0-1) 

2. The corresponding circuit `MainEVMCircuitMin` never constrains `outTimeStamp` or `calldataHash` against anything - it only proves `message <== Poseidon(1)([messageSeed])`: [3](#0-2) 
Since `messageSeed` is a value the attacker freely chooses, and `calldataHash` is merely `keccak256` over data the attacker fully controls (checked on-chain, not a secret), the attacker can trivially generate a valid proof with no relation to any real UTXO, nullifier, root hash, or signature.

3. `performHinkalChecks` is self-satisfiable by an unprivileged attacker (`relay = address(0)`, `originalSender = msg.sender`), and `dimensionsCheck` just requires all array lengths equal `tokenNumber = 0`: [4](#0-3) 

4. `Hinkal._externalTransact` builds a zero-length `deltaAmountChanges` array (matching the empty `erc20TokenAddresses`) and calls `EmporiumUpgradeable.runAction`: [5](#0-4) 

5. Inside `runAction`, `balancesBefore`/`balancesAfter` are computed only over the attacker-supplied (empty) `erc20TokenAddresses`, so the loop that would normally catch a negative/unauthorized balance change never executes: [6](#0-5) [7](#0-6) 

6. `verifyWallet`, when `stack.signerAddress == address(0)`, returns immediately after marking the message used - it performs **no signature check whatsoever** on `stack.ops`: [8](#0-7) 

7. The unauthenticated `stack.ops` (fully attacker-controlled via `externalActionData.externalActionMetadata`) are then executed with `op.endpoint.call{value: op.value}(op.callData)`, where `msg.sender` in that inner call is the `EmporiumUpgradeable` contract itself: [9](#0-8) 

Exploit: attacker sets `stack.signerAddress = address(0)`, `stack.ops = [{endpoint: victimToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transferFrom, (victim, attacker, amount))}]`, `erc20TokenAddresses = []`. They self-generate a trivial `MainEVMCircuitMin` proof and call `Hinkal.transact`. If `victim` has ever granted a standing ERC20 approval to the Emporium contract address (e.g., via a prior gasless/approval-based interaction with Emporium), `transferFrom` succeeds because `msg.sender == Emporium`, moving `victim`'s tokens directly to `attacker`. Since `erc20TokenAddresses` is empty, no balance check anywhere (`Hinkal.transact`'s slippage/balance-diff requires, nor `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter`) inspects `victimToken` at all - the theft is completely unaccounted.

Existing guards fail because: (a) `performHinkalChecks`'s `calldataHash` check is a hash over public, attacker-controlled data, not a genuine authentication mechanism; (b) the min circuit constrains nothing about `stack`/ops/signer; (c) `verifyWallet` explicitly special-cases `signerAddress == address(0)` to skip authentication; (d) all balance/slippage accounting is scoped to `circomData.erc20TokenAddresses`, which the attacker sets to empty specifically to avoid triggering `BalanceChangeShouldBePositive` or the `balanceDif` requires in `Hinkal.transact`.

### Impact Explanation
Direct theft of any ERC20 tokens for which a victim has a standing approval naming the `EmporiumUpgradeable` contract as spender - the attacker moves those tokens straight to their own address with zero UTXO/proof relation to the victim and zero on-chain accounting. This matches Immunefi Critical: "direct theft of shielded or in-flight user funds" and "executing calls or moving assets a wallet owner or prover never authorised." It is fully repeatable across victims/approvals and across transactions (only bounded by picking a fresh, unused `emporiumMessage` per call).

### Likelihood Explanation
Preconditions: (1) a Verifier must be registered for `buildVerifierId(dimensions={0,0,0}, HINKAL_EMPORIUM_ACTION_ID)` mapping to `MainEVMCircuitMin` (the existence of `formInputEmporiumMin` and the dedicated `MainEVMCircuitMin.circom` circuit indicates this path is deployed and supported); (2) some victim must have a standing ERC20 approval naming the Emporium contract as spender (plausible given Emporium's design around wallet-based/gasless interactions). Attacker cost is minimal - trivial proof generation over self-chosen `messageSeed`, no real funds required, no whitelisted relay needed (attacker acts as their own `originalSender`). This is fully within the unprivileged-attacker capability set (deploy nothing extra needed, just craft `CircomData`/`Dimensions`/`externalActionMetadata`).

### Recommendation
- Require `stack.signerAddress != address(0)` (and full EIP-712 signature verification over `stack.ops`) whenever `runAction` is reached via the Emporium min-proof path, or disallow the min-proof path from carrying arbitrary `ops` entirely.
- Constrain `calldataHash` (and hence `externalActionMetadata`/`stack.ops`) inside the `MainEVMCircuitMin` circuit itself, or otherwise cryptographically bind `emporiumMessage` to the exact `EmporiumOperation[]` being executed regardless of `signerAddress`.
- Never allow `verifyWallet` to skip authentication of `stack.ops`; the `signerAddress == address(0)` branch should either forbid non-empty `ops`, or authenticate ops via an alternative mechanism tied to the depositing UTXO owner.
- Do not let `erc20TokenAddresses.length == 0` bypass all balance accounting when `ops` can make arbitrary external calls capable of moving third-party approved funds.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (registered as external action + allowed recipient), a mock ERC20, and a min-path verifier stub that returns `true` for the specific `verifierId`.
2. `victim` calls `token.approve(emporiumAddress, amount)` to simulate a standing approval, and holds `amount` tokens.
3. Attacker builds `CircomData` with: `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress:address(0), ops:[EmporiumOperation({endpoint:address(token), invokeWallet:false, value:0, callData:abi.encodeCall(IERC20.transferFrom,(victim, attacker, amount))})], maxFee:0, deadline:type(uint256).max}))`, `erc20TokenAddresses=[]`, `amountChanges=[]`, `onChainCreation=[]`, `slippageValues=[]`, `inputNullifiers=[]`, `outCommitments=[]`, `relay=address(0)`, `originalSender=attacker`, computes `calldataHash = getHashedCalldata(circomData)` locally to match.
4. Assert BEFORE: `token.balanceOf(victim) == amount`, `token.balanceOf(attacker) == 0`.
5. Attacker calls `Hinkal.transact(a,b,c, dimensions={0,0,0}, circomData)` with a proof accepted by the stub verifier (or a real Groth16 proof for `MainEVMCircuitMin` with an arbitrary `messageSeed`).
6. Assert AFTER: `token.balanceOf(victim) == 0`, `token.balanceOf(attacker) == amount`, and that `Hinkal.transact` did not revert on any balance/slippage check (proving the equality "assets moved == assets accounted" is violated, since `victim`'s balance change was never inspected by `Hinkal.transact` or `EmporiumUpgradeable.runAction`).
