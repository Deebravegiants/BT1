### Title
Balance-check bypass via alias tokens sharing one real balance lets `Hinkal.transact` mint UTXOs on two `erc20TokenAddresses` entries backed by a single on-chain balance increase - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` computes `balanceDif` for every index of `circomData.erc20TokenAddresses` independently by calling `balanceOf()` on that specific address before and after the external action, then requires `balanceDif == (onChainCreation?0:amountChanges[i]) + utxoAmount`. Nothing in `Hinkal.sol` or `HinkalHelper.dimensionsCheck`/`checkOnchainCreation` enforces that the addresses in `erc20TokenAddresses` are unique or correspond to distinct underlying assets, so an attacker can supply two different contract addresses (`A`, `B`) whose `balanceOf(address(this))` both mirror one shared real balance (e.g., both forward to a common storage/registry). A single real token movement into Hinkal is then read twice - once through `A`, once through `B` - letting the same real deposit satisfy the per-index equality for two separate UTXO sets.

### Finding Description
The invariant that should hold is:
`net real tokens entering Hinkal == Σ amountChanges[i] + Σ onchain/offchain UTXO amounts minted[i]`

but the contract can only verify this per-index via `balanceOf` snapshots, not per real underlying asset: [1](#0-0) [2](#0-1) 

`getBalancesForArray` simply loops the caller-supplied `erc20TokenAddresses` and calls `balanceOf(address(this))` (or reads `address(this).balance` for ETH) per entry, with no deduplication or check that the addresses represent economically distinct assets: [3](#0-2) 

`HinkalHelper.dimensionsCheck` only validates array-length consistency between `erc20TokenAddresses`, `amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`, `outCommitments`, `encryptedOutputs` - it never checks uniqueness of `erc20TokenAddresses` entries or that they belong to a whitelist: [4](#0-3) 

`checkOnchainCreation` similarly only checks per-index consistency (zero amountChanges/nullifiers when `onChainCreation[i]` is true), not cross-index token identity: [5](#0-4) 

**Attack:** The attacker deploys two ERC20 contracts `A` and `B` that both implement `balanceOf`/`transferFrom` by forwarding to one shared external registry/storage (a legitimate-looking "linked token" pattern). The attacker registers a LiFi swap external action (`externalActionId != 0`) whose router calldata is fully attacker-controlled (`Exploit idea` scope: "attacker router calldata"). During `_externalTransact`, the router settles the swap by crediting Hinkal with `X` units of the aliased asset - this is a single real state change, but it is visible identically through both `A.balanceOf(Hinkal)` and `B.balanceOf(Hinkal)` because they read the same backing store.

In the post-swap loop at lines 97-146, the attacker sets `erc20TokenAddresses = [A, B, ...]` and provides an `IExternalActionV2.runAction` return value (`utxoSet`) containing two UTXOs: one tagged `erc20Address == A` with `amount == X`, and one tagged `erc20Address == B` with `amount == X`. Because the loop at lines 117-131 groups `utxoAmount` strictly by literal address match against `circomData.erc20TokenAddresses[i]`, both `utxoAmount` sums come out to `X` independently. Both `balanceDif` computations (for index of `A` and index of `B`) equal the same real increase `X` (since they both observe the same underlying balance change), so both per-index equalities:
```
balanceDif_A == amountChanges_A + X   (satisfied: X == 0 + X)
balanceDif_B == amountChanges_B + X   (satisfied: X == 0 + X)
```
pass simultaneously, even though only one real deposit of `X` occurred. The circuit's own conservation constraint (`inTotal + amountChanges === outTotal`) operates per declared token-id/address and has no notion that `A` and `B` are the same underlying asset, so it cannot detect the aliasing either - it just proves two independent, internally-consistent shielded balances were created for "token A" and "token B".

The result: `insertCommitments` mints two on-chain UTXO commitments totalling `2X` in shielded value while Hinkal's actual holdings increased by only `X`. This is a direct violation of the stated invariant `net tokens entering Hinkal == Σ amountChanges + Σ UTXO amounts minted`.

None of the existing guards catch this:
- `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only check array-length and per-index self-consistency, not cross-index token uniqueness or legitimacy of `erc20TokenAddresses`.
- `verifyProof` only checks the circuit's internal per-declared-token conservation, which is agnostic to real-world token identity.
- `rootHashExists`/`insertNullifiers` guard nullifier reuse, not balance-vs-mint consistency across aliased tokens.
- The `balanceDif` check in `Hinkal.sol` is the *only* real-value backing check, and it is computed per address via `balanceOf`, which is exactly the primitive the attacker's alias tokens subvert.

### Impact Explanation
An unprivileged attacker can mint shielded UTXOs (redeemable later via normal withdraw flows) worth up to `2X` for every `X` real value actually deposited/swapped into Hinkal, with the multiplier scalable by adding more alias addresses (`A`, `B`, `C`, ... all mirroring the same balance) in a single `erc20TokenAddresses` array, since there is no length cap tied to distinct assets beyond `dimensions.tokenNumber`. This is unbacked minting of shielded value, i.e., protocol insolvency - each additional withdrawal of the phantom UTXOs directly drains real assets belonging to other Hinkal depositors. This matches the Critical category: "minting shielded value without backing."

### Likelihood Explanation
- Preconditions: attacker must deploy their own alias ERC20 pair (fully within attacker's unprivileged capability - "attacker controls... the deployed token"), register/use an external action (LiFi swap) with attacker-controlled router calldata, and craft `CircomData`/UTXO amounts for their own leaves (also explicitly in-scope attacker capability).
- No privileged role, relay collusion, or victim funds are required; the attacker only needs their own proof and their own alias token pair.
- Cost is limited to gas and one legitimate swap-sized deposit `X`; gain is up to `2X` (or more with more aliases) in mintable shielded value.
- Fully repeatable per transaction with no cooldown or per-address dedup enforced anywhere in the reachable code path.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` entries per `transact` call (reject duplicates and semantically-aliased entries cannot be detected on-chain by address alone, so at minimum enforce strict `address` uniqueness) inside `dimensionsCheck` or `Hinkal.transact` before computing balances. Additionally, consider maintaining/consulting a token allowlist (e.g., via `HINKAL_HELPER_MANAGER`) so `erc20TokenAddresses` may only reference vetted asset contracts, closing off the alias-token vector entirely. As defense in depth, compute `oldBalances`/`newBalances` once per unique address and refuse proofs whose UTXO set references an address not present verbatim once in `erc20TokenAddresses`.

### Proof of Concept
Foundry test plan:
1. Deploy a `SharedRegistry` contract holding a single `mapping(address=>uint256) balances`.
2. Deploy `TokenA` and `TokenB`, both ERC20-compatible, whose `balanceOf`/`transferFrom`/`transfer` all read/write `SharedRegistry.balances`.
3. Deploy a mock `IExternalActionV2` (simulating a LiFi router settlement) whose `runAction` (a) performs one real transfer of `X` tokens into Hinkal via `TokenA.transfer`/registry update, and (b) returns a `UTXO[]` array with two entries: `{erc20Address: TokenA, amount: X}` and `{erc20Address: TokenB, amount: X}`.
4. Build `CircomData` with `erc20TokenAddresses = [TokenA, TokenB]`, matching `amountChanges = [0,0]`, `onChainCreation` per protocol rules for the swap-output leg, and a locally generated valid proof satisfying the circuit's `inTotal + amountChanges === outTotal` for each declared token id.
5. Call `Hinkal.transact(...)`.
6. Assert:
   - `TokenA.balanceOf(hinkal) - oldBalanceA == X` and `TokenB.balanceOf(hinkal) - oldBalanceB == X` (both pass, single real balance mirrored).
   - Total UTXO value minted across the two `OnChainCommitment`/off-chain commitments == `2X`.
   - Real net value added to Hinkal (measured via the single underlying `SharedRegistry` balance delta) == `X`.
   - Assert `2X > X`, proving minted shielded value exceeds real backing - confirming insolvency.
