Audit Report

## Title
CORS `isAllowedOrigin` wildcard suffix match lacks a label boundary, allowing origin allowlist bypass — ([File: core/services/gateway/network/httpserver.go])

## Summary
The Gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` validates wildcard CORS origins using `strings.HasSuffix(originHost, allowedHost)` without checking that the matched suffix is preceded by a `.` label separator. This allows an attacker who registers a domain that merely ends with the same byte sequence as an allowed domain (e.g., `evilethereum.org` against an allowlisted `*.ethereum.org`) to pass the CORS check and receive a reflected `Access-Control-Allow-Origin` header.

## Finding Description
In `isAllowedOrigin`, wildcard entries are handled by stripping the `*.` prefix and then doing a bare suffix comparison: [1](#0-0) . This never verifies a `.` boundary immediately precedes the matched suffix, so `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true` even though `evilethereum.org` is an entirely separate, attacker-controllable domain unrelated to `ethereum.org`. The exact-match branch above it is correct, but it does not protect the wildcard branch. Existing tests only cover true subdomains (`remix.ethereum.org`, `another.valid.domain.com`, `example.gov`) as shown at [2](#0-1) , and none exercise the boundary-omission bypass case, so the gap is unexercised in CI.

On a match, `handleRequest` reflects the attacker-controlled `Origin` header verbatim into `Access-Control-Allow-Origin` along with permissive `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`: [3](#0-2) .

## Impact Explanation
This is a genuine CORS allowlist bypass: an attacker-controlled origin can be granted cross-origin read access to Gateway responses that operators intended to restrict to specific trusted subdomains via wildcard `CORSAllowedOrigins` entries. This maps to the "allowlist bypass" impact category, gating cross-origin browser access to the Gateway's internet-facing `ProcessRequest` handler.

## Likelihood Explanation
Exploitation requires only that the operator has configured a wildcard entry in `CORSAllowedOrigins` (a supported, documented configuration pattern per the existing test suite), and that an attacker registers/hosts a page on a domain whose name ends with the same substring as the allowed domain (trivially achievable, e.g., `evilethereum.org` vs `*.ethereum.org`). No credentials, privileges, or host access are needed — only a victim visiting the attacker's page in a browser that then issues a cross-origin request to the Gateway. This is unprivileged, reachable, and reproducible.

## Recommendation
Enforce a proper label boundary in the wildcard branch: check `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of the bare `strings.HasSuffix(originHost, allowedHost)`.

## Proof of Concept
1. Configure the Gateway with `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` and `CORSEnabled: true`.
2. Send an HTTP request to the Gateway endpoint with header `Origin: https://evilethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` (since `strings.HasSuffix("evilethereum.org", "ethereum.org")` is `true`) and the response includes `Access-Control-Allow-Origin: https://evilethereum.org`.
4. This can be added as a unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, asserting that an origin like `https://evilethereum.org` is incorrectly accepted.

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
