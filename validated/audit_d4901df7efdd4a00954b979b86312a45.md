### Title
Initial LP mint amount in `process_initialize2` is derived from actual vault token balances rather than the declared `init_coin_amount`/`init_pc_amount`, enabling donation-based manipulation of the initial pool exchange rate - (File: program/src/processor.rs)

### Summary
This is the closest analog in this codebase to the reported Notional issue, where the initial exchange rate was derived from `IERC20.balanceOf(address(this))` instead of a validated, expected value. In `process_initialize2`, the vaults (`amm_coin_vault_info` / `amm_pc_vault_info`) are freshly created PDA token accounts, then the instruction transfers `init.init_coin_amount` / `init.init_pc_amount` into them, but the initial liquidity/LP-mint calculation reads back the raw post-transfer vault balances (`amm_coin_vault.amount`, `amm_pc_vault.amount`) rather than trusting the declared `init_coin_amount`/`init_pc_amount` values directly.

### Finding Description
In `process_initialize2` [1](#0-0) , the program transfers exactly `init.init_coin_amount` and `init.init_pc_amount` from the caller into the newly created coin/pc vaults. Immediately after, it re-unpacks the vault accounts and computes the initial liquidity purely from the vaults' on-chain balances: [2](#0-1) 

```
let liquidity = Calculator::to_u64(
    U128::from(amm_pc_vault.amount)
        .checked_mul(amm_coin_vault.amount.into())
        .unwrap()
        .integer_sqrt()
        .as_u128(),
)?;
let user_lp_amount = liquidity
    .checked_sub((10u64).checked_pow(lp_mint.decimals.into()).unwrap())
    .ok_or(AmmError::InitLpAmountTooLess)?;
```

Because `amm_coin_vault.amount`/`amm_pc_vault.amount` reflect whatever tokens are actually sitting in the vault token accounts at the time of the check — not a value bound to the caller-declared `init_coin_amount`/`init_pc_amount` — the initial exchange rate (`coin_amount : pc_amount`) and the resulting `amm.lp_amount` (recorded on line 977) can be set to any ratio the pool creator wants simply by choosing what to actually deposit, and this same value later seeds `target_order.check_init` and the AMM's `lp_amount` bookkeeping.

The vaults are PDA-derived, program-owned accounts created inside this same instruction call via `generate_amm_associated_spl_token` [3](#0-2) , so an outside attacker cannot pre-fund them before pool creation in a separate transaction (the account doesn't exist as an initialized SPL token account until this call creates it). This limits the attack primarily to the pool-creator itself, who already fully controls `init_coin_amount`/`init_pc_amount` and thus the initial ratio regardless — so the specific "balanceOf-derived exchange rate" pattern from the Notional report is present but its blast radius here is bounded to the pool creator's own choice of initial ratio, not a third-party donation attack at genesis (unlike the Notional case, where the migration read a balance influenced by unrelated existing users/dust).

### Impact Explanation
If this pattern were reachable by a party other than the pool creator (e.g., if the vault address could be pre-seeded before `Initialize2` executes), it would allow directly manipulating the initial coin:pc ratio and the initial LP mint amount, potentially setting up a subsequent inflation/rounding attack against early depositors via `process_deposit`'s balance-based accounting (`total_pc_without_take_pnl`/`total_coin_without_take_pnl` computed from `amm_pc_vault.amount`/`amm_coin_vault.amount` [4](#0-3) ). However, as implemented, the vault accounts are created and controlled entirely within the same `Initialize2` call by the pool creator, so the "manipulation" is equivalent to the creator simply choosing their own initial price — a capability inherent to any AMM pool creation, not a fund-theft vector against other users.

### Likelihood Explanation
Low as an exploitable vulnerability against third parties: the vault PDA cannot receive external donations prior to being initialized within the same transaction that mints the initial LP supply, and the pool creator already has full authority over `init_coin_amount`/`init_pc_amount`. This differs materially from the Notional bug, where the manipulated balance belonged to a shared/pre-existing token contract balance influenced by other actors and dust prior to the vulnerable read.

### Recommendation
No code change is proposed here since no concretely exploitable third-party-reachable path was found; however, for defense-in-depth, `process_initialize2` could assert that `amm_coin_vault.amount == init.init_coin_amount` and `amm_pc_vault.amount == init.init_pc_amount` right before computing `liquidity`, ensuring the mint calculation is strictly tied to the declared, transferred amounts and not to any incidental vault balance.

### Proof of Concept
Not applicable — no reachable attack path by an unprivileged third party was identified; the balance-derived calculation in `process_initialize2` is only influenced by the pool creator's own transaction, which already fully controls `init_coin_amount`/`init_pc_amount` [5](#0-4) .
