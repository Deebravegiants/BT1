## Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values consumed by `Registry.process` are taken from unauthenticated HTTP headers that are never included in the HMAC-signed material. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to attribute the payload to a tenant, so the equality the code relies on — *"HMAC-authenticated bytes == bytes used to determine which shop this event belongs to"* — does not hold.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header [1](#0-0) .

For webhook requests, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, which are **not** part of the signed string: [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the *body* is authentic) and then immediately hands `request.shop` — an unauthenticated header value — to the handler as the tenant identifier: [4](#0-3) 

This is the exact "field acted on but not covered by the HMAC" bug class: the byte range that is cryptographically verified (raw body) diverges from the byte range that determines which shop/session the event is attributed to (the `shopify-shop-domain` header).

### Impact Explanation
An unprivileged internet user can obtain one genuinely-signed webhook (e.g., by installing the target app on their own free/dev store and receiving any subscribed webhook such as `app/uninstalled` or `orders/create` for their own shop — a completely legitimate action requiring no special privilege). They then replay that captured `(raw_body, hmac header)` pair to the app's public webhook endpoint unmodified, but swap the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to point at an arbitrary victim shop domain. Because `HmacValidator` only checks the body bytes, the signature still validates, and `Registry.process` forwards `WebhookMetadata` with `shop: <attacker-chosen victim domain>` to the host application's handler. Any host app that uses this `shop` value to look up/update per-tenant state (as the gem's own documentation recommends via `ShopifyAPI::Webhooks::Registry.register_all(session: shop_session)` keyed on shop) can have data written, deleted, or attributed to the wrong tenant — a cross-tenant integrity break qualifying as Critical impact.

### Likelihood Explanation
Any app developer/merchant can install the target app on their own store to obtain a validly-signed webhook payload (no leaked secrets or privileged access needed), and replaying an HTTP request with a modified header is trivial. The only constraint is that the attacker needs some webhook topic whose body content is attacker-influenced or is generic enough to be harmful when replayed under another shop's identity (e.g., `app/uninstalled`, `shop/update`, or any topic whose handler performs shop-scoped side effects). This is a realistic, low-effort attack path.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting `request.shop` in `Registry.process`. At minimum, document that host applications must independently verify the `shop-domain` header against records they control (e.g., confirming an existing session/subscription for that shop) rather than trusting it as authenticated by the HMAC check.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com"
# and receives a legitimately signed webhook (any topic), capturing:
raw_body = '{"id":1,"note":"whatever"}'
hmac     = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker now replays it to the app's public webhook endpoint, but
# changes only the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic"        => "orders/create", # same topic as captured
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac), # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Passes HMAC validation because it only checks raw_body:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...))
```
The host app's handler now processes attacker-supplied data as if it originated from `victim-shop.myshopify.com`, despite the HMAC only ever proving the body's authenticity for the attacker's own shop's webhook.
