### Title
Accrued market value overflows `i128` and permanently freezes a pool market - (File: common/src/rates/simulate.rs)

### Summary
**Severity: Medium.** A permissionless `Controller::update_indexes` call can make interest accrual panic when a market’s scaled supply or debt multiplied by its index exceeds `i128::MAX`, permanently blocking subsequent accrual-dependent operations on that market. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::update_indexes(caller, assets)` is permissionless apart from `caller` authorization and forwards the requested `HubAssetKey` list to the pool. [1](#0-0) [3](#0-2) 

The pool’s `accrue` path loads each market and executes `interest::global_sync`, which chunks elapsed time and calls `accrue_step`. [4](#0-3) [5](#0-4) 

Before applying the borrow-index cap, `accrue_step` computes `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` through `scaled_to_original`. [2](#0-1) [6](#0-5) 

`Ray::mul` delegates to `mul_div_half_up`, which uses a widened intermediate but panics with `MathOverflow` if the resulting `i128` value is unrepresentable. [7](#0-6) [8](#0-7) 

Consequently, `MAX_BORROW_INDEX_RAY` does not protect very large markets: the pre-update value calculation at `accrue_step` can overflow before `update_borrow_index` is reached, and `calculate_supplier_rewards` also unscales `borrowed` at the new index. [9](#0-8) [10](#0-9) 

Because the panic aborts before `mark_accrued` or `commit`, `last_timestamp` remains old, so every later accrual retries the same overflowing interval. [11](#0-10) [12](#0-11) 

All normal pool mutation legs load a synced market before applying their operation, so the same overflow blocks exits, repayments, borrows, revenue claims, and liquidation-related pool mutations for that market. [13](#0-12) 

### Impact Explanation
A sufficiently large and long-accruing market can become permanently unusable: suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot progress through accrual-dependent liquidation paths. [14](#0-13) 

The in-repository regression test demonstrates this exact cliff: once `borrowed * borrow_index` exceeds the `i128` value domain, `update_indexes` returns `MathOverflow`, and subsequent withdraw and repay attempts fail with the same error. [15](#0-14) [16](#0-15) 

### Likelihood Explanation
Triggering the bug requires market exposure large enough that `scaled_shares * index / RAY` approaches `i128::MAX`; for an 18-decimal asset, the tested setup uses one billion whole tokens and remains below the index cap when the value overflows. [17](#0-16) [18](#0-17) 

The cap-validation domain permits up to approximately `i128::MAX / 10^(27-decimals)` native units, so sufficiently permissive configured caps can admit the required position scale. [19](#0-18) 

The final trigger itself is permissionless because any authorized caller may invoke `Controller::update_indexes`, but the need for exceptionally large liquidity and substantial index growth makes this a Medium-impact, conditional availability failure rather than a broadly reachable immediate DoS. [1](#0-0) [3](#0-2) 

### Recommendation
Enforce a market-level scaled-exposure bound such that `scaled * MAX_INDEX / RAY` remains representable in `i128`, or make accrual use an explicitly bounded/saturating market-value representation before the index cap is applied. [20](#0-19) [18](#0-17) 

Entry checks should account for future index growth rather than only validating that the deposited amount can be converted to RAY. [21](#0-20) [22](#0-21) 

### Proof of Concept
For a market `M` with 18 decimals and configured caps that admit the required exposure, one unprivileged address can create both the supplying and borrowing accounts. [23](#0-22) 

```rust
// Controller calls by attacker-controlled `caller`.
let supplier_account = controller.supply(
    caller,
    0,
    spoke_id,
    vec![(debt_asset, supply_amount)],
);

let borrower_account = controller.supply(
    caller,
    0,
    spoke_id,
    vec![(collateral_asset, collateral_amount)],
);

controller.borrow(
    caller,
    borrower_account,
    vec![(debt_asset, borrow_amount)],
    Some(caller),
);
```

Choose `borrow_amount` so that its scaled debt `borrow_amount * 10^(27 - decimals)` approaches the `i128` boundary, while satisfying the market’s borrow cap, utilization gate, collateral valuation, and liquidation-buffer checks. [24](#0-23) [25](#0-24) 

After ledger time has advanced enough that `borrowed_scaled * borrow_index / RAY > i128::MAX`, call:

```rust
controller.update_indexes(caller, vec![debt_asset]);
```

The call reaches `accrue_step`, where `scaled_to_original(borrowed, borrow_index)` panics with `MathOverflow`. [1](#0-0) [2](#0-1) 

Every later withdrawal, repayment, or other accrual-dependent operation on `M` repeats the same overflowing calculation before applying the user’s requested mutation. [13](#0-12) [26](#0-25)
