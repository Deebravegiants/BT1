### Title
`EvmHost.dispatch()` and `EvmHost.fundRequest()` Do Not Refund Excess Native Token Overpayment - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and forward it entirely to `swapETHForExactTokens` to buy the exact `fee`/`amount` of fee tokens needed. Any dust ETH refunded by the Uniswap router for overpayment is sent back to `msg.sender` of the swap call, which is the `EvmHost` contract itself — not the original caller who supplied the `msg.value`. The excess is permanently stranded in the host's balance instead of being returned to the paying user.

### Finding Description
In `dispatch(DispatchPost memory post)`: [1](#0-0) 

the function calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` and discards the returned `amounts` array, which reports how much ETH was actually spent. Standard `UniswapV2Router02.swapETHForExactTokens` refunds any unused ETH (`msg.value - amounts[0]`) to `msg.sender` of that call — here, `EvmHost` — via `TransferHelper.safeTransferETH`. Since `EvmHost` never forwards that refund to the account that originally supplied `msg.value` (e.g., a `HyperApp` contract or EOA calling `dispatch`), any overpayment beyond the exact fee-token cost is absorbed into `EvmHost`'s balance and is unrecoverable by the payer.

The identical pattern exists in `fundRequest()`: [2](#0-1) 

and in `dispatch(DispatchGet memory get)`.

This is directly analogous to the referenced report's root cause (`Gateway.query()` accepting `msg.value > estimateFee()` without refunding the difference), except here the excess arises from real-time Uniswap slippage/price movement between when a caller estimates the required native amount off-chain and when the swap executes on-chain — a difference that is expected and unavoidable, not just user error. Notably, the codebase's own `IntentGatewayV2.placeOrder` demonstrates the correct pattern is known and used elsewhere: it captures `amounts[0]` from the swap and explicitly refunds the leftover native value to `msg.sender`: [3](#0-2) 

`EvmHost.dispatch`/`fundRequest` lack this refund step entirely.

### Impact Explanation
Every unprivileged caller of `IDispatcher.dispatch()` (POST/GET) or `fundRequest()` who supplies native token to cover relayer fees is exposed. Because the required native input is quoted off-chain (docs explicitly warn against calling `quote()` on-chain due to sandwich-attack risk) and Uniswap V2 spot prices can differ from quote-time between transaction submission and execution, users/apps must send a safety buffer above the estimated cost. Any buffer beyond the exact swap cost is permanently lost to the `EvmHost` contract balance — this is a direct, permanent loss of user funds (Medium severity, financial loss, no admin/governance/dependency involvement, reachable directly by ordinary dispatchers).

### Likelihood Explanation
High likelihood of occurrence in normal operation: any caller sending native token with a reasonable slippage/safety margin (as recommended practice, and as documented in `docs/content/developers/evm/messaging/post-requests.mdx`, where callers "must send enough native tokens to cover fees") will overpay whenever the actual swap executes cheaper than the buffered estimate — which is the common case, not an edge case.

### Recommendation
Capture the `amounts` return value from `swapETHForExactTokens` in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()` (or `tx.origin`/an explicit payer parameter), mirroring the refund logic already implemented in `IntentGatewayV2.placeOrder`'s handling of `msgValue -= amounts[0]` followed by `_sendValue(msg.sender, msgValue)`.

### Proof of Concept
1. `HyperApp` (or any contract) calls `IDispatcher(host).dispatch{value: X}(post)` where `X` includes a safety buffer above the true swap cost for `post.fee` fee-token units (standard practice since exact on-chain quoting is discouraged).
2. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: X}(post.fee, ...)` spends only `amounts[0] < X` and the router refunds `X - amounts[0]` to `msg.sender`, i.e., `EvmHost`.
3. `EvmHost` never forwards this refund to the original caller; `address(EvmHost).balance` increases by `X - amounts[0]`, and the caller has permanently lost that amount with no recovery path.
