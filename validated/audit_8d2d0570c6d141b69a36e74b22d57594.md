### Title
Webhook tenant identity (`shop`) is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the tenant-identifying `shop` (and `topic`/`webhook_id`) values that are handed to the app's handler come from HTTP headers that are **not** covered by that signature. This breaks the identity binding `shop authenticated by HMAC == shop attributed to the webhook data`, analogous to the erigon report's pattern of trusting a field that isn't actually protected by the verification mechanism.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic protection: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and secret key comparison, never touching headers: [3](#0-2) 

`Registry.process` validates only this body HMAC, then constructs `WebhookMetadata` directly from the unauthenticated header-derived `request.shop`, `request.topic`, and `request.webhook_id`, and forwards it to the registered handler as if it were verified data: [4](#0-3) 

Because the signature check never binds `shop` to the payload, a request with a **valid** `(raw_body, hmac)` pair obtained from any genuinely-delivered webhook (e.g. one triggered on an attacker-controlled/installed shop) can be replayed to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop domain. `Registry.process` will accept it — `Utils::HmacValidator.validate(request)` only re-derives the HMAC from `@raw_body`, which is unchanged — and will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion at the point the gem authenticates and attributes the webhook. Any code that uses `WebhookMetadata#shop` to key persistence, redact/data-request handling, or other tenant-scoped operations (all four `WebhookHandler` implementations in this gem operate on that `shop` field) will act on the wrong tenant. This satisfies the "Critical - cross-tenant access" bar, since a piece of data cryptographically proven only to originate from the attacker's own shop is relabeled and processed as data from an arbitrary victim shop.

### Likelihood Explanation
Exploitation requires only that the attacker be an ordinary merchant who installs the target app on their own store (unprivileged, no access to `client_secret`, access tokens, or the victim's account) and can capture one legitimate webhook delivery from Shopify to obtain a valid `(raw_body, hmac)` pair. No secret material or victim credentials are needed — only an HTTP client capable of resending the captured request with a modified `shop` header, since the header is not part of the signed input in `Request#to_signable_string`.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically tie the `shop`/`topic`/`webhook_id` header values to the verified payload (e.g., include them in the value passed to `to_signable_string`, or require the host app to look up and pin the shop via a previously-established, credential-backed session rather than trusting the header verbatim). At minimum, document prominently that `WebhookMetadata#shop`/`topic`/`webhook_id` are unauthenticated header values so integrators do not treat them as verified.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and lets a webhook (e.g. `orders/create`) fire, capturing the raw POST body `B` and the `shopify-hmac-sha256` header value `H` that Shopify sent.
2. Attacker POSTs to the app's webhook endpoint again with body `B` unchanged, header `shopify-hmac-sha256: H` unchanged, but `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses this into a `Request` object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (`B`) using the app's secret — matching `H` — and passes.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., webhook_id: request.webhook_id)` and dispatches it to the handler, which now believes the (attacker-supplied) webhook data belongs to the victim shop. [4](#0-3)
