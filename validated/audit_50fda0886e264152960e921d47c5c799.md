## Title
Arbitrary-call `EmporiumOperation` lets any prover drain ERC20/ETH balances held by `Emporium` that fall outside the current transaction's `erc20TokenAddresses` list - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes a caller-supplied list of `EmporiumOperation`s. When `op.invokeWallet` is false (or `stack.signerAddress == address(0)`), the "Stateless Interaction" branch performs `op.endpoint.call{value: op.value}(op.callData)` directly from the `Emporium` contract with **no signature check at all** (`verifyWallet` returns immediately when `signerAddress == address(0)`) and no restriction on `endpoint`/`callData` other than blocking two specific wallet-only selectors. Any unprivileged EOA that produces a valid Hinkal transaction proof can embed such an operation. The only post-check is a balance-diff equation over `circomData.erc20TokenAddresses` — any asset outside that attacker-chosen list is completely unaccounted for, so it can be siphoned out of the `Emporium` contract to the attacker with zero balance-check interference. This mirrors the `swapLiquidity` bug class: an attacker-controlled destination/action is invoked by a shared contract, and value that the safety equation doesn't track gets stolen.

### Finding Description
`runAction`: [1](#0-0) 

builds `stack` by simply `abi.decode`-ing `circomData.externalActionData.externalActionMetadata`, which is fully attacker-controlled off-chain data used to build the ZK proof. When `stack.signerAddress == address(0)`: [2](#0-1) 
`verifyWallet` skips all signature verification, so the "Stateless Interaction" branch is unauthenticated beyond the ZK-proof over `circomData`. The attacker then reaches:
```solidity
(success, err) = op.endpoint.call{value: op.value}(op.callData);
```
with `endpoint` and `callData` entirely attacker-chosen (only `callHinkalWallet`/`doSendToRelay` selectors are blocked, which only matters for the wallet-invocation path anyway).

The only safety mechanism is the post-execution balance equation, which is scoped strictly to `circomData.erc20TokenAddresses`: [3](#0-2) 
The code comment itself confirms `Emporium` is expected to retain pre-existing balances across transactions ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call"), i.e., leftover token/ETH balances legitimately routed through `Emporium` by other users (rounding dust, un-swept reward/refund tokens from a DeFi op invoked via a prior `EmporiumOperation`, native ETH sent via `receive()`) can and do sit on the contract between transactions.

Because the balance check only iterates over the *current* transaction's `erc20TokenAddresses`, an attacker can submit a transaction whose own `erc20TokenAddresses` list contains only innocuous tokens/amounts (even a trivial deposit), while embedding a stateless `EmporiumOperation` with `endpoint = <token Emporium is holding a balance of>` and `callData = transfer(attacker, balance)` (or, for ETH, `endpoint = attacker`, `value = address(this).balance`). This asset movement is never seen by the balance-diff loop at all, so nothing reverts, and the stolen funds are never reflected in the derived UTXOs.

This is the direct structural analog of the `swapLiquidity` bug: a function takes an attacker-supplied "receiver/endpoint" and executes an operation/transfer trusted to be safe based on an incomplete balance/allowance check, letting the attacker extract value the check doesn't cover.

### Impact Explanation
This breaks the accounting equality the protocol relies on to ensure "no value leaves `Emporium` except what is reflected back into Hinkal's shielded UTXO set." Any ERC20 or ETH balance resident in `Emporium` outside the specific token set an attacker chooses to declare is unauthenticated, unauthorized, and undetectable theft of protocol/user funds — matching the "Critical: direct theft of shielded or in-flight user funds" / "High: theft of protocol/relay fees, unauthorised asset movement" criteria. Funds temporarily routed through `Emporium` on behalf of any user (mid-flight between being pulled from Hinkal and being converted back into a UTXO) are exposed for the duration they remain on the contract and are not part of the attacker's own declared token list.

### Likelihood Explanation
Any actor able to submit a normal Hinkal transaction with a valid ZK proof can trigger this — no relayer, admin, or other user's key is required, since the `stack`/`EmporiumOperation` payload is arbitrary off-chain-constructed metadata bound only by the prover's own proof. Exploitation requires only that `Emporium` be holding some balance of a token/ETH not included in the attacker's chosen `erc20TokenAddresses` at call time (residual dust, un-swept reward tokens, or in-flight balances of other concurrent/pending transactions), which the contract's own design (as evidenced by its "funds on emporium before the call" handling) shows is an expected, not edge-case, condition.

### Recommendation
Do not allow unauthenticated ("stateless", `signerAddress == address(0)`) `EmporiumOperation`s to target arbitrary `endpoint`/`callData`. At minimum:
- Restrict stateless operations to a governance-controlled allow-list of endpoints/selectors, or
- Require every `EmporiumOperation`, including stateless ones, to be authenticated by the depositing user (e.g., always require a signature check, not only when `signerAddress != address(0)`), and
- Extend the post-call balance accounting to sweep/verify against the full set of tokens `Emporium` could plausibly hold (or ensure `Emporium` never carries a non-zero balance between transactions), so no value can silently exit outside the tracked equation.

### Proof of Concept
1. Assume `Emporium` holds a nonzero balance of token `X` that is not part of any currently pending transaction's `erc20TokenAddresses` (e.g., leftover from a prior swap's slippage/rounding, or dust sent accidentally/as a reward during a previous op) — the contract's own accounting comment acknowledges this state is expected.
2. Attacker (any unprivileged EOA) crafts a Hinkal transaction where `circomData.erc20TokenAddresses` includes only tokens unrelated to `X` (e.g., a trivial self-deposit) and `externalActionData.externalActionMetadata` encodes an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: X, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, X_balance)) }`.
3. Attacker generates a valid ZK proof for this transaction (no special privilege needed) and calls Hinkal's transact entrypoint.
4. `Hinkal._externalTransact` -> `EmporiumUpgradeable.runAction` executes `verifyWallet` (no-op, `signerAddress == 0`), then executes the stateless op: `X.call(transfer(attacker, X_balance))`, moving all of token `X` from `Emporium` to the attacker.
5. The subsequent balance-diff loop only checks tokens in the attacker's declared `erc20TokenAddresses`, none of which is `X`, so the transaction completes successfully with the theft fully unaccounted for. [4](#0-3)

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }

        payRelayFees(circomData, stack.signerAddress, deltaAmountChanges);

        uint256[] memory balancesAfter = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        UTXO[] memory utxoSet = new UTXO[](
            circomData.erc20TokenAddresses.length
        );

        uint256 utxoSetLength;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 balanceChange = int256(balancesAfter[i]) -
                int256(balancesBefore[i]);

            if (deltaAmountChanges[i] < 0) {
                balanceChange -= deltaAmountChanges[i];
                // this equation reads: total change of emporium balance = what was moved to emporium (-deltaAmountChange) + how emporium balance changed through tx (balanceChange)
            }

            // the only case when balanceChange can be < 0, when there were some funds on emporium before the call
            if (balanceChange < 0) {
                revert BalanceChangeShouldBePositive();
            }

            UTXO memory utxoOut = handleOut(balanceChange, circomData, i);

            if (utxoOut.amount > 0) {
                utxoSet[utxoSetLength++] = utxoOut;
            }
        }
