### Title
Permanent freezing of relayer's Outbound Request Delivery Reward when `RequestCommitments` is pruned by a legitimate timeout before the reward is claimed - (File: modules/pallets/relayer/src/outbound_request.rs)

### Summary
`process_outbound_request_delivery_claim` in `pallet-relayer` requires the delivered request's commitment to still be present in `pallet_ismp::child_trie::RequestCommitments` at claim time. That entry is deleted whenever the same request is timed out via the ISMP timeout handler. A relayer who has already legitimately delivered a hyperbridge-originated request to its destination (proven by `RequestReceipts[commitment]`) can permanently lose the right to claim the configured `OutboundRequestDeliveryReward` if the commitment is removed from `RequestCommitments` by a timeout that runs (or is processed) before the reward claim lands — mirroring the reported veALCX pattern where burning the token before claiming destroys the ability to prove the claim.

### Finding Description
`process_outbound_request_delivery_claim` gates the entire verification/payout pipeline on the commitment still existing locally: [1](#0-0) 

This mirrors the on-chain "defence in depth" comment that says the commitment must be present or the claim is rejected as `OutboundRequestNotKnown`: [2](#0-1) 

Separately, the ISMP timeout handler unconditionally deletes `RequestCommitments` for a request the moment its module's `on_timeout` callback returns `Ok`: [3](#0-2) 

The timeout path is permissionless — any relayer/party can submit a `TimeoutMessage` once the non-membership proof for a state height *before* actual delivery is available and the request's `timeout_timestamp` has elapsed relative to that height's timestamp: [4](#0-3) 

The reward-eligible requests are exactly hyperbridge-originated system dispatches (host-executive, intents-coprocessor, token-governor, the relayer pallet's own withdrawal path) that today ship with zero fee/payer and therefore have no economic incentive tied to prompt, race-free delivery: [5](#0-4) 

Because ISMP's timeout check on the source (hyperbridge) is evaluated against a *previously finalized* state-machine height for the destination — not the destination's real-time clock — a relayer that delivers the request close to (or narrowly past) `timeout_timestamp` can be beaten by a timeout submitted against an earlier, still-valid non-membership proof. Once that timeout lands, `delete_request_commitment` removes the `RequestCommitments` entry entirely (this is the exact mechanism the timeout test explicitly asserts): [6](#0-5) 

At that point, even though the relayer's delivery is durably provable via `RequestReceipts[commitment]` on the destination chain, `process_outbound_request_delivery_claim`'s local-presence check (`RequestCommitments::<T>::get(commitment).is_some()`) fails permanently — `OutboundRequestNotKnown` — and no later resubmission of the claim can succeed, since the commitment can never be reinserted for that request. This is structurally identical to the veALCX bug: the withdrawal/burn (here, timeout+delete) happens on a different entitlement dimension (locked-token ownership / commitment bookkeeping) than the one gating the claim, but the claim's authorization check depends on state that gets destroyed by an independent, permissionless code path, permanently orphaning an already-earned reward.

### Impact Explanation
This is a permanent freezing-of-yield analog: the relayer did real, unbacked work (delivering a hyperbridge-originated message and paying the destination gas), and is contractually owed `OutboundRequestDeliveryReward[module_id]` from the treasury, but loses that payout irrecoverably purely due to bookkeeping cleanup that runs on an unrelated, permissionless path (timeout processing) with no re-crediting mechanism. Given that today's system dispatches carry `fee: 0`/`payer: 0` and no protocol-level incentive besides this reward, a race between delivery and timeout griefs exactly the mechanism meant to bootstrap relayer participation for these messages, undermining delivery incentives for host-executive, intents-coprocessor, token-governor, and the relayer pallet's own withdrawal messages.

### Likelihood Explanation
This requires: (1) a hyperbridge-originated (system) dispatch whose `timeout_timestamp` is non-zero and can elapse relative to an already-finalized-but-stale destination state height, (2) a relayer delivering close to that deadline, and (3) a timeout message being submitted (by anyone) using the stale non-membership proof before the reward claim is finalized. This is a narrower race condition than a straightforward "burn-then-claim" ordering bug (it depends on timing/latency between destination delivery, hyperbridge's view of destination state, and the relayer's own claim submission cadence), and the search could not fully confirm whether all currently reward-eligible system dispatchers (host-executive, intents-coprocessor, token-governor, relayer withdrawal) actually configure non-zero timeouts in practice — that would need verification in each pallet's dispatch call sites (only host-executive was found to reference "timeout" among those inspected, and the exact value used there was not confirmed within the available search budget). Assuming at least one eligible module sets a meaningful timeout, the race is plausible under adversarial or simply slow relayer conditions, particularly since this is exactly the destination/`RequestCommitments` lifecycle the timeout handler and reward-claim code both explicitly document as sensitive ("Re-check the commitment right before dispatch... a prior on_timeout... could have caused the commitment... to be removed").

### Recommendation
- Decouple the reward-claim's local eligibility check from `RequestCommitments` presence. Instead of requiring `RequestCommitments::<T>::get(commitment).is_some()` at claim time, persist a durable, append-only allowlist record (e.g., a dispatch-time log keyed by commitment plus `module_id`/`dest`) that is written once at dispatch and never deleted by the timeout path, so a legitimately delivered request remains claimable even if the corresponding timeout also later fires.
- Alternatively, make timeout processing and reward-claim processing mutually exclusive per commitment: before allowing a timeout to delete a `RequestCommitments` entry that is subject to `OutboundRequestDeliveryReward`, first check `RequestReceipts[commitment]` via a state proof (i.e., timeouts against system-incentivized modules should require a stronger present-time non-membership guarantee, not a stale finalized height).
- At minimum, emit and retain the deleted request's identifying data (commitment, `module_id`, `dest`) in a separate "orphaned system dispatch" log when `on_request_timeout` fires for a module with a non-zero `OutboundRequestDeliveryReward`, so a relayer that can still prove delivery via a destination state proof can claim against the archived record rather than the live `RequestCommitments` map.

### Proof of Concept
Conceptual sequence (constructing a concrete Foundry/simnode reproduction was outside the tool budget for this analysis; the described race is derivable directly from the cited code paths):
1. A hyperbridge pallet with a configured `OutboundRequestDeliveryReward[module_id] > 0` dispatches a `PostRequest` with a non-zero `timeout_timestamp`, creating `RequestCommitments[commitment]` [7](#0-6) .
2. Hyperbridge's tracked consensus state for the destination is finalized at height H, whose timestamp is already at/near `timeout_timestamp` (destination consensus updates can lag real time).
3. A relayer delivers the request to the destination after height H (writing `RequestReceipts[commitment]`), but before hyperbridge's view of the destination advances past H.
4. Any party submits `TimeoutMessage::Post` using a non-membership proof against height H (still valid, since delivery happened after H) — the timeout handler's `!post.timed_out(state.timestamp())` check passes because `state.timestamp()` (from H) is past `timeout_timestamp`, and `verify_non_membership` succeeds because the destination trie at H had no receipt yet [8](#0-7) .
5. The module's `on_timeout` callback returns `Ok`, so `delete_request_commitment` removes `RequestCommitments[commitment]` permanently [9](#0-8) .
6. The relayer now submits `claim_outbound_request_delivery_reward` with a valid destination state proof of `RequestReceipts[commitment]`; the claim reverts with `OutboundRequestNotKnown` at the `RequestCommitments::<T>::get(commitment).is_some()` check [10](#0-9) , and no valid resubmission path exists because the commitment cannot be reinserted for this now-timed-out request.

## The shape of the solution

The issue creator's preferred shape ([comment 4428807013](https://github.com/polytope-labs/hyperbridge/issues/532#issuecomment-4428807013)): use `pallet-relayer` to pay BRIDGE to whoever proves they delivered a hyperbridge-originated request. The messaging task in the tesseract relayer submits the claim.

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

The timeout `handle` is used to notify onchain `IsmpModule`s of outgoing requests that have now timed out. A relayer will construct the `TimeoutMessage` which holds a batch of these messages, and their relevant proofs. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the messages have indeed timed out
- Assert that the claimed messages are known by the host
- Assert that the relevant state machine's time has advanced past the `timeout_timestamp` of specified messages.
- Assert that the relevant non-membership proofs for the messages are valid
- Finally dispatch the timeouts to the relevant `IsmpModule::on_timeout` and delete the commitments for the outgoing messages.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_timeout` does not return `Ok`, the commitment of the relevant messages will not be deleted, allowing the timeout to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their timeout handler. This model ensures that if a timeout cannot be executed successfully, it can be retried later.
```
