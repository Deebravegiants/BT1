### Title
Division-by-zero panic in `Calculator::calc_x_power` reachable from `Deposit`/`Withdraw` PNL accounting can permanently deny LP withdrawals - (File: program/src/math.rs)

### Summary
The VLC CVE is a NULL-pointer dereference reached because a computed value (a seek position) was used without validating it could be zero/invalid, causing an unconditional crash. The equivalent bug class in this program is an unchecked-denominator division: `Calculator::calc_x_power` unconditionally divides by `current_y` with `.checked_div(current_y).unwrap()`, and this value derives from live, attacker-influenceable pool state (`total_coin_without_take_pnl`) with no zero-guard before the call.

### Finding Description
`Calculator::calc_x_power` computes: [1](#0-0) 
which does `checked_div(current_y).unwrap()` — if `current_y` (the normalized coin-side pool balance) is `0`, `checked_div` returns `None` and `.unwrap()` panics.

This function is called from `Processor::calc_take_pnl`: [2](#0-1) 
where `y1` is derived by `Calculator::normalize_decimal_v2(total_coin_without_take_pnl, ...)`, and `total_coin_without_take_pnl` is itself `coin_amount - amm.state_data.need_take_pnl_coin`: [3](#0-2) 

`calc_take_pnl` is invoked from `process_deposit` and `process_withdraw` (unprivileged LP-reachable instructions): [4](#0-3) [5](#0-4) 

Because `need_take_pnl_coin` is only ever incremented inside `calc_take_pnl` (protocol PNL debt) and reset by the privileged `WithdrawPnl` instruction, repeated fee-driven invariant growth followed by `Deposit`/`Withdraw` calls can push `need_take_pnl_coin` arbitrarily close to the vault's actual coin balance. If a sequence of trades and LP actions ever drives `total_coin_without_take_pnl` to exactly `0` (i.e., `need_take_pnl_coin == amm_coin_vault.amount`), then `y1` normalizes to `0` (normalization only ever scales up or preserves value, never rounds a nonzero raw amount down to zero, per `normalize_decimal_v2`), and any subsequent `Deposit` or `Withdraw` call unconditionally panics inside `calc_x_power` before completing.

### Impact Explanation
Once this zero-divisor state is reached, every future `Deposit` and `Withdraw` instruction against the pool will panic and revert, because both code paths unconditionally call `calc_take_pnl` (Withdraw skips it only when status is `WithdrawOnly`, which is an admin-only state change). This permanently locks LP principal in the pool — LPs can never again call `Withdraw` to redeem their LP tokens for underlying assets, constituting a permanent freezing of LP funds via an unprivileged, transaction-reachable panic.

### Likelihood Explanation
Reaching `total_coin_without_take_pnl == 0` precisely requires the PNL-taking mechanism to fully consume the coin-side pool balance, which in practice requires substantial fee-driven invariant growth accumulated across many swaps combined with well-timed `Deposit`/`Withdraw` calls to crystallize that growth into `need_take_pnl_coin`. This is not a one-transaction trivial exploit; it depends on pool-specific parameters (`fees.pnl_numerator/denominator`, trading volume, and pool size), so likelihood is low-to-moderate depending on the pool's fee/volume profile, but the root cause — an unguarded `unwrap()` on a division whose denominator is influenced by adversarial trading activity — is a genuine, reachable code defect and not merely theoretical.

### Recommendation
Replace the `.unwrap()` in `Calculator::calc_x_power` (and other unconditional `.unwrap()` calls in `calc_take_pnl`/`math.rs` that divide by pool-derived quantities) with `checked_div(...).ok_or(AmmError::...)?`, and add an explicit guard in `calc_take_pnl` to return a defined `AmmError` (rather than panicking) when `x1 == 0 || y1 == 0`, ensuring pools never become permanently unable to process `Withdraw`.

### Proof of Concept
1. Attacker (or any market participant) repeatedly performs large `SwapBaseIn`/`SwapBaseOut` trades against a low-liquidity pool to grow the invariant (`total_pc * total_coin`) substantially above the last recorded `target_orders.calc_pnl_x * calc_pnl_y`.
2. Attacker calls `Deposit` (minimal amount) to trigger `calc_take_pnl`, which computes `coin_pnl_amount` and adds it to `amm.state_data.need_take_pnl_coin`, shrinking `total_coin_without_take_pnl` for future calls.
3. Repeat steps 1–2, each time nudging `need_take_pnl_coin` closer to the vault's coin balance, until a `Deposit`/`Withdraw` call results in `need_take_pnl_coin == amm_coin_vault.amount` (i.e., `total_coin_without_take_pnl == 0`).
4. Any subsequent `Withdraw` call now computes `y1 = 0` and calls `calc_take_pnl` → `calc_x_power(..., current_y = 0)` → `checked_div(0).unwrap()` panics, aborting the transaction and permanently blocking all LPs from withdrawing.

        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
