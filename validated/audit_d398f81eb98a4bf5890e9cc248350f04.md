### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, and `webhook_id` from raw HTTP headers, but `to_signable_string` (the data actually authenticated by `HmacValidator.validate`) only covers the raw request body. `Registry.process` treats a valid HMAC as proof that the *entire request*, including the `shop` header, is trustworthy, and forwards `request.shop` straight into `WebhookMetadata` for the app's handler. This breaks the identity binding `verified_sender(raw_body) == shop_attributed_to_event`.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [1](#0-0) . For webhook requests, `to_signable_string` returns only `@raw_body`; it does not include `shop`, `topic`, or `webhook_id` [2](#0-1) . Those three values are read straight from attacker-controllable HTTP headers with no cryptographic binding to the signed body [3](#0-2) .

`Registry.process` only gates on `HmacValidator.validate(request)` succeeding, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata` passed to the app's registered handler [4](#0-3) . Because the shop identity is never part of the signed bytes, "HMAC valid" does **not** imply "this event genuinely belongs to the shop in the header." Any party who legitimately possesses one valid `(raw_body, hmac)` pair signed with the app's shared secret — for example an app-installing merchant receiving real webhooks to their own endpoint, where the body content is attacker-influenced (e.g., customer/order note fields on their own store) — can resend that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `topic`/`webhook-id`) header. `HmacValidator.validate` still succeeds because it never inspected those headers, and `Registry.process` dispatches the handler believing the event originates from the victim shop specified in the header [5](#0-4) .

This is the exact bug-class pattern flagged in the report — an action is gated on a signature/authorization check performed before/independently of the value that is actually consumed, so the value used downstream (`shop`) is never covered by the binding (`hmac`) that supposedly proves trust.

### Impact Explanation
Handlers built on this gem key their business logic off `WebhookMetadata#shop` (e.g. to select the tenant's session/access token, apply state changes, or provision/deprovision resources for "that shop"). Since `shop` is unauthenticated relative to the HMAC, an attacker who can obtain any single valid `(body, hmac)` pair for the app (trivially available to any merchant who installs the app, since Shopify will deliver real signed webhooks to them) can impersonate delivery "on behalf of" an arbitrary victim shop domain, causing the host application to execute tenant-specific logic against the wrong tenant. This is a cross-tenant identity confusion at the trust boundary the gem is supposed to enforce, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Any app using this gem must expose its webhook endpoint on the public internet for Shopify to reach it, so nothing beyond ordinary HTTP access is required to hit `Registry.process`. Obtaining one valid `(raw_body, hmac)` pair requires no secret knowledge — it only requires being (or observing) any legitimate webhook delivery for the shared app (e.g., installing the app on one's own store, a normal unprivileged action). Replaying that pair with a substituted `shop` header is a trivial HTTP-level forgery. Likelihood is High.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically tie the `shop` header to the specific delivery instead of trusting it independently of the HMAC. At minimum, `Registry.process`/`Request` should not treat HMAC validity over the body as validation of the shop header; the gem should document (or enforce) that host applications must independently verify `webhook_id` uniqueness/replay and cross-check the `shop` header against the shop that legitimately owns the topic subscription (e.g., via the webhook_id lookup already available in `Registry.get_webhook_id`), rather than trusting the header value directly for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker-shop.myshopify.com`) and subscribes to a webhook topic, e.g. `orders/create`.
2. Attacker creates an order on their own store, causing Shopify to POST a webhook to the app's public endpoint with a real `x-shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`.
3. Attacker captures this `raw_body` + `hmac` header pair (they own the request, no interception needed).
4. Attacker replays the same `raw_body`/`hmac` directly to the app's public webhook endpoint over the internet, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `Registry.process` verifies successfully because it only checks `raw_body` against the secret [6](#0-5) ; `request.shop` returns `victim-shop.myshopify.com` from the header [7](#0-6) .
6. The app's handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and attacker-supplied body content, even though no such event ever occurred on the victim's shop [8](#0-7) .
