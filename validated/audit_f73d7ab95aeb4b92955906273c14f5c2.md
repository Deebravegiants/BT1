### Title
Interest-accrual overflow can permanently freeze an overgrown debt market - (File: `common/src/rates/index.rs`)

### Summary

Scaled debt is represented as `RAY` shares, and every accrual multiplies total debt shares by the updated borrow index using checked `i128` arithmetic. [1](#0-0)  When `borrowed * new_borrow_index` exceeds `i128::MAX`, accrual panics with `MathOverflow` before the borrow-index cap can protect the market. [2](#0-1)  Because `update_indexes`, repayments, withdrawals, borrows, and liquidation legs all synchronize the market before mutating it, one crossing of this bound makes subsequent operations on that market revert. [3](#0-2) 

### Finding Description

`global_sync` splits elapsed time into bounded chunks, but each chunk calls `accrue_step`, which calculates the old and new RAY-denominated debt totals before deriving supplier rewards and protocol revenue. [4](#0-3) [2](#0-1)  `Ray::mul` is checked arithmetic, so a very large scaled debt base times a sufficiently grown index raises `MathOverflow` instead of saturating or capping the market value. [5](#0-4) 

The intended borrow-index ceiling is not sufficient because the debt-value multiplication can overflow while `new_borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [6](#0-5)  The repository’s stress test demonstrates this exact cliff: a one-billion-token, 18-decimal market at sustained high utilization eventually returns `MATH_OVERFLOW`, while the stored borrow index remains below the cap. [7](#0-6) 

Any address may authenticate to controller `update_indexes`, which forwards the selected market to the pool after only caller authorization and the flash-loan check. [8](#0-7) [9](#0-8)  The pool then runs the vulnerable accrual for each submitted `HubAssetKey`. [10](#0-9) 

After the overflow condition exists, `repay` reaches `load_leg`, synchronizes the market, and panics before any debt shares can be burned. [11](#0-10)  Likewise, `withdraw` synchronizes the market before resolving or burning supply shares. [12](#0-11)  The regression test confirms that both withdrawal and repayment fail with `MATH_OVERFLOW` after the condition is reached. [13](#0-12) 

### Impact Explanation

The affected market can enter a state where suppliers cannot withdraw and borrowers or third parties cannot repay through the normal controller paths because those paths accrue first. [14](#0-13) [15](#0-14)  Liquidation legs use the same synchronized market loading, so risk reduction cannot unblock the market once accrual itself overflows. [3](#0-2) 

This is a freeze of user funds and the market’s accounting path, not merely a failed malicious transaction: every later state transition that touches the market repeats the overflowing multiplication. [10](#0-9) [2](#0-1)  Recovery would require a remediation path that avoids the overflowing value calculation; the unprivileged repay, withdraw, liquidate, or `update_indexes` paths cannot do so. [16](#0-15) [17](#0-16) 

### Likelihood Explanation

Triggering the condition requires an extremely large debt base and enough index growth for `borrowed * index` to exceed the signed `i128` range. [1](#0-0)  A borrower can create the necessary state only on a market whose listed decimals, caps, available liquidity, collateral backing, and rate model permit such a position; those constraints make the issue conditional rather than universally reachable. [18](#0-17) 

Once that state exists, no privileged action or market manipulation is needed to trip it: an unprivileged caller signs `update_indexes(caller, [hub_asset])`, and ordinary elapsed ledger time supplies the remaining input. [8](#0-7)  The in-repository reproduction uses ordinary `supply`, `borrow`, repeated `update_indexes`, then failed `withdraw` and `repay` calls. [19](#0-18) 

### Recommendation

Calculate accrued debt interest without materializing the unchecked `borrowed * index` total in `i128`. [2](#0-1)  For example, compute the interest increment from a checked `borrowed * (new_index - old_index)` decomposition, use `I256`/widened arithmetic followed by an explicit domain check, or cap/saturate the RAY debt value before checked multiplication and define the resulting market state consistently. [20](#0-19) 

Add a regression test proving that a market near the RAY-value ceiling can still accrue, repay, withdraw, liquidate, and socialize debt, or else fail through a bounded state that does not poison every later operation. [21](#0-20)  The fix should be applied in the shared `common::rates` path so state-changing accrual and simulation cannot diverge. [22](#0-21) 

### Proof of Concept

1. On a listed high-decimal market `DEBT_ASSET` whose configuration permits the required caps and utilization, call `supply(caller, 0, spoke_id, [(DEBT_ASSET, principal)])` to create the liquidity account. [23](#0-22) 
2. Supply sufficient separate collateral to an account and call `borrow(caller, account_id, [(DEBT_ASSET, debt)], None)` so `borrowed` approaches the market’s permitted limit. [24](#0-23) 
3. Leave the position outstanding and call `update_indexes(caller, vec![DEBT_ASSET_KEY])`; repeat as ledger time advances until the next `borrowed.mul(new_borrow_index)` exceeds `i128::MAX`. [8](#0-7) [1](#0-0) 
4. The call returns `MathOverflow`; every subsequent `repay`, `withdraw`, or liquidation touching the same market synchronizes first and reverts on the same multiplication before its mutation can execute. [15](#0-14) [25](#0-24) 

The repository test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` reproduces this behavior with a one-billion-unit, 18-decimal market and 98% initial utilization. [21](#0-20)

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
    let mutation = cache.position_mutation(position, net_repay);

pub(crate) fn accounting(
    env: &Env,
    is_liquidation: bool,
    entry: &PoolWithdrawEntry,
) -> WithdrawOutcome {
    require_nonneg_amount(env, entry.protocol_fee);
    let (mut cache, position) = ops::load_leg(env, &entry.action);

    let (burned, gross_amount) = resolve_close_or_partial(&cache, entry.action.amount, position);
    // Burn first: `protocol_fee_shares` caps the fee mint at `i128::MAX - supplied`.
    let remaining = burn_position(env, &mut cache, position, burned);
    let net_transfer = withhold_liquidation_fee(
        env,
        &mut cache,
        gross_amount,
        is_liquidation,
        entry.protocol_fee,
    );

    // A footprint-only close must not add a utilization gate to same-market
    // net settlement: it burns no shares and moves no cash.

    gate_and_debit(env, &mut cache, net_transfer, is_liquidation || empty_close);

    let snapshot = cache.commit();
    let mutation = cache.position_mutation(remaining, gross_amount);
