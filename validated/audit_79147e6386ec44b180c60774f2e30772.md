Based on the webhook processing pipeline, I found a direct analog to the reported bug class: a field that is *acted on* by the library but is *not covered by* the HMAC signature.### Title
Webhook shop-tenant identity forgery via HMAC that only covers the raw body, not the `X-Shopify-Shop-Domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC. The shop-identifying header (`shopify-shop-domain`/`x-shopify-shop-domain`) that the registry later uses to attribute the webhook to a tenant is never included in the signed material, so it can be freely substituted by anyone who can produce one valid (body, hmac) pair for the shared app secret.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`to_signable_string` returns only `@raw_body`; none of the Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are part of the signed content. `Utils::HmacValidator.validate` then only checks that `raw_body` matches the given `hmac`, using the single app-wide `Context.api_secret_key`: [2](#0-1) 

`Registry.process` trusts `request.shop` (an unsigned header) as the tenant identity to dispatch to the handler: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The security-relevant binding the library should enforce is: `shop header == signed content`. Instead the actual behavior is `shop header != signed content` — the shop identity is acted upon (`WebhookMetadata.shop`, used by host apps to select the tenant/session/store record) but is never bound to the cryptographic signature at all. This is the exact analog of the reported bootloader bug class: a value consumed by downstream logic that is not covered by the integrity check meant to authenticate it.

Because webhook HMAC signing uses a single `api_secret_key` shared by the app across every installed shop (not a per-shop secret), and because Shopify apps conventionally register one shared callback URL for all shops (`Registration#callback_address`, used identically regardless of tenant), any shop that installs the app — an unprivileged action available to any internet user — receives real webhook deliveries with a valid `(raw_body, hmac)` pair signed under that same shared secret. An attacker can capture such a delivery from their own shop and replay it to the app's shared webhook endpoint with the `shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` still succeeds because only `raw_body` is checked, and `Registry.process` forwards the forged shop identity straight to the app's handler.

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately installs the app on a shop they control can forge webhook events attributed to any other shop that has installed the same app, without needing that shop's credentials. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the tenant's session/access token and process attacker-supplied `body` content "as" the victim shop), this can lead to cross-tenant data corruption or processing of attacker-controlled data under a victim's tenant context — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation only requires the capability every real-world multi-tenant Shopify app grants to any installer: receiving one authentic webhook POST at the shared callback endpoint (any topic works, since the same weakness applies to all of them), and then reissuing that same body/HMAC pair with a different `X-Shopify-Shop-Domain` header value. No knowledge of `api_secret_key`, any access token, or the victim's credentials is required.

### Recommendation
Bind the shop-domain (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived tenant identity to the signed body before it is used to construct `WebhookMetadata`, so that a valid signature for shop A's payload cannot be reattributed to shop B by simply changing an unsigned header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free, unprivileged action).
2. Shopify sends a legitimate webhook (e.g., `orders/create`) to the app's single shared webhook URL:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...attacker-controlled order data...}
   ```
3. Attacker captures this exact request (headers + body) and replays it, only changing:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   leaving `x-shopify-hmac-sha256` and the body untouched.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only and it still matches, since `shop-domain` was never part of the signed content (`lib/shopify_api/webhooks/request.rb:36-38`).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker-controlled body, ...)` to the app's registered handler, which now processes attacker-controlled data under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
