### Title
Unsafe low-level ERC20 `transfer` calls in Tron `IntentGatewayV2.withdraw()`/`SweepDust` accept a call that returns `false` as success, permanently freezing/misdirecting escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` settles escrow redemptions, refunds, and dust sweeps using a raw low-level `.call()` encoding the `IERC20.transfer` selector, and only checks that the *call itself* did not revert (`success`). It never decodes and checks the boolean return value of `transfer()`. Non-compliant tokens (common on Tron/TRC20, e.g. tokens that return `false` on failure instead of reverting, or tokens with no return data at all interpreted permissively) can cause this code to treat a failed transfer as successful.

### Finding Description
In `withdraw()`, which is invoked from `onAccept()` for `RequestKind.RedeemEscrow`/`RequestKind.RefundEscrow`, and from `onGetResponse()`: [1](#0-0) 

the token payout is performed as:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This only reverts if the external call itself reverts. If the token's `transfer()` implementation returns `false` on failure (a valid, standard-compliant ERC20/TRC20 behavior per the token standard, which does not mandate reverting), the low-level `call` still succeeds (`success == true`) with return data encoding `false`, so `!success` is `false` and no revert occurs.

The same unsafe pattern is used in the `SweepDust` handling branch inside `onAccept()`: [2](#0-1) 

and for the transaction-fee payout at the end of `withdraw()`: [3](#0-2) 

Meanwhile the same file elsewhere correctly uses `SafeERC20.safeTransferFrom` for pulling funds in (`placeOrder`) and imports `SafeERC20`: [4](#0-3) [5](#0-4) 

but the outbound payout paths in `withdraw()`/`SweepDust` deliberately bypass `SafeERC20.safeTransfer` in favor of the unchecked low-level call, exactly matching the reported bug class ("the code doesn't check these return values").

Crucially, `withdraw()` unconditionally decrements/deletes the escrow accounting (`_orders[body.commitment][token] -= amount;`, `delete _orders[...][TRANSACTION_FEES]`) and marks the order `_filled[body.commitment] = beneficiary` regardless of whether the token transfer actually moved funds: [6](#0-5) 

So for a token that returns `false` instead of reverting, the escrow bookkeeping is wiped out and the order is marked filled/refunded, but the beneficiary never receives the tokens — the funds remain stuck in the contract with no accounting path to recover them (no escrow entry left to redeem, no revert to retry).

### Impact Explanation
For any TRC20/ERC20 asset onboarded to the Tron `IntentGatewayV2` that follows the "return false on failure" semantics (a real-world pattern, especially plausible for non-standard or third-party Tron tokens, and this is precisely the audit-flagged risk class), a relayer-delivered `RedeemEscrow`/`RefundEscrow` message or a Hyperbridge-dispatched `SweepDust` message can silently fail to deliver tokens to the beneficiary while the contract's internal accounting proceeds as if the transfer succeeded. This causes:
- Permanent loss of the solver's/user's expected payout (their escrowed input tokens or transaction fee are debited from `_orders` without being received).
- Funds becoming permanently stuck in the `IntentGatewayV2` contract with no remaining escrow record to claim them.

This is reachable by any relayer submitting a normal settlement message (an unprivileged, expected message-delivery path), not requiring any malicious admin/governance action.

### Likelihood Explanation
Likelihood depends on whether a listed input/fee/dust token on the Tron deployment implements `transfer` in a non-reverting, boolean-returning-false manner on failure (insufficient balance edge cases, blacklists, paused states, etc.) — a real and common occurrence for TRC20 tokens on Tron. Any such token being configured as an order input, fee token, or dust asset triggers the bug on the very first failed transfer condition (e.g., blacklisted beneficiary, paused token, insufficient contract balance due to a race), with no attacker action required beyond normal relaying of settlement messages.

### Recommendation
Replace all `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and validates the boolean return value (and tolerates tokens with no return data) — consistent with the pattern already used for `safeTransferFrom` in `placeOrder` in the same contract.

### Proof of Concept
1. Deploy/onboard a TRC20 token on the Tron `IntentGatewayV2` whose `transfer()` returns `false` (instead of reverting) when, e.g., the recipient is blacklisted or the contract's balance momentarily can't cover the amount.
2. A user places an order with this token as an input; escrow amount is stored in `_orders[commitment][token]` via `safeTransferFrom` on `placeOrder` (funds correctly pulled in).
3. On settlement, a relayer delivers a `RedeemEscrow` request; `onAccept()` calls `withdraw(body, false)`.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; the token's internal logic returns `false` without reverting (`success == true`).
5. `!success` evaluates `false`, so no revert; `_orders[commitment][token] -= amount` deletes the escrow record and `_filled[commitment] = beneficiary` marks the order filled, even though the beneficiary's balance never increased.
6. The tokens remain locked in the `IntentGatewayV2` contract with no surviving escrow entry to reclaim them — a permanent loss for the beneficiary.
