### Title
Removing a chain from a Hyper Fungible Token via `update_token` permanently strands in-flight funds by making `on_timeout` unresolvable - ([File: modules/pallets/hyper-fungible-token/src/lib.rs, modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token::update_token` lets `CreateOrigin` remove a chain's `Precisions`/`TokenContracts` entries for an asset while ordinary users' previously-dispatched `send()` requests to that chain are still in flight. When such a request later times out, `on_timeout` looks up `Precisions::<T>::get(local_asset_id, dest)` and `ContractToAsset::<T>::get(dest, &to)`, both of which have been deleted, causing the callback to error and the escrowed/burned funds to become unrecoverable — mirroring the JUSDV1 pattern where a governance "delisting" action removes state that an in-flight/held user position still depends on, breaking the safe unwind path.

### Finding Description
An unprivileged user calls `send()` [1](#0-0) , which locks native assets in escrow or burns non-native assets, then dispatches a `DispatchPost` request to the destination chain via `pallet-ismp`. At this point the user's funds are held by the pallet, contingent on either successful delivery (`on_accept` on the remote side) or, if the request times out, a refund via `on_timeout` on this chain [2](#0-1) .

`update_token`, callable by `CreateOrigin`, can remove a chain's configuration for the asset at any time — deleting `ContractToAsset` and `Precisions` entries for that `(chain, asset)` pair, with no check for pending in-flight requests to that chain: [3](#0-2) 

When the earlier `send()` later times out (via the timeout handler in `modules/ismp/core/src/handlers/timeout.rs`), `on_timeout` re-derives the asset via `ContractToAsset::<T>::get(dest, &to)` and the decimals via `Precisions::<T>::get(local_asset_id, dest)`: [4](#0-3) 

If either lookup fails (because `update_token` removed the chain), `on_timeout` returns `Err(HftError::UnknownContractOnTimeout)` or `Err(HftError::DecimalsNotConfigured(dest))` instead of `Ok`. Per the ISMP timeout handler's documented invariant, when the module callback does not return `Ok`, the commitment is *not* deleted and the timeout can be replayed — but is also never resolved: [5](#0-4) [6](#0-5) 

Since the failure is deterministic (the storage that `on_timeout` needs is permanently gone unless governance re-adds an identical chain config), every future timeout replay attempt will fail identically. The user's escrowed/burned funds are permanently stuck with no code path to reconstruct the missing `Precisions`/`ContractToAsset` entries for their specific pending request, since `send()` no longer knows about the chain either (`TokenContracts` lookup would fail there too, so the user cannot re-send).

### Impact Explanation
This is a permanent freezing-of-funds bug reachable purely by an unprivileged user's normal `send()` call combined with a routine, non-malicious governance maintenance action (removing a stale/deprecated chain from a token's config, analogous to "delisting a reserve" in the JUSDV1 report). The user's collateral/asset value is neither refunded nor delivered — it is stuck in the pallet's escrow account (for native assets) or simply burned with no possibility of remint (for non-native assets), constituting a direct, permanent loss of user funds. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is meaningful in any deployment where `update_token` is used operationally to rotate/deprecate chain configurations (e.g., migrating to a new contract address or discontinuing support for a chain) while there exist in-flight `send()` requests with non-trivial timeout windows. Given that `send()` requests can have arbitrarily long `timeout` values and settlement can be delayed by relayer/consensus latency, there is a realistic window in which a `remove_chains` update can race an outstanding request.

### Recommendation
- Do not fully remove `Precisions`/`ContractToAsset`/`TokenContracts` entries for a chain in `update_token` while any requests dispatched to that chain are still outstanding; instead, retain them (or a snapshot) until all pending requests to that destination have resolved (delivered or timed out), or implement a soft-delist that keeps historical precision/contract data available strictly for `on_timeout` resolution.
- Alternatively, have `on_timeout` capture and encode the erc/local decimals and contract mapping into the outgoing request body (or ISMP request metadata) at `send()` time, so refunds never depend on mutable, subsequently-alterable storage.
- Add explicit handling: if `on_timeout` cannot resolve chain config, still refund at the asset's *current* decimals/config as a fallback rather than reverting the whole callback, ensuring the user's funds are recoverable even if precision‑exactness is imperfect.

### Proof of Concept
1. `CreateOrigin` registers asset `X` for `StateMachine::Evm(A)` via `register_token`, setting `TokenContracts`, `ContractToAsset`, `Precisions` for `(A, X)`. [7](#0-6) 
2. Alice (unprivileged) calls `send(params { asset_id: X, destination: A, amount, timeout: T })`. Her tokens are escrowed/burned and a `DispatchPost` is emitted with commitment `C`. [8](#0-7) 
3. Before the request is delivered or times out, `CreateOrigin` calls `update_token(asset_id: X, remove_chains: [A])`, deleting `TokenContracts::(A, X)`, `ContractToAsset::(A, <old contract>)`, and `Precisions::(X, A)`. [3](#0-2) 
4. Time passes beyond `T` and no delivery occurred. A relayer submits a timeout proof; `pallet-ismp`'s timeout handler deletes the request commitment and invokes `Pallet::<T>::on_timeout(request)`. [9](#0-8) 
5. Inside `on_timeout`, `ContractToAsset::<T>::get(A, &to)` returns `None` (removed in step 3) → returns `Err(HftError::UnknownContractOnTimeout)`. [10](#0-9) 
6. Because the callback errored, the handler restores the request commitment (per its documented retry design) rather than crediting Alice, and every retry of the timeout replays the same failure since the chain config is permanently gone. [5](#0-4)  Alice's escrowed/burned funds are now permanently unrecoverable.

			// Lock or burn the local asset

						params.asset_id.clone(),

						Fortitude::Polite,
					)?;
				}

					params.asset_id.clone(),
				)
			};

			// Encode the Message body
			let sender: [u8; 32] = who.clone().into();
			let amount: u128 = params.amount.into();
			let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);

			let token_message = Message {
				from: sender.to_vec().into(),
				to: params.recipient.to_vec().into(),
				amount: alloy_primitives::U256::from_be_bytes(erc20_amount.to_big_endian()),
				data: params.call_data.unwrap_or_default().into(),
			};

			let dispatch_post = DispatchPost {
				dest: params.destination,
				from: PALLET_ID.to_bytes(),
				to: token_contract,
				timeout: params.timeout,
				body: Message::abi_encode(&token_message),
			};

			let metadata = FeeMetadata { payer: who.clone(), fee: params.relayer_fee.into() };
			let commitment = dispatcher
				.dispatch_request(DispatchRequest::Post(dispatch_post), metadata)
				.map_err(|_| Error::<T>::DispatchError)?;

			Self::deposit_event(Event::<T>::TokenSent {
				from: who,
				to: params.recipient,
				dest: params.destination,
				amount: params.amount,
				commitment,
			});
			Ok(())
		}

		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}

			Self::deposit_event(Event::<T>::TokenRegistered {
				asset_id: registration.local_id,
				native: registration.native,
				chains,
			});
			Ok(())
		}

		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_timeout` does not return `Ok`, the commitment of the relevant messages will not be deleted, allowing the timeout to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their timeout handler. This model ensures that if a timeout cannot be executed successfully, it can be retried later.
