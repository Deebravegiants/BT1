### Title
Webhook shop/topic/webhook-id identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC signature it validates only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that the gem hands to the app's webhook handler are read straight from unauthenticated HTTP headers and play no part in the signature computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are never mixed into the HMAC input: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string and, on success, forwards the *unauthenticated* `request.shop`/`request.topic`/`request.webhook_id` straight to the app's handler as trusted tenant identity: [3](#0-2) 

`HmacValidator.validate` only compares `verifiable_query.hmac` against a signature computed from `to_signable_string`, i.e., the body — nothing else: [4](#0-3) 

The identity binding the gem implicitly claims to provide (per the docs, `process` "will verify the request did indeed come from Shopify" for *this* shop/topic/event) is actually: `HMAC-verified bytes (body only) == shop/topic/webhook_id used by the app`. That equality does not hold — an attacker who possesses *any* valid `(body, hmac)` pair signed with the app's `api_secret_key` (e.g., from a webhook Shopify legitimately sent to the attacker's own store, since the attacker is a normal, unprivileged merchant who installed the app) can replay that exact body+HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers to any other tenant. The signature still validates because those headers were never signed, and the handler receives forged tenant/topic identity as if Shopify itself asserted it.

### Impact Explanation
This breaks the tenant boundary the webhook system is meant to enforce: a merchant with a legitimate install (unprivileged relative to other tenants) can inject webhook events that the app attributes to a different merchant's shop, corrupting or exfiltrating cross-tenant state depending on what the handler does with `data.shop`/`data.body` (e.g., writing order data, triggering uninstall/re-auth flows, or app-uninstalled handling for a victim shop). This is a cross-tenant access/data-integrity break driven purely by a gap in this gem's identity binding.

### Likelihood Explanation
Any real merchant/tenant of the app can obtain a validly-HMAC-signed body for their own shop (Shopify sends it to them legitimately), then trivially replay it to the shared webhook endpoint with forged Shopify headers, since none of `shop`, `topic`, or `webhook_id` factor into the signature. No access to `api_secret_key`, access tokens, or privileged accounts is required — only normal use of the app as any merchant.

### Recommendation
Bind the tenant/topic identity into the verified data: include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them to the payload), or at minimum require callers of `Registry.process` to cross-check `request.shop` against a known/installed shop for the session before invoking the handler, and document this requirement clearly since it is not currently enforced by the library.

### Proof of Concept
1. App is installed on attacker's own store `attacker.myshopify.com`, which is a legitimate tenant.
2. Shopify sends a real webhook (e.g. `orders/create`) to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` and replays it to the same endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally forges `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request#hmac` decodes the forged header, `to_signable_string` still returns `B`; `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and it matches `H`, so validation passes.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: forged_topic, shop: "victim.myshopify.com", body: parsed(B), ...)`, and the app processes data for `victim.myshopify.com` that Shopify never actually sent for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
