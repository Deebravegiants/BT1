### Title
Webhook HMAC signature does not cover the `shop-domain` (or `topic`/`webhook-id`) header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` only proves the *body* bytes are untampered. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read directly from unauthenticated request headers and handed to the webhook handler as trusted identity data, even though none of them are covered by the signature.

### Finding Description
`Request#hmac` is computed from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, and `Registry.process` validates it against `to_signable_string`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; it does not fold in `shop`, `topic`, or `webhook_id`: [2](#0-1) [1](#0-0) 

`Registry.process` validates HMAC then trusts `request.shop`, `request.topic`, and `request.webhook_id` when constructing the metadata passed to the app's handler: [3](#0-2) 

Because `OpenSSL.secure_compare(computed_signature, received_signature)` in `HmacValidator` only checks the body bytes against the secret: [4](#0-3) 

the identity binding the app relies on — "shop that produced this signed payload" == "shop attributed to this webhook event" — is not actually enforced. Any body+HMAC pair that was legitimately produced for one shop (e.g. by installing the app on an attacker-controlled shop and capturing its own valid webhook, many of which have static/predictable bodies such as `{}` for `app/uninstalled`, `shop/redact`, etc., as seen in the test fixture using body `"{}"`) remains valid when replayed with a different `x-shopify-shop-domain` header value pointing at a victim shop. `Registry.process` will accept it and dispatch the handler with the attacker-chosen `shop`.

### Impact Explanation
This breaks the equality: `shop covered by HMAC == shop attributed to the webhook event delivered to the handler`. An unprivileged attacker who can produce one validly-signed webhook payload (trivially available by installing the app on their own store, since the API secret is not needed) can forge webhook deliveries — including control-plane topics like `app/uninstalled` or GDPR topics (`shop/redact`, `customers/redact`) — attributed to any other shop that has installed the app, since `topic` and `webhook-id` are equally unauthenticated. Depending on how the host app's handler acts on `WebhookMetadata#shop` (e.g. purging tokens/sessions, deactivating installs, deleting customer data), this enables cross-tenant interference/data manipulation without the app's `client_secret` or any credential belonging to the victim shop.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled development/trial shop to legitimately receive one HMAC-signed webhook with a body that is shop-independent or attacker-known (common for empty-body system topics), and (2) replaying that raw body + HMAC header combination against the app's webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or privileged access to the victim shop are required, making this reachable by any unprivileged internet user who can become an app installer.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the string that is HMAC-verified, or independently bind the shop domain used for dispatch to a value that Shopify's signature actually covers, so header values cannot be swapped independently of the signed body.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger (or wait for) a webhook delivery for a topic with a static/empty body, e.g. `app/uninstalled` with body `{}`; capture the raw body and the `x-shopify-hmac-sha256` header value — this HMAC is valid because it's computed by Shopify over the body with the real `api_secret_key`.
3. Replay a request to the app's webhook endpoint using the exact same raw body and `x-shopify-hmac-sha256` value, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (as in `lib/shopify_api/webhooks/request.rb`'s `to_signable_string`, only the body is checked), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)`, causing the host app to act on the victim shop's account under attacker control.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
