### Title
Webhook shop identity is not covered by HMAC verification, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body against the HMAC header, but the `shop` value used downstream as the tenant identifier is taken from an unauthenticated HTTP header and never bound to the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the request purely by checking `Utils::HmacValidator.validate(request)` — which recomputes `HMAC(secret, raw_body)` and compares it to the `hmac` header — and then, without any further check binding `shop` to the verified bytes, forwards `request.shop` to the handler as the trusted tenant identifier: [3](#0-2) 

The `HmacValidator` itself only ever checks the signable string produced by the request object, never any header value: [4](#0-3) 

This reproduces the report's bug class exactly: a record acted upon (`shop`, used as the tenant key passed to the host app's handler) is not covered by the HMAC that is supposed to authenticate the whole message, so the equality the library implicitly claims — `hmac_verified(shop_header) == hmac_verified(body)` — does not hold. Only the body is verified; the shop header is merely parsed and trusted.

### Impact Explanation
This breaks the tenant/shop authentication boundary between distinct merchants (a cross-tenant identity binding), which the "Reject analogs..." rule explicitly calls out as in-scope ("a shop authenticated versus the shop stored as a session key"). A host application built on this gem's documented API (`WebhookMetadata#shop`, as returned by `Registry.process`) has no means, using this library alone, to detect that the `shop` value was not actually the origin of the signed bytes — enabling cross-tenant data manipulation once webhook data is persisted keyed by that field.

### Likelihood Explanation
Exploitation requires an attacker to possess one genuine signed webhook delivery (raw body + valid HMAC) for a shop under their control (trivial: install the app on their own store and trigger any webhook event), then replay that exact body/HMAC pair to the target app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. No secret, access token, or privileged access is required — only the ability to send arbitrary HTTP requests to the app's public webhook URL, i.e., an unprivileged internet user.

### Recommendation
Include the shop domain (and other routing-critical headers such as topic) in the value verified by the HMAC check, or independently corroborate `request.shop` against data embedded in the verified body / a previously registered per-shop webhook secret before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-lookup key without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# 1. Attacker triggers any webhook (e.g. orders/create) and captures the
#    genuine raw body + "x-shopify-hmac-sha256" header sent by Shopify.
raw_body = captured_raw_body
valid_hmac_header = captured_hmac_header

# 2. Attacker POSTs the same body/HMAC to the app's webhook endpoint,
#    but swaps the shop-domain header to the victim's shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_header,   # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation succeeds because it only checks raw_body against the secret.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker's order data, ...))
```
The host app's handler receives data attributed to `victim-shop.myshopify.com` even though the payload actually originated from and was signed for `attacker-shop.myshopify.com`.
