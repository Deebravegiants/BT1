### Title
Unbounded RAY index accrual permanently freezes market withdrawals and repayments - (File: common/src/rates/scaling.rs)

### Summary
A large, highly utilized market can grow `borrowed * borrow_index` or `supplied * supply_index` beyond `i128::MAX` before the configured index ceiling is reached. Because every pool mutation first synchronizes interest and the unscale operation panics on overflow, the market becomes permanently unable to repay, withdraw, liquidate, or accrue without a privileged upgrade. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Controller::update_indexes(caller, assets)` is permissionless and forwards the attacker-selected `Vec<HubAssetKey>` to the pool after `caller.require_auth()`. [4](#0-3) [5](#0-4) 

The pool loads each selected market and calls `interest::global_sync`. [6](#0-5) 

`global_sync` processes elapsed ledger time in bounded chunks and calls `accrue_step`; the resulting borrow index, supply index, and revenue shares are committed to the cache. [7](#0-6) [8](#0-7) 

During accrual, utilization derives RAY-denominated totals through `scaled_to_original`, which multiplies scaled shares by the corresponding index and panics when the resulting value does not fit `i128`. [9](#0-8) [2](#0-1) 

Spoke caps only constrain the initial asset-to-RAY representation to approximately `i128::MAX / 10^(27-decimals)`; they do not reserve headroom for later index multiplication. [10](#0-9) [11](#0-10) 

The documentation explicitly acknowledges that valid caps and bounded indexes do not prevent accrued values from overflowing before the index ceiling. [12](#0-11) 

### Impact Explanation
Once the scaled market total crosses the representable RAY-value boundary, `update_indexes` reverts and leaves `last_timestamp` behind, so later calls attempt the same overflowing accrual again. [13](#0-12) [7](#0-6) 

This permanently freezes supplier principal and accrued yield because `withdraw` loads an interest-synced market before resolving or burning supply shares. [14](#0-13) [15](#0-14) 

Borrowers also cannot reduce the overflowing debt because `repay` performs the same synchronized load before resolving and burning debt shares. [16](#0-15) [15](#0-14) 

The repository’s own regression test demonstrates that a sufficiently large market hits `MATH_OVERFLOW` inside `scaled_to_original` before `MAX_BORROW_INDEX_RAY`, after which both withdrawal and repayment fail with the same error. [3](#0-2) 

### Likelihood Explanation
The attacker must create or borrow in a market whose scaled balance is close enough to the `i128` RAY-domain boundary for index growth to overflow it. The admitted cap maximum is about 170.14 billion whole tokens depending on decimals, so this requires extreme liquidity and a market configuration near the protocol’s arithmetic limits. [17](#0-16) 

The trigger itself is permissionless: after borrowing within the configured collateral, borrow cap, and utilization limits, any address can call `update_indexes(caller, [hub_asset])`. [4](#0-3) [5](#0-4) 

The concrete harness condition uses one-billion whole 18-decimal tokens and sustained 98% utilization, making exploitation capital-intensive but mechanically reproducible rather than dependent on oracle manipulation, privileged calls, leaked keys, or third-party contract behavior. [18](#0-17) 

### Recommendation
Constrain market and position entries so `scaled_amount * maximum_possible_index` remains representable, rather than bounding only the initial token-to-RAY conversion. [10](#0-9) [19](#0-18) 

Accrual should also detect the value-domain boundary before evaluating utilization and clamp or stop index growth in a recoverable state, so repayment and withdrawal remain possible even when additional interest can no longer be represented. [9](#0-8) [20](#0-19) 

### Proof of Concept
1. From one unprivileged address `A`, create an account with `supply(A, 0, spoke_id, [(VICTIM_ASSET, N_V), (COLLATERAL, N_C)])`, where both amounts are below their configured caps but `N_V` is large enough that the resulting RAY-scaled supply has little `i128` headroom. [21](#0-20) [22](#0-21) 
2. Call `borrow(A, account_id, [(VICTIM_ASSET, N_B)], None)` with `N_B` chosen to keep post-borrow health factor above one and utilization below the configured maximum while approaching the market cap. [23](#0-22) [24](#0-23) 
3. Allow the market to remain untouched while positive borrow interest grows `borrow_index`; then call `update_indexes(A, [VICTIM_ASSET])`. [4](#0-3) [6](#0-5) 
4. `global_sync` reaches `scaled_to_original(borrowed, borrow_index)` and raises `MathOverflow` when the exact RAY debt value exceeds `i128::MAX`. [7](#0-6) [2](#0-1) 
5. Subsequent `withdraw`, `repay`, `liquidate`, `borrow`, and `update_indexes` calls for that market all load an interest-synced cache first and therefore repeat the same overflow; the existing harness test asserts this exact frozen outcome for repayment and withdrawal. [25](#0-24) [26](#0-25)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}
```

```rust
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
```

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```
