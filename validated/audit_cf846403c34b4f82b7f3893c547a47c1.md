### Title
Permissionless third-party `supply` restamps a victim's stored LTV and can freeze collateral withdrawals - ([File: contracts/controller/src/positions/supply.rs](contracts/controller/src/positions/supply.rs))

### Summary
`supply` intentionally allows an arbitrary authenticated caller to add funds to an existing supply leg of another account, but the merge path also refreshes that leg's stored LTV from the live spoke configuration. After governance lowers an asset's LTV, an attacker can donate a dust amount to a victim's existing position and persist the lower LTV without the account owner's authority. If the victim's debt exceeds the newly LTV-weighted collateral while its health factor remains above 1, later withdrawals and borrows revert, temporarily freezing the collateral until enough debt is repaid or the LTV is restored.

### Finding Description
`process_supply` requires only `caller` authorization and lets a non-owner/non-delegate supply to an existing account as long as every submitted hub asset is already present in `account.supply_positions`. [1](#0-0)  The third-party restriction checks only slot existence; it does not prevent the subsequent write from mutating the victim's risk snapshot. [2](#0-1) 

Every supply leg reaches `merge_supply_leg`, which loads the current `AssetConfig` and calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`. [3](#0-2)  That refresh unconditionally assigns `position.loan_to_value = effective_config.loan_to_value`, even when the liquidation threshold/bonus/fee tuple is correctly held back by the health-factor gate. [4](#0-3) 

The borrow/withdraw solvency gate values collateral using each position's stored `min(loan_to_value, liquidation_threshold)`. [5](#0-4)  For any account that still has debt, `require_post_pool_risk_gates` requires `ltv_collateral >= total_debt` in addition to `health_factor >= 1`. [6](#0-5)  A dust supply therefore lets a stranger write the victim's stored LTV and can move `ltv_collateral` below the existing debt even though the account remains non-liquidatable under the unchanged liquidation threshold.

### Impact Explanation
The attacker can temporarily freeze the victim's collateral. The victim retains ownership and the added dust increases collateral, but withdrawal and further borrowing revert until the debt is reduced below the new LTV-weighted collateral or governance restores the parameter. This matches the "view/write permission mismatch" bug class: a low-privilege top-up path performs a security-relevant account-parameter write that should require account-owner/delegate authority.

The impact is temporary rather than permanent because anyone may repay the victim's debt, and `repay` is permissionless with excess refunded to the payer. [7](#0-6)  Still, a victim who lacks the debt asset cannot immediately exit, and integrators/keepers may be forced into an unplanned repayment before collateral can be withdrawn.

### Likelihood Explanation
The attack needs a governance LTV decrease for an already-held supply asset and a victim whose debt is between the new LTV bound and the liquidation-threshold bound. That is a plausible risk-parameter tightening scenario, and the trigger costs only a minimal amount of the existing collateral asset. No victim signature, delegate grant, liquidation eligibility, or account compromise is required.

The issue does not let the attacker seize collateral directly, because the liquidation tuple remains gated and HF can remain above 1. The practical effect is a temporary withdrawal/borrow denial rather than theft, so Medium is the appropriate severity.

### Recommendation
Do not run `RiskRefreshScope::FullTuple` or persist an LTV restamp from a third-party `supply`. Track whether `caller` passed `require_owner_or_delegate`; for foreign top-ups, merge only the pool supply shares and preserve the existing stored `loan_to_value`, `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees`. Alternatively, require owner/delegate authorization for any `supply` call that would change an existing position's risk snapshot. Add a regression test where a stranger tops up an existing leg after an LTV decrease and the victim's stored tuple remains unchanged.

### Proof of Concept
Assume a listed asset initially has `LTV = 7500` and `LT = 8000`.

1. Victim supplies `$10,000` of the asset and borrows `$6,000` of another asset.
   - Stored LTV is `7500`, so LTV collateral is `$7,500`.
   - Weighted collateral is `$8,000`, so HF is approximately `1.33`.
2. Governance changes the asset's listed LTV to `5000` without changing `LT`.
3. Attacker calls:

```text
supply(
  caller = attacker,
  account_id = victim_account,
  spoke_id = victim_spoke,
  assets = [(victim_collateral_hub_asset, 1)]
)
```

4. The call is authorized by `attacker`, passes the existing-slot check, transfers one unit to the pool, and persists `loan_to_value = 5000` on the victim's position.
5. The victim then calls `withdraw` for any amount while the `$6,000` debt remains.
6. The risk gate calculates LTV collateral as approximately `$5,000`; because `$5,000 < $6,000`, it reverts with `InsufficientCollateral`.
7. Withdrawals remain blocked until debt is repaid to `$5,000` or less, despite HF remaining above 1 under the unchanged liquidation threshold.

/// Supplies collateral, creating an account when `account_id` is zero.
/// Third parties may only add to existing supply positions. Returns the account id.
pub(crate) fn process_supply(
    env: &Env,
    caller: &Address,
    account_id: u64,
    spoke_id: u32,
    assets: &Vec<HubPayment>,
) -> u64 {
    validation::require_authorized_caller(env, caller);
    let aggregated = payments::aggregate_positive_payments(env, assets);
    let mut cache = Context::new(env);

    let (acct_id, mut account) = account::load_or_create_account(
        env,
        caller,
        account_id,
        spoke_id,
        PositionMode::Normal,
        account::AccountGuard::Supply,
        &mut cache,
    );

    require_third_party_existing_supply(env, account_id, acct_id, caller, &account, &aggregated);

    process_deposit(env, caller, &mut account, &aggregated, &mut cache);

/// Requires debt coverage by LTV-weighted collateral, health factor >= 1, and
/// the configured collateral floor. Debt-free accounts skip all three checks.
pub(crate) fn require_post_pool_risk_gates(env: &Env, cache: &mut Context, account: &Account) {
    if account.debt_free() {
        return;
    }

    let totals = risk::calculate_account_risk_totals(
        env,
        cache,
        &account.supply_positions,
        &account.borrow_positions,
    );

    assert_with_error!(
        env,
        totals.ltv_collateral >= totals.total_debt,
        CollateralError::InsufficientCollateral
    );

    spec_hooks::solvency_gate_checked(account);

    assert_with_error!(
        env,
        totals.health_factor >= Wad::ONE,
        CollateralError::InsufficientCollateral
    );

    let floor = storage::get_min_borrow_collateral_usd_wad(env);
    if floor != 0 && totals.ltv_collateral.raw() < floor {
        panic_with_error!(env, CollateralError::MinBorrowCollateralNotMet);
    }
