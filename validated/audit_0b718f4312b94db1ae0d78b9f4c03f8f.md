### Title
Attacker-controlled QR `parameters` octal value ≥8 triggers `assert_eq!` panic in `SweepConfiguration::parse_configuration_value`, crashing the signup thread - ([File: src/plans/biometric_capture/focus_sweep.rs])

### Summary
The Focus Sweep extension parses the QR-supplied `parameters` string as an octal `u8` via `u8::from_str_radix(parameter, 8)`, which accepts any valid octal digit string producing values in the full `u8` range (0–255). `parse_configuration_value` then asserts the value's 3-bit binary representation is exactly 3 characters long, an invariant that only holds for values 0–7. Any octal string parsing to 8 or greater (e.g. `"10"`, `"77"`, `"377"`) satisfies `from_str_radix` but violates this assumption and panics.

### Finding Description
`Plan::from` at [1](#0-0)  extracts `parameters` from `biometric_capture.signup_extension_config` (populated from the attacker's own user QR code, which specifies `mode: FocusSweepExtension` and a `parameters` field) and converts it with `u8::from_str_radix(parameter, 8).ok()`. This call succeeds for any string of octal digits ('0'-'7') representing values up to 255 (e.g. `"10"` → 8, `"77"` → 63, `"377"` → 255), not just 0–7 as intended by the "octal (<=3 bit)" comment.

`SweepConfiguration::new` then calls `parse_configuration_value` at [2](#0-1) , which formats the value as a zero-padded binary string with `format!("{configuration_value:0>3b}")`. For values ≥8, this produces 4+ characters (e.g., 8 → `"1000"`), and the subsequent `assert_eq!(binary_repr.chars().count(), 3, ...)` panics.

No validation clamps or rejects `configuration_value` before this assertion — the doc comment even flags this as a known gap ("TODO: Move parsing of configuration flag to QR code scanning phase -> Handle/Fail early" at line 159). The panic occurs inside the orb's signup execution flow (`Plan::from` invoked when entering the focus-sweep extension during biometric capture), unwinding the task/thread running the signup plan.

### Impact Explanation
This is a denial-of-service against the signup flow: an attacker presenting a self-crafted QR code with `mode='focus-sweep'` and a `parameters` value that parses to ≥8 in octal causes a panic that aborts the in-progress biometric capture/signup session. Depending on the panic-handling/supervision around the orb's async task executor, this can crash the signup thread mid-capture, disrupting the orb's operation for that session (and potentially requiring a restart), which matches an availability-impact bounty category rather than a direct authorization/identity-binding bypass.

### Likelihood Explanation
Precondition is that the orb build has extension-mode QR parsing enabled and the attacker scans their own QR code before biometric capture begins — no operator privilege, secrets, or hardware tampering required. The exploit is deterministic and trivially repeatable: any octal parameter string decoding to a value ≥8 (e.g. `"10"`, `"77"`, `"377"`) reaches the vulnerable assertion every time `Plan::from`/`SweepConfiguration::new`/`reset_extension` is invoked with that configuration.

### Recommendation
Validate and clamp `configuration_value` to the 0–7 range immediately after parsing (e.g., reject/mask values outside 0–7, or use `parameter.parse::<u8>()` bounded check) before constructing `SweepConfiguration`, or replace the `assert_eq!` with a graceful fallback (e.g., default configuration) instead of panicking on malformed/out-of-range values from untrusted QR input. Apply the same fix to the parallel logic in `src/plans/biometric_capture/mirror_sweep.rs`, which has the identical pattern.
