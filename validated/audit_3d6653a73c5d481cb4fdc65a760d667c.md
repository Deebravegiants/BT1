This confirms the analog. The gem's documentation at `docs/usage/webhooks.md:12-14` explicitly tells app developers that `data.shop` is "The shop domain of the webhook" — implying it is a trusted, verified identity field — yet the HMAC that `Registry.process` validates only covers the raw JSON body, never the shop-domain header.

### Title
Webhook HMAC does not bind the `shop` field, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `shop` value that is handed to the app's handler as an authenticated identifier is read straight from the `X-Shopify-Shop-Domain` header, which is completely outside the signed material [2](#0-1) [3](#0-2) .

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the Shopify-supplied headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) participate in the signature [3](#0-2) . `Registry.process` treats a successful HMAC check as proof the whole request "did indeed come from Shopify" (per the gem's own docs) and then forwards `request.shop` unmodified to the app's handler as `WebhookMetadata#shop` [5](#0-4) .

This breaks the identity binding: `shop_bound_by_hmac == shop_delivered_to_handler`. In truth, `shop_bound_by_hmac` is empty (the signature says nothing about which shop the body belongs to), while `shop_delivered_to_handler` is an attacker-controlled HTTP header.

Because the same `client_secret` (and hence the same computed HMAC digest) is shared across every shop that installs a given app, any body/HMAC pair legitimately delivered for **Shop A** remains a fully valid signature for that exact same body regardless of which shop header accompanies it. An attacker who is a merchant/collaborator on Shop A (an app installer — not a privileged Shopify employee, not someone holding the app's `client_secret`) can:
1. Install the target app on Shop A and passively capture one legitimate webhook delivery (body + `X-Shopify-Hmac-Sha256` header) for a topic whose body is static, empty, or otherwise attacker-influenced (e.g. `app/uninstalled`, `shop/redact`, or any topic where fields can be filtered down to `{}`).
2. Replay that exact `raw_body` + `hmac` to the app's public webhook endpoint, substituting `X-Shopify-Shop-Domain: shop-b.myshopify.com` for an arbitrary victim shop the attacker does not control.
3. `HmacValidator.validate` still succeeds (it never looked at the shop header), so `Registry.process` invokes the app's handler with `data.shop == "shop-b.myshopify.com"` and attacker-influenced `data.body`.

The documented contract in `docs/usage/webhooks.md` tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is simply "the shop domain of the webhook" [6](#0-5) [7](#0-6) , encouraging host apps to trust `data.shop` as an authenticated tenant identifier for record lookups (as shown in the doc's own example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [8](#0-7) ) without independently re-verifying it.

### Impact Explanation
This is a cross-tenant access vector: an app-installing merchant on their own shop can forge webhook deliveries that the host application will process as if they originated from a different, unrelated shop. Depending on how the host app uses mandatory-compliance topics like `shop/redact` / `customers/redact` / `customers/data_request` (which this gem specially recognizes as `MANDATORY_TOPICS` [9](#0-8) ) or state-changing topics like `app/uninstalled`, this can trigger deletion of another merchant's data/tokens, corruption of another tenant's stored state, or forged compliance events attributed to a shop the attacker never installed the app on — a cross-tenant integrity/confidentiality breach satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any user capable of installing the target app on a shop they control (the minimum privilege level assumed for "unprivileged internet user" here, since app installation itself requires no special credential from the app developer) can capture one legitimate webhook and replay it with a forged header. No access to `client_secret`, access tokens, or TLS interception is required — only observation of one's own webhook traffic and the ability to POST to the app's public callback URL.

### Recommendation
Include the `shop-domain` header (and ideally `topic` and `webhook-id`) in the HMAC-signed material verified by `HmacValidator`, or otherwise reject/ignore the header-supplied `shop` and instead resolve the shop from a value that is cryptographically bound to the request (e.g., have `Webhooks::Request#to_signable_string` incorporate the shop domain so a mismatched header invalidates the signature). At minimum, document prominently that `data.shop` is unauthenticated and must not be trusted as a tenant identifier without independent verification (e.g., cross-checking against a known, previously-registered shop for that webhook subscription).

forged_headers = {

  "x-shopify-hmac-sha256" => valid_hmac,       # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unverified
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HmacValidator.validate (registry.rb:190), handler.handle receives
#    data.shop == "victim-shop.myshopify.com" despite the request never
