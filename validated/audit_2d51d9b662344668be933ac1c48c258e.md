### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` identifiers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain`, `topic`, `webhook-id`, and `api-version` header values to the app's handler as trusted metadata. None of these header fields are included in the signed content, so they can be freely substituted on any request that carries a body/HMAC pair the attacker already possesses.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Utils::HmacValidator.validate` verifies exactly that string against the shared `api_secret_key`: [2](#0-1) 

`Registry.process` uses this single check as the entire authentication gate, and then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all pulled straight from attacker-controlled HTTP headers — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding broken is: `hmac(raw_body, api_secret_key) == valid` is treated as equivalent to `shop-domain header == the shop that produced this event`, but `shop`, `topic`, `webhook-id`, and `api-version` are never part of `to_signable_string`. Since Shopify signs webhooks with the app's single `client_secret` (identical across every shop that installs the app), any party who can obtain one legitimately-signed webhook body/HMAC pair for their own shop can resend that exact body+HMAC while swapping the `shop-domain` (and/or `topic`/`webhook-id`) header to impersonate a different tenant shop. `Registry.process` will not detect this because the signature check never touches those headers.

### Impact Explanation
This breaks the cross-tenant boundary the gem is supposed to enforce for webhook consumers: an app built on this gem's `WebhookHandler` interface receives events it believes originate from a specific shop (`data.shop`) with HMAC-verified authenticity, when in fact only the body content was verified — the shop attribution is unauthenticated. A host application that uses `data.shop` to select the tenant's session/data to act on (the intended and documented usage pattern) can be made to apply another shop's webhook payload against a shop chosen by the attacker, which is a cross-tenant data-integrity issue.

### Likelihood Explanation
Exploitation requires the attacker to control (or install the app onto) at least one shop so they can capture one real, correctly-signed webhook delivery from Shopify. From there, forging headers on an HTTP request to the app's own webhook endpoint is trivial. This is a design property of Shopify's webhook signing scheme (body-only HMAC) surfaced unmitigated through this gem's `Request`/`Registry` implementation, since the gem provides no header-binding or replay/shop-consistency check of its own.

### Recommendation
Have `Registry.process` cross-check `request.shop` (and ideally `topic`/`webhook_id`) against data independently known to the app (e.g., only accept a `shop` value that already has an active, previously stored session, and reject unknown shops before invoking the handler), and document that consumers must not treat unauthenticated headers as fully trusted tenant identifiers even after HMAC success. At minimum, expose a way to detect header/body mismatches versus previously seen deliveries.

### Proof of Concept
1. Install (or otherwise legitimately control) the target app on shop `attacker-shop.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: `raw_body` and header `x-shopify-hmac-sha256`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-webhook-id`).
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because only `raw_body` is checked; `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app handler as if the event genuinely came from `victim-shop.myshopify.com`.
