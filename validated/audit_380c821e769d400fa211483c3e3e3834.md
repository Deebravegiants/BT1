### Title
Webhook Shop-Domain Spoofing via HMAC Covering Only the Raw Body, Not the Shop Identity - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` computes/verifies the signature exclusively over that string. The `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) — the field actually used by `Registry.process` to attribute the webhook to a tenant — is never included in the signed material. This breaks the identity binding between "bytes verified by HMAC" and "shop the payload is attributed to."

### Finding Description
`Registry.process` verifies a webhook exclusively via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body: [3](#0-2) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from unauthenticated HTTP headers: [4](#0-3) 

and `shop` is exactly the field handed to the host application's handler to determine which tenant the payload belongs to: [5](#0-4) 

The binding that should hold is:
`shop_bound_by_HMAC == shop_used_for_tenant_attribution`

Here, `shop_bound_by_HMAC` is undefined (the signable string never contains `shop`), while `shop_used_for_tenant_attribution = request.shop` (an unauthenticated header value). Any raw body/HMAC pair that is valid for one shop is therefore also valid — unchanged — for a request claiming to be from a different shop, because the header is not part of what's signed.

### Impact Explanation
An unprivileged internet user who can obtain any legitimate `(raw_body, hmac)` pair for a shop under their own control (e.g., by installing the target app on their own free/dev Shopify store and observing a real webhook delivery from Shopify) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still passes because it never checks the header, and `Registry.process` dispatches the handler with `shop: <victim shop>` and the attacker-originated body. This lets an attacker inject or spoof webhook events attributed to a shop they do not control — a cross-tenant integrity violation, matching the "cross-tenant access" Critical impact category, without ever needing the app's `client_secret` or an access token.

### Likelihood Explanation
The attacker only needs to be able to install the app on a shop they control (a normal, unprivileged action any developer/merchant can perform) and capture one legitimate webhook delivery to observe a valid `(body, hmac)` pair, then replay it against the same public webhook endpoint with a different `shop-domain` header. No secret material, TLS interception, or privileged access is required, so the likelihood is realistic for any deployment relying on `Registry.process`/`request.shop` for tenant attribution.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the HMAC-covered material, or independently verify that the `shop` header corresponds to a shop for which this exact `(topic, webhook_id)` was actually registered/expected, rather than trusting the header once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) with attacker-controlled body content.
2. Attacker captures the legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sends for that delivery.
3. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request#hmac`/`#to_signable_string` only look at the body, so `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:198-199`) invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body, causing the host application to process attacker data under the victim tenant's identity.
