### Title
Missing bounds validation on user-QR-controlled wavelength parameter causes panic in `Configuration::new` - (File: `src/plans/biometric_capture/overcapture.rs`)

### Summary
`overcapture::Configuration::new` and its helper `parse_wavelength_configuration` assume the `wavelength_parameter: u8` is always in the `0..=7` (3-bit/octal) range, but the value is derived from a string parsed with `u8::from_str_radix(parameter, 8)`, which happily accepts multi-digit octal strings that evaluate to values greater than 7 (up to 255). This is the same root-cause class as the reported yearn-vaults issue: a constructor/initializer (`Configuration::new`) accepts an externally-supplied value without validating it against the domain it actually expects, and the object is initialized in an inconsistent/unsafe state. [1](#0-0) 

### Finding Description
`Configuration::new(wavelength_parameter, duration)` stores `wavelength_parameter` and immediately calls `Configuration::parse_wavelength_configuration(wavelength_parameter)`: [1](#0-0) 

`parse_wavelength_configuration` formats the byte as a 3-bit binary string and asserts the resulting string is exactly 3 characters long: [2](#0-1) 

The value fed into this constructor comes from `parse_u8_octal`, which uses `u8::from_str_radix(src, 8)`: [3](#0-2) 

`from_str_radix` with radix `8` accepts arbitrary-length digit strings composed of characters `0-7` and computes their numeric value in base 8 — it does **not** restrict the result to `0..=7`. For example the 2-character string `"10"` parses to the byte value `8`, `"17"`→`15`, `"77"`→`63`, `"777"` → overflow (parse failure, falls back to default 1), but any two-digit combination between `"10"` and `"73"` (values 8–59) parses successfully and is passed straight into `Configuration::new` without any range check.

The `wavelength_parameter` string itself originates from the extension-config `parameters` field carried by the scanned QR-code payload (`biometric_capture.signup_extension_config`), which is populated during user QR-code parsing in `src/plans/qr_scan/user.rs` and threaded through `Plan::from<biometric_capture::Plan>` conversions in `overcapture.rs`, `focus_sweep.rs`, and `mirror_sweep.rs`: [4](#0-3) 

Because there is no validation step ensuring the parsed `wavelength_parameter` is `<= 7` before it reaches the `Configuration` constructor (nor before `reset()` re-parses it later), a value in the unvalidated range (8–63, or others that don't produce a 3-character binary string) reaches the `assert_eq!` in `parse_wavelength_configuration` and triggers a Rust panic.

### Impact Explanation
A panic triggered from an unprivileged, attacker-controlled QR-code parameter unwinds/aborts the plan-execution task that drives the biometric-capture/signup state machine. Depending on how the async task panic propagates through the broker/agent runtime, this can crash or wedge the in-progress signup flow, causing denial of service for the signup pipeline (repeatable by anyone able to present a QR code with a crafted `signup_extension_config` parameter string). This maps to the “fraud/liveness bypass or fraud/signup state corruption” impact category via denial-of-service/crash of the capture plan rather than data exposure, since no bounds check exists analogous to the missing constructor parameter validation described in the report.

### Likelihood Explanation
Likelihood is moderate-to-high: the `parameters` string is attacker/operator-controlled content embedded in a scanned QR code and reaches `parse_u8_octal` → `Configuration::new`/`reset()` with no intervening validation of the resulting numeric range, and the same unchecked pattern is duplicated across three extension modules (`overcapture.rs`, `focus_sweep.rs`, `mirror_sweep.rs`) that all rely on `u8::from_str_radix(parameter, 8)` without an explicit `<= 7` bound check. [5](#0-4) [6](#0-5) 

### Recommendation
Validate the parsed octal parameter explicitly before constructing `Configuration` (and before `reset()` re-parses it): reject or clamp any value outside `0..=7` instead of relying on the downstream `assert_eq!` to catch out-of-range input via a panic. E.g., change `parse_u8_octal` to reject values `> 7` and fall back to the default, or replace the `assert_eq!` in `parse_wavelength_configuration` with a graceful fallback/error path so malformed/out-of-range QR parameters cannot crash the signup plan.

### Proof of Concept
1. Craft a user QR-code payload whose `signup_extension_config.parameters` field is set to an octal string such as `"10"` (or `"10:1000"` to also control duration).
2. When the orb scans this QR code and builds `overcapture::Plan` via `From<biometric_capture::Plan>`, `parse_u8_octal("10", 1)` returns `8` (`u8::from_str_radix("10", 8) == Ok(8)`). [7](#0-6) 
3. `Configuration::new(8, duration)` calls `parse_wavelength_configuration(8)`, producing `binary_repr = "1000"` (4 characters), which fails the `assert_eq!(binary_repr.chars().count(), 3, ...)` check and panics. [2](#0-1) 
4. The panic aborts the executing task handling the signup/biometric-capture plan, disrupting the in-progress signup for that session.

impl Configuration {
    fn new(wavelength_parameter: u8, duration: Duration) -> Self {
        let overcapture_wavelengths =
            Configuration::parse_wavelength_configuration(wavelength_parameter);
        Self { wavelength_parameter, overcapture_wavelengths, overcapture_duration: duration }
    }

    fn reset(&mut self) {
        self.overcapture_wavelengths =
            Configuration::parse_wavelength_configuration(self.wavelength_parameter);
    }

    fn parse_wavelength_configuration(configuration_value: u8) -> VecDeque<IrLed> {
        let binary_repr = format!("{configuration_value:0>3b}");
        assert_eq!(
            binary_repr.chars().count(),
            3,
            "Overcapture wavelength parameter needs to be octal (<=3 bit)!"
        );
        let mut wavelength_vec = VecDeque::new();
        for (n, c) in binary_repr.char_indices() {
            if c == '1' {
                wavelength_vec.push_front(WAVELENGTH_LUT[n]);
            }
        }
        wavelength_vec
    }
