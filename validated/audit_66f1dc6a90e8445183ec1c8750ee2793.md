### Title
Zero-address module identity forges `RedeemEscrow`/`RefundEscrow` authentication for `IntentGatewayV2` cross-chain deliveries - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents._authenticate` verifies that an incoming cross-chain `PostRequest` originates from the registered `IntentGatewayV2` peer on the source chain by comparing the request's `from` field against `_instance(request.source)`. When the source chain has no registered gateway instance, `_instance()` returns the Solidity default `address(0)`. An attacker who dispatches an ISMP request from any state-machine that Hyperbridge already recognizes via a valid consensus proof — but on which the intents gateway has not yet been deployed/registered — can set `request.from` to 20 zero bytes and pass `_authenticate` trivially, because both sides of the comparison are `address(0)`.

### Finding Description
`_authenticate` is defined as: [1](#0-0) 

and is the only gate applied before `RedeemEscrow`/`RefundEscrow` bodies are decoded and acted on in `onAccept`: [2](#0-1) 

`_instance(chain)` reads the `_instances` mapping, which is only ever populated by `_addDeployment` when Hyperbridge governance registers a new remote gateway: [3](#0-2) 

For any state machine ID that Hyperbridge's consensus layer recognizes (i.e. can produce a verified `PostRequest` for) but for which no `IntentGatewayV2` deployment has been registered yet, `_instances[keccak256(source)]` is the unset default, `address(0)`. `_authenticate` decodes `module = address(bytes20(request.from))` from attacker-controlled request data and only checks `_instance(source) != module`. An attacker who can dispatch an arbitrary ISMP `PostRequest` from that unregistered/unrelated source chain (any contract on that chain can address a `PostRequest` to the victim gateway's module ID — dispatch is not restricted to "the IntentGatewayV2 module") simply sets `from` to 20 zero bytes. Both sides of the comparison become `address(0)`, and `_authenticate` passes as if the request had genuinely come from a deployed, registered peer gateway.

This mirrors the Allo `RFPSimpleStrategy` bug class exactly: an authorization check that is supposed to bind the caller/sender to a specific registered identity is defeated because the *default/unset* value of the registered-identity lookup coincides with an attacker-controlled encoding, letting an unauthorized party masquerade as authorized without ever being registered.

The remaining gate, `_checkRelayer`, only restricts *who relays the delivery to the handler*, not which source chain or module the message claims to be from: [4](#0-3) 
A legitimate, honest relayer (or, before governance arms `_relayer`, any relayer) will happily deliver a validly-proven message regardless of its forged `from` field, since relayers are not expected to validate application-level semantics.

### Impact Explanation
Once `_authenticate` is bypassed, the attacker's forged `RedeemEscrow`/`RefundEscrow` body is decoded and passed straight into `_withdraw`, releasing escrowed input tokens for an attacker-chosen `commitment`/`beneficiary`: [5](#0-4) 
This allows theft of escrowed order funds on the source chain — a direct loss of user/protocol funds, satisfying "concrete theft ... of funds" and "forged message delivery" / "unauthorized app action" criteria.

### Likelihood Explanation
Exploitability depends on the existence of at least one state machine that Hyperbridge's consensus verification recognizes but on which `IntentGatewayV2` has not (yet) been deployed/registered as a peer — a very plausible situation given deployments are rolled out incrementally by governance across many connected chains/parachains. The attacker only needs to be able to dispatch an ISMP `PostRequest` from that chain (any application contract/pallet capable of dispatching, not necessarily privileged) addressed to the victim gateway's module id, with a crafted `from` of 20 zero bytes, and have it relayed through the normal path. No malicious relayer, admin, or governance action is required.

### Recommendation
`_authenticate` must reject the zero-address case explicitly, e.g. `if (module == address(0) || _instance(request.source) != module) revert Unauthorized();`, so an unregistered source chain can never satisfy the check regardless of the attacker-chosen `from` value.

### Proof of Concept
1. Identify a state machine ID `X` that Hyperbridge's host already accepts consensus proofs for, but for which `_instances[keccak256(X)]` has never been set via `_addDeployment` (no `IntentGatewayV2` peer registered on `X`).
2. From any contract/pallet on chain `X`, dispatch an ISMP `PostRequest` addressed to the victim `IntentGatewayV2` module id on the destination chain, with body `bytes.concat(bytes1(uint8(RequestKind.RedeemEscrow)), abi.encode(WithdrawalRequest({commitment: <victim_commitment>, tokens: <victim_tokens>, beneficiary: <attacker>})))` and `from` set to `abi.encodePacked(address(0))` (20 zero bytes).
3. Have the message relayed normally (real consensus proof, real `_checkRelayer`-passing relayer) to `EvmHost.dispatchIncoming`, which calls `ExtrinsicIntents.onAccept`.
4. `onAccept` decodes `RequestKind.RedeemEscrow`, calls `_authenticate`, which computes `module = address(0)` from the forged `from`, compares against `_instance(X) == address(0)` (unset), passes, and proceeds to `_withdraw`, releasing escrowed tokens to the attacker's `beneficiary`.
