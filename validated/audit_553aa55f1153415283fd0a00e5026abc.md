### Title
Webhook processing trusts the `shop-domain` header, which is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` (and `topic`/`webhook-id`/`api-version`) HTTP headers as-is to identify the tenant, even though none of these headers are covered by the HMAC signature.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 

The HMAC validation is computed only over `to_signable_string`, which returns the raw body — headers are never part of the signable string: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` and `validate_signature` only ever look at `verifiable_query.hmac` and `verifiable_query.to_signable_string`, so the `shop` header is never included in the value that is HMAC-checked: [4](#0-3) 

Yet `Registry.process` passes `request.shop` — sourced directly and unvalidated from the `shopify-shop-domain`/`x-shopify-shop-domain` header — into the handler as the tenant identity for the webhook, with no cross-check against `ShopValidator` or any registered/known shop list: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop header value == shop whose secret produced the HMAC over this body`. Since the HMAC never covers the shop header, this equality is not enforced by the gem — any request with a valid `(body, hmac)` pair (for the app's own `api_secret_key`) will be accepted regardless of which `shop-domain` header accompanies it. An unprivileged attacker who installs the app on their own shop receives genuine webhook deliveries with valid HMACs computed over bodies they fully control content of (webhook bodies are largely attacker-influenced resource data, e.g. order/product fields). They can capture one such `(body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Registry.process` will accept it as authentic and invoke the handler with `shop: <victim-domain>`, `body: <attacker-controlled data>`.

### Impact Explanation
This breaks the identity binding between "who has valid credentials for this data" and "who this data is attributed to," corresponding to the report's bug-class pattern of a "field acted on but not covered by the HMAC." A downstream app relying on `WebhookMetadata#shop` (the gem's documented API, per `docs/usage/webhooks.md`) to scope tenant data (e.g., writing incoming order/product data keyed by `data.shop`) can be made to ingest attacker-controlled data under another merchant's identity — a cross-tenant data integrity/confusion issue. Depending on the handler's use of `data.body` and `data.shop`, this can enable cross-tenant data injection into another shop's records.

### Likelihood Explanation
Any developer/attacker can register their own (free/dev) Shopify store, install the target app, and receive genuine webhooks with valid HMACs for bodies whose content they substantially control (e.g., product/order titles, metafields, note fields). Replaying the captured body+HMAC with a modified `shop-domain` header requires only unauthenticated HTTP access to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed, satisfying the "unprivileged internet user" constraint.

### Recommendation
Bind the shop identity to the verified request. Either:
- Verify that `request.shop` corresponds to a shop your app has legitimately installed on (cross-check against your own tenant store) before trusting it as the dispatch key, and/or
- Include the `shop-domain` header (and ideally `topic`, `webhook-id`) in the HMAC-signable string, or otherwise cryptographically bind the header value to the signed payload, so that changing the header invalidates the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, and triggers a webhook (e.g., `products/update`) with attacker-controlled fields in the body.
2. Attacker's endpoint (or a captured request) yields the raw body `B` and the valid `x-shopify-hmac-sha256` header `H`, both genuinely signed by the app's real `api_secret_key` for `B`.
3. Attacker sends a new HTTP POST to the app's webhook route with body `B` unchanged, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and matches `H` — validation passes.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker's data, ...)`, causing the app to process/store attacker-controlled content attributed to the victim shop.
