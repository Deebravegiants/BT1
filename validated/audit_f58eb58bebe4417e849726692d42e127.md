I have sufficient evidence to finalize this finding. The docs explicitly say `Registry.process` "will verify the request did indeed come from Shopify" based on `data.shop` being trustworthy — but the HMAC signature only covers the raw body, not the `shop-domain` header.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by calling `Utils::HmacValidator.validate(request)`, which only checks the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns solely the raw request body [1](#0-0) . The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers that are never included in the signed bytes [2](#0-1) , yet `Registry.process` passes this unverified `shop` value straight to the app's handler as the tenant identifier [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop_verified_by_hmac == shop_used_for_tenant_attribution`. In practice, the HMAC only binds the raw body bytes to the app's shared `client_secret`; the `shop-domain` header used to attribute the webhook to a specific merchant is parsed but never verified [4](#0-3) .

`HmacValidator.validate` calls `validate_signature`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [5](#0-4) . Because `Webhooks::Request#to_signable_string` returns only `@raw_body`, an attacker who has obtained one genuinely-signed webhook payload for shop A (which is trivial to do — e.g. as the merchant of their own store that has installed the app, since the app's `client_secret` is shared across every shop that installs it) can replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint, while substituting `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) with arbitrary values, e.g. a victim shop B's domain. The signature check still passes because it never inspected those headers, yet `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the attacker-controlled headers and hands it to the app's registered handler [6](#0-5) .

The docs explicitly instruct app developers to trust this flow for authenticity: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook" [7](#0-6) , and describe `data.shop` as "The shop domain of the webhook" without qualification [8](#0-7) . Any host application that keys its per-tenant logic (session/access-token lookup, data writes, job dispatch) off `data.shop`, as the gem's own documented example does (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [9](#0-8) , will process attacker-supplied body content under a victim's shop identity.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is documented to enforce ("verify the request did indeed come from Shopify"). An attacker who is a legitimate merchant of shop A (unprivileged relative to any other tenant) can cause the app to process a webhook body of their choosing while it is attributed to shop B. Depending on how the host app uses `data.shop` (e.g., looking up shop B's stored access token/session to act on the forged payload, or writing data into shop B's tenant records), this is a cross-tenant data integrity issue with the shop-identity binding fully controlled by the attacker.

### Likelihood Explanation
Moderate-to-high. It requires the attacker to possess at least one genuinely HMAC-signed webhook body (trivially available to anyone who installs the app on their own store) and the ability to POST to the app's public webhook endpoint with custom headers — no special privileges, tokens, or the app's `client_secret` are needed.

### Recommendation
Include the `shop-domain` header (and ideally `topic`/`webhook_id`) in the signed/verified bytes, or independently verify the `shop` value against a known-good registration before trusting it for tenant attribution, e.g., extend `VerifiableQuery`/`to_signable_string` for `Webhooks::Request` to incorporate these header values into the HMAC input, or require the host app to re-validate `shop` against its own webhook subscription state before acting on `WebhookMetadata#shop`.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app and receives a legitimate webhook, e.g. `orders/create`, with body `{"id":1}` and header `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Attacker replays an HTTP POST to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: orders/create`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged [10](#0-9) ; `HmacValidator.validate` recomputes the signature over `raw_body` only and it matches [11](#0-10) .
4. `Registry.process` calls the registered handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)` [12](#0-11) , so the app processes attacker-chosen body content as if it originated from `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
