Based on the FeeVault code, I found a valid structural analog to the Sherlock M-4 finding.

### Title
Blacklisted creator can never claim accrued fees — `FeeVault.claim()` has no escrow fallback - (File: `packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault.claim()` pays a creator's entire pooled USDC fee balance via a single direct `safeTransfer(msg.sender, amount)` with no try/catch or escrow fallback. If the creator's address is later added to USDC's blacklist (e.g. by Circle for sanctions/compliance reasons), every future call to `claim()` reverts unconditionally, permanently trapping all currently-accrued and all future-accrued creator fees in the vault with no recovery path.

### Finding Description
`FeeVault.accrue()` credits `creatorBalance[creator] += creatorAmount` on every buy/sell that Zap forwards [1](#0-0) . The only way to realize that balance is `claim()`:

```
function claim() external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(msg.sender, amount);
    emit CreatorFeesClaimed(msg.sender, amount);
}
``` [2](#0-1) 

This is exactly the pattern in the Sherlock M-4 report: fees are pushed directly to a single hardcoded recipient (`msg.sender`) via a plain `safeTransfer`, with no try/catch and no escrow-and-claim-later fallback. USDC (the fee asset here, per `docs/contracts-scope.md`'s Fees & FeeVault section) implements an `isBlacklisted` check that makes `transfer`/`transferFrom` revert for blacklisted addresses. If a token creator's wallet is ever blacklisted by the USDC issuer, `usdc.safeTransfer(msg.sender, amount)` reverts every single time `claim()` is called from that address, so the function can never succeed for that creator again.

Crucially, `Bonding.transferCreator(tokenAddress, newCreator)` does not help: it only changes `TokenInfo.creator`, which affects the recipient of *future* `accrue()` calls [3](#0-2) . It does not move the *already-accrued* balance sitting in `FeeVaultStorage.creatorBalance[oldCreator]` — that mapping entry is permanently keyed to the blacklisted address, and `FeeVault` exposes no admin/owner function to reassign or rescue an individual creator's balance (only `setFeeTo`, `addDepositor`/`removeDepositor`, and `sweepDonations`, none of which touch `creatorBalance`).

### Impact Explanation
Any USDC accrued to a creator address before or after that address becomes blacklisted is permanently frozen in `FeeVault` with no recovery mechanism — matching the "permanent freezing of ... creator ... funds" impact class. Since `Zap.createToken` lets any address become a token creator (an unprivileged, permissionless action), and creator fee accrual is automatic on every buy/sell of that creator's launched token, this is fully reachable without any privileged action.

### Likelihood Explanation
Triggering this requires only that the creator's own wallet address end up on USDC's blacklist at some point after launching a token and accruing fees — a real-world event for exchange-linked or sanctioned addresses. No attacker action against the protocol is needed; the freezing is inherent to the direct-transfer-with-no-escrow design of `claim()`. Given the number of arbitrary creators the permissionless `Zap.createToken` flow can onboard over time, the likelihood is non-trivial over the protocol's lifetime.

### Recommendation
Mirror the audited fix pattern: wrap the outbound transfer in `claim()` (and, for symmetry, `claimProtocol()`) in a `try/catch`. On failure, route the funds to a per-creator escrow balance (or leave `creatorBalance[msg.sender]` unzeroed / redirect to a rescue address) so the creator (or an admin on their behalf) can later claim to an alternate, non-blacklisted address, instead of permanently bricking `claim()` for that creator.

### Proof of Concept
1. Creator `C` calls `Zap.createToken(...)` and launches a token; users buy/sell it, and `Zap._accrueFee` repeatedly calls `feeVault.accrue(token, C, creatorShare, protocolShare, isBuy)`, growing `creatorBalance[C]` [4](#0-3) .
2. `C`'s address is later added to the real USDC contract's blacklist (external to the protocol).
3. `C` calls `FeeVault.claim()`. `amount = creatorBalance[C]` is read, `creatorBalance[C]` and `totalAccruedCreator` are zeroed in memory-storage terms, then `$.usdc.safeTransfer(msg.sender, amount)` reverts because USDC's `transfer` checks `!isBlacklisted(msg.sender)` and fails — the whole transaction (including the storage writes) reverts.
4. Every subsequent call to `claim()` from `C` reverts identically. `C` has no way to designate a different receiving address for the already-accrued balance, and `Bonding.transferCreator` only changes future attribution, not the frozen `creatorBalance[C]` entry in `FeeVault`. The USDC is permanently stuck in `FeeVault`.

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
