### Title
Missing ERC20 return-value validation in `IntentGatewayV2.withdraw()` / `SweepDust` handler causes silent escrow-release failures and permanently locked user funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed ERC20 tokens using a raw low-level `.call()` to `IERC20.transfer`, checking only that the call itself did not revert (`success`), but never decoding/validating the ABI-encoded `bool` return value the ERC20 standard requires. Non-reverting-but-failing tokens (return `false` instead of reverting) will cause the contract to believe a transfer succeeded, decrement/zero-out escrow accounting and mark the order as filled/refunded, while the beneficiary never actually receives the tokens — permanently losing the escrowed funds.

### Finding Description
`withdraw()` is the internal function invoked from `onAccept` when Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` request (the normal path by which a filled/cancelled cross-chain intent settles escrowed tokens to a beneficiary): [1](#0-0) 

Inside `withdraw()`, tokens are paid out with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

and the same unchecked-return pattern is used for the accumulated transaction fee payout: [3](#0-2) 

and again in the `SweepDust` handler that pays out accumulated dust to a beneficiary chosen by governance/Hyperbridge: [4](#0-3) 

`success` from a low-level `.call()` only reflects whether the *call itself* reverted — it says nothing about the decoded boolean payload that ERC-20's `transfer`/`transferFrom` are supposed to return. Tokens that are non-standard-compliant (return `false` on failure instead of reverting) will make this `.call()` return `success == true` even though no tokens moved. Immediately after, `_orders[body.commitment][token] -= amount;` unconditionally decrements the escrow bookkeeping and the function marks the order `EscrowReleased`/`EscrowRefunded` — permanently destroying the accounting record of the escrowed balance while the actual tokens remain stuck in the contract, unreachable by the intended beneficiary.

This is the exact bug class from the reference report (unchecked ERC20 `transfer` return value), reachable here through the core Hyperbridge intents-settlement path: any relayed `RedeemEscrow`/`RefundEscrow` message for an order whose input/fee token is non-standard-compliant.

Note that the non-Tron counterpart (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) already correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which reverts on `false` returns: [5](#0-4) 

The Tron variant, despite importing `SafeERC20` and using it in `placeOrder`'s `safeTransferFrom` calls, reverts to raw `.call()` + `success`-only checks specifically in the payout paths (`withdraw`, fee payout, `SweepDust`), reintroducing the vulnerability that `SafeERC20` was meant to eliminate.

### Impact Explanation
If any token integrated into the Tron `IntentGatewayV2` is non-standard-compliant (returns `false` on failed transfer rather than reverting — a documented, non-exotic ERC20 pattern), a solver's or user's escrowed balance can be zeroed out on-chain (`_orders[...] -= amount`) and the order finalized as filled/refunded, while the tokens themselves never leave the contract and are never delivered to the beneficiary. This is a permanent freezing/loss of user/solver funds with no recovery path, since the escrow accounting that tracked the entitlement has already been deleted. This qualifies as Medium/High severity permanent fund loss under the escrow/intents settlement flow.

### Likelihood Explanation
Likelihood depends on at least one integrated ERC20 exhibiting non-reverting failure semantics (e.g., paused/blacklist-style tokens that return `false`, or tokens with quirky failure modes). Given `IntentGatewayV2` is designed to be generically permissionless for arbitrary ERC20 input/output tokens (per `TokenInfo.token` being an arbitrary address), and Tron's own popular token ecosystem includes several non-standard-compliant tokens, this is a realistic and directly reachable condition triggered simply by normal message delivery (`RedeemEscrow`/`RefundEscrow`) for an order using such a token — no privileged action required.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()`, the fee payout, and the `SweepDust` handler) with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol`, `HyperFungibleToken.sol`, etc.), so that non-compliant tokens' `false` returns properly revert the transaction instead of silently corrupting escrow accounting.

### Proof of Concept
1. Deploy a non-standard ERC20 on Tron whose `transfer()` returns `false` on failure instead of reverting (e.g., insufficient balance triggered by an edge condition, or a deliberately "buggy"/malicious token registered as an input token for an order — nothing prevents an arbitrary token address being used as `order.inputs[i].token`).
2. Place a cross-chain order using this token as an input asset via `placeOrder` (escrowed via `safeTransferFrom`, which succeeds).
3. Cause conditions where the contract's outgoing `transfer` in `withdraw()` would fail post-escrow (e.g., token blacklists the gateway contract or the beneficiary, or supply constraints trigger `false` return rather than revert).
4. Hyperbridge relays the `RedeemEscrow`/`RefundEscrow` request; `withdraw()` executes `token.call(...)`, receives `success == true` (call didn't revert) despite the decoded `bool` payload being `false`; escrow is decremented and `EscrowReleased`/`EscrowRefunded` is emitted, even though the beneficiary received nothing.
5. The escrowed tokens remain stuck in the `IntentGatewayV2` contract with no on-chain record (`_orders[commitment][token]` now zero) to reclaim them.
