### Title
Unchecked RAY-value growth permanently freezes an overlarge borrowed market - ([File: common/src/rates/scaling.rs](common/src/rates/scaling.rs))

### Summary

The protocol bounds the borrow index at `MAX_BORROW_INDEX_RAY`, but it does not independently bound the product `borrowed_shares * borrow_index` to the `i128` RAY-value domain. During accrual, `calculate_supplier_rewards` converts scaled debt back to a RAY-denominated balance through `scaled_to_original`; once that product exceeds `i128::MAX`, the multiplication raises `MathOverflow`. Because every market mutation syncs interest before applying the operation, the market subsequently cannot repay, withdraw, liquidate, or otherwise mutate state.

### Finding Description

`scaled_to_original` computes `scaled.mul(env, index)`, which panics when the half-up multiplication does not fit in `i128`. [1](#0-0)  Interest accrual invokes that conversion for total borrowed shares at the beginning of each step and again when calculating supplier rewards. [2](#0-1)  `update_borrow_index` only caps the index itself; it does not bound the resulting total debt value. [3](#0-2)  The subsequent reward calculation multiplies the unchanged scaled debt by the new index and subtracts the old total debt, so overflow occurs before the index cap can make the operation harmless. [4](#0-3) 

All pool legs load an interest-synced cache through `synced_market`, and `load_leg` invokes it before withdrawal or repayment accounting. [5](#0-4)  Consequently, a single failing accrual blocks both exits and risk-reducing repayments rather than merely blocking new borrows. [6](#0-5) [7](#0-6) 

Cap validation limits only the token-to-RAY input domain: `max_cap_for_decimals` allows approximately 170 billion whole tokens, while valid cap configuration rejects only values above that input-domain ceiling. [8](#0-7)  That bound does not ensure that a large scaled debt remains representable after index growth. The integrated harness demonstrates the reachable boundary: a near-fully-utilized market using 18 decimals eventually reaches `MATH_OVERFLOW`, and subsequent `withdraw` and `repay` attempts fail with the same error before the index reaches `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

### Impact Explanation

This permanently freezes all funds in the affected hub market. Suppliers cannot withdraw because withdrawal first accrues, borrowers or third parties cannot repay because repayment first accrues, and liquidators cannot retire the debt because the liquidation repayment leg encounters the same accrual failure. The pool therefore retains neither a repayment path nor an exit path once the total-debt RAY product crosses the `i128` boundary.

### Likelihood Explanation

Medium likelihood: exploitation requires no privileged role, leaked key, upgrade, oracle manipulation, or malformed transaction. An attacker needs an existing market whose caps and utilization policy permit a debt position near the protocol’s large numeric domain, sufficient collateral to borrow near the market ceiling, and sustained conditions that grow the borrow index enough to make `borrowed * borrow_index` overflow. Those requirements are economically demanding and configuration-dependent, but the code and harness show they are not prevented by the index cap or by cap validation. Once crossed, the failure is deterministic and does not depend on continued attacker action.

### Recommendation

Enforce a second, explicit bound on the value-domain product, not just token amounts and indexes. Before admitting debt or supply, calculate the worst resulting `scaled_shares * index / RAY` under a checked operation and reject any state that cannot remain representable through the configured index ceiling. Accrual should also treat the total-debt RAY value as a protocol invariant and fail entry before the market reaches the boundary, rather than failing every later exit path. Cap checks should use checked scaled-cap conversion; a saturated cap should reject entry rather than silently become effectively unlimited.

### Proof of Concept

1. In a deployed spoke containing a high-decimal borrowed market `D` and a separate collateral market `C`, the attacker calls `supply(caller = attacker, account_id = 0, spoke_id = S, assets = [(C, collateral_amount)])` and receives an owned account id. `supply` is publicly callable when unpaused and creates the account. [10](#0-9) 
2. The attacker calls `borrow(caller = attacker, account_id = id, borrows = [(D, borrow_amount)], to = Some(attacker))` with `borrow_amount` selected so that `D` is near its allowed utilization and near the RAY-value domain boundary after subsequent index growth. [11](#0-10) 
3. Time passes while utilization remains high. Any subsequent operation on `D` invokes `load_leg`, which calls `synced_market` and `interest::global_sync` before the operation-specific logic. [5](#0-4) 
4. During `accrue_step`, `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)`. Once that product exceeds `i128::MAX`, `scaled_to_original` raises `MathOverflow`. [12](#0-11) [1](#0-0) 
5. A third-party rescue call such as `repay(caller = rescuer, account_id = id, payments = [(D, 1)])` reverts during accrual before any debt share can be burned. [6](#0-5) 
6. The repository’s integrated test reproduces this exact boundary and confirms that after the overflow, both raw withdrawal and repayment attempts fail with `MATH_OVERFLOW` while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [9](#0-8)

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)
```

```rust
pub(crate) fn synced_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {

/// Validates `action.amount ≥ 0`, syncs the market, and returns (cache, scaled position).
pub(crate) fn load_leg(env: &Env, action: &PoolAction) -> (Cache, Ray) {
    require_nonneg_amount(env, action.amount);
    let cache = synced_market(env, &action.hub_asset);
    (cache, Ray::from(action.position.scaled_amount))
```

```rust
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
```

```rust
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {

        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);

        "the index cap did not engage before the value overflow"
```
