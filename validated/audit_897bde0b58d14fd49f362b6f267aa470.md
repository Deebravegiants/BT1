### Title
Permissionless `CallDispatcher.dispatch()` lets anyone drain residual native ETH held by the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` has no access control whatsoever — any address can invoke it directly with an arbitrary `Call[]` array. The contract also accepts native ETH unconditionally via `receive()`. Since `CallDispatcher` is the shared, standalone contract that `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` route escrowed native ETH through during predispatch/postdispatch calldata execution, any residual native balance it holds at any point is a public bounty that an unprivileged actor can sweep with a single unsigned transaction — structurally the same "arbitrary call, any value, to anyone" primitive as the `VoterProxy.execute` finding, except here it is *fully permissionless* rather than gated behind a compromised operator.

### Finding Description
`CallDispatcher.dispatch` is defined as: [1](#0-0) 

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
```

There is no `msg.sender` check, no ownership/role gate, and no restriction on `to`/`value`/`data` beyond `to` needing to be a contract. Combined with the unconditional `receive() external payable {}`, any native ETH balance sitting in the deployed `CallDispatcher` instance at any block can be forwarded, in full, to an attacker-chosen address by simply calling `dispatch()` with `Call({to: attacker, value: address(this).balance, data: ""})`.

The contract is explicitly designed to *temporarily hold* funds mid-transaction for `IntentGatewayV2` predispatch/postdispatch flows and `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution: [2](#0-1) [3](#0-2) 

The project's own docs acknowledge the risk pattern of residual balances but the mitigation stops at "use exact approvals," not at gating the dispatch entry point itself: [4](#0-3) 

### Impact Explanation
Any native ETH that ends up in `CallDispatcher` outside the atomic transfer→dispatch→sweep window — e.g. dust from a `Call.value` that undershoots the deposited amount, ETH sent directly to the contract's `receive()` (accidental transfers, since the address is public and reused across `IntentGatewayV2`/HFT/WHFT deployments per the deploy scripts), or funds left over from a reverted downstream integration that nonetheless completed the deposit leg — is permanently and trivially stealable by any address. This is a direct loss-of-funds vector reachable from a single unsigned transaction with no special privileges, matching the "concrete theft of funds" bar.

### Likelihood Explanation
`CallDispatcher` is a small, address-public utility contract deployed once per app/chain (see `evm/script/DeployHFT.s.sol`, `DeployWrappedHFT.s.sol`, `DeployIntentGateway.s.sol`, and the TRON migration) and referenced persistently via `_params.dispatcher`. Its address is discoverable on-chain, and `dispatch()` costs nothing to call and requires no setup — any bot watching the dispatcher's balance can react within the same block a stray transfer lands. Likelihood is high whenever any non-atomic residual balance occurs (rounding, direct transfers, or third-party mistakes), even though the "happy path" flows are atomic per-transaction.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the authorized app contract(s) that deployed/configured it (e.g., an immutable `owner`/`caller` set in the constructor, checked via `require(msg.sender == authorizedCaller)`), or make each `CallDispatcher` instance single-tenant and non-reentrant with a strict "no balance may persist across transactions" invariant enforced by having callers verify pre/post balances are zero. At minimum, remove the unconditional `receive()` or sweep any balance back to a trusted address inside the same `dispatch()` call rather than relying on callers to compute exact sweep amounts externally.

### Proof of Concept
1. Observe (via a public block explorer or event `DustCollected`) that the deployed `CallDispatcher` used by `IntentGatewayV2`/`HyperFungibleToken` momentarily/persistently holds a native ETH balance greater than zero (e.g., from a stray direct transfer, or dust left after a predispatch/postdispatch call whose `Call.value` didn't consume the full deposited amount).
2. From any EOA, call:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({to: attacker, value: address(callDispatcher).balance, data: ""});
ICallDispatcher(callDispatcher).dispatch(abi.encode(calls));
```
3. The call succeeds unconditionally — `dispatch()` performs no sender check — and the entire native balance of the shared `CallDispatcher` is forwarded to `attacker`, with no way for the legitimate app or its users to recover it.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
