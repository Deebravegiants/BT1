### Title
Stale stored owner retains spending authority after position NFT transfer — withdrawn/borrowed funds go to the seller, not the NFT buyer - ([File: contracts/controller/src/account.rs])

### Summary
The controller binds spending authority to `account.owner`, a field written once at account creation, while ownership is actually transferable via the position NFT (`transfer`/`approve` on the OZ enumerable NFT). `require_owner_or_delegate` compares the caller against the stale stored `owner`, not the live NFT `owner_of`. An account owner who transfers the NFT retains full withdraw/borrow authority over the position — an authorization bypass reachable by any unprivileged address.

### Finding Description
`create_account` stores `owner` in the `Account` struct at mint time ( [1](#0-0) ). `is_owner_or_delegate` authorizes `caller` whenever `caller == owner`, where `owner` is that stored field ( [2](#0-1) ). All spending verbs — `borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend` — gate on `require_owner_or_delegate` against this stored owner, per the documented auth model ( [3](#0-2) ).

Meanwhile the position NFT is a stock OZ enumerable NFT whose `transfer`/`approve`/`transfer_from` mutate `owner_of` freely ( [4](#0-3) ). Nothing in the controller updates `account.owner` or clears `Delegates` on NFT transfer. Inconsistently, `require_account_owner` (used by `renew_account`, `add_delegate`, `remove_delegate`) checks the live NFT owner via `storage::account_owner` ( [5](#0-4) ) — so delegate management follows the NFT, but fund movement follows the stale record. The previous owner therefore keeps authority they demonstrably sold, and can drain collateral or open debt after the NFT changes hands. The new owner cannot revoke it either: `remove_delegate` requires the NFT owner, but the seller's own authority is `caller == account.owner`, not a delegate entry.

### Impact Explanation
Theft of user funds. The seller of a position NFT (or anyone who tricked the owner into an `approve` + `transfer_from`) can call `withdraw` and `borrow` on the sold account, extracting all collateral and maxing out borrows, leaving the buyer a hollow or liquidatable position. The receive address for `withdraw`/`borrow` legs is the caller-controlled path, so proceeds go to the ex-owner directly.

### Likelihood Explanation
Trivially reachable by any unprivileged address: open a position (`supply` with `account_id = 0`), transfer the NFT to a buyer contract or accomplice for a price, then call `controller::withdraw(account_id, ...)` — `require_owner_or_delegate` passes because `caller == account.owner`. No race or privileged state needed. The only mitigating uncertainty is whether a documented deployment integration wraps the NFT so it is never transferred; nothing in the contract code prevents it, and `transfer`/`approve` are ungated standard entrypoints.

### Recommendation
Authorize account mutation paths against the live NFT owner (`storage::account_owner` / `owner_of`) instead of the stored `account.owner`, or remove the redundant `owner` field and derive ownership from the NFT everywhere. Alternatively hook NFT `transfer` to resync `account.owner` and clear the delegate map — a single canonical ownership source is preferable.

### Proof of Concept
```rust
// Attacker (ALICE) flow, no privileged role:
// 1. ctrl.supply(alice, account_id=0, spoke_id, [USDC, amount])
//    -> creates account, stores owner=ALICE, mints NFT id N to ALICE.
// 2. nft.transfer(alice -> victim_buyer, N)         // OZ transfer, owner_of(N)=buyer
// 3. ctrl.withdraw(alice, N, [USDC, i128::MAX], to=alice)
//    -> require_owner_or_delegate: account.owner == ALICE -> passes.
//    -> buyer's NFT is worthless; collateral sent to ALICE.
// 4. ctrl.borrow(alice, N, [ETH, max]) -> same gate, debt accrues on
//    buyer's account -> buyer gets liquidated.
```
The asymmetry is visible in code: step 3 passes `caller == owner` on the stale field ( [6](#0-5) ), while a buyer attempting `add_delegate` fails `require_account_owner` only in reverse — the owner checks use two different sources of truth ( [5](#0-4) ).

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

#[contractimpl(contracttrait)]
impl NonFungibleToken for PositionNft {
    type ContractType = Enumerable;

    /// `{stored base_uri}{token_id}?isStatic=true&chain=STELLAR`
    ///
    /// Panics with the OZ `NonExistentToken` error for burned or never-minted
    /// ids, matching the stock behavior.
    fn token_uri(e: &Env, token_id: u32) -> String {
        let _owner = Base::owner_of(e, token_id);

        let base = Base::base_uri(e);
        let base_len = base.len() as usize;
        // OZ `set_metadata` caps the base at `MAX_BASE_URI_LEN` (200 bytes):
        // 200 + 10 digits (u32 max) + 28-byte suffix fits in 256.
        let mut buf = [0u8; 256];
        base.copy_into_slice(&mut buf[..base_len]);
        let mut len = base_len;
        // Decimal digits, most significant first. token_id >= 1 always
        // (id 0 is consumed at construction), so no zero special-case.
        let mut digits = [0u8; 10];
        let mut n = token_id;
        let mut count = 0usize;
        while n > 0 {
            digits[count] = b'0' + (n % 10) as u8;
            n /= 10;
            count += 1;
        }
        while count > 0 {
            count -= 1;
            buf[len] = digits[count];
            len += 1;
        }
        for b in TOKEN_URI_SUFFIX.bytes() {
            buf[len] = b;
            len += 1;
        }
        String::from_bytes(e, &buf[..len])
    }
}

#[contractimpl(contracttrait)]
