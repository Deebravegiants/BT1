### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` proves only that the *body bytes* were signed with the app's secret. The `shop` value that is subsequently handed to the app's webhook handler as the authoritative tenant identifier is read straight from the `x-shopify-shop-domain` HTTP header, which is never included in the signed material.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`HmacValidator.validate_signature` computes the expected signature over `verifiable_query.to_signable_string` and compares it with `verifiable_query.hmac`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns only `@raw_body` — it never incorporates `topic`, `shop`, `api_version`, or `webhook_id`: [3](#0-2) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are pulled directly from HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler`

but the actual binding enforced by the code is only:
`raw_body authenticated by HMAC == raw_body parsed`,
with `shop` (and the other headers) trusted independently and unauthenticated. Any party who can produce one validly-signed body/HMAC pair (e.g., by triggering a webhook delivery to their own shop, since Shopify signs with the *app's* shared secret which is identical for every shop installed on that app) can replay that exact `raw_body` + `hmac-sha256` header pair while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will invoke the app's handler believing the payload originated from the spoofed shop.

### Impact Explanation
This breaks the tenant/shop identity boundary the gem is supposed to enforce for webhook delivery: the app's `WebhookHandler` receives a `WebhookMetadata` claiming a `shop` that was never actually verified, enabling cross-tenant data injection/confusion (e.g., a handler that updates or deletes local records keyed by `shop` could be made to act on a victim shop's data using an attacker-controlled payload). This matches the "cross-tenant access" class of impact called out as Critical.

### Likelihood Explanation
Exploitation requires the attacker to have received (or captured) one genuine `raw_body`/`hmac-sha256` pair for the given app — trivially available to any merchant who installs the app on their own store and inspects webhook deliveries, or to anyone who can observe a single webhook POST (e.g., via logs, a proxy, or their own shop's webhook endpoint). No possession of `api_secret_key` or an access token is needed; only the ability to send an HTTP POST to the app's webhook endpoint with attacker-chosen headers and the captured body/HMAC. This is a low-effort, no-credential attack once a single legitimate delivery has been observed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified material instead of trusting the header independently. Concretely:
- Include the `x-shopify-shop-domain` value in `to_signable_string` where feasible, or
- Cross-check `request.shop` against a shop known to be associated with the specific webhook subscription/session before invoking the handler, and reject mismatches, or
- At minimum, document loudly that `request.shop` is unauthenticated and must be independently verified by the host app against its own tenant registry before use — but the safer fix is enforcing the binding inside `ShopifyAPI::Webhooks::Registry.process` itself so all consumers of this gem get the protection by default.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker-shop.myshopify.com`) and triggers any registered webhook topic, capturing the raw POST body `B` and the resulting `x-shopify-hmac-sha256` header `H` (both are valid, since Shopify signs with the app's single shared secret for every store).
2. Attacker crafts a new HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged or of interest
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and matches `H`, returning `true`.
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)`, even though the payload and topic actually originated from the attacker's own shop, not the victim's.
