Audit Report

## Title
Unauthenticated nil-pointer panic in `GatewayHandler.handlePublicKeyGet` due to missing `req.Params` nil check - (File: core/capabilities/vault/gw_handler.go)

## Summary
`GatewayHandler.HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` without routing it through the shared `GatewayVaultRequestProcessor` validation pipeline used by every other vault method. `handlePublicKeyGet` then unconditionally dereferences `*req.Params` in `json.Unmarshal(*req.Params, r)`, causing a nil-pointer panic if `Params` is nil/omitted, which is a protocol-legal JSON-RPC request shape.

## Finding Description
In `HandleGatewayMessage`, `MethodSecretsCreate`/`Update`/`Delete`/`List` all pass through `h.requestProcessor.ProcessRequest`, whose per-method handlers (e.g. `processDeleteSecretsRequest`) explicitly check `req.Params == nil` before unmarshaling. `MethodPublicKeyGet` instead calls `h.handlePublicKeyGet` directly, and that function dereferences `*req.Params` with no preceding nil check. On the gateway side, `handler.HandleJSONRPCUserMessage` also special-cases `MethodPublicKeyGet` to skip `requestProcessor.ProcessRequest` and, on cache miss, forwards the caller's raw request (including a possibly-nil `Params`) unmodified to nodes via `fanOutToVaultNodes`/`SendToNode`. No component in this specific code path enforces that `Params` is non-nil for `MethodPublicKeyGet`, unlike all sibling vault methods.

## Impact Explanation
This is a denial-of-service issue: an unauthenticated request through the gateway with `method: "vault_publicKeyGet"` and no/null `params` reaches the node's `handlePublicKeyGet` and panics, since `MethodPublicKeyGet` intentionally requires no authorization (it just returns a DON-wide public key). Depending on whether the panic is recovered elsewhere in the connector/goroutine stack, this could crash request handling for that gateway connection or the node process. This maps to a CWE-476/DoS class impact — no fund movement, key disclosure, or auth bypass, consistent with a moderate severity finding.

## Likelihood Explanation
High: the request is trivially constructible by any unprivileged actor able to reach the gateway's JSON-RPC vault endpoint, requires no credential, session, or role, and the exact "nil Params" shape is already exercised as a valid input in the codebase's own test (`TestVaultHandler_PublicKeyGet`, `Params: nil`). The only remaining unconfirmed detail is whether an outer gateway HTTP/JSON-RPC codec layer performs a blanket "params must be present" validation before reaching the vault handler — this could not be verified from the indexed files, but no such check exists within the vault-specific code paths examined.

## Recommendation
Add an explicit `req.Params == nil` guard at the top of `GatewayHandler.handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go`, returning a structured `UserMessageParseError`/`InvalidVaultParamsError` response instead of panicking, mirroring the guards already present in `processDeleteSecretsRequest`/`processListSecretIdentifiersRequest`. Consider routing `MethodPublicKeyGet` through the shared `requestProcessor` pipeline (with a no-auth-required flag) for consistency, and apply the same fix to the gateway-side `handler.HandleJSONRPCUserMessage`/`handlePublicKeyGet` path in `core/services/gateway/handlers/vault/handler.go` if it also forwards unchecked `Params`.

## Proof of Concept
1. Send a JSON-RPC request to the gateway's vault endpoint: `{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}` (no `params` field, so it decodes to `Params: nil`).
2. On a cache miss, the gateway's `handler.HandleJSONRPCUserMessage` forwards this request unchanged to DON nodes via `fanOutToVaultNodes`/`SendToNode` (`core/services/gateway/handlers/vault/handler.go:404-419, 692-708, 736-752`).
3. The node's `GatewayHandler.HandleGatewayMessage` dispatches it straight to `handlePublicKeyGet` (`core/capabilities/vault/gw_handler.go:207-208`), which executes `json.Unmarshal(*req.Params, r)` (`core/capabilities/vault/gw_handler.go:364-368`), panicking on the nil dereference.
4. A Go unit test constructing a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and calling `GatewayHandler.handlePublicKeyGet` directly reproduces the panic.

func (h *handler) handlePublicKeyGet(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
	if cachedPublicKey != nil {
		l.Debugw("returning cached public key response")
		return h.sendSuccessResponse(ctx, l, ar, &jsonrpc.Response[json.RawMessage]{
			Version: jsonrpc.JsonRpcVersion,
			ID:      ar.req.ID,
			Method:  ar.req.Method,
			Result:  (*json.RawMessage)(&publicKeyResponseBytes),
		})
	}

	l.Debugw("cache stale: forwarding request to nodes", "now", h.clock.Now())
	return h.fanOutToVaultNodes(ctx, l, ar)
}

func (h *handler) fanOutToVaultNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var nodeErrors []error
	for _, node := range h.donConfig.Members {
		err := h.don.SendToNode(ctx, node.Address, &ar.req)
		if err != nil {
			nodeErrors = append(nodeErrors, err)
			l.Errorw("error sending request to node", "node", node.Address, "error", err)
		}
	}

	if len(nodeErrors) == len(h.donConfig.Members) && len(nodeErrors) > 0 {
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes"), nil))
	}

	l.Debugw("successfully forwarded request to Vault nodes")
	return nil
}
