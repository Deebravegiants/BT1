## Finding

### Title
Webhook `shop` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `HmacValidator` never authenticates the `shop`, `topic`, `api-version`, or `webhook-id` headers. `Registry.process` uses the *unverified* `request.shop` and `request.topic` to route the payload to a handler and to identify which tenant the data belongs to, while only the body bytes are checked against the signature.

### Finding Description
The gem's HMAC check is implemented as: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

Only `@raw_body` is signed. The `shop`, `topic`, `webhook-id`, and `api-version` fields come from HTTP headers that are **not part of the signable string**: [2](#0-1) 

Yet `Registry.process` trusts these unverified header fields to select the handler and to hand the tenant identity (`shop`) to application logic: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

This breaks the identity binding: **`hmac-verified bytes == @raw_body` but `shop used by handler == request.shop header (unauthenticated)`**. The equality that should hold — "the shop the HMAC authenticates equals the shop the handler acts on" — does not hold, because the HMAC authenticates only the body, not the header claiming which shop it came from.

Because `api_secret_key` is a single app-wide secret shared across **every merchant/tenant** that installs the app (this is not a per-shop secret), any tenant that legitimately receives webhooks for their own shop possesses a valid `(raw_body, hmac)` pair signed with the very same secret used for all other tenants. A malicious tenant can:
1. Capture a legitimate webhook delivery to their own shop (raw body + `x-shopify-hmac-sha256` value) — this passes `HmacValidator.validate` because the secret is app-wide, not shop-specific.
2. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (only the body is checked), and `Registry.process` calls the handler with `shop: <victim-shop>` and the attacker's body content.

If the host application's webhook handler (following the documented `WebhookMetadata#shop` field) uses this value to select which tenant's database row to update, this allows a low-privilege tenant to inject or corrupt another tenant's data — a cross-tenant access violation.

### Impact Explanation
This satisfies the "Critical – cross-tenant access" bar: a merchant/tenant with no special privileges beyond having installed the app can forge webhook deliveries attributed to a different shop, because the shop identity is never bound to the HMAC that the gem verifies.

### Likelihood Explanation
Likelihood is contingent on the host application trusting `WebhookMetadata#shop` (the documented field) to select the tenant record, which is the expected/documented usage pattern for this field. The attacker only needs to be an app-installing merchant (unprivileged relative to other tenants) and to be able to send HTTP requests to the app's public webhook endpoint — no access token, secret, or the target victim's credentials are required.

### Recommendation
Include the `shop`, `topic`, and other trust-sensitive headers in the HMAC-signable representation (or otherwise cryptographically bind them to the payload), or require the caller to independently verify that `request.shop` matches an already-established/expected shop before trusting it, rather than relying solely on body-only HMAC verification while trusting header-derived shop/topic values.

### Proof of Concept
1. Attacker installs the target app for `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header value (both signed with the app's single, shared `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with the identical `raw_body` and `hmac` header, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <same or different registered topic>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `Digest.hexencode(...)` against `request.to_signable_string` (i.e., `@raw_body`) — validation succeeds.
4. The handler executes with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, as shown in `lib/shopify_api/webhooks/registry.rb:190-199`.
