## Title
CORS wildcard-origin allowlist bypass via missing domain-boundary check - (File: `core/services/gateway/network/httpserver.go`)

### Summary
The gateway's HTTP server implements a CORS origin allowlist that supports wildcard subdomain entries (e.g. `https://*.ethereum.org`). The matching logic strips the `*.` prefix and then checks whether the request's `Origin` host **ends with** the remaining string using `strings.HasSuffix`, without verifying that a domain-separator (`.`) precedes the matched suffix. This is the same root-cause bug class as CVE-2016-8746 (Apache Ranger): a policy/allowlist matcher that "incorrectly matches paths/strings in certain conditions" because it performs a raw substring/suffix comparison instead of a boundary-aware comparison.

### Finding Description
In `isAllowedOrigin`, for each configured allowed origin, the code does: [1](#0-0) 

```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```

If the operator configures `CORSAllowedOrigins: ["https://*.ethereum.org"]`, `allowedHost` becomes `"ethereum.org"`. `strings.HasSuffix(originHost, "ethereum.org")` is then true not only for legitimate subdomains like `remix.ethereum.org`, but also for any domain that merely *ends with the same characters*, such as `evilethereum.org` or `notethereum.org` — domains an attacker fully controls and can register, with no dot separator required before the matched suffix. This exactly mirrors the Ranger flaw: a "no wildcard, but recursive/boundary-unaware" comparison that treats a superstring as being within an intended scope.

This function is invoked on every request to the internet-facing gateway HTTP endpoint: [2](#0-1) 

```go
func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}
```

An unprivileged, unauthenticated remote actor who simply registers a domain sharing the suffix of an allowlisted wildcard entry (e.g. registering `evilethereum.org` to spoof an allowlist entry for `*.ethereum.org`) can have the gateway reflect `Access-Control-Allow-Origin: <attacker origin>`, defeating the intent of the `CORSAllowedOrigins` allowlist.

The existing test suite exercises only the "no-dot" negative case for a *different* TLD (`https://ethereum.remix.org` vs `*.ethereum.org`), and does not cover the suffix-substring case (e.g. `evilethereum.org`), so this gap is not caught: [3](#0-2) 

### Impact Explanation
CORS controls which cross-origin web pages may have their `fetch`/`XHR` requests responses read by browser JavaScript. Bypassing the wildcard-origin boundary check lets an attacker who controls a suffix-colliding domain (which they can freely register, e.g. `evilethereum.org` when `*.ethereum.org` is allowlisted) get the gateway to treat their page as trusted. This allows unauthorized cross-origin reading of gateway responses from a victim's browser session, i.e. request impersonation / cross-user response confusion at the gateway boundary — the class of impact the validation rules call out as acceptable (allowlist bypass, cross-user response confusion) for an unprivileged client-side actor.

### Likelihood Explanation
Exploitability only requires: (1) the operator configuring a wildcard entry in `CORSAllowedOrigins` (a documented, supported feature per `core/scripts/gateway/sample_config.toml`), and (2) the attacker registering/controlling a domain that shares the suffix without a preceding dot. Domain registration is trivial and fully within an unprivileged external actor's control, requiring no compromise of any Chainlink node or peer.

### Recommendation
Fix `isAllowedOrigin` in `core/services/gateway/network/httpserver.go` to require a boundary check when matching wildcard hosts, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // keep leading "."
    if originHost == suffix[1:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
i.e. compare against `.ethereum.org` (with the leading dot) rather than `ethereum.org`, so `evilethereum.org` no longer matches while `remix.ethereum.org` still does.

### Proof of Concept
1. Configure the gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. From an unprivileged network client, send a request to the gateway endpoint with header `Origin: https://evilethereum.org`.
3. Observe the server responds with `Access-Control-Allow-Origin: https://evilethereum.org`, even though `evilethereum.org` is not a subdomain of `ethereum.org` and was never intended to be trusted — reproducing the same `strings.HasSuffix`/`isAllowedOrigin` logic at [1](#0-0) .
