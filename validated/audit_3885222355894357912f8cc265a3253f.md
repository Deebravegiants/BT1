### Title
Registry.process trusts unauthenticated `shop-domain` header as tenant identity with no shop-to-registration binding check - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`Registry.process` verifies only that the raw request body's HMAC matches (integrity/origin-from-Shopify check), then builds `WebhookMetadata` using `request.shop`, a value taken verbatim from the `X-Shopify-Shop-Domain` header that is **not** included in the HMAC-signed payload. Because `@registry` is keyed only by `topic` (shared handler instance for every merchant), there is no server-side record tying "this topic was registered by shop Y" that `process` could check `request.shop` against, so any validly-HMAC'd webhook body can be replayed with an attacker-chosen shop-domain header.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`shop that produced/authorized this signed webhook body == request.shop passed into WebhookMetadata.shop`

Trace:
- `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Webhooks::Request#shop` reads the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header directly [2](#0-1) .
- `Registry.process` only calls `Utils::HmacValidator.validate(request)` (an integrity check over the signable string, i.e. the raw body) before looking up the handler by `request.topic` and constructing `WebhookMetadata` with `request.shop` taken verbatim [3](#0-2) .
- `Registry.add_registration` stores a single `Registration` per topic in `@registry`, a `Hash[String, Registration]` keyed only by topic — with no per-shop scoping [4](#0-3) , [5](#0-4) .
- `Registry.register(topic:, session:)` associates a `session` (and thus a shop) with a GraphQL call to Shopify to create the webhook subscription, but this association is never persisted into `@registry`/`Registration` for later verification in `process` [6](#0-5) .

Because the shop-domain header is not part of the signed content and no shop-registration mapping exists to cross-check against, an attacker who legitimately installs the app on their own development shop and receives a genuinely-signed webhook (valid body + HMAC for their own shop) can replay that exact body/HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g., a victim merchant's domain). `Utils::HmacValidator.validate` still passes because it only checks body integrity, and `Registry.process` will invoke the single globally-shared handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain, with body content controlled by the attacker's own shop's real webhook payload.

No existing guard closes this gap: HMAC validation only proves "this body was HMAC'd by holder of the api_secret_key" (i.e., genuinely came from Shopify for *some* shop), not "this body is authorized for the shop named in the header." There is no shop-membership or session-binding check anywhere in `Registry.process`.

### Impact Explanation
Any app relying on `WebhookMetadata.shop` to select or scope which merchant's data to update/query (a standard pattern) can be tricked into acting on/for a shop the attacker doesn't control. This is a cross-tenant integrity issue: attacker-controlled webhook payload data (from their own shop) is delivered to the handler tagged as belonging to an arbitrary victim shop-domain, since the same handler instance serves all shops and there's no verification tying shop identity to the specific webhook subscription that was registered. Impact severity aligns with "cross-tenant access via a globally shared handler," reachable per-request and repeatable against any victim shop domain the attacker chooses (domains are often guessable/known, e.g. `victim.myshopify.com`).

### Likelihood Explanation
Preconditions: attacker needs their own developer/test shop that can install the app and register a webhook (freely available to any internet user per the threat model), and the app must consume `WebhookMetadata.shop` for tenant-scoped logic (typical usage). Attacker cost is low: capture one legitimately-signed webhook from their own shop, then POST it to the app's known webhook endpoint URL with a modified shop-domain header — no cryptographic secret is required since the header isn't covered by the HMAC. This is fully repeatable for any topic/handler registered in the shared `@registry`.

### Recommendation
Bind webhook processing to a verified shop. Persist, at `add_registration`/`register` time, the set of shops that legitimately registered a subscription for a topic (or otherwise validate `request.shop` against Shopify's known shop record, e.g. by checking an active `Auth::Session`/offline token exists for that shop before dispatching), and reject/short-circuit in `Registry.process` when `request.shop` cannot be matched to a valid, currently-authorized registration. At minimum, document and enforce that host apps must independently verify `request.shop` is an installed, session-bearing shop before trusting `WebhookMetadata.shop`.

### Proof of Concept
Minitest + WebMock plan (no live shop):
1. Stub `Utils::HmacValidator.validate` to return `true` (simulating a genuinely Shopify-signed body) for a fixed `raw_body`.
2. Call `Registry.add_registration(topic: "orders/create", delivery_method: :http, path: "...", handler: mock_handler)`.
3. Build `Webhooks::Request.new(raw_body: fixed_body, headers: {"x-shopify-topic" => "orders/create", "x-shopify-hmac-sha256" => valid_hmac, "x-shopify-shop-domain" => "attacker-shop.myshopify.com", ...})` and call `Registry.process(request)`; assert `mock_handler` received `WebhookMetadata` with `shop == "attacker-shop.myshopify.com"`.
4. Build a second `Webhooks::Request` with identical `raw_body`/`hmac` but `"x-shopify-shop-domain" => "victim-shop.myshopify.com"`; call `Registry.process(request)` again; assert `mock_handler.handle` is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` — proving the same signed payload is accepted for an arbitrary shop with no shop-membership check.
5. Assert equality-before/after: `request1.shop != request2.shop` while `request1.hmac == request2.hmac` and both pass `HmacValidator.validate`, demonstrating the binding "authorized shop == WebhookMetadata.shop" does not hold.

```ruby
        def add_registration(topic:, delivery_method:, path:, handler: nil, fields: nil, filter: nil,
          metafield_namespaces: nil)
          @registry[topic] = case delivery_method
          when :pub_sub
            Registrations::PubSub.new(topic: topic, path: path, fields: fields,
              metafield_namespaces: metafield_namespaces, filter: filter)
          when :event_bridge
            Registrations::EventBridge.new(topic: topic, path: path, fields: fields,
              metafield_namespaces: metafield_namespaces, filter: filter)
          when :http
            unless handler
              raise Errors::InvalidWebhookRegistrationError, "Cannot create an Http registration without a handler."
            end

            Registrations::Http.new(topic: topic, path: path, handler: handler,
              fields: fields, metafield_namespaces: metafield_namespaces, filter: filter)
          else
            raise Errors::InvalidWebhookRegistrationError,
              "Unsupported delivery method #{delivery_method}. Allowed values: {:http, :pub_sub, :event_bridge}."
          end
        end
```

```ruby
        def register(topic:, session:)
          return mandatory_registration_result(topic) if mandatory_webhook_topic?(topic)

          registration = @registry[topic]

          unless registration
            raise Errors::InvalidWebhookRegistrationError, "Webhook topic #{topic} has not been added to the registry."
          end

          client = Clients::Graphql::Admin.new(session: session)
          register_check_result = webhook_registration_needed?(client, registration)

          registered = true
          register_body = nil

          if register_check_result[:must_register]
            register_body = send_register_request(
              client,
              registration,
              register_check_result[:webhook_id],
            )
            registered = registration_sucessful?(
              register_body,
              registration.mutation_name(register_check_result[:webhook_id]),
            )
          end

          RegisterResult.new(topic: topic, success: registered, body: register_body)
        end
```

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
