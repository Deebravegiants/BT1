Audit Report

## Title
Missing Authentication on LOOP Plugin `/pprof`, `/metrics`, and `/discovery` Endpoints Enables Unauthenticated Denial of Service - (File: core/web/router.go)

## Summary
The `loopRoutes` function in `core/web/router.go` registers `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` on the unauthenticated `api` group, unlike `debugRoutes` and the `/v2/debug/pprof` routes which are gated by `auth.Authenticate`. This is confirmed by both the source code and existing tests in `core/web/loop_registry_test.go`, where `app.NewHTTPClient(nil)` (no credentials) successfully calls these endpoints and receives `200 OK`.

## Finding Description
`NewRouter` mounts `loopRoutes` on the `api` group alongside `debugRoutes`, but only `debugRoutes` wraps its group in `auth.Authenticate(...)`. [1](#0-0) [2](#0-1) 
`loopRoutes` itself applies no auth middleware to its registered handlers. [3](#0-2) 
These handlers proxy directly to internal LOOP plugin processes' pprof/metrics servers, and `pluginPPROFHandler` forwards an attacker-supplied `seconds` parameter to control profiling duration. [4](#0-3) 
This is confirmed to behave as claimed: the existing test suite exercises these endpoints with an unauthenticated `NewHTTPClient(nil)` and asserts `200 OK` responses for `/discovery`, `/plugins/mockLoopImpl/metrics`, and `/metrics`. [5](#0-4) 

## Impact Explanation
The realistic impact is (a) resource exhaustion/denial-of-service against LOOP plugin processes via repeated unauthenticated pprof profiling requests, and (b) low-sensitivity information disclosure of plugin names, hostnames, and Prometheus metrics. Per the project's stated exclusion list, "Impacts that only require DDoS" and "Server-side non-confidential information disclosure, such as IPs, server names, and most stack traces" are explicitly out of scope. Neither the DoS nor the disclosure aspect rises to an in-scope Chainlink impact category (authentication/role bypass enabling fund movement, unauthorized job execution, key/secret exfiltration, gateway impersonation, allowlist bypass, or cross-user response corruption) — no code path here leads to key exfiltration, unauthorized transactions, or job manipulation.

## Likelihood Explanation
While the missing-auth condition is real and trivially reachable by any network-connected unprivileged client, likelihood of a qualifying, in-scope impact is low because the resulting harm is bounded to DoS/DDoS-class disruption and non-confidential metadata disclosure, both categories the program explicitly excludes.

## Recommendation
Wrap `loopRoutes` with the same `auth.Authenticate` middleware used by `debugRoutes`/`v2Routes`'s authenticated group as defense-in-depth, even though the resulting impact class does not meet the bounty's in-scope severity bar.

## Proof of Concept
Not applicable — the underlying code behavior is confirmed real (see `core/web/loop_registry_test.go`), but the resulting impact (DoS and non-confidential info disclosure) does not map to an in-scope impact category per program rules.

func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}
