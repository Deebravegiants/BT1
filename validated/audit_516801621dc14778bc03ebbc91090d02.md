### Title
Phantom-order price oracle can be skewed by a self-delegated solver's transiently inflated token balance, publishing a manipulated exchange rate - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` derives Hyperbridge's published cross-chain exchange rate for a token pair from a **liquidity-weighted median** of solver quotes, where the weight is each solver's *live, on-chain ERC-20/vault balance* of the leg's output token, read via `getBalance` at snapshot time [1](#0-0) . Any address can become a "verified" bidder simply by self-delegating via EIP-7702 to the public `SolverAccount` contract — there is no allowlist or governance approval gate on this step [2](#0-1) [3](#0-2) . Documentation itself states "a solver holding over half the leg's weight sets the published price verbatim" [4](#0-3) .

### Finding Description
The mechanism mirrors Edel Finance's wGOOGLx bug class: an externally-observable, momentarily-inflatable balance is read and trusted as ground truth for a price/valuation used elsewhere in the protocol.

1. Anyone can self-delegate an EOA to the public `SolverAccount` address via a standard EIP-7702 authorization transaction — this is a normal, unprivileged action any wallet can take, as demonstrated by the SDK's own delegation flow [5](#0-4) .
2. Once delegated, that address can submit a `fillOrder` bid to the coprocessor for any live phantom order, signed correctly per `SolverAccount.validateUserOp` [6](#0-5) .
3. The bid's quoted price is weighted purely by `getBalance` — the solver's momentary ERC-20/vault balance of the output token on the destination chain [7](#0-6) . Nothing requires this balance to be "real" committed liquidity or held for any duration — a flash loan, a borrowed/rented balance, or a brief transfer-in immediately before the indexer's read (which happens asynchronously after `PhantomBidWindowExhausted`, at a time and block the attacker does not fully control but can bracket by holding the balance across several blocks) is sufficient.
4. If the attacker's momentary balance exceeds half of the summed weight for that leg, `weightedMedian` returns the attacker's quoted price **verbatim**, without any bound relative to real market rates [8](#0-7) .
5. This manipulated median is persisted as `PhantomOrderPriceSnapshotV2.medianPrice`, renormalized into `LiquidityPool.sellRate`/`buyRate` by `updateLiquidityPools` [9](#0-8) , and is then served as ground truth to downstream consumers of the indexed rate feed via `quoteIntent()` and `queryBuyAndSellRates()` [10](#0-9) [11](#0-10) .

Unlike the Uniswap V4 venue path — which is explicitly protected by a configurable `checkPriceGuard` bounding deviation from a static reference price [12](#0-11)  — the phantom-bid weighted-median path has **no reference-price sanity check at all**. The only defenses present (bid signature verification, delegation check, per-solver dedup, zero-weight drop) all guard *authenticity of the bidder*, not *plausibility of the reported balance or price*, so a legitimately-delegated but capital-thin attacker can still buy a temporary outsized weight.

### Impact Explanation
This is the direct analog of the Edel Finance wGOOGLx incident: a protocol treats an attacker-controllable, transient on-chain value (there: an exchange-rate-bearing wrapped-token balance; here: a raw token balance used as bid weight) as an authoritative price input with no independent bound, allowing the attacker to unilaterally set a published exchange rate far from the real market rate. Consumers building orders from `quoteIntent`/`queryBuyAndSellRates` (SDK users, other integrators reading the indexer's `LiquidityPool.sellRate`/`buyRate`) receive amounts derived from a corrupted rate, and users following documented guidance to use "the returned amounts directly as the order's `inputs` and `output.assets`—no further fee or slippage adjustment is required" [13](#0-12)  can construct intent orders sized against a manipulated rate, creating a mispriced trade that a real filler either declines (denial of accurate service) or, if it blindly trusts the indexed rate for sizing, fills at a loss.

### Likelihood Explanation
Medium likelihood: requires the attacker to (a) self-delegate an EOA (trivial, unprivileged, one transaction), (b) acquire a large momentary balance of the specific output token on the destination chain (achievable via flash loan or short-term capital, especially for lower-liquidity exotic tokens like the ones this pricing pipeline explicitly targets — cNGN, ZARP, etc.), and (c) submit a bid during a live phantom order's bid window. No governance or relayer collusion is needed, and the weighted-median code path is exercised on every `PhantomBidWindowExhausted` event.

### Recommendation
Apply the same defense already used on the venue-pricing path to the phantom-bid weighted-median path: bound `medianPrice` (or the underlying bidder weight-share) against a governance-configured reference rate/`maxDeviationBps`, reject or cap outlier legs where a single bidder's weight exceeds a configurable share of total leg weight, and/or require the weighting balance to be observed as stable across multiple blocks (a TWAB-style check) rather than a single point-in-time read, mirroring `checkPriceGuard`'s protection against "a manipulated, stale, or thin pool."

### Proof of Concept
1. Attacker EOA `A` sends a standard EIP-7702 self-authorization transaction pointing at the deployed `SolverAccount` address on the target destination chain (same mechanism as `DelegationService.setupDelegation`) — no approval needed.
2. During a live `PhantomOrderV2` bid window, `A` acquires (e.g., via flash loan or temporary transfer) a balance of the leg's output token exceeding the combined balance of all other verified bidders.
3. `A` submits a correctly-signed `PackedUserOperation` bid quoting an output amount far above (or below) the true market rate for that pair, per the `SolverAccount.validateUserOp` / `isVerifiedSolverBid` requirements.
4. When `PhantomBidWindowExhausted` fires, `aggregatePhantomBids` weighs `A`'s quote by its (attacker-controlled) balance; since it exceeds 50% of total leg weight, `weightedMedian` returns `A`'s price verbatim as `medianPrice`.
5. The indexer's `updateLiquidityPools` publishes this as the pool's `sellRate`/`buyRate`, which `quoteIntent()`/`queryBuyAndSellRates()` then serve to any consumer as the market rate for that pair, without any external sanity check.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price

async function isDelegatedToSolverAccount(
	evmRpcUrl: string,
	account: string,
	solverAccounts: readonly string[],
): Promise<boolean> {
	const response = await rpcCall(evmRpcUrl, {
		id: 1,
		jsonrpc: "2.0",
		method: "eth_getCode",
		params: [account, "latest"],
	})
	// Anything that is not a code string means the node did not answer the question. Reading that
	// as "no delegation" is how a throttled endpoint silently unseats a real solver: the bid is
	// dropped, the legs only it quoted vanish, and the pool reports zero depth it actually has.
	if (typeof response.result !== "string") {
		throw new PhantomRpcError(`eth_getCode returned no code for ${account} on ${evmRpcUrl}`)
	}

	const code = response.result.toLowerCase()
	if (!code.startsWith(DELEGATION_INDICATOR_PREFIX)) return false

	const delegate = `0x${code.slice(DELEGATION_INDICATOR_PREFIX.length)}`
	return solverAccounts.some((solverAccount) => solverAccount.toLowerCase() === delegate)
}

    function validateUserOp(PackedUserOperation calldata op, bytes32 userOpHash, uint256 missingAccountFunds)
        public
        override
        onlyEntryPoint
        returns (uint256)
    {
        if (op.signature.length == ECDSA_SIGNATURE_LENGTH) {
            if (_containsFillOrder(op.callData)) return ERC4337Utils.SIG_VALIDATION_FAILED;
            return super.validateUserOp(op, userOpHash, missingAccountFunds);
        }

        // Expected format: abi.encodePacked(commitment, solverSignature, sessionSignature)
        // commitment: 32 bytes, solverSignature: 65 bytes, sessionSignature: 65 bytes
        if (op.signature.length < INTENT_SELECT_SIGNATURE_LENGTH) return ERC4337Utils.SIG_VALIDATION_FAILED;

        bytes32 commitment = bytes32(op.signature[0:32]);
        bytes calldata solverSignature = op.signature[32:97];
        bytes calldata sessionSignature = op.signature[97:162];

        // Call IntentGatewayV2.select to recover the sessionKey. This also stages the
        // transient-storage selection that fillOrder enforces at execution.
        SelectOptions memory selectOptions =
            SelectOptions({commitment: commitment, solver: address(this), signature: sessionSignature});
        bytes memory selectCalldata = abi.encodeWithSelector(SELECT_SELECTOR, selectOptions);
        (bool success, bytes memory returnData) = INTENT_GATEWAY_V2.call(selectCalldata);

        if (!success || returnData.length < 32) return ERC4337Utils.SIG_VALIDATION_FAILED;

        address sessionKey = abi.decode(returnData, (address));
        uint192 userOpNonce = uint192(uint256(keccak256(abi.encodePacked(commitment, sessionKey))));
        if (uint192(op.nonce >> 64) != userOpNonce) return ERC4337Utils.SIG_VALIDATION_FAILED;
        if (!_rawSignatureValidation(userOpHash, solverSignature)) return ERC4337Utils.SIG_VALIDATION_FAILED;

        // Pay for gas if needed
        _payPrefund(missingAccountFunds);

        return ERC4337Utils.SIG_VALIDATION_SUCCESS;
    }

### quoteIntent(params)

Quotes an intent from the latest aggregate pool buy or sell rate published by the indexer. The pool rate is depth-weighted from fresh chain samples. Pass token addresses directly—the SDK resolves their configured symbols and decimals. No `strategy` option is needed for indexed-rate quotes.

	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)

					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
