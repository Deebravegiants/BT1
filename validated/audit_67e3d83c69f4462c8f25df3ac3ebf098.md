### Title
Webhook Tenant Identity Spoofing — `shop` Field Not Covered by HMAC Signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop` header value — which is never included in the signed bytes — to the app as the trusted tenant identifier. This breaks the identity binding `hmac_verified_bytes == bytes_the_app_trusts_for_tenant_routing`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from an unauthenticated HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`), which is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `to_signable_string` (i.e., the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` performs exactly this body-only check, and then immediately trusts `request.shop` (the unauthenticated header) as the tenant identifier passed to the app's handler: [4](#0-3) 

The equality that should hold is: *the shop value the HMAC cryptographically vouches for* == *the shop value the app uses to attribute the webhook data*. Because the signature covers only `@raw_body`, the `shop` header can be altered in transit/replay without invalidating the HMAC, since the same `client_secret` is shared across every shop that installs the app (the HMAC is keyed only by `Context.api_secret_key`, not per-shop).

### Impact Explanation
If any party can produce or replay one authentically-signed `(raw_body, hmac)` pair for the app (e.g., from a webhook delivered for their own shop after installing the app — an action any unprivileged internet user can take by installing a public app), that same pair remains valid for the app's shared secret regardless of which shop's data the body actually describes. By resending the identical body with a different `shopify-shop-domain` header value, the request still passes `HmacValidator.validate`, and the app's `WebhookHandler` receives `WebhookMetadata` attributing the payload to an arbitrary victim shop chosen by the attacker. This is a cross-tenant data injection / mis-attribution primitive: attacker-controlled content ends up processed under another merchant's tenant context.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid `(body, hmac)` pair produced by Shopify for the target app's `client_secret`; this is achievable by an unprivileged actor who installs the same app on their own shop (no `api_secret_key`, access token, or privileged/intercepted access needed) and reuses a genuine webhook they can trigger and control the content of (e.g., `products/create`, where the JSON body largely echoes merchant-supplied fields). The `shop-domain` header itself is never covered by the signature check in this gem's code path, so no cryptographic barrier prevents header substitution once a valid body/hmac pair is obtained.

### Recommendation
Bind the shop identity to the signed bytes. Options:
- Include the shop domain in the HMAC-signed content (`to_signable_string` should incorporate `shop`), matching Shopify's newer webhook payload conventions that carry shop identity inside the signed JSON body.
- Alternatively, cross-check `request.shop` against a value independently derived from data already inside the verified body (when the topic payload includes a shop-scoped identifier), and reject the webhook if they diverge.
- At minimum, document/require callers to treat `WebhookMetadata#shop` as unauthenticated unless corroborated by out-of-band, per-shop webhook secrets/session state.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (an ordinary Shopify Partner/dev store — no credentials from the app owner required).
2. Attacker triggers a webhook-firing action they fully control the payload of (e.g., creating a product) so `raw_body` contains attacker-chosen content.
3. Attacker obtains this `(raw_body, hmac)` pair (any mechanism that lets a shop owner observe a delivery they triggered, e.g. webhook delivery details/logs).
4. Attacker POSTs the exact same `raw_body` and `hmac-sha256` header to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` → `HmacValidator.validate(request)` passes because it only checks `raw_body` against the shared `api_secret_key`: [5](#0-4) 
6. The app's handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, processing/storing it under the victim tenant.
