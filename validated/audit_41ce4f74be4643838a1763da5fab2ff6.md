### Title
Hyperbridge-originated system messages (relayer fee withdrawals, host-executive actions) are dispatched with zero relayer fee, leaving them undeliverable by the permissionless relayer network - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/host-executive/src/lib.rs`)

### Summary
Several pallets that originate ISMP POST requests *from* Hyperbridge itself — including the relayer pallet's own fee-withdrawal flow — dispatch those requests with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }`. This mirrors the root cause of the referenced Anycall finding: the mechanism that is supposed to fund cross-chain delivery is not actually supplied, so the message has no economic incentive attached for the permissionless relayer network to deliver it to its destination.

### Finding Description
`pallet-ismp-relayer`'s `Pallet::withdraw` builds a `DispatchPost` that instructs a destination chain's `HostManager` (EVM) or the built-in `HYPERBRIDGE_MODULE_ID` handler (Substrate) to pay out a relayer's accumulated fees, then dispatches it with a **zero fee and zero payer**: [1](#0-0) 

The same zero-fee, zero-payer pattern is used by `pallet-ismp-host-executive`'s `withdraw` and `updateHostParams` dispatch calls, which relay governance/protocol-fee-withdrawal instructions to EVM `HostManager` contracts: [2](#0-1) 

This is a documented, still-open issue in the repository itself: the tracking doc `docs/outbound-request-incentivization.md` explicitly states that "hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` ... Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism." [3](#0-2) 

This is structurally analogous to the Anycall finding: the dispatch path that is meant to pay for cross-chain delivery (be it via `msg.value` to `anyCall`, or via `FeeMetadata.fee` here) is never actually funded, so the call/message can silently fail to be delivered because no relayer is compensated.

### Impact Explanation
Because these dispatches carry no relayer fee, Hyperbridge's decentralized, profit-driven relayer network has no economic reason to pick up and deliver them (as pallet-ismp's normal `accumulate_fees`/reward flow depends on a nonzero fee escrowed at source). Concretely:
- A relayer's own `withdraw_fees` extrinsic — the only way an unprivileged relayer recovers previously-earned protocol fees — dispatches a POST request that nobody but the relayer itself (running its own infrastructure) is incentivized to deliver to the destination chain's `HostManager`. If the withdrawing relayer does not also independently run delivery infrastructure with a funded account, the withdrawal message may never be delivered, leaving the already-debited `Fees::<T>` balance (zeroed at dispatch time, see `Fees::<T>::insert(..., U256::zero())` at line 177) undeliverable and the funds effectively stranded in `RELAYER_FEE_ACCOUNT` / the destination `EvmHost`.
- Host-executive protocol-fee withdrawals and host-parameter governance updates face the same reliability gap.

This satisfies the "route unable to deliver messages" acceptance criterion — a permissionless, single-transaction action (a relayer's own fee withdrawal) can result in funds becoming practically inaccessible absent altruistic self-relaying.

### Likelihood Explanation
Every relayer withdrawal and every host-executive protocol action goes through this code path unconditionally — it's not a rare edge case, it is the *only* implementation currently in the codebase for these flows, and the project's own internal tracking doc (`docs/outbound-request-incentivization.md`, referencing tracking issue `polytope-labs/hyperbridge#532`) confirms the team is aware the current behavior relies purely on altruism rather than sound incentives. Likelihood is High for exposure (affects all relayer withdrawals) though actual fund loss is contingent on no altruistic relayer picking up the message.

### Recommendation
Attach a real, non-zero relayer fee (escrowed from a system-owned account, e.g. treasury/PalletId account) when dispatching Hyperbridge-originated requests such as relayer fee withdrawals and host-executive actions, so the existing incentive/reward machinery (`accumulate_fees`) can compensate whichever relayer delivers them — consistent with the "shape of the solution" already scoped in `docs/outbound-request-incentivization.md` (a per-`source_module_id` reward paid from treasury, claimed against a destination state proof), rather than depending on relayer altruism.

### Proof of Concept
1. A relayer accumulates fees on Hyperbridge via `accumulate_fees` and later calls `withdraw_fees` (`Pallet::withdraw`) to claim their balance on a destination EVM chain.
2. `Pallet::withdraw` zeroes the relayer's `Fees::<T>` entry and dispatches a `DispatchPost` to the destination `HostManager` with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` (`modules/pallets/relayer/src/withdrawal.rs:161-175`).
3. Because the dispatched request carries no relayer fee, no third-party relayer in the permissionless network has an economic incentive to submit the delivery proof to the destination chain's `HostManager.onAccept`.
4. If the relayer does not run their own dedicated delivery infrastructure with a funded destination-chain account, the withdrawal message is never delivered — the relayer's previously-earned fees (already zeroed out of `Fees::<T>`) remain undelivered/unpaid indefinitely.

```markdown
## The problem

A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.
```
