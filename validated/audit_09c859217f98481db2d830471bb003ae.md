### Title
Unvalidated route pool addresses let attacker code execute inside a victim's signed auth tree and drain arbitrary wallet tokens via `swap_collateral` / `swap_debt` / `repay_debt_with_collateral` / `multiply` - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The SSRF bug class — a protocol performing attacker-directed outbound calls — maps onto XOXNO Lending's strategy-swap path. The controller passes caller-supplied route bytes to the configured router, which invokes whatever pool/token addresses the payload names, with no allowlist. Because the whole call executes under the caller's `require_auth` tree, a malicious "hop pool" contract can append a `token.transfer(victim, attacker, amount)` child to that tree during simulation; a wallet that signs the recorded tree authorizes theft of any token the victim holds, far beyond the routed amount. Neither the payload `min_out` nor the controller's final risk gates bound the loss.

### Finding Description
`swap_tokens` (contracts/controller/src/strategies/swap.rs:13-55) is reached by `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`. It narrows the controller's grant to one exact `token_in.transfer(controller, router, amount_in)` invocation (INV-STRAT-01), then calls `router.execute_strategy(controller, amount_in, swap)` where `swap` is opaque caller-controlled XDR. The controller never inspects or restricts the venue/pool addresses inside the route; per the threat model, "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (docs/explanation/threat-model.md:154-165).

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the full chain: a rogue hop pool invoked inside a `swap_collateral` route calls `token.transfer(alice, attacker, WALLET_BALANCE)` on an unlisted token; simulation records that transfer as a sub-invocation of Alice's `swap_collateral` auth entry, the swap otherwise settles normally (fair output credited, risk gates pass), and Alice's unrelated wallet balance is reduced to zero while the attacker's is credited (lines 194-226). A second test (lines 322-367) confirms enforcing mode accepts the theft only when the tree is signed — which is exactly what simulation-driven wallets produce for the poisoned transaction.

### Impact Explanation
Theft of user funds: any token balance in the victim's wallet (including tokens the protocol never listed) can be transferred to the attacker in the same transaction that performs an otherwise-normal, healthy, successful strategy swap. The stolen amount is not limited to `amount_in`, `total_min_out`, or the account's position — it is the victim's entire balance of any token the attacker names. Severity Medium: theft is unbounded per victim but requires the victim to sign a transaction built on an attacker-influenced route payload (e.g., via a poisoned quote/frontend), which matches CVSS 4.3-style user-assisted disclosure/loss.

### Likelihood Explanation
Any unprivileged attacker can deploy a contract exposing the venue function ABI and craft route bytes naming it; no protocol privilege, leaked key, or upgrade is needed. Reachability is demonstrated end-to-end in-repo: recording-mode simulation attaches the rogue transfer under the caller's own entry, and enforcing mode executes it once signed. The only mitigating factor is that the victim must sign the expanded auth tree — Soroban wallets show the tree, but route XDR is opaque and clients are not required by the contracts to decode it, so a malicious route source makes exploitation realistic.

### Recommendation
The trust boundary sits in the swap-aggregator (out of scope to modify here), so the controller-level fix is to constrain what it will sign over: pin the expected `token_in`/`token_out` and reject routes whose asset registry introduces third-party addresses beyond declared markets where feasible, and surface the decoded route to the caller. At minimum, wallets/SDKs composing `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral` must decode the `StrategyPayload`, verify every hop pool against the intended venue, and refuse to sign an authorization tree containing any child other than the single expected input transfer. Longer term, an on-chain venue allowlist on the router removes the class entirely.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

- `RogueHopPool::swap` (lines 62-71) issues `token.transfer(victim, attacker, amount)` on an arbitrary wallet token from inside the route hop.
- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 194-226): `swap_collateral` through the rogue pool records the stolen transfer as a child of Alice's auth entry; asserting `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` while her ETH supply credit succeeds.
- `source_account_credentials_bind_the_rogue_transfer_to_the_tree_without_an_entry_signature` (lines 322-367): the same transfer fails under an honest tree and succeeds once the tree includes the rogue child — confirming the theft rides the victim's signature, not any protocol authorization.
