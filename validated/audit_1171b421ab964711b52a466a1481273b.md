### Title
SimplexPaymaster's Chainlink oracle pricing lacks L2 sequencer uptime checks, allowing stale-price gas payment on Arbitrum/Optimism during sequencer downtime - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` prices ERC-4337 UserOp gas payments in ERC-20 tokens (USDC/USDT/etc.) by reading `AggregatorV3Interface.latestRoundData()` for both the native asset and the token, checking only that the answer is positive and that `block.timestamp - updatedAt <= maxOracleAge`. It does not check a Chainlink L2 Sequencer Uptime Feed. The contract is deployed via the generic multi-chain deployment tooling (`evm/script/deploy.sh`, `evm/script/DeploySimplexPaymaster.s.sol`) which explicitly lists `arbitrum` and `optimism` among supported mainnets. [3](#0-2) [4](#0-3) 

### Finding Description
On Arbitrum/OP-stack L2s, Chainlink recommends gating price consumption on a dedicated Sequencer Uptime Feed because during sequencer outages (and immediately after they resume), the L2 aggregator's `updatedAt` timestamp can still look "fresh" relative to `maxOracleAge` while the underlying market data is stale or a malicious/compromised sequencer resequences transactions against out-of-date prices. `_getOraclePrice` only guards against staleness by comparing `updatedAt` to a governance-set `maxOracleAge` (deployed default ~90,000s ≈ 25h, hard ceiling `MAX_ORACLE_AGE = 7 days`), which is far too coarse to catch a sequencer-downtime window and provides no defense against the sequencer-restart replay scenario Chainlink's L2 guidance specifically warns about. [5](#0-4) [6](#0-5) 

Both `_tokenPrice` (used for `getTokenPrice`/`estimateTokenCost`/UserOp validation pricing) and `swapAndDeposit`'s expected-output computation rely on `_getOraclePrice`, so a stale/incorrect price during or immediately after an Arbitrum/Optimism sequencer outage directly affects: (1) how many tokens a permissionless UserOp sender is charged for gas, and (2) the minimum-output bound enforced on the treasury's fee-recycling swap. [7](#0-6) [8](#0-7) 

### Impact Explanation
Any unprivileged party submitting an ERC-4337 UserOperation through this permissionless paymaster is directly affected by whatever price `_getOraclePrice` returns. If the native/token price diverges from the true market price during a sequencer outage window (bounded only by the loose `maxOracleAge`, not by sequencer-restart grace-period logic), UserOps can be undercharged (loss to the protocol/treasury surplus) or overcharged (loss to users), and the same stale value feeds the `swapAndDeposit` slippage bound, so fee-recycling swaps can execute at an incorrect implied rate. This is a Medium-severity fund-loss vector reachable by a single submitted UserOp with no privileged access required.

### Likelihood Explanation
Likelihood is tied to sequencer downtime events on Arbitrum/Optimism, which do occur periodically; the contract's staleness bound is deliberately loose (governance sets it up to 7 days) to accommodate long stablecoin heartbeats, so it offers essentially no protection against the shorter sequencer-outage windows Chainlink's guidance targets. Any UserOp submitted during or shortly after such a window exploits this without needing special timing precision beyond monitoring sequencer status, which is public.

### Recommendation
Add a Chainlink `L2SequencerUptimeFeed` check (per-chain configurable, similar to `nativeOracle`/token oracles) inside `_getOraclePrice` or as a pre-check in `_tokenPrice`/`swapAndDeposit`: read `latestRoundData()` from the sequencer feed, revert if `answer == 1` (sequencer down) or if `block.timestamp - startedAt` is within the recommended grace period (e.g., 1 hour) after the sequencer came back up, consistent with Chainlink's documented L2 data-feed integration pattern.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum via `DeploySimplexPaymaster.s.sol` (a supported mainnet per `deploy.sh`'s chain list) with a Chainlink native/USD and token/USD feed.
2. Arbitrum's sequencer goes down; the aggregator's `updatedAt` on the last posted round remains within `maxOracleAge` (e.g., 25h default) even though the true price has since diverged.
3. An attacker (or any UserOp sender) submits a UserOperation with `paymasterData` referencing a registered token while the price is stale/incorrect; `fetchDetails`/`_tokenPrice` compute cost from the stale `_getOraclePrice` result, over- or under-charging the token amount relative to fair value, with no revert since only `updatedAt` staleness (not sequencer status) is checked.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
