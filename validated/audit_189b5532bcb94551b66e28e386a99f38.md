The docs explicitly claim `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and pass the header-derived `shop`, `topic`, `webhook_id`, `api_version` straight to the handler via `WebhookMetadata` [1](#0-0) . ### Title
Webhook HMAC only signs the raw body, not the `shop-domain`/`topic`/`webhook_id` headers, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` only proves the *body bytes* were signed by Shopify, while `Registry.process` trusts the unauthenticated `shop`, `topic`, and `webhook_id` header values when dispatching to handlers.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers, never included in the signed payload: [2](#0-1) 

The HMAC verification, `Utils::HmacValidator.validate`, computes the signature over `verifiable_query.to_signable_string`, i.e. `@raw_body` only: [3](#0-2) [4](#0-3) 

`Registry.process` uses this validation result as its sole authenticity gate, then dispatches using the *unsigned* `shop`, `topic`, and `webhook_id` fields: [1](#0-0) 

This is the same identity-binding defect class as the reported bug: a field the code *acts on* (here, `shop`/`topic`/`webhook_id`) is not covered by the cryptographic check (here, the webhook HMAC), even though the code and its own documentation assert that `process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`). The binding the code implicitly assumes — `hmac_signed(raw_body) == true` implies `shop header == tenant that generated raw_body` — does not hold, since `shop`, `topic`, and `webhook_id` are excluded from `to_signable_string`.

### Impact Explanation
An attacker who operates their own shop and has the app installed receives genuine, correctly HMAC-signed webhook deliveries from Shopify for their own shop/topic (e.g. `app/uninstalled`, `customers/data_request`, or any topic the app subscribes to). Because the signature covers only the raw body — not the shop domain, topic, or webhook id — the attacker can replay that exact `(raw_body, hmac)` pair directly against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop that also uses the app. `Utils::HmacValidator.validate` still returns `true` because the body/HMAC pair is legitimate, and `Registry.process` dispatches the handler with `shop: <victim shop>`, causing the app to act on another tenant's identity (cross-tenant access/confusion) — e.g. triggering uninstall/data-redaction handling or writing attacker-controlled data under the victim's shop record.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on their own shop (a normal, self-service action for public Shopify apps) can obtain at least one legitimate signed webhook body/HMAC pair and directly craft an HTTP request to the app's public webhook endpoint with forged headers, requiring no access token, `client_secret`, or privileged account.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable string, or otherwise cryptographically bind them (e.g. by validating them against Shopify's out-of-band webhook metadata/App's own session store for that shop) rather than trusting header values that sit outside the signature.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and register a webhook handler for topic `X`.
2. Capture a real Shopify-delivered webhook request: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but setting `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `HMAC(B) == H`; `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-supplied data as if it originated from the victim shop.
