Found the identity binding issue in `Webhooks::Request#shop` vs the HMAC-verified bytes.

### Title
Webhook `shop` and `topic` values used for routing/handler dispatch are unauthenticated header data, not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), while the HMAC signature covers only `@raw_body` (`to_signable_string` returns `@raw_body`). `Registry.process` validates the HMAC against the body, then trusts the header-derived `shop`/`topic` values verbatim to dispatch to a handler and to construct `WebhookMetadata`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw JSON body [1](#0-0) , and `HmacValidator.validate` computes/compares the signature purely over that string [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the HMAC at all [3](#0-2) . `Registry.process` validates the HMAC (over the body only) and then immediately trusts `request.topic` and `request.shop` to select the handler and populate `WebhookMetadata` passed to app code [4](#0-3) .

The identity binding broken: `hmac_signature ≟ HMAC(secret, raw_body)` is verified, but the equality that actually matters for tenant identification, `shop_header == shop_bound_by_hmac`, is never checked — the `shop` field is parsed from unauthenticated header bytes, not from bytes covered by the signature.

### Impact Explanation
An unprivileged attacker who can reach the app's webhook endpoint (this endpoint is typically public, since it must accept unauthenticated POSTs from Shopify) can send a request with a **valid HMAC for a body they control** (since they choose the raw body, they can compute the correct HMAC only if they know the secret — however the header values `shopify-shop-domain` and `shopify-topic` are not part of that signed content). This means the gem cannot detect if an intermediary/proxy or a request-forging actor swaps the `shop-domain` header while leaving a body/HMAC pair intact (e.g., replaying a captured legitimate webhook body under a different shop's identity, or a shared reverse proxy that mutates headers). The app's `handler.handle` is invoked with attacker-controlled `shop` metadata, causing cross-tenant data misattribution in the host application if it uses `WebhookMetadata#shop` to select which tenant's data to update — a cross-tenant boundary violation.

### Likelihood Explanation
This requires network-level control or an intermediary capable of tampering with headers of an otherwise-valid, HMAC-signed webhook body (e.g., a captured or replayed webhook where only header routing metadata is altered, or a misconfigured proxy/CDN in front of the app that does not preserve header integrity). It does not require the attacker to know the `api_secret_key`; they only need one legitimately-HMAC'd body (which is straightforward to obtain, since any real webhook delivery is a valid example) to replay with modified shop/topic headers, as long as they can reach the endpoint with adjustable headers.

### Recommendation
Include `shop`, `topic`, and any other header fields used for authorization/routing decisions in the HMAC-signed content (or otherwise authenticate them, e.g., via a signed JWT/session-token-style mechanism), so `to_signable_string` binds all security-relevant fields, not just the raw body. At minimum, document that consuming applications must not rely on `Request#shop`/`Request#topic` for tenant isolation unless header integrity is separately guaranteed by the deployment.

### Proof of Concept
1. Capture a legitimate Shopify webhook delivery to the app's public webhook endpoint for `shop-a.myshopify.com`, topic `orders/create`, with a valid `X-Shopify-Hmac-Sha256` header (correctly computed over the raw body).
2. Replay the exact same raw body and HMAC header, but modify `X-Shopify-Shop-Domain` to `shop-b.myshopify.com` (or modify `X-Shopify-Topic`).
3. `Webhooks::Request#initialize` parses the new headers, `HmacValidator.validate` still succeeds because it only checks the raw body against the HMAC [5](#0-4) .
4. `Registry.process` dispatches to the handler using `request.shop == "shop-b.myshopify.com"`, even though the signed payload actually belonged to `shop-a` [6](#0-5) .
