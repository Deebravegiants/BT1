Audit Report

## Title
Unauthenticated `/sessions` login endpoint distinguishes "Invalid email" vs "Invalid password" errors, enabling user email enumeration - (File: core/sessions/localauth/orm.go)

## Summary
The `POST /sessions` endpoint, registered on the unauthenticated route group in `core/web/router.go`, forwards raw email/password credentials to `SessionsController.Create` in `core/web/sessions_controller.go`, which calls `AuthenticationProvider().CreateSession`. In the local-auth implementation (`core/sessions/localauth/orm.go`), `CreateSession` returns distinct plain-text errors — `"Invalid email"`, `"Invalid password"`, or an underlying `sql.ErrNoRows`-derived error from `FindUser` — depending on why authentication failed, and these are serialized verbatim into the JSON:API response body by `jsonAPIError`/`models.NewJSONAPIErrorsWith(err.Error())`.

## Finding Description
`SessionsController.Create` ( [1](#0-0) ) passes any error from `CreateSession` straight into `jsonAPIError(c, http.StatusUnauthorized, err)`. `jsonAPIError` in `core/web/helpers.go` checks whether the error is a `*models.JSONAPIErrors`; since `CreateSession`'s errors are plain `pkgerrors.New(...)` values, it falls through to `c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))`, placing the raw error text directly in the response ( [2](#0-1) ).

`CreateSession` in `core/sessions/localauth/orm.go` first calls `FindUser`, propagating any lookup error (including `sql.ErrNoRows` for a nonexistent email) unmodified; then it separately returns `"Invalid email"` if the case-normalized email doesn't match, and `"Invalid password"` if the password hash check fails ( [3](#0-2) ). Because `findUser` uses a case-insensitive lookup (`SELECT * FROM users WHERE lower(email) = lower($1)`), a non-existent email produces a `sql.ErrNoRows`-based error at the `FindUser` step, distinct from the `"Invalid email"`/`"Invalid password"` strings produced later ( [4](#0-3) ).

The existing test, `TestSessionsController_Create`, exercises exactly this distinction ("incorrect pwd" vs "incorrect email" cases) but only asserts the status code, not response body content, confirming the difference is present and unguarded ( [5](#0-4) ). The only control on this route is a rate limiter, not response normalization ( [6](#0-5) , referenced from the report).

## Impact Explanation
This is a legitimate, low-severity information-disclosure issue: an unauthenticated actor can distinguish "email not registered" from "email registered, wrong password" by inspecting the JSON:API error body returned by `/sessions`, enabling enumeration of valid node API user email addresses. This maps to the "cross-user response corruption" / unauthenticated information-disclosure impact category, and can assist targeted credential-stuffing against a Chainlink node's admin API, though it does not itself grant authentication bypass or credential/key exfiltration.

## Likelihood Explanation
The endpoint is unauthenticated and reachable by design; any external network client can submit arbitrary email/password pairs and observe the response body. The only mitigating control is the configurable `UnauthenticatedPeriod`/`Unauthenticated` rate limit, which slows but does not prevent enumeration, particularly for a small/targeted list of candidate emails or when distributed across multiple source IPs.

## Recommendation
Normalize authentication failure responses in `core/sessions/localauth/orm.go` (and equivalent LDAP/OIDC providers) so that "user not found," "invalid email," and "invalid password" all produce an identical generic message and status code, and ensure `SessionsController.Create` in `core/web/sessions_controller.go` never forwards the underlying error text verbatim to the client (e.g., wrap all `CreateSession` failures in a fixed `"invalid credentials"` message before calling `jsonAPIError`).

## Proof of Concept
1. `POST /sessions` with `{"email":"<known-valid-user>","password":"wrong"}` → response body contains `"Invalid password"`.
2. `POST /sessions` with `{"email":"doesnotexist@example.com","password":"wrong"}` → response body contains a distinct message (DB no-rows-derived error, not `"Invalid password"`).
3. A Go integration test extending `TestSessionsController_Create` in `core/web/sessions_controller_test.go` that additionally asserts on `resp.Body` content for the "incorrect pwd" vs "incorrect email" cases would directly demonstrate the distinguishable error strings.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
