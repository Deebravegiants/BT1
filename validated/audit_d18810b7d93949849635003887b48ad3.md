### Title
Unchecked account index values in `parse_token_group_instruction`'s `InitializeGroup` arm cause an indexing panic during JSON-parsed transaction encoding - (File: transaction-status/src/parse_token/extension/token_group.rs)

### Summary
`check_num_token_accounts` in this module only validates the *count* of account indexes (`account_indexes.len() < num`), never the *values* of the byte indexes themselves. In the `InitializeGroup` arm, `account_keys[account_indexes[0] as usize]` (and indexes `[1]`, `[2]`) index directly into `AccountKeys`/`Vec<Pubkey>` without a bounds check, so a `CompiledInstruction.accounts` array with the correct length but out-of-range byte values causes an out-of-bounds indexing panic when a node later parses the committed transaction for `getTransaction`/`getConfirmedBlock`.

### Finding Description
`parse_token_group_instruction` in `transaction-status/src/parse_token/extension/token_group.rs` handles `TokenGroupInstruction::InitializeGroup` by calling: [1](#0-0) 

The guard is `check_num_token_accounts(account_indexes, 3)`, which forwards to `check_num_accounts`: [2](#0-1) 

This function only compares `accounts.len() < num`; it never validates that each `u8` value in `account_indexes` is `< account_keys.len()`. Immediately after this check passes, the code does `account_keys[account_indexes[0] as usize]`, `account_keys[account_indexes[1] as usize]`, and `account_keys[account_indexes[2] as usize]` via `Index` on `AccountKeys` (a thin wrapper around a `Vec<Pubkey>`/loaded-address slice), which panics on out-of-bounds access exactly like a normal slice index.

Because a `CompiledInstruction`'s `accounts: Vec<u8>` is attacker-controlled raw bytes (0–255) that are *not* validated against `account_keys.len()` anywhere in transaction sanitization/execution (account-index validity for *execution* is enforced during message loading/locking, but this parsing path runs independently, post-commit, purely for RPC encoding), an attacker can craft a `TokenGroupInstruction::InitializeGroup` instruction with exactly 3 accounts (satisfying the count check) whose byte values (e.g., `250`) are far beyond the transaction's actual `account_keys.len()` (e.g., 3). The instruction can even reference an unrelated/nonexistent program id in the `accounts` list — the transaction doesn't need to succeed at runtime; parsing happens on the *committed* transaction regardless of execution outcome (this parsing path is invoked from `parse_ui_instruction` / `parse` → `parse_token` → `parse_token_group_instruction`, used whenever any client requests `jsonParsed` encoding via `getTransaction`, `getConfirmedBlock`, or similar RPC methods).

This is the same unguarded-index pattern present throughout `parse_token.rs` and its extension parsers (e.g. `account_keys[instruction.accounts[0] as usize]` appears dozens of times), all relying solely on `check_num_accounts`'s length check, with no per-value bounds validation.

### Impact Explanation
A single, cheaply-crafted, unprivileged transaction that gets included in a block causes every RPC node that later serves `getTransaction`/`getConfirmedBlock` (or any JSON-parsed encoding of that transaction/block) with `encoding=jsonParsed` to panic inside the request-handling code path (`parse` → `parse_token` → `parse_token_group_instruction`). This breaks the stated invariant of deterministic, non-panicking transaction encoding for identical committed input across all RPC nodes, and denies that specific getTransaction/getConfirmedBlock request (and potentially the serving thread/handler) for every node that has indexed that block, not just the leader. This matches an RPC/API panic-DoS category: it requires only a single crafted transaction inserted once and a single subsequent RPC call to trigger — it does not require repeated calls per slot, multiple clients, or unfiltered `getProgramAccounts`, so it is not excluded by the SECURITY.md RPC-DoS carve-out.

Note: whether this crashes the entire RPC process or is contained to a single request thread depends on how the JSON-RPC framework (jsonrpc-http-server / tokio thread pool) handles panics in handler threads; I could not fully verify from the indexed code whether panics here are caught (e.g., via `catch_unwind`) at the HTTP server layer or propagate to abort the process. Regardless, at minimum this is a reliable denial of a specific RPC request/response for every node serving that transaction/block with `jsonParsed` encoding.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: only requires constructing a raw `CompiledInstruction` (not using the `spl_token_group_interface` builder helpers, which always emit correct indices) with a valid 3-account-length list containing out-of-range byte values, targeting the SPL Token-2022 program id with `TokenGroupInstruction::InitializeGroup` discriminant data. No special privileges, staked node, or validator control are needed — this is a standard transaction submitted to a public TPU/RPC endpoint. Execution success is irrelevant since parsing runs on the already-committed transaction. The bug is 100% deterministic and reproducible on every node that later parses this specific transaction with `jsonParsed` encoding.

### Recommendation
Add bounds validation for each account index value against `account_keys.len()` before indexing, e.g. extend `check_num_accounts`/`check_num_token_accounts` (or add a new helper) to verify `account_indexes.iter().all(|&i| (i as usize) < account_keys.len())`, returning `ParseInstructionError::InstructionKeyMismatch` (or a new dedicated error) instead of allowing direct indexing. Apply this fix uniformly across `parse_token.rs` and all its extension modules (`token_group.rs`, `confidential_transfer.rs`, `confidential_transfer_fee.rs`, `permissioned_burn.rs`, etc.), since they all share the identical unguarded-indexing pattern. Alternatively, replace direct `account_keys[idx]` indexing with `account_keys.get(idx)`, returning a parse error on `None`.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/token_group.rs (added test)
#[test]
fn test_initialize_group_out_of_range_account_index_does_not_panic() {
    use {
        solana_message::compiled_instruction::CompiledInstruction,
        spl_token_group_interface::instruction::TokenGroupInstruction,
    };

    // Only 3 real account keys in the message/transaction.
    let account_keys_vec = vec![
        Pubkey::new_unique(),
        Pubkey::new_unique(),
        Pubkey::new_unique(),
    ];
    let account_keys = AccountKeys::new(&account_keys_vec, None);

    // Craft raw CompiledInstruction bypassing spl_token_group_interface builder helpers:
    // 3 indexes (passes check_num_token_accounts(_, 3)) but each value (250) is
    // out of range for account_keys.len() == 3.
    let group = spl_token_group_interface::instruction::InitializeGroup {
        max_size: 10.into(),
        update_authority: None.into(),
    };
    let ix_data = TokenGroupInstruction::InitializeGroup(group)
        .pack(); // however the interface serializes this discriminant + payload

    let malicious_instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![250, 251, 252], // count == 3, but values out-of-range
        data: ix_data,
    };

    // Expectation: should return a graceful ParseInstructionError, NOT panic.
    let result = std::panic::catch_unwind(|| {
        crate::parse_token::parse_token(&malicious_instruction, &account_keys)
    });

    assert!(
        result.is_ok(),
        "parse_token panicked on out-of-range account indexes instead of returning an error"
    );
    // After the fix, expect:
    // assert!(result.unwrap().is_err());
}
```

Fuzz/invariant plan: for each `TokenGroupInstruction` variant and each account-index slot, generate `account_indexes` vectors whose length satisfies `check_num_token_accounts` but whose byte values range over `0..=255` independent of `account_keys.len()` (which should be varied from 0 up to a small bound like 5); assert that `parse_token`/`parse_token_group_instruction` never panics and, post-fix, returns `Err(ParseInstructionError::...)` whenever any index is out of range.

pub(crate) fn check_num_accounts(
    accounts: &[u8],
    num: usize,
    parsable_program: ParsableProgram,
) -> Result<(), ParseInstructionError> {
    if accounts.len() < num {
        Err(ParseInstructionError::InstructionKeyMismatch(
            parsable_program,
        ))
    } else {
        Ok(())
    }
}
