### Title
Missing L2 sequencer-uptime check in SimplexPaymaster's Chainlink price consumption - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `AggregatorV3Interface.latestRoundData()` for both the native/USD oracle and each token/USD oracle, and is explicitly designed to run on Base ("Base/Ethereum stablecoins up to 24h" heartbeat) among other chains. Its price-fetch helper, `_getOraclePrice`, only checks the answer's sign and its staleness against `maxOracleAge` — it never checks Chainlink's L2 Sequencer Uptime Feed, so a Base sequencer outage/restart can let the paymaster consume incorrect pricing data without reverting. [1](#0-0) [2](#0-1) 

### Finding Description
`_getOraclePrice` is the sole gate on Chainlink data used for pricing:

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
``` [3](#0-2) 

This function is reached from `_tokenPrice`, which is called by `_fetchDetails` (the unprivileged, permissionless path any ERC-4337 UserOperation sender triggers during paymaster validation) and by `getTokenPrice`/`estimateTokenCost`: [4](#0-3) [5](#0-4) 

Because there is no check of a Sequencer Uptime Feed (e.g. Base's `0xBCF85224...`), the contract cannot distinguish between:
- a genuinely fresh price, versus
- a price that is technically "fresh" by `updatedAt` timestamp but was produced/reported incorrectly around a sequencer outage/restart, or
- a price whose heartbeat has not yet lapsed `maxOracleAge` even though upstream updates have silently stalled because the sequencer that would relay new rounds is down.

The same unguarded `_getOraclePrice` is also used in `swapAndDeposit` to compute `amountOutMin` for a Uniswap V2 swap of accrued token fees to native currency: [6](#0-5) 

### Impact Explanation
Any unprivileged actor able to submit an ERC-4337 UserOperation through this paymaster can have their gas-token cost computed from a Chainlink price that is stale/incorrect due to an undetected Base sequencer outage, since `_getOraclePrice` performs no sequencer-liveness check before trusting `latestRoundData()`. This can result in:
- Users being charged an incorrect (favorable or unfavorable) amount of the registered ERC-20 token for gas, directly affecting fund transfers handled by `_prefund`/`postOp`.
- Governance-triggered `swapAndDeposit` computing an incorrect `amountOutMin`, risking treasury losses on the fee-recycling swap if invoked while the underlying price is unreliable.

This mirrors the reported bug class (no Chainlink Sequencer Uptime Feed check on an L2 such as Base), qualifying as a Medium-severity pricing/fund-safety issue.

### Likelihood Explanation
Base sequencer downtime is an infrequent but real, previously-observed event. Because `_getOraclePrice` is on the hot path of every gas-payment validation (`_fetchDetails`) that any UserOperation sender triggers, exploitation requires no special privilege — merely submitting a UserOperation during/shortly after a sequencer outage window would exercise the unguarded pricing logic.

### Recommendation
Integrate Chainlink's L2 Sequencer Uptime Feed check (per chain, e.g. Base's feed) into `_getOraclePrice` (and `swapAndDeposit`'s pricing), reverting or falling back safely when the sequencer is reported down or within the recommended grace period after it comes back up, consistent with Chainlink's documented L2 pattern.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Base with a registered token/USD Chainlink oracle, per `initialize`/`_registerToken`.
2. Simulate a Base sequencer outage/restart scenario where the price feed's `latestRoundData()` returns a value whose `updatedAt` is still within `maxOracleAge` (e.g., the feed reported one last round just before the outage, or reports an initial round right after restart) but that price is stale/unreliable relative to the market due to the sequencer being unavailable.
3. Submit a UserOperation with `paymasterData` selecting that token; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the price without any sequencer check, computing `tokenPrice` from unreliable data.
4. `_prefund`/`postOp` charge the user based on this tokenPrice, or `swapAndDeposit` computes `amountOutMin` from it, producing incorrect financial outcomes without any revert.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
