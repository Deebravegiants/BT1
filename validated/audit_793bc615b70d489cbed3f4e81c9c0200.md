### Title
Attacker-supplied `PreemptionPolicy` on `CompositePodGroup` bypasses validation/overwrite when `PodGroupPreemptionPolicy` feature gate is disabled - (File: plugin/pkg/admission/priority/admission.go)

### Summary
In `admitCompositePodGroup`, the preemption-policy reconciliation block is gated by a second, independent feature check `utilfeature.DefaultFeatureGate.Enabled(features.PodGroupPreemptionPolicy)` nested inside the outer `features.CompositePodGroup` gate. When `CompositePodGroup` is enabled but `PodGroupPreemptionPolicy` is disabled, the entire block that validates and derives `cpg.Spec.PreemptionPolicy` from the referenced `PriorityClass` is skipped, so a user-supplied `cpg.Spec.PreemptionPolicy` is left completely untouched and unvalidated.

### Finding Description
`admitCompositePodGroup` [1](#0-0)  first resolves priority and preemption policy from the referenced `PriorityClass` via `establishPriority`, and unconditionally sets `cpg.Spec.Priority` and `cpg.Spec.PriorityClassName` from that resolution [2](#0-1) . However, the code that translates the resolved `preemptionPolicy` into `scheduling.PreemptionPolicy`, rejects mismatched attacker-supplied values, and overwrites `cpg.Spec.PreemptionPolicy` is wrapped in `if utilfeature.DefaultFeatureGate.Enabled(features.PodGroupPreemptionPolicy) && preemptionPolicy != nil` [3](#0-2) . If `PodGroupPreemptionPolicy` is disabled while `CompositePodGroup` is enabled, this whole block is skipped — there is no forbidden check comparing `cpg.Spec.PreemptionPolicy` to the PriorityClass's `PreemptionPolicy`, and no overwrite occurs, leaving whatever value the attacker submitted in the request body untouched. This mirrors the identical pattern in `admitPodGroup` [4](#0-3) , confirming the pattern is a repeated design choice rather than a one-off bug.

An unprivileged user with only create permission on `compositepodgroups` can submit a `CompositePodGroup` referencing a `PriorityClass` whose `PreemptionPolicy` is `PreemptNever`, while explicitly setting `cpg.Spec.PreemptionPolicy: PreemptLowerPriority`. With the gate combination described (`CompositePodGroup=true`, `PodGroupPreemptionPolicy=false`), admission accepts and persists the object with the attacker's `PreemptLowerPriority` value, inconsistent with the priority class's intended non-preempting semantics.

### Impact Explanation
This falls under the Kubernetes bounty "admission/validation bypass leading to persisted invalid/protected field" class. Concretely, an object controlled by an unprivileged tenant can carry a preemption policy inconsistent with the cluster-defined `PriorityClass`, potentially allowing pods/groups scheduled under this composite pod group to preempt lower-priority tenant workloads even though the referenced PriorityClass intends `PreemptNever` semantics. The scope of the impact is bounded by whether downstream schedulers actually honor `CompositePodGroup.Spec.PreemptionPolicy` for preemption decisions — that consumption logic was not located/verified during this review.

### Likelihood Explanation
The precondition (`CompositePodGroup` enabled, `PodGroupPreemptionPolicy` disabled) is an operator/API-server feature-gate configuration decision, not something the attacker controls. Given that combination, the exploit is trivial and fully reproducible: any user with create permission on `compositepodgroups` can set the field directly in the request body, and no other validation layer was found in `pkg/apis/scheduling/validation/validation.go` that independently cross-checks `PreemptionPolicy` against the referenced `PriorityClass` (I was not able to confirm within the available tool calls whether `validation.go` performs any standalone consistency check for `CompositePodGroup.Spec.PreemptionPolicy` against the PriorityClass; this should be verified, since if such a check exists there, the admission-time bypass may be defense-in-depth only rather than a full validation bypass).

### Recommendation
Decouple the priority/preemption-policy derivation from feature-gate skipping: only gate whether the `PreemptionPolicy` API field is *acceptable* on the object schema (validation layer), but always perform the derivation/consistency check in admission when `CompositePodGroup` (and `PodGroupPreemptionPolicy`, if the field is meant to be feature-gated) is enabled — i.e., if `PodGroupPreemptionPolicy` is disabled, either strip/reject any client-supplied `cpg.Spec.PreemptionPolicy` value outright, or still validate/overwrite it from the resolved PriorityClass rather than silently skipping the whole block. Apply the same fix to `admitPodGroup`.

### Proof of Concept
Unit test in `plugin/pkg/admission/priority/admission_test.go` style:
1. Register a `PriorityClass` "pc-never" with `Value: 1000`, `PreemptionPolicy: PreemptNever` in the lister.
2. Set `utilfeature.DefaultFeatureGate` overrides: `CompositePodGroup=true`, `PodGroupPreemptionPolicy=false`.
3. Construct a `scheduling.CompositePodGroup` with `Spec.PriorityClassName: "pc-never"` and `Spec.PreemptionPolicy` explicitly set to `scheduling.PreemptLowerPriority`.
4. Call `plugin.admitCompositePodGroup(attributes)` for a Create operation.
5. Assert: no error returned, and `cpg.Spec.PreemptionPolicy` still equals `PreemptLowerPriority` (unchanged, not derived to `PreemptNever` and not rejected) — demonstrating attacker-controlled value persists despite referencing a PriorityClass with a conflicting policy.
6. Repeat with `PodGroupPreemptionPolicy=true` to show the same request is now rejected via `admission.NewForbidden`, confirming the gate-off path is the source of the bypass.

func (p *Plugin) admitCompositePodGroup(attributes admission.Attributes) error {
	if !utilfeature.DefaultFeatureGate.Enabled(features.CompositePodGroup) {
		return nil
	}

	cpg, ok := attributes.GetObject().(*scheduling.CompositePodGroup)
	if !ok {
		return errors.NewBadRequest("resource was marked with kind CompositePodGroup but was unable to be converted")
	}

	priorityClassName, priority, preemptionPolicy, err := p.establishPriority(attributes, &cpg.Spec.PriorityClassName)
	if err != nil {
		return err
	}
	// Reject if the composite pod group already contained a priority that differs from the one computed from the priority class.
	if cpg.Spec.Priority != nil && *cpg.Spec.Priority != priority {
		return admission.NewForbidden(attributes, fmt.Errorf("priority set in the composite pod group (%d) must match the priority computed (%d) based on the priority class set in the spec", *cpg.Spec.Priority, priority))
	}
	cpg.Spec.Priority = &priority
	cpg.Spec.PriorityClassName = priorityClassName

	var schedulingPreemptionPolicy scheduling.PreemptionPolicy
	if utilfeature.DefaultFeatureGate.Enabled(features.PodGroupPreemptionPolicy) && preemptionPolicy != nil {
		switch *preemptionPolicy {
		case apiv1.PreemptLowerPriority:
			schedulingPreemptionPolicy = scheduling.PreemptLowerPriority
		case apiv1.PreemptNever:
			schedulingPreemptionPolicy = scheduling.PreemptNever
		default:
			return admission.NewForbidden(attributes, fmt.Errorf("preemptionPolicy set in the PriorityClass object (%v) must match one of the allowed values of PreemptionPolicy type in composite pod group", *preemptionPolicy))
		}
		if cpg.Spec.PreemptionPolicy != nil && *cpg.Spec.PreemptionPolicy != schedulingPreemptionPolicy {
			return admission.NewForbidden(attributes, fmt.Errorf("the string value of PreemptionPolicy (%s) must not be provided in composite pod group spec; priority admission controller computed %s from the given PriorityClass name", *cpg.Spec.PreemptionPolicy, schedulingPreemptionPolicy))
		}
		cpg.Spec.PreemptionPolicy = &schedulingPreemptionPolicy
	}
	return nil
}
