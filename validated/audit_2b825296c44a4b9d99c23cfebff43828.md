### Title
Permanent freezing of escrowed intent funds if the beneficiary address is blacklisted by the escrowed ERC20 token - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` (and its Tron/legacy equivalent `IntentGatewayV2.withdraw`) transfers escrowed input tokens directly to a `beneficiary` address that was fixed at order-fill/cancel time, with no mechanism to redirect funds to an alternate address if that token contract (e.g. USDC/USDT-style blacklistable ERC20) refuses the transfer.

### Finding Description
When a solver fills a cross-chain order, `ExtrinsicIntents._fillCrossChain` hardcodes the beneficiary of the source-chain escrow release to `msg.sender` (the solver) and dispatches a `RedeemEscrow` message: [1](#0-0) . This message arrives on the source chain and is routed through `EvmHost.dispatchIncoming`, which calls the gateway's `onAccept` and, on any revert, simply deletes the request receipt "so that it can be retried" rather than reverting or permanently failing the whole batch: [2](#0-1) .

`onAccept` decodes the `WithdrawalRequest` and calls `_withdraw`, which unconditionally does `IERC20(token).safeTransfer(beneficiary, amount)` to the beneficiary baked into the message body — there is no parameter or later call that lets the solver (or the user, for `RefundEscrow`) supply an alternate receiving address: [3](#0-2) . The same pattern exists in the Tron/legacy `IntentGatewayV2.withdraw`: [4](#0-3) .

If the escrowed input token (a common ERC20 like USDC/USDT with blacklist functionality) blacklists the solver's address (for the `RedeemEscrow` case) or the original user's address (for the `RefundEscrow`/cancel case) at any point between order placement and message delivery, `safeTransfer` reverts every time `onAccept` is invoked. Because the host's retry mechanism only ever resubmits the exact same message with the exact same immutable beneficiary, the delivery will fail indefinitely — there is no code path to update the beneficiary or sweep the stuck escrow to a different address.

### Impact Explanation
The escrowed input tokens become permanently locked in the `IntentGatewayV2`/`ExtrinsicIntents` contract: the solver who already delivered the output tokens to the user can never redeem the input tokens they are owed, and a cancelling user can never recover their refund, if their address is blacklisted by the specific ERC20 in question. This is a permanent freezing of funds reachable by any relayer delivering a legitimately signed/dispatched cross-chain fill or cancel message — no privileged action is required to trigger it, only an external token issuer's blacklist action against a participant's address.

### Likelihood Explanation
Requires the input/escrowed asset to be a blacklistable token (USDC, USDT, and similar centrally-administered stablecoins are extremely common as intent input assets) and the filler or user's address to become blacklisted, which is a realistic occurrence for addresses interacting with many protocols/counterparties. Given intents commonly settle in stablecoins, this is a plausible, non-contrived scenario.

### Recommendation
Allow the beneficiary of `_withdraw`/`withdraw` to be redirected — e.g., let the solver supply/override a receiving address when constructing the `RedeemEscrow` request (or allow a later "rescue" call keyed by the original beneficiary to redirect to a new address), and similarly let the order owner specify an alternate refund address for `RefundEscrow`. Alternatively, on transfer failure, escrow the funds under a per-user pull-based claim mapping (rather than push via `safeTransfer`) so a blacklisted address can later claim to a different address it controls.

### Proof of Concept
1. Solver fills a cross-chain order on the destination chain via `_fillCrossChain`, embedding `beneficiary = msg.sender` (solver's address) in the `RedeemEscrow` body dispatched to the source chain [5](#0-4) .
2. Before the message is delivered, the input token's issuer blacklists the solver's address.
3. The relayer delivers the `RedeemEscrow` message; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw`, which calls `IERC20(token).safeTransfer(beneficiary, amount)` and reverts because the token blocks transfers to a blacklisted address [6](#0-5) .
4. `EvmHost.dispatchIncoming` deletes the receipt to allow a retry [7](#0-6) , but every subsequent retry hits the same revert since the beneficiary is immutable in the message body — the escrowed tokens are permanently stuck.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
