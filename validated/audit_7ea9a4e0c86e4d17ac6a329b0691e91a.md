### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, `api_version`, and `webhook_id` from raw HTTP headers, but the HMAC signature that `Registry.process` validates is computed only over the raw request body. None of these header-derived fields are bound into the signed payload, so the identity used to route/attribute the webhook is not authenticated by the HMAC check that gates processing.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., only the raw body) and compares it against the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are handed to the host application's handler via `WebhookMetadata`, unauthenticated: [5](#0-4) 

This breaks the intended identity binding: `HMAC-verified bytes (raw_body) != bytes the application attributes to a shop (headers)`. Concretely, the equality that should hold is:

`hmac(secret, signed_bytes) == received_hmac` AND `signed_bytes ⊇ {shop, topic}` — but in this implementation `signed_bytes = raw_body` only, while `shop`/`topic` are taken from headers outside `signed_bytes`.

Because HMAC-SHA256 with a fixed key produces the same digest for the same body regardless of headers, any legitimate webhook delivery for a given topic/body (e.g. a `shop/redact` or other webhook with an empty or highly predictable body such as `{}`) that an attacker can observe (their own installed app's own shop, a shared test webhook, or any webhook whose body an attacker can view) yields a valid `(body, hmac)` pair that remains valid when replayed with an arbitrary, attacker-chosen `x-shopify-shop-domain` header. The library will accept it as authentic and hand the forged shop value to the application's webhook handler, which typically uses `shop` to look up per-tenant offline sessions/access tokens or to write per-tenant data — this is a cross-tenant confusion at the point of trust hand-off from this gem to the host app.

### Impact Explanation
Passing an attacker-controlled `shop` value through a validated (`HmacValidator.validate` returns `true`) webhook request enables cross-tenant impact in any host application that trusts `WebhookMetadata#shop` for tenant attribution after a successful HMAC check — e.g., writing data under, or fetching the access token for, a shop the attacker does not control. This matches the "Critical — cross-tenant access" category since the shop-identity binding that the HMAC is supposed to guarantee is not actually enforced by this gem.

### Likelihood Explanation
Exploitability requires the attacker to know a `(raw_body, valid_hmac)` pair for the target `App`'s webhook secret. This is realistic for topics with static/empty bodies (`{}` for `orders/create` test pings, mandatory compliance webhooks, or any webhook body an attacker can capture from their own shop's install of the same app) since HMAC-SHA256 is deterministic for the same secret+body. No secret, token, or privileged access is required — only observation of one legitimate webhook delivery to any shop (including the attacker's own) using the same app.

### Recommendation
Bind the identity fields into the signed payload verification, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC. At minimum, `VerifiableQuery#to_signable_string` for webhook requests should incorporate the `shop`, `topic`, and `webhook_id` headers (concatenated with the body) before HMAC validation, so that tampering with these headers invalidates the signature. Alternatively, document explicitly and enforce in `Registry.process` that `request.shop` must independently be checked by the host application against a known/allow-listed shop before being trusted for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery with body `{}` and headers:
   ```
   x-shopify-topic: shop/redact
   x-shopify-hmac-sha256: <valid_hmac_for_body_{}>
   x-shopify-shop-domain: attacker.myshopify.com
   ```
2. Attacker replays the same body `{}` and same `x-shopify-hmac-sha256` value to the target app's webhook endpoint, but changes:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Request#to_signable_string` returns `"{}"` (raw body, unchanged), so `Utils::HmacValidator.validate` succeeds — see: [1](#0-0) 
4. `Registry.process` proceeds and invokes the host handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim.myshopify.com", ...)`: [5](#0-4) 
5. Any host application logic that uses `data.shop` to look up or act on the victim's tenant data now executes under attacker control, despite the HMAC check having "passed."
