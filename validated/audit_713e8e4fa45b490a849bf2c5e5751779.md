### Title
Live, unbounded `exchangeRate()` read lets a single actor force premature, irreversible graduation - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.canGraduate` decides the irreversible `Curve → Graduating` transition using a single live external price read, `IBounceLeveragedToken(info.ltAddress).exchangeRate()`, with no deviation bound, TWAP, or cross-check against a second source. This is the same bug class as the f(x) report: a critical, value-gated state transition is driven by one manipulable spot price instead of a protected anchor. Inflating `exchangeRate()` for a single call lets an attacker collapse the real-LT-raised requirement and force the curve to graduate far short of the intended `graduationThresholdUsd` (documented as ~$9k), permanently freezing further curve trading for that token.

### Finding Description
`canGraduate` computes the USD leg purely from a live call: [1](#0-0) 

`previewLtUntilGraduation`, which `Zap._executeBuy` uses to size the closing buy that crosses the threshold, derives the LT amount still needed as `graduationThresholdUsd * 1e18 / exchangeRate` (ceil): [2](#0-1) 

Both reads happen in the same transaction as the triggering buy, with zero deviation checking against any second price source (unlike f(x)'s Chainlink-anchored `minPrice`/`maxPrice` band). The Bonding code's own natspec acknowledges `exchangeRate()` can be pushed via a "donation attack on the LT's `baseAssetBalance`" and dismisses it only for the *launch-time* snapshot as "cost-negative" because the only victim there is the creator's own floored seed buy: [3](#0-2) 

That reasoning does not carry over to `canGraduate`/`previewLtUntilGraduation`: here the manipulated `exchangeRate()` doesn't just misprice the caller's own trade — it decides whether the *entire curve* graduates, an action that is explicitly one-directional and non-reversible per the documented lifecycle: [4](#0-3) 

An attacker who can transiently raise `exchangeRate()` (e.g., by donating/depositing base asset directly into the LT, a normal permissionless LT interaction, not a bug in the LT itself) in the same transaction as a modest `Zap.buy` call causes:
1. `previewLtUntilGraduation` to report an artificially small `ltUntilThreshold`, so `Zap._executeBuy`'s floor-bump branch sizes `baseToConvert` to just clear that shrunken cap.
2. The resulting `Bonding.buy` → `_executeBuy` → `canGraduate` check to fire true with real LT raised far below the intended `graduationThresholdUsd` (real USD value pinned to `VIRTUAL_LIQUIDITY_USD`/`3x` design, i.e. ~$9k): [5](#0-4) 
3. `_enterGraduating` immediately freezes `buy`/`sell` on the curve permanently (`Lifecycle.Graduating`/`Graduated` never reverts to `Curve`): [6](#0-5) 

While `_prepareGraduationLiquidity`/LP seeding itself is documented as donation- and exchange-rate-drift-resistant (it reads only stored curve reserves, not `exchangeRate()`), the *decision to graduate at all* is not protected the same way — it is gated by one unbounded live oracle read.

### Impact Explanation
Once `canGraduate` is tripped, `Bonding.buy`/`sell` permanently revert with `TokenIsGraduating` for all other traders on that curve, and the token is forced through graduation/LP-seeding at a real-LT-raised size the design (and creator/traders) did not intend and cannot reverse. This:
- Permanently freezes remaining curve capacity and future trading/fee revenue that traders and the creator would have obtained had the curve organically reached the $9k threshold (`Bonding.CURVE_BPS`/`graduationThresholdUsd` invariant broken).
- Forces an early, attacker-timed irreversible lifecycle transition (`Curve → Graduating → Graduated`) with no recourse — this is exactly the kind of permanent, value-relevant state change the report's "1% deviation bypass leads to early liquidation" class describes, mapped onto alt.fun's dual-trigger graduation instead of f(x)'s liquidation threshold.

### Likelihood Explanation
The attacker only needs: (a) ability to move `exchangeRate()` transiently via a normal, permissionless LT interaction (deposit/mint into the LT with their own capital) and (b) a single `Zap.buy` call sized against the now-shrunken `previewLtUntilGraduation` cap, all composable in one transaction by any unprivileged wallet. No privileged role, upgrade, or off-chain component is required — only `Zap.buy`, reachable by any trader.

### Recommendation
Do not gate the irreversible `canGraduate` USD trigger on a single unbounded live `exchangeRate()` read. Either (a) bound `exchangeRate()` deviation per call against a TWAP/previous checkpoint before accepting it for the USD leg, or (b) require the USD trigger to be confirmed across two consecutive blocks/reads before flipping lifecycle, mirroring the anchor-price cross-check f(x) uses instead of trusting one live spot source for a permanent state transition.

### Proof of Concept
1. Attacker deposits/mints into the target token's paired BounceTech LT with their own capital in a way that transiently raises `exchangeRate()` (a normal, permissionless LT action).
2. In the same transaction, attacker calls `Zap.buy(tokenAddress, usdcAmount, 0, address(0))` with `usdcAmount` sized so that, under the *inflated* `exchangeRate()`, `Bonding.previewLtUntilGraduation` returns a small `ltUntilThreshold`.
3. `Zap._executeBuy`'s floor-bump branch mints/consumes just enough LT to satisfy that shrunken cap; `Router.buy` → `Bonding._executeBuy` → `canGraduate(tokenAddress)` reads the still-inflated `exchangeRate()` via `IBounceLeveragedToken.exchangeRate()` and returns `true` even though real LT raised is far below the intended threshold.
4. `_enterGraduating` fires, permanently setting `Lifecycle.Graduating`; all further `Bonding.buy`/`sell` calls on the curve revert with `TokenIsGraduating` for every other trader, and the token is pushed into `finalizeGraduation` at the attacker-forced size.
