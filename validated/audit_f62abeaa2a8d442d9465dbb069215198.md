### Title
Webhook `topic`/`shop-domain` headers are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` (used by `Registry.process`) authenticates the request solely on `HMAC(secret, raw_body)`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from unauthenticated HTTP headers and forwarded into the app's `WebhookHandler#handle` as trusted identity fields, without ever being bound into the HMAC.

### Finding Description
The equality the code effectively relies on is:
`HMAC(client_secret, raw_body) == received_hmac` ⟹ "this whole (topic, shop, body) triple came from Shopify for this shop."

But the real binding that should hold is:
`HMAC(client_secret, raw_body ‖ topic ‖ shop ‖ webhook_id) == received_hmac`

Because `to_signable_string` only returns `@raw_body` [1](#0-0) , the `shop`, `topic`, and `webhook_id` accessors are populated purely from headers with no cryptographic tie to the body's signature [2](#0-1) .

`Registry.process` validates only via `Utils::HmacValidator.validate(request)` and then immediately trusts `request.topic` and `request.shop` to build `WebhookMetadata` and dispatch to the app-supplied handler [3](#0-2) . `HmacValidator.validate_signature` computes the digest exclusively over `verifiable_query.to_signable_string`, i.e. the body [4](#0-3) .

This is exactly the bug-class pattern from the report: a field that is acted upon (here, `shop`/`topic`, used to route/attribute the webhook to a tenant) is not covered by the integrity check (the HMAC), even though the check is presented as validating "the whole request."

### Impact Explanation
Any party that has legitimately received one real webhook from Shopify for their own shop (i.e., any merchant/developer who has installed the app on a shop they control — an "unprivileged" actor with respect to other tenants) possesses a valid `(raw_body, hmac)` pair. Because `shop-domain`/`topic`/`webhook-id` are not part of the signed content, that same `raw_body`+`hmac` can be replayed to the app's public webhook endpoint with a different `shop-domain` header (a victim shop) and/or a different `topic` header, and `HmacValidator.validate` will still return `true`. The app's `WebhookHandler#handle` will then execute business logic attributing the event to the victim shop (`data.shop`), e.g. triggering `app/uninstalled`-style session revocation, data mutation, or job enqueueing keyed to a shop the attacker does not control — a cross-tenant identity-binding bypass, achieved with no access token, no `client_secret`, and no privileged account, satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation requires an attacker to already have obtained one valid `(raw_body, hmac)` pair for *some* shop (trivially achievable by installing the app on their own free/dev store and receiving any webhook), and the app's webhook endpoint must be reachable over the internet with no additional shop-binding check — which is exactly how this gem's documented usage pattern works (`Registry.process` is presented as sufficient authentication, see `docs/usage/webhooks.md` "This will verify the request did indeed come from Shopify"). No credentials, TLS interception, or social engineering are needed; the header values are attacker-controlled at the transport layer once the (body, hmac) pair is known.

### Recommendation
Bind the identity fields into the HMAC verification instead of trusting bare headers. Since Shopify's HMAC only signs the raw body, the app-facing API should not expose `shop`/`topic`/`webhook_id` as "verified" fields under the same trust umbra as `hmac`; at minimum:
- Document/enforce that `shop` returned by `Request` must be cross-checked by the caller against a known/installed shop before being trusted as a tenant identifier, or
- Have `Registry.process` additionally verify that the `shop` header corresponds to a shop with an active app installation/session before invoking the handler, closing the gap between "HMAC valid" and "shop authentic."

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `app/uninstalled`, capturing `raw_body="{}"` and header `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`.
2. Attacker POSTs to the app's public webhook endpoint with the same `raw_body` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, raw_body)` [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` [3](#0-2) , causing the app to act on `victim-shop.myshopify.com` (e.g., delete its stored session/access token) despite the attacker never having authenticated as that tenant.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
