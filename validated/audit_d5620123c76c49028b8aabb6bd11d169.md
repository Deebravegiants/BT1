Confirmed: `HttpClient#initialize` builds `@base_uri` directly from `session.shop` (`"https://#{api_host || session.shop}"`) with no domain validation applied anywhere in the OAuth callback path. `ShopifyAPI::Auth::Oauth.validate_auth_callback` never calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on `auth_query.shop` — it only checks the HMAC over the query string and then uses `auth_query.shop` verbatim to build `null_session` and POST the token-exchange request carrying `client_secret`.

### Title
OAuth callback trusts unvalidated `shop` domain for the access-token POST host, enabling SSRF that leaks the app's `client_secret` - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` verifies only that the HMAC over the callback query (`code`, `host`, `shop`, `state`, `timestamp`) matches, then uses the `shop` value directly to build the HTTP client that POSTs the app's `client_id`/`client_secret`/`code` to obtain an access token. The equality the code assumes is: `shop bytes covered by valid HMAC == shop is a genuine *.myshopify.com host safe to receive client_secret`. Those are not the same thing — HMAC validity only proves the query was signed with `api_secret_key`; it does not constrain `shop` to a trusted Shopify domain, since `ShopValidator.sanitize!`/`sanitize_shop_domain` (which exists in this exact library, see `lib/shopify_api/utils/shop_validator.rb`) is never invoked in this flow.

### Finding Description
`Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-22` and `AuthQuery#to_signable_string` in `lib/shopify_api/auth/oauth/auth_query.rb:33-43` only recompute an HMAC over the literal query fields and compare bytes; they never assert that the `shop` field is restricted to `TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`). `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-98`) then does: [1](#0-0) 
which constructs `Auth::Session.new(shop: auth_query.shop)` and passes it straight into `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`. `HttpClient#initialize` then derives the actual request host from that unvalidated shop: [2](#0-1) 
The POST body sent to that host includes `client_secret: Context.api_secret_key` (`lib/shopify_api/auth/oauth.rb:74-79`). Because the library never calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` (`lib/shopify_api/utils/shop_validator.rb:23-64`) anywhere in this path, the only gate on `shop` is whatever the calling app's callback controller does with the query parameter before constructing `AuthQuery`. The gem's own documented example in `docs/usage/oauth.md` builds `AuthQuery` directly from `request.parameters`, with no shop sanitization step shown, so a straightforward integration passes attacker-influenced request parameters straight through to `HttpClient`.

This breaks the intended identity binding: "host validated (by HMAC as authentic-from-Shopify) versus host that receives the `client_secret`" — the code assumes the HMAC-authenticity of the query implies the `shop` value is a safe destination host, but the gem provides no such guarantee, and ships a dedicated `ShopValidator` module specifically for this purpose that this flow does not use.

### Impact Explanation
If any host application does not perform its own equivalent of `ShopValidator.sanitize!` before constructing `AuthQuery` (which the gem's docs do not clearly mandate for this specific field, and which the gem itself never enforces internally), an attacker able to supply/influence the `shop` parameter and produce or replay a signable query can cause the gem to issue an authenticated POST containing the app's `client_id`, `client_secret`, and authorization `code` to an attacker-chosen host. This is SSRF that carries the app's credentials (`client_secret`) — explicitly listed as a High-impact category — and can lead to `client_secret` disclosure to a third party host.

### Likelihood Explanation
Exploitability depends entirely on whether the embedding application validates `shop` before calling `validate_auth_callback`; the gem itself performs no such check in this code path despite bundling `ShopValidator` for exactly this purpose, and its own documentation examples do not demonstrate sanitizing `shop` prior to constructing `AuthQuery`. This makes the library's API easy to misuse in a security-critical way, which is the concrete gap being flagged (an internal missing sanity check on a field that feeds a credential-bearing outbound request), analogous to the original report's missing bound-relationship check that silently breaks an invariant relied on elsewhere in the code.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, call `Utils::ShopValidator.sanitize!(auth_query.shop)` (or `sanitize_shop_domain`) before using `auth_query.shop` to construct `null_session`/`HttpClient`, raising `Errors::InvalidShopError` for any shop that is not a trusted Shopify domain, so the credential-bearing POST can never be routed to an attacker-controlled host regardless of what the host application does upstream.

### Proof of Concept
1. A host application builds `ShopifyAPI::Auth::Oauth::AuthQuery.new(**request.parameters.symbolize_keys...)` directly from callback query parameters, as shown in the gem's own `docs/usage/oauth.md` example, without separately validating `shop`.
2. An attacker crafts a callback request where `shop` is set to an attacker-controlled host (e.g., `attacker.example.com`) alongside a `code`/`state`/`timestamp`/`host` combination for which the attacker can obtain (or has captured) a valid HMAC signed by the real `api_secret_key` — e.g., via a legitimate but redirected/relayed OAuth handshake, or any scenario where the signed query can be replayed with a substituted `shop`.
3. `Utils::HmacValidator.validate` succeeds because it only checks byte equality of the HMAC over the exact query string supplied (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `validate_auth_callback` builds `Auth::Session.new(shop: "attacker.example.com")` and `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, whose `@base_uri` becomes `https://attacker.example.com` (`lib/shopify_api/clients/http_client.rb:16-19`).
5. The gem POSTs `{client_id, client_secret, code, expiring}` to `https://attacker.example.com/admin/oauth/access_token`, leaking the app's `client_secret` to the attacker's server.
