### Title
Webhook shop/topic identity not bound to HMAC signature — cross-tenant webhook confusion via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry#process` authenticates a webhook using `Utils::HmacValidator.validate(request)`, but `Webhooks::Request#to_signable_string` only signs the raw request body. The `shop`/`topic`/`webhook-id` identity fields, which are read from unauthenticated HTTP headers, are never included in the signed bytes. Any tenant of a multi-tenant app can therefore replay a genuinely-signed webhook body (received for their own store) with a forged `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header, and the gem will treat it as authentic for a different shop/topic.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the caller-supplied `hmac` using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is simply the raw body — none of the HTTP headers are part of the signed material: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` values that the registry uses to route and label the event are pulled straight from `shopify_header`, i.e., from headers that are never part of the HMAC input: [3](#0-2) [4](#0-3) 

`Registry#process` validates only the HMAC, then dispatches the handler using `request.shop` and `request.topic` taken from those unauthenticated headers: [5](#0-4) 

Because every shop that installs a given app shares the same `api_secret_key`, `HmacValidator.validate` proves only "this body was HMAC'd with *this app's* secret" — it does not prove which shop or which topic produced it. This breaks the equality the host application relies on: `shop-that-produced-the-signed-bytes == shop-passed-to-the-handler`. An attacker who controls one legitimate installation of the app (e.g., a free developer/test store) can capture a genuinely-signed webhook body+HMAC for their own store, then resend that exact body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop, or the `X-Shopify-Topic` header changed to a more sensitive topic that shares a compatible body shape. `HmacValidator.validate` still succeeds (the body and HMAC are untouched and genuinely valid), and `Registry#process` hands the forged `shop`/`topic` straight to the host application's handler as if it were authentic.

### Impact Explanation
This is a cross-tenant confusion in the gem's own webhook authentication contract: it authenticates *bytes signed by the app secret*, not the *shop or topic identity* those bytes are claimed to belong to. Host applications that use `request.shop` (as is documented/intended usage of this gem) as a tenant key to look up sessions/data will process attacker-controlled data under a victim shop's identity, or under a spoofed topic, purely by replaying an HMAC that was legitimately computed for a different shop/topic. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any developer can install almost any Shopify app on a free development store, which is enough to obtain genuinely-signed webhook payloads for topics the attacker cares about. No access token, `client_secret`, or privileged account is required — only the ability to trigger a webhook on the attacker's own installation and then replay it with edited headers.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically bind the headers to the signature — e.g., include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string`, or verify that the shop/topic reported in headers matches an out-of-band record (such as the shop associated with the currently active session) before dispatching to handlers in `Registry#process`.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com` and triggers a webhook subscribed by the app, capturing the full raw body plus the `X-Shopify-Hmac-Sha256` header sent to the app's webhook endpoint.
2. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`).
3. `Registry#process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) raw body and succeeds, since headers are not part of the signed string. [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` (attacker-chosen), even though the payload never actually originated from that shop, letting the attacker inject data or trigger logic under the victim tenant's identity. [7](#0-6)
