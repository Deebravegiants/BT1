### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) fields are not covered by the HMAC signature, allowing tenant confusion in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that signable string [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers [3](#0-2)  and are passed downstream into `WebhookMetadata` used by the app's handler after only the body's HMAC is checked [4](#0-3) . This is the exact bug class from the report: a field (`shop`) that is acted on (used to attribute the webhook to a tenant) but not covered by the identity-binding HMAC.

### Finding Description
`Registry.process` binds trust to the HMAC over the raw body only:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [5](#0-4) 

`request.shop` is `shopify_header("shop-domain")` and `request.topic` is `shopify_header("topic")` — both plain HTTP headers with no cryptographic binding to the signature [6](#0-5) . The HMAC is computed only over `@raw_body` [1](#0-0)  using the app-level `Context.api_secret_key`, which is the same secret shared across every shop that has the app installed [7](#0-6) .

The equality that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)` (i.e., the tenant identifier is bound into what is verified). Instead the gem only verifies `hmac == HMAC(secret, body)`, leaving `shop` (and `topic`) outside the verified scope. Before the request: `(body, hmac)` is a valid pair for some real shop A. After an attacker's request: the same `(body, hmac)` is replayed with the `shopify-shop-domain` header rewritten to shop B; `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` forwards `shop: "B"` to the handler as if Shopify had generated an event for shop B.

Because the same `api_secret_key` is valid for the HMAC of every installed shop, any tenant that can trigger a real, correctly-signed webhook for their own store (which any merchant installing the app can do, e.g. by performing an action that fires an `orders/create`-style webhook) obtains a `(body, hmac)` pair that remains valid under `HmacValidator.validate` regardless of which `shopify-shop-domain` header accompanies it. Sending that pair to the app's webhook endpoint with a different `shop-domain` header causes `Registry.process` to invoke the handler with `WebhookMetadata#shop` set to an arbitrary (attacker-chosen) shop domain while the HMAC check reports success.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select which tenant's data/session to mutate (the documented and expected usage pattern for this struct), an attacker-controlled `shop` value combined with a validly-signed body lets one tenant inject a fabricated event under another tenant's identity — a cross-tenant confusion/write primitive. This matches the "Critical - cross-tenant access" impact bucket, because the trust boundary the gem is supposed to enforce (which shop a signed webhook belongs to) can be forged by any user who can obtain one valid signed body from their own installation.

### Likelihood Explanation
Medium-to-High: no access token, `api_secret_key`, or privileged access is required — only the ability to install/use the app on one's own shop to obtain a single valid `(body, hmac)` pair, plus the ability to send an arbitrary HTTP request with a spoofed `shopify-shop-domain` header to the app's public webhook endpoint. The attack requires no interaction with Shopify's real infrastructure beyond capturing one legitimate signed payload.

### Recommendation
Bind the tenant/topic identity into the value that is HMAC-verified, not just the raw body. Concretely, `Request#to_signable_string` (or a new verification step in `Registry.process`) should incorporate `shop`, `topic`, and `webhook_id` into the signed representation, or the header values should be cross-checked against a canonical `Client-generated` value (e.g., recomputing HMAC per-shop secret if available, or requiring the caller to additionally verify `shop` out-of-band against the currently expected/installed shop before dispatching to the handler). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values so implementers do not treat them as verified.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`. Attacker triggers any webhook subscription event on their own shop and captures the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent to the app's webhook endpoint (`H` is valid because `HMAC(secret, B) == H`).
2. Attacker (or any actor who can reach the same public endpoint) resends the exact same request, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`, keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [8](#0-7) ; validation succeeds because it only recomputes `HMAC(secret, B)` and compares it to `H` [9](#0-8) .
4. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` with `shop == "victim.myshopify.com"` taken straight from the attacker-controlled header [10](#0-9) , and the host app's `handler.handle` processes the event as belonging to the victim shop.
