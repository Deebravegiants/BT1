### Title

Malicious swap route executes arbitrary token transfers under the caller’s authorization - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

Controller strategy entrypoints accept an opaque `swap: Bytes` route and forward it to the configured router after authorizing only the controller’s exact input-token transfer. The route is an executable instruction program whose address registry can name arbitrary pool contracts. A malicious pool invoked by the router can perform an unrelated token transfer from the caller to an attacker; Soroban records that transfer as a child authorization of the caller’s controller call. If the victim signs the simulated authorization tree, the malicious route executes the injected transfer while still satisfying the controller’s balance-delta and risk checks.

### Finding Description

`swap_collateral(caller, account_id, current, amount, new, swap)` accepts caller-supplied route bytes and forwards them through `withdraw_and_swap_from_supply`. [1](#0-0) [2](#0-1) 

`StrategySwap` is only an opaque `Bytes` alias, so the controller does not inspect or constrain the pool addresses encoded inside it. [3](#0-2) 

Before invoking the router, the controller authorizes one exact `transfer(controller, router, amount_in)` and calls `execute_strategy(controller, amount_in, swap)`. [4](#0-3) 

The router decodes `assets` and `ops` into a program, then constructs each swap hop from attacker-controlled registry entries, including `pool`. [5](#0-4) [6](#0-5) 

The program’s structural validator checks opcode, registry indices, token-chain linkage, and split weights, but does not bind a hop’s pool address to an allowlist. [7](#0-6) [8](#0-7) 

The Aquarius adapter then invokes the supplied pool address directly. [9](#0-8) 

The controller’s post-call checks measure only the controller’s input spend and output receipt; they do not prevent unrelated side effects performed under the original caller’s authorization tree. [10](#0-9) 

### Impact Explanation

An attacker can steal unrelated wallet tokens from a user who signs a malicious route. The malicious pool’s transfer is represented as a nested authorization under the victim’s `swap_collateral` invocation; once signed, the token transfer executes even though the requested collateral swap itself remains economically valid. The harness demonstrates Alice losing her entire unrelated wallet balance while still receiving the expected swapped collateral. [11](#0-10) 

This is theft of user funds, not merely poor route quality: the encoded route invokes attacker-controlled code that can move assets outside the declared swap input and output. The same route argument reaches the router through `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and the optional `convert_swap` path. [12](#0-11) [13](#0-12) [14](#0-13) 

### Likelihood Explanation

The attack requires the victim to sign the simulated authorization tree containing the malicious transfer, analogous to the Vim issue’s requirement that a user open a crafted file and invoke completion. A route supplier can make the displayed swap economically fair so a wallet or UI that does not inspect nested authorizations presents the operation as a normal strategy call. [15](#0-14) 

Without the malicious child authorization, the host rejects the rogue transfer and rolls back the call; with the poisoned simulated tree, the transfer succeeds and pays the attacker. [16](#0-15) [17](#0-16) 

### Recommendation

Constrain executable route data before crossing the controller/router boundary:

- Maintain an allowlist or registry of approved venue pool contracts and reject any `pool` address outside it.
- Prefer route manifests containing immutable venue identifiers resolved by the router, rather than arbitrary contract addresses supplied in `assets`.
- Require route decoding and authorization-tree inspection in wallets/SDKs, and refuse trees containing children other than the expected controller token transfer.
- Emit or return a route digest so the signed transaction can be bound to a previously reviewed route.
- Add regression coverage asserting that a malicious pool cannot add a nested `token.transfer(victim, attacker, amount)` beneath `swap_collateral` or other strategy entrypoints.

### Proof of Concept

1. Deploy a contract exposing a pool-compatible `swap` method whose implementation calls `token.transfer(victim, attacker, wallet_balance)`. [18](#0-17) 

2. Build a route whose `assets` registry contains the legitimate input token, legitimate output token, and the malicious contract as the hop pool; encode one swap instruction pointing `idx_a` at that pool. The router accepts the address because validation checks only that the index exists. [8](#0-7) [19](#0-18) 

3. Have the victim invoke `swap_collateral(alice, account_id, usdc_key, amount, eth_key, malicious_route)`. The controller authorizes only the expected controller-to-router input transfer, then calls the router. [20](#0-19) 

4. The malicious pool pays a fair output while also attempting `wallet_token.transfer(alice, attacker, wallet_balance)`. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization. [21](#0-20) 

5. When Alice signs the poisoned tree, the route completes, the attacker receives `wallet_balance`, and Alice’s wallet balance becomes zero. [17](#0-16)
