### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop-attribution forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` value it later hands to the app's webhook handler is read from an HTTP header that is not included in that signature. An attacker who has captured any single valid `(raw_body, hmac)` pair for a registered topic (e.g. from their own shop's webhook deliveries, which they legitimately receive at their own endpoint) can replay that exact body/HMAC pair against the same app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The signature check still passes because the header is never part of the signed material, so the app processes the payload as if it belonged to a different, attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

But the value actually bound by the HMAC (`to_signable_string`) is only the raw body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. the body, and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this same HMAC check as its only authentication step, then trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because `shop`, `topic`, `api_version`, and `webhook_id` are all taken from headers outside the signed payload, none of them are cryptographically bound to the HMAC — only the JSON body is. The identity binding that should hold is:
`shop used for tenant attribution == shop that produced the signed body`
but the gem only enforces `hmac(body) == received_hmac`, leaving `shop` free for an attacker to set to any value while keeping a previously-observed valid `(body, hmac)` pair.

### Impact Explanation
This is a cross-tenant confusion vector at Critical severity: any actor capable of triggering or observing one legitimate webhook delivery (for instance the operator of their own shop that installed the app) can forge subsequent deliveries attributed to a different shop domain, as long as the JSON body happens to match (many webhook bodies for a topic are structurally identical or can be made byte-identical, e.g. `{}`/empty bodies, or when `fields`/filters produce constant payloads). Downstream consumers (per the gem's own documented pattern in `docs/usage/webhooks.md`, and the `shopify_app` reference implementation) key their persistence and business logic off `data.shop`, so this allows writing/attributing another tenant's webhook-triggered state under an attacker-chosen shop, i.e., cross-tenant access without holding that tenant's `client_secret` or access token.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint plus knowledge of one valid `(raw_body, hmac)` pair for the topic being targeted — attainable by any developer who has installed the app on their own shop and captured Shopify's webhook deliveries to themselves. No secrets, tokens, or privileged access are required, and the check that is bypassed (header-vs-body binding) is entirely internal to this gem's `Webhooks::Request`/`Registry`/`HmacValidator` code path.

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them (e.g., require the app to independently verify `shop` against a session/store lookup keyed by a value derived from the signature) before trusting `request.shop` in `WebhookMetadata`.

### Proof of Concept
1. Register the app's webhook handler and let Shopify deliver a legitimate webhook to the attacker's own installed shop, capturing `raw_body` and the corresponding `X-Shopify-Hmac-Sha256` value (both valid, since Shopify signed them for the attacker's own tenant).
2. Replay a request to the app's webhook endpoint with the same `raw_body` and `hmac` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `hmac(raw_body)`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and invokes the app's handler, causing the app to process/store data as belonging to `victim-shop`.
