### Title
Unallowlisted route contracts can execute attacker-chosen token transfers under the user's strategy authorization - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
A malicious route can name an attacker-controlled contract as a Phoenix/Soroswap/Sushi/Comet/Aquarius pool. During a user-signed controller strategy, that contract can invoke `wallet_token.transfer(victim, attacker, amount)`, causing simulation to append the theft as an authorized sub-invocation beneath the victim's strategy signature. If the victim signs the simulated authorization tree, the rogue venue steals unrelated wallet funds while still returning enough swap output to satisfy the controller's balance checks.

### Finding Description
`swap_collateral` is reachable by the account owner or delegate and accepts caller-supplied route bytes before forwarding them to the configured router. [1](#0-0) [2](#0-1) 

The controller authorizes only its own exact `token_in.transfer(controller, router, amount_in)`, then measures input spend and positive output receipt. [3](#0-2) 

Those checks do not restrict which contract the route designates as a pool: each swap op constructs `SwapHop` directly from the payload's `assets` registry and dispatches it to the selected venue adapter. [4](#0-3) [5](#0-4) 

For example, the Phoenix adapter invokes `swap` on the route-selected `hop.pool`; the pool is arbitrary contract code. [6](#0-5) 

Soroban records a nested `victim_token.transfer(victim, attacker, amount)` as an additional authorized sub-invocation of the victim's strategy authorization. The repository's threat model confirms that an unallowlisted route can place third-party code below the caller's authorization and consume a signed child transfer outside the routed amount. [7](#0-6) 

### Impact Explanation
A victim can lose tokens unrelated to the lending account and unrelated to the declared swap input. The attacker only needs the malicious route to return enough `token_out`—which the attacker or rogue pool can pre-fund—to satisfy the router minimum and controller's positive-output check. [8](#0-7) [9](#0-8) 

This is theft of user funds: the signed authorization tree permits the rogue pool's `transfer(victim, attacker, amount)` even though the user intended to authorize only the strategy's declared input transfer. [10](#0-9) [7](#0-6) 

### Likelihood Explanation
The attack requires the victim to submit a malicious route and sign the authorization tree produced by simulation. That is realistic for a malicious frontend, quote provider, browser extension, or transaction builder because the poisoned child authorization is embedded in an otherwise profitable-looking swap. [11](#0-10) [12](#0-11) 

No privileged role, leaked key, oracle manipulation, or contract upgrade is required; the attacker needs only a deployed pool-compatible contract and a route payload supplied to the victim. [13](#0-12) [14](#0-13) 

### Recommendation
Enforce a governance-controlled pool/venue allowlist before dispatching every route hop, rather than trusting an arbitrary `assets[idx_a]` address. [14](#0-13) 

The allowlist should be keyed by `(venue, token_in, token_out, pool)` and checked in `dispatch_hop` or before `execute_op` invokes the venue. Until contract-side enforcement exists, wallets and clients must reject any authorization tree containing transfers other than the declared route input pull. [15](#0-14) [7](#0-6) 

### Proof of Concept
1. Victim owns a lending account with USDC collateral and also holds an unrelated wallet token.
2. Attacker deploys `RoguePool`, pre-funds it with ETH output, and implements the Phoenix-compatible `swap(router, token_in, amount_in, ...)`.
3. `RoguePool.swap` pulls the authorized router input, calls `wallet_token.transfer(victim, attacker, victim_balance)`, and transfers enough ETH back to the router.
4. Attacker supplies a `swap_collateral` payload whose instruction uses the Phoenix swap opcode and whose `assets` entry names `RoguePool` as the pool.
5. Victim submits `swap_collateral(victim, account_id, usdc_market, amount, eth_market, malicious_swap)`.
6. `sender.require_auth()` covers the router execution, while simulation adds the rogue wallet-token transfer as a child authorization.
7. If the victim signs that tree, the unrelated wallet token moves to the attacker; the router still measures positive ETH output and pays the controller, so the strategy completes and deposits the output. [16](#0-15) [17](#0-16) [18](#0-17)

```rust
        account_id,
        current,
        from_amount,
        new,
        swap,
    } = params;

    require_authorized_caller(env, caller);

    assert_with_error!(env, current != new, GenericError::AssetsAreTheSame);
    config::require_hub_active(env, current.hub_id);

        &env.current_contract_address(),

        &mut cache,
```

```rust
pub(crate) fn run(env: Env, sender: Address, total_in: i128, payload: StrategyPayload) -> i128 {
    sender.require_auth();

    if total_in <= 0 {
        panic_with_error!(&env, Error::InvalidAmount);
    }

    let StrategyPayload {
        amounts,
        assets,
        ops,
    } = payload;
    let program = Program::decode(&env, &ops, assets.len(), amounts.len());

    let input_token = assets.get_unchecked(program.token_in);
    let output_token = assets.get_unchecked(program.token_out);
    let total_min_out = amounts.get_unchecked(program.min_out);
    if total_min_out <= 0 {
        panic_with_error!(&env, Error::SlippageExceeded);
    }

    let router = env.current_contract_address();
    let mut vault = Vault::new(&env);
    let mut tokens_cache: Map<Address, Vec<Address>> = Map::new(&env);

    // Credit the measured delta, not declared `total_in`: a fee-on-transfer
    // input would otherwise draw the shortfall from the fee reserve.
    let credited_in = transfer_amount_measured(
        &env,
        &input_token,
        &sender,
        &router,
        total_in,
        GenericError::AmountMustBePositive,
    );
    vault.deposit(&input_token, credited_in);

    let referral_id = program.referral_id;
    let fee_on_input = if referral_id != 0 {
        let list = storage::load_whitelist(&env);
        let in_wl = list.contains(&input_token);
        let out_wl = list.contains(&output_token);

        !out_wl || in_wl
    } else {
        false
    };

    if fee_on_input {
        fees::apply_fees_on_token(&env, &mut vault, &input_token, referral_id);
    }

    let ctx = Ctx {
        env: &env,
        router: &router,
        assets: &assets,
        amounts: &amounts,
        program: &program,
    };
    let mut prev: PrevOutput = None;
    for i in 0..program.len() {
        prev = execute_op(
            &ctx,
            &mut vault,
            program.op(&env, i),
            prev,
            &mut tokens_cache,
        );
    }

    if !fee_on_input {
        fees::apply_fees_on_token(&env, &mut vault, &output_token, referral_id);
    }

    let total_out = vault.balance_of(&output_token);
    if total_out < total_min_out {
        panic_with_error!(&env, Error::SlippageExceeded);
    }

    vault.withdraw(&output_token, total_out);
    token::Client::new(&env, &output_token).transfer(&router, &sender, &total_out);

    residual::accrue_residual_as_revenue(&env, &mut vault);

    total_out
```

```rust
    hop: &SwapHop,

    tokens_cache: &mut Map<Address, Vec<Address>>,

    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
