### Title
Unrestricted swap-route contracts can append unauthorized wallet-draining token transfers to the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

Controller strategy entrypoints pass caller-supplied opaque swap routes to the configured router while enforcing only the controller’s own balance deltas and final position risk. Because route execution can place arbitrary pool code below the caller’s `require_auth`, that code can add an unrelated `token.transfer(caller, attacker, amount)` as a child authorization and steal any token if the caller signs the expanded transaction authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description

The routed controller strategies authenticate the account caller and then execute the supplied route through `swap_tokens` or `swap_tokens_or_passthrough`. For example, `swap_collateral` authenticates the caller, verifies account ownership, withdraws collateral, and forwards the opaque `swap` bytes to the router. [3](#0-2) 

Inside `swap_tokens`, the controller explicitly authorizes only one input transfer of `amount_in` from the controller to the configured router. It then invokes `router.execute_strategy` and validates only the controller’s input spend, output receipt, and leftover input. [4](#0-3) 

That validation does not constrain actions performed by contracts invoked inside the route against the original caller’s authorization. A rogue pool can call `transfer(victim, attacker, amount)` for a completely unrelated token; Soroban records the call as a child under the caller’s strategy authorization, and enforcing mode executes it when that child appears in the signed tree. [5](#0-4) [6](#0-5) 

The affected entrypoints include `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply` when an initial payment requires `convert_swap`, and the ordinary swap inside `multiply`. `swap_collateral(caller, account_id, current, amount, new, swap)` provides the most direct unprivileged route because it withdraws existing collateral and executes caller-provided `swap` bytes. [7](#0-6) [8](#0-7) 

### Impact Explanation

An attacker can steal arbitrary unrelated assets from the strategy caller’s wallet, not merely consume the collateral or debt submitted to the strategy. The malicious pool can request a transfer for any token contract and amount held by the caller, while still returning sufficient route output for the controller’s `NoSwapOutput`, overspend, and final account-risk checks to pass. [9](#0-8) 

The repository’s reproduction drains the victim’s entire `WALLET_BALANCE` of an unlisted token while the protocol receives a fair `ETH` output and successfully updates the supplied collateral. [10](#0-9) 

### Likelihood Explanation

Likelihood is moderate because exploitation requires the victim to execute an attacker-influenced route and sign the authorization tree containing the malicious child transfer. An honest authorization tree rejects the rogue transfer, so this is not a silent signature bypass. [11](#0-10) 

The practical risk remains material because simulation naturally records required nested calls beneath the caller’s strategy authorization, and users or integrating clients may treat that tree as internal swap machinery rather than independently auditing every child invocation. The controller provides no venue allowlist or protocol-side check that distinguishes a legitimate pool callback from an unrelated wallet transfer. [12](#0-11) 

### Recommendation

Restrict swap routes to governance-approved venue contracts rather than accepting arbitrary pool addresses. The allowlist should be enforced for every hop before invoking external route code, and changes to it should use the same delayed governance controls as other security-sensitive configuration.

At minimum, controller and router clients should fail transaction construction when simulation produces any caller-authorization child other than the expected token pull. Contract-side venue allowlisting is the stronger mitigation because client-side tree inspection depends on each wallet or integration implementing it correctly.

### Proof of Concept

The repository already contains an executable proof of concept in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Alice owns a funded lending account and additionally holds `77_770_000_000` units of an unrelated, unlisted token. [13](#0-12) 
2. The attacker deploys `RogueHopPool`, whose `swap` function calls `token.transfer(alice, attacker, WALLET_BALANCE)` on that unrelated token. [14](#0-13) 
3. Alice invokes `controller.swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, malicious_route)`, where `malicious_route` names the rogue pool as a route hop. [15](#0-14) 
4. Simulation records the rogue wallet transfer as a child of Alice’s `swap_collateral` authorization, while the route still produces the expected collateral output. [10](#0-9) 
5. With a root-only authorization tree, the host rejects the rogue transfer. With the simulation-produced poisoned tree, the same transaction succeeds, Alice’s unrelated-token balance becomes zero, and the attacker receives the full balance. [16](#0-15)

```rust
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
```

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
