### Title
Zero-`tokensForLP` graduations (full curve sellout) combined with a hostile HyperSwap pre-seed permanently revert `finalizeGraduation`, freezing curve-raised LT and the LP-reserve tokens on `Bonding` forever - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` computes `tokensForLP` from the parabola `tokensForLP(sold) = sold·(S−sold)/S` [1](#0-0)  pinned at end of Phase 1 in `_prepareGraduationLiquidity`/`_enterGraduating` [2](#0-1) . When the token graduates via the **supply trigger** (`IPair.tokenBalance() == 0`, i.e. `sold == S`, the entire 750M curve supply sold) [3](#0-2) , the parabola forces `tokensForLP → 0`. If, during the permissionless Phase-1→Phase-2 window, anyone pre-creates the HyperSwap pair and mints hostile LP into it (`Regime 3`, the documented "mint pre-seed" attack) [4](#0-3) , `_seedRebalancing`/`_seedDirectMint` end up depositing `tokensForLP = 0` TOKEN into a non-empty pool via a direct `pair.mint(lpLock)` call [5](#0-4) . UniswapV2's `mint` requires `liquidity > 0` and reverts otherwise, and even if it somehow returned `0`, `LPLock.recordLock` explicitly reverts on `amount == 0` via `ZeroAmount()` [6](#0-5) . Either way `finalizeGraduation` unconditionally reverts, and there is no owner override, no alternate finalize path, and `LPLock`'s locker allowlist is add-only with "no removal path" [7](#0-6) , so the token is stuck in `Lifecycle.Graduating` permanently.

### Finding Description
This is the same bug class as CVE-2021-47360: a cleanup/completion step that is supposed to run to guarantee resource release/finalization can be silently deferred/blocked, leaving state permanently "hung." Here, the analog is `Bonding`'s two-phase graduation: Phase 1 (`_enterGraduating`) unconditionally drains the curve and parks `pendingGraduation[token].ltFromPair` (all curve-raised LT) plus the 250M `LP_RESERVE` tokens on `Bonding`, freezing trading [2](#0-1) . Completion is entirely dependent on a later, permissionless `finalizeGraduation` call succeeding [8](#0-7) .

The protocol's own documentation states the seeding logic (`_seedUniswapV2Direct`) "MUST never revert under any pre-seed shape" and calls this "the load-bearing security property" [9](#0-8) . The `_swapBudget` 1%-reservation mechanism is specifically designed to guarantee the deposit leg (`_routerDepositAndDispose`) always has a non-zero amount on both sides so `addLiquidity`/`pair.mint` never mints zero LP [10](#0-9) . That guarantee, however, is derived from the **input side's balance being non-zero to begin with**; it does not protect against `tokensForLP` itself being (near) zero, which is exactly the boundary condition of the supply-trigger graduation (`sold == S ⇒ tokensForLP(sold) = 0` by the documented parabola formula). In that case `_seedRebalancing`'s branch selection (`reserveToken * ltFromPair > reserveLT * tokensForLP`) routes to a swap/direct-mint path that ultimately calls `pair.mint(lpLock)` with `amount0 = 0` TOKEN against a non-empty pool, which V2's `mint` formula (`liquidity = min(amount0·S/reserve0, amount1·S/reserve1)`) drives to `liquidity = 0`, and standard UniswapV2Pair `mint` hard-reverts (`INSUFFICIENT_LIQUIDITY_MINTED`) on that outcome. Even in a code path that somehow returned `0` up to `finalizeGraduation`, `LPLock.recordLock` independently hard-reverts on `amount == 0`.

Because Phase 2 is intentionally permissionless (so "anyone can rescue a stuck token") [11](#0-10) , any unrelated wallet can *induce* this state without any privilege: buy the curve down to exactly `tokenBalance() == 0` (or wait for it to happen naturally in a hot token), then front-run/precede `finalizeGraduation` by creating the HyperSwap V2 pair and minting a small self-funded TOKEN/LT seed into it (the standard, already-documented "mint pre-seed" attack surface) before finalize lands.

### Impact Explanation
This causes **permanent freezing of trader/creator funds**: once triggered, `pendingGraduation[token]` is never cleared, `Lifecycle` never advances past `Graduating`, trading stays frozen (buys/sells revert with `TokenIsGraduating`), and all curve-raised LT plus the 250M `LP_RESERVE` tokens are permanently trapped in `Bonding` with no recovery mechanism — `LPLock`'s locker allowlist is add-only and there is no admin bypass for `finalizeGraduation`. This satisfies the Validate criterion of "permanent freezing of trader, creator or LP funds."

### Likelihood Explanation
The precondition (`sold == S`, i.e. the curve fully sells out via the supply trigger) is a normal, expected graduation path explicitly documented as one of the two graduation triggers ("handles flat/bear markets where $9K is never reached") [12](#0-11) , so it is not a contrived edge case — it will occur for popular/low-price tokens. Combining it with a hostile pre-seed only requires a single unprivileged wallet to call `factory.createPair` + `transfer` + `pair.mint(attacker)` during the Phase-1→Phase-2 window, which is exactly the attack surface the protocol's own "HyperSwap Pre-Seed Defense" section is built to defend against — meaning an attacker doesn't need any new capability, just to combine an already-anticipated attack with an already-anticipated (but apparently unguarded) boundary value of `tokensForLP`.

### Recommendation
- In `_prepareGraduationLiquidity`/`_enterGraduating`, special-case `tokensForLP == 0` (or below some dust floor) by skipping the LP mint/deposit entirely and burning/sweeping the corresponding side directly to the owner, rather than attempting a `pair.mint`/`addLiquidity` that is mathematically guaranteed to yield zero liquidity.
- Alternatively, allow `LPLock.recordLock` (or a dedicated `Bonding` path) to accept a zero-liquidity "no-op" graduation record so `finalizeGraduation` can still flip `Lifecycle` to `Graduated` and clear `pendingGraduation` even when no LP is minted, instead of reverting.
- Add a regression test that drives a token to the exact `tokenBalance() == 0` supply-trigger boundary, pre-seeds the HyperSwap pair via `Regime 3`, and asserts `finalizeGraduation` still succeeds (extending `test_brick_resistance_frontRun_dust_seed` to cover this specific `tokensForLP → 0` boundary, which the current suite does not appear to cover).

### Proof of Concept
1. Launch a token via `Zap.createToken` and buy through `Zap.buy`/`Bonding.buy` until `IPair(pair).tokenBalance() == 0` (full curve sellout), triggering Phase 1 (`_enterGraduating`) with `tokensForLP == 0` (parabola boundary at `sold == S`) — reachable purely with unprivileged buys.
2. Before anyone calls `finalizeGraduation`, an unrelated wallet calls the HyperSwap V2 factory's permissionless `createPair(token, lt)`, transfers a small amount of `token` and `lt` to the pair, and calls `pair.mint(attackerAddress)` — the standard "hostile mint pre-seed" already acknowledged in `packages/contracts/AGENTS.md`.
3. Anyone (or the keeper) calls `Bonding.finalizeGraduation(token)`. Because `tokensForLP == 0` and the pool has non-zero, attacker-controlled reserves, the seeding path attempts a `pair.mint(lpLock)`/`addLiquidity` call whose computed LP output is `0`, causing either the underlying V2 `mint` to revert with `INSUFFICIENT_LIQUIDITY_MINTED` or, if reached, `LPLock.recordLock` to revert with `ZeroAmount()`.
4. `finalizeGraduation` now reverts on every future call for this token — `Lifecycle` stays `Graduating` forever, trading stays frozen, and the LT raised by the curve plus the 250M `LP_RESERVE` tokens are permanently stuck in `Bonding`.

Note: I was not able to inspect the exact body of `_noFeeSwapInput` and the tail of `_prepareGraduationLiquidity`/`_enterGraduating` (lines beyond what was retrieved) within the available tool budget, so the precise arithmetic path by which `tokensForLP` reaches exactly `0` (versus a small non-zero dust value that the existing `DIRECT_MINT_PRESEED_BPS` guard already handles) is inferred from the documented parabola formula and branch conditions rather than directly confirmed against every line of `_noFeeSwapInput`. Confirming this boundary precisely (and whether the existing `DIRECT_MINT_PRESEED_BPS`/dust-fallback logic already absorbs it) would benefit from a Devin session with direct repository access to run `test/TwoPhaseGraduation.t.sol` and `test/NoFeeSwapInput.t.sol` against a crafted `tokensForLP == 0` scenario.

```markdown
#### Regime 3 — mint pre-seed (the actual exploit)

Attacker called `pair.mint(attacker)` against a self-funded dust seed. Reserves are non-zero at a hostile ratio. We:

1. **Compute the swap input** that would drive the pool ratio back to the curve-close ratio under the no-fee constant-product model: `s = sqrt(reserveIn · reserveOut · targetN / targetD) − reserveIn`, capped at our per-side budget. Implementation in `_noFeeSwapInput`. Closed-form via OZ `Math.sqrt + Math.mulDiv`; no binary search, no convergence loop.
2. **Execute the swap directly on the pair** via `pair.swap(amount0Out, amount1Out, address(this), "")`. We read the output from the pair's own fee-aware `getAmountOut` quote and pass it as the output. **Bypasses the router** — HyperSwap's V2 router has no canonical `swapExactTokensForTokens` (see "HyperSwap Router non-standard ABI" above). Same direct-to-pair pattern Zap uses for post-grad user swaps. Implementation in `_pairRebalance`.
3. **Deposit the remaining inventory** via `router.addLiquidity(rest, 1, 1, lpLock, ...)`. The router's `quote()`-based optimal split deposits only the matched-ratio subset; neither side becomes a `min()` donation. Off-ratio remainder stays in `Bonding`. The router's `addLiquidity` IS canonical V2 on HyperSwap (verified selector `0xe8e33700`), so this leg is safe to keep on the router and gets the `quote()` math for free.
4. **Dispose the off-ratio remainder.** TOKEN side burned (`Bonding` is the Token owner). LT side auto-swept to the protocol owner by `finalizeGraduation`'s post-sweep — emits `LTRescued(lt, owner, amount)` for observability. See "Per-graduation LT isolation" below.
```

```text
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
```

```text
    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
```

```text
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
```
