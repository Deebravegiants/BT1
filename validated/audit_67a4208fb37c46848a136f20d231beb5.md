Webhook shop-domain header is not covered by HMAC verification, allowing tenant (shop) spoofing via HMAC-valid webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)`, which computes and compares the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body [1](#0-0) . The `shop` value handed to the app's handler, however, is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) , which is never part of the signed content. The equality the gem is supposed to enforce — "the shop the HMAC authenticates" == "the shop the handler acts on" — does not hold, because the header is outside the HMAC's scope.

### Finding Description
`Registry.process` performs exactly one identity check before dispatching to the app-provided handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [3](#0-2) 

`HmacValidator.validate` recomputes the HMAC using `verifiable_query.to_signable_string` and `Context.api_secret_key`, then does a constant-time compare against `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , and the constructor stores headers and body independently, only checking presence, not binding them cryptographically [5](#0-4) .

This means:
- Bytes verified (the HMAC covers) = raw body only.
- Bytes acted on for tenant identity (`request.shop`, propagated into `WebhookMetadata.shop` and passed to the app handler) = the `shop-domain` header, which carries zero cryptographic binding.

Any unprivileged internet user who possesses one valid `(body, hmac)` pair — trivially obtainable by installing the target app on their own shop and triggering any subscribed webhook topic (e.g. `orders/create`) — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim's `myshopify.com` domain). `HmacValidator.validate` will still pass, because it never inspects the header. `Registry.process` will then invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, while `body`/`topic`/`webhook_id` remain the attacker's own legitimate data [6](#0-5) .

The gem's own documentation and reference handler pattern show this is the exact contract apps rely on: the handler is told to trust `data.shop` as the tenant scope for further processing (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) . Apps built per this documented pattern will store/attribute the replayed webhook body to the spoofed shop.

### Impact Explanation
This breaks the shop/tenant identity binding without needing the app's `client_secret`, an access token, or any privileged account — only knowledge of one's own valid webhook (obtainable by installing the app, a normal unprivileged action). The result is that an app processing this "authenticated" webhook can be made to attribute attacker-controlled data to a different, victim shop, corrupting per-tenant state or triggering tenant-scoped side effects (e.g. inventory/order updates, notifications, billing events) for a shop the attacker does not control. This is a cross-tenant integrity/data-attribution issue rooted in the gem's HMAC scope not covering the field ("shop") that the gem itself exposes and recommends apps use as the trust boundary.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must be able to (a) install the target Shopify app on a shop they control (unprivileged, self-service in most app models) to obtain one legitimate `(body, hmac)` pair for a chosen topic, and (b) reach the app's public webhook endpoint directly with a forged `shop-domain` header (no TLS interception or secret needed — HTTP header spoofing to an app's own exposed HTTP route). Both conditions are attacker-controlled and require no leaked credentials.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the verified body (e.g. include it in `to_signable_string`, or cross-check it against a shop value embedded in the payload/registered subscription). At minimum, document prominently that `data.shop` is *not* authenticated by the HMAC check and must not be trusted as a tenant boundary without additional verification (e.g., confirming the shop has an active, registered webhook subscription/session on record).

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, obtaining a legitimate webhook delivery for topic `orders/create`: body `B`, header `x-shopify-hmac-sha256: H` (valid for secret `S`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's public webhook route with the *same* raw body `B` and header `x-shopify-hmac-sha256: H`, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `to_signable_string` returns `B`, unaffected by the header change.
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC(`B`, `S`) == `H` → passes, since `S` never changed and `B` is untouched.
5. Handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — the app now processes attacker data under the victim's tenant identity.
