### Title
Permanent market freeze via `i128` overflow in interest accrual before the borrow-index cap engages - (File: common/src/rates/scaling.rs)

### Summary
`scaled_to_original` converts scaled shares back to value with `scaled.mul(index)`, which panics on `i128` overflow (surfaces as `GenericError::MathOverflow`). The borrow index is capped at `MAX_BORROW_INDEX_RAY` only on the index itself in `update_borrow_index`; nothing bounds the product `borrowed_scaled * borrow_index`. On a sufficiently large market at sustained high utilization, the index grows enough that `borrowed.mul(new_borrow_index)` inside `calculate_supplier_rewards` overflows while `new_borrow_index < MAX_BORROW_INDEX_RAY`, so the cap can never rescue it. Because every pool verb accrues first, the market is permanently frozen: no repay, withdraw, liquidation, or `clean_bad_debt` can execute. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
Accrual computes `old_total_debt = borrowed.mul(env, old_borrow_index)` and `new_total_debt = borrowed.mul(env, new_borrow_index)` in `calculate_supplier_rewards` (common/src/rates/index.rs:80-83). `Ray::mul` is a checked fixed-point multiply that traps on overflow. `update_borrow_index` clamps the new index to `MAX_BORROW_INDEX_RAY` (1e9 RAY, common/src/constants/pool.rs:19), but the clamp is applied to the index, not to the value product. For a market whose scaled debt shares are large — e.g., a high-decimals asset with ~1e9 whole units supplied — `borrowed_scaled * index` exceeds `i128::MAX` (~1.7e38) long before the index reaches its 1e9-RAY cap. Once that happens, `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `recapitalize` on that market all re-run the same accrual and revert identically, so the overflow is unrecoverable: no reachable path can shrink `borrowed` first, since even `repay` accrues before burning shares. The repository's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates exactly this: after the overflow, both `try_withdraw` and `try_repay` fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`. [5](#0-4) 

### Impact Explanation
All supplied collateral and all repaid-routable funds in that market are permanently frozen — suppliers cannot withdraw, borrowers cannot repay, liquidations cannot execute, and bad debt cannot be cleaned. This is the "permanent freezing of funds" / "contract unable to operate" class, matching the availability-only DoS shape of CVE-2021-2038 (complete crash of the service).

### Likelihood Explanation
All required entrypoints are permissionless: any unprivileged address can `supply`, `borrow`, and call `update_indexes`. The trigger needs (a) a listed market combining large supply volume and high decimals so scaled shares are large, and (b) sustained high utilization under a steep rate curve for an extended period, or a listing whose configured rate/scale makes the index grow faster. The capital requirement is substantial but borrowed liquidity can be recursive; once market parameters admit a large enough book, the cliff is a deterministic arithmetic outcome, not a race. Medium likelihood: real capital and time are needed, but no privileged access or oracle dishonesty is required, and once crossed the freeze is irreversible.

### Recommendation
Saturate or floor-cap the value products rather than only the index: compute `new_total_debt` via a saturating `mul` (or check `borrowed.raw() > i128::MAX * RAY / new_index` and clamp the index to the largest value that keeps the product representable). The index cap should be derived as `min(MAX_BORROW_INDEX_RAY, value_headroom_for(borrowed))` so that the cap actually engages before `scaled_to_original`/`calculate_supplier_rewards` can trap, and accrual must never panic since it gates every verb.

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
