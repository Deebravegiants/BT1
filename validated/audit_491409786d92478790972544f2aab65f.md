### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only checks that the HMAC matches the body, so any request with a previously valid (body, HMAC) pair can be replayed with an arbitrary `shop-domain` header and will still pass verification.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, and `shop`, `topic`, and `webhook_id` are pulled from headers that are never part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC of the request, then immediately trusts `request.shop` (an unauthenticated header) as the tenant identity passed to the app's handler: [3](#0-2) 

This breaks the identity binding `shop authenticated == shop used by handler as session/tenant key`. Because the signature only binds the body bytes to the secret, and the `shop-domain` header carries no cryptographic binding to that body, a party that legitimately receives one valid signed webhook body (e.g., from their own installed shop) can retransmit the exact same body to the app's webhook endpoint with the `shop-domain` header changed to any other shop. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
If the host application uses `data.shop` from `WebhookMetadata` to key session lookups, write to per-tenant records, or otherwise attribute actions to a shop (a documented and expected usage pattern per `docs/usage/webhooks.md`), an attacker can achieve cross-tenant data confusion/access by spoofing the tenant identity of an otherwise validly-signed webhook. This matches the "cross-tenant access" Critical-impact class since the shop-scoping boundary is broken using only a legitimately obtained webhook body and a modified header — no access token, `client_secret`, or privileged account is required.

### Likelihood Explanation
Any actor who can install the target app on their own store (a normal, no-privilege merchant action) can legitimately receive one signed webhook, then use it to construct a forged request against the app's public webhook endpoint with a different `shop-domain` header. No secret material, credential leakage, or side channel is required — only the standard, expected shape of a Shopify webhook request and knowledge of the target's shop domain, which is not secret.

### Recommendation
Bind the shop-domain (and topic/webhook-id, if used to route trust decisions) into the value that is HMAC-verified, or otherwise require the caller to separately verify that the shop in the header corresponds to a shop with a currently valid, previously-established session/installation before trusting the header value. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host app against a known set of currently-installed shops before being used as a lookup key.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; trigger an event so Shopify sends a legitimately signed webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture body `B` and its valid HMAC.
3. Send a new POST to the app's webhook endpoint with the same body `B`, the same valid HMAC header, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`B`) — the check passes. [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` despite the request never having been signed for that shop. [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
