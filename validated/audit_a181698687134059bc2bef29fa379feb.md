The strongest match to the report's bug class ("a field acted on but not covered by the HMAC") is in the webhooks flow.

## Title
Webhook `shop` identity is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes and routes a webhook using `Utils::HmacValidator.validate(request)`, but the HMAC signature computed by `HmacValidator` only covers the raw request body [1](#0-0) . The `shop` value the gem hands to the host application's handler comes from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed material [2](#0-1) .

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC-SHA256 over `verifiable_query.to_signable_string` and compares it to the `hmac` field using `OpenSSL.secure_compare` [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled unauthenticated straight from headers [4](#0-3) .

`Registry.process` treats a valid HMAC as proof of the entire request's authenticity and then forwards the header-derived, unsigned `shop` value directly to the app's webhook handler as the tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [5](#0-4) .

The binding that is broken is:
`shop authenticated by HMAC (bytes verified)` ≠ `shop delivered to the handler (bytes parsed from an unsigned header)`.

Concretely: an attacker who legitimately controls one Shopify store (e.g., their own free dev store) can trigger a real webhook to their own endpoint, obtaining a genuinely valid `(raw_body, hmac)` pair signed with the app's real `api_secret_key`. Because the signature never covers the shop-domain header, the attacker can replay that same body and HMAC to the target app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the (unmodified) body against the (unmodified) HMAC, so `Registry.process` accepts the request and invokes the handler believing the webhook came from the victim shop.

### Impact Explanation
Any host application that uses `request.shop` from `WebhookMetadata` to select which tenant's data to update, uninstall, resync, or delete (a documented and expected usage pattern, since `WebhookMetadata#shop` is the tenant key handed to `handler.handle`) can be made to act on the wrong merchant's data using attacker-supplied content, i.e. cross-tenant data confusion/injection. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is medium: the attacker needs their own Shopify store (any developer/free store qualifies) to capture one valid, real `(body, hmac)` pair for a webhook topic they choose to trigger (e.g., `app/uninstalled`, `shop/update`, `orders/create` with attacker-controlled body content), then replay it with a different `shop-domain` header value against the victim app's public webhook endpoint. No access token, `client_secret`, or privileged account is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material verified against the HMAC, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should include the header-derived identity fields it exposes to handlers, so a valid signature can only be produced for the specific `(shop, topic, body)` triple that was actually signed by Shopify.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and registers the app's webhook endpoint for `app/uninstalled` (or any topic).
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: H` where `H = HMAC(api_secret_key, B)`.
3. Attacker captures `B` and `H`, then sends a forged HTTP POST to the same webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)`, which still equals `H`, so validation passes [6](#0-5) .
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen body `B`, even though Shopify never sent this webhook for `victim-shop` [5](#0-4) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
