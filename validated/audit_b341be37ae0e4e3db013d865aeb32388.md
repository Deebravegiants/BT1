### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are trusted for tenant attribution but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), dispatch key (`topic`), and other metadata directly from unauthenticated HTTP headers, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` relies on to authenticate the request only covers the raw request body. This breaks the implicit binding `verified_bytes == attributed_shop`, allowing a valid (body, hmac) pair to be replayed with a forged `shop-domain` header.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers, none of which participate in the signed content: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC only over `to_signable_string` (i.e., the body) and compares it to the caller-supplied `hmac` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` to build the `WebhookMetadata` passed to the app's handler, with no cross-check that these header values are the ones the merchant/shop actually associated with the signed body: [4](#0-3) 

The equality the gem implicitly (and incorrectly) assumes is:
`hmac_valid(raw_body) == (shop_header, topic_header are trustworthy)`

In reality the HMAC only proves `raw_body` was produced with `api_secret_key`; it says nothing about `shop-domain`, `topic`, `webhook-id`, or `api-version`. Anyone who can capture one legitimate `(raw_body, hmac)` pair sent to their own app-installed store (which any developer can do without any privileged credential) can replay that exact body/hmac pair to the merchant's webhook endpoint while substituting a different `shop-domain` header value, and the HMAC check will still pass. The `WebhookMetadata` handed to the app's handler will report the attacker-chosen shop, topic, and webhook id even though none of those were signed.

### Impact Explanation
Handlers built on `WebhookMetadata#shop` typically use this value to attribute data (e.g., customer/shop redact handling, data updates, deletion triggers) to a tenant. Because `shop` is not bound to the HMAC-verified body, an attacker who owns a webhook-emitting store (an unprivileged action any developer can perform) can forge cross-tenant attribution: replaying their own legitimately-signed webhook body but relabeling it as belonging to a victim shop, tricking the host application into applying that body's action to the wrong tenant. This is a cross-tenant confusion vulnerability reachable without possessing the app's `client_secret` or any access token — matching the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Requires the attacker to control at least one shop where the target app is installed (to obtain a legitimate raw_body/hmac pair) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (trivial, since that endpoint must be internet-reachable to receive Shopify webhooks). No secret material, session, or elevated privilege is needed beyond normal app installation on an attacker-controlled store.

### Recommendation
Include `shop-domain`, `topic`, `api-version`, and `webhook-id` in the HMAC-signed payload verification (or otherwise bind these header values to the signed content), rather than trusting them as independent, unauthenticated inputs to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this is a valid `(raw_body, hmac)` pair signed with the app's real `api_secret_key`.
2. Attacker sends a new POST request to the same app's webhook endpoint with the identical `raw_body` and `hmac` header, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and/or `X-Shopify-Topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb#L190`), which succeeds because it only checks the (unchanged) `raw_body` against the (unchanged) `hmac`.
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the body/hmac pair was never produced for that shop, allowing cross-tenant data confusion in the host application.
