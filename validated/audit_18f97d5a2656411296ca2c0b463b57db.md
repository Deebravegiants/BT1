### Title
Missing Shop-Domain Validation in `Oauth.begin_auth` Allows Redirect of the OAuth Flow to an Attacker-Controlled Host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth "authorize" redirect URL directly from the caller-supplied `shop` value without ever validating that the value is a trusted Shopify domain. Every other credential-issuing entry point in this gem (`TokenExchange.exchange_token`, `Auth::ClientCredentials`, `Auth::RefreshToken`, `Clients::Graphql::Storefront`) explicitly calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` before trusting a `shop` string, but `Auth::Oauth.begin_auth` (and `auth_base_uri`) does not, breaking the intended invariant that `shop` == "a validated `*.myshopify.com`/trusted Shopify domain" before it is used to build a host that will receive the app's `client_id` and drive the merchant's browser.

### Finding Description
`ShopifyAPI::Auth::Oauth.begin_auth` takes a `shop:` argument and passes it straight to the private helper `auth_base_uri(shop)`, which returns `"https://#{shop}/admin"` with no membership check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [1](#0-0) [2](#0-1) 

Compare this to every other OAuth-credential code path in the same file/module family, which does call the validator: [3](#0-2) [4](#0-3) 

The gem's own documentation instructs integrators to feed `begin_auth` with a value taken directly from an unauthenticated HTTP request (e.g. `shop = request.headers["Shop"]`), consistent with the "Step 1" of the documented Authorization Code Grant flow: [5](#0-4) 

Because `begin_auth` performs zero validation, `shop` can be an attacker-chosen string (e.g. `evil.example.com`). `begin_auth` then:
1. Generates a per-flow nonce `state` and returns a `SessionCookie` whose value is that nonce.
2. Builds `auth_route = auth_base_uri(shop) + "/oauth/authorize?client_id=...&redirect_uri=#{Context.host}#{redirect_path}&state=#{state}&..."`. [6](#0-5) 

The calling app sets the returned cookie (binding the merchant's browser session to `state`) and 307-redirects the browser to `auth_route`, i.e., to the attacker's host, carrying the app's public `client_id` and — critically — the real, legitimate `redirect_uri` and `state` nonce in the query string.

This breaks the equality that should hold: `shop authority trusted to receive the OAuth authorize request` == `shop value supplied by the unauthenticated caller of begin_auth`. The library validates this exact equality in `TokenExchange`/`RefreshToken`/`ClientCredentials`/`Storefront` via `ShopValidator`, but omits it here, so `Oauth.begin_auth` is the one OAuth entry point in this gem where an unauthenticated `shop` string flows unchecked into a host that the merchant's browser is then sent to together with the app's `redirect_uri` and CSRF `state`.

### Impact Explanation
An attacker who can influence the `shop` value passed into `begin_auth` (a value the gem's own docs describe as coming straight from an unauthenticated request) causes the merchant's browser to be redirected — carrying the legitimate `redirect_uri` and the freshly minted `state`/session-cookie nonce — to a host the attacker controls instead of Shopify. This is a forced-OAuth-completion / session-fixation-class weakness (an explicitly in-scope High-impact category): the attacker's server can harvest the merchant's `redirect_uri` and the app-issued `state`, and (if the attacker can otherwise get the merchant to authorize the app, e.g. through a lookalike consent page or a separate confused-deputy interaction) attempt to drive a callback to the real app's callback endpoint with the correct `state`. This weakens the OAuth flow's confused-deputy/CSRF protections that `ShopValidator` is specifically designed to enforce elsewhere in this gem.

### Likelihood Explanation
The only precondition is that the integrating application uses `begin_auth` with a `shop` value taken from unauthenticated input, exactly the pattern the gem's own documentation instructs (`shop = request.headers["Shop"]`). No credentials, `api_secret_key`, or access tokens are needed by the attacker to trigger this path; they only need to reach the login route with a crafted `Shop` value. Since the gem enforces `ShopValidator.sanitize!` in every other OAuth code path, its absence here is a clear, code-provable gap rather than a theoretical concern.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth` before constructing `auth_base_uri(shop)`, mirroring the validation already performed in `TokenExchange.exchange_token`, `Auth::ClientCredentials`, `Auth::RefreshToken`, and `Clients::Graphql::Storefront`. Raise `Errors::InvalidShopError` for untrusted domains instead of building a redirect URL from them.

### Proof of Concept
1. Host application implements the login route exactly as documented:
```ruby
def login
  shop = request.headers["Shop"]
  auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")
  cookies[auth_response[:cookie].name] = { value: auth_response[:cookie].value, secure: true, http_only: true }
  redirect_to auth_response[:auth_route]
end
``` [5](#0-4) 
2. Attacker sends the victim a link to the app's login route with `Shop: evil-attacker.example` (or any header/param the host app maps into `shop`).
3. `ShopifyAPI::Auth::Oauth.begin_auth` builds:
```
https://evil-attacker.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=...&redirect_uri=https://legit-app.com/auth/callback&state=<NONCE>&grant_options[]=per-user
```
via `auth_base_uri`, with no domain check performed anywhere in the method. [7](#0-6) 
4. The victim's browser is redirected to the attacker's server with a legitimate session cookie set (`state` nonce) and the app's real `redirect_uri` and `client_id` exposed in the URL — none of which would have happened had `shop` been validated against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` as done in the gem's other OAuth flows.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
```

          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          shop_name = shop.split(".").first

        end
