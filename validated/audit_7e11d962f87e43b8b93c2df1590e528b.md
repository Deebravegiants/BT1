### Title
Panic-inducing size mismatch in BEEFY `Vote` signature conversion enables unrelayable BEEFY consensus updates - ([File: evm/rust/src/conversions.rs])

### Summary
The `From<Vote> for SignatureWithAuthorityIndex` conversion copies an attacker/relayer-controlled, variable-length Solidity `bytes signature` into a fixed 65-byte array via `copy_from_slice` without first validating the length matches 65 bytes, mirroring the CVE-2024-57983 class of bug (fixed-size buffer written from data whose size was not validated against the buffer's actual capacity).

### Finding Description
`Vote.signature` is declared as an unconstrained `bytes` type in Solidity [2](#0-1) . When a BEEFY consensus proof (`RelayChainProof` → `SignedCommitment` → `Vote[]`) is converted from the Solidity ABI struct into the Rust primitives consumed by `beefy_verifier_primitives`, the length is never checked before `copy_from_slice`:
```rust
let mut signature: TSignature = [0u8; 65];
signature.copy_from_slice(&sig_bytes);
```
`copy_from_slice` panics if `sig_bytes.len() != 65`. Since the `signature` field of `Vote` can be any length as submitted through the calldata path for a consensus-proof update, a relayer or any caller able to submit a `BeefyConsensusProof`/`RelayChainProof` can supply a `Vote` whose `signature` is not exactly 65 bytes, triggering a Rust panic during proof conversion instead of a graceful `Result::Err`.

This mirrors the reported kernel bug's root cause exactly: a fixed-size buffer (`[0u8; 65]` here vs. the mailbox driver's mis-sized register array) is written from a size that was not validated against the buffer's capacity, and only happens to be safe if the upstream caller always supplies exactly the expected size — an assumption that does not hold for externally supplied `bytes signature`.

### Impact Explanation
A panic inside proof-conversion code that runs as part of BEEFY consensus-state processing halts the client/host process handling that submission. Because this conversion sits directly in the path that ingests relayed consensus proofs and turns them into the state accepted by `verify_mmr_update_proof` (`modules/consensus/beefy/verifier/src/lib.rs`), a malformed but easily crafted `Vote.signature` can be used to reliably crash proof processing for BEEFY consensus updates, which blocks the client/route from delivering further finality updates and any ISMP messages/state proofs that depend on that consensus client's progression — a "route unable to deliver messages" condition as scoped by the task rules.

### Likelihood Explanation
Any account able to submit a `RelayChainProof`/`SignedCommitment` (an unprivileged relayer role, since BEEFY proofs are permissionlessly relayed) can trivially construct a `Vote` with a `signature` field of, e.g., 0 or 64 or 66 bytes. No cryptographic material or privileged access is required — only correctly-shaped calldata around the malformed field — making this straightforward to trigger.

### Recommendation
Validate `value.signature.len() == 65` before calling `copy_from_slice`, returning a typed conversion error (or making the `From` impl fallible, i.e. `TryFrom`) instead of panicking, consistent with how other fields in the same file use `try_into().expect(...)` intentionally on values that are already bounded by the ABI type (e.g., `u32`/`u64`) rather than on unconstrained `bytes`.

### Proof of Concept
1. Craft a `RelayChainProof` whose `signedCommitment.votes[0].signature` is a `bytes` value of length ≠ 65 (e.g., empty bytes or 64 bytes), with an otherwise well-formed `commitment` and `authorityIndex`.
2. Submit it through the BEEFY consensus proof ingestion path that invokes `From<Vote> for SignatureWithAuthorityIndex` (`evm/rust/src/conversions.rs:356-366`).
3. `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, aborting/crashing the conversion routine and thus the consensus-update handling for that call.
