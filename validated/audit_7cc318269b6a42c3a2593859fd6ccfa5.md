### Title
Concurrent `load()`/`enableBioAuth()`/`disableBioAuth()` calls can produce a lost-update race that converges `#authAtom.shouldAuthenticate` to `false` while `hasPin`/`hasBioAuth`/`hasDeviceAuth` secrets still exist in the keystore - (File: features/auth-mobile/module/auth.js)

### Summary
`Auth#load`, `Auth#enableBioAuth`, and `Auth#disableBioAuth` each perform multiple sequential `await`s against the keystore before calling the shared `#mergeIntoAtom` helper, and there is no mutex/queue serializing calls to the module. Because `#mergeIntoAtom` merges a caller-supplied snapshot (`params`) onto whatever `current` atom value exists *at the time that specific call's callback runs* — not a fresh re-read of the keystore — the completion order of concurrently-issued calls (not their invocation order) determines the final atom state, allowing a stale snapshot to overwrite a more recent, correct one.

### Finding Description
`load()` reads `hasPin`, `#hasBioAuth`, `#hasDeviceAuth`, and `biometry` sequentially [1](#0-0) , then calls `#mergeIntoAtom` with that snapshot. `enableBioAuth`/`disableBioAuth` similarly perform several sequential keystore writes/deletes via `#setBioAuth` before calling `#mergeIntoAtom` with a hard-coded literal (e.g. `{ hasBioAuth: true }` or `{ hasDeviceAuth: false, hasBioAuth: false }`) [2](#0-1) . `#mergeIntoAtom` itself does a shallow merge of `params` onto `current` and recomputes `shouldAuthenticate` from that merged object, without re-checking the keystore for ground truth [3](#0-2) .

Because these three methods (`load`, `enableBioAuth`, `disableBioAuth`) are all exposed on the public `authApi`/RPC bridge (`features/auth-mobile/api/index.js`) and can be invoked independently and concurrently (e.g., `auth.reload()`, `auth.enableBioAuth()`, `auth.disableBioAuth()` from the host app or its bridge), an attacker/racy caller who fires them close together can cause out-of-order completion: a `load()` call that began before a PIN/bio-auth was set can finish its multi-step read/merge sequence *after* a later `enableBioAuth`/`setPin` call, and overwrite the atom with a stale `false` value for `hasPin`/`hasBioAuth`, even though the actual keystore secret is present. There is no lock, sequence number, or generation check preventing a stale snapshot from clobbering the atom.

`shouldAuthenticate` (both in `#mergeIntoAtom` and the equivalent Redux selector [4](#0-3) ) is derived purely from these three booleans, and the atom is exposed directly via `auth.get` on the API and observed/broadcast to consumers via `createAuthObserver`/`authPlugin` [5](#0-4) , meaning any UI/wallet-gating logic keyed off `shouldAuthenticate` would incorrectly conclude no authentication is required.

### Impact Explanation
If `shouldAuthenticate` incorrectly converges to `false` while PIN/biometric/device-auth secrets are actually present in the keystore, any lock-screen/auth gate that trusts this atom (rather than re-querying the keystore) could skip prompting for PIN/biometrics, potentially allowing access to wallet actions that should require re-authentication. However, this repository (`features/auth-mobile`) only contains the auth-state module itself; the actual consumers that gate signing/wallet actions on `shouldAuthenticate` were not found in the indexed portion of this repo, so the concrete blast radius (e.g., whether this bypasses a lock screen only, or actually skips a signing-time authentication check) could not be fully confirmed from available code.

### Likelihood Explanation
This requires an attacker capable of triggering closely-timed, interleaved bridge calls to `load()`/`enableBioAuth()`/`disableBioAuth()` (e.g., via rapid RPC invocation), which is plausible given these are all reachable through the public `authApi` and native keystore calls have real, variable I/O latency (this is a React Native module bridging to native keychain/biometric APIs per `bio-auth.android.js`). No privileged state or secret material is needed — only unprivileged rapid/concurrent invocation of already-exposed methods. The race window and outcome are non-deterministic (depend on native I/O completion order), so reliable exploitation would require repeated attempts, but the underlying lost-update bug is real and reproducible in a mocked-async test with controlled interleaving.

### Recommendation
Serialize all mutating/loading operations on the `Auth` module (e.g., via a simple async mutex/queue keyed on the module instance) so that `load`, `setPin`, `removePin`, `enableBioAuth`, and `disableBioAuth` cannot interleave. Additionally, make `#mergeIntoAtom` authoritative by always re-deriving `hasPin`/`hasBioAuth`/`hasDeviceAuth` from a fresh keystore read at merge time (or tag each in-flight read with a monotonically increasing sequence number and drop stale merges) rather than trusting a snapshot captured before intervening awaits.

### Proof of Concept
Integration test (extending `features/auth-mobile/module/__tests__/auth.test.js` style with `createInMemoryAtom`):
1. Set up `keystore.getSecret` for `AUTH_KEYSTORE_PIN_KEY` to resolve on a controllable delay (e.g., using a manually-resolved promise) so `load()`'s read of `hasPin` can be paused mid-flight.
2. Start `auth.load()` — let it read `hasPin=false` (before PIN is set) and pause before calling `#mergeIntoAtom`.
3. While paused, call and fully await `auth.setPin('123456')`, which sets the keystore secret and calls `#mergeIntoAtom({hasPin: true})`; confirm `authAtom.get()` shows `hasPin: true, shouldAuthenticate: true`.
4. Resume the paused `load()` call so its `#mergeIntoAtom({hasPin: false, ...})` executes.
5. Assert that after both calls settle, `await authAtom.get()` incorrectly shows `hasPin: false, shouldAuthenticate: false` while `await keystore.getSecret(AUTH_KEYSTORE_PIN_KEY)` still returns the real PIN value — demonstrating the invariant "`shouldAuthenticate` matches actual keystore secret presence" is violated.

```javascript
  #mergeIntoAtom = async (params) => {
    await this.#authAtom.set((current) => {
      const data = {
        ...current,
        ...params,
      }

      const { hasBioAuth, biometry, hasPin, hasDeviceAuth } = data

      data.hasBioAuth = hasBioAuth && !!biometry
      data.shouldAuthenticate = hasDeviceAuth || hasBioAuth || hasPin

      if (isEqual(current, data)) return current

      this.#logger.info('Updated auth data', data)
      return data
    })
  }
```

```javascript
  enableBioAuth = async ({ fallbackToDevicePin = false } = {}) => {
    await this.#setBioAuth(true, { useDeviceAuth: fallbackToDevicePin })

  removePin = async () => {
    await this.disableBioAuth()
    await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_PIN_KEY))
    await this.#mergeIntoAtom({ hasPin: false })

    await this.#eventLog.record({ event: 'pin_auth_removed' })
  }

  disableBioAuth = async () => {

    await this.#mergeIntoAtom({ hasDeviceAuth: false, hasBioAuth: false })
  }
```
