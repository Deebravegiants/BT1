### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string solely from the raw request body (`to_signable_string` returns `@raw_body`), while `shop` (from the `X-Shopify-Shop-Domain` header) is read independently and never mixed into the signed material. `Registry.process` validates the HMAC against the body only, then hands `request.shop` straight to the app's webhook handler as the authoritative tenant identifier.

### Finding Description
The `VerifiableQuery` contract used for HMAC verification requires only `hmac` and `to_signable_string`. For webhooks, `to_signable_string` is defined as just `@raw_body` — no header, including `shop-domain`, `topic`, `webhook-id`, or `api-version`, is part of the signed data:

```ruby
def to_signable_string
  @raw_body
end
```

`Registry.process` uses this to authenticate the request and then trusts `request.shop` (parsed purely from the header, uncovered by the HMAC) to build the `WebhookMetadata` handed to the app-supplied handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
```

The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)` (or equivalent, binding the header claims to the signature) so that `shop` used for dispatch equals the `shop` that was actually the source of the signed payload. Instead, the binding actually enforced is only `hmac == HMAC(secret, body)`, with `shop` supplied out-of-band and unauthenticated.

Because Shopify's own webhook signing scheme (per Shopify's HMAC verification spec) also only signs the raw body, this is consistent with the upstream protocol — but it means the gem's `Request#shop` was never meant to be a trust boundary by itself. Any entity that has received one legitimately-signed webhook body/HMAC pair for a shop it controls (e.g., an attacker who installs the app on their own throwaway store to legitimately receive real webhook payloads and HMACs from Shopify for that store) can replay that exact `raw_body`/`hmac` pair while substituting an arbitrary `X-Shopify-Shop-Domain` header value. Since `to_signable_string` doesn't include the shop, the HMAC check in `HmacValidator.validate` still succeeds, and `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen `shop`.

If a host application relies on `data.shop` from `WebhookHandler#handle` to select which tenant's account/database row to update (a documented, expected usage per `docs/usage/webhooks.md`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this allows a webhook payload genuinely coming from Shop A to be attributed to a victim Shop B, corrupting or overwriting Shop B's data with Shop A's webhook content — a cross-tenant boundary violation, entirely from an internet-reachable webhook endpoint with no privileged credentials required by the attacker beyond running their own store and app install.

### Impact Explanation
This breaks the tenant isolation the gem's webhook processing API is documented to provide. An unprivileged internet user who can trigger a genuine webhook against their own installed shop can replay that exact signed body under an attacker-chosen `shop` value, causing an app to associate Shop A's webhook data with Shop B's tenant record. This is a cross-tenant access/data integrity violation, matching the "Critical: cross-tenant access" impact category, since the `shop` acted upon by the handler is not covered by the identity check that gates handler dispatch.

### Likelihood Explanation
The attacker only needs their own installed development/test store (no elevated credentials, no access to `api_secret_key`, no interception) to obtain valid `(raw_body, hmac)` pairs for topics of their choosing, then POST that pair with a forged shop-domain header to the app's public webhook endpoint. This requires no special access beyond normal use of the app as an installer, making it readily reachable by any unprivileged internet user who installs the target app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header value into the material used to verify webhook authenticity, or otherwise cross-check `request.shop` against a shop the app has verified as legitimately installed/authorized before trusting it in `WebhookMetadata`. At minimum, document/require that host apps re-validate that `request.shop` corresponds to a shop with an active session before acting on the payload, and consider extending `Webhooks::Request#to_signable_string` to include the shop-domain header when feasible, matching the intended identity binding of `hmac == HMAC(secret, shop ‖ body)`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker-shop.myshopify.com`; trigger a webhook (e.g., `orders/create`) to receive a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair signed by Shopify with the app's `client_secret`.
2. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are computed only from the header's `hmac-sha256` value and `@raw_body`; `HmacValidator.validate` succeeds because the signature still matches the (unchanged) body.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host app to process attacker-supplied data under the victim shop's identity.
