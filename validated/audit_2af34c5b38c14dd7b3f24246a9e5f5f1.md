### Title
Route-selected contracts can inject a wallet-token transfer into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts an opaque `StrategySwap` byte payload and forwards it to the configured router, while the controller’s own authorization grant only covers the exact input-token transfer to that router. [1](#0-0) [2](#0-1)  A malicious route can name an attacker-controlled pool contract, and code reached through that route can require the transaction caller’s authorization for an unrelated token transfer. [3](#0-2) [4](#0-3)  Simulation records that unrelated transfer as a sub-invocation of the caller’s `swap_collateral` authorization, so submitting the recorded authorization tree allows the transfer even though the measured swap remains economically valid. [5](#0-4) 

### Finding Description
`swap_collateral(caller, account_id, current, from_amount, new, swap)` authenticates only that `caller` owns or delegates the account, then withdraws `current` collateral and passes `swap` into the router path. [6](#0-5)  `StrategySwap` is only an opaque `Bytes` value, so the controller does not decode or validate the pool and token addresses embedded in the route. [1](#0-0)  `swap_tokens` grants the router authority solely for `token_in.transfer(controller, router, amount_in)` and then calls `router.execute_strategy(controller, amount_in, swap)`. [7](#0-6)  The venue layer derives the pool destination from `hop.pool`, but the measured input/output checks do not constrain what other caller-authorized calls that pool makes. [3](#0-2)  Because `caller.require_auth()` authorizes an invocation tree rather than only direct token spending, a route-selected contract can attach a separate `token.transfer(caller, attacker, amount)` beneath the signed `swap_collateral` invocation. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker can steal unrelated tokens held directly by the caller’s wallet while still returning enough routed output for the collateral swap and final account checks to succeed. [10](#0-9)  The loss is not limited to `amount_in`, the collateral position, router-held residue, or the route’s declared output token because the injected call transfers a different wallet-held token to the attacker. [4](#0-3) [11](#0-10) 

### Likelihood Explanation
Any unprivileged user can call `swap_collateral` with attacker-constructed route bytes, and the same pattern is reachable through `swap_debt` because it forwards its route to `swap_tokens_or_passthrough`. [12](#0-11) [13](#0-12)  Exploitation requires the victim to submit a transaction whose recorded authorization tree includes the injected transfer, and transaction simulation explicitly surfaces that tree. [14](#0-13)  Once that poisoned tree is signed, the host accepts the unrelated transfer and the complete swap succeeds. [15](#0-14) 

### Recommendation
Constrain route execution to governance-approved pool and venue contract addresses so route bytes cannot select arbitrary executable contracts beneath the caller’s authorization. [16](#0-15) [3](#0-2)  Until the external call graph is constrained, clients must reject any `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or direct router authorization tree containing children other than the expected input transfer. [7](#0-6) [15](#0-14) 

### Proof of Concept
1. Deploy a pool contract whose `swap` method performs `unrelated_token.transfer(victim, attacker, victim_balance)` after storing `(victim, unrelated_token, attacker, victim_balance)` during construction. [17](#0-16) 
2. Encode a swap route naming that contract as a hop pool while declaring a fair output amount. [18](#0-17) 
3. Have the victim invoke `swap_collateral(victim, account_id, USDC, 5_000_USDC, ETH, route_bytes)`. [19](#0-18) 
4. Transaction simulation records `unrelated_token.transfer(victim, attacker, victim_balance)` as a child of the victim’s `swap_collateral` authorization. [20](#0-19) 
5. Submitting that recorded authorization tree transfers the victim’s entire unrelated wallet balance to the attacker while crediting the victim with the expected swap output. [15](#0-14)

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
