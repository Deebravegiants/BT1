Webhook shop/topic identity spoofing via HMAC that only binds the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs (and later verifies) only the raw JSON body via HMAC, but the `shop`, `topic`, `api_version`, and `webhook_id` fields — all of which are trusted by `Registry.process` to route and attribute the webhook to a tenant — are read from unauthenticated HTTP headers that are never covered by that HMAC. This breaks the same "verified bytes vs. acted-upon field" identity binding described in the external report: the signature over-trusts one part of the request while a materially important field is asserted without being cryptographically bound to it.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` and compares it to the `hmac` field with a constant-time comparison: [5](#0-4) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts these header-derived fields to build the `WebhookMetadata` handed to the app's business logic — including `request.shop`, which most host apps use as the tenant key: [4](#0-3) 

This is the direct analog to the reported bug class: the equality that should hold is `bytes verified (HMAC over body) == identity fields acted upon (shop/topic/webhook_id)`, but the gem only enforces `HMAC(body) == hmac header`, leaving `shop`/`topic`/`webhook_id` completely unbound. For contrast, the OAuth callback path in this same gem does it correctly — `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, so `shop` cannot be swapped without invalidating the HMAC: [6](#0-5) 

The webhook path has no equivalent binding.

### Impact Explanation
Because the app's `client_secret`/api secret key is shared across every shop that installs the app (it is not per-tenant), an attacker who merely installs the target app on their own shop (an "unprivileged" merchant relative to any other tenant) will legitimately receive genuine webhook deliveries — complete with a valid body + HMAC computed by Shopify using the app's shared secret. The attacker can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header claiming to belong to a victim shop. `Registry.process` will pass HMAC validation (since only the body is checked) and dispatch the handler with the forged `shop`/`topic`, causing the host app to execute tenant-scoped business logic (e.g., data deletion for GDPR topics, deprovisioning on `app/uninstalled`, billing/entitlement changes, etc.) attributed to a shop the attacker does not control. This is a cross-tenant identity spoofing vulnerability reachable without ever knowing the app's `api_secret_key`.

### Likelihood Explanation
Any user able to install the target app on a shop they control (a low bar — free/public app installs, or a paid trial) can obtain a valid signed webhook body/HMAC pair for their own tenant and then replay it with a different `shop`/`topic` header value, since nothing in this gem prevents header tampering post-signature-check. No secrets, tokens, or elevated privileges are required beyond normal app installation.

### Recommendation
Bind the identity fields into the signed payload the way Shopify's own examples and the OAuth `AuthQuery#to_signable_string` do it: either verify `topic`, `shop-domain`, and `webhook-id` headers against values embedded/expected in the body/registration context, or otherwise cryptographically bind them (e.g., include them in the string that is HMAC-verified, or cross-check `shop` against the session/tenant that owns the currently processing webhook registration) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook (e.g. `customers/data_request`) at their public endpoint, with headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Topic: customers/data_request`
   - raw body `B`
2. Attacker replays the exact same `raw_body` and `hmac` header to the app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` [1](#0-0)  — validation succeeds because the body is unchanged.
4. The handler is invoked with `WebhookMetadata` built from `request.shop == "victim.myshopify.com"` [7](#0-6) , causing the host application to perform tenant-scoped actions against the victim shop's account/data based on a forged request the attacker fully controls the timing and (to the extent the body schema allows) content of.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
