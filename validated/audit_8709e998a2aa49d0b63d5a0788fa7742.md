### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` fields are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body, but the shop identity, topic, webhook id and API version used to route and process the webhook are read directly from HTTP headers that are never included in the signed payload. This breaks the equality *"shop authenticated == shop the handler acts on"*, allowing a party who can obtain one valid `(body, hmac)` pair to replay it against the app's public webhook endpoint while freely rewriting the `shop-domain` (and `topic`) header, causing the handler to process attacker-supplied data under a different tenant's identity.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing the HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers, which are not part of the signable string and therefore not covered by the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` from these unauthenticated header values, handing them to the app's registered handler: [4](#0-3) 

Because `shop` (and `topic`) are excluded from the signed content, the binding the app relies on — *"the HMAC-verified request corresponds to this particular shop/topic"* — does not hold. Any attacker who can obtain a single legitimate `(raw_body, hmac)` pair signed with the app's real `api_secret_key` (e.g., by triggering a webhook on their own store, which they legitimately control, and capturing what Shopify sends to the app's public callback endpoint) can replay that exact body/hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` passes the attacker-chosen shop value straight to the handler as `WebhookMetadata#shop`.

This contrasts with `Auth::Oauth::AuthQuery`, whose `to_signable_string` implementation binds the full query, including `shop`; the webhook path in this gem simply does not extend HMAC coverage to the identity fields it exposes to the handler.

### Impact Explanation
Cross-tenant access: an app built on this gem trusts `WebhookMetadata#shop` (and `#topic`) as if they were verified by the HMAC, since `Registry.process` performs the HMAC check right before constructing and dispatching that metadata. A host application processing webhooks per-shop (looking up sessions, updating tenant-scoped data, or running mandatory `shop/redact`/`customers/redact`/`customers/data_request` handlers) can be made to attribute attacker-controlled webhook body content to an arbitrary victim shop domain, since nothing in this gem prevents that mismatch. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The webhook receiving endpoint is, by design, a public, unauthenticated HTTP endpoint (Shopify posts to it without any session/auth token — verification is HMAC-only). An attacker only needs a single valid `(body, hmac)` pair, which they can trivially obtain from their own store/app installation (a legitimate, unprivileged action), then replay it with a modified `shop-domain` header. No secrets, tokens, or privileged access are required beyond controlling one's own shop — a realistic unprivileged-internet-user scenario.

### Recommendation
Include `shop`, `topic`, and ideally `webhook_id`/`api_version` in the HMAC-covered signable string for webhooks (or otherwise cryptographically bind them to the body), so that `Utils::HmacValidator.validate` fails if any of these header-derived identity fields are altered relative to what Shopify actually signed. At minimum, `Webhooks::Request#to_signable_string` should not diverge from the general pattern used by `AuthQuery`, where the fields relied upon downstream are part of what's verified.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and triggers a real webhook (e.g., `orders/create`) so Shopify sends a legitimately-signed request to the app's public webhook endpoint; attacker captures the exact `raw_body` and `X-Shopify-Hmac-Sha256` header value.
2. Attacker sends a new HTTP request to the same public webhook endpoint with the identical `raw_body` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` → returns the untouched `raw_body`, recomputes HMAC with the app's real secret, and it matches — validation passes.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...)` and invokes the app's handler, which now processes attacker-controlled data as if it originated from `victim.myshopify.com`. [5](#0-4) [6](#0-5)
