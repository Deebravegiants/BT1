### Title
Unchecked U128→u64 truncation in `swap_token_amount_base_out` fee scaling allows draining a pool with a wrapped/undersized `swap_in_after_add_fee` - ([File: program/src/processor.rs])

### Summary
`process_swap_base_out` (and its `_v2` twin) computes the amount a swapper must pay by inflating a U128 intermediate value and then calling `.as_u64()` on it directly, instead of using the checked `Calculator::to_u64()` helper that returns `Err` on overflow. Because the `uint` crate's `as_u64()` silently truncates to the low 64 bits rather than panicking or erroring, an attacker-chosen `amount_out` close to the pool's total balance can make the computed "amount to pay" wrap around to a small value, exactly mirroring the CVE-2021-47275 bcache pattern where an oversized computed quantity (`sectors`) silently overflowed a narrower field (`KEY_SIZE`), corrupting a downstream size used for both accounting and I/O.

### Finding Description
`Calculator::swap_token_amount_base_out` in [1](#0-0)  computes `amount_in` as `total_coin_or_pc * amount_out / (other_total - amount_out)`. The denominator `(total_pc_without_take_pnl - amount_out)` or `(total_coin_without_take_pnl - amount_out)` can be driven arbitrarily close to zero by an attacker choosing `swap.amount_out` close to (but below) the pool total, since the only guard is `swap.amount_out >= total_pc_without_take_pnl` performed *after* this division, not before [2](#0-1) . With a tiny denominator, `amount_in` (a `U128`) can grow to a value far exceeding `u64::MAX`.

This oversized `U128` is then further inflated by `checked_mul(amm.fees.swap_fee_denominator)` and divided again, and the final value is narrowed with a raw `.as_u64()` call rather than the fallible `Calculator::to_u64()`: [3](#0-2) 

The `uint` crate's generated `as_u64()` (used throughout `math.rs`/`processor.rs`, e.g. [4](#0-3) ) truncates to the low 64 bits instead of erroring on overflow — the exact same silent-truncation bug class as CVE-2021-47275, where a 17-bit `sectors` value was folded into a 16-bit `KEY_SIZE` bitfield and truncated to 0.

The truncated `swap_in_after_add_fee` is then used for both fund-sufficiency checks and the actual transfer amount: [5](#0-4) [6](#0-5) 

Because the check `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` operate on the already-truncated (potentially tiny) value, the attacker's real payment is bounded by the wrapped value, while the amount transferred out (`swap.amount_out`, controlled directly by the attacker's instruction data) is paid in full from the vault.

### Impact Explanation
An attacker can submit a single `SwapBaseOut`/`SwapBaseOutV2` transaction with `amount_out` chosen just under the pool's total coin or pc balance, forcing the fee/amount-in calculation to overflow `u64` and wrap. This lets the attacker withdraw nearly the entire opposite-side reserve of the pool while paying only the truncated (small/wrapped) `swap_in_after_add_fee`, directly and permanently draining LP/user funds and creating insolvent pool accounting — matching the "concrete theft ... of user or LP funds" / "insolvent pool accounting" impact bar.

### Likelihood Explanation
This is reachable by any unprivileged user through the public `SwapBaseOut`/`SwapBaseOutV2` instructions with fully attacker-controlled `amount_out`/`max_amount_in` and attacker-chosen token accounts satisfying the mint checks. No special privileges, validator behavior, or off-chain component is required — a single transaction with a large `amount_out` relative to the pool reserve is sufficient to trigger the truncation.

### Recommendation
Replace the raw `.as_u64()` calls on the fee-scaled `U128`/`U256` intermediates in `process_swap_base_out`/`process_swap_base_out_v2` (and any other place using `.as_u64()` on attacker-influenced arithmetic) with the fallible `Calculator::to_u64()` (or equivalent `checked` conversion) that returns `AmmError::ConversionFailure` on overflow instead of silently truncating. Additionally, validate `amount_out` against the pool reserve before performing the division in `swap_token_amount_base_out` so the denominator can never approach zero.

### Proof of Concept
1. Attacker observes a pool with `total_coin_without_take_pnl = C` and `total_pc_without_take_pnl = P`.
2. Attacker submits `SwapBaseOut` with `amount_out = C - 1` (direction `PC2Coin`), so the denominator `total_coin_without_take_pnl - amount_out = 1` in `swap_token_amount_base_out` ( [7](#0-6) ), producing `amount_in ≈ P * (C - 1)`, a value that can vastly exceed `u64::MAX` for realistic reserve sizes.
3. This oversized value is scaled further by `swap_fee_denominator` and narrowed via `.as_u64()` at [3](#0-2) , producing a wrapped, attacker-predictable small `swap_in_after_add_fee`.
4. The `user_source.amount < swap_in_after_add_fee` and `max_amount_in < swap_in_after_add_fee` checks ( [8](#0-7) ) pass trivially because the compared value is now tiny.
5. `Invokers::token_transfer` pulls only the truncated small amount from the attacker while `Invokers::token_transfer_with_authority` pays out the full `amount_out = C - 1` from the vault ( [9](#0-8) ), draining the pool.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
