### Title
Webhook shop-domain identity used by `Registry.process` is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` treats the HTTP body as the only HMAC-protected value, while the tenant identity (`shop`), `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers and handed to the app's handler as if they were verified.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns solely `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version` and `webhook_id` are all pulled straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values as the trusted tenant/topic context: [3](#0-2) 

The identity binding that should hold is: `shop header == shop the HMAC-signed body actually originated from`. Because the signature covers only bytes of the body, that equality is never checked — any request whose body happens to produce a valid HMAC (e.g., a genuine webhook captured from the attacker's own store, which any internet user can install the app on) can be replayed with an arbitrary `x-shopify-shop-domain` / `shopify-shop-domain` header, and the signature will still validate.

### Impact Explanation
An unprivileged attacker who can install the target app on their own store (a normal, unprivileged "merchant" action requiring no victim credentials) receives genuine Shopify-signed webhooks for their own shop. Because the HMAC never covers the shop-domain header, the attacker can replay that valid `(body, hmac)` pair to the app's webhook endpoint while substituting a different shop's domain in the header. `Registry.process` will still validate the HMAC (since it only checks the body) and will call the app's handler with `WebhookMetadata#shop` set to the attacker-chosen value. Any app logic that uses that `shop` value to key per-tenant lookups, writes, or invalidations (a common documented usage: "process a webhook ... for a shop") ends up performing an action attributed to a different tenant using attacker-controlled body content, i.e. cross-tenant confusion — mapping to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires no leaked secrets, tokens, or victim interaction: only that the attacker can install the vulnerable app on any store (self-serve, trivial) to obtain a genuinely-signed webhook body/HMAC pair, then forge the shop-domain header when POSTing to the app's public webhook endpoint. The gem provides no mechanism to bind headers to the signed payload, so any host application relying on `request.shop` from `ShopifyAPI::Webhooks::Registry.process` for tenant identity is exposed by design of this library code, not by host misuse.

### Recommendation
Include `shop`, `topic`, and `webhook_id` header values in the signable payload (or otherwise cryptographically bind them to the body before computing/verifying the HMAC), and reject requests where the recomputed signature does not cover the full set of security-relevant fields. At minimum, document/enforce that `shop`/`topic` must never be trusted as authenticated identity data derived only from the body's HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint: `raw_body = '{"id":123,...}'`, `x-shopify-hmac-sha256 = HMAC(api_secret_key, raw_body)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts this request and replays it to the same endpoint, changing only the header: `x-shopify-shop-domain: victim.myshopify.com` (body and HMAC unchanged).
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this successfully; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body, ...)` — the app now processes attacker-controlled event data under the victim shop's identity.           raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
