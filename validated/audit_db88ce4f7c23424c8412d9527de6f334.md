### Title
Unchecked ERC20/TRC20 `transfer()` return value allows silent failure of escrow release, refund, and fee sweep on Tron IntentGateway - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` and the `SweepDust` branch of `onAccept()` release escrowed tokens using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the call itself did not revert (`success`), without decoding/verifying the ABI-encoded boolean return value that `transfer()` is supposed to produce per EIP-20. [1](#0-0)  The same pattern appears for fee redemption [2](#0-1)  and for governance dust sweeps [3](#0-2) .

### Finding Description
`onAccept()` decodes an incoming `RedeemEscrow`/`RefundEscrow` Hyperbridge message and calls `withdraw()` to release escrowed input tokens (from `placeOrder` on the source chain) to the solver or refund them to the user. [4](#0-3)  For each token, the escrowed accounting `_orders[commitment][token]` is decremented and then a raw `.call` to `transfer()` is issued, with only the low-level call success checked:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

On Tron, TRC20 tokens are widely known to include non-compliant implementations that return `false` (instead of reverting) on failed transfers, similar to legacy ERC20 tokens such as ZRX. In such a case, the external `.call` itself succeeds (returns `success = true`) even though the token's internal `transfer()` logic returned `false` and moved no tokens. Because the code never decodes/checks that returned boolean, the function proceeds as if the transfer succeeded: it does not revert, `_filled[body.commitment]` is already marked finalized, and the escrow accounting has already been decremented before the transfer attempt. The end result is that the beneficiary receives nothing while the protocol's internal state treats the order as settled, permanently losing the escrowed funds with no recovery path (the state has already recorded the order as filled/refunded).

Notably, the equivalent EVM-side implementation in `evm/src/apps/intentsv2/IntentsBase.sol` uses OpenZeppelin's `SafeERC20.safeTransfer` for exactly this operation [5](#0-4) , and `_sweepDust` similarly uses `safeTransfer` [6](#0-5) . The Tron variant deviates from this safe pattern and reintroduces the unchecked-return-value bug that `safeTransfer` is specifically designed to prevent.

### Impact Explanation
This is reachable by any relayer delivering a normal cross-chain `RedeemEscrow`/`RefundEscrow` message that a solver or user is entitled to via ordinary intent fill/cancel flows — no privileged role is required to trigger delivery. If the escrowed token is a non-compliant TRC20/ERC20 that signals failure via a `false` return rather than reverting (deflationary/fee-on-transfer tokens, paused/blacklist tokens, or tokens with insufficient allowance/balance edge cases returning `false`), the beneficiary permanently loses their entitled funds while the contract's internal escrow ledger and `_filled` mapping already mark the order as settled, with no code path to retry or recover. This is a direct, permanent loss-of-funds bug for both solvers (fill payouts) and users (refunds), and also affects the governance-triggered `SweepDust` and protocol fee redemption paths.

### Likelihood Explanation
Likelihood is medium: it requires escrowing/sweeping a token whose `transfer()` implementation is non-reverting-on-failure, which is a known and common category of tokens, especially on Tron/TRC20 where such patterns are prevalent. No attacker action beyond normal message delivery is needed — the failure mode is triggered by ordinary use with any listed non-compliant token.

### Recommendation
Replace the raw `.call` + `success`-only checks with OpenZeppelin's `SafeERC20.safeTransfer` (as already used in `evm/src/apps/intentsv2/IntentsBase.sol`) so both the call and the ABI-decoded boolean return value are checked:
```diff
- (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
- if (!success) revert TransferFailed();
+ IERC20(token).safeTransfer(beneficiary, amount);
```
Apply this consistently to `withdraw()`'s token loop, the transaction-fee redemption, and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. A user places a cross-chain order via `placeOrder`, escrowing `TokenX` (a Tron TRC20 whose `transfer()` returns `false` on failure instead of reverting, e.g., when the recipient is blacklisted or the contract is paused).
2. A solver fills the order on the destination chain; Hyperbridge relays a `RedeemEscrow` message back to the Tron `IntentGatewayV2`.
3. `onAccept()` → `withdraw()` decrements `_orders[commitment][TokenX]` and calls `TokenX.call(transfer(solver, amount))`. Suppose `TokenX` is momentarily paused or the beneficiary is blacklisted: the low-level call returns `success = true` (execution didn't revert) with returndata `abi.encode(false)`.
4. Because only `success` is checked, `withdraw()` does not revert, marks `_filled[commitment] = beneficiary`, and emits `EscrowReleased`.
5. The solver never actually received `TokenX` (transfer returned `false`), yet the escrow accounting shows it as spent and the order as finalized — funds are permanently lost with no path to reclaim them.
