### Title
Stranded router-swap residue in `ExternalActionSwap.swap` can be siphoned by any caller in a later transaction - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`ExternalActionSwap.swap` (via `LifiExternalAction.callRouter`) grants the LI.FI router an unlimited approval and then forwards fully attacker-controlled `externalActionMetadata` calldata to that fixed router, with `swappedAmount` measured only as the output-token balance delta. `inputAmount` is never enforced to be fully consumed for ERC-20 swaps, so an attacker can craft a swap that leaves input-token dust/residue sitting on the action contract (funded by `-deltaAmountChanges` Hinkal already sent it), and later, from a fresh, unrelated `transact` call, direct the router's unlimited allowance to sweep that residue into an output token the attacker claims as their own UTXO — capturing value never attributed to that transaction's `-deltaAmountChanges`.

### Finding Description
The invariant that should hold is: **tokens leaving an action contract in transaction T == `-deltaAmountChanges` Hinkal sent that action in transaction T** (plus what the action legitimately produced from that input). This is what `Hinkal.transact`'s per-token balance-diff check is meant to enforce: [1](#0-0) 

However, this check only compares **Hinkal's own balance delta** for a token against `amountChanges[i] + utxoAmount` for that transaction. It has no way to distinguish "value that legitimately came from this transaction's input" from "value that was already sitting in the external action contract from a prior transaction."

In `ExternalActionSwap.swap`, the pulled-in input amount is computed once at the top: [2](#0-1) 
and the actual token movement is delegated entirely to `callRouter`, whose LI.FI implementation for ERC-20 tokens ignores `inputAmount` completely and instead grants an **unlimited approval** to the fixed `router`, then executes whatever calldata the attacker supplied: [3](#0-2) 

`swappedAmount` is derived purely from the output-token balance delta around that call: [4](#0-3) 

Because `router.call(externalActionMetadata)` is fully attacker-controlled and `inputAmount` is not enforced to be consumed, an attacker can:
1. **Transaction 1**: request a swap where `deltaAmounts[0]` claims to pull `X` of `inputToken` from Hinkal into the action, but craft `externalActionMetadata` so the router only consumes `X - r` (leaving residue `r` of `inputToken` sitting in the `LifiExternalAction` contract, still approved unlimited to `router`). The transaction's balance-diff equation in `Hinkal.transact` still balances internally (Hinkal's balance dropped by `X`, the declared `amountChanges[0]` is `-X`), so nothing reverts — the residue `r` is simply unaccounted-for value stranded on the action contract.
2. **Transaction 2** (can be from a different, unrelated attacker EOA who has never touched the stranded funds): call `Hinkal.transact` again through the same `ExternalActionSwap`/`LifiExternalAction`, declaring `amountChanges[0] = 0` for `inputToken` (so `_externalTransact` transfers nothing new into the action) and crafting `externalActionMetadata` to have the router pull the leftover residue `r` (still approved unlimited from step 1) and swap it to `outputToken`. `swappedAmount` picks up this residue as a genuine balance increase of `outputToken`, and it is forwarded to `msg.sender` (Hinkal) and wrapped into `utxoSet[0]` addressed to the attacker's own `stealthAddressStructure`.

From Hinkal's perspective in transaction 2, the balance-diff check for `inputToken` sees `balanceDif == 0 == amountChanges[0] (0) + utxoAmount(0)` — consistent, because Hinkal's own balance for `inputToken` never moved (the residue was already off Hinkal's books). The check for `outputToken` sees the swap output faithfully credited to a UTXO — also internally consistent. **Neither check can detect that the value paid out this transaction did not originate from `-deltaAmountChanges` sent this transaction**, because the residue value never round-tripped through Hinkal's balance sheet at all; it was parked directly in the action contract by transaction 1 and never returned. The attacker in transaction 2 effectively mints themselves a UTXO backed by value the protocol/user actually paid for in transaction 1 and never received back.

The mention of "field-boundary near `CIRCOM_P`" in the question does not add an additional exploit vector here: `CircomDataBuilder.formInputForCircom` bounds `amountChanges[i]` to `(-MAX_AMOUNT, MAX_AMOUNT)` before modular encoding, and `_calculateDeltaAmount`/Hinkal.sol always operate on the raw `int256` (not the field-wrapped value), so no additional divergence between the on-chain arithmetic and the field element was found in the accessible code. The core defect is the router-approval/output-only-accounting gap described above, independent of any near-`CIRCOM_P` value.

### Impact Explanation
An unprivileged attacker can direct value that a user's transaction paid into the swap action (via `-deltaAmountChanges`) but that the attacker-supplied router calldata deliberately left unconsumed, to be swept out as the attacker's own shielded UTXO in a completely separate transaction. This is a direct theft of in-flight user/protocol funds parked in an external action, matching the Critical impact category ("direct theft of shielded or in-flight user funds"). It is repeatable: any attacker who can call `Hinkal.transact` targeting the registered `LifiExternalAction`/`ExternalActionSwap` with self-crafted `externalActionMetadata` can create and later reap this residue, and multiple attackers or the same attacker across many transactions can each strand and later reclaim dust/rounding amounts, or larger amounts if the router itself can be coerced (e.g., via multicall-style calldata to itself) into leaving a deliberate remainder.

### Likelihood Explanation
- Preconditions: `LifiExternalAction`/`ExternalActionSwap` must be registered as a valid `externalActionId` in `Hinkal` (`registerExternalAction`), which is standard deployment configuration, not privileged access by the attacker.
- The attacker needs only to be able to submit `Hinkal.transact` calls with self-generated proofs for their own UTXOs and fully control `externalActionMetadata` (the calldata forwarded verbatim to `router`), which is explicitly within the attacker's granted capabilities per the rules.
- Feasibility depends on whether the fixed `router` (LI.FI diamond) can be made to execute a call that consumes less than the full approved/expected amount while still returning success — this is plausible given LI.FI routers expose many generic swap/bridge selectors and the contract approves *unlimited* allowance rather than an exact amount, so the attacker has full latitude to construct any sub-call that leaves a chosen remainder.
- Cost is low (gas plus whatever value is intentionally stranded, which the same attacker can later recover, or which comes from another party's transaction if margins/slippage naturally leave dust).
- Repeatable across many transactions and independent of any admin/relay privilege.

### Recommendation
Enforce full consumption of the intended input amount and remove any implicit "carry-over" balance between transactions in `ExternalActionSwap`/`LifiExternalAction`:
1. In `LifiExternalAction.callRouter`, snapshot the input-token balance before and after the router call and `require` that the decrease equals exactly `inputAmount` (do not silently accept partial consumption), rather than ignoring `inputAmount` for ERC-20 swaps.
2. Replace `approveUnlimited(inputToken, router)` with an exact, single-use approval of `inputAmount`, reset to zero after the call, so the router cannot later be triggered (by anyone, in a future transaction) to pull additional un-owned residue via a stale allowance.
3. Add an invariant check in `ExternalActionSwap.swap`/`EmporiumUpgradeable`-style actions that the action contract's balance of every token in `circomData.erc20TokenAddresses` returns to (or below) its pre-call baseline for tokens not represented in `utxoSet`, so that no value can be "parked" in the action across transactions.
4. Consider a per-action reentrancy/sweep guard that reverts if any registered ERC-20 balance held by the action contract is non-zero for tokens not explicitly declared as carrying UTXOs after `runAction` completes.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `LifiExternalAction` with a mock `router` contract that: (a) on a special calldata selector `partialSwap(uint256 consumeAmount, uint256 outAmount)`, pulls `consumeAmount` of `inputToken` via the existing unlimited allowance and sends `outAmount` of `outputToken` to the caller (`LifiExternalAction`); (b) accepts being called again to pull any further approved balance.
2. Register `LifiExternalAction` in `Hinkal` via `registerExternalAction`.
3. **Transaction 1** (attacker A): build valid `CircomData`/proof declaring `amountChanges[0] = -1000` (`inputToken`), and `externalActionMetadata` = `partialSwap(900, outAmount1)` — only 900 of the 1000 pulled from Hinkal is consumed by the mock router, leaving `100` of `inputToken` sitting on `LifiExternalAction` (still unlimited-approved to `router`). Assert `Hinkal.transact` succeeds; assert `IERC20(inputToken).balanceOf(lifiAction) == 100`.
4. **Transaction 2** (attacker B, unrelated account, no funds ever deposited by them for this token): build a second valid `CircomData`/proof declaring `amountChanges[0] = 0` for `inputToken` (no new funds pulled), and `externalActionMetadata = partialSwap(100, outAmount2)` — this call sweeps the stranded 100 units left from transaction 1 and produces `outAmount2` of `outputToken`.
5. Assert `Hinkal.transact` for attacker B succeeds (no revert from the balance-diff checks), and assert that attacker B's resulting encrypted UTXO/on-chain commitment for `outputToken` has `amount == outAmount2` funded entirely by the residue from transaction 1's `-deltaAmountChanges`, i.e., assert:
   - `balanceDif[inputToken] == 0 == amountChanges[0] (0) + utxoAmount(inputToken) (0)` — passes trivially, masking the theft.
   - `IERC20(inputToken).balanceOf(lifiAction) == 0` after transaction 2 (residue fully drained).
   - Attacker B receives a UTXO/`outputToken` value they never funded via any `-deltaAmountChanges` attributable to their own transaction.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
