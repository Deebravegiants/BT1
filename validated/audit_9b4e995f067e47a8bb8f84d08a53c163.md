## Analog Found

### Title
Signed-to-unsigned integer conversion in gateway staleness check allows bypass of message-age validation - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The `InsuranceFund` bug class in the report is about stale/expired data bypassing a validity guard due to an unchecked arithmetic operation. The chainlink analog is in `handler.HandleLegacyUserMessage`, which enforces a "message not stale" guard using an integer subtraction between a `uint` derived from the current time and a signed `int64` payload timestamp cast to `uint`. A caller-controlled negative timestamp wraps around during the `uint(payload.Timestamp)` conversion, defeating the staleness check entirely.

### Finding Description
`HandleLegacyUserMessage` decodes a `webapicap.TriggerRequestPayload` from the incoming message body and checks two conditions on `payload.Timestamp` before honoring the trigger request: [1](#0-0) 

```go
if payload.Timestamp == 0 { ... return UserMessageParseError }

if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    h.lggr.Errorw("stale message")
    return ...HandlerError "stale message"
}
```

`payload.Timestamp` is a signed `int64` field (as constructed in tests via `strconv.ParseInt`), yet it is compared using an unsigned `uint()` cast. If a caller submits a negative timestamp (e.g., `-1`), it passes the `== 0` check (it's nonzero), but `uint(payload.Timestamp)` wraps around to a value near `math.MaxUint64`, which is always larger than `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`. The comparison then evaluates false, and the "stale message" rejection never triggers — mirroring the analog bug class where an out-of-range/expired input silently bypasses the freshness/validity check instead of being rejected, rather than reverting via an arithmetic trap as in the original Solidity report (Go doesn't panic on this particular unsigned wraparound the way it does on signed overflow, so the effect here is a logic bypass rather than a crash, but the root defect — using unvalidated attacker-supplied timestamp data in an arithmetic freshness check without bounds/sign validation — is the same class of flaw).

Once past this check, the request is forwarded unmodified to every DON member via `don.SendToNode`: [2](#0-1) 

The `MaxAllowedMessageAgeSec` staleness guard is the only defense in this codepath preventing outdated/forged-timestamp trigger payloads from reaching the DON nodes (a `// TODO: apply allowlist and rate-limiting here` immediately follows, confirming there is no allowlist enforcement at this layer either): [3](#0-2) 

### Impact Explanation
An external client submitting an HTTP trigger request through the gateway controls the `TriggerRequestPayload.Timestamp` value entirely. By supplying a negative timestamp, the freshness/anti-staleness check is silently bypassed, meaning a message that should have been rejected as "stale" is instead forwarded to all DON member nodes as a legitimate trigger request. This undermines the intended integrity guarantee of `MaxAllowedMessageAgeSec` and could be used to push effectively unbounded-age webapi trigger events into the workflow pipeline that operators believed were time-bounded.

### Likelihood Explanation
The `Timestamp` field is fully attacker-controlled JSON input from the payload of an unprivileged, internet-facing HTTP request handled by `HandleLegacyUserMessage`; no additional privilege is required to set a negative value, only correct JSON structure (as demonstrated by the existing test helper constructing `TriggerRequestPayload` directly with an arbitrary `int64` timestamp).

### Recommendation
Validate `payload.Timestamp` is non-negative (and within a sane bound) before performing any unsigned conversion, or perform the freshness comparison entirely in signed arithmetic (`int64`) to avoid wraparound, e.g. reject when `payload.Timestamp < 0 || time.Now().Unix()-payload.Timestamp > int64(h.config.MaxAllowedMessageAgeSec)`.

### Proof of Concept
1. Construct a `TriggerRequestPayload` JSON body with `"timestamp": -1` (any negative int64).
2. Sign and send it as `HandleLegacyUserMessage` input (mirroring the pattern in the existing `triggerRequest` test helper at `core/services/gateway/handlers/capabilities/handler_test.go:193-234`, but with a negative timestamp string instead of `"123456"`).
3. Observe that `uint(payload.Timestamp)` wraps to a near-maximum `uint64` value, so `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec > uint(payload.Timestamp)` evaluates false, and the "stale message" branch is never taken — the request is forwarded to DON nodes instead of being rejected.
