The docs explicitly claim `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" — but the verification (`Utils::HmacValidator.validate`, computed over `to_signable_string` = `@raw_body` only, per `lib/shopify_api/webhooks/request.rb:35-38`) never covers the `shop`, `topic`, `webhook_id`, or `api_version` header values that are then handed unauthenticated straight into the handler via `WebhookMetadata` in `lib/shopify_api/webhooks/registry.rb:189-199`.

### Title
Webhook HMAC only signs the raw body, letting the `shop` (and `topic`) header be forged for cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` checks the `hmac` field against exactly that signable string [2](#0-1) . None of the `shop`, `topic`, `webhook-id`, or `api-version` values — all pulled straight from unauthenticated HTTP headers via `shopify_header` [3](#0-2)  — are covered by the signature. `Registry.process` nonetheless treats HMAC success as proof the whole request "did indeed come from Shopify" (per the gem's own documentation) and immediately forwards the unauthenticated `request.shop` into the app-facing `WebhookMetadata` used to dispatch/attribute the event: [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac_verified_bytes == bytes_used_to_identify_the_tenant`. Instead, `hmac_verified_bytes = raw_body` while `tenant_identifier_used = header["shop-domain"]`, an entirely different, unsigned byte range. Any party capable of producing one valid `(raw_body, hmac)` pair — e.g. a merchant who has installed the app and thus legitimately receives real Shopify webhooks with a valid HMAC for their own shop, or anyone who otherwise obtains a genuine webhook body/HMAC pair for a given payload — can resend that exact body/HMAC combination while substituting a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header value. `HmacValidator.validate` will still return `true` because it never inspects the header values [5](#0-4) , and `Registry.process` will dispatch the handler believing the event legitimately originates from the forged shop [6](#0-5) .

This is the same bug class as the report: a field acted on downstream (here, the tenant/shop identity used to route and attribute the webhook) is not covered by the integrity check (here, the HMAC), so the two states — "what was cryptographically verified" and "what was actually used" — diverge after the attacker's crafted request.

### Impact Explanation
Applications built on this gem are told by its documentation that `Registry.process` "will verify the request did indeed come from Shopify," and are given `data.shop` as the trusted tenant key with which to update per-shop records (see the documented handler example calling `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). A forged `shop` header lets an attacker cause the receiving application to process/attribute webhook data under a victim shop's tenant context — a cross-tenant confusion/injection condition, which per the impact rubric falls under Critical (cross-tenant access).

### Likelihood Explanation
Exploitability depends on the attacker having at least one legitimate `(raw_body, hmac)` pair, which is trivially available to anyone who has installed the app on any shop (every Shopify webhook delivered to the app is a valid pair for that install). No access to `api_secret_key`, access tokens, or the app's `client_secret` is required — only a normal, valid webhook the attacker's own shop received, replayed toward the app's webhook endpoint with a modified `shop-domain` header.

### Recommendation
Include the trusted header values (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-verified signable string, or otherwise cryptographically bind them to the body before `Registry.process` trusts `request.shop`/`request.topic` to construct `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook delivery with a valid `X-Shopify-Hmac-Sha256` for some `raw_body`.
2. Attacker captures that `(raw_body, hmac)` pair.
3. Attacker resends a POST to the app's webhook endpoint with the identical `raw_body`/`hmac`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` returns `true` (only `raw_body` is checked) [2](#0-1) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , causing the app to act on/attribute attacker-controlled data to the victim tenant.
