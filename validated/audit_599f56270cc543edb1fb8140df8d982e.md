### Title
Webhook `shop`/`topic`/`webhook_id` fields are trusted despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from HTTP headers, none of which are covered by that HMAC. This breaks the identity binding `HMAC-verified bytes == data acted upon`, letting a caller with any one valid `(raw_body, hmac)` pair for the app (e.g. captured from their own shop's genuine webhook, since the HMAC secret is per-app, not per-shop) replay it while freely rewriting the `shop-domain` header to impersonate a different merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers, which are not part of the signed payload: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that the *body* HMAC matches), then immediately builds `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` and hands it to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`/`client_secret`) is scoped to the app, not to an individual shop, any shop that has the app installed can obtain a valid `(raw_body, hmac)` pair from its own genuine webhook deliveries. Since the `shop-domain` header is never bound to that HMAC, an attacker can replay the exact same `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value. `Registry.process` will accept it (HMAC over the body still matches) and hand the handler a `WebhookMetadata` claiming to be from the victim shop with attacker-controlled body content — a cross-tenant identity confusion: the equality the code implicitly assumes, `hmac_valid(raw_body) == shop_header_is_authentic`, does not hold.

### Impact Explanation
This crosses a tenant boundary: a handler that keys any per-shop side effects (data storage, entitlement checks, sync triggers, uninstall/GDPR handling, etc.) off `WebhookMetadata#shop` can be made to act on behalf of a shop the attacker does not control, using content the attacker fully controls (subject to whatever body shape their own real webhook had). This matches the "cross-tenant access" Critical impact category, since the shop-identity binding that gates per-tenant behavior is not authenticated by the gem despite HMAC validation succeeding.

### Likelihood Explanation
Exploitability requires only: (1) the attacker's own shop has the app installed (any developer/free shop qualifies) so they can capture one genuine `raw_body` + `hmac-sha256` pair for a webhook topic they want to spoof, and (2) the app's webhook endpoint is reachable over the internet, which it is by design (Shopify calls it as a plain HTTPS webhook). No secret material or privileged access is required beyond normal app installation. The main constraint is that the replayed body content is fixed to whatever the attacker's own shop's webhook produced, which limits which fields can be manipulated, but `shop`, `topic`, `webhook_id`, and `api_version` are fully attacker-controlled regardless of body content.

### Recommendation
Bind the identity-relevant fields into the HMAC-covered payload, or otherwise cryptographically tie the `shop-domain`/`topic`/`webhook_id` headers to the signed content — e.g., include them in `to_signable_string`, or require the host application to independently confirm `request.shop` corresponds to a shop with an active session/installation before trusting `WebhookMetadata#shop` in `Registry.process`. At minimum, document prominently that `shop`, `topic`, and `webhook_id` are unauthenticated and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook (e.g. `orders/create`) and capture the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` Shopify sent (valid because it's HMAC'd with the app's shared `api_secret_key`).
2. Send a new POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid since body is unchanged), but `x-shopify-shop-domain: victim.myshopify.com` and any desired `x-shopify-topic`/`x-shopify-webhook-id`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H`.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, so the app now processes attacker-supplied content as if it came from the victim shop. [3](#0-2) [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
