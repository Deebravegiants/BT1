### Title
Webhook shop-domain identity spoofing via unauthenticated header (HMAC covers body only, not shop) - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::HmacValidator` verifies the HMAC signature exclusively over the raw request body. The shop identity delivered to the app's webhook handler (`WebhookMetadata#shop`) is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material. Any party that possesses one genuine, validly-signed webhook body/HMAC pair for the app (e.g., a merchant who has installed the app on their own store and receives real webhooks) can replay that exact body/HMAC while substituting an arbitrary `shop-domain` header value. `Registry.process` will accept it as valid and hand the handler a `WebhookMetadata` whose `shop` does not correspond to the entity that actually authorized/produced the body.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(... secret, verifiable_query.to_signable_string)` and compares it against the header-supplied HMAC [5](#0-4) . For webhook requests, `to_signable_string` is defined to be just `@raw_body` [1](#0-0) , and `shop` is parsed independently from the `shopify-shop-domain` header [2](#0-1) . Because the HMAC only binds the body bytes to the secret, the header carrying the identity of the shop is never covered by the signature — the equality the design implicitly assumes, `hmac_verified_originating_shop == request.shop`, does not actually hold. `Registry.process` raises only if the HMAC over the body fails [6](#0-5) , then unconditionally builds `WebhookMetadata` using `request.shop` from the header and dispatches it to the app's handler [7](#0-6) . This is precisely the bug-class analog called out in the task: a field (the shop identity) that is acted upon by the consumer but not covered by the cryptographic check (HMAC).

Because the same `api_secret_key` is shared by the app across all shops that install it, any merchant who installs the app legitimately can obtain a genuinely-signed webhook body (for their own shop) and then resend it to the app's webhook endpoint with the `shop-domain` header swapped to name a different, victim shop that also uses the app. The gem will report this as a validly-authenticated webhook for the victim shop.

### Impact Explanation
Apps built on this gem are documented to treat `data.shop` as the authoritative shop/tenant identifier for post-webhook processing (e.g., looking up the shop's session/access token, associating the delivered `body` with that shop's records) [4](#0-3) . An attacker-controlled shop can therefore inject data that the host app attributes to a different, arbitrary tenant, corrupting cross-tenant state or triggering shop-scoped side effects (e.g., data deletion/redaction flows for `MANDATORY_TOPICS` such as `shop/redact`) under a spoofed shop identity [8](#0-7) . This crosses a tenant boundary without needing the app's `client_secret`, an access token, or any privileged credential beyond installing the app on one's own store — matching the "cross-tenant access" High/Critical impact criteria.

### Likelihood Explanation
Any merchant capable of installing the target app on a store they control can trivially capture a legitimate webhook delivery (body + HMAC) and replay it with a modified `X-Shopify-Shop-Domain` header to the same public webhook endpoint. No secrets, tokens, or privileged access are required beyond normal app installation, which is available to any Shopify merchant/unprivileged internet user.

### Recommendation
Bind the shop identity into the signed material checked by `HmacValidator`, or otherwise cryptographically/contextually verify that the `shop-domain` header matches the shop that legitimately owns the delivered webhook subscription (e.g., cross-check against the shop's own registered webhook/session state rather than trusting the header value outright). At minimum, document prominently that `WebhookMetadata#shop` is not authenticated and must not be used as a tenant-authorization key without an independent verification step.

### Proof of Concept
1. App installs shop A (attacker-controlled) and legitimately receives a real webhook, e.g. body `{"id":1}"` with header `X-Shopify-Hmac-Sha256: <valid HMAC of body, using the app's api_secret_key>` and `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Attacker (as shop A) resends the exact same body and the exact same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: ..., headers: ...)` parses `shop` as `"victim-shop.myshopify.com"` [2](#0-1) .
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body bytes against the (unchanged, valid) HMAC [9](#0-8) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)`, causing the host app to process attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
