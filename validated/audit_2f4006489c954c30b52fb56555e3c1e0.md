**Analysis:** The claimed bypass does not exist in the code. `CrossShardStateView::get_state_value` has only two mutually exclusive branches keyed on a single `HashMap` lookup: [1](#0-0) 

If a `state_key` is present in `cross_shard_data` (i.e., it was declared as a cross-shard dependency during `create_cross_shard_state_view`), the function unconditionally calls `RemoteStateValue::get_value()`, which blocks on a `Condvar` until the status transitions from `Waiting` to `Ready`: [2](#0-1)  There is no branch that lets a registered key fall through to `base_view` — that fallback (`self.base_view.get_state_value(state_key)`) is only reached when the key is *absent* from `cross_shard_data`, meaning it was never declared as a dependency in the first place. Since `cross_shard_data` is populated up front from the declared `required_edges_iter()` of all transactions in the block [3](#0-2) , an attacker cannot cause the same `get_state_value` call, for a key that *is* registered, to instead resolve via `base_view`. The two code paths are deterministic and mutually exclusive on a single `HashMap::get` result within one function invocation — there is no race window between "checking membership" and "choosing which value source to read," so the described TOCTOU-style bypass is not constructible.

The proof idea in the question ("register a `state_key`... but issue the read through `base_view` fallback path") presupposes a code structure that lets a caller independently choose which branch executes for the same key, which is not how the function is written. This does not cross a real custody boundary; it is a mischaracterization of the control flow rather than an exploitable defect.
