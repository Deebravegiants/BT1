### Title
Webhook shop/topic identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop`, `topic`, and `webhook_id` values that are subsequently trusted and handed to the app's handler are read from HTTP headers that are **not** part of the signed content, breaking the binding between "the bytes the HMAC vouches for" and "the shop the app acts on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read directly from HTTP headers and are never mixed into the signed string: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string`: [3](#0-2) 

`Registry.process` relies on that same HMAC check and then trusts `request.shop`/`request.topic` (taken from headers) to build the `WebhookMetadata` that is dispatched to the app's handler: [4](#0-3) 

Because the signature only binds the body, an attacker who legitimately installs the app on their own shop (Shop A) will receive genuine, correctly-signed webhooks (valid `hmac-sha256` header for that body, since Shopify signs it with the app's `client_secret`/`api_secret_key`). The attacker — an otherwise unprivileged internet user with respect to any other merchant — can replay that same body and valid HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header to claim to be Shop B. `Registry.process` will accept it: `Utils::HmacValidator.validate(request)` still passes because it only checked the body bytes, and the handler receives `WebhookMetadata` attributing the payload to Shop B.

The broken identity equality is: `shop authenticated by the HMAC (none, since shop is unsigned) ≠ shop trusted and passed to the handler (header value)`.

### Impact Explanation
Any app logic that keys off `WebhookMetadata#shop` (e.g., looking up that shop's session/access token, updating per-shop state, or triggering shop-scoped side effects) can be made to act as if the request came from an arbitrary target shop domain, using a payload/signature pair the attacker legitimately obtained for their own store. This is a cross-tenant confusion: data or actions intended for one tenant get attributed to another tenant purely by header manipulation, without needing the target shop's credentials.

### Likelihood Explanation
Any developer/attacker can install the app on a shop they control to obtain a validly-signed webhook body+HMAC pair, then send an HTTP request directly to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No secrets, tokens, or privileged access to the target shop are required — only the ability to send an HTTP request, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content that is authenticated, or otherwise cryptographically bind the header-derived identity fields to the signed body (e.g., require the caller to additionally verify shop/topic against out-of-band registration state, or fold them into the HMAC input) before they are trusted and forwarded to the handler in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-controlled Shop A; trigger a webhook event to receive a real request with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `api_secret_key`).
2. Replay an HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a shop the attacker does not control) and optionally a different `X-Shopify-Topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (== `B`) against `H` — validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)`, causing the app to process/act on data as if it originated from Shop B.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
