## Title
Permissionless AMM PDA Front-Running via Unvalidated `market` Seed in `Initialize2` — Permanent DoS of Pool Creation - ([File: program/src/processor.rs])

### Summary
`process_initialize2` derives every deterministic PDA for a pool (`AmmInfo`, `TargetOrders`, LP mint, coin vault, pc vault) solely from the caller-supplied `market_info` account key, without validating that `market_info` is owned by a market program or otherwise authorized [1](#0-0) . Any unprivileged user can call `Initialize2` first with an arbitrary `market` pubkey (that a legitimate project intends to use) and attacker-controlled mints/vaults, permanently claiming the PDAs for that market and blocking the legitimate pool creator.

### Finding Description
In `process_initialize2`, the market account comments explicitly state it is "Just a seed for AMM account. Can be any account" and it is never checked against a real market program or ownership constraint [2](#0-1) [3](#0-2) . The only signer/authority requirement in the instruction is on `user_wallet_info`, the caller itself [4](#0-3) .

`market_info.key()` is then used as the sole seed (besides fixed literal seeds) to derive the addresses for the `AmmInfo`, `TargetOrders`, LP mint, coin vault, and pc vault PDAs via `generate_amm_associated_account`, `generate_amm_associated_spl_mint`, and `generate_amm_associated_spl_token` [5](#0-4) [6](#0-5) . Because these derivations depend only on `market_account.key()`, `program_id`, and a fixed literal seed, the resulting addresses are fully deterministic and reproducible by anyone who knows the target `market` pubkey.

Each of these helper functions guards against re-initialization by checking `associated_token_account.owner == system_program_account.key` and returning `AmmError::RepeatCreateAmm` if the account is already assigned to a non-system owner [7](#0-6) [8](#0-7) . This means whoever calls `Initialize2` first for a given `market` key permanently claims all downstream PDAs tied to it.

An attacker can front-run a legitimate pool creator by:
1. Observing (or predicting) the `market` pubkey a legitimate project intends to use for their Raydium pool.
2. Calling `Initialize2` first with that `market` key, but with attacker-chosen/worthless coin and pc mints and a tiny `init_coin_amount`/`init_pc_amount` (just above zero to pass the `InvalidSupply` check) [9](#0-8) [10](#0-9) .
3. Successfully initializing the `AmmInfo`, `TargetOrders`, LP mint, coin vault, and pc vault PDAs for that market key with worthless/malicious content.
4. Permanently locking the legitimate project out: when they later attempt their own `Initialize2` for the same `market`, the associated PDAs already exist and are owned by the program, so every one of the `generate_amm_associated_*` calls returns `AmmError::RepeatCreateAmm`.

This is directly analogous to Impact 2 in the referenced report ("Denial-of-Service for Legitimate Admin Oracle Account Creation"): the PDA is derived from a caller-supplied, non-signing, unvalidated key, allowing pre-emptive squatting that locks out the legitimate party.

### Impact Explanation
This results in permanent denial of service for legitimate pool creation on a specific market: once an attacker has claimed the PDAs, the intended pool operator can never initialize a valid Raydium AMM pool for that market via `Initialize2`, since the deterministic PDAs are already occupied by the attacker's fake pool. This is a griefing/DoS vector against pool creators reachable purely by an unprivileged user submitting a single transaction with attacker-chosen accounts and data — no funds of the legitimate creator are directly stolen, but their intended market/pool becomes permanently unusable through this program.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to know or guess the target `market` pubkey before the legitimate operator submits their own `Initialize2` transaction. This is plausible in practice because market accounts (e.g., OpenBook/Serum markets) are frequently created ahead of time and are publicly visible on-chain before the corresponding Raydium pool is initialized, giving attackers a window to front-run with minimal cost (a single transaction with negligible token amounts).

### Recommendation
- Validate that `market_info` is owned by an expected/whitelisted market program (or otherwise authenticate it) before using it as a PDA seed, rather than accepting "any account" as documented in the code comments.
- Alternatively, incorporate a value under the control of the legitimate creator (e.g., require `market_info` or an additional creator-authorized key to be a signer, or bind PDA derivation to the coin/pc mint pair plus creator authority) so that PDA addresses cannot be squatted by an unrelated third party before the legitimate initialization transaction.
- Consider adding a mechanism to reclaim/close PDAs that were initialized with degenerate/negligible liquidity, so front-run squats can be cleaned up.

### Proof of Concept
1. Attacker observes a `market` pubkey `M` that a legitimate project will use for their upcoming Raydium pool (visible on-chain once the market is created, before the Raydium pool is initialized).
2. Attacker creates two throwaway SPL mints `fake_coin` and `fake_pc`, mints `1` unit of each to attacker-controlled token accounts.
3. Attacker calls `initialize2` (per `program/src/instruction.rs` builder) with `market = M`, `amm_coin_mint = fake_coin`, `amm_pc_mint = fake_pc`, `init_coin_amount = 1`, `init_pc_amount = 1`, and the correctly derived `amm_authority`/`amm_config`/PDA addresses computed from `M`.
4. `process_initialize2` succeeds: it only checks `amm_authority`, `amm_config`, mint distinctness, vault ownership/supply > 0, and LP mint state — none of which reference the legitimate market's real mints or reject an arbitrary `market` key [11](#0-10) . The PDAs derived from `M` for `AmmInfo`, `TargetOrders`, LP mint, coin vault, and pc vault are now permanently owned by the Raydium program with attacker-controlled worthless content.
5. When the legitimate project later calls `initialize2` with the same `market = M` and their real mints, every `generate_amm_associated_*` call detects `associated_token_account.owner != system_program_account.key` and returns `AmmError::RepeatCreateAmm`, permanently blocking their pool creation for market `M`.
