### Title
`fungible_asset::withdraw_sanity_check_impl` uses `object::owns`, whose self-address short-circuit lets anyone drain a `FungibleStore` whose address equals the store's owner field - ([File: aptos-move/framework/aptos-framework/sources/object.move])

### Summary
`object::owns(object, owner)` is documented as "return true if the provided address has indirect or direct ownership of the provided object" and is used as the sole authorization check that gates fungible-asset withdrawal: `fungible_asset::withdraw_sanity_check_impl` calls `object::owns(store, owner_address)` and permission-denies only if it returns false. [1](#0-0)  But `owns` contains a self-referential short-circuit: before walking the real ownership chain, it checks `if (current_address == owner) { return true }`, where `current_address` is initialized to `object.object_address()` — the store's *own* address, not its owner. [2](#0-1)  This mirrors the reported Endpoint bug exactly: the authorization function accepts a "self" identity value (`address(this)` in the Solidity report; the object's own address here) as an implicit stand-in for a legitimately authorized principal.

### Finding Description
`withdraw_sanity_check_impl` is called with `owner_address = signer::address_of(owner)` — the caller's own address — and checks `object::owns(store, owner_address)`. [3](#0-2)  `owns` walks the object's ownership chain starting from `object.object_address()`, but before doing any real walk, it treats `owner == object_address` as automatic proof of ownership: `if (current_address == owner) { return true }`. [2](#0-1) 

Concretely: if a `FungibleStore` object happens to be created at (or be) an address that is itself a signer-controllable account address — which is exactly the case for resource accounts, code objects, and any object whose `ConstructorRef`/address a party can independently derive and later obtain signing capability for (e.g. via `create_resource_account`, `create_object_from_object`, or any deterministic/derived object address scheme) — then any signer holding that same address can call `fungible_asset::withdraw(owner, store, amount)` and pass the `owns` check purely because `signer::address_of(owner) == store.object_address()`, with **no traversal of the actual `ObjectCore.owner` field at all**. The real owner recorded in `ObjectCore.owner` is never consulted in this branch.

This differs from `is_owner`, which correctly compares against the *stored* `owner` field: `object.owner() == owner`. [4](#0-3)  `owns` was clearly intended as an extension of `is_owner` for indirect/nested ownership (object-owns-object chains), but its self-address short-circuit at the object's *own* address — rather than beginning the traversal at `ObjectCore.owner` — creates a bypass identical in shape to the reported `txnSender == address(this)` special case.

### Impact Explanation
`fungible_asset::withdraw` (and by extension anything built on `withdraw_sanity_check`, including `dispatchable_fungible_asset::withdraw`) is the primary custody gate for extracting value out of a `FungibleStore`. [5](#0-4)  If any deployed pattern creates a `FungibleStore` object address that coincides with an address a non-owner can sign for (derived/resource-account addresses, deterministic object addresses reused across modules, or objects nested such that an intermediate object's own address matches a caller-controlled address), the true store owner's asset can be withdrawn by that caller without ever satisfying the intended "owner or ancestor-in-ownership-chain" invariant. This is a direct custody violation: theft of fungible-asset value bypassing the owner-authorization check, which is explicitly in-scope under "Fungible asset metadata, primary and secondary stores, dispatchable hooks, and freeze state must preserve supply and holder identity."

### Likelihood Explanation
Exploitability depends on being able to make `owner_address == store.object_address()` for a store you do not actually own. This requires colliding/deriving object and store addresses with signer-controlled addresses, which is architecture-dependent (e.g., via resource accounts or object-nesting patterns where module code stores a `FungibleStore` directly at a `signer`-derivable address, or via `object::create_object_from_object` chains). I was not able to fully verify a concrete, reachable production callsite where a `FungibleStore`'s object address is guaranteed/likely to equal a value a non-owner signer controls — this needs further live tracing of `create_store`/`create_named_object` seed derivation across framework and ecosystem modules, which the index does not fully cover. Given index-size limits, some framework/ecosystem module contents were not retrievable; a full Devin session with complete repo access is recommended to confirm concrete reachable callsites (e.g., specific object/resource-account seed schemes used with `fungible_asset::create_store`) and produce a working PoC transaction sequence.

### Recommendation
Fix `object::owns` so the self-address short-circuit is removed or corrected to only match against `ObjectCore.owner` (i.e., start the loop check from `object.owner`, not `object.object_address()`), consistent with `is_owner`. Concretely, change:
```
let current_address = object.object_address();
...
if (current_address == owner) { return true };
```
to initialize `current_address` from `borrow_global<ObjectCore>(object.object_address()).owner` before any equality short-circuit, and audit all custody-sensitive callers of `object::owns` (notably `fungible_asset::withdraw_sanity_check_impl`) for correctness with the corrected semantics.

### Proof of Concept
Conceptual PoC (needs live-chain confirmation given the address-collision precondition noted above):
1. Create a `FungibleStore` object whose `object_address()` equals an address `A` that is *not* the actual `ObjectCore.owner` but for which an attacker can obtain a `signer` (e.g., via a resource-account signer capability or via `create_signer` in an object-extension flow tied to address `A`).
2. Attacker calls `fungible_asset::withdraw(attacker_signer_for_A, store, amount)`.
3. `withdraw_sanity_check_impl` calls `object::owns(store, A)`; since `store.object_address() == A`, the function short-circuits to `true` on the first line, bypassing the real `ObjectCore.owner` check.
4. Funds are withdrawn to the attacker without ever satisfying real ownership. [2](#0-1) [6](#0-5)
