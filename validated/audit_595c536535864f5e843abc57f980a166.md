### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then trusts `request.shop` as the tenant identity forwarded to the app's handler, breaking the binding `HMAC-signed content == identity used for tenant dispatch`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is included in the signable string. The `shop` accessor is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., only the body: [3](#0-2) 

`Registry.process` checks that HMAC and then immediately forwards the unauthenticated `request.shop` (and `request.topic`) to the registered handler as the trusted tenant identity: [4](#0-3) 

The gem's own documentation instructs apps to use `data.shop` directly to route/queue tenant-scoped work, confirming that this field is treated as authenticated tenant identity by design: [5](#0-4) 

Because the webhook signing secret (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant who installs the app on their own (attacker-controlled) shop can trigger a real webhook and legitimately receive a body + valid HMAC signed by Shopify. Since that signature covers only the body — not the `shop-domain` header — the attacker can replay the exact same body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain. `HmacValidator.validate` still passes because the body is unchanged, but `Registry.process` hands the handler a `WebhookMetadata` claiming the event originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary `shop claimed by request == shop that actually generated/authorized the signed content`. A host application that (as documented) uses `data.shop` to select which merchant's records to update, queue jobs against, or look up sessions for, can be made to process attacker-supplied webhook bodies under a victim shop's identity — a cross-tenant data-integrity/confusion issue reachable by any unprivileged party able to install the app on their own store, without needing the app's `api_secret_key`, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented pattern of trusting `data.shop`/`data.topic` for tenant dispatch: the attacker only needs to be able to install the target app on an attacker-owned shop (a normal, unprivileged action for any Shopify merchant/dev-store owner) to obtain a validly-signed body, then can replay it against the webhook endpoint with a forged `shop-domain` header using any standard HTTP client.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the HMAC-signed payload — e.g., derive `to_signable_string` from a canonical representation of headers used for identity plus the raw body — so header spoofing cannot bypass the HMAC. At minimum, document prominently that `data.shop`/`data.topic` are not part of the signed content and must not be trusted for tenant-scoping decisions without additional verification (e.g., cross-checking against a shop that is known to have an active webhook subscription/session).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`) with body `B`. Shopify signs the request with `HMAC-SHA256(api_secret_key, B)` and delivers headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H`.
2. Attacker captures `(B, H)` and sends a new POST request directly to the app's webhook endpoint with the same body `B` and HMAC header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` builds `Request` from these headers; `Utils::HmacValidator.validate` succeeds because `to_signable_string` (`@raw_body`) and `hmac` match — the shop header is irrelevant to the check.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, i.e., the app processes attacker-controlled data as if it were an authentic event from the victim shop.
