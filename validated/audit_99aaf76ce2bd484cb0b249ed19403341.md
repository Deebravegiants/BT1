### Title
Tokens transferred directly to the Controller are permanently locked with no recovery path - (File: contracts/controller/src/payments.rs)

### Summary
The XOXNO Lending controller contract can receive SAC token balances via direct `token.transfer`, but exposes no entrypoint that can move a pre-existing balance out. Every outbound token path in the controller is measured as a balance *delta* over a snapshot taken inside the same invocation, so any balance that existed before the call is deliberately preserved and can never be claimed. This is the Soroban analog of ETH locked in a contract with no withdrawal function.

### Finding Description
The controller's only generic outbound-transfer helper is `refund_controller_balance_delta` in `contracts/controller/src/payments.rs:41-52`, which computes `balance_delta_since(env, asset, &controller, balance_before)` — the increase *since a snapshot* — and forwards only that excess. The docstring states the intent: "Refunds only the controller balance increase since `balance_before`, preserving the pre-existing balance."

The same measured-delta discipline applies everywhere else:

- `claim_revenue` forwards only the measured receipt from the pool for that call; a pre-existing controller balance is untouched (pinned by `tests/test-harness/tests/controller/outbound_transfer_measurement.rs:148-151`, which asserts `controller_after == controller_before` even with a large stranded dust balance present).
- `migrate_from_blend` refunds only the measured delta and explicitly ignores pre-existing controller balances (`tests/test-harness/tests/strategy/migrate_blend.rs:497-535` asserts the stuck balance "must remain (not used as refund or swept)").
- The protocol's own regression suite acknowledges the stranding: `tests/test-harness/tests/controller/recipient_is_protocol_contract.rs:1-5` documents that tokens sent to the controller are "funds no balance-delta measurement can ever claim," and borrow/withdraw to the controller are rejected precisely because the transfer would strand tokens.
- No `sweep`/`rescue`/`recover` function exists in `contracts/controller/src/` (grep returns only unrelated "recovery" wording in strategy comments). Unlike the swap-aggregator, which provides `sweep_balance` for stray tokens (`contracts/swap-aggregator/tests/unit/sweep.rs`), the controller has no equivalent.

Because the controller is a contract address like any other, an unprivileged sender can call `token::Client::transfer(sender, controller, amount)` on any listed or unlisted SAC. The tokens arrive, belong to no account, no market book, and no refund delta, and no entrypoint — public or administrative — can move them.

### Impact Explanation
Permanent freezing of funds: any token balance held by the controller address is unrecoverable by anyone, including governance and the token sender. Beyond direct accidental transfers, callback-adjacent flows (flash receivers, swap routes, Blend/DeFindex integrations) can leave residual balances at the controller mid-flow; the measured-delta design means those residuals silently accumulate as permanently dead balances rather than being reclaimable. The pool-side analog does not apply — donations to the pool remain spendable custody backing exits — so the stranding is specific to the controller.

### Likelihood Explanation
Low-to-moderate per incident but structurally guaranteed over time: users and integrated contracts routinely send tokens to contract addresses observed in transactions (the controller address appears as sender/recipient in supply, repay, liquidate, and strategy flows). Each stray transfer permanently locks whatever amount is sent. The codebase already hardens the *protocol-initiated* side of this class (rejecting borrow/withdraw to the controller with `INVALID_FLASHLOAN_RECEIVER`), which demonstrates the authors consider controller-held balances irrecoverable — yet the externally-initiated transfer direction remains open and unrescuable. Severity Medium, matching the source report: losses are self-inflicted/accidental rather than attacker-extractable, but irreversible.

### Recommendation
Add a recovery path for stray controller balances. Options consistent with the existing design:

- A permissionless `sweep_stray(asset, to)` that transfers only the balance *in excess of* any in-flight obligation (in practice, the full balance minus nothing, since the controller books no token balance — it can transfer the entire `balance(controller)` for assets it never custodies by design), or
- A governance-gated `sweep_balance(recipient, assets)` mirroring the swap-aggregator's `sweep_balance`, restricted to tokens with no protocol accounting claim on the controller.

Any sweep must keep the measured-delta invariant intact: snapshots taken in `snapshot_balances` / `balance_delta_since` within a transaction must not be spoofsable by a nested sweep call mid-operation (Soroban's atomicity means a sweep in a separate transaction is safe; a sweep invocable as a callback target would need the flash/reentry guard).
