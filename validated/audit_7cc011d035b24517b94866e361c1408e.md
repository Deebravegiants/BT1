The `WebhookMetadata.shop` field, which is documented as the primary tenant identifier apps should use to route webhook data (`docs/usage/webhooks.md:14`), is populated directly from an unauthenticated header value rather than anything covered by the HMAC signature.

### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body [1](#0-0) , while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the HMAC at all [2](#0-1) . `Registry.process` verifies only the body's HMAC and then constructs `WebhookMetadata` using this unauthenticated `shop` value [3](#0-2) .

### Finding Description
This mirrors the report's bug class: a signature that authenticates only part of the semantically relevant data, letting an attacker supply a validly-signed payload in a different identity context than the one it was signed for. Here, Shopify signs webhook bodies with the app's `client_secret`, which is the **same secret for every shop** that has the app installed. Any merchant that installs the app can obtain genuine `(raw_body, hmac)` pairs for their own shop (either by receiving a real webhook or by triggering one through normal store activity). Because `shop` is never part of `to_signable_string`, that attacker can replay the exact same `raw_body`/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value (e.g., a victim shop that also has the app installed). `HmacValidator.validate` will report success since it only recomputes the HMAC over `raw_body` [4](#0-3) , and `Registry.process` passes the attacker-chosen `request.shop` straight into `WebhookMetadata` [5](#0-4) . The `shop` field is exactly the field documented and intended for tenant routing [6](#0-5) , so a host app following the gem's documented pattern will process attacker-controlled data under the victim's tenant identity. This breaks the intended binding: `shop that produced/authorized the signed payload == shop attributed to that payload by the gem`.

### Impact Explanation
This is a cross-tenant issue: an authenticated merchant of the app can cause data purportedly belonging to their own shop's webhook event to be attributed to a different, victim shop, since the gem itself supplies an unauthenticated `shop` value as the tenant key in `WebhookMetadata`. Any host application processing webhook data keyed by `data.shop` (the documented, intended usage) can be tricked into writing or acting on the attacker's payload as if it originated from the victim shop.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, independent merchant using the same app (a normal, low-privilege actor for a multi-tenant Shopify app), be able to obtain one genuine signed webhook body for their own shop, and be able to send an arbitrary HTTP request to the app's public webhook endpoint with a forged `shopify-shop-domain` header — all of which are within reach of any unprivileged internet user who installs the app on their own store.

### Recommendation
Include the shop domain (and ideally the webhook id or topic) inside the signed/verifiable content, or otherwise cryptographically bind the claimed `shop` to the signed body — for example by validating that `shop` matches a shop associated with a currently registered/active session before constructing `WebhookMetadata`, rather than trusting the raw header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and, through normal use, causes Shopify to deliver a real webhook, capturing `raw_body` and its `x-shopify-hmac-sha256` value (both valid because Shopify signs with the app's single `client_secret`, shared across all shops).
2. Attacker sends a POST to the app's webhook route with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a shop that also has the app installed).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [7](#0-6) .
4. `WebhookMetadata.new(shop: request.shop, body: request.parsed_body, ...)` is built with `shop = "victim-shop.myshopify.com"` and the attacker's body content [5](#0-4) .
5. The host app's handler (following the documented pattern of keying persistence/business logic on `data.shop`) processes the attacker's payload as belonging to the victim shop.
