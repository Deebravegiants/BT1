### Title
Bandwidth is irrecoverably consumed for requests that fail routing after the gate charge - (File: `parachain/runtimes/gargantua/src/ismp.rs`)

### Summary
`ProxyModule::on_accept` charges the sending app's bandwidth subscription for the full encoded size of every non-purchase POST request *before* determining whether the request can actually be routed to a destination module. When the destination module lookup fails (unknown `pallet_id`) or the request is otherwise not deliverable, the function returns an `Err`, but the bytes already deducted by `try_consume` are never refunded.

### Finding Description
`try_consume` is called unconditionally (for non-purchase messages) at the very top of `on_accept`, deducting `bytes = encode_post_request(&request).len()` from the `(source, app)` subscription list managed by `pallet-bandwidth`'s `Allowance` storage [1](#0-0) . Only after this charge does the code check `request.dest` and, for local delivery, resolve `pallet_id` via `ModuleId::from_bytes(&request.to)` and match it against known pallets; any unmatched id returns `Err(anyhow!("Destination module not found"))` [2](#0-1) .

The bandwidth pallet's only credit paths are `BandwidthCredited` (from a paid `purchase()` on `BandwidthManager.sol`) and `ForceCredited` (governance-only) [3](#0-2) . There is no compensating increment anywhere for a request whose gate charge succeeded but whose subsequent routing failed. This is structurally identical to the reported analog: a metered resource limit (`remaining_bytes` here, `dailyDebtIncreaseLimitLeft` there) is decremented on use but never restored when the corresponding operation does not actually complete/consume the underlying capacity it was charged for.

### Impact Explanation
An app that mis-targets `request.to` (wrong `pallet_id`) — or any request that is charged but subsequently rejected before actual delivery — permanently loses that portion of its paid-for bandwidth allowance with no way to recover it short of governance's `force_credit`. Because a tier purchase is a fixed, non-renewing, time-boxed allowance (`expires_at` fixed at purchase, never extends per the tier lifecycle docs), bytes lost this way are gone for the life of the subscription. Repeated misrouted/failed requests (e.g., a buggy or malicious app hammering an invalid `to` target, or requests aimed at the local Hyperbridge chain that then fail lookup) can exhaust a victim app's paid allowance without any successful message delivery, causing legitimate subsequent dispatches to be rejected by the gate (`GateError::Insufficient`/`NoAllowance`) — a liveness/DoS impact on the app's ability to use the bandwidth it paid for, and a permanent loss of the funds spent purchasing that bandwidth.

### Likelihood Explanation
Reachable by any account able to trigger a POST request accepted by the ISMP router for a bandwidth-managed `(source, app)` pair — i.e., any app already metered under `pallet-bandwidth` (a normal, expected configuration per the bandwidth docs) that sends a request with a `to` value not matching any registered `pallet_id`, or whose local-delivery module lookup otherwise fails after the gate charge. No special privilege is required; this is a straightforward consequence of the charge-before-validate ordering in `on_accept`, and can occur accidentally from an app misconfiguration or be triggered deliberately by any account.

### Recommendation
Reorder `on_accept` so bandwidth is only charged once destination routing has been resolved and delivery is guaranteed to be attempted (i.e., move the `try_consume` call after the `pallet_id` match succeeds / after non-local dispatch is confirmed routable), or add an explicit refund path in `pallet-bandwidth` that credits back the consumed bytes when the enclosing `on_accept` ultimately errors out before real delivery.

### Proof of Concept
1. Register a `BandwidthManager` for a source chain and configure a tier; have the app purchase bandwidth so its `(source, app)` subscription in `pallet-bandwidth::Allowance` has `remaining_bytes = N`.
2. Dispatch a non-purchase POST request from that app targeting the local chain (`request.dest == HostStateMachine::get()`) with `request.to` set to an arbitrary/unregistered module id (not `pallet_ismp_demo::PALLET_ID`, not the bandwidth pallet id, not `pallet_hyper_fungible_token::PALLET_ID`).
3. `ProxyModule::on_accept` executes `try_consume`, successfully deducting `encode_post_request(&request).len()` bytes from the app's subscription.
4. The subsequent `match pallet_id` falls through to `_ => Err(anyhow!("Destination module not found"))`, so no module ever processes the request and no delivery occurs.
5. Query `pallet_bandwidth::Pallet::<Runtime>::remaining(&source, &app)` — it reflects the deduction from step 3 with no corresponding credit, confirming the bytes are permanently lost despite the request never being delivered.
