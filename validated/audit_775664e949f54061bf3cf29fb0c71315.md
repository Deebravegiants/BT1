### Title
Uncounted-token theft via arbitrary CASE 2 calls in `EmporiumUpgradeable.runAction` - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only measures balance changes for tokens the caller lists in `circomData.erc20TokenAddresses`, yet the CASE 2 branch lets that same caller execute a fully arbitrary `op.endpoint.call{value: op.value}(op.callData)` against any contract, targeting any asset the Emporium happens to hold. Any ERC20/ETH/NFT position sitting on the Emporium that is simply omitted from the caller's own `erc20TokenAddresses` array (or the array is submitted empty, which is possible with a near-trivial proof) can be moved out to any attacker-chosen address with zero balance-diff enforcement, since the invariant check `BalanceChangeShouldBePositive()` is only evaluated per declared token index.

### Finding Description
The security invariant the code intends to enforce is:

`balancesAfter[i] - balancesBefore[i] + (-deltaAmountChanges[i] if negative) == amount handed to user as UTXO`, for every token `i` in `circomData.erc20TokenAddresses` [1](#0-0) 

This equality is never even computed for a token that the caller does not put in `circomData.erc20TokenAddresses`. `erc20TokenAddresses` is attacker-supplied, per-call data, not a fixed protocol-level list of "assets the Emporium may hold" [2](#0-1) .

Inside `runAction`'s loop, CASE 2 ("stateless") executes with an unrestricted target/payload — the only guard is a selector check preventing direct calls to `callHinkalWallet`/`doSendToRelay`: [3](#0-2) 

`verifyWallet` only checks the EIP-712 signature when `stack.signerAddress != address(0)`; when the caller sets `signerAddress == address(0)` (fully legal), the entire `ops` array — endpoint, callData, value — is unconstrained by any signature, and only gated by `calldataHash` equality that the attacker computes themselves off self-chosen data: [4](#0-3) [5](#0-4) 

Crucially, when `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and the caller sets `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose only public inputs are `emporiumMessage`, `timeStamp`, `calldataHash`: [6](#0-5) 

The circuit behind that path (`MainEVMCircuitMin`) has a single private input, `messageSeed`, freely chosen by the prover, with no nullifier, no Merkle-inclusion, no ownership proof of any UTXO whatsoever: [7](#0-6) 

So any unprivileged address can produce a trivially valid proof for a transaction that declares zero tokens, needs no real deposit, only an existing (public) Merkle root, and then drives `_externalTransact` → `Emporium.runAction` with `circomData.erc20TokenAddresses = []` and `deltaAmountChanges = []`. Both `getBalancesForArray` calls in `Hinkal.transact` and inside `runAction` iterate zero times, and the `BalanceChangeShouldBePositive` loop never runs at all: [8](#0-7) 

Meanwhile, the attacker's op inside that same call is a raw `endpoint.call(callData)` executed with `msg.sender == Emporium`. Any position the Emporium legitimately owns (e.g. an ERC4626 vault-share balance left by any prior op — the victim's or even the protocol's own — that was not withdrawn/fully accounted for, or plain leftover ETH/ERC20 dust, or an NFT) can be redeemed/transferred directly to an attacker-chosen address, e.g. `vault.redeem(shares, attacker, Emporium)`, since `owner == msg.sender == Emporium` satisfies standard ERC4626 authorization, and the payout never touches an address the balance loop is even watching.

Regarding the specific mechanism named in the prompt — routing proceeds through `circomData.relay` — that path is actually blocked: `relayerIsValid` requires `tx.origin == relay` and `isRelayInList(relay)` whenever `relay != address(0)`, so an unprivileged attacker cannot set `circomData.relay` to their own address [9](#0-8) . This does not save the protocol, however: the attacker never needs `payRelayFees`/`sendToRelayFromWallet` at all — they hard-code the destination address directly as an argument inside `op.callData`, bypassing the relay mechanism and the fee code entirely.

### Impact Explanation
Critical — direct theft of assets held by the Emporium contract (vault-share positions, dust ERC20/ETH balances, or NFTs) that are not part of the attacker's own declared `erc20TokenAddresses` set for that call. The attacker needs no ownership proof over the stolen asset and, via the empty-array/Min-circuit path, essentially no real funds or UTXO at all. This is repeatable per available leftover position and matches "executing calls or moving assets a wallet owner or prover never authorised" / direct theft of protocol/user-originated funds.

### Likelihood Explanation
Preconditions: (1) any ERC20/ERC4626-share/ETH/NFT balance sitting on the Emporium contract that is not part of the attacker's chosen token array for their exploit transaction (very easy to satisfy — the attacker fully controls `circomData.erc20TokenAddresses`, including submitting it empty); (2) a valid, publicly known historical Merkle root to satisfy `rootHashExists`; (3) ability to submit a Groth16 proof for `MainEVMCircuitMin`, which requires knowledge only of a self-chosen `messageSeed`. All of these are trivially satisfiable by an unprivileged EOA with no special role, at negligible cost, and the attack is repeatable for every leftover position discovered on-chain.

### Recommendation
Do not let `runAction`'s token-tracking domain be attacker-chosen per call. Either (a) maintain a protocol-enumerated, storage-tracked list of every ERC20/ERC721 address the Emporium can ever hold and force the balance-diff loop to run over that full set regardless of what the caller declares, or (b) disallow CASE 2 (`invokeWallet == false` / stateless) calls unless `stack.signerAddress != address(0)` and a valid EIP-712 signature authorizes the exact `ops` array — i.e., remove the `signerAddress == address(0)` bypass in `verifyWallet`, or restrict unsigned/stateless ops to a safelist of endpoints that cannot exfiltrate assets to arbitrary addresses. Additionally, reject `externalActionId == HINKAL_EMPORIUM_ACTION_ID` transactions with `erc20TokenAddresses.length == 0` unless `stack.ops` is provably empty or fully signature-gated, since the Min-circuit path currently allows executing arbitrary `ops` under a proof that requires no ownership of funds.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (registered as `onlyAllowedRecipient`), a mock ERC4626 vault, and mint/deposit so that the Emporium contract legitimately holds vault shares (simulate a prior op leaving them there, e.g. by directly transferring shares to the Emporium address to represent an unwithdrawn position).
2. As an unprivileged attacker EOA, craft `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: vault, invokeWallet: false, value: 0, callData: abi.encodeCall(vault.redeem, (shares, attacker, address(emporium)))})], ...}))`, `relay = address(0)`, `originalSender = attacker`, `rootHashHinkal` = an existing on-chain root, `calldataHash` computed locally to match `getHashedCalldata`.
3. Generate a `MainEVMCircuitMin` proof locally using a self-chosen `messageSeed` (no ownership requirements).
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
5. Assert: `vault`/underlying token balance of `attacker` increases by the value of `shares`; assert Emporium's shares balance decreases to 0; assert the transaction does not revert with `BalanceChangeShouldBePositive`; assert no UTXO/commitment was created for the stolen value (since `erc20TokenAddresses` was empty, `utxoSet` is empty).
