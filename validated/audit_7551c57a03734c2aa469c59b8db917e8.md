### Title
Stale storage-deposit cache lets `estimateWithdrawalFee` return `amount: 0n` after on-chain deregistration, producing a fee-less `ft_withdraw` intent and stuck/lost funds - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge.getCachedStorageDepositValue` only writes to its `LRUCache` when the destination account already has enough NEP-141 storage balance (`result[1] >= result[0]`), and it never invalidates on the account's real on-chain state changing. If the destination account is later deregistered on-chain (`storage_unregister`), a repeat `estimateWithdrawalFee` call within the 1‑hour TTL still returns the stale "no fee needed" tuple, causing `createWithdrawIntentPrimitive` to build an `ft_withdraw` intent with `storage_deposit: undefined`.

### Finding Description
The equality that should hold is: the `storage_deposit` field baked into the `ft_withdraw` intent by `createWithdrawIntentPrimitive` (via `getUnderlyingFee(feeEstimation, ..., "storageDepositFee")`) must reflect the **real on-chain** relationship between `minStorageBalance` and `userStorageBalance` for `destinationAddress` at execution time.

`getCachedStorageDepositValue` keys the cache purely on `${contractId}${accountId}` [1](#0-0)  and only stores the tuple when `result[1] >= result[0]` (i.e., only caches the "sufficiently funded, no fee" case) [2](#0-1) . Once cached with `ttl: 3600000` (1 hour) [3](#0-2) , `estimateWithdrawalFee` will keep reading that stale tuple and short-circuit to `amount: 0n, quote: null, storageDepositFee: 0n` regardless of the account's real state [4](#0-3) .

Exploit flow (attacker is the ordinary user, controlling `destinationAddress`'s keys and their own withdrawal):
1. Call `estimateWithdrawalFee` once while `destinationAddress` is registered on the NEP-141 token contract (`userStorageBalance >= minStorageBalance`). This primes the cache with the "no fee" tuple.
2. Call `storage_unregister` on the token contract for `destinationAddress` — a fully permissionless, self-authorized action any account holder can invoke.
3. Within the 1-hour TTL, call `estimateWithdrawalFee` again with the same `assetId`/`destinationAddress`. The cache hit returns the stale tuple, so `feeEstimation.amount === 0n`, `feeEstimation.quote === null`, and `underlyingFees[...].storageDepositFee === 0n`.
4. `createWithdrawalIntents` → `createWithdrawIntentPrimitive` builds the `ft_withdraw` intent with `storage_deposit: undefined` because `params.storageDeposit > 0n` is false [5](#0-4) .
5. When intents.near executes this intent, it uses `ft_transfer`/`ft_transfer_call` to `receiver_id` with no compensating `storage_deposit`. The contract-types schema explicitly documents: "NOTE: No refund will be made in case of insufficient `storage_deposit` on `token` for `receiver_id`" [6](#0-5) . Since the account is genuinely unregistered on-chain, the transfer fails and the funds are not refunded, leaving the withdrawal stuck pending manual intervention.

None of the existing guards prevent this: `validateWithdrawal` only checks address validity, token/destination collision and *account existence* (not storage registration) via a separate `accountExistenceCache` [7](#0-6) ; it does not re-check storage balance. There is no invalidation hook tied to `storage_unregister` events, and the cache is keyed only by `contractId+accountId` with no state fingerprint.

### Impact Explanation
The withdrawal intent debits the user's balance inside intents.near per `withdrawalParams.amount`, but the accompanying `ft_withdraw.storage_deposit` is wrongly `undefined`/0 because of the stale cache, while the destination is genuinely unregistered on the NEP-141 contract. Per the contract-types documentation, an insufficient `storage_deposit` leads to no refund on transfer failure — the withdrawal gets stuck (or funds are lost in transit), matching the "High: withdrawal stuck until manual intervention" category. This is repeatable by any user for any `assetId`/`destinationAddress` pair as long as they can toggle their own storage registration between two SDK calls inside the 1-hour cache TTL.

### Likelihood Explanation
Preconditions are trivial for an ordinary user: register (or already be registered) on the target NEP-141 token, call `estimateWithdrawalFee` once to prime the cache, call `storage_unregister` (a standard, permissionless NEP-141 action), then call `estimateWithdrawalFee`/withdraw again within the hour. No privileged access, relayer collusion, or contract bug is needed — only the SDK's own caching logic. This is realistically triggerable, though it primarily harms the same account that triggers it (self-inflicted) or a counterparty destination address if an integrator/solver controls when withdrawals for a shared destination are issued.

### Recommendation
Do not cache the "sufficient balance" branch indefinitely without invalidation, or shorten TTL drastically; better, re-validate `userStorageBalance` against the *current* on-chain value immediately before constructing the withdrawal intent (bypass cache) in `createWithdrawalIntents`, or invalidate/refresh the cache entry whenever the same `destinationAddress` is used for a withdrawal so stale "no-fee" entries cannot survive a state change. At minimum, cache only for very short TTL, or fetch fresh at intent-build time rather than trusting `feeEstimation` computed in a separate step.

### Proof of Concept
```ts
// direct-bridge.test.ts (vitest, mocking only the HTTP/RPC calls)
import { describe, it, expect, vi } from "vitest";
import * as internalUtils from "@defuse-protocol/internal-utils";
import { DirectBridge } from "./direct-bridge";

describe("DirectBridge stale storage-deposit cache", () => {
  it("returns stale amount:0 after on-chain storage_unregister", async () => {
    const bridge = new DirectBridge({ envConfig: {} as any, nearProvider: {} as any });

    const minStorageBalanceSpy = vi
      .spyOn(internalUtils, "getNearNep141MinStorageBalance")
      .mockResolvedValue(1_000_000n);

    const storageBalanceSpy = vi
      .spyOn(internalUtils, "getNearNep141StorageBalance")
      .mockResolvedValueOnce(2_000_000n) // call #1: registered, sufficient balance
      .mockResolvedValueOnce(0n);        // call #2: after storage_unregister, on-chain truth

    const params = {
      assetId: "nep141:token.near",
      destinationAddress: "alice.near",
      routeConfig: undefined,
    };

    // Call #1: primes cache with [1_000_000n, 2_000_000n] because 2_000_000n >= 1_000_000n
    const fee1 = await bridge.estimateWithdrawalFee({ withdrawalParams: params });
    expect(fee1.amount).toBe(0n);
    expect(fee1.underlyingFees.NearWithdrawal.storageDepositFee).toBe(0n);

    // Simulated on-chain state: alice.near called storage_unregister, real balance is now 0n
    // Real on-chain equality that SHOULD now hold: minStorageBalance(1_000_000n) > userStorageBalance(0n)

    // Call #2 within TTL: cache hit -> stale, does NOT re-query RPC
    const fee2 = await bridge.estimateWithdrawalFee({ withdrawalParams: params });

    // Assert the broken equality: SDK still thinks no fee is needed
    expect(fee2.amount).toBe(0n);
    expect(fee2.quote).toBeNull();
    expect(fee2.underlyingFees.NearWithdrawal.storageDepositFee).toBe(0n);

    // But the mocked second RPC call (never invoked due to cache hit) would have reported
    // userStorageBalance = 0n < minStorageBalance = 1_000_000n, i.e. storage IS required.
    expect(storageBalanceSpy).toHaveBeenCalledTimes(1); // proves RPC wasn't re-queried

    // Building the intent with the stale fee estimate omits storage_deposit entirely
    const intents = await bridge.createWithdrawalIntents({
      withdrawalParams: { ...params, amount: 500n } as any,
      feeEstimation: fee2,
    });
    const ftWithdraw = intents.find((i) => i.intent === "ft_withdraw") as any;
    expect(ftWithdraw.storage_deposit).toBeUndefined(); // BUG: should reflect 1_000_000n needed on-chain
  });
});
```
