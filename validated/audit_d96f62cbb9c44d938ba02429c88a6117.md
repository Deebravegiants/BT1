### Title
Batch withdrawals of the same token report the wrong destination/hash for one leg — `findMatchingWithdrawal()` matches by `assetId` only, not by index/destination - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain status of a specific withdrawal leg by scanning the PoA bridge API response and matching solely on `assetId` via `findMatchingWithdrawal()`. It ignores the `index`/`destinationAddress`/`amount` that uniquely identify a particular withdrawal leg inside a batched intent. When a single intent contains two or more withdrawals of the **same token** (e.g., split to two different destination addresses), both legs resolve to the same matched record, so the SDK reports the same status/`txHash` for both — misattributing completion of one leg to the other.

### Finding Description
`createWithdrawalIdentifier()` builds a `WithdrawalIdentifier` that carries `landingChain`, `index`, `withdrawalParams`, and `tx`, mirroring the equivalent HOT bridge/Omni bridge identifiers that do rely on `index` for matching (see `hot-bridge.ts`'s `describeWithdrawal`, which indexes `nonces[args.index]`). However, `PoaBridge.describeWithdrawal()` never uses `args.index`: [1](#0-0) 

and the matcher itself is explicitly assetId-only: [2](#0-1) 

The code comment even acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but nothing in `createWithdrawalIdentifiers()` (`packages/intents-sdk/src/core/withdrawal-watcher.ts`) or `PoaBridge.supports()` rejects or disambiguates same-asset batch withdrawals — the SDK's public batch-withdrawal API (`waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`) explicitly supports and indexes multiple legs per intent: [3](#0-2) [4](#0-3) 

So if `withdrawalParams` contains two entries with the same `assetId` (e.g., withdrawing USDC to address A and USDC to address B in one intent), `Array.prototype.find` in `findMatchingWithdrawal` returns the **first** withdrawal record matching that `assetId` for both legs. Both `describeWithdrawal` calls (index 0 and index 1) converge on the same `withdrawal.data.transfer_tx_hash` and `status`.

### Impact Explanation
This breaks the equality "status/hash reported == actual on-chain outcome of *that specific* withdrawal leg." Concretely:
- If leg A completes but leg B is still pending or failed, the SDK reports leg B as `completed` with leg A's `transfer_tx_hash` — an integrator polling per-leg promises (`createWithdrawalCompletionPromises`) would credit/mark leg B as done and release funds or confirmations based on a transaction hash that has nothing to do with leg B's actual destination.
- This is a status/hash misreport that can cause an integrator to double-credit (treat both legs as fulfilled from a single actual transfer) — matching the High-impact bucket "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Medium: it requires a caller to submit a batch withdrawal with two or more legs of the identical `assetId` (same underlying PoA token) in one intent — a valid, foreseeable usage pattern (e.g., splitting a large withdrawal across two destination addresses), and one that the SDK's granular batch-withdrawal design (`createWithdrawalCompletionPromises`, `watchWithdrawals`) is built to support generally. Nothing in `PoaBridge.supports()` or the withdrawal-identifier construction rejects or warns against this specific combination for the PoA route.

### Recommendation
Disambiguate matches using more than `assetId`: incorporate `destinationAddress` (and/or `amount`) into `findMatchingWithdrawal`, and when multiple PoA API records share the same `assetId`, consume matched records so each is only attributed to one local withdrawal index (e.g., mark used records, or sort both lists by amount as the existing comment suggests and pair them positionally). At minimum, `PoaBridge.supports()`/`createWithdrawalIdentifiers` should detect same-`assetId` legs within one batch and either reject them explicitly or fall back to a safer per-destination-address match.

### Proof of Concept
1. Submit one NEAR intent with two withdrawal legs, both `assetId: "nep141:eth.omft.near"`, but different `destinationAddress` (e.g., `0xAAA...` and `0xBBB...`), via `sdk.createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`.
2. PoA bridge indexer completes only the first leg (`0xAAA...`), returning one `COMPLETED` record with `near_token_id: "eth.omft.near"` and `transfer_tx_hash: "0xLegA"`.
3. `describeWithdrawal` is called for both index 0 and index 1 legs; `findMatchingWithdrawal(withdrawals, "nep141:eth.omft.near")` returns the same record for both because it does not consult `index` or `destinationAddress` (confirmed at [5](#0-4) ).
4. Both promises resolve `{ status: "completed", txHash: "0xLegA" }`, even though the `0xBBB...` leg never landed — an integrator relying on per-leg completion will incorrectly treat the second leg as fulfilled.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
