### Title
Unchecked ERC-20 `transfer` return value in `IntentGatewayV2.withdraw` (Tron variant) causes silent-failing token payouts and permanent loss of escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent tokens using a raw low-level `.call()` to `IERC20.transfer` and only checks that the call did not revert, never decoding/validating the boolean return value. Any input/output token used in an order that follows the non-reverting-`false`-on-failure ERC-20 pattern (very common on Tron/TRC20, e.g. USDT-style tokens) will cause the escrow accounting to be decremented and the order marked filled/refunded while the beneficiary receives nothing.

### Finding Description
`withdraw()` releases escrowed tokens to a beneficiary for both `RedeemEscrow` (fill) and `RefundEscrow` (cancel/timeout) flows: [1](#0-0) 

For every non-native token, the contract does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
This only checks that the external call itself did not revert; a low-level `call` returns `success = true` whenever the callee executes without reverting, **regardless of what boolean value `transfer` returns**. Many ERC20/TRC20 tokens (including well-known non-standard ones on the TRON/EVM ecosystem) return `false` instead of reverting on a failed transfer (e.g. insufficient allowance edge cases, blacklists, paused transfers). The code never decodes `returndata` to confirm `transfer` actually returned `true`.

Immediately after the unchecked transfer attempt, the accounting is unconditionally updated:
```solidity
_orders[body.commitment][token] -= amount;
```
and the order is marked filled (`_filled[body.commitment] = beneficiary;`) and an `EscrowReleased`/`EscrowRefunded` event is emitted, permanently finalizing the order regardless of whether tokens were actually delivered. The same unchecked pattern is repeated for the transaction-fee payout in the same function and for the `SweepDust` handler: [2](#0-1) [3](#0-2) 

`withdraw()` is reachable through the standard, unprivileged intent lifecycle: `onAccept` dispatches to `withdraw` for both `RedeemEscrow` and `RefundEscrow` request kinds after only `authenticate(incoming.request)` (source/dispatcher authentication, not any privileged-caller check on token semantics): [4](#0-3) 

and via `onGetResponse` for the refund-via-GET path: [5](#0-4) 

The input/output tokens used are arbitrary addresses chosen by the order-placing user in `placeOrder` (no token allow-list is enforced), so any user can create an order denominated in a token exhibiting this failure-without-revert behavior, and the resulting fill/cancel/refund will silently fail to deliver funds while the protocol's internal bookkeeping treats the order as settled.

This directly mirrors the reported `FootiumPrizeDistributor.claimERC20Prize` bug class: return value of `transfer` not checked, leading to loss of funds for the intended recipient while the contract records the claim/withdrawal as complete.

Note: the parallel non-Tron contract `evm/src/apps/intentsv2/IntentsBase.sol` uses OpenZeppelin's `safeTransfer` (`IERC20(token).safeTransfer(beneficiary, amount);`), which reverts on a `false` return, so that codepath is not affected — only the Tron variant’s manual low-level-call implementation.

### Impact Explanation
This is a High-severity fund-safety issue for the Hyperbridge intents protocol:
- The escrow record for the affected token is decremented and the order is marked `_filled`/refunded even though the beneficiary received zero tokens — the tokens remain permanently stuck in the `IntentGatewayV2` contract with no code path to re-claim them for that commitment (repeated calls revert with `UnknownOrder`/`Filled` once escrow is zeroed/order marked filled).
- This affects both the "fill" settlement path (solver/relayer delivering escrowed input tokens to the filler/beneficiary) and the "refund"/cancel path (returning a user's original deposit), meaning both solvers and end users can lose funds.
- Because token selection is user-controlled at order-placement time and not restricted to a known-safe list, any order denominated in a non-reverting-failure ERC20/TRC20 results in unbacked/lost escrow — a permanent freezing of funds condition.

### Likelihood Explanation
Likelihood is realistic: this requires no malicious admin, governance, or privileged actor — only a normal user placing an order (or the token itself misbehaving under ordinary conditions such as blacklist/pause) using a token that returns `false` on failed transfer instead of reverting, which is a well-documented, common real-world ERC20/TRC20 behavior class. Given Tron's ecosystem includes several long-standing tokens following the "return false, don't revert" convention, and the protocol is intended to support arbitrary ERC20/TRC20 tokens for intents, the precondition is easily met by ordinary usage, not an edge-case attack requiring special privileges.

### Recommendation
Replace all raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, the fee payout branch, and the `SweepDust` handler in `onAccept`) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the safer pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures the boolean return value (when present) is decoded and reverts on `false`, and non-standard tokens returning no data are still handled correctly, preventing escrow accounting from advancing when the underlying transfer did not actually succeed.

### Proof of Concept
1. User places an order via `placeOrder` on the source chain using an ERC20/TRC20 token `T` whose `transfer` implementation returns `false` (instead of reverting) when a transfer cannot be completed (e.g., recipient is blacklisted, or contract enters a paused/limited state that still returns a boolean).
2. Order is escrowed; `_orders[commitment][T] = amount`.
3. Order times out or is cancelled, triggering `RefundEscrow` (or is filled, triggering `RedeemEscrow`), which is delivered via `onAccept` → `withdraw(body, ...)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; `T.transfer` runs to completion and returns `false`, but the low-level call itself succeeds (`success == true`), so `if (!success) revert TransferFailed();` does not trigger.
5. `_orders[commitment][T] -= amount;` zeroes the escrow, `_filled[commitment] = beneficiary;` marks the order as finalized, and `EscrowRefunded`/`EscrowReleased` is emitted.
6. The beneficiary never received token `T`; the tokens remain locked in the `IntentGatewayV2` contract balance with no remaining accounting path to withdraw them for this commitment — a permanent loss/freeze of the escrowed funds.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

            }
        }
