I've confirmed the core finding: the webhook `shop` (and `topic`, `webhook_id`, `api_version`) header fields are trusted for identity/routing but are excluded from the HMAC signature, which covers only the raw body.### Title
Webhook shop-domain header trusted for identity but excluded from HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the `shop` value it then hands to the app's handler as the tenant identity is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed bytes. This breaks the intended binding of `hmac_valid(body) == shop_authenticated`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read straight from HTTP headers with no cryptographic linkage to the signature: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, request.to_signable_string)` — i.e., only over the body — and once that check passes, unconditionally forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` given to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm the signature check is body-only and secret-keyed, with no shop/topic binding whatsoever: [4](#0-3) 

The equality the gem implicitly promises is: *the shop that authored the signed bytes == the shop passed to the handler*. Because the shop header sits outside `to_signable_string`, that equality does not hold. Since Shopify signs all webhooks for every shop installing a given app with the same app-level `client_secret` (not a per-shop secret), an HMAC that is valid for a given body is valid regardless of which installed shop is named in the `shop-domain` header. Any tenant that can produce (or replay) one valid `(body, hmac)` pair for the shared secret — e.g., a webhook Shopify sent them for their own shop — can resubmit that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `shop-domain` header. `HmacValidator.validate` still returns `true` (it never looks at the header), and `Registry.process` will call the handler with `data.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding break inside the gem's own webhook verification path: the field the app is meant to trust for "which shop does this event belong to" is not covered by the same authentication mechanism (`HmacValidator`) that vouches for the payload. Any multi-tenant app that uses `data.shop` from `WebhookMetadata` (as the gem's own documentation instructs at `docs/usage/webhooks.md`) to key storage, dedupe, or fan out background jobs can be made to associate an attacker-supplied shop's body with an arbitrary victim's tenant, since the gem provides no other correlated field. This matches the Critical "cross-tenant access" impact category, since the vulnerability is intrinsic to the gem's `Webhooks::Request`/`Registry` implementation.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on one's own shop (any unprivileged Shopify merchant can do this for a public/multi-tenant app) to receive at least one legitimate webhook with a valid HMAC, and (2) POSTing that exact body with the original HMAC header but a modified `x-shopify-shop-domain` header to the app's public webhook endpoint. No secrets, tokens, or elevated access are required — only the ability to trigger a shop event and observe/resend the resulting webhook, which is intrinsic to being a shop-owner/tenant of the app. This is a purely mechanical replay against unprivileged internet-reachable infrastructure.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated bytes rather than trusting bare headers:
- Include the `shop-domain` header value in `to_signable_string`, or better, resolve the shop from a per-shop stored secret / installed-shop lookup keyed off an already-authenticated identifier before dispatching to the handler.
- At minimum, cross-check that the shop named in the header matches a shop with an active, expected installation state for the topic being delivered before invoking `handler.handle`, so a valid-body-but-wrong-shop replay is rejected even though the raw HMAC passes.

### Proof of Concept
1. Attacker installs the target multi-tenant app on `attacker-shop.myshopify.com`, triggering (or waits for) a webhook, e.g. `orders/create`, sent by Shopify to the app's registered callback URL with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(app_client_secret, B)`).
2. Attacker captures `B` and `H` (e.g., via browser devtools proxy on their own server, or a controlled receiving endpoint).
3. Attacker re-sends an HTTP POST to the app's public webhook endpoint with the same raw body `B`, the same `x-shopify-hmac-sha256: H` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate(request)` recomputes `HMAC(app_client_secret, B)` and finds it equal to `H` — validation passes since the shop header is never part of `to_signable_string`.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`, causing the app to process attacker-controlled data as if it originated from the victim shop.
