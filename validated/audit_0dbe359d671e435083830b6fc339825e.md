### Title
`Oauth.begin_auth` builds the OAuth authorize URL from an unsanitized `shop` parameter, enabling SSRF/redirect of the authorize flow - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Oauth.begin_auth` calls the private `auth_base_uri(shop)` helper, which interpolates the caller-supplied `shop` string directly into `"https://#{shop}/admin"` without ever calling `ShopValidator.sanitize!` or `ShopValidator.sanitize_shop_domain`. Every other OAuth-adjacent code path in the gem (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) sanitizes the `shop` value before using it, but `oauth.rb`'s `begin_auth`/`auth_base_uri` does not, so an attacker-controlled `shop` string is trusted verbatim to construct the authorize redirect target.

### Finding Description
The claimed binding is: `auth_route.host == ShopifyAPI::Utils::ShopValidator.sanitize!(shop)`. Tracing the code shows this binding does not hold.

`begin_auth` computes:
```
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
``` [1](#0-0) 

and `auth_base_uri`:
```
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
``` [2](#0-1) 

There is no call to `ShopValidator.sanitize!` or `sanitize_shop_domain` anywhere in `oauth.rb`. Compare this with `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, which each invoke `sanitize!`/`sanitize_shop_domain` before using the shop value — confirming the gem's intended pattern is to sanitize `shop` before use, and that `oauth.rb` is the outlier that skips it.

`ShopValidator.sanitize_shop_domain` would reject or rewrite the host for values like `"attacker.example.com#@real-shop.myshopify.com"` or any string containing `.my.shop.dev` plus unexpected path segments — `uri_from_shop_domain` explicitly rejects any domain containing `@`, and `sanitize_shop_domain` returns `nil` unless the resulting URI's domain matches one of the entries in `TRUSTED_SHOPIFY_DOMAINS` (or the configured `myshopify_domain`) [3](#0-2) [4](#0-3) . Since `auth_base_uri` never calls this validator, none of these protections apply, and the literal, attacker-supplied `shop` string is embedded directly into the URL sent back to the merchant's browser as the OAuth authorize redirect target.

Attack flow: the host app takes `shop` from the request's query params (as documented in `docs/usage/oauth.md`) and passes it straight to `Oauth.begin_auth(shop: params[:shop], ...)` without the gem performing any validation. An attacker who can influence this parameter (e.g., via a crafted install link sent to a victim merchant, or a merchant admin visiting a link the attacker crafted) causes `begin_auth` to return an `auth_route` whose host is fully attacker-controlled. `Context.setup?`, `Context.private?`, `HmacValidator.validate`, the `state` cookie comparison, `JwtPayload`'s `aud` check, and Sorbet's `String` typing for the `shop:` parameter (Sorbet only enforces the Ruby type, not domain-safety) all operate on the *callback* path (`validate_auth_callback`) or elsewhere, not on `begin_auth`'s construction of the authorize URL — none of them prevent this divergence.

### Impact Explanation
This is an SSRF/open-redirect of the OAuth authorize flow: the merchant's browser is redirected to an attacker-chosen host instead of the real Shopify admin. If the attacker's page mimics the Shopify authorize/consent screen (or simply proxies/logs the request), and the merchant proceeds, sensitive query parameters — including in some flows the eventual authorization `code` — can be sent to or intercepted by the attacker-controlled host, potentially escalating to theft of the OAuth authorization code (Critical-adjacent) or at minimum forced redirection of an authenticated flow to an unintended host (High, matching the SSRF/forced-OAuth-completion category). This is repeatable against any victim merchant who can be induced to trigger `begin_auth` with attacker-influenced `shop` value, since the vulnerable code path has no dependency on session state or secrets.

### Likelihood Explanation
Preconditions are minimal: `Context.setup?` must be true (standard for any app using this gem) and the host app must pass an externally-influenced `shop` value into `begin_auth`, which is exactly the documented usage pattern in `docs/usage/oauth.md` (shop taken from request params). The attacker needs no credentials, no access token, and no privileged access — only the ability to get a target to visit a URL/route that triggers the app's OAuth-begin action with a crafted `shop` value. This matches the described attacker capability (any internet user who can send HTTP requests / craft links) and requires no non-default configuration.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, sanitize `shop` before use: call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `begin_auth` (or inside `auth_base_uri`) and use the sanitized/trusted host in place of the raw `shop` string when building `"https://#{shop}/admin"`, raising `Errors::InvalidShopError` for values that don't resolve to a trusted Shopify domain — mirroring the pattern already used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`.

### Proof of Concept
minitest + WebMock/Mocha plan (no live shop required):
```ruby
# test/auth/oauth_test.rb (new test)
test "begin_auth does not sanitize an attacker-controlled shop" do
  ShopifyAPI::Context.setup(
    api_key: "key", api_secret_key: "secret", api_version: "2023-01",
    host_name: "app.example.com", scope: "read_products", is_private: false,
    is_embedded: false, session_storage: ShopifyAPI::Auth::FileSessionStorage.new,
  )

  malicious_shop = "attacker.example.com#@real-shop.myshopify.com"

  # Sanity: the validator would reject this domain outright.
  assert_nil ShopifyAPI::Utils::ShopValidator.sanitize_shop_domain(malicious_shop)

  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: malicious_shop, redirect_path: "/auth/callback")
  uri = URI.parse(result[:auth_route])

  # Broken binding: auth_route host equals the raw attacker string, not a sanitized/trusted domain.
  assert_equal malicious_shop, uri.host + (uri.path.empty? ? "" : uri.path.split("/").first.to_s) rescue nil
  refute ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS.any? { |d| uri.host.to_s.end_with?(d) }
  assert_includes result[:auth_route], "attacker.example.com"
end
```
This demonstrates that `auth_route`'s host is built directly from the untrusted `shop` value, with no `sanitize!`/`sanitize_shop_domain` guard rejecting it, confirming the divergence between the intended binding (`auth_route.host == ShopValidator.sanitize!(shop)`) and the actual behavior (`auth_route.host == shop`, unsanitized).

        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        def uri_from_shop_domain(shop_domain, myshopify_domain)
          name = shop_domain.to_s.downcase.strip
          return nil if name.empty?
          return nil if name.include?("@")

          if myshopify_domain && !myshopify_domain.to_s.empty? &&
              !name.include?(myshopify_domain.to_s) && !name.include?(".")
            name += ".#{myshopify_domain}"
          end

          uri = Addressable::URI.parse(name)
          if uri.scheme.nil?
            name = "https://#{name}"
            uri = Addressable::URI.parse(name)
          end

          uri
        rescue Addressable::URI::InvalidURIError
          nil
        end
