## Finding

### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity solely from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies covers only the raw request body. Because the app's `api_secret_key` is shared across every shop that installs the app, a valid `(body, hmac)` pair obtained from one tenant's webhook delivery remains cryptographically valid when replayed with a different `shop-domain` header, letting an attacker attribute a signed payload to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string` (i.e. the raw body) using the app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` trusts `request.shop` after this check succeeds and hands it straight to the handler as the tenant identity: [4](#0-3) 

The binding that should hold is:
`hmac-verified bytes == bytes that determine the shop identity acted upon`

but in this code:
`hmac-verified bytes == raw_body only`, while `shop identity used by the handler == unauthenticated header value`

Since `api_secret_key` is a single, per-app secret (not per-shop), any `(raw_body, hmac)` pair legitimately produced for one installed shop is a valid signature for the *same body* regardless of which shop header accompanies it. An attacker who controls (or has installed the same app on) one shop can capture a genuine webhook delivery — for example a `customers/data_request` or `orders/create` payload with its `X-Shopify-Hmac-Sha256` header — and re-POST the identical body to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `HmacValidator.validate` will still accept it because it never inspects the shop header, and `Registry.process` will dispatch it to the handler tagged with the victim's shop, breaking the shop-identity binding this gem is supposed to guarantee to the host application.

### Impact Explanation
This breaks the cross-tenant boundary the gem is meant to enforce for webhook processing: a signature check that is supposed to prove "this payload came from Shopify for shop X" instead only proves "this payload came from Shopify for some shop using this app," while `shop` is attacker-controlled at the HTTP layer. Any host application that relies on `WebhookMetadata#shop` (as documented/intended usage of `ShopifyAPI::Webhooks::Registry`) to select which merchant record, session, or access token to act on can be made to process attacker-supplied data under a victim shop's identity — this is a cross-tenant access class issue.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any shop the attacker controls (a normal, unprivileged action available to any developer for a public/dev app), (2) capturing one legitimate webhook delivery to obtain a valid `(body, hmac)` pair, and (3) sending an HTTP POST directly to the app's public webhook endpoint with a forged shop header. None of these require the app's `client_secret`, an access token, or any privileged credential belonging to the victim shop.

### Recommendation
Include the shop domain (and other identity-relevant headers such as `webhook-id`/`api-version`) in the signed material verified against the HMAC, or otherwise cryptographically bind the claimed `shop` to the signature — e.g., verify the HMAC over a canonical string that concatenates the raw body with the shop header, matching what a per-shop secret model would enforce. At minimum, document that `request.shop` is unauthenticated and must not be trusted by host applications without an independent cross-check against the shop that is expected to receive that webhook topic.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (a shop they control) and triggers a webhook, e.g. `orders/create`.
2. Attacker captures the delivered request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends a new POST directly to the app's public webhook endpoint with the same body `B` and same header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` decodes `H`; `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and it matches `H` (the shop header was never part of the signed bytes), so `Registry.process` accepts the request and dispatches it to the handler with `shop = "victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop.       def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
