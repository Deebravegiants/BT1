### Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable content for HMAC validation from the raw HTTP body only, while the `shop` value used to attribute the webhook to a specific merchant tenant is taken from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. The header is never included in the signed content, so an attacker who possesses one valid `(raw_body, hmac)` pair can replay it with an arbitrary `shop-domain` header and have `ShopifyAPI::Webhooks::Registry.process` accept it as authentic for a different tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC` over `verifiable_query.to_signable_string` (the raw body) and compares it via `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` only checks this body-only HMAC before dispatching to the registered handler, passing `request.shop` straight into `WebhookMetadata` untouched: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further validation, and is the sole tenant-identifying value the host application's `WebhookHandler#handle` implementation receives: [5](#0-4) 

The identity binding broken is: `shop_attributed_to_webhook (header, unauthenticated) != shop_covered_by_hmac (none — only raw_body is signed)`. Because the signature never binds the shop domain (or topic, webhook-id, api-version) to the body, any entity capable of obtaining one legitimately-signed `(body, hmac)` pair for a topic — trivially available to any merchant who installs the app and receives their own webhooks — can resend the exact same body/hmac to the app's webhook endpoint while substituting a different shop-domain header. `HmacValidator.validate` will still pass because it only recomputes the HMAC over the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant data/authorization confusion vector: the receiving application uses `WebhookMetadata#shop` to route webhook data to the correct merchant's records/session (e.g., to write order/product data, or to trigger `app/uninstalled` cleanup) — see the gem's guidance that handlers act on `data.shop`. An attacker who is a legitimate merchant of the app can capture a validly-signed webhook body for their own shop and replay it with a victim shop's domain in the header, causing the host app to process/store attacker-controlled data under the victim tenant's identity, or to trigger tenant-scoped side effects (e.g., forced "app/uninstalled" processing) against a shop they do not control. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (shop) is the exact security boundary this library exists to protect and it is not authenticated.

### Likelihood Explanation
Likelihood is high for any actor who can install the app on their own shop (a normal, unprivileged action) and capture the outbound webhook Shopify sends them — this gives them a valid `(raw_body, hmac)` pair signed with the app's real `client_secret` without ever needing to know the secret itself. Replaying that pair against the app's public webhook endpoint with a forged `shop-domain` header requires no special access, only the ability to send an HTTP POST, matching the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or explicitly bind/validate `request.shop` against records the app already trusts (e.g., verify the shop is a currently-installed shop with a stored session) before invoking the handler, rather than trusting the header value as-is once the body-only HMAC passes.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a legitimately signed webhook: body `B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's secret) and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (merchant A) captures `(B, H)` from their own webhook traffic.
3. Attacker resends the same body `B` and hmac `H` to the app's public webhook endpoint but sets `x-shopify-shop-domain: shop-victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `@raw_body` (`B`) — identical to step 1 — so validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(shop: "shop-victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process/store attacker-controlled data as if it originated from `shop-victim`.
