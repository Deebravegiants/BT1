### Title
Duplicate output-token legs in same-chain intent orders corrupt `_partialFills` accounting, allowing under-release or permanent freezing of solver escrow - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents._fillSameChain` tracks cumulative partial-fill progress per `(commitment, outputToken)` in `_partialFills`, exactly the same "amount minus already-claimed-under-this-key" accounting pattern as `FootiumPrizeDistributor.claimETHPrize`/`claimERC20Prize`. If an `Order.output.assets` array contains two (or more) entries with the same `token` address but different `amount`s — analogous to two Merkle leaves for the same address with different prize amounts — the second leg's `remaining = totalRequired - alreadyFilled` computation reads a `_partialFills[commitment][outputToken]` value that was already bumped by the first leg's fill, corrupting the fill math for the rest of that order.

### Finding Description
In `_fillSameChain` [1](#0-0) , for each output asset `i`:
```
uint256 totalRequired = order.output.assets[i].amount;
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
...
uint256 amountFilled = alreadyFilled + fillAmount;
_partialFills[commitment][outputToken] = amountFilled;
```
The storage key is `_partialFills[commitment][outputToken]` — keyed only by the order commitment and the output token address, not by the index `i` of the output leg. If the order's `output.assets` array (fully attacker/user-controlled at `placeOrder` time, since `Order` is hashed to produce `commitment` and nothing in `IntentsBase`/`IntrinsicIntents` enforces uniqueness of `output.assets[].token`) contains two entries for the same token but with different `amount`s, the second entry's `totalRequired - alreadyFilled` subtraction reads the accounting state that the first entry already mutated:

- If leg 0 has a smaller `amount` than leg 1 and gets fully filled first, `alreadyFilled` when leg 1 is processed already contains leg 0's `fillAmount`, so `remaining = leg1.amount - leg0.fillAmount`, permanently reducing what a solver can ever claim as leg 1's requirement — and once `_partialFills[commitment][token] >= leg1.amount` (satisfied purely by leg 0's contribution), `remaining` for leg 1 becomes `0`, so leg 1 is treated as "already filled" and skipped entirely, with `isFullyFilled` computed against a corrupted, too-small total.
- Symmetric to Footium: if the larger-amount leg is filled first (`alreadyFilled` climbs past a smaller leg's `totalRequired`), the smaller leg's `remaining = totalRequired - alreadyFilled` underflows in the same class of bug the report describes (Solidity ^0.8 reverts on underflow rather than wrapping, so this manifests as the fill reverting instead of releasing the smaller leg's escrow at all).

This is directly reachable by an unprivileged user: `placeOrder` accepts an arbitrary `Order` struct and escrows the `inputs` [2](#0-1) ; nothing rejects duplicate `token` entries in `output.assets`.

### Impact Explanation
A user who places a same-chain order with duplicate output tokens (whether deliberately, by tooling bug, or by any front-end that doesn't dedupe token legs) puts solver-supplied escrow release into corrupted or unreachable state:
- Escrow corresponding to the second (or later) leg of the same token can become permanently unfillable (`remaining` reverts to 0, or `remaining` computation underflows and always reverts), leaving that portion of `_orders[commitment][inputToken]` escrow (funds already locked from the user at `placeOrder`) stuck since `_withdraw` is only reachable via `_fillSameChain`/`_cancelSameChain` paths that key off the same corrupted commitment state.
- This is a fund-freezing bug reachable purely by a single unprivileged `placeOrder` transaction — no privileged actor required — matching the report's "Medium: causes loss of funds/freezing dependent on specific state" class.

### Likelihood Explanation
The order struct comes straight from the caller of `placeOrder`; there is no explicit check anywhere in `IntentsBase`/`IntrinsicIntents` rejecting duplicate `output.assets[].token` entries. While well-behaved front ends likely never construct such an order, nothing on-chain prevents it, and the condition is trivially triggerable with a single crafted transaction. Given the strict structural parity to the reported bug class (a shared accounting key reused across two distinct "entitlement" entries with different amounts), likelihood of accidental or adversarial triggering is non-negligible.

### Recommendation
Key `_partialFills` by the output-leg index (or an index-derived commitment) instead of by `outputToken` alone, e.g. `_partialFills[commitment][i]`, so each output leg tracks its own fill progress independently of any other leg that happens to reference the same token address. Alternatively, validate at `placeOrder` time (or during `_fillSameChain`) that `output.assets` contains no duplicate `token` entries, rejecting such orders outright.

### Proof of Concept
1. User calls `placeOrder` with `order.output.assets = [{token: DAI, amount: 100}, {token: DAI, amount: 500}]` and matching `order.inputs` escrowed.
2. Solver calls `fillOrder` supplying `outputs = [{token: DAI, amount: 100}, {token: DAI, amount: 500}]` in one transaction, or across two partial-fill transactions.
3. In the loop, leg `i=0` sets `_partialFills[commitment][DAI] = 100` (`alreadyFilled` starts at 0, `remaining = 100`).
4. Leg `i=1` reads `alreadyFilled = _partialFills[commitment][DAI] = 100`, computes `remaining = 500 - 100 = 400` instead of the correct `500` — the solver is shorted 100 units of proportional escrow release, and any independent partial fill for leg 1 alone (e.g., a different solver later attempting to fill exactly `100` for leg 1's requirement) will see `remaining` already fully or partially consumed by leg 0's accounting, causing incorrect escrow release amounts or a revert once `alreadyFilled` exceeds a later leg's smaller `totalRequired`.
