### Title
Non-atomic, unencapsulated PnL bookkeeping across `calc_take_pnl`/`process_deposit`/`process_withdraw` can desynchronize `TargetOrders.calc_pnl_x/y` from real vault reserves and permanently brick `Deposit`/`Withdraw` for all LPs - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
Exactly like the Audius `DelegateManager`/`Governance` pattern flagged in the external report, Raydium's PnL accounting is spread across multiple hand-written, non-atomic arithmetic steps duplicated in three separate instruction handlers (`process_deposit`, `process_withdraw`, `process_withdrawpnl`) instead of being encapsulated in a single well-tested state-transition function. Each handler independently: (1) computes `total_pc/coin_without_take_pnl` from raw vault balances via `Calculator::calc_total_without_take_pnl_no_orderbook` [1](#0-0) , (2) normalizes to `x1`/`y1` with decimal scaling, (3) calls `calc_take_pnl` which itself mutates `amm.state_data.need_take_pnl_pc/coin` and the local `total_*_without_take_pnl` variables in a multi-branch, partially-conditional way [2](#0-1) , and then (4) separately re-derives `target_orders.calc_pnl_x`/`calc_pnl_y` using yet another independent chain of `checked_add`/`checked_sub` operations in `process_deposit` [3](#0-2)  and `process_withdraw` [4](#0-3) . These four pieces of state (`need_take_pnl_pc`, `need_take_pnl_coin`, `target_orders.calc_pnl_x`, `target_orders.calc_pnl_y`) must stay perfectly consistent with each other and with the physical vault balances, but there is no single function that atomically guarantees this invariant — precisely the "complicated state updates" anti-pattern described in the report.

### Finding Description
`calc_take_pnl` enforces an invariant that the current unscaled reserve product must be at least the last recorded "no-pnl" product:
```
if pool_pc_amount.checked_mul(pool_coin_amount).unwrap()
    >= (calc_pc_amount).checked_mul(calc_coin_amount).unwrap()
{ ... } else {
    return Err(AmmError::CalcPnlError.into());
}
``` [5](#0-4) 

This function is invoked from every `Deposit` [6](#0-5)  and every `Withdraw` (unless status is `WithdrawOnly`) [7](#0-6) , and also from `WithdrawPnl` [8](#0-7) .

The `target_orders.calc_pnl_x`/`calc_pnl_y` fields that feed the right-hand side of this invariant (`calc_pc_amount`/`calc_coin_amount`) are recomputed independently in `process_deposit` and `process_withdraw` using `normalize_decimal_v2`/decimal-scaled arithmetic that truncates towards zero, while the left-hand side (`pool_pc_amount`/`pool_coin_amount`) is derived straight from exact on-chain SPL token vault balances via `calc_total_without_take_pnl_no_orderbook`. Because the two sides of the invariant are computed through two different, independently-maintained arithmetic paths (one that goes through decimal normalization/restoration with truncation, one that doesn't), and because both paths are updated by hand in each instruction handler rather than through one audited, atomic state-transition routine, any accumulated rounding drift between `calc_pnl_x*calc_pnl_y` and the true `pool_pc*pool_coin` value can push the invariant permanently negative. Once that happens, `calc_take_pnl` unconditionally returns `AmmError::CalcPnlError` for every future call, which means every future `Deposit` and every future `Withdraw` (while status is not `WithdrawOnly`) reverts unconditionally, for every liquidity provider, forever — the pool's LP funds become permanently locked with no path to reverse the state (there is no admin/owner instruction that resets `target_orders.calc_pnl_x/y` back into consistency with reserves outside of the same fragile update path).

This is a direct structural analog to the Audius bug class: state that must be kept "complete, consistent, and complementary" across multiple update sites is instead updated piecemeal in several places (`process_deposit`, `process_withdraw`, `process_withdrawpnl`, `calc_take_pnl`), with no single encapsulated function guaranteeing the invariant, so a single inconsistency—triggerable by ordinary user activity (repeated `Deposit`/`Withdraw` calls with unfavorable rounding, particularly on low-decimal or low-liquidity pools)—can permanently corrupt the accounting and lock funds for every other honest LP in the pool, exactly as the Audius delegator could lock stake/rewards for a victim service provider and all its honest delegators.

### Impact Explanation
If the invariant check in `calc_take_pnl` is ever violated, it is unrecoverable: `Deposit` and `Withdraw` both call it unconditionally under normal (`SwapOnly`/non-`WithdrawOnly`) status, and any failure returns `AmmError::CalcPnlError`, aborting the transaction. There is no other instruction in `processor.rs` that resets or repairs `target_orders.calc_pnl_x`/`calc_pnl_y` independent of this same code path, so once triggered this is a permanent denial of withdrawal/deposit for all LPs in the pool — a freezing-of-funds condition, which meets the "permanent freezing of user or LP funds" bar.

### Likelihood Explanation
The trigger condition depends on rounding/truncation drift between the decimal-normalized `target_orders.calc_pnl_x/y` bookkeeping and the raw-integer vault-balance bookkeeping accumulating across many ordinary `Deposit`/`Withdraw` calls (each of which independently re-derives and re-writes this state via hand-rolled arithmetic rather than one atomic, invariant-checked function). This does not require a privileged signer, malicious validator, or off-chain component — only repeated normal use of the public `Deposit`/`Withdraw` instructions, especially on pools with small reserves or coin/pc decimals that maximize truncation loss relative to reserve size. Because the exact conditions needed to flip the inequality require careful, hard-to-fully-verify multi-step rounding analysis across `normalize_decimal_v2`/`restore_decimal`, this is reported as a structural analog of the reported bug class (unencapsulated, error-prone multi-step state updates) rather than a fully demonstrated numeric PoC.

### Recommendation
Encapsulate all reads and writes of `state_data.need_take_pnl_pc/coin` and `target_orders.calc_pnl_x/calc_pnl_y` into single, dedicated internal functions (e.g. `_update_pnl_state`) that take the raw vault balances and the withdrawal/deposit deltas as input and atomically compute and write all four related fields together, enforcing the invariant internally instead of scattering the arithmetic across `process_deposit`, `process_withdraw`, and `calc_take_pnl`. Add a safety valve (e.g., a privileged recovery instruction, or reconciling `target_orders.calc_pnl_x/y` directly from current vault balances rather than incrementally) so a rounding-induced invariant violation cannot permanently brick `Deposit`/`Withdraw`. Add fuzz/property tests asserting `calc_pnl_x*calc_pnl_y <= pool_pc*pool_coin` holds after every possible sequence of `Deposit`/`Withdraw`/`WithdrawPnl` calls, mirroring the "thoroughly tested in isolation" remediation applied in Audius PR #539.

### Proof of Concept
Not independently reproduced with concrete numeric inputs; the structural code paths that create the risk are cited above (`calc_take_pnl` invariant at `program/src/processor.rs:190-192`, its unconditional invocation from `process_deposit` at `program/src/processor.rs:1166-1173` and `process_withdraw` at `program/src/processor.rs:1737-1749`, and the independent, hand-rolled re-derivation of `target_orders.calc_pnl_x/y` at `program/src/processor.rs:1352-1371` and `program/src/processor.rs:1818-1838`). A full numeric PoC would require enumerating decimal/rounding parameters (`pc_decimals`, `coin_decimals`, `sys_decimal_value`) and a sequence of deposit/withdraw amounts that drive `calc_pnl_x*calc_pnl_y` above `pool_pc*pool_coin`; this analysis was not completed within the scope of this review and should be validated with a fuzzer/property test before being treated as a confirmed exploit rather than a structural risk analog.
