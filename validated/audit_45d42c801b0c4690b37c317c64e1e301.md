Found it: `handlePostRequestTimeouts` and `handleGetRequestTimeouts` in `evm/src/core/HandlerV2.sol` index the `PolkadotTrie.VerifyProof` return array with a hardcoded `[0]` inside a loop that iterates over `timeoutsLength` requests, while the proof array (`message.proof`) is a single shared non-membership proof supplied by the caller for the *whole batch* — this is the same class of bug as the ksmbd CVE: code that indexes into a structure assuming a fixed single-item shape while it is actually reached through a batched/multi-item caller path, so the returned array's actual length is never checked against what's being indexed.

### Title
Unchecked `[0]` index into `PolkadotTrie.VerifyProof` result inside a per-request timeout loop can read out-of-bounds/wrong data - (File: evm/src/core/HandlerV2.sol)

### Summary
`handlePostRequestTimeouts` and `handleGetRequestTimeouts` both loop over a batch of timed-out requests (`message.timeouts`), and for **each** request build a fresh single-key array and call `PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0]`, indexing the very first element of whatever the trie verifier returns. `message.proof` is one relayer-supplied non-membership proof shared across the whole batch. Nothing in the handler enforces that `VerifyProof` returns exactly one entry per call, or that the entry returned actually corresponds to the single key just supplied for this iteration. ### Finding Description
The root cause mirrors the ksmbd CVE-2023-3867 pattern: a handler that processes one item assumes preconditions (here, "the proof-verification helper returns exactly the one value I asked for, at index 0") that were only guaranteed for a different, simpler call shape, but the function is actually reachable through a *batched* code path (`message.timeouts` is a `PostRequest[]`/`GetRequest[]`, i.e. an unprivileged relayer-controlled batch) where that invariant is never independently checked per iteration. `VerifyProof` is called fresh each loop iteration with a single-key array, but its return array's length and correspondence to `keys[0]` for *that* iteration is not validated before the unchecked `[0]` index is read. If the underlying `PolkadotTrie.VerifyProof` implementation can, for certain multi-node/malformed relayer-controlled proof inputs, return a value array whose length or ordering doesn't strictly match the 1-element `keys` input (e.g. returning zero entries for a particular key, or an array whose slot 0 doesn't correspond to the queried key), the `[0]` read will pull the wrong/uninitialized memory slot — reading state belonging to a different key/request than the one the safety check (`entry.value.length != 0`) is meant to gate. This lets an attacker's crafted batch that mixes normal keys with one adversarial key make the handler read the wrong "receipt" value for a timeout, potentially deciding a request has *not* been delivered (bypassing timeout eligibility protections) or dispatching a timeout for state that was never actually verified for that specific request.

### Impact Explanation
`handlePostRequestTimeouts`/`handleGetRequestTimeouts` are permissionless, unsigned-message-reachable entry points (any relayer can submit a batch of timeouts with a proof). A wrong-slot read from an unchecked `[0]` index means the non-membership check (`entry.value.length != 0`) — the sole gate preventing a timeout from firing on a request that was actually delivered — can be evaluated against data belonging to a different key in the batch. Bypassing that gate lets an attacker fire `host.dispatchTimeOut` for a request that was in fact delivered, causing double-processing/fund-release for a request that should be considered settled — a form of forged message delivery / unbacked timeout leading to fund loss on token-bridge or intents apps built atop ISMP.

### Likelihood Explanation
Exploitability depends on whether `PolkadotTrie.VerifyProof`'s Merkle/Patricia trie decode path can be driven, via a relayer-supplied multi-node proof, to return an array whose length/ordering diverges from the single requested key for a specific loop iteration in a batch context. This requires further verification of `PolkadotTrie.VerifyProof`'s internal invariants (not shown in the excerpts reviewed), so likelihood is Medium pending that confirmation, but the structural bug — indexing `[0]` on a per-item basis inside a batch loop without validating the returned array's length/identity each time — is present and directly analogous to the reported CVE's root cause (assuming per-call invariants that don't hold in a batched calling context).

### Recommendation
After each `VerifyProof` call inside both timeout loops, assert the returned array length equals 1 and that its key matches `keys[0]` before reading index 0, mirroring the `MismatchedValuesAndKeys`/`MismatchedProofsAndKeys` checks already used elsewhere in the codebase (e.g. `modules/ismp/state-machines/evm/src/tendermint.rs`, `modules/pallets/state-coprocessor`). Alternatively, batch all keys for the whole `timeoutsLength` loop into one `VerifyProof` call and match results positionally with an explicit length check, rather than re-invoking the verifier per key and blindly indexing the first slot.

### Proof of Concept
A concrete PoC requires instrumenting `PolkadotTrie.VerifyProof` (not included in the reviewed excerpts) with a crafted proof containing multiple trie nodes/keys such that, for a specific requested key, the returned `StorageValue[]` either has length 0 (causing revert, which is safe) or, more critically, length ≥1 with the entry at index 0 corresponding to a different key than the one requested this iteration. Submitting a `handlePostRequestTimeouts` batch mixing a decoy key (proven present) with a target key (actually delivered/present) in the same non-membership `proof` blob, ordered so the decoy's "absent" result lands at index 0, would let the target's delivered request pass the `entry.value.length != 0` check as if absent, firing an illegitimate timeout dispatch.

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
