### Title
Stale cached market state reused after pool mutation within one invocation (use-after-free analog) — (File: contracts/controller/src/context.rs)

### Summary
The MicroPython report describes a use-after-free: an object is resized (freeing its buffer) while a copy operation still references the old memory. The lending analog is a **use-after-invalidate** in the invocation-local `Context`: pool state fetched once is retained and reused after the underlying pool state has been mutated earlier in the same transaction, so a later step computes health/accounting on a freed (superseded) snapshot.

`Context::cached_pool_sync_data` returns the first-fetched `PoolSyncData` for a hub asset for the rest of the invocation — its own contract states it "does not accrue interest or refresh a cached snapshot" — and only `put_market_index` can restamp the index cache. Any flow that (a) loads sync data/indexes, (b) performs a pool mutation (borrow, repay, seize, withdraw) that changes debt/supply totals or indexes, and (c) re-queries `cached_pool_sync_data` or `cached_market_index` without a restamp, operates on the pre-mutation "freed" state.

### Finding Description
- `contracts/controller/src/context.rs:94-102` — `cached_pool_sync_data` caches `PoolSyncData` per `HubAssetKey` on first access and never invalidates it; there is no `put_pool_sync_data` equivalent to `put_market_index` (context.rs:105-107).
- `contracts/controller/src/context.rs:125-134` — `cached_market_index` similarly retains the first fetched index; correctness depends entirely on every pool-mutating call site remembering to call `put_market_index` afterward.
- `contracts/controller/src/context.rs:70-74` — `load_markets` explicitly retains already-cached values (`collect_uncached_keys` skips cached entries), so a second `load_markets` after an intermediate mutation silently keeps the stale snapshot.

Flows that combine a read of pool state, a pool mutation, and a subsequent risk/settlement read in one permissionless call — e.g. `multiply`, `repay_debt_with_collateral`, `swap_debt`/`swap_collateral`, `flash_position`, or the multi-leg liquidation `apply` path — are the reachable surface. Where a mutation site fails to restamp the cache, the post-mutation health-factor and seize/bonus math in `positions/liquidation` run on the obsolete totals/indexes.

### Impact Explanation
If a post-mutation step consumes stale indexes or `PoolSyncData` (supply/debt totals, cash), the controller can compute a health factor from pre-borrow collateral or pre-repay debt. Consequences include seizing more collateral than the current state justifies, crediting debt repayment against an obsolete index (over- or under-charging interest), or letting a position borrow/withdraw against freed collateral value — theft of user funds or protocol insolvency within a single unprivileged transaction.

### Likelihood Explanation
The hazard exists by construction: the cache layer guarantees staleness unless every writer restamps, and `PoolSyncData` has **no** restamp API at all — any flow that fetches it before a pool call and reads it again afterward necessarily sees freed state. Reachability is high: the listed strategies are all permissionless and combine pool mutations with subsequent risk checks. Whether a concrete exploitable path exists depends on each strategy's ordering; the absence of a `put_pool_sync_data` invalidation primitive makes at least one inconsistent read plausible across the strategy set.

### Recommendation
- Add an invalidation/`put_pool_sync_data` method symmetric to `put_market_index`, and call both after every pool-mutating external call (`borrow`, `repay`, `withdraw`, `seize`, `recapitalize`).
- Alternatively, clear `pool_sync_data`/`market_indexes` entries for a `HubAssetKey` whenever a pool op for that key completes, forcing the next read to fetch fresh state.
- Audit every strategy in `contracts/controller/src/strategies/` for read→mutate→read ordering against the same `HubAssetKey`.

### Proof of Concept
Sketch (requires a flow that does not restamp): in `repay_debt_with_collateral(hub, debt_asset, collateral_asset, ...)` — 1) invoke with a position whose `cached_pool_sync_data`/`cached_market_index` for the collateral key is loaded during the initial risk check; 2) the withdraw/seize leg mutates pool supply totals and accrues the index; 3) the subsequent debt-repayment sizing or post-action HF validation calls `cached_pool_sync_data`/`cached_market_index` again, receiving the pre-seize snapshot (context.rs:94-102, 125-134); 4) repayment is scaled by the stale debt index, leaving residual debt or over-seizing collateral. The exact discrepancy is bounded by the index drift and leg size but compounds for millisecond-chunked accrual on large positions.

Note: I was unable to fully trace each strategy's restamp discipline within the available context; the confirmed facts are the non-invalidated `pool_sync_data` cache (no restamp API exists) and the restamp-dependent `market_indexes` cache, which is where the use-after-free shape concretely lives in this codebase.
