### Title
Stale `Account.owner` lets a prior NFT holder retain spending authority after `transfer` — privilege escalation and collateral theft - ([File: contracts/controller/src/account.rs])

### Summary
The controller stores the owner address inside the `Account` struct at mint time (`Account { owner: owner.clone(), ... }`, `account.rs:64-65`) and never re-syncs it. Position-NFT `transfer`/`transfer_from` are the stock OpenZeppelin enumerable implementation — they update only the NFT's `Owner`/`Balance` entries in `position-nft` and emit no hook back to the controller (`position-nft/src/contract.rs:131-173`). Authorization for every fund-moving entrypoint (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) goes through `require_owner_or_delegate`, which compares `caller` against that **stale** `account.owner` field (`account.rs:130-140` → `is_owner_or_delegate`, `account.rs:115-127`: `if caller == owner { return true; }`). A seller who transfers the account NFT therefore keeps full spending authority, and the buyer — the real owner — inherits an account that an unprivileged third party (relative to them) can drain.

### Finding Description
- `create_account`/`create_account_with` mint the NFT to `owner` and persist `account.owner = owner` (`account.rs:62-70`). Nothing rewrites this field afterward; there is no `set_account_owner`/`update_owner` path anywhere in `contracts/` (grep over `owner:`/`set_account_owner`/`update_owner` shows only the mint-site write).
- NFT `transfer`, `transfer_from`, `approve` are the pinned stock OZ methods; they mutate `NFTStorageKey::Owner` in the NFT contract only. The controller is never invoked, so `account.owner` diverges from `owner_of(token_id)` the moment a transfer executes.
- The controller itself acknowledges the split-brain: `require_account_owner` (used by `add_delegate`, `remove_delegate`, `renew_account`) deliberately re-reads live NFT ownership via `storage::account_owner(env, account_id)` (`account.rs:143-148`) instead of trusting `account.owner` — proof that `account.owner` is known to be stale-capable. Yet the spending guard `require_owner_or_delegate` still trusts the stale field.
- Delegate entries are keyed by owner: `get_delegates(env, account_id, owner)` is looked up with the stale `account.owner` (`account.rs:126`), so the *previous* owner's delegates keep working post-transfer while the *new* owner cannot grant or use delegates at all (their own `add_delegate` fails because `require_account_owner` correctly reads the NFT and sees a different owner than the delegate-keyed map expects).

### Impact Explanation
Theft of user funds / protocol insolvency path, reachable by a single unprivileged address:

1. Attacker A supplies collateral to an account, then sells/transfers the position NFT to victim B (e.g., via any NFT marketplace or direct `transfer`).
2. A calls `controller.borrow` / `controller.withdraw` / `controller.repay_debt_with_collateral` with `caller = A`, `account_id` of the sold account. `A.require_auth()` is satisfied — A signs their own call — and `caller == account.owner` (stale) passes. A withdraws all collateral and borrows up to the LTV/threshold limits, receiving the proceeds.
3. B is left holding an NFT whose account is emptied or maximally levered; B cannot even remove A's old delegates, and B's attempts to act on the account through guarded paths see `account.owner = A`, so `require_owner_or_delegate` rejects B unless B's address happens to sit in A's delegate list.

Even an honest owner who transfers a position (wallet rotation, OTC sale) silently leaves the old wallet — and any delegate the old wallet ever approved while its manager registration was active — with live keys to the collateral.

### Likelihood Explanation
High once any NFT transfer occurs. The vulnerability requires no timing race, no oracle manipulation, no privileged state — only a stock `transfer` on the position NFT followed by a normal `borrow`/`withdraw` call signed by the former owner. Secondary-market trading of lending positions is a natural use of a transferable position NFT, so the trigger condition is routine rather than adversarial-exotic. The codebase's own invariant file (`scripts/permissionless_entrypoints.txt:111`) asserts "only the holder can move the whole account" — true for the NFT, but the controller's spending authority does not follow the token.

### Recommendation
- In `is_owner_or_delegate`/`require_owner_or_delegate` (and any other site reading `account.owner` for authorization, e.g. `load_or_create_account`, liquidation `resolve_seize_receiver`), resolve ownership from the position NFT's live `owner_of` via `storage::account_owner`, not from the stored `Account.owner` field; alternatively refresh `account.owner` from `owner_of` on every `get_account` and treat the stored field as a cache only.
- Key delegate storage by `account_id` alone (or migrate the delegate set on first post-transfer touch), so a transfer unambiguously severs the previous owner's grants — currently `get_delegates(account_id, stale_owner)` keeps the old owner's delegates alive.
- Add a fuzz test: mint → supply → `transfer` NFT → assert former owner is rejected by `borrow`/`withdraw` and former delegates are rejected, and that the new owner succeeds.

### Proof of Concept
```rust
// test-harness style sketch
let t = LendingTest::new().build();
let a = t.user();           // attacker / seller
let b = Address::generate(&env); // buyer

// A creates account 1 and supplies USDC collateral.
let account_id = t.supply(&a, 0, &usdc_hub_asset, 1_000e7);

// A sells the position: stock OZ transfer updates only NFT Owner entry.
t.nft_client().transfer(&a, &b, &(account_id as u32));
assert_eq!(t.nft_client().owner_of(&(account_id as u32)), b);

// account.owner in controller storage is still A (stored at mint,
// contracts/controller/src/account.rs:65; no resync exists).

// A (no longer the owner) drains collateral — passes require_owner_or_delegate
// because caller == stale account.owner.
t.env().mock_all_auths();
let ctrl = t.ctrl_client();
ctrl.borrow(&a, &account_id, &spoke_id, &borrow_payment); // should fail, succeeds
ctrl.withdraw(&a, &account_id, &spoke_id, &supply_payment); // drains collateral

// B, the actual NFT holder, is rejected on guarded paths:
assert!(ctrl.try_withdraw(&b, &account_id, &spoke_id, &supply_payment).is_err());
```

Caveat: I verified the stale write at `account.rs:65`, the stale read in `is_owner_or_delegate` at `account.rs:121`, and that the NFT `transfer`/`transfer_from` are stock OZ with no controller callback; I could not inspect `storage::get_account`'s internals in the remaining budget, so if `get_account` silently rewrites `account.owner` from `owner_of` on every load the finding collapses — that single line of `contracts/controller/src/storage/account.rs` is the decisive check.
