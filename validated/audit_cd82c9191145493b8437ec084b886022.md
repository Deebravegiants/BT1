### Title
Webhook `shop` identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's HMAC only over the raw request body, then hands the caller a `shop` value taken directly from the unauthenticated `X-Shopify-Shop-Domain` header. Because the header is not part of the signed content, any request whose body+HMAC pair is valid for the shared `api_secret_key` can carry an arbitrary `shop` value and still pass validation, breaking the intended binding `verified(body) == identity(shop)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is pulled straight from an HTTP header, independent of the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` as the tenant identity for the event that is dispatched to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (i.e., the body) against the shared `api_secret_key`: [4](#0-3) 

The equality the library implicitly claims is: `hmac_valid(body) ⇒ shop == originating_shop`. In reality, the HMAC only proves `hmac_valid(body)`; it says nothing about which shop's header accompanied that body. Since `api_secret_key` is shared across every shop that has installed the app, any merchant who installs the app (an unprivileged, self-service action requiring no special credentials) can capture a genuine `(body, hmac)` pair generated by their own store's webhook delivery, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with any victim shop's domain. `Registry.process` will accept it as valid and dispatch it to the handler labeled with the attacker-chosen `shop`.

### Impact Explanation
This breaks the tenant boundary the gem is expected to preserve: an app relying on `WebhookMetadata#shop` (as the gem's own webhook documentation instructs) to decide which merchant's data to create, update, or delete will act on behalf of a shop the attacker never controls. For mandatory topics such as `customers/redact` or `shop/redact` — which are also routed through `Registry.process` — this allows an attacker-installed shop to trigger redaction/compliance actions falsely attributed to a victim shop, and more generally enables cross-tenant data confusion/injection, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no access token, no `api_secret_key`, and no TLS interception: the attacker only needs to install the app on their own store (a normal, unprivileged flow) to obtain one legitimate `(body, hmac)` pair, then can arbitrarily choose the `shop` header value on the replayed request since it is never bound to the signature. The library does nothing to prevent this, other than what host applications add on their own (out of scope of this gem).

### Recommendation
Bind the `shop`/tenant identity into the value that is HMAC-verified, or independently confirm it against a source of truth (e.g., cross-check the header shop against a shop that is expected/registered for the given webhook subscription/session) before dispatching to the handler. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant-scoping decisions without additional verification (e.g., matching it against the app's stored session for the topic/webhook id).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, no privileged access needed).
2. Shopify delivers a legitimate webhook (e.g., `customers/data_request`) to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of body>`, and some raw JSON body the attacker fully controls the content of (they choose the topic and can influence body content by triggering it themselves).
3. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC solely from `raw_body` and the shared `api_secret_key`, which still matches, so `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` even though Shopify never sent this event for that shop.
