### Title
`calc_take_pnl` reachable from `Deposit`/`Withdraw` reverts on a normal, non-privileged rounding/precision drift, permanently bricking liquidity add/remove - (File: `program/src/processor.rs`)

### Summary
The reported Cooler issue is that an external dependency's internal invariant (`TRSRY.active`) can flip to a state that makes a core, non-recoverable function (`rebalance`) permanently revert. The closest reachable analog in this AMM program is `Processor::calc_take_pnl`, which is invoked unconditionally inside `process_deposit` and `process_withdraw` (the two LP-facing, unprivileged instructions) and hard-fails with `AmmError::CalcPnlError` whenever an internal invariant about pool value vs. the last stored `calc_pnl_x`/`calc_pnl_y` snapshot does not hold - with no fallback, retry, or ability to skip pnl accounting for the `Deposit`/normal `Withdraw` path.

### Finding Description
`calc_take_pnl` computes whether the current pool value (`pool_pc_amount * pool_coin_amount`) is still `>=` the last recorded snapshot value (`calc_pc_amount * calc_coin_amount`, derived from `target.calc_pnl_x` / `target.calc_pnl_y`): [1](#0-0) 

If this condition is ever violated, the function unconditionally returns `AmmError::CalcPnlError` with no recovery path: [2](#0-1) 

This function is called from `process_deposit` unconditionally (any depositor can trigger it) and from `process_withdraw` for every status except `WithdrawOnly`: [3](#0-2) [4](#0-3) 

`target.calc_pnl_x`/`calc_pnl_y` are updated after every deposit/withdraw/withdrawpnl using several chained `checked_sub`/`checked_add` on `U128` decimal-normalized values (`normalize_decimal_v2`/`restore_decimal`), which floor/truncate on every conversion: [5](#0-4) [6](#0-5) [7](#0-6) 

Because every deposit/withdraw path re-derives `total_pc_without_take_pnl`/`total_coin_without_take_pnl` from live vault balances (`Calculator::calc_total_without_take_pnl_no_orderbook`) but recomputes the `target` snapshot from repeatedly decimal-normalized (and thus rounded) intermediate values, small persistent rounding drift accumulates over many deposit/withdraw cycles. If drift ever causes the recorded snapshot product to exceed the live pool product (e.g., through repeated floor-rounding on `restore_decimal`/`normalize_decimal_v2` for a token pair with very different decimals, or through many rapid small withdraw/deposit cycles that shave the pool value down via truncation while the snapshot is only updated with the same truncation error), `calc_take_pnl` starts failing permanently for both `Deposit` and (non-`WithdrawOnly`) `Withdraw`. There is no code path that clears or resets `calc_pnl_x`/`calc_pnl_y` short of a privileged `SetParams`/status change to `WithdrawOnly` (which itself only bypasses the check for withdraw, not deposit).

This mirrors the reported bug class exactly: a state invariant maintained by the protocol's own internal accounting (analogous to Olympus TRSRY's `active` flag) can end up in a condition that makes an unprivileged, commonly-used instruction (`rebalance` there, `Deposit`/`Withdraw` here) permanently revert, with no try/catch, no graceful degradation, and no way for a normal user to recover funds through that path.

### Impact Explanation
If the invariant is violated, `Deposit` becomes permanently unusable (no LP can add liquidity) and `Withdraw` becomes permanently unusable for any status other than `WithdrawOnly` (an admin-only status change). LPs attempting normal withdrawal would have their funds effectively locked (frozen) until governance intervenes and flips the pool to `WithdrawOnly` - and even then, new deposits remain permanently blocked. This is a freezing-of-funds condition reachable purely through normal, permissionless use of `Deposit`/`Withdraw`, matching the severity bar of "permanent freezing of user or LP funds."

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires accumulated rounding drift across many deposit/withdraw cycles (more likely for token pairs with large decimal differences, e.g., 0 vs 9 decimals, or pools with very high transaction volume/small individual amounts, where `restore_decimal`/`normalize_decimal_v2` truncation is proportionally larger). It does not require any privileged actor, malicious validator, or off-chain component - it can emerge purely from organic protocol usage over time, the same "small likelihood, but real and unprivileged" profile the original TRSRY report was rated Medium for.

### Recommendation
- Avoid returning a hard, unrecoverable error from `calc_take_pnl` inside `process_deposit`; instead, treat a violated invariant defensively (e.g., clamp `delta_x`/`delta_y` to zero and skip pnl accounting for that call rather than aborting the whole instruction), similar to how `Withdraw` already special-cases `AmmStatus::WithdrawOnly` to skip pnl calc entirely. [4](#0-3) 
- Add an admin-callable recovery/reset path for `target.calc_pnl_x`/`calc_pnl_y` (or make `Deposit` also bypass `calc_take_pnl` in a restricted "deposit only" emergency mode) so a drifted invariant does not permanently brick core LP flows.
- Consider increasing intermediate precision or performing rounding in a fund-safe direction consistently across `normalize_decimal_v2`/`restore_decimal` so that drift can only ever move the invariant in the safe direction (pool value >= snapshot), never the reverse.

### Proof of Concept
Conceptual (cannot be fully proven without live rounding-drift simulation across many transactions, which is out of scope for static analysis):
1. Create a pool with highly disparate coin/pc decimals (e.g., coin_decimals = 0, pc_decimals = 9) via `Initialize2`.
2. Repeatedly call `Deposit` and `Withdraw` with small amounts chosen to maximize truncation loss in `restore_decimal`/`normalize_decimal_v2` on each call (each call updates `target.calc_pnl_x`/`calc_pnl_y` using floored decimal-normalized deltas while `calc_total_without_take_pnl_no_orderbook` reads exact on-chain vault balances).
3. After enough cycles, the accumulated rounding causes `pool_pc_amount.checked_mul(pool_coin_amount) < calc_pc_amount.checked_mul(calc_coin_amount)` in `calc_take_pnl`.
4. From that point on, every subsequent `Deposit` call and every `Withdraw` call while `amm.status != WithdrawOnly` returns `AmmError::CalcPnlError`, permanently reverting. [8](#0-7) [2](#0-1)
