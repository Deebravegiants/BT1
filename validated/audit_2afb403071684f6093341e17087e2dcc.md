### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only binds the raw body, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop` (and `topic`/`webhook_id`/`api_version`) values taken from request headers to build the `WebhookMetadata` passed to the host app's handler. The HMAC never binds the `shop` value, so any two payload/HMAC pairs that are valid for the app's single shared `client_secret` can be replayed with an arbitrary `shop` header, letting one tenant's genuine webhook be reattributed to another tenant.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 
`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the signed bytes: [3](#0-2) 

`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, to_signable_string)` and compares it to the `hmac` header value: [4](#0-3) 

`Registry.process` uses exactly this check as its sole authorization gate, then forwards the *unverified* `request.shop` value into `WebhookMetadata`, which the host application's `WebhookHandler#handle` uses to attribute the payload to a specific merchant: [5](#0-4) [6](#0-5) 

The identity binding that is broken (as an equality): the gem treats
`hmac_valid(raw_body, api_secret_key) == true` as proof that `shop_header == "the shop that actually produced raw_body"`.
In reality `hmac_valid` only proves `raw_body` was signed with the app's single, shop-independent `client_secret` — it says nothing about which shop the header claims to be. Because `client_secret` is shared by every merchant that has the app installed, any merchant who is a legitimate app user receives (and thus possesses) genuinely-signed `(raw_body, hmac)` pairs for their own store. That merchant can replay the same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for any other install of the same app (e.g., a competitor's shop, whose domain is public). `HmacValidator.validate` still succeeds because it never looks at the `shop` header, and `Registry.process` hands the forged shop identity straight to the handler.

### Impact Explanation
This is a cross-tenant identity-binding break: a validated payload from tenant A can be relabeled and delivered as tenant B's data with a passing signature check. Depending on how the host application's `WebhookHandler` implementation uses `data.shop` (e.g., to look up the merchant's stored session/access token and perform authenticated follow-up actions, or to write/sync business data keyed by shop), this enables cross-tenant data injection or corruption using only knowledge of the victim's `myshopify.com` domain, which is public. This matches the "cross-tenant access" Critical impact category, since the gem's own webhook trust boundary conflates "signature valid" with "shop claim authentic."

### Likelihood Explanation
Exploitation requires no secrets: the attacker only needs (a) their own legitimate app installation (any merchant can install a public/embedded app) so they receive genuinely HMAC-signed webhook deliveries, and (b) the victim's public shop domain. No access token, `api_secret_key`, or privileged account is required — only the ability to author/trigger a webhook-eligible action on the attacker's own store and replay the resulting request to the app's webhook endpoint with a modified header.

### Recommendation
Bind the claimed shop (and other trust-sensitive dispatch fields such as topic/webhook id) into the signed material, or otherwise cross-validate the header-derived `shop` against an independent authenticated source (e.g., verify the shop is one that has genuinely completed OAuth/token exchange with this app and correlate via a per-shop secret/session rather than the single shared `client_secret`) before constructing `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated header data and must not be used as a sole tenant-identity key without additional verification (e.g. cross-checking against the app's known installed shops before performing tenant-scoped side effects).

### Proof of Concept
1. App `X` is installed on both `attacker-shop.myshopify.com` (attacker) and `victim-shop.myshopify.com` (victim).
2. Attacker performs an action on their own store that triggers a genuine webhook delivery from Shopify to `https://app-x.example.com/webhooks`, e.g. `orders/create`. Attacker's own server/proxy captures the exact raw request: headers `x-shopify-hmac-sha256: <H>`, `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and raw body `B`. Because `H = HMAC-SHA256(client_secret, B)` and `client_secret` is shared for all installs of app `X`, this is a valid signature independent of shop.
3. Attacker replays the exact same body `B` and header `x-shopify-hmac-sha256: <H>`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`, and sends it directly to the app's public webhook endpoint.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` recomputes HMAC over `B` only (per `to_signable_string`) and it matches `H`, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, topic: "orders/create", ...)`, even though the payload never originated from the victim's store.
