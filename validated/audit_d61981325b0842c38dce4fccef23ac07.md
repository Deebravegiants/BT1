### Title
Webhook `shop-domain` (and `topic`/`webhook_id`) header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when computing/verifying the webhook HMAC, while the `shop`, `topic`, `api_version`, and `webhook_id` values consumed by the handler are taken directly from unauthenticated HTTP headers. Because a single `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant who can trigger a webhook for their own store obtains a `(body, hmac)` pair that remains valid no matter which `shop-domain` header accompanies it, enabling cross-tenant webhook injection.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `hmac`, `shop`, `topic`, `api_version`, and `webhook_id` accessors are all sourced from HTTP headers, none of which are included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (the body) and the app's secret, and does not fold in any header value: [3](#0-2) 

`Registry.process` then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` straight from the (unauthenticated) headers, after only checking that the HMAC over the body is valid: [4](#0-3) 

`WebhookMetadata` — the object handed to the host application's `WebhookHandler#handle` — carries this unverified `shop` value verbatim: [5](#0-4) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` says nothing about which shop, topic, or webhook the body belongs to. The equality that should hold but doesn't is: `shop header used by the handler == shop that Shopify actually attributes to this exact signed payload`. Since `Context.api_secret_key` (the app's `client_secret`) is identical for every shop tenant of a multi-tenant app, any two webhook deliveries — regardless of originating shop — that happen to carry the same body produce the same valid HMAC. A user who installs the app on their own store (an unprivileged, non-elevated action available to any merchant/internet user who can install a public app) can capture a legitimately-signed `(body, hmac)` pair from a webhook fired for their own store, then replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to a victim shop. `HmacValidator.validate` still returns `true` because it only re-derives the HMAC from the body, so `Registry.process` proceeds and invokes the host app's handler believing the payload is authentic data belonging to the victim shop.

### Impact Explanation
This is a cross-tenant confusion primitive: an attacker can cause the host application to process attacker-controlled data (any webhook body they can legitimately obtain, e.g. an `orders/create` or `customers/data_request` payload from their own shop) under the identity of a different, victim shop. Depending on how the host app's `WebhookHandler` implementations use `WebhookMetadata#shop` (e.g., to select the tenant's database record, revoke access, react to `app/uninstalled`, trigger GDPR data operations, etc.), this can lead to cross-tenant data corruption, spoofed lifecycle events (e.g., forging `app/uninstalled` or `shop/redact` for a shop the attacker doesn't own), or other tenant-boundary violations — matching the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only that the attacker be a merchant capable of installing the app on a store they control (a normal, unprivileged action) and being able to POST directly to the app's public webhook endpoint (which must be internet-reachable for Shopify to deliver webhooks). No access to `api_secret_key`, access tokens, or the victim's credentials is required — only replay of a previously-observed, self-generated `(body, hmac)` pair with a swapped header.

### Recommendation
Include the `shop`, `topic`, `api_version`, and `webhook_id` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed payload), so that `HmacValidator.validate` fails if any of these attacker-controllable headers are altered relative to what Shopify originally signed for that specific delivery.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook subscribed by the app (e.g., updates an order), causing Shopify to POST a body `B` with headers `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/updated` to the app's webhook endpoint. The attacker controls the traffic to their own server/proxy and can capture `B` and `H`.
2. Attacker crafts a new HTTP POST to the same public webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`, e.g. `app/uninstalled`, if a handler is registered for it and the body shape is compatible).
3. `Request.new` parses the forged headers and body without complaint (only presence of headers is checked): [6](#0-5) 
4. `HmacValidator.validate(request)` recomputes `HMAC(secret, B)`, which equals `H` because the body was unmodified, so validation passes even though the `shop` header no longer matches the shop that actually produced `H`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)`, causing the host application to act on `B` as if it were legitimately signed data belonging to `victim-shop.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
