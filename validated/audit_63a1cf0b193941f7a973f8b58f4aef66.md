### Title
Webhook `shop-domain` / `topic` headers are not covered by the HMAC, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body, never the `shop-domain`, `topic`, or `webhook-id` headers. `Registry.process` validates only that body against the HMAC and then trusts the unauthenticated `shop` and `topic` headers to build the `WebhookMetadata` passed to the app's handler.

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook == shop that produced the signed payload`. This equality is broken because the HMAC signature only covers `@raw_body`: [2](#0-1) 

`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to each other or to the body: [3](#0-2) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`: [4](#0-3) 

`Registry.process` accepts the request once the body-only HMAC passes, then forwards the caller-supplied `topic` and `shop` headers verbatim to the registered handler: [5](#0-4) 

Because a merchant/developer can legitimately install the app on their own store (or otherwise obtain a genuinely-signed webhook body+HMAC pair for their own shop from Shopify), they hold a body/HMAC pair that is valid for *any* `shop-domain` and `topic` header value, since neither is part of the signed content. Re-sending that exact body and HMAC to the app's webhook endpoint with a different `x-shopify-shop-domain` header (a victim's shop) and/or a different `x-shopify-topic` passes HMAC validation while attributing the event to a shop the attacker does not control.

### Impact Explanation
This breaks the tenant boundary the app relies on to route webhook data. An app developer implementing `WebhookHandler#handle` naturally trusts `data.shop` and `data.topic` as authenticated facts (since a valid HMAC was already required), and uses them to look up/update per-merchant state (e.g., process `app/uninstalled`, `customers/data_request`, `shop/redact`, or order/product mutations against the victim's tenant record). An attacker with no access token, no `api_secret_key`, and no privileged account can inject webhook events falsely attributed to a shop they don't own, i.e., cross-tenant data confusion/injection into another merchant's account — matching the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Reasonably likely: the attacker only needs one legitimately-signed body+HMAC pair, obtainable by installing the target app on a shop they control (all app developers on the Shopify platform can freely create development/test stores) or by observing/replaying any webhook delivery they legitimately received. No secrets, tokens, or victim credentials are required — only header manipulation on replay, which is fully within an unprivileged internet user's capability against a public webhook endpoint.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body (e.g., verify them against a separately-authenticated channel/session per shop) before constructing `WebhookMetadata`. At minimum, document that consumers of `ShopifyAPI::Webhooks::Registry.process` must not rely on `shop`/`topic` as authenticated unless a stronger binding is added in the gem, since header replay against a single valid body/HMAC pair currently defeats per-tenant attribution.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and lets it fire a real webhook (e.g., `orders/create`), capturing the raw JSON body and its valid `x-shopify-hmac-sha256` value computed by Shopify with the app's `api_secret_key`.
2. Attacker POSTs that exact captured body and HMAC header to the app's webhook endpoint again, but replaces:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any registered topic, since topic isn't signed either — only same-length constraints from the real payload's shape matter if the handler parses body fields)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) raw body against the (unchanged, still-valid) HMAC — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler, which processes an uninstall/data event for `victim-shop.myshopify.com` that the attacker never actually triggered on that shop.
