### Title
Unvalidated mint decimals in `Initialize2` allow permanently bricking a pool via panicking `checked_pow` unwrap in decimal-normalization math — (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`process_initialize2` accepts arbitrary, pool-creator-supplied SPL mints as `coin_mint`/`pc_mint` and stores their raw `decimals` field (a `u8`, unrestricted by the SPL Token program, so any value 0–255 is a valid mint) directly into `AmmInfo.pc_decimals`/`coin_decimals` without any upper-bound validation. <cite repo="Alyssadaypin/raydium-amm--007" path="program/src/processor.rs" start="742="745" end="745" /> [1](#0-0)  Every subsequent `Deposit`, `Withdraw`, `SwapBaseIn(V2)`, and `SwapBaseOut(V2)` instruction calls `Calculator::normalize_decimal`/`normalize_decimal_v2`/`restore_decimal`, which compute `U128::from(10).checked_pow(native_decimal.into())` and then `.unwrap()` the result. [2](#0-1) 

### Finding Description
`U128` is a 128-bit integer (max ≈ 3.4028×10^38). `10^39` already overflows a `U128`, so `checked_pow` returns `None` once `native_decimal >= 39`. Since `amm.pc_decimals`/`amm.coin_decimals` are populated straight from the pool-creator-chosen mints' `decimals` field with no range check, an unprivileged pool creator can mint an SPL token with `decimals` set to, e.g., 100 (a perfectly valid SPL Token Mint — the SPL Token program does not restrict `decimals` to realistic ranges) and use it as the `coin_mint` (or `pc_mint`) in `Initialize2`. [3](#0-2) 

Once the pool is initialized this way, `amm.coin_decimals`/`amm.pc_decimals` are permanently fixed in the on-chain `AmmInfo` account (there is no `SetParams` path to change decimals). Every normalization call performed by `process_deposit`, `process_withdraw`, `process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`, and `process_withdrawpnl` invokes `Calculator::normalize_decimal_v2`/`restore_decimal` with this decimals value: [4](#0-3) [5](#0-4)  Because `checked_pow` returns `None` and the code immediately `.unwrap()`s it, every one of these calls panics, aborting the transaction with a runtime panic rather than a controlled `ProgramError`. [6](#0-5) 

This is the direct structural analog of the TensorFlow `Conv3DBackpropFilterV2`/`UnsortedSegmentJoin` bug class: an externally supplied, unvalidated numeric parameter (there: `num_segments`; here: mint `decimals`) is fed straight into an arithmetic/allocation routine that assumes the value is within a safe range, and the missing bounds check leads to an unconditional `unwrap`/`CHECK` failure.

### Impact Explanation
Because the AMM already accepted user deposit tokens into the vaults at `Initialize2` time (`init_coin_amount`/`init_pc_amount` are transferred to the vaults before the decimals-derived panic path is even reachable in later calls), and because `amm.coin_decimals`/`amm.pc_decimals` cannot be altered after initialization, the pool becomes **permanently unusable**: every future `Deposit`, `Withdraw`, and swap instruction on that pool panics inside `normalize_decimal_v2`/`restore_decimal`, so the funds already sitting in `amm_coin_vault`/`amm_pc_vault` (the pool creator's own initial liquidity, and any LP tokens minted to them) can never be withdrawn through the program logic. This satisfies "permanent freezing of user or LP funds" — the vaults and minted LP tokens are stuck with no on-chain code path capable of returning `InsufficientFunds`/similar recoverable errors, since the panic occurs before any economic checks.

### Likelihood Explanation
Reachable from a single `Initialize2` transaction fully controlled by an unprivileged pool creator: they need only mint two SPL tokens (trivial, permissionless, no extra signer) with one mint's `decimals` field set ≥ 39, then call `Initialize2` supplying that mint as `coin_mint` or `pc_mint`. No malicious validator, leaked key, or off-chain component is required — the attack is a pure single-transaction, attacker-chosen-account/data operation squarely within the `Initialize2` entry point covered by scope.

### Recommendation
In `process_initialize2`, validate `coin_mint.decimals` and `pc_mint.decimals` against a safe upper bound (e.g., ≤ 19, consistent with `sys_decimal_value` scaling and `U128`'s ~38-digit capacity, leaving headroom for multiplication) before proceeding, returning a proper `AmmError` (e.g., `InvalidCoinMint`/`InvalidPCMint`) rather than allowing the value to propagate into `AmmInfo`. Additionally, harden `Calculator::normalize_decimal`, `normalize_decimal_v2`, and `restore_decimal` to use `checked_pow(...).ok_or(AmmError::...)?` instead of `.unwrap()`, so any future latent decimals-related overflow degrades to a recoverable program error instead of an unconditional panic.

### Proof of Concept
1. Attacker creates two new SPL Token mints, `mint_a` with `decimals = 9` and `mint_b` with `decimals = 100` (both valid per the SPL Token program, which does not bound the `decimals` field).
2. Attacker funds an ATA for each mint and calls `Initialize2` (`program/src/instruction.rs` `initialize2` builder) with `amm_coin_mint = mint_b`, `amm_pc_mint = mint_a`, arbitrary `init_coin_amount`/`init_pc_amount` > 0.
3. `process_initialize2` unpacks `coin_mint` and sets `amm.coin_decimals = coin_mint.decimals = 100` via `amm.initialize(...)`, with no bounds check. [1](#0-0) 
4. Any later call to `process_deposit`/`process_withdraw`/`process_swap_base_in` on this pool computes `Calculator::normalize_decimal_v2(total_coin_without_take_pnl, amm.coin_decimals=100, amm.sys_decimal_value)`, which executes `U128::from(10).checked_pow(100.into())` → `None` → `.unwrap()` panics, aborting the transaction. [6](#0-5) 
5. Since the pool's `coin_decimals` is immutable post-initialization and the initial deposit tokens are already locked in the vaults from step 2, the pool and its liquidity are permanently frozen.

    pub fn normalize_decimal(val: u64, native_decimal: u64, sys_decimal_value: u64) -> u64 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = Self::to_u64(
            ret_mut
                .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
                .unwrap()
                .as_u128(),
        )
        .unwrap();
        ret
    }

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }
