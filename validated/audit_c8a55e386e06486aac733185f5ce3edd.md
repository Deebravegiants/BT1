This confirms the root cause. The `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the unauthenticated `shopify-shop-domain` HTTP header [2](#0-1) . ### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used by the app's webhook handler from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature verification in `HmacValidator` and `Request#to_signable_string` only covers the raw request body. The shop header is never part of the signed payload, so it can be freely rewritten by anyone able to produce (or replay) a validly-signed body.

### Finding Description
`HmacValidator.validate` calls `validate_signature`, which computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it (via `OpenSSL.secure_compare`) to the received `hmac` header value [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . Meanwhile `shop` is read straight from the `shopify-shop-domain` header without any cryptographic binding [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — validating the body/HMAC pair — and then unconditionally trusts `request.shop` to build the `WebhookMetadata` object passed to the app-registered handler [4](#0-3) .

Since Shopify computes the HMAC the same way (over the raw body using the shared `client_secret`) for every shop using this app, and the shared secret is identical across all shops/tenants, any webhook payload+HMAC pair legitimately generated for the attacker's own shop (or the same JSON body Shopify sends, e.g. an empty body `{}` for many webhooks, or one with generic content) remains valid regardless of which `shop-domain` header is attached to the request. This breaks the identity binding: `shop authenticated == shop used to process the webhook` is not enforced — the bytes verified by HMAC (raw body) are decoupled from the tenant identity claim used by the handler (`shop` header).

### Impact Explanation
This is a cross-tenant identity confusion: the app-level webhook handler receives a `WebhookMetadata` believing it originates from shop A when the cryptographic proof (HMAC) only certifies the body, not the shop. An attacker controlling one shop that installed the app can capture a validly-signed webhook (or, in cases of generic/predictable bodies, forge one signed with the same shared secret across tenants) and resubmit it with an arbitrary victim `shop-domain` header, causing the host app to process actions/state changes attributed to the victim's tenant. Depending on how the app's handler uses `WebhookMetadata#shop` (e.g., to look up a session, update shop-scoped records, or trigger actions), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's tenant — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The `api_secret_key` is shared across all shops that install a given app (it's the app's client secret, not a per-shop secret), so the HMAC alone does not prove which shop the webhook is for — only that some request bearing this body was signed by Shopify using the app's global secret. Any actor who can trigger a webhook delivery for their own shop (installing the app on a store they control, as any unprivileged internet user can do) can capture a genuine `raw_body` + `hmac` pair and then send an HTTP request directly to the app's webhook endpoint with the `shop-domain` header set to any other shop's domain. No access token, TLS interception, or privileged account is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed payload before trusting it. At minimum, `Registry.process` should cross-validate that the `shop` header value is consistent with a shop-specific expectation (e.g., matched against a known/installed shop record) rather than trusting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; a webhook (e.g., `orders/create` with a generic/reproducible body such as `{}`) is delivered by Shopify with headers `x-shopify-hmac-sha256: <hmac-of-body-with-shared-secret>`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures the raw body and the HMAC header value.
3. Attacker sends a new HTTP POST directly to the app's webhook endpoint, reusing the identical raw body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC only over the raw body [3](#0-2)  — it still matches, since the body and secret are unchanged.
5. `Registry.process` proceeds to call the handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` is `"victim.myshopify.com"` [6](#0-5) , causing the app to process the payload as if it belongs to the victim's tenant.
