## Finding

### Title
Missing `chain_id` domain separation in `RotationProofChallenge` and `SignerCapabilityOfferProofChallengeV2` enables cross-chain replay of authentication-key rotation and signer-capability delegation - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
The external report's core invariant is: *a signed authorization message must be bound to a specific chain via a `chain_id`, otherwise it can be replayed on any other chain that shares the same signing scheme and validation logic.* In `aptos-core`'s account module, this exact invariant is broken for the messages that authorize **authentication-key rotation** and **signer-capability delegation**. `RotationProofChallenge` [1](#0-0)  and `SignerCapabilityOfferProofChallengeV2` [2](#0-1)  both omit `chain_id`, while the sibling struct `RotationCapabilityOfferProofChallengeV2` explicitly documents and includes it for this exact reason: "This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message." [3](#0-2) 

### Finding Description
`rotate_authentication_key` builds a `RotationProofChallenge` using only `sequence_number`, `originator`, `current_auth_key`, and `new_public_key` — no `chain_id` — and verifies two signatures (`cap_rotate_key`, `cap_update_table`) against it. [4](#0-3)  The same struct, with the same missing field, is reused in `rotate_authentication_key_with_rotation_capability`, keyed off `get_sequence_number(delegate_address)`. [5](#0-4) 

The `sequence_number` used in the challenge is not a transaction nonce tied to a unique global counter — it is simply the current on-chain `sequence_number` of the account being rotated (or of the delegate), read fresh from account state. [6](#0-5)  Any two chains that derive the same account state (identical address, identical current auth key/public key, identical sequence number — the common case for freshly created accounts, which start at `sequence_number = 0`) will produce a byte-identical `RotationProofChallenge` message. Because the challenge has no chain-specific salt, a signature valid on one Aptos-based chain (e.g., testnet, devnet, or any other aptos-core-derived network sharing account genesis/derivation logic) is also valid on another.

The verification path itself does not compensate for this: `assert_valid_rotation_proof_signature_and_get_auth_key` only checks the Ed25519/MultiEd25519 signature against the challenge struct and matches nothing chain-specific. [7](#0-6)  Compare this to `offer_rotation_capability`, which builds its proof challenge including `chain_id: chain_id::get()` precisely to block this replay class. [8](#0-7) 

### Impact Explanation
An attacker who observes a `cap_rotate_key`/`cap_update_table` signature pair (or a signer-capability delegation signature) authorized by a user on one Aptos-derived chain can replay it on another Aptos-derived chain to rotate that user's authentication key or hijack their signer-capability delegation there — without the user's consent on that second chain. Since the authentication key controls custody of all assets (APT, fungible assets, objects) held by the account, and rotation directly reassigns account control, a successful replay is a full custody takeover of the target account on the second chain: attacker gains signing authority over the account and can then transfer/burn/freeze any assets it holds. This matches the custody-impact gate criterion of "unauthorized takeover of ... resource-account control ... tied to live assets" and "owner reassignment."

### Likelihood Explanation
Exploitability depends on account state (address, current auth key, sequence number) coinciding across two networks that both run this framework code — which is realistic for many "aptos-core fork" or multi-network deployments (mainnet/testnet/devnet, or independent Aptos-SDK-based L1s) where users reuse the same key material and create accounts identically (sequence number starting at 0 is the most common trigger). This requires no privileged access and no cooperation from the victim beyond having signed a rotation message on any one such chain — an unprivileged, self-contained root cause in `account.move`.

### Recommendation
Add a `chain_id` field to `RotationProofChallenge` and `SignerCapabilityOfferProofChallengeV2`, mirroring `RotationCapabilityOfferProofChallengeV2`, and populate it via `chain_id::get()` in `rotate_authentication_key`, `rotate_authentication_key_with_rotation_capability`, and the signer-capability offer path so that rotation/delegation signatures are bound to a single chain and cannot be replayed across networks.

### Proof of Concept
1. On Chain A (e.g., testnet), a user creates a fresh account with public key `pk_old` at address `addr` (`sequence_number = 0`).
2. The user rotates their key to `pk_new`, signing `RotationProofChallenge{ sequence_number: 0, originator: addr, current_auth_key: addr, new_public_key: pk_new }` with both `pk_old` and `pk_new`, producing `cap_rotate_key`/`cap_update_table` and submitting via `rotate_authentication_key` [9](#0-8) .
3. An attacker who has observed these two signatures (e.g., from a public testnet transaction) replays them via `rotate_authentication_key` on Chain B (e.g., mainnet or another aptos-core-derived chain), where the user coincidentally holds funds at the same `addr` with the same `pk_old` and `sequence_number = 0`.
4. Since the challenge struct contains no `chain_id`, the signatures verify identically on Chain B, rotating the user's mainnet account's authentication key to `pk_new` without the user ever authorizing that action on Chain B, giving the attacker (or whoever controls `pk_new`) full custody of the account's assets on Chain B.

    public entry fun rotate_authentication_key(
        account: &signer,
        from_scheme: u8,
        from_public_key_bytes: vector<u8>,
        to_scheme: u8,
        to_public_key_bytes: vector<u8>,
        cap_rotate_key: vector<u8>,
        cap_update_table: vector<u8>,
    ) acquires Account, OriginatingAddress {
        let addr = signer::address_of(account);
        ensure_resource_exists(addr);
        let account_resource = &mut Account[addr];
        let old_auth_key = account_resource.authentication_key;
        // Verify the given `from_public_key_bytes` matches this account's current authentication key.
        if (from_scheme == ED25519_SCHEME) {
            let from_pk = ed25519::new_unvalidated_public_key_from_bytes(from_public_key_bytes);
            let from_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&from_pk);
            assert!(
                account_resource.authentication_key == from_auth_key,
                error::unauthenticated(EWRONG_CURRENT_PUBLIC_KEY)
            );
        } else if (from_scheme == MULTI_ED25519_SCHEME) {
            let from_pk = multi_ed25519::new_unvalidated_public_key_from_bytes(from_public_key_bytes);
            let from_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&from_pk);
            assert!(
                account_resource.authentication_key == from_auth_key,
                error::unauthenticated(EWRONG_CURRENT_PUBLIC_KEY)
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };

        // Construct a valid `RotationProofChallenge` that `cap_rotate_key` and `cap_update_table` will validate against.
        let curr_auth_key_as_address = from_bcs::to_address(account_resource.authentication_key);
        let challenge = RotationProofChallenge {
            sequence_number: account_resource.sequence_number,
            originator: addr,
            current_auth_key: curr_auth_key_as_address,
            new_public_key: to_public_key_bytes,
        };

        // Assert the challenges signed by the current and new keys are valid
        assert_valid_rotation_proof_signature_and_get_auth_key(
            from_scheme,
            from_public_key_bytes,
            cap_rotate_key,
            &challenge
        );
        let new_auth_key = assert_valid_rotation_proof_signature_and_get_auth_key(
            to_scheme,
            to_public_key_bytes,
            cap_update_table,
            &challenge
        );

    fun assert_valid_rotation_proof_signature_and_get_auth_key(
        scheme: u8,
        public_key_bytes: vector<u8>,
        signature: vector<u8>,
        challenge: &RotationProofChallenge
    ): vector<u8> {
        if (scheme == ED25519_SCHEME) {
            let pk = ed25519::new_unvalidated_public_key_from_bytes(public_key_bytes);
            let sig = ed25519::new_signature_from_bytes(signature);
            assert!(
                ed25519::signature_verify_strict_t(&sig, &pk, *challenge),
                std::error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE)
            );
            ed25519::unvalidated_public_key_to_authentication_key(&pk)
        } else if (scheme == MULTI_ED25519_SCHEME) {
            let pk = multi_ed25519::new_unvalidated_public_key_from_bytes(public_key_bytes);
            let sig = multi_ed25519::new_signature_from_bytes(signature);
            assert!(
                multi_ed25519::signature_verify_strict_t(&sig, &pk, *challenge),
                std::error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE)
            );
            multi_ed25519::unvalidated_public_key_to_authentication_key(&pk)
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        }
    }
