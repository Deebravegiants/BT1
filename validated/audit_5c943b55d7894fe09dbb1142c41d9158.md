### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` value used to route and attribute webhook data to a tenant is read from an unsigned HTTP header. Any party who can obtain one legitimate `(body, hmac)` pair for the app — e.g. by installing the app on their own store and receiving a real webhook — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, since the header is outside the signed content.

### Finding Description
The equality that should hold is: **the shop identity delivered to the handler == the shop identity covered by the HMAC**. Instead:

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 
- `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body HMAC), then immediately forwards `request.shop` into `WebhookMetadata` passed to the app's handler, without any check binding it to the signed payload: [3](#0-2) 

The gem's own documentation instructs app developers to treat `data.shop` as the authoritative tenant identifier for the webhook (e.g. to key a job queue or database write), reinforcing that this value is meant to be trusted as tenant-scoped: [4](#0-3) [5](#0-4) 

Because Shopify signs webhooks with a single `client_secret` per app (not per shop), any shop that has installed the app can generate a valid `(body, hmac)` pair. That pair remains valid under `HmacValidator.validate` (see `validate_signature`, which recomputes HMAC over `to_signable_string` and compares it to the received value): [6](#0-5)  The header carrying the shop can be freely swapped without invalidating that HMAC.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged installer of the app (attacker's own shop) can produce webhook requests that are cryptographically valid per this gem's own validation, but falsely attributed to any other merchant shop. Depending on the host app's usage of `data.shop` (as instructed by this gem's docs) this enables cross-tenant data injection, cache/queue poisoning keyed by shop, or triggering shop-scoped side effects (e.g. mandatory-topic handlers like `customers/redact`, `shop/redact`) against a victim tenant — a cross-tenant access vulnerability.

### Likelihood Explanation
Any user capable of installing the app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) can capture a legitimate webhook body+HMAC and replay it against the shared webhook endpoint with a forged shop header. No access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signable content, or otherwise cryptographically bind the header-derived `shop` to the verified payload before it is trusted (e.g., only accept `shop` values that are already associated with a locally-stored access token/session obtained through this gem's own OAuth flow), rejecting requests where the claimed shop cannot be corroborated by an existing session/installation record.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, completing OAuth normally.
2. Shopify sends a legitimate webhook to the app's callback URL with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` (they control the receiving endpoint's logs, or their own server if the app lets them configure it).
4. Attacker sends a new POST to the same app webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since `to_signable_string` only covers `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
5. `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only recomputes HMAC over `B`. It then dispatches `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed B, ...)` to the app's handler, which is now processing forged data under the victim's identity.
