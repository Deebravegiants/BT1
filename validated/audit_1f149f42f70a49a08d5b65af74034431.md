### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only. The `shop-domain` header — which is later trusted as the tenant identity and handed to the app's webhook handler — is never included in the signed material. An attacker who possesses one valid `(body, hmac)` pair (e.g., generated from a webhook delivered to their own shop) can resubmit it with an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header, and `Utils::HmacValidator.validate` will still accept it, because it verifies only the body against the secret.

### Finding Description
`Request#to_signable_string` returns just the raw JSON body, and `hmac` is read straight from the header: [1](#0-0) [2](#0-1) 

The `shop` accessor simply reads the `shop-domain` header, with no cryptographic tie to the signed body: [3](#0-2) 

`HmacValidator.validate_signature` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it only authenticates the body bytes, never the shop header: [4](#0-3) 

`Registry.process` gates only on this body-only HMAC check, then forwards the unauthenticated `request.shop` directly into `WebhookMetadata`, which apps use to attribute the payload to a tenant: [5](#0-4) 

The binding that should hold is:
`shop_bound_by_hmac == shop_delivered_to_handler`

but instead:
`shop_bound_by_hmac == ∅ (only raw_body is signed)`
`shop_delivered_to_handler == attacker_controlled_header`

Because the signature never covers `shop-domain`, any valid `(body, hmac)` pair remains valid under any shop header value.

### Impact Explanation
An attacker (a merchant installing the app, or anyone who can trigger/capture one legitimate webhook delivery for any shop, including their own) can replay that body+signature pair while substituting a victim shop's domain in the header. The application, trusting `WebhookMetadata#shop`, will process attacker-controlled webhook content as if it originated from the victim tenant — e.g., writing records, triggering side effects, or overwriting per-tenant state keyed by `shop`. This is a cross-tenant data/action confusion vulnerability, since it lets one tenant's traffic be attributed to another tenant purely by header manipulation, without needing the `api_secret_key`.

### Likelihood Explanation
Likelihood is high for any app that keys tenant-specific behavior off `WebhookMetadata#shop`, since obtaining one legitimate `(body, hmac)` pair only requires triggering any webhook-eligible event in an attacker's own store (a normal, unprivileged action), and the header is a plain HTTP header trivially modified on replay.

### Recommendation
Include the shop domain (and any other identity fields such as webhook topic and API version) in the signed material used to verify the webhook, or independently corroborate `request.shop` against a value obtained through an authenticated channel (e.g., cross-check with the registered subscription callback, or require the caller to bind webhook data to a session established via OAuth) before trusting it as the tenant identity in `WebhookMetadata`.

### Proof of Concept
1. As an attacker, create/own a development store and register the app's webhook endpoint for a topic (e.g. `orders/create`).
2. Trigger the event in the attacker's own store; capture the resulting POST — headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `B`.
3. Resend the exact same request to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and passes; `Registry.process` calls the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to process attacker-supplied data under the victim's tenant identity.
