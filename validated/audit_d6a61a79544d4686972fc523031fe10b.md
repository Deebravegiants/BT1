### Title
Permanent front-running griefing of AMM pool creation via market-only deterministic PDA derivation - ([File: program/src/processor.rs])

### Summary
`Initialize2` derives the addresses for the AMM account, LP mint, target-orders account, and coin/pc vaults deterministically from `program_id` and the **market account key only** (a fixed, publicly-known seed), with no dependency on the caller's wallet or any nonce. Because these PDAs are fully predictable by anyone who knows which Serum/OpenBook market a project intends to use, an attacker can front-run the legitimate pool creator, permanently occupy those PDAs with a minimally-funded pool, and prevent the intended pool for that market from ever being created — the exact same "deterministic-identifier front-run/griefing" bug class described in the nouns-builder report (deterministic `proposalId` allows front-run + cancel to permanently block a specific proposal).

### Finding Description
`Self::process_initialize2` computes the addresses for the AMM account, LP mint, target orders, and coin/pc vaults via `generate_amm_associated_account`, `generate_amm_associated_spl_mint`, and `generate_amm_associated_spl_token`, all of which call `get_associated_address_and_bump_seed(program_id, &market_account.key, associated_seed, program_id)`. [1](#0-0) [2](#0-1) 

These seeds are: the fixed program constants `AMM_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`, `LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED` combined only with the **market pubkey**. [3](#0-2) 

In `process_initialize2`, the `market_info` account is explicitly documented as "Just a seed for AMM account. Can be any account," and is used directly as the seed input to derive all of these addresses. [4](#0-3) 

There is no binding to `user_wallet_info` (the creator) or to any nonce/counter in the address derivation — the resulting pool address, LP mint, and vaults are 100% deterministic and publicly computable from the market pubkey alone. The guard against re-creation is `generate_amm_associated_*` checking that the target account is still owned by the System Program; if it is already owned by the AMM program, the call reverts with `AmmError::RepeatCreateAmm`. [5](#0-4) [6](#0-5) 

Because any market's future canonical AMM pool address is knowable in advance, an attacker can observe a project preparing to call `Initialize2` for a given `market` (e.g., in the mempool, or simply by knowing which OpenBook market a token team intends to use), and instead submit their own `Initialize2` call for that same `market` first — funding the vaults with a trivial non-zero amount (only `amm_coin_vault.amount == 0` is rejected, no minimum-liquidity floor is enforced) and paying the `create_pool_fee`. [7](#0-6) 

Once the attacker's transaction lands first, the AMM account, LP mint, and vault PDAs for that market are permanently allocated and owned by the AMM program, so `amm.status != AmmStatus::Uninitialized` and/or `RepeatCreateAmm` will cause every subsequent `Initialize2` call for the same market to fail forever — there is no `cancel`/`close` path in scope that would reclaim these PDAs. This mirrors the nouns-builder root cause: a deterministic identifier computed purely from attacker-visible input data with no per-caller differentiator, enabling permanent front-run griefing of the "create" action.

### Impact Explanation
This is a permanent denial-of-service against pool creation for a specific market: once squatted, the legitimate project can never initialize the canonical Raydium AMM pool for that OpenBook market through this program, since the PDAs are exhausted and immutable. Any user funds already routed to that market/pool would also be captured by whatever minimal, attacker-controlled pool now occupies that deterministic address — the attacker fully controls the pool's initial price ratio (via `init_coin_amount`/`init_pc_amount`), and LPs/traders who assume "the" pool for that market is the legitimate one interact with an attacker-seeded, price-manipulable pool instead. This constitutes an unauthorized privileged effect (squatting authority over a specific market's on-chain AMM identity) and a permanent freezing of the ability to create the intended pool.

### Likelihood Explanation
Any unprivileged actor who can submit a single transaction with the target `market` pubkey (public, known in advance for the market a project intends to launch on) can perform this attack; it requires only minimal non-zero token balances of both mints to pass the `amm_coin_vault.amount == 0` check and payment of the (admin-configurable, possibly zero) `create_pool_fee`. No special privileges, races beyond ordinary transaction ordering/front-running, or protocol-specific timing are required, matching the "single submitted transaction with attacker-chosen accounts and data" reachability bar.

### Recommendation
Bind the AMM pool address derivation to the intended creator as well as the market, e.g., include `user_wallet_info.key` (or a per-creator nonce) in the seeds passed to `get_associated_address_and_bump_seed`/`generate_amm_associated_*`, so that the resulting PDAs are not purely a function of public, pre-known market data. Alternatively, require the pool creation to be gated (e.g., only the market's designated authority, or a permissioned allowlist maintained by `AmmConfig`) so that arbitrary unprivileged accounts cannot pre-empt a specific market's canonical pool.

### Proof of Concept
1. Attacker observes/learns the `market` pubkey a legitimate team intends to use for their OpenBook/Serum listing (this is public before pool creation, e.g., from the market creation transaction).
2. Attacker computes the deterministic PDAs the same way the program does: `get_associated_address_and_bump_seed(program_id, &market.key, AMM_ASSOCIATED_SEED/…, program_id)` for `amm_info`, `amm_lp_mint`, `amm_target_orders`, `amm_coin_vault`, `amm_pc_vault`. [1](#0-0) 
3. Attacker calls `Initialize2` first (front-running the legitimate team's transaction), supplying their own wallet as `user_wallet_info`, minimal `init_coin_amount`/`init_pc_amount` (just above zero), and the same `market_info`. [8](#0-7) 
4. The System-Program-owned checks succeed (accounts not yet created), all associated accounts get allocated/assigned to the AMM program and initialized under the attacker's control, and `amm.status` becomes non-`Uninitialized`. [9](#0-8) 
5. When the legitimate team's `Initialize2` transaction for the same `market` executes afterward, `generate_amm_associated_account`/`generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` see the accounts already owned by the AMM program and return `AmmError::RepeatCreateAmm`, permanently blocking creation of the intended pool for that market. [5](#0-4)
