Confirmed: `ShopifyAPI::Webhooks::Registry.process` is the gem's documented, canonical webhook entry point [1](#0-0) . It computes `Utils::HmacValidator.validate(request)` against `request.to_signable_string`, which is only the raw body [2](#0-1) , and then passes `request.shop` (sourced solely from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header) straight into `WebhookMetadata` for the app's handler [3](#0-2) [4](#0-3) . The docs explicitly instruct developers to treat `data.shop` as "The shop domain of the webhook" and to use it as the tenant key when enqueueing work [5](#0-4) [6](#0-5) .

### Title
Webhook shop-tenant identity not covered by HMAC in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates that the *body bytes* were signed with the app's `client_secret`, but never authenticates the `shop-domain` header that `Registry.process` hands to the app's handler as the trusted tenant identifier.

### Finding Description
The identity binding that should hold is: `shop` used by the app to select/attribute tenant data == `shop` bound inside the HMAC-verified payload. In this gem it instead is: `shop` returned to the handler = `request.shop` (raw header) ≠ any field inside `to_signable_string` (body only) [7](#0-6) . `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac-sha256` header [8](#0-7) , so the signature check passes regardless of what value is placed in the `shop-domain` header. `Registry.process` then trusts `request.shop` unconditionally and forwards it to the app's `WebhookHandler` as the authenticated tenant, with the docs telling integrators to key their job/queue processing off `data.shop` [1](#0-0) [6](#0-5) .

Because the shop identity is never part of the signed material, any party who has legitimately received one valid, correctly-signed webhook body (e.g., a merchant who has the app installed on their own store, or anyone who has observed one such payload/signature pair) can replay that same body+signature pair while substituting an arbitrary `shop-domain` header value. The gem's own verification logic (`HmacValidator.validate`) will still return `true`, since it only checks the body bytes against the shared `client_secret` — it has no per-shop key and no binding of header to body.

### Impact Explanation
This breaks the shop/tenant authentication boundary: `Registry.process` is the gem's sole enforcement point for webhook authenticity, and it hands out an unauthenticated tenant identifier as if it were authenticated. Any app that follows this gem's documented pattern (using `data.shop` to route/attribute processing, as literally shown in the gem's own example handler) is exposed to cross-tenant data corruption/injection — an attacker can make the app believe processed webhook data (e.g., `orders/create`, `customers/data_request`) belongs to a different merchant's shop than the one that actually produced it. This matches the "cross-tenant access" Critical impact category, since it lets an attacker cause the app to associate one tenant's data/events with another tenant.

### Likelihood Explanation
Exploitation requires the attacker to be able to produce (or capture) at least one validly-signed webhook body — for example, as a merchant who has installed the app on their own store (a normal, unprivileged use of the app, not requiring `api_secret_key`, an access token, or any special privilege over the target shop). No cryptographic secret needs to be recovered; the flaw is structural (missing binding), not a broken MAC.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signable string bound by the HMAC, or otherwise cryptographically bind `request.shop` to the verified body before exposing it to `WebhookMetadata`/handlers. At minimum, document that `request.shop`/`data.shop` is NOT authenticated by `HmacValidator.validate` and must not be used as a trust boundary by itself.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` (a normal unprivileged app install) and triggers a real webhook (e.g., `customers/data_request`), capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` [9](#0-8) [10](#0-9) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload genuinely originated from `attacker-shop.myshopify.com`'s installation [4](#0-3) , causing the app to misattribute the webhook data to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
