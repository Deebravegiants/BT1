Based on my review, I found a concrete identity-binding gap in the webhook verification path that matches the reported bug class.This confirms the vulnerability: the `shop-domain` header is never covered by the HMAC signature.

### Title
Cross-Tenant Webhook Spoofing via Unauthenticated `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` (and `topic`) HTTP header to attribute the event to a tenant when invoking the app's handler. Because the header is never part of the signed material, any request bearing a body/HMAC pair that is valid for *some* shop can be replayed with a different `shop-domain` header value and will be processed by the app as if it originated from an arbitrary, attacker-chosen shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers, which are excluded from the signable content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header value — it never incorporates `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to construct `WebhookMetadata` passed to the app's handler, with no cross-check that the shop is actually bound to the signed body: [4](#0-3) 

The documented usage pattern shows the webhook endpoint is a publicly reachable HTTP route that any internet client can POST to directly — the gem provides no IP allow-listing or other request-origin restriction, delegating authentication entirely to `Registry.process`: [5](#0-4) 

**Identity-binding equality that is broken:** the gem treats `hmac_valid(raw_body) == true` as proof that `shop == request.shop`, but the HMAC only binds `secret ↔ raw_body`; it does not bind `raw_body ↔ shop`. Concretely: `HMAC(secret, raw_body) valid` ⇏ `shop-domain header == originating shop`.

**Exploitation path:** An attacker who has installed the app on their own shop (`shop-attacker.myshopify.com`, an ordinary unprivileged tenant of a multi-tenant app) can trigger a legitimate webhook delivery to capture a valid `(raw_body, hmac-sha256)` pair signed by Shopify with the app's real secret. The attacker then replays that exact body and HMAC to the app's public webhook endpoint, but substitutes the `x-shopify-shop-domain` header with a victim shop's domain (`victim-shop.myshopify.com`). `Utils::HmacValidator.validate` still succeeds (it never inspected the shop header), and `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, causing the host application to process forged data attributed to the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: the gem's own signature check is bypassed for the tenant-scoped fields (`shop`, `topic`, `webhook_id`) that the host application relies on to route/attribute webhook data per merchant. Any host app that uses `WebhookMetadata#shop` to look up/act on a specific merchant's records (the documented and intended usage) can be made to write, sync, or trigger business logic against a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
High likelihood: obtaining a valid `(body, hmac)` pair requires only installing the app to one's own shop (an ordinary, low-privilege action available to any developer/merchant using the app), and replaying the request with a modified header requires only basic HTTP tooling (e.g., `curl`) against the publicly documented webhook endpoint. No access to `api_secret_key`, tokens, or the app's infrastructure is required.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, `topic`, `webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. At minimum, cross-validate `request.shop` against an independently-verified source (e.g., an existing, previously-authenticated session/install record for that shop) before invoking the handler, rather than trusting the raw header value derived solely from body-only HMAC validation.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger any subscribed webhook topic (e.g., `orders/create`) to receive a legitimate webhook POST with a real `x-shopify-hmac-sha256` header computed over the raw JSON body.
2. Capture the raw body and `x-shopify-hmac-sha256` header value.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC — it never reads the `shop-domain` header — and then invokes the app's handler with `shop: "victim-shop.myshopify.com"`, i.e., the forged tenant identity, executing whatever business logic the host app associates with that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
