## Title
Webhook shop attribution not bound to HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that gets passed to the application's webhook handler from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC signature verified by `HmacValidator` covers only the raw request body. Any caller who can produce (or capture/replay) a body+HMAC pair that is valid for their *own* shop can attach an arbitrary `shopify-shop-domain` header value and have the library accept the request as an authentic webhook for a *different* shop, because the shop value is never part of the signed data.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the `hmac` accessor: [1](#0-0) 

For webhooks, `Webhooks::Request` implements `to_signable_string` to return only `@raw_body`: [2](#0-1) 

But the `shop` accessor — which is later used as the tenant identifier passed into application webhook handlers — is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, completely independent of the signed bytes: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant for the handler invocation, with no secondary binding check between the signed body and the shop header: [4](#0-3) 

This is the same class of bug as the reference report: an identity-relevant field (`shop`, analogous to `ibRatio`'s `startSupply`) is used in downstream accounting/logic (`handler.handle(... shop: request.shop ...)`) but is not part of the value that was cryptographically verified (the signed body, analogous to the correctly-tracked `totalSupply`). The equality that should hold — `shop-that-was-HMAC-authenticated == shop-passed-to-handler` — is broken: the HMAC authenticates `(secret, raw_body)`, but the trusted tenant identity is `header["shopify-shop-domain"]`, an entirely separate, unauthenticated channel.

### Impact Explanation
An unprivileged internet user who operates their own Shopify development/trial shop with the target app installed can trigger a real webhook (e.g. by editing a product), capture the exact `raw_body` and its genuine `x-shopify-hmac-sha256` value that Shopify sent to the app's public webhook endpoint, and then replay that identical body+HMAC pair to the same endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will succeed (it never inspects the header), and `Registry.process` will invoke the registered handler believing the payload legitimately originates from the victim shop. Any application logic that uses the webhook's `shop` field to scope database writes, cache invalidation, session/access-token lookups, or state transitions per tenant can be corrupted or cross-contaminated by attacker-controlled body content falsely attributed to another merchant — a cross-tenant data integrity/confusion issue reachable purely over the internet, without credentials, TLS interception, or code execution privileges.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is a normal public HTTP endpoint by design (that's how Shopify delivers webhooks), the attacker only needs their own (free/trial) shop with the app installed to legitimately obtain one valid `(raw_body, hmac)` pair, and no secret material or elevated access is required to then forge the header value on replay, since `Request#shop` and the signature computation are fully decoupled.

### Recommendation
Bind the tenant identity to the signed payload, or otherwise ensure the two channels cannot diverge:
- Where possible, cross-check the `shop` header value against the shop referenced inside the parsed body payload (Shopify webhook bodies generally include shop-scoped resource identifiers) before dispatching to a handler.
- At minimum, document prominently that `Webhooks::Request#shop` is unauthenticated and must not be used by consuming applications as the sole tenant-scoping key without an independent, authenticated cross-check (e.g., verifying the shop is one for which the app holds an active, previously-issued session/access token, and that no other signal contradicts it).
- Consider including the shop domain in the signable string used for verification if a future Shopify webhook signing scheme allows it, so the identity binding is enforced by the library itself rather than left to每个 consuming app.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/observes a webhook (e.g. `products/update`).
2. Attacker triggers the webhook and captures the exact HTTP request Shopify sends to the app's public callback URL, including `raw_body` and header `x-shopify-hmac-sha256: <valid_hmac>`.
3. Attacker replays this exact request to the same public endpoint, changing only the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into an object whose `hmac` still matches (`to_signable_string` = same `raw_body`), so `Utils::HmacValidator.validate(request)` returns `true`. [5](#0-4) 
5. `Registry.process` dispatches to the registered handler with `shop: request.shop` equal to `"victim-shop.myshopify.com"` and `body` containing the attacker's own product data, causing the app to process attacker-controlled content under the victim shop's tenant context.
