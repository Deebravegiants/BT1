Confirmed: the documentation explicitly instructs handlers to trust `data.shop` as "The shop domain of the webhook" (docs/usage/webhooks.md:14) and even shows a canonical example dispatching per-shop background jobs keyed on it (`perform_later(topic: data.topic, shop_domain: data.shop, ...)` at docs/usage/webhooks.md:26) — yet that field is never covered by the HMAC signature.

### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are unauthenticated and can be forged, breaking the HMAC-authenticated-shop binding — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` authenticates nothing but the JSON payload bytes. The shop identity (`X-Shopify-Shop-Domain` header, exposed as `request.shop`) that `Registry.process` hands to every app's `WebhookHandler` is read directly from an unsigned header and is never bound to the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` is defined as just the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic relationship to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then constructs the `WebhookMetadata` passed to the app's handler directly from those unsigned header values: [3](#0-2) 

The intended binding is: **the shop that receives the payload described by `shop` must equal the shop whose HMAC-verified secret produced `hmac`.** Because `to_signable_string` only covers `@raw_body`, this equality is never checked — `hmac` authenticates *"this body was produced with the app's client_secret,"* while `shop` (and `topic`/`webhook_id`/`api_version`) are simply asserted by the caller. Any two requests carrying the same JSON body and a real HMAC of that body (signed with the same app secret) will pass validation regardless of what shop-domain header accompanies them.

An unprivileged holder of a real, currently-installed instance of the app (e.g., someone who installed the app onto their own free/dev store) can receive a genuine webhook — body + valid HMAC — for their own store, then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or topic/webhook_id) header. `HmacValidator.validate` still succeeds because it never looks at those headers, and the handler receives `WebhookMetadata` claiming the payload originated from any shop the attacker chooses.

### Impact Explanation
The gem's own documentation instructs app authors to treat `data.shop` as the trusted origin of the webhook and to key downstream, per-tenant work off it — e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [4](#0-3) 

Since `shop` is attacker-controllable independent of the signed content, any handler that uses it to select a tenant record, session, or access token to act on (a normal and encouraged pattern, since webhook payloads never carry their own access token) can be tricked into applying attacker-supplied webhook data to a victim shop's tenant context — i.e. cross-tenant data confusion/corruption, satisfying the "cross-tenant access" bar. It also permits topic spoofing (dispatching an app's `orders/create` handler logic while claiming to be `app/uninstalled`, etc.), further widening the confusion an attacker can induce in per-tenant processing pipelines.

### Likelihood Explanation
Any user can install a public/free app on a store they control and thereby legitimately receive real webhook deliveries (valid body+HMAC pairs) for that store from Shopify. Replaying that pair to the same app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header requires no secret material, no privileged account, and no interception — only a basic HTTP client. This is a fully unprivileged, internet-reachable attack once the attacker has ever received one legitimate webhook.

### Recommendation
Bind the identity headers into the HMAC signature verification. Options:
1. Reject the request unless the `shop-domain` (and ideally `topic`, `webhook_id`) header is verified against Shopify's per-shop webhook registration data known to the app (i.e., only accept a shop value the app previously registered a session for), or
2. Where feasible, treat `shop`/`topic` purely as routing hints and require handlers to independently confirm the shop has an active, previously-established session/access token before performing any tenant-scoped mutation — document this requirement prominently since the gem cannot itself expand the HMAC coverage (Shopify's webhook signature is computed server-side over the body only).
3. At minimum, update `docs/usage/webhooks.md` to stop presenting `data.shop` as a trusted, HMAC-verified identity, and warn implementers explicitly that it is unauthenticated header data.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `evil.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the real POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `client_secret`).
2. Replay the identical request to the same webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` builds `Request` from these headers/body; `Utils::HmacValidator.validate(request)` calls `compute_signature(request.to_signable_string, secret)` — `to_signable_string` returns `B` only, so the computed HMAC equals `H` and validation succeeds.
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled body content is delivered under the victim shop's identity, exactly as demonstrated by the test fixtures that construct `Request` purely from header values and an HMAC of the body: [5](#0-4)
