### Title
Unauthenticated `/v2/resume/:runID` endpoint lets any unprivileged client resolve a pending pipeline task run with an attacker-controlled result - (File: core/web/pipeline_runs_controller.go)

### Summary
The Sherlock finding describes PartyB being able to observe favorable/unfavorable state on a locked order and then unilaterally unlock (undo) it to avoid unfavorable outcomes — i.e., an actor controls the resolution of a pending, supposedly-neutral state transition after inspecting it, without proper authorization tying that control to the legitimate party. The chainlink analog is the `PipelineRunsController.Resume` handler, which is deliberately mounted on the *unauthenticated* router group and lets any caller who can construct/guess a `runID` push an arbitrary `pipeline.Result` (value or error) into a suspended task run, finalizing it however they choose.

### Finding Description
`PipelineRunsController.Resume` is registered on the unauthenticated `v2Routes` group: [1](#0-0) 

```go
func v2Routes(app chainlink.Application, r *gin.RouterGroup) {
	unauthedv2 := r.Group("/v2")
	...
	unauthedv2.PATCH("/resume/:runID", prc.Resume)

	authv2 := r.Group("/v2", auth.Authenticate(...))
```

The handler itself performs no ownership or authorization check on the caller — it only validates that `runID` parses as a UUID and that the JSON body decodes into a `pipeline.ResumeRequest`: [2](#0-1) 

It then calls `App.ResumeJobV2`, which forwards straight to the pipeline runner's `ResumeRun`: [3](#0-2) [4](#0-3) 

`ResumeRun` writes the caller-supplied `Result{Value, Error}` directly into the task run via `orm.UpdateTaskRunResult` and, if this is the task that unblocks the run, restarts the pipeline scheduler with that value baked in — the exact mechanism a legitimate external task (e.g. an `ethsend`/`bridge`/webhook callback) uses to report its outcome back to the pipeline. Nothing in this path authenticates that the caller is the intended external system that owns that specific pending task; the only "secret" is the `runID` (a task UUID), which is not treated as a capability token anywhere in the code — it is not rate-limited, not scoped to origin, and is returned/loggable in various places (e.g. `respondWithPipelineRun`, DB rows, logs).

This mirrors the audit finding's root cause: an unprivileged actor can inspect/guess a pending item's identity and then choose the value that resolves it, rather than that resolution being restricted to the legitimate authorized party. The code even names the audit event for this action `UnauthedRunResumed`, acknowledging in-repo that this is an intentionally-unauthenticated write path: [5](#0-4) 

### Impact Explanation
Any party who learns or brute-forces a pending task run's UUID can:
- Force a suspended job/task to complete with an attacker-chosen `Value` (arbitrary JSON payload) instead of the value the legitimate external system/bridge would have produced, corrupting downstream pipeline computation (e.g., price data, condition results) feeding on-chain reports or further tasks.
- Force a suspended task to fail with an attacker-chosen `Error`, effectively "unlocking"/cancelling that pending resolution and letting the caller retry conditions until a run happens to be favorable, analogous to PartyB's lock→peek→unlock behavior.
- This is a write/state-mutation path reachable with zero authentication, exposed directly to the internet-facing node API.

This is scoped by the fact that `runID` must be a valid UUID for an existing pending run and the resumer race (start=true) depends on being the specific task expected next — but the endpoint provides no cryptographic or session-based binding of "who may resume this run," which is the same class of missing-authorization-on-a-privileged-state-transition as the reported bug.

### Likelihood Explanation
Likelihood is Medium: exploitation requires knowledge of a specific pending task run's UUID. In deployments where run UUIDs are exposed to less-trusted parties (returned in API responses to job creators, logged, or predictable/sequential due to reuse patterns), or where the intended external callback design already hands the UUID to a third-party bridge/adapter, any holder of that UUID — not just the intended bridge — can call this endpoint. There is no rate limiting or per-run single-use enforcement described in the code paths inspected beyond what `UpdateTaskRunResult`'s state check provides.

### Recommendation
Bind resume authorization to the specific task/run rather than relying solely on UUID secrecy: require a per-run, single-use signed token (HMAC over `runID` + task metadata) issued when the task is created and validated in `Resume`, or move the endpoint behind the standard bridge/external-initiator authentication used elsewhere (`auth.AuthenticateExternalInitiator`/`AuthenticateByToken`) scoped to the specific bridge that owns the task. At minimum, add rate limiting and audit alerting keyed to repeated failed/successful resumes on the same run, and ensure `runID` values are never logged or returned to parties other than the intended resumer.

### Proof of Concept
1. Discover or guess a pending pipeline task run UUID (`runID`) — e.g., from job creation output, logs, or database exposure.
2. Send an unauthenticated request:
```
PATCH /v2/resume/<runID>
Content-Type: application/json

{"value": "<attacker-chosen favorable result>"}
```
routed via `unauthedv2.PATCH("/resume/:runID", prc.Resume)` [6](#0-5) .
3. `PipelineRunsController.Resume` decodes the body and calls `App.ResumeJobV2(ctx, taskID, result)` with no authentication or ownership check [7](#0-6) .
4. `ResumeRun` commits the attacker-supplied value/error into the task run and resumes the pipeline, exactly as if the legitimate external system had reported that outcome [8](#0-7) .

```go
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
```

```go
func (r *runner) ResumeRun(ctx context.Context, taskID uuid.UUID, value any, err error) error {
	run, start, err := r.orm.UpdateTaskRunResult(ctx, taskID, Result{
		Value: value,
		Error: err,
	})
	if err != nil {
		return fmt.Errorf("failed to update task run result: %w", err)
	}

	// TODO: Should probably replace this with a listener to update events
	// which allows to pass in a transactionalised database to this function
	if start {
		// start the runner again
		go func() {
			ctx, cancel := r.chStop.NewCtx()
			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
```
