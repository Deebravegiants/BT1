### Title
RAY-scaled debt value overflows before the borrow-index cap engages, permanently freezing the market - (File: common/src/rates/scaling.rs)

### Summary
Interest accrual multiplies the RAY-scaled debt share total by the new borrow index (`borrowed * index`). The borrow index is capped at `MAX_BORROW_INDEX_RAY = 10^36`, but the product `borrowed * index` is unchecked for fitting `i128` except by a panic. A sufficiently large market at sustained high utilization reaches `scaled_debt * index > i128::MAX` long before the index itself reaches its cap, so `scaled_to_original` / `Ray::mul` panics with `MathOverflow` inside every accrual. Because every state-changing pool verb accrues first (`global_sync` → `accrue_chunk` → `accrue_step`), the market is bricked: no `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, or `recapitalize` can execute. All supplied funds are permanently frozen.

### Finding Description
The analog to CVE-2018-4358's memory-corruption class here is unguarded `i128` arithmetic corrupting protocol liveness: an intermediate product that escapes the representable range traps rather than saturating.

- `common/src/rates/index.rs:13-19` — `update_borrow_index` clamps the *index* to `MAX_BORROW_INDEX_RAY`, but that does nothing to bound the *value* `borrowed * index`.
- `common/src/rates/index.rs:80-83` — `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` via `scaled_to_original` (`common/src/rates/scaling.rs:14-16`), which is `mul_div_half_up` — it widens to `I256` for the intermediate but panics with `GenericError::MathOverflow` when the quotient doesn't fit `i128`.
- `contracts/pool/src/interest.rs:20-53` — `global_sync` runs accrual at the head of every op; once `borrowed * new_borrow_index` overflows, `accrue_chunk` aborts and `mark_accrued` is never reached, so the condition never self-heals.
- `common/src/constants/pool.rs:19` — the index cap is `10^36`; `i128::MAX ≈ 1.7e38`, so the value ceiling binds when `scaled_debt > ~170` RAY-units per index unit, i.e. reachable while `borrow_index < MAX_BORROW_INDEX_RAY`.

The repo's own test confirms this is reachable and irreversible: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361` supplies `10^9 * 10^18` units of an 18-decimal asset, borrows 98% of it on the XLM rate curve, advances years, and observes `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` ("the index cap did not engage before the value overflow… The market is frozen").

### Impact Explanation
Permanent freezing of user funds: once `borrowed * borrow_index` exceeds `i128::MAX`, every entrypoint that touches the market accrues first and reverts. Suppliers cannot withdraw, borrowers cannot repay (so positions can never be closed), liquidators cannot liquidate, and `clean_bad_debt`/`recapitalize` cannot run. This satisfies the "permanent freezing of funds" impact class directly.

### Likelihood Explanation
A single unprivileged actor can set up the precondition: `lift_caps`-able supply/borrow caps only govern per-call sizes, so a whale (or coordinated flow across hubs sharing one physical pool book) can deposit a massive principal and borrow ~98% at high utilization. Then anyone — including the same actor via the permissionless `update_indexes` / any verb — triggers accrual each period until the product crosses the ceiling. The attacker's own borrow is frozen too, but the freeze locks *all* suppliers' funds in that book, so this is a griefing/insolvency-priming vector rather than a profitable one; severity is bounded by the market size that must be assembled, but the cap validation (`require_cap_within_asset_domain`) does not bound scaled debt against `i128::MAX / MAX_BORROW_INDEX_RAY`.

### Recommendation
Bound the product, not just the index. Options: (a) cap `new_borrow_index` at `min(MAX_BORROW_INDEX_RAY, i128::MAX / borrowed)` inside `accrue_step` so `borrowed * index` always fits; (b) make `calculate_supplier_rewards`/`scaled_to_original` saturate to `i128::MAX` for the value product (consistent with `mul_div_floor_saturating` already used in `update_supply_index` and `protocol_fee_shares`); and/or (c) enforce a scaled-debt ceiling `borrowed <= i128::MAX / MAX_BORROW_INDEX_RAY` at borrow-mint time so the overflow state is unreachable.

### Proof of Concept
Existing reproducer: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361` (`a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`). It: supplies `BILLION * 10^18` of `BIG18` via `t.supply_raw(BOB, ...)`, borrows 98% via `t.borrow_raw(ALICE, ...)`, advances time year-by-year calling `t.try_update_indexes_for(&["BIG18"])` until it returns `MATH_OVERFLOW`, then asserts `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` while `book.borrow_index < MAX_BORROW_INDEX_RAY` — demonstrating the freeze precedes the cap and is permanent.
