Audit Report

## Title
Missing role restriction on `GET /v2/external_initiators` allows any authenticated user (including `view`-role) to read `AccessKey`/`OutgoingToken` key material reserved for `edit`-role - (File: core/web/router.go)

## Summary
The `Index` route for External Initiators is registered without any `auth.RequiresEditRole`/`RequiresRunRole` wrapper, while `Create` and `Destroy` for the same resource explicitly require `RequiresEditRole`. This lets any authenticated user, regardless of role (including the lowest `UserRoleView`), call `GET /v2/external_initiators` and read the `AccessKey` and `OutgoingToken` fields of every registered external initiator.

## Finding Description
`v2Routes` in `core/web/router.go` registers: [1](#0-0) 
Only `POST` and `DELETE` are gated by `auth.RequiresEditRole`; `GET` (`Index`) is reachable by any user who merely passes the base `authv2` group's session/token authentication, with no role check.

`ExternalInitiatorsController.Index` serializes the list using `presenters.NewExternalInitiatorResource`, confirmed to include `AccessKey` and `OutgoingToken`: [2](#0-1) [3](#0-2) 

`RequiresEditRole` blocks `view`- and `run`-role users; `RequiresRunRole` blocks only `view`-role. Neither is applied to `Index`: [4](#0-3) 

However, examining `bridges.ExternalInitiator` and `AuthenticateExternalInitiator` shows that authenticating as an external initiator (to gain `UserRoleRun` and trigger job runs) requires **both** the `AccessKey` header and the raw `Secret` header: [5](#0-4) [6](#0-5) 
Only a salted hash (`HashedSecret`) of the secret is persisted; the raw `Secret`/`OutgoingSecret` are never returned by `Index`'s `ExternalInitiatorResource` (they are absent from that struct entirely — only `ExternalInitiatorAuthentication`, returned once at `Create` time, carries `Secret`/`OutgoingSecret`). So leaking `AccessKey` via `Index` does **not** by itself let an attacker forge `AuthenticateExternalInitiator` and escalate to `UserRoleRun`; the claim's framing of this as enabling job-run triggering is overstated and not supported by the code.

That said, the underlying access-control gap is real and independently verifiable: `AccessKey` and `OutgoingToken` are key/credential material tied to a specific integration, and the sibling mutating routes for the same resource are intentionally restricted to `edit` role while the read route is not. A `view`-role user — who should have read-only, non-privileged access to non-sensitive data — can enumerate this key material, which is an unintended information-disclosure/access-control inconsistency.

## Impact Explanation
This is a legitimate but narrower-than-claimed access-control gap: it enables unauthorized disclosure of `AccessKey` and `OutgoingToken` values to any authenticated user regardless of role, which maps to the in-scope "key/secret exfiltration" / "role bypass" impact category. It does **not**, however, constitute full authentication bypass or unauthorized job-run triggering, because the `Secret` required by `AuthenticateExternalInitiator` is hashed at rest and never exposed by this or any other confirmed endpoint. The realistic impact is limited to disclosure of identifiers/tokens beyond the intended role boundary, not privilege escalation to actually invoke external-initiator-triggered runs.

## Likelihood Explanation
High likelihood for any deployment with multiple users of differing roles (a normal, supported configuration): any authenticated `view`-role user can trigger this with a single unauthenticated-role-check `GET` request, no special conditions required.

## Recommendation
Wrap `GET /v2/external_initiators` with `auth.RequiresEditRole` (matching `Create`/`Destroy`) or at minimum `auth.RequiresRunRole`, so read access to `AccessKey`/`OutgoingToken` is restricted to the same role level as mutation of the resource.

## Proof of Concept
1. Create a user with `UserRoleView`.
2. Authenticate as that user via `POST /sessions`.
3. Send `GET /v2/external_initiators` with the resulting session/token — server returns HTTP 200 with `accessKey`/`outgoingToken` fields for every registered initiator (verified via `ExternalInitiatorsController.Index` → `presenters.NewExternalInitiatorResource`).
4. Compare with `POST /v2/external_initiators` or `DELETE /v2/external_initiators/:Name` using the same view-role session — these correctly return `401 Unauthorized` due to `auth.RequiresEditRole`.
5. Note: this PoC demonstrates unauthorized disclosure of `AccessKey`/`OutgoingToken` only; it does not demonstrate ability to authenticate as the external initiator or trigger a job run, since `Secret` is not exposed by this endpoint.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
