## Analog Found

### Title
Hyper Fungible Token decimal-scaling helpers break (unbacked mint / fund freeze) when the local asset has more decimal precision than the registered remote precision - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The original report flags `Pool.sol`'s `_interest = _totalDebt * _borrowRate * _timeDelta / (365 days * 1e18)` rounding to zero for low-decimal tokens because the arithmetic implicitly assumes 18-decimal precision. `pallet-hyper-fungible-token` has the analogous decimal-scaling defect: its `convert_to_balance`/`convert_to_erc20` helpers both derive their scaling factor from `erc_decimals.saturating_sub(local_decimals)`, which silently collapses to `10**0 = 1` (no scaling at all) whenever `local_decimals > erc_decimals` — a configuration the pallet's own docs describe as normal ("Decimals between this chain and each remote chain may differ").

### Finding Description
`convert_to_erc20` (local → ERC20 units, used on `send`) and `convert_to_balance` (ERC20 → local units, used on `on_accept`/`on_timeout`) both key off the same one-directional factor: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions are only correct for `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals` (e.g. a local asset registered with 18 decimals paired with a 6-decimal ERC6160 mirror — an entirely valid, admin-configured `Precisions` entry per the pallet's own docs), `erc_decimals.saturating_sub(local_decimals)` saturates to `0`, so:

- `send()` calls `convert_to_erc20` (multiply by `10^0 = 1`) instead of dividing by `10^(local_decimals - erc_decimals)`. The raw local-decimal amount is forwarded unscaled as if it were already erc-decimal, inflating the message amount by `10^(local_decimals - erc_decimals)`. [2](#0-1) 

- `on_accept()` calls `convert_to_balance` (divide by `10^0 = 1`) instead of multiplying by the same missing factor, so an honestly-scaled inbound message is credited at its raw erc-decimal value with no upscaling, crediting the beneficiary a vanishingly small (`10^(local_decimals - erc_decimals)` times too small) local balance. [3](#0-2) 

The same defective helper is reused for the `on_timeout` refund path. [4](#0-3) 

### Impact Explanation
- On the outbound `send()` path, the pallet burns/locks the correct local amount but dispatches a `Message.amount` inflated by `10^(local_decimals - erc_decimals)`. When the paired `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract processes this in `onAccept`, it mints/releases the inflated amount — an **unbacked mint** on the destination chain, directly draining the counterpart's backing/liquidity.
- On the inbound `on_accept()` path (a message legitimately sent from the EVM side with correctly-scaled decimals), the beneficiary is credited a balance many orders of magnitude smaller than the tokens burned/locked on the source chain — a **permanent freezing/loss of funds** for the sender, with no recovery path since `on_timeout` uses the same broken conversion.
- Both are single-transaction/single-message reachable: any signed account can call `send()`, and any relayed cross-chain `PostRequest` delivered to `on_accept` triggers the conversion, satisfying the "single dispatched request" reachability bar.

### Likelihood Explanation
This does not require a malicious admin — it triggers under a routine, documented configuration where the local `pallet-assets`/native asset decimals exceed the registered remote (`Precisions`) decimals, which the pallet's own registration flow (`create_erc6160_asset`, `update_asset_precision`) allows without any validation ordering `local_decimals <= erc_decimals`. Any asset pairing where the substrate-side asset happens to use more decimal places than its EVM mirror (a plausible and even common setup, e.g. locally-defined 18-decimal representations of assets whose canonical ERC6160 deployment uses 6 or 8 decimals) hits this on every single transfer, not just for dust amounts.

### Recommendation
Fix both helper functions to correctly handle both scaling directions, e.g.:
```rust
pub fn convert_to_balance<B: FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
and the symmetric fix (swap multiply/divide) for `convert_to_erc20`. Add an invariant test asserting `convert_to_balance(convert_to_erc20(x, ...), ...) == x` for both `erc_decimals >= local_decimals` and `erc_decimals < local_decimals`.

### Proof of Concept
1. Governance registers asset `X` via `create_erc6160_asset`/`update_asset_precision` with `local_decimals = 18` (pallet-assets default) and `Precisions[X][EVM-dest] = 6` (the ERC6160 mirror uses 6 decimals) — a legitimate, unremarkable configuration.
2. Alice calls `send(asset_id = X, amount = 1_000_000_000_000_000_000 /* 1.0 token, 18dp */, destination = EVM-dest, ...)`.
3. `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18) = 0`, so `convert_to_erc20` multiplies by `10^0`, producing `Message.amount = 1_000_000_000_000_000_000` (still 1e18) instead of the correct `1_000_000` (1e6, i.e. "1.0" at 6 decimals). [5](#0-4) 
4. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract's `onAccept` mints/unlocks `1_000_000_000_000_000_000` raw units of a 6-decimal token — i.e. `1,000,000,000,000` tokens instead of `1` — from a single burn of 1 token on the source chain, an unbacked mint of 12 orders of magnitude.

///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.

	value: U256,
	erc_decimals: u8,
	local_decimals: u8,

	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision

}
