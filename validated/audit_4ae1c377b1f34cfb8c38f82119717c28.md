## Title
Webhook shop/topic identity spoofing via HMAC validation that only covers the body, not the trust-relevant headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by HMAC-validating only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the handler subsequently trusts and acts on are read directly from unauthenticated HTTP headers. An attacker who possesses one genuinely Shopify-signed `(raw_body, hmac)` pair (e.g. from their own store/app installation) can freely swap the `shop-domain`/`topic` headers and have the app process the payload as if it came from a different, victim shop or a different topic, even though `HmacValidator.validate` still reports success.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC solely against this signable string: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the whole request (including headers) "did indeed come from Shopify," then immediately builds `WebhookMetadata` from the unauthenticated header-derived `shop`, `topic`, `webhook_id`, and `api_version` accessors and dispatches it to the registered handler: [3](#0-2) [4](#0-3) 

The gem's own documentation reinforces that this "verify then trust" behaviour is the intended, documented contract — `process` "will verify the request did indeed come from Shopify," and the resulting `data.shop`/`data.topic` are presented to handler authors as reliable fields to key application logic on (e.g., looking up a shop's session, enqueuing per-shop jobs): [5](#0-4) [6](#0-5) 

This is exactly the analog of the reported bug class: a field that the application acts on (`shop`, used by handlers as the tenant key) is not covered by the same authenticity check (`hmac`) that is supposed to bind the whole request to Shopify. The identity binding that should hold — `shop header == shop that produced/authorized this body` — is not enforced; only `body == body that was HMAC-signed` is enforced.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), which is Critical per the given scale. An attacker who can obtain one legitimately-signed webhook body (trivially available to anyone who installs the app on their own development/test store, or who can otherwise trigger any webhook for a shop they control) can replay that exact `(raw_body, hmac)` pair against the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. Because `HmacValidator.validate` never inspects headers, the forged request still passes validation, and the app's handler will execute business logic (session lookup, job enqueuing, data writes) attributing the attacker-controlled body to a shop the attacker does not own — a cross-tenant identity-binding bypass.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that follows the documented pattern of keying per-shop logic off `data.shop` from `WebhookMetadata` without an independent, out-of-band verification that the shop is one the app actually has an active installation/session for on that exact topic/webhook id. No access token, `client_secret`, or privileged access is required — only the ability to send an HTTP request to the app's public webhook endpoint with a captured valid body/HMAC pair and modified headers, which any unprivileged internet user who has interacted with the app once (e.g., installed it on a shop they control) can do.

### Recommendation
Include the trust-relevant identifiers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., derive/verify them independently against Shopify, or document/enforce that consumers must cross-check `data.shop` against a webhook subscription record keyed by `webhook_id` fetched via the Admin API) so that the fields acted upon by handlers are covered by the same authenticity guarantee as the body.

### Proof of Concept
1. Attacker installs the target app on Shop A (a store they control) and receives a legitimate webhook delivery with raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)` — this is a real Shopify-issued request, so `H` is valid.
2. Attacker replays the captured request to the app's webhook endpoint but changes `x-shopify-shop-domain` to `shop-b.myshopify.com` (Shop B, a victim tenant) and/or `x-shopify-topic` to a different registered topic, keeping body `B` and hmac header `H` unchanged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this still matches because `to_signable_string` only returns `@raw_body`: [7](#0-6) 
4. Validation succeeds, and `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built from the attacker-controlled headers and passed to the app's handler, which acts as though the payload legitimately originated from Shop B / the spoofed topic: [8](#0-7)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
```
