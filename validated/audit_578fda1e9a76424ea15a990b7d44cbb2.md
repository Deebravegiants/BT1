### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the Shopify HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw request body only, while the shop identity, topic, and webhook id are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches the handler using these header-derived values, so the "shop this webhook is for" is never actually bound to the cryptographic signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from attacker-controllable HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cross-check against anything derived from the signed body: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC solely against `verifiable_query.to_signable_string`, i.e. the raw body — the headers play no part in the signature check: [3](#0-2) 

`Registry.process` validates that body-only HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata handed to the app's handler: [4](#0-3) 

This breaks the identity binding: `hmac-signed(body)` should imply `shop == the shop that body belongs to`, but the gem only proves `hmac-signed(body)` while `shop` comes from an unsigned header. An unprivileged internet user can install the target app on their own (attacker-controlled) shop, legitimately receive one real webhook (raw body + valid `shopify-hmac-sha256` computed from the app's `client_secret`, which they never need to know or extract), and then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain (or any other domain the app also serves). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the body originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the app-level handler receives attacker-supplied body content falsely attributed to another merchant's shop. Depending on how the host application's webhook handler uses `data.shop` (e.g., to look up sessions/access tokens, update per-shop state, or trigger side effects keyed by shop), this can lead to cross-tenant data corruption or actions performed under another merchant's identity — matching the Critical "cross-tenant access" impact category, since the gem itself provides no protection binding the signed payload to the claimed shop.

### Likelihood Explanation
Requires only becoming an app installer (unprivileged, self-service action available to any internet user who can install the target Shopify app) to obtain one legitimately signed `(body, hmac)` pair, plus the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified `shopify-shop-domain` header — no possession of `client_secret`, access tokens, or victim credentials is needed.

### Recommendation
Bind the shop (and topic/webhook id) into the signed content that `HmacValidator` verifies, or otherwise cryptographically tie the header-derived `shop` to the signed body (e.g., require the caller to independently confirm the header shop matches an active session/registration before dispatching to handlers), rather than trusting `shopify-shop-domain` as an unauthenticated header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimate webhook: raw body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's secret), `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the same `B`/`H` to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally changes `shopify-topic`/`shopify-webhook-id`, which are equally unauthenticated).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `Digest.hexencode(...)` against `to_signable_string` == `B`. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.
