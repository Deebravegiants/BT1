### Title
Webhook shop identity spoofing via unsigned `shop-domain` header while only the raw body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` verifies the HMAC solely against that string [2](#0-1) . The `shop` field, however, is read from the unauthenticated `shop-domain` header [3](#0-2)  and is trusted directly by `Registry.process`, which validates the HMAC and then hands `request.shop` to the app's handler without any binding to the signed payload [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_tenant`. In this gem it does not: `hmac_signed_bytes = raw_body` while `tenant (shop) = header["shop-domain"]`, a value never included in the signed content. Since every merchant's webhooks for a given app are signed with the same `Context.api_secret_key`, any attacker who legitimately receives one valid `(raw_body, hmac)` pair for their own shop — trivially obtainable by installing the target app on a free/self-controlled Shopify development store — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still pass because it never inspected the header, and `Registry.process` will invoke the app's handler with `WebhookMetadata.new(shop: <victim shop>, body: <attacker's own data>, ...)` [5](#0-4) , causing the host application to process attacker-controlled data as belonging to a different tenant.

### Impact Explanation
This is a cross-tenant integrity/access issue: an unprivileged attacker (who only needs to control one shop where the target app is installed, which is free to obtain via a Shopify dev store) can inject arbitrary payloads and topics that are attributed to any other merchant using the app, as documented for handler consumers who key persistence/business logic off `data.shop` [6](#0-5) . Depending on how the host app uses `data.shop` (e.g., looking up a session/store record and applying `data.body` to it), this can lead to cross-tenant data corruption, spoofed events (e.g., fake `app/uninstalled`, `orders/create`, GDPR-topic payloads) being attributed to victim shops, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Moderate-to-high: no secrets are required from the victim, TLS interception is unnecessary, and the attacker doesn't even need real access to the victim — only a self-obtained, freely available valid `(body, hmac)` pair from their own install of the app, plus the ability to send an HTTP POST with a modified header to the app's public webhook endpoint (a normal, unprivileged action).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is actually authenticated. Since Shopify's webhook signature does not cover headers, the gem/host app should independently corroborate `request.shop` against the value embedded in `request.parsed_body` (webhook payload bodies for most topics include the shop's identifying data, e.g. `X-Shopify-Shop-Domain` is documented by Shopify but not authenticated), or the host app should verify that the shop domain in the header matches a shop for which a webhook with that exact `webhook_id` was actually registered/expected before trusting `data.shop`. At minimum, document prominently in `docs/usage/webhooks.md` that `data.shop` is not covered by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a known list of installed shop domains before applying the payload).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, free dev store) and registers for topic `orders/create`.
2. Shopify sends the attacker a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker captures this exact `(B, hmac)` pair (they are the recipient, so no interception needed).
4. Attacker POSTs directly to the app's public webhook endpoint with the same `raw_body = B` and same `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` computes `HMAC(secret, B)` and it matches — validation passes [7](#0-6) .
6. `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, and the host app processes attacker-controlled data as if it originated from the victim shop [8](#0-7) .
