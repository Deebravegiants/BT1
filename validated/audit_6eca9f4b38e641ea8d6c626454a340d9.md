### Title
Reentrant escrow release in `withdraw` violates checks-effects-interactions - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the IntentGateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) contains an internal `withdraw` function that transfers escrowed collateral to a beneficiary via raw low-level `.call()` *before* decrementing the corresponding `_orders[commitment][token]` balance, and the function carries no reentrancy guard. This is the exact bug class described in the external report (`CollateralEscrowV1.withdraw`): external interaction before state update in a fund-release path.

### Finding Description
`withdraw(WithdrawalRequest memory body, bool isRefund)` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 691-730) does the following per escrowed token: [1](#0-0) 

1. Checks `_orders[body.commitment][token] == 0` (a stale-read guard, not a lock).
2. Sends value via `beneficiary.call{value: amount}("")` for native tokens, or invokes the token's `transfer` via a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for ERC-20 legs — **both are unguarded external calls that can trigger arbitrary code** (a `receive()`/`fallback()` on the beneficiary for native transfers, or a callback inside a malicious/non-standard token contract for the ERC-20 leg, since `placeOrder` lets any user register arbitrary token addresses as order inputs).
3. Only **after** the external call does it perform `_orders[body.commitment][token] -= amount;` (line 710).

This is reachable from:
- `onAccept` (RedeemEscrow / RefundEscrow) — invoked by the host when a relayer delivers a proven cross-chain settlement message: [2](#0-1) 
- `cancelOrder` for same-chain orders, callable directly by the order owner: [3](#0-2) 
- `onGetResponse`, invoked after a relayed storage-proof response: [4](#0-3) 

Notably, `onAccept` does **not** check `_filled[commitment]` before calling `withdraw` — it relies solely on the per-token `_orders[...] == 0` check inside the loop, which is exactly the value that is left stale during the external call.

This is a clear regression relative to the hardened, non-Tron implementation. The primary EVM `IntentsBase._withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol`) was fixed to decrement escrow **before** transferring funds and uses `SafeERC20.safeTransfer`: [5](#0-4) 

The project even has a dedicated regression-test suite (`IntrinsicIntentsReentrancyTest.sol`) documenting that this exact reentrant-escrow-theft class was previously exploitable and was fixed with a checks-effects-interactions (CEI) reordering plus `_filled` gating in the main EVM contracts: [6](#0-5) 

The Tron contract was apparently never updated to match this fix — it still uses the pre-fix transfer-then-decrement pattern with raw `.call` and no `nonReentrant` modifier anywhere in the file.

### Impact Explanation
Escrow accounting (`_orders[commitment][token]`) can be read/acted upon in a stale state during an external call in a fund-release function. Combined with the fact that the ERC-20 leg uses an unchecked, low-level `.call()` to an attacker-controllable token contract (any address can be registered as `order.inputs[i].token` at `placeOrder` time), and that `onAccept`'s only replay defense for the withdraw path is the very balance the reentrant call can catch before it's updated, this exposes the escrow to reentrant draining or corrupted accounting — a Medium-severity fund-safety issue matching the reported bug class (withdraw-before-state-update leading to abnormal withdrawal of escrow).

### Likelihood Explanation
Reachable by any user who places an order with a maliciously-crafted (attacker-controlled) input token, or is the beneficiary of a native-token settlement, and by any relayer delivering the corresponding cross-chain settlement message — no privileged role is required. However, full exploitability is bounded by `_filled[commitment]` being set at the very top of `withdraw` (blocking re-invocation of `cancelOrder`/`withdraw` for the *same* commitment through the public entry points), and `onAccept`/`onGetResponse` being `onlyHost`-gated so a malicious beneficiary cannot re-trigger the host callback directly. I was not able to fully trace a second entry point that reads/writes the same stale `_orders[commitment][token]` slot mid-callback within the available investigation budget — this residual uncertainty should be resolved by static/dynamic reentrancy testing (e.g., adapting `IntrinsicIntentsReentrancyTest.sol` against the Tron contract) before concluding definite fund loss.

### Recommendation
Port the CEI fix already applied to `evm/src/apps/intentsv2/IntentsBase.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`:
- Decrement `_orders[body.commitment][token]` **before** performing the native-value call or token transfer.
- Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` with OpenZeppelin's `SafeERC20.safeTransfer`.
- Add a `nonReentrant` guard (or transient-storage reentrancy lock) to `withdraw`, `cancelOrder`, `onAccept`, and `onGetResponse`.
- Explicitly check `_filled[commitment] == address(0)` before entering `withdraw` from `onAccept`, mirroring the guard already present for the same-chain `cancelOrder` path.

### Proof of Concept
1. Attacker calls `placeOrder` with two inputs: a small amount of native ETH and a large amount of an attacker-deployed `EvilToken` (its `transfer` function reenters the gateway), with `order.destination == order.source` (same-chain) so `cancelOrder` routes to `withdraw` directly.
2. After the deadline, attacker calls `cancelOrder`. Inside `withdraw`, `_filled[commitment]` is set, then the loop processes the ETH leg first via `beneficiary.call{value: amount}("")`.
3. During this native transfer, the attacker's beneficiary contract's `receive()` fires while `_orders[commitment][EvilToken]` is still non-zero (not yet decremented, since that token hasn't been processed in the loop yet) and while `_orders[commitment][ETH]` is also still non-zero (decrement at line 710 has not executed yet for the current iteration).
4. From this callback, the attacker's `EvilToken.transfer` (invoked later in the same loop, or via any other externally reachable function reading `_orders[commitment][...]`) can be crafted to observe/act on the stale (pre-decrement) escrow value, demonstrating the checks-effects-interactions violation described above.

Full confirmation of an end-to-end fund-drain requires building and running this scenario against the Tron contract with Foundry (using an approach similar to `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`), which was not runnable within this investigation.

        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

                if (!success) revert TransferFailed();
