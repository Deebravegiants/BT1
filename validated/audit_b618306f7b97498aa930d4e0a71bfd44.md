## Title
Native-fee dispatch (`EvmHost.dispatch`, `fundRequest`) can be DoS'd by manipulating the thin-liquidity local UniswapV2(-interface) pool used for the ETH→feeToken swap - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all let an unprivileged caller pay dispatch/fund fees in native token, converting it to the configured `feeToken` via a single on-chain AMM swap (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens`). This mirrors the reported bug class: relying on a single, potentially thin-liquidity market to gate a core unprivileged entry point lets an attacker manipulate that pool to revert or degrade legitimate users' transactions.

### Finding Description
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, whenever `msg.value > 0` the contract performs: [1](#0-0) [2](#0-1) [3](#0-2) 

`uniswapV2` is a single configured router address per chain in `HostParams`: [4](#0-3) 

The call `swapETHForExactTokens(fee, path, address(this), block.timestamp)` requests an *exact* amount of `feeToken` out, bounded implicitly by `msg.value` as the max input. This has no attacker-independent slippage buffer beyond what the caller happens to send, and the underlying pool's price is whatever the router/pool currently reflects. On chains where the configured router/pool has thin liquidity (a real concern the repo itself acknowledges — see `ConfiguredWrapperForkTest.t.sol`, which explicitly forks each mainnet chain to check "the configured wrapper is wired to a pool with real liquidity"), a single attacker can: [5](#0-4) 

- Front-run a victim's `dispatch`/`fundRequest` call with a swap that moves the pool price against the victim, causing `swapETHForExactTokens` to require more input than the victim's `msg.value` supplies, reverting the victim's dispatch (denial of service on message dispatch for anyone paying with native token).
- Repeat this cheaply against every native-fee dispatch as long as the pool stays thin, effectively DoS-ing the "pay-with-native-token" path of message dispatch on that chain, since there is no retry/backoff or minimum-liquidity guard in `EvmHost` itself.

Some chains route this swap through wrapper contracts around Uniswap V3/V4 (`UniV3UniswapV2Wrapper.sol`, `UniV4UniswapV2Wrapper.sol`) presenting the V2 interface, which still depend on the actual liquidity of the wrapped pool at swap time, so the same thin-liquidity/front-run exposure exists wherever the underlying pool (V2, wrapped V3, or wrapped V4) is shallow relative to the fee amounts being swapped. [6](#0-5) 

### Impact Explanation
This affects `EvmHost.dispatch`/`fundRequest`, which are core unprivileged entry points for dispatching POST/GET requests and funding pending requests — reachable by any user or app dispatching a cross-chain message and paying in native token. A successful griefing attack reverts legitimate dispatch transactions (denial of service of the native-fee path), and because gas/ETH spent to manipulate a thin pool for a block is cheap relative to potential disruption, this can be repeated to persistently block native-fee dispatch on a given chain. It does not directly cause fund loss but denies message delivery/funding via that fee-payment mode, which the report and validation criteria classify as a "route unable to deliver messages" — a Medium-severity availability issue localized to chains with thin swap-pool liquidity.

### Likelihood Explanation
Likelihood depends on the actual liquidity of the configured router/pool per chain; the project's own `ConfiguredWrapperForkTest.t.sol` treats "real liquidity" as something that must be explicitly verified per network, implying it is not guaranteed for every configured deployment (testnets, less liquid networks, or future added chains). Any chain whose configured pool is thin makes this attack economically trivial, matching exactly the attack pattern described in the reference report.

### Recommendation
- Do not rely on a single external AMM pool's live price for a fixed "exact output" swap without an explicit, caller/attacker-independent slippage tolerance parameter.
- Allow the caller to specify `amountInMaximum` explicitly (rather than implicitly via `msg.value`) and/or use `swapExactETHForTokens`-style logic with a minimum-out check plus refund, so a manipulated pool fails predictably rather than being griefable at negligible cost.
- Verify/monitor minimum liquidity depth for each chain's configured swap route as part of deployment/governance, and prefer routes into deep, well-audited pools (or the deepest available V3/V4 pool) over raw V2 pools, consistent with what the wrapper contracts already attempt.
- Consider allowing/require feeToken-denominated payment as the default recommended path (bypassing the swap) so a manipulated native-swap route cannot fully block dispatch for a determined caller.

### Proof of Concept
1. Attacker observes chain X has `HostParams.uniswapV2` pointing to a pool (or wrapped V3/V4 pool) with thin liquidity for the `WETH -> feeToken` pair.
2. Victim calls `EvmHost.dispatch(DispatchPost)` with `msg.value` sized to cover `post.fee` at the current quoted price via `swapETHForExactTokens`.
3. Attacker front-runs with a trade that shifts the pool price so that acquiring `post.fee` amount of `feeToken` now requires more ETH than the victim supplied.
4. Victim's `swapETHForExactTokens` call reverts inside `dispatch`, so the entire dispatch transaction reverts — the request is never created/emitted, denying that user's message dispatch.
5. Attacker repeats this against subsequent native-fee dispatch attempts as needed, at low cost, sustaining a DoS on that chain's native-fee dispatch path. [1](#0-0)

    /**
     * @notice Swaps ETH for exact amount of tokens through V3 with deadline protection.
     * @param amountOut The exact amount of tokens to receive
     * @param path Array of token addresses representing the swap path
     * @param recipient Address that will receive the output tokens
     * @param deadline Unix timestamp deadline by which the transaction must confirm
     * @return amounts Array of amounts [ethSpent, tokensReceived]
     */
    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });
