### Title
Webhook HMAC only covers the request body, letting an attacker forge the `shop-domain`, `topic`, and `webhook_id` fields to impersonate another shop — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` binds *nothing but the body bytes*. The `shop`, `topic`, `webhook_id`, and `api_version` values — all read straight from unauthenticated HTTP headers — are handed to the app's handler as trusted tenant/event identity without being part of the signed material.

### Finding Description
`Registry.process` is the library's entry point for verifying and dispatching inbound webhooks: [1](#0-0) 

It gates everything on `Utils::HmacValidator.validate(request)`, whose signature check is: [2](#0-1) 

`validate_signature` computes the HMAC over `verifiable_query.to_signable_string`. For webhook requests, that method is: [3](#0-2) 

It returns only `@raw_body` — none of `shop`, `topic`, `webhook-id`, or `api-version` are included in the signable string: [4](#0-3) 

These same unauthenticated header values are then passed straight through to the app's handler as the trusted identity of the event: [5](#0-4) 

Compare this to `Auth::Oauth::AuthQuery`, where every semantically important field (`code`, `host`, `shop`, `state`, `timestamp`) is included in `to_signable_string` and therefore cannot be tampered with once HMAC-verified: [6](#0-5) 

The equality the webhook code implicitly assumes is:
`HMAC_valid(body, secret) == (topic, shop, webhook_id, api_version are authentic)`

But the actual guarantee provided is only:
`HMAC_valid(body, secret) == (body bytes are authentic)`

Any party that can obtain one valid `(body, hmac)` pair — trivially available to any merchant who has installed the app on their own store, since Shopify sends them genuine webhooks with valid signatures for that shared secret — can replay that exact body and HMAC value to the app's webhook endpoint while substituting arbitrary values for `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id`. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will invoke the handler with attacker-chosen `shop`/`topic`/`webhook_id` values believed to be authentic.

### Impact Explanation
This breaks the tenant-identity binding that app developers are told to rely on (per `docs/usage/webhooks.md`, the handler is meant to trust `data.shop` and `data.topic` as coming from Shopify). An attacker who has legitimately installed the app on a shop they control can forge webhook deliveries that claim to originate from a *different* shop (or claim a different mandatory topic such as `shop/redact`, `customers/redact`, or `app/uninstalled`), causing the app to take shop-scoped actions (e.g., data deletion/redaction, marking a store uninstalled, revoking access, enqueuing jobs keyed by `shop`) against a victim tenant that never sent the request. This is cross-tenant impersonation of a webhook event, which lets an unprivileged internet user (any installer of the app) manipulate another merchant's data/state through the app.

### Likelihood Explanation
Reasonably likely: an attacker needs only to install the app once on a shop under their control to obtain a genuine, validly-signed webhook body/HMAC pair for a topic with a predictable/reproducible body (e.g., an empty-body mandatory webhook), then replay it with forged headers to the public callback endpoint. No secret key, access token, or privileged access is required — only network access to the app's webhook receiving route, which is by design internet-reachable.

### Recommendation
Include the tenant/event identity fields (at minimum `shop`, `topic`, and `webhook_id`) in the material that is HMAC-verified, or otherwise cryptographically bind them to the verified body (e.g., verify `shop` against the session/store the app already trusts for that install, rather than trusting the header value as-is). At minimum, document clearly that `data.shop`/`data.topic`/`data.webhook_id` are **not** covered by the HMAC and must not be used as an authorization/tenant boundary without independent verification (e.g., cross-checking against a known list of shops that have this webhook topic registered).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. for topic `app/uninstalled` with body `{}`, together with a valid `x-shopify-hmac-sha256` header (computed by Shopify with the app's real `client_secret`).
2. Attacker replays this exact `(body="{}", hmac=<valid>)` pair to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: shop/redact`
   - `x-shopify-webhook-id: <any-uuid>`
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (no header content is checked beyond presence), and `Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body` ("{}"), matching:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
```
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: {}, ...)`, and the app performs the corresponding action (e.g., data redaction/uninstall handling) for `victim-shop.myshopify.com`, despite the request never having been sent by Shopify on that shop's behalf.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
