### Title
Unvalidated mint `decimals` value causes permanent panic-based Denial of Service and fund freeze in `Calculator::normalize_decimal_v2`/`restore_decimal` - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`Initialize2` accepts attacker-supplied coin/pc SPL mints and stores their `decimals` field directly into `AmmInfo` without validating that the value is within a safe range for the fixed-point math used throughout the program. Every subsequent `Deposit`, `Withdraw`, `WithdrawPnl` and swap instruction calls `Calculator::normalize_decimal_v2`/`restore_decimal`, which perform `U128::from(10).checked_pow(native_decimal.into()).unwrap()`. Because `checked_pow` returns `None` on overflow, an unchecked `.unwrap()` panics whenever `native_decimal` is large enough to overflow a 128-bit integer. This mirrors the WildMIDI CVE-2017-11661 pattern, where a crafted field value drives an internal computation into an invalid/aborting state without any bounds validation, causing a crash.

### Finding Description
`Calculator::normalize_decimal_v2` and `Calculator::restore_decimal` compute `10u128.checked_pow(native_decimal)` where `native_decimal` derives from `amm.pc_decimals`/`amm.coin_decimals`: [1](#0-0) 

These decimals are populated at initialization directly from the SPL mint accounts supplied by the pool creator, with no explicit upper-bound check performed before calling `amm.initialize(...)`: [2](#0-1) 

`U128` is a 128-bit integer (max ≈ 3.4×10^38). Once `native_decimal` is large enough (SPL Token `decimals` is a `u8`, so values up to 255 are legal at the SPL-token level) `10^native_decimal` exceeds `U128::MAX`, so `checked_pow` returns `None`, and the subsequent `.unwrap()` panics, aborting the transaction.

This same `normalize_decimal_v2`/`restore_decimal` call is unconditionally exercised by every economically meaningful instruction that touches the pool state, e.g. `process_deposit`: [3](#0-2) 
`process_withdrawpnl` and `process_withdraw` (identical pattern): [4](#0-3) [5](#0-4) 

Because `amm.pc_decimals`/`amm.coin_decimals` are fixed at `Initialize2` time and never revalidated, once a pool is created with an over-sized decimals value, every future call into these code paths will panic deterministically — permanently bricking the pool.

### Impact Explanation
This is directly analogous to the CVE's bug class: a crafted/unchecked field value (mint `decimals`) drives a downstream computation (`checked_pow`) to an unrecoverable state (`None`), and the missing validation before the `.unwrap()` turns that into a hard panic (crash) rather than a graceful error. Because the tainted value is persisted in `AmmInfo` at `Initialize2` and re-used by every `Deposit`, `Withdraw`, `WithdrawPnl`, and swap instruction, the effect is not a single failed transaction but a **permanent freeze of all user and LP funds** in that pool — deposits, withdrawals, and swaps can never succeed again once the pool is created with an oversized decimals mint. This satisfies the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
`Initialize2` is a permissionless, unprivileged instruction — any pool creator can supply their own coin/pc mint accounts with an arbitrary `decimals` value (SPL Token allows up to 255) in a single transaction with attacker-chosen accounts and data, satisfying the reachability requirement. No privileged signer, off-chain component, or non-default build is required.

### Recommendation
Validate mint `decimals` (and any other externally supplied scaling factors) against a safe maximum (e.g., ensure `10^decimals` does not overflow `U128`/typically ≤ 19 given `sys_decimal_value` scaling) inside `process_initialize2` before calling `amm.initialize(...)`, rejecting mints whose decimals would overflow the fixed-point math. Additionally, replace the `.unwrap()` calls in `Calculator::normalize_decimal_v2`/`restore_decimal`/`normalize_decimal` with proper `checked_*` error propagation (`AmmError::ConversionFailure` or similar) so any future overflow degrades to a recoverable error instead of a panic.

### Proof of Concept
1. Create two SPL mints where at least one has `decimals` set to a value ≥ 39 (legal per SPL Token, `decimals: u8`).
2. Call `Initialize2` for a new AMM pool using these mints as coin/pc mints; the instruction succeeds because no decimals bound check exists (`program/src/processor.rs:931-938`).
3. Call `Deposit`, `Withdraw`, `WithdrawPnl`, or any swap instruction on the newly created pool.
4. Inside `Calculator::normalize_decimal_v2`, `U128::from(10).checked_pow(native_decimal.into())` returns `None` because `10^39` overflows `U128`; the subsequent `.unwrap()` panics, aborting every future transaction against this pool and permanently freezing deposited funds and LP tokens.
