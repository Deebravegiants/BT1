This confirms the vulnerability: `ShopifyAPI::Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`) derives the `shop` tenant identifier purely from the `x-shopify-shop-domain`/`shopify-shop-domain` header, while `to_signable_string` (used for HMAC computation in `lib/shopify_api/utils/hmac_validator.rb`) only covers the raw body. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) validates the HMAC and then passes the unauthenticated `request.shop` straight into `WebhookMetadata`, which host apps use as the tenant key (as documented in `docs/usage/webhooks.md`).

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook signature verification binds only the raw request body to the HMAC, but the `shop` (tenant identity) is read from a separate, unsigned header. Any party that can obtain one genuine `(body, hmac)` pair signed by the app's `client_secret` — trivially achievable by installing the app on their own shop and triggering a webhook — can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` accepts this as a validly-authenticated webhook and forwards the attacker-chosen shop to the app's handler, breaking the equality `shop_that_signed_the_hmac == shop_delivered_to_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read independently from a header that participates in no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature exclusively over `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (the unauthenticated header) as the tenant identity delivered to the app's handler: [4](#0-3) 

The `shop` field is documented as the authoritative tenant identifier handlers use to route/attribute webhook data: [5](#0-4) 

Because the signature never binds the `shop` claim, `HMAC(secret, body)` computed for shop A's webhook remains valid when replayed with `shop-domain: shop-B.myshopify.com`. This is the exact analog of the reported bug class: a field (`shop`) is acted upon (used as the tenant key) but is not covered by the authenticity check (HMAC over body only), i.e. "shop authenticated" ≠ "shop attributed to the data."

### Impact Explanation
Any unprivileged internet user who can install the app on a shop they control (e.g., a free Shopify dev/partner store) can trigger genuine webhooks with attacker-chosen body content, capture the valid `(body, hmac)` pair (since the same `client_secret` signs webhooks for every installed shop of a multi-tenant app), and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header identifying a victim shop. The host application — following this gem's documented contract that `data.shop` is trustworthy — will process attacker-controlled data as if it originated from the victim tenant. Depending on the webhook topic/handler logic, this enables cross-tenant data injection or corruption (e.g., forcing `customers/redact`, `shop/redact`, or order/product state changes to be attributed to and applied against another merchant's stored data/session), meeting the "cross-tenant access" criterion.

### Likelihood Explanation
High. No secrets, tokens, or privileged access are required — only the ability to install the app on any shop (self-serve via Shopify's normal app-install flow) to obtain one signed body/HMAC pair, plus the ability to send an HTTP POST with a modified header to the app's publicly reachable webhook endpoint. This requires no TLS interception, no leaked credentials, and no host-application misconfiguration beyond following this gem's documented usage exactly as shown in `docs/usage/webhooks.md`.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable string, or independently verify that the `shop-domain` header corresponds to a shop with a currently active, verified installation/session before trusting it. At minimum, document prominently that `x-shopify-shop-domain` is not authenticated by the HMAC and must be cross-checked by the host application against a known/installed shop list before use as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, no privileges needed).
2. Attacker triggers any subscribed webhook topic (e.g., `customers/update`) with attacker-controlled body content, and captures the resulting `x-shopify-hmac-sha256` header and raw body from the real Shopify-delivered request.
3. Attacker resends that exact `(raw_body, hmac)` pair to the app's webhook endpoint, replacing only the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`:
```ruby
hmac = <captured from real delivery for attacker-shop>
raw_body = <captured body>
headers = {
  "x-shopify-topic" => "customers/update",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request) # HMAC check passes; handler receives shop: "victim-shop.myshopify.com"
```
4. `Utils::HmacValidator.validate(request)` returns `true` (it never looked at the shop header), and the handler executes attacker-controlled `body` attributed to `victim-shop.myshopify.com`.
