### Title
Webhook `shop-domain` (and other Shopify headers) are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `x-shopify-shop-domain` (and `topic`/`webhook-id`/`api-version`) HTTP headers to build the `WebhookMetadata` passed to the app's handler. Because those headers are never part of the signed material, any party that can obtain one valid, HMAC-signed webhook body (e.g., by owning a shop that installs the app) can freely swap the `shop-domain` header to any other merchant's domain and have the gem accept it as an authenticated webhook "from" that other shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` performs only this body-HMAC check, then immediately trusts `request.shop` (the unauthenticated header) to construct the tenant-identifying `WebhookMetadata` delivered to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop header == shop cryptographically bound to the signed payload`. In reality the equality checked is only `HMAC(body) == received_hmac`; the `shop` value delivered to the handler is never part of that equation, so `shop_delivered_to_handler != shop_actually_authenticated`.

Because Shopify apps use a single `api_secret_key` shared across all installed shops (it is per-app, not per-shop), any attacker who controls a shop that has the app installed will legitimately receive Shopify webhooks whose HMAC is computed with that same shared secret over an attacker-chosen-shape body (attacker can trigger events, e.g. by creating orders/products in their own store, to get bodies they influence). The attacker can then replay that same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` hands the handler a `WebhookMetadata` claiming the event is `shop: <victim>`.

### Impact Explanation
This breaks the tenant isolation the gem is supposed to provide to webhook consumers: the handler receives data purportedly scoped to one merchant (`shop`) while it was never authenticated as coming from that merchant's install. Any host application that uses `WebhookMetadata#shop` (as the documented API expects, see `Registry.process`/`WebhookMetadata`) to select which tenant's records to create/update/delete based on webhook payload is exposed to cross-tenant data corruption/injection driven entirely by an unprivileged attacker who merely installs the app on their own store — no access token, `client_secret`, or privileged credential is needed. This matches the "High: cross-tenant access" impact bucket for this assessment.

### Likelihood Explanation
Likelihood is high: exploitation requires only (1) installing the target app on an attacker-controlled shop (a normal, unprivileged action for any Shopify merchant/dev store), (2) triggering an event that produces an attacker-influenced request body, and (3) resending that body to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No secrets need to be recovered or brute-forced; the HMAC the attacker already legitimately holds for their own body is reused verbatim.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`api-version`) headers into the signed material that is validated, or otherwise cryptographically verify that the shop domain in the request matches a shop actually authorized to send events for the payload (e.g., verify the header against Shopify's known relationship between webhook id/topic and destination shop server-side, or require the consuming application to independently confirm the shop is one that has completed OAuth for this app before trusting the payload). At minimum, update `Utils::HmacValidator`/`Webhooks::Request` so `to_signable_string` incorporates the `shop-domain` header (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed string), and document that consumers must not treat the header value as authenticated unless it participates in the signature.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g., `orders/create`) so Shopify sends a request with body `B` and header `x-shopify-hmac-sha256: HMAC(api_secret_key, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture `B` and its valid HMAC.
4. Resend the same body `B` and HMAC to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` — this only checks `HMAC(body)`, which still matches, so validation passes.
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)` — i.e., attacker-controlled data now appears authenticated as belonging to `victim.myshopify.com`, confirming the shop identity was never actually bound to the signature.
