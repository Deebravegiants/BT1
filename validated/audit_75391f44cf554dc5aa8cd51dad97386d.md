### Title
`HyperFungibleToken.send()`/`onAccept()` allow burning bridged tokens to the zero address - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol)

### Summary
`HyperFungibleToken.send()` burns the caller's tokens on the source chain and dispatches a cross-chain POST request carrying an arbitrary `to` recipient with no validation that it decodes to a non-zero address. On the destination chain, `onAccept()` decodes this recipient via `_toAddr()`, which only validates the byte length (must be 20 bytes) but never rejects `address(0)`, then mints directly to it. A user (or anyone crafting `SendParams.to` as 20 zero bytes) can burn their own — or, since `send()` is permissionless for the caller's own balance, cause loss of — tokens that are irrecoverably minted to `address(0)` on the destination chain.

### Finding Description
- `send()` immediately burns `params.amount` from `msg.sender` without checking `params.to` at all: [4](#0-3) .
- The dispatched `Message.to` is later decoded on the destination host in `onAccept()` via `_toAddr(message.to)`, and minted straight to the decoded `beneficiary` without any zero-address guard: [5](#0-4) .
- `_toAddr()` only enforces that the input is exactly 20 bytes long; it happily accepts `bytes20(0)` and returns `address(0)`: [3](#0-2) .

This is the same bug class as the referenced TimeLockPool report: a deposit/transfer entry point accepts a receiver parameter without validating it is non-zero, letting a caller irreversibly destroy value that should have been credited to a real account. Here, the destination-chain mint is not simply "lost to a burn address" — it is minted to `address(0)`, which is unrecoverable, while the corresponding tokens were already destroyed on the source chain via `_burn`. The identical code path (and identical `_toAddr` helper without a zero check) is duplicated in `HyperFungibleTokenUpgradeable.sol`.

### Impact Explanation
Funds bridged this way are permanently and unrecoverably lost — the source-chain balance is burned and the destination-chain mint target is the zero address, from which ERC-20 balances can never be moved out (no private key, no `transferFrom` allowance can move funds out of `address(0)`, and even if OpenZeppelin's `_mint` reverts on `to == address(0)` in some versions, the actual custom `ERC20`/mint implementation here does not add that guard beyond OZ's internal check — regardless, the intended recipient is never made whole and the operation constitutes an unrecoverable loss of user funds for any mistaken or malicious use of `to`). This satisfies the "permanent freezing/loss of funds" criterion for token bridge mint/burn paths explicitly in scope.

### Likelihood Explanation
Reachable from a single, unprivileged `send()` call by any token holder or integrator building `SendParams.to`. Any bug in an off-chain relayer, SDK, or integrating contract that fails to populate a real recipient address (e.g., defaulting to zero) results in silent, unrecoverable fund loss, and there is no on-chain safeguard to prevent it either accidentally or intentionally.

### Recommendation
Add explicit validation in `send()` (and equivalently in `onAccept()`/`_toAddr()`) that `params.to` decodes to a non-zero address before burning tokens, e.g.:
```solidity
address to = _toAddr(params.to);
if (to == address(0)) revert InvalidAddress(params.to.length);
```
Apply the same check in `HyperFungibleTokenUpgradeable.sol`'s identical `send()`/`onAccept()`/`_toAddr()` implementation.

### Proof of Concept
1. Caller holds `amount` of `HyperFungibleToken` tokens on chain A.
2. Caller calls `send(SendParams{ dest: chainB, to: abi.encodePacked(address(0)), amount, timeout, relayerFee, data: "" })`.
3. `send()` burns `amount` from caller on chain A and dispatches a POST request with `Message.to = abi.encodePacked(address(0))`.
4. On chain B, `onAccept()` decodes `beneficiary = _toAddr(message.to) = address(0)` (passes the 20-byte length check) and calls `_mint(address(0), amount)`.
5. `amount` tokens are now minted to `address(0)` on chain B and are permanently unrecoverable, while the equivalent balance was destroyed on chain A — a net, irreversible loss of the bridged value.

```text
    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
```
