### Title
`createMany`'s "allow updating existing ones" branch lets an attacker silently swap a wallet account's `seedId` for `passkey`-sourced accounts, bypassing `updateWalletAccount`'s immutability check - (File: `features/wallet-accounts/src/module/wallet-accounts.ts`)

### Summary
`WalletAccounts#createMany` overwrites `walletAccounts[walletAccount.toString()]` directly whenever the new account's `.toString()` collides with an existing entry, without going through `updateWalletAccount`, which is the only place that asserts `seedId` cannot change once set. Because `WalletAccount#toString()` deliberately omits `seedId` for any source other than `seed` (it only includes `id`, and `passkey` accounts are forbidden from having an `id`), a `passkey` account's `.toString()` is derived from `source`+`index` alone, so a second `create`/`createMany` call with the same index but a different `seedId` collides with the existing key and clobbers its `seedId` in the persisted store.

### Finding Description
`updateWalletAccount` enforces that `source`, `id`, and `index` never change and that `seedId` "can only be set if previously undefined": [1](#0-0) 

`createMany`, however, has a separate "allow updating existing ones" code path that does not call `updateWalletAccount` at all. It checks `exists` (whether `walletAccounts[walletAccount.toString()]` is already set) and, when `fillIndexGapsOnCreation` is enabled, simply merges the new `WalletAccount` object straight into the store: [2](#0-1) 

The duplicate-identity guard (`byUniqueFields`/`getUniqueTagForWalletAccount`, which does compare `id`/`seedId`/`index`) only runs in the `!exists` branch, so it is skipped entirely whenever the new account's `.toString()` already matches an existing key: [3](#0-2) 

The root cause is that `WalletAccount#toString()` is not a faithful encoding of all "identity" fields protected by `updateWalletAccount`. It joins `source`, `index`, and then either `[seedId, compatibilityMode]` (only for `source === 'seed'`) or `[id]` (for everything else): [4](#0-3) 

For `passkey` accounts specifically: `seedId` is required by the constructor (`assert(source !== PASSKEY_SRC || seedId, ...)`), but `id` is forbidden because `passkey` is in `SOFTWARE_SEED_SOURCES` (`assert(!isSoftware || !id, 'unexpected option "id" for a software wallet account')`): [5](#0-4) [6](#0-5) 

Since `toString()` for `passkey` falls into the `else` branch (`[this.id]`), and `id` is always `undefined`, the resulting key is just `passkey_<index>` regardless of `seedId`. Consequently, two `passkey` `WalletAccount` instances with the same `index` but different `seedId` produce the identical `.toString()` key, so the second `createMany`/`create` call takes the overwrite branch and replaces the stored account's `seedId` without ever passing through `updateWalletAccount`'s "seedId can only be set if previously undefined" assertion.

For `exodus`-sourced accounts this same gap exists in `toString()` (it also omits `seedId`), but `createMany` forcibly sets `data.seedId = primarySeedId` for `EXODUS_SRC` before construction, so an attacker cannot make it diverge: [7](#0-6)  There is no equivalent normalization for `passkey`, so the bypass is real there.

### Impact Explanation
`seedId` identifies which key material (which imported seed/credential) is used to derive addresses/signing keys for a wallet account. Silently swapping a `passkey` account's `seedId` after creation reassigns its derivation context to a different seed without any of the protections `updateWalletAccount` provides elsewhere, matching the "wrong-account/derivation-context reassignment" class of impact. This does not directly leak a secret or forge a signature by itself, but it corrupts the authenticity/consistency of persisted wallet-account state, which downstream signing/address-derivation code relies on to select the correct key material for a given account name.

### Likelihood Explanation
This requires the stated preconditions: `fillIndexGapsOnCreation: true` in module config, and the `create`/`createMany` module surface reachable by an unprivileged caller (per the question's precondition, without an unlock/lock-state gate). Given those preconditions, the exploit is deterministic and repeatable: any caller who can invoke `createMany` twice with the same `passkey` index but a different `seedId` will overwrite the stored account, since the code path contains no guard against this collision.

### Recommendation
In `createMany`'s overwrite branch, when `exists` is true, route the merge through `updateWalletAccount` (or replicate its `source`/`id`/`index`/`seedId` immutability assertions) instead of unconditionally assigning `walletAccounts[walletAccount.toString()] = walletAccount`. Alternatively, fix `WalletAccount#toString()` (or add a supplemental uniqueness check in `createMany`) so that `seedId` is always part of the identity comparison for any source that allows/requires `seedId` (`seed`, `exodus`, `passkey`), not just `seed`.

### Proof of Concept
Integration test in `features/wallet-accounts/src/module/__tests__/index.test.ts` style, with `fillIndexGapsOnCreation: true`:
```
1. walletAccounts.createMany([{ source: 'passkey', index: 0, seedId: 'seedA' }])
2. walletAccounts.createMany([{ source: 'passkey', index: 0, seedId: 'seedB' }])
3. const stored = await walletAccounts.get('passkey_0')
```
Expected (secure) behavior: step 2 should throw the same `'seedId can only be set if previously undefined'` error that `updateWalletAccount`/`update('passkey_0', { seedId: 'seedB' })` produces.
Actual (current) behavior: step 2 succeeds, and `stored.seedId === 'seedB'`, proving the identity field was overwritten without going through the immutability assertion.
