## Finding

### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body, not the shop-domain header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw JSON body. The `shop`, `topic`, `webhook_id`, and `api_version` values used to route and label the payload are read from HTTP headers that are **not included in the signed material**, so they can be freely rewritten by anyone who possesses one genuine, HMAC-valid webhook body for the app.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers, entirely outside that signed string: [2](#0-1) 

`Registry.process` validates only that HMAC-over-body, then dispatches the handler using the untrusted header-derived `shop`: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and `Context.api_secret_key`: [4](#0-3) 

The breaking identity equality is: **`shop` used by the handler == `shop` covered by the HMAC**. In this code, the HMAC covers `raw_body` only, while `request.shop` (and `request.topic`) come from unauthenticated headers. Because a single app's `api_secret_key` is shared across every merchant that installs the app, any actor who installs the app on their own store receives genuinely-signed webhook deliveries (valid `raw_body` + `hmac` pair). That attacker can then replay the identical `raw_body`/`hmac` to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to point at a victim shop. `Registry.process` will accept it as valid, since HMAC verification never touches the header, and will invoke the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` claiming to be the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: the handler code path in host applications typically uses `data.shop` to determine which merchant record to update (e.g. app/uninstalled, orders/create side effects, GDPR webhooks). An attacker-controlled body attributed to a victim's shop can be injected into the victim's application state — a cross-tenant data injection / spoofing that fits the Critical "cross-tenant access" impact category, since it lets one merchant forge webhook events on behalf of another merchant of the same app.

### Likelihood Explanation
Any unprivileged internet user can install a public app on their own development/trial store to obtain one legitimately signed `(raw_body, hmac)` pair for an arbitrary topic (many topics have attacker-influenced bodies, e.g. `app/uninstalled`, `customers/redact`, or order/product topics they control in their own store), then replay it against the same app's public webhook receiver endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged credential is required — only the ability to become a merchant of the target app, which is normally self-service.

### Recommendation
Bind the routing identity to the signed payload:
- Extract `shop`/`topic` from the JSON body when Shopify's webhook payload includes them, or otherwise fold the header values into the signable string before computing/verifying the HMAC.
- At minimum, cross-check the `shop` on `WebhookMetadata` against a shop known to be legitimately installed (and previously associated with a stored session/access token) before trusting it, rather than accepting whatever value arrives in the header.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com`.
2. App registers a webhook (e.g. `orders/create`); Shopify sends a legitimately HMAC-signed POST to the app's public webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and a valid `x-shopify-hmac-sha256` computed only over the JSON body.
3. Attacker crafts the order body content as desired (within what Shopify allows a merchant to control, e.g. order note/line items) and captures `(raw_body, hmac)`.
4. Attacker resends the same request to the same endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`).
5. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the unchanged HMAC: [5](#0-4) 
6. The handler executes believing the event genuinely originated from `victim.myshopify.com`, injecting attacker-controlled data into the victim's tenant state.
