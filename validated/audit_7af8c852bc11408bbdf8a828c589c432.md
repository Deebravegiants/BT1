Based on tracing the exact code paths, this claim does not hold.

**The equality to test:** `signed.deadline` (the value embedded in the ERC-191 payload string that was signed) must equal the value that ends up published to `intents.near`.

**Trace:**
- `IntentsSDK.sendSignedIntents` and `IntentExecuter.sendSignedIntents` take a caller-supplied `MultiPayload[]` and forward it verbatim to `intentRelayer.publishIntents({ multiPayloads: args.multiPayloads, quoteHashes })` — no parsing, no field extraction, no re-serialization occurs anywhere in this path. [1](#0-0) [2](#0-1) 
- `composeMultiPayloads` (used only by `signAndSendIntent`, not `sendSignedIntents`) only concatenates arrays of already-signed `MultiPayload` objects in order; it never mutates any payload's `payload` string or `deadline` field. [3](#0-2) 
- The ERC-191 signed bytes are `keccak256("\x19Ethereum Signed Message:\n" + len + payload)`, where `payload` is the exact JSON string (including `deadline`) produced at sign time by `IntentSignerViem.signIntent`. [4](#0-3) [5](#0-4) 

Since `sendSignedIntents` treats `MultiPayload` as an opaque blob and never re-derives or rewrites `payload`/`signature`, there is no code path by which the SDK could change `deadline` (or any other field) after signing while leaving the signature valid. Any attempt to tamper with the `payload` string post-signature would change the keccak256 preimage, causing `intents.near`'s own signature verification to reject the transaction — this is the standard ECDSA/ERC-191 message-integrity guarantee, not an SDK-level control, and it fully closes the gap the question describes. The "SDK only forwards; no check that fields match `envConfig`" premise is accurate but irrelevant to exploitability, because forwarding an opaque pre-signed blob cannot alter its signed content — the attacker who signs the payload with `deadline=X` is bound to `X` by cryptography, not by SDK validation.

The `mergeIntentPayloads` dedup via `new Set([...])` (used by `signAndSendIntent`, not `sendSignedIntents`) is a reference-based `Set`, so plain object literals are never reference-equal and are never collapsed; this doesn't affect the `deadline` field either, since `deadline` is a scalar field on the outer payload, not inside the `intents` array being deduped. import { keccak_256 } from "@noble/hashes/sha3";
import type { MultiPayload } from "@defuse-protocol/contract-types";

/**
 * Compute the prehash for ERC-191 payload
 * Format: "\x19Ethereum Signed Message:\n" + length + message
 */
function computeErc191Prehash(payload: string): Uint8Array {
	const data = new TextEncoder().encode(payload);
	const prefix = new TextEncoder().encode(
		`\x19Ethereum Signed Message:\n${data.length}`,
	);

	const result = new Uint8Array(prefix.length + data.length);
	result.set(prefix, 0);
	result.set(data, prefix.length);

	return result;
}

/**
 * Compute the Keccak256 hash of an ERC-191 payload
 * This is the hash that should be signed
 *
 * @param payload - The message string to hash
 * @returns 32-byte hash as Uint8Array
 */
function computeErc191Hash(payload: string): Uint8Array {
	const prehash = computeErc191Prehash(payload);
	return keccak_256(prehash);
}

/**
 * Compute hash from a signed ERC-191 payload
 *
 * @param signedPayload - The signed ERC-191 payload
 * @returns 32-byte hash as Uint8Array
 */
export function computeSignedErc191Hash(
	signedPayload: Extract<MultiPayload, { standard: "erc191" }>,
): Uint8Array {
	return computeErc191Hash(signedPayload.payload);
}
