## Analysis

The Tron deployment of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reproduces exactly the class of bug described in the report: escrow accounting is done from the *requested* transfer amount rather than the *actual* amount received by the contract, so fee-on-transfer tokens cause the protocol's internal bookkeeping to diverge from real token balances. Notably, the main EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against exactly this issue (balance-before/after measurement plus dedicated `FeeOnTransferToken` tests), but the Tron variant was not updated to match.

### Title
Fee-on-transfer tokens cause escrow over-crediting and protocol insolvency in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` on Tron computes the escrowed amount (`reducedInputs[i].amount`) from the order's requested input amount and protocol fee, but pulls tokens via `safeTransferFrom`/sweep without verifying the actual amount the contract received. For fee-on-transfer tokens, the amount credited to `_orders[commitment][token]` will exceed the tokens actually held by the contract.

### Finding Description
In the non-predispatch path: [1](#0-0) 

`order.inputs[i].amount` tokens are requested via `safeTransferFrom`, but the actual received amount is never measured. The escrow is then incremented by `reducedInputs[i].amount` — a value derived purely from `order.inputs[i].amount` and the protocol fee — regardless of what the gateway actually received: [2](#0-1) 

The predispatch/call-dispatcher path has a similar gap: it does check the dispatcher's balance before sweeping, but the final transfer of `balance` from the dispatcher back into the gateway (`IERC20.transfer.selector`) is not re-measured, so a second fee-on-transfer deduction on that hop is silently absorbed while the full `reducedInputs[i].amount` is still credited to escrow: [3](#0-2) 

This is the same root cause as the Blueberry `lend()` bug: the protocol records `pos.underlyingAmount += amount` using the pre-transfer-fee amount instead of the tokens it actually possesses, causing internal accounting to overstate real balances.

Contrast this with the main EVM contract, which was specifically fixed to handle fee-on-transfer tokens by snapshotting balances before/after every transfer and mutating `order.inputs[i].amount` to the actual received value before computing fees and crediting escrow: [4](#0-3) 
This fix is validated by dedicated tests (e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_Predispatch`): [5](#0-4) 
The Tron contract has no equivalent measurement logic, so it remains vulnerable.

### Impact Explanation
Every `placeOrder` call using a fee-on-transfer (or deflationary/rebasing-on-transfer) token as an input asset credits more to `_orders[commitment][token]` than the gateway actually holds. Because `withdraw`/redeem functions pay out based on this escrow ledger: [6](#0-5) 
the cumulative shortfall accumulates across multiple orders. Eventually some beneficiary's `transfer` call will fail (revert) or, worse, drain token balance meant for other still-pending orders — a direct case of protocol insolvency where later legitimate claimants cannot be paid the escrowed amount, i.e., permanent freezing/loss of funds for some order participants.

### Likelihood Explanation
Any unprivileged user can trigger this by calling `placeOrder` with an allow-listed fee-on-transfer ERC20 as an input token — no special privileges, admin action, or governance step is required. The only precondition is that the deployment's token allowlist/business use includes non-standard ERC20s (common on Tron given the diversity of TRC-20 tokens with transfer taxes).

### Recommendation
Mirror the fix already applied to the mainline EVM `IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after each `safeTransferFrom` (and after the dispatcher sweep in the predispatch path), mutate `order.inputs[i].amount` to the actual received amount, and compute `reducedInputs`/escrow credits from that actual amount rather than the caller-supplied `amount`.

### Proof of Concept
1. Admin whitelists a fee-on-transfer TRC-20 token `FOT` with a 1% transfer fee as a valid input asset.
2. Attacker/user calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, `protocolFeeBps = 0`.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; due to the 1% fee, the gateway's actual `FOT` balance only increases by `990e18`.
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits `1000e18` (since `protocolFeeBps == 0`, `reducedInputs == order.inputs`), not the `990e18` actually held.
5. When the destination-side redeem/refund path calls `withdraw`, it attempts to `transfer` up to `1000e18` `FOT` out of escrow for this and other orders, but the contract only holds `990e18` (minus whatever other orders similarly over-credited) — causing failed transfers or first-mover beneficiaries draining balance meant for others, i.e., protocol insolvency.

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
