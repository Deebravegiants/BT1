## Title
Webhook tenant identity (`shop` domain) is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from an **unauthenticated header** that is never part of the signed material. Any party who can produce one validly-signed webhook body (e.g. the legitimate operator of their own shop, who receives real, correctly-signed webhooks for their own tenant) can replay that exact body while substituting an arbitrary `x-shopify-shop-domain` header, and the HMAC check will still pass — because the signature never covered the header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic linkage to the body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then immediately forwards the untrusted `shop` header value to the handler as the tenant identifier, with no independent verification that this shop is the one that actually owns the signed body or has an active session/installation: [4](#0-3) 

The broken identity binding, stated as an equality that the code fails to enforce:
`shop-domain header used for tenant routing` ≠ `shop bytes covered by the HMAC signature`.

Concretely: a merchant who has legitimately installed the app receives real webhooks for their own shop, correctly signed with the app's `api_secret_key` over the JSON body. That merchant (an otherwise unprivileged party with respect to any other tenant) can capture such a payload and re-POST the identical body to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` still succeeds because the signature check never looked at the header, and `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim tenant with attacker-chosen body content.

### Impact Explanation
This breaks the shop/session tenant boundary (cross-tenant access): the gem hands application code a `shop` value it asserts is authenticated, but the field was never covered by the cryptographic check that produced that assertion. Any host application that uses `WebhookMetadata#shop` to select which merchant's session/data to read or mutate (the sanctioned use of this API, per `docs/usage/webhooks.md`) can be made to act on/for the wrong tenant using attacker-controlled body content, without any secret, access token, or privileged account beyond having installed the app for one's own store.

### Likelihood Explanation
Requires only: (1) the attacker's own installed shop to obtain one genuinely-signed webhook (trivial, they get many for their own tenant), and (2) the ability to send an HTTP POST with a custom header to the app's public webhook endpoint. No secret material, access token, or third-party compromise is required — only capturing traffic the attacker already legitimately receives.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind the header used for tenant routing to the verified body, e.g., recomputing/validating the HMAC using a signable string that concatenates header + body instead of body alone, or resolving the shop through server-side session lookup and cross-checking it against the header before dispatch. At minimum, document loudly that `request.shop` is unauthenticated and must be cross-verified by the host app before trust decisions.

### Proof of Concept
1. App installed on `attacker-shop.myshopify.com`; Shopify sends a real webhook:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B computed with app's api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   body: B
   ```
2. Attacker replays the exact same request but swaps the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC of body B>
   x-shopify-shop-domain: victim-shop.myshopify.com
   body: B
   ```
3. `Utils::HmacValidator.validate` — which only checks `body` — passes.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the app to act as if `victim-shop` sent this data, even though it never did.
