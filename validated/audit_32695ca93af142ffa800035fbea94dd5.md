### Title
Webhook HMAC only authenticates the raw body, not `x-shopify-topic`/`x-shopify-shop-domain`, allowing topic/shop spoofing on a validly-signed payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` (via `Registry.process`) authenticates nothing but the JSON body bytes. `Registry.process` then trusts the unauthenticated `topic` header to select which handler to invoke and passes the unauthenticated `shop` header straight into `WebhookMetadata`. Any HMAC-valid body can be replayed with an arbitrary topic and shop-domain header.

### Finding Description
The claimed binding is: `topic authenticated by the HMAC` should equal `topic the handler acts on (request.topic)`. Tracing the code shows this binding never exists:

- `Registry.process` computes validity as `Utils::HmacValidator.validate(request)` then does `handler = @registry[request.topic]&.handler` and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`. [1](#0-0) 
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac`. [2](#0-1) 
- `Webhooks::Request#to_signable_string` returns `@raw_body` only — it does **not** include `topic`, `shop`, `webhook_id`, or `api_version`: [3](#0-2) 
- `#topic` and `#shop` are read straight from attacker-controlled HTTP headers with no cross-check against the signed content: [4](#0-3) 

So the two sides of the equality diverge: the HMAC authenticates `HMAC_secret(raw_body)` only, while the handler dispatch and `WebhookMetadata.shop` act on `request.topic`/`request.shop`, values that are never part of the signed bytes.

Exploit flow with the defined attacker model: the attacker installs the app on their own development shop and registers a webhook endpoint they control. Shopify delivers a real webhook (e.g. `orders/create`) to that endpoint, HMAC-signed with the app's `api_secret_key` (the same secret shared across every shop that installs the app — it is not shop-scoped). The attacker captures the raw body and its valid `x-shopify-hmac-sha256` header, then replays that exact body+HMAC pair to the victim host app's webhook endpoint while rewriting `x-shopify-topic` to `shop/redact` and `x-shopify-shop-domain` to the victim's shop domain. Because neither header is part of `to_signable_string`, `HmacValidator.validate` still returns `true`, `Registry.process` looks up `@registry['shop/redact']`, and invokes the real GDPR shop-deletion handler with `shop:` set to the victim's shop domain.

No existing guard closes this gap: `HmacValidator.validate` only checks byte-for-byte HMAC over the body [5](#0-4) ; `ShopValidator`, JWT `aud` checks, and `Context.setup?/private?/embedded?` are unrelated to webhook body verification; Sorbet signatures only enforce types, not values.

### Impact Explanation
An attacker who can obtain any single valid HMAC-signed webhook body from Shopify (trivially available by installing the app on their own free development shop) can forge delivery of that body under any mandatory or optional topic name, and under any `shop-domain` value, to the host app's webhook endpoint. If the host app has registered a `shop/redact` (or `customers/redact`, `customers/data_request`) handler per the gem's documented usage, this lets an unprivileged attacker trigger GDPR shop-deletion/redaction logic against an arbitrary victim merchant shop — a destructive, cross-tenant action requiring no credentials belonging to the victim. This matches "Critical - cross-tenant access" causing destructive action on unintended tenant data, and it is trivially repeatable against any number of victim shop domains.

### Likelihood Explanation
Preconditions: the host app must expose a webhook endpoint calling `Registry.process` (documented normal usage) and must have a handler registered for a mandatory topic. Attacker cost is minimal — a free Shopify development store, installing the target app, and capturing one legitimate webhook delivery; no secrets, tokens, or privileged access are required. The attack is fully repeatable against arbitrary victim shop domains by simply changing the `x-shopify-shop-domain` header on each replay.

### Recommendation
Include the header values used for authorization/dispatch (`topic`, `shop-domain`, and ideally `webhook-id`/`api-version`) in the signable string, or otherwise cryptographically bind them to the HMAC before trusting them in `Registry.process`. At minimum, `to_signable_string` should incorporate the topic and shop headers so that changing them invalidates the signature, matching Shopify's documented webhook verification model where the HMAC is computed only over the body but the app is expected to still validate the delivered topic/shop against the subscription that was actually registered (i.e., cross-check `request.shop` against the session/shop that the app registered `shop/redact` handling for, rather than trusting the header value blindly).

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_allows_topic_and_shop_spoofing_on_valid_body_hmac
  raw_body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

  handler_called_with = nil
  handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| handler_called_with = data })

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "shop/redact", path: "path", delivery_method: :http, handler: handler,
  )

  # Attacker captured this exact (raw_body, hmac) pair from their OWN dev shop's
  # legitimately-signed "orders/create" webhook, then replays it with rewritten headers.
  forged_headers = {
    "x-shopify-topic" => "shop/redact",                     # rewritten from "orders/create"
    "x-shopify-hmac-sha256" => Base64.encode64(hmac),        # unchanged, still valid
    "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # rewritten from attacker's shop
  }

  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

  # Binding under test: HMAC-authenticated bytes (raw_body only) vs. what the handler acts on (topic/shop)
  assert_equal(raw_body, forged_request.to_signable_string)
  assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request)) # signature still valid

  ShopifyAPI::Webhooks::Registry.process(forged_request)

  assert_equal("shop/redact", handler_called_with.topic)
  assert_equal("victim-shop.myshopify.com", handler_called_with.shop) # attacker-chosen victim, never signed
end
```
This demonstrates that a body signed for one topic/shop is accepted by `Registry.process` for an entirely different, attacker-chosen topic and shop, confirming the broken binding.
