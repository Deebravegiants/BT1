### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  , which is what `Utils::HmacValidator.validate` checks against the `shopify-hmac-sha256` header [2](#0-1) . However, `Registry.process` takes the `shop`, `topic`, and `webhook_id` values straight from the (unsigned) HTTP headers and hands them to the app's handler as trusted identity/routing data [3](#0-2) , while those same fields are read via `shopify_header` from request headers that are never included in the signable string [4](#0-3) .

### Finding Description
The equality that should hold is: `shop_bound_by_hmac == shop_delivered_to_handler`. In this implementation that equality is broken: the HMAC only authenticates `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are pulled unauthenticated from HTTP headers [5](#0-4) . `Registry.process` validates only the body's HMAC, then constructs `WebhookMetadata` directly from these unauthenticated header values and dispatches it to the registered handler [6](#0-5) .

Because the shop identity is not cryptographically bound to the signed content, anyone who can capture one legitimate `(body, hmac)` pair — e.g., a merchant installing the app who legitimately receives webhooks for their own store — can replay that exact body/HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header value. `HmacValidator.validate` will still pass because it only recomputes the HMAC over `@raw_body`, which was untouched. The application-level handler then processes the payload as if it originated from the attacker-chosen shop, resulting in cross-tenant data injection/confusion in any app that uses `request.shop` (or `topic`/`webhook_id`) from `WebhookMetadata` to key persistence, cache invalidation, or business logic.

### Impact Explanation
This is a cross-tenant integrity/isolation violation, matching the Critical "cross-tenant access" category: a party who legitimately receives webhooks for their own tenant can forge webhook deliveries attributed to a victim tenant, since the shop identifier is unauthenticated relative to the HMAC that gates trust in the message.

### Likelihood Explanation
Likelihood is high for any attacker who is (or briefly becomes) a legitimate installer of the app — a low bar, since app installation itself typically requires no special privilege. That party inherently receives genuinely signed webhook bodies for their own shop and can trivially relay/replay them with modified `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers, since these headers are never part of the signed content.

### Recommendation
Bind the shop (and other identity/routing fields the handler trusts) into the HMAC-verified material, or otherwise cryptographically tie the header values to the verified request — e.g., include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed content [7](#0-6) ), or require the receiving app to independently cross-check the header-derived shop against an out-of-band trusted mapping (e.g., the session/shop the webhook subscription was created for) before acting on it.

### Proof of Concept
1. Attacker installs the app for their own shop `attacker.myshopify.com` and registers/receives a legitimate webhook, capturing the raw request body `B` and its valid `shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the shared secret).
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [8](#0-7) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, even though the HMAC never certified that association [9](#0-8) .
