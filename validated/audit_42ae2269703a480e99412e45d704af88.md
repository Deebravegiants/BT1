### Title
Escrowed order funds are permanently stuck if the beneficiary rejects the transfer, with no rescue path - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` (invoked from `ExtrinsicIntents.onAccept` / `IntentGatewayV2.onAccept` on `RedeemEscrow`/`RefundEscrow`) sends escrowed tokens straight to a `beneficiary` address derived from `order.user` (or the solver on redeem) with no fallback if the transfer reverts. There is no rescue/sweep mechanism for stuck order escrow analogous to the Kairos `AdminFacet` gap — the only sweep entrypoint in this contract (`SweepDust`) is scoped to protocol dust, not user escrow.

### Finding Description
`_withdraw` decrements `_orders[commitment][token]` and immediately pushes funds to `beneficiary` via `_sendValue` (native) or `IERC20.safeTransfer` (ERC-20): [1](#0-0) 

If the beneficiary is a contract that reverts on receiving native tokens, or the token itself reverts the transfer (e.g. a blacklist-capable stablecoin blacklisting the beneficiary after the order was placed but before settlement finalizes), the entire `_withdraw` call reverts. Since this is called from `onAccept`, which is invoked by the ISMP host on message delivery: [2](#0-1) 

the delivery of the `RedeemEscrow`/`RefundEscrow` message will always revert — every relayer retry hits the same revert deterministically, since the beneficiary and escrow contents never change. `_filled[commitment]` is never set (it's only assigned inside `_withdraw` when `finalize` is true, which is exactly the path that reverts), so the message can never be marked delivered, and the escrowed tokens sit in the contract forever.

Unlike the Kairos `AdminFacet`, which at least the report criticizes for lacking any emergency rescue, this contract has no owner/admin function capable of releasing a specific stuck order's escrow. The only privileged sweep is `SweepDust`, dispatched only by Hyperbridge itself and scoped to accumulated protocol dust (see `RequestKind.SweepDust` handling in `onAccept`), not to a specific order's `_orders[commitment][token]` balance: [3](#0-2) 

There is also no `onPostRequestTimeout`/`onGetTimeout` handler in `IntentsBase.sol` that could release escrow back to the user if the settlement message can never be delivered — confirmed absent by search of the file.

### Impact Explanation
This permanently freezes user/solver funds in the escrow contract with no recovery path — matching the "permanent freezing of funds" and "route unable to deliver messages" criteria. Once a beneficiary address becomes unable to receive the token (blacklisting, a contract without a payable fallback, a hostile `onERC721Received`-style rejection for non-standard tokens, etc.), both the escrowed principal and any accumulated `TRANSACTION_FEES` for that order (also paid out in the same reverting call) are stuck indefinitely, and the underlying ISMP message can never be marked delivered.

### Likelihood Explanation
Reachable from a single order lifecycle: any user can place an order whose destination beneficiary later becomes a rejecting recipient (deliberately or due to external token-level blacklisting), or a griefer can front-run to get a beneficiary blacklisted before settlement lands. No special privilege is required, and the failure is deterministic once triggered — every relayer delivery attempt reverts identically, so it isn't a transient issue that can self-resolve.

### Recommendation
Wrap the token transfer in `_withdraw` in a try/catch (or use a pull-payment pattern) so that a failing beneficiary transfer does not block finalization of the escrow record; on failure, credit the amount to an internal claimable balance tied to the commitment/beneficiary that can be withdrawn later via a separate `claim()` call (or redirected to a different address by the beneficiary), rather than reverting the entire message-delivery path. Alternatively, add a governance/timeout-triggered rescue path for a specific order's escrow analogous to how `SweepDust` exists for protocol dust.

### Proof of Concept
1. User places a cross-chain order whose `order.user` (echoed into `WithdrawalRequest.beneficiary`) is a smart-contract address without a receive/fallback function (for native-token orders), or a token address that has since blacklisted that beneficiary (for ERC-20 orders, e.g. USDC-style tokens).
2. Order proceeds normally: solver fills it, or the order is cancelled — either way a `RedeemEscrow`/`RefundEscrow` POST request is dispatched cross-chain and eventually delivered to the source chain's `onAccept`. [2](#0-1) 
3. `onAccept` calls `_withdraw(body, ..., true)`, which attempts `_sendValue`/`safeTransfer` to the rejecting beneficiary and reverts. [1](#0-0) 
4. Every relayer resubmission of the same message hits the identical revert; `_filled[commitment]` is never set, and the escrowed tokens plus accrued fees for that commitment remain locked in the contract with no admin or user-triggered function able to release them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }
