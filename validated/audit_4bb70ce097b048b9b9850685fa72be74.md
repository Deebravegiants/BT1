### Title
Unbounded `protocolFeeBps` / `surplusShareBps` in Tron `IntentGatewayV2.setParams()` Can Brick `placeOrder` or Confiscate 100% of User Escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` re-implements the mainline EVM gateway's parameter-setting logic but drops the bounds validation that the mainline implementation enforces. `setParams()` writes an attacker/operator-supplied `Params` struct — including `protocolFeeBps` — directly to storage with **no range check at all**, whereas the canonical EVM `IntentsBase._validateParams()` explicitly caps `protocolFeeBps < 10_000` and `surplusShareBps <= 10_000`. This is the exact bug class described in the external report: a percentage-typed configuration value (`_feePercentage` / here `protocolFeeBps`) is not regulated to a sane range (0–100%).

### Finding Description
`evm/tron/contracts/apps/IntentGatewayV2.sol` defines its own `setParams`: [1](#0-0) 

```solidity
function setParams(Params memory p) public {
    if (msg.sender != _admin) revert Unauthorized();
    _admin = address(0);
    _params = p;
}
```

No call to any validation routine is made before `_params = p` is committed. Compare this to the mainline EVM contract (`IntentsBase.sol`), which gates every params write through `_validateParams`: [2](#0-1) 

```solidity
function _validateParams(Params memory p) internal view {
    if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
    if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
    if (p.surplusShareBps > 10_000) revert InvalidInput();
    if (p.protocolFeeBps >= 10_000) revert InvalidInput();
    if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
}
```

and the dedicated foundry regression tests confirm this bound is a deliberate, security-relevant invariant on the mainline contract: [3](#0-2) 

The Tron variant's `_params.protocolFeeBps` (and `surplusShareBps`) is later consumed unguarded in `placeOrder`, exactly the same way as the mainline gateway: [4](#0-3) 

```solidity
uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
if (protocolFeeBps == 0) {
    protocolFeeBps = _params.protocolFeeBps;
}
...
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
```

If `protocolFeeBps` is set at or above `10_000` (100%), every subsequent `placeOrder()` call by any ordinary user reverts on the `originalAmount - protocolFee` underflow (Solidity 0.8 checked arithmetic) — permanently bricking order placement on this deployment. If it is set to a large value just under `10_000` (e.g., 9999 = 99.99%), the gateway confiscates nearly all of every user's escrowed input as "protocol fee/dust" while the user still receives (and pays for) a fill obligation sized off the original, un-reduced amount — a direct fund-loss vector for every unprivileged intent placer who interacts with the gateway after such a value is set.

### Impact Explanation
This directly maps to the two accepted impact classes:
- **Permanent freezing of funds / a route unable to deliver messages**: an out-of-range `protocolFeeBps` (≥10 000) causes an arithmetic underflow revert in `placeOrder`, permanently disabling the intents route on that Tron deployment for every future user.
- **Concrete theft of funds**: a value just below 10 000 lets the gateway sweep almost the entirety of every placed order's escrowed input as "dust," which is unrecoverable by the user under normal escrow/redemption flow.

Both outcomes are triggered the moment any unprivileged user calls the public, unauthenticated `placeOrder()` entry point — the same entry point every intent placer must use — once the unguarded `setParams` has installed an out-of-range value.

### Likelihood Explanation
`setParams` is a one-shot, admin-gated call (`_admin` is zeroed after use), so exploitation requires either (a) an operational/configuration mistake by whoever runs the one-time setup (entering percent instead of basis points, or a value ≥10 000 by fat-finger), or (b) a compromised admin key during that narrow initialization window. Unlike the mainline EVM contract, which structurally prevents this class of mistake with `_validateParams`, the Tron contract has no such defense-in-depth, so any slip during deployment/initialization is unrecoverable and immediately affects every subsequent unprivileged caller of `placeOrder`. This mirrors the original report precisely: the fix was to bound the percentage field, and that fix is present in the mainline contract but missing in this port.

### Recommendation
Port `IntentsBase._validateParams()` (or an equivalent check) into the Tron `IntentGatewayV2.setParams()` before committing `_params = p`, enforcing `protocolFeeBps < 10_000` and `surplusShareBps <= 10_000` (and the other `host`/`dispatcher`/`priceOracle` sanity checks already present on the mainline contract), and apply the same bound wherever `_destinationProtocolFees` entries are written for this Tron deployment.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` implementation; `_admin` is set in the constructor.
2. From `_admin`, call `setParams(Params({..., protocolFeeBps: 10_000, ...}))` — no revert occurs, unlike the mainline contract which would revert with `InvalidInput`.
3. Any user calls `placeOrder()` with any input token/amount:
   - `protocolFee = (originalAmount * 10_000) / 10_000 = originalAmount`
   - `reducedAmount = originalAmount - protocolFee = 0` succeeds only for `protocolFeeBps == 10_000`; for `protocolFeeBps > 10_000` the subtraction underflows and reverts, permanently bricking `placeOrder`.
   - For `protocolFeeBps == 9_999`, users escrow their tokens but only `0.01%` is credited toward `_orders[commitment][token]`, and the remaining `99.99%` is emitted as `DustCollected` — collectible by a beneficiary via `_sweepDust`, i.e., value permanently leaves the user's control for a fraction of the promised fill.
