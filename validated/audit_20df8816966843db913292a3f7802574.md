### Title
Cross-Tenant Webhook Impersonation via Unbound `shop-domain` Header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then trusts the unauthenticated `shopify-shop-domain` header as the tenant identity passed to the app's handler. Because the shop header is never included in the signed material, any party who can obtain one validly-signed webhook body (e.g., by installing the public app on their own free store) can replay that body to the app's webhook endpoint with a forged `shop-domain` header claiming to belong to a different (victim) merchant, causing the handler to process attacker-controlled data under the victim's tenant identity.

### Finding Description
The webhook signature is computed only over the raw HTTP body: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` — which checks `hmac == HMAC(secret, raw_body)` — and then immediately forwards the unauthenticated `request.shop` header value as the tenant identity to the registered handler: [3](#0-2) 

`HmacValidator.validate` confirms this: it only ever hashes `verifiable_query.to_signable_string`, which for `Webhooks::Request` is `@raw_body` alone: [4](#0-3) 

**The broken identity binding:** `shop header used to key/attribute the webhook == shop bytes actually covered by the HMAC`. The left side is attacker-controlled (any HTTP header on the POST request); the right side is only the JSON body. Since a single Shopify app's `client_secret` signs webhooks for *every* shop that has the app installed, an unprivileged user can install the app on their own store (no special credential needed — this is normal, free app installation), capture one of their own genuinely-signed webhook deliveries, and then POST that same `raw_body` + valid `hmac` to the app's webhook endpoint while swapping the `shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` will still pass (same body, same signature), and `Registry.process` will hand the handler a `WebhookMetadata` object asserting the victim's shop with attacker-chosen body content.

### Impact Explanation
This breaks the tenant boundary between shops sharing the same app installation (Critical — cross-tenant access): an attacker can inject or replay arbitrary (but validly-HMAC'd, from their own shop) webhook payloads attributed to a different merchant's `shop` identity. Any host application that uses `WebhookMetadata#shop` to select which tenant's data/session to update (the intended and documented use of this field) will apply attacker-supplied webhook data to the wrong tenant, corrupting or exfiltrating cross-tenant state depending on what the handler does with `data.shop` and `data.body`.

### Likelihood Explanation
Likelihood is realistic and requires no privileged credentials: any unprivileged internet user can install the target public app on a free/dev store, observe one legitimately Shopify-signed webhook delivery for a topic the app subscribes to, and replay it with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. No knowledge of `api_secret_key`, access tokens, or the victim's credentials is required — only the ability to send an arbitrary HTTP request to the app's public webhook endpoint, which is by definition internet-reachable.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable material, or independently verify that the `shop` header corresponds to a shop with a currently active installation/session before trusting it as the tenant key in `Registry.process`. At minimum, cross-check `request.shop` in `lib/shopify_api/webhooks/registry.rb#process` against a known-installed-shop store before dispatching to the handler.

### Proof of Concept
1. Install the target Shopify app (as any user) on `attacker-shop.myshopify.com`; trigger a subscribed webhook topic (e.g., `products/update`) to receive a genuinely Shopify-signed delivery:
   - Headers: `shopify-hmac-sha256: <valid HMAC of raw body with app secret>`, `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: products/update`.
   - Body: `{"id": 123, ...attacker-controlled product payload...}`.
2. Replay the exact same raw body and `shopify-hmac-sha256` value to the app's public webhook endpoint, but change the header to `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` (lines 12-31) recomputes the HMAC over `@raw_body` only, which is unchanged, so validation succeeds.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188-200) builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the forged `victim-shop.myshopify.com` value and passes it to the registered handler, which acts on the victim shop's tenant using attacker-supplied data.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
