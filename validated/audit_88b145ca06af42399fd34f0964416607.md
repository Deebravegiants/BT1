### Title
Webhook `shop-domain` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating `Utils::HmacValidator.validate(request)`, which computes/verifies the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) . The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from HTTP headers that are never part of the signed bytes [4](#0-3) . `Registry.process` passes this unauthenticated `shop` value straight into `WebhookMetadata` given to the app's handler as the tenant identity [2](#0-1) .

### Finding Description
The identity binding that should hold is: `HMAC-signed bytes == bytes the handler trusts as belonging to shop X`. Here it doesn't — the HMAC only binds the *body*, not the *shop* the body is attributed to. Because the app-level `client_secret`/`api_secret_key` used to sign webhooks is the same across every shop that installs the app (it's an app secret, not a per-shop secret), any actor who can install the app on their own shop (a normal, unprivileged action any internet user can do by installing a public/dev-store app) will receive genuinely Shopify-signed webhooks for their own shop, with valid HMACs computed over bodies they control. Since the `shop-domain` header sits outside the signed payload, that attacker can take a validly-signed `(raw_body, hmac)` pair from their own shop's webhook and replay it to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` will still succeed because it recomputes the HMAC only from `raw_body` [5](#0-4) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim's `shop` [6](#0-5) .

### Impact Explanation
This breaks the tenant boundary: the gem authenticates "this body came from Shopify," not "this body belongs to this shop." Any host application that uses `request.shop` from `WebhookMetadata` to key per-tenant data (session lookup, database writes, cache invalidation, billing state, etc.) — which is exactly the intended and documented usage pattern — will process attacker-controlled webhook content under a victim's identity, i.e., cross-tenant data injection/corruption using only the ability to self-install the app.

### Likelihood Explanation
Likelihood is realistic: installing a Shopify app on one's own development/trial store is trivial and gives an attacker a stream of validly-HMAC'd webhooks whose header fields (including `shop-domain`) are attacker-visible and swappable before hitting the app's endpoint. No access to the merchant's or app's secrets is required.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, and ideally `topic`/`webhook-id`) in the signable string that the HMAC is verified against, or otherwise cryptographically bind the shop header to the signature (e.g., verify shop against a known-registered shop/session before trusting it, or require the host application to independently confirm the shop owns the corresponding webhook subscription/session before acting on `WebhookMetadata#shop`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, completing OAuth normally.
2. Shopify sends the attacker's app endpoint a legitimate webhook, e.g. `orders/create`, with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and some `raw_body`.
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the unchanged HMAC [5](#0-4) .
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: attacker_controlled_body, ...)` and processes attacker-controlled data as if it belonged to `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
