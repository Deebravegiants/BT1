Webhook `shop` (and `topic`/`webhook-id`) identity is trusted from unauthenticated HTTP headers while HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` identity that is handed to the app's webhook handler is read from an HTTP header that is never included in the signed material. The binding "shop the HMAC vouches for" == "shop passed to the handler" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over exactly that `to_signable_string` value (the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` then raises only if this body-only HMAC fails, and afterwards constructs the metadata object passed to the app-defined handler using the **unauthenticated** `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

Because the signature is computed only from the body bytes and is completely independent of the `shop`/`topic`/`webhook-id` headers, any request whose body byte-for-byte matches a body that was legitimately HMAC-signed by Shopify for the app's `client_secret` will pass validation regardless of which `shop-domain`, `topic`, or `webhook-id` header accompanies it. An attacker who operates their own store using the app receives genuine, correctly-signed webhooks for their own shop (e.g., `orders/create`, `customers/data_request`, etc. with a body they can predict or observe). Because many webhook payloads are small, generic, or attacker-influenced (e.g., an app-defined webhook whose JSON body content the attacker controls or can force to a known/fixed value, or one where the attacker can find/produce a body that collides with another shop's plausible payload), the attacker can take that valid `(body, hmac)` pair from their own shop and replay it to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header value naming a victim shop. `Utils::HmacValidator.validate` still succeeds because it never inspected those headers, and `Registry.process` will invoke the app's handler with `WebhookMetadata.new(shop: <victim-shop>, ...)`.

The identity equality this breaks is:
`shop authenticated by the HMAC (∅, since HMAC covers no header)` ≠ `shop the handler is told the webhook came from (header value, attacker controlled)`.

This is exactly the "field acted on but not covered by the HMAC" bug class: the `shop` field drives per-tenant processing in the app (session/data lookups, GDPR redact flows, order/customer processing keyed by shop) but is not part of the signed payload the gem verifies.

### Impact Explanation
Any application built on this gem that keys per-shop side effects (writing shop-scoped data, triggering `customers/redact`/`shop/redact` mandatory compliance flows, updating a shop's local records, revoking access, etc.) off of `WebhookMetadata#shop` is exposed to cross-tenant data confusion/injection: a merchant using the app can forge webhook deliveries that the gem will authenticate as coming from a different merchant's shop, letting one tenant inject data or trigger sensitive lifecycle actions (e.g., forced data-erasure flows) against another tenant's shop record. This satisfies the "cross-tenant access" Critical impact category, since the security boundary between shop identity and the byte payload the gem actually verifies is not enforced by the library itself.

### Likelihood Explanation
Exploitation requires the attacker to have at least one shop able to install the app (any developer/partner or merchant account, which is an unprivileged capability relative to the app's own credentials) so they can obtain a validly-signed `(body, hmac)` pair, then send a raw HTTP POST to the app's public webhook endpoint with a spoofed `x-shopify-shop-domain`/`shopify-shop-domain` header. No access token, API secret, or privileged credential is required — the webhook endpoint is a public callback URL and the header manipulation happens entirely on the attacker's own outbound request. This is a direct exploitation of the gem's own verification logic (`Request#to_signable_string`, `HmacValidator.validate`, `Registry.process`), not a misuse of documented behavior by a host app.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) values as part of the material that is cryptographically bound to the request, or otherwise fail closed when they are inconsistent with data derivable from an already-authenticated source (e.g., verify `shop` against a previously established, HMAC/OAuth-authenticated session for that shop before dispatching to handlers). At minimum, document loudly and enforce in the gem that `WebhookMetadata#shop` must not be trusted for authorization decisions unless independently corroborated, since the current `to_signable_string` implementation binds the signature only to the body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers (or already receives) a legitimate webhook whose JSON body is fixed/predictable, e.g. `{}` for a `shop/redact` mandatory webhook. Shopify computes and sends:
   - Header `x-shopify-hmac-sha256: base64(HMAC-SHA256(app_secret, "{}"))`
   - Header `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Header `x-shopify-topic: shop/redact`
2. Attacker captures this `(body="{}", hmac)` pair.
3. Attacker sends their own POST directly to the app's webhook callback URL with the same body `"{}"` and the same `hmac` header, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` (per `lib/shopify_api/utils/hmac_validator.rb:26-31`) recomputes the HMAC over `to_signable_string` = `"{}"`, which still matches the supplied `hmac`, so validation passes.
5. `Registry.process` (per `lib/shopify_api/webhooks/registry.rb:188-199`) proceeds to call the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "shop/redact", ...)`, causing the app to execute shop-scoped logic (e.g., data deletion/redaction) attributed to `victim-shop.myshopify.com` even though Shopify never sent this request for that shop.
