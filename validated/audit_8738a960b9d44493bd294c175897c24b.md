### Title
GraphQL password-change mutation bypasses password complexity requirements - (File: core/web/resolver/mutation.go)

### Summary
The GraphQL `updateUserPassword` mutation, resolved by `Resolver.UpdateUserPassword`, allows an authenticated user to set an arbitrarily weak new password (empty, single character, containing their own email, etc.) because it never calls `utils.VerifyPasswordComplexity`, unlike the equivalent REST endpoint.

### Finding Description
The REST endpoint `PATCH /v2/user/password`, handled by `UserController.UpdatePassword`, validates the old password and then explicitly enforces complexity on the new password before persisting it: [1](#0-0) 

In contrast, the GraphQL mutation resolver `Resolver.UpdateUserPassword` performs the old-password check and session-clearing, then calls `SetPassword` directly with the user-supplied `NewPassword`, with no call to `utils.VerifyPasswordComplexity` or any other strength/length check anywhere in the function: [2](#0-1) 

`SetPassword` in the local-auth ORM performs no validation itself — it simply hashes and stores whatever string it is given: [3](#0-2) 

A repo-wide search confirms `utils.VerifyPasswordComplexity` is invoked only from `core/web/user_controller.go`, `core/cmd/key_store_authenticator.go`, `core/config/toml/types.go`, and `core/sessions/user.go` (initial user creation) — `core/web/resolver/mutation.go` is absent from that list, meaning the GraphQL path to change a password is not covered by the complexity check that the REST path enforces. This is the direct analog of CVE-2024-42850 (Silverpeas password-change function bypassing password complexity requirements): the same operation is validated on one interface and not on another, letting an unprivileged/authenticated user push an arbitrarily weak password (e.g. `""`, `"a"`, or a value containing their own email) through the alternate GraphQL entry point.

### Impact Explanation
Any authenticated Chainlink node user (any role, since `authenticateUser` only requires a valid session, not admin) can set their own account password to an empty string or a trivially guessable value via the GraphQL API, undermining the node's password policy (minimum 16 characters, no email substring, no whitespace) that is otherwise enforced everywhere else, including at user creation and REST-based password change. A weak/empty credential materially increases the risk of credential-stuffing or brute-force account takeover of node-admin-capable accounts, which control job specs, bridges, and fund-moving transfer endpoints on this internet-facing node API.

### Likelihood Explanation
High. No special privilege beyond a valid session is required; the mutation is reachable by any logged-in user via the standard GraphQL API of the node, and the flaw is a straightforward missing-check, not a race condition or edge case.

### Recommendation
Add a `utils.VerifyPasswordComplexity(args.Input.NewPassword, dbUser.Email)` check in `Resolver.UpdateUserPassword` immediately after the old-password verification and before calling `SetPassword`, mirroring the check already present in `UserController.UpdatePassword`, and surface complexity failures via `NewUpdatePasswordPayload` input errors (consistent with the existing `InputErrors` pattern used for the "old password does not match" case).

### Proof of Concept
1. Authenticate as any Chainlink node user (obtain a valid session cookie via `/sessions` login or GraphQL login).
2. Send the GraphQL mutation:
```graphql
mutation {
  updateUserPassword(input: { oldPassword: "<current password>", newPassword: "a" }) {
    ... on UpdatePasswordSuccess {
      user { email }
    }
    ... on InputErrors {
      errors { path message code }
    }
  }
}
```
3. Observe that the mutation succeeds (returns `UpdatePasswordSuccess`) despite `newPassword` being far below the mandated 16-character minimum and failing every other complexity rule, whereas the equivalent REST call `PATCH /v2/user/password` with the same body would be rejected with `422 Unprocessable Entity` per `core/web/user_controller_test.go` (lines 49-55), demonstrating the inconsistency/bypass.

func (r *Resolver) UpdateUserPassword(ctx context.Context, args struct {
	Input UpdatePasswordInput
}) (*UpdatePasswordPayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	session, ok := webauth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return nil, errors.New("couldn't retrieve user session")
	}

	dbUser, err := r.App.AuthenticationProvider().FindUser(ctx, session.User.Email)
	if err != nil {
		return nil, err
	}

	if !utils.CheckPasswordHash(args.Input.OldPassword, string(dbUser.HashedPassword)) {
		r.App.GetAuditLogger().Audit(audit.PasswordResetAttemptFailedMismatch, map[string]any{"user": dbUser.Email})

		return NewUpdatePasswordPayload(nil, map[string]string{
			"oldPassword": "old password does not match",
		}), nil
	}

	if err = r.App.AuthenticationProvider().ClearNonCurrentSessions(ctx, session.SessionID); err != nil {
		return nil, clearSessionsError{}
	}

	err = r.App.AuthenticationProvider().SetPassword(ctx, &dbUser, args.Input.NewPassword)
	if err != nil {
		return nil, failedPasswordUpdateError{}
	}

	r.App.GetAuditLogger().Audit(audit.PasswordResetSuccess, map[string]any{"user": dbUser.Email})
	return NewUpdatePasswordPayload(session.User, nil), nil
}
