### Title
`Auth::Oauth.begin_auth` sends `client_id`/`scope` to an unvalidated `shop` host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorize URL by interpolating the caller-supplied `shop` string directly into `https://#{shop}/admin` via the private `auth_base_uri` helper, without ever calling `ShopifyAPI::Utils::ShopValidator.sanitize!`. As a result, the authorize URL - including `client_id` and `scope` in its query string - is sent to whatever host string the caller passes as `shop`.

### Finding Description
The binding that should hold is: `URI(begin_auth(shop: shop, ...)[:auth_route]).host == ShopValidator.sanitize!(shop)` (i.e., the host used in the redirect must be a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`).

Tracing the code: [1](#0-0) 
builds `query` (containing `client_id: ShopifyAPI::Context.api_key` and `scope: scope.to_s`) and then calls `auth_base_uri(shop)`: [2](#0-1) 
`auth_base_uri` simply returns `"https://#{shop}/admin"` for any `shop` that doesn't end in `.my.shop.dev` — there is **no call to `ShopValidator.sanitize!`** or `ShopValidator.sanitize_shop_domain` anywhere in `begin_auth` or `auth_base_uri`. This is unlike the validator module that exists precisely for this purpose, `ShopifyAPI::Utils::ShopValidator`, which restricts hosts to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [3](#0-2) [4](#0-3) 

The gem's own documented usage pattern feeds `shop` straight from an unauthenticated request value (e.g. a header) into `begin_auth` with no validation step shown or required: [5](#0-4) 

Attacker request: `GET /install?shop=attacker.example.com` (or any string) reaching an app's login route that calls `Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` unchanged. Since `scope_override` defaults to `nil`, `scope = ShopifyAPI::Context.scope` (the app's full configured scope list), and `client_id = Context.api_key` are embedded into `https://attacker.example.com/admin/oauth/authorize?client_id=...&scope=...&...`, which is then set as the redirect `Location` header sent to the victim's browser.

No existing guard in this call path — `Context.setup?`, `Context.private?`, `HmacValidator.validate` (used only in `validate_auth_callback`, not `begin_auth`), or Sorbet's `String` typing on `shop` — prevents an arbitrary string from flowing unchecked into the redirect host. Sorbet only requires `shop` to be a `String`, not a valid Shopify domain.

### Impact Explanation
This discloses the app's `client_id` (public but sensitive) and the app's full requested `scope` list to an attacker-chosen host, and more importantly it hijacks the OAuth redirect target itself — a victim who is lured to `/install?shop=attacker.example.com` gets redirected to an attacker-controlled page dressed up to look like the Shopify authorize screen, enabling a forced/phishing OAuth completion against that victim. This matches the "High" category: forced OAuth completion / SSRF-style redirect to an unintended host driven by unauthenticated attacker input. It is repeatable against any victim who can be lured to click a crafted install link for any app built on this gem using the documented `begin_auth` pattern.

### Likelihood Explanation
No special preconditions beyond the app implementing the documented, gem-recommended pattern of passing an unsanitized `shop` value (from a query/header) into `begin_auth` — which is exactly what the docs' example code does (`shop = request.headers["Shop"]`, passed straight to `begin_auth`). The attacker only needs to control the `shop` value and get a victim to visit the crafted install URL — no credentials or elevated privileges required. Cost is trivial (a single crafted link).

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, validate `shop` with `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` at the top of `begin_auth` (and use the sanitized/returned trusted host in `auth_base_uri`) so that any non-Shopify-domain `shop` value raises `Errors::InvalidShopError` before any URL/query is constructed, rather than silently building a redirect to an arbitrary host.

### Proof of Concept
```ruby
# test/auth/oauth_test.rb (new test)
def test_begin_auth_rejects_unsanitized_shop_host
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret",
    scope: ["read_orders"], host_name: "app-host.com", api_version: "2024-01")

  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example.com", redirect_path: "/callback")
  end
end

def test_begin_auth_auth_route_host_is_always_trusted
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret",
    scope: ["read_orders"], host_name: "app-host.com", api_version: "2024-01")

  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "real-shop.myshopify.com", redirect_path: "/callback")
  host = URI.parse(result[:auth_route]).host
  assert ShopifyAPI::Utils::ShopValidator.sanitize_shop_domain(host), "host must be a trusted Shopify domain"
end
```
Current code fails the first assertion (no exception raised; `auth_route` host equals `attacker.example.com`), demonstrating the broken binding.

          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

        end

  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    head 307

  end
