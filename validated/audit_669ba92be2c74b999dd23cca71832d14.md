## Analysis

The `WrappedHyperFungibleToken` contract on the home chain locks the underlying ERC20 and encodes the caller-supplied `params.amount` into the cross-chain message, which is then minted 1:1 on the destination `HyperFungibleToken` deployment. The contract never verifies that the amount it actually received from `safeTransferFrom` matches the amount it commits to the message, unlike `IntentGatewayV2`, which explicitly measures balance-before/balance-after around every ERC20 pull specifically to guard against this class of bug (see the `DustCollected` / actual-received handling in `IntentGatewayV2.sol`).

### Title
Unbacked cross-chain mint from `WrappedHyperFungibleToken.send()` failing to account for fee-on-transfer / rebasing underlying tokens - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks `params.amount` of the configured `_underlying` token via `safeTransferFrom`, but always encodes the requested `params.amount` — not the actual amount received — into the `Message` dispatched cross-chain. If `_underlying` is a fee-on-transfer token (e.g. PAXG) or a rebasing/balance-adjusting token (e.g. stETH), the wrapper's actual escrowed balance will be less than `params.amount`, yet the peer `HyperFungibleToken` on the destination chain mints the full, uncorrected `params.amount`, producing unbacked supply on the destination chain.

### Finding Description
In `send()`: [1](#0-0) 

the underlying token is pulled with `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and the `DispatchPost` body is built from `_buildDispatchPost(params)`: [2](#0-1) 

which encodes `amount: params.amount` verbatim, with no check of the wrapper's balance before/after the transfer. On the destination chain, `HyperFungibleToken.onAccept` mints exactly `message.amount` to the beneficiary: [3](#0-2) 

This is the same root cause identified in the reference report (StakingToken.sol's `deposit`/`_withdraw`): the amount actually transferred is assumed equal to the amount requested, with no reconciliation. The codebase's own `IntentGatewayV2.placeOrder` demonstrates the correct pattern is already known internally — it measures `balanceOf` before and after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual received value before committing/escrowing: [4](#0-3) 

`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` do not apply this same correction anywhere in `send()`.

The same asymmetric-amount issue also affects `onAccept`/`onPostRequestTimeout`, which unlock/refund exactly `message.amount` of `_underlying` via `safeTransfer`: [5](#0-4) 
If the wrapper's actual escrowed balance is less than the sum of outstanding `message.amount` obligations (due to the fee-on-transfer shortfall accumulated on the way in, or negative rebasing of the underlying while locked), later `onAccept`/timeout calls will revert once the pool is drained, permanently freezing redemption for the remaining bridged supply.

### Impact Explanation
Each `send()` call with a fee-on-transfer or negative-rebasing `_underlying` causes the destination `HyperFungibleToken` to mint more tokens than are actually backed by the locked escrow on the home chain. This is an unbacked mint / protocol insolvency: destination-chain circulating supply exceeds the true backing balance held by `WrappedHyperFungibleToken`. As users progressively burn-and-unlock back to the home chain, the wrapper will eventually be unable to fulfill `onAccept`/timeout unlocks for the last redeemers, since `safeTransfer(beneficiary, message.amount)` will revert against an insufficient balance — a permanent freezing of funds for those users. This satisfies "unbacked mint" and "permanent freezing of funds" impact criteria.

### Likelihood Explanation
Any deployer configuring `WrappedHyperFungibleToken` with a fee-on-transfer token (there is no on-chain restriction preventing this — `configure()` accepts an arbitrary `underlying` address) or a rebasing token like stETH will trigger this on every single `send()` call, with no special conditions or privileged access required — an ordinary bridging user's own transaction is sufficient to create the mismatch. Given the documented feature that `WrappedHyperFungibleToken` is meant to work generically for "existing ERC20 tokens", this is a realistic deployment scenario, not a contrived edge case.

### Recommendation
In `send()` (and the upgradeable counterpart), measure `_underlying`'s balance of `address(this)` before and after `safeTransferFrom`, and use the actual delta as `amount` when building and dispatching the `Message`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`. Alternatively, explicitly document and enforce (e.g., via an allow-list or a documented restriction) that `_underlying` must be a standard, non-fee-on-transfer, non-rebasing ERC20.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A with `_underlying` set to a 1% fee-on-transfer token (as modeled by `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. Deploy `HyperFungibleToken` as the peer on chain B.
3. User calls `send({amount: 1000e18, to: recipient, dest: chainB, ...})`.
4. `safeTransferFrom` pulls 1000e18 but the wrapper only receives 990e18 due to the 1% fee; `_buildDispatchPost` still encodes `amount: 1000e18`.
5. On chain B, `onAccept` mints `1000e18` to `recipient` — 10e18 more than is actually escrowed on chain A.
6. Repeat sends accumulate unbacked mint; once cumulative bridged-back burns from chain B attempt to unlock more than the 990e18-per-send actually held, `onAccept`'s `safeTransfer` on chain A reverts, freezing the last redeemer's funds. [1](#0-0) [6](#0-5)

            dest: params.dest,
            to: dest,

            timeout: params.timeout,
