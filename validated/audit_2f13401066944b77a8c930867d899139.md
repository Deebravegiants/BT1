### Title
Inconsistent internal escrow balances for fee-on-transfer/deflationary tokens in Tron `IntentGatewayV2.placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the escrow ledger `_orders[commitment][token]` with the requested/reduced input amount without verifying that the same amount was actually received via `safeTransferFrom`, unlike the already-fixed EVM mainline `IntentGatewayV2.sol`, which snapshots balances before/after the transfer and mutates `order.inputs` to the actual received amount before computing fees and the commitment.

### Finding Description
In the non-predispatch branch of `placeOrder`, tokens are pulled directly from the user with no balance verification: [1](#0-0) 

```solidity
for (uint256 i; i < inputsLen;) {
    if (order.inputs[i].amount == 0) revert InvalidInput();
    address token = address(uint160(uint256(order.inputs[i].token)));
    if (token == address(0)) {
        if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
        msgValue -= order.inputs[i].amount;
    } else {
        IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
    }
    // Store reduced amount (after protocol fees) in escrow
    _orders[commitment][token] += reducedInputs[i].amount;
    ...
}
``` [2](#0-1) 

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the user-specified amount) minus the protocol fee — it is never reconciled against the actual token balance change on the contract. If `token` is a fee-on-transfer, deflationary, or rebasing ERC20, `safeTransferFrom` delivers less than `order.inputs[i].amount` to the gateway, yet the ledger `_orders[commitment][token]` is credited as if the full (reduced) amount arrived. This is exactly the `LibTransfer.receiveToken` bug class described in the external report: state accounting assumes `amount transferred == amount received`.

By contrast, the canonical EVM `IntentGatewayV2.sol` already fixes this by snapshotting `balanceOf` before/after every `safeTransferFrom` and mutating `order.inputs[i].amount` to the measured delta before computing fees/commitment/escrow: [3](#0-2) 

and this is explicitly validated with `FeeOnTransferToken` tests: [4](#0-3) 

The Tron contract's `placeOrder` (both the non-predispatch path above and the predispatch sweep at lines 416-446, which credits `reducedInputs[i].amount` regardless of the swept `balance`) never received this fix, so escrow accounting there can diverge permanently from actual token holdings.

### Impact Explanation
Because `_orders[commitment][token]` (and the commitment hash used for cross-chain settlement/withdrawal) reflect a higher balance than what the contract actually holds for such tokens, any downstream `withdraw`/`cancelOrder`/fill flow that pays out based on the escrow ledger will attempt to transfer more tokens than the contract possesses. This causes either reverting withdrawals (permanent freezing of legitimately owed funds for the order's counterparty) or, in a shared-liquidity escrow model, insolvency that lets earlier withdrawers drain funds that back other users' orders, at the expense of later claimants who cannot be paid in full. This matches the report's "concrete... permanent freezing of funds" impact class for an unprivileged single-transaction interaction (placing an order with a fee-on-transfer token).

### Likelihood Explanation
Any unprivileged user can trigger this by calling `placeOrder` with a fee-on-transfer, deflationary, or rebasing ERC20 as an input token — no special privileges, governance, or admin actions are required, and the whitelisting of intent-input tokens is up to the deployer/solver ecosystem, not necessarily restricted to "safe" tokens. This mirrors the same class of tokens (fee-on-transfer/deflationary) already acknowledged and fixed in the sibling EVM contract and covered by dedicated tests, confirming the project itself treats this token class as in-scope/reachable.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: snapshot `token.balanceOf(address(this))` (or `dispatcher`) before each `safeTransferFrom`/sweep, compute the actual received delta, and use that measured amount (not the user-specified `order.inputs[i].amount`) for `reducedInputs`, the commitment, and the `_orders[commitment][token]` escrow accounting, for both the non-predispatch (lines 451-468) and predispatch (lines 416-446) code paths.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) analogous to the `FeeOnTransferToken` test contract already used to validate the fix on the EVM side.
2. Call `IntentGatewayV2(tron).placeOrder(order, graffiti)` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` actually delivers only `990e18` to the gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol:459`), but `_orders[commitment][token] += reducedInputs[i].amount` credits `1000e18` (minus any protocol fee) `evm/tron/contracts/apps/IntentGatewayV2.sol:463`.
4. When the order is later cancelled/withdrawn (`cancelOrder` → `withdraw`), the contract attempts to pay out the escrowed (overstated) amount, exceeding its actual `FOT` balance — causing reverts (frozen funds) or depleting balances backing other orders.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
