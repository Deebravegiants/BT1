### Title
`rootHashHinkalIndex` is unconstrained by the ZK proof, `calldataHash`, and `signedMessageHash` — ([File: contracts/Hinkal.sol])

### Summary
This is a plausible but unproven analog to the reported `GetIdsOfActiveTopics` bug class ("a `CircomData` field acted on but outside `calldataHash` / `signedMessageHash` / the public-input vector"). `CircomData.rootHashHinkalIndex` is used in a security-critical check (`rootHashExists`) in `Hinkal.transact` but is never included in the values hashed into `calldataHash` (`CircomDataBuilder.getHashedCalldata1/2`), never included in `getSignedMessageHash`, and never passed as a circuit public input (`formBasicInput` / `formInputEmporiumMin`). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`Hinkal.transact` validates the root with:
```solidity
require(
    rootHashExists(circomData.rootHashHinkal, circomData.rootHashHinkalIndex),
    "Hinkal Root Hash is Incorrect"
);
``` [1](#0-0) 

`rootHashExists` checks `roots[_rootIndex] == _root` and bounds `_rootIndex` between `MINIMUM_INDEX` and `m_index`: [5](#0-4) 

The value `circomData.rootHashHinkal` (the root itself) is bound to the user's signature via `getSignedMessageHash` and to `calldataHash` via `getHashedCalldata1`, but `rootHashHinkalIndex` is not present in either hash computation, nor in the circuit's public inputs formed in `formBasicInput`/`formInputEmporiumMin`. Since `originalSender` can be zero and `relay` non-zero (i.e., a relay submits the transaction on behalf of a user who only signs an off-chain message), the relay has full unauthorised discretion to choose `rootHashHinkalIndex` at call time.

### Impact Explanation
In practice this is not concretely exploitable given the code seen: `roots` is populated by `Merkle.insert`/`insertMany` using Poseidon hashing that is effectively collision-resistant, and `m_index` is strictly increasing per transaction, so no two distinct indices are expected to store the same non-zero root value. Changing `rootHashHinkalIndex` without also matching the exact root value already committed to by the user's signature (`rootHashHinkal`) would simply cause `rootHashExists` to return `false`, reverting the transaction rather than allowing an unauthorised state change. I could not identify a path where the relay's freedom to pick `rootHashHinkalIndex` breaks the balance/nullifier/root equalities that the report's bug class targets (double-spend, unbacked minting, freezing, or proof/nullifier bypass).

### Likelihood Explanation
Low/unproven. The field is genuinely outside every integrity-hash and public-input mechanism, matching the literal shape of the reported bug class, but no concrete break of an equality (root/leaf pair the tree never produced, reusable nullifier, unauthorised transferFrom, etc.) was demonstrated with the code available. I was not able to fully trace `insertMany`'s behavior for intermediate indices within a batch (only the final index in a batch gets a `roots[]` entry written; earlier indices in the same batch default to `0`), which could theoretically matter if a stale/mid-batch root value could ever collide with a later index — but I found no mechanism producing that collision, and pursuing it further would require code/tests outside what I could verify in this session.

### Recommendation
No concrete fix is offered here since no exploit was proven. If pursued, the CircomDataBuilder hash functions and public-input builder should explicitly include `rootHashHinkalIndex` so that the exact `(root, index)` pair is bound to the user's authorization and the circuit's public inputs, removing the relay's discretion over that field entirely.

### Proof of Concept
Not provided — no concrete state transition was found where an attacker/relay choosing an alternate `rootHashHinkalIndex` for a fixed, signature-bound `rootHashHinkal` value passes `rootHashExists` while producing an outcome the user/prover did not authorize. This finding is reported as an unresolved, low-confidence structural observation rather than a validated vulnerability.

    function rootHashExists(
        uint256 _root,
        uint256 _rootIndex
    ) public view returns (bool) {
        if (m_index == MINIMUM_INDEX) {
            return _root == 0;
        }
        if (_rootIndex < MINIMUM_INDEX || _rootIndex >= m_index) {
            return false;
        }
        return _root != 0 && roots[_rootIndex] == _root;
    }
