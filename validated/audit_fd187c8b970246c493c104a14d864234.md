### Title
Withdrawal status matched only by `assetId` misreports destination and transaction hash for batch withdrawals sharing the same asset - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal (identified by `index` + `destinationAddress` + `amount`) by matching the POA Bridge's unsorted withdrawal list using **only `assetId`** (via `near_token_id`/`defuse_asset_identifier`), never the destination address or amount. When a single NEAR intent transaction contains multiple withdrawals of the same asset to different destination addresses (a legitimate batch-withdrawal use case explicitly supported by `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`, see `docs/design/rfc-batch-withdrawal-granular-control.md`), this lookup returns the wrong withdrawal's status/txHash for the requested index.

### Finding Description
`describeWithdrawal` fetches all withdrawals for a NEAR tx hash and finds the "matching" entry: [1](#0-0) 

The code comment explicitly states the matching strategy: "Response list is unsorted, so we match by assetId instead of index" [2](#0-1) . This is confirmed by the existing test `"matches withdrawal by assetId, not by index"` [3](#0-2) , which only exercises the case of *different* assetIds at different indices — it never covers the case where two withdrawal legs of the same batch share the **same** `assetId` but different `destinationAddress`/`amount`.

`WithdrawalIdentifier` carries `index`, `withdrawalParams` (which includes `destinationAddress` and `amount`), and `tx`, but none of `destinationAddress` or `amount` participate in the match key — only `assetId` does. The same pattern exists in `waitForWithdrawalCompletion`'s `WithdrawalCriteria`, which is typed as `{ assetId: string }` only: [4](#0-3) , and the "matches withdrawal by criteria when multiple withdrawals exist" test only exercises different assets, never same-asset/different-destination legs: [5](#0-4) .

The RFC that motivated granular batch tracking explicitly assumes "Index correspondence: Array index of returned promise matches array index of input `withdrawalParams`" [6](#0-5)  and the SDK README documents the same per-index guarantee for `createWithdrawalCompletionPromises` [7](#0-6) . This guarantee is broken by the asset-only matching: if a batch withdrawal sends the same token to two different addresses (e.g., `100 USDC` to address A and `50 USDC` to address B in one intent), `findMatchingWithdrawal` will return the same (first-found) entry for both `index` calls, so `promises[i]` can resolve with the `transfer_tx_hash`/status belonging to the *other* leg's destination.

### Impact Explanation
This breaks the equality "a status reported that is not the on-chain outcome" for the queried withdrawal identity (index/destination). An integrator using `sdk.createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` to track per-recipient completion of a batch withdrawal can be told that withdrawal to address B "completed" with the transaction hash that actually paid address A (or vice versa). Per the report's High-severity criteria ("a status or hash misreport making an integrator credit or refund twice"), an integrator crediting an off-chain ledger or releasing goods/service based on the reported `txHash`/`completed` status for a specific destination could credit/refund the wrong leg or double-credit, since both indices can resolve to the same tx hash while only one destination actually received funds.

### Likelihood Explanation
This requires no malicious actor — it triggers on the legitimate, SDK-documented batch-withdrawal flow whenever two withdrawal legs in the same intent share an `assetId` but differ in `destinationAddress`/`amount`. Given the SDK explicitly ships `createWithdrawalCompletionPromises` for "granular" per-leg tracking (RFC feature), same-asset multi-destination batches are a foreseeable normal use case, not a contrived edge case.

### Recommendation
Extend `findMatchingWithdrawal` (and `WithdrawalCriteria`) to disambiguate withdrawals by destination address (and amount, if the POA Bridge API doesn't guarantee direct comparability) in addition to `assetId`, so each `index`/`WithdrawalIdentifier` maps deterministically to its own on-chain withdrawal record rather than the first same-asset entry found.

### Proof of Concept
1. Submit a batch withdrawal intent from NEAR that sends `100 nep141:usdc.token.near` to `address A` (index 0) and `50 nep141:usdc.token.near` to `address B` (index 1) in the same tx.
2. POA Bridge processes and completes B first with `transfer_tx_hash: "hashB"`, while A is still `PENDING`.
3. Call `bridge.describeWithdrawal({ index: 0, withdrawalParams: { assetId: "nep141:usdc.token.near", destinationAddress: A, ... }, tx })`.
4. `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.token.near")` returns the first entry matching the asset — the completed B entry — so the function reports `{ status: "completed", txHash: "hashB" }` for index 0 (address A), even though A's withdrawal is still pending. [8](#0-7)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}
