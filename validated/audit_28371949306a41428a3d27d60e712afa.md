### Title
Emporium balance-diff accounting lets any user steal ERC20/ETH balances "parked" in the Emporium contract from prior transactions - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` mints an out-UTXO for a token based purely on `balancesAfter[i] - balancesBefore[i]` (adjusted by the caller's own declared `deltaAmountChanges[i]`), exactly the "collect balance-diff and mint" pattern flagged in the WildCredit report. Because the Emporium contract is a shared, persistent-balance proxy that executes arbitrary, prover-supplied calls (`op.endpoint.call{value: op.value}(op.callData)`), any residual ERC20/ETH balance or ERC20 allowance left in the Emporium contract from a previous transaction (attacker's own leftover, dust from slippage, or a not-yet-swept legitimate user residue) can be moved/converted during a completely unrelated, self-authored transaction and credited to the caller as a brand-new UTXO, even though `deltaAmountChanges` for that token never reflected an equivalent inflow from the caller.

### Finding Description
`runAction` snapshots balances before executing the EmporiumStack ops, executes attacker-controlled `op.endpoint.call(...)` operations (Case 2, "Stateless Interaction", reachable whenever `stack.signerAddress == address(0)` or `op.invokeWallet` is false), then computes: [1](#0-0) 

`handleOut` mints and immediately transfers out a UTXO worth `balanceChange` whenever it is positive: [2](#0-1) 

The code comment itself acknowledges the Emporium contract's balance is *not* zeroed between transactions ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call"), i.e. the Emporium is designed to be able to carry over token balances/allowances across separate `transact()` calls. Because `stack.ops` (arbitrary `endpoint`/`callData`/`value`) are fully attacker-chosen and merely committed into `calldataHash` (not otherwise constrained), an attacker's own valid proof can include an operation that:
1. Calls a token/router contract *as* the Emporium (msg.sender == Emporium), using any residual balance or leftover approval already sitting in the Emporium (e.g. from dust left by a prior swap, a not-yet-collected output, or another user's not-yet-withdrawn residual), and
2. Converts/moves that value into a token/address the attacker declares in `circomData.erc20TokenAddresses`.

Since `balanceChange` is computed purely from `balancesBefore`/`balancesAfter` and the caller's own `deltaAmountChanges` (which the attacker sets to `0` for the targeted output token — they never declared depositing anything for it), the resulting positive `balanceChange` is entirely attributable to funds that belonged to the Emporium's carried-over state, not to the attacker's own shielded deposit. `handleOut` nonetheless mints a fresh UTXO of that full amount to the attacker and physically transfers the tokens to `msg.sender` (Hinkal), which then credits the attacker's stealth address.

This exactly mirrors the WildCredit finding's root cause: a "collect and mint" function that lets a caller convert into new attributed value which was not accrued/verified against the caller's own contribution, using a pool of value ("parked liquidity"/leftover balance) that the accounting equation does not properly isolate per-caller.

The equality broken: `UTXO minted to caller == value the caller's own deltaAmountChanges actually moved in this transaction`. Here, `UTXO minted > 0` while the corresponding `deltaAmountChanges[i] == 0`, meaning value not contributed by the caller (residual Emporium balance/allowance) is captured and shielded under the attacker's stealth address.

### Impact Explanation
This is theft of protocol/user funds "parked" in the Emporium contract — funds that are not the attacker's own shielded balance. It maps to the High/Critical bucket: "theft or permanent freezing of protocol/relay fees" and effectively "unauthorised asset movement" out of the Emporium's carried-over balance, since the tokens transferred out never correspond to the attacker's declared `amountChanges`/nullifier spend. Any dust, un-swept output, or left-over allowance sitting in the Emporium contract between transactions is a target, and the amount stolen scales with whatever is parked there at the time (including from the attacker's own prior slippage/leftover, effectively "double-dipping" the same residual repeatedly if it reappears).

### Likelihood Explanation
Likelihood depends on the Emporium contract actually holding non-zero balances/allowances between transactions, which the contract's own comments concede is expected/possible ("the only case when balanceChange can be < 0 ... when there were some funds on emporium before the call"). Any swap/DeFi interaction leaving rounding dust, a partially-executed multi-step operation, or a legitimate user's un-collected leftover (analogous to Uniswap's `tokensOwed0/1` in the original report) creates exploitable residue. No admin/relayer/oracle assumption is needed — a normal unprivileged EOA constructing their own valid `transact()` proof with a self-chosen `EmporiumStack` can trigger this.

### Recommendation
- Do not rely purely on a before/after balance snapshot of a shared, persistent-balance contract to mint new UTXOs; the Emporium should not be allowed to retain a positive balance/allowance between transactions for tokens declared in `circomData.erc20TokenAddresses`.
- Sweep/zero out (or explicitly attribute) any pre-existing balance for each token before starting, e.g., require `balancesBefore[i] == 0` for tokens not currently tracked as "owned" by some pending UTXO, or fold any pre-existing balance into the depositor's own accounting instead of allowing it to be claimed by a later, unrelated caller.
- Alternatively, require that all approvals granted to routers/endpoints during ops be revoked (approve back to 0) at the end of `runAction`, and reject any op whose net effect leaves a non-zero balance in a token not included in the current `circomData.erc20TokenAddresses` set, closing the "parked value" window the WildCredit-style attack depends on.

### Proof of Concept
1. In one transaction (T1), a legitimate user's swap through Emporium leaves a small residual balance of `TOKEN_X` in the Emporium contract (rounding dust from a router swap, or a call the ops sequence didn't fully sweep) and/or a non-revoked `approve(router, MAX)` allowance from Emporium to a router.
2. Attacker submits their own `transact()` call to `Hinkal.transact` with a valid proof for their own (possibly zero) shielded inputs, setting `circomData.erc20TokenAddresses = [TOKEN_Y]`, `amountChanges[TOKEN_Y] = 0` (i.e., no declared deposit), and an `EmporiumStack.ops` entry: `op.endpoint = router`, `op.callData = swapExactTokensForTokens(residual_TOKEN_X_amount, 0, [TOKEN_X, TOKEN_Y], emporium, deadline)`.
3. Since `op.endpoint.call(...)` executes with `msg.sender == Emporium`, the router pulls `TOKEN_X` from Emporium's own balance (using the pre-existing allowance) and deposits the swapped `TOKEN_Y` back into Emporium.
4. `EmporiumUpgradeable.runAction` computes `balanceChange[TOKEN_Y] = balancesAfter - balancesBefore > 0` while `deltaAmountChanges[TOKEN_Y] == 0`; `handleOut` mints and transfers this full amount to the attacker's stealth address as a new UTXO — value the attacker never deposited.

Note: I could not find any additional runtime guard in `ExternalActionBaseUpgradeable`/`ExternalActionBaseV2` (only reachable via `grep_search`, not fully read) that restricts `op.endpoint` to a fixed allow-list of contracts/functions; based on the code read, the only restriction on Case 2 ops is blocking the `callHinkalWallet`/`doSendToRelay` selectors. If such a restriction exists elsewhere that I did not view, it would need to be confirmed before treating this PoC as fully unconstrained.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
