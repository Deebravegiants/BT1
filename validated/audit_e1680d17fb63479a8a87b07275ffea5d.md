### Title
Webhook shop/topic/webhook_id identity not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from only the raw request body [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by the handler are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over the body and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . The binding broken is: **bytes verified (raw body) ≠ identity acted on (shop-domain header)**.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it against the `hmac` field using `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) ; the `shop`, `topic`, `webhook_id`, and `api_version` fields are parsed straight out of the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the HMAC at all [2](#0-1) .

`Registry.process` uses the HMAC check purely as a body-authenticity gate, then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` header values straight into `WebhookMetadata`, which is the object the app's own `WebhookHandler#handle` uses to select the correct merchant/tenant to act on [3](#0-2) . The gem's own documentation states this `process` call "will verify the request did indeed come from Shopify" [5](#0-4)  and that host apps are expected to key their business logic (e.g. `shop_domain: data.shop`) directly off `data.shop` [6](#0-5) , i.e. the gem's documented contract explicitly encourages trusting `shop` as an authenticated tenant identifier, which it is not.

Since HMAC-SHA256 over the body is not a MAC over `(shop, topic, webhook_id, body)`, any attacker who is able to obtain one valid `(raw_body, hmac)` pair signed with the app's `client_secret`/webhook signing secret — most straightforwardly by owning/controlling a legitimate trial shop that has this app installed and receives real webhooks for that body — can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`, `x-shopify-webhook-id`) for a victim shop's domain. `Request.new` performs no cross-validation between the header values and the signed body [7](#0-6) , and `HmacValidator.validate` will accept the forged request because the body bytes it verifies are unchanged [8](#0-7) .

### Impact Explanation
This is a cross-tenant identity confusion: the app processes attacker-supplied data (a webhook the attacker legitimately triggered on their own store) but the handler is told, with an apparently-valid HMAC, that it originated from a different (victim) shop. Any host application that follows the gem's documented pattern of keying downstream side effects (queued jobs, database writes, cache invalidation, order/customer sync) off `data.shop` can be tricked into applying attacker-controlled webhook payloads under the victim shop's tenant context — a cross-tenant access/data-integrity issue.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a merchant/developer with their own store that has the target app installed (an ordinary, unprivileged install available to any internet user through the App Store or a dev store), so they can trigger a real, validly-signed webhook for arbitrary content they choose (e.g. via `products/update`), and (2) the ability to POST an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which requires no secret at all. No access token, `client_secret`, or victim credentials are needed.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` fields into the HMAC-verified signable content (e.g. by having `Webhooks::Request#to_signable_string` incorporate these header values, or by independently verifying that the `shop` header corresponds to a shop with a currently-registered webhook subscription for that exact `webhook_id`/topic before dispatching to the handler), and document clearly that `data.shop` is not itself HMAC-covered so host apps do not treat it as an authenticated tenant key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a real webhook, e.g. `products/update`, capturing the raw body `B` and its valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's shared secret).
2. Attacker crafts an HTTP POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since only body bytes are signed)
   - Header `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - Header `x-shopify-topic: products/update`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully since all required headers are present [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` and matches `H` — validation passes [9](#0-8) .
5. The handler is invoked with `WebhookMetadata.new(topic: "products/update", shop: "victim.myshopify.com", body: parsed(B), ...)` [10](#0-9) , causing the host app to act as if `victim.myshopify.com` sent this attacker-chosen payload.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
