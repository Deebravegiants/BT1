### Title
Webhook HMAC verification does not bind `shop`, `topic`, or `webhook_id` headers, allowing cross-tenant/topic webhook spoofing via signature replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . However, `Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from unauthenticated HTTP headers (`shop-domain`, `topic`, `webhook-id`) — to dispatch to the handler and construct `WebhookMetadata` [3](#0-2) . None of these header values are included in the HMAC-signed payload.

### Finding Description
The identity binding that should hold is: `shop/topic/webhook_id used by the handler == shop/topic/webhook_id authenticated by the HMAC`. In this implementation that equality does not hold, because the HMAC only authenticates `@raw_body` [4](#0-3) [1](#0-0) , while `shop`, `topic`, `webhook-id`, and `api-version` are read straight from headers with no cryptographic linkage to the HMAC computation [5](#0-4) .

Because the app's `client_secret` (used to sign webhooks) is shared across every shop that has the app installed, any merchant who installs the app can legitimately trigger a webhook delivery to their own endpoint and obtain a validly-signed `(raw_body, hmac)` pair for a known topic/body combination. Since the headers are not part of the signed content, that same `(raw_body, hmac)` pair remains valid when replayed with a different `shop-domain`, `topic`, or `webhook-id` header value. `Registry.process` will accept it via `Utils::HmacValidator.validate(request)` succeeding [6](#0-5) , then hand the forged `shop`/`topic`/`webhook_id` straight to the registered handler [7](#0-6) .

### Impact Explanation
An app that keys any tenant-scoped logic (e.g., cache invalidation, per-shop state transitions, uninstall/GDPR cleanup, billing state) off `WebhookMetadata#shop` or `#topic` without independently re-verifying the shop against its own session store can be tricked into acting on behalf of a shop it did not actually receive the event for, or under a different topic than actually occurred — a cross-tenant identity confusion rooted in this gem's webhook verification primitive.

### Likelihood Explanation
Exploitation requires only that the attacker be a shop owner who has installed the target app (an unprivileged, non-credentialed capability relative to the app's `client_secret`) so they can harvest one valid `(raw_body, hmac)` pair from their own shop's webhook deliveries, then replay it with altered headers toward the app's webhook endpoint. No access to `api_secret_key`, tokens, or TLS interception is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signed content, or have `Registry.process` cross-check the header-derived `shop`/`topic` against values embedded in and covered by the verified body/signature before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `carts/update` with body `{}`), capturing the legitimately signed `x-shopify-hmac-sha256` value Shopify computed over that body.
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `{}` and the captured HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: app/uninstalled`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the HMAC [2](#0-1) .
4. `Registry.process` dispatches to the handler registered for the spoofed topic with `shop: "victim-shop.myshopify.com"`, causing the app to act as though it received that event for a shop/topic it did not [8](#0-7) .
