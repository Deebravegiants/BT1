### Title
Chainlink oracle circuit-breaker (`minAnswer`/`maxAnswer`) not checked in `SimplexPaymaster` price fetch, allowing stale/incorrect gas-fee pricing during asset crashes - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` only validates that a Chainlink answer is positive and not stale; it never checks the answer against the aggregator's `minAnswer`/`maxAnswer` circuit-breaker bounds. [1](#0-0) 

### Finding Description
`_getOraclePrice` fetches `latestRoundData()` and reverts only on `answer <= 0` or when `block.timestamp - updatedAt > maxOracleAge`: [2](#0-1) 

Chainlink aggregators clamp reported answers to a configured `[minAnswer, maxAnswer]` band; if the underlying asset's real price falls outside that band (e.g. a depeg or crash, as happened to LUNA on Venus), `latestRoundData()` keeps returning the clamped bound value with a *fresh* `updatedAt` timestamp. Because the timestamp is current, `_getOraclePrice`'s staleness check passes and the clamped, economically-wrong price is treated as valid.

This clamped price feeds directly into `_tokenPrice`, which computes the gas-fee exchange rate between the native asset and each registered ERC-20 fee token: [3](#0-2) 

`_tokenPrice` is invoked from `_fetchDetails`, which the ERC-4337 `EntryPoint` calls during `_validatePaymasterUserOp` for **every UserOperation** — i.e. any unprivileged bandwidth purchaser paying gas through this paymaster reaches this code path with a single UserOp: [4](#0-3) 

The same unchecked price also drives `swapAndDeposit`'s minimum-output calculation for recycling collected fees through a Uniswap V2 swap: [5](#0-4) 

### Impact Explanation
If the native-asset oracle (e.g. BNB/USD) hits its `minAnswer` floor during a crash, `nativeUsd` is reported far *above* the real market price, causing `_tokenPrice` to overcharge every user paying gas in ERC-20 tokens for that block window — a direct value extraction from unprivileged bandwidth purchasers on every UserOp processed while the clamp is active. Conversely, if a registered fee token's oracle hits its floor while the token's real value has collapsed further, `tokenUsd` stays overstated, causing the paymaster to *undercharge* — draining the paymaster's treasury/EntryPoint deposit over the volume of UserOps processed, a protocol-level fund loss. `swapAndDeposit`'s slippage-protected minimum-output would likewise be computed from the wrong price, letting fee-recycling swaps execute at an incorrect rate. Both directions are a concrete loss of funds (theft from users or theft from the treasury), satisfying at least Medium severity.

### Likelihood Explanation
This only triggers when an underlying Chainlink feed's real price moves outside its configured `minAnswer`/`maxAnswer` band — a rare but historically observed event (LUNA/UST, and other depeg/crash events) for volatile assets or during a black-swan event on the native gas asset. Given `SimplexPaymaster` is designed to support "any token with a Chainlink feed" including volatile ERC-20s per its own documentation, and every UserOp routed through it hits the vulnerable path unconditionally, likelihood is non-negligible for the lifetime of a deployment, though it depends on an external market event rather than attacker-controlled input.

### Recommendation
In `_getOraclePrice`, additionally fetch and enforce the aggregator's configured bounds (or a governance-configured min/max sanity band per oracle) and revert (e.g. `InvalidOraclePrice`) when `answer` equals or is outside those bounds, in addition to the existing staleness and positivity checks, mirroring the `minPrice`/`maxPrice` recommendation from the referenced report.

### Proof of Concept
1. Deploy `SimplexPaymaster` with a native-asset Chainlink feed whose aggregator has `minAnswer = X`.
2. Simulate a market crash where the true price falls below `X`; the aggregator continues returning `answer = X` with `updatedAt = block.timestamp` (this is standard Chainlink aggregator behavior, reproducible with a mock oracle as in `MockOracle` in `evm/tests/foundry/SimplexPaymasterTest.t.sol`, lines 34-57, by fixing `answer` at the clamp value while calling `setUpdatedAt(block.timestamp)` each block).
3. Any user submits a UserOperation using this paymaster with an ERC-20 fee token; `_validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the stale-but-fresh clamped price without reverting.
4. The user is charged (or the paymaster is drained) at the clamped price instead of the true market price, with no revert or safeguard triggered.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
