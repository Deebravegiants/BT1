### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, enabling cross-tenant webhook shop-spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `Registry.process` accepts the request as valid once the body's HMAC checks out, then hands the header-derived `shop` value straight to the app's webhook handler as the tenant identifier — exactly the "field acted on but not covered by the HMAC" binding break described in the analog bug class.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all pulled independently from headers, none of which participate in the signature computed above: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then constructs `WebhookMetadata` using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` header values and dispatches it to the app's handler as the trusted tenant identity: [4](#0-3) 

The documented contract for handler implementers explicitly instructs them to trust `data.shop` as "The shop domain of the webhook": [5](#0-4) 

The identity binding broken is:
`HMAC-verified(bytes) == raw_body` **but** `attributed_tenant = header["shop-domain"]`, with no cryptographic link between the two. Because `Context.api_secret_key` is a single app-wide secret (not per-shop), any merchant who installs the app receives real webhooks with valid HMACs computed with that same shared secret. Such a merchant (an "unprivileged internet user" relative to any other tenant) can capture one legitimate `(raw_body, hmac)` pair from their own shop's webhook delivery, then replay it directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body bytes against the shared secret, and `Registry.process` forwards the spoofed `shop` value to the handler unchallenged.

### Impact Explanation
This allows one tenant to inject arbitrary attacker-controlled webhook payloads that the host application will process as belonging to a different, victim tenant (cross-tenant data confusion), since the gem's own documented contract instructs handlers to trust `data.shop`. This matches the Critical "cross-tenant access" impact category: an attacker can cause the host app to write/act on data under another merchant's identity using only their own legitimately-issued webhook traffic, without any of the victim's credentials.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple merchant shops: an attacker only needs to install the app on their own store (a normal, unprivileged action) to receive a genuinely-signed webhook, then replay it with a modified `shop-domain` header via a simple HTTP client. No access to `api_secret_key`, access tokens, or victim credentials is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-verified material, or otherwise cryptographically tie the header-derived shop to the verified body — e.g., require the caller to separately confirm the `shop` header matches a shop with a known, previously-stored session/webhook registration before treating the payload as authenticated for that shop, or require Shopify's newer verification headers that bind shop identity to the signature. At minimum, document prominently that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be used as the sole tenant-attribution key without additional server-side verification (e.g. cross-checking against the shop present in a Shopify Admin API call for that resource, or validating that the shop has a currently-registered webhook subscription with that specific `webhook_id`).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggers an event, and captures the raw POST body plus its valid `X-Shopify-Hmac-Sha256` header sent by Shopify (computed with the app's single, shared `api_secret_key`).
2. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared secret (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), and the host app — per the gem's documented contract — processes attacker-controlled data as if it originated from the victim shop.
