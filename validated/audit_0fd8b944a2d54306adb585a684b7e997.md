### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the registry uses to route and attribute the webhook are all pulled from unauthenticated HTTP headers. This breaks the binding `hmac-verified bytes == data acted upon`, allowing an attacker who has captured any single valid `(raw_body, hmac)` pair (e.g., from their own tenant's legitimate webhook deliveries, which any merchant/unprivileged internet user installing the app can obtain) to replay it against the same public webhook endpoint with a forged `shop-domain` header, causing the host application's handler to process/attribute that payload to a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-reachable headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the raw body) against the `hmac` header: [3](#0-2) 

`Registry.process` trusts this validation and then forwards the unsigned `request.shop`, `request.topic`, and `request.webhook_id` straight to the host application's handler as the tenant-identifying metadata: [4](#0-3) 

Because the equality that should hold is `hmac-authenticated bytes == bytes the handler acts on for tenant routing`, and here the HMAC only covers the body while `shop`/`topic`/`webhook_id` are excluded, any request whose body+HMAC pair is valid for *some* shop (trivially obtainable by any merchant who installs the app and receives their own legitimate webhook) can be replayed with a different `shop-domain`/`topic`/`webhook-id` header combination and will still pass `Utils::HmacValidator.validate`, since it never inspects those headers.

### Impact Explanation
This crosses a tenant boundary: a webhook payload can be attributed to a shop other than the one Shopify actually delivered it for. Any host application whose webhook handler uses `WebhookMetadata#shop` to key merchant records (the standard, documented usage pattern) can have another tenant's data corrupted or falsely triggered actions (e.g., a captured `app/uninstalled` or `orders/create` body replayed against a different `shop` value), which is a cross-tenant access/data-integrity impact.

### Likelihood Explanation
Exploitation requires only a single legitimate `(body, hmac)` pair, which is trivially available to any merchant who installs the app (an unprivileged actor with respect to other tenants) since they receive genuinely signed webhooks for their own shop. No access to `api_secret_key`, access tokens, or privileged accounts is needed — only the ability to POST directly to the app's public webhook endpoint with modified headers, which is the documented, internet-reachable entry point for this feature.

### Recommendation
Include the identity-binding headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable content (or otherwise cryptographically bind them to the verified body) inside `Webhooks::Request#to_signable_string`, so `Utils::HmacValidator.validate` fails whenever any of these fields is altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid for secret `S`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the same `B`/`H` pair to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `B` only and matches `H` — validation succeeds.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches it to the handler, which the host app has no way to detect is not a real webhook for `victim.myshopify.com`.
