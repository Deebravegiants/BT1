### Title
Fee-on-transfer input tokens cause escrow over-crediting in Tron `IntentGatewayV2.placeOrder` (direct-transfer path) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron deployment of `IntentGatewayV2.sol`, the direct-transfer branch of `placeOrder` (used whenever an order has no predispatch call) credits the escrow ledger `_orders[commitment][token]` with the user-*specified* input amount (minus protocol fee), instead of the amount the contract actually received via `safeTransferFrom`. If the input token charges a transfer fee (fee-on-transfer / deflationary ERC20), the contract's real balance is lower than what is recorded in escrow, producing an unbacked escrow credit.

### Finding Description
`placeOrder` computes `reducedInputs[i].amount` from the nominal `order.inputs[i].amount` (reduced only by the protocol fee), and in the non-predispatch branch simply does: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }

        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

Unlike the predispatch branch just above it — which measures `balance` on the dispatcher/gateway before crediting escrow and emits `DustCollected` for any shortfall/excess ( [2](#0-1) ) — this direct-transfer branch performs no balance check. `reducedInputs[i].amount` is derived purely from the caller-supplied `order.inputs[i].amount` (see the fee-deduction loop at [3](#0-2) ), so for a fee-on-transfer input token the amount credited to `_orders[commitment][token]` exceeds the tokens the contract actually holds.

This is precisely the bug class described in the external report (fee-on-transfer tokens causing accounting to diverge from actual received balance), and the project's own EVM mainline contract (`evm/src/apps/IntentGatewayV2.sol`) already fixes this exact issue by snapshotting `balanceOf(address(this))` before and after `safeTransferFrom` and using the delta to set `order.inputs[i].amount` [4](#0-3) , with dedicated fee-on-transfer regression tests [5](#0-4) . The Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated to include this same balance-delta measurement in its non-predispatch escrow path.

### Impact Explanation
The escrow ledger for a given commitment records more tokens than the contract actually holds. Later flows that pay out of escrow (solver fill/redeem, cancellation refund) rely on `_orders[commitment][token]` as the source of truth for the amount owed. An inflated escrow balance for one order means the contract is insolvent for that token by the fee amount, which can lead to failed withdrawals for legitimate participants or, if the shortfall is drawn from the shared pool of that token's balance across orders, a race where later redeemers/fillers cannot be paid in full — a form of fund freezing/loss for other users. This is a direct on-chain accounting bug reachable by any unprivileged user calling `placeOrder` with a fee-on-transfer token as an input asset, so it meets the Medium severity bar (concrete freezing/shortfall of escrowed funds), matching the original report's class.

### Likelihood Explanation
Any user can trigger this by simply calling `placeOrder` with a deflationary/fee-on-transfer ERC20 as an input token on the Tron deployment — no special privileges or timing needed. Fee-on-transfer tokens are common enough (reflection tokens, tax tokens) that this is a realistic, low-effort trigger whenever the Tron gateway allows arbitrary ERC20 inputs (no allowlist logic was found restricting input tokens in this snippet).

### Recommendation
Apply the same fix used in the mainline EVM contract: in the non-predispatch branch, snapshot `IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, and after the transfer compute `received = balanceOf(address(this)) - balBefore`. Use `received` (not the nominal `order.inputs[i].amount`) as the basis for `reducedInputs[i].amount`/protocol-fee deduction and for the amount stored in `_orders[commitment][token]`, mirroring `evm/src/apps/IntentGatewayV2.sol` lines 312-329.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and register it as an input token type for the Tron `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, no predispatch call/assets.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; due to the 1% fee the contract actually receives only 990e18.
4. `reducedInputs[0].amount` is computed from the nominal `1000e18` (minus protocol fee if any), and `_orders[commitment][token] += reducedInputs[0].amount` credits escrow with an amount based on 1000e18, while the contract's real FOT balance is only 990e18.
5. When a solver later fills/redeems against this commitment expecting to draw the credited escrow amount, the contract lacks sufficient FOT balance to honor it in full, demonstrated analogously by the existing test `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` on the mainline contract, which would fail if run against this Tron branch's unmodified logic because escrow would not match actual received balance.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
