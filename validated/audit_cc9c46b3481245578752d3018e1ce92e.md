### Title
Webhook shop attribution (`x-shopify-shop-domain`) is not covered by the HMAC signature, allowing cross-tenant shop spoofing via webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop` value it hands to a merchant's webhook handler purely from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that is verified only covers the raw request body. This breaks the identity binding `hmac-authenticated-bytes == bytes-used-for-shop-attribution`.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the presented `hmac`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns **only** the raw body: [2](#0-1) 

But the `shop` accessor used to attribute the webhook to a tenant is read straight from the `x-shopify-shop-domain` header, which is not part of the signed material at all: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately forwards `request.shop` — the unauthenticated header — to the app's handler as the tenant identity for the event: [4](#0-3) 

Because the webhook delivery endpoint is a single shared URL for all shops installed on an app, a merchant that legitimately controls Shop A can trigger a real webhook event in their own store (a valid HMAC computed by Shopify over the real body), capture that request, and replay it to the same endpoint with the `X-Shopify-Shop-Domain` header changed to Shop B's domain. Since the HMAC only signs `@raw_body` and that body is untouched, `HmacValidator.validate` still returns `true` — yet `Registry.process` now hands the app's handler `shop: "shop-b.myshopify.com"` with Shop A's body/content. The equality the gem should guarantee, `hmac-verified bytes == bytes used to derive shop attribution`, does not hold: the HMAC covers `raw_body` only, while `shop` is taken from an independent, unauthenticated header.

### Impact Explanation
This lets an authenticated merchant of Shop A forge the tenant binding for arbitrary data delivered to the app's shared webhook endpoint, causing the app to process/attribute another shop's webhook event or apply Shop A's payload to Shop B's tenant record — a cross-tenant integrity violation in the webhook processing pipeline built into this gem's `Webhooks::Registry`/`Webhooks::Request` API. This matches the "cross-tenant access" impact category, since it defeats the shop identity binding the app relies on this gem to enforce via HMAC validation.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker must control (be a merchant of) at least one shop installed on the target app in order to generate a genuinely-signed body, and (2) they must be able to intercept/replay their own webhook delivery to the same endpoint with a modified header, which is straightforward for any actor who owns an app installation and can watch/capture their own inbound webhook traffic (no secrets, tokens, or privileged access required). This is a realistic, low-privilege abuse path rather than a theoretical one, since only ordinary "installed the app on my own shop" access is needed.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the signed material used for HMAC verification, or otherwise cryptographically bind `X-Shopify-Shop-Domain` to the verified payload before it is used for tenant attribution in `Webhooks::Registry.process`/`WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and that consuming apps must independently verify shop identity (e.g., against a known/installed-shop list) before trusting it for tenant-scoped writes.

### Proof of Concept
1. Merchant M installs the app and owns `shop-a.myshopify.com`, which is registered for topic `orders/create`.
2. M triggers a real order on Shop A; Shopify sends a webhook to the app's shared endpoint with:
   - body `B` (order payload)
   - header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` (valid)
   - header `X-Shopify-Shop-Domain: shop-a.myshopify.com`
3. M captures this request and replays it to the same endpoint, changing only:
   - header `X-Shopify-Shop-Domain: shop-b.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` is constructed; `to_signable_string` still returns `B`, so `HmacValidator.validate` succeeds (per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` calls the handler with `shop: "shop-b.myshopify.com"` even though the payload actually originated from Shop A (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the app to attribute/act on Shop A's data under Shop B's tenant.
