I found a concrete analog to the Polaris pattern: an unsigned, unauthenticated extrinsic that credits a caller-chosen "location" (an arbitrary account address) with real value, before that address has any relationship to work actually verified.

### Title
Reputation minting in `handle_get_requests` credits an attacker-chosen address instead of the address that submitted the verified work - ([File: modules/pallets/state-coprocessor/src/impls.rs])

### Summary
`StateCoprocessor::handle_unsigned` is dispatched via `ensure_none(origin)` — i.e. it is a fully unsigned, permissionless extrinsic that any relayer/dispatcher can submit — carrying a `GetRequestsWithProof { requests, source, response, address }` payload. `address` is a raw, attacker-controlled 32 bytes with no cryptographic binding to the caller, the proof, or the requests. After the state/response proofs are verified, the pallet uses `address` directly as the recipient of a reputation-token mint proportional to the verified payload size.

### Finding Description
`handle_get_requests` in [1](#0-0)  destructures `address` straight out of the caller-supplied, unsigned `GetRequestsWithProof` message. The function performs all the legitimate protocol validation — dedup, timeout, source/dest chain match against the proof, membership proof, response state proof [2](#0-1)  — but none of that validation touches `address`. It is never checked against `msg.signer`, any registered relayer set, or any value derived from the proof itself.

At the end of the function, the pallet mints reputation tokens directly to whatever account `address` decodes to: [3](#0-2) 

The extrinsic's `validate_unsigned` implementation re-runs `handle_get_requests` for validity checking and only de-duplicates by the batch's request hashes, never by `address` [4](#0-3) , so `address` is not part of what the network treats as "the same claim" — a submitter can freely swap in a different `address` on every resubmission of the same underlying proof/requests without changing what is `provides`-tagged.

This is the same class of bug as the Apache Polaris CVE: a piece of state that should gate a valuable resource (there: the storage location that scopes vended credentials; here: the account entitled to a proportional mint of reputation) is taken from unvalidated, attacker-supplied input and used to grant value before any check ties it to the entity that actually did the verified work. Legitimate relayers authenticate themselves by signing the `Message::Request`/`Message::Response` payloads that `pallet-messaging-incentives::on_executed` recovers a relayer from via `sr25519` signature recovery [5](#0-4) ; the coprocessor path bypasses that signature-based attribution entirely and substitutes a bare, self-declared address.

### Impact Explanation
Any account submitting a `handle_unsigned` call to `StateCoprocessor` can direct the reputation mint to an address of their choosing — including one they don't control the underlying GET-request delivery work for, or a sybil address to launder attribution. Since the mint amount scales with `total_bytes` of verified payload [6](#0-5) , and any relayer capable of assembling valid source/response proofs for an in-flight GET request can submit the extrinsic, this allows unbacked/mis-attributed minting of `ReputationAsset` to arbitrary accounts, undermining whatever downstream trust or reward system (e.g. relayer selection, fee sharing) depends on that reputation asset being a faithful record of who delivered verified work. This is an unauthorized-mint / forged-attribution class issue reachable from a single unsigned, permissionless extrinsic.

### Likelihood Explanation
High: the call is `ensure_none` (no signature, no allowlist, no fee) and requires only a legitimate/valid GET-request proof pair — data that is public once a GET request is in flight and its response is known — to trigger the mint. No privileged role, governance action, or malicious insider is needed; a single relayer-class actor submitting an otherwise-normal `handle_unsigned` extrinsic with a self-chosen `address` field is sufficient.

### Recommendation
Bind `address` to something that is cryptographically tied to the caller/verified work, mirroring what `pallet-messaging-incentives` does elsewhere: e.g. require a signature over the request/response commitments recoverable to `address` (as `OutboundRequestDeliveryClaim` does for its `payee`/`signature` pair [7](#0-6) ), or recover the relayer identity the same way `pallet-messaging-incentives::relayer_for` does from the message signer, rather than trusting a bare unauthenticated field in the extrinsic payload. Additionally include `address` in the `provides` tag of `validate_unsigned` if it is meant to be idempotent per-submitter.

### Proof of Concept
1. Observe (or construct) any valid, in-flight `GetRequest` on a source chain that Hyperbridge already has state commitments for.
2. Obtain the corresponding source membership proof and destination response/state proof (public data any relayer can fetch via RPC, as shown in `relay_get_response_message` [8](#0-7) ).
3. Submit `StateCoprocessor::handle_unsigned(GetRequestsWithProof { requests, source, response, address: <attacker_chosen_32_bytes> })` as an unsigned extrinsic.
4. `handle_get_requests` verifies the proofs successfully (they are genuine) and mints `total_bytes * MintPerByte` of `ReputationAsset` to `attacker_chosen_32_bytes`, regardless of whether that account had anything to do with delivering the request/response.
5. Repeat with a different `address` value pointing to a sybil/attacker account each time, since `address` is not part of the anti-replay `provides` tag.

/// This function is used to fetch get request and construct get response and submit to chain
/// A(source chain)
async fn relay_get_response_message(
	chain_a_sub_client: SubstrateClient<Hyperbridge>,
	chain_b_sub_client: SubstrateClient<Hyperbridge>,
	get_request: ismp::router::GetRequest,
) -> Result<Vec<u8>, anyhow::Error> {
	let (chain_a_client, chain_b_client) =
		(Arc::new(chain_a_sub_client.clone()), Arc::new(chain_b_sub_client));

	// ======== process the request offchain ( 1. Make the response ) =============
	let response = {
		let dest_chain_block_hash =
			chain_b_client.client.rpc().block_hash(Some(get_request.height.into())).await?;
		let keys = get_request.keys.iter().map(|key| &key[..]).collect::<Vec<&[u8]>>();
		let value_proof =
			chain_b_client.client.rpc().read_proof(keys, dest_chain_block_hash).await?;
		let proof = value_proof.proof.into_iter().map(|bytes| bytes.0).collect::<Vec<Vec<u8>>>();

		let proof_of_value =
			StateMachineProof { hasher: HashAlgorithm::Keccak, storage_proof: proof };
		let proof = Proof {
			height: StateMachineHeight {
				id: chain_b_client.state_machine_id(),
				height: get_request.height,
			},
			proof: proof_of_value.encode(),
		};
		let response = ResponseMessage {
			requests: vec![get_request.clone()],
			proof,
			signer: chain_a_client.address(), // both A&B have same relayer address
		};

		Message::Response(response)
	};
	let cloned_chain_a_client = chain_a_client.clone();

	// =================== send to the source chain ================================

	// resubmit if fails

	let mut tx_res_hash = None;
	while let Ok(tx_hash) = send_unsigned_extrinsic(
		&cloned_chain_a_client.clone().client.clone(),
		Extrinsic::new("Ismp", "handle_unsigned", vec![response.clone()].encode()),
		true,
	)
	.await
	{
		tx_res_hash = tx_hash;
		break;
	}
