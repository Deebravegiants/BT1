Audit Report

## Title
Missing `return` after failed email-claim extraction lets OIDC login continue and create a valid session even when the client is told the request failed - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, the `email, ok := claims["email"].(string)` check at line 226 logs an error and writes a `500` response via `c.String(...)` when the assertion fails, but unlike every other error branch in the same function it omits the `return` statement. Execution falls through, and the function proceeds to insert a new row into `oidc_sessions`, set the session cookie, and return a `200 OK` body — meaning a client that receives a `500`-status response body can still walk away with a valid, persisted, authenticated session.

## Finding Description
The code path is: [2](#0-1) 
Every sibling error branch in `handleTokenExchange` returns immediately after writing its error response (e.g. lines 171, 182, 195, 203, 211, 218, 224, 244, 270), but this one does not, so execution continues into the session-creation and persistence logic: [3](#0-2) 
The role computed from `IDClaimsToUserRole` is independent of `email`, so it succeeds even with an empty email, and the session row is inserted, the audit log records `AuthLoginSuccessNo2FA`, and the `Set-Cookie` header for `clsession_id` is emitted before the final `c.JSON(http.StatusOK, ...)` call (which is written on top of the earlier `500` response, producing a Gin superfluous-write warning but not preventing the cookie from being sent). Downstream, `AuthenticateBySession` in `core/web/auth/auth.go` (lines 55-71) simply reads the `SessionIDKey` value from the session cookie and calls `AuthorizedUserWithSession`, with no check on how or under what conditions the session was originally created — so this session is fully valid for subsequent authenticated requests.

This matches the "checked-but-ignored" failure-signal anti-pattern: the `ok` boolean is checked and an error is logged, but the operation it should gate is not aborted.

## Impact Explanation
This is a genuine node API authentication-bypass-adjacent bug: an OIDC/SSO exchange that the client is told failed (`500` status) can still leave the attacker/user holding a valid session cookie tied to a real, persisted `oidc_sessions` row with a role mapped from verified group claims but an empty `user_email`. Any caller who inspects that cookie can authenticate as that role on any endpoint gated by `AuthenticateBySession`, which is a legitimate node API authentication integrity issue in-scope for the bounty.

## Likelihood Explanation
The trigger condition is narrow: it requires the OIDC ID token's claims payload to omit the `email` field (or return a non-string value) while still passing ID-token verification and yielding valid group claims for role mapping. This depends on the configured OIDC provider's claim shape rather than being freely triggerable by an arbitrary unprivileged HTTP client against a normally configured provider (e.g., Okta/Google normally always return `email` when the scope is requested). It requires either a misconfigured/non-standard IdP, a compromised/malicious IdP, or an edge case in provider behavior — a "provider-controlled" precondition rather than a pure unauthenticated-client-only path — which lowers but does not eliminate real-world likelihood, since OIDC providers/configurations vary and this is triggerable without any operator/admin privilege on the Chainlink node itself.

## Recommendation
Add a `return` statement immediately after `c.String(http.StatusInternalServerError, "Failed to get email from claims")` at line 229, matching every other error branch in `handleTokenExchange`, so that a missing/invalid email claim aborts session creation and persistence.

## Proof of Concept
1. Stand up or configure an OIDC provider (or a proxy intercepting the token exchange) whose ID token claims omit `email` or return it as a non-string, while still passing signature verification and providing valid group claims.
2. Drive the normal OIDC flow through `/oidc-login` and then the token exchange endpoint (`handleTokenExchange`).
3. Observe: HTTP response is `500 Internal Server Error` with body `"Failed to get email from claims"`, but the response also contains a `Set-Cookie` header with a valid `clsession_id`, and a new row is created in `oidc_sessions` with `user_email = ''` and the role derived from group claims.
4. Replay the received session cookie against any endpoint behind `auth.AuthenticateBySession` (`core/web/auth/auth.go` lines 55-71) — the request succeeds and is authenticated with the mapped role, despite the original exchange reporting failure.
