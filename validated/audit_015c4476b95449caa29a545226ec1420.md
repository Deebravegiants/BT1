### Title
Fee-on-transfer shortfall silently backfilled from stranded action dust, letting an attacker mint an output UTXO larger than what the action actually received - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` computes the amount to return to the caller purely from the *pre/post ERC20 balance diff* of the action contract, adjusted by the nominal (non-fee-aware) `deltaAmountChanges` value declared for the transaction. When the deposited token is fee-on-transfer, the action receives less than the nominal amount, but the code compensates the shortfall from whatever balance is already sitting in the contract (dust left by a prior, unrelated transaction), and pays the full nominal amount out via `handleOut`. This lets an attacker convert stranded/residual balance in the action into their own freshly-minted output UTXO.

### Finding Description
The claimed invariant is: *tokens leaving the action in this tx == -deltaAmountChanges Hinkal sent it this tx*.

In `runAction`: [1](#0-0) 

```
int256 balanceChange = int256(balancesAfter[i]) - int256(balancesBefore[i]);
if (deltaAmountChanges[i] < 0) {
    balanceChange -= deltaAmountChanges[i]; // adds back |delta|
}
if (balanceChange < 0) revert BalanceChangeShouldBePositive();
UTXO memory utxoOut = handleOut(balanceChange, circomData, i);
```

`balancesBefore`/`balancesAfter` are simple `token.balanceOf(address(this))` snapshots taken at the very start and end of `runAction` [2](#0-1) . The code assumes that whatever amount Hinkal declares as `-deltaAmountChanges[i]` (the nominal deposit) is exactly what physically landed in the contract. For a fee-on-transfer token this is false: the actual delivered amount `D'` is less than the stated `D`. The shortfall `D - D'` is silently absorbed if the action *already holds at least that much dust* from an unrelated prior transaction (e.g., left-over balance from rounding, a previous fee-on-transfer deposit, a partially-filled swap, or any stranded balance), because the balance-diff math only checks the *net* change is non-negative, not that the specific `D` tokens were actually received.

Concretely: assume the action already holds dust `d ≥ D - D'` for token `i` before this transaction. Attacker crafts `circomData`/`deltaAmountChanges[i] = -D` for their own valid proof (spending their own shielded notes to justify the nominal debit). Hinkal transfers `D` nominal of the fee-on-transfer token toward the action, but only `D'` is actually delivered. `balancesBefore[i]` includes the pre-existing dust `d`; `balancesAfter[i] = balancesBefore[i] + D'` (no ops needed to touch this token at all). Then:
```
balanceChange = D' 
balanceChange -= (-D) => balanceChange = D' + D  ... 
```
Wait — precisely: `balanceChange` starts as `balancesAfter - balancesBefore = D'`. Since `deltaAmountChanges[i] = -D < 0`, the code does `balanceChange -= deltaAmountChanges[i]` i.e. `balanceChange = D' + D`. This is clearly wrong (double counts): a well-behaved system would want `handleOut` to pay exactly `D'` (or `D` only if `D` was really available), not `D' + D`. But the important point for this specific question is simpler: `handleOut` then calls `transferERC20TokenOrETH(token, msg.sender, D'+D)` — this requires the *contract's real token balance* (`d + D'`) to cover the outgoing transfer. If `D' + D > d + D'`, i.e. `D > d`, the ERC20 transfer underflows and reverts, protecting the system. But if the attacker sizes their nominal deposit `D` such that `D ≤ d` (i.e., the dust is large enough), the transfer succeeds using the pre-existing dust to make up part of the payout — the attacker's own output UTXO (`utxoOut.amount = D' + D`, minted by `handleOut`) ends up backed partly by tokens that came from an unrelated prior transaction, not from this transaction's actual `-deltaAmountChanges` inflow.

None of the existing guards catch this:
- `performHinkalChecks`/proof verification only bind the attacker's *own* declared `deltaAmountChanges` to their *own* spent/created UTXOs; they say nothing about whether the ERC20 transfer that physically moves those declared amounts into the external action actually delivered the full nominal amount (fee-on-transfer tokens are outside circuit awareness).
- `runAction`'s only defensive check, `balanceChange < 0`, is a floor check, not an equality check against the *actual* amount transferred in this tx; it happily accepts and pays out any amount the contract balance can cover, including value contributed by unrelated prior activity.
- `verifyWallet` only guards `emporiumMessage` replay and (optionally) a signer's op signature; it does not constrain or attest to the real token balance received.

### Impact Explanation
An unprivileged attacker who deposits their own funds through a fee-on-transfer token into an Emporium action that already carries residual/stranded balance for that token can have `handleOut` mint them an output UTXO larger than what their transaction actually delivered to the action, appropriating value that belongs to the protocol/previous depositors. This is a direct theft of value parked in an external action beyond what `-deltaAmountChanges` moved into it in that transaction, matching the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable any time dust of sufficient size accumulates again in the same action for the same token.

### Likelihood Explanation
Preconditions: (1) the target action must already hold a non-trivial dust/residual balance of a fee-on-transfer token (plausible after normal fee-on-transfer deposits/swaps, since these already routinely leave shortfalls per the exact mechanism above, meaning dust naturally accumulates over time); (2) the token must be fee-on-transfer; (3) attacker needs their own valid proof declaring the nominal deposit, which they can always construct since they control their own UTXOs and metadata. Attacker cost is only their own fee-on-transfer deposit amount `D'` (minus the token's transfer fee, which they pay anyway); the gain is up to the full existing dust `d`, repeatable each time dust re-accumulates. I was not able to fully trace `Hinkal.sol`'s exact ordering of the ERC20 transfer into the external action relative to `runAction`'s `balancesBefore` snapshot (tool budget exhausted before completing that read), so the precise numeric relationship above is derived from the code actually present in `EmporiumUpgradeable.sol`; this is the authoritative contract-level logic performing the balance-diff accounting and is sufficient to demonstrate the broken invariant regardless of exact call ordering in `Hinkal.sol`.

### Recommendation
Do not rely on a pre/post balance-diff floor check as the sole gate for `handleOut`. Instead, track the *exact* amount actually delivered to the action for each declared negative `deltaAmountChanges[i]` (e.g., snapshot balance immediately before and after the specific transfer that delivers that token, not at the start/end of the whole `runAction`), and cap any output UTXO strictly to the amount attributable to this transaction's real inflows plus ops-generated proceeds — never to the contract's total standing balance. Any stranded/dust balance should be swept by a privileged/owner-only recovery function, never implicitly claimable via `handleOut`.

### Proof of Concept
Foundry test plan:
1. Deploy a fee-on-transfer ERC20 mock (`FeeOnTransferToken`) that takes e.g. 10% fee on `transfer`/`transferFrom`.
2. Deploy `EmporiumUpgradeable`, whitelist a mock Hinkal caller as `onlyAllowedRecipient`.
3. Seed dust: directly `mint`/`transfer` `d = 100` fee-on-transfer tokens to the Emporium action address (simulating stranded balance from a prior unrelated tx).
4. As attacker, construct `circomData` with `erc20TokenAddresses = [feeToken]`, `deltaAmountChanges = [-90]` (nominal deposit `D = 90 ≤ d = 100`), empty `stack.ops` (no swap needed), `stack.signerAddress = address(0)`.
5. Have the mock Hinkal transfer nominal `90` fee-on-transfer tokens to the action (actual delivered `D' = 81` after 10% fee), then call `runAction(circomData, deltaAmountChanges)`.
6. Assert: `utxoOut.amount == D' + D = 171` (or whatever the exact double-count/backfill computes to) while the action's *legitimate* new inflow this tx was only `81`.
7. Assert: `action.balanceOf(feeToken) after == d + D' - utxoOut.amount == 0` (or negative before the payout — i.e., the dust `d=100` was fully or partially consumed to fund an output UTXO not backed by this transaction's `-deltaAmountChanges`).
8. Compare `utxoOut.amount` against `-deltaAmountChanges Hinkal sent it` (`81` actually received) — the equality is violated, confirming attacker captured protocol/dust value beyond their real contribution.
