Webhook `shop-domain` (and `topic`/`webhook-id`) is trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated for a given shop once `Utils::HmacValidator.validate` passes, but the HMAC only covers the raw request body — never the `shop-domain`, `topic`, or `webhook-id` headers that the library (and its documentation) hands to the app as trusted, tenant-identifying metadata.

### Finding Description
`Registry.process` gates all further processing on a single check: [1](#0-0) 

The HMAC that gates this call is computed only over `to_signable_string`, which is simply the raw body: [2](#0-1) 

`request.shop`, `request.topic`, and `request.webhook_id`, however, are read straight from attacker-controllable HTTP headers with no cryptographic binding to the signature at all: [3](#0-2) [4](#0-3) 

`HmacValidator.validate_signature` verifies only `verifiable_query.to_signable_string` (the body) against the shared `api_secret_key`: [5](#0-4) 

After validation, `Registry.process` forwards the unauthenticated `request.shop` value straight into `WebhookMetadata` and hands it to the app's handler as the identity of the shop that generated the event: [6](#0-5) 

The identity binding broken is: `shop authenticated by HMAC` ≠ `shop asserted in WebhookMetadata.shop`. The signature only proves "this body byte-string was produced with the app's shared secret" — it says nothing about which shop the body belongs to. Because the same `api_secret_key` is shared across every shop installing the app, and topics with a fixed/predictable body (e.g. `app/uninstalled`, `shop/redact`, or filtered fields yielding identical JSON for two shops) produce an *identical valid HMAC regardless of which shop the event was for*, any legitimate installer of the app (an unprivileged internet user with respect to *other* shops) can capture one genuine webhook delivery for their own shop and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop domain. The HMAC still validates (it never looked at the header), and the handler executes business logic — including sensitive lifecycle events like `app/uninstalled`, `customers/data_request`, or `shop/redact` — attributed to the victim tenant.

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" (implying full authenticity, including the shop attribution), reinforcing that this is a documented guarantee the implementation does not actually provide: [7](#0-6) 

This is directly analogous to the reported `memcpy` flaw: a boundary/identity check exists (the HMAC check) but does not cover all the fields (`shop`, `topic`, `webhook_id`) that are subsequently trusted and acted upon — exactly the "field acted on but not covered by the HMAC" pattern called out in scope.

### Impact Explanation
An attacker who is a legitimate (unprivileged) installer of the target app on their own shop can forge webhook deliveries attributed to any other shop using the same app, without ever obtaining the app's `client_secret` or any victim credentials — they only need one HMAC signature computed by Shopify itself for their own shop with body content that happens to also be valid/identical for the topic in question. This enables cross-tenant confusion: triggering another shop's `app/uninstalled` cleanup, GDPR redaction handlers, or any other webhook side effects for a different tenant. This meets the "Critical - cross-tenant access" bar in scope.

### Likelihood Explanation
Moderate-to-high: exploitation requires the app to register for at least one topic whose body is shop-independent or whose relevant fields are attacker-predictable (common for mandatory topics like `app/uninstalled`, `shop/redact`, `customers/redact`, whose bodies contain only IDs the attacker may already know or a near-empty payload), and requires the attacker to control at least one shop that installs the app — a realistic bar for any public Shopify app, satisfying the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity to the signature verification. Compute (or require the host app to supply) a signable string that includes the `shop-domain` (and ideally `topic`/`webhook-id`) alongside the body, or otherwise cross-check `request.shop` against session/tenant state independently established from a source Shopify does authenticate for that channel, before dispatching to handlers. At minimum, document prominently that `shop`, `topic`, and `webhook_id` in `WebhookMetadata` are **not** cryptographically authenticated and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and subscribes to `app/uninstalled` (a mandatory/predictable-body topic).
2. Attacker uninstalls the app, capturing the genuine webhook request Shopify sends: body `"{}"`, header `x-shopify-hmac-sha256: <valid HMAC over "{}">`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb#L26-L31` succeeds because it only checks the body against the secret (identical body, same secret, same HMAC).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-L199`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to run uninstall cleanup logic for a shop the attacker never actually uninstalled from.
