### Title
POA Bridge `describeWithdrawal` matches withdrawal status by `assetId` only, causing wrong-withdrawal status/hash to be reported when a batch contains two withdrawals of the same asset - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain destination status of a specific withdrawal purely by matching the returned POA API records against `withdrawalParams.assetId`. When a batch withdrawal intent contains two or more withdrawals of the same asset (a scenario the SDK's own public API explicitly supports via `processWithdrawal`/`createWithdrawalCompletionPromises`), the lookup returns the first record with a matching `near_token_id`, regardless of which physical withdrawal it actually corresponds to.

### Finding Description
`findMatchingWithdrawal()` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 409-427) and its duplicate in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` (lines 135-153) select a withdrawal record using only:
```
withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId)
```
`describeWithdrawal()` (lines 313-343) then reports the `status`/`transfer_tx_hash` of that single matched record for the `index`-th withdrawal being polled, even though the `index` and full identity (amount/destination) of the withdrawal are never checked. This is called independently for every index (see `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` lines 80-107, which assigns a per-route `index` but that index is unused by the POA matcher).

The comment in the code (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` lines 409-416) acknowledges: "multiple withdrawals of the same token in a single transaction are not supported," but the public SDK surface (`processWithdrawal`, `waitForWithdrawalCompletion`, `createWithdrawalCompletionPromises`, documented in `packages/intents-sdk/README.md` lines 521-639) does not reject or warn against batching two withdrawals of the same asset, so an integrator can unknowingly hit this path.

### Impact Explanation
If a batch has two withdrawals of the same asset (e.g., two different amounts/destinations of `btc.omft.near`), both `promises[0]` and `promises[1]` (or repeated polling of `describeWithdrawal` for index 0 and index 1) will resolve to the *same* matched record's `status`/`transfer_tx_hash`. An integrator relying on `promises[i]` corresponding to `withdrawalParams[i]` (as stated in the README, line 639) can:
- Mark a still-pending withdrawal as completed using another withdrawal's destination transaction hash.
- Credit/refund the wrong destination transaction hash to the wrong withdrawal record, which is a status/hash misreport that can cause an integrator to credit twice or under two different accounting entries.

This falls under the "status/hash misreport making an integrator credit or refund twice" category.

### Likelihood Explanation
Likelihood is limited by the fact that it requires an integrator to submit a batch withdrawal with two entries sharing the exact same `assetId`, which the SDK does not block despite documenting it as unsupported for the POA route. This is a self-triggered condition (no adversarial input) but achievable simply by normal use of documented batch APIs without reading the internal implementation comment, since the public README does not warn against same-asset batching for POA-routed assets.

### Recommendation
- In `createWithdrawalIdentifiers`/`PoaBridge.supports`/`validateWithdrawal`, detect and reject (or explicitly warn/throw) when a batch contains multiple withdrawals resolving to the POA bridge with the same `assetId`, until the POA API supports disambiguation.
- Alternatively, implement the amount-based ordering heuristic mentioned in the existing code comment (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` lines 412-416) to correctly disambiguate multiple same-asset withdrawals instead of returning the first match.
- Update `packages/intents-sdk/README.md` batch withdrawal documentation to explicitly warn integrators about this limitation until fixed.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [{ assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: A }, { assetId: "nep141:btc.omft.near", amount: 500000n, destinationAddress: B }] })`.
2. Both withdrawals settle on POA bridge; suppose withdrawal to `A` completes first with `transfer_tx_hash = "tx-A"` while withdrawal to `B` is still `PENDING`.
3. `createWithdrawalCompletionPromises` returns `promises[0]` and `promises[1]`; internally each calls `PoaBridge.describeWithdrawal` with `index: 0` and `index: 1` respectively, but both invoke `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which returns the same (first) `COMPLETED` record for `A`.
4. Both `promises[0]` and `promises[1]` resolve with `{ status: "completed", txHash: "tx-A" }`, even though the withdrawal to `B` has not actually completed — the integrator's system records `tx-A` as the destination hash for both withdrawals. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],

		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

**Option B: Independent Promises (`createWithdrawalCompletionPromises`)**

For scenarios where fast withdrawals (Solana ~2s) shouldn't wait for slow ones (Bitcoin ~1hr), use `createWithdrawalCompletionPromises` to get promises that resolve independently:

```typescript
// Get array of promises - one per withdrawal
const promises = sdk.createWithdrawalCompletionPromises({
    withdrawalParams,
    intentTx
});

// Fire and forget - handle each independently
promises[0].then(tx => saveUsdc(tx)).catch(err => logError(0, err));
promises[1].then(tx => saveBtc(tx)).catch(err => logError(1, err));

// Or await a specific withdrawal (fast chain first)
const usdcTx = await promises[0];
await notifyUser('USDC received', usdcTx.hash);

// Or process as they complete with backpressure
const pending = new Map(promises.map((p, i) => [i, p]));
while (pending.size > 0) {
    const { index, tx } = await Promise.race(
        [...pending.entries()].map(async ([i, p]) => ({ index: i, tx: await p }))
    );
    pending.delete(index);
    await saveSuccess(index, tx);  // Backpressure maintained
}

// Or wait for all with independent error handling
const results = await Promise.allSettled(promises);
for (const [i, result] of results.entries()) {
    if (result.status === 'fulfilled') {
        await saveSuccess(i, result.value);
    } else {
        await saveFailure(i, result.reason);
    }
}
```

**With timeout control:**

```typescript
const promises = sdk.createWithdrawalCompletionPromises({
    withdrawalParams,
    intentTx,
    signal: AbortSignal.timeout(30_000)  // 30 second timeout
});
```

**Key benefits:**
- Fast withdrawals (Solana ~2s) aren't blocked by slow ones (Bitcoin ~1hr)
- One failure doesn't affect other withdrawals
- Recovery-friendly: recreate promises from saved `{ withdrawalParams, intentTx }`
- Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`
