### Title
Front-running the relayer's own `signer` field in `handle_unsigned` lets an attacker steal delivery-reward reputation for work it didn't do - ([File: modules/pallets/messaging-incentives/src/lib.rs])

### Summary
`pallet-messaging-incentives::on_executed` mints reputation to whichever account is recovered from a `RequestMessage`/`ResponseMessage`'s `signer` field, and that field is explicitly excluded from the mempool `provides` tag computed in `pallet_ismp`'s `validate_unsigned`. This mirrors the referral-mint bug class: a value that is supposed to identify "who actually performed the qualifying work" is instead a free-form field the extrinsic submitter fully controls and can swap for their own identity while riding on someone else's delivered proof.

### Finding Description
`RequestMessage`/`ResponseMessage::signer` is documented as "Ideally should be their account identifier" [1](#0-0) , and it is populated by whichever party calls `submit` when it signs the message body [2](#0-1) . `pallet_messaging_incentives::Pallet::relayer_for` recovers this signer purely from the signature over `keccak256(&requests.encode())`, with no binding to the extrinsic's actual sender (there is none — `handle_unsigned` is dispatched via `ensure_none`) [3](#0-2) . The mint then goes straight to that recovered account [4](#0-3) .

Crucially, `pallet_ismp`'s `validate_unsigned` explicitly excludes the `signer` from the mempool's `provides` dedup tag "so equivalent submissions from different relayers dedupe" [5](#0-4) . This means any unsigned `handle_unsigned` transaction sitting in the public mempool can be copied and rebroadcast by anyone with the requests/proof unchanged but the `signer` field replaced with a signature from an attacker-controlled keypair over the same `requests` bytes (which the attacker can trivially produce, since the signature only needs to verify against the unchanged `requests` payload, not against any secret the original relayer holds). Because `execute()` only validates the membership/state proof of the requests — not who supplied them — the swapped message is accepted identically, and whichever copy lands on-chain first (or is prioritized) determines who gets the `ReputationMinted` credit. This lets a bystander harvest another relayer's proof-fetching and relaying effort for itself, or a single actor sybil the reward across many self-controlled "signer" identities by resubmitting the same delivered requests with different signer keys before the original is included.

### Impact Explanation
Reputation minted here is explicitly soulbound and used for relayer ranking/incentive weighting (`pallet-collator-manager` resets it each session, and dispatched transfers of it are filtered) [6](#0-5) . An attacker who can consistently front-run the `signer` field can accumulate reputation disproportionate to actual relaying work performed, corrupting the incentive/ranking mechanism this pallet exists to drive — the analog of the audited contract's "receive referral points for himself" bug, since the value meant to attribute credit to the genuine actor is unauthenticated and swappable by any mempool observer.

### Likelihood Explanation
`handle_unsigned` is a fully permissionless, unsigned extrinsic with public mempool visibility, and the `provides` tag deliberately does not include the signer, so the attack requires no privileged access — only mempool monitoring and the ability to re-sign the same public `requests` bytes with a different keypair, which is always possible. Likelihood is Medium: it requires racing block inclusion, but no cryptographic or permission barrier prevents it.

### Recommendation
Bind the reward-recipient identity to something the attacker cannot independently reproduce, e.g., require `signer` to be committed within the state/membership proof itself, or require the message to be signed with a key whose signature also covers a value the original relayer alone knows/controls (such as its own nonce or a proof-of-delivery timestamp it fetched), or move to a signed-origin extrinsic where `frame_system`'s origin, not a free-form byte field, determines the reward recipient. At minimum, include `signer` in the `provides` tag computation (or a signer-bound uniqueness key) so that swapped-signer resubmissions of the same requests are treated as competing/duplicate transactions rather than silently accepted with a different beneficiary.

### Proof of Concept
1. Relayer A fetches a valid membership proof for `requests` and builds `Message::Request(RequestMessage { requests, proof, signer: sig_A })` via `submit`, broadcasting an unsigned `Ismp::handle_unsigned` extrinsic [7](#0-6) .
2. Attacker B observes this pending unsigned extrinsic in the mempool, copies `requests` and `proof` unchanged, computes `sig_B = sign_B(keccak256(requests.encode()))`, and rebroadcasts `Message::Request(RequestMessage { requests, proof, signer: sig_B })` with higher gas priority.
3. Because `provides` for `Message::Request` is derived only from `hash_request(post)` per request (excluding `signer`) [8](#0-7) , and `execute()`/proof verification succeeds identically for either submission, B's copy can be included instead of (or dedupe against) A's.
4. `pallet_messaging_incentives::on_executed` recovers B (not A) as the relayer and mints reputation to B [9](#0-8) , despite B having contributed no genuine relaying/proof-fetching work beyond copying A's public mempool transaction.

	/// Recover the relayer's account from the sr25519 signature on a
	/// `Message`'s `signer` field. Returns `None` if the message has
	/// no signer (e.g. consensus messages) or the signature is bad.
	fn relayer_for(message: &Message) -> Option<T::AccountId> {
		let (signer, signed) = match message {
			Message::Request(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			Message::Response(msg) =>
				(&msg.signer, sp_io::hashing::keccak_256(&msg.requests.encode())),
			_ => return None,
		};
		Signature::decode(&mut &signer[..])
			.ok()?
			.verify_and_get_sr25519_pubkey(&signed, None)
			.ok()
			.map(T::AccountId::from)
	}
}

/// The whole point of the soulbound treatment: a relayer that earned
/// reputation cannot dispatch a transfer of it to another account. The
/// rejection must come from the runtime call filter (so an unsigned
/// holder-driven dispatch fails); we verify that by routing through
/// `RuntimeCall::dispatch`, which is what production extrinsics use.
#[test]
fn dispatched_transfer_of_reputation_is_filtered() {
	new_test_ext().execute_with(|| {
		let relayer_pair = sr25519::Pair::from_seed(&[13u8; 32]);
		let relayer_account = AccountId32::new(relayer_pair.public().0);
		setup_relayer_and_asset(&relayer_account);

		MessagingRelayerIncentives::set_mint_per_byte(RuntimeOrigin::root(), 1).unwrap();
		MessagingRelayerIncentives::on_executed(
			vec![signed_request(&relayer_pair, vec![0u8; 100])],
			vec![],
		)
		.unwrap();
		assert_eq!(relayer_balance(&relayer_account), 100);

		let call = RuntimeCall::Assets(pallet_assets::Call::transfer {
			id: ReputationAssetId::get(),
			target: BOB.clone().into(),
			amount: 50,
		});
		// Bring `weigh_data` into scope so we exercise the same dispatch path
		// the runtime uses; assert the filter rejects rather than the inner call.
		let _ = call.get_dispatch_info();
		let err = call
			.dispatch(RuntimeOrigin::signed(relayer_account.clone()))
			.expect_err("reputation transfer must be filtered");
		assert_eq!(err.error, frame_system::Error::<Test>::CallFiltered.into());

		assert_eq!(relayer_balance(&relayer_account), 100);
		assert_eq!(relayer_balance(&BOB), 0);
	});
}
