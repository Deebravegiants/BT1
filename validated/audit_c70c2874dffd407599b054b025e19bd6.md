## Title
Webhook shop identity spoofing due to HMAC signature not covering the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The bug report describes a class of vulnerability where an identity-determining value is not actually bound by the cryptographic check that is supposed to authenticate the message. In `ShopifyAPI::Webhooks::Request`, the HMAC signature is computed only over the raw request body, while the `shop` (and `topic`, `webhook_id`) values used downstream to attribute the webhook to a specific merchant come from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors, however, are pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (the raw body only) and `verifiable_query.hmac` (from the `hmac-sha256` header): [3](#0-2) [4](#0-3) 

Because the signature check only proves "these body bytes were sent by Shopify with this app's `client_secret`", it says nothing about which shop or topic they belong to. The identity binding that should hold is:

```
shop authenticated (bound into HMAC) == shop attributed to the data (request.shop used by the app)
```

but instead the code enforces:

```
raw_body bytes verified (HMAC) ⇎ shop-domain header trusted (request.shop)
```

Any merchant who has installed the app (an unprivileged, legitimately-authenticated tenant of the app) receives real webhooks from Shopify with a valid HMAC over their own webhook body. Because the `shop-domain` header is excluded from the signed content, that same attacker-controlled HTTP client can replay the exact same body/signature pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value naming a victim shop. `Registry.process` will still consider the HMAC valid (it only checks the body) and will dispatch to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, attributing attacker-controlled body content to the victim shop: [5](#0-4) 

Any host application that uses `WebhookMetadata#shop` to key per-tenant storage/processing (which is the intended and only reasonable use of this field, since this is exactly what the gem hands to the handler for tenant attribution) will process/store attacker-supplied data under the wrong shop's identity — a cross-tenant data-confusion vector.

### Impact Explanation
This crosses a tenant boundary: an authenticated-but-unprivileged actor (a merchant with the app installed, who can legitimately trigger and observe their own webhooks) can cause the app to associate crafted body content with an arbitrary victim shop identifier, since the field used for tenant attribution (`shop`) is never included in the HMAC-protected content. This matches the "Critical – cross-tenant access" impact category: data intended to be scoped to one shop's session can be attributed to a different shop's identity purely through header manipulation, with a still-valid HMAC.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as a merchant (a normal, unprivileged action), (2) triggering a webhook for a topic the attacker controls (e.g., product/order events on their own store), and (3) replaying the captured body+signature to the app's public webhook endpoint with a modified `shopify-shop-domain` header. No access to `api_secret_key` or any victim credential is needed. The gem's own `Request`/`Registry` code performs no independent verification that the `shop-domain` header matches a value bound into the signature.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values as part of the signable content validated against the HMAC, or otherwise cryptographically bind the shop identity to the payload before dispatching `WebhookMetadata`. At minimum, document and/or enforce in `Registry.process` that `request.shop` must be cross-checked against a shop known to have installed the app/topic, so a valid signature for one shop's payload cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook:
```
headers: {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<valid-hmac-of-body>",
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  ...
}
body: '{"id": 1, "note": "malicious payload"}'
```
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, changing only:
```
"x-shopify-shop-domain" => "victim-shop.myshopify.com"
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only (see `to_signable_string` in `lib/shopify_api/webhooks/request.rb:35-38`) — validation succeeds because the body is unchanged.
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though Shopify never sent this payload for that shop — the app processes attacker-controlled data under the victim's tenant identity.
