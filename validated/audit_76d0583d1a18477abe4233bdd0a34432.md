## Finding

### Title
Webhook shop identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by checking an HMAC that is computed **only over the raw request body**, then hands the handler a `WebhookMetadata` object whose `shop` value comes from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, a field that is never included in the signed material. An attacker who can obtain one genuinely-signed webhook (e.g., by installing the app on their own store and triggering any webhook topic) can replay that exact body/HMAC pair while substituting an arbitrary shop domain in the header, and the request will still pass verification while being attributed to a shop the attacker does not control.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are all parsed straight from attacker-controllable HTTP headers and are not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, i.e. body only, comparing it against the value computed with the app's own `api_secret_key` (shared across every shop that has this app installed): [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the *entire request*, including the shop, is authentic, and immediately forwards `request.shop` — the unauthenticated header — into the handler: [4](#0-3) 

The documented contract for `process` explicitly promises this: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," reinforcing that consumers of this API are meant to trust the resulting `shop` field as authenticated.

**Identity binding broken:** the equality the gem implicitly guarantees is `HMAC valid ⇒ (body, shop) authentic`, but the code only enforces `HMAC valid ⇒ body authentic`. `shop` is bytes verified (the body) versus bytes parsed (the header) — exactly the pattern of an identity field acted upon without being covered by the HMAC.

**Attack sequence:**
1. Attacker installs the app on their own store `attacker.myshopify.com` (any developer/unprivileged internet user can do this for a public app).
2. Attacker's endpoint receives a legitimately-signed webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (both valid because they were genuinely sent by Shopify using the shared `api_secret_key`).
3. Attacker replays the exact same `raw_body` (`B`) and `hmac-sha256` header (`H`) to the victim app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over `B` with the app's secret — it matches `H`, so validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` and invokes the handler, which now processes attacker-supplied data as if it originated from, and pertains to, the victim's shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism is meant to enforce: the receiving application is told (with an apparently-valid signature) that arbitrary attacker-chosen data belongs to a shop the attacker has no relationship with. Depending on how the host app uses `data.shop` (commonly used as a lookup/foreign key to persist or act on per-tenant data), this enables cross-tenant data injection/corruption — one of the explicitly in-scope Critical impacts (cross-tenant access).

### Likelihood Explanation
Likelihood is High/practical: the only prerequisite is the ability to install the app on any single store (including a free development store) to obtain one valid, replayable body/HMAC pair for a chosen webhook topic, and the ability to send an HTTP request with a spoofed `X-Shopify-Shop-Domain` header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material used by `Request#to_signable_string`, or, at minimum, document and require that `Registry.process`/consumers independently verify `request.shop` against a known, previously-authenticated shop record (e.g., an existing installed session) before trusting it, rather than presenting `process` as fully verifying "the request."

### Proof of Concept
```ruby
# 1. Attacker installs app on their own shop and captures a real webhook delivery:
#    body = '{"id":1,...}'
#    headers = {
#      "x-shopify-topic" => "orders/create",
#      "x-shopify-hmac-sha256" => "<valid-base64-hmac-for-body-using-shared-secret>",
#      "x-shopify-shop-domain" => "attacker.myshopify.com",
#    }

# 2. Attacker replays identical body + hmac header to the victim app's webhook
#    endpoint, only changing the shop-domain header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# 3. Passes verification because HMAC only covers `body`, not the shop header:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Handler now receives forged shop identity:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(body), ...))
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
