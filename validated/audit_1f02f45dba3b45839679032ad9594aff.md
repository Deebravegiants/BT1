### Title
`StateMachine` Display/FromStr roundtrip collapses distinct non-UTF8 chain identifiers to the same wire string, enabling state-machine identity collision on dispatch/decode - ([File: modules/ismp/core/src/host.rs])

### Summary
`StateMachine::Substrate`, `StateMachine::Tendermint`, and `StateMachine::Relay` carry raw 4-byte consensus/chain identifiers. When these are rendered to the canonical wire string used for cross-chain dispatch (via `Display`), any identifier that is not valid UTF-8 is silently collapsed to the literal placeholder bytes `"XXXX"` instead of being rejected or uniquely encoded, and the resulting string is what actually gets embedded, hashed, and later re-parsed on the receiving side.

### Finding Description
`impl Display for StateMachine` renders `Substrate`, `Tendermint`, and `Relay` variants by attempting `String::from_utf8` on the raw 4-byte id and falling back to the literal string `"XXXX"` on failure: [1](#0-0) 

This `to_string()` output is not merely a debug/log representation — it is the actual wire encoding used for `source`/`dest` fields when converting `router::PostRequest`/`GetRequest` into the Solidity ABI types dispatched to `EvmHost`/`HandlerV2`, and the bytes committed/hashed as part of the request: [2](#0-1) 

On the receiving/decoding side, the same string is parsed back with `FromStr for StateMachine`, which reconstructs a `[u8; 4]` id directly from the string's ASCII bytes: [3](#0-2) [4](#0-3) 

This is the same bug class as ALPINE-CVE-2019-12290: a lossy encode→decode roundtrip where the decoded identity does not match the original input, permitting one identifier to be confused with (or impersonate) another. Here, any `StateMachine::Substrate`/`Tendermint`/`Relay` id whose 4 raw bytes are not valid UTF-8 is rendered identically to the id `*b"XXXX"` — a real, parseable, and legitimately assignable 4-byte ASCII chain identifier. Two semantically distinct state machines (one carrying arbitrary non-UTF8 bytes, one legitimately named `"XXXX"`) become indistinguishable once serialized to the wire string, and `from_str` will resolve the collapsed string back to `StateMachine::Substrate(*b"XXXX")`/`Tendermint(*b"XXXX")`/`Relay{relay:*b"XXXX",...}` regardless of which id produced it. The existing code comment even acknowledges the collapse ("Invalid byte sequence will result in a default state machine id") but only reasons about the message becoming "invalid and undeliverable" for the *originating* id — it does not consider that the collapsed string can collide with, and be delivered as, a *different, legitimately configured* chain identifier.

### Impact Explanation
Any component that constructs a `StateMachine::Substrate`/`Tendermint`/`Relay` value from raw, attacker- or relayer-influenced bytes (e.g., decoding `PostRequestEvent`/`GetRequestEvent` fields relayed from an EVM chain, or constructing dispatch requests where the consensus/parachain id bytes are not validated as UTF-8 ASCII) and later serializes it via `Display`/`to_string()` for cross-chain dispatch risks having the message routed, verified, or accepted as originating from/destined to the unrelated chain identified by the literal string `"XXXX"` (e.g., `SUBSTRATE-XXXX`, `TNDRMINT-XXXX`, `RELAY-XXXX-<para_id>`) if such a state machine is ever configured on the network. This can lead to forged message delivery/misrouted commitments (a message intended to be undeliverable or attributed to one chain instead resolving to another chain's identity), which affects the integrity of ISMP message routing between `EvmHost`/`HandlerV2` and `pallet-ismp` consensus clients.

### Likelihood Explanation
The likelihood is constrained: legitimate deployments choose ASCII, human-readable 4-byte identifiers (e.g. `hybr`, `CENJ` as seen in the codebase's own tests), so under normal operation both source and destination identifiers are valid UTF-8 and the collapse path is never hit. Exploitation requires (a) a code path that constructs a `StateMachine` value from raw, non-UTF8-validated 4-byte input under attacker/relayer influence, and (b) the network having (or an attacker being able to register) a state machine actually keyed as `"XXXX"`. I could not confirm within the available context whether any dispatch path constructs `StateMachine::Substrate/Tendermint/Relay` from unvalidated raw bytes rather than from a previously-validated string (the searches show `from_str` is the only reconstruction path found, and it already rejects malformed-length inputs per the `from_str_rejects_non_four_byte_consensus_ids` test) — so the primary exploitable point (an untrusted byte source bypassing `from_str`) is unverified.

### Recommendation
Make the `Display`/`to_string()` encoding injective for all inputs instead of collapsing on invalid UTF-8: use a hex-encoded or otherwise unambiguous representation for `Substrate`/`Tendermint`/`Relay` ids whenever the raw bytes are not valid printable ASCII, rather than the shared placeholder `"XXXX"`. Additionally, ensure `from_str` rejects the literal placeholder string `"XXXX"` (or any reserved sentinel) so a legitimately-configured chain can never be assigned an id that collides with the fallback, and audit all call sites that build `StateMachine` values from raw byte sources to confirm they reject non-ASCII/non-UTF8 ids at construction time rather than relying on the display fallback.

### Proof of Concept
1. Construct `let victim = StateMachine::Tendermint(*b"XXXX");` — a legitimately configured chain that a deployment could register (any 4 ASCII bytes are valid, as shown by the existing `state_machine_conversions` test using `*b"hybr"`).
2. Construct `let malicious = StateMachine::Tendermint(*b"\xf0\x28\x8c\xbc");` — as already exercised in `invalid_state_machine_conversions`, `malicious.to_string()` yields `"TNDRMINT-XXXX"`, identical to `victim.to_string()`: [5](#0-4) 
3. Both `victim.to_string()` and `malicious.to_string()` round-trip through `StateMachine::from_str` to the exact same value, `StateMachine::Tendermint(*b"XXXX")`: [6](#0-5) 
4. Any message whose `source`/`dest` is serialized through `PostRequest`/`GetRequest`'s `From<router::PostRequest>` conversion (`value.source.to_string().into_bytes()`) and later reconstructed via `TryFrom<PostRequest> for router::PostRequest` (`StateMachine::from_str(...)`) is therefore unable to distinguish the two originating identities once encoded on the wire: [7](#0-6) [4](#0-3)
