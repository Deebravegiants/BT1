### Title
Webhook shop-domain header is trusted for tenant attribution without being covered by the HMAC signature — cross-tenant webhook spoofing (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop` value that is subsequently handed to the application's webhook handler for tenant attribution is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material. Any request whose body/HMAC pair is valid (e.g., replayed from a legitimately received webhook) can be resubmitted with an arbitrary `shop-domain` header, causing the handler to process the payload as belonging to a shop it never came from.

### Finding Description
The binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler`

In `lib/shopify_api/webhooks/request.rb`:
```ruby
def to_signable_string
  @raw_body
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [1](#0-0) 

`to_signable_string` — the value fed into `HmacValidator` — is exactly `@raw_body`; the `shop-domain` header is read completely independently and is not part of the signed bytes.

In `lib/shopify_api/webhooks/registry.rb`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` only re-derives the HMAC from `verifiable_query.to_signable_string` (the raw body) and compares it to the header-provided `hmac-sha256` value:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

Because `shop` is never part of the signed string, the equality "shop verified" vs. "shop acted on" does not actually hold — an attacker who possesses any one previously-observed valid `(raw_body, hmac)` pair for the app (trivially obtainable since they can install the app on their own shop and capture the webhook Shopify sends them) can resend that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` still passes (it never looked at the header), and `Registry.process` forwards `shop: request.shop` — now attacker-chosen — straight into `WebhookMetadata`, which is what the app uses to decide which tenant's data the payload applies to.

### Impact Explanation
This breaks the tenant boundary the app relies on to attribute inbound webhook data to the correct shop, which maps to the "cross-tenant access" Critical-impact category in scope: an attacker can cause a webhook payload legitimately belonging to their own shop to be processed by the host application as if it belonged to a different, arbitrary shop domain, without ever needing `api_secret_key`, an access token, or any other credential — they only need one genuine webhook sample from their own installation of the app plus the ability to POST to the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who can install (or has installed) the target app on a shop they control: they merely capture one legitimate webhook delivery (any topic) to get a valid `(body, hmac)` pair, then replay it with a forged `shop-domain` header. No secret material or privileged access is required, and the webhook endpoint is, by design, publicly reachable so Shopify's servers can deliver to it.

### Recommendation
Bind the shop identity into the verified material, e.g., include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the string that is HMAC-verified, or independently verify that the `shop` a webhook claims to be for corresponds to a shop that has this specific webhook subscription/topic registered (e.g., cross-check against stored webhook registrations for that shop/topic) before invoking the handler with attacker-controlled tenant metadata.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook topic the app subscribes to; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this pair is valid because `HmacValidator` only signs the body:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
```
3. Resend the exact same body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it never inspects the shop header:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
5. The handler receives `shop: "victim-shop.myshopify.com"` and processes attacker-supplied data attributed to the victim tenant.
