Based on the investigation, the strongest matching analog in the Hyperbridge codebase is a missing zero-address check in the `UpdateParams` governance-message handler of `IntentGatewayV2`, which is the direct counterpart of `Token.sol`'s `updateFounders` failing to reject a zero-address founder.

### Title
Missing zero-address validation on `UpdateParams` governance message lets `_params.host`/`_params.dispatcher` be bricked, freezing escrowed intent funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.onAccept` applies a Hyperbridge-delivered `UpdateParams` message directly to storage — `_params = update.params;` — with no call to the same `_validateParams` routine that `initialize` uses to reject zero addresses for critical fields (`host`, `dispatcher`, `priceOracle`). This is the same bug class as the reported `Token.updateFounders`: a privileged config-mutation path omits the zero-address guard that a sibling initializer already enforces.

### Finding Description
`initialize` validates params before storing them: [1](#0-0) 

But the cross-chain `UpdateParams` handler, reachable from any correctly-authenticated Hyperbridge governance POST, assigns the decoded struct straight into `_params` without re-running that validation: [2](#0-1) 

`_params.dispatcher` and `_params.host` are load-bearing for every subsequent order flow: `host()` returns `_params.host` and is used to resolve `IDispatcher(hostAddr)` for fee/message dispatch throughout `placeOrder`, `fillOrder`, `cancelOrder`; `_params.dispatcher` is used by `_execute` to run output calldata: [3](#0-2) 

If a `ParamsUpdate` body carries `host == address(0)` or `dispatcher == address(0)` — whether from a governance encoding mistake or any bug upstream in the pallet that constructs it — the contract accepts it unconditionally, since only the message source (`keccak256(incoming.request.source) == hyperbridge`) is checked, not the field values.

### Impact Explanation
Once `_params.host` (or `_params.dispatcher`) is zeroed, every subsequent `placeOrder`/`fillOrder`/`cancelOrder` call that depends on `host()` or the dispatcher either reverts or behaves incorrectly (a call to `address(0)` for `IDispatcher`/`ICallDispatcher` silently "succeeds" with empty return data instead of performing the intended action). This permanently strands all tokens already escrowed in `_orders[...]` for pending intents (a route becomes unable to deliver/process messages, and escrowed funds become permanently frozen), matching the "permanent freezing of funds" / "route unable to deliver messages" acceptance criteria.

### Likelihood Explanation
The path is reachable purely from a correctly-authenticated relayed Hyperbridge POST request — no admin/governance key compromise is required to reach the code, only a malformed/zero-valued `ParamsUpdate` payload getting through, which the contract itself should — but currently does not — reject, unlike `initialize`, which explicitly calls `_validateParams`.

### Recommendation
Call the same `_validateParams(update.params)` (or an equivalent check that rejects `address(0)` for `host`, `dispatcher`, and `priceOracle`) inside the `UpdateParams` branch of `onAccept` before assigning `_params = update.params`, mirroring the guard already present in `initialize`.

### Proof of Concept
1. Governance dispatches a `RequestKind.UpdateParams` POST with `update.params.host = address(0)` (or `dispatcher = address(0)`), correctly sourced from the configured `hyperbridge` id.
2. `onAccept` passes the source check, decodes the body, and executes `_params = update.params;` with no field validation, per [4](#0-3) .
3. Any outstanding escrowed order (from prior `placeOrder` calls) can no longer be filled or cancelled because `host()`/`IDispatcher(host())` calls now target the zero address, permanently locking the escrowed tokens in the contract.

Note: this was confirmed against the Tron variant of `IntentGatewayV2.sol`; I was not able to fully re-verify within this session whether the primary EVM `IntentsBase`/`ExtrinsicIntents` `onAccept` implementation contains an equivalent `_validateParams` call for the `UpdateParams` branch — if it does have that check, the analog is confined to the Tron contract copy.
