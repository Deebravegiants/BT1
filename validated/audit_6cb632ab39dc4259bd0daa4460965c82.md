Confirmed: `Request#to_signable_string` (used by `HmacValidator.validate`) returns only `@raw_body`, and `shop` is read straight from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header, never included in the HMAC input.### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `Request#to_signable_string` — i.e. `@raw_body` only. The `shop` attribute that the gem hands to the app's `WebhookHandler#handle` (as `WebhookMetadata#shop`) is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header and is never included in the signed material.

### Finding Description
`Registry.process` is the sole authentication gate for inbound webhooks: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate`, which compares `verifiable_query.hmac` against a signature computed over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `Request#to_signable_string` returns only the raw body, while `Request#shop` is parsed straight out of the (attacker-controlled-at-the-HTTP-layer) header, with no cryptographic binding between the two: [3](#0-2) 

The unauthenticated `shop` value is then passed unmodified into `WebhookMetadata`, which is exactly what the host application's handler is documented to trust as "The shop domain of the webhook": [4](#0-3) [5](#0-4) [6](#0-5) 

The broken identity binding, as an equality that should hold but does not:
`shop_covered_by_hmac == shop_delivered_to_handler`
Before the request: both would be `shop_A` if bound correctly. After an attacker (who legitimately received one real webhook for their own installed shop, `shop_A`, with a valid `raw_body`/HMAC pair signed by the app's shared `api_secret_key`) replays that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header with `shop_B` (a victim tenant), `HmacValidator.validate` still returns `true` because the signature only covers `raw_body`, and the handler receives `data.shop == "shop_B"` for a payload that was never sent by Shopify on behalf of `shop_B`.

### Impact Explanation
Because `api_secret_key` is the same for every shop that installs a given app, any shop that has installed the app can obtain a validly-HMAC'd body (via any real webhook delivery), then replay that request with an arbitrary victim `shop-domain` header. Since the gem is the layer responsible for extracting and vouching for shop identity via `Registry.process`/`WebhookMetadata`, and its own documentation directs host applications to trust `data.shop` as "the shop domain of the webhook," this results in cross-tenant data confusion at the boundary the gem is expected to secure: actions such as `orders/create`, `app/uninstalled`, or the mandatory `customers/data_request`/`customers/redact`/`shop/redact` topics can be attributed to, and processed against, a shop that never sent the corresponding data.

### Likelihood Explanation
Exploitation only requires an unprivileged attacker who can install the target app on any shop they control (a normal, unprivileged workflow for public/embedded Shopify apps) and can freely craft raw HTTP headers when replaying the captured request to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim shop is required.

### Recommendation
Include the shop domain (and other routing-relevant headers such as topic/api-version) in the signable string used for HMAC verification, or otherwise cryptographically bind the `shop-domain` header to the signed body before it is surfaced to the handler in `WebhookMetadata`. At minimum, `Registry.process` should validate that the shop asserted by the header corresponds to a shop for which the app has actually registered/expects this webhook topic, and Shopify's documented webhook-verification guidance (verifying the full raw request, not just the body) should be followed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook (e.g. `orders/create`), capturing the exact `raw_body` and its `x-shopify-hmac-sha256` value.
2. Attacker POSTs the same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body's HMAC: [7](#0-6) 
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, causing the host app to act on behalf of `victim-shop.myshopify.com` using data that was never sent for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
