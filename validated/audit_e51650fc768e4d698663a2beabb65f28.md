## Title
Webhook `shop` identity is not cryptographically bound to the HMAC-signed payload, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`) values that are handed to the app's webhook handler are read from HTTP headers that are never included in the signed material. Because the HMAC secret (`api_secret_key`/`client_secret`) is shared across *every* shop that has installed the app, a valid `(raw_body, hmac)` pair obtained from one tenant's own legitimate webhook delivery remains valid when replayed with a different `shop-domain` header, letting an attacker impersonate another merchant's shop in the handler's eyes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` only checks that `hmac == HMAC(secret, to_signable_string)`, i.e. it verifies the body bytes, never the header set: [3](#0-2) 

`Registry.process` treats a successful HMAC check as authenticating everything in `request`, including `request.shop`, and forwards that trusted-looking value straight to the app's handler: [4](#0-3) 

The broken identity binding, stated as an equality that the gem fails to enforce:

`HMAC_valid(raw_body) ⇒ shop_header == shop_that_actually_generated(raw_body)`

This equality does not hold, because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, identical for all shops that installed the app — it is not shop-specific. Any bytes+signature pair legitimately produced for shop A's webhook delivery therefore also verifies successfully when the delivery is replayed with shop B's `x-shopify-shop-domain` header, since the validator never looks at that header at all.

### Impact Explanation
An unprivileged internet user who has installed the app on their own shop (attacker-controlled tenant) can:
1. Trigger a legitimate webhook for their own shop (e.g., create/update a resource) to obtain a `(raw_body, hmac)` pair that is valid under the app's shared secret.
2. Replay that exact body+HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain.
3. `Registry.process` passes HMAC validation (it only checks the body) and constructs `WebhookMetadata` with the attacker-controlled `shop` value, which host applications generally trust as the tenant identifier to look up sessions/records and apply the payload.

This is a cross-tenant confusion vector at the identity-binding layer inside this gem's webhook verification primitive — it can cause the host app to attribute attacker-influenced webhook data/events to another merchant's tenant.

### Likelihood Explanation
Requires only that the attacker run the target app on their own (attacker-owned) shop — a normal, unprivileged install — and be able to trigger at least one webhook delivery for content they control, plus the ability to POST to the app's public webhook endpoint with custom headers. No secrets, tokens, or privileged access are needed.

### Recommendation
Bind the shop identity into the verified material, e.g. include the `x-shopify-shop-domain` (and topic) header values in the HMAC input, or independently corroborate `request.shop` against a shop known to be associated with the specific webhook subscription/session before handing `WebhookMetadata` to handlers, rather than trusting an unauthenticated header once the raw-body HMAC passes.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., updates a product) causing Shopify to deliver a webhook: `raw_body = B`, `x-shopify-hmac-sha256 = H = HMAC(app_secret, B)`, `x-shopify-shop-domain = attacker.myshopify.com`.
3. Attacker POSTs the same `B` and `H` to the app's webhook route, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only checks presence, not shop match) — `lib/shopify_api/webhooks/request.rb:45-63`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(app_secret, B)` and compares to `H` — succeeds because it never inspects the shop header — `lib/shopify_api/utils/hmac_validator.rb:12-31`.
6. `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: parsed(B), ...)` is passed to the app's handler as if it were an authentic webhook from `victim.myshopify.com` — `lib/shopify_api/webhooks/registry.rb:198-199`.
