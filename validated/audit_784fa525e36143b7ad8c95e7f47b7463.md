## Finding: Unbounded recursive SCALE decode of cross-chain calldata in `pallet-hyper-fungible-token`

This is a genuine reachable analog to the CVE-2017-11164 bug class (attacker-controlled input triggers unbounded/uncontrolled recursion leading to stack exhaustion), except here it lives in Hyperbridge's own message-dispatch path rather than in a regex engine.

### Title
Unbounded recursive `Decode` of cross-chain call payload allows stack-exhaustion DoS in `on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`IsmpModule::on_accept` for `pallet-hyper-fungible-token` decodes the attacker-supplied `message.data` field into a `SubstrateCalldata`, then decodes the embedded `runtime_call` bytes with a plain, depth-unbounded `T::RuntimeCall::decode` call: [1](#0-0) [2](#0-1) 

`RuntimeCall` on the Nexus parachain (where this pallet is wired in) recursively nests through pallets such as `Utility`, `Proxy`, and `Multisig` (`Box<RuntimeCall>` / `Vec<RuntimeCall>` fields): [3](#0-2) 

### Finding Description
The codebase already recognizes and defends against exactly this bug class elsewhere: `pallet-call-decompressor` explicitly caps SCALE-decoding recursion with `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)`, and has a regression test proving a naive `Decode` on a 1000-deep nested `Sudo(Sudo(Sudo(...)))` call previously caused stack exhaustion: [4](#0-3) [5](#0-4) [6](#0-5) 

`pallet-hyper-fungible-token`'s `on_accept` handler, however, uses the plain `Decode::decode` with **no depth limit** on `substrate_data.runtime_call`, whose bytes are fully attacker-controlled — they arrive in the ISMP `PostRequest.body`'s ABI-decoded `data` field, sent from any source-chain contract mapped as a valid HFT counterpart. Any account able to trigger a token transfer with calldata (an unprivileged token bridger) can submit a payload that SCALE-encodes deeply-nested `Utility::batch(vec![Utility::batch(vec![...])])` (or `Proxy`/`Multisig`) wrappers, driving the decoder's native call stack to exhaustion.

### Impact Explanation
A WASM/native stack overflow during runtime call decoding is not a graceful `Err` — it traps/aborts execution rather than reverting an extrinsic. Because `on_accept` runs as part of processing an inbound ISMP message during normal block execution (invoked via `pallet_ismp::Pallet::execute`/`handle_unsigned`, reachable by any relayer delivering a proven cross-chain message), a crafted calldata payload can crash block execution/import on every node processing that block, halting the affected parachain — a route becoming unable to deliver messages, and potentially a broader denial of service impacting the token bridge and any in-flight funds.

### Likelihood Explanation
High: the trigger is a single ordinary token-transfer message with an attacker-chosen `data` field, requires no privileged relayer/governance/collator role, and the vulnerable code path executes unconditionally whenever `message.data` is non-empty.

### Recommendation
Replace `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` at `modules/pallets/hyper-fungible-token/src/module.rs:189` with a depth-limited decode (e.g., `codec::DecodeLimit::decode_all_with_depth_limit` using the same bound pattern as `pallet-call-decompressor`), and add a regression test analogous to `decompress_stack_exhaustion_poc` that submits a deeply-nested `Utility`/`Proxy`/`Multisig` call as calldata and asserts a clean decode error instead of a crash.

### Proof of Concept
1. Build a `RuntimeCall::Utility(Call::batch { calls: vec![...] })` nested N times (N large enough to exceed the runtime's stack, e.g. several thousand, mirroring the 1000-deep nesting used in `decompress_stack_exhaustion_poc`) and SCALE-encode it.
2. Wrap it as `SubstrateCalldata { signature: None, runtime_call: <encoded bytes> }`, SCALE-encode, and place it as the ABI `data` field of a `Message` sent via the paired HFT EVM/Substrate contract for a nominal token amount.
3. Relay the resulting ISMP `PostRequest` to the parachain; `on_accept` calls `T::RuntimeCall::decode` on the nested payload, exhausting the stack during decode and aborting block execution — reproducing the same failure the existing `decompress_stack_exhaustion_poc` test demonstrates for the (already-fixed) call-decompressor path.

#[test]
fn decompress_stack_exhaustion_poc() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		use crate::runtime::RuntimeCall;
		use codec::Encode;

		let inner_call = RuntimeCall::System(frame_system::Call::remark { remark: Vec::new() });

		let mut nested_calls =
			RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(inner_call) });

		for _ in 1..1000 {
			nested_calls =
				RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(nested_calls) });
		}

		let encoded = nested_calls.encode();
		let mut buffer = vec![0u8; 1000000];
		let compressed = zstd_safe::compress(&mut buffer[..], encoded.as_slice(), 3).unwrap();
		let final_compressed_call = buffer[..compressed].to_vec();

		let res = pallet_call_decompressor::Pallet::<Test>::decompress_call(
			RuntimeOrigin::none(),
			final_compressed_call.to_vec(),
			encoded.len() as u32,
		)
		.err()
		.unwrap();

		assert_eq!(
			res,
			DispatchError::Module(ModuleError {
				index: 10,
				error: [3, 0, 0, 0],
				message: Some("ErrorDecodingCall")
			})
		);
	});
