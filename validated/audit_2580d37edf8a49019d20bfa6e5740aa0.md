## Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC-verified payload from the raw body only, while the `shop` attribute used downstream to attribute the webhook to a tenant is read from an HTTP header that is never part of the signed bytes. This breaks the identity binding `HMAC-covered bytes == attributed tenant`, mirroring the ProposerIndex bug class where a field used for identity attribution is not covered by the cryptographic check that is assumed to validate it.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; the `shopify-shop-domain` / `x-shopify-shop-domain` header used to populate `request.shop` — and later `WebhookMetadata.shop` handed to the app's handler — is read out-of-band and never included in the HMAC computation: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` checks the HMAC using the app's single, shop-independent `Context.api_secret_key` (the same secret is shared across every shop that has installed the app): [5](#0-4) 

Because the signature only binds the raw body and not the shop header, and because the same `api_secret_key` verifies webhooks for *every* shop that installed the app, any user who legitimately controls a shop where the app is installed can:
1. Trigger a real Shopify webhook to their own shop (a body they can partially shape, e.g. via product/order titles, or a re-usable body like `app/uninstalled` with an empty `{}` body as shown in `test/webhooks/registry_test.rb`), obtaining a body+HMAC pair that is valid under the shared secret.
2. Replay that exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but substitute the `shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never looks at the shop header), so `Registry.process` calls the app's handler with `WebhookMetadata.shop` set to the victim's domain and attacker-influenced body.

This is the direct analog of the ProposerIndex bug: the RANDAO signature validated the reveal but never bound it to the specific proposer index, letting an attacker impersonate another proposer; here the HMAC validates the body but never binds it to the specific shop, letting an attacker impersonate another tenant's webhook.

### Impact Explanation
Any host application that trusts `WebhookMetadata.shop` (returned by `Registry.process`, per the documented usage in `docs/usage/webhooks.md`) to select which tenant's data/session to act on is exposed to cross-tenant webhook injection: an attacker-controlled shop can cause the app to process fabricated events "from" an arbitrary victim shop (e.g. spoofing `app/uninstalled` to make the app purge/deactivate a victim's stored access token, or injecting attacker-shaped order/product data attributed to the victim's tenant). This is a cross-tenant identity-binding bypass reachable by any unprivileged Shopify merchant who has installed the same public app — no access token, secret, or privileged account is required.

### Likelihood Explanation
Any user can install a public app on their own store (or use a development store) to legitimately receive Shopify-signed webhooks, then replay the body/HMAC pair with a forged `shop-domain` header at the app's public webhook endpoint. This requires no secrets beyond what a normal merchant already has, no host-application misuse of the documented `Registry.process` API, and directly exploits `Webhooks::Request`/`HmacValidator` as designed in this gem.

### Recommendation
Include the shop domain (and other trust-relevant headers such as `topic`, `webhook-id`, `api-version`) as part of the signed material verified against `Context.api_secret_key`, or alternatively require host applications to independently correlate the attested `shop` header against a shop-specific secret/session record before trusting it. At minimum, document and/or enforce that `WebhookMetadata.shop` must be cross-checked against the recipient's expected shop before being used to select tenant data.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook with a controllable/reusable body (e.g. `app/uninstalled`, body `{}`), capturing the resulting `x-shopify-hmac-sha256` header — this is valid because it's computed with the app's single, shared `api_secret_key`:
   `hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, "{}")` (see `test/webhooks/registry_test.rb` lines 284-296 for the exact construction the gem itself uses in tests).
2. Attacker POSTs to the app's public webhook endpoint with:
   ```
   headers = {
     "x-shopify-topic" => "app/uninstalled",
     "x-shopify-hmac-sha256" => <captured hmac>,
     "x-shopify-shop-domain" => "victim-shop.myshopify.com",
   }
   body = "{}"
   ```
3. `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers))` passes `Utils::HmacValidator.validate` (body-only check succeeds) and invokes the app's `app/uninstalled` handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the request never actually originated from Shopify for that shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
