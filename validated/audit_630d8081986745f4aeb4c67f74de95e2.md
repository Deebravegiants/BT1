### Title
Webhook HMAC covers only the raw body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read straight from unauthenticated request headers and forwarded to the app's handler as trusted metadata, even though none of them are covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` reads the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC passes, then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` taken directly from headers, none of which participated in the signature: [4](#0-3) 

The library's documentation confirms `data.shop` is meant to be trusted and used by the host app (e.g. to route work to the correct shop's job/session), reinforcing that this field is treated as authenticated: [5](#0-4) 

The equality that should hold is: `hmac_valid(raw_body, api_secret_key) == true` implies the request, including the shop it is attributed to, originated from the shop named in the `shop-domain` header. In this implementation the check only proves `hmac_valid(raw_body, api_secret_key) == true`; it proves nothing about which shop actually produced that body. Because a single app's `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app can legitimately trigger a webhook for their own store (e.g. by creating/updating a resource), capturing a validly HMAC-signed body from Shopify. That merchant can then replay the identical body to the app's webhook endpoint while swapping only the unauthenticated `x-shopify-shop-domain` header to name a victim shop. `Registry.process` will accept it (the body's HMAC is unchanged and still valid) and hand the handler `data.shop == "victim-shop.myshopify.com"` paired with attacker-controlled `data.body` content.

### Impact Explanation
This breaks the identity binding between the authenticated bytes (body) and the tenant identity the app acts on behalf of (`shop` header), enabling a form of cross-tenant request forgery: an attacker with only their own (unprivileged) shop installation can make the host application process attacker-influenced webhook payloads attributed to another merchant's shop. Depending on how the host app's handler uses `data.shop` (looking up the victim's session/access token, writing to the victim's local records, queuing shop-scoped background jobs, etc., exactly as shown in the gem's own documented example), this can lead to cross-tenant data corruption or unauthorized cross-tenant actions performed under the victim shop's identity.

### Likelihood Explanation
Exploitability requires only an unprivileged attacker to install the target app on their own store (a normal, permitted action), trigger a webhook-generating event with content they control (subject to `fields`/`filter` registration constraints), capture the raw POST, and resend it to the app's public webhook endpoint with a modified `shop-domain` header. No access token, `client_secret`, or privileged account is needed — the app's `api_secret_key` is shared across all installs, so the signature stays valid across the header swap.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or independently verify that the `shop-domain` header corresponds to a shop with an active app installation/session known to the host app before dispatching to the handler, rather than trusting the header purely on the strength of a body-only HMAC.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a subscribed webhook topic (e.g. `products/update`) with attacker-chosen field values, causing Shopify to POST a body `B` with a valid `x-shopify-hmac-sha256` header (signed with the app's shared `api_secret_key`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture this request, then replay it to the app's webhook endpoint unmodified except for the header `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `B` and matches the untouched signature, so the check passes.
5. The registered handler executes with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to process attacker-controlled content as if it originated from the victim shop.

```ruby
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```
