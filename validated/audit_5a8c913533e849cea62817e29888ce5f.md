### Title
Unauthenticated TCP connection to livestream Upstream causes biometric camera frames to be streamed via UDP to attacker-controlled IP - ([File: src/agents/livestream/mod.rs])

### Finding Description
`Upstream::new` binds a `TcpListener` on `0.0.0.0:9201` with no authentication of any kind [1](#0-0) . Any TCP client that connects yields `Event::Connected(addr)` from `Upstream::poll_next` purely based on `listener.poll_accept` succeeding, with no credential check [2](#0-1) . In `Agent::run` (the `agentwire::agent::Thread::run` impl for the livestream agent), this event unconditionally creates a new `Downstream` bound to the connecting socket's IP and stores it in `downstream` [3](#0-2) . `Downstream::new` builds a GStreamer pipeline whose `udpsink` is configured with `host = addr.to_string()` and a fixed `port = 9200`, i.e., the attacker's own IP [4](#0-3) . Whenever the broker forwards `Input::IrEyeFrame`/`IrFaceFrame`/`RgbFrame`/etc. (via `handle_ir_eye_camera`, `handle_ir_face_camera`, `handle_rgb_camera` in `src/brokers/orb.rs`), the frames are rendered by `gpu.render` and pushed to the currently connected `downstream` over UDP [5](#0-4) . There is no pairing, token, or backend-authorized allow-list check anywhere in this path.

However, this entire attack surface only exists when the `livestream` cargo feature is compiled in and the operator explicitly enables it at runtime via the `-l/--livestream` CLI flag [6](#0-5) , which in turn calls `orb.enable_livestream()` and starts the RGB camera, as seen in the `livestream`-only path in `src/bin/health-check.rs` [7](#0-6) . The `livestream` feature and its comment explicitly frame it as a debugging tool: "Enable livestream agent to debug cameras" [8](#0-7) . Camera frames are only routed into the `livestream` agent at all when `self.livestream.enabled()` is `Some`, i.e., when the agent was started via this explicit operator/developer opt-in [9](#0-8) .

### Impact Explanation
If an operator/developer has enabled livestream debugging mode (`-l` flag) during a real signup — e.g. on a staging/dev Orb, since `stage` feature enables `livestream` by default (`stage = [... "livestream" ...]`) but the runtime port only opens the agent thread and listener when `enable_livestream()` is invoked — any unprivileged device on the local network can connect to TCP port 9201 without credentials and hijack the video destination, causing raw IR/RGB/thermal/depth biometric frames of the person currently being enrolled to be streamed via UDP to the attacker's chosen IP:9200. This is a genuine biometric data disclosure to an unauthorized destination, matching a "sensitive data exposure" / "biometric data disclosure" bounty category.

### Likelihood Explanation
The vulnerability is fully reachable and trivially reproducible (a single TCP connect) whenever the livestream feature is compiled in AND the operator/developer has explicitly started the Orb with `--livestream`. This is not the default production runtime behavior — it requires an explicit operator/debug opt-in flag, which substantially narrows real-world likelihood on production Orbs. On any deployment where this debug flag is active (e.g., stage/dev builds used for testing with real signups on a shared local network), the exploit is 100% reliable with no authentication bypass needed, since none exists.

### Recommendation
Add authentication to the `Upstream` TCP listener (e.g., a pre-shared token or mutual TLS) before accepting a connection and creating a `Downstream`; alternatively restrict the listener to loopback/localhost or a specific trusted operator subnet by default, and require an explicit pairing handshake (e.g., a signed nonce) before `Event::Connected` is allowed to instantiate a new `Downstream` and start pushing frames. At minimum, the livestream feature should never be enabled in production builds and should log/alert when accepting connections from unexpected addresses.

### Proof of Concept
Integration test plan:
1. Start `Upstream::new()` bound to `0.0.0.0:9201` (as done in `Agent::run`).
2. From a separate test TCP socket bound to an arbitrary "attacker" loopback alias IP, connect to port 9201.
3. Assert that `Upstream::poll_next` yields `Event::Connected(addr)` with `addr` equal to the attacker socket, with no credential exchanged.
4. Simulate `Agent::run` receiving `Input::RgbFrame`/`IrEyeFrame` and confirm `Downstream::new(addr.ip())` is constructed and `gpu.render` invokes `downstream.push`, i.e., that the resulting GStreamer `udpsink` `host` property equals the attacker's IP and `port` equals `9200`.
5. Expected (failing) assertion demonstrating the bug: frames are pushed to the attacker's address without any authentication step; a fixed version should reject `Event::Connected` or require a successful pairing/authentication exchange before creating `Downstream`.
