## Analysis

The reachable analog to the phpseclib ASN1 length-guardrail bug (CVE-2024-27355 — a length field read straight off untrusted, unvalidated input is used to drive an unbounded loop/allocation) exists in the Pharos consensus verifier's validator-set state-proof decoding path.

### Title
Unbounded loop/allocation driven by unvalidated BLS string-length header in Pharos validator-set proof verification - (File: `modules/consensus/pharos/verifier/src/state_proof.rs`)

### Summary
`compute_all_storage_keys` derives a per-validator BLS "data slot count" from `storage_values[idx]` — a byte string supplied by the relayer in the proof — via `bls_data_slots_from_header`, and does this **before** those values are checked against the state root by `verify_all_storage_proofs`. The derived count is then used, unbounded, as a loop count in `get_validator_keys`.

### Finding Description
`bls_data_slots_from_header` treats the header slot as a Solidity long-string length encoding (`(header_value - 1) / 2`), truncates to `u64`, and returns `slots_needed = (str_len + 31) / 32` with no upper bound: [1](#0-0) 

`compute_all_storage_keys` calls this on the *unverified* `storage_values` array (verification against `state_root` happens afterward, in `verify_all_storage_proofs`) and feeds the resulting `data_slots` count directly into `layout.get_validator_keys`: [2](#0-1) 

`get_validator_keys` then loops `bls_data_slot_count` times with no bound at all, pushing a hash into a `Vec<H256>` each iteration: [3](#0-2) 

Because `header_value` is a raw `U256` read straight from an attacker-supplied `storage_values[idx]` entry (`decode_u256_from_storage`), `str_len` can be crafted up to `~2^64`, giving `slots_needed ≈ 5.76e17`. Nothing bounds this before `get_validator_keys` iterates that many times constructing and pushing hash values — an unbounded compute/memory loop over completely unauthenticated data, exactly the CWE-400 class in the phpseclib advisory (an OID/length field parsed before any authentication is used to drive unbounded work).

Contrast this with the one guard that does exist for the same value later in `decode_bls_key_from_string_slot`, which bounds `slots_needed` against the caller-supplied `data_slots.len()` — but that check happens only in the *second* consumer of this value, after the keys have already been generated and the proof step has already run: [4](#0-3) 

The `MAX_VALIDATORS` bound only limits the outer count of validators (4096), not the per-validator BLS data-slot count computed from the header: [5](#0-4) [6](#0-5) 

### Impact Explanation
`verify_validator_set_proof` — which calls `compute_all_storage_keys` first — is the entry point used to verify Pharos validator-set updates as part of consensus-state verification, driven by relayer-submitted proofs. An unprivileged relayer can submit a crafted `ValidatorSetProof` whose `storage_values` contain a bogus BLS-header slot with an inflated length, forcing up to ~5.7×10^17 loop iterations and unbounded `Vec<H256>` growth per validator entry (multiplied by up to `MAX_VALIDATORS` = 4096 validators) before any cryptographic check of those values takes place. This can hang or exhaust memory on any node (light client, relayer, or on-chain verifier) attempting to validate the Pharos consensus update, effectively denying delivery of Pharos state/consensus updates through Hyperbridge — a route rendered unable to deliver messages.

### Likelihood Explanation
High: the crafted length lives in a field that is only checked for internal consistency (`data_slots.len() < slots_needed`) inside a *different, later* function (`decode_bls_key_from_string_slot`), not in the key-derivation path where the unbounded loop actually executes. No signature, staking-contract control, or governance access is required — only the ability to submit a Pharos consensus/validator-set proof, which is the normal unprivileged relayer action.

### Recommendation
Bound `bls_data_slots_from_header`'s returned `slots_needed` (and therefore `data_slots` used in `compute_all_storage_keys`/`get_validator_keys`) to the maximum number of slots a legitimate 96/98-character BLS key string could ever require (i.e., cap at 4 slots) before it is used to size any loop or allocation, rejecting the proof outright if the header claims more.

### Proof of Concept
1. Construct a `ValidatorSetProof` with `storage_values[1]` = a small valid validator count (e.g. 1) so it passes the `MAX_VALIDATORS` check.
2. For the single validator's BLS header slot value, set the raw bytes to encode `header_val = odd, huge` (e.g., set the low bit and make the value close to `U256::MAX`), so `decode_u256_from_storage` returns a huge value and `bls_data_slots_from_header` computes `str_len ≈ 2^64 - 1`, giving `slots_needed ≈ 5.76e17`.
3. Submit this proof (with any filler for `storage_proof`) to `verify_validator_set_proof`.
4. `compute_all_storage_keys` calls `bls_data_slots_from_header` on the still-unverified header value and then `layout.get_validator_keys::<H>(&pool_id, data_slots)`, which begins looping `slots_needed` times — well before `verify_all_storage_proofs` ever runs to catch the forged value — hanging/exhausting memory on the verifying node.

	pub fn get_validator_keys<H: Keccak256>(
		&self,
		pool_id: &H256,
		bls_data_slot_count: usize,
	) -> Vec<H256> {
		let offsets = ValidatorStructOffsets::default();
		let mut keys = Vec::new();

		// BLS public key string slot (stores length for long strings)
		let bls_string_slot = self.validator_field_slot::<H>(pool_id, offsets.bls_public_key);
		keys.push(bls_string_slot);

		// BLS public key data slots (for long strings)
		// Data is stored at keccak256(string_slot) for `bls_data_slot_count` slots
		let bls_data_base = self.string_data_slot::<H>(&bls_string_slot);
		let bls_data_base_pos = U256::from_big_endian(bls_data_base.as_bytes());
		for i in 0..bls_data_slot_count {
			let slot_pos = bls_data_base_pos + U256::from(i);
			keys.push(H256(slot_pos.to_big_endian()));
		}

		// totalStake field
		keys.push(self.validator_field_slot::<H>(pool_id, offsets.total_stake));

		keys
	}

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
