### Title
Webhook HMAC only signs the raw body while `shop-domain`, `topic`, `api-version`, and `webhook-id` are trusted unauthenticated, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `Utils::HmacValidator.validate` binds solely to the JSON body [1](#0-0) . Every other value the registry trusts and forwards to the app's handler — `shop`, `topic`, `api_version`, and `webhook_id` — is read directly from HTTP headers that are never part of the signed payload [2](#0-1) .

### Finding Description
`Registry.process` validates the request with `Utils::HmacValidator.validate(request)`, then dispatches to the handler using `request.topic`, `request.shop`, `request.parsed_body`, `request.api_version`, and `request.webhook_id` [3](#0-2) . `HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header value [4](#0-3) . Since `to_signable_string` for a webhook request is just the raw body, the signature says nothing about which shop, topic, api version, or webhook id the body is claimed to belong to.

This breaks the intended identity binding: `hmac(body) == valid` should imply `(shop, topic) == what Shopify actually sent`, but the implementation only proves `hmac(body) == valid`, while `shop` and `topic` are asserted, unauthenticated header values `shopify-shop-domain` / `x-shopify-shop-domain` and `shopify-topic` / `x-shopify-topic` [5](#0-4) .

### Impact Explanation
Any body + HMAC pair that was ever legitimately signed by Shopify for the app's `client_secret` (e.g., a webhook the attacker's own store received after installing the app) remains valid forever for that exact byte sequence, regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it, because those fields are excluded from `to_signable_string`. Since `client_secret` is shared across every shop that installs the app, an attacker who is a normal, unprivileged installer of the app can capture one authentic signed webhook body sent to their own store and resubmit it to the app's public webhook endpoint with a different `shopify-shop-domain` header. The registry's HMAC check still passes, and `WebhookMetadata` is built with the attacker-chosen `shop` [6](#0-5) , so the host application's handler executes attacker-controlled body content attributed to a victim shop it has no relationship to — a cross-tenant data/action confusion.

### Likelihood Explanation
Exploitation only requires being a normal merchant who has installed the app (no special privilege, no leaked secret) and the ability to POST to the app's public webhook route, which by design accepts unauthenticated internet traffic and only relies on this HMAC check for trust [7](#0-6) .

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable content verified by `HmacValidator`, or otherwise cryptographically bind the header-derived metadata to the signed payload before it is trusted by `Registry.process`.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture a legitimate webhook POST (raw body `B`, header `x-shopify-hmac-sha256: H`) delivered by Shopify.
2. Replay the exact same request to the app's webhook endpoint, only changing `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Utils::HmacValidator.validate` recomputes HMAC over the unchanged raw body `B` and matches `H`, so `Registry.process` accepts the forged request and invokes the handler with `shop: "victim.myshopify.com"` and body `B` [8](#0-7) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          received_signature = verifiable_query.hmac
