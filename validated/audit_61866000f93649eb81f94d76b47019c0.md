### Title
Permissionless `CallDispatcher.dispatch()` allows theft of residual tokens/ETH left by HFT/WrappedHFT calldata-execution flows — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` accepts an arbitrary ABI-encoded `Call[]` from *any* caller with no access control, and executes each call in the dispatcher's own context. `HyperFungibleTokenUpgradeable.onAccept`, `WrappedHyperFungibleToken.onAccept`, and `WrappedHyperFungibleTokenUpgradeable.onAccept` mint/unlock bridged tokens to the recipient (which callers set to the `CallDispatcher` address to enable "transfer-and-swap" composability) and then forward `message.data` to `CallDispatcher.dispatch()` — but, unlike `IntentsBase._execute` and `IntentGatewayV2`'s predispatch/postdispatch paths, these HFT/WrappedHFT flows never sweep residual balances back out of the dispatcher afterward. This is directly analogous to the Sorbet Finance/G-UNI router incident, where a contract permitting arbitrary low-level calls left value briefly reachable and MEV searchers extracted $744,000 before it could be routed to its intended destination.

### Finding Description
`CallDispatcher.dispatch()` has no caller restriction at all: [1](#0-0) 

Any account can call it directly (it is not restricted to being invoked only through the HFT/WrappedHFT/IntentGateway flows), and it forwards value/calldata to whatever target the caller specifies, executing in its own storage/balance context.

Interface confirms this is meant to "dispatch untrusted call(s)" with no auth model at the dispatcher level: [2](#0-1) 

`HyperFungibleTokenUpgradeable.onAccept` mints tokens to `beneficiary` (which the docs explicitly instruct users to set to the `CallDispatcher` address so swap calldata can spend them) and then dispatches arbitrary calldata, with **no sweep-back of any leftover balance**: [3](#0-2) 

The same pattern (mint/unlock → dispatch, no sweep) appears in `WrappedHyperFungibleToken.onAccept` and `WrappedHyperFungibleTokenUpgradeable.onAccept`: [4](#0-3) [5](#0-4) 

The documented usage pattern for this calldata field explicitly routes a DEX swap through the dispatcher, e.g. `swapETHForExactTokens`, whose target amount-out is fixed while the ETH input forwarded (`Call.value`) can exceed what the swap consumes — any unspent ETH is refunded by the router to `msg.sender`, which is the `CallDispatcher` itself, not the beneficiary: [6](#0-5) 

By contrast, the intents code paths that use the same shared `CallDispatcher` are careful to sweep every residual balance back out immediately after dispatching untrusted calls, explicitly to prevent exactly this class of leftover-value exposure: [7](#0-6) [8](#0-7) 

Because `CallDispatcher` is a single shared, chain-wide deployment referenced by `_dispatcher`/`_params.dispatcher` across HFT, WrappedHFT, and the Intent Gateway (per the docs: "Existing `CallDispatcher` deployments are listed on the contract addresses page"), any residual token or ETH balance left behind by an HFT/WrappedHFT `onAccept` calldata execution sits in a permissionless, shared contract that any third party can drain in the very next call by invoking `dispatch()` with a `Call` that transfers out the dispatcher's current balance of that asset — with no relationship to the original cross-chain message required.

### Impact Explanation
Any cross-chain transfer that uses the optional calldata-execution feature (`data`/`call_data`) targeting the `CallDispatcher` as recipient and whose downstream call does not consume the entire bridged amount (slippage-bounded swaps, partial spends, approve-only calls, or any call that returns change to `msg.sender`) leaves real economic value sitting in a contract with a fully public, unauthenticated `dispatch()` entrypoint. That value is stealable by any address — including MEV searchers monitoring pending/mempool deliveries — via a single subsequent transaction, exactly mirroring how the Sorbet/G-UNI incident lost $744,000 to MEV because a contract permitting arbitrary low-level calls momentarily held value that legitimate flows had not yet claimed.

### Likelihood Explanation
This is triggerable by any relayer delivering a legitimate, ISMP-proof-backed HFT/WrappedHFT message whose sender opted into calldata execution routing through a DEX or any protocol whose call can leave unconsumed input (a documented, encouraged usage pattern, not a misuse). No privileged role, governance action, or malicious insider is required — an ordinary user's transfer-and-swap message combined with normal swap slippage is sufficient to create the exposure window, and exploitation is a single permissionless call to the shared `CallDispatcher`.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by an approved set of caller contracts (e.g., an `onlyAuthorizedCaller` allowlist of HFT/WrappedHFT/IntentGateway instances), removing the fully public invocation surface.
- Alternatively/additionally, have `HyperFungibleTokenUpgradeable.onAccept`, `WrappedHyperFungibleToken.onAccept`, and `WrappedHyperFungibleTokenUpgradeable.onAccept` sweep any residual token/ETH balance left on the dispatcher back to the intended beneficiary (or emit/refund it), mirroring the dust-sweep pattern already implemented in `IntentsBase._execute` and `IntentGatewayV2`.
- Consider deploying a fresh, single-use `CallDispatcher` instance per cross-chain message (e.g., via `CREATE2`/minimal proxy) so no shared, persistent balance can ever exist between unrelated calls.

### Proof of Concept
1. Deploy/observe an existing `CallDispatcher` shared across `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken` on a destination chain.
2. A legitimate user bridges tokens via `send()` with `to = CallDispatcher` and `data` encoding a `Call[]` that swaps the bridged asset through a router using an "exact-output" style call (e.g. `swapETHForExactTokens`), per the documented pattern in `docs/content/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token.mdx`.
3. A relayer delivers the message; `onAccept` mints/unlocks tokens to the `CallDispatcher`, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`; the swap executes and refunds unspent input (ETH or token change) to `msg.sender`, i.e., the `CallDispatcher`, per `sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol` lines 320-336.
4. No sweep occurs; the leftover balance remains on `CallDispatcher`.
5. Any third party calls `CallDispatcher.dispatch(abi.encode([Call({to: leftoverToken_or_self, value: dispatcher.balance, data: transferCalldata_or_empty})]))` directly — this call is unauthenticated and succeeds per `evm/src/utils/CallDispatcher.sol` lines 44-61 — transferring the leftover balance to the attacker's address.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

     * @param outputsLen The number of output assets to sweep after execution.

        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
