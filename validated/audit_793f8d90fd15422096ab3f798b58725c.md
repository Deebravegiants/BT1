### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable bytes from the raw HTTP body only, while the tenant-identifying `shop`, `topic`, `api_version`, and `webhook_id` fields are read straight from unauthenticated HTTP headers and are never part of what the HMAC covers. Any actor who can obtain one valid `(raw_body, hmac)` pair for their own shop (e.g., a merchant who installs the app and triggers a webhook) can replay that exact body/HMAC while forging the `x-shopify-shop-domain` and `x-shopify-topic` headers to attribute the event to a different shop or topic, since `Utils::HmacValidator.validate` only re-derives the signature over `raw_body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are parsed directly out of attacker-controllable headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which — per `VerifiableQuery`/`HmacValidator` — only checks that `hmac` matches `compute_signature(to_signable_string, secret)`, i.e. only the body bytes: [3](#0-2) 

After that check passes, `Registry#process` routes the handler using the header-derived `request.topic` and constructs `WebhookMetadata` using the header-derived `request.shop`, `webhook_id`, and `api_version` — none of which were authenticated: [4](#0-3) 

The broken binding, stated as an equality that the gem fails to enforce:
`HMAC-covered bytes (raw_body) == bytes acted upon (raw_body + shop + topic + webhook_id + api_version)`

Before the attacker's request: a legitimately-issued webhook has `hmac = HMAC(secret, raw_body)` and headers `shop = ShopA`, `topic = orders/create`, consistent with what Shopify sent.
After the attacker's request: the same `(raw_body, hmac)` pair is replayed with headers rewritten to `shop = ShopB`, `topic = customers/data_request` (or any other registered topic). `HmacValidator.validate` still returns `true` because it never inspects the headers, and `Registry.process` dispatches the (unmodified) body to the handler registered for the forged topic, tagging it with the forged `shop` in `WebhookMetadata`.

### Impact Explanation
This breaks the tenant/topic binding the gem is supposed to guarantee to the host application: the documented contract of `Webhooks::Registry.process` is that a validated request's `shop`/`topic` can be trusted to identify which merchant and event triggered the call. An attacker who has legitimately received one authentic webhook (by installing the app on any shop they control, which is available to any unprivileged internet user) can reuse it to spoof events as coming from an arbitrary other shop or an arbitrary other topic, causing the host app's handler to process attacker-controlled data under a victim tenant's identity — a cross-tenant access primitive.

### Likelihood Explanation
Moderate-to-high: the attacker needs only one authentic webhook delivery from their own store (trivial — install the app, trigger an order/customer event) and control over the headers of the replayed HTTP request to the app's webhook endpoint, both of which are available to any unprivileged actor without needing `api_secret_key` or an access token.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the bytes that are HMAC-verified (or otherwise cryptographically bind them to the raw body before trusting them), so that `Utils::HmacValidator.validate` fails if any of these header-derived fields have been altered relative to what Shopify originally signed.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B`), `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Replay the exact same `B` and `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: <any registered topic>`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B) == H`, as shown in [5](#0-4) .
4. `Registry.process(request)` dispatches to the handler for the forged topic and builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, as shown in [6](#0-5) , even though the body and signature originated from the attacker's own shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
