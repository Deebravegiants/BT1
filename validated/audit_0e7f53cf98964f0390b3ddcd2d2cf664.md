### Title
Webhook HMAC only covers the request body, allowing a replayed webhook to be relabeled with a forged `shop`/`topic`/`webhook-id` and processed as if it belonged to another tenant - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate`/`ShopifyAPI::Webhooks::Registry.process` only check the HMAC over that body. The identity-bearing headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that `Registry.process` hands to the merchant's handler as authenticated `WebhookMetadata` are never included in the signed material, so they can be forged independently of the (legitimately signed) body.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and the shop/topic/webhook-id/api-version accessors simply read attacker-controllable headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` verifies only the HMAC of the `Request` and then forwards the unauthenticated `shop`/`topic`/`webhook_id` fields straight into `WebhookMetadata` given to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` only compares a signature computed from `to_signable_string` (i.e., the raw body) against the received HMAC: [4](#0-3) 

This breaks the identity binding `authenticated(shop) == metadata.shop`: the gem's own documentation claims `process` "will verify the request did indeed come from Shopify," implying the whole request (including its shop/topic identity) is authenticated, but the HMAC only ever protects the body bytes. Because Shopify apps share a single `api_secret_key` across every shop that installs the app, any merchant who installs the app can legitimately receive a genuine `(body, hmac)` pair from Shopify for their own shop, then replay that exact body+HMAC pair to the app's webhook endpoint while substituting `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` calls the handler with `WebhookMetadata.shop` pointing at the victim shop even though the actual signed content originated from the attacker's own shop.

### Impact Explanation
Any application built on this gem that trusts `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) to select the tenant/session context for a write, a data-processing action, or an authorization decision can be made to attribute attacker-controlled webhook content to an arbitrary victim shop. This is a cross-tenant integrity/confusion issue: data nominally belonging to shop A is processed under shop B's identity purely because the gem exposes unauthenticated header values as if they were verified, satisfying the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an ordinary, unprivileged ability to install the target public app on any shop (the normal, unprivileged path any merchant/developer can take), capture one legitimate webhook delivery, and resend it with a modified `shopify-shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the app's `client_secret` is required, matching the rules' unprivileged-internet-user constraint.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the body before exposing them via `WebhookMetadata`, so that `Registry.process` cannot be tricked into reporting a different shop/topic/webhook-id than the one Shopify actually signed.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger a real webhook delivery so Shopify sends `raw_body = B` with header `x-shopify-hmac-sha256 = H` (computed by Shopify using the app's shared `api_secret_key`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same `raw_body = B` and `x-shopify-hmac-sha256 = H` to the app's webhook controller, but set `x-shopify-shop-domain: victim.myshopify.com` (and, if desired, a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only recomputes the HMAC over `raw_body` (see `to_signable_string`), so validation passes.
4. The app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and performs whatever tenant-scoped action it takes on webhook receipt, attributing attacker-supplied data/action to the victim shop.
