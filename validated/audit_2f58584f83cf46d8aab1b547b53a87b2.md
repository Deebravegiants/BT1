Based on my investigation, I found a concrete analog matching the exact bug class described in the rules: **"a field acted on but not covered by the HMAC."**

### Title
Webhook `shop` and `topic` are trusted from unsigned headers while only the raw body is HMAC-covered, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC computed by `HmacValidator` binds solely to `@raw_body`. However, `Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id` — all parsed from HTTP headers that are never part of the signed bytes — and passes them straight into the handler as the tenant identity for the webhook.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. `HmacValidator.validate_signature` computes the HMAC exclusively over that signable string: [2](#0-1) 
Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from mutable HTTP headers with no cryptographic binding: [3](#0-2) 
`Registry.process` validates the HMAC and then unconditionally forwards the header-derived `shop`/`topic` to the handler as the trusted tenant identity: [4](#0-3) 

The equality that should hold but doesn't: `shop_bound_by_hmac == shop_used_by_handler`. In reality, `shop_bound_by_hmac` doesn't exist at all — the signature never covers the shop-domain header — while `shop_used_by_handler` is taken verbatim from `x-shopify-shop-domain`/`shopify-shop-domain`.

Because the webhook HMAC secret (`Context.api_secret_key`, the app's single `client_secret`) is shared across every shop that has installed the same app, an attacker who controls one legitimate shop installation can:
1. Trigger a real webhook delivery to their own endpoint (or otherwise obtain a genuinely-signed `raw_body` + HMAC pair for their own tenant).
2. Replay that exact body/HMAC pair to the merchant application's webhook endpoint, but with `x-shopify-shop-domain` and `x-shopify-topic` headers rewritten to target a different (victim) shop and/or a different topic.
3. `HmacValidator.validate` still returns `true`, because it only checks the untouched raw body, and `Registry.process` will invoke the handler believing the event legitimately originated from the victim's shop/topic.

### Impact Explanation
This breaks the tenant identity binding a webhook consumer relies on: an unprivileged party who has just one legitimate app installation can inject events attributed to a different shop and/or of a different topic than what was actually signed, forging cross-tenant webhook data as processed by any host application built on this gem's exact documented API surface (`Registry.process` → `WebhookMetadata#shop`/`#topic`). This matches the "High/Critical - cross-tenant access" impact category, since the shop field driving tenant-scoped data storage/processing in the handler is fully attacker-controlled despite HMAC validation succeeding.

### Likelihood Explanation
Requires only an unprivileged attacker who can install the same app onto their own store (or otherwise capture one raw webhook body/HMAC pair) and the ability to send arbitrary HTTP requests to the target's public webhook callback URL — no access token, `client_secret`, or privileged account is needed. The `shop`/`topic` headers are trivially forgeable since the library performs no cross-check between them and the signed payload.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string, or otherwise cryptographically bind them (e.g., compute the signature over `headers + body` rather than body alone), so that `HmacValidator.validate` fails if any of these fields are altered in transit.

### Proof of Concept
```ruby
# Attacker has a legitimate install for "attacker-shop.myshopify.com" and
# captures a real webhook delivery: raw_body="{...}" with a valid
# x-shopify-hmac-sha256 signature computed by Shopify using the app's
# single client_secret.

forged_headers = {
  "x-shopify-topic"        => "shop/redact",          # attacker picks any topic
  "x-shopify-hmac-sha256"  => captured_valid_hmac,      # unchanged - still valid, only covers body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id"   => "forged-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true (only checks raw_body)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "shop/redact", ...))
# -> host app processes an event as if it legitimately came from victim-shop.
```
