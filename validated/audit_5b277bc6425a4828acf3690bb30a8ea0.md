### Title
Webhook shop identity spoofing via unbound `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes a webhook solely by verifying the HMAC over the raw request body, then trusts the shop identity from a header that is never covered by that signature. This breaks the same class of binding failure described in the reference report: a value that is *acted upon* (here, the shop that owns the webhook payload) is not the value that was actually *verified*.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are instead read directly from HTTP headers, which are not part of the signable string: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (body only) and compares it against the `hmac-sha256` header using the app's `api_secret_key`: [3](#0-2) [4](#0-3) 

Once the HMAC (computed only from the body) validates, `Registry.process` dispatches to the app's handler passing `shop: request.shop` — a value taken from an unsigned header — as the tenant identity for the webhook payload: [5](#0-4) 

**Binding that should hold:** `shop_bound_by_hmac == shop_used_by_handler`.
**Binding that actually holds:** `hmac_verifies(raw_body) == true`, independent of `shop-domain` header, while `shop_used_by_handler = header["x-shopify-shop-domain"]` (unauthenticated).

An attacker who legitimately installs the app on their own shop receives a genuine webhook with a body and HMAC signed by the real `api_secret_key`. Because the `shop-domain` header is excluded from the signed content, the attacker can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain. `HmacValidator.validate` still succeeds (the signed bytes — the body — are unchanged), and `Registry.process` calls the handler with the attacker-chosen `shop`. Any app that uses `data.shop` for tenant scoping (as documented) will attribute the forged payload to the wrong tenant.

### Impact Explanation
This allows cross-tenant data injection: an attacker-controlled webhook payload (from their own installation) can be replayed and attributed to an arbitrary Shopify shop, since the "shop" identity used by all downstream app logic is never included in what the HMAC actually authenticates. This matches the Critical "cross-tenant access" category — the app processes attacker-supplied data believing it originates from a different merchant's store.

### Likelihood Explanation
Requires only a legitimate installation of the target app on an attacker-controlled shop (to obtain one valid signed body/HMAC pair) and the ability to send an HTTP POST to the app's public webhook endpoint with modified headers — no TLS interception, no leaked credentials, and no privileged account is needed. The gem's documented webhook processing flow (`ShopifyAPI::Webhooks::Registry.process`) is used exactly as intended by host apps.

### Recommendation
Include the shop-identifying header(s) (and topic/webhook-id, to prevent cross-topic replay) in the signable content used for verification, or perform an explicit secondary check that binds the verified body to the specific shop/topic pair before dispatching to the handler — analogous to how `FeeTier::get` in the referenced report binds the token account's actual parsed owner to the expected owner rather than trusting an unverified field.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` header — both valid and signed by the app's real `api_secret_key`.
2. Attacker replays this exact body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the unmodified raw body.
4. The registered handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and processes attacker-supplied data as if it were sent by the victim shop, corrupting or polluting per-tenant application state that trusts `data.shop`.
