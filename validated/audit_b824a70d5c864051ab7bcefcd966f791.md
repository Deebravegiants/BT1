### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the shop identity (`X-Shopify-Shop-Domain` / `shopify-shop-domain` header) is read separately and passed to webhook handlers unauthenticated. This breaks the equality "bytes verified == bytes that determine tenant identity," letting a party who legitimately receives correctly-signed webhooks for their own shop relay them to the app with a different `shop` value and have the app process the event as belonging to another (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate header that is never mixed into the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (the body), and `Webhooks::Registry.process` gates only on that check before forwarding `request.shop` to the handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `hmac-verified bytes == bytes that determine tenant (shop)`. Here it does not — the HMAC only authenticates that the *body* was produced by a holder of `api_secret_key` (i.e., Shopify, on behalf of the app), but the `shop` (tenant) attribution comes from an unauthenticated header. All shops that install the same app share the same `api_secret_key`, so any tenant that has legitimately installed the app can obtain a validly-signed `(raw_body, hmac)` pair for their own store (e.g. from an `orders/create` webhook Shopify sends them), and then re-POST that exact body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header replaced by an arbitrary victim shop domain. `HmacValidator.validate` will still succeed (the body/HMAC pair is unmodified and genuinely signed), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
Any application-level logic that keys tenant-scoped actions off `WebhookMetadata#shop` (session/store cleanup on `app/uninstalled`, GDPR data deletion scoped by shop, per-shop feature toggles, billing state, etc.) can be triggered against a shop the attacker does not control, purely by replaying a webhook they legitimately received for their own installation. This is a cross-tenant identity-confusion vulnerability reachable by any unprivileged Shopify merchant who has installed the target app — no access token, `client_secret`, or privileged account is required.

### Likelihood Explanation
Any merchant who installs the app receives real, validly-signed webhooks for their own store. Capturing the raw body and `X-Shopify-Hmac-Sha256` header (both visible to the merchant/app since the payload is forwarded to their own endpoint or observable in transit) and replaying with a modified shop-domain header requires no special privilege or secret — only a normal app installation, making this readily reachable by an unprivileged internet user.

### Recommendation
Bind the shop identity into the verified material: e.g., require the app to look up/confirm the shop from the webhook's payload content or a `webhook_id` returned from a signed source, or fetch/validate the shop against previously registered webhook subscriptions before trusting `WebhookMetadata#shop`, rather than trusting the raw header value once the body-only HMAC passes. At minimum, document prominently that `shop` is unauthenticated and must be independently verified by the consuming application before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`). Shopify sends a POST with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(api_secret_key, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker intercepts/records `(B, H)`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Request#hmac` reads `H` from the header; `to_signable_string` returns `B`; `HmacValidator.validate` recomputes HMAC over `B` with the app's `api_secret_key` and it matches `H` — validation succeeds (per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`).
5. `Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198`), causing the app to process the event as if it originated from the victim's store.
