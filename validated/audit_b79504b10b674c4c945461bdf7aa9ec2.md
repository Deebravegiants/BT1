### Title
Webhook tenant identity (`shop-domain` header) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking `Utils::HmacValidator.validate(request)`, which validates the HMAC over `request.to_signable_string` — defined in `ShopifyAPI::Webhooks::Request#to_signable_string` as `@raw_body` only. Every other field the handler actually acts on — `topic`, `shop`, `api_version`, `webhook_id` — is read directly from HTTP headers (`shopify_header`) and is never included in the signed payload. This breaks the intended binding `hmac_verified_bytes == tenant_identity_bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from request headers via `shopify_header`, with no cryptographic tie to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC/body binding, then forwards the header-derived `shop` (and other header values) straight to the app's handler as the tenant identity: [3](#0-2) 

Because the signature only proves "this body was signed with `api_secret_key`," and says nothing about which shop the header claims to be from, an attacker who can obtain any one valid `(raw_body, hmac-sha256)` pair for their own shop (trivial — anyone can create a free/dev Shopify store and install a public app to receive real, validly-signed webhooks) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body against the HMAC, and the app's handler receives `WebhookMetadata` claiming the event belongs to the victim shop, with no revalidation against `ShopifyAPI::Utils::ShopValidator` or any other domain check anywhere in the webhook path.

The equality that should hold — `shop_bound_by_hmac == shop_acted_upon_by_handler` — is broken: the shop bound by the signature is "unauthenticated header string," while the shop acted upon is that same unauthenticated string.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged attacker (any developer with a free Shopify dev store and the target app installed) can forge webhook deliveries that appear to originate from an arbitrary victim shop domain while carrying attacker-controlled/attacker-chosen body content (from any topic/webhook they can legitimately trigger on their own store, e.g. `shop/redact`, `customers/redact`, order or app-subscription events). Any host application that uses `WebhookMetadata#shop` to key per-tenant side effects (e.g., look up/update a shop record, revoke access tokens, mark a shop as uninstalled, process GDPR redact/data-request against the wrong shop's data) can be manipulated into performing an action against a shop it was not intended for — satisfying the "cross-tenant access" criterion (Critical).

### Likelihood Explanation
High feasibility: the attacker only needs a self-controlled Shopify store to obtain one legitimately signed `(body, hmac)` pair for a chosen topic, and standard HTTP tooling to replay it with a modified header value. No access to the app's `api_secret_key`, access tokens, or any privileged account is required — only header manipulation on a normal, low-trust webhook POST, which any internet client can send to a publicly reachable webhook endpoint.

### Recommendation
Bind the tenant/topic identity into the signed payload verification: reject the header-derived `shop`, `topic`, `webhook_id`, and `api_version` unless they can be cross-checked against server-side state (e.g., the shop must already have an active, previously-established session/installation matching that domain, validated via `ShopifyAPI::Utils::ShopValidator.sanitize!`), and/or require the host application to independently verify that the claimed shop has a currently active app installation and session before acting on webhook content, rather than trusting the header value implicitly once HMAC-on-body passes.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) dev/trial store `attacker.myshopify.com`, and triggers a webhook (e.g. `orders/create`, `customers/redact`) — the app receives a legitimate request with a real `raw_body` and a real `X-Shopify-Hmac-Sha256` computed as `HMAC-SHA256(api_secret_key, raw_body)`.
2. Attacker captures this exact `raw_body` and `hmac-sha256` value.
3. Attacker replays a new POST to the app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, request.to_signable_string)` — i.e., over `@raw_body` only — and it matches, so validation passes: [4](#0-3) 
5. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)`, causing the host app to process attacker-controlled webhook content under the victim shop's tenant identity.
