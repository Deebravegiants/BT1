### Title
Stale `last-update` Timestamp Causes Retroactive Interest Over-Accrual When Utilization/Rate Returns From Zero - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vault contracts)

### Summary
This is a valid analog of the reported bug class. In the Sui report, `accumulate_strategy_reward` skips updating `last_reward_time` when `emission_per_second == 0`, so a later re-activation of emissions retroactively rewards the entire dormant period. The Zest vault contracts (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`) contain the same structural flaw in their interest-accrual routine: `last-update` is only advanced when the computed `index`/`lindex` actually changed, not unconditionally on every `accrue` call.

### Finding Description
`next-index` and `next-liquidity-index` compute a time-based multiplier from `interest-rate()` / `calc-liquidity-rate(...)` and `time-delta = (- stacks-block-time (var-get last-update))`: [1](#0-0) 

`accrue` then only persists `last-update` when at least one of the indexes actually moved: [2](#0-1) 

When utilization is zero (no outstanding debt), `interest-rate()` and `calc-liquidity-rate(...)` return `0`, making the multiplier equal to `INDEX-PRECISION` (i.e., "no change"). Under `(if (not (is-eq idx next)) (var-set index next) false)` and the equivalent for `lindex`, neither variable changes, so the `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)` branch is not taken and `last-update` remains frozen at its old value — exactly mirroring the reported `if (rewarder.emission_per_second == 0) { return; }` early-return that skips the `last_reward_time` update.

Every state-mutating entrypoint (`system-borrow`, `system-repay`, deposit/redeem, etc.) calls `accrue` first, using the *pre-transaction* utilization/rate. So when a borrow first turns utilization from `0` to positive, the `accrue` call inside that very transaction still observes the old (zero) rate and again fails to advance `last-update`. Only on the *next* `accrue` call (now with a positive rate) does `time-delta` get computed — but it is computed against the stale `last-update`, spanning the entire dormant zero-utilization period plus the time until the rate turned positive. This causes `next-index`/`next-liquidity-index` to apply the newly-positive rate as if it had been active for that whole stale interval, inflating debt (`principal-scaled * next / INDEX-PRECISION`) and the liquidity index in one artificial jump.

### Impact Explanation
This breaks the identity that debt growth (interest created) must equal the interest actually distributable to depositors/reserve over the real elapsed time. The over-accrual simultaneously inflates:
- `total-debt` owed by borrowers (via `index`), and
- redeemable value of `zft` shares (via `lindex`) and treasury share minting (`treasury-lp` minted to `.dao-treasury`),

without any corresponding increase in real underlying assets held by the vault. This can push the sum of redeemable share value above actual vault assets, i.e., a value-minted-from-nothing / protocol-insolvency style issue affecting supplier redemptions and treasury minting, which falls under the in-scope Critical/High impact categories (protocol insolvency, minting value from nothing).

### Likelihood Explanation
This requires no privileged access — any market where utilization can drop to zero (e.g., all debt repaid) and later increase again will trigger this path organically through normal `system-borrow`/`system-repay` usage, making it readily reachable by ordinary users/keepers without any special permission or DAO action.

### Recommendation
Update `last-update` unconditionally to `stacks-block-time` on every `accrue` call, regardless of whether `index`/`lindex` changed, mirroring the fix applied for the original rewarder bug (update the timestamp regardless of the emission/rate value).

### Proof of Concept
1. Vault has outstanding debt; utilization > 0.
2. All debt is repaid via `system-repay`, driving utilization (and thus `interest-rate`) to `0`. `accrue` runs, `next == idx` and `nliq == lindex`, so `last-update` is left at its old value `T0`.
3. Time passes (e.g., `time-delta` = large `D`), utilization remains `0`, no accrue calls change indexes, `last-update` stays at `T0`.
4. A new borrow occurs via `system-borrow`. The `accrue` call inside this transaction still sees utilization `0` (pre-borrow state), so indexes still don't change and `last-update` remains `T0`.
5. Some time later (`T1`), with debt now outstanding and a positive rate, any operation calls `accrue`. `time-delta = T1 - T0` now includes the entire dormant zero-utilization interval `D`, so `next-index`/`next-liquidity-index` apply the currently positive rate as though it had accrued over the whole stale interval `D`, producing an oversized jump in `index`/`lindex` and an oversized one-time `treasury-lp` mint relative to actual elapsed interest-bearing time.
