### Title
Webhook `shop` (and topic/id) Header Is Not HMAC-Covered, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the raw request body against the `X-Shopify-Hmac-Sha256` header, but the `shop` identity that the handler acts on is taken from an unauthenticated header field, not from the HMAC-covered payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely over that signable string (the body bytes) and compares it to the `hmac-sha256` header: [2](#0-1) 

But `Request#shop` (as well as `#topic`, `#webhook_id`, `#api_version`) is read directly from the `shop-domain` HTTP header, entirely outside of what the HMAC signs: [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body integrity) and then hands the unauthenticated `request.shop` straight to the app's registered handler as the tenant identity for the event: [4](#0-3) 

This is exactly the class of bug in the reference report: a field that is *acted upon* (here, the shop/tenant the webhook is attributed to) is not bound by the same authentication check (HMAC) that guards the rest of the request. An attacker who is a legitimate but unprivileged merchant on the platform (i.e., they run their own shop and have the app installed there) can trigger a genuine webhook to their own store, capturing a real `(raw_body, hmac)` pair signed by the app's shared secret for a topic they control (e.g. `orders/create`). Because `shop-domain` is not part of the signed material, they can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`, `webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (only the body is checked), so `Registry.process` will dispatch the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled/replayed body>, ...)`.

### Impact Explanation
This breaks the identity binding `shop-domain header == the shop the HMAC-authenticated payload actually originated from`. Any app that uses `data.shop` from the webhook handler to scope data writes, cache invalidation, billing state, order sync, or other per-tenant side effects can be made to apply attacker-controlled webhook content to a different merchant's tenant context — a cross-tenant data-integrity/confusion issue reachable by any unprivileged actor who can trigger one legitimate webhook delivery to their own store and replay it with a different header value at the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to install/operate the app on one's own shop (the normal, unprivileged path any Shopify merchant has) and send an HTTP POST to the app's own webhook callback.

### Likelihood Explanation
Likelihood is high for any app that trusts `data.shop` for tenant-scoping without independently correlating it to session/store state established via OAuth: capturing a valid `(body, hmac)` pair only requires installing the app on an attacker-controlled shop (readily available to anyone) and triggering an ordinary webhook event (e.g., placing an order), then re-POSTing it with a modified `shop-domain` header. No cryptographic material needs to be forged.

### Recommendation
Bind the `shop` (and `topic`/`webhook_id`) values into the HMAC-signable material, or otherwise cryptographically tie the header-provided shop to the verified body (e.g., have `to_signable_string` include the shop/topic headers, matching how Shopify's actual webhook HMAC scheme should be validated), and reject the request if the shop asserted in headers cannot be corroborated. At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are not authenticated by `HmacValidator.validate` and must not be used by consuming applications as a trusted tenant identifier without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker performs an action that triggers a real webhook delivery to the app's callback URL; they capture the raw body and the genuine `X-Shopify-Hmac-Sha256` value Shopify computed with the app's shared secret.
3. Attacker resends this exact `(raw_body, hmac)` pair to the same app endpoint, but sets the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the hmac — this passes. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's payload>, ...)`, causing the app to process attacker-controlled webhook content under the victim tenant's identity.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
