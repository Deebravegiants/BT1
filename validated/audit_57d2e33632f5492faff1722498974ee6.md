### Title
Webhook shop/topic identity spoofing via HMAC that covers only the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are trusted and forwarded to the host application's handler as the tenant/event identity — come from HTTP headers that are never covered by that signature.

### Finding Description
`Registry.process` validates a webhook solely with `Utils::HmacValidator.validate(request)`, then immediately builds `WebhookMetadata` using unauthenticated header values: [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.), with no cryptographic link to the signed body: [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(api_secret_key, raw_body ‖ shop ‖ topic)`. Instead the actual check is `hmac == HMAC(api_secret_key, raw_body)`, with `shop`/`topic` supplied separately and unauthenticated. This is exactly the "field acted on but not covered by the HMAC" bug class from the analog rules.

Critically, `api_secret_key` is the **app's** client secret, shared across every shop that installs the app — it is not per-shop. Any unprivileged user who installs the app on their own store can legitimately trigger events (e.g., create an order) and receive a genuinely-signed `(raw_body, hmac)` pair from Shopify for their own shop. Because the signature never binds to the shop, that exact `(raw_body, hmac)` pair remains valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a different (victim) shop.

### Impact Explanation
This lets an unprivileged app-installer forge/replay events "as" another tenant's shop, since `Registry.process` accepts the HMAC and passes the attacker-chosen `shop` value straight into the handler without any check that it matches the shop that actually produced the signed body. Depending on how host applications key their data storage/DB writes off `WebhookMetadata#shop` (which the library's own docs recommend as the tenant identifier), this enables cross-tenant data injection/corruption — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be a legitimate installer of the target app on a shop they control (no special privileges, no access to `api_secret_key`, no TLS interception) — well within "unprivileged internet user" scope. It does require the attacker to know/guess a victim shop domain and have the app's webhook endpoint reachable, which is normal for any multi-tenant Shopify app.

### Recommendation
Bind the shop (and ideally topic) into the signable content used for HMAC verification, or independently verify that `request.shop` corresponds to a shop with an active, matching session/installation before trusting it in `WebhookMetadata`. At minimum, document that host apps must not trust `Request#shop` for tenant identification without an additional installation-lookup check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `orders/create`) in their own store, capturing the genuine `raw_body` and `x-shopify-hmac-sha256` value Shopify sends to the app's callback endpoint.
3. Attacker POSTs that identical `raw_body` and `hmac` header to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (using the app's single shared `api_secret_key`) passes because it only checks the body. [4](#0-3) 
5. `Registry.process` invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the host app to process attacker-controlled data under the victim tenant's identity. [1](#0-0)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
