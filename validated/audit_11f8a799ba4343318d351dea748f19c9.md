Audit Report

## Title
Capability execution proceeds even when billing/metering deduction fails, allowing quota/balance bypass - (File: core/services/workflows/v2/capability_executor.go)

## Summary
In `ExecutionHelper.callCapability`, when `meterReport.Deduct` returns an error (e.g., `ErrInsufficientBalance` once a workflow has exhausted its credit balance), the code only logs the error via `c.cfg.Lggr.Errorw(...)` and falls through without returning, allowing `capability.Execute` to run regardless. This decouples metered capability execution from successful balance enforcement, letting a workflow continue invoking billed capabilities after its credits are exhausted.

## Finding Description
`callCapability` calls `meterReport.Deduct` with `metering.ByDerivedAvailability` to earmark credits before invoking a capability: [1](#0-0) . If `Deduct` fails, the error is only logged, with no `return`, and execution proceeds directly to constructing `capReq` and calling `capability.Execute(execCtx, capReq)`: [2](#0-1) . The underlying `balanceStore.Minus` returns `ErrInsufficientBalance` when the deduction amount exceeds the current balance, exactly the condition that should stop further billed execution: [3](#0-2) . `ByDerivedAvailability` propagates this error from `r.balance.Minus(limit.Decimal)` in its non-metering-mode return path: [4](#0-3) . There is no code path elsewhere in `callCapability` that aborts on this specific error or blocks subsequent capability calls for the execution once balance is exhausted.

## Impact Explanation
This is a legitimate billing/metering enforcement bypass: a workflow owner can keep invoking metered capabilities (HTTP calls, chain writes, consensus, etc.) after exhausting allotted credits, because the failure to deduct is only logged rather than enforced. This maps to an in-scope impact category of unauthorized/free resource consumption bypassing billing enforcement, which is a legitimate business-logic/access-control flaw rather than a purely cosmetic one.

## Likelihood Explanation
The scenario is easily reachable during normal operation: any workflow whose available balance is fully consumed will trigger `ErrInsufficientBalance` on every subsequent metered capability call for that execution, and the vulnerable code path executes unconditionally on that error, with no special privilege required beyond normal workflow-owner capability to submit/execute a workflow.

## Recommendation
In `callCapability`, when `meterReport.Deduct` returns an error — particularly `ErrInsufficientBalance` — abort the capability call and return an error to the caller instead of only logging and continuing to `capability.Execute`. Distinguish "fail open" conditions (e.g., billing-service communication errors, which intentionally switch to metering mode) from genuine balance-exhaustion errors, which should hard-stop billed execution.

## Proof of Concept
1. Construct a `metering.Report` via `NewReport` with a small balance/rate card such that a `Deduct` call will exceed available balance (see `Test_Report_Deduct` / `ByDerivedAvailability` tests: [5](#0-4) , which demonstrates `Deduct` returning `ErrInsufficientBalance` outside metering mode).
2. Drive a workflow execution to repeatedly call `ExecutionHelper.callCapability` (via `CallCapability` from workflow guest code) until `meterReport.Deduct` returns `ErrInsufficientBalance`.
3. Confirm in `capability_executor.go:199-209` that only `c.cfg.Lggr.Errorw(...)` is invoked and execution falls through to `capability.Execute` at line 254, allowing the capability call to succeed despite the exhausted balance — i.e., a unit/integration test asserting that after balance exhaustion, `callCapability` still returns a successful `capResp` (rather than an error) demonstrates the bypass.

// Minus lowers the current credit balance.
func (bs *balanceStore) Minus(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	if amount.GreaterThan(bs.balance) {
		return ErrInsufficientBalance
	}

	bs.balance = bs.balance.Sub(amount)

	return nil
}

// ByDerivedAvailability returns a DeductOpt that derives the maximum spend limit based on the user spend limit and
// the number of open concurrent call slots.
func ByDerivedAvailability(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
	info capabilities.CapabilityInfo,
	config *values.Map,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     info.ID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		limit, err := r.getMaxSpendForInvocation(userSpendLimit, openConcurrentCallSlots)
		if err != nil {
			return nil, err
		}

		if !limit.Valid {
			return []capabilities.SpendLimit{}, nil
		}

		step.Deduction = limit.Decimal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return r.creditToSpendingLimits(info, config, limit.Decimal), r.balance.Minus(limit.Decimal)
	}
