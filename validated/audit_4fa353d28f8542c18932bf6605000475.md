### Title
Fee-on-transfer / deflationary ERC20 underlyings cause under-collateralized locks in `WrappedHyperFungibleToken.send()` - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 by calling `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain `Message` that declares `amount = params.amount` was locked, without ever verifying how many tokens the contract actually received.

### Finding Description
In `send()`:
```solidity
function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
    uint256 msgValue = msg.value;
    if (_isWeth && msgValue >= params.amount) {
        ...
    } else {
        IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    }

    DispatchPost memory request = _buildDispatchPost(params);
    ...
}
``` [1](#0-0) 

`_buildDispatchPost` encodes `params.amount` (the caller-supplied amount, not the actually-received balance delta) into the cross-chain `Message.amount` field: [2](#0-1) 

If `_underlying` is a deflationary/fee-on-transfer or rebasing ERC20, the actual balance increase of the contract after `safeTransferFrom` will be less than `params.amount`. The contract nevertheless dispatches a POST request asserting the full `params.amount` was locked. On the destination side, `onAccept` (either on a peer `WrappedHyperFungibleToken` or a `HyperFungibleToken`) unconditionally unlocks/mints the full declared `message.amount`:
```solidity
IERC20(_underlying).safeTransfer(beneficiary, message.amount);
``` [3](#0-2) 

There is no post-transfer balance check (`balanceBefore`/`balanceAfter` delta) anywhere in `send()`, unlike the pattern already used elsewhere in the codebase for handling exactly this class of risk (e.g. `IntentGatewayV2` snapshots balances before/after a transfer specifically to measure actual amounts received): [4](#0-3) 

### Impact Explanation
Each `send()` call with a fee-on-transfer/rebasing underlying locks strictly less collateral than the amount the protocol commits to deliver cross-chain. Since the destination chain always mints/unlocks the full declared `amount`, repeated calls progressively drain the contract's real underlying reserve relative to its cross-chain liabilities. Eventually the `WrappedHyperFungibleToken` contract's underlying balance becomes insufficient to honor legitimate `onAccept`/`onPostRequestTimeout` unlocks, causing `safeTransfer` reverts and permanent freezing of funds for other users' bridged transfers, or allowing an attacker to extract more underlying tokens on the destination side than was ever actually escrowed on the source side — a direct value-extraction/insolvency vector reachable by any unprivileged token bridger.

### Likelihood Explanation
Any owner/integrator who configures `_underlying` to a non-standard ERC20 (fee-on-transfer, deflationary burn-on-transfer, or rebasing token) exposes this immediately; no special privileges are needed by the attacker — a single `send()` call from any user triggers the mismatch, and it is reachable purely through the exposed `send()` entry point with a supported, but non-standard, ERC20.

### Recommendation
Measure the actual amount received by comparing `balanceOf(address(this))` before and after the `safeTransferFrom` call in `send()`, and use that delta (not `params.amount`) both for constructing the dispatched `Message.amount` and for any relayer-fee/timeout accounting. Alternatively, explicitly document/enforce (e.g. via a registry or allowlist check) that only standard, non-rebasing, non-fee-on-transfer ERC20 tokens may be configured as `_underlying`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` configured with a fee-on-transfer ERC20 (e.g. 5% transfer fee) as `_underlying`.
2. Attacker calls `send({amount: 1000, dest: ..., to: attacker, ...})`. `safeTransferFrom` pulls 1000 tokens from attacker but the contract only receives 950 due to the fee; `params.amount = 1000` is still what gets dispatched.
3. On the destination chain's peer, `onAccept` unlocks/mints 1000 tokens to `attacker`.
4. Attacker has net gained 50 tokens of unbacked liquidity; repeating this drains the wrapper's true underlying reserves relative to its outstanding cross-chain liabilities, eventually causing `safeTransfer` in `onAccept`/`onPostRequestTimeout` to revert for other legitimate users due to insufficient balance.

        bytes memory body = abi.encode(HyperFungibleToken.Message({

            data: params.data

            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
