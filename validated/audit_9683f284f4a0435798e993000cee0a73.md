### Title
Silent ERC-20 transfer failures in `IntentGatewayV2.withdraw()` and dust-sweep let escrow accounting be finalized without tokens ever reaching the beneficiary - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds and swept dust using a raw low-level `.call` to the ERC-20 `transfer` selector, checking only that the call itself did not revert (`success`). It never decodes/validates the returned `bool` payload. Any ERC-20-compliant token that signals failure by returning `false` (rather than reverting) will be treated as a successful transfer, while the contract simultaneously finalizes escrow state (decrements internal accounting, emits `EscrowReleased`/`EscrowRefunded`/`DustSwept`) as if the beneficiary was paid.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

and for the transaction-fee payout:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
delete _orders[body.commitment][TRANSACTION_FEES];
``` [2](#0-1) 

and in the `SweepDust` unsigned-request handler:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

`success` here only reflects whether the low-level call reverted — it does **not** inspect the ABI-encoded return data. A standards-compliant ERC-20 (or a token that has been paused, has a blacklist, or otherwise returns `false` on failure instead of reverting) will make this call succeed at the EVM level while the token balance of the beneficiary never changes. The contract has no fallback check (e.g. `IERC20.balanceOf` diff, or decoding the return value with `abi.decode(data, (bool))`) — unlike the rest of the contract, which correctly uses `SafeERC20.safeTransferFrom`/`safeTransfer` for inbound transfers (see `evm/tron/contracts/apps/IntentGatewayV2.sol` lines ~250, ~321, ~405, ~459, ~484, and `import {SafeERC20} ...; using SafeERC20 for IERC20;`) [4](#0-3) .

This is the inverse of the report's bug class (revert-on-non-bool-return) but produces a strictly worse outcome for a subset of ERC-20 tokens: instead of reverting unexpectedly, the withdrawal silently "succeeds" from the contract's point of view even though funds were never delivered.

### Impact Explanation
`withdraw()` is reachable by any relayed `RedeemEscrow`/`RefundEscrow` ISMP request (authenticated only via `authenticate(incoming.request)`, i.e. any properly-routed cross-chain message reaching the gateway) and by `onGetResponse` for the refund path. If the output/fee token returns `false` on a failed transfer (e.g., temporarily paused, blacklisted beneficiary, insufficient allowance-adjacent edge case on some non-standard tokens, or simply a bug/limit in the token's own logic), the contract:
- Decrements `_orders[commitment][token]` and/or deletes `_orders[commitment][TRANSACTION_FEES]`, permanently marking the escrow as spent.
- Emits `EscrowReleased`/`EscrowRefunded`, which downstream systems (indexers, users, solvers) treat as a completed transfer.

The result is permanent loss of the escrowed tokens: the beneficiary never receives them, and the contract's own accounting prevents any retry since the entry is already zeroed/decremented. This is a concrete freezing/loss of user or filler funds, satisfying the "permanent freezing of funds" acceptance criterion. The same silent-failure risk applies to `SweepDust`, which can misreport dust as swept while the treasury/beneficiary receives nothing.

### Likelihood Explanation
Likelihood is Medium: it requires a token used as an order input/output/fee token to be one that returns `false` instead of reverting on failure (a known category of ERC-20 tokens, and common on many token deployments beyond the classic USDT-style "void return" case). Because the gateway is designed for arbitrary order tokens (input/output assets are user/solver-specified, not an allow-list of "safe" tokens as far as shown here), and Tron/TRC-20 tokens are notoriously inconsistent in their ERC-20 conformance, the probability of eventually encountering such a token in production on this Tron deployment is non-trivial.

### Recommendation
Replace the raw `.call` + `success`-only checks in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer` (already imported and used elsewhere in the same contract), which correctly handles both no-return-data tokens (like USDT) and tokens that return an explicit `false`:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
_orders[body.commitment][token] -= amount;
```
This ensures a `false` return causes a revert, keeping escrow accounting consistent with actual token movement.

### Proof of Concept
1. Deploy (or use) an ERC-20/TRC-20 token whose `transfer` function returns `false` on failure instead of reverting (e.g., a paused-state token, or a token with a blacklist check that returns `false`).
2. Create an order using this token as an output asset; a filler fills the order, escrowing input tokens.
3. Trigger the `RedeemEscrow`/`RefundEscrow` path so `withdraw()` executes with the beneficiary in a state that causes the token's `transfer` to return `false` (e.g., beneficiary blacklisted after order placement, or token paused).
4. `token.call(...)` returns `success = true` (no revert) with return data `abi.encode(false)`, which is never decoded.
5. `_orders[body.commitment][token] -= amount` executes, `EscrowReleased`/`EscrowRefunded` is emitted, yet the beneficiary's token balance is unchanged — the tokens are permanently stuck in the gateway with no code path left to reclaim them for that order.
