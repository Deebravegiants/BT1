### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the signed bytes. `Registry.process` validates the HMAC against the body only and then unconditionally trusts the header-derived `shop`/`topic` values to dispatch the payload to a handler and attribute it to a tenant. Any actor who can observe one legitimately-signed webhook (e.g., a merchant who has installed the app and receives real webhooks for their own store) can replay that exact body+HMAC pair while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to impersonate a different shop, because those fields are outside the cryptographic binding.

### Finding Description
The binding the gem is supposed to enforce is:
`hmac == HMAC(api_secret_key, bytes-that-determine-shop-and-topic)`

but the actual implementation enforces only:
`hmac == HMAC(api_secret_key, raw_body)` [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-visible/attacker-settable HTTP headers via `shopify_header`, completely outside `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against the received HMAC: [3](#0-2) 

`Registry.process` performs this check and then immediately trusts the header-derived `request.shop` and `request.topic` to route and attribute the webhook, with no secondary check that the shop is one that actually installed the app for this body/topic combination: [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (it is not per-installation), any merchant who has installed the app receives real, validly-signed webhooks addressed to their own shop. That merchant can capture the `(raw_body, hmac)` pair from one of their own legitimate webhooks and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain (and/or the `topic` header changed). `Utils::HmacValidator.validate` still succeeds because the signed bytes (the body) are unchanged, and `Registry.process` will dispatch the handler with `WebhookMetadata.new(shop: <attacker-chosen victim shop>, ...)`.

This is the same class of bug as the referenced report: a value the code treats as authoritative for a security decision (`isLastCollateral` derived from an oracle price that could legitimately be zero) is not actually backed by the check performed (`count == 0`). Here, the value treated as the authoritative tenant/shop identity (`request.shop`) is not actually backed by the cryptographic check performed (HMAC over body only).

### Impact Explanation
Cross-tenant access: an unprivileged installer of the app can cause the host application's webhook handler to process arbitrary attacker-selected payload bytes while believing they came from, and pertain to, a different merchant's shop (or a different topic than the one Shopify actually sent). Depending on what the app's `Handler#handle` implementation does with `WebhookMetadata#shop` (e.g., look up/update tenant records, sync inventory, issue refunds, mark GDPR/mandatory compliance actions), this allows one tenant to inject/replay data into another tenant's context — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any shop that installs the app is, by design, given real webhook traffic signed with the app's single shared `api_secret_key`. No access token, `client_secret`, or privileged account is required — only the ability to install the app as an ordinary merchant (or otherwise capture one legitimate webhook delivery) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. This is a low-effort, realistically reachable path through the gem's own `Webhooks::Request`/`Registry` code, not a misuse of undocumented behavior by the host app.

### Recommendation
Include the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material, or — since Shopify's real HMAC scheme only signs the body — have `Registry.process`/`Request` treat the header-derived `shop` and `topic` as untrusted until cross-checked against a set of shops/installations known to the host app, and document/enforce that requirement in this gem rather than leaving it entirely to callers. At minimum, `to_signable_string` should not be the sole basis for authorizing which `shop`/`topic` a payload is attributed to.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a real webhook to the app's endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over BODY>
   X-Shopify-Shop-Domain: shop-a.myshopify.com
   BODY: {"id":123,...}
   ```
   Merchant A (or anyone who can see this request, e.g. via a proxy they control since it's addressed to their own infrastructure) captures `BODY` and the valid `X-Shopify-Hmac-Sha256` value.
2. Merchant A resends the identical request to the same endpoint, only changing:
   ```
   X-Shopify-Shop-Domain: shop-victim.myshopify.com
   ```
   (`BODY` and `X-Shopify-Hmac-Sha256` unchanged.)
3. `Utils::HmacValidator.validate` recomputes the HMAC over `BODY` only and it matches, so validation passes (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "shop-victim.myshopify.com", topic: "orders/create", body: {"id":123,...}, ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), even though Shopify never sent this webhook for `shop-victim`.
