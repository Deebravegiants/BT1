### Title
Webhook HMAC validation does not bind the `shop`, `topic`, or `webhook_id` headers to the signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` [3](#0-2) , so the signature never binds the claimed shop/topic/webhook identity to the payload. `Registry.process` accepts the request once the body-only HMAC passes, then unconditionally trusts `request.shop` as the tenant identifier passed into the handler [4](#0-3) .

### Finding Description
This is the same identity-binding class described in the external report: a value that is *acted on* (the `shop` used to attribute the webhook to a tenant) is not the value *covered by the authentication mechanism* (the HMAC only signs `@raw_body`). Because a single app-level `client_secret`/`api_secret_key` is shared across every merchant that installs the app, any unprivileged party who installs the app on their own (even free/dev) store receives genuinely HMAC-signed webhook deliveries for that store. Since the signature never incorporates the `shop-domain`, `topic`, or `webhook-id` headers, that attacker can take a validly-signed body and re-submit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop's domain (and/or a different `topic`/`webhook-id`). `HmacValidator.validate` still returns `true` because it only checks the untouched body against the shared secret [5](#0-4) , and `Registry.process` hands the attacker-chosen `shop`/`topic`/`webhook_id` straight to the host application's handler as trusted `WebhookMetadata` [4](#0-3) .

The equality that should hold is: `shop_bound_by_signature == shop_acted_on_by_handler`. In this code, no such binding exists — the signature only proves "signed by holder of this app's secret", while the header-derived `shop` is taken at face value with no cryptographic tie to the signed bytes.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which tenant's data/session to mutate (e.g., processing `shop/redact`, `customers/redact`, or app-specific business logic keyed by shop) can be tricked into acting on an attacker-chosen shop identity while only proving possession of a signature for their own, different, legitimately-installed shop. This is a cross-tenant identity-confusion vulnerability: an unprivileged installer of the app can forge webhook deliveries that appear (post-HMAC-check) to originate from a different merchant, without ever needing that merchant's credentials.

### Likelihood Explanation
Exploitation only requires installing the target app on an attacker-controlled store (a normal, unprivileged action for any Shopify merchant/dev-store owner), capturing one legitimately-signed webhook body/HMAC pair, and replaying it with modified `shop-domain`/`topic`/`webhook-id` headers to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the real target merchant is needed.

### Recommendation
Include the header values that the application relies on for tenant/topic attribution (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used for `to_signable_string`, or otherwise cryptographically bind them to the HMAC (e.g., by validating them server-side against Shopify's registered webhook metadata rather than trusting client-supplied headers). At minimum, document that `request.shop`/`request.topic` are not covered by the HMAC and must not be used as an authoritative tenant key without additional verification.

### Proof of Concept
```
1. Attacker installs the target app on their own (free/dev) Shopify store "attacker.myshopify.com".
2. App's webhook endpoint receives a legitimate delivery:
   headers: {
     "x-shopify-topic" => "orders/create",
     "x-shopify-hmac-sha256" => "<valid HMAC over raw_body using shared app secret>",
     "x-shopify-shop-domain" => "attacker.myshopify.com",
     "x-shopify-webhook-id" => "abc-123"
   }
   body: '{"id": 1, ...}'
3. Attacker replays the exact same raw_body and hmac-sha256 header to the app's
   webhook endpoint, but changes:
     "x-shopify-shop-domain" => "victim-shop.myshopify.com"
4. ShopifyAPI::Webhooks::Registry.process(request) calls
   Utils::HmacValidator.validate(request), which recomputes HMAC over @raw_body only
   -> validation succeeds (body unchanged).
5. Registry.process invokes handler.handle(data: WebhookMetadata.new(
     topic: request.topic, shop: "victim-shop.myshopify.com", ...))
   -> the host app's handler processes an attacker-controlled shop identity as
      if it were an authentic delivery from victim-shop.myshopify.com.
```
