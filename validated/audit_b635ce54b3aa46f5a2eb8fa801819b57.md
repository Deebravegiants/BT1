### Title
Session Fixation via Predictable, Non-Embedded Session Cookie Value - (File: lib/shopify_api/auth/oauth.rb, lib/shopify_api/auth/session.rb, lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser's session cookie value to `session.id` [1](#0-0) , and `ShopifyAPI::Auth::Session.from` derives that `id` deterministically as `"offline_#{shop}"` for offline sessions or `"#{shop}_#{associated_user.id}"` for online sessions [2](#0-1) . `ShopifyAPI::Utils::SessionUtils.cookie_session_id` and `current_session_id` then trust this cookie value verbatim as the session lookup key, with no signature or binding to the browser that completed OAuth [3](#0-2) [4](#0-3) . The fixed, public `SESSION_COOKIE_NAME = "shopify_app_session"` constant means every app instance uses the same cookie name [5](#0-4) .

### Finding Description
The equality this breaks is: *the session id an app's session store trusts as "the session belonging to this browser"* should equal *a value only derivable by a browser that actually completed this app's OAuth handshake*. Instead it equals *a value any unauthenticated party can compute from public information* (the target shop's `myshopify.com` domain, and — for online/per-user sessions — the target user's numeric id, which is often guessable/enumerable and appears in other places such as `associated_user` payloads).

Flow:
1. `Session.from` computes `id = "offline_#{shop}"` (offline) or `id = "#{shop}_#{associated_user.id}"` (online) — a pure function of public/guessable inputs, not a secret nonce [6](#0-5) .
2. `validate_auth_callback` sets the returned cookie's `value` to this same `session.id` for non-embedded apps [7](#0-6) , exactly as the documentation instructs developers to do (`cookies[auth_result[:cookie].name] = { value: auth_result[:cookie].value, secure: true, http_only: true }`) [8](#0-7) .
3. On subsequent requests, `SessionUtils.current_session_id`/`cookie_session_id` reads that cookie value back out and returns it unmodified as the trusted session id [9](#0-8) [4](#0-3) .
4. The reference `shopify_app` retrieval pattern documented in this repo's own `BREAKING_CHANGES_FOR_V16.md` looks the session up purely `by: id` and hands back the stored `access_token` [10](#0-9) .

Because the cookie is a fixed, well-known name and the id space is fully predictable, an attacker who knows (or can enumerate/guess) a victim shop's domain can simply set their own browser's `shopify_app_session` cookie to `"offline_victim-shop.myshopify.com"` before ever touching the target app. If the victim shop later completes (or has already completed) installation/OAuth, the attacker's forged cookie resolves to the exact same session id the app stored for that shop, and the attacker is served the victim shop's session — including its access token — by the app's own session-retrieval logic, without needing to intercept anything or possess any secret.

### Impact Explanation
This is a session-fixation / cross-tenant access issue: an unprivileged attacker can pre-set a cookie value that collides with another tenant's legitimately-issued session id, letting them ride into that tenant's authenticated session (and its stored access token) once/if it exists in the app's session store. This maps to the High-impact category "session fixation or forced OAuth completion."

### Likelihood Explanation
Likelihood is meaningful specifically for non-embedded apps that follow the exact cookie flow shown in this gem's own `docs/usage/oauth.md` (plain `secure`/`http_only` cookie, no additional signing called out) [8](#0-7) . The offline session id format (`"offline_#{shop}"`) requires only knowledge of the target's `myshopify.com` domain, which is generally public. The online format additionally needs the numeric `associated_user.id`, which reduces likelihood somewhat but is not a secret and can appear in other Shopify-exposed data (webhooks, GraphQL `staffMember` ids, etc.).

### Recommendation
Do not use a deterministic, attacker-computable string as the browser-facing session cookie value. Instead, generate an unguessable random token (e.g., `SecureRandom.uuid`/`hex`) as the cookie value, and store a server-side mapping from that opaque token to the actual `Session` object/id — analogous to how `state` is already handled as a random nonce in `begin_auth` [11](#0-10) . Alternatively, require and clearly document that the cookie value must be cryptographically signed/encrypted (e.g., Rails' encrypted cookie jar) so the deterministic `session.id` can never be forged by a third party, and call this requirement out explicitly next to the current cookie example in `docs/usage/oauth.md`.

### Proof of Concept
1. Attacker learns (or guesses) that `victim-shop.myshopify.com` uses the target Rails app (shop domains are not secret).
2. Before the victim ever installs the app, or in parallel with them, the attacker sends a request to the app with the cookie:
   `shopify_app_session=offline_victim-shop.myshopify.com`
3. Once the victim shop completes OAuth (offline flow) and the app's session store persists a `Session` keyed by `id = "offline_victim-shop.myshopify.com"` (exactly reproducing `Session.from`'s deterministic id, per `lib/shopify_api/auth/session.rb` lines 107-118), the attacker's pre-set cookie resolves via `SessionUtils.cookie_session_id` → `current_session_id` to that same id.
4. The app's controller layer (following the documented `retrieve(id)` pattern) fetches the victim's `Session`, including its `access_token`, and serves the attacker's request as if they were the authenticated victim shop — achieving cross-tenant access with no credentials of their own.

        def from(shop:, access_token_response:)
          is_online = access_token_response.online_token?

          if is_online
            associated_user = T.must(access_token_response.associated_user)
            associated_user_scope = access_token_response.associated_user_scope
            id = "#{shop}_#{associated_user.id}"
          else

          end

          if access_token_response.expires_in
            expires = Time.now + access_token_response.expires_in.to_i
          end

          if access_token_response.refresh_token_expires_in
            refresh_token_expires = Time.now + access_token_response.refresh_token_expires_in.to_i
          end

          new(
            id: id,
            shop: shop,
            access_token: access_token_response.access_token,
            scope: access_token_response.scope,

            shopify_session_id: access_token_response.session,
