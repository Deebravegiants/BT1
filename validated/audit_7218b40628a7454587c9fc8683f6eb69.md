### Title
Unbounded length-prefixed allocation in Livestream Upstream TCP handler allows remote memory exhaustion / DoS - (File: src/agents/livestream/upstream.rs)

### Summary
The `EventReader::poll_stream` function in the `livestream` agent's upstream TCP handler reads a 4-byte big-endian length prefix from a network peer and allocates a buffer of that exact size with no upper bound check, mirroring the H-16 root cause (unbounded attacker-controlled length parameter driving unchecked memory allocation).

### Finding Description
`Upstream::new` binds a `TcpListener` on all interfaces at a fixed port (`0.0.0.0:{PORT}`, `PORT = 9201`), accepting a connection from any peer that can reach the orb on the network. [1](#0-0) 

Once connected, `EventReader::poll_stream` reads a 4-byte length value from the socket and immediately allocates a `Vec<u8>` of that size before any of the payload has actually been received or validated:
```
if self.len_read == 4 {
    self.buf = vec![0; u32::from_be_bytes(self.len) as usize];
}
``` [2](#0-1) 

There is no cap on the declared length: a peer can send `0xFFFFFFFF` as the 4-byte prefix, causing the process to attempt a ~4 GiB heap allocation for a single connection, and it can repeat this on subsequent reconnections (the `EventReader` is reset to default on each new "Connected" event) to repeatedly trigger large allocations. [3](#0-2) 

This is the same bug class as the reported issue: an externally reachable interface accepts an attacker-supplied length used directly to size a memory allocation, with no bound check, before any authentication or payload validation.

### Impact Explanation
A successful trigger causes a large, attacker-controlled heap allocation (up to ~4 GiB per connection) inside the `orb-core` process on the orb device. This can exhaust available memory and crash or destabilize the process running the livestream agent (and potentially other orb-core components sharing the same address space/process, depending on process architecture), leading to denial of service on the orb. Repeated connections/attempts amplify the effect. This does not directly expose biometric data or bypass signup/liveness/fraud checks, but it is a legitimate unauthenticated remote resource-exhaustion vector analogous to the reported OOM issue.

### Likelihood Explanation
The listener binds `0.0.0.0`, meaning any device that can reach the orb over the network (e.g., a device on the same local/Wi-Fi network as the orb, since this is a livestream/debugging feature) can connect without any authentication and send a single 4-byte prefix to trigger the oversized allocation — a trivial, low-cost attack requiring no special privileges. The likelihood of exploitation is limited primarily by whether the `livestream` feature is compiled into and enabled in the production build; this could not be conclusively confirmed from the available index (the feature is gated behind `#[cfg(feature = "livestream")]` and referenced from `Cargo.toml`, but I was unable to verify default-feature enablement or deployment configuration within the tool budget available).

### Recommendation
- Enforce a strict maximum allowed message size (e.g., a small constant matching the actual expected `livestream_event::Event` payload size) before allocating the buffer, rejecting/closing connections that declare an oversized length.
- Consider requiring authentication/handshake before accepting length-prefixed payloads on this socket.
- Apply the same bound check pattern used elsewhere (e.g., `SizeTooLarge` handling in `can/src/fd.rs`) which already validates sizes before use. [4](#0-3) 

### Proof of Concept
1. Ensure the orb-core binary is built/running with the `livestream` feature enabled.
2. From any host that can reach the orb's IP on TCP port 9201, open a raw TCP connection.
3. Send 4 bytes: `0xFF 0xFF 0xFF 0xFF` (big-endian `u32::MAX`).
4. Observe the process attempt to allocate a `Vec<u8>` of ~4 GiB in `EventReader::poll_stream`, before any further payload bytes are sent, causing memory pressure/crash on constrained hardware (repeat over multiple reconnects to amplify).
