### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC solely against that body [1](#0-0) . The `shop` value that `Registry.process` later uses to attribute the webhook to a tenant is read directly from the `x-shopify-shop-domain` header, which is completely outside the HMAC-signed content [2](#0-1) .

### Finding Description
`Registry.process` performs `Utils::HmacValidator.validate(request)` and, if it passes, immediately builds a `WebhookMetadata` using `request.shop` for the `shop` field: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string`, which for a webhook `Request` is `@raw_body` alone [4](#0-3) . The `shop` header used to identify which merchant/tenant the event belongs to is never included in the signed material.

The binding the code should enforce is: **shop attributed to the webhook == shop that Shopify actually signed for**. Instead, the code enforces only: **body is unmodified**, while **shop header is trusted unauthenticated**. Because the `api_secret_key` used to sign webhooks is the single app-wide secret (shared across every shop that installs the app, not shop-specific), any merchant who has installed the app can legitimately trigger webhooks and thus obtain valid `(body, hmac)` pairs signed with that same secret. That merchant (acting as an attacker) can replay one of their own legitimately-signed `(body, hmac)` pairs against the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes because it checks only `raw_body`; `Registry.process` then dispatches to the host application's handler with `data.shop` set to the victim shop domain and `data.body` set to attacker-controlled (though genuinely-signed) content.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery. Host applications are documented to trust `data.shop` as the tenant key when processing webhook data (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` per the gem's own usage docs) [5](#0-4) . An attacker with a legitimate install of the app can forge events that appear to originate from any other shop using the app, letting them inject attacker-controlled data (order/product/customer payloads, mandatory GDPR topics, etc.) into another tenant's data pipeline — a cross-tenant data integrity/confidentiality violation attributable entirely to a gap in this gem's identity binding, not to any misuse by the host application.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant with the app installed (no special privilege, no secret leakage, no TLS interception) — they only need to capture one webhook delivery to their own store (trivial, since they control that store and receive the webhook) and replay it with a different `shop-domain` header value to the app's public webhook endpoint. This is a realistic "unprivileged internet user" scenario for any multi-tenant Shopify app using this gem, since the `api_secret_key` is common to all installations of the app.

### Recommendation
Bind the shop domain into the verified signature context, or otherwise cryptographically/authoritatively confirm the `shop-domain` header against data derived independently of the header before dispatching to handlers. At minimum, `to_signable_string` (or an additional check in `Registry.process`) should incorporate the `shop`, `topic`, and `webhook_id` header values so that tampering with them invalidates the HMAC, e.g., include the shop domain in the signable payload used by `HmacValidator`, or perform a secondary Shopify API confirmation (e.g. cross-checking `webhook_id` ownership) keyed to the claimed shop before trusting `request.shop`.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and has the app installed (same api_secret_key
# is shared by Shopify for HMAC-signing webhooks to every shop that installs the app).

# 1. Attacker's own store legitimately triggers a webhook; attacker captures the
#    raw body + x-shopify-hmac-sha256 header Shopify sent to their endpoint.
raw_body = '{"id": 1, "note": "attacker-controlled content"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# 2. Attacker replays this exact (body, hmac) pair to the app's webhook endpoint,
#    but swaps the shop-domain header to the victim's shop.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. HMAC validation passes because only raw_body is checked.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
#    and data.body == attacker-controlled content, even though Shopify never
#    sent this webhook for victim-shop.
```
