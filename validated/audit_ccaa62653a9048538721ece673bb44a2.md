### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unsigned HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that a webhook is attributed to purely from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Registry.process` validates is computed **only over the raw request body**. The header carrying the shop identity is never part of the signed material, so the "shop this data belongs to" binding is not cryptographically tied to the signature that is supposed to authenticate the request. This is the same class of bug as the `FeeWrapper` finding: a value that is *acted on* (here, the shop identity used to route/attribute webhook data) is not *covered* by the authentication mechanism (the HMAC) that is meant to vouch for the whole request.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all read straight from HTTP headers, none of which feed into the signable string: [2](#0-1) 

`HmacValidator.validate` verifies the received `hmac` against `to_signable_string` (i.e., body-only) using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` only checks this body HMAC before dispatching the handler with `request.shop` taken from the unsigned header: [4](#0-3) 

The equality that should hold is:
`shop used to authorize/attribute the webhook == shop covered by the HMAC signature`

Instead, the gem enforces:
`shop used to authorize/attribute the webhook == value of an attacker-controllable HTTP header`
`HMAC covers == raw body only`

Any party capable of sending an HTTP request directly to the app's public webhook endpoint URL (which must be internet-reachable for Shopify to call it) can supply an arbitrary `X-Shopify-Shop-Domain` header together with any `(body, hmac)` pair for which they know a valid signature. Because the shop header is not part of the signed content, a valid signature for one body says nothing about which shop that body is allowed to be attributed to.

A realistic way to obtain a valid `(body, hmac)` pair without possessing `api_secret_key` is for the attacker to be a legitimate (unprivileged) merchant/installer of the target app on their own store: Shopify will deliver genuine webhooks to the app's endpoint for that attacker-owned shop, each with a correctly computed HMAC over a body the attacker fully observes. The attacker then replays that exact `(raw_body, hmac)` combination directly to the app's public webhook URL, but swaps the `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to a victim shop domain. `HmacValidator.validate` still passes (it only checks the body/hmac), and `Registry.process` calls the registered handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain and `body` set to the attacker's own (legitimately signed) payload.

### Impact Explanation
Downstream handlers (as shown in this gem's own documentation) use `data.shop` to key persistence, job dispatch, or business logic ("perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)"): [5](#0-4) 

Because `data.shop` is attacker-controllable while `data.body` is attacker-supplied content that nonetheless carries a cryptographically valid signature, an app built on this gem's documented pattern can be made to apply attacker-chosen webhook content under a victim shop's identity — a cross-tenant data-integrity/confusion issue reachable by an unprivileged internet user who only needs a normal (self-service) app install on their own store to mint one valid `(body, hmac)` pair, then a direct POST to the public webhook URL with a forged shop header.

### Likelihood Explanation
The webhook endpoint is necessarily public (Shopify must be able to reach it over the internet), so nothing prevents a non-Shopify actor from POSTing to it directly. Obtaining a valid signed body requires no privileged credentials — any user can install the target app on a store they control and observe a legitimately signed webhook. The gem performs no additional binding check between the signed body and the unsigned identity headers, so exploitation only requires crafting one HTTP request with a swapped header.

### Recommendation
Include the tenant/shop identity (and ideally topic and webhook id) as part of the material that is HMAC-verified, or otherwise cryptographically bind the `shop` header to the signed payload before it is trusted. At minimum, document that `X-Shopify-Shop-Domain` is unauthenticated and require applications to independently corroborate it (e.g., against a known/registered shop domain for the current webhook subscription) before using it to route or persist data.

### Proof of Concept
1. Install the target app (any Shopify app using this gem) on an attacker-controlled test store `attacker-shop.myshopify.com`, and capture a real inbound webhook request the app receives — record the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header value Shopify computed for it.
2. Build a `ShopifyAPI::Webhooks::Request` (or raw HTTP POST to the app's webhook route) reusing that identical `raw_body` and `hmac` header, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. Send this request directly to the app's public webhook endpoint.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `hmac` against `raw_body`:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `request.shop == "victim-shop.myshopify.com"`, even though the body content actually belongs to the attacker's own shop. [7](#0-6)
