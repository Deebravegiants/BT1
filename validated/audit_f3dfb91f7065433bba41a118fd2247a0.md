### Title
Webhook `shop` identity not covered by HMAC, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`, so `ShopifyAPI::Utils::HmacValidator.validate` (invoked from `ShopifyAPI::Webhooks::Registry.process`) authenticates the request body only. The `shop` value, read from the `x-shopify-shop-domain`/`shopify-shop-domain` header via `Request#shop`, is never included in the signed material, yet it is passed straight into `WebhookMetadata` and handed to the app's handler as the trusted tenant identifier.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, raw_body + shop)` such that the `shop` value delivered to the handler is cryptographically tied to the same request the HMAC vouches for. Instead the binding actually enforced is `hmac == HMAC(secret, raw_body)` only: [4](#0-3) [2](#0-1) 

`Registry.process` trusts this HMAC result and then forwards `request.shop` — an unauthenticated header — directly to the handler as the tenant identity: [5](#0-4) 

Because the same `api_secret_key` is shared across *every* shop that installs the app (this is not a per-tenant secret), any merchant who has installed the app is, relative to other tenants, an "unprivileged internet user." Such a merchant legitimately receives real, validly-HMAC'd webhook deliveries from Shopify for their *own* shop. Since the signature covers only `raw_body`, they can capture one of these genuine deliveries and replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the forged victim domain — exactly as the gem's own documentation instructs handlers to trust it (`docs/usage/webhooks.md:12-18`).

### Impact Explanation
Handlers are documented and expected to use `data.shop` as the authoritative tenant key (e.g., to look up sessions, attribute data, or trigger per-shop side effects) as shown in the gem's own usage example (`docs/usage/webhooks.md:19-30`, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). An attacker who controls one legitimate shop installation can therefore inject webhook events that are processed as if they originated from a different, arbitrary shop, achieving cross-tenant confusion of exactly the sort the "impact" criteria call Critical (cross-tenant access) — without needing the victim's credentials, access token, or the app's `client_secret`.

### Likelihood Explanation
Any shop that has installed the app can trigger real webhook events for itself (e.g., by editing a product) and capture the resulting HTTP request Shopify sends to the app, then replay it with a modified `shop-domain` header value to the same public endpoint. No secret material beyond what the attacker already legitimately possesses (their own shop's ability to trigger webhooks) is required.

### Recommendation
Bind the tenant identity into the authenticated material, or otherwise cross-check it: e.g., include the `shop` (and ideally `topic`, `webhook_id`) in the signable string, or independently verify that the reported `shop` corresponds to a shop that actually has this webhook topic registered/has an active session, rejecting mismatches, before dispatching to the handler.

### Proof of Concept
1. App installs and registers a webhook handler that keys behavior off `data.shop`, per the documented pattern in `docs/usage/webhooks.md`.
2. Attacker installs the same app on `attacker.myshopify.com` and triggers a real webhook (e.g. `products/update`) to their own registered callback, capturing the raw POST: `raw_body` + valid `x-shopify-hmac-sha256` + headers.
3. Attacker resends the identical POST to the app's webhook endpoint, replacing only the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act as though the event originated from the victim tenant.
