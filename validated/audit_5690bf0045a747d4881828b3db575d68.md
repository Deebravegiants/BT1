This confirms the asymmetry: `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the HMAC-signed string [1](#0-0) , but `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop`, `topic`, `api_version`, and `webhook_id` headers from the HMAC computation [2](#0-1) . `Registry.process` validates only this body-only HMAC and then trusts `request.shop` to build `WebhookMetadata` passed straight to the app's handler [3](#0-2) . The docs explicitly tell integrators that `data.shop` is "The shop domain of the webhook" and to use it to scope work (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [4](#0-3) , i.e., the gem's own documented API presents `shop` as trustworthy once `Registry.process` succeeds.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are taken verbatim from unauthenticated HTTP headers. `Registry.process` verifies the HMAC and then unconditionally forwards `request.shop` to the app's handler as trustworthy tenant identity.

### Finding Description
`HmacValidator.validate` computes `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [5](#0-4) . For webhook requests, `to_signable_string` returns `@raw_body` only [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from the `x-shopify-*`/`shopify-*` headers with no cryptographic binding to the signed payload [6](#0-5) .

`Registry.process` treats a successful HMAC check as sufficient authorization to build and dispatch `WebhookMetadata` containing the unauthenticated `shop`/`topic`/`webhook_id` fields to the app's handler: [3](#0-2) 

Compare this to `ShopifyAPI::Auth::Oauth::AuthQuery`, used for the OAuth callback, where `shop` **is** included in `to_signable_string` and therefore is cryptographically bound to the HMAC [1](#0-0) . The webhook path lacks the equivalent binding.

Because all shops installed under a single app share the same `api_secret_key`, any party who has ever received (or can otherwise obtain) one legitimately-HMAC'd webhook body for their own shop can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header value. `HmacValidator.validate` will still succeed because it never inspects those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the attacker-chosen shop [7](#0-6) . The binding broken is: `shop authenticated by HMAC` ≠ `shop used by the app to scope tenant data`.

### Impact Explanation
Since the gem's own documentation instructs integrators to use `data.shop` (post `Registry.process` success) as the trusted tenant key for enqueuing/attributing work [4](#0-3) , an attacker who is an installed merchant of the app (an "unprivileged" party relative to other tenants of the same app) can forge webhook deliveries that are attributed to a victim shop of the same app, causing cross-tenant data confusion/injection in downstream processing (e.g., data written or actions taken under another merchant's shop domain). This matches the High-impact category of "cross-tenant access."

### Likelihood Explanation
Requires the attacker to already be a legitimate merchant/tenant of the target app (to obtain one validly-signed webhook body under the shared `api_secret_key`) and for the app's webhook endpoint to be reachable from the internet — both are realistic for any multi-tenant Shopify app using this gem's webhook processing exactly as documented, with no additional secrets needed to perform the header substitution.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed string comparison, or otherwise independently verify these header values (e.g., cross-check `shop` against the recipient's registered webhook registration/session) before constructing `WebhookMetadata`, so that a body signed for one shop cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and a valid `x-shopify-hmac-sha256` header computed by Shopify using the app's shared `api_secret_key` over `B`.
2. Attacker resends the exact same `raw_body: B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only checks presence, not value binding) [8](#0-7) .
4. `Utils::HmacValidator.validate` succeeds because it only re-hashes `@raw_body` [5](#0-4) .
5. `Registry.process` calls the app's handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` [9](#0-8) , even though the payload `B` was never actually generated for that shop.
