### Title
Webhook shop-domain (and topic) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` verify a webhook's authenticity by HMAC-signing only the raw request body, while the shop identity (`shop-domain` header) and `topic` header used by `ShopifyAPI::Webhooks::Registry.process` to dispatch and attribute the webhook are read straight from unauthenticated headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` and `topic` accessors instead read directly from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) .

`HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`, i.e., the raw body: [3](#0-2) .

`Registry.process` accepts the request once the body HMAC checks out, and then uses the unauthenticated `request.shop` and `request.topic` values to build `WebhookMetadata` and dispatch to the registered handler: [4](#0-3) .

Since the app's `api_secret_key` is shared across every merchant that installs the app (it is the app's client secret, not per-shop), any merchant who has legitimately installed the app receives real webhook deliveries for their own shop, complete with a valid `hmac-sha256` signature computed over the body with that shared secret. Such a merchant (an "unprivileged" tenant with respect to other merchants' data) can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. Because the shop/topic are not part of the signed content, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the handler believing the payload legitimately originates from the victim shop — an equality the gem should enforce (`hmac-covered bytes == identity used for dispatch`) is not actually enforced (`request.shop` used for dispatch != any value bound by the HMAC`).

### Impact Explanation
This breaks the tenant-identity binding that webhook consumers rely on to trust `WebhookMetadata#shop`/`#topic`. Any host application that uses these fields to route data into per-shop storage, invoke per-shop business logic, or otherwise trust "this event is really about `shop`" is exposed to cross-tenant data confusion/injection driven entirely by a request that only requires knowledge of one's own (attacker's) shop's genuine webhook deliveries — no access token, secret, or privileged account for the victim shop is needed. This matches the Critical "cross-tenant access" impact category defined in scope, since it lets one tenant's legitimately-signed data be attributed to another tenant purely by header substitution.

### Likelihood Explanation
Any merchant that installs the target app already receives real webhook bodies with valid `hmac-sha256` values signed by the app's shared `client_secret`. No secret material needs to be obtained beyond what a normal, low-privilege app installer already has access to (their own webhook deliveries). Forging headers on a replayed HTTP POST requires no special access — it's a plain unauthenticated internet request to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and topic, api-version, webhook-id) in the signed content that is verified, or otherwise cryptographically bind these values to the payload before they are trusted downstream (e.g., have `Request#to_signable_string` mix in the shop/topic headers, or require the host app to separately verify `shop` against an active, known installation/session before processing). At minimum, document clearly that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC and must be independently corroborated (e.g., cross-checked against an active session/webhook subscription) before being trusted for per-tenant dispatch.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers/receives a legitimate webhook (e.g., `orders/create`) for topic `T` with genuine body `B` and a valid signature `HMAC = HMAC-SHA256(client_secret, B)` delivered with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: HMAC`, `X-Shopify-Topic: orders/create`.
2. Attacker replays the exact same body `B` and `HMAC` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes the HMAC over `B` only (see `to_signable_string`), which still matches, so `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` — [5](#0-4)  — even though the payload was never actually generated for that shop.
