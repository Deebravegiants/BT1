### Title
Webhook shop-domain identity is trusted for tenant routing without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity solely from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while `HmacValidator` only signs the raw request body. `Registry.process` then hands this unverified `shop` value straight to the app's webhook handler as `WebhookMetadata.shop`, creating an equality mismatch between "the shop whose secret verified this webhook" and "the shop the app believes it received data for."

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) ; the `shop` accessor is read independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is never included in the signed bytes [3](#0-2) .

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` and forwards it to the merchant's handler along with `request.parsed_body`: [4](#0-3) . The resulting `WebhookMetadata.shop` field [5](#0-4)  is exactly what host apps use to attribute incoming data/events to a tenant.

The binding that should hold is:
`shop_bound_by_hmac == shop_acted_on_by_handler`

But the actual binding is:
`shop_bound_by_hmac == "" (nothing – HMAC covers only raw_body)`
`shop_acted_on_by_handler == header value, fully attacker-controlled`

This mirrors the swafe root cause: a value that *looks* authenticated (arrives inside an "verified" webhook request) is not actually covered by the cryptographic check that gives it credibility, exactly like `recovery.social` being trusted as guardian-approved while its `threshold=0` parameters made it derivable without guardians.

### Impact Explanation
An unprivileged internet user who obtains one legitimate `(raw_body, hmac)` pair from any webhook belonging to any shop (e.g., by observing traffic to a public endpoint, or via a shop they control sending themselves a real webhook) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a *different* victim shop. Because `Registry.process` never checks that the header shop is consistent with anything cryptographically bound to the payload, the app's handler will process the payload as if it originated from the victim shop, causing cross-tenant data confusion (e.g., writing another merchant's order/customer payload into the attacker-chosen shop's records, or triggering mandatory GDPR webhook handlers like `customers/redact` against the wrong tenant). This is a cross-tenant access violation.

### Likelihood Explanation
This requires only the ability to (a) send an HTTP POST to the app's public webhook endpoint and (b) know or capture one valid `(body, hmac)` pair, which is possible for an attacker who has their own store installed on the same app (a normal, unprivileged app install) sending themselves a webhook and then replaying it against another shop's identifier. No access to `api_secret_key` or any privileged credential is required — the attacker only reuses ciphertext-equivalent bytes (body+hmac) that Shopify already produced for them.

### Recommendation
Bind the shop identity into the value that is actually HMAC-verified, or otherwise validate it against a trusted, HMAC-covered source before using it for tenant attribution:
- Include the `shop-domain` header (and ideally `webhook-id`/`api-version`) in the signable string used by `HmacValidator`, matching Shopify's documented HMAC computation semantics, or
- Cross-check `request.shop` against a `shop` field embedded in the JSON body signed by the HMAC (if the payload contains it) before trusting it for routing, and
- Reject/flag webhooks where the header-derived shop cannot be corroborated by the signed payload.

### Proof of Concept
1. App installs the gem and registers a webhook handler for topic `orders/create` via `Webhooks::Registry.add_registration`.
2. Attacker (who owns shop `attacker.myshopify.com`, a normal Shopify Partner/dev store) triggers a real webhook, capturing `raw_body` and the corresponding `X-Shopify-Hmac-Sha256` value that Shopify computed with the app's shared secret.
3. Attacker POSTs to the app's webhook endpoint with the captured `raw_body`/`hmac` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts the headers [6](#0-5) ; `HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the secret [7](#0-6) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [8](#0-7) , causing the app to process attacker-controlled data as belonging to the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
