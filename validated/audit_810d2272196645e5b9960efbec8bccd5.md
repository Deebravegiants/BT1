### Title
Webhook shop/topic/webhook-id identity is not covered by the HMAC signature, allowing cross-tenant spoofing of `WebhookMetadata` - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but attributes the request to a shop/topic using header values that are never included in that signature. This breaks the binding "shop the HMAC was computed for" == "shop the app acts on," analogous to the Astaria report's pattern of acting on a value that was never actually covered/verified in the check that gated the operation.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable payload as only the raw body: [1](#0-0) 

Note that `hmac` is read from the `hmac-sha256` header and `to_signable_string` returns `@raw_body` exclusively — `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers (`shopify_header`) and are not part of the bytes that get HMAC-verified: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `compute_signature(request.to_signable_string, secret) == request.hmac`, i.e., it verifies the raw body bytes and nothing else: [3](#0-2) 

`Registry.process` then trusts the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values directly to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) [5](#0-4) 

Because the app's `client_secret`/`api_secret_key` is the same across every shop that installs the app (it is not per-tenant), any user who can obtain one HMAC-valid `(raw_body, hmac)` pair — for example by installing the app on their own free/dev store and capturing a legitimate webhook delivery for that store — can resubmit that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header for an arbitrary victim shop domain. `HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` will accept the request and hand the handler a `WebhookMetadata` whose `shop` field is attacker-chosen and does not correspond to the shop that actually produced the signed body.

### Impact Explanation
This is a cross-tenant identity-binding failure: the equality that should hold is `shop_bound_by_hmac == shop_used_for_data_attribution`, but in this code path `shop_used_for_data_attribution` (the `shop-domain` header) is never part of what the HMAC covers. Any app built on this gem that keys behavior off `WebhookMetadata#shop` (e.g., updating/deleting per-shop records, triggering `shop/redact` or `customers/redact` compliance flows, or gating access by shop) can be made to act on a victim shop's identifier using a payload that was never actually associated with that shop. This falls under the "cross-tenant access" Critical-impact category defined in scope.

### Likelihood Explanation
Requires only unprivileged access: create/install the target app on a shop the attacker controls (e.g., a free development store) to obtain one legitimately HMAC-signed webhook body, then replay that body to the app's public webhook endpoint with a forged `shop-domain` header pointing at any victim shop. No access token, `api_secret_key`, or privileged account for the *victim* shop is needed — only a normal, self-service Shopify Partner/dev-store signup, which is the kind of unprivileged internet-user access this scan is scoped to.

### Recommendation
Extend the webhook signature verification to bind the identity headers the app relies on, not just the raw body. Concretely: include `shop-domain`, `topic`, and `webhook-id` in the signed/verified material (or, at minimum, require the app to independently confirm that `shop-domain` corresponds to a shop with an active session/installation before trusting `WebhookMetadata#shop`), so that `to_signable_string`/`HmacValidator.validate` cannot pass while these header values are forged independently of the body's origin shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` computes `HMAC(B, secret)` and compares to `H` — this still matches because `to_signable_string` never includes the shop header, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim.myshopify.com"`, even though that shop never produced or authorized this payload (`lib/shopify_api/webhooks/registry.rb:188-200`).

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
