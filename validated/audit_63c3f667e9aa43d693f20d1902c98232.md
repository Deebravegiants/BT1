### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using `shop`, `topic`, and `webhook_id` values that are read from HTTP headers which are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers (`shop-domain`, `topic`, `webhook-id`) with no cryptographic binding to those headers [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only, per the above) and compares it against the `hmac-sha256` header value [4](#0-3) .

The equality that should hold is: `shop_that_HMAC_authenticates == shop_passed_to_handler`. In reality, the HMAC only authenticates `body`, so the binding is `HMAC(body) == HMAC(body)` — it says nothing about which shop, topic, or webhook id the body is attributed to. Since Shopify signs webhook deliveries with a per-app secret (the app's `client_secret`) that is identical for every shop that has installed the app, any entity capable of receiving one legitimate webhook delivery for the app (e.g., a merchant who installs the app on their own store, an unprivileged internet user in the threat model given by the task) obtains a `(body, hmac)` pair that remains valid for that body regardless of which `shop-domain`/`topic`/`webhook-id` header accompanies it. That party can resubmit the same body + valid HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`. `Registry.process` will accept it as authentic (HMAC passes) and hand the attacker-chosen `shop`/`topic`/`webhook_id` to the app's webhook handler alongside the replayed body.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for webhook delivery: `WebhookMetadata#shop` is meant to identify which merchant's data the body belongs to, but that identity is attacker-controllable independent of body authenticity. Any app that uses `WebhookMetadata.shop` to select which tenant's data to write, delete, or resync (a very common use, e.g., GDPR `customers/redact`/`shop/redact` handlers, which this gem lists as mandatory topics [5](#0-4) ) can be tricked into applying another shop's webhook body to a different shop, or applying a replayed body under an attacker-chosen topic. This is a cross-tenant data-integrity/isolation bypass rooted entirely in this gem's webhook verification code, not in host-application misuse.

### Likelihood Explanation
Requires the attacker to have received at least one legitimate signed webhook body from Shopify for the app (e.g., by installing the target app on their own store and triggering any webhook), and the ability to POST directly to the app's public webhook endpoint with arbitrary headers — both are available to an unprivileged internet user with no special credentials. No knowledge of `client_secret` or an access token is required, only a previously observed `(body, hmac)` pair.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used for HMAC verification, or otherwise cryptographically bind them (e.g., verify them against Shopify's registered webhook subscription for the delivered `webhook_id`) instead of trusting raw headers by convention. At minimum, `to_signable_string` should combine the headers with the raw body so that swapping `shop-domain`/`topic` while replaying a body invalidates the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and captures a legitimate webhook delivery (raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`).
2. Attacker POSTs to the app's webhook endpoint with body `B`, headers:
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - `X-Shopify-Topic: customers/redact` (optionally changed)
   - `X-Shopify-Webhook-Id: <any-id>`
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and finds it equals `H` — validation succeeds because the check only ever looked at `B` [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to act on data attributed to `victim-shop.myshopify.com` despite the payload never having been signed with that shop's association.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
