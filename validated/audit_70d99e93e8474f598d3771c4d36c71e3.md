### Title
Webhook HMAC only authenticates the raw body, letting shop/topic/webhook-id be forged - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's webhook handler with a `shop` field the docs describe as trustworthy ("The shop domain of the webhook"). In reality, the HMAC only signs the raw request body; the `shop`, `topic`, `webhook_id`, and `api_version` values come from HTTP headers that are never covered by the signature. An attacker who can obtain any one valid `(raw_body, hmac)` pair for the app (e.g., from a webhook delivered to their own installed shop, since a merchant fully controls the HTTP traffic reaching their own webhook receiver/proxy, or by observing any publicly-loggable webhook) can replay that exact body+HMAC to the app's webhook endpoint while forging the `shop-domain`, `topic`, and `webhook-id` headers to arbitrary values, since none of those bytes are checked against the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from unauthenticated headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over that signable string (the raw body) and, once it passes, unconditionally forwards the attacker-controllable `shop`, `topic`, and `webhook_id` header values into the handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac` header — again, this only proves the *body bytes* were signed by holders of the app's `client_secret` (i.e., genuinely came from Shopify for *some* webhook, to *some* shop), not that the specific `shop-domain`/`topic`/`webhook-id` headers accompanying this particular replayed request are authentic: [4](#0-3) 

The documented contract explicitly promises verification of Shopify origin and describes `shop` as a trustworthy identifier for the handler to act on: [5](#0-4) [6](#0-5) 

**Broken equality**: `shop authenticated-by-HMAC` (∅ — no header is covered by the signature) ≠ `shop delivered-to-handler` (`request.shop`, taken from an arbitrary, unauthenticated `shop-domain`/`x-shopify-shop-domain` header). Any request whose raw body byte-for-byte matches a body previously (or ever) HMAC-signed with the app's secret will pass `HmacValidator.validate`, regardless of which shop/topic/webhook-id headers are attached.

### Impact Explanation
Because the app's `webhook_secret` (the API `client_secret`) is shared across all merchants using the app, and the HMAC ignores headers entirely, any actor capable of producing or capturing one legitimately-signed `(body, hmac)` pair — most directly, a merchant who has installed the app and can freely control/replay the raw HTTP traffic hitting their own webhook endpoint — can resubmit that exact payload while relabeling the `shop-domain` (and `topic`/`webhook-id`) headers to point at a different, victim shop. `Registry.process` will accept it as validated and hand the forged `shop` value straight to the app's business logic (`WebhookMetadata#shop`), which apps are told (per the docs) they can trust to select the tenant record to act on. This crosses the tenant boundary: an app that keys database writes, webhook idempotency, uninstall/GDPR redaction, or session invalidation off `data.shop` can be made to apply another merchant's webhook body under a victim's `shop` identity — a cross-tenant data-integrity/confidentiality violation.

### Likelihood Explanation
Requires the attacker to already have at least one valid `(raw_body, hmac)` pair for the app. The easiest source is the attacker's own installed shop: a merchant installing the app receives genuinely-signed webhooks and, because signature verification is header-agnostic, can trivially replay one to the same endpoint with a modified `shop-domain` header. No access to `client_secret`, access tokens, or TLS interception is needed — only ordinary use of the app as an unprivileged merchant, which is within reach of any internet user who installs the target app.

### Recommendation
Bind the tenant/topic identity into the signed payload the gem actually verifies:
- Either require and verify the `shop-domain` (and ideally `topic`/`webhook-id`) headers against Shopify's registered webhook subscription for that shop, or
- Extend `to_signable_string` (or add a secondary check in `Registry.process`) so headers like `shop-domain` are cross-checked against a value independently known to the app (e.g. the app's own topic/callback registration, or matching against a store of currently-installed shops) before dispatching to the handler, rather than trusting the raw header value implicitly promised as "verified" in the docs.

### Proof of Concept
1. App has topic `orders/create` registered, and is installed on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimately HMAC-signed webhook for `attacker-shop.myshopify.com` to the app's callback URL; the attacker (who controls the receiving infrastructure/proxy for their own shop, e.g. via a reverse proxy in front of the app or by simply capturing the raw POST before their own app processes it) records the exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Attacker POSTs the identical `raw_body` and `hmac` header to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-webhook-id`/`x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Request.new` parses attacker-supplied headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled webhook content under the victim shop's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
