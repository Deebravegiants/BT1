### Title
Unvalidated octal wavelength parameter causes `assert_eq!` panic and orb-core process crash mid-signup - (File: `src/plans/biometric_capture/overcapture.rs`)

### Summary
`Configuration::parse_wavelength_configuration` assumes any `u8` produced by `parse_u8_octal` fits in 3 bits, but `parse_u8_octal` only rejects strings that are not valid base-8 digit strings — it does not bound the resulting numeric value. A crafted signup extension parameter (e.g. `"77"`, `"377"`) parses successfully to a `u8` value (e.g. 63, 255) whose `{:0>3b}` representation is longer than 3 characters, hitting the `assert_eq!` and panicking the whole orb-core process in the middle of a signup.

### Finding Description
`parse_u8_octal` is defined as: [1](#0-0) 
It uses `u8::from_str_radix(src, 8)`, which only validates that each character is a digit 0-7; it does not limit the *value* of the parsed octal number to 3 bits (0-7). Multi-digit octal strings such as `"77"` (=63) or `"377"` (=255) are valid `u8` values and pass this parse without error.

That value flows unchecked into `Configuration::new`: [2](#0-1)  and then into `parse_wavelength_configuration`: [3](#0-2) 
For values needing more than 3 bits, `binary_repr.chars().count()` is greater than 3, so `assert_eq!` panics with `"Overcapture wavelength parameter needs to be octal (<=3 bit)!"`. In a Rust binary this default panic behavior aborts/unwinds and terminates the orb-core process, since `Plan::from` is invoked synchronously while building the biometric capture plan and there's no `catch_unwind`/error-boxing at this call site — the panic is not converted into a `Result::Err`.

The wavelength parameter is derived from the signup extension configuration string, which is sourced through the QR/user data flow (`signup_extension_config` referenced in `src/plans/qr_scan/user.rs`) rather than validated against an octal-digit range before being handed to `parse_u8_octal`.

### Impact Explanation
A malformed extension parameter crashes the orb-core process while a signup is in progress, which is a denial-of-service against the current signup session (a "signup-state wedge"). This matches Worldcoin/Orb bounty categories for availability-impacting bugs against the signup pipeline. However, the claim that this leaves *un-flushed frames from the crashed session bleeding into a subsequent session's in-memory `Capture` buffers* is not substantiated by anything in this file or the surrounding code: a process crash terminates the whole orb-core binary, and any successor process (e.g., restarted by a supervisor) starts from a fresh `Plan`/`Capture` state — no shared/global mutable state that would carry stale frames across a full process restart is shown here. So the confirmed, code-supported impact is a crash/DoS of the in-progress signup, not demonstrated cross-session biometric data bleed.

### Likelihood Explanation
The panic is trivially reproducible: any octal string whose decimal value exceeds 7 (e.g., `"10"`=8, `"77"`=63, `"377"`=255) triggers it deterministically, and it does not require special privileges — only the ability to influence the extension configuration parameter string reaching `Configuration::from`. Repeatability is 100% given the same malformed input.

### Recommendation
Replace the `assert_eq!` with a bounds check on the parsed value (e.g., `u8::from_str_radix(src, 8).ok().filter(|v| *v <= 7).unwrap_or(default)` in `parse_u8_octal`, or validate `configuration_value <= 7` in `parse_wavelength_configuration` and return a `Result`/fall back to a default instead of panicking) so malformed input is handled gracefully rather than crashing the process.

### Proof of Concept
Unit test:
```rust
#[test]
fn wavelength_parameter_out_of_range_should_not_panic() {
    // "77" in octal parses to 63, which needs 6 bits, not 3.
    let value = parse_u8_octal("77", 1);
    assert_eq!(value, 63);
    // Currently this panics via assert_eq! inside parse_wavelength_configuration.
    let _ = Configuration::new(value, Duration::from_millis(1000));
}
```
Expected (fixed) behavior: `Configuration::new` should clamp/reject out-of-range values (e.g., fall back to default) instead of panicking. Currently, running this test aborts the test process with the `assert_eq!` panic message, confirming the crash path.
