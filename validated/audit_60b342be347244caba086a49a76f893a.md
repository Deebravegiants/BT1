### Title
Stale operator QR-code authorization window reused after `operator_qr_expiration_time` freshness check due to check-before-recompute ordering - ([File: src/plans/mod.rs])

### Summary
The reported bug class is a *check performed too early*: a value (`trueOrderSize`) is validated against a threshold, but is later reassigned/recomputed by a slow, externally-influenceable step, and the final value is never re-checked against that threshold before being used to finalize the transaction. The same "check-then-recompute-without-re-check" pattern exists in `MasterPlan::scan_remaining_qr_codes` in orb-core, where operator-session freshness (`operator_qr_expiration_time`) is validated as a match guard *before* an unbounded, externally-influenceable wait (`scan_user_qr_code`), and the freshness of `operator_data` is never re-validated once that wait completes and the signup is finalized.

### Finding Description
`scan_remaining_qr_codes` checks freshness of a previously-captured `operator_data` once, at the top of the match: [1](#0-0) 

```
QrCodes::Operator { operator_data }
    if operator_data.timestamp.elapsed() < operator_qr_expiration_time =>
{
    let Some((user_qr_code, user_data, user_qr_code_string)) =
        self.scan_user_qr_code(orb, &operator_data).await?
    else {
        break Ok(None);
    };
    break Ok(Some(ResolvedQrCodes {
        operator_data,
        user_qr_code,
        user_data,
        user_qr_code_string,
    }));
}
```

The freshness guard `operator_data.timestamp.elapsed() < operator_qr_expiration_time` is evaluated only once, at match time — analogous to the reported `_validateBondingCurveBuy` check `if (trueOrderSize < minOrderSize) revert SlippageTooHigh();` being evaluated before `trueOrderSize` is reassigned. After the guard passes, `self.scan_user_qr_code(orb, &operator_data).await?` is invoked [2](#0-1) , which internally loops scanning for the user QR code up to `self.qr_scan_timeout` [3](#0-2) . This is an operator-and-user-controlled wait (the user must physically present a QR code), during which real time elapses that is *not* counted against `operator_data.timestamp` again. Once `scan_user_qr_code` returns, the code immediately builds and returns `ResolvedQrCodes { operator_data, ... }` using the same, now-possibly-stale `operator_data`, without re-checking `operator_data.timestamp.elapsed() < operator_qr_expiration_time`. This `ResolvedQrCodes` (including the operator location binding `operator_data.location_data`) is subsequently used to build the debug report and PCP/enrollment credentials in `do_signup` [4](#0-3) .

Just as in the reported bug, the intended protection ("the operator authorization/location binding must be no older than `operator_qr_expiration_time` at the moment it is used to finalize the transaction") is only enforced against the *pre-recomputation* state, not the *final* state that is actually persisted/used.

### Impact Explanation
`operator_qr_expiration_time` exists specifically to bound how long an operator's scanned/validated QR-code session and location data can be reused for subsequent signups [5](#0-4) . If the freshness check is only enforced before the (potentially long, user-driven) wait for the user QR-code scan, a signup can complete and be attributed to an operator session/location that is, at the moment of use, already past its intended freshness window. This weakens the freshness guarantee the same way the original bug weakened slippage protection: the check exists in the code, but is bypassed for the actual final value used.

### Likelihood Explanation
Exploitability depends on how long `scan_user_qr_code` can block relative to `operator_qr_expiration_time`; with the default 23-hour expiration [6](#0-5)  this is unlikely to matter in practice, but the check-ordering flaw is structurally identical to the reported bug class and would become impactful if `operator_qr_expiration_time` is configured to a short/tight value (e.g., to enforce frequent operator re-verification), since `qr_scan_timeout` waits are not bounded against it after the guard passes.

### Recommendation
Re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` immediately before constructing `ResolvedQrCodes` (i.e., after `scan_user_qr_code` returns), not only as the match guard, mirroring the report's recommendation of moving the size/threshold check to the end of the function so it is enforced against the final value actually used.

### Proof of Concept
1. Configure a short `operator_qr_expiration_time` (e.g., a few seconds) for stricter operator re-verification.
2. Scan a valid operator QR code, entering the `QrCodes::Operator { operator_data }` branch where the freshness guard passes.
3. Delay presenting the user QR code until just after `operator_qr_expiration_time` has elapsed but before `self.qr_scan_timeout` expires (`scan_user_qr_code` at src/plans/mod.rs:942-976 keeps looping/waiting).
4. `scan_user_qr_code` succeeds; `scan_remaining_qr_codes` returns `ResolvedQrCodes` still carrying the now-expired `operator_data`, and `do_signup` proceeds to finalize the signup/enrollment using this stale operator binding, without any renewed freshness check.

    /// Scans the user QR-code.
    async fn scan_user_qr_code(
        &self,
        orb: &mut Orb,
        operator_data: &OperatorData,
    ) -> Result<Option<(qr_scan::user::Data, backend::user_status::UserData, String)>> {
        orb.set_phase("User QR-code scanning").await;
        dd_incr!("main.count.signup.during.general.user_identification_request");

        // QR capture starts now and timeout is updated after each scan attempt
        let qr_capture_start = Instant::now();
        loop {
            let scan_result = if let Some(new_timeout_ms) =
                self.qr_scan_timeout.checked_sub(qr_capture_start.elapsed())
            {
                if let Some(qr) = &self.user_qr_code_override {
                    tracing::info!("User QR-code provided from CLI");
                    Ok(qr.clone())
                } else {
                    orb.reset_rgb_camera().await?;
                    qr_scan::Plan::<qr_scan::user::Data>::new(Some(new_timeout_ms), false)
                        .run(orb)
                        .await?
                }
            } else {
                Err(qr_scan::ScanError::Timeout)
            };
            if let Some(result) = self
                .handle_user_qr_code(scan_result, orb, operator_data, Some(qr_capture_start))
                .await?
            {
                break Ok(result);
            }
        }
    }
