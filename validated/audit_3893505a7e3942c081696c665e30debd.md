### Title
Freezable collateral in AMM liquidity pools permits permanent lock of counterparty funds - (File: `substrate/frame/asset-conversion/src/lib.rs`, `substrate/frame/assets/src/lib.rs`)

### Summary
`pallet-asset-conversion` allows any signed account to `create_pool` for an arbitrary pair of `T::AssetKind` assets and pool them at a deterministic `pool_account` derived by `T::PoolLocator`. When the underlying token is a `pallet-assets` asset, the asset's `freezer` role can call the permissionless-from-role-perspective `freeze` extrinsic on *any* account holding that asset — including the pool's own account — which blocks all outgoing transfers from that account. This is structurally the same root cause as the reported issue: the protocol accepts a token as pooled/collateral without accounting for the token issuer's unilateral power to freeze the escrow/pool account, leading to fund lock for innocent counterparties (LPs).

### Finding Description
`pallet-assets` supports per-asset `Freezer`/`Admin` roles that can call `freeze(origin, id, who)` to set `AccountStatus::Frozen` on any account holding that asset: [1](#0-0) 
Once frozen, `reducible_balance`/transfer checks reject any transfer *from* that account with `Error::Frozen`, while transfers *into* the account remain allowed: [2](#0-1) [3](#0-2) 

`pallet-asset-conversion` lets any user create a pool for two `AssetKind`s and deposits/withdraws directly against a shared `pool_account`: [4](#0-3) 
`remove_liquidity` performs `T::Assets::transfer(asset, &pool_account, withdraw_to, ...)` to return the underlying assets to a liquidity provider: [5](#0-4) 

Because `pallet-assets`' asset creation assigns the creator as `owner`/`issuer`/`admin`/`freezer` and asset creation itself is generally permissionless (subject to a deposit), an attacker can: (1) create a new asset where they control the `freezer` role, (2) pair it against a legitimate/native asset via `create_pool`, (3) attract genuine liquidity providers to `add_liquidity`, and (4) call `Assets::freeze(origin, asset_id, pool_account)` on their own malicious asset targeting the `pool_account`. From that point, `remove_liquidity` and any swap leg that needs to move the frozen asset **out of** the pool account will fail with `Error::<T>::Frozen`, permanently trapping the counterparty side of the pool (the paired asset and/or LP principal) with no path for victims to recover funds through the pallet's own dispatchables. This mirrors the external report exactly: the protocol integrates an externally-controlled token without validating/guarding against the issuer's freeze capability over the pooled/collateral account.

I was not able to fully confirm within the available context whether `pallet-assets::create` (the permissionless dispatchable, as opposed to `force_create` which I did confirm requires root) is wired up as-is in every runtime configuration that also includes `pallet-asset-conversion` (e.g., Asset Hub), nor whether `CreatePoolOrigin`/`AssetKind` in specific production runtimes restrict pools to a curated, non-freezable asset allowlist. This limits certainty about real-world reachability in the exact deployed runtime, though the pallet code itself imposes no generic protection against this pattern.

### Impact Explanation
A malicious actor can permanently freeze one side of an AMM pool they seeded, causing legitimate liquidity providers' deposited funds (both assets, since `remove_liquidity` burns LP tokens and transfers both legs atomically — if one leg's transfer fails, the whole extrinsic fails) to become unwithdrawable. This is a direct, avoidable loss of user/LP funds via a state that cannot be repaired by any pallet-asset-conversion dispatchable (only the asset's own admin/freezer can `thaw`, and the attacker who is the freezer has no incentive to do so). This matches "Medium" severity precedent set in the referenced report — rare but concretely harmful to innocent (non-privileged) parties, and avoidable if checked/scoped at pool-creation or asset-registration time.

### Likelihood Explanation
Requires an unprivileged attacker only to: create a `pallet-assets` asset (a normal, non-privileged action gated by a deposit, not special permission), pair it in a pool with a pre-existing/legitimate asset, wait for third-party LPs to add liquidity, then call `freeze` on the pool account using their own asset's freezer role — all standard extrinsics reachable by any signed account. No governance, root, or bridge/node-level access is needed. The main variable affecting likelihood is whether the specific runtime restricts which `AssetKind`s can be paired in `pallet-asset-conversion` pools (e.g., allowlisting only sufficient/trusted assets); if such a restriction exists in a given runtime config, this reduces to theoretical, but the core pallet logic provides no such protection.

### Recommendation
- In `pallet-asset-conversion`, require or allow configuring an `AssetKind` filter/allowlist (e.g., via `T::AssetKind`/pool-creation origin checks) so pools can only be created for assets known not to have an active/mutable freezer, or restrict freezable non-sufficient assets from being poolable.
- Alternatively/additionally, expose a recovery path (e.g., an `AdminOrigin`-gated `force_remove_liquidity` or a `Preservation`/timeout-based override) that lets governance rescue LP funds if a pool account becomes frozen for one leg.
- Document in `pallet-assets`/`pallet-asset-conversion` that composing pallets accepting arbitrary `T::AssetKind` collateral/pool assets must verify the asset's `freezer`/`admin` is either `None`/burned or a trusted multisig/governance account before accepting deposits, analogous to checking SPL `freeze_authority == None` before accepting a token as collateral.

### Proof of Concept
1. Attacker (account `A`) calls `pallet_assets::create` (or a permissionless variant) to create asset `X`, becoming its `owner`/`admin`/`freezer`.
2. `A` calls `AssetConversion::create_pool(origin=A, asset1=Native, asset2=X)`, deriving `pool_account` via `PoolLocator`.
3. Victim LP `B` calls `AssetConversion::add_liquidity(..., asset1=Native, asset2=X, ...)`, transferring `Native` and `X` into `pool_account` and receiving LP tokens.
4. `A` calls `pallet_assets::freeze(origin=A, id=X, who=pool_account)` (see `substrate/frame/assets/src/lib.rs:1193-1216`), setting `pool_account`'s `AccountStatus::Frozen` for asset `X`.
5. `B` calls `AssetConversion::remove_liquidity(...)`; the internal `T::Assets::transfer(asset2=X, &pool_account, withdraw_to, amount2, Expendable)` (see `substrate/frame/asset-conversion/src/lib.rs:951-952`) fails with `pallet_assets::Error::Frozen` (see `substrate/frame/assets/src/tests.rs:1037-1051` for the underlying transfer-from-frozen-account behavior), causing the whole `remove_liquidity` call to revert and permanently trapping `B`'s principal in both assets.

		pub fn freeze(
			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			who: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let id: T::AssetId = id.into();

			let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
			ensure!(
				d.status == AssetStatus::Live || d.status == AssetStatus::Frozen,
				Error::<T, I>::IncorrectStatus
			);
			ensure!(origin == d.freezer, Error::<T, I>::NoPermission);
			let who = T::Lookup::lookup(who)?;

			Account::<T, I>::try_mutate(&id, &who, |maybe_account| -> DispatchResult {
				maybe_account.as_mut().ok_or(Error::<T, I>::NoAccount)?.status =
					AccountStatus::Frozen;
				Ok(())
			})?;

		pub(crate) fn do_create_pool(

			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// pay the setup fee
			let fee =
				Self::withdraw(T::PoolSetupFeeAsset::get(), creator, T::PoolSetupFee::get(), true)?;
			T::PoolSetupFeeTarget::on_unbalanced(fee);

			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};
