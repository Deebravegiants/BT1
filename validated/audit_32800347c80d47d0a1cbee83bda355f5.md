## Analysis

The reported bug class—missing L2 sequencer uptime validation on a Chainlink-based oracle—has a direct analog in Hyperbridge's `SimplexPaymaster` contract.

`SimplexPaymaster` prices ERC-20 gas payments using two Chainlink `AggregatorV3Interface` feeds (native/USD and token/USD) fetched by `_getOraclePrice`, which is reachable by any unprivileged UserOp sender via `_fetchDetails` → `_tokenPrice` (during ERC-4337 validation) and by the treasury-only `swapAndDeposit`. The staleness check only compares `block.timestamp - updatedAt` against `maxOracleAge`; it never verifies that the underlying L2 sequencer is actually up, unlike Chainlink's documented `L2 Sequencer Uptime Feed` pattern. [1](#0-0) 

The contract is explicitly deployed cross-chain including on sequencer-based L2s (Base, Optimism, Arbitrum are the standard Hyperbridge EVM deployment targets referenced throughout the SDK's Chainlink price-feed address maps). [2](#0-1) 

### Title
Missing L2 sequencer uptime check in `SimplexPaymaster::_getOraclePrice` allows stale-oracle exploitation during sequencer downtime - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` computes the token price charged for ERC-4337 gas sponsorship using two Chainlink `latestRoundData()` calls in `_getOraclePrice`. On sequencer-based L2 deployments (Base, Optimism, Arbitrum), this function only checks `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`, but never checks whether the L2 sequencer is currently up, as recommended by Chainlink's official L2 data feed guidance.

### Finding Description
`_getOraclePrice` is the sole gate on freshness for both `nativeOracle` and each token's `tokenOracle`: [1](#0-0) 

When an L2 sequencer goes down, the last Chainlink round remains "frozen" — `updatedAt` stops advancing but `block.timestamp` (as observed by the sequencer once it resumes, or by an L1-originated forced-inclusion transaction) can jump forward all at once when the sequencer catches up, or a user may submit a forced transaction directly to the L2 inbox from L1 during the outage. In either case, the price used by `_tokenPrice`/`_getOraclePrice` can be based on a round that is stale relative to real market conditions but still within `maxOracleAge`, since the staleness window is calculated from `updatedAt`, which itself may be innocuous while the real-world price has since diverged materially. There is no additional gate (e.g. `sequencerUptimeFeed.latestRoundData()` plus a grace period after restart) to reject pricing during or immediately after an outage.

This is directly reachable by any unprivileged UserOp sender: `_fetchDetails`, which is invoked by the ERC-4337 flow for every sponsored operation, calls `_tokenPrice(cfg)` → `_getOraclePrice` for both the native and token oracle. [3](#0-2) 

It is also reachable via the treasury-facing `swapAndDeposit` path that derives `amountOutMin` from the same oracle calls, though that entry point is treasury-gated. [4](#0-3) 

### Impact Explanation
If the native asset's real market price diverges significantly from the last-reported (but not yet "stale" by the `maxOracleAge` clock) Chainlink round during sequencer downtime or immediately following sequencer recovery, an attacker can submit UserOps priced off the frozen/incorrect rate. Because `_tokenPrice` sets `tokenPrice = nativeUsd * 10^tokenDecimals * (1+markup) / tokenUsd`, a mispriced `nativeUsd` (or `tokenUsd`) directly determines how much ERC-20 the paymaster charges versus how much native gas it fronts via the EntryPoint. An attacker exploiting a stale favorable rate can systematically underpay in ERC-20 tokens for the native gas the paymaster fronts, draining the paymaster's native EntryPoint deposit funded by the treasury — a direct theft of protocol funds analogous to the original `OracleAdapter` finding, where stale prices are relied upon incorrectly during sequencer downtime.

### Likelihood Explanation
L2 sequencer outages are a recurring, publicly observed event on Arbitrum, Optimism, and Base (the chains this contract targets, per the SDK's `CHAINLINK_PRICE_FEED_CONTRACT_ADDRESSES` and `SUPPORTED_ASSETS_CONTRACT_ADDRESSES` deployment lists). Exploiting a stale price requires only submitting a normal ERC-4337 UserOp (mode 0x00 or 0x02) with the exploitative token during or right after an outage — no special privileges, proofs, or governance access are needed, only correctly timed transaction submission, which is exactly the class of attack the Chainlink sequencer-uptime pattern is designed to prevent.

### Recommendation
Add an `AggregatorV2V3Interface` (or equivalent) sequencer uptime feed address per chain to `SimplexPaymaster`'s configuration, and in `_getOraclePrice` (or a wrapper called before it) verify `answer == 0` (up) and enforce a grace period (e.g. Chainlink's recommended `GRACE_PERIOD_TIME`) after `startedAt` before trusting any price feed read, reverting with a dedicated error (e.g. `SequencerDown`) otherwise — mirroring the fix already applied to `OracleAdapter::fetchExchangeRate` in the referenced report.

### Proof of Concept
1. Assume `SimplexPaymaster` is deployed on Arbitrum with `nativeOracle` = ETH/USD Chainlink feed and a registered stablecoin `tokenOracle`.
2. The Arbitrum sequencer halts. During the outage the ETH/USD Chainlink round is not refreshed, but `block.timestamp - updatedAt` (as later observed once the sequencer resumes or via an L1 forced transaction) remains below `maxOracleAge`, even though ETH's real market price has moved substantially (e.g., dropped sharply) during the outage.
3. An attacker submits a UserOp with mode `0x00` and `paymasterData` targeting the registered stablecoin, sized so that `_validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` reads the stale-but-"fresh-enough" ETH/USD round.
4. `_erc20Cost(maxCost, maxFeePerGas, tokenPrice)` computes an ERC-20 charge based on the outdated (higher) ETH price, letting the attacker pay disproportionately little stablecoin for the ETH gas the paymaster fronts via `entryPoint().depositTo`.
5. Repeating this across multiple UserOps during/after the outage window drains the paymaster's EntryPoint deposit, funded by governance/treasury, at a loss determined by the price divergence versus the oracle's actual round staleness.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
