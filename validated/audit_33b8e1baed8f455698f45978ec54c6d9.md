Confirmed analog: the phantom-order pricing pipeline applies a **fixed 10bps haircut** for any bid backed by a Uniswap V4 position, regardless of the position's actual pool fee tier. `decodePoolAndPositionInfo` reads the pool's real `fee` field from the `PoolKey` returned by `getPoolAndPositionInfo` [1](#0-0) , but that value is never consulted when deciding the haircut — `poolPriced` is a boolean derived only from whether the bid *declares any* V4 position tokenIds, not which fee tier those positions sit in [2](#0-1) . The design docs confirm the constant is intentionally a single hardcoded number rather than reading the real pool tier: "the pool tier stays a constant because it stands in for a Uniswap pool fee, which is not the gateway's to set" and "a knob invites the number to drift out of sync" [3](#0-2) [4](#0-3) .

This is the same bug class as the USSD report: a hardcoded fee/tier assumption is embedded in code that computes a swap-relevant amount from an AMM position, while Uniswap pools of the same pair exist across multiple tiers (0.01%/0.05%/0.3%/1%). A solver can pick which pool tier to sit its declared position in, and the aggregation gives every tier the identical 10bps discount regardless of its real cost.

### Title
Hardcoded Uniswap V4 haircut ignores the pool's actual fee tier, letting a solver bias the published phantom price - (File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts)

### Summary
`aggregatePhantomBids` haircuts every pool-priced phantom quote by a single hardcoded constant, `UNISWAP_QUOTE_HAIRCUT_BPS` (10bps), whenever a bid's declaration names any Uniswap V4 position, without reading the actual fee tier of the pool that position sits in.

### Finding Description
When resolving a phantom bid, the code decides whether to apply the pool haircut purely from the *presence* of declared position tokenIds (`poolPriced = declaration.uniswapV4Positions.length > 0`), then calls `applyUniswapQuoteHaircut` unconditionally for those bids [2](#0-1) . The position's real pool fee is available on-chain — `readV4Position` reads `getPoolAndPositionInfo` and decodes the `PoolKey`, which includes a `fee` field, via `decodePoolAndPositionInfo` [5](#0-4) [6](#0-5)  — but that field is discarded (`PoolAndPositionInfo` only keeps `currency0`, `currency1`, `poolKeyEncoded`, `tickLower`, `tickUpper`) and never fed back into the haircut decision. A separate flow (`UniswapV4FundingPlanner`) shows the same discipline of reading `poolKey.fee` from the identical ABI call, confirming the fee is readable and simply unused here [7](#0-6) . Since Uniswap V4/V3 pools for the same pair exist at multiple fee tiers (500/3000/10000, i.e. 0.05%/0.3%/1%, as enumerated elsewhere in this codebase's own pricing utilities) [8](#0-7) , a solver can back its bid with a position in a high-fee-tier (1%) pool while the pipeline discounts it as if it only cost 10bps, or conversely park in a low-fee pool and still absorb the flat discount that no longer matches the tier's real execution cost. The aggregation's own commit history acknowledges the tradeoff is deliberate and treats "the number drifting out of sync" as an accepted risk rather than something read live, unlike the sibling `protocolFeeBps` haircut which *is* read from the live contract for exactly this reason [9](#0-8) .

### Impact Explanation
This median price feeds `BIDS_RECEIVED`/phantom order pricing that downstream consumers (indexer entities, simplex's own filler) treat as the executable rate for a leg. Because the haircut does not reflect the pool tier actually backing a bid, a solver can systematically under-discount a quote sourced from an expensive pool, winning the liquidity-weighted median with a price that is not truly executable at that cost, or a competing legitimate low-fee-tier solver's honestly-priced bid gets equally discounted despite a real cost far below 10bps — degrading the fairness/accuracy of the published rate that other participants (auction takers selecting bids, other solvers reading the published snapshot) rely on. This is a state/price-integrity issue in a path directly reachable by any solver submitting a phantom bid to a legitimate order (an unprivileged, permissionless actor).

### Likelihood Explanation
High reachability: any solver can freely choose which Uniswap V4 pool tier to fund its declared position from, and the declaration mechanism accepts any owned position without validating or normalizing for tier. No special privilege is required — this is exercised on every phantom order that receives a V4-position-backed bid.

### Recommendation
Read the pool's actual `fee` from `PoolAndPositionInfo`/`getPoolAndPositionInfo` and apply a haircut proportional to that fee tier (or at minimum bucket the haircut per known tier: 0.05%/0.3%/1%), instead of a single flat `UNISWAP_QUOTE_HAIRCUT_BPS` applied uniformly to every V4-position-backed bid — mirroring how `protocolFeeBps` is already read live from the gateway rather than hardcoded.

### Proof of Concept
1. Solver A owns a Uniswap V4 position in a 1% (10000) fee-tier pool for `tokenOut`.
2. Solver A submits a phantom bid declaring that position's tokenId in `paymasterAndData` per `decodePhantomBidPaymasterAndData`.
3. `aggregatePhantomBids` sees `declaration.uniswapV4Positions.length > 0`, sets `poolPriced = true`, and discounts the quoted leg amount by only `UNISWAP_QUOTE_HAIRCUT_BPS` (10bps) via `applyUniswapQuoteHaircut`, regardless that the real cost of sourcing through that pool is ~100bps [10](#0-9) .
4. This under-discounted quote enters `weightedMedian` alongside honestly-priced wallet-funded or lower-fee-tier quotes, skewing the published `medianPrice` for the leg to a level the pool cannot actually deliver at.

/** A decoded `getPoolAndPositionInfo` return: the pool's key words plus the packed position info. */
export interface PoolAndPositionInfo {
	currency0: HexString
	currency1: HexString
	/**
	 * The ABI-encoded PoolKey exactly as returned, i.e. the first five words. A static struct's
	 * abi.encode IS its concatenated words, so `keccak256` of this slice is the pool id — no
	 * re-encoding, and no chance of the re-encoding disagreeing with what the chain hashed.
	 */
	poolKeyEncoded: HexString
	tickLower: number
	tickUpper: number
}

/** Decodes `getPoolAndPositionInfo(uint256)` return data (five static PoolKey words + info). */
export function decodePoolAndPositionInfo(data: string): PoolAndPositionInfo {
	const hex = data.startsWith("0x") ? data.slice(2) : data
	if (hex.length < 6 * 64) throw new Error("getPoolAndPositionInfo returned too little data")
	const { tickLower, tickUpper } = positionTicks(word(data, 5))
	return {
		currency0: addressFromWord(data, 0),
		currency1: addressFromWord(data, 1),
		poolKeyEncoded: `0x${hex.slice(0, 5 * 64)}` as HexString,
		tickLower,
		tickUpper,
	}
}
