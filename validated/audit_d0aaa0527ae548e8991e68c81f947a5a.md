### Title
`computeTonConnectHash` corrupts SHA-256 preimage for `timestamp >= 2**31` via 32-bit signed `>>=` in `numberToBigEndian` - ([File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts])

### Summary
`numberToBigEndian` in `packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts` uses JavaScript's `num >>= 8`, which performs `ToInt32` coercion before every shift. [1](#0-0)  For `timestamp >= 2**31`, `Number(timestamp)` becomes a value whose 32-bit signed representation is negative, so `>>` sign-extends with `1`s into the high bytes instead of zero-filling, producing an 8-byte big-endian encoding that diverges from the correct unsigned 64-bit BE encoding used to build the SHA-256 preimage in `computeTonConnectHash`. [2](#0-1) 

### Finding Description
The equality claimed to hold is: `computeIntentHash(multiPayload)` (locally computed by the SDK, via `computeIntentHashHashBytes` → `computeSignedTonConnectHash` → `computeTonConnectHash`) must equal the contract/relayer's own hash of the identical signed `ton_connect` payload. [3](#0-2) 

Tracing `numberToBigEndian(Number(timestamp), 8)`: for `bytes=8`, the loop runs `i` from 7 down to 0, and each iteration does `result[i] = num & 0xff; num >>= 8`. [1](#0-0)  Both `&` and `>>=` in JS coerce their left operand via `ToInt32`, which is a 32-bit signed operation. For `timestamp = 3000000000` (which is `> 2**31 - 1`), `ToInt32(3000000000)` yields a negative 32-bit value (`3000000000 - 2**32 = -1294967296`), whose bit pattern is `0xB2D05E00`. As the loop proceeds, `>>` performs an arithmetic (sign-extending) shift: once the sign bit is set, every subsequent shift fills the vacated high bits with `1`s rather than `0`s. By the time the loop reaches the top 4 bytes (`i = 3..0`), `num` has become `-1` (`0xFFFFFFFF`), so those bytes are written as `0xFF 0xFF 0xFF 0xFF` instead of the correct `0x00 0x00 0x00 0x00`. The correct unsigned 64-bit BE encoding of `3000000000` should be `00 00 00 00 B2 D0 5E 00`; the buggy function instead produces `FF FF FF FF B2 D0 5E 00` (or similar, verification would require running the exact loop, but the sign-extension effect on the high 4 bytes is unambiguous from the semantics of `ToInt32` + arithmetic `>>`).

This corrupted 8-byte segment feeds directly into the SHA-256 preimage assembled in `computeTonConnectHash`, so the resulting hash differs from any correctly-computed 64-bit BE hash (e.g., the one presumably computed on-chain/by the relayer using full-width unsigned encoding). [4](#0-3) 

The value comes directly from the signed `MultiPayload`'s `timestamp` field, which for the `ton_connect` standard is produced by the wallet/signer at signing time and is not re-validated or range-checked anywhere in this hashing path. [5](#0-4)  `IntentExecuter.signAndSendIntent` calls `computeIntentHash(multiPayload)` right before invoking the `onBeforePublishIntent` hook, and this locally-computed hash is what gets surfaced to integrators for tracking/persistence before the payload is sent to the relayer for actual publishing. [6](#0-5) 

No existing guard (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `FeeExceedsAmountError`, etc.) touches this hashing code path; the bug is a pure arithmetic defect in `numberToBigEndian`, and the only existing test for this file exercises address-representation equivalence, not large timestamps, so it does not catch the divergence. [7](#0-6) 

### Impact Explanation
The hash mismatch affects only the SDK's own client-side bookkeeping value (`intentHash` returned to `onBeforePublishIntent`), not any signed message content, amount, receiver, nonce, or fee — the actual TON Connect signature covers the raw payload fields, and the relayer/contract path is unaffected by this JS-side hash miscomputation. If an integrator relies on this locally-computed hash to correlate the published intent with its eventual on-chain settlement (e.g., for status tracking via `waitForSettlement`/`waitForIntentSettlement`), a mismatch could cause the integrator to treat a successfully settled intent as unmatched, requiring manual reconciliation. This matches the "withdrawal stuck until manual intervention" / "status misreport" categories, but only for the specific standard `ton_connect` and only when `timestamp >= 2**31` (≈ Feb 2038 for second-precision Unix time, or reachable immediately if an attacker/wallet supplies an arbitrarily large timestamp value directly, since it is not bounds-checked).

### Likelihood Explanation
Preconditions: the payload standard must be `ton_connect`, and the wallet-supplied `timestamp` value must be at or above `2**31` (2147483648). Under normal wall-clock operation (seconds-based Unix timestamps), this does not occur until year 2038, but there is no explicit validation rejecting an attacker-supplied out-of-range timestamp today. An unprivileged user fully controls their own wallet's signed payload, including `timestamp`, so they could self-trigger this divergence at zero cost, repeatably. However, the effect only corrupts the *locally-derived* hash used for the `onBeforePublishIntent` hook / client bookkeeping — I could not verify from this repo whether the relayer or contract independently recomputes and compares against this same locally-derived hash (that comparison logic, if any, lives outside what is indexed/available here, e.g. in `intents.near` or the relayer service, which are out of scope per the rules). Without confirming that an actual on-chain/relayer-side value is compared against this specific buggy computation in a way that blocks settlement or causes fund misdirection, the concrete "stuck until manual intervention" impact cannot be fully confirmed within this repo alone.

### Recommendation
Rewrite `numberToBigEndian` to avoid 32-bit signed bitwise operators entirely for the 8-byte case, e.g. using `BigInt`:
```ts
function numberToBigEndian(num: number, bytes: number): Uint8Array {
  const result = new Uint8Array(bytes);
  let big = BigInt(num);
  for (let i = bytes - 1; i >= 0; i--) {
    result[i] = Number(big & 0xffn);
    big >>= 8n;
  }
  return result;
}
```
This removes the `ToInt32` sign-extension problem and correctly supports 64-bit unsigned timestamps.

```ts
import { describe, expect, it } from "vitest";

function numberToBigEndian(num: number, bytes: number): Uint8Array {
  const result = new Uint8Array(bytes);
  for (let i = bytes - 1; i >= 0; i--) {
    result[i] = num & 0xff;
    num >>= 8;
  }
  return result;
}

function numberToBigEndianCorrect(num: bigint, bytes: number): Uint8Array {
  const result = new Uint8Array(bytes);
  let big = num;
  for (let i = bytes - 1; i >= 0; i--) {
    result[i] = Number(big & 0xffn);
    big >>= 8n;
  }
  return result;
}

describe("numberToBigEndian 64-bit overflow", () => {
  it("diverges from correct 64-bit BE encoding for timestamp >= 2**31", () => {
    const timestamp = 2 ** 31 + 100; // 2147483748
    const buggy = numberToBigEndian(Number(timestamp), 8);
    const correct = numberToBigEndianCorrect(BigInt(timestamp), 8);
    expect(buggy).not.toEqual(correct); // proves divergence
  });
});
```
This demonstrates the divergence in the byte-encoding helper feeding `computeTonConnectHash`'s SHA-256 preimage; a full end-to-end assertion would additionally call `computeTonConnectHash` with a `ton_connect` payload containing `timestamp: 3000000000n`/`3000000000` and show the resulting SHA-256 digest differs from a digest computed with a manually corrected 64-bit BE encoding of the same timestamp.

```typescript
	const parsedAddress = parseTonAddress(address);

	const schemaType = payloadSchema.type;
	switch (schemaType) {
		case "text": {
			const payloadPrefix = "txt";
			const payloadData = new TextEncoder().encode(payloadSchema.text);

			// Build the message to hash
			const parts: Uint8Array[] = [
				new Uint8Array([0xff, 0xff]),
				new TextEncoder().encode("ton-connect/sign-data/"),
				numberToBigEndian(parsedAddress.workchainId, 4),
				parsedAddress.address,
				numberToBigEndian(domain.length, 4),
				new TextEncoder().encode(domain),
				numberToBigEndian(Number(timestamp), 8),
				new TextEncoder().encode(payloadPrefix),
				numberToBigEndian(payloadData.length, 4),
				payloadData,
			];

			// Concatenate all parts

			let offset = 0;

				message.set(part, offset);
				offset += part.length;
```
