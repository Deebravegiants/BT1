Given the extensive investigation of alt.fun's graduation/brick-resistance machinery, the closest legitimate analog to CVE‑2023‑39328's class ("existing protection bypassed by crafted input, causing a crash/DoS") is a gap in the brick-resistance guarantee of `Bonding._noFeeSwapInput`.

### Title
Unguarded overflow in `_noFeeSwapInput` can revert and permanently brick `finalizeGraduation` - (`packages/contracts/src/Bonding.sol`)

### Summary
`Bonding._seedUniswapV2Direct`/`_seedRebalancing` is explicitly documented and tested as a "brick-resistance contract" — it must never revert under *any* hostile HyperSwap V2 pre-seed shape, because a revert leaves the token permanently stuck in `Lifecycle.Graduating` (no holder can exit, LP tokens never reach `LPLock`). [1](#0-0)  The documented defenses only catch the case where the rebalance swap *rounds to zero* (`s == 0` or `getAmountOut(s) == 0`), falling back to a direct mint. [2](#0-1)  However, `_noFeeSwapInput` itself computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` and its own natspec admits that "constructed adversarial inputs" that push the final divided result above `type(uint256).max` will cause OpenZeppelin's `Math.mulDiv` to revert rather than "silently truncate." [3](#0-2)  That revert happens *inside* `_noFeeSwapInput`, before the `s == 0` fallback check in `_pairRebalance` can run, so it is not caught by the documented brick-resistance layering.

### Finding Description
`_pairRebalance` calls `_noFeeSwapInput(reserveIn, reserveOut, targetN, targetD, maxSwap)` and only handles the return value `s == 0` as the signal to fall back to `_seedDirectMint`. [4](#0-3)  But if `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` itself exceeds `type(uint256).max`, the call reverts (a panic from OZ's `mulDiv`) instead of returning a value — there is no `try/catch` around this call. This is documented as an accepted, unguarded risk: "Constructed adversarial inputs that violate this would `revert` rather than silently truncate, which is the correct failure mode." [5](#0-4) 

`reserveIn`/`reserveOut` are read live from the HyperSwap V2 pair as `uint112` values (attacker-controlled via the well-documented front-run: `factory.createPair` + `transfer` + `pair.mint(attacker)` before `finalizeGraduation` runs). [6](#0-5)  `targetN`/`targetD` are `tokensForLP`/`ltFromPair`, cached at phase 1 from the curve's real state; `ltFromPair` in particular has no protocol-enforced upper bound (only `tokensForLP ≤ LP_RESERVE` is invariant). [7](#0-6)  By choosing `reserveIn`/`reserveOut` near the `uint112` ceiling on the attacker-controlled side of a pre-created pair, an attacker can push `reserveIn * reserveOut * targetN / targetD` past `type(uint256).max`, causing `_noFeeSwapInput` to revert with no way for `_pairRebalance`/`_seedRebalancing` to catch and fall back.

### Impact Explanation
`finalizeGraduation` is permissionless and is the only path that can move a token from `Lifecycle.Graduating` to `Lifecycle.Graduated`; there is no retry, no admin override, and no alternate `finalizeGraduation` entry point. [8](#0-7)  If the underlying call reverts unconditionally for every future invocation (the pre-seeded reserves are on-chain and durable), the token is permanently frozen in `Graduating`: trading is already frozen at phase 1, the curve-raised LT and 250M reserved tokens sit locked inside `Bonding` forever, and no holder can exit via either the curve (frozen) or the HyperSwap pool (never seeded). This is a permanent freeze of creator/trader/LP funds, which the "brick resistance" design was specifically built to prevent.

### Likelihood Explanation
Reaching the vulnerable branch requires the attacker to front-run a specific token's `finalizeGraduation` with a self-funded HyperSwap V2 mint pre-seed sized so that `reserveIn`/`reserveOut` sit far above the `DIRECT_MINT_PRESEED_BPS` band (so the rebalance path, not direct mint, is taken) and are large enough (near the `uint112` ceiling on one side) relative to `targetN`/`targetD` to overflow the final `mulDiv` division. This requires meaningful capital (funding `uint112`-scale reserves in one of the two assets) and precise sizing relative to that token's specific `tokensForLP`/`ltFromPair`, so it is not a cheap dust-griefing attack like the ones already defended against — but it is reachable by an unprivileged address with sufficient capital and is explicitly acknowledged as an unguarded revert path in the contract's own comments.

### Recommendation
Wrap the `Math.mulDiv` call (or the full `_noFeeSwapInput` call from `_pairRebalance`) in a `try/catch`, treating any revert the same as `s == 0` (fall back to `_seedDirectMint`), so a single degenerate/adversarial reserve ratio can never propagate a revert out of `finalizeGraduation`.

### Proof of Concept
1. Launch a token via `Zap.createToken`; buy enough on the curve via `Zap.buy` to cross the graduation threshold and cache a `(tokensForLP, ltFromPair)` pair in `pendingGraduation` (phase 1, `Bonding._enterGraduating`). [9](#0-8) 
2. Before anyone calls `finalizeGraduation`, front-run: call HyperSwap V2 `factory.createPair(token, lt)`, transfer attacker-held TOKEN/LT to the pair at a ratio and magnitude (one side near `type(uint112).max`) engineered so `reserveIn * reserveOut * targetN / targetD` from `_noFeeSwapInput`'s formula exceeds `type(uint256).max`, then call `pair.mint(attacker)`. [10](#0-9) 
3. Call `Bonding.finalizeGraduation(token)`. `_seedRebalancing` takes the rebalance branch (reserves outside the direct-mint band), calls `_pairRebalance` → `_noFeeSwapInput`, which reverts on the oversized `mulDiv` division. [11](#0-10) 
4. Every subsequent call to `finalizeGraduation(token)` reverts identically (the pre-seeded reserves persist on-chain), permanently freezing the token in `Lifecycle.Graduating`.

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    ///      `Math.mulDiv` keeps the intermediate product
    ///      `reserveIn * reserveOut * targetN` inside its 512-bit working
    ///      space, but the final result `... / targetD` must still fit in
    ///      uint256. Call sites must keep that invariant — in practice
    ///      both the V2 uint112 reserve cap and the bound that
    ///      `tokensForLP` ≤ `LP_RESERVE` and `ltFromPair` ≤ raised LT
    ///      are well inside the safe envelope. Constructed adversarial
    ///      inputs that violate this would `revert` rather than silently
    ///      truncate, which is the correct failure mode.
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
