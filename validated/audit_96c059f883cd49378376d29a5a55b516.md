### Title
Webhook `shop`/`topic`/`webhook-id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely by validating an HMAC over the raw request body, then trusts unauthenticated header values (`shop`, `topic`, `webhook_id`, `api_version`) to build the `WebhookMetadata` object passed to the app's handler. Because the HMAC only signs `@raw_body`, any of the header-derived fields can be freely modified by an attacker without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines: [1](#0-0) 
so `to_signable_string` returns only the raw body, never the shop domain, topic, or webhook id headers. `HmacValidator.validate` computes the signature over that signable string and compares it to the `hmac` value: [2](#0-1) 

`Registry.process` uses this validation as the sole authorization gate, then forwards `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from unauthenticated headers — directly to the app handler: [3](#0-2) 

The `shop` accessor itself is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload: [4](#0-3) 

The `api_secret_key` (the app's `client_secret`) used to sign webhooks is shared across every shop that has the app installed — it is not shop-specific. Consequently, a merchant who has installed the app on their own store receives genuine webhooks whose HMAC is valid for that same shared secret. Since the shop domain is excluded from the signed content, that merchant can capture a legitimately-signed webhook body+HMAC pair and replay it with the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) rewritten to name a different (victim) shop. `HmacValidator.validate` still succeeds because it only checks the untouched body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

This is the same binding-break class as the report's oracle issue: a value the code acts on (`shop`, used to route/attribute webhook data to a tenant) is not covered by the integrity check (`HMAC` over `raw_body` only) that is supposed to authenticate the whole message.

### Impact Explanation
Any app built on this gem that uses `request.shop` from `WebhookMetadata` to select which merchant's data/session to update (a standard, documented usage pattern) can be tricked into cross-tenant data corruption or disclosure: an attacker-controlled shop can forge webhook deliveries that appear to originate from an arbitrary victim shop, spoofing topic/shop attribution while still passing HMAC verification. This satisfies the "Critical — cross-tenant access" impact bar, since it lets one tenant impersonate another to this gem's own HMAC-authentication boundary without any token, secret, or privileged access beyond having the app installed on their own shop.

### Likelihood Explanation
Requires only that the attacker have the target app installed on any shop (a normal, unprivileged merchant action) and be able to send arbitrary HTTP requests to the app's webhook endpoint (which is public, per the webhook delivery model). No secrets, tokens, or elevated access are needed — only the ability to capture one legitimately delivered webhook and replay it with modified headers.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable content used by `HmacValidator`, or otherwise bind them cryptographically (e.g., verify `shop` against session/tenant storage keyed by data actually present in the signed body, or require Shopify's newer per-shop verification mechanisms) rather than trusting header values that fall outside the HMAC's coverage.

### Proof of Concept
1. App has two shops installed: `attacker.myshopify.com` and `victim.myshopify.com`, both under the same app `client_secret`.
2. Attacker triggers a webhook event on their own shop, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(secret, B)`.
3. Attacker POSTs the same body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and adjusts `X-Shopify-Topic`/`X-Shopify-Webhook-Id` as desired).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `to_signable_string` (`B`) against `H`.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: attacker-chosen, body: B, ...)`, believing the (attacker-supplied) event pertains to the victim shop.
