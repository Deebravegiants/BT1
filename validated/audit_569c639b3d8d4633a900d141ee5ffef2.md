Confirmed. The `shop` field passed to app webhook handlers via `WebhookMetadata#shop` [1](#0-0)  is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [2](#0-1)  and this header is never part of the HMAC-signed payload — only the raw body is signed [3](#0-2) .

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC-SHA256 over the raw request body, then trusts the `shop` value taken from an unauthenticated HTTP header to attribute the payload to a specific merchant.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to the app's handler [4](#0-3) . `HmacValidator.validate_signature` computes the expected signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value with `OpenSSL.secure_compare` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [3](#0-2) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from request headers without any cryptographic binding to the signature [6](#0-5) .

Because Shopify signs webhooks with the single, app-wide `api_secret_key` (not a per-shop secret), any shop that has the app installed can capture a body+HMAC pair for a webhook event it can trigger on its own store, then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because the signature check never inspects the `shop` header, and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata#shop` [7](#0-6)  to the app's `WebhookHandler#handle` [8](#0-7) .

The broken identity binding, expressed as an equality that the gem fails to enforce:
`shop` header value used by the handler == `shop` value cryptographically committed to by the HMAC — but the HMAC only commits to `raw_body`, never to `shop`.

Before the attacker's request: a genuine webhook for shop A has `(raw_body_A, hmac(raw_body_A))` and header `shop-domain: A`.
After the attacker's replay: the same `(raw_body_A, hmac(raw_body_A))` is sent with header `shop-domain: B` (a victim shop using the same app). `HmacValidator.validate` passes (body/hmac pair is genuinely valid), and `Registry.process` invokes the handler with `shop: "B"`, misattributing shop A's event data to shop B.

### Impact Explanation
Any app that keys per-tenant logic, storage writes, or authorization decisions off `WebhookMetadata#shop` (the documented and only field applications are given to identify which shop a webhook belongs to) can have data cross-attributed between shops that both use the app — this is a cross-tenant data confusion issue caused entirely by a field acted upon (`shop`) that the gem does not cover with the HMAC it validates.

### Likelihood Explanation
Any unprivileged internet user who installs the app on their own store (a normal, unprivileged action requiring no special access) can trigger events to obtain valid `(raw_body, hmac)` pairs and then freely replay them against the app's public webhook endpoint with a forged `shop-domain` header, since nothing in `Webhooks::Request` or `Registry.process` binds that header to the signature.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signable string that is HMAC-verified, or otherwise cryptographically bind them to the signed payload (e.g., derive/verify `shop` from a value embedded in and covered by the signed body, or require applications to cross-check the header `shop` against an independently known/registered shop identity before trusting it). At minimum, document that `WebhookMetadata#shop` is not authenticated and must not be used as a sole tenant-identification key.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook event whose body content is attacker-controllable within Shopify's constraints (e.g., an order/customer update with attacker-chosen fields), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends.
3. Replay that exact body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged header [9](#0-8) ; `Registry.process` calls `HmacValidator.validate(request)` which succeeds because it only checks `raw_body` against the HMAC [10](#0-9) ; the handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, processing attacker-supplied data under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
