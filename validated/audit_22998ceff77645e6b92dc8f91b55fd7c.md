### Title
Interest accrual overflows the RAY value domain before the index cap, permanently freezing all market operations - (File: common/src/rates/index.rs)

### Summary
The ImageMagick report's class — a code path that traps/crashes on attacker-influenced input, causing denial of service — maps onto the pool's accrual step: `calculate_supplier_rewards` and `update_supply_index` multiply the RAY-scaled share totals by the index in plain `i128` (`Ray::mul`), which panics with `MathOverflow` once `supplied * index` (or `borrowed * new_index`) exceeds the RAY value domain. Because `interest::global_sync` runs first inside every pool verb, once a market's scaled debt/supply is large enough for accrual to push the product past `i128::MAX`, the panic precedes the `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` clamps and the market is bricked forever: no `update_indexes`, `repay`, `withdraw`, `net_settle`, liquidation seizure, `clean_bad_debt`, or `recapitalize` can execute. This is proven by the in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`update_borrow_index` clamps the index itself at `MAX_BORROW_INDEX_RAY` (10^36), but `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` *before* that cap can protect anything — and the multiplication traps on overflow rather than saturating. The same applies to `update_supply_index`'s `supplied.mul(env, old_index)` at line 34. Per `docs/reference/formulas.md`, the token-to-RAY input maximum is ~170.14 billion whole tokens, so a whale can supply/borrow a position whose RAY value is already a large fraction of `i128::MAX`; sustained high-utilization accrual then pushes `borrowed * new_borrow_index` past the domain while `borrow_index < MAX_BORROW_INDEX_RAY`, so the cap "never engages". The panic is a typed `GenericError::MathOverflow` revert, but since `global_sync` is the first step of `Cache`-driven mutation in every entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `flash_loan`, `create_strategy`, `recapitalize`, `claim_revenue`, `update_indexes`), the revert is permanent — there is no code path that mutates the market without accruing first. `docs/reference/formulas.md:435` acknowledges "value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first" but provides no mitigation, and the accruing helpers have no saturating/try variant wired into accrual. [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
Permanent freezing of funds for all suppliers and permanent prevention of liquidation/bad-debt cleanup for all borrowers of the affected market. The test demonstrates concretely that after the cliff is crossed, `withdraw`, `repay`, and `update_indexes` all revert with `MathOverflow` while the index is still below its cap — supplier principal, accrued yield, and borrower collateral locked against the market become unrecoverable through any on-chain path, and governance cannot fix it because `update_params` and every other mutation also accrue first. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
Reaching the cliff needs a whale-scale position (≈10^29 base units for an 18-decimal asset, ~170 billion whole tokens) and years of high-utilization accrual, and requires governance-granted caps (`lift_caps`) large enough to admit the position — caps are validated with `require_cap_within_asset_domain` so they can legitimately be set near the asset's decimal domain. No privileged or malicious key is needed at trigger time: any account calling `update_indexes` (permissionless) detonates the freeze once the accrued value crosses `i128::MAX`, and the setup is just ordinary `supply`/`borrow` calls. On high-supply-cap markets this is reachable by a single well-funded unprivileged address; the timeframe and capital requirement keep it below high severity, consistent with the Medium DoS rating of the source advisory. [10](#0-9) [11](#0-10) 

### Recommendation
Make accrual saturate instead of trapping when the RAY value product overflows: in `calculate_supplier_rewards` and `update_supply_index`, use `mul_div_floor_saturating`/`try_mul_div_half_up`-style non-panicking paths (or clamp `new_borrow_index`/`new_supply_index` so that `borrowed * index` and `supplied * index` stay inside `i128`, i.e. cap the index at `i128::MAX / shares` before computing totals). Alternatively, add an emergency non-accruing escape hatch — e.g. allow `withdraw`/`repay` against the last committed indexes when `accrue_step` provably overflows — so a market that crosses the value ceiling degrades (no further interest) rather than bricking. As a defense-in-depth measure, bound admitted caps so `cap * MAX_SUPPLY_INDEX_RAY / RAY` cannot exceed the RAY value domain. [12](#0-11) [13](#0-12) 

### Proof of Concept
The repository's own harness test demonstrates the attack end-to-end (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`):

1. Attacker (unprivileged) supplies `10^9 * 10^18` units of an 18-decimal asset (`BIG18`) after caps are lifted to the asset-domain maximum.
2. Attacker supplies collateral in a second market and borrows 98% of the `BIG18` liquidity, pinning utilization on the steep segment of the interest curve.
3. Time advances; each year anyone calls the permissionless `update_indexes`. Within ~a decade the accrual's `borrowed * new_borrow_index` product overflows `i128` inside `calculate_supplier_rewards` while `borrow_index < MAX_BORROW_INDEX_RAY` (the cap never engages).
4. From that block onward, `update_indexes`, `withdraw(1)`, and `repay(1)` all revert with `MathOverflow` — permanently — because `interest::global_sync` runs `accrue_step` before any mutation. All supplier and collateral funds in the market are frozen. [14](#0-13)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}
```

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```

pub fn mul_div_floor_saturating(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    require_nonzero_divisor(env, d);
    if let Some(quotient) = x
        .checked_mul(y)
        .and_then(|product| div_floor_i128(product, d))
    {
        return quotient;
    }
    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    div_floor_i256(
        env,
        &x256.mul(&y256),
        &d256,
        quotient_is_nonnegative(x, y, d),
    )
    .to_i128()
    .unwrap_or(if quotient_is_negative(x, y, d) {
        i128::MIN
    } else {
        i128::MAX
    })
}
