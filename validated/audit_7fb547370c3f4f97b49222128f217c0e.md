### Title
Webhook shop identity spoofing — HMAC signs only the raw body, not the shop-domain header ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` binds the `x-shopify-shop-domain` header to a webhook event without that header ever being covered by the HMAC signature that `Utils::HmacValidator` verifies. The signature only authenticates the raw JSON body, so any actor who can obtain one validly-signed webhook body/HMAC pair (e.g. from their own shop's installation of the app) can resubmit it to the app's webhook endpoint with an arbitrary `shop` header and have the library accept it as an authentic webhook "from" that other shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the webhook purely by checking the HMAC over the body via `HmacValidator.validate(request)`: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` computes the signature only from `to_signable_string` (i.e. the raw body) against the app's `api_secret_key`: [4](#0-3) 

Since `api_secret_key` is a single, shared secret for the app across *all* installed shops (not per-shop), a valid HMAC only proves "this body was authenticated by holders of the app's client secret" — it does not prove which shop the request is attributed to. That attribution comes solely from the `shop` header, which is completely outside the signed content.

This breaks the identity binding: `hmac_authenticated_body == body` but the record is keyed by `shop_header != hmac_signed_shop` (no such binding exists at all). This is precisely the "shop authenticated versus the shop stored as a session key" pattern the report class targets — analogous to the PRBProxy bug where privileged state (there: plugins/permissions; here: shop attribution) is not re-validated/rebound when the trust boundary (there: proxy ownership; here: webhook shop identity) changes.

### Impact Explanation
Any merchant who installs the app (an unprivileged actor from the app's perspective — they only have their own store) legitimately receives HMAC-signed webhook deliveries for their own shop. Because the shop-domain header is unsigned, that same merchant can capture one valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still returns `true` (the body/HMAC pair is authentic), so `Registry.process` passes it through to the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain: [5](#0-4) 

Any app logic that keys state, session lookups, or side effects (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, order/product mutation triggers) off `WebhookMetadata#shop` can now be triggered against a shop the attacker does not own — a cross-tenant confusion/injection primitive that the app author has no way to detect using this library's API, since the library itself asserts the webhook as valid.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own shop to have the app installed and receive at least one real webhook (trivial — happens automatically on install/any event), and (2) network ability to POST to the app's public webhook endpoint with custom headers (also trivial, it's a public HTTP endpoint). No access token, `client_secret`, or privileged credential is needed — the whole point of the flaw is that the shop identity is not covered by the credential.

### Recommendation
Include the target shop domain in the HMAC-signed content (or derive/validate shop identity from a value that is itself covered by the signature), and reject webhooks where the declared `shop` header cannot be cryptographically tied to the signed payload. At minimum, document/enforce that `WebhookMetadata#shop` must not be trusted as authenticated shop identity unless the host app independently correlates it against a known/registered shop session, and consider binding the webhook HMAC to shop-specific keying material rather than a single app-wide secret.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook event (or waits for `app/uninstalled`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent to the app's public webhook URL.
2. Attacker resends the exact same request to the same webhook endpoint, but changes:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - keeps body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` using the app's `api_secret_key` and matches `H` — validation succeeds: [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)`, and the app processes the event as if it genuinely originated from `victim.myshopify.com`, even though `victim.myshopify.com` never sent this webhook.

          received_signature = verifiable_query.hmac
