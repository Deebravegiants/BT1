### Title
Insolvency from Balance-Blind Lock Accounting for Non-Standard (Fee-on-Transfer / Rebasing) Underlying Tokens - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken` locks an underlying ERC20 on the home chain and lets a peer mint/unlock the same nominal `amount` on the destination chain. The contract trusts `params.amount` as the true amount custodied, rather than measuring the actual balance delta received. If the configured `underlying` token is fee-on-transfer, deflationary, or a rebasing asset that can decrease balances outside of transfers (the same asset class flagged in the OETH report — tokens whose balance doesn't move 1:1 with nominal transferred amounts unless special handling is opted into), the wrapper's escrow becomes under-collateralized relative to the cross-chain liabilities it has dispatched.

### Finding Description
In `send()`, the contract does: [1](#0-0) 
It pulls tokens with `safeTransferFrom(msg.sender, address(this), params.amount)` and then unconditionally encodes `params.amount` into the dispatched `Message`, without ever checking the contract's actual balance before/after the transfer: [2](#0-1) 

On the destination side (or on the same chain for a return trip / timeout), `onAccept` and `onPostRequestTimeout` release exactly `message.amount` of the underlying from escrow: [3](#0-2) [4](#0-3) 

If `underlying` is a token whose held balance does not track the nominal transferred/locked amount 1:1 (fee-on-transfer tokens that deduct on transfer, or rebasing tokens like OETH-style assets that can shrink balances the custodian never opted to track), the escrow accumulates a shortfall each time `send()` is called or during idle custody between sends. Later `onAccept`/`onPostRequestTimeout` calls for other in-flight messages then draw down a shared pool that is short, so some legitimate unlock/refund calls will revert (insufficient balance) or drain the pool such that the last message(s) can never be honored. This is a permanent freezing of user funds tied to a normal `send()`/deliver flow, not a malicious-admin action — mirroring the OETH root cause where the *design* silently loses track of true backing without an explicit opt-in accounting for the asset's real behavior.

Same construction (and same missing balance-delta check) exists in the upgradeable variant: [5](#0-4) 

Notably, elsewhere in this same SDK, the team explicitly documents and defends against this exact asset class for `StreamingYieldVault` ("Standard ERC-20 only. Fee-on-transfer and rebasing assets desync the vault's accounting"): [6](#0-5) 
No equivalent balance-delta accounting or restriction exists in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`, and neither the contract nor its docs place any restriction on `configure()`'s `underlying` token type.

### Impact Explanation
A deployment that configures `underlying` to a non-standard token (fee-on-transfer, deflationary, or rebasing) accrues a persistent gap between the escrow's true balance and the sum of nominal amounts it has committed to honor across chains. This is a concrete path to permanent freezing of user funds: some senders' locked tokens can never be fully unlocked or refunded because the on-chain balance backing them has been silently reduced. Given `WrappedHyperFungibleToken` is a generic, reusable primitive intended to wrap "existing ERC20 tokens" (the docs give USDC and WETH as examples but impose no restriction), this reaches Medium/High severity for any deployment onto a token with these properties.

### Likelihood Explanation
Reaching this requires only ordinary use: a single unprivileged user calling `send()` against a wrapper configured (by the deploying team, not an attacker) with a fee-on-transfer or rebasing token, exactly as an unprivileged token bridger would interact with the contract in normal operation. No malicious admin, governance, or privileged action is needed — the flaw is triggered by the intersection of the contract's balance-blind accounting and the token's inherent transfer/rebase mechanics, matching the "design flaw" nature of the referenced OETH report.

### Recommendation
Compute locked amounts from actual balance deltas (`balanceBefore`/`balanceAfter`) around `safeTransferFrom` in `send()`, and use that measured amount (not `params.amount`) in the dispatched `Message`. Additionally, document/restrict `configure()` to standard, non-rebasing, non-fee-on-transfer ERC20s, or require the integrator to use an accounting wrapper (as `StreamingYieldVault` recommends) if a non-standard asset must be bridged.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` and `configure()` it with a fee-on-transfer token (e.g., one that burns 1% per transfer) as `underlying`.
2. User A calls `send(amount = 100)`; `safeTransferFrom` moves only 99 tokens into the wrapper (1 burned), but `Message.amount = 100` is dispatched.
3. Destination wrapper (or same-chain refund path) later attempts to unlock/refund 100 tokens against escrow that only received 99 net per such transfer; as more sends accumulate the shortfall, eventual `onAccept`/`onPostRequestTimeout` calls for remaining in-flight messages revert with insufficient balance, permanently freezing the corresponding users' funds.

            to: dest,

            timeout: params.timeout,
            fee: params.relayerFee,

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
