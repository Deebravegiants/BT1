### Title
Attacker-supplied pool addresses in `swap_xdr` execute arbitrary contract code beneath the signer's authorization tree, enabling full wallet drain - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The swap-aggregator's venue dispatcher invokes whichever pool/token addresses the caller-supplied `StrategyPayload.assets` registry names, with no allowlist or ABI validation — the direct analog of passing an unvalidated `model_path` into `AutoModel.from_pretrained(trust_remote_code=True)`. A rogue "pool" contract placed in a route runs arbitrary code on the call stack **below the signer's authorization entry**: any `token.transfer(victim, …)` it makes is recorded as a child of the signer's root auth node, and executes if the signer approves the simulation-produced auth tree — which every standard client auto-signs. The stolen amount is the victim's entire wallet of any token, unbounded by `min_out` or any protocol risk gate.

### Finding Description
`execute_strategy` decodes `swap_xdr` and runs the packed program in `contracts/swap-aggregator/src/lib.rs:250-255`. The `assets` registry — tokens, pools, LP share tokens — is fully attacker-controlled; `Program::decode` validates only byte layout and index ranges, never that an address is a real DEX pool or a specific token contract. `dispatch_hop` then calls `soroswap::swap`, `comet::swap`, etc., which `env.invoke_contract(&ctx.hop.pool, …)` the attacker-named address (`contracts/swap-aggregator/src/venues/mod.rs:34-40`, `contracts/swap-aggregator/src/venues/comet.rs:30-34`).

Inside that call, the malicious contract calls `token::Client::transfer(&victim, &attacker, &amount)` for any token the victim holds. Under Soroban invoker-auth recording, this attaches as a `sub_invocation` of the signer's root entry (`controller::swap_collateral` / `swap_debt` / `repay_debt_with_collateral` / `multiply`, or `Router::execute_strategy` directly). The threat model itself documents this: "a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount" (`docs/explanation/threat-model.md:154-165`). The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-268` proves end-to-end that simulation records the theft under the caller's entry and that enforcing mode executes it once the poisoned tree is signed.

### Impact Explanation
Theft of user funds — the entire wallet balance of every token held by the signing victim, including tokens the protocol never listed. The victim only sees a normal `swap_collateral`/`execute_strategy` authorization request; the rogue `transfer` hides as a child node of the simulated tree that mainstream wallets and `assembleTransaction` sign without inspection. Neither the payload's `min_out` nor the controller's post-swap health-factor gate bounds the loss, because the stolen transfer is authorized, not measured.

### Likelihood Explanation
An unprivileged attacker deploys one contract (`RogueHopPool`-shaped: one `swap` entrypoint performing a `transfer` of a victim token) and injects it as a hop `pool` address in a `swap_xdr` served to victims — via a lookalike quote endpoint, phishing front-end, or a compromised/malicious route builder. Crafting the payload requires no privileges: `assets[i]` is arbitrary. Exploitation is deterministic whenever a victim signs the simulated tree, which is the default client flow for every router swap and every controller strategy embedding a route.

### Recommendation
Enforce venue allowlisting at decode or dispatch time: maintain an owner-curated registry of pool addresses per venue (or pool-code-hash allowlist) and reject hops whose `pool`/`token_in`/`token_out` are not registered. At minimum, hard-verify that each hop `token_in`/`token_out` equals a protocol-listed asset and that `pool` resolves to a factory-verified instance for the declared venue. Documenting "clients must decode the auth tree" is insufficient — the contract should not place unvetted code beneath user signatures.

### Proof of Concept
1. Attacker deploys `RogueHopPool` storing `(victim, victim_wallet_token, attacker, amount)` in `PLAN`; its `swap()` calls `token::Client::new(&env, &wallet_token).transfer(&victim, &attacker, &amount)` (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:54-72`).
2. Attacker builds a `StrategyPayload` whose swap instruction's `idx_a` points to `RogueHopPool`, with a fair-looking route so the victim signs.
3. Victim calls `controller::swap_collateral` (or `Router::execute_strategy`) with that `swap_xdr`. Simulation runs the rogue pool; the wallet-token `transfer(victim → attacker)` is recorded under the victim's root auth entry (test lines 194-227 show the recorded tree and `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`).
4. The victim's wallet signs the simulated tree; in enforcing mode the host accepts the child transfer because it is now authorized — `try_swap_with_signed_tree` succeeds and the full `WALLET_BALANCE` moves to the attacker while the swap still completes normally (lines 259-268). #[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
