### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while the `shop` (tenant) identity used by the handler comes from the unauthenticated `x-shopify-shop-domain` header. `Utils::HmacValidator` only verifies the body against the HMAC, so `shop` can be forged independently of the signature that "proves" the payload is genuine.

### Finding Description
`Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which computes an HMAC over `request.to_signable_string` and compares it to `request.hmac`: [1](#0-0) [2](#0-1) 

`Request#to_signable_string` is defined to return only `@raw_body`: [3](#0-2) 

But `Request#shop` — the tenant identity later handed to the application's webhook handler as `WebhookMetadata#shop` — is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed material at all: [4](#0-3) [1](#0-0) [5](#0-4) 

The identity binding that should hold is: `shop used by handler == shop the body/HMAC was actually generated for`. Because the HMAC only covers the raw body bytes and never binds `shop`, `topic`, `webhook-id`, or `api-version` headers, an attacker who owns a legitimate Shopify store can trigger a real webhook (obtaining a valid `raw_body` + `hmac` pair signed with the app's real `client_secret`/`api_secret_key` for their own shop), then replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will call the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the attacker-chosen victim shop domain.

This breaks the equality: `verified_bytes (body) == identity_bytes (shop header)`. The gem verifies the body but the application-facing identity (`shop`) is parsed independently and trusted without being part of the verified bytes.

### Impact Explanation
Applications built on this gem's webhook handling almost universally look up the tenant's session/access-token or write to per-shop storage keyed by `data.shop` from `WebhookMetadata`. Since `shop` is never authenticated by the HMAC, an attacker can cause the application to attribute a webhook body to (and act on behalf of) a shop they do not own — a cross-tenant write/read primitive. This satisfies the "cross-tenant access" criterion for Critical severity, since the trust boundary between tenants (shops) that the HMAC is supposed to enforce is not actually covering the datum (`shop`) used to select the tenant.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own legitimate, registered Shopify store (any developer/merchant can install a Shopify app and receive real signed webhooks for their own shop), and (2) the ability to POST an HTTP request with arbitrary headers to the app's public webhook endpoint — no access token, `client_secret`, or victim credentials are needed. This is a fully unprivileged, internet-reachable attack once the attacker has any store install of the target app.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook-id`, `api-version`) into the signed/verifiable material, or otherwise cryptographically bind them to the verified body — e.g., include the shop domain in `to_signable_string`, or require callers to independently verify the header against a value derived from a trusted source (such as a previously stored, verified shop for that webhook subscription) rather than trusting the header outright. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant selection without additional verification.

### Proof of Concept
1. Attacker registers/installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the legitimate `x-shopify-hmac-sha256` header Shopify sent — both are valid and signed with the real `client_secret`.
2. Attacker replays this exact captured body/HMAC pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, storing `shop = "victim.myshopify.com"` while `@raw_body`/`hmac` are unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which HMACs only `@raw_body` — the check passes because the body/HMAC pair is genuinely valid (just for a different shop).
5. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the host application processes/stores data as if it legitimately originated from `victim.myshopify.com`, even though `victim.myshopify.com` never sent this webhook.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
