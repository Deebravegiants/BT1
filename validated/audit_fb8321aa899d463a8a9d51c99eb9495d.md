Confirmed: the Tron variant of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) never verifies the actual token balance received against the requested `order.inputs[i].amount`, unlike the main EVM `IntentGatewayV2.sol`, which explicitly measures `balanceOf` before/after every transfer for exactly this reason.

### Title
IntentGatewayV2 (Tron) escrows more than it actually holds for fee-on-transfer input tokens, insolvent escrow across orders - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` in the Tron `IntentGatewayV2` credits escrow with `reducedInputs[i].amount` (the user-declared amount minus protocol fee) instead of the amount the contract actually received from `safeTransferFrom`. For a fee-on-transfer (or otherwise non-standard) ERC-20 used as an order input, the contract receives less than `order.inputs[i].amount` but still books the full (fee-reduced) amount into `_orders[commitment][token]`.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally does `_orders[commitment][token] += reducedInputs[i].amount;` — with no balance-before/after check. `reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (the user-supplied requested amount) minus the protocol fee: [2](#0-1) 

This is structurally the same assumption error as the Sherlock M-2 finding: `AlphaBetaSplitter` assumed `withdrawAll()` on `TrueFiStrategy` returned the full underlying balance instead of checking what was actually returned, leading to an accounting figure that diverges from the real on-chain balance. Here, the gateway assumes `safeTransferFrom` moved the full requested amount into the contract instead of checking the actual balance delta, so `_orders[commitment][token]` can be inflated above the contract's real token holdings for that input.

The predispatch branch of the same file has a `dust`/balance check (`balance = IERC20(token).balanceOf(dispatcher); ... uint256 dust = balance - requiredAmount;`) but that check is against the call-dispatcher's balance, not a before/after delta capturing fee-on-transfer loss on the initial `safeTransferFrom(msg.sender, dispatcher, amount)` call for predispatch assets, and it still credits `reducedInputs[i].amount`, not the measured `balance`, into escrow — see line 441: `_orders[commitment][token] += reducedInputs[i].amount;`. The main, non-Tron `IntentGatewayV2.sol` explicitly avoids this by re-measuring `IERC20(token).balanceOf(address(this))` before and after every transfer and mutating `order.inputs[i].amount` to the real received amount before computing `reducedInputs`/escrow, confirming that this exact class of bug was previously recognized and fixed for the primary EVM deployment but the fix was not carried over to the Tron contract: [3](#0-2) 

### Impact Explanation
Escrow accounting (`_orders[commitment][token]`) becomes an IOU exceeding the contract's real token balance for that asset. Because escrow is a shared per-token ledger across all orders in the gateway (not a segregated balance), over-crediting one order's escrow means that a legitimate `_withdraw` call for that or another order using the same token can drain tokens that back other users' escrowed positions, causing insolvency: some subsequent order's `withdraw()` or `cancelOrder()` will either revert (freezing funds for that user, since the token balance is insufficient) or, if enough headroom exists from other honest deposits, silently transfer out tokens that rightfully belong to a different user's order. This satisfies the "permanent freezing of funds" / "unbacked" ledger criterion in a solver/user-reachable path (`placeOrder` is called by any user with a fee-on-transfer or otherwise deflationary ERC-20).

### Likelihood Explanation
Any unprivileged user can trigger this by placing an order (`placeOrder`) with a fee-on-transfer, rebasing, or otherwise non-1:1-transfer ERC-20 token as an input on Tron's IntentGatewayV2 deployment. No admin/relayer cooperation is required; a single `placeOrder` call is sufficient to under-fund escrow relative to what is recorded. The bug is deterministic for any token exhibiting transfer-amount deviation and requires no adversarial market conditions, unlike the original TrueFi liquidity-lag scenario.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom` in the Tron contract's non-predispatch branch, and compute `reducedInputs`/escrow credit from the actual received delta rather than the caller-declared `order.inputs[i].amount`. Apply the same balance-delta correction to the predispatch branch's final escrow credit (line 441) so `_orders[commitment][token]` always equals real held balance.

### Proof of Concept
1. Deploy/target the Tron `IntentGatewayV2` with a fee-on-transfer ERC-20 (e.g., 5% transfer tax) registered as a valid input token, `protocolFeeBps = 0` for simplicity.
2. Attacker calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000}`.
3. `safeTransferFrom(attacker, address(this), 1000)` executes; due to the 5% fee, the gateway actually receives only 950 tokens.
4. `reducedInputs[0].amount` = 1000 (no protocol fee), so `_orders[commitment][FOT] += 1000` — 50 more than the contract actually holds.
5. Repeat or combine with a genuine user's honest (non-FOT) escrow of the same token address space is not needed; simply attempt `withdraw()`/`cancelOrder()` on this order for the full 1000, or have a subsequent legitimate order on the same token find its available balance insufficient — the shared token balance is now short by 50 per repetition, and repeated exploitation compounds the shortfall until withdrawals begin reverting or draining other users' escrow.

*Note*: I could not fully verify whether `_withdraw`/`cancelOrder` in the Tron contract's `IntentsBase`/`IntrinsicIntents` counterparts have an independent balance check that would catch this discrepancy before payout, since only the main (non-Tron) `IntentsBase.sol` was inspected in depth; if the Tron variant reuses the same `_withdraw` transfer-based logic without a balance guard, the insolvency described above is directly exploitable.
