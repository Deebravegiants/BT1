### Title
Unchecked, caller-chosen `circomData.timeStamp` in `DepositOnChainUtxosExternalAction` lets an attacker engineer commitment/nullifier collisions and permanently freeze a victim's legitimate deposit - (File: `contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction` builds on-chain UTXO commitments using `circomData.timeStamp` (plus a local index offset) instead of `block.timestamp`, exactly as the contract's own doc-comment states: "their timestamps come from `circomData.timeStamp` rather than from the block." [1](#0-0)  This field is a fully attacker-controlled `uint256` with no range check, no monotonicity check against `block.timestamp`, and no uniqueness check against previously used values. [2](#0-1)  This is the direct analog of the AI Arena bug: a value that feeds a downstream commitment/state (weight/element there, `timeStamp` here) is taken from user input with no validation, and it directly determines equality/uniqueness properties the rest of the system depends on.

### Finding Description
The on-chain commitment is `hash4(amount, erc20TokenAddress, stealthAddress, timeStamp)` [3](#0-2) , and the nullifier used to prevent double-spend is `Poseidon(commitment, signature)` where `signature` is derived deterministically from `commitment` and the spender's `nullifyingPrivateKey` [4](#0-3) . Critically, the nullifier depends only on the **value** of the commitment, not on which leaf/index in the Merkle tree it occupies [5](#0-4) .

Because `timeStamp` is not tied to `block.timestamp` and is fully caller-chosen, any unprivileged EOA calling `Hinkal.transact()` (self-generating an EdDSA keypair and message, which is trivial since no funds are being spent in a deposit) can:
1. Choose a target victim's public stealth address (`H1x, H1y, stealthAddress`), which is meant to be publicly reusable for receiving payments.
2. Choose the exact `(amount, erc20TokenAddress)` pair and a `timeStamp` value equal to one that a legitimate future depositor is likely (or can be made, e.g. via front-running/predictable timing) to use for a genuine deposit to the same victim/stealth-address/amount/token.
3. Actually transfer the matching real token amount (`transferERC20TokenFrom`) to satisfy the balance checks [6](#0-5) , producing a commitment `C` that is bit-for-bit identical to the one the legitimate depositor will later produce.

Both real deposits get inserted as distinct leaves in the Merkle tree via `insertMany` [7](#0-6) , but since the nullifier is a pure function of the commitment value (not the leaf index), spending either leaf produces the exact same nullifier. Once the victim spends the first of the two identical-commitment leaves, `insertNullifiers` marks that nullifier as used [5](#0-4) , permanently blocking any future attempt to spend the second (equally real, equally funded) leaf - the victim's second real deposit becomes permanently frozen even though both deposits were independently, fully backed by real transferred tokens.

### Impact Explanation
This breaks the leaf/commitment uniqueness assumption the protocol relies on for correct nullifier accounting, and results in **permanent freezing of a user's funds** that were never the attacker's own balance - the frozen deposit is real money transferred by a legitimate third-party depositor, not merely the attacker griefing themselves. This matches the "Critical" impact bucket (permanent freezing of user funds via a leaf/root/commitment invariant the tree never uniquely enforces).

### Likelihood Explanation
Likelihood is bounded by the difficulty of colliding `(amount, erc20TokenAddress, stealthAddress, timeStamp)` exactly. `stealthAddress` values are meant to be publicly shared for receiving deposits (a core design goal of stealth-address schemes), and `amount`/`erc20TokenAddress` for common flows (e.g., round-number payments to a known merchant/donation address) are often predictable or attacker-chosen ahead of time. Since `timeStamp` is not derived from `block.timestamp` and has no server-side entropy or nonce requirement, an attacker who can predict or influence the value a future depositor will use (e.g. by colluding, front-running a known/expected value such as `0`, or simply exploiting depositors who reuse the same timestamp/nonce convention) can force the collision deterministically. This requires no privileged role, only an unprivileged EOA able to call `Hinkal.transact()` with a self-crafted proof for a deposit-only path.

### Recommendation
Do not let external callers freely choose the timestamp field embedded in the commitment for on-chain-created UTXOs. Either:
- Force `utxo.timeStamp` to be derived from `block.timestamp` (as done in `ExternalActionSwap.sol` and `Hinkal._createProoflessDepositCommitments`) instead of `circomData.timeStamp`, or
- Add a strictly monotonically increasing per-recipient nonce/counter enforced on-chain, or
- Include a fresh, unpredictable/random on-chain value (e.g., `block.number`, a global commitment counter, or `keccak256` of prior leaf count) into the commitment preimage so duplicate commitments for the same `(amount, token, stealthAddress)` cannot be engineered by an attacker.

### Proof of Concept
1. Attacker observes/knows a victim's public stealth address `S` (published for receiving payments) and predicts/colludes on a future legitimate deposit of `1000 USDC` to `S` that will use `timeStamp = T`.
2. Attacker calls `Hinkal.transact()` targeting `DepositOnChainUtxosExternalAction`, with `circomData.stealthAddressStructure = S`, `erc20TokenAddresses = [USDC]`, `utxoAmounts = [[1000e6]]`, `circomData.timeStamp = T`, and self-generated EdDSA keys/proof (no real secret needed since this is a pure deposit path with `inputNullifiers` and `amountChanges` forced to `0`) [8](#0-7) . Attacker pays the real 1000 USDC themselves.
3. The commitment `hash4(1000e6, USDC, S, T)` is inserted at leaf index `X`.
4. Later, the legitimate depositor's real transaction (paying their own 1000 USDC to `S` with the same `T`) inserts the identical commitment at leaf index `Y`.
5. Victim spends leaf `X` first via normal `transact()`, recording nullifier `N = Poseidon(C, signature)`.
6. Victim attempts to later spend leaf `Y` (the legitimate, independently-funded deposit) - the circuit produces the same nullifier `N`, and `insertNullifiers` reverts with `"Nullifier cannot be reused"` [9](#0-8) , permanently freezing the second, fully-backed 1000 USDC deposit.

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) external override onlyAllowedRecipient returns (UTXO[] memory utxoSet) {
        uint256 tokenCount = circomData.erc20TokenAddresses.length;
        require(
            tokenCount > 0 && deltaAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: token count mismatch"
        );

        address userAddress = circomData.originalSender;
        require(
            userAddress != address(0),
            "DepositOnChainUtxosExternalAction: Invalid originalSender"
        );

        uint256[][] memory utxoAmounts = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (uint256[][])
        );
        require(
            utxoAmounts.length == tokenCount,
            "DepositOnChainUtxosExternalAction: metadata length mismatch"
        );

        utxoSet = new UTXO[](countUtxos(utxoAmounts));

        uint256 utxoIndex = 0;
        for (uint256 i = 0; i < tokenCount; i++) {
            require(
                deltaAmounts[i] == 0,
                "DepositOnChainUtxosExternalAction: Delta amount must be zero"
            );

            address tokenAddress = circomData.erc20TokenAddresses[i];
            uint256 tokenTotal = 0;

            for (uint256 j = 0; j < utxoAmounts[i].length; j++) {
                uint256 amount = utxoAmounts[i][j];
                require(
                    amount > 0,
                    "DepositOnChainUtxosExternalAction: UTXO amount must be positive"
                );
                tokenTotal += amount;

                utxoSet[utxoIndex] = UTXO({
                    amount: amount,
                    erc20Address: tokenAddress,
                    stealthAddressStructure: circomData.stealthAddressStructure,
                    timeStamp: circomData.timeStamp + utxoIndex
                });
                utxoIndex++;
            }

            if (tokenAddress != address(0) && tokenTotal > 0) {
                transferERC20TokenFrom(
                    tokenAddress,
                    userAddress,
                    msg.sender,
                    tokenTotal
                );
            }
        }

        emit BlockedUtxosCreated();
    }

  signal output out;
