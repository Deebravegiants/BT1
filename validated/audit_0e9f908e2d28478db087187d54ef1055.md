### Title
Unbounded RAY-scale market totals permanently freeze a lending market - (File: `common/src/rates/index.rs`) [1](#0-0) 

### Summary
A very large market can make the aggregate `borrowed * borrow_index` or `supplied * supply_index` value exceed `i128::MAX` before the configured index cap is reached, causing every subsequent interest-accrual attempt to panic and permanently freezing withdrawals, repayments, liquidations, and bad-debt processing for that market. [2](#0-1) [3](#0-2) 

### Finding Description
`update_borrow_index` multiplies the stored index by the interest factor before applying `MAX_BORROW_INDEX_RAY`, while `calculate_supplier_rewards` separately multiplies aggregate scaled debt by both the old and new indexes. [4](#0-3) [1](#0-0) 

The same i128 ceiling applies to supplier accounting because `update_supply_index` computes `supplied * old_index` before distributing rewards. [5](#0-4) 

`global_sync` only advances `last_timestamp` after every accrual chunk succeeds, so once one of these multiplications overflows, every retry re-enters the same overflowing interval. [6](#0-5) 

Every ordinary pool mutation leg calls `load_leg`, which calls `synced_market`, which unconditionally performs `global_sync` before the requested accounting mutation. [7](#0-6) 

Consequently, controller-reachable `withdraw`, `repay`, `supply`, `borrow`, liquidation legs, and the permissionless `update_indexes` path all fail at the same accrual precondition after the cliff is reached. [8](#0-7) [9](#0-8) [10](#0-9) 

The repository already contains a regression test documenting this state: a one-billion-token, 18-decimal market at 98% utilization eventually makes `scaled_to_original` overflow before `MAX_BORROW_INDEX_RAY` is reached, and subsequent withdrawal and repayment attempts revert with `MathOverflow`. [3](#0-2) 

### Impact Explanation
All supplier principal and yield in the affected `(hub_id, asset)` market become permanently inaccessible because withdrawals cannot pass the mandatory accrual phase. [11](#0-10) [3](#0-2) 

Borrowers cannot repay and liquidators cannot execute debt repayment or collateral seizure, so underwater positions can neither be cured nor closed. [12](#0-11) [7](#0-6) 

Because `last_timestamp` is not committed before the panic, there is no path that skips or bounds the overflowing interval; this is a permanent freezing-of-funds condition rather than a transient rejected transaction. [6](#0-5) 

### Likelihood Explanation
Triggering the cliff requires a validly configured market to admit an extremely large position, with the documented reproduction lifting caps to the 18-decimal maximum and using a curve configured for 100% maximum utilization. [13](#0-12) [14](#0-13) 

The reproduction uses `1e27` base units of an 18-decimal asset and borrows 98% of it, requiring extraordinary capital and sustained high utilization, but no privileged runtime call is needed to keep the poisoned state alive once such a market and position exist. [15](#0-14) [10](#0-9) 

The required aggregate-value boundary is deterministic: once scaled supply or debt is near `i128::MAX / index`, any positive accrual can cross the representable range regardless of whether the fixed index cap has been reached. [1](#0-0) [5](#0-4) 

### Recommendation
Compute index updates and aggregate market values with overflow-aware intermediates, and dynamically clamp each index to `min(protocol_cap, i128::MAX / aggregate_scaled_shares)` before evaluating supplier rewards or supplied value. [16](#0-15) 

Accrual should commit a bounded state instead of panicking, because a fixed index cap cannot guarantee that `scaled_shares * index` remains representable for every admitted market size. [2](#0-1) [17](#0-16) 

Add boundary tests proving that, at `borrowed * borrow_index > i128::MAX` or `supplied * supply_index > i128::MAX`, `update_indexes`, `withdraw`, `repay`, liquidation, and `clean_bad_debt` still complete under the selected clamping or bad-debt policy. [7](#0-6) [3](#0-2) 

### Proof of Concept
Assuming an 18-decimal market whose caps and utilization limits permit the documented book, one unprivileged address can execute the following calls:

```text
account_id = controller.supply(
    attacker,
    0,
    spoke_id,
    [({ hub_id, asset: collateral_asset }, sufficient_collateral)]
);

controller.supply(
    attacker,
    account_id,
    spoke_id,
    [({ hub_id, asset: borrow_asset }, 1_000_000_000 * 10^18)]
);

controller.borrow(
    attacker,
    account_id,
    [({ hub_id, asset: borrow_asset }, 980_000_000 * 10^18)],
    None
);
```

The attacker then repeatedly calls `controller.update_indexes(attacker, [{ hub_id, asset: borrow_asset }])` as ledger time advances; once aggregate scaled debt times the accrued borrow index exceeds the `i128` domain, the call reverts in supplier-reward calculation before the accrual timestamp can advance. [10](#0-9) [1](#0-0) [6](#0-5) 

At that point, `controller.withdraw(attacker, account_id, [({ hub_id, asset: borrow_asset }, 1)], None)` and `controller.repay(attacker, account_id, [({ hub_id, asset: borrow_asset }, 1)])` also revert with `MathOverflow`, matching the checked-in reproduction. [18](#0-17) [19](#0-18) [20](#0-19)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
    let mutation = cache.position_mutation(position, net_repay);
