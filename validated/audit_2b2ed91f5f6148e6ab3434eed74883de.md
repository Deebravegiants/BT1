### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate`, which computes the HMAC only over `to_signable_string`, i.e. the raw request body. The `shop` value that is subsequently trusted and handed to the app's `WebhookHandler` is read directly from the `x-shopify-shop-domain` HTTP header, which is never included in the signed bytes. This breaks the identity binding: `hmac_verified_bytes = raw_body != shop_bound_to_signature`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, unconditionally forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute and compare the HMAC using `Context.api_secret_key`, which is the **same secret for every shop that has installed the app** — the signature is not shop-specific: [4](#0-3) 

Because the secret is app-wide (not per-shop) and the signable string excludes the shop header, any `(raw_body, hmac)` pair that is valid for one shop's webhook is also valid when replayed with a different `x-shopify-shop-domain` header — the signature check passes regardless of which shop value accompanies it. The documentation's claim that `Registry.process` "will verify the request did indeed come from Shopify" is misleading: it only proves the *body* bytes are unmodified from *some* genuine Shopify webhook signed with this app's secret, not that the accompanying `shop` field is authentic for that body.

### Impact Explanation
An attacker who installs the same app on a shop they control (a normal, unprivileged action) can trigger the app to send them legitimately HMAC-signed webhook bodies (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`, `orders/create`, etc., all signed with the single app-wide `client_secret`). The attacker can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` header. `Registry.process` will accept it as valid (HMAC checks only the body) and dispatch it to the app's handler labeled as coming from the victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g. deleting/deauthorizing tenant data on `app/uninstalled`, or fulfilling `customers/redact`/`shop/redact` for the wrong tenant), this is a cross-tenant data-integrity/action-confusion primitive — the app acts on tenant B's data/session using a payload actually originating for tenant A.

### Likelihood Explanation
Low-to-moderate: the attacker needs only their own legitimate app installation (no special privilege) to obtain a valid signed body/HMAC pair, and then a single unauthenticated HTTP POST to the app's public webhook callback URL with a forged shop header. No secret, token, or credential of the victim is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the `shop` value to the payload before trusting it in `WebhookMetadata`. At minimum, `Registry.process`/`Request` should cross-check that `request.shop` corresponds to a shop with an active, previously-registered webhook subscription for that `webhook_id`/topic before dispatching to the handler, rather than trusting an unauthenticated header value directly.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving genuine webhooks (e.g. `app/uninstalled`) signed by the app's single `client_secret`. They capture `raw_body` and its valid `x-shopify-hmac-sha256` value.
2. Attacker sends `POST /webhook_path` to the app's public endpoint with the same `raw_body`/`hmac`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(...)` parses this and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the app-wide secret — the header substitution is invisible to the check: [3](#0-2) 
4. The handler receives `WebhookMetadata(shop: "victim.myshopify.com", topic: "app/uninstalled", ...)` and performs whatever tenant-scoped action the app implements for that topic against the victim's tenant, even though the victim never uninstalled anything.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
