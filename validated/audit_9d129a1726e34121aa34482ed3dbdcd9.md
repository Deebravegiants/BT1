### Title
Webhook shop/topic identity spoofing — HMAC covers only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers used for tenant attribution ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body alone, while the `shop`, `topic`, and `webhook_id` fields used to route and attribute the webhook to a tenant are read straight from unauthenticated HTTP headers. `Registry.process` validates only the body-HMAC and then unconditionally trusts these header-derived fields, breaking the intended binding `HMAC-verified bytes == identity used by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are pulled directly from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) .

`Registry.process` validates the HMAC of the body only, via `Utils::HmacValidator.validate(request)`, and — once that single check passes — dispatches to the handler using `request.topic` and `request.shop` taken from those unauthenticated headers: [4](#0-3) . `HmacValidator` in turn calls `verifiable_query.to_signable_string`, so for `Webhooks::Request` this reduces to `OpenSSL.secure_compare(HMAC(secret, raw_body), received_hmac)` — a check that says nothing about which shop or topic the body belongs to: [5](#0-4) .

Because the app's `api_secret_key` is shared across every shop that has the app installed (it is not a per-shop secret), any merchant that installs the app receives valid `(body, hmac)` pairs for their own webhook traffic. The documented integration pattern feeds `request.headers` straight from the raw HTTP request into `Webhooks::Request.new` with no additional verification: [6](#0-5) , and host apps are told to trust `data.shop` as "The shop domain of the webhook" for attribution/persistence: [7](#0-6) .

This breaks the intended equality `HMAC-authenticated payload == (shop, topic) used to store/attribute the data`. An attacker who controls a shop with the app installed can capture one legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered to their own callback endpoint, then replay that exact body/HMAC combination directly to the app's public webhook endpoint (bypassing Shopify's delivery infrastructure entirely) while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain (and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`). `Registry.process` will accept it, because HMAC validation only checks the body against the shared secret, and will invoke the handler with `WebhookMetadata` claiming the data belongs to the victim shop/topic.

### Impact Explanation
This is a cross-tenant data-injection primitive: an attacker-controlled webhook body can be attributed to a shop the attacker does not control, since the shop identity is asserted via an unauthenticated header rather than being covered by the signature. Depending on how the host application persists webhook data keyed by `data.shop` (the gem's own documented pattern, e.g. `shop_domain: data.shop`), this can corrupt or inject records into another tenant's data store — a cross-tenant access impact.

### Likelihood Explanation
Requires only: (1) attacker has legitimate app access for their own shop (any merchant can install a public/custom app) to obtain one valid `(body, hmac)` pair, and (2) direct network access to the app's webhook HTTP endpoint, which by design is a public, unauthenticated-by-transport route (documented as a plain Rails controller action). No access to `api_secret_key`, access tokens, or victim credentials is needed.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed payload verified by `HmacValidator`, or otherwise require callers to separately verify that the shop asserted in the webhook headers matches a shop the app expects to hear from (e.g., cross-check against installed-shop records) before trusting `WebhookMetadata#shop`/`#topic`. At minimum, document prominently that `request.shop`/`data.shop` is not authenticated by the HMAC and must not be treated as a trusted tenant identifier without additional verification by the host application.

### Proof of Concept

#    and receives a legitimate webhook, e.g. for topic "customers/data_request":
raw_body = '{"id":1,"note":"attacker-controlled content"}'
hmac_b64 = "<value from genuine X-Shopify-Hmac-Sha256 header captured by attacker>"

# 2. Attacker replays the exact same body + hmac directly to the app's
#    public webhook endpoint, but swaps the shop/topic headers:
headers = {
  "x-shopify-topic"       => "customers/data_request", # or any registered topic
  "x-shopify-hmac-sha256" => hmac_b64,                  # unchanged, still validates
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id"  => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) passes, because it only checks HMAC(secret, raw_body).
# => Handler is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...),
#    even though the body/webhook was never issued for that shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
