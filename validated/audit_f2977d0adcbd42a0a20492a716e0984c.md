### Title
Unbounded busy-loop in `BeefyHost::start_consensus`'s mandatory-proof drain loop causes 100% CPU livelock and blocks consensus delivery - (File: `tesseract/consensus/beefy/src/host.rs`)

### Summary
`BeefyHost::start_consensus` drains the mandatory-proof queue in an inner `loop { ... }` that pulls one item via `receive_mandatory_proof`, and on the "future set_id" branch (`set_id != consensus_state.next_authorities.id` after the `set_id < ...` case was already handled) it executes a bare `continue` with **no sleep and no deletion of the un-acked item**, then immediately re-enters `receive_mandatory_proof` on the same message. [1](#0-0) 

### Finding Description
This is structurally identical to the ImageMagick JPEG-extent bug: a `continue` inside a retry/binary-search-style loop that spins forever when the condition it depends on (here, `set_id == consensus_state.next_authorities.id`) persistently fails to hold. Unlike the sibling and later-hardened implementation in `tesseract/consensus/admin-relayer/src/task.rs`, which explicitly sleeps on the analogous "future handover" branch: [2](#0-1) 

the `beefy/src/host.rs` loop has no `tokio::time::sleep` and no `delete_message` call before looping back: [3](#0-2) 

If `receive_mandatory_proof` re-delivers the same un-acked queue item (rather than advancing to a different item or blocking until new data arrives), the loop becomes a tight CPU-bound spin: it repeatedly calls `query_consensus_state`, decodes it, and re-evaluates the same stale mismatch, with no backoff and no progress, exactly mirroring the "continue statement... causes an infinite loop when [the operation] persistently fails" root cause from the ImageMagick advisory.

### Impact Explanation
A relayer process running `BeefyHost::start_consensus` for a counterparty chain would pin a CPU core at 100% and never submit the mandatory authority-set-handover message, since the loop starves the async task of any opportunity to make forward progress. Because mandatory (epoch-change) proofs gate all subsequent consensus/message proof submissions to that counterparty (the outer `while let Some(item) = notifications.next().await` loop and the messages-queue loop are only reached after this inner loop `break`s), a persistently mismatched `set_id` can permanently block consensus updates and therefore all downstream message delivery to that destination — a denial-of-service against the relayer's ability to route messages, i.e., "a route unable to deliver messages."

### Likelihood Explanation
The failure condition (`set_id` ahead of what the destination's `next_authorities.id` currently shows) is a normal, easily reachable state whenever a mandatory proof is queued for a rotation the destination hasn't observed yet, or when queue ordering/duplication puts a "future" proof ahead of the one that would actually advance `next_authorities.id`. Since the exact same condition class was patched with a sleep/backoff in the sibling implementation (`admin-relayer/src/task.rs`), it is reasonable to infer this branch was an oversight left over from the older `beefy::host` code path, not a case that requires an adversarial input to trigger — a benign state-machine ordering causes it, making the likelihood of occurrence in production moderate to high whenever this host implementation is used.

### Recommendation
Add a bounded backoff (`tokio::time::sleep(...)`) before the `continue` on the future-set-id branch, mirroring the pattern already used in `admin-relayer/src/task.rs`, so the loop yields between retries instead of spinning. Additionally verify whether `receive_mandatory_proof`'s semantics allow the same un-acked item to be redelivered without limit; if so, this should be confirmed against `tesseract/consensus/beefy/src/backend/{memory,redis,onchain}.rs`, which I was not able to fully verify in this session due to iteration limits — that verification is necessary to be certain the loop is a true unbounded busy-loop rather than one bounded by an underlying blocking read.

### Proof of Concept
1. Queue two mandatory proofs for the same counterparty state machine, ordered so that the proof with `set_id = N+2` is delivered by `receive_mandatory_proof` before the proof with `set_id = N+1` (e.g., due to backend redelivery or out-of-order queue population).
2. On the first pull, `consensus_state.next_authorities.id == N+1`, so `set_id (N+2) != N+1` → the `set_id < next_authorities.id` branch is skipped, and the mismatch branch at line 225 fires, running `continue` with no sleep.
2. `receive_mandatory_proof` returns the same/next unresolved item, `query_consensus_state` is queried again, the same mismatch reproduces, and the loop repeats indefinitely — observable as sustained 100% CPU on the task with no progress and no further tracing output indicating a delivered proof.
