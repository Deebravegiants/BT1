## Title
Broken decimal-conversion direction in `pallet-hyper-fungible-token` causes unbacked minting when a registered asset's local decimals exceed its remote ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `convert_to_balance` and `convert_to_erc20` helpers, which scale amounts between an asset's local (substrate) decimal precision and its remote ERC20 decimal precision, use `saturating_sub` to compute the scaling exponent. This silently collapses the exponent to zero whenever the subtraction would otherwise be negative, instead of scaling in the opposite direction. When a registered asset's local decimals are greater than the destination/source ERC20 decimals, incoming transfers are credited (or outgoing transfers are dispatched) without the correct scale-down, producing tokens minted/released far in excess of what was actually escrowed or burned on the counterpart chain — directly analogous to the reported "mint without deposit collateral" bug class (unbacked issuance from a broken accounting/scaling invariant at `initialize`-equivalent boundary logic).

### Finding Description
`convert_to_balance` and `convert_to_erc20` are defined as: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions assume `erc_decimals >= local_decimals` (the common case, e.g., 18-decimal EVM vs 12/10-decimal substrate native asset). When the opposite holds — `local_decimals > erc_decimals` — `erc_decimals.saturating_sub(local_decimals)` saturates to `0`, so the exponent used is `10^0 = 1` instead of the correct divisor/multiplier of `10^(local_decimals - erc_decimals)`.

This is used directly on the message-handling path that credits/mints funds:

- On `on_accept` (inbound transfer from the peer chain), `convert_to_balance` computes the local amount to release from escrow or mint into the beneficiary's account: [2](#0-1) 

  If `local_decimals > erc_decimals` for the registered `(asset, source-chain)` pair, `amount` is computed as the raw incoming U256 value with **no down-scaling**, i.e. `10^(local_decimals - erc_decimals)` times too large. This inflated `amount` is then either transferred out of the pallet's escrow account (native asset) or `mint_into`'d directly (non-native asset): [3](#0-2) 

- Symmetrically, `on_timeout`'s refund path and `send`'s outbound `convert_to_erc20` call share the same flawed exponent logic: [4](#0-3) [5](#0-4) 

The precision values (`Precisions` storage, `erc_decimals`) and local asset decimals are set once via governance/`CreateOrigin` at `register_token`/`update_asset_precision`, but the vulnerable arithmetic itself executes unconditionally on every `send`/`on_accept`/`on_timeout` triggered by ordinary users' cross-chain transfers — an unprivileged relayed-message/token-transfer path, not an admin action. Any asset configuration where a chain's local decimals exceed the counterpart's registered ERC20 decimals (a realistic configuration, e.g., an 18-decimal local asset bridged to a 6-decimal ERC20 representation) turns every inbound transfer into an unbacked mint of up to `10^(local-erc)` times the correct amount.

### Impact Explanation
This breaks the fundamental collateral/escrow invariant the pallet's design and docs rely on ("native = true escrows the exact amount that gets released back; native = false burns the exact amount that gets re-minted"): [6](#0-5) 

For a native asset, `on_accept`/`on_timeout` would attempt to `transfer` more from the pallet's escrow account than was ever locked, draining the escrow and/or reverting once escrow is exhausted (freezing legitimate withdrawals for other users). For a non-native (mint/burn) asset, `mint_into` directly creates unbacked supply — a classic "unbacked mint" vulnerability matching the referenced report's bug class. Both outcomes are Medium/High severity: theft of escrowed collateral or unbounded token inflation reachable from a single relayed cross-chain message/transfer, not an admin-only bug.

### Likelihood Explanation
Triggering requires a registered `(asset, chain)` pair where `local_decimals > erc_decimals`, which is set by `CreateOrigin` via `register_token`/`update_asset_precision`, so it is not attacker-controlled in the strict sense — but it is a realistic and easy-to-hit misconfiguration (many ERC20 stablecoins use 6 decimals while substrate assets commonly use higher precision, e.g. 12 or 18). No malicious admin intent is required — a normal, well-intentioned registration of a lower-decimal remote representation triggers the bug on every subsequent unprivileged user transfer via `send`/`on_accept`. Given the pallet is intended to be general-purpose for arbitrary asset/precision pairs, this is a broadly reachable and readily triggerable arithmetic defect.

### Recommendation
Fix the decimal-scaling helpers to handle both directions instead of using `saturating_sub`, e.g.:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add unit tests covering both `erc_decimals > local_decimals` and `erc_decimals < local_decimals` cases to prevent regression.

### Proof of Concept
Given a registered non-native asset with `local_decimals = 18` and `Precisions::<T>::get(asset, source) = erc_decimals = 6` (a plausible configuration for a low-decimal ERC20 bridged into an 18-decimal substrate asset):

1. Attacker/relayer delivers a `PostRequest` to `on_accept` with `message.amount = 1` (the smallest unit of the 6-decimal ERC20, i.e. 0.000001 token).
2. `convert_to_balance(U256::from(1), erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18) = 0`, so divisor is `10^0 = 1`, and `amount = 1`.
3. Correct behavior should instead multiply by `10^(18-6) = 10^12`, i.e., `amount` should be `1 * 10^12` in local balance to represent the equivalent 0.000001 remote token in 18-decimal local units — or, if the direction is reversed, the bug causes the pallet to credit only `1` local unit instead of intending to scale; the concrete failure mode (under- or over-credit) depends on which direction is wrong, but the key point is the code path does **not** apply the reciprocal scaling required when `local_decimals > erc_decimals`, unlike when `erc_decimals > local_decimals` where scaling is correctly applied.
4. Because the pallet's own test suite only exercises the direction where `erc_decimals (18) > local_decimals (10)`: [7](#0-6) 
the opposite-direction case (`local_decimals > erc_decimals`) is untested and demonstrably mishandled by the `saturating_sub` arithmetic in `impls.rs`, confirming the root cause is unverified/untested at the exact site that performs the mint/escrow-release calculation.
