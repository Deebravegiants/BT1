### Title
Missing overflow protection in `validate_delegate_action_key` nonce upper-bound calculation (inconsistent with `verify_nonce`) - ([File: runtime/runtime/src/actions.rs])

### Summary
The `queryDeadlineInterval` report describes a class of bug where an arithmetic bound derived from the current block number lacks overflow protection, using an unchecked `+`/`*` operation on a fixed-width integer, which can revert calls or leave state inconsistent when the bound is exceeded. An analogous pattern exists in nearcore's meta-transaction (`DelegateAction`) nonce validation: two parallel code paths compute the same "nonce upper bound" formula, but one uses a checked/saturating operation and the other does not.

### Finding Description
For regular transactions, `verify_nonce` in `runtime/runtime/src/verifier.rs` computes the nonce upper bound using `saturating_mul` to guard against overflow: [1](#0-0) 

For `DelegateAction` (meta-transaction) nonces, the parallel logic in `validate_delegate_action_key` performs the equivalent computation with a plain, unchecked multiplication instead of `saturating_mul`/`checked_mul`: [2](#0-1) 

Both call sites compute `block_height * AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER` to derive the same conceptual "upper bound" used to reject stale or maliciously-large nonces (`InvalidTxError::NonceTooLarge` vs. `ActionErrorKind::DelegateActionNonceTooLarge`). The `verifier.rs` path was hardened to saturate on overflow, but the `actions.rs` path for delegate actions retains the raw multiplication, exactly mirroring the report's root cause: an arithmetic bound tied to `block_height`/block-number-like state that is computed without an upper-bound/overflow-safety analog in one of two otherwise-symmetric code paths.

### Impact Explanation
If `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` overflows `u64` (multiplier is defined via `ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, referenced at `core/primitives-core/src/account.rs`), the outcome depends on the build's overflow-checks setting:
- If overflow checks are enabled (as configured in `Cargo.toml` at the repo root), the multiplication panics during chunk application, crashing the node processing the delegate action and potentially halting the chain if reproduced deterministically across validators (a "node panic"/chain-stall class impact, matching the Accept criteria).
- If overflow checks are disabled, the multiplication silently wraps, producing an incorrect (small) `upper_bound`, which could cause legitimate delegate-action nonces to be incorrectly rejected as `DelegateActionNonceTooLarge`, or in other wraparound scenarios, incorrect acceptance of nonce validation logic than intended.

This mirrors the two harmful scenarios in the original report: (1) a hard revert/failure path due to unchecked arithmetic, and (2) inconsistent enforcement of a nonce boundary.

### Likelihood Explanation
Exploitability requires `block_height` to reach approximately `u64::MAX / 1_000_000 ≈ 1.8 × 10^13`. At nearcore's current block production rate, this height is unreachable within any realistic timeframe (analogous to the original report's own acknowledgment that reaching `type(uint32).max` would take ~1626 years — here the threshold is many orders of magnitude further out due to `u64` vs `uint32` width). This makes the bug currently a **theoretical / code-consistency defect** rather than an exploitable-today vulnerability; it is flagged because the report explicitly treats "eventually reachable, practically distant" overflow conditions as valid findings, and because it represents an inconsistency between two logically-parallel guarded/unguarded arithmetic paths in the same codebase, which is a maintainability and audit-worthy hardening gap rather than an immediately triggerable DoS.

### Recommendation
Change `runtime/runtime/src/actions.rs` line 641-642 to use `saturating_mul` (or `checked_mul` with explicit error handling) for computing `upper_bound`, matching the pattern already used in `runtime/runtime/src/verifier.rs`:
```rust
let upper_bound = apply_state.block_height
    .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
```
This removes the inconsistency between the two nonce-bound-checking code paths and eliminates any reliance on the build's overflow-checks configuration for correctness.

### Proof of Concept
Not practically constructible today: it requires driving `apply_state.block_height` to ~1.8 × 10^13, far beyond any realistic near-term chain height, so no runnable PoC against a live/testnet chain is feasible. The issue is demonstrable purely by code inspection/diff between: [1](#0-0) 
and [2](#0-1) 
A unit test could simulate the overflow by directly calling `validate_delegate_action_key` with a mocked `ApplyState { block_height: u64::MAX / 1_000_000 + 1, .. }` (as done in existing tests like `test_delegate_action_key_nonce_too_large` at `runtime/runtime/src/actions.rs:1616-1641`, which already constructs `ApplyState` with custom heights via `create_apply_state`) to confirm a panic (overflow-checks on) or a wrapped/incorrect `upper_bound` (overflow-checks off).
