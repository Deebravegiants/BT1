### Title
Webhook `shop` tenant identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shop-domain` header, yet `Registry.process` trusts `request.shop` as the authenticated tenant identifier when dispatching to app handlers. The HMAC binds `shop == shop` is never enforced; only `body == body` is checked.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it with the `hmac` field using a constant-time comparison. [5](#0-4) 

For webhooks, `to_signable_string` is defined to be exactly `@raw_body`: [2](#0-1) 

Meanwhile, `shop` is parsed independently from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is not part of the signed material at all: [1](#0-0) 

`Registry.process` validates only the HMAC over the body, then immediately forwards `request.shop` to the app-supplied handler as the trusted tenant identity for that webhook body: [4](#0-3) 

This is precisely the class of defect described in the Oval report: a value that is *acted upon* (here, `shop`, used to route/attribute the webhook body to a specific merchant/tenant) is not covered by the same authentication mechanism (`HmacValidator.validate`) that is supposed to prove the message's authenticity/origin. The equality the code implicitly assumes is:

`shop_used_by_handler == shop_that_Shopify_actually_sent_this_body_for`

but the code only ever proves:

`raw_body_bytes_verified == raw_body_bytes_received`

Because any party who legitimately receives Shopify webhooks for **their own shop** obtains valid `(raw_body, hmac)` pairs signed with the app's `api_secret_key`-derived signature (the signature is a function of `api_secret_key` + body only, not shop), that same `(raw_body, hmac)` pair remains valid if replayed to the same app's webhook endpoint with the `shop-domain` header rewritten to a *different* installed shop. `HmacValidator.validate` will still pass, since the signable string (`@raw_body`) is unchanged, and `Registry.process` will hand the forged `shop` value straight to the handler, which typically uses it to look up/act on a specific merchant's records.

### Impact Explanation
This breaks the tenant/shop identity binding that webhook HMAC verification is meant to guarantee, enabling cross-tenant data confusion/injection: an attacker who is a legitimate, unprivileged merchant on Shop A (and therefore receives real signed webhooks for Shop A) can replay that exact same signed payload against the app's webhook endpoint while claiming to be Shop B, causing the host application to process attacker-controlled (or attacker-replayed) webhook content under a victim tenant's identity. Depending on the handler, this can lead to cross-tenant data corruption, privilege confusion, or injection of forged business events (e.g., fake `orders/create`, `app/uninstalled`, GDPR redact payloads) attributed to a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who has installed the target app on at least one shop (a normal, unprivileged onboarding step): they receive real Shopify-signed webhooks for their own shop, can capture `(raw_body, hmac-sha256 header)` pairs, and can freely replay them to the same public webhook endpoint with an arbitrary `shop-domain`/`x-shopify-shop-domain` header, since the gem's `Registry.process` and `HmacValidator.validate` never check that the header matches the signed content.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the bytes verified by the HMAC, or otherwise cryptographically bind `shop` to the signature before it is trusted. Since Shopify's actual HMAC only covers the body by protocol design, at minimum the gem should document/enforce that `request.shop` must be cross-checked against a shop already known/authorized by the host app (e.g., an existing session) before being used, or the gem should compute and expose a combined "authenticated identity" (raw body + shop header) so integrators are not implicitly trusting an unauthenticated header value as tenant identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify sends a legitimate webhook to the app's endpoint: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)`.
4. Attacker crafts a new HTTP request to the same webhook endpoint with the *same* body `B` and the *same* header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B` and whose `shop` is `victim-shop.myshopify.com`.
6. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H` — validation passes. [6](#0-5) 
7. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, believing this content was authentically sent by Shopify for `victim-shop`, even though it was replayed by an unrelated unprivileged party.
