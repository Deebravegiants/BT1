### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC is only computed over the raw request body. The `shop` identifier that is subsequently handed to the app's handler is read straight from the unauthenticated `X-Shopify-Shop-Domain` header, so the binding `shop-header == shop-that-produced-the-signed-body` is never checked.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `#shop` is parsed directly from the `shop-domain` header with no cross-check against the signature [2](#0-1) . `Utils::HmacValidator.validate` only recomputes and compares the HMAC over `to_signable_string` (i.e. the body) [3](#0-2) . `Registry.process` gates purely on that body-HMAC check and then forwards `request.shop` — the unauthenticated header value — straight to the app's handler as the tenant identifier: [4](#0-3) .

Because the app's `api_secret_key` is shared across every shop that installs the app, any developer can install the app on their own (attacker-controlled) shop, receive a legitimately Shopify-signed webhook body+HMAC pair for their own store's activity, then replay that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The gem's HMAC check still passes (the body byte and secret match), but the `shop` value delivered to `WebhookMetadata` is entirely attacker-controlled, breaking the binding: `shop authenticated == shop acted upon`.

The gem's own documentation reinforces the false sense of security: it states that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4) , without disclosing that the `shop` field passed to `handle` is unauthenticated, and the example handler in the same doc uses `data.shop` directly as the tenant key [6](#0-5) .

### Impact Explanation
This is a cross-tenant identity confusion inside the gem's documented API surface (not a host-app misuse issue): the gem itself asserts the shop is verified as part of "came from Shopify," yet only the body bytes are checked. Any app that keys per-tenant storage, access-token lookups, or side effects off `WebhookMetadata#shop` (exactly as the documented example does) can have data attributed to, or actions taken against, the wrong merchant's tenant record, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any developer can freely create a Shopify development/trial store and install the target app on it at no privilege cost — this is normal unprivileged internet-user capability. Once installed, all webhook bodies for actions on that developer's own store are validly signed with the app's shared secret. Capturing and replaying such a payload with a modified `Shop-Domain` header requires only a basic HTTP client; no secrets, tokens, or elevated access are needed.

### Recommendation
Bind the shop identity into the verified signal:
- Either include the `shop-domain` header value (and topic) in the string that is HMAC-verified, or
- Have `Registry.process` cross-validate `request.shop` against an out-of-band trusted value (e.g., require callers to supply the expected shop and compare it against the header) before dispatching to `handler.handle`.

At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. Install the target Shopify app on an attacker-owned development store (`attacker-shop.myshopify.com`).
2. Trigger a webhook (e.g. `orders/create`) on the attacker's own store; Shopify sends a POST with a body and a valid `X-Shopify-Hmac-Sha256` computed with the app's shared `api_secret_key`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Capture this raw body and HMAC header.
4. Replay the exact same body and HMAC header to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (body/HMAC pair is legitimate) [7](#0-6) , and `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` [4](#0-3) , causing the app to process attacker-supplied data under the victim tenant's identity.
