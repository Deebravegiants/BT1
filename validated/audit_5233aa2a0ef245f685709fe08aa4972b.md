### Title
RAY-value overflow during interest accrual permanently freezes an oversized market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Pool market mutations accrue interest before changing supply or debt. Accrual multiplies scaled balances by their indexes through `scaled_to_original`, and that multiplication panics once the RAY-denominated market value exceeds `i128::MAX`, even though the configured index ceiling permits much larger indexes. An unprivileged attacker can place a market in this state by creating a sufficiently large, highly utilized position and later triggering accrual through `update_indexes`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ops::load_leg` loads a market through `synced_market`, which unconditionally calls `interest::global_sync` before returning the user's scaled position. [4](#0-3)  `global_sync` processes every elapsed chunk through `accrue_chunk`, which calls `common::rates::accrue_step`. [1](#0-0) [5](#0-4) 

`accrue_step` first converts total borrowed and supplied shares to their original values with `scaled_to_original`, which is implemented as `scaled.mul(env, index)`. [6](#0-5) [3](#0-2)  It later multiplies debt by the newly grown borrow index in `calculate_supplier_rewards`, so crossing the representable RAY-value boundary can trap during either the old-value or new-value calculation. [7](#0-6) 

Market caps only bound the original token amount to the asset's RAY domain and do not reserve multiplication headroom for index growth. [8](#0-7)  The protocol index ceiling is `1e36` raw RAY, or one billion times the initial index, while a one-billion-whole-token market at 18 decimals already occupies approximately `1e36` scaled units and overflows at an index around 170 times RAY. [9](#0-8) [10](#0-9) 

The integration test reproduces this condition and confirms that the index cap is not reached before accrual fails, after which both withdrawal and repayment still fail because they attempt accrual first. [11](#0-10) 

### Impact Explanation
Once the stored scaled market total multiplied by its stored or next index exceeds `i128::MAX`, every operation routed through `load_leg` reverts before its action-specific accounting runs. [12](#0-11)  Suppliers cannot withdraw and borrowers cannot repay that market, while liquidation and debt cleanup paths that must load the same synced market are likewise blocked. [13](#0-12) [14](#0-13) 

Because `global_sync` traps before `mark_accrued`, the stale `last_timestamp` is not committed and retrying later starts from the same overflowing state. [1](#0-0)  This creates a permanent freeze of the market's funds absent a privileged contract upgrade, satisfying permanent freezing of funds and a market unable to operate. [15](#0-14) 

### Likelihood Explanation
The attack requires a deployed market whose cap admits enough tokens to approach the RAY-value domain and enough debt utilization for interest to grow the index beyond `i128::MAX / scaled_balance`. [16](#0-15) [9](#0-8)  The required token quantity is extreme, but it is admitted by the configured cap domain and the failing sequence uses only unprivileged `supply`, `borrow`, and `update_indexes` calls. [17](#0-16) [18](#0-17) 

### Recommendation
Cap market totals and positions against the largest allowed index rather than only the raw asset domain, or perform accrual with saturating/widened arithmetic that clamps indexes to the last representable market value. In particular, enforce `scaled_supply * MAX_SUPPLY_INDEX_RAY <= i128::MAX` and `scaled_debt * MAX_BORROW_INDEX_RAY <= i128::MAX` before admitting new exposure, and add a recovery-safe accrual path that commits bounded progress instead of trapping before `mark_accrued`. [19](#0-18) [1](#0-0) 

### Proof of Concept
The repository's regression test demonstrates the path on an 18-decimal market configured with a cap and collateral sufficient for a one-billion-token book. [20](#0-19) 

1. Supply `1_000_000_000 * 10^18` base units of the debt asset and borrow `98%` of it from attacker-controlled collateral. [21](#0-20) 
2. Advance ledger time and repeatedly call `controller.update_indexes(caller, vec![hub_asset])` until the borrow index approaches the RAY-value cliff. [22](#0-21) 
3. The next `update_indexes` call reverts with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`. [23](#0-22) 
4. Subsequent `withdraw` and `repay` calls on that market also revert with `MathOverflow` because both load the market through `global_sync` first. [24](#0-23) [12](#0-11)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {

    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);

    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
