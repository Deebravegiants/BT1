## Title
Webhook HMAC signature does not bind the `shop` (or `topic`) header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the tenant-identifying `shop-domain` header (and `topic`) are read separately and never covered by the signature. `Registry.process` trusts `request.shop` for tenant dispatch after validating only the body's HMAC, so any request with a previously-valid `(body, hmac)` pair can be replayed with an attacker-chosen `shop-domain` header and will still pass verification.

### Finding Description
The identity binding that should hold is:

`HMAC-verified(shop-domain header) == shop used to dispatch the webhook to a tenant`

In this gem, that equality is broken. `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived independently from the (unsigned) header: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (i.e., the body) only and compares it to the received signature — it never incorporates `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to the handler using `request.shop` taken straight from the unverified header, with no further check that this shop is the one the payload actually originated from: [4](#0-3) 

Because the signature is computed purely over the body bytes, any attacker who can obtain one legitimate `(raw_body, hmac)` pair — e.g., by installing the app on their own store and receiving any real webhook for it — can resend that exact body/HMAC combination to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header of a different, victim shop. `HmacValidator.validate` will still succeed because it never inspects those headers, and `Registry.process` will hand the payload to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the cross-tenant boundary the HMAC is meant to enforce: an attacker-controlled payload (from their own shop) can be delivered to the app's webhook handler tagged as belonging to another merchant's shop domain. Depending on how the app's handler uses `WebhookMetadata#shop` (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or any handler that persists/acts on data keyed by `shop`), this enables cross-tenant data corruption, forced deauthorization, or processing of forged data under another tenant's identity — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker needs only unprivileged access: their own (attacker-controlled) shop to legitimately receive one webhook of any topic, and network access to POST to the target app's public webhook endpoint with modified headers. No access token, `api_secret_key`, or privileged account is required, since the signature never covers the header being spoofed.

### Recommendation
Bind the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) into the signed/verified content, or otherwise cryptographically bind them to the raw body before trusting `request.shop` for dispatch. At minimum, `to_signable_string` should incorporate the shop-domain header (mirroring how the OAuth `AuthQuery#to_signable_string` binds `shop` into its signable string), and `Registry.process` should not trust `request.shop` unless it round-trips through the verified signature.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and lets it register a webhook (any topic).
2. Shopify sends a legitimate webhook to the app: `raw_body = B`, `X-Shopify-Hmac-Sha256 = H`, `X-Shopify-Shop-Domain = attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays a POST to the app's webhook endpoint with the same `B` and `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only [5](#0-4)  and it matches `H`, so validation succeeds.
5. `Registry.process` dispatches the handler with `shop: request.shop` = `"victim.myshopify.com"` [6](#0-5) , causing the app to act on attacker-controlled data as if it originated from the victim's shop.
