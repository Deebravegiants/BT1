### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on an otherwise-valid webhook body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body, while the `shop` value handed to the application's webhook handler is read straight from the unauthenticated `X-Shopify-Shop-Domain` header. Because the app's `api_secret_key` is shared across *all* shops that installed the app, any body+HMAC pair that is valid for Shop A's webhook is also a valid HMAC for the exact same body claimed to originate from Shop B — the signature check cannot bind the body to a specific tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. the raw body only) using the app's `Context.api_secret_key`: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` (the unverified header) to build the `WebhookMetadata` object passed to the app's handler: [4](#0-3) 

The equality the code implicitly assumes but never enforces is:
`shop_that_signed_the_body == shop_claimed_in_header`

In reality only `hmac == HMAC(api_secret_key, raw_body)` is checked. Since `api_secret_key` is a single app-level secret (not shop-scoped — see its usage throughout `Context`), a body signed for tenant A remains a validly-signed payload no matter which shop-domain header accompanies it. A user who merely has the ability to trigger app webhook deliveries for their own shop (an ordinary, unprivileged merchant using the app — not a privileged account, and requiring no access token, no `client_secret`, and no interception) can:

1. Install the app on their own shop, and capture one legitimate webhook delivery (raw body + `X-Shopify-Hmac-Sha256` header) that Shopify sends to the app's endpoint.
2. Replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain.
3. `HmacValidator.validate` passes, because the HMAC was computed only over `raw_body`, and `Registry.process` builds `WebhookMetadata` with `shop: request.shop`, i.e. the attacker's chosen victim shop.

Any app logic that persists/branches on `data.shop` (offline session lookup, GDPR data flows, order/customer ingestion keyed by shop, etc.) is now attributed to the victim shop using attacker-controlled content, breaking shop/tenant isolation.

### Impact Explanation
This breaks the identity binding between "who signed this data" and "which tenant it is recorded against," enabling cross-tenant data injection: an attacker's own webhook payload (which they fully control, since they control their own store's order/product/customer content) can be delivered to the app's pipeline attributed to a different, victim shop. This matches the "Critical — cross-tenant access" impact category, since it is the *shop identity itself* that is spoofed, not merely a payload field, and the mechanism is entirely internal to this gem's `Webhooks::Request`/`Registry`/`HmacValidator` trio.

### Likelihood Explanation
Requires only: (a) the attacker be an ordinary user able to install the app on their own store (no elevated privileges) to legitimately obtain a valid `(raw_body, hmac)` pair, and (b) the ability to send an arbitrary HTTP POST to the app's public webhook route (that route is, by design, unauthenticated aside from the HMAC check). No `access_token`, `client_secret`, or TLS interception is needed — the whole point is that the HMAC check never binds to a specific shop in the first place. Likelihood is High for any app that keys business logic off `WebhookMetadata#shop` without independent verification.

### Recommendation
Bind the verified shop to the signed content instead of trusting an unauthenticated header:
- Include the `shop-domain` (and `topic`, `webhook-id`, `api-version`) in the signable string so they participate in HMAC verification, or
- Cross-check `request.shop` against an offline session/shop record that was independently established during OAuth/install for that specific shop id embedded in the (now-covered) signed payload, rejecting webhooks whose header shop does not match a shop the app can prove installed it with a corresponding shop-scoped secret/session.
At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a tenant boundary without additional verification by the host application.

### Proof of Concept
```ruby
# Attacker step 1: install the app on their own "attacker-shop.myshopify.com"
# and capture a real webhook delivery Shopify sends to the app, e.g.:
raw_body = '{"id":1,"note":"hello from attacker shop"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
hmac_b64 = Base64.encode64(valid_hmac)   # captured from the real Shopify request

# Attacker step 2: replay it directly to the app's webhook endpoint,
# swapping only the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_b64,          # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (it only checks raw_body),
#    and the app's handler receives WebhookMetadata with shop == "victim-shop.myshopify.com"
#    even though the body actually came from the attacker's own shop.
```
