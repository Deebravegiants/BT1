### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header spoofing due to HMAC covering only the raw body — cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`, `api_version`, `webhook_id`) values that are handed to the app's webhook handler are read straight from HTTP headers that are **not** part of the signed content, so any party who can capture one valid `(raw_body, hmac)` pair for the app's shared `api_secret_key` can replay it with a different `X-Shopify-Shop-Domain` header and have it processed as if it originated from a different, unrelated merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` is derived from the `hmac-sha256` header and verified via `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` to compute the expected signature: [1](#0-0) [2](#0-1) 

`to_signable_string` returns **only `@raw_body`**. It excludes `shop`, `topic`, `api_version`, and `webhook_id`, which are instead read directly and unauthenticated from headers: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever checks the HMAC against `to_signable_string` (the raw body), never against the shop or topic headers: [4](#0-3) 

`Registry.process` trusts these unauthenticated header values wholesale and forwards them straight into the app-level handler as the tenant identity for the event: [5](#0-4) 

**Binding that should hold but doesn't:** `HMAC(raw_body, api_secret_key) valid` should imply `request.shop == the shop the raw_body was actually generated for`. In reality, the HMAC only proves the body's integrity/origin under the app's secret; it says nothing about which shop the body belongs to. An unprivileged internet user who runs the app on their own store (a legitimate, non-privileged installer, not requiring anyone else's credentials, access token, or `client_secret`) receives real Shopify webhooks — raw body plus a valid HMAC computed with the app's shared secret — for events on their own store. They can then replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `topic`/`webhook-id`) for a different, victim merchant's shop domain. `HmacValidator.validate` still succeeds because it only checks the untouched raw body, and `Registry.process` passes the attacker-chosen `shop` value into `WebhookMetadata`, so the host application processes/persists the payload under the wrong tenant.

### Impact Explanation
This breaks the identity binding between "HMAC-authenticated bytes" and "the shop those bytes are attributed to," letting one merchant's authenticated webhook traffic be attributed to (and acted upon for) a different merchant. Depending on how the host app's webhook handler uses `data.shop` (e.g., looking up/mutating that shop's stored session, orders, inventory, or billing state), this can result in cross-tenant data corruption or cross-tenant access, matching the "Critical - cross-tenant access" impact category. It requires no `api_secret_key`, no access token, and no privileged account beyond operating the app on one's own store — squarely an unprivileged-internet-user primitive.

### Likelihood Explanation
Any developer/merchant who installs the app can trivially capture legitimate webhook traffic sent to their own endpoint (it is delivered directly to them) and replay it with a modified `shop`-domain header using a basic HTTP client — no cryptographic secret is needed since the header isn't covered by the signature. The gem provides no independent verification that the `shop` header matches the shop the payload was generated for.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values in the HMAC-signed content, or independently validate them (e.g., cross-check `request.shop` against a shop resolved from an authenticated source, or require it to be present in and validated from the signed payload) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Install/run the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw request: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC-SHA256(api_secret_key, B)`).
2. Replay the captured request to the same webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (per [6](#0-5) ) succeeds because it only checks `B` against `H`.
4. `Registry.process` (per [5](#0-4) ) invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body `B`, causing the host application to process/act on data under the victim shop's identity.
