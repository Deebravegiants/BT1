### Title
Concurrent hardware-wallet signing requests can be merged/confused via `restrictConcurrency` de-duplication - ([File: features/hardware-wallets/src/module/hardware-wallets.ts])

### Summary
`HardwareWallets#signTransaction` / `#signMessage` funnel through a single shared method `#signGeneric`, wrapped with `restrictConcurrency` (the `make-concurrent` package) with no explicit options. [1](#0-0)  `make-concurrent`'s default (no `{ concurrency: 1 }` queueing option, no `byArguments`) behavior is to de-duplicate: if the wrapped async function is invoked again while a previous invocation's returned promise has not yet settled, the call returns the **same in-flight promise** rather than starting a new execution. Because `#signGeneric` does not resolve until the physical-device signing flow (`retrySigningRequest` → `request.sign({ device })`) finishes, any second call to `signTransaction`/`signMessage` that arrives while a first request is still awaiting device approval will not create an independent signing request — it will instead be silently collapsed onto the first one's outstanding promise.

### Finding Description
`#signGeneric` creates a fresh `id`, stores it as `this.#signingRequest`, fires `void this.retrySigningRequest(id)` (fire-and-forget), and then returns `deferred.promise`, which is only resolved/rejected once the user approves/rejects on the physical device. [1](#0-0)  Since the wrapped async function's own completion is defined by that same `deferred.promise`, the `restrictConcurrency` wrapper treats the whole signing round-trip (including the user's manual button-press on the hardware device) as "one execution in flight."

If `signTransaction`/`signMessage` is invoked a second time (e.g., from a different caller/origin such as a dApp-connected web3 provider) before the user finishes approving the first request on the device, `restrictConcurrency`'s default dedupe semantics mean the second caller receives the identical pending promise object created for the *first* request — the second call's own `baseAssetName`/`unsignedTx`/`message`/`walletAccount` arguments are discarded, and `#signGeneric`'s inner logic (which builds a *new* `sign` closure per call) is never re-executed for that second request. Internal state (`this.#signingRequest`) is likewise never updated to reflect the second call, so the UI signing prompt (`#signingRequestAtom`) is only ever shown for the first request. [2](#0-1)  When the user physically approves what they believe is a single transaction, both the original caller and the second, unrelated caller resolve with the signature produced for the *first* request's payload.

This mirrors the root cause of the referenced Buyout bug: a critical piece of shared state (`buyoutInfo` / here `this.#signingRequest` and the underlying concurrency guard's in-flight promise) is expected to represent exactly one live operation, but overlapping invocations before that operation truly settles cause a second, distinct request to be silently merged into / blocked by the first instead of being independently tracked, processed, or rejected.

### Impact Explanation
An unprivileged caller (e.g., a second dApp tab, or a malicious/compromised page using the wallet's web3 provider) that issues a `signTransaction`/`signMessage` request while another legitimate request from a different origin/account context is pending on a hardware device can receive the **signature computed for someone else's transaction/message** instead of its own, or have its own signing request silently swallowed without ever prompting the user or surfacing an error for that specific request. This is a cross-request/cross-origin state-bleed in the signing pipeline: the caller who issued the second call gets a result it did not consent-flow through the UI for, and the legitimate first caller's approval is effectively reused for an operation the user never saw. Depending on how the returned signature is used downstream (e.g., broadcast of an unintended payload, or a dApp obtaining a signature over data it supplied but never actually got the device to sign), this can result in unauthorized signing / mismatched approval, which is a meaningful trust-boundary violation for a hardware wallet flow.

### Likelihood Explanation
Triggering this requires nothing more than two overlapping hardware-wallet sign requests reaching `HardwareWallets` within the window between "user physically has the device pending" and "device approval/rejection completes" — a window that can be several seconds to tens of seconds for hardware devices. Any code path capable of invoking `signTransaction`/`signMessage` twice in quick succession (multiple open dApp connections, rapid consecutive requests, or an application bug that retries) can hit this without any special privileges, making the precondition easy to reach in normal multi-tab / multi-dApp usage.

### Recommendation
Do not rely on default (dedupe) `restrictConcurrency` semantics for a function whose completion depends on unbounded, user-driven, per-request I/O. Either:
- Use `make-concurrent`'s `{ concurrency: N }` queueing mode (which serializes distinct calls with distinct arguments rather than merging them), or
- Explicitly key concurrency by request (e.g., `byArguments`) so each `signTransaction`/`signMessage` call gets its own promise/signing request, and reject/queue overlapping requests explicitly instead of allowing them to be silently combined.

Additionally, `#signGeneric` should validate, when resolving `deferred.promise`, that the resolved signature actually corresponds to the caller's original request payload (matching on `id`) before returning it, so that a stale or mismatched dedupe never surfaces a signature for the wrong data.

### Proof of Concept
1. Two independent callers (e.g., two dApp connections) call `hardwareWallets.signTransaction({ unsignedTx: txA, ... })` and shortly after `hardwareWallets.signTransaction({ unsignedTx: txB, ... })` respectively, while the hardware device is still waiting for the user's physical approval of the first request.
2. Because `#signGeneric` is wrapped in `restrictConcurrency` without explicit queueing/argument-keying options, and its own completion is defined by `deferred.promise` (which only resolves after device approval), the second call is deduplicated onto the first call's in-flight execution instead of creating a new `#signingRequest`/`id`.
3. The user approves the (only visible) prompt for `txA` on the device; `request.sign` resolves `deferred.promise`.
4. Both the first caller and the second caller (who requested a signature over `txB`) receive the signature produced for `txA`, without the wallet ever asking the user to approve `txB`.

Note: This analysis is based on the documented/standard default behavior of the `make-concurrent` npm package (dedupe unless `{ concurrency: N }`/`byArguments` is passed), as used elsewhere in this repo with explicit `{ concurrency: 1 }` options for genuine queueing. [3](#0-2)  The exact installed version/behavior of `make-concurrent` was not directly inspectable in this index; confirming its precise semantics (dedupe vs. queue) in the pinned version should be part of validating this finding.

    async ({ baseAssetName, scenario, sign, walletAccount }: GenericSignParams) => {
      const id = randomBytes(16).toString('hex')
      this.#logger.debug(
        `Starting signing request for ${baseAssetName} with scenario: ${scenario} and id: ${id}`

      // Track the signing request in the internal map

            baseAssetName,
