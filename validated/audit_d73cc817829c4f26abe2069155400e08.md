Based on the investigation, the closest analog in this codebase is how Chainlink stores and exposes the bridge **`OutgoingToken`** — a credential used to authenticate the node when calling external adapters/bridges.

### Title
Bridge `OutgoingToken` is stored in plaintext and exposed to any authenticated (viewer-level) user - ([File: core/bridges/bridge_type.go])

### Summary
Chainlink's bridge subsystem generates two secrets per bridge: `IncomingToken` (used by the external adapter to authenticate *to* the node) and `OutgoingToken` (used by the node to authenticate *to* the external adapter). While `IncomingToken` is correctly hashed with a salt before storage (`IncomingTokenHash`), `OutgoingToken` is persisted and returned in plaintext.

### Finding Description
`NewBridgeType` generates `outgoingToken := utils.NewSecret(24)` and stores it unhashed directly in the `BridgeType.OutgoingToken` field, which maps to the `outgoing_token` DB column defined as plain `text` in the schema. [1](#0-0) [2](#0-1) [3](#0-2) 

This plaintext token is then unconditionally serialized into the `BridgeResource` presenter (unlike `IncomingToken`, which has an `omitempty` tag and is only populated once, at creation time) and returned by the REST bridge endpoints (`Index`, `Show`) and by the GraphQL `bridges`/`bridge` queries. [4](#0-3) [5](#0-4) [6](#0-5) 

GraphQL mutation-level access control distinguishes `view`/`run`/`edit`/`admin` roles (`authenticateUserCanEdit`, `authenticateUserCanRun`, `authenticateUserIsAdmin`), but query-level access for `bridges`/`bridge` only calls `authenticateUser`, which does not check role beyond having a valid session (`view` role passes). [7](#0-6) [8](#0-7) 

This means any authenticated node-UI user, even one with the lowest `view` role, can retrieve the plaintext `outgoingToken` for every configured bridge.

### Impact Explanation
The `OutgoingToken` is a credential used by the node to authenticate to external adapter services. Exposing it in plaintext to low-privilege (`view`-role) users allows those users to impersonate the node when calling the external adapter, or to reuse the credential outside the node context — analogous to the Jenkins advisory pattern where a plaintext-stored credential is readable by users who should only have limited/extended-read access.

### Likelihood Explanation
Any authenticated Operator UI/API user (including `view` role, the lowest privilege tier) can trigger this exposure simply by calling the `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName` REST endpoints, or the GraphQL `bridges`/`bridge` queries — no special permission bypass is required, only normal, intended read access with the lowest role.

### Recommendation
- Do not return `OutgoingToken` in plaintext to read-only/`view`-role sessions. Either hash/mask it in the presenter and GraphQL type (similar to how `IncomingToken` is handled — only returned once at creation), or restrict its exposure to `admin`/`edit` roles.
- Consider hashing `OutgoingToken` at rest as well, having the runner re-derive or fetch it via a secure channel only when executing bridge calls.

### Proof of Concept
1. Create an admin user and a second user with `view` role.
2. As admin, create a bridge via `POST /v2/bridge_types`, noting its `outgoingToken`.
3. Authenticate as the `view`-role user and call `GET /v2/bridge_types/:BridgeName` (or the GraphQL `bridge(name: ...)` query).
4. Observe that the response includes the same plaintext `outgoingToken`, even though this user has only `view` privileges and cannot create/edit/delete bridges.

**Note on confidence**: I could not fully confirm the REST route-level role middleware for `bridge_types` endpoints specifically (the `router.go` grep for the bridge routes did not return the relevant lines before the session ended), so it's possible additional role middleware is applied there that isn't visible in the GraphQL layer. This should be verified directly in `core/web/router.go` before treating this as fully confirmed.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
