### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the identity of the tenant a webhook belongs to (the `shop-domain` header) to processing, but the HMAC signature that authenticates the webhook only covers the raw body. This breaks the identity binding `authenticated_bytes == acted_upon_shop`, letting a holder of one valid (body, HMAC) pair relabel it as belonging to any other shop served by the same app.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop`, `#topic`, and `#webhook_id` are read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the body only) and compares it against `request.hmac`: [3](#0-2) [4](#0-3) 

Once the body/HMAC pair validates, `Registry.process` passes `request.shop` straight into `WebhookMetadata` and into the app's handler, unauthenticated: [5](#0-4) 

Because a single `api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app (an unprivileged internet user with respect to *other* tenants) legitimately receives real Shopify webhooks whose HMAC is computed with that same secret over their own webhook body. That attacker can capture one such (raw_body, hmac) pair from their own shop and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` only checks the body against the HMAC — it never checks that the `shop` header used to route the payload was the one Shopify actually associated with that HMAC — so the forged request passes validation and is dispatched to the handler tagged as belonging to the victim tenant.

This is the same class of bug as the report's root cause: a value that is *acted upon* (here, the shop that gets attributed to the incoming webhook data) is not covered by the authentication check (here, the HMAC), so the two diverge and can be independently manipulated by the caller.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended by this gem) to key which tenant's data gets updated, an attacker who runs their own trial/dev shop with the app installed can inject arbitrary webhook payloads under another merchant's shop identity — a cross-tenant data integrity/confidentiality violation. This matches the Critical bucket ("cross-tenant access").

### Likelihood Explanation
Requires only that the attacker install the target app on their own shop (an ordinary unprivileged action any merchant can perform) and be able to send an HTTP request to the app's public webhook endpoint with attacker-controlled headers — no access token, secret, or privileged account is needed.

### Recommendation
Bind the `shop` (and `topic`) values into the authenticated material, e.g., by verifying them against the shop registered for the given webhook subscription/session before dispatch, or by requiring the host application to cross-check `request.shop` against an independently trusted source (e.g., looking up the webhook subscription id returned by Shopify) rather than trusting the header value implicitly once the body HMAC passes.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a real webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and its valid HMAC.
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against the HMAC.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches to the handler, which processes attacker-controlled data as if it came from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
