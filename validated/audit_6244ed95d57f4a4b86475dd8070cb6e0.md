### Title
Excess native token sent to `EvmHost.dispatch()` for fee payment gets permanently locked in the Host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` accepts `msg.value` and swaps it for the exact required `feeToken` amount via Uniswap, but never captures the swap's return value or refunds unspent native tokens to the caller, unlike the sibling `IntentGatewayV2.placeOrder()` implementation which explicitly tracks and refunds leftover native token after the same kind of swap.

### Finding Description
In `EvmHost.dispatch()`, when a caller pays the dispatch fee in native token, the function performs: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
}
```

`swapETHForExactTokens` (whether the real Uniswap V2 router or the project's own wrappers such as `UniV3UniswapV2Wrapper.swapETHForExactTokens`/`UniV4UniswapV2Wrapper.swapETHForExactTokens`) only guarantees `post.fee` output tokens and refunds any unspent native ETH — but that refund goes to the caller of the swap, which here is `EvmHost` itself (since `EvmHost` is `msg.sender` of the swap call), not the original transaction sender who supplied `msg.value` to `dispatch()`. [2](#0-1) [3](#0-2) 

The docstring for `dispatch()` itself even documents that "Payment for the request can be made with either the native token or the feeToken. If native tokens are supplied, it will perform a swap under the hood... Will revert if enough native tokens are not provided" — it never mentions handling of excess, and the code confirms no excess handling exists. [4](#0-3) 

Contrast this with `IntentGatewayV2.placeOrder()`, which performs the exact same kind of native-to-feeToken swap for `order.fees`, but explicitly captures the `amounts` array returned by the swap and refunds the leftover `msgValue` to `msg.sender` at the end of the function: [5](#0-4) 

This demonstrates that the protocol's own pattern for correctly handling native-token overpayment during a Uniswap fee swap requires capturing `amounts[0]` and refunding the difference — a step that is missing entirely in `EvmHost.dispatch()` (and likely in the analogous GET-dispatch and `fundRequest` paths that follow the same pattern, e.g. `fundRequest` at lines 1031-1042, which has the identical missing-refund issue). [6](#0-5) 

### Impact Explanation
Any unprivileged user or relayer/message dispatcher calling `EvmHost.dispatch()` (or `fundRequest()`) with native token to pay the relayer fee, who sends more native token than the exact amount consumed by the Uniswap swap (a very easy and common scenario since callers cannot know the exact optimal swap amount in advance and typically send a buffer, exactly as intentionally exercised in the project's own test `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` which validates the correct refund behavior exists elsewhere), will have their excess native token permanently trapped inside the `EvmHost` contract with no code path to reclaim it. This is a direct, permanent loss of user funds for every dispatcher who overpays, which will happen routinely in production given normal fee-estimation slippage.

### Likelihood Explanation
High likelihood: this affects the core, most commonly used entry point `dispatch()` for every application built on top of `EvmHost` (any `HyperApp` sending a POST/GET request and paying in native token), and any caller who sends `msg.value` larger than the precise fee-token cost — which is the expected, recommended usage pattern shown in the documentation (`sendMessageWithNative` example instructs callers to just forward `msg.value: msg.value`) — will lose the difference on every call. [7](#0-6) 

### Recommendation
Capture the `amounts` array returned from `swapETHForExactTokens` in `EvmHost.dispatch()` (and in `fundRequest()` and the GET-dispatch equivalent), compute the leftover native value (`msg.value - amounts[0]`), and refund it to `_msgSender()`, mirroring the pattern already implemented correctly in `IntentGatewayV2.placeOrder()`.

### Proof of Concept
1. A `HyperApp` contract calls `IDispatcher(host()).dispatch{value: msg.value}(post)` where `post.fee` requires only a small amount of native token to acquire via the Uniswap swap, but the caller sends a generous buffer (e.g., 5x the estimated fee, as recommended practice to guard against slippage — exactly as demonstrated in `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`).
2. `EvmHost.dispatch()` executes `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`.
3. The router/wrapper spends only the amount needed and refunds the rest of the ETH — but to `address(this)` (`EvmHost`), not to the original caller, because `EvmHost` is `msg.sender` from the router's perspective.
4. `EvmHost.dispatch()` returns without ever checking or forwarding the refunded ETH balance back to `_msgSender()`.
5. The excess native token remains stuck in the `EvmHost` contract's balance indefinitely — there is no user-facing withdrawal path for it in the reviewed code. [1](#0-0)

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
```
