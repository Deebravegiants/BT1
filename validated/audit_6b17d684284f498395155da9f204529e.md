### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are not HMAC-covered, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. An unprivileged internet user who can obtain any single valid `(body, hmac)` pair for the app (e.g. from their own free/dev shop that has the app installed) can replay that body with a forged `x-shopify-shop-domain` header pointing at a victim shop, and the signature check still passes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated headers, not from the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature via `verifiable_query.to_signable_string` (i.e. the body only) and compares it against `request.hmac`: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then immediately trusts the header-derived `request.shop` (along with `topic`/`webhook_id`) to build `WebhookMetadata` and dispatch it to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field handed to the app's `WebhookHandler#handle`: [5](#0-4) 

The identity binding that is expected — `shop` claimed in the request == `shop` cryptographically bound to the signed bytes — does not hold. The secret used (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop/tenant the app serves, not a per-shop secret. Consequently, HMAC validity only proves "this body was signed by an entity holding the app's `client_secret`" (i.e. Shopify's webhook delivery for *some* shop with this app installed), not "this body belongs to the shop named in this header." Any actor who can install the app on any shop (including a free/dev store they control) can capture one legitimate `(raw_body, hmac)` pair and replay it against the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (or the newer `shopify-shop-domain`) header value, since header normalization simply trusts whatever `shop-domain`/`topic`/`webhook_id` header is present, and the request's own validation logic never cross-checks the header-derived `shop` against anything cryptographically bound to it: [6](#0-5) 

### Impact Explanation
This breaks the tenant identity binding `authenticated_shop == handler_dispatched_shop`. If the host application (as documented and intended by this gem — see `docs/usage/webhooks.md`) uses `WebhookMetadata#shop` to select which tenant's session/data the webhook body should be applied to, an attacker can inject or attribute another shop's (attacker-controlled) webhook body under a victim shop's identity, i.e. cross-tenant data injection. This maps to the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic for any multi-tenant Shopify app: obtaining one valid `(body, hmac)` pair only requires installing the app on any shop (including a free dev/partner store), which is achievable by an unprivileged internet user without any leaked credential, TLS interception, or social engineering. Forging the `shop-domain` header on the replayed HTTP request is trivial since the gem performs no additional binding check between the signed bytes and the header-derived shop.

### Recommendation
Bind the shop identity into the signed payload verification path: either require the app to independently authenticate `request.shop` against a known/expected session before trusting it, or extend `Utils::HmacValidator`/`VerifiableQuery` so that the signable string incorporated for webhook requests includes the `shop-domain` (and ideally `topic`/`webhook_id`) headers, not just the raw body, so that any header tampering invalidates the signature. Document this gap prominently if the header-derived `shop` is meant to remain unauthenticated by design.

### Proof of Concept
1. Attacker installs the target app on a shop they control, `attacker.myshopify.com`, and lets it deliver a real webhook (e.g. `orders/create`) to the app's registered endpoint. They capture the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` from that legitimate delivery (trivially observable by controlling the receiving endpoint or via any request-capturing proxy on infrastructure they own).
2. Attacker crafts a new HTTP POST to the same app endpoint with:
   - Body: identical bytes `B`
   - `x-shopify-hmac-sha256: H` (unchanged — still valid, since it only signs `B`)
   - `x-shopify-shop-domain: victim.myshopify.com` (forged)
   - `x-shopify-topic`, `x-shopify-webhook-id` as desired (also unsigned)
3. The app's controller constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` using the app's single shared `client_secret` and it matches `H`, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and dispatches it to the app's handler (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the attacker-authored body to be processed under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
