### Title
Webhook Shop, Topic, and Webhook-ID Are Not Covered by the HMAC Signature, Allowing Cross-Tenant Data Injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly and unauthenticated from HTTP headers. `Webhooks::Registry.process` validates the HMAC over the body alone and then hands the unauthenticated header-derived `shop` value straight to the app's webhook handler as trusted metadata. This mirrors the reported bug class: a field (`shop`) is acted upon by trust-sensitive logic while not being covered by the same cryptographic check (`HMAC`) that is supposed to bind the request to its issuer, exactly like the vault's stake amount being added without the lockup-expiry check binding the new deposit to the original commitment.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field of the same object: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers, none of which participate in the signed string: [3](#0-2) 

`Registry.process` validates only the body HMAC, then forwards the header-derived, unauthenticated `shop` (along with `topic`/`webhook_id`) to the registered handler as trusted `WebhookMetadata`: [4](#0-3) 

The identity-binding equality that should hold is: `shop_that_signed(raw_body) == shop_delivered_in_headers`. Because the signature covers only `raw_body`, this equality is never checked — the two sides can diverge, and the check that exists (HMAC of body) answers a question ("is this body's bytes untampered under our shared secret") different from the one the handler actually relies on ("which shop does this data belong to").

### Impact Explanation
An app built on this gem typically keys its own database, feature flags, or business logic by the `shop` value supplied via `WebhookMetadata#shop`. Since that value is never bound to the signed bytes, an attacker who can obtain any one valid `(raw_body, hmac)` pair signed by the app's secret (which the attacker fully controls the content of, see PoC) can replay it with an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. The HMAC check still passes because it only verifies the body was signed with the correct secret — it says nothing about which shop that body was meant to represent. This lets an unprivileged actor inject attacker-chosen webhook payloads that are processed by the app under a victim tenant's identity, i.e., a cross-tenant data-integrity/access issue.

### Likelihood Explanation
Any merchant/developer who installs the app themselves (a normal, unprivileged action available to anyone) receives legitimately-HMAC-signed webhook deliveries for their own store. They fully control the body content Shopify sends for many webhook topics they can trigger themselves (e.g., updating their own store's resource), giving them a valid `(raw_body, hmac)` pair. They can then POST that exact body/HMAC pair to the app's webhook endpoint while setting the `shop-domain` header to any other shop's domain. Nothing in `Request`, `HmacValidator`, or `Registry.process` rejects this, since none of them cross-check the header against the signed content.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string the HMAC is computed over — or, since Shopify's webhook payloads already carry shop-identifying information in the JSON body for most topics, require app handlers to cross-validate `request.shop` against the shop the app has an active session/install record for before trusting it. At minimum, document that `WebhookMetadata#shop` (and `topic`/`webhook_id`) are not authenticated by the delivered HMAC and must not be used as the sole tenant key without an independent lookup (e.g., verifying an existing installation record for that shop).

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` (a normal unprivileged action).
2. Attacker triggers a webhook topic they control the content of, so Shopify sends a request with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(app_secret, B)` — computed in `lib/shopify_api/webhooks/request.rb` `to_signable_string`/`hmac`.
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any `X-Shopify-Topic`/`X-Shopify-Webhook-Id` they like.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(app_secret, B) == H`: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, `topic`, and `webhook_id`, processing attacker data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
