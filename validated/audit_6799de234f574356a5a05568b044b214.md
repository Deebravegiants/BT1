Confirmed root cause: `lib/shopify_api/webhooks/request.rb#to_signable_string` returns only `@raw_body` [1](#0-0)  and `shop` is read straight from the (unauthenticated) `shopify-shop-domain` header [2](#0-1) . `HmacValidator.validate` only checks `to_signable_string` (the body) against the HMAC [3](#0-2) , and `Registry.process` passes `request.shop` straight into the handler after only that body-HMAC check succeeds [4](#0-3) .

### Title
Webhook shop-domain spoofing via HMAC that only covers the body, not the `shopify-shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string from the raw body only. The `shop` (merchant identity) delivered to the app's webhook handler comes from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the signed material. Because the app's `client_secret` (`api_secret_key`) used to sign webhooks is a single shared secret across all merchants/shops installed on the app, anyone who is a merchant of the app (an ordinary unprivileged tenant) can obtain a validly-signed `(raw_body, hmac)` pair for their own store's webhook and then replay that exact body/hmac to the app's public webhook endpoint with the `shop-domain` header changed to point at a *different* tenant. `Registry.process` will accept it as authentic, since HMAC validation succeeds, and will hand the (attacker-controlled) body to the handler tagged with the victim's shop.

### Finding Description
- `Request#shop` reads the tenant identity purely from an HTTP header, uncontrolled by the signature: [2](#0-1) .
- `Request#to_signable_string` — the only material verified by HMAC — is just `@raw_body`, excluding `shop`, `topic`, `webhook_id`, and `api_version`: [1](#0-0) .
- `HmacValidator.validate`/`validate_signature` compute/compare the HMAC solely over `to_signable_string` — i.e., body bytes: [3](#0-2) .
- `Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the whole request, then forwards `request.shop` (the header value) to the handler as `WebhookMetadata#shop`: [4](#0-3) .

The identity binding broken is: **`shop` claimed in the header ≠ `shop` actually covered by the HMAC**. Since the signing secret (`api_secret_key`) is identical for every shop that installs the same app, a valid `(body, hmac)` obtained from one tenant's own legitimate webhook traffic remains a valid signature for that same body regardless of which `shop-domain` header value accompanies it. An unprivileged app installer/merchant can therefore forge webhook deliveries that the receiving app will attribute to any other shop merely by changing an HTTP header, without ever learning `api_secret_key`.

### Impact Explanation
This breaks the tenant boundary the webhook API is meant to enforce: the handler code in host applications typically keys persistence/business logic (e.g., "update order X for shop Y", "process refund for shop Y") off `WebhookMetadata#shop`. An attacker-controlled merchant can inject arbitrary attacker-chosen webhook bodies (subject to the topic's schema, populated with data they fully control from their own store, e.g. product/order/customer field values) and have them processed by the app as though they came from a victim's store — a cross-tenant data-integrity/confusion issue reachable by any ordinary app-installing user, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own store (an ordinary, unprivileged action) and be able to POST directly to the app's public webhook endpoint (bypassing Shopify's delivery infrastructure entirely, which the gem's `Registry.process`/`Request` API does not prevent — it does not verify the request actually originated from Shopify's IP space, nor bind `shop`/`topic` into the signature). No secrets, tokens or social engineering are needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signable material, or otherwise cryptographically bind them to the payload before `HmacValidator.validate` succeeds, mirroring the treatment already given to `shop` in `Oauth::AuthQuery#to_signable_string` [5](#0-4) . At minimum, document prominently that `WebhookMetadata#shop` must not be trusted unless independently cross-checked by the host app (e.g., against a shop that has an active, previously-established session/installation), and provide a built-in helper for that cross-check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (an ordinary, permitted action for any Shopify merchant).
2. Attacker triggers a webhook topic they control the content of (e.g., `products/update`) and captures the raw POST body and its `x-shopify-hmac-sha256` value sent by Shopify to the app's webhook endpoint — this HMAC is valid because `HmacValidator.validate_signature` recomputes it purely from `raw_body` and the shared `api_secret_key` [3](#0-2) .
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` directly to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [6](#0-5) , `Registry.process` validates the HMAC successfully (it never checked `shop`) and invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , causing the host application to process attacker-supplied data as if it belonged to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
