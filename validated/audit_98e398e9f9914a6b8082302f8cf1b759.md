### Title
Predispatch escrow accounting in the Tron IntentGatewayV2 credits assumed balances instead of actually-received amounts, permanently freezing escrow for non-standard tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Sherlock report describes a swap function that credits `amount_out_received` back to the caller without verifying the tokens were actually transferred to the contract. The Tron variant of `IntentGatewayV2.placeOrder` has the same root-cause pattern in its predispatch escrow path: it credits the internal `_orders[commitment][token]` escrow ledger with an *assumed* amount before/without verifying that the actual token transfer from the `CallDispatcher` back to the gateway delivered that amount.

### Finding Description
In `placeOrder`, when an order has `predispatch` calldata, the contract sends the predispatch assets to `dispatcher`, executes arbitrary calldata via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, then attempts to sweep the resulting tokens back to the gateway: [1](#0-0) 

The loop snapshots `balance = IERC20(token).balanceOf(dispatcher)` (or `dispatcher.balance` for native), checks `balance >= requiredAmount`, builds a `transferCalls[i]` entry that will move `balance` tokens back to `address(this)`, and — critically — **immediately credits** `_orders[commitment][token] += reducedInputs[i].amount` inside this same loop, *before* the transfer calls are even dispatched: [2](#0-1) 

The actual sweep only happens afterward, in a single batched call: [3](#0-2) 

Unlike the mainline EVM `IntentGatewayV2.sol`, this Tron implementation never re-measures the gateway's actual token balance after the sweep executes. The mainline version snapshots `balancesBefore` *before* dispatching the sweep and computes `received = balanceAfter - balancesBefore` *after* dispatching it, then sets `order.inputs[i].amount = received` so the escrow ledger reflects what was truly received: [4](#0-3) 

The Tron file has no equivalent post-dispatch balance check. It simply trusts that `transferCalls[i]` — which invokes `IERC20(token).transfer(address(this), balance)` on the *dispatcher's* behalf — will deliver exactly `balance` tokens to the gateway, and credits escrow using `reducedInputs[i].amount` (derived from `order.inputs[i].amount`, the value declared by the user), not the amount actually measured to arrive. For any token with fee-on-transfer, rebasing, or other non-standard transfer semantics (the same class of token explicitly tested and handled in the mainline EVM contract's `testPlaceOrder_FeeOnTransferToken_Predispatch` test), the gateway will receive strictly less than `balance` when `transferCalls` executes, yet `_orders[commitment][token]` is already credited with the larger, unverified amount.

### Impact Explanation
Because escrow accounting (`_orders[commitment][token]`) is inflated relative to the gateway's actual token holdings, a subsequent solver fill/settlement that reads this escrow value and calls `IERC20(token).safeTransfer(beneficiary, amount)` will attempt to pay out more than the gateway actually holds for that specific token bucket. `safeTransfer` will revert once the contract's real balance is insufficient, permanently blocking settlement/withdrawal for that order (and potentially cross-contaminating other orders sharing the same token, since `_orders` is a per-token/per-commitment ledger but the underlying token balance is a shared pool). This is a permanent freezing-of-funds condition: user-escrowed principal becomes stuck because the ledger claims more tokens than physically exist in the contract, and no code path reconciles the deficit. This matches the “funds not actually returned to the contract but accounted for as received” bug class from the reference report, reachable by any user who places an order with a predispatch swap into a fee-on-transfer/deflationary ERC-20 (a common, permissionless, attacker-reachable input since `order.predispatch.assets`/tokens are user-chosen).

### Likelihood Explanation
Likelihood is High: placing an order is a completely permissionless, single-transaction user action; the user (or an attacker orchestrating the predispatch calldata) fully controls which token is used as the predispatch/input asset. Using any fee-on-transfer, deflationary, or otherwise non-1:1-transfer ERC-20 as the swap output in `order.predispatch` is sufficient to trigger the discrepancy — no special privileges or complex conditions are required, and the mainline codebase already has an explicit regression test acknowledging this exact token class must be handled by measuring actual received balances.

### Recommendation
Mirror the mainline EVM `IntentGatewayV2.sol` pattern in the Tron contract: snapshot `balanceOf(address(this))` (or native balance) *before* dispatching the sweep `transferCalls`, dispatch them, then compute `received = balanceAfter - balanceBefore` and use that measured value — not `reducedInputs[i].amount`/`requiredAmount` — to credit `_orders[commitment][token]`. Emit `DustCollected` only for any surplus over the required amount, and revert (or reduce escrow accordingly) if the received amount is less than required, consistent with the EVM implementation.

### Proof of Concept
1. User places an order with `order.predispatch.assets`/`order.predispatch.call` configured to swap into a fee-on-transfer token `FOT` (e.g., 1% fee on every transfer), requesting `order.inputs[0] = {token: FOT, amount: X}`.
2. `placeOrder` executes the predispatch call, leaving the `CallDispatcher` holding `balance` FOT tokens (`balance >= X`).
3. The loop at `evm/tron/contracts/apps/IntentGatewayV2.sol#L416-446` builds `transferCalls[0] = {to: FOT, data: transfer(gateway, balance)}` and immediately credits `_orders[commitment][FOT] += reducedInputs[0].amount` (based on `X`, not on what will actually be received).
4. `ICallDispatcher(dispatcher).dispatch(transferCalls)` executes the FOT `transfer`, which due to the 1% fee delivers only `balance * 0.99` tokens to the gateway — less than the `reducedInputs[0].amount` already credited to escrow.
5. When a solver later fills the order and the settlement path calls `IERC20(FOT).safeTransfer(solver, escrowedAmount)` using the inflated `_orders[commitment][FOT]` value, the transfer reverts because the gateway's real `FOT` balance is insufficient — the order (and its escrow) becomes permanently stuck.

                uint256 requiredAmount = order.inputs[i].amount;
                uint256 balance;

                if (token == address(0)) {
                    balance = address(dispatcher).balance;
                    if (balance < requiredAmount) revert InsufficientNativeToken();
                    transferCalls[i] = Call({to: address(this), value: balance, data: ""});
                } else {
                    balance = IERC20(token).balanceOf(dispatcher);
                    if (balance < requiredAmount) revert InvalidInput();
                    transferCalls[i] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                }

                uint256 dust = balance - requiredAmount;
                if (dust > 0) emit DustCollected(token, dust);

                // Store reduced amount (after protocol fees) in escrow
                _orders[commitment][token] += reducedInputs[i].amount;

                    ++i;
                }
