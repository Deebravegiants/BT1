### Title
Unvalidated ERC-20 `transfer` return data in Tron `IntentGatewayV2.withdraw`/`onAccept` lets a non-reverting, false-returning token silently "succeed" while marking escrow as paid - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` pays out escrowed order funds (fills, refunds, dust sweeps, tx-fee redemption) using raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks the low-level `success` boolean, never the ABI-decoded boolean return value of `transfer`. This is the exact "lack of external calls validation" class from the external report, reachable by any relayer delivering an ISMP message or any user calling `cancel`/withdrawal paths.

### Finding Description
`withdraw()` (called from `onAccept` on `RedeemEscrow`/`RefundEscrow`, and from `onGetResponse`) and the `SweepDust` branch of `onAccept` pay tokens out with: [1](#0-0) [2](#0-1) [3](#0-2) 

In all of these, `success` from `.call()` only reflects whether the callee's code executed without reverting — it does **not** reflect the ABI-encoded `bool` many ERC-20/TRC-20 tokens return to signal `false` on failed transfers (e.g. insufficient balance held by the contract for a non-standard/blacklist-aware token, or a token that returns `false` instead of reverting). The same file explicitly imports and uses `SafeERC20`/`using SafeERC20 for IERC20` elsewhere in the contract, showing the safe pattern was known and used inconsistently: [4](#0-3) 

Because `success` is true even when the token silently returns `false`, `withdraw()` decrements `_orders[commitment][token]` and emits `EscrowReleased`/`EscrowRefunded` (and the outer `onAccept` deletes the pending message receipt) as if the beneficiary was paid, while the tokens actually remain stuck in the gateway contract — this is unlike the intentional `EvmHost.dispatchIncoming` pattern (which checks a real bool and rolls back on failure, see `evm/src/core/EvmHost.sol:794-818`), so it is not covered by that already-reviewed design.

### Impact Explanation
This is a fund-freezing/loss bug reachable from a single relayed ISMP message: a solver/relayer delivering a `RedeemEscrow` or `RefundEscrow` POST (or a GET response for a refund) can trigger `withdraw()` for a token whose `transfer` returns `false` on failure rather than reverting. The escrow accounting is finalized (decremented / order marked withdrawn) even though the beneficiary never received the funds, permanently freezing the user's/solver's escrowed tokens with no path to retry (the receipt gets consumed, so a resend of the same request is treated as a duplicate/unknown order). This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is bounded by needing a non-standard ERC-20/TRC-20 token in the order's input/output/fee-token set that returns `false` instead of reverting on failed transfer (common on Tron's TRC-20 ecosystem, where token implementations vary more than on EVM mainnet, and where `IntentGatewayV2`'s protocol/gateway fee token or a user-chosen input token could plausibly be such a token). No privileged role is required — the fill/withdraw/cancel/sweep paths are reachable by ordinary users, solvers and relayers as part of normal intent-fulfillment flow.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `withdraw()` and the `SweepDust` branch of `onAccept` with `IERC20(token).safeTransfer(...)` (the `SafeERC20` library is already imported and used elsewhere in the same contract), so both the call-success and the returned boolean are validated before escrow state is finalized and success events are emitted.

### Proof of Concept
1. Governance/owner deploys an order whose input or fee token is a TRC-20 implementation that returns `bool false` on a failed `transfer` (instead of reverting) — a legitimate real-world token behavior on the Tron ecosystem.
2. A user or relayer triggers `withdraw()` via `onAccept` (`RedeemEscrow`/`RefundEscrow`) or `onGetResponse`, when the gateway's actual token balance is insufficient (e.g., due to prior dust/fee mis-accounting or a paused/blacklisted token state) so `transfer` returns `false`. [5](#0-4) 
3. `token.call(...)` returns `success = true` (no revert) even though the encoded return data is `false`; the `if (!success) revert TransferFailed();` check passes.
4. `_orders[body.commitment][token] -= amount;` executes, `EscrowReleased`/`EscrowRefunded` is emitted, and the host's request receipt is cleared as delivered — the order is now considered settled even though the beneficiary received nothing, permanently freezing those tokens in the gateway.
