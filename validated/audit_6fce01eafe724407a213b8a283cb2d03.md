### Title
Delegated (meta-tx) `DeterministicStateInitAction` receiver check can be bypassed on pre-fix protocol versions, allowing malicious front-running/griefing of deterministic account initialization - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
The reported Sherlock finding describes a CREATE2-style front-running attack: an attacker deploys the same deterministic clone address before the legitimate `createStream()` call, so the real transaction's post-deployment `initialize()` call is blocked, rendering the protocol unusable. nearcore has a directly analogous "deterministic account" primitive — NEP-616 `DeterministicStateInitAction`, whose target account id is derived from the content of the state-init payload itself (`derive_near_deterministic_account_id`) — and it historically had a receiver-validation gap when the action was wrapped in a meta-transaction (`DelegateAction`), which let an attacker submit a `DeterministicStateInitAction` that appears to target one account during transaction admission checks while actually being routed to a different deterministic receiver.

### Finding Description
`DeterministicStateInitAction` creates/initializes an account whose id must equal `derive_near_deterministic_account_id(&action.state_init)`. This is enforced by `validate_deterministic_state_init`: [1](#0-0) 

However, when this action is wrapped inside a `DelegateAction`/meta-transaction, the pre-fix validation path checked the *outer* transaction's `receiver_id` rather than the `delegate_action.receiver_id` when validating the inner actions, allowing an exploit transaction to pass initial admission checks despite the wrapped `DeterministicStateInitAction` actually targeting a different account than the outer receiver: [2](#0-1) 

The exploit scenario builds a `DelegateAction` whose `receiver_id` intentionally differs from the state-init-derived account, signed by a key belonging to a properly-initialized deterministic account (`det_account_b`), targeting a *different* deterministic account (`det_account_a`): [3](#0-2) 

This is fixed by the `FixDelegatedDeterministicStateInit` protocol feature, which is gated to activate only at protocol version 85, not folded into the "always enabled" base-protocol gates: [4](#0-3) 

Per the same spec, `MIN_SUPPORTED_PROTOCOL_VERSION` is 83, and only the deprecated global-contract/deterministic-account-id/eth-implicit gates are called out as always enabled — `FixDelegatedDeterministicStateInit` is not among them, meaning any node/chain still running at protocol version 83 or 84 remains exposed to this validation gap: [5](#0-4) 

The pre-fix behavior is explicitly demonstrated by a regression test showing the exploit transaction passes initial tx validation and only fails later, at `validate_receipt` unpacking time, with `InvalidDeterministicStateInitReceiver`: [6](#0-5) 

### Impact Explanation
This is a direct protocol analog of the reported bug class: content-addressed/deterministic account initialization whose receiver-authorization check can be bypassed at transaction admission time via a wrapper (`DelegateAction`) that decouples the outer, checked receiver from the actual receiver of the sensitive action, closely mirroring the report's front-running/receiver-manipulation-of-deterministic-deployment theme. On affected (pre-fix) protocol versions, an attacker can craft a meta-transaction that is accepted at the mempool/tx-validation stage despite targeting the wrong deterministic account, wasting relayer gas and disrupting deterministic account initialization workflows (DoS-style griefing), consistent with the "protocol becomes useless" impact described in the original report. This does not require any special/validator privileges — it is reachable by any account that can sign a meta-transaction.

### Likelihood Explanation
Exploitability requires the network to be running at protocol version 83 or 84 (before `FixDelegatedDeterministicStateInit` activates at v85). The codebase's own regression test (`test_deterministic_state_init_meta_tx_receiver_check_pre_fix`) confirms the exploit transaction passes initial validation on those versions. Since NEAR mainnet's live protocol version determines applicability, likelihood depends on whether any currently-supported/deployed network configuration still runs below version 85; the fix is present in code but not universally gated as "always on" the way other deterministic-account-id features are.

### Recommendation
Ensure `FixDelegatedDeterministicStateInit` is treated as always-enabled (folded into base protocol) for all supported protocol versions, consistent with the other deterministic-account-id (NEP-616) gates that are already unconditionally active per `MIN_SUPPORTED_PROTOCOL_VERSION`. Confirm no production network or client build can currently negotiate protocol version 83/84 without this fix, and if any such path exists, backport/force-enable the receiver check fix in `validate_delegate_action`/`validate_actions_with_mode` unconditionally.

### Proof of Concept
The existing test suite already encodes the proof of concept: [7](#0-6) 
Run at `fix_version - 1`, `try_meta_tx_deterministic_receiver_exploit` demonstrates the exploit transaction is accepted at initial tx validation and only rejected downstream during receipt validation, confirming the receiver-check bypass window on pre-fix protocol versions: [8](#0-7)

fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }

/// Ensure there is no exploit with invalid deterministic account ids through
/// meta transactions.
///
/// With the old (buggy) code, `validate_delegate_action` used
/// `outer_tx.receiver_id` instead of `delegate_action.receiver_id` when
/// checking inner actions. The exploit tx therefore passes initial tx
/// validation. The exploit is prevented by a following `validate_receipt` check
/// when the meta transaction is unpacked.
#[test]
fn test_deterministic_state_init_meta_tx_receiver_check_pre_fix() {
    let fix_version = ProtocolFeature::FixDelegatedDeterministicStateInit.protocol_version();
    let outcome = try_meta_tx_deterministic_receiver_exploit(fix_version - 1)
        .expect("without the fix, exploit tx passes initial tx validation");

    assert_matches!(
        outcome.status,
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            kind: ActionErrorKind::NewReceiptValidationError(
                ReceiptValidationError::ActionsValidation(
                    ActionsValidationError::InvalidDeterministicStateInitReceiver { .. }
                )
            ),
            ..
        })),
        "expected InvalidDeterministicStateInitReceiver in NewReceiptValidationError, got: {:?}",
        outcome.status
    );
}

/// With `FixDelegatedDeterministicStateInit` in place, the exploit should
/// already be caught at the first tx validation.
#[test]
fn test_deterministic_state_init_meta_tx_receiver_check() {
    let fix_version = ProtocolFeature::FixDelegatedDeterministicStateInit.protocol_version();
    let err = try_meta_tx_deterministic_receiver_exploit(fix_version)
        .expect_err("exploit tx must be rejected at tx validation with the fix");
    assert_matches!(
        err,
        InvalidTxError::ActionsValidation(
            ActionsValidationError::InvalidDeterministicStateInitReceiver { .. }
        ),
        "wrong error: {err:?}"
    );
}

fn try_meta_tx_deterministic_receiver_exploit(
    protocol_version: ProtocolVersion,
) -> Result<FinalExecutionOutcomeView, InvalidTxError> {
    let mut env = TestEnv::setup_with_version(Balance::from_near(100), protocol_version);
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let (_state_init_a, det_account_a) = env.new_deterministic_account_with_data(small());
    let (state_init_b, det_account_b) = env.new_deterministic_account_with_data(big());
    assert_ne!(det_account_a, det_account_b);

    // Deploy det_account_b and add a full-access key so it can act as meta_tx_sender.
    let user_signer = create_user_test_signer(&env.user_account());
    let storage_balance = env.balance_for_storage(state_init_b.clone());
    let deploy_tx = SignedTransaction::deterministic_state_init(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,
    );
    env.run_tx(deploy_tx);

    let meta_tx_sender_signer = create_user_test_signer(&det_account_b);
    let pk_base64 = near_primitives_core::serialize::to_base64(
        &borsh::to_vec(&meta_tx_sender_signer.public_key()).unwrap(),
    );
    let add_key_args = serde_json::json!([
        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
        {
            "action_add_key_with_full_access": {
                "promise_index": 0,
                "public_key": pk_base64,
                "nonce": 0
            },
            "id": 0,
            "return": true
        }
    ]);
    let add_key_tx = SignedTransaction::call(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        Balance::from_near(2),
        "call_promise".to_owned(),
        serde_json::to_vec(&add_key_args).unwrap(),

        env.get_tx_block_hash(),
    );
    env.run_tx(add_key_tx);

    // In no protocol version can this ever be allowed to be executed successfully.
    let relayer = env.independent_account();

        deposit: Balance::ZERO,

    let delegate_nonce = env.next_nonce_for(&det_account_b);
    let delegate_action = DelegateAction {
        sender_id: det_account_b.clone(),
        receiver_id: det_account_a,
        actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],
        nonce: delegate_nonce,
        max_block_height: 1_000_000,
        public_key: meta_tx_sender_signer.public_key(),

        SignedDelegateAction::sign(&meta_tx_sender_signer, delegate_action);

        env.next_nonce(),
        relayer,
        det_account_b,
        &relayer_signer,

        env.get_tx_block_hash(),
    );
    env.try_execute_tx(tx)
