### Title
Removing a chain from `HyperFungibleToken`/`pallet-hyper-fungible-token` permanently strands already-burned in-flight transfers - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.removeChain()` (and the equivalent `pallet_hyper_fungible_token::update_token` with `remove_chains`) deletes the chain's routing/authentication config with no check for messages that are already burned and in flight to or from that chain. Because `send()` uses `timeout: 0` as a valid "no timeout" value, any transfer sent before the removal can never be delivered nor refunded once the destination config is deleted, permanently freezing the burned tokens — the same root cause as the reported Union Finance bug: an admin removes a resource (adapter/token/chain) that still has funds or obligations attached to it, with no pre-check and no way to recover them afterward.

### Finding Description
`HyperFungibleToken` is a burn-and-mint bridge app: `send()` burns tokens from the caller and dispatches an ISMP POST request to the destination chain's paired contract: [1](#0-0) 

On the destination side, `onAccept()` authenticates the inbound message purely against the current `_supportedChains` mapping and mints only if that mapping still matches: [2](#0-1) 

The owner can delete a chain's configuration at any time via `removeChain`, with no check for pending/in-flight messages or any accounting of funds already committed to that route: [3](#0-2) 

If a user calls `send()` to a chain shortly before the owner calls `removeChain()` for that same chain (a routine action, e.g. during contract migration, decommissioning a chain, or reacting to a compromised peer), the relayed POST request will later hit `onAccept()` on the destination side, find `_supportedChains[request.source].length == 0`, and revert with `UnsupportedChain()`. Since delivery reverts entirely (no partial state change), the request is never marked accepted.

The only theoretical recovery path is the request's timeout mechanism (`onPostRequestTimeout`, which re-mints the burned amount back to the sender): [4](#0-3) 

However, `SendParams.timeout` is a caller-supplied value and is commonly set to `0` (see the documented API and tests), and in ISMP semantics a `timeout` of `0` means the request never expires — there is no timestamp after which anyone can call the timeout path. Consequently, once the destination chain's config for the source chain is deleted, an in-flight `timeout == 0` transfer can neither be delivered (destination always reverts) nor refunded (no timeout ever fires): the burned tokens are permanently unrecoverable.

The identical pattern exists on the Substrate side in `pallet_hyper_fungible_token::update_token`, where `remove_chains` deletes `TokenContracts`/`ContractToAsset`/`Precisions` for the (asset, chain) pair with no check for outstanding in-flight sends: [5](#0-4) 

`on_accept` on that side relies on `ContractToAsset` to resolve an inbound message to the local asset (per the pallet's own documentation), so deleting this mapping breaks delivery for any message already dispatched by the peer contract before the removal: [6](#0-5) 

### Impact Explanation
This is a direct, permanent freezing-of-funds bug reachable by any ordinary user of the token bridge (a single `send()` call), triggered by a routine, non-malicious admin action (chain removal/migration) that the protocol explicitly documents as supported ("Only callable by the contract owner"). Funds already burned on the source chain can become permanently unmintable/unrefundable on the destination chain, with no code path to recover them — matching the accepted impact criteria of "permanent freezing of funds."

### Likelihood Explanation
Chain/config removal is a normal, expected admin operation (e.g., deprecating a chain, rotating a peer contract, or reacting to a compromised deployment), not a malicious-governance scenario. Any user transaction in flight at that moment is affected; the race window is bounded only by the time between message dispatch and relay/finality, which realistically spans minutes to hours on many supported chains, making accidental collision plausible during any legitimate maintenance action.

### Recommendation
Before allowing `removeChain`/`update_token(remove_chains=...)` to take effect, either:
1. Require a mandatory minimum timeout (disallow `timeout == 0`) for `send()` at the protocol level, so every request can eventually revert to a well-defined timeout path, or
2. Keep the old chain/contract mapping (`_supportedChains` / `ContractToAsset`) authenticatable for delivery of already-dispatched messages even after removal (e.g., maintain a "retired but still deliverable" registry per chain instead of instantly deleting), or
3. Introduce a delay/grace-period between removal and hard deletion of the routing config, long enough to guarantee all in-flight requests targeting that chain have either been delivered or timed out.

### Proof of Concept
1. User A on chain X calls `HyperFungibleToken.send({dest: chainY, timeout: 0, amount: 100, ...})`. Tokens are burned from A's balance on chain X per `send()`.
2. Before the ISMP relayer delivers the POST request to chain Y, the owner of the chain-Y `HyperFungibleToken` contract calls `removeChain(chainX)` (e.g., part of a routine migration to a new deployment address).
3. The relayer submits the request to chain Y's host, which calls `onAccept`; `_supportedChains[chainX]` is now empty, so the call reverts with `UnsupportedChain()`. The request is never accepted and no tokens are minted on chain Y.
4. Because `timeout == 0`, the request has no expiry — `onPostRequestTimeout` never becomes callable on chain X to re-mint A's burned tokens.
5. A's 100 tokens are burned on chain X, never minted on chain Y, and can never be refunded: a total, permanent loss of funds caused solely by a routine chain-removal admin action with no funds-in-flight check.

```text
    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
```

```text
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
```

```markdown
## ISMP module behaviour

- `on_accept` — receives `Send` messages from the paired EVM contract. Maps
  the source contract back to a local asset via `ContractToAsset`, scales the
  amount using `Precisions`, then mints (non-native) or releases from escrow
  (native) to the beneficiary. Emits `TokenReceived`.
- `on_timeout` — refunds the original sender's balance from escrow or by
  re-minting. Emits `TokenRefunded`.
- `on_response` — unused; this pallet uses post-only messaging.
```
