### Title
Opaque swap routes can invoke attacker-controlled contracts that abuse the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept opaque route bytes and pass them to the configured router without decoding or constraining the contracts invoked by that route. [1](#0-0)  The controller limits its own authorization to one exact input transfer, but code reached through the route can request additional authorization from the user; Soroban records that request as a child of the user’s `swap_*` authorization tree. [2](#0-1)  If the user signs the simulated tree without noticing the additional child invocation, the route can transfer unrelated wallet tokens to an attacker while still returning valid swap output. [3](#0-2) 

### Finding Description
The vulnerable dispatch point is `swap_tokens`: it snapshots the declared input and output balances, authorizes only `token_in.transfer(controller, router, amount_in)`, and then invokes `router.execute_strategy` with caller-supplied opaque `swap` bytes. [4](#0-3)  Its post-call checks only bound the controller’s measured input spend and require positive measured output; they do not prevent route-invoked code from requesting authority directly from `caller`. [5](#0-4) 

This is the lending analogue of trusting a user-declared media type to select a decoder: the controller treats the declared route as opaque execution instructions, and those instructions can select an untrusted contract rather than the venue the user intended. [6](#0-5)  The host records a route contract’s `token.transfer(victim, attacker, amount)` request under the victim’s controller authorization entry during simulation, and enforcement accepts it if the victim signs that tree. [7](#0-6) 

### Impact Explanation
A malicious route can steal unrelated wallet assets from the user who signs the poisoned authorization tree, not merely the collateral amount routed through the controller. [8](#0-7)  The protocol’s measured-output and final-account-risk checks can still pass because the route returns a sufficient output token while the child authorization moves a separate token. [5](#0-4) 

### Likelihood Explanation
Exploitation requires user interaction: the attacker must cause the victim to submit a malicious route and sign an authorization tree containing the extra token transfer. [9](#0-8)  That interaction is realistic when routes are supplied by a compromised quote service, malicious UI, phishing flow, or copied transaction payload. [10](#0-9)  The issue is not bounded by the declared input amount or route output because the stolen invocation consumes unrelated user authority embedded in the signed tree. [10](#0-9) 

### Recommendation
Do not execute route-selected contracts that can request caller authority unless every callable venue and pool is constrained by a governance-managed allowlist or a verified route manifest. [11](#0-10)  At minimum, route construction and signing flows must simulate the complete transaction, decode the authorization tree, and reject any child invocation other than the expected input-token pull. [10](#0-9) 

### Proof of Concept
1. The attacker gives the victim a `swap_collateral` route whose encoded pool/venue invokes a contract that calls `unrelated_token.transfer(victim, attacker, victim_balance)`. [12](#0-11) 
2. Simulation accepts the route and records the wallet-token transfer as a child of the victim’s `swap_collateral` authorization entry. [7](#0-6) 
3. With the victim’s signed poisoned tree, enforcement executes the rogue transfer; the test shows the victim’s unrelated balance moving to the attacker while the expected ETH output is credited. [13](#0-12) 
4. The controller-side checks still pass because `swap_tokens` only verifies bounded controller input spend and positive output, not the route’s additional authorization requests. [5](#0-4)

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
