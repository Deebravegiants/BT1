### Title
Cross-chain intent escrow permanently locks native-ETH funds when the fixed beneficiary/user address cannot receive ETH - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`IntentsBase` settles native-ETH escrow (fills, refunds, cancellations) by force-pushing ETH via a low-level `.call{value: amount}("")` to a beneficiary address baked into the order (`order.user` for refunds/cancels, the solver/beneficiary for fills). If that address is a smart contract without a payable `receive()`/`fallback()`, the transfer reverts and there is no alternate pull-based claim path, so the escrowed ETH becomes permanently stuck. Because `EvmHost.dispatchIncoming` swallows failed `onAccept` calls (to allow retries) rather than reverting the batch, the delivery is retried indefinitely but deterministically fails forever for the same order — the route can never deliver that message.

### Finding Description
`IntentsBase._sendValue` is the sole native-token transfer primitive used by escrow release/refund logic: [1](#0-0) 

It is invoked from `_withdraw`, which is called for both order fills (`RedeemEscrow`) and cancellations/refunds (`RefundEscrow`), always sending to a fixed `beneficiary` decoded from the `WithdrawalRequest`: [2](#0-1) 

The beneficiary for a refund/cancellation is `order.user`, i.e., the same address that originally placed the order (`order.user = bytes32(uint256(uint160(msg.sender)))` at order placement); the beneficiary for a fill settlement is the solver's chosen recipient. Neither can be redirected at claim time — if that specific address is a smart contract that lacks a payable fallback, the `.call{value: amount}("")` in `_sendValue` reverts, and `_withdraw` (and thus `onAccept`/`onGetResponse`) reverts.

Crucially, the host does not abort the whole delivery on a reverting `onAccept` — it deliberately swallows the failure and clears the request receipt so the message "can be retried": [3](#0-2) 

Since the failure condition (the beneficiary address's inability to receive ETH) is a permanent, deterministic property of that address, every retry of the same commitment fails identically. There is no fallback-wrap mechanism analogous to the one implemented for WETH-style tokens (`WrappedHyperFungibleToken.onAccept`, which retries as an ERC-20 transfer if the native push fails): [4](#0-3) 

No such fallback exists in `IntentsBase._withdraw`/`_sendValue`, nor in the equivalent Tron fork's `withdraw()` function, which has the identical push-only pattern: [5](#0-4) 

This is the same bug class as the reported Footium issue: eligibility/settlement is bound to a specific address that cannot be redirected, and the payout mechanism unconditionally pushes ETH to that address with no pull-based alternative, so a non-payable-contract address permanently bricks the claim.

### Impact Explanation
For cross-chain orders, an ETH refund (order cancellation from either source or destination chain) or an ETH fill-settlement whose designated recipient is a contract without a payable fallback can never be delivered: `onAccept`/`onGetResponse` will revert every time it's attempted, the request receipt is deleted for retry each time (per `EvmHost.dispatchIncoming`), and the escrowed ETH remains locked in the `IntentGatewayV2`/`IntentsBase` contract indefinitely. This is a permanent freezing of user/solver funds and an unresolvable ISMP message route (the message can never be successfully delivered), matching the "permanent freezing of funds" / "route unable to deliver messages" impact categories. Any user or protocol integration that specifies (or is forced to use, e.g. via a smart-contract wallet, proxy, or vault that has no payable fallback) such an address as `order.user`/beneficiary is exposed, and the funds cannot be recovered through any other code path in the contract.

### Likelihood Explanation
Likelihood is moderate-to-high: it does not require any malicious actor — it can be triggered unintentionally by any user placing a same-chain or cross-chain native-ETH order from (or refunding to, or filling to) a smart-contract account that has no `receive()`/payable `fallback()` (e.g., a Gnosis Safe misconfiguration, a vault/contract wallet, or an intermediary contract used to place the order on someone's behalf). Given how common non-EOA order placers/fillers are becoming (smart accounts, aggregators, vaults), this is a realistic and easily reproducible condition.

### Recommendation
Do not unconditionally push native ETH to a caller-controlled/immutable address as the only settlement path. Options:
1. Fall back to a pull-based claim (e.g., track an internal balance for the beneficiary and let them call a `withdraw()`/`claim()` with an address of their choosing) when the direct push fails, mirroring the WETH pattern already used elsewhere in the codebase (`WrappedHyperFungibleToken.onAccept`), instead of reverting `_sendValue`.
2. Alternatively, add an escrowed-fallback mapping keyed by `beneficiary` that credits the amount when the `.call` fails, allowing anyone to later trigger delivery to an alternate address supplied by the beneficiary (analogous to how `retryPayload` provides alternate recovery in `HyperbridgeLzEndpoint`).
3. At minimum, decouple "who is authorized to claim" from "where funds are sent," so a stuck native-ETH settlement doesn't permanently brick the whole commitment and its associated ISMP message delivery.

### Proof of Concept
1. User (or a protocol acting on their behalf) calls `placeOrder` with a native-ETH input (`token == address(0)`) where `order.user` resolves to a smart-contract address with no `receive()`/payable `fallback()` (e.g., a bare `Ownable` contract or a misconfigured proxy).
2. Before the order is filled, the user (or, post-deadline, anyone) calls `cancelOrder`, which eventually dispatches a `RefundEscrow` (destination-chain cancel) or a `DispatchGet`/`onGetResponse` (source-chain cancel) request targeting `IntentsBase._withdraw`/`IntentGatewayV2.withdraw`.
3. On delivery, `_withdraw`/`withdraw` calls `_sendValue(beneficiary, amount)` → `beneficiary.call{value: amount}("")` → the call fails because `beneficiary` has no payable receiver.
4. `onAccept` (or `onGetResponse`) reverts; `EvmHost.dispatchIncoming` catches this, deletes the request receipt ("so that it can be retried") and returns without emitting `PostRequestHandled`.
5. Any subsequent relayer resubmission of the same proof/commitment hits the identical revert — the ETH remains escrowed in the gateway contract permanently, with no alternative claim mechanism available to the user.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
