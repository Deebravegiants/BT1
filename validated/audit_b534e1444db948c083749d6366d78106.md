### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `HmacValidator.validate` verifies the HMAC solely against that raw body and the app's `api_secret_key`. The `x-shopify-shop-domain` header, exposed via `Request#shop` and forwarded verbatim into `WebhookMetadata#shop` given to the host application's `WebhookHandler#handle`, is never included in the signed material and is never validated against a merchant registry.

### Finding Description
`Registry.process` performs exactly one check before dispatching to the handler: [1](#0-0) 
i.e. `raise Errors::InvalidWebhookError ... unless Utils::HmacValidator.validate(request)`, then calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`.

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC: [2](#0-1) 

For webhooks, `to_signable_string` is defined as just the raw body: [3](#0-2) 

Meanwhile `shop` is read straight off an attacker-controllable header with no relation to the signature: [4](#0-3) 

Because a single app-wide `api_secret_key` is shared across every merchant installation of a public app, any user can install the app on their own store and receive genuinely Shopify-signed webhooks for that store (with body content they substantially control, e.g. order notes, customer fields, product titles). Since the HMAC covers only the body and not the `shop-domain` header, that attacker can replay the exact same signed body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (or `shopify-shop-domain`) with a victim merchant's domain. `HmacValidator.validate` still succeeds because the body/secret pair is valid, and `Registry.process` passes `request.shop` (now the victim's domain) unmodified into `WebhookMetadata`, which the host application typically uses to look up per-shop session/tokens or to route/persist data. The binding that is broken: `shop (as validated by the HMAC) == shop (as trusted/acted upon by the handler)` — the HMAC only proves "this body came from an app installation using this secret," not "this event happened on this specific shop."

### Impact Explanation
Applications built on this gem's documented API commonly key their session/data store by `WebhookMetadata#shop` (see `docs/usage/webhooks.md`), so this allows an attacker who controls (or triggers webhooks on) any single shop that has installed the app to inject spoofed webhook events attributed to an arbitrary victim shop — a cross-tenant confusion/write primitive achieved purely through the gem's own header-vs-signature handling, without needing the app's `client_secret` or any victim credential.

### Likelihood Explanation
Requires only the ability to install a public app (or otherwise trigger a real webhook) on an attacker-owned store and the ability to send an HTTP POST with modified headers to the app's webhook endpoint — both achievable by an unprivileged internet user with no credentials belonging to the app or the victim.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the signed material verified by `HmacValidator`, or independently verify that `request.shop` corresponds to a shop actually known/installed by the app before dispatching to the handler, rather than trusting the unauthenticated header value end-to-end.

### Proof of Concept
1. Install the target public app on attacker-owned store `attacker.myshopify.com`; trigger `orders/create` to receive a genuine webhook POST with a valid `x-shopify-hmac-sha256` computed over the raw JSON body using the app's real `api_secret_key`.
2. Capture the raw body and the valid HMAC header.
3. Replay the identical raw body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` validates successfully (`Utils::HmacValidator.validate` only checks the body) and invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host app to process attacker-supplied data as belonging to the victim shop.
