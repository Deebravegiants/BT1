### Title
Cross-Tenant Webhook Spoofing via Unsigned `shop-domain` Header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Registry.process` never covers the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `Registry.process` still forwards `request.shop` to the app's webhook handler as the authoritative tenant identifier, breaking the binding `shop authenticated by HMAC == shop attributed to the webhook`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` compute/verify the signature strictly over `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from an HTTP header with no relation to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then passes `request.shop` unchecked into the app-level handler as the tenant identity: [2](#0-1) 

The documented integration pattern treats `data.shop` as trustworthy for tenant attribution/enqueuing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), which is exactly the binding this gem is expected to guarantee once `Registry.process` returns without error.

Because the signature only covers the body, any party in possession of one genuinely-signed webhook (raw_body + hmac pair) — for example a merchant/attacker's own store, which they can trigger themselves by placing an order, updating a product, etc. — can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary value in the `shop-domain` header. `HmacValidator.validate` will still succeed since it only recomputes the signature over `@raw_body`, and `Registry.process` will hand the forged `shop` value to the handler as if Shopify had authenticated it as originating from that other shop.

### Impact Explanation
This is a cross-tenant identity confusion at the boundary the gem is responsible for: it verifies the payload's authenticity but silently omits the shop identity from that authentication, then exposes the unauthenticated identity to the host application as if it were verified. Any host app following the documented pattern (attributing/queuing/persisting webhook data keyed by `data.shop`) can be made to associate one tenant's genuine event data with another tenant's identifier, enabling cross-tenant data leakage or corruption without needing the app's `client_secret` or any merchant credential — only a legitimately-received webhook of the attacker's own shop is required.

### Likelihood Explanation
Any merchant installing the app can generate a legitimate webhook for their own shop at will (e.g., creating an order/product), giving them a valid raw_body+HMAC pair to replay. The `shop-domain` header is fully attacker-controlled at replay time since it's outside the transport's TLS-authenticated channel from the app's perspective (the app only trusts the HMAC). No secret material is needed beyond what a normal, malicious merchant already legitimately receives.

### Recommendation
Include the shop domain (and ideally other webhook-identifying headers) in the signed content verified by `HmacValidator`, or independently bind `request.shop` to a value derived from data already authenticated by Shopify (e.g., cross-check against the resource/shop ids embedded in the signed body) before handing it to the handler. At minimum, document prominently that `data.shop` from `Registry.process` is unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-SHA256` header sent by Shopify.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC.
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's own order/product data, causing the host app to process/store this data under the victim tenant's identity.
