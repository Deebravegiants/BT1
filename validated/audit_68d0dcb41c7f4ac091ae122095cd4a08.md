### Title
Pausable/blacklistable ERC-20 input tokens can permanently block escrow release in IntentGateway's `_withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()`, used by `ExtrinsicIntents.onAccept()` to process `RedeemEscrow` and `RefundEscrow` messages, iterates over *all* the tokens bundled in a single `WithdrawalRequest` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one in a single atomic loop, with no isolation between tokens. If any one of the escrowed input tokens is a pausable or blacklist-capable ERC-20 (e.g. USDC-style tokens with `blacklist`, or any token with a `whenNotPaused` transfer guard) and that token's transfer to the beneficiary reverts, the entire `_withdraw` call reverts — which reverts the whole `onAccept` call.

### Finding Description
Users choose arbitrary ERC-20 tokens as order inputs in `placeOrder` (`evm/src/apps/IntentGatewayV2.sol` / `evm/src/apps/intentsv2/IntrinsicIntents.sol`) with no restriction on token type, and the protocol explicitly supports fee-on-transfer and other exotic ERC-20s [1](#0-0) . When the order is filled cross-chain, the destination gateway dispatches a `RedeemEscrow` message back to the source chain, which the source `ExtrinsicIntents.onAccept` decodes and passes to `_withdraw` [2](#0-1) :

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    ...
    for (uint256 i; i < len; i++) {
        ...
        if (token == address(0)) {
            _sendValue(beneficiary, amount);
        } else {
            IERC20(token).safeTransfer(beneficiary, amount);
        }
    }
    ...
}
```

There is no try/catch or per-token isolation — a revert on any single token's `safeTransfer` (e.g. because the token is paused, or the beneficiary is blacklisted on that token) reverts the whole withdrawal, including the release of all *other*, unaffected tokens bundled in the same commitment, and prevents `_filled[commitment]` from ever being set.

The host layer treats a reverting `onAccept` as "not yet delivered" rather than permanently failed: `EvmHost.dispatchIncoming` deletes the request receipt on failure "so that it can be retried" [3](#0-2) , and the ISMP handler-level documentation confirms the same semantics — a reverting `on_accept` leaves the request replayable rather than terminally failed [4](#0-3) . This means the message can be resubmitted indefinitely, but if the underlying condition (token permanently paused, or beneficiary permanently blacklisted, which is common and often irreversible for sanctioned addresses under USDC/USDT-style blacklists) never clears, the `RedeemEscrow`/`RefundEscrow` message can never be successfully delivered, and the escrowed tokens for that commitment — including any non-problematic tokens bundled with the bad one — remain locked in the gateway contract forever with no fallback path (there is no per-token retry or exclusion mechanism, and no way to redirect delivery to an alternate beneficiary once the order is filled/cancelled and the commitment is fixed).

This is the same bug class as the original report: an externally-controlled asset property (pause/blacklist) that the protocol does not account for turns a routine settlement operation into a permanently undeliverable one, freezing escrowed value.

### Impact Explanation
This is a permanent freezing-of-funds / undeliverable-message issue reachable by a single user action (placing or filling an order with an arbitrary ERC-20 input, which the protocol explicitly allows and even test-covers for weird token behaviors like fee-on-transfer). If the beneficiary/solver becomes blacklisted on one of the escrowed tokens (which is realistically possible for USDC/USDT- style tokens, either organically through OFAC-driven blacklisting or, in a griefing scenario, a solver intentionally filling orders whose inputs include a token they know will later be paused/blacklisted for another party), the entire batch of escrowed tokens for that order commitment becomes permanently stuck: `_withdraw` will keep reverting on every retry, `_filled` never finalizes, and none of the co-bundled tokens (even perfectly fine ones) can ever be released. This satisfies "permanent freezing of funds" / "a route unable to deliver messages" per the validation criteria.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an order with an ERC-20 input token that has pause/blacklist semantics, and (b) that token entering a paused/blacklisted state for the beneficiary at redemption time. Both conditions are realistic given the protocol's explicit design to support arbitrary ERC-20s (including "weird" tokens, per the fee-on-transfer test suite) with no allow-list or per-token isolation in `_withdraw`. No privileged role is required to trigger it — an ordinary order placer or filler can end up in this state, and once triggered there is no on-chain remediation path.

### Recommendation
- Make `_withdraw`'s per-token transfer loop fault-tolerant: wrap each `safeTransfer`/`_sendValue` call in a low-level call with try/catch (or use `Address.functionCall` with error swallowing) so a single problematic token cannot block release of the other tokens in the same commitment.
- Track per-token release state independently (e.g. only decrement/mark a specific `_orders[commitment][token]` entry as released on success) so failed tokens can be retried or swept separately without blocking the rest.
- Consider adding a governance-controlled "force sweep to alternate recipient" or "blacklist a problematic token from a specific order" path so genuinely stuck funds are not permanently unrecoverable when a beneficiary is sanctioned/blacklisted.

### Proof of Concept
1. User places a same-chain-style cross-chain order via `IntentGatewayV2.placeOrder`/`IntrinsicIntents` with two input tokens: `TOKEN_A` (normal ERC-20) and `TOKEN_B` (a pausable/blacklistable ERC-20, e.g., mock USDC with `blacklist(address)`).
2. Solver fills the order on the destination chain; destination gateway dispatches `RedeemEscrow` back to source with `WithdrawalRequest{ tokens: [TOKEN_A, TOKEN_B], beneficiary: solver }`.
3. Before the message is relayed and delivered, `TOKEN_B`'s issuer blacklists `solver` (or pauses the contract).
4. Relayer submits the `RedeemEscrow` proof; `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `ExtrinsicIntents.onAccept` → `_withdraw`.
5. `_withdraw`'s loop successfully transfers `TOKEN_A` to `solver`, then calls `IERC20(TOKEN_B).safeTransfer(solver, amount)`, which reverts because `solver` is blacklisted.
6. The whole `_withdraw` call reverts, so `onAccept` reverts; `EvmHost.dispatchIncoming` deletes the receipt (line 812-816) so the message is "retryable" — but every retry will keep reverting for as long as `solver` remains blacklisted on `TOKEN_B`, which for compliance-driven blacklists is typically permanent.
7. Result: both `TOKEN_A` and `TOKEN_B` escrow for this commitment remain locked in the gateway forever — `TOKEN_A`'s release is blocked purely because it was bundled with the problematic `TOKEN_B`, and there is no code path to separate or force-release it.

A relayer will construct the `RequestMessage` which holds a batch of new `PostRequest`s, as well as a _multi-proof_<sup>[1]</sup> of their existence on the source chain. The handler will perform the following operations

- Assert that the state machine's consensus client is not frozen
- Assert that the configured `challenge_period` for the `StateCommitment` has elapsed
- Assert that the requests have not been previously processed
- Assert that the requests have not timed out
- Assert that the membership proof for the requests verify
- Finally dispatch the requests to the relevant `IsmpModule::on_accept` and store a receipt for each request to prevent requests from being replayed.

<Callout title={'Danger'} type={"warn"}>
It's important to note that if the `IsmpModule::on_accept` does not return `Ok`, the receipt of this request will not be persisted, allowing the request to be **replayed**. Consequently, the `IsmpModule` is responsible for maintaining all invariants before modifying it's internal state to prevent partial state changes that could result in critical vulnerabilities in their request handler. This model ensures that if a request cannot be executed successfully on a destination state machine, it can time out gracefully on the source.
