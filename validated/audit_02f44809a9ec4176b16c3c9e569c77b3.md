### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while the shop identity (`shopify-shop-domain` header) is never included in the HMAC-signed payload. Since a single `api_secret_key` is shared by the app across every merchant shop that installs it, any merchant who installs the app can obtain a genuinely-signed webhook body and then replay that body while forging the `shop-domain` header to impersonate a different (victim) shop. `ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the body and then trusts the unauthenticated `shop` header to build `WebhookMetadata`, which host applications are documented to use as the authoritative tenant identifier.

### Finding Description
The HMAC validation binding is:

`computed_hmac(raw_body, api_secret_key) == received_hmac` 

but the trust the library extends is:

`shop = header("shopify-shop-domain")` (unauthenticated) 

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which uses `request.to_signable_string`, defined as just `@raw_body`: [1](#0-0) 

The `shop` accessor pulls straight from headers with zero verification: [2](#0-1) 

`Registry.process` verifies only the body HMAC, then immediately forwards the unauthenticated `request.shop` to the handler as the tenant identifier: [3](#0-2) 

`HmacValidator` computes the digest exclusively over `to_signable_string` (the body) using the app-wide secret, with no per-shop binding: [4](#0-3) 

Because `Context.api_secret_key` is one static value for the whole app (shared across all merchant installs), the HMAC only proves "this body was signed by someone holding the app's client secret" (i.e., genuinely came from Shopify for *some* shop that installed the app), not "this body/shop pairing came from *this specific* shop." Any attacker who installs the app on their own store receives real, validly-signed webhook deliveries and can replay the identical signed body to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim's domain. The signature still validates because the header is not part of the signed content.

The library's own documentation instructs host applications to treat `data.shop` as the trusted tenant identifier immediately after HMAC verification: [5](#0-4) [6](#0-5) 

This is the exact "field acted on but not covered by the HMAC" pattern: the `shop` field is used as the tenant key for dispatch/storage, but it is excluded from `to_signable_string`.

### Impact Explanation
This breaks the tenant identity binding `authenticated_signer == acted_upon_shop`. An attacker who installs the app on their own (attacker-controlled) shop can forge webhook deliveries that any host application built per this gem's documented pattern will process as originating from an arbitrary victim shop, since `WebhookMetadata#shop` is trusted downstream to look up/scope data (e.g., `perform_later(shop_domain: data.shop, ...)` per the docs). This constitutes cross-tenant access — a Critical-impact category per the given rules — enabling injection of attacker-controlled data (order/product/customer payloads) tagged as belonging to a victim's shop, potentially corrupting victim-shop data stores, queues, or triggering unauthorized actions keyed on the spoofed shop.

### Likelihood Explanation
The only prerequisite is that the attacker can install the target app on any Shopify store they control (a routine, low-privilege action available to any Shopify merchant/developer, not requiring the app's `client_secret`, an access token, or any victim credentials). No cryptographic secret needs to be broken; the attacker simply reuses a legitimately-issued HMAC for a differently-labeled request.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically verify the shop header against a value derived from a per-shop secret (e.g., the shop's own access token/session) rather than the shared `api_secret_key`. At minimum, before trusting `request.shop`, cross-check it against a `shop` value obtained from a store the app can trust (e.g., verify the request also came through a registered webhook subscription tied to that shop through Shopify's `X-Shopify-Webhook-Id` lookup via the Admin API), or require applications to reconcile `data.shop` against known installed-shop records rather than trusting it outright. Document explicitly, at minimum, that `data.shop` is not covered by the HMAC and must not be treated as authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`) via the normal OAuth+registration flow supported by this gem.
2. Shopify sends a legitimately HMAC-signed webhook to the attacker's endpoint:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
   - Body: attacker-controlled order JSON (attacker creates the order in their own store to control the body content).
3. Attacker replays the exact same body and HMAC to the victim app's webhook endpoint but changes only the header: `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` verifies `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC — this passes because the body and HMAC are unmodified originals.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_json, ...)`, and any host application following this gem's documented pattern (`perform_later(shop_domain: data.shop, webhook: data.body)`) processes/stores attacker-controlled data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
