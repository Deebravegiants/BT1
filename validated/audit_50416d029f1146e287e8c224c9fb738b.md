### Title
Stake account state can drift between epoch-reward calculation and partitioned distribution, causing panic on delegation mismatch - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
The Lido report describes a class of bug where an amount is fixed/committed at one point in time (`initiatingAdminSettleDebt`) but the underlying account state can still change before it is actually settled (`adminSettleDebt`), producing an inconsistent, loss-causing outcome. The agave analog is in the partitioned epoch-rewards distribution path: stake rewards are computed once at the epoch boundary (`Calculation` phase) using a stake-history snapshot, but the actual crediting to each stake account happens later, over multiple subsequent blocks (`Distribution` phase), by re-reading the *live* `stakes_cache` for that pubkey and asserting that its current delegation equals the value predicted at calculation time.

### Finding Description
`distribute_partitioned_epoch_rewards` computes `PartitionedStakeReward`s once, then applies them block-by-block via `store_stake_accounts_in_partition` → `build_updated_stake_reward` [1](#0-0) . Inside `build_updated_stake_reward`, the current, live version of the account is fetched from `stakes_cache_accounts` (i.e., whatever the delegation currently is in this later block, not what it was at calculation time) [2](#0-1) . When `adjust_delegations_for_rent` is false, the code asserts that the live stake's delegation, plus the pre-computed `stake_reward`, exactly equals the pre-computed `new_stake.delegation.stake`:

```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, "stake reward delegation must be consistent with the updated stake account lamport balance");
``` [3](#0-2) 

The comment on `store_stake_accounts_in_partition` explicitly acknowledges the underlying assumption that makes this safe: *"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned."* [4](#0-3) . This is precisely the same trust assumption that failed in the Lido report — a value is fixed at "commit" time on the belief that the underlying balance/state cannot move before "settle" time.

Unlike the nonce/fee-payer path, which explicitly re-validates state at load time for every transaction (`validate_transaction_nonce`, `validate_transaction_fee_payer` re-check current account state rather than trusting a stale snapshot) [5](#0-4) , the epoch-reward distribution path does not re-validate; it simply asserts the live state matches the calculation-time prediction and panics via `assert_eq!` if not. I could not find, within the areas covered by the search tool, an equivalent guard inside the stake program (`programs/stake*`) that would categorically prevent a stake delegation from changing between the calculation slot and a subsequent distribution slot (e.g., via `DeactivateDelegated`, `Split`, `Merge`, `Redelegate`, or `SetLockup`-adjacent flows touching `delegation.stake` during the multi-block reward interval). The `stake_at_distribution_epoch` calculation elsewhere in the same function does account for warmup/cooldown effects across epochs, indicating that stake state is understood to evolve, yet the static "no burn" assertion assumes it cannot for the immediate reward-affecting delegation field between calculation and store.

### Impact Explanation
If a stake account's delegation can be legitimately mutated by its own staker/withdrawer between the reward-calculation block and its corresponding distribution block (which can be up to 10% of an epoch's slots later, per `get_reward_distribution_num_blocks`) [6](#0-5) , the `assert_eq!` in `build_updated_stake_reward` fires and the process panics. Because `distribute_partitioned_epoch_rewards` is invoked unconditionally for every bank at the start of block processing while rewards are active [7](#0-6) , a deterministic panic here would be hit identically by every validator replaying the same block, producing a network-wide halt rather than a single-node crash — a severe availability impact, analogous in spirit to the value-loss impact described in the report but manifesting as a chain halt instead of a fund loss.

### Likelihood Explanation
Likelihood depends entirely on whether the stake program (not fully visible via the available search tooling) blocks the specific instructions that could change `delegation.stake` for any stake account that has an outstanding, uncredited `PartitionedStakeReward` during the multi-block distribution window. If such a block exists and is complete, this is not exploitable. I was unable to locate and confirm such a guard in `programs/stake*` using the tools available (searches for `reward_interval`/`EpochRewardStatus` under `programs/stake*` returned no matches), so I cannot confirm whether the safeguard the code comments describe is actually implemented and complete, or whether an edge case (e.g. across epoch/root boundaries, or via a normal stake operation not covered by the restriction) allows the mismatch to occur.

### Recommendation
Given the uncertainty above, this should be independently verified against `programs/stake-program`/`programs/stake` source (or an equivalent SIMD spec) for a complete, gap-free guard preventing stake-delegation mutation for any account with a pending `PartitionedStakeReward`. If no such complete guard exists, `build_updated_stake_reward` should be hardened to gracefully handle (rather than `assert_eq!`/panic on) delegation mismatches — e.g., by burning/logging the discrepancy through the existing `DistributionError` path instead of an unconditional assertion, consistent with how `Err` results are already handled elsewhere in `store_stake_accounts_in_partition`.

### Proof of Concept
Not independently reproducible with the tools available in this session; the finding is based on static analysis of `build_updated_stake_reward`'s hard assertion (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:284-294`) together with the explicit code comment asserting an external invariant ("further state mutation prevents by stake-program restrictions") that could not be located/confirmed in the stake program source via search. A Devin session with full repository access and the ability to run the reward-distribution integration tests (e.g. modifying `test_delegation_adjustment_at_distribution`-style tests in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` to mutate a stake account's delegation, not just its lamports, between the calculation and distribution blocks) would be needed to confirm whether this path is actually reachable and panics.

    fn validate_transaction_nonce<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        message: &impl SVMMessage,
        nonce_address: &Pubkey,
        next_durable_nonce: &DurableNonce,
        next_lamports_per_signature: u64,
        strict_nonce_size_check: bool,
        error_counters: &mut TransactionErrorMetrics,
    ) -> TransactionResult<NonceInfo> {
        // When SIMD83 is enabled, if the nonce has been used in this batch already, we must drop
        // the transaction. This is the same as if it was used in different batches in the same slot.
        // It is possible that the nonce account was used, closed, closed and reopened, closed and
        // spoofed by a non-system program, or had its authority changed. Such a transaction cannot
        // be processed, even as fee-only.

        let Some(mut nonce_account) = account_loader
            .load_transaction_account(nonce_address, true)
            .map(|loaded| loaded.account)
        else {
            error_counters.account_not_found += 1;
            return Err(TransactionError::AccountNotFound);
        };

        if strict_nonce_size_check && nonce_account.data().len() != NonceState::size() {
            error_counters.blockhash_not_found += 1;
            return Err(TransactionError::BlockhashNotFound);
        }

        // This function verifies:
        // * Nonce account owner is SystemProgram
        // * Nonce account parses as State::Initialized
        // * Stored durable nonce matches the message blockhash
        let Some(nonce_data) = verify_nonce_account(&nonce_account, message.recent_blockhash())
        else {
            error_counters.blockhash_not_found += 1;
            return Err(TransactionError::BlockhashNotFound);
        };

        // We must still check that the nonce account is usable and that its authority has signed.
        let nonce_can_be_advanced = &nonce_data.durable_nonce != next_durable_nonce;
        let nonce_authority_is_valid = message
            .get_ix_signers(NONCED_TX_MARKER_IX_INDEX as usize)
            .any(|signer| signer == &nonce_data.authority);

        if nonce_can_be_advanced && nonce_authority_is_valid {
            let next_nonce_state = NonceState::new_initialized(
                &nonce_data.authority,
                *next_durable_nonce,
                next_lamports_per_signature,
            );
            nonce_account
                .set_state(&NonceVersions::new(next_nonce_state))
                .expect("Serializing into a validated nonce account cannot fail");

            Ok(NonceInfo::new(*nonce_address, nonce_account))
        } else {
            error_counters.blockhash_not_found += 1;
            Err(TransactionError::BlockhashNotFound)
        }
    }

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
