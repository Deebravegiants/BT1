### Title
Excess native token sent to `EvmHost.dispatch`/`fundRequest` is swapped in full and any Uniswap refund is captured by `EvmHost` instead of the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost memory post)`, `EvmHost.dispatch(DispatchGet memory get)`, and `EvmHost.fundRequest(...)` are all `payable` and, when `msg.value > 0`, forward the **entire** `msg.value` to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. This mirrors the analog report's root cause: a payable entrypoint accepts native token, performs an operation that only needs a fixed sub-amount, and never returns the unused remainder to the original caller.

### Finding Description
In `dispatch(DispatchPost memory post)`: [1](#0-0) 
the full `msg.value` is forwarded to the Uniswap router even though only `post.fee` worth of fee tokens is required. The identical pattern exists in `dispatch(DispatchGet memory get)`: [2](#0-1) 
and in `fundRequest`: [3](#0-2) 

`IUniswapV2Router02.swapETHForExactTokens` refunds any leftover ETH to `msg.sender` of the router call — but because `EvmHost` itself is the caller of the router (not the original end user), that refund lands back in `EvmHost`'s own balance, not in the address that originally sent the overpaying transaction. There is no code path in `EvmHost.sol` that forwards this reclaimed ETH back to `_msgSender()`/`post.payer`, nor is there a documented `withdraw`/sweep function visible in the indexed portion of the contract for recovering this balance to the original payer.

This is the same bug class as the audit report: a payable function accepts native token for an operation, computes/consumes only a fixed sub-amount, and the surplus is not returned to the address that supplied it — it instead accumulates in the protocol contract.

By contrast, the higher-level apps in this repo (e.g. `IntentGatewayV2`, `ExtrinsicIntents`) explicitly track `msgValue` and refund any leftover to the caller after use: [4](#0-3) 
which shows the project is aware of this exact overpayment-refund requirement elsewhere, but `EvmHost.dispatch`/`fundRequest` (the lowest-level, most widely reachable dispatch primitive used by every app, including the documented direct-usage pattern) lacks this same refund logic. The official documentation even instructs developers to call `dispatch{value: msg.value}(post)` directly with the caller's full `msg.value`: [5](#0-4) 
which is the exact overpayment vector: any user or integrating contract that sends more native token than the router needs to buy `post.fee`/`get.fee`/`amount` worth of fee token loses the difference into `EvmHost`.

### Impact Explanation
Any external caller (an unprivileged message dispatcher/relayer/app) that calls `EvmHost.dispatch(...)` or `EvmHost.fundRequest(...)` with `msg.value` greater than what's needed to purchase the exact fee amount permanently loses the excess native token — it becomes stuck in `EvmHost`'s balance with no return path to the original sender. This is a direct freezing-of-funds bug reachable from the primary, permissionless dispatch entrypoint that every Hyperbridge application (HyperFungibleToken, IntentGatewayV2, LayerZero endpoint adapter, etc.) and any third-party integrator relies on.

### Likelihood Explanation
High likelihood of occurrence in practice: exact fee-token pricing via a live Uniswap pool is inherently imprecise (slippage, price movement between quote and execution), so integrators are expected to send a safety margin of native token (as explicitly suggested in the SDK/docs' "excess native is refunded by the uniswap router" comment in `HyperbridgeLzEndpoint.sol`, which is actually incorrect given the refund lands in `EvmHost`, not the caller). Any slight overestimation of `msg.value` versus `swapETHForExactTokens`'s required input silently locks funds.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, after calling `swapETHForExactTokens`, capture its return value (amounts spent) or measure `address(this).balance` delta and refund any unspent native token back to `_msgSender()` (or `post.payer`), consistent with the refund pattern already implemented in `IntentGatewayV2` and `ExtrinsicIntents.sol`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: X}(post)` where `X` is meant to loosely cover `post.fee` in `feeToken()`.
2. `EvmHost` executes `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`; suppose only `Y < X` wei of ETH is actually needed to buy `post.fee` tokens at the current pool price.
3. The Uniswap V2 router refunds `X - Y` wei of ETH to `msg.sender`, which is `EvmHost`, not the original caller.
4. `EvmHost`'s native balance permanently increases by `X - Y`; the original caller has no function to reclaim it. [1](#0-0)
