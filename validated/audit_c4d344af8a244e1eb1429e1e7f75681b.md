### Title
Webhook Shop/Topic Identity Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by HMAC-checking only the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers — none of which are covered by that signature — when building the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Request#to_signable_string` returns solely the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from separate, unsigned headers: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that signature against `to_signable_string` (the body): [3](#0-2) 

`Registry.process` performs this single check and then immediately trusts the unsigned `request.shop` / `request.topic` values to build the metadata delivered to the app's handler: [4](#0-3) 

This breaks the identity binding `shop_bound_by_hmac == shop_used_by_handler`: the HMAC only proves "this body byte-string was signed with the api_secret_key at some point," it proves nothing about which shop or topic that body belongs to. The `docs/usage/webhooks.md` description explicitly states that `Registry.process` "will verify the request did indeed come from Shopify," implying full authenticity of the delivered event including its tenant attribution, but the implementation only authenticates the body bytes.

### Impact Explanation
An attacker who has installed the app for their own shop receives a batch of genuinely Shopify-signed webhook deliveries (body + valid `X-Shopify-Hmac-Sha256`) for their own tenant. Because the signature never covers the `X-Shopify-Shop-Domain` or `X-Shopify-Topic` headers, the attacker can replay the exact same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop (and/or the `topic` header for a different registered topic). `HmacValidator.validate` still succeeds — the body and HMAC are unchanged and genuinely signed — so `Registry.process` invokes the handler with `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim's shop. Any app logic that uses `data.shop` to select the tenant record/session to write into (a standard and encouraged pattern) will process attacker-supplied content under another tenant's identity, i.e. cross-tenant data injection/corruption.

### Likelihood Explanation
Any unprivileged internet user who can install the app once (to obtain valid signed webhook payloads for their own shop) and knows another tenant's shop domain (public information, e.g. `victimshop.myshopify.com`) can perform this attack purely by replaying an HTTP POST with a modified header — no secret key, access token, or privileged access is required.

### Recommendation
Include the tenant/topic identity in the value that is HMAC-verified, or independently bind the `shop-domain` header to a known/allow-listed installed shop before trusting it, e.g.:
- Have `Request#to_signable_string` incorporate the `shop`, `topic`, and `webhook_id` headers together with the body (matching what Shopify actually signs, if it does), or
- Require callers of `Registry.process` to supply the expected shop (from their own session lookup) and assert `request.shop == expected_shop` before invoking the handler, and document this requirement clearly so `process` cannot be mistaken for full attribution verification.

### Proof of Concept
1. Attacker installs the target app for `attacker-shop.myshopify.com` and registers to receive a webhook topic the app processes (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's shared endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: attacker-controlled order JSON (attacker can create arbitrary order content in their own shop).
3. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) body against the (unmodified) HMAC: [5](#0-4) 
5. The app's registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's body, and processes it as if it were a genuine event from the victim's store.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end
