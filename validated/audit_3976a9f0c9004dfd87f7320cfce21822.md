### Title
Payload-supplied pool addresses are invoked without an allowlist, letting attacker contract code run under the swapper's auth tree and transfer arbitrary tokens out of their wallet - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The docling-core bug class is *unsafe resolution of untrusted remote input*: a server-provided `Content-Disposition` filename was resolved to a local destination without normalization, enabling access outside the intended directory (SSRF / path escape). The on-chain analog is the swap router resolving **server/route-supplied destination addresses** (pools, tokens in the `assets` registry) into contract invocations with no allowlist or normalization. A malicious quote/route names an attacker-deployed contract as a hop pool; the router calls it while the victim's `require_auth` tree is open, and the rogue pool can append a `token.transfer(victim → attacker)` call that the simulator records as a child of the victim's authorization entry. If the victim signs that tree, the transfer executes — draining wallet funds unrelated to the swap.

### Finding Description
`execute_strategy` decodes a fully caller-supplied `StrategyPayload` (`contracts/swap-aggregator/src/lib.rs:250-255`). The `assets` registry contains arbitrary `Address` values supplied in the XDR; `Program::decode` only range-checks registry *indices*, never the resolved addresses (`contracts/swap-aggregator/src/program.rs:213`). During execution, `execute_op` builds each `SwapHop` with `pool: ctx.assets.get_unchecked(op.idx_a)` (`contracts/swap-aggregator/src/execute/mod.rs:153-157`) and `dispatch_hop` invokes it through venue adapters with no venue or pool allowlist (`contracts/swap-aggregator/src/venues/mod.rs:34-40`). Adapters call payload-named contracts directly, e.g. `env.invoke_contract(&ctx.hop.pool, "swap", ...)` (`contracts/swap-aggregator/src/venues/soroswap.rs:85-87`).

The only signature is `sender.require_auth()` at `execute/mod.rs:52`. A rogue pool invoked mid-route can call `token::transfer(victim, attacker, amount)` on any token the victim holds; because it executes inside the victim's authorized invocation, simulation appends it as a child of the victim's auth entry, and a signature over that tree authorizes the theft. The protocol's own threat model documents exactly this: "a route can put third-party code on the call stack below the caller's authorization ... it executes if the caller signs that tree. The loss is then the caller's wallet" (`docs/explanation/threat-model.md:154-165`). The same exposure exists via controller strategies (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`), which forward caller-supplied `swap_xdr`, and is proven by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:301-368`, where the rogue pool's transfer from the victim's wallet succeeds once the simulated tree is signed.

### Impact Explanation
Theft of user funds. The stolen amount is unbounded by the routed input, the payload `min_out`, or the controller's final risk gates — the rogue transfer moves any token in the victim's wallet directly to the attacker. The attacker is unprivileged: they only need to supply a crafted route (malicious quote server, compromised route API, or a phishing route handed to the victim) naming their own contract as a hop pool.

### Likelihood Explanation
Requires the victim to sign an authorization tree whose simulation includes the rogue child transfer. Honest clients decode and reject unexpected children, but the signed-tree requirement is the only barrier — no on-chain check prevents it, and users routinely sign whatever the route server returns. The venue/pool set is unrestricted by design and the quote server is off-chain, so a single malicious or compromised route source can reach every router user.

### Recommendation
Maintain an on-chain allowlist of venue pool addresses (or venue contract WASMs), set via governance/owner, and have `dispatch_hop` reject hops whose `pool` is not registered. Alternatively, restrict the auth surface: perform venue calls so that the sender's auth cannot be extended by nested contracts — e.g., require routes to resolve pools from a governance-curated registry keyed by token pair rather than from the payload `assets` vector. At minimum, document and enforce client-side rejection of any auth child beyond the single input `transfer`.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. `RogueHopPool` (lines 51-72) is an attacker contract whose `swap` entrypoint calls `token.transfer(victim, attacker, amount)` on an unrelated wallet token.
2. A route payload names `RogueHopPool` as the hop pool (lines 111-125); `execute_strategy`/`swap_collateral` invokes it mid-route under the victim's `require_auth`.
3. Lines 322-368 show the theft is refused under an honest tree but executes once the victim signs the simulated tree containing the rogue `transfer` child — `token.moved() == Some((attacker, 99))`.

Mirrors the docling advisory: an untrusted remote party supplies a destination (filename / pool address) that the system resolves and dereferences without restriction, reaching resources (local files / the caller's wallet via their auth tree) outside the intended scope.
