### Title
Fee-on-transfer tokens break escrow accounting in Tron `IntentGatewayV2.placeOrder()` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits escrow based on the *nominal* `order.inputs[i].amount` (minus protocol fee) rather than the actual amount of tokens the contract received via `safeTransferFrom`. For fee-on-transfer (FoT) ERC-20 input tokens, the contract will under-receive tokens but over-credit escrow, creating an accounting shortfall.

### Finding Description
In `placeOrder`, when there is no predispatch call, tokens are pulled with a plain `safeTransferFrom` and the escrow ledger is incremented by `reducedInputs[i].amount`, which is derived directly from `order.inputs[i].amount` (the amount the *caller specified*), not from any measured balance change: [1](#0-0) 

Compare this to the mainline EVM `IntentGatewayV2.placeOrder()` in `evm/src/apps/IntentGatewayV2.sol`, which explicitly snapshots `balanceOf` before and after the `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received amount before computing protocol fees and crediting escrow — the code even has a comment stating "For fee-on-transfer tokens, the gateway receives less than the requested amount. We mutate order.inputs to reflect actual received": [2](#0-1) [3](#0-2) 

The predispatch branch of the Tron contract also credits `_orders[commitment][token] += reducedInputs[i].amount` using the pre-fee nominal amount rather than the measured `dust`-adjusted balance: [4](#0-3) 

This is directly analogous to the reported Allo `_fundPool()` bug: a fixed nominal amount is trusted as "amount transferred in," while the actual token balance received is smaller due to a transfer fee, causing the internal accounting (`_orders` escrow mapping here, `increasePoolAmount` in Allo) to overstate the true balance held by the contract.

The dedicated fee-on-transfer regression tests (`testPlaceOrder_FeeOnTransferToken*`) exist only against the mainline `evm/src/apps/IntentGatewayV2.sol` contract, confirming this is a known, deliberately fixed bug class for that contract but not for the Tron fork: [5](#0-4) 

### Impact Explanation
Escrow accounting (`_orders[commitment][token]`) will show a balance that exceeds the contract's actual token holdings for any FoT input token. When a solver later fills the order or the user cancels it, `withdraw()` releases `body.tokens[i].amount` (sourced from the inflated `_orders` value) via a plain ERC-20 transfer: [6](#0-5) 

Because escrow bookkeeping across all orders is tracked per-token in a single global-per-commitment mapping funded from a shared contract token balance, over-crediting one order's escrow can allow that order's beneficiary to be paid out more of a given token than the gateway actually holds for it, which is only satisfiable by draining balance belonging to other users' escrowed orders of the same token — a fund-freezing/insolvency condition for the last order(s) to withdraw. This is a genuine loss/freezing-of-funds path reachable by any user simply calling `placeOrder` with a permitted FoT token, matching the required "unprivileged... reachable" and "concrete theft or permanent freezing of funds" criteria.

### Likelihood Explanation
Likelihood depends on whether Tron token deployments used with this gateway include fee-on-transfer semantics (e.g., TRC-20 equivalents of STA/PAXG-style tokens, or a token that later adds a transfer tax via upgradeable/proxy logic). Because the whitelist of acceptable input tokens is presumably governance/config-controlled rather than enforced on-chain by this contract, and the gateway itself makes no invariant check against such tokens, any single order placement with such a token triggers the miscounting deterministically — no adversarial coordination is required beyond choosing/onboarding a FoT token.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron fork: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` (and after the predispatch sweep), use the actually-received delta as `order.inputs[i].amount` before computing `protocolFeeBps` and before crediting `_orders[commitment][token]`, and emit `DustCollected` for any positive/negative discrepancy exactly as the mainline contract does.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and register a fee-on-transfer TRC-20 token (analogous to the Foundry `FeeOnTransferToken` test helper) with e.g. a 1% transfer fee, as an allowed input token.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch call, approving the gateway for 1000e18.
3. `safeTransferFrom` pulls 1000e18 from the user's balance but the gateway's TRC-20 balance only increases by 990e18 (1% burned/redirected as fee).
4. The Tron contract nonetheless computes `reducedInputs[0].amount` from the nominal `1000e18` (minus protocol fee, if any) and sets `_orders[commitment][FOT] = reducedInputs[0].amount` (≈ up to 1000e18 minus protocol fee), which is greater than the 990e18 actually held for this order.
5. When the order is filled/cancelled, `withdraw()` attempts to pay out the inflated escrowed amount, which — once multiple orders interact with the same FoT token pool — can only be satisfied by consuming token balance escrowed for other users, resulting in some order's beneficiary being unable to be paid in full (frozen funds) or another order's escrow being silently drained.
