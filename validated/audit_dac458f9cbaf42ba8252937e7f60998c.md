### Title
Third-party pre-funding of a signer's HinkalWallet lets externally-arriving tokens bypass the Emporium balance-delta accounting and sit unswept - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction()` computes `balancesBefore`/`balancesAfter` only on `address(this)` (the Emporium contract), while `CASE 1: Stateful Interaction` (`invokeWallet == true`) routes calls through the signer's separate `HinkalWallet` contract [1](#0-0) . Any tokens an external protocol call sends to that wallet are never observed by the delta calculation unless a specific, pre-signed op inside the same `EmporiumStack` explicitly moves them to the Emporium contract [2](#0-1) .

### Finding Description
`getBalancesForArray`/`getERC20OrETHBalance` always read `address(this)`'s balance [2](#0-1) , i.e. the Emporium proxy's balance, never the per-signer `HinkalWallet`'s balance. When `op.invokeWallet && stack.signerAddress != address(0)`, the call is executed by `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`, so any value an external DeFi protocol returns (reward claim, swap output, unstake, etc.) lands on the `HinkalWallet` contract, not on the Emporium [3](#0-2) [4](#0-3) .

`handleOut()`'s `balanceChange = balancesAfter[i] - balancesBefore[i]` is the only source of truth for what gets converted into an outgoing UTXO to the caller [5](#0-4) . If the `EmporiumOperation[]` sequence that the signer pre-authorized (via the EIP-712 signature checked in `verifyWallet`) moves only a fixed/expected amount from the wallet to the Emporium (or omits that step entirely, e.g., because a "claim rewards" op simply calls a protocol's `getReward(walletAddress)`-style function and relies on the wallet's balance being swept in a follow-up call), then any tokens that reach the `HinkalWallet` from a source other than that exact accounted flow are invisible to the Emporium's delta accounting.

This is the same root cause as the referenced report: **any unprivileged address can trigger a permissionless reward/claim function that targets a fixed beneficiary address** (here, the `HinkalWallet` address, which is deterministic/known once deployed) at a time the signer does not control. Because the `EmporiumOperation.callData` and `value` are fixed at signature time (`EMPORIUM_OPERATION_TYPEHASH`/`EMPORIUM_SIGNATURE_TYPEHASH`), the wallet-to-Emporium sweep step in that pre-signed op set can only move the amount anticipated when the message was signed - not any additional balance that arrived on the wallet from an out-of-band, third-party-triggered claim/reward call. Those extra tokens remain in the `HinkalWallet`, uncounted by `balancesBefore`/`balancesAfter`, and cannot be converted into a spendable UTXO by that transaction.

### Impact Explanation
This breaks the balance equation Hinkal relies on to mint UTXOs backed by real token movement: value legitimately reaches a Hinkal-controlled contract (the signer's `HinkalWallet`) but is excluded from `circomData`/the public-input vector that produces the corresponding UTXO commitment, because the accounted balances are only ever taken on the Emporium address. Until the signer crafts and submits an entirely new, freshly-signed `EmporiumStack` whose op explicitly sweeps the wallet's current (now-larger, and possibly unknown at signing time) balance, those funds sit frozen and non-spendable inside the wallet - a temporary freezing of user funds, matching the "High" impact tier (temporary freezing of user funds / protocol funds via a flow not authorized by the balance equation).

### Likelihood Explanation
Likelihood depends on external protocols allowing permissionless claim/reward calls with an attacker-chosen or already-known beneficiary equal to the victim's `HinkalWallet` address, which is a common DeFi pattern (e.g., Aura/Convex-style `getReward(address)`, staking reward claim functions, etc.) - exactly the pattern cited in the source report. Any unprivileged EOA that knows or predicts a user's `HinkalWallet` address (deployed contract, address is public/derivable) can call such a claim function ahead of, or independent from, the user's intended `runAction` transaction, at zero cost to the attacker and without needing the signer's key.

### Recommendation
- Track and reconcile balances on the `HinkalWallet` itself (not just on the Emporium contract) whenever `invokeWallet` ops are used, or force every wallet-routed op sequence to end with an unconditional "sweep full current balance to Emporium" step computed at execution time rather than a value hard-coded at signature time.
- Alternatively, add a permissionless `sweepToEmporium(address[] tokens)` function on `HinkalWallet` (callable by anyone, but only forwarding to the owning Emporium, never to an arbitrary recipient) so stray tokens can be swept into the balance-delta accounting without requiring a brand-new signed message, and design op templates so the amount moved is "whatever the current balance is" rather than a fixed pre-signed amount.

### Proof of Concept
1. Signer S authorizes (via EIP-712, `EMPORIUM_SIGNATURE_TYPEHASH`) an `EmporiumStack` whose op set: (a) calls an external protocol via `HinkalWallet(S).callHinkalWallet(...)` to claim rewards, expecting `X` reward tokens, then (b) transfers `X` reward tokens from the wallet to the Emporium.
2. Before this transaction lands, attacker A calls the same external protocol's permissionless reward function directly, e.g. `RewardsContract.getReward(walletAddress)`, causing `X` (or more) reward tokens to be transferred to `HinkalWallet(S)` immediately.
3. S's pre-signed `runAction` executes: step (a)'s protocol call now returns `0` new rewards (already claimed), so step (b)'s fixed transfer of `X` either reverts (insufficient marginal rewards were actually newly claimed) or, if step (b) is a fixed-amount transfer independent of the claim's return value, it still moves `X` tokens out - but any protocol logic that pays out MORE than `X` after A's front-run (e.g., due to reward-rate accrual between A's and S's calls) leaves the surplus stuck on `HinkalWallet(S)`, since `balancesBefore`/`balancesAfter` in `runAction` never inspect the wallet's balance at all [6](#0-5) .
4. The surplus is not represented by any UTXO and is inaccessible to S until a new signed `EmporiumStack` is constructed and submitted specifically to sweep it.

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }
    }

    function getBalancesForArrayMemory(
        address[] memory erc20TokenAddresses
    ) internal view returns (uint256[] memory balances) {
        balances = new uint256[](erc20TokenAddresses.length);
        for (uint64 i; i < erc20TokenAddresses.length; i++) {
            balances[i] = getERC20OrETHBalance(erc20TokenAddresses[i]);
        }
    }
