### Title
Webhook `topic` and `shop` fields are trusted for tenant/handler dispatch without HMAC coverage - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then dispatches the handler and attributes the event to a tenant using two header-derived fields (`topic`, `shop`) that are never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile `topic` and `shop` are read directly from HTTP headers with no cryptographic binding to the body or to the HMAC [3](#0-2) .

`Registry#process` uses exactly this unguarded pair to decide which handler to invoke and which shop to attribute the payload to:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [4](#0-3) 

The equality the design implicitly (and incorrectly) assumes is:
`HMAC-valid(raw_body)` ⇒ `(topic, shop)` are the values Shopify actually associated with that body.

In reality the binding only guarantees the raw body bytes are untampered; `topic` and `shop` are attacker-controlled header values whenever the request does not originate from Shopify's own infrastructure (e.g., a merchant/attacker who has installed the app and thus legitimately received real webhook deliveries containing a valid `body + HMAC` pair signed with the app's shared `client_secret`). Such an actor can replay a body/HMAC pair they legitimately received for their own shop while substituting the `shop-domain` header to name a different (victim) shop, and/or substituting the `topic` header to route the same body to a different handler than the one Shopify actually triggered it for. Since neither field is part of `to_signable_string`, `HmacValidator.validate` still returns `true`.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: the `shop` value handed to application handlers (used by consuming apps to key their per-tenant data, per the documented `WebhookMetadata#shop` contract [5](#0-4) ) can be forged to any shop domain while still passing the gem's own HMAC check. An attacker who is a legitimate merchant of the app (i.e., has previously received real webhook bodies with valid signatures for their own shop) can cause the app to process/attribute forged webhook data as belonging to another tenant, or trigger the wrong topic's handler (e.g., feed an `orders/create` body into whatever handler is registered under a forged `app/uninstalled` topic) — a cross-tenant data-integrity/authentication issue.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus possession of one legitimately-received `raw_body + hmac-sha256` pair (trivially available to any merchant/attacker who has installed the app, since Shopify delivers these to the app's own registered endpoint). No access to `api_secret_key`, access tokens, or the target victim shop's credentials is needed — only header substitution on replay, which is directly reachable through this gem's documented `Registry.process` API without the host app deviating from the documented usage in `docs/usage/webhooks.md`.

### Recommendation
Include `topic` and `shop` (and ideally `webhook_id`/`api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., verify the request against Shopify's published sender IP ranges in addition to HMAC, or require the consuming app to correlate `webhook_id`/`shop` against the specific webhook subscription that was registered for that topic/shop pair) before dispatching to the handler or attributing the event to a tenant.

### Proof of Concept
1. App registers webhook handler `H` for topic `orders/create`, delivery path `/webhooks`.
2. Attacker installs the app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate `orders/create` webhook to `/webhooks`, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header — a valid `(body, hmac)` pair under the app's shared `client_secret`.
3. Attacker replays this exact `(raw_body, hmac-sha256)` pair to `/webhooks`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` [1](#0-0) .
5. `WebhookMetadata` is constructed with `shop: "victim-shop.myshopify.com"` (attacker-chosen) and the handler processes it as if it were a genuine event for the victim tenant [4](#0-3) .
