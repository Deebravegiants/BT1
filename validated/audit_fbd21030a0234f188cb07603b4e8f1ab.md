### Title
Webhook shop-domain identity used for tenant routing is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body, while the `X-Shopify-Shop-Domain` header — the value the gem hands to the app's handler as the authoritative tenant identifier — is taken verbatim from an unauthenticated header and never included in the HMAC-covered material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads the `hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

`Request#shop`, by contrast, is read directly from the `shop-domain` header with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (and `request.topic`) to build the metadata dispatched to the app's handler: [4](#0-3) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for a `Request` is only `@raw_body` — the `shop`, `topic`, `api_version`, and `webhook_id` header values are excluded from the signed string entirely: [5](#0-4) 

The identity binding this breaks: `hmac_verified(raw_body) == valid` is treated as proof of `shop_header == authenticated_tenant`, but the equality that actually holds is only `hmac_verified(raw_body) == valid`; `shop_header` is disjoint from the signed material.

Because the webhook secret (the app's `client_secret`) is the same for every shop installing the app (it is not a per-shop key), any tenant that can trigger a webhook delivery to their own store can capture a body + valid HMAC pair and resubmit it directly to the app's webhook endpoint with the `shop-domain` header rewritten to name a different (victim) shop. The signature still validates because it only covers the body, and `Registry.process` passes the attacker-chosen shop straight to the handler as `WebhookMetadata#shop`.

### Impact Explanation
This crosses a tenant boundary: a merchant-controlled webhook payload can be presented to the app as if it originated from an arbitrary other shop, causing the app's business logic (data writes, entitlement checks, notifications, etc.) keyed on `data.shop` to be executed against the wrong tenant. This matches the "cross-tenant access" Critical category, since the app has no way to distinguish a legitimately-routed webhook for shop A from a replayed one falsely labeled as shop B.

### Likelihood Explanation
Any developer/merchant account with a working installation of the app can register a webhook subscription for their own shop (or observe a naturally-triggered one), capture the raw body and the corresponding `X-Shopify-Hmac-Sha256` value, and POST it to the app's public webhook receiver endpoint with a forged `X-Shopify-Shop-Domain` header. No access to the app's `client_secret` or any other shop's credentials is required — only the ability to operate a shop that uses the app, which is the "unprivileged internet user" tier for this class of app.

### Recommendation
Include the shop domain (and topic/webhook id, where used for routing or idempotency) inside the HMAC-signed material, or otherwise cryptographically bind `Request#shop` to the verified signature before it is trusted, e.g. by validating that the shop belongs to a known/authorized installation (looked up via an already-authenticated offline session) rather than trusting the header value directly. At minimum, document that `request.shop` from `ShopifyAPI::Webhooks::Request` is unauthenticated and must be independently corroborated (e.g., against a stored session for that shop) before being used for tenant-scoped operations.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and registers/triggers a webhook (e.g. `orders/create`), receiving from Shopify a request with body `B`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`, and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends a POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks body `B` against `H`, which still matches: [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: request.shop, ...)` using the attacker-controlled `shop-domain` header value and dispatches it to the app's handler as if it came from `victim.myshopify.com`: [7](#0-6)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
