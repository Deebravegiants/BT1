### Title
Webhook tenant identity (`shop` header) is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, excluding the `shopify-shop-domain` / `x-shopify-shop-domain` header. `ShopifyAPI::Utils::HmacValidator.validate` therefore only proves that the *body* bytes were HMAC-signed by Shopify with `api_secret_key`; it says nothing about which shop the request actually belongs to. `ShopifyAPI::Webhooks::Registry.process` accepts this partial proof and passes the caller-supplied, unauthenticated `shop` value on to the host app's handler as trusted tenant identity.

### Finding Description
The intended invariant is: `HMAC-verified bytes == shop attribution used by the app`. In this gem that equality is broken:

- `Utils::HmacValidator.validate` computes/compares HMAC over `verifiable_query.to_signable_string` (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
- `Webhooks::Request#to_signable_string` returns `@raw_body` only (`lib/shopify_api/webhooks/request.rb:36-38`); `shop` comes from a separate, unsigned header (`lib/shopify_api/webhooks/request.rb:20-23`).
- `Registry.process` validates the HMAC and, once it passes, builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`) and hands it to the app's registered handler as the authoritative tenant for that payload.

Because `shop` is outside the signed byte range, any request bearing a *valid* `(body, hmac)` pair — which an attacker can obtain legitimately by operating their own (even free/dev) Shopify store and receiving a real webhook for it — can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never looks at the header, and `Registry.process` dispatches the (attacker-controlled shop, victim-body) pair straight to the handler.

### Impact Explanation
This crosses the tenant boundary that the HMAC is supposed to protect: a payload the app believes is scoped to shop A can be delivered while claiming to be shop B. Any host app logic that trusts `WebhookMetadata#shop` to select which merchant's data/session/state to mutate (the documented and expected use, e.g. order/customer/GDPR redact handlers) can be made to write, delete, or process data under the wrong tenant's identity — a cross-tenant access primitive, matching the Critical impact bucket ("cross-tenant access").

### Likelihood Explanation
An attacker only needs their own registered shop (no privileged credentials, no `api_secret_key`, no TLS interception) to legitimately receive a validly-signed webhook body/HMAC pair, then resend it to the target app's public webhook endpoint with a substituted `shop` header. No cryptographic secret is required to forge this because the field being trusted is simply not part of what's verified.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered signable string, or otherwise cryptographically bind the `shop` header to the signed payload before `Registry.process` forwards it to handlers. At minimum, `Webhooks::Request#to_signable_string` should not omit fields that downstream code treats as trusted identity.

### Proof of Concept
1. Attacker creates/owns Shopify dev store `attacker.myshopify.com`, installs the target app, and triggers a webhook (e.g. `orders/create`) — Shopify sends: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B`), `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, changing only `shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` (per `lib/shopify_api/webhooks/request.rb:36-38`) — passes, since `B` and `H` are unchanged.
4. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` to the app's handler (`lib/shopify_api/webhooks/registry.rb:198-199`), which processes/updates data attributing it to `victim-shop.myshopify.com` despite the payload originating from the attacker's own shop.
