### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then uses the `shop` value taken from an HTTP header — which is never included in the signed material — as the trusted tenant identifier passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all read straight from attacker-controllable HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the body HMAC and then forwards `request.shop` (and `request.topic`) directly to the registered handler as the authoritative tenant/topic identity: [3](#0-2) 

Because a single app has one `client_secret` (`Context.api_secret_key`) shared across every merchant that installs it, any merchant who installs the app can generate their own genuinely-signed webhook deliveries (Shopify computes the HMAC the same way with the same secret for all shops of that app). Such a user — who is an unprivileged internet user with respect to any *other* tenant — can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret: [4](#0-3) 

This breaks the identity binding: `shop authenticated (via body HMAC + shared client_secret) ≠ shop attributed to the processed data (via unauthenticated header, used as the tenant key passed to the handler)`. Any host application that persists or acts on `WebhookMetadata#shop` (session/store lookup, data writes, "app/uninstalled" or GDPR topics like `shop/redact`, `customers/redact`, `customers/data_request` which this gem treats as mandatory topics) will process data under the wrong tenant.

### Impact Explanation
This allows cross-tenant data injection/confusion: an attacker who legitimately installs the app on their own (possibly free/dev) store can forge webhook deliveries that the library will validate as authentic and attribute to any other shop of the attacker's choosing, since `shop` is not part of the signed payload. This matches the Critical "cross-tenant access" impact category, as the tenant boundary that `Registry.process` is supposed to enforce is not cryptographically anchored.

### Likelihood Explanation
Exploitation requires only installing the target app on an attacker-controlled Shopify store (a normal, unprivileged action any developer/merchant can take) to obtain valid `(body, hmac)` pairs, then sending a crafted HTTP request with an altered shop-domain header to the app's public webhook endpoint. No access token, `client_secret`, or privileged credentials are required — only knowledge of a victim's shop domain, which is routinely public (`*.myshopify.com`).

### Recommendation
Bind the tenant identity to the signed payload rather than trusting an unauthenticated header: either include `shop`/`topic` in the signable string used for HMAC validation, or require the host application to cross-check `request.shop` against an independently known/expected shop for that webhook subscription (e.g., validate that the shop is one that has a stored, active session/access token) before acting on the payload, and document this requirement prominently since the library currently exposes `WebhookMetadata#shop` as if it were an authenticated value.

### Proof of Concept
1. Attacker creates/uses their own store `attacker.myshopify.com` and installs the target Shopify app (obtaining genuine webhook deliveries signed with the app's shared `client_secret`).
2. Attacker captures a webhook delivery's raw JSON body `B` and its valid `X-Shopify-Hmac-Sha256` header value `H` (computed by Shopify over `B` using the shared secret).
3. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, so `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds), but with `X-Shopify-Shop-Domain: victim.myshopify.com` and any desired `X-Shopify-Topic`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) accepts the request as valid and invokes the app's handler with `shop: "victim.myshopify.com"`, causing the host app to process attacker-supplied data as if it originated from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
