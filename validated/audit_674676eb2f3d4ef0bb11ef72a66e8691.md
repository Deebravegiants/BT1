### Title
Silent, unrecoverable loss of a completed signup's Tier-1/Tier-2 personal custody package with no retry, refund, or rollback mechanism - ([File: src/agents/data_uploader.rs])

### Summary
The `data_uploader` agent that asynchronously uploads a user's Tier-1/Tier-2 personal custody package (containing encrypted iris/face key shares generated during signup) has no mechanism to recover, retry, or roll back a signup when that upload is dropped or permanently fails. `do_signup` fires-and-forgets the Tier-1/Tier-2 upload into a bounded queue and immediately proceeds to enroll the user regardless of the eventual outcome of that upload, mirroring the reported bug class: a state-changing operation is initiated, the caller (here, the signup pipeline) commits to a "successful" outcome, and if the downstream step later fails there is no compensating action to reconcile the mismatch.

### Finding Description
In `do_signup`, once the personal custody package (PCP) is built, Tier-0 is uploaded synchronously with retries and a hard failure path that aborts the signup: [1](#0-0) 

But Tier-1 and Tier-2 packages — which carry the encrypted key shares needed for the user's self-custody recovery — are merely pushed onto the `data_uploader` agent's queue with `.send(...)` and never awaited for success: [2](#0-1) 

Immediately after, regardless of whether that queued upload will ever complete, the code proceeds to call `enroll_user` and determine final `success`: [3](#0-2) 

Inside the `data_uploader` agent, the queue that holds these Tier-1/Tier-2 packages silently discards the oldest pending package once a configured `dropping_threshold` is reached, with no notification, retry, or reconciliation: [4](#0-3) [5](#0-4) 

Separately, even when a package is not dropped, `upload_pcp` gives up permanently on any HTTP client error, again with no mechanism for the pipeline or the user to be informed or for a retry/rollback to occur: [6](#0-5) 

The only backpressure mechanism, `wait_queues`/`WaitQueues`, blocks new *pushes* when queues are near capacity but does nothing to fix or roll back packages that are already lost or permanently failed: [7](#0-6) 

This is structurally the same root cause as the reported issue: an operation is split into a "commit" step (biometric enrollment, marked success) and an asynchronous, unreliable "settlement" step (Tier-1/Tier-2 custody package delivery) with no mechanism to detect the mismatch and refund/retry/rollback when the settlement step silently fails or is dropped.

### Impact Explanation
When the Tier-1/Tier-2 package is dropped (queue full) or permanently fails (client error) after the signup has already been reported as successful and enrollment recorded, the user ends up enrolled/de-duplicated in the system without the backend ever receiving the corresponding encrypted key-share package for that signup. Because there is no compensating rollback (e.g., un-enrolling, forcing re-upload, or flagging the signup for manual reconciliation) and no user-facing signal, this creates a cross-signup state bleed: the enrollment record and the biometric custody data become permanently inconsistent, with no path back for the affected user's data ever to be completed. This mirrors the "no refund mechanism" impact class — silent, un-recoverable loss of critical state after an operation is already treated as successful.

### Likelihood Explanation
This requires no malicious actor — it happens under ordinary conditions such as sustained backend unavailability, transient network errors returning HTTP 4xx, or high signup throughput causing the bounded in-memory queue (`pcp_tier1_dropping_threshold`/`pcp_tier2_dropping_threshold`) to fill and silently drop the oldest entries. Given `do_signup` never checks or waits on the outcome of the Tier-1/Tier-2 send before declaring the enrollment successful, the failure/drop path is reachable in normal unprivileged signup flows.

### Recommendation
Track the delivery status of Tier-1/Tier-2 packages per signup and do not treat a signup as fully successful until that upload is confirmed, or, if enrollment must proceed regardless, persist a durable record of pending/failed uploads with guaranteed retry (rather than silent `drop_oldest`) and an explicit reconciliation/rollback path (e.g., re-triggering enrollment removal or re-queuing indefinitely with durable persistent storage) when the upload ultimately cannot be delivered.

### Proof of Concept
1. Configure `pcp_tier1_dropping_threshold`/`pcp_tier2_dropping_threshold` to a small value, or simulate sustained backend downtime/4xx responses.
2. Run signups through `do_signup`; once Tier-0 succeeds, Tier-1/Tier-2 packages are queued via `orb.data_uploader.enabled().unwrap().send(...)` without awaiting outcome (`src/plans/mod.rs:613-636`).
3. Let the queue in `src/agents/data_uploader.rs` reach `dropping_thresholds[i]`; the next `Input::Pcp` push triggers `queues[i].drop_oldest().await` (`src/agents/data_uploader.rs:143-144`, `343-361`), silently discarding an older signup's Tier-1/Tier-2 package.
4. Observe that `enroll_user`/`success` in `do_signup` is unaffected by this loss (`src/plans/mod.rs:639-662`) — the signup is reported successful while its custody package is permanently missing, with no retry, refund, or rollback mechanism anywhere in the code path.

    async fn drop_oldest(&mut self) {
        match self {
            Self::Memory { queue } => {
                queue.pop_back();
            }
            Self::Persistent { path, queue, .. } => {
                let Some(id) = queue.pop_back() else { return };
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during drop_oldest, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {}
                }
            }
        }
    }

/// Waits for all queues to be not full.
pub async fn wait_queues(port: &mut port::Outer<Agent>) -> Result<()> {
    let (tx, rx) = oneshot::channel();
    port.send(port::Input::new(Input::WaitQueues(tx))).await?;
    Ok(rx.await?)
}
