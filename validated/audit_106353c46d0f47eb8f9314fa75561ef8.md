### Title
User-supplied route XDR executes arbitrary pool contract code inside the caller's authorization tree, enabling theft of the caller's wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The analog of CVE-2020-15167 — trusting attacker-supplied input that causes unintended code execution — is the `swap: Bytes` / `swap_xdr` parameter accepted by `multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral` and the router's `execute_strategy`. The route payload names the pool contract addresses to invoke, and neither the controller nor the router maintains a venue/pool allowlist. A malicious payload therefore places attacker-deployed contract code on the call stack while the caller's `require_auth` frame is still open, so any `token.transfer(victim, attacker, x)` issued by the rogue pool is recorded by the host as a child of the victim's authorization entry and executes if the victim signs the simulated auth tree — draining tokens unrelated to the swap.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` grants exactly one authorization — `authorize_transfer_as_current(env, token_in, controller, router, amount_in)` — then calls `router.execute_strategy(controller, amount_in, swap)` inside a flash guard that only prevents reentry into the controller; it does not restrict which contracts the route reaches. The router decodes `swap_xdr` into a `StrategyPayload` whose `assets` registry contains arbitrary pool addresses, and `dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs`) invokes `hop.pool` directly with no allowlist. The repo's own harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the mechanism: `RogueHopPool::swap` calls `token::Client::transfer(victim, attacker, amount)`; under recording mode the transfer joins the caller's auth tree, and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the signed tree moves Alice's entire `WALLET_BALANCE` of an unlisted token to the attacker. The threat model itself concedes the gap: "a route can put third-party code on the call stack below the caller's authorization… The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md`).

### Impact Explanation
Theft of user funds. An unprivileged attacker who gets a victim (or the quote path the victim trusts) to execute a route containing a rogue hop pool can transfer any SEP-41 tokens the victim holds, in amounts unbounded by the swap input, the payload `min_out`, or the controller's post-swap solvency checks — the theft is a host-level authorization child, invisible to `RouterOverspend`/`NoSwapOutput` balance-delta checks. The on-chain measured-settlement design (`dispatch_hop` input/output measurement, `SlippageExceeded`, `ExcessiveResidual`) bounds only the routed funds; it cannot bound auth-tree children.

### Likelihood Explanation
Reachable by any unprivileged address via `execute_strategy` directly or via `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` with a crafted `swap` argument. Exploitation requires the victim's wallet to sign the poisoned authorization tree that simulation returns — simulation faithfully lists the rogue `transfer` as a child entry, so a client that signs the simulated tree verbatim (the standard flow for `transaction.simulated` envelopes, per `payload.md`) is exploitable. The mitigation is entirely client-side and is not enforced anywhere on-chain, which keeps this a real contract-level analog rather than user error alone.

### Recommendation
Enforce a venue/pool allowlist on-chain: the router (or controller) should reject any `hop.pool` address not registered by the owner, so no route can put arbitrary contract code on the call stack under the sender's auth. As a weaker interim, the router could refuse hop pools that perform any `require_auth`-consuming calls other than the registered input pull, though Soroban offers no primitive to sandbox a callee's auth usage — so the allowlist is the robust fix. Short of that, SDK/wallet integrations must decode `swap_xdr` before signing and reject any authorization tree containing children beyond the single expected `token_in.transfer` (per the threat model's guidance).

### Proof of Concept
1. Attacker deploys a contract `RogueHopPool` whose `swap` function calls `token::Client::transfer(victim, attacker, victim_balance_of_any_token)` (as in `rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, `RogueHopPool::swap`, lines 62–72).
2. Attacker crafts a `swap_xdr`/`swap` payload whose `assets` registry includes the rogue pool address and whose instruction references it as the hop pool for a plausible route (e.g., USDC→ETH with a fair-looking `min_out`).
3. Victim calls `controller.swap_collateral(caller, account_id, USDC, amount, ETH, swap)` (or `execute_strategy` directly). The controller calls `authorize_transfer_as_current` for only the input pull (`swap.rs:34`), then `router.execute_strategy` → `dispatch_hop` invokes `hop.pool.swap` (`venues/mod.rs:34–40`) with no allowlist check.
4. Simulation records the rogue `transfer` as a child of the victim's auth entry; the victim's wallet signs the simulated tree; enforcement accepts it and the victim's unrelated wallet tokens move to the attacker while the swap itself settles normally and all controller balance-delta/risk checks pass — confirmed by the test at lines 229–269 where `wallet(alice)` goes from `77_770_000_000` to `0` and `wallet(attacker)` to the full balance.
