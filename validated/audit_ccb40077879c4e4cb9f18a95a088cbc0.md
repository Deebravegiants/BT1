Based on the investigation, the strongest reachable analog to the reported "unchecked token decimals/supply breaking arithmetic" bug class is in `VWAPOracle.sol`'s decimal normalization, which is driven by an **untrusted, externally-controlled** `decimals()` read on the intent's own output token.

### Title
Untrusted `decimals()` on an order's output token can overflow/revert `VWAPOracle._normalizeAmount`, blocking price recording during intent fills - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle.recordSpread` is restricted to be called only by the configured `_intentGateway`, i.e., it runs synchronously inside the intent fill flow. [1](#0-0) 
For each token leg it computes `outputDecimals` by calling `IERC20Metadata(outputToken).decimals()` directly on the local-chain token contract rather than from a curated/registry table (unlike `inputDecimals`, which is read from the governed `_tokenDecimals` storage populated only via cross-chain `UpdateTokenDecimals` requests from Hyperbridge). [2](#0-1) 

### Finding Description
`_normalizeAmount` scales an amount to 18 decimals using the token's reported `decimals` value: [3](#0-2) 
When `_decimals > 18`, it computes `amount / (10 ** (_decimals - 18))`. Because `outputDecimals` for a non-native output token is read live from an arbitrary ERC-20 contract (`IERC20Metadata(outputToken).decimals()`), any user placing an order whose output token is a contract they control can make `decimals()` return an arbitrary `uint8` value (up to 255). A value like `_decimals = 255` makes the exponent `237`, and `10 ** 237` overflows `uint256` (max ~1.15e77, i.e., only up to `10**77` fits). Solidity ≥0.8 reverts on this overflow rather than wrapping silently, which is the direct analog of the reported issue: unchecked assumptions about a token's decimals cause the arithmetic to break/overflow because no plausibility bound is enforced on the value before it drives an exponentiation.

This mirrors the report's root cause precisely — "the pool does not check for token decimal precision/supply before doing math with it" — except here the unchecked input is a token's self-reported `decimals()` fed into an exponent rather than a debt/collateral ratio mantissa.

### Impact Explanation
If `recordSpread` is invoked unconditionally as part of the fill path (it is `restrict`ed to be callable only by the intent gateway, indicating it is called synchronously from `fillOrder`/settlement) and the call is not wrapped in a try/catch, a revert inside `_normalizeAmount` propagates and reverts the entire fill transaction. An order whose output token is a malicious/misconfigured contract with an out-of-range `decimals()` would then be permanently unfillable through this code path — freezing whatever funds are already escrowed for that order (a concrete funds-freezing outcome, matching the audit's required impact bar), and in the worst case denying the price/liquidity oracle service for that market entirely.

### Likelihood Explanation
Likelihood is limited to orders that use a deliberately malicious or buggy output token, but no privileged action is needed to reach it — any unprivileged order originator/attacker can deploy a token contract that returns an extreme `decimals()` value and use it as an order's output token. I was unable to conclusively verify from the available files whether the caller of `recordSpread` (in `IntentGatewayV2.sol`/`IntentsBase.sol`) wraps the call in a try/catch, which materially affects severity — if it is defensively wrapped, this degrades to a lost price-sample (Low), not a fill-blocking DoS. This should be verified directly in the fill-settlement code before treating this as confirmed Medium+ severity.

### Recommendation
- Clamp/validate `decimals()` reads from arbitrary output tokens to a sane range (e.g., `<= 18` or a small upper bound like 36) before using them as an exponent, reverting cleanly or skipping normalization instead of allowing an unbounded `10 ** (_decimals - 18)`.
- Wrap the `recordSpread` call (or at minimum `_normalizeAmount`) in a try/catch at the call site so a malformed/malicious token cannot block order fills or escrow release.
- Apply the same bound to `TokenDecimalsUpdate.decimals` validated for the source-chain path (`_processTokenDecimalsUpdates` only rejects `0`, not implausibly large values), for symmetry. [4](#0-3) 

### Proof of Concept
1. Attacker deploys `EvilToken` implementing `IERC20Metadata` where `decimals()` returns `250`.
2. Attacker (or any user) creates/places an intent order whose output asset is `EvilToken`.
3. A solver fills the order; the fill path calls `IIntentPriceOracle.recordSpread(commitment, sourceChain, inputs, outputs)` where `outputs[i].token == EvilToken`.
4. Inside `recordSpread`, `outputDecimals = IERC20Metadata(EvilToken).decimals()` returns `250`; `_normalizeAmount` computes `outputAmountNormalized = amount / (10 ** (250 - 18))`, i.e., `10 ** 232`, which overflows `uint256` and reverts.
5. If the enclosing fill transaction does not catch this revert, the entire `fillOrder` call reverts, and the order cannot be settled through this path.

Note: I could not confirm within the available index whether the gateway's fill call site wraps `recordSpread` in a try/catch — this should be checked directly in `evm/src/apps/IntentGatewayV2.sol` / `evm/src/apps/intentsv2/IntentsBase.sol` before treating the DoS/freezing impact as confirmed, since the index only surfaced 2 `priceOracle` references there without full context of the call site.

    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }

    function _processTokenDecimalsUpdates(TokenDecimalsUpdate[] memory updates) internal {
        uint256 updatesLen = updates.length;
        for (uint256 j = 0; j < updatesLen; j++) {
            bytes32 chainHash = keccak256(updates[j].sourceChain);
            uint256 tokensLen = updates[j].tokens.length;
            for (uint256 i = 0; i < tokensLen; i++) {
                if (updates[j].tokens[i].decimals == 0) revert InvalidInput();

                _tokenDecimals[chainHash][updates[j].tokens[i].token] = updates[j].tokens[i].decimals;
                emit TokenDecimalsUpdated(
                    updates[j].sourceChain, updates[j].tokens[i].token, updates[j].tokens[i].decimals
                );
            }
        }
    }
