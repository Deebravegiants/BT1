### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC covers only the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to app webhook handlers directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` verifies is computed only over the raw request body, never over that header. This breaks the equality "shop authenticated == shop bound by the HMAC," analogous to H-30's `utilization` not reflecting the value it is derived from.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the HMAC-covered content [2](#0-1) . `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, if it passes, immediately builds a `WebhookMetadata` using `request.shop` verbatim and dispatches it to the app's handler [3](#0-2) . `HmacValidator.validate_signature` recomputes the digest from `verifiable_query.to_signable_string` (the body) and compares it to the supplied `hmac` value [4](#0-3) ; the `shop` header never enters that computation. `WebhookMetadata.shop` is a plain, unauthenticated `String` field passed on to the handler [5](#0-4) .

Consequently, for any request body/HMAC pair that is valid for the app's secret (e.g., a previously captured legitimate webhook, or any body the attacker can get validly signed for a topic they control, such as one from their own shop), an attacker can freely substitute the `X-Shopify-Shop-Domain` header value. `Registry.process` will still report `hmac_valid = true` and forward the attacker-chosen `shop` value to the handler as if it were authenticated tenant identity.

### Impact Explanation
Apps built on this gem use `WebhookMetadata#shop` as the trusted per-tenant identifier to route webhook side effects (e.g., look up the merchant's session/access token, write to the merchant's records, trigger merchant-scoped billing or data operations) because the gem asserts the request passed HMAC validation. Since `shop` is not bound by that validation, an attacker who can obtain any validly-signed webhook body for the same app (their own shop's webhook, or a replayed one) can relabel it under a victim shop's domain, producing cross-tenant data confusion in the handler layer. This matches the "cross-tenant access" Critical-impact category, since the boundary broken is exactly "the shop authenticated ≠ the shop bound by the HMAC."

### Likelihood Explanation
Requires only the capability an ordinary internet-connected app already exposes: an endpoint receiving Shopify webhook POSTs. An attacker who operates their own Shopify development store can generate arbitrary bodies validly HMAC-signed by the same app secret (since every merchant with the app installed can trigger webhooks for their own shop), then replay that same body/HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a different (victim) shop. No access token, `client_secret`, or privileged account is needed—only normal use of the app as an installed merchant, which satisfies the "unprivileged internet user" analog.

### Recommendation
Bind `shop` to the HMAC-verified payload rather than trusting the header in isolation:
- Include the `shop`/`webhook_id`/`topic` header values in the signable string used by `HmacValidator`, or
- Have `Registry.process` independently confirm that `request.shop` matches a shop the app currently has an active/expected session/installation for before invoking the handler, and reject mismatches.

### Proof of Concept
1. App has webhook endpoint using `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers/captures a legitimate webhook: body `B` with header `X-Shopify-Hmac-Sha256: H` (valid for app's `api_secret_key`).
3. Attacker replays `POST /webhooks` with the same body `B` and `Hmac: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5)  — succeeds because only body `B` and secret are checked.
5. Handler receives `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, believing it is an authenticated event for `victim.myshopify.com` even though it was never signed as such.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
