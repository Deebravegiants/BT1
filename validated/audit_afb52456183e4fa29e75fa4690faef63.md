Found a solid analog in the Tron variant of `IntentGatewayV2`, where escrowed-token payouts use unchecked low-level `.call` instead of `SafeERC20`, matching the reported bug class ("assumes success without checking the actual outcome of a token movement, then commits state as if it succeeded").

### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw`/`SweepDust` permanently freezes escrowed funds on failed transfers - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron `IntentGatewayV2` contract imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`) everywhere else in the contract, but its escrow-payout paths — `withdraw()` and the `SweepDust` branch of `onAccept` — bypass it and instead make a raw low-level `.call` to the token's `transfer` selector, checking only that the call itself did not revert, not the ERC20 boolean return value. [1](#0-0) [2](#0-1) 

### Finding Description
In `withdraw(WithdrawalRequest memory body, bool isRefund)`, for every escrowed ERC20 token:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

This only checks that the external call did not revert; it never decodes/validates the returned `bool`. Many ERC20/TRC20 tokens — including several deployed on Tron, which is exactly the chain this contract variant targets — signal failure (insufficient balance, paused, blacklisted recipient, etc.) by returning `false` rather than reverting. In that case `success` is `true` even though no tokens actually moved.

Immediately after this unchecked "transfer", the contract commits the withdrawal as final:
```solidity
_filled[body.commitment] = beneficiary;
...
_orders[body.commitment][token] -= amount;
...
emit EscrowRefunded(...) / emit EscrowReleased(...)
``` [4](#0-3) 

Once `_orders[commitment][token]` is decremented and `_filled[commitment]` is set, there is no other path in the contract to re-attempt payout for that beneficiary — the escrow accounting for that commitment/token is gone even though the tokens never left the contract. The same unchecked pattern is used for both native-fee payouts (`IERC20(feeToken)`), and for the `SweepDust` handler triggered from `onAccept`, which sweeps solver dust to an arbitrary `req.beneficiary` using the identical unchecked low-level call.

This directly parallels the referenced Sherlock report's root cause ("not checking the valid amount/result of a transfer is not safe, but the contract still thinks the transfer happened and proceeds"), just moved from a lending-pool `withdraw()` call to an escrow-releasing ERC20 `transfer()` call.

### Impact Explanation
Any beneficiary of an order fill, refund, or fee payout whose escrowed token silently returns `false` on transfer failure will have their entitlement zeroed out of `_orders` and the commitment marked `_filled`, while the tokens remain stuck in the `IntentGatewayV2` contract with no way to claim them — a permanent freezing/loss of user or solver funds. This is triggerable by a relayer delivering a legitimate fill/refund/timeout message for an order involving such a token; no privileged role or malicious actor collusion is required beyond normal message delivery, which is within the reachable-message-dispatch class this scan is scoped to.

### Likelihood Explanation
Likelihood is proportional to how often a false-returning (non-reverting) ERC20/TRC20 token is used as an order input/output on Tron, which is plausible given this contract file specifically exists to support Tron's TRC20 ecosystem, where such non-conforming tokens are common. No attacker action beyond normal order placement/fill with such a token is needed to trigger permanent fund loss for that order's beneficiary.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handling with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the same contract (`using SafeERC20 for IERC20;`). `safeTransfer` reverts on both a failed call and a `false`/malformed return value, ensuring `_orders` is only decremented and `_filled` only set when the token transfer actually succeeded.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token whose `transfer` implementation returns `false` on failure instead of reverting (e.g., because the recipient is blacklisted or the contract's internal balance bookkeeping fails) — a broadly known non-standard ERC20 behavior class, common among TRC20 tokens.
2. A user places an order with this token as input; it gets escrowed in `_orders[commitment][token]`.
3. Trigger a refund/fill delivery that calls `withdraw(body, isRefund)` for a beneficiary condition under which the token's `transfer` call returns `false` (e.g., beneficiary blacklisted by the token, or token temporarily paused).
4. The low-level `.call` succeeds (`success == true`) since the call itself doesn't revert; `if (!success) revert TransferFailed();` does not fire.
5. `_orders[body.commitment][token] -= amount;` executes, zeroing the escrow record, and `_filled[body.commitment] = beneficiary;` is set, with `EscrowReleased`/`EscrowRefunded` emitted — even though the beneficiary's on-chain token balance never increased.
6. The beneficiary's tokens are now permanently stuck in the `IntentGatewayV2` contract with no remaining code path to claim them for that commitment.
