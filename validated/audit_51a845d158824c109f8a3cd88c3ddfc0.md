### Title
Webhook Shop-Domain Spoofing via HMAC That Only Covers the Raw Body, Not the `shop-domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop identity (`shop-domain` header) that the rest of the library and any host-app webhook handler treats as the trusted tenant identifier is never included in the signed material. This breaks the intended binding `HMAC-verified-bytes == identity-bytes-acted-on`, mirroring the `BatchDeposit2.sol` flaw where the length check validated one thing (`argv.length / 0xd0`) while a different, unvalidated quantity (the true byte content) was actually used downstream.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop` is read straight from an unauthenticated header, independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only ever calls `verifiable_query.to_signable_string` (the raw body) and `verifiable_query.hmac` to compute/compare the signature — it never touches `shop`: [3](#0-2) 

`Registry.process` gates entirely on this HMAC check, and then forwards `request.shop` — the unauthenticated header value — as the tenant identity to the handler: [4](#0-3) 

So the equality the library implicitly promises is:
`shop_used_by_handler (request.shop) == shop_that_the_HMAC_actually_authenticates`

But in reality:
`HMAC authenticates {raw_body}` while `handler receives {shop-domain header, raw_body}`, and the header is not part of the signed set. Any two values of `shop-domain` are equally "valid" for the same signed body, so the check answers permissively — it validates that *the body* was not tampered with, but silently accepts an unauthenticated header value as if it had been verified.

### Impact Explanation
This crosses a tenant boundary: a party able to submit a request to the app's webhook endpoint with a *genuine* `(body, hmac)` pair (e.g., captured from their own shop's legitimate webhook traffic, or via a body they can influence, such as a comment/description field on their own store that Shopify includes verbatim in a webhook payload) can freely swap the `shop-domain` header to name a victim shop. `Registry.process` will accept the HMAC (it only checks the body) and hand the handler `WebhookMetadata` claiming to be from the victim shop, with attacker-influenced body content. Any host application that keys behavior (session/store lookup, data writes, uninstall/GDPR handling, etc.) off `request.shop` — which is the documented, intended use of this attribute — is therefore exposed to cross-tenant data injection/impersonation purely through this gem's verification logic, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Reachable by any unprivileged internet user who can (a) send an HTTP request to the app's public webhook endpoint and (b) obtain at least one legitimately-signed `(body, hmac)` pair for their own tenant/shop (trivial for anyone who has installed the app once and can trigger any webhook topic on their own store, or otherwise cause Shopify to emit a webhook containing attacker-influenced text). No access token, `api_secret_key`, or privileged account is required — only the ability to send network requests to the endpoint and to be an unprivileged merchant/user of the app.

### Recommendation
Bind the identity fields used downstream into the signed material, or otherwise cryptographically tie `shop-domain` to the HMAC, e.g. include `shop-domain`, `topic`, and `webhook-id` (concatenated with the body, or via a header-scoped signature) inside `to_signable_string`, so that `HmacValidator.validate` cannot pass unless the shop header matches the value Shopify actually signed for. At minimum, document and enforce that `request.shop` must never be trusted for authorization decisions without an additional out-of-band check (e.g. cross-referencing against a known/installed shop list) since the HMAC in this gem does not cover it.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook topic (e.g. `products/update`) so Shopify sends a legitimately HMAC-signed body to the app's public webhook URL. Attacker can control content of that body via fields they set on their own store (e.g. a product title containing arbitrary text) so the raw body bytes are attacker-influenced.
2. Attacker replays that exact `(raw_body, hmac)` pair to the same endpoint but sets header `x-shopify-shop-domain: victim-shop.myshopify.com` instead of their own shop.
3. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present) and `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `@raw_body`, which is unchanged and still valid: [5](#0-4) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the host application to act on attacker-controlled data under the victim's tenant identity — despite the HMAC never having authenticated that shop value.
