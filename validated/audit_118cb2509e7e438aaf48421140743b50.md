### Title
Webhook `shop` (tenant) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (tenant identifier) is read separately from the unauthenticated `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` only proves that the *body* bytes match the HMAC, never that the `shop` header is bound to that HMAC. `Registry.process` then trusts `request.shop` verbatim to build `WebhookMetadata` and dispatches it to the app's `WebhookHandler`, which typically uses `data.shop` to select/scope tenant data (e.g., look up the merchant's session, database record, etc.).

### Finding Description
The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on`

In `lib/shopify_api/webhooks/request.rb`:
- `hmac` is derived from the `hmac-sha256` header.
- `to_signable_string` returns `@raw_body` only — it never includes `shop`, `topic`, or `webhook_id`.
- `shop` is read directly from the `shop-domain` header with no cryptographic tie to the HMAC.

`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC — i.e., it validates the body only.

`Registry.process` (`lib/shopify_api/webhooks/registry.rb`) does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
Because `shop` is outside the signed material, any request carrying a *previously valid* `(body, hmac)` pair (from any topic/shop this app receives webhooks for) will pass validation regardless of what `shop-domain` header value is attached to it. An attacker who can capture one legitimate webhook delivery for their own shop (e.g., by installing the app and inspecting/logging their own webhook traffic, which is not a privileged action) can replay that exact `body` + `hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. The signature check still passes because it never examined the header, and the handler receives `WebhookMetadata` claiming a different, attacker-chosen tenant.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: an unprivileged app installer (any merchant who installs the app, no special access) can forge webhook events "from" another shop that never sent them, because the `shop` field is unauthenticated relative to the HMAC. Applications built on this API (which typically key data by `data.shop` from `WebhookMetadata`) can be tricked into writing/reading data under another tenant's identity — cross-tenant access, matching the report's bug class of "a field acted on but not covered by the HMAC."

### Likelihood Explanation
Moderate: it requires the attacker to already be an authorized installer of the target app on their own store (to legitimately receive at least one webhook with a body they can replay, e.g., a mandatory `shop/redact` or any subscribed topic with attacker-influenceable/predictable body content), and to be able to POST directly to the app's public webhook endpoint with custom headers — both are realistic for any external, unprivileged user of a public Shopify app.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) as part of the signed/verified material for webhook requests, or otherwise cryptographically bind the header-derived `shop` to the verified body before constructing `WebhookMetadata`. At minimum, `Utils::HmacValidator.validate` should be passed a signable string that incorporates the `shop-domain` header so that swapping the header invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and captures a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(client_secret, B) == H` — true, since `B` and `H` are unchanged.
4. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` is built and passed to `handler.handle`, causing the app to process an event as if it originated from `victim-shop.myshopify.com`, even though it never sent it.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
