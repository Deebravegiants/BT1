### Title
Webhook shop/topic identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` proves nothing more than "this body was generated with the app's secret." The `shop-domain` and `topic` HTTP headers — which `ShopifyAPI::Webhooks::Registry.process` uses to route the payload to a specific handler and stamp the resulting `WebhookMetadata` as belonging to a given shop — are never included in the signed material. Because a single app's `api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app can obtain a genuine, validly-signed `(body, hmac)` pair for content of their choosing, then replay that pair to the app's webhook endpoint while substituting the `shop-domain`/`topic` headers of a different (victim) tenant.

### Finding Description
`process(request)` only checks the HMAC over the body: [1](#0-0) 

The signature check itself delegates to `HmacValidator.validate`, which in turn calls `to_signable_string`: [2](#0-1) 

And `Request#to_signable_string` is defined as just the raw body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated headers: [3](#0-2) 

The identity binding that should hold is:
`shop attested by HMAC == shop used to route/identify the webhook in WebhookMetadata`

In this implementation, the left side is empty (the HMAC covers no shop/topic claim at all), so the equality trivially fails to be enforced — the "verified" side (body signature) and the "acted-upon" side (`shop`, `topic` headers passed into `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`) are decoupled.

### Impact Explanation
This breaks the multi-tenant boundary the library is supposed to preserve for webhook processing. Any merchant who has installed the app (an "unprivileged" party with respect to any other tenant's data) can:
1. Trigger a webhook delivery for their own shop by editing some field that becomes part of the JSON body (e.g., an order note, product title, metafield value) to attacker-chosen content, and capture the resulting valid `(body, hmac)` pair Shopify sends to the app's public webhook endpoint.
2. POST that exact body and HMAC directly to the app's webhook endpoint again, but with the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers changed to point at a victim shop / different topic.
3. `Registry.process` accepts the request because `HmacValidator.validate` only checks the body, and calls the registered handler with `shop: <victim shop>`.

Any host application relying on this gem's webhook handling to determine "which tenant does this update belong to" purely from `WebhookMetadata#shop`/`#topic` (as the gem's own docs/examples instruct) can be tricked into writing attacker-controlled data into another tenant's records, deleting/re-provisioning another tenant's resources on `app/uninstalled`, or triggering `customers/redact`-style flows against a victim shop. This is a cross-tenant access vulnerability.

### Likelihood Explanation
Any merchant who installs the app satisfies the "unprivileged internet user" bar relative to other tenants, and installing an app is a normal, low-privilege action requiring no special credentials, TLS interception, or access to `api_secret_key`. Capturing your own webhook's `(body, hmac)` pair requires no more than watching your own store's outgoing webhook traffic (e.g., via a request bin or your own server logs), and replaying an HTTP POST with modified headers is trivial. No knowledge of the app's `client_secret` is required — only reuse of a signature the attacker legitimately received for their own tenant.

### Recommendation
- **Short term:** Include the `shop-domain` and `topic` (and ideally `webhook_id`) header values in the HMAC signable string (or otherwise cryptographically bind them to the body) inside `ShopifyAPI::Webhooks::Request#to_signable_string`, so `HmacValidator.validate` fails if any of these are altered relative to what Shopify actually sent.
- **Long term:** Document/emphasize that webhook shop/topic identity must never be trusted independent of signature coverage, and consider exposing a single verified struct from the gem (body + shop + topic bound together) rather than separate accessors that can be mixed from different sources.

### Proof of Concept
1. App has one merchant `attacker-shop.myshopify.com` and one victim `victim-shop.myshopify.com`, both installed on the same app (shared `api_secret_key`).
2. Attacker performs some action on their own store that causes Shopify to send a webhook with body `B` and a valid signature `H = HMAC-SHA256(api_secret_key, B)` to the app's public webhook URL, with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker captures `(B, H)` (e.g., from their own network traffic) and replays:
```
POST /webhooks HTTP/1.1
X-Shopify-Hmac-SHA256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Topic: orders/create
Body: B
```
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` using `request.to_signable_string == B`, which matches `H`, so validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-chosen content under the victim shop's identity. [1](#0-0) [4](#0-3)
