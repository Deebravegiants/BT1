Yes — there's a direct analog to this bug class in `Bonding.transferCreator`, which rotates the "credit owner" role without moving the already-accrued balance sitting under the old address, exactly mirroring how `Operation.setInsurance` swaps the insurance address without moving its credit.

### Title
`Bonding.transferCreator` rotates fee attribution without moving the creator's already-accrued `FeeVault` balance, permanently stranding it if the old address is compromised or lost - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.transferCreator` lets the current creator of a launched token reassign the `creator` role to a new address for *future* fee attribution, but it never touches the creator's pooled, already-earned USDC balance held in `FeeVault.creatorBalance[oldCreator]`. That balance can only be withdrawn by the exact address that earned it, via `FeeVault.claim()`'s `msg.sender` check.

### Finding Description
`transferCreator` only rewrites `info.creator` in `Bonding`'s `TokenInfo` struct; it performs no interaction with `FeeVault` at all: [1](#0-0) 

Meanwhile, `FeeVault.accrue` credits fees to whichever `creator` address `Zap` reports (sourced from `Bonding.tokenInfo(token).creator` at the time of the trade), and stores it in a per-address mapping: [2](#0-1) 

Claiming is strictly `msg.sender`-gated against that same mapping key, with no admin override, no migration path, and no way for a *different* address to redeem another address's `creatorBalance`: [3](#0-2) 

Once `transferCreator` is called, all fees accrued *before* the call remain keyed to the old creator address in `FeeVault.creatorBalance`, and only that old address can ever call `claim()` to retrieve them — `transferCreator` gives the new address zero access to the old balance. The project's own docs confirm the split is deliberate but incomplete: "transfers role and future fee attribution" — leaving past attribution behind. [4](#0-3) 

The scenario mirrors the reported bug precisely: `Operation.setInsurance` rotates an address without moving the credit tied to it, so if the rotation is done specifically *because* the old address is compromised/lost, the credit becomes permanently unreachable. Here, a creator whose private key is compromised or lost has no recourse but to call `transferCreator` to protect *future* earnings — but any USDC already sitting in `FeeVault.creatorBalance[oldCreator]` is permanently frozen, since the only path to it (`claim()`) requires `msg.sender == oldCreator`, and that address is exactly the one being abandoned.

### Impact Explanation
This causes permanent freezing of creator funds inside `FeeVault`. Any USDC fees accrued to a creator address before that address becomes compromised, lost, or otherwise abandoned are locked forever with no owner-level recovery mechanism (`FeeVault` has no sweep/rescue path for `creatorBalance`, only for unbacked donation surplus via `sweepDonations`, which explicitly excludes backed balances).

### Likelihood Explanation
Medium likelihood: this triggers any time a creator legitimately needs to rotate away from a compromised or lost key while they still have an unclaimed balance — a realistic and expected operational scenario for any long-lived token that has already earned trading fees, not an exotic edge case.

### Recommendation
Have `Bonding.transferCreator` (or a paired call) also migrate the outstanding `FeeVault.creatorBalance[oldCreator]` to `newCreator` — e.g., an owner-or-creator-callable `FeeVault.migrateCreatorBalance(oldCreator, newCreator)` invoked atomically from `transferCreator`, so credit follows the role exactly as the recommendation in the source report requires ("`setInsurance` should also move the credit").

### Proof of Concept
1. Token is launched via `Zap.createToken`; `creator` address accrues fees over several buys/sells, building up `FeeVault.creatorBalance[creator] = X` (per `FeeVault.accrue`, `Bonding.sol:738-748` attribution path).
2. `creator`'s private key is compromised (or simply lost). They must use it one last time to call `Bonding.transferCreator(tokenAddress, newSafeAddress)` to protect future fee attribution.
3. `info.creator` is now `newSafeAddress`; all *future* fees route correctly.
4. `FeeVault.creatorBalance[creator]` still equals `X`; `FeeVault.claim()` can only be called successfully with `msg.sender == creator` — the now-compromised/inaccessible address.
5. `X` is permanently unclaimable by the legitimate project/creator going forward (or is stealable by whoever holds the compromised key, i.e., an attacker), since no function in `FeeVault` or `Bonding` allows `newSafeAddress` to redeem it.

        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
