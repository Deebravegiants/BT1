### Title
Permanent freeze of graduation funds via unhandled `Math.mulDiv` overflow in `Bonding._noFeeSwapInput` when a hostile-preseeded HyperSwap V2 pair is rebalanced against extreme curve targets - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`finalizeGraduation` is the sole, permissionless path that releases the LT raised on the curve and mints the `LP_RESERVE` (up to 250M) tokens parked in `Bonding` during `Lifecycle.Graduating` [1](#0-0) . When the HyperSwap V2 pair has been pre-seeded (mint pre-seed), it calls `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, which computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` on values derived from attacker-influenceable pool reserves and curve-derived `(tokensForLP, ltFromPair)` targets [2](#0-1) . The contract's own natspec acknowledges that "constructed adversarial inputs" to this function "would revert rather than silently truncate" [3](#0-2) . Unlike the kubo bug where a panic from decoding an attacker's bytes killed the whole daemon, here the equivalent "uncaught exceptional condition" bricks the one shared recovery path (`finalizeGraduation`) for that token: because the pre-seeded pair reserves are persistent on-chain state that the attacker does not need to keep re-supplying, every subsequent call reverts the same way, and there is no reset/rescue function that returns a token from `Lifecycle.Graduating` back to `Curve` or otherwise frees the escrowed LT/tokens.

### Finding Description
`_seedRebalancing` reads the live HyperSwap V2 pair reserves and compares them against the cached `(tokensForLP, ltFromPair)` graduation targets [4](#0-3) . Outside the tiny-preseed band it calls `_pairRebalance`, which calls `_noFeeSwapInput(reserveIn, reserveOut, targetN, targetD, maxSwap)` [5](#0-4) . That helper computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` and takes `sqrt` of the result [6](#0-5) . `Math.mulDiv` reverts if the final quotient does not fit in 256 bits.

- `targetD` is `ltFromPair` (or `tokensForLP`), a curve-state value that shrinks as the LT's `exchangeRate()` (chosen by the token creator via `ltAddress` at `launch`) grows — a launch is only rejected for `exchangeRate` too *low* (`ExchangeRateTooLow`), never too high [7](#0-6) . A curve that graduates against a very-high-`exchangeRate()` LT can close with `ltFromPair` (real LT raised, in wei) many orders of magnitude smaller than `tokensForLP` (up to `LP_RESERVE = 250_000_000e18`) [8](#0-7) .
- `reserveIn`/`reserveOut` are the live V2 pair reserves, which any unprivileged address can push up (within `uint112` bounds) by pre-creating the pair and minting/transferring real TOKEN and LT into it before `finalizeGraduation` runs — exactly the "mint pre-seed" (Regime 3) scenario the natspec on `_seedUniswapV2Direct` is designed to defend against [9](#0-8) .

With a sufficiently skewed `targetN/targetD` ratio (driven by the chosen LT's exchange rate) combined with a preseed sized to make `reserveIn * reserveOut` large, `Math.mulDiv`'s final division overflows `uint256` and reverts. Because this happens inside `finalizeGraduation`'s only non-empty-pair code path, and the pre-seed persists on-chain indefinitely, **every** future call to `finalizeGraduation(tokenAddress)` reverts identically. The token is stuck forever in `Lifecycle.Graduating`: the LT already pulled off the curve via `Router.graduate` in phase 1 [10](#0-9)  and the `tokensForLP`/burn-adjusted token allocation sit unrecoverable in `Bonding`, and traders can never sell or buy the token again (`Lifecycle.Graduating` blocks `buy`/`sell`) [11](#0-10) . `Bonding` exposes no admin path to reset a stuck lifecycle or rescue the escrowed LT/tokens for a token that never reaches `Graduated`.

### Impact Explanation
This is a permanent freeze of trader/creator funds: all real LT raised by the curve (up to the graduation threshold or the full curve sell-out) and the LP-bound token allocation become permanently unrecoverable, and the token can never complete graduation, list on the DEX, or resume curve trading. This satisfies the "permanent freezing of trader, creator or LP funds" bar. The griefing cost to the attacker is bounded to the tokens/LT they must acquire to build the pre-seed (which they can partially recover as reserves in the pre-existing, now permanently-open V2 pair they control), making it economically motivated for a competitor or short-seller wanting to permanently kill a specific launch.

### Likelihood Explanation
Reaching the overflow requires two attacker-influenceable but non-trivial conditions to align: (1) a token launched against an LT whose live `exchangeRate()` is high enough to make `ltFromPair` tiny relative to `tokensForLP`, and (2) a V2 pre-seed large enough, within `uint112` reserve limits and the token's real total supply, to push `reserveIn * reserveOut * targetN / targetD` past `type(uint256).max`. Both dimensions are bounded by real economic cost and by the `uint112` pair-reserve ceiling, which the code's own natspec relies on to argue this case is not practically reachable. Given those bounds, triggering the exact overflow with realistic capital is plausible but not trivially cheap, and no worked numeric PoC within `uint112`/total-supply constraints was fully derived here — flagging this as a real but conditionally-likelihood-limited path rather than a proven, minimal-cost exploit.

### Recommendation
Replace the unchecked-revert `Math.mulDiv` call in `_noFeeSwapInput` with a saturating/clamped computation (or an explicit pre-check that clamps `reserveIn`/`reserveOut`/`targetN`/`targetD` combinations before the final division), and add a fallback identical to the "swap rounds to zero" path (`_pairRebalance` returning `false` → `_seedDirectMint`) for the overflow case, so that any adversarial reserve/target combination degrades to the safe direct-mint regime instead of causing `finalizeGraduation` to revert unrecoverably. Additionally, consider adding an owner-gated (or time-delayed) rescue/reset path for a token irrecoverably stuck in `Lifecycle.Graduating` so a future edge case in the seeding math cannot permanently strand curve-raised LT and LP tokens.

### Proof of Concept
1. Attacker (as creator) launches a token via `Zap.createToken` pairing against a BounceTech LT whose `exchangeRate()` is very high, so `_deployAndSeed` computes a very small `virtualLtReserve` (still passing the `ExchangeRateTooLow`/`type(uint112).max/4` checks) [7](#0-6) .
2. Attacker (or colluding trader) trades the curve to a graduation trigger (`canGraduate` via USD or sellout) so that `_prepareGraduationLiquidity` caches a `tokensForLP` near `LP_RESERVE` and a very small `ltFromPair` [8](#0-7) , entering `Lifecycle.Graduating`.
3. Before anyone calls `finalizeGraduation`, attacker calls the HyperSwap V2 factory to `createPair(token, lt)` and mints a large, imbalanced amount of TOKEN/LT liquidity into it directly (pre-creating/pre-seeding the pair before graduation, an explicitly in-scope reachable action).
4. Any address calls `Bonding.finalizeGraduation(tokenAddress)`. `_ensureUniswapV2Pair` returns the existing pre-seeded pair [12](#0-11) ; `_seedUniswapV2Direct` routes to `_seedRebalancing` (non-zero `totalSupply`) [13](#0-12) ; `_pairRebalance` calls `_noFeeSwapInput` with the skewed `reserveIn/reserveOut` and tiny `targetD`, and `Math.mulDiv` reverts on the final division.
5. `finalizeGraduation` reverts every time it is retried, since the pair reserves and cached `PendingGraduation` values are unchanged; the token is permanently stuck in `Lifecycle.Graduating` with its LT and LP-bound tokens unrecoverable.

        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    /// @dev Smallest swap input that drives the pool's reserve ratio
    ///      `(reserveIn + s) / (reserveOut - out)` to `targetN/targetD`
    ///      under the no-fee constant-product model:
    ///        `(reserveIn + s)² = reserveIn * reserveOut * targetN/targetD`
    ///      ⇒ `s = sqrt(reserveIn * reserveOut * targetN/targetD) - reserveIn`,
    ///      capped at `maxSwap`. The actual swap is fee-charging (the pair's
    ///      live fee), so the post-swap ratio drifts from the target by the
    ///      fee; the balanced-subset deposit absorbs the residual without
    ///      donating.
    ///
    ///      `Math.mulDiv` keeps the intermediate product
    ///      `reserveIn * reserveOut * targetN` inside its 512-bit working
    ///      space, but the final result `... / targetD` must still fit in
    ///      uint256. Call sites must keep that invariant — in practice
    ///      both the V2 uint112 reserve cap and the bound that
    ///      `tokensForLP` ≤ `LP_RESERVE` and `ltFromPair` ≤ raised LT
    ///      are well inside the safe envelope. Constructed adversarial
    ///      inputs that violate this would `revert` rather than silently
    ///      truncate, which is the correct failure mode.
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
