### Title
Missing null-pair guard in `Router.buy` mirrors the unchecked-allocation-result pattern of CVE-2019-14877 - (File: `packages/contracts/src/Router.sol`)

### Summary
CVE-2019-14877 is a missing-failure-check bug: `Balloc`'s result is used by `__mdiff` without verifying the allocation succeeded, so a null pointer is dereferenced. In `Router.sol`, `buy()` resolves `pairAddr` from `factory.getPair(token, asset)` and immediately feeds it into `_computeBuy`/`IPair(pairAddr)` calls without checking `pairAddr == address(0)` first — the same "use a lookup result before verifying it resolved" class of bug. Every sibling entry point in the same file (`getAmountOut`, `previewBuy`, `sell`) performs this exact check before use.

### Finding Description
`Router.sol`'s `buy()`:
```
function buy(uint256 amountIn, address token, address to)
    external onlyRole(BONDING_ROLE) returns (uint256 amountInUsed, uint256 tokensOut)
{
    if (amountIn == 0) revert ZeroAmount();
    address asset = assetTokenFor(token);
    address pairAddr = factory.getPair(token, asset);
    (amountInUsed, tokensOut) = _computeBuy(pairAddr, amountIn);
    IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed);
    IPair(pairAddr).transferToken(to, tokensOut);
    IPair(pairAddr).swap(0, tokensOut, amountInUsed, 0);
}
``` [1](#0-0) 

There is no `if (pairAddr == address(0)) revert PairNotFound();` guard here, whereas `getAmountOut`, `previewBuy`, and `sell` all include it explicitly: [2](#0-1) [3](#0-2) [4](#0-3) 

If `pairAddr` resolves to `address(0)` (the equivalent of a failed allocation returning a null pointer), `_computeBuy` calls `IPair(address(0)).getReserves()` / `.k()` / `.tokenBalance()`, and the outer `buy()` calls `IPair(address(0)).transferToken(...)` and `.swap(...)`. On a chain without code at `address(0)`, these calls either revert on the low-level call, or — depending on EVM semantics for calling an address with no code — can silently return zero-valued data instead of reverting, which is the direct Solidity analog of "dereferencing" invalid/zero data instead of catching the failure explicitly. This is a missing input-validation bug of the same root-cause shape as the CVE: the code trusts the lookup's result is valid without checking it, unlike its sibling functions in the same contract.

### Impact Explanation
`Router.buy` is only reachable through `Bonding.buy`, which is gated to `BONDING_ROLE` and, per `Bonding`'s design, a `pair` is always created at `launch()` before any token is registered in `tokenInfo`. I was not able to fully verify, within the remaining budget, whether there exists any registered-token / asset-pairing state (e.g. via `Factory`'s multi-LT `ltFor` mapping, or a race between `Factory.createPair` and `Bonding.launch`) where `factory.getPair(token, asset)` can return `address(0)` for a token that already passes `Bonding.buy`'s `TokenNotTrading`/lifecycle checks. Without that reachability being confirmed, this cannot be asserted as a concretely exploitable theft-or-freeze path from an unprivileged trader — it stands only as a code-consistency/defensive-check gap analogous to the CVE's root cause, not a proven fund-loss bug.

### Likelihood Explanation
Low-to-unknown. `Bonding.launch` creates the pair synchronously before any buy can be routed to a token, and `BONDING_ROLE` is restricted to `Bonding`, so under the documented lifecycle a null `pairAddr` should not normally reach `Router.buy`. Confirming or ruling out any edge case (e.g., a multi-LT pairing state, an LT de-registration path, or an `assetTokenFor` mismatch) requires deeper reachability analysis than could be completed in this session.

### Recommendation
Add the same `if (pairAddr == address(0)) revert PairNotFound();` guard to `Router.buy` that already exists in `getAmountOut`, `previewBuy`, and `sell`, for defense-in-depth and consistency, regardless of whether a concrete reachable trigger is later found.

### Proof of Concept
Not established. I could not confirm, within the available tool budget, a concrete unprivileged-caller path through `Bonding.buy` that reaches `Router.buy` with an unregistered `(token, asset)` pair. This finding is reported as a code-pattern analog (missing failure-check before use of a lookup result, mirroring the CVE's root cause) rather than a proven exploit; further investigation of `Factory`'s pair-registration invariants and `Bonding.launch`'s ordering guarantees is needed to determine reachability.

    function getAmountOut(
        address token,
        bool isBuy,

    ) public view returns (uint256) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();

        if (isBuy) {
            (, uint256 tokensOut) = _computeBuy(pairAddr, amountIn);
            return tokensOut;

        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 newReserveToken = reserveToken + amountIn;
        uint256 newReserveAsset = pair.k() / newReserveToken;
        return reserveAsset - newReserveAsset;
    }
