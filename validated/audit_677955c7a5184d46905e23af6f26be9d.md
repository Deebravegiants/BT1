### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted by `Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then forwards the shop domain taken from an **unauthenticated header** to the app's handler as if it were verified tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop`/`topic`/`webhook_id`/`api_version` are read directly from HTTP headers without any cryptographic binding to the signed body [2](#0-1) .

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which internally calls `validate_signature`, computing the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and comparing it to the received `hmac` header [3](#0-2) . Once this check passes, `process` immediately dispatches to the app's handler, constructing `WebhookMetadata` directly from `request.shop`, `request.topic`, and `request.webhook_id` — none of which participated in the HMAC computation [4](#0-3) .

Critically, the HMAC secret (`Context.api_secret_key`) is the **app's single client secret**, shared across every merchant/shop that has installed the app — it is not a per-shop secret. Any unprivileged internet user can install the app on their own (e.g. free/dev) Shopify store to become a legitimate webhook source, capturing a body + valid HMAC pair signed with the app's shared secret. Because the shop domain is not part of the signed content, that same `(body, hmac)` pair remains valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to an arbitrary victim shop. `Registry.process` will accept it as authentic and hand the handler a `WebhookMetadata` claiming to originate from the victim shop.

This breaks the intended identity binding: **shop claimed in `WebhookMetadata#shop` (used by the app to select/act on tenant data) ⇔ shop cryptographically proven by the signature**. The gem provides no mechanism or documented requirement to independently reconcile `request.shop` against the shop that actually produced the signed bytes, yet exposes it to the handler as trusted metadata.

### Impact Explanation
This meets the "High" bar: a scope/tenant-binding check that answers permissively — an attacker with no privileges beyond installing the app on their own shop can forge webhook events attributed to an arbitrary victim shop, causing the app to act on/store data under the wrong tenant (cross-tenant data confusion) via a component (`ShopifyAPI::Webhooks::Registry`/`Request`) that is squarely in scope.

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` for tenant selection (a natural and encouraged usage pattern, as shown in the gem's own tests using `data.shop` for tenant identification [5](#0-4) ). The only requirement is that the attacker be able to install the app on a shop they control (unprivileged, no special credentials, no access token needed) and replay a captured HTTP request with a modified header.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified signable content, or require the host application to independently validate that `request.shop` corresponds to a shop with an active, known installation before trusting it — and document this requirement prominently since the current API surface (`WebhookMetadata`) implies the `shop` field is already verified once `process` succeeds.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal unprivileged install action) and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — still valid, since `B` and `secret` are unchanged [6](#0-5) .
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)` [7](#0-6) , causing the app to process attacker-controlled data as if it came from the victim shop.
