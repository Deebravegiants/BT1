### Title
Fee-on-transfer tokens cause escrow accounting to overstate actual balance held in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` (evm/tron/contracts/apps/IntentGatewayV2.sol) fails to account for fee-on-transfer ERC20 tokens in its direct-transfer code path, unlike the canonical EVM implementation which explicitly measures actual received balances for this purpose.

### Finding Description
In the main EVM contract `evm/src/apps/IntentGatewayV2.sol`, the direct-transfer branch of `placeOrder` (no predispatch call) correctly measures the actual amount received before crediting escrow: [1](#0-0) 
which snapshots `balBefore`, performs the `safeTransferFrom`, and computes `order.inputs[i].amount` as the delta — so fee-on-transfer tokens are handled correctly and confirmed by dedicated tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`). [2](#0-1) 

The Tron fork of the same contract, however, drops this balance-delta measurement in the equivalent branch: [3](#0-2) 
Here, `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` is called, but the escrow is incremented by `reducedInputs[i].amount`, which is derived purely from the caller-supplied nominal `order.inputs[i].amount` (see `reducedInputs` computation at lines 359–385), not from the token balance actually received by the contract. If the input token charges a transfer fee (or later enables one, e.g. USDT-style fee switch), the gateway's real token balance will be strictly less than what `_orders[commitment][token]` records as escrowed.

### Impact Explanation
`_orders[commitment][token]` is the internal accounting ledger that downstream fill/withdrawal/cancellation logic in the same contract relies on to release funds to solvers or refund users. Because this ledger is inflated relative to the contract's real token balance whenever a fee-on-transfer token is used, the pooled balance for that token across all outstanding orders becomes under-collateralized. This is a shared-pool accounting bug: it does not merely fail the fee-on-transfer depositor's own order, it can cause unrelated orders denominated in the same token to be unable to be fully paid out (fund freezing) or, if the shortfall is not detected atomically, lets a fee-on-transfer depositor's inflated escrow entry be paid out from token balance funded by other users' legitimate deposits (fund theft/insolvency by first-come-first-served withdrawal draining shared balance). This is a concrete accounting/fund-safety defect in a reachable, unprivileged path (`placeOrder`, callable by any depositor), qualifying as Medium/High severity depending on whether the token is later selected as an input asset and other orders share the same token.

### Likelihood Explanation
Likelihood is moderate: it requires (a) deployment/use of the Tron `IntentGatewayV2` variant, and (b) an input token that charges a transfer fee (many real tokens do, e.g. certain stablecoins with fee switches, deflationary/reflection tokens). Since any unprivileged user chooses the `order.inputs` token when calling `placeOrder`, no operator error or governance action is required to trigger the mismatch — a single user depositing a fee-on-transfer token is sufficient to desynchronize the ledger from real balance for that token.

### Recommendation
Mirror the canonical EVM implementation's fix in the Tron contract: measure the actual token balance received before and after `safeTransferFrom` in the non-predispatch branch of `placeOrder`, and use that delta (rather than the nominal `order.inputs[i].amount`) both for computing `reducedInputs`/protocol fees and for crediting `_orders[commitment][token]`, consistent with how the predispatch branch already reconciles balances via `balance`/`dust`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g., 1% fee) as an allowed input token, mirroring `FeeOnTransferToken` from `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` (lines 2690–2730).
2. User A calls `placeOrder` with `order.inputs[0].amount = 1000e18` of the fee-on-transfer token, no `predispatch`. The contract only receives `990e18` (1% fee), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` computed from `1000e18` (minus any protocol fee), i.e. more than the `990e18` actually held.
3. User B places a separate, unrelated order using the same token with a correct (non-fee) transfer, correctly funding its own escrow entry in full.
4. When solvers/fillers attempt to withdraw escrowed amounts across both orders, the contract's total tracked liabilities for that token (`sum(_orders[*][token])`) exceed its actual `IERC20(token).balanceOf(address(this))`, so a later legitimate withdrawal for User B's order can revert (funds temporarily/permanently frozen) or, depending on withdrawal ordering, an earlier withdrawer can drain balance that rightfully belongs to another user's order (fund insolvency).

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
