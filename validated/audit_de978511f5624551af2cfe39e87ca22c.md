### Title
Webhook tenant impersonation via unsigned `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values consumed by webhook handlers are read from HTTP headers that are never included in the signed data. This breaks the binding between "HMAC-authenticated bytes" and "tenant identity acted upon", allowing a captured, validly-signed webhook body/HMAC pair to be replayed with a different `x-shopify-shop-domain` header, causing the handler to process it as if it originated from an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: 
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over exactly that signable string using the app's `client_secret` and does a constant-time compare against the `hmac-sha256` header [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled straight from headers via `shopify_header`, none of which participate in the signature [2](#0-1) .

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (and `request.topic`) to route and construct `WebhookMetadata` passed to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [3](#0-2) 

Because the HMAC only proves "this body was signed by Shopify with the app's secret at some point," not "this body belongs to shop X," an entity that legitimately receives a genuinely-signed webhook for their own shop (e.g., an attacker who has the app installed on their own store, a scenario requiring no special privilege beyond being any merchant who can install a public app) can capture that valid `{raw_body, hmac}` pair and replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because the signature check never inspected the header, and `Registry.process` hands `WebhookMetadata` attributing the payload to the victim shop to the app's handler.

This is exactly the "field acted on but not covered by the HMAC" binding break: the equality the library should enforce is `shop_bound_by_hmac == shop_acted_on`, but instead `shop_acted_on` is taken from an out-of-band, unsigned header while the HMAC only covers the body.

### Impact Explanation
Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up/mutate per-tenant data, mark GDPR `shop/redact` or `customers/redact` compliance actions, trigger uninstall cleanup, or update billing/subscription state), this enables cross-tenant confusion: an attacker-controlled webhook body can be attributed to a shop the attacker does not own. This matches the Critical "cross-tenant access" impact category, since the identity binding the gem is supposed to guarantee (HMAC-signed payload ⇒ trusted tenant identity) is broken by design in `Webhooks::Request`.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuinely-signed webhook body/HMAC pair, which is trivial for anyone who can install the app on any shop they control (a normal, unprivileged flow for public apps) and capture their own inbound webhook traffic. No access to `api_secret_key` or any victim credentials is needed — the attacker only replays previously-observed valid bytes with a substituted header against the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material that `Registry.process` verifies, or otherwise cryptographically tie the header-derived tenant identity to the HMAC-covered body (e.g., require the webhook payload itself to carry/echo the shop domain and cross-check it against the header before trusting either). At minimum, document and enforce that consumers of `WebhookMetadata#shop` must not treat it as authenticated unless it is independently verified against signed content.

### Proof of Concept
1. Install the target app (as any merchant) on `attacker-shop.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) so Shopify sends a genuinely HMAC-signed request to the app's webhook endpoint, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-signature-for-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: ...
   Body: {"id": 123, ...}
   ```
2. Capture this exact `{body, hmac}` pair.
3. Replay it to the same endpoint, changing only the header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same-valid-signature>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: <same body>
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` at `lib/shopify_api/utils/hmac_validator.rb:13-22` returns `true` because it only checks `@raw_body` against the signature, which is unchanged. `ShopifyAPI::Webhooks::Registry.process` at `lib/shopify_api/webhooks/registry.rb:188-199` then calls the app's handler with `shop: "victim-shop.myshopify.com"`, letting the attacker's forged body be processed as if it came from the victim shop.
