### Title
Creator-supplied, unvalidated `ltAddress` lets a malicious "LT" contract capture Zap's USDC and drain buyers via `Zap.createToken` / `Bonding.launch` - ([File: packages/contracts/src/Bonding.sol], [File: packages/contracts/src/Zap.sol])

### Summary
The Jenkins Bitbucket plugin bug is a trust-the-payload SSRF: the plugin took a URL supplied in an inbound webhook and used stored Bitbucket credentials to connect to it, letting an attacker redirect the plugin's privileged connection anywhere and capture credentials. The analogous root cause in `alt.fun` is that `Bonding.launch` (reached via `Zap.createToken`/`createTokenWithPermit`) accepts an attacker-chosen `ltAddress` field inside `Bonding.LaunchParams` and — as far as could be verified in `packages/contracts/src/Bonding.sol` and `packages/contracts/src/interfaces/IBounceFactory.sol` — never calls `IBounceFactory.ltExists(ltAddress)` (or any other allow-list check) before wiring that address in as the token's "reserve asset." From that point on, every buy/sell/zap flow (`Zap._executeBuy`, `Zap._sellInternal`) treats the caller-supplied address as a real BounceTech LT and sends it USDC to mint against, and trusts its `exchangeRate()`/`redeem()` return values, exactly like the plugin trusted the caller-supplied webhook URL and used privileged credentials against it.

### Finding Description
`Zap.createToken`/`createTokenWithPermit` take a `Bonding.LaunchParams calldata params` struct containing `params.ltAddress`, checked only for `address(0)`: [1](#0-0) 

`params.ltAddress` is passed straight through to `Bonding.launch(params, msg.sender)`, which — per `docs/contracts-scope.md` and the visible portion of `Bonding.sol` — stores it as the pair's reserve asset and uses it going forward for `exchangeRate()`, minting, and redemption: [2](#0-1) 

The interface `IBounceFactory.ltExists(address)` exists specifically to let a caller verify "True iff `ltAddress_` was deployed via this factory's `createLt`": [3](#0-2) 

However, grepping `Bonding.sol` for `ltExists`/`IBounceFactory` usage in the launch path did not turn up a call gating `launch()` on this check — the import is present (used elsewhere for other reads), but the actual validation call inside `launch()` could not be confirmed in the visible source. If, as the evidence suggests, `launch()` does not call `ltExists` before accepting `params.ltAddress`, then any address — including an attacker's own malicious contract implementing `IBounceLeveragedToken` — can be registered as the reserve asset for a brand-new token/pair. Once accepted, every subsequent `Zap.buy`/`Zap.buyWithPermit` for that token pulls the buyer's USDC into `Zap`, then calls `mint()` on the attacker-controlled "LT" (per the buy-flow description: "Net USDC is minted to LT"). A malicious LT contract can simply keep the USDC (never actually minting an ERC20 balance back, or reporting a favorable `exchangeRate()`/fake balance) while the curve still credits the buyer with real launched tokens computed from the (attacker-forged) minted amount — this mirrors the SSRF pattern of trusting attacker-supplied data to drive privileged token transfers.

### Impact Explanation
Because the reserve-asset address is fully attacker-chosen and drives real USDC transfers from every buyer of that token (Zap mints/redeems against it on every `Zap.buy`/`Zap.sell`), an attacker can create a token whose "LT" is a malicious contract that (a) accepts and keeps buyers' USDC forwarded by `Zap` without minting real backing, and/or (b) reports a manipulated `exchangeRate()` so sells redeem far more USDC than was ever deposited, draining `Zap`'s USDC balance held for other tokens. This is concrete theft/freezing of trader funds and can cause insolvency in shared `Zap` USDC balances, satisfying the "concrete theft or freezing of trader funds" bar.

### Likelihood Explanation
Reaching this path requires only an unprivileged call to `Zap.createToken`/`createTokenWithPermit` with a self-deployed contract address as `params.ltAddress`, followed by normal `Zap.buy` calls from victims (or the attacker's own seed buy) — no privileged role, upgrade, or off-chain component is needed, matching the "single unprivileged address" bar. Likelihood is contingent on confirming that `Bonding.launch()` genuinely omits the `IBounceFactory.ltExists` gate; this could not be fully confirmed from the visible slice of `Bonding.sol`.

### Recommendation
In `Bonding.launch`, before accepting `params.ltAddress`, call `IBounceFactory(bounceFactory).ltExists(params.ltAddress)` (the interface already exists in the codebase) and revert if false, so only LTs genuinely deployed by BounceTech's factory can be paired with a launched token.

### Proof of Concept
Not fully constructible with certainty: the decisive fact — whether `Bonding.launch()` calls `ltExists` on `params.ltAddress` — sits in a portion of `packages/contracts/src/Bonding.sol` that could not be retrieved within the tool budget for this scan. The reachable attacker steps that *are* confirmed are:
1. Attacker deploys a contract implementing `IBounceLeveragedToken` that accepts `mint()` calls and keeps the USDC, or returns a manipulated `exchangeRate()`.
2. Attacker calls `Zap.createToken({ ..., ltAddress: <malicious contract> }, seedUsdcAmount)` [4](#0-3) .
3. Any trader calling `Zap.buy(tokenAddress, usdcAmount, minTokensOut, referrer)` on this token has their USDC minted into the malicious LT per the documented buy flow [5](#0-4) .

Given the inability to confirm the missing `ltExists` gate with certainty in the available source, this should be treated as a **finding requiring confirmation** rather than a proven vulnerability — a Devin session with full repository access should grep the complete `Bonding.sol::launch` function body to verify whether the `ltExists` check is present or absent before this is escalated.

## Token Launch

Creator calls `Zap.createToken({ name, ticker, ltAddress, description, image, urls }, seedUsdcAmount)`. The router calls `Bonding.launch()` to deploy the curve, then performs the **mandatory** seed buy via the standard `Zap.buy` path so it inherits the same pro-rata fee handling and leftover refund as any other buy.

### Anti-snipe gate

`seedUsdcAmount` must be `≥ Zap.MIN_SEED_USDC` (`$20`, real USDC, 6dp). On top of that, `Bonding` blocks every public buy on the bonding curve for the next `LAUNCH_TRADING_DELAY_BLOCKS` (`= 3`) blocks — trading opens at `launchBlock + LAUNCH_TRADING_DELAY_BLOCKS + 1`. The seed buy bypasses the gate via a transient-storage flag set inside `Bonding.launch` and consumed by the very next `Bonding.buy` in the same tx, so the creator's seed always lands while same-block sniper bundles (separate txs, transient cleared) revert with `TradingNotOpen`. The gate is buy-only: sells are not delayed, so a creator can withdraw the seed within the window — accepted for the same reason the seed is uncapped (below), since a creator controls their own open regardless and cannot be forced to leave the seed in  ... (truncated)

There is **no upper bound** on the seed. A cap is trivially bypassable (the same creator seeds via wallet A then snipes the open at block N+4 from wallet B), and seed-and-burn launches are a legitimate supply pattern. The floor is the only side that protects the curve floor from being free.

This deploys a `Token` clone (1B supply) and creates a `Pair` (token/LT). K is computed per token so every token opens at ~`$3K` market cap regardless of which LT is paired.

**Virtual token reserve.** The pair's `reserve0` is seeded at `totalSupply` (1B) while only `curveSupply = 75%` (750M) of real tokens are actually transferred. The other 250M are held in `Bonding` as `lpReserve`. This virtual-reserve design:

- Extends the curve beyond the sellable supply.
- Gives a deterministic supply trigger (curve exhausts at 750M sold).
- Makes the dynamic-LP-seeding parabola `tokensForLP(sold) = sold·(S−sold)/S` peak at exactly `S/4 = 250M = LP_RESERVE` — so `tokensForLP ≤ lpReserve` is a mathematical invariant, not a runtime guess.

Each token stores: creator, token address, pair address, paired LT address, metadata, trading status, graduation status.

## Buy Flow

1. `Zap.buy(tokenAddress, usdcAmount, minTokensOut, referrer)`
2. `Zap` pulls `usdcAmount` USDC and deducts the 0.75% Alt Fun fee up-front (forwarded to `FeeVault`, split 0.5% protocol / 0.25% creator). The fee is charged on every buy — curve **and** post-graduation — not just curve trades.
3. Net USDC is minted to LT
4. If on curve: routes through `Bonding.buy()` (the internal AMM `Router.sol`). If graduated: swaps on HyperSwap V2 (TOKEN/LT pool). The 0.75% Alt Fun fee is identical on both paths; post-grad, HyperSwap also charges its own 0.3% LP fee on the swap leg, on top of the Alt Fun fee.
5. Tokens sent to user; on a capped buy, any LT minted but not consumed by the curve is returned directly as LT, while unconverted USDC and the pro-rata fee over-charge are refunded in USDC

**Overflow buy protection.** On the final buy that would empty the curve, `Router.buy` caps `tokensOut` at the pair's real token balance and back-calculates the LT actually required (`amountInUsed`). `Bonding.buy` returns both `tokensOut` and `amountInUsed`. `Zap.buy` transfers the LT it minted but the curve didn't consume (`ltMinted - amountInUsed`) straight back to the buyer as LT — it is **not** redeemed, since round-tripping the dust overshoot through `redeem()` would re-incur the LT's redemption fee. Net USDC that was never minted into LT, plus the pro-rata fee over-charge, is refunded separately in USDC.
