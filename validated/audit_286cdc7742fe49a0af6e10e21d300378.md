### Title

Unvalidated route payload can attach unauthorized token transfers to the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

The controller accepts an opaque `swap` payload and forwards it to the configured swap aggregator without constraining which contracts the route may invoke. If a crafted route invokes attacker-controlled code, that code can request token transfers from the caller to an attacker-controlled recipient. Soroban records the malicious transfer as a sub-invocation of the caller’s signed `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` authorization tree; if the caller signs the simulated tree, the unrelated wallet funds are transferred.

### Finding Description

`swap_tokens` reads only the configured aggregator address, snapshots the input and output balances, authorizes one exact controller-to-router input transfer, and invokes `execute_strategy` with the caller-supplied opaque payload [1](#0-0) . Its post-call checks bound only the controller’s measured input spend, refund unused controller-held input, and require positive measured output; they do not restrict contracts reached through the route [2](#0-1) .

The vulnerable parameter reaches four unprivileged strategy entrypoints. `swap_collateral` passes caller-controlled `swap` bytes after withdrawing account collateral [3](#0-2) . `swap_debt` passes its route after borrowing new debt [4](#0-3) . `multiply` accepts both a main route and a `convert_swap` route [5](#0-4) . `repay_debt_with_collateral` passes a route when collateral and debt differ [6](#0-5) .

A malicious route can name an attacker-controlled hop contract. That contract runs below the signed strategy invocation and can invoke `token.transfer(caller, attacker, amount)` for any token whose authorization the caller’s signed tree includes. The repository’s authorization harness demonstrates that simulation records this rogue transfer as a child of `swap_collateral`, and enforced auth executes it when the caller signs the poisoned tree [7](#0-6) .

### Impact Explanation

Theft of user funds: an attacker can steal wallet tokens unrelated to the lending operation. The theft is not limited to the swapped collateral because the malicious child invocation can name a separate token contract and recipient; the measured input/output checks only account for the controller’s strategy legs, not unauthorized child transfers made under the caller’s authorization [8](#0-7) .

The fair route output can still be delivered, so balance-delta checks and final account risk checks do not prevent the theft [9](#0-8) .

### Likelihood Explanation

Exploitation requires the victim to submit a crafted route and sign an authorization tree containing the malicious child transfer. This is reachable by an unprivileged attacker through a malicious route quote, compromised automation, or socially engineered route payload; those paths are analogous to crafted command input in the reference issue.

Without the additional signed child authorization, the host rejects the rogue transfer and rolls back the transaction [10](#0-9) . Therefore, likelihood is limited by the need to get the victim to sign the poisoned tree, but a successful signature results in direct token theft.

### Recommendation

Constrain route execution so venue calls cannot inherit unintended caller authorization. Prefer a router design that uses `require_auth_for_args` or equivalent scoped authorization for exactly the expected token transfer, isolates route execution from the user’s authorization tree, and maintains a governance-approved venue allowlist. At minimum, clients must decode the complete simulated authorization tree and reject any child invocation other than the expected input-token transfer; this client-side mitigation should not replace protocol-level isolation.

### Proof of Concept

The repository contains a focused harness proving the primitive:

1. Alice supplies USDC and holds an unrelated wallet token [11](#0-10) .
2. A crafted route names a rogue hop contract configured to call `token.transfer(Alice, attacker, amount)` [12](#0-11) .
3. Simulation records the rogue wallet transfer beneath Alice’s `swap_collateral` authorization root [13](#0-12) .
4. The honest authorization tree rejects the transfer, while the poisoned simulated tree executes it and moves Alice’s full unrelated token balance to the attacker [14](#0-13) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
