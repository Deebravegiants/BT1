### Title
Webhook shop-domain (tenant) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `ShopifyAPI::Utils::HmacValidator` verifies binds nothing but the JSON payload. The `shop` (from the `X-Shopify-Shop-Domain` header) and `topic` are read separately from unauthenticated headers and passed straight through to the app's webhook handler as the tenant/shop identity, without being covered by the same signature that authenticates the request.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, then immediately forwards `request.shop` to the handler: [1](#0-0) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field: [2](#0-1) 

But `Webhooks::Request#to_signable_string` is defined as just the raw body: [3](#0-2) 

while `shop` and `topic` are pulled from headers that are never part of the signed material: [4](#0-3) 

Because Shopify signs an app's webhooks using the app's single `client_secret`/`api_secret_key` shared across every merchant that installs the app (not a per-shop secret), any merchant who installs the app receives genuinely-signed `(body, hmac)` pairs for their own shop. Since `shop` is not part of the signed bytes, that same valid `(body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a different (victim) shop's domain. `HmacValidator.validate` will still return `true` because only the body is checked, yet `WebhookMetadata.shop` — the value handed to the app's handler as the request's tenant identity — will be the attacker-forged domain: [5](#0-4) 

This is structurally the same class of bug as the reported issue: an identity/attribution field (`shop`, analogous to the relayer address) is used to drive downstream behavior but is not bound by the very authentication mechanism (`HMAC`, analogous to fee transfer authorization) that is supposed to guarantee its authenticity.

### Impact Explanation
This breaks the equality "shop authenticated by HMAC == shop attributed to the webhook handler." A multi-tenant app that keys its per-shop state/session lookup off `WebhookMetadata#shop` (the documented, intended usage per `docs/usage/webhooks.md`) can be made to apply another merchant's genuine webhook event under a different shop's identity, or attacker-influenced data (e.g. a legitimately triggered `orders/create` payload from the attacker's own shop) can be attributed to a victim shop. This is a cross-tenant identity-binding break enabled entirely by this gem's own `Webhooks::Request`/`Registry` implementation, independent of how carefully the host app implements its own logic on top of the documented API.

### Likelihood Explanation
Any actor who can install the app on their own shop (default state for public/multi-tenant Shopify apps) legitimately receives correctly HMAC-signed webhook deliveries for events on their own shop. Forging the `X-Shopify-Shop-Domain` header on a replayed request requires no secret knowledge — only capturing one's own genuine webhook body+HMAC and resending it with a modified header, which the gem's verification logic does not detect.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable material, or otherwise cryptographically bind the shop-domain header to the signed payload before it is trusted and forwarded to handlers in `Webhooks::Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; register a webhook (e.g. `orders/create`).
2. Trigger the event so Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Capture the raw body and HMAC header from that delivery.
4. Replay the identical raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` succeeds (only body is checked, per `lib/shopify_api/webhooks/request.rb:35-38`), and `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to process attacker-supplied event data under the victim's tenant identity.
