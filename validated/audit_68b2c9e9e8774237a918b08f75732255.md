### Title
Excess native-token dust from `EvmHost.dispatch`/`fundRequest` ETH-to-feeToken swaps is trapped in `EvmHost` with no refund or sweep path - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` accept `msg.value` and forward it wholesale to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard UniswapV2 router implementation refunds any unspent ETH (`msg.value - amountIn`) to its immediate caller — `EvmHost` itself — not to the original transaction sender. Every over-estimated native-token payment therefore leaves residual ETH permanently stranded inside `EvmHost`, exactly mirroring the LamboVEthRouter bug class: user-facing dispatch functions that accept native value and perform an internal swap/refund cycle, but never route the leftover value back out to the payer or to any sweep function.

### Finding Description
In `EvmHost.sol`, all three entry points that accept native-token payment for protocol fees follow the same pattern: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `msg.value` is passed entirely into `swapETHForExactTokens`, and the return value (`amounts[0]`, the ETH actually spent) is discarded — `EvmHost` never compares it against `msg.value` and never forwards a refund to `_msgSender()`. Reference implementations of Uniswap V2's router (e.g. `UniswapV2Router02.swapETHForExactTokens`) refund `msg.value - amounts[0]` to `msg.sender` of that call, which in this flow is `address(this)` (`EvmHost`), not the original caller of `dispatch`/`fundRequest`. As a result, any transaction that supplies more native value than the router actually consumes for the exact fee-token output leaves the difference sitting in `EvmHost`'s own balance.

This is structurally identical to the LamboVEthRouter finding: a public/external payable entry point performs an internal swap/refund step whose leftover value is not routed back to the caller, and the receiving contract has no `receive()`-triggered accounting or sweep mechanism to recover it. Nothing in `EvmHost.sol` (no `receive()`, no native-ETH withdraw/sweep function found in the contract) allows the admin, hostManager, or users to reclaim this accumulated ETH; only fee-token balances are governed by `IHostManager.withdrawFunds`-style flows tied to `feeToken()`, not native ETH.

### Impact Explanation
This is reachable by any unprivileged account dispatching a POST/GET request or funding a request with native-token payment — a routine, permissionless action central to Hyperbridge's fee-payment UX (`dispatch{value: ...}`). Because slippage and price movement make it impractical for callers to supply the exact ETH amount the swap will consume, essentially every native-value dispatch on every EVM deployment of `EvmHost` leaks some ETH into the contract. Over the life of the protocol across many chains and many dispatches, this is a permanent, unrecoverable loss of user funds accumulating inside a core, high-traffic contract, with no mechanism to sweep or refund it — a genuine freezing-of-funds condition rather than a low/informational rounding issue.

### Likelihood Explanation
High. This triggers on the ordinary "pay dispatch fee with native token" code path (documented as the recommended UX for one-off/user-facing dispatches), and does not require any adversarial behavior — only normal slippage/estimation imprecision in `msg.value` sizing, which is unavoidable when swap quotes are estimated off-chain before submission (as the project's own documentation instructs: "Use the `quote()` view function from your frontend... Do not call `quote()` in smart contract transactions" due to sandwich-attack exposure — meaning some slippage buffer, and hence overpayment, is expected practice).

### Recommendation
After each `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, compare `amounts[0]` (ETH actually spent) to `msg.value` and refund the difference to `_msgSender()` via a low-level call, mirroring the pattern already used correctly elsewhere in the codebase (e.g. `IntentGatewayV2._buyQuote`/`ExtrinsicIntents` refund unspent `msgValue` to `msg.sender`, and `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper` explicitly forward router refunds back to their caller). As a defense-in-depth measure, also add an admin/hostManager-gated native-ETH sweep function to recover any ETH that becomes stranded despite the fix (e.g. from `selfdestruct` or `coinbase` transfers).

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` (in feeToken) is quoted off-chain to require roughly 0.5 ETH worth of input, but with slippage buffer the user sends 1 ETH.
2. `dispatch` executes:
   ```solidity
   IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
       post.fee, path, address(this), block.timestamp
   );
   ``` [4](#0-3) 
3. The Uniswap V2 router spends only `amounts[0]` (~0.5 ETH) and refunds `1 ether - amounts[0]` (~0.5 ETH) to its `msg.sender`, which is `EvmHost`.
4. `EvmHost.dispatch` never reads or forwards this refund — the returned `uint[] memory amounts` from the swap call is not even captured in this function. The ~0.5 ETH remains in `EvmHost`'s balance permanently, with no code path (`receive()`/sweep/withdraw) that returns it to the user or the protocol.
5. Repeating this across every native-value dispatch/fundRequest transaction (the intended default UX per the project's own documentation) accumulates unrecoverable ETH in `EvmHost` indefinitely.
