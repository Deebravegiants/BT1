### Title
Malicious `IApp` implementation can permanently block relayer-fee refunds on POST-timeout by consuming forwarded gas in `onPostRequestTimeout` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchTimeOut(PostRequestTimeout)` invokes the source application's `onPostRequestTimeout` callback via an unbounded, gas-unlimited low-level `.call()` *before* refunding the relayer fee to the fee payer. Any contract implementing `IApp` can deliberately make this callback always fail (revert, or burn all forwarded gas), which permanently prevents the escrowed relayer fee from ever being refunded to the original fee payer — a different party than the app author. This mirrors the "Cooler" bug class: a party controlling a callback invoked mid-settlement can grief a counterparty's ability to recover funds.

### Finding Description
When a POST request dispatched by an `IApp` contract times out, a relayer submits a timeout proof to the handler, which calls `IHost.dispatchTimeOut(PostRequestTimeout, meta, commitment)`. The implementation: [1](#0-0) 

```solidity
function dispatchTimeOut(
    PostRequestTimeout memory timeout,
    FeeMetadata memory meta,
    bytes32 commitment
) external restrict(_hostParams.handler) {
    // replay protection
    delete _requestCommitments[commitment];
    (bool success,) = _bytesToAddress(timeout.request.from)
        .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

    if (!success) {
        // so that it can be retried
        _requestCommitments[commitment] = meta;
        return;
    }

    if (meta.fee != 0) {
        // refund relayer fee
        IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
    }
    emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
}
```

Key facts:
- The call to `timeout.request.from` (the dispatching app) forwards essentially all remaining gas (no gas stipend is specified), exactly the "unbounded callback" pattern flagged in the reference report.
- The refund of `meta.fee` (the relayer fee originally escrowed from `meta.sender`, the fee **payer**, at dispatch time) only happens **after** the callback succeeds. This is explicitly documented as intentional behavior: [2](#0-1) 

```
### dispatchTimeOut(PostRequestTimeout)

Dispatches a timed-out POST request to the source application's `onPostRequestTimeout()` callback. If the callback succeeds, refunds the relayer fee to the payer.
...
**Important:** Fee refund only happens if the application's timeout callback succeeds.
```

- If the callback fails, the code path is designed to be "retriable" (`_requestCommitments[commitment] = meta;`), but if the destination `IApp` is malicious and *always* reverts or *always* consumes all forwarded gas, every future retry by any relayer will fail identically. The commitment is permanently stuck in "pending timeout" state and `meta.fee` — already collected from `meta.sender` at dispatch — can never be released.
- Critically, `meta.sender` (the fee payer) is not necessarily the app author. Any unprivileged user who dispatches a POST request through a third-party `IApp` contract (e.g., a cross-chain messaging app, a bridge, or any integrator built on Hyperbridge) pays the relayer fee up front via `dispatch(DispatchPost)`. If that app's `onPostRequestTimeout` is malicious (or simply buggy/adversarially upgraded) and unconditionally reverts/burns gas, the user's escrowed relayer fee is permanently frozen inside `EvmHost`, with no other code path to reclaim it. The docs even acknowledge the app owns the responsibility ("Don't revert unless absolutely necessary... Keep gas costs low") — but nothing in the host enforces this, and there is no gas cap, no try/catch-with-fixed-gas, and no way for the fee payer to force the refund independently of the (adversarial) app's cooperation.

### Impact Explanation
This is a concrete, permanent freezing-of-funds bug: the relayer fee is deducted from a user (or any other integrator) at dispatch time and is unrecoverable once the destination/source app's timeout callback is deliberately made to always fail. Because the failure path is "retry forever," and the retry always hits the same unconditionally-failing callback, this is not a transient DoS — it is a permanent loss for the fee payer. The affected funds are held by the core `EvmHost` contract, a shared, non-optional dependency for every ISMP-integrated application, meaning any single malicious or compromised `IApp` deployment can trap fees belonging to arbitrary third-party users who interacted with it.

### Likelihood Explanation
Likelihood is High. No privileged role is required — anyone can deploy an `IApp` contract implementing a malicious `onPostRequestTimeout` (e.g., `revert()` unconditionally, or an assembly loop that burns gas until out-of-gas) and get ordinary users to route POST dispatches through it (this is exactly how third-party integrations onboard onto Hyperbridge — deploying their own `IApp`). Triggering the timeout path only requires the dispatched request to expire and a relayer (anyone) to submit the timeout proof, which is a normal permissionless operation.

### Recommendation
- Cap the gas forwarded to `IApp.onPostRequestTimeout` (and similarly to `onAccept`, `onGetResponse`, `onGetTimeout`) to a fixed, bounded stipend so a malicious/broken app cannot consume the entire transaction's gas or endlessly revert to block state transitions that belong to the protocol rather than the app (e.g., fee refunds).
- Decouple the relayer-fee refund from the success of the application callback: refund `meta.fee` to `meta.sender` unconditionally (or via a separate, always-executed code path) regardless of whether the app's callback succeeds, since the fee refund is a protocol-level obligation to the payer, not something that should be gated by cooperative application behavior.
- Consider using `try/catch` with an explicit gas limit and treating callback failure as "delivered but with logged failure" rather than silently making the refund contingent on an untrusted external call succeeding.

### Proof of Concept
1. Deploy `MaliciousApp implements IApp` with:
   ```solidity
   function onPostRequestTimeout(PostRequestTimeout calldata) external pure {
       revert("always fail");
   }
   ```
2. A victim user calls `dispatch(DispatchPost)` from `MaliciousApp` (or `MaliciousApp` dispatches on the victim's behalf), paying `fee` in `feeToken`, which `EvmHost` escrows.
3. The request times out on the destination chain without being delivered.
4. A relayer submits the timeout proof; the handler calls `EvmHost.dispatchTimeOut(PostRequestTimeout, meta, commitment)`.
5. `dispatchTimeOut` calls `MaliciousApp.onPostRequestTimeout`, which reverts; `success == false`, so `_requestCommitments[commitment] = meta;` is restored and the function returns without refunding `meta.fee`.
6. Any subsequent relayer retry of the timeout proof repeats step 5 forever — `meta.fee` is permanently locked in `EvmHost`, unrecoverable by `meta.sender`.
