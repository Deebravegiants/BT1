### Title
Excess native token sent to `EvmHost.dispatch()` / `fundRequest()` is refunded by Uniswap to the Host contract instead of the original caller, permanently stranding funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and forward it to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` without checking or refunding the leftover ETH to the original sender. This is the same bug class as the Sherlock/Gitcoin Allo report: any native token sent in excess of the amount actually required is not returned to the user.

### Finding Description
In `dispatch(DispatchPost memory post)`: [1](#0-0) 

and identically in `dispatch(DispatchGet memory get)`: [2](#0-1) 

and `fundRequest()`: [3](#0-2) 

The standard `UniswapV2Router02.swapETHForExactTokens` implementation computes `amounts[0]` (the actual ETH consumed for `amountOut`) and refunds `msg.value - amounts[0]` dust ETH back to `msg.sender` of that call — see the router's known implementation pattern, confirmed by the test that documents the wrapper "refunds the excess" to its caller: [4](#0-3) 

However, the caller of `swapETHForExactTokens` here is `EvmHost` itself (it invokes the router with `{value: msg.value}` from inside `dispatch`/`fundRequest`), not the end user who called `EvmHost.dispatch()`. Therefore the router's dust-ETH refund lands back in `EvmHost`'s own balance rather than being forwarded to `_msgSender()`/`post.payer`/`get.payer`. None of the three functions capture the router's returned `amounts` array or forward any leftover `msg.value` back to the caller. `EvmHost.sol` was not observed to contain any `receive()`/native-ETH-refund path for these dispatch functions in the reviewed region.

This exactly mirrors the reported Allo issue: a user funds an operation with more native token than strictly required, and the surplus is not returned but is trapped inside the intermediary contract (`EvmHost` here, `Allo` in the original report).

### Impact Explanation
Any user or integrating contract (e.g. `ExtrinsicIntents._post`, `IntentGatewayV2` order flows, `HyperbridgeLzEndpoint.send`, `WrappedHyperFungibleToken.send`) that calls `dispatch{value: msg.value}(...)` or `fundRequest{value: ...}(...)` with any margin above the exact Uniswap `amountIn` required to buy `post.fee`/`get.fee`/`amount` fee-tokens will have the difference permanently stuck in `EvmHost`. Since exact fee-token pricing depends on live pool reserves at execution time (subject to slippage/front-running), callers are effectively forced to either under-fund (risking a revert on `EXCESSIVE_INPUT_AMOUNT`-type checks) or over-fund defensively — and any overfunding is a direct, unrecoverable loss of user native token. This is a concrete, direct loss of funds for any unprivileged caller of the dispatch/fundRequest paths, which are core, permissionless entry points to the protocol.

### Likelihood Explanation
High likelihood: this occurs on virtually every native-token payment through `dispatch()`/`fundRequest()`, since `amountIn` (ETH price of the requested fee-token amount) fluctuates block-to-block, and client-side estimation (`quote()`) is explicitly documented as an off-chain approximation vulnerable to sandwiching, meaning callers routinely must send a `msg.value` buffer above the estimate to avoid reverts — guaranteeing dust/excess ETH gets swept into `EvmHost` on essentially every native-funded dispatch.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` back to `_msgSender()` (or the designated payer) via a safe ETH transfer, mirroring the pattern already implemented correctly elsewhere in the codebase, e.g. `IntentGatewayV2.sol`'s "Refund any unspent native tokens to the user" logic: [5](#0-4) 

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1 ether}(DispatchPost{fee: X, ...})` where the current pool price only requires `0.6 ether` to obtain `X` fee-tokens.
2. Inside `dispatch`, `EvmHost` calls `router.swapETHForExactTokens{value: 1 ether}(X, path, address(this), ...)`.
3. The router spends `0.6 ether`, buys `X` fee-tokens for `EvmHost`, and refunds the remaining `0.4 ether` to `msg.sender` of the swap call — which is `EvmHost`, not the user.
4. `EvmHost.dispatch` returns normally, the request is created, but the user's `0.4 ether` surplus is now silently absorbed into `EvmHost`'s ETH balance with no code path to return it to the user. [1](#0-0)
