### Title
Missing transaction-expiration guard lets a `Zap.sell` graduation-trigger call silently execute as an unprotected zero-slippage sale - (File: packages/contracts/src/Zap.sol)

### Summary
`Zap.sell`/`Zap.sellWithPermit` have no deadline parameter. When a caller believes a token is graduatable, the protocol *requires* them to submit `minUsdcOut == 0`, because a positive minimum is rejected on the graduation branch [2](#0-1) . `canGraduate()` is a live view over the pair's stored reserves and the LT's `exchangeRate()` — both mutate on every trade and every rate update [1](#0-0) . If the transaction sits in the mempool and the curve state changes before inclusion (a competing sell/buy, or a rate drift) such that `canGraduate()` flips from `true` to `false`, the same call no longer takes the graduation branch and instead executes as a genuine sale — with `minUsdcOut` still pinned at `0`, i.e. with **zero** slippage protection [3](#0-2) . There is no deadline mechanism to invalidate the stale intent, unlike the swap-deadline pattern DEXes use (the exact gap the referenced report calls out for `repay()`).

### Finding Description
1. A trader holds tokens on a curve that is currently graduatable (`canGraduate(token) == true`), typically because LT appreciation pushed the curve's real-LT value above the USD threshold without any new buy landing.
2. Per protocol design, the trader must call `zap.sell(token, tokenAmount, 0)` — any nonzero `minUsdcOut` reverts with `TokenIsGraduating` on this branch — expecting the call to no-op into `Bonding.triggerGraduation` and leave their tokens untouched [2](#0-1) .
3. While the transaction is pending, an attacker (or ordinary market activity) shifts the curve/LT state so `canGraduate()` flips to `false` before the trader's transaction lands — e.g. a competing sell reduces the stored LT reserve, or the LT's `exchangeRate()` moves down.
4. `_sellInternal` re-evaluates `canGraduate()` at execution time, so the same call now falls through to the real sell path (`_sellOnCurve` / curve redeem), still carrying `minUsdcOut == 0` from step 2 [3](#0-2) .
5. Because `minUsdcOut == 0`, the `usdcOut < minUsdcOut` guard never reverts regardless of price [4](#0-3) , so an attacker who additionally sandwiches the trade (front-run sell to depress the curve price, let the victim's zero-floor sell execute, back-run buy to restore price) can extract nearly all the value of the victim's sale.
6. There is no deadline argument anywhere in `Zap.sell`/`sellWithPermit` (the `PermitData.deadline` only governs the ERC-2612 signature, not trade freshness) [5](#0-4) [6](#0-5) , so this stale-intent execution cannot be prevented on-chain by the caller.

### Impact Explanation
A trader can lose the majority of their sale proceeds through a classic sandwich, purely because the protocol's own required calling convention (`minUsdcOut = 0` for graduation-trigger sells) leaves them with no slippage protection the moment the on-chain condition they relied on (`canGraduate`) is no longer true by the time of inclusion. This is direct theft of trader funds via price manipulation enabled by a stale, unprotected transaction — a concrete loss to an unprivileged trader, matching the Medium-severity impact class of the referenced report.

### Likelihood Explanation
Any address holding curve tokens on a near-threshold curve can be targeted. The precondition (`canGraduate() == true` at submission, `false` at execution) is achievable by an attacker simply front-running with a small sell that nudges the stored LT reserve below the USD threshold, which is a normal, permissionless action (`Zap.sell`) requiring no special privilege. Given public mempool visibility of the victim's zero-floor sell, this is a straightforward MEV/sandwich opportunity.

### Recommendation
Add a `deadline` parameter (checked via `block.timestamp <= deadline`) to `Zap.sell`/`sellWithPermit` (and `buy`/`buyWithPermit` for symmetry), and additionally re-derive the "graduation-trigger" branch from an explicit caller-supplied flag or a fresh check that reverts (rather than silently falling through to a live sale) when the expected `canGraduate()` state no longer holds — e.g. revert with a dedicated error instead of executing the sale at `minUsdcOut == 0` when the caller clearly intended only a no-op trigger.

### Proof of Concept
1. Launch a token and stage LT via buys until `canGraduate(token) == true` (as in `test_canGraduate_returnsTrueWhenThresholdMet`, achieved purely via `lt.setExchangeRate`) [7](#0-6) .
2. Victim submits `zap.sell(token, victimTokenAmount, 0)`, expecting the graduation no-op.
3. Attacker front-runs with `zap.sell(token, smallAmount, 0)` (or otherwise nudges reserves) so that by the time the victim's tx is mined, `canGraduate(token)` has flipped `false` (e.g. real-LT-raised drops just under the USD threshold).
4. Victim's transaction now executes `_sellOnCurve` for the full `victimTokenAmount` at `minUsdcOut == 0`, receiving whatever the (attacker-depressed) curve returns.
5. Attacker back-runs with a buy to restore the curve and capture the spread, netting the difference between the fair price and the depressed execution price at the victim's expense.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
