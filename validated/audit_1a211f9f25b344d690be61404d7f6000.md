### Title
Webhook HMAC only covers the raw body, not the `shop-domain`/`topic` identity headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature Shopify sends verifies solely the byte content of the body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and are never part of the signed material, yet they are trusted as the tenant/event identity when the payload is dispatched to a handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body` — none of `shop`, `topic`, `webhook_id`, or `api_version` (all read from headers via `shopify_header`) participate in the signable string.

`HmacValidator.validate` then checks `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is `HMAC(secret, verifiable_query.to_signable_string)`: [2](#0-1) 

`Registry.process` validates the HMAC and then dispatches using the unauthenticated `shop`/`topic` headers as the trusted identity: [3](#0-2) 

The identity binding that should hold is:
`hmac_signed_bytes == (raw_body ‖ shop ‖ topic)`

but the actual implementation is:
`hmac_signed_bytes == raw_body` while `shop` and `topic` are taken from unauthenticated headers and used downstream as if they were verified.

Because a merchant/app-installer is themselves an "unprivileged internet user" with respect to *other* tenants of the same app, this satisfies the "field acted on but not covered by the HMAC" analog: any legitimate webhook body+HMAC that Shopify delivered for the attacker's own shop (attacker installs the app on their own free/dev store — no special privilege required) can be replayed verbatim to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop, or the `X-Shopify-Topic` header rewritten to a different topic. `HmacValidator.validate` will still succeed because the signature only ever covered the raw body, and `Registry.process` will hand `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the host application's handler with an attacker-chosen `shop`/`topic` that was never bound to the HMAC.

### Impact Explanation
This is a cross-tenant identity-confusion vector inside the gem's own webhook verification primitive: the shop identifier that host applications rely on (`WebhookMetadata#shop`) to route data to the correct tenant/session is not covered by the cryptographic check the gem performs. A host app that trusts `Registry.process`'s HMAC validation as proof that "this event genuinely belongs to shop X" is not correctly protected — an attacker who legitimately receives a signed webhook for their own store can splice a different `shop-domain` header onto that same signed body and have it accepted as authentic for another tenant, leading to cross-tenant data confusion in the application layer built on top of this gem.

### Likelihood Explanation
Requires only that the attacker control one legitimate shop that has the target app installed (a normal, unprivileged action — creating a Shopify dev/partner store is free and requires no special access), and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-controlled headers. No access token, `client_secret`, or leaked credential is needed since the attacker reuses a genuinely-issued HMAC.

### Recommendation
Include the tenant/event identity in the signed material actually verified by the gem, or explicitly document and enforce that `shop`/`topic` from the webhook headers are advisory only and callers must independently verify `shop` against the session/store the message claims to belong to before trusting it. Concretely, extend `Request#to_signable_string` (or add a secondary constant-time comparison) to bind `shop-domain` and `topic` to the verified HMAC context, e.g. by requiring the host app to compare `request.shop` against an out-of-band known session shop after `HmacValidator.validate` succeeds, and by rejecting requests whose `shop` was not part of the cryptographic proof.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook: body `B`, headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(secret, B)` (per `Request#to_signable_string`, only `B` is signed).
2. Attacker resends the identical body `B` and HMAC `H` to the app's webhook endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because `shop` was never part of the signed bytes: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes attacker-controlled data as if it were an authentic event for the victim tenant.
