Audit Report

## Title
CORS Origin Allowlist Wildcard Subdomain Bypass via Improper Suffix Matching - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` implements wildcard CORS origin matching (e.g. `*.remix.com`) using a bare `strings.HasSuffix(originHost, allowedHost)` check without enforcing a dot boundary before the matched suffix. As a result, any attacker-registered domain that merely ends with the configured suffix string (e.g. `evilremix.com` for an allowlisted `*.remix.com`) is treated as an authorized subdomain.

## Finding Description
The wildcard branch of `isAllowedOrigin` strips the `*.` prefix from the configured allowlist entry and then does a raw suffix comparison: [1](#0-0) 

`strings.HasSuffix` has no concept of domain-label boundaries, so `originHost = "evilremix.com"` satisfies `strings.HasSuffix("evilremix.com", "remix.com")` even though `evilremix.com` is an entirely different, attacker-controlled domain and not a true subdomain of `remix.com`. This is the same bug class as CVE-2024-0753 (HSTS subdomain bypass from imprecise suffix matching).

This function directly gates whether `Access-Control-Allow-Origin` is set to reflect the requester's `Origin` header in `handleRequest`, the entry point for all traffic to the gateway's public HTTP endpoint: [2](#0-1) 

No other origin-boundary check exists in the exact-match branch (`originHost == allowedHost`, line 181) or elsewhere in the function, so the suffix flaw is unmitigated whenever a wildcard entry is configured.

Separately, actual authorization of gateway requests (message signatures / Bearer JWT extracted explicitly from the `Authorization` header) is independent of CORS and is not ambient browser-supplied credential (no cookie-based session was found), which limits — but does not eliminate — the practical exploitability of this specific bug: a cross-origin browser page from an attacker-controlled domain sharing the configured suffix would still incorrectly receive a permissive `Access-Control-Allow-Origin` reflection, in violation of the operator's intended origin scoping, whenever such ambient/browser-managed credentials (e.g., cookies, or credentials the browser attaches automatically) are or become in use.

## Impact Explanation
The finding is a genuine, precisely-located logic bug: `isAllowedOrigin`'s wildcard suffix matching (`core/services/gateway/network/httpserver.go` lines 184-190) fails to enforce a `.`-boundary, allowing any domain sharing a suffix with a configured wildcard entry to be incorrectly treated as an authorized subdomain and receive a reflected `Access-Control-Allow-Origin` header. This breaks the intended origin-allowlist security boundary on the gateway's internet-facing HTTP endpoint. However, based on the code reviewed, the gateway's actual request authorization relies on message-level signatures/JWT tokens explicitly attached by the client rather than ambient browser credentials (cookies) that are automatically sent cross-origin, which constrains the concrete, demonstrable impact of this specific bypass beyond the CORS header itself.

## Likelihood Explanation
Exploitation only requires an operator to configure a wildcard `CORSAllowedOrigins` entry (a supported, documented feature) and an attacker to register/control any domain sharing that suffix — both low-cost and requiring no privileged access to the node. This is directly reachable via a normal HTTP request specifying a crafted `Origin` header.

## Recommendation
Enforce a dot-boundary check in the wildcard match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```
This ensures `originHost` must equal the base domain or end with `.` + the base domain, preventing suffix-only matches like `evilremix.com` against `remix.com`.

## Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. Send an HTTP request to the gateway's endpoint with header `Origin: https://evilremix.com`.
3. Observe that `isAllowedOrigin` computes `allowedHost = "remix.com"` and `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, causing the response to include `Access-Control-Allow-Origin: https://evilremix.com`.
4. This can be verified with a Go unit test directly calling `httpServer.isAllowedOrigin("https://evilremix.com")` against a config with `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting it incorrectly returns `true`.

	if s.config.CORSEnabled {

		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
