### Title
Emporium min-path `runAction` executes unconstrained external calls that move Emporium's own ERC20 balance with zero accounting - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose circuit only constrains `message == Poseidon(messageSeed)`, `timeStamp`, and `calldataHash` — nothing about token amounts, roots, or nullifiers. Combined with an `EmporiumStack.signerAddress == address(0)`, `EmporiumUpgradeable.verifyWallet` returns immediately with no signature check at all, letting an attacker submit an arbitrary `ops` array executed as `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own address, while the balance-accounting loop in `runAction`/`Hinkal.transact` iterates zero elements and enforces nothing.

### Finding Description
The claimed invariant is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter` (and Hinkal's post-call balance/slippage loop)*.

Trace:
- `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` [1](#0-0) . When `erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, it selects `formInputEmporiumMin`, whose public input array is only `[emporiumMessage, timeStamp, calldataHash]` [2](#0-1) . `VerifierEVMMin0v4` confirms `inputAmount = 3` [3](#0-2) , i.e. no root hash, nullifiers, token addresses, or amount changes are constrained by the proof.
- `Hinkal.transact` still calls `rootHashExists(circomData.rootHashHinkal, ...)`, but since the circuit never uses `rootHashHinkal`, the attacker can pick any historical valid root — this check is meaningless for the min path [4](#0-3) .
- `_externalTransact` iterates `erc20TokenAddresses` (length 0), so no funds are pulled from/sent to the caller, and calls `EmporiumUpgradeable.runAction` [5](#0-4) .
- Inside `runAction`, `balancesBefore`/`balancesAfter` are computed over the (empty) `erc20TokenAddresses` array, so the post-loop `balanceChange` checks never execute for any token [6](#0-5) .
- `verifyWallet(stack, circomData)` is called before the ops loop. With `stack.signerAddress == address(0)`, it marks the message used and returns immediately — no signature, deadline, or `maxFee` check is performed [7](#0-6) .
- The ops loop then executes `op.endpoint.call{value: op.value}(op.callData)` for every op since `stack.signerAddress != address(0)` is false, taking the "Stateless Interaction" branch — the only restriction is that the selector isn't `callHinkalWallet`/`doSendToRelay` [8](#0-7) .
- Back in `Hinkal.transact`, the post-execution slippage/balance-equation loop also iterates `circomData.erc20TokenAddresses` (length 0), so it enforces nothing either [9](#0-8) .

Root cause: the "min" proof and the empty-token-array accounting path were designed for operations that don't touch Hinkal/Emporium-tracked balances, but nothing prevents an attacker from setting `signerAddress == 0` (removing all wallet-signature guarantees) while still supplying arbitrary `ops` that call `op.endpoint.call(...)` — e.g., `IERC20(token).transfer(attacker, amount)` — executed with `msg.sender == Emporium`. Any ERC20 balance actually held by the Emporium contract (leftover deposits, fee-token dust, tokens sent to it, or funds momentarily routed there) can be moved out with zero accounting, zero signature check, and a proof that only requires knowledge of a self-chosen Poseidon preimage.

**One caveat on the question's framing**: `HinkalWrapper` only wraps `prooflessDeposit` (it has no function that forwards to `Hinkal.transact` or Emporium) [10](#0-9) . The "routed through HinkalWrapper's fee settlement first" detail in the question does not apply to this attack; the exploit is reachable directly via `Hinkal.transact` without any `HinkalWrapper` hop.

### Impact Explanation
An attacker can drain any ERC20 balance the Emporium contract holds at the time of the call, to an address of their choosing, with no signature verification and no on-chain accounting constraint. This is theft of any protocol/relay/user funds sitting in Emporium's balance — matching Critical: direct theft of shielded or in-flight user funds. It is repeatable each time Emporium holds a nonzero token balance and a fresh, unused `emporiumMessage` value is used (attacker fully controls the message and its Poseidon preimage).

### Likelihood Explanation
Preconditions: Emporium contract must hold a nonzero ERC20 balance (this can occur from leftover dust, mis-sent tokens, or funds transiently routed through Emporium during other flows). Attacker cost is a single transaction with a self-generated trivial min-circuit proof (proving knowledge of a self-chosen Poseidon preimage) and a crafted `EmporiumStack` with `signerAddress == address(0)` and `erc20TokenAddresses == []`. No privileged role, no other user's key, and no dependency on `HinkalWrapper` is required, making this highly feasible for any unprivileged attacker.

### Recommendation
- Do not allow the min-circuit/empty-token path to bypass wallet signature verification: require `stack.signerAddress != address(0)` (or otherwise cryptographically bind `ops`) whenever `erc20TokenAddresses.length == 0`, or disallow arbitrary-target `ops` entirely on that path.
- Make the accounting invariant independent of `erc20TokenAddresses.length`: track and validate balance changes for every token actually touched by `stack.ops` (e.g., derive touched tokens from `op.endpoint`/`op.callData` or require them to be declared and included in `erc20TokenAddresses`), not just the tokens the caller chooses to declare.
- Constrain `rootHashHinkal`/nullifiers even in the "min" circuit input, or otherwise ensure the min-path proof cannot be satisfied independent of any real UTXO/authorization state.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as registered `HINKAL_EMPORIUM_ACTION_ID` external action), a mock ERC20 `TKN`.
2. Fund Emporium directly with `TKN.transfer(emporiumAddress, 1000e18)` to simulate leftover/protocol balance.
3. Generate a real min-circuit proof (`VerifierEVMMin0v4`) for `emporiumMessage = Poseidon(seed)` with attacker-chosen `seed`, `timeStamp`, `calldataHash` matching `CircomDataBuilder.getHashedCalldata`.
4. Build `CircomData` with `erc20TokenAddresses = []`, `externalActionData = {externalAddress: emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: address(TKN), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))}], maxFee: 0, deadline: type(uint256).max}) }`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from attacker EOA.
6. Assert: `TKN.balanceOf(attacker)` increases by `1000e18` and `TKN.balanceOf(emporiumAddress)` goes to `0`, while `balancesBefore`/`balancesAfter` arrays inside `runAction` were both empty (length 0) and no `require` in `Hinkal.transact`'s balance-equation loop or `EmporiumUpgradeable.runAction`'s `balanceChange` check ever executed — demonstrating the equality "assets moved == assets accounted for" is broken (nonzero moved, zero accounted).
