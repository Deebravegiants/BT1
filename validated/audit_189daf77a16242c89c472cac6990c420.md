### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` only checks the HMAC over `to_signable_string` [3](#0-2) , so the `shop-domain` header is never bound to the signature. `Registry.process` trusts `request.shop` and hands it to the handler as the tenant identity after only verifying the body HMAC [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop authenticated by HMAC == shop the handler acts on`. Instead, the HMAC only authenticates the byte content of `@raw_body`; the `shop-domain` header used to construct `WebhookMetadata` (and passed to `handler.handle`) is completely outside the signed data. Because `Context.api_secret_key` is a single app-wide secret shared across every merchant/shop that installs the app (not a per-shop secret), any attacker who is themselves a merchant (or otherwise obtains) a legitimately signed `(raw_body, hmac)` pair for one shop can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. `HmacValidator.validate` will still succeed because it never inspects the header, and `Registry.process` will invoke the app's handler with `shop: <attacker-controlled value>` alongside a valid-looking signature [5](#0-4) .

### Impact Explanation
Any downstream app logic that uses `WebhookMetadata#shop` to decide which merchant's data/session/tenant to act on (a very common pattern for multi-tenant Shopify apps) can be tricked into associating attacker-supplied webhook content with a victim shop, or into believing a fabricated event originated from a shop it did not — a cross-tenant confusion/spoofing condition. This satisfies the "cross-tenant access" impact criterion since the shop identity supplied to app code is unauthenticated while wrapped in an apparently-valid signature.

### Likelihood Explanation
Exploitation requires only unprivileged capability that is normal for any developer using the Shopify platform: the attacker installs the target app on a shop they control (or otherwise gets a legitimately signed body/HMAC), captures a valid `(raw_body, hmac)` pair from their own store's real webhook delivery, and replays it to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account beyond a normal store owner/developer account is needed, and the flaw sits entirely within this gem's own `Webhooks::Request`/`Registry` code (not host-app misuse), so it is in scope and realistically reachable.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or otherwise validate that the shop performing the delivery matches an app-expected/registered shop (e.g., compare against a per-shop secret, or require the caller to independently confirm `request.shop` via a trusted registration/session record) before trusting it in `WebhookMetadata`. At minimum, document prominently that `request.shop` is not authenticated by the HMAC so integrators do not rely on it as a trust boundary — but the safer fix is to include shop/topic in the signable string check or require server-side shop allow-listing.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; Shopify delivers a webhook to the app with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `B` and the HMAC value.
3. Attacker sends `raw_body: B`, headers `{"x-shopify-hmac-sha256" => <same value>, "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-topic" => "<same topic>"}` directly to the app's webhook endpoint.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-computes the HMAC over `B` [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <parsed B>, ...)` [5](#0-4) , letting the attacker inject content attributed to a shop they do not control.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
