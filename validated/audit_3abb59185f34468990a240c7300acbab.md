### Title
Permanent market freeze from aggregate RAY-value overflow during interest accrual - (File: common/src/rates/index.rs)

### Summary
A large, highly utilized market can grow until its aggregate scaled balance multiplied by an interest index exceeds `i128::MAX`, after which every accrual panics and the market can no longer process `repay`, `withdraw`, `liquidate`, `update_indexes`, or related operations. [1](#0-0) 

### Finding Description
An unprivileged user can create and own an account with `supply(caller, 0, spoke_id, assets)`, supply an extremely large amount of a high-decimal borrow asset, add sufficient collateral, and call `borrow(caller, account_id, [(hub_asset, amount)], None)` to push the market to approximately 98% utilization. [2](#0-1)  The borrow path is permitted only if the remaining cash covers the 2% liquidation buffer and the configured utilization cap allows the draw. [3](#0-2) 

Every pool mutation loads the market through `ops::load_leg`, which calls `synced_market`, and `synced_market` always invokes `interest::global_sync` before the requested operation. [4](#0-3)  `global_sync` does not mark the market accrued until all accrual chunks complete. [5](#0-4) 

Accrual multiplies total scaled borrow and supply balances by their respective indexes: `calculate_supplier_rewards` evaluates `borrowed * old_borrow_index` and `borrowed * new_borrow_index`, while `update_supply_index` evaluates `supplied * old_index`. [6](#0-5) [7](#0-6)  `Ray::mul` reports `MathOverflow` when the resulting aggregate RAY value cannot fit in `i128`. [8](#0-7)  The configured index ceiling is `1e36`, but aggregate balances can be large enough for the value calculation to overflow far below that ceiling. [9](#0-8) 

`Controller::update_indexes` is callable by an authorized caller and forwards the selected `HubAssetKey` list to the pool. [10](#0-9)  The pool's `update_indexes` then calls `ops::market::accrue`, which loads the market and invokes `global_sync`. [11](#0-10) [12](#0-11)  Once the aggregate value crosses the `i128` boundary, that call panics before `mark_accrued`, so the same overflow is attempted again by the next call. [13](#0-12) 

### Impact Explanation
This permanently freezes all funds in the affected market: supplier withdrawals call `load_leg` and accrue first, borrower repayments call `load_leg` and accrue first, and liquidation withdrawals use the same path. [14](#0-13) [15](#0-14)  Even changing the pool's rate model cannot recover the market because `replace_rate_model` commits a synced cache before writing the new model. [16](#0-15) 

### Likelihood Explanation
The attack requires a market whose configured supply and borrow caps admit enough exposure for `scaled_balance * index` to exceed `i128::MAX`, plus enough collateral to open the borrow and sustained utilization until the index reaches the overflow point. [17](#0-16) [18](#0-17)  For an 18-decimal asset, one billion whole tokens upscale to `1e36` RAY, so the aggregate value reaches the roughly `1.7e38` `i128` limit when the relevant index passes approximately 170×, well before the `1e36` index ceiling. [19](#0-18) [9](#0-8) 

The checked-in regression test constructs this state with `principal = 1e9 * 10^18`, borrows 98%, advances accrual until `update_indexes` fails with `MathOverflow`, and verifies that subsequent withdraw and repay attempts fail with the same error. [20](#0-19) 

### Recommendation
Enforce a market-level aggregate RAY-value limit that is below `i128::MAX` for both `supplied * supply_index` and `borrowed * borrow_index`, rather than relying on the `1e36` index ceiling and asset-unit caps. [6](#0-5)  Entry paths should reject a new supply or borrow when the post-operation scaled total leaves insufficient headroom for subsequent index multiplication. [18](#0-17) 

Accrual should also clamp the effective index to the largest value representable for the market's aggregate scaled balance before evaluating total value, while still advancing `last_timestamp` so a saturated market does not repeatedly trap. [13](#0-12)  Recovering an already frozen market requires a code upgrade or another migration path because every existing pool operation accrues before performing the requested mutation. [21](#0-20) 

### Proof of Concept
1. Using a listed 18-decimal borrow asset `BIG` and a separate collateral asset `COL`, call:
   `supply(attacker, 0, spoke_id, [(BIG, 1_000_000_000 * 10^18)])`. [22](#0-21) 
2. On the same owned account, supply enough `COL` and call:
   `borrow(attacker, account_id, [(BIG, 980_000_000 * 10^18)], None)`. [23](#0-22) 
3. Leave the market at sustained high utilization until `borrowed * borrow_index` or `supplied * supply_index` exceeds `i128::MAX`. [24](#0-23) [25](#0-24) 
4. Call:
   `update_indexes(attacker, [HubAssetKey { hub_id, asset: BIG }])`. [10](#0-9) 
5. The call panics with `MathOverflow`; because `last_timestamp` was not advanced, later `withdraw`, `repay`, `liquidate`, and `update_indexes` calls for `BIG` repeat the same failing accrual. [13](#0-12) [26](#0-25)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)
