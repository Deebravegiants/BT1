### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw body only, while the shop domain, topic, webhook id and API version are all taken directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then passes those unauthenticated header values straight into the `WebhookMetadata` object delivered to the host app's handler, without ever binding them to the signature it just verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers via `shopify_header`, entirely outside the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., only `@raw_body`), and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The equality this design implicitly promises is: `HMAC-verified(body)` == `HMAC-verified(shop, topic, webhook_id, body)`. In reality only the body half is checked, so the tenant-identifying `shop` header is never bound to the signature that authenticates the request.

Because the app's `api_secret_key` is shared across every shop that installs the app, any attacker who can install the app on their own store (an unprivileged, self-service action) will legitimately receive real webhooks with a valid `X-Shopify-Hmac-Sha256` value computed over a body they control (e.g. by placing an order to trigger `orders/create`, or triggering `app/uninstalled`/`customers/redact`). The attacker can capture that `(body, hmac)` pair and replay it directly to the merchant app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because the body/HMAC pair is untouched, and `Registry.process` will hand the app's handler a `WebhookMetadata` claiming the event belongs to the victim shop: [5](#0-4) 

The gem's own documentation shows handlers keying downstream, per-tenant work off `data.shop` (e.g. enqueuing a job scoped to `shop_domain: data.shop`), confirming that `shop` is treated as a trusted tenant identifier by consumers of this API: [6](#0-5) 

### Impact Explanation
This breaks the identity binding between the cryptographically-verified payload and the tenant (`shop`) it is attributed to, letting an unprivileged attacker who merely installs the app on their own store forge webhook deliveries that the host application will process as originating from an arbitrary victim shop. Depending on the handler's use of `data.shop` (session/token lookup, GDPR data deletion via `customers/redact`/`shop/redact`, revoking access on `app/uninstalled`, etc.), this is a cross-tenant integrity/action attack: the app performs tenant-scoped side effects (deleting data, invalidating sessions, mutating records) for a shop the attacker does not control, using data the attacker fully controls (the forged body).

### Likelihood Explanation
Moderate-to-high: the only prerequisite is installing the target app on any shop the attacker controls (a normal, unprivileged action for any Shopify merchant/developer), and the ability to POST directly to the app's registered webhook callback URL with custom headers — no `api_secret_key`, access token, or other privileged credential is required, and no TLS interception is needed.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content (or otherwise cryptographically bind them, e.g. by deriving `shop` only from a value embedded in the signed body, or by re-verifying `shop` against the shop that owns the specific `webhook_id` through a server-side lookup) rather than trusting them from unauthenticated headers once the body-only HMAC check passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a real webhook (e.g., `orders/create`) and capture the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` value `H` — this is a valid `(B, H)` pair for the app's shared `api_secret_key`.
3. Replay a POST to the merchant app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (only `B`/`H` are checked, per `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/utils/hmac_validator.rb`), and `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: B, ...)`, causing the app to act as if `victim-shop.myshopify.com` sent this webhook.
