### Title
Unchecked-length `copy_from_slice` panic in BEEFY `Vote`→`SignatureWithAuthorityIndex` conversion reachable from a signed `submit_proof` extrinsic - ([File: evm/rust/src/conversions.rs])

### Summary
`impl From<Vote> for SignatureWithAuthorityIndex` in `evm/rust/src/conversions.rs` copies an attacker-controlled, variable-length ABI `bytes` field into a fixed 65-byte array with `copy_from_slice` and no length check, unlike every other conversion in this file which correctly returns errors or uses `try_into()`.

### Finding Description
`evm/rust/src/conversions.rs` defines the Solidity-ABI-to-Substrate conversions used when a `BeefyConsensusProof` (NAIVE proof type) submitted to `pallet-beefy-consensus-proofs` is decoded and converted into `beefy_verifier_primitives::ConsensusMessage`: [1](#0-0) 

```
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);
        ...
```

`Vote.signature` is an ABI `bytes` field (arbitrary length, fully attacker-controlled since it comes from `abi_decode_params` on raw proof bytes), yet it is copied directly into a fixed `[u8; 65]` array without first checking `sig_bytes.len() == 65`. `copy_from_slice` panics on any length mismatch.

This is reached from `pallet_beefy_consensus_proofs::Pallet::verify_and_apply`, which decodes the `PROOF_TYPE_NAIVE` payload via `ismp_abi::ecdsa_beefy::BeefyConsensusProof::abi_decode_params` and converts it with `.into()`: [2](#0-1) 

```
types::PROOF_TYPE_NAIVE => {
    let abi_proof =
        <ismp_abi::ecdsa_beefy::BeefyConsensusProof as SolType>::abi_decode_params(
            abi_payload,
        )
        .map_err(|_| Error::<T>::AbiDecodeFailed)?;
    let scale_proof: beefy_verifier_primitives::ConsensusMessage = abi_proof.into();
```

The `From<BeefyConsensusProof> for ConsensusMessage` → `From<RelayChainProof> for MmrProof` → `value.signedCommitment.votes.into_iter().map(Into::into).collect()` chain (all in the same `conversions.rs`) eventually calls the vulnerable `From<Vote>` impl for every vote in the submitted proof: [3](#0-2) 

This is the exact bug class described in CVE-2017-11362: an unbounded/unvalidated attacker-supplied length is used to write into a fixed-size buffer, causing a crash rather than a graceful rejection. In this codebase every sibling conversion (`block_number.try_into().expect(...)`, `validator_set_id.try_into()...`, etc.) uses `try_into()` which is length-checked, and this is the one path that instead uses a raw, unchecked `copy_from_slice`. Notably, the codebase already contains numerous fixes for exactly this pattern elsewhere (e.g. `modules/utils/serde/src/lib.rs` `as_utf8_string`, `parachain/node/fisherman/src/lib.rs` `consensus_state_id_from_str`, `modules/ismp/core/src/host.rs` `StateMachine::from_str`) with comments explicitly noting that unchecked `copy_from_slice` on untrusted input caused a production node crash — confirming this exact bug class is a known, previously-exploited crash vector in this codebase, and this call site was missed.

### Impact Explanation
`submit_proof` on `pallet-beefy-consensus-proofs` is callable by any signed account (permissionless proof submission, rewarded on success but not gated by any privileged role). A malicious signer can submit a NAIVE BEEFY proof whose ABI-encoded `votes[i].signature` is not exactly 65 bytes. When the runtime processes the extrinsic, `copy_from_slice` panics. A panic inside runtime/WASM execution is a much more severe failure mode than a returned `DispatchError` — it can abort block execution, trip the executor's unwind/abort path, and in native-execution configurations can crash the node process outright. This directly threatens the "route unable to deliver messages" / halted-consensus-verification class of impact called out in scope (denial of service against the BEEFY consensus update path used to finalize/deliver ISMP messages), consistent with the Critical DoS severity of the source CVE.

### Likelihood Explanation
High. The vulnerable code is reached with a single, permissionless, signed extrinsic (`submit_proof`) and only requires crafting an ABI `bytes` field of a length other than 65 — a trivial malformation, no cryptographic material or special privileges needed. The `AbiDecodeFailed` check only validates that the outer ABI structure decodes; it does not validate the length of nested `bytes` fields such as `signature`.

### Recommendation
In `evm/rust/src/conversions.rs`, change `impl From<Vote> for SignatureWithAuthorityIndex` to a fallible conversion (`TryFrom`) that checks `sig_bytes.len() == 65` and returns an error (propagated as `AbiDecodeFailed`/`VerificationFailed`) instead of panicking, mirroring the length checks already used for `block_number`, `validator_set_id`, etc. in the same file. Audit the rest of `evm/rust/src/conversions.rs` for any other unchecked `copy_from_slice`/fixed-array writes from ABI-decoded `bytes` fields and apply the same treatment.

### Proof of Concept
1. Craft a `BeefyConsensusProof` ABI payload where `relay.signedCommitment.votes` contains one `Vote` entry whose `signature` field is, e.g., 64 or 66 bytes (any length ≠ 65) instead of the required 65-byte ECDSA signature. All other fields can be arbitrary/well-formed enough to pass `abi_decode_params`.
2. Prefix the payload with `PROOF_TYPE_NAIVE` (`0x00`) as required by `verify_and_apply`.
3. Submit via `BeefyConsensusProofs::submit_proof(origin, proof)` from any signed account.
4. Execution reaches `abi_proof.into(): ConsensusMessage` → `...MmrProof` → `Vote::into(): SignatureWithAuthorityIndex`, where `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, aborting extrinsic/block execution instead of returning `Error::<T>::AbiDecodeFailed`.
