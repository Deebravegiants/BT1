## Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers to route and process the payload. Because those identity-bearing headers are not part of the signed material, an attacker who can obtain any single valid `(raw_body, hmac)` pair — trivially available by triggering a real webhook on their own, legitimately installed shop — can replay that exact body/HMAC pair while swapping the `shop-domain` (and/or `topic`) headers to point at a victim shop, and the library will accept and process it as if Shopify genuinely reported that event for the victim's tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read directly from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the body-based HMAC, then immediately trusts `request.shop` and `request.topic` (both header-derived, unsigned values) to select the handler and construct `WebhookMetadata` that is dispatched to app code: [3](#0-2) 

The equality this breaks: `bytes verified by the HMAC` should equal `bytes (headers) acted upon to determine tenant/event identity`, but here `verified bytes = raw_body` while `acted-upon identity = headers{shop-domain, topic, webhook-id}`, which are disjoint from the signed material.

### Impact Explanation
Any actor with a legitimate app installation on their own store (i.e., any merchant who can install the target app, which is normally an unprivileged action) can capture a real `(raw_body, hmac-sha256)` pair from a webhook Shopify sends them, then directly POST that same body/HMAC to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to name a different, victim shop. Because `Registry.process` never checks that the header-derived shop/topic are consistent with anything cryptographically verified, the app's webhook handler executes believing the event legitimately originated from the victim shop. Depending on how the host application's handler uses `WebhookMetadata#shop`/`#topic` (e.g., updating billing state, disabling the app, mutating per-shop data keyed by `shop`), this allows cross-tenant data manipulation — an attacker-controlled tenant forging state changes attributed to a victim tenant.

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the app on a store they control (a routine, unprivileged action for any Shopify app that isn't tightly gated), since:
- No access to `api_secret_key`, access tokens, or any victim credentials is required.
- The attacker only needs one genuine webhook delivery to their own shop to obtain a valid `(body, hmac)` pair.
- Replaying the request with modified headers is a simple direct HTTP POST to the app's public endpoint; nothing in this gem's `HmacValidator`/`Registry.process` path rejects header/body mismatches.

### Recommendation
Bind the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) into the value that is authenticated, or otherwise cryptographically verify that the delivered `shop`/`topic` match the shop/topic the HMAC-protected body actually pertains to. At minimum, `Registry.process` should reject requests whose `shop`/`topic` cannot be corroborated against a source that is itself covered by the signature (e.g., include these fields in the signable string, or independently verify the shop against a known, previously-registered installation before dispatching the handler).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook subscription (e.g., `orders/create`) on that shop; capture the exact raw body `B` and the `x-shopify-hmac-sha256` header value `H` that Shopify sends (valid because `H = HMAC-SHA256(secret, B)`).
3. Send a direct HTTP POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid because `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` only checks the body)
   - Header `x-shopify-shop-domain`: `victim.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged or forged to another registered topic
4. `ShopifyAPI::Webhooks::Registry.process` accepts the request (`Utils::HmacValidator.validate(request)` passes because it only checks `B` against `H`), and dispatches to the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
