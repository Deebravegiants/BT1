### Title
Unchecked arbitrary calls in `EmporiumUpgradeable.runAction` allow draining any token balance/approval held by the Emporium contract that the attacker omits from `erc20TokenAddresses` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` only measures the balance-preservation invariant (`balanceChange == -deltaAmountChanges` after ops run) for the tokens listed in the attacker-supplied `circomData.erc20TokenAddresses` array. Because the ops themselves (`stack.ops`, decoded from attacker-controlled `externalActionMetadata`) can make arbitrary low-level calls from the Emporium contract's own context, an attacker can insert an op that calls `token.transfer(attacker, amount)` (or `transferFrom` against a leftover/persistent approval set by a prior op) for any token simply left off the `erc20TokenAddresses` list, so the invariant is never evaluated for that token and the drained value is never reconciled against `deltaAmountChanges`.

### Finding Description
The invariant the protocol relies on is: *for every token, the net balance change of the action contract during the tx equals `-deltaAmountChanges[i]`* — enforced only inside the loop at [1](#0-0) 

This loop iterates strictly over `circomData.erc20TokenAddresses`, which is attacker-supplied per the question's "Attacker controls" list. `balancesBefore`/`balancesAfter` are captured only for addresses present in that array: [2](#0-1) 

In between those two snapshots, `stack.ops` — fully attacker-controlled via `externalActionMetadata` — are executed. In the stateless branch, the only restriction is that the call's selector is not `callHinkalWallet` or `doSendToRelay`; any other call, including a raw `ERC20.transfer`/`transferFrom`, is permitted and executed with `msg.sender == EmporiumUpgradeable` (or the attacker's own `HinkalWallet` in the stateful branch): [3](#0-2) 

Because a prior Emporium operation (executed by any user, in any transaction) may have left the Emporium contract holding a token balance, or an outstanding `approve()` on some router set on the Emporium's behalf, an unprivileged attacker can:
1. Craft `externalActionMetadata` with a single op whose `endpoint` is the target ERC20 token and `callData = transfer(attacker, residualAmount)` (moves Emporium's own balance directly) or `transferFrom(emporium, attacker, amount)` against a router the Emporium previously approved.
2. Set `circomData.erc20TokenAddresses` to omit that token entirely (or include unrelated tokens only), and set `deltaAmountChanges` for the tokens actually declared to be consistent/zero so `performHinkalChecks`/circuit constraints on the *declared* tokens pass normally.
3. Because the stolen token is never in `erc20TokenAddresses`, `balancesBefore`/`balancesAfter`/`balanceChange` are never computed for it, so `BalanceChangeShouldBePositive` never fires and no accounting ties the theft back to `deltaAmountChanges`.

The circuit and `performHinkalChecks` only constrain the UTXOs/tokens that are part of the proof's public inputs (the declared `erc20TokenAddresses`/`deltaAmountChanges`); they impose no constraint that ops cannot touch *other* tokens, and `runAction`'s on-chain invariant likewise only checks the declared set. Thus `-deltaAmountChanges` (over the declared set) no longer equals total tokens leaving the action (over all tokens actually moved), breaking the stated invariant.

### Impact Explanation
An unprivileged attacker can drain any ERC20 balance or exploit any lingering approval held by the shared `EmporiumUpgradeable` contract (funds parked there from previous users'/relayers' operations, refunds, dust, or persistent router approvals), sending it straight to their own address with a single crafted `runAction` call, with no on-chain check ever comparing it to what Hinkal actually sent them. This is direct theft of protocol/user-parked funds and is repeatable for every token/approval left stranded on the shared Emporium contract, matching the Critical category ("direct theft of shielded or in-flight user funds").

### Likelihood Explanation
The only precondition is that the Emporium contract holds some token balance or outstanding approval left by a prior transaction (a normal and expected occurrence given multi-op sequences, refunds from routers, or partial fills). The attacker needs no privileges — only the ability to deposit their own funds, generate a valid proof for their own UTXOs, and freely craft `externalActionMetadata`, `erc20TokenAddresses`, and `deltaAmountChanges`, all of which are explicitly listed as attacker-controlled. The exploit costs only gas and is repeatable every time residual value exists.

### Recommendation
Do not let `erc20TokenAddresses`/ops scope be attacker-defined without constraint. Either (a) require the circuit/`performHinkalChecks` to bind every token address touched by any op (including tokens targeted by low-level calls) into the public-input/constrained `erc20TokenAddresses` set, or (b) track balances for *all* tokens interacted with during op execution (e.g., via a whitelist of allowed op targets, or by snapshotting balances for a comprehensive/protocol-maintained token registry rather than an attacker-chosen array), or (c) disallow raw `transfer`/`transferFrom`-style calls to arbitrary ERC20 tokens from within stateless ops entirely, restricting ops to a vetted allowlist of endpoints.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, fund it directly with `TOKEN_X.mint(emporium, 1000e18)` to simulate residual/stranded balance from a prior op.
2. As attacker, build `CircomData` with `erc20TokenAddresses = [TOKEN_Y]` (unrelated token, with `deltaAmountChanges[0] == 0`), and `externalActionMetadata` encoding an `EmporiumStack` with one op: `{endpoint: TOKEN_X, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))}`, `signerAddress: address(0)`.
3. Generate a valid proof for the declared (unrelated) UTXO/token set and call `Hinkal.transact` → `EmporiumUpgradeable.runAction`.
4. Assert: `TOKEN_X.balanceOf(attacker) == 1000e18` after the call, while `deltaAmountChanges` for `TOKEN_X` was never declared (equals 0/absent), proving tokens left the action with no corresponding negative `deltaAmountChanges`, i.e. `tokens_leaving_action != -deltaAmountChanges_sent`.
5. Assert the call does not revert with `BalanceChangeShouldBePositive` (confirming the invariant check never covers `TOKEN_X`).
