### Title
Unvalidated swap routes can execute attacker-controlled token transfers under the caller’s authorization - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller accepts caller-supplied `swap` bytes in `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`, then forwards them to the configured router without validating which contracts the route invokes. A malicious route can place attacker-controlled contract code inside the authorized invocation tree and make that code request `caller.require_auth()` indirectly through a token transfer. Simulation records the malicious transfer as a child authorization, and a signature over that tree allows theft of unrelated wallet assets, not just the swap input.

### Finding Description
`swap_collateral` accepts a caller-controlled `swap: Bytes` argument and forwards it through `process_swap_collateral` after caller authentication and account ownership checks. [1](#0-0) [2](#0-1) 

`swap_tokens` passes the same bytes verbatim to the configured aggregator’s `execute_strategy` while the controller is inside the caller’s authorized invocation. [3](#0-2) 

The controller protects only its own input balance and measured output; it does not constrain route-selected external calls. [4](#0-3) 

The same pattern applies to `swap_debt`, which borrows into the controller and passes caller-controlled `swap` bytes to `swap_tokens_or_passthrough`. [5](#0-4) 

`repay_debt_with_collateral` similarly forwards the route after withdrawing collateral to the controller. [6](#0-5) 

The project’s threat model states that the router invokes pool and token addresses named by the payload, maintains no allowlist, and can therefore put third-party code below the caller’s authorization. [7](#0-6) 

### Impact Explanation
A malicious venue can invoke `token.transfer(caller, attacker, amount)` while executing under the caller’s `swap_collateral` authorization tree. [8](#0-7) 

Simulation records that transfer as a sub-invocation of the caller’s controller authorization, even though the stolen token is unrelated to the swap input. [9](#0-8) 

If the signed authorization tree includes that recorded child, the malicious transfer succeeds and drains the unrelated wallet token. [10](#0-9) 

This is theft of user funds beyond the amount intentionally routed through the strategy.

### Likelihood Explanation
Any unprivileged account owner or delegate can reach `swap_collateral`, `swap_debt`, or `repay_debt_with_collateral` with arbitrary route bytes. [11](#0-10) 

The attacker must get the victim to submit or sign a transaction containing the malicious route and its expanded authorization tree, but neither the controller’s output check nor final account risk check bounds unrelated-token transfers made under that tree. [7](#0-6) 

The regression test demonstrates the complete mechanism: an unsigned malicious child fails, while the same child succeeds once included in the signed tree. [12](#0-11) 

### Recommendation
Constrain strategy routes to an allowlisted set of venue contracts and token contracts, or change the execution model so route-selected third-party contracts cannot request authorization attributable to the lending caller.

At minimum, reject authorization trees containing sub-invocations other than the expected strategy token movement, and expose machine-readable route metadata that lets clients verify every external contract before signing.

### Proof of Concept
1. Victim owns a lending account with USDC collateral and holds an unrelated token.
2. Attacker deploys a contract whose `swap` method calls `token.transfer(victim, attacker, unrelated_balance)`.
3. Attacker constructs a `swap_collateral` route that pays a valid amount of the requested collateral but names the malicious contract as a hop.
4. Victim calls:
   ```text
   controller.swap_collateral(
       caller = victim,
       account_id = victim_account,
       current = USDC hub asset,
       amount = collateral_amount,
       new = ETH hub asset,
       swap = malicious_route,
   )
   ```
5. Simulation records a child `transfer(victim, attacker, unrelated_balance)` under the victim’s `swap_collateral` authorization. [13](#0-12) 
6. Signing that tree executes both the apparently fair collateral swap and the unrelated-token theft. [14](#0-13)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
