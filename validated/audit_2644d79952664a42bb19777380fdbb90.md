### Title
Front-running `Initialize2` allows an attacker to seize a not-yet-created pool PDA and set an unfair initial price, extracting value from subsequent depositors and swappers - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` (the analog of Uniswap V3's `initialize`) has no access control restricting who may call it, and the resulting pool price is derived entirely from the attacker-chosen `init_pc_amount`/`init_coin_amount` supplied in the instruction, not from any market-derived reference price. Because the AMM PDA and all associated vault/mint accounts are deterministically derived only from the `market` account and the program ID, any party can watch for a pending pool-creation transaction, front-run it with their own `Initialize2` call using minimal capital and a heavily skewed ratio, and claim the deterministic pool address first.

### Finding Description
`process_initialize2` derives the pool's `AmmInfo`, LP mint, coin vault and pc vault accounts via `generate_amm_associated_account` / `generate_amm_associated_spl_mint` / `generate_amm_associated_spl_token`, all seeded only by `market_info.key` and `program_id`: [1](#0-0) 

The instruction is permissionless — the only signer check is that `user_wallet_info.is_signer`, with no requirement that the caller be a specific privileged deployer or that the price match any oracle/market reference: [2](#0-1) 

The initial pool "price" and LP supply are computed purely from the caller-supplied `init.init_pc_amount` and `init.init_coin_amount`, transferred straight from the caller's own token accounts into the newly created vaults: [3](#0-2) [4](#0-3) 

Because the PDA is deterministic and derivable by anyone who knows the `market`, `coin_mint`, and `pc_mint` (all public, predictable prior to the legitimate creator's transaction landing), an attacker observing a pending `Initialize2` transaction in the mempool can front-run it with the same accounts but a small, extremely skewed `init_pc_amount`/`init_coin_amount` ratio, since the only floor check is that the resulting `liquidity - 10^lp_decimals` be positive (`InitLpAmountTooLess`): [5](#0-4) 

Once the attacker's transaction lands, the pool for that `market` already exists (`amm.status != Uninitialized`), so the legitimate creator's own `Initialize2` transaction will fail (`AlreadyInUse`): [6](#0-5) 

Subsequent liquidity providers who call `Deposit` are not protected by any price sanity check against an oracle — `process_deposit` only validates account bindings and signer status, then computes required counterpart deposit amounts from the pool's current (attacker-set) vault ratio: [7](#0-6) 

This is the direct analog of the reported Uniswap V3 issue: an unprivileged actor front-runs the price-setting call on a not-yet-fully-initialized pool, and later liquidity providers (and the program's own economic invariants) are exposed to the skewed price with no recourse, since `Initialize2` has no access control and no market-price validation.

### Impact Explanation
An attacker can claim a pool's deterministic PDA ahead of the legitimate creator with a tiny amount of capital and an arbitrary skewed ratio. Any subsequent `Deposit` calls by liquidity providers who assume the newly created pool reflects fair market pricing will deposit funds at the attacker-controlled ratio, and the attacker can immediately arbitrage this mispricing via `SwapBaseIn`/`SwapBaseOut`, extracting value from the depositors' funds. This constitutes concrete theft of LP funds through insolvent/unfair pool pricing at creation time.

### Likelihood Explanation
Pool creation transactions (`Initialize2`) are broadcast publicly before confirmation and the resulting account addresses are fully deterministic and computable in advance from public inputs (`market`, `coin_mint`, `pc_mint`, program ID), making front-running straightforward for any searcher/attacker monitoring the mempool. The cost to the attacker is minimal since the only constraint is a small positive minted-LP floor.

### Recommendation
- Add an authorization mechanism (e.g., require the pool creator to be a pre-registered/whitelisted account, or bind pool creation to a specific expected creator pubkey passed at request time and checked on-chain) so `Initialize2` cannot be executed by an arbitrary third party for someone else's intended pool.
- Alternatively, validate the initial price against an independent reference (e.g., require depositors to specify an acceptable price range/slippage bound at deposit time relative to the pool's already-set ratio, rejecting deposits when the pool's ratio deviates too far from a caller-supplied expected ratio).
- Document clearly that pool creators must verify the pool's ratio immediately after `Initialize2` succeeds before advertising the pool address or before others deposit.

### Proof of Concept
1. Alice constructs an `Initialize2` transaction for a new `market` M, `coin_mint` C, `pc_mint` P, intending a fair ~1:1 ratio, and broadcasts it.
2. Eve observes the pending transaction, computes the same deterministic PDAs from `market_info.key = M`, and submits her own `Initialize2` instruction with the same accounts but `init_coin_amount = 1`, `init_pc_amount = 1_000_000` (or any extreme skew), using only her own minimal token balances, with higher priority fee so it lands first: [3](#0-2) 
3. Eve's transaction succeeds, creating the pool at the deterministic address with an unfair price; Alice's transaction then fails with `AmmError::AlreadyInUse`: [6](#0-5) 
4. A naive liquidity provider (unaware the pool was front-run) calls `Deposit`, which computes required deposit ratio from Eve's skewed vault balances rather than any market reference price: [7](#0-6) 
5. Eve calls `SwapBaseIn`/`SwapBaseOut` against the pool to arbitrage the mispricing introduced by her own initial deposit and the naive LP's subsequent deposit, extracting value.
