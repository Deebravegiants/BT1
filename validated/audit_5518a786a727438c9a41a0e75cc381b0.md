Webhook shop identity is not bound to the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` (invoked from `Registry.process`) authenticates nothing but the body bytes. The `shop`, `topic`, and `webhook_id` values that the handler acts on are read straight from HTTP headers that are never covered by the signature, breaking the binding: `authenticated(body) == acted_on(shop, topic, webhook_id)`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only `@raw_body` is returned. `HmacValidator.validate` computes the HMAC purely from this signable string: [2](#0-1) 
Meanwhile, `Registry.process` uses `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from unsigned headers — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 
The `shop`, `topic`, and `webhook_id` accessors simply read the corresponding HTTP header value with no cryptographic tie to the signed body: [4](#0-3) 

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any user who installs the app on their own store receives genuine `(raw_body, x-shopify-hmac-sha256)` pairs signed by Shopify for their own shop's webhook events. That attacker can then POST that same authentic `(body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` claiming the victim's tenant, even though the payload actually originated from the attacker's own store.

Per the documented handler contract, apps are told to trust `data.shop` as "The shop domain of the webhook" and to key their business logic on it: [5](#0-4) 
An app that (as documented) uses `data.shop` to select the tenant/session context to update (e.g., write/update records keyed by shop) will act on attacker-supplied data attributed to a shop it does not control — a cross-tenant identity break entirely inside the gem's own verification code path (`Registry.process` → `HmacValidator.validate` → `Request#shop`).

### Impact Explanation
This is a cross-tenant integrity issue: an unprivileged internet user who can install the target app on their own (attacker-controlled) Shopify store obtains valid HMAC-signed webhook bodies signed with the app's single shared `client_secret`, and can replay them against the app's webhook endpoint with a forged shop header to inject fabricated events attributed to any other merchant using the app. Since the gem's own `Registry.process`/`HmacValidator` is the only verification boundary and it does not bind `shop`/`topic`/`webhook_id` to the signed content, this crosses the tenant boundary the HMAC is supposed to enforce, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker who is permitted to install the app (a normal, unprivileged path for any public Shopify app), since no privileged credentials, TLS interception, or leaked secrets are needed — only a legitimately obtained webhook payload from the attacker's own shop and control over the headers of the forged HTTP request sent to the app's public webhook endpoint.

### Recommendation
Bind `shop`/`topic`/`webhook_id` to the HMAC verification, e.g.:
- Include the relevant headers (topic, shop-domain, webhook-id, api-version) in the signable string computed by `Request#to_signable_string`, matching what Shopify actually signs, if Shopify's real signing algorithm allows verifying them; or
- Since Shopify's real webhook signature is computed over the raw body only, the gem must instead require/document that consuming apps validate `data.shop` against a known/expected shop (e.g., one with an active registration/session) before trusting it, and the library should expose or enforce this check rather than silently handing over an unauthenticated `shop` value that mirrors the accessor pattern used for authenticated fields elsewhere (e.g. `AuthQuery#to_signable_string`, which does include `shop` in the signed payload) as the safe pattern to follow.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`) for that store.
2. Shopify sends the app a legitimate request: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(shared client_secret, B)`), and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers))`.
5. `Utils::HmacValidator.validate` succeeds (body/HMAC match, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`), and the handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, causing the app to process attacker-controlled data as if it belonged to the victim's tenant.
