### Title
Unguarded `assetReserve - virtualLtReserve` subtraction in `Bonding.canGraduate` / `previewLtUntilGraduation` / `_prepareGraduationLiquidity` permanently bricks trading and graduation via an arithmetic Panic - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The external report is a reachable-assertion bug: `RequestMacroChain::handle` selects a locator based on a *weaker* check ("is on main chain") and then calls a function that assumes a *stronger* invariant ("is a macro block"), `.unwrap()`-panicking when an attacker arranges for the weaker condition to be true while the stronger one is false. `Bonding.sol` has the same shape: three call sites compute `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` assuming the *stored* `assetReserve` can never fall below the launch-time virtual LT reserve floor, but the actual on-chain invariant guaranteeing that is enforced only via `Pair.swap`'s "+1" K-slack rounding tolerance — a weaker, rounding-tolerant check, not an exact one. If a trader can round-trip the curve down to a state where stored `assetReserve` is even 1 wei below `_launchTimeVirtualLtReserve`, every subsequent read of this subtraction reverts with a Solidity arithmetic Panic (0x11), and unlike the sibling code in `finalizeGraduation` (which the authors explicitly hardened with a saturating subtract "to keep finalize from bricking on a Panic"), these three call sites were never given the same defensive treatment.

### Finding Description
`Bonding.canGraduate` performs an unchecked, non-saturating subtraction: [1](#0-0) 

The same pattern recurs in `previewLtUntilGraduation`: [2](#0-1) 

and in `_prepareGraduationLiquidity` (invoked by phase‑1 `_enterGraduating`): [3](#0-2) 

All three assume `assetReserve >= _launchTimeVirtualLtReserve(token_, pair)` unconditionally. The codebase's own documentation states this floor is a mathematical identity derived from `Pair.k()` staying fixed and swaps only moving reserves along the constant-product curve, and the team is clearly aware this class of arithmetic-Panic bug is reachable: the sibling code path in `finalizeGraduation` was deliberately patched with a saturating subtraction specifically to avoid this: [4](#0-3) 

That comment ("a balance below `p.ltFromPair` shouldn't be reachable in normal operation, but we keep finalize from bricking on a Panic if any future code path... violates the invariant") is a direct acknowledgment that the "invariant always holds" assumption is not something the authors are willing to bet the whole function on — yet exactly that assumption is left unguarded in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity`.

Crucially, `canGraduate` is not a passive view called only off-chain — it is invoked automatically inside every buy: [5](#0-4) 

and inside the permissionless `triggerGraduation`: [6](#0-5) 

The only enforcement mechanism for the "stored `assetReserve` floor" invariant is `Pair.swap`'s K-invariant check, which the project's own scope notes call out as containing a `+1` rounding slack (per the task's mapped attack surface: "`Pair.swap`'s `+1` K slack"). A rounding-tolerant invariant check is precisely the kind of "weaker" guarantee the nimiq analog exploits: the K-check only guarantees `newReserve0 * newReserve1 >= K - slack`, not an exact floor on `assetReserve` alone. A sequence of small sells that repeatedly lands on the rounding-favorable side of that `+1` slack can walk the stored `assetReserve` down past the exact `virtualLtReserve_init` floor by a small integer amount while `reserve0` is still capped at `TOTAL_SUPPLY` — a state the exact-floor identity documented in `_launchTimeVirtualLtReserve`'s NatSpec assumes is impossible.

### Impact Explanation
Once stored `assetReserve` for a given curve is pushed even 1 wei below `_launchTimeVirtualLtReserve(token, pair)` by a sell (a plain, unprivileged `Bonding.sell`/`Zap.sell` call, which does not itself invoke `canGraduate`), the corrupted state is committed on-chain. Every subsequent call that reaches `canGraduate` — i.e. every future `buy` via `Zap.buy`/`Bonding.buy` (through `_executeBuy`) and every call to `triggerGraduation` — will now revert with an arithmetic Panic instead of executing. This permanently bricks:
- All future buys on the affected curve (the `_executeBuy` call always ends by invoking `canGraduate`).
- Permissionless graduation (`triggerGraduation` also calls `canGraduate` first).

Because trading and graduation are both permanently frozen for that token, the 750M real curve tokens and all LT already raised on that curve become permanently unreachable — they can never be sold into HyperSwap via graduation, and buyers can no longer participate. This is a permanent freezing of trader and creator funds tied to that bonding curve, matching the required impact bar.

### Likelihood Explanation
The trigger requires only unprivileged `sell` calls (`Zap.sell` → `Bonding.sell` → `Router.sell` → `Pair.swap`) chosen to land on the rounding-favorable side of the K-check's documented `+1` slack, repeated enough times to walk `assetReserve` 1 wei below the exact virtual floor. No privileged role, no upgrade, and no off-chain component is needed — any address holding curve tokens (obtained via ordinary buys) can attempt this. The exact number of rounding-favorable transactions needed depends on the K-check's rounding direction in `Pair.swap`, which was not independently re-derived here; confidence is Medium because the precise rounding arithmetic of `Pair.swap`'s `+1` slack was not verified line-by-line in this pass, but the complete absence of a saturating guard at three call sites — despite an explicit, deliberate fix for the identical pattern elsewhere in the same file — is a directly confirmed root-cause defect regardless of exactly how many sell transactions are needed to reach the underflow.

### Recommendation
Apply the same saturating-subtraction pattern already used in `finalizeGraduation` (`ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0`) to `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity`: compute `realLtRaised = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0` in all three places. Additionally, tighten `Pair.swap`'s K-check rounding so `assetReserve` can never legitimately fall below `virtualLtReserve_init`, removing the root cause rather than only the symptom.

### Proof of Concept
1. Launch a token via `Zap.createToken` with a seed buy (curve initialized, `Pair.k()` fixed).
2. As an unprivileged trader, execute a sequence of small `Zap.sell` calls sized to repeatedly land on the rounding-favorable branch of `Pair.swap`'s K-invariant check (the `+1` slack), each time nudging stored `assetReserve` down without pushing `reserve0` back to exactly `TOTAL_SUPPLY`, until `assetReserve` is 1 wei below `_launchTimeVirtualLtReserve(token, pair) = Pair.k() / Token.TOTAL_SUPPLY()`.
3. Call `Bonding.buy` (via `Zap.buy`) on the same token, or call `Bonding.triggerGraduation(token)` directly.
4. Observe the transaction revert with a Solidity Panic (`0x11`, arithmetic underflow) from `canGraduate`'s `assetReserve - _launchTimeVirtualLtReserve(...)` line.
5. Repeat step 3 with any other address/any other buy amount — every future buy and every `triggerGraduation` call on this token reverts identically, permanently freezing the curve's tokens and raised LT.
