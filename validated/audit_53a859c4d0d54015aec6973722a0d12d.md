### Title
Webhook `shop-domain` header is trusted as the tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop-domain` header — the value the gem hands to app code as the authoritative tenant identifier — is excluded from the signed bytes. Any party that can obtain one genuine, HMAC-valid webhook delivery for their own shop (every merchant who installs the app receives these) can replay the identical body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value, and `ShopifyAPI::Webhooks::Registry.process` will accept it as valid and dispatch it to the app's handler labeled with the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, and — on success — immediately builds `WebhookMetadata` using `request.shop` as the trusted tenant identifier passed to the app's handler, with no additional check binding the header to the signed content: [3](#0-2) 

`HmacValidator.validate` only compares `verifiable_query.hmac` against an HMAC computed from `verifiable_query.to_signable_string`, i.e. the body bytes, using the app's single, shop-independent `api_secret_key`: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no relation enforced to the HMAC-covered content, and is documented as the tenant identifier apps use to route/attribute webhook data: [5](#0-4) 

The broken identity binding, stated as an equality that the gem fails to enforce:
`bytes verified by HMAC (== @raw_body only)` ≠ `shop identity acted upon (== request.shop, an unsigned header)`.

Because every shop that installs the app shares the same `api_secret_key`, and Shopify webhook HMACs are computed the same way for every shop, any installed merchant can capture one of their own legitimate webhook deliveries (body + valid HMAC), then send a forged HTTP request directly to the app's public webhook endpoint with the same body/HMAC but an arbitrary `shop-domain` header value naming a different, victim shop. `Registry.process` will report a valid HMAC (the body wasn't modified) and hand the attacker-chosen `shop` straight to the app's `WebhookHandler#handle`.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an unprivileged merchant of Shop A can cause the app to process a webhook payload as if it originated from Shop B. Depending on how the host app uses `WebhookMetadata#shop` (commonly used as a lookup/storage key for the tenant's records, or to gate the effect of mandatory webhooks like `app/uninstall`, `shop/redact`, `customers/redact`), this enables cross-tenant data injection or cross-tenant state mutation attributed to a shop the attacker does not own and never authorized. This matches the "cross-tenant access" Critical-impact category: the gem itself fails to bind the identity value it hands to application code to the bytes it actually verified.

### Likelihood Explanation
Any merchant who installs the app is, by design, sent genuine webhooks with valid HMACs for their own shop — no credential theft, TLS interception, or privileged access is required. The webhook receiving endpoint is by necessity internet-reachable and unauthenticated apart from the HMAC check. Replaying a captured body+HMAC pair with a modified header requires only basic HTTP tooling, making this readily reachable by any unprivileged tenant of a multi-tenant app built on this gem.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signable/verifiable content for webhook requests, or independently verify that `request.shop` corresponds to a shop the app expects to receive this specific webhook_id/topic for (e.g., cross-check the topic+webhook_id against records created when the webhook was registered for that shop) before handing it to `WebhookHandler#handle`. At minimum, document prominently that `WebhookMetadata#shop` is not itself HMAC-verified and must not be trusted as an identity boundary by host applications without additional validation.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's endpoint with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body `B`.
2. The merchant operating `shop-a` (an unprivileged actor with respect to `shop-b`) captures this raw body `B` and its valid HMAC value.
3. The attacker sends a new HTTP request directly to the app's public webhook receiver with the same body `B` and the same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present); `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` (unchanged) and it matches, so validation succeeds:
```ruby
Registry.process(request) # request.shop == "shop-b.myshopify.com", hmac still valid
```
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ..., ...))`, causing the app to process attacker-supplied data attributed to `shop-b`, even though `shop-b` never sent this webhook and the payload originated from `shop-a`.
