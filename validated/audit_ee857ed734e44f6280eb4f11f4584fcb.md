## Analysis

The core vulnerability class in the report is a *missing binding* between a value the code trusts and the cryptographic proof that's supposed to authenticate it. The strongest analog in this gem is in the webhook‑processing flow, where the HMAC only covers the request body, while the `shop`, `topic`, `api-version`, and `webhook-id` fields — read from unauthenticated HTTP headers — are handed to the app's handler as if verified.

### Title
Webhook `shop`, `topic`, and other identifying fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed in `ShopifyAPI::Webhooks::Registry.process` proves nothing about the `shopify-shop-domain`, `shopify-topic`, `shopify-api-version`, or `shopify-webhook-id` headers. These header-derived fields are passed straight into the handler's `WebhookMetadata` and trusted as the identity of the originating shop/topic. Any HTTP body/HMAC pair captured for one shop (which is trivial to legitimately obtain — an attacker merely needs to install the app on their own store and trigger a webhook, since it's the *same* app `client_secret` for every installation) is a valid `(body, hmac)` pair regardless of which `shop` header accompanies it, because the header is never part of the signed content.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all parsed from headers that are entirely outside that signed string: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only that the *body* was HMAC'd with the app's secret) and then dispatches the handler using the unverified `request.shop`, `request.topic`, etc.: [4](#0-3) 

This breaks the intended identity binding: **shop authenticated by the HMAC (none — the HMAC authenticates only the body/secret pair) ≠ shop delivered to the application handler (`request.shop`, taken from an attacker-controllable header)**. Because the app's `client_secret` (and therefore HMAC key) is identical across every shop that installs the app, a valid `(body, hmac)` pair obtained from one tenant (the attacker's own shop) remains a "valid" signature no matter what `shop`/`topic`/`webhook-id` headers are attached to it when replayed.

### Impact Explanation
An unprivileged internet user who has merely installed the app on their own Shopify store (a routine, unprivileged action) can capture a legitimately-signed webhook body/HMAC pair from their own store, then replay that exact body to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to an arbitrary victim shop domain (and/or the topic/webhook-id headers changed). `Registry.process` will accept it as valid because the HMAC only ever checked the body content, and the handler will process attacker-controlled data as if it originated from, and belongs to, the victim shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the victim's session/access token, update the victim's local records, or trigger tenant-specific side effects), this constitutes cross-tenant data injection / cross-tenant access — the impact classified as Critical (cross-tenant access) in the rubric.

### Likelihood Explanation
Likelihood is high: the exploit requires no special privileges beyond installing the app on the attacker's own store (which any merchant can do), no leaked secrets, and no host cooperation beyond correctly using the documented `Registry.process` / `WebhookMetadata` API exactly as intended by this gem. The attacker fully controls the headers of the HTTP request to the app's webhook endpoint, since headers are never covered by the signature.

### Recommendation
Include the identifying headers (`shop`, `topic`, `api_version`, `webhook_id`) in the signed payload verification, or otherwise cryptographically bind them to the HMAC-verified body (e.g., derive/validate the shop from the body payload itself where Shopify includes it, or require the host application to cross-check `request.shop` against a known/allow-listed set of installed shop domains before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be trusted as tenant identifiers without additional server-side verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving:
   - raw body `B`
   - header `x-shopify-hmac-sha256: H` (valid, since it's `HMAC(app_secret, B)`)
   - header `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker resends this exact `(B, H)` pair to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally the topic/webhook-id headers).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes `HMAC(app_secret, B)` and compares to `H` — unaffected by the header change: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, and the host application processes it as a legitimate event for the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
