Confirmed: the `WebhookMetadata.shop` field is passed to app handlers (`ShopifyAPI::Webhooks::WebhookMetadata` at `lib/shopify_api/webhooks/webhook_handler.rb:6-12`) and is populated straight from `request.shop`, which reads the `x-shopify-shop-domain` header, while the HMAC signature that gates `Registry.process` only covers the raw request body.

### Title
Webhook `shop` (tenant) identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Request#to_signable_string` method that feeds the HMAC computation returns only `@raw_body` [2](#0-1) . However, the `shop` value delivered to the app's `WebhookHandler#handle` callback (`WebhookMetadata.shop`) is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is not part of the signed content at all [3](#0-2) .

### Finding Description
The identity binding that should hold is:
```
HMAC-verified bytes == bytes the handler treats as tenant identity
```
Here it does not: `raw_body` is HMAC-verified, but `shop` (the tenant identity used by the handler) is taken from an unauthenticated header [3](#0-2) . `Registry.process` passes this unverified `shop` straight into `WebhookMetadata`, which is the only tenant-identifying field the host application's handler receives [1](#0-0) [4](#0-3) .

Because the app's `client_secret`/webhook signing secret is shared across all shops that install the app (it is not per-shop), any merchant that installs the app receives their own legitimately HMAC-signed webhooks. Since the HMAC covers only the body and never the `shop-domain` header, that same attacker-controlled merchant can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and will still succeed, because the check never binds `shop` to the signature [5](#0-4) . The handler then executes business logic (e.g., updating order/customer/inventory data, triggering mandatory-topic actions like `customers/redact`) believing the data belongs to the victim shop, when it actually originates from the attacker's own shop and content.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an authenticated (as far as the gem's API is concerned) webhook can be attributed to an arbitrary shop chosen by the sender. This falls into the "cross-tenant access" Critical category since the `shop` value is the tenant selector used by any host application built with this gem's documented webhook API, and the vulnerability is entirely inside the gem's `HmacValidator`/`Request`/`Registry` code path, not a misuse by the host app.

### Likelihood Explanation
Any shop that installs the app (an "unprivileged" party relative to other tenants of the same app) can generate valid `(raw_body, hmac)` pairs for themselves by triggering ordinary store events, then replay them with a modified `shop-domain` header using nothing but a standard HTTP client. No access to the app's `api_secret_key` or any victim credentials is required.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`) header values in the HMAC-signable string, or otherwise independently verify that the `x-shopify-shop-domain` header matches a shop the app has installed/expects for that specific webhook, rather than trusting it purely because the body-only HMAC passed.

### Proof of Concept
1. Register the app on Shop A (attacker-controlled) and Shop B (victim), sharing the same app `client_secret`.
2. Trigger any subscribed webhook event on Shop A; capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it only signs `raw_body`.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body` [2](#0-1) ; `Registry.process` invokes the handler with `shop: "shop-b.myshopify.com"` [6](#0-5) , causing Shop A's data/event to be processed as if it belongs to Shop B.
