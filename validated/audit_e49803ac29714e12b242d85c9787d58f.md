I found a valid analog. `CallDispatcher.sol` is an unprivileged, permanently-shared singleton contract that mints/unlocks bridged tokens and native ETH directly to itself (per the HFT/WrappedHFT and IntentGateway `data` calldata flow), and it exposes `receive() external payable {}` but has no function whatsoever to withdraw stray/leftover native ETH — exactly the `donateETH()`-with-no-withdraw pattern from the report.

### Title
Native ETH sent to or stranded in `CallDispatcher` can never be recovered or withdrawn - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` accepts arbitrary native ETH via `receive()` and is the designated recipient/executor for cross-chain token+calldata flows (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`), but the contract has no owner, no admin, and no withdrawal function of any kind for native ETH left in its balance.

### Finding Description
`CallDispatcher` declares `receive() external payable {}` [1](#0-0)  so it can accept native ETH transfers. Its only other function is `dispatch(bytes memory encoded)`, which decodes a `Call[]` array and forwards `call.value` amounts of its own held balance to each `call.to` target [2](#0-1) . There is no `withdraw`, `sweep`, `rescue`, `owner`, or `restrict` mechanism anywhere in the contract, and `ICallDispatcher` only defines `dispatch` [3](#0-2) .

`CallDispatcher` is documented and used as the destination for unwrapped native ETH in cross-chain flows: `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` unwrap WETH to native ETH and deliver it to the `to` address, which application docs explicitly instruct callers to set to the `CallDispatcher` address so it can forward the ETH via `Call.value` to a router [4](#0-3) . `IntentGatewayV2` also routes predispatch/postdispatch calldata (potentially carrying native value) through the same `CallDispatcher` [5](#0-4) .

Any of the following leaves native ETH permanently stuck in `CallDispatcher` with zero recovery path:
- Direct/accidental ETH transfers to the contract (accepted unconditionally by `receive()`).
- A `dispatch()` call whose `Call[]` forwards less value than the ETH actually delivered/unwrapped to the dispatcher for that operation (e.g. rounding, partial swap outputs, or a caller-supplied `Call.value` that under-forwards the amount).
- Any `CallFailed` revert path notwithstanding, once ETH does land in the contract's balance without being spent by a subsequent `dispatch()` call, there is no function callable by anyone — user, relayer, or governance — to move it out.

This is structurally the same defect as the OptimismPortal `donateETH()` finding: a contract intentionally designed to hold native value has no corresponding withdrawal path, so any balance is permanently unrecoverable.

### Impact Explanation
Because `CallDispatcher` is a single shared, non-upgradeable utility contract referenced by multiple production apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`) across chains, any native ETH that accumulates in it (leftover dust from swaps, under-specified `Call.value` amounts, or direct transfers) is permanently and irrecoverably locked — a real loss of funds with no governance or admin override available, unlike `EvmHost`, which exposes a governance-gated `withdraw()` for exactly this purpose [6](#0-5) .

### Likelihood Explanation
`CallDispatcher.dispatch()` is invoked on every cross-chain transfer that includes calldata, and native ETH forwarding through `Call.value` is an explicitly documented, encouraged pattern (e.g. "the CallDispatcher holds the unwrapped ETH and forwards it via Call.value") [7](#0-6) . Any mismatch between ETH delivered to the dispatcher and ETH consumed by the encoded calls — which is entirely caller-controlled and not validated by the contract — results in stuck funds, making this readily reachable through normal, unprivileged usage rather than a contrived edge case.

### Recommendation
Add a permissioned (or even permissionless-to-original-depositor) sweep/withdraw function to `CallDispatcher` that allows recovery of any residual native ETH (and stray ERC20 tokens) left in the contract after a `dispatch()` call, similar to the dust-sweeping mechanisms already present in `IntentGatewayV2` (`SweepDust`) and `EvmHost.withdraw()`.

### Proof of Concept
1. An application (e.g. `WrappedHyperFungibleTokenUpgradeable.onAccept`) unwraps WETH and transfers native ETH to `to = CallDispatcher` per the documented pattern, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)` [8](#0-7) .
2. The attacker/user crafts `message.data` so that the encoded `Call[]` array's `call.value` sums to less than the ETH amount delivered to the dispatcher (e.g. a single call with `value: 0` performing an ERC20-only action), or simply sends ETH directly to `CallDispatcher` via its `receive()`.
3. `dispatch()` succeeds; the leftover ETH remains in `CallDispatcher`'s balance.
4. No function in `CallDispatcher` (or any other contract) can extract that ETH — it is permanently locked, exactly mirroring the `donateETH()` scenario in the reported OptimismPortal issue.

## Calldata

Orders support arbitrary calldata execution at two points in the lifecycle — before escrow (predispatch) and after fill (postdispatch). Both are executed through the `CallDispatcher` contract, which takes an ABI-encoded `Call[]` array:

```solidity
struct Call {
    address to;      // Target contract (must have code, reverts with NotContract otherwise)
    uint256 value;   // ETH to send with call
    bytes data;      // Calldata to execute
}
```

The `CallDispatcher` executes each call sequentially and reverts the entire batch if any call fails.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
