### Title
Division-before-multiplication precision loss in `VWAPOracle.recordSpread` corrupts the cumulative spread oracle - (File: evm/src/utils/VWAPOracle.sol)

### Summary
`VWAPOracle.recordSpread` computes a per-fill spread in basis points via division, then immediately multiplies that truncated value back by the same volume figure to produce the "weighted spread" it accumulates. This is the same anti-pattern flagged in the external report (dividing before multiplying instead of multiplying before dividing), and it discards precision that a correct implementation would retain exactly.

### Finding Description
In `recordSpread`, for each same-token input/output pair:
```solidity
int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
...
int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
_updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);
``` [1](#0-0) 

Mathematically, `weightedSpread` should equal `amountDiff * BPS_DENOMINATOR` exactly — the division by `inputAmountNormalized` to get `spreadBps` and the subsequent multiplication by the same `inputAmountNormalized` are inverse operations that cancel out algebraically. Instead, the code performs the division first (Solidity integer division truncates toward zero), then re-multiplies the truncated `spreadBps` by `inputAmountNormalized`, permanently losing up to `inputAmountNormalized - 1` units of precision (scaled by the truncation in the bps division) on every single fill. This loss accumulates into on-chain storage (`weightedSpreadSum`, `totalVolume`) via `_updateCumulativeSpread` [2](#0-1) , and is read back by `spread()`, which divides the cumulative sum by cumulative volume to report the oracle's tracked spread [3](#0-2) .

`recordSpread` is gated only by `restrict(_intentGateway)` [4](#0-3) , meaning the IntentGateway itself calls it on every same-token order fill — the inputs (`inputs[i].amount`/`outputs[i].amount`) originate from the order and the solver's fill amounts, values an unprivileged solver controls when constructing and filling an order. Every fill through the gateway therefore feeds attacker-influenced amounts into this precision-lossy accumulator.

### Impact Explanation
The precision loss corrupts the VWAP oracle's cumulative spread tracking for every same-token pair on every fill. Because a solver controls `outputs[i].amount` (the amount they choose to fill with) and `inputs[i].amount` (from the order), they can shape many small fills to repeatedly exploit the truncate-then-rescale step, skewing `weightedSpreadSum`/`totalVolume` away from the true aggregate spread over time. Since `IIntentPriceOracle` is wired as `priceOracle` in the gateway's parameters (per `evm/src/apps/intentsv2/IntentsBase.sol` and the gateway params struct), a corrupted spread value is the kind of oracle state that governance/pricing logic downstream may rely on, meaning this is a real, unbounded, protocol-level unsound-state-commitment issue rather than a one-off rounding dust of at most 1 wei (the report's bug class). This satisfies the "unsound state commitment" acceptance criterion for a Medium-severity analog.

### Likelihood Explanation
High likelihood of triggering the precision loss: it occurs on **every** same-token fill through `IntentGatewayV2`/`recordSpread`, requiring no special conditions beyond a normal fill of a same-token order pair, which is a standard, permissionless action available to any solver.

### Recommendation
Compute `weightedSpread` directly as `amountDiff * int256(BPS_DENOMINATOR)` (multiplication only, no intermediate division), and only divide by `totalVolume` once, at final read time in `spread()`. If `spreadBps` must be reported per-fill (e.g., for the `SpreadRecorded` event), keep that division separate from the value that's accumulated into `weightedSpreadSum`, so the stored sum stays exact rather than double-rounded.

### Proof of Concept
Given `inputAmountNormalized = 99_999_999_999_999_999` (1e18-scale) and `outputAmountNormalized = 100_000_000_000_000_000` (a 1 wei-per-1e18 spread):
- `amountDiff = 1`
- Correct exact weighted spread: `amountDiff * BPS_DENOMINATOR = 10_000`
- Buggy path: `spreadBps = (1 * 10_000) / 99_999_999_999_999_999 = 0` (truncates to zero)
- `weightedSpread = 0 * 99_999_999_999_999_999 = 0`

The true contribution (`10_000`) is silently discarded to `0` on this fill, and the same shape of loss recurs on every fill where the bps-scaled diff is smaller than the input volume — an amount fully controllable by the filling solver.
