### Title
Webhook shop identity is not covered by the HMAC, allowing cross-tenant shop-domain spoofing on webhook delivery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop`, `topic`, `api-version`, and `webhook-id` values are read from unauthenticated HTTP headers and passed downstream to the registered handler as trusted identity data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC solely against that signable string [2](#0-1) . Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled directly from HTTP headers with no cryptographic binding to the signed payload [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., the body signature) before dispatching to the handler using `request.topic` and constructing `WebhookMetadata` with `request.shop` [4](#0-3) . There is no check that the `shop-domain` header is consistent with anything covered by the signature.

This breaks the identity-binding equality the rules describe as "a field acted on but not covered by the HMAC": the gem treats `verified(raw_body)` as equivalent to `authenticated(shop, topic, raw_body)`, but only the former is true. Concretely: `HMAC_valid(body) != HMAC_valid(shop ∧ body)`.

This directly mirrors the referenced report's bug class — a value (`amounts[i]` for ERC721 / here, the `shop-domain` header) is not covered by the check that gates the security-relevant action (`amounts[i] > 0` reclaim check / here, the HMAC signature check that gates trusting the payload as belonging to a given shop), so the value can be manipulated independently of the verified data.

### Impact Explanation
Any Shopify merchant (an unprivileged party from the perspective of another tenant) with a legitimately installed app receives real, correctly-HMAC-signed webhook deliveries for their own shop. Because the shop-domain header is not part of the signed bytes, that same body+HMAC pair remains "valid" if replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to name a different, victim shop. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop [5](#0-4) . Any host application that uses `data.shop` to select which tenant's session/store the payload applies to (the documented and expected usage pattern) will process attacker-controlled data under the wrong tenant identity — i.e., cross-tenant data confusion/injection using a genuine signature obtained from the attacker's own store.

### Likelihood Explanation
Requires only: (1) the attacker holds a legitimate account/app installation on their own shop (trivial, self-service on Shopify), (2) the ability to capture their own valid webhook deliveries and replay them to the target app's public webhook URL with a modified `shop-domain` header — an ordinary unauthenticated HTTP POST, no secret material needed. No TLS interception, no leaked credentials, no privileged account on the victim's side required.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the value bound by the HMAC verification, or independently verify that the `shop-domain` header corresponds to a shop with an active, known installation/session before trusting it, rather than trusting it purely because the body-only HMAC passed. At minimum, document/require that consuming applications must cross-check `data.shop` against a stored session before acting on webhook contents, since `Registry.process` currently provides no such binding itself [6](#0-5) .

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`). Shopify sends a POST with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the shared `api_secret_key`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and `X-Shopify-Topic: orders/create`.
2. Attacker captures this raw body and HMAC value unmodified.
3. Attacker replays the same body + same HMAC header to the app's public webhook receiver, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unmodified) body against the (unmodified) HMAC [8](#0-7) .
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's order payload, `body: request.parsed_body` [5](#0-4) , even though the data never originated from or was authorized by the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
