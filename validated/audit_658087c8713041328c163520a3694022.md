### Title
RAY index accrual overflows and permanently freezes a saturated market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

Interest accrual multiplies stored RAY-scaled shares by the borrow or supply index before applying the index ceiling, so a sufficiently large high-utilization market can overflow `i128` before `MAX_BORROW_INDEX_RAY` is reached. [1](#0-0)  Once the product no longer fits, `scaled_to_original` propagates `GenericError::MathOverflow` through `Ray::mul` into the accrual path. [2](#0-1) [3](#0-2) 

### Finding Description

Every pool leg calls `load_leg`, which synchronizes the market through `global_sync` before performing the requested operation. [4](#0-3)  `global_sync` calls `accrue_step`, which first computes `borrowed * borrow_index` and `supplied * supply_index` as RAY values. [5](#0-4) [6](#0-5)  Although `update_borrow_index` caps the resulting index at `MAX_BORROW_INDEX_RAY`, that cap is applied only after the already-overflowing position-value multiplication. [7](#0-6)  The repository’s long-horizon test demonstrates that a one-billion-whole-token market at 98% utilization reaches the RAY-value ceiling before the index cap and then fails with `MATH_OVERFLOW`. [8](#0-7) 

An unprivileged attacker can create the prerequisite state with ordinary calls: `Controller::supply(caller, 0, spoke_id, [(hub_asset, amount)])` to seed the market, and `Controller::borrow(caller, account_id, [(hub_asset, debt)], to)` to push it to high utilization. [9](#0-8)  A later permissionless `Controller::update_indexes(caller, [hub_asset])` call forces accrual and triggers the overflow when enough ledger time has elapsed. [10](#0-9) [11](#0-10) 

### Impact Explanation

After the overflow threshold is crossed, withdrawals, repayments, liquidations, further borrows, index updates, and other market legs all run accrual first and revert on the same `MathOverflow`. [12](#0-11) [13](#0-12)  Supplier principal, borrower collateral backing that market, and unclaimed yield become unavailable through the normal contract paths, while bad debt cannot be liquidated or cleaned up. [14](#0-13)  Without a privileged code change or other administrative rescue path, this is a permanent freeze of all funds and obligations in the affected market. [15](#0-14) 

### Likelihood Explanation

The attack does not require privileged calls at execution time, but it requires a listed market whose caps admit an extremely large position and enough real token liquidity to seed and borrow it. [16](#0-15) [17](#0-16)  It also requires sustained high utilization and enough elapsed time for the index to grow to the overflow point; the included regression test reaches the cliff only after repeated yearly advances. [18](#0-17)  Because the attacker’s initial supply remains locked in the frozen market, exploitation is costly, but the consequences affect every user of that market rather than only the attacker. [8](#0-7) 

### Recommendation

Bound RAY-denominated position values, not merely indexes, before accrual. In `accrue_step`, use a non-panicking checked product for `borrowed * borrow_index` and `supplied * supply_index`; on overflow, cap or chunk the represented value before reward calculation, and make the corresponding index ceiling engage without reverting. [19](#0-18)  At minimum, cap `borrowed` and `supplied` share totals at `i128::MAX / index` before index updates and document/enforce that limit at every minting boundary. [20](#0-19)  Add regression coverage proving that `update_indexes`, `repay`, `withdraw`, and `liquidate` continue operating at the bound rather than failing inside `scaled_to_original`. [8](#0-7) 

### Proof of Concept

The existing test constructs an 18-decimal market, supplies `1_000_000_000 * 10^18` base units, borrows 98% of it, advances time in one-year intervals, and observes `MATH_OVERFLOW` from `update_indexes`; subsequent one-unit withdrawal and repayment attempts fail with the same error. [21](#0-20) 

```rust
// Attacker-controlled, after the asset and collateral markets are listed.
let market = HubAssetKey { hub_id, asset: debt_asset };
let principal = 1_000_000_000i128 * 10i128.pow(18);
let debt = principal / 100 * 98;

controller.supply(attacker, 0, spoke_id, vec![env, (market.clone(), principal)]);
// Supply sufficient collateral in another listed market on the same account.
controller.borrow(attacker, account_id, vec![env, (market.clone(), debt)], None);

// After enough ledger time for index growth:
controller.update_indexes(attacker, vec![env, market.clone()]);
// Expected: Error(Contract, MATH_OVERFLOW)

controller.repay(attacker, account_id, vec![env, (market.clone(), 1)]);
controller.withdraw(attacker, supply_account_id, vec![env, (market, 1)], None);
// Both also accrue first and fail with MATH_OVERFLOW.
```

This sequence uses only public controller operations; the precondition is that the deployment’s caps and asset liquidity permit the required position size. [22](#0-21)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);

            years <= 40,

            LegDirection::Entry {
                asset_decimals: result.asset_decimals,
            },
            &LegOutcome::from(&result),
            cache,
        );
