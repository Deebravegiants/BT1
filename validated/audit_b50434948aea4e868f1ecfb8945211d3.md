### Title
Webhook shop/topic/webhook-id identity fields are trusted while unsigned by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are pulled straight from unauthenticated HTTP headers. This breaks the intended identity binding of `shop-authenticated == shop-processed`, allowing an attacker who possesses one genuinely-signed webhook body (which any merchant can obtain simply by installing the app on their own store and triggering a webhook) to relabel that request as belonging to a different shop.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

All the fields that identify *which tenant* the webhook is for are read from headers that are not part of the signed message: [2](#0-1) 

`Registry.process` validates only the body HMAC, then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

The equality the library is implicitly supposed to guarantee is:
`shop that the HMAC over the bytes actually authenticates == shop the application acts on (request.shop)`

Because the HMAC covers only `@raw_body`, this equality does not hold: an attacker can take a validly-signed body (e.g., HMAC computed by Shopify with the app's real `client_secret` for a webhook delivered to the attacker's own store) and resend it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header pointing at a victim shop. `Utils::HmacValidator.validate` in `Registry.process` still succeeds because it only checks the raw body bytes against the secret, so the handler executes believing the event originates from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handlers receive `WebhookMetadata` whose `shop` field is fully attacker-controlled despite the request passing HMAC verification. Any app logic that keys behavior off `data.shop` (billing state changes, uninstall/GDPR handling, data deletion, shop-scoped cache invalidation, etc.) can be triggered against a shop the attacker does not own, using a signature that was never generated for that shop. This matches the Critical "cross-tenant access" impact category, since it lets one merchant's genuinely-signed webhook traffic be reattributed to another merchant's tenant scope.

### Likelihood Explanation
Any unprivileged internet user can install the target app on their own development/trial store (standard, unprivileged action), causing Shopify to deliver a legitimately HMAC-signed webhook body to the app. The attacker only needs to replay that exact body to the app's public webhook endpoint with modified `shop-domain`/`topic`/`webhook_id` headers — no access to `api_secret_key`, access tokens, or any privileged credential is required, and the HMAC check as implemented cannot detect the header substitution because those fields are never part of `to_signable_string`.

### Recommendation
Include the identity-critical fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify them against a value embedded in the payload, or require the app to cross-check `request.shop` against a shop the app already has an active session/install record for) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook subscription/event, causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the app's real `client_secret`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and identical `x-shopify-hmac-sha256: H` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — identical to `B` — and succeeds: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, even though that shop never authorized or sent this webhook, demonstrating the broken `shop-authenticated == shop-processed` binding.
