### Title
Webhook HMAC only signs the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` proves nothing about which shop, topic, or webhook id the payload is associated with. `request.shop`, `request.topic`, and `request.webhook_id` are read straight from unauthenticated HTTP headers and passed to the handler unchecked.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (== `@raw_body`) and checks it against the `hmac-sha256` header using the app's `api_secret_key`: [1](#0-0) [2](#0-1) 

However, the `shop`, `topic`, and `webhook_id` values used downstream are taken directly from request headers (`shop-domain`, `topic`, `webhook-id`) that are **not** part of the signed content: [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(shop ‖ topic ‖ body)` bound to the specific tenant. Instead the actual check is only `hmac == HMAC(body)`, i.e. `shop` (and `topic`/`webhook_id`) are "acted on but not covered by the HMAC" — precisely the class of binding failure the report describes for `l2SystemContractsUpgradeBlockNumber` (a value used to make a security-relevant decision without being re-validated/re-bound at the point of use).

Since a single app-wide `api_secret_key` is used for **all** shops that install the app (not a per-shop secret), any body content that produces a valid signature for one shop's real webhook produces an equally valid signature when replayed with a different `shop-domain` header. An attacker who controls (or has legitimately received) one valid `(body, hmac)` pair — e.g., by installing the app on their own store and triggering any webhook whose body they influence, or one with a fixed/empty body — can resend that exact body and HMAC to the app's webhook endpoint while spoofing the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to name a victim shop. `Registry.process` will accept it as valid and dispatch it to the handler tagged with the victim shop: [4](#0-3) 

### Impact Explanation
This breaks the shop/tenant boundary: an unprivileged actor who merely installs the target app on their own store can forge webhook events that the app's `WebhookHandler` will process as if they came from a different, arbitrary merchant (`WebhookMetadata#shop`). Depending on what the host app's handlers do with `data.shop` and `data.body` (e.g., updating shop records, revoking/rotating credentials, writing customer data, honoring GDPR/data-request or `app/uninstalled` events), this can lead to cross-tenant data injection/corruption attributed to a victim shop — meeting the "cross-tenant access" Critical bar in scope.

### Likelihood Explanation
Likely for any app that (a) has at least one webhook topic with attacker-controllable or predictable body content (many topics carry data the subscribing merchant themselves control, e.g. `products/update`, `orders/create` on the attacker's own store), and (b) trusts `WebhookMetadata#shop`/`#topic` from the gem without extra validation, as the gem's own documentation and API present `shop` as already-authenticated. No secret, token, or privileged access is required — only the ability to install the app on any store and send a normal HTTP POST to the app's public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the payload before `Registry.process` trusts `request.shop`/`request.topic` for dispatch. At minimum, document/enforce that host applications must independently verify `shop` against their own installed-shop registry before acting on webhook data, since the gem's own HMAC check does not bind it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives a webhook for a topic whose body they can make deterministic or fully control (e.g., trigger `products/update` with a crafted payload, or use a topic whose body is `{}`).
2. Attacker captures the genuine `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`, `X-Shopify-Shop-Domain: attacker.myshopify.com` headers and raw body from the real webhook delivery.
3. Attacker POSTs the exact same raw body and `hmac-sha256` value to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(body)` with the app's single `api_secret_key`, which matches the replayed `hmac`, so `Registry.process` succeeds and invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: attacker_controlled_body, ...)`, as shown in [1](#0-0)  and [5](#0-4) .

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
