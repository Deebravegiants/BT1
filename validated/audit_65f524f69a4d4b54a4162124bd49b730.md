### Title
Webhook HMAC only authenticates the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing shop (tenant) impersonation in `WebhookMetadata` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as fully authenticated once `Utils::HmacValidator.validate(request)` returns `true`, and then forwards `request.shop`, `request.topic`, and `request.webhook_id` to the host application's handler as trusted metadata. However, `HmacValidator.validate` only verifies `Request#to_signable_string`, which is defined as `@raw_body` alone. The `shop`, `topic`, and `webhook_id` values are read straight from unauthenticated HTTP headers and are never included in the HMAC computation. This breaks the intended binding: `hmac == HMAC(secret, body)` is verified, but the application actually needs `hmac` to also vouch for `shop == request.shop`, which it does not.

### Finding Description
`lib/shopify_api/webhooks/request.rb` defines:
```ruby
def to_signable_string
  @raw_body
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def topic
  T.cast(shopify_header("topic"), String)
end
``` [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` gates on this validation, then passes header-derived, unauthenticated `shop`, `topic`, and `webhook_id` values into `WebhookMetadata` as if they were verified:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The binding broken is exactly the pattern flagged in the report: a field that is acted on (`shop`, used by the host app to attribute the webhook to a tenant) is not covered by the HMAC that is supposed to authenticate the whole request. Concretely: the equality the gem should enforce is `hmac == HMAC(secret, shop || topic || webhook_id || body)`, or at minimum the consumer should be told that only the body is signed. Instead only `hmac == HMAC(secret, body)` is checked, while `shop` is taken verbatim from the `X-Shopify-Shop-Domain` header.

Any actor who can install the app on their own store (an unprivileged action any merchant/attacker can perform) can trigger a legitimate webhook delivery for their own shop, capture the exact `(raw_body, hmac)` pair Shopify sent (this hmac is computed with the shared `api_secret_key`, valid for any shop using this app), and replay that same body/hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and even the topic/webhook-id headers) for a victim shop. `HmacValidator.validate` will still succeed because it only checks the untouched body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an app built on this gem cannot distinguish "authentic webhook for shop X" from "authentic webhook body attributed to a forged shop." If the host application uses `data.shop` from `WebhookMetadata` (as the documented API explicitly encourages, since `shop` is exposed as trusted metadata alongside the HMAC-gated `process` call) to look up or write per-tenant records, an attacker can inject data attributed to another merchant's shop, or trigger mandatory-webhook-style side effects (e.g., redaction/data-request flows) against a shop identifier they do not own — a cross-tenant access/write vulnerability rooted entirely in this gem's authentication primitive.

### Likelihood Explanation
Likelihood is high in terms of feasibility for anyone who can install the app (a normal, unprivileged use of the app — no leaked secrets or elevated access needed): the attacker only needs one authentic webhook delivery to their own shop to obtain a `(body, hmac)` pair signed with the shared `api_secret_key`, and can then freely vary the `shop-domain` (and other) headers on replay, since none of them are covered by the signature.

### Recommendation
Include the identity-bearing headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-covered signable string, or otherwise cryptographically bind `shop` to the payload before exposing it in `WebhookMetadata`. At minimum, `Utils::HmacValidator.validate` should not be presented as validating the whole `Request`, and `Registry.process` should not trust `request.shop`/`request.topic` derived purely from unauthenticated headers when forwarding to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
2. Attacker replays the exact same request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (topic/webhook-id can also be altered) while keeping the raw body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed.
4. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes `HMAC(secret, B)` and compares to `H`, both unchanged. [5](#0-4) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host application to process/store the payload as if it legitimately originated from `victim-shop.myshopify.com`. [4](#0-3)
