### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` authenticates nothing but that body against the shared secret. The `shop` (and `topic`/`webhook-id`) values are read straight from HTTP headers and are never included in the signed material, yet `Registry.process` trusts `request.shop` as the authoritative tenant identifier when constructing `WebhookMetadata` and dispatching to the app's handler.

### Finding Description
`Request#hmac` / `#to_signable_string` bind the HMAC only to the raw body: [1](#0-0) 

`shop` is derived purely from a header, entirely outside the signed payload: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` (the raw body) against `verifiable_query.hmac`, and returns a boolean — it never touches `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) as the tenant identity handed to the app's business logic, with no cross-check between the signed body and the unsigned `shop` header: [4](#0-3) 

The binding that should hold is:
`shop_used_by_handler (request.shop, read from x-shopify-shop-domain header)` == `shop_authenticated_by_hmac (none — HMAC only covers raw_body)`

Because the HMAC never binds the `shop` header to the signed body, any attacker who can obtain one valid `(raw_body, hmac)` pair from Shopify — trivially available to any merchant who installs the app on their own store and lets Shopify deliver a real webhook to them — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass (it only checks the body against the secret), and `Registry.process` will hand the app's handler a `WebhookMetadata` claiming the payload belongs to the victim shop: [5](#0-4) 

This is a direct instance of "a field acted on but not covered by the HMAC" — the exact class of bug named in the report, applied to the `shop` identity binding instead of a price oracle value.

### Impact Explanation
This crosses a tenant boundary: an unprivileged merchant (attacker installs the app on their own shop, a normal, unprivileged action) can make the app process attacker-controlled webhook data under a victim merchant's shop identity. Any host application logic keyed off `WebhookMetadata#shop` — such as looking up a shop's session/store to apply a `customers/redact`, `app/uninstalled`, `shop/update`, or inventory-affecting webhook — can be triggered against a shop the attacker does not control, purely because the gem never binds the signed body to the claimed shop. This matches the Critical/High class of "cross-tenant access" defined in scope.

### Likelihood Explanation
Likelihood is high: the only prerequisite is that the attacker's own shop has the app installed (a normal, unprivileged merchant action), letting them capture one genuine `(raw_body, hmac)` pair from a real Shopify-delivered webhook, then replay it with a forged `x-shopify-shop-domain` header. No access to `api_secret_key`, tokens, or any privileged capability is required, and the flow goes through the gem's own documented `Registry.process` entry point exactly as intended by host apps.

### Recommendation
Include the header-derived identity fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the material that is authenticated, or independently verify that the `shop` header matches a shop already known/authorized for the given app installation before dispatching to handlers. At minimum, `to_signable_string` should not be limited to the raw body alone when other unsigned headers are subsequently trusted as identity by `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`), capturing the exact `raw_body` and `x-shopify-hmac-sha256` header value that Shopify computed with the app's real secret.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - Same `raw_body`
   - Same `x-shopify-hmac-sha256`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only and it matches, so validation succeeds.
4. `Registry.process` looks up the `orders/create` handler and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to apply attacker-controlled data under the victim's tenant identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
