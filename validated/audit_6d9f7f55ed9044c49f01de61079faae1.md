Based on the analysis, I've confirmed the vulnerability. The webhook HMAC only signs the raw body, while the `shop`, `topic`, `webhook-id`, and `api-version` fields — which drive tenant attribution and routing — come from unauthenticated HTTP headers.### Title
Webhook `shop` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via HMAC replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` verifies the HMAC solely over that raw body. The `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unsigned headers and passed unchanged into the handler as the trusted tenant/topic identity, breaking the intended binding between "HMAC-verified bytes" and "the shop this webhook is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request` defines: [1](#0-0) 

- `hmac` is decoded from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header.
- `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from other headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) with no cryptographic protection.
- `to_signable_string` returns `@raw_body` only — none of those header fields are part of the signed content.

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the raw body) and compares it to the received HMAC: [2](#0-1) 

`Registry.process` only checks this body HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the data handed to the app's webhook handler: [3](#0-2) 

This reproduces the report's bug class: a field that is *acted on* (here, the `shop` identity used to attribute/process the webhook) is not covered by the integrity check (the HMAC), even though a different field (the body) *is* verified. The equality that should hold — `shop bound by HMAC == shop used for tenant attribution` — does not hold, because HMAC binds only the body bytes, not the shop header.

### Impact Explanation
Because the signature only covers the body, an unprivileged attacker who obtains any single valid `(raw_body, hmac)` pair for a topic that your app processes (e.g., from their own installed test shop, from a public/leaked webhook payload, or from a topic whose body is not tenant-specific/secret) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` will hand the app's handler a `WebhookMetadata` claiming this event came from a shop that never sent it. Depending on how the host app uses `shop` from `WebhookMetadata` (e.g., to look up/update per-tenant records, load a session, or run business logic keyed on shop), this can lead to cross-tenant data confusion or forged events attributed to a shop, which maps to a cross-tenant access impact under the given severity classification.

### Likelihood Explanation
Medium. Exploitation doesn't require the app's `api_secret_key` or an access token — only a legitimately observed `(body, hmac)` pair for some topic, and the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers (both realistic for an "unprivileged internet user," similar to how the oracle report describes an attacker driving updates without special privileges). The severity of the resulting cross-tenant confusion depends entirely on how strongly the host app relies on the gem's `WebhookMetadata#shop`/`topic` without independent verification (e.g., checking that the shop is one it has installed and matches other signed data), which the gem does not enforce or document as unnecessary.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable content, or at minimum document/require verification that `request.shop` matches an expected/installed shop, and give the `HmacValidator` a way to bind the header values instead of only the raw body. At the very least, `to_signable_string` for `Webhooks::Request` should include the same header/body binding that is done for OAuth (`Auth::Oauth::AuthQuery#to_signable_string` includes `shop`, `host`, `code`, `state`, `timestamp`), so the shop attribution is cryptographically tied to the signature, not just carried in a plain header: [4](#0-3) 

### Proof of Concept
1. Register a webhook handler for topic `orders/create` (or any topic whose payload the attacker can observe, e.g. from their own dev shop).
2. Capture a legitimate webhook delivery: raw body `B` and its `x-shopify-hmac-sha256` header `H` (valid HMAC of `B` under the app's `api_secret_key`, computed by Shopify).
3. POST to the app's webhook endpoint with:
   - body `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid because only `B` is signed)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (attacker-chosen, arbitrary)
   - `x-shopify-topic`, `x-shopify-webhook-id` optionally altered too, since they are also unsigned.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `B` against `H`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-supplied `shop`, and invokes the handler as if `victim-shop.myshopify.com` sent this webhook — even though the real sender may be a different shop or the attacker's own script, and the shop value was never authenticated by Shopify's signature.

          received_signature = verifiable_query.hmac
