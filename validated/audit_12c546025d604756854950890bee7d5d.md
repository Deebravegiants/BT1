### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` as plain, unauthenticated HTTP headers, while `to_signable_string` — the value that is actually verified by the HMAC — returns only the raw request body. [1](#0-0)  `Registry.process` accepts the webhook once `Utils::HmacValidator.validate(request)` succeeds, and then forwards `request.shop` (taken straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header) to the app's handler as the tenant identifier, with no additional binding to the signed body. [2](#0-1) 

### Finding Description
The identity binding that should hold is:

`shop_the_HMAC_authenticates == shop_the_handler_acts_on`

In this gem that equality never actually exists, because the HMAC only ever covers the raw JSON body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [3](#0-2) 

and `HmacValidator.validate_signature` compares `compute_signature(verifiable_query.to_signable_string, secret)` (i.e. a signature over the body alone) against the received signature: [4](#0-3) 

Meanwhile `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` are read directly from HTTP headers with no cryptographic tie to the body: [5](#0-4) 

`Registry.process` gates only on the HMAC of the body, then builds `WebhookMetadata` — which app handlers use to select the tenant/store the payload applies to — directly from those unauthenticated headers:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

Because the same `api_secret_key` is shared across all shops installed on a given app (it is not per-shop), any shop owner who legitimately receives a valid `(body, hmac)` pair for their own store's webhook can replay that exact body/HMAC pair while substituting a different `x-shopify-shop-domain` header value. The signature still validates (it never looked at the shop header), and `WebhookMetadata.shop` now falsely claims the payload belongs to a shop the attacker does not control. Any handler that uses `data.shop` to decide which tenant record to update, delete, or credit (a very common pattern for GDPR redact handlers, order/customer sync, etc.) will act on the attacker-chosen victim shop using attacker-controlled (albeit HMAC-valid-for-some-other-shop) body content.

### Impact Explanation
This breaks the shop/tenant identity boundary the gem is expected to provide via HMAC verification of the webhook request. An unprivileged internet user (a legitimate merchant installing the app on their own store, or anyone able to capture one authentic webhook delivery) can force the app to process a webhook payload while attributing it to an arbitrary other shop, resulting in cross-tenant access/data corruption — matching the "cross-tenant access" Critical impact category, since no additional secret, access token, or privileged account is required beyond receiving one normal webhook for the attacker's own installed shop.

### Likelihood Explanation
Likelihood is meaningfully high for any app that installs the same webhook secret for all shops (the standard model in this gem, driven by a single `Context.api_secret_key`) and whose handlers trust `WebhookMetadata#shop` to select the tenant scope, since the header is fully attacker-controlled and completely outside of what `to_signable_string` signs.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-verified signable string, or otherwise cryptographically bind the `shop` header to the authenticated request (e.g., verify that the `x-shopify-shop-domain` header value matches a value embedded in/derived from the signed payload) before constructing `WebhookMetadata` and dispatching to the handler.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, valid header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical `(B, hmac)` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)` against the (unmodified) signature: [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: B, ...)` and invokes the app's handler, which now processes payload `B` as if it belonged to `victim.myshopify.com`. [7](#0-6)
