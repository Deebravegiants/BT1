## Title
Withdraw's slippage protection is silently bypassed when only one of `min_coin_amount`/`min_pc_amount` is set — ([File: program/src/processor.rs])

### Summary
The `Withdraw` instruction lets a user submit `min_coin_amount: Option<u64>` and `min_pc_amount: Option<u64>` as explicit, per-transaction slippage-protection opt-ins [1](#0-0) . In `process_withdraw`, the check that enforces these minimums is gated by a hardcoded `AND` condition that requires **both** fields to be `Some` before any enforcement happens at all:

```rust
if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some() {
    if withdraw.min_coin_amount.unwrap() > coin_amount
        || withdraw.min_pc_amount.unwrap() > pc_amount
    {
        return Err(AmmError::ExceededSlippage.into());
    }
}
``` [2](#0-1) 

If a user (or an integrating client/SDK building the instruction) supplies only one of the two minimums — e.g., sets `min_coin_amount = Some(x)` but leaves `min_pc_amount = None` — the entire protection block is skipped, and the withdrawal proceeds unconditionally with whatever `coin_amount`/`pc_amount` the pool's current (attacker-influenceable) state produces. The user's explicit, singular opt-in for slippage protection is silently overridden/ignored by the hardcoded dual-`is_some()` gate, structurally mirroring the report's bug class (CWE-693: a hardcoded internal condition defeats an explicit user security opt-out/opt-in).

### Finding Description
`Withdraw` burns LP tokens and pays out `coin_amount`/`pc_amount` computed from the pool's live vault balances at execution time via `Calculator::calc_total_without_take_pnl_no_orderbook` and `InvariantPool::exchange_pool_to_token` [3](#0-2) . Because the payout is derived from live state, another transaction in the same block/slot (e.g., a large swap immediately preceding the withdraw, executed by the pool creator, an LP, or any unprivileged actor performing a sandwich) can shift the coin:pc ratio so that one side of the withdrawal is worth far less than expected.

The `min_coin_amount`/`min_pc_amount` fields exist precisely to let the withdrawing user bound this risk per-side. However, the enforcement requires **both** to be present simultaneously. Any legitimate client that only cares about protecting one side of the withdrawal (a common integration pattern — many client SDKs may only populate one Option, or a caller could reasonably assume each Option is checked independently as in `Deposit`'s analogous `other_amount_min` handling [4](#0-3) ) gets **zero** slippage protection instead of partial protection, with no error and no signal that the check was skipped.

This is directly comparable to the report's root cause: a hardcoded condition (`trust_remote_code=True` / here, the `is_some() && is_some()` gate) unconditionally overrides the caller's explicit, narrower security intent, producing a silent full bypass rather than the expected partial-or-full enforcement.

### Impact Explanation
An LP who withdraws liquidity while relying on only one of the two minimum-amount guards receives no slippage protection whatsoever. Combined with the ability of any unprivileged actor to move the pool's coin:pc ratio via the public swap instructions (`SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2`) immediately before the withdraw lands, an attacker can sandwich the withdrawal to extract value: the LP burns their LP tokens and receives a payout materially worse than intended, resulting in concrete theft of LP funds. This satisfies the "concrete theft of LP funds" impact bar.

### Likelihood Explanation
Reachable directly from `Withdraw`, an unprivileged, single-transaction instruction available to any liquidity provider [5](#0-4) . The only precondition is that the client populates just one of the two `Option<u64>` fields — a plausible integration mistake or a deliberate attacker-crafted transaction on behalf of a victim-facing wrapper — combined with a preceding attacker-controlled swap in the same or an adjacent slot, which any user can execute at will via the public swap instructions.

### Recommendation
Change the gating logic so each provided minimum is enforced independently, e.g.:
```rust
if let Some(min_coin) = withdraw.min_coin_amount {
    if min_coin > coin_amount { return Err(AmmError::ExceededSlippage.into()); }
}
if let Some(min_pc) = withdraw.min_pc_amount {
    if min_pc > pc_amount { return Err(AmmError::ExceededSlippage.into()); }
}
```
This mirrors the already-correct independent-check pattern used in `process_deposit`'s `other_amount_min` handling [4](#0-3)  and ensures a user's partial opt-in is honored rather than silently discarded.

### Proof of Concept
1. LP builds a `Withdraw` instruction with `amount = X`, `min_coin_amount = Some(expected_coin)`, `min_pc_amount = None`.
2. Attacker (or the same actor orchestrating a sandwich) submits a large `SwapBaseIn`/`SwapBaseOutV2` transaction just before, skewing `total_pc_without_take_pnl` vs `total_coin_without_take_pnl`.
3. `process_withdraw` computes `pc_amount` far below what the LP expected.
4. Because `min_pc_amount` is `None`, the condition `withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` at [6](#0-5)  evaluates `false`, so no `ExceededSlippage` check runs for either side — including the side (`min_coin_amount`) the LP explicitly tried to protect.
5. The withdrawal executes, transferring the degraded `pc_amount`/`coin_amount` to the LP and burning their LP tokens, realizing the loss.
