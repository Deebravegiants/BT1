### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies an inbound webhook's authenticity by computing an HMAC over the raw request body only, but the tenant-identifying `shop-domain` header (and `topic`) that host applications use to route/process the webhook are never included in the signed material. An attacker who can produce (or replay) a payload with a valid HMAC for the raw body can freely set the `shop-domain` header to any value, causing the receiving application to attribute the webhook payload to an arbitrary shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over exactly this `to_signable_string` value and compares it to the `hmac` accessor, which is read from the `hmac-sha256`/`x-shopify-hmac-sha256` header: [2](#0-1) [3](#0-2) 

However, `shop` and `topic` — the fields a receiving application uses to determine *which tenant* the webhook payload belongs to and how to route it — are read directly from unauthenticated headers, independent of the HMAC check: [4](#0-3) 

This is the same class of defect as the reported Niftyswap bug: a value that downstream logic treats as authoritative (`getPrice_*` reflecting balances) is derived from state/inputs that are not fully covered by the protection mechanism (`nonReentrant`/HMAC) applied elsewhere in the flow. Here, the binding that should hold is:

`shop header used to attribute/process the webhook == shop cryptographically bound by the HMAC`

but the code only enforces `HMAC(raw_body) == signature`, with no binding of `shop-domain` (or `topic`) into that signature at the library level.

### Impact Explanation
If a host application uses `Webhooks::Request#shop` to select which tenant's data to update (a very common pattern — e.g., locating the merchant record by shop domain before applying the webhook body), an attacker capable of obtaining a validly-signed webhook body for their own shop (or replaying/crafting a body whose HMAC they can compute, e.g. for a shop they control) can swap in a victim's `shop-domain` header value. Because the header is not part of the signed content, the HMAC check will still pass, and the payload will be processed as if it originated from the victim shop — a cross-tenant data confusion. This satisfies the Critical "cross-tenant access" impact category, since the identity binding between the authenticated bytes (body) and the trusted tenant identifier (shop header) is broken.

### Likelihood Explanation
Exploitability depends on whether the attacker can obtain a validly-HMAC-signed raw body at all (normally only Shopify can sign with the app's `client_secret`/webhook secret). Within the constraints of this analysis (no access to `api_secret_key`/credentials assumed), an attacker who operates their own store can receive genuinely-signed webhooks for their own shop and then replay that same body+HMAC to the app's webhook endpoint while altering only the `shop-domain` header — this requires no secret material, only network access to the app's public webhook endpoint. This makes the likelihood high whenever the host application trusts `request.shop` without independently correlating it to account/tenant context established via other authenticated channels.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed payload used for HMAC verification, or explicitly document that `shop`, `topic`, and other headers are NOT covered by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against a known/expected shop from the app's own session store). At minimum, update `to_signable_string` guidance/documentation so integrators understand only the raw body is authenticated, not the headers.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B`), header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com"})` is constructed; `Utils::HmacValidator.validate(request)` calls `to_signable_string` (only `B`) and validates successfully against `H`. [1](#0-0) 
4. The host application, trusting `request.shop` (`"victim.myshopify.com"`) after a passing HMAC check, applies the payload `B` to the victim's tenant record.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
