### Title
Division-by-zero panic in `SwapBaseOut`/`SwapBaseOutV2` when `amount_out` equals the full remaining pool reserve - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
`Calculator::swap_token_amount_base_out` computes the constant-product swap input as `numerator.checked_ceil_div(denominator).unwrap()`, where `denominator = pool_reserve.checked_sub(amount_out).unwrap()`. This subtraction is only guarded against underflow, not against reaching exactly zero. In `process_swap_base_out` and `process_swap_base_out_v2`, the safety check that rejects `amount_out >= pool_reserve` is performed *after* this division, so an attacker who submits `swap.amount_out` exactly equal to the current `total_pc_without_take_pnl` (or `total_coin_without_take_pnl` for the opposite direction) triggers a division by zero before the guard can reject the request.

### Finding Description
`swap_token_amount_base_out` in `math.rs`: [1](#0-0) 

For `SwapDirection::Coin2PC`, `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()`. `checked_sub` only fails (panics via `.unwrap()`) if `amount_out > total_pc_without_take_pnl`; when `amount_out == total_pc_without_take_pnl`, the subtraction succeeds and yields `0`, which is then used as the divisor in `checked_ceil_div(denominator).unwrap()`.

In the instruction handlers, the order of operations is:
1. Compute reserves via `calc_total_without_take_pnl_no_orderbook`.
2. Call `Calculator::swap_token_amount_base_out(swap.amount_out, ...)` — the vulnerable division.
3. Only afterwards check `swap_amount_out/amount_out >= total_pc_without_take_pnl` (or `total_coin_without_take_pnl`) and reject with `AmmError::InsufficientFunds`. [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The exact-equality check `>=` (rather than requiring the value to already have been validated before the math call) confirms the intent was to disallow draining the reserve down to zero, but the check is placed too late — the division-by-zero panic occurs first, in both `process_swap_base_out` (legacy path with OpenBook accounts) and `process_swap_base_out_v2` (direct vault path), which is the exact same bug class as the reported `ResourceGather` issue: a size/denominator value is computed and divided into without first verifying it is non-zero.

### Impact Explanation
A Rust panic inside a Solana on-chain program causes the transaction to abort (and, depending on the runtime/BPF panic handling, can manifest as a compute/panic failure). While this does not directly cause fund loss or insolvency, it is an unprivileged, single-transaction, attacker-controlled crash trigger on the core swap instructions (`SwapBaseOut`, `SwapBaseOutV2`) that any user can invoke by specifying `amount_out` equal to the pool's current unclaimed reserve. Because this occurs in the primary trading instruction reachable by any swapper, it can be used to grief specific pools (deny withdrawal-adjacent, closely-timed exact-drain swaps) or to probe/DoS classes of pools with very small pc/coin reserves, where hitting the exact boundary value is far more likely (e.g., pools near depletion or freshly initialized with minimal liquidity).

### Likelihood Explanation
Reaching this condition requires the attacker to know (or observe) the exact current `total_pc_without_take_pnl` / `total_coin_without_take_pnl` value and submit `amount_out` equal to it in a single `SwapBaseOut`/`SwapBaseOutV2` transaction — both quantities are readable on-chain from the AMM/vault accounts immediately before submitting the transaction, and no privileged signer or non-default configuration is needed. This makes the trigger straightforward for a normal user/liquidity-drainer to construct, especially against pools with small reserves.

### Recommendation
In `Calculator::swap_token_amount_base_out`, explicitly check that `amount_out < pool_reserve` (i.e., that `denominator != 0`) before calling `checked_ceil_div`, returning an `AmmError` (e.g., `CalculationExRateFailure` or a new `InsufficientLiquidity` variant) instead of relying on `.unwrap()`. Additionally, move the `amount_out >= total_*_without_take_pnl` bound checks in `process_swap_base_out` / `process_swap_base_out_v2` to occur *before* calling `Calculator::swap_token_amount_base_out`, so the amount is validated prior to any division.

### Proof of Concept
1. Read the AMM's current `amm_pc_vault.amount`, `amm_coin_vault.amount`, and `amm.state_data.need_take_pnl_pc/coin` to compute `total_pc_without_take_pnl` (as done in `calc_total_without_take_pnl_no_orderbook`, `program/src/math.rs:238-250`).
2. Submit a `SwapBaseOut` (or `SwapBaseOutV2`) instruction with `user_source` = coin token account, `user_destination` = pc token account (direction `Coin2PC`), and `amount_out` set exactly equal to the computed `total_pc_without_take_pnl`.
3. During processing, `Calculator::swap_token_amount_base_out` computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap() == 0`, then `checked_ceil_div(0).unwrap()` panics before the later `if swap_amount_out >= total_pc_without_take_pnl` guard at `program/src/processor.rs:2402-2406` is ever reached.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
