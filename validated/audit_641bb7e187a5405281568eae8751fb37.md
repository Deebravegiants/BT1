### Title
Truncating decimal-precision conversion in `convert_to_balance` permanently loses/locks user funds on every fractional cross-chain transfer - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` and `on_timeout` handlers convert an incoming ERC-20 `U256` amount into a local balance by integer division that always rounds down, with no mechanism to ever recover or account for the truncated remainder, mirroring the GVault report's rounding-direction bug class but with no upside for the protocol — the truncated value is simply destroyed or permanently escrowed with no owner.

### Finding Description
`convert_to_balance` scales an incoming ERC-20 amount down to local precision using plain integer division, which floors (rounds toward zero) whenever the amount is not an exact multiple of the decimal-scaling factor: [1](#0-0) 

This is invoked in `on_accept` (delivering a message from an EVM chain) to compute the amount to mint or release from escrow to the beneficiary: [2](#0-1) 

and again in `on_timeout` to compute the refund amount owed to the original sender after a timed-out `send`: [3](#0-2) 

The forward direction (`send`, substrate → EVM) uses `convert_to_erc20`, a pure multiplication that is exact and lossless: [4](#0-3) [5](#0-4) 

but the reverse direction is not: the EVM-side `HyperFungibleTokenUpgradeable.send()` burns the caller's *exact* ERC-20 amount and dispatches a message carrying that exact value — [6](#0-5) 

— with no requirement that the amount be an exact multiple of `10^(erc_decimals - local_decimals)`. Whenever it is not (which is the common case, since ERC-20 balances accrue fractional dust from swaps, transfers, and the ~1,000,000x scaling factor typical for e.g. BRIDGE's 18 EVM decimals vs. 12 nexus decimals, per `BridgeToken.sol`'s own documented scaling), `convert_to_balance` silently floors the credited/refunded amount: [7](#0-6) 

For the **native custody model**, the shortfall stays in the pallet's escrow account (`pallet_account`) forever, since nothing ever accounts for or releases it — a genuine, ownerless permanent freeze: [8](#0-7) 

For the **non-native (mint/burn) model**, the shortfall is simply destroyed: the EVM side already burned the full amount, and the substrate side mints strictly less, with the delta unaccounted for anywhere — an unrecoverable user loss, the mirror image of the GVault report's "protocol gives away value" pattern, except here it is the user (or the total cross-chain supply invariant) that is permanently shortchanged with zero compensation and zero salvage path.

### Impact Explanation
Every single-transaction, unprivileged cross-chain token transfer through this pallet that carries a fractional remainder below the destination chain's decimal granularity permanently loses that remainder. There is no batching, no dust ledger, and no path to reclaim it — for native assets it becomes forever-locked collateral in `pallet_account`, and for non-native assets it is an outright, uncompensated burn of user funds. Because this triggers on ordinary `send`/timeout-refund flows (not an edge case requiring adversarial setup), and directly causes permanent freezing/loss of user funds, this meets the "permanent freezing of funds" impact bar.

### Likelihood Explanation
High. Any token bridger who sends back a non-round-multiple ERC-20 amount — which is the default outcome any time the local asset has fewer decimals than its EVM counterpart (a configuration explicitly supported and used for BRIDGE itself, 18 vs. 12 decimals) — reproduces the loss with a single `send()`/`transferAndCall` call, with no special privileges or timing required.

### Recommendation
Round conversions consistently in the protocol's favor and reconcile the delta instead of silently discarding it: either reject `send()` amounts that are not exact multiples of the scaling factor at the EVM contract level (so no dust can ever be created), or have `convert_to_balance` return both the floored local amount and the truncated remainder, crediting the remainder to a recoverable dust account (or refunding it to the sender) rather than letting it vanish into an ownerless escrow or a silent burn.

### Proof of Concept
1. Deploy `BridgeToken` on an EVM chain (18 decimals) paired with nexus (12 decimals), per `evm/src/apps/BridgeToken.sol`.
2. A user receives `MINT_AMOUNT + 1` wei of BRIDGE on EVM (e.g., via a DEX trade or transfer, not necessarily a multiple of `10^6`) — see `evm/tests/foundry/BridgeTokenTest.t.sol` for the mint/send round-trip harness (`testSendToNexusBurns`, lines 121-143) which currently only exercises exact-multiple amounts.
3. The user calls `send()` with the full non-multiple-of-`10^6` balance; `HyperFungibleTokenUpgradeable.send()` burns the entire exact amount and dispatches a POST to nexus.
4. `pallet-hyper-fungible-token::on_accept` computes `convert_to_balance(amount, 18, 12)`, flooring away the sub-`10^6` remainder, and releases/mints strictly less than what was burned on the EVM side — the difference is permanently lost (native model: stuck in `pallet_account`; non-native model: burned with no local credit at all).

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
