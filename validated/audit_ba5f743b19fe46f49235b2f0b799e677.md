### Title
Panic-inducing unchecked `try_into().expect()` type conversion on attacker-controlled SP1 BEEFY proof fields halts consensus-proof processing - (File: `evm/rust/src/conversions.rs`)

### Summary
The `Sp1BeefyProof` ABI-to-SCALE conversion performs `try_into().expect(...)` on attacker-supplied `U256` fields (`blockNumber`, `validatorSetId`) taken directly from a submitted proof, without any bounds validation before the conversion. This is reachable from the permissionless, signed `submit_proof` extrinsic, so any account can submit a malformed proof that panics during dispatch.

### Finding Description
`impl From<crate::sp1_beefy::SP1Beefy::SP1BeefyProof> for Sp1BeefyProof` converts the Solidity ABI-decoded proof commitment fields into the SCALE proof type used internally: [1](#0-0) 

`block_number` and `validator_set_id` are declared as `U256` on the Solidity side and are converted with `.try_into().expect("block number out of bounds")` / `.expect("validator set id out of bounds")` into the narrower Rust integer types the pallet uses. Neither field is range-checked before this conversion — the values come straight from the ABI-decoded bytes an untrusted caller supplies.

This conversion is invoked from `Pallet::verify_and_apply`, which ABI-decodes the SP1 proof payload immediately after it is pulled out of the extrinsic-supplied byte blob: [2](#0-1) 

`verify_and_apply` is called from `do_submit_proof`, which is in turn the direct implementation of the `submit_proof` extrinsic — a signed, permissionless call open to any account, gated only by `BoundedVec<u8, T::MaxProofSize>` (a size bound, not a value bound): [3](#0-2) [4](#0-3) 

Because the offending field (e.g. `blockNumber` set above `u64::MAX`, or `validatorSetId` set above its target width) is only checked by `.expect()`, dispatch of this extrinsic panics inside runtime STF execution rather than returning a typed `DispatchResult` error. No pre-check on `commitment.blockNumber`/`commitment.validatorSetId` exists anywhere upstream of this conversion — the transaction-pool-level validation for a signed extrinsic only checks signature/nonce/fee, not the proof contents, so the panic is only triggered when a block producer actually executes the call while building/importing a block.

### Impact Explanation
A Rust panic raised during dispatch of an on-chain extrinsic in a Substrate/Polkadot-SDK runtime unwinds to the Wasm execution boundary and traps the runtime call, which fails block execution rather than gracefully returning a `DispatchError`. Any block that includes this extrinsic cannot be successfully authored/imported, which halts progression of BEEFY consensus-proof processing for Hyperbridge's coprocessor state machine — i.e. a route that becomes unable to deliver/process consensus messages until operators identify and evict the poisoned extrinsic. This is a denial-of-service against the primary consensus-update ingestion path (`submit_proof`), which every downstream ISMP message relay and reward accounting on the affected route depends on.

### Likelihood Explanation
High: `submit_proof` is a public, unprivileged, signed extrinsic; constructing a proof with an out-of-range `blockNumber`/`validatorSetId` (e.g. a `U256` value above `u64::MAX`) is trivial ABI encoding, and it only needs to pass SCALE size bounding, not proof correctness, since the panic fires during the ABI→SCALE conversion, which happens before any cryptographic verification.

### Recommendation
Replace the `.expect(...)` calls in `Sp1BeefyProof::from` (and the analogous conversion in `MmrProof`/`RelayChainProof`, `evm/rust/src/conversions.rs:368-417`) with fallible `try_into()` propagated as a typed error (e.g. `Result<Sp1BeefyProof, ConversionError>`), and thread that error through `verify_and_apply`/`do_submit_proof` so an out-of-range field yields `Error::<T>::AbiDecodeFailed` (or a new dedicated error) instead of panicking. Add explicit range validation on `blockNumber`/`validatorSetId` immediately after ABI decoding, before any `From`/`Into` conversion is invoked.

### Proof of Concept
1. Craft an SP1 BEEFY proof ABI payload (`SP1Beefy::SP1BeefyProof`) with `commitment.blockNumber` set to a `U256` value greater than `u64::MAX` (e.g. `2^64`).
2. Submit it via `beefy_consensus_proofs.submit_proof(proof)` from any signed account; the `BoundedVec<u8, MaxProofSize>` bound only limits byte length, not field values, so the extrinsic is accepted into the pool.
3. When a block producer executes `do_submit_proof` → `verify_and_apply` → `Sp1BeefyProof::from`, the `try_into().expect("block number out of bounds")` panics, aborting execution of that block for every node that attempts to author/import it.
