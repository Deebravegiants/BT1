### Title
Webhook `shop` (and other Shopify headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and other trust-relevant metadata (`topic`, `api_version`, `webhook_id`) exclusively from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only verifies the raw request body against the app's `client_secret`. The `shop-domain` header used to attribute a webhook to a specific merchant is never included in the signed content, so a value that is authenticated (the request body) is not equal to the value that is acted upon (the shop the webhook is attributed to). This mirrors the reported bug class: an assumption is made about which piece of data corresponds to which identity, without actually verifying the binding cryptographically.

### Finding Description
`Webhooks::Registry.process` gates all webhook handling on the HMAC check: [1](#0-0) 

The HMAC check itself calls `HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to obtain the bytes to verify: [2](#0-1) 

For webhook `Request` objects, `to_signable_string` returns only the raw HTTP body — none of the Shopify-supplied headers are part of the signed payload: [3](#0-2) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` — all taken straight from headers via `shopify_header` — are trusted downstream and passed into the handler as the identity/context of the webhook: [4](#0-3) [5](#0-4) 

Because the HMAC only proves "this body was signed with the app's secret at some point, for some shop that installed the app," but not "this body was signed for the shop named in this specific `shop-domain` header," any attacker who is themselves a legitimate installer of the app (or who otherwise obtains one valid `(raw_body, hmac)` pair for a webhook addressed to their own shop) can replay that same body/HMAC pair to the app's webhook endpoint while substituting a different value in `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`). The signature verification in `HmacValidator.validate` will still pass because it only checks the untouched body bytes against the shared `client_secret` — it never checks that the body was actually intended for the shop named in the headers.

This breaks the identity binding: `authenticated_bytes == raw_body`, but `acted_on_identity == header["shop-domain"]`, and nothing ties the two together.

### Impact Explanation
This enables cross-tenant confusion in any app built on this gem's webhook handling API: a handler that persists or acts on webhook data keyed by `data.shop` (as documented and demonstrated in `WebhookMetadata`) can be made to attribute attacker-supplied (but validly-signed-for-a-different-shop) payload content to an arbitrary victim shop domain, since the HMAC does not bind the payload to that shop value. This is a cross-tenant access primitive at the boundary the gem is responsible for validating (`Registry.process`), independent of how the host application implements its handler — the gem's `HmacValidator` is advertised as the mechanism that authenticates the tenant/webhook, but it does not actually authenticate the `shop` field it exposes.

### Likelihood Explanation
Requires the attacker to have or obtain at least one legitimately-signed webhook body from Shopify for a shop they control (trivially available to anyone who installs the app on their own development/test store) and the ability to send an HTTP request to the app's public webhook endpoint with custom headers — both of which are available to any unprivileged internet user/app installer, with no leaked credentials or privileged account required.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used by `HmacValidator`, or otherwise cryptographically bind them to the payload (e.g., verify them against the shop/session under which the webhook subscription was registered), so that the HMAC check certifies the full identity tuple rather than only the raw body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a body they fully control (e.g. an order with attacker-chosen `note` or `email` fields).
2. Shopify delivers the webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed over that body using the shared `client_secret`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this exact `(raw_body, X-Shopify-Hmac-Sha256)` pair and replays it directly to the same endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and adjusts `webhook-id`/`api-version` headers as desired — none of which are checked).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates only `raw_body` against `client_secret` — validation succeeds because the body and secret are unchanged.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled data>, ...)`, causing the app to act on attacker-controlled webhook content under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
