### Title
Fee-on-transfer / deflationary tokens allow escrow-shortfall drain in `WrappedHyperFungibleToken.send` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain message that unconditionally encodes `params.amount` as the transferred amount, without ever measuring the actual tokens received by the contract. `IntentGatewayV2.sol` was hardened against exactly this class of bug by snapshotting balances before/after transfers and mutating `order.inputs[i].amount` to the actual received delta [1](#0-0) , but `WrappedHyperFungibleToken` was never given the same treatment.

### Finding Description
In `send()`, for the ERC20 (non-WETH) path, the contract calls `safeTransferFrom` for `params.amount` and immediately builds/dispatches a `DispatchPost` whose body encodes `params.amount` as the `Message.amount`, with no balance check: [2](#0-1) 

On the destination chain, `onAccept` trusts `message.amount` from the decoded body and unconditionally transfers that full amount of the underlying token out of the destination wrapper's balance to the beneficiary: [3](#0-2) 

If `_underlying` is a fee-on-transfer or deflationary token, the amount actually received/locked by the source-chain wrapper (`address(this)` balance increase) is strictly less than `params.amount`, yet the full, un-reduced `params.amount` is what gets committed into the cross-chain message and later unlocked on the destination chain. The same unchecked-amount pattern also exists in `onPostRequestTimeout`, which re-releases `message.amount` (the original unreduced amount) back to the refundee on the source chain even though only the reduced amount was ever actually locked: [4](#0-3) 

This is precisely the bug class from the external report: shares/entitlements (here, the cross-chain unlock amount) are computed off the pre-fee amount instead of the actually-received/locked amount. The identical `HyperFungibleTokenUpgradeable`-family variant (`WrappedHyperFungibleTokenUpgradeable.sol`) has the same unchecked `safeTransferFrom`/`message.amount` pattern.

### Impact Explanation
Each cross-chain send of a fee-on-transfer underlying token causes the destination wrapper to unlock more tokens than the source wrapper actually locked. Over repeated sends this progressively drains the destination-chain wrapper's underlying token balance beyond what it holds in escrow, eventually causing insolvency (unable to honor later unlocks/timeouts) — a permanent freezing/loss of funds for legitimate users and other token holders relying on the wrapper's escrow backing. This matches the "concrete theft or permanent freezing of funds" acceptance bar, reachable by any unprivileged user who owns/controls a fee-on-transfer or deflationary ERC20 and calls the public `send()` function.

### Likelihood Explanation
Likelihood is low-to-moderate: the vulnerability is only triggered when the token configured as `_underlying` (chosen by the deploying owner, not by users) is a fee-on-transfer, deflationary, or rebasing ERC20. For a standard ERC20 configured as underlying, there is no impact. However, once such a token is configured, any user can trigger the drain with a single `send()` call, requiring no special privileges.

### Recommendation
In `WrappedHyperFungibleToken.send()` (and its upgradeable counterpart), snapshot `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual received delta as `Message.amount` in the dispatched body, mirroring the pattern already applied in `IntentGatewayV2.sol`'s `placeOrder`. Alternatively/additionally, explicitly document and enforce (e.g., via a `SafeERC20`/allow-list check or an on-configure balance-delta self-test) that `_underlying` must not be a fee-on-transfer, rebasing, or max-uint-interpreting token, since the destination-side `onAccept`/`onPostRequestTimeout` trust the committed `message.amount` as fully backed.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` on chain A and B, configures `_underlying` = a fee-on-transfer token `FOT` (1% fee) on both chains, registers each other as peers.
2. Attacker holds `1000 FOT` on chain A, approves the wrapper, calls `send({amount: 1000, dest: B, to: attacker})`.
3. `safeTransferFrom` moves `1000 FOT` from attacker, but due to the 1% fee only `990 FOT` actually lands in the chain-A wrapper's balance [5](#0-4) .
4. The dispatched `Message.amount` is still `1000` (unreduced) [6](#0-5) .
5. On chain B, `onAccept` transfers a full `1000 FOT` (previously bridged/escrowed liquidity) to the attacker's address on chain B [7](#0-6) , even though chain A only ever locked `990 FOT`.
6. Repeating this drains chain B's wrapper balance by 1% of every transferred amount beyond what chain A actually backs, eventually causing shortfalls that prevent honest unlocks/timeout refunds for other users.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
