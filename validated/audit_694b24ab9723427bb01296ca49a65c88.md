### Title
Webhook `shop`/`topic` identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook using `Utils::HmacValidator.validate(request)`, but the signature only ever covers the raw HTTP body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are never included in the signed material, yet they are the exact fields used to route the payload and to identify which tenant ("shop") the data belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from client-controlled headers with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` accepts the request as authentic once the body HMAC checks out, and then forwards the *unauthenticated* `request.shop` and `request.topic` values to the application's webhook handler as the tenant/event identity: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop header value used by the handler == shop that the HMAC-signed body actually originated from`
Because the header is outside the signed scope, these two values are never actually bound together by the gem — anyone who can obtain one valid `(raw_body, hmac)` pair (e.g., from their own store's legitimate webhook traffic, which is delivered in plaintext HTTP headers/body to the app's public endpoint) can replay that exact body+HMAC to the same endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will hand the forged shop identity straight to the app's handler.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce: an attacker who controls or has observed one legitimate (body, HMAC) pair can make the app process that payload under a different shop's identity, or under a different topic than what was actually signed for. Depending on how the host app persists/acts on `WebhookMetadata#shop` (e.g., looking up that shop's stored access token/session to react to the event), this can lead to cross-tenant data confusion or actions being misattributed to the wrong merchant — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint plus possession of any single valid `(raw_body, hmac)` pair — which an attacker can obtain cheaply by owning/operating their own Shopify store and capturing their own store's legitimate webhook delivery (a normal unprivileged internet user capability, requiring no `api_secret_key` or stolen credentials). No interaction with Shopify's servers is needed to replay the forged headers to the app.

### Recommendation
Include the tenant/routing-identifying fields (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) as part of the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., derive/confirm the shop from a signed field inside the JSON payload where available, or require the host app to independently confirm the header-derived shop against a value obtained through an authenticated channel) before using them to key any application logic.

### Proof of Concept
1. Attacker registers webhooks on their own store (`attacker-shop.myshopify.com`) pointing at the target app's public webhook endpoint, and captures one delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared secret — the attacker doesn't need to know the secret, they just observe a valid pair from real traffic).
2. Attacker sends a new POST request directly to the same app webhook endpoint with:
   - Body: the same `B`
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since only `B` is signed)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic:` optionally altered to another registered topic
3. `Utils::HmacValidator.validate` returns `true` (it only checks `B` against `H`).
4. `Registry.process` dispatches to the matching handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <forged-or-original>, body: <parsed B>, ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
