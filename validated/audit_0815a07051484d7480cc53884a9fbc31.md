### Title
Webhook shop-domain identity spoofing due to HMAC signing only the raw body, not the tenant header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` value that the app's handler subsequently trusts as the tenant identifier is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed bytes. This breaks the equality `shop bound by HMAC == shop used by handler`, allowing a shop-domain value that was never authenticated by the signature to be delivered to app logic as if it were.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC against `Context.api_secret_key` (the same secret for every shop that has installed the app, since `client_secret`/`api_secret_key` is app-wide, not per-shop) and then hands the unauthenticated `request.shop` straight to the handler: [4](#0-3) 

The handler receives this value as the trusted tenant key inside `WebhookMetadata`: [5](#0-4) 

Because the HMAC secret is shared across all shops on the app and the signature covers only the body, any body+HMAC pair that is valid for one shop's webhook delivery remains valid when replayed with a different `shop-domain` header value. The gem provides no binding between the authenticated bytes (body) and the identity field (`shop`) that downstream application code (via `Registry.process`/`WebhookMetadata`) uses to decide which tenant's data/state to act on.

### Impact Explanation
Host applications built on this gem are expected to key their persistence/business logic off `WebhookMetadata#shop` (e.g., updating local records, deleting data on `app/uninstalled`, revoking access tokens) because that is the field this library exposes as "the shop." Since that field carries no cryptographic guarantee, an attacker who is a legitimate merchant of the app (and thus receives real signed webhooks for their own shop) can replay the identical signed body while substituting a victim shop's domain in the header, causing the app to attribute the (attacker-controlled) event to the victim tenant. This is a cross-tenant integrity break directly caused by the gem's signature scope, matching the High/Critical "cross-tenant access" impact class.

### Likelihood Explanation
Requires only: (1) the attacker owns a shop that has the app installed (able to trigger and capture a legitimately signed webhook body+HMAC for any topic they choose), and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a spoofed `shop-domain` header, both of which are available to an ordinary, unprivileged app user — no `api_secret_key`, access token, or other privileged capability is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material used by `to_signable_string`, or otherwise cryptographically bind `shop` to the verified payload before it is passed to `WebhookHandler#handle`, so `Registry.process` cannot be fed a shop value that was not covered by the HMAC that was actually checked.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com, which has the app installed.
# Triggering any webhook-eligible action on shop-a causes Shopify to POST:
#   headers: { "x-shopify-hmac-sha256" => <valid hmac of body over api_secret_key>,
#              "x-shopify-shop-domain" => "shop-a.myshopify.com",
#              "x-shopify-topic" => "orders/create", ... }
#   body: <raw JSON body>
#
# Attacker captures (body, hmac) and replays to the same endpoint, only
# changing the shop-domain header to a victim shop that also has the app installed:
request = ShopifyAPI::Webhooks::Request.new(
  raw_body: captured_body,
  headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => captured_hmac,   # unchanged, still validates
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  },
)

ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (HmacValidator only checks @raw_body)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app now processes attacker-controlled webhook content as belonging to victim-shop.
```
