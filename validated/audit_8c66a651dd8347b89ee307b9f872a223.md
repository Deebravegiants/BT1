## Title
Webhook shop identity (`shop-domain`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the application's webhook handler are read from unauthenticated HTTP headers. Any attacker who can obtain one valid `(body, hmac)` pair — trivially available to anyone who installs the app on a shop they control — can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, causing the host application to process/attribute the webhook to a victim tenant it never actually came from.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the request: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate`, which checks the signature against `to_signable_string` (i.e., the body only), and then immediately hands the *unverified* `request.shop` (along with `topic`/`webhook_id`) to the application's registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` / `validate_signature` confirm this: the HMAC is computed exclusively over `verifiable_query.to_signable_string`, never over any header-derived field: [4](#0-3) 

This breaks the intended identity binding: `shop` value trusted by the handler == `shop` value verified by the HMAC. In practice, `HMAC(body) == HMAC(body)` holds regardless of what `shop-domain` header accompanies the request, so the two sides of the equality diverge as soon as an attacker swaps the header.

### Impact Explanation
Since `Registry.process` forwards `request.shop` into `WebhookMetadata` without any HMAC coverage, a host application that uses this `shop` value to select/update per-tenant data (the documented, expected usage pattern shown in `docs/usage/webhooks.md`) can be made to apply attacker-supplied webhook content to a different shop's tenant record — a cross-tenant data-integrity/access issue. This matches the Critical "cross-tenant access" impact category, since the security boundary between tenants (each identified by their `shop` domain) is what the HMAC is meant to protect and does not.

### Likelihood Explanation
Likelihood is Medium-to-High: an unprivileged internet user only needs to control any single Shopify store (trivially obtainable, e.g., a free development store) that has the target app installed. They receive a legitimate, correctly-signed webhook `(body, hmac)` pair from Shopify for their own store, then directly POST that identical body/HMAC to the app's public webhook endpoint with the `shop-domain` header rewritten to the victim shop's domain. No access to the victim's credentials, `api_secret_key`, or any TLS interception is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, or otherwise cryptographically/contextually bind the `shop` header value to a request the app already trusts (e.g., cross-check `request.shop` against previously stored/authorized shops for that app, not solely against the raw header). At minimum, document prominently that `request.shop` is NOT covered by HMAC verification and must not be used for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify sends the attacker a legitimate webhook request with a valid body `B` and header `X-Shopify-Hmac-Sha256: H`, computed as `HMAC-SHA256(secret, B)`.
3. Attacker replays the exact same body `B` and `X-Shopify-Hmac-Sha256: H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B) == H` — the forged `shop-domain` header is irrelevant to this check.
5. The application's webhook handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the attacker's payload as if it originated from the victim shop.
