## Title
`EvmHost` resets the consensus staleness clock on every (re)deployment, defeating the long-range-attack expiry check - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost`'s constructor unconditionally sets `_consensusUpdateTimestamp = block.timestamp` every time the contract is deployed, and `setConsensusState` does the same whenever a genesis/re-genesis consensus state is seeded. `HandlerV2.handleConsensus` uses this timestamp as the sole guard against accepting consensus proofs for an authority set that may already have unstaked (the "long-range attack" mitigation). Exactly like the reported `LivenessGuard` bug — where redeploying the guard silently refreshed every owner's liveness clock — redeploying or re-seeding `EvmHost` silently refreshes the consensus staleness clock to "now," regardless of how old the actual authority-set/consensus data being carried over really is.

### Finding Description
`EvmHost`'s constructor:

<cite repo="AYontt/hyperbridge--003" path="evm/src/core/EvmHost.sol" start="359="369" end="369" />

```solidity
constructor(address _admin) {
    _consensusUpdateTimestamp = block.timestamp;
    _hostParams.admin = _admin;
}
``` [1](#0-0) 

and `setConsensusState`, the one-shot (per `_canReinitConsensus`) function that seeds/reseeds the trusted consensus state: [2](#0-1) 

both stamp `_consensusUpdateTimestamp` with the *current* block time, not with any notion of "how stale is the state I'm actually importing."

This timestamp is the entire basis for the anti-long-range-attack check in `HandlerV2.handleConsensus`: [3](#0-2) 

```solidity
function handleConsensus(IHost host, bytes calldata proof) external notFrozen(host) {
    uint256 delay = block.timestamp - host.consensusUpdateTime();
    if (delay >= host.unStakingPeriod()) revert ConsensusClientExpired();
```

The protocol docs describe exactly the invariant this is meant to protect: a consensus client that hasn't been updated within the tracked chain's unbonding/unstaking period must be treated as expired, because validators who signed the last known state may have already exited the validator set and can no longer be slashed for signing a forked/eclipsed history (documented at `docs/content/protocol/interoperability/consensus-proofs.mdx` "Long Range Attacks" section and mirrored in the Rust `IsmpHost::is_expired` reference implementation).

Because `EvmHost` (and `TronHost`, which also seeds via constructor/`init`) always resets this clock to `block.timestamp` on deployment/re-init, any time a host is replaced or its consensus state is re-seeded (bug fix, migration to a new implementation, disaster recovery, chain relaunch, etc.) with an authority set/consensus state that is objectively old relative to the source chain's real unbonding period, the new host grants relayers a *fresh* full `unStakingPeriod` window to submit a "first" consensus proof for that already-stale state — exactly mirroring how the `LivenessGuard` constructor granted every owner, active or not, a fresh `LIVENESS_INTERVAL`.

### Impact Explanation
The `unStakingPeriod`/`ConsensusClientExpired` check exists specifically to reject consensus updates once enough time has passed that the original signers could have safely unbonded and can no longer be slashed for having signed a forked/eclipsed chain. Resetting the staleness clock to "now" on every redeploy means a maliciously or accidentally seeded stale consensus state (e.g., one imported during a host migration that is already past its real safety window on the source chain) is treated by the new `EvmHost` as freshly updated, silently re-opening the long-range/eclipse-attack window described in the protocol's own threat model. An attacker (or set of validators who have already exited stake) could then submit a forged consensus proof built on that stale trusted state within the newly-granted window, which `HandlerV2.handleConsensus` would accept as valid, allowing forged state commitments and unsound message delivery (fabricated deposits/withdrawals) to be accepted by the bridge.

### Likelihood Explanation
This occurs automatically, without any attacker action, whenever an `EvmHost` is redeployed or its consensus state is (re)seeded via `setConsensusState`/`initialize_state`-style flows — which the repo's own migration/deploy scripts (`evm/script/DeployIsmp.s.sol`, `evm/tron/migrations/2_deploy_ismp.js`) demonstrate is a routine, supported operational path. Any future upgrade, migration, or disaster-recovery re-deployment of the host silently re-arms the expiry window regardless of the actual age of the imported consensus data, exactly as guaranteed-on-replace as the original `LivenessGuard` finding.

### Recommendation
When constructing a new `EvmHost`/seeding `setConsensusState` from a previously-existing trusted state (rather than a brand-new chain genesis), initialize `_consensusUpdateTimestamp` from the *actual* last-known-good update time of the state being imported (e.g., pass it explicitly as a parameter validated against the source chain, or copy it from the previous host being replaced) instead of unconditionally stamping `block.timestamp`. Only a true first-ever genesis deployment for a brand-new consensus client should use `block.timestamp`.

### Proof of Concept
1. Assume an `EvmHost` H1 tracks a Polkadot/BEEFY consensus state whose authority set last updated its commitment 20 days ago, and the tracked network's real unbonding/unstaking period is 21 days — i.e., H1 is 1 day from legitimately expiring per `HandlerV2.handleConsensus`'s `delay >= host.unStakingPeriod()` check.
2. Governance needs to redeploy the host (bug fix in `EvmHost`, or migrate to `TronHost`-style deployment) and seeds the new host H2 with the same (already 20-day-old) consensus state via `setConsensusState`, per `evm/src/core/EvmHost.sol` lines 776-788, or the constructor in `evm/src/core/EvmHost.sol` lines 366-369.
3. H2's `_consensusUpdateTimestamp` is stamped with `block.timestamp` at deployment time, not `now - 20 days`. `host.consensusUpdateTime()` (`evm/src/core/EvmHost.sol` lines 417-422) now reports the state as freshly updated.
4. `HandlerV2.handleConsensus` (`evm/src/core/HandlerV2.sol` lines 144-146) now computes `delay = block.timestamp - host.consensusUpdateTime() ≈ 0`, well under `unStakingPeriod`, so H2 will continue accepting consensus proofs built on that trusted state for a full new `unStakingPeriod` (21 days) — 20 days beyond when H1 would have correctly rejected them as expired.
5. Any validator who exited the original authority set in that 20-day-old snapshot (and thus is no longer economically slashable) can, within that improperly re-opened window, submit a forged/eclipsed consensus proof extending from the stale trusted state; `handleConsensus` accepts it, `IConsensusV2(host.consensusClient()).verify` operates on attacker-controlled fork data, and `host.storeConsensusState`/`storeStateMachineCommitment` persist forged state commitments that downstream request/response handling treats as authentic.
