### Title
Webhook shop-domain (tenant) identifier is not covered by the HMAC signature, allowing cross-shop spoofing of `WebhookMetadata#shop` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body, never over the shop-domain header. This breaks the intended binding: `hmac == HMAC(secret, body)` should also guarantee `shop == the shop that produced the body`, but the header is fully outside the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is read straight from an unauthenticated header: [2](#0-1) , via `shopify_header`, which just does a hash lookup on caller-supplied headers with no cross-check against the signed body: [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier for dispatch, passing it straight into `WebhookMetadata` for the handler: [4](#0-3) .

Contrast this with the OAuth callback path (`Auth::Oauth::AuthQuery`), where `Utils::HmacValidator.validate` is also used, but there every field participating in the request (`code`, `host`, `shop`, `state`, `timestamp`) is part of `to_signable_string` and therefore covered by the same HMAC check: [5](#0-4) , [6](#0-5) . The webhook path deviates from that pattern: the signature only binds the body, not the tenant-identifying header that the gem hands to application code as authoritative.

Because the same `client_secret` is used to sign webhooks for every shop installed on a given app, an attacker who controls (or has a free/trial) shop that is installed on the target app can:
1. Trigger a legitimate webhook for their own shop and capture the raw body + valid `X-Shopify-Hmac-Sha256` value.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim merchant's domain.
3. `Utils::HmacValidator.validate` still succeeds, because the header is not part of `to_signable_string`. `Registry.process` then calls the handler with `WebhookMetadata#shop` set to the victim's domain [7](#0-6) .

If a host application (as documented/intended by this gem's API) uses `WebhookMetadata#shop` to look up the tenant's session/access token or to route the body's contents into per-tenant storage — which is the gem's documented usage pattern for webhook handlers — this results in cross-tenant data being attributed to the wrong shop, i.e. a cross-tenant confusion primitive achieved purely through this gem's own signature-verification code, with no credentials beyond installing the app on an attacker-controlled shop.

### Impact Explanation
This is a genuine binding break inside the gem: `hmac` is verified against `raw_body` only, while the tenant identity (`shop`) consumed by downstream handler code comes from an unsigned header. This enables cross-tenant webhook injection/confusion — an attacker-controlled shop's authentic webhook can be relabeled as belonging to any other shop on the same app, without needing the app's `client_secret`, an access token, or any privileged account. This matches the Critical "cross-tenant access" impact category, since the vulnerable binding lives entirely in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`, not in host-application misuse.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on an attacker-owned development/trial store (a normal, low-privilege capability for any Shopify Partner) to obtain one legitimate `(raw_body, hmac)` pair, then replaying it with a modified `Shop-Domain` header to the app's public webhook endpoint. No secrets, tokens, or social engineering are required, and the flaw is deterministic and always reachable through `Registry.process`.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the HMAC-signed material, or independently verify that the `X-Shopify-Shop-Domain` header matches a shop field embedded in the signed body/metadata before trusting it. At minimum, `Request#to_signable_string` should incorporate the shop-domain header so `Utils::HmacValidator.validate` cannot succeed with a mismatched tenant identifier, restoring the same "all fields covered by HMAC" property already used for `Auth::Oauth::AuthQuery`.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com", which has the target app installed.
# Step 1: Attacker triggers any event to receive one authentic webhook and captures:
raw_body = '{"id": 1, "note": "hello"}'
valid_hmac = "<value Shopify sent in X-Shopify-Hmac-Sha256 for this exact body>"

# Step 2: Attacker replays it to the app's webhook endpoint, swapping only the header:
headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,        # unchanged, still verifies vs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
  "x-shopify-webhook-id"  => "spoofed-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true, because to_signable_string == raw_body only.
# => The registered handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed raw_body, ...)
```
This demonstrates that `lib/shopify_api/webhooks/request.rb`'s `hmac`/`to_signable_string` and `shop` accessors are independently controllable: the signature check passes while the tenant identifier used by the application is attacker-chosen.
