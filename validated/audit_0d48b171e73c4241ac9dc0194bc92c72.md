### Title
Meta-transaction (`DelegateAction`) signatures lack chain/network binding, enabling cross-chain replay - (File: core/primitives/src/action/delegate.rs)

### Summary
The NEP-366/NEP-461 meta-transaction signature scheme used for `DelegateAction` / `DelegateActionV2` binds a user's signature only to `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`, and a fixed NEP discriminant. It never includes any value that identifies the specific chain/network instance (no genesis hash, no chain id, no equivalent of the outer transaction's `block_hash`). This mirrors the eth-bridge finding: signature schemes that omit an instance identifier allow signatures to be replayed across different deployments/forks that share equivalent state.

### Finding Description
`SignedDelegateAction::verify`/`sign` and `VersionedSignedDelegateAction::verify`/`sign` compute the signed hash via `get_nep461_hash`, which wraps the action in a `SignableMessage` tagged only with a `SignableMessageType` (`DelegateAction` or `DelegateActionV2`), via a fixed `MessageDiscriminant` per NEP number: [1](#0-0) [2](#0-1) 

The struct being signed contains no chain-identifying field at all: [3](#0-2) [4](#0-3) 

By contrast, the outer `SignedTransaction`/`TransactionV1` includes a `block_hash` field used purely for freshness/expiry within one chain, and nonce validation is scoped to the `(signer_id, public_key)` access key state on that chain: [5](#0-4) [6](#0-5) 

Because the inner `DelegateAction` payload is signed independently of any chain identity, the exact same signed bytes are valid wherever the same `sender_id`/`public_key`/`nonce` state exists — e.g., on any nearcore-based chain that shares the same account/access-key state as the chain the user intended to sign for (forked networks, disaster-recovery/canary chains restored from a genesis/state snapshot, or test networks cloned from mainnet/testnet state, a pattern nearcore explicitly supports via genesis export/import tooling such as `tools/mirror`, which itself re-signs delegate actions when mapping state precisely because the original signature can't be trusted to be chain-specific): [7](#0-6) 

### Impact Explanation
If two independently operated nearcore chains share equivalent account/access-key state (e.g., a chain fork after an incident, a disaster-recovery chain restored from a state dump, or any environment cloned from another chain's genesis/state), a `DelegateAction` signed by a user for one chain (e.g., adding a full-access key, transferring funds, or granting a function-call key) can be captured and replayed verbatim by wrapping it in a fresh outer `SignedTransaction` on the second chain via a normal RPC submission. Since the relayer role can be filled by anyone (the outer transaction's signer/fee-payer is untrusted with respect to the inner delegate action's authorization), this results in unauthorized state/authorization changes (e.g., unauthorized key addition or fund transfer) on the second chain, matching the "unauthorized state or balance change" impact category.

### Likelihood Explanation
Exploitation does not require a malicious validator or network-layer control — an unprivileged actor who has observed a signed `DelegateAction` (e.g., a relayer, or anyone monitoring pending/finalized transactions) can resubmit it through a standard RPC path as long as a second chain exists with matching account/nonce state. This is a realistic but conditional scenario: it requires two chain instances sharing identical account/access-key state, which nearcore's own tooling for chain migration/mirroring (`tools/mirror`) demonstrates is an actively supported operational pattern.

### Recommendation
Include a chain-identifying value (e.g., the target chain's genesis hash / chain id) in the `SignableMessage` payload for `DelegateAction`/`DelegateActionV2`, analogous to how `TransactionV1` includes `block_hash`, so that a signature produced for one chain instance cannot be replayed on another chain sharing equivalent account state. Document this binding explicitly as part of the NEP-461/NEP-366 signing scheme.

### Proof of Concept
Not independently executable without two live nearcore deployments sharing identical genesis/account state; the code-level root cause (absence of any chain-binding field in `DelegateAction`'s signed payload) is demonstrated by [1](#0-0)  and [3](#0-2) , and the existing test suite confirms the signature only binds nonce/version/discriminant, not chain identity: [8](#0-7) .

    pub fn get_nep461_hash(&self) -> CryptoHash {

        hash(&bytes)
    }

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
