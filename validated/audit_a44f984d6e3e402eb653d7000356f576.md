### Title
Zero-fee dispatch of Hyperbridge-originated system requests (relayer withdrawals, host-executive, token-governor, intents-coprocessor messages) leaves them permanently undelivered absent governance action - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/host-executive/src/lib.rs`, `modules/pallets/intents-coprocessor/src/lib.rs`, `modules/pallets/token-governor/src/impls.rs`)

### Summary
This mirrors the Aloe M-9 pattern: a required step in a multi-step flow has no incentive for any third party to perform it, so the dependent, valuable step never happens and funds get stuck. On Hyperbridge, several pallets dispatch ISMP `PostRequest`s that must be relayed off-chain to a destination chain to take effect (fee withdrawals, host parameter propagation, token-governor mint/burn instructions, intents-coprocessor responses), but these dispatches are made with `FeeMetadata { payer: [0u8;32], fee: 0 }` — i.e. zero relayer fee. Relayers are rational economic actors who pick up and deliver messages based on fee; a zero-fee message gives no reason for any relayer to spend gas delivering it.

### Finding Description
The dispatch sites documented in `docs/outbound-request-incentivization.md` (lines 9-11) explicitly state:

> "hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }`... Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism." [1](#0-0) 

The most directly reachable-by-unprivileged-actor instance is `modules/pallets/relayer/src/withdrawal.rs`: any relayer that has earned fees calls the withdraw extrinsic on the relayer pallet, which internally dispatches an ISMP `PostRequest` to the destination chain instructing the host contract to release the relayer's owed funds [2](#0-1) . That request is dispatched with zero fee/payer just like the other system messages, so — absent the mitigating fix below — no relayer (including a third-party relayer other than the withdrawer) has any economic reason to actually deliver it to the destination chain, analogous to nobody being incentivized to call `warn()` in Aloe.

The protocol team is aware of this and has built a mitigation: a governance-set, per-`module_id` `OutboundRequestDeliveryReward` allowlist plus a `claim_outbound_request_delivery_reward` extrinsic that pays BRIDGE from the treasury to whoever delivers and proves delivery of a hyperbridge-originated request [3](#0-2) . Critically, this reward is **zero by default** for every module — "0 (the default) means both 'no reward' and 'module not on the allowlist'" [4](#0-3) , and "governance enables a module by setting a non-zero reward" [5](#0-4) . Until an admin/governance explicitly calls `set_outbound_request_delivery_reward` for a given `module_id` (e.g. the relayer-withdrawal module, or any newly added system module such as "bandwidth"), the relayer-withdrawal request, host-executive update, or token-governor message dispatched by that module remains a zero-fee, zero-incentive message that rational relayers will not pick up — exactly the "no incentive to call warn" scenario, but here the un-incentivized step is "deliver the withdrawal/system request" rather than "warn the borrower."

### Impact Explanation
If a relayer's withdrawal request (or a host-executive / token-governor system message) is never delivered because no third party is economically motivated to relay it, the funds/parameter update it represents are effectively frozen indefinitely — the relayer cannot get their earned fees released on the destination chain, and system-critical configuration/mint/burn messages never land. This matches the accepted Medium-severity classification of the Aloe finding ("no incentive to call function X leads to loss/freezing of funds") since the withdrawal message carries real value (a relayer's earned fees) and has no timeout, so it can sit un-relayed forever.

### Likelihood Explanation
The likelihood is tied entirely to whether governance has proactively registered a non-zero reward for every module that dispatches hyperbridge-originated requests. New modules (per the doc, "future modules like bandwidth") default to zero reward. Any window between a module going live and governance registering its reward — or any oversight where a module is simply never added to the allowlist — reproduces the exact unincentivized-relaying condition. Because the reward pallet code and design already exist (confirmed in `modules/pallets/relayer/src/outbound_request.rs` and `lib.rs`), this is a partially-mitigated but not structurally-closed issue: it depends on continuous, correct governance configuration rather than a protocol invariant.

### Recommendation
- Do not let hyperbridge-originated dispatches default to a zero reward; either require a non-zero reward to be set atomically when a new dispatching pallet/module is added to the runtime, or fund a baseline default reward from protocol treasury automatically for all `IsmpDispatcher::dispatch_request` calls that have `payer == [0u8;32]`.
- Add invariant checks/tests (e.g., a runtime genesis or migration check) asserting that `OutboundRequestDeliveryReward` is non-zero for the relayer-withdrawal module_id and other known system module_ids before those pallets are enabled.
- Consider allowing the withdrawing relayer to self-fund the fee for their own withdrawal (attach a real, non-zero, refundable fee at withdrawal time from their own already-accumulated balance) rather than depending on a separate treasury-funded reward mechanism gated by governance.

### Proof of Concept
1. Deploy/enable a new hyperbridge-originated dispatching module (or observe that the relayer-withdrawal module's `OutboundRequestDeliveryReward` has not yet been set by governance to a non-zero amount) — confirmed default is zero per `OutboundRequestDeliveryReward<T>::insert` only being called via `set_outbound_request_delivery_reward`, which requires `T::RelayerOrigin::ensure_origin` (governance/root) [6](#0-5) .
2. An ordinary relayer calls the relayer pallet's withdraw extrinsic to claim previously accumulated fees, which dispatches a zero-fee `PostRequest` to the destination chain [2](#0-1) .
3. Because `OutboundRequestDeliveryReward[relayer_module_id] == 0`, `retain_incentivized_requests` drops the request off-chain (gas-saving optimization) and even if forced through, `process_outbound_request_delivery_claim` rejects any claim attempt with `OutboundRequestNoRewardConfigured` [7](#0-6) [8](#0-7) .
4. No relayer has economic incentive to deliver the withdrawal message to the destination chain (message carries zero fee), so it is never delivered, and the withdrawing relayer's earned funds remain locked/unreleased on the destination chain indefinitely — the same "no incentive to perform the prerequisite step" failure mode as Aloe's unincentivized `warn()` call leading to un-liquidatable, loss-accruing borrower positions.

To initiate a withdrawal from hyperbridge, a relayer needs to submit a transaction to hyperbridge which triggers the withdrawal request. This extrinsic is unsigned and will not require any native tokens for execution fees. Once the extrinsic is executed, hyperbridge dispatches a POST request that when executed on its destination, will provide the relayer with the fees they've accrued. The relayer account must have sufficient funds to deliver this request to its destination chain.

		/// Pay the configured `OutboundRequestDeliveryReward` to the relayer
		/// that delivered a hyperbridge-originated request to the destination.
		///
		/// Unsigned. Spam-protected by `validate_unsigned` (the encoded
		/// payload becomes a unique tag, so a duplicate submission with the
		/// same `commitment` is rejected at the txpool stage).
		#[pallet::call_index(5)]
		#[pallet::weight({1_000_000})]
		pub fn claim_outbound_request_delivery_reward(
			origin: OriginFor<T>,
			claim: OutboundRequestDeliveryClaim,
		) -> DispatchResult {
			ensure_none(origin)?;
			Self::process_outbound_request_delivery_claim(claim)
		}

		/// Governance-set per-`module_id` reward for delivering a
		/// hyperbridge-originated request from that module. Setting
		/// `amount = 0` removes the module from the allowlist.
		#[pallet::call_index(6)]
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 1))]
		pub fn set_outbound_request_delivery_reward(
			origin: OriginFor<T>,
			module_id: BoundedVec<u8, ModuleIdBound>,
			amount: BalanceOf<T>,
		) -> DispatchResult {
			T::RelayerOrigin::ensure_origin(origin)?;
			OutboundRequestDeliveryReward::<T>::insert(&module_id, amount);
			Self::deposit_event(Event::OutboundRequestDeliveryRewardUpdated {
				module_id,
				new_reward: amount,
			});
			Ok(())
		}
