### Title
Launched Token / LT sent directly to `FeeVault` (or `Zap`/`Bonding`) is permanently stuck — no rescue path exists - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault` (and `Zap`/`Bonding`) accept and hold funds without any general mechanism to recover an unsupported ERC20 that lands there outside the intended fee-accrual flow. Every recovery function in `FeeVault` — `claim`, `claimProtocol`, `sweepDonations` — is hard-typed to the vault's single recognized asset, `$.usdc`. A launched `Token` or the reserve `LT`, which are both ordinary ERC20s that any unprivileged trader can `transfer` directly to `FeeVault`'s address (e.g. by mistake, or by copy/pasting the wrong recipient instead of calling `Zap.sell`), is invisible to the vault's accounting and has zero withdrawal path — exactly the "unsupported deposited token" freeze pattern described in the external `VaultBooster.deposit` report, except here the destination contract doesn't even have an owner-only sweep-to-owner escape hatch for arbitrary tokens the way `VaultBooster.withdraw` does.

### Finding Description
`FeeVault`'s three fund-moving functions are all scoped to `$.usdc`: [1](#0-0) [2](#0-1) [3](#0-2) 

`sweepDonations` is the only function that even acknowledges "unbacked" balances, but it computes `backed`/`balance` purely against `$.usdc.balanceOf(address(this))` — a directly-transferred `Token` or `LT` never enters this calculation at all, so it is neither claimable by a creator/protocol nor sweepable by the owner. There is no `rescueERC20`/`recoverToken` function anywhere in `FeeVault.sol`.

The same gap exists in `Zap.sol` and `Bonding.sol`: their token-moving logic (`_executeBuy`, `_sellInternal`, `_accrueFee`, `launch`, `finalizeGraduation`) is entirely keyed off the specific `tokenAddress`/`lt` pair being traded or graduated at that moment; `Bonding._sweepLTToOwner` only fires for the specific LT of a graduation *in progress* inside `finalizeGraduation`, and only for the LT of that particular token — it does not cover a `Token` or `LT` sent to `Bonding` outside a graduation, nor tokens sent to `Zap` at all. Neither contract exposes an owner-only rescue for arbitrary stray ERC20 balances, unlike `VaultBooster`'s confirmed `withdraw(token, amount)` (which at least lets the owner recover the stuck asset, even if not back to the original depositor).

This mirrors the root cause in the external report precisely: a contract that can receive an ERC20 transfer with no validation of "is this token supported by my accounting" and no recovery mechanism once it lands.

### Impact Explanation
Any trader or creator who sends a launched `Token` or the reserve `LT` directly to `FeeVault` (or to `Zap`/`Bonding` outside the exact buy/sell/graduation call that consumes it) permanently loses those tokens: they are not tracked by any balance mapping, they cannot be claimed via `claim`/`claimProtocol`, and `sweepDonations` cannot see or move them because it only inspects the vault's `usdc()` balance. This is a permanent freeze of trader/creator funds with no on-chain recovery path — the accepted class of impact for this bug family, matching the confirmed severity of the analogous `VaultBooster` M-11 finding.

### Likelihood Explanation
Reachable purely by an unprivileged trader/creator submitting a standard ERC20 `transfer` call — no special privileges, no timing dependency, no interaction with any other protocol component required. The likelihood is bounded by user behavior (accidentally or mistakenly sending tokens to a contract address instead of calling `Zap.sell`), which is the same trigger condition that was accepted as valid in the original `VaultBooster` disclosure.

### Recommendation
Add an `onlyOwner` rescue function to `FeeVault` (and consider the same for `Zap`/`Bonding` for balances outside their active trade/graduation working set) that can `safeTransfer` any ERC20 token that is not `$.usdc` out of the contract to a specified recipient (or, at minimum, to `feeTo`), e.g.:
```solidity
function rescueERC20(IERC20 token, address to, uint256 amount) external onlyOwner {
    if (address(token) == address(_s().usdc)) revert InvalidInput(); // usdc goes through sweepDonations
    token.safeTransfer(to, amount);
}
```
This closes the freeze without weakening the existing USDC accrual/underfund invariants.

### Proof of Concept
1. A launched `Token` (or the LT reserve asset) is a standard ERC20 that any holder can call `transfer` on.
2. User calls `Token(tokenAddress).transfer(feeVaultAddress, amount)` directly (bypassing `Zap.sell`).
3. `FeeVault.claim()`/`claimProtocol()` only ever move `$.usdc` and are keyed to `creatorBalance`/`protocolBalance`, both of which are untouched by this transfer — see [4](#0-3) .
4. `sweepDonations()` computes `balance = $.usdc.balanceOf(address(this))`, which does not include the `Token`/`LT` balance at all — see [3](#0-2) .
5. No other function in `FeeVault.sol` references any ERC20 other than `$.usdc`. The transferred `Token`/`LT` sits in `FeeVault` forever, unrecoverable by the sender or the owner.

**Uncertainty note:** I was not able to fully read `Pair.sol`, `Router.sol`, `Factory.sol`, or `Token.sol` in this pass (time/tooling budget), so I cannot rule out an existing rescue function there; based on everything reviewed in `FeeVault.sol`, `Zap.sol`, and `Bonding.sol`, no general-purpose stray-ERC20 rescue exists in those three contracts.

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;

        emit CreatorFeesClaimed(msg.sender, amount);

    function claimProtocol() external nonReentrant returns (uint256 amount) {

        amount = $.protocolBalance;
        if (amount == 0) revert NothingToClaim();
        $.protocolBalance = 0;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit ProtocolFeesClaimed(feeTo_, amount);
    }

    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
