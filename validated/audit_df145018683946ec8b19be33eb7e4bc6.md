Audit Report

## Title
Unbounded GraphQL pagination `limit` allows resource-exhaustion (DoS) via authenticated "view"-role queries - ([File: core/web/resolver/query.go])

## Summary
The GraphQL pagination helper `pageLimit` converts a client-supplied `*int32` limit directly to an `int` with no maximum bound, and this value flows unchecked into ORM queries (`Bridges`, `Jobs`, `Nodes`, `JobRuns`, `EthTransactions`, etc.) that are reachable by any authenticated user via the minimal `authenticateUser` check, which grants access regardless of role (including the lowest "view" role). This allows a low-privileged authenticated client to request an arbitrarily large `LIMIT` (e.g. `2147483647`), which is passed straight through to backend ORM/SQL calls and could cause excessive memory/DB load.

## Finding Description
`pageLimit` performs no validation or capping of the client-supplied value: [1](#0-0) . This is used by numerous resolvers that only require `authenticateUser`, a check that succeeds for any authenticated session regardless of role, explicitly documented as granting "view" access: [2](#0-1) . Resolvers such as `Bridges`, `Nodes`, `JobRuns`, and `EthTransactions` all forward the unclamped `limit` into ORM calls like `r.App.JobORM().PipelineRuns(ctx, nil, offset, limit)` or `r.App.TxmStorageService().Transactions(ctx, offset, limit)` with no intermediate bound check, confirmed by inspection of `core/web/resolver/query.go` (Bridges L50-67, Nodes L389-413, JobRuns L415-432, EthTransactions L536-553). No query-complexity or max-query-length middleware was found guarding the GraphQL server (no matches for `MaxQueryComplexity`, `QueryComplexity`, or similar), and no cap constant like `MaxPageLimit` exists alongside `PageDefaultLimit` in `core/web/resolver/helpers.go`. This confirms the root cause: an unbounded, attacker-controlled size parameter reaches backend paginated queries under only the lowest privilege tier.

## Impact Explanation
This maps to a resource-exhaustion / denial-of-service concern for the node's authenticated operator API. An authenticated user holding only the "view" role (the minimum role recognized by the RBAC model) can request maximal-size result sets, causing the backend ORM/SQL layer to build very large `LIMIT` clauses and marshal large JSON responses. The actual blast radius depends on downstream SQL `LIMIT` behavior and any DB/connection-level protections (e.g., statement timeouts), which could not be fully verified in this pass — I was unable to retrieve the exact `PipelineRuns` SQL implementation in `core/services/job/orm.go` to confirm whether the `limit` is inserted verbatim into a `LIMIT` clause with no server-side cap. Given the pattern (raw `int` limit passed to a paginated ORM method), it is reasonable to expect it maps into a SQL `LIMIT`, but this specific query text was not directly confirmed due to tool budget exhaustion.

## Likelihood Explanation
Exploitation requires only a normal authenticated session — no admin/edit/run privilege, no host or DB access, and no social engineering — matching the minimal-credential bar for a valid finding. The GraphQL query itself is trivial to construct and repeatable. This is a genuine, low-effort, authenticated-but-unprivileged-triggerable issue, consistent with an in-scope DoS/resource-exhaustion impact class rather than an operator/admin-only or host-level issue.

## Recommendation
Introduce a `MaxPageLimit` constant in `core/web/resolver/helpers.go` and clamp/reject any client-supplied `limit` exceeding it inside `pageLimit`, returning a GraphQL error for out-of-range requests. Apply the same server-side maximum uniformly across all paginated resolvers (`Bridges`, `Jobs`, `Nodes`, `JobRuns`, `EthTransactions`, `EthTransactionsAttempts`) and the legacy REST pagination helper `ParsePaginatedRequest` in `core/web/api.go`, which has the same missing upper-bound validation.

## Proof of Concept
As a session authenticated with only the "view" role, submit to the node's GraphQL `/query` endpoint:
```graphql
{
  jobRuns(limit: 2147483647) {
    results { id }
  }
}
```
This flows through `JobRuns` → `pageLimit(args.Limit)` (no cap) → `r.App.JobORM().PipelineRuns(ctx, nil, offset, limit)`, per `core/web/resolver/query.go` (L415-432) and `core/web/resolver/helpers.go` (L43-51), with no authorization check beyond `authenticateUser` (L11-17 of `core/web/resolver/auth.go`) and no complexity/size middleware detected in the GraphQL server setup. A concrete Go integration test would call the `JobRuns` resolver (or hit the `/query` HTTP endpoint) with a "view"-role session and an extreme `limit` value, asserting that the request either succeeds (confirming the vulnerability) or is now rejected/clamped after the fix.

```go
// pageLimit returns the default page limit if nil, otherwise it returns the
// provided limit.
func pageLimit(limit *int32) int {
	if limit == nil {
		return PageDefaultLimit
	}

	return int(*limit)
}
```
