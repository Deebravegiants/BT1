This confirms the root cause: the gem's own documentation explicitly instructs developers to trust `data.shop` as the tenant identifier returned from `ShopifyAPI::Webhooks::Registry.process`, while `Utils::HmacValidator.validate` (invoked in `lib/shopify_api/webhooks/registry.rb`) only authenticates the raw request body, never the `shop-domain` header that `Request#shop` returns.

### Title
Webhook tenant identity (`shop`) is derived from an HMAC-unauthenticated header, breaking the shop-authenticated = shop-acted-upon binding - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the webhook's raw body via HMAC, but delivers the `shop` value taken from an unauthenticated HTTP header to the app's handler as the trusted tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) authenticates solely the body bytes with `Context.api_secret_key`: [1](#0-0) [2](#0-1) 

Separately, `Request#shop` simply reads the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then constructs `WebhookMetadata` using that unauthenticated `request.shop` value, handing it to the app-supplied handler as the identified tenant: [4](#0-3) 

The gem's own documentation instructs developers to trust `data.shop` directly as "The shop domain of the webhook" for dispatching per-tenant work, with no guidance to cross-check it against anything else: [5](#0-4) 

The broken binding is: `shop_authenticated_by_hmac == shop_used_by_handler`. In truth, since the app's `api_secret_key` (and thus the HMAC) is shared across *all* shops that install the app, any two webhook deliveries with identical raw bodies produce identical valid HMACs, regardless of which shop they claim to be from. Many webhook topics have bodies that don't embed the shop's `myshopify.com` domain (e.g. small/generic payloads, metafield/format-filtered payloads via the `fields` feature described in the docs, or topics like `app/uninstalled`/`shop/redact` with minimal or predictable bodies). An unprivileged internet user who controls one shop that has the app installed can capture a legitimate `(raw_body, hmac)` pair delivered to their own webhook endpoint, then replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary victim's `shop-domain` header value. `HmacValidator.validate` still passes (body unchanged), and `WebhookMetadata#shop` reports the attacker-chosen victim shop, causing the host app to process/store attacker-controlled webhook data under another tenant's identity.

### Impact Explanation
This breaks tenant isolation for webhook processing: an app relying on `data.shop` (as instructed by the gem's docs) to select which merchant's record/session to update would apply attacker-controlled data (or trigger tenant-specific side effects, e.g. `app/uninstalled` cleanup, `customers/redact`) against a victim shop it never sent the corresponding event for. This is a cross-tenant access impact.

### Likelihood Explanation
Likelihood is limited by the practical requirement that the attacker find or produce a webhook body that is topic-generic/predictable enough to not encode their own shop's identity (achievable for several topics and via the `fields`/filter customization described in the docs), and that they control at least one shop with the app installed to obtain a valid `(body, hmac)` pair — both of which are available to any unprivileged app-installing user, requiring no secrets, tokens, or privileged access.

### Recommendation
Do not treat the `shop-domain` header as trusted merely because the body's HMAC validates. Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or require the caller/host app to independently verify `request.shop` against a shop that is actually registered/subscribed for that specific webhook (e.g. compare to a known list of installed shops before dispatching), rather than exposing `WebhookMetadata#shop` as an implicitly-authenticated value straight from an unauthenticated header.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook (e.g. `app/uninstalled` with body `{}` or another topic filtered down via `fields`/`filter` to a fixed, shop-agnostic body) to the app's public endpoint, capturing the raw body and the valid `X-Shopify-Hmac-Sha256` header value.
2. Attacker sends a forged HTTP POST to the same app endpoint with the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the signed material is only the (unchanged) body: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, and the app performs tenant-scoped actions against the victim shop as instructed by the docs' example (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), even though the victim shop never sent this webhook.
