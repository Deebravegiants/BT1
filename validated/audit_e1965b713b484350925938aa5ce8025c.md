### Title
Webhook `shop` identity is read from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking the HMAC over the raw request body only, but the shop identity handed to the application's handler is taken verbatim from the `shop-domain` HTTP header, which is not covered by that signature at all.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string using `Context.api_secret_key` [2](#0-1) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) with no cryptographic binding to the signed bytes [3](#0-2) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body signature) and then forwards `request.shop` unchanged into `WebhookMetadata` that is passed to the app's handler as the authenticated tenant identity: [4](#0-3) . The `WebhookMetadata#shop` field is documented as "The shop domain of the webhook" and is the value app developers are expected to use to scope per-tenant data/session lookups [5](#0-4) [6](#0-5) .

The identity binding that should hold is: `shop_used_by_handler == shop_that_signing_secret_authenticated`. In this gem it instead holds: `shop_used_by_handler == header_value_never_covered_by_hmac`. Any two shops that are both merchants of the same app share the same `Context.api_secret_key`. A caller who has obtained one valid `(raw_body, hmac)` pair for Shop A (e.g., a legitimate webhook delivery, or any request body/HMAC combination they can compute-check, since this gem's own tests show the HMAC is computed over `"{}"` independent of shop) can resubmit that same body/HMAC while substituting the `shop-domain` header with Shop B's domain. `Registry.process` will validate successfully — the HMAC check never inspects the header — and the handler will be invoked with `data.shop == "shop-b.myshopify.com"` even though nothing shop-specific was ever verified.

### Impact Explanation
This breaks the tenant-identity binding that host applications rely on when using this gem's documented webhook API. Handlers that key session/data lookups off `WebhookMetadata#shop` (as explicitly recommended in the gem's own documentation and `BREAKING_CHANGES_FOR_V15.md` migration guide) can be made to process arbitrary body content under an attacker-chosen shop domain, causing cross-tenant data confusion (e.g., writing/deleting data attributed to the wrong merchant, or triggering mandatory `shop/redact` / `customers/redact` / `customers/data_request` processing for a shop that never actually sent the request). This qualifies as cross-tenant access per the impact criteria.

### Likelihood Explanation
Exploitability only requires network access to the app's public webhook endpoint plus knowledge of any single valid `(raw_body, hmac)` pair for the shared `api_secret_key` — no leaked credentials, TLS interception, or privileged account needed. Since the HMAC is computed purely over the JSON body and the shared app secret (independent of shop), and this gem performs no additional binding of headers to the signature, the header can be freely substituted by an unprivileged internet user who can reach the endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) as part of the signed/verified payload, or otherwise cryptographically bind them to the HMAC before trusting them, rather than deriving `WebhookMetadata#shop` solely from an unauthenticated header. At minimum, document prominently that `data.shop` from `WebhookMetadata` is not authenticated by the HMAC check and must not be trusted for tenant-scoping without additional verification (e.g., cross-checking against a known/registered shop for a stored session).

### Proof of Concept
1. App has one `api_secret_key` shared across all installed shops (standard Shopify OAuth model).
2. Attacker captures/derives a valid `hmac-sha256` for body `"{}"` (as shown in this repo's own test fixtures, `OpenSSL::HMAC.digest(sha256, api_secret_key, "{}")` [7](#0-6) ), which is valid for any shop since the shop header plays no part in the signature.
3. Attacker POSTs to the app's webhook endpoint with headers `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <that hmac>`, `x-shopify-shop-domain: victim-shop.myshopify.com`, and body `"{}"`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because it only checks the body [8](#0-7) , then invokes the handler with `data.shop == "victim-shop.myshopify.com"` [9](#0-8) , even though the request was never actually issued by or verified against `victim-shop`.
