### Title
`remove_account` (DeleteAccount) fails to clean up `PromiseYieldReceipt`/`PromiseYieldStatus`/`PostponedReceipt`/`PendingDataCount`/`ReceivedData` entries left in state - (File: `core/store/src/utils/mod.rs`)

### Summary
This is the same bug class as the Visor `transferERC721` finding: a "delete/consume" code path (`remove_account`, used by `DeleteAccountAction`) cleans up some per-account keyed bookkeeping (the `Account` record, contract code, access keys, gas-key nonces, contract data) but omits other per-account keyed bookkeeping tied to cross-receipt async state (`PromiseYieldReceipt`, `PromiseYieldStatus`, `PostponedReceipt`/`PostponedReceiptId`, `PendingDataCount`, `ReceivedData`). These entries remain in the trie, keyed by `account_id`, after the account is deleted.

### Finding Description
`remove_account` in [1](#0-0)  explicitly removes `TrieKey::Account`, `TrieKey::ContractCode`, all `TrieKey::AccessKey`/gas-key-nonce entries, and `TrieKey::ContractData` entries for the account, but never iterates or removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::ReceivedData` keyed to that `account_id`.

`action_delete_account` in [2](#0-1)  calls `remove_account` and only checks storage-usage size and gas-key balance thresholds before deleting; it performs no check for outstanding postponed receipts, pending data counts, or parked `PromiseYield` receipts belonging to the account being deleted.

Compare this to the `PromiseResume` handling path, which *does* correctly clean up all yield-related keys when a yield naturally resolves (`remove_promise_yield_receipt`, `remove_promise_yield_status`, `remove_yield_id_mappings`) — see [3](#0-2) . This shows the protocol design expects these entries to always be cleaned up when consumed/superseded — exactly the "some paths clean it, one path doesn't" pattern from the ERC721 report (`timeUnlockERC721` cleans `timelockERC721s`, `transferERC721` doesn't).

If an account with a pending `PromiseYieldReceipt` (an action receipt parked awaiting a `promise_yield_resume`) or a `PostponedReceipt` (an action receipt awaiting `input_data_ids`) is deleted, those entries are orphaned in the trie under that `account_id` rather than removed.

### Impact Explanation
The account model allows deleted account ids to be recreated later (e.g., via `CreateAccountAction` for named sub-accounts, or implicit-account creation for the same derived id in edge cases). If the account_id is recreated and a `PromiseResume`/`Data` receipt with a matching `data_id` subsequently arrives (e.g., an in-flight resume/timeout receipt that was already in transit when the account was deleted, or a stale receipt reprocessed after resharding/GC edge cases), the runtime will find the orphaned `PromiseYieldReceipt`/`PostponedReceipt` under the (now different) account and execute it — an action receipt that the current account owner never authorized, running with the new account's state/actor context. This is an unauthorized state/action execution analogous to reusing a stale timelock key against the wrong owner. Additionally, orphaned `ReceivedData`/`PendingDataCount` entries permanently bloat state (never garbage collected, since nothing ever visits or removes them once the parent postponed receipt path is broken), representing unbounded/unaccounted state growth not covered by the account's own storage-staking accounting (the account no longer exists to pay for it).

### Likelihood Explanation
Reaching this requires: (1) an account has an in-flight parked yield or postponed action receipt, (2) a `DeleteAccount` action deletes that account (which is permitted — the only actor-permission requirement is no locked stake and storage-usage size caps; there is no check against pending yields/postponed receipts), and (3) the vacated account_id is later reused (sub-account re-creation is straightforward since `CreateAccount` has no uniqueness check beyond a fresh `Account` write) or a same-shard in-flight resume/timeout receipt lands afterward. Steps (1) and (2) are fully controllable by any unprivileged account owner via ordinary transactions; step (3) requires either account_id reuse or timing races on in-flight cross-shard/parked receipts, which is plausible but not guaranteed on every attempt.

### Recommendation
When executing `DeleteAccountAction`, either:
- Reject deletion if the account has any outstanding `PromiseYieldReceipt`, `PromiseYieldStatus`, `PostponedReceipt`/`PostponedReceiptId`, or `PendingDataCount` entries (mirroring the existing "must not be staking" check), or
- Extend `remove_account` to enumerate and delete all such entries under the account's key prefix (the same iterate-and-remove pattern already used for access keys and contract data at [4](#0-3) ), including any `ReceivedData` entries.

### Proof of Concept
1. Account `A` creates a `PromiseYield`/awaits a callback with an unmet `input_data_id`, causing the runtime to store a `PostponedReceipt`/`PendingDataCount` (or `PromiseYieldReceipt`/`PromiseYieldStatus`) keyed to `A` via `set_postponed_receipt`/`set_promise_yield_receipt` (see [5](#0-4) ).
2. Before the dependency resolves, `A` submits `DeleteAccountAction`; `action_delete_account` succeeds (no check blocks it) and calls `remove_account`, which does not remove the postponed/yield keys ( [1](#0-0) ).
3. `A`'s account_id is recreated (e.g., as a fresh sub-account or via account_id reuse) with different owner/keys.
4. The originally in-flight `Data`/`PromiseResume` receipt (or a maliciously crafted one, if `receiver_shard_id`/timing allow) arrives and matches the stale `data_id`/`receipt_id`; the runtime finds the orphaned postponed/yield receipt still present under `A` and executes it against the new account state, an action neither authorized nor expected by the new owner. Full exploitation would need to be verified via an integration test that interleaves `DeleteAccountAction` with a pending yield/postponed receipt and subsequent account recreation, which is outside available static-analysis confirmation here.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
