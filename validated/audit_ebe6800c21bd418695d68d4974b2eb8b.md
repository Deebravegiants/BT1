### Title
Cross-Chain Decimal Mismatch in `HyperFungibleToken`/`WrappedHyperFungibleToken` Causes Silent Value Corruption on Mint - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
The `HyperFungibleToken` / `WrappedHyperFungibleToken` EVM bridge apps treat the `amount` field in the ISMP `Message` payload as a raw integer with no decimal metadata, validation, or scaling anywhere in the Solidity contracts. When the underlying/local token decimals differ between the two EVM deployments of the same logical asset (e.g. `WrappedHyperFungibleToken` locking a 6-decimal ERC20 on the home chain while `HyperFungibleToken` mints on a remote chain with 18 decimals), every cross-chain transfer silently destroys or inflates value.

### Finding Description
`HyperFungibleToken.Message` carries only `from`, `to`, `amount`, `data` — no decimals field: [1](#0-0) 

`ConfigOptions` for the contract stores only `host` and `dispatcher` — no local or remote decimals: [2](#0-1) 

On `onAccept`, the raw `message.amount` decoded from the incoming payload is minted directly with zero rescaling: [3](#0-2) 

`WrappedHyperFungibleToken.onAccept` similarly transfers/unwraps the raw `message.amount` of the underlying ERC20 with no decimal conversion: [4](#0-3) 

A `grep` for `decimals` across every file in `sdk/packages/core/contracts/apps/*.sol` returns matches only in `IntentPriceOracle.sol` — confirming `HyperFungibleToken.sol` and `WrappedHyperFungibleToken.sol` contain no decimal-awareness whatsoever.

By contrast, the parallel Substrate leg of the same architecture, `pallet-hyper-fungible-token`, explicitly recognizes this exact bug class and mitigates it: it stores per-`(AssetId, StateMachine)` EVM decimals in the `Precisions` storage map, and every send/receive path rescales the amount via `convert_to_erc20`/`convert_to_balance` before encoding/after decoding: [5](#0-4) [6](#0-5) [7](#0-6) 

This confirms the project is aware of and deliberately engineers around this bug class for the substrate↔EVM leg, but the pure EVM↔EVM leg (`HyperFungibleToken` deployed on multiple EVM chains, or paired with `WrappedHyperFungibleToken` locking a real ERC20 of arbitrary decimals) has no equivalent safeguard. The foundry test comments even acknowledge decimal mismatches exist across legs of the same architecture ("18 here while BRIDGE is 12 decimals on nexus, so the pallet scales by 10^6 in both directions"): [8](#0-7) 
— but no such scaling exists for `HyperFungibleToken`/`WrappedHyperFungibleToken` on the pure-EVM path.

### Impact Explanation
If a `WrappedHyperFungibleToken` on a home chain locks an underlying ERC20 with fewer decimals (e.g. 6-decimal USDC) while a peer `HyperFungibleToken` on a remote EVM chain mints its own ERC20 with the OpenZeppelin default of 18 decimals, every `send()`/`onAccept()` round trip either destroys ~10^12 of the transferred value or mints ~10^12x more tokens than were locked, depending on direction. This is an unbacked-mint / permanent-value-destruction class bug reachable by any ordinary user calling `send()` — exactly the class the external report flags, and it maps onto the "token bridge mint/burn" reachable surface.

### Likelihood Explanation
Reachable by any unprivileged token bridger via a single `send()` call once the admin has deployed/configured peer `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts with differing token decimals — no attacker privilege beyond a normal transfer is required, and the underlying misconfiguration is not validated or rejected anywhere in the contract or the pallet's peer registration flow (`addChain`), which stores only the contract address, not decimals.

### Recommendation
Add a `decimals` field (local decimals and/or remote/expected decimals) to `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `ConfigOptions`/`addChain` registration, matching the pattern already implemented in `pallet-hyper-fungible-token`'s `Precisions` storage. On `send()`, normalize the local raw amount to a canonical precision before encoding into `Message.amount`; on `onAccept()`, denormalize from canonical precision to the local token's actual decimals before minting/transferring. Reject configuration/registration calls where decimals cannot be verified, mirroring `pallet-hyper-fungible-token::Error::DecimalsNotFound`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A wrapping an ERC20 with 6 decimals (e.g. USDC-like token) — see the underlying-token lock/unlock logic in `WrappedHyperFungibleToken.sol` (`onAccept` at lines 301-336).
2. Deploy `HyperFungibleToken` on chain B, which per `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` inherits standard ERC20 with default 18 decimals; register the peer via `addChain` (no decimals recorded).
3. User calls `send()` on chain A with `amount = 1_000_000` (1.0 token at 6 decimals); the underlying ERC20 is locked and `Message.amount = 1_000_000` is dispatched raw.
4. `onAccept` on chain B (`HyperFungibleToken.sol` lines 292-313) mints `1_000_000` raw units to the recipient, which at 18 decimals equals `0.000000000001` tokens — 99.9999999999% of value destroyed. The reverse direction (send from 18-decimal chain B, receive on 6-decimal chain A) causes ~10^12x inflation upon unlock.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
